Based on my analysis, I found a confirmed candidate: when `buildRevertOutbound` (`x/uexecutor/keeper/build_revert_outbound.go`) fails to fetch gas info from `UniversalCore.getOutboundTxGasAndFees` (which reverts if e.g. `baseGasLimitByChainNamespace`/gas-token config is unset or the contract call otherwise fails), it logs a warning and returns the outbound with `GasPrice`/`GasFee`/`GasLimit` left as empty strings. That `INBOUND_REVERT` outbound is then persisted as `Status_PENDING` and indexed in `PendingOutbounds`. On the universalClient side, `TxBuilder.GetOutboundSigningRequest` (`universalClient/chains/evm/tx_builder.go:98-106`) unconditionally rejects any outbound whose `GasPrice` is zero/empty with `"gas price is zero or missing in outbound event"`. Since `x/uexecutor/README.md` documents that `PendingOutbounds` entries are **never automatically removed except by validator quorum** (no ballot-expiry cleanup, no auto-retry, no auto-refund — by explicit design, to avoid double-pay/double-delivery risk), an outbound that can never produce a valid signing request is stuck forever: it can never be signed, never voted, and never cleared from `PendingOutbounds`, permanently freezing the user's revert/refund funds with no on-chain recovery path.

This is reachable by an ordinary unprivileged user simply triggering any inbound deposit failure that requires a revert (e.g., `GAS` swap failure, `FUNDS_AND_PAYLOAD` pre-deposit failure) on any chain/token combination for which the `UniversalCore` contract's per-chain gas config (`baseGasLimitByChainNamespace`, `gasTokenPRC20ByChainNamespace`) is unset or that specific view call reverts — no validator or admin misbehavior is required, and no privileged action is needed to trigger it once such a config gap exists for a chain.

### Title
Permanent freeze of INBOUND_REVERT outbound funds when UniversalCore gas-fee lookup fails - (File: x/uexecutor/keeper/build_revert_outbound.go)

### Summary
`buildRevertOutbound` gracefully "degrades" by omitting gas fields when the `UniversalCore.getOutboundTxGasAndFees` EVM call fails, but this degraded `OutboundTx` is unbroadcastable: `GetOutboundSigningRequest` hard-rejects a zero/empty `GasPrice`, and per the documented `PendingOutbounds` lifecycle, such stuck outbounds are never auto-cleared, retried, or refunded.

### Finding Description
`buildRevertOutbound` at <cite repo="patrichyt/push-chain-node--008" path="x/uexecutor/keeper/build_revert_outbound.go" start="38,48" end="48,48" /> calls `GetGasFeeInfoForRevertOutbound`, which wraps a read-only `CallEVM` to `UniversalCore.getOutboundTxGasAndFees` <cite repo="patrichyt/push-chain-node--008" path="x/uexecutor/keeper/gas_fee.go" start="26,40" end="40,40" />. If this call errors for any reason (missing per-chain config in `UniversalCore`, a logical revert in the contract, or any transient EVM failure), the function logs a warning and returns the `OutboundTx` unchanged, leaving `GasToken`, `GasFee`, `GasPrice`, and `GasLimit` as empty strings <cite repo="patrichyt/push-chain-node--008" path="x/uexecutor/keeper/build_revert_outbound.go" start="41,47" end="47,47" />.

This outbound is committed as `Status_PENDING` and indexed in `PendingOutbounds` through the normal inbound-failure/revert path (e.g. `ExecuteInboundGas`, `ExecuteInboundGasAndPayload`) whenever `shouldRevert` is set <cite repo="patrichyt/push-chain-node--008" path="x/uexecutor/keeper/execute_inbound_gas_and_payload.go" start="190,209" end="209,209" />.

On the universalClient side, `GetOutboundSigningRequest` unconditionally rejects any outbound event whose `GasPrice` parses to zero: <cite repo="patrichyt/push-chain-node--008" path="universalClient/chains/evm/tx_builder.go" start="98,106" end="106,106" />. This means the TSS coordinator can never produce a valid signing request for this outbound — it can never be signed or broadcast.

Per the documented lifecycle, `PendingOutbounds` entries are removed **only** on validator-vote quorum; ballot expiry does **not** remove them, and there is intentionally no auto-refund or auto-retry mechanism because "auto-refund risks double-pay ... auto-retry risks double-delivery" <cite repo="patrichyt/push-chain-node--008" path="x/uexecutor/README.md" start="273,282" end="282,282" />. Consequently, an outbound that can never even be signed is permanently stuck with no path to resolution other than manual governance intervention outside the protocol's own state machine.

### Impact Explanation
This is a direct analog of the BAMM `thusd2UsdPriceAggregator` bug: an external dependency (here, `UniversalCore`'s per-chain gas configuration) that can revert or return missing data causes the caller to silently degrade to a "safe" default (empty gas fields) that is not actually safe — it produces state that downstream logic cannot process. The result is the same class of impact flagged in the report: permanent freezing of user funds, since the `INBOUND_REVERT` outbound (which exists specifically to return a user's funds after a failed deposit) can never complete.

### Likelihood Explanation
Any unprivileged user can trigger this by causing an inbound execution that requires a revert (e.g. failed auto-swap on the `GAS`/`GAS_AND_PAYLOAD` path, or any pre-deposit failure) for any (source chain, token) pair whose `UniversalCore` gas configuration entry is absent, stale, or whose lookup transiently reverts at the moment of the call. No validator, admin, or attacker-controlled malicious behavior is needed — the trigger is an ordinary user operation combined with a plausible operational/config gap in `UniversalCore`.

### Recommendation
Do not create/commit a `PENDING` `INBOUND_REVERT` outbound with empty gas fields. Instead: (a) fail the revert-outbound construction and retry lazily (e.g., re-attempt the gas-fee lookup on a later block rather than baking in permanently-empty fields), or (b) fall back to a safe, protocol-defined default gas price/limit (analogous to the BAMM fix's 1:1 conversion fallback) so the outbound remains signable, or (c) add an explicit "stuck outbound needing manual gas-field backfill" queryable state and a governance-gated repair message, rather than relying on silent degradation plus an implicit, undocumented dependency between `buildRevertOutbound`'s optimistic omission and `GetOutboundSigningRequest`'s hard rejection.

### Proof of Concept
1. Ensure `UniversalCore`'s per-chain gas config for a given `chainNamespace` (used by `getOutboundTxGasAndFees`) is unset or causes the view call to revert (e.g., a fresh chain onboarded to `x/uregistry` before its `UniversalCore` gas params are configured).
2. As an ordinary user, submit a `GAS` or `GAS_AND_PAYLOAD` inbound whose auto-swap step fails (e.g., insufficient liquidity/slippage on the Uniswap V3 quoter), forcing `shouldRevert = true` in `ExecuteInboundGas`/`ExecuteInboundGasAndPayload`.
3. `buildRevertOutbound` calls `GetGasFeeInfoForRevertOutbound` → `GetOutboundTxGasAndFees`, which errors; the outbound is committed with `GasPrice = ""`.
4. The universalClient's outbound-signing flow calls `GetOutboundSigningRequest`, which returns `"gas price is zero or missing in outbound event"` every tick, forever.
5. The outbound remains `Status_PENDING` in `PendingOutbounds` indefinitely; the user's original funds (meant to be returned via this revert outbound) are permanently unrecoverable through protocol mechanics.
