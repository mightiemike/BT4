### Title
Attached deposit permanently stuck in `WalletContract` when intermediate cross-contract calls fail before reaching the refund logic - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is a `#[payable]` entry point, so any `NearToken` attached by the caller is credited to the wallet contract's own account balance as soon as the transaction/receipt is applied, independent of whether the eventual multi-step promise chain succeeds. The contract only pays this deposit back to the caller in one place — the `PromiseResult::Failed` branch of `rlp_execute_callback` — via `CallerDeposit`. Several other failure branches in the promise chain (`address_check_callback`, `nep_141_storage_balance_callback`) return an error `ExecuteResponse` directly, without forwarding the `caller_deposit` refund logic, leaving the attached deposit permanently stuck in the wallet contract with no recovery path.

### Finding Description
`rlp_execute` accepts an attached deposit (`#[payable]`) and builds a `CallerDeposit` from the execution context to be refunded later if the underlying action fails: [1](#0-0) [2](#0-1) 

For flows requiring a preliminary lookup (e.g. eth-emulated base-token transfers with `address_check`, or ERC-20 transfers needing a NEP-141 `storage_balance_of` check), the promise chain first calls an external contract and only reaches the final refund-capable callback (`rlp_execute_callback`) after that check succeeds: [3](#0-2) 

In the intermediate callbacks, when the *preliminary* cross-contract call itself fails or returns unexpected data, the code returns an `ExecuteResponse { success: false, ... }` directly — it never issues a refund transfer of `caller_deposit` back to the caller: [4](#0-3) [5](#0-4) 

The `caller_deposit` variable is only consulted for a refund inside `rlp_execute_callback`'s `PromiseResult::Failed` arm: [6](#0-5) 

Because the attached NEAR was already credited to the wallet contract's own balance when the original `FunctionCall` action (with deposit) was applied by the runtime, and because none of the early-return error branches in `address_check_callback` / `nep_141_storage_balance_callback` re-attach or forward that value back to the caller, the deposit remains on the wallet contract's account balance with no code path that can later reclaim or redistribute it to the rightful owner. This mirrors the reported pattern in the external report: a failure path that is caught/handled generically (via `try/catch` there, via early-return `PromiseResult::Failed`/`Err` handling here) omits the compensating action needed to return value to its rightful owner, permanently trapping it in the contract.

### Impact Explanation
Any unprivileged caller (the wallet owner or a relayer acting via `rlp_execute`) who attaches a deposit for an ERC-20 transfer to an unregistered NEP-141 receiver, or for an address-check-gated base-token transfer, can lose that deposit permanently if the preliminary lookup call (`storage_balance_of` or the address registrar `lookup`) fails or returns malformed data. The funds are not burned or sent to an attacker, but they become permanently frozen inside the `WalletContract` account with no user- or relayer-triggered mechanism to reclaim them, matching the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires an external dependency call (registrar `lookup` or a NEP-141 `storage_balance_of` call) to fail or return unexpected data at the exact point the deposit hasn't yet been forwarded to its intended destination. This can occur due to the target contract being malicious, buggy, paused, or simply returning malformed/unexpected JSON, all of which are plausible in production usage of the wallet contract's ERC-20/address-check emulation paths.

### Recommendation
In `address_check_callback` and `nep_141_storage_balance_callback`, thread `caller_deposit` through every early-return error branch and issue the same refund transfer that `rlp_execute_callback` performs on `PromiseResult::Failed`, so that any attached deposit is always returned to the caller whenever the multi-step promise chain terminates in failure before the final action executes.

### Proof of Concept
1. Deploy the wallet contract for an eth-implicit account and fund it with an attached deposit via `rlp_execute` encoding an ERC-20 `transfer` action whose `receiver_id` is not yet registered with the target NEP-141 token (so the `nep_141_storage_balance_callback` `None` branch is taken).
2. Make the target token contract's `storage_balance_of` view call fail (e.g., point `target` at a contract that panics or does not implement `storage_balance_of`), or return non-JSON data.
3. `nep_141_storage_balance_callback` receives `PromiseResult::Failed` (or a deserialization error) and returns `ExecuteResponse::success = false` at lines 203–220 without refunding `caller_deposit`.
4. The deposit attached in step 1 remains permanently on the wallet contract's balance; no subsequent call by the user or relayer can recover it, since `caller_deposit` is dropped once the callback returns.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
