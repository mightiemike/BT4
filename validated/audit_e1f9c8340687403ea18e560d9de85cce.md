### Title
Unchecked-length `binary.BigEndian.Uint32` panic on malformed Solana `DestExecData` causes OCR pipeline DoS - ([File: core/capabilities/ccip/ccipsolana/extradatacodec.go])

### Summary
`ExtraDataDecoder.DecodeDestExecDataToMap` in `core/capabilities/ccip/ccipsolana/extradatacodec.go` calls `binary.BigEndian.Uint32(destExecData)` directly on attacker-influenced, untrusted bytes without validating that the slice is at least 4 bytes long. Unlike the sibling `ccipevm.abiDecodeUint32` implementation and the `ccipaptos` implementation (which checks `des.Remaining() != 4`), this Solana codec has no length guard, so a `TokenAmounts[].DestExecData` shorter than 4 bytes will cause a runtime panic (`index out of range`) instead of returning an error.

### Finding Description
`DecodeDestExecDataToMap` is invoked from multiple reachable OCR/CCIP paths whenever a message whose source chain family is Solana (or any lane using this codec, e.g. via `ccipsolana.MessageHasherV1.Hash`, or from OCR execute-report decoding in `core/capabilities/ccip/ocrimpls/svm_contract_transmitter.go`'s `decodeExecData`) is processed. Each `RampTokenAmount.DestExecData` value originates from the on-chain source-chain message and is relayed through CCIP OCR reporting into the node's off-chain plugin logic:
- `ccipsolana.MessageHasherV1.Hash` at `core/capabilities/ccip/ccipsolana/msghasher.go:59` calls `h.extraDataCodec.DecodeTokenAmountDestExecData(ta.DestExecData, ...)` for every token amount in the message, with no length check on `ta.DestExecData` beforehand.
- This delegates through `ExtraDataCodecRegistry.DecodeTokenAmountDestExecData` (`core/capabilities/ccip/common/extradatacodecregistry.go:76`) to the per-chain-family `SourceChainExtraDataCodec`, and for the Solana family that is `ccipsolana.ExtraDataDecoder.DecodeDestExecDataToMap`.
- That function unconditionally executes `binary.BigEndian.Uint32(destExecData)` at `core/capabilities/ccip/ccipsolana/extradatacodec.go:88`, which panics if `len(destExecData) < 4`.
- Contrast with `ccipevm.ExtraDataDecoder.DecodeDestExecDataToMap` (`core/capabilities/ccip/ccipevm/extradatacodec.go:26-30`), which uses `abiDecodeUint32` that returns an error for malformed input, and `ccipaptos.ExtraDataDecoder.DecodeDestExecDataToMap` (`core/capabilities/ccip/ccipaptos/extradatadecoder.go:35-39`), which explicitly checks `des.Remaining() != 4` and returns an error.
- No upstream caller (message hasher, execute/commit report decoding in `ocrimpls`) validates the length of `DestExecData` before calling into the codec, so nothing stops a malformed/short byte slice from reaching the unguarded `binary.BigEndian.Uint32` call.

### Impact Explanation
A panic inside `Hash`/execute-report decoding during OCR commit/execute plugin processing crashes the goroutine processing that report. Since these code paths run inside the node's core OCR/CCIP plugin execution (not isolated per-request handlers with recover), an unrecovered panic can crash the node process or otherwise halt CCIP commit/execute processing for the affected lane, resulting in a denial of service for CCIP message relaying on Solana-sourced lanes. This matches a node-availability / DoS impact class.

### Likelihood Explanation
The precondition is that `TokenAmounts[].DestExecData` for a Solana-sourced (or any lane using `ccipsolana.ExtraDataDecoder`) cross-chain message is attacker-influenced and can be set to fewer than 4 bytes. Since `DestExecData` is chain-specific message payload data relayed from source-chain contract calls, and no strict on-chain enforcement of its exact byte length is verified at this decode layer (only the destination-family codec's own checks would normally catch it, and this one doesn't), an attacker who can trigger a cross-chain message with malformed `DestExecData` (e.g. via a permissionless send on the source chain or a crafted message some source-chain program allows) can reliably trigger this panic. It is deterministic and repeatable given the malformed byte length.

### Recommendation
Add an explicit length check in `ccipsolana.ExtraDataDecoder.DecodeDestExecDataToMap` before calling `binary.BigEndian.Uint32`, mirroring the checks in `ccipevm` and `ccipaptos`, e.g.:
```go
func (d ExtraDataDecoder) DecodeDestExecDataToMap(destExecData cciptypes.Bytes) (map[string]any, error) {
	if len(destExecData) != 4 {
		return nil, fmt.Errorf("dest exec data invalid length: %d, should be 4 bytes", len(destExecData))
	}
	return map[string]any{
		svmDestExecDataKey: binary.BigEndian.Uint32(destExecData),
	}, nil
}
```

func decodeExecData(report ccipocr3.ExecuteReportInfo, codec ccipocr3.ExtraDataCodecBundle) (ccipcommon.ExtraDataDecoded, error) {
	// only one report one message, since this is a stop-gap solution for solana
	if len(report.AbstractReports) != 1 {
		return ccipcommon.ExtraDataDecoded{}, fmt.Errorf("unexpected report length, expected 1, got %d", len(report.AbstractReports))
	}
	if len(report.AbstractReports[0].Messages) != 1 {
		return ccipcommon.ExtraDataDecoded{}, fmt.Errorf("unexpected message length, expected 1, got %d", len(report.AbstractReports[0].Messages))
	}
	message := report.AbstractReports[0].Messages[0]
	extraDataDecoded := ccipcommon.ExtraDataDecoded{}

	var err error
	extraDataDecoded.ExtraArgsDecoded, err = codec.DecodeExtraArgs(message.ExtraArgs, report.AbstractReports[0].SourceChainSelector)
	if err != nil {
		return ccipcommon.ExtraDataDecoded{}, fmt.Errorf("failed to decode extra args: %w", err)
	}
	// stopgap solution for missing extra args for Solana. To be replaced in the future.
	destExecDataDecoded := make([]map[string]any, len(message.TokenAmounts))
	for i, tokenAmount := range message.TokenAmounts {
		destExecDataDecoded[i], err = codec.DecodeTokenAmountDestExecData(tokenAmount.DestExecData, report.AbstractReports[0].SourceChainSelector)
		if err != nil {
			return ccipcommon.ExtraDataDecoded{}, fmt.Errorf("failed to decode token amount dest exec data: %w", err)
		}
	}
	extraDataDecoded.DestExecDataDecoded = destExecDataDecoded

	return extraDataDecoded, nil
}
