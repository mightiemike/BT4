### Title
Unauthenticated `txpool_removeTransactionsByHash` / `txpool_removeTransactionsBySender` RPC methods allow any client on the sequencer's public JSON-RPC port to delete arbitrary users' pending transactions - (File: `crates/sequencer/src/rpc.rs`, `crates/common/src/rpc/auth.rs`)

### Summary
The `FeeSplitter.setCurves` analog here is a state-mutating entry point that lacks any authorization check even though a comparable, sensitive setter should be gated. In Citrea's sequencer RPC server, `citrea::rpc::auth::Auth` only requires an API key for three methods (`backup_create`, `backup_validate`, `backup_info`); every other method registered on the same jsonrpsee module — including `txpool_removeTransactionsByHash` and `txpool_removeTransactionsBySender` — is reachable by any caller who can reach `eth_sendRawTransaction` on the standard public RPC port, with zero authentication.

### Finding Description
`Auth::call` in [1](#0-0)  hard-codes a `PROTECTED_METHODS` allow-list of only three backup-related methods; any method name not in that list is passed straight through to the underlying service with no credential check at all:
```
const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];
...
if !PROTECTED_METHODS.contains(&method) {
    return Box::pin(service.call(req));
}
```
This `Auth` middleware is installed as the single RPC-layer gate for the sequencer's JSON-RPC server in [2](#0-1) , and it wraps the exact same `RpcModule` that serves the public, unprivileged `eth_sendRawTransaction` endpoint ( [3](#0-2) ).

The sequencer trait also exposes mempool-mutation methods on that same module without any additional guard:
```
#[method(name = "txpool_removeTransactionsByHash")]
async fn txpool_remove_txs_by_hash(&self, hashes: Vec<B256>) -> RpcResult<Vec<B256>>;

#[method(name = "txpool_removeTransactionsBySender")]
async fn txpool_remove_txs_by_sender(&self, sender: Address) -> RpcResult<Vec<B256>>;
``` [4](#0-3) 

Unlike `citrea_testPublishBlock`, which explicitly checks `self.context.test_mode` before acting ( [5](#0-4) ), there is no equivalent mode/role/API-key check gating the txpool-removal handlers before they mutate the mempool. This is the direct analog of `FeeSplitter.setCurves`: a state-changing entry point (`setCurves` swaps a critical dependency; `txpool_removeTransactionsBy*` deletes arbitrary in-flight user transactions) that omits the access-control modifier that comparable functions in the same contract/module do apply.

### Impact Explanation
This matches the report's own explicitly allowed High-severity category: "an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`." Any network client capable of submitting `eth_sendRawTransaction` to a Citrea sequencer — i.e., any ordinary, unprivileged user, since that endpoint is the standard public transaction-submission interface — can also call `txpool_removeTransactionsByHash`/`txpool_removeTransactionsBySender` to purge other users' pending transactions from the sequencer's mempool before they are included in an L2 block. This is a concrete authorization-boundary break at the RPC layer (not a deployment misconfiguration, since the same port and same `Auth` layer are documented to serve public traffic), and it lets an attacker selectively censor/remove transactions belonging to victims of their choosing, directly mutating sequencer state without any credential.

### Likelihood Explanation
Likelihood is high: the attack requires no privileged role, no key, and no special network position — only the ability to send a standard JSON-RPC request to the sequencer's already-public RPC endpoint, exactly the same access level needed to submit `eth_sendRawTransaction`. The `Auth` allow-list is a simple, deterministic code path with no dependence on race conditions or non-standard configuration.

### Recommendation
Add `txpool_removeTransactionsByHash` and `txpool_removeTransactionsBySender` (and any other state-mutating administrative RPC method not intended for public callers) to the `Auth` middleware's protected/authenticated set in `crates/common/src/rpc/auth.rs`, or gate them behind the same `test_mode`/API-key check pattern already used for `citrea_testPublishBlock`, `citrea_haltCommitments`, and `citrea_resumeCommitments` in `crates/sequencer/src/rpc.rs`.

### Proof of Concept
1. Stand up a sequencer node with its public RPC port reachable (the same port that serves `eth_sendRawTransaction`).
2. As an unprivileged attacker with no API key, submit a raw transaction from victim address `V` (observed via `eth_getTransactionByHash`/mempool inspection) or learn its hash.
3. Call:
```
curl -X POST $SEQUENCER_RPC -d '{"jsonrpc":"2.0","id":1,"method":"txpool_removeTransactionsByHash","params":[["0x<victim_tx_hash>"]]}'
```
or
```
curl -X POST $SEQUENCER_RPC -d '{"jsonrpc":"2.0","id":1,"method":"txpool_removeTransactionsBySender","params":["0x<victim_address>"]}'
```
4. Observe (per `Auth::call`, since these method names are absent from `PROTECTED_METHODS`) that the request is forwarded and processed without any API key, and the victim's transaction(s) are removed from the mempool — confirmable via a follow-up `eth_getTransactionByHash` returning `None` for a transaction the victim never withdrew.

Note: I was unable to fully trace the concrete `remove_transactions`/mempool-eviction implementation body in `crates/sequencer/src/mempool.rs` within the available search budget to confirm exactly which internal removal primitive is invoked; this does not affect the core finding (the missing `Auth` gate on these two RPC methods), but a full review of that removal logic is recommended before remediation to ensure no additional side effects.

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }

        let Some(api_key) = api_key else {
            return Box::pin(async move {
                MethodResponse::error(
                    req.id().clone(),
                    ErrorObjectOwned::owned(401, "Cannot access protected method", None::<String>),
                )
            });
        };
