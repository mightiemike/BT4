This confirms the analog vulnerability: when an `L1HandlerTransaction` exceeds the protocol-fixed `l1_handler_max_amount_bounds`, `execute_raw` reverts the state (`execution_state.abort()`) but still returns `Ok(...)` — meaning the transaction is treated as "accepted/consumed" rather than "rejected." It is then added to `consumed_l1_handler_tx_hashes` (confirmed by the `failed_l1_handler_transaction_consumed` test and `collect_execution_results_and_stream_txs` in `apollo_batcher/src/block_builder.rs`), which is irreversible — the L1-to-L2 message nonce is permanently consumed with no replay path, unlike a normal `Err` (rejected) transaction which stays `Pending` for retry.

### Title
L1Handler transactions that exceed the fixed protocol gas bounds are permanently consumed with no replay, causing loss of bridged L1 funds - (File: crates/blockifier/src/transaction/l1_handler_transaction.rs)

### Summary
`L1HandlerTransaction::execute_raw` executes every L1-to-L2 message against a single, protocol-wide, non-configurable gas ceiling (`l1_handler_max_amount_bounds`). If the target entry point's actual gas/resource usage exceeds that ceiling, the post-execution check fails, the state changes are aborted, and the transaction is returned as `Ok(...)` with a `revert_error` rather than an execution `Err`. Because it is `Ok`, the batcher classifies it as accepted/consumed (not rejected), permanently removing the underlying L1 message from the pending pool with no mechanism to resubmit or replay it — mirroring the CrossDomainMessenger class of bug where a message can be "used up" without its intended effect actually happening.

### Finding Description
`execute_raw` in <cite repo="Thankgoddavid56/sequencer--019" path="crates/blockifier/src/transaction/l1_handler_transaction.rs" start="64="/> `l1_handler_transaction.rs` fixes `remaining_gas` to the constant `l1_handler_bounds.l2_gas.0` taken from `block_context.versioned_constants.os_constants.l1_handler_max_amount_bounds` [1](#0-0) . This bound is a single global protocol constant (e.g. `l1_gas: 40000, l1_data_gas: 20000, l2_gas: 100000000` in v0.14.0) applied uniformly to every L1-to-L2 message regardless of the amount of computation the target `l1_handler` entry point actually needs [2](#0-1) .

After execution, `FeeCheckReport::check_all_gas_amounts_within_bounds` compares actual usage of `l1_gas`, `l2_gas`, and `l1_data_gas` against these bounds [3](#0-2) . If any resource is exceeded, the execution is aborted (`execution_state.abort()`) and a `reverted_l1_handler` receipt is produced, but the function still returns `Ok(l1_handler_tx_execution_info(...))` with `revert_error: Some(fee_check_error.into())` — it does not return an `Err` [4](#0-3) . This exact scenario is exercised by `test_l1_handler_resource_bounds`, which shows a transaction that has "enough gas to run" but still fails the post-execution resource-bounds check and reverts with `fee == Fee(0)` [5](#0-4) .

At the batcher level, `collect_execution_results_and_stream_txs` distinguishes only between `Ok` (successfully executed, even if reverted) and `Err` (rejected, kept `Pending` for retry). Every L1Handler transaction that returns `Ok` — including reverted ones — is inserted into `consumed_l1_handler_tx_hashes` [6](#0-5) , and this behavior is explicitly validated by the regression test `failed_l1_handler_transaction_consumed`, whose comment states "Verify that all L1 handler transaction's are included in the consumed l1 transactions" even after an execution failure [7](#0-6) . Consumed transactions are then committed via `L1EventsProvider::commit_block`/`TransactionManager::commit_txs`, transitioning the L1 message's `TransactionRecord` state from `Pending` to `Committed`/`Consumed` permanently — there is no `Pending`-restoring path for a transaction whose execution reverted, only for those in `rejected_tx_hashes` (i.e. `Err`) [8](#0-7) .

### Impact Explanation
Any L1-to-L2 message (e.g. a bridge deposit that calls an `l1_handler` to credit an L2 balance) whose actual entry-point execution cost exceeds the fixed, non-adjustable `l1_handler_max_amount_bounds` will be permanently marked as consumed on both L1 and L2 bookkeeping while doing none of its intended state changes (the state diff is aborted). The L1 sender has no way to resend/replay the message with more gas, since the message is uniquely identified by its L1 nonce and is now irrevocably in the `Committed`/`Consumed` state. This is a concrete, permanent loss of bridged funds/functionality for the L1 message sender — the same fund-loss class as the CrossDomainMessenger bug: a "guaranteed executable" cross-layer message silently and irreversibly failing without possibility of retry.

### Likelihood Explanation
Reachable purely by any L1 contract/user sending a `sendMessageToL2`-style message whose target `l1_handler` legitimately needs more resources than the current protocol bound allows (e.g. a bridge contract handling a large batch, a complex accounting update, or a contract whose gas usage grows with payload/state size). Because the bound is a fixed protocol constant rather than something the L1 sender can size their transaction against per-call, and because historical values of this constant have changed materially across versions (e.g. `l2_gas` dropped from `10_000_000_000` in v0.13.x to `100_000_000` in v0.14.0), a message that would have safely succeeded under one version's bound can start failing and being permanently burned under a later one purely due to a protocol constant change, with no user-side mitigation.

### Recommendation
When the post-execution resource-bounds check fails for an `L1HandlerTransaction` (the `Err(fee_check_error)` branch in `execute_raw`), do not classify the transaction as consumed/committed. Instead, treat it equivalently to a `rejected` transaction so the L1 message remains `Pending` and can be retried in a later block (e.g., after a subsequent protocol bound increase, or via off-chain intervention), or otherwise ensure a message that fails purely due to resource exhaustion is not permanently and silently burned without an explicit protocol-level acknowledgment/refund path.

### Proof of Concept
1. Configure (or await) a `BlockContext` where `os_constants.l1_handler_max_amount_bounds.l2_gas` is set below what a given `l1_handler` entry point needs — this is directly reproduced by `test_l1_handler_resource_bounds` in [9](#0-8) , using `L2Gas => GasAmount(200000)`.
2. Submit an `L1HandlerTransaction` (i.e., simulate an L1-to-L2 message) targeting that entry point.
3. Observe `tx.execute(...)` returns `Ok(TransactionExecutionInfo { execute_call_info: None, revert_error: Some(RevertError::PostExecution(FeeCheckError::MaxGasAmountExceeded { .. })), receipt: TransactionReceipt { fee: Fee(0), .. } })` — an `Ok` result despite full state rollback [10](#0-9) .
4. Trace this `Ok` result through `collect_execution_results_and_stream_txs`, which inserts the transaction hash into `consumed_l1_handler_tx_hashes` regardless of the revert [11](#0-10) , matching the assertion in `failed_l1_handler_transaction_consumed` that a transaction which failed execution is still recorded as consumed [12](#0-11) .
5. This hash flows into `commit_block`, transitioning the corresponding `TransactionRecord` in the `TransactionManager`/`L1EventsProvider` to `Committed`, permanently precluding the L1 sender from ever having the message re-processed.

    pub fn check_all_gas_amounts_within_bounds(
        max_amount_bounds: &GasVector,
        gas_vector: &GasVector,
    ) -> FeeCheckResult<()> {
        // TODO(Arni): Consider refactoring the returned error. The first failed check will hide
        // future checks.
        for (resource, max_amount, actual_amount) in [
            (L1Gas, max_amount_bounds.l1_gas, gas_vector.l1_gas),
            (L2Gas, max_amount_bounds.l2_gas, gas_vector.l2_gas),
            (L1DataGas, max_amount_bounds.l1_data_gas, gas_vector.l1_data_gas),
        ] {
            if max_amount < actual_amount {
                return Err(FeeCheckError::MaxGasAmountExceeded {
                    resource,
                    max_amount,
                    actual_amount,
                });
            }
        }

        Ok(())
    }
