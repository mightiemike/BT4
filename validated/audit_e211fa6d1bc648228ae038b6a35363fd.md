### Title
`DelegateAction` Signed Payload Contains No Chain Identifier, Enabling Cross-Chain Replay of Meta Transactions — (`File: core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

---

### Summary

`DelegateAction` (NEP-366 meta transactions) and `DelegateActionV2` (NEP-611) produce signatures over a payload that contains no chain-specific identifier — no `chain_id` string and no genesis block hash. The signed bytes are `borsh(fixed_discriminant || delegate_action_fields)` where the discriminant is a compile-time constant. A `SignedDelegateAction` that is valid on mainnet is cryptographically valid on testnet, betanet, or any fork of mainnet that shares the same account state, provided the nonce is still acceptable on the target chain.

---

### Finding Description

**Signed payload construction — no chain binding**

`DelegateAction::get_nep461_hash()` builds the hash that is signed:

```rust
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
``` [1](#0-0) 

`SignableMessage` serialises as `(discriminant: u32 || msg: T)`:

```rust
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}
``` [2](#0-1) 

The discriminant is a fixed compile-time constant derived from the NEP number:

```rust
SignableMessageType::DelegateAction =>
    MessageDiscriminant::new_on_chain(NEP_366_META_TRANSACTIONS).unwrap()
// NEP_366_META_TRANSACTIONS = 366  →  discriminant = (1 << 30) + 366
``` [3](#0-2) 

The `DelegateAction` struct itself contains:

```rust
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,
    pub nonce: Nonce,
    pub max_block_height: BlockHeight,
    pub public_key: PublicKey,
}
``` [4](#0-3) 

There is no `chain_id` field and no genesis block hash. The same is true for `DelegateActionV2` / `VersionedDelegateActionPayload`: [5](#0-4) [6](#0-5) 

**Contrast with regular `SignedTransaction`**

A regular `SignedTransaction` contains a `block_hash` field — a hash of a recent block on the specific chain — which provides chain-binding because a mainnet block hash does not exist on testnet:

```rust
pub struct TransactionV1 {
    ...
    pub block_hash: CryptoHash,   // chain-specific anchor
    ...
}
``` [7](#0-6) 

`DelegateAction` has no equivalent. Its only time-bounding is `max_block_height`, which is a plain integer that is identical across all NEAR networks at the same height.

**Validation path — no chain check**

`apply_delegate_action` verifies the signature, checks `max_block_height`, validates the nonce, and checks access-key permissions. It never checks that the action was intended for the current chain:

```rust
pub(crate) fn apply_delegate_action(...) {
    if !signed_delegate_action.verify() { ... }          // sig ok
    if apply_state.block_height > delegate_action.max_block_height() { ... } // height ok
    if delegate_action.sender_id() != sender_id { ... }  // sender ok
    validate_delegate_action_key(...)?;                  // nonce + key ok
    // ← no chain_id check
}
``` [8](#0-7) 

---

### Impact Explanation

**Scenario A — Cross-network replay by a malicious relayer**

A user signs a `DelegateAction` off-chain and hands it to a relayer. The relayer is an unprivileged user with no special protocol role. A malicious relayer can submit the same `SignedDelegateAction` to a different NEAR network (e.g., testnet, betanet, or a future fork) instead of, or in addition to, the intended network. If the user's account exists on the target network with the same key and the nonce is still valid there, the inner actions execute without the user's consent on that network — an unauthorized transaction.

**Scenario B — Fork replay**

If mainnet ever forks (e.g., a contentious protocol upgrade), both chains share identical account state and nonces at the fork point. A `SignedDelegateAction` executed on one branch can be replayed on the other branch by any observer who saw it on-chain, because the signed bytes are identical on both branches. This can cause loss of real funds on the fork.

The broken invariant: a `SignedDelegateAction` must only be executable on the chain for which it was created. The signed payload contains no value that distinguishes one NEAR network from another.

---

### Likelihood Explanation

- **Cross-network replay**: Requires a malicious relayer and the victim's account to exist on the target network with the same key and a valid nonce. Many accounts exist on both mainnet and testnet with identical keys. Testnet tokens have no monetary value, limiting financial impact in this sub-scenario.
- **Fork replay**: Requires a mainnet fork. If one occurs, every `SignedDelegateAction` that was on-chain before the fork is immediately replayable on the other branch by any unprivileged observer. This is the highest-impact sub-scenario.

Overall likelihood is **low** in the absence of a fork, but the design flaw is structural and the fix is straightforward.

---

### Recommendation

Include the `chain_id` (the genesis chain identifier string, e.g., `"mainnet"`) and/or the genesis block hash in the signed payload of `DelegateAction` and `DelegateActionV2`. The cleanest approach is to add a `chain_id: String` field to both structs, or to incorporate it into the `SignableMessage` wrapper so all future message types inherit the binding automatically. This mirrors the EIP-712 DOMAIN_SEPARATOR pattern and the `block_hash` binding already present in `SignedTransaction`.

---

### Proof of Concept

1. Alice signs a `DelegateAction` on mainnet to transfer 100 NEAR to Bob, with `nonce = N+1` and `max_block_height = H+1000`.
2. The signed bytes are `sha256( borsh(0x4000016E || sender_id || receiver_id || actions || N+1 || H+1000 || pubkey) )`. The constant `0x4000016E` = `(1<<30)+366` is identical on every NEAR network.
3. Alice's account exists on testnet with the same key and `nonce = N` (common for accounts created with the same seed phrase).
4. A malicious relayer wraps the same `SignedDelegateAction` in a testnet transaction addressed to Alice's testnet account.
5. `apply_delegate_action` on testnet: signature verifies (same bytes, same key), `block_height ≤ max_block_height` (testnet height is also below `H+1000`), nonce `N+1 > N` passes. The inner transfer executes on testnet.
6. Alice's testnet tokens are transferred to Bob without her consent on testnet.

For the fork variant: replace step 3–4 with "after a mainnet fork, any observer replays the on-chain `SignedDelegateAction` on the fork branch before Alice's nonce advances there."

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

    // Generate a new receipt from DelegateAction.
    let new_receipt = Receipt::V0(ReceiptV0 {
        predecessor_id: sender_id.clone(),
        receiver_id: delegate_action.receiver_id().clone(),
        receipt_id: CryptoHash::default(),

        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: action_receipt.signer_id().clone(),
            signer_public_key: action_receipt.signer_public_key().clone(),
            gas_price: action_receipt.gas_price(),
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: delegate_action.get_actions(),
        }),
    });

    // Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas.
    // If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction.
    // Gas is refunded to the signer, this is Relayer.
    // Some contracts refund the deposit. Usually they refund the deposit to the predecessor and this is sender_id/Sender from DelegateAction.
    // Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit.

    let prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, action_receipt.actions())?;
    let required_cost = receipt_required_cost(apply_state, &new_receipt)?;
    // This gas will be burnt by the receiver of the created receipt.
    // Compute costs of that are not relevant at this point, the "used" gas is
    // only reserved for execution later, potentially on a different shard.
    result.gas_used = result.gas_used.checked_add_result(required_cost.gas)?;
    // This gas was prepaid on Relayer shard. Need to burn it because the receipt is going to be sent.
    // gas_used is incremented because otherwise the gas will be refunded. Refund function checks only gas_used.
    result.gas_used = result.gas_used.checked_add_result(prepaid_send_fees.gas)?;
    result.gas_burnt = result.gas_burnt.checked_add_result(prepaid_send_fees.gas)?;
    result.compute_usage = safe_add_compute(result.compute_usage, prepaid_send_fees.compute)?;
    result.new_receipts.push(new_receipt);

    Ok(())
}
