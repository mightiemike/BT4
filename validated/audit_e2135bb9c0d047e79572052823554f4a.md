### Title
TRC10 asset (token) name can be front-run in `AssetIssueActuator`, causing griefing/name-squatting when `AllowSameTokenName` is disabled - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
The reported bug class is that a unique, human-readable identifier (a DAO name) is claimed on a first-come-first-served basis at contract-execution time, allowing anyone observing a pending creation transaction to front-run it and steal the name. The same pattern exists in java-tron's TRC10 token issuance path: when the `ALLOW_SAME_TOKEN_NAME` chain parameter is disabled, `AssetIssueActuator` treats the raw asset `name` as the sole uniqueness key, checked only at `validate()` time against the current chain state, with no reservation/commit step tied to the submitting account.

### Finding Description
In `AssetIssueActuator.validate()`, the uniqueness check for a new TRC10 token name is: [1](#0-0) 

```java
if (dynamicStore.getAllowSameTokenName() == 0
    && assetIssueStore.get(assetIssueContract.getName().toByteArray())
    != null) {
  throw new ContractValidateException("Token exists");
}
```

This check is performed against the current (pre-block) state of `assetIssueStore`, keyed purely by the raw `name` string, exactly the same pattern as `MembershipFactory::createNewDAOMembership`'s `getENSAddress[daoConfig.ensname] == address(0)` check. Any pending `AssetIssueContract` transaction broadcasting a chosen `name` is visible in the mempool before block inclusion. A malicious actor can observe the name in the pending transaction, submit their own `AssetIssueContract` with the identical `name` and a higher energy/bandwidth fee or via direct relationship with a block-producing witness, and have their transaction included first. Because the store lookup keys strictly on `name` (not on `(creator, name)` or any commitment scheme), whichever transaction is processed first claims the name; the original creator's transaction then fails validation with `"Token exists"`.

This is confirmed as a first-come-first-served, unprivileged-user race by the existing test `IssueSameTokenNameAssert` which demonstrates the exact "Token exists" rejection path when a name is already claimed: [2](#0-1) 

### Impact Explanation
When `ALLOW_SAME_TOKEN_NAME == 0`, any account can front-run a pending `AssetIssueContract` transaction to steal the desired token name. The victim's transaction fails, they lose the paid `AssetIssueFee` (transaction is rejected in validate, so the fee generally is not charged, but bandwidth/energy and time are consumed, and the creator must choose a new name), and the attacker can grief specific projects (denial-of-service on branding) or set up honeypot tokens using a name expected to belong to a legitimate project. This mirrors the impact described in the original report: griefing and honeypot creation via name squatting.

### Likelihood Explanation
Likelihood depends on the current value of `ALLOW_SAME_TOKEN_NAME`, which is a network parameter governed by an on-chain proposal (`ProposalUtil`/`ProposalService`), not a fixed constant in code. I could not conclusively determine from the indexed code whether `ALLOW_SAME_TOKEN_NAME` is currently enabled (`1`) on the live mainnet/testnet this repository targets — the default/initial value is set via chain parameters/proposal state rather than a hardcoded constant I could locate in `DynamicPropertiesStore`. If the network currently has `ALLOW_SAME_TOKEN_NAME == 1` (which historical TRON documentation suggests became the case after a network upgrade), tokens are keyed by an auto-incrementing numeric `id` rather than the raw name, and this specific front-running vector on `AssetIssueActuator` would no longer be exploitable in practice (duplicate names would simply coexist as distinct tokens). This uncertainty should be verified against current on-chain proposal state before treating the finding as immediately exploitable in production.

### Recommendation
- If `ALLOW_SAME_TOKEN_NAME` is still disabled on any network instance, treat it as legacy/deprecated and encourage migration to the V2 (id-keyed) path, since the V2 scheme already avoids the front-running issue by not enforcing name uniqueness.
- For any future features that reintroduce name-based uniqueness (e.g., future TRC10-like registries), avoid keying solely on a user-chosen string; instead commit-reveal the name, or key on `(creator_address, name)`/hash, or allow duplicate names with a separate unique numeric identifier, consistent with the already-adopted V2 approach.

### Proof of Concept
1. Ensure `ALLOW_SAME_TOKEN_NAME == 0` on the target chain (this is a network-governed parameter and may not be the case on current mainnet).
2. Victim broadcasts an `AssetIssueContract` transaction with `name = "MYTOKEN"`.
3. Attacker observes the pending transaction in the mempool, crafts an `AssetIssueContract` with the identical `name = "MYTOKEN"`, and gets it included first (e.g., via higher fee/energy or relationship with block producer).
4. `AssetIssueActuator.validate()` for the attacker's transaction succeeds because `assetIssueStore.get("MYTOKEN") == null` at time of processing.
5. When the victim's transaction is subsequently processed, `assetIssueStore.get("MYTOKEN") != null`, causing `ContractValidateException("Token exists")` per [1](#0-0) , and the victim's token creation fails while the attacker now controls the name "MYTOKEN".
