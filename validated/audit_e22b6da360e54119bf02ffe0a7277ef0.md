## Analog Found: Ambiguous Length-Delimiting in `ConsensusHash::from_ops`

The reported Sui bug is a classic "concatenation without padding" collision: variable-length byte strings are joined without length delimiters, so two logically-different inputs can serialize to the identical byte stream and therefore hash identically. The same structural pattern exists in this repo's consensus-hash computation.

### Title
Ambiguous PoX-bitvector/consensus-hash-chain boundary in `ConsensusHash::from_ops` enables hash-preimage collisions between different fork states - (File: `stackslib/src/chainstate/burn/mod.rs`)

### Summary
`ConsensusHash::from_ops` hashes a preimage built by concatenating fixed-size fields with one *variable-length, unprefixed* field — the `PoxId`'s `Display` string (a sequence of ASCII `'0'`/`'1'` characters, one per historical reward cycle) — immediately followed by a variable-count sequence of fixed-size (20-byte) `ConsensusHash` values. Because the `PoxId` string has no explicit length prefix or terminator, and the following `prev_consensus_hashes` bytes are unconstrained 20-byte blobs that can themselves contain byte values `0x30`/`0x31` (ASCII `'0'`/`'1'`), the boundary between "how many PoX fork bits" and "which previous consensus hashes" is not self-describing in the hashed byte stream. This is exactly the "lack of padding between items" bug class from the reported PoC.

### Finding Description [1](#0-0) 

Walking through `from_ops`:
- `SYSTEM_FORK_SET_VERSION` — fixed.
- `burn_header_hash` — fixed 32 bytes.
- `opshash` — fixed 32 bytes.
- `burn_bytes` (`total_burn.to_be_bytes()`) — fixed 8 bytes.
- `write!(hasher, "{}", pox_id)` — **variable-length ASCII string**, one byte (`'0'` or `'1'`) per bit in the PoX fork bit-vector [2](#0-1) .
- `for ch in prev_consensus_hashes { hasher.update(ch.as_bytes()) }` — a variable-*count* sequence of fixed 20-byte `ConsensusHash` values, with **no explicit count or separator** written before/between them.

Because the `PoxId` string has no length prefix and is immediately followed by raw hash bytes that are indistinguishable in encoding (a `ConsensusHash` byte can legally equal `0x30`/`0x31`), two structurally different tuples — `(pox_id_A, prev_chs_A)` vs. `(pox_id_B, prev_chs_B)` — can produce byte-for-byte identical hash preimages if a `prev_consensus_hashes[0]` happens to begin with `'0'`/`'1'`-valued bytes that get reinterpreted as additional PoX bits when the bit-vector length is shifted by the corresponding number of bytes. This directly mirrors the `compute_digest_for_modules_and_deps` flaw: a variable-length item's boundary is not fixed by the encoding, so the "unique hash" invariant the consensus hash is relied on for is not actually guaranteed.

`SortitionId::new` has the identical pattern — it hashes `bhh.0` immediately followed by `write!(hasher, "{pox}")` with no delimiter [3](#0-2) , compounding the same ambiguity into sortition identifiers.

### Impact Explanation
`ConsensusHash` is the core value used to identify a specific burnchain/PoX fork state throughout sortition processing (`BlockSnapshot.consensus_hash`, `SortitionId::new`, PoX-fork agreement in `getpoxinv`/`PoxInvData` peer negotiation). If two distinguishable fork histories (different `PoxId` bit-vectors and/or different prior consensus-hash chains) can be engineered to hash to the same `ConsensusHash`, this breaks the equality "one consensus hash ⇒ one canonical fork state" that peer nodes and the sortition DB rely on to agree on which PoX fork a given consensus hash belongs to. This falls under the "a committed state root no node reproduces" / "a validation verdict two nodes disagree on" category, which is High impact per the rules (bounded, minority-triggerable state/verdict divergence in sortition machinery), since exploiting it does not require majority collusion — only crafting/discovering a fork history whose serialized hash preimage aligns with another's.

### Likelihood Explanation
This is a genuine structural flaw of the same class as the reported bug, but the practical likelihood of exploitation is low: a real collision additionally requires that a legitimately-produced `ConsensusHash` (a RIPEMD160(SHA256(...)) output, not attacker-chosen) coincidentally begins with byte(s) in `{0x30, 0x31}` at exactly the alignment needed to reinterpret them as extra/fewer PoX bits, and that all downstream bytes remain validly interpretable. This is a probabilistic precondition (not a deterministic construction like the Sui PoC), so it is much harder to trigger deliberately than the reported bug, but it is not cryptographically infeasible and the underlying encoding defect (no length prefix on `PoxId`) is unconditionally present in the code today.

### Recommendation
Prefix the serialized `PoxId` string (or better, its raw bit-vector) with an explicit length field (e.g., a `u32` bit-count or byte-count) before writing it into the hasher, and/or write an explicit count of `prev_consensus_hashes` before iterating them, so that the preimage is self-describing and no two distinct `(pox_id, prev_consensus_hashes)` pairs can serialize identically. Apply the same fix to `SortitionId::new`, which has the identical unprefixed-`PoxId`-concatenation pattern.

### Proof of Concept
Conceptual (mirroring the reported PoC's structure, adapted to this codebase's types):
1. Suppose `prev_consensus_hashes_A = [CH_x, CH_y]` where `CH_x.as_bytes() = [0x31, b1, b2, ..., b19]` (i.e., its first byte happens to equal ASCII `'1'`).
2. Preimage using `pox_id_A = "1"` (1-bit history) followed by `prev_consensus_hashes_A` contains the byte sequence: `... <pox_id_A bytes: 0x31> <CH_x: 0x31,b1,...,b19> <CH_y: 20 bytes> ...`.
3. Construct `pox_id_B = "11"` (2-bit history) with `prev_consensus_hashes_B = [CH_x', CH_y]` where `CH_x'` is defined so that its bytes, shifted by consuming one fewer leading byte, reproduce the same 19+20 trailing bytes as `CH_x`/`CH_y` above (i.e., the reader would need `CH_x'` to still decode as a valid, fixed 20-byte `ConsensusHash` from the shifted offset — achievable if the surrounding byte stream from a genuinely different fork happens to align, since `get_prev_consensus_hashes` count is independent of the exact byte content).
4. Both `(pox_id_A, prev_chs_A, ...)` and `(pox_id_B, prev_chs_B, ...)` feed identical bytes into `Sha256::update`/`Ripemd160`, yielding the same `ConsensusHash`, despite representing two different PoX fork states — call sites: [4](#0-3) .

This is presented as a structural demonstration of the missing length-delimiter, per the same logic as the reported `compute_digest_for_modules_and_deps` PoC (hiding one variable-length item's boundary inside another item's raw bytes).

    fn from_ops(
        burn_header_hash: &BurnchainHeaderHash,
        opshash: &OpsHash,
        total_burn: u64,
        prev_consensus_hashes: &[ConsensusHash],
        pox_id: &PoxId,
    ) -> ConsensusHash {
        // NOTE: unlike stacks v1, we calculate the next consensus hash
        // simply as a hash-chain of the new ops hash, the sequence of
        // previous consensus hashes, and the total burn that went into this
        // consensus hash.  We don't turn them into Merkle trees first.
        // We also make it so the consensus hash commits to both the transactions and the block
        // that contains them (so two different blocks with the same Blockstack-relevant transactions
        // in the same order will have two different consensus hashes, as they should).

        let burn_bytes = total_burn.to_be_bytes();
        let result;
        {
            let mut hasher = Sha256::new();

            // fork-set version...
            hasher.update(SYSTEM_FORK_SET_VERSION);

            // burn block hash...
            hasher.update(burn_header_hash.as_bytes());

            // ops hash...
            hasher.update(opshash.as_bytes());

            // total burn amount on this fork...
            hasher.update(&burn_bytes);

            // pox-fork bit vector
            write!(hasher, "{}", pox_id).unwrap();

            // previous consensus hashes...
            for ch in prev_consensus_hashes {
                hasher.update(ch.as_bytes());
            }

            result = hasher.finalize();
        }

        use ripemd::Digest;
        let mut r160 = Ripemd160::new();
        r160.update(&result);

        let mut ch_bytes = [0u8; 20];
        ch_bytes.copy_from_slice(r160.finalize().as_slice());

        ConsensusHash(ch_bytes)
    }
