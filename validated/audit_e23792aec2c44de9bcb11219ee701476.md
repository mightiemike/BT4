### Title
Wallet Contract permanently retains attached deposit when intermediate cross-contract check fails or returns non-standard data - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Wallet Contract's `rlp_execute` flow tracks a caller's attached NEAR deposit (`CallerDeposit`) so it can be refunded if the resulting cross-contract action fails [1](#0-0) . However, refund logic is only implemented in the final `rlp_execute_callback` [2](#0-1) . The two intermediate callbacks that decode responses from external contracts — `address_check_callback` (decoding the address registrar's `lookup` response) and `nep_141_storage_balance_callback` (decoding a token's `storage_balance_of` response) — silently drop `caller_deposit` on every failure/decode-error branch without refunding it [3](#0-2) [4](#0-3) .

### Finding Description
This is the structural analog of the reported Solidity bug: code that blindly assumes an external call returns data in one canonical, decodable shape, and a mismatch (or failure) between the assumption and reality causes the caller-facing operation to break down — except here the failure mode isn't a revert, it's silent loss of caller-attached funds.

`CallerDeposit::new` captures the predecessor's attached deposit whenever the predecessor is not the wallet's own account [5](#0-4) . This value is threaded through the promise chain so it can be refunded if the eventual action fails, which is exactly what happens in `rlp_execute_callback`:

```rust
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(...);
    }
    ...
}
``` [6](#0-5) 

But for `EthEmulationKind::EOABaseTokenTransfer { address_check: Some(_), .. }` and `EthEmulationKind::ERC20Transfer { .. }` transactions, execution first goes through `address_check_callback` or `nep_141_storage_balance_callback` before ever reaching `rlp_execute_callback` [7](#0-6) . In both of these intermediate callbacks, the `PromiseResult::Failed` branch and the `serde_json::from_slice` decode-error branch return an `ExecuteResponse::success:false` directly, with `caller_deposit` simply going out of scope and never being refunded:

```rust
PromiseResult::Failed => {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false, success_value: None,
        error: Some("Call to Address Registrar contract failed".into()),
    });
}
...
Err(_) => {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false, success_value: None,
        error: Some("Unexpected response from account registrar".into()),
    });
}
``` [3](#0-2) 

The identical pattern exists in `nep_141_storage_balance_callback`:
```rust
PromiseResult::Failed => {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false, success_value: None,
        error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
    });
}
``` [4](#0-3) 

Any deposit that is attached to the transaction reaching these two paths (registrar lookup during an eth-implicit target's base-token transfer, or `storage_balance_of` during an emulated ERC-20 transfer) is at risk: if the registrar contract is down, out of gas, or the target token contract returns a `storage_balance_of` response that does not parse as `Option<StorageBalance>` (e.g. a non-standard NEP-141 implementation, or the call simply fails due to gas exhaustion), the wallet keeps the attached deposit permanently instead of refunding the caller as the `CallerDeposit` mechanism was designed to do.

### Impact Explanation
This is reachable by any unprivileged RPC caller or relayer that calls `rlp_execute` on a Wallet Contract account with an attached deposit while routing through the ERC-20-transfer or eth-implicit-target base-token-transfer code paths. A failure or unexpected response in the single intermediate cross-contract call (registrar lookup / `storage_balance_of`) — which can be triggered simply by targeting a token contract that doesn't implement the NEP-141/NEP-145 storage standard exactly, or that runs out of allocated gas — causes the attached deposit to be permanently stuck in the wallet contract with no path to recovery, since the refund logic that exists elsewhere in the same contract is not exercised on this path. This matches the "permanently frozen funds" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires attaching a non-zero deposit to an `rlp_execute` call whose parsed transaction kind is `EOABaseTokenTransfer` with `address_check: Some(_)` or `ERC20Transfer`, and encountering a failure/non-standard response in the intermediate check. This can happen accidentally (non-standard token contracts, gas mis-estimation) or be induced deliberately (e.g., targeting a crafted token contract account as `target` for an ERC20Transfer emulation whose `storage_balance_of` returns malformed JSON) by any caller who wants to grief a wallet's attached funds, or simply as user error resulting in silent, permanent fund loss.

### Recommendation
Refund `caller_deposit` in the failure/decode-error branches of both `address_check_callback` and `nep_141_storage_balance_callback`, mirroring the refund logic already present in `rlp_execute_callback`, so that the invariant "the caller's deposit is refunded whenever the transaction does not complete successfully" holds uniformly across every callback stage of the promise chain.

### Proof of Concept
1. Deploy a Wallet Contract for an eth-implicit account and fund it with an access key as in the `test_erc20_emulation` test flow [8](#0-7) .
2. Have an external predecessor (not the wallet account itself) call `rlp_execute` with a signed Ethereum transaction encoding an `ERC20_TRANSFER_SELECTOR` call targeting a token contract account, attaching a non-zero NEAR deposit alongside the call (so `CallerDeposit::new` produces `Some(..)` per [5](#0-4) ).
3. Point `target` at a contract account whose `storage_balance_of` method either fails (e.g., insufficient gas allocated via `NEP_141_STORAGE_BALANCE_OF_GAS`) or returns a value that does not deserialize as `Option<StorageBalance>`.
4. Observe that `nep_141_storage_balance_callback` returns `ExecuteResponse { success: false, .. }` [4](#0-3)  without issuing any refund promise for the attached deposit, whereas the predecessor is never returned their attached NEAR — permanently lost.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
