### Title
Exchange pool balance underflow due to unchecked subtraction in default (non-hardened) `ExchangeCapsule.transaction` path - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The reported `LPDA` bug class is: a price/accounting value derived from unchecked arithmetic subtraction can underflow, corrupting protocol state with no built-in bound check. The closest reachable analog in java-tron is the TRX/TRC10 bancor-style `Exchange` (market maker) pool balance update in `ExchangeCapsule.transaction()`, whose default arithmetic path performs raw `long` subtraction of pool balances without any negative-result validation, unlike the "hardened" path which is gated behind a governance-controlled chain parameter that is off by default.

### Finding Description
`ExchangeCapsule.transaction()` computes new pool balances after a swap using either raw arithmetic or `StrictMathWrapper` checked arithmetic, selected by the `hardenedCalc` flag: [1](#0-0) 

Specifically, in the non-hardened branch the code computes:
```
newSecondTokenBalance = secondTokenBalance - buyTokenQuant;
```
with no check that the result is non-negative. The only guard against a negative resulting balance is: [2](#0-1) 
which is itself conditioned on `hardenedCalc` being `true`.

Whether `hardenedCalc` is `true` is controlled by `AbstractExchangeActuator.allowHarden()`, which reads the `ALLOW_HARDEN_EXCHANGE_CALCULATION` dynamic property: [3](#0-2) 

This parameter is only settable via committee proposal after `ForkBlockVersionEnum.VERSION_4_8_2`, and its default value is `0` (disabled) unless a witness proposal explicitly turns it on: [4](#0-3) 

The `ExchangeProcessor`/`ExchangeToSupply`/`ExchangeFromSupply` bancor-curve math is `double`-based and can itself produce results larger than the actual reserve for pathological/edge-case inputs (extreme balances, near-zero reserves, rounding). If the computed `buyTokenQuant` (or `anotherTokenQuant`, computed similarly in `ExchangeWithdrawActuator` via `BigInteger` multiply/divide) exceeds the pool's actual reserve, the default-path subtraction silently underflows into a negative `long` value and is persisted directly into the `Exchange`/`ExchangeV2` protobuf state: [5](#0-4) 

Unlike Solidity 0.8's checked-math revert (which "bricks" the LPDA contract but at least halts state corruption), Java's `long` subtraction does not throw on going negative — it silently stores a corrupted (negative) reserve balance into on-chain state. This is arguably a stronger analog of the underlying bug class ("unchecked accounting math on user-influenced/administratively-set inputs") because it produces silent invalid-state corruption in the default configuration, rather than a clean revert.

### Impact Explanation
A corrupted negative pool balance in `ExchangeCapsule`/`ExchangeV2Store` breaks the invariant that AMM reserves must be non-negative. Once one side's balance goes negative, subsequent `ExchangeSellAssetActuator`/`ExchangeTransactionActuator`/`ExchangeWithdrawActuator` calls that read `firstTokenBalance`/`secondTokenBalance` to compute swap/withdraw amounts will operate on invalid state, potentially permanently disabling further correct trading on that pair (denial of service / bricking of the exchange pool) and/or enabling further arithmetic exploitation (e.g., additional users withdrawing against a corrupted ratio), which maps to the "invalid-state/divergence" and "underpriced-public-work"-style impact categories.

### Likelihood Explanation
The default network configuration has `ALLOW_HARDEN_EXCHANGE_CALCULATION = 0`, meaning the unchecked path is the live path on any deployment that hasn't passed the corresponding committee proposal. Triggering the underflow requires an edge-case set of pool balances/quantities (extreme swap size relative to reserves, or near-zero reserve) that push the bancor-curve `double` computation to return a `buyTokenQuant` exceeding the actual reserve — this is a permissionless action (any user can call `ExchangeTransactionActuator`/`ExchangeSellAssetActuator`/`ExchangeWithdrawActuator` on a pool they've created or interacted with), so exploitability does not require a privileged role, matching the "unprivileged-user" constraint. However, I was not able to fully trace `ExchangeTransactionActuator`'s exact call arguments to `transaction()` within the available search budget, so the precise trigger conditions (magnitude of imbalance needed) are not conclusively proven — this remains a plausible but not fully validated path.

### Recommendation
Make the non-negative balance check unconditional (independent of `hardenedCalc`/`allowHardenExchangeCalculation`), i.e., always validate `newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0` in `ExchangeCapsule.transaction()` and throw `ContractValidateException` before persisting state, regardless of which arithmetic mode is selected. Consider also bounding `buyTokenQuant`/`anotherTokenQuant` against `firstTokenBalance`/`secondTokenBalance` directly in the actuators' `validate()` methods before calling `transaction()`/`setBalance()`.

### Proof of Concept
Not independently reproduced against this repository within the scope of this analysis — the finding is based on static code-path analysis of `ExchangeCapsule.transaction()` and `AbstractExchangeActuator`'s conditional hardening, cross-referenced against the existing repository test suite (`ExchangeCreateActuatorTest.hardenedSubtractExactOverflowOnFee`, `ExchangeWithdrawActuatorTest.hardenedSubtractExactUnderflow`, `ExchangeTransactionActuatorTest.hardenedExecuteOverflowThrowsArithmeticException`) which confirm that these underflow/overflow guards exist ONLY in the hardened path: [6](#0-5) [7](#0-6) 
A concrete exploit trace (constructing pool balances/quantities that force `buyTokenQuant > secondTokenBalance` under the default `useStrictMath=false, hardenedCalc=false` configuration) would require additional investigation of `ExchangeTransactionActuator`/`ExchangeSellAssetActuator` validation logic, which was not completed due to tool-call budget exhaustion.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  protected boolean allowHarden() {
    return chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation();
  }

  public long subtractExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.subtractExact(x, y) : x - y;
  }

  public long addExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.addExact(x, y) : x + y;
