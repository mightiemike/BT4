Based on my investigation, I found a self-documented integrity gap in the transaction-info comparison logic used across chunk replay, restore, and replay-verify tooling.

### Title
Replay/restore verification (`ensure_match_transaction_info`) omits checkpoint-hash comparison, allowing state-root divergence to pass as a valid replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single verification routine used to confirm that a locally re-executed (replayed) transaction's output actually matches the authenticated `TransactionInfo` that was committed to the ledger/accumulator. It is invoked from the chunk executor's replay path, the replay-verify db-tool, the Move CLI, and the Aptos debugger. The function checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but — by its own inline TODO — deliberately skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values recomputed locally. [1](#0-0) [2](#0-1) 

### Finding Description
`ensure_match_transaction_info` compares `self.status()`, `self.gas_used()`, the hash of `self.write_set()` against `txn_info.state_change_hash()`, and the event-accumulator root against `txn_info.event_root_hash()`. It never compares any checkpoint-hash field: [3](#0-2) 

The comment directly above the function's `Ok(())` return states the exact gap: the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution," and instructs that these hashes must be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." [4](#0-3) 

`state_checkpoint_hash` is the authenticated root of the Sparse/Jellyfish Merkle state tree at a checkpoint version, and `TransactionInfoV1` additionally carries `hot_state_checkpoint_hash` and the repurposed `position_state_checkpoint_hash` field — all of which are part of the value committed into the accumulator and signed by validators: [5](#0-4) 

Because `ensure_match_transaction_info` is the shared invariant check used by the chunk executor (`execution/executor/src/chunk_executor/mod.rs`), the replay-verify db-tool (`storage/db-tool/src/replay_on_archive.rs`), the debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`), and the CLI (`aptos-move/cli/src/commands.rs`), any of these call sites can be satisfied (returns `Ok(())`) even if the state, hot-state, or position-state root computed by local re-execution diverges from what was actually agreed upon and committed on-chain in the corresponding `TransactionInfo`.

### Impact Explanation
This breaks the "replay/restore paths must preserve deterministic proof binding" invariant: a node performing chunk-executor-based state sync/replay, or an operator running `replay_on_archive` to validate historical execution against archived ledger data, can be told replay succeeded while the locally materialized state Merkle root (and therefore all subsequently derived state, proofs, and API responses) is silently wrong. Given the explicit mention of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (a feature computing an additional/new state root variant), this is precisely the class of hard-fork/feature-rollout divergence the scan targets: a bug where the new-state-root computation diverges from the authenticated value but no comparator catches it, so a syncing/replaying node commits and serves state that doesn't match the real ledger.

### Likelihood Explanation
This is not an attacker-triggered exploit against consensus in real time; it requires (a) a code path that computes checkpoint hashes differently than the canonical execution (e.g., a bug in `compute_trading_native_state_roots`/hot-state or position-state root computation), and (b) that path being exercised during replay/restore/verification, where this comparator is the only automatic safety net. The maintainers' own TODO comment confirms the gap is real and was consciously left open pending a fix before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled — i.e., it's an acknowledged unpatched latent verification hole rather than a hypothetical one. I was not able to fully confirm, within the available iterations, whether every call site (`aptos-debugger`, CLI `commands.rs`) has an independent secondary check on checkpoint hashes that would compensate for this gap; that would need further tracing of those call sites before treating this as certain end-to-end impact.

### Recommendation
Extend `ensure_match_transaction_info` (or add a companion check invoked at every call site) to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed output and the authenticated `TransactionInfo`, and fail replay/restore/verification when they differ. This should be done and merged before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any hot-state/position-state root feature) is enabled on any network, exactly as the existing code comment recommends.

### Proof of Concept
Not exploitable as a standalone remote PoC — the gap is a missing check in verification logic. Conceptual reproduction:
1. Introduce (or trigger via an existing bug in) `compute_trading_native_state_roots` a discrepancy between the locally recomputed `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` and the one recorded in the historical, validator-signed `TransactionInfo`.
2. Run chunk-executor replay or `db-tool replay_on_archive` over the affected version range.
3. Because `ensure_match_transaction_info` only checks status/gas/write-set-hash/event-root-hash (`types/src/transaction/mod.rs:2159-2196`), the mismatch in checkpoint hashes is never surfaced; replay reports success while the locally persisted state tree root is wrong.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
