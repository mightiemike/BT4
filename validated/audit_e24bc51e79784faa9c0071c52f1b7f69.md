Based on my investigation, I found a concrete analog to the CVE-2019-6475 bug class (a validity-check error that allows previously-validated trust-anchored data to be silently accepted for different, unvalidated data via a caching/reuse shortcut).

### Title
Proof-verification skip via global `proof_facts`-hash cache lets attacker bind an unrelated valid proof to a different malicious computation - ([File: crates/apollo_transaction_converter/src/transaction_converter.rs])

### Summary
`run_proof_verification` skips cryptographic proof verification whenever `proof_manager_client.contains_proof(proof_facts)` returns true, treating any transaction whose `proof_facts` hash is already known to the proof manager as already verified, without ever inspecting the caller-supplied `proof` bytes attached to the current transaction.

### Finding Description
`run_proof_verification` in [1](#0-0)  first checks `contains_proof(proof_facts.clone())`; if true it returns `Ok(false)` (verification "skipped") without ever calling `starknet_proof_verifier::verify_proof`. The proof manager's cache/storage is keyed purely by `proof_facts.hash()` [2](#0-1) [3](#0-2)  — the key is a hash over the `ProofFacts` felt array only [4](#0-3) , and it is *not* bound to the specific `proof` bytes that accompany a given submission.

This means: once *any* sender causes a given `proof_facts` value to be marked "contains_proof = true" in the proof manager (e.g., by submitting one transaction with valid `proof_facts`/`proof` through the gateway, which calls `spawn_proof_verification` → `run_proof_verification` → verifies once, then a caller invokes `store_proof_in_proof_manager`/`spawn_verify_and_store_proof` to persist it), any subsequent unprivileged transaction sender can submit a *different* transaction (different `calldata`, `sender_address`, `resource_bounds`, `nonce`, etc.) carrying the *same* `proof_facts` value paired with an arbitrary/garbage `proof` field. `run_proof_verification` will see `contains_proof == true` and skip verification of the newly supplied (bogus) `proof` entirely, treating the transaction as if its proof had been legitimately checked.

Downstream, `blockifier`'s `validate_proof_facts` in [5](#0-4)  only checks that the `proof_facts` themselves are well-formed (allowed program hash, allowed proof version, valid base block hash/number, matching OS config hash) — it never re-verifies that the caller's `proof` bytes actually correspond to this transaction's content. Because the `proof_facts` in this virtual-OS scheme only attest to `[proof_version, VIRTUAL_SNOS, program_hash, output_version, block_number, block_hash, config_hash]` [6](#0-5)  and not to the specific transaction's calldata/sender/resource bounds, the "proof of a valid client-side prove" is effectively fungible across any transaction reusing the same facts.

This is directly analogous to the BIND mirror-zone flaw: an entity that once passed the strict validity check (trust anchor/DNSSEC validation, here: `verify_proof`) has its validated status cached and later reused as an implicit trust signal for different, unvalidated data supplied afterward by a potentially malicious party, bypassing the intended per-submission cryptographic check.

### Impact Explanation
An unprivileged transaction sender can get a transaction accepted by the gateway/consensus pipeline as having passed client-side proof verification without an actually valid proof over its own content, because the skip decision is keyed only on `proof_facts` (not on `proof` nor on tx-specific data). Depending on what invariants the "client-side proving" feature is relied upon to guarantee downstream (e.g., skipping fee/resource re-computation or validation in the blockifier for such transactions), this can let an attacker submit computations that were never actually proven correct, undermining the integrity guarantee the proof was meant to provide. This maps to "unauthorized account action" / accounting or invariant violation categories.

### Likelihood Explanation
Reachable by any external unprivileged actor able to submit an RPC Invoke V3 transaction with `proof_facts`/`proof` set (a supported first-class gateway feature per `apollo_http_server/resources/deprecated_gateway/invoke_tx_client_side_proving.json` and `allow_client_side_proving` config). The only precondition is that some `proof_facts` value has been legitimately verified and persisted once (trivial to arrange, even by the attacker themselves using a cheap valid computation), after which it can be reused indefinitely by different transactions/senders since the proof manager cache has no expiry tied to the original submitter or proof content.

### Recommendation
Bind the "already verified" cache/skip decision to the actual `(proof_facts, proof)` pair rather than `proof_facts` alone, or bind `proof_facts` cryptographically to the specific transaction (e.g., include tx-specific commitments such as sender_address/calldata/resource_bounds hash inside the SNOS proof facts, not just the block/program/config triple), so that a cached "verified" status cannot be replayed against unrelated proof bytes or unrelated transactions.

### Proof of Concept
1. Submit transaction T1 (any sender) with valid `proof_facts=F` and a correctly generated `proof=P1` via the gateway; `run_proof_verification` calls `verify_proof(F, P1)` successfully and `store_proof_in_proof_manager`/`spawn_verify_and_store_proof` persists `contains_proof(F) == true`.
2. Attacker submits transaction T2 with different `sender_address`/`calldata`/`resource_bounds` but the identical `proof_facts=F`, paired with an arbitrary or malformed `proof=P2` (e.g., empty-content garbage bytes that would fail `verify_proof`).
3. `run_proof_verification` calls `contains_proof(F)` → `true` → returns `Ok(false)` and never invokes `verify_proof(F, P2)`; T2 is treated as having a validated proof despite `P2` never having been checked against its own content.

        &self,
        block_context: &BlockContext,
        state: &mut dyn State,
    ) -> TransactionPreValidationResult<()> {
        // Only Invoke V3 transactions can carry proof facts.
        let Transaction::Invoke(invoke_tx) = &self.tx else {
            return Ok(());
        };
        if invoke_tx.version() < TransactionVersion::THREE {
            return Ok(());
        }

        // Parse proof facts.
        let proof_facts = invoke_tx.proof_facts();
        let snos_proof_facts = match ProofFactsVariant::try_from(&proof_facts)
            .map_err(|e| TransactionPreValidationError::InvalidProofFacts(e.to_string()))?
        {
            ProofFactsVariant::Empty => return Ok(()),
            ProofFactsVariant::Snos(snos_proof_facts) => snos_proof_facts,
        };
        let os_constants = &block_context.versioned_constants.os_constants;

        if !os_constants.allowed_proof_versions.contains(&snos_proof_facts.proof_version.as_felt())
        {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Proof version {} is not allowed under this protocol version.",
                snos_proof_facts.proof_version
            )));
        }

        // Validate the program hash.
        let allowed = &os_constants.allowed_virtual_os_program_hashes;
        if !allowed.contains(&snos_proof_facts.program_hash) {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS program hash {} is not allowed",
                snos_proof_facts.program_hash
            )));
        }

        // Validate the block hash and block number.
        let proof_block_hash = snos_proof_facts.block_hash.0;
        let proof_block_number = snos_proof_facts.block_number.0;
        Self::validate_proof_block_number(
            proof_block_number,
            block_context.block_info.block_number,
        )?;
        Self::validate_proof_block_hash(proof_block_hash, proof_block_number, os_constants, state)?;

        // Validate the config hash.
        let virtual_os_config_hash = block_context.virtual_os_config_hash();
        let proof_config_hash = snos_proof_facts.config_hash;
        if virtual_os_config_hash != proof_config_hash {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS config hash mismatch. Computed virtual OS config hash: \
                 {virtual_os_config_hash}, expected virtual OS config hash: {proof_config_hash}."
            )));
        }

        Ok(())
