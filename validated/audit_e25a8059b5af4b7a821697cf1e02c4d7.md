### Title
Improper Certificate Validation in the Transaction Prover's Blocking-Check HTTP Client — ([File: crates/starknet_transaction_prover/src/blocking_check.rs])

### Summary
`BlockingCheckClient::new` unconditionally builds its `reqwest::Client` with `.danger_accept_invalid_certs(true)`, disabling TLS certificate validation for all calls to the external "blocking check" (`starknet_checkTransaction`) service that the prover consults before generating a proof for a client-submitted transaction. [1](#0-0) 

### Finding Description
`prove_transaction` — reachable by any unprivileged caller who submits an `RpcTransaction` to the prover — optionally routes the transaction through an external blocking/screening check before proving it, via `prove_with_blocking_check`. [2](#0-1) 
That check is performed over HTTPS by `BlockingCheckClient`, whose `reqwest::Client` is constructed with `danger_accept_invalid_certs(true)`, meaning the client accepts *any* certificate — self-signed, expired, wrong hostname, or attacker-issued — from whatever host responds at `blocking_check_url`. [1](#0-0) 

This is the same root-cause bug class as the reported Graylog CVE-2020-15813: a network client that talks to a security-relevant external service (there, an LDAP directory used for authentication; here, a compliance/screening oracle used to gate whether a transaction may be proven) performs no certificate validation, so an on-path attacker can transparently redirect the connection to an attacker-controlled endpoint without the client noticing, defeating the entire trust model of the external check.

The response from this endpoint directly controls a security decision: `check_transaction` parses the JSON-RPC response and yields `Allowed`, `Blocked`, or `Inconclusive` [3](#0-2) 
and `prove_with_blocking_check` uses that outcome (plus the `fail_open` policy on inconclusive/timeout) to decide whether to abort proving (`TransactionBlocked`) or to proceed and return a proof, additionally relaying an opaque `additional_data`/screening signature verbatim into the response. [4](#0-3) 

### Impact Explanation
An attacker able to intercept or redirect traffic between the prover and the configured `blocking_check_url` (e.g. via DNS spoofing, ARP/route manipulation, or compromising an intermediate network hop — the same threat model as the original Graylog advisory) can:
- Force every check to return `Allowed`, spoofing an `additional_data`/screening-signature payload that the prover relays verbatim as trusted output, effectively forging compliance/screening approval for a transaction that the real screening service would have blocked (unauthorized account action / bypass of an intended access-control gate).
- Force `Blocked` on arbitrary legitimate transactions, causing denial of proof service for a targeted user.

Because the check gates whether the prover produces a proof at all, and the additional_data is treated as an authoritative "screening signature" that downstream consumers may rely on, defeating certificate validation here undermines the integrity guarantee the blocking-check mechanism exists to provide — a concrete unauthorized-action outcome, not merely a resource/DoS issue.

### Likelihood Explanation
The vulnerable code path executes on every `prove_transaction` call when a blocking-check client is configured (a supported, documented production configuration, not test/mock-only) and requires no privileged position beyond a standard on-path network attacker — the same attacker capability assumed in the source advisory. No cryptographic key compromise or insider access is required; only network position between the prover process and the check service.

### Recommendation
Remove `danger_accept_invalid_certs(true)` from `BlockingCheckClient::new` and use the default `reqwest::Client` TLS validation (or, if a private/self-signed CA is legitimately used for this internal service, pin that specific CA certificate/root store instead of disabling validation altogether). Enforce hostname verification and certificate chain validation for the `blocking_check_url` connection just as is done for the server-side TLS acceptor in `crates/starknet_transaction_prover/src/server/tls.rs`.

### Proof of Concept
1. Deploy the prover with `blocking_check_url` pointing at `https://check.internal.example`.
2. As a network-position attacker (e.g., via ARP spoofing / DNS hijack / compromised router on the path to `check.internal.example`), redirect the TCP connection to an attacker-controlled server presenting a self-signed or arbitrary certificate.
3. Submit any transaction to the prover's `starknet_proveTransaction` endpoint. Because `BlockingCheckClient` calls `.danger_accept_invalid_certs(true)`, the TLS handshake succeeds against the attacker's certificate [5](#0-4) 
4. The attacker's server returns a crafted JSON-RPC success response with a forged `additional_data`/signature, which `check_transaction` parses as `Allowed` [6](#0-5) 
5. `prove_with_blocking_check` proceeds to produce and return a proof carrying the forged `additional_data`, bypassing the intended screening/blocking control. [7](#0-6)

    /// Sends `starknet_checkTransaction` to the external service and interprets the response.
    pub(crate) async fn check_transaction(
        &self,
        block_id: BlockId,
        transaction: RpcTransaction,
    ) -> BlockingCheckResult {
        let request_body = JsonRpcRequest {
            jsonrpc: "2.0",
            method: "starknet_checkTransaction",
            params: CheckTransactionParams { block_id, transaction },
            id: 1,
        };

        let response =
            match self.http_client.post(self.url.as_str()).json(&request_body).send().await {
                Ok(resp) => resp,
                Err(err) => {
                    warn!("Blocking check request failed: {err}");
                    return BlockingCheckResult::Inconclusive;
                }
            };

        // Only a 2xx response carries a trustworthy decision. A non-success status (e.g. a 5xx
        // from a broken upstream) may still return a body without an `error` field, which would
        // otherwise deserialize to `Allowed` and bypass the operator's fail-close policy.
        let status = response.status();
        if !status.is_success() {
            warn!("Blocking check returned non-success HTTP status: {status}");
            return BlockingCheckResult::Inconclusive;
        }

        let body = match response.text().await {
            Ok(text) => text,
            Err(err) => {
                warn!("Failed to read blocking check response body: {err}");
                return BlockingCheckResult::Inconclusive;
            }
        };

        let json_rpc_response: JsonRpcResponse = match serde_json::from_str(&body) {
            Ok(parsed) => parsed,
            Err(err) => {
                warn!("Failed to parse blocking check response: {err}");
                return BlockingCheckResult::Inconclusive;
            }
        };

        match json_rpc_response.error {
            None => BlockingCheckResult::Allowed(
                json_rpc_response.result.and_then(|check_result| check_result.additional_data),
            ),
            Some(err) if err.code == BLOCKED_ERROR_CODE => BlockingCheckResult::Blocked,
            Some(err) => {
                warn!("Blocking check returned non-blocking error code: {}", err.code);
                BlockingCheckResult::Inconclusive
            }
        }
    }

    async fn prove_with_blocking_check(
        &self,
        client: &BlockingCheckClient,
        block_id: BlockId,
        transaction: RpcTransaction,
        invoke_tx: InvokeTransaction,
    ) -> Result<ProveTransactionResult, VirtualSnosProverError> {
        // Kick off proving in parallel with the check. Clone is cheap: inner fields are
        // Arcs or small configs.
        let prover = self.clone();
        let prove_handle =
            tokio::spawn(async move { prover.run_and_prove(block_id, vec![invoke_tx]).await });

        let timeout_duration = std::time::Duration::from_millis(client.timeout_millis);
        let check_outcome =
            tokio::time::timeout(timeout_duration, client.check_transaction(block_id, transaction))
                .await;

        // A transaction allowed via the fail-open policy (inconclusive check or
        // timeout) carries no additional_data.
        let (allow, additional_data) = match check_outcome {
            Ok(BlockingCheckResult::Blocked) => {
                info!("Transaction blocked by external check");
                (false, None)
            }
            Ok(BlockingCheckResult::Allowed(additional_data)) => {
                info!("Transaction allowed by external check");
                (true, additional_data)
            }
            Ok(BlockingCheckResult::Inconclusive) => {
                info!(fail_open = client.fail_open, "Blocking check inconclusive");
                (client.fail_open, None)
            }
            Err(_) => {
                info!(fail_open = client.fail_open, "Blocking check timed out");
                (client.fail_open, None)
            }
        };

        if !allow {
            prove_handle.abort();
            return Err(VirtualSnosProverError::TransactionBlocked);
        }

        let mut result = match prove_handle.await {
            Ok(prove_result) => prove_result?,
            Err(err) if err.is_panic() => std::panic::resume_unwind(err.into_panic()),
            Err(err) => unreachable!("prove task cancelled unexpectedly: {err}"),
        };
        result.additional_data = additional_data;
        Ok(result)
    }
