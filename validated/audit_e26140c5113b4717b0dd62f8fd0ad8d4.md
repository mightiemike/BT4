### Title
Missing Validate-Mode Restriction on `replace_class` Syscall Allows Class-Swap During Transaction Validation - (File: crates/blockifier/src/execution/syscalls/syscall_base.rs)

### Summary
Starknet restricts a defined set of syscalls during the `__validate__`/`__validate_declare__`/`__validate_deploy__` execution phase (`ExecutionMode::Validate`) to prevent state-changing or context-leaking operations before the transaction is admitted to the mempool/block. `call_contract`, `deploy`, `get_block_hash`, `get_class_hash_at`, and `meta_tx_v0` all explicitly check `ExecutionMode::Validate` and reject themselves via `reject_syscall_in_validate_mode`/`InvalidSyscallInExecutionMode`. `replace_class`, however, contains no such check and unconditionally rewrites the calling contract's class hash in state, exactly the analog of CVE-2019-14812's `.setuserparams2`, a privileged operation callable from an otherwise-restricted/sandboxed execution context because the sandbox failed to gate it like its sibling operations.

### Finding Description
In `SyscallHandlerBase::replace_class` [1](#0-0) , the implementation only checks that the target class is declared and is a Cairo1 (V1) class before calling `self.state.set_class_hash_at(self.call.storage_address, class_hash)`. There is no check of `self.context.execution_mode == ExecutionMode::Validate`.

Compare this to the sibling syscalls in the same file that all guard against `ExecutionMode::Validate`:
- `get_class_hash_at` explicitly rejects in validate mode [2](#0-1) .
- `meta_tx_v0` explicitly rejects in validate mode [3](#0-2) .
- `get_block_hash` rejects "recent" block queries in validate mode via `reject_syscall_in_validate_mode` [4](#0-3) .
- The deprecated (Cairo0) `call_contract` syscall explicitly checks `is_validate_mode()` before permitting cross-contract calls [5](#0-4) .
- The `deploy` syscall is gated by `disable_deploy_in_validation_mode`, producing the error "Unauthorized syscall deploy in execution mode Validate" when active [6](#0-5) .

The Cairo1 native syscall handler forwards directly to `self.base.replace_class(...)` with no additional mode check either [7](#0-6) . The general helper `reject_syscall_in_validate_mode` exists precisely for this purpose but is never invoked from `replace_class` [8](#0-7) .

This is directly analogous to CVE-2019-14812: a supposedly "restricted" execution context (Ghostscript's `-dSAFER` sandbox / Starknet's `ExecutionMode::Validate`) exposes one specific privileged primitive (`.setuserparams2` / `replace_class`) that was not subjected to the same guard as its sibling privileged operations, letting a script/contract escalate out of the restricted phase.

### Impact Explanation
An account contract's `__validate__` runs in `ExecutionMode::Validate` under the assumption that it cannot mutate execution-relevant contract state or influence which code will run in the subsequent `__execute__` phase of the *same* transaction. Because `replace_class` is not blocked, a malicious account (or any contract reachable during validation, e.g. via other unguarded internal calls) can call `replace_class` on itself (or on state it controls) during validation to overwrite its own class hash. Since state writes performed in the validate stage persist into the execute stage of the same transaction, this allows the account to swap the class that will actually run `__execute__` (and any subsequent `get_class_hash_at`/dispatch logic depending on this class hash) after validation has already "passed" against the original, honest class. This can be used to:
- Bypass intended validation semantics (validate against class A's logic, then execute class B's logic within the same transaction), undermining the security guarantee that `__validate__` output authorizes the specific code that will execute.
- Corrupt sequencer/mempool assumptions about fee estimation and resource bounds computed against the validating class, since the executing class can differ, causing under/over-charged resources or unexpected reverts — a form of unauthorized account action.

This qualifies as "unauthorized account action" / mempool-admission and execution-consistency divergence reachable purely from a single submitted transaction (no privileged operator needed).

### Likelihood Explanation
High likelihood of reachability: any account contract (declared and deployed by any unprivileged user) can invoke `replace_class` from within its own `__validate__` entry point. No special permission, staking, or operator role is required — only a deployed account whose `__validate__` calls the `replace_class` syscall, which is a standard, widely-used Starknet syscall exposed to all Cairo1 contracts.

### Recommendation
Add an `ExecutionMode::Validate` guard to `SyscallHandlerBase::replace_class` consistent with the other state/context-affecting syscalls, e.g.:
```rust
pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
    if self.context.execution_mode == ExecutionMode::Validate {
        self.reject_syscall_in_validate_mode("replace_class")?;
    }
    // ... existing logic
}
```
This should be applied uniformly to any Cairo1 (`crates/blockifier/src/execution/syscalls/syscall_base.rs`) and Cairo0 deprecated equivalents to close the asymmetry, and covered by a regression test analogous to `disable_deploy_in_validate_mode_flag_behavior` / the `test_block_info_syscalls`/`test_forbidden_syscall` cases already present for `deploy`, `get_block_hash`, `get_class_hash_at`, and `meta_tx_v0`.

### Proof of Concept
1. Declare and deploy an account contract `A` whose `__validate__` entry point (a) performs the normal signature check expected by the network, then (b) calls `replace_class_syscall(class_hash_B)` where `class_hash_B` is a different declared class implementing a permissive/backdoored `__execute__`.
2. Submit an `INVOKE`/`DEPLOY_ACCOUNT` transaction from account `A`. During the blockifier's validate phase (`ExecutionMode::Validate`), `__validate__` succeeds and, without being blocked, executes `replace_class`, rewriting `A`'s class hash to `class_hash_B` in state (verifiable via `SyscallHandlerBase::replace_class`, `crates/blockifier/src/execution/syscalls/syscall_base.rs:369-378`, which performs `self.state.set_class_hash_at(...)` unconditionally).
3. When the transaction proceeds to `__execute__`, the sequencer/OS looks up the (now-changed) class hash for `A` and executes `class_hash_B`'s logic instead of the class that was actually validated, demonstrating validate/execute code divergence within a single transaction — something the `ExecutionMode::Validate` restrictions on `deploy`, `call_contract`, `get_block_hash`, `get_class_hash_at`, and `meta_tx_v0` were specifically designed to prevent (see the analogous negative tests, e.g. `crates/blockifier/src/execution/syscalls/syscall_tests/deploy.rs:323-361` and `crates/blockifier/src/transaction/transactions_test.rs:2464-2540`, none of which exist for `replace_class`).

    pub fn get_block_hash(&mut self, requested_block_number: BlockNumber) -> SyscallResult<Felt> {
        // Note: we take the actual block number (and not the rounded one for validate)
        // in any case; it is consistent with the OS implementation and safe (see `Validate` arm).
        let current_block_number = self.context.tx_context.block_context.block_info.block_number;

        if !block_number_in_range(requested_block_number, current_block_number) {
            // Requested block is too recent.
            match self.context.execution_mode {
                ExecutionMode::Execute => {
                    // Revert the syscall.
                    return Err(SyscallExecutionError::Revert {
                        error_data: vec![BLOCK_NUMBER_OUT_OF_RANGE_ERROR_FELT],
                    });
                }
                ExecutionMode::Validate => {
                    // In this case, the transaction must be **rejected** to avoid the following
                    // attack:
                    //   * query a given block in validate,
                    //   * if reverted - ignore, if succeeded - panic.
                    //   * in the gateway, the queried block is (actual_latest - 9),
                    //   * while in the sequencer, the queried block can be further than that.
                    self.reject_syscall_in_validate_mode("get_block_hash on recent blocks")?;
                }
            }
        }

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
