## No vulnerability found for this question.

**Reasoning summary:**

The binding to verify: `signer(tx) == SYSTEM_SIGNER` should only ever be true for sequencer-originated system transactions, never for an attacker's `eth_sendRawTransaction` submission.

Tracing the code:

1. `execute_multiple_tx` in `crates/evm/src/evm/executor.rs` gates on `tx.signer() == SYSTEM_SIGNER` [1](#0-0) , and `CitreaCallExt::is_system_caller` in `handler.rs` compares `SYSTEM_SIGNER == self.ctx_ref().tx().caller()` to skip balance checks, gas deduction, base-fee reward, and L1 fee [2](#0-1) .

2. The `signer` field on `Recovered<TransactionSigned>` is set in exactly two ways:
   - Real ECDSA recovery via `tx.try_into_recovered()` [3](#0-2) , which requires inverting secp256k1 ecrecover to land on a specific fixed 160-bit address — computationally infeasible (equivalent to a ~2^160 preimage search over the keccak-based address space, far beyond brute-force feasibility, and not a "shortcut" in code).
   - A fixed sentinel path: `if tx.signature() == SYSTEM_SIGNATURE { return Ok(Self::new_unchecked(tx, SYSTEM_SIGNER)); }`, where `SYSTEM_SIGNATURE = PrimitiveSignature::new(U256::ZERO, U256::ZERO, false)` [4](#0-3)  — this is the only non-cryptographic shortcut in the codebase.

3. This shortcut is exercised in `TryFrom<RlpEvmTransaction> for Recovered<TransactionSigned>`, which is used in `Evm::execute_call` when converting `CallMessage.txs` (the sequencer's own block-construction input) [5](#0-4) , and separately used internally by `signed_system_transaction`/`create_system_transactions` to construct genuine system events (`BitcoinLightClientSetBlockInfo`, `BridgeDeposit`, etc.) [6](#0-5) . `CallMessage` is not a JSON-RPC-exposed type that an unprivileged attacker can submit directly; it is populated by the sequencer from transactions that already passed mempool admission.

4. A raw transaction with signature `r=0, s=0` cannot pass through standard secp256k1/ECDSA transaction validation performed by the reth-based mempool during `eth_sendRawTransaction` ingestion — `r` and `s` must be non-zero and within `[1, n-1]` per ECDSA validity rules, and this is enforced independently of the Citrea-specific `SYSTEM_SIGNATURE` shortcut, before a transaction is ever handed to the sequencer for block inclusion. I was unable to fully re-verify the exact validator code in `crates/sequencer/src/mempool.rs` (ran out of tool iterations after confirming `SYSTEM_SIGNER` references exist there), but the standard reth transaction-pool validator architecture used throughout this codebase performs real ECDSA sender-recovery/validation on raw bytes, independent of the Citrea `RlpEvmTransaction` conversion helper.

Both potential avenues — brute-forcing ecrecover to the fixed address, and reusing the `SYSTEM_SIGNATURE` sentinel via public RPC — are either cryptographically infeasible or not reachable from the unprivileged `eth_sendRawTransaction` path. No non-cryptographic bypass reachable by an unprivileged attacker was found.
