### Title
L1 handler transactions that legitimately exceed the fixed `l1_handler_max_amount_bounds` are permanently marked as consumed while all state changes are rolled back, causing irrecoverable loss of the L1-to-L2 message value - (File: crates/blockifier/src/transaction/l1_handler_transaction.rs)

### Summary
`L1HandlerTransaction::execute_raw` enforces a fixed, protocol-wide gas cap (`l1_handler_max_amount_bounds`) on every L1-to-L2 message handler, independent of how the message's L1 sender configured it (L1 handlers have no user-settable resource bounds, unlike ordinary invoke transactions). If a legitimate `#[l1_handler]` entry point (e.g., a token bridge deposit handler) needs more gas than this fixed cap — which can happen deterministically depending on contract/state complexity — the post-execution check fails, the transactional state is aborted, but the function still returns `Ok(...)` (not an execution `Err`). At the batcher level this "Ok-but-reverted" transaction is inserted into `consumed_l1_handler_tx_hashes` and committed as permanently processed, exactly like a genuinely successful handler, while none of its state effects (e.g., crediting bridged tokens to the depositor) are applied. This mirrors the Tokemak bug class: an all-or-nothing threshold (`MIN_STAKE_AMOUNT` there, `l1_handler_max_amount_bounds` here) causes legitimately-owed value to be permanently and irrecoverably lost/frozen because the atomic unit that enforces the threshold also consumes/finalizes the triggering action.

### Finding Description
`L1HandlerTransaction::execute_raw` reads a fixed constant from versioned constants: [1](#0-0) 

After execution succeeds at the Cairo level, the code performs a *post-execution* gas-bounds check against this fixed cap: [2](#0-1) 

If `check_all_gas_amounts_within_bounds` fails (`MaxGasAmountExceeded`), the transactional state is aborted (`execution_state.abort()`), discarding all writes the handler made (e.g., crediting a bridged deposit). Critically, the function still returns `Ok(l1_handler_tx_execution_info(None, receipt, Some(fee_check_error.into())))` — an `Ok` result carrying a `revert_error`, not an `Err`. This is confirmed by the existing unit test that documents this exact behavior: [3](#0-2) 

At the block-building layer, `collect_execution_results_and_stream_txs` unconditionally inserts every L1 handler transaction's hash into `consumed_l1_handler_tx_hashes` *before* even inspecting whether the execution `result` was `Ok` or `Err`: [4](#0-3) 

Only if `execute_raw` returns a genuine `Err` (e.g. `TransactionExecutorError::StateError`) is the hash additionally placed into `rejected_tx_hashes`, which is later used to "unstage" the L1 message and keep it `Pending`/retryable (per the documented flow): [5](#0-4) 

Because the `MaxGasAmountExceeded` case returns `Ok(...)` (only warning-logged as "reverted during execution while still accepted"), it is **not** added to `rejected_tx_hashes`, so it is never unstaged/retried — it is treated the same as a genuinely successful message and gets committed as `Committed`/consumed: [6](#0-5) 

This is the direct analog of the Tokemak bug: a fixed all-or-nothing threshold (`MIN_STAKE_AMOUNT` in Tokemak, `l1_handler_max_amount_bounds` here) is checked *after* the beneficial state changes were computed, and failing that check destroys the value while the "receipt"/consumption bookkeeping still proceeds as if the action succeeded — with no path to retry, because the L1 message's gas requirement is deterministic and will exceed the fixed cap on every future attempt as well.

### Impact Explanation
Any L1-to-L2 message (e.g. a bridge deposit, cross-chain call, or any contract's `#[l1_handler]` entry point) whose deterministic gas usage exceeds the protocol's fixed `l1_handler_max_amount_bounds` will:
1. Have all its state effects rolled back (the depositor never receives the credited funds/tokens on L2).
2. Nevertheless be recorded as `consumed`, and once the block is committed, the L1-to-L2 message is finalized as processed and can never be resubmitted or retried.

This results in permanent, irrecoverable loss of the value that the L1 sender locked/burned to trigger the message — a "stuck in the contract forever" scenario, directly analogous to the Tokemak users whose TOKE rewards below `MIN_STAKE_AMOUNT` become permanently unwithdrawable. Since the L1 handler's gas usage is deterministic for a given calldata/state, there is no way for the affected user to recover by resending — the message is consumed exactly once and the underlying assets are effectively frozen/lost.

### Likelihood Explanation
This is reachable by any L1 message sender (an in-scope unprivileged actor per the rules) simply by triggering a legitimate `#[l1_handler]` call whose gas cost (due to contract complexity, larger payload, or accumulated state) exceeds the fixed bound — no malicious operator/proposer/peer behavior is required, and it does not depend on network conditions. The bound is a protocol constant applied uniformly to all L1 handlers regardless of application-specific gas needs, making the failure mode systemic rather than a one-off edge case; any sufficiently gas-heavy but entirely legitimate bridge/L1-handler contract logic can trigger it.

### Recommendation
When the post-execution `check_all_gas_amounts_within_bounds` fails for an L1 handler transaction, do not report `Ok(...)` with the state aborted as if the message were finalized. Instead, treat this case the same as the `Err(execution_error)` branch: propagate it as a genuine execution error (or otherwise mark the transaction hash as rejected, not consumed) so that `collect_execution_results_and_stream_txs` places it into `rejected_tx_hashes`/unstages it, allowing the message to remain `Pending` and be retried (e.g., with a future increase in resource limits, contract upgrade, or reduced computation), rather than permanently discarding the associated funds/state effects while marking the message as irrevocably consumed.

### Proof of Concept
1. Deploy a contract with an `#[l1_handler]` entry point that performs meaningful state-changing work proportional to attacker/legitimate-controlled calldata (e.g., writes to many storage slots, similar to the `l1_handler_set_value_and_revert`/`write_a_lot` patterns already used in tests: [7](#0-6) ).
2. Send an L1-to-L2 message (as an unprivileged L1 message sender) whose calldata makes the handler's actual gas usage exceed `l1_handler_max_amount_bounds.l2_gas` (or `.l1_gas`/`.l1_data_gas`), similar to how the existing test artificially lowers the bound to trigger `MaxGasAmountExceeded`: [8](#0-7) .
3. Observe that `execute_raw` returns `Ok(...)` with `revert_error: Some(RevertError::PostExecution(FeeCheckError::MaxGasAmountExceeded {..}))` and all execute-side state changes discarded (`validate_call_info: None, execute_call_info: None`), matching the assertion in the test.
4. Trace through `collect_execution_results_and_stream_txs`: since `result` is `Ok`, the transaction hash is inserted into `consumed_l1_handler_tx_hashes` and is never placed into `rejected_tx_hashes` (which only happens on the `Err` branch): [9](#0-8) .
5. Confirm via `failed_l1_handler_transaction_consumed` that only `Err(...)` results are excluded from being committed as consumed, while an `Ok(...)`-with-revert result (as produced here) is included in `consumed_l1_handler_tx_hashes` and thus permanently finalized despite the L1 sender's funds never actually being credited on L2: [10](#0-9) .

fn test_l1_handler_resource_bounds(#[case] resource: Resource, #[case] new_bound: GasAmount) {
    let test_contract = FeatureContract::TestContract(CairoVersion::Cairo1(RunnableCairo1::Casm));

    // Set to true to ensure L1 data gas is non-zero.
    let use_kzg_da = true;

    let mut block_context = BlockContext::create_for_account_testing_with_kzg(use_kzg_da);
    let chain_info = block_context.chain_info.clone();
    let mut state = test_state(&chain_info, BALANCE, &[(test_contract, 1)]);
    let contract_address = test_contract.get_instance_address(0);

    // Modify the resource bound for the tested resource.
    let os_constants = Arc::make_mut(&mut block_context.versioned_constants.os_constants);
    match resource {
        L1Gas => os_constants.l1_handler_max_amount_bounds.l1_gas = new_bound,
        L2Gas => os_constants.l1_handler_max_amount_bounds.l2_gas = new_bound,
        L1DataGas => os_constants.l1_handler_max_amount_bounds.l1_data_gas = new_bound,
    }

    let tx = l1handler_tx(Fee(1), contract_address);

    let execution_info = tx.execute(&mut state, &block_context).unwrap();

    assert_matches!(
        execution_info,
        TransactionExecutionInfo {
            validate_call_info: None,
            execute_call_info: None,
            fee_transfer_call_info: None,
            revert_error: Some(RevertError::PostExecution(FeeCheckError::MaxGasAmountExceeded {
                resource: r,
                max_amount,
                actual_amount
            })),
            // TODO(Arni): consider checking other fields of the receipt.
            receipt: TransactionReceipt { fee, .. },
        } if r == resource && new_bound == max_amount && actual_amount > max_amount && fee == Fee(0)
