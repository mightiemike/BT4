### Title
Missing length validation on `ask`/`alpha`/`dataToBeSigned` before native JNI call in `ZenTransactionBuilder.createSpendAuth` - ([File: framework/src/main/java/org/tron/core/zen/ZenTransactionBuilder.java])

### Summary
`ZenTransactionBuilder.createSpendAuth` passes `expsk.getAsk()` and `alpha` byte arrays directly into the native `JLibrustzcash.librustzcashSaplingSpendSig` JNI call with no length or null checks. Shielded-transaction build flows (`build(true)`) populate `spends` from client-supplied key/note material via `addSpend`, and no length validation is performed anywhere in this class before the native boundary is crossed.

### Finding Description
`createSpendAuth` iterates over `spends` and directly calls the native signer: [1](#0-0) 

Unlike `generateOutputProof`, which does validate `ovk.length != 32` before use, `createSpendAuth` performs no such check on `expsk.getAsk()`, `spends.get(i).alpha`, or `dataToBeSigned` lengths: [2](#0-1) 

`spends` entries are populated through several `addSpend` overloads, at least one of which stores raw `ExpandedSpendingKey`/`alpha`/`anchor` byte arrays supplied by the caller with no size validation at construction time: [3](#0-2) 

The native Sapling signing routine (`librustzcashSaplingSpendSig`) expects fixed-size byte buffers (32-byte `ask`/`alpha`, 32-byte message digest) on the Rust side. If Java-side arrays of the wrong length are passed across the JNI boundary, the Rust implementation's fixed-size array conversion (e.g. `try_into()` on a slice) will panic; a Rust panic unwinding across an FFI/JNI boundary is undefined behavior and, by default, aborts the JVM process rather than throwing a catchable Java exception. This is a real DoS-class primitive because Java code has no defensive length check to reject malformed input before it reaches the native library.

### Impact Explanation
If reachable with attacker-controlled byte lengths, the impact is a node crash (process abort) via the native library boundary, matching TRON's "DoS via the TRON protocol implementation" bounty class. Full RCE cannot be confirmed from this code path alone (no evidence of memory corruption beyond panic/abort semantics), so the concrete confirmed impact is node crash/DoS, not confirmed RCE.

### Likelihood Explanation
Reachability depends on how upstream RPC/HTTP handlers (e.g. `Wallet.createShieldedTransaction`/`Wallet.createSpendAuthSig`, `CreateSpendAuthSigServlet`) convert client-supplied protobuf `bytes` fields (`ask`, `alpha`) into the `ExpandedSpendingKey`/`SpendDescriptionInfo` objects consumed here. I could not fully verify from available context whether `Wallet.java` or `ExpandedSpendingKey`'s constructor enforces a 32-byte length constraint on these fields before they reach `ZenTransactionBuilder.createSpendAuth`; this is a gap in my analysis given tool-call limits. What is confirmed directly from the code is that `ZenTransactionBuilder.createSpendAuth` itself performs zero length validation — the class's own invariant ("validates all lengths before the JNI/native call") is false for this method, unlike the sibling `generateOutputProof` method which does check `ovk` length. If any upstream caller fails to enforce fixed sizes on `ask`/`alpha` bytes (protobuf `bytes` fields impose no length constraint by default), this defect is directly exploitable by an unprivileged client submitting a shielded transaction build/sign request.

### Recommendation
Add explicit length assertions in `createSpendAuth` before calling `JLibrustzcash.librustzcashSaplingSpendSig`, e.g. require `expsk.getAsk() != null && expsk.getAsk().length == 32`, `alpha != null && alpha.length == 32`, and `dataToBeSigned != null && dataToBeSigned.length == 32`, throwing `ZksnarkException` otherwise — mirroring the existing `ovk.length != 32` check already present in `generateOutputProof`. Additionally, harden the JNI layer (`JLibrustzcash`) to validate array lengths in Java before invoking any native method, so no code path can reach the native library with unchecked-length buffers.
