### Title
Malformed-length signer keys silently coerced to the all-zero key, poisoning signer weight accounting - ([File: stackslib/src/chainstate/nakamoto/signer_set.rs])

### Summary
`RawRewardSetEntry::from_pox_4_tuple` parses the `signer` field returned from the `pox-4`/`pox-5` PoX contracts as a `(buff 33)` value. Clarity's `(buff 33)` type only bounds the *maximum* length of the buffer, not its minimum, so a stacker can lock STX with a signer-key shorter than 33 bytes. When the Rust code encounters such a non-33-byte buffer, instead of rejecting or skipping the malformed entry, it silently substitutes an all-zero 33-byte array as the signing key.

The comment on line 310 explicitly acknowledges that the `(buff 33)` Clarity type does not enforce a minimum length, meaning a caller can supply a signer-key of any length ≤ 33 bytes (including 0 bytes). Rather than treating a wrong-length key as an error and excluding that entry (as is done elsewhere for genuinely inconsistent/zero-value state, e.g. the PoX-5 iterator explicitly skips entries with zero delegated µSTX), this code converts *any* malformed-length key into the exact same all-zero value `[0; 33]`.

That value then flows into `StacksChainState::make_signer_set`, which groups entries by `signing_key` and sums their `amount_stacked`: [3](#0-2) 

Any number of stackers who (deliberately or accidentally) end up with a non-33-byte `signer` value in their PoX reward-set entry will have their stacked amounts merged into a single phantom "signer" whose signing key is all zeros — a key for which no one can possibly hold the corresponding private key (it isn't a valid secp256k1 public key point). If the combined stacked amount of these entries crosses the reward-slot threshold, this phantom entry becomes a real `NakamotoSignerEntry` with non-zero `weight`, included in the `.signers` contract and used for the Nakamoto signer quorum and the `signers-voting` aggregate-key threshold (`get-threshold-weight`, `get-signer-weight`) in `stackslib/src/chainstate/stacks/boot/signers-voting.clar`.

### Impact Explanation
This breaks the intended equality that "signer weight in the reward/signer set corresponds to a real, key-holding signer". Weight assigned to the coerced all-zero key is permanently unsignable — no party can produce a valid signature attributable to it. Any minority stacker (no majority or admin privilege required — only needing to end up with a malformed-length `signer` buffer in their locked PoX-4/PoX-5 entry) can inflate this dead-weight bucket, silently reducing the pool of *live*, sign-capable weight relative to the *nominal* total weight used for the Nakamoto block-signing/aggregate-key threshold. This can push the network toward being unable to reach the required signing threshold (a temporary tip/signing disagreement or stall bounded to that reward cycle), which falls under the "High" impact category (minority-triggerable signer weight divergence from the correct set).

### Likelihood Explanation
Reaching this path requires only an ordinary, unprivileged PoX-4/PoX-5 stacking transaction whose `signer-key` argument is not exactly 33 bytes. The Clarity contract type signature `(buff 33)` does not prevent this at the type level, and the Rust-side ingestion code confirms in its own comment that this length is unchecked. I could not fully verify in this session whether the current `pox-4.clar` signature-authorization path (`verify-signer-key-sig`/`consume-signer-key-authorization`, or the self-service `set-signer-key-authorization` path) rejects a length-mismatched key before it is persisted into `reward-cycle-pox-address-list`; this is the main remaining uncertainty. If a self-authorization or aggregate-commit path allows a stacker to register a non-33-byte key without a value-matching signature check, the likelihood is high and requires no privileged access.

### Recommendation
In `from_pox_4_tuple` (and the analogous PoX-5 signer-key extraction path), treat a `signer` buffer whose length is not exactly `SIGNERS_PK_LEN` (33) as a hard/skip error (as is already done elsewhere in this file for zero-valued delegated µSTX), rather than silently coercing it to the all-zero key. This prevents unrelated malformed entries from being merged into a single non-attributable "signer" and prevents dead weight from being injected into the Nakamoto signer set.

### Proof of Concept
1. Submit a `stack-stx` (or `delegate-stack-stx`/`stack-aggregation-commit`) transaction to `pox-4`/`pox-5` with a `signer-key` argument that is fewer than 33 bytes (permitted by the `(buff 33)` Clarity type) but whose associated authorization check passes (via `set-signer-key-authorization` self-authorization or an aggregate-commit flow that does not require a value-matching signature over the exact byte length).
2. When the reward/signer set for the cycle is computed, `RawRewardSetEntry::from_pox_4_tuple` reads this entry's `signer` buffer, finds `signer.len() != 33`, and coerces it to `[0; 33]` (`stackslib/src/chainstate/nakamoto/signer_set.rs:310-317`).
3. Repeat with one or more additional stackers producing the same malformed-length condition; their `amount_stacked` accumulates under the same all-zero signing key in `StacksChainState::make_signer_set` (`stackslib/src/chainstate/stacks/boot/mod.rs:1039-1049`).
4. If the combined amount crosses the PoX threshold, the resulting `.signers` reward set contains a `NakamotoSignerEntry` with `signing_key = [0;33]` and non-zero `weight`, contributing to the total weight used for Nakamoto's signing/aggregate-key thresholds, even though no party can ever produce a valid signature for this key.
