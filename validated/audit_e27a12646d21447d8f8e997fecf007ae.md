## Title
Swapped `account`/`market` fields when popping native arguments corrupts `TradingNativeKey::Position` state keys - (File: `aptos-move/framework/position-natives/src/natives.rs`)

### Summary
The `TSender` bug stems from code that pops/derives fields from an ordered payload using positional assumptions that don't match how the payload was actually laid out, causing values to be associated with the wrong identity. The same *class* of bug (mis-paired positional extraction of an ordered argument stack) is present in the Aptos-native `native_set_position` / `native_delete_position` implementations, which build the `StateKeyInner::TradingNative(TradingNativeKey::Position)` state key used to persist perpetual-trading positions.

### Finding Description
`native_set_position` and `native_delete_position` pop Move-native call arguments off a `VecDeque<Value>` using `pop_back()`, which removes elements in reverse of push order (i.e., last declared argument first). Given the Move-side calling convention (`exchange`, `account`, `market`, `position`, pushed front-to-back), the correct pop order to recover values in call order is: `position`, then `market`, then `account`, then `exchange`.

The code instead pops: [1](#0-0) 

```
let position_val = args.pop_back()...;   // correctly: position
let account: AccountAddress = safely_pop_arg!(args, AccountAddress);  // actually pops `market`
let market: AccountAddress = safely_pop_arg!(args, AccountAddress);   // actually pops `account`
let exchange: AccountAddress = safely_pop_arg!(args, AccountAddress); // correctly: exchange
```

The second and third pops are mislabeled: the value that is really the `market` address is bound to the local variable `account`, and the value that is really the `account` address is bound to the local variable `market`. The same swapped pair is then used verbatim to build the persisted key: [2](#0-1) 

The identical swap occurs in `native_delete_position`: [3](#0-2) 

`TradingNativeKey::Position{exchange, account, market}` is BCS-encoded verbatim (tag + three raw 32-byte addresses) into the physical `StateKey`, with no re-validation of field identity at encode time: [4](#0-3) 

Because `account` and `market` are transposed before the key is constructed, the write is committed under a state key that differs from the one the caller (and any correctly-implemented reader/verifier) would derive for `(exchange, account, market)`. This is architecturally the same integrity failure as the `TSender` bug: a positional/offset mismatch between how data is produced and how it's consumed causes the wrong entity (here, address `market` in the position of `account`, and vice versa) to become bound to the persisted value.

### Impact Explanation
This corrupts committed ledger state relative to the correct VM/application semantics:
- The `NativePosition` value ends up durably stored (and later reflected in the Jellyfish Merkle tree / state proofs) under `StateKey::position(exchange, market_addr, account_addr)` instead of `StateKey::position(exchange, account_addr, market_addr)`.
- Any query, proof, or subsequent Move read expecting the position at `(exchange, account, market)` will not find it (or will find/overwrite an unrelated position belonging to a different logical `(account, market)` pairing if the swapped tuple happens to coincide with another legitimate position key), effectively binding trading state to the wrong account/market identity.
- `native_delete_position` has the identical swap, so deletions target the wrong key too, potentially leaving a stale (never-deleted) position for the real `(account, market)` pair while erasing an unrelated position.
- Because this executes deterministically inside VM execution (not consensus-specific), all validators compute the same wrong state, so it does not cause a fork by itself, but it does mean the authoritative, authenticated ledger state (and any proof issued for it) is bound to the wrong account/market object — a state-commitment integrity violation matching the required impact class ("Authenticated API or state-view output bound to the wrong version, object, or proof context").

### Likelihood Explanation
This triggers on every ordinary, unprivileged call to `native_set_position`/`native_delete_position` (guarded only by the `NATIVE_POSITION` feature flag), with no special preconditions beyond the feature being enabled — i.e., it's not an edge case, it is the deterministic behavior of the natives whenever `account != market`.

### Recommendation
Do not rely on positional pop-order matching mnemonic variable names; pop arguments in the exact reverse order of the Move declaration and immediately verify/name them consistently, e.g.:
```rust
let market: AccountAddress = safely_pop_arg!(args, AccountAddress);
let account: AccountAddress = safely_pop_arg!(args, AccountAddress);
let exchange: AccountAddress = safely_pop_arg!(args, AccountAddress);
```
(or otherwise confirm against the actual `native_position.move` signature) and add a unit/property test asserting `native_set_position(exchange, account, market, pos)` followed by a read reproduces the position at the expected `(exchange, account, market)` key with `account != market`.

### Proof of Concept
1. Enable `FeatureFlag::NATIVE_POSITION`.
2. Call the Move entry that invokes `native_set_position(exchange, account, market, position)` with distinct `account` and `market` addresses.
3. Inspect the resulting write set: the `StateKey` written is `TradingNativeKey::Position{exchange, account: market, market: account}` (swapped), verifiable by decoding the key bytes produced by `StateKeyInner::encode` and comparing to the expected `(exchange, account, market)` ordering supplied by the caller.
4. A subsequent lookup for the position at the caller-supplied `(exchange, account, market)` returns nothing (or a stale/foreign value), while the true position resides at the swapped key — demonstrating state committed under the wrong identity, mirroring the address/amount mix-up in the original `TSender` report.

*Note:* I could not directly view `aptos-move/framework/aptos-experimental/sources/trading/position/native_position.move` (Move-side native declaration) in this session to re-confirm the exact declared parameter order; the analysis above assumes the conventional `(exchange, account, market, position)` order implied by the variable names and by the symmetric field order used in `TradingNativeKey::Position` and `StateKeyRegistry::position`. If the Move declaration instead orders parameters as `(exchange, market, account, position)`, the pops would be correct and this finding would not hold — this should be verified by reading that `.move` file directly in a full development environment.
