### Title
Unbounded array growth in KV session storage shop-index causes DoS of session-lookup/auth handlers - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`KVSessionStorage` maintains a secondary index (`shop:<shop>` key) that lists all session IDs belonging to a shop, used by `findSessionsByShop`. Every call to `storeSession` unconditionally appends the session ID to this index array without checking for duplicates or bounding its size, mirroring the "unbounded array + full iteration" pattern described in the external report (an ever-growing array that is fully scanned on every lookup, eventually making the operation prohibitively expensive).

### Finding Description
`storeSession` calls `addShopIds(session.shop, [session.id])` on every store operation: [1](#0-0) 

`addShopIds` simply reads the existing array and concatenates the new ID(s), with no de-duplication and no cap on size: [2](#0-1) 

Offline sessions use a deterministic ID (`offline_<shop>`), so every re-authentication of the same shop (e.g. re-installing the app, refreshing an expired/invalid session, or any flow that causes `storeSession` to run again for that shop) appends another duplicate entry to the shop's ID array instead of replacing it. Because OAuth/token flows in this repo are triggered by unauthenticated redirects (e.g. `ensureInstalledOnShop` redirecting to `/auth` whenever no valid session is found) this array can be driven to grow indefinitely by repeated, attacker-triggerable authentication attempts against a single shop: [3](#0-2) 

`findSessionsByShop` then loads every ID in that (ever-growing, duplicate-laden) array on each call: [4](#0-3) 

This function is relied upon by `AppInstallations.includes`/`AppInstallations.delete`, which are invoked from the `APP_UNINSTALLED` webhook handler — a request path reachable by any actor able to deliver (or spoof delivery timing of) that webhook to the app's webhook endpoint: [5](#0-4) [6](#0-5) 

`removeShopIds` (used on `deleteSession`) is similarly unbounded, performing a full array filter on every deletion: [7](#0-6) 

### Impact Explanation
As the per-shop ID array grows without bound, every `findSessionsByShop` call becomes progressively more expensive (it issues one KV `get` per stored ID, including stale duplicates), and the underlying KV `put` payload for the index key itself grows unbounded, risking hitting KV value-size limits. This degrades or eventually breaks `AppInstallations.includes`/`delete`, which gate app-uninstall cleanup and billing/session checks — a low-severity but genuine availability degradation of an auth-adjacent handler, consistent with the "unbounded loop/array" bug class in the report, but scoped to a single shop's own data (no cross-tenant impact).

### Likelihood Explanation
Likelihood is limited: it requires many repeated `storeSession` calls for the same shop (e.g. via repeated OAuth re-authorizations), which is plausible for a merchant/attacker able to force repeated auth flows against their own installed shop, but it does not provide cross-tenant access or session forgery, and impact is confined to that shop's own session bookkeeping.

### Recommendation
De-duplicate IDs in `addShopIds` (e.g. use a `Set`), or better, replace the raw JSON-array index with a bounded/keyed structure (e.g. individual `shop:<shop>:<id>` marker keys with KV `list()`, or store only the current offline session ID for the shop instead of an ever-growing history). Also cap/dedupe on `removeShopIds` and periodically compact the shop index.

### Proof of Concept
1. Configure an app to use `KVSessionStorage`.
2. Repeatedly complete OAuth for the same shop (uninstall/reinstall, or force `ensureInstalledOnShop` to redirect to auth and complete the callback multiple times), each time calling `storeSession` with the same offline session ID.
3. Observe the `shop:<shop>` KV value's array (`addShopIds`) grows by one entry per auth completion, never shrinking or deduplicating, even though only one offline session is logically valid.
4. Call `findSessionsByShop(shop)` and observe the number of `namespace.get` calls (and elapsed time) scale linearly with the number of historical auth completions rather than the number of actually distinct sessions.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async removeShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(
      key,
      JSON.stringify(shopIds.filter((id) => !ids.includes(id))),
    );
  }

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
      );
    }
  }
