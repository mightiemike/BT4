### Title
Wallet-contract `has_in_flight_tx` flag can be left permanently `true`, freezing the account for all future `rlp_execute` calls - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `near-wallet-contract` (NEAR's Ethereum-emulation wallet, deployed to eth-implicit accounts) uses a boolean `has_in_flight_tx` to serialize transaction processing: `rlp_execute` refuses new work while `true`, and only the contract's own `#[private]` callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) are allowed to clear it back to `false`. If the receipt that runs one of these callbacks fails/panics after entry, the whole receipt (including the `has_in_flight_tx = false` statement) is rolled back, but the earlier `has_in_flight_tx = true` write from the initiating `rlp_execute` receipt was already committed in a prior receipt and is not undone. Because the only way to schedule any of these clearing callbacks is through `rlp_execute` itself, and `rlp_execute` immediately short-circuits with an error whenever `has_in_flight_tx == true`, the contract has no remaining code path capable of ever resetting the flag - the account is stuck in the "in-flight" (pending) state forever, exactly mirroring the reported bug class ("rejected/committed default state has no closing transition").

### Finding Description
`WalletContract::rlp_execute` sets `self.has_in_flight_tx = true` as soon as it decides to create a promise, and that state change is committed as part of the `rlp_execute` receipt: [1](#0-0) 

Every documented recovery path runs inside a `#[private]` callback that is only reachable by being chained (`.then(...)`) from a promise created inside `rlp_execute` (or a prior callback): [2](#0-1) [3](#0-2) [4](#0-3) 

Each of these callback functions sets `self.has_in_flight_tx = false` as its very first statement, but that statement is only durable if the *entire receipt executing the callback* succeeds. Per the runtime's action-receipt execution model, a failing receipt is rolled back in full: "Commit or rollback: success commits with `ReceiptProcessing`; failure calls `state_update.rollback()`, discarding all state changes from the receipt" (`runtime/runtime/src/lib.rs:961`). If, for instance, `nep_141_storage_balance_callback` is invoked and then panics while constructing its own downstream promise chain (e.g. attempting to schedule a further cross-contract call to a target token contract with a fixed, contract-hardcoded gas budget such as `NEP_141_STORAGE_DEPOSIT_GAS`/`RLP_EXECUTE_CALLBACK_GAS` that turns out insufficient for whatever the receiver requires), the whole callback receipt fails and is rolled back — including the `has_in_flight_tx = false` write already executed at the top of the function.

Because `rlp_execute` is the sole entry point that can create a new promise chain and it unconditionally refuses to do any work while `has_in_flight_tx` is `true`: [5](#0-4) 
there is no longer any way to schedule `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, or `ban_relayer` again — the only functions capable of clearing the flag. The account permanently rejects every future `rlp_execute` call with "transaction already in progress, please try again later," even though no transaction is actually pending.

### Impact Explanation
The wallet contract is the account's sole interface for authorizing NEAR actions on behalf of the Ethereum-style key that controls it (base-token transfers, ERC-20/NEP-141 transfers, arbitrary function calls routed through `rlp_execute`). Once `has_in_flight_tx` is stuck `true`, the account can never again process a signed Ethereum transaction; any NEAR tokens or NEP-141 token balances the account holds (or is trying to withdraw/transfer through this mechanism) become permanently inaccessible via the wallet's intended interface, matching the "permanently frozen funds" acceptance criterion. This is reachable by any relayer forwarding an otherwise-valid signed transaction that happens to trigger a downstream callback failure (e.g., targeting a NEP-141 token contract that is unregistered for the receiver and whose `storage_deposit`/transfer chain exceeds the contract's fixed gas allotment), i.e. an ordinary transaction/RPC caller path, no validator or network-level access required.

### Likelihood Explanation
Triggering requires only that a normal `rlp_execute` call reach a point where one of the private callbacks itself fails after it starts running (e.g. insufficient statically-budgeted gas for a nested cross-contract hop, or any other panic inside the callback body after the initial `has_in_flight_tx = false` write). Because the callback gas amounts are fixed compile-time constants (`RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_DEPOSIT_GAS`, etc.) rather than dynamically sized to the actual downstream call's needs, an attacker (a malicious or careless relayer, or an attacker-controlled destination NEP-141 contract) has direct influence over whether the callback receipt succeeds or fails. This does not require validator collusion, network manipulation, or any privileged role — a single crafted `rlp_execute` call targeting a suitable receiver contract is sufficient, making the likelihood moderate-to-high for any actively used wallet-contract account interacting with adversarial or misbehaving token contracts.

### Recommendation
- Provide an unprivileged (or owner-only, signature-gated) "reset"/"unstick" entry point that can clear `has_in_flight_tx` after some safety window (e.g., once outstanding promises are known to have resolved or after a timeout), independent of the normal callback chain.
- Alternatively, make the flag-clearing resilient to partial failure: e.g., set `has_in_flight_tx = false` in a receipt that is guaranteed to commit regardless of whether the nested cross-contract calls it schedules ultimately succeed, or use `Promise::and`/separate low-risk "finally" callback with minimal, guaranteed-sufficient gas that only flips the flag and nothing else.
- Audit all gas constants used for `.with_static_gas(...)` in chained calls to ensure they are dynamically sized or generously bounded so that legitimate cross-contract flows cannot panic mid-callback due to gas exhaustion.

### Proof of Concept
1. Deploy the `near-wallet-contract` on an eth-implicit account `W` and fund it with NEAR and a NEP-141 token balance.
2. Craft (or have a relayer submit) a valid RLP-encoded transaction from `W`'s eth key that triggers `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer)` targeting `receiver_id` that is *not yet registered* for storage on the NEP-141 token, and where the token contract's `storage_deposit` + transfer flow, once chained via `.then(ext.rlp_execute_callback(...))` inside `nep_141_storage_balance_callback`, exceeds `NEP_141_STORAGE_DEPOSIT_GAS`/`RLP_EXECUTE_CALLBACK_GAS` (e.g. by pointing at a token contract with more expensive `storage_deposit`/`ft_transfer` logic than the NEP-141 reference implementation assumed by the hardcoded constants).
3. `rlp_execute` succeeds, committing `has_in_flight_tx = true` (`lib.rs:93-128`), and schedules `nep_141_storage_balance_callback`.
4. When that callback's receipt executes, it sets `has_in_flight_tx = false` first, but then panics while scheduling its own downstream promise/`.then()` chain due to insufficient attached static gas; the receipt fails and is rolled back per `runtime/runtime/src/lib.rs:961`, so `has_in_flight_tx` remains `true` in committed state.
5. Any subsequent call to `rlp_execute` on `W` (from the legitimate key or any relayer) immediately returns `success: false, error: "transaction already in progress, please try again later."` forever, since the only functions able to reset the flag can no longer be scheduled.

Note: the exact gas thresholds and whether a specific NEP-141 contract can be found/crafted that reliably exceeds the hardcoded constants was not independently executed in a live environment; this PoC outline follows directly from the code paths cited above but the precise gas-exhaustion trigger should be validated empirically by a background agent with test-execution access.

    #[payable]
    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

    #[private]
    pub fn ban_relayer(&mut self) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        ExecuteResponse {
            success: false,
            success_value: None,
            error: Some("Error: faulty relayer".into()),
        }
    }
