Based on the investigation, I found a concrete analog in the `AccountCostIncrease` account-creation fee mechanism, which structurally mirrors the reported bug: a "price" quantity that is designed to fund a fee silently degrades to zero under an easily reachable, non-exceptional condition, and the caller has no fallback check — so the fee is effectively bypassed.

### Title
Account-creation charge (`account_creation_charge`) is silently bypassed when gas price ≥ `min_gas_purchase_price` - ([File: runtime/runtime/src/lib.rs])

### Summary
`refund_unspent_gas_and_deposits` funds the `account_creation_charge` fee exclusively from `burned_gas_refund`, which under `AccountCostIncrease` equals `price_surplus` — a value that is mathematically forced to `0` whenever the current block gas price is at or above the receipt's purchase price (the common case whenever gas price sits above `min_gas_purchase_price`, or the receipt executes in the same block it was created). When that happens, `amount_actually_charged = min(amount_to_charge, burned_gas_refund)` collapses to `0`, so a newly created account is charged only the base `create_account` exec-gas cost instead of the intended `account_creation_charge` (0.007 N on mainnet), with no revert or fallback path.

### Finding Description
`gas_burn_price` under `AccountCostIncrease` is computed as `min(gas_purchase_price, apply_state.gas_price)`: [1](#0-0) 

`price_surplus` is only non-zero when `gas_burn_price < gas_purchase_price`; when the burn price equals the purchase price (i.e. the current block gas price is ≥ the receipt's purchase price), `price_surplus` is exactly `0`: [2](#0-1) 

`burned_gas_refund` (fed by `price_surplus`) is the *only* source of funds for the extra `account_creation_charge` top-up: [3](#0-2) 

`amount_to_charge = desired_cost.saturating_sub(burned_cost)` is computed independently of whether a surplus exists, but `amount_actually_charged = min(amount_to_charge, burned_gas_refund)` is capped by whatever surplus happens to be available — with no error, revert, or alternate charging path when `burned_gas_refund == 0`. The code even contains a `debug_assert!` acknowledging the assumption that a surplus should "always" exist when `gas_purchase_price >= min_gas_purchase_price`, which does not hold once the *market* gas price itself reaches or exceeds `min_gas_purchase_price` (a state within the normal `[min_gas_price, max_gas_price]` range documented at `core/primitives/src/block.rs`), since then `gas_purchase_price = max(current_gas_price, min_gas_purchase_price) = current_gas_price`, and if the price does not subsequently drop before the receipt executes, `gas_burn_price == gas_purchase_price` and the surplus is zero.

### Impact Explanation
This is a direct fee-bypass affecting on-chain economics: `account_creation_charge` exists specifically to price/deter account creation (a state-bloat/spam control mechanism, `core/parameters/src/config.rs`, `parameter.rs:31`). When network gas price is elevated (which any unprivileged spammer can induce by congesting the chain, or which happens naturally as load rises toward `max_gas_price`), every `CreateAccount` action executed while `gas_burn_price >= gas_purchase_price` pays only the base gas fee instead of the intended surcharge — silently reducing burnt supply relative to the protocol's designed economics and undermining the anti-spam charge exactly during the high-congestion periods it is meant to matter most.

### Likelihood Explanation
This does not require any privileged access — any transaction signer creating a new account (directly, via implicit-account transfer, or via a `CreateAccount` action) triggers this path whenever gas price is at/above `min_gas_purchase_price` and does not drop before execution, which is common for same-block receipt execution and is easily reachable/inducible by congesting a shard with ordinary transactions.

### Recommendation
Do not rely solely on `price_surplus`/`burned_gas_refund` to fund `account_creation_charge`. If `burned_gas_refund` is insufficient to cover `amount_to_charge`, the shortfall should be charged from the unused-gas refund (`unused_gas_balance_refund`) or from the account's balance directly, ensuring `account_creation_charge` is always fully collected regardless of the relationship between purchase and burn price.

### Proof of Concept
1. Let block gas price `apply_state.gas_price = min_gas_purchase_price` (e.g. `1_000_000_000` yN, as configured for mainnet at PV85).
2. Submit a `CreateAccount` (or implicit-account-creating `Transfer`) transaction; `receipt.gas_price()` (purchase price) is set to `max(current_gas_price, min_gas_purchase_price) = current_gas_price`.
3. Have the receipt execute in the same or a later block where `apply_state.gas_price` has not dropped below the purchase price.
4. `gas_burn_price = min(gas_purchase_price, apply_state.gas_price) = gas_purchase_price`, so `price_surplus = 0` at [4](#0-3) , hence `burned_gas_refund = 0`.
5. `amount_actually_charged = min(amount_to_charge, 0) = 0` at [5](#0-4) , so the account is created without the `account_creation_charge` (0.007 N) being burnt, only the base `create_account` exec-gas fee.
