### Title
`library_call` syscall bypasses the `block_direct_execute_call` protection that restricts direct invocation of `__execute__` - (File: `crates/blockifier/src/execution/syscalls/hint_processor.rs`, `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`, `crates/blockifier/src/execution/native/syscall_handler.rs`)

### Summary
The bug class in the external report is: a privileged/guarded operation (`collectRewards()`) can be reached directly, bypassing the intended intermediary (`LiquidationRow`) that is supposed to be the sole caller, because the guard is attached to the wrong/insufficient check. The analogous pattern in this sequencer codebase is the `block_direct_execute_call` protection: it is meant to prevent any contract from directly invoking another contract's `__execute__` entry point via a syscall, but the guard is only wired into the `call_contract` syscall path and is missing from the `library_call` syscall path, which can reach the exact same `__execute__` selector with attacker-controlled `class_hash`.

### Finding Description
`call_contract` explicitly blocks calls whose selector equals `EXECUTE_ENTRY_POINT_NAME` when `versioned_constants.block_direct_execute_call` is set, via `maybe_block_direct_execute_call`: [1](#0-0) 
This check is invoked from `call_contract` in the native syscall handler: [2](#0-1) 
and from the deprecated `call_contract` implementation: [3](#0-2) 

However, the `library_call` implementations do not perform an equivalent selector check against `EXECUTE_ENTRY_POINT_NAME`/`EXECUTE_ENTRY_POINT_SELECTOR` in any of the three execution backends:
- Cairo1/VM syscall hint processor `library_call`: [4](#0-3) 
- Native syscall handler `library_call`: [5](#0-4) 
- Deprecated (Cairo0) `library_call`/`library_call_l1_handler`, which funnel into `execute_library_call` with no selector restriction: [6](#0-5) [7](#0-6) 

The same asymmetry exists in the Starknet OS Cairo re-implementation: `execute_contract_call_syscall` explicitly rejects `EXECUTE_ENTRY_POINT_SELECTOR`, but `execute_library_call` (the OS's library-call implementation) has no such check: [8](#0-7) [9](#0-8) 
The deprecated (Cairo0) OS dispatcher shows the same pattern: `CALL_CONTRACT_SELECTOR` handling asserts the selector is not `EXECUTE_ENTRY_POINT_SELECTOR`, but the `LIBRARY_CALL_SELECTOR` branch has no equivalent assertion: [10](#0-9) 

Because `library_call` takes an attacker-controlled `class_hash` and `function_selector`, any contract can invoke `library_call(class_hash=<any_account_class>, function_selector=EXECUTE_ENTRY_POINT_SELECTOR, calldata=...)`, running the account class's `__execute__` code path in a delegate-call context, entirely unblocked by `block_direct_execute_call`.

### Impact Explanation
This is a genuine architectural asymmetry in the codebase: the protection labeled `block_direct_execute_call`, whose comment/error explicitly states "Calling `__execute__` directly is not allowed" [11](#0-10) , is not actually comprehensive across all syscalls capable of reaching `__execute__` (`call_contract` vs. `library_call`). Blockifier and the Starknet OS must re-execute transactions identically; any divergence in this guard between blockifier and OS is symmetric here (both miss the check on `library_call`), so it does not by itself cause blockifier/OS state divergence. However, the security guarantee that the flag is intended to provide — "no contract can trigger `__execute__` logic directly, only the transaction-processing flow can" — is only partially enforced. Whether this constitutes exploitable "unauthorized account action" ultimately depends on account contracts' own caller checks inside `__execute__` (e.g., asserting `caller_address == 0`), which most account implementations shown in this repo enforce as a second line of defense (see `account_with_real_validate.cairo` and `account_with_dummy_validate.cairo`, both asserting `get_caller_address().is_zero()`). Because `library_call` preserves the original caller_address (delegate-call semantics) rather than resetting it to zero, this specific gap likely does not defeat those per-account caller checks, meaning practical impact is limited to cases where an account's `__execute__` relies solely on the `block_direct_execute_call` flag rather than its own caller assertion — I could not find such an account in this codebase's feature-contract set.

### Likelihood Explanation
Low-to-moderate: reachable by any unprivileged contract via a standard `library_call` syscall inside a single transaction, but yields concrete unauthorized-invocation impact only if some account class relies on `block_direct_execute_call` instead of (or in addition to) its own caller check in `__execute__`. I was unable to fully confirm, within the accessible index, whether all account classes / OS assumptions treat this flag as a sufficient sole guard, or whether it's understood as defense-in-depth atop per-account checks.

### Recommendation
Mirror the `maybe_block_direct_execute_call` (Rust) / `EXECUTE_ENTRY_POINT_SELECTOR` (Cairo/OS) check inside all `library_call` implementations (native, VM/Casm, deprecated Cairo0, and the OS's `execute_library_call` and `LIBRARY_CALL_SELECTOR` dispatch branch in `deprecated_execute_syscalls.cairo`) so that the `block_direct_execute_call` protection uniformly rejects `EXECUTE_ENTRY_POINT_NAME`/`EXECUTE_ENTRY_POINT_SELECTOR` regardless of whether it is reached via `call_contract` or `library_call`, keeping blockifier and the Starknet OS re-execution semantics consistent.

### Proof of Concept
Not independently executed; based on static code review only, due to the index's coverage limits for full call-graph tracing across the OS Cairo sources and inability to run the workspace's test suite from this environment. Conceptually:
1. Deploy/declare any attacker contract `A`.
2. `A` calls the `library_call` syscall with `class_hash` = the class hash of any existing account contract, `function_selector` = `selector_from_name("__execute__")`, and arbitrary `calldata`.
3. Because `library_call` never calls `maybe_block_direct_execute_call` (Rust) nor asserts against `EXECUTE_ENTRY_POINT_SELECTOR` (OS Cairo), the call proceeds to execute the account class's `__execute__` code in `A`'s own storage/caller context — unlike the identical attempt via `call_contract`, which is rejected with `DirectExecuteCall`/`INVALID_ARGUMENT_FELT` when `block_direct_execute_call` is enabled, as demonstrated by the existing test `test_direct_execute_call` in `crates/blockifier/src/execution/syscalls/syscall_tests/call_contract.rs` (lines 277-344) and `crates/starknet_os_flow_tests/src/tests.rs` (lines 2737-2775), neither of which have a `library_call` counterpart in the reviewed sources.

    pub(crate) fn maybe_block_direct_execute_call(
        &mut self,
        selector: EntryPointSelector,
    ) -> SyscallResult<()> {
        let versioned_constants = &self.context.tx_context.block_context.versioned_constants;
        if versioned_constants.block_direct_execute_call
            && selector == selector_from_name(EXECUTE_ENTRY_POINT_NAME)
        {
            return Err(SyscallExecutionError::Revert { error_data: vec![INVALID_ARGUMENT_FELT] });
        }
        Ok(())
    }

pub fn execute_library_call(
    syscall_handler: &mut DeprecatedSyscallHintProcessor<'_>,
    vm: &mut VirtualMachine,
    class_hash: ClassHash,
    code_address: Option<ContractAddress>,
    call_to_external: bool,
    entry_point_selector: EntryPointSelector,
    calldata: Calldata,
) -> DeprecatedSyscallResult<ReadOnlySegment> {
    let entry_point_type =
        if call_to_external { EntryPointType::External } else { EntryPointType::L1Handler };
    let entry_point = CallEntryPoint {
        class_hash: Some(class_hash),
        code_address,
        entry_point_type,
        entry_point_selector,
        calldata,
        // The call context remains the same in a library call.
        storage_address: syscall_handler.storage_address,
        caller_address: syscall_handler.caller_address,
        call_type: CallType::Delegate,
        initial_gas: syscall_handler.context.gas_costs().base.default_initial_gas_cost,
    };

    execute_inner_call(entry_point, vm, syscall_handler).map_err(|error| {
        error.as_lib_call_execution_error(
            class_hash,
            syscall_handler.storage_address,
            entry_point_selector,
        )
    })
}

// Implements the library_call syscall.
func execute_library_call{
    range_check_ptr,
    syscall_ptr: felt*,
    builtin_ptrs: BuiltinPointers*,
    contract_state_changes: DictAccess*,
    contract_class_changes: DictAccess*,
    revert_log: RevertLogEntry*,
    outputs: OsCarriedOutputs*,
}(block_context: BlockContext*, caller_execution_context: ExecutionContext*) {
    let request = cast(syscall_ptr + RequestHeader.SIZE, LibraryCallRequest*);
    let (success, remaining_gas) = reduce_syscall_base_gas(
        specific_base_gas_cost=LIBRARY_CALL_GAS_COST, request_struct_size=LibraryCallRequest.SIZE
    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    // Prepare execution context.
    tempvar calldata_start = request.calldata_start;
    tempvar caller_execution_info = caller_execution_context.execution_info;
    tempvar execution_context: ExecutionContext* = new ExecutionContext(
        entry_point_type=ENTRY_POINT_TYPE_EXTERNAL,
        class_hash=request.class_hash,
        calldata_size=request.calldata_end - calldata_start,
        calldata=calldata_start,
        execution_info=new ExecutionInfo(
            block_info=caller_execution_info.block_info,
            tx_info=caller_execution_info.tx_info,
            caller_address=caller_execution_info.caller_address,
            contract_address=caller_execution_info.contract_address,
            selector=request.selector,
        ),
        deprecated_tx_info=caller_execution_context.deprecated_tx_info,
    );

    return contract_call_helper(
        remaining_gas=remaining_gas,
        block_context=block_context,
        execution_context=execution_context,
    );
}
