## Title
`ensure_match_transaction_info` skips verifying state/hot-state/position checkpoint hashes, allowing state-root divergence to go undetected during replay/verification - (File: `types/src/transaction/mod.rs`)

## Summary

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is the local-code guard whose job is to confirm that a freshly-computed `TransactionOutput` (from VM execution or replay) matches the authenticated `TransactionInfo` that was committed to the transaction accumulator (and thus signed by validators/backed by an accumulator proof). It checks status, gas used, write-set hash (`state_change_hash`), and event root hash [1](#0-0) .

Critically, it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed state root. The code contains an explicit acknowledgment of this gap: [2](#0-1) 

This means the function can return `Ok(())` — i.e., report a full match — even when the state Merkle root actually produced by local execution/replay diverges from the state root that was authenticated in the committed `TransactionInfo`.

### Impact Explanation
This helper is used by replay/verification tooling, specifically `storage/db-tool/src/replay_on_archive.rs` and `execution/executor/src/chunk_executor/mod.rs` (both reference `ensure_match_transaction_info`), whose purpose is precisely to detect state-commitment divergence between a locally re-executed/replayed transaction and the authenticated on-chain ledger data. Since the state/hot-state/position checkpoint hash comparison is skipped, a state-root computation bug (in the state Merkle tree, hot-state logic, or the "trading-native" position state feature referenced by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` flag in the comment) would not be flagged by this verifier. A replay could be reported as successful while the authenticated state root has actually diverged from local execution — exactly the "Wrong ... state proof accepted as valid" / "Hard-fork-only divergence during commit, replay ... verification" class of impact called out in the state-integrity gate.

### Likelihood Explanation
This is not a hypothetical instrumentation gap that requires external steps: any transaction whose state-checkpoint hash is wrong (e.g., due to a bug in the sparse Merkle tree, hot-state root computation, or the newer position-state-root path) triggers the missing check silently the very next time replay-verify tooling processes that transaction, provided all other checked fields (write set, events, gas, status) still happen to match. This makes the blind spot directly reachable through the normal replay-verify workflow rather than an artificial edge case.

### Recommendation
Extend `ensure_match_transaction_info` to also recompute and compare `state_checkpoint_hash` (and, where applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the values in `txn_info`, failing with the same `ERR_MSG` pattern used for the other fields, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/related state-root features are enabled in production reliance on this verifier.

### Proof of Concept
1. During chunk replay/verification (`replay_on_archive` or the state-sync chunk executor path that calls `ensure_match_transaction_info`), suppose a bug in state-root computation (hot-state or position-state) causes the locally recomputed `state_checkpoint_hash` for version `V` to differ from the `state_checkpoint_hash` embedded in the authenticated `TransactionInfo` for `V`.
2. `write_set_hash`, `event_root_hash`, `gas_used`, and `status` are unaffected by this particular bug and still match.
3. `ensure_match_transaction_info` returns `Ok(())`, and the calling verifier logs the replay as successful.
4. The archive/verification report certifies state consistency at version `V` even though the actual persisted/authenticated state root has diverged from what local execution would produce — corrupting the trust guarantee that replay-verify is meant to provide.

**Confidence caveat:** I could not fully trace, within the available iterations, the exact call sites in `execution/executor/src/chunk_executor/mod.rs` and `storage/db-tool/src/replay_on_archive.rs` (i.e., the surrounding function bodies) to confirm whether an additional/independent state-root check exists elsewhere in those call paths that would compensate for this specific gap. The gap itself, and the maintainers' own TODO acknowledging it, is confirmed directly in `types/src/transaction/mod.rs`, but whether it is currently exploitable end-to-end in a specific verification pipeline (versus being caught by a separate check upstream) is not fully verified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
