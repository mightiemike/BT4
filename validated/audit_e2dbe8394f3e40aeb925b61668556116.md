### Title
Anonymous transactions pay zero fee for expensive multi-signature verification that fails permission checks - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
The external report describes a class of bug where an expensive, user-triggerable computation (WASM bytecode decompression) is performed *before* the fee/gas for that computation is charged, so a crafted input that makes the computation fail lets the attacker avoid paying for the CPU work performed. The analogous pattern in java-tron is in `Manager.processTransaction`, where transaction signature verification (`trxCap.validateSignature(...)`) — which can involve multiple expensive ECDSA public-key recovery operations — is executed *before* `consumeBandwidth(trxCap, trace)` is called to charge bandwidth/fee for the transaction.

### Finding Description
In `Manager.processTransaction`, the call order is: [1](#0-0) 

`validateTapos`, `validateCommon`, `validateDup` and `trxCap.validateSignature(...)` all run before `consumeBandwidth(trxCap, trace)`. `validateSignature` delegates to `validatePubSignature`, which performs ECDSA signature recovery and (for accounts using custom permissions) `TransactionCapsule.checkWeight`, which loops over every signature attached to the transaction and calls `SignUtils.signatureToAddress` (an EC public-key recovery, i.e., an elliptic-curve operation) for each one: [2](#0-1) [3](#0-2) 

Notably, the code already contains an ad-hoc guard/instrumentation (`SLOW_SIG_VERIFY_MS`, `logSlowSigVerify`) that logs a warning when this signature verification step is unusually slow — evidence that the maintainers are aware this step can be computationally expensive: [4](#0-3) 

If verification throws `ValidateSignatureException`, `SignatureException`, `PermissionException`, or `SignatureFormatException` (e.g., an attacker submits an account with a large custom permission — up to `getTotalSignNum()` keys — and attaches the maximum allowed number of syntactically valid but wrong/duplicate signatures so that the loop performs multiple EC-recover operations before ultimately throwing), `processTransaction` exits with an exception *before* `consumeBandwidth`/`consumeMultiSignFee` ever executes. Consequently, the CPU work already spent on signature recovery is never billed to the sender — exactly the "expensive computation performed before the corresponding charge, with failure meaning no charge" pattern described in the report.

### Impact Explanation
An attacker can flood the network (via the anonymous broadcast-transaction RPC path) with transactions targeting an account configured with many permission keys, using the maximum permitted signature count (`getTotalSignNum()`) filled with syntactically valid but incorrect/duplicate signatures. Each such transaction forces multiple EC public-key recoveries in `checkWeight`/`validatePubSignature` on every node that receives and validates it, yet ultimately fails validation and is never billed for bandwidth/energy. This allows a computational proof-of-work-free denial-of-service vector: node/validator CPU time is consumed for cryptographic verification work that the sender never pays for, and can be aimed at every node in the network simultaneously via ordinary p2p transaction propagation, not just a single node's mempool.

### Likelihood Explanation
Likelihood is moderate: the attacker needs a funded account with a custom active permission configured (achievable via `AccountPermissionUpdateContract`, a standard, unprivileged operation), then can repeatedly submit unsigned-correctly or duplicate/garbage-but-well-formed signature sets. No privileged access, leaked keys, or malicious peer/node behavior is required — only standard transaction broadcast.

### Recommendation
- Short term: charge (or reserve/pre-charge) bandwidth/energy for the transaction *before* performing expensive signature verification, or bound the cost of failed verification (e.g., charge a minimal fee proportional to the number of signatures/keys checked regardless of outcome), similar to charging gas before decompression in the original WASM report.
- Additionally, cap `checkWeight`'s EC-recovery loop cost independent of transaction acceptance outcome, and consider charging `consumeMultiSignFee` (or an equivalent minimum fee) even when signature/permission validation ultimately fails, so the cost of the cryptographic work performed is always recovered from the submitter.
- Long term: audit all other actuator/`validate()` paths that perform computationally expensive work (loop-based signature recovery, `ValidateMultiSign`/`BatchValidateSign` precompiles, large ABI decoding, etc.) that are reachable pre-fee-charge from an anonymous transaction, to ensure equivalent early/guaranteed billing.

### Proof of Concept
1. Create/fund an account and set an active permission with the maximum allowed number of keys (`getTotalSignNum()`), each key belonging to distinct addresses controlled or not controlled by the attacker.
2. Build a transaction from that account referencing this permission (`permissionId != 0`).
3. Attach `getTotalSignNum()` syntactically valid (65-byte) but incorrect/duplicate signatures (fails permission match or "signed twice" check in `checkWeight`).
4. Broadcast the transaction repeatedly via the public broadcast-transaction RPC.
5. Observe that `Manager.processTransaction` invokes `trxCap.validateSignature` — performing up to `getTotalSignNum()` EC-recovery operations per transaction — and then throws `ValidateSignatureException` before `consumeBandwidth`/`consumeMultiSignFee` are ever reached, meaning the sender is charged nothing for the CPU work every receiving node performed.   public static long checkWeight(Permission permission, List<ByteString> sigs, byte[] hash,
      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;
  }

  /**
   * validate signature
   */
  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

  /**
   * WARN-logs when a single signature verification exceeds
   * {@link #SLOW_SIG_VERIFY_MS}. Package-private so it can be exercised from
   * tests without forcing a real slow crypto path.
   */
  void logSlowSigVerify(long startNs) {
    long costMs = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startNs);
    if (costMs > SLOW_SIG_VERIFY_MS) {
      logger.warn("slow verify: txId={}, sigCount={}, cost={} ms",
          getTransactionId(), this.transaction.getSignatureCount(), costMs);
    }
  }
