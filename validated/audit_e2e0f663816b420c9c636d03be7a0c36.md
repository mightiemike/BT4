### Title
Unbounded Gzip Decompression DoS in `decompress_program` via Simulate/Estimate JSON-RPC Calls with a `DECLARE` V1 Transaction - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
The `decompress_program` helper in the RPC execution layer decompresses a user-supplied, base64+gzip-encoded Cairo0 `program` field with no size limit, unlike the equivalent path used for actual mempool-bound Declare transactions in the gateway, which enforces `decode_and_decompress_with_size_limit`.

### Finding Description
`decompress_program` base64-decodes the caller-supplied `compressed_program` string and streams it through a `GzDecoder`, reading the entire output into memory with `read_to_end`, with an explicit `// TODO(dan): add time and size limits.` marker showing the limit is known-missing: [1](#0-0) 

This function is invoked from `user_deprecated_contract_class_to_sn_api`, which is called from `TryFrom<BroadcastedDeclareTransaction> for ExecutableTransactionInput` for the `V1` (Cairo0) variant: [2](#0-1) 

`ExecutableTransactionInput` is the type consumed by `apollo_rpc_execution::simulate_transactions` and `estimate_fee`, which are wired into the JSON-RPC handlers in `crates/apollo_rpc/src/v0_8/api/api_impl.rs` (imports `exec_estimate_fee`, `exec_simulate_transactions`, `ExecutableTransactionInput`): [3](#0-2) 

This is reachable by any unauthenticated/unprivileged JSON-RPC caller who submits a `starknet_estimateFee` or `starknet_simulateTransactions` request containing a `BROADCASTED_DECLARE_TXN` (V1) with a crafted `contract_class.program` field. Unlike the actual class-declaration ingestion path in `crates/apollo_http_server/src/deprecated_gateway_transaction.rs`, which calls `decode_and_decompress_with_size_limit` (bounded, using `flate2`'s `.take()` combinator to cap output size), this simulate/estimate path has no such bound: [4](#0-3) [5](#0-4) 

A gzip payload can achieve extremely high compression ratios (a well-known "zip bomb" construction), so a small base64 request body can expand to gigabytes in memory before any size check occurs, exactly matching the CVE-2026-58107 bug class (one-shot unbounded zlib/gzip decompression of attacker-controlled data materialized fully in memory).

### Impact Explanation
A single unauthenticated JSON-RPC request to `starknet_estimateFee` or `starknet_simulateTransactions` with a crafted, highly-compressed `program` blob can cause the RPC/full node process to allocate an unbounded amount of memory, exhausting process or host memory and causing denial of service to that node process. This does not corrupt state or produce wrong commitments, but it can crash/hang a sequencer/RPC node, degrading the network's ability to serve and, if colocated with block-building/execution components, potentially impacting availability of transaction confirmation on that node.

### Likelihood Explanation
Likelihood is high for triggering the resource exhaustion: no authentication or special permission is required beyond calling a public read-style RPC method (estimate_fee/simulate_transactions), and the vulnerable code path is unconditionally reached whenever a `BroadcastedDeclareTransaction::V1` is present in the request, since `decompress_program` performs the unbounded decompression before any downstream size validation.

### Recommendation
Use the existing bounded utility (`starknet_api::compression_utils::decode_and_decompress_with_size_limit`, which already implements the `.take(max_size + 1)` pattern) inside `decompress_program`/`user_deprecated_contract_class_to_sn_api`, passing a configured maximum decompressed program size (mirroring `HttpServerDynamicConfig::max_sierra_program_size` used in the gateway path) so simulate/estimate requests are bounded identically to real Declare submissions.

### Proof of Concept
1. Craft a gzip stream that decompresses to a very large size but is small when base64-encoded (a classic zip/gzip bomb, e.g. compressing a large run of a single repeated byte achieves ratios well over 1000:1).
2. Base64-encode the compressed bytes and place them into the `contract_class.program` field of a `BROADCASTED_DECLARE_TXN` (V1) payload.
3. Submit this payload via `starknet_estimateFee` or `starknet_simulateTransactions` JSON-RPC call to the node.
4. `decompress_program` ( [1](#0-0) ) fully decompresses the payload into memory via `read_to_end` before any size check, causing large memory allocation and potential OOM/DoS on the node process, with no equivalent size-limit guard as exists in the gateway's `decode_and_decompress_with_size_limit` path.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
