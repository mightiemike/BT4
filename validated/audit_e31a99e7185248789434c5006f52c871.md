### Title
OAuth state (nonce) cookie is not scoped per shop, allowing one shop's authorization flow to invalidate a concurrent, unrelated shop's OAuth flow - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
The M-16 report describes a design flaw where a resource meant to be isolated per-tenant (a base lending pool) is instead shared/aggregated across tenants, so one tenant's settings can affect another tenant's otherwise-healthy, independent state. The same structural flaw exists in `shopify-app-js`'s OAuth `begin`/`callback` flow: the `shopify_app_state` nonce cookie used to protect each OAuth handshake is written with a `path` that is common to every shop (`callbackPath`), rather than being scoped per-shop like the session cookie now is. As a result, concurrent OAuth flows for two different, unrelated shops in the same browser collide on the same cookie, and the second flow silently invalidates the first.

### Finding Description
In `begin()`, the OAuth nonce is stored in a signed cookie named `STATE_COOKIE_NAME` (`shopify_app_state`) with `path: callbackPath`: [1](#0-0) 

`callbackPath` is the same route for every shop that installs/authenticates against a given app (e.g. `/auth/callback`), so the cookie's `(name, path)` pair is identical across shops - there is no shop-specific scoping.

In `callback()`, the state is read back from that same cookie and compared against the `state` query parameter returned by Shopify for the specific shop being authenticated: [2](#0-1) [3](#0-2) 

The library already recognizes and partially fixed this exact class of bug for the *post-auth* session cookie: `cookiePath` was added specifically because "all shops shared a single `shopify_app_session` cookie at `path=/`, so authenticating a new shop would silently overwrite the previous shop's session": [4](#0-3) [5](#0-4) 

However, that fix is only applied to `SESSION_COOKIE_NAME` in `callback()`: [6](#0-5) 

The *pre-auth* `STATE_COOKIE_NAME` cookie set in `begin()` was left unscoped, using only `callbackPath`, which does not vary per shop. This is structurally identical to the base-pool isolation bug: a single shared piece of state (base pool LTV / here, the nonce cookie) is used to gate the health/validity of multiple logically-independent flows (base pools / here, per-shop OAuth handshakes), so activity in one flow (pool A changing LTV / here, shop B starting OAuth) unexpectedly breaks the validity of another, unrelated flow (pool B's healthy position / here, shop A's in-flight OAuth handshake) even though shop A did nothing wrong and its own parameters are entirely valid.

### Impact Explanation
Any legitimate user managing multiple Shopify stores who initiates the app's OAuth install/auth flow for Shop A in one browser tab, then does the same for Shop B in another tab of the same browser (a normal, unprivileged, commonly-occurring scenario for multi-store merchants/agencies), will have Shop B's `shopify_app_state` cookie silently overwrite Shop A's. When Shop A's OAuth redirect returns to the callback, `stateFromCookie` will be Shop B's nonce, `safeCompare(query.state, stateFromCookie)` will fail, and `callback()` throws `InvalidOAuthError`, aborting Shop A's authentication. This is a concrete denial-of-service against the auth handler for one of the two shops, triggered purely by normal, unprivileged multi-tenant usage patterns - directly mirroring how M-16 shows those isolated risk domains bleeding into each other.

### Likelihood Explanation
Non-embedded apps (or apps supporting non-embedded installs) that are used by merchants/partners/agencies managing several stores are the most exposed; opening two install/re-auth flows in parallel tabs of the same browser is an ordinary, foreseeable action, not an attack requiring special access. The same-named/same-path cookie collision is deterministic, not probabilistic, so any such concurrent usage reliably reproduces the failure.

### Recommendation
Scope the `STATE_COOKIE_NAME` cookie per shop the same way the `cookiePath` fix scopes the session cookie - e.g., derive its `path` from the shop (or embed the shop into the cookie name/value) instead of using the app-wide `callbackPath` alone, so concurrent OAuth flows for different shops in the same browser do not collide.

### Proof of Concept
1. Configure a non-embedded app with a single `callbackPath` (e.g. `/auth/callback`), default `cookiePath`.
2. In Tab 1, call `shopify.auth.begin({shop: 'shop-a.myshopify.com', callbackPath: '/auth/callback', ...})` - this sets `shopify_app_state=nonceA` at `path=/auth/callback` per [7](#0-6) .
3. In Tab 2 (same browser/cookie jar), call `shopify.auth.begin({shop: 'shop-b.myshopify.com', callbackPath: '/auth/callback', ...})` - this overwrites the same cookie with `nonceB`.
4. Complete Shopify's authorization for Shop A first; the browser sends back `state=nonceA` in the query string, but the `shopify_app_state` cookie now contains `nonceB`.
5. `shopify.auth.callback({rawRequest})` for Shop A executes `safeCompare(query.state, stateFromCookie)` → `nonceA !== nonceB` → `InvalidOAuthError` thrown per [3](#0-2) , aborting Shop A's authentication despite it being a completely valid, independent flow.

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
