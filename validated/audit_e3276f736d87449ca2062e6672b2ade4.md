### Title
Deposit Refund Misdirected to Sender Instead of Relayer in Meta-Transaction Delegate Action — (`File: runtime/runtime/src/actions.rs`)

### Summary

In `apply_delegate_action`, the inner receipt spawned from a `Delegate`/`DelegateV2` action hardcodes `predecessor_id = sender_id` (Alice, the delegate sender). When that inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` sends the full deposit refund to `balance_refund_receiver()`, which resolves to `predecessor_id` = Alice — not to the relayer who actually paid the deposit. An unprivileged user (Alice) can exploit this to drain the relayer's deposit by crafting a delegate action with a large attached deposit that is guaranteed to fail.

### Finding Description

`apply_delegate_action` constructs the inner receipt as a V1 `ActionReceipt` (no `refund_to` field) with `predecessor_id` set to `sender_id` (Alice): [1](#0-0) 

The `balance_refund_receiver()` method returns `refund_to` if present, otherwise falls back to `predecessor_id`: [2](#0-1) 

Because the inner receipt is always `ReceiptEnum::Action` (V1), `refund_to` is always `None`: [3](#0-2) 

When the inner receipt fails, `refund_unspent_gas_and_deposits` issues a deposit refund receipt to `receipt.balance_refund_receiver()` — which resolves to Alice: [4](#0-3) 

The relayer paid the deposit (it was deducted from the relayer's balance at transaction conversion time), but the refund goes to Alice. The nearcore documentation explicitly acknowledges this: [5](#0-4) 

The code comment in `apply_delegate_action` also acknowledges it: [6](#0-5) 

Critically, there is **no mechanism** for the relayer to override the refund destination. The `promise_set_refund_to` host function is only callable from within contract execution, not from the outer transaction layer. The inner receipt is always created as V1 (`ReceiptEnum::Action`), so `refund_to` is structurally absent. [7](#0-6) 

### Impact Explanation

The relayer's deposit balance is permanently transferred to Alice. The exact corrupted value is `total_deposit` (the sum of all `deposit` fields in the inner actions), which is credited to Alice's account instead of the relayer's account. This is a direct, on-chain loss of funds for the relayer with no recovery path.

### Likelihood Explanation

Any relayer that submits a `Delegate`/`DelegateV2` action containing inner actions with non-zero deposits is at risk. Alice can craft a delegate action with a large deposit attached to a function call targeting a contract that will fail (e.g., calling a non-existent method, or relying on state changes between relayer verification and execution). The relayer cannot distinguish a "safe" delegate action from an exploitative one purely by static inspection, because execution outcome depends on on-chain state at execution time.

### Recommendation

In `apply_delegate_action`, construct the inner receipt as `ReceiptEnum::ActionV2` with `refund_to` set to the relayer's account (`action_receipt.signer_id()`), so that deposit refunds on failure are returned to the party who paid them: [8](#0-7) 

Alternatively, enforce at the protocol level that delegate actions with non-zero deposits must carry an explicit `refund_to` field pointing to the relayer, rejecting delegate actions that omit it.

### Proof of Concept

1. Alice creates a `DelegateAction` with `receiver_id = bob.near`, inner action `FunctionCall { method_name: "nonexistent", deposit: 10_000_000_000_000_000_000_000_000 /* 10 NEAR */ }`, signed with Alice's key.
2. Alice presents this to a relayer. The relayer verifies the signature and nonce, then submits the outer transaction (paying the 10 NEAR deposit from its own balance).
3. On Bob's shard, the function call fails (`MethodNotFound` or any other error).
4. `refund_unspent_gas_and_deposits` fires: `deposit_refund = 10 NEAR`, `receipt.balance_refund_receiver() = alice.near`.
5. A `Receipt::new_balance_refund(&alice_account(), 10_NEAR)` is emitted.
6. Alice's balance increases by 10 NEAR; the relayer's balance is permanently reduced by 10 NEAR.

The `test_gas_key_refund` integration test confirms the deposit-refund-to-predecessor behavior on failure: [9](#0-8)

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
