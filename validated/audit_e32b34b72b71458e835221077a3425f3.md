### Title
Signers-voting contract never enforces its own prepare-phase voting window, letting a vote finalize an aggregate key outside the intended DKG round window - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
`signers-voting.clar` defines `is-in-voting-window`, a helper meant to restrict `vote-for-aggregate-public-key` to the prepare phase of the reward cycle for which the signer set was most recently computed, but this helper is never called as an `asserts!` inside `vote-for-aggregate-public-key`. This is structurally the same defect as the Llama finding: a time/window predicate exists in the codebase but the state-transition function that is supposed to be gated by it does not actually check it, so the action (here, casting a DKG vote that can finalize the `aggregate-public-keys` map) remains available outside the window it was designed for.

### Finding Description
`is-in-voting-window` is defined at [1](#0-0)  and checks that the reward cycle being voted for is the last cycle for which the node has committed a signer set, and that the current burn height falls in that cycle's prepare phase, via `is-in-prepare-phase` [1](#0-0) .

However, `vote-for-aggregate-public-key` — the only public entry point that records votes and can finalize the `aggregate-public-keys` map — never calls `is-in-voting-window`. Its asserts only check: the key hasn't already been approved for the cycle, the key is 33 bytes, the key hasn't been reused across cycles, the caller hasn't already voted this round, and the round only increments by at most one: [2](#0-1) 

Notably, `ERR_OUT_OF_VOTING_WINDOW` (the error code whose name implies the window check) is actually returned by the "key already set" assertion instead of an actual window/time check: [3](#0-2) 

Because `is-in-voting-window` is unreferenced anywhere else in this contract, a signer belonging to the signer set for `reward-cycle` (verified only by `get-signer-weight`'s `tx-sender` equality check at [4](#0-3) ) can submit `vote-for-aggregate-public-key` at any burn height, not just during that cycle's prepare phase. This breaks the intended equality "vote is only counted while `current-reward-cycle == committed signer-set cycle AND height is in prepare phase`" — the contract accepts votes with no temporal binding to the DKG round it is supposed to represent.

### Impact Explanation
This maps to the "signer weight below threshold or from the wrong set" / "reward paid twice or to wrong party"-adjacent class called out in scope: a signer's vote can be recorded and tallied toward `threshold-weight` and can trip `map-insert aggregate-public-keys reward-cycle key` at a time the protocol did not intend to accept it, e.g., long before the node has actually finalized the signer set state for that cycle in a way consistent with `check_and_handle_prepare_phase_start`/`process_vote_for_aggregate_key_ops` timing in the Rust caller [5](#0-4) , or after the prepare phase for that cycle has long closed and a new cycle's signer computation is already underway. Since the aggregate public key selected for a reward cycle gates that cycle's signature/consensus set, a vote accepted outside the intended window is a case of a decision ("which aggregate key is approved for reward-cycle N") being reached via an input that should have been rejected — an equality/validity check silently missing, in the same bug class as the disapproval-after-deadline issue (a state-changing action lacking its documented time guard).

### Likelihood Explanation
Likelihood is bounded by the requirement that the caller be a member of the signer set entitled to vote for that `reward-cycle` (`get-signer-weight` enforces `tx-sender` = the signer at `signer-index`), so this is not exploitable by an arbitrary unprivileged account, but any single signer (a minority-weight participant) can trigger it without needing majority cooperation or any other party's key, satisfying the "minority-triggerable" requirement. No time estimate is asserted here per instruction; the code path is directly reachable by simply calling the public function with the current signer index/cycle at any burn height.

### Recommendation
Add `(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))` (or equivalent) as an explicit check inside `vote-for-aggregate-public-key`, using the correct dedicated error code for the window failure, distinct from the "key already approved" case which currently overloads `ERR_OUT_OF_VOTING_WINDOW`.

### Proof of Concept
1. Deploy/observe `signers-voting.clar`; note `is-in-voting-window` at lines 95-98 is defined but `grep`-confirmed to have zero call sites other than its own definition [6](#0-5) .
2. As a signer entitled to vote for `reward-cycle = N` (per `get-signer-weight`), call `vote-for-aggregate-public-key` at a burn height outside `N`'s prepare phase (e.g., well after it closed, or before the node has advanced `last-set-cycle` to `N`).
3. Observe the transaction succeeds: it passes every `asserts!` in the function body (lines 154-163) because none of them reference burn height or prepare-phase membership, and the vote is tallied into `tally`/`round-data` and can finalize `aggregate-public-keys` for `N` if `new-total >= threshold-weight` (lines 180-197).

I was not able to fully verify at what point (if any) an out-of-contract/off-chain guard in the Rust node layer independently re-validates the voting window before submitting `vote-for-aggregate-public-key` transactions in production flows; the index does not show such a guard being called from within this Clarity contract itself, and a full trace of every caller of `vote-for-aggregate-public-key` across the Rust node was not completed within the available tool budget. If such an external guard exists, it would reduce but not eliminate this issue, since the on-chain contract itself provides no protection against a directly-submitted transaction bypassing that guard.
