### Title
Denial-of-Service via Front-Runnable Shared `DONLimit` in WorkflowRegistry `UpsertWorkflow` - (File: `workflow_registry_wrapper_v2` bindings / underlying `WorkflowRegistry` contract, referenced from `deployment/cre/workflow_registry/v2/changeset/operations/contracts/configure_workflow_registry_ops.go`)

### Summary
The `WorkflowRegistry` v2 contract enforces a shared, DON-family-wide cap on the number of registered workflows via `SetDONLimit` / `GetMaxWorkflowsPerDON`, analogous to the `maxContractBalance` cap in the referenced Reality Cards `deposit` bug. Because this is a single shared counter checked at `UpsertWorkflow` time, any allowed workflow owner can race to fill the DON-wide quota and cause other legitimate owners' `UpsertWorkflow` transactions to revert, denying them the ability to register/activate workflows on that DON family.

### Finding Description
`SetDONLimit(donFamily, donLimit, userDefaultLimit)` configures a maximum number of workflows (`GetMaxWorkflowsPerDON`) that can be registered for a given `donFamily` [1](#0-0) . Any allowed signer/owner can call `UpsertWorkflow(name, tag, id, status, donFamily, binaryURL, configURL, attributes, keepAlive)` to register a workflow against that `donFamily` [2](#0-1) . This mirrors the `maxContractBalance` pattern exactly: a single mutable, shared numeric cap (`GetMaxWorkflowsPerDON`) is checked against a running counter of registrations for the DON family, and any unprivileged (but allowlisted) caller can push that counter to its limit before another user's transaction lands, causing the victim's `UpsertWorkflow` call to revert once the DON-wide quota is exhausted — the exact "front-run the balance/limit check" pattern described in the report. Because this limit is per-DON-family and shared across *all* owners registered to that family (not per-user), a single owner (or several colluding/sybil owners, since `IsAllowedSigner`/allowlisting is typically broad for participating workflow owners) can consume the entire quota, permanently or temporarily locking out other legitimate owners from registering workflows on that DON — unlike `PerOwner`/`UserDefaultLimit`, which is scoped per-account and not directly exploitable this way.

I was unable to retrieve the actual Solidity source of `WorkflowRegistry.sol` (it is not indexed in this snapshot — only generated Go bindings/wrappers and deployment/test helpers referencing `UpsertWorkflow`, `SetDONLimit`, and `GetMaxWorkflowsPerDON` were found). I therefore cannot cite the exact `require`/`revert` statement inside `UpsertWorkflow` that performs the DON-limit check, nor confirm whether the count is decremented on workflow deletion/pause in a way that would make the race window narrow or wide. This should be verified directly against the on-chain contract source before treating this as fully confirmed.

### Impact Explanation
If exploitable as described, a malicious or self-interested workflow owner could monopolize a DON family's workflow slot capacity, preventing competing owners from registering or updating workflows on that DON — a direct availability/service-denial impact on the workflow ingestion path, analogous to the referenced finding's "prevents them from renting cards" impact and to "any users can be blocked" language in the original report.

### Likelihood Explanation
Likelihood depends on: (1) how tightly `DONLimit` values are set relative to expected real usage (the test/deployment defaults use large limits, e.g. `defaultWorkflowRegistryDONLimit = 5000` [3](#0-2) , which reduces practical exploitability in those configured environments), and (2) whether `donFamily` allowlisting restricts the attacker population to a small, already-trusted set of owners (reducing the "unprivileged attacker" applicability). Without the contract source confirming exact check/revert ordering and count decrement semantics, I cannot fully assess whether this is trivially front-runnable in production DON configurations or only a theoretical concern under tight limits.

### Recommendation
- Confirm in `WorkflowRegistry.sol` whether the DON-family workflow count check in `UpsertWorkflow` can be front-run by a burst of registrations from allowed owners.
- Consider using per-owner reservations/quotas rather than (or in addition to) a purely shared DON-wide counter, or implement a queueing/priority mechanism so a single owner cannot consume the entire shared capacity in one block.
- If the shared cap is retained, ensure `DONLimit` is set generously relative to expected DON family membership size, and monitor/alert when DON family workflow counts approach the cap, similar to the "toggle" mitigation accepted by the Reality Cards team for `maxContractBalance`.

### Proof of Concept
Not fully verifiable from the indexed code alone (Solidity source unavailable). Conceptually:
1. DON family `X` has `SetDONLimit(X, N, userLimit)` set, so `GetMaxWorkflowsPerDON(X).MaxWorkflows == N` [4](#0-3) .
2. Owner count for family `X` is currently `N-1`.
3. Victim submits `UpsertWorkflow(..., donFamily=X, ...)` to register a new workflow.
4. Attacker (an already-allowed owner for family `X`) front-runs with their own `UpsertWorkflow(..., donFamily=X, ...)` call, pushing the family's workflow count to `N`.
5. Victim's transaction reverts due to the DON-family limit being reached, denying their workflow registration — same mechanic as the `maxContractBalance` "Limit hit" revert in the original report.

func updateAllowedDONsV2(
	t *testing.T,
	th *testutils.EVMBackendTH,
	wfRegC *workflow_registry_wrapper_v2.WorkflowRegistry,
	donFamilies []string,
) {
	t.Helper()
	for _, donFamily := range donFamilies {
		workflowLimit := uint32(10000)
		userLimit := uint32(1000)
		_, err := wfRegC.SetDONLimit(th.ContractsOwner, donFamily, workflowLimit, userLimit)
		require.NoError(t, err, "failed to update DONs")

		th.Backend.Commit()
		th.Backend.Commit()
		th.Backend.Commit()

		// Double check that DON has limit set
		maxWorkflows, err := wfRegC.GetMaxWorkflowsPerDON(&bind.CallOpts{
			From: th.ContractsOwner.From,
		}, donFamily)
		require.NoError(t, err)
		require.Equal(t, workflowLimit, maxWorkflows.MaxWorkflows, "max workflows mismatch")
	}
}

func upsertWorkflowV2(
	t *testing.T,
	th *testutils.EVMBackendTH,
	wfRegC *workflow_registry_wrapper_v2.WorkflowRegistry,
	input RegisterWorkflowCMDV2,
) {
	t.Helper()
	_, err := wfRegC.UpsertWorkflow(
		th.ContractsOwner,
		input.Name,
		input.Tag,
		input.ID,
		input.Status,
		input.DonFamily,
		input.BinaryURL,
		input.ConfigURL,
		input.Attributes,
		input.KeepAlive,
	)
	require.NoError(t, err, "failed to register workflow")
	th.Backend.Commit()
	th.Backend.Commit()
	th.Backend.Commit()

	workflow, err := wfRegC.GetWorkflow(&bind.CallOpts{
		From: th.ContractsOwner.From,
	},
		th.ContractsOwner.From, input.Name, input.Tag,
	)
	require.NoError(t, err, "failed to register workflow")
	require.Equal(t, input.Name, workflow.WorkflowName, "workflow name mismatch")
	require.Equal(t, input.Tag, workflow.Tag, "workflow tag mismatch")
	require.Equal(t, input.ID, workflow.WorkflowId, "workflow ID mismatch")
	require.Equal(t, input.Status, workflow.Status, "workflow status mismatch")
	require.Equal(t, input.BinaryURL, workflow.BinaryUrl, "workflow binary URL mismatch")
	require.Equal(t, input.ConfigURL, workflow.ConfigUrl, "workflow config URL mismatch")
	// From contract comment:
	// For ACTIVE workflows this will resolve to the correct DON label.
	// For PAUSED/never‑assigned workflows the label is the empty string.
	if input.Status == WorkflowStatusActive {
		require.Equal(t, input.DonFamily, workflow.DonFamily, "workflow DON family mismatch")
	}
}
