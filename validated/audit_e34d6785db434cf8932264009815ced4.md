### Title
`ensure_match_transaction_info` skips validating `state_checkpoint_hash`/`position_state_checkpoint_hash` during chunk/replay verification, allowing a corrupted state root to be accepted as matching a committed `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by state-sync chunk execution and replay-verify tooling to confirm that a locally-computed `TransactionOutput` matches an authenticated, proof-carrying `TransactionInfo` before it is treated as validated. The function checks `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`, but it explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [1](#0-0) . The in-code comment acknowledges this gap directly: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution" [2](#0-1) .

### Finding Description
`TransactionInfo` carries the Sparse-Merkle-Tree state-checkpoint root hash(es) that bind a transaction's output to a specific ledger/state root [3](#0-2) , and for the newer `TransactionInfoV1`, also `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` (the "trading native" position-state tree root) [4](#0-3) . These roots are the on-chain-committed, accumulator-covered proof anchors for state at a checkpoint. `ensure_match_transaction_info` is the invariant-checking function called from `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `storage/db-tool/src/replay_on_archive.rs`, and `aptos-move/cli/src/commands.rs` , all of which rely on it to confirm that locally re-executed output actually matches the trusted, accumulator-verified `TransactionInfo` fetched from a proof or archive. Because the state-checkpoint fields are silently excluded from the comparison, any divergence between the locally computed state root and the authenticated root — e.g., from a bug in state-checkpoint hash computation, a corrupted JMT/position-state update, or non-determinism in `DoStateCheckpoint` — would not be detected by this check.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result must be detected" invariant for any code path relying on this comparator as its correctness gate (state-sync chunk apply verification and replay-verify/debugger tooling). A silently accepted mismatch means a node could persist a state root that has diverged from the network's authenticated state while its own consistency check reports success, undermining confidence in replay-verify-based bootstrapping/backup validation and this specific state-integrity gate. The comment in the code itself flags this as a known omission("replay-verify tooling... can report a successful replay even when the authenticated position state root diverges from local execution"), which is direct local evidence of the broken invariant.

### Likelihood Explanation
The gap only manifests when the position-state/hot-state checkpoint computation is enabled and diverges from the committed root; the code comment indicates the intent is to close this gap "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [2](#0-1) , implying the feature may not be fully active yet. I was not able to confirm within this session whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or the `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO` features referenced in `execution/executor/src/workflow/do_ledger_update.rs`) is enabled on mainnet, nor whether `state_checkpoint_hash` omission (which is unconditional, not just the position/hot-state fields) already applies to the currently-shipped V0 path. This uncertainty should be resolved before treating this as confirmed exploitable in production.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` (already present in V0) and, when present, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` against the locally computed values, failing loudly on mismatch just as it does for `write_set_hash` and `event_root_hash`.

### Proof of Concept
Not independently constructible from the available index snippets — reproducing this would require exercising the chunk-executor/replay-verify path with a deliberately corrupted state-checkpoint hash and confirming `ensure_match_transaction_info` still returns `Ok(())`. I was unable to fully trace the exact call site inside `execution/executor/src/chunk_executor/mod.rs` in the time available, so this should be verified against the full file before treating the finding as fully confirmed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
