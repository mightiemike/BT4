### Title
Poison-microblock validation only checks signer-key equality, not sequence equality, enabling slashing of honest non-equivocating miners - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
`check_microblock_header_signer` only verifies that two microblock headers were signed by the same key; it never checks that the two headers share the same sequence number, differ in content, or otherwise represent a genuine equivocation. `handle_poison_microblock`, which consumes this check, likewise never re-validates sequence equality before recording a punishment via `insert_microblock_poison`. This lets an attacker submit two legitimately-produced, different-sequence microblock headers from an honest, non-forking miner as a "poison" and have the miner's reward slashed.

### Finding Description
The broken equality is: **"two headers signed by the same key" (checked)** vs. **"two headers at the SAME sequence number with differing content" (a true double-sign, NOT checked)**.

`check_microblock_header_signer` recovers the pubkey hash from each header and only compares `pkh1 != pkh2`: [1](#0-0) 

`handle_poison_microblock` calls this check and then proceeds directly to look up the miner's pubkey height, verify maturity, and call `insert_microblock_poison(mblock_pubk_height, &sender_principal, mblock_header_1.sequence)` — at no point does it assert `mblock_header_1.sequence == mblock_header_2.sequence`, that `prev_block`/`version` match, or that the headers actually differ meaningfully (i.e., represent a genuine fork rather than two ordinary, sequential, honestly-produced microblocks): [2](#0-1) 

Notably, a stronger equality check (`sequence`, `prev_block`, `version` must all match, plus differing pubkeys rejected) does exist — but only in the mempool admission path `will_admit_mempool_tx`, not in the consensus-critical `process_transaction`/`handle_poison_microblock` path: [3](#0-2) 

Since mempool admission is a policy gate that a block-producing miner can bypass by constructing their own block/transactions directly (the mempool check is not part of the state-transition function `process_transaction`), a malicious miner — who only needs a single sortition win, satisfying the "unprivileged, single miner slot" threat model — can include a PoisonMicroblock transaction referencing `mblock_header_1` and `mblock_header_2` taken from two different, valid sequence numbers of an honest miner's legitimate, non-forking microblock stream (both correctly signed by that honest miner's key). Every honest node validating the block runs `process_transaction` → `handle_poison_microblock` → `check_microblock_header_signer`, which only checks the key match, and will accept the transaction as valid, applying the slashing/commission record against the honest miner.

### Impact Explanation
This falls under the "poison or reward mis-payment bounded to fees" High-severity category: the honest, non-equivocating miner's Stacks-block reward/coinbase is wrongfully slashed and a commission is potentially awarded to the malicious reporter, while the underlying chain state/consensus (block acceptance, MARF root, tenure ordering) is not otherwise disrupted — it does not cause a chain split or invalid-block-accepted/valid-block-rejected network-wide divergence, since all honest nodes independently reach the identical (wrong) verdict deterministically. This is a reward-mispayment vulnerability, not a fork/consensus-divergence vulnerability.

### Likelihood Explanation
The attacker only needs (a) knowledge of two legitimately-produced, differently-sequenced, honestly-signed microblock headers from a victim miner (trivially obtainable by observing the public microblock stream), and (b) the ability to get a PoisonMicroblock transaction processed by consensus code — either by winning a single sortition and including it directly in their own block (bypassing mempool admission entirely) or by convincing/waiting for it to be included some other way that doesn't run the mempool-only sequence check. No majority stake, no signer key compromise, and no privileged role is required, matching the allowed unprivileged threat model.

### Recommendation
Add an explicit equivocation check inside `check_microblock_header_signer` (or immediately before/inside `handle_poison_microblock`) mirroring the mempool-level check in `blocks.rs`: require `mblock_header_1.sequence == mblock_header_2.sequence`, `mblock_header_1.prev_block == mblock_header_2.prev_block`, `mblock_header_1.version == mblock_header_2.version`, and that the two headers are not identical (different `tx_merkle_root`/signature), in addition to the existing same-key check, before allowing `insert_microblock_poison` to proceed.

### Proof of Concept
Rust integration test plan (extending existing tests in `stackslib/src/chainstate/stacks/db/transactions.rs`, e.g. near `process_poison_microblock_valid_transaction`):
1. Generate an honest miner key `block_privk` and simulate a legitimate, monotonic microblock stream: `mblock_seq_5 = make_signed_microblock(&block_privk, &tx_privk, hash_a, 5)` and `mblock_seq_6 = make_signed_microblock(&block_privk, &tx_privk, hash_b, 6)`, ensuring `mblock_seq_6.header.prev_block == mblock_seq_5.block_hash()` (i.e., no fork — assert `mblock_seq_5.header.sequence != mblock_seq_6.header.sequence` and `mblock_seq_5.block_hash() == mblock_seq_6.header.prev_block`, the "equality" that should NOT be conflated with equivocation).
2. Craft `TransactionPayload::PoisonMicroblock(mblock_seq_5.header.clone(), mblock_seq_6.header.clone())`, sign with an attacker/reporter key, and call `StacksChainState::process_transaction`.
3. Assert BEFORE the fix: `process_transaction` returns `Ok(..)` and `StacksChainState::get_poison_microblock_report` shows a punishment recorded against `block_privk`'s pubkey hash despite no equivocation (`mblock_seq_5.header.sequence != mblock_seq_6.header.sequence`).
4. Assert AFTER the fix: `process_transaction` returns `Err(Error::ClarityError(ClarityError::BadTransaction(msg)))` with `msg` indicating "PoisonMicroblock transaction does not correspond to a valid fork" (or similar), i.e. `InvalidStacksTransaction`, and no poison report is inserted.

**Caveat**: I could not fully trace whether an equivalent sequence-equality check might exist elsewhere in the block-acceptance path (e.g., in `append_block` static-validation prior to invoking `process_transaction`) due to tool/iteration limits — the `will_admit_mempool_tx` check I found is explicitly a mempool-policy function, not consensus code, but I was unable to grep the full call graph for `process_transaction` invocations within `blocks.rs`'s block-validation routine (`append_block`) to rule out a duplicate guard there. If such a guard exists and is unconditionally applied to all transactions in every accepted block, this finding would be invalidated.

        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
