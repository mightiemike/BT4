### Title
Send-on-closed-channel panic / unsynchronized map access in `processTrigger` vs `UnregisterTrigger` crashes the node - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
`processTrigger` iterates `h.registeredWorkflows` and sends to `trigger.ch` without holding `h.mu`, while `UnregisterTrigger` takes `h.mu`, closes the channel, and deletes the map entry. Because the local `trigger` variable retains a reference to the same channel object, a concurrent `UnregisterTrigger` call can close the channel between the moment `processTrigger` reads it from the map and the moment it executes `case trigger.ch <- tr:`, causing an unrecovered "send on closed channel" panic in the gateway message-handling path.

### Finding Description
`processTrigger` (core/capabilities/webapi/trigger/trigger.go:80-149) ranges over `h.registeredWorkflows` (line 97) and later performs a blocking send `case trigger.ch <- tr:` (line 134) with **no mutex held** at all in this function. `UnregisterTrigger` (lines 255-266) is the only place that mutates the same map/channel, and it does so under `h.mu.Lock()`, calling `close(workflow.ch)` (line 263) followed by `delete(h.registeredWorkflows, req.TriggerID)` (line 264).

Because `trigger` in `processTrigger` is a value copied out of the map by `range`, but `trigger.ch` is a channel (a reference type), the copy still refers to the exact same underlying channel object that `UnregisterTrigger` can close concurrently. If an attacker keeps a `MethodWebAPITrigger` flood going so that a `processTrigger` goroutine is blocked (or about to block) on `trigger.ch <- tr` for a given `workflowID`, and an operator concurrently redeploys/deletes that workflow (triggering `UnregisterTrigger` for the same `TriggerID`), `close(workflow.ch)` can race with the pending send. A send to an already-closed channel panics at runtime with "send on closed channel," which is not recovered anywhere in this call chain (`HandleGatewayMessage` → `processTrigger` → gateway connector's message dispatch loop), crashing the node process rather than failing a single request.

Separately, and even more directly reachable without hitting the closed-channel race: `processTrget` ranges `h.registeredWorkflows` (line 97) with **no lock**, while `UnregisterTrigger` deletes from the same map under lock (line 264). Concurrent unsynchronized map iteration and map write is detected by the Go runtime and causes an immediate `fatal error: concurrent map iteration and map write` — this is a guaranteed crash (not merely a `-race` finding) whenever an unregister happens while a trigger message is being processed, since ranging a map is itself an unsynchronized read racing with a mutex-protected write elsewhere.

No authz/rate-limit check in `processTrigger` (sender/topic checks at lines 99-109) prevents this, since the race exists at the map/channel access layer, entirely independent of message content validity — an attacker only needs to be an allowed/valid-looking sender able to submit `MethodWebAPITrigger` gateway messages to keep triggers flowing while normal operational unregistration happens.

### Impact Explanation
This matches "Denial of service — node crash" impact category. A single race between routine workflow unregistration (redeploy/delete, an ordinary and frequent operational event) and attacker-controlled trigger traffic can crash the entire Chainlink node process, taking down all capabilities and jobs on that node, not just the web API trigger capability. This is a critical availability impact reachable purely through externally-submitted gateway messages combined with ordinary node operations, no privileged access required by the attacker.

### Likelihood Explanation
The precondition is realistic: any attacker who can reach `MethodWebAPITrigger` gateway messages for a workflow they're an allowed sender for can keep messages flowing continuously; workflow unregistration (redeploy/delete) is a normal, frequent operational event on the node, not privileged in the sense of requiring attacker cooperation. Given Go's map iteration/write race detection is unconditional (`fatal error: concurrent map iteration and map write` triggers deterministically once the runtime detects it, without needing `-race`), and channel double-close/send races are readily reproducible under load or with `-race`, this is a feasible and repeatable crash. The window is a genuine TOCTOU race in unsynchronized code, not a purely theoretical `-race`-only issue.

### Recommendation
Hold `h.mu` (a `RLock`/`Lock`) for the full duration of the map iteration and the channel send in `processTrigger`, or restructure so that `close()` in `UnregisterTrigger` is deferred/synchronized (e.g., using a per-trigger `sync.Once` guarded close, or replacing "close on unregister" with a `context.CancelFunc`/`done` channel that `processTrigger`'s `select` also watches instead of relying on channel closure) so that a send can never race with a close. At minimum, wrap the `range h.registeredWorkflows` and subsequent per-trigger access under `h.mu.RLock()`/`Unlock()`, and make `UnregisterTrigger`'s close/delete mutually exclusive with any in-flight send (e.g., use a `sync.WaitGroup` per trigger, or signal via a separate stop channel checked in the `select` instead of closing `trigger.ch` directly while it may still be sent to).

### Proof of Concept
1. Unit test in `core/capabilities/webapi/trigger/trigger_test.go` (run with `-race`):
   - Register a trigger via `RegisterTrigger` with a `TriggerID`/`workflowID`, no consumer reading from the returned channel.
   - Launch goroutine A: repeatedly call `HandleGatewayMessage`/`processTrigger` with valid `MethodWebAPITrigger` payloads matching the registered topic/sender, driving the send at line 134 to block (buffer of 1000 is easy to fill or make the send pending by not consuming).
   - Launch goroutine B: call `UnregisterTrigger` for the same `TriggerID` concurrently with goroutine A's in-flight `processTrigger` call.
   - Assert: the test should complete without panicking — but with the current code, a panic `"send on closed channel"` (or `fatal error: concurrent map iteration and map write`) is expected to surface, proving the race.
2. Alternative direct repro: manually construct `triggerConnectorHandler` with two workflows registered; use synchronization primitives (channels) to force `processTrigger`'s range to read `trigger.ch` for workflow X, block via a test-controlled full buffer, then have a second goroutine call `close(workflow.ch)` for workflow X via `UnregisterTrigger`; assert `recover()` catches "send on closed channel" panic that would otherwise propagate to the gateway connector's dispatch goroutine and crash the process. func (h *triggerConnectorHandler) processTrigger(ctx context.Context, gatewayID string, body *api.MessageBody, sender ethCommon.Address, payload webapicap.TriggerRequestPayload) error {
	// Pass on the payload with the expectation that it's in an acceptable format for the executor
	wrappedPayload, err := values.WrapMap(payload)
	if err != nil {
		return fmt.Errorf("error wrapping payload %w", err)
	}
	topics := payload.Topics

	// empty topics is error for V1
	if len(topics) == 0 {
		return errors.New("empty Workflow Topics")
	}

	// workflows that have matched topics
	matchedWorkflows := 0
	// workflows that have matched topic and passed all checks
	fullyMatchedWorkflows := 0
	for _, trigger := range h.registeredWorkflows {
		for _, topic := range topics {
			if trigger.allowedTopics[topic] {
				matchedWorkflows++
				if !trigger.allowedSenders[sender.String()] {
					err = fmt.Errorf("unauthorized Sender %s, messageID %s", sender.String(), body.MessageId)
					h.lggr.Debugw(err.Error())
					continue
				}
				if !trigger.rateLimiter.Allow(body.Sender) {
					err = fmt.Errorf("request rate-limited for sender %s, messageID %s", sender.String(), body.MessageId)
					continue
				}
				fullyMatchedWorkflows++
				TriggerEventID := body.Sender + payload.TriggerEventId

				// Emit trigger execution started event
				workflowExecutionID, genErr := events.GenerateExecutionID(trigger.workflowID, TriggerEventID)
				if genErr != nil {
					h.lggr.Errorw("failed to generate execution ID", "err", genErr)
					workflowExecutionID = ""
				}
				emitErr := events.EmitTriggerExecutionStarted(ctx, map[string]string{}, TriggerEventID, workflowExecutionID)
				if emitErr != nil {
					h.lggr.Errorw("failed to emit trigger execution started event", "err", emitErr)
				}

				tr := capabilities.TriggerResponse{
					Event: capabilities.TriggerEvent{
						TriggerType: TriggerType,
						ID:          TriggerEventID,
						Outputs:     wrappedPayload,
					},
				}
				select {
				case <-ctx.Done():
					return nil
				case trigger.ch <- tr:
					// Sending n topics that match a workflow with n allowedTopics, can only be triggered once.
					break
				}
			}
		}
	}
	if matchedWorkflows == 0 {
		return errors.New("no Matching Workflow Topics")
	}

	if fullyMatchedWorkflows > 0 {
		return nil
	}
	return err
}

func (h *triggerConnectorHandler) UnregisterTrigger(ctx context.Context, req capabilities.TriggerRegistrationRequest) error {
	h.mu.Lock()
	defer h.mu.Unlock()
	workflow, ok := h.registeredWorkflows[req.TriggerID]
	if !ok {
		return fmt.Errorf("triggerId %s not registered", req.TriggerID)
	}

	close(workflow.ch)
	delete(h.registeredWorkflows, req.TriggerID)
	return nil
}
