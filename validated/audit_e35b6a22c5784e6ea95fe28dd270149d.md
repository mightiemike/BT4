### Title
Duplicate obsolete-account marking in `ObsoleteAccounts::mark_accounts_obsolete` causes double-counted obsolete bytes and account counts - (File: accounts-db/src/obsolete_accounts.rs)

### Summary
`ObsoleteAccounts::mark_accounts_obsolete()` blindly pushes each `(offset, data_len, slot)` triple onto an internal `Vec` with no check for whether that offset has already been recorded as obsolete. [1](#0-0)  This mirrors the reported Forta pattern: `reward()` wrote `_rewardsPerEpoch[shareId][epochNumber] = amount` and unconditionally added `amount` to `totalRewardsDistributed` with no check that the epoch had already been rewarded, corrupting the running total. Here, if the same account offset within a storage is marked obsolete more than once (e.g., by two different call sites reaching the same storage/offset), the vector accumulates duplicate entries, and every downstream sum over `self.accounts` (obsolete byte/account totals) double-counts that account.

### Finding Description
`mark_accounts_obsolete` is called from multiple, independent code paths against the same `AccountStorageEntry.obsolete_accounts`: `accounts_db.rs`, `ancient_append_vecs.rs` (ancient-storage packing/shrink), and `account_storage_reader.rs` (snapshot rebuild path), in addition to test call sites. [2](#0-1)  Nothing in `AccountStorageEntry` or `ObsoleteAccounts` de-duplicates by `offset` before pushing, unlike the analogous `zero_lamport_single_ref_offsets` and `tombstone_offsets` trackers in the same file, which are `IntSet`s that explicitly return whether the insert was new and are documented as intentionally allowing at most a bounded double-count ("we will count this account as dead twice... this should be fine"). [3](#0-2) [4](#0-3)  `ObsoleteAccounts`, by contrast, is a plain `Vec<ObsoleteAccountItem>` with no such bound or safeguard, so a duplicate mark is not a single documented double-count but an unbounded accumulation each time the same offset is marked again. [5](#0-4) 

The consequence surfaces in `get_obsolete_bytes()`, which sums `calculate_stored_size(data_len)` over every entry in `self.accounts` (after filtering by slot) to compute obsolete bytes for a storage: any duplicate entries produced by a second call to `mark_accounts_obsolete` on already-marked offsets inflate this sum beyond the storage's real obsolete byte count. [6](#0-5)  This value feeds shrink/ancient-packing decisions and obsolete-account accounting used by `generate_index_for_slot`/index rebuild during startup, which separately tracks `num_obsolete_accounts_marked`, `num_obsolete_bytes_removed`, and `storage_info` (`stored_size`/`count`) totals used to size and validate storages. [7](#0-6) [8](#0-7)  A test elsewhere in the same file explicitly documents and asserts on the expected `stored_size` being exactly the sum of non-obsolete accounts' sizes, showing how sensitive this accounting is to correct (non-duplicated) obsolete tracking. [9](#0-8) 

### Impact Explanation
If an offset is marked obsolete twice for the same storage (via two independent call paths that both decide the account at that offset is now obsolete, e.g. clean followed by ancient-append-vec packing, or a startup rebuild path re-marking accounts already marked by an earlier pass), the storage's obsolete-byte accounting becomes inflated relative to reality. This can cause `get_obsolete_bytes()` to report more obsolete bytes than the storage actually contains, skewing shrink-candidate selection, ancient-storage packing math (`total_rewrite_bytes`, `alive_bytes_after_shrink`), and the size-assertion checks in `assert!(info.stored_size <= u64_align!(storage.accounts.len()), ...)` used during index generation. [10](#0-9)  In the worst case this manifests as an incorrect accounting of alive/obsolete bytes for a storage that persists across snapshot writes (`obsolete_accounts_for_snapshots`), producing a snapshot whose obsolete-account bookkeeping diverges from an honestly-replayed node's live state — a snapshot-vs-replay accounting mismatch rather than a crash.

### Likelihood Explanation
This is a low/uncertain-likelihood finding: I was not able to fully trace, within the available index, whether any of the concrete call sites in `accounts_db.rs`, `ancient_append_vecs.rs`, or `account_storage_reader.rs` can legitimately invoke `mark_accounts_obsolete` twice for the *same offset* on the *same storage* under normal operation (the file/index size limits prevented me from reviewing every call site's guarding logic in full). It is plausible that callers already guarantee each offset is only ever marked once (e.g., by removing/consuming index entries before marking), in which case this would not be practically reachable. The complete absence of a de-duplication check, in a codebase that explicitly implements de-duplication (`IntSet`, `bool`/count-returning inserts) for the structurally similar `zero_lamport_single_ref_offsets` and `tombstone_offsets` trackers on the very same struct, is what makes this worth flagging as a latent risk rather than a confirmed exploit.

### Recommendation
Add an idempotency check to `ObsoleteAccounts::mark_accounts_obsolete` (or to its callers) so that marking the same `offset` obsolete more than once is a no-op (or updates in place) rather than appending a duplicate `ObsoleteAccountItem`, mirroring the pattern already used for `zero_lamport_single_ref_offsets`/`tombstone_offsets` (dedup via `IntSet`, returning whether the insert was new). Additionally, consider asserting/logging when a duplicate mark is attempted so any latent double-invocation from clean/shrink/ancient-packing/startup-rebuild paths is caught rather than silently inflating obsolete-byte totals.

### Proof of Concept
Conceptual repro (not confirmed against real caller invariants due to index limits):
1. Create an `AccountStorageEntry` and write an account at some `offset` with `data_len` bytes.
2. Call `storage.obsolete_accounts.write().unwrap().mark_accounts_obsolete([(offset, data_len)].into_iter(), slot_a)`.
3. Call it again for the same `(offset, data_len)` with `slot_b >= slot_a` (simulating two independent code paths marking the same account obsolete, e.g. once during clean and again during ancient-append-vec packing or index regeneration).
4. Observe `storage.get_obsolete_bytes(None)` returns roughly `2 * calculate_stored_size(data_len)` instead of `calculate_stored_size(data_len)`, analogous to `RewardsDistributor.reward()` adding the same epoch's `amount` twice into `totalRewardsDistributed`. [1](#0-0) [11](#0-10)

#[test_case(8)]
#[test_case(5)]
#[test_case(0)]
fn test_calculate_storage_count_and_alive_bytes_obsolete_account(
    num_accounts_to_mark_obsolete: usize,
) {
    let accounts = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    accounts.accounts_index.set_startup(Startup::Startup);

    let account_sizes = [1, 5, 10, 50, 100, 500, 1000, 2000];

    // Make sure we have enough accounts to mark obsolete. If this fails, just add more
    // entries to account_sizes
    assert!(account_sizes.len() >= num_accounts_to_mark_obsolete);

    let account_list: Vec<_> = account_sizes
        .into_iter()
        .map(|size| {
            (
                Pubkey::new_unique(),
                AccountSharedData::new(1, size, AccountSharedData::default().owner()),
            )
        })
        .collect();

    let slot0 = 0;
    let storage = accounts.create_store(slot0, 10_000);
    let offsets = storage.accounts.write_accounts(&(slot0, &account_list[..]));

    let offsets = offsets.unwrap().offsets;
    let data_lens = storage.accounts.get_account_data_lens(&offsets);
    let mut offsets: Vec<_> = offsets.into_iter().zip(data_lens).collect();

    // Randomize the accounts that get marked obsolete
    let mut rng = rand::rng();
    offsets.shuffle(&mut rng);

    let (accounts_to_mark_obsolete, accounts_to_keep) =
        offsets.split_at(num_accounts_to_mark_obsolete);

    storage
        .obsolete_accounts
        .write()
        .unwrap()
        .mark_accounts_obsolete(accounts_to_mark_obsolete.iter().cloned(), slot0 + 1);

    let mut reader = crate::append_vec::new_scan_accounts_reader();
    let mut accum = IndexGenerationAccumulator::with_slots_capacity(1);
    accounts.generate_index_for_slot(&mut reader, &mut accum, 0, &storage);
    assert_eq!(
        accum.num_obsolete_accounts_skipped,
        num_accounts_to_mark_obsolete as u64
    );
    assert_eq!(
        accum.storage_info.len(),
        if num_accounts_to_mark_obsolete < account_sizes.len() {
            1
        } else {
            0
        }
    );

    for (slot, value) in accum.storage_info {
        // Sum up the stored size of all non obsolete accounts
        let expected_stored_size: usize = accounts_to_keep
            .iter()
            .map(|(_, data_len)| storage.accounts.calculate_stored_size(*data_len))
            .sum();

        assert_eq!(
            (slot, value.count, value.stored_size),
            (0, accounts_to_keep.len(), expected_stored_size)
        );
    }
    accounts.accounts_index.set_startup(Startup::Normal);
