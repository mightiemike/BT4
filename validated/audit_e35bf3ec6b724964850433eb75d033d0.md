### Title
Tombstone offsets are silently dropped on `bank_from_snapshot_dir` restore, causing dead accounts to be re-inserted into the index during `generate_index` - (File: `accounts-db/src/account_storage_entry.rs`, `runtime/src/serde_snapshot/obsolete_accounts.rs`, `runtime/src/serde_snapshot.rs`)

### Summary
An unprivileged user can drive zero-lamport churn that causes `shrink` to carry forward "tombstone" accounts (zero-lamport accounts physically retained in a storage but deliberately removed from the accounts index). The obsolete-accounts snapshot file written for fastboot (`fastboot_version >= 2`) only serializes `obsolete_accounts`, never `tombstone_offsets`, and `reconstruct_single_storage`/`AccountStorageEntry::new_existing` never restore `tombstone_offsets` either. As a result, after `bank_from_snapshot_dir` restores storages and runs `generate_index`, previously-dead tombstone bytes are rescanned as ordinary live zero-lamport accounts and re-inserted into the accounts index — a state a from-genesis replay (or a live, never-restarted node) never reaches.

### Finding Description
`AccountStorageEntry` tracks two independent "dead but still physically present" sets: `obsolete_accounts` and `tombstone_offsets`. [1](#0-0) 

Both sets are combined by `excluded_offsets()`, which is what `scan_accounts`/`scan_accounts_without_data` use to skip dead bytes: [2](#0-1) 

`generate_index_for_slot` (used only at startup/snapshot-restore time to rebuild the accounts index from raw storage bytes) relies on this same `scan_accounts`, and treats any zero-lamport account it encounters as alive, pushing it into the index and marking it a "zero-lamport single ref" candidate: [3](#0-2) [4](#0-3) 

Tombstones are created by `shrink`/`store_tombstones`, which writes the tombstone bytes into a *new* storage and records the offsets only via `batch_insert_tombstone_offsets` — explicitly *not* adding them back to the index: [5](#0-4) 

However, when a fastboot (dir-based) snapshot is written and later restored, only `obsolete_accounts` are persisted and rehydrated — `tombstone_offsets` is never part of the serialized format: [6](#0-5) [7](#0-6) 

`rebuild_storages_from_snapshot_dir` only deserializes and threads through `obsolete_accounts`, feeding it into `SnapshotStorageRebuilder::rebuild_storages`; there is no equivalent path for `tombstone_offsets`: [8](#0-7) 

Consequently, a freshly reconstructed `AccountStorageEntry` from `bank_from_snapshot_dir` always starts with an **empty** `tombstone_offsets` set (there is no constructor path that populates it from the snapshot). When `reconstruct_accountsdb_from_fields` subsequently calls `generate_index`, the tombstone bytes are no longer excluded by `excluded_offsets()`, so they are scanned as ordinary zero-lamport accounts and inserted into the freshly built accounts index — even though, pre-restart, that exact pubkey had been explicitly and permanently removed from the index (that is the entire purpose of the tombstone mechanism, per the doc comment: "The index has no slot_list entry pointing at them"). [9](#0-8) 

This is a genuine index-state divergence between (a) a live node that has processed the shrink and never restarts (tombstone stays index-absent forever) and (b) the same node after a fastboot-dir restart (tombstone becomes index-present again as a zero-lamport-single-ref entry), and it is a divergence from full ledger replay from genesis, which — since it always builds the index incrementally via normal store/clean/shrink transitions rather than via `generate_index`'s raw storage rescans — never resurrects a tombstoned entry.

Preconditions match the attacker model exactly: an unprivileged user only needs to fund an account, then zero it out (send all lamports away) while an older reference to the same account still exists elsewhere, and then let a later transaction dirty/clean the older slot so `shrink` converts the zero-lamport single-ref into a tombstone (`store_tombstones`) instead of purging it outright — this is exercised directly by `test_shrink_converts_zero_lamport_single_ref_account_to_tombstone`. [10](#0-9) 

### Impact Explanation
This falls under "an honest node's own snapshot generation, packaging, or rebuild produces a bank disagreeing with full ledger replay". Concretely:
- The restored node's accounts index gains a slot-list entry for a pubkey that a from-genesis replay (or the pre-restart live node) would never have in the index, breaking the "no index entry for tombstoned/finalized accounts" invariant.
- The restored `AccountStorageEntry`'s `num_alive_accounts`/`num_alive_bytes` (and consequently `alive_bytes()`) accounting diverges from a from-genesis-replay reaching the same slot, since the tombstone bytes are now counted as alive in the rebuilt storage but were dead bytes before restart.
- Because the account is re-treated as a "zero-lamport single ref" rather than a tombstone, subsequent clean/shrink decisions for this storage on the restarted node take a different path than they would on a non-restarted or freshly-replayed node, which can cascade into further storage/hash bookkeeping divergence at later slots.

This matches the scoped-impact category of "honest-node snapshot-vs-replay mismatch" that can corrupt post-restart index/storage state, potentially contributing to bank-hash divergence after further processing.

### Likelihood Explanation
- Fully reachable by an unprivileged user: fund → zero-lamport → force clean/shrink is ordinary account lifecycle activity requiring no special privileges, only lamports to pay for the transactions.
- Requires no validator/operator cooperation — any honest validator running default clean/shrink/snapshot logic with `fastboot_version >= 2` snapshot dirs is affected.
- Requires the operator/validator to actually restart from a fastboot snapshot directory (not an archive) while tombstones exist in the affected storage, which is a normal, encouraged operational flow (fastboot exists specifically to speed up restarts).
- Repeatable: any zero-lamport churn pattern that produces tombstones via shrink, followed by a restart from snapshot dir, reproduces the divergence deterministically.

### Recommendation
Extend the fastboot snapshot-dir format to also persist and restore `tombstone_offsets` per storage, symmetric to how `obsolete_accounts` is handled today:
- Add tombstone offsets to `SerdeObsoleteAccounts`/`SerdeObsoleteAccountsMap` (or a sibling structure) in `runtime/src/serde_snapshot/obsolete_accounts.rs`.
- Thread the deserialized tombstone offsets through `reconstruct_single_storage` in `runtime/src/serde_snapshot.rs` and into `AccountStorageEntry::new_existing` (or call `batch_insert_tombstone_offsets` immediately after construction) in `runtime/src/snapshot_utils.rs`'s `rebuild_storages_from_snapshot_dir`.
- Add a regression test mirroring `test_shrink_converts_zero_lamport_single_ref_account_to_tombstone` but going through `create_bank_snapshot_from_bank` + `bank_from_snapshot_dir`, asserting the tombstoned pubkey remains absent from the restored bank's accounts index.

pub(crate) fn reconstruct_single_storage(
    slot: &Slot,
    append_vec_file_info: FileInfo,
    id: AccountsFileId,
    obsolete_accounts: Option<(ObsoleteAccounts, AccountsFileId, usize)>,
) -> Result<Arc<AccountStorageEntry>, SnapshotError> {
    // The storage length is taken directly from the on-disk file size (see
    // `AccountsFile::new_for_startup`). When restoring from an archive the obsolete accounts have
    // been physically removed during serialization, and when restoring from a snapshot directory
    // they are still present in the file. In both cases the file size already reflects the exact
    // number of bytes the storage spans, so there is no need to carry the length separately in the
    // snapshot fields.
    //
    // When restoring from an archive, obsolete accounts will always be `None`.
    // When restoring from fastboot, obsolete accounts will be 'Some' if the storage contained
    // accounts marked obsolete at the time the snapshot was taken.
    let obsolete_accounts =
        if let Some((obsolete_accounts, obsolete_id, _obsolete_bytes)) = obsolete_accounts {
            if obsolete_id != id {
                return Err(SnapshotError::MismatchedAccountsFileId(id, obsolete_id));
            }

            obsolete_accounts
        } else {
            ObsoleteAccounts::default()
        };

    let accounts_file = AccountsFile::new_for_startup(append_vec_file_info)?;
    Ok(Arc::new(AccountStorageEntry::new_existing(
        *slot,
        id,
        accounts_file,
        obsolete_accounts,
    )))
}
