# No vulnerability found for this question.

**Analysis:**

The premise that an honest miner could produce two `StacksMicroblockHeader`s with matching `sequence` but differing `prev_block` as a "legitimate stream continuation, not equivocation" does not hold under the codebase's actual invariants.

Within a single legitimate (non-conflicting) microblock stream produced by one honest signing key, the sequence number strictly and uniquely identifies position: each sequence value has exactly one valid header, whose `prev_block` is fixed by the hash of the prior microblock in that same stream [1](#0-0) . The codebase's own fork-detection logic in `validate_parent_microblock_stream` treats "same sequence number, different block hash" as, by definition, a *deliberate microblock fork* [2](#0-1) , and this exact criterion is exercised by the "deliberate miner fork" test which asserts a `PoisonMicroblock` payload is correctly produced from such a pair [3](#0-2) . There is no honest-operation code path that produces two distinct, validly-signed headers at the same sequence number within one continuous stream without that being an actual double-signature at that slot.

The only way `check_microblock_header_signer` could accept two same-signer headers with matching `sequence` but different `prev_block` from genuinely unrelated tenures is if the miner's microblock private key were deterministically reused across two different tenures/forks. The keychain derivation ties the microblock key to `(burn_block_height, parent_stacks_hash)` [4](#0-3)  and [5](#0-4) , so any such collision would require the honest miner to actually mine competing tenures on a genuine, simultaneous burnchain fork sharing the same parent Stacks block and burn height — a scenario dependent on real Bitcoin-level fork conditions outside the attacker's control, and explicitly out of scope ("Bitcoin-consensus defects with no path through this repo").

`handle_poison_microblock`'s slashing logic (`check_microblock_header_signer`, `get_microblock_pubkey_hash_height`, maturity window check) correctly reduces to: same signer + same sequence-or-prev_block ⇒ genuine double-signature at that slot, for any stream produced under the documented non-equivocation invariant [6](#0-5) . The equality "poison-microblock reward paid == exactly one valid double-signature by the slashed miner at the same slot" is preserved; the described proof-of-concept scenario cannot be constructed for an honestly-operating, non-equivocating miner.

    /// `salt` can be any byte string; in practice, it's the parent Stacks block's block ID hash.
    pub fn make_microblock_secret_key(
        &mut self,
        burn_block_height: u64,
        salt: &[u8],
    ) -> StacksPrivateKey {
        let (_, mut sk) = self.make_stacks_keypair(burn_block_height, salt);

        );
        sk
