### Title
Unbounded, un-timed blocking wait on the class manager / state-sync client during stateful transaction validation can pin a gateway thread indefinitely - (File: `crates/apollo_gateway/src/sync_state_reader.rs`)

### Summary
The Xen CVE describes a resource (the p2m lock) that can be left "unavailable indefinitely" because an error path never releases it, letting a single guest hang the host. The sequencer has the same bug class in `SyncStateReader`, which the gateway uses as the `StateReader` for stateful validation of every incoming transaction: its class/state lookups call `Handle::block_on` on the class-manager/state-sync RPC futures with **no timeout or deadline**, so a stalled dependency permanently pins the calling thread, exactly the hazard that a sibling component (`apollo_state_reader::ClassReader`) was explicitly hardened against.

### Finding Description
`SyncStateReader::read_sierra` and `SyncStateReader::get_contract_class_from_client` drive the class-manager and state-sync clients synchronously via `self.runtime.block_on(...)`, with no timeout wrapper: [1](#0-0) 

This is structurally identical to the pattern that was independently identified and fixed in `apollo_state_reader::ClassReader::block_on_request`, which explicitly bounds the class-manager wait with a `deadline` because, in its own words, "nothing can cancel a thread parked there" once it enters `block_on` on a request that never completes: [2](#0-1) 

The regression test for that fix documents the exact failure mode being defended against — a class manager that "never answers" pins the thread "forever," turning any caller reaching it (e.g. `call_contract`/block production) into a stuck thread: [3](#0-2) 

`SyncStateReader` is wired in as the gateway's `StateReader` (`gateway_fixed_block_state_reader`) and reached from `get_nonce_from_state` / class-hash resolution during `run_pre_validation_checks`, i.e. on the path every submitted transaction takes through stateful validation: [4](#0-3) [5](#0-4) 

Unlike `ClassReader`, `SyncStateReader` has no `deadline` field and no bound on how long `block_on` can wait for `get_sierra` / `is_class_declared_at` / `get_executable` to resolve. If the class-manager or state-sync client backing the gateway stalls or is slow to answer for even a subset of class hashes (network partition, backpressure, an overloaded local component reached over an in-process channel with "no request timeout of its own" — as literally described in the sibling fix's comments), the thread executing that transaction's validation is pinned indefinitely, never returned to the pool that services subsequent transaction validations, mirroring the Xen bug where the p2m lock is "unavailable indefinitely" because of an unbounded wait in an error/edge condition.

### Impact Explanation
Every gateway worker/blocking-thread that gets stuck this way is permanently removed from the pool that performs stateful validation for newly submitted transactions. Because the reachable trigger is any transaction whose validation needs a class lookup through this reader, an attacker can repeatedly submit such transactions during a period when the dependency is slow (which does not require compromising the class manager — only for it to be legitimately congested or partitioned, a condition attacker traffic itself can help induce). Enough stuck threads exhaust the validation pool, so the gateway can no longer admit or validate new transactions — "a network unable to confirm new transactions," one of the explicitly accepted impacts for this analog.

### Likelihood Explanation
The trigger requires only ordinary transaction submission by any unprivileged sender whose transaction validation needs to resolve a class through `SyncStateReader` (e.g. account/class existence checks) at a moment when the class-manager/state-sync dependency is slow or backed up — no special privileges, no malicious operator, and no p2p/consensus role are required. The absence of any deadline (in contrast to the already-hardened `ClassReader`) means there is no existing safety net on this path.

### Recommendation
Apply the same fix pattern used for `ClassReader`: add a `deadline`/timeout parameter to `SyncStateReader`, and wrap each `block_on` call (`get_sierra`, `is_class_declared_at`, `get_executable`) with `tokio::time::timeout_at`, spawning the request rather than racing it directly so the underlying RPC/channel isn't torn down mid-flight (mirroring `ClassReader::block_on_request`). Surface a bounded `StateError::StateReadError("...timed out")` instead of blocking forever, so a stalled dependency degrades gateway throughput instead of permanently starving its validation thread pool.

### Proof of Concept
1. Configure (or induce, e.g. via load) a class-manager/state-sync backend that is slow or unresponsive for a given `class_hash` used by `SyncStateReader::read_sierra` / `get_contract_class_from_client`.
2. Submit a transaction whose stateful validation resolves that class (e.g. a `Declare`/`Invoke` referencing that class) through the gateway's `StatefulTransactionValidator`, which uses `gateway_fixed_block_state_reader` (`SyncStateReader`) — see `run_pre_validation_checks` in `crates/apollo_gateway/src/stateful_transaction_validator.rs`.
3. Observe that the worker thread handling this validation blocks indefinitely inside `Handle::block_on` in `crates/apollo_gateway/src/sync_state_reader.rs` (`read_sierra`/`get_contract_class_from_client`), since no timeout exists on this path, unlike the analogous, already-fixed `ClassReader::block_on_request` in `crates/apollo_state_reader/src/apollo_state.rs`.
4. Repeat with concurrent submissions until the gateway's available validation threads/tasks are exhausted, at which point new legitimate transactions can no longer be validated/admitted.

**Note on completeness:** I was not able to fully trace, within the available tool budget, the exact concurrency primitive (e.g., which specific blocking-thread pool or `spawn_blocking` call) that hosts `SyncStateReader` validation calls in the gateway's request-handling pipeline, so the precise thread-pool-exhaustion mechanics (pool size, request-handling concurrency model) are inferred from the analogous, documented fix in `apollo_state_reader::ClassReader` rather than directly confirmed in `apollo_gateway`. A Devin session with full repository access would be needed to pin down the exact call site that invokes `SyncStateReader` per incoming transaction and its threading model.

                )
            });

        Ok(contract_class)

impl ClassReader {
    /// Runs `request` on `self.runtime`, bounding it by `self.deadline` when set.
    ///
    /// Spawns `request` rather than awaiting it directly: a local class manager is reached
    /// through a channel whose response sender the server already holds once the request is
    /// sent (see `LocalComponentClient::send`), and the server panics if that channel's receiver
    /// is dropped before the response is sent — "considered a bug" by its own comment, since a
    /// well-behaved client always waits for its response. Racing `request` itself against the
    /// deadline with `tokio::time::timeout` would drop it, and that receiver, the moment the
    /// deadline passed. Spawning first means only our wait is bounded; `request` keeps running
    /// to completion in the background so the server never observes a closed channel.
    fn block_on_request<Fut>(&self, request: Fut) -> StateResult<Fut::Output>
    where
        Fut: Future + Send + 'static,
        Fut::Output: Send + 'static,
    {
        let Some(deadline) = self.deadline else {
            return Ok(self.runtime.block_on(request));
        };

        self.runtime.block_on(async {
            let request_task = self.runtime.spawn(request);
            match tokio::time::timeout_at(deadline.into(), request_task).await {
                Ok(join_result) => join_result.map_err(|join_error| {
                    StateError::StateReadError(format!(
                        "Class manager request task panicked: {join_error}"
                    ))
                }),
                Err(_elapsed) => Err(StateError::StateReadError(
                    "Class manager request timed out; the reader's deadline passed.".to_string(),
                )),
            }
        })
    }

/// Without a `deadline`, a class manager that never answers hangs `get_compiled_class` forever:
/// `ClassReader` blocks the thread it runs on (a shared blocking-pool thread when reached through
/// `call_contract` or block production) inside `block_on`, and nothing can cancel a thread parked
/// there. A `deadline` bounds the wait, so the thread is released within that window instead of
/// being pinned indefinitely.
#[tokio::test(flavor = "multi_thread")]
async fn class_reader_times_out_when_the_class_manager_never_answers() {
    let class_hash = ClassHash(felt!(0x1234_u16));
    // Cairo 1 declaration marker only, with no definition behind it: `is_declared` reads this
    // table, so reading the class must go through the class manager.
    let state_diff = ThinStateDiff {
        class_hash_to_compiled_class_hash: IndexMap::from([(
            class_hash,
            CompiledClassHash::default(),
        )]),
        ..Default::default()
    };

    let ((storage_reader, mut storage_writer), _temp_dir) = get_test_storage();
    storage_writer
        .begin_rw_txn()
        .unwrap()
        .append_state_diff(BlockNumber::default(), state_diff)
        .unwrap()
        .commit()
        .unwrap();

    let request_timeout = Duration::from_millis(200);
    let class_reader = Some(ClassReader {
        reader: Arc::new(StalledClassManagerClient),
        runtime: tokio::runtime::Handle::current(),
        deadline: Some(Instant::now() + request_timeout),
    });
    let apollo_reader =
        ApolloReader::new_with_class_reader(storage_reader, BlockNumber(1), class_reader);

    // Bounds the test itself: without the fix, the call below hangs forever, turning a
    // regression into a stuck test rather than a failing one.
    let result = tokio::time::timeout(
        request_timeout * 10,
        tokio::task::spawn_blocking(move || apollo_reader.get_compiled_class(class_hash)),
    )
    .await
    .expect("get_compiled_class did not return within 10x its own request timeout.")
    .expect("Reading a declared class panicked.");

    assert_matches!(
        result,
        Err(StateError::StateReadError(message)) if message.contains("timed out")
    );
}
