### Title
Stale cached `cycle-total-weight` in `signers-voting.clar` can desync the voting threshold from the live `.signers` weight set - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
`signers-voting.clar` caches the sum of all signer weights for a reward cycle the first time it is needed and never refreshes it, exactly the same "unrefreshed accounting snapshot" defect described in the external report (a per-user snapshot that is not updated after the underlying state changes, so later calculations use stale data). Here the snapshot is `cycle-total-weight`, and the underlying state it is supposed to track is the `.signers` contract's per-cycle weight table, which can be (re)written more than once for the same `reward-cycle` by the node's boot-contract update path.

### Finding Description
`get-and-cache-total-weight` memoizes the sum of `.signers get-signers` weights the first time it's invoked for a `reward-cycle`, and every subsequent call for that cycle returns the cached value without recomputation: [1](#0-0) 

This cache feeds `get-threshold-weight`, which is the equality signers rely on to decide whether an aggregate public key is "approved": [2](#0-1) 

Meanwhile, `vote-for-aggregate-public-key` computes each individual vote's weight *live*, straight from `.signers get-signer-by-index`, not from the cache: [3](#0-2) 

The `.signers` boot contract's guard against corruption is only that `last-set-cycle` must equal the `reward-cycle` argument — it does **not** prevent `set-signers` from being called a second time for the *same* `reward-cycle` with a different weight distribution: [4](#0-3) 

The node writes both `last-set-cycle` and the weight table atomically from `update_signers`, back-to-back in the same Clarity transaction: [5](#0-4) 

`update_signers` is invoked by `pox_4_compute_and_update_signers` / `pox_5_compute_and_update_signers`, each of which recomputes the signer set (and therefore each signer's `weight`, since weight is a *quotient/apportionment* of stacked amounts against a threshold, not additive): [6](#0-5) [7](#0-6) 

Because nothing in `signers.clar` or in the calling `update_signers` path enforces "compute and publish the reward-cycle's signer weights exactly once," any code path that reprocesses/rewrites the boundary block for an upcoming reward cycle (e.g. the burnchain tip for the prepare-phase-closing block being replaced by a competing block at the same height — an ordinary, unprivileged fork-choice event, not a 51% attack) can cause `set-signers` to run twice for the same `reward-cycle`, with a different `stacked_amt`/`weight` apportionment the second time (the Hare-quota logic in `make_signer_set`/`pox_5_make_signer_set` is sensitive to exactly which stake entries are included, e.g. via `equal_stakes_exceeding_reward_slots_are_not_all_zeroed`-style tie-break/threshold edge cases): [8](#0-7) 

If any `vote-for-aggregate-public-key` call already occurred for that `reward-cycle` under the *first* weight distribution (which populates `cycle-total-weight` via `get-and-cache-total-weight`), the cache is never invalidated when `.signers` is subsequently rewritten. All later votes in that cycle are then judged against `threshold-weight = f(stale total)`, while each vote's own weight is read live from the *new* `.signers` table. The equality "signer's weight is a fraction of the *current* total signer weight, and reaching `threshold-consensus`% of that current total approves the key" is broken: the threshold denominator and the per-vote weight numerator come from two different signer-set snapshots.

### Impact Explanation
If the stale (first) total is smaller than the true (second, live) total, a strict subset of signers — controlling less than the intended `threshold-consensus`/1000 fraction of the *actual* reward-cycle weight — can push `new-total >= threshold-weight` and get `aggregate-public-keys` populated for the reward cycle, i.e. an aggregate public key is "approved" without the genuine supermajority of the live signer set having voted for it. This is a minority-triggerable signer-weight/threshold divergence bounded to the signer-voting boot contract's state — falls under "High: a minority-triggerable ... static-validation divergence, signer weight below threshold or from the wrong set."

### Likelihood Explanation
The precondition — `set-signers` being invoked more than once for the same `reward-cycle` with a different resulting weight apportionment, interleaved with at least one already-cast vote for that cycle — depends on the exact retry/reorg semantics of the Nakamoto reward-cycle/anchor-block computation pipeline that calls `pox_4_compute_and_update_signers`/`pox_5_compute_and_update_signers`. I was not able to fully trace, within the available tool budget, the exact call sites in `stackslib/src/chainstate/nakamoto/mod.rs` that invoke this recomputation to confirm whether it can genuinely be triggered twice for one reward cycle under an ordinary (non-majority) burnchain fork/reorg during the prepare phase, versus being architecturally guaranteed to run exactly once. This should be verified against the reward-set computation call sites before treating this as confirmed-exploitable; the cache-staleness bug itself (no invalidation of `cycle-total-weight` on `.signers` rewrite) is confirmed by direct code inspection.

### Recommendation
- Remove the memoization in `get-and-cache-total-weight`/`cycle-total-weight`, or invalidate/recompute it whenever `.signers.set-signers` writes a new entry for that `reward-cycle` (e.g., have `set-signers` clear/overwrite the cached total, or have `signers-voting.clar` recompute the total on every vote instead of caching).
- Alternatively, make `.signers.set-signers` reject a second write for a `reward-cycle` that has already been set (idempotency guard), so the signer weight table for a cycle is provably immutable once voting can begin.

### Proof of Concept
1. Node computes reward-cycle `N`'s signer set via `pox_5_compute_and_update_signers`, writing weights `W1` to `.signers` (`update_signers`), giving total weight `T1`.
2. A signer calls `vote-for-aggregate-public-key` for cycle `N`, round `0`; this populates `cycle-total-weight[N] = T1` via `get-and-cache-total-weight`, and `threshold-weight = T1 * threshold-consensus / 100`.
3. Before the reward cycle activates, the block that triggered step 1 is replaced (ordinary fork-choice/reorg at the prepare-phase boundary), and the coordinator recomputes the reward set for cycle `N`, this time producing a different weight apportionment `W2` with a larger true total `T2 > T1` (e.g., different stake entries pass the Hare-quota threshold). `update_signers` calls `set-signers` again for cycle `N`, since `last-set-cycle == N` still holds (see `signers.clar` lines 22-33 above).
4. Signers now holding weights from `W2` vote using `get-signer-weight`, which reads live `W2` weights, but `get-threshold-weight` still divides by the stale `T1` cached in step 2.
5. A set of signers whose summed `W2` weight is `>= T1 * threshold-consensus/100` but `< T2 * threshold-consensus/100` gets `aggregate-public-keys[N]` set — the key is "approved" without meeting the genuine consensus threshold over the reward cycle's actual signer weight.

    pub fn make_signer_set(
        threshold: u128,
        entries: &[RawRewardSetEntry],
    ) -> Option<Vec<NakamotoSignerEntry>> {
        let Some(first_entry) = entries.first() else {
            // entries is empty: there's no signer set
            return None;
        };
        // signing keys must be all-or-nothing in the reward set
        let expects_signing_keys = first_entry.signer.is_some();
        for entry in entries.iter() {
            if entry.signer.is_some() != expects_signing_keys {
                panic!("FATAL: stacking-set contains mismatched entries with and without signing keys.");
            }
        }
        if !expects_signing_keys {
            return None;
        }

        let mut signer_set = BTreeMap::new();
        for entry in entries.iter() {
            let signing_key = entry
                .signer
                .expect("BUG: signing keys should all be set in reward-sets with any signing keys");
            if let Some(existing_entry) = signer_set.get_mut(&signing_key) {
                *existing_entry += entry.amount_stacked;
            } else {
                signer_set.insert(signing_key, entry.amount_stacked);
            };
        }

        let mut signer_set: Vec<_> = signer_set
            .into_iter()
            .filter_map(|(signing_key, stacked_amt)| {
                let weight = u32::try_from(stacked_amt / threshold)
                    .expect("CORRUPTION: Stacker claimed > u32::max() reward slots");
                if weight == 0 {
                    return None;
                }
                Some(NakamotoSignerEntry {
                    signing_key,
                    stacked_amt,
                    weight,
                })
            })
            .collect();

        // finally, we must sort the signer set: the signer participation bit vector depends
        //  on a consensus-critical ordering of the signer set.
        signer_set.sort_by_key(|entry| entry.signing_key);

        Some(signer_set)
