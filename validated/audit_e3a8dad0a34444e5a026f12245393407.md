### Title
Transaction-triggerable panic (chain halt) via `.unwrap()` on `receiver_shard_id()` in delayed-receipt processing after resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The CVE describes a NULL-pointer-dereference DoS in OpenJPEG where crafted input reaches a code path that dereferences an unchecked/unvalidated value, crashing the process. The closest reachable analog in nearcore is a `.unwrap()` on a `Result` that can legitimately be `Err` for a `GlobalContractDistribution` receipt whose `target_shard` no longer resolves under the current (or historical) shard layout, causing a validator/RPC node panic while draining the delayed receipt queue.

### Finding Description
`Receipt::receiver_shard_id` computes the destination shard for a receipt. For `GlobalContractDistribution` receipts, if the recorded `target_shard` is not part of the current shard layout, the code tries to remap it via `shard_layout.resolve_to_current_shard(target_shard)`, and explicitly returns an `Err(EpochError::ShardingError(...))` when no descendant shard can be found (i.e., the target shard is not resolvable in the split history): [1](#0-0) 

This is a real, non-hypothetical failure mode: the target shard of a `GlobalContractDistribution` receipt can become stale relative to the current layout after resharding events, and `resolve_to_current_shard` is documented as unable to always find a match.

The consuming site, `receipt_filter_fn` in the delayed-receipt-queue wrapper, discards this `Result` and calls `.unwrap()` directly: [2](#0-1) 

This function is invoked from `DelayedReceiptQueueWrapper::pop` and `peek_iter`, which are part of the normal chunk-apply loop that processes the delayed receipt backlog every chunk: [3](#0-2) 

A repository-local regression test explicitly documents and exercises this exact scenario, confirming the bug class is understood by the maintainers as a real (previously present) crash: [4](#0-3) [5](#0-4) 

`GlobalContractDistribution` receipts are generated by any account submitting a `DeployGlobalContract` transaction (an ordinary, unprivileged action available to any funded account) and are propagated to the shard(s) hosting existing accounts as background housekeeping receipts — they are not gated by any special privilege. Because these receipts are queued and delayed across chunk boundaries and shard splits, an attacker who controls the timing of deploys relative to resharding boundaries can produce a `GlobalContractDistribution` receipt whose `target_shard` becomes unresolvable by the time the delayed queue drains it, triggering the `.unwrap()` panic in `receipt_filter_fn`.

### Impact Explanation
A panic inside `receipt_filter_fn`, called from `DelayedReceiptQueueWrapper::pop`/`peek_iter` during ordinary chunk `apply`, crashes the runtime thread processing that chunk. Because every honest validator/RPC node applies the same chunk deterministically, this is not a localized failure — it is a chain-wide liveness halt: any node that reaches the affected chunk (validators producing/validating it, and any full/RPC node replaying history or tracking the shard) will panic identically. This matches the "transaction-triggered halt" acceptance criterion: a state-transition function panic reachable from ordinary user transactions (global contract deployment) that stalls chunk production for the affected shard.

### Likelihood Explanation
Likelihood is not trivial to reach on-demand (it requires the receipt to survive in the delayed queue across a shard-splitting resharding event with a target shard that is no longer resolvable), but it does not require any special privilege — only submitting a standard `DeployGlobalContract` transaction at the right time relative to a scheduled resharding. The existence of a dedicated regression test in the codebase (`global_contracts_distribution.rs`, explicitly commented "If the vulnerability exists... will panic") indicates the maintainers consider/considered this a credible, reachable defect rather than a purely theoretical one.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:876`) with proper error propagation (`?` through a `Result`-returning signature, or treat unresolved receipts as retained/re-queued rather than panicking), so a `GlobalContractDistribution` receipt with a stale, unresolvable `target_shard` degrades gracefully (e.g., logged and skipped/delayed further) instead of crashing chunk application. Audit all other call sites of `receiver_shard_id()` (e.g., in `runtime/runtime/src/congestion_control.rs`, `chain/chain/src/chain.rs`, `core/primitives/src/state_record.rs`) for the same unwrap pattern.

### Proof of Concept
Exact reproduction requires driving a live resharding schedule across two generations while a `GlobalContractDistribution` receipt for an account in the split shard is delayed in the queue — this is precisely what the existing test does: [4](#0-3) 
This test asserts that the chain does not stall past `drain_end`, which is the observable symptom of the underlying panic in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:876`) being hit when draining the delayed queue. I could not fully verify from the available index whether this specific path is currently patched (e.g., whether `resolve_to_current_shard` was hardened afterward) or still exploitable in this snapshot — this should be confirmed by running the cited test and by tracing `resolve_to_current_shard`'s behavior across multiple resharding generations, which I was unable to fully inspect due to iteration limits.

    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }
