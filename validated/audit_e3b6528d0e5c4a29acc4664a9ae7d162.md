### Title
Unbounded storage-dependent loop in `getAssetIssueList` / `getAssetIssueListByName` / `getAssetIssueByAccount` causes RPC/HTTP DoS via unprivileged asset issuance - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
Any unprivileged account can call `AssetIssueContract`/`AssetIssueActuator` to create a new asset (subject only to paying `AssetIssueFee` and holding enough balance), which permanently appends a new row to the `AssetIssueStore`/`AssetIssueV2Store`. Several unauthenticated, unbounded gRPC/HTTP API handlers in `Wallet.java` load and iterate the *entire* asset-issue store on every single request with no pagination and no cap, mirroring the analog bug class (`allPairs`-style unbounded array growth followed by a full-array loop with no way to bound execution).

### Finding Description
`AssetIssueActuator.execute()` lets any account holding sufficient balance create a new asset and register it permanently in `AssetIssueStore`/`AssetIssueV2Store`: [1](#0-0) 

`AssetIssueStore.getAllAssetIssues()` streams the *entire* store with no size bound: [2](#0-1) 

This unbounded getter is invoked directly by multiple public `Wallet` methods exposed as anonymous, unauthenticated RPC/HTTP endpoints:

- `Wallet.getAssetIssueList()` – iterates all assets and, for each one, runs `BandwidthProcessor.updateUsage()`: [3](#0-2) 

- `Wallet.getAssetIssueByAccount()` – loads the full list and filters in-memory: [4](#0-3) 

- `Wallet.getAssetIssueListByName()` – same pattern: [5](#0-4) 

These are wired to unauthenticated gRPC methods (`GetAssetIssueList`, `GetAssetIssueListByName`) and to an HTTP servlet with no offset/limit parameters: [6](#0-5) [7](#0-6) 

A bounded/paginated sibling API exists (`getAssetIssueList(offset, limit)` / `GetPaginatedAssetIssueList`, capped by `ASSET_ISSUE_COUNT_LIMIT_MAX`): [8](#0-7) 
but the unbounded, non-paginated variants remain reachable and are the ones with no mitigation, exactly analogous to the `setPeriodSize` loop in the external report: the array (`allPairs`/`AssetIssueStore`) can be grown without bound by any unprivileged actor, and a separate function that must loop the whole array has no way to chunk or bound its work.

### Impact Explanation
Because asset creation is unprivileged (any funded account can call `AssetIssueContract`), an attacker can repeatedly issue low-value assets to grow `AssetIssueStore` to an arbitrarily large size. Every subsequent call to `GetAssetIssueList`/`GetAssetIssueListByName`/`getAssetIssueByAccount` (unauthenticated, callable by anyone against any full node) then performs O(n) work — loading every `AssetIssueCapsule` from the DB, deserializing it, and running `BandwidthProcessor.updateUsage()` on each — with no pagination, no timeout, and no upper bound. As the store grows, each such RPC/HTTP call becomes increasingly expensive in CPU, I/O, and memory, degrading node responsiveness and potentially causing request timeouts, thread-pool/resource exhaustion, or full node service disruption for all API consumers (a node-level DoS of the JSON-RPC/gRPC/HTTP query surface), without requiring any privileged role.

### Likelihood Explanation
Likelihood is limited by the cost of asset issuance: each `AssetIssueContract` costs `AssetIssueFee` (a positive, configurable TRX amount) and consumes bandwidth/energy for the transaction itself, so unlike the completely free `createPair` call in the external report, this attack has an ongoing TRX cost per array element. However, the fee is a fixed, bounded cost (not scaling with existing store size), and the attack does not require governance/admin privileges, malicious peers, or leaked keys — only a funded account submitting ordinary broadcast transactions repeatedly over time. This makes the analog reachable purely from unprivileged transaction/RPC paths, though the economic cost reduces the immediate severity compared to the original completely-free `createPair` spam.

### Recommendation
- Deprecate/remove or gate the non-paginated `GetAssetIssueList`, `GetAssetIssueListByName`, and `getAssetIssueByAccount` APIs (or enforce a mandatory server-side page-size cap and reject/paginate when the store size exceeds it), mirroring the already-existing `getAssetIssueList(offset, limit)` bound (`ASSET_ISSUE_COUNT_LIMIT_MAX`).
- Apply the same offset/limit bound used by `getAssetIssuesPaginated` to all asset-issue listing/filtering entry points, including `getAssetIssueByAccount` and `getAssetIssueListByName`.
- Consider indexing asset issues by owner address (secondary index) rather than filtering the full store in memory, to avoid O(n) scans irrespective of pagination.
- Add rate limiting/backpressure on these RPC/HTTP endpoints proportional to store size, and monitor/alert on `AssetIssueStore` growth rate.

### Proof of Concept
1. Using N distinct funded accounts (or one account submitting sequential name-varied `AssetIssueContract` transactions, subject to `AllowSameTokenName`/uniqueness rules), broadcast enough `AssetIssueContract` transactions to grow `AssetIssueStore` to a very large size (e.g., hundreds of thousands of entries), each paying `AssetIssueFee`.
2. Call the unauthenticated `GetAssetIssueList` gRPC/HTTP endpoint (`Wallet.getAssetIssueList()`) against a full node.
3. Observe that response latency and node CPU/memory usage scale linearly with the total number of assets ever issued, with no pagination or cap, degrading availability of the node's query API for all users; verifiable directly from `AssetIssueStore.getAllAssetIssues()` having no limit and `Wallet.getAssetIssueList()` iterating the full result with per-item `BandwidthProcessor.updateUsage()` work.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
