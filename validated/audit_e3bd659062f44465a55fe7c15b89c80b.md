### Title
Witness/SR block and transaction-fee rewards accrued during cycles with zero recorded vote count are permanently unclaimable - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java], [File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java], [File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
java-tron's DPoS voting-reward mechanism uses the same "rate accrues regardless of participants" pattern that caused the BathBuddy finding: block/tx-fee rewards are unconditionally accrued into a per-cycle, per-witness reward pool, but the pool is only distributable to voters who have a recorded vote count for that exact cycle. If a witness's recorded vote count for a cycle is `0`/unset (e.g., a freshly-elected witness before votes have propagated to a new cycle boundary, or a cycle where all voters unvoted), the reward accrued in that cycle is silently skipped in both the legacy and the new "Vi" reward algorithm and can never be attributed to anyone — it is permanently stranded in `DelegationStore`.

### Finding Description
Rewards are pushed into the per-cycle reward accumulator unconditionally whenever a witness produces a block or earns transaction fees: [1](#0-0) 

`payReward` calls `delegationStore.addReward(cycle, witnessAddress, value)` with no check on whether any vote count is recorded for that witness in that cycle.

Distribution back to voters is proportional to `totalVote` recorded for that same cycle. In the legacy algorithm: [2](#0-1) 

`if (totalVote == DelegationStore.REMARK || totalVote == 0) { continue; }` skips the reward entirely for that cycle — the accrued value added via `addReward` is never redistributed to any voter, present or future.

The current "Vi" (reward-per-vote index) algorithm has the identical gap: [3](#0-2) 

When `voteCount == 0` for the cycle, the accumulator simply forwards the previous `Vi` without folding in the reward, so the reward is dropped from the distribution index and can never be claimed by any past or future voter. This routine is invoked once per cycle for every witness in `MaintenanceManager.doMaintenance()`: [4](#0-3) 

`DelegationStore.getWitnessVote` explicitly returns the sentinel `REMARK = -1` when no vote-count entry exists for a cycle: [5](#0-4) [6](#0-5) 

The per-cycle vote-count snapshot used for the *next* cycle's distribution is only written at the end of `doMaintenance()`: [7](#0-6) 

so any cycle in which a witness's recorded vote count is 0 (a witness just elected/receiving votes for the first time, or a cycle in which its voters withdraw votes) results in that cycle's accrued block reward and transaction-fee reward (paid unconditionally via `payBlockReward`/`payTransactionFeeReward`/`payStandbyWitness`) being permanently orphaned, exactly analogous to the BathBuddy "rewards for initial period lost" bug class: a reward rate/pool is established for a period, but if there is no "participant" (recorded voter stake) for that specific period, the funds become unclaimable forever.

### Impact Explanation
Rewards (TRX) that are correctly earned by block producers/witnesses through ordinary block production and transaction processing become permanently stuck in `DelegationStore` and are never credited to any account's `allowance`/balance. This is an accounting/asset-loss bug reachable purely through normal network operation (every block and every broadcast transaction that pays a fee triggers `payBlockReward`/`payTransactionFeeReward`), not requiring any privileged actor. The loss is bounded per affected cycle/witness but is systemic: any witness onboarding period, or any cycle where a witness's votes are entirely withdrawn and then later re-added, triggers the loss deterministically.

### Likelihood Explanation
High for at least one occurrence class: every newly elected Super Representative/witness that starts producing blocks before its first vote-count snapshot is recorded for the current cycle will lose that cycle's block/tx-fee reward. Vote-clearing scenarios (all voters withdrawing votes from a witness in a given cycle) are also realistic on a live network and trigger the same loss for the legacy and Vi reward paths.

### Recommendation
Do not use per-cycle recorded vote count as a gating condition for whether a reward is distributable. Instead, either (a) skip/defer adding a witness's reward for a cycle until it actually has nonzero recorded votes and carry the reward forward to the next cycle where votes exist (rather than discarding), or (b) initialize/seed the vote-count/Vi state at the moment a witness starts being eligible for rewards, so a reward-earning cycle never has an undefined/zero vote-count baseline. Add an accounting invariant check (sum of amounts credited to voters + still-pending == sum of `addReward` calls) to detect any future drift/loss in either the legacy or the Vi-based algorithm.

### Proof of Concept
Conceptual reproduction using existing test scaffolding (`framework/src/test/java/org/tron/core/services/DelegationServiceTest.java`, `framework/src/test/java/org/tron/common/runtime/vm/VoteTest.java`):
1. Create/elect a witness `W` such that it becomes an active SR in cycle `N`, but no account has cast a vote for `W` recorded for cycle `N` (i.e., `DelegationStore.getWitnessVote(N, W)` returns `REMARK`/`0`).
2. Have blocks produced by `W` in cycle `N`, causing `MortgageService.payBlockReward`/`payTransactionFeeReward` to call `delegationStore.addReward(N, W, value)`.
3. Advance past cycle `N` via `MaintenanceManager.doMaintenance()`.
4. Have a voter later vote for `W` and call `mortgageService.queryReward`/`withdrawReward` (or the TVM `WithdrawRewardProcessor`/`VoteRewardUtil.withdrawReward` path).
5. Observe that `computeReward`/`accumulateWitnessVi` never includes cycle `N`'s reward (the `totalVote == REMARK/0` branch is taken), so `delegationStore.getReward(N, W)` remains nonzero forever while no account's `allowance` ever reflects it — matching the expected/actual balance divergence shown in the original BathBuddy PoC.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
