## Title
Ignored `reduceAssetAmountV2`/`addAssetAmountV2` return value in Exchange actuators can desynchronize account asset balances from exchange pool accounting - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator.execute()`, `ExchangeWithdrawActuator.execute()`, and `ExchangeTransactionActuator.execute()` call `AccountCapsule.reduceAssetAmountV2(...)` / `addAssetAmountV2(...)` and discard the boolean success/failure return value, exactly mirroring the reported bug class (ignoring the boolean result of a balance-mutating call before committing dependent state). Other actuators in the same codebase (`TransferAssetActuator`, `ParticipateAssetIssueActuator`, `Commons.adjustAssetBalanceV2`) explicitly check this return value and throw `ContractExeException`/`BalanceInsufficientException` on failure, showing the intended pattern is to fail loudly. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
In `ExchangeInjectActuator.execute()`, the pool balance (`exchangeCapsule.setBalance(...)`) is updated to credit the injected token amount *before* the owner's account asset is actually reduced, and the reduction call's boolean result is never checked: [4](#0-3) 

The same pattern (ignored `reduceAssetAmountV2`/`addAssetAmountV2` return) occurs in `ExchangeWithdrawActuator.execute()` [5](#0-4)  and `ExchangeTransactionActuator.execute()` [6](#0-5) .

`AccountCapsule.reduceAssetAmountV2` returns `false` (doing nothing) instead of throwing when the requested amount exceeds the account's current balance for that token key: [7](#0-6) 

By contrast, `TransferAssetActuator`, `ParticipateAssetIssueActuator`, and the shared helper `Commons.adjustAssetBalanceV2` all explicitly check this boolean and abort the transaction on failure: [8](#0-7) 

Under the current `validate()` → `execute()` flow (both called back-to-back for the same transaction without other transactions being interleaved), `validate()` computes the same balances/keys via `assetBalanceEnoughV2` and should normally guarantee `reduceAssetAmountV2` succeeds at execute time. I could not find, within the tool budget available, a concrete state-mutation path (e.g., re-entrant call, differing token-name-resolution key between `assetBalanceEnoughV2` and `reduceAssetAmountV2`, or a mid-processing toggle of `AllowSameTokenName`) that would make `validate()`'s check diverge from `execute()`'s check within the same actuator invocation. Without such a divergence, the ignored return value is currently *dead code from a security standpoint* — the class of bug exists in the code (unlike the Amp.sol case, there is no direct external call whose result can be manipulated by a third party; the callee is `AccountCapsule`, an internal same-transaction database mutation).

### Impact Explanation
If validate/execute state ever diverges (e.g. future refactors that separate these calls, or an untested interaction where `getAllowSameTokenName()`/token id resolution paths between `assetBalanceEnoughV2` and `reduceAssetAmountV2` disagree), the exchange pool's `ExchangeCapsule` balance would be credited with tokens the injecting/trading account never actually surrendered, silently inflating the "backed" liquidity of the AMM-like Exchange pool. This is an accounting-corruption class bug (asset creation out of thin air within the Exchange subsystem) rather than an immediately provable, currently-exploitable vulnerability.

### Likelihood Explanation
Low under present code as written, because `doValidate()` in each of these three actuators independently recomputes the exact same balance-sufficiency check (`assetBalanceEnoughV2`) that `reduceAssetAmountV2` internally performs, and both run synchronously for the same transaction with no external call or reentrancy point in between. I was not able to fully verify, given the remaining tool budget, whether `assetBalanceEnoughV2`'s key-resolution logic (token name vs token ID, under `AllowSameTokenName` toggling) is byte-for-byte identical to `reduceAssetAmountV2`'s, which is the one place a divergence could hide.

### Recommendation
Regardless of current reachability, harden the code defensively to match the pattern already used elsewhere in the codebase (`TransferAssetActuator`, `ParticipateAssetIssueActuator`, `Commons.adjustAssetBalanceV2`): check the boolean return of `reduceAssetAmountV2`/`addAssetAmountV2` in `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator`, and throw `ContractExeException` on failure instead of silently continuing and committing the already-mutated `ExchangeCapsule` pool balance.

### Proof of Concept
Not established. I could not construct a concrete transaction sequence, using the tools available, that causes `reduceAssetAmountV2`/`addAssetAmountV2` to return `false` inside these actuators' `execute()` when their corresponding `doValidate()` succeeded for the same transaction — the two checks currently appear to be kept in lock-step by design. A full PoC would require tracing `assetBalanceEnoughV2` and `reduceAssetAmountV2`'s complete key-derivation logic across all `AllowSameTokenName`/`AllowAssetOptimization` combinations, which was not completed within this investigation.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
