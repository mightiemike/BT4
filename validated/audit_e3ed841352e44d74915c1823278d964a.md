Based on my investigation, the batch prover RPC server exposes `batchProver_setCommitments` — a state-mutating admin method — with no access control, on the same JSON-RPC surface that is bound to a configurable (often `0.0.0.0`) address per deployment configs.

### Title
Missing Access Restriction on `batchProver_setCommitments` allows unauthenticated overwrite of sequencer commitments - (File: `crates/batch-prover/src/rpc.rs`)

### Summary
The batch prover's `Auth` RPC middleware only requires an API key for three hardcoded methods (`backup_create`, `backup_validate`, `backup_info`); every other RPC method, including `batchProver_setCommitments`, is let through unauthenticated [1](#0-0) . `set_commitments` directly overwrites `SequencerCommitment` entries in the ledger DB used by the prover's proving pipeline, with an explicit warning in its own docstring that it "overrides the commitment already if exists, so use with caution" [2](#0-1) .

### Finding Description
The `Auth` middleware wraps every RPC server (sequencer, batch prover, light client prover) and is meant to gate sensitive operations behind an API key, but its allowlist covers only backup-related methods [3](#0-2) . The batch prover exposes `setCommitments`, which lets a caller supply arbitrary `SequencerCommitmentRpcParam` values and unconditionally persists them via `put_commitment_by_index`, `put_commitment_index_by_l1`, and `put_prover_pending_commitment`, overwriting any existing commitment at that index [4](#0-3) . This RPC method-to-Auth-modifier gap is exactly analogous to the reported pattern: a state-mutating entry point (`fullSync`/`setWstTBYBridge`) that should have been gated by a restrictive check (`onlyStTBY`/deployer-only) but was left reachable by any caller who can reach the interface.

`RpcConfig.api_key` is optional and, when unset (the default in most sample configs and tests), the `Auth` layer has no key to check against at all, and even when set it still only checks 3 methods [5](#0-4) . Several bundled/sample deployment configs bind the RPC server to `0.0.0.0` (e.g. `docker-compose.yml`, `resources/configs/devnet/rollup_config.toml`, `resources/configs/testnet/rollup_config.toml`), making the interface reachable beyond localhost.

Downstream, `SequencerCommitmentAccessor` entries fed by this same commitment set are consumed by the light-client-prover circuit to advance the proved L1↔L2 binding (`process_complete_proof` / `SequencerCommitment` handling) [6](#0-5) , and by `submit_fake_proof`, which builds a `BatchProofCircuitOutput` directly from whatever commitments are stored in the ledger DB without re-deriving them from an L1-verified source [7](#0-6) . If an attacker can inject or overwrite commitments via `setCommitments`, they can corrupt the prover's local view of which sequencer commitments exist for a given index/L1 height, and combine this with `submitFakeProof`/`prove` (also unauthenticated per the same middleware gap) to have the prover build proof inputs and even attempt to submit forged batch-proof outputs referencing attacker-supplied commitment data instead of the ones actually observed on Bitcoin DA.

### Impact Explanation
This falls under the High-impact category "an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`." A caller with no privileges other than network access to the batch prover's RPC port can overwrite the prover's local commitment-index database, corrupting the correspondence between what the batch prover believes it has committed/proved and what is actually anchored on Bitcoin DA — the equality that should hold between "sequencer commitments recorded by the node" and "sequencer commitments actually posted to and verified from the DA blob set." In the worst case this can be chained with `prove`/`submitFakeProof` (equally unauthenticated) to attempt submission of proofs built over attacker-controlled/incorrect commitment data.

### Likelihood Explanation
Likelihood depends on whether the batch prover's RPC endpoint is exposed beyond a trusted network boundary. Several shipped configuration examples in this repository bind to `0.0.0.0` and the `Auth` middleware's allowlist design shows the intent was for API-key gating to cover privileged mutating methods, but the implementation only protects the 3 `backup_*` methods, leaving `setCommitments`, `prove`, `submitFakeProof`, and `pauseProving` unauthenticated by design/oversight. This is a code-level gap independent of any specific deployment's firewall choices, matching the report's pattern of a function that was clearly intended to be restricted but isn't.

### Recommendation
Extend the `Auth` middleware's `PROTECTED_METHODS` list (or add a per-route allowlist/authorization check) to cover all state-mutating batch-prover admin RPCs — at minimum `setCommitments`, `prove`, `submitFakeProof`, and `pauseProving` — requiring the configured `api_key` (or another privileged credential) before they can be invoked, consistent with how `backup_create`/`backup_validate`/`backup_info` are already protected.

### Proof of Concept
1. Start a batch prover node with default/sample config (no `api_key` set, or `api_key` set but irrelevant since `setCommitments` isn't in `PROTECTED_METHODS`) with its RPC bound to a reachable address.
2. From any unauthenticated client, call:
```json
{"jsonrpc":"2.0","id":1,"method":"batchProver_setCommitments","params":[[{"merkleRoot":"0x...attacker chosen...","index":"0x5","l2EndBlockNumber":"0x64","l1Height":"0x10"}]]}
```
3. Observe via `get_commitment_indices_by_l1`/ledger DB inspection that the attacker-supplied commitment silently overwrote the legitimate commitment at that index [4](#0-3) , with no API key or role check required [8](#0-7) .

    async fn set_commitments(
        &self,
        commitments: Vec<SequencerCommitmentRpcParam>,
    ) -> RpcResult<()> {
        for commitment in commitments {
            let l1_height = commitment.l1_height.to::<u64>();
            let commitment = SequencerCommitment {
                merkle_root: commitment.merkle_root,
                index: commitment.index.to::<u32>(),
                l2_end_block_number: commitment.l2_end_block_number.to::<u64>(),
            };

            info!(
                "Overriding sequencer commitment, index={} merkle_root={} l2_end_height={} l1_height={}",
                commitment.index,
                hex::encode(commitment.merkle_root),
                commitment.l2_end_block_number,
                l1_height,
            );

            self.context
                .ledger_db
                .put_commitment_by_index(&commitment)
                .map_err(internal_rpc_error)?;
            // This might cause some duplicate commitment indices appear in l1 -> index table which is ok
            self.context
                .ledger_db
                .put_commitment_index_by_l1(SlotNumber(l1_height), commitment.index)
                .map_err(internal_rpc_error)?;
            self.context
                .ledger_db
                .put_prover_pending_commitment(commitment.index)
                .map_err(internal_rpc_error)?;
        }

        Ok(())
    }
