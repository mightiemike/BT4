### Title
Stale `borrow-index` used to compute and record debt principal in `repay` before removal - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`repay` binds `borrow-index` from the market's per-block index cache once, then uses that single snapshot to (1) size the maximum repayable amount, (2) compute the scaled debt actually removed from the user's position, and (3) transfer/repay funds to the vault — all without re-reading the index after the vault-mutating call that can itself change accrual state within the same call.

### Finding Description
`repay` retrieves the cached liquidity/borrow index via `get-cached-indexes` at the very top of the `let`, before `vault-system-repay` executes: [1](#0-0) 

This `borrow-index` is the same value used to compute `max-repay-tokens`, `scaled-debt-repayment`, `repaid-scaled-debt`, and `amount-to-repay`, and it is only after all of these derivations that the vault call `vault-system-repay` is invoked with the pre-computed `amount-to-repay`: [2](#0-1) 

The cache itself is populated via `accrue-and-cache`, a fold/match pattern keyed by `{ timestamp: stacks-block-time, aid }`: [3](#0-2) 

Because the cache key is `stacks-block-time`, not a per-call nonce, any prior operation in the *same transaction* (e.g. a preceding `borrow`/`liquidate` on a different account routed through the same market call, or a multi-step batched call from a contract-caller) that already wrote a cache entry for this `aid` will be reused verbatim by `repay`'s `get-cached-indexes asset-id` lookup — this is the "cached value not invalidated when its source moves" pattern applied to accrual index rather than a domain-separator version string. If `repay` is composed with any earlier call in the same transaction that itself calls `vault-system-borrow`/`vault-system-repay` for the same `aid` (both of which internally call the vault's own `accrue`), the vault's on-chain `index`/`lindex` can move forward (due to `total-borrowed` changes feeding `next-index`) after the market's cache entry for that timestamp was already written and is never refreshed for the remainder of the transaction, per `accrue-and-cache`'s cache-HIT branch which unconditionally returns the stale tuple: [4](#0-3) 

### Impact Explanation
`amount-to-repay` and `repaid-scaled-debt` are derived from `borrow-index`, which can diverge from the vault's authoritative on-chain `index` once a same-block/same-transaction accrual event has moved the vault's actual debt index past the cached snapshot. Using a stale (lower) index to size `amount-to-repay` under-reports the debt owed relative to the real vault index, letting a user's scaled debt be cleared (`repaying-all`) for less underlying than the vault's live accounting would require, producing a shortfall the vault absorbs — a temporary/permanent freezing or shortfall of protocol-held funds (insolvency risk) rather than a simple two-user race.

### Likelihood Explanation
This requires only a single transaction that triggers an intervening accrual-changing call (e.g. another `borrow`/`liquidate` touching the same `aid`) prior to a `repay` on that asset within the same contract execution — reachable by any contract-mediated batch caller of the market, consistent with Clarity's sequential same-transaction evaluation order, no privileged access or multi-block timing needed.

### Recommendation
Re-fetch (or invalidate and force re-accrual of) the vault index immediately before computing `amount-to-repay` in `repay`, or make `accrue-and-cache` accrual-aware per call rather than purely timestamp-keyed, ensuring `borrow-index` used for debt sizing always reflects the state right before the vault-mutating call it feeds.

### Proof of Concept
1. Attacker-controlled contract, within a single transaction, calls the market's `borrow` (or `liquidate`) for asset `aid`, which calls `accrue-and-cache aid`, populating `index-cache` for `{timestamp: stacks-block-time, aid}` with the vault's current index and also causing the vault's own internal `accrue()` (invoked again in `vault-system-borrow`) to advance `index`/`lindex` further based on updated `total-borrowed`/utilization.
2. In the same transaction, the same contract then calls `repay` for the same `aid`; `get-cached-indexes asset-id` hits the cache from step 1 and returns the now-stale `borrow-index` (unmoved since caching), while the vault's live `index` has since advanced.
3. `repay` computes `max-repay-tokens`, `scaled-debt-repayment`, and `amount-to-repay` using the stale, lower `borrow-index`, understating the actual debt in tokens.
4. `vault-system-repay` is called with this understated `amount-to-repay`; `debt-remove-scaled` clears `repaid-scaled-debt` (potentially all of the account's scaled debt) for less underlying value than the vault's authoritative index implies, leaving a shortfall absorbed by the vault's remaining liquidity providers.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
