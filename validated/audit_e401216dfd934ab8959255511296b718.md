**Analysis:**

`PartialVMError::new` unconditionally sets `sub_status: None` regardless of `major_status`, and the `debug_assert!(major_status != StatusCode::EXECUTED)` only guards against calling `new()` with `EXECUTED` at all — it isn't what would let a nonzero `sub_status` reach `into_vm_status`. [1](#0-0) 

The only way to get a `PartialVMError`/`VMError` with `major_status == StatusCode::EXECUTED` and `sub_status == Some(_)` would be to explicitly call `.with_sub_status(x)` after constructing it with `StatusCode::EXECUTED` — a combination that no code in the repository actually performs. [2](#0-1) 

Searching the codebase for `StatusCode::EXECUTED` usage shows it only appears in `errors.rs` (the definition site and the `debug_assert!` guard itself), in the `vm_status.rs` enum/status-type definitions, and in the unrelated `move-unit-test` test runner tool — none of which construct an error with `EXECUTED` plus an attached `sub_status`. There is no unprivileged-transaction-reachable call site in the VM, executor, or verifier code that builds such a malformed error object.

Since no such "non-standard error-construction call site" exists anywhere in production code, the described divergence path is purely hypothetical: it would require a future/hidden bug at an unspecified call site that doesn't currently exist, rather than a demonstrable path from unprivileged transaction/package/API/proof input through existing code. The `debug_assert!` is a development-time invariant check that guards against internal programming mistakes, not attacker-controlled state, so per the Decision Standard ("reject anything that depends on trusted operator/developer mistakes alone") this does not qualify as a state-integrity vulnerability reachable by unprivileged input.
