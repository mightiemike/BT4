### Title
Default `constantCallTimeoutMs=0` lets unauthenticated `triggersmartcontract`/constant calls occupy RPC worker threads for the full per-transaction CPU budget, enabling thread-pool exhaustion - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
`VMActuator.calculateCpuLimitInUs` gives constant/view TVM calls (reached via `TriggerSmartContractServlet.doPost` → `Wallet.triggerContract` → `VMActuator.call`/`create`) the same CPU deadline as an ordinary block transaction whenever the operator leaves `CommonParameter.constantCallTimeoutMs` at its default of `0`. Because `Program.checkCPUTimeLimit` only enforces this deadline once per opcode rather than preempting execution, an attacker can craft a low-energy, CPU-dense loop that runs an HTTP request thread close to the full `maxCpuTimeOfOneTx` budget on every call, and repeat this via unauthenticated flooding of the endpoint.

### Finding Description
`VMActuator.calculateCpuLimitInUs` computes the CPU deadline for both constant and non-constant calls: [1](#0-0) 

When `constantCallTimeoutMs` is `0` (the default, per `CommonParameter.java`), a constant call falls back to `maxCpuTimeOfOneTxMs * cpuLimitInUsRatio`, exactly the same formula used for normal, non-constant transaction execution: [2](#0-1) 

This is confirmed by the shipped unit test showing that with `constantCallTimeoutMs=0`, a constant call gets the full network deadline (`400_000` = `80ms * 1000 * 5.0`) instead of a small dedicated bound: [3](#0-2) 

Inside `VM.play`, the CPU-time check is only invoked after each opcode executes (`program.checkCPUTimeLimit(opName)`), so it cannot preempt mid-opcode or bound the number of opcodes executed except by walking the deadline one instruction at a time: [4](#0-3) 

`Program.checkCPUTimeLimit` itself only throws once `System.nanoTime()/1000` exceeds `vmShouldEndInUs`: [5](#0-4) 

For loops built from cheap-but-nonzero-cost opcodes (e.g. `JUMPDEST`/`JUMP`/`PUSH` sequences), energy accounting via `spendEnergy`/`spendEnergyWithPenalty` still limits total iterations to whatever `maxEnergyLimit`/`maxEnergyLimitForConstant` allows, but a contract can be engineered so that the energy-per-iteration is small relative to wall-clock cost per iteration (e.g. heavy `SLOAD`/`SHA3`/memory-touching ops with amortized low energy relative to actual CPU work, or simply many cheap iterations), letting execution run close to the full CPU deadline before hitting the energy ceiling or CPU deadline, whichever comes first.

Note: contrary to the question's premise, `getCpuLimitInUsRatio()` only multiplies by `maxTimeRatio` when `ExecutorType.ET_NORMAL_TYPE` and the block is being verified (not self-generated) — i.e., during block replay/verification, not for direct RPC-triggered constant calls: [6](#0-5) 
For the RPC/API path the ratio is `1.0`, so the effective per-call ceiling is `maxCpuTimeOfOneTx` (a chain parameter, typically tens of ms), not `maxCpuTimeOfOneTx * maxTimeRatio`. The exploitable gap is therefore narrower than described in the question, but still real: absent a dedicated `constantCallTimeoutMs`, every constant call is allowed to run up to the full single-transaction CPU budget instead of a small RPC-specific bound.

`TriggerSmartContractServlet.doPost` is reachable by any unauthenticated caller and synchronously calls into `Wallet.triggerContract`, which drives TVM execution on the servlet's own worker thread: [7](#0-6) 

### Impact Explanation
Concrete scoped impact: **DoS via RPC-API**. An attacker who deploys an adversarial contract and then floods `/wallet/triggersmartcontract` calls against it can cause each HTTP request to occupy a servlet worker thread for close to `maxCpuTimeOfOneTx` (bounded, not "infinite"), rather than a much smaller dedicated constant-call budget. With enough concurrent requests this can starve the HTTP thread pool (`maxHttpConnectNumber`) on a node, degrading availability of the RPC service for legitimate clients. This does not affect consensus, funds, or keys — it is confined to RPC worker-thread exhaustion on the queried node.

### Likelihood Explanation
- No privileged role or non-default configuration is required to trigger the underlying behavior; `constantCallTimeoutMs=0` is the shipped default.
- Attacker only needs to deploy a contract (paying normal deployment fee/energy) and then issue repeated `triggersmartcontract` calls; constant calls do not require broadcasting a signed transaction with real fee payment in the same way full execution does, lowering per-call cost.
- `TriggerSmartContractServlet` extends `RateLimiterServlet`, which is an existing mitigating control whose exact throttling parameters were not retrieved; depending on configured limits, a single attacker IP may already be throttled, requiring distributed sources to sustain enough concurrency for full thread-pool exhaustion.
- The severity is inherently bounded per call by `maxCpuTimeOfOneTx` (tens of ms), so this is a throughput/availability degradation issue rather than an unbounded hang, and node operators already have `constantCallTimeoutMs` available to close the gap.

### Recommendation
Set a conservative non-zero default for `constantCallTimeoutMs` (e.g., a few ms) so constant/view calls served over RPC use a dedicated, tight CPU deadline independent of `maxCpuTimeOfOneTx`, and document this as the recommended production configuration. Additionally, consider making `checkCPUTimeLimit` cheaper/more frequent for high-iteration-low-energy opcode patterns, and ensure `RateLimiterServlet` limits account for expensive TVM calls (e.g., per-endpoint concurrency caps) rather than only request-count throttling.

  private double getCpuLimitInUsRatio() {

    double cpuLimitRatio;

    if (ExecutorType.ET_NORMAL_TYPE == executorType) {
      // self witness generates block
      if (blockCap != null && blockCap.generatedByMyself
          && !blockCap.hasWitnessSignature()) {
        cpuLimitRatio = 1.0;
      } else {
        // self witness or other witness or fullnode verifies block
        if (trx.getRet(0).getContractRet() == contractResult.OUT_OF_TIME) {
          cpuLimitRatio = CommonParameter.getInstance().getMinTimeRatio();
        } else {
          cpuLimitRatio = CommonParameter.getInstance().getMaxTimeRatio();
        }
      }
    } else {
      // self witness or other witness or fullnode receives tx
      cpuLimitRatio = 1.0;
    }

    return cpuLimitRatio;
  }

  static long calculateCpuLimitInUs(boolean isConstantCall, long maxCpuTimeOfOneTxMs,
      double cpuLimitInUsRatio, long constantCallTimeoutMs) {
    if (isConstantCall && constantCallTimeoutMs > 0L) {
      return constantCallTimeoutMs * VMConstant.ONE_THOUSAND;
    }
    return (long) (maxCpuTimeOfOneTxMs * VMConstant.ONE_THOUSAND * cpuLimitInUsRatio);
  }
