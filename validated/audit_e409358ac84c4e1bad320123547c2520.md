## Analysis

The Auction.sol bug is about a state-changing parameter update landing mid-flight on a request that was already "locked in" under old parameters, so some participants get treated more favorably than others depending purely on timing around the parameter change.

The closest reachable analog in `patrichyt/nearcore--002` is the **`AccountCostIncrease` protocol-upgrade boundary in `refund_unspent_gas_and_deposits`**, which is exercised by any ordinary `CreateAccount` transaction — no privileged actor needed.

### Root cause

`account_creation_charge` is a new fee introduced by the `AccountCostIncrease` protocol feature [1](#0-0) . It is levied by *subtracting it from the receipt's own gas-price "surplus" refund* (`burned_gas_refund`), never from the account's principal balance:

```
let amount_actually_charged = std::cmp::min(amount_to_charge, burned_gas_refund);
```

`burned_gas_refund` is `gas_refund_result.price_surplus`, which is only non-zero when `gas_purchase_price > gas_burn_price` for *this receipt* [2](#0-1) . A receipt whose gas was purchased **before** the epoch that activates `AccountCostIncrease` crosses into execution **after** activation with `gas_purchase_price == gas_burn_price` (no feature-driven price delta existed at purchase time), so `price_surplus == 0`, hence `burned_gas_refund == 0`, hence `amount_actually_charged = min(desired_cost, 0) = 0`. The account is created but the fee is silently skipped.

This exact mechanism is documented and asserted by the repo's own test, `test_create_account_cost_protocol_upgrade`: [3](#0-2) 

The test explicitly buckets outcomes into "before" (cheap), "crossing" (still cheap — fee bypassed), and "after" (full charge) [4](#0-3) , confirming the boundary-straddling transaction pays strictly less than every fully-post-upgrade transaction for the identical `CreateAccount` action.

### Why this matches the report's bug class

- The Auction report's bug is "parameter updated mid-flight ⇒ unfair advantage between users depending on timing." Here the analogous "parameter" is `account_creation_charge`, gated by the `AccountCostIncrease` feature that activates at a specific protocol version [5](#0-4) [6](#0-5) .
- Reachability: any unprivileged account can submit an ordinary `CreateAccount` transaction near a known, public upgrade-schedule boundary (schedules are public, e.g. mainnet's fixed `2026-07-20` PV-86 vote date) [7](#0-6) , and time it (or simply resubmit repeatedly during the boundary window) so that gas is purchased pre-upgrade and the receipt executes post-upgrade.
- Impact: this is a concrete **fee bypass** — a class explicitly listed as acceptable impact ("fee or gas bypass") — giving an unfair token-cost advantage to whoever's account-creation receipt happens to straddle the upgrade, versus every other user who creates an account fully after the upgrade and pays the full `account_creation_charge`.

### Severity caveat

This is deterministic and identical on every honest node (no state-root divergence, no double-spend, no fund freezing) — it is a fairness/fee-bypass defect bounded to the single-epoch upgrade transition window, and the code even contains defensive comments/`debug_assert!`s acknowledging the reduced-refund scenario for cross-boundary receipts [8](#0-7) , suggesting this was a known, accepted trade-off rather than an unnoticed defect.

### Title
Account-creation fee (`account_creation_charge`) can be bypassed for `CreateAccount` transactions straddling the `AccountCostIncrease` protocol upgrade boundary - (File: `runtime/runtime/src/lib.rs`)

### Summary
`refund_unspent_gas_and_deposits` funds the new `account_creation_charge` fee exclusively out of a receipt's own gas-price surplus refund. A `CreateAccount` transaction whose gas is purchased in the epoch *before* `AccountCostIncrease` activates and whose receipt executes in the epoch *after* activation has zero price surplus, so the fee collapses to zero even though the feature is active at execution time.

### Finding Description
`create_account_charge` is computed as `min(desired_cost, burned_gas_refund)` where `burned_gas_refund` equals `price_surplus = gas_purchase_price - gas_burn_price` for that specific receipt [9](#0-8) . For a receipt purchased pre-upgrade, `gas_purchase_price` was set without any `AccountCostIncrease`-driven adjustment, so it equals `gas_burn_price`, making `price_surplus = 0` and thus `amount_actually_charged = 0`. The account is nonetheless created successfully. This is confirmed by the project's own test assertions distinguishing "before", "crossing", and "after" upgrade cases, where both "before" and "crossing" pay less than `account_creation_charge` while "after" pays more [4](#0-3) .

### Impact Explanation
Users who time (or simply happen to send) their `CreateAccount` transaction so its receipt straddles the publicly-known protocol upgrade boundary avoid a fee that every other post-upgrade user must pay, creating an unfair, timing-dependent cost advantage — a fee-bypass condition.

### Likelihood Explanation
Upgrade schedules and voting thresholds are public and epoch-boundary timing is observable in advance [7](#0-6) , so any account holder can attempt to land a `CreateAccount` transaction's receipt exactly across the boundary; this requires no special privilege beyond normal transaction submission.

### Recommendation
Base `create_account_charge` eligibility/amount on the protocol version active when the receipt is *created* (or on a fixed floor independent of price-surplus availability) rather than deriving it opportunistically from the receipt's own price-surplus refund, so the fee cannot be reduced to zero purely due to upgrade-boundary timing.

### Proof of Concept
Reproduced directly by the existing test `test_create_account_cost_protocol_upgrade`: it submits `CreateAccount` transactions every block across an `AccountCostIncrease` upgrade and asserts `cost < account_creation_charge` for both "before" and "crossing" buckets, and `cost > account_creation_charge` only for the "after" bucket [10](#0-9) .

**`AccountCostIncrease` (v85)** changes the gas-price model: `gas_burn_price = min(gas_purchase_price, apply_state.gas_price)` instead of the current price (`runtime/runtime/src/lib.rs:920`-`927`). Post-feature, the price surplus (purchase > burn) is refunded as `burned_gas_refund`, and creating an account triggers `create_account_charge` — an extra charge up to `account_creation_charge` taken out of the burned-gas refund (`runtime/runtime/src/lib.rs:1234`-`1280`). Pre-feature, the surplus was instead folded into `tx_burnt_amount` (`runtime/runtime/src/lib.rs:978`).
