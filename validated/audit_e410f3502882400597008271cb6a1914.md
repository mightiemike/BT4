### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting corrupted state roots pass replay/consistency checks - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by replay-verification tooling such as `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`) is the function that is supposed to confirm a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain/in the archive. It checks status, gas, write-set hash and event-root hash, but by its own documented admission it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed values.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  validates only:
- `status` vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `write_set_hash` (recomputed `CryptoHash::hash(self.write_set())`) vs. `txn_info.state_change_hash()`
- `event_root_hash` (recomputed) vs. `txn_info.event_root_hash()`

The function then has an explicit `TODO` comment stating the checkpoint hashes are intentionally skipped: [2](#0-1) 

`TransactionInfo` (both V0 and V1 variants) carries `state_checkpoint_hash`, and V1 additionally carries `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` — all of which are Merkle-root-binding fields meant to authenticate the post-transaction state (including the "trading-native" position/state roots), as defined in [3](#0-2)  and produced during commit in `assemble_transaction_infos` [4](#0-3) . Because `ensure_match_transaction_info` never recomputes and compares these checkpoint roots, any divergence between the locally-computed state/hot-state/position-state root and the value stored in the authenticated `TransactionInfo` will not be detected by this check.

### Impact Explanation
This function is the integrity gate used by replay/verification tooling (`replay_on_archive`, `aptos-debugger`, `aptos-move/cli`) to detect whether locally re-executed transactions reproduce the exact committed ledger state. Skipping the checkpoint-hash comparison means these tools can report a "successful" replay/verification even when the state-checkpoint root (and, once `compute_trading_native_state_roots`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, the position/hot-state root) computed locally diverges from what was actually committed and authenticated on-chain. This directly matches the required "State-Commitment Gate" impact category: a wrong accumulator/checkpoint root could be silently accepted as consistent, masking state divergence during replay/consistency-checking of committed, authenticated ledger data.

However, this check is *not* part of the consensus/commit-time write path (`do_ledger_update.rs`/`aptosdb` writer paths compute and persist `state_checkpoint_hash` faithfully into the accumulator and are unaffected). The vulnerability is confined to a downstream, already-authenticated consistency check used by auditing/verification tooling — meaning it cannot itself corrupt the canonical ledger state or forge a proof, but it can hide a real divergence from operators using this tool as their "did replay reproduce the state?" gate. Given the explicit "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" caveat in the code comment, the maintainers are already aware this gap exists and consider it unsafe to enable that feature without fixing it first — reinforcing this is a genuine, acknowledged integrity gap rather than a stylistic nit.

### Likelihood Explanation
This is not remotely triggerable by an unprivileged attacker to alter consensus-committed state; it requires that a divergence between local execution and the authenticated `TransactionInfo` already exists (e.g. due to a state-computation bug, non-determinism, or corrupted archive data) for the gap to matter. It is a "silent failure to detect" rather than a exploitable forgery, so likelihood of triggering a security-relevant impact depends entirely on some other bug or corruption existing upstream, which this check would then fail to catch.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, and where applicable `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against the values in `txn_info`, especially before `compute_trading_native_state_roots`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled in production, as the existing comment already flags.

### Proof of Concept
Not applicable as a remote exploit — this is a missing-check/logic-gap finding. Demonstration path: construct a `TransactionOutput` whose write set and events hash-match `txn_info`, but whose resulting state Merkle root differs from `txn_info.state_checkpoint_hash()` (e.g. simulate a state-computation regression). Calling `ensure_match_transaction_info` on this pair returns `Ok(())` despite the checkpoint-root mismatch, as shown by the code path at [5](#0-4) , which never reads `state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` for comparison.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
