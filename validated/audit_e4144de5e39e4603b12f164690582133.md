Based on my investigation, I found a locally provable, code-acknowledged integrity gap in the transaction-info matching logic used across replay/verification paths.

### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay-verify to accept an authenticated position/state root that diverges from local execution - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used to validate that freshly executed `TransactionOutput`s match the authenticated `TransactionInfo` (i.e., the ledger-committed hashes) during chunk replay/verification (`execution/executor/src/chunk_executor/mod.rs`) and archive replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/cli/src/commands.rs`). It validates status, gas used, write-set hash, and event root hash, but explicitly and admittedly does **not** validate the state checkpoint hash, hot-state checkpoint hash, or `position_state_checkpoint_hash` fields carried in `TransactionInfo`.

### Finding Description [1](#0-0) 

The function checks four things: transaction status, gas used, write-set hash (`state_change_hash`), and event root hash. It then returns `Ok(())` without checking any checkpoint hash field, with an explicit TODO comment: [2](#0-1) 

This comparator is the sole "does execution match the authenticated ledger" gate used by:
- `ChunkExecutorInner::verify_execution`, which is the chunk-executor's execution-verification path during state sync / chunk replay [3](#0-2) 
- `storage/db-tool/src/replay_on_archive.rs`, the tool operators use to replay-verify an entire archived chain against locally re-executed VM output.

`TransactionInfo` carries a `state_checkpoint_hash()` and (per the TODO) a `position_state_checkpoint_hash`, which are supposed to bind the transaction to the resulting Merkle state root at that version — these are exactly the state-commitment fields covered by the Proof And Storage Pivots (accumulators/JMT roots must "preserve deterministic proof binding"). Because `ensure_match_transaction_info` never compares these fields against the locally computed checkpoint hash, a divergence between the locally re-executed state root and the authenticated on-chain state root at that version is silently accepted as "verified."

### Impact Explanation
If the VM/state-merkle computation for a given version diverges from the historically committed chain (e.g., due to a state-computation bug, a hard-fork-style behavior change, or corrupted/incorrect replay logic), `verify_execution` and `replay_on_archive` will still report success because they only check write-set hash and event root hash — not the resulting state root. This means:
- A silent state-root divergence during chunk-based state sync execution verification can go undetected, since the write set can still hash-match the recorded state-change hash while the actual merklized state (checkpoint hash) differs from the authenticated ledger — this is the exact "committed state that differs from correct VM result" and "Hard-fork-only divergence during commit/replay/verification" category called out in the task's required impacts.
- Operators relying on `replay_on_archive` to detect execution-divergence bugs get a false negative: the tool can report a clean replay while the authenticated position/state root has actually diverged, as literally documented in the code's own TODO.

This is high-impact because it defeats the primary safety mechanism (replay verification / chunk execution verification) meant to catch and prevent state divergence between the recorded ledger and locally computed state, undermining confidence in state root integrity checks across the codebase.

### Likelihood Explanation
Likelihood of exploitation via a malicious actor is low (this isn't attacker-triggerable network input; it's a self-detection tool gap), but likelihood of *masking a real divergence bug* is high given it is gated behind a not-yet-enabled feature flag (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`), meaning the checkpoint-hash fields exist in `TransactionInfo` but simply aren't checked anywhere in this comparator today. Any future or existing state-computation bug that changes checkpoint hashes without changing the write-set/event hashes (unlikely but not proven impossible given write-set hash and state root are logically distinct commitments) — or any bug specifically in the state-checkpoint/Merkle-tree computation path itself — would go undetected by this verifier today.

### Recommendation
Add checkpoint-hash comparisons (`state_checkpoint_hash`, hot-state checkpoint hash, and `position_state_checkpoint_hash` when present) to `ensure_match_transaction_info`, comparing the locally computed values (from `do_state_checkpoint.rs` / `state_checkpoint_output.rs`) against `txn_info`'s fields, before removing/deprioritizing this as a TODO. At minimum, `replay_on_archive` and `ChunkExecutorInner::verify_execution` should not report "verified"/success while checkpoint hashes remain unchecked, or should surface a clear warning that the state root itself was not verified.

### Proof of Concept
No exploit PoC applies here (this is an incompleteness in a defensive verification function). Local proof of the gap:
1. `TransactionInfo` includes checkpoint-hash fields (`state_checkpoint_hash`, etc.) used elsewhere in restore-flow validation, e.g. `storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs` (`ensure_state_checkpoint_hash()`), confirming these are meaningful state-commitment fields [4](#0-3) .
2. `ensure_match_transaction_info` only checks status/gas/write-set-hash/event-root-hash and explicitly skips checkpoint hashes, per its own TODO comment [5](#0-4) .
3. This function is the terminal check in `ChunkExecutorInner::verify_execution`, meaning a version passes execution verification without its resulting state root ever being validated against the authenticated ledger [6](#0-5) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
