### Title
`ensure_match_transaction_info()` skips checkpoint-hash validation, letting replay/restore tooling accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the integrity check that binds an executed `TransactionOutput` to the archived/authenticated `TransactionInfo` for a version. It validates status, gas, write-set hash, and event-root hash, but never validates `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This function is the sole verification gate used by `storage/db-tool/src/replay_on_archive.rs`, so replay-verification of archived history can report success even when the locally re-executed state-checkpoint root diverges from the version's authenticated `TransactionInfo`.

### Finding Description
`ensure_match_transaction_info()` explicitly documents the gap it leaves open: [1](#0-0) [2](#0-1) 

It checks `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash` against the `TransactionInfo`, but the comparator never reads `txn_info.state_checkpoint_hash()`, the hot-state checkpoint hash, or `position_state_checkpoint_hash()` — fields that exist on `TransactionInfoV1` alongside `state_change_hash`/`event_root_hash`: [3](#0-2) 

`db-tool`'s `replay_on_archive` uses this exact function as its only pass/fail criterion when replaying archived transactions through the VM and comparing outputs to the trusted, backed-up `TransactionInfo`: [4](#0-3) 

Because `ensure_match_transaction_info` never checks the checkpoint hashes, a divergence in the re-executed state/hot-state/position checkpoint root (the values that ultimately roll up into the accumulator/`TransactionInfo` hash and, transitively, the ledger's committed root) is invisible to this replay-verify path. The comment itself flags that this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" — confirming the authors are aware this comparator is currently unsound for that purpose: [5](#0-4) 

### Impact Explanation
Replay-verify is one of the primary mechanisms operators and the Aptos Labs team use to independently confirm that a candidate execution engine (or a new node/DB implementation) reproduces the exact, authenticated ledger state for historical mainnet data. Because the checkpoint-hash fields are silently excluded from the comparison, a bug in state-checkpoint or position-state computation that causes the re-executed root to diverge from the real historical root would not be caught by `replay_on_archive`, i.e., a corrupted/incorrect state commitment could pass verification as "correct." This is a proof-integrity gap in the exact tool meant to catch that class of divergence, though its blast radius is currently limited because `position_state_checkpoint_hash`/hot-state checkpoint verification is tied to features (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that are not yet in general use, and this is a verification-tooling gap rather than a consensus-path acceptance of an invalid `LedgerInfo`.

### Likelihood Explanation
The gap is deterministic and always present whenever `replay_on_archive` (or any other caller of `ensure_match_transaction_info`, e.g. `aptos-debugger`/CLI commands) is used to validate a version whose `TransactionInfoV1` carries a non-trivial `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`. It requires no attacker action — only an underlying computation bug in state-checkpoint/position-state derivation to remain undetected by this checker.

### Recommendation
Extend `ensure_match_transaction_info()` to also assert equality between the locally computed state checkpoint hash / hot-state checkpoint hash / position-state checkpoint hash (when available) and the corresponding fields on `txn_info` (`TransactionInfoV1`), consistent with how `write_set_hash` and `event_root_hash` are already checked, before any feature (such as `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that relies on these roots is enabled.

### Proof of Concept
1. Produce (or simulate) a version whose real execution changes the state-checkpoint root (e.g., due to a bug in hot-state or position-state tree computation) while write-set hash, event-root hash, gas, and status remain identical to the archived `TransactionInfo`.
2. Run `db-tool replay-on-archive` against the archived backup for that version.
3. `execute_and_verify` → `ensure_match_transaction_info` returns `Ok(())` because it never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so the tool reports a successful replay despite the authenticated checkpoint root actually diverging from local execution — exactly the failure mode called out in the code's own TODO comment.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
