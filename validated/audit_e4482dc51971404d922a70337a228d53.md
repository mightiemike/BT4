### Title
Restore path saves unverified `WriteSet`s to storage without checking them against the authenticated `TransactionInfo.state_change_hash` - (File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs)

### Summary
During transaction restore (the "save-before-replay" fast path), the backup CLI reads `(Transaction, PersistedAuxiliaryInfo, TransactionInfo, ContractEvent, WriteSet)` tuples from a backup chunk file and verifies only the `Transaction`/`TransactionInfo`/events against the accumulator-anchored ledger info via `TransactionListWithProofV2::verify`. That verification path (`TransactionListWithProof::verify`) checks transaction hashes against `txn_info.transaction_hash()` and event roots against `txn_info.event_root_hash()`, but it never checks the `WriteSet` against `txn_info.state_change_hash()` — unlike `TransactionOutputListWithProof::verify`, which does perform that exact check.

### Finding Description
`LoadedChunk::load` in [1](#0-0)  deserializes `write_set` independently from the record and stores it in `LoadedChunk::write_sets`, separate from the `TransactionListWithProofV2` object that is actually verified. The verification call `txn_list_with_proof.verify(ledger_info.ledger_info(), Some(manifest.first_version))?` only covers `txns`, `txn_infos`, and `event_vecs` — the `write_sets` vector is not part of that structure at all and is never cross-checked against `txn_info.state_change_hash()`.

Contrast this with the correct invariant enforced elsewhere for transaction-output backups, where `TransactionOutputListWithProof::verify` explicitly computes `CryptoHash::hash(&txn_output.write_set)` and requires it to equal `txn_info.state_change_hash()`: [2](#0-1) .

In `save_before_replay_version`, for versions before the replay-from version, these unverified write sets are persisted directly via `restore_handler.save_transactions(first_version, &txns_to_save, ..., &txn_infos_to_save, &event_vecs_to_save, write_sets_to_save)` [3](#0-2) . That call chain leads into `save_transactions_impl` / `save_transactions` in `storage/aptosdb/src/backup/restore_utils.rs`, which writes the write set to `WriteSetDb` and, when `kv_replay` is enabled, feeds the same unverified write sets directly into `calculate_state_and_put_updates` to derive the JMT state updates: [4](#0-3) .

Because the write set is trusted as ground truth for state derivation (and for later transaction-info reconstruction and replay context), a corrupted or tampered `WriteSet` in the backup transaction-chunk file (distinct from the state-snapshot/output-chunk files) that does not match `txn_info.state_change_hash()` would be silently accepted and committed, even though the accumulator proof over `txn_info` is valid.

### Impact Explanation
This breaks the "committed state must match the correct/authenticated result" invariant central to restore-path integrity: a node restoring from a backup could persist an arbitrary write set diverging from the actual state committed on mainnet, while its `TransactionInfo` (and thus proofs derived from it, like `state_checkpoint_hash`) remain the legitimately-signed ones. This can lead to that node's post-restore state root diverging from the network, corrupting durable ledger data and any state proofs it later serves, without the standard verification path (used for output backups) catching the mismatch. This qualifies as a state-commitment/proof-integrity issue under the stated impacts (committed state differing from the correct result; API/state output bound to a mismatched proof context).

### Likelihood Explanation
Exploitability requires control over, or corruption of, the backup storage/transport (an untrusted or compromised backup source, or a bit-flip/corruption in the transaction-chunk file that isn't caught because the write set is outside the verified structure). This is not exploitable by a normal unprivileged network peer against a live node's consensus path — it specifically affects the backup/restore tooling's trust boundary on the loaded backup file. I could not fully trace whether any downstream chunk-executor replay path re-derives/re-verifies the write set against VM re-execution for these "save-before-replay" versions (only versions strictly before the replay-from version take this path; versions at/after are replayed by the VM via `ChunkExecutor`, which would independently produce write sets and might catch a mismatch through separate state-checkpoint hash comparisons — this part I was not able to verify with certainty in the time available).

### Recommendation
Before persisting `write_sets_to_save` in `save_before_replay_version` (and generally before any restore code trusts backup-file write sets), require that `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for each transaction, analogous to the check already present in `TransactionOutputListWithProof::verify`. Add this assertion either in `LoadedChunk::load` right after loading `write_sets` and `txn_infos`, or in `restore_utils::save_transactions_impl`, and fail/abort restoration on mismatch rather than silently persisting unverified state-affecting data.

### Proof of Concept
Not independently reproduced end-to-end (no test harness run); the gap is demonstrated structurally by comparing the verification code paths:
- Missing check: `TransactionListWithProof::verify` (used in `LoadedChunk::load`) has no write-set/state_change_hash check — see the full function body: [5](#0-4) .
- Present check (for the analogous output-backup structure), showing what's missing: [2](#0-1) .
- The unverified `write_sets` flowing straight to disk/state derivation: [6](#0-5)  and [4](#0-3) .

**Caveat**: I was unable to fully confirm within the available time whether `RestoreHandler::save_transactions` (declared in `storage/aptosdb/src/backup/restore_handler.rs`, whose body I could not retrieve due to index/size limits) performs any additional validation before delegating to `restore_utils::save_transactions`, nor whether the chunk-executor replay path for post-replay-from versions has independent safeguards that would limit the practical blast radius. I recommend a Devin session with full repository access to inspect `RestoreHandler::save_transactions`'s complete body and the `ChunkExecutor` replay/verification code to confirm the exact boundary of exploitability before treating this as fully proven.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
