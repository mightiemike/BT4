### Title
Unbounded loop over `VotesStore` in DPoS maintenance can grow without limit via cheap Sybil voting - ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
The external report flags `massUpdatePools()`-style unbounded loops that iterate over a list whose length is fully attacker/user-influenced, risking gas/processing-limit exhaustion. The strongest analog in java-tron is `MaintenanceManager.countVote()`, which iterates over every entry of `VotesStore` on every maintenance cycle (~every 6 hours, at every `doMaintenance()` call), a set that is directly grown by any unprivileged account calling the public `VoteWitnessContract` actuator.

### Finding Description
`MaintenanceManager.doMaintenance()` is executed periodically as part of consensus/chain state advancement and calls `countVote(votesStore)`: [1](#0-0) 

This method does `Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator(); while (dbIterator.hasNext()) { ... }`, i.e., it processes **every record ever written to `VotesStore`** in one pass, with no offset/limit/pagination parameters — the same anti-pattern flagged in the external `massUpdatePools()` report ("a loop that depends on [list].length ... in the case [of a] significant amount of [items], this function potentially could not be completed").

Crucially, the size of `VotesStore` is controlled by ordinary, unprivileged users: any account can submit a `VoteWitnessContract` transaction via `VoteWitnessActuator`, which only requires that the account exist, hold enough frozen TRON Power to cover the requested vote count, and vote for existing witnesses: [2](#0-1) 

`countVoteAccount()` then writes/updates a `VotesCapsule` entry keyed by the voter's address into `votesStore`: [3](#0-2) 

There is a per-transaction cap (`MAX_VOTE_NUMBER`) on the number of distinct witnesses a single vote transaction can target, but there is **no cap on the number of distinct voter accounts**, and thus no cap on the total number of entries in `VotesStore`. An attacker can cheaply create a large number of accounts, freeze the minimum required TRX for 1 TRON Power on each, and cast 1 vote each — creating unboundedly many `VotesStore` entries.

This differs from the trusted-role `ProposalController.processProposals()` loop (also unbounded, over `ProposalStore`), which is not reachable by unprivileged users because `ProposalCreateActuator.validate()` requires the proposer to already be a registered witness: [4](#0-3) 
That path is excluded per the analog-report rules (trusted-role only). By contrast, voting is fully public and unprivileged, making `countVote()` in `MaintenanceManager` the valid analog.

### Impact Explanation
`doMaintenance()` runs on every full node as part of the deterministic state-transition/consensus flow at each maintenance cycle boundary. If `VotesStore` is inflated with a very large number of entries by a Sybil-voting campaign, `countVote()`'s full-table iteration (plus the per-entry `votesStore.delete()` calls) becomes proportionally slower on every node, every cycle, indefinitely (entries are cleared each cycle but can be immediately re-populated by resubmitting votes, or by new distinct spam accounts). This can:
- Slow down maintenance processing time, risking missed block-production windows for witnesses (each SR has a fixed ~3s slot), which can cascade into consensus/liveness degradation.
- Because `doMaintenance()` sits inside the block-processing path (triggered when `nextMaintenanceTime <= block.getTimeStamp()`), a sufficiently bloated `VotesStore` could cause processing of the maintenance block to overrun expected timing across the entire network simultaneously (since all nodes process the same state), creating a synchronized network-wide slowdown rather than a localized DoS — a systemic liveness/availability risk to the chain's state-transition determinism and block cadence.

### Likelihood Explanation
Voting is a core, permissionless, everyday feature of TRON with no built-in cap on the number of distinct voting accounts. The economic cost to an attacker is bounded by account-creation fees and minimal TRON Power freezing costs per account, which are the cheapest tier of on-chain interactions on java-tron. Achieving enough entries to cause a measurable, sustained slowdown requires large-scale automation but no privileged access, elevated capital relative to normal usage, or special timing — making this a realistic, moderate-likelihood scenario for a well-resourced or scripted attacker, though a full network halt would require an extreme entry count that has not been empirically confirmed against production node hardware/timeouts.

### Recommendation
- Add an explicit comment/design note documenting that `VotesStore` size is expected to remain bounded, or
- Introduce a cap on the number of distinct voter entries (or an offset/limit-based batched processing loop) in `countVote()`/`doMaintenance()`, spreading vote-tallying work across multiple maintenance passes if the store grows beyond a safe threshold, mirroring the pagination pattern already used elsewhere in the codebase (e.g., `Wallet.getPaginatedNowWitnessList`, `Wallet.getPaginatedProposalList`).
- Consider adding an economic disincentive (e.g., minimum TRON Power threshold per vote, or per-account vote-record garbage collection) to bound `VotesStore` growth from cheap Sybil accounts.

### Proof of Concept
1. Script the creation of N accounts (e.g., tens/hundreds of thousands), each funded with the minimum TRX needed to freeze for TRON Power.
2. For each account, submit a `VoteWitnessContract` transaction voting a small amount for any existing witness — this creates/updates one `VotesCapsule` entry in `VotesStore` per account via `VoteWitnessActuator.execute()` → `countVoteAccount()`. [5](#0-4) 
3. Observe that at the next maintenance cycle, `MaintenanceManager.doMaintenance()` → `countVote(votesStore)` must iterate all N entries and issue N deletes: [6](#0-5) 
4. Measure maintenance-cycle processing time as N scales; demonstrate that processing time grows linearly/unbounded with attacker-controlled input and is not capped by any pagination or entry-count limit in the code path.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
