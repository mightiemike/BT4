## Analog Identified: Permanently Stuck Excess Gas Fee on Outbound Refund Failure

### Title
Unrecoverable freezing of excess outbound gas fee when `refundUnusedGas` fails on both swap and no-swap paths - (`x/uexecutor/keeper/outbound.go`)

### Summary
The `earlyEndGame` bug pattern — a fee is deducted upfront from a user, but the mechanism meant to return the unused portion has no fallback if the transfer fails, permanently trapping funds — has a direct analog in `applyGasRefund` in `x/uexecutor/keeper/outbound.go`. Excess outbound gas fee (`gasFee - gasFeeUsed`) is escrowed on-chain at outbound creation and is supposed to be returned to the user via `CallUniversalCoreRefundUnusedGas`. If both the swap-refund and the no-swap fallback calls fail, the code simply records a `FAILED` status on `PcRefundExecution` and moves on — there is no retry mechanism, no abort/rescue path, and no way to ever re-trigger the refund.

### Finding Description
When an outbound is created, `BuildOutboundsFromReceipt` captures `GasFee` and `GasToken` straight from the `UniversalTxOutboundEvent` emitted by `UniversalGatewayPC` — meaning the user's gas token was already collected/escrowed at creation time. [1](#0-0) 

Once the outbound is finalized (either observed successfully or reverted), `FinalizeOutbound` calls `handleSuccessfulOutbound`/`handleFailedOutbound`, both of which call `applyGasRefund` to return any excess gas fee to the user: [2](#0-1) 

`applyGasRefund` computes the excess and attempts two strategies in sequence — refund with swap, then refund without swap. If the second (no-swap) call also fails, the function only records the failure and returns; the outbound has already transitioned to its terminal status (`OBSERVED`/`REVERTED`) at this point, and nothing in the codebase re-attempts the refund afterward: [3](#0-2) 

This differs materially from the sibling failure path for the *bridged-funds* re-mint (`handleFailedOutbound`), which explicitly calls `AbortOutbound` for manual intervention when the re-mint fails: [4](#0-3) 

No equivalent abort/rescue exists for a failed gas refund — `RefundSwapError` and `PcRefundExecution.Status == "FAILED"` are stored purely as informational fields, with no other code path in the repository reading them to retry or flag manual recovery (confirmed by searching for any consumer of `RefundSwapError` outside tests/proto).

An unprivileged actor can force this outcome deterministically: the refund recipient is derived from `RevertInstructions.FundRecipient` or `outbound.Sender`, both of which are attacker-controlled inputs supplied when the outbound-triggering payload/inbound was created. By setting the recipient to a contract (or PRC20-gated address) that unconditionally reverts on receiving the gas-token deposit/swap-output, the attacker guarantees `CallUniversalCoreRefundUnusedGas` fails on both the swap and no-swap branches, permanently trapping the escrowed excess gas fee inside the `UniversalCore`/gateway contracts with the honest UV set correctly voting and no protocol path left to recover it.

### Impact Explanation
This is a permanent freezing of protocol/user-escrowed funds (the excess portion of the outbound gas fee), triggered purely by an unprivileged user's choice of `RevertInstructions.FundRecipient`/inbound `Sender`, with no admin, governance, or retry mechanism able to recover it afterward. It matches the "Allowed Impact Gate" category of permanent freezing of user or protocol-controlled funds via a corrupted/terminal refund-accounting outcome.

### Likelihood Explanation
High — the trigger requires no privileged access, no validator collusion, and no consensus divergence. Any user submitting a cross-chain transaction can set the refund/revert recipient to a simple reverting contract, and every outbound that produces excess gas (a normal, expected occurrence whenever actual gas used is less than the pre-paid fee) will hit this path.

### Recommendation
Treat a fully-failed `applyGasRefund` (both swap and no-swap attempts failing) the same way `handleFailedOutbound`'s failed re-mint is treated: call `AbortOutbound` (or an equivalent rescue-eligible terminal state) so the stuck gas fee is flagged for manual/admin recovery, or add a queryable "stuck refund" registry with a permissionless retry entry point that lets a different, valid recipient address claim the trapped amount after a timeout.

### Proof of Concept
1. Attacker submits an inbound/payload that will later create an outbound with `RevertInstructions.FundRecipient` (or `Sender`) set to `AttackerRevertingRecipient`, a contract whose `receive`/token-transfer hook always reverts.
2. UVs observe and finalize the outbound normally (honest validators, no collusion needed); `gasFeeUsed < gasFee` so `applyGasRefund` computes a positive `refundAmount`.
3. `CallUniversalCoreRefundUnusedGas(..., withSwap=true, ...)` reverts because delivering swapped PC to `AttackerRevertingRecipient` fails.
4. Fallback `CallUniversalCoreRefundUnusedGas(..., withSwap=false, ...)` also reverts for the same reason.
5. `applyGasRefund` sets `refundPcTx.Status = "FAILED"` and `outbound.RefundSwapError`, then returns; `outbound.OutboundStatus` remains at its terminal value (`OBSERVED`/`REVERTED`).
6. No further code path in `x/uexecutor` ever re-attempts or exposes recovery for this specific `OutboundTx`'s excess gas fee — it is permanently locked in the `UniversalCore` contract's escrow.
