### Title
Reward dust permanently lost due to truncating division in DPoS voter/witness reward accounting - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The reported Curves bug is a class of "accumulator truncation" flaw: an accrual index (`cumulativeFeePerToken`) is incremented using integer division (`msg.value * PRECISION / totalSupply_`), and each holder's claim is computed as `balance * (cumulativeFeePerToken - userFeeOffset)`, which always rounds down. The remainder from every division is never attributable to anyone and stays permanently stuck. Java-tron's DPoS voter-reward pipeline in `MortgageService`/`DelegationStore` implements the structurally identical pattern, with the same rounding-loss defect, but for real, protocol-collected value (block rewards and transaction fees) rather than ERC-20 fees.

### Finding Description
`MortgageService.payReward` splits a witness's block/transaction-fee reward into a brokerage cut and a voter pool, using floating-point truncation: [1](#0-0) 
`brokerageAmount = (long) (brokerageRate * value)` truncates towards zero, and the residual `value` is stored as the cycle's voter reward pool via `delegationStore.addReward(cycle, witnessAddress, value)`.

When a voter withdraws, `MortgageService.computeReward` (old algorithm) apportions that pool per voter using another truncating floating-point multiplication: [2](#0-1) 
`voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;` — each voter's share is floored to a `long`, so the sum of all voters' claims is strictly ≤ `totalReward`, exactly mirroring Curves' `balance * (cumulativeFeePerToken - userFeeOffset)` truncation.

The newer Vi-based algorithm has the same defect, just using `BigInteger` floor division instead of `double`: [3](#0-2) 
`accumulateWitnessVi` computes `deltaVi = reward * DECIMAL_OF_VI_REWARD / voteCount` (BigInteger `divide`, i.e. floor), which is the direct analog of Curves' `cumulativeFeePerToken += (msg.value * PRECISION) / totalSupply_`. Later, `computeReward`/`VoteRewardUtil.computeReward` recovers each voter's share via `deltaVi * userVote / DECIMAL_OF_VI_REWARD`, again floor-dividing: [4](#0-3) [5](#0-4) 

This code path is reachable by any unprivileged TRX holder who votes for witnesses: withdrawal is triggered from `WithdrawBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, and `VoteWitnessActuator` (all of which call `mortgageService.withdrawReward`), as well as from the TVM-exposed native contract `WithdrawRewardProcessor`/`VoteRewardUtil.withdrawReward` that any smart contract can invoke. [6](#0-5) 

### Impact Explanation
Every cycle, for every witness with voters, the brokerage split and the per-voter reward split each floor-truncate. Because the source value (`getWitnessPayPerBlock()`, `getTransactionFeePool()`) represents real TRX obligations that are supposed to be fully distributed to the brokerage owner and to voters proportional to their stake, the truncated remainder in each of these calculations is never credited to anyone — it is a systematic accounting shortfall, structurally identical to the "stuck rewards" defect in the report (an accrual index/division pattern that guarantees some fraction of distributable value is permanently unclaimable). Given the scale of TRON's DPoS reward distribution (every block, every cycle, every witness/voter pair), this dust loss compounds over the life of the chain, causing a persistent, protocol-wide value leakage/underpayment in the voter-reward accounting subsystem — an accounting/settlement divergence between "value that should be distributable" and "value actually claimable."

### Likelihood Explanation
This code executes unconditionally on every block reward payment (`payReward`), on every maintenance cycle (`MaintenanceManager.doMaintenance` → `accumulateWitnessVi`), and on every voter's reward withdrawal (`withdrawReward`/`computeReward`), all of which are triggered by ordinary unprivileged user actions (voting, freezing/unfreezing, withdrawing balance) with no attacker action required — the loss occurs automatically and continuously as a byproduct of normal protocol operation.

### Recommendation
Track and periodically reconcile/redistribute (or explicitly document/burn) the residual dust left after each truncating division in `MortgageService.payReward`, `MortgageService.computeReward`, and `DelegationStore.accumulateWitnessVi`, e.g. by carrying forward remainders into the next cycle's pool instead of discarding them, similar to how remittance systems avoid systematic rounding loss.

### Proof of Concept
1. Configure a witness with `brokerage = 20` and `totalPay = value` such that `brokerageRate * value` is non-integer (e.g. `value = 100000007`, `brokerage = 33` → `brokerageRate = 0.33`), producing a fractional `brokerageAmount` that gets floored in `payReward` (`chainbase/src/main/java/org/tron/core/service/MortgageService.java:79-87`); the truncated fraction is lost from both the brokerage payout and the voter pool.
2. Have several voters (with vote counts that don't evenly divide `totalVote`, e.g. `userVote` values like 100000001, 100000002, ...) vote for that witness across a few maintenance cycles, causing `DelegationStore.accumulateWitnessVi` (`chainbase/src/main/java/org/tron/core/store/DelegationStore.java:133-146`) to floor-divide `reward * DECIMAL_OF_VI_REWARD / voteCount` each cycle.
3. Have all voters withdraw via `mortgageService.withdrawReward` and sum their `adjustAllowance` credits; the sum will be strictly less than the total `totalReward`/brokerage value originally intended for distribution, with the shortfall growing each additional cycle — mirroring the Curves PoC pattern where `totalClaimableByUsers` is always less than the total fees added, and the difference is never distributed to anyone.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
