### Title
Non-hardened exchange arithmetic path allows pool balance underflow / conservation-check bypass in `ExchangeTransactionActuator` - (`actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionActuator.execute` and its supporting `ExchangeCapsule.transaction` compute a floating-point AMM/bonding-curve swap and then apply the result to account balances and exchange-pool balances. The overflow/underflow protections (`StrictMathWrapper.addExact/subtractExact` and the explicit `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard) are only applied when the governance-controlled flag `allowHardenExchangeCalculation` is enabled; when it is disabled the same code paths use raw `+`/`-` arithmetic with **no negative-balance or overflow check at all**.

### Finding Description
`ExchangeTransactionActuator.execute` obtains `anotherTokenQuant` from `ExchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` [1](#0-0) , where `allowHarden()` reads the dynamic-store flag `allowHardenExchangeCalculation` [2](#0-1) .

Inside `ExchangeCapsule.transaction`, the new pool balances are computed either with checked `StrictMathWrapper` arithmetic plus an explicit `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` throw, **or**, when `hardenedCalc` is `false`, with plain `long` addition/subtraction and **no negative-value check whatsoever**: [3](#0-2) 

The actual exchanged quantity (`buyTokenQuant`) is produced by `ExchangeProcessor.exchange`, which relies on `double`-precision `Math.pow` bonding-curve math (`exchangeToSupply`/`exchangeFromSupply`) [4](#0-3) . Floating-point rounding in this curve can, for extreme or carefully chosen `sellTokenQuant`/pool-balance ratios, yield a `buyTokenQuant` that exceeds the real token balance available in the pool.

`ExchangeTransactionActuator.doValidate` only checks that the *selling*-side pool balance plus quant stays under `balanceLimit` (`tokenBalance = addExact(tokenBalance, tokenQuant); if (tokenBalance > balanceLimit) …`) and that `anotherTokenQuant >= tokenExpected` [5](#0-4) . There is **no explicit check that the computed `anotherTokenQuant` does not exceed the current balance of the token being bought** — unlike `ExchangeWithdrawActuator.doValidate`, which explicitly checks `firstTokenBalance < tokenQuant || secondTokenBalance < anotherTokenQuant` [6](#0-5) . For `ExchangeTransactionActuator`, this safety net exists only inside `ExchangeCapsule.transaction`'s hardened branch; it is absent when `allowHardenExchangeCalculation` is off.

Consequently, if the network parameter `allowHardenExchangeCalculation` is not active, an attacker can broadcast an `ExchangeTransactionContract` with a `tokenQuant` engineered (in combination with a thinly-capitalized exchange pool) to make the floating-point bonding curve compute a `buyTokenQuant`/`anotherTokenQuant` larger than the pool's actual balance of that token. `execute()` then unconditionally applies this to both the exchange pool (`Commons.putExchangeCapsule`) and to the attacker's own account (`addAssetAmountV2`/`setBalance`) [7](#0-6) , driving the exchange pool's token balance negative and crediting the attacker with more of the asset than was ever deposited into the pool — a supply/accounting invariant violation.

### Impact Explanation
This breaks the invariant that exchange-pool balances and account asset/TRX balances never underflow or exceed real issuance, matching the "Asset/accounting corruption (Critical)" impact class: an attacker can mint excess asset/TRX credit into their own account backed by a negative (impossible) pool balance, and subsequent withdrawals/injections against that corrupted `ExchangeCapsule` state would propagate the corruption further.

### Likelihood Explanation
Exploitability is conditional: it requires (1) `allowHardenExchangeCalculation` to be disabled on the running network (the checked-arithmetic/negative-balance guard in `ExchangeCapsule.transaction` is only active when this flag is on — this is a committee/SR-activated proposal parameter, not attacker-controlled), and (2) finding specific pool-balance/quant combinations where the `double`-based bonding curve in `ExchangeProcessor` produces a `buyTokenQuant` that exceeds the true pool balance. I was not able to confirm from the available index whether this flag defaults to enabled or disabled on the target deployment (`DynamicPropertiesStore`'s default/persisted value could not be fully verified in this pass), so likelihood should be treated as **unconfirmed/conditional** rather than certain — this should be validated against the live chain's `allowHardenExchangeCalculation` state before treating this as immediately exploitable. If the flag is off, the attack costs only ordinary transaction fees (bandwidth/energy) and requires no privileged role, no leaked keys, and is fully repeatable.

### Recommendation
Make the negative-balance/overflow protection in `ExchangeCapsule.transaction` and `ExchangeTransactionActuator.doValidate`/`execute` unconditional (not gated behind `allowHardenExchangeCalculation`): always use checked arithmetic (`Math.addExact`/`Math.subtractExact`) for pool balance updates, and always assert `newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0` regardless of the hardened flag. Additionally, add an explicit `doValidate` check that `anotherTokenQuant` does not exceed the current balance of the token being purchased, mirroring `ExchangeWithdrawActuator`'s check.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
