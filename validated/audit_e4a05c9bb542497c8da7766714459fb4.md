### Title
Unbounded O(active ballots) work in `ExpireBallotsBeforeHeight` executed on every `CreateBallot` call — attacker-floodable, non-network-level DoS - ([File: x/uvalidator/keeper/ballot.go])

### Summary
`CreateBallot` unconditionally calls `k.ExpireBallotsBeforeHeight(ctx, blockHeight)` before persisting a new ballot [1](#0-0) . `ExpireBallotsBeforeHeight` performs a full iteration of the entire `ActiveBallotIDs` set, doing a `k.Ballots.Get` read per active ballot [2](#0-1) . Because `CreateBallot` is invoked (via `GetOrCreateBallot`) on the first vote for every distinct new ballot ID [3](#0-2) , the per-tx cost of creating a ballot scales linearly with the current size of the active-ballot set rather than being O(1).

### Finding Description
Ballot IDs are derived from source-chain event identity (chain, sender, log index, etc.), so any distinct externally observable deposit/event produces a distinct ballot ID. An attacker who is fully unprivileged with respect to Push Chain — they only need to originate cheap, distinct events on a source chain (e.g., varying sender or log index across many minimal-value deposits) — can cause honest Universal Validators, acting entirely within their normal, honest duty of observing and voting on inbound events, to submit vote transactions for a large number of previously-unseen ballot IDs in a short window. Each such vote triggers `GetOrCreateBallot` → `CreateBallot`, and every single one of those calls re-walks the *entire* `ActiveBallotIDs` set via `ExpireBallotsBeforeHeight`, fetching and evaluating every currently active ballot regardless of whether it needs expiry. If the attacker sustains ballot creation faster than the natural expiry rate (`expiryAfterBlocks`), the active set grows, and each subsequent ballot creation becomes proportionally more expensive — an O(N) cost per new ballot and O(N²) total cost for N floodable events, all driven purely by ordinary/honest deposit-and-vote processing with no validator misbehavior required.

### Impact Explanation
This does not corrupt any ballot value, funds, or consensus state — MarkBallotExpired/Finalize logic and vote tallies remain correct. The impact is purely a resource-consumption/liveness concern: increasing gas/CPU cost per UV vote transaction as the active-ballot backlog grows, which can degrade throughput of the ballot-voting pipeline (inbound/outbound observation finalization) for all UVs, potentially delaying finalization of legitimate deposits/withdrawals under sustained flooding. This is a non-network-level DoS against a specific module's processing pipeline rather than a fund-loss, accounting-corruption, or unauthorized-execution bug.

### Likelihood Explanation
Reachable purely from unprivileged, ordinary source-chain deposit activity combined with entirely honest UV behavior — no malicious validator, admin, or governance action is required, satisfying the scope's requirement for an unprivileged, honest-validator-preserving path. Feasibility depends on how cheaply an attacker can generate many distinct source-chain events relative to `expiryAfterBlocks` and the marginal gas cost of the extra `Ballots.Get` reads; this bounds severity to moderate/low rather than a full chain halt.

### Recommendation
Decouple ballot expiry sweeping from the ballot-creation hot path: (1) move stale-ballot pruning to `EndBlock`/`BeginBlock` (already bounded by block cadence) instead of running it inline inside `CreateBallot`, and/or (2) bound the per-call expiry work with a cap (e.g., expire at most K stale ballots per call, resuming next time), and/or (3) maintain expiry via a height-indexed secondary index so only ballots actually due for expiry at `blockHeight` are touched instead of iterating the whole active set.

### Proof of Concept
A Go benchmark seeding `ActiveBallotIDs` with N ballots (via direct keeper calls, not needing malicious actors) and then calling `CreateBallot` for one additional distinct ID demonstrates `ExpireBallotsBeforeHeight` performs N `Ballots.Get` reads regardless of how many (if any) are actually expired, confirming linear-in-N cost per creation as shown in [2](#0-1) , invoked unconditionally from [1](#0-0) .

```go
// GetOrCreateBallot returns the ballot if it exists, otherwise creates it.
func (k Keeper) GetOrCreateBallot(
	ctx context.Context,
	id string,
	ballotType types.BallotObservationType,
	voters []string,
	votesNeeded int64,
	expiryAfterBlocks int64,
) (types.Ballot, bool, error) {

	if ballot, err := k.Ballots.Get(ctx, id); err == nil {
		k.Logger().Debug("ballot found (existing)", "ballot_id", id)
		return ballot, false, nil
	}

	k.Logger().Debug("ballot not found, creating new", "ballot_id", id, "ballot_type", ballotType.String())
	newBallot, err := k.CreateBallot(ctx, id, ballotType, voters, votesNeeded, expiryAfterBlocks)

	return newBallot, true, err
}
```

```go
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
```
