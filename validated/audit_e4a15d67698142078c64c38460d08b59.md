### Title
Unbounded native recursion in `get_recursive_transaction_results` allows an RPC caller to crash a node via stack overflow - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` (`chain/chain/src/chain.rs`, around lines 3190-3207) walks the DAG of execution outcomes/receipts spawned by a transaction using plain, unbounded Rust function recursion — one stack frame per level of receipt nesting, with no depth cap. This function is the backbone of `get_final_transaction_result` and `get_partial_transaction_result_option`, which are invoked from the `ViewClientActor`'s `TxStatus`/`TxStatusRequest` handlers, which in turn back the public JSON-RPC `tx` endpoint (`chain/jsonrpc/src/lib.rs::tx_status_common` → `tx_status_fetch` → `TxStatus`). Any account can submit a transaction that produces a deeply nested chain of cross-contract-call receipts (via `promise_batch_create`/`promise_then` self-recursion, as already exercised by `max_self_recursion_delay` in `runtime/near-test-contracts/test-contract-rs/src/lib.rs`), then simply query `tx`/`EXPERIMENTAL_tx_status` for that transaction hash. Each queried node that tracks the shard will recurse to the same depth while assembling the response, risking a stack overflow that aborts the node process — a transaction-triggered node crash reachable purely from unprivileged transaction submission plus a follow-up unauthenticated RPC call.

### Finding Description
`get_recursive_transaction_results` is defined as: [1](#0-0) 

For each outcome it pushes the current outcome and then calls itself once per receipt id produced by that outcome. Stack depth grows linearly with the *depth* of the receipt DAG (i.e., with how many sequential hops a chain of receipts triggers), not with node count, because sibling receipts are visited sequentially within the same stack frame while a chain of `receiptA -> receiptB -> receiptC -> ...` (self-recursive cross-contract calls, or any linear chain) each adds a new stack frame before returning.

This function backs two public entry points:
- `get_final_transaction_result`: [2](#0-1) 
- `get_partial_transaction_result_option`, used by the tx-status query path: [3](#0-2) 

`get_partial_transaction_result_option` is the function called on the read path of `ViewClientActor::get_tx_status`, which serves `TxStatus`/`TxStatusRequest` actor messages: [4](#0-3)  and [5](#0-4) . These messages are what the public JSON-RPC `tx` / `EXPERIMENTAL_tx_status` handler (`tx_status_common` → `tx_status_fetch` → `tx_status_fetch_single`) uses to answer any unauthenticated caller's transaction-status request: [6](#0-5) , [7](#0-6) .

The depth an attacker can achieve is bounded only by the total attached prepaid gas divided by the minimal per-hop cost of creating a self-recursive receipt (a `FunctionCall` action that immediately schedules another minimal `FunctionCall` to itself), not by any explicit depth limit. The existing test contract `max_self_recursion_delay` demonstrates such self-recursion is a supported, unprivileged pattern that already reaches depths in the hundreds with normal (non-minimized) per-hop costs: [8](#0-7) , [9](#0-8) . With a contract optimized purely to minimize gas cost per hop (skip the body logic, just re-issue the promise), the achievable depth scales with `max_total_prepaid_gas` (1e15 gas per NEP config: [10](#0-9) ) divided by the minimal action-receipt-creation + function-call base cost, which is several orders of magnitude smaller than the total, giving room for a much deeper chain than the 221 seen in the existing test — plausibly tens of thousands of stack frames.

Notably, the codebase elsewhere explicitly recognizes and defends against exactly this class of unbounded-recursion bug: `ReceiptToTx`'s traversal enforces a hard `MAX_DEPTH=1000` and returns a `DepthExceeded` error instead of recursing further, as shown by the dedicated regression test: [11](#0-10) . `get_recursive_transaction_results` has no analogous guard, despite building the same style of receipt-chain traversal from user-controlled data.

### Impact Explanation
A stack overflow in Rust is not a catchable/recoverable error — it triggers immediate process abort (SIGSEGV/SIGABRT), not a panic that can be caught at a call-site boundary. Because `get_tx_status`/`get_partial_transaction_result_option` run inside the `ViewClientActor`, an actor within the node process (not a sandboxed thread with guarded exit), crashing that stack aborts the whole node process. This is a transaction-triggered node halt: any validator or RPC node that tracks the relevant shard and later serves a `tx`/`EXPERIMENTAL_tx_status`/`TxStatusRequest` query for the malicious transaction hash can be crashed by an unauthenticated third party issuing that RPC call. Given `tx_status_fetch`/`send_tx_commit` polling paths call this internally too, a normal `broadcast_tx_commit` on such a transaction can independently trigger the same crash on the submitting node itself. This satisfies the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
High: constructing a deep self-recursive receipt chain requires only a standard `FunctionCall` action from any funded account with `promise_batch_create`/`promise_then`-style self-calls — a pattern already validated as supported and exercised in the existing test suite (`max_self_recursion_delay`). No special privileges, validator status, or malicious peer/node access are required — only the ability to submit one transaction and later issue a normal `tx` RPC query, both of which are core, expected use cases for any transaction signer / RPC caller.

### Recommendation
Bound the recursion depth in `get_recursive_transaction_results` explicitly (e.g., convert to an iterative worklist/BFS with an explicit stack, or add a `MAX_DEPTH` check analogous to the one already used for `ReceiptToTx` traversal) and return a graceful error (e.g., `DepthExceeded`) instead of recursing unboundedly. This should be applied wherever this function's outputs are exposed to untrusted/RPC-triggered code paths (`get_final_transaction_result`, `get_partial_transaction_result_option`).

### Proof of Concept
1. Deploy (or reuse) a contract exposing a method that recurses via `promise_batch_create` + `promise_batch_action_function_call_weight` + `promise_return`, calling itself with minimal-cost arguments (as in `max_self_recursion_delay`, but stripped of any extra logic to minimize per-hop gas cost) so that available prepaid gas maximizes hop count.
2. Submit a `FunctionCall` transaction invoking this method with `gas: max_total_prepaid_gas` from any funded account (no special permission needed).
3. Wait for the transaction and its self-recursive receipt chain to execute across subsequent blocks, producing a receipt-outcome chain many thousands of hops deep.
4. Issue a normal `tx` / `EXPERIMENTAL_tx_status` JSON-RPC request (or a `send_tx_commit`) for the transaction hash against any node tracking that shard.
5. `ViewClientActor::get_tx_status` → `Chain::get_partial_transaction_result_option` → `get_recursive_transaction_results` recurses to the full chain depth, overflowing the actor's stack and crashing the node process.

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[0]));

    match result {
        Err(GetReceiptToTxError::DepthExceeded { receipt_id, limit }) => {
            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),
    }

    // Sanity: receipt_2 (999 FromReceipt + 1 terminal = 1000 iter) succeeds
    // — exactly at limit.
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[2]));
    assert!(result.is_ok(), "1000 hops succeed, got: {result:?}");
    let response = result.unwrap();
    assert_eq!(response.transaction_hash, CryptoHash::hash_bytes(b"tx"));
    assert_eq!(response.sender_account_id.as_str(), "sender");
}
