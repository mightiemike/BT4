### Title
Deposit mints zero shares for real underlying after `socialize-debt` zeroes out `assets`, permanently freezing new deposits - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent vault contracts)

### Summary
Each vault's `deposit` function computes shares to mint via `convert-to-shares-preview`, which silently returns `u0` shares whenever `total-assets-preview` (`ta`) is zero, regardless of the deposited `amount`. Unlike `redeem`, which asserts `(> inkind u0)` (`ERR-OUTPUT-ZERO`), `deposit` has no equivalent zero-output guard — it only checks `(>= inkind min-out)`. `ta` can be legitimately driven to `u0` by `socialize-debt`, a normal, authorized bad-debt write-down flow that sets `assets` to `u0` while the FT `total-supply` (existing LP shares) remains untouched and non-zero. In that state, any subsequent `deposit` transfers real underlying tokens into the vault but mints `u0` shares whenever the caller does not set a strictly positive `min-out`, permanently freezing the depositor's funds — the exact "reserve reaches zero, subsequent liquidity provider gets zero shares" bug class from the HydraDX report.

### Finding Description
`convert-to-shares-preview` in every vault contract (e.g. `v0-vault-usdc.clar:306-317`) is defined as:
```clarity
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```
`ta` (`total-assets-preview`) is `(var-get assets)` plus accrued interest (`v0-vault-usdc.clar:339-344`). The `assets` variable is authoritative "book value" tracked separately from the FT `total-supply`.

`socialize-debt` (`v0-vault-usdc.clar:942-982`), callable by any address passing `check-caller-auth` (an authorized system/liquidation contract, not requiring DAO compromise), can zero the `assets` variable on a full bad-debt write-down:
```clarity
(var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
```
This is a legitimate, designed state transition (bad debt socialization), not an attack on the registry or a privileged-key compromise. After a full write-down, `assets = u0`, `total-borrowed = u0`, but the FT `total-supply` (shares already held by LPs) is **not** burned or reduced — it stays exactly as it was before the write-down.

Once `ta = u0` while `ts > u0`, `convert-to-shares-preview` returns `u0` for *any* deposited amount, per the inner `(if (is-eq ta u0) u0 ...)` branch. `deposit` (`v0-vault-usdc.clar:761-793`) uses this value directly:
```clarity
(inkind (convert-to-shares-preview amount))
...
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
...
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
```
There is no `(asserts! (> inkind u0) ...)` guard in `deposit`, unlike `redeem` which explicitly has `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` at `v0-vault-usdc.clar:809`. So if the caller supplies `min-out = u0` (a common default for a first, or naive, integration/UI call, since the depositor has no reason to expect `ta=0`), the deposit succeeds: real underlying tokens are pulled from the depositor (`receive-underlying`) and `u0` shares are minted. The depositor's principal is absorbed into the vault's `assets` bookkeeping with no corresponding claim.

This is the single-transaction analog of the HydraDX bug: a value (`ta`) bound at the start of `deposit`'s evaluation is invalidated by a prior state-changing event (`socialize-debt` zeroing `assets`) and is then used by a fold (`convert-to-shares-preview`) that absorbs the zero-reserve failure into a silent `u0` result instead of reverting, and the caller's later mutation (`ft-mint?` / fund transfer) proceeds anyway.

### Impact Explanation
Any deposit made after a full `socialize-debt` write-down, with `min-out` not set strictly above `u0`, permanently freezes the depositor's underlying funds: real tokens leave the depositor's wallet into the vault, but zero LP shares are minted, so the depositor has no mechanism to redeem or reclaim the deposited amount. This is a freezing-of-funds impact for the depositing user. Because `deposit` is a normal, expected user action and the `ta = u0` state is a normal (not exotic) consequence of an intended bad-debt socialization event, this can occur without any second malicious user — it is the depositor's own single-transaction interaction with a vault state left over from a system operation.

### Likelihood Explanation
`socialize-debt` writing off 100% of a vault's `assets` in one call requires the vault's entire outstanding principal to be marked as bad debt in a single or cumulative write-down where `principal-reduction >= current-assets` — a plausible edge case for a vault after a severe under-collateralized liquidation shortfall, especially for a fully or nearly fully utilized vault. Once that state is reached, exploitation only additionally requires a depositor (or an automated integrator/keeper) to call `deposit` with `min-out = u0`, which is a common default in front-ends/scripts that don't anticipate a zero-share outcome. No attacker collusion, no flashloan, and no privileged-key/DAO compromise is needed — only the described sequence of a completed authorized write-down followed by an ordinary deposit call.

### Recommendation
Add a zero-output guard to `deposit` symmetric to the one already present in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
Additionally, consider making `convert-to-shares-preview` revert (or fall back to 1:1 `amount` minting, as already done for the `ts = u0` branch) when `ta = u0` but `ts > u0`, rather than silently returning `u0`, so any caller — regardless of the `min-out` they supply — cannot have real funds accepted without a corresponding share mint.

### Proof of Concept
1. Vault has active depositors: `total-supply` (`zft`) `> 0`, `assets = A > 0`, matching outstanding `principal-scaled`/`total-borrowed` debt.
2. An authorized caller (e.g., a liquidation/risk contract) invokes `socialize-debt` with `scaled-amount` equal to the vault's entire `principal-scaled`, such that `principal-reduction >= current-assets`. This sets, per `v0-vault-usdc.clar:964`:
   `(var-set assets u0)`
   while `ft-get-supply zft` remains unchanged (existing LP shares are not burned).
3. `total-assets-preview` now evaluates to `u0` (`current-assets = 0`, and `interest = max(debt - borrowed, 0)` is `0` right after the write-down since debt/borrowed were reduced together).
4. A new (or existing) depositor calls `deposit(amount, min-out: u0, recipient)`.
   - `inkind = (convert-to-shares-preview amount)` evaluates the `(is-eq ta u0)` branch → `inkind = u0`.
   - `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes trivially (`u0 >= u0`).
   - `(try! (receive-underlying amount account))` pulls `amount` of real underlying from the depositor into the vault.
   - `(try! (ft-mint? zft inkind recipient))` mints `u0` shares to the depositor.
   - `(var-set assets (+ current-assets amount))` updates bookkeeping, but the depositor holds no shares representing the newly deposited `amount`.
5. The depositor's funds are now indistinguishable from vault assets belonging to other, unrelated shareholders; the depositor cannot redeem any amount back, matching the "permanent freezing of funds" impact. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
