## Finding

Confirmed local root cause in `types/src/transaction/mod.rs`, function `TransactionOutput::ensure_match_transaction_info`.

### Title
Replay/execution verification skips checkpoint-hash comparison, allowing corrupted state roots to pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the single audit gate used by all replay/verification tooling (`db-tool`'s `replay_on_archive`, `aptos-debugger`, the chunk executor's `ReplayChunkVerifier` path, and the CLI) to confirm that a freshly re-executed `TransactionOutput` matches the previously committed, authenticated `TransactionInfo`. The function explicitly checks status, gas, write-set hash, and event root hash — but does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as acknowledged directly in the code's own TODO comment.

### Finding Description [1](#0-0) 

The function verifies four fields (status, gas_used, write_set hash, event_root_hash) but explicitly and admittedly skips checkpoint hash comparisons: [2](#0-1) 

This means the state-checkpoint root (the Sparse/Jellyfish Merkle root of the entire world state at a checkpoint boundary, and — when `compute_trading_native_state_roots` is enabled — the position-state root) computed during a local replay is never compared to the value recorded in the trusted `TransactionInfo` that was fetched from backup/archive storage. This function is used as the correctness oracle in:
- `storage/db-tool/src/replay_on_archive.rs`, `execute_and_verify`, which calls it after replaying transactions against archived data [3](#0-2) 
- `execution/executor/src/chunk_executor/mod.rs`, `verify_execution`, used during chunk replay/verification [4](#0-3) 

Because these are the exact call sites meant to catch state divergence during replay-verify (e.g., to detect a bad executor build, VM regression, or storage corruption that changes world-state without changing the write-set/events/gas), a state root divergence between actual replayed state and the archived/authenticated checkpoint hash will not be detected. The gap is severest for `compute_trading_native_state_roots`, whose feature-gated position-state root [5](#0-4)  is produced by a separate accumulator (`ProvablePositionStateSummary`) computed in the chunk executor's ledger-update path [6](#0-5)  — this is exactly the kind of newly-added, less-tested commitment root that this verification gate is supposed to catch when it silently diverges.

### Impact Explanation
This breaks the "authenticated API/proof-bearing output must stay bound to the correct ledger version, root, and object" invariant for the tooling that is specifically responsible for detecting exactly that class of divergence. A silent state-root corruption (from a storage bug, VM bug, or malicious archive/full-node serving corrupted TransactionInfo-adjacent state during replay) would be reported as a successful, verified replay even though the actual Merkle/JMT root of the ledger state differs from the authenticated one. This directly matches the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong ... state proof accepted as valid" impact categories in scope. Impact is High: replay-verify tooling exists specifically to catch state-commitment bugs before they propagate; this gap defeats that safety net for state-checkpoint and position-state roots.

### Likelihood Explanation
Likelihood is Medium: exploitation/triggering requires a pre-existing state-divergence bug (in the VM, executor, or storage layer) that changes committed state without changing the write set hash or gas/events — an unlikely but not impossible combination, and specifically acknowledged as unaddressed by the code's own TODO note that gates enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on this fix. Since `compute_trading_native_state_roots` requires several feature flags to be simultaneously enabled (`transaction_info_v1`, `hotness_in_epilogue`, and `is_compute_trading_native_state_roots_enabled`) [7](#0-6) , it does not currently appear active by default, but the state_checkpoint_hash gap (independent of that flag) is unconditional and always present in `ensure_match_transaction_info`.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) between the locally computed checkpoint output and the trusted `TransactionInfo`, consistent with what the code's own TODO describes, before any feature that relies on this verification path (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled on mainnet.

### Proof of Concept
Not independently reproducible without a triggering root-cause bug elsewhere (e.g., a VM/storage divergence bug) — the finding is that *if* such a divergence in state-checkpoint root existed, `ensure_match_transaction_info` would fail to detect it, as demonstrated by the code path tracing above (checked fields vs. TODO-documented omitted fields) and its exclusive use as the verification oracle in `replay_on_archive.rs` and `chunk_executor/mod.rs`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
