### Title
Unnecessary minimum-amount check in `DelegateResourceActuator` can strand small frozen resource balances - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceActuator.validate()` unconditionally rejects any `DelegateResource` transaction whose `balance` field is less than `TRX_PRECISION` (1 TRX), even when the user is delegating an amount they already legitimately hold as frozen resource (via `FreezeBalanceV2Contract`). This mirrors the reported GiantPool bug class: an arbitrary minimum-amount gate applied on an operation that moves/uses an existing balance, which can leave a small remainder of that balance permanently unusable for its intended purpose (delegation) unless the user tops up with additional TRX and pays extra fees.

### Finding Description
`DelegateResourceActuator.validate()` enforces: [1](#0-0) 

```
long delegateBalance = delegateResourceContract.getBalance();
if (delegateBalance < TRX_PRECISION) {
  throw new ContractValidateException("delegateBalance must be greater than or equal to 1 TRX");
}
```

A user builds up frozen resource (bandwidth/energy) via `FreezeBalanceV2Actuator`, which itself only enforces the 1 TRX minimum at freeze time, not on the resulting balance that later needs to be split/delegated: [2](#0-1) 

Once frozen, a user's `getFrozenV2BalanceForBandwidth()`/`getFrozenV2BalanceForEnergy()` can end up with a remainder smaller than 1 TRX after prior delegations, unfreeze operations, or usage accounting (e.g., available balance = `frozenV2Balance - v2NetUsage`, checked at): [3](#0-2) 

If that remaining frozen balance is below `TRX_PRECISION`, the account owner can never delegate it to any receiver — the `delegateBalance < TRX_PRECISION` check rejects the request regardless of whether the frozen balance actually exists and is otherwise fully valid for delegation. There is no compensating mechanism that lets the user consolidate or withdraw this dust; the only paths are (a) freeze additional TRX to push the remainder above 1 TRX, incurring an extra on-chain transaction and fee, or (b) leave the dust frozen and functionally unusable for delegation.

This is analogous to the reported `GiantPoolBase.withdrawETH` issue: an unconditional `require(_amount >= MIN_STAKING_AMOUNT)` check applied to an operation on an existing balance, which serves no protocol-integrity purpose (the balance is already validated/tracked on-chain) but can strand small remainders and force users into extra transactions/fees for no benefit.

### Impact Explanation
Users who accumulate small leftover frozen-resource balances (a normal byproduct of partial delegation/unfreeze cycles) cannot delegate that portion to any receiver. This is a funds/resource-usability impairment (denial of a legitimate on-chain function) and forces users to pay additional transaction fees to work around an artificial threshold that does not protect any consensus or accounting invariant (the underlying value is already tracked precisely in `long` units, not subject to precision loss).

### Likelihood Explanation
This condition arises naturally whenever a user delegates or unfreezes resources incrementally, which is a common usage pattern for TRON staking/delegation (via `FreezeBalanceV2Contract`, `DelegateResourceContract`, `UnDelegateResourceContract`, `UnfreezeBalanceV2Contract`). Any anonymous account can trigger and hit this condition through ordinary broadcast transactions, requiring no privileged role.

### Recommendation
Remove or relax the `delegateBalance < TRX_PRECISION` check in `DelegateResourceActuator.validate()`, or apply it only when it would leave a legitimate remaining frozen balance below `TRX_PRECISION` that is not going to be delegated in full (i.e., only enforce a minimum on the freeze operation itself, not on subsequent delegate/undelegate operations acting on an already-frozen balance). At minimum, allow delegating the full remaining frozen balance regardless of its size when that balance is less than 1 TRX, matching `UnDelegateResourceActuator`'s simpler `unDelegateBalance <= 0` check.

### Proof of Concept
1. Account A freezes 1.5 TRX for BANDWIDTH via `FreezeBalanceV2Contract` (passes the `>= 1 TRX` check in `FreezeBalanceV2Actuator`). [2](#0-1) 
2. Account A delegates 1.0 TRX of that frozen balance to Account B via `DelegateResourceContract` (passes the `delegateBalance < TRX_PRECISION` check). [1](#0-0) 
3. Account A now has 0.5 TRX of frozen bandwidth remaining (`FrozenV2BalanceForBandwidth - v2NetUsage` = 0.5 TRX), which is below `TRX_PRECISION`.
4. Account A attempts to delegate the remaining 0.5 TRX to Account C; the transaction is rejected with `"delegateBalance must be greater than or equal to 1 TRX"` even though the balance genuinely exists and is otherwise valid. [1](#0-0) 
5. Account A must freeze additional TRX (extra transaction and fee) just to be able to delegate the previously stranded 0.5 TRX.
