### Title
Node panic on disk-full (ENOSPC) during account append due to `.expect()` on `AppendVec::append_ptrs_locked` I/O error - ([File: accounts-db/src/append_vec.rs])

### Finding Description
`write_buffer_to_file` in `fs/src/file_io.rs` correctly handles the "no progress" write condition: when `arch_write_at` (`file.write_at`) returns `0` bytes written — the classic signal for `ENOSPC` (disk full) on Linux/Unix — it returns `Err(io::ErrorKind::WriteZero.into())` instead of looping forever or panicking. [1](#0-0) 

This error correctly propagates up through `AppendVec::append_ptr` via `?`: [2](#0-1) 

and through `AppendVec::append_ptrs_locked`, which also uses `?` and returns `io::Result<Option<usize>>`: [3](#0-2) 

However, the sole caller, `AppendVec::append_accounts`, does not handle this `Err` gracefully. It calls `.expect("must append data to append_vec")` directly on the `io::Result`: [4](#0-3) 

Any `Err` returned by `append_ptrs_locked` — including `WriteZero` produced by a disk-full condition — causes this `.expect()` to panic and crash the validator process. This is precisely the "unwrap-driven crash" scenario the question describes: the low-level I/O layer signals the error correctly (`WriteZero`), but the AccountsDb caller converts that recoverable error into a hard panic instead of backing off or surfacing a recoverable failure.

The reachable path from an unprivileged attacker is: a user creates/writes many accounts (controlling data sizes and write frequency, paying rent-exempt lamports for the space used) via normal transactions. These accounts flow through `AccountsDb::do_flush_slot_cache` → `store_accounts_for_flush` → `write_accounts_to_storage` → `AccountsFile::write_accounts` → `AppendVec::append_accounts`, ultimately calling `write_buffer_to_file`. [5](#0-4) 

If the node's disk approaches capacity (which an attacker can accelerate by paying for large, numerous accounts to inflate on-disk account storage), the very next `arch_write_at` call that cannot make progress returns `wrote_len == 0`, `write_buffer_to_file` returns `WriteZero`, and `append_accounts`'s `.expect()` panics the node — rather than allowing AccountsDb to retry, back off, or fail the block/slot gracefully.

### Impact Explanation
This is a node panic reachable through a resource-exhaustion path an unprivileged user can materially accelerate (by writing many/large rent-paid accounts to inflate account-storage disk usage over time). Once local disk space is exhausted, the very next account flush hits this `.expect()` and crashes the validator, rather than the intended graceful/recoverable error handling that `write_buffer_to_file` was designed to provide. This matches the "node panic" and "disproportionate storage cost" bounty impact categories, since normal AccountsDb code assumes write failures here are effectively "can't happen" and treats them as an invariant violation instead of a recoverable I/O condition.

### Likelihood Explanation
No privileged access is required — an attacker only needs to be a fee/rent-paying user who creates and writes many accounts to grow the validator's on-disk account storage footprint over time (this contributes toward, though does not solely cause, disk exhaustion, since other legitimate ledger/snapshot growth also consumes space). Once any write during account flush cannot make forward progress due to insufficient space, the crash is deterministic and 100% reproducible for any node in that low-disk-space state — there's no timing race or other precondition beyond "disk has no more free blocks to allocate."

### Recommendation
Change `AppendVec::append_accounts` (and any similar call site, e.g. `write_accounts_to_storage`'s `unwrap_or_else(|| panic!(...))` on write failure) to propagate the `io::Result` from `append_ptrs_locked` as a recoverable error instead of using `.expect()`/`panic!()`. AccountsDb callers (e.g., `do_flush_slot_cache`, `store_accounts_for_flush`) should be updated to handle this error path — e.g., halting further storage attempts, surfacing the error up to trigger a controlled shutdown, or backing off/retrying if transient — instead of crashing via an unwrap on a codepath that is documented (via `write_buffer_to_file`'s own comment and `WriteZero` semantics) to be a real, expected I/O failure mode.

pub fn write_buffer_to_file(
    file: &File,
    mut buffer: &[u8],
    mut offset: FileSize,
) -> io::Result<()> {
    while !buffer.is_empty() {
        let wrote_len = arch_write_at(file, buffer, offset)?;
        if wrote_len == 0 {
            return Err(io::ErrorKind::WriteZero.into());
        }
        buffer = &buffer[wrote_len..];
        offset += wrote_len as FileSize;
    }
    Ok(())
}

    fn append_ptrs_locked(
        &self,
        offset: &mut usize,
        vals: &[(*const u8, usize)],
    ) -> io::Result<Option<usize>> {
        let mut end = *offset;
        for val in vals {
            end = u64_align!(end);
            end += val.1;
        }

        if (self.file_size as usize) < end {
            return Ok(None);
        }

        let pos = u64_align!(*offset);
        for val in vals {
            self.append_ptr(offset, val.0, val.1)?
        }
        self.current_len.store(*offset, Ordering::Release);
        Ok(Some(pos))
    }
