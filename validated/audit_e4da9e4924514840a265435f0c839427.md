### Title
Unbounded-length numeric JSON fields cause disproportionate CPU cost in `Util.getJsonLongValue` before rejection - ([File: framework/src/main/java/org/tron/core/services/http/Util.java])

### Summary
`Util.getJsonLongValue` converts a JSON numeric field directly into a `BigDecimal` and calls `longValueExact()` without any bound on the digit count of the input string. [1](#0-0)  Any HTTP servlet that reads an amount-like field through this helper (e.g. `TransferServlet`, `WithdrawBalanceServlet`, `ProposalCreateServlet`, `MarketSellAssetServlet`) inherits this cost before the oversized value is finally rejected with an `ArithmeticException`.

### Finding Description
`getJsonLongValue(JSONObject jsonObject, String key, boolean required)` fetches the field via `jsonObject.getBigDecimal(key)` and immediately calls `bigDecimal.longValueExact()`. [1](#0-0)  Both `BigDecimal` construction from a string and `longValueExact()`'s internal range check require parsing/traversing the full digit sequence, and `BigInteger`/`BigDecimal` string-to-value conversion in the JDK has superlinear (roughly quadratic for very large inputs) cost. Because there is no explicit digit-count or string-length check on the raw value before it is handed to `BigDecimal`, a caller can supply a decimal string with a very large number of digits (e.g. hundreds of thousands) as `amount`, `frozen_balance`, `bandwidth`, or similar fields and force the servlet thread to spend CPU proportional (and potentially superlinear) to that length before the eventual `ArithmeticException`/"out-of-range" rejection.

The only backstop in the codebase is a global HTTP body-size guard (`SizeLimitHandler` / `CommonParameter.getHttpMaxMessageSize`, wired in `HttpService`), which limits the overall request payload, not the length of any individual numeric field. [2](#0-1)  This means an attacker is still free to put the bulk of the allowed message size (which defaults to hundreds of kilobytes depending on configuration) into a single numeric field, since there is no field-level length validation in `getJsonLongValue` or its call sites (`TransferServlet`, `WithdrawBalanceServlet`, `ProposalCreateServlet`, `MarketSellAssetServlet`).

### Impact Explanation
This is a CPU-cost amplification issue: an unprivileged, unauthenticated caller of a broadcast-adjacent HTTP endpoint (transaction construction, not requiring a signed/valid transaction) can force disproportionate CPU consumption per request relative to the bytes sent, by embedding an oversized digit string in a numeric field. Repeated requests could degrade responsiveness of the HTTP API layer. It does not lead to unauthorized execution, fund theft, or consensus divergence — the affected servlets only build/print transactions or estimate fees; the impact is scoped to public API/node availability degradation.

### Likelihood Explanation
Feasibility is high in principle (a single JSON POST with a very long numeric string), but the practical severity is constrained by the existing global HTTP message-size limit, which bounds the maximum digit count any single field can reach in one request. Whether this limit is small enough to make the per-request CPU delta negligible could not be conclusively determined from the code inspected (the exact default/configured value of `httpMaxMessageSize` and JDK version's `BigInteger` string-parsing complexity were not fully verified here). Absent a field-specific length cap, the amplification is real but its magnitude is bounded by that global body-size setting rather than being unbounded.

### Recommendation
Add an explicit length bound (e.g., reject strings longer than the maximum meaningful digit count for a valid `long`, such as ~20 characters) on numeric string values before constructing a `BigDecimal` in `Util.getJsonLongValue`, or validate digit-count cheaply prior to parsing. This closes the gap regardless of the global body-size configuration.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/services/http/UtilTest.java (illustrative addition)
@Test
public void testGetJsonLongValueLargeDigitString() {
  JSONObject jsonObject = new JSONObject();
  StringBuilder sb = new StringBuilder();
  for (int i = 0; i < 200_000; i++) {
    sb.append('9');
  }
  jsonObject.put("amount", sb.toString());

  long start = System.nanoTime();
  try {
    Util.getJsonLongValue(jsonObject, "amount", true);
    Assert.fail("expected ArithmeticException for out-of-range value");
  } catch (ArithmeticException expected) {
    // expected: value out of long range
  }
  long elapsedMs = (System.nanoTime() - start) / 1_000_000;

  // Assert parsing did not take disproportionate time relative to a bound,
  // e.g. fail if elapsedMs exceeds a small threshold (demonstrates current lack of guard).
  Assert.assertTrue("BigDecimal parsing of oversized numeric string took too long: "
      + elapsedMs + "ms", elapsedMs < 50);
}
```
This test demonstrates that `getJsonLongValue` performs full `BigDecimal` parsing on an attacker-controlled, arbitrarily long digit string before rejecting it, with no field-level length guard in place.
