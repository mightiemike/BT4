### Title
Division-before-multiplication truncation in legacy `calculateGlobalEnergyLimit()` under-computes frozen-energy allowance - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
The reported ARCH-token bug (`(leverageAmount / _archToLevRatio) * 1 ether`) performs integer division before multiplication, truncating the result and under-crediting the user. The same arithmetic-ordering defect is present in java-tron's legacy (non-hardened) resource-limit formula in `EnergyProcessor.calculateGlobalEnergyLimit()`, which is still reachable whenever the `allowHardenResourceCalculation` chain parameter is not active.

### Finding Description
`calculateGlobalEnergyLimit()` truncates `frozeBalance` by integer-dividing it by `TRX_PRECISION` *before* multiplying by the limit/weight ratio: [1](#0-0) 

```java
if (hardenCalculation()) {
  return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
}
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```

This mirrors the audited pattern exactly: `frozeBalance / TRX_PRECISION` is an early, lossy integer division analogous to `leverageAmount / _archToLevRatio`, and the fractional remainder of `frozeBalance` (anything below `TRX_PRECISION`, i.e. below 1 TRX) is silently discarded before the ratio is ever applied. The codebase's own hardening work acknowledges this: the replacement `calculateGlobalLimitV1`/`calculateGlobalLimitV2` in `ResourceProcessor.java` explicitly documents preserving "fractional weight ... through the multiplication and only truncat[ing] at the final divide" — the opposite, correct order of operations: [2](#0-1) 

and a dedicated regression test computes the "buggy" legacy value and asserts it differs from the hardened one: [3](#0-2) 

```java
long expected = java.math.BigInteger.valueOf(10000L)
    .multiply(java.math.BigInteger.valueOf(totalEnergyLimit))
    .divide(java.math.BigInteger.valueOf(totalEnergyWeight))
    .longValueExact();
Assert.assertEquals(expected, resultNew);
Assert.assertEquals(resultOld, resultNew);

long buggy = 10000L * (totalEnergyLimit / totalEnergyWeight);
Assert.assertNotEquals(buggy, resultNew);
```

Whether this legacy path is active depends entirely on the `allowHardenResourceCalculation` runtime flag, which is loaded through `ConfigLoader`/`VMConfig` and is expected to be governed by a committee proposal (the same mechanism used for other `allow*` hard-fork flags): [4](#0-3) [5](#0-4) 

Until that proposal is activated on a given network, `hardenCalculation()` returns `false` and the truncating legacy formula in `EnergyProcessor.calculateGlobalEnergyLimit()` (and the equivalent duplicated logic in `RepositoryImpl.calculateGlobalEnergyLimit()`) is the one actually used for computing an account's frozen-energy allowance: [6](#0-5) 

### Impact Explanation
`calculateGlobalEnergyLimit()` feeds directly into `getAccountLeftEnergyFromFreeze()`, which determines how much free/frozen energy a caller or contract creator can use for a transaction: [7](#0-6) 

and the same value flows into `VMActuator.getAccountEnergyLimitWithFixRatio()` / `getAccountEnergyLimitWithFloatRatio()`, which set `energyLimit` for a transaction's actual VM execution: [8](#0-7) 

Because the early division discards the sub-`TRX_PRECISION` remainder of `frozeBalance`, any account whose frozen balance is not an exact multiple of `TRX_PRECISION` (1,000,000 sun) is systematically under-credited relative to its true proportional share of network energy — this is a real, protocol-level accounting inaccuracy (loss of legitimately owned resource entitlement), not a cosmetic rounding issue, and it applies to every account on the network whenever the harden flag is off. This is directly analogous to a user being under-supplied resources they are entitled to, as in the original ARCH finding.

### Likelihood Explanation
This code path executes on every call to `calculateGlobalEnergyLimit()`/`getAccountLeftEnergyFromFreeze()` for any account with non-round frozen balances, which is the default/common case for real users, and requires no special privilege or interaction — it triggers automatically as part of ordinary resource accounting whenever `allowHardenResourceCalculation` is not yet enabled on the chain. The severity is bounded because the loss per account is small (at most just under 1 unit of `energyWeight` per calculation) and the project has already built (but apparently not yet defaulted-on) a fix.

### Recommendation
Ensure `allowHardenResourceCalculation` is activated (or make the corrected `calculateGlobalLimitV1`/`V2` order-of-operations the unconditional default) so the legacy truncating formula in `EnergyProcessor.calculateGlobalEnergyLimit()` and `RepositoryImpl.calculateGlobalEnergyLimit()` is never exercised in production; alternatively, remove the legacy branch entirely and always multiply before dividing (or use `BigInteger`/`divideCeil`-style exact arithmetic) as already done in `calculateGlobalLimitV1`/`calculateGlobalLimitV2`.

### Proof of Concept
Given `frozeBalance = 1_500_000` sun (1.5 TRX), `TRX_PRECISION = 1_000_000`, `totalEnergyLimit = 50_000_000_000`, `totalEnergyWeight = 1_000_000`:
- Legacy path: `energyWeight = 1_500_000 / 1_000_000 = 1` (truncated from 1.5), then `1 * (50_000_000_000.0/1_000_000) = 50_000` energy.
- Correct (hardened) path: `(1_500_000 * 50_000_000_000) / (1_000_000 * 1_000_000) = 75_000` energy.

The account is under-credited by 25,000 energy (33%) purely due to the early integer division, confirmed by the project's own test in `RepositoryImplHardenTest.testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio` which explicitly asserts `buggy != resultNew`. [9](#0-8)

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
```

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
```

  public long getAccountEnergyLimitWithFixRatio(AccountCapsule account, long feeLimit,
      long callValue) {

    long sunPerEnergy = VMConstant.SUN_PER_ENERGY;
    if (rootRepository.getDynamicPropertiesStore().getEnergyFee() > 0) {
      sunPerEnergy = rootRepository.getDynamicPropertiesStore().getEnergyFee();
    }

    long leftFrozenEnergy = rootRepository.getAccountLeftEnergyFromFreeze(account);
    if (VMConfig.allowTvmFreeze() || VMConfig.allowTvmFreezeV2()) {
      receipt.setCallerEnergyLeft(leftFrozenEnergy);
    }

    long energyFromBalance = max(account.getBalance() - callValue, 0,
        VMConfig.disableJavaLangMath()) / sunPerEnergy;
    long availableEnergy = addExact(leftFrozenEnergy, energyFromBalance,
        VMConfig.disableJavaLangMath());

    long energyFromFeeLimit = feeLimit / sunPerEnergy;
    if (VMConfig.allowTvmFreezeV2()) {
      long now = rootRepository.getHeadSlot();
      EnergyProcessor energyProcessor =
          new EnergyProcessor(
              rootRepository.getDynamicPropertiesStore(),
              ChainBaseManager.getInstance().getAccountStore());
      energyProcessor.updateUsage(account);
      account.setLatestConsumeTimeForEnergy(now);
      receipt.setCallerEnergyUsage(account.getEnergyUsage());
      receipt.setCallerEnergyWindowSize(account.getWindowSize(ENERGY));
      receipt.setCallerEnergyWindowSizeV2(account.getWindowSizeV2(ENERGY));
      account.setEnergyUsage(
          energyProcessor.increase(account, ENERGY,
              account.getEnergyUsage(), min(leftFrozenEnergy, energyFromFeeLimit,
                  VMConfig.disableJavaLangMath()), now, now));
      receipt.setCallerEnergyMergedUsage(account.getEnergyUsage());
      receipt.setCallerEnergyMergedWindowSize(account.getWindowSize(ENERGY));
      rootRepository.updateAccount(account.createDbKey(), account);
    }
    return min(availableEnergy, energyFromFeeLimit, VMConfig.disableJavaLangMath());
