In contrast, the TVM native-contract counterpart `UnfreezeBalanceProcessor.execute()` calls `VoteRewardUtil.withdrawReward(ownerAddress, repo)` only conditionally — inside an `if (VMConfig.allowTvmVote() && !accountCapsule.getVotesList().isEmpty())` block, and only when `accountCapsule.getTronPower() < usedTronPower * TRX_PRECISION` — and it is invoked *after* `repo.updateAccount(...)` has already persisted the reduced frozen balance/`tronPower`.

### Title
Reward snapshot (`VoteRewardUtil.withdrawReward`) skipped/deferred in TVM `UnfreezeBalanceProcessor`, allowing vote-reward gain/loss analogous to esLBR `refreshReward()` bypass - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java)

### Summary
`UnfreezeBalanceProcessor.execute()` is the TVM-precompiled equivalent of `UnfreezeBalanceActuator` (invoked from within smart-contract execution when `VMConfig.allowTvmFreeze()`/`allowTvmVote()` are active). Unlike the plain actuator, it does not unconditionally call `VoteRewardUtil.withdrawReward()` before changing frozen balance and (potentially) tron power. Instead the reward/vote reconciliation only fires deep inside a conditional branch, after the account's balance and frozen state have already been persisted.

### Finding Description
Compare the two code paths:
- `UnfreezeBalanceActuator.execute()` (actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java:74) calls `mortgageService.withdrawReward(ownerAddress)` first, unconditionally, before any frozen/balance mutation — matching the pattern used everywhere else (`VoteWitnessActuator` line 161, `UnfreezeBalanceV2Actuator` line 72, `UnfreezeBalanceV2Processor` line 121, `VoteWitnessProcessor` line 41): reward is always snapshotted before the state that affects future reward accrual changes.
- `UnfreezeBalanceProcessor.execute()` (actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java:104-227) instead:
  1. Mutates `accountCapsule` balance/frozen lists (lines 108-188).
  2. Persists it via `repo.updateAccount(...)` (line 203).
  3. Only *then*, checks `if (VMConfig.allowTvmVote() && !accountCapsule.getVotesList().isEmpty())` and, only if the account's remaining `tronPower` is now insufficient to cover its cast votes, calls `VoteRewardUtil.withdrawReward(ownerAddress, repo)` (line 211) — i.e., the reward snapshot/allowance settlement is conditionally skipped entirely whenever the account still has enough remaining `tronPower` after unfreezing to cover its votes.

This mirrors the reported bug class: the reward-affecting balance/weight mutation (unfreeze reducing `tronPower`/frozen weight) is decoupled from the mandatory reward snapshot (`withdrawReward`/`refreshReward` analog). A user (or a contract calling the TVM unfreeze precompile) can repeatedly unfreeze/refreeze balance through the TVM path without ever triggering `withdrawReward`, as long as remaining `tronPower` stays ≥ the vote count, deferring the cycle-based reward snapshot (`delegationStore`/`repository.updateAccountVote`) to an arbitrary later point chosen by the caller (e.g. right after a large batch of `payReward`/Vi updates favorable to them, or right before an unfavorable one for a victim, since anyone can trigger reward finalization for any address indirectly through later actions).

### Impact Explanation
`VoteRewardUtil.withdrawReward` is the sole mechanism that finalizes and snapshots per-cycle vote rewards (`repository.updateAccountVote`, `adjustAllowance`) based on the account's current vote/tronPower state. Because the TVM unfreeze path can skip this call while still mutating the underlying frozen/tronPower state that reward accrual depends on, an attacker can manipulate the timing of when their vote-weighted `Vi`-based reward is captured relative to state changes, potentially inflating their own allowance or, when triggered by a third party's subsequent action, causing another account's pending reward computation to use a stale/altered vote snapshot. This is a resource/reward accounting corruption reachable purely through a normal contract-invoked TVM unfreeze operation (`allowTvmFreeze`/`allowTvmVote`), not requiring any privileged role.

### Likelihood Explanation
Reachable by any account/contract that calls the TVM unfreeze-balance precompiled contract while holding votes and while `allowTvmVote`/`allowTvmFreeze` are enabled (both are standard mainnet feature flags). The conditional skip is a deterministic function of the account's own vote count vs. remaining tronPower, so an attacker can reliably arrange for `withdrawReward` to be skipped by simply keeping votes below the tronPower threshold after unfreezing (e.g., partially unfreeze, or vote for a small amount).

### Recommendation
Make `VoteRewardUtil.withdrawReward(ownerAddress, repo)` mandatory at the start of `UnfreezeBalanceProcessor.execute()`, mirroring `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Processor`/`VoteWitnessProcessor`, instead of conditionally invoking it after the balance/frozen state mutation. Remove the dependency of the reward snapshot on the `usedTronPower` check so reward finalization is unconditionally tied to the balance-changing action.

### Proof of Concept
Conceptual PoC (mirrors the esLBR mint/burn PoC pattern):
1. Attacker account freezes balance and votes for a witness such that `usedTronPower` is comfortably below `tronPower` (e.g., votes for only half of available power).
2. Attacker triggers the TVM unfreeze precompile (`UnfreezeBalanceProcessor.execute`) for a portion of frozen balance small enough that remaining `tronPower` still covers `usedTronPower`; `VoteRewardUtil.withdrawReward` is never invoked (line 210's condition is false), so no cycle reward snapshot is taken even though the account's backing weight has shrunk.
3. Attacker repeats step 2 across multiple cycles/blocks, accumulating reward-relevant weight changes without any `withdrawReward` snapshot, then finally calls `WithdrawRewardProcessor`/`VoteWitnessProcessor` (which call `withdrawReward` unconditionally) at a moment chosen to maximize the `computeReward` result versus a victim whose own pending reward was already snapshotted earlier at an unfavorable rate — exactly as in the original esLBR `testMintFailRefreshReward`/`testBurnFailRefreshReward` scenarios where deferring the mandatory accounting call produces a reward-timing advantage/disadvantage.   public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }
