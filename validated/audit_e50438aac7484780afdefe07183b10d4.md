### Title
Unbounded `WitnessStore.getAllWitnesses()` serialization in `ListWitnessesServlet`/`Wallet.getWitnessList()` allows attacker-funded witness-count inflation to cause unbounded per-request CPU/memory work - ([File: `framework/src/main/java/org/tron/core/services/http/ListWitnessesServlet.java`])

### Summary
`WitnessCreateActuator.validate()` imposes no cap on the total number of witnesses that can be created network-wide, only requiring the calling account's balance to exceed `getAccountUpgradeCost()`. `Wallet.getWitnessList()`, reachable from the public `GET /wallet/listwitnesses` endpoint (and the equivalent gRPC `ListWitnesses` call), unconditionally serializes the *entire* `WitnessStore.getAllWitnesses()` result with no page/size limit, unlike the sibling `getPaginatedNowWitnessList` which is explicitly capped at `WITNESS_COUNT_LIMIT_MAX`.

### Finding Description
`WitnessCreateActuator.validate()` at [1](#0-0)  only checks that the witness address doesn't already exist and that `accountCapsule.getBalance() >= dynamicStore.getAccountUpgradeCost()`. There is no per-account or global cap on the number of `WitnessCreateContract` transactions that can succeed, so an attacker with N funded addresses can broadcast N independent `WitnessCreateContract` transactions and each will create a permanent entry in `WitnessStore`, as done in `createWitness()` at [2](#0-1) .

`ListWitnessesServlet.doGet` is a public, unauthenticated HTTP GET endpoint that calls `wallet.getWitnessList()` directly with no offset/limit parameters: [3](#0-2) 

`Wallet.getWitnessList()` fetches and serializes the *complete* witness list with no size bound: [4](#0-3) 

This contrasts directly with `Wallet.getPaginatedNowWitnessList`, which explicitly caps `limit` at `WITNESS_COUNT_LIMIT_MAX` before doing any work: [5](#0-4) 

The only mitigating control on the servlet is `RateLimiterServlet`, which enforces a QPS-style permit/token limiter per endpoint and a global limiter — it bounds *request rate*, not the *amount of work per request*: [6](#0-5) 

Because the per-request cost of `/wallet/listwitnesses` scales linearly with the total number of stored witnesses, and that number is attacker-inflatable at a one-time on-chain cost (`AccountUpgradeCost` per witness), the attacker converts a bounded, one-time payment into unbounded, repeatable, free public-API CPU/memory/bandwidth cost for every future caller of this endpoint (and the sibling `ListWitnesses` gRPC and PBFT/Solidity variants which all delegate to the same `Wallet.getWitnessList()` / unbounded `getAllWitnesses()`), as seen in `RpcApiService.WalletSolidityApi.listWitnesses` at [7](#0-6)  and the PBFT/Solidity HTTP wrappers at [8](#0-7) .

No auth, accounting, or per-response-size guard exists to stop this: rate limiting throttles calls/second, not payload size; `WitnessCreateActuator` charges a fee for creation but does not cap total witness count.

### Impact Explanation
Once N witness records exist in `WitnessStore`, every call (from any unprivileged caller, not just the attacker) to `/wallet/listwitnesses` (HTTP), `ListWitnesses` (gRPC full/solidity/PBFT) triggers O(N) DB reads and protobuf/JSON serialization work. Repeated calls (each within normal QPS limits) impose sustained CPU, memory (large `WitnessList` object graphs), and bandwidth cost on the full node, degrading service for all public API callers — a persistent, low-cost, amplifying DoS vector.

### Likelihood Explanation
Feasible with only public transaction broadcast capability: an attacker funds N addresses each with balance ≥ `AccountUpgradeCost` (a fixed, one-time, non-privileged network parameter), broadcasts N `WitnessCreateContract` transactions (one per address, since `witnessStore.has(ownerAddress)` only blocks re-registering the *same* address), and then repeatedly issues free, unauthenticated GET requests. This is fully repeatable and does not require any admin/governance action, leaked keys, or off-chain access — witness records are also permanent (no deletion path visible in this actuator), so the inflated cost is permanent once achieved.

### Recommendation
Apply a hard cap (e.g., `WITNESS_COUNT_LIMIT_MAX` or similar) to `Wallet.getWitnessList()`/`ListWitnessesServlet` analogous to `getPaginatedNowWitnessList`, or convert `ListWitnesses`/`listwitnesses` into a paginated-only API and deprecate/limit the unbounded variant. Additionally, consider adding a maximum total witness count enforced in `WitnessCreateActuator.validate()` to bound worst-case state growth.

```java
@Test
public void testUnboundedListWitnessesGrowsWithWitnessCount() throws Exception {
  int[] sizes = {100, 5000, 50000};
  long[] elapsedNanos = new long[sizes.length];

  for (int i = 0; i < sizes.length; i++) {
    // Seed WitnessStore with sizes[i] witness capsules directly bypassing consensus
    // (simulating outcome of sizes[i] successful WitnessCreateContract broadcasts)
    for (int j = 0; j < sizes[i]; j++) {
      WitnessCapsule w = new WitnessCapsule(
          ByteString.copyFromUtf8("fake_witness_" + i + "_" + j), 0, "url");
      chainBaseManager.getWitnessStore().put(w.createDbKey(), w);
    }

    MockHttpServletRequest request = new MockHttpServletRequest();
    MockHttpServletResponse response = new MockHttpServletResponse();

    long start = System.nanoTime();
    listWitnessesServlet.doGet(request, response);
    elapsedNanos[i] = System.nanoTime() - start;

    Assert.assertEquals(200, response.getStatus());
  }

  // Assert response time grows roughly linearly / unbounded with N,
  // in contrast to getPaginatedNowWitnessList which is capped.
  Assert.assertTrue("Serialization time should scale with witness count, showing no cap",
      elapsedNanos[2] > elapsedNanos[1] && elapsedNanos[1] > elapsedNanos[0]);

  // Compare with GetPaginatedNowWitnessListServlet under same seeded state:
  // its response size/time should be capped regardless of N due to WITNESS_COUNT_LIMIT_MAX.
}
```
Expected assertion: `ListWitnessesServlet` response time/size scales with the number of seeded witnesses without any upper bound, whereas `GetPaginatedNowWitnessListServlet.fillResponse` remains bounded by `WITNESS_COUNT_LIMIT_MAX` regardless of `N`, demonstrating the missing cost/response-size cap.

```java
    String contextPath = req.getContextPath();

    // break downstream servlets that read it themselves.
```
