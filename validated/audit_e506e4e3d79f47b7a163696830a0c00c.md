### Title
Session cookie overwrite across shops due to domain-wide cookie path in non-embedded OAuth callback - (File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts)

### Summary
The OAuth `callback` handler in `shopify-api` writes the `shopify_app_session` cookie using a `path` that defaults to `/` (domain-wide) unless the app developer explicitly opts in to a per-shop `cookiePath`. This mirrors the CidNFT "overwrite without checking prior state" bug class: the code performs a direct write of new session identifying data (`session.id`) into a shared storage slot (the browser cookie) without checking or preserving any previously-stored value for a different shop, silently clobbering it.

### Finding Description
In the OAuth callback flow for non-embedded apps, after a successful token exchange the library sets the session cookie like this: [1](#0-0) 

`cookiePath` defaults to `'/'` when not configured, and the cookie name `SESSION_COOKIE_NAME` (`shopify_app_session`) is constant/shared regardless of which shop authenticated: [2](#0-1) 

Because the cookie is scoped to the whole domain by default, if a browser (or a specific user) completes OAuth for shop A and later (or in another tab) completes OAuth for shop B against the same app domain, the second `setAndSign(SESSION_COOKIE_NAME, ...)` call silently overwrites the first shop's cookie value — analogous to `cidData[...].ordered[_key] = _nftIDToAdd` overwriting a prior value without any existence check in the CidNFT report. This was acknowledged directly by the maintainers in the config documentation and changelog as a known collision: [3](#0-2) [4](#0-3) 

The remediation shipped is an **opt-in** `cookiePath` factory (`cookiePath: (session) => \`/shops/${session.shop}/\``); the default behavior (`path: '/'`) remains vulnerable to overwrite for any app that has not explicitly configured this option, which is the majority of existing non-embedded, multi-tab/multi-shop deployments.

### Impact Explanation
When the cookie is overwritten, a browser tab that previously held an authenticated session for shop A will silently start using shop B's session id for all subsequent requests referencing `shopify_app_session`, without any error or re-authentication prompt. This is a cross-tenant session confusion condition: a user's browser context can end up bound to the wrong shop's session, and the original shop's session becomes orphaned in `SessionStorage` (unreachable via cookie, similar to the "trapped forever" NFT in the analog) even though it's still valid/active server-side, extending exposure. In multi-shop non-embedded app scenarios this can result in actions or data intended for one shop leaking into or being executed against another shop's session context in the same browser.

### Likelihood Explanation
This triggers under normal (non-attacker) usage whenever a single browser is used to authenticate more than one shop against a non-embedded app that has not set `cookiePath` — a default configuration. No privileged access or secret leakage is required; it can also be induced by a malicious actor tricking a victim into completing OAuth for an attacker-controlled/second shop domain in the same browser (since `path: '/'` and same-origin cookie scoping do not distinguish shop), causing the victim's existing session cookie for their real shop to be overwritten.

### Recommendation
Change the default `cookiePath` behavior so the session cookie is scoped per-shop by default (e.g., derive a shop-specific path automatically, or make `cookiePath` mandatory for non-embedded apps), rather than relying on developers to opt in. At minimum, emit a runtime warning when `isEmbeddedApp` is `false` and `cookiePath` is left at the domain-wide default, and document this prominently as a security-relevant setting rather than a cosmetic one.

### Proof of Concept
1. Configure a non-embedded app without setting `cookiePath` (default `'/'`).
2. In one browser, complete OAuth for `shop-a.myshopify.com` — cookie `shopify_app_session` is set at `path: '/'` referencing session id `A`, per `packages/apps/shopify-api/lib/auth/oauth/oauth.ts:219-230`.
3. In the same browser, complete OAuth for `shop-b.myshopify.com` against the same app host — the `cookies.setAndSign(SESSION_COOKIE_NAME, session.id, {..., path: '/'})` call overwrites the existing cookie value with session id `B`.
4. Any tab/request that still references shop A's context now presents cookie value `B`, resolving to shop B's session — silently switching tenant context without any error, consistent with the maintainers' own changelog description of "authenticating a new shop would silently overwrite the previous shop's session."

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
