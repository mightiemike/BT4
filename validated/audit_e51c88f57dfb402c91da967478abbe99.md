### Title
Legitimate Stake::Split or Stake::Withdraw during the reward-distribution window triggers a deterministic `assert_eq!` panic in `Bank::build_updated_stake_reward` - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`Bank::build_updated_stake_reward` compares a `PartitionedStakeReward` frozen at the calculation-phase block against the *live* `StakesCache` entry at distribution time, asserting `stake.delegation.stake + stake_reward == new_stake.delegation.stake`. Nothing in `store_stake_accounts_in_partition`, `distribute_epoch_rewards_in_partition`, or the stake program prevents an ordinary staker from submitting `Stake::Split` (or, in restricted cases, `Withdraw`) on their own already-rewarded stake account between the calculation block and their assigned partition/distribution block, which changes `delegation.stake` in the live cache and desynchronizes it from the frozen reward record.

### Finding Description
`Bank::begin_partitioned_rewards` (called from `process_new_epoch` at the epoch boundary) computes `PartitionedStakeReward` for every delegated stake account using the `StakesCache` snapshot as of that block, and stores it as `EpochRewardPhase::Calculation`/`Distribution` (`runtime/src/bank/partitioned_epoch_rewards/mod.rs:146-177`). The `inflation.stake` field freezes `delegation.stake_at_calc_time + stake_reward` (see `test_calculate_stake_vote_rewards`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:2390-2405`, where `stake.delegation.stake += stake_reward`).

Distribution happens over multiple subsequent blocks. Each block calls `distribute_partitioned_epoch_rewards` → `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:78-224, 336-423`), which re-reads the account from the *current, live* `self.stakes_cache.stakes()` (line 361-362) rather than from a frozen snapshot, and passes it into `Bank::build_updated_stake_reward` (lines 239-325):

Nothing gates ordinary stake-program instructions during the reward interval: `test_rewards_period_system_transfer` in `runtime/src/bank/partitioned_epoch_rewards/mod.rs:1082-1165` explicitly documents that transfers/transactions continue to be processed normally throughout the epoch-boundary/reward interval, and `RewardInterval`/`get_reward_interval` is only a test-module helper enum (`runtime/src/bank/partitioned_epoch_rewards/mod.rs:534-564`) with no enforcement in production transaction processing (`runtime/src/bank/check_transactions.rs`, `runtime/src/bank.rs:4026-4059`) that blocks stake instructions.

The stake program's `Split` instruction is a normal, signed, self-service instruction that reduces `delegation.stake` on the source account for an active/activating delegation while creating a second delegated stake account (documented client-side usage in `cli/src/stake.rs:1994-2145`, and used routinely to split active stakes as in `cli/tests/stake.rs:1569-1735`). If a staker calls `Split` on their own delegated stake account for pubkey `P` after `P`'s `PartitionedStakeReward` has already been calculated/cached but before `P`'s partition/block is processed by `store_stake_accounts_in_partition`, the live `StakesCache` entry for `P` will have a *lower* `delegation.stake` than the value baked into `partitioned_stake_reward.inflation.stake`. When `build_updated_stake_reward` runs for `P` (with `adjust_delegations_for_rent == false`, i.e., `relax_post_exec_min_balance_check` inactive), `expected_delegation` (computed from the now-reduced live stake plus the reward) will not equal `new_stake.delegation.stake` (the frozen calculated value), and the `assert_eq!` panics.

This panic occurs inside normal block replay/execution logic that every validator runs identically and deterministically (it is driven by on-chain account state, not by any single validator's private inputs), so it is not merely a single-node crash but a consensus-halting event when the offending block is processed across the cluster.

### Impact Explanation
A successful trigger causes a Rust `panic!` inside `Bank::build_updated_stake_reward`, invoked from the mandatory per-block `distribute_partitioned_epoch_rewards` path that every validator executes while replaying/producing blocks during the reward-distribution window. Because the panic is deterministic given the on-chain state (the attacker's own signed `Split`/`Withdraw` plus the cached reward), all validators that reach this code with the same ledger state will panic identically — this is a cluster-wide liveness halt (denial of service), matching the "cluster-halting panic" bounty category. No funds are stolen and no consensus divergence occurs (all nodes panic the same way rather than disagreeing), but block production/validation for the network stops.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: a funded keypair, an actively delegated stake account, and the reward-distribution multi-block window with `relax_post_exec_min_balance_check` inactive (the `adjust_delegations_for_rent = false` branch, which is/was the default/legacy behavior prior to that feature's activation). The attacker needs only to:
1. Delegate stake normally.
2. Wait for the epoch-boundary calculation block to cache their `PartitionedStakeReward`.
3. Submit a signed `Stake::Split` (self-to-self, moving any nonzero amount) on their own stake account before their account's designated partition/distribution block is processed.

The cost is a single stake-program transaction fee; the attack is fully repeatable each epoch boundary while the vulnerable code path/feature configuration is live, and requires no validator, leader, or network-level access — only normal RPC/TPU transaction submission.

### Recommendation
`Bank::build_updated_stake_reward` must not assume the live `StakesCache` entry is unchanged since the calculation phase. Options:
- Recompute/verify the reward against a value derived only from the frozen calculation state, not from re-reading the current live delegation, when checking consistency in the `adjust_delegations_for_rent == false` branch.
- Alternatively, detect discrepancies between the calculated `PartitionedStakeReward` and the current stake account state and gracefully handle them (e.g., recalculate the reward the way `adjust_delegations_for_rent == true` does, or burn/skip the reward and log an error rather than asserting), instead of panicking.
- Consider disallowing stake-account-shape-changing instructions (`Split`, `Withdraw`, `Merge`, `Deactivate`) for accounts with a pending cached `PartitionedStakeReward`, or recalculate rewards per-partition immediately before applying them (similar to `recalculate_partitioned_rewards_if_active` used after snapshot restore) so that live mutations can't desynchronize the frozen reward record from the current delegation.

        /// Return `RewardInterval` enum for current bank
        fn get_reward_interval(&self) -> RewardInterval {
            if matches!(self.epoch_reward_status, EpochRewardStatus::Active(_)) {
                RewardInterval::InsideInterval
            } else {
                RewardInterval::OutsideInterval
            }
