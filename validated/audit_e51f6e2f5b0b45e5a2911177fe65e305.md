### Title
Missing MessageId uniqueness check in `HandleLegacyUserMessage` allows callback slot overwrite / response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` inserts a new entry into `h.savedCallbacks` keyed solely by `msg.Body.MessageId` without checking whether an entry for that ID already exists. If two in-flight requests share the same `MessageId` (e.g., attacker replays/guesses another user's still-pending ID within `MaxAllowedMessageAgeSec`), the second insertion silently overwrites the first caller's stored `handlers.Callback`, so the DON node's eventual trigger response is delivered to the wrong caller.

### Finding Description
`HandleLegacyUserMessage` decodes the incoming `webapicap.TriggerRequestPayload`, validates staleness against `payload.Timestamp` and `h.config.MaxAllowedMessageAgeSec`, and then unconditionally stores the callback: [1](#0-0) 

There is no check of `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { ... }` before the map write. The staleness check only rejects messages that are *too old*; it does nothing to prevent two distinct requests with the same `MessageId` and a *valid* (non-stale) timestamp from being processed concurrently: [2](#0-1) 

When a node responds via `MethodWebAPITrigger`, the handler looks up and deletes exactly one entry by `MessageId` and routes the response to whatever `savedCallback` is currently stored under that key: [3](#0-2) 

If the legitimate caller's entry is overwritten by an attacker's second call using the same `MessageId` before the DON responds, the eventual `SendResponse` call is delivered to the attacker's callback (or vice versa, the attacker's forged/duplicate request response is delivered to the original legitimate caller), producing cross-request response confusion. The original caller's request is effectively orphaned (its callback reference is lost, so it will never receive a response and will presumably time out), while the second submitter receives a response tied to a `MessageId` that was not exclusively theirs.

### Impact Explanation
This is a response/callback confusion issue: an unprivileged attacker who can predict or observe another user's in-flight `MessageId` can overwrite that user's callback slot, causing the user's HTTP-triggered workflow response to be redirected to the attacker instead, and/or causing the original caller to silently lose their response. Depending on payload content (e.g., trigger data forwarded via `don.SendToNode`), this could expose response data intended for another caller — an indirect information-disclosure / cross-tenant response confusion issue rather than a direct secret leak, since the attacker still needs a valid, colliding `MessageId` to trigger the condition.

### Likelihood Explanation
Exploitability depends entirely on how `MessageId` is generated/assigned upstream of `HandleLegacyUserMessage` (e.g., whether it is client-supplied and predictable, or gateway-generated with high entropy such as a UUID). This code path itself performs no uniqueness enforcement, so if `MessageId` generation is ever predictable, sequential, or derived from user-observable data (as could occur in some legacy/external-initiator integrations), the race is easy to trigger deterministically by an unprivileged client submitting two requests with the same ID inside the `MaxAllowedMessageAgeSec` window. I was not able to fully trace the exact call site(s) that construct `msg.Body.MessageId` for legacy user messages in the time available, so the actual attacker-controllability of `MessageId` (a precondition explicitly stated in the question) remains unverified from this codebase alone.

### Recommendation
Add an explicit collision check under the existing `h.mu` lock before inserting into `h.savedCallbacks` in `HandleLegacyUserMessage`: if an entry for `msg.Body.MessageId` already exists (and has not expired), reject the new request with a distinct error response (e.g., `api.HandlerError`, "duplicate message id") instead of overwriting the map entry. Additionally, ensure `MessageId` values are gateway-generated (not client-controlled) or bound to a unique per-caller/session identifier to prevent collisions from being attacker-influenced.

### Proof of Concept
Unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two distinct `handlers.Callback` mocks, `callbackA` and `callbackB`.
2. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` with a valid, non-stale `webapicap.TriggerRequestPayload` and `msg.Body.MessageId = "dup-id"`; assert it succeeds and `h.savedCallbacks["dup-id"].Callback == callbackA`.
3. Before delivering any node response, call `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` with the same `MessageId = "dup-id"` (simulating replay/guess) and a valid timestamp.
4. Assert that the second call returns an error (e.g., "duplicate message id in flight") and that `h.savedCallbacks["dup-id"].Callback` still equals `callbackA` — i.e., no overwrite occurred.
5. Currently (pre-fix), assert (to demonstrate the bug) that step 3 succeeds without error and `h.savedCallbacks["dup-id"].Callback == callbackB`, proving `callbackA` was silently discarded and would never receive its trigger response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
