## Title
Address Lookup Table resolution races with concurrently-scheduled ALT-mutating transactions during replay, allowing non-deterministic `LoadedAddresses` and bank-hash divergence - (`runtime/src/bank/address_lookup_table.rs`, `accounts-db/src/accounts.rs`, `ledger/src/blockstore_processor.rs`)

### Summary
`Accounts::load_lookup_table_addresses_into` resolves ALT addresses via an unsynchronized, unlocked read of the account (`load_with_fixed_root`) that is never registered with the account-lock/usage-queue system used to serialize conflicting accesses. During replay, this resolution runs on a transaction-verification thread pool (`entry::validate_and_hash_transactions`) for a newly-arrived shred/entry batch while the *unified scheduler* is still asynchronously executing and committing a prior, already-scheduled entry batch in the same slot — with no wait in between except at block-footer markers. If a user's earlier transaction closes and recreates an ALT account at the same key within that in-flight window, a later transaction's address resolution can non-deterministically observe either the pre-close or post-recreate ALT contents depending purely on thread-scheduling timing.

### Finding Description
`Accounts::load_lookup_table_addresses_into` fetches the ALT account with `self.load_with_fixed_root(ancestors, address_table_lookup.account_key)` and deserializes whatever is currently visible in AccountsDb for that fork [1](#0-0) . This call is not protected by `Accounts::account_locks` (write/read locks) — that lock set is populated only later, from the already-resolved `account_keys()` of the transaction, in `Accounts::lock_accounts` [2](#0-1) . The ALT account key itself is never part of that lock set — only the addresses stored *inside* it become locked keys.

`Bank::load_addresses_from_ref` (called via the `AddressLoader for &Bank` impl used by `RuntimeTransaction::try_create`/`SanitizedTransaction` construction) performs this same unlocked read using `self.ancestors` [3](#0-2) . This resolution happens as part of transaction verification/sanitization, e.g. in `Bank::verify_transaction_with_serialized_message` [4](#0-3) .

During ledger replay, `confirm_slot_entries` synchronously calls `entry::validate_and_hash_transactions` (which invokes `verify_transaction_with_serialized_message`, i.e. ALT resolution) for the *current* batch of entries, then calls `process_entries`, which merely *schedules* transaction execution onto the bank's unified scheduler and returns without waiting for completion [5](#0-4) . The outer loop over `slot_components` (successive shred/entry batches for the same slot) proceeds immediately to the next batch's `confirm_slot_entries`/resolution step; a synchronization wait (`bank.wait_for_completed_scheduler()`) is only performed at a `BlockMarker` footer boundary, explicitly because "All prior transactions must finish first so vote account view is deterministic" for that specific case [6](#0-5) . For ordinary `EntryBatch` components there is no such wait [7](#0-6) .

Consequently, an attacker can submit (a) a transaction that closes an ALT account they own and recreates a new ALT at the same key with a different address list, and (b) a transaction referencing that ALT via `address_table_lookups`, arranged so they land in the same slot but in different shred/entry batches. If (a) is scheduled but not yet committed when (b)'s batch begins its resolution pass, the observed ALT contents for (b) depend on a genuine data race between the async scheduler's commit of (a) and the verification thread pool's read for (b) — a race with no consensus-level tie-breaking, since the read is not mediated by the account-lock/usage-queue ordering that the scheduler relies on for all other conflict resolution.

### Impact Explanation
This can cause two honest validators (or a single validator across two runs, e.g., leader-vs-replay or replay-vs-snapshot-catchup) to compute different `LoadedAddresses` for the same transaction, which feeds directly into which accounts are locked, executed, and modified by that transaction. Divergent resolved addresses produce divergent account state changes and thus divergent bank hashes for the same block — a consensus-safety violation (honest-node bank hash mismatch), matching Agave's "hash/capitalization divergence" / "honest-node snapshot-vs-replay mismatch" bounty category.

### Likelihood Explanation
Exploitation requires only unprivileged actions available to any user: creating an ALT, extending it, closing it, and recreating a new ALT reusing the same derived PDA (same authority + a `recent_slot` value still present in the `SlotHashes` sysvar), plus submitting a second transaction referencing that ALT. The attacker cannot directly control shred/entry batch boundaries or scheduler thread timing, so the race window is probabilistic rather than guaranteed on every attempt, but it is reproducible under load/timing pressure and does not require any leader, validator, or gossip privileges — only normal transaction submission and account ownership.

### Recommendation
Ensure ALT address resolution during replay cannot race with in-flight scheduled execution of transactions in the same slot: either (1) include the ALT account key itself in the transaction's lock/usage-queue set so the scheduler serializes readers/writers of the table, or (2) make `confirm_slot_entries` wait for the scheduler to drain execution of all previously-scheduled entries in the slot before beginning verification/resolution of a new entry batch, or (3) re-validate/re-resolve ALT addresses at execution time (immediately before locking, under the scheduler's ordering) rather than trusting addresses resolved earlier by an unsynchronized read.

### Proof of Concept
Integration test plan (in `ledger/src/blockstore_processor.rs` test module, alongside existing `test_process_entries_2_entries_par`/`test_process_entries_2nd_entry_collision_with_self_and_error` style tests):
1. Create an ALT (`alt_key`) owned by an attacker-controlled authority, funded and extended with addresses `[X, Y]`, committed in an earlier slot.
2. Build a slot with multiple entry batches: batch 1 contains a transaction that closes `alt_key` and, in the same batch, recreates a new ALT at the same `alt_key` (same authority/recent_slot) with addresses `[Z, W]`; batch 2 (delivered as a separate `BlockComponent::EntryBatch`) contains a transaction `Tx_ref` whose `address_table_lookups` reference `alt_key`.
3. Drive `confirm_full_slot` (or `process_entries`/`schedule_transaction_executions` directly) twice with artificially delayed/advanced scheduler execution (e.g., inject a sleep in the mocked scheduler's `schedule_execution` for the close/recreate transaction) to force batch 2's `validate_and_hash_transactions` to run before vs. after batch 1's commit completes.
4. Assert that `Tx_ref`'s resolved `LoadedAddresses` (and the resulting bank hash) differ between the two timing orders, demonstrating that resolution is not deterministic given identical entries/transactions — i.e., the same block replayed under different thread-timing produces different `Bank::hash()`.

    #[must_use]
    pub fn lock_accounts<'a>(
        &self,
        txs: impl Iterator<Item = &'a (impl SVMMessage + 'a)>,
        results: impl Iterator<Item = Result<()>>,
        tx_account_lock_limit: usize,
    ) -> Vec<Result<()>> {
        // Validate the account locks, then get keys and is_writable if successful validation.
        // We collect to fully evaluate before taking the account_locks mutex.
        let validated_batch_keys = txs
            .zip(results)
            .map(|(tx, result)| {

                    .map(|_| TransactionAccountLocksIterator::new(tx).accounts_with_is_writable())
            })
            .collect::<Vec<_>>();

        let account_locks = &mut self.account_locks.lock().unwrap();
        account_locks.try_lock_transaction_batch(validated_batch_keys)

impl Bank {
    /// Load addresses from an iterator of `SVMMessageAddressTableLookup`,
    /// additionally returning the minimum deactivation slot across all referenced ALTs
    pub fn load_addresses_from_ref<'a>(
        &self,
        address_table_lookups: impl Iterator<Item = SVMMessageAddressTableLookup<'a>>,
    ) -> Result<(LoadedAddresses, Slot), AddressLoaderError> {
        let slot_hashes = self
            .transaction_processor
            .sysvar_cache()
            .get_slot_hashes()
            .map_err(|_| AddressLoaderError::SlotHashesSysvarNotFound)?;

        let mut deactivation_slot = u64::MAX;
        let mut loaded_addresses = LoadedAddresses::default();
        for address_table_lookup in address_table_lookups {
            deactivation_slot = deactivation_slot.min(
                self.rc
                    .accounts
                    .load_lookup_table_addresses_into(
                        &self.ancestors,
                        address_table_lookup,
                        &slot_hashes,
                        &mut loaded_addresses,
                    )
                    .map_err(into_address_loader_error)?,
            );
        }

        Ok((loaded_addresses, deactivation_slot))
    }

fn process_entries(bank: &BankWithScheduler, entries: Vec<ReplayEntry>) -> Result<()> {
    let mut tick_hashes = vec![];

    for ReplayEntry {
        entry,
        starting_index,
    } in entries
    {
        match entry {
            EntryType::Tick(hash) => {
                // If it's a tick, save it for later
                tick_hashes.push(hash);
                if bank.is_block_boundary(bank.tick_height() + tick_hashes.len() as u64) {
                    break;
                }
            }
            EntryType::Transactions(transactions) => {
                if transactions.is_empty() {
                    continue;
                }

                // Any bank replaying transactions must have a scheduler installed. Slot 0 -
                // the only bank replayed before the scheduler pool is installed - is tick-only,
                // so it never reaches here.
                assert!(
                    bank.has_installed_scheduler(),
                    "no scheduler installed for bank of slot {} during replay",
                    bank.slot()
                );
                validate_entry_transactions(
                    &transactions,
                    bank.get_transaction_account_lock_limit(),
                )?;

                let indexes = starting_index..starting_index + transactions.len();
                // Widening usize index to OrderedTaskId (= u128) won't ever fail.
                let task_ids = indexes.map(|i| i.try_into().unwrap());

                bank.schedule_transaction_executions(transactions.into_iter().zip_eq(task_ids))?;
            }
        }
    }
    for hash in tick_hashes {
        bank.register_tick(&hash);
    }
    Ok(())
}
