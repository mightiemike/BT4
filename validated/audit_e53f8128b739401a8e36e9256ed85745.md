### Title
Contract self-destruct (`suicide`) fails to transfer all frozen-resource "collateral" types to the inheritor, permanently stranding value - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The DYAD `liquidate` bug moved only one class of "collateral" (non-Kerosene vaults) while leaving another class (Kerosene) stranded on the liquidated position, causing an inconsistent, lossy asset transfer. The closest reachable analog in java-tron is `Program.suicide()` / `Program.suicide2()`, which is directly reachable from any contract that executes the `SELFDESTRUCT` opcode via an ordinary broadcast transaction. When a contract self-destructs, the VM is supposed to move *all* of the owner's value classes (TRX balance, TRC10 tokens, old-model frozen resources, and FreezeV2 frozen resources) to the designated `obtainer`/inheritor. However `transferDelegatedResourceToInheritor()`, which handles the pre-FreezeV2 ("old freeze") resource model, only moves frozen balance for `BANDWIDTH` and `ENERGY`, while the sibling old-model `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor` show that the same account state also tracks a third resource type, `TRON_POWER`, with its own frozen balance and its own way of being cleared/unfrozen.

### Finding Description
`transferDelegatedResourceToInheritor()` reads only two frozen-balance fields off the owner's `AccountCapsule` and forwards them to the inheritor: [1](#0-0) 

and the clean-up helper invoked right afterward only clears the bandwidth/energy fields: [2](#0-1) 

By contrast, the same old-model resource accounting exposed through `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor` explicitly treats `TRON_POWER` as a third, independent frozen-balance bucket with its own weight bookkeeping and its own "clear" logic: [3](#0-2) 
and [4](#0-3) 

`suicide()` calls `transferDelegatedResourceToInheritor()` when `VMConfig.allowTvmFreeze()` is enabled, and it never reads or forwards `getTronPowerFrozenBalance()`/clears `TronPower`, exactly mirroring the DYAD bug pattern of enumerating only a subset of the position's "collateral" types during an irreversible, full state-clearing operation: [5](#0-4) 

The FreezeV2 path (`transferFrozenV2BalanceToInheritor`) correctly iterates over all three `FreezeV2` types (`BANDWIDTH`, `ENERGY`, `TRON_POWER`): [6](#0-5) 

which confirms the old-model handler is the outlier — it was clearly meant to sweep all frozen resource classes for the contract but omits one, just as `VaultManagerV2::liquidate` omitted Kerosene collateral while correctly handling the other collateral vaults.

### Impact Explanation
If a contract account had frozen TRX for `TRON_POWER` under the legacy freeze model (via `FreezeBalanceContract` with resource `TRON_POWER`) and subsequently self-destructs, that frozen value is neither transferred to the `obtainer`/inheritor address nor cleared from the owner account before the account is marked deleted (`getResult().addDeleteAccount(...)`), producing an accounting inconsistency: the value is not credited to any live account balance, effectively becoming unspendable/stranded TRX, while the global total weight for that resource is also never decremented for this component (unlike bandwidth/energy, whose weights are explicitly decremented). This is a state-consistency and fund-availability defect reachable purely from a normal contract call (`SELFDESTRUCT`), with no privileged actor required.

### Likelihood Explanation
Reachability requires only that a smart contract account previously froze balance for `TRON_POWER` under the old (pre-FreezeV2) freeze model and later executes `SELFDESTRUCT` — both are plain, unprivileged actions available to any user/contract deployer via ordinary broadcast transactions, gated only by feature flags `VMConfig.allowTvmFreeze()`/`allowTvmSelfdestructRestriction()` that are chain-wide config, not access-control. Since the old freeze model is legacy/being phased out in favor of FreezeV2, the practical likelihood on a fully upgraded mainnet may be lower, but the code path remains live and reachable wherever old-model freezing is still permitted.

### Recommendation
In `transferDelegatedResourceToInheritor()`, add handling for the old-model `TRON_POWER` frozen balance symmetrically with `BANDWIDTH`/`ENERGY`: read `ownerCapsule`'s tron-power frozen balance, add it into `frozenBalanceForBandwidthOfOwner + frozenBalanceForEnergyOfOwner` before crediting `inheritorAddr`, decrement the corresponding total weight via `repo.addTotalTronPowerWeight(...)`, and clear it in `clearOwnerFreeze()` alongside `setFrozenForBandwidth`/`setFrozenForEnergy`.

### Proof of Concept
Conceptual PoC (mirrors the DYAD report's structure):
1. Deploy a contract account and, under `VMConfig.allowTvmFreeze()`, freeze balance for the contract's own account with resource type `TRON_POWER` (legacy `FreezeBalanceContract`).
2. Confirm via `AccountCapsule.getTronPowerFrozenBalance()` (as exercised by `UnfreezeBalanceActuator`, `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java:227-235`) that the frozen balance is non-zero.
3. Trigger `SELFDESTRUCT` (`suicide`) from the contract, targeting a different `obtainer` address.
4. Observe that `transferDelegatedResourceToInheritor()` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:588-618`) only forwards bandwidth/energy frozen amounts to `obtainer`'s balance; the tron-power frozen amount is neither transferred nor cleared, while the owning account is deleted — leaving that value permanently orphaned in state (not reflected in any live account's spendable balance or in `TotalTronPowerWeight` accounting).

  private long transferFrozenV2BalanceToInheritor(byte[] ownerAddr, byte[] inheritorAddr, Repository repo) {
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddr);
    AccountCapsule inheritorCapsule = repo.getAccount(inheritorAddr);
    long now = repo.getHeadSlot();

    // transfer frozen resource
    ownerCapsule.getFrozenV2List().stream()
        .filter(freezeV2 -> freezeV2.getAmount() > 0)
        .forEach(
            freezeV2 -> {
              switch (freezeV2.getType()) {
                case BANDWIDTH:
                  inheritorCapsule.addFrozenBalanceForBandwidthV2(freezeV2.getAmount());
                  break;
                case ENERGY:
                  inheritorCapsule.addFrozenBalanceForEnergyV2(freezeV2.getAmount());
                  break;
                case TRON_POWER:
                  inheritorCapsule.addFrozenForTronPowerV2(freezeV2.getAmount());
                  break;
              }
            });
