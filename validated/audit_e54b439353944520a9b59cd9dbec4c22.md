Based on my investigation, I found the exact analog: `last-update` is only advanced when the computed index actually changes, which matches the "clock advanced only on change" bug class.

### Title
Interest clock frozen when rounding yields no index delta, permanently understating accrued interest - (File: `local-testing/contracts/vault/vault-stx.clar`, and duplicated across `vault-sbtc.clar`, `vault-ststx.clar`, `vault-usdc.clar`, `vault-usdh.clar`, `vault-ststxbtc.clar` and their `mainnet/contracts/vault/v0-vault-*.clar` counterparts)

### Summary
`accrue()` computes `next-index`/`next-liquidity-index` from `time-delta = stacks-block-time - last-update`, but only advances the `last-update` clock var if the resulting index actually changed value: [1](#0-0) 

### Finding Description
`next-index` and `next-liquidity-index` derive the elapsed period from `(- stacks-block-time (var-get last-update))`: [2](#0-1) 

`accrue()` is the only place `last-update` is mutated, and it is guarded by an equality check rather than being unconditionally set to `stacks-block-time` whenever accrual is attempted:
```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
``` [3](#0-2) 

`calc-multiplier-delta` computes `INDEX-PRECISION + mul-div-{up,down}(rate, time-delta * INDEX-PRECISION, SECONDS-PER-YEAR-BPS)`: [4](#0-3) 

Because `mul-div-down`/`mul-div-up` truncate/round at integer precision, when utilization is very low (near-zero borrow rate) or `time-delta` is small (e.g. accrue called every block, or immediately after a prior accrual within the same or an adjacent block), the multiplier can round back to exactly `INDEX-PRECISION`, so `next` equals the current `idx` and `nliq` equals the current `lidx`. In that case the `is-eq` guards are both true, `last-update` is *not* advanced, and the true elapsed time carried by `last-update` keeps growing across every subsequent call in which this rounding condition recurs. This is a direct analog of the report's "clock advanced only on change" pattern: a monotonic clock variable that is supposed to track elapsed real time but is instead only bumped when a *derived* value changes, allowing the underlying time delta to silently accumulate unbounded while the tracked "last update" timestamp lags further and further behind `stacks-block-time`.

The accumulated backlog is not lost — once utilization/rate rises enough that the multiplier no longer rounds to `INDEX-PRECISION`, the *entire* backlogged `time-delta` (which can span many blocks/hours of missed low-utilization periods) is applied in a single `calc-multiplier-delta` call, producing an interest jump that reflects an artificially long borrow window at the rate prevailing only in the single block where accrual finally triggers. This means the index used in that block understates or overstates real per-block interest relative to what should have compounded incrementally, and the resulting single-block delta feeds directly into the treasury fee calculation (`reserve-inc`, `treasury-lp`) and into `debt`/`collateral` valuations used by `market.clar`'s `accrue-and-cache`, health checks, and liquidation math.

### Impact Explanation
This changes the timing/compounding of interest realized in a single block versus what continuous per-block accrual would have produced, which can permanently misstate accrued (unclaimed) yield distributed to depositors and to the DAO treasury (`treasury-lp` mint in `accrue`) — i.e., permanent freezing/misallocation of unclaimed yield, which is an in-scope High impact class. It does not require any privileged actor and is reachable purely by ordinary transaction timing/interest-rate conditions within a single vault contract (no cross-user interference, no DAO compromise).

### Likelihood Explanation
Requires utilization/rate conditions or short intervals between `accrue()` invocations such that the rounding in `calc-multiplier-delta` yields exactly `INDEX-PRECISION` — plausible during low-utilization periods or with tight interest curves, but not guaranteed on every block, making this a conditional, rounding-dependent occurrence rather than a certainty on every transaction.

### Recommendation
Decouple the elapsed-time tracking from whether the derived index changed: always set `last-update` to `stacks-block-time` on every `accrue()` invocation that is not paused, regardless of whether `next`/`nliq` differ from the stored `index`/`lindex`, so that `time-delta` in the next call reflects only genuinely un-accrued time rather than an unbounded backlog.

### Proof of Concept
1. Vault is under very low utilization such that `interest-rate()` returns a small `rate`.
2. Call `accrue()` (directly, or indirectly via `system-borrow`/`system-repay`/market's `accrue-and-cache`) in block N: `time-delta` is small, `calc-multiplier-delta` rounds to `INDEX-PRECISION`, so `next == idx` and `nliq == lidx`; per [3](#0-2) , `last-update` is NOT advanced.
3. Repeat step 2 across many subsequent blocks while the same low-utilization condition holds — `last-update` remains frozen at block N's timestamp while `stacks-block-time` keeps advancing.
4. Eventually utilization/rate rises so the multiplier no longer rounds to `INDEX-PRECISION`. The next `accrue()` call computes `time-delta` as the full backlog (block N to current), applying that entire elapsed window's interest in one step via `calc-multiplier-delta`, producing an index jump and a `treasury-lp` mint computed from `debt-delta` that reflects the whole backlog compressed into a single block's `total-supply`/`total-assets-preview` snapshot rather than what would have compounded incrementally block-by-block — permanently altering the yield split between depositors and treasury relative to correct continuous accrual.
