### Title
Unbounded gzip decompression of a user-supplied legacy contract program allows a Denial-of-Service via JSON-RPC simulate/estimate execution endpoints - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
The Starknet JSON-RPC read node's execution helper `decompress_program` decompresses a base64-encoded gzip payload supplied by the caller (the `program` field of a `DEPRECATED_CONTRACT_CLASS`/`BroadcastedDeclareV1Transaction.contract_class`) with **no compression-ratio, byte-count, or time limit**, unlike every other decompression path in this codebase.

### Finding Description
`decompress_program` reads the user-controlled compressed program directly into an unbounded `Vec<u8>`: [1](#0-0) 

The code contains an explicit acknowledgement of the missing guard (`// TODO(dan): add time and size limits.`) at line 677. This function is invoked from `user_deprecated_contract_class_to_sn_api`, which is used when converting a caller-submitted `BroadcastedDeclareTransaction::V1` (containing an inline, attacker-chosen `DeprecatedContractClass.compressed_program`) into an `ExecutableTransactionInput` for local execution (fee estimation / simulation): [2](#0-1) 

This is architecturally identical to every other place in the repo that decodes a base64+gzip-compressed program supplied by an untrusted party — except that all of those other paths use `decode_and_decompress_with_size_limit`, which bounds the decompressed size and rejects over-budget payloads: [3](#0-2) [4](#0-3) [5](#0-4) 

`decompress_program`'s lack of the same guard is the exact bug class described in the external report: an unguarded archive/gzip extraction path that allows a small compressed input to expand to an arbitrarily large decompressed size ("zip/gzip bomb"), consuming excessive memory and CPU.

### Impact Explanation
Any RPC caller invoking the execution-simulation flow (fee estimation / simulate transactions) with a `DECLARE` v1 transaction whose legacy contract class contains a crafted gzip bomb (e.g., a few KB compressing several GB of repeated zero bytes) forces the RPC node to allocate and populate a multi-gigabyte `Vec<u8>` and then attempt to `serde_json::from_reader` it. This can exhaust node memory/CPU, causing the RPC node process to slow to a crawl, be OOM-killed, or become unresponsive to legitimate requests — a resource-exhaustion Denial-of-Service (CWE-400/CWE-770) matching the referenced advisory's class and severity (Medium/High CVSS AC:L/PR:N/UI:R/A:H analog: here **UI:N** since it is a direct RPC call, arguably higher likelihood than the original).

### Likelihood Explanation
The path is reachable from a single externally-submitted JSON-RPC request (no special privileges, no consensus/mempool admission needed — this is pure client-facing RPC execution) making it trivially and repeatedly triggerable by any user with API access, at negligible bandwidth cost (a small compressed payload).

### Recommendation
Replace the manual `GzDecoder::new(...).read_to_end(...)` in `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) with the existing size-limited helper `decode_and_decompress_with_size_limit` (or an equivalent bounded `Read::take(max_size)` pattern), enforcing the same `MAX_CAIRO0_PROGRAM_SIZE`/`DEFAULT_MAX_SIERRA_PROGRAM_SIZE`-style ceiling already applied to all other compressed-program ingestion points, and reject with a client error instead of allocating unbounded memory.

### Proof of Concept
1. Craft a legacy (`DeprecatedContractClass`) program JSON consisting of a highly repetitive large payload (e.g., several GB of `0` bytes/whitespace).
2. Gzip-compress it (achieving a very high compression ratio, e.g., >1000:1) and base64-encode the result to produce `compressed_program`.
3. Submit a `starknet_estimateFee`/`starknet_simulateTransactions` JSON-RPC request containing a `BroadcastedDeclareV1Transaction` whose `contract_class.compressed_program` is the crafted payload.
4. Observe `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) decompress the payload into an unbounded in-memory buffer, driving the RPC node's memory/CPU usage far beyond the small compressed request size, degrading or crashing the node.

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.

    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
