The reported bug class—prototype pollution via unguarded `object[key]` lookups falling back to inherited `Object.prototype` methods—is a JavaScript-specific issue. It does not map onto nearcore's Rust codebase, where the equivalent method/action dispatch sites use exhaustive, closed-set matching rather than dynamic property access on prototype-chained objects.

Specifically:
- JSON-RPC method routing in `chain/jsonrpc/src/lib.rs` uses `match request.method.as_ref()` with a hardcoded list of string literals and an explicit `_ => return Err(request)` / `method_not_found` fallback, so an unrecognized or crafted method name (e.g. `"toString"`, `"constructor"`) cannot resolve to any unintended handler. [1](#0-0) [2](#0-1) 
- The runtime's `Action` enum dispatch (`runtime/runtime/src/lib.rs`, `core/primitives/action/mod.rs`) is a compiler-enforced exhaustive `match` over a closed set of variants; there is no dynamic string-keyed lookup into a map that could return an inherited/default function. [3](#0-2) 
- The NEAR wallet contract's selector-based dispatch (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`) matches raw 4-byte selectors against fixed constants and returns `UserError::UnknownFunctionSelector` for anything unmatched, again a closed-set match with no fallthrough to an unintended handler. [4](#0-3) 

None of these use JavaScript-like object property access with prototype-chain fallback, so there is no reachable analog of "accessing inherited functions from Object.prototype to invoke unintended methods" in nearcore.
