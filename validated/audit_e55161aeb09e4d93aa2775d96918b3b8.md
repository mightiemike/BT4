### Title
Sandwichable on-chain Uniswap V3 quote-then-swap in gas-abstraction deposit and outbound gas refund flows enables value extraction from PRC20/gas accounting - (File: `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`, `x/uexecutor/keeper/evm.go`)

### Summary
The Hyperdrive report describes a class of bug where an atomic state update to a shared AMM-like reserve is quoted and consumed within the same manipulable window, letting an attacker sandwich the update for profit at the expense of other pool participants. Push Chain's `x/uexecutor` module reproduces this pattern natively: it fetches a Uniswap V3 `QuoterV2` quote against the live on-chain WPC/PRC20 pool and derives a fixed `minPCOut = quote * 95 / 100` slippage floor from that very quote, then immediately executes the swap using that floor. Because the quote and the swap both read the same manipulable pool reserves in the same transaction/block, and the "slippage protection" is self-referential (derived from the possibly-manipulated quote rather than an independent oracle or TWAP), an unprivileged attacker who also trades against the underlying pool can sandwich these consensus-triggered swaps to extract value from user deposits/refunds and drain the pool, mirroring the Hyperdrive "quote from reserves you're about to move" flaw.

### Finding Description
Three flows share the same pattern — fetch a spot quote, derive a 5% band from it, then swap:

- Gas-abstraction inbound deposit auto-swap: `GetSwapQuote` → `minPCOut = quote*95/100` → `CallPRC20DepositAutoSwap` in `ExecuteInboundGas`. [1](#0-0) 
- The same pattern for `GAS_AND_PAYLOAD` inbounds via `gasAndPayloadDepositAutoSwap`. [2](#0-1) 
- Outbound excess-gas refund swap-back (`gasToken → PC`) via `applyGasRefund`/`getSwapQuoteForRefund`. [3](#0-2) 

`GetSwapQuote` calls `QuoterV2.quoteExactInputSingle` against the live pool state (no historical/TWAP source, `SqrtPriceLimitX96=0`, i.e., no independent price limit) via `CallEVM`, returning the current spot-derived output amount. [4](#0-3) 

That same quote is then used to compute the *only* slippage protection (`minPCOut = quote * 95 / 100`) before the real swap executes via `DerivedEVMCall` to `depositPRC20WithAutoSwap` or `refundUnusedGas`. [5](#0-4) [6](#0-5) 

Because the floor is derived from the same instantaneous pool state that the swap itself consumes, this "protection" only bounds *execution slippage within the same transaction* — it does nothing to stop the quote itself from being manipulated beforehand. An attacker can push the pool price before the quote is read (front-run) and reverse the position after the deposit/refund swap lands (back-run), just as the Hyperdrive attacker moves reserves before the checkpoint update and reverses after — extracting the difference between the honest price and the manipulated price from the protocol/PRC20 accounting and other pool LPs, while the module's guard rails remain satisfied because they were computed off the manipulated state itself.

This directly touches the "Registry and accounting path" and "gas token selection... revert instructions must not misroute value" impact category: it corrupts PRC20/native accounting and gas-refund accounting reachable purely from unprivileged, honest-validator-processed inbound/outbound flows (an ordinary GAS inbound deposit, or an ordinary outbound whose relayer under-spent gas).

### Impact Explanation
An attacker can extract value from:
1. Users bridging in via `TxType_GAS`/`GAS_AND_PAYLOAD` inbounds, whose auto-swapped PC proceeds are minted based on a manipulated quote (users receive less PC than fair value).
2. The gas-refund path, where excess relayer gas is swapped back to PC for the user — again executed at a manipulated price.
3. The underlying Uniswap V3 pool / LPs, who absorb the sandwich loss.

Since these swaps are triggered automatically by the protocol (module-originated `DerivedEVMCall`s) as part of normal consensus-driven UTX execution, not by the depositor's own transaction, the depositor cannot set their own slippage tolerance or protect themselves — the protocol's fixed 5% band is the only guard, and it's ineffective against a self-referential-quote sandwich. This is a repeatable, unprivileged value-extraction vector against protocol/user funds, matching "corruption of PRC20 or native asset accounting, gas fee accounting, refund accounting" in the allowed impact list.

### Likelihood Explanation
High for any deployment where the WPC/PRC20 pools have realistic (non-infinite) liquidity: the attacker needs no privileged role, no validator collusion, and no protocol bug beyond submitting an ordinary bridge deposit (or waiting for an ordinary outbound requiring gas refund) while trading against the same pool in adjacent transactions within the same block or MEV bundle. The severity scales inversely with pool depth — the same dynamic the original Hyperdrive report highlighted with maximal-short sandwiching near zero reserves.

### Recommendation
- Do not derive slippage protection from a quote fetched in the same execution path as the swap. Use a manipulation-resistant reference price (e.g., a TWAP oracle, or an independently governed/registry-set price ceiling/floor) to bound `minPCOut`, or require the deposit/refund amounts to be small relative to pool depth with circuit breakers.
- Consider adding a maximum single-swap size relative to pool liquidity, or routing auto-swaps through a protocol-owned/deep liquidity venue insulated from user-triggered pool manipulation.
- Add a configurable minimum time/price divergence check between the quote and the actual execution (i.e., detect abnormal price movement between quote block and execution block) and abort/fallback to the no-swap PRC20 deposit path (which already exists as a fallback for failed swaps).

### Proof of Concept
Conceptual PoC (mirrors the Hyperdrive PoC structure but for the AMM sandwich in this repo — not executed, as this requires the full EVM/Uniswap V3 pool + module test harness which is outside the scope of static analysis performed here):
1. Attacker observes/knows an upcoming `GAS` inbound (or triggers their own) that will cause `ExecuteInboundGas` to call `GetSwapQuote(gasToken, WPC)` then `CallPRC20DepositAutoSwap`.
2. In the same block (or as the immediately preceding transaction), attacker swaps a large amount of `gasToken` for `WPC` in the underlying Uniswap V3 pool, moving the spot price down.
3. The module reads the now-depressed quote via `GetSwapQuote`, computes `minPCOut = quote*95/100` off that depressed price, and executes `depositPRC20WithAutoSwap`, minting the victim/protocol far less PC than fair value.
4. Attacker immediately reverses their initial swap (WPC back to gasToken), realizing the price impact they caused as profit, extracted from the depositor/protocol/LPs.

I was not able to execute this in a live fork/test harness (no terminal/EVM access in this session), so the exact extractable percentage (analogous to Hyperdrive's 1021% ROI figure) is not verified numerically — this should be confirmed by a Devin session with access to the EVM contracts (`UniversalCore`, `depositPRC20WithAutoSwap`, `refundUnusedGas`) and the Uniswap V3 pool bytecode/liquidity used in `interchaintest`/local-multi-validator setups.

// gasAndPayloadDepositAutoSwap handles the swap quote + deposit autoswap for GAS_AND_PAYLOAD.
func (k Keeper) gasAndPayloadDepositAutoSwap(
	sdkCtx sdk.Context,
	prc20AddressHex common.Address,
	ueaAddr common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	quoterAddr, err := k.GetUniversalCoreQuoterAddress(sdkCtx)
	if err != nil {
		return nil, err
	}

	wpcAddr, err := k.GetUniversalCoreWPCAddress(sdkCtx)
	if err != nil {
		return nil, err
	}

	fee, err := k.GetDefaultFeeTierForToken(sdkCtx, prc20AddressHex)
	if err != nil {
		return nil, err
	}

	quote, err := k.GetSwapQuote(sdkCtx, quoterAddr, prc20AddressHex, wpcAddr, fee, amount)
	if err != nil {
		return nil, err
	}

	// 5% slippage: minPCOut = quote * 95 / 100
	minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
	minPCOut.Div(minPCOut, big.NewInt(100))

	return k.CallPRC20DepositAutoSwap(sdkCtx, prc20AddressHex, ueaAddr, amount, fee, minPCOut)
}

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
