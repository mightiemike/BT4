### Title
Missing Chain/Domain Separation in TVM `ValidateMultiSign` Precompile Enables Cross-Chain Signature Replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x...a`) computes the message hash that off-chain multisig signatures must cover using only `account address || permissionId || data`, with no chain identifier, genesis hash, or contract address folded into the digest. Any smart contract built on top of this precompile to authorize actions via off-chain multisig approvals inherits a signature scheme with zero domain separation across TRON-compatible networks (mainnet, testnets, and private/forked chains), mirroring the exact bug class described in the external report: EIP‑712-style signature verification that omits `chainId`.

### Finding Description
`ValidateMultiSign.execute` builds the signed digest like this: [1](#0-0) 

```
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(..., combine);
```

The resulting `hash` is what off-chain signers must sign, and `recoverAddrBySign` recovers each signer against it, checking permission weight from the account's on-chain `Permission`: [2](#0-1) 

No component of this digest is chain-specific: there is no TRON chain ID / genesis block hash, and no binding to the calling contract's address. TRON account addresses are derived deterministically from public keys and are identical across mainnet, Nile/Shasta testnets, and any other TRON-compatible network (including private forks and future hard-fork chains) that shares the same account/permission state or where an attacker can replicate the target permission configuration. This is structurally the same root cause as the reported Beanstalk bug: the digest lacks a domain separator that binds the signature to one specific chain/deployment, so a signature valid on one network can be replayed verbatim on another.

Contrast this with the base account signature path, `TransactionCapsule.checkWeight`, which signs the *raw transaction bytes* (`Sha256Hash.hash(trx.getRawData())`), which already contain chain-specific `ref_block_hash`/expiration fields tying the signature to a specific chain's block history: [3](#0-2) 

The `ValidateMultiSign` precompile, however, is a general-purpose primitive callable by *any* deployed TVM smart contract to implement its own custom multisig/authorization logic (e.g., escrow release, withdrawal approval, marketplace settlement) purely from `(address, permissionId, data)` — none of which are chain-bound.

### Impact Explanation
Any DApp/smart contract that relies on `ValidateMultiSign` to gate a state-changing action (fund transfer, withdrawal, order settlement) using off-chain-collected multisig approvals is vulnerable to cross-chain replay: if the same bytecode/contract is deployed at the same account structure on a second TRON-compatible network (mainnet vs. testnet, or after/around a chain fork/hard-fork event), a signature set collected for the intended chain can be resubmitted on the other chain to pass the exact same weight/threshold check, since the digest that was signed carries no chain-specific data. This can trigger unauthorized fund movement or unauthorized approval of privileged actuator-callable operations in the replaying contract, matching the "unauthorized claims of tokens and transfers" impact class from the reference report.

### Likelihood Explanation
Reachability requires no privileged role: any user can deploy a contract that calls `ValidateMultiSign`/`BatchValidateSign` and any attacker who has observed a valid signed approval (e.g., leaked/relayed via a DApp's off-chain relay service, or intercepted from a public broadcast on one network) can replay it on another network where an identically-configured account/permission exists. Given TRON's own multi-network deployment model (mainnet, Nile, Shasta, and various permissioned/private TRON forks used by exchanges and enterprises) and the precompile's design being purely a generic signing primitive without any built-in domain separation, this is a realistic and reachable path rather than a purely theoretical one — although actual exploitation depends on a downstream contract author not manually adding their own chain-id/nonce binding inside `data`.

### Recommendation
Bind the digest computed inside `ValidateMultiSign` (and document the same requirement for consumers of `BatchValidateSign`) to chain-specific context, e.g. include the TRON chain ID (`ChainId` exposed via `GetChainParameter`/`block.chainid` equivalent) and/or the calling contract's address in the `combine` byte sequence before hashing:
```
byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), chainId, callerAddress, data);
```
This mirrors the report's recommended fix of adding `block.chainid` to the EIP-712 struct hash, ensuring signatures cannot be replayed across TRON-compatible networks or after a chain fork.

### Proof of Concept
1. Deploy the same TVM contract `C` (which calls `ValidateMultiSign(address, permissionId, dataHash, sigs[])` to authorize a withdrawal) at account `A` on both TRON mainnet and a second TRON-compatible network (e.g. a private fork or testnet) where `A` has an identical `Permission` configuration (attacker-controlled or replicated by the DApp operator during a migration/fork event).
2. Collect a valid signature set `sigs[]` produced off-chain for `hash = sha256(address || permissionId || data)` authorizing a withdrawal on network 1.
3. Submit the identical `(address, permissionId, data, sigs[])` payload to contract `C`'s withdrawal function on network 2.
4. `ValidateMultiSign.execute` recomputes the exact same `hash` (no chain-specific input), `recoverAddrBySign` recovers the same signer addresses, `TransactionCapsule.getWeight` finds them in the (replicated) permission, and the threshold check at [4](#0-3)  succeeds — authorizing the withdrawal on network 2 without any new signatures from the actual key holders for that network.
