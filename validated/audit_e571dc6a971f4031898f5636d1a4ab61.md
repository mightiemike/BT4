### Title
Unbounded `ActiveBallotIDs` growth causes O(n) `CreateBallot`/`ExpireBallotsBeforeHeight` cost on every inbound/outbound vote, enabling gas/CPU-based DoS of the ballot voting pipeline - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
`x/uvalidator.Keeper.CreateBallot` unconditionally calls `ExpireBallotsBeforeHeight`, which iterates over the *entire* `ActiveBallotIDs` KeySet and does a `Ballots.Get` for each entry, every single time a brand-new ballot is created. [2](#0-1) [3](#0-2)  Because `x/uexecutor` sets `DefaultExpiryAfterBlocks = 100_000_000` for every inbound/outbound ballot (effectively disabling expiry), the set of active ballots only shrinks on quorum finalization, not on a timer. [1](#0-0)  This is the same bug class as the Alchemix `Voter#distribute` finding: an ever-growing, attacker-influenced collection is fully iterated inside a hot path, with no cap, causing per-call cost to scale linearly (and unboundedly) with collection size.

### Finding Description
Every inbound observation and every outbound observation is routed through `VoteOnInboundBallot` / `VoteOnOutboundBallot`, which call `uvalidatorKeeper.VoteOnBallot(...)` with `expiryAfterBlocks = types.DefaultExpiryAfterBlocks` (100,000,000 blocks). [4](#0-3) [5](#0-4)  `VoteOnBallot` calls `GetOrCreateBallot`, and on first vote for a new ballot ID, `CreateBallot` is invoked, which — before writing the new ballot — calls `k.ExpireBallotsBeforeHeight(ctx, blockHeight)`: [6](#0-5) 

`ExpireBallotsBeforeHeight` fully iterates `ActiveBallotIDs` (an unbounded `KeySet[string]`) and performs a `Ballots.Get` lookup for every entry to check its expiry height: [7](#0-6) 

Because the default expiry is ~19 years, virtually no ballot naturally expires via this path — the set only drains via `MarkBallotFinalized` on PASSED/REJECTED (i.e., only once >2/3 of UVs vote the same way). `PendingInboundEntry`/`PendingOutboundEntry` records are per-distinct-observation (keyed by `sha256(source_chain:tx_hash:log_index)` for inbound, deterministic outbound ID for outbound), so any unprivileged user who triggers many distinct source-chain events that Push Chain's gateway ingests (e.g., many small/cheap inbound deposit calls with distinct tx hashes/log indices) causes proportionally many distinct ballots to be created and voted on by honest UVs. [8](#0-7) [9](#0-8)  As long as quorum has not yet been reached for a given ballot (e.g., while votes are still trickling in from a validator set, or the observation is contested/variant-fragmented), that ballot stays in `ActiveBallotIDs` for effectively unlimited time — while `ActiveBallotIDs` keeps growing with every new event.

Every subsequent `MsgVoteInbound`/`MsgVoteOutbound` transaction from any (honest) UV then pays the O(n) cost of `ExpireBallotsBeforeHeight` iterating the whole active set, exactly analogous to `Voter#distribute` paying O(gauges) on every distribution call.

### Impact Explanation
As `ActiveBallotIDs` grows (driven purely by ordinary/attacker-generated inbound/outbound observation volume — no privileged role needed to *create* the underlying events), the fixed per-vote overhead of `CreateBallot`→`ExpireBallotsBeforeHeight` grows linearly and unboundedly. This raises the gas/CPU cost of processing every subsequent `MsgVoteInbound`/`MsgVoteOutbound` transaction. If the active set grows large enough, this can push per-tx execution time/gas high enough to degrade or stall the vote-tallying pipeline shared by all inbound/outbound finalization — i.e., new deposits and withdrawals cannot reach quorum/finalize in a timely manner, matching the "Temporary freezing of funds" impact class from the seed report (funds already in flight per `x/uexecutor/README.md`'s note that "Ballot expiry does NOT remove the entry... user's funds are already in flight"). [10](#0-9) 

### Likelihood Explanation
Moderate-to-uncertain. The trigger (creating many pending, not-yet-finalized ballots) requires generating many distinct source-chain observations that validators pick up but that don't immediately reach the 2/3 quorum threshold — this is more easily achievable if validator votes are naturally staggered across blocks (a normal condition) rather than requiring an adversarial validator. However, I could not fully verify from the indexed code (a) the exact per-iteration cost in gas terms (IAVL read cost per `Ballots.Get`) to estimate how many active ballots are needed to cause material degradation, or (b) whether any other gas-accounting/ante-handler limits bound worst-case execution time for `MsgVoteInbound`/`MsgVoteOutbound` before this becomes exploitable in practice. These require empirical benchmarking (analogous to the original PoC's gas measurements) that is outside what static code search can confirm.

### Recommendation
- Decouple ballot expiry pruning from the hot `CreateBallot` path — e.g., run expiry sweeps in `BeginBlocker`/`EndBlocker` with a bounded batch size per block instead of a full-set scan on every new ballot creation.
- Cap the number of ballots processed per `ExpireBallotsBeforeHeight` call, or maintain a secondary index sorted by expiry height so only genuinely-expired entries are touched (avoiding a full `ActiveBallotIDs` scan).
- Reconsider `DefaultExpiryAfterBlocks = 100_000_000` for inbound/outbound ballots, or add an explicit cap/rate-limit on the number of concurrently pending (non-finalized) ballots to bound `ActiveBallotIDs` size.

### Proof of Concept
Could not be empirically produced/benchmarked via static repository search (no terminal/execution access in this mode). Conceptually: repeatedly submit distinct inbound events on a source chain (distinct tx hashes/log indices, minimal value) so validators emit many `MsgVoteInbound` calls that each create a new, non-quorum-reaching ballot via `CreateBallot`/`ExpireBallotsBeforeHeight` [2](#0-1) ; measure wall-clock/gas cost of subsequent `MsgVoteInbound` transactions as `ActiveBallotIDs` size grows, mirroring the original report's gas-vs-gauge-count measurement methodology. This would need to be run in a live/simulated Push Chain node to obtain concrete numbers.

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}

### `PendingInbounds`

- **Created** by the FIRST validator vote on a given inbound (`RecordInboundVote`
  inside `VoteInbound`). The chain learns about the source-chain event from
  validator observations.
- **Keyed** by `utx_key = sha256(source_chain:tx_hash:log_index)`.

  for the same logical event (different decoded fields, formatting, etc.), each
  unique payload becomes its own `InboundVariant` inside the entry, with its

  variant ended `PASSED`, the existing post-finalization path in `VoteInbound`
  produced a `UniversalTx`. If ALL variants ended `EXPIRED`/`REJECTED`, the
  full per-variant audit trail is moved to `ExpiredInbounds` for the future
  escape-hatch refund flow.
- The cleanup-on-terminal logic lives in `keeper/ballot_hooks.go` (the
  `BallotHooks` impl wired into `x/uvalidator`).
