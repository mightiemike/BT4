### Title
Unbounded L1-handler calldata/payload permits permanently unincludable messages, stalling the L1→L2 message queue - (File: `crates/blockifier/src/bouncer.rs`, `crates/apollo_l1_events/src/transaction_manager.rs`)

### Summary
L1-to-L2 messages are converted into `L1HandlerTransaction`s with a `calldata`/payload of attacker-controlled, effectively unbounded length (an L1 sender can call the core contract's `sendMessageToL2` with an arbitrarily large payload array). Unlike RPC-submitted transactions (Invoke/Declare/DeployAccount), which go through `StatelessTransactionValidator::validate_tx_extended_calldata_size` and are rejected pre-emptively if too long, `L1HandlerTransaction` is never subject to this check — the gateway's size validation only inspects `RpcTransaction::Declare/DeployAccount/Invoke` variants. [1](#0-0) 

### Finding Description
The `payload_size` used throughout fee/resource accounting is derived directly from the raw calldata length without any upper bound: [2](#0-1) 

This payload size feeds into `get_message_segment_length`, which is unbounded and directly proportional to the attacker-supplied payload: [3](#0-2) 

The `message_segment_length` becomes one of the bouncer's `BouncerWeights`, which are capped by a fixed per-block maximum (`message_segment_length: 3700` by default): [4](#0-3) 

When a *single* transaction's weight exceeds this maximum block capacity on its own, the codebase's own tests demonstrate this causes a panic/error ("Transaction size exceeds the maximum block capacity"), i.e., the transaction can never be included in any block, no matter how it's retried: [5](#0-4) [6](#0-5) 

Because L1 handler transactions are scraped from L1 messages and staged for inclusion strictly by arrival/timestamp order (FIFO), and there is no size gate rejecting an oversized message before it is queued: [7](#0-6) [8](#0-7) 

an L1 sender (any unprivileged Ethereum account calling the core contract's `sendMessageToL2`) can submit a message with a payload large enough that its resulting `L1HandlerTransaction` will never fit inside a block's bouncer capacity. This is the direct analog of the reported HGT/LayerZero issue: an arbitrarily sized cross-chain payload that the receiving side's resource/gas accounting cannot bound, causing the message (and, in blocking-style delivery systems, everything queued behind it) to become permanently stuck.

### Impact Explanation
If the L1 events queue processes messages in strict arrival order (as shown by the "returns in arrival order" test) and does not allow the batcher to skip past an unincludable transaction to reach subsequent ones, an attacker-crafted oversized `sendMessageToL2` payload would permanently block that message and any L1→L2 messages behind it from ever being consumed on L2. This is a denial-of-service on the L1→L2 messaging bridge: legitimate L1→L2 messages (deposits, bridge calls, etc.) queued after the malicious one could never be delivered, freezing user funds/actions that depend on L1-to-L2 message delivery. This matches the "network unable to confirm new transactions" / "permanent freezing of funds" criteria.

### Likelihood Explanation
Likelihood is High: sending an L1→L2 message with a large payload requires no special privilege — any Ethereum account can call `sendMessageToL2` on the core contract with an arbitrarily long `uint256[]` payload and pay the corresponding L1 gas cost, which is a bounded, predictable cost on L1 (unlike the potentially unbounded resource impact on L2). No stateful validation currently rejects this before the message is scraped and queued as an `L1HandlerTransaction`.

### Recommendation
- Enforce a maximum payload/calldata length for `L1HandlerTransaction` analogous to `StatelessTransactionValidatorConfig::max_calldata_length`, either at the L1 events scraper/provider layer (drop/flag oversized messages before staging) or as an explicit bounds check when the message is fetched/converted from `L1ToL2Message`/`L1HandlerTransaction`.
- Ensure the bouncer/message-segment accounting for L1 handler transactions can never accept (or must explicitly reject with a distinct, actionable error) a message whose payload alone would exceed `block_max_capacity.message_segment_length`, and make sure the transaction manager/L1 events provider can skip past a permanently-unfittable transaction (e.g., mark and permanently exclude it, or require it to be retried at a smaller granularity) rather than blocking FIFO delivery of subsequent messages.
- Add regression tests exercising an L1Handler transaction whose payload size alone exceeds `bouncer_config.block_max_capacity.message_segment_length`, verifying it does not permanently stall processing of later-queued L1 handler transactions.

### Proof of Concept
1. An attacker calls the L1 core contract's `sendMessageToL2(to_address, selector, payload)` with a `payload` array long enough that `payload.len() + 1` (the `calldata` including `from_address`) makes `get_message_segment_length` exceed `BouncerWeights::default().message_segment_length` (3700) on its own [4](#0-3) [3](#0-2) .
2. The L1 events scraper converts this into an `L1HandlerTransaction` via `L1HandlerTransaction::create`/`Event::from_l1_event` with no size check [9](#0-8) , and it is queued by the transaction manager in arrival order.
3. When the batcher/block builder attempts to include this transaction (or any earlier-queued one behind which subsequent legitimate messages wait), `try_update`/`verify_tx_weights_within_max_capacity` computes weights that cannot fit in any block's max capacity, producing the "Transaction size exceeds the maximum block capacity" failure mode demonstrated in the test suite [5](#0-4) .
4. Because there is no mechanism (found in the reviewed code) allowing the L1 events provider/transaction manager to permanently and safely skip such a transaction while still processing later, valid L1-to-L2 messages, the queue behind it is effectively stalled — mirroring the LayerZero "arbitrary size `_toAddress`/payload blocks the channel" bug class.

**Uncertainty**: I could not fully verify from the retrieved code whether the L1 events/transaction-manager pipeline has an explicit fallback that skips a permanently-oversized transaction after a failed inclusion attempt (I found `get_txs`/staging logic and the bouncer's hard rejection, but not the batcher's exact recovery path for a `BlockFull`/`TransactionTooLarge` error on an L1 handler tx specifically). This should be confirmed by inspecting `crates/apollo_l1_events/src/transaction_manager.rs` and the batcher's `ProposeTransactionProvider`/`ValidateTransactionProvider` error-handling code for L1 handler transactions in a live session before treating this as fully confirmed.

    fn validate_tx_extended_calldata_size(
        &self,
        tx: &RpcTransaction,
    ) -> StatelessTransactionValidatorResult<()> {
        let total_length = match tx {
            RpcTransaction::Declare(_) => return Ok(()),

            RpcTransaction::DeployAccount(RpcDeployAccountTransaction::V3(tx)) => {
                tx.constructor_calldata.0.len()
            }

            RpcTransaction::Invoke(RpcInvokeTransaction::V3(tx)) => {
                tx.calldata.0.len() + tx.proof_facts.0.len()
            }
        };

        if total_length > self.config.max_calldata_length {
            return Err(StatelessTransactionValidatorError::CalldataTooLong {
                calldata_length: total_length,
                max_calldata_length: self.config.max_calldata_length,
            });
        }

        Ok(())
    }

pub fn get_message_segment_length(
    l2_to_l1_payload_lengths: &[usize],
    l1_handler_payload_size: Option<usize>,
) -> usize {
    // Add L2-to-L1 message segment length; for each message, the OS outputs the following:
    // to_address, from_address, payload_size, payload.
    let mut message_segment_length = l2_to_l1_payload_lengths
        .iter()
        .map(|payload_length| constants::L2_TO_L1_MSG_HEADER_SIZE + payload_length)
        .fold(0, |accumulator, length| {
            usize::checked_add(accumulator, length).expect(
                "Sending a message to L1 costs gas proportional to payload, so total cannot \
                 exceed usize.",
            )
        });

    if let Some(payload_size) = l1_handler_payload_size {
        // The corresponding transaction is of type L1 handler; add the length of the L1-to-L2
        // message sent by the sequencer (that will be outputted by the OS), which is of the
        // following format: from_address=calldata[0], to_address=contract_address,
        // nonce, selector, payload_size, payload=calldata[1:].
        message_segment_length += constants::L1_TO_L2_MSG_HEADER_SIZE + payload_size;
    }
