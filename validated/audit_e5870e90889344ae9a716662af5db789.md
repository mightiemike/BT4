### Title
Signer global-state agreement threshold uses floor division while the consensus-critical block-approval threshold uses ceiling division, causing a rounding mismatch analogous to the "decimals not accounted for" fee-calculation bug - ([File: libsigner/src/v0/signer_state.rs])

### Summary
The external report's bug class is a rounding/scale mismatch in an amount calculation that two independently-solved computations should agree on but don't, because one path truncates and the other doesn't. The equivalent pattern exists in the signer-weight threshold math used for Nakamoto consensus: the authoritative, consensus-critical threshold function rounds up (ceiling), while the signer-side "global agreement" threshold used for determining protocol state (burn view, current miner, tx replay set, protocol version) rounds down (floor). This is the same class of defect — a scaled/percentage quantity computed with two different, non-equivalent rounding rules — applied to the signer network rather than to a token-amount fee split.

### Finding Description
The consensus-critical function that determines whether a Nakamoto block has enough signer weight to be accepted uses ceiling division to compute the 70% threshold: [1](#0-0) 

```
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil)...
}
```
This is invoked by `verify_signer_signatures`, which every node uses to validate that a Nakamoto block header's aggregate signer weight meets the 70% bar before accepting the block into chainstate: [2](#0-1) .

By contrast, the `GlobalStateEvaluator::reached_agreement` function — used by the signer binary to decide when a threshold ("70%") of signer weight has agreed on the burn view, the current miner, the active tx-replay set, and the supported protocol version — uses plain floor division, with no rounding-up adjustment: [3](#0-2) 

```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
```

These two functions use the *same* nominal constant (`NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7`, i.e. 70%) but compute non-equivalent thresholds whenever `total_weight * 7` is not a multiple of 10. For example, with `total_weight = 3`: `compute_voting_weight_threshold` returns `ceil(2.1) = 3`, while `reached_agreement` accepts `floor(2.1) = 2`. This is used across multiple signer decision points: protocol-version agreement, burn-view agreement, current-miner/state-machine agreement, and tx-replay-set agreement: [4](#0-3) [5](#0-4) .

### Impact Explanation
`reached_agreement`/`reached_disagreement` decide what a signer believes is the network's globally agreed miner, burn view, and transaction-replay set — inputs that feed into whether a signer signs or rejects a given block proposal. Because the rounding is off by one weight-unit relative to the canonical node-side threshold, a minority set of signers whose combined weight sits exactly in the rounding gap (e.g., weight = `floor(0.7*total)` but `< ceil(0.7*total)`) can be treated by the signer-state evaluator as having "reached agreement" on a state/miner/replay-set view that a node validating a block against `compute_voting_weight_threshold` would not consider sufficiently supported. This can cause a subset of signers to sign/broadcast a block or drive their local decision (miner selection, tx-replay acceptance) based on a threshold that is one unit below the canonical 70% bar, producing a temporary tip/verdict disagreement between signers/nodes that use the two different threshold functions. This matches the "signer weight below threshold" / "validation verdict two nodes disagree on" analog class, bounded to a High-severity temporary disagreement (not necessarily a permanent chain split, since block finalization ultimately still requires `compute_voting_weight_threshold` for actual block acceptance) — the mismatch is confined to the signer-side global-state agreement determination.

### Likelihood Explanation
This triggers deterministically whenever `total_weight * 7` is not exactly divisible by 10 (a very common case, since `total_weight` is the sum of arbitrary per-signer weights) and the actual supporting weight lands exactly on the rounding boundary between floor and ceil. No majority collusion is required — it is purely a function of the existing weight distribution and vote tally, so it is minority-triggerable/naturally occurring rather than requiring an attacker-controlled majority.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement` use the same ceiling-division formula as `NakamotoBlockHeader::compute_voting_weight_threshold` (or better, have both call a single shared threshold function) so that "70% agreement" always means the identical integer threshold across the signer-state evaluator and the node's block-verification logic.

### Proof of Concept
1. Configure a reward cycle where the sum of signer weights (`total_weight`) is such that `total_weight * 7` is not a multiple of 10, e.g. `total_weight = 3` (weights could be `[1,1,1]`).
2. `compute_voting_weight_threshold(3)` computes `ceil(21/10) = 3`, i.e., all 3 weight units are required for the canonical node-side threshold.
3. `GlobalStateEvaluator::reached_agreement(2)` with `total_weight = 3` computes `floor(21/10) = 2`, so `vote_weight = 2 >= 2` returns `true`.
4. Thus with only 2 of 3 signer-weight-units agreeing on a burn view / current-miner / protocol version, the signer-side evaluator declares "agreement reached," while a node checking actual signer-signature weight against `compute_voting_weight_threshold` for block acceptance would require all 3 units — a divergence between the "signer consensus" logic and "node consensus" logic on the same nominal 70% threshold, unverified beyond static code analysis since I could not execute the signer/node runtime to confirm downstream effects on block broadcast behavior.

    /// Determine what the maximum signer protocol version that a majority of signers can support
    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }
