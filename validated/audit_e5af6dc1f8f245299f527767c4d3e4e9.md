### Title
Excess outbound gas fee refund is permanently lost with no retry path when `CallUniversalCoreRefundUnusedGas` fails - (File: x/uexecutor/keeper/outbound.go)

### Summary
This is the direct analog of the Tap.sol bug class: a computed "amount owed to the user" gets capped/dropped when the immediate transfer attempt cannot complete, and the protocol keeps no record enabling the user to claim it later. In Push Chain, this manifests in `applyGasRefund`, which computes the excess outbound gas fee (`gasFee - gasFeeUsed`) owed back to the sender/fund-recipient and attempts a single, one-shot on-chain transfer via `CallUniversalCoreRefundUnusedGas`. If both the swap-based and no-swap fallback calls fail, the refund amount is recorded only as a `FAILED` status string with no retry mechanism, no escrow, and no way for the affected user to reclaim the excess gas fee later.

### Finding Description
`applyGasRefund` in `x/uexecutor/keeper/outbound.go` computes `refundAmount := gasFee - gasFeeUsed` [1](#0-0)  and attempts to deliver it to the recipient by calling `k.CallUniversalCoreRefundUnusedGas` first with a swap and, on failure, without a swap as a fallback [2](#0-1) . If both attempts return an error, the function simply records `refundPcTx.Status = "FAILED"` and `refundPcTx.ErrorMsg`, then stores `outbound.PcRefundExecution = refundPcTx` and `outbound.RefundSwapError` [3](#0-2) .

`applyGasRefund` is only ever invoked once per outbound, from `handleFailedOutbound` and `handleSuccessfulOutbound`, both of which are called from `FinalizeOutbound`, which itself only runs when `outbound.OutboundStatus == types.Status_OBSERVED` [4](#0-3) . `FinalizeOutbound` is invoked exactly once, from `VoteOutbound`, immediately after the ballot reaches quorum and the outbound is transitioned to `OBSERVED` [5](#0-4) . `VoteOutbound` explicitly rejects any further votes on the same outbound once it is no longer `Status_PENDING` ("outbound with key %s is already finalized") [6](#0-5) , so there is no code path that revisits a finalized outbound to retry the gas refund. I found no `RetryRefund`/`retryRefund` function or governance/msg handler anywhere in the repository that reads `PcRefundExecution.Status == "FAILED"` and re-attempts the transfer — the only occurrences of `PcRefundExecution`/`RefundSwapError` outside generated protobuf code are in `outbound.go` itself and the integration test file.

This mirrors the Tap.sol pattern precisely: an amount is calculated as owed (`tapped` in Tap.sol / `refundAmount` here), an attempt to pay it out is made, and if that attempt cannot fully succeed, the shortfall (the entire `refundAmount` here, since there's no partial-refund concept) is discarded rather than persisted for a later claim.

### Impact Explanation
This falls squarely within the "permanent loss of user or protocol-controlled funds" impact category. Whenever the swap-based refund fails (e.g., due to insufficient DEX liquidity for the gas token/PC pair, slippage exceeding the `minPCOut` bound, quoter/fee-tier misconfiguration, or a transient/no-liquidity condition) and the no-swap fallback also fails (e.g., depositPRC20 to the recipient reverts for any reason — recipient contract rejecting the call, gas token registry issue, etc.), the excess gas fee that was already deducted from the sender's original payment is neither transferred to the recipient nor recoverable through any code path. The value is stranded — the corresponding tokens presumably remain in the UniversalCore/module's control but there is no accounting record or fund-recipient claim mechanism identified that would allow the money to be paid out at a later time when conditions change.

### Likelihood Explanation
This condition is reachable purely through ordinary honest-validator finalization of a normal outbound with an unprivileged/ordinary destination-chain gas price that undershoots the estimated `gasFee` (a routine occurrence — `gasFeeUsed < gasFee` is explicitly tested as the common case in `test/integration/uexecutor/gas_fee_refund_test.go`). The only additional condition needed is that the refund-delivery call itself fails on-chain (swap slippage/liquidity, or a reverting recipient/no-swap deposit) — a state achievable without any privileged actor, simply by an attacker/user controlling the recipient contract behavior or by naturally occurring low-liquidity market conditions for the gas token pair. No malicious validator, admin, or TSS action is required.

### Recommendation
When both the swap and no-swap refund attempts fail, do not treat the outbound as terminally settled with the funds abandoned. Instead:
1. Persist the refund as a distinct pending/claimable state (e.g., add a `Status_REFUND_PENDING` or a separate claimable-refund index keyed by recipient/outbound id) rather than only recording a `FAILED` string.
2. Provide a retry path — either automatic (retried on subsequent blocks/via a keeper hook) or a user-callable message (e.g., `MsgClaimRefund`) that recipients can invoke once liquidity/conditions improve, mirroring the AragonBlack/fundraising#162 fix of preserving the "amount still owed" rather than zeroing it out.
3. Ensure the underlying PRC20/native tokens are actually held in an identifiable escrow (module account) matching the recorded pending-refund amount so the claim is always backed by real funds.

### Proof of Concept
Conceptual trace (based on code reading; not independently executed):
1. An inbound/outbound flow creates an `OutboundTx` with `GasFee = X` and `GasToken = T` (a PRC20-wrapped gas token).
2. Validators reach quorum voting `Success = true` (or `false`) with `GasFeeUsed = Y` where `Y < X`, matching the tested scenario in `gas_fee_refund_test.go` ("refund execution recorded when gasFee exceeds gasFeeUsed") [7](#0-6) .
3. `VoteOutbound` finalizes the outbound and calls `FinalizeOutbound` → `handleSuccessfulOutbound`/`handleFailedOutbound` → `applyGasRefund`.
4. `applyGasRefund` computes `refundAmount = X - Y` and attempts `CallUniversalCoreRefundUnusedGas(..., withSwap=true, ...)`. Assume the DEX quote/swap reverts (e.g., token T has no liquid pool, or `minPCOut` cannot be met) — the swap path fails, triggering the no-swap fallback.
5. Assume the no-swap `depositPRC20Token`-based call to the recipient also fails (e.g., recipient is a contract without a `receive`/token-accepting path, or the gas token's PRC20 contract has since been paused).
6. `outbound.PcRefundExecution.Status = "FAILED"`, `outbound.RefundSwapError` set, and `UpdateOutbound` persists this final state.
7. Because `VoteOutbound` blocks any further voting on an outbound once its status is no longer `PENDING`, and no other code path reads `PcRefundExecution.Status == "FAILED"` to retry, `refundAmount` of tokens is permanently unrecoverable — the analog of the Tap.sol "capped tapped value reset to zero" bug.

Note: I was not able to fully trace where the underlying PRC20/native gas-token funds physically reside after a failed refund (i.e., whether they remain in a module escrow account or were already burned/consumed elsewhere), since that would require inspecting the `UniversalCore` Solidity contract's `refundUnusedGas` implementation, which is out of scope of the indexed Go code. This detail affects whether the loss is "unauthorized burn" vs. "permanent freeze," but under either interpretation the funds become unrecoverable by the intended recipient given the current Go-side keeper logic.

func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}

	fee, swapErr := k.GetDefaultFeeTierForToken(ctx, gasToken)
	var swapFallbackReason string

	if swapErr == nil {
		quote, quoteErr := k.getSwapQuoteForRefund(ctx, gasToken, fee, refundAmount)
		if quoteErr == nil {
			minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
			minPCOut.Div(minPCOut, big.NewInt(100))

			resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, true, fee, minPCOut)
			if err == nil {
				refundPcTx.TxHash = resp.Hash
				refundPcTx.GasUsed = resp.GasUsed
				refundPcTx.Status = "SUCCESS"
				outbound.PcRefundExecution = refundPcTx
				return
			}
			swapFallbackReason = fmt.Sprintf("swap refund failed: %s", err.Error())
		} else {
			swapFallbackReason = fmt.Sprintf("quote fetch failed: %s", quoteErr.Error())
		}
	} else {
		swapFallbackReason = fmt.Sprintf("fee tier fetch failed: %s", swapErr.Error())
	}

	// Step 2: fallback — refund without swap (deposit PRC20 directly to recipient)
	ctx.Logger().Error("applyGasRefund: swap refund failed, falling back to no-swap",
		"outbound_id", outbound.Id,
		"reason", swapFallbackReason,
	)

	resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, false, big.NewInt(0), big.NewInt(0))
	if err != nil {
		refundPcTx.Status = "FAILED"
		refundPcTx.ErrorMsg = err.Error()
	} else {
		refundPcTx.TxHash = resp.Hash
		refundPcTx.GasUsed = resp.GasUsed
		refundPcTx.Status = "SUCCESS"
	}

	outbound.PcRefundExecution = refundPcTx
	outbound.RefundSwapError = swapFallbackReason
}
