## Finding: Unvalidated array-length field used directly for memory-range read in the deprecated (Cairo0) syscall calldata parser

### Title
Unbounded/unvalidated array-length felt used to size a VM memory read in `read_felt_array` (Cairo0 syscalls) - (File: `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`)

### Summary
The Wireshark CVE-2017-11407 bug class is "a length field taken from untrusted input is used to drive a reassembly/read operation without first validating it against the actual available data." The sequencer's deprecated (Cairo0) syscall calldata reader has the same shape: it reads an attacker-controlled `array_size` felt directly from Cairo VM memory and immediately converts it to a `usize` and passes it straight into a bulk memory-range read, with no upper-bound or availability check.

### Finding Description
`read_felt_array` in the deprecated syscalls hint processor reads the array length as a raw `Felt` from the calldata memory, converts it to `usize`, and calls `felt_range_from_ptr` with that unchecked size: [1](#0-0) 

`felt_range_from_ptr` forwards this attacker-controlled `size` straight to `vm.get_integer_range`, which allocates/collects a `Vec<Felt>` of that length: [2](#0-1) 

This is called from `read_calldata`/`read_call_params`, used for the deprecated `CALL_CONTRACT`, `LIBRARY_CALL`, and `DELEGATE_CALL` syscalls in Cairo0 contracts: [3](#0-2) 

By contrast, the newer Cairo1 execution path enforces an explicit bound on the calldata/array size before using it (`SIERRA_ARRAY_LEN_BOUND` check against `range_check_ptr`) prior to walking the memory: [4](#0-3) 

and the Cairo1 syscall-side `read_felt_array` in `crates/blockifier/src/execution/syscalls/hint_processor.rs` derives the array size from the *difference between two already-validated pointers* (`array_data_end_ptr - array_data_start_ptr`) rather than trusting an arbitrary felt: [5](#0-4) 

The deprecated Cairo0 variant has no equivalent check — the length felt is fully attacker-controlled (it lives in Cairo0 program memory that the contract deployer/executor controls) and is used without validating it against `2**128`/`SIERRA_ARRAY_LEN_BOUND`-style limits or against the actual amount of readable/allocated memory before the bulk read is attempted.

### Impact Explanation
A malicious contract deployer can craft a legacy (Cairo0/`DeprecatedContractClass`) contract whose bytecode, when invoked via `CALL_CONTRACT`/`LIBRARY_CALL`/`DELEGATE_CALL`, places an extremely large value (e.g., near `usize::MAX`) as the calldata array-size felt. When this contract is declared and then invoked by any transaction sender, the sequencer's execution of that entry point drives `read_felt_array` → `felt_range_from_ptr` → `vm.get_integer_range` to attempt to allocate/iterate a vector of that (attacker-chosen) size. This can cause an allocation failure/panic (crash) or extreme resource consumption during block building/execution — i.e., a node executing that transaction can crash or hang, directly affecting the sequencer's ability to build/re-execute blocks (denial of service / halted transaction confirmation), which matches the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
Reachability is straightforward and needs only a single unprivileged actor: declare a Cairo0 class with the crafted calldata length, deploy/invoke it, and trigger the vulnerable syscall path from within `__execute__` or via nested `library_call`/`call_contract`. No special privileges (operator, prover, staker) are required — this is purely a transaction sender + contract deployer path, which is explicitly in-scope per the prompt's reachable-path list (blockifier execution, syscalls).

### Recommendation
Add an explicit bound check on `array_size` in `read_felt_array` (deprecated_syscalls) before it is used to size the memory read — mirroring the Cairo1 path's `SIERRA_ARRAY_LEN_BOUND` check or otherwise validating `array_size` against a sane maximum (e.g., calldata/segment size limits) before calling `felt_range_from_ptr`, and/or deriving the size from actual memory-segment bounds instead of trusting the raw felt.

### Proof of Concept
1. Author a Cairo0 contract whose bytecode, upon `__execute__`, issues a legacy `CALL_CONTRACT` (or `LIBRARY_CALL`) syscall request where the syscall request's calldata "size" felt is set to a very large value (e.g., `2^63`), while the calldata "start pointer" felt is any valid relocatable/segment reference.
2. Declare and deploy this contract, then send an ordinary invoke transaction that triggers the vulnerable entry point.
3. During execution, `read_calldata`/`read_call_params` → `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:931-949`) reads the oversized `array_size` and calls `felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)`, which attempts to allocate/copy a `Vec<Felt>` of that size in `vm.get_integer_range`, causing an allocation failure/panic or severe resource exhaustion in the executing node.

```rust
pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
```

```rust
pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
```
