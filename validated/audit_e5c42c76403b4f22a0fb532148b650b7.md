### Title
Webhook Domain Header Not Bound to HMAC-Authenticated Payload Enables Cross-Tenant Webhook Spoofing - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`, `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
Similar to the Triton VM `sponge_absorb_mem` flaw, where a hash is verified but not bound to the actual claimed memory source, `shopify-app-js`'s webhook authentication computes and verifies an HMAC only over the raw request body, while the `X-Shopify-Shop-Domain` (and topic/webhook-id) header — used to select which merchant's session/access token the webhook is processed under — is never included in the authenticated data. Any party capable of producing one valid `(body, hmac)` pair for the shared app secret can replay it with an arbitrary `domain` header and have it accepted as if it originated from that other shop.

### Finding Description
Webhook validation authenticates only the raw body: [1](#0-0) 
The result is checked, and if the HMAC over `rawBody` is valid, the function proceeds to read identifying headers — including `domain` — without any cryptographic binding to the just-validated body: [2](#0-1) [3](#0-2) 

The `domain` value returned from this check (`check.domain`) is then used directly to load the offline session/access token that will be used to process the webhook: [4](#0-3) 
(identical logic exists in `packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts:35-96`)

Because `apiSecretKey` is a single, app-wide secret (not per-shop), any merchant who has installed the app can trigger a legitimate webhook to their own store and thereby obtain a body+HMAC pair that Shopify (or the attacker directly) has signed with the same key used for every installation of the app. That pair validates successfully against `validateHmacFromRequestFactory` regardless of which shop's domain header accompanies it, because the domain header is not part of the HMAC input — only `rawBody` is: [5](#0-4) 

This is the direct analog of the Triton VM bug: the "hash"/authenticator (HMAC) is verified, but the constraint that ties the authenticated data to its claimed origin/location (`domain`) is missing, allowing an attacker to substitute the claimed source metadata while reusing a validly-authenticated payload.

### Impact Explanation
An attacker who is a legitimate (unprivileged) merchant of the app can:
1. Trigger a webhook to their own shop (or otherwise obtain a valid `(rawBody, hmac)` pair for any topic they control, e.g. `products/create`).
2. Replay the exact same POST request to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Webhook-Id`/topic) header changed to a victim merchant's domain.
3. The HMAC still validates (it only covers the body), header presence checks pass, and `ensureValidOfflineSession` loads the victim shop's stored offline session/access token.
4. The app's webhook handler then executes attacker-chosen payload content using the victim shop's admin access token/session — a cross-tenant confused-deputy condition (webhook handler acting on the wrong tenant's credentials with attacker-controlled data).

Depending on what the app's webhook handlers do (e.g., write data, trigger side effects, billing actions, GDPR data changes) this can result in cross-tenant data corruption or unauthorized actions being performed against a merchant that never sent that webhook.

### Likelihood Explanation
Reachable from a single unprivileged merchant/customer request with no need to leak secrets or perform MITM — they only need the ability to trigger one webhook they legitimately control (something available in most app installations) and then replay it directly to the exposed `/webhooks` endpoint with a modified header, which any HTTP client can do. This satisfies the "single merchant" unprivileged threat model.

### Recommendation
Bind identifying/authorization-relevant metadata (at minimum the shop domain, and ideally topic/webhook id) into the authenticated data used to select which session/access token processes the webhook — e.g., verify that the `domain` header corresponds to the session actually returned/expected, cross-check it against another Shopify-verified signal, or extend the HMAC computation/verification to include these header values (mirroring how the OAuth/App Proxy validators in `hmac-validator.ts` sign the full query, not just part of it). At minimum, ensure the webhook processing pipeline cannot be pointed at an arbitrary shop's session using a body signed under a different tenant's context.

### Proof of Concept
1. As merchant A, trigger any webhook subscribed by the app (e.g. `products/create`) and capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` value `H` sent by Shopify (both are valid because the app's secret is shared across installations).
2. Send a new POST to the app's `/webhooks` endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain` set to victim shop `victim.myshopify.com` (and matching topic/webhook-id headers as needed).
3. `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-201`) validates the HMAC successfully against `B`.
4. `checkWebhooksHeaders` (`packages/apps/shopify-api/lib/webhooks/validate.ts:99-146`) accepts the forged `domain` header.
5. `authenticateWebhookFactory` (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:52`) loads and uses `victim.myshopify.com`'s offline session/access token to process attacker-supplied payload `B`.

Note: I was unable to fully verify what any specific downstream webhook handler does with the session/payload in a hosted deployment (that is app-specific business logic outside this library), so real-world impact severity depends on the consuming app's webhook handlers, but the authentication/authorization gap itself is confirmed at the library level.
