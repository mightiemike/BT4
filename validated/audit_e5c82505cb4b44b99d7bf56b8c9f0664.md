### Title
ETH-implicit accounts are created pointing at a global wallet-contract hash with no existence check, permanently freezing deposited funds if the wallet contract was never deployed - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_implicit_account_creation_transfer` creates ETH-implicit accounts by unconditionally binding them to `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))`, without ever checking that this global contract actually exists in state. This mirrors the external report's root cause: a privileged capability ("owner" in the Solidity report, "the global contract that provides all functionality" here) is assumed to be correctly wired up, but nothing in the code enforces that assumption, so the entity that should be able to act (mint tokens / operate the account) permanently cannot.

### Finding Description
For `AccountType::EthImplicitAccount`, the implicit-creation-by-transfer path does: [1](#0-0) 

It computes `global_contract_hash = eth_wallet_global_contract_hash(&chain_id)` and directly constructs the account with `AccountContract::Global(global_contract_hash)` — with no lookup into the trie to confirm that a global contract with that hash was ever deployed.

Contrast this with the sibling path `use_global_contract`, which is the only other place in the runtime that assigns a global-contract reference to an account, and which explicitly guards against exactly this condition: [2](#0-1) 

`use_global_contract` looks up `TrieKey::GlobalContractCode` and returns `ActionErrorKind::GlobalContractDoesNotExist` if the code is missing, refusing the state transition. The ETH-implicit path has no equivalent check.

The design intent is that node operators/protocol governance deploy the wallet-contract WASM as a global contract (`GlobalContractDeployMode::CodeHash`) matching `eth_wallet_global_contract_hash(chain_id)` before/at the point `EthImplicitGlobalContract` activates, as shown in the test setup: [3](#0-2) 

But nothing in `action_implicit_account_creation_transfer` verifies this precondition holds at the time an ETH-implicit account is actually created. Any ordinary user (or a bot deriving arbitrary secp256k1 addresses) can send a `Transfer` to any `0x...` account id and trigger creation, regardless of whether the referenced global contract exists on that shard.

By protocol design, ETH-implicit accounts are permanently locked to this operating model — they have no owner-controllable access key and cannot be deleted: [4](#0-3) 

So if the global contract hash is missing (never deployed, deployed to the wrong shard/hash, or the account was created in the gap between feature activation and deployment finishing its network-wide propagation — note global contract distribution is itself an asynchronous, receipt-based process per `initiate_distribution`), the account is created, funds are deposited, but the account can never be operated: no `FunctionCall` (including `rlp_execute`) can execute because `RuntimeContractIdentifier::resolve` finds no code, no `AddKey`/`DeleteAccount` is possible since ETH-implicit accounts only accept actions routed through the (non-existent) wallet contract's own logic, and the funds cannot be recovered.

### Impact Explanation
This produces permanently frozen funds triggered purely by an ordinary `Transfer` transaction from any unprivileged signer to an ETH-implicit account id — no validator or operator collusion is required. The affected funds (the transfer deposit, plus anything sent afterward, since the account id is externally derivable and reusable) become permanently inaccessible, matching the "permanently frozen funds" impact class.

### Likelihood Explanation
The precondition — the wallet contract global-code entry existing under the exact hash computed by `eth_wallet_global_contract_hash(chain_id)` on every shard — is an off-chain/global-contract-distribution dependency, not something enforced or asserted by the action handler itself. Any deployment gap, shard-propagation delay for the global contract distribution receipts, or hash mismatch between the deployed WASM and the hard-coded hash constants in `runtime/near-wallet-contract/src/lib.rs` silently produces unusable, fund-locking accounts rather than a rejected transaction — the runtime has no defense-in-depth check analogous to `use_global_contract`'s existence check.

### Recommendation
Before assigning `AccountContract::Global(global_contract_hash)` to a freshly created ETH-implicit account, verify the referenced global contract code actually exists in state (the same check already performed in `use_global_contract`). If it does not exist, either reject the transfer/account-creation (returning an appropriate action error) or fall back to a safe no-op path rather than creating an account permanently bound to nonexistent code.

### Proof of Concept
1. On a chain where the `EthImplicitGlobalContract` feature is active but the wallet-contract global contract (matching `eth_wallet_global_contract_hash(chain_id)`) has not yet been deployed/propagated to the shard hosting a given ETH-implicit address (e.g., right after feature activation, before the async global-contract distribution receipt in `initiate_distribution` completes on that shard, or due to any hash/deploy mismatch).
2. Any account sends `SignedTransaction::send_money` with a nonzero deposit to a derived `0x...` ETH-implicit account id (as in `integration-tests/src/tests/features/wallet_contract.rs::test_eth_implicit_account_creation`), which triggers `action_implicit_account_creation_transfer`.
3. The account is created with `AccountContract::Global(global_contract_hash)` pointing at code that doesn't exist on this shard (per `runtime/runtime/src/actions.rs:255-269`), and the deposit is now held by this account.
4. Any subsequent `rlp_execute` call (or any `FunctionCall`) against this account fails with a missing-code condition; the account cannot add a full access key or be deleted per protocol rules for ETH-implicit accounts, so the deposited balance is permanently unrecoverable.

```rust
pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
```
