### Title
Unchecked subtraction of `accounts_data_len_from_duplicates` can underflow `accounts_data_len` during index generation - ([File: accounts-db/src/accounts_db.rs])

### Summary
During `generate_index` (invoked when rebuilding `AccountsDb` from a snapshot), the accumulator's `accounts_data_len` field is decremented with a raw `-=` operator rather than a checked/saturating subtraction, unlike the parallel `capitalization` field in the same function, which uses `checked_sub(...).expect(...)`.

### Finding Description
In `AccountsDb::generate_index`, after computing per-duplicate-pubkey totals via `visit_duplicate_pubkeys_during_startup`, the code does:
```rust
total_accum.capitalization = total_accum
    .capitalization
    .checked_sub(capitalization_from_duplicates)
    .expect("capitalization cannot underflow");
total_accum.accounts_data_len -= accounts_data_len_from_duplicates;
``` [1](#0-0) 

The `capitalization` subtraction is checked and will panic loudly on underflow, while the semantically identical `accounts_data_len` subtraction is a raw, unchecked `u64` subtraction. `accounts_data_len_from_duplicates` is accumulated from `DuplicatePubkeysVisitedInfo::accounts_data_len_from_duplicates`, computed by summing per-account `data_len` across all-but-one version of duplicate pubkeys found while visiting the accounts index during startup/snapshot-load. This value is subtracted from `total_accum.accounts_data_len`, which was itself summed while scanning every account in every storage, counting every version of every account (including all duplicates) as `account.data.len()` when the account is non-zero-lamport.

This is a build-profile-dependent bug consistent with the M-01 report's "unchecked math" class: in debug builds `-=` panics identically to a failed `checked_sub`, but in release builds (the profile agave validators run) integer arithmetic wraps silently rather than panicking. Because the surrounding logic has no other guard for this specific field (only `capitalization` and `calculated_capitalization`'s later u64 cast are checked), any accounting mismatch between the "raw sum including duplicates" and "duplicates-only sum" for `accounts_data_len` will wrap to a near-`u64::MAX` value instead of panicking or saturating.

### Impact Explanation
The resulting `total_accum.accounts_data_len` is returned as `IndexGenerationInfo::accounts_data_len` [6](#0-5) , forwarded unchanged as `ReconstructedAccountsDbInfo::accounts_data_len` in `reconstruct_accountsdb_from_fields` [7](#0-6) , and passed directly into `Bank::new_from_snapshot(..., reconstructed_accounts_db_info.accounts_data_len, ...)` [4](#0-3) , which sets `accounts_data_size_initial`. This value underlies `Bank::load_accounts_data_size()` [5](#0-4) , which enforces the network's total accounts-data-size cap used to reject transactions that would allocate new account data beyond the limit.

A silently wrapped, near-`u64::MAX` `accounts_data_len` after a snapshot-load would cause a node to believe the accounts data size is essentially maxed out, causing it to reject all further account-data-allocating transactions — a state divergence between a node that booted from this snapshot (broken) and one that replayed the chain live from genesis (correct), i.e., an honest-node snapshot-vs-replay behavioral mismatch. This does not corrupt the bank hash or capitalization (those are separately checked/verified), but does corrupt validator-local resource-accounting state, potentially halting a node's ability to process legitimate transactions after a restart from a snapshot.

### Likelihood Explanation
Triggering this requires the very-unlikely situation where the summed `data_len` across a slot's duplicate account versions somehow exceeds the running total accumulated for all accounts across all bins processed so far by that point in the parallel fold, which should not happen under correct account/duplicate-detection logic. However, this is exactly the class of "should never happen, but let's use checked math to be defensive" scenario that the neighboring `capitalization` code already guards against — the report's original underlying bug class (unchecked math beside checked math for a parallel value) is directly present here. Likelihood is low under normal operation but the code path executes on every snapshot load/restart, and any latent bug in duplicate detection or accounting (e.g., in `visit_duplicate_pubkeys_during_startup`) would silently manifest as a wrapped value in release builds instead of a clear panic.

### Recommendation
Change `total_accum.accounts_data_len -= accounts_data_len_from_duplicates;` to use `checked_sub` with an explicit `.expect(...)` (mirroring the `capitalization` handling directly above it), so that any such underflow is caught deterministically in all build profiles rather than silently wrapping in release builds:
```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```

### Proof of Concept
Not exploitable via a single crafted transaction; would require a scenario (bug or otherwise) in which duplicate-pubkey data-length accounting temporarily exceeds the running total during `generate_index`. The defect is demonstrated structurally by comparing the two adjacent lines in `accounts_db.rs:6108-6112`: the `capitalization` field is protected with `checked_sub().expect(...)`, while `accounts_data_len`, populated and consumed through an identical accumulate/duplicate-subtract pattern, is not.
