### Title
Missing zero-address/empty validation on PC-initiated withdraw recipient (`OutboundTx.Recipient`) allows permanent loss of bridged funds - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`BuildOutboundsFromReceipt` decodes the `UniversalTxOutbound` event emitted by `UniversalGatewayPC.withdraw` and copies the attacker/user-controlled `Target` bytes directly into `OutboundTx.Recipient` with no validation that it is non-empty or non-zero, unlike the equivalent `Inbound` path which explicitly rejects empty/invalid recipients in `ValidateForExecution`. This is the same bug class as the cited FETH `withdrawFrom` finding: a withdrawal recipient that is never checked against the zero address before funds are irreversibly sent out.

### Finding Description
`DecodeUniversalTxOutboundFromLog` unpacks the `target` field straight from ABI-decoded event bytes into `event.Target` with no length/content check: [1](#0-0) 

`BuildOutboundsFromReceipt` then assigns this unchecked value directly to `outbound.Recipient` and proceeds to attach the outbound to the `UniversalTx`, emit `OutboundCreatedEvent`, and enqueue it for TSS signing/broadcast — with no zero-address or empty-string guard: [2](#0-1) [3](#0-2) 

By contrast, the `Inbound` type — which represents chain-to-PushChain deposits — has explicit recipient validation in `ValidateForExecution`, rejecting empty or malformed recipients before execution: [4](#0-3) 

No equivalent check exists for the outbound withdrawal path taken when a user calls the `UniversalGatewayPC.withdraw` function on Push Chain with an attacker/user-supplied `to`/`target` value. Once the `PRC20` has been burned/escrowed on Push Chain and the `OutboundTx` is created and handed to the `universalClient` TSS/tx-builder pipeline (EVM and SVM `tx_builder.go`), the destination-chain transfer targets whatever `Recipient` string was decoded — including a zero address (`0x000...0` or an all-zero Solana pubkey) — with the SVM builder observed to pass `recipientPubkey` straight into account lists without an `IsZero()` guard on the recipient itself (only unrelated PDA slots are zero-checked as "None" sentinels).

### Impact Explanation
An unprivileged user who calls the gateway's withdraw entry point with `to = address(0)` (or an all-zero non-EVM address) burns/locks their PRC20 on Push Chain, but the resulting `OutboundTx` will still be finalized, signed by TSS, and broadcast to the destination chain with a zero-address recipient. This causes permanent, unrecoverable loss of the user's bridged funds — the honest-validator/TSS pipeline faithfully executes an outbound to an unspendable address because nothing in the scoped Go code (`create_outbound.go`, `gateway_pc_event_decode.go`) rejects it before finalization. This falls squarely under the allowed impact "permanent loss ... of user or protocol-controlled funds" reachable purely from an ordinary unprivileged withdraw call.

### Likelihood Explanation
High from a triggerability standpoint: any user can call `withdraw`/trigger the `UniversalTxOutbound` event with a zero or malformed `target`, either by mistake or via a buggy integrating dApp/wallet, and the flow proceeds unmodified through quorum-observed nodes to TSS signing. There is no on-chain (contract) or off-chain (Go keeper) rejection point identified in the scoped repository for this specific field.

### Recommendation
Add explicit validation in `BuildOutboundsFromReceipt` (and equivalently in `AttachRescueOutboundFromReceipt` / `attachOutboundsToUtx`) that rejects `event.Target`/`outbound.Recipient` when it decodes to an empty value, the EVM zero address, or (for non-EVM destinations) an all-zero byte sequence, mirroring the `Inbound.ValidateForExecution` recipient checks. On rejection, fail the receipt-derived outbound creation (and surface this back to the originating PC transaction) rather than silently producing a `PENDING` outbound bound for an unspendable destination.

### Proof of Concept
1. User calls `UniversalGatewayPC.withdraw(to=0x000...000, amount, ...)` (or the non-EVM equivalent with an all-zero target) on Push Chain, burning/escrowing their PRC20.
2. The contract emits `UniversalTxOutbound` with `target = 0x` (zero-length or all-zero bytes).
3. `DecodeUniversalTxOutboundFromLog` decodes this into `event.Target` unchecked (`x/uexecutor/types/gateway_pc_event_decode.go:78`).
4. `BuildOutboundsFromReceipt` copies it into `outbound.Recipient` unchecked (`x/uexecutor/keeper/create_outbound.go:71`) and `attachOutboundsToUtx` finalizes/emits the outbound for TSS signing.
5. TSS signs and the relayer broadcasts a withdrawal to the destination chain's zero address, permanently losing the user's funds — with no step in the scoped Go code having rejected the zero/empty recipient.

Note: I was unable to fully inspect `x/uexecutor/types/outbound_tx.go`'s `ValidateBasic`/`Validate` method (only located it via grep, contents not retrieved) due to reaching the tool-call limit; it is possible that function performs some validation on `OutboundTx.Recipient` that would mitigate this finding, but it is evidently not invoked anywhere in the `BuildOutboundsFromReceipt` / `attachOutboundsToUtx` code path shown above, so the described gap stands based on the code actually exercised in this flow.
