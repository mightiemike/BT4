### Title
Stale liquidity-index cache overvalues zToken collateral after `socialize-debt` write-down within the same transaction - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`market.clar` maintains a per-transaction cache (`index-cache`, keyed by `{ timestamp: stacks-block-time, aid }`) of each vault's `index`/`lindex` to avoid repeated cross-contract calls (`accrue-and-cache`). Vault `lindex` (liquidity index) can also be mutated directly and immediately by `socialize-debt`, called from `liquidate`'s bad-debt path, bypassing `accrue-and-cache`/`vault-accrue`. Because the cache key only changes at block granularity, any subsequent read of `get-cached-indexes`/`accrue-and-cache` for that same `aid` **within the same transaction** returns the pre-write-down (stale, higher) `lindex`, which is used to price zToken collateral via `resolve-ztoken`.

### Finding Description
`index-cache` is populated once per `{timestamp, aid}` and never invalidated except by a new block: [1](#0-0) 

`socialize-debt` in every vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, etc.) writes `lindex` directly via `var-set`, completely independent of `accrue`/`vault-accrue` and of the market's cache: [2](#0-1) 

`liquidate` in `market.clar` calls `accrue-and-cache` first (populating the cache for the debt/collateral asset ids of *that* position), then later — after seizing collateral — calls the fold `socialize-debt-asset` (invoking `vault-socialize-debt` → vault `socialize-debt`) which mutates the vault's `lindex` in place when the borrower has no collateral left: [3](#0-2) [4](#0-3) 

After this write-down, the market's `index-cache` for that `aid` still holds the pre-socialization `lindex` for the remainder of the transaction (same `stacks-block-time`). `resolve-ztoken`, used for any zToken collateral pricing anywhere else in the same transaction, reads that stale cache entry instead of the vault's true post-write-down state: [5](#0-4) 

`borrow` also uses `accrue-and-cache`/`get-cached-indexes` for health checks and to price zToken collateral before its own borrow-index lookup: [6](#0-5) 

Because `accrue-and-cache` treats a cache hit as authoritative and never re-queries the vault once populated for a given `{timestamp, aid}`, any contract-call sequence within one atomic transaction that first triggers `liquidate` (causing `socialize-debt` to write down a vault's `lindex`) and then triggers a second market entry point (e.g. `borrow`, or another position inside `liquidate-multi`) that prices a zToken backed by the same vault, will use the overvalued, pre-write-down `lindex`. This is a single-transaction "cached value not invalidated when its source moves" defect: the value bound is the `index-cache` entry populated by the first `accrue-and-cache` call; the invalidating event is the vault's `socialize-debt` mutation of `lindex`; the later use is any subsequent `resolve-ztoken`/`get-cached-indexes` call for the same `aid` in the same transaction.

### Impact Explanation
zToken collateral is overvalued relative to the true, freshly-socialized vault state for the rest of the transaction. An attacker contract can chain calls in one transaction: (1) call `liquidate` on a victim position that has no other collateral, forcing `socialize-debt` to write down `lindex` for vault X; (2) within the same transaction, call `borrow` (or process another position in `liquidate-multi`) where the attacker holds zToken(X) as collateral — the health check and collateral valuation use the stale, higher `lindex`, permitting the attacker to borrow against collateral that is actually worth less post-socialization, or to avoid a liquidation that should otherwise trigger on their own position. This can result in newly originated under-collateralized debt (protocol insolvency risk / bad debt) — a Critical-class outcome (protocol insolvency), since the loan is issued against an inflated collateral valuation baked into the same atomic transaction that caused the devaluation.

### Likelihood Explanation
The precondition (`no-collateral-left` triggering bad-debt socialization) requires a borrower whose only collateral asset was fully seized by the liquidation and who still has debt remaining — a legitimate, reachable state during normal liquidations of unhealthy positions, not requiring any privileged access or DAO action. Chaining `liquidate` and `borrow` (or two `liquidate` calls sharing an `aid`) in a single transaction is straightforward via a caller contract that performs sequential `contract-call?`s, which Clarity fully supports within one atomic transaction/block. No governance, oracle, or third-party compromise is needed.

### Recommendation
Invalidate or refresh the `index-cache` entry for an `aid` whenever `socialize-debt` (or any other direct vault state mutation) changes that vault's `lindex`/`index`, e.g., by having `vault-socialize-debt` in `market.clar` explicitly `map-delete`/`map-set` the corresponding `index-cache` entry with the vault's freshly written values immediately after the vault call, so that all subsequent `accrue-and-cache`/`get-cached-indexes` reads within the same transaction observe the updated liquidity index rather than the pre-socialization cached value.

### Proof of Concept
1. Attacker deploys a wrapper contract that, in a single transaction, sequentially calls `market.liquidate(...)` on victim `B` (whose only collateral is fully seized, leaving remaining debt on vault `X`, triggering `socialize-debt` and writing down `lindex` for `X`) and then calls `market.borrow(...)` on behalf of the attacker, who holds `zX` (zToken for vault `X`) as collateral.
2. `liquidate` populates `index-cache` for `{timestamp, X}` at step "accrue-user-debts/collateral", then later invokes `socialize-debt-asset` → vault `X`'s `socialize-debt`, which `var-set`s `lindex` to a lower value in vault storage — but does not touch `market.clar`'s `index-cache`. [4](#0-3) 
3. The subsequent `borrow` call by the attacker (same transaction, same `stacks-block-time`) resolves `zX` collateral price via `resolve-callcode` → `resolve-ztoken` → `get-cached-indexes`, which hits the stale cache entry for `{timestamp, X}` still holding the pre-write-down `lindex`. [5](#0-4) 
4. The attacker's `is-healthy-with-mask` check in `borrow` passes using the inflated collateral valuation, allowing the attacker to originate debt beyond what the true (post-socialization) collateral value supports. [7](#0-6) 

Note: I was unable to fully verify, from the indexed excerpts alone, whether any additional guard elsewhere in the full transaction-execution path (e.g., a global re-accrual before every public entry point, or a cross-contract-call barrier) prevents chaining `liquidate` and `borrow` within one transaction; the market's own code as indexed shows no such barrier, but a full manual/dynamic trace through a Devin session would be needed to confirm end-to-end exploitability.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
