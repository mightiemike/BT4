### Title
`DelegateResourceParam` drops the `lock`/`lock_period` expiration fields when resource delegation is triggered from TVM smart contracts - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java])

### Summary
The `expiresAfter`-style bug class (a caller-supplied time-boundary field that exists in the protocol/API but is silently dropped in one code path while being fully honored in another) has a concrete analog in java-tron's resource-delegation feature. The `DelegateResourceContract` protobuf message carries `lock` and `lock_period` fields that determine how long a delegated resource remains locked/non-revocable, and the wallet-broadcast actuator path fully honors them, but the TVM-native-contract path used when a smart contract invokes resource delegation never carries these fields at all.

### Finding Description
`DelegateResourceContract` supports `lock` and `lock_period` to make a delegation irrevocable until an expiration time. In the actuator invoked by a broadcast transaction, this is fully implemented: `DelegateResourceActuator.validate()`/`execute()` read `getLock()`/`getLockPeriod()`, validate the lock period against `getMaxDelegateLockPeriod()`, and compute a real `expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL` that is persisted on the `DelegatedResourceCapsule`. [1](#0-0) [2](#0-1) [3](#0-2) 

By contrast, `DelegateResourceParam`, the data object used for the TVM native-contract call path (resource delegation triggered from inside a smart contract's execution), has no `lock`/`lockPeriod` fields at all: [4](#0-3) 

`DelegateResourceProcessor.execute()`/`delegateResource()` (the corresponding processor invoked for this path) always builds the `DelegatedResourceCapsule` with a hard-coded `expireTime` of `0` and always writes to the unlocked key (`createDbKeyV2(ownerAddress, receiverAddress, false)`), regardless of caller intent: [5](#0-4) 

This mirrors the reported bug class exactly: a time-limiting parameter that exists and is respected on one call path is never wired through on another reachable call path, so the resulting state permanently loses the caller's expiration/lock intent.

### Impact Explanation
Downstream contracts or protocols built on top of the TVM-invocable delegate-resource native contract cannot obtain a locked (non-revocable) delegation the way `DelegateResourceContract`-based delegations can. Any receiver-side logic (e.g., staking/voting/escrow dApps) that assumes a delegated resource will remain available and non-revocable for a committed period is defeated: the owner can call the analogous `UnDelegateResourceProcessor` at any time to reclaim the resource immediately, since no lock entry (`createDbKeyV2(..., true)`) is ever created and `expireTime` is always `0`. This is a state-transition/accounting correctness issue in the actuator/TVM native-contract layer that can cause unexpected loss of guaranteed resource availability for third parties relying on the lock semantics.

### Likelihood Explanation
This path is reachable by any transaction that triggers a smart contract calling the delegate-resource native contract — no privileged actor is required. The discrepancy is deterministic and code-visible (`DelegateResourceParam` structurally cannot carry lock data), so it will manifest every time this call path is used, though I could not fully verify from the indexed code whether the underlying Solidity-facing precompiled interface (constructed in `actuator/src/main/java/org/tron/core/vm/program/Program.java`) ever exposes a lock-capable calldata signature to callers, or whether it was simply designed as unlocked-only from the start. Because of this limitation in what the index exposes, the "field silently dropped" framing (rather than "feature intentionally absent") could not be conclusively confirmed against the Solidity-facing ABI.

### Recommendation
If the TVM-invocable delegate-resource native contract is intended to support locked delegations analogous to `DelegateResourceContract`, add `lock`/`lockPeriod` fields to `DelegateResourceParam`, thread them through `DelegateResourceProcessor.validate()`/`execute()`/`delegateResource()` with the same lock-period bounds checking (`getMaxDelegateLockPeriod()`) and expiration computation used in `DelegateResourceActuator`, and persist to the correct locked/unlocked key accordingly. If locking was intentionally excluded from the smart-contract-facing interface, this should be explicitly documented so downstream contract authors are not misled into assuming lock semantics are honored.

### Proof of Concept
1. Deploy or call a smart contract that invokes the native `delegateResource` functionality (via the TVM operation backed by `DelegateResourceProcessor`) to delegate BANDWIDTH/ENERGY to a receiver, with an expectation (e.g., encoded in the calling contract's business logic) that the delegation should remain locked for a period.
2. Observe that `DelegatedResourceCapsule` is written under the unlocked key with `expireTime = 0` (see `DelegateResourceProcessor.delegateResource`, lines 153–164).
3. Immediately call the corresponding `UnDelegateResourceProcessor`/`UnDelegateResourceContract` for the same owner/receiver pair — the delegation can be reclaimed with no lock-period restriction, contradicting the intended lock behavior that exists in the `DelegateResourceActuator` path.
