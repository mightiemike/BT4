## Title
Vault `deposit` mints zero shares for a nonzero underlying transfer when the share-conversion rounds to zero — ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

## Summary
`deposit` computes the shares to mint (`inkind`) via integer division (`mul-div-down`) and only checks that the *input* amount is nonzero and that the slippage bound is respected. It never checks that the *computed output* (`inkind`) is nonzero, unlike the sibling `redeem` function in the same contract, which explicitly guards against a zero output with `ERR-OUTPUT-ZERO`. When the vault's assets-to-shares ratio is high enough, a deposit amount can round down to `0` shares while the full underlying amount is still pulled from the depositor and added to vault assets, permanently transferring the depositor's principal to existing shareholders with zero compensation. This is reachable in a single transaction by any single caller — no front-running or second user is required.

## Finding Description
`convert-to-shares-preview` rounds down when converting deposit amount to shares: [1](#0-0) 

`deposit` uses this value as `inkind` and asserts only `amount > u0` and `inkind >= min-out` (slippage), plus the supply cap — but never asserts `inkind > u0`: [2](#0-1) 

Contrast this with `redeem` in the very same contract, which explicitly guards the analogous rounding case with `ERR-OUTPUT-ZERO`: [3](#0-2) 

The error code exists in the contract (`ERR-OUTPUT-ZERO`, `u803012`) and is used for `redeem`, but is simply omitted from `deposit`'s assertion list: [4](#0-3) 

This is the same rounding-to-zero root cause described in the external report (an amount divided by a ratio rounds to `0` and the code that consumes that zero value fails to guard against it), except here the omitted guard doesn't cause a permanent revert — it lets the transaction succeed while silently discarding the depositor's funds:
1. `receive-underlying` pulls the full `amount` of real underlying tokens from the depositor.
2. `ft-mint?` mints `inkind = 0` shares to the recipient.
3. `assets` is increased by `amount`.
4. The function returns `(ok 0)`.

The same pattern (deposit lacking the `inkind > u0` check present in redeem) is structurally identical across all tokenized vaults in the mainnet deployment (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`), since they share the same boilerplate deposit/redeem implementation.

## Impact Explanation
A depositor who calls `deposit` with a `min-out` of `u0` (the natural default when no slippage protection is desired, or when a front-end simply mirrors `min-out: 0` for "no minimum") and an `amount` small relative to the vault's assets-per-share ratio will have their entire deposited amount transferred into the vault's `assets` total but receive zero `zft` shares in return. Because vault share price (`total-assets-preview / total-supply-preview`) naturally grows over time as interest accrues while total supply of shares can remain comparatively static, this ratio can organically become large enough that ordinary-looking, small deposit amounts round to zero shares. The depositor's principal becomes an irrecoverable donation to existing shareholders — this is a permanent loss of funds for the depositor, executed atomically within a single transaction and requiring no interference from any other party.

## Likelihood Explanation
The condition depends purely on the vault's current `ta/ts` ratio (which grows monotonically with accrued interest and shrinks only when supply grows through deposits) and the size of the individual deposit relative to it — no attacker action, front-running, or governance/oracle manipulation is needed. Any user (or any integration/script) that computes `min-out` as `u0`, or that deposits a small dust amount relative to the current share price, will trigger this on their own. The likelihood increases the longer a vault operates and accrues interest without proportional new deposits, which is the expected steady-state behavior of a lending vault.

## Recommendation
Add the same `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check to `deposit` that already exists in `redeem`, in all `v0-vault-*.clar` contracts, before minting shares and updating `assets`. Alternatively/additionally, round the shares-preview calculation up (`mul-div-up`) for deposits to ensure `amount` is never fully absorbed without a corresponding nonzero share mint.

## Proof of Concept
1. Vault state (after accrued interest): `total-assets-preview = 2,000,000_000000` (2,000,000 USDC, 6 decimals), `total-supply-preview = 1,000_000000` (1,000 zUSDC) → share price ≈ 2,000 USDC/zUSDC.
2. A depositor calls `deposit(amount: u500, min-out: u0, recipient: depositor)` (500 raw units = 0.0005 USDC).
3. `inkind = convert-to-shares-preview(500) = mul-div-down(500, 1000_000000, 2000000_000000) = floor(0.25) = u0` — see [1](#0-0) .
4. Guard checks: `amount > u0` → passes (`500 > 0`). `inkind >= min-out` → passes (`0 >= 0`). Supply cap check passes. There is no `inkind > u0` check.
5. `receive-underlying(500, account)` transfers 500 units of real USDC from the depositor into the vault.
6. `ft-mint? zft u0 recipient` mints 0 shares.
7. `assets` is incremented by 500; the call returns `(ok u0)`.
8. The depositor has permanently lost 500 units of USDC with no shares, no revert, and no recourse — the funds are now embedded in `assets` and shared among all existing `zft` holders.

```text
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

```text
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (account contract-caller)
      (CAP-SUPPLY (var-get cap-supply))
      (current-assets (var-get assets))
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))

    (print {
      action: "deposit",
      caller: contract-caller,
      data: {
        depositor: account,
        recipient: recipient,
        amount: amount,
        shares-minted: inkind,
        assets: (+ current-assets amount)
      }
    })

    (ok inkind)))

(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    (states (var-get pause-states))
    (u (try! (accrue)))
    (account contract-caller)
    (current-assets (var-get assets))
    (balance (get-balance-internal account))
    (balance-check (asserts! (>= balance amount) ERR-INSUFFICIENT-BALANCE))
    (available-assets (get-available-assets))
    (inkind (convert-to-assets-preview amount)))

  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  (asserts! (>= available-assets inkind) ERR-INSUFFICIENT-LIQUIDITY)

  (try! (ft-burn? zft amount account))
  (try! (send-underlying inkind recipient))
  (var-set assets (- current-assets inkind))
```
