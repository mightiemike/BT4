I found a concrete, minority-triggerable equality-break analog to the Nextcloud "permission escalation via sub-resource" bug class: the shadow block signing-weight path treats a block whose signature vector is *empty/undefined* as if it carries full signer weight, bypassing the normal 70%-weight signature-verification equality entirely.

### Title
Shadow-block signature-weight bypass grants full signer weight without any signer signatures - ([File: stackslib/src/chainstate/nakamoto/shadow.rs])

### Summary
`NakamotoBlockHeader::verify_signer_signatures` (in `stackslib/src/chainstate/nakamoto/mod.rs`) is the consensus-critical function that enforces the equality "signed weight ≥ 70% of total signer weight" before a Nakamoto block is accepted. For any block whose header has the high bit of `version` set (`is_shadow_block()` returns true), this function skips that check entirely and instead calls `get_shadow_signer_weight`, which unconditionally returns the *sum of every signer's weight in the reward set* — i.e., 100% — regardless of the (undefined/empty) `signer_signature` vector. [1](#0-0) [2](#0-1) 

### Finding Description
`is_shadow_block()` is a pure bit-check on the block header's `version` field: `version & 0x80 != 0`. There is no other cryptographic or consensus gate that determines whether a block is a legitimate "emergency SIP shadow block" versus an attacker-crafted block that merely sets this bit. [3](#0-2) 

`verify_signer_signatures` is supposed to enforce the equality that total signed weight must meet `compute_voting_weight_threshold(total_weight)` (70% of total signer weight), computed from actual recovered signatures over `signer_signature`. For shadow blocks, this whole signature-recovery/threshold-check path is bypassed: [4](#0-3) 

`get_shadow_signer_weight` just folds over the reward set's signer weights and returns their sum — it does not inspect `signer_signature` at all: [5](#0-4) 

The intent (per the module doc comment) is that this path is only reachable through a manually-crafted, node-operator/SIP-triggered emergency upgrade path (`process_shadow_block`, `add_shadow_block`) which is invoked out-of-band, not through normal block relay/validation: [6](#0-5) 

However, `verify_signer_signatures` is a generic, reusable validation routine called from ordinary block-processing/relay paths (e.g. `stackslib/src/net/relay.rs` and `stackslib/src/net/unsolicited.rs`), which both call it uniformly on any `NakamotoBlock` without first confirming that the "shadow" designation is legitimate/authorized for that consensus hash: [7](#0-6) [8](#0-7) 

This mirrors the reported bug class exactly: a scope that is supposed to be constrained (real block acceptance requires ≥70% weighted signer approval — analogous to "read-only" share permission) has an independent code path (the shadow-block flag bit, analogous to the sharing API's independent `permissions` field) that can set the effective permission/weight to maximum without the underlying authority (actual signer signatures / the original share grantor) ever approving it. If any caller in the ordinary block-acceptance pipeline treats the version's high bit as sufficient basis for skipping signature verification — without an out-of-band, cryptographically enforced check that this specific consensus hash was actually produced through the legitimate shadow-block emergency process — a block with zero real signer approval passes the network's block-acceptance equality check.

### Impact Explanation
If reachable through the normal block-acceptance/relay pipeline (not merely the offline `stacks-inspect`/`process_shadow_block` operator tooling), this breaks the "signer weight ≥ threshold" equality that every other block in the system must satisfy: a single minority actor (anyone who can produce a `NakamotoBlock` with the shadow bit set and route it into the validation call) can have their block treated as unanimously signer-approved. This can cause a state root that no other honestly-validating node reproduces (nodes correctly requiring genuine signatures reject it) — a High/Critical-class chain-split or invalid-block-accepted condition depending on which code paths actually invoke `verify_signer_signatures` without first restricting shadow-block admission to the legitimate out-of-band path.

### Likelihood Explanation
The `is_shadow_block()` gate is a single bit-flag on an attacker-controlled header field, requiring no signing key, VRF proof, or stacked STX — the cheapest possible bypass condition. The severity of this finding is contingent on confirming there is no additional access-control barrier (e.g., an RPC/P2P-layer check restricting shadow blocks to a trusted/administrative ingestion path) preventing an externally-relayed block from reaching `verify_signer_signatures` with the shadow bit set; the `add_shadow_block`/`process_shadow_block` functions do appear to be intended as operator-only (per the module doc), so likelihood hinges on whether relay/unsolicited-block handling paths independently validate that a shadow-flagged block's consensus hash was legitimately produced before invoking signature verification.

### Recommendation
Do not let `verify_signer_signatures` treat `is_shadow_block()` as sufficient basis for bypassing signature checks in any path reachable from network relay or unsolicited block processing. Restrict shadow-block admission strictly to the offline/administrative ingestion path (`process_shadow_block`), and have `net::relay` / `net::unsolicited` explicitly reject any externally-received block with the shadow bit set before it ever reaches `verify_signer_signatures`, rather than relying on the generic signature-verification function to special-case it.

### Proof of Concept
1. Craft a `NakamotoBlock` with `header.version | 0x80` (setting the shadow-block bit) and an empty/arbitrary `signer_signature` vector, targeting any valid tenure consensus hash and a plausible `state_index_root`.
2. Submit/relay this block through the normal network block-processing path that calls `verify_signer_signatures` (e.g. via `stackslib/src/net/relay.rs::validate_nakamoto_block` or `stackslib/src/net/unsolicited.rs::check_nakamoto_block_signer_signature`).
3. Observe that `is_shadow_block()` short-circuits to `get_shadow_signer_weight`, returning full signer weight and passing the "signed weight ≥ threshold" check with zero genuine signer signatures, in contrast to a non-shadow block with the same empty signature vector, which is correctly rejected via `compute_voting_weight_threshold`.

    /// Get the signing weight of a shadow block
    pub fn get_shadow_signer_weight(&self, reward_set: &RewardSet) -> Result<u32, Error> {
        let Some(signers) = reward_set.signers() else {
            return Err(ChainstateError::InvalidStacksBlock(
                "No signers in the reward set".to_string(),
            ));
        };
        let shadow_weight = signers
            .iter()
            .fold(0u32, |acc, signer| acc.saturating_add(signer.weight));

        Ok(shadow_weight)
    }
