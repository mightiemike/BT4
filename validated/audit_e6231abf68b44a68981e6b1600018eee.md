### Title
Attacker-Controlled `tip` Can Overflow-Panic `GasVector::cost`, Crashing Nodes During Fee Computation - (File: `crates/starknet_api/src/execution_resources.rs`)

### Summary
`GasVector::cost()` adds a transaction's user-supplied `tip` directly to the protocol `l2_gas_price` using `checked_add(...).unwrap_or_else(|| panic!(...))`. Because `tip` is an attacker-controlled field of any V3 transaction, and because the exact same combination (`gas_price + tip`) is handled safely elsewhere in the codebase via `saturating_add`, this is an inconsistent, unguarded arithmetic path that an unprivileged transaction sender can drive to overflow, triggering a Rust panic instead of a graceful rejection.

### Finding Description
`GasVector::cost` computes the fee token cost of a gas vector and is reached whenever a node (proposer or validator, during execution/re-execution) needs to price a transaction's resource consumption: [1](#0-0) 

Specifically:
```
let tipped_l2_gas_price =
    gas_prices.l2_gas_price.checked_add(tip.into()).unwrap_or_else(|| {
        panic!(
            "Tip overflowed: addition of L2 gas price ({}) and tip ({}) resulted in \
             overflow.",
            gas_prices.l2_gas_price, tip
        )
    });
``` [2](#0-1) 

`tip` originates from the transaction itself (a V3 invoke/declare/deploy-account transaction field) and is therefore fully attacker-controlled up to its declared type's maximum. If `tip` is large enough that `l2_gas_price + tip` exceeds `u128::MAX`, `checked_add` returns `None` and the `unwrap_or_else` branch panics.

Critically, the codebase already recognizes this exact overflow risk and mitigates it in a sibling function, `ValidResourceBounds::max_possible_fee`, which performs the identical operation using `saturating_add` instead of a panicking `checked_add`:

```
l2_gas.max_amount.saturating_mul(
    l2_gas.max_price_per_unit.saturating_add(tip.into())
)
``` [3](#0-2) 

This shows the intended, safe design pattern for tip+price arithmetic is "saturate," yet `GasVector::cost` — which is used for the *actual* fee charged during execution, not merely bound estimation — uses the unsafe panicking pattern instead. This mirrors the reported analog precisely: an unbounded/extreme user-supplied numeric input (there, `totalGrantAmount`; here, `tip`) is fed into arithmetic that is guarded in some code paths but not others, and the unguarded path aborts computation entirely instead of safely clamping.

### Impact Explanation
`GasVector::cost` is invoked during fee/gas-vector computation paths that run as part of transaction execution and re-execution (including by the Starknet OS / re-execution flow and blockifier fee utilities that consume `GasVector`/`GasPriceVector`). A panic inside this call, if not caught by a `catch_unwind` boundary in the calling execution pipeline, aborts the executing thread/process. Because every honest node that attempts to execute or re-execute the same malicious transaction (proposer during block building, validators during re-execution, full nodes syncing the block) would hit the identical panic on identical inputs, this can manifest as a synchronized crash/DoS across the network when processing a single crafted transaction — i.e., a network unable to confirm new transactions, rather than a localized, single-user issue. At minimum, it is a reliable single-transaction DoS of any node that attempts to price/execute it, directly analogous to the reported "bricks `getVestedAmount()`/`claim`" DoS impact.

### Likelihood Explanation
Likelihood is high for triggering the panic itself: `tip` is a plain transaction field set by the sender with no evidence found (within the code explored) of an upper bound enforced at the gateway that would prevent `l2_gas_price + tip` from exceeding `u128::MAX`, since `l2_gas_price` is itself a `u128` and `tip`'s type allows large values. I was not able to fully verify, given tool budget, (a) the exact numeric type/max bound enforced on `tip` at gateway admission, and (b) whether the execution pipeline wraps this call in `catch_unwind` such that a panic would be caught and converted into a normal transaction rejection rather than crashing the node/thread. These two points materially affect whether this is a full node-crash DoS (High) or a caught/contained panic that only fails one transaction gracefully (Medium/Low). This uncertainty should be resolved before treating severity as final.

### Recommendation
- Replace `checked_add(...).unwrap_or_else(|| panic!(...))` in `GasVector::cost` (crates/starknet_api/src/execution_resources.rs, lines 157-164) with `saturating_add`, consistent with `ValidResourceBounds::max_possible_fee`, or explicitly validate/bound `tip` at the gateway (stateless transaction validation) so it can never combine with `l2_gas_price` to overflow `u128`.
- Audit all other `unwrap_or_else(|| panic!(...))` overflow-guards on attacker-influenced values in the fee/gas computation path (e.g., `to_discounted_l1_gas`, `ArchivalDataResources::to_gas_vector`, `ComputationResources::to_gas_vector`) for the same inconsistency between "saturate" and "panic" handling, and confirm whether execution paths are protected by `catch_unwind` boundaries; if not, convert these panics into `TransactionExecutionError`/rejection paths.

### Proof of Concept
1. Craft a V3 invoke transaction and set its `tip` field to a value close to `u128::MAX` (subject to whatever gateway-level bound, if any, exists on `tip`).
2. Submit the transaction to a sequencer node.
3. During fee/gas-vector cost computation, `GasVector::cost` executes `gas_prices.l2_gas_price.checked_add(tip.into())`; with `l2_gas_price + tip > u128::MAX`, `checked_add` returns `None`, and the `unwrap_or_else` panics with `"Tip overflowed: ..."`.
4. Observe whether the panic propagates and aborts the executing node/thread (full verification of this final step requires runtime testing, which was not performed here). [1](#0-0) [4](#0-3)

    /// Computes the cost (in fee token units) of the gas vector (panicking on overflow).
    pub fn cost(&self, gas_prices: &GasPriceVector, tip: Tip) -> Fee {
        let tipped_l2_gas_price =
            gas_prices.l2_gas_price.checked_add(tip.into()).unwrap_or_else(|| {
                panic!(
                    "Tip overflowed: addition of L2 gas price ({}) and tip ({}) resulted in \
                     overflow.",
                    gas_prices.l2_gas_price, tip
                )
            });

        let mut sum = Fee(0);
        for (gas, price, resource) in [
            (self.l1_gas, gas_prices.l1_gas_price, Resource::L1Gas),
            (self.l1_data_gas, gas_prices.l1_data_gas_price, Resource::L1DataGas),
            (self.l2_gas, tipped_l2_gas_price, Resource::L2Gas),
        ] {
            let cost = gas.checked_mul(price.get()).unwrap_or_else(|| {
                panic!(
                    "{resource} cost overflowed: multiplication of gas amount ({gas}) by price \
                     per unit ({price}) resulted in overflow."
                )
            });
            sum = sum.checked_add(cost).unwrap_or_else(|| {
                panic!(
                    "Total cost overflowed: addition of current sum ({sum}) and cost of \
                     {resource} ({cost}) resulted in overflow."
                )
            });
        }
        sum
    }

    /// Returns the maximum possible fee that can be charged for the transaction.
    /// The computation is saturating, meaning that if the result is larger than the maximum
    /// possible fee, the maximum possible fee is returned.
    pub fn max_possible_fee(&self, tip: Tip) -> Fee {
        match self {
            ValidResourceBounds::L1Gas(l1_bounds) => {
                l1_bounds.max_amount.saturating_mul(l1_bounds.max_price_per_unit)
            }
            ValidResourceBounds::AllResources(AllResourceBounds {
                l1_gas,
                l2_gas,
                l1_data_gas,
            }) => l1_gas
                .max_amount
                .saturating_mul(l1_gas.max_price_per_unit)
                .saturating_add(
                    l2_gas
                        .max_amount
                        .saturating_mul(l2_gas.max_price_per_unit.saturating_add(tip.into())),
                )
                .saturating_add(
                    l1_data_gas.max_amount.saturating_mul(l1_data_gas.max_price_per_unit),
