### Title
Unanchored `exitIframeRE` prefix regex + `embedded=1` query param bypasses the install/session gate in `ensureInstalledOnShop` - (File: `packages/apps/shopify-app-express/src/middlewares/ensure-installed-on-shop.ts`)

### Summary
`ensureInstalledOnShop` builds `exitIframeRE` from `config.exitIframePath` using `new RegExp('^' + config.exitIframePath, 'i')` with no end-boundary anchor and no regex-escaping, so it matches any URL that merely *starts with* the configured path, not just the exact exit-iframe route. Combined with the fact that satisfying the `req.query.embedded === '1'` branch skips *all* further access-token/session validation, an unauthenticated attacker can reach `next()` (the protected route handler) for any URL sharing the `exitIframePath` prefix without ever completing OAuth or holding a valid session.

### Finding Description
The gate is:
```ts
const exitIframeRE = new RegExp(`^${config.exitIframePath}`, 'i');
if (!session && !req.originalUrl.match(exitIframeRE)) {
  return redirectToAuth({req, res, api, config});
}
``` [1](#0-0) 

Because the regex is only anchored with `^` and not terminated with a path-boundary (`/`, `$`, or `?`), any `req.originalUrl` that begins with the configured prefix matches — e.g. `exitIframePath = '/exitiframe'` matches `/exitiframe-admin-panel`, `/exitiframestats`, etc. — even though those are unrelated routes.

Once this first check is bypassed (or the session simply doesn't exist and the URL happens to match), execution falls through to:
```ts
if (api.config.isEmbeddedApp && req.query.embedded !== '1') {
  if (await sessionHasValidAccessToken(api, config, session)) { ... }
  else { return redirectToAuth(...); }
}
addCSPHeader(api, req, res);
return next();
``` [2](#0-1) 

If the attacker also supplies `embedded=1` (fully attacker-controlled, unsigned query parameter), this second block is skipped entirely — `sessionHasValidAccessToken` is never called — and the middleware proceeds straight to `next()`, handing control to the downstream route/middleware chain with **no session, no access token, and no shop-installation verification at all**.

This is exactly the scenario the existing test suite intentionally allows for the *real* exit-iframe route:
```ts
it('does NOT redirect to auth if shop NOT installed AND url is exit iFrame path', async () => {
  ...
  await request(app)
    .get(`/exitiframe?shop=${TEST_SHOP}&host=${encodedHost}&embedded=1`)
    .expect(200);
});
``` [3](#0-2) 

The test only exercises the exact path `/exitiframe`, not adjacent paths that share the same prefix, so the regex's lack of boundary anchoring was never verified. In real deployments, `ensureInstalledOnShop()` is typically mounted broadly (e.g. `app.use(shopify.ensureInstalledOnShop())` protecting the whole app, including a catch-all frontend route), and `exitIframePath` defaults to the short, generic `/exitiframe` string set in `validateAppConfig`:
```ts
exitIframePath: '/exitiframe',
``` [4](#0-3) 

Any other route path in the app whose name happens to begin with `exitiframe` (or any prefix relationship, since the string isn't escaped/anchored either) inherits this bypass.

### Impact Explanation
An anonymous, unprivileged attacker can reach the protected middleware chain (`next()`) for routes gated by `ensureInstalledOnShop` without ever completing OAuth or holding a session cookie/token, purely by crafting a URL path with the exit-iframe prefix and adding `embedded=1`. This defeats the core purpose of the middleware — "verifies that the request received is for a shop that has installed the app when rendering HTML" — allowing unauthenticated access to whatever the app serves at that route (frontend HTML/JS, or any logic in the next handler that trusts having passed this gate). This maps to Shopify's "authorization bypass leading to unauthorized access to app functionality/content" impact class.

### Likelihood Explanation
Preconditions match the ones stated in the question and are realistic, not exotic: `config.future.tokenExchange` disabled (the OAuth Auth Code flow, still the common/default flow) and `exitIframePath` at its library default `/exitiframe`, a short generic string. The attacker needs no secrets, no privileged role, and no session — only the ability to send a single unauthenticated GET request with attacker-chosen path and query string. This is trivially repeatable and requires no timing or race conditions.

### Recommendation
Anchor the exit-iframe check to an exact path match (or a path-segment boundary) instead of a bare prefix, and escape any regex metacharacters in `config.exitIframePath`:
```ts
const escaped = config.exitIframePath.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
const exitIframeRE = new RegExp(`^${escaped}(?:[/?]|$)`, 'i');
```
Additionally, do not let `req.query.embedded === '1'` alone skip `sessionHasValidAccessToken`; that check should still run (or the route should require the presence of a valid session) even when the request claims to be embedded, so that an unauthenticated caller cannot use the `embedded=1` flag to skip session verification altogether.

### Proof of Concept
```ts
// packages/apps/shopify-app-express/src/middlewares/__tests__/ensure-installed-on-shop.test.ts
it('bypasses install/session check via prefix-confused path + embedded=1', async () => {
  // No session stored -> shop is NOT installed.
  const encodedHost = Buffer.from(SHOPIFY_HOST, 'utf-8').toString('base64');

  // Mount a route that merely starts with the exitIframePath prefix,
  // simulating a real app route ('/exitiframe-admin-panel') protected
  // by the same global middleware.
  app.use('/exitiframe-admin-panel', shopify.ensureInstalledOnShop());
  app.get('/exitiframe-admin-panel', async (_req, res) => {
    res.send('sensitive-panel-content');
  });

  const response = await request(app)
    .get(`/exitiframe-admin-panel?shop=${TEST_SHOP}&host=${encodedHost}&embedded=1`)
    .expect(200); // EXPECTED (secure): 302 redirect to auth via redirectToAuth

  expect(response.text).toBe('sensitive-panel-content'); // reached next() with no session
});
```
Expected secure behavior: the request should be redirected to `redirectToAuth` (302) because no session exists for the shop; instead, due to the unanchored prefix match plus `embedded=1` skipping the access-token check, the handler is reached directly (200), confirming the bypass.
