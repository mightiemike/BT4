### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, letting replay-verify accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the single correctness check used by the replay-verify tooling to confirm that freshly re-executed transaction output matches the authenticated `TransactionInfo` recovered from backup/archive, only compares status, gas, write-set hash, and event root hash. It explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the freshly-computed state root, a gap acknowledged directly in the code's own TODO comment.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates a re-executed `TransactionOutput` against an expected `TransactionInfo` by checking status, gas used, the write-set hash (`state_change_hash`), and the event root hash. The function's own comment states:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

This function is the sole per-transaction verification gate used by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes transactions read from a backup and calls `executed_outputs[idx].ensure_match_transaction_info(...)` to decide pass/fail: [2](#0-1) . Because the comparator never touches `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a divergence between the state root produced by local re-execution and the state root embedded/authenticated in the archived `TransactionInfo` (e.g., from a corrupted backup, a non-deterministic bug in state-checkpoint/JMT construction, or a native "position" state root computed incorrectly) is invisible to this check and the replay is reported as successful.

The `TransactionInfo` type itself carries these checkpoint hashes as first-class committed/proof-bearing fields (`maybe_state_checkpoint_hash`, `maybe_hot_state_checkpoint_hash`, `maybe_position_state_checkpoint_hash`) built during normal commit in `DoLedgerUpdate::assemble_transaction_infos` [3](#0-2) , so these hashes are exactly the state-commitment fields the state-integrity gate cares about, yet the one place designed to independently re-verify archived data against re-execution silently omits them.

### Impact Explanation
This breaks the "replay/restore/proof-verification must independently re-derive and confirm the committed state root" invariant. If a state root (state checkpoint, hot-state checkpoint, or native position checkpoint) stored in an archive/backup diverges from what correct re-execution actually produces — whether from backup corruption, a bug in checkpoint hash computation, or non-determinism in state-checkpoint construction — the replay-verify tool (the primary tool used to catch exactly this class of bug before/after mainnet incidents) will report the chunk as verified/passing. This directly undermines the auditability and detection of a wrong state root being treated as valid, which is the impact category explicitly called out ("Wrong accumulator root ... state proof accepted as valid").

### Likelihood Explanation
The gap is deterministic and always present whenever `replay_on_archive` is run — it doesn't require any adversarial network condition, only a divergence between locally re-executed state roots and the ones already persisted/backed up (which can arise from bugs elsewhere in the checkpoint/JMT pipeline, from backup corruption, or from any node whose local re-execution disagrees with the canonical historical state root for reasons the write-set/event checks don't cover). The condition is acknowledged by an in-repo TODO tied to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, confirming maintainers are aware the check is incomplete for that feature path, but the gap already exists for the ordinary `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields today, independent of that feature flag.

### Recommendation
Extend `ensure_match_transaction_info` to compute the actual state-checkpoint hash (and hot-state/position checkpoint hashes when applicable) from re-execution and compare them against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, failing the check (and thus `replay_on_archive`) on any mismatch, before any feature that relies on these roots (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled.

### Proof of Concept
1. Take a backup/archive whose stored `TransactionInfo` for some version has a `state_checkpoint_hash` that does not match the state actually reachable by correctly re-executing all prior transactions (simulate via a deliberately corrupted backup file, or a state-checkpoint computation bug).
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`) over the range covering that version.
3. `Verifier::execute_and_verify` calls `ensure_match_transaction_info` [4](#0-3) , which checks status/gas/write-set-hash/event-root-hash only [5](#0-4)  and returns `Ok(())` despite the state checkpoint hash mismatch.
4. The tool reports the replay as fully verified even though the archived state root does not match what correct execution produces.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
