### Title
Replay-verification and chunk-execution commit accept transaction outputs whose position/hot-state checkpoint roots diverge from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single invariant check used by chunk execution/state-sync commit and by replay-verify tooling to confirm a locally re-derived `TransactionOutput` matches the authenticated `TransactionInfo` bound to a ledger-info-signed accumulator leaf. The function only checks status, gas used, write-set hash, and event root hash — it explicitly does **not** check the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields carried by `TransactionInfo`, per the code's own TODO comment.

### Finding Description
`ensure_match_transaction_info` [1](#0-0)  validates only 4 of the fields that `TransactionInfo` V1 authenticates: status, gas_used, `state_change_hash` (write-set hash), and `event_root_hash`. The function's own comment documents the gap explicitly: [2](#0-1)  — it ignores `state_checkpoint_hash`/`hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, and states this allows "replay-verify tooling (e.g. db-tool's `replay_on_archive`) [to] report a successful replay even when the authenticated position state root diverges from local execution."

This matters because `TransactionInfo` (V1) carries these checkpoint hashes as part of what's hashed into the accumulator leaf that the ledger-info signature authenticates [3](#0-2) . This means the state-checkpoint/hot-state/position roots are consensus-critical committed values, yet the one reusable function meant to cross-check a locally computed `TransactionOutput` against the authenticated `TransactionInfo` skips exactly those fields. `ensure_match_transaction_info` is invoked from `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`, all of which are code paths for state-sync chunk application, replay, and debugging/verification tooling that rely on this check as their state-commitment integrity gate.

### Impact Explanation
If a divergence exists between the locally-computed position/hot-state checkpoint root and the one embedded (and signed over) in the authenticated `TransactionInfo`, this check would not catch it — silently accepting a `TransactionOutput` (and by extension, committing/replaying against it) whose derived state root does not match what consensus actually signed. This is a genuine "authenticated proof/root accepted without verifying against the correct committed value" class of bug: a divergence in position-state or hot-state tree roots (used for accelerated read paths / state-sync fast paths per the "trading-native" feature referenced by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) would go undetected during chunk execution commit and during replay-verify audits, which is precisely the class of hard-fork-only-divergence-during-commit/replay impact in scope.

### Likelihood Explanation
This is a real, standing gap in the codebase (self-documented via TODO), not a speculative one. However, the impact is contingent on the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature/flag being enabled and on there actually existing a code path that produces a position/hot-state checkpoint hash divergent from the correct value — I was not able to fully trace, within the remaining tool budget, whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently active on mainnet or gated behind an unshipped feature, nor pin down every producer of `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` to confirm an achievable, unprivileged root-cause divergence exists today. The TODO comment itself frames this as a known pre-existing gap to be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," suggesting the feature may not yet be fully active, which would reduce current exploitability. Given this uncertainty, I can confirm the missing-invariant defect with certainty but cannot confirm the surrounding pieces make this fully exploitable at high/critical severity on mainnet today without further investigation of `storage/aptosdb/src/db/aptosdb_reader.rs`'s `COMPUTE_TRADING_NATIVE_STATE_ROOTS` usage and the `ProvablePositionStateSummary`/`ProvableStateSummary` machinery.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the locally computed equivalents whenever the corresponding on-chain feature (e.g. `HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled for the `TransactionInfo` V1 variant, before this function is relied upon as a commit/replay-verify gate.

### Proof of Concept
Not constructible from static review alone — this finding is a documented missing-invariant defect (verified directly in code and its own TODO) rather than a demonstrated end-to-end exploit; confirming full exploitability requires tracing whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are active and identifying a producer of an incorrect position/hot-state checkpoint hash, which was not completed within the available investigation.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
