### Title
BatchValidateSign MAX_SIZE guard bypassed pre-fork, enabling unbounded RecoverAddrTask submission to shared thread pool - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `BatchValidateSign` precompile's `sigArraySize`/`addrArraySize` bound check against `MAX_SIZE` (16) is only enforced inside a `VMConfig.allowTvmSelfdestructRestriction()` conditional, rather than unconditionally. On any deployment/fork state where that hard-fork flag has not yet been activated (the default state prior to governance activation), the size guard is skipped entirely, letting an attacker submit arbitrarily large signature/address arrays that are each turned into a `RecoverAddrTask` and pushed into the shared `ExecutorServiceManager` thread pool.

### Finding Description
`PrecompiledContracts.java` defines `BatchValidateSign` with a `MAX_SIZE = 16` constant and computes `sigArraySize`/`addrArraySize` from the raw calldata, then submits one `RecoverAddrTask` per signature/address pair to a shared worker pool sized at `Runtime.availableProcessors()/2+1` threads. The size-bound check that rejects (`Pair.of(true, DATA_FALSE)`) inputs exceeding `MAX_SIZE` is wrapped in `if (VMConfig.allowTvmSelfdestructRestriction()) { ... }`, meaning it only executes when that specific hard-fork proposal has been activated on-chain. Before that fork flag is turned on (or on any network/fork copy where it remains disabled), `doExecute` proceeds to the `workers.submit` loop without bounding array size, so an attacker-controlled `TriggerSmartContract` call reaching `BatchValidateSign.doExecute` can supply signature/address arrays far larger than 16, queuing a correspondingly large number of `RecoverAddrTask` jobs onto the shared thread pool used by all concurrently executing contracts. The energy/fee accounting in `getEnergyForData` does not by itself prevent thread-pool saturation from being reached before energy exhaustion halts execution, since the guard that was intended to bound resource usage is the one being bypassed.

### Impact Explanation
Because `ExecutorServiceManager`'s pool is shared across all VM executions on a node, an attacker who submits a single transaction with an oversized signature/address array (while the fork flag is inactive) can flood the pool with excess `RecoverAddrTask` jobs, delaying or starving legitimate concurrent contract calls relying on the same executor — a node-level availability/DoS impact rather than a state-corruption one.

### Likelihood Explanation
This requires the specific precondition that `allowTvmSelfdestructRestriction()` is not yet active for the chain being targeted (true by default until the corresponding hard-fork proposal is passed, and true unconditionally for any fork/testnet that never activates it). Given that precondition, the exploit is trivially reproducible: any unprivileged account can call `TriggerSmartContract` against a contract invoking the `BatchValidateSign` precompile with a crafted array size, requiring no special privileges.

### Recommendation
Move the `sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE` check outside the `VMConfig.allowTvmSelfdestructRestriction()` conditional so it is enforced unconditionally regardless of fork-activation state, consistent with the stated invariant that public precompile calls must always be bounded.

### Proof of Concept
```java
// framework/src/test/java/org/tron/common/runtime/vm/BatchValidateSignMaxSizeTest.java
@Test
public void testMaxSizeEnforcedRegardlessOfForkFlag() {
    for (boolean flag : new boolean[]{true, false}) {
        VMConfig.initAllowTvmSelfdestructRestriction(flag ? 1 : 0);
        byte[] input = buildBatchValidateSignInput(/* sigArraySize */ 17, /* addrArraySize */ 17);
        BatchValidateSign contract = new BatchValidateSign();
        Pair<Boolean, byte[]> result = contract.execute(input);
        // Expect rejection in both fork states
        assertTrue(result.getLeft());
        assertArrayEquals(DATA_FALSE, result.getRight());
    }
}
```
Expected current (vulnerable) behavior: assertion fails when `flag == false`, since the guard is skipped and `doExecute` proceeds to submit 17+ `RecoverAddrTask` jobs instead of returning `DATA_FALSE`. [1](#0-0) [2](#0-1)
