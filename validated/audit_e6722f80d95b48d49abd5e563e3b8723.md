Gas-abstraction auto-swap trusts a live, unauthenticated AMM quote with only a static 5% slippage bound, letting an attacker sandwich the module's mandatory swap - (File: `x/uexecutor/keeper/execute_inbound_gas.go`)

### Summary
The Algebra report's root cause is that a pool's price can be set/moved by an unprivileged actor immediately before a protocol operation consumes that price, with no adequate slippage protection, letting the attacker capture value from the victim's forced transaction. Push Chain's `x/uexecutor` module has an analogous pattern in its gas-abstraction inbound flow (`ExecuteInboundGas`) and the payload+gas flow (`ExecuteInboundGasAndPayload`): the module fetches a *live* AMM quote from the Universal Core quoter immediately before performing a mandatory PRC20→PC auto-swap, and only enforces a fixed 5% slippage tolerance computed from that just-fetched quote.

### Finding Description
In `ExecuteInboundGas`, once quorum is reached on a `MsgVoteInbound`, the keeper:
1. Calls `GetSwapQuote` against the Universal Core quoter/pool to get the current expected PC output for the bridged token amount [1](#0-0) .
2. Computes `minPCOut = quote * 95 / 100` — a static 5% slippage buffer derived from that same live quote [2](#0-1) .
3. Immediately executes the deposit+swap using that `minPCOut` via `CallPRC20DepositAutoSwap` [3](#0-2) .

The identical quote→5%-buffer→swap pattern is repeated in `ExecuteInboundGasAndPayload` for the funds-and-payload gas-abstraction path [4](#0-3) .

Because the AMM pool the quoter reads from is a normal on-chain pool on Push Chain's own EVM (the "Universal Core" WPC/PRC20 pool), any unprivileged user can move its price with an ordinary swap transaction in the same block, in the same way the Algebra report's attacker moves a pool's price with a token-free or cheap swap before the victim's `mint`. Because module execution here is triggered synchronously by a normal `MsgVoteInbound` transaction (the last vote to reach quorum) processed within an ordinary block, an attacker who can see/predict that transaction (mempool observation, or simply submitting swaps before/after it in the same block by paying for transaction ordering) can:
1. Front-run: swap into the pool to push the PC price down right before the quorum-triggering vote lands.
2. Let the module's `GetSwapQuote` + `CallPRC20DepositAutoSwap` execute at the manipulated price — the 5% band is computed from the manipulated quote itself, so it does not protect against price movement that already happened before the quote was even read.
3. Back-run: reverse the initial swap, extracting the difference between the fair price and the manipulated price, at the expense of the value the bridging user should have received in PC.

This mirrors the report's core defect exactly: relying on a spot/live price read with no external reference (TWAP, external oracle bound, or price staleness check) and a slippage tolerance computed from that same manipulated read, rather than from the value the user actually deposited or a pre-committed price.

### Impact Explanation
The gas-abstraction auto-swap converts a portion of the user's bridged asset into `upc` to fund their new UEA's gas. If the pool price is manipulated downward before the module's swap and restored afterward, the user's UEA receives less PC than it should for their bridged funds, and the attacker captures the difference — a direct, repeatable value-extraction/MEV attack against ordinary bridging users, reachable by any party with no privileged role. This falls within the allowed impact ("corruption of ... gas fee accounting ... revert destination ... canonical UniversalTx state" and "unauthorized module-originated EVM execution" producing a wrong economic outcome) since the module executes a `DerivedEVMCall`-based swap using attacker-influenced pricing without protecting the user.

### Likelihood Explanation
Likelihood is bounded by two factors I could not fully verify from the available code: (1) how deep/liquid the Universal Core AMM pool is in practice (thin liquidity increases attacker profitability and the feasibility of a 5%+ price swing), and (2) whether block proposers/relayers give an attacker reliable enough transaction ordering control to guarantee the sandwich within the same block as the quorum-finalizing vote. Because `MsgVoteInbound` triggers are gasless and predictable (validators vote in a known pattern), and swap/quote calls are plain public EVM calls, the preconditions for a sandwich are present, but I was unable to inspect the actual `GetSwapQuote`/`CallPRC20DepositAutoSwap`/quoter contract implementations (only call sites in `evm.go` matched grep for other helpers, but the quoter/pool source itself was not indexed) to confirm the presence or absence of a TWAP or other price-staleness protection at the contract level, which would materially change likelihood.

### Recommendation
- Do not compute the slippage bound purely from a quote taken immediately before the swap in the same execution; instead derive `minPCOut` from a manipulation-resistant reference (e.g., a time-weighted average price, or an oracle-bound sanity check) and/or record the expected minimum output as part of the inbound observation that Universal Validators vote on, so it is agreed by quorum rather than computed unilaterally at execution time from a possibly-manipulated spot price.
- Consider tightening or making configurable the 5% slippage constant, and add a check that the realized swap output cannot deviate more than a bounded percentage from a recent moving-average price, not just from the just-fetched spot quote.
- Add per-block or per-pool volume/price-impact guards on the Universal Core pool(s) used for gas abstraction to blunt one-block sandwich attacks, analogous to the Algebra report's recommendation to constrain swaps that would move price cheaply within zero/low-liquidity ranges.

### Proof of Concept
Conceptual (I could not execute this against the live AMM/quoter contracts since their bytecode/source was not available in the indexed context):
1. Attacker observes a pending `MsgVoteInbound` transaction (the vote that will bring an inbound to quorum and trigger `ExecuteInboundGas`).
2. Attacker submits a swap on the Universal Core PRC20/WPC pool used by `GetSwapQuote`/`CallPRC20DepositAutoSwap`, in the same block, ordered before the quorum vote, pushing the pool price so that PC is undervalued relative to the bridged token.
3. The quorum vote lands; `ExecuteInboundGas` calls `GetSwapQuote` (reads the now-manipulated price), computes `minPCOut = quote*95/100` from that manipulated quote [5](#0-4) , and executes `CallPRC20DepositAutoSwap`, minting less PC into the user's UEA than fair value.
4. Attacker submits a reverse swap after, restoring the price and pocketing the extracted PC, which came at the expense of the bridging user's gas-abstraction proceeds.
