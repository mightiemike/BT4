## Title
Unchecked object size in mmap-backed storage writer can exceed allocated file capacity, causing an out-of-bounds write / SIGBUS crash - (File: `crates/apollo_storage/src/mmap_file/mod.rs`)

## Summary
The ImageMagick CVE stems from writing an oversized, attacker-controlled data chunk (an "extremely large image profile") into an encoder buffer without verifying it fits the buffer that was actually allocated. The sequencer's mmap-backed storage layer has the same structural defect: `FileHandler<V, RW>::append` copies a serialized value into the memory-mapped file based on the value's *actual* serialized length, while the code that decides whether the file needs to grow only guarantees that `max_object_size` bytes of headroom exist — not that the specific object about to be written fits.

## Finding Description
`MMapFile`/`FileHandler` is documented as relying on caller discipline rather than enforcing the invariant in code: [1](#0-0) 

The actual write path never checks the serialized length against any bound before copying it into the mapped region: [2](#0-1) 

Capacity is only pre-grown using the fixed constant `max_object_size`, evaluated **after** the previous write completed, for the *next* write — not validated against the length of the object currently being written: [3](#0-2) 

The mmap itself is created for the full `max_size` (1 TB by default) as a virtual mapping, while the backing file is only physically extended (`set_len`) in `grow()` up to `size`: [4](#0-3) 

If any serialized value (`V::serialize(val)`) exceeds `config.max_object_size` (default 256 MB, per `MmapFileConfig::default`), the `copy_from_slice` write will write past the region that `grow_file_if_needed` guaranteed was backed by the file, landing in virtually-mapped-but-not-yet-file-backed pages. Touching such pages triggers `SIGBUS` on POSIX systems, crashing the process — the direct Rust-safe analog of a native heap/buffer overflow, since the bug class is identical (writing size-unchecked data past the buffer that was actually provisioned for it).

## Impact Explanation
`apollo_storage` persists blocks, state diffs, and contract classes (`SierraContractClass`, `CasmContractClass`, `DeprecatedContractClass`, `ThinStateDiff`, transaction bodies) via this exact `Writer`/`append` mechanism, as seen in the compressed `StorageSerde` implementations for these types: [5](#0-4) [6](#0-5) 

A crash of the storage writer during block commit on every node that persists the offending block (proposer and all honest full nodes/sequencers re-executing or syncing it) is a node-availability failure that can halt block production/finalization — matching the "network unable to confirm new transactions" impact bar.

## Likelihood Explanation
Gateway-side stateless validation does cap a *single* declared contract class's serialized size well below `max_object_size` (`max_contract_class_object_size` defaults to ~4 MB, `max_contract_bytecode_size` to 81920 felts): [7](#0-6) [8](#0-7) 

However, this size limit is enforced only at the gateway for a single declare transaction's contract class; it is not re-validated inside `mmap_file::append` itself, and the value actually stored via this path is often an aggregate (e.g., a full block's `ThinStateDiff`, which sums the diffs of *every* transaction in a block) rather than a single transaction's payload. There is no visible check tying block-level aggregate resource/bouncer limits directly to `MmapFileConfig::max_object_size`, so the safety of this invariant currently depends entirely on limits enforced far away from the storage layer (gateway, bouncer) rather than being defended in the storage code itself — exactly the pattern that caused the ImageMagick issue (relying on an external assumption instead of validating at the point of the write). I was not able to fully trace every producer of values written through `Writer::append` (e.g., state-sync ingestion from peers, or CLI import tools) within the scope of this analysis to confirm whether all such paths are bounded below `max_object_size` in every deployment configuration.

## Recommendation
In `FileHandler<V, RW>::append` (`crates/apollo_storage/src/mmap_file/mod.rs`), assert/validate that `serialized.len() <= self.config.max_object_size` (returning an error instead of panicking/crashing) before performing `copy_from_slice`, and make `grow_file_if_needed` grow based on the actual `len` of the object about to be written rather than the fixed `max_object_size` constant, so the invariant is enforced defensively in code rather than only documented as a caller responsibility.

## Proof of Concept
1. Construct (or obtain, e.g., via block sync) a value `V::Value` whose `StorageSerde::serialize_into` output, after compression, exceeds `MmapFileConfig::max_object_size` (256 MB default) — e.g., a `ThinStateDiff` aggregating an unusually large number of storage diffs/declared classes within a single block, or a compiled `CasmContractClass` whose bytecode is close to the gateway's separately-configured (and potentially larger) `max_compiled_contract_class_object_size` limit.
2. Persist this value through `FileHandler::append` during normal block-commit storage writes.
3. Because `grow_file_if_needed` only guarantees `max_object_size` bytes of slack based on the previous call, and the write itself performs no length check, `mmap_slice[..len].copy_from_slice(&serialized)` writes into file-backed-but-unallocated (or not-yet-extended) mmap pages, resulting in `SIGBUS`/undefined I/O behavior and crashing the storing node.

Note: I could not fully verify within the available exploration whether every real caller of `apollo_storage`'s `Writer` trait is bounded below `max_object_size` by upstream configuration in all deployments (e.g., relative sizing of `max_compiled_contract_class_object_size` vs. `MmapFileConfig::max_object_size`, and aggregate per-block state-diff sizes vs. bouncer limits). Confirming this end-to-end would benefit from a full Devin session with build/test access to trace all `Writer::append` call sites and their upstream size guarantees.

impl<V: ValueSerde> MMapFile<V> {
    /// Grows the file by the growth step.
    fn grow(&mut self) {
        self.flush();
        let new_size = self.size + self.config.growth_step;
        let new_size_u64 = u64::try_from(new_size).expect("usize should fit in u64");
        debug!("Growing file to size: {}", new_size);
        self.file.set_len(new_size_u64).expect("Failed to set the file size");
        self.size = new_size;
    }

    /// Flushes the mmap to the file.
    fn flush(&mut self) {
        trace!("Flushing mmap to file");
        self.mmap.flush().expect("Failed to flush the mmap");
        self.should_flush = false;
    }
}

/// Open a memory mapped file, create it if it doesn't exist.
#[instrument(level = "debug", err)]
pub(crate) fn open_file<V: ValueSerde>(
    config: MmapFileConfig,
    path: PathBuf,
    offset: usize,
) -> MmapFileResult<(FileHandler<V, RW>, FileHandler<V, RO>)> {
    let file = OpenOptions::new().read(true).write(true).create(true).truncate(false).open(path)?;
    let size = file.metadata()?.len();
    let mmap = unsafe { MmapOptions::new().len(config.max_size).map_mut(&file)? };
    let mmap_ptr = mmap.as_ptr();
    let mmap_file = MMapFile {
        config,
        file,
        mmap,
        size: size.try_into().expect("size should fit in usize"),
        offset,
        should_flush: false,
        _value_type: PhantomData {},
    };
    let shared_mmap_file = Arc::new(Mutex::new(mmap_file));

    let mut write_file_handler: FileHandler<V, RW> = FileHandler {
        memory_ptr: mmap_ptr,
        mmap_file: shared_mmap_file.clone(),
        _mode: PhantomData,
    };
    write_file_handler.grow_file_if_needed(0);

    let read_file_handler: FileHandler<V, RO> =
        FileHandler { memory_ptr: mmap_ptr, mmap_file: shared_mmap_file, _mode: PhantomData };

    Ok((write_file_handler, read_file_handler))
}

impl<V: ValueSerde + Debug> Writer<V> for FileHandler<V, RW> {
    fn append(&mut self, val: &V::Value) -> LocationInFile {
        trace!("Inserting object: {:?}", val);
        let serialized = V::serialize(val).expect("Should be able to serialize");
        let len = serialized.len();
        let offset;
        {
            let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
            offset = mmap_file.offset;
            trace!("Inserting object at offset: {}", offset);
            let mmap_slice = &mut mmap_file.mmap[offset..];
            mmap_slice[..len].copy_from_slice(&serialized);
            mmap_file
                .mmap
                .flush_async_range(offset, len)
                .expect("Failed to asynchronously flush the mmap after inserting");
            mmap_file.offset += len;
            mmap_file.should_flush = true;
        }
        let location = LocationInFile { offset, len };
        self.grow_file_if_needed(location.next_offset());
        location
    }

    fn serialize_into(&self, res: &mut impl std::io::Write) -> Result<(), StorageSerdeError> {
        let mut to_compress: Vec<u8> = Vec::new();
        self.prime.serialize_into(&mut to_compress)?;
        self.compiler_version.serialize_into(&mut to_compress)?;
        self.bytecode.serialize_into(&mut to_compress)?;
        self.bytecode_segment_lengths.serialize_into(&mut to_compress)?;
        self.hints.serialize_into(&mut to_compress)?;
        self.pythonic_hints.serialize_into(&mut to_compress)?;
        self.entry_points_by_type.serialize_into(&mut to_compress)?;
        if to_compress.len() > crate::compression_utils::MAX_DECOMPRESSED_SIZE {
            warn!(
                "CasmContractClass serialization size is too large and will lead to \
                 deserialization error: {}",
                to_compress.len()
            );
        }
        let compressed = compress(to_compress.as_slice())?;
        compressed.serialize_into(res)?;

        Ok(())
    }

    fn deserialize_from(bytes: &mut impl std::io::Read) -> Option<Self> {
        let compressed_data = Vec::<u8>::deserialize_from(bytes)?;
        let data = decompress(compressed_data.as_slice())
            .expect("destination buffer should be large enough");
        let data = &mut data.as_slice();
        Some(Self {
            prime: BigUint::deserialize_from(data)?,
            compiler_version: String::deserialize_from(data)?,
            bytecode: Vec::<BigUintAsHex>::deserialize_from(data)?,

            entry_points_by_type: CasmContractEntryPoints::deserialize_from(data)?,
        })
    }
