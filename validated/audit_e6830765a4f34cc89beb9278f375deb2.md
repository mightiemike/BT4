### Title
Unmetered `TriggerConstantContract`/`estimateEnergy` RPC and HTTP endpoints allow anonymous callers to flood full nodes with fee-free TVM execution, enabling node-level DoS - (File: framework/src/main/java/org/tron/core/services/RpcApiService.java, actuator/src/main/java/org/tron/core/actuator/VMActuator.java)

### Summary
The SEDA report's root cause is that specific message types (`CommitDataResult`/`RevealDataResult`) are executed with gas price forced to `0` in the `AnteHandler`, so an attacker can flood validators with unlimited, effectively free executions and delay/halt the chain. java-tron has a structurally analogous unmetered-execution surface: the `TriggerConstantContract` and `EstimateEnergy` gRPC/HTTP/JSON-RPC endpoints execute arbitrary TVM bytecode via `VMActuator` with `isConstantCall = true`, but the call is never broadcast as an on-chain transaction, is not charged any energy/bandwidth fee against any real account, and is reachable by any anonymous caller of the node's public API.

### Finding Description
`RpcApiService.callContract()` routes both `TriggerContract` and `TriggerConstantContract` requests to `Wallet.triggerConstantContract()` → `callConstantContract()`, which builds a `TransactionContext` and runs it through `VMActuator` with `isConstantCall = true`: [1](#0-0) 

Inside `VMActuator`, when `isConstantCall` is true the executor type is forced to `ET_PRE_TYPE` (a "pre-execution"/local-only mode) and the energy limit is capped by a node-configured `maxEnergyLimitForConstant` rather than by the caller's actual frozen/delegated energy or account balance: [2](#0-1) [3](#0-2) 

In the `call()` path, when `isConstantCall` is true, `energyLimit` is simply set to `maxEnergyLimit` (the constant-call cap) instead of being derived from the caller's real energy/balance via `getTotalEnergyLimit()`, and the CPU-time budget is computed from `CommonParameter.getInstance().getConstantCallTimeoutMs()` rather than tied to any resource deduction: [4](#0-3) 

Because this call path never produces a broadcast transaction (it is explicitly a local/"constant" execution, mirrored in `Wallet.triggerContract()` which only executes the constant branch and otherwise returns the unexecuted capsule), it bypasses the entire `BandwidthProcessor`/`EnergyProcessor` accounting pipeline that normally enforces `useAccountNet`/`useFreeNet`/energy-fee deduction for on-chain transactions: [5](#0-4) 

This is functionally the same bug class as the SEDA issue: a class of "message" (here, a constant/`eth_call`-style contract invocation) that the protocol intentionally treats as fee-free is exposed on a public interface with no duplicate/volume check and no economic cost, so any anonymous caller can submit unlimited such calls, each of which still consumes real CPU/memory on the node to execute TVM bytecode (up to `maxEnergyLimitForConstant`/`getMaxCpuTimeOfOneTx()` worth of work per call), unlike the SEDA case there is also no per-caller identity or duplicate-suppression check at all — every call is accepted as long as the RPC/HTTP/gRPC service thread pool has capacity.

### Impact Explanation
Because `TriggerConstantContract`/`EstimateEnergy` (and the JSON-RPC `eth_call`/`eth_estimateGas` equivalents, per `TronJsonRpcImpl.estimateGas()`) are reachable by anonymous RPC/HTTP clients and are not gated by TRX balance, frozen energy, or bandwidth, an attacker can submit a very high volume of such requests, each triggering expensive TVM execution (loops, storage reads, precompile calls) up to the per-call CPU/energy cap. Because these calls consume real node CPU/memory/thread-pool capacity without any balance or resource deduction, a sustained flood can starve the gRPC/HTTP worker pool and degrade or halt normal block production/validation/API service on the targeted full node(s) — a node-level DoS in the same spirit as the SEDA "flood validators with free messages to delay blocks/DoS the node" bug, though scoped to constant-call execution nodes rather than causing consensus-wide block delay.

### Likelihood Explanation
Likelihood is high for causing local node degradation: the endpoints are unauthenticated by design (public read/query API), require no TRX or energy balance, and are only bounded by node-level configuration (`maxEnergyLimitForConstant`, `getMaxCpuTimeOfOneTx()`, service thread-pool size) rather than any per-caller cost or rate limit intrinsic to the protocol logic itself. This is lower severity than the SEDA case because it does not directly corrupt consensus state or force gas price to zero for on-chain transactions — it targets node availability rather than chain-wide block production, and most operators front these endpoints with a reverse proxy/rate limiter, which is outside the scope of this code.

### Recommendation
- Enforce a strict per-IP/per-connection rate limit and a hard concurrency cap specifically for `TriggerConstantContract`/`EstimateEnergy` (gRPC, HTTP `wallet/triggerconstantcontract`, and JSON-RPC `eth_call`/`eth_estimateGas`) independent of the general RPC connection pool.
- Consider requiring a nominal `feeLimit`-derived energy budget check (already partially present via `getMaxFeeLimit()`) to be enforced consistently across all constant-call entry points, and lower `maxEnergyLimitForConstant`/CPU timeout defaults for public-facing nodes.
- Ensure `estimateEnergy`'s binary-search loop (`estimateEnergy()` in `Wallet.java`), which can trigger many repeated constant executions per single client request, is itself bounded and rate-limited, since it multiplies the CPU cost of a single flood request.

### Proof of Concept
No PoC was executed (index/read-only access only). Conceptually: an anonymous client repeatedly calls the gRPC `TriggerConstantContract` (or HTTP `wallet/triggerconstantcontract`, or JSON-RPC `eth_call`) endpoint against a heavy/looping smart contract method, using `maxEnergyLimitForConstant` worth of computation per call and no account/balance requirement, at a request rate exceeding the node's spare CPU/thread capacity, to degrade or DoS the node's RPC/API service and, if resources are shared with block processing, to negatively impact block production performance.
