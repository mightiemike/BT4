## Analog Found: Duplicate vote-address entries not deduplicated when building the account/votes list — VoteWitnessActuator vs. VoteWitnessProcessor

### Title
Duplicate witness addresses in `VoteWitnessContract.votes` are not merged/deduplicated before being inserted into the account's votes list - ([File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java])

### Summary
The reported bug class is: a function that builds a list from a caller-supplied array of addresses without checking for duplicates, leaving the list (and dependent state) inconsistent, later fixed by merging/deduplicating entries before insertion. Java-tron has this exact pattern in its legacy `VoteWitnessActuator`, and — notably — the newer TVM-native equivalent (`VoteWitnessProcessor`) already contains the fix (an explicit merge step), demonstrating the two code paths are inconsistent with each other.

### Finding Description
`VoteWitnessActuator.validate()` iterates the `votes` list from an unprivileged, user-submitted `VoteWitnessContract` and only checks that each `vote_address` is well-formed, corresponds to an existing account/witness, and that the total summed vote count doesn't exceed the account's `tronPower`: [1](#0-0) 

It never checks whether the same `vote_address` appears more than once in the list. Then, in `countVoteAccount()` (called from `execute()`), each `Vote` entry is applied directly, one at a time, to both the `VotesCapsule` and the `AccountCapsule`, with no deduplication/merging by address: [2](#0-1) 

`VotesCapsule.addNewVotes()` simply appends a new `Vote` entry to the underlying protobuf list on every call — it performs no lookup/merge for an already-present address: [3](#0-2) 

If a caller submits the same `vote_address` twice (e.g., `[ (W, 5), (W, 5) ]`), the resulting `AccountCapsule`/`VotesCapsule` state ends up with two separate `Vote` entries for witness `W` in the same list, rather than one merged entry of `10`. This is precisely the class of bug from the report: `initialize`-style bulk insertion into a list, without validating for duplicate keys, producing an inconsistent internal state.

By contrast, the newer TVM-native equivalent, `VoteWitnessProcessor.execute()`, explicitly recognizes and fixes this exact problem — it accumulates votes into a `Map<ByteString, Long>` keyed by address ("merge vote for same witness") before writing them to state: [4](#0-3) 

This side-by-side comparison is strong evidence the vulnerability class is real and was already fixed once in this codebase — but only in one of the two implementations of "vote for witnesses" logic.

### Impact Explanation
An unprivileged user (any account owner) can submit a `VoteWitnessContract` with duplicate `vote_address` entries through the legacy (non-TVM) `VoteWitnessActuator` path. This creates duplicate `Vote` entries for the same witness inside `AccountCapsule.votes` and `VotesCapsule.newVotes`. This is a state/accounting divergence: the account's persisted vote-list representation no longer matches the invariant (at most one entry per witness) that other logic — such as `MortgageService`'s old-vote/new-vote diffing used for reward distribution during maintenance — is implicitly built around. Depending on how that diff logic keys/aggregates by address, duplicate entries can cause reward or vote-count accounting to diverge from the amount actually authorized/checked against `tronPower`, i.e., an invalid-state/accounting-divergence condition rather than a direct fund-theft primitive.

### Likelihood Explanation
High: any account holder can trigger this by simply repeating the same `vote_address` in the `votes` list of a standard `VoteWitnessContract`. No special privilege or precondition beyond having some `tronPower` is required, and the total-vote-count cap does not check per-address duplication, only the aggregate sum.

### Recommendation
In `VoteWitnessActuator.countVoteAccount()` (and its `validate()`), deduplicate/merge `Vote` entries by `vote_address` before calling `votesCapsule.addNewVotes()` / `accountCapsule.addVotes()`, mirroring the `voteMap` merging already implemented in `VoteWitnessProcessor.execute()`. Alternatively, reject transactions whose `votes` list contains a duplicate `vote_address`, consistent with how `AccountPermissionUpdateActuator.checkPermission()` already rejects non-distinct addresses in a permission's key list: [5](#0-4) 

### Proof of Concept
1. Fund an account and freeze balance to obtain `tronPower`.
2. Submit a `VoteWitnessContract` via the legacy gRPC/API path that routes to `VoteWitnessActuator` (not the TVM native `vote` precompile), with `votes = [ {vote_address: W, vote_count: N}, {vote_address: W, vote_count: N} ]`, where `2*N*TRX_PRECISION <= tronPower`.
3. `validate()` passes, since it only checks the aggregate sum against `tronPower` and per-entry validity — it never checks address uniqueness: [1](#0-0) 
4. `execute()` → `countVoteAccount()` applies both entries independently via `forEach`, producing two `Vote` entries for `W` in `AccountCapsule.votes` and `VotesCapsule.newVotes` instead of one merged entry: [6](#0-5) 
5. Inspect the account's `votes` list (e.g., via `getaccount` API) to confirm duplicate `Vote` entries for the same witness address persist in state, contrasting with the merged single-entry behavior produced by `VoteWitnessProcessor` for the equivalent TVM-native `vote` operation.

**Uncertainty**: I was not able to fully trace the exact downstream consumer(s) of `AccountCapsule.votes`/`VotesCapsule.newVotes` in `MortgageService` (reward distribution) within the available index to conclusively prove a quantifiable fund/reward miscalculation results from the duplicate entries; the index does not appear to include the full body of that reward-diffing logic. A Devin session with full repository access would be needed to trace `MortgageService`'s vote-diff/reward computation to confirm whether duplicate `Vote` entries cause a concrete reward-accounting error versus being purely a benign representational redundancy.

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
