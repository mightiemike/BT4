### Title
Public gateway HTTP server has no connection/request timeout or connection-count limit, allowing unauthenticated slow-loris connection-slot exhaustion - (File: crates/apollo_http_server/src/http_server.rs)

### Summary
`HttpServer::run` in `apollo_http_server` binds the externally-facing transaction-submission endpoint and serves it with bare `axum::serve(listener, app)` over an unmodified Tokio `TcpListener`, with no per-connection timeout, no header/body read-timeout, and no cap on the number of concurrent TCP connections/streams. [1](#0-0) 

### Finding Description
`HttpServerConfig` only exposes `max_request_body_size` and `dynamic_config_poll_interval`; there is no timeout or connection-limit field at all. [2](#0-1) 

Compare this to the sequencer's own internal `RemoteComponentServer` (used for component-to-component RPC, e.g. gateway↔mempool), which explicitly guards against exactly this bug class: it bounds concurrent connections with a `Semaphore` sized by `max_concurrency`, immediately returns 503 and drops the connection when the semaphore is exhausted, and additionally sets a TCP-level keepalive/probe timeout (`with_time`, `with_interval`, `with_retries`) plus an HTTP/2 `keep_alive_interval`/`keep_alive_timeout` to reclaim idle/stalled connections. [3](#0-2) [4](#0-3) [5](#0-4) 

None of those protections exist on the externally-reachable `apollo_http_server`, which is precisely the endpoint any unprivileged remote client uses to submit transactions (`/gateway/add_rpc_transaction`, `/gateway/add_transaction`). [6](#0-5) 

This mirrors the ALPINE-CVE-2026-70464 bug class in `rsync`: an attacker opens many TCP connections to the daemon/service and either sends no data at all, or trickles data extremely slowly, never completing the request (analogous to "stalling before/after module selection"). Because there is no forward-progress timeout and no bound on the number of simultaneously accepted connections, each stalled connection consumes a Tokio task and an OS socket/file descriptor indefinitely, exhausting available connection slots for legitimate transaction submitters. `RequestBodyLimitLayer`/`DefaultBodyLimit` bound total bytes accepted per completed request, but they do nothing for a connection that never sends a complete request (or any bytes) in the first place — those layers only trigger once bytes are being read into the body decoder. [7](#0-6) 

### Impact Explanation
This is a network-availability DoS against the sequencer's transaction-ingestion HTTP endpoint reachable by any unauthenticated remote sender (no signature, no fee payment, no valid transaction required — the connection need never even complete a valid HTTP request). Sustained exploitation prevents new legitimate transactions from being submitted through this HTTP entry point, which can amount to "a network unable to confirm new transactions" via this ingress path, consistent with the accepted-impact class in the validation criteria.

### Likelihood Explanation
Low cost, no privileges, no valid transaction/signature needed, and no special knowledge of the protocol is required — any TCP client can open a socket to the gateway's HTTP port and simply not send data (or trickle bytes below any implicit OS-level read granularity). Because axum's default `serve()` in this codebase applies no idle/request timeout and no explicit connection cap distinct from OS/file-descriptor limits, exploitation is straightforward and repeatable, and the sequencer's own `apollo_infra` component already demonstrates awareness of, and mitigation for, this exact bug class elsewhere in the codebase — but that mitigation was not applied to the public-facing `apollo_http_server`.

### Recommendation
Apply the same defense-in-depth pattern already implemented in `RemoteComponentServer` to `apollo_http_server`:
- Add a bounded `Semaphore`/connection-count limit around the `TcpListener::accept()` loop (or a `tower::limit::ConcurrencyLimitLayer` equivalent), rejecting/closing excess connections immediately.
- Add explicit read/header timeouts (e.g., a `TimeoutLayer` on the request future and/or a low-level `http1_header_read_timeout` / equivalent hyper builder setting instead of bare `axum::serve`) so that connections which do not make forward progress within a bounded window are closed.
- Add TCP keepalive with a bounded probe/time window on accepted sockets, mirroring `remote_component_server.rs`'s `TcpKeepalive` configuration.
- Expose these as configurable fields on `HttpServerStaticConfig`, analogous to `RemoteServerConfig`'s `keepalive_interval_ms`/`keepalive_timeout_ms`/`max_concurrency`.

### Proof of Concept
1. Start the sequencer node with `apollo_http_server` bound to its default port.
2. From an attacker machine (no account, no funds, no valid Starknet transaction needed), open N TCP connections to the HTTP server's port (`connect()` only, or send a partial HTTP request line and then stop sending bytes / send bytes at a rate below any timeout threshold) — since `axum::serve(listener, app)` is invoked with no additional timeout/connection-limit layer, each such connection is accepted and its handling task kept alive indefinitely. [1](#0-0) 
3. Repeat until the process's file-descriptor/socket limit or the runtime's task-handling capacity is exhausted.
4. Observe that legitimate clients issuing POST requests to `/gateway/add_rpc_transaction` or `/gateway/add_transaction` can no longer establish new connections or receive timely responses, confirming the connection-slot exhaustion. [8](#0-7)
