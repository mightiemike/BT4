### Title
Missing calling-contract binding in `ValidateMultiSign` precompile signing hash enables cross-contract signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract computes the message hash that off-chain signers must sign as `sha256(account_address || permissionId || data)`, where `data` is fully attacker-controlled, arbitrary calldata provided by whatever TVM contract invokes the precompile. Unlike the calling/target contract's address, this identifier is never mixed into the hash. This is the same root cause pattern as the reported `_createLeaf()` bug in `SuperVaultAggregator.sol`: an authorization primitive hashes only the "arguments" and omits the identity of the consumer (hook address / calling contract) that is supposed to scope the authorization, so any two unrelated contexts that happen to encode identical `data` bytes end up requiring/accepting the exact same signature.

### Finding Description
`ValidateMultiSign.execute()` builds the signed message as: [1](#0-0) 

`address` is the TRON account whose permission is being checked, `permissionId` selects which of that account's `Permission` entries to use, and `data` is an arbitrary byte string supplied by the calling smart contract (not the account owner). The resulting `hash` is what off-chain key holders sign, and `recoverAddrBySign` / `TransactionCapsule.getWeight` are used purely against this `hash`.

Nothing in this computation binds the hash to the identity of the invoking contract, to a purpose/action tag, or to any other context describing what the signature is meant to authorize. Any TVM contract can call this precompile with any `data` it likes; the precompile has no way to know, and does not attempt to record, which contract or which logical action requested the check. This mirrors the SuperVaultAggregator flaw precisely: `_createLeaf()` double-hashed only the ABI-encoded arguments and dropped the hook address, so two hooks (`RequestDeposit7540VaultHook` and `RequestRedeem7540VaultHook`) that happen to encode `(yieldSource, amount)` identically ended up sharing one authorization leaf. Here, two unrelated TVM contracts (or two unrelated code paths within the same contract) that build `data` using the same encoding convention (e.g. `abi.encode(counterpartyAddress, amount)`) will produce the exact same `hash` for the same account/permissionId, so a signature a user produced to authorize action A in contract X is equally valid to authorize action B in contract Y (or a completely different, attacker-deployed contract) as long as the attacker can reproduce/observe the same `data` bytes and reuse a captured signature.

This differs from ordinary TRON transaction signing (`TransactionCapsule.checkWeight`/`WalletUtil.checkPermissionOperations`), where the signed hash is over the full `raw_data`, which itself embeds the specific `ContractType` and full protobuf-encoded contract fields — i.e. domain separation by contract/action type is present there. `ValidateMultiSign` is the one authorization primitive in the codebase that intentionally hands full control of the "leaf payload" to an arbitrary, unprivileged TVM contract, exactly like `_createLeaf(hookArgs)` handed control of the encoded arguments to arbitrary hook contracts, without adding an equivalent of `hookAddress`.

### Impact Explanation
Any account holder who signs a `ValidateMultiSign`-style authorization for one dApp/contract can have that same signature accepted by a second, different dApp/contract as authorization for a different action, provided the second contract's `data` encoding collides with the first's. Because `data` is unbounded, attacker-authored bytes chosen by whichever contract calls the precompile, an attacker can deliberately design a malicious contract whose `data` layout matches a popular legitimate contract's layout (a "signature phishing" contract), then capture/observe a user's genuine signature (e.g., leaked via a public transaction, mempool, or a dApp UI) and replay it through the malicious contract to pass its `ValidateMultiSign` check, unlocking whatever privileged action that check gates (fund transfer, permission-gated call, etc.). This is a concrete authorization/replay impact class (auth bypass via signature reuse), directly analogous to the "loss of funds" impact called out in the original report.

### Likelihood Explanation
`ValidateMultiSign` is a public precompile reachable from any TVM smart contract by any unprivileged caller/deployer — no special role is required to build a colliding contract or to observe/replay a target signature. The likelihood of exploitation depends on the existence (or attacker-crafted creation) of contracts that reuse the same `data` layout for different purposes, which is exactly the kind of "same encoding, different intent" scenario the original report demonstrates is realistic for hook-style modular systems, and is equally plausible for TVM dApps that adopt a common ABI-encoding convention for multisig-gated actions.

### Recommendation
Bind the signed hash to the identity/context of the requesting contract and its intended purpose, not just to the raw argument bytes:
- Include the calling contract's address (the TVM `CONTRACT` / `msg.sender` equivalent visible to the precompile) and/or an explicit action-type discriminator in the `combine` buffer before hashing, e.g. `combine = merge(callingContractAddress, actionTag, address, permissionId, data)`.
- Document that `data` alone must never be assumed to be self-describing across different consuming contracts, and require dApps to embed a domain-separation tag (contract address + purpose) inside `data` if the precompile itself is not changed, though the safer fix is enforcing it at the precompile level so it cannot be omitted by careless integrators.

### Proof of Concept
1. Deploy legitimate contract `A` that calls `ValidateMultiSign(address, permissionId, data)` where `data = abi.encode(counterparty, amount)` to authorize, say, a withdrawal of `amount` to `counterparty`.
2. A user with `permissionId` signs off-chain over `sha256(address || permissionId || data)` believing they are authorizing contract `A`'s withdrawal for a specific `counterparty`/`amount` pair.
3. Attacker deploys contract `B`, which independently also calls `ValidateMultiSign` and happens to (or is deliberately crafted to) build the identical `data = abi.encode(counterparty, amount)` for an entirely different action (e.g., transferring a different asset, or granting a permission change) gated by the same account/permissionId.
4. Attacker submits the user's previously-observed signature to contract `B`. Because `hash` in `PrecompiledContracts.java:1062-1064` depends only on `address`, `permissionId`, and `data` — never on which contract (`A` or `B`) is calling — the signature validates successfully in `B`, and `B`'s unrelated privileged action executes without the user ever having intended to authorize it.
