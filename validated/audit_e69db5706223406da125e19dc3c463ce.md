### Title
Stale `tracked_shards` in `ShardedRpcPool` Remote Nodes Causes Permanent `UnavailableShard` Errors After Dynamic Resharding - (`File: chain/jsonrpc/src/sharded_rpc.rs`)

---

### Summary

`ShardedRpcNode.tracked_shards` is a `Vec<ShardId>` populated once at pool initialization from static config and never refreshed. When dynamic resharding splits a parent shard into child shards with new `ShardId` values, the remote nodes' `tracked_shards` lists still contain the old parent IDs. The routing functions `nodes_for_account_in_epochs` and `nodes_for_shard_in_epochs` check `node.tracked_shards.contains(&child_shard_id)`, which always returns `false` for the new child IDs. No remote node is selected, the emergency fallback routes to the local node, and the local node also does not track the child shard — producing a permanent `UnavailableShard` error for every RPC query targeting any account on a split shard.

---

### Finding Description

`ShardedRpcNode` stores the remote node's shard coverage as a plain `Vec<ShardId>`:

```rust
pub struct ShardedRpcNode {
    pub client: Arc<JsonRpcClient>,
    pub tracked_shards: Vec<ShardId>,   // set once at init, never updated
}
``` [1](#0-0) 

These IDs are copied verbatim from the static `ShardedRpcConfig` at startup:

```rust
tracked_shards: node_config.tracked_shards.clone(),
``` [2](#0-1) 

The routing functions then do a plain membership test against the post-resharding child shard IDs. In `nodes_for_account_in_epochs`:

```rust
// Check which remote nodes match.
for node in &self.nodes {
    if epoch_shard_ids
        .iter()
        .any(|(_epoch_id, shard_id)| node.tracked_shards.contains(shard_id))
    {
        result.push(RpcNodeHandle::RemoteNode(node.client.clone()));
    }
}
``` [3](#0-2)

```rust

// not epoch-dependent, so a single membership check is enough.
for node in &self.nodes {
    if node.tracked_shards.contains(&shard_id) {
``` [4](#0-3) 

After dynamic resharding, the epoch manager assigns entirely new `ShardId` values to child shards (e.g., parent shard `3` becomes children `4` and `5`). The remote node's `tracked_shards` still holds `[3]`. The `contains(&4)` and `contains(&5)` checks both return `false`, so no remote node is selected.

The emergency fallback then routes to the local node:

```rust
if nodes.is_empty() {
    return Ok(vec![RpcNodeHandle::LocalNode]);
}
``` [5](#0-4) 

The local node's `ShardTracker` correctly handles descendants via `check_if_descendant_of_tracked_shard`, which traverses the shard layout history: [6](#0-5) 

But if the local node does not track the relevant parent shard (which is the normal case in a sharded RPC pool where each node tracks only a subset of shards), the local node also returns `UnavailableShard`. The result is a permanent routing failure for all accounts on the split shard.

The codebase explicitly acknowledges this in the ignored integration test:

---

### Impact Explanation

After any dynamic resharding event, every JSON-RPC query (`query`, `view_account`, `view_access_key`, `view_code`, `view_state`, `call_function`, etc.) for an account whose shard was split returns `UnavailableShard` from the sharded RPC pool. This is a non-network-level denial of service for the entire RPC surface covering the affected accounts. It cannot self-heal without a node restart or config update, and it affects all users of the pool — not just a single attacker.

The `RpcQueryError::UnavailableShard` propagates through every query type: [8](#0-7) 

---

### Likelihood Explanation

Dynamic resharding is an active protocol feature (`ShardLayoutConfig::Dynamic`) that triggers automatically when trie memory usage crosses `memory_usage_threshold`. Once any shard splits, the stale `tracked_shards` bug activates immediately for the next epoch. The `force_split_shards` config option also allows operators to trigger splits deliberately. The bug is permanent until the pool is reconfigured or the node is restarted with updated `tracked_shards` values. [9](#0-8) 

---

### Recommendation

Replace the static `Vec<ShardId>` membership check for remote nodes with the same descendant-aware logic used for the local node. Specifically, `nodes_for_account_in_epochs` and `nodes_for_shard_in_epochs` should call `ShardLayout::get_children_shards_uids` (or equivalent ancestor lookup) to determine whether a remote node's configured parent shard IDs cover the queried child shard ID in the current epoch. Alternatively, the `ShardedRpcPool` should subscribe to epoch transitions and update each `ShardedRpcNode.tracked_shards` to include child shard IDs whenever a tracked parent is split.

---

### Proof of Concept

The test harness in `test-loop-tests/src/tests/sharded_rpc_resharding.rs` already demonstrates the failure path:

1. Start a 2-shard network with `rpc0` tracking shard `shard_uids[0]` and `rpc1` tracking shard `shard_uids[1]`.
2. Enable `DynamicReshardingConfig` with `force_split_shards: vec![shard_to_split]` to force a split of the shard containing `alice`.
3. Run until the epoch manager reports a new shard layout (2 → 3 shards).
4. Issue a `ViewAccount` query for `alice` from either RPC node.

Expected (correct): the coordinator forwards to the node tracking the child shard and returns `alice`'s balance.

Actual (buggy): `nodes_for_account_in_epochs` computes the new child `shard_id` for `alice`, finds no remote node whose static `tracked_shards` contains it, falls back to `LocalNode`, and the local node returns `UnavailableShard` because it also does not track the child shard.

The test is marked `#[ignore]` precisely because this failure is confirmed and unfixed: [10](#0-9)
