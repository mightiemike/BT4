Based on my investigation, I found a concrete, unverified-write-set gap in the transaction backup restore path.

### Title
Transaction backup restore trusts unverified write sets that are never checked against the authenticated `state_change_hash` - ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
`TransactionRestoreController` loads transaction chunks from backup storage and verifies them using `TransactionListWithProofV2` / `TransactionListWithProof::verify`, which only authenticates the transaction hash, the accumulator/ledger-info proof over `TransactionInfo`, and (optionally) events. It never checks that the separately-loaded `write_set` for each transaction hashes to `TransactionInfo::state_change_hash()`. These unverified write sets are then persisted directly to the ledger DB (and, for KV-only replay, used to compute the restored state) without ever being validated against the proof-bound commitment.

### Finding Description
`LoadedChunk::load` in [1](#0-0)  deserializes `(txn, aux_info, txn_info, events, write_set)` tuples independently from the backup file. It builds a `TransactionListWithProofV2` (not `TransactionOutputListWithProofV2`) from `txns`, `event_vecs`, and `txn_infos`, and calls `.verify(...)`, but `write_sets` is not part of that structure at all: [2](#0-1) .

The verification method `TransactionListWithProof::verify` only checks (1) transaction hash vs. `txn_info.transaction_hash()`, (2) the accumulator proof binding `txn_info` to the ledger info, and (3) event root hash if events are present — it contains no check of `write_set` against `txn_info.state_change_hash()`: [3](#0-2) . Compare this with `TransactionOutputListWithProof::verify`, used elsewhere, which explicitly does `ensure!(txn_info.state_change_hash() == write_set_hash, ...)`: [4](#0-3) , and `TransactionOutput::ensure_match_transaction_info`, which does the same check: [5](#0-4) . Neither of these hash-verifying paths is invoked on the `write_sets` loaded in `LoadedChunk::load`.

After loading, the unpacked `write_sets` are used either to save transactions directly (pre-`replay_from_version` versions) via `restore_handler.save_transactions` [6](#0-5) , or, for KV-only replay, via `save_transactions_and_replay_kv` [7](#0-6) . Both call into `restore_utils::save_transactions_impl`, which writes `write_sets` into `WriteSetDb` and, when `kv_replay` is true, feeds them straight into `state_store.calculate_state_and_put_updates` to compute and persist the resulting ledger state — again with no hash check against `txn_info.state_change_hash()`: [8](#0-7) .

### Impact Explanation
If the backup storage/transport (a component treated as untrusted input by the restore tool, since correctness must come from cryptographic proofs rather than storage trust) supplies a `write_set` that does not match the committed `state_change_hash`, the restore tool will accept it silently: the transaction, its accumulator-proven `TransactionInfo`, and events all check out, but the actual write set placed into the DB (and used to derive the restored state, in the KV-replay path) can diverge arbitrarily from the correct VM/consensus-committed result. This corrupts durable ledger data on the restoring node and produces committed state that differs from the correct result, and downstream proofs/serving from this node (e.g., authenticated state at that version) would be wrong even though the node believes it restored a verified backup.

### Likelihood Explanation
Likelihood depends on control over/corruption of the backup artifact (medium — backup files are typically fetched from cloud storage or a backup service that is not the source of truth for cryptographic guarantees; a compromised or buggy backup provider, or a corrupted/tampered file, is a realistic threat model that these proofs are specifically supposed to defend against). No signature or hash requires collision-finding: the write set is simply unchecked, so any different byte content is accepted outright.

### Recommendation
In `LoadedChunk::load`, after deserializing `write_sets`, verify `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every transaction (mirroring `TransactionOutput::ensure_match_transaction_info` / `TransactionOutputListWithProof::verify`), and fail the chunk load if any mismatch is found, before the write sets are handed to `save_transactions` / `save_transactions_and_replay_kv`.

### Proof of Concept
1. Produce a valid transaction backup manifest/chunk where `txn`, `txn_info`, and `events` are all genuine and pass proof verification.
2. Replace the serialized `write_set` bytes in the chunk file (e.g., with a semantically different but same-length write set) so that `CryptoHash::hash(write_set) != txn_info.state_change_hash()`.
3. Run `TransactionRestoreController::run` (or the KV-only replay path) against this tampered chunk.
4. Observe that `LoadedChunk::load`'s `txn_list_with_proof.verify(...)` succeeds (it never inspects `write_set`), and the tampered write set is persisted via `restore_utils::save_transactions_impl`, corrupting the resulting ledger/state at that version despite a "verified" restore.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
