### Title
Attacker-controlled `pluginConfig.command`/`envVars` in FMS `ProposeJob`/`ApproveSpec` reach `RegisterLOOP` and spawn a subprocess with attacker-chosen environment before/at approval - ([File: core/services/feeds/service.go, core/services/ocr2/validate/validate.go])

### Summary
`ApproveSpec` only validates bridge existence (`AssertBridgesExist`) after `generateJob` parses the proposal's TOML, but `generateJob` itself (also invoked from `validateProposeJobArgs` during `ProposeJob`) calls `ocr2.ValidatedOracleSpecToml` → `validateSpec` → `validateGenericPluginSpec`, which reads attacker-controlled `pluginConfig.Command`/`EnvVars` and calls `rc.RegisterLOOP` to actually spawn (`plugin.Start(ctx)`) an `exec.Command` subprocess with those environment variables. The only gate on `Command` is `exec.LookPath`, meaning any binary that exists on the node's `PATH` (e.g. `bash`, `sh`, `python3`, `node`, `env`) can be selected; `EnvVars` are appended to the child process's environment with no allow-list at all.

### Finding Description
- `core/services/feeds/service.go:1440-1489` `generateJob` parses the FMS-supplied TOML and, for `job.OffchainReporting2`, calls `ocr2.ValidatedOracleSpecToml(ctx, s.ocr2cfg, s.insecureCfg, spec, s.loopRegistrarConfig)` [1](#0-0) .
- `generateJob` is called both from `ProposeJob`'s `validateProposeJobArgs` (i.e., before any node-operator approval) and from `ApproveSpec` [2](#0-1) [3](#0-2) .
- `validateSpec` dispatches `types.GenericPlugin` to `validateGenericPluginSpec(ctx, spec.OCR2OracleSpec, rc)` [4](#0-3) .
- `validateGenericPluginSpec` unmarshals `pluginConfig` JSON into `OCR2GenericPluginConfig{}`, takes `p.Command` (attacker-controlled) if non-empty, checks only `exec.LookPath(command)` (i.e., the binary must exist on `PATH`, but any existing interpreter/utility qualifies), builds `envVars` by appending `p.EnvVars` (fully attacker-controlled key=value pairs) with **no validation or allow-list**, and calls `rc.RegisterLOOP(plugins.CmdConfig{ID: loopID, Cmd: command, Env: envVars})`, then **starts** the plugin process (`plugin.Start(ctx)`) as part of spec validation [5](#0-4) .
- `RegisterLOOP` → `NewCmdFactory` builds `exec.Command(lcfg.Cmd)` and appends `lcfg.Env` to `cmd.Env` verbatim [6](#0-5) .
- `ApproveSpec` (core/services/feeds/service.go:953) only performs `AssertBridgesExist` after `generateJob` — it never inspects/limits `pluginConfig.command`/`envVars` [7](#0-6) .
- At full job start (delegate path), `newServicesGenericPlugin` again reads `pCfg.Command`/`pCfg.EnvVars` from the persisted spec and calls `d.cfg.RegisterLOOP` with the same attacker-controlled values [8](#0-7) .

Root cause: node-operator trust boundary assumption is violated — the plugin command allow-list is effectively "any binary already on the node's PATH," and the plugin environment variables have zero validation. Because many common interpreters/binaries honor environment variables that trigger code execution (e.g. `LD_PRELOAD`, `BASH_ENV`, `PYTHONSTARTUP`, `NODE_OPTIONS=--require`, `PERL5OPT`), an attacker who only controls the `pluginConfig` of a `pluginType = "plugin"` OCR2 job proposal can achieve code execution on the node host by picking a pre-existing interpreter as `Command` and injecting a malicious environment variable via `EnvVars`. Crucially, this occurs even at the `ProposeJob` step (via `validateProposeJobArgs`), i.e., **before any node-operator approval**, because `validateGenericPluginSpec` unconditionally starts the LOOPP subprocess as part of spec validation.

### Impact Explanation
This is a real command-execution / secret-disclosure vector from a low-trust FMS input path: a compromised/spoofed Feeds Manager can cause the node process to spawn an OS subprocess with attacker-controlled environment variables, potentially leading to arbitrary code execution on the node host (via interpreter env-var injection techniques), disclosure of node secrets/keys accessible to that process, and use of that access as a pivot for further compromise — all without node-operator credentials, and (for the `ProposeJob` step) without even requiring `ApproveSpec` to be called.

### Likelihood Explanation
Feasible for any actor that can reach the FMS gRPC channel (MITM) or that operates/compromises a tenant feeds manager with proposal rights, matching the stated precondition. The only barrier is `exec.LookPath(command)` succeeding, which is trivially satisfiable on virtually any node host (bash/sh/python present). No node key or admin login is required. The `ProposeJob` code path making this reachable without approval significantly increases likelihood/severity versus what the question's call sequence describes.

### Recommendation
- Enforce a strict allow-list of permitted `pluginConfig.Command` values (e.g., only names matching pre-configured, node-operator-approved plugin binaries via `env.NewPlugin(pCfg.PluginName)`, ignoring/rejecting any `Command` override supplied by an external proposal).
- Reject or strip attacker-supplied `EnvVars` in specs originating from external Feeds Managers; if custom env vars are needed, require them to be defined by the node operator's local config, not by remote proposal content.
- Do not execute/start plugin subprocesses (`plugin.Start`) as part of `ProposeJob`/spec validation before operator approval; defer any process spawning to post-approval, operator-invoked steps.
- Have `ApproveSpec`/`AssertBridgesExist`-equivalent checks explicitly validate `pluginConfig.command` and `pluginConfig.envVars` against an allow-list before calling `generateJob`/`RegisterLOOP`.

### Proof of Concept
Integration test plan (Go, in `core/services/feeds` and `core/services/ocr2/validate`):
1. Construct an OCR2 TOML spec string with `pluginType = "plugin"`, `[pluginConfig]` containing `PluginName="test"`, `OCRVersion=2`, `Command="/usr/bin/env"` (or `"bash"`), and `EnvVars={"BASH_ENV"="/tmp/poc.sh"}` (a probe script created by the test that writes a sentinel file / exfiltrates an env var).
2. Call `feeds.service.ProposeJob` (or directly `validateProposeJobArgs`/`generateJob`) with this spec and assert:
   - `AssertBridgesExist`/`validateGenericPluginSpec` return **no error** for the non-allow-listed `Command`/`EnvVars` (demonstrating the missing check).
   - The mocked `RegistrarConfig.RegisterLOOP` (as in `capturingRegistrar` used in `standard_capabilities_test.go`) is invoked and captures a `CmdConfig` whose `Cmd`/`Env` match the attacker-supplied values.
3. Assert the sentinel file created by the probe script exists (or the injected env var appears in the spawned command's `Env`), proving attacker-controlled `Command`/`EnvVars` reach process execution without any node-operator confirmation.
4. Repeat via `ApproveSpec(id)` to confirm the same unchecked values flow through `jobSpawner.CreateJob` → `ocr2/delegate.go`'s `newServicesGenericPlugin` → `RegisterLOOP` at job start.
