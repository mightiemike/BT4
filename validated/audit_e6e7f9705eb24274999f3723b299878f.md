### Title
Silent `long` truncation via `BigInteger.longValue()` in witness-vote reward computation can corrupt reward accounting - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The vote-reward computation used across `MortgageService`, `VoteRewardUtil`, and `RewardViCalService` accumulates a per-witness "Vi" value (`BigInteger`) every cycle without any upper bound, then converts a scaled `BigInteger` result back to a `long` using the non-throwing `longValue()` method instead of `longValueExact()`. This mirrors the `FarmAccounting` bug class: an unbounded accumulator combined with a scale-down operation whose result is not range-checked, causing a silent incorrect (wrapped/truncated) result rather than an exception, and ultimately corrupting reward accounting for participants.

### Finding Description
`DelegationStore`/`RewardViCalService` maintain a cumulative reward-per-vote value `Vi` as a `BigInteger`, incremented every cycle by `reward * DECIMAL_OF_VI_REWARD / voteCount`: [1](#0-0) 

This value grows monotonically and without bound across cycles (analogous to `FarmAccounting.Info.reward` growing unboundedly with elapsed time in the Farm bug). When a user later claims their reward, the delta between two `Vi` snapshots is multiplied by the user's vote count and divided back down by `DECIMAL_OF_VI_REWARD`, with the final `BigInteger` result converted to `long` via `.longValue()`: [2](#0-1) 

The identical pattern exists in: [3](#0-2) [4](#0-3) 

Unlike `longValueExact()` (used consistently elsewhere in the hardened resource/exchange calculation code, e.g. `ResourceProcessor.divideCeilExact` and `ExchangeInjectActuator.doValidate`), `BigInteger.longValue()` performs a **silent, non-throwing truncation** to 64 bits when the value exceeds the `long` range — this is exactly the "no bounds check, silent incorrect result" defect class described in the report (there, `startFarming()`'s bound check didn't match the real overflow boundary of the downstream computation; here, there is no bound check at all on the intermediate `BigInteger` before a lossy conversion). If the accumulated `Vi` delta times `userVote` divided by `DECIMAL_OF_VI_REWARD` ever exceeds `Long.MAX_VALUE` (e.g., after very long-running vote accumulation, large vote counts, or witness rewards accumulating over many un-withdrawn cycles), the computed `reward` silently wraps to an arbitrary (potentially negative) value instead of throwing, and that incorrect value is then added to the user's allowance via `adjustAllowance`, corrupting on-chain TRX reward accounting.

### Impact Explanation
If triggered, this results in **accounting corruption**: a voter's claimable reward (`AccountCapsule.allowance`) could be computed as a wildly incorrect (or negative-then-clamped/exception-raising) value, causing participants to receive far less (or, in edge cases, far more) TRX reward than they are entitled to — the same "participants receive less than they are owed" impact called out in the report. Because `adjustAllowance` throws on negative-allowance underflow, a wrapped negative `amount` could also produce unexpected `BalanceInsufficientException` failures, effectively bricking reward withdrawal for affected accounts. This is unprivileged-actor reachable: any account holder who votes for a super representative and calls `queryReward`/reward withdrawal triggers this path.

### Likelihood Explanation
This requires the accumulated `Vi` values (which grow indefinitely with witness rewards and shrink with vote count) to reach a magnitude where `deltaVi * userVote / DECIMAL_OF_VI_REWARD` exceeds `Long.MAX_VALUE` (~9.2×10^18). Given real mainnet reward/vote magnitudes (TRX amounts are bounded to ~10^17 sun total supply, and `DECIMAL_OF_VI_REWARD` is a large fixed decimal scaling constant), this is a low-probability but non-zero risk over long time horizons for very large voters/witnesses; the exact scaling constant's value could not be fully confirmed from the available index in this session, so the precise numeric threshold at which truncation occurs is uncertain and should be verified directly against `DelegationStore.DECIMAL_OF_VI_REWARD`.

### Recommendation
Replace `.longValue()` with `.longValueExact()` in the three vote-reward computation call sites (`MortgageService.computeReward`, `VoteRewardUtil.computeReward`, `RewardViCalService.getNewRewardAlgorithmReward`) so that any out-of-range result throws `ArithmeticException` (caught and handled as a validation/consensus-safe failure) rather than silently producing an incorrect reward value — consistent with the hardened-calculation pattern already used elsewhere in the codebase (`ResourceProcessor`, `RepositoryImpl`, `ExchangeInjectActuator`). Additionally, confirm the actual maximum safe bound for `Vi` accumulation given `DECIMAL_OF_VI_REWARD`'s value, and consider bounding/normalizing `Vi` growth similarly to how the Farm fix capped `_MAX_REWARD_AMOUNT`.

### Proof of Concept
Not independently reproducible from the indexed code alone — reproducing requires knowing the exact value of `DelegationStore.DECIMAL_OF_VI_REWARD` and simulating many reward cycles to grow `Vi` past the overflow boundary, which could not be confirmed with certainty in this session (the constant's declaration file was not retrievable via the available search). A concrete PoC should be constructed by a background engineer who can inspect `DelegationStore.DECIMAL_OF_VI_REWARD`'s value and unit-test `MortgageService.computeReward`/`RewardViCalService.getNewRewardAlgorithmReward` with a crafted `Vi` delta (via `setWitnessVi`) chosen to exceed `Long.MAX_VALUE` after the multiply/divide, verifying that `.longValue()` returns a wrapped/incorrect value while `.longValueExact()` throws.
