### Title
Stale zero-balance `DelegatedResource` records are never deleted from storage when undelegating via TVM native contract - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
`UnDelegateResourceProcessor.execute`, invoked when a smart contract calls the `unDelegateResource` native/precompiled contract, always calls `repo.updateDelegatedResource(key, delegatedResourceCapsule)` at the end of execution, even when the resulting `DelegatedResourceCapsule` has zero balances for both bandwidth and energy. Unlike the equivalent broadcast-transaction actuators (`UnfreezeBalanceActuator`, `UnDelegateResourceActuator`), which explicitly call `delegatedResourceStore.delete(key)` in this case, the processor's write always persists through `RepositoryImpl.commitDelegatedResourceCache`, which has no zero-value deletion logic (unlike its sibling `commitDelegatedResourceAccountIndexCache`, which does check and delete on empty value).

### Finding Description
The code path is:
1. `UnDelegateResourceProcessor.execute` zeroes out the relevant frozen balance field of `delegatedResourceCapsule` and, if both bandwidth and energy balances are zero, only clears the `DelegatedResourceAccountIndex` entries (setting them to an empty `DelegatedResourceAccountIndexCapsule`), but never removes the `DelegatedResourceCapsule` record itself.
2. `repo.updateDelegatedResource(key, delegatedResourceCapsule)` is always invoked unconditionally, marking the entry `DIRTY` in `RepositoryImpl.delegatedResourceCache`.
3. On commit, `RepositoryImpl.commitDelegatedResourceCache` iterates the dirty cache and unconditionally calls `getDelegatedResourceStore().put(...)`, persisting the record with zero-value fields rather than removing it.

This leaves a residual "empty" `DelegatedResource` key/value entry permanently in the `DelegatedResourceStore` (a `TronStoreWithRevoking`-backed persistent store) instead of removing it, unlike the equivalent flow for the ordinary (non-TVM) `UnfreezeBalanceActuator` and `UnDelegateResourceActuator`, both of which explicitly `delete()` the key when balances reach zero.

### Impact Explanation
This does not directly leak sensitive secrets (there are no private keys in `DelegatedResourceCapsule`), but it does cause a persistent state/storage-hygiene divergence: an account that undelegated resources through a smart contract (TVM path) will retain a stale, non-deleted `DelegatedResourceCapsule` record with zero balances, whereas an account that did the same operation via a direct `UnDelegateResourceContract`/`UnfreezeBalanceContract` transaction gets its record properly deleted. This causes unbounded accumulation of dead entries in `DelegatedResourceStore`, inconsistent state between different code paths performing logically identical operations, and can affect any downstream logic or RPC queries that rely on `DelegatedResourceStore.get(key) == null` to determine "no delegation exists" versus "empty stale record exists."

### Likelihood Explanation
Any contract that calls the resource-delegation native contract (`unDelegateResource`) to fully undelegate bandwidth/energy will trigger this code path, so it is easily and repeatedly reachable via ordinary smart-contract calls (broadcast transactions triggering TVM execution), without requiring any privileged role.

### Recommendation
In `UnDelegateResourceProcessor.execute`, mirror the pattern used in `UnfreezeBalanceActuator`/`UnDelegateResourceActuator`: when both `getFrozenBalanceForBandwidth()` and `getFrozenBalanceForEnergy()` are zero, delete the `DelegatedResourceCapsule` entry (e.g., via a `Repository.deleteDelegatedResource` method) instead of calling `updateDelegatedResource`. Alternatively/additionally, add a zero-value check in `RepositoryImpl.commitDelegatedResourceCache`, analogous to the existing check in `commitDelegatedResourceAccountIndexCache`, so dirty entries with empty/zero-valued capsules are deleted from `DelegatedResourceStore` rather than persisted.

### Proof of Concept
1. Deploy a smart contract capable of invoking the `delegateResource`/`unDelegateResource` native precompiled contracts (as done in `FreezeV2Test`/`UnDelegateResourceActuatorTest`).
2. Freeze balance for bandwidth, delegate it fully to a receiver via the contract.
3. Undelegate the full amount via the contract's `unDelegateResource` call, driving `delegatedResourceCapsule.getFrozenBalanceForBandwidth()` and `...ForEnergy()` to 0.
4. Query `DelegatedResourceStore.get(key)` for the owner/receiver pair afterward: it returns a non-null `DelegatedResourceCapsule` with zero balances instead of `null`, contrasting with the equivalent test assertions in `UnDelegateResourceActuatorTest.testUnDelegateForBandwidth` (lines 207-210) which assert `Assert.assertNull(delegatedCapsule)` for the actuator (non-TVM) path.
