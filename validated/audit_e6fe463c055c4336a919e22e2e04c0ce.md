### Title
Cairo 0 classes served from the global contract cache are never re-verified against the current declared-class state, allowing execution of a class from a reverted/uncommitted block - (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
The reported bug class is "a cached/tracked value is not cleared/invalidated when the underlying state changes (e.g., on rejection/revert), and a later check trusts that stale value." In the sequencer, the analogous location is `StateReaderAndContractManager::get_compiled_from_class_manager`, which serves compiled classes from a long-lived, cross-block `GlobalContractCache`. For Cairo 1 classes, the code explicitly re-verifies declaration against the current state reader because "existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)." For Cairo 0 (deprecated) classes, this re-verification is deliberately skipped.

### Finding Description
`get_compiled_from_class_manager` looks up a class hash in the process-global `ContractClassManager` cache (`self.contract_class_manager.get_runnable(...)`), which is never invalidated per-block or per-revert — it is only bounded by LRU size [1](#0-0) . When a hit occurs, the code branches on the runnable class type: [2](#0-1) 

For any non-`V0` (i.e., Cairo 1/Sierra) class, it calls `self.state_reader.is_declared(class_hash)` and rejects the class with `StateError::UndeclaredClassHash` if the current state does not show it declared — precisely to guard against the cache holding an entry "from a reverted block." For `RunnableCompiledClass::V0(_)` (Cairo 0 classes), **no such check is performed**; the cached class is returned unconditionally.

This asymmetry is confirmed by the `FetchCompiledClasses::is_declared` contract itself, which documents that it only tracks Cairo 1 declarations and "Cairo 0 classes always return `false`" [3](#0-2) , and is implemented consistently across state-reader backends, e.g. `SyncStateReader::is_declared` only queries `is_cairo_1_class_declared_at` [4](#0-3)  and `DictStateReader::is_declared` explicitly returns `false` for any `V0` class [5](#0-4) .

Root cause: the global class cache is a stale, unbounded-lifetime tracker of "declared" status, exactly like the `amountDeposited` value in the referenced report that is never reset when the underlying acceptance state changes. The Cairo 1 path was hardened against this staleness (comment explicitly calls out reverted blocks), but the Cairo 0 path was left unguarded, so cached compiled Cairo 0 classes are trusted without confirming they are actually declared in the state the current transaction is executing against.

### Impact Explanation
If a Cairo 0 class becomes populated in the global cache (e.g., via a declare transaction that is later reverted/not committed, or via a block that is reorganized out), later transactions in a *different* execution context (mempool validation, a different fork, or a subsequent block after a revert) that reference the same class hash will successfully execute against a class that the canonical state says is undeclared. This can cause:
- Divergence between honest sequencer nodes evaluating the same transaction with a warm vs. cold cache, since one has the class cached (execution proceeds) and another does not (execution fails with `UndeclaredClassHash`), leading to non-deterministic transaction acceptance and diverging state/receipts.
- Execution and inclusion of a transaction that should have been rejected as invalid (undeclared class), producing a state diff / committed root that would differ from a node that correctly rejects the transaction — a wrong committed root/block-hash risk consistent with the "wrong committed root or honest-node divergence" impact category.
- Fee bypass in spirit similar to the original report: a class re-used without being properly (re-)declared and paid for in the current chain state.

### Likelihood Explanation
Reachable via a single submitted transaction (a Declare transaction that gets reverted or excluded from the canonical chain, followed by an Invoke/Deploy referencing the same Cairo 0 class hash) — no privileged operator/proposer role is required, matching the "single submitted transaction, contract call, declared class" reachability constraint. The cache is process-global and shared across the mempool's stateful validator (`StatefulTransactionValidator`, which is built on `StateReaderAndContractManager`) and the block-execution path, so validation-time and execution-time caching interplay increases the chance of the stale-cache condition being hit in normal operation (declare-then-fail patterns, re-orgs, or gateway/mempool retries).

### Recommendation
Apply the same re-verification that Cairo 1 classes receive to Cairo 0 classes: extend `FetchCompiledClasses::is_declared` (or add a parallel check) to also confirm Cairo 0 declaration status against the current `state_reader` before trusting a cached `RunnableCompiledClass::V0` entry, removing the `RunnableCompiledClass::V0(_) => {}` no-op branch in `get_compiled_from_class_manager` in favor of an actual declared-state check, consistent with how `is_declared` is already implemented for Cairo 1 classes.

### Proof of Concept
Not independently verifiable from static code review alone — reproducing the divergence requires an end-to-end scenario (populate the shared `GlobalContractCache`/`ContractClassManager` with a Cairo 0 class via a Declare transaction, then revert/exclude that block or run a parallel validation context so the state reader no longer reports the class declared, then submit a second transaction referencing that class hash and observe it executes successfully instead of failing with `UndeclaredClassHash`). This would need to be exercised with a running node/test harness (e.g., in `crates/blockifier/src/state/state_reader_and_contract_manager_test.rs`, which already has scenarios like `cached_but_verification_failed_after_reorg_scenario` for Cairo 1 but no equivalent Cairo 0 case) — I could not execute or extend these tests in this read-only session and could not confirm at what exact call sites (mempool stateful validator vs. block executor) the shared cache is populated across reverted transactions in practice.
