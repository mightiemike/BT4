### Title
`ensure_match_transaction_info` never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so replay-verify accepts a corrupted state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single function used by every replay/verification tool (`chunk_executor::verify_execution`, `db-tool replay_on_archive`, `aptos-debugger`, `aptos-move/cli`) to confirm that re-executing a transaction against archived inputs reproduces the exact same ledger commitment recorded on-chain. It checks status, gas used, write-set hash, and event root hash, but it explicitly skips the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields of `TransactionInfo` — the fields that authenticate the actual Merkle root of world state. A state-root divergence (e.g. a Jellyfish Merkle Tree / state-summary bug) can therefore pass every replay-verify and debugger check as "correct" even though the locally computed state root does not match the authenticated ledger state.

### Finding Description
`ensure_match_transaction_info` in [2](#0-1)  validates only 4 fields: `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`. The function's own trailing comment admits the gap: [3](#0-2) 

This comment states the comparator "ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution", and calls out that checkpoint hashes must be validated before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled — but the primary `state_checkpoint_hash` field (already active on mainnet, unlike hot-state/position hashes which are currently `None`) is equally unchecked by this same function, for every caller.

Concretely, the write-set match only proves that the *delta* applied to storage is byte-identical; it says nothing about whether applying that delta to the correct prior state produces the correct new Merkle root. A bug anywhere in the JMT/state-summary path (e.g. `execution/executor/src/workflow/do_state_checkpoint.rs`, `storage/aptosdb`'s state-merkle commit, or hot-state/position-state root computation) that causes a wrong `state_checkpoint_hash` to be computed would still let `ensure_match_transaction_info` return `Ok(())`, because that field is simply never compared: [4](#0-3) 

This function is the terminal correctness check in every caller that matters for cross-checking state-root integrity against archived, authenticated data:
- `execution/executor/src/chunk_executor/mod.rs` `verify_execution` — the state-sync/chunk-executor's own re-execution verification path [5](#0-4) 
- `storage/db-tool/src/replay_on_archive.rs` `execute_and_verify` — the dedicated replay-verify tool run before hard forks/network upgrades to confirm deterministic replay of the entire chain history [6](#0-5) 
- `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` debugging/replay utilities.

None of these call sites independently re-derive or compare `state_checkpoint_hash`. So the one authenticated field that actually binds a transaction to "the world state Merkle root is X" is never verified end-to-end by the tooling whose entire purpose is to catch exactly this class of divergence.

### Impact Explanation
This breaks the "committed state must match the correct VM result" and "wrong state proof/root accepted as valid" invariants specifically for the replay/verification tooling. If a state-root computation bug is introduced (e.g., in JMT construction, hot-state merklization, or position-state root logic), replay-verify — which is Aptos's designated safety gate for validating full-history determinism before protocol/hard-fork changes — would report success even though the locally recomputed state Merkle root diverges from the one committed on mainnet. This is a hard-fork/replay-only divergence that silently escapes detection, directly matching the "wrong accumulator/state proof accepted as valid" and "hard-fork-only divergence during replay/verification" impact categories.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires an underlying state-root computation bug to exist first (this finding does not itself corrupt state), but when such a bug exists, this gap guarantees it is undetected by the very tool built to catch it — as evidenced by the code's own comment acknowledging the blind spot for `position_state_checkpoint_hash`, which trivially extends to the currently-active `state_checkpoint_hash` field as well, since the same function skips it unconditionally for all callers, not just when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is on.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s independently-recomputed state checkpoint hash(es) (when the local checkpoint output produced one for this transaction index) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, mirroring the existing `ensure!` pattern already used for `write_set_hash` and `event_root_hash`. Since `TransactionOutput` doesn't currently carry the computed checkpoint hash, thread it through (or add an optional parameter) from `DoStateCheckpoint`'s output so all four call sites (`chunk_executor`, `replay_on_archive`, `cli`, `aptos-debugger`) get it validated without each needing bespoke logic.

### Proof of Concept
1. Introduce (for testing) a deliberate off-by-one or wrong-ordering bug in the JMT update path used by `DoStateCheckpoint` (e.g. `execution/executor/src/workflow/do_state_checkpoint.rs`) so the locally computed `state_checkpoint_hash` differs from the one already persisted/archived for a given version, while keeping the write set, events, gas, and status identical (achievable since the state-checkpoint hash is derived from applying the same write set to the SMT — a bug in SMT node ordering/hashing produces a different root without changing the write set itself).
2. Run `db-tool replay-on-archive` (or `chunk_executor::verify_execution`) over that version range against the archived DB.
3. Observe that `ensure_match_transaction_info` ( [2](#0-1) ) returns `Ok(())` because it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, so the tool reports the replay as successfully verified despite the world-state root having silently diverged from the authenticated ledger.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
