### Title
`ensure_match_transaction_info` skips validating `position_state_checkpoint_hash` (and `hot_state_checkpoint_hash`), letting replay/backup verification accept a divergent trading-native state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-equivalence check used by replay/verification tooling (db-tool `replay-verify`, `aptos-debugger`, chunk executor, `aptos-move/cli`) to confirm that a locally re-executed `TransactionOutput` matches a trusted, ledger-committed `TransactionInfo`. The function checks status, gas, `write_set` hash (`state_change_hash`) and event root hash, but it explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or the newly introduced `position_state_checkpoint_hash` field — a gap the code itself documents as a known, unfixed hole.

### Finding Description
`TransactionInfoV1` now carries a `position_state_checkpoint_hash` field that commits to the root of the "trading-native" position Sparse Merkle Tree, computed in `DoStateCheckpoint::compute_position_checkpoint` (`execution/executor/src/workflow/do_state_checkpoint.rs:90-190`) whenever `execution_output.compute_trading_native_state_roots` is set. This root is derived purely from `native_position_iter()` write-set entries and is meant to be an independently-verifiable commitment to position ledger state, analogous to `state_checkpoint_hash`.

However, `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) validates only:
- status vs `txn_info.status()`
- `gas_used()`
- `write_set` hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

and returns `Ok(())` without ever inspecting `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The function's own trailing comment acknowledges this: [1](#0-0) 

This comparator is the actual verification primitive used by `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` to decide whether a replayed chunk matches the trusted archived `TransactionInfo`s: [2](#0-1) 

and by `aptos-debugger` (`aptos-move/aptos-debugger/src/aptos_debugger.rs:233-246`) and `aptos-move/cli/src/commands.rs:2809-2813`, all of which are explicitly presented as "did the replay reproduce the correct/authenticated ledger state" tools.

Because none of these call sites separately re-derive and compare the position state root, a bug in `compute_position_checkpoint` (or in any native-position write-set entry translation feeding `native_position_iter`) that produces a wrong position SMT root would go completely undetected by `replay-verify`, `aptos-debugger execute-past-transactions`, and `aptos move replay` output comparisons — these tools would report a clean, successful match even though the durable position-state commitment diverges from the correct value.

### Impact Explanation
This breaks the state-commitment integrity invariant that "committed/replayed state must be provably bound to the correct root," specifically for the newly added trading-native position state root. A wrong `position_state_checkpoint_hash` is exactly the class of "wrong accumulator/state root accepted as valid" impact called out in the task's required-impact list, because the very tool designed to catch such divergence (`replay-verify`, used to audit synced/backup ledger data against trusted history) silently ignores this field. In a hard-fork/execution-divergence scenario (e.g., a bug in `compute_position_checkpoint`'s collapsing of latest-per-key writes, or a native-position related VM bug), replay-verify would report success while the position ledger state genuinely diverged from what is committed on mainnet — undermining confidence in archive/replay-based integrity audits and potentially masking real consensus-breaking bugs in the position-state subsystem. This is high severity for a proof/state-integrity gate because it defeats a security control (replay verification) rather than corrupting consensus-critical state directly; the committed `TransactionInfo.position_state_checkpoint_hash` itself is still what the ordinary consensus verification (`AccumulatorProof`/`TransactionOutputListWithProof::verify`) is anchored to, but the auditing/backup-verification tooling built on `ensure_match_transaction_info` provides a false sense of assurance.

### Likelihood Explanation
The gap is deterministic and always present — every call to `ensure_match_transaction_info` skips these fields, not just under some rare condition. It requires no attacker privilege to trigger; it is exposed any time the feature computing trading-native state roots (`compute_trading_native_state_roots`) is active and someone relies on `replay-verify`/`aptos-debugger`/CLI comparison to validate replayed history. The realistic trigger is a separate bug in the position-state computation path (which is a newer, less-hardened piece of code per the surrounding comments referring to "trading-native" as WIP) combined with reliance on these verification tools to catch it — likelihood of exploitation-by-a-bug is moderate/plausible given the code is explicitly flagged as incomplete by its own authors.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values whenever those fields are populated on `txn_info`, or supply them as additional expected-value parameters analogous to `expected_write_set`/`expected_events`. At minimum, gate `replay_on_archive.rs` and the CLI/debugger replay tools behind an explicit check that recomputes and compares the position state root before reporting a chunk as verified, matching what is already done for `write_set`/`events`.

### Proof of Concept
Not directly exploitable by an external attacker as a standalone PoC — the flaw is a missing check rather than an accepted forged proof. Demonstration path: enable `compute_trading_native_state_roots`, inject an artificial off-by-one in `DoStateCheckpoint::compute_position_checkpoint`'s `collect()` closure (e.g., skip the last write in a checkpoint range) so the produced `position_state_checkpoint_hash` differs from a correctly computed one, then run `replay-on-archive` or `aptos-debugger` comparison against the archived (correct) `TransactionInfo`s carrying the original hash. Because `ensure_match_transaction_info` never reads `position_state_checkpoint_hash()`, the tool reports the replay as matching/verified despite the wrong root, confirmed by inspection of the function body at [3](#0-2) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
