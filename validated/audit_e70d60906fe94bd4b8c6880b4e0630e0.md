### Title
Oversized-receipt size clamp in cross-shard forwarding lets a single transaction bypass the granted bandwidth/size limit - (File: runtime/runtime/src/congestion_control.rs)

### Summary
The Sherlock report describes `maxPotentialDebt` being exceeded because the check compares only the *existing* debt against the cap, omitting the new amount being added. The analogous defect in nearcore is in `ReceiptSinkV2::try_forward`, which decides whether a cross-shard receipt may be forwarded by comparing an artificially *reduced* size value against the receiver's granted bandwidth (`forward_limit.size`), instead of the receipt's true size — letting the actual bytes sent exceed the size the receiving shard/bandwidth scheduler explicitly granted.

### Finding Description
`try_forward` clamps the receipt's size down to `max_receipt_size` purely "for the limit comparison" whenever the real receipt is larger than `max_receipt_size`: [1](#0-0) 

The comparison and bookkeeping then use this clamped value: [2](#0-1) 

`forward_limit.size >= size` is checked against the clamped `size`, and `forward_limit.size -= size` decrements by the clamped amount — but the actual `Receipt` object pushed into `outgoing_receipts` (and ultimately serialized into the chunk / state witness / receiver's incoming receipts) still carries its true, oversized payload. The same clamping-for-limit-purposes pattern is repeated for bandwidth-request generation: [3](#0-2) 

The root cause enabling an oversized receipt to exist in the first place is that `validate_receipt` only enforces `max_receipt_size` in `NewReceipt` mode, at creation time, before certain fields (e.g. `output_data_receivers`, a large returned value from `promise_return`) are appended: [4](#0-3) 

This exact bypass is already reproduced by existing tests, confirming it is reachable from ordinary user transactions/contract calls with no special privilege: [5](#0-4) [6](#0-5) 

The code even self-documents this as a known, tracked defect (`ExistingReceipt` mode / issue #12606): [7](#0-6) 

Just like the `maxPotentialDebt` check that neglected to add the new debt before comparing against the cap, `try_forward`'s size check substitutes a smaller, capped stand-in value for the real quantity being admitted against the limit, so the limit (`forward_limit.size`, i.e., the bandwidth grant computed by `CongestionControl`/the bandwidth scheduler) is not actually enforced against the true value being pushed through it.

### Impact Explanation
An unprivileged account can, via ordinary contract calls (`promise_return`, large return values, yield/resume with large payload — as shown in the reproducing tests), create an action/data receipt whose real serialized size exceeds `max_receipt_size`. When that receipt is routed cross-shard, `try_forward` treats it as if it were only `max_receipt_size` bytes for the purpose of comparing against and decrementing the receiver's bandwidth grant (`OutgoingLimit.size`), while the full oversized payload is actually transmitted and later must be incorporated into `source_receipt_proofs`/`ChunkStateWitness` on the receiving side. This violates the protocol's own invariant that `outgoing_size_limit`/bandwidth grants bound the bytes any shard may push to another shard per block — the exact protection this accounting exists to enforce (per `protocol-model/spec/cross-shard-congestion.md`, "Oversized-receipt workaround" and "state witness size limits" documentation) can be silently exceeded. This can inflate the receiving shard's `ChunkStateWitness` size beyond the limits the whole size-budget design (~21MiB target documented in `docs/misc/state_witness_size_limits.md`) is meant to guarantee, and can defeat backpressure/congestion guarantees a strategy of validators relies on to bound per-block work/memory.

### Likelihood Explanation
Reachable by any account with a deployed contract and no special permission: a single transaction/contract call producing a large `promise_return`/value/yield payload is sufficient, exactly as reproduced in `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`. No malicious validator, network-layer, or leaked-key assumption is required — this is a plain transaction/RPC-reachable path through normal receipt creation and the deterministic apply loop.

### Recommendation
Do not substitute a clamped/capped value for the real size when comparing against or decrementing `forward_limit.size` (or any other size/gas cap). Instead, fix the root cause: enforce `max_receipt_size` for *every* mutation that can grow a receipt after its initial creation-time check (e.g., `promise_return`, output_data_receivers assignment, yield/resume payload assembly) so that an oversized receipt can never be constructed, matching the recommendation pattern of always incorporating the full/actual new value into the check rather than working around it downstream with an approximation.

### Proof of Concept
The existing test suite already demonstrates the underlying oversized-receipt creation and the runtime's workaround path: [8](#0-7) 
A contract call chain creates promise `C` whose base receipt is at `max_receipt_size`, then `output_data_receivers` is appended afterward, pushing the true serialized size above `max_receipt_size` — this receipt then flows through `try_forward`, where its size is clamped only for the bandwidth-limit comparison/decrement, not for what is actually transmitted.

            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,

        }),
    });

        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
