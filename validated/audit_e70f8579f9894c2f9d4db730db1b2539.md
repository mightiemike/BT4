### Title
Unhandled panic in synchronous Sierra-to-Native compilation path causes sequencer-wide crash on a single declare transaction - (File: `crates/blockifier/src/state/native_class_manager.rs`)

### Summary
Analogous to the Chainlink report's root cause — an unhandled failure of an external, un-mockable dependency call that the caller cannot recover from — the sequencer's `NativeClassManager::set_and_compile` invokes the Sierra→Native compiler and, depending on configuration, either panics directly or (more subtly) reaches an `.expect()`/`panic!` on channel failure. Because compilation is triggered synchronously (`CairoNativeMode::WaitOnCompilation`) from the state-reading path used during transaction execution, a class that the network already accepted (it passed Sierra→CASM compilation and Sierra class-hash validation) but that fails the separate Sierra→Native compiler can bring down the executing thread/process with no caller-side recovery, unlike the CASM compilation path in the gateway which is isolated in a subprocess with resource limits.

### Finding Description
`ClassManager`/gateway declare-transaction admission compiles Sierra to CASM in an isolated subprocess (`crates/apollo_compile_to_casm/src/compiler.rs`), and failures there are returned as `Result` and rejected safely [1](#0-0) . However, the *native* compilation path used by the execution engine (`blockifier`) is different: `NativeClassManager::start` optionally runs Sierra→Native compilation **in-process** rather than in an isolated subprocess, and when `cairo_native_mode` is `WaitOnCompilation`, compilation happens synchronously inline in `set_and_compile`, which is called from `StateReaderAndContractManager::get_compiled_from_class_manager` — i.e., directly on the transaction-execution/state-read hot path reachable by any submitted transaction that references a declared class [2](#0-1) .

`process_compilation_request` calls `compiler.compile(...)` and, on failure, **panics** if `panic_on_compilation_failure` is enabled: [3](#0-2) 

Separately, even when `panic_on_compilation_failure` is `false` (the shipped default in `batcher_config.json` and `gateway_config.json`), the asynchronous `LazyCompilation` path relies on an `mpsc::sync_channel`; if the receiver end (compilation worker thread) has terminated for any reason, `send_compilation_request` unconditionally panics: [4](#0-3) 

This mirrors the Chainlink bug class precisely: a call into a dependency (`feed.latestRoundData()` / the native compiler) whose failure is not defensively handled with a fallback, causing the caller to be permanently stuck. Here, the "feed" is the native compiler binary/thread, and the class hash — like the Chainlink feed address — cannot be un-declared once accepted by CASM compilation; a class that fails native compilation will be retried on every block/transaction that touches it.

Unlike `_run_executor`'s `catch_unwind`, which isolates worker-thread panics *within the concurrent executor* and re-panics via `resume_unwind` to abort the whole worker pool [5](#0-4) , a panic on this path is not silently absorbed — it deliberately aborts the executor, which is by design for other panic scenarios (e.g., logic bugs) but is inappropriate for a compiler-dependency failure that is attacker-triggerable via a legitimately-declared, network-accepted Sierra class that merely fails the separate native-compiler pass.

### Impact Explanation
If Sierra→Native compilation of a validly-declared class fails (a real, historically-observed possibility since the CASM compiler and native compiler are separate codebases with different bug surfaces/feature coverage), and `panic_on_compilation_failure` is enabled, or the compilation worker channel is disconnected, then:
- The panic propagates through `WorkerPool::_run_executor` via `resume_unwind`, aborting the entire block execution (`panic!("One of the threads panicked.")` in `check_panic`) [6](#0-5) .
- Since block execution/re-execution is deterministic and every honest validator running with the same configuration would process the same declared class the same way, all nodes attempting to build/validate a block containing an invocation of that class would crash identically, halting block production network-wide — a permanent denial of service until the offending class is somehow avoided (impossible, since it is already committed to state and cannot be un-declared, exactly as in the Chainlink report where "feeds cannot be changed after they are configured").
- This satisfies the required impact bar: a network unable to confirm new transactions.

### Likelihood Explanation
Likelihood depends on operational configuration (`panic_on_compilation_failure=true`, which is not the current default in the sampled `batcher_config.json`/`gateway_config.json`) or on the compilation worker thread dying (e.g., due to an unrelated panic inside `run_compilation_worker`'s loop causing `unwrap_or(())` to be bypassed by a channel disconnect, or an operator misconfiguration). Since defaults observed show `panic_on_compilation_failure: false`, the primary panic path is not enabled by default, lowering baseline likelihood; however, the channel-disconnect panic in `send_compilation_request` (unconditional, not gated by config) is reachable any time the worker thread has exited unexpectedly, which is a plausible fault condition once native compilation is enabled (`lazy_compilation` mode, as configured in `batcher_config.json`).

### Recommendation
- Never `panic!` on a compiler-dependency failure reachable from transaction execution; always return a typed error and fall back to the CASM (`CompiledClassV1`) execution path, exactly as `CachedCairoNative::CompilationFailed(casm)` already does for the non-panicking branch.
- Remove or hard-disable `panic_on_compilation_failure` in any production-reachable execution path (restrict it to test/dev tooling only).
- Make `send_compilation_request`'s `TrySendError::Disconnected` case degrade gracefully (log + fallback to CASM) instead of `panic!`, and ensure the compilation worker thread is supervised/restarted rather than allowed to silently die.
- Isolate native compilation the same way CASM compilation is isolated for declare transactions (subprocess + resource limits), preventing an in-process crash of the compiler from taking down block execution.

### Proof of Concept
1. Configure a sequencer node with `contract_class_manager_config.cairo_native_run_config.cairo_native_mode = "wait_on_compilation"` and `panic_on_compilation_failure = true` (a supported, documented configuration value, see `crates/apollo_node/resources/config_schema.json` lines 3012-3026).
2. Submit (or have accepted historically) a `Declare` transaction for a Sierra class that compiles successfully to CASM (passing gateway admission) but fails Sierra→Native compilation (e.g., due to a native-compiler-specific limitation/bug on certain libfuncs).
3. Submit any `Invoke`/`L1Handler` transaction that triggers execution of that class.
4. During execution, `StateReaderAndContractManager::get_compiled_from_class_manager` calls `set_and_compile`, which synchronously invokes `process_compilation_request`; the compile fails and, with `panic_on_compilation_failure=true`, panics [7](#0-6) .
5. The panic propagates and aborts block execution for every node attempting to execute/re-execute that transaction, since the class (once declared) cannot be un-declared, permanently blocking any block containing a call to it — network-wide denial of service, analogous to the Chainlink feed that "cannot be changed after they are configured."

    fn _run_executor(&self, worker_executor: &WorkerExecutor<S>) {
        if self.a_thread_panicked.load(Ordering::Acquire) {
            panic!("Another thread panicked. Aborting.");
        }

        // Making sure that the program will abort if a panic occurred while halting
        // the scheduler.
        let abort_guard = AbortIfPanic;
        // If a panic is not handled or the handling logic itself panics, then we
        // abort the program.
        let res = panic::catch_unwind(panic::AssertUnwindSafe(|| {
            worker_executor.run();
        }));
        if let Err(err) = res {
            // First, set the panic flag. This must be done before halting the scheduler.
            self.a_thread_panicked.store(true, Ordering::Release);

            // If the program panics here, the abort guard will exit the program.
            // In this case, no panic message will be logged. Add the cargo flag
            // --nocapture to log the panic message.

            worker_executor.scheduler.halt();
            abort_guard.release();
            panic::resume_unwind(err);
        }
