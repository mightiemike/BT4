### Title
Unrecoverable burn of a deleted account's balance when `DeleteAccountAction.beneficiary_id` does not exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` unconditionally emits a `Receipt::new_balance_refund` to `delete_account.beneficiary_id` carrying the account's entire remaining balance, and then immediately deletes the account and clears `*account = None`. Neither `validate_delete_action` (`runtime/runtime/src/action_validation.rs:447-451`) nor `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) checks that the beneficiary account exists. Because the payout receipt is constructed via `new_balance_refund`, it is a "refund" receipt (`predecessor_id == "system"`), and per the documented refund semantics, "If the execution of a refund fails, the refund amount is burnt" [1](#0-0) . Refund receipts are also never allowed to implicitly create the destination account, confirmed by `implicit_creation_allowed` returning `false` whenever `is_refund` is set [2](#0-1)  and by the dedicated regression test `refund_may_not_create_universal_account` which asserts the refund fails with `AccountDoesNotExist` and the account is not created [3](#0-2) .

### Finding Description
An unprivileged account owner submits their own `DeleteAccountAction { beneficiary_id }` transaction (this is a normal, permissionless self-service action, reachable directly via RPC/transaction submission). The action:
1. Reads `account_balance = account_ref.amount()` and unconditionally schedules `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` [4](#0-3) .
2. Immediately removes the account from state (`remove_account`, `*account = None`) with no rollback path tied to whether the beneficiary receipt later succeeds [5](#0-4) .
3. The only validation performed on `beneficiary_id` at admission time is a syntax check, not an existence check [6](#0-5) .

If `beneficiary_id` names an account that does not exist (e.g., a typo, a never-created named account, or an account that was deleted in the interim), the follow-up transfer receipt is processed as a refund, and `check_account_existence` rejects the `Transfer` action with `AccountDoesNotExist` because refunds are barred from implicit account creation [7](#0-6) [2](#0-1) . Per protocol design, a failed refund's balance is simply burnt rather than returned to the (now-deleted) originating account [1](#0-0) .

This is structurally identical to the reported Solidity bug class: a value-transfer path assumes the destination can validly receive funds without checking first, and the failure mode destroys value instead of reverting the state change that produced the payout. In Solidity, a missing `payable` cast can cause the whole transaction to revert (funds stay with the contract); in nearcore, the destructive step (account deletion) is already committed and cannot be undone when the compensating transfer later fails, so the loss is permanent and one-directional.

### Impact Explanation
Funds are irrecoverably burnt from circulating supply due to an unprivileged, single-transaction user action combined with a benign input mistake (an existent-looking but not-yet-created or mistyped beneficiary account id). This is a genuine, transaction-triggered supply/value-destruction bug reachable by any account holder with no special privileges, satisfying "permanently frozen/lost funds" and "supply deflation via unintended burn" impact criteria.

### Likelihood Explanation
Likelihood is driven entirely by user/relayer error or a race (beneficiary account deleted between when the `DeleteAccountAction` is signed and when it executes) — no attacker cooperation from a third party is required, and the action is a first-class, commonly available user operation (self-service account deletion with an explicit beneficiary, also exposed via Rosetta's `DELETE_ACCOUNT`/`REFUND_DELETE_ACCOUNT` operations, per `pytest/tests/sanity/rosetta.py`).

### Recommendation
Before deleting the account, validate that `beneficiary_id` refers to an existing account (or restrict it to always be `predecessor_id`/an already-known related account, or run the funds through a non-refund transfer path that supports implicit creation, mirroring the general `Transfer` action's `check_account_existence`/`implicit_creation_allowed` gating). At minimum, fail the `DeleteAccount` action outright (leaving the account and its balance intact) if the beneficiary does not exist, instead of committing the deletion and letting the compensating refund silently burn the balance.

### Proof of Concept
1. Create account `victim.near` with balance `B`.
2. Submit `SignedTransaction` from `victim.near` to itself containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent-typo.near" })` (a syntactically valid but never-created account id — passes `validate_delete_action`).
3. `action_delete_account` runs: emits `Receipt::new_balance_refund("nonexistent-typo.near", B)` and deletes `victim.near` from state.
4. The refund receipt is processed against `nonexistent-typo.near`; `check_account_existence` rejects the `Transfer` (refund, so no implicit creation) with `ActionErrorKind::AccountDoesNotExist`.
5. Per `docs/RuntimeSpec/Refunds.md`, the failed refund amount `B` is burnt. `victim.near` no longer exists and `nonexistent-typo.near` never received anything — balance `B` is permanently destroyed with no recovery path, confirmed by the pattern already tested (for a different target type) in `refund_may_not_create_universal_account` [8](#0-7) .
