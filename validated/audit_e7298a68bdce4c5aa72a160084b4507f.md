## Title
Webhook shop-domain spoofing via unauthenticated headers — `X-Shopify-Shop-Domain`/topic/webhookId are not covered by HMAC, enabling cross-tenant webhook impersonation - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts](https://github.com/Thankgoddavid56/shopify-app-js--010))

### Summary
The Escher report's root cause is that a value used to establish *identity/authorization* (`sale.edition`) is accepted from an untrusted party and never checked against the *cryptographically trustworthy* source (the legitimate `Escher721Factory`). The analogous defect in `shopify-app-js` is in the webhook pipeline: the HMAC that authenticates an inbound webhook is computed **only over the raw body**, while the shop identity (`X-Shopify-Shop-Domain`), topic, and webhook id are read from unauthenticated headers and trusted as-is to select which tenant's offline session/admin client to attach to the request.

### Finding Description
`validateHmacFromRequestFactory` in [1](#0-0)  computes and checks the HMAC using `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` — i.e., it authenticates the byte content of the body only, with the shared per-app `apiSecretKey`.

`validateFactory` in [2](#0-1)  calls this HMAC check first, and only *after* it passes, separately reads `domain`, `topic`, `webhookId` straight out of request headers via `checkWebhooksHeaders`/`checkEventsHeaders` [3](#0-2) . None of these header values are included in the HMAC computation, so they are not cryptographically bound to the signed body — they are effectively attacker-controllable metadata for any request that carries a body+HMAC pair the attacker happens to have received legitimately (e.g., from their own shop's installation of the app).

Downstream, `authenticateWebhookFactory` in both the Remix and React Router adapters takes `check.domain` at face value and uses it to load the tenant's offline session/admin client: [4](#0-3) 

Because `apiSecretKey` is a single secret shared by the app across **all** shops (not shop-specific), any actor who can install the app on a shop they control (an ordinary, unprivileged merchant) can capture a legitimately Shopify-signed webhook body+HMAC pair, then replay that exact body to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's domain. The HMAC check still passes because it only validates the body bytes, and `ensureValidOfflineSession(params, check.domain)` will load the victim's offline session if one exists, attaching a victim-authenticated `admin` client and shop context to the (attacker-controlled) payload.

### Impact Explanation
This lets a single unprivileged actor with their own shop's app installation impersonate arbitrary other tenants of the same app in the webhook processing pipeline: they can supply attacker-chosen payload bytes labeled as coming from a victim's shop/topic, causing the app's webhook handler business logic to execute with a victim-scoped offline session and admin client. Depending on what the app does in its webhook handler (e.g., write victim data, trigger admin API mutations, delete records, sync state), this is a concrete cross-tenant access / forged Shopify request vector — directly matching the report's core lesson that the accepted "identity" of the incoming entity must be validated against something the attacker cannot control, not trusted from unauthenticated fields.

### Likelihood Explanation
Exploitability requires only: (1) the attacker be an ordinary merchant who can install the target app on their own store to receive at least one real signed webhook, and (2) send a raw HTTP POST with the captured body/HMAC but a spoofed shop-domain/topic header to the app's public webhook endpoint. No secrets, MITM, or privileged access are required, making this a realistic scenario for any public multi-tenant Shopify app built on this library that has an installed base including the attacker's own store — a low-to-moderate-effort, single-actor attack.

### Recommendation
Bind the header-derived identity fields into the authenticated data before trusting them: include `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` (or a canonicalized header block) in the HMAC input, or otherwise cryptographically verify that the claimed `domain`/`topic` are consistent with a value Shopify signed for that specific webhook delivery. At minimum, downstream consumers of `webhooks.validate`/`webhooks.process` should be documented/enforced to treat `domain` as untrusted for authorization decisions unless independently corroborated (e.g., cross-checked against the API version/id and rejecting duplicate/replayed `webhookId`s per shop), and libraries should consider de-duplicating `webhookId` per shop to reduce replay usefulness.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any webhook subscription (e.g. `PRODUCTS_CREATE`), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header value sent by Shopify.
2. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `validateHmacFromRequestFactory` recomputes the HMAC over the (unchanged) body using the shared `apiSecretKey` and it matches, so `valid: true` is returned [5](#0-4) .
4. `checkWebhooksHeaders` reports `domain: 'victim.myshopify.com'` straight from the spoofed header [6](#0-5) .
5. `authenticateWebhookFactory` loads the victim's offline session via `ensureValidOfflineSession(params, check.domain)` and hands the attacker-supplied payload to the app's webhook handler with a victim-scoped `admin` client attached [7](#0-6) .

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
