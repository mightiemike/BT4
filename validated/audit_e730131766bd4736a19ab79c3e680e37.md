### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash validation, allowing `db-tool replay-verify` to certify a divergent authenticated state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the sole per-transaction comparator used by `db-tool`'s `replay_on_archive::execute_and_verify` [2](#0-1)  to check freshly re-executed transaction outputs against the archived, ledger-info-authenticated `TransactionInfo`. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as documented in its own TODO comment [3](#0-2) .

### Finding Description
`TransactionInfoV1` carries multiple state-root fields beyond `state_change_hash` — notably `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — each of which is bound into the accumulator-authenticated `TransactionInfo` hash and represents a distinct commitment to a computed state tree root at that version [4](#0-3) . The comparator function used to validate re-executed output against the archived, signed `TransactionInfo` skips exactly these fields:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution.
``` [3](#0-2) 
This means `replay_on_archive` — a tool used to independently re-verify that historical mainnet execution reproduces the ledger's authenticated state — can silently accept a `TransactionOutput` whose write-set matches (same `state_change_hash`) but whose resulting Merkle/JMT root (state checkpoint, hot-state, or native-position state root) diverges from the value actually committed and signed into the `LedgerInfo`.

### Impact Explanation
This does not affect consensus/commit correctness directly (the primary commit-time verification path, `LedgerUpdateOutput::ensure_transaction_infos_match`, compares whole `TransactionInfo` objects via `==`, which does include these hash fields) [5](#0-4) . However, `replay_on_archive` is exactly the tool relied upon to catch state-computation regressions (e.g., a bug in native-position/hot-state root computation) against real historical chain data. Because the comparator omits checkpoint-hash checks, a genuine divergence in state-root computation (e.g., from a future change under the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature referenced in the TODO) could pass replay-verify undetected, masking a hard-fork-class state-divergence bug until it surfaces in production. The impact is therefore indirect (an integrity-tooling blind spot rather than a live acceptance of a wrong proof/root on mainnet).

### Likelihood Explanation
Currently low: the feature this gap is meant to guard (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`/native-position state roots) is explicitly noted as not yet enabled, and the code comment itself flags this as a known, pre-existing TODO rather than an exploitable path today. It becomes directly relevant once that feature is turned on, at which point replay-verify would lose its ability to catch position/hot-state root divergences.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info` and computable/known locally) before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any hot-state root feature) is enabled, so `db-tool`'s replay-verify path cannot report success while the authenticated state root diverges from local execution.

### Proof of Concept
Not applicable as a live mainnet exploit — this is a tooling/verification gap, not an on-chain state-acceptance bug. The gap is demonstrated by inspecting `ensure_match_transaction_info`, which never reads `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, and its unique caller `execute_and_verify` in `replay_on_archive.rs`, which relies solely on this function to certify per-transaction correctness during replay against archived, signed ledger data.

    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())
        {
            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
    }
