### Title
Front-runnable, unauthenticated `BOOTSTRAP` declare transaction allows squatting/poisoning of the genesis class hash - ([File: crates/starknet_api/src/executable_transaction.rs], [File: crates/blockifier/src/transaction/account_transaction.rs], [File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo])

### Summary
Starknet's genesis/bootstrap flow declares initial classes (account, ERC20, etc.) via a special, hard-coded `sender_address = 'BOOTSTRAP'` that completely bypasses signature/`__validate__` checks and fee enforcement [1](#0-0) . This is directly analogous to an unprotected/unauthenticated `initialize()`: any transaction sender who knows (or can compute offline) the deterministic class hash the operator intends to declare during genesis can submit their own zero-fee, unsigned `Declare` transaction from the same `BOOTSTRAP` address for that same class hash first, permanently occupying that class-hash slot before the legitimate declare is processed.

### Finding Description
`DeclareTransaction::bootstrap_address()` returns a fixed, publicly known constant address (`0x424f4f545354524150`, i.e. `'BOOTSTRAP'`) [2](#0-1) . `is_bootstrap_declare` only checks that the sender is this constant address, nonce is `0`, and fee is not charged — it performs no signature or account-ownership check [3](#0-2) .

In `AccountTransaction::execute_raw`, when a `Declare` transaction satisfies `is_bootstrap_declare`, the blockifier explicitly skips `perform_pre_validation_stage` and the account's `__validate_declare__` entry point entirely, and just executes the declaration [4](#0-3) . The same bypass is mirrored in the Starknet OS Cairo implementation: `execute_declare_transaction` special-cases `sender_address == 'BOOTSTRAP' and tx_info.nonce == 0 and tx_info.version == 3` with `max_possible_fee == 0`, and directly writes the class hash mapping with `dict_update(... prev_value=0, new_value=compiled_class_hash)`, then `%{ SkipTx %}` [5](#0-4) . The only integrity check is `prev_value=0`, i.e., that this exact `class_hash` has not already been declared — there is no check on who is allowed to be the bootstrap sender or on which `compiled_class_hash` is bound to it.

Because `class_hash` is a deterministic hash of a Sierra/Cairo program, it is publicly computable in advance for any known, standard contract (e.g., the account or ERC20 contract the chain operator intends to bootstrap with). This lets an unprivileged party front-run the legitimate bootstrap declare of that exact `class_hash` with an attacker-chosen (and possibly incorrect/malicious) `compiled_class_hash`, using the same public `BOOTSTRAP` sender address, zero nonce, and zero fee — all of which require no signature and no special privilege, exactly mirroring the reported "front-runnable `initialize()`" pattern where a race to call a privileged setup function first lets an attacker seize control of critical protocol parameters.

The gate that is supposed to prevent this outside of an actual genesis window is a gateway/mempool config flag (`validate_resource_bounds` / `authorized_declarer_accounts`) that rejects zero-resource-bound transactions unless explicitly disabled for bootstrap [6](#0-5) . During the window in which this flag is (necessarily) disabled to allow the real genesis declares to go through, the check is symmetric for every sender — there's no additional restriction (e.g., only the batcher/node operator, or a specific L1-provided key) tying the `BOOTSTRAP` declare privilege to the actual chain operator.

### Impact Explanation
If an attacker's transaction with the target `class_hash` is admitted/ordered ahead of the legitimate operator's bootstrap declare (e.g., by submitting during the narrow genesis window with equal or better priority), the `prev_value=0` check in the OS will succeed for the attacker's transaction and permanently occupy that class hash with an attacker-chosen `compiled_class_hash`. The legitimate bootstrap declare for the intended account/ERC20 contract will then fail (`prev_value != 0`), permanently preventing the chain from ever correctly declaring that specific class via bootstrap. Depending on which contract is targeted (e.g., the fee-token ERC20 or the default account class used to fund/deploy subsequent bootstrap transactions), this can permanently break genesis initialization of the network, i.e., a network unable to properly commence/confirm transactions as intended, satisfying the "permanent freezing" / "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
Exploitation requires: (1) the target chain to be in its bootstrap/genesis window with `validate_resource_bounds` disabled (an operational precondition, not attacker-controlled, but a real and expected operational phase for every new deployment), and (2) the attacker to know or predict the exact `class_hash` about to be bootstrap-declared (feasible since standard/well-known account and token contracts are used and their class hashes are deterministic and public before declaration). Given both, the exploit itself requires no special key, no signature, and no fee — just crafting a well-formed `Declare` transaction with `sender_address = 'BOOTSTRAP'`, matching the same public-knowledge race pattern as the referenced report.

### Recommendation
- Restrict the `BOOTSTRAP` declare path so it can only be exercised in a way that is provably tied to the chain operator (e.g., gate it by a one-time flag that is cleared once any block exists, or require it to originate from an explicit allow-list / dedicated L1-provided authorization rather than by pure knowledge of the constant sender address), rather than by a config flag that is symmetric for all callers.
- Consider binding the accepted `compiled_class_hash` for bootstrap declares to a pre-committed, operator-signed manifest of expected class hashes, so that even if raced, an attacker cannot bind an arbitrary `compiled_class_hash` to a target `class_hash`.
- Alternatively, ensure `validate_resource_bounds`/bootstrap-mode is enabled for the minimum possible time and that the batcher local-orders (rather than mempool-orders) the operator's own bootstrap declares first, closing the race window.

### Proof of Concept
1. Chain operator starts a new deployment with `gateway_config`/`mempool` configured with `validate_resource_bounds = false` (bootstrap mode), intending to declare a well-known account contract class `C` via a bootstrap `Declare` (as in `generate_bootstrap_declare`) [7](#0-6) .
2. An attacker computes `class_hash(C)` offline (deterministic from the public Sierra program) and crafts their own `Declare` V3 transaction with `sender_address = DeclareTransaction::bootstrap_address()`, `nonce = 0`, zero resource bounds, `class_hash = class_hash(C)`, and an attacker-chosen `compiled_class_hash`.
3. The attacker submits this transaction to the gateway/mempool before the operator's legitimate bootstrap declare for `C` is processed.
4. Per `is_bootstrap_declare`/`execute_raw`, no signature or `__validate_declare__` check runs [8](#0-7) ; the OS `dict_update` with `prev_value=0` succeeds for the attacker's transaction and writes the attacker's `compiled_class_hash` for `class_hash(C)` [9](#0-8) .
5. The operator's subsequent legitimate bootstrap declare for `C` now fails the `prev_value=0` assertion permanently, since `class_hash(C)` is already declared with the wrong `compiled_class_hash`, breaking genesis bootstrapping of the intended contract.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }

        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
