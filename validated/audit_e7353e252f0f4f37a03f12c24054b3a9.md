### Title
Bond-path stake mutations skip `settle-rewards`/`settle-staker-rewards`, permanently freezing rewards for the mutated shares - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`add-staker-to-bond-for-cycle` and `remove-staker-from-bond-for-cycle` in `pox-5.clar` mutate `signer-shares-staked-for-cycle`, `total-shares-staked-for-cycle`, and `staker-shares-staked-for-cycle` for the bond-staking path without first calling `settle-rewards` / `settle-staker-rewards`, unlike the parallel STX-only path (`add-staker-to-signer-for-cycle`) which explicitly settles both signer- and staker-level reward snapshots before touching the same maps.

### Finding Description
`settle-rewards` computes `earned` from `shares * (rpt - rpt_paid)` and then snapshots `rpt_paid = rpt` into `signer-rewards-per-token-settled-for-cycle` (or the per-staker equivalent for `settle-staker-rewards`), and the comment above it states this "MUST be called before any update to `signer-shares-staked-for-cycle`, because changes to that state will effect rewards calculations" [1](#0-0) .

The STX-only staking mutator, `add-staker-to-signer-for-cycle`, honors this invariant: it calls `settle-rewards` and (conditionally) `settle-staker-rewards` before mutating `signer-shares-staked-for-cycle`/`total-shares-staked-for-cycle`/`staker-shares-staked-for-cycle` [2](#0-1) .

The bond-staking mutator `add-staker-to-bond-for-cycle`, however, mutates the identical maps (`total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`, `staker-shares-staked-for-cycle`) with no `settle-rewards`/`settle-staker-rewards` call at all: it directly adds `amount-sats` to signer/total shares and *overwrites* `staker-shares-staked-for-cycle` to the raw `amount-sats` value, then stamps `staker-rewards-per-token-settled-for-cycle` to the *current* `rewards-per-token-for-cycle` without crediting any reward differential first [3](#0-2) .

The companion `remove-staker-from-bond-for-cycle` has the same gap: it decrements `total-shares-staked-for-cycle`/`signer-shares-staked-for-cycle` and zeroes `staker-shares-staked-for-cycle` for that signer/staker/bond/cycle with no settle call beforehand [4](#0-3) .

Because `settle-rewards`/`settle-staker-rewards` are the only place that read `signer-rewards-per-token-for-cycle`/`rewards-per-token-for-cycle` against the *old* shares and roll the delta into `signer-unclaimed-rewards-for-cycle` / `staker-unclaimed-rewards-for-cycle`, skipping them before a shares mutation means: (1) any reward differential that accrued on the old share amount for that reward-cycle since the last settlement is never captured into the unclaimed-rewards accumulator, and (2) the settled-`rpt` snapshot is fast-forwarded to the current value regardless. This makes the un-credited delta permanently unrecoverable for that (signer, staker, bond-index, cycle) — future `settle-*` calls compute `earned` starting from the new `rpt_paid`, so the gap between the old and new snapshot values is dropped rather than accrued to anyone.

### Impact Explanation
This directly parallels the reported StaticATokenLM bug class: a balance-affecting operation that mutates a rewards-bearing quantity without first checkpointing the global/per-user reward-per-token snapshot, causing the affected party's already-accrued (but not yet settled) reward to be silently lost. In this repo's context that is a reward mis-payment/permanent loss of sBTC bond rewards bounded to whatever reward inflow occurred between the last settlement and the mutating call — matching the "High: minority-triggerable reward mis-payment bounded to fees" tier, since any single staker/signer can trigger this merely by calling `register-for-bond`/`unstake-sbtc`/`update-bond-registration` (the public entry points that fold over `add-staker-to-bond-cycles`/`remove-staker-from-bond-cycles`) themselves — no majority or privileged party is required.

### Likelihood Explanation
Any bond participant can trigger the affected code paths unilaterally: registering for a bond mid-cycle after the bond has already been receiving reward distributions, or updating/removing a bond registration, both route through `add-staker-to-bond-for-cycle`/`remove-staker-from-bond-for-cycle`. The bug only manifests when there is a reward delta pending between the last settlement (`rewards-per-token-for-cycle` update) and shares are subsequently mutated by one of these paths for a given (signer, staker, bond-index, cycle) tuple — a condition trivially reachable in normal operation whenever `calculate-rewards` has run and then a registration/unregistration/rollover follows within the same cycle window.

### Recommendation
Add `settle-rewards` and `settle-staker-rewards` calls at the top of `add-staker-to-bond-for-cycle` and `remove-staker-from-bond-for-cycle`, mirroring `add-staker-to-signer-for-cycle`'s pattern, before any mutation of `signer-shares-staked-for-cycle`, `total-shares-staked-for-cycle`, or `staker-shares-staked-for-cycle` for the corresponding `bond-index`/cycle. Also change the absolute `map-set staker-shares-staked-for-cycle ... amount-sats` in `add-staker-to-bond-for-cycle` to an additive update (`+ current amount-sats`) consistent with the signer/total accounting, unless it is proven that this map is always empty at call time for every caller.

### Proof of Concept
1. Bond `bond-index=0` exists with signer `S` and staker `A` having `staker-shares-staked-for-cycle{cycle=c, bond-index=0, signer=S, staker=A} = X`, and rewards have accrued such that `signer-rewards-per-token-for-cycle{S,c,0}` has advanced past `staker-rewards-per-token-settled-for-cycle{...,staker=A}`.
2. Staker `A` (or the flow that re-invokes `add-staker-to-bond-for-cycle` for the same tuple, e.g. via `update-bond-registration`/rollover) calls into `add-staker-to-bond-for-cycle` again for the same `(reward-cycle, bond-index, signer, staker)`.
3. The function overwrites `staker-shares-staked-for-cycle` to the new `amount-sats` and stamps `staker-rewards-per-token-settled-for-cycle` to the *current* `rewards-per-token-for-cycle`, without ever computing `earned = X * (rpt_current - rpt_settled)` and crediting it to `staker-unclaimed-rewards-for-cycle`.
4. The reward delta accrued on the pre-existing `X` shares between the last settlement and this call is lost — no subsequent `settle-staker-rewards` call can recover it, since the settled snapshot has already advanced past that delta.
