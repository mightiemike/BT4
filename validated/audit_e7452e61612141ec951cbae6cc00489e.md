### Title
Integer-division truncation in `CalculateGasCost` zeroes out UEA execution gas fees, giving free-of-charge `MsgExecutePayload` EVM execution - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`x/uexecutor/keeper/fees.go:CalculateGasCost` converts the fee-market `baseFee` (an 18-decimal-precision `sdkmath.LegacyDec`) into an integer "whole `upc`" amount by doing `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` [1](#0-0) . Because Go's `big.Int.Div` truncates, any base fee smaller than one full `upc` unit (`1e18`) — which is the normal, expected range for an EIP-1559 base fee (typically expressed in gwei-scale units, i.e. `1e9`–`1e12`) — collapses to `0`. `effectiveGasPrice` is then `0`, so `gasCost = effectiveGasPrice * gasUsed = 0` for every `MsgExecutePayload` execution, and `DeductGasFeesFromReceipt` short-circuits with `if gasCost.Sign() <= 0 { return nil }`, skipping fee collection entirely [2](#0-1) .

### Finding Description
This is the same bug class as the external M-11 report: a fee/premium computation that can legitimately settle to zero under normal (not just adversarial) input, letting a caller consume protocol-mediated execution resources at no cost.

`MsgExecutePayload` is a gasless Cosmos message (no ante-level fee is charged — see the gasless whitelist) [3](#0-2) ; the *only* fee actually meant to be paid for this flow is the EVM gas fee computed and deducted from the UEA's `upc` balance inside `DeductGasFeesFromReceipt`/`ExecutePayloadV2` [4](#0-3) , and documented explicitly as such in the module README ("The actual EVM execution gas is deducted from this UEA's balance (`DeductGasFeesFromReceipt`)") [5](#0-4) .

The unit-conversion comment in the code claims "the base fee is always a whole number of upc — no fractional upc exists" [6](#0-5) , but this assumption is false for a chain whose gas price is denominated the way EVM chains normally are (small integer gwei-scale units far below `1e18`). Any `baseFee` value under `1e18` — i.e., essentially all realistic base fees — is floored to `0` by the integer division, making `effectiveGasPrice` (and therefore `gasCost`) permanently `0` regardless of how much gas (`receipt.GasUsed`) the payload actually consumed.

### Impact Explanation
- Any unprivileged user can submit `MsgExecutePayload` (gasless at the Cosmos tx layer) and have the corresponding UEA execute arbitrary EVM calls through `CallUEAExecutePayload`/`DerivedEVMCall` while never being billed real gas fees, because the intended gas-fee accounting always computes to `0`.
- This directly corrupts "gas fee accounting" in the allowed-impact list: the protocol's only intended charge for UEA-routed EVM execution is defeated by a rounding bug, not by a privileged actor.
- Because `DeductAndBurnFees` is never invoked (gas cost `<= 0` short-circuits before it), there is no balance check either — a UEA with zero `upc` balance can still execute payloads that consume real EVM gas resources (mirrors the "malicious occupation" / "no-cost loan" pattern in the source report), enabling spam/DoS-style resource consumption of the module-account-nonce-gated `DerivedEVMCall` execution path without payment, and generally breaking protocol economics around UEA execution.
- This does not directly mint/burn/drain user funds, but it is a concrete, reachable break of an explicit fund-accounting invariant (gas fee accounting) via an ordinary unprivileged flow — in scope per "corruption of ... gas fee accounting."

### Likelihood Explanation
High. This is not an edge case requiring an attacker to manipulate anything: real-world EIP-1559 `baseFee` values are virtually always far below `1e18` in the fee-market's native unit (fee markets typically operate at gwei-like granularity), so the truncation to `0` will occur under essentially all normal operating conditions, not just contrived ones. No malicious validator, relayer, or privileged actor is required — any ordinary user submitting `MsgExecutePayload` triggers the flawed calculation.

### Recommendation
Do not floor-divide the fee-market `baseFee` by `1e18` before multiplying by `gasUsed`. Instead, keep the multiplication in the higher-precision domain and divide only once, at the end, e.g. compute `gasCost = (baseFeeWei * gasUsed) / 1e18` using the full-precision `baseFee.BigInt()` value directly against `gasUsed`, or perform the entire calculation in `sdkmath.LegacyDec` and round the final `upc` charge (with rounding up, not down, to avoid recreating the same zero-floor problem for sub-unit amounts). Add a unit test asserting that a realistic gwei-scale base fee (e.g. `1e9`) combined with non-trivial `gasUsed` produces a non-zero, correctly scaled fee.

### Proof of Concept
Given the code path:
```go
baseFeeBig := baseFee.BigInt()                       // e.g. baseFee = 1_000_000_000 (1 gwei-equivalent) as LegacyDec-scaled = 1e9 * 1e18 internal? 
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))          // any realistic gwei-scale value / 1e18 == 0
effectiveGasPrice := baseFeeBig                       // == 0
gasCost := effectiveGasPrice * gasUsed                // == 0 regardless of gasUsed
``` [7](#0-6) 

Then in `DeductGasFeesFromReceipt`:
```go
gasCost, _ := k.CalculateGasCost(baseFee, ...)
if gasCost.Sign() <= 0 {
    return nil   // no fee deducted, no balance check performed
}
``` [2](#0-1) 

An attacker can:
1. Deploy/own a UEA (any user account) with `0` `upc` balance.
2. Submit `MsgExecutePayload` with a payload whose `maxFeePerGas` ≥ the (near-zero-relative-to-1e18) current base fee, and whose EVM call consumes non-trivial gas.
3. Observe: `CallUEAExecutePayload` executes fully, `receipt.GasUsed > 0`, yet `DeductGasFeesFromReceipt` returns `nil` (no fee charged) because `gasCost` computed to `0` — the caller obtained real EVM execution at zero cost, repeatable indefinitely.

I was unable to directly inspect the genesis/feemarket parameter files to confirm the exact numeric scale used for `base_fee` on Push Chain's live configuration (searches for `base_fee`/`min-gas-price` JSON config values did not return file contents in the index), so the precise magnitude of the base fee in production is inferred from standard EIP-1559/cosmos-evm conventions rather than confirmed from a specific config file in this repo. A Devin session with full repository access could verify the exact genesis `base_fee` value to confirm real-world triggering conditions.

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}
