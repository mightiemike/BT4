This is directly analogous to the Sweepable.sol bug class: an ordinary, unprivileged `DeleteAccount` transaction with a typo'd/nonexistent `beneficiary_id` causes the entire account balance to be irrecoverably destroyed, with no way to move it out — a stronger outcome than "locked," since here funds are provably burned forever.

### Title
Deleting an account with a nonexistent `beneficiary_id` permanently burns the account's entire balance instead of refunding it - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` unconditionally emits a `Receipt::new_balance_refund` to whatever `beneficiary_id` the caller specified in the `DeleteAccount` action, without checking that the beneficiary account exists. If it does not exist, the refund receipt fails and its entire deposit (the deleted account's whole balance) is burned rather than returned to anyone.

### Finding Description
`action_delete_account` pays out the deleted account's remaining balance via a system-generated deposit-refund receipt addressed to `delete_account.beneficiary_id`, with no existence check on that ID: [1](#0-0) 

Deposit-refund receipts are special "refund" receipts (`predecessor_id == "system"`). By protocol design, refund receipts can never implicitly create an account, even for account types that would normally allow implicit creation via a bare transfer: [2](#0-1) 

So if `beneficiary_id` names an account that does not currently exist (e.g. a typo, an account that was never created, or one that was deleted earlier in the same chunk), `check_account_existence` rejects the `Transfer` action inside the refund receipt with `AccountDoesNotExist`. When a system-predecessor (refund) receipt fails, the runtime does not reroute or preserve the deposit — it burns it: [3](#0-2) 

This is confirmed by the project's own regression test, whose comment states the beneficiary must exist "otherwise the balance transfer the delete sends it would come straight back as a refund" — which is inaccurate: it doesn't come back, it is burned, and a dedicated test elsewhere shows a refund to a nonexistent account fails and never creates the account: [4](#0-3) [5](#0-4) 

The general refund semantics documenting this burn-on-failure behavior for refunds are described in the docs as well: [6](#0-5) 

### Impact Explanation
This is directly reachable by any unprivileged account owner signing an ordinary `DeleteAccount` transaction (`integration-tests/src/user/mod.rs` exposes `delete_account_with_beneficiary_set` as a normal user action) [7](#0-6) . Specifying a `beneficiary_id` that does not exist — whether by mistake, a stale reference to a since-deleted account, or a race where the beneficiary account is deleted in the same or an earlier receipt of the same chunk — causes the deleting account's *entire* balance to be permanently and irrecoverably destroyed (burned), not merely stuck. Unlike ordinary transfers (`Transfer` action), which fail atomically and roll back if the receiver doesn't exist, `DeleteAccount` has already deleted the source account by the time the refund receipt executes, so there is no way to recover the funds, no owner to retry, and no mechanism to redirect them. This is a permanent, protocol-level loss of user funds triggered by a single crafted or mistaken transaction — no attacker action against another party is even required; a user can destroy their own funds through an easily-triggered input-validation gap, and equally, careless account-deletion tooling/wallets that don't pre-validate the beneficiary could destroy user funds unexpectedly.

### Likelihood Explanation
High likelihood: `beneficiary_id` is a free-form, unvalidated `AccountId` field supplied directly in a `DeleteAccountAction` by the transaction signer; the only requirement checked ahead of time is that it parses as a syntactically valid account ID (`InvalidAccountId`) — no existence check occurs before execution. Any typo, use of a not-yet-created account, or deletion ordering issue silently destroys the full balance instead of erroring out safely up front or refunding to a safe fallback (e.g., the deleting account's own predecessor/signer).

### Recommendation
Before deleting the account, verify that `beneficiary_id` exists (or is capable of receiving the refund), and fail the `DeleteAccount` action with a clear validation error (analogous to `AccountDoesNotExist`) if it does not, so the account and its balance are preserved instead of destroyed. Alternatively, route the refund through a mechanism that is not restricted by `implicit_creation_allowed`'s "refunds never create accounts" rule for this specific payout, or fall back to refunding the deleting account's own predecessor/signer if the specified beneficiary cannot receive funds.

### Proof of Concept
1. Create account `victim.near` with a nonzero balance and a full-access key.
2. Sign and submit a `DeleteAccount { beneficiary_id: "typo-does-not-exist.near" }` transaction from `victim.near` (as in `delete_account_with_beneficiary_set`) [7](#0-6) .
3. `action_delete_account` runs, deletes `victim.near`, and queues `Receipt::new_balance_refund("typo-does-not-exist.near", victim_balance)` [1](#0-0) .
4. When that refund receipt is processed, `check_account_existence` rejects the `Transfer` action because refunds cannot implicitly create accounts and `typo-does-not-exist.near` doesn't exist [2](#0-1) .
5. Since the failing receipt's predecessor is `system`, the runtime adds the full deposit to `other_burnt_amount` instead of refunding it anywhere [3](#0-2) .
6. Result: `victim.near` no longer exists, `typo-does-not-exist.near` was never created, and the entire balance is permanently gone from circulation — confirmed by the pattern in the existing `refund_may_not_create_universal_account` test, which shows a refund to a missing account fails and the account is never created (i.e., the funds go nowhere) [8](#0-7) .

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
