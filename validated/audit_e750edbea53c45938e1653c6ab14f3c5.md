### Title
`block_direct_execute_call` protection is not enforced for `library_call`/`library_call_l1_handler` syscalls, allowing bypass of the direct-`__execute__`-call guard - (File: crates/blockifier/src/execution/syscalls/hint_processor.rs)

### Summary
The blockifier enforces a security guard, `block_direct_execute_call`, that is supposed to prevent any contract from invoking another contract's `__execute__` entry point through a syscall (mirroring the Starknet OS's own hard-coded rejection of `__execute__` via `CallContract`). This guard is checked only in the `call_contract` syscall implementation, via `maybe_block_direct_execute_call`, but is never checked in the `library_call` / `library_call_l1_handler` syscall implementations (VM, Native, and deprecated variants). This is structurally the same class of bug as GHSA-v3xv-8vc3-h2m6: the validating function (`resolve_name`/`validate_plugin_code` in PySpector, `maybe_block_direct_execute_call` here) is called on one code path (`ast.Name`/`ast.Attribute` resolution, `call_contract`) but is silently skipped on an alternate, functionally-equivalent path (`ast.Call`/indirect `getattr`, `library_call`).

### Finding Description
`maybe_block_direct_execute_call` is defined in `SyscallHandlerBase` and rejects a call whose selector equals `EXECUTE_ENTRY_POINT_NAME` when the `block_direct_execute_call` versioned constant is set: [1](#0-0) 

This check is invoked from the VM `call_contract` syscall handler: [2](#0-1) 

and from the Native `call_contract` syscall handler: [3](#0-2) 

and, in an equivalent inline form, from the deprecated (Cairo 0) `call_contract` handler: [4](#0-3) 

However, the `library_call` handler for the VM builds an identical `CallEntryPoint` (same `entry_point_selector`, just with `call_type: CallType::Delegate` instead of `CallType::Call`), and never calls `maybe_block_direct_execute_call` or performs any equivalent selector check: [5](#0-4) 

The same omission exists in the Native `library_call` handler: [6](#0-5) 

and in the deprecated `library_call`/`library_call_l1_handler` handlers, which route to `execute_library_call`, a helper with no `__execute__`-selector rejection at all: [7](#0-6) [8](#0-7) 

This is corroborated by the Starknet OS Cairo implementation of these syscalls: `execute_contract_call` (backing `CallContract`) explicitly checks `request.selector == EXECUTE_ENTRY_POINT_SELECTOR` and fails the syscall, while `execute_library_call` (backing `LibraryCall`), a few lines below in the same file, performs no such check: [9](#0-8) [10](#0-9) 

The deprecated (Cairo0) OS syscall dispatcher likewise only asserts `selector != EXECUTE_ENTRY_POINT_SELECTOR` for `CALL_CONTRACT_SELECTOR`, and does not repeat this assertion for `LIBRARY_CALL_SELECTOR`: [11](#0-10) 

Because blockifier execution and the Starknet OS re-execution must agree, and both independently omit the guard on `library_call`, any contract can invoke `library_call_syscall(class_hash=<victim class hash>, function_selector=selector!("__execute__"), calldata=<attacker-controlled>)` and have the victim's `__execute__` code executed — under `CallType::Delegate` semantics — while `block_direct_execute_call` intended to make this globally unreachable.

### Impact Explanation
`block_direct_execute_call` exists specifically to prevent contracts from invoking `__execute__` on behalf of another class outside of the OS's own validate→execute transaction flow (which normally enforces nonce increments, `__validate__` success, and fee charging before `__execute__` runs). Being able to trigger a victim class's `__execute__` logic via `library_call` — bypassing this guard — lets an attacker-controlled contract run the victim account's business logic in the *caller's* storage/authorization context (delegate-call semantics) whenever calldata parsing in `__execute__` does not itself re-validate the caller. For accounts (and any other contract) whose `__execute__` assumes it is only reachable post-validation via the standard transaction flow (as the `block_direct_execute_call` feature assumes system-wide), this can lead to unauthorized state transitions and honest-node/consensus impact if OS re-execution and blockifier execution diverge in whether this path is actually blocked versus not, and more directly, enables execution of privileged account logic (`__execute__`) without going through `__validate__`/nonce/fee enforcement, undermining an explicit protocol-level invariant that `block_direct_execute_call` is meant to guarantee for every `CallEntryPoint` reaching `__execute__` through a syscall. This is a High-severity bypass of an intended security control reachable by any unprivileged contract deployer/transaction sender via ordinary `invoke` transactions.

### Likelihood Explanation
Trivial to trigger: any contract already has access to `library_call_syscall`, which is on the standard allowed-libfuncs list (`library_call_syscall` appears in `allowed_libfuncs.json`), requires no special permissions, and only needs the victim's `class_hash` (public information) and the well-known `__execute__` selector. No race conditions, special execution mode, or privileged role is required — a single `invoke` transaction from any account can exercise this path in both Execute and Validate-adjacent contexts (subject to the separate, unrelated Validate-mode restrictions on `library_call`, which do not check for `__execute__` either).

### Recommendation
Apply the same `maybe_block_direct_execute_call(selector)` check (or an OS-side `assert_not_equal(selector, EXECUTE_ENTRY_POINT_SELECTOR)`) uniformly to every syscall path that can dispatch a `CallEntryPoint` to arbitrary code with an attacker-chosen `entry_point_selector`: `library_call`, `library_call_l1_handler`, `delegate_call`, and `delegate_l1_handler`, in all three execution engines (VM `hint_processor.rs`, Native `syscall_handler.rs`, deprecated `hint_processor.rs`), and correspondingly in the Cairo OS implementations (`syscall_impls.cairo`'s `execute_library_call`, and `deprecated_execute_syscalls.cairo`'s `LIBRARY_CALL_SELECTOR`/`DELEGATE_CALL_SELECTOR`/`DELEGATE_L1_HANDLER_SELECTOR` branches) so that blockifier and OS re-execution remain consistent and no syscall bypasses the `__execute__` restriction.

### Proof of Concept
1. Note that `EXECUTE_ENTRY_POINT_SELECTOR`/`EXECUTE_ENTRY_POINT_NAME` protection is enforced only inside `call_contract`'s handler via `maybe_block_direct_execute_call` (`crates/blockifier/src/execution/syscalls/hint_processor.rs:539`) and confirm `library_call`'s handler (`hint_processor.rs:631-649`) builds the same `CallEntryPoint` shape without ever calling `maybe_block_direct_execute_call`.
2. Deploy any victim contract (e.g., an account contract) with a `class_hash` `C`, and an "attacker" contract exposing a thin wrapper that calls `starknet::library_call_syscall(class_hash: C, function_selector: selector!("__execute__"), calldata: <attacker_calldata>)`.
3. With `versioned_constants.block_direct_execute_call = true`, call `call_contract_syscall(attacker, "__execute__", ...)` directly — this fails with `Invalid argument` per `test_direct_execute_call` in `crates/blockifier/src/execution/syscalls/syscall_tests/call_contract.rs:297-344`.
4. Instead invoke the attacker contract's wrapper that issues the equivalent call via `library_call_syscall` with the same `class_hash`/selector — this succeeds and runs the victim class's `__execute__` code, because no equivalent check exists on the `library_call` path, demonstrating the bypass of the `block_direct_execute_call` protection.

pub fn execute_library_call(
    syscall_handler: &mut DeprecatedSyscallHintProcessor<'_>,
    vm: &mut VirtualMachine,
    class_hash: ClassHash,
    code_address: Option<ContractAddress>,
    call_to_external: bool,
    entry_point_selector: EntryPointSelector,
    calldata: Calldata,
) -> DeprecatedSyscallResult<ReadOnlySegment> {
    let entry_point_type =
        if call_to_external { EntryPointType::External } else { EntryPointType::L1Handler };
    let entry_point = CallEntryPoint {
        class_hash: Some(class_hash),
        code_address,
        entry_point_type,
        entry_point_selector,
        calldata,
        // The call context remains the same in a library call.
        storage_address: syscall_handler.storage_address,
        caller_address: syscall_handler.caller_address,
        call_type: CallType::Delegate,
        initial_gas: syscall_handler.context.gas_costs().base.default_initial_gas_cost,
    };

    execute_inner_call(entry_point, vm, syscall_handler).map_err(|error| {
        error.as_lib_call_execution_error(
            class_hash,
            syscall_handler.storage_address,
            entry_point_selector,
        )
    })
}
