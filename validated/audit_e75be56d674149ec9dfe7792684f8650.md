### Title
Integer-overflow bypass of `exchangeBalanceLimit` safety check in `ExchangeTransactionActuator.doValidate()` when `allowHardenExchangeCalculation()==false` - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`ExchangeTransactionActuator.doValidate()` computes `tokenBalance = addExact(tokenBalance, tokenQuant)` and rejects the transaction only if this exceeds `dynamicStore.getExchangeBalanceLimit()`. The `addExact` used here is not `Math.addExact`, but `AbstractExchangeActuator.addExact`, which silently falls back to plain `x + y` (wraparound, no exception) whenever `allowHarden()` (i.e. `allowHardenExchangeCalculation()`) is `false`. An attacker who can supply a `tokenQuant` near `Long.MAX_VALUE - tokenBalance` can wrap the sum to a small/negative value and defeat the balance-limit guard, while the real trade math in `ExchangeProcessor`/`ExchangeCapsule.transaction()` is computed independently with `double`-based bancor formulas and is not protected by this guard at all.

### Finding Description
- `ExchangeTransactionActuator.doValidate()` reads the exchange's current pool balance for the traded token (`firstTokenBalance`/`secondTokenBalance`, bounded at exchange-creation time to `exchangeBalanceLimit` by `ExchangeCreateActuator.doValidate()`), and adds the attacker-supplied `tokenQuant`: [1](#0-0) 
- `addExact` is not the standard overflow-checked `Math.addExact`; it is the actuator's own helper which only does overflow-checked math when the chain parameter `allowHardenExchangeCalculation` is enabled: [2](#0-1) 
- When `allowHarden()==false`, `tokenBalance + tokenQuant` is plain 64-bit two's-complement addition, so a sufficiently large `tokenQuant` (close to `Long.MAX_VALUE - tokenBalance`) wraps the result to a small or negative value, which trivially passes `tokenBalance > balanceLimit`.
- The only remaining gate on `tokenQuant` is `accountCapsule.assetBalanceEnoughV2(tokenID, tokenQuant, dynamicStore)` (or the TRX-balance check), i.e. the attacker must actually hold that quantity of the asset: [3](#0-2) 
- This is satisfiable by an unprivileged account: `AssetIssueActuator.validate()` only requires `getTotalSupply() > 0` — there is no upper bound on total supply — so an attacker can self-issue a TRC10 token with `totalSupply` close to `Long.MAX_VALUE` and hold the (nearly) entire freshly-issued balance themselves: [4](#0-3) [5](#0-4) 
- Having bypassed the `balanceLimit` guard, `execute()` calls the real trade computation, `exchangeCapsule.transaction(...)`, which for `first`/`second` tokens ultimately calls `ExchangeProcessor.exchange()` — this is computed with `double` arithmetic on the raw (non-overflowing at these magnitudes) `long` balance/quant values, entirely independent from the wrapped `tokenBalance` used only in `doValidate()`'s discarded guard: [6](#0-5) [7](#0-6) 
- Because the AMM formula uses an extreme sell/buy ratio (attacker's `tokenQuant` vastly larger than the pool's real reserve), the bancor-style formula (`exchangeToSupply`/`exchangeFromSupply`) produces an `anotherTokenQuant` that is a function of the counterpart pool's real balance and can approach or exceed a very large fraction of it — a result the `balanceLimit` check exists specifically to prevent by capping how large a single trade against the pool can be. Skipping that check via the overflow lets an oversized trade reach the (unrelated, double-math) AMM engine which was never validated against such an extreme input ratio.

### Impact Explanation
This maps to asset/accounting corruption and unauthorized extraction of pooled exchange assets: an attacker can craft a single `ExchangeTransactionContract` that the `balanceLimit` safety check should reject, causing the actuator to run the AMM trade formula on an out-of-range input ratio and pull a disproportionate amount of the counterpart token out of the exchange's reserve pool, at the expense of other liquidity participants in that exchange pair.

### Likelihood Explanation
Preconditions match an unprivileged, low-cost attack path: (1) `allowHardenExchangeCalculation()==false` (a real, historically-default chain parameter state before the hardening fork activated it — see `DynamicPropertiesStore`/`ForkController` gating referenced by `allowHarden()`), (2) attacker self-issues a TRC10 asset with near-`Long.MAX_VALUE` total supply (only costs the `AssetIssueFee`, no upper-bound validation blocks it), (3) attacker creates or targets an exchange pair using that token, (4) attacker submits one `ExchangeTransactionContract` with `tokenQuant` chosen so `tokenBalance + tokenQuant` wraps below `balanceLimit`. All steps are reachable by a normal funded account broadcasting signed transactions; no privileged role or non-default node config is required. The main constraint reducing exploitability is that `allowHardenExchangeCalculation` must be off for the target chain — if it is already enabled, `addExact` uses `Math.addExact`/`StrictMathWrapper` and throws `ArithmeticException`, which `validate()`/`execute()` explicitly catch and convert to a rejected/failed transaction, closing this path.

### Recommendation
Make `AbstractExchangeActuator.addExact`/`subtractExact` always use the overflow-checked variants (`Math.addExact`/`StrictMathWrapper`) regardless of `allowHarden()`, or at minimum apply overflow-checked arithmetic specifically to the `exchangeBalanceLimit` comparison in `ExchangeTransactionActuator.doValidate()` (and the analogous checks in `ExchangeCreateActuator`/`ExchangeInjectActuator`) so the safety guard cannot be defeated by integer wraparound irrespective of the hardening flag's on-chain state.

### Proof of Concept
```java
// JUnit-style illustration of the overflow bypass in isolation
long tokenBalance = 900_000_000_000_000L; // bounded by exchangeBalanceLimit at creation
long tokenQuant = Long.MAX_VALUE - tokenBalance + 5; // crafted near Long.MAX_VALUE - tokenBalance
boolean allowHarden = false;

long result = allowHarden
    ? StrictMathWrapper.addExact(tokenBalance, tokenQuant) // would throw ArithmeticException
    : tokenBalance + tokenQuant; // wraps to Long.MIN_VALUE + 4 (negative)

// Assert the exploit condition:
assertTrue(result < 0); // wrapped value
long balanceLimit = 1_000_000_000_000_000L;
assertTrue(result <= balanceLimit); // guard in doValidate() is bypassed
```
Full end-to-end reproduction requires: broadcasting an `AssetIssueContract` with `total_supply` ≈ `Long.MAX_VALUE`, an `ExchangeCreateContract` establishing the pool (bounded to `exchangeBalanceLimit`), then an `ExchangeTransactionContract` with `quant` ≈ `Long.MAX_VALUE - tokenBalance`, on a chain state where `allowHardenExchangeCalculation()` returns `false`, and asserting that `validate()` does not throw `ContractValidateException("token balance must less than ...")` and that `execute()` credits an `anotherTokenQuant` disproportionate to the legitimate pool reserve.

**Uncertainty noted:** I was unable to inspect `ExchangeCapsule.transaction()`/`ExchangeCapsule.setBalance()` internals (not retrieved in this session) to precisely quantify how much of the counterpart reserve can be drained by the resulting extreme-ratio AMM call, or whether that method applies its own independent bounds. This should be verified directly in the code (or with a live Devin session) before finalizing severity/exploitability numbers.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
