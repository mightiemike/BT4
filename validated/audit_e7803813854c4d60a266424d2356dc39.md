### Title
Witness cycle rewards become permanently stuck when a witness's registered vote count for that cycle is zero - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
Analogous to the `Staking.sol` bug where WETH rewards are silently orphaned whenever `totalSupply == 0`, java-tron's DPoS reward-index mechanism has the same structural flaw: TRX block/transaction-fee rewards are added to a per-cycle reward pot (`delegationStore.addReward`) that is only ever converted into the distributable reward index (`Vi`) if the witness's recorded vote count for that cycle is non-zero. If a witness produces blocks and accrues reward for a cycle while its vote count for that same cycle is `0`, the reward for that cycle is silently dropped and can never be claimed by anyone, nor refunded to the witness.

### Finding Description
Block and transaction-fee rewards are credited via `MortgageService.payReward`, which splits the value into an immediate brokerage payout and a remainder that is booked into the cycle's reward pot: [1](#0-0) 

That remainder is only usable if it gets converted into the accumulated value index (`Vi`) for that cycle. The conversion, driven from `MaintenanceManager.doMaintenance()`, calls `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` using the vote count that was in effect for the cycle **before** applying that epoch's vote changes: [2](#0-1) 

Inside `accumulateWitnessVi`, if `voteCount == 0`, the accrued reward for that cycle is discarded — the previous `Vi` is merely carried forward, and the reward value itself is never folded into the index: [3](#0-2) 

The same skip logic exists in the legacy (per-cycle) reward computation path, which never revisits or redistributes a cycle whose recorded `totalVote == 0`: [4](#0-3) 

This exactly mirrors the reported root cause: a value ("balance"/reward) is accrued and tracked unconditionally, but the index that makes it claimable is only updated when a supply/vote-count guard (`totalSupply > 0` / `voteCount > 0`) is true. Any reward accrued for a cycle where that guard is false is orphaned permanently — there is no mechanism to carry it forward into a later cycle once votes reappear, unlike the intentional pre-vote carry-forward of `Vi` itself.

The precondition for this to occur is that a witness can be an active block/tx-fee reward recipient for a cycle while its registered vote count (`delegationStore.getWitnessVote(cycle, address)` / `witness.getVoteCount()`) for that cycle is `0`. This is realistic in networks where the number of registered witnesses is at or below the active-witness limit (so all witnesses remain "active" block producers regardless of vote ranking), or immediately after all voters withdraw their votes from a witness that is still finishing out its current cycle as an active SR — the vote-count-zero state takes effect for the *next* cycle's bookkeeping via `setWitnessVote(nextCycle, ...)`, while blocks (and their rewards) produced by that witness in that next cycle still occur: [5](#0-4) 

### Impact Explanation
Any TRX reward accrued for a cycle in which a witness's registered vote count is zero is permanently unclaimable by any voter and is not returned to the witness or treasury — it is effectively burned/stuck in the accounting layer with no recovery path. This is a state/accounting integrity issue in the core DPoS reward-distribution mechanism affecting real TRX value, matching the "stuck rewards" impact class of the reported bug.

### Likelihood Explanation
The scenario requires a witness to earn block/fee rewards during a cycle while carrying a recorded vote count of zero for that cycle. This is plausible in real deployments where the active witness set size is not larger than the number of registered witnesses (so vote ranking does not gate block production), or transiently when a witness's votes are fully withdrawn while it is still completing an active cycle. It does not require any privileged role — it is a natural consequence of ordinary voting/unvoting and normal witness reward accrual, i.e., an unprivileged-user-triggerable state/accounting condition.

### Recommendation
When accumulating the per-cycle reward into `Vi` (`DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`), do not silently discard reward accrued for cycles with zero recorded votes. Instead, carry the un-distributed reward amount forward and add it to the next cycle's reward pot (so it can be distributed once votes exist), or refund it to the witness/treasury, rather than leaving it permanently orphaned in `DelegationStore`'s reward records.

### Proof of Concept
1. Deploy/operate a network where the number of registered witnesses is ≤ the active witness count limit, so all witnesses remain active regardless of vote count.
2. Register a new witness with `voteCount == 0` (or have all voters unvote an existing active witness so its vote count becomes 0 for cycle N, recorded via `setWitnessVote(N, witness, 0)` at the prior maintenance).
3. That witness continues to produce blocks in cycle N, causing `MortgageService.payBlockReward` / `payTransactionFeeReward` → `payReward` → `delegationStore.addReward(N, witness, value)` to accumulate a non-zero reward pot for cycle N.
4. At the next maintenance, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, witness, 0)` (vote count 0 for cycle N), which takes the "forward preVi, skip reward" branch, discarding the cycle-N reward entirely.
5. No voter can ever claim this reward (`totalVote == 0` causes `continue` in `computeReward`), and the witness cannot reclaim it either — the TRX is permanently stuck in the reward accounting.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
