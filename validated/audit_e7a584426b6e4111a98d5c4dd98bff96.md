## Finding: Stale-cache class execution bypasses declaration re-verification for Cairo 0 classes

### Title
Stale global class-cache entries let a sequencer execute Cairo 0 classes that are no longer canonically declared, causing honest-node state divergence — (File: `crates/blockifier/src/state/state_reader_and_contract_manager.rs`)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` serves compiled classes from a process-global, cross-block `ContractClassManager` cache. For Cairo 1 classes it explicitly re-checks `is_declared` on every cache hit because "existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)" [1](#0-0) . For Cairo 0 (`RunnableCompiledClass::V0`) the same re-verification is explicitly skipped (`RunnableCompiledClass::V0(_) => {}`) [2](#0-1) , and the accompanying trait doc even states "Cairo 0 classes always return `false`" for `is_declared`, meaning the class-manager treats V0 declaration status as unverifiable/unverified by design [3](#0-2) . The test suite explicitly documents this asymmetry: `cairo_0_cached_scenario` expects no `is_declared` call at all, unlike the Cairo 1 equivalent `cairo_1_cached_scenario`, which models exactly the "verification fails after reorg" case for Cairo 1 but has no analogous negative test for Cairo 0 [4](#0-3) .

### Finding Description
This mirrors the Elasticsearch bug class: a read path (`get_compiled_class`) serves data from a cache/index that has not been reconciled with the authoritative, most-recently-committed permission/existence state (there, Document/Field Level Security on a stale-but-cached document; here, class declaration status on a stale-but-cached compiled class).

The `RawClassCache`/`GlobalContractCache` backing `ContractClassManager` is populated as a side effect of any successful `get_compiled_classes` read [5](#0-4) , and it persists across block boundaries and is shared by the whole sequencer process [6](#0-5) . If a Cairo 0 class is declared during speculative/concurrent execution or in a block that is later reverted/reorged, the resulting compiled class remains cached even though the class is no longer declared in canonical state. Because the V0 branch performs no `is_declared` re-check, any subsequent transaction referencing that class hash (e.g. via `deploy`, `replace_class`, or `library_call`) will receive the stale cached class and execute successfully, instead of failing with `StateError::UndeclaredClassHash` as the Cairo 1 path (and as any node without the poisoned cache entry) would.

The concurrency test scaffolding confirms that per-transaction reads and writes for `declared_contracts` are tracked and validated during optimistic-concurrency validation/re-execution [7](#0-6) , but that mechanism only protects intra-block/`VersionedState` consistency — it does nothing to invalidate the separate, longer-lived `ContractClassManager` global cache checked in `get_compiled_from_class_manager`.

### Impact Explanation
A sequencer node whose global class cache contains a stale Cairo 0 entry (from a reverted block, failed speculative execution, or reorg) will accept and execute transactions that reference an undeclared class hash, while an honest node without that cache entry — or any node replaying/re-executing the block from scratch (e.g. Starknet OS re-execution or full sync) — will reject the same transaction with `UndeclaredClassHash`. This produces:
- Honest-node divergence: different nodes compute different execution results/state diffs for the same transaction set.
- Wrong committed state root / block hash if the poisoned node proposes or commits a block built on this execution.
- Potential unauthorized contract behavior, since code that was never canonically declared can be executed as if it were.

### Likelihood Explanation
The scenario requires a Cairo 0 class to be declared then reverted/reorged (or fail commit after being cached), which is a realistic operational occurrence (reorgs, concurrent-execution aborts, mempool re-execution, bouncer rejection after execution). The bug is fully triggerable by an ordinary unprivileged declare + reference-by-hash transaction pair from any account, with no special privileges — it only depends on timing relative to a revert/reorg, which is explicitly acknowledged as a real case in the code comments for the Cairo 1 branch.

### Recommendation
Apply the same `is_declared` re-verification for `RunnableCompiledClass::V0` cache hits as is already done for Cairo 1 classes in `get_compiled_from_class_manager`, removing the `RunnableCompiledClass::V0(_) => {}` no-op branch, or otherwise invalidate/evict cached Cairo 0 entries whenever the corresponding block is reverted/reorged.

### Proof of Concept
1. Submit a `DECLARE` transaction for a Cairo 0 class `X` such that `get_compiled_classes(X)` succeeds and is cached via `set_and_compile` [8](#0-7) , then have the containing block/transaction reverted (e.g., via reorg or execution abort) so canonical state no longer reflects `X` as declared.
2. Submit a second transaction (e.g., `deploy_account`, `replace_class`, or an invoke performing a `library_call`) referencing class hash `X`.
3. Observe that `get_compiled_class(X)` returns the stale cached `RunnableCompiledClass::V0` without calling `is_declared`, succeeding where it should fail with `StateError::UndeclaredClassHash`, as demonstrated by the divergent expectations between `cairo_0_cached_scenario` (no `is_declared` check) and `cached_but_verification_failed_after_reorg_scenario` (Cairo 1 only) in the existing test matrix [9](#0-8) .
