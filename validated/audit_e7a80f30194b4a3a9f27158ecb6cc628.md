### Title
Cross-tenant webhook forgery via unverified `X-Shopify-Shop-Domain` header — ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
Shopify's webhook HMAC (`X-Shopify-Hmac-Sha256`) is computed and verified over the raw request body only. The `X-Shopify-Shop-Domain` header — which is subsequently trusted to look up the offline session and, in some flows, to delete session data — is never included in the signed material. Any actor able to obtain one authentic, Shopify-signed webhook delivery (e.g. a merchant with the app installed on their own store) can replay that body/HMAC pair while swapping the `X-Shopify-Shop-Domain` header to name a different tenant that also has the app installed. This is directly analogous to the reported `_srcChainSender` issue: a parameter that identifies "who this operation is really for" is accepted by the receiving code but never cryptographically bound to the rest of the authenticated payload, letting the attacker impersonate a different principal (a different shop) in a privileged flow.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC solely from `rawBody`: [1](#0-0) 

The `domain` value used downstream comes from the `X-Shopify-Shop-Domain` header, which is only checked for *presence*, never bound to the HMAC: [2](#0-1) 

The overall `validate()` flow validates the HMAC over the body and independently reads the (unsigned) headers, returning `domain` straight from the header: [3](#0-2) 

Both `shopify-app-remix` and `shopify-app-react-router` then use this attacker-influenceable `check.domain` value to load the *victim's* offline session and build an authenticated admin client, with the request body still fully attacker-controlled: [4](#0-3) 

In `shopify-app-express`, the built-in `APP_UNINSTALLED` handler goes further and actively deletes all sessions for whatever shop the header claims: [5](#0-4) [6](#0-5) 

Since `apiSecretKey` is shared across every shop that has the app installed (it's an app-level secret, not per-shop), any merchant who installs the app on their own store can obtain a genuinely Shopify-signed webhook body+HMAC for an event they control (e.g. by installing/uninstalling the app, or performing any action that fires a subscribed topic). Because the domain header is not part of the signed content, that same body+HMAC pair remains valid when replayed directly to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to any other shop's domain that also has the app installed.

### Impact Explanation
- **Denial of Service on a specific victim tenant**: replaying a self-obtained `APP_UNINSTALLED` webhook with the victim's domain triggers `AppInstallations.delete()`, wiping the victim shop's stored sessions/access tokens via the default Express wrapper, forcing the merchant to reinstall/reauthenticate and breaking any app functionality relying on the stored offline token in the interim.
- **Cross-tenant session/context confusion**: for `shopify-app-remix`/`shopify-app-react-router`, a forged webhook causes the app's business logic to run with the *victim's* `session`/`admin` API client while processing a body the attacker fully controls (their own store's data, but able to include IDs/values referencing arbitrary resources), which can lead to unintended cross-tenant reads/writes depending on the app's webhook handler logic.
- Requires only that the attacker be a legitimate/self-service merchant able to install the app on a store they control — no privileged access or leaked secrets are required, satisfying an unprivileged, cross-tenant, concrete-impact analog.

### Likelihood Explanation
Any public/multi-tenant Shopify app is affected, since the vulnerability lies in how the library binds (or fails to bind) the shop identity to the signed payload — the `apiSecretKey` is shared across all installs. An attacker needs only to install the app (a normal, unprivileged onboarding action for any Shopify merchant) to obtain one valid signed webhook, then can freely target any other install of the same app whose domain they can guess or discover (many shop domains are guessable/public). This is low-effort and repeatable.

### Recommendation
Bind the shop identity to the verified payload rather than trusting the unsigned `X-Shopify-Shop-Domain` header in isolation:
- Where the webhook payload itself contains the originating shop/domain (many topics include shop-identifying fields in the JSON body), cross-check that value against the header before trusting `domain` for session lookup or destructive actions.
- Consider incorporating a per-shop binding (e.g., verifying the resolved offline session's own stored shop matches the header, and rejecting if a session for that domain was not the one associated with the specific webhook subscription ID/topic combination) before performing session-mutating operations like `AppInstallations.delete()`.
- At minimum, rate-limit/log anomalous webhook deliveries whose `X-Shopify-Webhook-Id` was not one actually registered/expected for the claimed domain.

### Proof of Concept
1. Attacker registers as a normal merchant and installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers (or waits for) a webhook delivery for a subscribed topic, e.g. `APP_UNINSTALLED`, capturing the raw body and the `X-Shopify-Hmac-Sha256` header Shopify computed with the app's shared secret.
3. Attacker resends this exact body and HMAC directly to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a shop known to have the same app installed).
4. `validateHmacFromRequestFactory`/`checkWebhooksHeaders` validates successfully because HMAC only covers `rawBody`. [7](#0-6) 
5. Downstream code (Express's `deleteAppInstallationHandler`, or Remix/React Router's `ensureValidOfflineSession(params, check.domain)`) acts on `victim-shop.myshopify.com`, deleting its session or processing attacker-controlled payload under the victim's session context.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
