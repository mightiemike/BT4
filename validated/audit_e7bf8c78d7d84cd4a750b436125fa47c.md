### Title
Reward checkpoint snapshotting allows "flash-vote" gaming of TRON witness voting rewards via freeze/vote/unfreeze cycling — (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
TRON's Stake 2.0 witness-voting reward system (`MortgageService`/`VoteRewardUtil` + `DelegationStore`) computes a voter's cycle reward from a **point-in-time snapshot** of the voter's vote weight, taken by whichever transaction happens to trigger `withdrawReward()` first after a maintenance cycle boundary. Because the snapshot is not time-weighted over the cycle, a user can freeze a large TRX balance and vote right before a maintenance boundary, let the checkpoint lock in that vote weight for the newly-started cycle, and then immediately unfreeze the balance, still collecting the full cycle's reward for capital that was actually locked for only an instant. This mirrors the RAAC Gauge "stake/withdraw cycling" bug class: reward accrual keyed to an instantaneous balance/vote snapshot rather than a duration-weighted stake.

### Finding Description
Vote rewards are accrued per maintenance cycle using a Vi (value-per-vote index) accumulator. At each maintenance boundary, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` using the witness's *current* aggregate vote count, then applies pending vote deltas from `VotesStore` and finally persists the vote total for the *next* cycle via `delegationStore.setWitnessVote(nextCycle, witness, witness.getVoteCount())`. [1](#0-0) 

An individual voter's own reward is computed as `deltaVi * userVoteCount`, where `userVoteCount` is taken from an **`AccountCapsule` snapshot stored per cycle** (`delegationStore.setAccountVote(cycle, address, accountCapsule)`), not from a time-weighted average of the voter's stake through the cycle: [2](#0-1) [3](#0-2) 

Crucially, this snapshot is taken by whichever transaction first calls `withdrawReward()` while the newly-started cycle is still "current" — it captures whatever vote weight the account happens to have at that moment, and that snapshot is used later to pay out the *entire* cycle's reward once the cycle fully ends. `UnfreezeBalanceV2Actuator.execute()` calls `mortgageService.withdrawReward(ownerAddress)` **before** it reduces the frozen balance or updates the vote list: [4](#0-3) 

So the sequence:
1. Freeze a large TRX amount right before a maintenance boundary and vote for a witness (`FreezeBalanceV2Actuator`/`VoteWitnessActuator`, which also calls `withdrawReward` first, locking in the account-vote snapshot for the freshly started cycle): [5](#0-4) 
2. The maintenance boundary fires, the witness's aggregate vote count (including the new stake) is captured for the new cycle via `setWitnessVote`.
3. Immediately after, the user calls `UnfreezeBalanceV2Contract` to withdraw the stake. `withdrawReward()` runs first and persists an `AccountCapsule` snapshot for the just-started cycle **using the still-full vote weight**, before `updateVote()`/`updateTotalResourceWeight()` reduce the stake.
4. `updateVote()`'s reduction only propagates to `VotesStore.newVotes`, which is only applied to the witness's aggregate at the *next* maintenance — i.e., it affects future cycles, not the one whose reward has just been locked in by the snapshot.
5. Once that cycle fully elapses, any later `withdrawReward` call (vote/freeze/unfreeze/explicit withdraw) credits the user's `allowance` for that cycle using the locked-in (briefly-held) vote weight, even though the capital was unfrozen almost immediately after step 3.

This can be repeated every maintenance cycle (default ~6 hours), letting a user capture full-cycle voting rewards while only exposing capital for a fraction of the cycle, diluting rewards for consistent long-term voters — functionally identical to the RAAC Gauge stake/withdraw gaming pattern, just expressed at cycle granularity instead of per-block granularity.

### Impact Explanation
This allows disproportionate extraction of witness-voting rewards (paid from TRX inflation/transaction fees into the `allowance` balance via `WithdrawBalanceActuator`/`WithdrawRewardProcessor`) without bearing the intended capital lock-up. Reward funds are a shared pool; gaming this mechanism dilutes rewards earned by genuine long-term voters and misrepresents the economic assumption that voting rewards compensate for locked/at-risk stake. This is a concrete accounting/incentive-manipulation impact on a public, unprivileged-user-reachable reward flow.

### Likelihood Explanation
The actions involved (`FreezeBalanceV2`, `VoteWitnessContract`, `UnfreezeBalanceV2Contract`, `WithdrawBalanceContract`) are all ordinary unprivileged user transactions with no minimum holding-period enforcement tied to the maintenance-cycle reward snapshot. The only constraints are needing enough TRX to freeze and paying normal transaction fees/bandwidth, both trivial for well-funded actors, and the timing requirement (transact near a maintenance boundary) is easily automatable since maintenance times are deterministic and queryable via `ConsensusDelegate`/`DynamicPropertiesStore`.

### Recommendation
Tie voter reward eligibility for a cycle to whether the stake/vote was held for a minimum duration spanning that cycle (e.g., require the freeze to predate the cycle's start by more than a grace threshold, or compute a time-weighted average vote weight across the cycle) rather than snapshotting whatever vote weight is present at the first `withdrawReward()` call after the cycle begins. Alternatively, enforce that `UnfreezeBalanceV2`/vote-reduction actions occurring within the same cycle as a fresh `FreezeBalanceV2`/vote retroactively reduce that cycle's `AccountCapsule` reward snapshot before it is finalized in `DelegationStore`.

### Proof of Concept
Conceptual sequence exercising the existing actuators (no code changes needed to demonstrate, as this is inherent contract-level logic):
1. Just before `nextMaintenanceTime`, submit `FreezeBalanceV2Contract` (`TRON_POWER`) for a very large amount, then `VoteWitnessContract` voting entirely for one witness — reaching `VoteWitnessActuator.countVoteAccount` which calls `mortgageService.withdrawReward` and sets `accountCapsule`'s vote list.
2. Let/force a block to cross `nextMaintenanceTime`; `MaintenanceManager.doMaintenance()` applies the new vote to the witness total and calls `delegationStore.setWitnessVote(nextCycle, witness, ...)` including the new stake.
3. Immediately submit `UnfreezeBalanceV2Contract` for the full amount. Inside `UnfreezeBalanceV2Actuator.execute()`, `mortgageService.withdrawReward(ownerAddress)` runs first (line 72) and calls `delegationStore.setAccountVote(nextCycle, address, accountCapsule)` while `accountCapsule` still reflects the full (not-yet-reduced) vote weight; only after that does `updateVote()` reduce the vote for future propagation.
4. After the cycle fully elapses (next maintenance), any trigger of `withdrawReward` (e.g., another vote/freeze/unfreeze, or explicit `WithdrawBalanceContract`) computes `computeReward(beginCycle, endCycle, accountCapsule)` in `MortgageService`, crediting the account the full cycle's reward proportional to the huge (briefly held) vote weight recorded in step 3, even though the stake was unfrozen almost immediately after the maintenance boundary.   public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
