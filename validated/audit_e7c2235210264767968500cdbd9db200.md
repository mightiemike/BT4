## Title
Wallet Contract `has_in_flight_tx` Flag Can Permanently Brick ETH-Implicit Accounts, Freezing All Funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract, which is the global contract deployed to every ETH-implicit account, gates all mutating entry points behind an in-flight-transaction boolean (`has_in_flight_tx`). The only path that can clear this flag after a faulty-relayer ban is a single, non-atomic action batch (`delete_key` + `function_call_weight("ban_relayer")`) rather than a `.then()`-chained callback. If the first action in that batch fails, `ban_relayer` never executes and `has_in_flight_tx` is left `true` forever, permanently disabling the account's only entry point.

### Finding Description
An ETH-implicit account is created with a `Global` contract reference to the Wallet Contract and by design "can only be used by calling the methods of the Wallet Contract. It cannot be deleted, nor can a full access key be added" [1](#0-0) . This makes `rlp_execute` the account's *sole* means of ever moving funds or state — structurally identical to the report's pattern where `withdraw()`/`quitLock()`/`delegate()` are the only exits and are all gated by one shared, mutable condition (there `isBlocked()`, here `has_in_flight_tx`).

`rlp_execute` refuses to do anything at all while `has_in_flight_tx` is `true`: [2](#0-1) 

When a relayer using an access key misbehaves, the contract sets the flag and dispatches a single promise batch meant to both revoke the bad key and reset the flag: [3](#0-2) [4](#0-3) 

Unlike every other path in the contract (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`), which reset `has_in_flight_tx` in a `.then()`-chained callback that always fires regardless of the preceding action's success/failure, `create_ban_relayer_promise` bundles `delete_key` and the `ban_relayer` call (the only place that clears the flag on this path) as two actions of the *same* action receipt via `function_call_weight` rather than a chained promise. If `delete_key` fails within that receipt (e.g., `DeleteKeyDoesNotExist` because the key was already removed by a prior, partially-successful attempt, or any other action-receipt-level failure), the whole action receipt aborts and `ban_relayer` — the only statement that sets `self.has_in_flight_tx = false` on this path — never runs.

Because `rlp_execute` unconditionally short-circuits at the top when `has_in_flight_tx == true`, and because the account structurally can never obtain a full-access key or deploy alternate code to route around the broken contract, this leaves the account permanently unable to execute any further Ethereum-emulated transaction — freezing whatever NEAR balance or NEP-141/NEP-171 assets are held under that account with no unblock/recovery mechanism, exactly mirroring the report's core defect: a single mutable gate with no way to clear it once it traps an account, and no alternate exit for the victim.

### Impact Explanation
Any funds (NEAR balance, or assets managed through the wallet, e.g. FT balances transferred to the account) become permanently unreachable once the flag is stuck, since:
- The account cannot add a full-access key (`AddFullAccessKey` is explicitly rejected by contract logic and the account type itself forbids it at protocol level) [5](#0-4) .
- The account cannot be deleted or have its contract replaced (ETH-implicit accounts are permanently bound to the wallet contract) [1](#0-0) .
- `rlp_execute` is gated entirely by `has_in_flight_tx`, with no other host-level or admin mechanism to reset it [6](#0-5) .

This matches the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
This requires the relayer-error path to be triggered (an unprivileged relayer — anyone the user or previous flow trusted with a `FunctionCall`-permission key — submits a transaction that resolves to `Error::Relayer`) *and* the subsequent `delete_key` batch action to fail. The latter can plausibly occur under a race (the relayer's key already deleted/rotated concurrently, e.g., by the user rotating relayers) or any other action-level failure of `delete_key` within that same receipt. Because the ban path is used specifically to punish already-misbehaving/untrusted relayers, the exact conditions under which it fires are attacker-adjacent, making deliberate or accidental triggering plausible without needing validator or network-level compromise. I was not able to fully trace every runtime code path that decides whether a `DeleteKeyDoesNotExist` action failure aborts remaining batch actions in the same receipt (this is asserted from documented actions-batch/action-receipt failure semantics, not directly verified for this repo's `apply_action_receipt` implementation in this session).

### Recommendation
Chain `ban_relayer` to the `delete_key` promise via `.then()` (as the other three flag-reset paths do) rather than batching it as a second action on the same receipt, so that `has_in_flight_tx` is guaranteed to be cleared via a callback that fires whether or not `delete_key` succeeds. Additionally, consider an explicit timeout/liveness fallback (e.g., a self-callback that unconditionally resets the flag after a bounded number of blocks) so a stuck flag cannot permanently brick the account regardless of failure mode.

### Proof of Concept
1. Register a relayer key with `FunctionCall` permission on an ETH-implicit account's Wallet Contract, per `test_register_relayer` [7](#0-6) .
2. Have the relayer submit an `rlp_execute` call that triggers a `Error::Relayer` classification, causing `rlp_execute` to build `create_ban_relayer_promise` and set `has_in_flight_tx = true` [3](#0-2) .
3. Before that receipt executes, remove the relayer's public key from the wallet account through another concurrent path (or otherwise cause the `delete_key` action in `create_ban_relayer_promise` to fail), so the batch receipt fails before reaching `function_call_weight("ban_relayer", …)`.
4. Observe that `self.has_in_flight_tx` remains `true` permanently, and all further `rlp_execute` calls immediately return the "transaction already in progress" error [8](#0-7) , with no way to reset it and no alternate account-recovery action available to an ETH-implicit account.

fn create_ban_relayer_promise(current_account_id: AccountId) -> Promise {
    let pk = env::signer_account_pk();
    Promise::new(current_account_id).delete_key(pk).function_call_weight(
        "ban_relayer".into(),
        Vec::new(),
        NearToken::from_yoctonear(0),
        Gas::from_tgas(1),
        GasWeight(1),
    )
}

// A relayer can use its own Near account to send a transaction containing data
// signed by the user which adds a FunctionCall access key to the Wallet
// Contract account. This allows the relayer to send transactions on the user's
// behalf while the user covers the gas costs.
#[tokio::test]
async fn test_register_relayer() -> anyhow::Result<()> {
    let TestContext { worker, mut wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let relayer_pk = wallet_contract.register_relayer(&worker).await?;
    let key = wallet_contract.inner.as_account().view_access_key(&relayer_pk).await?;
    match &key.permission {
        AccessKeyPermission::FunctionCall(access) => {
            assert_eq!(access.allowance, None);
            assert_eq!(access.receiver_id.as_str(), wallet_contract.inner.id().as_str());
            assert_eq!(&access.method_names, &[RLP_EXECUTE]);
        }
        _ => panic!("Unexpected full access key"),
    }
