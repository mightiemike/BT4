### Title
Silent swallow of outbound-attachment failure after committed EVM payload execution permanently loses user withdrawal outbounds - (File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go / execute_inbound_gas_and_payload.go)

### Summary
Both `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload` chain two logically dependent operations the same way a shell script chains `&&`/`;` groups: (1) execute the user's payload through the UEA via `ExecutePayloadV2`, which internally commits its EVM state via a `CacheContext`/`writeCache()`, and (2) call `AttachOutboundsToExistingUniversalTx` to parse the resulting receipt logs and register any withdrawal as a `PendingOutbounds`/`OutboundTx` entry for TSS signing. If step (2) fails, the error is only stored as a string in `utx.RevertError` and the function still returns `nil` — exactly the "group fails, but the chain keeps going and is treated as fine" pattern described in the external report.

### Finding Description
In `ExecuteInboundFundsAndPayload` (and the analogous `ExecuteInboundGasAndPayload`): [1](#0-0) 

`ExecutePayloadV2` already commits the EVM call and fee deduction to real state via its own `CacheContext.writeCache()` before returning: [2](#0-1) 

Once that has committed, `AttachOutboundsToExistingUniversalTx` is invoked using the real `sdkCtx` (not a cache), and it parses the receipt for a `UniversalTxOutboundEvent` and resolves the withdrawn PRC20 to its external token config via `GetTokenConfigByPRC20`: [3](#0-2) 

If that lookup (or the outbound-enabled check, or log decoding) fails, `BuildOutboundsFromReceipt` returns an error, which propagates up through `AttachOutboundsToExistingUniversalTx`. The caller catches this `attachErr` and does nothing but write a string into `utx.RevertError`, then returns `nil`: [4](#0-3) 

There is no compensating outbound, no automatic retry, and `RevertError` is not consumed anywhere else to drive a refund/retry flow — it exists purely as a diagnostic field on the stored `UniversalTx` object.

### Impact Explanation
This lets an unprivileged user cause a **permanent loss of protocol/user-controlled value**: the UEA-driven EVM call that already executed (e.g., a token withdraw/bridge-out routine inside the user's own contract logic invoked via `MsgExecutePayload`/inbound execution) burns or locks the underlying PRC20 as part of a genuine withdraw call to the `UniversalGatewayPC`, emitting the `UniversalTxOutboundEvent`. If the withdrawn PRC20 address does not resolve via `uregistry`'s `GetTokenConfigByPRC20` (e.g., attacker crafts a payload that calls the gateway's withdraw path for an unmapped/unsupported PRC20, or targets an chain whose config was removed/mis-set after the tx was built), the EVM-side effects (burn, balance change, fee deduction) are already irreversibly committed, but the corresponding `OutboundTx`/`PendingOutbounds` entry that would let TSS actually execute the destination-chain send is never created. The withdrawal is silently dropped — funds are debited on Push Chain with no destination-chain delivery and no automated remedy, matching the "permanent freezing/loss of user funds" impact category.

### Likelihood Explanation
Reachable purely through the standard `MsgExecutePayload` gasless flow that any account can submit, with a UEA/contract payload that calls a withdraw path routing through an arbitrary/edge-case PRC20 address. No validator, admin, or TSS-participant collusion is required — an honest node executing an ordinary payload from an ordinary user is sufficient to hit the code path, provided the token/PRC20 → chain mapping check in `uregistry` fails at the moment `BuildOutboundsFromReceipt` runs (mapping drift, disabled chain, or attacker-selected token address not present in `uregistry`). Likelihood is moderate: it requires either an unmapped token or a race with a governance-driven config change, but the resulting swallow-and-continue behavior applies universally to any `AttachOutboundsToExistingUniversalTx` failure, not just this one trigger.

### Recommendation
**Short term:** Do not treat `attachErr` as a soft, string-only failure. Since the EVM state (burn/withdraw) is already committed by the time this check runs, the correct remedial action is to either (a) wrap the entire payload-execution + attach-outbound sequence in a single outer `CacheContext` so a failure to attach rolls back the EVM state too, or (b) if that is architecturally infeasible (payload execution must be observable independently), synthesize and attach an automatic compensating `RESCUE_FUNDS`/refund outbound the moment `AttachOutboundsToExistingUniversalTx` fails, instead of just recording a string.

**Long term:** Split the "execute payload" and "attach outbound" steps into independently retryable, explicitly-modeled state transitions (mirroring the report's guidance to avoid chaining unrelated command groups): persist a distinct "outbound-attach-pending" status on the `UniversalTx` so a background sweep can retry attachment once the `uregistry` mapping issue is resolved, rather than relying on an inert `RevertError` string with no consumer.

### Proof of Concept
1. Register a PRC20 token/chain mapping in `uregistry`, deploy a UEA, and fund it.
2. Submit `MsgExecutePayload` (or an inbound funds-and-payload flow) whose UEA-executed payload calls the `UniversalGatewayPC` withdraw entry point using a PRC20 address that has since been removed from `uregistry` (or was never added), while destination-chain outbound is otherwise enabled.
3. `ExecutePayloadV2` succeeds and commits (fees deducted, EVM burn/withdraw applied) — see the commit path at [5](#0-4) .
4. `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt` fails at the `GetTokenConfigByPRC20` lookup [6](#0-5) .
5. The caller records `utx.RevertError` and returns `nil` [4](#0-3) ; querying `UniversalTx` shows no `OutboundTx` entries and no `PendingOutbounds` record exists for the withdrawal — the burned/withdrawn value has no path to reach its destination chain.

Note: I was not able to fully trace whether any background reconciliation job outside `x/uexecutor` consumes `RevertError` to trigger manual/governance remediation — if such a process exists, it would reduce (but not eliminate, since it is off-chain/manual, not protocol-enforced) the severity of this finding. I recommend verifying this in a Devin session against the full repository, since index size limits may have excluded any operator-facing reconciliation tooling.
