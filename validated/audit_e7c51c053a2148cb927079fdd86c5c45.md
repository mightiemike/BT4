### Title
Cross-tenant impersonation via unauthenticated `shop` query parameter in `MerchantCustomAuth.authenticate` - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/merchant-custom-app.ts])

### Summary
`MerchantCustomAuth.authenticate` mints a session directly from `sessionContext.shop` via `api.session.customAppSession(shop)` with no cryptographic verification of the shop's identity. For merchant-custom-app/single-merchant apps, `config.isEmbeddedApp` is normally `false`, so the caller (`getSessionTokenContext` in `authenticate.ts`) skips the JWT-based `validateSessionToken` path entirely and instead reads `shop` directly from the unauthenticated URL query string.

### Finding Description
The call chain is: `authenticateAdmin` (`packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`, lines 143-186) calls `getSessionTokenContext(params, request)` to derive `shop`, then invokes `strategy.authenticate(request, {session, sessionToken, shop})`.

Inside `getSessionTokenContext` (same file, lines 189-229), the only shop-authenticity check is gated behind `if (config.isEmbeddedApp)`: [1](#0-0) 

When `config.isEmbeddedApp` is `false` (the documented/typical configuration for `AppDistribution.ShopifyAdmin` / merchant-custom apps, as shown in the repo's own tests), `shop` is taken verbatim from `url.searchParams.get('shop')` with no HMAC, JWT, or session-token verification whatsoever: [2](#0-1) 

`validateShopAndHostParams`, the other pre-check invoked earlier in `authenticateAdmin`, also only runs its `sanitizeShop`/`sanitizeHost` checks `if (config.isEmbeddedApp)`: [3](#0-2) 

That unvalidated `shop` value is then passed straight into `MerchantCustomAuth.authenticate`, which trusts it completely to build the session: [4](#0-3) 

`customAppSession` itself performs only format sanitization (`sanitizeShop`), not authenticity verification: [5](#0-4) 

Repo tests confirm this exact flow is the intended/expected behavior: a plain unauthenticated request with only `?shop=<value>` in the query string produces a valid session for that shop, with no Authorization header or session token check involved: [6](#0-5) 

### Impact Explanation
Because the merchant-custom-app strategy always uses the app's single statically configured `adminApiAccessToken` (not a per-shop token derived from the `shop` value), the practical impact is that the resulting `session.shop` field — used as a data/tenant key throughout the app (session storage, webhooks, app-level per-shop data lookups) — is fully attacker-controlled without any signature check. An attacker can cause the app to construct a "session" tagged with an arbitrary `shop` string while all API calls still execute against the real configured merchant. This corresponds to the AUTHENTICITY / TENANT_ISOLATION invariant: the `shop` claimed by a request is never cryptographically bound to the requester when `isEmbeddedApp` is `false`, which is the standard, documented configuration for this distribution type (`AppDistribution.ShopifyAdmin`, non-embedded, single merchant custom app) — not a misconfiguration.

### Likelihood Explanation
This is inherent to how `AppDistribution.ShopifyAdmin` (merchant custom app) is designed in this library: such apps are documented as non-embedded, single-tenant apps that don't use OAuth/session tokens at all (see `packages/apps/shopify-api/docs/guides/custom-store-app.md`), so there is no JWT to check by design. Reaching this code path requires no privileged access — merely sending a plain HTTP request with a `shop` query parameter to a route protected by `authenticate.admin()` in an app configured with `distribution: AppDistribution.ShopifyAdmin`. However, this is the intended, documented operating mode for this specific app type (single custom app per merchant, no multi-tenant session storage expected), which limits the exploitable blast radius primarily to apps that mistakenly key sensitive per-shop application data off the unverified `session.shop` string rather than the (correctly-authenticated) fixed shop the access token belongs to.

### Recommendation
For non-embedded merchant-custom-app / single-merchant configurations, do not derive `session.shop` from an unauthenticated query parameter. Either bind the session's shop to the statically configured shop domain (a value the app developer configured, not attacker input), or require some other tamper-proof means of shop identification for this distribution type, rather than trusting `url.searchParams.get('shop')` verbatim in `getSessionTokenContext`.

### Proof of Concept [6](#0-5) 

```ts
// Jest PoC
const config = testConfig({
  isEmbeddedApp: false,
  distribution: AppDistribution.ShopifyAdmin,
  adminApiAccessToken: 'test-token',
});
const shopify = shopifyApp(config);

// Attacker picks an arbitrary shop with no Authorization header / session token
const { session } = await shopify.authenticate.admin(
  new Request(`${APP_URL}?shop=attacker-picked-tenant.myshopify.com`),
);

// Expected (secure) behavior: request should be rejected because "shop" is unverified.
// Actual behavior: session.shop === "attacker-picked-tenant.myshopify.com" with no verification performed.
expect(session.shop).toBe('attacker-picked-tenant.myshopify.com');
```

export function validateShopAndHostParams(
  params: BasicParams,
  request: Request,
) {
  const {api, config, logger} = params;

  if (config.isEmbeddedApp) {
    const url = new URL(request.url);
    const shop = api.utils.sanitizeShop(url.searchParams.get('shop')!);
    if (!shop) {
      logger.debug('Missing or invalid shop, redirecting to login path', {
        shop,
      });
      throw redirectToLoginPath(request, params);
    }

    const host = api.utils.sanitizeHost(url.searchParams.get('host')!);
    if (!host) {
      logger.debug('Invalid host, redirecting to login path', {
        shop,
        host: url.searchParams.get('host'),
      });
      throw redirectToLoginPath(request, params);
    }
  }
