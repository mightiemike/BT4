### Title
Outbound `Target`/`Recipient` accepted as raw arbitrary bytes with no destination-VM address-format validation before TSS signing - ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
`event.ChainId` and `event.Target` in `UniversalTxOutboundEvent` are fully attacker-controlled: any user can drive a `withdraw`/`withdrawAndExecute` call from their UEA (via `MsgExecutePayload` → arbitrary EVM call data to `UniversalGatewayPC`) that emits `UniversalTxOutbound` with a CAIP-2 `chainId` string and an arbitrary-length `target` `bytes` blob [1](#0-0) [2](#0-1) . `BuildOutboundsFromReceipt` only checks that the destination chain is enabled and that a token config exists; it copies `event.Target` verbatim into `OutboundTx.Recipient` with no check that the byte length/format matches the destination chain's `VmType` (EVM 20-byte address vs. Solana 32-byte pubkey, etc.) [3](#0-2) . `OutboundTx.ValidateBasic()` likewise only requires `Recipient` to be a non-empty string — it performs no chain/VmType-specific address validation, unlike `Inbound.ValidateForExecution()`, which does enforce hex-address format for FUNDS/GAS types [4](#0-3) [5](#0-4) .

### Finding Description
This is the direct Push Chain analog of the Wormhole bug: a value meaningful in one chain-id/address space is accepted and propagated into another without validating it is well-formed for the actual destination environment. In WormholeFacet, `block.chainid` (EVM) was compared against a Wormhole chain id, and an EVM `address` truncation was used for non-EVM recipients, silently permitting malformed data to reach bridging logic. In Push Chain, the outbound-creation pipeline takes `event.ChainId` (arbitrary CAIP-2 string, validated only for "is outbound enabled") and `event.Target` (arbitrary-length raw bytes, ABI-decoded as generic `bytes`, not `address`) straight from an EVM log emitted by a user-controlled EVM call, and stores them as `OutboundTx.DestinationChain` / `OutboundTx.Recipient` [6](#0-5) . Nothing in this on-chain path cross-checks `Target`'s byte-length/encoding against the registered `ChainConfig.VmType` for that `ChainId` (`uregistry` stores `VmType` per chain [7](#0-6) , but `create_outbound.go` never reads or enforces it).

The malformed `OutboundTx` is then attached to the UTX and written to `PendingOutbounds` for UV/TSS pickup and signing [8](#0-7) , entering the same signing/broadcast flow as legitimate outbounds. The final parsing of `Recipient` bytes happens off-chain in the relayer/universalClient tx builders (e.g. Solana's `TxBuilder`, which tries base58 first and falls back to raw 32-byte hex) [9](#0-8) , meaning the honest-node/TSS layer will happily sign and broadcast a withdrawal to whatever bytes were embedded by the attacker's payload, exactly mirroring the Wormhole report's warning that "if a bridge would be done to a non-EVM chain... then the tokens would be lost" due to address-format truncation/mismatch.

### Impact Explanation
If an unprivileged user crafts a payload (via `MsgExecutePayload`) that calls `UniversalGatewayPC.withdraw`/`withdrawAndExecute` with a `target` that is malformed for the destination chain's VM (wrong length/encoding for the configured `VmType`), the resulting `OutboundTx` will still pass `ValidateBasic()` (only checks non-empty) and be queued for TSS signing. Depending on how the destination-chain tx builder/gateway ultimately treats the malformed bytes, this can produce a signed and broadcast outbound to an address that decodes to an unintended or unowned account/PDA — resulting in permanent loss of the bridged funds. This satisfies "permanent loss of user or protocol-controlled funds" in the allowed-impact gate, reachable purely from an ordinary user's own payload/transaction (their own funds are what get burned/minted-out to the mismatched recipient), with honest validators/TSS signers processing the ballot exactly as designed.

### Likelihood Explanation
Medium. The attacker needs control over the calldata reaching `UniversalGatewayPC.withdraw`, which is achievable by any UEA owner submitting `MsgExecutePayload` with a payload targeting the gateway contract — this is a standard, unprivileged user flow, not a privileged one. The chain-id must correspond to an already-configured (`IsChainOutboundEnabled`) chain, which narrows exploitation to registered chains, but nothing in the reviewed code stops a mismatched/malformed `target` from being embedded against any of those chains's `VmType`.

### Recommendation
In `BuildOutboundsFromReceipt` (and generally in `OutboundTx.ValidateBasic()`), fetch the destination `ChainConfig.VmType` for `event.ChainId` and validate `event.Target`/`Recipient` against the expected address encoding for that VM type (e.g., 20-byte checksummed hex for `VmType_EVM`, valid 32-byte Solana pubkey for `VmType_SVM`) before creating the `OutboundTx` and before it is queued into `PendingOutbounds`. Reject/route to an error/PCTx-failed path (analogous to the inbound recipient validation) rather than silently accepting arbitrary bytes.

### Proof of Concept
1. Attacker deploys/controls a UEA on Push Chain and calls `MsgExecutePayload` with a `UniversalPayload.Data` that ABI-encodes a call to `UniversalGatewayPC.withdraw(...)`/`withdrawAndExecute(...)` specifying `chainId = "solana:<registered-cluster>"` and `target` as a 20-byte EVM-style address (or any byte string not forming a valid Solana pubkey).
2. `BuildOutboundsFromReceipt` decodes the log, confirms `IsChainOutboundEnabled("solana:...")==true`, resolves the token config, and creates `OutboundTx{DestinationChain: "solana:...", Recipient: "0x<20-byte-blob>", ...}` with no VmType/address-format check [10](#0-9) .
3. `OutboundTx.ValidateBasic()` passes because `Recipient` is non-empty [11](#0-10) .
4. The outbound is attached to the UTX and placed in `PendingOutbounds` for UV/TSS signing [12](#0-11) , and ultimately gets broadcast to the Solana gateway with a malformed/foreign recipient pubkey once the relayer parses the bytes (via the base58/32-byte-hex fallback logic) [9](#0-8) .

Note: I could not fully verify (index limits / no further tool calls available) whether the Solidity `UniversalGatewayPC.withdraw`/`withdrawAndExecute` functions themselves perform any client-side length/format check on `target` before emitting the event, since the Solidity contract source was not indexed in this repo scan — only the ABI-decode side (`x/uexecutor/types/gateway_pc_event_decode.go`) and the Go keeper/off-chain tx-builder code were reachable. If the Solidity contract already enforces a fixed-length encoding matching the destination `VmType`, this reduces likelihood; that should be confirmed in a full Devin session with access to the contracts repository.

// ValidateBasic does the sanity check on the OutboundTx fields.
func (p OutboundTx) ValidateBasic() error {
	// Validate destination_chain (must follow CAIP-2 format)
	chain := strings.TrimSpace(p.DestinationChain)
	if chain == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "destination_chain cannot be empty")
	}
	if !strings.Contains(chain, ":") {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "destination_chain must be in CAIP-2 format <namespace>:<reference>")
	}

	// recipient must not be empty
	if strings.TrimSpace(p.Recipient) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
	}

	// sender
	if strings.TrimSpace(p.Sender) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "sender cannot be empty")
	}
	if !utils.IsValidAddress(p.Sender, utils.HEX) {
		return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid sender address: %s", p.Sender)
	}
