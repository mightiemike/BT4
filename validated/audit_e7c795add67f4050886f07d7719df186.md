### Title
`DelegateAction`/`DelegateActionV2` NEP-461 signature scheme omits a chain/network identifier, allowing a `SignedDelegateAction` from one NEAR network to be replayed on another - (File: `core/primitives/src/signable_message.rs`)

### Summary
NEAR's meta-transaction signing scheme (NEP-366/NEP-461) computes the hash that a user signs to authorize a `DelegateAction` purely from a `MessageDiscriminant` plus the action payload — it never includes any network/chain identifier (genesis hash, chain id, etc.). This mirrors the reported Telcoin issue where `getTransactionHash` omits `chainId`, letting the same signed payload be valid on more than one chain.

### Finding Description
`SignableMessage::new`/`sign` builds the signed byte string as just `{discriminant, msg}` and hashes it: [1](#0-0) 

`DelegateAction::get_nep461_hash` / `VersionedDelegateActionPayload::get_nep461_hash` feed `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` into that scheme — none of which is chain-specific: [2](#0-1) [3](#0-2) 

Verification (`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify`) only checks the signature against this network-agnostic hash and the embedded `public_key`: [4](#0-3) [5](#0-4) 

Contrast this with a regular `SignedTransaction`, which binds itself to a specific fork by embedding `block_hash` (used purely as a freshness/liveness check, not a network id, but which incidentally differs per-chain): [6](#0-5) 

`DelegateAction` has no equivalent binding at all — only `max_block_height`, a plain integer that has no chain-specific entropy and can coincide across networks: [7](#0-6) 

The only replay protection for a delegate action is the sender's access-key `nonce`, which is local, per-account, per-network state: [8](#0-7) 

Because nothing in the signed bytes ties the `SignedDelegateAction` to a particular network, the identical signature is accepted by `apply_delegate_action` on any NEAR-protocol-compatible chain where the sender account, public key, and nonce state line up: [9](#0-8) 

### Impact Explanation
If the same account id and access key exist on two different NEAR-protocol networks (mainnet, testnet, or any other chain running this codebase/genesis-fork with the same accounts — e.g. migration/canary networks, private deployments, or a user who reused a keypair across networks as recommended by wallets), a relayer or any observer who captures a `SignedDelegateAction` intended for network A can resubmit the exact same bytes as a meta-transaction on network B. If the account's nonce on network B has not yet advanced past the nonce used, `apply_delegate_action` will accept it and execute the delegated actions (transfers, function calls, key/account management) against the victim's account on the unintended network — a concrete unauthorized-value-movement / invalid-state-acceptance outcome caused purely by hash collision across chains, exactly the bug class described in the report.

### Likelihood Explanation
Exploitation requires the same account id + public key + comparable nonce state to be reachable on more than one active NEAR-protocol network — a realistic condition given that operators regularly stand up compatible networks (testnets, canary/shadow chains, or forks) seeded from the same or overlapping accounts/keys, and users are known to reuse keys across environments. No validator or node misbehavior is needed; a normal relayer or any third party who has observed a `SignedDelegateAction` can trigger this by submitting it as a transaction on the other network. Likelihood is moderate — it depends on operational cross-network key/account overlap rather than being universally exploitable on isolated mainnet alone.

### Recommendation
Include a network-binding value (e.g. genesis hash or a protocol-defined `chain_id`) inside the `SignableMessage`/`DelegateAction` payload that is hashed and signed, similar to how EIP-712/EIP-155 include `chainId`. This should be added as a field of `DelegateAction`/`DelegateActionV2` (or folded into the `MessageDiscriminant`/`SignableMessage` wrapper) and checked during `apply_delegate_action` verification, so a signature produced for one network can never validate on another.

### Proof of Concept
1. On Network A (e.g. testnet), account `alice.near` with access key `K` signs a `DelegateAction { sender_id: alice.near, receiver_id: bob.near, actions: [Transfer{...}], nonce: N, max_block_height: H, public_key: K }` via `DelegateAction::get_nep461_hash` / `SignedDelegateAction::sign` (`core/primitives/src/action/delegate.rs:92-96`).
2. Suppose Network B (another NEAR-protocol chain/fork sharing genesis accounts, or a network where `alice.near` was independently created with the same key `K`) also has `alice.near`'s access key `K` with nonce state `< N`.
3. An observer copies the exact `SignedDelegateAction` bytes from Network A's mempool/receipt and wraps them in a fresh relayer transaction submitted to Network B (`test-loop-tests/src/tests/gas_keys.rs:220-266` shows the standard wrapping flow via `Action::Delegate`/`Action::DelegateV2`).
4. `apply_delegate_action` on Network B calls `signed_delegate_action.verify()`, which succeeds because the hashed bytes contain no chain-specific data (`runtime/runtime/src/actions.rs:474-477`), and — provided the nonce/`max_block_height` checks pass — executes the `Transfer` action against `alice.near`'s balance on Network B, which she never authorized on that network.

pub struct SignableMessage<'a, T> {

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]

pub enum SignableMessageType {
    /// A delegate action, intended for a relayer to included it in an action list of a transaction.
    DelegateAction,
    /// A delegate action with gas key support, intended for a relayer to include it in an action
    /// list of a transaction.
    DelegateActionV2,
}

    UnknownOnChainNep(u32),
    #[error("NEP {0} does not have a known off-chain use")]
    UnknownOffChainNep(u32),
    #[error("discriminant is in the range for transactions")]
    TransactionFound,
}

    #[error("nep number {0} is too big")]

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }

it is required to arrive within a certain number of blocks from the block
identified by the `block_hash`.  Any transaction arriving outside this
threshold is considered to be invalid.  Allowed delay is defined by
`transaction_validity_period` option in the chain’s genesis file.  On
mainnet, this value is 86400 (which corresponds to roughly a day) and
on testnet it is 100.

struct DelegateAction {

```markdown
## Limitation: Accounts must be initialized

Any transaction, including meta transactions, must use NONCEs to avoid replay
attacks. The NONCE must be chosen by Alice and compared to a NONCE stored on
chain. This NONCE is stored on the access key information that gets initialized
when creating an account.

Implicit accounts don't need to be initialized in order to receive NEAR tokens,
or even $FT. This means users could own $FT but no NONCE is stored on chain for
them. This is problematic because we want to enable this exact use case with
meta transactions, but we have no NONCE to create a meta transaction.

For the MVP, the proposed solution, or work-around, is that the relayer will
have to initialize the account of Alice once if it does not exist. Note that
this cannot be done as part of the meta transaction. Instead, it will be a
separate transaction that executes first. Only then can Alice even create a
`SignedDelegateAction` with a valid NONCE.
```

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
