## Title
`ensure_match_transaction_info` skips `state_checkpoint_hash`/`position_state_checkpoint_hash` verification, letting `replay_on_archive`/replay-verify accept a divergent state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/backup-verification tooling (e.g. `storage/db-tool/src/replay_on_archive.rs`) to check that a locally re-executed `TransactionOutput` matches an authenticated `TransactionInfo` pulled from a backup/archive. It checks status, gas used, write-set hash, and event root hash, but — per its own inline TODO — it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, all of which are hashes committed into the transaction accumulator (i.e., proof-bearing, consensus-verified fields on `TransactionInfoV1`).

### Finding Description
`ensure_match_transaction_info` in `types/src/transaction/mod.rs` (around lines 2139-2204) validates:
- `status()` vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- `write_set` hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

It explicitly does **not** validate `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` against the locally computed state (JMT), hot-state, or native-position state roots. The code contains a self-admitted acknowledgment of this gap: [1](#0-0) 

This is the single call site consuming this method for archival verification: [2](#0-1) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as fields bound to the accumulator-verified `TransactionInfo`: [3](#0-2) 

These checkpoint hashes are exactly the state-commitment analog to the LUP recomputation bug: a value (the state root) is computed/derived elsewhere in the pipeline but the "does this recomputed value match the authenticated one" check silently omits it, so a divergence is not caught by the comparator that is supposed to be the safety net.

### Impact Explanation
`replay_on_archive` (and any other consumer of `ensure_match_transaction_info`, such as backup/restore verification flows) is a designated tool for independently re-executing historical transactions against an archive and confirming the resulting ledger state matches what was actually committed and signed off by validators. Because the state-root-bearing fields are excluded from the comparison, if execution diverges only in the state/hot-state/native-position tree (write-set hash, events, gas, and status all otherwise matching, or diverging in a way not covered), the tool reports success (`Ok(())`), incorrectly certifying that the local replay reproduces the authenticated ledger state. This directly matches the "Authenticated API or state-view output bound to the wrong version, object, or proof context" and "Committed state that differs from the correct VM result... accepted as valid" impact classes: an integrity break (corrupted/incorrect state root) can pass proof/replay verification undetected. The code's own comment flags this as a real, currently-live gap tied to `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `TRANSACTION_INFO_V1` feature rollout, i.e., this is not hypothetical — it's an acknowledged incomplete check guarding mainnet-bound state integrity of a new subsystem (native trading/position state root, hot-state root).

### Likelihood Explanation
Likelihood is tied to the feature flags in play: `TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (feature flag `122`) gate when `TransactionInfoV1` fields are actually populated/authenticated on-chain: [4](#0-3) 
Once these are enabled, any bug in the native-position/hot-state root computation path (which is new, actively-developed code per the surrounding TODOs) would not be caught by `replay_on_archive`, because the verification function that is supposed to be the last line of defense for detecting exactly this class of divergence does not check these hashes. This does not require an attacker; it's an operator/verification-tooling correctness gap that could mask a genuine consensus-vs-replay divergence (hard-fork-class bug) during audits, incident response, or automated replay-verify pipelines.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `txn_info.state_checkpoint_hash()` (against the locally computed JMT root when the transaction is a checkpoint), `txn_info.hot_state_checkpoint_hash()` (when `HOT_STATE_ROOT_IN_TXN_INFO` is relevant), and `txn_info.position_state_checkpoint_hash()` (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled), analogous to how `write_set_hash` and `event_root_hash` are already validated. Until this is done, `COMPUTE_TRADING_NATIVE_STATE_ROOTS` should not be treated as safely verifiable by `replay_on_archive`-based tooling, consistent with the TODO's own caution.

### Proof of Concept
1. Enable (or simulate) `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`TRANSACTION_INFO_V1` so `TransactionInfoV1.position_state_checkpoint_hash` is populated and committed to the accumulator on-chain.
2. Introduce (or naturally hit, via a real bug in the new native-position/hot-state root computation code) a divergence such that local replay produces the correct write set, events, gas, and status, but a different native-position/hot-state root than what was actually committed.
3. Run `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which calls `ensure_match_transaction_info` at [5](#0-4) .
4. Observe that `Ok(())` is returned — no error is raised — because the comparator never reads `position_state_checkpoint_hash`/`state_checkpoint_hash`/`hot_state_checkpoint_hash` from either side, confirming the corrupted/divergent state root is accepted as verified.

Note: I could not fully trace how/where `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` are computed during real block execution (e.g., in `execution/executor/src/workflow/do_state_checkpoint.rs`) within the available index, so I cannot confirm whether a concrete computation bug currently exists in that path — the finding here is strictly that the verification function itself has a proven, code-documented gap in what it checks, independent of whether the root-computation code is currently correct.
