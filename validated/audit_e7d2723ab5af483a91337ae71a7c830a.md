## Title
`TransactionOutput::ensure_match_transaction_info` silently skips checkpoint-hash verification, letting archive replay-verify accept a divergent state/hot-state/position state root - ([File: types/src/transaction/mod.rs])

## Summary
`TransactionOutput::ensure_match_transaction_info` is the per-transaction correctness check used by output-based replay/verify tooling to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` pulled from an (untrusted-until-verified) backup/archive. It checks status, gas used, write-set hash, and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. A backup/archive whose committed state root (or hot-state/position-state root) diverges from the true VM-computed state can pass this check as if it were fully verified.

## Finding Description
`ensure_match_transaction_info` at [1](#0-0)  compares only status, gas_used, the write-set hash against `txn_info.state_change_hash()`, and the event root hash. It never reads `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, and the function itself documents this omission: [2](#0-1) .

This is the sole verification hook invoked by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes transactions pulled from a backup and calls this function against the `expected_txn_info` read from the backup's transaction-info file: [3](#0-2) . It is also used by `aptos-debugger`'s mismatch printer: [4](#0-3) .

By contrast, the corresponding proof-verification path for `TransactionOutputListWithProof::verify` (used when consuming state-sync/API-delivered proofs) also only checks write-set hash, gas, status, event root, and transaction hash — it likewise omits the state-checkpoint hashes: [5](#0-4) . The state-checkpoint hash itself only ends up authenticated transitively via `TransactionInfo::hash()` being included in the accumulator leaf that the `AccumulatorProof`/`LedgerInfo` binds — so this omission does not break consensus-verified `TransactionInfoWithProof.verify()` (accumulator-proof paths still bind the full `TransactionInfo`, including checkpoint hashes, via its hash). However, `ensure_match_transaction_info`/`replay_on_archive` is an out-of-band **content check** (VM output vs. claimed TransactionInfo) that is explicitly relied upon as a replay-verification tool for auditing archived/backed-up chain history, independent of whether the accumulator proof itself is valid — the comment states this directly: "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

Given the newly introduced `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` features (see `types/src/on_chain_config/aptos_features.rs:203-209` and `types/src/block_executor/config.rs:173-189`), once these are enabled on-chain, the true state-integrity invariant is "committed `TransactionInfoV1.state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` equal the values the VM would deterministically produce for the same inputs." `ensure_match_transaction_info` does not enforce this invariant.

## Impact Explanation
This directly matches the "Committed state that differs from the correct VM result" and "Authenticated API or state-view output bound to the wrong version/root" bug classes from the gate: if an archived/backup ledger segment's transaction info encodes an incorrect `state_checkpoint_hash` (e.g., due to a bug elsewhere in state-checkpoint or position-state root computation, or a corrupted/tampered backup), `replay_on_archive`'s verification tool — the primary tool operators use to confirm historical ledger integrity/state root correctness before trusting or republishing a backup — will report success even though the local VM computed a different state root. This can mask a genuine consensus-breaking divergence (a state-root bug) as "verified," delaying detection of a hard fork or corrupted archived ledger data. Because `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are new, not-yet-widely-exercised features, this is exactly the kind of silent gap where a state-root computation bug could go undetected by the standard verification path.

## Likelihood Explanation
Likelihood is high for silent masking (the check is always skipped, unconditionally, whenever this codepath is used) but the trigger for actual harm requires (a) `TRANSACTION_INFO_V1` and the trading-native/hot-state features to be enabled on-chain, and (b) an actual state-root divergence bug or corrupted backup to exist. The gap itself is unconditional and already flagged by the developers as needing to be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," confirming this is a known, currently-open integrity gap in the verification tooling rather than a defense-in-depth nicety.

## Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` from `txn_info` against values recomputed locally (the state-checkpoint hashes are available in `StateCheckpointOutput` upstream of this per-transaction check and would need to be threaded through, similar to how `write_set`/`events` are passed in). At minimum, gate enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` in production until this verification gap is closed, as the code comment itself recommends.

## Proof of Concept
1. Enable `TRANSACTION_INFO_V1` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or `HOT_STATE_ROOT_IN_TXN_INFO`) on-chain.
2. Introduce (or encounter) a bug that causes the locally computed `position_state_checkpoint_hash` (or `state_checkpoint_hash`/`hot_state_checkpoint_hash`) to diverge from what is stored in a backup's `TransactionInfoV1` for some transaction (e.g. a bug in `DoStateCheckpoint::compute_position_checkpoint`, `execution/executor/src/workflow/do_state_checkpoint.rs:62-84`).
3. Run `storage/db-tool/src/replay_on_archive.rs` against that backup.
4. `Verifier::execute_and_verify` calls `ensure_match_transaction_info` (`storage/db-tool/src/replay_on_archive.rs:392-405`), which passes because it never inspects the checkpoint-hash fields, even though the actual committed ledger state diverges from local VM execution — the tool reports the replay as verified/successful.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );
