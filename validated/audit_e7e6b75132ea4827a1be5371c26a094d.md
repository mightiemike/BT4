### Title
Missing TLS Certificate Validation in Prover's Blocking-Check Client Enables MITM Bypass/Forgery of Transaction Screening - (File: crates/starknet_transaction_prover/src/blocking_check.rs)

### Summary
`BlockingCheckClient::new` unconditionally builds its `reqwest::Client` with `.danger_accept_invalid_certs(true)`, which disables TLS certificate validation entirely (not merely tolerating self-signed certs, but accepting *any* certificate, including one presented by an attacker) for the HTTPS connection used to call the external `starknet_checkTransaction` compliance/screening service. [1](#0-0) 

### Finding Description
Every call to `prove_transaction` for an Invoke V3 transaction is routed through `prove_with_blocking_check` whenever `blocking_check_url` is configured, which sends the full transaction to an external JSON-RPC service to decide whether the transaction is `Allowed` or `Blocked`. [2](#0-1) 

The HTTP client used for this call is built with `danger_accept_invalid_certs(true)` unconditionally in `BlockingCheckClient::new` — this is not gated by any operator configuration flag, it is hardcoded into the client construction path used in production (`VirtualSnosProver::new`). [3](#0-2) 

Because certificate validation is fully disabled, an attacker positioned on the network path between the prover and the configured `blocking_check_url` (e.g., the "elliptic proxy" mentioned in the code comments) can perform a Man-in-the-Middle attack and return a forged JSON-RPC response, exactly matching the bug class in GHSA-65gg-3w2w-hr4h (podman's TLS verification skip during OCI image downloads). [4](#0-3) 

Depending on the forged response, the attacker can force either outcome:
- Force `Allowed` for a transaction that the legitimate screening service would have flagged (`error.code == BLOCKED_ERROR_CODE`), causing the prover to generate a valid proof and relay a forged `additional_data` (which, per the code comments, can carry a "screening signature") for a transaction that should have been blocked.
- Force `Blocked` for a transaction that should be `Allowed`, causing legitimate, unprivileged transaction submitters' requests to be rejected with `TransactionBlocked`. [5](#0-4) [6](#0-5) 

The default policy is fail-close (`blocking_check_fail_open: false`), which underscores that this screening gate is treated as a security control the operator relies on to prevent proving of disallowed transactions, making its integrity important. [7](#0-6) 

### Impact Explanation
This vulnerability is triggerable by any transaction submitted for proving via `starknet_proveTransaction` on a deployment that enables the blocking-check feature — no special privilege is required from the transaction sender; the sender only needs to submit a transaction while an on-path attacker MITMs the prover-to-screening-service link. A successful MITM attack can:
1. Bypass compliance/screening controls, allowing a proof (and its relayed `additional_data`, e.g. a forged screening signature) to be produced for a transaction that should have been blocked — an unauthorized action bypassing the operator's intended fail-close policy.
2. Selectively censor legitimate transactions by forging `Blocked` responses, preventing the network from confirming otherwise-valid transactions from arbitrary senders.

Both outcomes constitute concrete security-relevant harm (unauthorized action / inability to confirm transactions), matching the severity class of the original CVE-2025-6032.

### Likelihood Explanation
The `danger_accept_invalid_certs(true)` call is unconditional and hardcoded — it does not depend on misconfiguration by the operator, so any deployment using the `blocking_check_url` feature is affected as soon as an attacker gains a network position between the prover and the screening endpoint (e.g., via DNS hijacking, ARP spoofing on a shared network, compromised proxy, or a rogue CA). No exploitation of the sequencer's transaction-validation logic itself is required beyond submitting an ordinary transaction to trigger the check request.

### Recommendation
Remove `.danger_accept_invalid_certs(true)` from `BlockingCheckClient::new` and use the default `reqwest` TLS validation (or, if the screening service legitimately uses self-signed certificates, add a pinned custom CA/root certificate via `reqwest::Client::builder().add_root_certificate(...)` instead of disabling verification globally).

### Proof of Concept
1. Deploy `starknet_transaction_prover` with `blocking_check_url` set to an HTTPS endpoint (e.g., `https://screening.example.com`).
2. As an attacker with a MITM network position between the prover and `screening.example.com` (e.g., ARP spoofing, compromised router, or DNS hijack), present any certificate (even self-signed, for any hostname) when the prover connects.
3. Submit an ordinary transaction via `starknet_proveTransaction`; the prover's `BlockingCheckClient` (`crates/starknet_transaction_prover/src/blocking_check.rs`) accepts the MITM'd TLS connection without validating the certificate.
4. Respond with a forged JSON-RPC body containing no `error` field (or `error.code != 10000`), causing `check_transaction` to return `Allowed`/`Inconclusive` for a transaction that the real screening service would have blocked (or vice versa, forge a `10000` error code to block a legitimate transaction).

```rust
    async fn prove_with_blocking_check(
        &self,
        client: &BlockingCheckClient,
        block_id: BlockId,
        transaction: RpcTransaction,
        invoke_tx: InvokeTransaction,
    ) -> Result<ProveTransactionResult, VirtualSnosProverError> {
        // Kick off proving in parallel with the check. Clone is cheap: inner fields are
        // Arcs or small configs.
        let prover = self.clone();
        let prove_handle =
            tokio::spawn(async move { prover.run_and_prove(block_id, vec![invoke_tx]).await });

        let timeout_duration = std::time::Duration::from_millis(client.timeout_millis);
        let check_outcome =
            tokio::time::timeout(timeout_duration, client.check_transaction(block_id, transaction))
                .await;

        // A transaction allowed via the fail-open policy (inconclusive check or
        // timeout) carries no additional_data.
        let (allow, additional_data) = match check_outcome {
            Ok(BlockingCheckResult::Blocked) => {
                info!("Transaction blocked by external check");
                (false, None)
            }
            Ok(BlockingCheckResult::Allowed(additional_data)) => {
                info!("Transaction allowed by external check");
                (true, additional_data)
            }
            Ok(BlockingCheckResult::Inconclusive) => {
                info!(fail_open = client.fail_open, "Blocking check inconclusive");
                (client.fail_open, None)
            }
            Err(_) => {
                info!(fail_open = client.fail_open, "Blocking check timed out");
                (client.fail_open, None)
            }
        };

        if !allow {
            prove_handle.abort();
            return Err(VirtualSnosProverError::TransactionBlocked);
        }
```
