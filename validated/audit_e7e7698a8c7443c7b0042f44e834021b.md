## Finding

### Title
Wallet Contract permanently absorbs relayer's attached $NEAR deposit when `rlp_execute` fails to parse the Ethereum transaction (no refund path) - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point is `#[payable]` and accepts an attached NEAR deposit from any external caller (typically a relayer forwarding an Ethereum-style transaction on behalf of an ETH-implicit account owner). When the attached transaction is well-formed enough to reach the cross-contract-call stage, a failed sub-call correctly triggers a refund of the caller's deposit via `CallerDeposit`. However, when parsing of the RLP transaction fails with a `UserError` (e.g. malformed ABI-encoded calldata, unknown function selector), `inner_rlp_execute` returns early with `Err(err)` without ever creating a refund promise for the already-tracked `caller_deposit`, and the outer `rlp_execute` converts this into a *successful* function-call outcome (`PromiseOrValue::Value(e.into())`), meaning the attached deposit is retained by the contract instead of being refunded or having any rescue mechanism.

### Finding Description
`rlp_execute` is marked `#[payable]` at [1](#0-0) , allowing any predecessor to attach a NEAR deposit when calling it. Inside `inner_rlp_execute`, `CallerDeposit::new(&context)` captures the caller's deposit for later refund [2](#0-1) , and `CallerDeposit` is only populated when the caller is external (`predecessor_account_id != current_account_id`) [3](#0-2) .

If `internal::parse_rlp_tx_to_action` fails with `Error::User(_)` (malformed/garbage ABI-encoded payload, unknown selector, etc.), the function increments the nonce and returns `Err(err)` immediately, without creating any promise to refund `caller_deposit`: [4](#0-3) . Back in `rlp_execute`, this `Err(e)` case is converted to `PromiseOrValue::Value(e.into())` [5](#0-4)  — i.e. the function call *succeeds* from the runtime's perspective (it does not panic), so the attached deposit is not returned to the caller via the protocol's automatic deposit-refund-on-failure mechanism (which only triggers for failed receipts, per `docs/RuntimeSpec/Refunds.md`).

By contrast, when a promise-based sub-call fails later in the flow, `rlp_execute_callback` explicitly creates a `promise_batch_action_transfer` refund to the tracked `caller_deposit.account_id` [6](#0-5) , showing the developers intended callers to always get their deposit back on failure — but this path is missing for early `Error::User` parse failures.

### Impact Explanation
Any unprivileged caller (relayer or any account) that calls `rlp_execute` on someone else's ETH-implicit wallet with an attached deposit and a malformed/garbage `tx_bytes_b64` payload will have that deposit permanently absorbed into the wallet contract's balance instead of refunded. There is no `rescue`/withdrawal function for such misdirected/failed-call deposits distinct from the wallet owner's own normal `Transfer` actions, so the caller has no way to recover the funds — mirroring the "Stream doesn't have ability to rescue native token" bug class (native tokens sent to a contract become effectively unrecoverable by the sender). This constitutes unauthorized value transfer: value moves from the calling relayer to the wallet owner's balance with no consent, refund, or rescue path, satisfying the required "concrete unauthorized value movement" impact bar.

### Likelihood Explanation
This is trivially reachable by any account: simply call `rlp_execute` on any ETH-implicit account (all such accounts run this same globally-deployed Wallet Contract) with any non-zero attached deposit and calldata that fails to parse as a valid Ethereum-emulated action (e.g., `UnknownFunctionSelector` or `InvalidAbiEncodedData`). No special privileges, races, or malicious infrastructure roles are required — an ordinary relayer mistake or a malicious "helper" contract inducing a bad payload from a naive relayer is sufficient to trigger the loss.

### Recommendation
In `inner_rlp_execute`, when returning early on `Err(err @ Error::User(_))` (and any other early-return error path where a non-zero `caller_deposit` exists), schedule a transfer promise refunding `caller_deposit.account_id` for `caller_deposit.yocto_near`, mirroring the refund logic already present in `rlp_execute_callback`. Alternatively, panic instead of returning a `PromiseOrValue::Value` for parse errors that occur before nonce-sensitive state changes are needed, so that the runtime's automatic deposit-refund-on-failed-receipt mechanism reimburses the caller.

### Proof of Concept
1. Deploy/derive an ETH-implicit account `A` running the global Wallet Contract.
2. As an external caller `C` (a relayer, or anyone), call `A.rlp_execute(target, tx_bytes_b64)` with `tx_bytes_b64` set to bytes that fail ABI decoding (e.g., truncated/garbage RLP or unknown 4-byte selector as covered by `tests/user_error.rs`), attaching a deposit (e.g. 3 NEAR), analogous to the existing `test_caller_refunds` setup in [7](#0-6)  but using a malformed transaction rather than an existing-recipient failure.
3. Observe: `rlp_execute` returns `success: false` (an `ExecuteResponse` value, not a panic), but `C`'s deposit is never transferred back — `A`'s balance permanently increases by the attached amount while `C` has no function to reclaim it.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
