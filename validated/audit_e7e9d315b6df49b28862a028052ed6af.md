## Title
Uncontrolled recursion in compiled-class-hash computation over attacker-supplied bytecode segmentation - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
The PostgreSQL analog is uncontrolled recursion triggered by attacker-controlled negotiation data, causing a native stack overflow and process crash. The sequencer has a directly analogous pattern: `bytecode_hash_node()`, used to compute a declared class's compiled-class-hash, recurses once per node of the `NestedIntList` bytecode-segmentation tree produced when compiling a user-submitted Sierra class, with no depth limit or explicit stack-size protection, and runs in-process (not inside the resource-limited compiler subprocess).

### Finding Description
`bytecode_hash_node` in [1](#0-0)  recurses on every non-leaf node of the `NestedIntList`/`HashableNestedIntList` bytecode-segment structure with no depth bound, no iterative rewrite, and no recursion-depth guard analogous to the one used elsewhere in the codebase for call-stack recursion (`RecursionDepthGuard` at [2](#0-1) ).

This function is invoked from `hash_inner`/`HashableCompiledClass::hash` at [3](#0-2) , which is called directly, **in-process**, by the Sierra compiler service after the Sierra→CASM compilation subprocess returns its result: [4](#0-3) 

Unlike the actual CASM compilation step, which is deliberately isolated in a subprocess with CPU-time and memory limits (`resource_limits::ResourceLimits`, see [5](#0-4) ), the subsequent hash computation over the compiler's output (`executable_class.hash(&HashVersion::V2)`) runs unsandboxed in the class-manager/compiler process itself. The `bytecode_segment_lengths` tree shape is derived from the user-submitted Sierra program's control-flow structure (functions/branches), so a class crafted with many levels of nested branches can force the compiler to emit a deeply nested `NestedIntList`, driving `bytecode_hash_node` to recurse to a depth proportional to that nesting, up to the bytecode-size limit (`max_bytecode_size`, default 81920 felts, see `sierra_compiler_config.max_bytecode_size` in [6](#0-5) ) — far beyond what a native thread stack tolerates.

This is corroborated by the codebase's own internal assumption elsewhere that segmentation nesting is normally bounded to a very shallow depth: `NestedFeltCounts::new_inner` explicitly asserts `segmentation_depth <= 1` and panics otherwise, per [7](#0-6) , showing that the depth of this structure is attacker/compiler-input controlled and not defensively bounded across all code paths that consume it.

### Impact Explanation
A crafted Sierra class submitted via a normal `DECLARE` transaction can drive the class-manager/Sierra-compiler component's native process to recurse until it overflows the stack, crashing that component (denial of service against class declaration/compilation for the sequencer), or (in the `NestedFeltCounts` path) trigger an unhandled `panic!` when converting the compiled class into `CompiledClassV1`, which is on the hot path for every declared/executed class. Either failure mode halts processing of declare transactions (and any transaction touching classes going through that conversion), i.e. a network unable to confirm new transactions of that type until the affected node/component restarts — matching the "network unable to confirm new transactions" impact criterion.

### Likelihood Explanation
Reachable directly and repeatedly by any unprivileged account submitting a `DECLARE` transaction with a specially structured Sierra program (deep nested branching) that still respects the declared-class size limits; no special privileges, timing, or race conditions are required.

### Recommendation
- Convert `bytecode_hash_node` (and the corresponding `NestedFeltCounts::new_inner`) to an iterative, explicit-stack algorithm, or add an enforced maximum segmentation-tree depth that is validated immediately after compilation and before hashing/conversion.
- Alternatively, run the post-compilation hash computation inside the same resource/stack-limited execution context as the compiler subprocess rather than in the parent process.
- Remove the unchecked `assert!(segmentation_depth <= 1)` panic path and replace it with a proper validation error returned to the caller.

### Proof of Concept
1. Construct a Sierra contract whose control-flow graph is intentionally deeply and linearly nested (e.g., thousands of sequential nested `if`/`match` branches), sized to stay under `max_bytecode_size` (81920 felts).
2. Submit it as a `DECLARE` transaction to the sequencer.
3. The Sierra-to-CASM compiler subprocess (resource-limited) successfully compiles it and returns a `CasmContractClass` whose `bytecode_segment_lengths` is a `NestedIntList` nested to a depth proportional to the crafted branch nesting.
4. `SierraCompiler::compile` then calls `executable_class.hash(&HashVersion::V2)` in-process (`crates/apollo_compile_to_casm/src/lib.rs:69`), which recurses through `bytecode_hash_node` to that same depth, overflowing the native stack and crashing the class-manager/compiler process — or, in the blockifier's `CompiledClassV1::try_from` path, hitting the `segmentation_depth <= 1` assertion and panicking.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
