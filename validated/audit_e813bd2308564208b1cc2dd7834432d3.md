Based on my investigation, I confirmed that `get_split_parent_shard_ids()` only returns the parent from the **immediately preceding** shard layout transition (for V3 layouts it's exactly `{v3.last_split}`, a single shard). This is used by `forward_from_buffer` to know which parent-shard outgoing-receipt buffers still need draining after a shard split.

### Title
Parent shard's outgoing-receipt buffer becomes permanently frozen if not fully drained within one epoch after resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
After a shard split, `ReceiptSinkV2WithInfo::forward_from_buffer` only drains outgoing-receipt buffers keyed under the *parent* shard id for the epochs where `ShardLayout::get_split_parent_shard_ids()` still names that parent as the most recent split. Once a second resharding occurs (or once the layout otherwise stops reporting that parent as `last_split`), that parent's buffer entry is silently dropped from the iteration set, even if it still holds unforwarded receipts and non-zero congestion-info bytes/gas, because there is no step in `retain_split_shard`/child congestion-info construction or in `forward_from_buffer` that reindexes or force-flushes the stale entry — this mirrors the reported bug class where `removeAdapter()` fails to pop a stale index from `withdrawSeq`, leaving state unreachable by future operations.

### Finding Description
`ShardsOutgoingReceiptBuffer` is a trie-backed map keyed by receiver `ShardId` (`core/store/src/trie/receipts_column_helper.rs:285-334`). After a shard splits, some outgoing receipts destined for the old parent id can remain in the buffer, so `forward_from_buffer_to_shard` is deliberately called for `parent_shard_ids` in addition to the current layout's shard ids: [1](#0-0) 

`parent_shard_ids` is computed once per epoch from the epoch's shard layout via `ShardLayout::get_split_parent_shard_ids()`: [2](#0-1) 

Critically, `get_split_parent_shard_ids` for `ShardLayoutV3` returns only `{last_split}` — the single most recent split parent — not the full historical set of all ancestor shards that might still have residual buffered receipts: [3](#0-2) 

The draining code itself carries an explicit acknowledged TODO confirming the buffer entry for a drained parent is never removed/reindexed, and implicitly assumes full drainage happens before the parent stops being reported: [4](#0-3) 

If the parent shard's buffer cannot be fully drained within the single epoch during which it is still recognized as `last_split` (e.g., because outgoing gas/bandwidth limits to a congested receiver throttle forwarding, per `try_forward`'s early `break` on `NotForwarded`), and then a second resharding happens (changing `last_split` to a new parent), the old parent's buffer entry keyed by the old `ShardId` is never again visited by `forward_from_buffer`. The receipts remain in trie storage under `TrieKey::BufferedReceipt { index, receiving_shard: <old_shard_id> }` forever, and the bytes/gas they represent remain permanently counted in `own_congestion_info` (via the assert at `congestion_control.rs:282-283` which would then fail congestion-info bookkeeping, or the metric leaks and the funds inside those receipts — e.g., attached deposits from `Transfer`/`FunctionCall` actions — never reach their destination).

### Impact Explanation
This causes permanently frozen/stuck receipts (and the value/deposits they carry) with no user-callable recovery path, analogous to the reported "index not popped" bug preventing further withdrawals. It is reachable purely from ordinary user activity: any account submitting cross-shard transactions/receipts that get buffered for congestion control during a resharding window can have those receipts become permanently stranded if a second resharding occurs before the first parent buffer fully drains. This matches the required impact categories ("permanently frozen funds", "receipt loss").

### Likelihood Explanation
Requires two reshardings (or repeated dynamic resharding) to occur before a congested parent-shard buffer fully drains, which is a low-frequency but expected long-term protocol event (dynamic resharding is an active production feature per `docs/architecture/how/dynamic_resharding.md`). Congestion delaying full drainage for a full epoch is plausible under sustained load. No malicious actor is required — likelihood is driven entirely by protocol operation, and any user's cross-shard receipts sent during that period are at risk.

### Recommendation
Either (a) have `forward_from_buffer` iterate and drain *all* historical parent shard ids still present in `ShardsOutgoingReceiptBuffer::shards()` (not just the immediate `last_split`/`get_split_parent_shard_ids()`), until each buffer is empty, or (b) force-migrate/merge any non-empty parent buffer into the appropriate child buffer(s) at the resharding boundary (similar to how `write_delayed_receipts` re-keys delayed receipts across the split) rather than relying on best-effort draining within a single epoch.

### Proof of Concept
1. Configure a shard layout that reshards twice within a short number of epochs (e.g., via `TestEpochConfigBuilder`, as done in `test-loop-tests/src/tests/resharding_v3.rs`).
2. During the epoch of the first split, saturate the receiver shard's congestion (drive `outgoing_gas_limit`/`bandwidth` to near zero) so that the parent shard's outgoing buffer (`ShardsOutgoingReceiptBuffer` under the old `ShardId`) cannot be fully drained by `forward_from_buffer_to_shard` before the epoch ends.
3. Trigger the second resharding so `ShardLayout::get_split_parent_shard_ids()` now returns the new parent id, no longer the original old-parent id.
4. Observe that `forward_from_buffer` in `ReceiptSinkV2WithInfo` (`congestion_control.rs:253-266`) no longer includes the original parent id in its loop, and any remaining receipts under `TrieKey::BufferedReceipt { receiving_shard: <old_shard_id> }` are never read/forwarded again, effectively freezing them and their attached deposits/gas indefinitely.

**Note on confidence**: I was not able to execute a live repro in this environment (no filesystem/terminal access), and the exact conditions under which draining fails to complete within one epoch (bandwidth/gas throttling specifics) were not fully traced end-to-end within the available search budget. This should be validated with an actual test-loop run before treating it as confirmed exploitable; the code-level gap (TODO at `congestion_control.rs:337` plus the single-generation scope of `get_split_parent_shard_ids`) is verified directly from source, but the multi-epoch, multi-resharding timing precondition is inferred rather than empirically reproduced.

    pub fn get_split_parent_shard_ids(&self) -> BTreeSet<ShardId> {
        // V3 doesn't store shards which weren't split in the map, so we can return early.
        // Using explicit match to force handling a new shard layout version when it's added.
        match self {
            ShardLayout::V0(_) | ShardLayout::V1(_) | ShardLayout::V2(_) => {}
            ShardLayout::V3(v3) => return BTreeSet::from([v3.last_split]),
        }

        let mut parent_shard_ids = BTreeSet::new();
        for shard_id in self.shard_ids() {
            let parent_shard_id = self
                .try_get_parent_shard_id(shard_id)
                .expect("shard_id belongs to the shard layout");
            let Some(parent_shard_id) = parent_shard_id else {
                continue;
            };
            if parent_shard_id == shard_id {
                continue;
            }
            parent_shard_ids.insert(parent_shard_id);
        }
        parent_shard_ids
    }
