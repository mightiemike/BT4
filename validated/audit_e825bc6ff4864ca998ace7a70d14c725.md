## Title
Session token's shop can be decoupled from the caller-supplied `shop` in `tokenExchange`, enabling cross-tenant session storage - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`shopify.auth.tokenExchange` decodes and verifies the JWT session token's *signature* but never checks that the decoded token's `dest` (the shop it was actually issued for) matches the `shop` argument supplied by the caller. The `shop` value used to build the OAuth token-exchange request, and the value used to store the resulting `Session`, is taken solely from the caller-supplied parameter — a value the library's own documentation instructs developers to source directly from the request query string rather than from the verified token payload.

### Finding Description
In `tokenExchange`, the session token is decoded purely to validate its signature/expiry; the return value is discarded: [1](#0-0) 

```ts
export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({shop, sessionToken, requestedTokenType, expiring}: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);
    ...
    const cleanShop = sanitizeShop(config)(shop, true)!;
    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`, ...);
    ...
    return { session: createSession({ ..., shop: cleanShop, ... }) };
  };
}
``` [1](#0-0) 

There is no assertion that `new URL(payload.dest).hostname === sanitizeShop(config)(shop)`. The `shop` used both to build the outbound `/admin/oauth/access_token` request and to key the returned `Session` (which the caller subsequently persists via `sessionStorage.storeSession`) is entirely decoupled from the value cryptographically bound inside the session token.

This is the direct analog of the reported ERC721 bug: the "owner" of a legitimate, verifiably-signed artifact (the session token) is able to independently set an unrelated identifying field (`shop`/"dest" vs. an attacker-chosen `shop`) that downstream code treats as authoritative, allowing the artifact's real identity/data to be spoofed relative to another one (another shop).

The library's own reference documentation reinforces the unsafe pattern by sourcing `shop` from the raw incoming request rather than from the verified token: [2](#0-1) 

```ts
app.get('/auth', async (req, res) => {
  const shop = shopify.utils.sanitizeShop(req.query.shop, true);
  ...
  await shopify.auth.tokenExchange({
    sessionToken,
    shop,
    requestedTokenType: RequestedTokenType.OfflineAccessToken,
    expiring: true,
  });
});
``` [2](#0-1) 

By contrast, the maintained framework packages (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`) do derive `shop` from the decoded token's `dest` claim before calling `tokenExchange`, e.g.: [3](#0-2) 

This inconsistency shows the safety property (shop must match the token) is enforced only by convention at each call site, not by the core `tokenExchange`/`decodeSessionToken` API itself — the same "acknowledged, it's up to the caller" pattern for which the original report was still rated Medium severity by the judge, despite the maintainer's dispute.

### Impact Explanation
If any caller of the public `shopify.auth.tokenExchange` API (including one following the package's own documented example) supplies a `shop` value from an untrusted source (e.g. `req.query.shop`) instead of the verified token's `dest`, an attacker who can obtain any valid session token from App Bridge (even for their own installed shop) can influence which shop's OAuth access-token endpoint is hit and which `shop` value is embedded in the resulting `Session` object that gets written to app-provided session storage via `sessionStorage.storeSession`. This can corrupt/poison the session storage under a shop key the attacker does not legitimately control (cross-tenant session storage injection), and causes an outbound `/admin/oauth/access_token` request with `client_secret` to be sent to an attacker-chosen host, mirroring an SSRF-adjacent, secret-disclosure-risk primitive.

### Likelihood Explanation
Exploitability is bounded by Shopify's server-side validation of the `subject_token` (session token) during actual token exchange — Shopify's own OAuth endpoint would need to accept a token whose `dest`/audience doesn't correspond to the shop being queried for this to fully succeed end-to-end. However, the client secret and subject token are transmitted to an attacker-controlled `shop` hostname regardless of whether Shopify's backend ultimately rejects the mismatched grant, and any successful or partially-successful response is persisted under the attacker-influenced `shop` key without any local consistency check. The root cause — no correlation between token `dest` and caller-supplied `shop` inside the shared library function, combined with a documented usage pattern that sources `shop` from raw request input — is concretely present and reachable from any request handler built per the documented API.

### Recommendation
Have `tokenExchange` capture the decoded payload and assert that `new URL(payload.dest).hostname` matches the sanitized `shop` parameter, throwing `InvalidJwtError` (or similar) on mismatch, rather than trusting the caller-supplied `shop` independently of the verified token. Update `docs/reference/auth/tokenExchange.md` to derive `shop` from the decoded session token instead of `req.query.shop`.

### Proof of Concept
1. App exposes `/auth` per the documented pattern, deriving `shop` from `req.query.shop` and calling `shopify.auth.tokenExchange({ sessionToken, shop, requestedTokenType })`.
2. Attacker obtains a valid, signed session token for their own installed shop `attacker-shop.myshopify.com` from App Bridge.
3. Attacker sends `GET /auth?shop=victim-shop.myshopify.com` together with the `Authorization: Bearer <attacker's token>` header (or embeds it per the app's token retrieval mechanism).
4. `tokenExchange` calls `decodeSessionToken` (which only verifies signature/`aud`, discarding the result) and then issues `POST https://victim-shop.myshopify.com/admin/oauth/access_token` using the attacker's `sessionToken` as `subject_token`, sending the app's `client_secret` to `victim-shop.myshopify.com`.
5. Regardless of Shopify's backend response, `createSession` builds and returns a `Session` with `shop: 'victim-shop.myshopify.com'`, which the app then persists via `sessionStorage.storeSession`, potentially overwriting/poisoning session data associated with `victim-shop`.
