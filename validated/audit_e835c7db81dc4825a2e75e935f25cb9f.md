### Title
DoS via Unbounded `VotesStore` Iteration in Consensus Maintenance - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
`MaintenanceManager.doMaintenance()` runs synchronously as part of every block that crosses a maintenance boundary, and it calls `countVote()`, which fully iterates the entire `VotesStore` with no size cap. Since any unprivileged, funded account can cheaply cast a `VoteWitnessContract` (a free-fee actuator that only consumes bandwidth) to insert/overwrite an entry in `VotesStore`, the number of entries processed synchronously in the consensus/block-production path is effectively attacker-influenced and unbounded. This mirrors the reported `TreasuryVester.distribute()` class of bug: an unbounded, attacker-growable list is iterated inside a core, automatically-triggered function, risking a slowdown/halt of essential protocol logic (witness reward distribution, active-witness set update) for the whole network rather than just the caller.

### Finding Description
`VoteWitnessActuator.countVoteAccount()` creates or updates one `VotesCapsule` entry in `VotesStore`, keyed by the voter's own address, whenever an account votes: [1](#0-0) 

This actuator charges no explicit fee (`calcFee()` returns `0`), so the only cost of voting is ordinary bandwidth consumption: [2](#0-1) 

Every maintenance cycle, `MaintenanceManager.doMaintenance()` calls `countVote()`, which iterates the *entire* `VotesStore` with no pagination, batching, or upper bound, then deletes each processed entry: [3](#0-2) 

`doMaintenance()` itself, plus the subsequent processing of `countWitness` (which walks `getAllWitnesses()` and `newWits`/`currentWits` multiple times), is invoked directly inside `applyBlock()`: [4](#0-3) [5](#0-4) 

`applyBlock()` is called from `DposService.applyBlock()`, which in turn is invoked from `Manager.processBlock()` — the core block-processing routine executed by every full node/witness on the block-production critical path: [6](#0-5) [7](#0-6) 

Because any account with nonzero TRON Power (obtainable via a small `FreezeBalance`/`FreezeBalanceV2`) can vote for at least 1 witness, and the entry it creates persists in `VotesStore` until the next maintenance cycle processes and deletes it, an attacker can cheaply fund a large number of accounts and have each cast a vote shortly before a maintenance boundary, maximizing the number of entries `countVote()` must iterate synchronously inside block processing.

### Impact Explanation
Unlike a per-caller self-DoS, this loop executes automatically for *every* node processing the maintenance block and gates witness reward accounting (`IncentiveManager.reward`), active witness set updates (`DposService.updateWitness`), and SR metrics — core consensus bookkeeping that affects the whole network, not just the attacker's own transaction. If the iteration becomes large enough relative to the block/consensus time budget, it can slow block production or cause block-processing timeouts at maintenance boundaries, which is a state/consensus-availability impact analogous to the referenced block-gas-limit DoS (a growable list blocking essential periodic contract/protocol logic for everyone).

### Likelihood Explanation
Likelihood is low-to-moderate: while voting itself is cheap, the attack requires funding and freezing balance on a very large number of distinct accounts and coordinating their vote transactions to land within a single maintenance epoch to maximize `VotesStore` size before it's drained by `countVote()`. There is no explicit account/entry cap enforced on `VotesStore` size, so the cost is roughly linear in the number of accounts an attacker controls, not prohibitively expensive at scale, but it does require non-trivial upfront resources (many funded accounts + freeze operations) and precise timing.

### Recommendation
Introduce a bound on the amount of `VotesStore` work performed per maintenance cycle (e.g., process voters in bounded batches across multiple blocks, or cap/rate-limit distinct voter entries processed per cycle), and/or track vote-count deltas incrementally at vote time (in `VoteWitnessActuator`) instead of doing a full-store scan in `countVote()` during consensus-critical block processing. This decouples the growth of `VotesStore` from the synchronous per-block/maintenance path.

### Proof of Concept
1. Fund `N` accounts, each freezing the minimum TRX required to obtain nonzero TRON Power.
2. Just before a maintenance boundary (`nextMaintenanceTime`), submit a `VoteWitnessContract` from each of the `N` accounts (free fee, only bandwidth cost) — see `VoteWitnessActuator.countVoteAccount()` at [1](#0-0) , which writes one `VotesStore` entry per distinct account.
3. When the maintenance-triggering block is processed, `Manager.processBlock()` → `DposService.applyBlock()` → `MaintenanceManager.doMaintenance()` → `countVote()` must iterate all `N` entries synchronously within block processing, as shown at [3](#0-2) .
4. Scaling `N` sufficiently increases the synchronous work performed inside the block-processing critical path for every node, analogous to the unbounded-recipient-list DoS in the referenced `TreasuryVester.distribute()` report.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
