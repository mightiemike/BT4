### Title
Unbounded `PendingInbounds.Walk` full-collection scan on every ballot expiry enables attacker-driven O(n²) block-processing DoS - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
The Biconomy report's bug class is "attacker appends unboundedly to a shared list; a later unrelated operation must iterate the whole list, and the resulting gas cost DoSes a legitimate participant." The nearest reachable analog in Push Chain is `BallotHooks.afterInboundBallotTerminal` in `x/uexecutor/keeper/ballot_hooks.go`, which performs a full linear `Walk` over the entire `PendingInbounds` collection every single time *any* inbound ballot reaches a terminal state (`PASSED`, `EXPIRED`, `REJECTED`), and this collection's size is directly controlled by unprivileged, permissionless external-chain deposit activity.

### Finding Description
`RecordInboundVote` (`x/uexecutor/keeper/inbound.go:27-88`) creates a new `PendingInboundEntry` in the `PendingInbounds` collections.Map the moment the *first* validator votes on any inbound (keyed by `sha256(source_chain:tx_hash:log_index)`). Any unprivileged external-chain user can trigger this by sending arbitrarily many low-value (dust) deposits through the gateway on any enabled source chain — each unique `(source_chain, tx_hash, log_index)` produces a distinct entry, and there is no cap, fee, or rate-limit on the number of simultaneously-pending inbounds tracked on Push Chain.

When any one of the resulting ballots later reaches a terminal state (e.g. it expires because it never reaches quorum, or an honest majority rejects it), `x/uvalidator`'s ballot lifecycle invokes `AfterBallotTerminal` → `afterInboundBallotTerminal` (`x/uexecutor/keeper/ballot_hooks.go:72-143`). This handler cannot reverse the one-way ballot ID, so — per the comment "the pending set is small and transient" — it does a full `h.k.PendingInbounds.Walk(ctx, nil, ...)` over *every* pending entry, scanning each entry's `Variants` slice, just to find the one entry containing the terminating ballot ID (lines 86-94).

This is structurally identical to the reported bug: `PendingInbounds` is the shared list that an attacker can push into without limit (analogous to `nftIdsStaked`), and `afterInboundBallotTerminal` is the unrelated iteration that must walk the entire list (analogous to the victim's NFT withdrawal loop). The assumption baked into the code ("pending set is small and transient") is exactly the assumption an attacker can invalidate: by flooding many small deposits from a chain with long confirmation windows (`BlockConfirmation.StandardInbound`), an attacker can keep hundreds/thousands of entries live in `PendingInbounds` simultaneously, each contributing one ballot. As those ballots begin expiring (whether from attacker-designed timing, natural expiry, or honest-validator rejection), each expiry triggers an O(n) walk over the current pending set. With `m` ballots terminating in overlapping blocks and `n` pending entries, total EndBlocker work is O(n·m), i.e. quadratic in attacker-controlled input, executed by every honest node for every block that processes ballot expiries.

### Impact Explanation
This falls under the explicitly allowed "consensus or state-machine divergence / DoS reachable from ordinary user deposits ... alone" and "denial of service only when it is not network-level and is reachable without privileged control" categories. Because the cost is paid identically and deterministically by every honest validator node during ordinary block processing (not a network-level flood), sustained growth of `PendingInbounds` degrades block production time chain-wide and, in the worst case with a sufficiently large backlog, can push processing time for a single block beyond acceptable bounds, materially slowing or stalling the chain for all users — a protocol-level DoS with no privileged actor involved.

### Likelihood Explanation
Medium-to-High. No permission, stake, or special access is required — any external-chain address that can call the gateway with a minimal or fee-only deposit can create a `PendingInbounds` entry. The cost to the attacker (source-chain gas for many dust transactions) is low relative to the O(n) cost imposed on every Push Chain validator per terminal ballot. The mitigating factor is that reaching a large backlog requires sustained volume of distinct source-chain transactions before quorum/expiry catches up, and per-inbound execution/removal happens continuously, so an attacker needs to outpace normal drain to build up a large `n`. I could not fully verify the exact ballot expiry cadence/batch size in `x/uvalidator`'s EndBlocker (i.e., how many ballots can terminate in a single block) within the available context, which affects how large `m` can practically get per block; this bounds my confidence in the precise severity multiplier.

### Recommendation
Replace the reverse lookup with a proper index instead of a full collection walk: maintain a secondary index (e.g. `collections.Map[ballotID string, utxKey string]`) populated in `RecordInboundVote` whenever a new variant/ballot is created, so `afterInboundBallotTerminal` can do a direct O(1) lookup by `ballotID` instead of walking all of `PendingInbounds`. Additionally, consider bounding the maximum number of concurrently pending inbound variants/entries (or per-source-chain rate limits) to remove the unbounded-growth precondition entirely.

### Proof of Concept
1. Attacker controls (or merely uses) an external EVM chain enabled for inbound in `x/uregistry`, with a non-trivial `StandardInbound` confirmation window.
2. Attacker submits N distinct low-value/dust gateway deposit transactions in rapid succession (each with a unique `tx_hash`/`log_index`), well before Universal Validators can confirm and reach quorum on each.
3. Universal Validators begin submitting `MsgVoteInbound` for each; `RecordInboundVote` (`x/uexecutor/keeper/inbound.go`) creates N entries in `PendingInbounds`, since votes arrive independently and each inbound event is distinct.
4. As some of these ballots reach `BlockHeightExpiry` without quorum (attacker can intentionally keep some ballots from reaching quorum, e.g. targeting a fork/format that not enough validators independently canonicalize the same way, or simply relies on natural expiry under load), `x/uvalidator` marks them expired and invokes `BallotHooks.AfterBallotTerminal` for each.
5. Each invocation of `afterInboundBallotTerminal` performs a full `PendingInbounds.Walk` over the still-large N-sized collection, so total EndBlocker work across all terminating ballots in the block scales as O(N × M), where M is the number of ballots terminating in that block — both driven by attacker-supplied volume, with zero privileged access required. func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}

func (k Keeper) RecordInboundVote(
	ctx context.Context,
	inbound types.Inbound,
	voter string,
	ballotID string,
) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	height := uint64(sdkCtx.BlockHeight())
	utxKey := types.GetInboundUniversalTxKey(inbound)

	entry, err := k.PendingInbounds.Get(ctx, utxKey)
	if err != nil && !errors.Is(err, collections.ErrNotFound) {
		return err
	}
	if errors.Is(err, collections.ErrNotFound) {
		entry = types.PendingInboundEntry{
			UtxKey:          utxKey,
			CreatedAtHeight: height,
		}
	}

	// Find or create the variant for this ballot.
	variantIdx := -1
	for i, v := range entry.Variants {
		if v.BallotId == ballotID {
			variantIdx = i
			break
		}
	}
