### Title
Adversary-crafted transaction can permanently brick block-building via unrecoverable panic in `Bouncer::try_update` weight accounting - (File: `crates/blockifier/src/bouncer.rs`)

### Summary
`Bouncer::try_update` accumulates per-transaction resource weights (`BouncerWeights`, containing `l1_gas`, `sierra_gas`, `proving_gas`, `receipt_l2_gas`, `state_diff_size`, etc.) into the block-wide running total using `checked_add(...).expect(&err_msg)`. Unlike the Zora Auction bug (where mismatched independently-computed totals caused a hard revert), here the addition of two independently-derived weight values (accumulated block weights + newly computed per-tx weights, themselves built from several independently rounded/derived sub-computations such as `total_sierra_gas`, `total_proving_gas`, `message_starknet_l1gas`, `state_diff_size`) is allowed to panic instead of gracefully erroring, if the sum overflows the underlying integer type. [1](#0-0) 

### Finding Description
`try_update` computes `tx_weights` via `get_tx_weights`, which independently derives multiple weight components (`sierra_gas`, `proving_gas`, `state_diff_size`, `l1_gas`, `receipt_l2_gas`) from different sub-calculations (VM resource costs, Casm-hash migration gas, Patricia update resources, DA gas costs, etc.), each combined with `checked_add_panic_on_overflow` or `checked_add`. [2](#0-1) 

The final step of `try_update` adds these newly computed `tx_bouncer_weights` to the block's `accumulated_weights.bouncer_weights` using:
```
let next_accumulated_weights =
    self.get_bouncer_weights().checked_add(tx_bouncer_weights).expect(&err_msg);
```
If this checked_add returns `None` (i.e., overflow of any underlying numeric field, e.g. `usize` for `l1_gas`/`state_diff_size`/`message_segment_length`, or `u64`-backed `GasAmount` for `sierra_gas`/`proving_gas`/`receipt_l2_gas`), the `.expect()` panics instead of returning a typed `TransactionExecutorError`. [3](#0-2) 

The same unwrap-on-overflow pattern is repeated in `Bouncer::update`:
```
self.accumulated_weights.bouncer_weights = self
    .accumulated_weights
    .bouncer_weights
    .checked_add(tx_weights.bouncer_weights)
    .expect(&err_msg);
``` [4](#0-3) 

Because the `Bouncer` is shared across the entire block-building lifecycle (batcher process, single instance per block, reused for successive candidate transactions as shown in the "block full" regression tests which loop `try_update` on the same shared bouncer), a panic here would unwind/abort the batcher task rather than returning a controlled error to reject only the offending transaction. This differs from a normal "transaction too large" rejection (which is handled gracefully via `TransactionExecutorError::TransactionTooLarge`), and instead crashes block production itself.

An adversary who controls transaction content (calldata size, number of storage writes/events/messages, declared classes with casm-hash migration, deep VM builtin usage, etc.) influences several of the independently-computed weight sub-components that feed into `tx_bouncer_weights`. Since accumulated block weights are already close to (but under) their configured `block_max_capacity` bound by design in normal operation, and the bound check `bouncer_config.has_room(...)` only runs *after* the `checked_add(...).expect(...)` succeeds, an attacker-crafted transaction whose weights, when added to the current accumulated weights, cross the numeric overflow boundary of the underlying primitive type (rather than merely the configured capacity) triggers the panic path instead of the intended capacity-rejection path.

### Impact Explanation
A successful panic inside `try_update`/`update` crashes (or forces recovery/restart of) the batcher/block-building task that holds the shared `Bouncer` instance for the block currently being proposed or validated. Because this code path is reachable purely from resource accounting performed on every submitted transaction during block building, a malicious but otherwise valid transaction could repeatedly crash block production, preventing the sequencer from confirming new transactions (a network-availability/DoS impact analogous to the Auction contract being permanently bricked in the referenced report — legitimate protocol flow (auction settlement / here, block building) becomes unusable until manual intervention).

### Likelihood Explanation
Likelihood depends on whether an attacker can actually construct a set of resource values (calldata length, storage writes, events, sierra/proving gas contributions, casm-hash migration costs) whose sum with the currently accumulated block weights exceeds the numeric type's maximum (`usize::MAX` / `u64::MAX`) before the configured (much smaller) `block_max_capacity` check would otherwise reject it. Given the block-level accumulators are bounded in practice by realistic `block_max_capacity` values (millions, not `u64::MAX`), reaching a true overflow of the underlying primitive requires either an implementation bug in how a single transaction's weight is computed (making a single tx's contribution enormous, e.g. via a huge casm-hash migration or corrupted state) or a bounded-input path that is not itself capped before this addition. This makes the practical likelihood moderate-to-low without further evidence of a value that can be inflated unboundedly by a single crafted transaction, but the code pattern itself — a `.expect()` panic on a resource-accounting overflow reachable from adversary-influenced transaction data — is a valid finding independent of whether every increment can reach that exact overflow boundary today.

### Recommendation
Replace the panicking `.expect(&err_msg)` calls in `Bouncer::try_update` and `Bouncer::update` (`crates/blockifier/src/bouncer.rs`) with proper error propagation (e.g., return `TransactionExecutorError::TransactionExecutionError` or a dedicated overflow variant) so that an overflow in weight accumulation results in transaction rejection rather than a process-level panic. Additionally, audit all per-component weight derivations feeding `get_tx_weights` to ensure a single transaction cannot cause a weight value large enough to overflow when added to typical accumulated block weights.

#[allow(clippy::too_many_arguments)]
pub fn get_tx_weights<S: StateReader>(
    state_reader: &S,
    executed_class_hashes: &HashSet<ClassHash>,
    n_visited_storage_entries: usize,
    tx_resources: &TransactionResources,
    state_changes_keys: &StateChangesKeys,
    versioned_constants: &VersionedConstants,
    tx_cairo_primitives_counters: &CairoPrimitiveCounterMap,
    bouncer_config: &BouncerConfig,
    receipt_l2_gas: GasAmount,
) -> TransactionExecutionResult<TxWeights> {
    let message_resources = &tx_resources.starknet_resources.messages;
    let message_starknet_l1gas = usize_from_u64(message_resources.get_starknet_gas_cost().l1_gas.0)
        .expect("This conversion should not fail as the value is a converted usize.");

    // Casm hash resources.
    let class_hash_to_casm_hash_computation_resources =
        map_class_hash_to_casm_hash_computation_resources(state_reader, executed_class_hashes)?;

    // Patricia update + transaction resources.
    let patricia_update_resources = get_patricia_update_resources(
        n_visited_storage_entries,
        // TODO(Yoni): consider counting here the global contract tree and the aliases as well.
        state_changes_keys.storage_keys.len(),
    );
    let vm_resources =
        &tx_resources.computation.total_extended_vm_resources() + &patricia_update_resources;

    // Builtin gas costs for stone and for stwo.
    let sierra_builtin_gas_costs = &versioned_constants.os_constants.gas_costs.builtins;
    let proving_builtin_gas_costs = &bouncer_config.builtin_gas_costs();

    // Casm hash migration resources.
    let migration_data = CasmHashMigrationData::from_state(
        state_reader,
        executed_class_hashes,
        versioned_constants,
    )?;
    // Total state changes keys are the sum of marginal state changes keys and the
    // migration state changes.
    let mut total_state_changes_keys = StateChangesKeys {
        compiled_class_hash_keys: migration_data.class_hashes_to_migrate.keys().cloned().collect(),
        ..Default::default()
    };
    total_state_changes_keys.extend(state_changes_keys);

    // Migration occurs once per contract and is not included in the CASM hash computation, which
    // is performed every time a contract is loaded.
    let sierra_migration_gas = migration_data.to_gas(sierra_builtin_gas_costs, versioned_constants);
    let proving_migration_gas =
        migration_data.to_gas(proving_builtin_gas_costs, versioned_constants);

    // Sierra gas computation.
    let (total_sierra_gas, casm_hash_computation_data_sierra_gas, vm_resources_sierra_gas) =
        compute_sierra_gas(
            &vm_resources,
            sierra_builtin_gas_costs,
            versioned_constants,
            tx_resources,
            sierra_migration_gas,
            &class_hash_to_casm_hash_computation_resources,
        );

    // Proving gas computation.
    let cairo_primitives_for_proving_gas = get_cairo_primitives_for_proving_gas_computation(
        patricia_update_resources.prover_builtins(),
        tx_resources.computation.os_vm_resources.prover_builtins(),
        tx_cairo_primitives_counters,
    );

    let (total_proving_gas, casm_hash_computation_data_proving_gas) = compute_proving_gas(
        &cairo_primitives_for_proving_gas,
        vm_resources_sierra_gas,
        versioned_constants,
        proving_builtin_gas_costs,
        sierra_builtin_gas_costs,
        proving_migration_gas,
        &class_hash_to_casm_hash_computation_resources,
    );

    let bouncer_weights = BouncerWeights {
        l1_gas: message_starknet_l1gas,
        message_segment_length: message_resources.message_segment_length,
        n_events: tx_resources.starknet_resources.archival_data.event_summary.n_events,
        state_diff_size: get_onchain_data_segment_length(&total_state_changes_keys.count()),
        sierra_gas: total_sierra_gas,
        n_txs: 1,
        proving_gas: total_proving_gas,
        receipt_l2_gas,
    };
