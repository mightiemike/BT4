### Title
Missing zero-weight guard in `EnergyProcessor.calculateGlobalEnergyLimit()` causes `ArithmeticException` (division by zero) when hardened resource calculation is enabled - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit()` relies on an `assert` statement (a no-op in production JVMs, since assertions are disabled by default) to guarantee `totalEnergyWeight > 0` before calling `calculateGlobalLimitV1()`, which performs a `BigInteger` division by `totalEnergyWeight`. If `totalEnergyWeight` is `0` while `allowNewReward()` is `false`, the divisor reaches the division step as zero, throwing an uncaught `ArithmeticException`. This mirrors the reported `LiquidityPool.getTransferFee()` bug class: a fee/limit calculation with an unguarded zero-denominator path.

### Finding Description
`calculateGlobalEnergyLimit()`:
```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  ...
  long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
  if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
    return 0;
  } else {
    assert totalEnergyWeight > 0;
  }
  if (hardenCalculation()) {
    return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
  }
  ...
}
``` [1](#0-0) 

`calculateGlobalLimitV1()` performs an unguarded `BigInteger` division:
```java
protected long calculateGlobalLimitV1(long frozeBalance, long totalLimit, long totalWeight) {
  long weight = frozeBalance / TRX_PRECISION;
  return BigInteger.valueOf(weight)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(totalWeight))
      .longValueExact();
}
``` [2](#0-1) 

The guard `if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) return 0;` only short-circuits when the `allowNewReward` hard-fork flag is active. When it is not active, the code falls through to `assert totalEnergyWeight > 0`, which is compiled out at runtime unless the JVM is started with `-ea` (not the default for production nodes). No explicit `if (totalEnergyWeight == 0) return 0;` exists here, unlike the sibling implementations:
- `EnergyProcessor.calculateGlobalEnergyLimitV2()` explicitly checks `if (totalEnergyWeight == 0) { return 0; }` [3](#0-2) 
- `BandwidthProcessor.calculateGlobalNetLimit()` explicitly checks `if (totalNetWeight == 0) { return 0; }` in addition to the `allowNewReward` check [4](#0-3) 

This asymmetry indicates the guard was forgotten specifically in `calculateGlobalEnergyLimit()` (the V1/legacy path), leaving an unguarded division-by-zero when `totalEnergyWeight` is `0` and the `allowNewReward` hard fork is not yet active.

### Impact Explanation
`calculateGlobalEnergyLimit()` is invoked from `EnergyProcessor.useEnergy()` and `getAccountLeftEnergyFromFreeze()`, which are called on the hot path for every smart-contract transaction's energy accounting (via `ReceiptCapsule` energy billing and `VMActuator`/`RepositoryImpl` energy-limit computations during TVM execution). [5](#0-4) [6](#0-5) 

If `totalEnergyWeight` is `0` (e.g., no accounts have frozen balance for energy — plausible on a freshly bootstrapped chain, private/test network, or after a wide-scale unfreeze event) and `hardenCalculation()`/`allowHardenResourceCalculation()` is enabled while `allowNewReward()` is not, any `TriggerSmartContract` transaction processed by any node will throw an uncaught `ArithmeticException` during transaction execution/energy billing. This is a broadcast-reachable, protocol-implementation bug that can cause block processing failures or node crashes — a DoS on transaction/block processing (consensus-affecting availability issue), not merely a caught, recoverable exception.

### Likelihood Explanation
The trigger condition requires: (1) `allowHardenResourceCalculation()` enabled (a deployed hard-fork/feature flag), (2) `allowNewReward()` not yet active, and (3) `totalEnergyWeight == 0`. Condition 3 is realistic on new/private networks or test environments before any account has frozen TRX for energy, and combinations of hard-fork flags being independently toggled are plausible during staged rollouts. This is a narrower window than the original LiquidityPool bug (which triggers on ordinary "no liquidity" states), so likelihood is moderate rather than high.

### Recommendation
Add an explicit zero-weight guard identical to the one already present in `calculateGlobalEnergyLimitV2()` and `BandwidthProcessor.calculateGlobalNetLimit()`:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
before the `hardenCalculation()` branch in `calculateGlobalEnergyLimit()`, removing reliance on the runtime-disabled `assert` statement.

### Proof of Concept
1. Configure/observe a node state where `dynamicPropertiesStore.getTotalEnergyWeight() == 0` (no frozen-for-energy balances recorded) and `allowNewReward()` returns `false`, while `allowHardenResourceCalculation()` is enabled.
2. Broadcast any `TriggerSmartContract` transaction against a deployed contract.
3. Transaction processing invokes `EnergyProcessor.useEnergy()` → `calculateGlobalEnergyLimit()` → (assert is a no-op) → `calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, 0)` → `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`, uncaught by the surrounding contract-validate/execute try/catch blocks that only handle `ContractValidateException`/`AccountResourceInsufficientException`, resulting in a runtime crash of transaction processing for that node.

**Note:** I was unable to fully trace and confirm every runtime configuration path where `allowNewReward()` could realistically be `false` while `allowHardenResourceCalculation()` is `true` on live mainnet (this depends on the exact hard-fork rollout ordering encoded in `ForkController`/`ConfigLoader`, which I did not have time to fully verify). If a background agent investigates further, it should confirm the exact hard-fork activation ordering to determine whether this state is actually reachable on mainnet or only on test/private/new networks.
