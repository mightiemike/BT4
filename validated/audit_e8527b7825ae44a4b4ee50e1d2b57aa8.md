### Title
Sequencer removes fetched deposits from `DepositDataMempool` even when `process_sys_txs` reverted them - ([File: crates/sequencer/src/runner.rs])

### Summary
`CitreaSequencer::produce_l2_block_inner` fetches a batch of pending deposits, threads it through `dry_run_transactions` → `produce_and_run_system_transactions` → `process_sys_txs`, and after block production calls `remove_deposits(&deposit_data)` using the *original, unfiltered* fetched batch. `process_sys_txs` silently reverts and skips (`continue`s) any deposit whose system transaction fails with `EvmSystemTransactionNotSuccessful`, excluding it from the produced block, but that failed deposit's raw bytes remain in the `deposit_data` slice that is later passed to `remove_deposits`, so it is permanently dropped from the mempool despite never having a successful `BridgeContract.deposit()` recorded on-chain.

### Finding Description
The claimed binding is:
`deposit set removed via DepositDataMempool::remove_deposits(&deposit_data)` == `deposit set that actually executed BridgeContract.deposit() successfully in the produced block`.

Tracing the code shows this binding is broken:

1. `produce_l2_block_inner` fetches deposits without removing them yet: `let deposit_data = self.deposit_mempool.lock().fetch_deposits(...)` [1](#0-0) .
2. The same unfiltered `deposit_data` reference is passed into `dry_run_transactions`, which builds `SystemEvent::BridgeDeposit` events from it and runs them through `process_sys_txs` [2](#0-1) .
3. Inside `process_sys_txs`, when applying a deposit system tx fails with `StateTransitionError::ModuleCallError(L2BlockModuleCallError::EvmSystemTransactionNotSuccessful)` and `is_deposit` is true, the code reverts the working set, decrements the sovereign nonce, and `continue`s the loop without recording that this specific deposit failed — it is simply omitted from `all_txs` [3](#0-2) .
4. After the block is produced and saved, the sequencer unconditionally removes the *entire original fetched batch* from the mempool: `self.deposit_mempool.lock().remove_deposits(&deposit_data)` [4](#0-3) . There is no filtering step that excludes deposits that were reverted in step 3 — `deposit_data` at this point is the same variable fetched in step 1, not the list of deposits that actually succeeded.
5. `DepositDataMempool::remove_deposits` removes any deposit in the passed slice from both `accepted_deposit_txs` and `pending_deposits` purely by matching `calc_tx_id`, with no on-chain success check [5](#0-4) .

This is deterministically reproducible: the existing unit test already demonstrates a deposit deterministically returning `EvmSystemTransactionNotSuccessful` (e.g., malformed input count) [6](#0-5) , confirming that any deposit whose `BridgeContract.deposit()` call reverts at block-build time — whether due to malformed data, a reverting recipient contract, or (as posed) attacker-engineered state that differs between the `eth_call` simulation performed by `citrea_sendRawDepositTransaction` at submission time and the state at actual block-build time — hits this exact code path.

One caveat on the specific griefing mechanism proposed in the prompt: system events (including `BridgeDeposit`) are applied by `produce_and_run_system_transactions`/`process_sys_txs` *before* the ordinary EVM transaction loop begins in `dry_run_transactions` (system txs are processed first, then `while let Some(evm_tx) = transactions.next()` runs) [7](#0-6) [8](#0-7) . Therefore an attacker's *own ordinary tx in the same block* cannot execute before the deposit system tx to flip state and induce the revert; that specific same-block reordering premise is factually incorrect. The equivalent effect is however achievable by flipping the recipient's contract state via an ordinary tx in an *earlier* block (before the sequencer fetches/includes the deposit), since the RPC-time `eth_call` simulation (`BlockId::pending`) and the actual block-build execution can be separated by any number of blocks while the deposit sits in the mempool [9](#0-8) . The unconditional-removal bug itself is independent of this exact griefing vector and triggers for any deposit that reverts for any reason at block-build time.

### Impact Explanation
A deposit that reverts during `process_sys_txs` never mints cBTC, but is nonetheless struck from `DepositDataMempool` as if it succeeded. The underlying Bitcoin deposit's `pending_deposits` tracking is lost, requiring the depositor (or anyone with the raw deposit bytes) to notice the failure and manually resubmit via `citrea_sendRawDepositTransaction`. If whatever condition caused the revert is repeatable at will (an attacker-controlled recipient contract, or a griefer who can always re-flip state before each retry is fetched into a block), resubmission can be made to fail every time, leaving BTC locked with no path to mint cBTC through this mechanism — matching the "funds permanently frozen" Critical category. The blast radius is per-deposit and per-block; it can affect any depositor whose chosen recipient contract can legitimately or maliciously revert between RPC-simulation time and block-build time, not just self-targeted attacker deposits.

### Likelihood Explanation
The attacker only needs unprivileged capabilities already in scope: call `citrea_sendRawDepositTransaction` with a deposit blob targeting a contract they control, and send ordinary EVM transactions to toggle that contract's behavior. No sequencer, prover, or DA privilege is required. The failure path (`EvmSystemTransactionNotSuccessful` on a deposit) is already exercised deterministically by existing tests, so triggering it is trivial; the only extra step is timing the state flip so it lands before the deposit's eventual inclusion, which is fully within an unprivileged attacker's control given deposits can sit in the mempool for multiple blocks before being fetched.

### Recommendation
Track which deposits in the fetched batch actually succeeded during `process_sys_txs` (e.g., return a `Vec<Deposit>` of only the deposits whose system tx did not hit the `EvmSystemTransactionNotSuccessful`/`is_deposit` revert branch) and pass only that successful subset to `remove_deposits` in `produce_l2_block_inner`, instead of the full unfiltered `deposit_data` fetched at the start of the block.

### Proof of Concept
```
cargo test -p citrea-sequencer -- deposit_removed_without_success
```
Test plan:
1. Deploy a recipient contract with a toggle (`setReject(bool)`), initially `false`.
2. Call `citrea_sendRawDepositTransaction` with a deposit blob targeting this contract; assert it passes `eth_call` and is added to `DepositDataMempool` (`pending_deposits` contains its `calc_tx_id`).
3. Send an ordinary tx calling `setReject(true)` and let it land in an earlier block.
4. Drive `CitreaSequencer::produce_l2_block_inner` (or directly `process_sys_txs` with a `BridgeDeposit` event for this blob) so the deposit's system tx reverts with `EvmSystemTransactionNotSuccessful`.
5. Assert both sides of the binding: (a) no `BridgeContract.deposit()` success recorded — recipient balance/mint event absent; (b) `DepositDataMempool::pending_deposits` no longer contains the deposit's `calc_tx_id` after `produce_l2_block_inner` returns, because `remove_deposits(&deposit_data)` was called with the unfiltered fetched batch — demonstrating the mismatch between "removed from mempool" and "successfully applied on-chain."

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });
