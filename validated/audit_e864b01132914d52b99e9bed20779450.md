## Finding

### Title
`liquidate-multi` swallows a failed bad-debt socialization inside `liquidate`, letting already-executed debt-repayment and collateral-seizure state persist while the error is silently discarded - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` calls the public function `liquidate` via a bare (non-`contract-call?`) private helper `call-liquidate`, collecting results with `map` instead of propagating failures with `try!`. Inside `liquidate`, the bad-debt socialization step (a `fold` over `socialize-debt-asset`) can fail *after* the debt repayment and collateral seizure have already been committed via `contract-call?` to `.v0-market-vault`. Because the failure is only surfaced as an `(err ...)` element inside the list returned by `liquidate-multi`, and `liquidate-multi` itself still returns `(ok ...)`, the whole transaction commits - stranding the already-executed collateral/debt state changes for that borrower while the required bad-debt write-down never happens.

### Finding Description
In `mainnet/contracts/market/v0-4-market.clar`, `liquidate` performs its state-changing steps in this order:
1. All health/eligibility `asserts!` (lines 1488-1493).
2. `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` (line 1496) - pulls tokens from the liquidator and repays the vault.
3. `(try! (contract-call? .v0-market-vault debt-remove-scaled ...))` (line 1499) - removes the borrower's debt obligation.
4. `(try! (contract-call? .v0-market-vault collateral-remove ...))` (line 1506) - seizes the borrower's collateral and sends it to the receiver.
5. Only *after* steps 2-4 have already committed, if `no-collateral-left` is true, a `fold` over `socialize-debt-asset` attempts to write down any remaining bad debt (lines 1544-1548), and `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` (line 1548) can abort `liquidate` with an error.

Each `contract-call?` in steps 2-4 is a genuine cross-contract call to `.v0-market-vault`; once it returns `(ok ...)`, its state effects are only rolled back if the ultimate top-level transaction itself returns `(err ...)`. When `liquidate` is invoked directly (as the top-level transaction), an error at step 5 does cause the whole transaction (and thus steps 2-4) to roll back correctly.

However, `liquidate-multi` (lines 1593-1599) invokes `liquidate` indirectly through `call-liquidate` (lines 907-918), a private helper that calls `liquidate` as a bare function (not `contract-call?`) and returns its raw response. `liquidate-multi` then does `(ok (map call-liquidate positions))` - `map` collects every result (whether `ok` or `err`) into a list without short-circuiting, and the outer function still returns `(ok ...)`. Because the *outermost* transaction returns `ok`, Clarity's rollback rule (tied strictly to the outermost transaction's result) does not fire, even though one element of the mapped list is an `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`. All state changes made by that specific `liquidate` call before its internal failure - the vault-system-repay transfer, `debt-remove-scaled`, and `collateral-remove` (i.e., collateral already sent to the receiver and the corresponding scaled debt already erased) - persist, while the corresponding required socialization of any remaining bad debt on other assets is skipped entirely.

This is the same bug shape as the SwapRouter report: a multi-step operation performs and commits partial value-moving effects up front, then a later step can fail, but the entry point (batch wrapper) absorbs that failure instead of reverting, permanently stranding/mismatching value relative to bookkeeping.

### Impact Explanation
Skipping bad-debt socialization while still recording the debt-repay/collateral-seizure as done means the vault's internal accounting (`total-assets`/`principal-scaled`) is never written down for the un-socialized remaining debt of a borrower left with zero collateral. That debt keeps inflating the vault's recorded assets/share price even though it can never be recovered from the (now collateral-less) borrower, misstating redeemable value for all vault depositors - a form of protocol insolvency that is silently introduced through the batch path, which the single-call `liquidate` path does not have (there, the same failure would correctly revert everything).

### Likelihood Explanation
Reaching `no-collateral-left` with `remaining fresh-debt-list` and having `socialize-debt-asset` fail on at least one remaining asset (e.g., that asset's own `vault-socialize-debt` or `debt-remove-scaled` cross-call failing) is a real, reachable code path in ordinary graduated/partial liquidations of multi-asset positions, and any liquidator can trigger it simply by calling `liquidate-multi` with such a position instead of `liquidate` directly.

### Recommendation
`liquidate-multi` should not use `map`+bare function calls to swallow errors from a function whose failure path performs irreversible-if-uncaught side effects. Either:
- Invoke each position's liquidation via `(as-contract? ... (contract-call? .v0-market-vault ...))`-style isolated sub-call (i.e. use `contract-call?` to itself, `(contract-call? .v0-4-market liquidate ...)`, so each position gets its own atomic rollback boundary independent of the others), or
- Restructure `liquidate` so the bad-debt socialization check happens strictly before any of the debt-repay/collateral-seizure mutations (fail-fast, mirroring the existing `asserts!` block), so a later socialization failure can never leave earlier mutations committed regardless of how the caller aggregates results.

### Proof of Concept
1. Borrower has a graduated-liquidatable position with two debt assets (`debt-aid` A and `debt-aid` B) and only enough collateral to fully cover the seized amount for asset A, leaving zero collateral remaining (`no-collateral-left` = true).
2. Liquidator calls `liquidate-multi` with a single position targeting debt asset A.
3. Inside `liquidate`: `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` for asset A all succeed and commit (real STX/token transfers, real obligation-map mutations via `contract-call? .v0-market-vault`).
4. `no-collateral-left` is true; the `fold` over `socialize-debt-asset` attempts to write down asset B's leftover debt but one of its internal `contract-call?`s (e.g., `vault-socialize-debt` or `debt-remove-scaled` for asset B) fails, so `socialization-result.success` is `false`.
5. `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` fires, and `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.
6. `call-liquidate` returns this err value; `map` places it in the result list; `liquidate-multi` returns `(ok (list (err ERR-BAD-DEBT-SOCIALIZATION-FAILED)))`.
7. The overall transaction commits: the liquidator has already received borrower's asset-A collateral and the borrower's asset-A debt is erased, but the borrower's asset-B debt (now fully unsecured) is never socialized, permanently distorting `.v0-market-vault`'s recorded total-assets/debt for asset B. (define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))

            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
