### Title
Pre-fork signature-malleability double-count in `TransactionCapsule.checkWeight` inflates multisig weight - (File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java)

### Summary
Before the `VERSION_4_7_1` fork is active, `checkWeight` deduplicates signatures by their base64-encoded `(r, s, v)` bytes rather than by the recovered signer address, so a single key's two ECDSA-malleable signatures (`s` and `SECP256K1N - s` with flipped `v`) over the same hash are treated as two distinct entries and their weights are summed. After the fork this is fixed by keying on the recovered address instead.

### Finding Description
`TransactionCapsule.checkWeight` builds a dedup map `addMap` keyed differently depending on fork status: [1](#0-0) 

For each signature it computes `base64 = getBase64FromByteString(sig)`, which goes through `Rsv.fromSignature` and `ECDSASignature.fromComponents(...).toBase64()`: [2](#0-1) 

`Rsv.fromSignature` merely slices `r`, `s`, `v` out of the raw 65-byte signature with no canonicalization of `s`: [3](#0-2) 

It then computes `address = SignUtils.signatureToAddress(hash, base64, ...)`. Only *after* computing the address does the code branch on fork status:

```java
if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
  base64 = encode58Check(address);
}
if (addMap.containsKey(base64)) { throw ... }
addMap.put(base64, weight);
```

- **Pre-fork**: `base64` remains the raw signature encoding. Since a valid ECDSA signature `(r, s)` and its malleable twin `(r, n-s)` with the correspondingly flipped recovery id both recover to the *same* address/public key (standard secp256k1 malleability), but their `s`/`v` bytes differ, `getBase64FromByteString` yields two different strings for the same signer. `addMap` therefore does not detect the duplicate, and both entries' weights are summed into `currentWeight`.
- **Post-fork**: `base64` is overwritten with `encode58Check(address)`, so both the original and the malleable twin key to the identical map entry and the second one triggers `"... has signed twice!"`.

This function is reachable from real transaction-processing paths: `addSign`/`validateSignature` (used during signing and block/transaction validation) and `Wallet.getTransactionSignWeight` / `getTransactionApprovedList` (public API endpoints), all of which call `checkWeight` with attacker-supplied signature lists. [4](#0-3) [5](#0-4) 

### Impact Explanation
For an Active permission with `threshold >= 2` and keys of weight 1 each, an attacker controlling only one of the required private keys can derive the malleable twin of their own signature and submit `[sig, malleable-twin(sig)]`. Pre-fork, `checkWeight` returns `currentWeight = 2 * weight` instead of `weight`, satisfying a threshold that should have required a second, independent signer. This allows execution of a transaction/contract call under that `permissionId` (e.g., transfer or TVM call) with fewer real distinct signers than the multisig policy requires — a genuine authorization bypass, but only while the chain has not yet activated `VERSION_4_7_1`.

### Likelihood Explanation
The flaw is deterministic and trivially reproducible given: (1) the target account has a multisig Active permission with `N >= 2` keys, and (2) the network's `ForkController` has not yet passed `VERSION_4_7_1`. The attacker needs no special privileges — just one of the account's private keys and the ability to submit signatures via `addSign`/broadcast. However, `VERSION_4_7_1` is a network-wide hard-fork toggle controlled by chain governance/witness voting, not by the attacker; on any network where this fork has already activated (the intended target state for current mainnet-derived chains), the address-keyed dedup fully blocks this attack. The exploit window is therefore limited to chains/environments that remain pre-fork.

### Recommendation
Always key `addMap` by the recovered signer address (or a canonicalized signature form) regardless of fork status, i.e., remove the fork gate and unconditionally do `base64 = encode58Check(address)` before deduplication, or canonicalize `s` to the low-S form in `Rsv.fromSignature`/`ECDSASignature.fromComponents` before deriving `base64`. Since this is exactly what the post-fork branch already does, the safest fix is simply making that behavior unconditional (which also simplifies the code and removes the historical fork check entirely, since the fork should already be permanently active on all supported networks).

### Proof of Concept
```java
// framework/src/test/java/.../ChecksWeightMalleabilityTest.java
@Test
public void testMalleableTwinDoubleCountsPreFork() throws Exception {
  // 1. Build account with Active permission: threshold=2, keys=[key1(w=1), key2(w=1)]
  // 2. Build tx, compute hash = getTransactionId().getBytes()
  // 3. sig1 = key1.sign(hash) via ECKey -> 65 bytes (r|s|v)
  // 4. Derive malleable twin:
  byte[] r = Arrays.copyOfRange(sig1, 0, 32);
  BigInteger s = new BigInteger(1, Arrays.copyOfRange(sig1, 32, 64));
  BigInteger sTwin = ECKey.CURVE.getN().subtract(s); // SECP256K1N - s
  byte vOrig = sig1[64];
  byte vTwin = (byte) (vOrig == 27 ? 28 : (vOrig == 28 ? 27 : (vOrig == 0 ? 1 : 0)));
  byte[] sigTwin = concat(r, bigIntTo32Bytes(sTwin), new byte[]{vTwin});

  // sanity: both recover to key1's address
  assertArrayEquals(key1.getAddress(),
      ECKey.signatureToAddress(hash, base64Of(sig1)));
  assertArrayEquals(key1.getAddress(),
      ECKey.signatureToAddress(hash, base64Of(sigTwin)));

  // Pre-fork (ForkController not passing VERSION_4_7_1):
  long weightPre = TransactionCapsule.checkWeight(
      permission, Arrays.asList(ByteString.copyFrom(sig1), ByteString.copyFrom(sigTwin)),
      hash, new ArrayList<>());
  assertEquals(2, weightPre); // BUG: should be 1 (one real signer), reaches threshold=2

  // Post-fork (simulate ForkController.instance().pass(VERSION_4_7_1) == true):
  long weightPost = TransactionCapsule.checkWeight(
      permission, Arrays.asList(ByteString.copyFrom(sig1), ByteString.copyFrom(sigTwin)),
      hash, new ArrayList<>());
  // expected: throws PermissionException("... has signed twice!")
}
```
Expected result: pre-fork assertion shows `currentWeight == 2` (threshold met with one real signer, confirming the bug); post-fork call throws `PermissionException` (confirming the existing fix is effective once the fork is active).

  public static Rsv fromSignature(byte[] sign) {
    byte[] r = Arrays.copyOfRange(sign, 0, 32);
    byte[] s = Arrays.copyOfRange(sign, 32, 64);
    byte v = sign[64];
