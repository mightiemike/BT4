### Title
Unbounded, dust-value inbound events force permanent `UniversalTx`/UEA storage growth at near-zero attacker cost - (File: `x/uexecutor/types/inbound.go`, `x/uexecutor/keeper/msg_vote_inbound.go`, `x/uexecutor/keeper/evm.go`)

### Summary
`Inbound.ValidateForExecution` only rejects a **zero** amount for `FUNDS`/`GAS` tx types; there is no minimum-value floor analogous to HydraDX's `MinimumPoolLiquidity`. Any externally-observable gateway deposit of `amount = 1` (the smallest positive integer) on a whitelisted source chain passes validation, is honestly voted in by Universal Validators, and causes the core validator to permanently persist a `UniversalTx` record and (on first use of a given origin) pay for a brand-new UEA contract deployment on the Push Chain EVM — all funded by the protocol/module account, not the attacker.

### Finding Description
`Inbound.ValidateForExecution` in [1](#0-0)  enforces only that the amount is a valid non-negative uint256 and, for `FUNDS`/`GAS`, strictly positive — there is no lower bound tied to economic value (e.g., no per-token minimum comparable to `TokenConfig.LiquidityCap`, which is only an upper bound, per [2](#0-1) ).

`VoteInbound` unconditionally creates a `UniversalTx` the moment quorum is reached, regardless of the size of the deposit, and the module's own documentation states the record is retained forever: "One UTX is created per observed inbound and lives forever (it is never deleted, only mutated as new pieces of evidence arrive)" per [3](#0-2) . The creation path is in [4](#0-3) .

When the recipient's UEA has not yet been deployed for a given `(chainNamespace, chainId, owner)` triple, execution automatically deploys one via a `DerivedEVMCall` issued by the module account (`CallFactoryToDeployUEA`), e.g. in `ExecuteInboundFunds`-style flows such as [5](#0-4)  and [6](#0-5) , with the underlying call defined at [7](#0-6) . Per the module's design notes, "even though the protocol pays the gas, the tx receipt still needs `gas_used` populated," confirming the EVM execution cost of this deployment is borne by the protocol, per [8](#0-7) .

Because the UEA address is derived deterministically from `(chainNamespace, chainId, owner)` — i.e., from the source-chain sender address — an attacker can generate an unlimited number of fresh, cost-free source-chain keypairs and send a `1`-wei/unit deposit from each. Each such deposit:
1. Is truthfully observed and voted by honest UVs (no malicious validator assumption required).
2. Passes `ValidateForExecution` (amount > 0 is satisfied).
3. Triggers a brand-new UEA deployment (new EVM contract storage, permanent) the first time that origin is seen.
4. Creates a permanent `UniversalTx` entry, keyed by `sha256(sourceChain:txHash:logIndex)`, that per design is never deleted.

The attacker's cost is bounded by the source-chain gas fee plus one unit of the bridged token; the protocol's cost includes a full UEA contract deployment (EVM storage) and an immortal `UniversalTx` record, mirroring the HydraDX pattern of a storage-write cost that is orders of magnitude below the resource actually consumed by the chain.

### Impact Explanation
This allows an unprivileged external-chain user to force Push Chain's core validator to grow `UniversalTx` storage and deploy EVM contracts indefinitely at negligible cost, without any privileged or malicious-validator assumption. Over time this degrades node storage/state-sync costs and EVM state size, a state-safety/DoS impact reachable purely from ordinary unprivileged user deposit flows, consistent with the in-scope "denial of service ... reachable without privileged control" category.

### Likelihood Explanation
Likelihood is high: the only requirement is generating disposable source-chain addresses (free) and sending trivially small deposits of a whitelisted token (bounded only by source-chain gas), which is standard, expected traffic pattern from the protocol's point of view and requires no validator collusion or admin/governance interaction.

### Recommendation
Introduce a minimum-value floor for inbound execution, analogous to `MinimumPoolLiquidity` in the HydraDX report — e.g., a per-token `MinInboundAmount` field on `TokenConfig` (mirroring the existing `LiquidityCap` upper bound) enforced in `Inbound.ValidateForExecution` alongside the existing zero-amount check, so than dust amounts are rejected with a `FAILED` PCTx/revert before any UEA deployment or permanent `UniversalTx` write is committed for that variant. Alternatively, decouple UEA deployment from dust deposits (e.g., require a minimum balance before auto-deploying) as is already partially done for `ExecutePayload`'s pre-funded auto-deploy check in [9](#0-8) , but that guard does not exist in the inbound-vote execution paths.

### Proof of Concept
1. Register a whitelisted token config with no minimum-amount restriction (current default), e.g. as in [10](#0-9) .
2. From a fresh, disposable source-chain address, emit a gateway deposit event with `Amount = "1"` for `TxType_FUNDS`.
3. Have the (honest) Universal Validators vote it via `MsgVoteInbound` to quorum — validation passes since only `amount == 0` is rejected, per [11](#0-10) .
4. Observe: a new UEA is deployed for that origin (`ExecuteInboundFunds`/`ExecuteInboundGas` paths call `DeployUEAV2`), and a permanent `UniversalTx` entry is created that is never pruned.
5. Repeat with a new disposable address; each repetition costs the attacker ~1 unit of token + source-chain gas, while the protocol pays for a new EVM contract deployment and permanent storage entry each time.

```go
func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}
```

```go
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token contract address cannot be empty")

		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token address for chain %s: %s", p.Chain, err)
	}

	if strings.TrimSpace(p.Name) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token name cannot be empty")
	}

	if strings.TrimSpace(p.Symbol) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token symbol cannot be empty")

		return errors.Wrap(sdkerrors.ErrInvalidRequest, "decimals must be greater than zero")
```

```go
// CallFactoryToDeployUEA deploys a new UEA using factory contract
// Returns deployment response or error if deployment fails
func (k Keeper) CallFactoryToDeployUEA(
	ctx sdk.Context,
	from, factoryAddr common.Address,
	universalAccount *types.UniversalAccountId,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: deployUEA",
		"factory", factoryAddr.Hex(),
		"chain_namespace", universalAccount.ChainNamespace,
		"chain_id", universalAccount.ChainId,
		"owner", universalAccount.Owner,
	)

	abi, err := types.ParseFactoryABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse factory ABI")
	}

	abiUniversalAccount, err := types.NewAbiUniversalAccountId(universalAccount)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal account")
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,        // who is sending the transaction
		factoryAddr, // destination: FactoryV1 contract
		big.NewInt(0),
		nil,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"deployUEA",
		abiUniversalAccount,
	)
}
```

```markdown
## The `gasless` Flag

`gasless=true` tells the fork: "this call is part of internal protocol bookkeeping, don't bill any account for the gas." Right now, every Push Chain call site passes `gasless=false`, with the inline comment:

> `// gasless = false (@dev: we need gas to be emitted in the tx receipt)`

The reason: even though the protocol pays the gas, the tx receipt still needs `gas_used` populated so off-chain services (Universal Validators, explorers, the gas-fee accounting in `x/uexecutor`) can read it back. Setting `gasless=true` would suppress the gas field and break that read path.

The flag exists for future use — protocol housekeeping calls that don't need to be observable via receipts (e.g. genesis-time bytecode patches). For day-to-day inbound/outbound execution, `gasless` stays `false`.
```
