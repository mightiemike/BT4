## Title
Unbounded iteration over the full (non-active) witness set enables governance/consensus-cycle cost inflation - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
The external report describes `for` loops in a governance contract that are bounded by an actor-controlled set (trusted nodes / proposal candidates) with no on-chain maximum, risking gas-limit exhaustion. The closest reachable analog in java-tron is the set of loops that iterate over **all registered witnesses** (`WitnessStore.getAllWitnesses()`), not just the 27/127 *active* super representatives. Becoming a witness (`WitnessCreateContract`) is a permissionless action gated only by a fixed TRX fee, so the size of this list is not capped on-chain, mirroring the reported bug class of "loop bound variable expected to stay small but unenforced."

### Finding Description
`MaintenanceManager.doMaintenance()` iterates `consensusDelegate.getAllWitnesses()` (the entire witness registry, not the elected/active set) multiple times per maintenance cycle: [1](#0-0) [2](#0-1) [3](#0-2) 

`Wallet.getPaginatedNowWitnessList` similarly loads and sorts the *entire* witness list before pagination: [4](#0-3) 

Any account can register as a witness via `WitnessCreateActuator`, which — like `Inflation`'s "winners" or `PolicyVotes`'s "candidate proposals" in the report — is intended to stay small (the protocol design assumes on the order of ~127 witnesses) but has no cap enforced by the create-witness path itself beyond a flat fee. This matches exactly the reported bug class: "these variables are supposed to be small... but there is nothing in the contracts... that enforces a maximum value."

### Impact Explanation
If the number of registered witnesses grows very large (an attacker repeatedly pays the create-witness fee from many accounts), every maintenance cycle (`doMaintenance`, run once per epoch as part of block production) does O(n) to O(n log n) work over the full witness set — several `forEach`/iteration passes plus a sort in `WitnessStore.sortWitnesses`. This increases the CPU/time cost of block production at each maintenance boundary, and the same unbounded list is read by the public `getPaginatedNowWitnessList` wallet/API RPC, which sorts the entire list on every call. In the worst case this degrades node/consensus performance (denial-of-service risk to block production timing) rather than causing fund loss — an "invalid-state/halt"-class impact per the report's the DoS root cause (unbounded gas/CPU consumption from an actor-controlled loop bound).

### Likelihood Explanation
Becoming a witness costs a fixed TRX fee (no scaling deterrent), and there is no code-enforced ceiling on the total number of witness records in `WitnessStore`. The economic cost of spamming thousands of witness registrations is the primary practical deterrent, which is analogous to the original finding being rated only "Medium" because the loop-bound actors are economically constrained but not protocol-constrained. I was not able to directly retrieve `WitnessCreateActuator.java`'s fee constant or `DposService.updateWitness` implementation in this session (tool calls were cut off), so I cannot confirm the exact current fee value or whether any additional witness-count cap was added elsewhere; this limits full certainty about real-world exploit cost.

### Recommendation
- Enforce an explicit, on-chain maximum number of registered witnesses (not just active/elected witnesses) in `WitnessCreateActuator.validate()`, rejecting new registrations beyond a safe bound.
- Where full-list iteration is unavoidable (`MaintenanceManager.doMaintenance`, `Wallet.getPaginatedNowWitnessList`), document the assumed/enforced bound and add defensive checks/metrics that alert if the witness set size exceeds expectations.
- Consider separating "candidate" witness bookkeeping from data structures that are iterated/sorted on every maintenance cycle, so growth in the candidate set does not linearly increase per-cycle consensus overhead.

### Proof of Concept
Conceptual (not independently executed in this session due to tool-call limits):
1. From many distinct accounts, submit `WitnessCreateContract` transactions, each paying the fixed witness-creation fee, to register a large number (e.g., tens of thousands) of witnesses in `WitnessStore`.
2. Observe that `MaintenanceManager.doMaintenance()` — invoked at every maintenance/epoch boundary — must call `consensusDelegate.getAllWitnesses()` and iterate/sort the complete list several times (vote accumulation, `newWitnessAddressList` construction, brokerage/vote persistence loops), with per-cycle cost growing linearly with the total witness count.
3. Observe that calls to the public `getPaginatedNowWitnessList` RPC also load and sort the full witness list before applying pagination, so its latency also grows with the unbounded witness count, even for small requested page sizes.

**Uncertainty note:** I could not confirm within this session (a) the exact fee amount in `WitnessCreateActuator`, (b) whether `DposService.updateWitness` contains additional bounding logic that mitigates this, since the final file reads for those two files did not complete before the session ended. These should be verified directly in the repository before treating this as a confirmed, exploitable finding.
