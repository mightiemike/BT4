## Analog Vulnerability Found

### Title
Uncontrolled gzip decompression of user-submitted deprecated (Cairo0) declare-transaction programs enables memory/CPU exhaustion - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
The HuTool advisory (CVE-2022-4565) is a classic decompression-bomb / uncontrolled resource consumption bug: attacker-supplied compressed input is decompressed without bounding the output size or time, letting a small payload expand to consume unbounded memory/CPU. The sequencer's JSON-RPC layer contains an analogous pattern: `decompress_program` decompresses a user-controlled, base64-encoded gzip blob with no size or time limit, and it is invoked while converting a raw `BroadcastedDeclareTransaction` (Cairo0/V1) into an `ExecutableTransactionInput` for locally executed RPC methods (`estimateFee`, `simulateTransactions`, `traceTransaction`, `call`-adjacent flows) — reachable directly from any unprivileged RPC caller/transaction sender, with no upstream size check.

### Finding Description
`decompress_program` reads the caller-supplied `compressed_program` field and decompresses it via `GzDecoder::read_to_end` into an in-memory `Vec<u8>` with no cap on the decompressed size and no timeout, as flagged by its own TODO comment: [1](#0-0) 

This function is called from `user_deprecated_contract_class_to_sn_api`, which is invoked when converting a `BroadcastedDeclareTransaction::V1` (a Cairo0/deprecated declare transaction supplied directly by an RPC client) into an `ExecutableTransactionInput`: [2](#0-1) 

Notably, every *other* decompression path found in this codebase (e.g. `starknet_api::compression_utils::decode_and_decompress_with_size_limit`, used for the RPC-native `DeprecatedGatewaySierraContractClass` conversion, and `apollo_storage::compression_utils::decompress`) enforces a hard `max_size` bound and rejects oversized output: [3](#0-2) 

`decompress_program` is the one outlier that lacks this protection, matching the "unbounded ZipUtil-style decompression" bug class from the HuTool advisory.

### Impact Explanation
An attacker can craft a tiny gzip payload (a "decompression/gzip bomb") that expands to gigabytes, then submit it as the `contract_class.program` of a `BROADCASTED_DECLARE_TXN` (V1/Cairo0) to any of the RPC node's execution-related methods that build an `ExecutableTransactionInput` from raw broadcasted transactions (e.g. fee estimation/simulation/trace endpoints). Because there is no size or time bound before or during decompression, the node will attempt to allocate an unbounded buffer and spend unbounded CPU decompressing it, which can exhaust memory and crash or freeze the serving process — a network-reachable, unauthenticated resource-exhaustion (CWE-400/404) condition on a component reachable by any transaction sender/RPC client, with no fee or resource-bound gate in front of it (this code path runs before any gas/fee metering, analogous to the Sierra compilation resource-limit concerns already handled carefully elsewhere in the codebase, e.g. `apollo_sierra_compilation_config`/`ResourceLimits`).

### Likelihood Explanation
High likelihood: no authentication, no special privileges, and no resource bound are required — a single crafted JSON-RPC request with a small (few-KB) malicious payload is sufficient to trigger unbounded decompression. The existence of a size-limited sibling function in the same file/crate (`decode_and_decompress_with_size_limit`) confirms the missing bound here is an oversight rather than an intentional design choice, and the inline `// TODO(dan): add time and size limits.` comment explicitly documents the gap.

### Recommendation
Bound `decompress_program`'s output size (and ideally decompression time) the same way `decode_and_decompress_with_size_limit` does elsewhere in the codebase — e.g. wrap the `GzDecoder` reader with `.take(max_size + 1)` and reject the input if the decompressed length exceeds the configured maximum (mirroring `DEFAULT_MAX_SIERRA_PROGRAM_SIZE` / `MAX_CAIRO0_PROGRAM_SIZE` conventions already used for the RPC-native class conversion path), returning a client error instead of allocating unbounded memory.

### Proof of Concept
1. Craft a small gzip blob that decompresses to several GB of arbitrary bytes (e.g. many repeated zero bytes), base64-encode it.
2. Submit a JSON-RPC call to `starknet_estimateFee` (or `starknet_simulateTransactions`/`traceTransaction`) with a `BROADCASTED_DECLARE_TXN` of version 1 (Cairo0) whose `contract_class.program` field is the crafted base64 string.
3. The server calls `user_deprecated_contract_class_to_sn_api` → `decompress_program`, which decompresses the payload fully into memory with no size cap, causing large memory allocation/CPU usage per request; repeated/concurrent requests can exhaust node memory and degrade or crash the RPC service.

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.

    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
