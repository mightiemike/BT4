## Title
`ensure_match_transaction_info` silently skips checkpoint-hash validation, letting replay-verify/db-tool accept a diverged state root as authenticated - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to confirm that a re-executed (replayed) `TransactionOutput` matches an authenticated `TransactionInfo` pulled from a backup/proof. It checks status, gas used, write-set hash, and event root hash, but the code contains an explicit acknowledgment that it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [1](#0-0) . These checkpoint hashes are exactly the fields that bind a `TransactionInfo` (and therefore the transaction accumulator / ledger proof) to a specific state root.

### Finding Description
`ensure_match_transaction_info` is called from two proof-integrity-sensitive consumers:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which is the core of `db-tool`'s `ReplayOnArchive`/replay-verify machinery: it re-executes historical transactions from an authenticated backup and calls `ensure_match_transaction_info` per transaction to confirm the replayed output matches the `TransactionInfo` recorded in the backup/ledger [2](#0-1) .
- `aptos_debugger.rs::print_mismatches`, used to diagnose divergence between actual and expected outputs [3](#0-2) .

Because the function omits comparison of `state_checkpoint_hash` (the Sparse-Merkle-Tree world-state root recorded per checkpoint), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, a replayed transaction whose resulting state root differs from the one committed in the authenticated `TransactionInfo` (and thus from the one bound into the transaction accumulator / ledger info via `TransactionInfoV1`, see the struct fields) [4](#0-3)  will still be reported as "matching." The comment in the code itself flags this as a known gap that must be closed before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled [1](#0-0) , i.e. before the position/native-trading state root becomes consensus-authenticated via `TransactionInfoV1` [5](#0-4) .

This is a genuine gap in the "proof and storage pivot" invariant that "authenticated API and proof-bearing responses must stay bound to the right ... root": the function whose entire purpose is to bind a re-derived `TransactionOutput` to the accumulator-proven `TransactionInfo` fails to check the fields that carry the state root.

### Impact Explanation
If a bug in execution, in state-checkpoint hashing, or in `NATIVE_POSITION`/`compute_trading_native_state_roots` logic causes a divergent state root without changing gas/status/events/write-set hash of the *checkpoint transaction itself* (state-checkpoint-hash divergence can happen independent of a single transaction's own write set, since it is computed from the *entire accumulated state* at the checkpoint boundary — see `do_state_checkpoint.rs::get_state_checkpoint_hashes`) [6](#0-5) , the `replay-verify`/`replay_on_archive` tooling — which operators rely on as the audit oracle that a node's history is consistent with the authenticated backup — would report success despite the true world-state root differing from the one committed on-chain. This directly matches the "wrong state proof accepted as valid" impact class: an authenticated-response consumer treats a corrupted/incorrect state commitment as verified.

The severity is bounded by the fact that this code path is a verification/audit tool, not the live consensus/commit path (state-sync's `ChunkResultVerifier` in `chunk_result_verifier.rs` uses full `TransactionInfo` struct equality via `ensure_transaction_infos_match`, which does compare complete `TransactionInfo` objects field-by-field and is not affected) [7](#0-6) [8](#0-7) . So this cannot by itself corrupt the committed ledger or forge an accumulator/Merkle proof accepted by a validating node; its blast radius is limited to false confidence in replay-verify/db-tool audits (`ReplayOnArchive`, `aptos-debugger`), which is a real but narrower proof-integrity gap than a consensus-breaking bug.

### Likelihood Explanation
The gap is unconditionally present today (not gated behind a feature flag) since `ensure_match_transaction_info` always skips these fields regardless of whether `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled. It requires only that a real divergence exist in the checkpoint/hot-state/position-state root computation (e.g., a latent state-computation bug) for the audit tooling to silently miss it. The code author's own TODO confirms this is a recognized, un-fixed condition, which raises confidence this is a genuine local defect rather than speculation.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on either side) between the computed output and the expected `TransactionInfo`, mirroring the full-equality check already used in `ensure_transaction_infos_match`. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the code comment itself states.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO` (or hypothetically `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) so `TransactionInfoV1.state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` carry real, consensus-committed roots.
2. Take an authenticated backup containing a `TransactionInfo` with checkpoint hash `H`.
3. Replay the same transactions with `db-tool replay-on-archive` against a build where a state-computation bug (or corrupted native-position state) produces checkpoint hash `H' != H`, while gas/status/events/write-set hash of the individual transactions are unaffected (state_checkpoint_hash is computed over the accumulated state, not just from the one transaction).
4. `execute_and_verify` → `ensure_match_transaction_info` in `execution/executor/src/chunk_executor/mod.rs` reports no error because it never compares checkpoint hashes [9](#0-8) [1](#0-0) .
5. `replay-verify`/`ReplayOnArchive` exits with success despite the divergent, incorrect state root — a false assurance of ledger integrity.

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }

    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())
        {
            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
    }
