### Title
Missing length validation on `ak` parameter in `ShieldedTRC20ParametersBuilder.generateSpendProof` allows malformed-length byte array into native JNI call - ([File: framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java])

### Finding Description
In `generateSpendProof` (lines 116-165), when a spend is constructed via the `ak`/`nsk`-based `addSpend(byte[] ak, byte[] nsk, Note note, ...)` overload (line 607-617, using the private `SpendDescriptionInfo(byte[] ak, byte[] nsk, ...)` constructor at line 675-690), the code branches on `!ArrayUtils.isEmpty(spend.ak)` (line 125) and, if true, uses `spend.ak` and `spend.nsk` directly with **no call to `LibrustzcashParam.valid32Params`** or any length check on `ak` [1](#0-0) .

Contrary to the question's premise, `nsk` is not actually unchecked in this path: it is first passed to `JLibrustzcash.librustzcashNskToNk(spend.nsk)` (line 127), and that method internally calls `LibrustzcashParam.valid32Params(nsk)` before touching native code, throwing a `ZksnarkException` for any array not exactly 32 bytes [2](#0-1) . So a malformed `nsk` is rejected before any native call.

However, `ak` has no equivalent guard anywhere in this call path. `ArrayUtils.isEmpty` only rejects `null` or zero-length arrays, not arrays of the wrong size (e.g., 4 or 1024 bytes). This unchecked `ak` is passed into `note.nullifier(ak, ...)` and then directly into `JLibrustzcash.librustzcashSaplingSpendProof(...)` (lines 142-154), which forwards it unchecked to the native `INSTANCE.librustzcashSaplingSpendProof(...)` JNI call (`JLibrustzcash.java` lines 123-128) with no `valid32Params` call, unlike sibling functions such as `librustzcashAskToAk` (line 76) and `librustzcashNskToNk` (line 87) that do validate.

### Impact Explanation
If the native `librustzcashSaplingSpendProof` implementation assumes `ak` is exactly 32 bytes and reads/writes a fixed-size buffer without its own bounds checks, a caller-supplied `ak` of incorrect length could cause an out-of-bounds native memory read (or corruption), leading to a node crash (DoS) or potentially memory corruption inside the JNI bridge.

### Likelihood Explanation
This is narrower than stated in the question: the `nsk` half of the claim is already mitigated by existing validation in `JLibrustzcash.librustzcashNskToNk`. The exploitable gap is limited to the `ak` parameter. Whether this is reachable by an unprivileged remote attacker depends on whether a public Wallet/RPC API actually exposes the `addSpend(byte[] ak, byte[] nsk, ...)` overload with attacker-controlled `ak`; based on the code searched, this overload appears used within `ShieldedTRC20ParametersBuilder`/`ZenTransactionBuilder`, but I could not confirm within the available tool calls that an unauthenticated RPC/HTTP endpoint passes raw, attacker-supplied `ak` bytes into this specific constructor (as opposed to internally-derived, correctly-sized `ak` values). This reachability question remains unverified.

### Recommendation
Add explicit `LibrustzcashParam.valid32Params(spend.ak)` (and defensively re-validate `spend.nsk`) immediately when entering the `ak`/`nsk` branch in `generateSpendProof`, before calling `note.nullifier` or `librustzcashSaplingSpendProof`, mirroring the pattern already used in `librustzcashAskToAk`/`librustzcashNskToNk`.

Because the `nsk`-only portion of the reported vulnerability is already mitigated by existing code (`JLibrustzcash.librustzcashNskToNk` calls `valid32Params`), and full remote reachability of the raw `ak`/`nsk` `addSpend` overload from an unprivileged RPC caller could not be confirmed with the available evidence, this should be treated as a **partial/unconfirmed finding** limited to the unchecked `ak` parameter rather than the full RCE claim as stated.
