### Title
App Proxy HMAC canonicalization allows parameter‑boundary smuggling due to missing delimiter between key/value pairs - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`stringifyQueryForAppProxy`, used to build the string that Shopify App Proxy signatures (`signature` query param) are verified against, concatenates sorted `key=value` pairs with **no delimiter between pairs** and **no escaping of values**. This mirrors the reported `DKGResultVerification.verify` bug class: packing multiple logical fields together without length validation or a separating salt lets an attacker shift bytes across field boundaries while producing an identical packed value (and therefore an identical valid signature) for a different set of underlying parameters.

### Finding Description
The App Proxy canonicalization function is: [1](#0-0) 

Unlike `stringifyQueryForAdmin`, which uses `ProcessedQuery.stringify(true)` (percent-encoded, `&`-joined pairs), `stringifyQueryForAppProxy` simply does `${acc}${key}=${value}` for each sorted entry with nothing between one pair and the next: [2](#0-1) 

This same function is used both when building `localHmac` for verification and (per test fixtures) mirrors how Shopify itself builds the canonical string: [3](#0-2) 

Only four parameter names (`hmac`, `shop`, `signature`, `timestamp`) are protected from being supplied multiple times / as arrays: [4](#0-3) 

All other query parameter names and values — including application-defined and customer-related ones such as `logged_in_customer_id` and `path_prefix` — are freely attacker/customer-controllable and flow directly into the un-delimited canonical string: [5](#0-4) 

Because there is no separator (not even `&`) between consecutive `key=value` segments, the mapping from `{query params} → canonical string` is **not injective**: different sets of parameter names/values can yield the exact same byte string, and therefore the exact same `createSHA256HMAC` output used in `validateHmac`: [6](#0-5) 

This is structurally identical to the reported `abi.encodePacked(groupPubKey, misbehaved)` issue: packing two variable-length fields together without a length prefix/delimiter lets an attacker move bytes between fields while preserving the packed representation (and thus the signature) — here the "fields" are the individual `key=value` query parameters instead of `groupPubKey`/`misbehaved`.

### Impact Explanation
An attacker who has observed one legitimately Shopify-signed App Proxy request (which is trivial — the signed URL, including `signature`, is delivered to the customer's own browser on every App Proxy page load) can restructure the query string — merging or splitting adjacent parameters at their alphabetical boundary — so that:
- `stringifyQueryForAppProxy` produces the identical canonical string as the original, so
- the original captured `signature` still validates successfully via `safeCompare(hmac, localHmac)`,

while the parameters the app actually receives (e.g. `logged_in_customer_id`, `path_prefix`, or any app-specific parameter) differ from what Shopify actually signed. Any app-proxy handler that trusts `logged_in_customer_id`/other query fields as "verified by Shopify" once `validateHmac`/`shopify.authenticate.public.appProxy` succeeds is exposed to parameter smuggling — potentially leading to customer-identity confusion or bypass of app-side authorization logic that depends on these fields, without needing the app's `apiSecretKey`.

### Likelihood Explanation
Exploitation only requires:
1. The attacker being a normal (possibly unauthenticated or low-privilege) visitor to the merchant's storefront/app proxy endpoint, and
2. Observation of a single valid, previously-issued signed App Proxy URL (readily available since it's rendered directly in the browser).

No secret key or elevated access is required, and the vulnerable function `stringifyQueryForAppProxy` is on the App Proxy authentication path used by `shopify.utils.validateHmac(..., {signator: 'appProxy'})` across `shopify-app-remix`/`shopify-app-react-router`'s `authenticate.public.appProxy` flow.

### Recommendation
Change `stringifyQueryForAppProxy` (and any place relying on it) to build a canonicalization that is injective for its inputs, e.g.:
- Use an explicit, unambiguous delimiter between key/value pairs (e.g. `&`), and
- Percent-encode/escape both keys and values before concatenation (consistent with `stringifyQueryForAdmin`'s use of `ProcessedQuery`),

so that no combination of attacker-controlled parameter names/values can produce a canonical string that collides with a different, legitimately-signed parameter set.

### Proof of Concept
Given a legitimate Shopify-signed App Proxy request with query params:
```
logged_in_customer_id=100
path_prefix=/apps/foo
shop=my-shop.myshopify.com
timestamp=1700000000
signature=<SIG>
```
`stringifyQueryForAppProxy` builds (sorted alphabetically, no delimiter):
```
logged_in_customer_id=100path_prefix=/apps/fooshop=my-shop.myshopify.comtimestamp=1700000000
```
An attacker captures `<SIG>` (visible in their own browser) and replays a forged request that **omits the `path_prefix` key** and instead folds its content into the value of `logged_in_customer_id`:
```
logged_in_customer_id=100path_prefix=/apps/foo
shop=my-shop.myshopify.com
timestamp=1700000000
signature=<SIG>
```
`stringifyQueryForAppProxy` produces the byte-for-byte identical canonical string, so `validateHmac` (via `safeCompare`) still returns `true`: [7](#0-6) 

but the app now receives `logged_in_customer_id = "100path_prefix=/apps/foo"` and no `path_prefix` parameter at all — demonstrating that field boundaries in the signed data can be manipulated by an attacker without invalidating the signature.

```typescript
function stringifyQueryForAdmin(query: AuthQuery): string {
  const processedQuery = new ProcessedQuery();
  Object.keys(query)
    .sort((val1, val2) => val1.localeCompare(val2))
    .forEach((key: string) => processedQuery.put(key, query[key]));

  return processedQuery.stringify(true);
}

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}
```

```typescript
export function validateHmac(config: ConfigInterface) {
  return async (
    query: HmacQuery,
    {signator}: {signator: HMACSignator} = {signator: 'admin'},
  ): Promise<boolean> => {
    const normalizedQuery = normalizeQuery(query, signator);

    if (signator === 'admin' && !normalizedQuery.hmac) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain an HMAC value.',
      );
    }

    if (signator === 'appProxy' && !normalizedQuery.signature) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain a signature value.',
      );
    }

    validateHmacTimestamp(normalizedQuery);

    const hmac =
      signator === 'appProxy'
        ? normalizedQuery.signature
        : normalizedQuery.hmac;
    const localHmac = await generateLocalHmac(config)(
      normalizedQuery,
      signator,
    );

    return safeCompare(hmac as string, localHmac);
  };
}
```
