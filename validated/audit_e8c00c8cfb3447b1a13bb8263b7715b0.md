### Title
DelegateAction executes at `max_block_height` instead of expiring — off-by-one boundary bypass in `apply_delegate_action` (File: runtime/runtime/src/actions.rs)

### Summary
`apply_delegate_action` only rejects a `DelegateAction` when the current block height is *strictly greater than* `max_block_height`, but the field itself is documented as "the maximal height of the block in the blockchain **below which** the given DelegateAction is valid." This means a meta-transaction that should be expired once the chain reaches `max_block_height` is instead still accepted and executed exactly at that height, one block later than the documented semantics allow.

### Finding Description
The expiry check in `apply_delegate_action` is: [1](#0-0) 

```rust
let delegate_action = signed_delegate_action.delegate_action();
if apply_state.block_height > delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
```

The `max_block_height` field is documented as the height **below which** the delegate action is valid: [2](#0-1) 

i.e. the intended valid range is `block_height < max_block_height`, and expiry should trigger at `block_height >= max_block_height`. The actual guard only triggers expiry at `block_height > max_block_height`, so a chunk producer or relayer can include the delegate action's containing transaction/receipt exactly at `block_height == max_block_height` and it is treated as still valid, generating a new receipt and executing the delegated actions: [3](#0-2) 

The existing unit test only exercises the `max_block_height + 1` case (confirming expiry) and treats `block_height == max_block_height` as the success/happy-path setup, cementing the off-by-one rather than catching it: [4](#0-3) 

This is directly analogous to the reported ERC5095 bug class: a `>` check is used where an `>=` check is documented/expected at a maturity/deadline boundary, allowing an action "at maturity" that should be rejected.

### Impact Explanation
A `SignedDelegateAction` is signed once by the sender and can be held and submitted later by an untrusted relayer (any transaction/meta-transaction sender can construct and submit the enclosing transaction). Users and wallets rely on `max_block_height` as a hard cutoff to bound the window during which a relayer can execute their meta-transaction (e.g., to bound token approvals, transfers, or swaps to a short window). Because the runtime treats the deadline block itself as still valid, a relayer (or anyone who obtained the signed delegate action) can force execution of actions — including value-moving actions such as `Transfer`, `FunctionCall` with deposits, or delegated calls into DeFi/token contracts — one block past the height at which the signer/wallet UI would have considered the authorization expired. This can result in unauthorized value movement from the sender's account after the user believes their authorization has lapsed.

### Likelihood Explanation
This is trivially reachable by any unprivileged actor who receives or intercepts a signed `DelegateAction`: no validator, network, or node compromise is needed. All that's required is submitting/including the containing transaction at exactly `block_height == max_block_height`, which is a normal, permissionless action for a relayer.

### Recommendation
Change the comparison in `apply_delegate_action` to reject at the boundary, consistent with the field's documented "valid below max_block_height" semantics:

```rust
if apply_state.block_height >= delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
```

Also update `docs/RuntimeSpec/Actions.md` and the `DelegateActionExpired` doc comment in `core/primitives/src/errors.rs` to consistently describe the corrected (inclusive) boundary, and add a unit test asserting that `block_height == max_block_height` is treated as expired.

### Proof of Concept
1. A user signs a `DelegateAction` with `max_block_height = H`, intending it to be unusable once the chain reaches height `H`.
2. A relayer withholds submission until a block at height exactly `H` is being produced/applied, then submits the transaction wrapping the `SignedDelegateAction`.
3. In `apply_delegate_action`, `apply_state.block_height (== H) > delegate_action.max_block_height() (== H)` is `false`, so the expiry check is skipped and the delegated actions (e.g., a `Transfer`) execute normally, moving value from the sender despite the user's expectation that the authorization expired at height `H`. This mirrors the test setup at [4](#0-3)  where `create_apply_state(max_block_height)` (i.e., `block_height == max_block_height`) is used as a non-expired, successful execution case.
