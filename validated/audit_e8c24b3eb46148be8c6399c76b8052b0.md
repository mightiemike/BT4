### Title
Deposit Refund Misdirection in Meta Transactions: Relayer Loses Funds to User on Inner Receipt Failure — (File: `runtime/runtime/src/actions.rs`)

---

### Summary

When a user (`Alice`) crafts a `DelegateAction` with a large deposit attached to an inner action that will fail on the receiver's shard, the relayer pays the deposit upfront but `Alice` receives the full deposit refund. The root cause is that `apply_delegate_action` sets the inner receipt's `predecessor_id` to `sender_id` (Alice), not the relayer. On failure, the protocol's deposit-refund logic routes the refund to `predecessor_id`, giving Alice the relayer's money. This is a protocol-level fund-loss path reachable by any unprivileged user.

---

### Finding Description

`apply_delegate_action` in `runtime/runtime/src/actions.rs` constructs the inner action receipt as follows:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // ← Alice, not the relayer
    receiver_id: delegate_action.receiver_id().clone(),
    ...
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // ← relayer
        ...
        actions: delegate_action.get_actions(),
    }),
});
``` [1](#0-0) 

The `signer_id` (relayer) is preserved for gas refunds, but `predecessor_id` is set to `sender_id` (Alice). The code comment even acknowledges the consequence:

> "If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. Gas is refunded to the signer, this is Relayer." [2](#0-1) 

When the inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` issues a deposit-refund receipt:

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),
        deposit_refund,
    ));
}
``` [3](#0-2) 

`balance_refund_receiver()` resolves to `predecessor_id()` for `ReceiptEnum::Action` (V1) receipts, because `refund_to` is always `None` for that variant:

```rust
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
``` [4](#0-3) 

```rust
ReceiptEnum::Action(_) | ... => &None,   // refund_to is always None for V1
``` [5](#0-4) 

So the deposit refund is sent to Alice (`predecessor_id`), not to the relayer (`signer_id`) who actually paid it. The nearcore architecture documentation explicitly acknowledges this attack surface:

> "there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [6](#0-5) 

---

### Impact Explanation

The relayer pays the full deposit for the inner action (e.g., 100 NEAR attached to a `FunctionCall`). If the inner receipt fails on the receiver's shard, the 100 NEAR deposit refund is credited to Alice's account, not the relayer's. The relayer suffers a net loss equal to the deposit amount. Alice gains that amount at zero cost. This is a direct, protocol-enforced transfer of funds from the relayer to the user, triggered by a deliberately crafted failing `DelegateAction`.

---

### Likelihood Explanation

Any user with a NEAR account can create a `DelegateAction` with an arbitrarily large deposit attached to an inner action that is guaranteed to fail (e.g., calling a non-existent method on a contract, or calling a contract that always panics). The relayer cannot fully prevent this: even if the relayer checks Alice's balance and the contract state before submission, Alice can manipulate the contract state in a preceding transaction in the same block, causing the inner receipt to fail after the relayer has already committed. No special privileges are required. The attack is repeatable and scales with the deposit size.

---

### Recommendation

The inner receipt created in `apply_delegate_action` should use `ReceiptEnum::ActionV2` (which carries a `refund_to` field) and set `refund_to: Some(relayer_id)`, where `relayer_id` is `action_receipt.signer_id()`. This would route deposit refunds back to the relayer on failure, matching the gas-refund behavior. The `ActionReceiptV2` struct and the `refund_to` field already exist in the codebase and are already consulted by `balance_refund_receiver()`. [7](#0-6) 

---

### Proof of Concept

1. Alice deploys (or identifies) a contract `bob.near` whose method `drain` always panics.
2. Alice creates and signs a `DelegateAction`:
   - `sender_id`: `alice.near`
   - `receiver_id`: `bob.near`
   - `actions`: `[FunctionCall { method_name: "drain", gas: 30 TGas, deposit: 100 NEAR }]`
   - `max_block_height`: current + 100
3. Alice sends the `SignedDelegateAction` to a relayer.
4. The relayer wraps it in a transaction (relayer is signer), paying the 100 NEAR deposit from its own balance, and submits it.
5. On Alice's shard, `apply_delegate_action` creates the inner receipt with `predecessor_id = alice.near`, `signer_id = relayer.near`.
6. On Bob's shard, the `drain` call panics. `refund_unspent_gas_and_deposits` issues:
   - Gas refund → `signer_id` = `relayer.near` ✓ (correct)
   - Deposit refund → `balance_refund_receiver()` = `predecessor_id` = `alice.near` ✗ (wrong)
7. Alice's balance increases by 100 NEAR. The relayer's balance decreases by 100 NEAR (net of gas refund). The relayer has no recourse.

The attack is repeatable with any deposit size Alice can convince the relayer to accept.
