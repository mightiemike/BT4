## Analysis

The `preValidateTransactionSign` optimization is only a pre-check, not the authoritative validation used to mutate state. Tracing `processBlock`: [1](#0-0) 

`preValidateTransactionSign` runs `ValidateSignTask` in parallel across all transactions in the block against the *current* `AccountStore`/`DynamicPropertiesStore` snapshot before any transaction in the block is executed: [2](#0-1) [3](#0-2) 

Critically, after this parallel pre-check, `processBlock` then executes transactions **sequentially** via `processTransaction(transactionCapsule, block)` in the `for` loop: [4](#0-3) 

`processTransaction` invokes the actuator pipeline, which for any transaction calls `validate()` and `execute()` under the actual (sequentially-updated) state at that point — the actuator's own signature/permission checks (via `TransactionCapsule.validateSignature`, which checks `isVerified` cache) are re-evaluated as part of normal validation flow, not solely relying on the parallel pre-check's cached result to authorize state mutation. The parallel `preValidateTransactionSign` sets `isVerified = true` on the capsule as a cache [5](#0-4)  — meaning if T1 (permission update) and T2 (transfer using now-revoked key) are both validated in parallel against the *pre-block* snapshot, and both mark `isVerified = true`, then when T2 executes sequentially after T1 (which already updated the permission in the AccountStore), `validateSignature` is short-circuited by the `isVerified` flag and skips re-validating against the *new* post-T1 state.

This means: T2's signature check is effectively validated once, against the stale pre-block permission snapshot, and cached as `isVerified = true`; the actuator layer during execution does not force a re-check of signature/permission against updated state because `isVerified` guards re-entry into `validatePubSignature`. So a key revoked by an earlier transaction in the same block can still authorize a later transaction in that same block, because the caching mechanism explicitly bypasses redoing the permission-dependent signature check at execution time.

This is a genuine, plausible determinism/authorization-ordering issue rooted in the interaction between the parallel `preValidateTransactionSign` optimization and the `isVerified` caching flag in `TransactionCapsule`, combined with sequential execution order in the same block. However, I could not fully verify from the available code snippets whether `AccountPermissionUpdateContract`'s actuator additionally re-derives/re-checks the owner's permission validity against fresh state independent of the `isVerified` flag (e.g., via a separate permission check inside the actuator's `validate()`/`execute()`), which could act as a secondary gate. I was not able to view `AccountPermissionUpdateContractActuator` or the full actuator `validate()` implementations in this session to confirm whether such a secondary check exists and would block this exploit.

### Title
Stale parallel signature-validation cache allows a same-block, since-revoked key to authorize a transaction - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`preValidateTransactionSign` validates all transactions in a block in parallel against a single pre-block `AccountStore` snapshot and marks each `TransactionCapsule` as `isVerified = true`. Because `TransactionCapsule.validateSignature` short-circuits when `isVerified` is already true, a transaction spending under a permission that is revoked by an earlier transaction in the same block will not have its signature/permission re-checked against the updated state during sequential execution.

### Finding Description
`processBlock` calls `preValidateTransactionSign(txs)` before the sequential execution loop [1](#0-0) . This method submits a `ValidateSignTask` per transaction to a thread pool, all reading `chainBaseManager.getAccountStore()`/`getDynamicPropertiesStore()` concurrently [2](#0-1) [3](#0-2) . `TransactionCapsule.validateSignature`/`validatePubSignature` set `isVerified = true` after a successful check and then guard against re-running the check (`if (!isVerified) {...}`) [5](#0-4) [6](#0-5) . Since all N transactions are validated concurrently against the same pre-block snapshot before any of them executes, a transaction T2 signed with a key that is valid before the block but revoked by an earlier transaction T1 (e.g., `AccountPermissionUpdateContract`) in the same block will pass the parallel pre-check and be cached as verified, even though sequential execution order means T1 should have invalidated T2's authorization by the time T2 actually runs in the `for` loop over `block.getTransactions()` [4](#0-3) .

### Impact Explanation
If the actuator execution path for the affected contract type relies on the cached `isVerified` flag rather than independently re-deriving permission validity at execution time, this allows unauthorized state changes (e.g., a transfer or other authorized action) using a key that the account owner has explicitly revoked within the same block — a form of unauthorized account operation / authorization bypass, matching TRON's "unauthorized state change" bounty impact class.

### Likelihood Explanation
Preconditions require only an unprivileged account broadcasting two ordinary, fee-paying, size-compliant transactions from the same owner address into the same block: an `AccountPermissionUpdateContract` and a transfer signed with the old (soon-to-be-revoked) key. This is fully achievable by any funded account without special privileges, though it depends on both transactions being packed into the same block by the block producer — feasible but not fully attacker-controlled (attacker can only broadcast, not guarantee block packing order), and requires the secondary actuator-level permission check to be absent, which I could not confirm from available code.

### Recommendation
Do not treat `isVerified` as authoritative once set by the pre-block parallel check. Either (a) invalidate/re-derive signature and permission verification per-transaction at execution time whenever any preceding transaction in the same block modifies the signer's account permissions, or (b) have the parallel pre-check operate only as a fast-reject filter for cryptographic signature format/recovery, while the authoritative permission-weight check against post-prior-tx state is always performed at `processTransaction` time regardless of `isVerified`.

  private void preValidateTransactionSign(List<TransactionCapsule> txs)
      throws InterruptedException, ValidateSignatureException {
    int transSize = txs.size();
    if (transSize <= 0) {
      return;
    }
    Histogram.Timer requestTimer = Metrics.histogramStartTimer(
        MetricKeys.Histogram.VERIFY_SIGN_LATENCY, MetricLabels.TRX);
    try {
      CountDownLatch countDownLatch = new CountDownLatch(transSize);
      List<Future<Boolean>> futures = new ArrayList<>(transSize);

      for (TransactionCapsule transaction : txs) {
        Future<Boolean> future = validateSignService
            .submit(new ValidateSignTask(transaction, countDownLatch, chainBaseManager));
        futures.add(future);
      }
      countDownLatch.await();

      for (Future<Boolean> future : futures) {
        try {
          future.get();
        } catch (ExecutionException e) {
          throw new ValidateSignatureException(e.getCause().getMessage());
        }
      }
    } finally {
      Metrics.histogramObserve(requestTimer);
    }
  }

  private static class ValidateSignTask implements Callable<Boolean> {

    private TransactionCapsule trx;
    private CountDownLatch countDownLatch;
    private ChainBaseManager manager;

    ValidateSignTask(TransactionCapsule trx, CountDownLatch countDownLatch,
        ChainBaseManager manager) {
      this.trx = trx;
      this.countDownLatch = countDownLatch;
      this.manager = manager;
    }

    @Override
    public Boolean call() throws ValidateSignatureException {
      try {
        trx.validateSignature(manager.getAccountStore(), manager.getDynamicPropertiesStore());
      } catch (ValidateSignatureException e) {
        throw e;
      } finally {
        countDownLatch.countDown();
      }
      return true;
    }
  }

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

  public boolean validateSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore) throws ValidateSignatureException {
    if (!isVerified) {
      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);
        } else { //transfer from shielded address
          if (this.transaction.getSignatureCount() > 0) {
            throw new ValidateSignatureException("there should be no signatures signed by "
                    + "transparent address when transfer from shielded address");
          }
        }
      }
      isVerified = true;
    }
    return true;
  }
