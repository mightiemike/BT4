### Title
CREATE2 contract deployments can be front-run and permanently blocked by an attacker observing pending deploy transactions, mirroring the cross-chain `createAccount` griefing bug - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
The reported bug lets an attacker observe a user's pending account-creation transaction and preemptively "claim" the same account ID on the destination chain, causing the victim's transaction to revert and lose the fees it already paid. The same root cause — a deterministic, attacker-predictable identifier that anyone can claim first, causing the legitimate creator's transaction to permanently fail — exists in java-tron's TVM `CREATE2` implementation.

### Finding Description
`CREATE2` addresses in java-tron are computed deterministically as `sha3omit12(factoryAddress || salt || sha3(initCode))`, exactly like EVM `CREATE2`: [1](#0-0)  This formula depends only on the calling contract's own fixed address, the `salt`, and the `initCode` — none of which are secret or tied to the caller (`tx.origin`), so anyone who observes a pending "deploy" call in the mempool (calldata containing `salt`/`code`, as in the `Factory.deploy(bytes,uint256)` pattern exercised in [2](#0-1) ) can compute the exact same resulting address off-chain.

In `Program.createContractImpl`, before running the init code, the VM checks whether an account already exists (and, when Constantinople rules apply, whether it is already a contract) at the computed address: [3](#0-2)  If that check is true, contract execution never happens, and the VM instead records an unrecoverable exception, effectively failing the create and consuming the reserved energy: [4](#0-3)  and [5](#0-4) 

Because both the attacker and the legitimate deployer would call the *same* factory contract's `deploy(code, salt)` entry point with the *same* `code`/`salt` pair (the attacker only needs to copy the observed pending transaction's parameters and resubmit it with higher energy/bandwidth fee to get mined first), the attacker's transaction succeeds in creating the contract at the predicted address, and the victim's later transaction with identical parameters unavoidably hits the `contractAlreadyExists` branch and fails — exactly the "listen for a pending tx, race to claim the same identifier first" pattern described in the report for cross-chain `createAccount`.

### Impact Explanation
This is a concrete Denial-of-Service/griefing vector: a legitimate user (or a factory contract relying on deterministic `CREATE2` deployment addresses, e.g., for deterministic wallets/counterfactual deployments) can have their deployment permanently and repeatably blocked by any third party who is watching the mempool, with no profit motive required for the attacker (pure griefing). The victim loses the energy spent on the reverted transaction and cannot obtain the contract at the address they had counted on, breaking any protocol logic (factory patterns, deterministic wallet deployment, state-channel counterfactual instantiation) that depends on being able to deploy to a specific pre-computed address.

### Likelihood Explanation
Likelihood is high wherever `CREATE2` is used with attacker-observable `salt`/`code` parameters in a public factory function, since TRON's mempool (like most chains') exposes pending transaction calldata before inclusion, and front-running (resubmitting the identical call with a higher fee/priority) is a well-understood, low-cost attack requiring no special privileges.

### Recommendation
Follow the report's own recommended mitigation pattern: derive the deployment "claim" from something the attacker cannot trivially replay, e.g., bind the `CREATE2` salt (or an additional access-control check inside the factory) to `msg.sender`/`tx.origin` so a copied transaction from a different caller does not resolve to the same address, or have the factory perform an authorization check before deployment so a front-running third party cannot successfully deploy in the victim's place. This is a smart-contract-level (factory design) mitigation rather than a protocol change, since the underlying `CREATE2` semantics in `Program.createContractImpl` correctly implement the EVM/TVM specification.

### Proof of Concept
1. Deploy a `Factory` contract with `deploy(bytes code, uint256 salt)` that performs `CREATE2` internally, as in [6](#0-5) .
2. Victim submits a transaction calling `Factory.deploy(initCode, salt)` intending to deploy to the deterministic address `generateContractAddress2(factoryAddress, salt, initCode)` as computed in [7](#0-6) .
3. Attacker observes the pending transaction, extracts `(initCode, salt)` from its calldata, and submits an identical `Factory.deploy(initCode, salt)` call with a higher fee so it is included first.
4. The attacker's transaction succeeds and deploys the contract at the predicted address.
5. The victim's original transaction is later executed; `createContractImpl` finds `existingAccount != null` and `isContractExist(...) == true`, sets `contractAlreadyExists = true`, and produces `createResult.setException(new BytecodeExecutionException("Trying to create a contract with existing contract address: 0x..."))` as in [8](#0-7) , permanently blocking the victim's intended deployment while consuming their energy.
