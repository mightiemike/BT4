### Title
Unrestricted `deploy` syscall enables deterministic contract-address squatting that permanently blocks legitimate account/contract deployment - (File: `crates/blockifier/src/execution/syscalls/syscall_base.rs`)

### Summary
Analogous to the reported handler-contract bug where any unprivileged caller could invoke an unprotected `update()` and overwrite/claim ownership state that a legitimate actor needed, the sequencer's `deploy` syscall lets *any* contract, invoked from *any* unprivileged transaction, permanently reserve a specific `ContractAddress` for itself before the intended (legitimate) deployer's transaction executes. Since `set_class_hash_at` is a write-once allocation, whoever deploys first to a given address wins, and every subsequent (legitimate) deployment to that same address — including `DeployAccountTransaction`s — fails permanently.

### Finding Description
The `deploy` syscall computes the target address deterministically from `(deployer_address, salt, class_hash, constructor_calldata)`: [1](#0-0) 

When `deploy_from_zero = true`, `deployer_address` is forced to `0`, meaning the resulting address depends only on public data (`salt`, `class_hash`, `constructor_calldata`): [2](#0-1) 

This exact `deployer_address = 0` scheme is also what `DeployAccountTransaction` uses to compute a fresh account's contract address (since accounts have no on-chain existence yet). Because `salt` for accounts is conventionally the account's public key (or another value predictable/observable ahead of confirmation, e.g. once a `DeployAccountTransaction` is broadcast to the mempool), and `class_hash`/`constructor_calldata` are also public, any unprivileged contract can precompute the exact same address and call the `deploy` syscall (with `deploy_from_zero=true`) to claim it first.

Allocation is a strict write-once check in `execute_deployment`: [3](#0-2) 

and `State::set_class_hash_at` is documented as "write once... raises an exception if the address is already assigned": [4](#0-3) 

Once an attacker's transaction deploys (any class) to the target address, the legitimate deploy attempt (whether via a normal `deploy` syscall call or a `DeployAccountTransaction`) will always fail with `StateError::UnavailableContractAddress`, as demonstrated in the existing negative test: [5](#0-4) [6](#0-5) 

This mirrors the report's bug class precisely: an unauthorized/unprivileged caller can exercise a state-mutating primitive with no restriction to the legitimate owner, and the resulting state change (address/ownership allocation) makes the rightful actor permanently unable to perform their intended, otherwise-valid on-chain action.

### Impact Explanation
Any unprivileged account with a deployed contract can permanently block a targeted counterparty from ever deploying their intended contract/account to a specific, predictable address. For account deployment specifically, this can be used to grief users out of activating their intended counterfactual address (address squatting/denial), which is an unauthorized interference with account creation and a form of permanent freezing of the intended deployment path for that address — matching the "unauthorized account action" / "permanent freezing" impact classes.

### Likelihood Explanation
High: this requires only a single ordinary invoke transaction calling `deploy` with `deploy_from_zero=true` on any already-deployed contract that exposes a deploy wrapper (a very common pattern, e.g. factory contracts), and knowledge of the salt/class_hash/constructor_calldata that the target intends to use — which is standard/public information for counterfactual account deployment (e.g., predictable salts such as the account's public key). No special privilege or race beyond ordinary mempool inclusion ordering is required.

### Recommendation
Consider documenting/enforcing stronger guidance or protocol-level mitigations for `deploy_from_zero` usage (e.g., encouraging/enforcing salts bound to the deployer's own future identity or requiring additional binding data in the address derivation) so that an arbitrary unprivileged contract cannot pre-compute and squat another party's counterfactual deployment address. At minimum, this address-squatting behavior and its user-facing consequences (deployment reverting with `UnavailableContractAddress`) should be clearly called out as a known, exploitable griefing vector so wallets/tooling can pick unpredictable salts.

### Proof of Concept
1. Alice intends to deploy an account via `DeployAccountTransaction` using `class_hash = C`, `constructor_calldata = D` (e.g., her public key), computed address `A = calculate_contract_address(salt=S, C, D, deployer_address=0)` (see `crates/starknet_api/src/core.rs:326-346`). `S`, `C`, and `D` are public/predictable (common wallet convention uses the public key as salt).
2. Attacker Bob, from any already-deployed contract, invokes an ordinary transaction that triggers the `deploy` syscall with `deploy_from_zero=true`, `contract_address_salt=S`, `class_hash=C`, `constructor_calldata=D` (`crates/blockifier/src/execution/syscalls/syscall_base.rs:380-426`), which computes the same address `A` and calls `execute_deployment`.
3. `execute_deployment` (`crates/blockifier/src/execution/execution_utils.rs:337-356`) sees `current_class_hash == ClassHash::default()` (unused) and succeeds, calling `state.set_class_hash_at(A, attacker_class_hash)`.
4. Alice's subsequent `DeployAccountTransaction` targeting the same address `A` computes the identical address and fails during `execute_deployment` with `StateError::UnavailableContractAddress(A)`, exactly as reproduced in the existing test `crates/blockifier/src/transaction/transactions_test.rs:2312-2338`. Alice can never deploy her account to address `A`.

pub fn calculate_contract_address(
    salt: ContractAddressSalt,
    class_hash: ClassHash,
    constructor_calldata: &Calldata,
    deployer_address: ContractAddress,
) -> Result<ContractAddress, StarknetApiError> {
    let constructor_calldata_hash = Pedersen::hash_array(&constructor_calldata.0);
    let contract_address_prefix = format!("0x{}", hex::encode(CONTRACT_ADDRESS_PREFIX));
    let address = Pedersen::hash_array(&[
        Felt::from_hex(contract_address_prefix.as_str()).map_err(|_| {
            StarknetApiError::OutOfRange { string: contract_address_prefix.clone() }
        })?,
        *deployer_address.0.key(),
        salt.0,
        class_hash.0,
        constructor_calldata_hash,
    ]);
    let (_, address) = address.div_rem(&L2_ADDRESS_UPPER_BOUND);

    ContractAddress::try_from(address)
}
