### Title
Unbounded O(n) migration cost in `DelegatedResourceAccountIndexStore.convert()` lets an attacker pre-build a legacy delegation-index backlog that forces an unrelated future transaction to pay for its migration - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`convert(byte[] address)` migrates the entire legacy `toAccountsList`/`fromAccountsList` of a `DelegatedResourceAccountIndexCapsule` into the new key-per-pair format by calling `delegate()` once per entry, with no bound on list size. Because `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, and `DelegateResourceActuator` all call `convert(ownerAddress)`/`convert(receiverAddress)` unconditionally whenever `supportAllowDelegateOptimization()` is enabled, an attacker who builds a large legacy backlog for an address before the optimization flag is turned on can force whichever transaction next touches that address (potentially sent by an unrelated party) to pay the full O(n) migration cost.

### Finding Description
`convert()` loops over `indexCapsule.getToAccountsList()` and `getFromAccountsList()` and calls `this.delegate()` (2 DB `put` calls each) per entry, with no size cap: [1](#0-0) 

Before `ALLOW_DELEGATE_OPTIMIZATION` is enabled, `FreezeBalanceActuator.delegateResource()` appends unique receiver/owner addresses to the legacy lists with no cap on the number of distinct entries: [2](#0-1) 

The only per-transaction constraints are `frozenBalance >= 1 TRX`, `frozenCount` (0 or 1) on the owner's own frozen slots, and that the receiver account must exist — none of these limit how many *distinct* receiver/owner entries can accumulate in `toAccountsList`/`fromAccountsList` over many transactions. An attacker can therefore freeze 1 TRX at a time to thousands of distinct (attacker-controlled) receiver addresses under one owner key, building an arbitrarily large legacy list.

Once the network enables `supportAllowDelegateOptimization()` (via `ALLOW_DELEGATE_OPTIMIZATION` proposal, handled in `ProposalService`), every subsequent `FreezeBalanceActuator`/`UnfreezeBalanceActuator`/`DelegateResourceActuator` execution against that poisoned address unconditionally triggers full migration: [3](#0-2) [4](#0-3) 

Critically, `convert()` is called on both the owner and receiver address of the *current* transaction, regardless of whether that address has a small or huge backlog. This means an unrelated third party who happens to freeze/unfreeze/delegate involving a previously-poisoned address (e.g., the attacker's own account acting as receiver in someone else's delegation, or simply the poisoned account itself performing any new unrelated freeze/delegate action) is forced to pay for migrating the attacker's entire pre-built backlog in that single transaction — even though `calcFee()` for these actuators returns a fixed value (e.g., `0` for `FreezeBalanceActuator`) unrelated to the backlog size: [5](#0-4) 

No existing guard bounds `toAccountsList`/`fromAccountsList` length, and no fee/bandwidth/energy charge scales with the number of migrated entries — the cost is entirely unpriced and deferred to whichever future transaction happens to trigger `convert()`.

### Impact Explanation
This allows an unprivileged attacker to pre-stage disproportionate, unbounded CPU and DB-write cost (thousands of `put`/`delegate` calls) that gets executed inside a victim's or unrelated node's transaction processing once the network-wide optimization switch occurs, without the triggering transaction paying commensurate fees. This can materially slow block processing for whichever block contains the triggering transaction, and constitutes underpriced public work relative to the resource/fee model, though it does not directly enable fund theft or double-settlement.

### Likelihood Explanation
Exploitability requires: (1) the network having `supportDR()` enabled (already active on mainnet), (2) the attacker performing many cheap freeze transactions (1 TRX each, refundable after minimum freeze duration) to build a large legacy backlog before optimization is enabled, and (3) `ALLOW_DELEGATE_OPTIMIZATION` subsequently being switched on (a real chain-parameter transition that already occurred historically on the TRON network). Given the switch is a one-time network event and legacy backlogs from before that event persist in state, this is a realistic, repeatable precondition rather than a purely theoretical one — the attack cost (many 1-TRX freezes) is attacker-controlled and can be amortized over time before the optimization activation.

### Recommendation
Cap the number of legacy `toAccounts`/`fromAccounts` entries a single address can accumulate under `FreezeBalanceActuator`/pre-optimization delegation, and/or make `convert()` incremental (migrate a bounded number of entries per call, tracking migration progress) rather than migrating the full backlog synchronously inside an unrelated transaction. Alternatively, price `convert()`'s work into the triggering transaction's fee/bandwidth/energy consumption proportional to the number of entries migrated.

### Proof of Concept
Java unit test plan (extends `DelegatedResourceAccountIndexStoreTest`/`BaseTest` pattern already in repo):
1. Build a `DelegatedResourceAccountIndexCapsule` for address `A` with `N = 50_000` unique `toAccountsList` entries (random addresses), via `setAllToAccounts`, mirroring `testConvert()`.
2. `delegatedResourceAccountIndexStore.put(A, capsule)`.
3. Enable `dynamicPropertiesStore.saveAllowDelegateOptimization(1L)`.
4. Construct an `UnfreezeBalanceActuator` (or `FreezeBalanceActuator`) transaction touching address `A` as owner or receiver, unrelated to the pre-built backlog, and call `actuator.execute(ret)`.
5. Measure wall-clock time and count `put`/`delegate` calls triggered transitively by `convert(A)` inside `execute()`.
6. Assert that execution time/DB-write count scales linearly with `N` and is not bounded by a constant independent of the attacker-chosen backlog size — demonstrating the unpriced O(n) cost shifted onto the triggering transaction.

```java
  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
```
