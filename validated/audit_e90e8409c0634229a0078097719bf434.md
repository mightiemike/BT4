### Title
`liquidate-multi` swallows a mid-fold `socialize-debt-asset` failure inside `liquidate`, permanently committing partial vault write-downs and debt-removal side effects instead of rolling back - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` invokes the public function `liquidate` directly through the private helper `call-liquidate` inside a `map`, and then unconditionally wraps the whole result list in `(ok ...)` [1](#0-0) . Because `liquidate` is called intra-contract (not via `contract-call?`), Clarity's automatic rollback-on-error checkpointing — which only wraps `contract-call?` boundaries — does not apply to `liquidate`'s own failure; any prior successful nested `contract-call?`s it made (vault repay, debt removal, collateral seizure, and any already-successful `socialize-debt-asset` fold iterations) remain permanently committed even when `liquidate` itself ultimately returns an `err`.

### Finding Description
1. `liquidate-multi` builds `(ok (map call-liquidate positions))` [1](#0-0) ; `call-liquidate` calls `(liquidate ...)` directly with `price-feeds` = `none` [2](#0-1) . This is a plain in-contract function call, not `contract-call?`.
2. Inside `liquidate`, once `no-collateral-left` is true, the fold `(fold socialize-debt-asset fresh-debt-list {borrower: borrower, success: true})` runs, followed by `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [3](#0-2) .
3. In `socialize-debt-asset`, for each debt entry the accumulator carries a `success` flag; on the first failing entry it short-circuits all remaining entries but the *prior* entries' effects (each committed via its own `contract-call?` to `.v0-market-vault` for `vault-socialize-debt` and `debt-remove-scaled`, plus the intra-contract `map-set index-cache` write) are not undone [4](#0-3) .
4. If any later entry's `vault-socialize-debt` or `debt-remove-scaled` fails, `unwrap!` yields `failed-status`, the fold returns `success: false`, and the `asserts!` at line 1548 fails - `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.
5. Because that failure occurs inside a direct (non-`contract-call?`) invocation of `liquidate`, and `liquidate-multi` never checks per-entry results before wrapping everything in `(ok ...)`, the top-level transaction succeeds. All previously-committed `contract-call?`s inside that particular `liquidate` invocation - `vault-system-repay`, `debt-remove-scaled` for the primary debt asset, `collateral-remove` to the liquidator, and any prior fully-successful `socialize-debt-asset` write-downs - stay permanently committed, while the remaining, un-socialized debt entries are neither removed from the borrower's book nor reflected in the emitted `bad-debt-socialized`/`liquidate` events (those `print`s never execute for this position, since `liquidate` returned before reaching them).
6. The invariant "the state a safety check approved is the state the money movement executes against" breaks: the `asserts!` intended to guarantee full-list socialization or full failure only prevents the *logical* success value from being `ok`; it cannot undo money movement that already happened through independently-committed `contract-call?`s.

### Impact Explanation
The vault(s) for already-processed debt entries have their liabilities written down (loss socialized to depositor shares) while the borrower's remaining scaled debt for other assets is left outstanding and now uncollateralized (`no-collateral-left` was already true), permanently orphaning that liability with no corresponding collateral or vault-side counterpart. This produces an unreconciled shortfall between recorded vault liabilities/asset backing and the sum of individual borrower obligations, i.e., stranded/lost value at the protocol level, matching Critical-severity protocol insolvency / permanent freezing of funds. It also silently loses the `bad-debt-socialized` audit trail for the affected position, since the emitting `print` never executes for the failing entry.

### Likelihood Explanation
The interleaving is not attacker-forced in a simple, single-shot way - it requires a later step within `socialize-debt-asset`'s fold (a second `vault-socialize-debt` or `debt-remove-scaled` call) to fail while an earlier step already succeeded, which depends on vault-side conditions not fully characterized here. The entry point (`liquidate-multi` with `price-feeds` = `none`, unprivileged, single transaction) is trivially reachable by any caller, and no special capital or governance access is required, but reliably engineering the specific mid-fold failure requires further confirmation against `v0-market-vault.clar`'s `vault-socialize-debt`/`debt-remove-scaled` failure conditions, which were not available in this review.

### Recommendation
Route `liquidate` calls from `call-liquidate`/`liquidate-multi` through `contract-call?` (even self-referential) so that a failing `liquidate` invocation is rolled back atomically at that boundary, or explicitly check each `map` result in `liquidate-multi` and `asserts!`/revert the whole batch (or the specific failed sub-flow) on any `err`, matching the documented "success flag" invariant to actual on-chain state.

### Proof of Concept

A Clarinet simnet PoC should: (a) set up a borrower with two debt assets and zero remaining collateral so `no-collateral-left` is true and the `fresh-debt-list` has ≥2 entries; (b) engineer/mock a condition where the second entry's `vault-socialize-debt` or `debt-remove-scaled` returns `err` (e.g., by manipulating vault state between fold iterations); (c) call `liquidate-multi` with that position and assert the transaction returns `(ok (list (err ERR-BAD-DEBT-SOCIALIZATION-FAILED)))`; (d) assert post-state shows the first debt asset's vault write-down and the primary debt/collateral movement already committed, while the second debt asset remains on the borrower's book with no collateral - demonstrating stranded, unreconciled value despite the reported `err`.

```text
(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
```
