## Title
Signature malleation allows fabricating a "second" PoisonMicroblock header from a single genuine miner signature, causing coinbase slashing without real equivocation - (`stackslib/src/chainstate/stacks/db/transactions.rs`, `stacks-codec/src/transaction.rs`)

## Summary
`check_microblock_header_signer` and the underlying `StacksMicroblockHeader::check_recover_pubkey` use `recover_to_pubkey_without_validating_low_s`, which accepts high-S malleated ECDSA signatures and recovers the same public key hash. The only "distinctness" guard on `PoisonMicroblock` headers, `TransactionPayload::PoisonMicroblock`'s `consensus_deserialize` check (`h1 == h2` rejection at `stacks-codec/src/transaction.rs:2905-2925`), compares raw struct fields including the raw `signature` bytes — so a signature malleated to its `s' = -s mod n` counterpart trivially satisfies "must differ in some field" while representing the exact same semantic signature over the exact same message.

## Finding Description
The broken equality is: **"a valid `PoisonMicroblock` report proves two distinct signed microblock headers (i.e., real equivocation by the miner)"** vs. what the code actually enforces: **"two `StacksMicroblockHeader` structs that differ in *any* byte and recover to the same pubkey hash."**

The relevant path:
- `StacksMicroblockHeader::check_recover_pubkey` (`stacks-codec/src/transaction.rs:2598-2616`) calls `StacksPublicKey::recover_to_pubkey_without_validating_low_s` (`stacks-common/src/util/secp256k1/native.rs:200-205`), which skips the low-S canonicalization check present in `recover_to_pubkey` (used for normal tx auth). This means both the original signature `s` and its malleated counterpart `s' = n - s` (with adjusted recovery id) recover to the identical public key / `Hash160`.
- `check_microblock_header_signer` (`stackslib/src/chainstate/stacks/db/transactions.rs:684-712`) only checks `pkh1 == pkh2`; it does not compare any other content of the two headers (sequence, prev_block, tx_merkle_root are never diffed here).
- The only place that requires the two headers to differ is the codec-level guard in `TransactionPayload::consensus_deserialize` (`stacks-codec/src/transaction.rs:2905-2925`): `if h1 == h2 { ... "microblock headers match" }`. This is a byte-level struct equality check. Since malleating `s` changes the raw `signature` bytes, `h1 != h2` trivially holds even when `version`, `sequence`, `prev_block`, and `tx_merkle_root` are all identical and only one real signing event ever occurred.
- `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs:722-856`) then accepts the pair, uses `mblock_header_1.sequence` as `reported_seq`, and records/updates a poison report via `insert_microblock_poison`. Downstream, `calculate_miner_reward` in `stackslib/src/chainstate/stacks/db/accounts.rs:804-980` diverts a fraction of the miner's coinbase (`poison_microblock_commission`) to the reporter whenever `get_poison_microblock_report` returns a hit for that block height — regardless of whether the underlying "fork" was real.

**Why existing guards fail:** None of the three checks (`consensus_deserialize` equality, `check_microblock_header_signer` pubkey-hash match, `handle_poison_microblock`'s height/maturity checks) verify that the two headers encode *semantically distinct signed content* (different `sequence`+`prev_block`+`tx_merkle_root` combination representing genuine equivocation). Malleating a signature is a zero-cost, deterministic elliptic-curve operation requiring no private key knowledge — the attacker only needs to observe one broadcast/relayed microblock header and its `MessageSignature`.

## Impact Explanation
If exploitable end-to-end, this would allow an unprivileged attacker (anyone who observes a broadcast microblock) to submit a `PoisonMicroblock` transaction using the real header plus a malleated clone, causing:
- `handle_poison_microblock` to accept the report as if it proved a real fork.
- The honest miner's coinbase for that block height to be slashed via `calculate_miner_reward`'s `poison_reporter_opt` branch, with a commission diverted to the attacker's address.

This matches the "poison or reward mis-payment bounded to fees" / miner-coinbase-theft category described as **High/Critical** in the rules, since it results in reward paid to the wrong party (the attacker) at the expense of an honest miner who never equivocated.

## Likelihood Explanation
- **Preconditions:** Requires only observing one broadcast, signed `StacksMicroblockHeader` (trivial — miners broadcast microblocks publicly) and performing standard secp256k1 signature malleation (`s' = n - s`, flipped recovery id) — this needs no private key and is a well-known, cheap operation.
- **Cost:** Attacker needs only to submit one `PoisonMicroblock` transaction (a normal `StacksTransaction` with a fee) into the mempool/mined block; no BTC spend or stake is required beyond the transaction fee.
- **Repeatability:** In principle repeatable against any miner's signed microblocks, for any epoch/build where microblocks and `PoisonMicroblock` handling are active (legacy Stacks 2.x microblock era; the `#[cfg(not(any(test, feature = "testing")))]` gate around signature well-formedness in `consensus_deserialize` is a red herring — it only checks that the signature parses as a valid recoverable signature, not that it is low-S-canonical, and it exists in production builds).
- **Caveat on likelihood:** I could not locate, within the available index, the code path that ultimately validates whether the "malleated" signature's recovery id computation actually decodes/serializes correctly through the `MessageSignature` 65-byte format and `to_secp256k1_recoverable()` parsing used elsewhere in the codebase (i.e., I have not been able to confirm there is no additional low-S enforcement earlier in the mempool/block-acceptance pipeline for `PoisonMicroblock`-specific transactions, only that `check_recover_pubkey` itself doesn't enforce it). Given the index size limits, I recommend a Devin session be used to fully trace the mempool admission path (`mempool.rs`) and confirm no additional signature-canonicalization gate exists before `handle_poison_microblock` is reached for a mined block.

## Recommendation
- In `TransactionPayload::consensus_deserialize`'s `PoisonMicroblock` branch, reject headers whose *semantic* content (fields other than `signature`) is identical, in addition to (or instead of) full-struct equality — i.e., require the headers to differ in `sequence`+`prev_block`+`tx_merkle_root`, not merely in raw signature bytes.
- Alternatively/additionally, enforce low-S canonicalization on microblock header signatures (use `recover_to_pubkey` instead of `recover_to_pubkey_without_validating_low_s` in `check_recover_pubkey`), so that malleated high-S signatures are rejected outright during header verification.
