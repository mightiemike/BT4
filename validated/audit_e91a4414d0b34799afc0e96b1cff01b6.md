## Finding

### Title
Replay-verification skips authenticated state-checkpoint root fields, allowing corrupted state roots to pass verification undetected - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by Aptos's archive replay-verification tooling to confirm that re-executing a transaction produces the exact ledger state that was originally committed and signed off on by validators. This function checks status, gas, the write-set hash, and the event root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields in `TransactionInfo` that commit to the authenticated Merkle/JMT state root of the ledger. A bug in state-summary/root computation (JMT construction, hot-state summary, or the newer position-state accumulator) that produces a wrong root, while still applying the identical per-transaction write set, will silently pass replay verification.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates a freshly-executed `TransactionOutput` against a `TransactionInfo` pulled from an authenticated backup/archive. It checks:
- execution status
- gas used
- `write_set_hash == txn_info.state_change_hash()`
- `event_root_hash == txn_info.event_root_hash()`

It explicitly does **not** check the checkpoint-root fields, and the code says so directly: [2](#0-1) 

`TransactionInfoV1` (the authenticated, signed structure written to the ledger/transaction accumulator) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class committed fields, per the builder at [3](#0-2) . These roots are computed independently of the per-transaction write set by `DoStateCheckpoint::run`, which folds writes into a `LedgerStateSummary`/JMT and, when the trading-native feature is enabled, into a separate position-state accumulator: [4](#0-3) . Because these roots are derived through their own tree-construction/accumulator logic (distinct from simply hashing the write set), a defect there (e.g. in JMT restore, hot-state folding, or `compute_position_checkpoint`'s SMT extension) can yield a wrong root while the write-set hash and event root remain byte-identical to what a correct execution would produce.

The only call site that uses this comparator for security-relevant verification is the archive replay-verify tool: [5](#0-4) 

Because `ensure_match_transaction_info` never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, `replay_on_archive` — Aptos's tool for proving that replaying an entire backup produces bit-identical ledger state to what was originally committed and certified by validator signatures — will report success even when the locally recomputed authenticated state root diverges from the one recorded (and signed) in the historical `TransactionInfo`.

### Impact Explanation
This breaks the "committed state must match the correct VM/state-summary result" and "proof/commitment fields must survive... unchanged" invariants for the one tool whose job is to detect exactly that class of divergence. A latent bug in state-root construction (JMT restore, hot-state, or the newly-added position-state accumulator) could go completely undetected by replay-verify across the entire history of a chain, since the check that would have caught it (`state_checkpoint_hash` / `position_state_checkpoint_hash` mismatch) is never performed. This is a hard-fork-class integrity gap: replay/verification tooling gives false assurance of correctness for authenticated state commitments, exactly the "Hard-fork-only divergence during commit, replay, restore, or proof verification" category called out as in-scope.

### Likelihood Explanation
The gap is unconditional — it applies to every invocation of `replay_on_archive`, not to a rare edge case — and it is explicitly acknowledged by an in-code TODO, confirming it is a currently-live gap rather than a hypothetical one. It requires no attacker privilege: any accidental non-determinism or logic bug in the (relatively new and actively evolving) position-state / hot-state checkpoint computation is sufficient to trigger silent divergence that operators/auditors relying on `replay_on_archive` would fail to catch.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (recomputing the corresponding roots from the executed output) against the values carried in the trusted `TransactionInfo`, removing the current carve-out, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state or hot-state checkpointing is relied upon in production replay-verification.

### Proof of Concept
Not directly exploitable by an external attacker (no privileged bypass), but demonstrable statically: inspect `ensure_match_transaction_info` at [1](#0-0)  and note it only asserts on `status`, `gas_used`, `write_set_hash`, and `event_root_hash`, while `TransactionInfoV1` carries three additional checkpoint-root fields (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`, see builder at lines 2261-2284) that are never read by this function. Any test that constructs a `TransactionOutput` whose write set/events hash correctly but is checked against a `TransactionInfo` with a deliberately mutated `state_checkpoint_hash`/`position_state_checkpoint_hash` will show `ensure_match_transaction_info` returning `Ok(())`, and consequently `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` (lines 388-406) reporting no failure.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
