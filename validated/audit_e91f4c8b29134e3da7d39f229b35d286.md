## Finding

### Title
Replay-verification skips checkpoint-hash comparison, letting corrupted/incorrect state roots pass as "verified" - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the routine used by chunk-executor replay and db-tool's replay-verify to authenticate a re-executed transaction against the `TransactionInfo` recorded on-chain, only compares `status`, `gas_used`, `write_set` hash, and `event_root_hash`. It explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, even though these fields are part of the authenticated `TransactionInfo` that is itself covered by the transaction-accumulator proof / `LedgerInfo` signatures.

### Finding Description [1](#0-0) 

The function is documented with its own admission of the gap: [2](#0-1) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

`TransactionInfo` (`V0`/`V1`) carries `state_checkpoint_hash` and (for `V1`) `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, all of which are folded into the `TransactionInfo` hash that is the accumulator leaf authenticated by consensus signatures: [3](#0-2) [4](#0-3) 

These hashes are computed from the state/position Merkle checkpoints during normal executor commit (`DoLedgerUpdate::assemble_transaction_infos`), so the checkpoint hash is the authenticated binding between a transaction and the resulting state tree root: [5](#0-4) 

`ensure_match_transaction_info` is called from `chunk_executor` when replaying archived transactions to validate that locally re-executed output matches the persisted, cryptographically-authenticated `TransactionInfo` before that output is accepted/re-committed, and from the CLI/debugger tooling that underlies db-tool's `replay_on_archive` used in replay-verify pipelines: [6](#0-5) 

Because the state-checkpoint hash (and, once the "trading-native" position-state feature is enabled, the position-state checkpoint hash) is skipped, a locally computed state root that diverges from the one actually committed/signed by validators will not be flagged. The check silently treats "same write-set hash + same events + same status/gas" as sufficient proof of a matching final state, when it is not — a corrupted or incorrectly re-derived Merkle/JMT root for the state tree (or, once native position-state is turned on, the position tree) would go undetected.

### Impact Explanation
This breaks the "authenticated API/state-view output bound to the right ledger version, object, and proof context" and "replay must preserve deterministic proof binding" invariants called out in the task's proof/storage pivots. Replay-verify is one of the primary defenses used to detect a hard fork, storage corruption, or a bug that produces an incorrect state root while other fields (write set bytes, events) happen to still line up — or, more concerning, any bug in the state-checkpoint/position-checkpoint hash computation path itself (e.g., in `DoStateCheckpoint`/native-position handling) would not be caught by replay-verify because this comparator is the gate used to confirm correctness. Since Aptos is actively rolling out a "trading-native"/native position-state feature guarded by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, enabling that feature while this comparator remains incomplete means the position-state root — a new piece of durable, authenticated ledger data — has no independent verification path during replay, so replay-verify could report false-positive "matches" even when the authenticated position state root diverges from local execution, exactly as the code's own comment states. This is a genuine gap in mainnet state-integrity tooling (not a Consensus Observer/DAG/permissioned-signer issue), but its severity is currently bounded because, per the same comment, the intent is to enable this check before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` goes live — i.e., the feature this specific hash defends is still gated off.

### Likelihood Explanation
The main-state `state_checkpoint_hash` gap is already live today (V0 and V1 transaction infos always carry it), so any historical divergence in the main state Merkle root (from an executor bug, a storage bug, or a malicious/corrupted archive) is already unverifiable via `ensure_match_transaction_info`. Realizing broad impact from this specific gap requires either (a) an independent bug/corruption that causes the state root to diverge while write set/events still hash identically (a further precondition), or (b) enabling the not-yet-active `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state feature, at which point the hole in verifying `position_state_checkpoint_hash` becomes directly exploitable by any replay/backup discrepancy in the position tree. This makes it a real, provable gap in the verification code today, though its blast radius is currently limited to detection-only paths (chunk replay validation, db-tool replay-verify) rather than the primary consensus/commit hot path, and is explicitly acknowledged as pending work in-repo rather than a silent, unknown defect.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, and — once available/relevant — `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against the locally recomputed values before treating a replayed transaction as verified. Do this before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production, as the code comment itself recommends, so that replay-verify tooling cannot report success while the authenticated state (or position-state) root has actually diverged.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-logic gap discoverable by static code inspection: [1](#0-0)  shows the comparator never touches `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, while [7](#0-6)  confirms these fields exist on `TransactionInfo` and are part of its authenticated hash. A conceptual PoC: during replay, construct a `TransactionOutput` whose write set and events exactly match the recorded `TransactionInfo`, but whose underlying state tree (or position tree, if native-position is enabled) was built from a different sequence of intermediate writes yielding a different checkpoint root; `ensure_match_transaction_info` will return `Ok(())` despite the mismatched root because it never checks it.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
