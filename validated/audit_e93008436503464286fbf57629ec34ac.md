### Title
Gas-griefing bypass of the NEAR Wallet Contract's relayer gas-sufficiency ban check — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The reported Nouns-Builder bug is a class of "gas-griefing changes a `try/catch` outcome": an attacker crafts the exact amount of gas forwarded to an external call so that it fails only due to gas exhaustion (not real business logic), and the surrounding error-handling path (a `catch`) then performs a state-changing action that would not occur under normal, well-gassed execution. The closest reachable analog in nearcore is the NEAR Wallet Contract's relayer gas check in `validate_tx_relayer_data`, which decides — based on `env::prepaid_gas()` measured at one point in execution — whether a relayer attached "enough" gas, but the actual gas available at the point the real cross-account action is later dispatched can be lower, because further gas is burned by parsing/validation/(sometimes) an async registrar round-trip in between.

### Finding Description
`inner_rlp_execute` → `parse_rlp_tx_to_action` → `validate_tx_relayer_data` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:312-368`) performs the sole gas-sufficiency check for a relayer-submitted Ethereum-style transaction: [1](#0-0) 

```
    // Relayers must attach at least as much gas as the user requested.
    let gas_limit = if tx.gas_limit < U64_MAX { tx.gas_limit.as_u64() } else { u64::MAX };
    if env::prepaid_gas().as_gas() < gas_limit.saturating_mul(GAS_MULTIPLIER) {
        return Err(Error::Relayer(RelayerError::InsufficientGas));
    }
```

`env::prepaid_gas()` is the *total* gas attached to the current function-call execution (a constant for the whole call), not the *remaining* gas at the point the check runs. This check happens partway through `inner_rlp_execute`, before the actual downstream action/promise is dispatched (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:108-128`, `internal.rs` and `action_to_promise` further down the call). Additional gas is consumed after the check for: RLP parsing, ABI decoding, and — for many `TransactionKind::EthEmulation` paths — an intermediate cross-contract call to the address registrar with its own callback (`address_check_callback`, `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:130-192`), which itself consumes gas before the "real" action promise is finally created.

If the relayer's `prepaid_gas()` exactly (or just barely) satisfies `gas_limit * GAS_MULTIPLIER` at the time of the check, but the real action ends up requiring more gas than what remains after all the intervening gas burn, the WASM host runtime will abort the *entire* function-call execution with `HostError::GasExceeded`/`GasLimitExceeded` (`runtime/near-vm-runner/src/logic/gas_counter.rs:152-215`) rather than following the contract's own graceful `RelayerError::InsufficientGas` → `create_ban_relayer_promise` path (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:121-125`).

This distinction matters because of nearcore's receipt-atomicity invariant: on `Err`, the whole receipt's `TrieUpdate` is rolled back (`runtime/runtime/src/lib.rs:961-970`, documented in `protocol-model/spec/runtime-execution.md:149`: *"Failed receipt atomicity: a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting."*). Consequently, when a relayer deliberately engineers the gas amount to pass the check but fail later purely on gas, `self.nonce` is never incremented and the relayer's access key is never banned via `ban_relayer`/nonce-increment logic — unlike the intended "faulty relayer" ban flow that is exercised and asserted by the contract's own test suite for every other kind of relayer misbehavior (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs`).

### Impact Explanation
A malicious or compromised relayer holding a `FunctionCall` access key to a user's Wallet Contract (the standard relayer on-boarding flow documented in `test_register_relayer`) can repeatedly submit transactions that pass the shallow `prepaid_gas()` check but are engineered to run out of gas deeper in execution (during ABI decode, registrar round-trip, or promise dispatch). Because the resulting `GasExceeded`/`GasLimitExceeded` error is a `VMOutcome.aborted` failure that rolls back all state, the contract's designed anti-abuse mechanism (revoking the relayer's access key on any relayer fault, and advancing the nonce to prevent stale-nonce replay) never fires. This lets the malicious relayer indefinitely grief the user by never being banned while their access key remains valid, effectively denying the user reliable use of the wallet through that access key (their transactions can be starved/blocked) without triggering the safety mechanism explicitly built to detect and stop exactly this class of relayer misbehavior — a transaction-triggered halt of the intended protection logic for that account, reachable by any account holding (or that manages to obtain) a function-call key to the wallet contract.

### Likelihood Explanation
The relayer role is by design an untrusted, external, unprivileged party (the whole point of the Wallet Contract's relayer model is that a possibly-adversarial relayer pays gas on behalf of the user), so the actor model matches "unprivileged transaction/contract caller." Constructing a transaction whose gas consumption crosses this specific boundary requires only knowledge of the constant gas costs in this contract (parsing/callback constants such as `RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS` are fixed constants defined in `lib.rs:34-41`), which are visible in the deployed contract's compiled code and are deterministic — an attacker can reliably compute the exact attached-gas value needed to pass the check but still run out later.

### Recommendation
Perform the gas-sufficiency check against the gas actually remaining at (or immediately before) the point the real downstream promise/action is dispatched — i.e., compare `env::prepaid_gas() - env::used_gas()` (or an equivalent remaining-gas measurement taken right before creating the final action promise) against `gas_limit * GAS_MULTIPLIER` plus the fixed overhead of any intervening cross-contract calls (registrar lookup, callbacks), rather than checking total `prepaid_gas()` once, early, before that overhead has been paid.

### Proof of Concept
Conceptual outline (unable to execute in this ask-only session; verification would require a Devin session running `runtime/near-wallet-contract`'s sandbox test harness):
1. Deploy a Wallet Contract instance and register a relayer access key, as in `test_register_relayer` (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs:25-52`).
2. Craft a signed Ethereum-style transaction whose `target` requires the address-registrar round trip (`EthEmulationKind`), so that meaningful gas is spent between the `validate_tx_relayer_data` check and the final action dispatch.
3. Attach `gas` to the outer `rlp_execute` NEAR call equal to exactly `gas_limit.saturating_mul(GAS_MULTIPLIER)` (satisfying the check) but insufficient to also cover parsing + registrar round trip + final dispatch.
4. Submit via the relayer key repeatedly and observe: the call fails with a raw `GasExceeded`/`GasLimitExceeded` VM error (not `"Error: faulty relayer"`), and — unlike `test_relayer_insufficient_gas` (`relayer.rs:278-324`), which asserts `assert_revoked_key` — the relayer's access key remains valid and its nonce state is untouched, allowing indefinite repetition.
