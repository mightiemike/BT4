## Title
`grow_index` can compute a no-op new capacity due to integer-division rounding, causing an infinite retry loop when growing a small/nearly-full index bucket - (File: `bucket_map/src/bucket.rs`)

### Summary
`Bucket::grow_index` computes the next index-bucket capacity as `(current_capacity * 110 / 100).max(anticipated_size)`. For small `current_capacity` values, integer-division rounding truncates the 10% growth increment to zero, so `new_capacity` can equal `current_capacity`. This is the same root cause as the referenced Putty finding: a percentage-based calculation that rounds down to zero and is then used in a code path that assumes a nonzero/effective change, causing the operation to be perpetually retried instead of failing loudly.

### Finding Description
`grow_index` is called whenever an index bucket runs out of space during insertion (`BucketMapError::IndexNoSpace`). Its job is to reallocate a strictly larger index storage and re-insert every existing entry into it: [1](#0-0) 

```
pub fn grow_index(&self, mut current_capacity: u64) {
    if self.index.contents.capacity() == current_capacity {
        let anticipated_size = self.anticipated_size * 140 / 100;
        ...
        loop {
            count += 1;
            // grow relative to the current capacity
            let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
            let (mut index, file_name) = BucketStorage::new_with_capacity(..., Capacity::Actual(new_capacity), ...);
            current_capacity = index.capacity();
            let mut valid = true;
            for ix in 0..self.index.capacity() {
                if !self.index.is_free(ix) {
                    let new_ix = Self::bucket_create_key(&mut index, &elem.key, self.random, true);
                    if new_ix.is_err() { valid = false; break; }
                    ...
                }
            }
            if valid { ...; break; }
        }
        ...
    }
}
```

`current_capacity * 110 / 100` uses integer arithmetic, so for small capacities the 10% increment rounds down to 0 (e.g. `9 * 110 / 100 = 9`). If `anticipated_size` (derived from `self.anticipated_size * 140 / 100`, which is also subject to the same rounding, and defaults to 0 unless `set_anticipated_count` was called with a nonzero value) is not larger than `current_capacity`, then `new_capacity == current_capacity`. `BucketStorage::new_with_capacity` may then allocate a storage of the same (or, due to page-alignment rounding in `allocate_to_fill_page`, possibly the same) size as before via `Capacity::Actual`.

Since the new storage has the same capacity and the same `max_search`, re-inserting the same set of keys via `bucket_create_key` (which does its own linear probing bounded by `max_search`) has the same probability of failing with `Err(BucketMapError::IndexNoSpace)` that caused the original growth need. When it fails, `valid` is set to `false` and the loop iterates again, but `current_capacity` is reassigned to `index.capacity()`, which is the same value as the previous iteration — so `new_capacity` is computed identically on the next pass. The loop has no escape condition other than `valid == true`, so if the recompute is a true no-op, the function spins forever recomputing the same capacity and re-attempting the same (deterministically failing) reindex, burning CPU without making progress.

This mirrors the reported bug class exactly: a percentage-based amount rounds down to zero, and the code that consumes that value has no explicit check for the zero/no-op case, so instead of visibly failing (like the reverting zero-value ERC-20 transfer), it degrades into an unbounded, silent retry loop.

### Impact Explanation
If triggered on a validator/RPC node's accounts index bucket map (disk index enabled, e.g. `IndexLimit::Minimal` or `Threshold`), this would manifest as `grow_index` spinning indefinitely on a single thread holding the write path for that bucket, causing:
- Disproportionate CPU cost (a hot, unproductive loop) on the thread performing the insert that triggered the growth.
- Indefinite blocking of further writes to that accounts-index bucket, since `grow_index` is invoked synchronously from the insert path, effectively hanging accounts-index updates for that bin.

This falls within the accepted “disproportionate storage and CPU cost” validation criterion.

### Likelihood Explanation
Likelihood depends on how small `current_capacity` can realistically get and whether `anticipated_size` is ever nonzero and larger. Bucket sizes are normally seeded from `DEFAULT_CAPACITY_POW2` and grown geometrically as pubkeys are inserted, so `current_capacity` is unlikely to remain in the very small range (single digits) where 10%-growth rounds to zero for long in a production cluster with many accounts. This makes the scenario plausible primarily in low-population bins, freshly created buckets, or pathological/degenerate distributions of pubkeys across bins (bucket assignment is derived from the pubkey's high bits, so an adversary cannot directly force a specific bin's population, but small/edge-case configurations, e.g. test/validator startup with very few accounts or a bucket map manually configured with a tiny `max_buckets`, could be affected). I could not fully verify from static reading alone whether `allocate_to_fill_page`'s page-size rounding in `BucketStorage::new_with_capacity` always bumps `Capacity::Actual` up enough to break the tie in practice for all cell sizes, which would mitigate (but not eliminate) the issue in some configurations — this needs runtime verification.

### Recommendation
In `grow_index`, explicitly guard against a no-op capacity increase: compute `new_capacity` and if it is not strictly greater than `current_capacity`, force it to `current_capacity + 1` (or some minimum absolute increment) before calling `BucketStorage::new_with_capacity`, e.g.:
```rust
let new_capacity = (current_capacity * 110 / 100)
    .max(anticipated_size)
    .max(current_capacity + 1);
```
Additionally, consider adding a maximum-retry bound (or a `debug_assert!`/metric) on the `loop` in `grow_index` so that if reindexing repeatedly fails at the same capacity, the condition is detected and logged/panicked rather than spinning forever.

### Proof of Concept
Conceptual repro (not executed):
1. Construct a `Bucket<T>` whose index `BucketStorage` has a very small `Capacity::Actual` (e.g. 9) via `BucketStorage::new_with_capacity(..., Capacity::Actual(9), ...)`, and do not call `set_anticipated_count` (so `anticipated_size == 0`).
2. Fill the index bucket to capacity so any further insert returns `BucketMapError::IndexNoSpace`, and call `bucket.grow_index(9)`.
3. Observe that `new_capacity = (9 * 110 / 100).max(0) = 9`, equal to `current_capacity`; `BucketStorage::new_with_capacity` allocates a storage with `capacity() == 9` (subject to page-rounding); the reindex loop attempts to reinsert the same keys into a same-capacity table with the same `max_search`, which — for a table that was already full — fails again with the same error, setting `valid = false` and looping without termination.         if self.index.contents.capacity() == current_capacity {
            // make sure to grow to at least % more than the anticipated size
            // The indexing algorithm expects to require some over-allocation.
            let anticipated_size = self.anticipated_size * 140 / 100;
            let mut m = Measure::start("grow_index");
            //debug!("GROW_INDEX: {}", current_capacity_pow2);
            let mut count = 0;
            loop {
                count += 1;
                // grow relative to the current capacity
                let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
                let (mut index, file_name) = BucketStorage::new_with_capacity(
                    Arc::clone(&self.drives),
                    1,
                    std::mem::size_of::<IndexEntry<T>>() as u64,
                    Capacity::Actual(new_capacity),
                    self.index.max_search,
                    Arc::clone(&self.stats.index),
                    Arc::clone(&self.index.count),
                );
                // index may have allocated something larger than we asked for,
                // so, in case we fail to reindex into this larger size, grow from this size next iteration.

                    if !self.index.is_free(ix) {
                        let elem: &IndexEntry<T> = self.index.get(ix);

                            valid = false;
                            break;
                        }
                        let new_ix = new_ix.unwrap();
                        let new_elem: &mut IndexEntry<T> = index.get_mut(new_ix);

    pub fn new_with_capacity(
        drives: Arc<Vec<PathBuf>>,
        num_elems: u64,
        elem_size: u64,
        mut capacity: Capacity,
        max_search: MaxSearch,
        stats: Arc<BucketStats>,
        count: Arc<AtomicU64>,
    ) -> (Self, u128) {
        let offset = Self::get_offset_to_first_data();
        let cell_size = elem_size * num_elems + offset;
        let bytes = Self::allocate_to_fill_page(&mut capacity, cell_size);
        let (mmap, path, file_name) = Self::new_map(&drives, bytes, &stats);
        (
            Self {
                path,
                mmap,
                cell_size,
                count,
                stats,
                max_search,
                contents: O::new(capacity),
                // by default, newly created files will get deleted when dropped
                delete_file_on_drop: true,
            },
            file_name,
        )
    }

    fn allocate_to_fill_page(capacity: &mut Capacity, cell_size: u64) -> u64 {
        let mut bytes = capacity.capacity() * cell_size;
        if let Capacity::Actual(_) = capacity {
            // maybe bump up allocation to fit a page size
            const PAGE_SIZE: u64 = 4 * 1024;
            let full_page_bytes = bytes / PAGE_SIZE * PAGE_SIZE / cell_size * cell_size;
            if full_page_bytes < bytes {
                let bytes_new = ((bytes / PAGE_SIZE) + 1) * PAGE_SIZE / cell_size * cell_size;
                assert!(
                    bytes_new >= bytes,
                    "allocating less than requested, capacity: {}, bytes: {bytes}, bytes_new: \
                     {bytes_new}, full_page_bytes: {full_page_bytes}",
                    capacity.capacity()
                );
                assert_eq!(bytes_new % cell_size, 0);
                bytes = bytes_new;
                *capacity = Capacity::Actual(bytes / cell_size);
            }
        }
        bytes
    }
