### Title
Unbounded Storage Growth in `KVSessionStorage` via Repeated Session Persistence (No Deduplication) - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession` appends the session id to a per-shop index list on every single invocation, without checking whether that id is already present [3](#0-2) . The private `addShopIds` helper simply concatenates the new id(s) onto the existing array and writes it back, with no deduplication or size bound [4](#0-3) . This mirrors the Mintbase `nft_on_approve` bug class: an operation that increases persistent storage usage on every call is exposed on a code path an ordinary (non-privileged) actor can trigger repeatedly, with no cost, rate limit, or idempotency check to bound the growth.

### Finding Description
`storeSession` is called from several normal authentication paths whenever the offline access token needs to be (re)persisted — most notably `ensureOfflineTokenIsNotExpired`, which is invoked on essentially every authenticated request (admin, webhook, app-proxy) whenever the stored offline token is within 5 minutes of expiring [1](#0-0) , and from the token-exchange authentication strategy, which persists a (re-)exchanged offline session whenever no active session is found [5](#0-4) .

Because the offline session id is deterministic per shop (`getOfflineId(shop)`), every one of these refresh/persist events writes to the *same* KV key for the session record, but `addShopIds` still appends that same id again to the `shop:<shop>` index array without ever checking for an existing entry [4](#0-3) . Nothing in this flow deduplicates, caps, or charges for this growth — the KV `deleteSession`/`removeShopIds` path is the only place ids are ever pruned, and it is not invoked on the refresh path [6](#0-5) .

An actor who can force repeated token refreshes/exchanges against their own shop's session (a single, unprivileged merchant/customer-level actor — no admin/internal privilege required) can therefore cause the `shop:<shop>` KV value to grow without bound, purely by making ordinary authenticated requests over time (or forcing session invalidation/expiry cycles). This is directly analogous to the reported `nft_on_approve` issue: an operation that is individually "valid"/authorized still increases shared storage on every call, with no mechanism requiring the caller to fund or bound that increase.

### Impact Explanation
Unbounded growth of the `shop:<shop>` KV value will eventually:
- Exceed the KV backend's per-value size limits, causing `findSessionsByShop`/`storeSession`/`addShopIds` to fail for that shop, denying future session persistence and effectively locking the shop out of session-storage-backed session refresh (`ensureValidOfflineSession` returning stale/broken data, or writes throwing) [7](#0-6) .
- Increase read/write latency and cost for every session read/write on that shop as the JSON array is repeatedly serialized/deserialized and grown, degrading availability of the auth/session layer for that tenant (a DoS of the session-storage/auth-refresh path), even without any malicious behavior beyond normal repeated use.

This does not grant cross-tenant access or credential exposure — the impact is confined to storage exhaustion / availability degradation of the session-storage backend for the affected shop(s), which use this specific adapter.

### Likelihood Explanation
Any app using `@shopify/shopify-app-session-storage-kv` in production is affected, since the growth occurs on the standard token-refresh/token-exchange code paths that are exercised by ordinary app usage (every request that needs to refresh a soon-to-expire offline token, or repeat token exchanges) [8](#0-7) . No special privilege is required — a merchant/customer simply needs to interact with the app over a long enough period (or an attacker can intentionally force repeated re-authentication/token-exchange cycles) to accumulate duplicate ids indefinitely.

### Recommendation
In `addShopIds`, check whether each id already exists in the array before appending (or use a `Set`) so that re-persisting the same session id is a no-op for the index list. Consider bounding/capping the index array size and reconciling it (e.g., pruning ids whose corresponding session no longer exists) rather than relying solely on `deleteSession`/`deleteSessions` to prune stale entries.

### Proof of Concept
1. Configure an app with `KVSessionStorage` and `expiringOfflineAccessTokens` enabled.
2. As a normal merchant, make authenticated requests to the app repeatedly across time such that the offline token is refreshed multiple times (each refresh is a legitimate, individually-authorized operation) — this occurs automatically via `ensureOfflineTokenIsNotExpired` whenever the offline token is within 5 minutes of expiry [8](#0-7) .
3. Each refresh calls `sessionStorage.storeSession(offlineSession)` with the same offline session id, and `addShopIds` appends that id again to the `shop:<shop>` KV array without deduplication [9](#0-8) .
4. Over many refresh cycles, the `shop:<shop>` array grows unbounded, eventually causing `findSessionsByShop` reads and further `storeSession` writes for that shop to slow down or fail once the KV value size limit is reached.

**Note on scope/uncertainty:** I was unable to fully verify the exact KV backend's hard size limit within this codebase (it depends on the deployment's `KVNamespace` implementation, e.g., Cloudflare KV's 25 MiB value limit), so the precise threshold at which this becomes a practical DoS could not be confirmed from the repository alone.

  public async deleteSession(id: string): Promise<boolean> {
    const session = await this.loadSession(id);
    if (!session) {
      return true;
    }

    await this.namespace.delete(id);
    await this.removeShopIds(session.shop, [session.id]);
    return true;
  }

  public async deleteSessions(ids: string[]): Promise<boolean> {

    for (const id of ids) {
