### Title
Streamed microblock fee reward rounding causes silent 1 uSTX loss when `tx_fees_streamed % 5 != 0` - (File: stackslib/src/chainstate/stacks/db/accounts.rs)

### Summary
`MinerPaymentSchedule::streamed_tx_fees_confirmed` and `streamed_tx_fees_produced` split the streamed microblock tx fees into a 3/5 (child/confirmer) and 2/5 (parent/producer) share using integer floor division. Because floor division is not distributive over addition, whenever `tx_fees_streamed` is not a multiple of 5 the two shares sum to less than the original total, permanently burning the remainder.

### Finding Description
The claimed invariant is:
`streamed_tx_fees_confirmed() + streamed_tx_fees_produced() == tx_fees_streamed`

The code is: [1](#0-0) 

Both functions independently floor-divide the same `tx_fees_streamed` value: `(tx_fees_streamed * 3) / 5` and `(tx_fees_streamed * 2) / 5`. For `tx_fees_streamed = 7`: confirmed = `21/5 = 4`, produced = `14/5 = 2`, sum = `6 != 7`. The dropped 1 uSTX is not credited to any account (miner, parent, or burn address) — it is simply never included in either `MinerReward` computed in `calculate_miner_reward`: [2](#0-1) 

The attacker (an unprivileged miner) controls the transaction fees included in the microblocks they stream, so they can trivially make `tx_fees_streamed` non-divisible by 5 (this happens naturally for ~4/5 of all possible totals, requiring no special effort at all). The parent-miner reward and the child-miner reward are both computed from independent floor divisions with no reconciliation or remainder-assignment step, and no downstream check (`check_tenure_tx`, `common_validate_against_burnchain`, MARF hashing, maturation window) re-verifies that the two shares sum to the original streamed-fee total.

### Impact Explanation
This is a reward mis-payment bounded strictly to the streamed microblock tx-fee portion (not the coinbase or anchored fees), and the lost uSTX (0, 1, 2, 3, or 4 depending on `tx_fees_streamed mod 5`) is burned/lost rather than paid to any party — it does not cause a chain split, invalid-block-acceptance, or state-root divergence, since all nodes compute the same (slightly too small) amounts deterministically. This matches the "High - reward mis-payment bounded to fees" category from the rules.

### Likelihood Explanation
No special preconditions beyond a normal Epoch2 tenure with a microblock stream are required. Any miner who mines microblocks with transaction fees summing to a non-multiple of 5 (the overwhelming majority of possible fee totals) triggers the loss on every affected block, deterministically and repeatably, using only their own mining slot — no majority stake or privileged role needed.

### Recommendation
Compute one share via floor division and derive the other by subtraction from the total (e.g., `confirmed = (streamed * 3) / 5; produced = streamed - confirmed;`), or otherwise allocate the remainder deterministically (e.g., give it to the confirming/child miner) so that `confirmed + produced == streamed` for all inputs.

### Proof of Concept
Add a Rust unit test in `stackslib/src/chainstate/stacks/tests/accounting.rs` (or accounts.rs test module) that constructs a `MinerPaymentSchedule` with `MinerPaymentTxFees::Epoch2 { anchored: 0, streamed: n }` for `n in 0..100`, and asserts:
```rust
for n in 0u128..100 {
    let sched = make_schedule_with_streamed(n); // helper to build schedule
    let confirmed = sched.streamed_tx_fees_confirmed();
    let produced = sched.streamed_tx_fees_produced();
    assert_eq!(confirmed + produced, n, "mismatch for streamed={}", n);
}
```
This test fails for every `n` not divisible by 5 (e.g. `n=7` yields `confirmed=4, produced=2, sum=6`), confirming the loss.
