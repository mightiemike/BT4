### Title
Fund migration sweep uses a stale pre-inbound balance snapshot, permanently stranding new deposits in the retired TSS vault - (File: universalClient/chains/evm/tx_builder.go)

### Summary
This is the closest scoped analog to the reported `stakedButUnverifiedNativeETH` bug: an accounting value (the amount to sweep during TSS fund migration) is computed once from a point-in-time balance snapshot and then treated as authoritative for the entire migration, even though the underlying balance can still change (increase) between the snapshot and the point where the retired key becomes permanently unusable — exactly the "effective balance changes after the fixed value was recorded" pattern from the EigenLayer report.

### Finding Description
`InitiateFundMigration` (`x/utss/keeper/msg_initiate_fund_migration.go`) only requires that **outbound** be disabled and that no pending outbounds remain for the chain before migration starts: [1](#0-0) 

It does **not** require or check that **inbound** is disabled for that chain. `IsChainInboundEnabled`/`IsChainOutboundEnabled` are independent flags in `x/uregistry`, and integration tests confirm inbound can remain enabled while outbound is disabled: [2](#0-1) 

Once migration is initiated, the Universal Validator client builds the sweep transaction by querying the **current on-chain balance of the old TSS address once**, then computes `maxTransfer = balance - gasCost - l1GasFee` and signs a transaction for exactly that amount: [3](#0-2) 

The comment explicitly documents the (incomplete) invariant the code relies on: "Fund migration only triggers when outbound is disabled and no pending outbounds remain, so the balance at signing time will equal the balance at broadcast time." This reasoning covers *outbound*-driven balance changes only. It does not account for an ordinary, unprivileged user submitting a normal gateway deposit (inbound) on the source chain to the **old** vault address after the balance snapshot is taken but before/after the TSS-signed sweep transaction is broadcast. Because `computeFundMigrationTransfer` hard-codes the amount into the signed transaction (`TSSFundMigrationAmount`), any native value that lands in the old vault after the snapshot is not included in the sweep: [4](#0-3) 

Meanwhile, on Push Chain's side, the corresponding inbound is still voted on and processed normally (PRC20 minted / UTX created) since inbound remains enabled — the protocol now records synthetic/PRC20 backing for value that never reaches the current TSS vault, because the source-chain native funds are stuck at an address whose signing key (the old TSS key) is retired once migration completes.

### Impact Explanation
Any native-asset deposit that lands at the old TSS vault address in the window between the migration balance snapshot and the sweep broadcast is permanently unrecoverable — the old key is retired by design after migration (that's the entire purpose of TSS key rotation), so there is no future signing path to reclaim it. This is a permanent freezing/loss of user-and-protocol funds on the source chain while Push Chain's own accounting (PRC20 mint) proceeds as if the deposit was safely custodied, corrupting the native/PRC20 backing invariant.

### Likelihood Explanation
The trigger requires no privileged access — an ordinary user only needs to send a normal deposit transaction to the (still-public) gateway/vault address during an admin-initiated migration window. Because inbound is never disabled as part of the migration precondition, the window is not artificially closed, and any user (or an attacker specifically racing to grief the protocol / a target's own deposit) can hit it. The severity is bounded by the length of the signing+broadcast window, but the root cause — no re-validation of balance/no inbound gating before broadcast — is a genuine design gap.

### Recommendation
Require `IsChainInboundEnabled(chain) == false` as an additional precondition in `InitiateFundMigration`, alongside the existing outbound check, so no new deposits can be routed to the old vault after migration begins. Alternatively/additionally, re-query the balance immediately before broadcast (or use a "sweep remaining balance" pattern instead of a fixed pre-computed amount) and support a secondary sweep pass for any residual balance detected after the primary migration.

### Proof of Concept
1. Admin disables outbound for chain X and calls `MsgInitiateFundMigration` (inbound remains enabled).
2. The `FundMigrationInitiated` event fires; a Universal Validator's coordinator calls `buildFundMigrationTransaction` → `GetFundMigrationSigningRequest`, which queries `oldTSSAddr`'s balance (e.g. 10 ETH) and builds/signs a sweep tx for `10 ETH - gas - L1 fee`.
3. Before that signed tx is broadcast/confirmed, an ordinary user submits a normal gateway deposit of 1 ETH to `oldTSSAddr` on chain X.
4. Universal Validators observe and vote the inbound; Push Chain mints the corresponding PRC20 to the user via `VoteInbound`/`ExecuteInbound` normally (inbound is still enabled).
5. The sweep tx executes for the pre-computed 10 ETH (minus fees), leaving the new 1 ETH deposit in `oldTSSAddr`.
6. The old TSS key is retired as part of the completed migration — the 1 ETH is now permanently unrecoverable, while the user already holds the minted PRC20 for it on Push Chain.

// GetFundMigrationSigningRequest builds a native token transfer for fund migration,
// transferring the maximum possible balance (balance minus gas cost minus L1 fee).
// Fund migration only triggers when outbound is disabled and no pending outbounds remain,
// so the balance at signing time will equal the balance at broadcast time.
// L1GasFee covers OP-stack sequencer data-availability charges; 0 for non-L2 chains.
func (tb *TxBuilder) GetFundMigrationSigningRequest(ctx context.Context, data *common.FundMigrationData, nonce uint64) (*common.UnsignedSigningReq, error) {
	fromAddr := ethcommon.HexToAddress(data.From)
	toAddr := ethcommon.HexToAddress(data.To)

	if data.GasPrice == nil || data.GasPrice.Sign() == 0 {
		return nil, fmt.Errorf("gas price must be provided for fund migration")
	}
	if data.GasLimit == 0 {
		return nil, fmt.Errorf("gas limit must be provided for fund migration")
	}

	var balance *big.Int
	if data.Balance != nil {
		balance = new(big.Int).Set(data.Balance)
	} else {
		queried, err := tb.rpcClient.GetBalance(ctx, fromAddr)
		if err != nil {
			return nil, fmt.Errorf("failed to get balance of %s: %w", data.From, err)
		}
		balance = queried
	}

	maxTransfer, err := computeFundMigrationTransfer(balance, data.GasPrice, data.GasLimit, data.L1GasFee)
	if err != nil {
		return nil, err
	}

// computeFundMigrationTransfer returns the native amount to sweep from the old
// TSS address to the new one: balance - (gasPrice * gasLimit) - l1GasFee.
// The l1GasFee covers OP-stack sequencer data-availability charges (0 for
// non-L2 chains). All validators must compute the same value — any drift
// here breaks the TSS signing hash.
func computeFundMigrationTransfer(balance, gasPrice *big.Int, gasLimit uint64, l1GasFee *big.Int) (*big.Int, error) {
	gasCost := new(big.Int).Mul(gasPrice, new(big.Int).SetUint64(gasLimit))
	totalFee := new(big.Int).Set(gasCost)
	if l1GasFee != nil && l1GasFee.Sign() > 0 {
		totalFee.Add(totalFee, l1GasFee)
	}
	maxTransfer := new(big.Int).Sub(balance, totalFee)
	if maxTransfer.Sign() <= 0 {
		return nil, fmt.Errorf("insufficient balance for gas: balance=%s gasCost=%s l1GasFee=%s",
			balance.String(), gasCost.String(), l1GasFeeString(l1GasFee))
	}
	return maxTransfer, nil
}
