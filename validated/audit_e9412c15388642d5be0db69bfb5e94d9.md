### Title
Replay-verify silently accepts diverged state/hot-state/position checkpoint roots because `TransactionOutput::ensure_match_transaction_info` never checks them - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by state-integrity replay/restore tooling to confirm that locally re-executed transaction outputs match the `TransactionInfo` recorded in an (untrusted) backup archive. It validates status, gas, write-set hash (`state_change_hash`), and event root hash, but explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the very fields that authenticate the Sparse-Merkle/JMT state root, hot-state root, and native-position state root against the accumulator-committed `TransactionInfo`. The gap is even documented in-code as a known TODO, yet the function still returns `Ok(())` without performing the check.

### Finding Description
`ensure_match_transaction_info` in `types/src/transaction/mod.rs` is defined as: [1](#0-0) 

It checks `status`, `gas_used`, `write_set` hash vs `txn_info.state_change_hash()`, and `event_root_hash` vs `txn_info.event_root_hash()`. It then contains the explicit admission:

```

// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
``` [2](#0-1) 

This function is the sole per-transaction correctness check used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which drives the `replay_on_archive` tool's version of authenticated replay verification against archived backup data: [3](#0-2) 

`TransactionInfo::state_checkpoint_hash()`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are the fields that are hashed into `TransactionInfo` and, in turn, into the transaction accumulator that backs `LedgerInfo::transaction_accumulator_hash()` — the field validators sign over. `TransactionInfoV1` explicitly carries these fields: [4](#0-3) 

Because `ensure_match_transaction_info` never re-derives or compares these hashes against what local re-execution produced (via `StateCheckpointOutput`/`DoStateCheckpoint`), a `TransactionInfo` in an archived backup whose `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` differs from what local re-execution actually computes will pass verification as long as status/gas/write-set/events match. The comment itself states this can occur "even when the authenticated position state root diverges from local execution."

### Impact Explanation
This breaks the core state-integrity guarantee of the replay/restore path: replay-verify tooling exists specifically to detect divergence between an archived ledger and independently re-executed results, gating trust in restored/backup data before it is used (e.g., to seed a new full node, or to certify that a backup archive is not corrupted/tampered). With this gap:
- A corrupted or tampered `TransactionInfo` (or a state root computed by a buggy/malicious executor) whose checkpoint hash fields don't match locally re-derived roots will be reported as a successful, verified replay.
- This allows a node operator to unknowingly restore from, or trust, an archive whose committed Sparse Merkle Tree / hot-state / native-position roots do not correspond to the actual VM-derived state, i.e., a "wrong state root accepted as valid" scenario in an authenticated verification path — squarely inside the State-Integrity Gate's protected impacts ("Wrong accumulator root, Merkle proof ... accepted as valid" and "Hard-fork-only divergence during ... replay, restore ... accepted as valid").
- Given this is an explicitly acknowledged, still-open TODO ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), the check is provably absent in the current code, not merely theoretical.

### Likelihood Explanation
The check is unconditionally absent for every call, regardless of whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled — the state and hot-state checkpoint hashes are skipped even on the ordinary (non-position) path. Any scenario that produces a bad/mismatched checkpoint hash in a `TransactionInfo` — corrupted backup data, a bug elsewhere in state-checkpoint computation, or a malicious backup source — will not be caught by this comparator. The only mitigating factor is that a full accumulator-consistency check may occur elsewhere in some paths (e.g., ledger accumulator proof verification against a trusted waypoint/`LedgerInfo`), but the `replay_on_archive` tool's `execute_and_verify`, as shown, relies solely on `ensure_match_transaction_info` for this per-transaction check, so it does not independently confirm the checkpoint hash there.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) against the actual state summary produced by local re-execution (via `StateCheckpointOutput`), erroring out on mismatch just as is already done for `state_change_hash` and `event_root_hash`. This should be done before any feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that depends on these fields is enabled in production, and ideally regardless of that feature flag, since the state/hot-state checkpoint hashes are meaningful even without native-position support.

### Proof of Concept
Conceptual PoC (cannot be executed without a live archive/tooling environment):
1. Construct a backup archive (transaction/write-set/events unchanged) but with a `TransactionInfo` whose `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) is altered to a different, syntactically-valid `HashValue`.
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs::Verifier::verify` → `execute_and_verify`) against this archive.
3. Because `execute_and_verify` calls `TransactionOutput::ensure_match_transaction_info` [5](#0-4)  which only checks status/gas/write_set hash/event root hash [6](#0-5) , the tool reports success despite the tampered/diverged checkpoint hash, since the checkpoint-hash comparison is entirely absent [2](#0-1) .

I was unable to fully verify whether any other independent layer in the broader `replay_verify` coordinator pipeline (`storage/backup/backup-cli/src/coordinators/replay_verify.rs`) separately re-derives and checks the state checkpoint hash outside of `TransactionRestoreBatchController`/`ChunkExecutor`'s own internal ledger-update/accumulator-consistency logic; a full trace of `ChunkExecutor::update_ledger`/`commit` was not completed within the available budget. If such an independent accumulator-root check exists and is always exercised in that specific pipeline, impact would be limited to the `db-tool replay_on_archive` utility specifically; however, the comparator function itself, its explicit TODO, and its direct use in `replay_on_archive.rs`'s per-transaction verification loop are confirmed in the current code.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
