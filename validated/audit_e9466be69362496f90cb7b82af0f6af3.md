### Title
`WalletContract::rlp_execute` accepts an attached NEAR deposit but permanently strands it when transaction parsing/validation fails without ever forwarding or refunding it - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is marked `#[payable]`, so any unprivileged predecessor (an external caller, a relayer, or the wallet owner itself) can attach a NEAR deposit when submitting an RLP-encoded Ethereum transaction. That deposit is unconditionally added to the wallet account's balance the moment the `FunctionCall` receipt is processed by the NEAR runtime, independent of what the contract logic subsequently does. However, several parsing/validation failure paths inside `inner_rlp_execute` return a plain `Err(...)` that is converted directly into a non-panicking `ExecuteResponse{success:false,...}` value, with **no promise ever created** to forward the deposit to the intended `target`/action recipient nor to refund it back to the `predecessor_account_id`.

### Finding Description
`rlp_execute` computes `caller_deposit` (a `CallerDeposit` capturing the external caller and the attached deposit) purely so that it can be refunded later: [1](#0-0) 

That refund logic, however, only ever runs inside `rlp_execute_callback`, and only in the `PromiseResult::Failed` branch of an actual cross-contract call: [2](#0-1) 

The problem is that several error paths in `inner_rlp_execute`/`rlp_execute` never reach this callback at all, because no promise is ever created:

- `Err(err @ Error::User(_))` from `parse_rlp_tx_to_action` (e.g. `UnsupportedAction`, `InvalidAbiEncodedData`, `ExcessYoctoNear`, invalid keys, etc.) increments the nonce and returns immediately: [3](#0-2) 
- Any other `Err(err)` (e.g. `AccountId` errors) is likewise returned directly: [4](#0-3) 
- `action_to_promise(target, action)?` in the default match arm can also fail (e.g. `UnsupportedAction::AddFullAccessKey`) and propagate up through the same `?` operator, after the nonce has already been incremented and `caller_deposit` has already been computed: [5](#0-4) [6](#0-5) 

All of these `Err` values bubble up to `rlp_execute`, where they are turned into an ordinary (non-panicking) return value with no promise/receipt created to move the attached deposit anywhere: [7](#0-6) 

Since the `FunctionCall` action does not fail/panic (by design, per the comment in `ExecuteResponse`, so that state changes like nonce increments and relayer bans can persist even on error), the NEAR protocol's automatic "deposit refund on receipt failure" mechanism never triggers either — that mechanism only fires when the receipt execution itself fails, not when a successful call happens to return `success:false` in its own response payload. The attached deposit is therefore absorbed into the wallet account's balance and stays there permanently, with no code path ever sending it to the `target` account (the depositor's real intent) or back to the `predecessor_account_id` (the depositor's fallback).

### Impact Explanation
Any unprivileged account (in particular, an external caller who is not the wallet owner and has no long-term relationship with the wallet, i.e. `CallerDeposit::new` only tracks external callers) can attach real NEAR value to a `rlp_execute` call. If the RLP-encoded action is one of the several inputs that trigger a `UserError`/`AccountIdError`/`UnsupportedAction` (all reachable with attacker/relayer-controlled inputs, no special privilege required), the deposit is permanently and irreversibly merged into the wallet contract's balance instead of being forwarded to the intended target or refunded to the sender. This is a concrete, unauthorized value-retention bug: the depositor loses their funds while the wallet account (controlled by a third party, the wallet's ETH-derived owner) unexpectedly gains them, with no mechanism in the contract to reclaim or redirect them. This matches the "value sent but lost" class from the reference report precisely, differing only in that the funds land in another party's live account balance rather than being burned outright.

### Likelihood Explanation
This is trivially reachable by any account able to submit a `FunctionCall` to an eth-implicit account's `rlp_execute` method with an attached deposit and a malformed or unsupported action encoded in the RLP transaction (e.g. an `AddKey` action requesting a full-access key, which is explicitly disallowed via `UnsupportedAction::AddFullAccessKey`, or malformed ABI-encoded call data). No validator collusion, access key theft, or race condition is required — a single, ordinary transaction from any signer is sufficient.

### Recommendation
In every early-return `Err` path of `inner_rlp_execute`/`rlp_execute` (i.e., whenever `caller_deposit`/`env::attached_deposit()` is non-zero and no promise chain that could refund it via `rlp_execute_callback` is created), explicitly create a promise to refund `env::attached_deposit()` back to `predecessor_account_id` before returning the error `ExecuteResponse`. Alternatively, restructure the code so any failure prior to committing to a downstream promise chain always routes through a refund step, mirroring the `PromiseResult::Failed` handling already present in `rlp_execute_callback`.
