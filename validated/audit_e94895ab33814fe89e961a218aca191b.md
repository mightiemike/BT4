### Title
Cross-tenant shop impersonation via unsigned `X-Shopify-Shop-Domain` header trusted after body-only HMAC check - (File: `packages/apps/shopify-api/lib/fulfillment-service/validate.ts`, consumed in `packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts` and `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts`)

### Summary
`validateFactory` in `fulfillment-service/validate.ts` delegates entirely to `validateHmacFromRequestFactory`, which computes the HMAC over `rawBody` only and never includes the `X-Shopify-Shop-Domain` header in the signed data. The consuming code in `shopify-app-remix`/`shopify-app-react-router` then reads the shop identity directly from that unsigned header and uses it to look up the offline session, meaning shop identity is never cryptographically bound to the verified signature.

### Finding Description
`validateFactory` (`packages/apps/shopify-api/lib/fulfillment-service/validate.ts:10-20`) forwards the request straight to `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-201`), which:
1. Reads the `X-Shopify-Hmac-Sha256` header.
2. Verifies `hmac == HMAC-SHA256(apiSecretKey, rawBody)` via `validateHmacString`/`safeCompare`.
3. On success returns only `{valid: true}` — no shop/topic/domain fields are checked or returned [1](#0-0) .

Critically, the signed material is the raw body alone — headers such as `X-Shopify-Shop-Domain` are completely outside the HMAC. The downstream consumer, `authenticateFulfillmentServiceFactory`, then reads the shop identity independently from the unsigned header:
```
const result = await api.fulfillmentService.validate({rawBody, rawRequest: request});
...
const shop = request.headers.get(ShopifyHeader.Domain) || '';
...
const session = await ensureValidOfflineSession(params, shop);
``` [2](#0-1) 

The same pattern exists in the generic webhook path: `validateHmacFromRequestFactory` verifies the body HMAC, then `checkWebhookHeaders`/`checkWebhooksHeaders` reads `domain`/`topic` straight from headers with no cryptographic tie to the HMAC [3](#0-2) , and `authenticateWebhookFactory` uses `check.domain` to fetch the offline session and build the admin client [4](#0-3) .

Because `apiSecretKey` is a single secret shared by the app across **all** installed shops (it is the app's client secret, not a per-shop secret), any merchant who has the app installed on their own shop can obtain a genuinely-signed `(rawBody, hmac)` pair — for example by creating their own webhook subscription pointing at an endpoint they control, or by capturing a real fulfillment-service notification sent to their own callback URL. Since the domain header is not part of the signed content, that same valid `(rawBody, hmac)` pair can be replayed to the app's public webhook/fulfillment endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. The HMAC check passes (it only checks the body), and the app then looks up and acts using the victim shop's offline session/access token, resulting in cross-tenant action: the attacker-supplied payload is processed as if it came from, and is attributed to, the victim shop.

### Impact Explanation
This breaks the invariant that shop identity must be bound to the verified signature. It allows a single attacker who is a legitimate merchant of the app (an "unprivileged" actor in the threat model — no special access, no leaked secret, no app-developer role) to forge a webhook/fulfillment-service request that the app attributes to a different, victim shop, causing the app to fetch the victim's offline session/admin token and execute the app's normal webhook/fulfillment-order handling logic against the victim's store using attacker-chosen payload content. This matches "cross-tenant webhook action" (forged authenticated request causing state change/data access on another tenant).

### Likelihood Explanation
- Requires only that the attacker have the app installed on any single shop (no elevated privilege) so they can obtain one genuinely HMAC-signed `(body, hmac)` pair for the shared `apiSecretKey`.
- Requires knowledge of a victim shop's domain, which is generally public/known (`*.myshopify.com`).
- Requires the app to already have an offline session/token stored for the victim shop (i.e., victim has installed the app too) — a realistic precondition for any multi-tenant app.
- No timestamp/nonce/replay protection or additional binding of domain to signature exists in this code path, so the attack is repeatable at will.

### Recommendation
Bind shop identity to the verified signature instead of trusting the header independently:
- Include the shop domain/topic (and ideally a timestamp/nonce) as part of the HMAC-signed payload, or
- Require that the domain claimed in the header match a domain that Shopify would have derived independently (e.g., cross-check against a per-shop secret, or validate the request originates from Shopify's known infrastructure), and
- At minimum, document and warn app developers not to use the unsigned `X-Shopify-Shop-Domain` header as the sole tenant-selection key after body-only HMAC validation, and provide a library-level check that ties the two together before returning `valid: true`.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/fulfillment-service/__tests__/spoof.test.ts
import {shopifyApi} from '../..';
import {ShopifyHeader} from '../../types';
import {createSHA256HMAC, HashFormat, type NormalizedRequest} from '../../../runtime';
import {testConfig} from '../../__tests__/test-config';

it('accepts a valid HMAC regardless of the shop-domain header value', async () => {
  const shopify = shopifyApi(testConfig());
  const payload = {field: 'attacker-controlled'};
  const rawBody = JSON.stringify(payload);
  const validHmac = await createSHA256HMAC(shopify.config.apiSecretKey, rawBody, HashFormat.Base64);

  // Attacker obtained (rawBody, validHmac) legitimately for THEIR OWN shop
  // via a self-created webhook subscription, then replays it claiming to be victim-shop.
  const spoofedReq: NormalizedRequest = {
    method: 'POST',
    url: 'https://my-app.example.com/fulfillment_order_notification',
    headers: {
      [ShopifyHeader.Hmac]: validHmac,
      [ShopifyHeader.Domain]: 'victim-shop.myshopify.com', // unsigned, attacker-controlled
    },
  };

  const result = await shopify.fulfillmentService.validate({
    rawBody,
    rawRequest: spoofedReq,
  });

  // The library reports the request as VALID even though the domain
  // header was never covered by the HMAC.
  expect(result).toMatchObject({valid: true});
});
```
This demonstrates that `validateFactory`/`validateHmacFromRequestFactory` never checks or returns the shop domain, so any downstream consumer that trusts `request.headers.get(ShopifyHeader.Domain)` after a `valid: true` result (as `authenticateFulfillmentServiceFactory` and `authenticateWebhookFactory` do) can be steered to act on behalf of an arbitrary shop domain using an HMAC that was only ever proven valid for the body content, not for the claimed shop. export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
