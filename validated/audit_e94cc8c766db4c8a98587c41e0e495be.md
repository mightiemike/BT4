### Title
Liquidation of a fully-collateral-drained borrower can be permanently blocked by a single failing debt-asset socialization - (File: `mainnet/contracts/market/v0-4-market.clar`, function `liquidate`)

### Summary
`liquidate()` performs bad-debt socialization across *every* remaining debt asset of the borrower in one atomic fold, and `asserts!`s that **all** of them succeed. If a single one of those per-vault `socialize-debt` calls fails (e.g. because that vault is paused, or for any other single-point reason), the assertion reverts the whole liquidation — including the seizure of collateral/repayment of debt for the asset the liquidator actually targeted, which has nothing to do with the failing vault. This mirrors the Sherlock `payOffDebtAll` bug class: a fold over multiple entries that halts an entire critical operation when any single entry cannot be processed.

### Finding Description
When a borrower's collateral is fully removed by a liquidation (`no-collateral-left` becomes true), `liquidate()` builds `fresh-debt-list` containing all of the borrower's remaining scaled-debt entries across all asset vaults, and folds `socialize-debt-asset` over that list: [1](#0-0) 

```
(let ((bad-debt-socialized 
        (if no-collateral-left
            (let ((stripped-debt-list (filter-out-debt-asset (get debt pos-full) debt-aid))
                  (fresh-debt-list ...))
              (if (> (len fresh-debt-list) u0)
                (let ((socialization-result (fold socialize-debt-asset 
                                                  fresh-debt-list 
                                                  { borrower: borrower, success: true })))
                  (asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)
                  ...
```

Each element of `fresh-debt-list` corresponds to a debt the borrower has in a *different* asset vault (e.g. STX, sBTC, USDC, USDH), and `socialize-debt-asset` calls that vault's public `socialize-debt` entry point: [2](#0-1) 

The vault-level `socialize-debt` function is state-mutating and, like other vault system functions in this codebase, is gated by authorization checks and (in sibling functions such as `system-borrow`/`system-repay`) explicit pause-state assertions: [3](#0-2) 

If the `socialize-debt` call for *any single one* of the borrower's other debt assets fails (paused vault, an internal `asserts!`, or any other per-vault condition), the corresponding fold iteration returns `success: false`, and the top-level `asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` reverts the **entire** `liquidate()` call — including the debt-asset/collateral pair the liquidator actually intended to liquidate, which may be entirely unrelated to the failing vault.

This is structurally identical to the Sherlock finding: `payOffDebtAll` iterated over all of a token's protocols and reverted the whole batch if one protocol's balance couldn't cover its debt; here, `liquidate()`'s bad-debt-socialization step iterates over all of a borrower's remaining debt assets and reverts the whole liquidation if one asset's socialization step fails.

### Impact Explanation
As long as one of the borrower's debt-asset vaults cannot successfully execute `socialize-debt` (e.g., it is paused for maintenance, upgrade, or any other reason), the borrower's fully-undercollateralized position can **never** be liquidated via `liquidate()`, because the transaction always reverts at the `ERR-BAD-DEBT-SOCIALIZATION-FAILED` assertion. The bad debt remains permanently stuck on the books, uncollateralized, and cannot be written off — this is a protocol insolvency risk (bad debt accrues and cannot be removed) and a permanent freezing-of-funds condition for that position (the collateral, if any is later re-added, and any recoverable value tied to closing the position, cannot be resolved). Note `liquidate-multi` claims failed liquidations "don't revert entire batch" only at the batch-of-positions level (`map call-liquidate`), which does not protect the single-position path described above. [4](#0-3) 

### Likelihood Explanation
This requires that at least one of the borrower's several debt-asset vaults be in a state where `socialize-debt` cannot succeed while the borrower still has debt outstanding there. Given six separate vault contracts (`STX`, `sBTC`, `stSTX`, `USDC`, `USDH`, `stSTXbtc`), each independently pausable and each with its own internal invariants, and given that borrowers are encouraged by the protocol's design to hold multi-asset positions, the probability that at least one vault is paused or otherwise unable to process `socialize-debt` at the moment a liquidation is needed is non-trivial, especially since vault pauses are an ordinary operational/governance action unrelated to any specific borrower.

### Recommendation
Do not let a single failing per-asset socialization abort the entire liquidation. Options:
- Make `socialize-debt-asset` accumulate failures without reverting, and only revert (or skip socialization for) the specific failing asset, while still completing the primary `debt-remove-scaled`/`collateral-remove`/`vault-system-repay` operations for the targeted debt/collateral pair.
- Decouple bad-debt socialization from the liquidation transaction — allow `liquidate()` to succeed and complete the targeted repay/seizure, and let socialization of remaining bad debt be retried independently (e.g., a separate `socialize-remaining-debt` call), so a single stuck vault cannot block liquidation of the position.

### Proof of Concept
1. Borrower opens a position with debt in two vaults: `STX` and `USDC`, backed by a single collateral asset.
2. Collateral price drops; position becomes fully liquidatable and collateral is insufficient to cover any remaining debt (`no-collateral-left` will evaluate true after the liquidation call below).
3. Governance (or the pause mechanism) pauses the `USDC` vault such that its `socialize-debt` entry point cannot succeed (e.g., its pause-state check fails, mirroring the `ERR-PAUSED` guards seen in `system-borrow`/`system-repay` for the same vault contract).
4. A liquidator calls `liquidate(borrower, collateral-ft, STX-debt-ft, debt-amount, ...)` to liquidate the `STX` debt.
5. Because the borrower's collateral is fully drained (`no-collateral-left = true`), `liquidate()` builds `fresh-debt-list` including the borrower's remaining `USDC` debt entry, and folds `socialize-debt-asset` over it, which internally invokes the paused `USDC` vault's `socialize-debt`.
6. That call fails; the fold returns `success: false`; `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` reverts the whole transaction.
7. The `STX` debt/collateral, which had nothing to do with the paused `USDC` vault, cannot be liquidated — the borrower's insolvent position is stuck until the `USDC` vault is unpaused, during which bad debt continues to be unaccounted for in the protocol's insolvency accounting. [5](#0-4)
