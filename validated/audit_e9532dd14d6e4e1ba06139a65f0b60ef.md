## Local Analog Found

### Title
`TransactionOutput::ensure_match_transaction_info` omits checkpoint-hash validation, letting replay-verify accept a divergent state/hot-state/position root - (File: `types/src/transaction/mod.rs`)

### Summary
The report's bug class is "a verification routine's binding fields don't match the object it's supposed to authenticate, so a corrupted/unexpected object passes verification." The Aptos-native analog is `TransactionOutput::ensure_match_transaction_info`, the function used by replay/verification tooling to assert that a locally-produced `TransactionOutput` matches the authenticated `TransactionInfo` for a version. It checks status, gas, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that bind the *state root* (not just the write set) into the authenticated `TransactionInfo`.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates:
- execution status
- gas used
- write-set hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

but the function's own trailing comment admits the gap: [2](#0-1) 

This means the function never re-derives or compares the Sparse-Merkle state root (`state_checkpoint_hash`), the hot-state root (`hot_state_checkpoint_hash`), or the newer trading-native position-tree root (`position_state_checkpoint_hash`) that are carried inside the *authenticated* `TransactionInfo` (proven via the transaction accumulator, see `TransactionInfoV1` fields at [3](#0-2) ). It is called from tooling paths (`aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `storage/db-tool/src/replay_on_archive.rs`) whose entire purpose is to assert "the locally re-executed/replayed state equals the chain's authenticated state at this version."

By contrast, the parallel proof-verification path `TransactionOutputListWithProof::verify` (state-sync/consensus data path) also never validates the checkpoint hash against a *locally computed* root — but that path is safe because it doesn't claim to validate state-root correctness, only that the given output's write set/events/status are consistent with the (already accumulator-proven) `TransactionInfo`; the actual state root binding happens later in `DoStateCheckpoint` when applying writes to the state tree in `execution/executor/src/chunk_executor/mod.rs` (`known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints`, [4](#0-3) ), which *does* recompute and compare state roots.

`ensure_match_transaction_info`, however, is the function specifically invoked by replay/debug/db-tool code paths that do **not** go through `DoStateCheckpoint`'s root recomputation — they call this function directly as their sole correctness gate for a replayed transaction. Since it skips the checkpoint-hash fields, a replay whose actual computed state (post write-set application) diverges from the authenticated `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` will still report "match" success, because the write-set *hash* equality check only proves the write set bytes are identical to what's recorded — it does not prove that applying that write set produces the correct resulting Merkle root, nor does it catch cases where the checkpoint hash itself was mis-derived or omitted upstream.

### Impact Explanation
This directly matches one of the required Proof/Storage Pivots: *"Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state,"* and *"Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding."* A replay-verification tool (e.g., `db-tool`'s `replay_on_archive`, or `aptos-debugger`) that is meant to catch "hard-fork-only divergence during commit, replay, or proof verification" will silently report success even though the position/hot-state/state root diverges from the authenticated ledger value. This is exactly the class of bug the scan targets: a proof/commitment field the code is supposed to bind against is missing from the check, so a wrong state-commitment "accepted as valid."

### Likelihood Explanation
The gap is currently latent/moderate-likelihood rather than immediately exploitable on mainnet: the comment says the checkpoint hashes should be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying the feature flag gating the new position-state root is not yet fully enabled, and the primary commit path (`DoStateCheckpoint` in `execution/executor/src/chunk_executor/mod.rs`) does perform the real root comparison independently during normal chunk/state-sync execution. The exposure is specifically in replay/debug verification tooling paths that call `ensure_match_transaction_info` as their end-to-end correctness assertion without an independent root recomputation step of their own — I could not fully confirm (given tool-call limits) whether `aptos-debugger`, `cli/src/commands.rs`, or `replay_on_archive.rs` perform any *additional* independent root check beyond this function, which is necessary to establish that this is the sole gate in those tools.

### Recommendation
Extend `ensure_match_transaction_info` to compare the actual post-write-set state root (and hot-state/position roots when applicable) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, as the existing in-code TODO already specifies, before any dependent feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled on mainnet. Alternatively, ensure all callers of this function (`db-tool/replay_on_archive`, `aptos-debugger`, `cli/src/commands.rs`) independently recompute and check these checkpoint hashes so replay success cannot be reported when the authenticated state root diverges.

### Proof of Concept
Not independently verifiable without running the replay tooling end-to-end (would require executing `db-tool replay-on-archive` against a chain segment with `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state enabled and a deliberately corrupted local state root to observe a false "match" report). The code-level proof is the explicit TODO comment at [2](#0-1)  combined with the absence of any `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` comparison in the function body at [5](#0-4) , contrasted with the independent, complete checkpoint-hash validation performed in the normal chunk-execution ledger-update path at [4](#0-3) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
