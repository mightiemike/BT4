No vulnerability found for this question.

**Reasoning:**

The premise that `@aptos_fungible_asset` could "be bound differently across a state view/version boundary" queried by the same authenticated API call is incorrect for how Move named addresses work.

`@aptos_fungible_asset` is a compile-time named address constant substituted into the module bytecode when the `aptos_account` module is compiled and published — it is not a runtime-resolved value read from storage at query time. The address is baked into the deployed bytecode itself, as seen in `primary_fungible_store_address`, which simply calls `object::create_user_derived_object_address(account, @aptos_fungible_asset)` with the literal constant already substituted at compile time. [1](#0-0) 

Since Aptos's state view is inherently versioned, querying the ledger at version `V` always executes/reads the module bytecode as it existed at version `V`. If a framework upgrade changed the named-address binding, that change would only take effect in the newly published module bytecode from the upgrade transaction onward — a query at a pre-upgrade version deterministically uses the pre-upgrade bytecode with the pre-upgrade constant baked in, and a query at a post-upgrade version uses the post-upgrade bytecode. There is no mechanism by which a single authenticated response at a fixed version could resolve to two different addresses; the addressing is version-scoped by construction, not "unstable."

Furthermore, `primary_store_address` (the actual function used generally by `primary_fungible_store`) derives from the `metadata: Object<T>` object address parameter, not from a named address, reinforcing that runtime derivation depends only on explicit object addresses passed to the call, not shifting compile-time constants. [2](#0-1) 

Changing what `@aptos_fungible_asset` resolves to would require a governance-approved framework upgrade (a privileged/trusted-operator action), which is explicitly out of scope per the review rules ("Reject anything that depends on trusted operator mistakes alone" / privileged governance assumptions excluded). The native derivation function itself is a pure, deterministic hash of the two addresses passed in, with no version-dependent behavior of its own. [3](#0-2) [4](#0-3) 

No unprivileged input path exists that can cause a stable-version authenticated query to return an address bound to the wrong version's object; the described scenario requires a privileged governance framework upgrade and even then remains correctly version-scoped by Aptos's versioned execution/state model.

fn native_create_user_derived_object_address_impl(
    context: &mut SafeNativeContext,
    ty_args: &[Type],
    mut args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    debug_assert!(ty_args.is_empty());
    debug_assert!(args.len() == 2);

    context.charge(OBJECT_USER_DERIVED_ADDRESS_BASE)?;

    let object_context = context.extensions().get::<NativeObjectContext>();
    let derive_from = safely_pop_arg!(args, AccountAddress);
    let source = safely_pop_arg!(args, AccountAddress);

    let derived_address = *object_context
        .derived_from_object_addresses
        .borrow_mut()
        .entry((derive_from, source))
        .or_insert_with(|| {
            AuthenticationKey::object_address_from_object(&source, &derive_from).account_address()
        });

    Ok(smallvec![Value::address(derived_address)])
}

pub fn create_derived_object_address(
    creator: AccountAddress,
    object_address: AccountAddress,
) -> AccountAddress {
    let mut input = bcs::to_bytes(&creator).unwrap();
    input.extend(bcs::to_bytes(&object_address).unwrap());
    input.push(Scheme::DeriveObjectAddressFromObject as u8);
    let hash = HashValue::sha3_256_of(&input);
    AccountAddress::from_bytes(hash.as_ref()).unwrap()
}
