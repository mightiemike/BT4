I have sufficient evidence to write the analog finding now.### Title
Meta-transaction sender can weaponize deposit refund routing (`predecessor_id`) to profit at the relayer's expense - ([File: runtime/runtime/src/lib.rs])

### Summary
The Cooler report's bug class is: a party can deliberately construct a transaction that costs a counterparty real value while the party itself is never economically penalized, and then collect the resulting refund/reward. The nearcore analog is the documented meta-transaction (NEP-366) deposit-refund routing: when a relayer submits a `DelegateAction` on behalf of a sender, the relayer pays all gas and attached deposits, but on execution failure the refund of the attached deposit is routed to the `predecessor_id` of the failing receipt (the sender/"Alice"), not to the relayer who actually paid.

### Finding Description
In `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1284-1419`), a failed action receipt causes `deposit_refund = total_deposit` to be pushed as `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)` (`runtime/runtime/src/lib.rs:1402-1407`). The refund receiver is derived from the receipt's `predecessor_id` (or an explicit `refund_to` override via `promise_set_refund_to`, see `runtime/near-vm-runner/src/wasmtime_runner/logic.rs:690-705`), not from whoever funded the deposit.

For a normal transaction, predecessor and funder are the same account, so this is safe. For a meta-transaction (`Delegate`/`DelegateV2`, handled by `apply_delegate_action` in `runtime/runtime/src/actions.rs:453-535`), the relayer is the signer who pays for the deposit and gas of the inner actions, but the new inner-action receipt is created with `predecessor_id: sender_id.clone()` (the delegating account, "Alice"), not the relayer (`runtime/runtime/src/actions.rs:500-513`). This is spelled out explicitly in the code comment: *"Gas is refunded to the signer, this is Relayer... deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction"* (`runtime/runtime/src/actions.rs:515-519`), and further documented in `docs/architecture/how/meta-tx.md:225-242`: *"there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard."*

The exploit mirrors the Cooler pattern exactly:
- Alice (the borrower analog) constructs a meta-transaction with an inner action to Bob's contract carrying a large attached deposit, engineered to fail (e.g., calling a nonexistent method, or a receiver that will reject the call).
- The relayer (the lender/protocol analog) pays for the deposit upfront when converting the delegate action to a receipt.
- On failure at Bob's shard, the deposit is refunded to `predecessor_id` = Alice, not to the relayer who funded it — Alice pockets tokens she never spent, and the relayer suffers the loss.
- There is no "margin" or penalty mechanism preventing Alice from doing this repeatedly, just like the Cooler borrower incurring no penalty for defaulting.

### Impact Explanation
Any account acting as, or colluding with, a meta-transaction sender can cause direct unauthorized value transfer from a relayer to itself: the relayer's balance is debited for the deposit at receipt-conversion time, but the deposit refund on failure is credited to the sender instead of the relayer. This is concrete unauthorized value movement between two on-chain accounts reachable purely by an unprivileged account submitting a signed `DelegateAction` to any willing/naive relayer — a real balance loss for the relayer with no compensating mechanism, matching the "Medium/High, unauthorized value movement" criteria.

### Likelihood Explanation
This requires a relayer that accepts arbitrary user-specified inner actions/deposits without restricting them to trusted, side-effect-safe contracts, or without pre-simulating execution to guarantee success. This is a known, documented risk (not a coding bug in trie/consensus logic) explicitly called out by the protocol's own docs as something "relayer implementations must be aware of." Because it is a documented, intended design trade-off of NEP-366 rather than an unintended coding defect, exploitation likelihood is entirely a function of relayer implementation quality, not protocol-level flaws; well-implemented relayers should be resistant. It is not a state-root divergence, receipt-loss, or consensus-halting bug.

### Recommendation
No protocol-level code fix is needed for the meta-transaction protocol contract per se (the design decision is explicit and documented), but relayer implementations should: pre-simulate/validate that all inner actions of a delegated transaction will succeed before paying for the deposit; only accept delegate actions whose receiver method(s) are known-safe/trusted; require signer-controlled bonding or deposit escrow so refunds route back to the relayer explicitly via `promise_set_refund_to`/`refund_to_account_id` mechanisms; or refuse to relay any inner action carrying attached deposits from untrusted senders.

### Proof of Concept
1. Deploy a relayer service that blindly forwards `SignedDelegateAction`s from arbitrary senders and pays gas/deposit as in `apply_delegate_action` (`runtime/runtime/src/actions.rs:453`).
2. Alice signs a `DelegateAction` with `sender_id = Alice`, `receiver_id = Bob`, containing a `FunctionCall` action with a large deposit and a `method_name` guaranteed to fail on Bob's contract (e.g., a nonexistent method, or logic that always panics).
3. Relayer submits the wrapping transaction; the relayer's account is charged for gas + the attached deposit at tx-conversion time (`runtime/runtime/src/lib.rs:1798`/`process_transactions`).
4. On Bob's shard, the inner action receipt fails; `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1284`) computes `deposit_refund = total_deposit` and issues `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`, where `balance_refund_receiver()` resolves to `predecessor_id = Alice` (per `runtime/runtime/src/actions.rs:515-519` and `core/primitives/src/receipt.rs`).
5. Alice receives the deposit back on her own account while the relayer's balance has been permanently reduced by the same amount — repeatable at will, with no penalty to Alice. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

```rust
        result: &mut ActionReceiptResult,

        created_account: bool,

        let total_deposit = total_deposit(&action_receipt.actions())?;
        let prepaid_gas = total_prepaid_gas(&action_receipt.actions())?
            .checked_add(total_prepaid_send_fees(config, &action_receipt.actions())?.gas)
            .ok_or(IntegerOverflowError)?;
        let prepaid_exec_gas =
            total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
                .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee())
                .ok_or(IntegerOverflowError)?;
        let deposit_refund = if result.result.is_err() { total_deposit } else { Balance::ZERO };
        let gross_gas_refund = if result.result.is_err() {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_burnt)
                .unwrap()
        } else {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_used)
                .unwrap()
        };

            gas_purchase_price
```

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
