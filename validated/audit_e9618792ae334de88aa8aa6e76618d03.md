### Title
Wallet Contract permanently absorbs relayer's attached deposit when `address_check_callback` short-circuits with a `Value` response - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point is `#[payable]` and tracks any deposit attached by a non-owner caller (typically a relayer) via `CallerDeposit`, intending to refund it later if the underlying cross-contract action fails [1](#0-0) . That refund is only implemented inside `rlp_execute_callback`, which is reached at the end of the normal promise chain [2](#0-1) . However, in `address_check_callback`, when the address-registrar lookup shows the target is already a named account and the caller is not the wallet owner, the function returns an `ExecuteResponse` `Value` directly instead of continuing to `rlp_execute_callback` [3](#0-2) . The `caller_deposit` value carried into this callback is simply dropped on this path, so the previously attached deposit is never refunded and never spent on any protocol action — it is permanently retained by the wallet contract's account balance.

### Finding Description
`rlp_execute` is `#[payable]`; any yoctoNEAR attached to the call is immediately credited to the wallet contract's account balance at the protocol level (Transfer/FunctionCall deposit accounting, `action_transfer_or_implicit_account_creation`), independent of what the contract logic subsequently does with it [4](#0-3) . Because this initial receipt itself succeeds (it merely schedules a promise), the protocol's automatic "deposit refund on failed receipt" mechanism described in `docs/RuntimeSpec/Refunds.md` never triggers [5](#0-4) . The contract therefore implements its own manual refund via `CallerDeposit`, which is only tracked for external (non-self) callers [6](#0-5)  and is only actually refunded inside `rlp_execute_callback` on `PromiseResult::Failed` [2](#0-1) .

The bug is that one call path — `address_check_callback`'s "target resolves to an existing named account and caller isn't the wallet owner" branch — bypasses `rlp_execute_callback` entirely and returns a `PromiseOrValue::Value(...)` immediately [3](#0-2) . The `caller_deposit` argument passed into `address_check_callback` is a plain function parameter that is dropped when this branch returns, with no promise created to send it back. This mirrors the Booster.sol pattern in the report: tokens (here, attached NEAR deposit) are absorbed by the contract's own balance with no code path that ever moves them back out — they become permanently commingled with the wallet's regular funds, indistinguishable from and inaccessible to the original depositor.

### Impact Explanation
Any external relayer submitting an `rlp_execute` transaction to a wallet contract, targeting another eth-implicit address with `address_check: Some(...)`, while attaching a non-zero deposit, and where that target address happens to already be a registered named account, will have their attached deposit permanently trapped in the wallet contract with no reachable recovery path. This is an unauthorized/irretrievable value loss for the relayer — reachable purely via crafting an ordinary RPC-submitted transaction (no privileged role, malicious validator, or network-level assumption required). This satisfies the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
The trigger requires: (1) a relayer/caller other than the wallet owner attaching a deposit to `rlp_execute`, and (2) the parsed transaction being an `EOABaseTokenTransfer` with `address_check: Some(address)` (i.e., targeting another eth-implicit account) where that address is discovered to already correspond to a named account in the registrar. Both conditions are achievable by any actor controlling the relayer role and crafting the RLP-encoded Ethereum transaction and target account, without needing validator or node privileges — a normal transaction/RPC path. This makes the bug realistically triggerable, though it depends on the specific combination of "relayer attaches deposit" and "target collides with an already-registered account," which is a narrower but still concretely reachable condition.

### Recommendation
In `address_check_callback`, before returning the early `Value(ExecuteResponse{...})` in the "target already registered, caller != owner" branch, refund `caller_deposit` (if present) via a `Promise::new(caller_deposit.account_id).transfer(...)`, exactly as `rlp_execute_callback` does on `PromiseResult::Failed`. More generally, centralize the caller-deposit refund logic so every early-return / error path in the callback chain (not just the final `rlp_execute_callback`) guarantees the deposit is either consumed by a successful action or refunded to its sender.

### Proof of Concept
1. A relayer (not the wallet owner) submits a signed RLP transaction to `wallet_contract.rlp_execute(target, tx_bytes_b64)`, attaching a deposit `D > 0`.
2. The parsed transaction is an `EOABaseTokenTransfer` whose target has `address_check: Some(address)`, causing `inner_rlp_execute` to call the address registrar and chain into `address_check_callback` with `caller_deposit = Some(CallerDeposit { account_id: relayer, yocto_near: D })` [7](#0-6) .
3. The registrar lookup returns `Some(existing_account_id)` (i.e., `address` already maps to a named account) and `env::signer_account_id() != current_account_id`, so `address_check_callback` executes:
```rust
return PromiseOrValue::Value(ExecuteResponse {
    success: false,
    success_value: None,
    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
});
``` [8](#0-7) 
4. No promise is created to refund `caller_deposit`; the function returns a plain value. The deposit `D`, already credited to the wallet contract's balance at receipt-application time, remains there permanently — verifiable by comparing the relayer's account balance before/after (decreases by `D` and never returns) versus the wallet contract's balance (increases by `D` and stays increased), analogous to the assertions used in `test_caller_refunds` for the working refund paths [9](#0-8) .
