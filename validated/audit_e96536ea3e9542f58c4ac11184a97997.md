Based on my investigation, I found a concrete, locally-provable gap in the replay-verification integrity check, distinct from a mere restatement of the external report.

### Title
Replay verification (`ensure_match_transaction_info`) never checks state/hot-state checkpoint roots, letting state-root divergence pass as a verified replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by `replay-verify`/`replay-on-archive` tooling to confirm that locally re-executing a transaction reproduces the canonical, validator-signed `TransactionInfo` from an on-chain backup. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but never checks `state_checkpoint_hash` or `hot_state_checkpoint_hash` — the fields that actually commit to the resulting global state (Sparse-Merkle/Jellyfish-Merkle) root. This is acknowledged directly in the code by an unresolved `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates four properties of the replayed `TransactionOutput` against the trusted `TransactionInfo`: status, gas used, `state_change_hash` (write-set hash), and `event_root_hash`. It explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, as documented in the trailing comment: [2](#0-1) 

The `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields are the actual commitments to the post-execution global state tree, computed independently of the write-set hash via `DoStateCheckpoint::run`, which derives them from the accumulated Sparse-Merkle summary root, not from any single transaction's write set: [3](#0-2) . A per-transaction write-set hash match does not imply that applying that write set on top of the correct prior state yields the correct resulting state root — e.g., if a prior transaction's write-set application diverges (double-apply, ordering bug, or an omitted upstream key), the local `state_change_hash` may still match for the current transaction while the cumulative state root drifts.

The only consumer that performs this specific comparison is `replay_on_archive.rs`'s `execute_and_verify`, which calls exactly this function and nothing else to confirm a match: [4](#0-3) . There is no additional step in that flow that independently recomputes the JMT/SMT root from replayed writes and compares it to the archived `state_checkpoint_hash`.

### Impact Explanation
`replay-on-archive`/`replay-verify` is the mechanism operators and the Aptos Foundation use to confirm that VM execution against archived transactions reproduces the exact canonical ledger state — this is the primary hard-fork/non-determinism detection tool. Because the comparator never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`, a class of bugs that corrupts the accumulated state tree (while leaving the immediate write-set hash of the currently-replayed transaction untouched — e.g., a stale/incorrect base state carried from a previous transaction, an execution-order bug, or a state-tree update bug) would be silently reported as a successful, verified replay. This directly matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category: the divergence is real and undetected specifically because a required proof/commitment field is skipped in the checker, not because of any external validator misbehavior.

### Likelihood Explanation
This is not a hypothetical extrapolation — it is a currently-shipped, unprivileged blind spot in the verification code path itself, independent of external inputs; any state-divergence bug (VM non-determinism, execution-order bug, hot-state/SMT update bug) that preserves per-txn write-set/event/gas/status equality will pass `replay-verify` undetected today for both `state_checkpoint_hash` and `hot_state_checkpoint_hash` (which are populated in production block/chunk execution regardless of the still-disabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature that only gates `position_state_checkpoint_hash`). The comment itself confirms the gap is understood as real but unresolved.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_output`'s locally-computed post-execution `state_checkpoint_hash` (and `hot_state_checkpoint_hash`, when present) against the corresponding hashes carried in the trusted `TransactionInfo`, at least whenever the checkpoint is expected at that version, before treating a replay as matching.

### Proof of Concept
Not directly exploitable via a single crafted transaction from this codebase alone; the gap is a missing invariant check. A conceptual PoC: introduce (or trigger via an existing non-determinism/state-update bug) a code path where a transaction's write-set bytes/hash, gas, status, and events are reproduced identically on replay, but the state actually applied to storage before/after this transaction differs from the canonical state (e.g., due to a stale base state or an incorrect Merkle update), producing a different `state_checkpoint_hash`/`hot_state_checkpoint_hash`. Running `replay-on-archive` over that range via [5](#0-4)  will report a clean/successful replay despite the state-root divergence, because `ensure_match_transaction_info` never inspects the checkpoint-hash fields.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

        if cur_txns.is_empty() {
