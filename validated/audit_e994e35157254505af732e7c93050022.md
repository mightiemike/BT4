### Title
Unbounded gas on `executeUniversalTx` callback to attacker-deployed CEA recipient contract enables gas griefing during inbound finalization - (File: `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
`RFTLib`'s `settle()`/`reentrantSettle()` call an arbitrary, caller-supplied `payer` contract's `tokenRequestCB()` with no gas cap, so a malicious payer can grief the caller's gas. Push Chain has the same pattern: for CEA (contract-execution-address) inbounds, the uexecutor module calls `executeUniversalTx` on an attacker-chosen `Recipient` contract via `CallExecuteUniversalTx` → `DerivedEVMCall`, passing `gasLimit = nil` [1](#0-0) , with no caller-imposed cap on how much gas that untrusted callback can consume.

### Finding Description
For `IsCEA` inbounds, the recipient is whatever hex address the (unprivileged) source-chain sender put in the inbound event; the module checks only whether it is a UEA, and if not, whether it "has code" (`GetCodeHash`) to decide it's a smart contract to call back into [2](#0-1) . Any attacker can pre-deploy an arbitrary contract at that address and trigger an inbound targeting it — no privileged role is required.

Once flagged as a smart-contract recipient, the module invokes `CallExecuteUniversalTx`, which calls `executeUniversalTx` on that untrusted, attacker-controlled contract through `DerivedEVMCall` with `gasLimit=nil`: [1](#0-0) 

Per the project's own documentation, `gasLimit=nil` means "use a sensible default," and there is no mechanism at any of the three call sites (`execute_inbound_funds_and_payload.go`, `execute_inbound_gas_and_payload.go`) to bound or cap the gas the untrusted recipient contract can consume before this default kicks in [3](#0-2) [4](#0-3) . This is functionally identical to the `RFTLib` issue: an untrusted, attacker-supplied contract is invoked as a callback in a consensus-critical execution path (every honest Universal Validator/node executing inbound finalization must replay this same call to reach the same state), with the caller ceding control over gas consumption to the callee. A malicious recipient contract can implement an expensive `executeUniversalTx` (e.g., large loops/storage writes bounded only by the "sensible default"/block gas limit) to maximize gas burned by every node executing this inbound.

I was unable to locate the exact numeric value or resolution logic behind the "sensible default" (it appears to live in the forked `github.com/pushchain/evm` dependency, not in this repository), so I cannot state precisely how large the attacker-achievable griefing window is — this is a genuine unknown given the index's visibility into the forked EVM module.

### Impact Explanation
Every inbound of this shape must be independently re-executed by each node during finalization to converge on the same `UniversalTx`/PCTx state. If an attacker can force worst-case (near block-gas-limit) EVM execution on every such inbound, this is a resource-exhaustion/DoS vector reachable by an ordinary unprivileged user (attacker only needs to deploy a contract on the destination chain matching the CEA `Recipient` and originate one inbound event) — falling squarely under the "denial of service...reachable without privileged control" allowed impact for this scope. It can also distort gas-fee accounting downstream, since `DeductGasFeesFromReceipt` uses `contractReceipt.GasUsed` to charge fees against the deposited PRC20, coupling accounting correctness to the attacker-inflated gas figure (I could not locate `DeductGasFeesFromReceipt`'s implementation in the index to fully verify the accounting consequence, so this secondary effect is noted as unconfirmed).

### Likelihood Explanation
Medium. The trigger requires only deploying a contract on a supported chain and initiating one CEA inbound with `Recipient` pointing at it — no privileged role, no validator collusion, and no special timing is needed. The main uncertainty is the actual ceiling imposed by the fork's "sensible default" gas limit, which bounds how severe the griefing can get per call.

### Recommendation
- Introduce an explicit, protocol-configured (e.g., via `x/uregistry` params) gas cap for `CallExecuteUniversalTx`'s `executeUniversalTx` invocation instead of relying on the fork's implicit default, mirroring the report's recommendation to let the caller set an explicit gas cap on the untrusted callback.
- Ensure the cap is small enough to bound worst-case per-inbound execution cost while still allowing legitimate CEA use cases, and fail closed (mark the PCTx `FAILED`, no fund loss) when the cap is hit rather than propagating unbounded cost.
- Audit `DeductGasFeesFromReceipt` to confirm gas-fee accounting cannot be distorted by attacker-inflated `GasUsed` values from a malicious recipient.

### Proof of Concept
1. Attacker deploys a contract `Malicious` on a supported source-adjacent chain context whose `executeUniversalTx(...)` implementation performs gas-maximizing work (e.g., a loop writing many storage slots) bounded only by whatever gas is forwarded.
2. Attacker submits/originates a CEA inbound event with `Recipient = address(Malicious)` and `IsCEA = true`.
3. Universal Validators vote on and the module finalizes the inbound; `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` detect `isSmartContract=true` and call `k.CallExecuteUniversalTx(...)` [5](#0-4) , which issues `DerivedEVMCall(..., gasLimit=nil, ...)` [1](#0-0) , letting `Malicious` consume gas up to the fork's uncapped default on every honest node processing this inbound.
