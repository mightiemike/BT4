### Title
`isSafe` in `validate-redirect-url.ts` accepts protocol-relative URLs (`//evil.com`, `\\evil.com`), causing host confusion - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts`)

### Summary
`isSafe`/`sanitizeRedirectUrl` is meant to restrict redirects to the app's own domain, but it validates `url.pathname` after WHATWG `URL` resolution rather than the raw input. A redirect target of `//evil.com` (or the backslash-equivalent `\\evil.com`, since WHATWG URL treats `\` as `/` for special schemes) is parsed as a protocol-relative URL, changing the resolved host to `evil.com` while leaving `pathname` as `/`, so none of the existing checks reject it.

### Finding Description
`isSafe` performs these checks on `redirectUrl` (`packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts:16-53`):
1. `FILE_URI_MATCH = /\/\/\//` rejects triple-slash (file-style) URLs. [1](#0-0) 
2. `WHITESPACE_CHARACTER` rejects whitespace.
3. `new URL(redirectUrl, domain)` is used to resolve the URL against the app's domain. [2](#0-1) 
4. `INVALID_RELATIVE_URL = /[/\\][/\\]/` is checked against `url.pathname` (the already-resolved URL's path), not the raw `redirectUrl` string. [3](#0-2) 
5. Only `http:`/`https:` protocol and optional SSL requirement are enforced afterward. [4](#0-3) 

The flaw: when `redirectUrl` is `//evil.com` (or the backslash equivalent, which the WHATWG URL parser normalizes to slashes for special schemes like `http`/`https`), `new URL("//evil.com", "https://app.example.com")` resolves to `https://evil.com/` — the scheme-relative syntax overrides the host from the base `domain`. After this resolution, `url.pathname` is simply `/`, which does **not** match `INVALID_RELATIVE_URL` (it only catches doubled slashes in the *path*, not in the *authority* part that was already consumed during parsing). The double slash triggering the host override happened before the pathname check runs, so it's invisible to that regex. `FILE_URI_MATCH` (triple-slash) also does not match a two-slash prefix. The protocol check passes because `evil.com` is resolved with `https:` protocol inherited from the resolution rules. Consequently `isSafe` returns `true`, and `sanitizeRedirectUrl` returns a `URL` object pointing at `evil.com` instead of throwing.

This function is used by `renderAppBridge` (`packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/render-app-bridge.ts:21`) to sanitize a `redirectTo.url` before embedding it in a `window.open(...)` script, and by the equivalent React Router package. [5](#0-4) 

### Impact Explanation
If any caller passes an attacker-influenced value into `redirectTo.url` (e.g. a `return_to`/`redirect` query parameter surfaced through app logic built on top of `renderAppBridge`), this bug allows the sanitizer to "approve" a URL whose host is fully attacker-controlled (`evil.com`) despite the domain-restriction intent of `sanitizeRedirectUrl`. This is a classic open-redirect/host-confusion primitive: the browser is directed to open an attacker's origin from inside the merchant's authenticated admin/app context, which can be leveraged for token theft or phishing if any sensitive parameters (session tokens, host/shop params) are also forwarded to the redirect target by the host application.

### Likelihood Explanation
The bypass itself is trivially reproducible with a unit test calling `sanitizeRedirectUrl` directly, requires no privileges, and needs only sending a crafted `//evil.com` or `\\evil.com` string as the redirect target. Full exploitability at the HTTP-request level then depends on whether a specific caller in the app (or in this SDK) forwards a raw, attacker-controlled query parameter into `sanitizeRedirectUrl`/`renderAppBridge` without prior restriction — the callers found in this SDK (`redirect-to-bounce-page.ts`, `redirect-to-install-page.ts`, etc.) mostly construct the URL internally rather than take it directly from user input, so I could not fully confirm an end-to-end unauthenticated HTTP path within this SDK's own code in the time available. The core library-level flaw (the sanitizer's failure to prevent protocol-relative URLs) is nonetheless real and directly demonstrable.

### Recommendation
Reject scheme-relative/authority-changing inputs before resolving with `new URL()`, e.g. explicitly reject any `redirectUrl` starting with `//` or `\/` or `\\` (after normalizing backslashes to slashes) prior to parsing, and/or compare `url.host`/`url.origin` of the resolved URL against the expected `domain`'s origin rather than only checking `pathname` and `protocol`. For example:

```ts
if (/^[/\\]{2}/.test(redirectUrl.replace(/\\/g, '/'))) {
  return false;
}
...
if (url.origin !== new URL(domain).origin) {
  return false;
}
```

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
