### Title
JSON-RPC receipt reports non-null `contractAddress` for failed `CreateSmartContract` deployments (e.g. out-of-energy) - (File: framework/src/main/java/org/tron/core/services/jsonrpc/types/TransactionReceipt.java)

### Summary
`TransactionReceipt` populates `contractAddress` solely based on `contract.getType() == ContractType.CreateSmartContract`, without checking whether `txInfo.getReceipt()`/`status` indicates success. Because the contract address is deterministically computed and written into `ProgramResult` *before* constructor execution runs (in `VMActuator.create()`), and `TransactionUtil.buildTransactionInfoInstance` unconditionally copies `programResult.getContractAddress()` into the persisted `TransactionInfo` regardless of whether the transaction result was `SUCESS` or `FAILED`, a reverted/out-of-energy contract creation still surfaces a non-empty `contractAddress` field in the eth-style receipt even though `status` is `"0x0"`.

### Finding Description
In `VMActuator.create()`, the deterministic contract address is computed via `WalletUtil.generateContractAddress(trx)` and immediately set on `program.getResult()` at line 437, *before* the VM constructor bytecode executes [4](#0-3) . If the constructor subsequently fails (e.g. runs out of energy, or throws an exception caught elsewhere in the execution pipeline), nothing observed in `buildTransactionInfoInstance` clears `programResult.getContractAddress()`; the builder only toggles `result` between `SUCESS`/`FAILED` based on `trace.getRuntimeError()`/exception, while `contractAddress` is copied unconditionally from `programResult.getContractAddress()` at line 93/97 [5](#0-4) .

Downstream, `TransactionReceipt`'s constructor sets `status` from `txInfo.getReceipt().getResultValue()` [6](#0-5)  but sets `contractAddress` independently, purely gated on `contract.getType() == ContractType.CreateSmartContract`, with no cross-check against `status` or `txInfo.getResult()` [7](#0-6) . This means the deterministic pre-computed address (which is always derivable off-chain from the sender + nonce/txid and doesn't depend on execution success) is echoed back in the receipt even for failed deployments.

### Impact Explanation
This is an off-spec API/accounting-representation deviation, not a fund-theft or authorization bypass: no value is moved, no double-settlement occurs, and no unauthorized state change happens, since the actual on-chain state (`AccountCapsule`/contract code) is not created for a failed deployment — only the JSON-RPC surface reports an address. It could mislead external tooling/wallets/exchanges into believing a contract was successfully deployed at that address when in fact no code exists there, which could cause off-chain accounting confusion.

### Likelihood Explanation
This is trivially and repeatably reproducible by any unprivileged user: broadcast a `CreateSmartContract` transaction with a `feeLimit`/constructor gas cost engineered to run out of energy during construction, then query the receipt via `eth_getTransactionReceipt`. Given the address is deterministic and computed before execution, and there is no cleanup of `contractAddress` on constructor failure, this is expected to reproduce consistently.

### Recommendation
In `TransactionReceipt`, only populate `contractAddress` when both `contract.getType() == ContractType.CreateSmartContract` AND the transaction succeeded (e.g. `txInfo.getReceipt().getResultValue() <= 1` / `status == "0x1"`, matching Ethereum JSON-RPC semantics where `contractAddress` is null on failed deployments). Alternatively/additionally, clear `programResult.getContractAddress()` in `TransactionUtil.buildTransactionInfoInstance` (or in `VMActuator`) when the deployment result is `FAILED`/reverted, so the underlying `TransactionInfo.contract_address` itself is not populated for failed creations.
