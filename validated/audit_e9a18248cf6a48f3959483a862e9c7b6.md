Based on my investigation, the strongest candidate is a documented-but-real gap in `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs`, used by replay-verification tooling (`db-tool`'s `replay_on_archive`, `aptos-debugger`, and the CLI). This function is explicitly designed to authenticate a locally-recomputed `TransactionOutput` against a `TransactionInfo` fetched (with proof) from an authenticated source, but it does not check all the fields that are actually part of the hashed/committed `TransactionInfo`.

### Title
Replay-verification only authenticates a subset of `TransactionInfo` fields, allowing corrupted state-checkpoint roots to pass as valid - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the function used to authenticate that a freshly-executed transaction output matches the on-chain `TransactionInfo` during replay/verification (e.g. `replay_on_archive`). It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of `TransactionInfoV1` and are included in the accumulator-hashed struct [2](#0-1) .

### Finding Description
This mirrors the reported bug pattern: a function meant to validate "the whole committed state" only covers part of it, silently omitting a component that should have been included. Here, `ensure_match_transaction_info`'s own doc comment acknowledges the gap: [3](#0-2) 

The state/hot-state checkpoint hashes and the newly added `position_state_checkpoint_hash` (used for the "trading native state roots" feature, gated by `compute_trading_native_state_roots`, see `execution/executor/src/workflow/do_state_checkpoint.rs` and `types/src/block_executor/config.rs`) are computed by a separate, more complex pipeline (`do_state_checkpoint.rs`'s `get_position_checkpoint_hashes`/checkpoint extension logic) that is not exercised by this comparator at all.

### Impact Explanation
If the position/hot-state checkpoint computation ever diverges from the authenticated ledger value (due to a bug in `do_state_checkpoint.rs`'s checkpoint-range collapsing logic, a state-sync/restore ordering issue, or a non-deterministic node bug), `replay_on_archive` and other replay-verify tooling will report a **successful** replay/verification even though the locally-computed authenticated state root for the position/native-trading state has silently diverged from the real ledger. This is exactly the class of "authenticated API or state-view output bound to the wrong version, object, or proof context" that the gate calls out — operators and node runners relying on replay-verify to detect state divergence get a false "all good" signal for a subset of committed durable ledger data.

### Likelihood Explanation
This is a **detection gap**, not an active state-corruption bug by itself — it requires an independent root-cause bug in checkpoint/hash computation to actually produce a divergent value. The comparator's omission is explicit, intentional (per the TODO), and gated behind an unreleased/experimental feature flag (`compute_trading_native_state_roots`), which lowers the likelihood of exploitation on current mainnet. I was not able to fully verify whether `compute_trading_native_state_roots` is enabled on mainnet or still gated as a feature under development, since the flag definition search only surfaced usages, not is-mainnet-live status.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally-computed output and the trusted `TransactionInfo`, at least when `compute_trading_native_state_roots` (or the relevant feature) is enabled, so replay/verify tooling cannot report false success while a checkpoint root diverges.

### Proof of Concept
Not applicable as a standalone PoC — this is a coverage gap in a diagnostic/verification comparator, not a executable state-corruption exploit path by itself; confirming real impact would require a separate PoC that first produces a divergent position/hot-state checkpoint hash (from a bug in the checkpoint pipeline), then shows `ensure_match_transaction_info` incorrectly returning `Ok(())` for it. I could not construct or confirm such a root-cause divergence within the scope of this investigation, so confidence in this finding rising above "informational/detection-gap" is limited.

**Caveat:** Given the explicit TODO acknowledging this limitation and the gated nature of the affected feature, this finding is best characterized as a low/medium-severity detection-gap rather than a directly exploitable High/Critical state-integrity vulnerability. If your bar requires only High/Critical, independently-provable root causes, this candidate does not fully clear that bar, and I did not find another local Aptos-native analog with a stronger, self-contained proof of a broken invariant, corrupted value, and independently verifiable impact within my search budget.
