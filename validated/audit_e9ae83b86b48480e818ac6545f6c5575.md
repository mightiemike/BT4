**Analysis:**

The claimed desync path requires a "later collection-level mutability flag flip" for `mutable_token_description`, `mutable_token_name`, or `mutable_token_uri` on `AptosCollection`. These fields are set once in `create_collection_object` [1](#0-0)  and there is no entry function anywhere in `aptos_token.move` that mutates them after creation — the only collection-level setters present (`set_collection_description`, `set_collection_uri`) touch the separate `mutable_description`/`mutable_uri` fields (collection metadata mutability), not the token-mutability flags [2](#0-1) .

Because `mutable_token_description`/`mutable_token_name`/`mutable_token_uri` are immutable for the lifetime of the collection, the decision made once in `mint_internal` to populate `mutator_ref` (based on those same flags at mint time) [3](#0-2)  stays permanently consistent with what `is_mutable_description`/`is_mutable_name`/`is_mutable_uri` report, since those view functions read the identical, never-changed collection fields [4](#0-3) [5](#0-4) . There is no code path — privileged or unprivileged — that flips these specific flags post-creation, so the premised "later collection-level mutability flag flip" does not exist in this module.

Additionally, `#[view]` functions here directly borrow the live on-chain resource (`borrow_collection`/`borrow`) rather than any cached or derived proof artifact [6](#0-5) , so there is no separate proof/accumulator/state-proof binding that could diverge from the resource's committed value — the view result and the stored `Option` state are read from the exact same storage slot.

Since the flag-flip premise is false and the view functions are simple direct reads of committed resource state with no independent proof material to desynchronize, this does not meet the state-integrity/proof-corruption bar required by the review scope.
