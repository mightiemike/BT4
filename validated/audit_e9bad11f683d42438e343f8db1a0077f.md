### Title
Stale-Cache Authorization Bypass for Cairo 0 Classes on Block Revert — ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` re-validates a cache hit against current declared-state only for Cairo 1 (`V1`/`V1Native`) classes, explicitly because "existence in the cache does not guarantee [declaration] ... it might contain a declared class from a reverted block." Cairo 0 (`V0`) classes are returned straight from the global cache with **no** equivalent re-validation, so the exact staleness scenario the code was written to prevent for V1 is left open for V0.

### Finding Description
`get_compiled_from_class_manager` looks up the class in the process-wide `GlobalContractCache` (`ContractClassManager`/`class_cache`, an LRU cache keyed only by `ClassHash`, with no block/state-number dimension): [1](#0-0) 

For non-`V0` classes it calls `self.state_reader.is_declared(class_hash)` before trusting the cached value, explicitly to guard against a class hash whose cache entry originates "from a reverted block." For `V0` this check is skipped entirely — the branch is a no-op: [2](#0-1) 

Crucially, `FetchCompiledClasses::is_declared` is documented to only ever report `true` for Cairo 1 classes ("Cairo 0 classes always return `false`"), which is why the asymmetry exists — but it means the exact protection applied to V1 simply has no analog for V0: [3](#0-2) 

`ApolloReader::is_declared` computes declaration validity against a specific `state_number` (pinned block), confirming that declaration status is inherently block/state-relative and can legitimately differ between two reader instances pinned at different blocks: [4](#0-3) 

The `GlobalContractCache` itself carries no notion of the state/block at which an entry was populated — it is a flat `ClassHash -> CompiledClasses` LRU shared by whichever `ContractClassManager` clone uses it: [5](#0-4) 

Given the comment's own acknowledgment that a block revert can leave the cache holding an entry for a class hash that is not (or not yet) actually declared in the current committed state, a Cairo 0 class hash that once got cached (e.g., speculatively executed then reverted, or declared in a later block than the one a given state reader is pinned to) will be served as a valid, executable class with zero re-validation, while an equivalent Cairo 1 class hash in the identical situation is correctly rejected via `UndeclaredClassHash`.

### Impact Explanation
If a Cairo 0 class becomes stale-cached against a particular declared/undeclared state, downstream consumers (block execution, stateful validation pinned to a fixed block) can treat an undeclared class hash as executable, producing incorrect execution results relative to the true committed state. This can drive execution down a path that diverges from what an honest re-execution against the correct declared-state would produce (wrong resource accounting, wrong call results), and in the Starknet OS re-execution / commitment path this generates the risk of computing a wrong state root or diverging from other honest nodes that never had the stale cache entry.

### Likelihood Explanation
This requires a state where a class-hash's declaration status can legitimately differ between the cache-population point and the query point — i.e., across a block revert or across two differently-pinned state readers sharing the same process-wide `GlobalContractCache`. This is exactly the scenario the code's own comment calls out as a real, encountered condition for V1; nothing distinguishes V0 classes from that same risk other than the design choice to skip the check, so the trigger is not attacker-privileged — it is any Cairo 0 declare whose containing block is later reverted/re-ordered during normal sequencer operation.

### Recommendation
Add an equivalent freshness check for `V0` cache hits, e.g., extend `FetchCompiledClasses::is_declared` (or a new state-reader method) to also validate Cairo 0 class declaration status at the current state, and call it in the `V0` branch of `get_compiled_from_class_manager` exactly as done for the non-`V0` branch, rather than treating `V0` as inherently safe to trust from cache.

### Proof of Concept
1. Declare a Cairo 0 class `C` (class hash `H`) in a speculative/candidate block; some component populates the shared `GlobalContractCache` for `H` (e.g., via `get_compiled_from_class_manager` during speculative execution).
2. That block is reverted/re-ordered such that, in the finally-committed state, `H` is not declared (or not declared until a later block).
3. A subsequent state reader pinned to the committed state (pre-declaration) calls `get_compiled_class(H)`; because `H` is a `V0` entry, `get_compiled_from_class_manager` returns the cached compiled class directly without calling `is_declared`, silently treating an undeclared class hash as valid and executable — unlike the identical scenario for a `V1` class hash, which is correctly rejected with `StateError::UndeclaredClassHash`.

pub struct GlobalContractCache<T: Clone>(pub Arc<Mutex<ContractLRUCache<T>>>);

impl<T: Clone> GlobalContractCache<T> {
    /// Locks the cache for atomic access. Although conceptually shared, writing to this cache is
    /// only possible for one writer at a time.
    pub fn lock(&self) -> LockedClassCache<'_, T> {
        self.0.lock().expect("Global contract cache is poisoned.")
    }

    pub fn get(&self, class_hash: &ClassHash) -> Option<T> {
        self.lock().cache_get(class_hash).cloned()
    }

    pub fn set(&self, class_hash: ClassHash, contract_class: T) {
        self.lock().cache_set(class_hash, contract_class);
    }

    pub fn clear(&mut self) {
        self.lock().cache_clear();
    }

    pub fn new(cache_size: usize) -> Self {
        Self(Arc::new(Mutex::new(ContractLRUCache::<T>::with_size(cache_size))))
    }
