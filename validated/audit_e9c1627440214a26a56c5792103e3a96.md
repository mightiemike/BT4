### Title
Floating-point exchange-curve math (`ExchangeProcessor`/`MathWrapper.pow`) can diverge across platforms and produce imprecise results, mirroring the ABDKMathQuad edge-case bug - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The bancor-style TRC10 exchange curve implemented by `ExchangeProcessor` performs its core supply/balance conversion using native Java `double` arithmetic and a platform-specific `pow` implementation (`MathWrapper.pow`, with separate `arm` and `x86` builds), exactly the class of "limited precision math library" bug described in the ABDKMathQuad report: fixed/floating-point libraries with edge cases where conversions and exponentiation do not round consistently. [1](#0-0) [2](#0-1) 

### Finding Description
`ExchangeCapsule.transaction()` selects between the legacy `ExchangeProcessor` (double-based `Math.pow`) and a `SafeExchangeProcessor` (BigDecimal-based) depending on a governance-controlled flag `allowHardenExchangeCalculation`/`hardenedCalc`. [3](#0-2) 

The legacy `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` methods compute `Math.pow(1 + quant/balance, 0.0005)` and `Math.pow(1 + supplyQuant/supply, 2000.0)` entirely in `double` precision, then truncate to `long`: [4](#0-3) 

The `pow` operation itself is dispatched through `Maths.pow(a, b, useStrictMath)`, which either calls `StrictMathWrapper.pow` or `MathWrapper.pow`, and the codebase ships **separate `MathWrapper` implementations for `arm` and `x86` platforms** (`platform/src/main/java/arm/org/tron/common/math/MathWrapper.java` and `platform/src/main/java/x86/org/tron/common/math/MathWrapper.java`). This is directly analogous to the ABDKMathQuad finding: an underlying numeric library whose precision/rounding behavior can differ at the edges depending on implementation/platform, causing the same exchange transaction to yield different `anotherTokenQuant` results on different validator hardware.

This double-precision path is reachable by any account through an unprivileged, anonymous broadcast transaction — `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all invoke `exchangeCapsule.transaction(...)` with `useStrictMath` derived from `dynamicStore.allowStrictMath()`, and by default the "hardened" (BigDecimal) calculation path is disabled unless activated by a committee proposal. [5](#0-4) [6](#0-5) 

### Impact Explanation
Because different SR/witness nodes may run on different CPU architectures, a `double`-based `pow` computation whose last-bit rounding differs between `arm` and `x86` `MathWrapper` implementations can cause the *same* `ExchangeTransactionContract` to compute a different `anotherTokenQuant` on different nodes, leading to disagreement on the resulting `ExchangeCapsule` balances and account asset amounts. Since this quantity is written directly into consensus state (`AccountCapsule` balances, `ExchangeCapsule.setBalance`), a divergence here can produce a **state/consensus divergence** between nodes — the most severe class of impact for this bug pattern. Even absent literal fork risk, precision loss in the curve math can be leveraged by a user to extract more tokens than the intended AMM invariant allows, i.e., **accounting corruption** in the exchange pool.

### Likelihood Explanation
Likelihood is moderate: the vulnerable double/`pow`-based path is the *default* production path (hardened BigDecimal calculation must be explicitly enabled by committee proposal), and it is triggered by ordinary, unprivileged `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions that any account can broadcast. Exploiting it to produce a cross-platform divergence, however, requires validators to actually be running mixed architectures and requires finding input values near a rounding boundary in `Math.pow`, which is the same "requires fuzzing to find edge cases" caveat the original report itself acknowledges (FairSide's own response treated it as low severity for this reason).

### Recommendation
- Ensure `allowHardenExchangeCalculation` (BigDecimal-based `SafeExchangeProcessor`) is the enforced default consensus path rather than an optional proposal, removing the legacy `double`/`Math.pow` path from `ExchangeProcessor` entirely once activated network-wide.
- Eliminate architecture-specific `MathWrapper` implementations for consensus-critical paths (`arm` vs `x86`), or verify via fuzzing (e.g., Echidna-equivalent JVM fuzzing/property tests) that `MathWrapper.pow` produces bit-identical results across supported platforms for the full range of `(balance, quant)` values.
- Add exhaustive edge-case/differential tests (as already partially done in `CalculateGlobalLimitHardenTest`/`RepositoryImplHardenTest`) specifically comparing `ExchangeProcessor` vs `SafeExchangeProcessor` outputs across the full input domain, not just spot values, and fail closed (reject the transaction) rather than silently returning divergent results if a difference exceeding a defined epsilon is found.

### Proof of Concept
1. Deploy two validator nodes, one on `x86`, one on `arm`, both with `allowHardenExchangeCalculation = 0` (default).
2. Broadcast an `ExchangeTransactionContract` with `firstTokenBalance`/`secondTokenBalance`/`sellTokenQuant` chosen near a `double` rounding boundary for `Math.pow(1+x, 0.0005)` (values can be found via fuzzing similar to the Echidna approach referenced in the report).
3. Compare the `anotherTokenQuant` computed by `ExchangeProcessor.exchange()` on each node; a differing last-digit result — reachable directly through `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java` lines 17-39 — demonstrates the precision-divergence class of bug described in the report, applied to java-tron's exchange curve implementation.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
