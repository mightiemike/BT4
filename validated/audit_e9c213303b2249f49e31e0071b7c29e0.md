I have sufficient evidence to identify a valid analog. This proportional vote-scaling logic in `UnfreezeBalanceV2Actuator.updateVote` (and its identical twin in `UnfreezeBalanceV2Processor.updateVote`, reachable from a TVM contract call) is a direct analog of the reported rounding-down bug in `Voter.sol`.

### Title
Proportional vote-count rescaling after `UnfreezeBalanceV2` rounds down per-witness allocations, wasting a voter's residual TRON Power - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java`)

### Summary
When an account unfreezes part of its stake via `UnfreezeBalanceV2Contract` (or the equivalent TVM native-contract path), and the account's votes now exceed its remaining TRON Power, `updateVote()` proportionally rescales each witness's vote count using per-vote floating point division and floor-casting to `long`. Just like the reported `Voter.sol` bug, this independent-per-item rounding causes the sum of the rescaled vote counts to be strictly less than the truly available TRON Power, silently discarding voting power instead of allocating it to any witness.

### Finding Description
`updateVote` computes each witness's new vote count as: [1](#0-0) 

```java
for (Vote vote : accountCapsule.getVotesList()) {
  long newVoteCount = (long)
      ((double) vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION);
  ...
}
```

Each term is independently floored via the `(long)` cast, exactly the pattern described in the report (`_poolWeight = (_weights[i] * totalPower) / _totalVoteWeight` — per-item floor division without reconciling the remainder against the total). Because the cast happens per-witness and no witness receives the leftover remainder, `sum(newVoteCount)` can be — and typically is — strictly less than the account's true proportional share of `ownedTronPower`. The identical logic exists in the TVM native-contract path used when unfreezing is triggered via a contract call: [2](#0-1) .

This code is reached from a broadcast `UnfreezeBalanceV2Contract` transaction via `UnfreezeBalanceV2Actuator.execute()` [3](#0-2) , and from a smart contract's native "unfreezeBalanceV2" precompile call via `UnfreezeBalanceV2Processor.execute()` [4](#0-3)  — both are anonymous, unprivileged entry points.

### Impact Explanation
The rounding loss means an unfreezing voter's usable TRON Power for governance/witness voting is understated versus its true remaining stake, analogous to the original report's "voters disadvantaged, skewed voting results" impact. Because the calculation is fully deterministic and identical across all nodes, this does not cause consensus divergence; it is a value/vote-power leakage issue rather than a corruption of shared state, consistent with the reported impact category "fails to deliver promised (voting) power, doesn't lose value" (the discarded vote fraction is simply never counted for any witness). Witness vote totals used for standby-reward calculations (`MortgageService.payStandbyWitness`, `IncentiveManager.reward`) and SR ranking are downstream consumers of these vote counts, so repeated unfreeze operations by many accounts can compound this systematic undercount across the active witness set.

### Likelihood Explanation
Likelihood is high for occurrence (any account with multiple witness votes that partially unfreezes stake below its total vote count triggers this path) but the per-transaction magnitude is small (sub-integer TRX rounding, since `TRX_PRECISION` divides at the end). It requires no special privilege — any account holder can trigger it by voting for multiple witnesses and then unfreezing.

### Recommendation
Do not floor every per-witness share independently. Instead, either (a) use `BigInteger` for the intermediate multiplication and reconcile the last processed vote's count as `ownedTronPower/TRX_PRECISION - sumOfPreviouslyAllocated` so the total exactly matches the account's available TRON Power, or (b) track the cumulative allocated total across the loop and adjust the final vote (or largest vote) by the leftover remainder, mirroring the "allocate the last item via subtraction, not division" fix recommended in the original report for `Voter.sol`.

### Proof of Concept
Given an account with 3 votes of counts `[10, 50, 75]` (`totalVote = 135`) and `ownedTronPower` corresponding to `500` TRX-equivalent vote units after unfreeze:
```
newVoteCount(10) = floor(10/135*500)  = 37
newVoteCount(50) = floor(50/135*500)  = 185
newVoteCount(75) = floor(75/135*500)  = 277
sum = 499  <  500  (1 unit of TRON Power silently lost, not credited to any witness)
```
This mirrors the reported PoC exactly and reproduces via `UnfreezeBalanceV2Actuator.updateVote` [1](#0-0)  whenever `ownedTronPower < totalVote * TRX_PRECISION` after an `UnfreezeBalanceV2Contract` transaction.
