### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay/chunk-execution verification to accept a divergent committed state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by the chunk executor and replay/verification tooling to confirm that a freshly re-executed `TransactionOutput` matches the already-committed `TransactionInfo` pulled from storage/backup. The function validates status, gas used, write-set hash, and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents with a `TODO`.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks four fields (status, gas_used, write_set_hash, event_root_hash) against the stored `TransactionInfo`, then returns `Ok(())` without ever comparing `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The code comment makes the gap explicit: [2](#0-1) 

This function is consumed as the sole cross-check in:
- `execution/executor/src/chunk_executor/mod.rs` (chunk replay during state sync / fast sync)
- `storage/db-tool/src/replay_on_archive.rs` (operator/verification tooling that replays historical transactions against an archive and is meant to catch consensus/state divergence)
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`

The checkpoint hashes are exactly the fields that summarize the Sparse-Merkle-Tree / hot-state / native-position state roots at a checkpoint version — i.e., the actual world-state commitment (`TransactionInfoV1.state_checkpoint_hash`, `.hot_state_checkpoint_hash`, `.position_state_checkpoint_hash`, defined at [3](#0-2) ). These are the values folded into the `TransactionInfo` hash that ultimately feeds the transaction accumulator root committed on-chain (see `DoLedgerUpdate::assemble_transaction_infos`, which builds these hashes into `TransactionInfo::builder_v1()` at [4](#0-3) ).

Because `ensure_match_transaction_info` never checks these fields, a local re-execution that produces a *different* state-checkpoint root (state SMT root, hot-state root, or native-position root) than the one already committed to the ledger will still be reported as "matching" by chunk-executor replay and by `replay_on_archive`. The state root divergence — the exact signal that state-integrity tooling exists to catch — is silently ignored.

### Impact Explanation
This breaks the proof/state-integrity invariant that "committed state that differs from the correct VM result" must be detectable by replay verification. If a bug in state-checkpoint computation (SMT update, hot-state update, or the newer native-position state root under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) causes a node's locally computed checkpoint root to diverge from the already-authenticated on-chain root, chunk-executor replay (used during fast-sync/state-sync) and `db-tool replay-on-archive` (used to detect state divergence/hard forks against the authenticated chain) will both report success instead of flagging a fork. This directly undermines the fork/divergence detection mechanism relied upon for state-integrity assurance on mainnet, matching the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "committed state that differs from the correct VM result" impact categories.

### Likelihood Explanation
The gap is triggered any time state-checkpoint computation diverges from committed data during a chunk-executor replay or an operator running `replay_on_archive`/debugger-based replay-verify — this is code that is invoked in normal state-sync and verification operations, not a privileged or adversarial-only path. The severity is contingent on there being an actual root-divergence bug elsewhere (e.g., in state-checkpoint SMT computation), but the detection mechanism meant to catch such bugs is proven, by direct code inspection, to skip checking exactly the fields that would reveal it. I could not fully verify whether `is_compute_trading_native_state_roots_enabled()` is currently active on mainnet (the TODO suggests it is guarded and not yet enabled), which affects whether `position_state_checkpoint_hash` divergence is presently reachable; however, `state_checkpoint_hash` and `hot_state_checkpoint_hash` are checked/produced unconditionally in `TransactionInfoV0`/`V1` today, so the missing validation of at least `state_checkpoint_hash` already applies to current mainnet replay/verify paths.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on both sides) against the freshly computed checkpoint hashes before returning `Ok(())`, so that chunk-executor replay and `replay_on_archive` correctly detect and reject any state-root divergence rather than silently ignoring it.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-logic gap rather than an on-chain exploit. The proof is structural: trace `ensure_match_transaction_info` ( [5](#0-4) ) call sites in `chunk_executor/mod.rs` and `replay_on_archive.rs`, and observe that none of the three checkpoint-hash fields defined on `TransactionInfoV0`/`V1` ( [6](#0-5) ) are read or compared anywhere in the function body, despite these being the fields that encode the authenticated state root.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
