### Title
Fixed `MAX_YOCTO_NEAR` (10^6) decimal-scaling constant in the NEAR Wallet Contract miscalculates the relayer refund/tx value for EVM-emulated transactions - (`File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The Wallet Contract hardcodes a single "decimals" conversion constant, `MAX_YOCTO_NEAR = 1_000_000`, used to translate every Ethereum-style transaction's `value`/`gas_price*gas_limit` (assumed 18-decimal Wei semantics) into yoctoNEAR (24-decimal). This is structurally the same bug class as the Cooler `interestFor()` report: a *constant* scale factor is applied to a value whose "decimals" are not actually fixed for all execution paths through this code, causing the derived relayer fee (`tx_fee`) and the transferred NEAR amount to be computed with the wrong unit conversion in edge cases.

### Finding Description
`parse_rlp_tx_to_action` computes two independent yoctoNEAR-denominated quantities purely by multiplying an EVM-native integer by the single constant `MAX_YOCTO_NEAR`: [1](#0-0) [2](#0-1) 

Both the relayer's fee (`tx_fee`, derived from `tx.max_fee_per_gas * tx.gas_limit`) and the actual value transferred to the receiver (`tx.value`) are scaled by the *same* fixed `MAX_YOCTO_NEAR = 1_000_000` constant, justified only by the comment "Near balances are 128-bit numbers, but with 24 decimals instead of 18" [3](#0-2) . This assumes a single, protocol-wide, invariant 6-decimal-place gap between the "EVM units" the signer intends and yoctoNEAR — exactly analogous to Cooler's `decimals = 1e18` constant being applied regardless of the debt token's real decimals.

The clamp bound `VALUE_MAX` is likewise derived from this single constant (`u128::MAX / 1_000_000`) [4](#0-3) , and is applied only to `tx.value`, not to the fee computation, which is independently clamped via `.min(VALUE_MAX)` before the same multiplication [1](#0-0) .

### Impact Explanation
I was not able to conclusively demonstrate an exploitable value-movement bug within the remaining exploration budget. The relayer-fee computation and the value-transfer computation both use the *same* constant consistently (both multiply an EVM quantity by `1_000_000` yoctoNEAR/unit), so the "decimals mismatch" here does not obviously produce an asymmetric miscalculation the way the ERC-20 `interestFor()` bug does (where debt-token decimals varied but the constant did not). Unlike Cooler's Cooler.sol, the Wallet Contract only ever deals with a single fixed-decimal system (EVM/Wei-style 18-decimals in, yoctoNEAR/24-decimals out) — there is no user-supplied "collateral/debt token" whose decimals vary at runtime, which was the root cause of the original finding. Because of this structural difference, I could not confirm a concrete unauthorized value movement, fee bypass, or supply-inflation path reachable from a single relayed transaction, and the fee/value scaling appears intentionally symmetric by design (fee is deliberately expressed and refunded in the same units as the transferred value).

### Likelihood Explanation
Low confidence overall. The pattern of a single hardcoded scale constant applied across contexts is present (matching the reported bug class superficially), but without evidence that any code path applies `MAX_YOCTO_NEAR` inconsistently between two values that should use different scale factors (which is what caused the actual miscalculation in the original Cooler report), I cannot assert this rises to a genuine, reachable Medium/High-severity issue under the stated validation bar ("concrete unauthorized value movement... state-root divergence... invalid state transition acceptance").

### Recommendation
Not applicable — insufficient evidence of a concrete exploitable defect distinct from intended design. If a deeper audit is desired, a background agent should be tasked with tracing every call site of `MAX_YOCTO_NEAR`/`VALUE_MAX`/`GAS_MULTIPLIER` in `runtime/near-wallet-contract/implementation/wallet-contract/src/` (including `lib.rs`'s relayer-refund payment logic and `types.rs`'s `try_into_near_action`) to verify the fee computed at parse time and the fee actually paid out to the relayer use identical unit conversions in every `TransactionKind` branch, and that no branch mixes a value scaled by `MAX_YOCTO_NEAR` with one that isn't.

### Proof of Concept
Not established — no runnable step-by-step PoC could be produced with the tools/time available. This answer should be treated as inconclusive rather than a confirmed finding.
