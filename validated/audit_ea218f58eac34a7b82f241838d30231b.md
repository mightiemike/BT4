### Title
Unbounded growth of `DelegatedResourceAccountIndex` via low-cost `FreezeBalanceContract`/`DelegateResourceContract` delegation enables RPC-API DoS - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
Any account can call `FreezeBalanceActuator` (or `DelegateResourceActuator`/`FreezeBalanceProcessor` for TVM) with `receiverAddress` set to an arbitrary victim account and only 1 TRX of frozen balance, forcing an entry to be appended to that victim's `DelegatedResourceAccountIndexCapsule.fromAccountsList` (or, under the "optimized" model, a new DB row under the victim's `V2_TO_PREFIX`/`FROM_PREFIX` key range). There is no cap on the number of distinct delegator addresses that can be recorded against a single victim, so an attacker using many disposable accounts can grow this list/keyspace without bound. This mirrors the reported `create_lock_for()` issue: an attacker abuses a "for another account" entry point with minimal value to force unbounded growth of a per-account data structure that the victim cannot unilaterally shrink.

### Finding Description
`FreezeBalanceActuator.execute()` calls `delegateResource()` whenever `receiverAddress` is set and `dynamicStore.supportDR()` is true [1](#0-0) . `validate()` only requires `frozenBalance >= 1 TRX` and `receiverAddress != ownerAddress`; it places no limit on how many distinct owners may delegate to the same receiver [2](#0-1) [3](#0-2) .

In the legacy (non-optimized) code path, `delegateResource()` loads the receiver's entire `DelegatedResourceAccountIndexCapsule`, appends the new owner address to its `fromAccountsList` if not already present, and rewrites the whole capsule back to the store: [4](#0-3) . Every additional attacker-controlled sender address grows this list by one entry, and the entire list is re-serialized on each write — an O(n) write cost per delegation with no accompanying fee (`calcFee()` returns 0) [5](#0-4) .

Even under the newer "delegate optimization" model, each delegation is stored as a separate DB row keyed by `V2_FROM_PREFIX`/`V2_TO_PREFIX` concatenated with the address pair [6](#0-5) . Reading the index for an account (`getIndex`/`getV2Index`, used by the `GetDelegatedResourceAccountIndex(V2)` RPCs) performs a `prefixQuery` over every row that shares the address prefix and sorts the entire result set in memory before returning it: [7](#0-6) . These are exposed directly to unauthenticated gRPC/HTTP clients: [8](#0-7)  and served by `Wallet.getDelegatedResourceAccountIndex(V2)` [9](#0-8) .

Because the minimum delegated amount is only 1 TRX (versus the 1-wei example in the report) and the frozen TRX is later fully recoverable via `unfreeze`, an attacker can cheaply and repeatedly grow a target account's delegation index using disposable sender addresses. Each subsequent `GetDelegatedResourceAccountIndex(V2)` query for that victim then costs O(n) DB scan + sort + serialization on the node, and the response payload itself grows unbounded, both of which are amplification vectors against a full node's RPC-API surface.

### Impact Explanation
This does not corrupt consensus state or funds, but it lets an attacker: (1) inflate a specific victim account's on-chain index data indefinitely at low, partially-recoverable cost, and (2) impose unbounded CPU/IO cost and unbounded response size on any full node serving `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` for that account, degrading RPC-API availability for that account (and consuming node resources) — a Medium-severity, RPC-API-facing DoS analogous to the reported array-filling attack.

### Likelihood Explanation
Reachable by any unauthenticated account broadcasting ordinary `FreezeBalanceContract`/`DelegateResourceContract` transactions; no privileged role or leaked key is required. Likelihood is somewhat lower than the original report because 1 TRX (not 1 wei) is locked per entry and the receiver-side `fromAccountsList`/index growth requires many distinct funded addresses, but this is still cheap and fully automatable at scale, and the locked TRX is recoverable after the freeze period, allowing repeated reuse of capital.

### Recommendation
- Enforce a maximum number of distinct delegator/delegatee entries per account in `DelegatedResourceAccountIndexCapsule`/`DelegatedResourceAccountIndexStore` (analogous to `MAX_DELEGATES` in the reported contract), rejecting new delegations to a receiver once its `fromAccountsList` (or its V2 prefix row-count) exceeds the cap.
- Add pagination/limits to `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` so a single query cannot force an unbounded `prefixQuery` + sort + serialization on the node.
- Consider raising the effective cost of delegating to an account not controlled by the sender (e.g., a per-delegation fee) so index growth cannot be driven at near-zero marginal cost.

### Proof of Concept
1. Attacker creates N disposable accounts, each funded with the network's minimum 1 TRX.
2. For each disposable account, broadcast `FreezeBalanceContract` with `frozenBalance = 1 TRX`, `resource = BANDWIDTH` (or `ENERGY`), and `receiverAddress = victim`, which is accepted by `FreezeBalanceActuator.validate()`/`execute()` and appends the disposable owner to the victim's delegation index [4](#0-3) .
3. Repeat for arbitrarily large N (bounded only by attacker's willingness to fund N disposable accounts, which is recoverable via `unfreeze` after the freeze period).
4. Any subsequent `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` RPC call for `victim` now performs an O(N) prefix scan/sort and returns an O(N)-sized response, degrading that RPC path for all callers.

  public DelegatedResourceAccountIndexCapsule getIndex(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = get(address);
    if (indexCapsule != null) {
      return indexCapsule;
    }
    return getWithPrefix(FROM_PREFIX, TO_PREFIX, address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
