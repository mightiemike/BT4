### Title
`ValidateMultiSign` precompile counts a single signer's weight multiple times when the same key produces distinct valid signature bytes over the same hash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompiled contract sums up the weights of the addresses recovered from a caller-supplied array of raw signatures, exactly mirroring the Oracle-report pattern of summing voting power per vote entry without ensuring each *validator* (here, each key/address) is counted only once. The dedup logic keys on the exact `(recoveredAddr, signatureBytes)` pair rather than on `recoveredAddr` alone, so if the same private key produces two different but individually valid 65-byte signatures over the identical hash (trivial via ECDSA's nonce/malleability), both entries pass and their weights are both added to `totalWeight`.

### Finding Description
`ValidateMultiSign.execute` recovers an address for every signature in the caller-supplied array and accumulates `Permission` key weight for each recovered address: [1](#0-0) 

The relevant dedup check is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
This only `continue`s (skips adding weight) when the *exact same signature bytes* for that address have already been seen. If the address has been seen before but with **different signature bytes** (still recovering to the same address over the same hash), the code falls through and adds the weight again — it never checks "have I already counted this address's weight," only "have I already seen this exact signature blob." Because ECDSA signing is non-deterministic (or trivially malleable: for any valid `(r, s, v)` the pair `(r, n-s, 1-v)` is also a valid signature of the same hash), a single private key can trivially produce multiple syntactically distinct 65-byte signatures over the same `hash`, each recovering to the same address, and each adds `weight` again to `totalWeight`.

This is the exact analog of the Oracle vote-extension bug: `sumVP += power.Int64()` there summed voter power per vote entry without checking `vote.Validator` uniqueness; here `totalWeight += weight` sums key weight per signature entry without checking address uniqueness, only checking exact byte-for-byte signature duplication.

For comparison, the on-chain permission/multisig path (`TransactionCapsule.checkWeight`, used for `broadcastTransaction`, `AccountPermissionUpdateActuator`, etc.) correctly dedups by *recovered address* via `addMap.containsKey(base64)` and throws `"has signed twice!"`: [2](#0-1) 
The TVM precompile `ValidateMultiSign` (and its energy-metered sibling `BatchValidateSign`, which is unaffected since it checks explicit addresses per signature rather than summing weight) diverges from this correct address-based dedup pattern and instead uses signature-byte-based dedup, reintroducing the duplicate-counting flaw that the on-chain transaction path already guards against.

### Impact Explanation
Any smart contract deployed on TRON can call the `validatemultisign(address,uint256,bytes32,bytes[])` precompile (invoked via `PrecompiledContracts`, instantiated as `validateMultiSign` at [3](#0-2)  and dispatched from the TVM opcode handling) to check whether a set of signatures satisfies an account's Active/Owner permission threshold. Contracts commonly use this precompile as an on-chain multisig gate for high-value operations (custodial wallets, DAO/multisig treasuries, bridges, escrow). If a single key holder — whose weight alone is below the required threshold — can submit two or more distinct valid signatures over the same hash, the precompile will incorrectly report the permission as satisfied (`DataWord.ONE`), letting that single signer bypass the multi-party approval requirement enforced by the calling contract. This is a direct authorization bypass / accounting corruption for any downstream contract logic gated on this precompile's result, fully analogous in class and mechanism to the Oracle vote-duplication issue (single signer overriding a quorum requirement).

### Likelihood Explanation
Likelihood is high for any deployed contract relying on `ValidateMultiSign` for permission gating: the attacker only needs their own private key (already a signer with nonzero permission weight below the account's threshold) and standard ECDSA signing/malleability to generate two distinct valid signatures over the identical hash — no cooperation from other key holders and no privileged access is required. The call is fully reachable from any address via a normal `TriggerSmartContract` transaction into a contract that calls this precompile.

### Recommendation
Change the dedup key in `ValidateMultiSign.execute` from `(recoveredAddr, signatureBytes)` to `recoveredAddr` alone (mirroring `TransactionCapsule.checkWeight`'s `addMap`/`has signed twice` logic): once an address has contributed weight, skip it (or reject the call) regardless of whether the newly-seen signature bytes for that address are byte-identical to a previously seen one.

```java
Set<ByteString> countedAddresses = new HashSet<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  ByteString addrKey = ByteString.copyFrom(recoveredAddr);
  if (!countedAddresses.add(addrKey)) {
    continue; // already counted this signer's weight
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) {
    return Pair.of(true, DATA_FALSE);
  }
  totalWeight += weight;
}
```

### Proof of Concept
1. Deploy an account with an `Active` permission containing two keys, `key1` (weight 1) and `key2` (weight 1), threshold = 2 (as in `ValidateMultiSignContractTest.testDifferentCase`, see [4](#0-3) ).
2. Attacker controls only `key1`.
3. Compute `hash = sha256(address || permissionId || data)` as done in the precompile ( [5](#0-4) ).
4. Sign `hash` twice with `key1`, producing two distinct signature byte strings `sig1a` and `sig1b` (e.g., via malleable transformation `s' = n - s`, `v' = 1 - v`, or simply two independent nondeterministic ECDSA signing calls if the signer uses randomized `k`).
5. Call `validatemultisign(address, permissionId, data, [sig1a, sig1b])`.
6. In `ValidateMultiSign.execute`, both signatures recover to `key1`'s address; the first adds weight 1, the second — despite recovering to the same address — is not byte-identical to the first, so `matrixContains(executedSignList, sign)` returns false, `continue` is skipped, and weight 1 is added again, making `totalWeight == 2 >= threshold (2)`. The precompile returns `dataOne()` (success), even though only one of the two required key holders actually signed.
