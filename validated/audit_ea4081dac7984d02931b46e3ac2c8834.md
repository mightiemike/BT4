### Title
Attacker-crafted pubkeys deterministically collide into a single AccountsIndex bin, defeating anti-grinding randomization and causing disproportionate serialized index/clean cost - ([File: accounts-db/src/pubkey_bins.rs])

### Summary
`PubkeyBinCalculatorBuilder::with_bins` picks a random bit offset to read 4 bytes from a pubkey for bin assignment, intending to prevent grinding, but the entire possible read window (bytes 2–29) is a fixed, attacker-visible sub-range of the pubkey. An attacker who fixes those 28 bytes and varies only the untouched outer bytes (0–1 and 30–31) can guarantee that thousands of distinct, self-funded accounts land in exactly the same `AccountsIndex` bin regardless of the runtime-random offset, causing serialized lock contention and unbalanced parallel `clean_accounts` scans.

### Finding Description
`PubkeyBinCalculator::bin_from_pubkey` (`accounts-db/src/pubkey_bins.rs:58-71`) reads 4 bytes from the pubkey starting at `byte_offset` (derived from a randomly chosen `offset`), and masks/shifts to get the bin index. The offset is chosen once at builder construction: [1](#0-0) 

with `SKIP = 16` bits (2 bytes) skipped at both the beginning and end of the pubkey "to skip the beginning and end of the pubkey range, which is the most common to grind" (comment at line 132). Given `MAX_OFFSET = 231`, the resulting `byte_offset` ranges only from 2 to 26, and since 4 bytes are read, the union of all possible read windows across every possible random offset is exactly bytes `[2, 30)` of the pubkey — i.e., a fixed 28-byte span that never varies no matter which offset the validator randomly picked at startup.

This means an attacker does **not** need to guess or leak the random offset at all. By fixing bytes `[2, 30)` to a constant pattern across many generated pubkeys and varying only the untouched bytes (`[0,1]` and `[30,31]`, giving ~2^32 combinations — more than enough for thousands of unique addresses), every one of these pubkeys is guaranteed to produce the *same* `read_bytes()` value and therefore the *same* bin, under any possible randomized offset the validator could have chosen. No private key or curve validity is required for these pubkeys: Solana account creation via `SystemInstruction::Transfer`/`CreateAccount` to an arbitrary destination pubkey does not require a signature from the destination, so the attacker fully controls the byte pattern of the destination address.

This bin index (`AccountsIndex::get_bin`, `accounts-db/src/accounts_index.rs:662-664`) determines:
- Which `InMemAccountsIndex`'s `RwLock<HashMap<Pubkey, AccountMapEntry>>` (`map_internal`) is locked for every `upsert`/`get`/`remove` touching those accounts.
- Which single on-disk `Bucket` file (`storage.disk.get_bucket_from_index(bin)`) all of the colluding accounts' index entries are stored in.
- Which `candidates[bin]` `RwLock<HashMap<Pubkey, CleaningInfo>>` bucket (`accounts-db/src/accounts_db.rs:1617-1629`, and the parallel scan at `accounts-db/src/accounts_db.rs:1916-2013`) receives all of the colluding pubkeys during `clean_accounts`.

With `BINS_DEFAULT = 8192` (`accounts-db/src/accounts_index.rs:49`), the `do_clean_scan` closure runs `candidates.par_iter().for_each(...)` across all 8192 bins on the background thread pool. If an attacker concentrates N accounts into one bin, 8191 bins finish almost instantly while a single thread must serially process the entire N-account bin under its own `RwLock` write lock, since `candidates_bin.retain(...)` (line 1927) holds one write lock per bin for the whole scan of that bin. This turns an operation that should be spread ~evenly across the background thread pool into one dominated by a single serialized unit of work, and additionally concentrates all of these accounts' index entries into one on-disk `Bucket` (causing more frequent resizes/growth and open-addressing probe overhead for that single file, per `bucket_map/src/bucket_map.rs:176-200` and `bucket_map/src/bucket.rs`).

No existing guard mitigates this: the randomization in `PubkeyBinCalculatorBuilder::with_bins` is intended exactly to stop this kind of grinding, but its skip window is too large relative to the read window size, so the entire possible read range is always fully attacker-controllable.

### Impact Explanation
This matches the "resource-exhaustion / disproportionate background-thread cost" bounty category described in the question. The attacker pays only ordinary account-creation/transfer fees and rent, but can force a specific `AccountsIndex` bin's lock and its associated on-disk bucket file to carry a disproportionate share of index maintenance work relative to other bins, degrading the parallelism of `clean_accounts`/`shrink_candidate_slots` and creating a lock-contention hotspot for any operation touching that bin (index `upsert`/`get`, scan, and background flush/age operations in `InMemAccountsIndex`). This is a constant-factor (bounded by thread pool size) but real and directly reproducible degradation of background index maintenance, not proportional to the (low) fees paid to create the colliding accounts.

### Likelihood Explanation
Fully feasible for an unprivileged attacker: they only need to send `SystemInstruction::Transfer` (or fund via `CreateAccount`) to self-chosen destination pubkeys with a fixed 28-byte middle pattern, which requires no signature from the destination and no special privileges. Generating thousands of such addresses with ~32 bits of free entropy is trivial and repeatable on any cluster, and the collision is deterministic regardless of the validator's randomly chosen bin-calculator offset (no timing/side-channel needed to learn the secret offset).

### Recommendation
Widen the random read window so it can span the entire pubkey (or use a keyed/full-pubkey hash, e.g., a random-seeded hash similar to what `Bucket::bucket_index_ix` already does with `ahash::RandomState::with_seeds(...).hash_one(key)`, applied over the whole 32-byte pubkey) rather than reading a fixed 4-byte slice from a constrained offset range. This removes the fixed 28-byte "always-read" region that lets an attacker guarantee collisions independent of the random offset.

### Proof of Concept
Rust unit test to add near `accounts-db/src/pubkey_bins.rs` tests module, demonstrating guaranteed collision across all valid offsets:
```rust
#[test]
fn test_attacker_can_force_bin_collision_regardless_of_random_offset() {
    // Fix bytes [2,30) — the union of every possible read window for any offset —
    // and vary only bytes [0,1] and [30,31].
    let fixed_middle = [0x42u8; 28]; // bytes 2..30
    let make_pubkey = |i: u32| {
        let mut bytes = [0u8; 32];
        bytes[0..2].copy_from_slice(&(i as u16).to_le_bytes());
        bytes[2..30].copy_from_slice(&fixed_middle);
        bytes[30..32].copy_from_slice(&((i >> 16) as u16).to_le_bytes());
        Pubkey::new_from_array(bytes)
    };

    let num_bins = NonZeroUsize::new(8192).unwrap();
    // Try every possible offset the validator's randomized builder could pick.
    for offset in 16..=(231 - 16) {
        let bin_calculator = PubkeyBinCalculatorBuilder::with_bins_and_offset(num_bins, offset);
        let first_bin = bin_calculator.bin_from_pubkey(&make_pubkey(0));
        for i in 1..10_000u32 {
            let pk = make_pubkey(i);
            assert_eq!(
                bin_calculator.bin_from_pubkey(&pk),
                first_bin,
                "crafted pubkey {i} did not collide into the same bin at offset {offset}"
            );
        }
    }
}
```
Expected: the assertion passes for every possible randomized offset, proving the attacker can force 10,000 distinct, unprivileged-fundable pubkeys into a single bin without needing to know the validator's secret random offset — confirming that `clean_accounts`'s per-bin parallel scan (`accounts-db/src/accounts_db.rs:1916-2013`) and per-bin index locks (`accounts-db/src/accounts_index.rs:662-664`) will serialize disproportionate work onto a single bin/thread.
