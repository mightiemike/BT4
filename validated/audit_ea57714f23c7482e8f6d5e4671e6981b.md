## Title
Replay-verify accepts a corrupted/diverged state root because `TransactionOutput::ensure_match_transaction_info` never checks the state checkpoint hashes - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay/verification tooling to confirm that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` that was persisted/archived for a version. It checks status, gas used, write-set hash, and event root hash, but it never compares the state checkpoint hash (nor the hot-state or `position_state_checkpoint_hash`) between the locally computed state and the expected/archived one. The code itself documents this gap as an open TODO, but the check is nonetheless treated as a pass/fail integrity gate by db-tool's `replay-verify` command.

### Finding Description
`ensure_match_transaction_info` validates the transaction status, gas usage, `write_set` hash against `txn_info.state_change_hash()`, and event root hash against `txn_info.event_root_hash()`, then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()` (or the V1 `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) to anything computed from the freshly executed state: [1](#0-0) 

The comment directly above the `Ok(())` acknowledges the gap: [2](#0-1) 

This function is the sole per-transaction correctness oracle used by the `replay-verify` (`replay_on_archive`) db-tool, which re-executes archived transactions and compares the result to the expected, previously-committed `TransactionInfo`: [3](#0-2) 

Because the state (Sparse Merkle Tree) checkpoint root hash is the actual authenticated commitment to the entire post-transaction world state — a value that is *not* derivable from the write-set hash alone (the write set contains only the delta, while the checkpoint hash commits to the full resulting global state tree) — omitting it from the comparator means replay-verify can declare success even when the locally re-executed global state diverges from the state that was actually committed/archived, as long as the write set and events for the individual transaction still match.

### Impact Explanation
Replay-verify exists specifically to catch divergence between archived/committed ledger state and independently re-executed state (a "hard-fork-only divergence" class issue per the state-integrity gate). Because the state (and hot-state / position-state) checkpoint hash is never checked, a scenario where an archive's state tree was corrupted, tampered with, or diverged from the true VM result at a checkpoint boundary would not be detected by `replay-verify`, even though the write set of the offending or subsequent transactions is unaffected. This directly matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Committed state that differs from the correct VM result" impact categories: an operator relying on `replay-verify` to certify the integrity of a backup/archive database would get a false-positive "all good" result while the underlying state commitment is wrong.

### Likelihood Explanation
This is not a hypothetical: the code path is exercised directly by the `replay_on_archive` tool, which is the primary tool for auditing archived/backup ledger data. The gap is deterministic (always present, not a race condition) and is explicitly flagged as unresolved by the developers' own TODO comment, confirming the code's current behavior is a known but unremediated correctness gap rather than only an unlikely edge case.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash()` (and, when the corresponding features are enabled, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the checkpoint hash computed from actual post-execution state, failing verification on mismatch just as it does today for the write-set and event root hashes.

### Proof of Concept
1. Take an archived/backup Aptos DB where the state-checkpoint hash stored in a `TransactionInfo` at some checkpoint version has been corrupted (e.g., tampered with, or produced by a buggy/forked node) while the per-transaction write set and events remain byte-identical.
2. Run `db-tool replay-on-archive` for a range spanning that version, as done in `Verifier::execute_and_verify` (`storage/db-tool/src/replay_on_archive.rs:349-415`), which calls `ensure_match_transaction_info` for each executed transaction.
3. Observe that `ensure_match_transaction_info` returns `Ok(())` because it only checks `status`, `gas_used`, `write_set_hash`, and `event_root_hash` (`types/src/transaction/mod.rs:2139-2204`) — the corrupted `state_checkpoint_hash` is never compared, so replay-verify reports success despite the state root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
