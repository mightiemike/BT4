### Title
Meta-Transaction Deposit Refund Misdirection Allows Delegate Sender to Drain Relayer Deposits - (`runtime/runtime/src/actions.rs`)

### Summary

`apply_delegate_action` sets the spawned inner receipt's `predecessor_id` to `delegate_action.sender_id()` (Alice, the delegate signer). When that inner receipt fails on the receiver's shard, the deposit refund is sent to Alice — not to the relayer who actually paid the deposit. Any user who can submit a `DelegateAction` to a relayer can deliberately cause the inner receipt to fail and receive the full attached deposit at the relayer's expense.

### Finding Description

In `apply_delegate_action` (`runtime/runtime/src/actions.rs`), the new receipt spawned from a `DelegateAction` is constructed as:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),          // ← Alice
    receiver_id: delegate_action.receiver_id().clone(),
    ...
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // ← Relayer
        ...
    }),
});
``` [1](#0-0) 

`sender_id` here is `delegate_action.sender_id()` — Alice — enforced by the check at line 439: [2](#0-1) 

When this inner receipt fails on Bob's shard, `refund_unspent_gas_and_deposits` issues a deposit-refund receipt via:

```rust
result.new_receipts.push(Receipt::new_balance_refund(
    receipt.balance_refund_receiver(),
    deposit_refund,
));
``` [3](#0-2) 

`balance_refund_receiver()` returns `refund_to.as_ref().unwrap_or_else(|| self.predecessor_id())`: [4](#0-3) 

Because the inner receipt carries no `refund_to` override (it is a plain `ReceiptEnum::Action`, not `ActionV2`), the refund receiver resolves to `predecessor_id` = **Alice**. The relayer, who is only the `signer_id`, receives nothing.

The relayer paid the deposit when the outer transaction was converted to a receipt on the relayer's shard. The deposit is deducted from the relayer's balance at that point. Alice never contributed any funds.

The nearcore documentation explicitly acknowledges this asymmetry:

> "But what if the transaction fails execution on Bob's shard? At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a **financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard**." [5](#0-4) 

The protocol provides no mechanism for the relayer to redirect the deposit refund to itself before submitting the meta-transaction. The `ActionReceiptV2.refund_to` field exists for contracts to redirect refunds via `promise_refund_to`, but the relayer cannot set it on the inner receipt created by `apply_delegate_action` — that receipt is constructed entirely from the `DelegateAction` payload signed by Alice.

### Impact Explanation

**Loss of funds for relayers.** Alice constructs a `DelegateAction` with a large `deposit` attached to a `FunctionCall` that she knows will fail (e.g., targeting a non-existent method, a contract that always panics, or a contract whose state Alice can manipulate to cause failure). The relayer pays the deposit. The call fails. Alice receives the full deposit refund. The relayer's balance is permanently reduced by the deposit amount with no recourse.

The attack is repeatable: Alice can submit many such `DelegateAction`s to the same relayer, draining it incrementally. The relayer cannot distinguish a legitimately-failing call from a deliberately-failing one before submission.

### Likelihood Explanation

Any unprivileged NEAR account can create and sign a `DelegateAction`. The only prerequisite is finding a relayer willing to submit it. Public relayer services (e.g., those supporting gasless transactions for dApps) are the primary target. Alice does not need any special permissions, staked tokens, or validator access. The attack requires only a valid NEAR account and knowledge of a function call that will fail.

### Recommendation

The deposit refund for a meta-transaction inner receipt should be directed to the relayer (the `signer_id` of the outer receipt), not to Alice (the `predecessor_id` of the inner receipt). Concretely, `apply_delegate_action` should construct the inner receipt as a `ReceiptEnum::ActionV2` with `refund_to: Some(action_receipt.signer_id().clone())`, so that `balance_refund_receiver()` returns the relayer's account rather than Alice's. [6](#0-5) 

Alternatively, the protocol could require relayers to explicitly opt in to deposit-bearing `DelegateAction`s only after verifying the call will succeed, but this is an off-chain mitigation that does not fix the on-chain invariant.

### Proof of Concept

1. Alice creates a `DelegateAction` with `receiver_id = bob.near`, inner action `FunctionCall { method_name: "always_panic", deposit: 100_NEAR, ... }`, signed with her full-access key.
2. Alice submits the `SignedDelegateAction` to a public relayer.
3. Relayer wraps it in a transaction (`signer = relayer`, `receiver = alice`), paying 100 NEAR deposit from its own balance.
4. On Alice's shard, `apply_delegate_action` spawns inner receipt: `predecessor_id = alice`, `signer_id = relayer`.
5. On Bob's shard, `always_panic()` panics; `refund_unspent_gas_and_deposits` issues `Receipt::new_balance_refund(&alice, 100_NEAR)`.
6. Alice's balance increases by 100 NEAR; relayer's balance is permanently reduced by 100 NEAR.

The attack is confirmed by the runtime's own comment at line 472–475: [7](#0-6) 

> "Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas. If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction."
