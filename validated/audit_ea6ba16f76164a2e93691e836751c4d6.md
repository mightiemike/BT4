### Title
DeleteAccount with a non-existent (but syntactically valid) `beneficiary_id` permanently burns the account's balance instead of transferring it - (File: `runtime/runtime/src/actions.rs`)

### Summary
The reported bug is a missing destination-address validity check in a withdraw function that lets a user's collateral become permanently frozen because the contract never verifies that `receiver` is a usable address before crediting it. The same bug class exists in nearcore's `DeleteAccount` action: the `beneficiary_id` supplied by the user is validated only for syntactic correctness, never for whether the account actually exists. If it doesn't, the balance that should have been transferred is instead permanently burnt.

### Finding Description
When a `DeleteAccount` action executes, `action_delete_account` pushes a balance-transfer receipt to the specified beneficiary without checking whether that account exists: [1](#0-0) 

The only validation performed on `beneficiary_id` anywhere in the action-validation path is a syntax check (that it parses as a valid `AccountId`), not an existence check: [2](#0-1) 

The resulting receipt is a **refund** (`Receipt::new_balance_refund`, `predecessor_id == "system"`). When this refund receipt is later applied to the (non-existent) beneficiary account, `check_account_existence` rejects the embedded `Transfer` action because refunds are explicitly barred from implicitly creating an account: [3](#0-2) 

Because the receipt fails and it is a system/refund receipt, the runtime does not retry, bounce, or re-refund it — refunds are terminal. Per the documented refund semantics and the exec-loop implementation, a failed refund's deposit is simply burnt: [4](#0-3) [5](#0-4) 

This exact behavior is confirmed by an existing unit test, which asserts that a refund to a missing account fails with `AccountDoesNotExist` and does **not** create the account — i.e., the tokens are lost, not delivered: [6](#0-5) 

### Impact Explanation
Any unprivileged transaction signer who submits a `DeleteAccount` action (directly, or as the inner action of a meta-transaction/delegate action, per `runtime/runtime/src/action_validation.rs` delegate handling) with a `beneficiary_id` that is a syntactically valid `AccountId` which has never been created (e.g., a plausible-looking but unregistered named account) causes their entire remaining account balance to be irreversibly burnt instead of transferred. This is a concrete, protocol-level permanent loss of funds triggered purely by a missing existence check on a user-supplied destination account, mirroring the original report's "receiver validity check" bug class (frozen/lost collateral due to an unchecked destination). The loss can also be triggered against a relayer-sponsored meta-transaction sender, and is deterministic and reproducible by any signer, satisfying the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
High likelihood: the only actions required are (1) constructing a `DeleteAccountAction` with `beneficiary_id` set to any never-created, validly-formatted `AccountId`, and (2) signing/submitting it as an ordinary transaction. No special privileges, timing, or races are needed; validation at both the action-validation stage (`validate_delete_action`) and the execution stage (`action_delete_account`) never checks account existence, only string validity.

### Recommendation
Before enqueuing the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or is a supported implicit-account form) and reject the `DeleteAccount` action (returning an execution/validation error) if it does not, rather than allowing the funds to move into an unreachable/burning refund receipt. Alternatively, route delete-account beneficiary transfers through a non-refund receipt path so a missing beneficiary produces a bounce/refund back to the deleting account instead of an unrecoverable burn.

### Proof of Concept
1. Create account `victim.near` with a nonzero balance and a full-access key.
2. Submit a transaction from `victim.near` to itself containing a single `DeleteAccount` action with `beneficiary_id = "totally-unused-name.near"` (a syntactically valid, never-created named account).
3. `action_delete_account` (`runtime/runtime/src/actions.rs:380-386`) removes `victim.near` and enqueues `Receipt::new_balance_refund("totally-unused-name.near", account_balance)`.
4. When this refund receipt is processed, `check_account_existence`/`implicit_creation_allowed` reject the `Transfer` because refunds cannot create accounts (`runtime/runtime/src/actions.rs:928-947`), producing `ActionErrorKind::AccountDoesNotExist`.
5. Because the receipt's predecessor is `"system"` (a refund), the failed deposit is added to `other_burnt_amount` (`runtime/runtime/src/lib.rs:1047-1055`) instead of being returned anywhere — `victim.near`'s balance is permanently gone. This exact flow (fail + no account created) is already exercised by `refund_may_not_create_universal_account` in `runtime/runtime/src/tests/apply.rs:6870-6926`, which can be adapted to a plain named `beneficiary_id` to demonstrate the fund loss.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

    /// free, so they must not create an account, a `0u` one included.

    fn refund_may_not_create_universal_account() {
        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],
            Balance::from_near(100),
            Balance::ZERO,
            Gas::from_teragas(1000),
        );

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.
        let [outcome] = &result.outcomes[..] else {
            panic!("the refund receipt must produce exactly one outcome, got {:?}", result.outcomes)
        };
        assert_matches!(

            ExecutionStatus::Failure(TxExecutionError::ActionError(err))
                if matches!(err.kind, ActionErrorKind::AccountDoesNotExist { .. }),
            "a refund to a missing `0u` id must fail with AccountDoesNotExist",
        );
        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "a refund must not bring a `0u` account into existence",
        );
    }
