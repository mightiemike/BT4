### Title
`replay-verify` / debugger transaction-output verification silently skips state-checkpoint root comparison, allowing divergent committed state to pass as "verified" — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by `db-tool replay-on-archive`, `aptos-debugger`, and the CLI simulation/replay tooling) validates a locally re-executed `TransactionOutput` against the `TransactionInfo` recorded/authenticated on the ledger by checking status, gas, write-set hash, and event-root hash — but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The code contains its own acknowledgement of this: [1](#0-0) 

This means the one authenticated field that actually proves "the committed state root after this transaction is X" is never re-derived and compared during replay verification.

### Finding Description
`TransactionInfo` is the accumulator leaf that binds a transaction's execution result — including `state_checkpoint_hash` (and, on `V1`, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) — into the signed ledger. These checkpoint hashes are exactly the values computed by `DoStateCheckpoint::run` from the authoritative `LedgerStateSummary`/JMT root during normal execution: [2](#0-1) , and are wired into the final `TransactionInfo` at commit time in `assemble_transaction_infos`: [3](#0-2) .

`TransactionOutput::ensure_match_transaction_info` is the function tools (`replay_on_archive`, `aptos-debugger`, CLI `commands.rs`) call to confirm that a freshly re-executed transaction reproduces the transaction info stored/authenticated in the archive: [4](#0-3) [5](#0-4) 

It checks `status`, `gas_used`, write-set hash (`state_change_hash`), and event root hash. It never recomputes or compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` against the values in `txn_info`. Callers are invoked at: [6](#0-5)  and `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`.

Because the write set hash check (`state_change_hash`) only proves the *set of write operations* hashes correctly — it says nothing about the resulting Merkle/JMT root actually recorded and signed by validators — a state root divergence (e.g., a state-merkle commit bug, a corrupted persisted snapshot, an incorrect checkpoint-boundary computation, or a bug in `state_summary.update`) can produce an execution that "matches" per this function while the actual committed JMT root on-chain differs from what local replay/restore would derive.

### Impact Explanation
Replay-verification and debugger-based auditing tools are one of the primary integrity backstops used to detect state-commitment corruption in aptos-core (including in the `trading-native` position-state-root path referenced directly by the code comment). If these tools report success despite a genuine state-checkpoint root divergence, operators/validators lose the ability to detect that committed ledger state differs from the correct VM/execution result — directly matching the "Committed state that differs from the correct VM result" and "wrong ... state proof accepted as valid" impacts in scope. This is a proof-integrity gap in a tool explicitly meant to catch exactly this class of bug, and the code's own comment states this concern applies specifically before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, i.e., it is a known, currently-live gap rather than a hypothetical one.

### Likelihood Explanation
This is not an attacker-triggered exploit in the traditional sense — it requires an underlying state-commitment bug elsewhere (e.g., in `do_state_checkpoint.rs`'s summary update logic, JMT restore, or sharded state merklization) to actually exist first. However, given the explicit maintainers' TODO acknowledging this exact scenario ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"), the gap is real, present in code today, and would mask any independent state-integrity bug rather than surface it — making the overall detection/response likelihood for any future or existing corruption bug significantly lower.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash` (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` when present) against the locally-derived checkpoint roots, failing loudly on mismatch, consistent with how `write_set_hash` and `event_root_hash` are already validated in the same function.

### Proof of Concept
Not independently exploitable as a standalone PoC without a second, separate state-commitment bug to trigger the divergence; the proof here is the code-level gap itself:
1. `do_state_checkpoint.rs` computes `state_checkpoint_hash` from `state_summary.update(...)` [2](#0-1) , and this value is embedded into the signed `TransactionInfo`.
2. Any code path that produces a `TransactionOutput` whose materialized write set hashes identically (or whose state changes are otherwise unaffected by a downstream root-computation defect) but whose downstream checkpoint root differs, would still pass `ensure_match_transaction_info` because only `write_set_hash`/`event_root_hash`/`status`/`gas_used` are asserted: [7](#0-6) .
3. Tools relying on this function (`replay_on_archive.rs`) would report the transaction as "verified" despite the state-checkpoint root mismatch, as flagged directly by the maintainers' own comment.

Because I could not locally construct an independent unprivileged trigger that produces a genuine checkpoint-hash divergence purely within the scope explored (it depends on a separate root-computation defect), confidence in "Critical" severity is bounded — the missing-check itself is proven and acknowledged in-code, but a concrete standalone unprivileged exploit chain producing the divergence was not found within this investigation.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
