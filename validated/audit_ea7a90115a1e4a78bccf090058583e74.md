### Title
Unchecked slice indexing on attacker-supplied `bytecode_segment_lengths` causes out-of-bounds panic in `create_bytecode_segment_structure_inner` - ([File: crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs])

### Summary
`create_bytecode_segment_structure_inner` slices a compiled class's `bytecode: &[Felt]` using an offset/length pair taken directly from the `NestedIntList` `bytecode_segment_lengths` field of a `CasmContractClass`, without first checking that the declared segment length stays within the bounds of the actual bytecode array. This mirrors the CVE-2020-1893 bug class: a boundary check that should happen *before* reading/indexing into a buffer is instead performed only *after* the read, at which point an out-of-bounds access has already occurred.

### Finding Description
`create_bytecode_segment_structure_inner` at [1](#0-0)  computes `segment_end = bytecode_offset + length` and then directly executes `bytecode[bytecode_offset..segment_end].to_vec()` for every `NestedIntList::Leaf(length)` in the tree, with no check that `segment_end <= bytecode.len()`.

The caller, `create_bytecode_segment_structure`, only validates the *total* summed length against `bytecode.len()` *after* the recursive call has already returned (or panicked): [2](#0-1) . Because Rust slice indexing panics immediately on an out-of-range range, any single leaf whose `length` value causes `segment_end` to exceed `bytecode.len()` triggers an unrecoverable panic before the higher-level sanity check ever executes — exactly the "check after read" defect pattern in the CVE.

`bytecode_segment_lengths` is untrusted data associated with a declared class (`CasmContractClass`), and this function is invoked during Starknet OS re-execution when building bytecode segment structures for compiled classes: `load_classes_and_create_bytecode_segment_structures` calls `create_bytecode_segment_structure(..., compiled_class.get_bytecode_segment_lengths())` for every compiled class known to the hint processor [3](#0-2) . `get_bytecode_segment_lengths` falls back to whatever `bytecode_segment_lengths` was carried on the `CasmContractClass` if present [4](#0-3) .

### Impact Explanation
A panic inside the Starknet OS re-execution / hint-processing path (invoked from Cairo VM hint execution while running the OS program) is a crash, not a memory-disclosure bug in this Rust codebase (Rust slice bounds panics abort safely rather than reading adjacent heap memory as in the HHVM C++ case). The class-hash mismatch check that exists (`total_len != bytecode.len()`) shows the intent was to reject malformed segment-length metadata gracefully, but the unchecked slice access can short-circuit that intended graceful error path with a hard panic. If reachable with attacker-controlled `bytecode_segment_lengths` before the class's `compiled_class_hash` is otherwise validated against the network-computed hash, this can crash the OS/re-execution process handling a specific declared class, causing a localized denial of service for whichever component processes that class (fits the "network unable to confirm new transactions" bucket only if it can reach block-building or OS proving on the hot path for an as-yet-unvalidated class).

### Likelihood Explanation
I could not fully verify, within the given search budget, whether `bytecode_segment_lengths` is cross-checked against the actual bytecode length *before* reaching this function anywhere earlier in the declare/compile pipeline (e.g., in blockifier's `NestedFeltCounts::new`/`casm_hash_estimation.rs`, or in gateway-side Sierra→CASM compilation validation). If such validation exists and runs strictly before this code path, likelihood is low since malformed compiled classes would be rejected earlier. I was not able to confirm this with certainty due to running out of tool iterations — this should be verified directly in the code (`crates/blockifier/src/execution/casm_hash_estimation.rs`, `NestedFeltCounts::new`, and the gateway class-compilation validation flow) before treating this as confirmed-exploitable.

### Recommendation
Add an explicit bounds check in `create_bytecode_segment_structure_inner` before slicing: if `bytecode_offset + length > bytecode.len()`, return a `Result`/`OsHintError::AssertionFailed` immediately instead of panicking, and propagate that error through `create_bytecode_segment_structure_inner`'s signature (currently `-> (BytecodeSegmentNode, usize)`, not a `Result`). Also verify at the earliest possible point (Sierra→CASM compilation / class hash computation in the gateway) that submitted `bytecode_segment_lengths` never describes segments exceeding the bytecode array size.

### Proof of Concept
Not independently confirmed end-to-end (would require constructing a `CasmContractClass` with a crafted `bytecode_segment_lengths: Some(NestedIntList::Leaf(N))` where `N > bytecode.len()`, then driving it through the exact caller that reaches `create_bytecode_segment_structure` without an earlier bounds check, and confirming that reaches Starknet OS re-execution/hint processing on an unprivileged declare path). Given the inability to fully trace the earlier validation stages in this session, I flag this as a **candidate** analog rather than a fully proven one.

pub(crate) fn create_bytecode_segment_structure(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
) -> Result<BytecodeSegmentNode, OsHintError> {
    let (structure, total_len) =
        create_bytecode_segment_structure_inner(bytecode, bytecode_segment_lengths, 0);
    // Sanity checks.
    if total_len != bytecode.len() {
        return Err(OsHintError::AssertionFailed {
            message: format!(
                "Invalid length bytecode segment structure: {}. Bytecode length: {}.",
                total_len,
                bytecode.len()
            ),
        });
    }

    Ok(structure)
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
