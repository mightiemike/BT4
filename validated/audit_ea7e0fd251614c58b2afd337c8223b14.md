### Title
`ensure_match_transaction_info` never verifies `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, letting replay/backup verification accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by restore/replay-verification tooling to confirm that a locally re-executed `TransactionOutput` matches an authenticated `TransactionInfo` pulled from a backup or archive. It checks status, gas, write-set hash, and event-root hash, but never checks the state-checkpoint-related hashes carried in `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`). A code comment in the function itself acknowledges the gap for the trading-native field, but the same gap already exists for the pre-existing `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields regardless of any new feature flag.

### Finding Description
`TransactionInfoV0`/`TransactionInfoV1` carry `state_checkpoint_hash` (JMT root after a checkpoint), `hot_state_checkpoint_hash`, and (V1) `position_state_checkpoint_hash` as committed, accumulator-covered fields: [1](#0-0) 

`ensure_match_transaction_info` is supposed to be the single place that proves a freshly executed `TransactionOutput` is consistent with a trusted `TransactionInfo` (which itself is proven against a `LedgerInfo` via the accumulator). It validates status, gas, write-set hash, and event-root hash, but stops there — the state checkpoint hashes are never compared, and the function unconditionally returns `Ok(())` afterward: [2](#0-1) 

The in-repo TODO explicitly documents that this is a known integrity gap for the new position/trading-native state root, but the omission is broader: `state_checkpoint_hash` and `hot_state_checkpoint_hash` are also silently skipped, independent of any feature flag.

This comparator is relied on by state-integrity verification tooling:
- `storage/db-tool/src/replay_on_archive.rs` re-executes transactions pulled from a backup and calls `ensure_match_transaction_info` to decide whether the replay matches the archived, authenticated `TransactionInfo`: [3](#0-2) 
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, used by chunk-executor verify-execution mode (restore/backup verification path), calls the same comparator per-transaction: [4](#0-3) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` also uses it to print/accept mismatches: [5](#0-4) 

Because none of these call sites independently re-check the state-checkpoint hashes elsewhere, a re-executed transaction whose resulting JMT state root (or hot-state root, or position/trading-native root) diverges from the archived/authenticated `TransactionInfo.state_checkpoint_hash` will still be reported as "verified" / "matching" by all three tools, since only write-set hash, event hash, gas, and status are checked — not the state root itself.

### Impact Explanation
This breaks the proof-and-storage-pivot invariant that "Authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object" for the replay/restore verification surface. `replay_on_archive` and `verify_execution` exist specifically to independently prove that a backup/archive's committed ledger state is reproducible by re-execution; skipping the state-checkpoint-hash comparison means these tools can validate a backup/chunk as "correct" even though the actual state root the executor derived diverges from the authenticated root committed in `TransactionInfo` and covered by the accumulator/`LedgerInfo` signature. This undermines the integrity guarantee that operators, indexers, and node operators rely on when using these tools to detect state corruption, storage bugs, or a hard-fork-only divergence during restore — exactly the class of impact the state-integrity gate calls out ("Hard-fork-only divergence during commit, replay, restore, or proof verification").

The impact is scoped to verification tooling rather than the live consensus-commit path (`AptosDB`'s actual commit path independently computes and persists roots via `commit_transaction_accumulator`/`calculate_state_and_put_updates`, which are not gated by this comparator), so it does not directly corrupt a live node's committed ledger. However, it does mean a corrupted or maliciously altered backup/archive dataset, or a genuine state-root-divergence bug elsewhere in execution, would go undetected by the exact tools designed to catch it.

### Likelihood Explanation
The gap is deterministic and always present — it is not a race condition or hard-to-trigger edge case. Any divergence in state-checkpoint hash (from a storage/execution bug, a backup corruption, or a hard fork mismatch) that does not also change the write set hash, event hash, gas, or status will be silently accepted by `replay_on_archive`, `verify_execution`, and `aptos_debugger`. The TODO comment confirms the maintainers are aware of at least the trading-native portion of this gap but the fix has not landed for the pre-existing `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields either.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute (or accept as a parameter) the state-checkpoint hash(es) produced by execution and compare them against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (V1), and `txn_info.position_state_checkpoint_hash()` (V1) whenever those fields are `Some`, failing verification (as the other checks do via `ensure!`) on mismatch. This must be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, and ideally is fixed independently of that flag since the state/hot-state checkpoint hash gap predates it.

### Proof of Concept
Not applicable as a standalone runnable PoC — the vulnerable code path is a validation omission, not an exploitable execution bug. The proof is structural: trace `replay_on_archive::execute_and_verify` → `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) shows that no comparison of `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` occurs before returning `Ok(())`, so any test that constructs a `TransactionOutput` with a correct write set/events/gas/status but wraps it with a `TransactionInfo` carrying a different `state_checkpoint_hash` will pass verification unmodified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
