## Title
`TransactionOutput::ensure_match_transaction_info` skips state/hot-state/position checkpoint hash validation, allowing replay-verify and chunk-replay tooling to accept a locally computed state root that diverges from the authenticated ledger root — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness gate used by `execution/executor/src/chunk_executor/mod.rs::verify_execution`, `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, and `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches` to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` pulled from a backup/archive (which is itself bound to a proof-verified `LedgerInfoWithSignatures`). The function validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but — per its own inline TODO — never validates `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The function checks four fields (status, gas, write-set hash, event root hash) and then returns `Ok(())` without comparing the checkpoint-hash fields carried by `TransactionInfoV1`/`V0` against anything locally computed. The comment explicitly documents the gap: [2](#0-1) 

These checkpoint hashes are the Sparse-Merkle/Jellyfish-Merkle roots of the full world state (and hot-state / position-state variants) computed by `DoStateCheckpoint::run`, and are part of what is hashed into `TransactionInfo` and folded into the transaction accumulator by `DoLedgerUpdate::assemble_transaction_infos`: [3](#0-2) 

They are the durable, authenticated commitment to committed state — distinct from the per-transaction `write_set` hash, which only commits to that transaction's own deltas, not the resulting aggregate state tree. Two different sequences of writes (or different resolution of the same writes, e.g. from AggregatorV1/DelayedField materialization, resource-group unpacking, or hot-state/position-state accounting bugs) can produce the same `write_set_hash` per transaction while yielding a different global state root.

Since `ensure_match_transaction_info` never compares `state_checkpoint_hash` (or the hot-state / position-state variants) between the locally computed output and the trusted `TransactionInfo`, all three call sites accept a "match" even when the locally materialized ledger state diverges from the network's authenticated state root at checkpoint boundaries:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution` (used when replaying/verifying chunks during restore/execution-mode verification) [4](#0-3) 
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` (the dedicated tool whose entire purpose is to detect exactly this kind of divergence against archived, ledger-info-verified transaction infos) [5](#0-4) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches` [6](#0-5) 

### Impact Explanation
This breaks the "committed state must survive executor-to-storage handoff and replay unchanged" and "authenticated proof-bearing responses must stay bound to the right root" invariants required by the gate: a state-root divergence — caused by a VM/executor bug, a checkpoint-computation bug (e.g. in `DoStateCheckpoint::compute_position_checkpoint` or hot-state accounting), or corrupted archive data feeding the state tree — would silently pass `replay_on_archive` and chunk-executor `verify_execution`, both of which exist specifically to catch this class of bug before it reaches production. Because the check is a no-op for checkpoint hashes, operators relying on these tools for state-integrity assurance (e.g., before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, or during routine archive replay-verification) get a false "all clear," masking a real divergence between locally executed state and the authenticated on-chain state root. This is a proof-verification/replay-integrity gap rather than a live consensus-safety bypass (the consensus/commit path derives roots independently and is not gated by this function), but it directly matches the "wrong accumulator root / proof accepted as valid" and "hard-fork-only divergence during commit, replay, restore, or proof verification" impact categories in scope.

### Likelihood Explanation
The gap is deterministic and always present — it is not conditional on attacker behavior; it fires whenever `ensure_match_transaction_info` is invoked and the two implementations diverge only in checkpoint hashes (which is exactly the failure mode most likely from a subtle state-computation bug, since write-set and event hashes are much simpler and more likely to be caught by existing checks). The gap is self-acknowledged in the code via the TODO, indicating it is a known, currently-shipped, non-hypothetical omission. Its main condition for triggering a high-severity outcome is a checkpoint-computation bug elsewhere in the state-checkpoint/state-summary code (e.g. `DoStateCheckpoint`), which this function is specifically supposed to catch during replay-verify but currently cannot.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()` (for `TransactionInfoV1`), and `position_state_checkpoint_hash()` against the corresponding locally computed checkpoint hashes whenever they are `Some` in the trusted `TransactionInfo`, returning an error on mismatch just as is done today for `state_change_hash` and `event_root_hash`. This requires threading the locally computed checkpoint hash(es) into `TransactionOutput` (or passing them as an additional parameter similar to `expected_write_set`) at each of the three call sites before comparison. Do this before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production, as the code comment itself recommends.

### Proof of Concept
Not directly exploitable via a single reproducible transaction (this is a missing-check bug in an offline verification/debugging tool, not a consensus-path vulnerability). The "PoC" is structural: construct two `TransactionOutput`s with identical `write_set` bytes (hence identical `state_change_hash`) and identical `events` (hence identical `event_root_hash`) and identical gas/status, but where the surrounding checkpoint computation (a different `DoStateCheckpoint` state-tree assembly, e.g. from a divergent hot-state or position-state extension) yields a different `state_checkpoint_hash` in the corresponding `TransactionInfo`. Calling `ensure_match_transaction_info` with such inputs returns `Ok(())` today because no field of the function's body reads `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` from `txn_info`, confirmed by direct inspection of the function body [1](#0-0) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
