### Title
Client-side-proving `proof` field is excluded from the signed transaction hash, allowing proof substitution without invalidating the sender's signature - ([File: crates/starknet_api/src/rpc_transaction.rs])

### Summary
`RpcInvokeTransactionV3` (and `InternalRpcInvokeTransactionV3`) carry two client-side-proving fields: `proof_facts` (claims about a prior virtual-OS/SNOS execution) and `proof` (the actual STARK/circuit proof attesting to those facts). Only `proof_facts` is folded into the Poseidon transaction hash that the sender signs; `proof` is explicitly dropped when converting to the hashed `InvokeTransactionV3` representation. This is structurally the same bug class as CVE-2022-22934 (SaltStack): a security-relevant payload (pillar data / proof) is not bound by the cryptographic signature/verification path that is supposed to authenticate it, so it can be substituted in transit without the substitution being detectable via signature verification.

### Finding Description
`InvokeTransactionV3` (the struct used to compute `TransactionHash`, i.e., the pre-image signed by the sender's account) has a `proof_facts` field but no `proof` field: [1](#0-0) 

The conversion from `RpcInvokeTransactionV3`/`InternalRpcInvokeTransactionV3` to `InvokeTransactionV3` explicitly drops the `proof` field with a comment acknowledging this: [2](#0-1) [3](#0-2) 

The invoke V3 hash function only chains `calldata`, `account_deployment_data`, `paymaster_data`, resource bounds/tip and (conditionally) `proof_facts` — never `proof`: [4](#0-3) 

The gateway only checks presence-consistency between `proof_facts` and `proof` (both empty or both non-empty), not that `proof` cryptographically matches `proof_facts`, nor that the pair is bound to the transaction hash/signature: [5](#0-4) 

The actual STARK-proof verification against `proof_facts` happens asynchronously/out-of-band via the proof manager (`contains_proof`/`set_proof`), decoupled from the signature-verified transaction path: [6](#0-5) 

Because `proof` is never covered by the hash that the account's `__validate__` entry point checks against the sender's signature (see the signed-hash-based validation pattern), an attacker who intercepts, relays, or re-broadcasts a transaction (e.g., in the mempool-p2p gossip path, or a malicious/compromised intermediary along the tx-submission flow) can strip or swap the `proof` bytes for a different (invalid, stale, or crafted) blob while keeping `proof_facts` and the original valid signature intact. The transaction hash and signature remain valid because `proof` was never part of what was signed.

### Impact Explanation
`proof_facts` are trusted, security-relevant claims (SNOS/virtual-OS block hash, block number, program hash, config hash) used by `perform_pre_validation_stage`/`validate_proof_facts` to gate proof-related pre-validation and fee/gas accounting for client-side proving transactions: [7](#0-6) 

If the binding `proof` blob that is supposed to substantiate these claims can be silently swapped in-flight without invalidating the sender's signature, an attacker can decouple the signed claims from the actual cryptographic proof that should back them, defeating the purpose of proof-facts pre-validation for this transaction type and creating a path for admitting/executing transactions whose "proven" execution context does not match what was actually verified. Depending on how strictly downstream consumers (proof manager, consensus/executor) enforce successful verification prior to block inclusion versus relying on the gateway/mempool having already checked it, this can result in acceptance of client-side-proving invoke transactions with mismatched or unverifiable proofs reaching block building/execution — a correctness/integrity violation of the transaction's cryptographic guarantees, meeting the "unauthorized action / honest-node divergence" bar since different nodes could end up with different `proof` bytes for the same signed, same-hash transaction.

### Likelihood Explanation
The `proof` field is only reachable when `allow_client_side_proving` is enabled and reaches the gateway through a standard, unprivileged `add_transaction` RPC call or via mempool-p2p propagation between sequencers — no special privileges are required to submit or relay a client-side-proving invoke transaction. Any relayer/propagator node on the standard tx-submission/broadcast path (gateway → mempool P2P propagator → peer gateway, per the tx submission flow) can mutate the `proof` bytes of an in-flight transaction with a valid signature/hash still intact, since the hash used by gateway/mempool/consensus never covers `proof`.

### Recommendation
Include a binding commitment to `proof` (e.g., `proof.hash()`) in the invoke-transaction hash pre-image alongside `proof_facts`, so any substitution of `proof` invalidates the sender's signature. Alternatively, cryptographically bind `proof` to `proof_facts` and to the transaction hash at the protocol level (e.g., require the transaction hash itself as public input to the proof), and enforce this binding check as an early, mandatory stateless validation step in `StatelessTransactionValidator` rather than only checking presence-consistency.

### Proof of Concept
1. Enable client-side proving (`allow_client_side_proving = true`) and craft a valid `RpcInvokeTransactionV3` with non-empty `proof_facts` (valid SNOS claims) and a corresponding valid `proof`.
2. Compute `tx_hash = calculate_transaction_hash(...)` — verified to exclude `proof` per `get_invoke_transaction_v3_hash` (only `proof_facts` is chained).
3. Sign `tx_hash` with the sender's key to produce `signature`.
4. Intercept the transaction on the wire (e.g., in mempool P2P propagation between sequencer A and B, as depicted in `docs/diagrams/02-tx-submission-flow.md`) and replace the `proof` bytes with a different value (garbage, stale, or a proof for different `proof_facts`), leaving `sender_address`, `calldata`, `proof_facts`, `nonce`, `resource_bounds`, `tip`, and `signature` unchanged.
5. Submit the mutated transaction to the gateway: `validate_transaction_hash`/`calculate_transaction_hash` reproduces the same `tx_hash` (since `proof` isn't hashed), signature verification in `__validate__` still succeeds, and `validate_proof_facts_and_proof_consistency` only checks that `proof` is non-empty when `proof_facts` is non-empty — it does not verify `proof` actually attests to `proof_facts`.
6. The mutated transaction with a signature-valid but content-mismatched `proof`/`proof_facts` pair proceeds into further validation/execution, demonstrating the missing cryptographic binding.

pub(crate) fn get_invoke_transaction_v3_hash<T: InvokeTransactionV3Trait>(
    transaction: &T,
    chain_id: &ChainId,
    transaction_version: &TransactionVersion,
) -> Result<TransactionHash, StarknetApiError> {
    let tip_resource_bounds_hash =
        get_tip_resource_bounds_hash(&transaction.resource_bounds(), transaction.tip())?;
    let paymaster_data_hash =
        HashChain::new().chain_iter(transaction.paymaster_data().0.iter()).get_poseidon_hash();
    let data_availability_mode = concat_data_availability_mode(
        transaction.nonce_data_availability_mode(),
        transaction.fee_data_availability_mode(),
    );
    let account_deployment_data_hash = HashChain::new()
        .chain_iter(transaction.account_deployment_data().0.iter())
        .get_poseidon_hash();
    let calldata_hash =
        HashChain::new().chain_iter(transaction.calldata().0.iter()).get_poseidon_hash();
    let mut hash_chain = HashChain::new()
        .chain(&INVOKE)
        .chain(&transaction_version.0)
        .chain(transaction.sender_address().0.key())
        .chain(&tip_resource_bounds_hash)
        .chain(&paymaster_data_hash)
        .chain(&Felt::try_from(chain_id)?)
        .chain(&transaction.nonce().0)
        .chain(&data_availability_mode)
        .chain(&account_deployment_data_hash)
        .chain(&calldata_hash);
    if !transaction.proof_facts().0.is_empty() {
        let proof_facts_hash =
            HashChain::new().chain_iter(transaction.proof_facts().0.iter()).get_poseidon_hash();
        hash_chain = hash_chain.chain(&proof_facts_hash);
    }
    Ok(TransactionHash(hash_chain.get_poseidon_hash()))
}

                has_proof_facts,
                has_proof,

    fn validate_proof_facts(
        &self,
        block_context: &BlockContext,
        state: &mut dyn State,
    ) -> TransactionPreValidationResult<()> {
        // Only Invoke V3 transactions can carry proof facts.
        let Transaction::Invoke(invoke_tx) = &self.tx else {
            return Ok(());
        };
        if invoke_tx.version() < TransactionVersion::THREE {
            return Ok(());
        }

        // Parse proof facts.
        let proof_facts = invoke_tx.proof_facts();
        let snos_proof_facts = match ProofFactsVariant::try_from(&proof_facts)
            .map_err(|e| TransactionPreValidationError::InvalidProofFacts(e.to_string()))?
        {
            ProofFactsVariant::Empty => return Ok(()),
            ProofFactsVariant::Snos(snos_proof_facts) => snos_proof_facts,
        };
        let os_constants = &block_context.versioned_constants.os_constants;

        if !os_constants.allowed_proof_versions.contains(&snos_proof_facts.proof_version.as_felt())
        {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Proof version {} is not allowed under this protocol version.",
                snos_proof_facts.proof_version
            )));
        }

        // Validate the program hash.
        let allowed = &os_constants.allowed_virtual_os_program_hashes;
        if !allowed.contains(&snos_proof_facts.program_hash) {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS program hash {} is not allowed",
                snos_proof_facts.program_hash
            )));
        }

        // Validate the block hash and block number.
        let proof_block_hash = snos_proof_facts.block_hash.0;
        let proof_block_number = snos_proof_facts.block_number.0;
        Self::validate_proof_block_number(
            proof_block_number,
            block_context.block_info.block_number,
        )?;
        Self::validate_proof_block_hash(proof_block_hash, proof_block_number, os_constants, state)?;

        // Validate the config hash.
        let virtual_os_config_hash = block_context.virtual_os_config_hash();
        let proof_config_hash = snos_proof_facts.config_hash;
        if virtual_os_config_hash != proof_config_hash {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS config hash mismatch. Computed virtual OS config hash: \
                 {virtual_os_config_hash}, expected virtual OS config hash: {proof_config_hash}."
            )));
        }

        Ok(())
    }
