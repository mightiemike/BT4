### Title
`validate_delegate_action_key` Missing Early Return on `DepositWithFunctionCall` Advances Nonce on Failed Delegate Action — (`runtime/runtime/src/actions.rs`)

### Summary

In `validate_delegate_action_key`, when a `DelegateAction` signed with a `FunctionCallPermission` access key contains a `FunctionCall` action with a nonzero deposit, the function sets `result.result = Err(DepositWithFunctionCall)` but — before protocol version 85 — does **not** return early. Execution falls through to the `receiver_id` and `method_name` checks. If those checks pass (receiver matches, method is allowed), the function reaches the nonce-update block at lines 685–699 and **writes the advanced nonce to trie state** before returning. The caller (`apply_delegate_action`) then sees `result.result.is_err()` and aborts without creating the inner receipt — but the nonce has already been permanently consumed.

### Finding Description

`validate_delegate_action_key` (`runtime/runtime/src/actions.rs:535`) validates the access key used to sign a `DelegateAction`. For a `FunctionCallPermission` key the function must enforce three constraints in order: (1) deposit must be zero, (2) receiver must match, (3) method must be allowed. Each failing check is supposed to set an error and `return Ok(())` immediately.

The deposit check at line 637 sets the error but, before `FixDelegateActionDepositWithFunctionCallError` (protocol version 85), omits the early return:

```rust
if function_call.deposit > Balance::ZERO {
    result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
        InvalidAccessKeyError::DepositWithFunctionCall,
    ).into());
    // ← no return here before the fix
}
``` [1](#0-0) 

Execution then falls through to the receiver and method checks. When both pass (receiver matches, method list is empty or the method is allowed), the function exits the permission block and unconditionally executes the nonce-update block:

```rust
match nonce_update {
    DelegateNonceUpdate::AccessKey => {
        access_key.nonce = delegate_nonce.nonce();
        set_access_key(state_update, sender_id.clone(), public_key.clone(), &access_key);
    }
    ...
}
``` [2](#0-1) 

The nonce is written to trie state even though `result.result` is `Err`. Back in `apply_delegate_action`, the error is detected and the inner receipt is not created — but the nonce mutation is already committed to the `TrieUpdate`: [3](#0-2) 

### Impact Explanation

The broken invariant is: **a delegate action that fails permission validation must not advance the sender's access-key nonce**. Here the nonce is advanced despite the action being rejected. Concretely:

- The sender's `FunctionCallPermission` access key nonce is incremented to `delegate_nonce.nonce()` even though no inner receipt is produced.
- Any subsequent delegate action signed with the same key must use a nonce strictly greater than the now-advanced value. A relayer in possession of multiple pre-signed delegate actions from the same sender (e.g., a batch) can submit the invalid one first, silently burning a nonce slot and invalidating any pre-signed action that reused that nonce value.
- The error reported to the user is also wrong: when the receiver also mismatches, `ReceiverMismatch` overwrites `DepositWithFunctionCall`, masking the real rejection reason. [4](#0-3) 

### Likelihood Explanation

The trigger requires a `FunctionCallPermission` access key and a `DelegateAction` whose inner `FunctionCall` carries a nonzero deposit. This is an easy mistake for a sender who intends to attach a deposit but forgets that `FunctionCallPermission` forbids it. A relayer who receives such a pre-signed action can submit it, consuming the nonce. The bug is present on any node running protocol version < 85.

### Recommendation

The fix is already present in the codebase, gated by `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` (protocol version 85): [5](#0-4) [6](#0-5) 

The correct behavior — `return Ok(())` immediately after setting the `DepositWithFunctionCall` error — is enforced for all nodes at protocol version ≥ 85. No further action is needed beyond ensuring the protocol upgrade is applied.

### Proof of Concept

The repository's own test `test_delegate_deposit_with_function_call_reports_receiver_mismatch_before_fix` demonstrates the pre-fix behavior: [7](#0-6) 

To observe the nonce advancement, extend the test helper `deposit_with_function_call_and_receiver_mismatch` to use a matching receiver (so `ReceiverMismatch` is not triggered) and inspect the stored access-key nonce after the call. Before the fix, `get_access_key` on the `state_update` will show `nonce == initial_nonce + 1` even though `result.result` is `Err(DepositWithFunctionCall)`. After the fix (protocol version ≥ 85), the nonce remains at `initial_nonce`.
