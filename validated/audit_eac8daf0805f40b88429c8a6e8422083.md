### Title
Exchange pool ratio manipulation via repeated floor-rounded micro-injections — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` computes the paired-token contribution (`anotherTokenQuant`) required to inject `tokenQuant` of one side of a Bancor-style TRC10 exchange pool using integer floor division. Because this rounding is always applied in the same direction (down, in favor of the injector) and only a minimal positive value is enforced (`anotherTokenQuant <= 0` fails), an exchange creator can split a large injection into many minimal `tokenQuant` calls, each rounding `anotherTokenQuant` down more aggressively than a single large call would, systematically under-contributing to the paired side of the pool relative to the true (non-integer) proportional share. This mirrors the Morpho liquidation bug pattern: a single-sided rounding decision, applied to a value that simultaneously affects two economically linked quantities (fair pool ratio vs. actual contribution), is exploitable by transaction-splitting because the rounding error is realized on every call rather than being bounded once.

### Finding Description
In `ExchangeInjectActuator.execute()`:
```java
anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance);
exchangeCapsule.setBalance(addExact(firstTokenBalance, tokenQuant),
    addExact(secondTokenBalance, anotherTokenQuant));
``` [1](#0-0) 

`doValidate()` computes the same value with `BigInteger` division (also floor / truncating) and only rejects when `anotherTokenQuant <= 0`:
```java
anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance).longValueExact();
...
if (anotherTokenQuant <= 0) {
  throw new ContractValidateException("the calculated token quant  must be greater than 0");
}
``` [2](#0-1) 

The true proportional contribution required to keep the pool's price ratio (`firstTokenBalance/secondTokenBalance`) unchanged is `secondTokenBalance * tokenQuant / firstTokenBalance` as a real number; truncating this discards the fractional remainder on every single call. Because the check only requires the truncated quantity to be `> 0`, an attacker (the exchange creator — anyone who calls `ExchangeCreateContract` can become a creator of their own pool, this is not a privileged system role) can choose `tokenQuant` values close to the minimum needed to keep `anotherTokenQuant >= 1`, then repeat the injection many times via ordinary broadcast transactions. Each call discards a comparatively large fractional remainder relative to the injected amount (the smaller `tokenQuant` is, the larger the proportional rounding loss becomes, since the discarded fraction is bounded by 1 unit of `anotherTokenQuant` regardless of `tokenQuant` size), letting the creator inflate the `firstToken`/`secondToken` pool ratio in their favor far more than a single equivalent-sized injection would allow. The creator can later use `ExchangeWithdrawActuator`, which computes withdrawal amounts from the current (now-skewed) pool ratio via `divideToIntegralValue` [3](#0-2) , to extract a disproportionate amount of the counter-token relative to what fair proportional injection would have entitled them to, at the expense of the token reserves that other traders' `ExchangeTransactionContract` swaps rely on for correct pricing via `ExchangeProcessor`/`SafeExchangeProcessor`'s Bancor formula [4](#0-3) .

### Impact Explanation
This allows the creator of a TRC10/TRX exchange pool (an unprivileged, self-service action reachable by broadcasting `ExchangeCreateContract` then repeated `ExchangeInjectContract` transactions) to skew the pool's stored token ratio through many rounding-favorable micro-injections, then withdraw a value disproportionate to their real contribution via `ExchangeWithdrawContract`. This is an accounting/market-math corruption of on-chain exchange reserves at the expense of other participants who trade against the pool at the manipulated price, analogous to the reported Morpho issue where transaction splitting exploits a single-direction rounding rule to extract more value than intended.

### Likelihood Explanation
Any account can create an exchange pool and is automatically its creator (`accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` check at validate time simply confirms self-created pool ownership) [5](#0-4) . Exploitation only requires broadcasting many low-fee `ExchangeInjectContract` transactions with small `tokenQuant`, which is straightforward and does not require special privileges, making likelihood moderate to high, bounded mainly by the number of transactions needed to accumulate meaningful drift and the fee cost of each transaction.

### Recommendation
Track and carry forward the fractional remainder discarded by `floorDiv`/`divide` across injections (e.g., using a running remainder or higher-precision fixed-point accounting), or require the injector to round `anotherTokenQuant` up when it benefits the pool (mirroring the recommended Morpho fix of using distinct rounding directions for the two economically linked quantities: contribution vs. pool-state impact), so that repeated small injections cannot systematically bias the pool ratio in the injector's favor.

### Proof of Concept
Not executed against a live node (no filesystem/terminal access in this environment); however, the exploitable logic can be reproduced as a unit test analogous to `ExchangeCapsuleTest`:
1. Create an exchange pool with `firstTokenBalance = 1_000_000`, `secondTokenBalance = 1_000_000` as creator `A`.
2. Repeatedly call `ExchangeInjectActuator.execute()` with `tokenQuant = 1` (first token) for `N` iterations. Each iteration computes `anotherTokenQuant = floorDiv(secondTokenBalance * 1, firstTokenBalance)`, which truncates to `0` unless `secondTokenBalance >= firstTokenBalance`; adjust `tokenQuant` to the minimal value that keeps `anotherTokenQuant == 1` (validate's floor of the `BigInteger` division) each time.
3. Compare final pool ratio and total tokens actually contributed by `A` vs. the ratio/contribution that a single equivalent-sized injection would have required — the split-injection path contributes measurably less of `secondToken` per unit of `firstToken` injected than the fair ratio, mirroring the Morpho PoC pattern of splitting into minimal repayments to exploit one-directional rounding.
