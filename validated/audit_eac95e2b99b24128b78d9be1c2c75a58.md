### Title
Unbounded array allocation from attacker-controlled length field in `ValidateMultiSign`/`BatchValidateSign` precompiles leads to memory-exhaustion DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts decode ABI-encoded array arguments from arbitrary contract calldata using helper functions (`extractBytesArray`, `extractSigArray`, `extractBytes32Array`) that read a "length" word directly out of attacker-supplied calldata and immediately allocate a Java array of that size — before any bound check is applied. This mirrors the reported `attest/core` bug class: a size value taken from untrusted input is used to size a memory allocation with no upper bound, comparable to `serde`'s unbounded `Vec::with_capacity(seq.size_hint())` pattern.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` each read `len` straight from calldata (`words[offset].intValueSafe()`) and construct `new byte[len][]` immediately: [1](#0-0) [2](#0-1) 

The `MAX_SIZE`-bound check in `ValidateMultiSign.execute` and `BatchValidateSign.doExecute` is only performed when `VMConfig.allowTvmSelfdestructRestriction()` returns true; when that fork/config flag is off, `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are invoked with the raw, unvalidated `len` before any size check occurs: [3](#0-2) [4](#0-3) 

Even in the "optimized" branch (flag on), `extractBytes32Array` for `addresses` is bounded by the pre-check on `addrArraySize`, but `extractBytesArray`/`extractSigArray` for `signatures` still perform the array construction using the same `len` field internally — the outer `MAX_SIZE` rejection (`signatures.length == 0 || signatures.length > MAX_SIZE`) happens only *after* the array is already allocated. This means the allocation always occurs with the attacker-chosen size before any validation can reject it in the un-guarded (pre-fork / config-off) code path, and the additional `isValidAbiEncoding` check on overall calldata length does not constrain the independent, embedded `len` word value read from inside the payload.

### Impact Explanation
Any account can invoke these precompiles (addresses `0x...9` `batchvalidatesign` and `0x...a` `validatemultisign`) via a normal smart-contract `CALL`/`TriggerSmartContract` transaction, i.e., no privileged role or malicious peer/node is required — this is a standard, unprivileged transaction. A crafted `len` value close to `Integer.MAX_VALUE` causes an immediate attempt to allocate an array of that many object references (`byte[][]`), which throws `OutOfMemoryError` or otherwise forces the JVM into extreme GC pressure on every full node/validator processing the transaction (during both block production and block replication/consensus validation), producing a broadcast-transaction-triggered denial of service across the network — matching the report's exploit scenario ("Eve sends a crafted transaction … causing the memory to be exhausted").

### Likelihood Explanation
Likelihood is high for the un-guarded code path: it requires only a single crafted transaction calling a `TriggerSmartContract`/`CALL` to the precompile address, no special account balance/permission beyond covering execution fees, and no consensus-privileged actor. The bug is gated behind a config/fork flag (`VMConfig.allowTvmSelfdestructRestriction`), so exploitability depends on whether that flag is enabled on the target network at the time of the attack — if it is disabled, this is directly reachable; if enabled, the `signatures`/`addresses` allocation size is bounded, but the exact interaction of the "optimized" branch with `extractBytesArray`'s internal reads (`bytesOffset`, `bytesLen`) was not further audited to rule out additional out-of-bounds/large-allocation edge cases in the bounded path.

### Recommendation
- Validate the decoded array-length word against `MAX_SIZE` (and against the actual remaining `words` array bounds) inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves, *before* allocating the array, rather than relying on a call-site check that is conditioned on a fork flag.
- Reject calldata whose declared length exceeds a hard bound (e.g., `MAX_SIZE`) or whose length disagrees with the calldata size implied by `isValidAbiEncoding`, independent of `VMConfig.allowTvmSelfdestructRestriction()`.
- Add fuzz tests targeting these ABI-array extraction helpers with adversarial length words to catch similar unbounded-allocation issues.

### Proof of Concept
1. Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` (or `batchvalidatesign`) where the head words are well-formed enough to pass `isValidAbiEncoding`, but the embedded length word for the `bytes[]` parameter (`words[offset]`) is set to a very large value (e.g., `0x7FFFFFFF`).
2. Deploy/call a contract that performs a `CALL` to precompile address `0x...a` (`validateMultiSign`) or `0x...9` (`batchValidateSign`) with this calldata, in an environment/network where `VMConfig.allowTvmSelfdestructRestriction()` is not yet enabled.
3. Observe that `extractBytesArray`/`extractSigArray` executes `new byte[len][]` with `len` ≈ `0x7FFFFFFF`, causing `OutOfMemoryError` (or multi-second+ GC stalls) on the node processing the transaction, before the subsequent `signatures.length > MAX_SIZE` check is ever reached.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
