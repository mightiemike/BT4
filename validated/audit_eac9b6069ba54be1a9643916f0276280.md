### Title
Accrue-Pause Pass-Through Returns Stale Index That Gets Block-Cached and Consumed by Market Health/Liquidation Math - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
`accrue` in each vault (e.g. `v0-vault-stx.clar`) has a pause branch that returns the *current* `index`/`lindex` without reverting and without recomputing interest, instead of blocking the call. `market.clar`'s `accrue-and-cache` then stores whatever `accrue`/`vault-accrue` returns into `index-cache-`/`index-cache` keyed only by `{ timestamp: stacks-block-time, aid }`, and every later read of that asset's index within the same transaction/block (borrow post-checks, liquidation math, ztoken price resolution) blindly trusts the cached value via `unwrap-panic (get-cached-indexes ...)`. If `accrue` is unpaused *mid-transaction* (via a DAO call sequenced by an aggregator/multi-step proposal executor) after the market has already cached the pre-unpause index, the stale cached index is used for the rest of that transaction's calculations.

### Finding Description
`accrue` is implemented with a pass-through-on-pause pattern: [1](#0-0) 

When `(get accrue states)` is true, the function returns `{ index: idx, lindex: lidx }` — the vars as they currently sit in storage — without touching `last-update`, `index`, or `lindex`. This is a "pause that passes through instead of reverting" rather than aborting the caller.

`market.clar` (`v0-4-market.clar`) wraps every vault accrual behind a per-block cache keyed by `stacks-block-time` and the asset id: [2](#0-1) 

The cache is written on **first** access to an asset within a block/tx and is blindly trusted afterward — every subsequent read in that same tx (`get-cached-indexes`, used in `borrow`, `resolve-ztoken`, and liquidation math) does `(unwrap-panic (get-cached-indexes asset-id))` with no re-validation against the vault's live pause/accrual state: [3](#0-2) [4](#0-3) 

The DAO's `set-pause-states` function explicitly documents that unpausing `accrue` jumps `last-update` forward to "skip the paused period," i.e., the source-of-truth for the index moves atomically without any interest for the paused window ever being applied: [5](#0-4) 

Sequence:
1. Vault's `accrue` pause is active; `index`/`lindex` are frozen at some stale value `idx0`.
2. A user (or the same DAO proposal/aggregator transaction) triggers a market operation (e.g. `borrow`) on that asset. `accrue-and-cache` is called, cache-misses, calls `vault-accrue` → hits the pause pass-through branch → caches `idx0` under `{timestamp: stacks-block-time, aid}`.
3. Within that same transaction (multi-step proposal executing several `try!`-chained contract-calls, exactly the "multi-step entry point" pattern), a DAO call to `set-pause-states` unpauses `accrue` on the vault, which jumps `last-update` to `stacks-block-time` — silently discarding all interest that should have accrued from the vault's true last real update to now, and changing the *true* index going forward.
4. A second market operation in the same transaction (e.g. `is-healthy-with-mask` / liquidation `calc-final-liquidation-amounts` / `resolve-ztoken`) needs the index again. `accrue-and-cache` cache-hits on the same `{timestamp, aid}` key from step 2 and returns `idx0` again — even though the vault's real state (and the "moved" `last-update`) already reflect the unpause event.
5. Debt/collateral notional values, borrow health post-checks, and liquidation payout math computed with this stale cached index diverge from the vault's actual accounting, because the cache was populated from the paused branch's frozen value and never invalidated when the underlying pause state changed within the block.

This satisfies the required analog mechanics: a cached value (`index-cache`) not invalidated when its source (`accrue`/pause state via DAO `set-pause-states`) moves within the same block/transaction, combined with a pause that passes through instead of reverting.

### Impact Explanation
The market's health checks (`is-healthy-with-mask`) and liquidation math (`process-debt-asset`, `calc-final-liquidation-amounts`) directly consume `accrue-and-cache`'s cached index to compute USD notional collateral/debt values. If those values are computed from a stale, unpaused-then-changed index within one transaction, a borrow can pass a post-check that would otherwise fail (temporary freezing/loss of protocol solvency guarantees), or a liquidation can compute an incorrect `debt-to-repay`/`coll-final`, leading to over- or under-collateralized outcomes and mispriced liquidations. This lands on **temporary freezing of funds / protocol insolvency risk** class (accounting divergence between cached and true vault state within the exploit window), consistent with the impact classes allowed in scope.

### Likelihood Explanation
This requires the DAO-controlled `set-pause-states` call to be interleaved with a user- or protocol-triggered market operation within the same transaction/block — most plausible via a multi-step DAO proposal script (the repo's proposal pattern chains many `try!` contract-calls in one `execute`), or an aggregator contract that batches a pause-toggle with a borrow/liquidation call. Because `stacks-block-time` is block-granular, all calls in one block share the same cache key, making the interleaving straightforward within Clarity's sequential evaluation order (no reentrancy needed — just ordering within one transaction/block).

### Recommendation
Invalidate or re-validate the `index-cache-`/`index-cache` entry whenever a vault's pause/accrual state changes (e.g., bump a per-asset epoch/nonce on `set-pause-states` and include it in the cache key), or have `accrue-and-cache` always re-call `vault-accrue` rather than trusting a cache populated before a pause-state mutation. At minimum, `accrue`'s paused branch should not be treated as equivalent-to-fresh for caching purposes.

### Proof of Concept
1. Vault `v0-vault-stx`: DAO sets `accrue: true` in `pause-states` (interest accrual paused); `index` frozen at `I0`.
2. Within one transaction/proposal `execute`:
   a. Call `.v0-1-market borrow` on STX for account A → `accrue-and-cache` cache-misses, calls `vault-accrue` → hits paused branch in `accrue` ( [6](#0-5) ), caches `{index: I0, lindex: L0}` under `{timestamp: T, aid: STX}`.
   b. Call `.v0-vault-stx set-pause-states` to unpause `accrue` → `last-update` jumps to `T` ( [7](#0-6) ), meaning the vault's true index basis has shifted (all pre-unpause pending interest for the paused window is discarded and future accrual starts fresh from `T`), but the market's cache still holds `I0`.
   c. Trigger a second market operation in the same transaction (e.g., `liquidate` on a borrower with STX debt) → `get-cached-indexes STX` cache-hits and returns the stale `{index: I0, lindex: L0}` ( [4](#0-3) ) instead of reflecting the just-changed vault state, producing liquidation amounts computed against a value the vault's own accounting no longer agrees with for the rest of that transaction.

Note: I could not fully trace `next-index()`/`next-liquidity-index()` internals (interest-rate curve math) before running out of iterations, so the exact numeric magnitude of index drift during a pause window is not verified here — only the caching/staleness mechanism itself, which is directly supported by the cited code.
