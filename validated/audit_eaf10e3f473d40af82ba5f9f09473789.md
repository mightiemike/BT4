### Title
Front-runnable counterfactual account address squatting via `deploy` syscall's `deploy_from_zero` flag causes permanent DoS of `DeployAccountTransaction` and fund freezing - (File: `crates/blockifier/src/execution/syscalls/syscall_base.rs`, `crates/starknet_api/src/transaction.rs`, `crates/blockifier/src/execution/execution_utils.rs`)

### Summary
Starknet contract addresses are deterministic, computed as `Pedersen(prefix, deployer_address, salt, class_hash, hash(constructor_calldata))`. For `DeployAccountTransaction`s, `deployer_address` is hard-coded to zero. Any contract can reach that exact same "zero-deployer" address space through the ordinary `deploy` syscall by setting `deploy_from_zero = true`. Because the resulting address depends only on publicly-known values (salt, class hash, constructor calldata) that a user must reveal off-chain in order to receive funds at their not-yet-deployed counterfactual account address, an unprivileged attacker can pre-emptively invoke the `deploy` syscall (e.g. through the widely used, permissionless Universal Deployer Contract pattern) with those exact parameters and `deploy_from_zero=true` to occupy the address first. This mirrors the LamboFactory `createPair` front-running DoS: the victim's subsequent `DeployAccountTransaction` will permanently fail because the target address is no longer available, and since the address is bound to the user's already-published salt/class_hash/calldata, there is no way to "retry" with a different address without abandoning any funds already sent there.

### Finding Description
The contract-address derivation is implemented in `calculate_contract_address` in `crates/starknet_api/src/core.rs`: [1](#0-0) 

For `DeployAccountTransaction`, the deployer address is unconditionally fixed to zero: [2](#0-1) 

Independently, the generic `deploy` syscall (reachable from any contract call in any transaction) allows the caller to explicitly opt into the same "deployer address = 0" address space via the `deploy_from_zero` flag: [3](#0-2) 

This means that for a given `(class_hash, contract_address_salt, constructor_calldata)` triple, both a legitimate `DeployAccountTransaction` and an arbitrary contract's `deploy(..., deploy_from_zero=true)` call converge on the *identical* resulting `ContractAddress`. Since a user must publish their counterfactual account address's `salt`/`class_hash`/`constructor_calldata` off-chain (typically derived from their public key) in order to receive funds before deploying their account, these values are necessarily public knowledge before the `DeployAccountTransaction` is submitted.

When the deployment address is already occupied, `execute_deployment` in `crates/blockifier/src/execution/execution_utils.rs` rejects the deployment outright: [4](#0-3) 

This is confirmed by existing tests showing `StateError::UnavailableContractAddress` is raised when a `DeployAccountTransaction` targets an address that already has a nonzero class hash: [5](#0-4) [6](#0-5) 

No mechanism (analogous to the recommended `getPair()` existence check in the external report) exists in the deploy path to detect that the target address is intended for a specific future account and reject/short-circuit the squatting deployment, nor to reserve the address for the rightful owner. Because the derivation formula is fully deterministic and the salt is chosen off-chain and already communicated to depositors, the victim cannot "just pick a new salt" without abandoning the address (and any funds sent there) entirely — an exact analog to the LamboFactory scenario where the pre-computed pool address cannot be reused once squatted.

### Impact Explanation
Any unprivileged party who learns a user's future counterfactual account address parameters (something that is unavoidably public, since the whole point of counterfactual deployment is to let others send funds to that address before the account exists) can invoke the permissionless `deploy` syscall with `deploy_from_zero=true` and identical `class_hash`/`salt`/`constructor_calldata` to occupy that address with a throwaway/garbage contract. This:
- Permanently prevents the rightful account owner's future `DeployAccountTransaction` from succeeding at that address (an honest, valid transaction submitted by any sender will deterministically revert forever with `StateError::UnavailableContractAddress`).
- Permanently freezes any funds already transferred to that counterfactual address, since the account contract that would grant control over those funds can never be deployed there.

This matches the required impact bar: permanent freezing of funds / unauthorized denial of an account action, reachable purely from an unprivileged transaction sender.

### Likelihood Explanation
The attack requires no special privileges — it is a normal contract call (`deploy` syscall with `deploy_from_zero=true`) available to any invoke transaction, commonly exposed through the widely deployed, permissionless Universal Deployer Contract pattern used across the Starknet ecosystem. The only prerequisite is that the attacker learns the victim's counterfactual salt/class_hash/calldata, which is inherent to the counterfactual-deployment UX (the values must be shared to receive funds ahead of deployment). The attack is cheap (a single deploy transaction) and fully deterministic in outcome.

### Recommendation
- Consider disallowing (or gating) `deploy_from_zero=true` for the generic `deploy` syscall so that arbitrary contracts cannot squat the same zero-deployer address space reserved for `DeployAccountTransaction`s, or scope that address space so it cannot collide with account-derivation addresses.
- Alternatively/additionally, document and mitigate at the wallet/SDK level by binding account salts to values unpredictable to third parties until deployment is submitted (e.g., commit-reveal), and avoid publishing raw salt/class_hash/calldata for counterfactual addresses before the deploy transaction is in-flight.
- Evaluate whether an existence check (return a distinguished, non-fatal error rather than an unrecoverable state, or allow re-derivation with an additional secret nonce known only to the intended owner) can reduce the permanence of the DoS.

### Proof of Concept
1. Alice generates a counterfactual account address using `calculate_contract_address(salt_A, class_hash_A, calldata_A, deployer_address=0)` and shares this address publicly to receive funds (standard Starknet UX), thereby revealing `salt_A`, `class_hash_A`, `calldata_A`.
2. Attacker Bob observes these public parameters and, before Alice submits her `DeployAccountTransaction`, submits an ordinary invoke transaction that calls a permissionless deployer contract's `deploy_contract` entry point (calling the `deploy` syscall documented at `crates/blockifier/src/execution/syscalls/syscall_base.rs:380-426`) with `class_hash_A`, `salt_A`, `calldata_A`, and `deploy_from_zero=true`.
3. `calculate_contract_address` computes the identical address as Alice's intended account address; `execute_deployment` (`crates/blockifier/src/execution/execution_utils.rs:337-356`) finds `current_class_hash == ClassHash::default()` (address free) and successfully deploys Bob's arbitrary class there.
4. Alice later submits her `DeployAccountTransaction` for the same address; `execute_deployment` now finds a nonzero class hash and returns `StateError::UnavailableContractAddress`, permanently failing Alice's deployment (as reproduced by the existing test in `crates/blockifier/src/transaction/transactions_test.rs:2308-2339`). Any funds sent to Alice's address prior to this remain permanently inaccessible since the account contract can never be deployed there.

pub fn calculate_contract_address(
    salt: ContractAddressSalt,
    class_hash: ClassHash,
    constructor_calldata: &Calldata,
    deployer_address: ContractAddress,
) -> Result<ContractAddress, StarknetApiError> {
    let constructor_calldata_hash = Pedersen::hash_array(&constructor_calldata.0);
    let contract_address_prefix = format!("0x{}", hex::encode(CONTRACT_ADDRESS_PREFIX));
    let address = Pedersen::hash_array(&[
        Felt::from_hex(contract_address_prefix.as_str()).map_err(|_| {
            StarknetApiError::OutOfRange { string: contract_address_prefix.clone() }
        })?,
        *deployer_address.0.key(),
        salt.0,
        class_hash.0,
        constructor_calldata_hash,
    ]);
    let (_, address) = address.div_rem(&L2_ADDRESS_UPPER_BOUND);

    ContractAddress::try_from(address)
}

impl<T: DeployTransactionTrait> CalculateContractAddress for T {
    /// Calculates the contract address for the contract deployed by a deploy account transaction.
    /// For more details see:
    /// <https://docs.starknet.io/architecture-and-concepts/smart-contracts/contract-address/>
    fn calculate_contract_address(&self) -> StarknetApiResult<ContractAddress> {
        // When the contract is deployed via a deploy-account transaction, the deployer address is
        // zero.
        const DEPLOYER_ADDRESS: ContractAddress = ContractAddress(PatriciaKey::ZERO);
        calculate_contract_address(
            self.contract_address_salt(),
            self.class_hash(),
            self.constructor_calldata(),
            DEPLOYER_ADDRESS,
        )
    }
}
