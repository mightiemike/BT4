### Title
Signer v2 (`GlobalStateView`) tenure-change validation omits the reorg-permission check that v1 enforces - ([File: stacks-signer/src/chainstate/v2.rs])

### Summary
The signer chainstate module has two parallel implementations of block-proposal validation for tenure-change blocks: `SortitionsView::validate_tenure_change_payload` (v1) and `GlobalStateView::validate_tenure_change_payload` (v2). Both are meant to enforce the same set of consensus rules before a signer places its signature on a tenure-change block. v1 calls `SortitionData::check_parent_tenure_choice(...)` to verify that a tenure reorg is actually permitted (i.e., the reorged tenures produced zero blocks, or their sole block landed within the allowed burn-block timing window) before accepting the tenure change. v2's equivalent function does not call this check at all.

### Finding Description
`stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` (lines 461-520) performs, in order:
1. Verify `tenure_change.prev_tenure_consensus_hash == parent_tenure_id`.
2. Verify `SortitionData::check_tenure_change_confirms_parent(...)`.
3. **Verify `proposed_by.state().data.check_parent_tenure_choice(signer_db, client, &self.config.first_proposal_burn_block_timing)` and reject with `RejectReason::ReorgNotAllowed` if it returns `false`.**
4. Reject duplicate tenure-change if a block was already globally accepted in this tenure.

`check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-204`) is precisely the guard that decides whether a miner is allowed to reorg away one or more prior tenures: a permitted reorg requires that every reorged tenure produced zero blocks, or produced its single block very close to the burn-block transition (governed by `first_proposal_burn_block_timing`). This is the core anti-reorg protection for the tenure-change acceptance path.

`stacks-signer/src/chainstate/v2.rs::validate_tenure_change_payload` (lines 306-359) performs steps 1, 2, and 4 above, but never calls `check_parent_tenure_choice`. There is no equivalent check anywhere else in `GlobalStateView::check_proposal` (lines 113-301) either — the function only checks `ConsensusHashMismatch`, `PubkeyHashMismatch`, `InvalidBitvec`, and tenure-extend timing, none of which substitute for the "was the reorg actually permitted" check.

This mirrors exactly the structural bug pattern in the referenced report: one of two parallel code paths that are supposed to enforce the same authorization/validation invariant is missing the check that the other path performs.

### Impact Explanation
Signers running the v2/global-state-machine protocol (selected once the network activates `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`, per `stacks-signer/src/v0/signer_state.rs` and `stacks-signer/src/chainstate/mod.rs`) will sign a tenure-change block that illegitimately reorgs a prior tenure that produced one or more blocks outside of the permitted burn-block timing window, whereas signers still evaluating proposals via the v1 path would reject the same block with `RejectReason::ReorgNotAllowed`. This breaks the equality that all correctly-configured signers must agree on the same accept/reject verdict for a tenure-change proposal. In a mixed-protocol-version signer set (an expected, supported transitional state per `stacks-node/src/tests/signer/multiversion.rs`), this can let a minority-aligned or malicious miner obtain enough v2-signer signatures to push through a tenure-change that reorgs blocks that were supposed to be protected, while v1 signers refuse — producing a genuine validation-verdict divergence and a path to an illegitimate reorg/tip disagreement bounded to the signer set that has moved to v2. This matches the "High" impact category: a minority-triggerable static-validation divergence causing temporary tip disagreement (and, if the v2-signing weight alone crosses the block-approval threshold, a chain fork).

### Likelihood Explanation
This is triggerable by any miner submitting a tenure-change proposal whose `prev_tenure_consensus_hash` targets a tenure that legitimately produced blocks outside the allowed timing window — no elevated privileges are required, and no majority is needed beyond whatever weight of v2-protocol signers exists in the network at the time (the codebase explicitly supports a mixed v1/v2 signer population during protocol migration, evidenced by `multiversion.rs` tests). Because `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` gates a live migration path, this divergence is reachable under normal operational conditions, not just a hypothetical.

### Recommendation
Add a call to `SortitionData::check_parent_tenure_choice` inside `GlobalStateView::validate_tenure_change_payload` (in `stacks-signer/src/chainstate/v2.rs`), mirroring the v1 implementation: after `check_tenure_change_confirms_parent` succeeds, call `check_parent_tenure_choice` using the current sortition's data (equivalent to `proposed_by.state().data` in v1) and reject with `RejectReason::ReorgNotAllowed` if it returns `false`, before evaluating duplicate-block-found. Add a regression test in `stacks-signer/src/chainstate/tests/v2.rs` analogous to the existing v1 reorg tests to assert `GlobalStateView::check_proposal` rejects a tenure change that reorgs a tenure whose block was produced outside the permitted timing window.

### Proof of Concept
Not independently executable from static analysis alone (requires a running multi-signer devnet with a mix of v1/v2 protocol signers). The root-cause code comparison is directly reproducible by diffing the two validation functions:
- `stacks-signer/src/chainstate/v1.rs:461-504` (contains the `check_parent_tenure_choice` call and `ReorgNotAllowed` rejection)
- `stacks-signer/src/chainstate/v2.rs:306-339` (equivalent function, missing the same call/rejection)

A concrete PoC would: (1) stand up a signer set where some signers run the pre-`GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (v1) code path and others the v2 path; (2) have a miner submit a tenure-change block whose `prev_tenure_consensus_hash` reorgs a tenure that produced a block well outside `first_proposal_burn_block_timing`; (3) observe v1 signers reject with `RejectReason::ReorgNotAllowed` while v2 signers accept and sign, producing a signature-set/verdict split.
