## Title
Wallet Contract `rlp_execute` permanently keeps the caller's attached NEAR deposit even when the requested action needs zero value - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is a `#[payable]` entry point that lets *any* predecessor (a relayer or any other unprivileged account) attach a NEAR deposit when submitting an RLP-encoded Ethereum transaction to be executed on behalf of the wallet owner. The attached deposit is only ever refunded to the caller if the resulting cross-contract promise **fails**. If the promise **succeeds**, the deposit is unconditionally kept by the wallet contract's account balance - even for actions such as `AddKey`/`DeleteKey` (and view-style ETH emulations like `ERC20Balance`/`ERC20TotalSupply`) that structurally require zero value. This mirrors the reported Optimism bug class: a `payable` function that forwards to a code path not requiring the attached value, without returning the unused portion to the sender.

### Finding Description
`rlp_execute` is marked `#[payable]` and forwards `env::attached_deposit()` into `ExecutionContext`: [1](#0-0) [2](#0-1) 

The deposit is captured into a `CallerDeposit` struct, but only tracked for *external* (non-self) predecessors, and it is only ever refunded from within `rlp_execute_callback` when the inner promise fails: [3](#0-2) [4](#0-3) 

However, the actual value moved by the decoded Near action is computed independently from `attached_deposit` - it comes from the ETH `value` field of the RLP transaction plus any inline `yocto_near`, via `Action::try_into_near_action`: [5](#0-4) 

For `AddKey` and `DeleteKey` actions, `Action::value()` is hard-coded to zero, and `action_to_promise` never forwards any deposit for these actions either (it only calls `add_access_key_allowance_with_nonce` / `delete_key`, no `.transfer()`/deposit parameter): [6](#0-5) [7](#0-6) 

So if an external caller (e.g. a relayer account, or any other account that is not the wallet owner) submits an `AddKey`/`DeleteKey` (or a similarly zero-value ETH emulation such as `ERC20Balance`/`ERC20TotalSupply`) request through `rlp_execute` while attaching a NEAR deposit, and the underlying promise succeeds, that deposit is never used by the action and is never refunded - it simply becomes part of the wallet contract account's balance. Refund logic only fires on `PromiseResult::Failed`, not based on whether the deposit was actually needed/consumed by the chosen action.

### Impact Explanation
Any unprivileged account acting as predecessor to `rlp_execute` (typically a relayer, but reachable by any signer since the method has no access restriction beyond the RLP-tx signature check against the *wallet owner's* Ethereum key) that attaches NEAR to a call whose decoded action is `AddKey`, `DeleteKey`, or a read-only ETH emulation query, loses that NEAR permanently to the wallet contract's account balance on success. This is unauthorized value movement/fund loss for the caller - functionally identical to the Optimism report where ETH attached for one code path is silently kept even though the executed path (ERC20) never needed it. There is no legitimate protocol reason for the wallet contract to retain deposits attached for actions that require zero value.

### Likelihood Explanation
Reachable directly from a single unprivileged NEAR transaction/contract call: any account can call `rlp_execute` on any eth-implicit wallet contract with an attached deposit and a validly-signed RLP transaction encoding an `AddKey`/`DeleteKey`/query action. No special privileges, validator status, or multi-step attack are required - only an accidental or naive relayer/caller attaching a deposit for a zero-value action triggers the loss, and it is deterministic given `PromiseResult::Successful`.

### Recommendation
Refund the caller's unused/unneeded attached deposit unconditionally when the action does not consume it, rather than only refunding on `PromiseResult::Failed`. Concretely, compute the amount actually forwarded to the target account (`Action::value()` plus any deposit consumed in `action_to_promise`) and, in `rlp_execute_callback` (and in the `Successful` branch), refund `attached_deposit - amount_actually_used` back to the tracked `CallerDeposit.account_id`, instead of only tracking/refunding on failure.

### Proof of Concept
1. Deploy/target an eth-implicit `WalletContract` account `W`.
2. As any account `C` (external, `C != W`), sign an RLP Ethereum transaction with `W`'s private key that ABI-encodes a `DeleteKey` (or `AddKey`) action targeting `W` itself (a `SelfNearNativeAction`), with the wallet's correct `nonce`.
3. Call `C.rlp_execute(target=W, tx_bytes_b64=...)` attaching e.g. 5 NEAR (`#[payable]`).
4. `inner_rlp_execute` builds `CallerDeposit { account_id: C, yocto_near: 5 NEAR }` (per `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs:180-191`), but the resulting promise is `Promise::new(W).delete_key(pk)` which uses none of the attached deposit (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:497-499`).
5. The `delete_key` action succeeds → `rlp_execute_callback` receives `PromiseResult::Successful` → no refund branch is taken (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:313-316`).
6. Result: `C`'s 5 NEAR is now part of `W`'s account balance, never returned to `C`, despite the executed action requiring zero value.
