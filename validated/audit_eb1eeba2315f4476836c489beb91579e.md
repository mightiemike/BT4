### Title
Unrandomized top-level bucket routing in the accounts-index `BucketMap` lets an attacker grind pubkeys to force disproportionate CPU/storage load on a single bucket - ([File: bucket_map/src/bucket_map.rs])

### Summary
`BucketMap::bucket_ix` selects the top-level shard (bucket) for a pubkey using an unsalted, purely deterministic function of the raw pubkey bytes, while the intra-bucket hash function (`Bucket::bucket_index_ix`) is explicitly randomized per-process specifically to prevent an attacker from clustering keys. Because Solana account addresses/PDAs are attacker-choosable via cheap "vanity" grinding, an unprivileged user can create arbitrarily many accounts whose pubkeys route to the same top-level bucket, forcing that one on-disk/in-mem bucket to grow and be scanned far more than its peers — a disproportionate storage/CPU cost DoS vector, directly analogous to the report's "single malicious actor forces a shared resource path to behave adversarially for everyone."

### Finding Description
`BucketMap::bucket_ix` computes the bucket for a pubkey purely from the raw key bytes with no randomization: [1](#0-0) 

Contrast this with the per-bucket index slot selection, `Bucket::bucket_index_ix`, whose author comment states the randomization exists precisely to stop this class of attack: [2](#0-1) 

`bucket_ix` takes the top `max_buckets_pow2` bits of the big-endian interpretation of the pubkey's first 8 bytes to pick a bucket, deterministically and without any per-process salt. Every account created on-chain (token mints, associated token accounts, PDAs, or freshly generated keypairs used as account addresses) has a pubkey that is either fully attacker-chosen (keypair grinding) or attacker-influenced (PDA seed grinding, both of which are permissionless and inexpensive). By grinding pubkeys whose leading bits match, an attacker can direct an arbitrary number of accounts into a single bucket while every other validator's bucket assignment for the same accounts is identical (since the routing bits are not randomized per node, unlike the intra-bucket hash), guaranteeing the skew is consistently reproduced across the whole cluster, not just one node.

Once accounts are concentrated in one bucket, all subsequent inserts/updates/reads for those pubkeys go through `BucketApi`/`Bucket` operations scoped to that single bucket: `Bucket::try_write` → `bucket_create_key`/`batch_insert_non_duplicates_internal`, which search up to `max_search` (default `MAX_SEARCH_DEFAULT = 32`) slots and, on failure, trigger `grow_index`, an O(n) full copy-and-rehash of every live entry in that bucket into a larger allocation: [3](#0-2) [4](#0-3) 

Because bucket sizing/growth is per-bucket and the routing key cannot be changed after the fact, the attacker's targeted bucket alone bears the repeated resize cost, disk allocation growth, and larger scan/search times, while sibling buckets (and the rest of the accounts index) remain lightly loaded. This is a structural imbalance attack against the accounts index's sharding scheme — the same bug class as the external report, where a single adversarial party (the malicious "creator", here the pubkey-grinding attacker) can unilaterally force a shared subsystem meant to serve everyone fairly (the fee-transfer path / the bucket-sharded index) into a degraded, attacker-controlled state.

### Impact Explanation
A skewed bucket incurs repeated O(bucket-size) `grow_index`/`grow_data` rehashes, larger mmap allocations, and longer linear searches (`max_search` scans) for every account routed to it, compared to a uniformly-distributed load. Since bucket-to-account routing is the same deterministic function on every validator, the imbalance is reproduced cluster-wide rather than being isolated to one node, producing disproportionate and sustained CPU and disk usage on the accounts-index shard for the price of ordinary permissionless account/PDA creation.

### Likelihood Explanation
Likelihood is high in the sense that pubkey/PDA grinding is a normal, permissionless, and computationally cheap operation already used for vanity addresses; no special privilege, validator role, or malicious snapshot is required — only the ability to submit transactions that create accounts with chosen or influenced addresses.

### Recommendation
Apply the same defense used for `bucket_index_ix` to the top-level bucket selection in `bucket_ix`: mix a per-process (or per-cluster-agreed, if determinism is required) random/salt value into the bucket-routing hash instead of using the raw pubkey bytes directly, so an attacker cannot pre-compute which bucket a grindable pubkey will land in.

### Proof of Concept
Not independently verified against a live validator in this review; the mechanism is demonstrated by static code inspection: `bucket_ix` (bucket_map.rs:192-200) uses `read_be_u64(key.as_ref())` with no salt, while `bucket_index_ix` (bucket.rs:822-828) explicitly adds `random` seeds "to make it hard for an attacker to deterministically cause all the pubkeys to land in the same location," confirming the top-level routing lacks the mitigation applied one layer down. A concrete PoC would require pubkey/PDA grinding tooling to generate N keys sharing the top `max_buckets_pow2` bits and observing `BucketMapStats` (`resizes`, `failed_resizes`, `resize_us`, `max_size`) diverge sharply for that bucket versus others under the same total account count — this dynamic validation was not run as part of this review.

    /// Get the bucket index for Pubkey `key`
    pub fn bucket_ix(&self, key: &Pubkey) -> usize {
        if self.max_buckets_pow2 > 0 {
            let location = read_be_u64(key.as_ref());
            (location >> (u64::BITS - self.max_buckets_pow2 as u32)) as usize
        } else {
            0
        }
    }

    pub fn grow_index(&self, mut current_capacity: u64) {
        if self.index.contents.capacity() == current_capacity {
            // make sure to grow to at least % more than the anticipated size
            // The indexing algorithm expects to require some over-allocation.
            let anticipated_size = self.anticipated_size * 140 / 100;
            let mut m = Measure::start("grow_index");
            //debug!("GROW_INDEX: {}", current_capacity_pow2);
            let mut count = 0;
            loop {
                count += 1;
                // grow relative to the current capacity
                let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
                let (mut index, file_name) = BucketStorage::new_with_capacity(
                    Arc::clone(&self.drives),
                    1,
                    std::mem::size_of::<IndexEntry<T>>() as u64,
                    Capacity::Actual(new_capacity),
                    self.index.max_search,
                    Arc::clone(&self.stats.index),
                    Arc::clone(&self.index.count),
                );
                // index may have allocated something larger than we asked for,
                // so, in case we fail to reindex into this larger size, grow from this size next iteration.
                current_capacity = index.capacity();
                let mut valid = true;
                for ix in 0..self.index.capacity() {
                    if !self.index.is_free(ix) {
                        let elem: &IndexEntry<T> = self.index.get(ix);
                        let new_ix =
                            Self::bucket_create_key(&mut index, &elem.key, self.random, true);
                        if new_ix.is_err() {
                            valid = false;
                            break;
                        }
                        let new_ix = new_ix.unwrap();
                        let new_elem: &mut IndexEntry<T> = index.get_mut(new_ix);
                        *new_elem = *elem;
                        index.copying_entry(new_ix, &self.index, ix);
                    }
                }
                if valid {
                    self.stats.index.update_max_size(index.capacity());
                    let mut items = self.reallocated.items.lock().unwrap();
                    items.index = Some(index);
                    self.reallocated.add_reallocation();
                    self.restartable_bucket.set_file(file_name, self.random);
                    break;
                }
            }
            m.stop();
            if count > 1 {
                self.stats
                    .index
                    .failed_resizes
                    .fetch_add(count - 1, Ordering::Relaxed);
            }
            self.stats.index.resizes.fetch_add(1, Ordering::Relaxed);
            self.stats
                .index
                .resize_us
                .fetch_add(m.as_us(), Ordering::Relaxed);
        }
    }

    fn bucket_index_ix(key: &Pubkey, random: u64) -> u64 {
        // the locally generated random will make it hard for an attacker
        // to deterministically cause all the pubkeys to land in the same
        // location in any bucket on all validators
        let hasher_builder = ahash::RandomState::with_seeds(random, random, random, random);
        hasher_builder.hash_one(key)
    }
