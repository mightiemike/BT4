### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay-verify tooling to accept divergent state roots - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the authoritative comparator used by replay/verification tooling (`db-tool`'s `replay_on_archive`, `aptos-debugger`, chunk executor, CLI commands) to confirm that a locally re-executed `TransactionOutput` matches a `TransactionInfo` retrieved from an authenticated source (backup/archive). The function validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` carried by the same `TransactionInfo`, as acknowledged in its own TODO comment.

### Finding Description
`TransactionInfo` carries multiple root-hash fields binding a transaction's execution result to the ledger's state trees: `state_change_hash` (write-set hash), `event_root_hash`, and separately `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` (state Merkle roots computed periodically, e.g. per block) [1](#0-0) . These checkpoint hashes are exactly the values that bind a version to its Jellyfish Merkle / position-state root, and are what `TransactionAccumulatorProof`/`TransactionInfoWithProof::verify` ultimately authenticate against a signed `LedgerInfo` [2](#0-1) .

`ensure_match_transaction_info` is supposed to be the local-execution-vs-authenticated-info gate: it checks `status`, `gas_used`, `write_set_hash == state_change_hash`, and `event_root_hash`, but never touches `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [3](#0-2) . The function's own comment states this directly: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [4](#0-3) .

This function is used by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes transactions pulled from a backup and calls `ensure_match_transaction_info` against the `expected_txn_infos` recovered from the (presumably authenticated) backup manifest to decide whether replay "succeeded" [5](#0-4) . Because the state/hot-state/position checkpoint hashes are not compared, a chain where local re-execution produces a *different* state Merkle root than the archived/authenticated `TransactionInfo` (while write-set bytes and events happen to match, or coincidentally on transactions where checkpoint fields are the only diverging signal) will still be reported as "no error" by this specific check.

### Impact Explanation
This is a real, code-acknowledged gap: `ensure_match_transaction_info` is the primary invariant-check function binding VM re-execution output to the authenticated `TransactionInfo` used across `aptos-debugger`, CLI `verify` commands, and `chunk_executor`. If the state-checkpoint root ever diverges from local execution (e.g. state-sync/restore corruption, a bug in JMT construction, or divergence introduced by future feature flags like `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), the archive-replay verification tool used to detect exactly such divergences would silently pass. That undermines the primary safety net for detecting non-deterministic/incorrect state commitment across the fleet — a proof-integrity tooling gap rather than a live consensus-safety bypass.

### Likelihood Explanation
The gap is deterministic and always present (not merely a corner case) — every call to `ensure_match_transaction_info` skips checkpoint-hash comparison, so any divergence that happens to leave write-set bytes/events/gas/status matching (or where the divergence occurs specifically in state-tree construction rather than in the write set contents) is undetectable by this function. I could not fully confirm within tool budget how `chunk_executor` and `aptos-debugger` use this function's result (i.e., whether they have independent, redundant checkpoint-hash verification elsewhere covering the same guarantee) — this is a caveat on true end-to-end impact that would need further code tracing.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed output and the expected `TransactionInfo` whenever these fields are `Some` in the expected info, failing loudly on mismatch, consistent with how `state_change_hash` and `event_root_hash` are already validated.

### Proof of Concept
1. Author/obtain a `TransactionInfo` (as pulled from backup/archive) whose `state_checkpoint_hash` differs from what local re-execution of the corresponding transaction would produce, while write set bytes, events, gas, and status remain identical (or verify same write bytes with a state-tree construction bug).
2. Run `db-tool replay-on-archive` (or any caller of `ensure_match_transaction_info`) over that version range.
3. Observe `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` returns `Ok(None)` (no failure reported) despite the state Merkle root having diverged, because `ensure_match_transaction_info` never inspects `state_checkpoint_hash` [3](#0-2) [5](#0-4) .

**Uncertainty/limitations:** I was unable to fully trace whether `execution/executor/src/chunk_executor/mod.rs` or `aptos-move/aptos-debugger/src/aptos_debugger.rs` perform independent checkpoint-hash validation elsewhere before or after calling `ensure_match_transaction_info`, which could reduce practical severity for those callers specifically. This should be checked in a follow-up session with full tool access before treating this as fully exploitable end-to-end.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
