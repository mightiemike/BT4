### Title
Panic-inducing `.unwrap()` on `receiver_shard_id()` for stale `GlobalContractDistribution` receipts after resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
This is a valid nearcore analog to the KVM CVE-2026-72284 bug class: a "pending" piece of protocol state (a queued/delayed receipt with an embedded shard reference) is trusted as still valid at consumption time, but the underlying condition (the shard layout) can have changed since the receipt was queued, and the consuming code unconditionally unwraps the now-possibly-failing lookup, causing a deterministic node panic (chunk-application halt) reachable purely from a normal user transaction (a global contract deployment) combined with the protocol's own resharding schedule.

### Finding Description
`DelayedReceiptQueueWrapper::receipt_filter_fn` in [1](#0-0)  computes the shard-id of a delayed receipt via `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()`. For `GlobalContractDistribution` receipts, `receiver_shard_id` (in `core/primitives/src/receipt.rs`) resolves the receipt's `target_shard()` against the *current* shard layout; if the stored `target_shard` no longer exists in the current layout, it falls back to `shard_layout.resolve_to_current_shard(target_shard)`, and only returns `Ok` if a mapping is found — otherwise it returns `Err(EpochError::ShardingError(...))` [2](#0-1) .

The caller (`receipt_filter_fn`, called from `pop()` at [3](#0-2) ) discards the `Result` with `.unwrap()`, so any case where `resolve_to_current_shard` cannot find a mapping — e.g., after a receipt has been delayed across resharding events deep enough that split-history tracking cannot map the stale `target_shard` back to a live shard — will panic the runtime `apply()` call while draining the delayed-receipt queue, which every honest validator/chunk-producer executes deterministically. This mirrors the KVM bug exactly: an internal "pending work item" (PV-EOI service request / delayed receipt) is validated against a *stale* precondition, and the consuming code asserts/unwraps success instead of gracefully skipping or erroring, turning normal state divergence over time into a `BUG`/panic.

Repo evidence that this exact scenario is a live concern is a dedicated regression test, `test_stale_global_contract_distribution_after_double_resharding`, which deploys a global contract, force-saturates compute so the resulting `GlobalContractDistribution` receipt sits in the delayed queue across **two** resharding events, and explicitly documents: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations."* [4](#0-3) 

While `receiver_shard_id` itself was hardened to return an `Err` (via `resolve_to_current_shard`) rather than panicking outright for a single resharding step, the `.unwrap()` in `receipt_filter_fn` at `congestion_control.rs:876` still converts any such `Err` into an unconditional panic. Whether `resolve_to_current_shard`'s split-history tracking is guaranteed complete for arbitrarily many chained resharding events (more than the two exercised by the existing test) could not be fully verified from the index alone — the `ShardLayout` split-history implementation in `core/primitives/src/shard_layout/v3.rs` was located but its full body was not retrieved in this session, so the exact bound on how many resharding generations `resolve_to_current_shard` can walk back through is unconfirmed.

### Impact Explanation
If `resolve_to_current_shard` fails to map a stale `target_shard` (e.g., after resharding history exceeds whatever depth is tracked, or after other edge cases in shard-layout evolution), every validator applying the chunk that drains that delayed receipt panics simultaneously, since delayed-receipt processing is part of the deterministic `Runtime::apply` path executed by all nodes. This is a chain-halting condition (transaction-triggered halt via a global contract deployment transaction plus the network's own resharding schedule), which the rules classify as in-scope (state-root divergence / chain halt from a reachable, non-privileged action).

### Likelihood Explanation
The receipt is created by any unprivileged account issuing a `DeployGlobalContract` action (fully within the "single submitted transaction" reachability requirement). The rest of the trigger — the receipt getting delayed across multiple resharding boundaries — depends on the network's dynamic-resharding schedule and congestion state, which an attacker does not directly control but can influence indirectly (e.g., by saturating compute on the target shard to keep the receipt in the delayed queue, similar to how the existing test forces the condition). The existence of a dedicated test file exercising exactly two resharding generations suggests the nearcore team identified this failure mode as realistic enough to guard against, but the guard is only proven for two generations, and the sink (`receipt_filter_fn`) still unwraps rather than propagating the error for any generation count the mapping logic cannot resolve.

### Recommendation
Change `receipt_filter_fn` (and its caller `pop()`) in `runtime/runtime/src/congestion_control.rs` to propagate `receiver_shard_id`'s `Result` as a `RuntimeError`/`StorageError::StorageInconsistentState` instead of `.unwrap()`ing, so an unresolvable stale shard reference produces a handled error path rather than a panic. Additionally, verify (or extend) `ShardLayout::resolve_to_current_shard`'s split-history bookkeeping in `core/primitives/src/shard_layout/v3.rs` to guarantee resolution across an unbounded number of chained resharding events, and extend the existing `test_stale_global_contract_distribution_after_double_resharding` test to cover three or more sequential resharding generations to confirm the fix holds beyond the two-generation case currently tested.

### Proof of Concept
1. Deploy a contract on account `A` on shard `S0` of the base shard layout.
2. Submit a `DeployGlobalContract` transaction from `A`, generating a `GlobalContractDistribution` receipt with `target_shard = S0`.
3. Saturate compute on `S0` every block (e.g., repeated expensive function calls) so the distribution receipt is pushed into, and remains in, the delayed-receipt queue.
4. Force/await dynamic resharding to split `S0` and then split one of its children again, so two resharding generations elapse while the receipt is still delayed (as done in `test_stale_global_contract_distribution_after_double_resharding` at [5](#0-4) ).
5. Stop saturating and let the delayed queue drain; if `resolve_to_current_shard` cannot map the doubly-stale `target_shard`, `receipt_filter_fn`'s `.unwrap()` at `congestion_control.rs:876` panics, halting chunk application for every honest validator on that shard.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");
