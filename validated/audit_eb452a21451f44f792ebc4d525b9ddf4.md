### Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, letting replay-verify tooling silently accept a diverged state/hot-state/position-state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by offline auditing tools (`replay_on_archive`, `aptos-debugger`, `cli`) to confirm that a freshly re-executed transaction output matches the `TransactionInfo` that was actually committed to the ledger/accumulator on mainnet. The function validates status, gas used, write-set hash, and event-root hash, but explicitly and intentionally omits comparison of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the exact fields that bind a `TransactionInfo` to the authenticated state/JMT root at that version.

### Finding Description
In `types/src/transaction/mod.rs`, `TransactionInfo::builder_v1` records three checkpoint-hash fields that commit to the state Merkle root (and the newer "hot state" / position-state roots) at a checkpoint version: [1](#0-0) 

These are exactly the fields that `execution/executor/src/workflow/do_ledger_update.rs` populates from `state_checkpoint_output.state_checkpoint_hashes` / `hot_state_checkpoint_hashes` / `position_state_checkpoint_hashes`, and they feed the accumulator leaf hash that is ultimately certified by validator signatures on the `LedgerInfo` root: [2](#0-1) 

However, the only function that independently re-derives a `TransactionInfo` from freshly executed output and compares it against the historically committed one — `ensure_match_transaction_info` — never checks these three fields: [3](#0-2) 

The comment left in the code confirms this is a known, acknowledged gap rather than an oversight discovered here: [4](#0-3) 

This comparator is the sole verification step used by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes historical transactions from backup and calls `ensure_match_transaction_info` per transaction to flag any divergence from the archived/committed `TransactionInfo`: [5](#0-4) 

Because the checkpoint-hash fields are skipped, if a local re-execution (running on new code, a different DB implementation, or a future hard fork) produces a different state root, hot-state root, or position-state root than what was actually committed and signed on mainnet, `replay_on_archive` (and the equivalent debugger/CLI paths) will report **success** instead of surfacing the divergence.

### Impact Explanation
This falls squarely under the accepted "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Authenticated API or state-view output bound to the wrong version, object, or proof context" categories: the authenticated state-checkpoint root is precisely the value auditors rely on `replay_on_archive`/`aptos-debugger` to validate against the historical, consensus-certified ledger. A state-divergence bug elsewhere in the VM or storage layer that corrupts only the state/hot-state/position-state checkpoint hash (without touching write-set or event hashes) would go completely undetected by this tool, defeating its purpose as the primary safety net for catching consensus-breaking non-determinism before/after upgrades. This is a genuine gap in a security-relevant integrity check, not merely cosmetic.

### Likelihood Explanation
The bug is deterministic and always present — it is not a heisenbug or timing-dependent — any state-checkpoint-only divergence trivially bypasses the check on every invocation of the three call sites. However, the *impact* is contingent on there being a genuine, independent VM/storage bug that produces a different checkpoint root while still preserving an identical write-set hash and event-root hash. This makes it a detection/verification gap (defense-in-depth loss) rather than a live corruption of mainnet state by itself: this code path runs in offline auditing tools, not in the online consensus/commit path (`do_ledger_update.rs`, `aptosdb_writer.rs`), so it does not directly corrupt committed data — it can only mask an existing divergence from operators who rely on the tool to catch it.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the freshly computed values whenever the transaction is a checkpoint (matching the comment's own suggested fix), gating on the `TRANSACTION_INFO_V1` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flags as needed so the comparison activates once the fields are populated on all versions being replayed.

### Proof of Concept
Not applicable as a runnable PoC per the source report's own note — the vulnerability is provable by direct code reading: `ensure_match_transaction_info` in `types/src/transaction/mod.rs:2139-2204` never reads or asserts on `txn_info`'s `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` accessors, while `do_ledger_update.rs:95-121` shows these are populated fields of `TransactionInfo::V1` used to build the accumulator leaf/root that consensus signs. Any test constructing a `TransactionOutput` whose committed hot-state/position-state root differs from an `expected_txn_info`'s corresponding field, holding write-set and event hashes constant, will pass `ensure_match_transaction_info` without error, confirming the gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
