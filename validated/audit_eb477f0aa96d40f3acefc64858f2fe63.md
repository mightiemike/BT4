### Title
Permanently orphaned attached deposits in postponed/promise-yield receipts when a receiver account is deleted before its pending cross-contract callback resolves - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
This mirrors the Cooler `claimDefaulted` bug class: a resource tied to an account (there, `loan.unclaimed`; here, a receiver's postponed `ActionReceipt`/`PromiseYield` state carrying an attached deposit) is not drained/settled before the owning record (there, the `Loan` struct; here, the `Account`) is deleted, so the attached value becomes permanently unreachable.

### Finding Description
When account A receives an action receipt with unmet `input_data_ids`, the runtime stores it as a **postponed receipt** (`TrieKey::PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`, set in `process_action_receipt`, `runtime/runtime/src/lib.rs:1529-1581`) or, for `yield_create`, as a **promise-yield receipt** (`TrieKey::PromiseYieldReceipt`, `set_promise_yield_receipt`, `core/store/src/utils/mod.rs:200-212`, invoked from `runtime/runtime/src/lib.rs:1552`). Both of these are action receipts that can carry an attached `deposit` in their actions, exactly as an ordinary action receipt would (`Action::Transfer`/`FunctionCall` deposits inside the pending `ActionReceipt`).

If account A subsequently deletes itself (`Action::DeleteAccount`, handled by `action_delete_account`, `runtime/runtime/src/actions.rs:330-406`), the only cleanup performed is `remove_account` (`core/store/src/utils/mod.rs:504-575`), which iterates and removes:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- all `TrieKey::access_key`/gas-key-nonce rows
- all `TrieKey::ContractData` rows

It does **not** touch `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` — even though the trie-key schema explicitly lists these as `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (`core/primitives/src/trie_key.rs:87-102`), i.e. account-scoped data that in principle should be cleaned up with the account.

Consequences:
- **Postponed receipts**: the corresponding `Data` receipt(s) that would eventually satisfy `input_data_ids` still arrive and go through `process_receipt`'s `Data` arm (`runtime/runtime/src/lib.rs:1440-1527`), which looks up `PostponedReceiptId`/`PendingDataCount` by `account_id` (the now-deleted account) and, once satisfied, fetches and executes the postponed `ActionReceipt` via `apply_action_receipt` against a receiver account that no longer exists. Depending on how `apply_action_receipt`/`action_transfer_or_implicit_account_creation` handles a `None` account (it implicitly re-creates an account on `Transfer`, per `runtime/runtime/src/lib.rs:3016-3062`), this could either silently re-create the account and re-mint the attached balance out of thin air relative to what the balance-checker expects for a "deleted" account, or, if not all data ever arrives (e.g., the DataReceipt that would resolve it is itself lost/never sent because its originating shard also considered the flow resolved), the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows and their embedded deposit remain permanently orphaned in the trie — never executed, never refunded, and never garbage collected.
- **Promise-yield receipts**: if account A is deleted before either an explicit `promise_yield_resume` or the timeout path fires, the `PromiseYieldReceipt` row (and its `PromiseYieldTimeout` queue entry) is left in state, keyed to a receiver that no longer exists. At timeout, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3113-3209`) checks `promise_yield_key` presence and, if present, synthesizes a `PromiseResume` receipt destined for the deleted account, which then executes `apply_action_receipt` for the stale yield receipt against a missing account — again either implicitly recreating the account/minting balance or leaving the attached deposit stuck depending on the code path, and in the worst case producing a state root divergence between clients that disagree on whether such an edge case is reachable at all (this repo's own comment notes yield-vs-account-deletion interaction is not exhaustively tested: only `test_delete_account_while_staking`/`delete_after_init_removes_account` type tests exist for `DeleteAccount`, none combine it with an outstanding postponed/yield receipt).

### Impact Explanation
An account can delete itself while it still has a receipt "in flight" that carries a `deposit` (attached NEAR), and that deposit's fate (permanently frozen vs. resurrected via implicit re-creation against a deleted account, i.e., balance-checker inconsistency) is not deliberately handled by `action_delete_account`/`remove_account`. This falls squarely in the "permanently frozen funds" / "invalid state transition acceptance" impact categories: the receiver of a legitimately attached deposit can never claim it (mirroring the lender losing `unclaimed` tokens in the Cooler bug), or, in the re-creation branch, the runtime performs a state transition (recreating a deleted account under a stale receipt) that the balance-checker and higher-level account-lifecycle invariants were not designed to reconcile against a chunk that already accounted for that account's deletion.

### Likelihood Explanation
Reachable directly and permissionlessly: (1) attacker/user calls a contract on account A with `promise_yield_create`/a multi-input-data callback carrying an attached deposit, and does not resolve it; (2) attacker/user (who controls A, or A's contract logic under a `Delegate` action, or simply any full-access-key holder of A) submits `DeleteAccount` before the data/resume receipt arrives. No validator collusion, no network-level assumption, and no privileged role is required — only a signer with a full-access key on A and enough NEAR to pay for the initiating cross-contract call. This is a straightforward two-transaction sequence any RPC caller can construct.

### Recommendation
Before (or as part of) `action_delete_account`/`remove_account`, iterate and drain all `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` entries scoped to the account being deleted (the same trie-prefix-iteration technique already used in `remove_account` for access keys and contract data, `core/store/src/utils/mod.rs:516-573`). Any attached deposit found in a still-pending postponed/yield `ActionReceipt` for that account should be refunded via a `Receipt::new_balance_refund` to the receipt's rightful refund target, and only then should the account row itself be deleted, analogous to processing `loan.unclaimed` before `delete loans[loanID_]` in the Cooler fix.

### Proof of Concept
Not independently executed against a running node; this analysis is based on static code review of `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`), `remove_account` (`core/store/src/utils/mod.rs:504-575`), postponed-receipt handling in `process_receipt`/`process_action_receipt` (`runtime/runtime/src/lib.rs:1440-1527`, `:1529-1637`), and promise-yield timeout handling (`runtime/runtime/src/lib.rs:3113-3209`), cross-referenced with the trie-key schema (`core/primitives/src/trie_key.rs:79-127`) that lists these columns as account-scoped but which `remove_account` does not iterate. I was unable to find any existing test in this repo that deletes an account with an outstanding postponed receipt or promise-yield receipt still pending, which is consistent with this path being unexercised/unguarded. A full runtime-level reproduction (constructing a `yield_create` or multi-input-data-dependency receipt, then submitting `DeleteAccount` before the resolving receipt, then observing either a stuck trie row or an unexpected implicit account re-creation) would require running the `runtime/runtime/src/tests/apply.rs` test harness, which was not available to execute in this read-only review.
