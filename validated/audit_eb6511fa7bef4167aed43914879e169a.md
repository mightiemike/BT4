## Analysis Result

### Title
Missing `supportUnfreezeDelay` Feature-Flag Check in `WithdrawExpireUnfreezeProcessor` (TVM Native Contract Path) - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java`)

### Summary
The Superfluid bug is a missing state-gating check (`unlockAvailable` modifier) on two functions, allowing users to bypass a committee/owner-controlled feature toggle. The java-tron analog is the `WithdrawExpireUnfreezeProcessor` used by the `WITHDRAWEXPIREUNFREEZE` TVM opcode, which omits the `supportUnfreezeDelay()` committee-feature-flag check that its sibling transaction-level actuator (`WithdrawExpireUnfreezeActuator`) explicitly enforces.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` gates the entire "withdraw expired unfreeze" functionality behind a committee-controlled dynamic property: [1](#0-0) 

```java
if (!dynamicStore.supportUnfreezeDelay()) {
  throw new ContractValidateException("Not support WithdrawExpireUnfreeze transaction,"
      + " need to be opened by the committee");
}
```

This is the same feature that is invoked from the TVM through the `WITHDRAWEXPIREUNFREEZE` opcode, which is wired through `OperationActions.withdrawExpireUnfreezeAction()` → `Program.withdrawExpireUnfreeze()` → `WithdrawExpireUnfreezeProcessor.validate()`/`execute()`. [2](#0-1) [3](#0-2) 

However, `WithdrawExpireUnfreezeProcessor.validate()` performs address, existence, balance-overflow, and amount checks but never checks `dynamicStore.supportUnfreezeDelay()`: [4](#0-3) 

The only gate on the opcode itself is `VMConfig::allowTvmFreezeV2`, which is a distinct, broader proposal controlling FreezeV2 opcode availability in general, not the specific unfreeze-delay withdrawal permission: [5](#0-4) 

Because `allowTvmFreezeV2` and `supportUnfreezeDelay` are separate committee proposals, it is possible for `allowTvmFreezeV2` to be active while `supportUnfreezeDelay` is still disabled by the committee — in that state, direct transactions via `WithdrawExpireUnfreezeActuator` are correctly blocked, but a smart contract can still invoke the `WITHDRAWEXPIREUNFREEZE` opcode to withdraw expired unfrozen balance, since `WithdrawExpireUnfreezeProcessor` never checks the flag.

### Impact Explanation
This breaks the intended committee-controlled activation/deactivation semantics for the unfreeze-delay withdrawal feature: a smart-contract-based caller can invoke functionality the committee has explicitly not yet enabled, via a divergent code path between the actuator (transaction) and native-contract (TVM opcode) implementations of the same feature. This is a state-gating/invalid-state divergence issue rather than a direct fund-theft bug, since the balance being withdrawn is legitimately the caller's own already-expired unfrozen balance; the concrete harm is bypass of the governance-controlled feature flag and inconsistent contract-vs-transaction behavior.

### Likelihood Explanation
Exploitability requires only that `allowTvmFreezeV2` be enabled while `supportUnfreezeDelay` remains disabled — an achievable and plausible rollout ordering for two independently-managed committee proposals. Any account with expired `UnFreezeV2` entries could call the opcode from a contract to trigger this divergence without any privileged role.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check to `WithdrawExpireUnfreezeProcessor.validate()` that already exists in `WithdrawExpireUnfreezeActuator.validate()`, so both execution paths enforce the same committee-controlled feature-gating semantics.

### Proof of Concept
1. Committee enables `allowTvmFreezeV2` (activating FreezeV2 opcodes) but leaves `supportUnfreezeDelay` disabled.
2. A user accumulates entries in `UnfrozenV2List` with expired `unfreezeExpireTime` (via `UnfreezeBalanceV2Actuator`, unaffected by `supportUnfreezeDelay`).
3. Attempting `WithdrawExpireUnfreezeContract` via the normal transaction path fails with "Not support WithdrawExpireUnfreeze transaction... need to be opened by the committee" per `WithdrawExpireUnfreezeActuator.validate()`.
4. The same user deploys/calls a smart contract that executes the `WITHDRAWEXPIREUNFREEZE` opcode; `WithdrawExpireUnfreezeProcessor.validate()`/`execute()` runs without any `supportUnfreezeDelay` check and successfully credits the expired unfrozen balance back to the account, bypassing the committee's feature gate.

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
  }
