### Title
Truncated liquidity-index accrual permanently lost when only the borrow index changes and `last-update` advances - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and identical logic in the other vault contracts)

### Summary
`accrue()` recomputes the borrow index and the liquidity index from the elapsed time since `last-update`, but only advances `last-update` when *either* index actually changed. Because the borrow-index multiplier rounds **up** and the liquidity-index multiplier rounds **down**, a short elapsed period can produce a case where the borrow index changes (so `last-update` is advanced) while the liquidity index's fractional increase is truncated to zero (so `lindex` does not change). Once `last-update` moves forward, that period's truncated depositor-yield fraction can never be recovered in a future accrual, because the next call only integrates time from the new `last-update` onward.

### Finding Description
`next-index` (borrow) and `next-liquidity-index` (liquidity) both derive a `multiplier` from `calc-multiplier-delta`, which is called with `round-up=true` for the borrow index and `round-up=false` for the liquidity index: [1](#0-0) 

`calc-multiplier-delta` itself performs a `mul-div-up`/`mul-div-down` truncating division over `rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS`: [2](#0-1) 

In `accrue()`, the two indexes are updated independently, and `last-update` is advanced if *either* one changed: [3](#0-2) 

Because the liquidity rate is derived by scaling the borrow rate down by utilization and the reserve factor (`calc-liquidity-rate`), it is strictly smaller than the borrow rate: [4](#0-3) 

For a short `time-delta`, it is possible for the (larger, round-up) borrow-index multiplier to tick over `INDEX-PRECISION` while the (smaller, round-down) liquidity-index multiplier truncates to exactly `INDEX-PRECISION` (no change). Since `idx != next` is true, `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))` evaluates true and `last-update` is set to `stacks-block-time`, discarding the elapsed period entirely from the liquidity-index calculation. The next `accrue()` call computes `time-delta` from this new, advanced `last-update`, so the fractional liquidity-index growth that should have accrued during the discarded interval is permanently lost — it can never be folded into a subsequent calculation.

`accrue()` is invoked on essentially every state-changing vault operation (deposit, redeem, borrow, repay, flashloan, etc. — 20 call sites in this file), so frequent user- or bot-triggered calls with short inter-call time deltas make this truncation-then-advance sequence realistic and repeatable, not a one-off edge case: [5](#0-4) 

This is the same root cause described in the external report: a value that should accrue continuously is computed via truncating division tied to an elapsed-time window, and a state variable (`last-update`, analogous to Locke.sol's checkpoint) is advanced based on whether *some* rounded quantity changed, silently discarding the sub-precision remainder rather than carrying it to the next period. Every vault contract in the repo (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdh`, `v0-vault-ststxbtc`) shares the identical `accrue`/`next-index`/`next-liquidity-index` pattern.

### Impact Explanation
The lost fraction is depositor yield (liquidity index growth) that is deterministically discarded rather than merely delayed, because the checkpoint (`last-update`) that would allow it to be re-included has already moved past the interval in which it accrued. Repeated frequent activity (normal user transactions, or a bot deliberately calling any state-changing entry point in quick succession) compounds this loss across many small intervals. This is a permanent loss of unclaimed yield for zft (vault share) holders, matching the "High" impact class (permanent freezing/loss of unclaimed yield).

### Likelihood Explanation
Likelihood is moderate to high in busy markets: any two calls to a state-changing vault function separated by a short time span (common on Stacks given block-time granularity) can trigger this divergence between the round-up borrow multiplier and round-down liquidity multiplier. No privileged access or malicious setup is required — normal transaction traffic on an active vault is sufficient, and an attacker (or even non-malicious high-frequency user activity) can amplify it by repeatedly calling low-cost state-changing entry points.

### Recommendation
Do not gate `last-update` advancement on whether the rounded index values actually changed. Always advance `last-update` to `stacks-block-time` whenever accrual logic runs (unless paused), and instead track any truncation remainder explicitly (e.g., accumulate the un-applied fractional interest and carry it into the next period's `time-delta`/rate computation) so no period's yield can be silently dropped from the liquidity index.

### Proof of Concept
1. Assume a vault where `total-borrowed`/`principal-scaled` is non-trivial and `utilization` combined with `fee-reserve` scales the liquidity rate to a noticeably smaller value than the borrow rate (typical steady-state condition), per `calc-liquidity-rate`: [4](#0-3) 
2. Choose (or wait for) a short `time-delta = stacks-block-time - last-update` such that:
   - `calc-multiplier-delta(rate, time-delta, true)` for the borrow index rounds **up** to a value `> INDEX-PRECISION`, so `idx != next`.
   - `calc-multiplier-delta(liquidity-rate, time-delta, false)` for the liquidity index rounds **down** to exactly `INDEX-PRECISION`, so `lidx == nliq`.
3. Call any state-changing entry point that triggers `accrue()` (e.g., `deposit`) at this `time-delta`.
4. Inside `accrue()`: `var-set index next` executes (borrow index updates), `var-set lindex nliq` is skipped (no change), but because `idx != next`, the `or` condition is true and `var-set last-update stacks-block-time` executes: [6](#0-5) 
5. The next `accrue()` call computes `time-delta` starting from this new `last-update`, so the liquidity yield that should have accrued over the interval covered in step 3 is permanently excluded from all future liquidity-index calculations — depositors' `convert-to-assets` redemption value never reflects that period's yield.
