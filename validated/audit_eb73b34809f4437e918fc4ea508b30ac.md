## Analog Found

### Title
Stale Cairo0 class-cache entries are never re-validated against on-chain declaration status - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
The reported bug pattern is: a piece of state (`exchangeRate`) is cached, the underlying entity is turned "off" (invalidating the cached value), and when it's turned back "on" the stale cached value is used without refresh, producing incorrect results. The sequencer has the exact same class of defect in its process-wide compiled-class cache: for Cairo1 classes the code explicitly re-validates a cache hit against the authoritative "declared" status (to guard against exactly this kind of staleness), but the identical guard is deliberately skipped for Cairo0 (`V0`) classes.

### Finding Description
`StateReaderAndContractManager::get_compiled_from_class_manager` retrieves a `RunnableCompiledClass` from the process-global `ContractClassManager` cache (`GlobalContractCache`/`RawClassCache`, which persists across blocks and across state-reader instances). On a cache hit, the code branches on class type: [1](#0-0) 

For non-`V0` (Cairo1) classes it explicitly re-checks `self.state_reader.is_declared(class_hash)` before trusting the cached entry, with the comment: *"the Cairo1 class is cached; verify it is declared, since existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)."* For `V0` (Cairo0/deprecated) classes, this validation is entirely skipped (`RunnableCompiledClass::V0(_) => {}`), and the trait itself documents that `is_declared` "always return[s] `false`" for Cairo0 classes, so there is no way to re-validate a cached Cairo0 entry at all: [2](#0-1) 

This mirrors the vault scenario precisely: the cache is populated (vault "on" / class considered declared), the authoritative state later changes (vault "off" / class becomes undeclared, e.g. because the block that declared it is reverted, as explicitly called out in the existing V1 fix's comment and exercised by the `cached_but_verification_failed_after_reorg_scenario` / `declare_revert_declare_scenario` tests), and then the class is used again — but for V0 the stale, unvalidated cached bytecode is served forever, with no equivalent of "when you turn it back on, refresh the value."

Corroborating tests show the asymmetry is intentional and only covers V1: [3](#0-2) [4](#0-3) 

### Impact Explanation
The `ContractClassManager` cache (`class_cache`) is a long-lived, process-global structure shared across block-building attempts, not scoped to a single committed block's state (`crates/blockifier/src/state/native_class_manager.rs` / `contract_class_manager.rs`). If a candidate block that declares a Cairo0 class is built (e.g. during proposal/consensus round-tripping) and populates this global cache, but that block is ultimately discarded/reverted (a normal occurrence of block building, not requiring a malicious actor), a node that retains the warm cache will continue to treat that class hash as usable, executing calls against it (deploy, `library_call`, replace-class) without any declaration check — because Cairo0 entries bypass `is_declared` entirely. A node that never warmed its cache (or one whose cache entry expired) will correctly return `UndeclaredClassHash`. This produces divergent execution results for the same transaction/block between honest nodes with different cache histories, i.e. state root / block hash divergence — exactly the "honest-node divergence" impact class this scan is scoped to accept.

### Likelihood Explanation
Reachable purely through the normal sequencer pipeline: (1) a declare transaction for a Cairo0 class is included in a candidate block that populates the shared cache, (2) that candidate block is discarded (reorg/rebuild is a routine, non-malicious event in block-building/consensus), (3) a subsequent transaction (deploy/invoke/replace_class) references the same class hash. No privileged actor, prover, or p2p manipulation is required — only a chain of ordinary transactions and a normal block-building retry. The existing code comment and dedicated regression test for the V1 case ("reverted block") confirm the sequencer team already knows this exact staleness scenario occurs in practice; it was simply not fixed for V0.

### Recommendation
Remove the special-case exemption for `RunnableCompiledClass::V0` in `get_compiled_from_class_manager`: require an authoritative re-check equivalent to `is_declared` for Cairo0 cache hits as well (e.g., extend `FetchCompiledClasses::is_declared` to cover Cairo0 classes, or invalidate/scope the `ContractClassManager` cache per committed state rather than keeping it valid across discarded candidate blocks).

### Proof of Concept
1. Node builds candidate block `A` containing `declare` of Cairo0 class `C` (hash `h`). `get_compiled_from_class_manager` cache-misses, fetches, and calls `contract_class_manager.set_and_compile(h, ...)`, populating the global cache. [5](#0-4) 
2. Block `A` is discarded/replaced by block `B` (normal consensus round failure) which does not include the declare of `C`.
3. A later transaction in an accepted block calls `deploy`/`library_call`/`replace_class` referencing class hash `h`. On the node that built candidate `A`, `get_compiled_from_class_manager` hits the warm cache and returns the `V0` class with **no** declaration check, executing successfully.
4. A different honest node that never built candidate `A` (cold cache) executes the same transaction, misses the cache, queries `state_reader.get_compiled_classes(h)`, finds it undeclared, and returns `StateError::UndeclaredClassHash` — causing the two nodes to disagree on the transaction's execution result and resulting state diff/root.
