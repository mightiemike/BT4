### Title
Taker fully pays remaining sell tokens but receives floor-divided buy tokens, losing the rounding remainder with no refund - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchSingleOrder` matches an on-chain limit order ("taker") against a resting order ("maker") in TRON's TRC10 order-book market. When the taker's entire remaining sell-token balance, converted at the maker's price, buys fewer tokens than the maker has available (the "taker < maker" branch), the code awards the maker the taker's *entire* remaining sell-token quantity, while the taker receives only the floor-divided buy-token amount computed by `MarketUtils.multiplyAndDivide`. The rounding remainder of the taker's payment is never refunded and is effectively transferred to the maker.

### Finding Description
In `matchSingleOrder`: [1](#0-0) 
`takerBuyTokenQuantityRemain` is computed as `floor(takerSellRemainQuantity * makerSellQuantity / makerBuyQuantity)` via `MarketUtils.multiplyAndDivide`, which performs integer (floor) division: [2](#0-1) 

In the branch where this floor-divided amount is smaller than the maker's remaining sell quantity ("taker < maker"): [3](#0-2) 
the taker's order is fully closed (`setSellTokenQuantityRemain(0)`), and the maker receives the **full** `takerOrderCapsule.getSellTokenQuantityRemain()` (line 446), while the taker only receives `takerBuyTokenQuantityReceive = takerBuyTokenQuantityRemain` — the floor-divided (rounded-down) buy amount. The exact cost of that floor-divided buy amount, expressed in the taker's sell token, is `takerBuyTokenQuantityRemain * makerBuyQuantity / makerSellQuantity`, which is always ≤ `takerSellRemainQuantity`. The difference between the taker's full remaining sell balance and this exact cost is the rounding "dust" that should be refunded to the taker (analogous to the `refund` value in the external report), but the code instead hands it entirely to the maker via `makerBuyTokenQuantityReceive = takerOrderCapsule.getSellTokenQuantityRemain()`.

This mirrors the reported `fulfillWindow` bug class exactly: a party (here, the taker) pays a full amount, receives only `floor(volume/price)` worth of the counter-asset, and the un-refunded remainder is transferred away rather than returned. The magnitude of the loss is bounded by `makerBuyQuantity/makerSellQuantity` (i.e., up to just under the cost of one whole unit of the bought asset at the maker's price), which can be economically significant when the price ratio is large (e.g., an expensive token priced in a fine-grained token).

By contrast, the code's other two branches handle the leftover correctly: in the "taker == maker" branch the leftover is retained in the taker's own order (`takerSellTokenLeft`), and in the "taker > maker" branch the leftover is subtracted from the taker's remaining sell balance (line 480-481) rather than being handed unconditionally to the counterparty. Only the "taker < maker" branch discards the rounding remainder without accounting for it.

Note: there is a documented mechanism to fully refund the taker when the entire computed buy quantity would floor to `0`: [4](#0-3) 
This shows the codebase acknowledges the need to refund dust in the zero case, but does not extend that same protection to the nonzero partial-rounding case in the "taker < maker" branch.

### Impact Explanation
This is reachable by any user broadcasting a `MarketSellAssetContract` transaction (the on-chain order matching market, `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`), with no privileged role required — it is a direct accounting-corruption bug in resource/asset settlement during order matching. Each affected trade silently transfers value from the taker (who pays a full remaining balance) to the maker (who receives the excess) whenever the exact settlement quantity is not a multiple of the maker's price ratio. Because this occurs on every fill that lands in the "taker < maker" case with a non-exact ratio, the aggregate value leakage across many trades can be significant, particularly for price pairs with large `makerBuyQuantity/makerSellQuantity` ratios.

### Likelihood Explanation
High. Exact-integer price ratios are the exception rather than the rule for arbitrary TRC10 token pairs and arbitrary order sizes; any market participant submitting sell/buy quantities that don't divide evenly into the maker's price ratio will trigger this rounding loss whenever their order is smaller than the matched maker liquidity. No special conditions, privileged access, or attacker cooperation are required — it happens organically during ordinary trading.

### Recommendation
In the "taker < maker" branch, compute the exact sell-token cost corresponding to `takerBuyTokenQuantityRemain` (i.e., `ceil` or exact `takerBuyTokenQuantityRemain * makerBuyQuantity / makerSellQuantity`), transfer only that exact amount to `makerBuyTokenQuantityReceive`, and either (a) leave the remainder in the taker's order for further matching against other price levels, or (b) refund the remainder back to the taker's account instead of unconditionally assigning `takerOrderCapsule.getSellTokenQuantityRemain()` in full to the maker.

### Proof of Concept
Given a maker order selling token A at price `makerSellQuantity : makerBuyQuantity` (e.g., `1 A : 1,000,000 TRX`, i.e., 1 A costs 1,000,000 TRX) with `makerSellRemainQuantity = 10` A available, and a taker order with `takerSellRemainQuantity = 1,999,999` TRX wanting to buy A:

1. `takerBuyTokenQuantityRemain = floor(1,999,999 * 1 / 1,000,000) = 1` (per `MarketUtils.multiplyAndDivide`, [2](#0-1) ).
2. Since `1 < makerSellRemainQuantity (10)`, the "taker < maker" branch executes ( [3](#0-2) ).
3. `takerBuyTokenQuantityReceive = 1` A is credited to the taker.
4. `makerBuyTokenQuantityReceive = takerOrderCapsule.getSellTokenQuantityRemain() = 1,999,999` TRX is credited to the maker — even though the exact cost of 1 A at the stated price is only 1,000,000 TRX.
5. The taker's order is closed (`setSellTokenQuantityRemain(0)`), so the taker permanently loses the ~999,999 TRX difference with no refund, and the maker receives it as an unearned windfall.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
