### Title
Unauthenticated module-originated `executeUniversalTx` calls to arbitrary CEA-recipient contracts - (File: `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/evm.go`)

### Summary
For `isCEA` inbounds whose `Recipient` resolves to a deployed non-UEA smart contract, `x/uexecutor` calls `executeUniversalTx(sourceChain, ceaAddress, payload, amount, prc20AssetAddr, txId)` on that contract as the trusted `uexecutor` module account, with **zero cryptographic authorization** of the call parameters. Every argument — `sourceChain`, `ceaAddress` (=attacker-supplied `Sender`), `payload`, and (since the recent zero-amount upgrade) `amount` — is fully attacker-controlled via a source-chain gateway event that any unprivileged user can create. This mirrors the M-03 pattern: no entry check on who/what can be targeted, and the target contract address ("pairs" analog) is fully attacker-specified.

### Finding Description
The isCEA execution path in both `ExecuteInboundGasAndPayload` and `ExecuteInboundFundsAndPayload` branches into two mutually-exclusive treatments of `Recipient`:
1. **Recipient is a UEA** → payload is executed via `ExecutePayloadV2`/`CallUEAExecutePayload`, and the UEA contract cryptographically verifies `VerificationData` against the owner's key [2](#0-1) .
2. **Recipient is a deployed non-UEA contract** ("smart contract" branch) → `CallExecuteUniversalTx` is invoked directly, with **no signature/verification-data check at all** [3](#0-2) [4](#0-3) .

`CallExecuteUniversalTx` issues a `DerivedEVMCall` with `isModuleSender=true`, using the `uexecutor` module account as `from`, targeting the attacker-chosen `recipientAddr` [5](#0-4) . The only gate before reaching this call is `ValidateForExecution`, which validates that `Recipient` is *a syntactically valid hex address* — nothing more [6](#0-5) . There is no registry/whitelist of approved "CEA" contracts anywhere in `x/uregistry`.

Since the `Inbound` (`SourceChain`, `Sender`, `Recipient`, `Amount`, `UniversalPayload.Data`) is derived from a real event a user creates on an external gateway contract, and Universal Validators (assumed honest) faithfully report exactly what happened, an ordinary unprivileged user fully controls all of these fields. Combined with the recently added zero-amount-inbound feature (`cea-gas-and-payload` upgrade) [7](#0-6) , an attacker can trigger `executeUniversalTx` on **any deployed contract on Push Chain** with attacker-chosen `sourceChain`, `ceaAddress`, arbitrary `payload` bytes, and `amount=0`, with the trusted module account (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`) as `msg.sender` — at zero cost to the attacker beyond a cheap external-chain transaction.

### Impact Explanation
Any third-party contract on Push Chain that implements `executeUniversalTx` and trusts `msg.sender == UNIVERSAL_EXECUTOR_MODULE` as proof of a legitimate, validator-attested crosschain deposit (the same trust assumption the UEA contracts rely on, per the module's own README security argument) can be invoked with entirely forged parameters — forged source chain, forged sender identity, forged payload, and zero real value transferred. This is "unauthorized module-originated EVM execution" per the allowed-impact gate: the module executes EVM calls on behalf of the protocol into recipient contracts without any authentication of the call's content, letting an attacker impersonate a genuine crosschain deposit/payload event on any CEA-integrated contract. Depending on what such contracts do in `executeUniversalTx` (e.g., credit balances, unlock funds, trigger further transfers based on the reported `amount`/`sourceChain`/`ceaAddress`), this can lead to theft or corruption of funds held by those contracts.

### Likelihood Explanation
High for any contract that adopts the CEA integration pattern without its own additional authentication, since the only "check" performed by the chain is that the target address has bytecode and is not a recognized UEA — a condition trivially satisfied by any deployed contract, and reachable purely through ordinary, unprivileged user-submitted source-chain transactions plus normal, honest validator voting.

### Recommendation
Require an explicit, admin-curated registry (analogous to `x/uregistry`'s chain/token whitelisting) of contracts allowed to receive `isCEA` `executeUniversalTx` calls, and/or require the contract itself to perform its own authentication of the reported `sourceChain`/`sender`/`payload` (e.g., via a signature or a pre-registered mapping) before trusting `msg.sender == UNIVERSAL_EXECUTOR_MODULE` as sufficient proof of authenticity. At minimum, do not allow `amount == 0` combined with attacker-fully-controlled `payload`/`sourceChain`/`sender` on the isCEA smart-contract path unless the destination contract has opted in to this trust model via registration.

### Proof of Concept
1. Attacker deploys `MaliciousCEA.sol` implementing `executeUniversalTx(string sourceChain, bytes ceaAddress, bytes payload, uint256 amount, address prc20AssetAddr, bytes32 txId)`, gated only on `require(msg.sender == UNIVERSAL_EXECUTOR_MODULE)`.
2. Separately, a legitimate dApp `VictimCEA.sol` is deployed by an unrelated party, also implementing `executeUniversalTx` and trusting `msg.sender == UNIVERSAL_EXECUTOR_MODULE` combined with `sourceChain`/`ceaAddress`/`amount` to credit user balances or release funds (the intended usage pattern for CEA integration).
3. Attacker submits a gateway transaction on a supported external chain (e.g. Ethereum Sepolia) with `TxType = GAS_AND_PAYLOAD`, `IsCEA = true`, `Recipient = VictimCEA` address, `Amount = 0`, `Sender = <forged identity of attacker's choosing>`, and `UniversalPayload.Data` crafted to whatever `VictimCEA.executeUniversalTx` expects to trigger a privileged action.
4. Honest Universal Validators observe this real (attacker-controlled) event and vote it in via `MsgVoteInbound`; ballot finalizes normally.
5. `x/uexecutor` resolves `Recipient` as a non-UEA smart contract (`isSmartContract = true`) and calls `CallExecuteUniversalTx` on `VictimCEA`, passing the attacker's forged `sourceChain`, `ceaAddress` (=`Sender`), `payload`, and `amount=0`, with `msg.sender == UNIVERSAL_EXECUTOR_MODULE`.
6. `VictimCEA` accepts the call as a "legitimate" crosschain event because its only check (`msg.sender == UNIVERSAL_EXECUTOR_MODULE`) passes, executing attacker-chosen logic against forged inputs.

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**

// CallExecuteUniversalTx calls executeUniversalTx on a smart-contract recipient.
// This is used for isCEA inbounds whose recipient is a deployed contract (not a UEA).
func (k Keeper) CallExecuteUniversalTx(
	ctx sdk.Context,
	recipientAddr common.Address,
	sourceChain string,
	ceaAddress []byte,
	payload []byte,
	amount *big.Int,
	prc20AssetAddr common.Address,
	txId [32]byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	recipientABI, err := types.ParseRecipientContractABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse recipient contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		recipientABI,
		ueModuleAccAddress,
		recipientAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"executeUniversalTx",
		sourceChain,
		ceaAddress,
		payload,
		amount,
		prc20AssetAddr,
		txId,
	)
}
