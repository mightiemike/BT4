### Title
`DeleteAccountAction` Transfers Balance to Unvalidated Beneficiary — Balance Burned on Non-Existent Recipient - (File: `runtime/runtime/src/actions.rs`)

---

### Summary

`action_delete_account` creates a system-predecessor balance-transfer receipt to `beneficiary_id` without verifying the beneficiary account exists. When the beneficiary is a syntactically valid but non-existent named account, the transfer receipt fails silently and the entire deleted account's balance is permanently burned by the runtime's system-receipt failure handler.

---

### Finding Description

`validate_delete_action` in `runtime/runtime/src/action_validation.rs` only checks that `beneficiary_id` is a syntactically valid account ID string:

```rust
fn validate_delete_action(action: &DeleteAccountAction) -> Result<(), ActionsValidationError> {
    validate_action_account_id(&action.beneficiary_id)?;
    Ok(())
}
``` [1](#0-0) 

No existence check is performed. `action_delete_account` then unconditionally creates a balance-transfer receipt via `Receipt::new_balance_refund`:

```rust
let account_balance = account_ref.amount();
if account_balance > Balance::ZERO {
    result
        .new_receipts
        .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
}
``` [2](#0-1) 

`Receipt::new_balance_refund` sets `predecessor_id = "system"`: [3](#0-2) 

When this system receipt is later processed and the beneficiary does not exist (and is not an implicit account type), the `Transfer` action fails with `AccountDoesNotExist`. The runtime's system-receipt failure path at `lib.rs:926–934` then burns the deposit instead of returning it:

```rust
if receipt.predecessor_id().is_system() {
    // If the refund fails tokens are burned.
    if result.result.is_err() {
        stats.balance.other_burnt_amount = safe_add_balance(
            stats.balance.other_burnt_amount,
            total_deposit(&action_receipt.actions())?,
        )?
    }
    GasRefundResult::default()
}
``` [4](#0-3) 

The `DeleteAccount` action itself succeeds and is committed. The account is removed from state. The balance-transfer receipt failure is a separate, subsequent receipt execution. The user observes a successful `DeleteAccount` outcome but the balance is gone.

---

### Impact Explanation

An unprivileged user who submits a `DeleteAccountAction` naming a syntactically valid but non-existent named account as `beneficiary_id` permanently loses their entire account balance. The balance is added to `other_burnt_amount` and removed from total supply. The deletion is irreversible — the account is already removed from trie state before the transfer receipt executes. This is a direct, on-chain loss of funds reachable from a standard JSON-RPC transaction submission with no privileged preconditions.

The broken invariant: the protocol documentation states "the tokens are transferred to `beneficiary_id`" — but when the beneficiary does not exist, the tokens are silently burned rather than transferred or the action being rejected. [5](#0-4) 

---

### Likelihood Explanation

Likelihood is low. A user must specify a non-existent named account as beneficiary. This can occur through a typo, a stale account ID (beneficiary was deleted), or a cross-shard race where the beneficiary is deleted between transaction submission and execution. The scenario is not adversarially triggered against a third party — the user is the sole victim of their own transaction. However, the protocol provides no guard to prevent it.

---

### Recommendation

Add an existence check for `beneficiary_id` at execution time inside `action_delete_account`, before creating the balance-transfer receipt. If the beneficiary does not exist and is not an implicit account type eligible for creation-by-transfer, either:

1. Reject the `DeleteAccount` action with a new `ActionErrorKind::BeneficiaryDoesNotExist` error, or
2. Fall back to sending the balance to `receipt.predecessor_id()` (the transaction signer), consistent with how deposit refunds work on failed receipts.

Option 1 is safer because it makes the failure explicit and reversible before the account is deleted.

---

### Proof of Concept

1. Alice has account `alice.near` with balance 100 NEAR.
2. Alice submits a `DeleteAccount` transaction with `beneficiary_id = "nonexistent.near"` (a syntactically valid but non-existent account).
3. `validate_delete_action` passes — `"nonexistent.near"` is a valid account ID string.
4. `action_delete_account` executes: Alice's account is removed from trie state; a `Receipt::new_balance_refund("nonexistent.near", 100 NEAR)` is queued.
5. The balance-transfer receipt executes on the `nonexistent.near` shard. `check_account_existence` returns `AccountDoesNotExist` for the `Transfer` action (since `nonexistent.near` is not an implicit account).
6. Since `predecessor_id == "system"`, the runtime burns the 100 NEAR into `other_burnt_amount`.
7. Alice's account is gone. Her 100 NEAR is gone. No error is surfaced to the original transaction outcome — the `DeleteAccount` receipt shows `SuccessValue`.

pub(crate) fn check_account_existence(
    action: &Action,
    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            } else {
                if account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts) {
                    // If the account doesn't exist and it's implicit, then you
                    // should only be able to create it using single transfer action.
                    // Because you should not be able to add another access key to the account in
                    // the same transaction.
                    // Otherwise you can hijack an account without having the private key for the
                    // public key. We've decided to make it an invalid transaction to have any other
                    // actions on the implicit hex accounts.
                    // The easiest way is to reject the `CreateAccount` action.
                    // See https://github.com/nearprotocol/NEPs/pull/71
                    return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed {
                        account_id: account_id.clone(),
                    }
                    .into());
                }
            }
        }
        Action::Transfer(_) => {
            if account.is_none() {
                return check_transfer_to_nonexisting_account(
                    config,
                    account_id,
                    implicit_account_creation_eligible,
                );
            }
        }
        Action::DeterministicStateInit(_) => {
            // Existing and non existing is valid for DeterministicStateInit.
            // Does not exist => The account will be created by the action.
            // Does exist => Nothing happens but the receipt is not aborted to
            // allow optional init before other actions.
        }
        Action::DeployContract(_)
        | Action::FunctionCall(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeleteAccount(_)
        | Action::Delegate(_)
        | Action::DelegateV2(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::TransferToGasKey(_)
        | Action::WithdrawFromGasKey(_) => {
            if account.is_none() {
                return Err(ActionErrorKind::AccountDoesNotExist {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
    };
    Ok(())
}
