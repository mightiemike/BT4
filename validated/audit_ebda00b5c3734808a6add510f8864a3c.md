### Title
Transaction Pool Exhaustion via Nonce-Gapped Strict-Nonce Transactions with No Per-Account Limit or Eviction Strategy — (File: `chain/pool/src/lib.rs`)

---

### Summary

nearcore's `TransactionPool` enforces only a total byte-size cap (`total_transaction_size_limit`, default 100 MB). When that cap is reached, `insert_transaction` returns `InsertTransactionResult::NoSpaceLeft` and silently drops the incoming transaction — there is no cross-account eviction, no per-account slot limit, and no priority-based replacement. A single unprivileged account can exploit this by submitting a large number of strict-nonce transactions with arbitrarily high nonces (nonce-gapped). Each such transaction passes initial RPC validation (nonce > ak\_nonce is satisfied), enters the pool, and occupies space for up to `transaction_pool_strict_nonce_ttl_blocks` (default 64) blocks before being evicted during `prepare_transactions`. Because the balance check at submission time reads the current committed state without deducting pending amounts, one account with a small NEAR balance can pass the balance check for thousands of distinct gapped transactions simultaneously, filling the entire pool and blocking all legitimate users from submitting transactions for up to 64 blocks.

---

### Finding Description

**Root cause 1 — No eviction on pool full:**

`TransactionPool::insert_transaction` in `chain/pool/src/lib.rs` checks the total byte size and, if the limit would be exceeded, returns `NoSpaceLeft` immediately:

```rust
if let Some(limit) = self.total_transaction_size_limit {
    if new_total_transaction_size > limit {
        return InsertTransactionResult::NoSpaceLeft;
    }
}
``` [1](#0-0) 

There is no mechanism to evict an existing transaction (from any account) to make room for the incoming one. The caller in `rpc_handler.rs` simply logs a trace and continues:

```rust
InsertTransactionResult::NoSpaceLeft => {
    // ... just logs, transaction is lost
}
``` [2](#0-1) 

**Root cause 2 — Nonce-gapped strict-nonce transactions occupy pool space for up to 64 blocks:**

During `prepare_transactions`, when a strict-nonce transaction is detected as gapped (`tx_nonce > current_nonce + 1`), it is left in the pool (not popped) as long as its TTL has not expired:

```rust
if tx_nonce > current_nonce.saturating_add(1) {
    if !validate_tx_ttl(tx_peek.to_signed_tx()) {
        transaction_group_iter.next();
        continue;
    }
    break;  // leave in pool
}
``` [3](#0-2) 

The TTL is `transaction_pool_strict_nonce_ttl_blocks` (default 64 blocks): [4](#0-3) 

**Root cause 3 — Balance check at submission does not account for pending transactions:**

`can_verify_and_charge_tx` checks the account balance against the current committed state root. Because no balance is actually deducted at submission time, one account with balance B can submit thousands of transactions that each independently pass the balance check, all referencing the same committed balance B.

**Root cause 4 — No per-account transaction count limit in the pool:**

`TransactionPool` stores transactions in a `BTreeMap<PoolKey, Vec<ValidatedTransaction>>` with no cap on the number of entries per group: [5](#0-4) 

A single `(signer_id, public_key)` group can grow to fill the entire pool.

---

### Impact Explanation

An unprivileged attacker with one NEAR account and a small balance (e.g., 1 NEAR) can:

1. Submit thousands of strict-nonce transactions with nonces far above the current access-key nonce (e.g., nonce = 10^6, 10^6+1, 10^6+2, …). Each has a distinct hash and passes `can_verify_and_charge_tx`.
2. Fill the 100 MB pool (~333,000 transactions at ~300 bytes each).
3. For the next 64 blocks (~64 seconds), every legitimate user's transaction submitted to that chunk producer's pool receives `NoSpaceLeft` and is silently dropped.
4. The attacker refreshes by submitting new gapped transactions before the TTL window expires, sustaining the blockade indefinitely at low cost.

The broken invariant: a legitimate user's valid, funded transaction must not be permanently excluded from the pool solely because an attacker has pre-filled it with non-executable transactions that will never appear in a committed block.

This is a non-network-level DoS (each validator maintains its own pool) fixable without a hardfork.

---

### Likelihood Explanation

- **Attacker cost is low.** One account with ~1 NEAR suffices; no privileged access, no validator control, no key compromise is required.
- **Attack is repeatable.** The attacker can continuously refresh gapped transactions before the 64-block TTL expires.
- **No existing guard prevents it.** The pool has no per-account slot cap, no priority-based replacement, and no cross-account eviction.
- **The `transaction_pool_size_limit` is `Option<u64>`** — nodes that set it to `None` (unbounded) are additionally vulnerable to memory exhaustion. [6](#0-5) 

---

### Recommendation

1. **Add a per-account (per-PoolKey group) transaction count or byte limit** inside `insert_transaction` to prevent one account from monopolizing the pool.
2. **Implement a cross-account eviction strategy**: when the pool is full, evict the oldest or lowest-priority transaction from any account rather than dropping the incoming transaction.
3. **Reject or strictly cap nonce-gapped strict-nonce transactions at submission time** (e.g., reject if `tx_nonce > ak_nonce + MAX_NONCE_GAP`) so they cannot enter the pool at all, rather than relying solely on TTL eviction during chunk production.
4. **Enforce that `transaction_pool_size_limit` is always set** (remove the `None`/unbounded option in production configurations).

---

### Proof of Concept

```
1. Attacker holds account "attacker.near" with ak_nonce = 0 and balance = 1 NEAR.

2. Attacker submits 333,000 strict-nonce (V1) transactions:
     nonce = 1_000_000, 1_000_001, 1_000_002, …, 1_333_000
   Each references a recent block_hash (within transaction_validity_period).
   Each passes can_verify_and_charge_tx:
     - nonce (1_000_000) > ak_nonce (0) ✓
     - balance (1 NEAR) covers gas cost ✓ (same committed state for all)

3. All 333,000 transactions enter the pool (distinct hashes, same PoolKey group).
   Pool reaches 100 MB → total_transaction_size_limit exceeded.

4. Any subsequent transaction from any legitimate user:
     pool.insert_transaction(...) → InsertTransactionResult::NoSpaceLeft
   The transaction is dropped silently.

5. During prepare_transactions for each of the next 64 blocks:
     tx_nonce (1_000_000) > current_nonce (0) + 1 → gapped
     validate_tx_ttl → TTL still valid → break (left in pool)
   No legitimate transactions are included from the pool.

6. After 64 blocks, gapped transactions are evicted.
   Attacker immediately repeats step 2 to sustain the blockade.
``` [7](#0-6) [8](#0-7) [9](#0-8)

```rust
    /// Inserts a signed transaction that passed validation into the pool.
    pub fn insert_transaction(
        &mut self,
        validated_tx: ValidatedTransaction,
    ) -> InsertTransactionResult {
        let tx_hash = validated_tx.get_hash();
        if self.unique_transactions.contains(&tx_hash) {
            return InsertTransactionResult::Duplicate;
        }
        // We never expect the total size to go over `u64` during real operation as that would
        // be more than 10^9 GiB of RAM consumed for transaction pool, so panicking here is intended
        // to catch a logic error in estimation of transaction size.
        let new_total_transaction_size = self
            .total_transaction_size
            .checked_add(validated_tx.wire_size())
            .expect("Total transaction size is too large");
        if let Some(limit) = self.total_transaction_size_limit {
            if new_total_transaction_size > limit {
                return InsertTransactionResult::NoSpaceLeft;
            }
        }

        // At this point transaction is accepted to the pool.

        // This is guaranteed to succeed because of the check above that the
        // hashset does not contain this hash.  This can be improved once the
        // entries API is stabilized
        // (https://github.com/rust-lang/rust/issues/60896).
        assert_eq!(self.unique_transactions.insert(tx_hash), true);
        self.total_transaction_size = new_total_transaction_size;
        let signer_id = validated_tx.signer_id();
        let signer_public_key = validated_tx.public_key();
        self.transactions
            .entry(self.key(signer_id, signer_public_key, validated_tx.nonce().nonce_index()))
            .or_insert_with(Vec::new)
            .push(validated_tx);

        self.transaction_pool_count_metric.inc();
        self.transaction_pool_size_metric.set(self.total_transaction_size as i64);
        InsertTransactionResult::Success
    }
