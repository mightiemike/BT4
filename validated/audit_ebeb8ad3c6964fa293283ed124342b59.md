### Title
Multisig weight double-counting via signature recycling in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiled contract `ValidateMultiSign` (`PrecompiledContracts.java`, class `ValidateMultiSign`) deduplicates submitted signatures by comparing the *exact raw signature bytes* merged with the recovered address, rather than deduplicating by the recovered signer address alone. Because ECDSA signatures are not unique per `(message, key)` pair — a signer can trivially produce additional, byte-different, but equally valid signatures over the same hash (e.g. via standard signature malleability `s' = n - s, v' = 1 - v`, or simply by re-signing with a different nonce) — a single signer can submit two or more distinct-looking signatures that each pass the "new signature" check and each add that signer's weight again, letting one weight allocation satisfy a higher threshold than intended.

### Finding Description
`ValidateMultiSign.execute` recovers the address for each submitted signature and tracks "seen" signatures in `executedSignList`: [1](#0-0) 

The loop logic is:
- For each signature, recover `recoveredAddr`.
- If `recoveredAddr` was already seen, only `continue` (skip) if the *exact* `merge(recoveredAddr, sign)` byte sequence was already seen (`ByteArray.matrixContains(executedSignList, sign)`).
- Otherwise (same address, different raw signature bytes) it calls `MUtil.checkCPUTime()` and then falls through to add the weight again via `TransactionCapsule.getWeight(permission, recoveredAddr)` and `totalWeight += weight`.

This means the check only rejects *literal* duplicate signature bytes, not duplicate *signers*. It does not track "used signer addresses" the way `TransactionCapsule.checkWeight` does (which keys a `HashMap` by recovered address and explicitly throws `"has signed twice!"`): [2](#0-1) 

Because ECDSA allows a signer (or even anyone in possession of one valid signature, via the standard `s -> n-s`, `v -> 1-v` malleation, which requires no private key) to produce a second distinct-byte but equally valid signature over the identical hash for the same public key, that second signature will recover to the same address yet not byte-match any previously seen entry, and will therefore be counted as an additional "unique" contribution to `totalWeight`. This is the same bug class as the reported `UserOpMultiSigVerifier` issue: the validator prevents literal signature reuse (analogous to preventing "index" reuse) but fails to prevent the same underlying signer/address from being counted multiple times.

Note this is distinct from `AccountPermissionUpdateActuator.checkPermission`, which enforces that owner addresses in a `Permission` are unique at permission-creation time: [3](#0-2) 
That protects against duplicate *owner entries*, but does nothing to prevent a single legitimate owner from submitting multiple distinct valid signatures for the same message to be counted multiple times inside `ValidateMultiSign`.

### Impact Explanation
`ValidateMultiSign` is a precompiled contract callable from any smart contract, and thus reachable by any externally owned account through a normal `TriggerSmartContract` transaction to any dApp that uses this precompile to gate multisig-authorized actions (a common on-chain multisig/authorization pattern for TRC20 vaults, DAOs, etc.). A signer holding only a fraction of the required weight (e.g. weight 1 of threshold 2) can single-handedly satisfy the threshold by submitting their own signature twice in a malleated/re-signed form, defeating the multi-party authorization guarantee the calling contract relies on. This can lead to unauthorized execution of privileged on-chain actions (asset transfers, permission changes, governance actions) gated by this precompile — an accounting/authorization corruption impact.

### Likelihood Explanation
Medium: exploitation requires only that the attacker is one of the legitimate signers in the target permission (a "rogue signer", matching the original report's threat model) and needs no protocol-level privilege, no p2p/node compromise, and no additional secret material — ECDSA signature malleability (`s' = n - s`) is a well-known, trivial transformation. The attack is reachable purely via a standard smart-contract call carrying attacker-controlled signature bytes into `ValidateMultiSign.execute`.

### Recommendation
Deduplicate by recovered **signer address**, not by raw signature bytes. Track a `Set<byte[]>`/`List<byte[]>` of addresses already counted and skip (rather than re-add weight) whenever `recoveredAddr` has already contributed weight, regardless of whether the raw signature bytes differ:
```java
if (ByteArray.matrixContains(executedAddrList, recoveredAddr)) {
    continue; // address already counted, ignore new/malleated signature
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
executedAddrList.add(recoveredAddr);
```
This mirrors the fix already present in `TransactionCapsule.checkWeight`, which keys uniqueness by recovered address rather than by signature bytes.

### Proof of Concept
1. Signer `S` has weight `1` in a permission with `threshold = 2` and one other signer `T` with weight `1` (so `S` alone should never reach threshold).
2. `S` signs `hash` once, obtaining `(r, s, v)`.
3. `S` (or anyone with that one signature) computes the malleated signature `(r, n-s, 1-v)`, which recovers to the same address `S` but has different raw bytes.
4. `S` calls the contract that invokes `ValidateMultiSign(address, permissionId, hash, [sig1, sig2])` with both signatures.
5. In `ValidateMultiSign.execute`, the first signature adds `weight=1` for `S`. The second signature recovers to the same `recoveredAddr` but its merged bytes don't match the first entry in `executedSignList`, so it is *not* skipped — it adds `weight=1` again.
6. `totalWeight = 2 >= threshold(2)` → the precompile returns success (`dataOne()`), even though only one real signer participated. [4](#0-3)
