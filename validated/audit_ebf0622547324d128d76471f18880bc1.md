### Title
Webhook `topic`/`domain`/`webhookId`/`apiVersion` header fields are not covered by the HMAC signature, allowing a replayed webhook to be processed under an attacker-chosen shop and topic - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`, `packages/apps/shopify-api/lib/webhooks/validate.ts`)

### Summary
Shopify webhook authenticity is validated by computing an HMAC over the raw request body only. The `shop`, `topic`, `webhook-id`, `api-version`, and other identifying values are taken from unauthenticated HTTP headers and are never included in the signed material. Any actor who has legitimately received one authentic `(rawBody, hmac)` pair for the app (e.g., by installing the app on their own shop and letting a real webhook fire) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting arbitrary values for the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers. Validation still succeeds because the HMAC check never touches these fields, and the framework then loads the offline session/admin client for the forged `domain` and dispatches the forged `topic` to the app's business logic using attacker-controlled body content.

### Finding Description
`validateHmacFromRequestFactory` computes the HMAC exclusively from `rawBody`: [1](#0-0) 

`shopify.webhooks.validate` (`validateFactory`) runs this body-only HMAC check and, once it passes, reads `domain`, `topic`, `webhookId`, `apiVersion`, `eventId`, etc. straight out of request headers with no cryptographic binding to the verified body: [2](#0-1) 

The header names read (per webhook type) come straight from `WEBHOOK_HEADER_NAMES`, none of which are part of the HMAC input: [3](#0-2) 

Downstream, the `shopify-app-remix` and `shopify-app-react-router` `authenticate.webhook` handlers trust `check.domain` to look up and construct an authenticated offline session/admin client, and trust `check.topic` for dispatch, all without any signature guaranteeing these values matched what Shopify actually sent for that body: [4](#0-3) [5](#0-4) 

The lower-level `shopify.webhooks.process` API exhibits the same pattern: it dispatches to handlers keyed by `webhookCheck.topic` and calls the registered callback with `webhookCheck.domain` — both header-derived, unsigned values — alongside the (signed) `rawBody`: [6](#0-5) 

This mirrors the reported Cairo bug class exactly: a field (`payload_type` there, `domain`/`topic`/`webhookId` here) that is emitted/consumed for downstream trust decisions is not included in the message-authentication computation, so it can be manipulated independently of the verified payload.

### Impact Explanation
Because `domain` is not bound to the signed body, an attacker who legitimately possesses one authentic `(rawBody, hmac)` pair for the app (trivially obtainable by installing the app on any shop, including a free/dev store, and receiving one real webhook, or via Shopify's admin "send test webhook" feature) can:

1. Replay that exact body/HMAC to the app's public `/webhooks` endpoint.
2. Set the `X-Shopify-Shop-Domain` header to a *different*, targeted merchant's shop domain.
3. Cause `ensureValidOfflineSession(params, check.domain)` to load and use the **victim shop's** offline access token, constructing an `admin`/`storefront` client authenticated as the victim.
4. Optionally also forge `X-Shopify-Topic` to route the forged payload into a different registered handler than the one that originally produced it, running business logic against attacker-controlled content under the victim's session.

This is a cross-tenant access primitive: business logic intended to run against the merchant who actually triggered the webhook instead runs with another merchant's credentials and app data. The severity depends on what the app's webhook callbacks do with the session (e.g., write to the store, issue refunds, modify orders/products), but in the worst case it enables unauthorized cross-tenant API actions using another shop's access token.

### Likelihood Explanation
Likelihood is moderate: exploitation requires only (a) the ability to install the target app on any shop to obtain a single authentic `(rawBody, hmac)` pair — a normal, unprivileged action any developer/attacker can perform — and (b) knowledge or guessing of a target shop's `*.myshopify.com` domain, which is often public/discoverable. No secret key, MITM position, or elevated privilege is required; this is a same-endpoint request-forgery issue reachable from any external unauthenticated HTTP client hitting the app's public webhook route.

### Recommendation
Bind the identifying headers into the authenticated material rather than trusting them independently of the HMAC:
- Include `shop`, `topic`, and `webhook_id` (or a canonical concatenation of them) as part of the HMAC input, or verify them via a second signed channel (e.g., cross-check against the webhook subscription registered for that shop/topic combination).
- Alternatively, after HMAC validation, re-derive the expected shop/topic from Shopify by looking up the webhook subscription ID (`X-Shopify-Webhook-Id`) via the Admin API and confirming it matches the claimed `domain`/`topic`, rejecting mismatches.
- At minimum, document and warn integrators that `domain`/`topic`/`webhookId` are not authenticated by the HMAC and must not be used for authorization decisions without additional verification (e.g., confirming the returned `domain` actually owns an active subscription for the returned `webhookId`/`topic`).

### Proof of Concept
1. Install the vulnerable app on an attacker-controlled shop `attacker.myshopify.com`; wait for (or trigger) a legitimate webhook delivery, capturing `rawBody` and its `X-Shopify-Hmac-Sha256` value.
2. Send a new POST request to the app's `/webhooks` endpoint with the identical `rawBody` and `X-Shopify-Hmac-Sha256`, but replace:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: <arbitrary-registered-topic>` (optional)
   - `X-Shopify-Webhook-Id: <any string>`
3. `shopify.webhooks.validate`/`validateFactory` accepts the request because `validateHmacString` only checks `rawBody` against the HMAC — see `packages/apps/shopify-api/lib/utils/hmac-validator.ts` lines 189-197 and `packages/apps/shopify-api/lib/webhooks/validate.ts` lines 46-74.
4. `authenticate.webhook` in `shopify-app-remix`/`shopify-app-react-router` calls `ensureValidOfflineSession(params, check.domain)` with `check.domain = 'victim.myshopify.com'`, returning the victim's offline session and an `admin` client authenticated as the victim shop (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts` lines 33-56, 88-103).
5. The app's webhook business logic executes using the attacker's payload but the victim's Admin API credentials/session context.
