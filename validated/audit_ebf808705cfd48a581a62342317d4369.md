### Title
Unsanitized External Adapter (Bridge) Error Messages Reflected to Node Operator UI/API - ([File: core/services/pipeline/task.bridge.go])

### Summary
Chainlink's `BridgeTask` extracts the `error.message` field verbatim from an external adapter's (EA) HTTP response body and stores it as the pipeline task/run error. This raw, attacker/compromised-adapter-controlled string is later surfaced unsanitized through the node's public GraphQL and REST APIs (`fatalErrors`/`allErrors`) that node operators view in the Operator UI, mirroring the reported analog where JSON-RPC error text from an untrusted remote endpoint is reflected directly into the wallet UI.

### Finding Description
`eautils.BestEffortExtractEAError` parses an `AdapterError{Name, Message}` struct straight out of the bridge/EA HTTP response body with no validation or sanitization of content (control characters, newlines, HTML/markdown-like text, etc.): [1](#0-0) 

`BridgeTask.resolveFailureOrCache` uses this extracted error directly as the task's error on any non-2xx/failed bridge call, favoring the adapter-supplied message over the transport error: [2](#0-1) 

This raw error string becomes the task run's `Result.Error`, which the pipeline `runner` aggregates into the `Run.AllErrors`/`Run.FatalErrors` fields with no additional filtering: [3](#0-2) 

These fields are then exposed unsanitized to node operators via two production interfaces:
- GraphQL `JobRun.fatalErrors` / `JobRun.allErrors` resolvers, which just copy the string content through: [4](#0-3) 
- REST `PipelineRunResource` (`/v2/jobs/:id/runs/:id`) via `NewPipelineRunResource`, which similarly forwards `StringFatalErrors`/`StringAllErrors`: [5](#0-4) 

The `job.graphql`/REST schema confirms these are plain, unstructured `String` arrays rendered by the Operator UI: [6](#0-5) 

This is directly analogous to the reported bug class: an external, potentially compromised network endpoint (the bridge/EA, playing the role of the impersonated `zcashd` in the original report) supplies free-form error text that is reflected verbatim into a trusted UI surface viewed by the operator, with no encoding of newlines or control characters and no separation between "safe pre-canned" messages and verbose diagnostic text.

### Impact Explanation
A malicious or network-compromised external adapter (a component explicitly in the "bridge/external-adapter abuse" trust boundary) can craft an `error.message` payload that is displayed as-is in the node operator's Job Run view (both GraphQL and REST). Because the text is not sanitized, an attacker can inject misleading operational messages (e.g., fake "critical update required" or "corrupted key store, re-enter your credentials" prompts) directly into the trusted Operator UI, exactly the social-engineering vector described in the original report (used historically to trick users into installing malicious updates). It can also be used to obscure/confuse audit logs or inject formatting to make phishing content appear more legitimate within the same JSON error field the UI trusts.

### Likelihood Explanation
Bridges/external adapters are configured by node operators and often point at internet-reachable or partner-operated endpoints; a compromise of DNS, TLS, or the adapter host itself, or a bridge intentionally supplying malformed/malicious JSON, easily satisfies the trigger condition (`resp.StatusCode != http.StatusOK` or `eaResp.Result == "error"`-style path). No authentication bypass is needed — any bridge response with `{"error":{"name":..,"message":..}}` on a non-200/failure path reaches this code, making the likelihood moderate-to-high for a scenario with a compromised or malicious bridge target.

### Recommendation
- Do not forward raw adapter-supplied `error.message` text into `Result.Error`/`FatalErrors` verbatim; strip/escape control characters (especially newlines) and cap length before storing.
- Consider separating "diagnostic" error detail (kept only in structured logs) from a sanitized, bounded user/operator-facing error string, similar to the `sanitizeNodeErrorMessage` helper already used elsewhere in the gateway code (`core/services/gateway/handlers/confidentialrelay/bundler.go`) for peer/node error text, and apply the same pattern to `BestEffortExtractEAError` output before it flows into `Result.Error`.
- Consider not letting untrusted adapter text override the normal internal error entirely; at minimum tag/label it (e.g., "adapter reported: ...") so operators know it's untrusted-endpoint text, not a validated system message.

### Proof of Concept
1. Configure a bridge whose EA endpoint is attacker-controlled/compromised.
2. Have the EA return, on the failure path, e.g.:
   ```json
   {"error": {"name": "AdapterError", "message": "SECURITY ALERT\nYour node key is compromised. Download the fix at http://evil.example/update.sh and run it now."}}
   ```
3. Trigger the bridge task (e.g., via `TestBridgeTask_PipelineAdapterLWBAError`-style flow, which already demonstrates the adapter error message propagating into `finalResult.Result.Error` unmodified — see `core/services/pipeline/task.bridge_test.go:1307-1349`): [7](#0-6) 
4. Query the run via GraphQL `jobRun(id:...) { fatalErrors allErrors }` or REST `/v2/jobs/:id/runs/:id`; the operator sees the crafted phishing text rendered as-is in their trusted node dashboard.

func NewPipelineRunResource(pr pipeline.Run, lggr logger.Logger) PipelineRunResource {
	lggr = lggr.Named("PipelineRunResource")
	trs := make([]PipelineTaskRunResource, 0, len(pr.PipelineTaskRuns))
	for i := range pr.PipelineTaskRuns {
		trs = append(trs, NewPipelineTaskRunResource(pr.PipelineTaskRuns[i]))
	}

	outputs, err := pr.StringOutputs()
	if err != nil {
		lggr.Errorw(err.Error(), "out", pr.Outputs)
	}

	fatalErrors := pr.StringFatalErrors()

	return PipelineRunResource{
		JAID:         NewJAIDInt64(pr.ID),
		Outputs:      outputs,
		Errors:       fatalErrors,
		AllErrors:    pr.StringAllErrors(),
		FatalErrors:  fatalErrors,
		Inputs:       pr.Inputs,
		TaskRuns:     trs,
		CreatedAt:    pr.CreatedAt,
		FinishedAt:   pr.FinishedAt,
		PipelineSpec: NewPipelineSpec(&pr.PipelineSpec),
	}
}
