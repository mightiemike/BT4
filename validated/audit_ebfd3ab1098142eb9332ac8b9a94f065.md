Based on my investigation, I found a real gap in the JSON-RPC transaction-decode path that mirrors the CVE-2017-5335 bug class (unbounded allocation from an attacker-controlled length prefix before the rest of the data is validated).

### Title
Unbounded memory allocation from attacker-controlled Borsh length prefix in JSON-RPC `send_tx`/`tx` transaction decoding - ([File: chain/jsonrpc/src/api/transactions.rs])

### Summary
`decode_signed_transaction` in [1](#0-0)  base64-decodes the RPC caller-supplied `signed_tx_base64` string and calls `SignedTransaction::try_from_slice(&bytes)` directly, with no upper bound on the declared/decoded size before Borsh deserialization begins. This is reachable unauthenticated from `send_tx`, `broadcast_tx_async`, `broadcast_tx_commit`, and `tx` JSON-RPC methods, whose request types (`RpcSendTransactionRequest`, `RpcTransactionStatusRequest`) route straight into this function via `RpcRequest::parse` [2](#0-1) .

### Finding Description
The Borsh wire format encodes `Vec`/`String`/collection fields as a length prefix followed by the element bytes. Nested inside `SignedTransaction` → `Transaction` → `Vec<Action>`, and further inside action payloads such as `FunctionCallAction { args: Vec<u8> }`, `DeployContractAction { code: Vec<u8> }`, or `DeployGlobalContractAction`, there are multiple attacker-chosen `u32` length prefixes. A caller can submit a very small base64 payload whose length prefix(es) claim a length near `u32::MAX` while supplying only a few actual bytes; the deserializer allocates (or reserves) memory proportional to the claimed length before discovering the underlying byte slice is exhausted and failing.

This is exactly the same bug class as CVE-2017-5335: "the stream reading functions ... allow ... denial of service (out-of-memory error and crash) via a crafted ... certificate" whose length-prefixed fields are trusted for allocation sizing before the corresponding bytes are verified to exist.

Critically, the codebase's own authors have already recognized and mitigated this exact class elsewhere: `try_from_slice_with_limit` was added specifically to bound decode-time allocation for P2P `PeerMessage::Transaction` and `Routed` bodies before calling `try_from_slice` [3](#0-2) , with comments explicitly stating the purpose: "a maliciously inflated peer payload cannot force a large allocation at decode time" [4](#0-3) , and there are dedicated regression tests (`transaction_size_gate`, `routed_message_size_gate`) proving oversized bodies are rejected *before* Borsh-decoding [5](#0-4) . The equivalent `max_transaction_size` check in `ValidatedTransaction::check_valid_for_config` [6](#0-5)  only runs *after* the transaction has already been fully decoded — it cannot prevent the OOM that happens during decode itself. The JSON-RPC entry point (`decode_signed_transaction`) never applies any pre-decode size gate, unlike its P2P-network counterpart.

### Impact Explanation
An unprivileged, unauthenticated RPC caller can send crafted `send_tx`/`tx` requests that force the node to attempt very large memory allocations during Borsh deserialization, before any transaction validation, signature check, or size limit is applied. Repeated or concurrent requests of this kind can exhaust node memory and crash the JSON-RPC-serving node process — a transaction/RPC-request-triggered denial of service, matching the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
High likelihood of reachability: `send_tx`/`tx` are public, unauthenticated JSON-RPC endpoints exposed by every node that runs the JSON-RPC server (the default for many node configurations, including RPC nodes relied upon by wallets and indexers). No signature, stake, or account state is required to reach `decode_signed_transaction` — it is the very first step of request parsing, before any validation.

### Recommendation
Apply the same mitigation already used for the P2P path: reject the base64-decoded byte length against a hard cap (e.g. reuse or mirror `MAX_TRANSACTION_SIZE_BYTES` from `chain/network/src/network_protocol/proto_conv/peer_message.rs`, or use `try_from_slice_with_limit`) in `decode_signed_transaction` before calling `SignedTransaction::try_from_slice`, so an inflated length prefix cannot be used to force a large allocation prior to any real size or signature validation.

### Proof of Concept
1. Construct a byte buffer that begins with a valid `SignedTransaction` Borsh discriminant/`AccountId` prefix, then set an inner `Vec<Action>` (or a `FunctionCallAction.args` / `DeployContractAction.code`) length field to `0xFFFFFFFF`, followed by only a handful of trailing bytes (well under 100 bytes total).
2. Base64-encode this buffer and submit it as `signed_tx_base64` to the `send_tx` (or `tx`) JSON-RPC method on a target node.
3. Observe `decode_signed_transaction` (`chain/jsonrpc/src/api/transactions.rs:71-76`) attempting to allocate/reserve ~4 GiB for the claimed vector length before the read fails, with no pre-decode size gate to stop it; repeating this concurrently drives the node toward OOM.

fn decode_signed_transaction(value: String) -> Result<SignedTransaction, RpcParseError> {
    let bytes = near_primitives::serialize::from_base64(&value)
        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))?;
    SignedTransaction::try_from_slice(&bytes)
        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))
}

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}

/// Upper bound on the Borsh-encoded size of a peer-supplied transaction body,
/// enforced before the body is deserialized to mitigate maliciously inflated
/// transactions exhausting node memory at decode time. Set comfortably above
/// the largest valid transaction (`max_transaction_size`, historically 4 MiB)
/// and far below the 512 MiB peer-frame cap.
const MAX_TRANSACTION_SIZE_BYTES: usize = 16 * MIB as usize;

/// Upper bound on the Borsh-encoded size of a peer-supplied routed-message body,

/// `ForwardTx` carrying an oversized delegate action) cannot exhaust node memory
/// at decode time.
const MAX_ROUTED_MESSAGE_SIZE_BYTES: usize = 64 * MIB as usize;
