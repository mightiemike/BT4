### Title
Legacy `DelegatedResourceAccountIndex` (`toAccounts`/`fromAccounts`) can be grown without bound and at zero marginal fee, forcing unbounded read/rewrite cost onto unrelated victims - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
The external report describes NFTfi's `proceeds` array, which appended one element per refinance with no cap and no cost proportional to array size, so it could be grown by a malicious actor and later forced an unrelated party (the borrower) to pay for iterating/settling the whole bloated array. The closest analog in java-tron is the legacy (pre-`AllowDelegateOptimization`) `DelegatedResourceAccountIndex` mechanism used by `FreezeBalanceContract`/`UnfreezeBalanceContract`. When resource delegation optimization is not enabled, delegating resources appends the counterparty address to a `toAccounts`/`fromAccounts` list stored as a single protobuf blob keyed by account, with no maximum size, and this list must be fully loaded, copied, linearly searched, and rewritten on every delegate/undelegate touching that account — while the actuator itself charges zero fee (`calcFee()` returns `0`).

### Finding Description
In the legacy path of `FreezeBalanceActuator.delegateResource()`, whenever an owner delegates bandwidth/energy to a receiver, both the owner's and the receiver's `DelegatedResourceAccountIndexCapsule` are updated: [1](#0-0) 

Each call does:
- `delegatedResourceAccountIndexStore.get(ownerAddress)` — loads the *entire* existing list.
- `if (!toAccountsList.contains(...)) ownerIndexCapsule.addToAccount(...)` — an O(n) `contains()` check against the whole list before appending.
- The same is mirrored on the receiver's `fromAccountsList`.
- The updated capsule (now containing the whole, ever-growing list) is written back to the DB in full: `delegatedResourceAccountIndexStore.put(...)`.

The list itself is unbounded — there is no cap analogous to `MultiSourceLoan._maxSources` limiting the number of `toAccounts`/`fromAccounts` entries a single index can hold: [2](#0-1) 

Crucially, an attacker does **not** need the victim's cooperation to grow the victim's list: the attacker can create many distinct owner accounts and delegate small (or even minimal) resource amounts *to* a fixed victim receiver address, appending an entry to the victim's `fromAccountsList` every time. Because this is the *receiver's* list, the victim has no control over how large it grows.

Once the list is large, cleanup is expensive for anyone who touches the affected address. In `UnfreezeBalanceActuator`, releasing a single delegated resource entry requires copying the *entire* list into a new `ArrayList`, doing a linear `remove()`, and writing the entire list back: [3](#0-2) 

This mirrors the report's core defect: an attacker-controlled, unbounded, append-only structure that (a) is not capped, (b) is not priced according to its growth, and (c) must be fully traversed/rewritten by unrelated parties during normal, unprivileged operations (`FreezeBalanceContract`/`UnfreezeBalanceContract`), which both charge `calcFee() == 0`: [4](#0-3) 

The optimized path (`supportAllowDelegateOptimization()`) replaces this with per-pair keyed entries (`delegate`/`unDelegate`/`delegateV2`/`unDelegateV2`) that avoid single-blob growth: [5](#0-4) 
but the legacy code path remains present and reachable whenever the `AllowDelegateOptimization` committee proposal has not been (or was not yet) enabled, and any state accumulated under the legacy scheme persists in the DB even if the proposal is later toggled on.

### Impact Explanation
If the delegate-optimization proposal is not enabled (or wasn't enabled from genesis on some chain/testnet/fork based on this codebase), an attacker can:
1. Create N throwaway accounts (bounded only by account-creation cost, not the state-bloat cost).
2. Have each account send a `FreezeBalanceContract` (fee = 0, only bandwidth/energy consumption) delegating a minimal amount of resource to one fixed victim address.
3. Each such transaction is O(1) to construct/broadcast for the attacker but permanently appends to the victim's `fromAccountsList`, an object that is deserialized and reserialized in full on every future interaction (delegate/undelegate, or any wallet/API query of `getDelegatedResourceAccountIndex`) touching that address.

This causes state bloat and asymmetric, underpriced computation: readers/writers of the victim's index (including block-validating full nodes) must pay ever-increasing (de)serialization and list-copy cost that is not reflected in the bandwidth/energy fee model, since `calcFee()` for these actuators is fixed at 0 and consumption is based on raw transaction size, not on the size of the state structure being mutated. In the worst case this can degrade block-processing performance for all nodes and denies/burdens the victim (and any node syncing/querying its delegation index) — an accounting/state-growth impact class analogous to the original "proceeds array" DoS.

### Likelihood Explanation
Likelihood is moderate: exploitation only works on chains/environments where the legacy (non-optimized) delegated-resource path is active, i.e., `supportAllowDelegateOptimization()` is false. I could not fully confirm from the index alone whether this proposal is enabled by default on current java-tron mainnet or only becomes enabled via committee proposal after a certain block; the code clearly still supports and executes the legacy branch when the flag is off, and historical/legacy-accumulated indexes are not automatically pruned or capped when the optimization is turned on later. Additionally, the actuator's own fee is zero, and the primary cost to the attacker is only bandwidth/account-creation, which is comparatively cheap relative to the growing burden imposed on the victim address and any node that must process it.

### Recommendation
- Cap the number of entries permitted in a single `DelegatedResourceAccountIndexCapsule`'s `toAccounts`/`fromAccounts` lists (analogous to `MultiSourceLoan._maxSources`), rejecting further legacy-style delegations once the cap is reached and directing users to the optimized (`delegate`/`delegateV2`) keyed-index scheme instead.
- Migrate/deprecate the legacy single-blob index entirely (retire the `supportAllowDelegateOptimization() == false` branch) so all delegation bookkeeping uses the per-pair keyed store, which does not require loading/rewriting an entire list per operation.
- If the legacy path must remain for backward compatibility, price `FreezeBalanceContract`/`UnfreezeBalanceContract` fees (or bandwidth consumption) proportionally to the current size of the target account's delegation index, so the cost of forcing state growth is borne by the party causing it.

### Proof of Concept
1. Deploy/observe a java-tron network where `DynamicPropertiesStore.supportAllowDelegateOptimization()` returns `false` (default/un-proposed state).
2. Choose victim address `V` (does not need to sign or approve anything).
3. Loop N times (bounded only by attacker's TRX for account creation and fees):
   - Create a new throwaway account `Ai`.
   - Send `FreezeBalanceContract` from `Ai` with `receiverAddress = V`, a minimal `frozenBalance`, for `BANDWIDTH` or `ENERGY`, hitting `FreezeBalanceActuator.delegateResource()`.
4. Each iteration appends one entry to `V`'s `fromAccountsList` via `DelegatedResourceAccountIndexCapsule.addFromAccount()`, growing the single protobuf-serialized blob stored under `V`'s key in `DelegatedResourceAccountIndexStore` without limit.
5. Observe that any subsequent `UnfreezeBalanceContract` touching `V` (from any of the `Ai` accounts) must deserialize, copy, and rewrite `V`'s entire `fromAccountsList` (`UnfreezeBalanceActuator.java` lines 162-182), with cost growing linearly in N, while `calcFee()` for both actuators remains `0`, demonstrating the unbounded, underpriced state-growth/DoS analog to the original "proceeds array" issue.

    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);

  public void delegate(byte[] from, byte[] to, long time) {
    byte[] fromKey = Bytes.concat(FROM_PREFIX, from, to);
    DelegatedResourceAccountIndexCapsule toIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));
    toIndexCapsule.setTimestamp(time);
    this.put(fromKey, toIndexCapsule);

    byte[] toKey = Bytes.concat(TO_PREFIX, to, from);
    DelegatedResourceAccountIndexCapsule fromIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(from));
    fromIndexCapsule.setTimestamp(time);
    this.put(toKey, fromIndexCapsule);
  }

  public void delegateV2(byte[] from, byte[] to, long time) {
    byte[] fromKey = Bytes.concat(V2_FROM_PREFIX, from, to);
    DelegatedResourceAccountIndexCapsule toIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));
    toIndexCapsule.setTimestamp(time);
    this.put(fromKey, toIndexCapsule);

    byte[] toKey = Bytes.concat(V2_TO_PREFIX, to, from);
    DelegatedResourceAccountIndexCapsule fromIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(from));
    fromIndexCapsule.setTimestamp(time);
    this.put(toKey, fromIndexCapsule);
  }
