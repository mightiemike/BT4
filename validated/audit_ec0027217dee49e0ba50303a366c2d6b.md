### Title
Missing `supportUnfreezeDelay()` committee-gate check in TVM native `UnDelegateResourceProcessor` allows resource unlocking via smart-contract calls before the feature is enabled - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
`UnDelegateResourceActuator.validate()` requires both `dynamicStore.supportDR()` and `dynamicStore.supportUnfreezeDelay()` to be true before allowing an un-delegate-resource operation to proceed. The TVM-native equivalent, `UnDelegateResourceProcessor.validate()` (invoked when a smart contract calls the native `unDelegateResource` precompile/opcode), only checks `supportDR()` and never checks `supportUnfreezeDelay()`.

### Finding Description
The regular contract-type actuator gates execution with two committee proposal flags: [1](#0-0) 

The TVM native-contract processor used by `TriggerSmartContract`/`CreateSmartContract` calls (reachable by any ordinary account or contract deployer, no privileged role needed) only checks `supportDR()`: [2](#0-1) 

Grepping the codebase for `UnfreezeDelay`/`supportUnfreezeDelay` shows no occurrence in `Program.java`, `OperationRegistry.java`, or `OperationActions.java` — the opcode dispatch layer that routes TVM contract calls into `UnDelegateResourceProcessor` — confirming there is no additional gate at the VM level either. This means once the committee enables `AllowDelegateResource` (`supportDR()`), but before it separately enables the `UnfreezeDelay` proposal (`supportUnfreezeDelay()`), an ordinary account can deploy or call a smart contract that invokes the native `unDelegateResource` precompile and successfully execute the same state-mutating logic (`execute()` in `UnDelegateResourceProcessor`, lines 91-210) that the plain `UnDelegateResourceContract` transaction path would reject.

This is not literally the "different ContractType routes to the same actuator `execute()`" mechanism hypothesized in the question — `TransactionFactory`/`ActuatorCreator` bind each `ContractType` to exactly one `Actuator` class 1:1, and `this.any.is(UnDelegateResourceContract.class)` in `validate()` rejects mismatched payload types, so that specific bypass vector does not exist. [3](#0-2) [4](#0-3)  However, the TVM native-contract path is a genuinely separate, parallel code path implementing equivalent state changes with a strictly weaker gate, which is a real feature-gate inconsistency of the same class described in the invariant (AUTHORIZATION_ENFORCED at protocol/feature-gate level).

### Impact Explanation
If `AllowDelegateResource` is enabled but `UnfreezeDelay` is intentionally kept disabled by the committee (e.g., during a phased rollout), any unprivileged smart-contract deployer/caller can still trigger the un-delegate/unlock logic via the TVM path, unlocking delegated resources ahead of the intended gated rollout. Because this is deterministic logic executed identically by all nodes running the same code (not a fork/version split), it does not cause consensus divergence between nodes, but it does violate the intended committee-controlled feature gate, resulting in unauthorized/premature resource unlocking.

### Likelihood Explanation
Preconditions: `AllowDelegateResource` proposal enabled, `UnfreezeDelay` proposal disabled — a plausible intermediate chain state during phased feature rollouts. The attacker needs only a funded account able to deploy/trigger a smart contract that calls the native `unDelegateResource` precompile, paying ordinary energy/bandwidth fees — no privileged role, MITM, or non-default configuration required.

### Recommendation
Add a `dynamicStore.supportUnfreezeDelay()` check to `UnDelegateResourceProcessor.validate()` in `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`, mirroring the check present in `UnDelegateResourceActuator.validate()`, so both entry points enforce identical committee-gated feature flags.

### Proof of Concept
```java
// JUnit-style PoC in framework/src/test/java/org/tron/core/vm/nativecontract (conceptual)
@Test
public void testUnDelegateResourceProcessorBypassesUnfreezeDelayGate() throws Exception {
  dynamicStore.saveAllowDelegateResource(1);   // supportDR() == true
  // supportUnfreezeDelay() left at default/disabled (0)

  UnDelegateResourceParam param = new UnDelegateResourceParam();
  param.setOwnerAddress(ownerAddress);
  param.setReceiverAddress(receiverAddress);
  param.setUnDelegateBalance(1_000_000L);
  param.setResourceType(BANDWIDTH);

  UnDelegateResourceProcessor processor = new UnDelegateResourceProcessor();
  // Expected (per actuator parity): should throw ContractValidateException
  // Actual: passes validate() because supportUnfreezeDelay() is never checked
  processor.validate(param, repository); // does NOT throw -> gate bypass confirmed
  processor.execute(param, repository);  // resource state mutated
}
```
Real-world trigger: deploy a Solidity contract invoking the native `unDelegateResource` precompile and broadcast a `TriggerSmartContract` transaction to it while `UnfreezeDelay` is disabled; compare against a direct `UnDelegateResourceContract` transaction, which is correctly rejected with `"Not support unDelegate resource transaction, need to be opened by the committee"`.
