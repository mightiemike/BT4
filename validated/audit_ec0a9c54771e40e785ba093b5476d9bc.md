### Title
Post-validation `output_data_receivers` append lets receipts exceed `max_receipt_size`, bypassing the size gate that bounds `ChunkStateWitness` and congestion accounting - ([File: runtime/runtime/src/lib.rs])

### Summary
This is a genuine, currently-open analog of the CVE-2023-3611 bug class: a size-derived limit (`max_receipt_size`, playing the role of `lmax`) is validated once against a value that is *later* mutated (growing the object) without re-validation, letting the object exceed the bound that downstream code assumes is authoritative. In nearcore the object is a `Receipt`, not a kernel packet buffer, so the consequence is not raw memory corruption, but it breaks the protocol invariant that receipt/witness sizes are capped, which the codebase itself explicitly tracks as an unresolved defect (`https://github.com/near/nearcore/issues/12606`).

### Finding Description
`validate_receipt` in `ValidateReceiptMode::NewReceipt` mode checks a freshly created receipt's borsh size against `limit_config.max_receipt_size` [1](#0-0) . This check runs immediately after `apply_action` produces `new_receipts` for the current action [2](#0-1) .

However, in `Runtime::process_action_receipt`, *after* actions are executed and results merged, the code mutates a receipt that already exists in `new_receipts` by appending `output_data_receivers` onto it when the action's result is `ReturnData::ReceiptIndex` (the `promise_return` case): `new_action_receipt.output_data_receivers.extend_from_slice(&action_receipt.output_data_receivers())` [3](#0-2) . This mutation happens strictly after the per-action `validate_receipt` size check already passed for that receipt, so a receipt that was exactly at (or near) `max_receipt_size` at validation time can grow past the limit afterward with no re-check. The `ValidateReceiptMode::ExistingReceipt` doc comment and the dedicated regression tests confirm this is a known, still-open issue (nearcore issue #12606), not a theoretical concern [4](#0-3) [5](#0-4) .

The `max_receipt_size` bound is not cosmetic — it is one of the load-bearing limits that keep `ChunkStateWitness` under its ~21 MiB design budget, alongside `outgoing_receipts_usual_size_limit`/`outgoing_receipts_big_size_limit` and `main_storage_proof_size_soft_limit` [6](#0-5) . The runtime is aware oversized receipts exist in the wild and only papers over the *forwarding* consequence by clamping the observed size to `max_receipt_size` when checking bandwidth/congestion admission — but this clamp does not shrink the actual serialized receipt that gets embedded in a chunk/witness, it only fudges the accounting so the receipt is not stuck forever: `if size > max_receipt_size { ...; size = max_receipt_size; }` [7](#0-6) . The same clamp-workaround is duplicated in bandwidth-request generation for the same reason [8](#0-7) .

### Impact Explanation
An unprivileged contract deployer/caller (any account, via a normal `FunctionCall` with a nested `promise_then`/`promise_return` DAG) can craft a receipt whose args are sized to sit at `max_receipt_size` and then have `output_data_receivers` appended post-validation, pushing the true serialized size above the protocol's declared cap while all downstream size-gating code (congestion/bandwidth admission) is fooled into treating it as `max_receipt_size`. Because `main_storage_proof_size_soft_limit`, `combined_transactions_size_limit`, and the receipt-size budget were sized specifically to keep total `ChunkStateWitness` size bounded (~21 MiB), an attacker can inflate actual witness/receipt bytes beyond the assumed budget while congestion bookkeeping (`receipt_bytes`, `buffered_receipts_gas`) undercounts the true size. This is a state-witness/size-limit-integrity violation reachable purely from transaction submission, matching the in-scope "state-witness limits" and "cross-shard receipts with congestion control and bandwidth scheduling" categories. It is not (in current Rust nearcore) a raw out-of-bounds memory write like the Linux kernel bug, but it is the direct structural analog: a bound is validated against a size that is allowed to grow afterward without re-validation, and the system's own tests document the runtime currently "shouldn't die" when this occurs, i.e., it's treated as tolerated bad state rather than fixed.

### Likelihood Explanation
High likelihood of reachability: it requires only a signed transaction from any funded account with a deployed contract that builds a two-hop promise DAG (`promise_then` then `promise_return` with a receipt near `max_receipt_size`), exactly as reproduced by the existing `test_max_receipt_size_promise_return` regression test [9](#0-8) . No privileged role, validator collusion, or network-level assumption is needed.

### Recommendation
Re-validate (or re-clamp/reject) receipt size after any post-hoc mutation of `new_receipts` — in particular after the `output_data_receivers.extend_from_slice` in `runtime/runtime/src/lib.rs` around line 1164 — instead of only validating once before the mutation. Alternatively, reserve headroom in the pre-mutation check (subtract the maximum possible `output_data_receivers` bytes from the size budget before creating the receipt) so the post-append size can never exceed `max_receipt_size`. Track this against the existing tracked issue #12606 rather than leaving the size-limit invariant unenforced.

### Proof of Concept
Use the existing repo regression test as the reproduction recipe: deploy `near_test_contracts::rs_contract()`, call `max_receipt_size_promise_return_method1` with `args_size` sized so the intermediate receipt's `FunctionCall` payload equals `max_receipt_size - base_receipt_size` (4 194 304 − base size), which builds DAG `A -> B` then, inside `A`'s execution, creates promise `C` at exactly `max_receipt_size` and does `promise_return(C)`, causing `C`'s `output_data_receivers` to be extended post-validation and pushing its true size above `max_receipt_size` [10](#0-9) [11](#0-10) .

**File:** docs/misc/state_witness_size_limits.md (L13-40)
```markdown
* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
* `max_receipt_total_input_size - 4 MiB + 640 B`
  * Hard limit on the combined size of a receipt's resolved promise inputs (the `ReceivedData` referenced by its `input_data_ids`). Receipts which exceed it fail with `TotalPromiseInputSizeExceeded` without executing their actions.
  * These inputs are read before `per_receipt_storage_proof_size_limit` starts counting, so without this limit a single receipt could pull `max_number_input_data_dependencies * max_receipt_size` (128 * 4 MiB) into the witness.
  * The limit is `max_length_returned_data` (4 MiB) plus the worst-case per-input framing overhead (128 * 5 bytes), so 4 MiB of input data always fits no matter how it's split across data receipts.
* `combined_transactions_size_limit - 4 MiB`
  * Hard limit on total size of transactions from this and previous chunk. `ChunkStateWitness` contains transactions from two chunks, this limit applies to the sum of their sizes.
* `new_transactions_validation_state_size_soft_limit - 500 KiB`
  * Validating new transactions generates storage proof (recorded trie nodes), which has to be limited. Once transaction validation generates more storage proof than this limit, the chunk producer stops adding new transactions to the chunk.
* `per_receipt_storage_proof_size_limit - 4 MB`
  * Executing a receipt generates storage proof. A single receipt is allowed to generate at most 4MB of storage proof. This is a hard limit, receipts which generate more than that will fail.
* `main_storage_proof_size_soft_limit - 4 MB`
  * This is a limit on the total size of storage proof generated by receipts in one chunk. Once receipts generate more storage proof than this limit, the chunk producer stops processing receipts and moves the rest to the delayed queue.
  * It's a soft limit, which means that the total size of storage proof could reach 8 MB (3.99MB + one receipt which generates 4MB of storage proof)
  * Due to implementation details it's hard to find the exact amount of storage proof generated by a receipt, so an upper bound estimation is used instead. This upper bound assumes that every removal generates additional 2000 bytes of storage proof, so receipts which perform a lot of trie removals might be limited more than theoretically applicable.
* `outgoing_receipts_usual_size_limit - 100 KiB`
  * Limit on the size of outgoing receipts to another shard. Needed to keep the size of `source_receipt_proofs` small.
  * On most block heights a shard isn't allowed to send receipts larger than 100 KiB to another shard.
* `outgoing_receipts_big_size_limit - 4.5 MiB`
  * On every block height there's one special "allowed shard" which is allowed to send larger receipts, up to 4.5 MiB in total.
  * A receiving shard will receive receipts from `num_shards - 1` shards using the usual limit and one shard using the big limit.

In total that gives 4 MiB + 500 KiB + 8MB + 4 MiB + 5*100 KiB + 4.5 MiB ~= 21 MiB of maximum witness size. Possibly a little more on missing chunks.
```
