### Title
Permission_id is printed as a per-contract JSON field but never explicitly re-applied by `packTransaction`, risking silent auth-scope loss on display-edit-resubmit - ([File: framework/src/main/java/org/tron/core/services/http/Util.java])

### Summary
`Util.printTransactionToJSON` and `Util.packTransaction` are not symmetric with respect to `permission_id`. The print path explicitly injects `contract.getPermissionId()` into a synthetic `Permission_id` key on each contract's JSON object, while the pack path never reads that key back out explicitly — it relies entirely on `JsonFormat.merge` reconstituting the field from the whole-transaction JSON string against the `Transaction.Contract` protobuf descriptor. The claimed "different Java class between print and pack" precondition in the question is **not** true (both paths call the identical `TransactionFactory.getContract(contract.getType())`), but the `permission_id` propagation path is genuinely asymmetric and unverified in the code itself.

### Finding Description
In `printTransactionToJSON`, the contract type lookup is identical between print and pack — both call `TransactionFactory.getContract(contract.getType())` [1](#0-0) [2](#0-1) , so there is no class-mapping divergence to exploit.

For `permission_id`, the print path adds it as a sibling key on the per-contract JSON object only when it is greater than zero: [3](#0-2) 

`packTransaction`, however, only explicitly reads and remaps `"type"` and `"parameter"` from each contract JSON object [4](#0-3) . The `Permission_id` key is never explicitly extracted or set on the rebuilt `Transaction.Contract` builder anywhere in `packTransaction`. Its only possible path back into the final `Transaction` is via the single trailing call `JsonFormat.merge(jsonTransaction.toJSONString(), transactionBuilder, selfType)` [5](#0-4) , which merges the entire JSON tree (including the untouched `contract` array elements) generically against the `Transaction` proto descriptor.

This is inherently fragile because elsewhere in the same file, `Permission_id` is treated as a *custom, non-protobuf-native* API convention that must be read out and applied manually via `setTransactionPermissionId(JSONObject, Transaction)` [6](#0-5) , rather than something `JsonFormat.merge` is expected to understand automatically for arbitrary nested contract objects. `packTransaction` does not call this helper, nor any equivalent, for the per-contract `Permission_id` values it silently carries through in the JSON structure.

I was unable to fully verify, within the available tool budget, whether `JsonFormat.merge`'s internal field-matching logic (case sensitivity / snake_case vs. camelCase handling / unknown-field tolerance) happens to coincidentally succeed in mapping `"Permission_id"` onto the real `permission_id` field descriptor of `Transaction.Contract`. If it does not match:
- Either the merge throws a `ParseException` on the unknown field, causing the *entire* transaction reconstruction to fail (`packTransaction` returns `null`) for any transaction that had a non-zero `permission_id` on any contract, or
- The merge silently ignores the unrecognized key, causing the resulting `Transaction.Contract.permission_id` to default to `0` (owner permission) even though the printed/displayed JSON showed a non-zero permission.

### Impact Explanation
If the "silent drop" behavior occurs, a transaction requiring a specific multi-signature permission (e.g., an "active" permission with a distinct signer set/threshold) that is displayed via `printTransactionToJSON` and later reconstructed via `packTransaction` (e.g. in an edit/resubmit or JSON-based signing workflow) would have its `permission_id` reset to `0`. This changes which key set and signature threshold is required at broadcast/validation time relative to what was shown to the signer, which is exactly the auth-invariant violation the question describes. If instead the "hard failure" behavior occurs, the impact is a denial-of-service / correctness bug (any non-default-permission transaction cannot be round-tripped) rather than an authorization bypass.

### Likelihood Explanation
This requires exact confirmation of `JsonFormat.merge`'s (framework/src/main/java/org/tron/core/services/http/JsonFormat.java) field-matching behavior for unrecognized JSON keys nested inside a repeated message field, which I could not verify with the tools available in this session. The asymmetry in the code (explicit read of `type`/`parameter`, no explicit read of `Permission_id`) is confirmed and real, but whether it manifests as an actual runtime bypass, a runtime parse failure, or a harmless no-op (if merge happens to correctly resolve the field) is unconfirmed.

### Recommendation
Regardless of `JsonFormat.merge`'s exact behavior, `packTransaction` should not rely on implicit merge behavior for `permission_id`. It should explicitly read `contract.getInteger(Util.PERMISSION_ID)` for each contract element and call `.setPermissionId(...)` on the rebuilt `Transaction.Contract.Builder`, mirroring how `type` and `parameter` are already handled explicitly. Add a full byte-equality round-trip unit test across every registered `ContractType` (including a non-zero `permission_id`) to lock in this invariant going forward.

### Proof of Concept
```java
// In UtilTest.java (or a new fuzz test class)
@Test
public void testPermissionIdRoundTrip() {
  for (ContractType type : TransactionFactory_getAllRegisteredTypes()) { // iterate contractMap keys
    Transaction original = buildTransactionWithContract(type, /* permissionId */ 2);
    String json = Util.printTransaction(original, true);
    Transaction rebuilt = Util.packTransaction(json, true);
    assertNotNull("packTransaction returned null for type " + type, rebuilt);
    assertEquals("permission_id lost/changed for type " + type,
        original.getRawData().getContract(0).getPermissionId(),
        rebuilt.getRawData().getContract(0).getPermissionId());
    assertArrayEquals("raw_data byte mismatch for type " + type,
        original.getRawData().toByteArray(), rebuilt.getRawData().toByteArray());
  }
}
```
Expected result if the bug is present: either an `AssertionError` on `permission_id` (silently reset to 0) or `rebuilt == null` (merge failure) for contracts with non-zero `permission_id`, confirming the round-trip asymmetry.
