### Title
Stale cached `cycle-total-weight` in `.signers-voting` lets a minority of signer weight approve or block an aggregate public key - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
`.signers-voting` caches the total signer weight for a reward cycle the first time it is needed, and never recomputes it even if the underlying `.signers` contract's `cycle-signer-set` for that same reward cycle is later overwritten. This mirrors the reported bug class: a derived/cached scalar (`unit` in the report, `cycle-total-weight` here) is not kept in sync with the array/list it was derived from (`curve`/`cycle-signer-set`), so the equality/threshold computed from the stale cache diverges from what the live data would produce.

### Finding Description
`.signers` stores per-cycle signer lists in the `cycle-signer-set` map, gated only by `last-set-cycle` matching the given `reward-cycle` — nothing prevents `set-signers` from being invoked more than once for the same `reward-cycle` value: [1](#0-0) 

`.signers-voting` caches the total weight for a reward cycle on first use and thereafter always returns the cached value without checking whether `.signers`' underlying list has changed: [2](#0-1) 

The consensus threshold and the vote-acceptance path both key off this stale cache: [3](#0-2) [4](#0-3) 

Per-signer weight lookups (`get-signer-weight` → `.signers.get-signer-by-index`) are *not* cached and always read the live, current `cycle-signer-set`: [5](#0-4) [6](#0-5) 

This is the same shape as the reported bug: `total_signing_weight`/`unit`-style derived aggregates are computed once and cached, but the source array they were derived from (`curve` in the report, `cycle-signer-set` here) can subsequently change, and nothing invalidates or recomputes the cached aggregate. On the node side, the reward set / signer set for a given reward cycle is (re)computed via `pox_4_compute_and_update_signers` / `pox_5_compute_and_update_signers`, which call `update_signers` → `.signers.set-signers`: [7](#0-6) [8](#0-7) 

If the reward-set/signer-set calculation is (re)performed a second time for the same `reward_cycle` number against a different chain state (e.g. a different fork's tip, or a later block within the same prepare phase that recomputes participation from a changed liquid-uSTX / stacked amount), `set-signers` will happily overwrite `cycle-signer-set` for that cycle (its only guard is `last-set-cycle == reward-cycle`, which the caller trivially still satisfies), while `.signers-voting`'s `cycle-total-weight` map for that same cycle keeps the value computed from the *first* signer set it ever saw.

### Impact Explanation
Once the signer list for a cycle is updated a second time but the cached total weight is not, two live values diverge that must stay in lock-step for the consensus computation to be correct:
- `get-signer-weight` reads the *new* (post-update) signer weight for a voting signer.
- `get-threshold-weight`/`cycle-total-weight` still reflects the *old* (pre-update) total weight.

If the new signer set's real total weight is larger than the stale cached total (e.g. more/larger signers registered on the second computation), the 70%-of-total threshold computed from the smaller stale total is easier to reach: a genuinely minority fraction of the *actual* current signer weight can push `new-total >= threshold-weight` and get an aggregate public key approved in `aggregate-public-keys` for that cycle, even though it did not command 70% of the true, live signer weight. This is a minority-triggerable divergence between the on-chain "approved aggregate key" state and what the honest majority of the current signer set would have produced — a consensus-threshold violation bounded to the DKG/vote-approval path (temporary tip/consensus disagreement about which aggregate key is authoritative for the cycle), matching the "signer weight below threshold or from the wrong set" analog class explicitly called out as in-scope.

### Likelihood Explanation
This requires that `pox_{4,5}_compute_and_update_signers`/`update_signers` actually execute more than once for the same `reward_cycle` value with a different underlying signer/stake snapshot (e.g., across a fork/reorg at the prepare-phase boundary, or a later block in the prepare window recomputing PoX-5 stake entries as more `stack-stx`/delegation transactions land before the cycle boundary is finalized). I was not able to fully confirm from the excerpts examined whether the node-side reward-cycle-calculation trigger is provably idempotent (called exactly once per cycle) or can be invoked again for the same `reward_cycle` under a reorg/late-participation scenario — this needs further tracing of the call sites feeding `pox_4_compute_and_update_signers`/`pox_5_compute_and_update_signers` in `stackslib/src/chainstate/stacks/db/blocks.rs`, which reference these functions but were not opened in full. If invocation is strictly idempotent per cycle in practice, this finding degrades to defense-in-depth; if not, it is directly triggerable by any minority signer submitting votes after such a re-set.

### Recommendation
- Invalidate (delete) `cycle-total-weight` for a reward cycle whenever `.signers.set-signers` is called again for that cycle, or
- Recompute (don't cache) the total weight on every vote by summing the *current* `.signers.get-signers` list, or
- Have `.signers-voting` cache a checksum/version of the signer list alongside the cached total, and recompute if the version changes.

### Proof of Concept
1. Node computes the reward-cycle signer set the first time and calls `.signers.set-signers(reward_cycle, signers_v1)`, where `total_weight(signers_v1) = W1`.
2. A signer calls `vote-for-aggregate-public-key`, which triggers `get-and-cache-total-weight` to cache `W1` in `cycle-total-weight[reward_cycle]`.
3. Before the vote reaches the (70% of `W1`) threshold, the node recomputes the reward set for the same `reward_cycle` (e.g., due to a fork/reorg or a later prepare-phase recalculation with more participation) and calls `set-signers(reward_cycle, signers_v2)` again, where `total_weight(signers_v2) = W2 >> W1` (more/larger signers registered).
4. Remaining voting signers (still a small fraction of `W2`, but comparable to `W1`) vote; `get-signer-weight` reads their *live* weight from `signers_v2`, but `get-threshold-weight` still divides by the stale cached `W1`.
5. `new-total >= (W1 * 70) / 100` is reached using only a minority fraction of the true `W2` total, and the aggregate key gets inserted into `aggregate-public-keys[reward_cycle]` — a consensus approval that does not reflect 70% of the actual signer weight for that cycle.

    fn update_signers(
        clarity: &mut ClarityTransactionConnection,
        reward_cycle: u64,
        signers: &Vec<NakamotoSignerEntry>,
        signers_contract: &QualifiedContractIdentifier,
        has_participation: bool,
        coinbase_height: u64,
        is_mainnet: bool,
    ) -> Result<Vec<StacksTransactionEvent>, ChainstateError> {
        let sender_addr = PrincipalData::from(boot::boot_code_addr(is_mainnet));
        let stackerdb_list = if !has_participation {
            vec![]
        } else {
            signers
                .iter()
                .map(|signer| {
                    let signer_hash = Hash160::from_data(&signer.signing_key);
                    let signing_address = StacksAddress::p2pkh_from_hash(is_mainnet, signer_hash);
                    let tuple_data = TupleData::from_data(vec![
                        (
                            ClarityName::from_literal("signer"),
                            Value::Principal(PrincipalData::from(signing_address)),
                        ),
                        (ClarityName::from_literal("num-slots"), Value::UInt(1)),
                    ])
                    .map_err(|e| {
                        ChainstateError::Expects(format!(
                            "Failed to create tuple for stackerdb entry: {e}"
                        ))
                    })?;
                    Ok::<Value, ChainstateError>(Value::Tuple(tuple_data))
                })
                .collect::<Result<Vec<_>, _>>()?
        };

        let signers_list = if !has_participation {
            vec![]
        } else {
            signers
                .iter()
                .map(|signer| {
                    let signer_hash = Hash160::from_data(&signer.signing_key);
                    let signing_address = StacksAddress::p2pkh_from_hash(is_mainnet, signer_hash);
                    let tuple = TupleData::from_data(vec![
                        (
                            ClarityName::from_literal("signer"),
                            Value::Principal(PrincipalData::from(signing_address)),
                        ),
                        (
                            ClarityName::from_literal("weight"),
                            Value::UInt(signer.weight.into()),
                        ),
                    ])
                    .map_err(|e| {
                        ChainstateError::Expects(format!(
                            "Failed to create tuple for signers entry: {e}"
                        ))
                    })?;
                    Ok::<Value, ChainstateError>(Value::Tuple(tuple))
                })
                .collect::<Result<Vec<_>, _>>()?
        };

        if signers_list.len() > SIGNERS_MAX_LIST_SIZE {
            return Err(ChainstateError::Expects(format!(
                "signers list returned by reward set calculations longer than maximum ({} > {SIGNERS_MAX_LIST_SIZE})",
                signers_list.len()
            )));
        }

        let set_stackerdb_args = [
            SymbolicExpression::atom_value(Value::cons_list_unsanitized(stackerdb_list).map_err(

                        "Failed to create cons list for stackerdb arg: {e}"
                    ))
                },
            )?),

                    ChainstateError::Expects(format!(
                        "Failed to create cons list for signers arg: {e}"
                    ))
                },
            )?),
        ];

        let (value, _, events, _) = clarity.with_abort_callback(

    /// For PoX-4, compute the reward set for the next reward cycle,
    /// store it, and write it to the .signers contract.
    ///
    /// * `reward_cycle` is the reward cycle for the calculation (i.e., the next cycle).
    fn pox_4_compute_and_update_signers(
        clarity: &mut ClarityTransactionConnection,
        pox_constants: &PoxConstants,
        reward_cycle: u64,
        pox_contract: &str,
        coinbase_height: u64,
    ) -> Result<SignerCalculation, ChainstateError> {
        let is_mainnet = clarity.is_mainnet();
        let signers_contract = &boot_code_id(SIGNERS_NAME, is_mainnet);

        let liquid_ustx = clarity.with_clarity_db_readonly(|db| db.get_total_liquid_ustx())?;
        let reward_slots = Self::get_pox_4_reward_slots(clarity, reward_cycle, pox_contract)?;
        let (threshold, participation) = StacksChainState::get_reward_threshold_and_participation(
            pox_constants,
            &reward_slots[..],
            liquid_ustx,
        );

        let reward_set =
            StacksChainState::make_reward_set(threshold, reward_slots, StacksEpochId::Epoch30);

        test_debug!("Reward set for cycle {}: {:?}", &reward_cycle, &reward_set);

        let empty_signers = vec![];
        let events = Self::update_signers(
            clarity,
            reward_cycle,
            reward_set.signers().unwrap_or(&empty_signers),
            signers_contract,
            participation > 0,
            coinbase_height,
            is_mainnet,
        )?;

        Ok(SignerCalculation { events, reward_set })
    }
