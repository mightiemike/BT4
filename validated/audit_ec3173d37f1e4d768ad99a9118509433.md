### Title
Exchange pool balance can go negative when `allowHardenExchangeCalculation` is disabled, corrupting AMM pricing - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Finding Description
`ExchangeCapsule.transaction(byte[], long, boolean, boolean)` computes `newFirstTokenBalance`/`newSecondTokenBalance` using either the legacy `ExchangeProcessor` (double-precision `Math.pow`-based bancor-style AMM math) or the `SafeExchangeProcessor`, selected by the `hardenedCalc` argument [1](#0-0) . The only sanity check that the resulting pool balances remain non-negative is gated behind `hardenedCalc`:

```java
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [2](#0-1) 

`hardenedCalc` is supplied by `ExchangeTransactionActuator` as `allowHarden()`, which simply reads the dynamic chain parameter `allowHardenExchangeCalculation()` from `DynamicPropertiesStore` [3](#0-2) . Both `doValidate()` and `execute()` call `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` with this same flag [4](#0-3) [5](#0-4) .

When the flag is `false` (the pre-hardening / not-yet-activated network state), the negative-balance guard is skipped entirely, and the legacy `ExchangeProcessor.exchange` (floating-point `exchangeToSupply`/`exchangeFromSupply` using `Maths.pow`) determines `buyTokenQuant` [6](#0-5) . Neither `ExchangeTransactionActuator.doValidate()` nor `execute()` independently verifies that `anotherTokenQuant` (i.e., `buyTokenQuant`) does not exceed the current balance of the opposite token in the pool — the only balance-related checks are an upper-bound check on the *sold* token side against `dynamicStore.getExchangeBalanceLimit()` [7](#0-6)  and a slippage check `anotherTokenQuant < tokenExpected` [8](#0-7) , neither of which prevents draining the opposite balance below zero. Because floating-point `Math.pow` computations can produce results that are inconsistent/imprecise near extreme input ratios, a crafted `sellTokenQuant` can cause `buyTokenQuant` to exceed the current opposite-side balance, and with `hardenedCalc=false` this negative result is persisted directly via `Commons.putExchangeCapsule(...)` in `execute()` [9](#0-8) , corrupting the pool state used for all future price computations.

### Impact Explanation
A negative pool balance corrupts the AMM invariant relied upon by `ExchangeProcessor.exchange` for all subsequent trades against that exchange pair, since the bancor-style formulas assume non-negative balances. This can allow later trades (by the same or other users) to extract disproportionate value or produce further undefined/incorrect pricing, degrading the integrity of that exchange's token accounting.

### Likelihood Explanation
The vulnerable path is reached through the fully public `ExchangeTransactionContract`/`ExchangeTransactionActuator`, requiring no special privilege — any account with sufficient balance/asset holdings can submit it. However, the precondition `hardenedCalc == false` is determined solely by the network-wide dynamic property `allowHardenExchangeCalculation`, which per `ProposalUtil.java` is a committee/governance-controlled chain parameter, not something an individual transaction or attacker can toggle. The window in which this is exploitable is therefore limited to networks/periods where that hardening parameter has not yet been activated by chain governance; once activated, `SafeExchangeProcessor` plus the guard at line 160 fully closes this path. I was unable to confirm the current default/activation state of `allowHardenExchangeCalculation` in this repo since the property definition wasn't located in `DynamicPropertiesStore.java` search results, so whether this is presently exploitable on a live deployment (flag off) versus already mitigated (flag on) is uncertain and depends on the deployed chain parameters.

### Recommendation
Make the non-negative balance check unconditional in `ExchangeCapsule.transaction`, independent of `hardenedCalc`:
```java
if (newFirstTokenBalance < 0 || newSecondTokenBalance < 0) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
```
This ensures the accounting invariant holds regardless of the state of the `allowHardenExchangeCalculation` governance flag, while `hardenedCalc` can remain solely responsible for choosing strict-overflow arithmetic vs. legacy arithmetic.

### Proof of Concept
```java
// Illustrative test targeting ExchangeCapsule.transaction with hardenedCalc=false
@Test
public void testNegativeBalanceUnguardedWhenNotHardened() throws Exception {
  ExchangeCapsule exchangeCapsule = new ExchangeCapsule(
      ByteString.copyFromUtf8("owner"), 1L, 0L,
      "_".getBytes(), "abc".getBytes());
  // Set up small balances so legacy floating point math can overshoot
  exchangeCapsule.setBalance(1_000L, 1_000L);

  // sellTokenQuant crafted to make legacy ExchangeProcessor.exchange()
  // return buyTokenQuant > secondTokenBalance due to Math.pow precision behavior
  long sellTokenQuant = /* crafted large/extreme value relative to balance */ 999_999_999L;

  long buyTokenQuant = exchangeCapsule.transaction(
      "_".getBytes(), sellTokenQuant, /*useStrictMath=*/false, /*hardenedCalc=*/false);

  // Assert the invariant: this currently FAILS with hardenedCalc=false because
  // the guard at ExchangeCapsule.java:160 is skipped.
  assertTrue("Second token balance must never go negative",
      exchangeCapsule.getSecondTokenBalance() >= 0);
}
```
Expected result on unpatched code: `getSecondTokenBalance()` returns a negative value and no `ContractValidateException` is thrown, confirming the guard bypass when `hardenedCalc=false`. After applying the recommended fix (unconditional check), the same test should throw `ContractValidateException("Exchange balance must be >=0 after transaction")` instead.
