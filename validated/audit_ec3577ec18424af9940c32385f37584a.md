### Title
Silent skip of the `afterAuth` hook on session-token replay due to a stale idempotency entry that is never cleared on failure - ([File: packages/apps/shopify-app-express/src/helpers/idempotent-promise-handler.ts])

### Summary
`IdempotentPromiseHandler` records a session-token identifier as "already run" *before* the wrapped promise settles, and never removes that entry if the wrapped promise throws. The only cleanup is a TTL sweep that runs as a side effect of some later, unrelated `handlePromise` call. This is the same bug class as the Zebra `SentHashes` issue: a failed/rejected operation leaves a stale "done" marker that causes a subsequent, legitimate call with the same identifier to be silently treated as already completed and skipped.

### Finding Description
`isPromiseRunnable()` inserts the identifier into the `identifiers` map synchronously, then returns `true` so the caller executes the promise; on a second call with the same identifier it returns `false` and the promise function is *not* invoked at all, yet `handlePromise` still resolves successfully: [1](#0-0) 

Cleanup only happens via `clearStaleIdentifiers`, which deletes entries older than `IDENTIFIER_TTL_MS` (60 seconds), and it is only invoked from inside `handlePromise`'s `finally` block — i.e., cleanup is a side effect of some `handlePromise` call, not tied to whether the original promise succeeded or failed: [2](#0-1) 

This handler is keyed by the raw session token used in Shopify's token-exchange auth flow. In `shopify-app-express`, `callAfterAuthHook` uses the session token as the identifier when invoking the app's `afterAuth` hook after a successful token exchange: [3](#0-2) 

In `performTokenExchange`, if the `afterAuth` hook throws, the handler still marks the token identifier as consumed (it was recorded before the hook ran), the request is failed with a 500 response, but the identifier stays "poisoned" in the map for up to 60 seconds: [4](#0-3) 

If the same session token is presented again within that window (client retry after a transient failure, or a duplicate/concurrent request using the identical token — session/ID tokens are not single-use), `handlePromise` silently returns without executing `afterAuth`, `performTokenExchange` treats this as success, and calls `next()`/returns the session to the app as if `afterAuth` had actually run. The identical construct and vulnerable pattern is duplicated in `shopify-app-remix` and `shopify-app-react-router`: [5](#0-4) [6](#0-5) 

### Impact Explanation
The `afterAuth` hook is the app-defined post-authentication setup step (e.g., webhook registration, initial data sync, billing checks). A single merchant's client (embedded app frontend, App Bridge) can cause this hook to be silently skipped for any request that repeats an identical session token within the 60-second TTL window after an initial failure, without any error being surfaced to the app or the merchant. The token-exchange request itself succeeds and the merchant proceeds as if setup completed, while critical setup logic never executed. This is a functional-integrity/DoS-of-auth-handler issue rather than data exposure or cross-tenant compromise — the affected state is in-memory and bounded to the TTL window, matching the "Medium" characterization of the analog.

### Likelihood Explanation
Triggering this requires only: (1) an app whose first `afterAuth` hook invocation throws (easy to happen under normal transient conditions — DB hiccup, rate limit, network blip during webhook registration, etc.), and (2) a second request reusing the identical session token within 60 seconds, which is plausible via ordinary client retry logic or trivial to force deliberately since nothing in the code prevents reuse of the same still-valid session/ID token. No special privileges, RPC access, or authentication beyond a normal merchant session are needed.

### Recommendation
- Remove the identifier from the map only when the wrapped promise successfully completes, or record success/failure state explicitly instead of using a bare "seen" marker.
- On promise failure, delete the identifier (or requeue) so a legitimate retry with the same identifier actually re-executes `promiseFunction`, rather than being silently swallowed.
- Consider using the resolved/rejected `Promise` itself as the map value (so concurrent callers await the same in-flight promise and receive the same success/failure outcome) instead of a boolean/timestamp gate that discards the outcome.

### Proof of Concept
1. Configure an app with `hooks.afterAuth` that throws on its first invocation (e.g., simulate a transient webhook-registration failure).
2. Send a token-exchange request (e.g., hit the Express `performTokenExchange` middleware) with session token `T`. The offline/online tokens are exchanged and stored, `callAfterAuthHook` runs, throws, and the middleware returns HTTP 500 — but `T` is now recorded in `IdempotentPromiseHandler.identifiers`.
3. Within 60 seconds, resend the same request with the identical session token `T` (simulating a client retry).
4. Observe: `isPromiseRunnable('T')` returns `false`, so `afterAuth` is never invoked, yet `handlePromise` resolves without error; `performTokenExchange` proceeds to `res.locals.shopify = {...}; next();` returning a 2xx response as though setup succeeded, confirming the silent skip described in `packages/apps/shopify-app-express/src/helpers/idempotent-promise-handler.ts` and `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`.

```typescript
  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }
```

```typescript
  private async clearStaleIdentifiers() {
    this.identifiers.forEach((date, identifier, map) => {
      if (Date.now() - date > IDENTIFIER_TTL_MS) {
        map.delete(identifier);
      }
    });
  }
```
