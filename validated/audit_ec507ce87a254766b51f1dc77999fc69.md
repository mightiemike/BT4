### Title
Unbounded gzip decompression of attacker-supplied `compressed_program` in deprecated (Cairo 0) declare transactions causes node OOM/DoS - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
`decompress_program` performs an unbounded `GzDecoder::read_to_end` on user-controlled base64/gzip data taken from a declare transaction's deprecated contract class, with no size or time limit, mirroring the exact bug class in CVE-2026-47860 (unbounded decompression of attacker-supplied compressed message bodies).

### Finding Description
`decompress_program` decodes the base64 payload and then streams it through `flate2::bufread::GzDecoder`, reading to completion into an unbounded `Vec<u8>` with an explicit `TODO(dan): add time and size limits.` comment acknowledging the gap: [1](#0-0) 

This function is invoked from `user_deprecated_contract_class_to_sn_api`, which converts a user-supplied `DeprecatedContractClass` (containing the attacker-controlled `compressed_program` field) into the node's internal representation on the declare-transaction processing path: [2](#0-1) 

Unlike the size-bounded decompression helpers used elsewhere in the codebase — e.g. `decode_and_decompress_with_size_limit` in `starknet_api::compression_utils`, which caps output via `.take(max_size + 1)` and returns `CompressionError::SizeLimitExceeded`: [3](#0-2) 

and the RPC server's own zstd body-decompression guard tested in `apollo_http_server`: [4](#0-3) 

`decompress_program` has no equivalent guard. A gzip bomb of a few KB/MB can decompress to gigabytes, causing unbounded memory allocation for a single unprivileged submission.

### Impact Explanation
A single account, using an ordinary Cairo 0 declare transaction with a maliciously crafted `compressed_program` (a gzip bomb), can force the RPC/gateway node processing it to attempt an unbounded in-memory decompression, exhausting memory and crashing or hanging the node process. Since this occurs prior to transaction validation and hashing, an unprivileged transaction sender can repeatedly trigger this to deny service to the affected node component, matching CVSS Availability:High impact of the referenced CVE.

### Likelihood Explanation
This is trivially reachable by any account submitting a Cairo 0 declare transaction. No special privileges, contract deployment, or state setup is required — only crafting a gzip-compressed `compressed_program` field with a very high compression ratio, analogous to the ~1MB message described in the CVE.

### Recommendation
Apply a bounded decompression, matching the pattern already used in `starknet_api::compression_utils::decode_and_decompress_with_size_limit` (using `.take(max_size)` on the `GzDecoder` reader) or the zstd/http-body size limits used elsewhere, and reject/error out if the decompressed size or decompression time exceeds a configured maximum.

### Proof of Concept
1. Craft a gzip payload with a very high compression ratio (e.g., zeros compressed with `flate2`) that decompresses from a few KB to several hundred MB/GB.
2. Base64-encode this payload and place it in the `compressed_program` field of a `DeprecatedContractClass` used in a declare transaction, or in the corresponding user path that calls `user_deprecated_contract_class_to_sn_api` / `decompress_program`.
3. Submit the transaction; `decompress_program` calls `decoder.read_to_end(&mut decompressed)` with no size cap, causing large/unbounded memory allocation on the receiving node. [5](#0-4)

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.

    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}

#[tokio::test]
async fn zstd_decompressed_request_too_large() {
    // 10 KB of repeated bytes — compresses to ~50 bytes with zstd.
    let large_body = vec![b'a'; 10 * 1024];
    let mut encoder = zstd::stream::write::Encoder::new(Vec::new(), 0).unwrap();
    encoder.write_all(&large_body).unwrap();
    let compressed_body = encoder.finish().unwrap();

    // Limit between compressed size and decompressed size.
    // compressed_body is ~50 bytes; decompressed is 10240 bytes.
    let max_request_body_size = large_body.len() - 1;
    assert!(compressed_body.len() < max_request_body_size);

    let http_client = HttpClientServerSetupBuilder::new(unique_u16!())
        .with_max_request_body_size(max_request_body_size)
        .build()
        .await;

    let response = http_client.add_rpc_tx_with_zstd(compressed_body).await;

    assert_eq!(response.status(), StatusCode::PAYLOAD_TOO_LARGE);
}
