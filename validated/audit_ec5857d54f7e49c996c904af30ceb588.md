### Title
Unbounded eth_getLogs section-executor task submission enables shared-threadpool exhaustion DoS - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java])

### Finding Description
`LogBlockQuery.getPossibleBlock()` iterates every AND/OR condition and, for each block-bloom "section" in the requested `fromBlock`/`toBlock` range, calls `partialMatch()`, which for every **unique bitIndex** in that section submits a task to a shared `ExecutorService sectionExecutor` and blocks on `Future.get()`: [1](#0-0) 

This `sectionExecutor` is passed in from the JSON-RPC service layer and is a single, size-limited pool shared across **all concurrent `eth_getLogs` requests from all clients** (test harnesses create it via `ExecutorServiceManager.newFixedThreadPool(name, 5)`, illustrating it is a small fixed-size pool). Because the number of submitted tasks scales with `(number of sections in range) × (unique bit indexes per section, up to address+topic count×3)`, and `LogBlockQuery` computes `minSection`/`maxSection` directly from attacker-supplied `fromBlock`/`toBlock` without a hard cap on the block range before task submission: [2](#0-1) 

an unauthenticated JSON-RPC caller can request a wide block range (e.g., `fromBlock: earliest`, `toBlock: latest`) with multiple address/topic conditions, causing many sections × many bitIndex submissions to the shared executor. The `MAX_RESULT` (10000) check in `getPossibleBlock()` only throws `JsonRpcTooManyResultException` *after* all sections have already been scanned and all executor tasks already submitted and awaited — it does not bound task submission up front: [3](#0-2) 

Because `sectionBloomStore` is shared across all invocations and each `partialMatch` call blocks the calling JSON-RPC handler thread while waiting on `Future.get()`, multiple parallel `eth_getLogs` calls each spawning many futures against the same fixed-size executor will saturate the pool/queue, delaying or starving other callers' section lookups — including benign clients' queries — since the pool has no per-client or per-request quota, and there is no visible rate limiter for JSON-RPC filter calls in this code path.

### Impact Explanation
This maps to a JSON-RPC-API DoS: legitimate `eth_getLogs` callers experience degraded latency or timeouts because their `partialMatch` tasks compete for the same limited executor slots/queue as an attacker's flood of wide-range, multi-condition queries. This is a resource-exhaustion/service-degradation issue rather than consensus or asset-safety impact.

### Likelihood Explanation
No authentication, fee, or address-permission check gates `eth_getLogs`; any anonymous HTTP/JSON-RPC client can issue many concurrent requests with wide block ranges and multiple topics/addresses at negligible cost (no on-chain fee, bandwidth/energy accounting does not apply to JSON-RPC HTTP calls). The attack is trivially repeatable and scriptable. However, actual severity depends on node-level HTTP/JSON-RPC concurrency limits, executor pool sizing in production configuration, and whether an upstream global block-range limit exists elsewhere in the JSON-RPC config (not fully visible in the reviewed code) — this could reduce but not eliminate the exposure.

### Recommendation
- Enforce a maximum block-range/section count (and a maximum number of address/topic combinations) at the very start of `LogBlockQuery` construction, before any section scanning or executor submission, rejecting oversized queries early with `JsonRpcInvalidParamsException`/`JsonRpcExceedLimitException`.
- Bound total task submissions per request (cap unique bitIndex × section submissions) and/or use a bounded queue with rejection policy on `sectionExecutor` so a single client cannot monopolize it.
- Add per-client/per-connection concurrency limiting or a token-bucket rate limiter for `eth_getLogs`/filter-creation endpoints in the JSON-RPC service layer.
