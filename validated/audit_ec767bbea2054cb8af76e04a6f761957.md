I found a verified, code-confirmed integrity gap. It's not the same bug as the oracle report, but it is directly analogous: a validation function accepts committed transaction results as "matching" even though it omits comparison of the authenticated state/proof-carrying hash fields, which lets divergent state be accepted as verified.

### Title
Replay-verification incorrectly reports success despite state-root divergence because `ensure_match_transaction_info` skips checkpoint-hash comparison - (`File: types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness check used by the `db-tool replay-on-archive` and `aptos-debugger` tooling to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` recovered from a backup/archive. The function validates status, gas, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the locally computed values, even though these fields are part of the authenticated, proof-bound `TransactionInfo` that is itself hashed into the transaction accumulator.

### Finding Description
`ensure_match_transaction_info` computes and compares only `status`, `gas_used`, `write_set_hash` (vs `state_change_hash`), and `event_root_hash`: [1](#0-0) 

The comment inline in the function is a direct admission of the gap: the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the only correctness check performed per-transaction in `replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions with the VM and calls `ensure_match_transaction_info` against the `expected_txn_info` pulled from the backup archive (itself covered by an accumulator/ledger-info proof): [2](#0-1) 

Because `state_checkpoint_hash` (and hot-state/position variants) are never independently recomputed and compared here, a divergence in the locally-computed state Merkle root — caused by a VM/state-computation bug, a hot-state or position-state computation bug, or a subtly corrupted execution path — will not be detected by this tool even though the archived `TransactionInfo` (and its accumulator proof) legitimately commits to the correct root. The tool will report "replay success" while the locally materialized ledger state has silently diverged from the authenticated on-chain state root.

### Impact Explanation
Replay-verify tooling exists specifically to catch state-computation divergence between different versions/binaries of the node against real (mainnet/testnet) transaction history — this is the standard mechanism used to certify that a new release, or a hard fork change, still produces identical state to history. If this tool silently passes despite an actual state-root mismatch, a state-computation bug (including one introduced by a future change) could ship to mainnet undetected, since the primary regression-detection safety net accepts the wrong result as valid. This falls under the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated ... proof-bearing responses ... bound to the right ... root" impact categories: the authenticated `state_checkpoint_hash` field is exactly the proof-bearing root that should gate acceptance and currently does not.

### Likelihood Explanation
This does not require any external attacker — it's a systemic gap in an internal verification path that always triggers whenever `replay_on_archive` (or `aptos-debugger`'s equivalent invocation) is run, on every replayed transaction, unconditionally, regardless of the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag. Any real divergence in state/hot-state/position root computation — which is exactly the class of bug replay-verify is meant to catch — will go unreported.

### Recommendation
Extend `ensure_match_transaction_info` to recompute the local `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) from the post-execution state view and assert equality against `txn_info`'s corresponding fields, mirroring the write-set-hash and event-root-hash checks already present. This should be enabled before relying on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-gated replay verification, per the TODO already present in the code.

### Proof of Concept
1. Take any archived transaction range with a known-correct `TransactionInfo` (with valid `state_checkpoint_hash`) and a corresponding buggy VM/state-computation build that produces a different state root for a checkpoint transaction but coincidentally identical `write_set_hash`/`event_root_hash`/`gas_used`/`status` (e.g., a bug only in hot-state or position-state root aggregation, which is tracked in a separate hash entirely from `state_change_hash`).
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`) over that range.
3. Observe `execute_and_verify` calls `ensure_match_transaction_info`, which never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so the check passes and no failure is reported for the divergent state root.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
