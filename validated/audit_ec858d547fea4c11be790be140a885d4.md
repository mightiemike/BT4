### Title
Gateway target response payload is unmarshaled and forwarded without invoking `Response.Validate()`, allowing invalid/inconsistent fields to reach workflow execution - ([File: core/capabilities/webapi/target/target.go])

### Summary
`Capability.Execute` in `target.go` deserializes the raw gateway response bytes directly into `ghcapabilities.Response` via `json.Unmarshal` and immediately builds the `CapabilityResponse.Value` from the unvalidated struct fields, without ever calling the `Response.Validate()` method defined for exactly this purpose. This means the codec/schema invariants encoded in `Validate()` (e.g., `ExecutionError=true` must not carry a populated `StatusCode`/`Headers`/`Body`, and `StatusCode` must be in `100-599` when not an execution error) are never enforced before results are surfaced to the workflow engine.

### Finding Description
`Response.Validate()` is defined at [1](#0-0)  and encodes the invariant that a response with `ExecutionError=true` must have empty `StatusCode`/`Headers`/`Body`, and otherwise `StatusCode` must fall in `100-599`.

In `Capability.Execute`, the gateway's single-node response is unmarshaled directly with no call to `Validate()`: [2](#0-1) 

The unvalidated `StatusCode`, `Headers`, and `Body` fields are passed straight into `values.NewMap` and returned as the `CapabilityResponse.Value`, which downstream workflow steps then consume as trusted data. There is no other call site in the repo (`grep` for `.Validate()` across the codebase shows no hits in `target.go`, `outgoing_connector_handler.go`, or the gateway handler send path) that invokes `ghcapabilities.Response.Validate()` before this data is trusted — the only usages of `Response` type outside `webapi.go` are in test files and `target.go` itself, and none call `Validate()`.

Because `HandleSingleNodeRequest` returns the raw gateway message body (`resp.Body.Payload`) that is only structurally decoded (JSON-parsed) but not schema-validated, an inconsistent payload (e.g., `ExecutionError=true` combined with a non-zero `StatusCode`/populated `Body`, or a `StatusCode` outside the valid HTTP range) will still be accepted and forwarded as `CapabilityResponse.Value`.

### Impact Explanation
This is a data-integrity/misreporting issue: invalid or self-contradictory response data (e.g., claiming an execution error occurred while also supplying a "successful" status code and body) can be embedded in the workflow's executed result value, which downstream workflow logic may branch on. This does not grant privilege escalation or code execution directly, but it violates the codec invariant and could cause unsafe/incorrect workflow execution decisions based on malformed data that the response schema was specifically designed to prevent.

### Likelihood Explanation
Exploitation requires the ability to control or forge the gateway response body delivered for the specific pending `messageID` — i.e., a compromised or malicious gateway, or a compromised/malicious DON node that services the single-node gateway request. This is not reachable by an ordinary unprivileged external attacker via normal web/API input; it requires compromise of infrastructure that sits in the gateway/node trust boundary, which is explicitly excluded by the audit rules ("no malicious node/peer/operator assumptions").

### Recommendation
Call `payload.Validate()` immediately after `json.Unmarshal` in `Capability.Execute` (`core/capabilities/webapi/target/target.go`), and return an error (rather than constructing `CapabilityResponse`) if validation fails, ensuring the codec invariant is enforced before any field is surfaced to the workflow engine.

### Proof of Concept
Add a test in `core/capabilities/webapi/target/target_test.go` that:
1. Mocks `connectorHandler.HandleSingleNodeRequest` to return a `resp.Body.Payload` JSON-encoding `ghcapabilities.Response{ExecutionError: true, StatusCode: 200, Body: []byte("ok")}`.
2. Calls `Capability.Execute` with a valid request/config.
3. Asserts that `Execute` currently returns a successful `CapabilityResponse` containing the inconsistent fields (demonstrating `Validate()` is bypassed), and asserts that after the fix, `Execute` returns an error matching `"executionError is true but response details (statusCode, headers, body) are populated"`.

Note: this finding depends on the precondition that the gateway response for the given `messageID` can be attacker-influenced, which requires compromise of the gateway or a DON node — a trust boundary outside the scope of an unprivileged external attacker as defined by the audit rules.

func (r Response) Validate() error {
	if r.ExecutionError {
		if r.ErrorMessage == "" {
			return errors.New("executionError is true but errorMessage is empty")
		}
		if r.StatusCode != 0 || len(r.Headers) > 0 || len(r.Body) > 0 {
			return errors.New("executionError is true but response details (statusCode, headers, body) are populated")
		}
		return nil
	}

	if r.StatusCode < 100 || r.StatusCode > 599 {
		return errors.New("statusCode must be a valid HTTP status code (100-599)")
	}

	return nil
}
