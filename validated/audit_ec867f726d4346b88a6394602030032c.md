### Title
Unbounded per-request O(N log N) sort in `DelegatedResourceAccountIndexStore.getWithPrefix` enables computational-cost amplification via inflated delegation index - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`getIndex`/`getV2Index` call `getWithPrefix`, which loads every prefix-matching entry for an address and sorts both the "to" and "from" lists on every single invocation with no caching, pagination, or cap on list size. Since the number of entries `N` under an address is fully attacker-controlled (grown via cheap `delegate()`/`DelegateResource` transactions), each subsequent read-only RPC/HTTP call re-executes O(N log N) work, while the endpoint's only defense is a fixed QPS-based rate limiter that is unaware of per-request computational cost.

### Finding Description
`getWithPrefix` performs, for each of the two prefixes (`V2_FROM_PREFIX`/`V2_TO_PREFIX` or `FROM_PREFIX`/`TO_PREFIX`): [1](#0-0) 

a `prefixQuery` DB scan followed by `tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp))` and a stream/collect to rebuild the full list — all done freshly on every call, with no memoization, no limit on the number of entries returned, and no pagination parameter exposed to the caller.

`getIndex`/`getV2Index` are the sole entry points, invoked directly by `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`, which are reachable from anonymous HTTP endpoints (`GetDelegatedResourceAccountIndexServlet`, `GetDelegatedResourceAccountIndexV2Servlet`) and the corresponding gRPC methods in `RpcApiService`: [2](#0-1) 

These servlets extend `RateLimiterServlet`, whose only protection is a QPS/IP-based token-bucket limiter (`DefaultBaseQqsAdapter`/`IPQPSRateLimiterAdapter`) that gates the *number* of requests per unit time, not the *cost* of each request: [3](#0-2) 

No existing check (signature validation, permission weight, `DecodeUtil.addressValid`, actuator `validate()`, energy/bandwidth accounting) applies here because this is a pure read path with no transaction involved — reads are free by design, and the rate limiter treats all requests to the endpoint as equal cost regardless of the target address's state size. An attacker who has inflated `N` for their own address via many `DelegateResourceActuator` calls can therefore force the node to repeatedly perform O(N log N) sorting work per allowed request, at the QPS ceiling, indefinitely.

### Impact Explanation
Each read RPC against an inflated address costs disproportionately more CPU (and DB scan I/O) than the fixed per-request cost the rate limiter assumes, while the caller pays nothing beyond a normal HTTP/gRPC call. This is a **DoS via RPC-API** style finding: sustained calls at the permitted QPS against a large-N address elevate CPU usage on the RPC-serving thread pool, degrading responsiveness for other API/RPC callers on the same node. Impact is scoped to availability/performance degradation of a single node's RPC service, not to consensus, funds, or key material.

### Likelihood Explanation
Preconditions: attacker must first inflate `N` under an address by issuing many `DelegateResource` transactions (a separate, already-identified cost/DoS vector), then repeatedly call the read-only `GetDelegatedResourceAccountIndexV2` endpoint. The read calls themselves are free and unauthenticated, and are only throttled by a fixed QPS/IP limiter unrelated to `N`, so the attack is fully repeatable as long as the QPS quota allows it. Feasibility depends heavily on how large `N` can practically be grown and on the configured QPS limits (not verified in this pass) — a low default QPS could substantially blunt real-world impact, so severity should be considered moderate rather than critical without further calibration.

### Recommendation
- Cap the number of entries returned/sorted per `getWithPrefix` call (e.g., enforce a `MAX_DELEGATE_LIST_SIZE` similar to existing delegation-count protections), or paginate the API.
- Avoid re-sorting on every call: maintain sorted order at write time (`delegate`/`delegateV2` already know the insertion `time`, so entries could be stored/queried in already-sorted order) instead of doing an O(N log N) sort per read.
- Consider a request-cost-aware rate limiter (e.g., weight requests by the size of data touched) for these endpoints, or return a bounded/paged result set by default.

public void testGetV2IndexCostScalesWithN() {
  byte[] address = randomAddress();
  int N = 50_000; // grown cheaply via repeated delegate() / DelegateResource transactions
  for (int i = 0; i < N; i++) {
    store.delegateV2(address, randomAddress(), i); // simulate attacker-inflated index
  }

  long start = System.nanoTime();
  DelegatedResourceAccountIndexCapsule result = store.getV2Index(address);
  long elapsed = System.nanoTime() - start;

  // elapsed grows with N (O(N log N)), while HTTP layer only rate-limits by QPS,
  // not by result size -> repeated calls at allowed QPS multiply this cost.
  assertTrue(elapsed > /* baseline for small N */ 10_000_000L);
}

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
