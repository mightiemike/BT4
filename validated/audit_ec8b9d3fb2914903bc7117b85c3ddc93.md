## Finding

The bug pattern in the H-11 report (a value that's supposed to be validated/converted before use, but is trusted verbatim and silently corrupts downstream calculations) has a genuine analog in Aptos's backup restore path for transactions.

### Title
Unverified `write_set` accepted during transaction-chunk restore, allowing state corruption despite passing accumulator-proof verification - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
`LoadedChunk::load` in the transaction-restore path deserializes `(txn, aux_info, txn_info, events, write_set)` tuples from a backup chunk file and only runs the accumulator-proof `verify()` over `txns`, `events`, and `txn_infos` (via `TransactionListWithProofV2`/`TransactionListWithProof::verify`). The `write_sets` vector is carried alongside but is **never checked against `txn_info.state_change_hash()`**, unlike the equivalent `TransactionOutputListWithProof::verify` path elsewhere in the codebase, which explicitly performs this check.

### Finding Description
`LoadedChunk::load` reads records and separates them into `txns`, `persisted_aux_info`, `txn_infos`, `event_vecs`, and `write_sets`: [1](#0-0) 

It then builds a `TransactionListWithProofV2` (wrapping `TransactionListWithProof`) using only `txns`, `event_vecs`, and `txn_infos`/`range_proof`, and calls `.verify()`: [2](#0-1) 

`TransactionListWithProof::verify` checks: (1) transaction hash matches `txn_info.transaction_hash()`, (2) `txn_infos` are proven under the ledger info via the accumulator proof, and (3) event root hashes match `txn_info.event_root_hash()` — but it never touches `write_set` or `state_change_hash`: [3](#0-2) 

Compare this with `TransactionOutputListWithProof::verify`, which does perform the equivalent check elsewhere in the codebase: [4](#0-3) 

Because `write_sets` are deserialized from the same untrusted chunk file but excluded from the proof check, `LoadedChunk` (with unverified `write_sets`) is passed straight to `restore_utils::save_transactions`, which persists them via `WriteSetDb::put_write_set` and, when `kv_replay` is enabled, feeds them directly into `state_store.calculate_state_and_put_updates` to derive the restored ledger state: [5](#0-4) 

The correct, hash-authenticated `TransactionInfo::state_change_hash()` (which is bound inside the accumulator-proven `TransactionInfo`) is silently ignored as a cross-check for the write set that actually gets committed.

### Impact Explanation
A corrupted or maliciously altered backup chunk file (bit flip, storage-provider tampering, or bug in a third-party backup source) can substitute an arbitrary `write_set` for a version while `LoadedChunk::load`'s verification still succeeds, because the proof only authenticates `txn_infos`/`txns`/`events`, not `write_sets`. This directly violates the "proof-bearing responses / committed state must survive handoff unchanged" invariant: the restored node's state-KV store and JMT state root would then diverge from the correct, hash-committed state — a hard-fork-class / archival-integrity divergence, and any API serving `write_set` or restored state for that version would return authenticated-looking but corrupted data.

### Likelihood Explanation
This requires the restore/backup archive itself to be corrupted or tampered with — a scenario administrators historically assume is protected by proof verification within the restore tool itself. Since the tool already re-implements/re-uses `TransactionListWithProof::verify` specifically to validate chunk integrity, the omission of the write-set check is a genuine gap in that intended integrity boundary, not an out-of-scope "malicious peer" issue — it's a local code defect in `restore.rs`/`TransactionListWithProof::verify` moved out of the state-integrity gate exclusions since it concerns restore/proof verification code, not peer-to-peer networking.

### Recommendation
In `LoadedChunk::load` (or in `TransactionListWithProof::verify`), add an explicit check that `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every record, mirroring the check already implemented in `TransactionOutputListWithProof::verify`, before the chunk is accepted and forwarded to `restore_utils::save_transactions`.

### Proof of Concept
1. Take a legitimate transaction-backup chunk file (`TransactionChunkFormat::V1`), which stores BCS-serialized `(txn, aux_info, txn_info, events, write_set)` records.
2. Modify only the `write_set` bytes of one record (leaving `txn`, `txn_info`, `events` untouched), producing a chunk where the accumulator-proof-covered `txn_info.state_change_hash()` still matches the original, correct write set, but the actual `write_set` bytes stored in the file are different.
3. Run `TransactionRestoreController`/`LoadedChunk::load` against this tampered chunk: `txn_list_with_proof.verify(...)` at line 167 succeeds (it never inspects `write_sets`), so `LoadedChunk` is returned with the tampered `write_sets` untouched.
4. `restore_utils::save_transactions` persists the tampered write set to `WriteSetDb`, and, if `kv_replay` is enabled, the restored account/resource state used to build the JMT differs from the original chain state — with no error raised by the restore pipeline. [6](#0-5)

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
