### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, allowing replay-verify tooling to accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (chunk executor's `verify_execution`, the CLI's transaction replay, and `db-tool`'s replay-on-archive) to confirm that a locally re-executed transaction produced the same result as the one already committed and authenticated on-chain via `TransactionInfo`. The function checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that bind the transaction to the authenticated state (Merkle) root. This is acknowledged in-code by a `TODO(trading-native)` comment, confirming the gap is a genuine, current omission rather than a misreading.

### Finding Description
`TransactionInfo` carries multiple root-hash fields that commit to different parts of ledger state:
- `state_change_hash` — hash of the write set (checked)
- `event_root_hash` — hash of the events (checked)
- `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` — the authenticated state-tree roots (Jellyfish Merkle root, hot-state root, position-state root) produced by `DoStateCheckpoint` at checkpoint boundaries — **not checked** [1](#0-0) 

In `ensure_match_transaction_info`, after validating status, gas, write-set hash and event-root hash, the function returns `Ok(())` without comparing any of the checkpoint hashes present on `txn_info`, with an explicit comment stating the comparator "ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution." [2](#0-1) 

This function is the authoritative correctness check used by:
- `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution`, which re-executes a chunk of transactions and calls `ensure_match_transaction_info` per-transaction to accept or reject a replay against known `TransactionInfo`s. [3](#0-2) 
- `aptos-move/cli/src/commands.rs`'s transaction replay/simulation path. [4](#0-3) 
- `storage/db-tool/src/replay_on_archive.rs`, which is explicitly built to validate archived backups against locally recomputed execution results.

Because the checkpoint hashes (i.e., the state-tree roots) are never compared, a divergence between the locally computed state root and the one embedded in the trusted `TransactionInfo` (sourced from an epoch-ending `LedgerInfo`/backup) will not be flagged as long as the write set, events, gas, and status happen to match. Write set equality does not imply state-tree root equality when the state root also depends on ancillary structures such as the hot-state bucket or position-state tree (as is explicit in the comment referencing "hot-state" and `position_state_checkpoint_hash`), or on any other divergent state-checkpoint computation logic (e.g., an aggregator/JMT bug, a hard-fork feature-flag mismatch, or a bug in `DoStateCheckpoint`).

### Impact Explanation
This breaks the "committed state must survive proof/replay verification unchanged" invariant for any tool relying on `ensure_match_transaction_info` as ground truth:
- Replay-verify (used to certify that historical backups/chunks accurately reflect the correct VM execution) can report success even when the state root diverges — silently certifying a corrupted or incorrectly-forked backup as valid.
- This directly maps to the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Wrong ... state proof accepted as valid" impact classes: a state root mismatch (which normally would be the strongest possible signal of ledger corruption or of a subtle nondeterministic bug) is masked.
- Because this is the verification gate used by `db-tool`'s replay-on-archive tooling and the chunk executor's replay-verification mode (used in backup verification / disaster-recovery workflows), a real divergence in state computation would go undetected until it manifests elsewhere (e.g., state sync fails), potentially after such backups have already been trusted/distributed.

The severity is high on any mainnet-operations path that depends on this function to assert "my locally executed replay matches the historical, authenticated ledger," since that assertion is not actually complete.

### Likelihood Explanation
This is not an attacker-triggered exploit in the classic sense (no unprivileged network input reaches this directly to corrupt live consensus state), but it is a real, code-confirmed correctness gap with a governing TODO acknowledging the exact conditions under which it activates (any code path in which write set/events/gas/status match but the state-checkpoint roots differ — e.g. the mentioned "hot-state" and "position-state" trading-native features, or any subtly nondeterministic state-checkpoint computation). Given the codebase already flags this with a dated code comment naming a concrete upcoming feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that would make this divergence possible, the likelihood of the gap actually being exercised (rather than purely theoretical) is elevated once that feature activates, and the tooling exists and is reachable today.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the corresponding value is computable/known from the locally-executed `TransactionOutput`/`StateCheckpointOutput`, mirroring the strict checks already done for `state_change_hash` and `event_root_hash`. At minimum, gate any feature (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) behind having this validation in place first, as the comment itself recommends.

### Proof of Concept
Not independently exploitable via a PoC transaction — the flaw is a verification-logic gap, demonstrated directly by the code itself:
1. `execution/executor/src/chunk_executor/mod.rs::verify_execution` re-executes transactions and calls `txn_out.ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))`. [5](#0-4) 
2. `ensure_match_transaction_info` checks status, gas, write-set hash, event-root hash only, then returns `Ok(())`. [6](#0-5) 
3. Construct (in a test) a `TransactionOutput` whose write set/events/gas/status match a given `TransactionInfo`, but pair it with a `TransactionInfo` (or execution context) carrying a different `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` than what local state-checkpoint computation would produce; `ensure_match_transaction_info` will return `Ok(())`, demonstrating the accepted-but-wrong-root condition described by the in-code TODO.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
