### Title
Lack of slippage/minimum-output protection in `ExchangeWithdrawContract` allows front-run sandwich extraction of exchange creator's withdrawal - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator` computes the "another token" amount a user receives when withdrawing liquidity from a bancor-style `Exchange` pair purely from the pool's current on-chain ratio at execution time, with no user-supplied minimum-acceptable-output field in the protobuf contract. This mirrors the RUSH1-4 finding: `redeem()`/withdraw operations that derive output amounts from a mutable pool state without a slippage bound, letting the actual output diverge from what the user expected when they signed and broadcast the transaction.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum field, unlike its sibling `ExchangeTransactionContract` which explicitly has an `expected` field used to enforce a minimum-received check (`anotherTokenQuant < tokenExpected` → revert) in `ExchangeTransactionActuator`. [1](#0-0) 

In `ExchangeWithdrawActuator.doValidate()`/`execute()`, `anotherTokenQuant` (the amount of the paired token the withdrawer will receive) is derived at validation/execution time solely from the exchange's live `firstTokenBalance`/`secondTokenBalance` ratio: [2](#0-1) 
and executed unconditionally against whatever the ratio happens to be by the time the transaction is applied: [3](#0-2) 

Between when a withdraw transaction is signed/broadcast and when it is packed into a block, any anonymous actor can submit `ExchangeTransactionContract` (buy/sell against the pair) or `ExchangeInjectContract` transactions that shift `firstTokenBalance`/`secondTokenBalance`. Because block producers order transactions and the withdraw transaction has no bound on `anotherTokenQuant`, an attacker can sandwich the withdrawer: trade against the pool immediately before the withdraw executes to skew the ratio unfavorably, extract the withdrawer's expected value, then reverse the trade afterward — the classic no-slippage-protection extraction pattern described in the RUSH1-4 report, just implemented against TVM-level bancor exchange pairs instead of an ERC4626 vault.

### Impact Explanation
The exchange creator (the only account authorized to call `ExchangeWithdrawContract`, per the `is not creator` check) can have the value of a withdrawal reduced through pool-ratio manipulation timed around their transaction, without any recourse or on-chain check to abort the withdrawal if output falls below their expectation. This causes real value loss/accounting divergence from what the user intended, directly analogous to the reported medium-severity issue.

### Likelihood Explanation
Requires an attacker to observe a pending `ExchangeWithdrawContract` transaction (via the public mempool/broadcast network) and race in trade transactions against the same exchange pair before it is included — a standard, low-cost sandwich pattern reachable purely through broadcasting ordinary contract types (`ExchangeTransactionContract`/`ExchangeInjectContract`) from any account, no privileged access needed.

### Recommendation
Add a minimum-output (`expected`) field to `ExchangeWithdrawContract`, analogous to the `expected` field already present in `ExchangeTransactionContract`, and enforce `anotherTokenQuant >= expected` in `ExchangeWithdrawActuator.doValidate()`/`execute()`, aborting with `ContractValidateException`/`ContractExeException` when the computed output is below the caller-specified bound.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` transaction for `exchange_id=E`, `token_id=T`, `quant=Q` in the transaction pool, submitted by the exchange creator.
2. Attacker submits an `ExchangeTransactionContract` trading a large amount into/out of the pair `E`, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably relative to the ratio the creator expected when signing, and ensures it lands in an earlier position in the block (front-run).
3. The pending withdraw transaction executes against `ExchangeWithdrawActuator.execute()` using the now-skewed balances at lines 74-89, yielding a much lower `anotherTokenQuant` than the creator anticipated, with no validation reverting the transaction since there is no `expected`/minimum field to check against. [4](#0-3) 
4. Attacker reverses their trade afterward (back-run) to restore the pool and pocket the extracted value, completing the sandwich against the withdrawer.
