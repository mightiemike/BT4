### Title
Relayer fee for emulated ERC-20/base-token transfers is paid unconditionally before the underlying transfer's outcome is known - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The NEAR Wallet Contract (deployed as the global contract behind every ETH-implicit account, per `EthImplicitGlobalContract`) emulates Ethereum EOA/ERC-20 transfers over NEP-141 tokens. When parsing an RLP-encoded transaction that represents an `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, `inner_rlp_execute` immediately fires a `promise_batch_action_transfer` refund of `fee` to the relayer (`context.predecessor_account_id`) as a *separate* promise, created before — and independently of — the promise that performs the actual underlying transfer/`ft_transfer` call. [3](#0-2) 

### Finding Description
`parse_rlp_tx_to_action` (`internal.rs`) computes `tx_fee` purely from the signed Ethereum transaction's declared `max_fee_per_gas * gas_limit`, an amount that is nominal/declared by the user, not a value that has been verified against the eventual real transfer outcome: [2](#0-1) 

Back in `inner_rlp_execute`, for `EOABaseTokenTransfer`/`ERC20Transfer` kinds with non-zero fee, a *standalone* promise batch transferring `fee` to the relayer is created and dispatched right after parsing, unconditionally: [1](#0-0) 

Only afterward is the promise for the actual action (the `Transfer` action or the NEP-141 `ft_transfer`/`storage_deposit` batch) constructed and chained to `rlp_execute_callback`, which is the only place that performs a refund — and only refunds `caller_deposit` (the attached NEAR deposit), not the already-paid relayer `fee`: [4](#0-3) 

Because the fee-refund promise and the underlying-transfer promise are two independent receipts (not batched into one atomic receipt), NEAR's per-receipt failure atomicity — where a failed receipt's state changes roll back (`state_update.rollback()`) — only protects each receipt individually; it does not couple the relayer's fee payment to the success of the wallet's/token's transfer. If the underlying transfer subsequently fails (e.g., the NEP-141 token's `ft_transfer` panics due to insufficient sender balance, or the target contract rejects it, or address-registrar/nep-141-storage-balance checks lead to a different final outcome than assumed at parse time), the relayer nonetheless keeps the fee that was computed under the assumption the transfer would succeed as specified. This is the same class of defect as the reported Sherlock issue: an amount recorded/moved based on an *assumed* outcome of a token transfer diverges from the *actual* outcome, because the code path does not verify the real balance delta/result before committing to the recorded amount.

### Impact Explanation
An externally-callable path (any account can call `rlp_execute`/`rlp_execute_from` on an ETH-implicit account's wallet contract, which every ETH-implicit account runs as its global contract per `EthImplicitGlobalContract`) allows unauthorized/unintended value movement: the relayer is compensated in NEAR tokens for a token transfer that never actually completes, effectively extracting value from the wallet owner without a corresponding successful transfer. This is a concrete unauthorized value movement rather than a mere resource/gas griefing issue, since real NEAR balance leaves the wallet account regardless of whether the emulated transfer (the actual value the fee was meant to compensate for) succeeds.

### Likelihood Explanation
Likelihood is high in practice because: (1) any relayer submitting `rlp_execute` on behalf of a user can trigger this path merely by constructing a signed Ethereum transaction with a non-zero `max_fee_per_gas`; (2) the failure of the *chained* second promise (`ft_transfer`/target call) can be caused by ordinary conditions unrelated to the relayer's honesty — e.g., insufficient token balance, receiver not registered and `storage_deposit` failing, or the target contract panicking — none of which are checked before the fee promise fires; (3) the code comments in `inner_rlp_execute` acknowledge this fee is "not guaranteed" only from the relayer's own perspective ("Relayers should also verify the fee before sending"), but do not protect the *wallet owner* from paying a fee for a transfer that fails.

### Recommendation
Do not dispatch the relayer fee transfer as an independent up-front promise. Instead, batch the fee-transfer action into the same receipt/promise chain as the underlying transfer (or move the fee payment into `rlp_execute_callback` conditioned on `PromiseResult::Successful`), so that the relayer is compensated only if the underlying transfer actually succeeds — mirroring how `caller_deposit` refunds are already gated on the callback's promise result rather than being sent unconditionally at parse time.

### Proof of Concept
1. Deploy an ETH-implicit account backed by the Wallet Contract global contract (per `EthImplicitGlobalContract`, `runtime/runtime/src/actions.rs:238`), and fund it with a NEP-141 token balance.
2. Have the wallet owner sign an Ethereum-formatted `Transaction2930` calling `ERC20_TRANSFER_SELECTOR` with `to`/`value` that will make `ft_transfer` fail on-chain (e.g., a `value` exceeding the wallet's actual token balance, or a receiver that the token contract will reject), and with a non-zero `gas_price`/`gas_limit` so `tx_fee` in `parse_rlp_tx_to_action` is non-zero.
3. Have any relayer submit this signed transaction via `rlp_execute_from`.
4. Observe: `inner_rlp_execute` fires the relayer-fee `promise_batch_action_transfer` immediately (`lib.rs:381-384`), and this receipt succeeds independently of the subsequent `ft_transfer` promise chain.
5. Observe the `ft_transfer`/`storage_deposit` chained promise ultimately fails (per the constructed scenario), triggering `rlp_execute_callback`'s `PromiseResult::Failed` branch — but this branch only refunds `caller_deposit` (attached NEAR deposit), never the already-paid `fee`.
6. Final state: the relayer's NEAR balance increased by `fee`, and the wallet's NEAR balance decreased by `fee`, despite the emulated token transfer never taking effect — demonstrating unauthorized value extraction decoupled from the underlying (failed) transfer.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
