### Title
Malicious NEP-141 token can permanently freeze a NEAR Wallet Contract instance via unbounded callback gas exhaustion - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (used to emulate Ethereum-style transactions on NEAR) tracks in-flight execution with a single boolean flag, `has_in_flight_tx`, that is reset to `false` only inside the promise callbacks after a cross-contract call resolves. If an attacker-controlled NEP-141 token causes one of these callbacks to panic (e.g. by exhausting the fixed gas budget), the entire callback's state changes — including the flag reset — are rolled back by NEAR's atomic function-call semantics, permanently stranding the flag at `true` and locking the wallet out of all future transactions.

### Finding Description
`WalletContract` maintains the invariant that `has_in_flight_tx` is `true` while a promise chain is outstanding and `false` otherwise, and `rlp_execute` unconditionally rejects any new transaction while the flag is `true`: [1](#0-0) [2](#0-1) 

The flag is only ever reset back to `false` at the *start* of the various private callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`): [3](#0-2) [4](#0-3) 

For an emulated ERC-20 transfer, the contract first calls the target NEP-141 token's `storage_balance_of` and schedules `nep_141_storage_balance_callback` with a *fixed* static gas allocation: [5](#0-4) [6](#0-5) 

`nep_141_storage_balance_callback` reads the raw `PromiseResult` returned by the (attacker-controlled) token contract and deserializes it via `serde_json::from_slice` before it can reach the line that resets `has_in_flight_tx = false` and schedule any follow-up promise: [7](#0-6) 

Because `target` (the token contract account) is fully attacker-controllable (it is whatever `to` address/account the signed Ethereum-style transaction points at), a malicious NEP-141 implementation can return an arbitrarily large byte blob from `storage_balance_of` instead of the small standard JSON object. Reading that blob out of the promise result and deserializing it consumes gas proportional to its size. Since the callback's static gas is a fixed constant (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` = 5 Tgas, folded into a larger but still bounded `callback_gas`), a sufficiently large malicious payload can exhaust the callback's entire prepaid gas before it finishes, causing the WASM execution to trap ("Exceeded the prepaid gas"). NEAR's runtime treats a trapped/failed function call as fully atomic: none of the function's storage writes — including the `self.has_in_flight_tx = false` write executed at the top of the function — are persisted.

The net effect: `has_in_flight_tx` remains `true` forever in the contract's persisted state, and `rlp_execute` is the only externally reachable entry point capable of resetting it, but it immediately short-circuits and refuses to run while the flag is `true`. There is no recovery path.

### Impact Explanation
This permanently locks the given Wallet Contract instance out of ever again executing any Ethereum-style transaction — including native NEAR transfers, NEP-141 transfers, and any other action routed through `rlp_execute`. Because the Wallet Contract is the sole intended mechanism for a user to authorize actions from their eth-derived NEAR account, this is a permanent freeze of the account's usable value/authority through its intended interface — directly analogous to the referenced report's "one bad token permanently freezes claim funds" bug class. This qualifies as concrete "permanently frozen funds" impact.

### Likelihood Explanation
Any user who signs (or is tricked/relayed into signing) an Ethereum-style ERC-20-transfer transaction whose `to` address resolves to a malicious NEP-141 contract triggers this path; the attacker only needs to deploy a token contract that returns an oversized `storage_balance_of` payload, i.e. a single crafted transaction/RPC submission reaching an unprivileged, permissionless code path (`rlp_execute` → `inner_rlp_execute` → the ERC-20-transfer promise chain). No validator, network, or operator privilege is required.

### Recommendation
- Bound the size of `storage_balance_of` return data before deserializing (e.g. reject/short-circuit if `value.len()` exceeds a sane threshold), and/or
- Restructure the state machine so `has_in_flight_tx` is cleared unconditionally by a mechanism that cannot be reverted by a callback panic — e.g. reset the flag in a preceding, minimal-gas step that is guaranteed to commit regardless of what the external token contract does, or use `#[callback_unwrap]`/two-phase commit patterns that separate "clear in-flight flag" from "process untrusted response" into different receipts so a downstream panic cannot roll back the flag reset.

### Proof of Concept
1. Deploy a malicious NEP-141-like contract whose `storage_balance_of` method returns an extremely large byte payload (e.g. several hundred KB to a few MB of JSON) instead of a small `StorageBalance` object.
2. Have the Wallet Contract owner (or a relayer on their behalf) sign and submit an emulated ERC-20 `transfer` Ethereum transaction with `to` pointing at the malicious token (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-458`).
3. `rlp_execute` sets `has_in_flight_tx = true` and schedules `storage_balance_of` → `nep_141_storage_balance_callback` with the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`-derived budget.
4. The malicious contract's oversized return value causes `nep_141_storage_balance_callback` to exceed its prepaid gas while reading/deserializing the promise result (`lib.rs:203-221`), causing the receipt to fail/panic.
5. Because the function call failed, `self.has_in_flight_tx = false` (line 202) is not persisted; the contract's stored state still has `has_in_flight_tx = true`.
6. Any subsequent call to `rlp_execute` (for any target, including a legitimate one) immediately fails with "transaction already in progress, please try again later" (`lib.rs:97-105`), forever, since nothing else can clear the flag.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
