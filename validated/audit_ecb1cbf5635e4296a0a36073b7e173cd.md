### Title
Method-name delimiter confusion in NEAR Wallet Contract's `action_to_promise()` allows privilege injection into `FunctionCall` access keys - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Vim CVE root cause is a crafted value (filename) being interpolated into a delimiter-based command string with insufficient escaping of the delimiter, allowing an attacker-controlled value to be re-parsed as multiple, unintended commands. The equivalent bug class exists in the NEAR Wallet Contract, where a list of method names is serialized with `Vec<String>::join(",")` and later re-parsed by splitting on the very same `,` delimiter (`split_method_names`) without any check that individual method-name strings do not themselves contain a comma.

### Finding Description
When the Wallet Contract processes an ETH-style `AddKey` action for a `FunctionCall` access key, it converts the ABI-decoded `method_names: Vec<String>` into a single comma-joined string before invoking the NEAR SDK promise API: [1](#0-0) 

This joined string is transmitted as the raw `method_names` bytes of `promise_batch_action_add_key_with_function_call` / `promise_batch_action_add_gas_key_with_function_call`. On the runtime/host-function side, this single string is re-split into a `Vec<Vec<u8>>` using the same `,` separator, with the only validation being rejection of *empty* segments — not rejection of commas embedded in a segment that was meant to be a single method name: [2](#0-1) 

The resulting `Vec<Vec<u8>>` is converted into the final `FunctionCallPermission.method_names` that gets persisted as an access key and later checked against the actual `FunctionCall` action's `method_name` in both direct calls and meta-transactions: [3](#0-2) [4](#0-3) [5](#0-4) 

Because the ETH-ABI decode step in `parse_tx_data` (`ADD_KEY_SELECTOR` branch) accepts `method_names` as an `Array(String)` with no restriction on the character set of each string element, a wallet owner's ETH-signed transaction can legally include an array element that itself contains a literal comma character, e.g. `["safe_method,other_method"]`: [6](#0-5) 

When this single array entry is later joined with `,` in `action_to_promise`, the resulting string is byte-for-byte indistinguishable from the two-entry array `["safe_method", "other_method"]`. The downstream `split_method_names` call has no way to tell these two semantically different inputs apart, so the created `FunctionCallPermission.method_names` silently expands to permit calling `other_method` in addition to (or instead of) the single method name that was actually intended/displayed to the signer.

### Impact Explanation
This is a state-transition/authorization-integrity bug: the on-chain permission granted by an `AddKey` action can diverge from what was represented to and cryptographically authorized by the account owner. A user or a UI that displays/derives the intended permission from the ABI-decoded array (a single entry) can be misled into believing a narrow, harmless function-call permission is being granted, while the actual runtime-enacted `FunctionCallPermission` (after join+split) grants access to a second, real, and potentially privileged method name (e.g., `ft_transfer`, `ft_transfer_call`, or any other sensitive method on the receiver contract). Since function-call access keys are the mechanism gating unauthorized value movement and method invocation for ETH-implicit ("wallet contract") accounts, this can result in an access key that unlocks calls the signer did not intend to authorize — a concrete privilege-escalation / method-restriction-bypass affecting fund-moving operations reachable purely from a signed transaction/relayer-submitted meta-transaction.

### Likelihood Explanation
Reachable with a single, standard `rlp_execute`/`AddKey`(FunctionCall) ETH transaction routed through the Wallet Contract's public entry point, requiring no validator or node compromise — only the ability to encode an ABI string parameter containing a comma, something ordinary Ethereum tooling permits without restriction. The relayer does not need to be malicious; the confusion is introduced entirely by the Wallet Contract's own serialization logic, so any legitimately signed transaction with such a crafted method-name string triggers it deterministically.

### Recommendation
- In `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs::action_to_promise`, reject (or percent/escape) any `method_names` entry containing the `,` separator before calling `.join(",")`, returning a `UserError` instead.
- In `runtime/near-vm-runner/src/logic/utils.rs::split_method_names` and the corresponding host functions in `wasmtime_runner/logic.rs`, treat commas embedded within an intended single method name as invalid input (defense in depth), since this ambiguity affects every caller of the comma-joined method-names host API, not just the Wallet Contract.
- Prefer switching the host function ABI (or the Wallet Contract's internal call) to a length-prefixed / structurally unambiguous encoding (e.g., passing a `Vec<String>` directly through borsh/serde rather than a comma-joined string) to eliminate the delimiter-confusion class entirely.

### Proof of Concept
1. Construct a valid Ethereum transaction (correctly ECDSA-signed by the ETH-implicit account owner) invoking the Wallet Contract's `rlp_execute` with an `AddKey` action whose ABI-encoded `method_names` array contains exactly one string: `"safe_method,ft_transfer"`.
2. Submit via any relayer to `rlp_execute` targeting the account itself (`ADD_KEY_SELECTOR` requires `SelfNearNativeAction`), per `parse_tx_data` in `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`.
3. In `action_to_promise`, `access.method_names.join(",")` produces the string `"safe_method,ft_transfer"` — identical to what a legitimate two-entry array `["safe_method", "ft_transfer"]` would produce.
4. The promise executes `promise_batch_action_add_key_with_function_call`, whose host implementation calls `split_method_names`, splitting the string back into two entries: `"safe_method"` and `"ft_transfer"`.
5. The resulting `AddKeyAction` persists a `FunctionCallPermission { method_names: ["safe_method", "ft_transfer"], .. }` on the account, even though the signer's ABI payload only ever contained one array element and may have intended to scope the key to a single (nonexistent) method name string.
6. Any holder of this access key can now call the real `ft_transfer` method on the restricted `receiver_id`, verified via `verify_function_call_permission` in `runtime/runtime/src/verifier.rs`, which only checks exact string membership in `method_names` and has no awareness that the list was reconstructed from an ambiguous comma-joined string.

/// Uses `,` separator to split `method_names` into a vector of method names.
/// Returns an empty vec if the empty slice is given.
/// Throws `HostError::EmptyMethodName` in case there is an empty method name inside.
pub(crate) fn split_method_names(method_names: &[u8]) -> Result<Vec<Vec<u8>>, HostError> {
    if method_names.is_empty() {
        Ok(vec![])
    } else {
        method_names
            .split(|c| *c == b',')
            .map(|v| if v.is_empty() { Err(HostError::EmptyMethodName) } else { Ok(v.to_vec()) })
            .collect()
    }
}
