### Title
Unbounded Growth of `Stakes.vote_accounts` Enables Validator-Registration DoS at Epoch Boundaries - (File: `runtime/src/stakes.rs`)

### Summary
Any unprivileged client can create an unlimited number of vote accounts via the vote program's `InitializeAccount`/`InitializeAccountV2` instruction for only the cost of a rent-exempt reserve, which is fully recoverable. Every such account is permanently cached in the bank-wide `Stakes.vote_accounts` map maintained by `StakesCache`, and this *unfiltered* set is iterated in full, once per epoch, by every validator in the cluster as part of consensus-critical epoch-boundary processing. Because there is no limit on the number of vote accounts admitted into this set (unlike the bounded, alpenglow-specific "VAT"-filtered subset), an attacker can grow this table without bound, directly increasing consensus-critical computation performed by every validator at every epoch transition — precisely the "unrestricted validator registration → unbounded linear-time table" pattern described in the analogous Ditto report.

### Finding Description
Vote accounts are created permissionlessly. `StakesCache::check_and_store` inserts *any* correctly sized and initialized vote-program-owned account into the cache's `vote_accounts` map, without any stake or balance requirement: [1](#0-0) 

This insertion happens for every stored account after every transaction via `update_stakes_cache`: [2](#0-1) 

At every epoch boundary, `process_new_epoch` calls `compute_new_epoch_caches_and_rewards`, which calls `stakes.calculate_activated_stake(...)`, which in turn calls `refresh_vote_accounts`. This function iterates over the **entire, unfiltered** `self.vote_accounts` map — not the alpenglow "VAT"-bounded subset: [3](#0-2) [4](#0-3) 

The result — `unfiltered_distribution_vote_accounts` — is exactly what gets persisted back into the cache for the next epoch via `activate_epoch`, so the table never shrinks and every future epoch iterates the ever-growing set: [5](#0-4) [6](#0-5) 

A limit does exist, but it is only applied to a *derived, filtered* copy used for reward distribution and leader-schedule snapshotting (`clone_and_filter_for_vat`, bounded by `MAX_ALPENGLOW_VOTE_ACCOUNTS`): [7](#0-6) 

This filtering step happens *after* the expensive unfiltered `refresh_vote_accounts` pass has already run over the full (unbounded) account set, so the mitigation does not bound the actual per-epoch computational cost — only the size of the cached leader-schedule/reward snapshot.

### Impact Explanation
`process_new_epoch` runs synchronously and identically on every validator in the cluster as part of freezing/creating the first bank of a new epoch — it is not gated by the per-transaction compute budget that bounds ordinary program execution. If the size of `Stakes.vote_accounts` grows unbounded due to cheap, permissionless vote-account creation, the CPU work performed by `refresh_vote_accounts` (and related O(n) passes such as `parse_epoch_vote_accounts` inputs and `staked_nodes()` computation) grows linearly with the number of ever-created vote accounts. Because this work occurs at every epoch boundary for the lifetime of the chain (accounts are never pruned unless explicitly closed by their creator), a sustained spam campaign can progressively increase the time every validator spends processing each epoch transition, risking degraded liveness, missed slots, or in the worst case desynchronized/stalled epoch transitions across the cluster — a consensus-availability risk rather than a per-instruction gas griefing issue.

### Likelihood Explanation
Creating a vote account only requires funding a `system_instruction::create_account` for `VoteStateV4::size_of()` bytes at the rent-exempt minimum and issuing `InitializeAccount`/`InitializeAccountV2` — no stake, minimum balance beyond rent-exemption, or governance is required, and the rent-exempt lamports are fully recoverable by the attacker later (via `CloseVoteAccount` style withdrawal). This makes bulk creation of large numbers of "fake" vote accounts inexpensive and repeatable over time, so the preconditions for triggering unbounded growth of `Stakes.vote_accounts` are trivially reachable by any ordinary client.

### Recommendation
Apply an admission limit (or a minimum stake/balance requirement) directly at vote-account creation/insertion time in `StakesCache::check_and_store` / `VoteAccounts::insert`, rather than only filtering a derived snapshot after the expensive unfiltered pass has already executed. Alternatively, bound `refresh_vote_accounts`'s working set to the same `MAX_ALPENGLOW_VOTE_ACCOUNTS`/minimum-balance criteria used by `clone_and_filter_for_vat` *before* the O(n) computation runs, so that the per-epoch consensus-critical cost is provably capped regardless of how many vote accounts have ever been created.

### Proof of Concept
1. Repeatedly submit transactions from any funded account calling `system_instruction::create_account` (owner = vote program, size = `VoteStateV4::size_of()`, funded to rent-exemption) followed by `VoteInstruction::InitializeAccount`, as done in `vote_instruction::create_account_with_config` (see `cli/src/vote.rs:1052-1074` for the exact instruction sequence used by ordinary clients).
2. Repeat this a very large number of times across many slots (bounded only by attacker's available fee-paying capital, since the rent-exempt reserve is recoverable by later closing the accounts).
3. Observe that each such account is unconditionally inserted into `Stakes.vote_accounts` by `StakesCache::check_and_store` (`runtime/src/stakes.rs:118-127`) with no cap.
4. At the next epoch boundary, `process_new_epoch` → `compute_new_epoch_caches_and_rewards` → `calculate_activated_stake` → `refresh_vote_accounts` iterates the full unbounded `vote_accounts` map (`runtime/src/stakes.rs:481-491, 796-807`) on every validator, with per-epoch cost scaling linearly with the number of accounts created in step 1/2, and the resulting unfiltered set is persisted for all future epochs via `activate_epoch` (`runtime/src/bank.rs:1858-1863`).
