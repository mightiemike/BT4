### Title
Overly-broad ChainError → RejectCode collapse causes signers to permanently and irrecoverably reject validly-proposable blocks on transient failures - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
`BlockValidateRejectReason`'s blanket `From<T> where T: Into<ChainError>` conversion collapses every chainstate/DB error except `db_error::NotFoundError` into the single generic `ValidateRejectCode::ChainstateError` code. [1](#0-0)  The signer's re-evaluation logic, `should_reevaluate_reject_reason`, then treats `ValidationFailed(NotFoundError)` as a transient/retryable rejection but treats every other `ValidationFailed(_)` variant — including the generic `ChainstateError` bucket that any transient DB/chainstate failure falls into — as permanent, non-retryable. [2](#0-1)  This is the same root-cause pattern as the Reserve `DutchTrade`/`BackingManager` finding: a heuristic that assumes "no specific error data/code" implies one narrow condition (out-of-gas there, "not found" here), when in fact many unrelated conditions collapse into the same generic bucket, and the code treats the generic bucket as if it always meant the narrow, more severe condition.

### Finding Description
`postblock_proposal.rs` defines `ValidateRejectCode` with a dedicated `NotFoundError` variant and a catch-all `ChainstateError` variant. [3](#0-2)  The generic `From` impl used throughout block-proposal validation maps `db_error::NotFoundError` specifically to `ValidateRejectCode::NotFoundError`, and maps *every other* `ChainError` (including all other `db_error` variants such as I/O errors, lock/busy errors, corruption, MARF errors propagated as chainstate errors, etc.) to the same generic `ValidateRejectCode::ChainstateError`:

```
ChainError::DBError(db_error::NotFoundError) => ValidateRejectCode::NotFoundError,
_ => ValidateRejectCode::ChainstateError,
``` [4](#0-3) 

On the signer side, once a block is marked rejected with a given `reject_reason`, `should_reevaluate_reject_reason` decides whether a later re-proposal (or a re-check) of that same block is allowed to overturn the earlier verdict. It explicitly whitelists `ValidationFailed(ValidateRejectCode::NotFoundError)` (along with a few clearly-transient categories such as `ConnectivityIssues`, `NoSortitionView`, `TestingDirective`) as reevaluable, but funnels *every other* `ValidationFailed(_)` code — which is where the generic `ChainstateError` bucket lands — into the "no need to re-validate" branch, i.e. permanently final:

```
RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
| RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
| RejectReason::NoSortitionView
| RejectReason::ConnectivityIssues(_)
| ... => true,
RejectReason::ValidationFailed(_)
| RejectReason::RejectedInPriorRound
| ... => false,   // "No need to re-validate these types of rejections."
``` [2](#0-1) 

This decision gates `should_reevaluate_block`, which is invoked whenever a block proposal (or re-proposal with the same signature hash) arrives for a block the signer already has an opinion on. [5](#0-4)  If `should_reevaluate_reject_reason` returns `false`, the signer either re-sends its (stale) previous determination or does nothing — it never re-runs validation, even if the original failure was a purely transient chainstate/DB condition (lock contention, disk I/O hiccup, momentary MARF read failure, etc.) that has since cleared.

Just as in the Reserve report — where "empty revert data" was assumed to mean "out of gas" when it can also mean "any other silent revert" — here "`ChainstateError`" is a single bucket that is assumed by the re-evaluation policy to always mean "the block/chain state is genuinely, permanently wrong," when in fact it is populated by any non-`NotFoundError` variant of `ChainError`, including transient infrastructure failures unrelated to the block's validity. The classification is performed once, at the moment of the transient hiccup, and the resulting verdict is then locked in as permanent by `should_reevaluate_reject_reason`.

### Impact Explanation
A signer that experiences a momentary chainstate/DB hiccup (e.g., lock contention from a background compaction, a transient I/O error, or any other non-`NotFoundError` propagated as `ChainError`) while validating one otherwise-valid block proposal will record a permanent `ValidationFailed(ChainstateError)` rejection for that specific `signer_signature_hash`, in `handle_block_validate_ok`/rejection handling paths that persist `block_info.reject_reason`. [6](#0-5)  Because `should_reevaluate_reject_reason` will never allow this signer to reconsider that verdict for that block hash, this signer's vote for that exact block is permanently withheld even after the transient condition has fully resolved and every other honest signer validates and signs the block. This is exactly the "a validation verdict two nodes disagree on" scenario the rules list as an accepted High-severity impact class: two otherwise-honest, unprivileged signer nodes reach different, non-reconcilable verdicts on the same valid block because of a purely incidental, non-adversarial local condition rather than any real state difference — and one of them is permanently and irrecoverably wrong about it. In the degenerate but realistic case where several signers hit similar transient load conditions around the same block (e.g., during high mempool/database load at a tenure boundary), the loss of their pooled weight can push the block below the signing threshold, forcing a stalled tenure/re-proposal — a temporary tip disagreement/liveness impact bounded to that block.

### Likelihood Explanation
Likelihood is comparable to the original Reserve finding's assessment (accepted as Medium there, and analogous "signer transient error" cases in this repo's own changelog show the team is aware such transient errors occur and require explicit retry handling — see the miner-thread fix that specifically retries on "DB contention... mempool cache reset failure" rather than giving up). [7](#0-6)  The miner side of the codebase was patched to distinguish transient failures from fatal ones and retry; the signer's block-rejection reconsideration policy has not received the same treatment, and the underlying `From<T> for BlockValidateRejectReason` conversion actively erases the distinction needed to do so, since it discards the specific `ChainError` variant in favor of one generic code.

### Recommendation
Do not collapse all non-`NotFoundError` `ChainError` variants into a single generic `ValidateRejectCode::ChainstateError`. Instead, classify errors by whether they are known-transient (I/O, lock/busy, MARF/database contention) versus errors that genuinely indicate the block or chain state is invalid, and expose that distinction through `ValidateRejectCode` (or an additional field) so that `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs` can correctly allow re-validation for transient failures, mirroring the treatment already given to `NotFoundError`, `ConnectivityIssues`, and `NoSortitionView`.

### Proof of Concept
1. A miner proposes a valid Nakamoto block `B` with signer-signature-hash `H`.
2. A signer `S` (unprivileged, no majority coordination required) calls `BlockProposal::validate`, which internally hits a transient `ChainError` unrelated to block validity (e.g., a momentary sqlite `db_error` variant other than `NotFoundError`, surfaced through any `?`-propagated call in the validation path).
3. The generic `From<T> for BlockValidateRejectReason` impl converts this into `ValidateRejectCode::ChainstateError`, and `S` persists `block_info.reject_reason = RejectReason::ValidationFailed(ValidateRejectCode::ChainstateError)`. [8](#0-7) 
4. The transient condition clears immediately afterward; block `B` is in fact perfectly valid, and every other signer signs it.
5. The miner (or another signer) re-proposes/re-broadcasts the identical block `B` (same `H`) — this happens routinely in the existing re-proposal/pre-commit flow.
6. `S`'s `should_reevaluate_block` calls `should_reevaluate_reject_reason(block_info)`, which matches `ValidationFailed(ChainstateError)` in the `false` arm and refuses to re-validate. [9](#0-8) [10](#0-9) 
7. `S` permanently withholds its signature for block `B`, disagreeing with every other honest signer's verdict on the exact same, valid block, for the lifetime of that block hash.

impl<T> From<T> for BlockValidateRejectReason
where
    T: Into<ChainError>,
{
    fn from(value: T) -> Self {
        let ce: ChainError = value.into();
        let reason_code = match ce {
            ChainError::DBError(db_error::NotFoundError) => ValidateRejectCode::NotFoundError,
            _ => ValidateRejectCode::ChainstateError,
        };
        Self {
            reason: format!("Chainstate Error: {ce}"),
            reason_code,
            failed_txid: None,
        }
    }
}

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
