### Title
Webhook HMAC does not bind shop domain/topic to signature, enabling cross-tenant webhook forgery - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The Shopify webhook authenticity check computes an HMAC only over the raw request body, using the app's single shared `apiSecretKey`. The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers used to identify which tenant/shop and which event the webhook belongs to are never included in the HMAC-covered data, so any valid `(rawBody, hmac)` pair obtained from one shop can be replayed against the app's public webhook endpoint with a forged domain/topic to be accepted as an authentic event for a *different* shop.

### Finding Description
`validateHmacString` computes `createSHA256HMAC(config.apiSecretKey, data, format)` over `rawBody` alone and compares it to the caller-supplied HMAC header with `safeCompare`: <cite repo="patrichyt/shopify-app-js--005" path="packages/apps/shopify-api/lib/utils/hmac-validator.ts" start="153="162" /> Actually let's cite precisely: [1](#0-0) 

`validateHmacFromRequestFactory` only feeds `rawBody` (and the HMAC header value) into this check; it never mixes in the `domain`, `topic`, or `webhookId` headers: [2](#0-1) 

After the HMAC passes, `validateFactory`/`checkWebhooksHeaders` reads `domain`, `topic`, `webhookId`, and `apiVersion` directly from request headers, with **no cryptographic link to the already-validated body/HMAC**, and returns them as trusted fields: [3](#0-2) 

Both the Remix and React Router `authenticate.webhook` implementations then use `check.domain` directly to load the real offline session/access token for that shop and construct an authenticated Admin API client, and dispatch to the handler keyed by `check.topic`: [4](#0-3) [5](#0-4) 

The Express-style `process()` handler routes to registered callbacks the same way, passing `webhookCheck.domain` (attacker-controlled header) straight to the handler callback: [6](#0-5) 

Because `config.apiSecretKey` is the single secret shared by **all shops that install the app** (this is a multi-tenant SaaS secret, not per-shop), any shop/merchant that has installed the app can trigger Shopify to send them a legitimately HMAC-signed webhook for their own store, capture the `(rawBody, hmac)` pair, and then POST that exact pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to point at a victim shop. `validateHmacString` cannot detect this because the domain/topic were never part of what was signed — directly analogous to the reported `OnChainLab::isValidSignature` issue where the raw hash doesn't bind `address(this)`, letting one valid signature be replayed against a different account context.

### Impact Explanation
An attacker who is merely an app-installing merchant (unprivileged relative to other tenants) can forge webhook deliveries "from" any other shop that has the same app installed:
- Load the victim's real offline session/access token via `ensureValidOfflineSession(params, check.domain)` and get an authenticated `admin` client scoped to the victim shop, driving app business logic (e.g., data sync, order processing) against the victim's store using attacker-chosen `rawBody` content.
- Trigger sensitive lifecycle handlers such as `APP_UNINSTALLED` for a victim shop, potentially causing the app to delete/invalidate the victim's stored session or perform other destructive cleanup — a cross-tenant, unauthenticated DoS/data-integrity issue.
- More generally, break the app's trust boundary between tenants, since headers that identify "which shop" and "which event" are unauthenticated relative to the payload's HMAC.

### Likelihood Explanation
Likelihood is high in any multi-tenant deployment of this framework: the attacker only needs to be able to install the app on one shop they control (a very low bar — trial/dev stores are trivial to create) and to be able to send raw HTTP POSTs to the app's public `/webhooks` endpoint, which by design accepts unauthenticated inbound requests validated only by HMAC.

### Recommendation
Bind the tenant/event context into the authenticated data before comparing HMACs, e.g. compute/verify the HMAC over a canonical string that includes the `domain` (and ideally `topic`/`webhookId`) headers concatenated with `rawBody`, or otherwise cryptographically tie the trusted headers to the signed payload rather than trusting them independently. At minimum, cross-check that the resolved shop domain corresponds to a shop that is expected to be the source of this specific webhook delivery (e.g., validate it's actually installed and that the webhook subscription for that topic/shop was registered), rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any Shopify event (e.g., `orders/create`) that causes Shopify to POST a webhook to the app's endpoint; capture the raw request body and the `X-Shopify-Hmac-Sha256` header value — this HMAC is valid because it's computed with the shared `apiSecretKey`, independent of the shop domain.
3. Replay that exact `(rawBody, hmac)` pair via a direct POST to the app's `/webhooks` endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally forge `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `validateHmacFromRequestFactory` accepts the request as valid (per [7](#0-6) ), `checkWebhooksHeaders` extracts `domain = 'victim-shop.myshopify.com'`, and `authenticate.webhook` loads `victim-shop.myshopify.com`'s real offline session and dispatches the (forged) event to the app's handler as if Shopify itself had sent it for that shop.
