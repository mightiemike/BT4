### Title
`clean_accounts()` panics via `.unwrap()` on a missing storage entry when computing store counts, aborting the entire clean pass - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::clean_accounts()` iterates over all clean candidates (pubkeys across many bins/slots) to compute `store_counts`, the reference counts used to decide which accounts can be purged. For the first pubkey seen in a given slot, it looks up the storage entry for that slot/store-id and calls `.unwrap()` directly on the `Option` returned by `get_account_storage_entry`, with no fallback path. If the storage entry is absent, the whole thread executing `clean_accounts()` panics, aborting cleaning for *all* other unrelated candidates being processed in that same pass — not just the pubkey/slot whose storage went missing. This mirrors the SafEth pattern where one derivative's unchecked failure condition reverts the entire multi-item `stake()` loop instead of being isolated.

### Finding Description
In the store-count computation loop of `clean_accounts()`: [1](#0-0) 

```rust
let count = self
    .storage
    .get_account_storage_entry(*slot, account_info.store_id())
    .map(|store| store.count())
    .unwrap()
    - 1;
```

`candidates_bin` entries are built earlier in the same function from a parallel index scan (`self.accounts_index.scan(...)`) that reads `slot_list` from the accounts index independent of the storage map's current state: [2](#0-1) 

Because the index scan and the later store-count loop are two separate passes over the same `candidates` structure, and `clean_accounts()` runs concurrently with (or interleaved with) other background maintenance (shrink, purge, `handle_reclaims`, storage removal on `remaining_accounts == 0` in `clean_accounts_older_than_root`/reclaim handling, dead-slot dropping), it is architecturally possible for a storage entry that the index still references in `slot_list` to have already been removed from `self.storage` by the time this loop runs — for example a slot dropped concurrently via `handle_reclaims`/dead-slot removal, or a race between candidate construction and reclaim application within the same `clean_accounts()` call. In that situation `get_account_storage_entry` returns `None`, and `.unwrap()` panics.

This is analogous to the SafEth report's core defect: a single item in a larger iteration (one derivative / here, one slot's storage lookup) that lacks a defensive check causes an unrecoverable failure of the *entire* surrounding operation (the whole `stake()` call / the whole `clean_accounts()` pass across all other unrelated candidates), rather than being skipped or handled gracefully.

### Impact Explanation
`clean_accounts()` is not an isolated per-item operation — it is the primary garbage-collection routine for `AccountsDb`, invoked continuously by the accounts background service and via `shrink_all_slots`'s `maybe_clean()` path: [3](#0-2) 

A panic here crashes the calling thread (the background cleaning thread, or, at startup, the foreground thread doing `shrink_all_slots(is_startup=true, ...)`), which for a validator process results in a node crash/DoS. Because the check-then-panic occurs deep inside a routine that services *all* dirty candidates in the pass, a single stale/missing storage reference takes down cleanup for every other pubkey/slot being processed in that call, consistent with the "disproportionate ... CPU cost" / "node panic" impact categories called out in scope.

### Likelihood Explanation
The precondition (storage entry present in `slot_list` from the index scan but absent from `self.storage` by the time the store-count loop executes) requires a race between two separate traversals of shared, concurrently-mutated state (`accounts_index` and `self.storage`) within a single `clean_accounts()` invocation, and/or concurrent background threads mutating storage (shrink, purge, other clean passes). This is a maintenance-path issue reachable purely through normal validator operation (no attacker-controlled or malicious-snapshot input is required), which is why it is being reported as a concrete internal invariant violation rather than a purely theoretical one. Exact triggering conditions (how the index and storage map can diverge across the two passes of the same `clean_accounts()` call) were not fully traced within the available exploration; confirming the precise race requires deeper analysis of `handle_reclaims`, `purge_keys_exact`, and any locking discipline between `self.accounts_index` and `self.storage` mutation, which time did not permit to fully verify here.

### Recommendation
Replace the `.unwrap()` with a graceful fallback: if `get_account_storage_entry` returns `None` for a slot referenced by a clean candidate, log/record the anomaly, skip that slot/pubkey (treat it as already reclaimed) rather than panicking, and continue processing the remaining candidates in `store_counts`. This preserves fail-open availability of the cleaning process instead of allowing one missing entry to abort cleanup for the whole batch, and is consistent with the more defensive `continue`/`filter_map` patterns already used elsewhere in this same function (e.g., `select_candidates_by_total_usage`'s `let Some(store) = ... else { continue; }` pattern) and elsewhere in `accounts_db.rs`.

### Proof of Concept
A minimal repro sketch (not executed, derived from code inspection):
1. Store an account for pubkey `P` in slot `S`, root it, and flush.
2. Concurrently trigger a code path that drops slot `S`'s storage entry from `self.storage` (e.g., via a reclaim that marks `S` fully dead) at the same moment `clean_accounts()`'s index scan has already captured `P`'s `slot_list` containing `(S, account_info)`.
3. Call `clean_accounts()` (or let the background cleaning thread run it). When the store-count loop reaches `P`, `self.storage.get_account_storage_entry(S, account_info.store_id())` returns `None`, and `.unwrap()` panics, terminating the cleaning thread/process while other unrelated candidates in the same batch are left unprocessed.

Note: I was not able to fully construct and verify a deterministic concurrent trigger for the race within the scope of this review; the finding is based on the concrete absence of an error-handling path (`.unwrap()` vs. graceful skip) at this specific site, contrasted with the defensive patterns used in sibling code in the same file.
