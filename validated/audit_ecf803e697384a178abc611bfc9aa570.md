### Title
Checked-arithmetic "hardening" in `ResourceProcessor.increase()` reverts (via `ArithmeticException`) instead of the originally-desired silent overflow, risking permanent DoS of resource accounting for an account - (File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java)

### Summary
The Sherlock report describes UniswapV2-derived code that intentionally relies on silent wraparound arithmetic for `timeElapsed`/`priceCumulative`, but because the fork moved to Solidity ≥0.8.0 (checked arithmetic by default), the same operation that used to wrap now reverts, permanently bricking core pool functions. `ResourceProcessor` in java-tron contains an analogous dual-path design: a legacy path that uses plain Java `long` arithmetic (which silently wraps on overflow, matching the original UniswapV2/Solidity 0.6.6 behavior) and a "hardened" path, gated by `hardenCalculation()`, that instead performs the same math with `BigInteger` and converts back with `.longValueExact()` / `StrictMathWrapper.addExact` style calls that throw `ArithmeticException` if the value cannot be represented in a `long`. [1](#0-0) 

### Finding Description
`increase()` (used for both bandwidth and energy accounting) computes `averageLastUsage`/`averageUsage` either via unchecked `long` multiplication/division (silent overflow, "wrap" semantics – the old, "desired" behavior) or, when `hardenCalculation()` is true, via `BigInteger.multiply(...)` followed by `divideCeilExact(...)`, which calls `BigInteger.longValueExact()` internally and throws `ArithmeticException` on overflow. [2](#0-1) 

The same pattern recurs in `increase(AccountCapsule...)`, `increaseV2`, `unDelegateIncreaseV2`, and `getNewWindowSize`, all of which switch between raw `long` math and BigInteger-exact math depending on `hardenCalculation()`. [3](#0-2) [4](#0-3) 

These `increase()`/`recovery()` helpers are invoked directly from the transaction-processing path in `BandwidthProcessor.consume()` (bandwidth accounting for every transaction) via `useAccountNet`, `useFreeNet`, `useTransactionFee`, `consumeBandwidthForCreateNewAccount`, and `useAssetAccountNet`. [5](#0-4) [6](#0-5) 

`RepositoryImpl` in the VM/actuator layer contains an equivalent `increase()` for energy metering with the exact same hardened/unhardened split. [7](#0-6) 

The existence of dedicated tests explicitly confirming `ArithmeticException` is thrown under hardening but silently succeeds without it (`testIncreaseOverflowDetectedWithHardening` vs `testIncreaseOverflowSilentWithoutHardening`) demonstrates the behavior change is intentional and acknowledged by the code owners, but it means once `hardenCalculation()` is turned on (via the `AllowHardenResourceCalculation` dynamic property/proposal), any account whose long-running usage/window bookkeeping crosses the point where `lastUsage * precision` (or similar cross-products) no longer fits into a 64-bit `long` will start throwing `ArithmeticException` from a call that used to silently overflow and produce a (safe, self-correcting) wrapped result. [8](#0-7) 

### Impact Explanation
If `ArithmeticException` is thrown from within `BandwidthProcessor.consume()` or the analogous `EnergyProcessor`/`RepositoryImpl.increase()` calls during normal transaction processing, and this unchecked exception is not caught by a resource-accounting-specific handler upstream (only `ContractValidateException`, `AccountResourceInsufficientException`, `TooBigTransactionException`, `TooBigTransactionResultException` are declared/caught in this code path), it will propagate as an uncaught runtime exception during block application. Depending on where the exception is ultimately caught by the block-processing framework, this could either (a) cause repeated transaction/block-application failures for the affected account (a persistent, un-fixable DoS on that account's bandwidth/energy operations, mirroring the "permanently broken pool" impact in the Sherlock report), or (b) in the worst case propagate further and destabilize block processing on nodes that have `hardenCalculation()` enabled, which is a consensus-relevant DoS risk since it changes deterministic transaction outcomes based on the flag/activation state.

### Likelihood Explanation
Likelihood is **low-to-uncertain** and could not be fully confirmed from the indexed code: (1) I could not verify from available context whether `hardenCalculation()`/`AllowHardenResourceCalculation` is enabled by default, staged as a hard-fork feature, or opt-in only, which determines whether this checked path is reachable in production. (2) I could not locate a catch-all handler for `ArithmeticException` in the transaction-application call chain (`TransactionTrace`/actuator execution) to confirm whether such an exception would crash block processing outright or be safely rejected per-transaction. (3) Reaching the actual overflow requires resource usage/window-size values to grow large enough that a `long` multiplication result exceeds `Long.MAX_VALUE`, which — unlike the Solidity report's 32-bit timestamp that overflows in a fixed, guaranteed number of years — depends on the magnitude of frozen balances, resource limits, and window sizes in java-tron's resource model; whether this is realistically reachable under real network/resource-limit parameters is not established here.

### Recommendation
- Confirm the activation status and enablement conditions of `AllowHardenResourceCalculation` and audit all call sites of `ResourceProcessor.increase/recovery/getNewWindowSize` and `RepositoryImpl.increase` for `ArithmeticException` reachability.
- Ensure the transaction-processing pipeline (`BandwidthProcessor.consume`, `EnergyProcessor.consume`, actuator execution in `RepositoryImpl`) explicitly catches `ArithmeticException` originating from the hardened math path and converts it into a normal `ContractValidateException`/resource-insufficient rejection of the specific transaction, rather than letting it propagate as an unchecked runtime exception.
- Add regression/integration tests that exercise the hardened path through the full `consume()`/block-application flow (not just the unit-level `increase()` calls) to verify no uncaught exception can halt block processing.

### Proof of Concept
Not fully constructible from the indexed code alone — a concrete PoC would require reproducing account state (large `getUsage`, `getWindowSize`, or `getWindowSizeV2` values plus the relevant frozen-balance/limit configuration) that drives `lastUsage * precision` or `remainUsage * remainWindowSize` past `Long.MAX_VALUE` while `AllowHardenResourceCalculation` is active, then invoking `BandwidthProcessor.consume()`/`RepositoryImpl.increase()` and observing whether the resulting `ArithmeticException` escapes normal per-transaction error handling. The existing unit tests already demonstrate the throw in isolation: [9](#0-8)

  protected long increase(long lastUsage, long usage, long lastTime, long now, long windowSize) {
    long averageLastUsage;
    long averageUsage;
    if (hardenCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize);
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision), biWindowSize);
    } else {
      averageLastUsage = divideCeil(lastUsage * precision, windowSize);
      averageUsage = divideCeil(usage * precision, windowSize);
    }

    if (lastTime != now) {
      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay,
            this.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }

  public long increaseV2(AccountCapsule accountCapsule, ResourceCode resourceCode,

    long oldWindowSize = accountCapsule.getWindowSize(resourceCode);
    long averageLastUsage;
    long averageUsage;
    if (hardenCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(this.precision);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision),
          BigInteger.valueOf(oldWindowSize));
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision),
          BigInteger.valueOf(this.windowSize));
    } else {
      averageLastUsage = divideCeil(lastUsage * this.precision, oldWindowSize);
      averageUsage = divideCeil(usage * this.precision, this.windowSize);
    }

    if (lastTime != now) {
      if (lastTime + oldWindowSize > now) {
        long delta = now - lastTime;
        double decay = (oldWindowSize - delta) / (double) oldWindowSize;
        averageLastUsage = round(averageLastUsage * decay,
            this.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }

    long newUsage = getUsage(averageLastUsage, oldWindowSize, averageUsage, this.windowSize);
    long remainUsage = getUsage(averageLastUsage, oldWindowSize);
    if (remainUsage == 0) {
      accountCapsule.setNewWindowSizeV2(resourceCode, this.windowSize * WINDOW_SIZE_PRECISION);
      return newUsage;
    }

    long remainWindowSize = oldWindowSizeV2 - (now - lastTime) * WINDOW_SIZE_PRECISION;
    long newWindowSize;
    if (hardenCalculation()) {
      BigInteger biNewWindowSize = BigInteger.valueOf(remainUsage)
          .multiply(BigInteger.valueOf(remainWindowSize))
          .add(BigInteger.valueOf(usage)
              .multiply(BigInteger.valueOf(this.windowSize))
              .multiply(BigInteger.valueOf(WINDOW_SIZE_PRECISION)));
      newWindowSize = divideCeilExact(biNewWindowSize, BigInteger.valueOf(newUsage));
    } else {
      newWindowSize = divideCeil(
          remainUsage * remainWindowSize + usage * this.windowSize * WINDOW_SIZE_PRECISION,
          newUsage);
    }
    newWindowSize = min(newWindowSize, this.windowSize * WINDOW_SIZE_PRECISION,
        this.disableJavaLangMath());
    accountCapsule.setNewWindowSizeV2(resourceCode, newWindowSize);
    return newUsage;
  }

  private long divideCeil(long numerator, long denominator) {
    return (numerator / denominator) + ((numerator % denominator) > 0 ? 1 : 0);
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }

  private boolean useAccountNet(AccountCapsule accountCapsule, long bytes, long now) {

    long netUsage = accountCapsule.getNetUsage();
    long latestConsumeTime = accountCapsule.getLatestConsumeTime();
    long netLimit = calculateGlobalNetLimit(accountCapsule);

    long newNetUsage;
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newNetUsage = increase(netUsage, 0, latestConsumeTime, now);
    } else {
      // only participate in the calculation as a temporary variable, without disk flushing
      newNetUsage = recovery(accountCapsule, BANDWIDTH, netUsage, latestConsumeTime, now);
    }


    if (bytes > (netLimit - newNetUsage)) {
      logger.debug("Net usage is running out, now use free net usage."
              + " Bytes: {}, netLimit: {}, newNetUsage: {}.",
          bytes, netLimit, newNetUsage);
      return false;
    }

    long latestOperationTime = chainBaseManager.getHeadBlockTimeStamp();
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newNetUsage = increase(newNetUsage, bytes, now, now);
    } else {
      // Participate in calculation and flush disk persistence
      newNetUsage = increase(accountCapsule, BANDWIDTH, netUsage, bytes, latestConsumeTime, now);
    }

    accountCapsule.setNetUsage(newNetUsage);
    accountCapsule.setLatestOperationTime(latestOperationTime);
    accountCapsule.setLatestConsumeTime(now);

    chainBaseManager.getAccountStore().put(accountCapsule.createDbKey(), accountCapsule);
    return true;
  }
