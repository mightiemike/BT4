### Title
Unbounded proposal creation allows any funded witness-registrant to spam governance proposals and grow `processProposals()` iteration cost - (File: actuator/src/main/java/org/tron/core/actuator/ProposalCreateActuator.java)

### Summary
`ProposalCreateActuator` has no per-account rate limit, no "no active proposal" check, and no cap on how many proposals a single owner address can create. Any account that pays the (fixed, non-consensus-gated) `AccountUpgradeCost` to register as a witness via `WitnessCreateContract` can then submit an unlimited number of duplicate/spam proposals, each consuming a monotonically increasing `latestProposalNum` slot in the `ProposalStore` that is later walked in full by `ProposalController.processProposals()` every maintenance cycle.

### Finding Description
The Nouns report's root cause is that spam mitigation (`checkNoActiveProp`) is keyed to a mutable/transferable identity (the proposer address) rather than the underlying resource (the Noun), and that no threshold re-check exists at proposal-update time — letting an attacker multiply proposals across addresses.

In java-tron, the analogous `ProposalCreateActuator.validate()` only checks that the address exists in the `AccountStore` and `WitnessStore`, and that the parameters are well-formed — it performs **no check at all** on how many proposals that address (or any address) has open or has ever created: [1](#0-0) 

`execute()` simply increments the global counter and stores a new proposal every time, with no de-duplication or per-owner cap: [2](#0-1) 

This is confirmed by the test `duplicateProposalCreateSame`, which explicitly shows two *identical* proposals from the same owner both succeeding with no restriction: [3](#0-2) 

The only gate on who may call `ProposalCreateContract` is `witnessStore.has(ownerAddress)` — i.e., being registered as a witness (candidate), not being an elected Super Representative. Witness registration itself is open to any account holding enough balance to pay `AccountUpgradeCost` via `WitnessCreateActuator`, which likewise has no limit on how many distinct addresses may register (only "witness already exists" for the *same* address is checked): [4](#0-3) 

Thus, exactly like the Nouns bug, an attacker can move/split funds across many addresses, register each as a witness, and from each address submit an unbounded number of proposals — there is no Noun-analog resource-based limit, and in fact tron's version is weaker than Nouns' since even the address-scoped "one active proposal" check does not exist here.

Every stored proposal (whether spam or legitimate) is scanned on each maintenance cycle by `ProposalController.processProposals()`, which walks backward from `latestProposalNum` through every un-processed proposal ID: [5](#0-4) 

### Impact Explanation
An attacker can permanently grow `latestProposalNum` and the `ProposalStore` without bound, since creation cost is a one-time, fixed TRX burn (`AccountUpgradeCost`), unrelated to the number of proposals subsequently submitted from that address. This causes:
- Unbounded on-chain storage growth in `ProposalStore`.
- Increasing linear-scan cost in `ProposalController.processProposals()` every maintenance interval, since it iterates every un-processed proposal ID back to the oldest unprocessed one.
- Governance DoS/griefing: legitimate voters/committee members must manually identify and cancel spam proposals among an arbitrarily large set, mirroring the "substantial effort... to differentiate... and cancel" impact in the original report.

This is a protocol-level DoS/griefing vector reachable from any account, not requiring privileged access — consistent with Medium severity as in the original finding, given it requires funding many accounts and doesn't directly corrupt consensus state, but does degrade node processing and DAO/committee usability over time.

### Likelihood Explanation
Medium likelihood: creating a witness registration costs a fixed `AccountUpgradeCost` (paid once) and creating a proposal is otherwise free apart from base transaction bandwidth/energy fees; an attacker with modest capital can fund N accounts, register each as a witness, and script mass proposal submission. No governance approval, veto, or reputation gate blocks initial submission — approval/disapproval only happens at proposal maturity in `processProposal()`.

### Recommendation
1. Add a per-owner-address rate limit or "no active/pending proposal" check in `ProposalCreateActuator.validate()`, analogous to Nouns' `checkNoActiveProp()`, before allowing a new proposal from the same address.
2. Consider tying proposal-creation eligibility to a resource that cannot be trivially multiplied (e.g., total frozen/staked balance or SR election status) rather than mere witness-candidate registration, since registering many witness candidates is cheap and does not require being an elected SR.
3. Consider bounding the total number of un-expired, unprocessed proposals `ProposalController.processProposals()` must scan, or introducing an increasing marginal cost for repeated proposal creation from the same funding source.

### Proof of Concept
Conceptual reproduction using the existing test harness pattern (`ProposalCreateActuatorTest`):
1. Fund N new accounts each with balance ≥ `AccountUpgradeCost`.
2. For each account, submit `WitnessCreateContract` (succeeds per `WitnessCreateActuator.validate()`, only rejecting if that same address is already a witness) — see: [6](#0-5) 
3. From each newly-registered witness address, repeatedly submit `ProposalCreateContract` with arbitrary/duplicate parameters. As demonstrated by `duplicateProposalCreateSame`, this succeeds without limit and increments `latestProposalNum` every time: [7](#0-6) 
4. Repeat across many addresses/transactions to grow `ProposalStore` and `latestProposalNum` arbitrarily, degrading `ProposalController.processProposals()` scan performance and burying legitimate proposals under spam.

  public void processProposals() {
    long latestProposalNum = manager.getDynamicPropertiesStore().getLatestProposalNum();
    if (latestProposalNum == 0) {
      logger.info("latestProposalNum is 0, return");
      return;
    }

    long proposalNum = latestProposalNum;

    ProposalCapsule proposalCapsule = null;

    while (proposalNum > 0) {
      try {
        proposalCapsule = manager.getProposalStore()
            .get(ProposalCapsule.calculateDbKey(proposalNum));
      } catch (Exception ex) {
        logger.error("", ex);
        proposalNum--;
        continue;
      }

      if (proposalCapsule.hasProcessed()) {
        logger
            .info("Proposal has processed, id:[{}], skip it and before it",
                proposalCapsule.getID());
        //proposals with number less than this one, have been processed before
        break;
      }

      if (proposalCapsule.hasCanceled()) {
        logger.info("Proposal has canceled, id:[{}], skip it", proposalCapsule.getID());
        proposalNum--;
        continue;
      }

      long currentTime = manager.getDynamicPropertiesStore().getNextMaintenanceTime();
      if (proposalCapsule.hasExpired(currentTime)) {
        processProposal(proposalCapsule);
        proposalNum--;
        continue;
      }

      proposalNum--;
      logger.info("Proposal has not expired, id:[{}], skip it", proposalCapsule.getID());
    }
    logger.info("Processing proposals done, oldest proposal[{}]", proposalNum);
  }
