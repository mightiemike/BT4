## Finding

### Title
Wallet Contract permanently retains an external caller's attached NEAR deposit when `rlp_execute` fails before a promise is created - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is a `#[payable]` method that accepts an attached NEAR deposit from any caller, tracks it as a `CallerDeposit` for refund purposes, but only ever issues that refund inside `rlp_execute_callback`, which is only reached if a cross-contract promise was actually created. Several failure paths in `inner_rlp_execute` return an `Err` *before* any promise is created, and those errors are turned into a normal `ExecuteResponse` return value rather than a panic. Since the call still "succeeds" at the protocol level, the deposit that was already credited to the wallet contract's balance is never forwarded to the intended target nor refunded to the caller.

### Finding Description
`rlp_execute` computes `caller_deposit` from the attached deposit before doing any validation of the RLP-encoded transaction: [1](#0-0) 

If `internal::parse_rlp_tx_to_action` fails (e.g. malformed RLP, unparseable ABI data, invalid access key data, oversized deposit) it returns early with `Err(err)` **without creating any `Promise`**: [2](#0-1) 

Back in `rlp_execute`, the top-level match only creates a refund/ban promise for `Error::Relayer` errors coming from the account's *own* signer key; every other error (including `Error::User`, `Error::AccountId`, `Error::AccountNonceExhausted`, and `Error::Relayer` from an external caller) falls into the final arm, which simply returns a value instead of a promise: [3](#0-2) 

The only place a `CallerDeposit` is ever refunded is `rlp_execute_callback`, and only when a scheduled promise later fails: [4](#0-3) 

`CallerDeposit` is created specifically to represent a *non-self* predecessor's attached deposit: [5](#0-4) 

Since `rlp_execute` returns `PromiseOrValue::Value(...)` (not a panic) on these early errors, the receipt is considered successful by the NEAR runtime, so the attached deposit that had already been credited to the wallet-contract account's balance as part of executing the `FunctionCall` action is **not** auto-refunded by the protocol's failure-refund mechanism, and no application-level refund promise was created either. The deposit is simply absorbed into the wallet-contract's own balance.

### Impact Explanation
Any account can call `rlp_execute` on someone else's ETH-implicit wallet-contract account, attach a NEAR deposit, and supply a deliberately malformed/garbage `tx_bytes_b64` (or otherwise trigger a `User`/`AccountId`/`Relayer` error prior to promise creation). The caller's attached NEAR is permanently and unintentionally transferred into the wallet-contract account's balance with no refund path and no way for the caller to recover it — the exact same "accepts a native-asset deposit but doesn't have a code path to move it correctly" bug class described in the reference report. This is a concrete unauthorized value movement / permanent loss of funds for the caller.

### Likelihood Explanation
Trivially reachable: any transaction signer can submit a single `FunctionCall` to `rlp_execute` with attached yoctoNEAR and invalid/garbage RLP data (there are multiple `UserError`/`AccountIdError`/`RelayerError` variants that are easy to trigger, e.g. `InvalidAbiEncodedData`, `UnknownFunctionSelector`, `InvalidBase64`, `TxParsing`). No special privileges, no cross-shard timing, and no validator/relayer cooperation are required.

### Recommendation
Ensure every early-return error path in `rlp_execute`/`inner_rlp_execute` that has a non-empty `CallerDeposit` either (a) schedules a refund promise back to the caller before returning, or (b) panics so the NEAR protocol's standard deposit-refund mechanism (`refund_unspent_gas_and_deposits`) takes over. At minimum, the final `Err(e) => PromiseOrValue::Value(e.into())` arm in `rlp_execute` should check for an outstanding `caller_deposit` and issue a transfer-back promise before returning.

### Proof of Concept
1. Attacker (or any user) funds/knows of a live ETH-implicit account `victim.near` with the Wallet Contract deployed.
2. Attacker submits a `FunctionCall` transaction to `victim.near::rlp_execute` with:
   - `target`: any account id,
   - `tx_bytes_b64`: a syntactically invalid base64/RLP string (triggers `Error::Relayer(RelayerError::InvalidBase64)` or `Error::User(UserError::InvalidAbiEncodedData)` depending on payload),
   - attached deposit: e.g. 1 NEAR.
3. `inner_rlp_execute` returns `Err(...)` without creating a promise; `rlp_execute` returns `PromiseOrValue::Value(ExecuteResponse{success:false,...})`.
4. The receipt succeeds (no panic), so no protocol-level refund occurs; the 1 NEAR deposit remains permanently on `victim.near`'s account balance, never refunded to the caller and never used for the intended action.
