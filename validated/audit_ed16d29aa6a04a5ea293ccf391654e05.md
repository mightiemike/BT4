## Finding

Based on my research, the nearcore JSON-RPC server exposes a resource-exhaustion vulnerability analogous to CVE-2018-1274: the HTTP layer only bounds request *size* (10 MiB), not JSON nesting *depth*, before handing the body to a fully recursive, non-tail-call `serde_json::Value` deserializer.

### Title
Unbounded JSON nesting depth in the JSON-RPC request parser allows an unauthenticated stack-overflow denial of service - (File: chain/jsonrpc/src/lib.rs)

### Summary
The `/` JSON-RPC endpoint deserializes every incoming HTTP body directly into `near_jsonrpc_primitives::message::Message`, whose `params`/`result`/`id` fields are typed as `serde_json::Value` [1](#0-0) . The only protection applied before parsing is a body-size limit (`RequestBodyLimitLayer`, default 10 MiB) and CORS — there is no JSON nesting-depth limit [2](#0-1) . `rpc_handler()` uses Axum's `Json<Message>` extractor, which internally calls `serde_json`'s recursive-descent parser to build the `Value` tree [3](#0-2) .

### Finding Description
`serde_json::Value`'s deserializer recurses once per level of array/object nesting with no built-in recursion-depth cap. An attacker can send a POST body such as `{"jsonrpc":"2.0","method":"x","params":[[[[...]]]]],"id":1}` with millions of nested `[` characters — trivially fitting under the 10 MiB body limit (each nesting level costs only 1 byte) — and drive the parser's call stack far beyond the default thread stack size before any application-level validation (`process()`, `process_request()`, method routing, gas/fee accounting) is ever reached. This mirrors the Spring Data Commons property-path-parser bug class: unauthenticated, unbounded resource consumption purely from parsing untrusted input, with no cost accounting gating the work (nearcore's gas metering, which bounds all *runtime* execution paths, never comes into play here because the crash happens during HTTP/JSON parsing, before any transaction or view-call logic executes).

Unlike a catchable panic, a Rust stack overflow triggers the process's guard page and typically aborts the entire process (SIGSEGV/SIGABRT), not just the offending async task. Because the JSON-RPC server runs in the same process as `ClientActor`/`ViewClientActor`/`RpcHandlerActor` (block production, chunk production, transaction processing, etc.) [4](#0-3) , a stack overflow triggered by one crafted RPC request can take down the whole node, not merely the RPC listener.

### Impact Explanation
Any anonymous RPC caller can crash a validator or RPC node with a single HTTP request, with no signed transaction, no gas payment, and no prior authentication. If exploited broadly against RPC-serving validators, this can halt block production/finality for the affected nodes — a transaction/RPC-triggered halt, which is explicitly in-scope per the validation criteria.

### Likelihood Explanation
High. The request requires no special privileges — just network access to the public JSON-RPC port (default 3030) that every nearcore node exposes. The payload is trivial to construct (repeated single-byte bracket characters) and fits comfortably within the existing 10 MiB body-size limit, so no other mitigation currently blocks it.

### Recommendation
Add an explicit JSON nesting-depth limit before/during deserialization of RPC bodies (e.g., reject requests whose JSON exceeds a small fixed depth, or parse with a depth-limited/streaming JSON parser instead of unguarded `serde_json::Value`), independent of the existing byte-size limit. Alternatively, run body deserialization on a dedicated thread/task with a guarded, limited stack so an overflow only kills that task instead of the whole process, and add a regression test that POSTs deeply nested JSON and asserts the server remains responsive.

### Proof of Concept
```
POST / HTTP/1.1
Host: <node>:3030
Content-Type: application/json
Content-Length: <~9MB>

{"jsonrpc":"2.0","method":"status","params":[[[[[[[[[[ ... (millions of nested '[' ) ... ]]]]]]]]]]],"id":1}
```
Sending this (well under the 10 MiB `RequestBodyLimitLayer` cap) to the `/` endpoint causes `axum`'s `Json<Message>` extractor to recurse through `serde_json`'s `Value` visitor far beyond the worker thread's stack, aborting the process before `JsonRpcHandler::process()` [3](#0-2)  is ever invoked.
