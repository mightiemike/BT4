### Title
Missing re-validation of shadow-parent block-commit consistency at block-processing time allows a transient staging-time gap to become a permanent chain divergence - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`validate_shadow_parent_burnchain` only checks block-commit/shadow-parent consistency (`block_commit.parent_vtxindex`/`parent_block_ptr`) when the parent header is already present in `staging_db`; if the parent header is not yet known it silently returns `Ok(())` [1](#0-0) . This check is invoked once, at block-acceptance time inside `validate_normal_nakamoto_block_burnchain`/`accept_block` [2](#0-1) , but is never re-run when the block is later actually appended to the chain in `append_block`/`process_next_nakamoto_block`, which only re-fetches the parent's *processed* header for continuity checks, not the shadow-parent/block-commit consistency check [3](#0-2) .

### Finding Description
The broken equality is: *"decision to accept block B whose parent is a shadow block S" on node A at time T1 (parent header for S absent from A's staging_db) must equal "decision to accept the same block B" on node A at time T2 (parent header for S now present)*. Because the consistency check is gated behind a one-shot `Ok(())` early return when the parent header lookup misses [4](#0-3) , and because that check is never repeated at processing time, this equality can be broken.

Concretely:
- `validate_shadow_parent_burnchain(staging_db, ...)` looks up `block.header.parent_block_id` in `staging_db`. If not found, it returns `Ok(())` unconditionally, treating the parent as "not a shadow block" (this is by design for legacy epoch2 parents, per the comment "the parent can be a (non-shadow) epoch2 block not present in the staging chainstate") [5](#0-4) .
- If instead the parent header *is* found and is a shadow block, the function enforces `block_commit.parent_vtxindex == 0` and `block_commit.parent_block_ptr == parent_sn.block_height`, returning `Err(InvalidStacksBlock)` on mismatch [6](#0-5) .
- This check runs exactly once, inside `validate_normal_nakamoto_block_burnchain`, which is called from `accept_block` (staging path) and from `postblock_proposal::validate` (miner-signing path) [7](#0-6) .
- Once staged, the block is later dequeued and appended via `append_block`, reached through `process_next_nakamoto_block`. That routine re-fetches the parent header from the **processed headers table** (not `staging_db`) purely to check chain continuity and length [3](#0-2) , and `append_block` itself performs burn-total, VRF, and tenure checks but does **not** call `validate_shadow_parent_burnchain` again [8](#0-7) .

Root cause: the shadow-parent consistency check is treated as a pure "staging gate" rather than a chain-processing invariant, and its correctness depends on transient local DB state (whether the parent header happens to already be known) at the moment of first receipt, with no re-check before the block is durably appended to the chainstate.

### Impact Explanation
If a malicious block B (block-commit's `parent_vtxindex`/`parent_block_ptr` inconsistent with its true shadow parent S) reaches Node A before S's header is locally known, Node A stages B successfully (validator short-circuits to `Ok(())`). Node A can only append/process B once S is processed and in the headers table, but at that point the (now-detectable) mismatch is never re-checked, so B is appended into A's canonical chain. Node B, which already had S's header before B arrived, correctly rejects B at staging time via the same function and never stores or processes it. This produces two honest, fully-synced nodes with divergent canonical tips over the same underlying data — a fork rooted in a block that should be uniformly invalid. If further blocks are built/relayed on top of B, this becomes a deep fork requiring reorg, matching the "Critical - chain split / deep fork" impact category.

### Likelihood Explanation
Preconditions: a shadow-block-enabled chain, and a P2P/relay path where block B can be delivered to a node before that node's staging DB has ingested the shadow parent's header — plausible under normal asynchronous network delivery/reordering, and exploitable by strategically pushing B directly to a target node before it (through however it obtains shadow blocks) records S locally. No majority stake is needed; a single miner-slot/block-commit attacker can craft the mismatched block-commit and control delivery timing to at least one honest node. This is repeatable per shadow-block tenure transition.

### Recommendation
Re-run `validate_shadow_parent_burnchain` (or an equivalent check against the now-processed parent header) inside `append_block`/`process_next_nakamoto_block` immediately after the parent header is confirmed to exist, before the block is durably appended, so that no block can be committed to the canonical chain based on a stale/absent-parent validation result. Alternatively, defer/reject staging of any block whose parent header cannot yet be classified as shadow-or-not, rather than defaulting to `Ok(())`.

### Proof of Concept
Rust integration test plan (two-node harness):
1. Construct a chain with shadow-block support enabled; produce shadow block `S` and a subsequent Nakamoto block `B` whose block-commit has `parent_vtxindex = 1` (inconsistent with the required `0` for a shadow parent).
2. Node A: call `accept_block` for `B` while `S`'s header is absent from `staging_db` — assert `Ok(())`/`true` (block staged).
3. Node B: insert `S`'s header into `staging_db` first, then call `accept_block` for `B` — assert `Err(ChainstateError::InvalidStacksBlock(_))`.
4. On Node A, now insert/process `S`, then drive `process_next_nakamoto_block` until `B` is appended — assert that `B` becomes part of Node A's canonical chain (`get_block_header` returns `Some` and stacks tip advances past `B`).
5. Assert the equality violation: Node A's final verdict for `B` (`accepted+processed`) differs from Node B's (`rejected`), with no retroactive invalidation mechanism firing on Node A after `S` becomes known.
