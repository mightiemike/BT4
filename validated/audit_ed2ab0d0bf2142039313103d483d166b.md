### Title
Missing enforcement of DKG voting-window guard lets a minority signer finalize/extend the aggregate-key vote outside its mandated window - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
`signers-voting.clar` defines a private guard, `is-in-voting-window`, whose stated purpose is to restrict votes for a reward cycle's WSTS aggregate public key to the prepare-phase window immediately following the node's `set-signers` call for that cycle. This guard is never invoked anywhere in the contract — it is dead code, exactly analogous to a `whenNotPaused` modifier that is defined but never attached to the state-mutating entry point.

### Finding Description
`vote-for-aggregate-public-key` is the sole public, state-mutating entry point that records votes, advances DKG rounds, and can finalize (`map-insert`) the approved aggregate public key for a reward cycle: [1](#0-0) 

Its doc-comment states the intended invariant explicitly: *"This vote must happen after the list of signers has been set by the node, which occurs in the first block of the prepare phase."* The helper meant to enforce exactly this is: [2](#0-1) 

`ERR_OUT_OF_VOTING_WINDOW` (`u12`) is declared for this purpose, but the only place it is actually returned is an unrelated check that the key for the reward cycle hasn't been set yet: [3](#0-2) 

A repo-wide search confirms `is-in-voting-window` is referenced nowhere else — it is defined and never called. The asserts present in `vote-for-aggregate-public-key` check: (1) the key isn't already approved, (2) key length, (3) key novelty across cycles, (4) no duplicate vote by the same signer/round, and (5) round increments by at most 1 — none of these check that `burn-block-height` is within the prepare phase, nor that `reward-cycle` equals the node's `last-set-cycle`.

Before/after comparison of the equality the guard is supposed to enforce:
- Intended invariant: `approved-aggregate-key[rc]` is only derived from votes cast while `is-in-voting-window(height, rc) == true`.
- Actual behavior: `approved-aggregate-key[rc]` can be derived from votes cast at **any** block height, for as long as `(map-get? aggregate-public-keys rc)` is `none`, i.e. for the entire remaining lifetime of the contract if the round never crosses `threshold-weight`.

### Impact Explanation
Any single signer who is a member of the reward-cycle's signer set (an unprivileged, minority actor — no majority coordination required) can submit `vote-for-aggregate-public-key` transactions long after the prepare-phase window that legitimate signer software and miner tooling assume voting is closed for. Because `get-and-cache-total-weight` caches the denominator on first read and `update-last-round` only bounds the round number's *increment* (not its timing), a straggling or adversarial signer can keep the round open and eventually push a candidate key past `threshold-weight` at a time other honest participants — who follow the documented prepare-phase protocol and stop tracking/voting after it closes — no longer expect state changes to occur. This produces an approved aggregate public key that the rest of the signer/miner software did not agree would be finalized at that time, a High-severity "validation verdict two nodes disagree on"/timing-divergence class result bounded to the signer-boot-contract subsystem, without requiring a majority of signers or any privileged role.

### Likelihood Explanation
High likelihood of triggerability: it requires only a normal signer-set member (index + reward cycle they legitimately belong to) submitting an otherwise well-formed transaction; no majority collusion, no node operator, and no extra privilege is needed. The only preconditions are that the target reward cycle's aggregate key has not yet been finalized and that the round hasn't already advanced by more than 1.

### Recommendation
Add the missing check to `vote-for-aggregate-public-key`, e.g.:
```clarity
(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))
```
placed alongside the other `asserts!` guards, so that votes (and therefore round advancement and key approval) are only accepted while the reward cycle is the most-recently-set cycle and the chain tip is within its prepare phase, matching the documented protocol and the already-declared `ERR_OUT_OF_VOTING_WINDOW` error code's evident intent.

### Proof of Concept
1. Node sets signers for reward cycle `N` at the first block of cycle `N-1`'s prepare phase (`.signers::set-signers`), making `last-set-cycle == N`.
2. The prepare-phase window for cycle `N` ends; honest signer software (per the documented protocol) stops issuing/expecting `vote-for-aggregate-public-key` calls for cycle `N`.
3. A single signer (any member with nonzero weight in cycle `N`'s signer set) who did not reach threshold during the window continues submitting `vote-for-aggregate-public-key` calls for `reward-cycle = N` at arbitrary later block heights (even after cycle `N` has begun).
4. Because `vote-for-aggregate-public-key` never calls `is-in-voting-window`, none of the five existing `asserts!` reject these late calls (the key for cycle `N` is still `none`, the key is well-formed/novel, this signer hasn't voted in this exact round yet, and the round increments legally).
5. If/when the accumulated `new-total` for a candidate key crosses `get-threshold-weight`, `map-insert aggregate-public-keys reward-cycle key` finalizes the key — outside the window the rest of the protocol assumed voting was restricted to, confirming the missing-guard root cause.

    (let ((last-cycle (unwrap-panic (contract-call? .signers get-last-set-cycle))))
        (and (is-eq last-cycle reward-cycle)
            (is-in-prepare-phase height))))

                )
        ;; Check that the key has not yet been set for this reward cycle
        (asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))
