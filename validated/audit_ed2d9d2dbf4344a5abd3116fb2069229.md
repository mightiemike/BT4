### Title
Missing zero-address validation in `AccountPermissionUpdateActuator` permits an account to permanently lock its own owner/active permission - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator`, which processes the unprivileged, user-broadcast `AccountPermissionUpdateContract`, validates permission keys only through `DecodeUtil.addressValid`, which checks length/prefix but never rejects the all-zero ("null") address. A user can set the `Owner` permission's key(s) to the null address (or to any address they do not control), permanently and irrecoverably losing control of the account's owner role, directly mirroring the Trail-of-Bits UniswapV3Factory finding where missing `_owner`/`address(0)` validation can permanently lock the owner role.

### Finding Description
`checkPermission()` in `AccountPermissionUpdateActuator` validates key count, threshold, weight sums, and calls `DecodeUtil.addressValid()` per key [2](#0-1) . `addressValid` merely confirms the byte array is 21 bytes and starts with the correct network prefix byte [1](#0-0) ; a value such as `41` followed by 20 zero bytes passes this check even though it is not a real, controllable account key. The `validate()` method requires an `Owner` permission to be present [3](#0-2) , but nothing prevents that `Owner` permission's key(s) from pointing at the zero address or any address whose private key the caller does not hold. Once executed, the account's owner permission (and, by the same path, active/witness permissions) is overwritten with this unusable key set, and there is no recovery function, no two-step ownership transfer, and no `renounceOwnership`-style guard — exactly the class of bug described in the Uniswap report.

Notably, `Manager.resetBlackholeAccountPermission()` explicitly constructs a permission whose key is the all-zero address (`byte[21]` with only the prefix byte set) and assigns it as the owner permission of the blackhole account [4](#0-3) , confirming that the zero address is treated internally as a valid, deliberately-unusable/"burn" key — the very trap an ordinary user can now fall into unintentionally (or be tricked into) via `AccountPermissionUpdateContract`.

### Impact Explanation
If an account's `Owner` permission keys are set to the zero address or an uncontrolled address, that account can never again submit an owner-permission-gated transaction (including any subsequent `AccountPermissionUpdateContract` to fix the mistake, since that operation itself requires owner-permission signatures). All value, delegated resources, votes, and any smart-contract ownership tied to that account's owner permission become permanently frozen — a direct funds/asset-accounting lockup analogous to the Uniswap factory redeploy scenario. This is a real, unrecoverable DoS against the affected account's own funds and role, reachable purely through a normal broadcast transaction.

### Likelihood Explanation
Likelihood is moderate: this requires either user error (mistakenly supplying an all-zero or wrong key when constructing the JSON/protobuf payload for `AccountPermissionUpdateContract`, e.g. via a buggy wallet/dApp integration) or a malicious front-end/dApp tricking a user into signing such a transaction. Given multisig/permission management UIs assemble raw key/address fields and the actuator performs no "is-zero" or "is-a-real-account" check, the mistake is plausible, especially since the codebase itself treats the all-zero address as a legitimate permission key for the blackhole account, suggesting no developer safeguard exists against it being reused by regular accounts.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly reject the all-zero address (and any other well-known non-recoverable sentinel address) as a permission key, and/or add safeguards analogous to Trail-of-Bits' recommendation: verify that owner-permission keys correspond to accounts capable of signing, and consider a mandatory "confirm-in-second-transaction" step for lowering/replacing the entire owner-permission key set to reduce catastrophic one-shot lockouts. At minimum, add:
```java
if (Arrays.equals(key.getAddress().toByteArray(), new byte[]{DecodeUtil.addressPreFixByte, 0,0,...,0})) {
  throw new ContractValidateException("key must not be the zero address");
}
```

### Proof of Concept
1. Attacker/careless user crafts an `AccountPermissionUpdateContract` for their own account with `owner.keys[0].address` = the network prefix byte followed by 20 zero bytes, weight ≥ threshold.
2. Broadcasts it; `AccountPermissionUpdateActuator.validate()` passes `checkPermission(owner)` because `DecodeUtil.addressValid` only checks length/prefix [5](#0-4) .
3. `execute()` writes this owner permission into the account's `AccountCapsule`, permanently replacing the previous, controllable owner key.
4. The account can never construct a validly-signed owner-permission transaction again (no private key exists for the zero address), permanently locking any owner-gated capability of that account, mirroring the Uniswap `_owner` lockup scenario.

      return false;

    }
    return true;
  }
