### Title
DeleteAccountAction sends the account's entire balance to an unvalidated `beneficiary_id`, causing permanent, silent loss of funds if the target account does not exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
The GranularRoles report is about a one-step, irrevocable ownership handoff (`transferOwnership`) that permanently destroys access if the caller supplies a bad target address, with no acceptance/verification step. The closest reachable analog in nearcore is `action_delete_account`, which unconditionally routes the account's whole balance to `delete_account.beneficiary_id` via a refund receipt, without ever checking that the beneficiary account exists or can receive it, and with no two-step or "accept" mechanism.

### Finding Description
`action_delete_account` reads the account's current balance and, if positive, immediately queues a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`, then deletes the account and clears its state in the same step: [1](#0-0) 

The only validation performed on `beneficiary_id` anywhere in the action pipeline is that it is a syntactically valid `AccountId` string (per `docs/RuntimeSpec/Actions.md`): [2](#0-1) 

There is no check that the beneficiary account actually exists, nor any two-phase "propose beneficiary / accept transfer" flow. This mirrors the `GranularRoles.transferOwnership` pattern exactly: a single signed action performs an irreversible state transition to an attacker- or user-supplied identifier that is never validated for reachability.

Per the documented action-receipt execution model, refund receipts (predecessor is the system account) are treated specially: they are free (no gas refund generated), and if a refund receipt fails to apply (e.g., because the named beneficiary account does not exist and a plain `Transfer` cannot create a non-implicit named account), its deposit is burned into `other_burnt_amount` rather than returned to anyone: [3](#0-2) 

So a `DeleteAccountAction` with a beneficiary that is a syntactically-valid but non-existent, non-implicit `AccountId` (e.g. a typo'd named account, or one that was never registered) results in the entire account balance being irrecoverably destroyed instead of transferred - the funds go nowhere and cannot be recovered by anyone, not even the original owner.

### Impact Explanation
Any account holder who submits `DeleteAccountAction` with a mistyped or non-existent `beneficiary_id` permanently loses their entire account balance with no recovery path — this is a direct "permanently frozen/lost funds" outcome from a single unprivileged transaction, matching the report's "owner permanently lost, financial loss" impact category. Because the check for `beneficiary_id` validity is purely syntactic (`InvalidAccountId` for malformed strings) and not existence-based, the runtime happily accepts and executes destructive transactions that irreversibly burn value, exactly the "no two-step / no validation before an irrevocable transfer" bug class from the report.

### Likelihood Explanation
This requires only a single, ordinary `DeleteAccountAction` from any full-access-key holder — no special privilege, no cross-shard timing, no malicious peer or validator involvement. The only precondition is a user error (typo, copy-paste mistake, or referencing an account that hasn't been created yet), which is a common and realistic occurrence, especially for relayer/automation tooling constructing `beneficiary_id` programmatically.

### Recommendation
Before queuing the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` refers to an existing account (or is a valid implicit-account id capable of being created by a plain transfer), and reject the action with a clear `ActionError` otherwise. Alternatively, document and/or enforce this at validation time (mirroring `InvalidAccountId`) so that RPC/wallet clients can pre-flight-check beneficiary existence and warn users, preventing accidental permanent fund loss.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance and a full-access key.
2. Submit `SignedTransaction` from `alice.near` to itself containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent-account.near".parse().unwrap() })`, where `nonexistent-account.near` is a syntactically valid but never-created named account.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) removes `alice.near` and queues `Receipt::new_balance_refund("nonexistent-account.near", account_balance)`.
4. When the refund receipt is applied against `nonexistent-account.near`, the receiver account does not exist and a plain `Transfer` cannot create a non-implicit named account, so the refund receipt fails; per the documented refund-failure handling, its deposit is burned into `other_burnt_amount` instead of being restored to `alice.near` or delivered to any beneficiary.
5. Result: `alice.near`'s entire balance is irrecoverably destroyed — no account holds it, and there is no path to reverse the transaction.
