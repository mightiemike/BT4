### Title
Static `MarketSellFee` does not scale with order-matching work, underpricing the network cost of market order execution - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.calcFee()` charges a single flat, statically-configured fee (`dynamicStore.getMarketSellFee()`) for every `MarketSellAssetContract`, regardless of how much on-chain work the transaction actually triggers via `matchOrder()`, which can iterate and settle up to `MAX_MATCH_NUM` (20) maker orders. This mirrors the GMX finding: a static gas/fee estimate that ignores variable, execution-dependent work performed later in the same call (there: token swaps at the end of withdrawal execution; here: the order-matching loop at the end of order creation).

### Finding Description
`calcFee()` is defined as: [1](#0-0) 

This fee is charged unconditionally in `execute()` before the variable-cost matching logic runs: [2](#0-1) 

The subsequent `matchOrder()` call can walk multiple price levels and, within each price level, multiple maker orders, executing store reads/writes (`orderStore.put`, `pairPriceToOrderStore` updates, `accountStore` balance/asset adjustments) for **each** matched order, up to `MAX_MATCH_NUM = 20` matches: [3](#0-2) 

Each match performs non-trivial state mutation via `matchSingleOrder()` (balance/asset transfers for both taker and maker, order-state updates, and order-detail construction), which is executed once per matched maker order: [4](#0-3) 

Unlike smart-contract execution (which is metered by TVM `energy`, e.g. via `VMActuator`/`VM.play`), `MarketSellAssetContract` is not an energy-metered contract type — it only pays bandwidth for its raw transaction size plus the flat `calcFee()`. There is no per-match or per-iteration fee component anywhere in `calcFee()`, `validate()`, or `execute()` — `MAX_MATCH_NUM` only bounds the worst case, it does not scale the price charged. This is structurally identical to the GMX bug: a static fee formula is used to price a call whose actual cost is driven by a variable-length, data-dependent loop (token swaps in GMX; order matching in java-tron) that is not reflected in the fee.

### Impact Explanation
Because the fee is fixed irrespective of the number of matches, a user submitting a `MarketSellAssetContract` that triggers a full 20-order match pays exactly the same fee as a user whose order matches nothing. The chain (validating Super Representatives/witnesses) must nonetheless execute up to 20 iterations of store reads/writes and balance/asset accounting logic for the same flat price. This is an underpriced-public-work condition: the resource cost imposed on the network by processing/settling matched orders scales with market depth and is not compensated, allowing users to cheaply trigger disproportionately expensive state work (creating a rational incentive to build order books to specifically to enable this asymmetry, and a moderate load-based vector to make block processing costlier than compensated for).

### Likelihood Explanation
This path is reachable by any unprivileged account with a valid `MarketSellAssetContract`, requires no special privileges, and depends only on the existing order book depth, which the caller can also independently construct by placing multiple small maker orders beforehand (self-funded), then submitting a taker order that matches all of them in one transaction. This makes the underpricing both easy to trigger and directly reachable via a standard public actuator (`MarketSellAssetActuator.execute()`/`validate()`).

### Recommendation
Scale `calcFee()` (or add a separate resource charge) to the actual number of matched orders/price levels touched during `matchOrder()`, analogous to how `GasUtils.estimateExecuteDepositGasLimit` was fixed to incorporate swap steps. For example, charge an incremental fee per matched maker order (tracked via `matchOrderCount` in `matchOrder()`), validated in `execute()`/`validate()`, so the fee scales with `MAX_MATCH_NUM` in the worst case rather than remaining flat.

### Proof of Concept
1. Attacker creates ~20 small maker `MarketSellAssetContract` orders for a token pair (self-funded, cheap, each paying the flat sell fee for order creation only, without triggering any matches).
2. Attacker then submits one taker `MarketSellAssetContract` order sized to match all 20 resting orders in a single call to `matchOrder()`.
3. `calcFee()` returns the same static `getMarketSellFee()` value as would be charged for an order that matches zero orders — [1](#0-0) .
4. The network executes 20 iterations of `matchSingleOrder()` (balance updates, asset transfers, order removal/store writes) for the price of one — [5](#0-4) , demonstrating the fee is decoupled from the actual on-chain work performed, exactly analogous to the GMX underestimated-withdrawal-gas issue.

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0

        // remove order
        if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) {
          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
