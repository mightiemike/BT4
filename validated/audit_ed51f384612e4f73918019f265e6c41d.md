### Title
Leader ingress prefilter admits already-processed transactions into the banking-stage buffer and the consume path never re-checks the status cache before execution, enabling double execution of a committed transaction - (File: `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs`, `runtime/src/bank/check_transactions.rs`, `core/src/banking_stage/consumer.rs`)

### Summary
`precheck_transaction` (ingress) calls `Bank::check_transaction_without_status_cache`, which by design skips `BankStatusCache`, so a duplicate packet for an already-committed signature is admitted into the `TransactionViewStateContainer` instead of being dropped. The internal-scheduler execution path used by `ConsumeWorker` (`Consumer::process_and_record_aged_transactions`) only resanitizes for epoch/ALT expiry (`Bank::resanitize_transaction_minimally`) and never calls `Bank::check_transactions`/`check_status_cache` before locking accounts and calling `Bank::load_and_execute_transactions`, unlike the full `Consumer::process_and_record_transactions` path which does perform that check.

### Finding Description
The banking-stage ingress fast path is:

`TransactionViewReceiveAndBuffer::process_packet_batch` → check-worker → `precheck_transaction` (`core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs:65-116`), which calls: [1](#0-0) 

`Bank::check_transaction_without_status_cache` is explicitly documented as a "leader-only function" that skips the status cache and only checks transaction age: [2](#0-1) 

This is confirmed by an existing unit test showing that an already-processed transaction (inserted into `status_cache`) is rejected by `check_transactions` (status-cache path) but accepted (`Ok(None)`) by `check_transaction_without_status_cache`: [3](#0-2) 

Consequently, a committed transaction resubmitted as raw packet bytes is admitted into the scheduler's buffer, as directly demonstrated by the existing test `test_receive_and_buffer_buffers_already_processed`, which processes a transaction on the bank, then resends the identical packet and asserts `num_dropped_on_already_processed == 0` and `num_buffered == 1`: [4](#0-3) 

Once buffered, the transaction is dispatched to a `ConsumeWorker`, whose `consume` method calls `Consumer::process_and_record_aged_transactions`: [5](#0-4) 

That function's pre-results come only from `Bank::resanitize_transaction_minimally` (epoch/ALT expiry check) — not from `Bank::check_transactions` (which includes `check_status_cache`): [6](#0-5) 

This is in stark contrast to `Consumer::process_and_record_transactions` (used elsewhere, e.g. for votes/tests), which explicitly performs the full status-cache check via `bank.check_transactions(...)` before locking and executing: [7](#0-6) 

From there, `process_and_record_transactions_with_pre_results` locks accounts and calls `bank.load_and_execute_transactions` directly with whatever `pre_results` it received, with no additional status-cache gate: [8](#0-7) [9](#0-8) 

I was not able to fully inspect `Bank::resanitize_transaction_minimally` or the internals of `Bank::load_and_execute_transactions`/SVM account loader within the tool-call budget of this session to conclusively rule out a redundant status-cache check deeper in the SVM pipeline. Based on the code read, `resanitize_transaction_minimally` is documented/used solely for epoch and ALT-invalidation checks (consistent with the `MaxAge{ sanitized_epoch, alt_invalidation_slot }` struct built at ingress in `receive_and_buffer.rs`), and the SVM `CheckedTransactionDetails` produced by `check_age_and_compute_budget_limits` conventionally trusts the caller to have already excluded `AlreadyProcessed` — but I could not directly confirm the absence of a fallback check in `load_and_execute_transactions` itself. This should be verified before treating the impact as fully proven.

### Impact Explanation
If confirmed, this allows a transaction that already executed and moved funds in a previous slot to be re-admitted and re-executed by the same leader in a later block within `max_processing_age`, i.e. a double-spend / replay of a signed transfer — a direct funds-safety violation (double-spend/replay bounty category). The `test_receive_and_buffer_buffers_already_processed` test itself demonstrates the intake side of the bug (already-committed tx is buffered rather than dropped as `AlreadyProcessed`); the remaining open question is whether the downstream consume path (as traced) or a lower SVM layer ultimately blocks re-execution.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: an ordinary funded keypair sends a transaction, waits for on-chain commitment, then immediately resends the identical raw packet to the same leader's TPU while the transaction's blockhash is still within `max_processing_age`. No validator/leader/network privileges are required. The window is bounded by leader rotation and buffer/consume timing, so it is not guaranteed on every attempt, but is repeatable across many committed transactions/leaders.

### Recommendation
Ensure the internal-scheduler consume path performs the same status-cache check as `Consumer::process_and_record_transactions` before locking/executing aged transactions — e.g., have `Consumer::process_and_record_aged_transactions` additionally call `Bank::check_transactions`/`check_status_cache` (or equivalent) on the working bank immediately prior to `execute_and_commit_transactions_locked`, so that `AlreadyProcessed` signatures are always rejected right before execution, regardless of what the leader-only ingress prefilter admitted.

### Proof of Concept
1. Extend `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs::test_receive_and_buffer_buffers_already_processed` (already shows admission) into a full integration test in `core/src/banking_stage/consumer.rs` or a `scheduler_controller` test:
   - Fund a keypair, submit and commit a transfer transaction on `bank` (slot N).
   - Resubmit the identical raw transaction bytes through `TransactionViewReceiveAndBuffer` into the container.
   - Advance to slot N+1 (still within `max_processing_age`), route the buffered transaction through the real `ConsumeWorker`/`SchedulerController` pipeline (not directly calling `process_and_record_transactions`) to `ConsumeWorker::consume`.
   - Assert: `commit_transactions_result` for the duplicate is `Err(TransactionError::AlreadyProcessed)` and `bank.get_balance(recipient)` reflects only one transfer, and only one `Executed`/committed entry with that signature exists in the block.
2. If the assertion fails (i.e., the duplicate is executed a second time and the balance changes twice), this confirms the double-execution bypass.

    /// Checks a sanitized transaction against the bank for age,
    /// without checking the status cache. This is a leader-only
    /// function and must not be used in replay without a feature gate.
    pub fn check_transaction_without_status_cache(
        &self,
        tx: &impl SVMMessage,
        max_age: usize,
        error_counters: &mut TransactionErrorMetrics,
    ) -> TransactionResult<Option<Pubkey>> {
        let feature_set: &FeatureSet = &self.feature_set;
        let feature_snapshot = feature_set.snapshot();
        let enable_tx_v1 = feature_snapshot.enable_tx_v1;

        if !enable_tx_v1 && tx.version() == TransactionVersion::Number(1) {
            return Err(TransactionError::UnsupportedVersion);
        }

        let hash_queue = self.blockhash_queue.read().unwrap();
        let next_durable_nonce = hash_queue.next_durable_nonce();

        self.check_transaction_age(
            tx,
            max_age,
            &next_durable_nonce,
            &hash_queue,
            error_counters,
            true, // strict_nonce_size_check
            true, // strict_nonce_authority_check
        )
    }

    fn consume(
        &self,
        work: ConsumeWork<Tx>,
    ) -> Result<ProcessingStatus<Tx>, ConsumeWorkerError<Tx>> {
        let Some(leader_state) = active_leader_state(&self.shared_leader_state) else {
            return Ok(ProcessingStatus::CouldNotProcess(work));
        };
        let bank = leader_state
            .working_bank()
            .expect("active_leader_state should only return an active bank");
        if bank.slot() != work.target_slot {
            return Ok(ProcessingStatus::CouldNotProcess(work));
        }
        self.metrics
            .count_metrics
            .num_messages_processed
            .fetch_add(1, Ordering::Relaxed);

        let output = self.consumer.process_and_record_aged_transactions(
            bank,
            &work.transactions,
            &work.max_ages,
            &ExecutionFlags {
                drop_on_failure: false,
                all_or_nothing: false,
            },
        );
        self.metrics.update_for_consume(&output);
        self.metrics.has_data.store(true, Ordering::Relaxed);

        self.consumed_sender.send(FinishedConsumeWork {
            work,
            retryable_indexes: output
                .execute_and_commit_transactions_output
                .retryable_transaction_indexes,
        })?;
        Ok(ProcessingStatus::Processed)
    }

    pub fn process_and_record_aged_transactions(
        &self,
        bank: &Bank,
        txs: &[impl TransactionWithMeta],
        max_ages: &[MaxAge],
        flags: &ExecutionFlags,
    ) -> ProcessTransactionBatchOutput {
        // Need to filter out transactions since they were sanitized earlier.
        // This means that the transaction may cross and epoch boundary (not allowed),
        //  or account lookup tables may have been closed.
        let pre_results = txs.iter().zip(max_ages).map(|(tx, max_age)| {
            bank.resanitize_transaction_minimally(
                tx,
                max_age.sanitized_epoch,
                max_age.alt_invalidation_slot,
            )
        });
        self.process_and_record_transactions_with_pre_results(bank, txs, pre_results, flags)
    }

    fn execute_and_commit_transactions_locked(
        &self,
        bank: &Bank,
        batch: &TransactionBatch<impl TransactionWithMeta>,
        flags: &ExecutionFlags,
    ) -> ExecuteAndCommitTransactionsOutput {
        let transaction_status_sender_enabled = self.committer.transaction_status_sender_enabled();
        let mut execute_and_commit_timings = LeaderExecuteAndCommitTimings::default();

        let mut error_counters = TransactionErrorMetrics::default();
        let mut retryable_transaction_indexes: Vec<_> = batch
            .lock_results()
            .iter()
            .enumerate()
            .filter_map(|(index, res)| match res {
                // following are retryable errors
                Err(TransactionError::AccountInUse) => {
                    error_counters.account_in_use += 1;
                    // locking failure due to vote conflict or jito - immediately retry.
                    Some(RetryableIndex {
                        index,
                        immediately_retryable: true,
                    })
                }
                Err(TransactionError::WouldExceedMaxBlockCostLimit) => {
                    error_counters.would_exceed_max_block_cost_limit += 1;
                    Some(RetryableIndex {
                        index,
                        immediately_retryable: false,
                    })
                }
                Err(TransactionError::WouldExceedMaxVoteCostLimit) => {
                    error_counters.would_exceed_max_vote_cost_limit += 1;
                    Some(RetryableIndex {
                        index,
                        immediately_retryable: false,
                    })
                }
                Err(TransactionError::WouldExceedMaxAccountCostLimit) => {
                    error_counters.would_exceed_max_account_cost_limit += 1;
                    Some(RetryableIndex {
                        index,
                        immediately_retryable: false,
                    })
                }
                Err(TransactionError::WouldExceedAccountDataBlockLimit) => {
                    error_counters.would_exceed_account_data_block_limit += 1;
                    Some(RetryableIndex {
                        index,
                        immediately_retryable: false,
                    })
                }
                // following are non-retryable errors
                Err(TransactionError::TooManyAccountLocks) => {
                    error_counters.too_many_account_locks += 1;
                    None
                }
                Err(_) => None,
                Ok(_) => None,
            })
            .collect();

        let (load_and_execute_transactions_output, load_execute_us) =
            measure_us!(bank.load_and_execute_transactions(
                batch,
                bank.max_processing_age(),
                &mut execute_and_commit_timings.execute_timings,
                &mut error_counters,
                TransactionProcessingConfig {
                    account_overrides: None,
                    log_messages_bytes_limit: self.log_messages_bytes_limit,
                    limit_to_load_programs: true,
                    recording_config: ExecutionRecordingConfig::new_single_setting(
                        transaction_status_sender_enabled
                    ),
                    drop_on_failure: flags.drop_on_failure,
                    all_or_nothing: flags.all_or_nothing,
                    strict_nonce_size_check: true,
                    drop_noop_transactions: true,
                }
            ));
