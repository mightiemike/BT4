### Title
Unbounded proof-generation loop before spend/receive count validation in `transfer` builder - ([File: framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java])

### Finding Description
In the `TRANSFER` branch of `build(boolean withAsk)`, the code iterates unconditionally over the full `spends` and `receives` lists, calling `generateSpendProof`/`generateOutputProof` for every entry before any bound check is applied: [1](#0-0) 

Each `generateSpendProof` call allocates 192/32-byte buffers and invokes the native zk-SNARK proving routine `JLibrustzcash.librustzcashSaplingSpendProof`, and each `generateOutputProof` similarly invokes `librustzcashSaplingOutputProof`: [2](#0-1) [3](#0-2) 

The only place the `spendCount < 1 || spendCount > 2` bound is enforced is inside `transferParamsToHexString`, which is called from `getTriggerContractInput` only after `builder.build()` has already completed and all spend/receive proofs for every supplied entry have been generated: [4](#0-3) [5](#0-4) 

This builder is reached from an unauthenticated HTTP endpoint `CreateShieldedContractParametersServlet.doPost`, which merges the raw JSON request body into a `PrivateShieldedTRC20Parameters` protobuf and forwards it to `wallet.createShieldedContractParameters(...)`: [6](#0-5) 

The only size guard visible at the servlet layer is `Util.checkBodySize(contract)`, a generic total-request-size limit, not a per-array element count check. I was unable to verify (due to reaching the tool-call limit) whether `Wallet.createShieldedContractParameters` performs an explicit `spends.size()`/`receives.size()` bound check before populating the builder and calling `build()`. If it does not — which is plausible since the count validation logic clearly lives inside `transferParamsToHexString`, i.e., after-the-fact — then an attacker-supplied JSON body with many `shielded_spends`/`shielded_receives` entries will cause the server to perform one expensive native zk-SNARK proof computation per entry before any rejection occurs.

### Impact Explanation
If no earlier bound check exists in `Wallet.java`, an unprivileged HTTP client can submit an oversized `shielded_spends`/`shielded_receives` array in a `transfer`-type request to `/wallet/createshieldedcontractparameters`, forcing the RPC handler thread to perform N native zk-SNARK proof generations (each computationally expensive) before the `spendCount > 2` check ever fires. This matches a DoS-via-RPC-API impact class: sustained CPU/memory consumption on the full node serving RPC requests, degrading node responsiveness for other RPC callers.

### Likelihood Explanation
I could not confirm this is exploitable end-to-end because the request-body size limit (`Util.checkBodySize`) and any array-size validation inside `Wallet.createShieldedContractParameters` were not verified within my available searches. The vulnerability, as written in `ShieldedTRC20ParametersBuilder.build()`/`transferParamsToHexString` alone, clearly places the bound check after the expensive work, but whether that code path is actually reachable with an oversized array depends on unverified upstream validation in `Wallet.java`.

### Recommendation
Move the `spendCount`/`recvCount` bound checks (`spends.size() < 1 || spends.size() > 2`, and equivalent for `receives`) to the very start of the `TRANSFER` case in `build()`, before entering the proof-generation loops, and equivalently validate list sizes as early as possible in `Wallet.createShieldedContractParameters` right after deserializing the request, rejecting oversized requests before any native proving calls are invoked.

### Proof of Concept
Could not be fully constructed/verified: a definitive PoC requires confirming the absence of a pre-existing size check in `Wallet.createShieldedContractParameters`, which I was unable to inspect before exhausting my tool budget. A reproducible test would need to call `wallet.createShieldedContractParameters` (or POST to `/wallet/createshieldedcontractparameters`) with a `transfer`-type `PrivateShieldedTRC20Parameters` containing e.g. 1000 `shielded_spends` entries and measure whether `generateSpendProof` is invoked 1000 times (via instrumentation/logging) prior to the `IllegalArgumentException("invalid transfer input number")` being thrown in `transferParamsToHexString`.
