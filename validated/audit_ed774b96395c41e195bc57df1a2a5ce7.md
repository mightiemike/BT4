### Title
Malformed `host` Query Parameter Causes Unhandled Exception (DoS) in `sanitizeHost` — ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
The Solidity report describes a corner case where an unguarded arithmetic condition (`mark == lowerBound` and `period >= 346279`) makes a critical validation function revert unexpectedly instead of failing gracefully, blocking the `Controller` contract. The direct analog in `shopify-app-js` is in `sanitizeHost`, a security-critical input-validation function used throughout the OAuth/embedded-app authentication flow: its regex check for the `host` query parameter does not enforce a corner-case invariant required by the underlying decoder (`atob`), so a crafted-but-regex-valid `host` value causes an uncaught native exception instead of the intended `InvalidHostError`.

### Finding Description
`sanitizeHost` validates the `host` parameter with:
```ts
const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
  ...
``` [1](#0-0) 

`decodeHost` is a thin wrapper around the native `atob`: [2](#0-1) 

The regex `^[0-9a-zA-Z+/]+={0,2}$` only checks the *character set* of the base64 payload; it does not check that the (unpadded) length is a multiple of 4 minus {0,1,2} valid remainders (i.e., that total length % 4 != 1). Per the WHATWG forgiving-base64 algorithm implemented by `atob`, a payload whose length modulo 4 equals 1 (e.g., `host=A`) throws a native `InvalidCharacterError`/`DOMException` rather than returning a decoded string. Because this call happens unconditionally inside `sanitizeHost` with no `try/catch`, the exception propagates out of `sanitizeHost` itself — bypassing the intended `throwOnInvalid` → `InvalidHostError` contract — as an unexpected, uncaught error type.

`sanitizeHost` is invoked directly from unauthenticated, attacker-controlled query parameters at several points in the authentication pipeline, with no surrounding `try/catch`:
- `validateShopAndHostParams`, executed at the very start of admin authentication for every embedded-app request: [3](#0-2) 
- `redirectWithExitIframe`: [4](#0-3) 
- `redirectToShopifyOrAppRoot` (remix and react-router variants): [5](#0-4) [6](#0-5) 
- `getEmbeddedAppUrl` / `buildEmbeddedAppUrl`: [7](#0-6) 
- Express `redirectToAuth` / `redirectToShopifyOrAppRoot` middleware: [8](#0-7) [9](#0-8) 

This exactly mirrors the reported bug class: an input-validation function is expected to guard against a specific corner case (base64 length) before performing an operation that can otherwise fail (decode/arithmetic), but the guard is incomplete, so a crafted request that passes the coarse check still reaches the failing operation and throws unexpectedly instead of returning the documented, gracefully-handled error.

### Impact Explanation
Any of these entry points are reachable by a fully anonymous HTTP request that merely supplies a crafted `host` query-string value (e.g., `host=A`, or any base64-charset string whose length % 4 == 1). This causes `sanitizeHost` to throw an uncaught `DOMException`/`InvalidCharacterError` instead of the expected `InvalidHostError`. Depending on the calling framework's error handling:
- In Express middlewares that are synchronous (`redirectToShopifyOrAppRoot`, `redirectToAuth`), an uncaught throw is not passed to Express's `next(err)` error chain automatically for all versions/configurations, and can surface as an unhandled exception rather than the documented 500/400 flow, defeating the app's intended error handling for the auth flow.
- The core `sanitizeHost` utility is documented and relied upon by app authors as the primary safe way to validate the `host` param before feature use (see `docs/reference/utils/sanitizeHost.md`); its silently different failure mode (an unexpected exception type, uncatchable via the library's own `InvalidHostError` type) can break app-level error handling and, in poorly-configured setups (e.g., background workers, non-Express adapters without global exception handling around sync code), lead to process-level failures for that request — a denial-of-service of the authentication entry point that the report's rules classify as valid impact.

This is not a full-tenant compromise, but is a legitimate availability issue in an authentication-adjacent input-validation routine reachable from a single anonymous request, matching the "DoS of an auth handler" acceptance criterion.

### Likelihood Explanation
High. The trigger requires no authentication, no secrets, and no special conditions — only a single crafted query string value satisfying the character-class regex but violating base64 padding-length invariants (`host` length % 4 == 1). This is trivially producible by any anonymous client hitting the app's OAuth begin/callback, `exitIframe`, or admin authentication endpoints.

### Recommendation
- Strengthen the `base64regex` (or add an explicit length check) in `sanitizeHost` (`packages/apps/shopify-api/lib/utils/shop-validator.ts`) to reject any string whose base64 length is not valid (i.e., reject length % 4 == 1, and validate padding count consistent with length), before calling `decodeHost`.
- Wrap the `decodeHost` call inside `sanitizeHost` in a `try/catch`, converting any decode failure into the documented `InvalidHostError` (respecting `throwOnInvalid`) instead of letting the native exception propagate.
- Add negative test cases for malformed-but-regex-matching base64 `host` values (e.g., length % 4 == 1) to `shop-validator.test.ts` to prevent regression.
- More broadly, review other utility functions where a coarse regex is treated as a full validity guard before an operation that has its own stricter parsing rules (`atob`, `URL`, `JSON.parse`, etc.) and ensure exceptions from those operations are caught and normalized to the library's documented error types.

### Proof of Concept
```ts
import {shopifyApi} from '@shopify/shopify-api';

const shopify = shopifyApi({/* ... valid config ... */});

// "A" matches /^[0-9a-zA-Z+/]+={0,2}$/ but has length 1 (mod 4 == 1),
// which is invalid base64 padding and causes atob() to throw.
try {
  shopify.utils.sanitizeHost('A', true);
} catch (e) {
  console.log(e.constructor.name); // DOMException / InvalidCharacterError, NOT InvalidHostError
}
```
Sending an authentication/redirect request such as:
```
GET /auth/callback?shop=my-shop.myshopify.com&host=A
```
to an app built with `@shopify/shopify-app-remix`, `@shopify/shopify-app-react-router`, or `@shopify/shopify-app-express` drives execution into `validateShopAndHostParams` / `redirectToShopifyOrAppRoot` / `redirectWithExitIframe`, which call `api.utils.sanitizeHost(...)` unguarded, reproducing the uncaught exception in the authentication code path described above.

export function getEmbeddedAppUrl(config: ConfigInterface): GetEmbeddedAppUrl {
  return async ({...adapterArgs}: GetEmbeddedAppUrlParams): Promise<string> => {
    const request = await abstractConvertRequest(adapterArgs);

    if (!request) {
      throw new ShopifyErrors.MissingRequiredArgument(
        'getEmbeddedAppUrl requires a request object argument',
      );
    }

    if (!request.url) {
      throw new ShopifyErrors.InvalidRequestError(
        'Request does not contain a URL',
      );
    }

    const url = new URL(request.url, `https://${request.headers.host}`);
    const host = url.searchParams.get('host');

    if (typeof host !== 'string') {
      throw new ShopifyErrors.InvalidRequestError(
        'Request does not contain a host query parameter',
      );
    }

    return buildEmbeddedAppUrl(config)(host);
  };
}

export function buildEmbeddedAppUrl(
  config: ConfigInterface,
): BuildEmbeddedAppUrl {
  return (host: string): string => {
    sanitizeHost(config)(host, true);
    const decodedHost = decodeHost(host);

    return `https://${decodedHost}/apps/${config.apiKey}`;
  };
}

import {Request, Response} from 'express';

import {ApiAndConfigParams} from '../types';

import {RedirectToShopifyOrAppRootMiddleware} from './types';

export function redirectToShopifyOrAppRoot({
  api,
  config,
}: ApiAndConfigParams): RedirectToShopifyOrAppRootMiddleware {
  return function () {
    return async function (req: Request, res: Response) {
      if (res.headersSent) {
        config.logger.info(
          'Response headers have already been sent, skipping redirection to host',
          {shop: res.locals.shopify?.session?.shop},
        );

        return;
      }

      const host = api.utils.sanitizeHost(req.query.host as string)!;
      const redirectUrl = api.config.isEmbeddedApp
        ? await api.auth.getEmbeddedAppUrl({
            rawRequest: req,
            rawResponse: res,
          })
        : `/?shop=${res.locals.shopify.session.shop}&host=${encodeURIComponent(
            host,
          )}`;

      config.logger.debug(`Redirecting to host at ${redirectUrl}`, {
        shop: res.locals.shopify.session.shop,
      });

      res.redirect(redirectUrl);
    };
  };
}
