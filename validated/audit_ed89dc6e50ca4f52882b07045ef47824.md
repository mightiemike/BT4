### Title
`safeCompare` throws an uncaught `SafeCompareError` (instead of returning `false`) when OAuth callback `state` is missing, causing inconsistent/500 error handling in the OAuth callback path - (File: packages/apps/shopify-api/lib/auth/oauth/safe-compare.ts)

### Summary
This is the closest reachable analog to the referenced bug class ("a low-level primitive reverts/throws unexpectedly on an edge-case input instead of the intended graceful failure, defeating the caller's error-handling design"). In this codebase, `safeCompare` throws `SafeCompareError` on type mismatch instead of returning `false`, and it is used to validate the anti-CSRF `state` parameter during the unauthenticated OAuth callback, where a missing/malformed `state` value naturally has a different `typeof` than the value read from the signed cookie.

### Finding Description
`safeCompare` is documented and implemented to compare values and return a boolean, but it deviates from that contract for type mismatches, throwing instead: [1](#0-0) 

It is invoked from the OAuth callback's CSRF check, `validQuery`, as `safeCompare(query.state!, stateFromCookie)`: [2](#0-1) 

`query.state` comes directly from `Object.fromEntries(query.entries())` on the raw request URL, i.e., attacker-controlled and force-cast with `!` (non-null assertion), while `stateFromCookie` is always a `string` (or the flow already threw `CookieNotFound` earlier): [3](#0-2) 

If an anonymous caller hits the OAuth callback endpoint with a `state` parameter omitted entirely (`query.state === undefined`), `typeof undefined !== typeof stateFromCookie` ('string'), so `safeCompare` throws `SafeCompareError` rather than the expected `InvalidOAuthError` that the surrounding code is designed to handle. Consuming frameworks' callback handlers explicitly branch on `InvalidOAuthError`, `CookieNotFound`, and `BotActivityDetected`, falling through to a generic `500` for anything else — meaning a malformed/missing `state` query param turns a "should-be-400 invalid OAuth request" into an unhandled `500`, as seen in `shopify-app-express`'s handler: [4](#0-3) 

### Impact Explanation
This is a low-severity availability/robustness issue, not a session forgery or authentication bypass: the request is still correctly rejected, just with the wrong status code (500 vs. 400) and via an unexpected error type rather than the semantically appropriate `InvalidOAuthError`. It could be leveraged as a minor DoS-on-observability vector (noisy 500 errors/alerts for what is just malformed attacker input on an anonymous endpoint) and it breaks callers that specifically pattern-match on the library's documented error hierarchy (`InvalidOAuthError`) to decide how to respond, similar in spirit to the referenced report's theme: an internal primitive reverting/throwing unexpectedly under a specific edge-case input undermines the caller's intended handling logic.

### Likelihood Explanation
High likelihood of being triggered: the OAuth callback route is a public, unauthenticated endpoint (`/auth/callback` or similar) and omitting or malforming the `state` query parameter is a trivial, single-request action for any anonymous actor. No privileged access or secret knowledge is required — this is the standard "hit the callback endpoint without going through `begin()`" scenario.

### Recommendation
Make `safeCompare` fail closed instead of throwing on type mismatch (return `false`) for benign type mismatches originating from optional/absent user input, or explicitly guard `validQuery` to check `typeof query.state === 'string'` before calling `safeCompare`, converting a missing/wrong-typed `state` into the intended `InvalidOAuthError` path. Alternatively, wrap `safeCompare` calls in oauth.ts in a try/catch that re-throws as `InvalidOAuthError` so all call sites preserve the documented `SafeCompareError`-throwing contract for legitimate internal type-mismatch bugs while normalizing user-supplied malformed input into the expected client-error path.

### Proof of Concept
1. An app is configured normally; a user begins OAuth via `shopify.auth.begin(...)`, which sets the signed `shopify_app_state` cookie containing a `state` nonce (string) as shown in `begin()`.
2. Attacker (or any client) sends a GET to the callback endpoint with a valid signed `shopify_app_state` cookie (can be replayed/observed on an anonymous test store) but omits the `state` query parameter entirely, e.g. `GET /auth/callback?shop=test.myshopify.com&hmac=<valid-or-omitted>` with no `state=`.
3. In `callback()`, `stateFromCookie` is retrieved successfully (cookie present), so the `CookieNotFound` branch is not hit.
4. `validQuery` executes `safeCompare(query.state!, stateFromCookie)` where `query.state` is `undefined` and `stateFromCookie` is a `string`.
5. `safeCompare` throws `ShopifyErrors.SafeCompareError` instead of returning `false`.
6. In `shopify-app-express`'s `authCallback`, this error is caught but does not match `InvalidOAuthError`, `CookieNotFound`, or `BotActivityDetected`, so `handleCallbackError` falls through to the `default` branch and returns HTTP `500` instead of the expected `400 Invalid OAuth callback`.

Note: I was not able to fully verify whether every downstream framework package (e.g. `shopify-app-remix`, `shopify-app-react-router`) explicitly catches `SafeCompareError` differently than `shopify-app-express` does, due to index/time constraints — this would be worth confirming with a full repository checkout before treating this as more than a low-severity error-handling defect.

export const safeCompare: SafeCompare = (strA, strB) => {
  if (typeof strA === typeof strB) {
    const enc = new TextEncoder();
    const buffA = enc.encode(JSON.stringify(strA));
    const buffB = enc.encode(JSON.stringify(strB));

    if (buffA.length === buffB.length) {
      return timingSafeEqual(buffA, buffB);
    }
  } else {
    throw new ShopifyErrors.SafeCompareError(
      `Mismatched data types provided: ${typeof strA} and ${typeof strB}`,
    );
  }
  return false;
};

async function handleCallbackError(
  req: Request,
  res: Response,
  api: Shopify,
  config: AppConfigInterface,
  error: Error,
) {
  switch (true) {
    case error instanceof InvalidOAuthError:
      res.status(400);
      res.send(error.message);
      break;
    case error instanceof CookieNotFound:
      await redirectToAuth({req, res, api, config});
      break;
    case error instanceof BotActivityDetected:
      res.status(410);
      res.send(error.message);
      break;
    default:
      res.status(500);
      res.send(error.message);
      break;
  }
}
