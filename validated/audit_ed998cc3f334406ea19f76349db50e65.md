### Title
Malicious actor can permanently DoS legitimate `UnfreezeBalanceContract` (delegated resource reclaim) transactions via unbounded growth of the legacy `DelegatedResourceAccountIndexCapsule` list - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`FreezeBalanceActuator.delegateResource()` lets any account freeze a small amount of TRX and delegate the derived bandwidth/energy to an **arbitrary receiver address**, without that receiver's consent — the same "act on behalf of someone else" pattern from the report. When the network is still running the legacy (pre-`AllowDelegateOptimization`) delegation-index format, each such delegation appends an entry into the receiver's `DelegatedResourceAccountIndexCapsule` (a single protobuf object holding a repeated `fromAccounts`/`toAccounts` list) with no upper bound on size. Once `AllowDelegateOptimization` is enabled, any legitimate delegator who later calls `UnfreezeBalanceActuator` (specifying that flooded address as `receiverAddress` or `ownerAddress`) is forced to run `DelegatedResourceAccountIndexStore.convert()`, which iterates and re-inserts **every single element** of that legacy list before it can complete. An attacker who inflates the list to a very large size can push this one-shot migration past the energy/gas budget of a single transaction, causing legitimate unfreeze transactions touching the flooded account to revert with an out-of-energy failure every time they are retried (since `convert()` only deletes the old record after finishing the full loop).

### Finding Description
`FreezeBalanceActuator.delegateResource()` calls the legacy index mutators when optimization is not yet active: [1](#0-0) 

The underlying capsule stores the delegation targets as an in-object repeated list with unbounded `addToAccount`/`addFromAccount` operations and no size checks: [2](#0-1) 

`FreezeBalanceActuator` never limits how many distinct receiver addresses an account may delegate to, or how many distinct delegators may target one receiver — the freeze amount only needs to be non-zero, so an attacker can create a large number of freeze-with-receiver transactions (from many sybil source accounts or the same one, targeting a fixed victim) to inflate the victim's index entry: [3](#0-2) 

The `convert()` migration path, triggered from `UnfreezeBalanceActuator` once `supportAllowDelegateOptimization()` is enabled, must process the *entire* legacy list for an address before deleting it, re-inserting each entry one at a time via `delegate()` (two DB writes per entry): [4](#0-3) 

`UnfreezeBalanceActuator.execute()` calls `convert(ownerAddress)` and `convert(receiverAddress)` unconditionally on both parties of a delegated unfreeze before the actual `unDelegate()`: [5](#0-4) 

If a victim address has been flooded with thousands of legacy delegation-index entries (as either the "from" or "to" side), the first innocent counterparty transaction that must run `convert()` on that flooded address inside `UnfreezeBalanceActuator.execute()` will attempt to loop over the whole bloated list within a single transaction's energy budget, which can run out of energy before finishing. Because `convert()` only deletes the legacy entry (line 60) after the loop completes, a partial/aborted execution leaves the bloated legacy record in place, so **every subsequent retry of that legitimate unfreeze transaction fails the same way**, permanently blocking legitimate reclaiming of delegated frozen balance involving the flooded address.

### Impact Explanation
This is a DoS on the state-transition (actuator) layer reachable from any anonymous, unprivileged broadcast transaction: an attacker can flood a targeted address's legacy delegation index with unbounded entries at negligible cost (minimum freeze amount, sybil source accounts), and any innocent third party whose `UnfreezeBalanceActuator` transaction needs to `convert()` that flooded address will have their withdrawal of already-legitimately-owned delegated resources permanently blocked by out-of-energy reverts, mirroring the "flood array → OOG on withdraw" bug class from the report.

### Likelihood Explanation
The delegation mechanism (`FreezeBalanceActuator` with `receiverAddress` set) is fully permissionless and requires no privileged role, matching the report's "stake on behalf of someone else" primitive. The cost to the attacker is proportional to the minimum freeze amount times the number of entries needed to make `convert()` exceed a transaction's energy limit, which is a bounded, attacker-controllable cost. The main mitigating factor is that this legacy-format vulnerability only manifests for addresses that still carry old-format delegation index records and are later touched by a delegated `UnfreezeBalanceContract` after `AllowDelegateOptimization` activation — this is a real migration path in the current codebase, not a hypothetical.

### Recommendation
- Enforce an upper bound on the number of entries in `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` (analogous to `UnfreezeBalanceV2Actuator.UNFREEZE_MAX_TIMES`).
- Make `DelegatedResourceAccountIndexStore.convert()` incremental/resumable (e.g., migrate and persist partial progress, or convert lazily on a per-pair basis) instead of requiring the full legacy list to be processed and only deleted at the very end within one transaction.
- Consider requiring receiver consent, or at least accounting/limiting delegation-index growth per receiver, in `FreezeBalanceActuator`/`DelegateResourceActuator`.

### Proof of Concept
1. Before `AllowDelegateOptimization` is enabled on a private/test network, use many source accounts (or repeated `FreezeBalanceContract` calls with different owners) each freezing the minimum allowed TRX amount and setting `receiverAddress` = victim, driving `DelegatedResourceAccountIndexCapsule.fromAccountsList` for the victim to a very large size via `addFromAccount` [6](#0-5) .
2. Enable `AllowDelegateOptimization` on the network.
3. Have any legitimate account submit an `UnfreezeBalanceContract` with `receiverAddress` = the flooded victim; observe `UnfreezeBalanceActuator.execute()` invoking `delegatedResourceAccountIndexStore.convert(receiverAddress)` [5](#0-4) , which loops over the full flooded list [7](#0-6) .
4. With a sufficiently large flooded list, the transaction exhausts its energy/gas budget and reverts before `this.delete(address)` executes, so the legacy bloat persists and the same failure recurs on every retry.

    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
