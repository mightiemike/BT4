### Title
Order-matching failures in `MarketSellAssetActuator` propagate uncaught, causing whole-block rejection instead of single-transaction failure - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
java-tron's on-chain TRC10 exchange ("Market") matches a single taker order against up to `MAX_MATCH_NUM` maker orders inside one actuator `execute()` call. This is the java-tron analog of the reported "batch order matching" pattern: many independent fill operations are processed together in a loop, and if any single one fails, the checked exception is not handled gracefully — it unwinds out of the batch, out of the actuator, and (unlike during block generation) is left **unguarded** in the block-application path `Manager.processBlock`, causing the entire containing block to be rejected/rolled back instead of just the offending transaction.

### Finding Description
`MarketSellAssetActuator.matchOrder` iterates over maker orders and calls `matchSingleOrder` for each match: [1](#0-0) 

If the number of matches exceeds `MAX_MATCH_NUM` (20), a `ContractValidateException` is thrown mid-loop instead of the match simply stopping gracefully: [2](#0-1) 

`matchSingleOrder` also performs an unguarded `orderStore.get(orderId)`-style lookup and arithmetic (`MarketUtils.multiplyAndDivide`) that can throw `ItemNotFoundException`/`ArithmeticException`: [3](#0-2) 

All of these exceptions are caught only at the top of `execute()` and re-thrown as `ContractExeException`: [4](#0-3) 

`TransactionTrace.exec()` declares (and does not internally catch) `ContractExeException`: [5](#0-4) 

`Manager.processTransaction` likewise declares and propagates it: [6](#0-5) 

Critically, the two call sites that invoke `processTransaction` treat this failure very differently:
- In `generateBlock` (block production), each transaction runs in its own session with a local `try { ... } catch (Exception e) { logger.warn(...) }` that simply *skips* the failing transaction without breaking the block: [7](#0-6) 
- In `processBlock` (block application/replay, used when validating a block received from the network or during fork switching), the same `processTransaction` call has **no per-transaction try/catch**: [8](#0-7) 

An exception here propagates out of `processBlock` → `applyBlock` → `pushBlock`, where it is caught generically and causes the **entire block** to be discarded/rolled back: [9](#0-8) 

The same unguarded `applyBlock` call is reused during `switchFork` (reorg replay), where transaction execution state (order book contents, order IDs, maker balances) legitimately differs from the original branch, making a previously-successful `MarketSellAssetContract` transaction able to fail deterministically on replay (e.g., a maker order consumed/removed on one branch causing `ItemNotFoundException`, or a different set of resting orders pushing the match count above `MAX_MATCH_NUM`): [10](#0-9) 

This is structurally the same root cause as the reported bug: a "batch" of independent fill/match operations (here, up to 20 maker-order fills within one transaction, and more broadly, all transactions within one block) is executed without a NoThrow/best-effort variant, so a single failing element (an unlucky/insufficiently-available maker order, or an attacker deliberately queuing >20 resting orders at the matching price) reverts everything around it — in java-tron's case, the entire block rather than just one exchange fill.

### Impact Explanation
Any account can submit `MarketSellAssetContract` transactions and populate the order book with many resting orders at a specific price to intentionally cause a future taker's match loop to exceed `MAX_MATCH_NUM`, or can otherwise arrange order-book state so a legitimate taker's transaction throws during matching. Because `Manager.processBlock`'s per-transaction execution loop has no exception isolation, this failure — when it occurs during block validation/replay by a non-producing node or during fork-switch replay — causes rejection/rollback of the entire block containing the transaction, not just failure of that one exchange fill. This is a denial-of-service/griefing vector against the exchange feature and, in the fork-replay case, can cause avoidable block/chain-processing failures on nodes reorganizing across forks, delaying settlement for all makers/takers in the affected block.

### Likelihood Explanation
Reachable from an unprivileged, ordinary broadcast transaction (`MarketSellAssetContract`) with no special privileges required; an attacker only needs to place resting orders to influence match counts or order-book state. The condition is most reliably triggered in `switchFork`/`processBlock` replay paths, which do occur naturally during normal blockchain fork resolution, making the missing per-transaction exception isolation in `processBlock` a real, exploitable, difficulty-moderate design gap, matching the "high difficulty, batch processing griefing" classification of the original report.

### Recommendation
- Short term: wrap the per-transaction execution inside `Manager.processBlock`'s loop with the same "skip and continue"/"mark failed" semantics already used in `generateBlock`, so a single transaction's execution failure (including `ContractExeException` from `MarketSellAssetActuator`) does not abort processing of the entire block; ensure block-level acceptance rules (e.g., matching the ret/receipt already committed by the original block producer) are preserved instead of re-throwing.
- Also bound `matchOrder`'s work (`MAX_MATCH_NUM`) by truncating gracefully (partially filling and leaving the remainder on the book) rather than throwing `ContractValidateException` mid-batch.
- Long term: audit all actuators that internally perform iterative/batch sub-operations (matching, multi-order processing) to ensure a single failing sub-operation degrades to a partial/no-op result rather than raising an exception that can escape to block-level control flow.

### Proof of Concept
Conceptual PoC (cannot be executed without a running node):
1. Attacker submits `MarketSellAssetContract` orders to create 21+ resting maker orders at the same matching price for a token pair (exceeding `MAX_MATCH_NUM = 20`). [11](#0-10) 
2. A victim taker submits a `MarketSellAssetContract` order large enough to match against all of them.
3. During block generation by the producing witness, `matchOrder` throws `ContractValidateException("Too many matches...")`; `generateBlock`'s try/catch silently drops the transaction — no block impact there.
4. However, if state differs across a fork switch (`switchFork`) such that this transaction was already included in an accepted block on one branch, replaying it against the alternate branch's order-book state in `applyBlock`/`processBlock` can throw the same/analogous exception (`ItemNotFoundException` for a since-removed maker order, or a differently-ordered match count exceeding `MAX_MATCH_NUM`), which propagates uncaught out of `processBlock` and causes `pushBlock` to discard the entire block: [12](#0-11)
