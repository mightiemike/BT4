### Title
OAuth callback shop-parameter confusion: HMAC/state validated shop can differ from shop used for token exchange and session creation - (File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts)

### Summary
In `callback()`, the `shop` value that is protected by HMAC/state validation is extracted differently from the `shop` value actually used to build the access-token exchange URL and the resulting `Session`. This is structurally the same bug class as the reported `permit` issue: a value is validated/"signed" in one form, but a second, independently-derived copy of that same logical value is what actually gets consumed by the sensitive operation, and the two can diverge.

### Finding Description
In `callback()` [1](#0-0) , the shop is first read directly off the `URLSearchParams` object:

```ts
const query = new URL(request.url, ...).searchParams;
const shop = query.get('shop')!;
```

`URLSearchParams.get()` returns the **first** occurrence of a repeated key.

The value that is actually protected by the request's HMAC and state check is built differently, via `Object.fromEntries(query.entries())` [2](#0-1) :

```ts
const authQuery: AuthQuery = Object.fromEntries(query.entries());
if (!(await validQuery({config, query: authQuery, stateFromCookie}))) {
  throw new ShopifyErrors.InvalidOAuthError('Invalid OAuth callback.');
}
```

`Object.fromEntries` iterates the `URLSearchParams` entries in order and, for a repeated key, the **last** occurrence wins (each insertion overwrites the previous one in the resulting object). Inside `validQuery`, `validateHmac` computes the local HMAC from this `authQuery` object using `stringifyQueryForAdmin`, which simply iterates `Object.keys(query)` [3](#0-2)  — since duplicate keys were already collapsed by `Object.fromEntries`, `normalizeQuery` (which only rejects duplicate values for `URLSearchParams` inputs, not for the already-deduped plain object) does not catch this [4](#0-3) .

Then, after the HMAC/state check passes, the code re-reads `shop` a **second time** from the raw `URLSearchParams` (first occurrence) to build the actual token-exchange target and the session's shop:

```ts
const cleanShop = sanitizeShop(config)(query.get('shop')!, true)!;
...
const postResponse = await fetchRequestFactory(config)(
  `https://${cleanShop}/admin/oauth/access_token`, ...);
...
const session: Session = createSession({..., shop: cleanShop, ...});
``` [5](#0-4) 

So: if a request contains `shop` twice (`?shop=<first>&...&shop=<last>&hmac=...&state=...`), the HMAC/state validation is computed and checked against the **last** `shop` value, while the actual OAuth token exchange and resulting `Session.shop` use the **first** `shop` value. These two extraction paths for the same logical field can be made to diverge by an unauthenticated caller crafting the callback URL directly (`/auth/callback` is a public GET endpoint), exactly mirroring the reported pattern where a value used for a signature/validation step is not the same value later consumed by the sensitive operation.

### Impact Explanation
This breaks the invariant that "the shop that was cryptographically verified by Shopify's HMAC is the shop the library acts on." Concretely:
- The `cleanShop` used to build the `admin/oauth/access_token` request target, and the `shop` field written into the resulting `Session` object (which apps then persist via `sessionStorage.storeSession`), is **not** the value that was actually checked against Shopify's HMAC.
- This is a session/shop-identity confusion bug in the OAuth handler that a background agent/security team should treat as a potential cross-tenant/session-storage-injection risk, since downstream code trusts `session.shop` as having been Shopify-verified.

The real-world blast radius depends on an external factor this repo does not control: whether Shopify's `/admin/oauth/access_token` endpoint itself rejects an authorization `code` when POSTed to a shop domain different from the one the code was issued for. If Shopify enforces that binding server-side, the practical effect degrades to a failed request (denial of the OAuth flow) — the same "logic failure/mismatch" class of impact as the original `permit` report, rather than full token theft. This external dependency could not be verified from the codebase alone.

### Likelihood Explanation
The `/auth/callback` endpoint is unauthenticated and accepts arbitrary query strings from any anonymous caller, so constructing a request with a duplicated `shop` parameter is trivial. However, exploitation still requires the attacker to possess: (1) a cookie-bound `state` value from a prior legitimate `begin()` call, and (2) a Shopify-issued HMAC/`code` pair for some shop. These are obtainable by an attacker performing their own legitimate install flow, making the divergence self-inducible and testable, but turning it into cross-tenant impact against a third-party victim shop requires the additional (unverified) assumption about Shopify's server-side code/shop binding.

### Recommendation
Extract the `shop` value exactly once, from the same normalized source that is fed into HMAC/state validation, and reuse that single value everywhere (for logging, the token-exchange URL, and the created `Session`). Concretely, derive `cleanShop` from `authQuery.shop` (the same object validated by `validQuery`) instead of re-reading `query.get('shop')` a second time, and reject any request containing duplicate security-relevant parameters (`shop`, `hmac`, `state`, `code`, `timestamp`) before validation — mirroring the duplicate-parameter rejection that already exists for `appProxy` signator requests in `normalizeQuery`/`APP_PROXY_SINGLE_VALUE_PARAMS` [6](#0-5) .

### Proof of Concept
1. Attacker performs a normal `GET /auth/begin?shop=attacker-shop.myshopify.com`, receiving a signed `shopify_app_state` cookie with `state=S`.
2. Attacker completes Shopify's real consent screen for `attacker-shop.myshopify.com`, and Shopify redirects the browser to:
   `GET /auth/callback?code=C&hmac=H&shop=attacker-shop.myshopify.com&state=S&timestamp=T`
   where `H` is a valid Shopify-computed HMAC over exactly those params.
3. Instead of following that redirect, the attacker sends a modified request directly to the app server:
   `GET /auth/callback?shop=victim-shop.myshopify.com&code=C&hmac=H&shop=attacker-shop.myshopify.com&state=S&timestamp=T`
4. `query.get('shop')` (used for `cleanShop`/session) returns `victim-shop.myshopify.com` (first occurrence).
5. `Object.fromEntries(query.entries())` (used for `authQuery`, HMAC/state validation) collapses to `shop=attacker-shop.myshopify.com` (last occurrence) — matching `H`, so validation passes.
6. The library proceeds to POST to `https://victim-shop.myshopify.com/admin/oauth/access_token` using `code=C`, and (if that request were accepted) would create a `Session` with `shop: 'victim-shop.myshopify.com'` despite the HMAC never having verified anything about `victim-shop.myshopify.com`.

Whether step 6 succeeds in creating a usable session for `victim-shop.myshopify.com` depends on Shopify's own OAuth server validating the code-to-shop binding — this could not be confirmed from the repository and would need to be verified against live Shopify behavior or Shopify's OAuth documentation.

function stringifyQueryForAdmin(query: AuthQuery): string {
  const processedQuery = new ProcessedQuery();
  Object.keys(query)
    .sort((val1, val2) => val1.localeCompare(val2))
    .forEach((key: string) => processedQuery.put(key, query[key]));

  return processedQuery.stringify(true);
}
```

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
