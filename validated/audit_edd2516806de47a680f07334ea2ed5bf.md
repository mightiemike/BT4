## Finding

### Title
Unbounded up-front allocation from an attacker-controlled length felt in deprecated (Cairo0) syscall array reads - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The Cairo0 ("deprecated") syscall array-reading helper `read_felt_array` takes an array-size value directly from a felt written into VM memory by the executing contract, converts it to `usize`, and passes it straight into a range-read over VM memory without first checking it against any sane bound (e.g. remaining calldata/segment size or a protocol-level array-length cap) [1](#0-0) . This mirrors the reported Bouncy Castle bug class: a definite/declared length is used to drive an up-front allocation before the data actually backing that length has been validated.

### Finding Description
`read_felt_array` reads `array_size` as a raw `Felt` from the syscall segment and converts it with `usize::try_from(array_size.to_biguint())`, then calls `felt_range_from_ptr(vm, array_data_start_ptr, size)` [2](#0-1) . `felt_range_from_ptr` forwards `size` unchanged into `vm.get_integer_range(ptr, size)` [3](#0-2) , a cairo-vm API that allocates a result buffer sized to the requested length before validating that each of the `size` memory cells actually contains data.

This helper is used to parse the calldata/keys/data/payload arguments of every deprecated syscall reachable from Cairo0 contract execution: `CallContract`, `DeployRequest`, `EmitEventRequest` (keys and data), and `SendMessageToL1Request` (payload) [4](#0-3) [5](#0-4) [6](#0-5) . Because a Cairo0 contract can write an arbitrary felt (up to the field prime, truncated by the `usize::try_from` conversion, i.e. up to `usize::MAX` on 64-bit) into the `*_len` memory cell just before invoking one of these syscalls, the "declared length" is fully attacker-controlled and independent of how much data is actually present in the referenced memory segment.

By contrast, the newer (Cairo1) `read_felt_array` computes size as the difference between two pointers that must resolve to real relocatable memory addresses in the same segment, which is a materially different (and less attacker-friendly) constraint [7](#0-6) . The deprecated path has no equivalent guard.

### Impact Explanation
A malicious contract deployer can deploy (or already control) a Cairo0 class and, during any transaction that invokes it (`__execute__`, `__validate__`, a nested `call_contract`/`library_call`, or during simulation/estimate-fee), issue a deprecated syscall (e.g. `EmitEvent`) with a huge `keys_len`/`data_len` felt. When the sequencer/blockifier executes that transaction, `read_felt_array` attempts to allocate/read a vector sized to that attacker-chosen length, which can trigger an out-of-memory condition or an extremely expensive allocation in the sequencer process. This can crash or stall the node executing the transaction (batcher, gateway simulation, RPC re-execution), which for a single node is a resource-exhaustion/availability issue; if triggered consistently across honest sequencers processing the same block/mempool entry, it can prevent block production, i.e. a network unable to confirm new transactions.

### Likelihood Explanation
Deploying and calling Cairo0 (`ContractClass::V0`) contracts remains fully supported for backward compatibility, and any account can submit an `Invoke`/`Declare` transaction that reaches this code path, so the trigger requires nothing more than an ordinary transaction from an unprivileged sender. The only friction is that the syscall executes under a Cairo VM step/gas budget, but writing a single large felt into the `*_len` memory cell and invoking the syscall costs a fixed, small number of steps regardless of the declared value, so the attacker does not need proportional gas to trigger the oversized read attempt.

### Recommendation
In `read_felt_array` (deprecated_syscalls/hint_processor.rs), validate `array_size` against a sane upper bound (e.g., the size of the referenced memory segment, or a protocol-level `sierra_array_len_bound`-style constant) before calling `felt_range_from_ptr`, mirroring the approach already used for retdata array parsing elsewhere in the codebase, which explicitly checks the declared length against the remaining input before calling `Vec::with_capacity` [8](#0-7) .

### Proof of Concept
1. Deploy a Cairo0 contract whose external function, before calling the `emit_event` (or `send_message_to_l1`) syscall, writes an oversized value (e.g. `2**40`) into the `keys_len`/`data_len`/`payload_size` memory cell of the syscall request segment, leaving the corresponding data pointer as a segment with far fewer actual felts.
2. Submit an ordinary `INVOKE` transaction that calls this external function.
3. During execution, `EmitEventRequest::read` invokes `read_felt_array`, which converts the oversized felt to `usize` and calls `felt_range_from_ptr`/`vm.get_integer_range` with that size, attempting a multi-terabyte allocation/read before any element is validated, crashing or stalling the executing sequencer process [4](#0-3) [1](#0-0) .

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
