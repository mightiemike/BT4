Based on available evidence, I found a genuine "cached value not invalidated when its source moves" analog to the Derby M-38 pattern, though I could not fully trace the exact market-contract call site that combines the cache read with a `socialize-debt` call within the same transaction (I ran out of tool iterations before reading `v0-4-market.clar`'s liquidation flow in full). I present the finding with that caveat noted explicitly.

### Title
Market index-cache is not invalidated when a vault's `lindex` is written down by `socialize-debt` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` caches each vault's `{index, lindex}` per `{timestamp, aid}` to avoid repeated cross-contract accrual calls within the same block. This cache is populated only through `accrue-and-cache`, which calls the vault's own `accrue` function. However, vault contracts also expose a separate `socialize-debt` entry point that mutates `lindex` directly — bypassing `accrue` entirely — so the market's cache is never told that the vault's `lindex` changed.

### Finding Description
`market.clar` defines a per-block cache: [1](#0-0) 

populated lazily by `accrue-and-cache`, which returns the cached tuple if already set for the current `stacks-block-time`, and otherwise calls the vault's `accrue` and stores the result: [2](#0-1) 

Separately, every vault exposes `socialize-debt`, used to write down bad debt by reducing `lindex` proportionally to a loss in `total-assets`. Critically, this function does **not** call `accrue` first, and it writes `lindex` directly via `var-set`: [3](#0-2) 

Because `socialize-debt` never goes through `accrue-and-cache`, if the market has already cached `{index, lindex}` for a vault's `aid` earlier in the same block (e.g., as part of a health check, collateral valuation, or price resolution triggered by any market operation), and `socialize-debt` is subsequently invoked on that vault later in the same block to write down bad debt, any further market operation in that block that calls `accrue-and-cache` for the same `{timestamp, aid}` key will hit the stale cache entry and reuse the pre-write-down `lindex`. `resolve-ztoken` derives the zToken price directly from this cached `lindex`: [4](#0-3) 

This is structurally identical to the M-38 pattern: a state-mutating operation (`socialize-debt`, analogous to `settleDeltaAllocation`) runs and changes the value (`lindex`) that a downstream computation depends on, but the downstream computation (a later `accrue-and-cache` lookup within the same block, analogous to `storePriceAndRewards`) does not observe the mutation because it consults a cache instead of the live source, and nothing invalidates that cache when the source is mutated out-of-band.

### Impact Explanation
If the stale, artificially-high `lindex` is reused for pricing a zToken as collateral within the same block/transaction after a debt write-down (which by definition happens when the vault is already under-collateralized), users' collateral value would be overstated relative to the post-write-down reality, permitting borrowing or withdrawal actions against inflated collateral valuations before the cache naturally expires at the next block. This falls under temporary freezing/impairment of protocol solvency margins — a High-severity issue per the accepted impact classes (temporary mispricing affecting protocol solvency accounting within the affected block).

### Likelihood Explanation
This requires `socialize-debt` to be invoked on a vault in the same block where the market has already cached that vault's index for another operation — a scenario plausible during liquidation/bad-debt-socialization flows that are typically bundled with other market operations in one transaction. I was not able to confirm, before running out of tool calls, the exact function in `v0-4-market.clar` that calls `socialize-debt` and whether it is combined with a prior `accrue-and-cache` lookup in the same call graph, so likelihood should be verified against that specific call site before treating this as confirmed.

### Recommendation
Invalidate (or update) the market's `index-cache-` entry for a vault whenever that vault's `lindex`/`index` is mutated by any path other than `accrue` — either by having `socialize-debt` push the updated `lindex` back to the market's cache, or by having the market re-fetch (rather than cache-read) the vault's index/lindex immediately after any bad-debt socialization step within the same transaction.

### Proof of Concept
1. In block N, a user action (e.g., `collateral-add`) causes `market.clar` to call `accrue-and-cache` for vault `aid=X`, which calls the vault's `accrue`, computes `{index, lindex}`, and stores it in `index-cache-` keyed by `{timestamp: stacks-block-time, aid: X}`.
2. Later in the same block N, the market (or an authorized caller) invokes vault `X`'s `socialize-debt`, which reduces `lindex` directly via `var-set lindex new-lindex` per [3](#0-2)  without touching the market's cache.
3. Still within block N, another market operation (e.g., a different user's `collateral-add`, `borrow`, or price resolution for a position holding zToken-X) calls `accrue-and-cache` for `aid=X` again; because an entry already exists for `{timestamp: N, aid: X}`, the stale pre-write-down `lindex` is returned instead of the updated value.
4. `resolve-ztoken` prices zToken-X collateral using this stale `lindex`, overstating its value for the remainder of block N, letting a user borrow or avoid a health check against collateral that is actually worth less post-write-down.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
