## Title
Nested `WithdrawFromGasKey` inside a meta-transaction bypasses the SPICE pending-transaction-queue's gas-key balance accounting, allowing over-commitment/double-spend of gas key funds before certification - ([File: core/primitives-core/src/version.rs])

## Summary
Nearcore's SPICE `PendingTransactionQueue` (PTQ) mirrors the exact bug class from the external report: balance/nonce checks are performed when a transaction is *admitted* into a block (based on then-current certified state), but the guarantee that later, not-yet-certified transactions cannot double-spend the same funds depends on PTQ correctly *scanning* every transaction for its economic effect. A `WithdrawFromGasKey` action nested inside a `Delegate`/meta-transaction is not scanned by PTQ (which only inspects top-level actions), so the gas key balance it drains is never added to `pending_gas_key_costs`. A second, independently-admitted gas-key transaction that PTQ still believes is "funded" can then be admitted and later fail (or, in the worst case, interact with a balance that has already been drained), exactly mirroring the fund_token.move scenario of stale checks at settlement time.

## Finding Description
`PendingTransactionQueue::add_chunk_transactions` and `PendingTxSession::check_pending` compute a `PendingConstraints` snapshot (`paid_from_balance`, `paid_from_gas_key`, `max_nonce`) that the runtime's `verify_and_charge_gas_key_tx_ephemeral` uses to make sure a chunk producer does not admit two, not-yet-certified transactions that would jointly overdraw a gas key [1](#0-0) . The scan for `WithdrawFromGasKey` effects is explicit and only looks at top-level `tx.actions()`:

```
// Scan actions for WithdrawFromGasKey (affects gas key balance).
for action in tx.actions() {
    if let Action::WithdrawFromGasKey(withdraw) = action { ... }
}
``` [2](#0-1) 

The same top-level-only scan is repeated in the per-chunk-production session tracker [3](#0-2) .

A `WithdrawFromGasKey` action can, however, also be nested inside a `Delegate` (meta-transaction) action's inner action list, executed later against the sender's own gas key via `validate_delegate_action_key`/`apply_delegate_action` [4](#0-3) . Because PTQ's `add_chunk_transactions` and `check_pending` never look inside a delegate action's `actions` list, a delegated `WithdrawFromGasKey` drains the gas key balance in the actual runtime apply step without ever being reflected in `pending_gas_key_costs`. This lets an account admit further gas-key transactions in the same certification window that PTQ still treats as "funded," reproducing the report's core defect: the check performed at admission time does not match the state that will actually exist at settlement time.

This exact gap is documented as a known, protocol-gated fix in the codebase itself:
```
/// Reject a `WithdrawFromGasKey` action nested inside a delegate action.
/// The SPICE pending transaction queue scans only the top level actions of
/// a transaction for `WithdrawFromGasKey`, so a nested one drains a gas key
/// that the queue still counts as funded.
RejectWithdrawFromGasKeyInDelegate,
``` [5](#0-4) 

`validate_delegate_action`/`action_validation.rs` only rejects a nested `WithdrawFromGasKey` when `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is enabled for the current protocol version, and only for `ValidateReceiptMode::NewReceipt` (in-flight receipts created before the rule are still executed) [6](#0-5) . The dedicated regression test `test_reject_delegated_gas_key_withdraw_protocol_upgrade` demonstrates, pre-upgrade, that the nested withdrawal is admitted and "drains the gas key" while PTQ's accounting is unaware of it [7](#0-6) .

## Impact Explanation
While this hole is closed by a protocol feature flag (`RejectWithdrawFromGasKeyInDelegate`) for any protocol version where the fix is active, it demonstrates a structural weakness of the PTQ design pattern: settlement-time state (the real gas-key balance after execution) is not re-checked against what admission-time bookkeeping assumed, exactly as in the reported bug class. If a validator/network runs at (or briefly transitions through) a protocol version where this fix is not yet active, or if a similar gap exists for any other action nested inside a delegate/meta-transaction not yet enumerated by PTQ's scan, an attacker can:
- Submit several gas-key transactions plus a delegate action with a nested `WithdrawFromGasKey` in the same admission window, causing PTQ to admit transactions it believes are funded when they are not, leading to a chunk-application-time failure of the trailing transactions (denial of service / wasted gas by the relayer), or
- Exploit timing so that funds committed to one purpose are silently redirected via the nested withdrawal, subverting the economic guarantee the PTQ is meant to provide before certification.

This matches the report's exploit pattern of "creating multiple requests that pass individual admission checks but collectively invalidate one another due to a state change unaccounted for at settlement."

## Likelihood Explanation
Reachable by a single unprivileged transaction signer/relayer building an ordinary `SignedTransaction` containing a `Delegate` action whose inner actions embed a `WithdrawFromGasKey`; no validator, network, or SPICE-consensus-specific privilege is required beyond running under the SPICE protocol feature with pending-transaction-queue admission enabled. Likelihood is Low-to-Medium on the current stable protocol (86) since `RejectWithdrawFromGasKeyInDelegate` appears designed to close this specific gap, but the same class of gap (an admission-time scanner missing nested/derived economic effects) could recur with any future action type added inside `DelegateAction`, since the scanning logic in `pending_transaction_queue.rs` is a manually maintained, non-exhaustive enumeration rather than a structural guarantee.

## Recommendation
- Make PTQ's economic-effect scanning exhaustive over nested actions (i.e., recurse into `Delegate`/`DelegateV2` action lists) rather than maintaining a per-action-type allowlist that must be updated whenever a new action can indirectly move balance.
- Add a structural invariant/test that fails CI if a new `Action` variant capable of moving gas-key or account balance is introduced without a corresponding update to `pending_transaction_queue.rs`'s scanning logic.
- Continue to gate any newly-discovered nested-action gaps behind protocol features exactly as done for `RejectWithdrawFromGasKeyInDelegate`/`RejectDelegateV2`, and document the residual risk window between feature introduction and activation.

## Proof of Concept
Based on `test_reject_delegated_gas_key_withdraw_protocol_upgrade` [8](#0-7) :
1. Run a SPICE-enabled network at a protocol version prior to `RejectWithdrawFromGasKeyInDelegate` activation, with the pending-transaction-queue admission enabled.
2. Account `alice` adds a gas key and funds it via `TransferToGasKey`.
3. `alice` builds a `DelegateAction` whose single inner action is `WithdrawFromGasKey` targeting her own gas key, signed with her plain access key, and has relayer `relayer` wrap/submit it as a `Delegate` transaction.
4. Simultaneously (same admission window/chunk), `alice` submits an ordinary gas-key transaction spending from the same gas key, up to the balance PTQ still believes is available (since the nested withdrawal was never scanned into `pending_gas_key_costs`).
5. Observe that PTQ admits both, yet the actual runtime execution order can leave the gas-key balance either fully drained (leaving the ordinary tx to fail at settlement) or overcommitted relative to what admission-time checks guaranteed — reproducing the "checks not re-validated at settlement" defect from the report.

fn validate_delegate_action(
    limit_config: &LimitConfig,
    delegate_action: VersionedDelegateActionRef<'_>,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ActionsValidationError> {
    // Check the count before `get_actions()` clones the list, so a huge
    // nested-action list can't force the allocation before being rejected.
    // Consensus-neutral: same `TotalNumberOfActionsExceeded` as the check in
    // `validate_actions_with_mode` below.
    let num_actions = delegate_action.actions().len() as u64;
    if num_actions > limit_config.max_actions_per_receipt {
        return Err(ActionsValidationError::TotalNumberOfActionsExceeded {
            total_number_of_actions: num_actions,
            limit: limit_config.max_actions_per_receipt,
        });
    }
    let actions = delegate_action.get_actions();
    // As with the `DelegateV2` removal above, receipts created before this rule
    // are still in flight and must keep executing.
    if mode == ValidateReceiptMode::NewReceipt
        && ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(current_protocol_version)
        && actions.iter().any(|action| matches!(action, Action::WithdrawFromGasKey(_)))
    {
        return Err(ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate);
    }

#[test]
fn test_reject_delegated_gas_key_withdraw_protocol_upgrade() {
    init_test_logger();

    if !ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(PROTOCOL_VERSION) {
        return;
    }

    let new_protocol = ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.protocol_version();
    let old_protocol = new_protocol - 1;
    assert!(
        old_protocol >= MIN_SUPPORTED_PROTOCOL_VERSION,
        "no supported protocol version still admits a delegated WithdrawFromGasKey, so there is \
         nothing left to test here - remove this test"
    );

    let sender = create_account_id("alice");
    let relayer = create_account_id("relayer");
    let epoch_length = 10;

    // Boundary "mm": "alice" lands on the first shard, "relayer" on the second,
    // so the delegate receipt crosses a shard on its way to the sender.
    let shard_layout = ShardLayout::multi_shard_custom(vec![create_account_id("mm")], 1);

    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .protocol_version(old_protocol)
        .protocol_upgrade_schedule(ProtocolUpgradeVotingSchedule::new_immediate(new_protocol))
        .epoch_length(epoch_length)
        .shard_layout(shard_layout)
        .add_user_account(&sender, Balance::from_near(1_000))
        .add_user_account(&relayer, Balance::from_near(1_000))
        .build();

    let gas_key: Signer =
        InMemorySigner::from_seed(sender.clone(), KeyType::ED25519, "gas_key").into();
    let add_key_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::AddKey(Box::new(AddKeyAction {
            public_key: gas_key.public_key(),
            access_key: AccessKey::gas_key_full_access(1),
        }))],
    );
    env.rpc_runner().run_tx(add_key_tx, Duration::seconds(10));

    let fund_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::TransferToGasKey(Box::new(TransferToGasKeyAction {
            public_key: gas_key.public_key(),
            deposit: Balance::from_near(10),
        }))],
    );
    env.rpc_runner().run_tx(fund_tx, Duration::seconds(10));

    // Before the upgrade the nested withdrawal is admitted and moves balance out
    // of the gas key, which is the hole this rule closes.
    assert_eq!(
        env.rpc_node().protocol_version_at_head(),
        old_protocol,
        "expected to start pre-upgrade"
    );
    let (_, balance_before) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    let tx = delegated_withdraw_tx(&env, &sender, &relayer, &gas_key);
    let outcome = env
        .rpc_runner()
        .execute_tx(tx, Duration::seconds(10))
        .expect("delegated withdrawal admitted pre-upgrade");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::SuccessValue(_),
        "pre-upgrade delegated withdrawal should execute",
    );
    let (_, balance_after) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    assert_eq!(
        balance_after,
        balance_before.checked_sub(WITHDRAW_AMOUNT).unwrap(),
        "the nested withdrawal should have drained the gas key",
    );
