### Title
Constant-call energy clamp is bypassed when `fee_limit` is omitted, always granting the max free `maxEnergyLimitForConstant` energy budget - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
`VMActuator.validate()` only tightens `maxEnergyLimit` down from `CommonParameter.maxEnergyLimitForConstant` when `isConstantCall && trx.getRawData().getFeeLimit() > 0`. `TriggerConstantContractServlet` never reads or sets `fee_limit` from the request body onto the transaction (unlike `TriggerSmartContractServlet`, which explicitly parses `fee_limit` and injects it via `rawBuilder.setFeeLimit(feeLimit)`), so every constant call submitted via `/wallet/triggerconstantcontract` has `feeLimit == 0` and the clamp condition is never true.

### Finding Description
The clamp logic in `VMActuator.validate()` is: [1](#0-0) 

```
trx = context.getTrxCap().getInstance();
// If tx`s fee limit is set, use it to calc max energy limit for constant call
if (isConstantCall && trx.getRawData().getFeeLimit() > 0) {
  maxEnergyLimit = min(maxEnergyLimit, trx.getRawData().getFeeLimit()
      / context.getStoreFactory().getChainBaseManager()
      .getDynamicPropertiesStore().getEnergyFee(), VMConfig.disableJavaLangMath());
}
```

`maxEnergyLimit` is initialized in the constructor to `CommonParameter.getInstance().maxEnergyLimitForConstant` [2](#0-1) , and if `isConstantCall` is true this value is used directly as `energyLimit` in both `create()` and `call()` when `feeLimit <= 0` bypasses the clamp [3](#0-2) .

Tracing the HTTP entry point, `TriggerConstantContractServlet.doPost()` parses the request body only into a `TriggerSmartContract` proto via `JsonFormat.merge(contract, build, visible)` and then calls `wallet.createTransactionCapsule(build.build(), ContractType.TriggerSmartContract)` — there is no `fee_limit` extraction anywhere in this servlet [4](#0-3) . This is a structural gap, not merely an omitted optional field: `TriggerSmartContract` (the proto used for constant calls) has no `fee_limit` field at all — `fee_limit` only exists on `Transaction.raw`. Contrast this with `TriggerSmartContractServlet` (the non-constant sibling), which explicitly reads `fee_limit` from the JSON body and injects it into the raw transaction before calling the actuator: [5](#0-4) .

Because the constant-call servlet path never populates `feeLimit`, the transaction capsule built for every `/wallet/triggerconstantcontract` HTTP call carries `feeLimit == 0`, so `trx.getRawData().getFeeLimit() > 0` is always false and the min-clamp is dead code for this endpoint. The `estimateEnergy`/`cleanContextAndTriggerConstantContract` path in `Wallet.java` does call `txCap.setFeeLimit(feeLimit)` for its own binary-search purposes [6](#0-5) , but that is unrelated to the plain `triggerConstantContract` RPC/HTTP call used by ordinary clients.

### Impact Explanation
Every unauthenticated/unprivileged caller of `/wallet/triggerconstantcontract` (or the gRPC `triggerConstantContract`/JSON-RPC `eth_call`-equivalent path that doesn't set fee_limit) always receives the full `maxEnergyLimitForConstant` (default 100,000,000, floor-clamped to at least 3,000,000 by `VmConfig.postProcess()` [7](#0-6) ) energy budget for free, regardless of the node operator's intended fee-based throttling via the dynamic `getMaxFeeLimit()`/`getEnergyFee()` properties. This maximizes the CPU/energy cost per free constant call an attacker can trigger, amplifying resource-exhaustion / DoS potential against RPC-API nodes (repeated calls into energy-heavy view functions consuming full VM execution budget each time), matching the "DoS via RPC-API" bounty impact class.

### Likelihood Explanation
Trivial and fully repeatable: no special account, signature, or fee payment is required since constant calls are unsigned/free reads. The attacker simply POSTs a JSON body to `/wallet/triggerconstantcontract` omitting `fee_limit` (the field doesn't even exist on the `TriggerSmartContract` proto the servlet parses), targeting a contract function that is energy-heavy. This works with 100% of default node configurations because the code path (`TriggerConstantContractServlet` → `Wallet.triggerConstantContract` → `VMActuator.validate`) is unconditional and unauthenticated.

### Recommendation
Since constant calls are not fee-metered by design (no real fee is charged), the "clamp via feeLimit" mechanism is inherently unreliable as a DoS control for the public triggerconstantcontract endpoint. Rely primarily on `maxEnergyLimitForConstant` itself as the sole authoritative cap (already bounded to a sane default) rather than a fee-based clamp that can't be enforced without an actual paying transaction. If a fee-based clamp is still desired, it should be removed as dead/misleading code for the constant-call path, or documented clearly that `maxEnergyLimitForConstant` alone governs the free-call energy ceiling; node operators concerned about DoS should tune `vm.maxEnergyLimitForConstant` down and/or add request-level rate limiting (already partially provided via `RateLimiterServlet`) rather than depending on this clamp.

### Proof of Concept
```java
// JUnit-style illustration of VMActuator.validate() behavior
@Test
public void testConstantCallEnergyClampBypassedWithZeroFeeLimit() throws Exception {
  // trx built with feeLimit = 0 (default when TriggerConstantContractServlet
  // never populates fee_limit on the TriggerSmartContract-derived TransactionCapsule)
  TransactionCapsule trxCapZeroFee = buildTriggerSmartContractCapsule(/* feeLimit */ 0L);
  VMActuator vmActuator = new VMActuator(true /* isConstantCall */);
  TransactionContext ctx = new TransactionContext(blockCap, trxCapZeroFee, storeFactory, true, false);
  vmActuator.validate(ctx);
  // maxEnergyLimit remains CommonParameter.maxEnergyLimitForConstant (100_000_000 by default)
  assertEquals(CommonParameter.getInstance().getMaxEnergyLimitForConstant(),
      getPrivateMaxEnergyLimit(vmActuator));

  // Compare with feeLimit > 0, e.g. feeLimit = 1000 sun, getEnergyFee() = 100 sun/energy
  TransactionCapsule trxCapWithFee = buildTriggerSmartContractCapsule(/* feeLimit */ 1000L);
  VMActuator vmActuator2 = new VMActuator(true);
  TransactionContext ctx2 = new TransactionContext(blockCap, trxCapWithFee, storeFactory, true, false);
  vmActuator2.validate(ctx2);
  // clamp applies: min(100_000_000, 1000/100) = 10
  assertEquals(10L, getPrivateMaxEnergyLimit(vmActuator2));
}
```
