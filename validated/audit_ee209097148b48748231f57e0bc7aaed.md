### Title
No Rate Limiting on `query` (CallFunction) JSON-RPC Endpoint Enables Non-Network-Level DoS - (File: `chain/jsonrpc/src/lib.rs`)

### Summary

The nearcore JSON-RPC server exposes a `query` endpoint that accepts `CallFunction` sub-requests. Each such request executes a WASM contract function inside `TrieViewer::call_function()` against the trie, consuming CPU up to `max_gas_burnt_view` gas. No rate limiting, concurrency cap, or per-IP throttle exists anywhere in the RPC handler. An unprivileged user can flood this endpoint with concurrent requests, exhausting all `ViewClientActor` worker threads and causing legitimate RPC queries to time out — a non-network-level, hardfork-free-fixable DoS.

---

### Finding Description

The `process_request_internal` function in `chain/jsonrpc/src/lib.rs` dispatches every incoming JSON-RPC call with no rate limiting or concurrency guard: [1](#0-0) 

The only middleware applied at the axum router level is a `RequestBodyLimitLayer` for payload size: [2](#0-1) 

A grep of `chain/jsonrpc/src/` for any rate-limiting, semaphore, or throttle construct returns zero matches.

When the `query` method receives a `CallFunction` sub-request, it routes to `call_function_local()` (or `call_function_sharded()`), which sends a `ClientQuery` to `ViewClientActor`: [3](#0-2) 

`ViewClientActor` handles this by calling `TrieViewer::call_function()`, which instantiates and runs the WASM VM up to `max_gas_burnt_view` gas: [4](#0-3) 

`ViewClientActor` is spawned as a multithread actor with a fixed `view_client_threads` count: [5](#0-4) 

With no rate limiting at the RPC layer, an attacker can saturate all `view_client_threads` worker threads with long-running WASM executions, starving all other `ViewClientActor` message handlers (block queries, tx status, validator info, etc.).

The same path applies to `ViewState` without pagination, which iterates the trie with no per-request concurrency guard: [6](#0-5) 

---

### Impact Explanation

- **Scope match:** Non-network-level DoS, fixable without a hardfork — explicitly in scope per HackenProof.
- **Broken invariant:** The RPC layer must remain available to serve legitimate users. Exhausting `ViewClientActor` threads breaks this invariant.
- **Affected resources:** All `ViewClientActor`-backed RPC methods (`block`, `chunk`, `tx`, `validators`, `query`, etc.) become unresponsive while the attack is ongoing.
- **No privileged access required:** The `query` endpoint is public and unauthenticated.

---

### Likelihood Explanation

- The `query` endpoint is documented and widely used.
- A single attacker with a modest HTTP client can open hundreds of concurrent connections and issue `CallFunction` requests targeting a contract with a CPU-intensive view method.
- `max_gas_burnt_view` bounds per-call CPU but does not bound the number of concurrent calls.
- Default `view_client_threads` is small (typically 4), so saturation requires few concurrent requests.

---

### Recommendation

Add a concurrency semaphore or token-bucket rate limiter in `process_request_internal` (or as an axum middleware layer) specifically for expensive query sub-types (`CallFunction`, `ViewState`). A per-IP or global concurrency cap on `ClientQuery` messages dispatched to `ViewClientActor` would prevent thread exhaustion without a protocol change.

---

### Proof of Concept

import asyncio, aiohttp, json

TARGET = "http://<node>/"
PAYLOAD = json.dumps({
    "jsonrpc": "2.0", "id": "x", "method": "query",
    "params": {
        "request_type": "call_function",
        "finality": "final",
        "account_id": "<contract_with_heavy_view>",
        "method_name": "heavy_view",
        "args_base64": ""
    }
})

async def flood():
    async with aiohttp.ClientSession() as s:
        await asyncio.gather(*[
            s.post(TARGET, data=PAYLOAD,
                   headers={"Content-Type": "application/json"})
            for _ in range(500)
        ])

asyncio.run(flood())
# After this, legitimate `block` / `tx` / `validators` RPC calls time out
# because all ViewClientActor threads are occupied with WASM execution.
