### Title
Fork-dependent poison-microblock report causes non-deterministic `MinerReward` for the same matured block, triggering a fatal `assert_eq!` panic that halts only nodes that observe both forks - ([File: stackslib/src/chainstate/stacks/db/accounts.rs])

### Summary
`find_mature_miner_rewards` computes a block's matured reward by checking `get_poison_microblock_report(clarity_tx, reward_height)` against the *current* fork's Clarity state, not against state that is fixed at the shared ancestor block. If a poison-microblock report is filed on one fork but not on a sibling fork that shares the same matured `(parent_block_id, child_block_id)`, the two forks compute two different `MinerReward` values for the identical key, and `inner_insert_matured_miner_reward`'s `assert_eq!` at line 515 panics for any node that processes both forks, while nodes that only see one fork continue running.

### Finding Description
The broken equality is: `MinerReward computed for (parent_block_id, child_block_id) on fork X == MinerReward computed for (parent_block_id, child_block_id) on fork Y`, which the code itself assumes must hold — the comment at [1](#0-0)  states "the only time it's okay to re-insert the same reward is if there are two Stacks forks trying to store the same matured rewards for a common ancestor block," and the code enforces this with a hard `assert_eq!` rather than tolerating disagreement: [2](#0-1) 

The reward is computed in `find_mature_miner_rewards`, which looks up the poison-microblock report for `reward_height` using the *current tip's* `clarity_tx`, not a value pinned to the ancestor block being matured: [3](#0-2) 

That lookup result (`poison_recipient_opt`) is fed into `calculate_miner_reward`, which changes who gets the coinbase/fees (the original miner vs. the poison reporter) based on whether a report is present: [4](#0-3) 

Because `MINER_REWARD_MATURITY` imposes a delay between when a block is mined (`reward_height`) and when its reward matures (`tip_stacks_height`), a poison-microblock report referencing an equivocation at `reward_height` can legally be broadcast and mined in *any* block within that maturity window — i.e., in blocks that only exist on one of two sibling forks that diverge after `reward_height` but before maturation. An attacker (a miner or minority participant) can:
1. Mine a block at `reward_height` with an equivocating (forked) microblock stream.
2. Extend two competing tenures/forks from that point (fork X and fork Y), both sharing the same `parent_block_id`/`child_block_id` for the block at `reward_height`.
3. Submit a valid `PoisonMicroblock` report transaction only into fork X within the maturity window.
4. Let both forks mature the reward for the same `(parent_block_id, child_block_id)` key — fork X routes the reward to the poison reporter, fork Y routes it to the original miner/parent.

Any node (including the attacker's own, or an archive/relay node) that processes and appends blocks from both fork X and fork Y far enough to reach maturation on each will attempt two `INSERT`s for the same key with differing `MinerReward` content, hitting the `assert_eq!` panic and crashing the process. Nodes that only ever see one of the two forks (e.g., because the losing fork stops being relayed) never observe the conflict and keep running — this is the "verdict on node A != verdict on node B" divergence: some nodes halt, others don't, for the same underlying attacker-crafted history.

Existing guards do not prevent this: `check_tenure_tx`/`verify_signer_signatures`/VRF/static validators operate on block validity, not on reward-schedule agreement across forks, and there is no mechanism that pins the poison-report visibility to the ancestor block rather than to the querying fork's live Clarity tip.

### Impact Explanation
This is a chain-halting divergence: a subset of nodes (any node that has processed/validated both sibling forks up to the maturation point) crashes via `panic!` from the `assert_eq!`, while other nodes continue operating normally on whichever single fork they saw. This matches the Critical category "chain split or deep fork" in effect, since it produces inconsistent process liveness across the network triggered by a deterministic, attacker-controlled input (which fork includes the poison report), not by node misconfiguration. It does not by itself steal funds, but it can persistently take a portion of honest nodes offline whenever they track both forks, which can happen during any real reorg near the maturity window.

### Likelihood Explanation
Preconditions: the attacker needs the ability to produce a microblock equivocation (achievable with a single miner slot — an attacker who wins one sortition and orphans/forks their own microblock stream), then extend two forks from that block and get a `PoisonMicroblock` report transaction included on only one of them within the `MINER_REWARD_MATURITY` window. No majority stake, signer set, or admin access is required — filing a poison report and forking one's own tenure are both actions available to an ordinary unprivileged participant. The main uncertainty (not fully confirmed in this review due to tool-call limits) is the precise mechanics of how/when a `PoisonMicroblock` transaction becomes associated with `reward_height` in `transactions.rs`, i.e., whether there is an additional constraint that ties the report strictly to blocks that are common to both forks (which would neutralize this issue). The `get_poison_microblock_report(clarity_tx, reward_height)` call being evaluated against the *current* fork's Clarity connection at maturation time, rather than a value fixed at the ancestor block, is the concrete piece of evidence in `accounts.rs` supporting the divergence, but the full round-trip through `RecordPoisonMicroblock` handling in `transactions.rs` was not traced to completion.

### Recommendation
Pin the poison-microblock report lookup used for reward maturation to the ancestor block being matured (e.g., record/consult the report as of the block at `reward_height` itself, or require any valid report to be present in the shared ancestor history of every fork that could later re-mature the same key) rather than resolving it against the current tip's live Clarity state. Additionally, replace the `assert_eq!` in `inner_insert_matured_miner_reward` with a non-panicking error path so that a detected divergence produces a recoverable `Error` instead of crashing the node process, and add telemetry to detect the divergence proactively rather than fatally.

### Proof of Concept
Rust integration test plan (two-fork harness):
1. Build a local two-node/two-fork chainstate harness (as used in existing Nakamoto/staging tests) that mines a shared prefix of tenures up to and including a block `B` at height `reward_height`, including a deliberately forked (equivocating) microblock stream from `B`'s miner.
2. From the block following `B`, fork the chainstate into fork X and fork Y sharing the same `parent_block_id`/`child_block_id` for `B`.
3. In fork X only, include a valid `PoisonMicroblock` transaction reporting the equivocation from `B`; in fork Y, include no such transaction.
4. Advance both forks by `MINER_REWARD_MATURITY` blocks so each independently calls `find_mature_miner_rewards` for `B`'s reward.
5. Assert: `reward_X = MinerReward computed on fork X` has `recipient == poison_reporter`; `reward_Y = MinerReward computed on fork Y` has `recipient == original_miner`; assert `reward_X != reward_Y`.
6. Feed both `insert_matured_child_miner_reward` calls (one from each fork's processing) into the same underlying `matured_rewards` table/DB transaction sequence (simulating a node that tracked both forks) and assert that the second call panics via the `assert_eq!` at `accounts.rs:515`, while a control run that only replays fork Y's blocks completes without panicking — demonstrating the node-to-node divergence in liveness.
