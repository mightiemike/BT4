### Title
Unbounded recursion in JSON-RPC request parsing via `serde_json::Value` can crash the RPC server with a stack overflow - ([File: chain/jsonrpc-primitives/src/message.rs])

### Summary
The ImageMagick advisory (CVE-2025-68618) is a CWE-674 "uncontrolled recursion" bug: parsing an SVG with deeply nested elements causes unbounded recursive descent in `SVGStartElement`, overflowing the stack. The analogous pattern in nearcore's public JSON-RPC endpoint is the untrusted `Request.params` field, typed as `serde_json::Value`, which is deserialized with the stock recursive-descent `serde_json` deserializer with no explicit nesting-depth limit.

### Finding Description
`Request` (the top-level JSON-RPC request object) declares `params: Value` [1](#0-0) , and the wire message is parsed with `serde_json::de::from_slice::<WireMessage>` in `from_slice()` [2](#0-1) . `serde_json::Value`'s `Deserialize` implementation recurses once per nesting level for arrays/objects (e.g. `[[[[...]]]]`), and `serde_json` does not impose a nesting-depth limit by default. This is functionally the same bug class as the SVG parser's `SVGStartElement`/`ResizeQuantumMemory` recursion in the report: an attacker-controlled, deeply-nested input structure drives unbounded native-stack recursion in a library's recursive-descent parser, with no depth cap enforced by the calling application before or during parsing.

I was not able to confirm within the index whether the JSON-RPC HTTP layer (`chain/jsonrpc/src/lib.rs`, using Axum) applies any body-size limit *before* invoking the JSON decoder, nor whether `serde_json`'s crate-level recursion behavior is otherwise constrained (e.g. via a wrapping bounded-depth deserializer). The wiki-derived architecture notes mention "request body size limit (default 10MB)" as middleware, but I could not locate the exact `DefaultBodyLimit`/`RequestBodyLimitLayer` wiring or its value in the indexed source to confirm the limit is actually applied ahead of parsing, or that 10MB is insufficient to reach a stack-overflow-inducing nesting depth (a payload like `"["*N` needs only a few bytes per nesting level, so tens of thousands of nesting levels — vastly less than 10MB — is enough to overflow a typical thread stack).

### Impact Explanation
A single unauthenticated HTTP POST to the JSON-RPC endpoint (`/`, handled by `process()`/`process_request()` per `chain/jsonrpc/src/lib.rs`) with deeply nested JSON in `params` (or in the top-level message body before `Request` is even distinguished from `Broken`) could exhaust the native call stack during `serde_json` deserialization. In Rust, a stack overflow triggers an abort (SIGSEGV/segfault), which is not a recoverable `Result`/panic — it terminates the process handling the request. Depending on how the RPC server is deployed (in-process with the validator/chunk-producing node vs. a separate proxy process), this could translate into a transaction/request-triggered halt of node availability, which is explicitly in scope as a valid impact category (transaction-triggered halt).

### Likelihood Explanation
This is reachable by any unauthenticated RPC caller with no prerequisites (no valid transaction, no account, no gas cost) — it only requires sending one HTTP request to a public JSON-RPC endpoint. However, I could not confirm from the available code index whether the Axum body-size limit or any pre-parse depth/size validation would prevent reaching stack-overflow depths, so the likelihood of this being currently exploitable is **uncertain** — it depends on middleware/config details I was unable to verify (specifically the exact body-limit wiring in `chain/jsonrpc/src/lib.rs`).

### Recommendation
Given the incomplete verification, I cannot assert with confidence that this is an unmitigated, exploitable vulnerability in the current codebase; the analog to the ImageMagick bug class is architecturally plausible (recursive-descent parsing of attacker-controlled untrusted, deeply-nestable input with no depth cap) but I could not confirm the absence of a depth-limiting layer. A background engineering session with full repository access would be needed to inspect the exact Axum router/middleware setup and confirm whether `DefaultBodyLimit`/other guards are sufficient, and if not, to introduce an explicit JSON nesting-depth limit (e.g., a bounded-depth `Deserializer` wrapper or a pre-scan depth check) ahead of `serde_json::de::from_slice` in `chain/jsonrpc-primitives/src/message.rs`.

### Proof of Concept
Not independently verified end-to-end due to inability to confirm the exact Axum body-size-limit configuration in this index; conceptually: `curl -X POST http://<node>:3030 -d '{"jsonrpc":"2.0","id":1,"method":"query","params":' + ("["*N) + ...`, where `N` is large enough to overflow the RPC-handling thread's stack, well under any multi-MB body cap.
