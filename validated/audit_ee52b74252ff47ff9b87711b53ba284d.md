### Title
Fund-migration TSS signing hash depends on a live, attacker-donatable balance, allowing permanent DoS of fund migration finalization - ([File: universalClient/chains/evm/tx_builder.go], [File: universalClient/tss/coordinator/coordinator.go], [File: universalClient/tss/sessionmanager/sessionmanager.go])

### Summary
The reported bug is a class of "balance-derived strict-equality check that an unprivileged attacker can corrupt by donating funds to a monitored address, causing a finalization step to fail forever." The Push Chain analog is the fund-migration signing flow in `x/utss`/`universalClient/tss`: the transfer amount swept from the old TSS address to the new TSS address is computed from a live external-chain balance query, independently re-queried by the coordinator and by each Universal Validator during signature verification. Because the old TSS address is a normal, publicly known address on the external chain, anyone can send it a deposit between these independent queries, causing the computed `SigningHash`/`TSSFundMigrationAmount` to diverge across validators and the DKLS signing session to fail its cross-validator hash check.

### Finding Description
`GetFundMigrationSigningRequest` in [1](#0-0)  computes the amount to sweep as `balance - gasCost - l1GasFee`, where `balance` is fetched live via `tb.rpcClient.GetBalance(ctx, fromAddr)` whenever `data.Balance` is not pre-supplied. This amount feeds directly into the transaction's `SigningHash` (`signer.Hash(tx)`).

The coordinator computes this signing request once, when creating the DKLS setup message, with `claimedAmount == nil` — i.e., always by querying the live chain balance: [2](#0-1) 

Independently, every participating Universal Validator re-derives the *same* signing request for verification in `verifyFundMigrationSigningRequest`, again without supplying a pinned balance — it also calls `GetFundMigrationSigningRequest`, which re-queries the live chain balance at whatever time that particular validator's `SessionManager` happens to run the check: [3](#0-2) 

The code even documents the load-bearing (but false) assumption that removes the race: *"Fund migration only triggers when outbound is disabled and no pending outbounds remain, so the balance at signing time will equal the balance at broadcast time."* [4](#0-3)  — this only guards against Push Chain's own outbound activity changing the balance; it does not, and cannot, prevent an arbitrary external-chain account from sending a deposit directly to the old TSS address, which is a normal, receive-capable address with a publicly known/derivable value (`DeriveEVMAddressFromPubkey(migrationData.OldTssPubkey)`).

If an attacker sends any amount of the native asset to the old TSS address between the coordinator's initial balance query (when building the setup message) and a given validator's independent re-query (during `verifyFundMigrationSigningRequest`), that validator computes a different `maxTransfer` and thus a different `SigningHash`/`TSSFundMigrationAmount` than the coordinator announced: [5](#0-4) 
This causes the validator to reject the signing request outright ("fund migration signing hash mismatch"), refusing to participate in that DKLS signing round. This mirrors the HarTokenSale pattern exactly: a strict equality (`bytes.Equal` on the hash, and `Cmp() != 0` on the amount) is derived from a balance an unprivileged attacker can move by directly transferring funds to a chain address the protocol is about to act on, and a mismatch permanently blocks the finalization the check exists to protect.

### Impact Explanation
Because DKLS signing requires a quorum/threshold of validators to independently verify and sign the same message, an attacker who can cause even a handful of validators to see a different balance than the coordinator (by donating dust to the old TSS address at an unpredictable moment, then repeating on every retry) can prevent the threshold from ever being reached. This blocks `FundMigration` finalization for that (old_key, chain) pair indefinitely — locked funds under the old TSS key can never be swept to the new key, and repeated `KEYGEN` rotations leave stranded balances on external chains. This is a denial of service against a core TSS coordination flow, reachable purely by sending an ordinary external-chain transaction (no privileged access, no malicious validator/relayer needed), which fits the in-scope "denial of service ... reachable without privileged control" and "TSS coordination" categories.

### Likelihood Explanation
The old TSS address and the fact that a migration is pending are both derivable from on-chain data (`FundMigrationInitiatedEventData` carries `OldTssPubkey`), so an attacker only needs to watch for `FundMigrationInitiated` events and send a cheap native-asset transfer to the old TSS address at any point during the (potentially multi-round, multi-second) DKLS signing ceremony. Because there is no synchronization pinning the balance read across coordinator and validators, this race does not require precise timing against a mempool transaction — any deposit landing between the various independent `GetBalance` calls across the validator set is sufficient, and the attacker can simply repeat the donation on every retry.

### Recommendation
Do not let each validator independently re-query a mutable, attacker-writable balance to reconstruct the signing hash. Instead:
1. Have the coordinator commit to a specific `TSSFundMigrationAmount` (and the balance it was derived from) as part of the signed setup message, and have participants verify the *coordinator-supplied* amount against a chain-state proof/threshold instead of recomputing an independent live balance.
2. Alternatively, snapshot the old-TSS balance at a fixed, agreed block height/timestamp shared by all validators, and reject any migration if the balance changes before broadcast (falling back to a fresh, re-agreed round) rather than only comparing hashes for equality that may spuriously fail.
3. Ensure the reconciliation/ACK path (`claimedAmount` reconstruction in `rebuildSigningHash`) is the *only* way amount is derived post-setup, and make the primary verification path in `verifyFundMigrationSigningRequest` use the coordinator's announced amount plus a tolerance/deterministic snapshot rather than a fresh `GetBalance` call.

### Proof of Concept
1. Admin/UV set initiates a `KEYGEN`, producing a `FundMigrationInitiated` event for `(oldTssPubkey, chain)`; the old TSS EVM address is derivable via `DeriveEVMAddressFromPubkey`.
2. The coordinator on validator A builds the setup message, calling `createFundMigrationSignSetup` → `buildFundMigrationTransaction` → `GetFundMigrationSigningRequest`, which reads `balance_1` from the old TSS address and computes `SigningHash_1` embedding `maxTransfer_1 = balance_1 - gas - l1Fee`. This is broadcast to all participants ( [6](#0-5) ).
3. An external, unprivileged actor sends a plain native-token transfer to the old TSS address on the source chain right after step 2.
4. Validator B receives the setup message and calls `verifyFundMigrationSigningRequest`, which independently calls `GetFundMigrationSigningRequest` again; it now reads `balance_2 = balance_1 + donation`, computing `SigningHash_2 != SigningHash_1` ( [7](#0-6) ).
5. Validator B's hash comparison fails and it refuses to sign; repeating the donation before every retry attempt keeps enough validators from converging, preventing the threshold from ever being met and permanently stalling this fund migration.

```go
func (tb *TxBuilder) GetFundMigrationSigningRequest(ctx context.Context, data *common.FundMigrationData, nonce uint64) (*common.UnsignedSigningReq, error) {
	fromAddr := ethcommon.HexToAddress(data.From)
	toAddr := ethcommon.HexToAddress(data.To)

	if data.GasPrice == nil || data.GasPrice.Sign() == 0 {
		return nil, fmt.Errorf("gas price must be provided for fund migration")
	}
	if data.GasLimit == 0 {
		return nil, fmt.Errorf("gas limit must be provided for fund migration")
	}

	var balance *big.Int
	if data.Balance != nil {
		balance = new(big.Int).Set(data.Balance)
	} else {
		queried, err := tb.rpcClient.GetBalance(ctx, fromAddr)
		if err != nil {
			return nil, fmt.Errorf("failed to get balance of %s: %w", data.From, err)
		}
		balance = queried
	}

	maxTransfer, err := computeFundMigrationTransfer(balance, data.GasPrice, data.GasLimit, data.L1GasFee)
	if err != nil {
		return nil, err
	}

	tb.logger.Debug().
		Str("from", data.From).
		Str("to", data.To).
		Str("balance", balance.String()).
		Str("gas_price", data.GasPrice.String()).
		Uint64("gas_limit", data.GasLimit).
		Str("l1_gas_fee", l1GasFeeString(data.L1GasFee)).
		Str("transfer_amount", maxTransfer.String()).
		Msg("building fund migration tx")

	tx := types.NewTransaction(
		nonce,
		toAddr,
		maxTransfer,
		data.GasLimit,
		data.GasPrice,
		nil, // no calldata for simple transfer
	)

	signer := types.NewEIP155Signer(big.NewInt(tb.chainIDInt))
	txHash := signer.Hash(tx).Bytes()

	// TSSFundMigrationAmount rides alongside Nonce in the req — both are signing-time-decided
	// values that must reach broadcast unchanged so the signed tx is reproduced exactly.
	return &common.UnsignedSigningReq{
		SigningHash:            txHash,
		Nonce:                  nonce,
		TSSFundMigrationAmount: new(big.Int).Set(maxTransfer),
	}, nil
```
