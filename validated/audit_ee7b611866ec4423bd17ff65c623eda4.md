**Rationale:** The premise in the question conflates a test-only code path with production behavior. In `third_party/move/move-core/types/src/safe_serialize.rs`, the serialize limit is defined as:

```rust
const MAX_TYPE_TAG_NESTING_WHEN_SERIALIZING: u8 =
    MAX_TYPE_TAG_NESTING + if cfg!(test) { 1 } else { 0 };
``` [1](#0-0) 

`cfg!(test)` is only `true` when the crate is compiled as a unit-test binary (via `cargo test`); it is never `true` in a release/production node binary, and it is not a runtime feature flag that could "drift" between deployed node versions as the question hypothesizes — it's resolved at compile time based on the build profile, not a feature-gated constant. In any real production build, `MAX_TYPE_TAG_NESTING_WHEN_SERIALIZING` equals `MAX_TYPE_TAG_NESTING` (8), so `type_tag_recursive_serialize` and `type_tag_recursive_deserialize` share exactly the same bound in every honest validator's production binary. [2](#0-1) 

The unit test `test_nested_type_tag_struct_serde` explicitly documents that the "serialize accepts one more level than deserialize" behavior exists only "for this test" (i.e., under `cfg(test)`), confirming this asymmetry is intentional test scaffolding to probe the boundary, not a production code path. [3](#0-2) 

Since all mainnet validators run release binaries (not `cfg(test)` builds) and `MAX_TYPE_TAG_NESTING` is a hardcoded `pub(crate) const` (not runtime-configurable, not behind an on-chain or CLI feature flag), there is no mechanism by which unprivileged write-set bytes could serialize successfully on one honest validator but fail deserialization on another honest validator due to this constant — both sides of the round-trip use the identical value 8 in production. The scenario of "feature-flag drift between node versions" affecting this specific constant is not substantiated by the code; it is a fixed compile-time value shared by the whole binary.

Separately, `parser.rs`'s `parse_type_tag` also references `MAX_TYPE_TAG_NESTING` for parsing string-form type tags (a different, non-BCS code path used e.g. for CLI/API text-based type parsing), with a `depth > MAX_TYPE_TAG_NESTING` check, which is consistent with (not divergent from) the BCS deserialization bound and does not introduce cross-validator state divergence. [4](#0-3) 

Since there's no code path where honest production validators would apply different effective nesting limits to the same committed bytes, the hypothesized state-integrity/hard-fork divergence does not exist in this codebase.

thread_local! {
    static TYPE_TAG_DEPTH: RefCell<u8> = const { RefCell::new(0) };

pub(crate) fn type_tag_recursive_serialize<S, T>(t: &T, s: S) -> Result<S::Ok, S::Error>
where
    S: Serializer,
    T: Serialize,
{
    use serde::ser::Error;

    // For testability, we allow to serialize one more level than deserialize.
    const MAX_TYPE_TAG_NESTING_WHEN_SERIALIZING: u8 =
        MAX_TYPE_TAG_NESTING + if cfg!(test) { 1 } else { 0 };

    TYPE_TAG_DEPTH.with(|depth| {
        let mut r = depth.borrow_mut();
        if *r >= MAX_TYPE_TAG_NESTING_WHEN_SERIALIZING {
            return Err(S::Error::custom(
                "type tag nesting exceeded during serialization",
            ));
        }
        *r += 1;
        Ok(())
    })?;
    let res = t.serialize(s);
    TYPE_TAG_DEPTH.with(|depth| {
        let mut r = depth.borrow_mut();
        *r -= 1;
    });
    res
}
