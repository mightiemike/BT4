### Title
Race condition in `performTokenExchange` can invalidate a freshly-obtained access token using a stale in-memory session, causing DoS of the token-exchange auth handler - ([File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts])

### Summary
`performTokenExchange` (and the equivalent `authenticate`/`handleClientError` logic in `shopify-app-remix`/`shopify-app-react-router` token-exchange strategies) reads a session once at the start of the request (`sessionToInvalidate = session`) and later, on a 401 from Shopify's token endpoint, blindly overwrites session storage with that stale, captured object via `invalidateAccessToken`. This is the same "read state → act on stale copy → destructive write" pattern as the SecondSwap `transferVesting`/`claim` race: a concurrent legitimate write (a successful token exchange) can be clobbered by a second, differently-timed request's error-handling write that operates on outdated data, resulting in denial of service for the shop's auth/session state.

### Finding Description
In `performTokenExchange` [1](#0-0) , the handler:
1. Loads the current session once and stores it in the outer-scoped variable `sessionToInvalidate`.
2. If the session is inactive, calls `exchangeToken` and `storeSession(offlineSession)` to persist a **fresh, valid** access token [2](#0-1) .
3. If instead the exchange throws an `HttpResponseError` with code 401, the outer `catch` unconditionally calls `invalidateAccessToken(sessionToInvalidate, config)`, which sets `session.accessToken = undefined` on the **stale, pre-exchange snapshot** and calls `storeSession` again [3](#0-2) [4](#0-3) .

Because `storeSession` is a blind upsert keyed by session id (see e.g. `DrizzleSessionStorage*`, `RedisSessionStorage`, `MongoDBSessionStorage` implementations, all of which simply overwrite the row/document for that id) [5](#0-4) , there is no optimistic-concurrency check between the read in step 1 and the write in step 3. If two concurrent requests for the same shop/session id are in flight (e.g. a document load and a background `fetch` from App Bridge, both racing after an expired offline token, which is an expected and documented scenario per `WITHIN_MILLISECONDS_OF_EXPIRY`/retry semantics), the following interleaving is possible:

- Request A and Request B both load the same stale/expired session (`sessionToInvalidate_A == sessionToInvalidate_B`, both without a valid access token yet, or with the old expired token).
- Request A successfully performs `tokenExchange` and calls `storeSession(offlineSession)` with a brand-new, valid access token.
- Request B's `tokenExchange` call fails with a 401 (transient failure, or Shopify rejecting a slightly-stale `id_token` used by B) and B's catch handler invokes `invalidateAccessToken(sessionToInvalidate_B, config)`, which stores B's stale copy (accessToken explicitly nulled) for the same session id — overwriting A's just-obtained valid token.

The same read-old/write-stale pattern exists in the remix/react-router equivalents via `invalidateAccessToken` used from `handleClientError` in the token-exchange strategy [6](#0-5)  and `invalidateAccessToken(params, session)` helper [7](#0-6) , where `session` is the object bound at the start of the request/authenticate call, not re-fetched immediately before the destructive write.

### Impact Explanation
The net effect mirrors the vesting DoS: a legitimate, successfully-committed state change (a freshly minted, valid offline/online access token) can be wiped out by a second request's error path acting on outdated data. This forces the app into a broken authentication state for that shop/session id — every subsequent API call using the (just-nulled) session will fail until the client goes through another full token-exchange/reauth cycle, and in the interim other concurrent operations relying on `hasValidAccessToken`/`isActive` checks will be denied. This is a denial-of-service of the authentication handler for a legitimate merchant. It does not itself allow forging a session or leaking secrets, so it should be scoped as a reliability/DoS issue rather than a bypass.

### Likelihood Explanation
Likelihood is analogous to the original report's characterization: it requires a specific timing window between two concurrent requests that both trigger the token-exchange retry path for the same session id, plus one of them receiving a 401 from Shopify (rather than a decode/JWT invalid-subject-token error, which is handled separately and does not invalidate the token). This is not attacker-controlled in the classic sense — it's triggered by ordinary concurrent client behavior (multiple tabs, prefetch + main document load, or fast repeated fetches during token expiry) combined with a transient 401 from Shopify's OAuth endpoint. This matches the judged severity of the original finding (Medium: low-probability but real, with tangible impact when it happens).

### Recommendation
Avoid overwriting session storage with a stale in-memory snapshot. Before invalidating, re-load the session immediately prior to the write (or use a compare-and-swap / conditional update keyed on the access token value or a version/updated-at field) so that `invalidateAccessToken` only clears the token it actually observed failing, and never clobbers a token that a concurrent request has since refreshed successfully. Alternatively, serialize token-exchange attempts per session id (e.g., via the existing `idempotentPromiseHandler` pattern already used for `afterAuth`) so only one exchange/invalidate operation can mutate a given session id at a time.

### Proof of Concept
Not independently reproducible without a live two-request race against the sandboxed session storage and a way to force one of the two token-exchange calls to receive an HTTP 401 from Shopify while the other succeeds; this requires runtime/integration testing (e.g., mocking `api.auth.tokenExchange` to succeed on one concurrent call and reject with a 401 `HttpResponseError` on another for the same `sessionId`, then asserting the stored session's `accessToken` was wiped after the successful one persisted). This should be validated with a Devin session running the existing Jest suite in `packages/apps/shopify-app-express/src/middlewares/__tests__/perform-token-exchange.test.ts` with an added concurrency test, since the ask-only index does not let me execute code to confirm the exact interleaving outcome.

import {Session} from '@shopify/shopify-api';

import type {BasicParams} from '../../types';

export async function invalidateAccessToken(
  params: BasicParams,
  session: Session,
): Promise<void> {
  const {logger, config} = params;

  logger.debug(`Invalidating access token for session - ${session.id}`, {
    shop: session.shop,
  });

  session.accessToken = undefined;
  await config.sessionStorage!.storeSession(session);
}
