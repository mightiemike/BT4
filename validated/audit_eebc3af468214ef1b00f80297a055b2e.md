## #Title
AccountPermissionUpdateActuator permanently locks account permissions by allowing the zero/blackhole-style address as a key with no admin-recoverability check — analogous to `LibOwnable._setAdmin` accepting `address(0)` (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The reported bug class is that `LibOwnable._setAdmin` lets a privileged caller set the admin to `address(0)`, silently bricking all admin-gated functionality because no one can ever satisfy that admin check again. The java-tron analog is `AccountPermissionUpdateActuator.checkPermission`, which only validates a permission key's address via `DecodeUtil.addressValid`, a check that verifies address length/prefix but never excludes the "zero address" (prefix byte + 20 zero bytes). This is the exact same byte pattern the codebase itself uses elsewhere to intentionally and permanently disable an account's owner permission.

### Finding Description
`AccountPermissionUpdateActuator.checkPermission` validates each `Key` in a `Permission` only for address format, non-zero weight, distinctness, and threshold arithmetic: [1](#0-0) 

The address-format check is `DecodeUtil.addressValid`, which only checks length (21 bytes) and the network prefix byte — it does not reject the "prefix + all-zero" address: [2](#0-1) 

That this exact zero-filled address is a known "burn"/unrecoverable key is proven by `Manager.resetBlackholeAccountPermission`, which deliberately sets the blackhole account's owner permission key to this address specifically so nobody can ever control it again: [3](#0-2) 

Because `AccountPermissionUpdateActuator` does not special-case or forbid this address (or any other address for which no signer can ever exist) when a user sets their own `owner`/`witness`/`active` permission, an account owner (or anyone signing with sufficient weight in the current owner permission) can update their own owner permission's key list to only contain this unrecoverable address. `AccountCapsule.updatePermissions` then persists it as the new owner permission with no further validation: [4](#0-3) 

Once persisted, signature verification for that account's owner permission (id 0) can never succeed, since `TransactionCapsule.checkWeight`/`getWeight` requires a signature recovering to one of the permission's key addresses, and nobody holds the private key that hashes to the all-zero address: [5](#0-4) [6](#0-5) 

This is functionally identical to `LibOwnable._setAdmin(address(0))`: a state-mutating, permission-gated setter accepts a "black hole" identity without any check, permanently disabling the very admin-controlled functionality (further permission updates, and any active-permission-gated contract calls) that the setter itself is supposed to protect.

### Impact Explanation
Any account whose owner permission is updated to only contain the zero/burn address loses the ability to ever again call `AccountPermissionUpdateContract` (to fix the permission) or any contract requiring owner-permission or now-orphaned active-permission signatures, permanently freezing account control and any TRX/TRC10/resources reachable only via that permission's signing key set. This is reachable via a normal broadcast transaction (`AccountPermissionUpdateContract`) processed by `AccountPermissionUpdateActuator.execute`, which is invoked from ordinary transaction processing after `validate()` passes.

### Likelihood Explanation
Triggering requires only that the calling account currently satisfies its own owner-permission threshold (i.e., it is a self-inflicted or social-engineered action — akin to the original report's "admin sets admin to 0" pattern), which is unprivileged from the protocol's perspective: it's simply a normal `AccountPermissionUpdateContract` transaction any account holder can broadcast against their own account. No special node privilege, key leak, or malicious peer is required — anyone can permanently self-lock, and an attacker who compromises or phishes a target's signing keys can weaponize this to permanently and provably-unrecoverably disable an account rather than merely draining it.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission` (and analogous permission-setting paths), explicitly reject the reserved zero/all-zero-body address (the same value used by `Manager.resetBlackholeAccountPermission`) as a key address for `owner`/`witness`/`active` permissions, unless the target account is the designated blackhole account. Consider also warning/rejecting when the resulting permission's key set cannot be verified against any known account, mirroring the recommendation to explicitly guard against unrecoverable "admin" values.

### Proof of Concept
1. Attacker/account holder crafts an `AccountPermissionUpdateContract` for `ownerAddress = A`, with `owner` permission containing a single `Key{address = <prefix>+0x00*20, weight = 1}` and `threshold = 1`.
2. Submit via normal transaction broadcast; `AccountPermissionUpdateActuator.validate()` passes because `DecodeUtil.addressValid` only checks length/prefix (`common/src/main/java/org/tron/common/utils/DecodeUtil.java:15-33`), and `execute()` calls `AccountCapsule.updatePermissions` to persist it (`actuator/.../AccountPermissionUpdateActuator.java:47-52`, `chainbase/.../AccountCapsule.java:1301-1320`).
3. From then on, no signature can ever recover to the zero address (`TransactionCapsule.getWeight`), so `checkWeight`/`validateSignature` can never reach the threshold for account `A`'s owner permission, permanently freezing the account exactly as `Manager.resetBlackholeAccountPermission` does intentionally for the blackhole account.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
