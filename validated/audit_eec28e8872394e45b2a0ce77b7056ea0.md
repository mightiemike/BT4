### Title
Replay-verify path skips checkpoint-hash comparison, allowing undetected state divergence to be reported as a valid replay - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` — the check used by the chunk-executor's replay/verify path (backup restore verification, `db-tool`'s `replay_on_archive`, and `TransactionReplayer::enqueue_chunks` → `verify_execution`) — validates status, gas used, the per-transaction write-set hash (`state_change_hash`), and the event root hash against the recorded `TransactionInfo`, but deliberately does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is an explicit, acknowledged gap in the code itself. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` checks four items derived from the transaction's own output (status, gas, write-set hash, event root hash) [2](#0-1)  but explicitly skips the state/hot-state/position checkpoint hashes, with an in-repo TODO stating:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [3](#0-2) 

This function is used in `ChunkExecutorInner::verify_execution`, which is the code path invoked by `TransactionReplayer::enqueue_chunks` during backup verification/replay (`storage/backup/backup-cli` verify/restore flows and `db-tool`'s `replay_on_archive`/`replay_verify`): [4](#0-3) 

The `state_change_hash`/write-set hash check only proves that a given transaction's own write-set diff is self-consistent with the recorded per-transaction hash — it does **not** prove that the accumulated Sparse-Merkle-Tree root over the full account/resource state (the `state_checkpoint_hash`) matches what was actually committed to the authenticated ledger. This is a materially different invariant: the periodic checkpoint hash is the thing that actually binds "committed state" to the ledger, per `TransactionInfoV0`/`V1`'s own documentation ("The root hash of the Sparse Merkle Tree describing the world state at the end of this transaction") [5](#0-4) . If VM/state-merklization non-determinism (e.g., a bug affecting global state derivation but not an individual transaction's own write-set contents) caused a divergence, replay-verify would not detect it, because the only thing standing in for "the committed ledger state is correct" here is skipped.

By contrast, the live chunk-execution/state-sync path (`ChunkExecutorInner::update_ledger`) does correctly validate computed checkpoints against `known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints` via `DoStateCheckpoint::run()` [6](#0-5) , so nodes performing normal fast/chunk sync are protected. The gap is isolated to the offline replay/verify tooling path that reuses `ensure_match_transaction_info`.

### Impact Explanation
Replay-verify tooling (`db-tool replay-on-archive`, backup-cli's verify coordinator) exists specifically to catch state-commitment divergences — i.e., to detect hard-fork-class bugs where local execution no longer reproduces the ledger's authenticated state root. Because the checkpoint-hash fields are excluded from the comparison, this tooling can report "successful replay" for a version range even though the true state root (state/hot-state/position) diverged from the one recorded on-chain. This undermines a core proof/commitment invariant this task is scoped to protect ("Committed state that differs from the correct VM result...", "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state").

However, the practical blast radius is constrained: this affects only the detection capability of an offline verification/replay tool, not the acceptance of bad state by a live node's actual consensus/state-sync commit path (which is separately and correctly validated via `DoStateCheckpoint`). It does not by itself let an attacker corrupt mainnet committed state or forge an accepted Merkle/accumulator proof; it is a false-negative in a safety-net tool used to catch and audit determinism/hard-fork bugs after the fact.

### Likelihood Explanation
The gap is unconditionally present in the code as written (not gated behind an unreleased flag) since `ensure_match_transaction_info` is the sole invariant check for this replay path and always omits the checkpoint hashes, regardless of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. Triggering an actual undetected divergence requires an underlying non-determinism/state-merklization bug to exist that changes the global checkpoint root without altering any individual transaction's own write-set/event hashes — a comparatively rare bug class, and I could not confirm from local code whether such a bug currently exists (my search did not identify one). This is why the TODO frames it as pre-emptive hardening ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS") rather than describing an active exploit.

### Recommendation
Extend `ensure_match_transaction_info` (or its caller in `ChunkExecutorInner::verify_execution`) to compare the locally-recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values recorded in the trusted `TransactionInfo`, at least at checkpoint boundaries, before this path is relied upon for correctness auditing, and definitely before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Proof of Concept
Not applicable as a live exploit — this is a self-identified detection gap in offline replay-verify tooling rather than an exploitable path to corrupt live consensus state. The evidentiary trail is the code itself: `ensure_match_transaction_info`'s explicit omission of the three checkpoint-hash comparisons combined with the in-repo TODO acknowledging that `replay_on_archive`-style tooling can report success despite a diverged authenticated state root.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
