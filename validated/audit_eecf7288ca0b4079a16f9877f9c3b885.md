### Title
Declare-transaction front-running lets an attacker steal a pending class declaration and force the original declarer's transaction to revert - (File: `crates/blockifier/src/transaction/transactions.rs`)

### Summary
Starknet Declare transactions carry the full Sierra class bytecode, which is publicly visible in the mempool/gossip layer before it lands on-chain. Class declaration is keyed only by the deterministic `class_hash` of the bytecode, not by the sender's address. Any unprivileged actor can copy the bytecode of a pending Declare transaction they observe, submit their own Declare transaction with a higher tip so it gets sequenced first, and cause the original declarer's transaction to fail its execution with `ClassAlreadyDeclared`/`DeclareTransactionError` once it finally executes. This directly mirrors the reported bug class: an unprivileged party observing a pending transaction can consume/"use up" a shared resource (nonce in the original report, class hash here) ahead of the legitimate submitter, causing the legitimate transaction to revert.

### Finding Description
The declare execution logic enforces a "declare-once" invariant purely based on `class_hash`: [1](#0-0) 
```
fn try_declare<S: State>(...) -> TransactionExecutionResult<()> {
    match state.get_compiled_class(class_hash) {
        Err(StateError::UndeclaredClassHash(_)) => { ... declare it ... Ok(()) }
        Err(error) => Err(error)?,
        Ok(_) => {
            // Class is already declared, cannot redeclare.
            Err(TransactionExecutionError::DeclareTransactionError { class_hash })
        }
    }
}
```
The same "prev_value=0 enforces a class may be declared only once" invariant is repeated in the Starknet OS Cairo program: [2](#0-1) 

Because the class hash is a deterministic function of the bytecode and is entirely independent of the sender/account, any node that observes a Declare transaction in the mempool (or received over the mempool-P2P gossip layer, which broadcasts full `InternalRpcTransaction` objects) can extract the class bytecode and re-submit it from a different account with a more attractive tip/fee, causing the mempool's fee-priority ordering to sequence the attacker's Declare ahead of the victim's.

The mempool developers are aware of the general risk of this class of front-running and added a partial mitigation: a "declare delay" that withholds newly submitted Declare transactions from the priority queue for a configurable duration (`declare_delay`, default 1 second) before making them eligible for `get_txs`: [3](#0-2) 
```
fn add_ready_declares(&mut self) {
    let now = self.clock.now();
    while let Some((submission_time, _args)) = self.delayed_declares.front() {
        if now - self.config.static_config.declare_delay < *submission_time {
            break;
        }
        ...
    }
}
```
and a guard that rejects fee-escalation replacement attempts against a delayed declare's `(address, nonce)` slot: [4](#0-3) 

However this delay mechanism only protects the *specific `(address, nonce)` slot* of the delayed declare from being replaced by a competing transaction targeting the *same account*; it does nothing to stop an unrelated third-party account from submitting its own, independent Declare transaction carrying the identical class bytecode with a higher tip. Nothing in `validate_fee_escalation`, `validate_incoming_tx`, or `add_tx_inner` checks whether the *class hash* being declared is already pending elsewhere in the pool: [5](#0-4) 

So the victim's declare_delay window (1 second by default, configurable) is even easier for an attacker to beat: the attacker only needs to observe the victim's Declare transaction (available immediately upon gateway/gossip broadcast) and race a competing Declare with a higher tip before the delay elapses, or simply outbid on tip generally since fee-priority ordering (not FIFO) governs non-echonet mempool mode.

### Impact Explanation
When the attacker's copy of the class gets included first, the legitimate declarer's transaction proceeds to execution and fails deterministically inside `try_declare` with `DeclareTransactionError` (`ClassAlreadyDeclared`). Per `TransactionPreValidationError`/`handle_nonce` semantics, the nonce is still incremented and the fee is still charged/collected even on this kind of execution failure (see the general revert-charges-fee behavior tested in `test_revert_invoke`/nonce-increment-on-revert path in `account_transaction.rs::handle_nonce`): [6](#0-5) 

This causes concrete loss of funds for the victim (fees paid for a transaction that cannot achieve its purpose) and permanently prevents the victim from ever declaring that specific class themselves under that transaction — they must resubmit with an incremented nonce, at additional cost, while the attacker can repeat the griefing indefinitely for any Declare transaction they can see in the network, including ones from accounts/dApps repeatedly deploying identical, well-known class code (e.g., popular account or wallet implementations), and can extract MEV-like value in doing so or simply degrade UX/deployment reliability for any specific target.

### Likelihood Explanation
The attack requires no privileged access — any single unprivileged transaction submitter can execute it by monitoring the public gateway/mempool-P2P broadcast for Declare transactions, extracting the (unencrypted, public) Sierra bytecode, and re-submitting it with a marginally higher tip. This is directly reachable from a single submitted transaction. The declare_delay mitigation raises the bar only slightly (a fixed short delay, default 1 second) and does not defend against attackers who can react quickly or simply outbid via tip, since the mitigation only guards against replacement within the *same* `(sender, nonce)` slot, not against an unrelated account declaring the same class hash first.

### Recommendation
- Track pending/declared class hashes across the whole mempool (not just per `(address, nonce)`), and reject or delay a newly submitted Declare transaction whose class hash matches a class hash already pending in the pool from a different sender, or apply the existing `declare_delay` protection at the class-hash granularity rather than only at the `(sender, nonce)` granularity.
- Consider a commit-reveal declare flow, or requiring class declaration to bind to the sender address that first submitted it (e.g., an escrow/first-claim marker keyed by class hash validated at inclusion time), so a copied bytecode cannot be "raced" ahead of the original submitter.
- Alternatively, do not charge fees/increment nonce for a Declare transaction that fails purely due to `ClassAlreadyDeclared`, mitigating the fund-loss impact even if front-running cannot be fully prevented.

### Proof of Concept
1. Victim submits Declare transaction `D_v` (sender `A`, nonce `n_A`, tip `t_v`) declaring class `C` (Sierra bytecode `B`), computing `class_hash = hash(B)`.
2. Attacker observes `D_v` via gateway broadcast/mempool-P2P propagation (transactions are broadcast in full, including full class bytecode, per the tx submission flow): [7](#0-6) 
3. Attacker extracts `B`, and submits its own Declare transaction `D_a` (sender `X`, nonce `n_X`, tip `t_a > t_v (+ required margin)`) declaring the identical class `C`.
4. Because mempool is fee-priority ordered by default, `D_a` is picked by `get_txs` ahead of `D_v` (assuming attacker's tip wins and both survive/expire `declare_delay`).
5. `D_a` executes first: `try_declare` finds `UndeclaredClassHash` and successfully sets `class_hash -> compiled_class_hash` in state: [8](#0-7) 
6. `D_v` executes afterward: `try_declare` now sees `Ok(_)` (class already exists) and returns `DeclareTransactionError { class_hash }`, as also exercised in the existing regression test for redeclaration: [9](#0-8) 
7. Victim's nonce for account `A` is consumed/incremented and fee charged, despite the declare's failure, resulting in wasted funds and denial of the intended declaration.

/// Attempts to declare a contract class by setting the contract class in the state with the
/// specified class hash.
fn try_declare<S: State>(
    tx: &DeclareTransaction,
    state: &mut S,
    class_hash: ClassHash,
    compiled_class_hash: Option<CompiledClassHash>,
) -> TransactionExecutionResult<()> {
    match state.get_compiled_class(class_hash) {
        Err(StateError::UndeclaredClassHash(_)) => {
            // Class is undeclared; declare it.
            state.set_contract_class(class_hash, tx.contract_class().try_into()?)?;
            if let Some(compiled_class_hash) = compiled_class_hash {
                state.set_compiled_class_hash(class_hash, compiled_class_hash)?;
            }
            Ok(())
        }
        Err(error) => Err(error)?,
        Ok(_) => {
            // Class is already declared, cannot redeclare.
            Err(TransactionExecutionError::DeclareTransactionError { class_hash })
        }
    }
}

        &self,

    ) -> MempoolResult<Option<TransactionReference>> {

        self.validate_no_delayed_declare_front_run(incoming_tx_reference)?;

        if !self.config.static_config.enable_fee_escalation {

    fn handle_nonce(
        state: &mut dyn State,
        tx_info: &TransactionInfo,
        strict: bool,
    ) -> TransactionPreValidationResult<()> {
        if tx_info.is_v0() {
            return Ok(());
        }

        let address = tx_info.sender_address();
        let account_nonce = state.get_nonce_at(address)?;
        let incoming_tx_nonce = tx_info.nonce();
        let valid_nonce = if strict {
            account_nonce == incoming_tx_nonce

            account_nonce <= incoming_tx_nonce
        };
        if valid_nonce {
            return Ok(state.increment_nonce(address)?);
        }
        Err(TransactionPreValidationError::InvalidNonce {
            address,
            account_nonce,
            incoming_tx_nonce,
        })
    }
