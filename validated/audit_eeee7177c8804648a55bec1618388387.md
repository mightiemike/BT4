### Title
Duplicate `PCTx` Entries in `UniversalTx` via Redundant Inbound Execution - ([File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go])

### Summary
The `ExecuteInboundFundsAndPayload` function (and similar inbound execution handlers) appends new `PCTx` (Push Chain Execution) records to a `UniversalTx` without checking if a record for the same execution already exists. While the top-level `UniversalTx` creation is guarded, the internal execution flow can be triggered multiple times if consensus is reached on multiple variants or through race conditions in vote finalization, leading to corrupted accounting and duplicate execution history.

### Finding Description
In Push Chain, a `UniversalTx` (UTX) tracks the lifecycle of cross-chain transactions. When an inbound transaction is finalized via validator voting, the `uexecutor` module executes the associated logic (e.g., minting tokens, running payloads) and records these actions as `PCTx` entries.

The vulnerability lies in how `PCTx` entries are added to the UTX state. In `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, the code performs multiple `UpdateUniversalTx` calls that unconditionally append to the `PcTx` slice: [1](#0-0) [2](#0-1) [3](#0-2) 

Unlike the top-level `CreateUniversalTx` function, which correctly checks for existing keys [4](#0-3) , these internal update paths assume they are the first and only execution of that specific stage. 

If a logical inbound event has multiple variants (due to minor byte-level differences in validator observations), the system tracks them in `PendingInboundEntry.Variants`. If multiple variants independently reach quorum or if the execution logic is re-invoked (e.g., via admin-revert or manual intervention), the same UTX will accumulate duplicate `PCTx` entries for the same logical actions (e.g., two "SUCCESS" mints recorded for one inbound).

### Impact Explanation
This leads to the **corruption of canonical UniversalTx state** and accounting. Specifically:
1. **Double Accounting:** External observers and indexers relying on the `PcTx` list will see multiple execution records for a single event, potentially leading to double-counting of processed funds.
2. **State Bloat:** An attacker or a set of diverging validators can cause the `PcTx` slice to grow indefinitely by submitting variant votes that repeatedly trigger execution logic.
3. **Audit Trail Integrity:** The append-only invariant is preserved, but the lack of uniqueness checks breaks the mapping between a source event and its unique Push Chain execution receipt.

### Likelihood Explanation
The likelihood is medium. While it requires validators to submit different variants of the same inbound, the codebase explicitly acknowledges that "multiple variants may exist for the same UTX key" [5](#0-4) . If the logic that gates the transition from `PendingInbounds` to `UniversalTx` execution does not strictly ensure a "exactly-once" execution across all variants, the redundant appends will occur.

### Recommendation
Implement a uniqueness check within the `UpdateUniversalTx` closure before appending to `PcTx`. The check should verify if a `PCTx` with the same `TxHash` (or a specific execution stage identifier) already exists in the slice.

```go
updateErr := k.UpdateUniversalTx(ctx, universalTxKey, func(utx *types.UniversalTx) error {
    for _, existing := range utx.PcTx {
        if existing.TxHash == depositPcTx.TxHash {
            return nil // Already recorded
        }
    }
    utx.PcTx = append(utx.PcTx, &depositPcTx)
    return nil
})
```

### Proof of Concept
1. Setup a network with 4 validators.
2. Submit `MsgVoteInbound` for Variant A (lowercase addresses) from Validators 1, 2, and 3. Quorum is reached, `ExecuteInboundFundsAndPayload` runs, and appends `PCTx` (Mint) to the UTX.
3. Submit `MsgVoteInbound` for Variant B (EIP-55 addresses) from Validators 2, 3, and 4. 
4. If the variant-handling logic triggers execution for the second finalized variant of the same logical UTX ID, the `UpdateUniversalTx` call will append a second, identical `PCTx` entry to the same UTX record, even though the minting only happened once or failed the second time at the EVM level.
5. Query `GetUniversalTx` to observe the `PcTx` slice containing duplicate or redundant execution records. [6](#0-5)
