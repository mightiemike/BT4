## Analog Found

### Title
Re-freezing balance always overwrites the lock expiration with the newly supplied (potentially shorter) duration, unlocking previously-locked funds early - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java`)

### Summary
`FreezeBalanceActuator.execute()` and `FreezeBalanceProcessor.execute()` (the TVM native-contract equivalent) both accumulate the frozen amount (`frozenBalance + accountCapsule.getFrozenBalance()`), but overwrite the previous `expireTime` with a brand-new one computed only from `now + frozenDuration`, with no comparison against the existing/remaining lock time.

### Finding Description
`accountCapsule.setFrozenForBandwidth(newFrozenBalanceForBandwidth, expireTime)` (and the Energy/TronPower equivalents) replace the whole `Frozen` record — both the aggregated balance and the expire time — with the value computed from the *new* freeze request: [1](#0-0) 

The setter itself simply replaces the single `Frozen` entry unconditionally: [2](#0-1) 

The same unconditional-overwrite pattern exists in the TVM-callable `FreezeBalanceProcessor.execute()`: [3](#0-2) 

`FreezeBalanceActuator.validate()` only checks that `frozenDuration` (a fresh, independent value supplied in the new contract) is within `[minFrozenTime, maxFrozenTime]` — it never checks it against the remaining time of the account's *existing* frozen balance: [4](#0-3) 

This is functionally identical to the reported `SapienVault` bug class: a user first stakes/freezes with a long duration (e.g. `maxFrozenTime`), building up an expiration far in the future, then re-freezes any additional amount (even the minimum 1 TRX) with the minimum allowed `frozenDuration`. Because the code recomputes `expireTime = now + newDuration` and stores it as the single, authoritative expire time for the *entire* combined frozen balance (old + new), the whole balance's lock is now governed by the shorter period. The report's contract used a weighted average; this implementation is actually a stronger analog because it does a full overwrite rather than even a weighted average — the newer, shorter duration always wins outright regardless of the size of the additional freeze.

Notably, the codebase itself demonstrates awareness of this exact bug class and how to fix it, in the sibling `DelegateResourceActuator`, which explicitly enforces that a new lock period cannot be shorter than the remaining time of the existing lock via `validRemainTime()`: [5](#0-4) 
That protection is present for delegated (locked) resources but is absent from the base `FreezeBalanceActuator`/`FreezeBalanceProcessor` freeze-v1 path.

### Impact Explanation
An account can strategically shorten the lock time on its entire pre-existing frozen (staked-for-bandwidth/energy/TRON-power) balance by submitting a second `FreezeBalanceContract` (or invoking the corresponding TVM freeze precompile) with the minimum `frozenDuration` and a token amount as small as `1 TRX`. This lets the user reclaim (unfreeze) balances earlier than the network's resource/voting/staking model intends, undermining the intended commitment window used for resource pricing, TRON Power-based voting weight, and witness election stability — an accounting/consensus-relevant guarantee. This can be triggered directly via a broadcast `FreezeBalanceContract` transaction from any account, or via a smart contract calling the freeze-balance-v1 native precompile.

### Likelihood Explanation
`FreezeBalanceContract`/freeze-v1 is legacy but still reachable when `dynamicStore.supportUnfreezeDelay()` is not enabled (i.e., on chains/environments that have not migrated to freeze-v2, since the actuator explicitly rejects the v1 contract only once v2/unfreeze-delay is turned on): [6](#0-5) 
On any network still running with freeze-v1 active, any account can trigger this with a plain, unprivileged transaction requiring only ordinary account balance — no special permission is needed, making likelihood high wherever v1 freeze is still enabled.

### Recommendation
When adding to an existing frozen balance (`FreezeBalanceActuator.execute()` and `FreezeBalanceProcessor.execute()`), do not unconditionally overwrite `expireTime`. Instead, take `max(existingExpireTime, newlyComputedExpireTime)`, mirroring the `validRemainTime()` safeguard already used in `DelegateResourceActuator`, so a shorter subsequent freeze duration can never reduce the effective lock time on the combined balance.

### Proof of Concept
1. Account A submits `FreezeBalanceContract` with `frozenBalance = 1000 TRX`, `frozenDuration = maxFrozenTime` (e.g., long lock). `setFrozenForBandwidth` stores `expireTime1 = now + maxFrozenTime*FROZEN_PERIOD`.
2. Later, Account A submits a second `FreezeBalanceContract` with `frozenBalance = 1 TRX` (minimum allowed) and `frozenDuration = minFrozenTime` (minimum allowed).
3. `FreezeBalanceActuator.execute()` computes `newFrozenBalanceForBandwidth = 1 + 1000` TRX and calls `setFrozenForBandwidth(1001, now + minFrozenTime*FROZEN_PERIOD)`, replacing the single `Frozen` record.
4. The entire 1001 TRX is now governed by the much shorter `expireTime2`, and Account A can submit `UnfreezeBalanceContract` for the full amount once `expireTime2` passes — far earlier than the originally committed `expireTime1`.

  public void setFrozenForBandwidth(long frozenBalance, long expireTime) {

        .setFrozenBalance(frozenBalance)
        .setExpireTime(expireTime)
        .build();

    long frozenCount = getFrozenCount();
    if (frozenCount == 0) {
      setInstance(getInstance().toBuilder()
          .addFrozen(newFrozen)
          .build());
    } else {
      setInstance(getInstance().toBuilder()
          .setFrozen(0, newFrozen)

      );

  private void validRemainTime(ResourceCode resourceCode, long lockPeriod, long expireTime,
      long now) throws ContractValidateException {
    long remainTime = expireTime - now;
    if (lockPeriod * BLOCK_PRODUCED_INTERVAL < remainTime) {
      throw new ContractValidateException(
          "The lock period for " + resourceCode.name() + " this time cannot be less than the "
              + "remaining time[" + remainTime + "ms] of the last lock period for "
              + resourceCode.name() + "!");
    }
