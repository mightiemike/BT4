### Title
Caller's attached deposit is permanently locked when an intermediate NEP-141/registrar check promise fails in the NEAR wallet contract's `rlp_execute` flow - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract::rlp_execute` flow tracks an external caller's attached deposit in a `CallerDeposit` struct so it can be refunded if the underlying action ultimately fails. The refund logic that actually issues the transfer only exists in the terminal callback `rlp_execute_callback`. The two intermediate callbacks, `address_check_callback` and `nep_141_storage_balance_callback`, drop `caller_deposit` on the `PromiseResult::Failed` branch of their own (unrelated) sub-calls without ever forwarding it to a refund, so the caller's NEAR remains stuck in the wallet contract forever.

### Finding Description
`CallerDeposit::new` records the predecessor's attached deposit whenever `rlp_execute` is invoked by someone other than the contract's own owner (`current_account_id != predecessor_account_id`): [1](#0-0) 

For two transaction kinds — `EOABaseTokenTransfer` with an `address_check`, and `ERC20Transfer` — `inner_rlp_execute` does not go directly to the action promise. Instead it first calls an auxiliary contract (the address registrar, or the token's `storage_balance_of`) and schedules `address_check_callback` / `nep_141_storage_balance_callback` as the continuation, passing `caller_deposit` through: [2](#0-1) 

In both intermediate callbacks, if that auxiliary call fails, the function returns an error `ExecuteResponse` immediately and simply discards `caller_deposit` — no transfer is scheduled: [3](#0-2) [4](#0-3) 

By contrast, the terminal `rlp_execute_callback` — reached only when the actual action promise (not these auxiliary probes) resolves — does perform the refund on failure: [5](#0-4) 

This is structurally identical to the reported Cooler bug class: a value-handling routine exists on the "main"/expected path, but an alternate reachable path (a different callback invoked when an earlier step fails) has an empty/no-op handler for the same funds, so the funds get stuck in the contract with no code path that ever moves them out.

The only test that exercises refund behavior, `test_caller_refunds`, exercises failure of the *final* action call (through `rlp_execute_callback`), not failure of the intermediate registrar/storage-balance lookup, so this gap is untested: [6](#0-5) 

### Impact Explanation
Any external (non-owner) caller/relayer who attaches a deposit while calling `rlp_execute` for an `EOABaseTokenTransfer` targeting an unregistered eth-implicit address, or an `ERC20Transfer`, risks permanent loss of that deposit if the address-registrar lookup or the token's `storage_balance_of` call fails (e.g., due to the auxiliary contract being paused, deleted, out of gas, or otherwise erroring). The deposit remains locked in the wallet contract's balance with no code path returning it to the caller — this is a permanently frozen funds condition triggered by a single ordinary transaction.

### Likelihood Explanation
Reachable directly from a single unprivileged `FunctionCall` transaction to `rlp_execute` on any deployed wallet contract instance, requiring only that the caller is not the wallet owner and attaches a nonzero deposit while targeting an eth-implicit address requiring an address check, or performing an ERC-20 transfer. Auxiliary contract failures (registrar unavailable, or a token contract's `storage_balance_of` reverting/panicking) are a realistic occurrence in production, not a contrived edge case, making this readily triggerable without any privileged access.

### Recommendation
In `address_check_callback` and `nep_141_storage_balance_callback`, mirror the refund logic used in `rlp_execute_callback`: on `PromiseResult::Failed`, if `caller_deposit` is `Some`, schedule a transfer of `yocto_near` back to `account_id` before returning the failed `ExecuteResponse`, exactly as done in `rlp_execute_callback`'s `Failed` branch ( [5](#0-4) ). Consider factoring this into a shared helper to avoid re-introducing the gap for future intermediate callbacks.

### Proof of Concept
1. Deploy a `WalletContract` and register an `ADDRESS_REGISTRAR_ACCOUNT_ID` contract.
2. Have an external relayer account call `rlp_execute` with a nonzero attached deposit, targeting an eth-implicit `target` account with an `address_check` present, so `inner_rlp_execute` schedules `address_registrar.lookup(...).then(address_check_callback(...))` as in [7](#0-6) 
3. Cause the `lookup` call to fail (e.g., point `ADDRESS_REGISTRAR_ACCOUNT_ID` at an account with no such method deployed, or one that panics).
4. `address_check_callback` receives `PromiseResult::Failed` and returns immediately, per [3](#0-2) 
without ever transferring the caller's deposit back.
5. Observe the relayer's balance never recovers the deposit, and the wallet contract's balance permanently retains it (analogous to `test_caller_refunds` but targeting the intermediate `address_check_callback`/`nep_141_storage_balance_callback` failure paths, which the existing test at [6](#0-5) 
does not cover).

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
