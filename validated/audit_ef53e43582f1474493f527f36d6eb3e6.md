### Title
On-chain reserve-based Exchange price allows single-block sandwich manipulation - (`chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The TRX↔TRC10 bancor-style `Exchange` market in java-tron prices every swap purely from the on-chain pool reserves (`firstTokenBalance`/`secondTokenBalance`) stored in `ExchangeCapsule`, with no TWAP, oracle, or anti-manipulation mechanism. Any account can submit `ExchangeTransactionContract` transactions (via the unprivileged `ExchangeTransaction` gRPC/HTTP API), and because the swap output is a deterministic function of the current reserves at execution time, an attacker can move the pool's price with one swap and profit from — or force unfavorable pricing onto — subsequent trades within the same block, exactly the "pool reserve as price source" pattern flagged in the external report.

### Finding Description
`ExchangeCapsule.transaction()` computes the swap output solely from the current `firstTokenBalance`/`secondTokenBalance` of the `Exchange` object, feeding them into the bancor-curve `ExchangeProcessor`/`SafeExchangeProcessor`: [1](#0-0) 

The underlying pricing math (`exchangeToSupply`/`exchangeFromSupply`) is a pure function of `balance` and `quant` taken directly from the reserve state, with no external price reference: [2](#0-1) 

`ExchangeTransactionActuator` is reachable from any unprivileged, broadcast transaction (`ExchangeTransactionContract`), reads the exchange's live reserves and executes the swap against them without any block-level rate limiting, minimum-liquidity lock, or TWAP averaging: [3](#0-2) 

The only protection present is the caller-supplied `tokenExpected` slippage check, which protects the *submitter* of that specific transaction from receiving less than expected, but does nothing to prevent an attacker from shifting the reserve ratio before/after a victim's trade executes in the same block: [4](#0-3) 

This mirrors the report's root cause precisely: a market feature relies directly on spot pool-reserve ratios to price trades, and those reserves can be moved arbitrarily (here, via ordinary swap transactions rather than a flash loan) because there is no TWAP or oracle, and no protection for other participants whose trades get sandwiched.

### Impact Explanation
An attacker who can predict or influence transaction ordering within a block (e.g., by submitting multiple transactions from the same or colluding accounts, or via witness/relay-level ordering advantages) can:
1. Front-run a pending large `ExchangeTransactionContract` by swapping to shift the reserve ratio unfavorably for the victim.
2. Let the victim's trade execute at the manipulated price.
3. Back-run by reversing the swap, extracting the victim's loss as profit.

This results in economic loss for legitimate `Exchange` users (over/under-paying for TRX or TRC10 tokens) — a direct asset/accounting corruption for affected accounts, purely through unprivileged, publicly reachable transactions.

### Likelihood Explanation
Any account can call `ExchangeTransaction` at any time with no special permission, and the pricing function is fully deterministic given the reserves, making manipulation mechanically simple to execute. The primary constraint is control over transaction ordering within a block, which is a normal capability for well-resourced or colluding participants (and trivially achievable for self-sandwiching one's own two transactions when a witness includes both, or across the same block via fee/priority). No flash loan is even required, unlike the referenced report, because pool balances themselves are the manipulable state and swaps directly move them.

### Recommendation
- Add a time-weighted average price (TWAP) component, or a minimum number of blocks/settlement delay between manipulating and consuming a given price level, for the `Exchange` module's swap pricing.
- Consider deprecating/disabling the legacy bancor `Exchange` (`ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`) pricing model in favor of the order-book based `Market` (`MarketSellAssetActuator`) which is not subject to reserve-manipulation in the same way.
- If the legacy Exchange must remain active, expose stricter slippage/price-impact limits enforced at the protocol level (not just caller-supplied `tokenExpected`), and consider rate-limiting reserve-ratio changes per block.

### Proof of Concept
1. Attacker observes/anticipates a victim's pending `ExchangeTransactionContract` swapping token A for token B on exchange `E` (reserves `firstTokenBalance`, `secondTokenBalance`).
2. Attacker submits an `ExchangeTransactionContract` swapping a large amount of A into E, shifting the ratio so B becomes more expensive, exploiting `ExchangeCapsule.transaction()`'s pure dependence on live reserves: [5](#0-4) 
3. Victim's swap executes against the now-worse ratio (still passes because `tokenExpected` was set loosely or the victim used default expectations).
4. Attacker submits a reverse swap (B back to A) immediately after, capturing the price differential as profit, with `ExchangeTransactionActuator` performing no cross-transaction/cross-block price sanity checks: [6](#0-5)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
