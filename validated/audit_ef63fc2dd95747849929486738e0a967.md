### Title
Denial-of-Service via unbounded `BigDecimal` scientific-notation exponent in HTTP API numeric field parsing - (File: `framework/src/main/java/org/tron/core/services/http/Util.java`)

### Summary
The external report describes a client-side crash caused by large numeric input being auto-converted to scientific notation, which the front-end failed to handle. The equivalent, reachable server-side analog exists in java-tron's Full Node HTTP API: numeric transaction fields (e.g. `call_value`, `fee_limit`, `call_token_value`, `token_id`) are parsed from raw JSON via `Util.getJsonLongValue`, which pulls a `BigDecimal` out of the request and calls `longValueExact()` without first bounding the value's magnitude or scale.

### Finding Description
`Util.getJsonLongValue` retrieves the field as a `BigDecimal` and immediately calls `longValueExact()`: [1](#0-0) 

The underlying JSON layer (`org.tron.json.JSON`) is configured with `USE_BIG_DECIMAL_FOR_FLOATS` enabled and only constrains nesting depth and token count — there is no limit on the numeric exponent/scale of a parsed number: [2](#0-1) 

An attacker can submit a JSON body such as `{"call_value": "1e2147483000", ...}` to an unauthenticated HTTP API endpoint that uses `Util.getJsonLongValue` on attacker-controlled fields, e.g. `DeployContractServlet`: [3](#0-2) [4](#0-3) [5](#0-4) 

The literal string parses cheaply into a `BigDecimal` with `unscaledValue=1` and a very large negative `scale`, but `BigDecimal.longValueExact()` internally must normalize/rescale this value (equivalent to multiplying by `10^|scale|`), which for an exponent near `Integer.MAX_VALUE` requires an enormous `BigInteger` computation — consuming large amounts of CPU and memory on the servlet thread handling the request. `TriggerSmartContractServlet` and other servlets that call `Util.getJsonLongValue` on request-controlled numeric strings are similarly exposed (confirmed via reference in `Util.java`) [6](#0-5) , though I was not able to fully inspect `TriggerSmartContractServlet.java`'s exact call sites within this session.

This mirrors the reported bug class exactly: a numeric input silently converted to/parsed as scientific notation causes the handling process to hang/become unresponsive, except here it manifests as a node-side resource-exhaustion DoS reachable from any anonymous HTTP client rather than a browser-side JS crash.

### Impact Explanation
A single crafted HTTP POST to a Full Node's public wallet API (no authentication required) can force the servlet thread into an expensive `BigInteger`/`BigDecimal` computation, tying up CPU and heap memory. Repeated requests can exhaust worker threads or trigger `OutOfMemoryError`, degrading or crashing the node's HTTP API — a DoS against RPC-API availability. It does not directly corrupt consensus state or leak keys, but a widely-deployed public/full-node endpoint could be knocked offline.

### Likelihood Explanation
The attack requires only crafting a JSON string with an unusually large exponent and sending it to an existing, unauthenticated HTTP endpoint (e.g. `/wallet/deploycontract`). No special privileges, timing, or race conditions are needed, making exploitation straightforward once the endpoint is reachable.

### Recommendation
In `Util.getJsonLongValue` (and any other caller of `BigDecimal.longValueExact()`/`toBigIntegerExact()` on request-controlled values), validate the `BigDecimal`'s `precision()`/`scale()` bounds before performing exact conversions, or reject inputs whose scale magnitude exceeds a small sane threshold (e.g., reject if `Math.abs(bigDecimal.scale()) > 64`). Alternatively, parse amount-like fields as plain integers/longs rather than accepting arbitrary decimal/exponent notation from JSON.

### Proof of Concept
```
POST /wallet/deploycontract HTTP/1.1
Host: <full-node>:8090
Content-Type: application/json

{
  "owner_address": "<hex address>",
  "call_value": "1e2147483000",
  "fee_limit": 1000000,
  "bytecode": "60806040"
}
```
This triggers `Util.getJsonLongValue(jsonObject, "call_value")` → `BigDecimal.longValueExact()` on a value with an astronomically large scale, causing excessive CPU/memory consumption on the handling thread.

  public static long getJsonLongValue(JSONObject jsonObject, String key, boolean required) {
    BigDecimal bigDecimal = jsonObject.getBigDecimal(key);
    if (required && bigDecimal == null) {
      throw new InvalidParameterException("key [" + key + "] does not exist");
    }
    return (bigDecimal == null) ? 0L : bigDecimal.longValueExact();
  }
