### Title
Interest index clock advances only on change, allowing stale interest periods to be retroactively charged at the current rate - (File: mainnet/contracts/vault/v0-vault-stx.clar)

### Summary
Each Zest vault contract tracks a borrow `index` and liquidity `lindex`, refreshed via `accrue()`. The timestamp used to measure the elapsed period for interest accrual, `last-update`, is only advanced when the newly computed index actually differs from the stored one. Because the multiplier computation uses integer division (`mul-div-down`/`mul-div-up`), any block where `rate * time-delta` rounds to a multiplier equal to `INDEX-PRECISION` leaves `next == idx` (and `nliq == lidx`), and `last-update` is therefore left unchanged. Time silently accumulates against a stale anchor, and the accumulated stale duration is later applied in a single jump using whatever rate is current at that later point, rather than the (possibly much lower, or zero) rate that actually prevailed during the skipped interval.

### Finding Description
`next-index` and `next-liquidity-index` compute a new index using `interest-rate()` (from current `utilization()`) and `time-delta = stacks-block-time - last-update`: [1](#0-0) 

The multiplier arithmetic truncates: [2](#0-1) 

`accrue()` only persists `index`/`lindex` and — critically — only advances `last-update` when the index actually moved: [3](#0-2) 

Because `last-update` is the sole clock used by every subsequent `next-index`/`next-liquidity-index` call (invoked from `accrue`, itself called at the top of `deposit`, `redeem`, `system-borrow`, `system-repay`, and from the market's `accrue-and-cache`), any interval where the rounded multiplier equals `INDEX-PRECISION` (low `rate` combined with a short `time-delta`, or a zero-rate/zero-utilization period) causes the clock to freeze rather than advance. The unrecorded time is not lost — it is folded into whichever future `time-delta` eventually produces a nonzero multiplier, at whatever `rate` is prevailing at that later point in time, not the rate(s) that actually applied while the vault sat idle.

This is structurally the same defect class as the referenced report: a value (there, liquidity; here, elapsed time/rate) is captured using the state that exists *after* the relevant activity has changed, rather than accumulating the value incrementally as it actually occurred across the interval. Just as AlgebraPool "borrowed" the wrong liquidity by only reading it after the price stopped moving, Zest's vaults "borrow" the wrong rate by charging all of an untracked idle interval at the rate observed only once accrual finally becomes non-trivial.

### Impact Explanation
Debt (`index`) and yield (`lindex`) indexes govern every user's scaled debt/share value in the protocol, as well as the reserve-factor-driven `dao-treasury` minting computed inside the same `accrue()` call: [4](#0-3) 

If a stale interval is retroactively priced at a later (potentially materially different) rate, the resulting `debt-delta` used for the reserve/treasury mint, and the interest actually charged to every existing borrower in that vault, will not correspond to interest that was economically earned in real time. This misallocates yield between borrowers, suppliers, and the treasury protocol-wide (not an isolated two-user interaction), constituting theft/misallocation of unclaimed yield — an in-scope High impact per the rules ("theft of unclaimed yield ... temporary freezing of funds").

### Likelihood Explanation
The rounding condition (`mul-div-down`/`mul-div-up` producing exactly `INDEX-PRECISION`) is common in low-utilization vaults or during short block intervals with low rates, and requires no privileged access, no oracle manipulation, and no DAO action — it is a naturally occurring consequence of normal usage patterns (e.g., a period of very low or zero borrowing followed by a jump in utilization). This makes the defect readily reachable without any adversarial precondition beyond normal transaction timing, which the attacker/observer can influence by timing calls to `deposit`/`redeem`/`system-borrow` to control when the clock resumes.

### Recommendation
Advance `last-update` unconditionally on every `accrue()` invocation once the block has changed, regardless of whether the rounded index changed, so that no interval is ever silently excluded from the elapsed-time accounting; alternatively, accumulate a running remainder across calls so no fractional interest is lost or displaced onto a later, differently-rated period.

### Proof of Concept
1. Vault utilization is low enough (or rate low enough) that in consecutive blocks `calc-multiplier-delta` rounds to exactly `INDEX-PRECISION` for several blocks in a row — `next-index`/`next-liquidity-index` return unchanged values, so `accrue()`'s `(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)` branch never fires; `last-update` stays pinned at an old block time. [5](#0-4) 
2. Over subsequent blocks, borrowing activity increases utilization and the effective rate rises substantially.
3. A user calls `system-borrow`/`deposit`/`redeem`, triggering `accrue()`. `time-delta` is now `stacks-block-time - last-update`, spanning the entire pinned-stale interval (including the earlier low-utilization period). `next-index`/`next-liquidity-index` apply the current (higher) rate over that entire span. [6](#0-5) 
4. The resulting `debt-delta` is used to mint `treasury-lp` and to increase every existing borrower's `total-debt`, applying interest that was never actually accrued at the rates that prevailed during the pinned interval. [7](#0-6) 

Note: I was unable to confirm from the in-scope files whether the deployed interest-rate curve's zero-utilization point is configured as exactly `u0` (which would make the freeze condition trivially reachable at zero debt); the rounding-based freeze condition, however, does not depend on that and is reachable purely through integer-division truncation at low rate × short time-delta combinations.
