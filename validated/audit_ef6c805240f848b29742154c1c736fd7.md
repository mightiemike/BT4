## Analog Found

### Title
Relayer fee refund is paid unconditionally, before the underlying transfer/ERC-20 action is known to succeed - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract's `inner_rlp_execute` pays the relayer's fee via an immediate, independent `Promise::promise_batch_action_transfer` as soon as the Ethereum transaction is parsed into an `EOABaseTokenTransfer`/`ERC20Transfer` action — **before** the actual transfer/`ft_transfer` action is even scheduled, let alone confirmed to have succeeded. The success/failure of that action is only checked later, asynchronously, in `rlp_execute_callback`, which has no mechanism to claw back the fee that was already sent. [1](#0-0) 

### Finding Description
In `inner_rlp_execute`, once parsing succeeds and the transaction kind is determined to be `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero fee, a completely separate promise batch is created to transfer the fee to `context.predecessor_account_id` (the relayer):

```rust
if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
    env::promise_batch_action_transfer(refund_promise, *fee);
}
``` [2](#0-1) 

This receipt is completely disconnected from the promise chain that actually performs the requested transfer (built afterward via `action_to_promise(...).then(ext.rlp_execute_callback(...))`, or via the multi-step NEP-141 storage-deposit flow for `ERC20Transfer`). The eventual success/failure of that action is checked in `rlp_execute_callback` only against `PromiseResult`, and on failure it only refunds an *attached deposit* recorded in `caller_deposit` — it has no way to reclaim the fee already paid to the relayer: [3](#0-2) 

The nonce is also incremented at parse time (line 364) independent of whether the action later succeeds, so the transaction cannot be resubmitted even if it fails. Combined with the unconditional fee payment, this means: the fee is always paid to the relayer once the Ethereum transaction is successfully *parsed and validated as a relayer-honest tx*, regardless of whether the requested base-token transfer or ERC-20 `ft_transfer` (which can fail for reasons like insufficient token balance, missing storage deposit funds, or gas exhaustion in the downstream cross-contract call) actually completes.

This is directly analogous to the reported bug class ("return value of transfer not checked leading to accounting error / silent failure with unexpected consequences"): here, the wallet contract does not gate value movement (the fee payment) on confirmation that the corresponding action succeeded — it commits the transfer optimistically and never reconciles it against the real outcome.

### Impact Explanation
A user's ETH-implicit wallet loses the fee amount (extracted as $NEAR from the wallet balance) any time a submitted, relayer-honest ERC20Transfer/EOABaseTokenTransfer fails downstream (e.g., insufficient ERC-20 balance at execution time, gas exhaustion in the `storage_deposit`+`ft_transfer` batch, or receiver contract panics) — the user pays for a service (the intended transfer) that they never receive, and their nonce is burned so they cannot retry with the same signed transaction. This is unauthorized value movement out of the user's account without the corresponding, expected state change taking place.

### Likelihood Explanation
Reachable by any relayer holding a validly signed relayed transaction (relayers do not need special privileges beyond the function-call access key already granted for `rlp_execute`) or even by the wallet owner acting as their own relayer. Any legitimate ERC-20 transfer that fails at execution time (e.g., due to stale balance information, or a downstream contract requiring more gas than budgeted) triggers the fee loss automatically, without requiring an actively malicious actor — making it easily triggerable in normal operation, not just as a crafted attack.

### Recommendation
Move the fee-refund promise so that it is scheduled as part of the same callback chain that also performs the intended action, conditioned on that action's `PromiseResult::Successful` outcome (e.g., pay the fee inside/after `rlp_execute_callback` only when the underlying transfer succeeded), or refund the fee back to the user if the downstream action fails.

### Proof of Concept
1. User signs an RLP transaction encoding an `ERC20Transfer` with a non-zero `fee` (derived from `max_fee_per_gas * gas_limit`) to a NEP-141 token where the wallet's actual token balance is insufficient (or becomes insufficient between signing and execution).
2. A relayer submits `rlp_execute(target, tx_bytes_b64)` with sufficient attached gas; `validate_tx_relayer_data` passes (relayer is "honest").
3. `inner_rlp_execute` immediately creates and sends the fee-transfer promise to the relayer's account, per [4](#0-3) .
4. The subsequent `storage_balance_of` → `ft_transfer` promise chain fails (e.g., `ft_transfer` panics due to insufficient balance), and `rlp_execute_callback` reports failure and only refunds `caller_deposit` (an attached-deposit refund unrelated to the fee).
5. Net effect: the relayer keeps the fee even though the ERC-20 transfer the user paid for never happened, and the user's nonce has already been incremented so the identical signed transaction cannot be resubmitted.
