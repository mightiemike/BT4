## Finding confirmed — missing root-match check in `capability::revoke`

### Title
Missing root validation in `capability::revoke` lets any capability holder desynchronize `CapState<Feature>.delegates` from `CapDelegateState<Feature>` for unrelated roots - (File: `aptos-move/framework/aptos-stdlib/sources/capability.move`)

### Summary
`revoke` destroys the `CapDelegateState<Feature>` resource at `from` and discards the `root` field it reads from that resource, then removes `from` from the delegate list of `self.root` (the caller-supplied capability's root) instead of the delegate's *actual* registered root. There is no assertion that these two roots match.

### Finding Description
`revoke` is implemented as: [1](#0-0) 

```
public fun revoke<Feature>(self: Cap<Feature>, _feature_witness: &Feature, from: address)
acquires CapState, CapDelegateState
{
    if (!exists<CapDelegateState<Feature>>(from)) return;
    let CapDelegateState { root: _root } = move_from<CapDelegateState<Feature>>(from);
    remove_element(&mut borrow_global_mut<CapState<Feature>>(self.root).delegates, &from);
}
```

The delegate's stored `root` (`_root`) is unconditionally discarded instead of being checked against `self.root`. Contrast with `validate_acquire`, which *does* cross-check the delegate's stored root against the `CapState` it's supposed to belong to: [2](#0-1) 

If a caller who legitimately holds any `Cap<Feature>{root: R2}` (obtained validly via `acquire` for a different capability root of the same `Feature` type) calls `revoke<Feature>(cap_R2, witness, from)` where `from` is actually a delegate registered under a different root `R1` (`CapDelegateState<Feature>{root: R1}` at `from`), the function:
1. Deletes `from`'s `CapDelegateState<Feature>` resource entirely (the `exists` check only looks at `from`, not at what root it points to).
2. Attempts to remove `from` from `CapState<Feature>` at `R2`'s (i.e. `self.root`'s) `delegates` vector — a no-op since `from` was never listed there.

The result: `CapState<Feature>.delegates` at the true root `R1` still lists `from`, but `from` no longer holds a `CapDelegateState<Feature>` resource, breaking the documented invariant (`delegates` at a root must exactly mirror `CapDelegateState.root == root` registrations, per the module's own spec invariants at lines 61-71). Once `from`'s `CapDelegateState` is gone, `from` can even re-register as a delegate of a completely different root `R3` via `delegate`, since `delegate` only checks `exists<CapDelegateState<Feature>>(addr)`: [3](#0-2) 

leaving `R1`'s `delegates` vector permanently holding a stale address whose live root is now `R3`, while `R1` has no way to ever clean it up (a legitimate `revoke<Feature>(cap_R1, witness, from)` issued by `R1`'s true owner would delete `from`'s current `CapDelegateState<Feature>{root: R3}` and then fail to remove it from `R1`'s vector either, since `remove_element` on `self.root == R1` succeeds this time — but only accidentally, since the actual owner would need to have observed the stale entry to invoke it at all).

### Impact Explanation
This corrupts durable ledger state for any account/module using `0x1::capability` with more than one independent root sharing the same `Feature` type: `CapState<Feature>.delegates` at one root can be made permanently inconsistent with the real `CapDelegateState<Feature>` registrations, by any party holding a valid `Cap<Feature>` for an unrelated root (not by the root owner whose vector is affected). This is exploitable purely through composable third-party Move packages deployed by unprivileged accounts — no operator/admin trust is required, only that the underlying feature module allows more than one root for the same phantom `Feature` type and exposes revoke to more than the sole trusted root owner.

### Likelihood Explanation
Currently, no module in `aptos-framework`/`aptos-experimental` in this snapshot imports `aptos_std::capability` (verified via search); it is a general-purpose library available to any third-party Move package on mainnet under `0x1::capability`. Exploitability therefore depends on a downstream package design that (a) permits multiple independent capability roots for the same `Feature` type and (b) allows a party other than the true root owner to obtain a `Cap<Feature>` and invoke `revoke` against arbitrary `from` addresses. Given the library's use is entirely mediated by phantom-typed witnesses controlled by whichever module defines `Feature`, likelihood is moderate and contingent on downstream package design rather than affecting Aptos core protocol state directly.

### Recommendation
Add an explicit check in `revoke` that the delegate's stored root matches `self.root` before mutating any `delegates` vector:
```
let CapDelegateState { root } = move_from<CapDelegateState<Feature>>(from);
assert!(root == self.root, error::invalid_argument(EDELEGATE));
remove_element(&mut borrow_global_mut<CapState<Feature>>(self.root).delegates, &from);
```

### Proof of Concept
1. Two accounts `A` (root `R1`) and `B` (root `R2`) each call `create<Feature>` to register independent capability classes for the same `Feature` type.
2. `A` delegates to account `D` via `delegate<Feature>(cap_R1, witness, &signer_D)`; now `CapDelegateState<Feature>{root: R1}` exists at `D`, and `R1`'s `CapState<Feature>.delegates` contains `D`.
3. `B` acquires `Cap<Feature>{root: R2}` via `acquire<Feature>(&signer_B, &witness)`.
4. `B` calls `revoke<Feature>(cap_R2, witness, D)`.
5. Assert: `exists<CapDelegateState<Feature>>(D) == false` (destroyed), but `borrow_global<CapState<Feature>>(R1).delegates` still contains `D` — the invariant is broken with no path for `A` to detect or repair it other than manually noticing the stale entry. [1](#0-0)
