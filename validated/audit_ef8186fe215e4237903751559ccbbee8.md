Based on my research, I found a confirmed structural analog: `TokenConfig.LiquidityCap` is defined and validated for non-emptiness, but is never read or enforced anywhere in the deposit/mint path.

### Title
Unenforced `LiquidityCap` on Token Configs Allows Unbounded PRC20 Minting via Inbound Deposits - (File: `x/uexecutor/keeper/handler.go`)

### Summary
Similar to the bonding-curve report where `stepsize * numSteps` was never validated against `curveSupply`, Push Chain's `uregistry.TokenConfig` declares a `liquidity_cap` field that is documented as "max supply cap for this token" [1](#0-0)  and is required to be non-empty by `ValidateBasic` [2](#0-1) , yet the value is never read or checked anywhere in the inbound deposit/mint flow.

### Finding Description
`depositPRC20` (called from `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGas`, and outbound-revert re-mint paths) looks up the `TokenConfig` purely to resolve the PRC20 contract address, and then calls `CallPRC20Deposit` with the caller-controlled/observed `inbound.Amount`, with no comparison against `tokenConfig.LiquidityCap` or against any running total of minted supply: [3](#0-2) 

`CallPRC20Deposit` then unconditionally mints the PRC20 to the recipient via `depositPRC20Token` on `UniversalCore`: [4](#0-3) 

A grep across the entire `x/uexecutor` module confirms zero references to `LiquidityCap`/`liquidity_cap`, meaning no keeper, no ante-like guard, and no EVM-side check consults this field before minting. The cap is a purely decorative, admin-set number stored in `uregistry` state with no code path that ever reads it back during minting.

This mirrors the reported bug exactly: a configuration invariant ("the sum of everything mintable should not exceed the declared cap") that the schema implies but the implementation never checks, because the two quantities (declared cap vs. actual cumulative mint amount) are never cross-validated.

### Impact Explanation
An unprivileged user who can get inbound votes recorded for a given `(source_chain, asset_addr)` pair (a normal, honest-validator-observed deposit on the external chain) can mint an arbitrary amount of the corresponding PRC20 on Push Chain, unbounded by the token's configured `liquidity_cap`. Since PRC20 tokens back synthetic representations of external assets and are consumed throughout `x/uexecutor` for outbound transfers, swaps, and gas-fee refunds, this can lead to PRC20 supply inflation beyond what the protocol's own accounting model assumes, i.e., unauthorized mint of protocol-controlled synthetic assets, which is explicitly in scope ("unauthorized mint ... of user or protocol-controlled funds").

However, I could not verify within the available context whether the cap is instead enforced at the PRC20 Solidity-contract level (e.g., inside the `UniversalCore`/`PRC20` contract's `depositPRC20Token` implementation, which lives in `precompiles`/`core-contracts` and was not indexed in this search). Because the actual minting authorization/enforcement logic for `depositPRC20Token` resides in Solidity contract code that is outside the Go-side `x/` scope and not fully retrievable via the available search tools, I cannot confirm with certainty that the Go-level omission translates into an actual unbounded-mint vulnerability rather than a defense-in-depth gap that is compensated for on the contract side.

### Likelihood Explanation
If the cap truly has no enforcement anywhere, likelihood is high and trivially triggerable by any user able to get 2/3+ honest Universal Validators to vote in a legitimate deposit observation (the standard inbound flow) — no privileged action or malicious validator is required, since the validators are just honestly reporting a real external deposit; the missing check is purely on the Push Chain side of how much to mint relative to the configured limit. Likelihood is contingent on whether the Solidity `UniversalCore`/PRC20 contract independently enforces the cap, which is unverified here.

### Recommendation
- If `liquidity_cap` is meant to be enforced, add a check in `depositPRC20` (or in `CallPRC20Deposit`) in `x/uexecutor/keeper/handler.go` / `evm.go` that reads `tokenConfig.LiquidityCap`, tracks cumulative minted supply per token (e.g., via a new keeper-side counter or by querying PRC20 `totalSupply()`), and rejects/caps deposits that would exceed it.
- Alternatively, if enforcement is intentionally delegated to the Solidity `UniversalCore` contract, add an explicit code comment/reference in `token_config.go` and the `x/uregistry` README clarifying that `liquidity_cap` is purely informational on the Go side and is enforced on-chain in the EVM contract, to avoid the false impression of protocol-level enforcement.
- Add unit/integration tests asserting that a deposit exceeding `liquidity_cap` is rejected (or, if enforcement is contract-side, that the contract call reverts and is properly surfaced as a `FAILED` `PCTx`/`INBOUND_REVERT`).

### Proof of Concept
Not independently reproducible from the available Go-level code alone, since minting success/failure ultimately depends on the (unindexed) Solidity `UniversalCore.depositPRC20Token` implementation. At the Go level, the following demonstrates the missing check:
1. Register a `TokenConfig` with `liquidity_cap = "1000000000000000000000000"` (1e24) as shown in `test/integration/uexecutor/inbound_cea_gas_and_payload_test.go`.
2. Submit/vote an `Inbound` of `TxType_FUNDS` with `Amount` far exceeding the cap (e.g., `"999999999999999999999999999999"`).
3. Observe that `depositPRC20` (`x/uexecutor/keeper/handler.go:12-46`) performs no comparison against `tokenConfig.LiquidityCap` before calling `CallPRC20Deposit`, so if the underlying EVM call succeeds, the full over-cap amount is minted, as reflected in existing tests like `inbound_solana_test.go:158-164`, which assert `balanceOf(recipient) == inbound.Amount` with no cap check anywhere in the assertion chain.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
