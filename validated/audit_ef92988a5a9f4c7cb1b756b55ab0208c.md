### Title
Stale/replayed SignedOCRResponse acceptance due to missing requestID binding when `signedResponseRequestIDGate` is disabled - ([File: core/services/gateway/handlers/vault/aggregator.go])

### Summary
When the `signedResponseRequestIDGate` feature gate is disabled, `baseAggregator.Aggregate` calls `validateUsingSignatures` with `validateSignedPayloadRequestID=false`, which validates only the cryptographic signature/quorum threshold (`don.F+1`) on the `SignedOCRResponse` and never checks that the signed payload corresponds to the current `requestID`. Because the OCR signature covers only `Context` and `Payload` (not the outer `jsonrpc.Response.ID` envelope field used for request/response correlation), an attacker positioned on the gateway-to-node transport can replay a previously valid, fully-signed response for a different (stale) request by rewriting only the unsigned envelope `ID` to match the currently pending request.

### Finding Description
`baseAggregator.Aggregate` branches on `signedResponseRequestIDEnabled`: [1](#0-0) 

- When the gate is enabled, `validateUsingSignatures(..., true)` is used, and `SignedPayloadRequestID` is extracted from the payload and compared to `requestID`, rejecting mismatches: [2](#0-1) 
- When the gate is disabled, `validateUsingSignatures(..., false)` returns immediately after signature validation succeeds, with **no** requestID binding at all: [3](#0-2) 

`vaulttypes.ValidateSignatures` only checks that `len(resp.Signatures) >= minRequired (F+1)` and that each signature recovers to an allowed signer address, computed over `Context` (config digest + epoch/round) and `Payload`: [4](#0-3) 

Critically, this signature hash does **not** cover the outer `jsonrpc.Response.ID` field, which is the correlation key used by the gateway's active-request tracking to match a node response to a pending client request. Because the signed hash is independent of that envelope ID, a transport-level attacker (unprivileged network position between gateway and node, per the threat model) can take a genuinely-signed `SignedOCRResponse` captured from a prior/stale round (request A) and re-wrap it inside a `jsonrpc.Response` envelope whose `ID` field is set to the currently pending `requestID` (request B). The signatures remain valid (they don't cover the envelope ID), `ValidateSignatures` passes, and since `validateSignedPayloadRequestID=false`, the payload's embedded `RequestId` (which would show "A", not "B") is never checked — so the stale response is accepted as the authoritative answer for request B.

This is consistent with the existing test comment acknowledging the fallback exists to "temporarily tolerate signed OCR reports from vault nodes that have not upgraded to include requestId in the signed payload" (CRE-4875) and the differential behavior demonstrated by `TestAggregator_SignedResponseRequestIDMismatch`, which passes only when the gate is enabled: [5](#0-4)  — with the gate disabled, an equivalent mismatched-requestID response is accepted rather than rejected.

### Impact Explanation
A successful replay causes the gateway to return stale vault secret operation results (e.g., a stale `CreateSecretsResponse`/`UpdateSecretsResponse`/`ListSecretIdentifiersResponse`) as if they were the authoritative, fresh response for an unrelated pending request. This can mislead callers about the outcome of the current operation (e.g., presenting a stale success/failure/error state, or stale secret identifier listings) and undermines the integrity guarantee that OCR-signed vault responses are bound to a specific request. Impact is scoped to data integrity/tampering of vault operation results relayed through the gateway, matching a "misreporting/data tampering" bounty category rather than direct secret disclosure, since the payload content itself must have been a legitimately-signed prior response.

### Likelihood Explanation
Exploitability requires: (1) the `signedResponseRequestIDGate` to be disabled (this is presented in the code as a legacy/transitional fallback path, not a hardened default; whether it is enabled by default in current deployments could not be confirmed from the index and would need to be checked directly against the CRE gate configuration), and (2) an attacker able to intercept and modify gateway-to-node traffic (a network MITM position), which fits the "unprivileged network position" threat model given in the question. Given those preconditions, the exploit is deterministic and repeatable: any captured, validly-signed stale response can be replayed against any future pending request of the same method as long as the attacker can rewrite the outer envelope ID before the gateway processes it.

### Recommendation
Remove the `validateSignedPayloadRequestID=false` fallback path (or make request-ID binding mandatory regardless of the gate), and/or extend the OCR signature hash (`ocr2key.ReportToSigData`) to also cover the request-correlation ID so that the envelope ID cannot be altered without invalidating signatures. At minimum, always verify `resp.ID == requestID` at the JSON-RPC envelope level before accepting a signature-only-validated response, independent of the `signedResponseRequestIDGate` state.

### Proof of Concept
Add a differential unit test in `core/services/gateway/handlers/vault/aggregator_test.go`:
1. Use `makeSignedCreateSecretsResponse(t, "A", 2)` to build a genuinely-signed response for request "A" (as done in `TestAggregator_Valid_Signatures`).
2. Construct `agg := testAggregator(t, mcr, false)` (gate disabled).
3. Call `agg.Aggregate(ctx, l, "B", responses, &currResp)` where `currResp.ID` has been rewritten to `"B"` but the inner `SignedOCRResponse.Payload` still contains `RequestId: "A"`.
4. Assert that `Aggregate` returns `err == nil` and the stale payload (`RequestId: "A"`) is returned as the accepted response for request `"B"` — demonstrating acceptance of a replayed/stale signed response across differing request IDs, contrasted with `TestAggregator_SignedResponseRequestIDMismatch` which correctly rejects the same scenario when the gate is enabled (`true`).

func ValidateSignatures(resp *SignedOCRResponse, allowedSigners []common.Address, minRequired int) error {
	if len(resp.Context) < 64 {
		return fmt.Errorf("context too short: expected min 64 bytes, got %d bytes", len(resp.Context))
	}

	if len(resp.Signatures) < minRequired {
		return fmt.Errorf("not enough signatures: expected min %d, got %d", minRequired, len(resp.Signatures))
	}

	// The context contains:
	// 0:32 -> config digest
	// 32:64 -> epoch + round, namely:
	//   - 0:27 -> zero padding
	//   - 27:31 -> sequence number (big endian uint32)
	//   - 31:32 -> zero round value
	// 64:96 -> extra hash (not used by the vault plugin)
	cd, epochRound := resp.Context[:32], resp.Context[32:64]
	configDigest, err := ocr2types.BytesToConfigDigest(cd)
	if err != nil {
		return fmt.Errorf("invalid config digest in signature: %w", err)
	}

	epoch := binary.BigEndian.Uint32(epochRound[27:31])
	round := epochRound[31]

	fullHash := ocr2key.ReportToSigData(ocr2types.ReportContext{
		ReportTimestamp: ocr2types.ReportTimestamp{
			ConfigDigest: configDigest,
			Epoch:        epoch,
			Round:        round,
		},
	}, []byte(resp.Payload))

	validSigners := map[common.Address]bool{}
	for _, s := range resp.Signatures {
		signerPubkey, err := crypto.SigToPub(fullHash, s)
		if err != nil {
			return fmt.Errorf("invalid signature: %w", err)
		}
		signerAddr := crypto.PubkeyToAddress(*signerPubkey)

		for _, as := range allowedSigners {
			if as.Hex() == signerAddr.Hex() {
				validSigners[signerAddr] = true
				break
			}
		}

		if len(validSigners) >= minRequired {
			return nil
		}
	}

	return fmt.Errorf("only %d valid signatures, need at least %d", len(validSigners), minRequired)
}
