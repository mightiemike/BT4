### Title
Replay-Verification Ignores State/Hot-State/Position Checkpoint Hashes, Allowing a Divergent State-Commitment Root to Pass as Verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the sole comparator used by replay-verification tooling (`storage/db-tool/src/replay_on_archive.rs`) and by chunk replay (`execution/executor/src/chunk_executor/mod.rs`), checks transaction status, gas used, write-set hash, and event root hash against the persisted `TransactionInfo`, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` is documented in-code as intentionally incomplete: [2](#0-1) 

It validates:
- `status` vs `txn_info.status()`
- `gas_used`
- `write_set_hash == txn_info.state_change_hash()`
- `event_root_hash == txn_info.event_root_hash()` [3](#0-2) 

But it does **not** compare the locally-computed state checkpoint root (`state_checkpoint_hash`), hot-state checkpoint root (`hot_state_checkpoint_hash`), or the trading-native position-state root (`position_state_checkpoint_hash`) against the authenticated `TransactionInfo` fields that are actually part of the accumulator-committed, signature-verified ledger record. These checkpoint hashes are produced independently by `DoStateCheckpoint::run` from the locally re-executed state updates and then folded into the `TransactionInfo` that is hashed into the transaction accumulator during normal block execution: [4](#0-3) [5](#0-4) 

The only two call sites of this comparator are:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which calls it after re-executing archived transactions to confirm the replay matches the backed-up, ledger-info-signed `TransactionInfo` list. [6](#0-5) 
- `execution/executor/src/chunk_executor/mod.rs`, used during chunk replay/verify flows.

Because neither the write-set hash comparison nor the event-root comparison covers the state (or hot-state / position-state) Merkle root, a discrepancy that only manifests in the post-write-set state summary (e.g., a bug in `DoStateCheckpoint`'s JMT/position-state root construction, in `LedgerStateSummary::update`, or in the on-chain `hot_state_root_in_txn_info` / `compute_trading_native_state_roots` feature wiring) will not be caught by replay verification even though the write set and events match. This is a real, unresolved gap acknowledged by the `TODO(trading-native)` comment, tied specifically to the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature that is being actively developed in this codebase (visible via `compute_trading_native_state_roots`, `PositionStateWithSummary`, `ProvablePositionStateSummary` in `do_state_checkpoint.rs`). [7](#0-6) 

### Impact Explanation
Replay-verify (`db-tool replay-on-archive`) and chunk replay/verify are the primary trust mechanisms that confirm archived/backed-up transaction execution reproduces the exact ledger state that was signed by validators and stored durably. If the state (or, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, the position-state) root computed locally during replay silently diverges from the authenticated `TransactionInfo.state_checkpoint_hash` / `position_state_checkpoint_hash`, that divergence is **not** detected — `ensure_match_transaction_info` returns `Ok(())` regardless. This directly violates the required invariant that "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and that state proofs/roots be validated during replay. A replay tool operator (auditor, backup verifier, indexer) could be given false assurance that the archived data matches on-chain reality when in fact the state root — the value clients use for Merkle proof verification of arbitrary account/resource state — is wrong. This is state-commitment/proof-integrity relevant because `state_checkpoint_hash` is exactly the root against which `SparseMerkleProof`/state proofs served over the authenticated API are checked (as seen in `execution/executor/tests/storage_integration_test.rs`, which uses `txn_info.state_checkpoint_hash()` to verify a state proof). A silent bug in state-root computation (e.g., in the new position-state summary code path) would go undetected by the very tool meant to catch it.

### Likelihood Explanation
This requires (1) an underlying bug elsewhere causing a state/hot-state/position root divergence during re-execution (not proven here — that root cause is outside this file), and (2) reliance on `replay_on_archive`/chunk replay as the detection mechanism. The comparator gap itself is proven and acknowledged in-repo via the `TODO(trading-native)` comment, and is real, current code (not a test/mock) gating an in-development feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`). However, this finding is a verification-blind-spot, not a demonstrated live consensus/commit-time divergence — the executor's normal commit path (`DoLedgerUpdate`) still folds the correctly-computed checkpoint hash into `TransactionInfo` and the transaction accumulator, so honest nodes producing correct state roots are unaffected. The risk materializes only if a separate defect causes local state-checkpoint computation to diverge from the authoritative committed hash, which this comparator would then fail to catch.

### Recommendation
Extend `ensure_match_transaction_info` (and any parallel comparators used by chunk replay) to compare the locally recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields on `txn_info`, failing loudly on mismatch, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production, per the existing TODO.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-gap finding. Conceptual demonstration:
1. Take an archived transaction list plus its signed `TransactionInfo`s (as loaded by `replay_on_archive.rs`).
2. Re-execute so that `write_set` and `events` match exactly, but induce (via a hypothetical bug in `DoStateCheckpoint::get_state_checkpoint_hashes` / position-state summary logic) a different `state_checkpoint_hash` / `position_state_checkpoint_hash` than the one embedded in the original `TransactionInfo`.
3. Call `ensure_match_transaction_info` — this returns `Ok(())` because it never inspects those hash fields, even though the resulting `TransactionInfo` would hash differently and produce a different transaction-accumulator root than the authenticated ledger.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())

pub struct DoStateCheckpoint;

#[bon::bon]
impl DoStateCheckpoint {
    #[builder(finish_fn = build)]
    pub fn run<'a, 'db>(
        execution_output: &'a ExecutionOutput,
        parent_state_summary: &'a LedgerStateSummary,
        persisted_state_summary: &'a ProvableStateSummary<'db>,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        known_hot_state_checkpoints: Option<Vec<Option<HashValue>>>,
        parent_position_state_summary: Option<&'a LedgerWithSummary<PositionStateWithSummary>>,
        persisted_position_state_summary: Option<&'a ProvablePositionStateSummary<'db>>,
        known_position_state_checkpoints: Option<Vec<Option<HashValue>>>,
    ) -> Result<StateCheckpointOutput> {
        let _timer = OTHER_TIMERS.timer_with(&["do_state_checkpoint"]);

        let state_summary = parent_state_summary.update(
            persisted_state_summary,
            &execution_output.hot_state_updates,
            execution_output.to_commit.state_update_refs(),
        )?;

        let last_checkpoint = state_summary.last_checkpoint();

        let state_checkpoint_hashes = Self::get_state_checkpoint_hashes(
            execution_output,
            known_state_checkpoints,
            last_checkpoint.root_hash(),
            "state",
        )?;
        let hot_state_checkpoint_hashes = execution_output
            .hot_state_root_in_txn_info
            .then(|| {
                Self::get_state_checkpoint_hashes(
                    execution_output,
                    known_hot_state_checkpoints,
                    last_checkpoint.hot_root_hash()?,
                    "hot_state",
                )
            })
            .transpose()?;

        let (position_state_summary, position_state_checkpoint_hashes) =
            if execution_output.compute_trading_native_state_roots {
                let persisted = persisted_position_state_summary
                    .expect("persisted position summary required when feature on");
                let (summary, hashes) = Self::compute_position_checkpoint(
                    execution_output,
                    parent_position_state_summary,
                    persisted,
                    known_position_state_checkpoints,
                )?;
                (Some(summary), Some(hashes))
            } else {
                (None, None)
            };

        Ok(StateCheckpointOutput::builder()
            .state_summary(state_summary)
            .state_checkpoint_hashes(state_checkpoint_hashes)
            .maybe_hot_state_checkpoint_hashes(hot_state_checkpoint_hashes)
            .maybe_position_state_summary(position_state_summary)
            .maybe_position_state_checkpoint_hashes(position_state_checkpoint_hashes)
            .build())
