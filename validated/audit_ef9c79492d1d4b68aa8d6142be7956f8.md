### Title
Client-side proving accepts a valid SNOS proof without binding it to the specific invoke transaction's sender/calldata/nonce - (File: crates/starknet_proof_verifier/src/proof_verifier.rs)

### Summary
The `pac4j-jwt` bug allows an attacker to wrap unsigned/arbitrary claims (`PlainJWT`) inside a validly-encrypted envelope, and the verifier accepts the envelope's validity as proof of the (forged) claims. The sequencer's client-side-proving feature has an analogous structural gap: `verify_proof` cryptographically checks that a STARK proof is valid for the public output encoded in `proof_facts`, but `proof_facts` never commits to the specific invoke transaction (`sender_address`, `calldata`, `nonce`) it is attached to. Any submitter can therefore reuse a legitimately-generated `(proof_facts, proof)` pair on an entirely different, attacker-chosen invoke transaction and have the gateway/transaction-converter treat it as "verified."

### Finding Description
`RpcTransaction`/`InvokeV3` lets a client directly attach arbitrary `proof_facts` and `proof` fields to a transaction [1](#0-0) . The gateway spawns verification purely from these two fields, decoupled from the rest of the transaction: [2](#0-1) . `run_proof_verification` first checks a hash-keyed cache (`contains_proof`) and, only if missing, calls the cryptographic verifier — again with only `proof_facts`/`proof`, no transaction hash, sender, or calldata: [3](#0-2) .

The actual cryptographic check, `verify_proof`, reconstructs the STARK's public output solely from `proof_facts` and verifies the proof against that output: [4](#0-3) . Per the documented output contract, the virtual-OS public output is only `[output_version, base_block_number, base_block_hash, starknet_os_config_hash, n_l2_to_l1_messages, message_hash_0, ...]` — explicitly excluding any transaction-identifying data (no sender, no calldata hash, no nonce, no state diff): [5](#0-4)  and its Rust-side parser confirms the same fields: [6](#0-5) . The parsed `SnosProofFacts` struct used by the blockifier likewise only carries `proof_version`, `program_hash`, `block_number`, `block_hash`, `config_hash` — nothing tying it to a specific sender/calldata/nonce: [7](#0-6) .

The blockifier-side pre-validation (`validate_proof_facts`) only checks that the proof version is allowed, the program hash is on an allow-list, and the block hash/number/config-hash match chain state — again nothing about the current transaction's own content: [8](#0-7) .

As a result, a previously-generated, cryptographically-valid `(proof_facts, proof)` pair (e.g. obtained legitimately for one transaction, or via the public proving RPC in `starknet_transaction_prover`) can be pasted verbatim onto a different `RpcInvokeTransaction` with an attacker-chosen `sender_address`, `calldata`, and `nonce`. The verifier and the pre-validation stage both pass, because none of them re-derive or check a binding between the proof's attested execution and the transaction it now accompanies. This is structurally the same class of bug as the JWE-wrapped `PlainJWT`: a cryptographically-valid outer artifact (proof / JWE) is accepted as authenticating an inner payload (transaction fields / JWT claims) that was never actually covered by that cryptographic check.

### Impact Explanation
Client-side proving exists to let the sequencer skip full re-execution/re-verification of the "virtual OS run," trusting the proof's asserted `n_l2_to_l1_messages`/message hashes and block linkage. If the proof is not bound to the specific transaction it is submitted with, an attacker can attach any prior valid proof (potentially one they generated cheaply/for free, since client-side proving transactions require zero fees per the prover README [9](#0-8) ) to a transaction with different (and unauthorized) parameters. Depending on how `messages_to_l1_hashes` output is consumed downstream (not fully traceable within the indexed code), this can translate into acceptance of transactions whose sender/calldata were never actually validated by the claimed proof, i.e. an authentication-bypass for the "proof of correct execution" — analogous to accepting forged claims. This maps to unauthorized account action / wrong committed state under the reachable-path rules (attacker: any unprivileged transaction sender via the gateway RPC).

### Likelihood Explanation
Any unprivileged client can submit an `RpcInvokeTransaction` with `proof_facts`/`proof` fields copied from an unrelated, previously-verified or independently-obtained proof; no additional privilege or interaction with other systems is required, and the code path (`gateway` → `TransactionConverter` → `verify_proof`) is on the default transaction-admission path for any V3 invoke transaction carrying non-empty `proof_facts`.

### Recommendation
Bind the proof's public output/`proof_facts` to a commitment of the specific transaction it accompanies (e.g., include a poseidon hash of `sender_address`, `calldata`, and `nonce` in the virtual-OS output/`proof_facts`, and have `verify_proof`/`validate_proof_facts` check this commitment against the actual transaction fields before treating the proof as valid for that transaction).

### Proof of Concept
Conceptual PoC (exact reachability of downstream consumption of `messages_to_l1_hashes` should be confirmed with a Devin session that can trace the full data-flow, since this was not fully verifiable within the indexed code):
1. Obtain a valid `(proof_facts, proof)` pair for transaction A (e.g., via the public `starknet_transaction_prover` RPC, using zero-fee client-side-proving fields as documented).
2. Construct a new `RpcInvokeTransaction` B with a different `sender_address`, `calldata`, and `nonce`, but attach A's `proof_facts`/`proof` verbatim.
3. Submit B to the gateway; `convert_rpc_tx_to_internal_rpc_tx` → `spawn_proof_verification` → `run_proof_verification` → `starknet_proof_verifier::verify_proof(proof_facts, proof)` succeeds because it only checks internal proof/proof_facts consistency, not linkage to B's sender/calldata/nonce [3](#0-2) .
4. Blockifier `validate_proof_facts` also passes, since it only checks version/program-hash/block-hash/config-hash, not transaction-specific fields [8](#0-7) .

/// Reconstructs the output preimage from proof facts for circuit verification.
///
/// Proof facts layout: `[PROOF_VERSION_V*, variant, program_hash, ...task_output]`
/// Output preimage layout: `[num_tasks=1, output_size, program_hash, ...task_output]`
/// where `output_size = task_content.len() + 1` (includes itself).
pub fn reconstruct_output_preimage(
    proof_facts: &ProofFacts,
) -> Result<Vec<Felt>, VerifyProofError> {
    // Proof facts must contain at least [PROOF_VERSION_V*, variant, program_hash].
    if proof_facts.0.len() < 3 {
        return Err(VerifyProofError::ProofFactsTooShort { length: proof_facts.0.len() });
    }
    // Skip PROOF_VERSION_V* (index 0) and variant (index 1).
    let task_content = &proof_facts.0[2..];
    let output_size = Felt::from(
        u64::try_from(task_content.len() + 1).expect("task content length exceeds u64::MAX"),
    );
    Ok([Felt::ONE, output_size].into_iter().chain(task_content.iter().copied()).collect())
}

/// Verifies a submitted proof against the proof facts using the circuit verifier.
///
/// The first element of `proof_facts` must be V1, verified via `privacy-circuit-verify-v1`.
pub fn verify_proof(proof_facts: ProofFacts, proof: Proof) -> Result<(), VerifyProofError> {
    // Reject empty proof payloads before running the verifier.
    if proof.is_empty() {
        return Err(VerifyProofError::EmptyProof);
    }

    let proof_version_felt = proof_facts.0.first().copied().unwrap_or_default();
    let proof_version = ProofVersion::try_from(proof_version_felt)
        .map_err(|()| VerifyProofError::InvalidProofVersion { actual: proof_version_felt })?;

    let output_preimage = reconstruct_output_preimage(&proof_facts)?;
    // TODO(Avi): Avoid cloning the proof.
    let proof_bytes = proof.0.to_vec();

    match proof_version {
        // V0 proofs are no longer verifiable: the v0 circuit was removed. V0 proof facts are only
        // tolerated by the blockifier (gated per protocol version) for replaying historical blocks.
        ProofVersion::V0 => {
            return Err(VerifyProofError::InvalidProofVersion { actual: proof_version_felt });
        }
        ProofVersion::V1 => {
            let proof_output = privacy_circuit_verify_v1::PrivacyProofOutput {
                proof: proof_bytes,
                output_preimage,
            };
            privacy_circuit_verify_v1::verify_recursive_circuit(&proof_output)
                .map_err(|e| VerifyProofError::Verification(e.to_string()))?;
        }
    }

    Ok(())
}

    fn validate_proof_facts(
        &self,
        block_context: &BlockContext,
        state: &mut dyn State,
    ) -> TransactionPreValidationResult<()> {
        // Only Invoke V3 transactions can carry proof facts.
        let Transaction::Invoke(invoke_tx) = &self.tx else {
            return Ok(());
        };
        if invoke_tx.version() < TransactionVersion::THREE {
            return Ok(());
        }

        // Parse proof facts.
        let proof_facts = invoke_tx.proof_facts();
        let snos_proof_facts = match ProofFactsVariant::try_from(&proof_facts)
            .map_err(|e| TransactionPreValidationError::InvalidProofFacts(e.to_string()))?
        {
            ProofFactsVariant::Empty => return Ok(()),
            ProofFactsVariant::Snos(snos_proof_facts) => snos_proof_facts,
        };
        let os_constants = &block_context.versioned_constants.os_constants;

        if !os_constants.allowed_proof_versions.contains(&snos_proof_facts.proof_version.as_felt())
        {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Proof version {} is not allowed under this protocol version.",
                snos_proof_facts.proof_version
            )));
        }

        // Validate the program hash.
        let allowed = &os_constants.allowed_virtual_os_program_hashes;
        if !allowed.contains(&snos_proof_facts.program_hash) {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS program hash {} is not allowed",
                snos_proof_facts.program_hash
            )));
        }

        // Validate the block hash and block number.
        let proof_block_hash = snos_proof_facts.block_hash.0;
        let proof_block_number = snos_proof_facts.block_number.0;
        Self::validate_proof_block_number(
            proof_block_number,
            block_context.block_info.block_number,
        )?;
        Self::validate_proof_block_hash(proof_block_hash, proof_block_number, os_constants, state)?;

        // Validate the config hash.
        let virtual_os_config_hash = block_context.virtual_os_config_hash();
        let proof_config_hash = snos_proof_facts.config_hash;
        if virtual_os_config_hash != proof_config_hash {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS config hash mismatch. Computed virtual OS config hash: \
                 {virtual_os_config_hash}, expected virtual OS config hash: {proof_config_hash}."
            )));
        }

        Ok(())
    }

### Transaction requirements

- Only INVOKE V3 transactions (`"type": "INVOKE"`, `"version": "0x3"`) are accepted.
- **Prices and tip must be zero**: since proving is client-side and no fees are charged, each
  resource bound (`l1_gas`, `l2_gas`, `l1_data_gas`) must have `max_price_per_unit` set to `"0x0"`,
  and `tip` must be `"0x0"`. Disable this check with `SKIP_FEE_FIELD_VALIDATION=true`.
- **`l2_gas.max_amount` must be non-zero**: this value is the gas limit the OS enforces on the
  transaction. Set it to the value returned by `starknet_estimateFee`, or use `"0x5f5e100"`
  (100,000,000) as a safe upper bound — this is sufficient for approximately 1 million Cairo steps.
- **`l1_gas.max_amount` and `l1_data_gas.max_amount`** do not affect OS execution and can be any
  value (including zero).
- The `proof` and `proof_facts` fields are output-only and must be absent from the request (they
  are not part of the `RpcTransaction` input type).
