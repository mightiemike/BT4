This confirms the analog: a deterministic account can receive a plain `Transfer` deposit into `uninit` state before the `DeterministicStateInitAction` (which references a `GlobalContractIdentifier`) is ever successfully executed — and by design, deterministic accounts can *never* receive a full access key, `DeployContract`, or `CreateAccount` by any other path, so if the referenced global contract is never deployed (or the code hash/account id is wrong), the deposited funds are permanently unreachable.

### Title
Deterministic accounts can be permanently locked with unreclaimable NEAR when funded via `Transfer` before their referenced global contract exists - (File: `runtime/runtime/src/deterministic_account_id.rs`, `runtime/runtime/src/global_contracts.rs`)

### Summary
NEP-616 deterministic accounts (`0s...` account IDs) are created and "activated" strictly through `DeterministicStateInitAction`, which sets the account's code to a referenced global contract identified either by `CodeHash` or `AccountId` [1](#0-0) . However, the docs and code explicitly allow funding such an account with a plain `Transfer` *before* that init action succeeds, leaving the account in an "uninit" state with a balance but no contract [2](#0-1) . Deterministic accounts can never receive `AddKey`, `DeployContract`, or `CreateAccount` — these are explicitly rejected to prevent hijacking the account before `StateInit` [3](#0-2) . If the `GlobalContractIdentifier` referenced by the account's derived state (which is fixed forever by the deterministic-id derivation) is never deployed, or is a `GlobalContractIdentifier::AccountId(...)` for a publisher who never deploys code there, `use_global_contract` will always return `GlobalContractDoesNotExist` and the state-init action can never succeed [4](#0-3) , exactly analogous to the reported `_claimManager == 0` bug: a required "manager"/dependency reference is empty/unset at the time value is committed, and there is no privileged bypass to recover it later.

### Finding Description
The core apply logic in `action_deterministic_state_init` transitions an account through `nonexist -> uninit -> active` [5](#0-4) . The `uninit` state is reached the moment any `Transfer` targets the (not-yet-existing) deterministic account id, via `action_implicit_account_creation_transfer`'s `NearDeterministic` branch, which just calls `create_deterministic_account` with `AccountContract::None` [6](#0-5) . From this point:
- The account cannot be deleted (no owning key, `DeleteAccount` requires a signer with a full-access key).
- No `AddKey`, `DeployContract` or `CreateAccount` action can ever reach this account by design, confirmed by `test_transfer_and_add_key_to_deterministic_account` and `test_transfer_and_deploy_contract_to_deterministic_account`, which show these are rejected with `AccountDoesNotExist` because deterministic-account creation only recognizes single-action `Transfer` or `DeterministicStateInitAction` [7](#0-6) .
- The *only* path to unlock the funds is a successful `DeterministicStateInitAction` referencing the exact `GlobalContractIdentifier` baked into the account id's derivation (since the id is `keccak256(borsh(DeterministicAccountStateInitV1))`) [8](#0-7) .
- `use_global_contract` fails deterministically with `GlobalContractDoesNotExist` whenever the trie lacks that exact global-contract code entry [9](#0-8) , and this is confirmed as a first-class, reachable failure mode by `test_deterministic_state_init_missing_global_contract` [10](#0-9) .

Because the `GlobalContractIdentifier` (particularly the `AccountId` variant, which depends on whatever code that *other* account currently has deployed, and can be deployed/redeployed/never-deployed entirely independently of the deterministic account's existence) is fixed forever inside the derived account id, any unprivileged party (an RPC caller/transaction signer) can:
1. Derive a deterministic account id referencing a `GlobalContractIdentifier::AccountId(X)` where `X` currently has no global contract deployed (or will never deploy one, e.g., a typo'd/burn account).
2. Convince another party (or accidentally do it themselves) to `Transfer` NEAR into that not-yet-existing account id.
3. The deposit succeeds and creates the account in `uninit` state holding the balance.
4. Since `X` never deploys the referenced global contract, `DeterministicStateInitAction` can never succeed for that specific derived account id, and no other action (`AddKey`/`DeployContract`/`CreateAccount`/`DeleteAccount`) is permitted against a deterministic account outside this narrow path.
5. The deposited NEAR is permanently frozen with no possible recovery — no owner, no contract, no bypass.

### Impact Explanation
This results in permanently frozen user funds with no recovery path reachable by any account holder, matching the "permanently frozen funds" acceptance criterion. Any transaction signer who transfers to a deterministic account id whose referenced global-contract publisher never deploys code (intentionally or by oversight) loses those funds forever, since the runtime provides no privileged or fallback mechanism to reclaim balance from an `uninit` deterministic account.

### Likelihood Explanation
Reachable by a single, unprivileged `Transfer` transaction to any derivable `0s...` account id — no special permissions, staking, or validator/operator actions are required. The likelihood of accidental loss is non-trivial given that `GlobalContractIdentifier::AccountId` contracts can be deployed after the deterministic id was already derived/shared, or never deployed at all, and wallets/dApps constructing such transfers based on a not-yet-confirmed global contract deployment would trigger this unintentionally; a malicious actor could also intentionally construct such an id to solicit deposits that can never be recovered.

### Recommendation
Consider one or more of:
- Disallow plain `Transfer` to a not-yet-existing deterministic account id entirely, requiring the `DeterministicStateInitAction` (with its deposit field) to be the only way to fund it, removing the "pre-pay" convenience that creates the stuck window.
- Provide a protocol-level or refund mechanism (e.g., a receipt that returns the balance to the original sender) if `GlobalContractDoesNotExist` persists for a deterministic account beyond some condition, or allow a `Transfer` back out of an `uninit` deterministic account by the *original sender* under strict conditions.
- At minimum, strongly warn in wallets/SDKs constructing `Transfer`s to deterministic account ids that the referenced global contract must already exist on-chain, since the funds cannot be recovered otherwise.

### Proof of Concept
1. Derive `DeterministicAccountStateInit::V1(DeterministicAccountStateInitV1 { code: GlobalContractIdentifier::AccountId("nonexistent-publisher.near"), data: {} })` and compute `det_account = derive_near_deterministic_account_id(&state_init)` (mirrors `new_deterministic_account_with_data` in tests [11](#0-10) ).
2. Send a `Transfer` from any funded account to `det_account`. This succeeds and creates the account in `uninit` state (mirrors the pre-pay flow in `test_deterministic_state_init_prepay_for_storage` [12](#0-11) ).
3. Never deploy a global contract at `nonexistent-publisher.near` (or a `CodeHash` global contract matching the identifier).
4. Attempt `DeterministicStateInitAction` for `det_account` — it fails with `ActionErrorKind::GlobalContractDoesNotExist` exactly as demonstrated by `test_deterministic_state_init_missing_global_contract` [10](#0-9) .
5. Attempt `AddKey`, `DeployContract`, `CreateAccount`, or `DeleteAccount` against `det_account` from any signer — all are rejected as shown in `test_transfer_and_add_key_to_deterministic_account` / `test_transfer_and_deploy_contract_to_deterministic_account` [13](#0-12) .
6. The balance transferred in step 2 remains locked in `det_account` indefinitely, with no available action to move or reclaim it.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }

pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}
