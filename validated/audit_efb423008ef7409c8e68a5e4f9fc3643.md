### Title
Uncontrolled Recursion in Compiled Class Hash Bytecode Segment Hashing Causes Stack-Overflow DoS - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node` recursively walks the `NestedIntList`/`NestedFeltCounts` segment tree that describes how a CASM program's bytecode is partitioned into hash segments. The recursion has no depth limit, and the tree it walks is derived from attacker-controlled Sierra source code submitted in a `DECLARE` transaction. A contract declarer can craft a Sierra program whose compiled bytecode segmentation is deeply, linearly nested, forcing unbounded recursion and a stack overflow when the compiled class hash is computed — directly analogous to the infinite-recursion parsing bug in `BigTiffImage::printIFD` (CVE-2019-9144), where a crafted file drives an unbounded recursive parser to a crash.

### Finding Description
`bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` recurses once per level of the segment tree with no depth guard: [1](#0-0) 

The tree it operates on (`NestedIntList`) is not a fixed-height structure like the Patricia tree (which is capped by `SubTreeHeight::ACTUAL_HEIGHT`); it directly mirrors the segmentation the Sierra→CASM compiler chooses for the *submitted, attacker-authored* Sierra program (e.g., driven by function/branch nesting). The relevant code path:

1. A user submits a `DECLARE` transaction with an arbitrary Sierra `ContractClass`.
2. `SierraCompiler::compile` in `crates/apollo_compile_to_casm/src/lib.rs` compiles it to `CasmContractClass` and then immediately computes its hash: [2](#0-1) 
3. `.hash(&HashVersion::V2)` dispatches to `HashableCompiledClass::hash` → `hash_inner` → `bytecode_hash` → `bytecode_hash_node`: [3](#0-2) 
4. The segmentation structure hashed here (`bytecode_segment_lengths`) comes straight from the compiler's `CasmContractClass.bytecode_segment_lengths`, which is influenced by the shape of the attacker's Sierra source, not sanitized or depth-bounded before hashing.

There is a second, semi-mirrored implementation, `NestedFeltCounts::new_inner` in `crates/blockifier/src/execution/contract_class.rs`, which does assert a depth cap (`segmentation_depth <= 1`), but that assert is a `panic!` on violation rather than a graceful error — itself a crash-on-attacker-input issue if that code path is exercised in production (it is currently `#[allow(unused)]`, so its exposure is unclear from static inspection alone): [4](#0-3) 

Only resource limits (`max_bytecode_size`, `max_memory_usage`, `max_cpu_time`) are enforced around the external Sierra-to-CASM compiler subprocess: [5](#0-4) 
None of these limits bound the *recursion depth* of the segment tree that `bytecode_hash_node` walks afterward — a program can be well within the byte-size limit while still producing a segmentation tree that is degenerate/deeply nested (one child per node), just as a small crafted TIFF file in the CVE can still trigger deep IFD recursion.

### Impact Explanation
If `bytecode_hash_node`'s recursion depth exceeds the thread stack size, the process crashes (stack overflow / SIGSEGV) rather than returning an error. Because this hash computation runs:
- In the Sierra compiler component when a class is declared (`SierraCompiler::compile`), reachable by any account submitting a `DECLARE` transaction,
- Potentially again during blockifier state reads / class hash verification, and
- During Starknet OS re-execution, which must recompute the same commitments to reach the same result as honest nodes,

a crafted class can crash the sequencer/full-node process handling it, causing denial of service. If different nodes crash inconsistently (e.g., depending on stack size, OS, build), this can also cause consensus/re-execution divergence between nodes that manage to complete the hash and those that crash, potentially halting block production or causing an inability to confirm new transactions — satisfying the "network unable to confirm new transactions" / "honest-node divergence" impact bar.

### Likelihood Explanation
Likelihood is High: no privileged role is required — any account able to submit a `DECLARE` transaction (or class declaration via L1/CASM path) can attempt this. Crafting Sierra code that produces deeply, linearly nested bytecode segments (e.g., long chains of nested scopes/branches) is within reach of the declared-class size limits already enforced (`max_bytecode_size`), since recursion depth and total size are not the same constraint — a program can stay small in total bytes while its segmentation tree is deep.

### Recommendation
- Convert `bytecode_hash_node` (and the mirrored `NestedFeltCounts::new_inner`) to an iterative, explicit-stack-based (or work-queue) traversal instead of native recursion, so depth is bounded only by available heap, not stack.
- Enforce and validate an explicit maximum nesting depth for `NestedIntList`/`bytecode_segment_lengths` immediately after Sierra→CASM compilation and before any hashing/consumption, rejecting classes whose segmentation tree exceeds the bound with a normal `CompilationUtilError`/`StateError` instead of panicking or overflowing the stack.
- Replace the `assert!(segmentation_depth <= 1, ...)` in `NestedFeltCounts::new_inner` with a checked, recoverable error path if that function is ever wired into a live code path.
- Add fuzz/regression tests that submit adversarially deep-but-small-byte Sierra programs to confirm bounded, graceful failure rather than crash.

### Proof of Concept
1. Author a Sierra/Cairo1 contract whose control flow is structured to produce a maximally nested, single-child-per-level bytecode segmentation from the compiler (e.g., deeply nested `if`/scoped blocks or nested function definitions many thousands of levels deep), while staying under `max_bytecode_size`.
2. Submit it as the class in a `DECLARE` transaction (or via `SierraCompiler::compile` directly, as done in `crates/apollo_compile_to_casm/src/lib.rs:60-74`).
3. Observe that `CasmContractClass::hash(&HashVersion::V2)` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:144-178`, via `bytecode_hash_node`) recurses once per nesting level with no depth check, exhausting the call stack and crashing the compiling/hashing process before any resource-accounting/step-limit mechanism (which governs VM execution, not this hashing routine) can intervene.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

/// Computes the compiled class hash for a given hashable class using the specified hash algorithm.
fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }
