Based on the code I examined, this confirms the mechanism precisely: `AccountsCacheIndex::remove` decrements a ref-count per pubkey and only returns the pubkey as "removed" once its ref count hits zero (`accounts-db/src/accounts_cache.rs:209-225`), and `test_remove_slot_cleans_up_index` demonstrates that a pubkey present in multiple cached slots (e.g., slots 1 and 3) is *not* included in `pubkeys_removed` until the *last* cached slot containing it is flushed.

### Title
Write-through of the accounts index can be indefinitely stalled by continuously re-writing the same account, causing unbounded in-memory index growth despite a configured disk-index memory threshold - ([File: accounts-db/src/accounts_db.rs], [File: accounts-db/src/accounts_index/in_mem_accounts_index.rs])

### Finding Description
`write_through_pubkeys` is only invoked from the slot-cache-flush path (`AccountsDb::flush_slot_cache_with_locks` at [1](#0-0) ), and only for the pubkeys returned by `AccountsCache::remove_slot`, i.e. pubkeys that have left *every* cached slot ( [2](#0-1) ). `AccountsCacheIndex::remove` decrements a per-pubkey reference count and only reports removal when it reaches zero ( [3](#0-2) ), confirmed by `test_remove_slot_cleans_up_index` showing a pubkey present in two cached slots stays out of the "removed" set until both are flushed ( [4](#0-3) ).

Separately, the normal per-slot index update path — `InMemAccountsIndex::upsert` → `get_or_create_index_entry_for_pubkey` → `lock_and_update_slot_list` — unconditionally calls `entry.mark_dirty()` but never calls `write_through` inline ( [5](#0-4)  and [6](#0-5) ). Only `replace()` and `slot_list_mut_with_entry()` do inline write-through; `upsert()` (the path used when flushing a slot's accounts into the index, see `store_accounts_for_flush` in `flush_slot_cache_with_locks`) does not. Furthermore, the background `flush_internal` scan explicitly skips dirty entries when `should_write_through` is enabled, per `test_flush_internal_evicts_in_should_write_through_mode` ( [7](#0-6) ) — the design intentionally defers write-through to the cache-flush path.

Consequently, an attacker can keep a fixed set of pubkeys perpetually "dirty" in the in-memory index bin by ensuring each pubkey is re-written (touched) in at least one still-unrooted/cached slot at all times, before the previous cached slot containing it is flushed. As long as this holds, `remove_slot`'s ref-count for that pubkey never reaches zero, so it's never included in `pubkeys_removed`, so `write_through_pubkeys` never runs for it, so the in-memory `AccountMapEntry` stays dirty indefinitely and is never persisted to the on-disk bucket via `try_write_through`/`write_through`. Since `should_write_through` mode disables background flushing of dirty entries (deferring entirely to this cache-exit path) and additionally the inline eviction logic in `get_or_create_index_entry_for_pubkey` only evicts *clean* (non-dirty) entries (`map.iter().find(|(_, v)| !v.dirty())` at [8](#0-7) ), such dirty entries can never be evicted from memory either — they are permanently pinned in RAM regardless of the configured `IndexLimitThreshold::num_bytes` memory limit.

### Impact Explanation
This allows an unprivileged user to force the in-memory accounts index to grow (and stay) unboundedly beyond the operator-configured disk-index memory threshold at the cost of ordinary transaction fees for repeatedly writing to a fixed set of self-owned accounts once per slot (or fast enough to always stay "cached"). This falls into the "disproportionate storage/memory cost" bounty category — an attacker pays flat per-transaction fees while the validator accrues unbounded, non-evictable memory pressure in the accounts index bins, risking OOM on nodes that intentionally enabled the disk index specifically to bound memory usage.

### Likelihood Explanation
Preconditions: validator must have disk index enabled with `IndexLimit::Threshold` (an operator config choice, not attacker-controlled) — this is a legitimate, documented production configuration meant to bound memory. Given that, the only requirement on the attacker side is writing to the same account(s) frequently enough (roughly once per slot, well within normal transaction throughput and well under the `CLUSTER_SLOT_TIME_TARGET / 2` rate-limit noted in scope) to keep it present in an unflushed cached slot continuously. This is fully reproducible and requires no validator/leader control — it exploits how `flush_slot_cache` and `AccountsCacheIndex` ref-counting interact with `write_through_pubkeys`.

### Recommendation
Decouple "is dirty and write-through-eligible" from "has left every cached slot." Either (a) have the background flush/scan periodically also attempt `try_write_through` for dirty, single-ref, single-slot-list entries even under `should_write_through` mode (bounding dirty residency time regardless of cache-cycling), or (b) track per-pubkey write-through eligibility based on elapsed age/dirty-duration rather than solely on cache membership, so an attacker cannot indefinitely defer write-through by continuously re-touching the same key.

### Proof of Concept
Rust integration test plan (extends existing test infrastructure in `accounts-db/src/accounts_db/tests/impl.rs` and `in_mem_accounts_index.rs`):
1. Build an `AccountsDb` with `IndexLimit::Threshold` (small `num_bytes`/`num_entries_overhead`/`num_entries_to_evict` for fast triggering), similar to `test_purge_unrooted_slot_writes_through_surviving_entry`.
2. Create N pubkeys (N > high-water-mark entries per bin).
3. In a loop over slots `0..M`: for each pubkey, `store_for_tests` into the *current* slot AND ensure the pubkey also still exists in the *previous* unflushed slot (i.e., write to slot `s` and `s+1` before flushing `s`), then `add_root_and_flush_write_cache(s)` for the older slot while pubkey remains cached in slot `s+1`.
4. After many iterations, assert via `db.accounts_index.stats()` that `count_in_mem`/`capacity_in_mem` for the index bin has grown well past `threshold.num_bytes`/high-water-mark, and that `flush_entries_updated_on_disk_immediate` + `flush_entries_updated_on_disk_background` remain at 0 for these pubkeys (i.e., `write_through_pubkeys` never fired), and that `get_and_then` shows `entry.dirty() == true` for all of them indefinitely — demonstrating unbounded in-memory growth beyond the configured threshold with no path to eviction.

    /// the count reaches zero. `max_slot` is not updated; it will become stale if the removed slot
    /// is the highest slot. Returns a vec of pubkeys removed from the index.
    fn remove(&self, pubkeys: impl IntoIterator<Item = Pubkey>) -> Vec<Pubkey> {
        let mut removed_pubkeys = Vec::new();
        for pubkey in pubkeys {
            let Entry::Occupied(mut occupied_entry) = self.entries.entry(pubkey) else {
                // If this has happened the index is corrupted
                panic!("pubkey {pubkey} not found in cache index during remove");
            };
            let (_, ref_count) = occupied_entry.get_mut();
            *ref_count -= 1;
            if *ref_count == 0 {
                occupied_entry.remove_entry();
                self.num_unique_pubkeys.fetch_sub(1, Ordering::Relaxed);
                removed_pubkeys.push(pubkey);
            }
        }
        removed_pubkeys
    }

    fn lock_and_update_slot_list(
        current: &AccountMapEntry<T>,
        new_value: SlotListItem<T>,
        other_slot: Option<Slot>,
        reclaims: &mut ReclaimsSlotList<T>,
        reclaim: UpsertReclaim,
    ) -> usize {
        let mut slot_list = current.slot_list_write_lock();
        let (slot, new_entry) = new_value;
        let (ref_count_change, slot_list_len) = Self::update_slot_list(
            &mut slot_list,
            slot,
            new_entry,
            other_slot,
            reclaims,
            reclaim,
        );

        match ref_count_change.cmp(&0) {
            cmp::Ordering::Equal => {
                // Do nothing
            }
            cmp::Ordering::Greater => {
                // If the ref count change is positive, it must be 1 as only one entry is being added
                assert_eq!(ref_count_change, 1);
                current.addref();
            }
            cmp::Ordering::Less => {
                current.unref_by_count(ref_count_change.unsigned_abs());
            }
        }
        current.mark_dirty();
        slot_list_len
    }
