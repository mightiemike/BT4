## Finding: `KvOnly` state-snapshot restore mode skips Merkle range-proof verification entirely

### Title
State values accepted into the state-KV DB without Merkle range-proof verification in `KvOnly` restore mode - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
`StateSnapshotRestore::add_chunk` in `storage/aptosdb/src/state_restore/mod.rs` dispatches on `StateSnapshotRestoreMode`. In `Default` mode the code explicitly verifies the `SparseMerkleRangeProof` against the manifest's `expected_root_hash` before writing (`jmt_verify_chunk` → `state_value_add_chunk` → `jmt_commit_chunk`). In `KvOnly` mode, the same `add_chunk` receives an identical `proof: SparseMerkleRangeProof` argument but **never calls `verify_chunk`/`verify` on it** — it goes straight to `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?`. [1](#0-0) 

### Finding Description
`KvOnly` is a real, reachable production code path: the backup restore coordinator explicitly restores the "kv snapshot before ledger history start version" using `StateSnapshotRestoreMode::KvOnly`. [2](#0-1) 

The caller `StateSnapshotRestoreController::run_impl` only verifies the *overall* `TransactionInfoWithProof` / ledger-info binding and checks that `manifest.root_hash` matches the transaction-info's state-checkpoint hash once, up front — this proves the *manifest's declared root* is authentic, but it does not prove that any individual chunk of key/value blobs actually hashes into that root. [3](#0-2) 

That per-chunk binding is supposed to be established by `SparseMerkleRangeProof::verify`, which walks the right-siblings from the rightmost leaf of the chunk up to `expected_root_hash`. [4](#0-3) 

But for `KvOnly`, `JellyfishMerkleRestore::verify_chunk` (which calls `SparseMerkleRangeProof::verify` internally) is never invoked; only `StateValueRestore::add_chunk` runs, which persists the K/V blobs as-is. [5](#0-4) 

Compare with `TreeOnly`/`Default`, which both call into `verify_chunk`/`add_chunk_impl` that does `self.verify_chunk(...)?; self.commit_chunk()` — enforcing the increasing-key-order invariant and the proof chain to `expected_root_hash` before any data is committed. [6](#0-5) 

As a result, in `KvOnly` mode a backup-storage provider (the `BackupStorage` trait implementation, e.g. an S3/GCS bucket, or any MITM on that channel) can substitute arbitrary `(StateKey, StateValue)` blobs for a chunk without those values ever being checked against the accumulator/state root that was authenticated via the ledger info. The values get durably written to the state-KV DB (`self.position_db`-style `write_kv_batch`/state-value writer commit) and later get read back as the "restored" state at that version.

### Impact Explanation
This breaks the "authenticated response/data bound to the correct root" invariant that the whole snapshot-restore protocol exists to enforce: a state snapshot backup is supposed to be trustless specifically because every K/V chunk is range-proof bound to a ledger-info-signed root hash. If the `KvOnly` path lets unverified K/V blobs into the state-KV store, a compromised or malicious backup storage backend can inject corrupted account/resource state that later gets treated as genuine committed ledger state (used to compute storage usage, serve reads, and be replayed against by later phases of the same restore). This is a durable-ledger-data corruption / wrong-authenticated-state-view class issue, matching the "state that differs from the correct VM result / corrupts durable ledger data" and "authenticated API output bound to the wrong version/object/proof" impact categories.

### Likelihood Explanation
The `KvOnly` mode is not test-only or debug-only code — it is exercised by the standard restore-coordinator flow (`storage/backup/backup-cli/src/coordinators/restore.rs`) whenever `ledger_history_start_version` differs from the tree-snapshot version, which is a normal restore configuration, not an edge case. Exploitation requires control over (or MITM of) the backup storage the operator restores from — this is a real, non-privileged threat model for anyone restoring a node from third-party/CDN-hosted or attacker-influenced backup archives, which is explicitly one of the scenarios backup-and-restore tooling is designed to defend against via proof verification.

### Recommendation
In `StateSnapshotRestore::add_chunk` (`storage/aptosdb/src/state_restore/mod.rs`), always verify the `SparseMerkleRangeProof` against `expected_root_hash` for the `KvOnly` branch as well, before calling into `kv_restore.add_chunk`. This likely means either (a) unifying `KvOnly` and `Default`/`TreeOnly` to run `verify` against an in-memory/lightweight accumulator reconstruction even when the persistent JMT tree itself is not being written, or (b) requiring `KvOnly` restores to always be paired with a prior/parallel `TreeOnly` or `Default` pass over the same chunks so the proof check is never skipped.

### Proof of Concept
1. Configure a `RestoreCoordinator` with `ledger_history_start_version` earlier than the selected tree snapshot version, so `do_phase_1` is true and a `kv_snapshot` is selected (`storage/backup/backup-cli/src/coordinators/restore.rs:196-260`).
2. Control (or MITM) the `BackupStorage` backing the `manifest_handle` chunks for that KV snapshot so that `Self::read_state_value` returns attacker-chosen `(StateKey, StateValue)` pairs for one chunk, while leaving `chunk.proof`'s bytes anything at all (even garbage), since it is downloaded but discarded for `KvOnly`.
3. `StateSnapshotRestoreController::run_impl` calls `receiver.add_chunk(blobs, proof)` (`storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs:212-215`), which for `KvOnly` mode reaches `StateSnapshotRestore::add_chunk` → `kv_restore.add_chunk(chunk)` with **no call** to `verify`/`verify_chunk` (`storage/aptosdb/src/state_restore/mod.rs:213-218`).
4. The forged state values are committed to the state-KV DB and become the node's "restored" ledger state for that version, despite never having been checked against the ledger-info-authenticated `manifest.root_hash`.

**Note on confidence:** I was not able to fully trace whether a later phase (e.g. transaction replay in phase 1.b, which uses `kv_replay_version`) independently re-derives or cross-checks the state root against these injected KV values before they become permanently authoritative, since that would require deeper tracing through `TransactionRestoreBatchController` and the executor replay path that I did not have iterations left to complete. If such a downstream check exists and rejects a root mismatch before finalizing the restore, the practical severity would be reduced to "wasted work / DoS on restore" rather than durable state corruption — this should be verified before treating the impact as confirmed Critical.

        match self.restore_mode {
            StateSnapshotRestoreMode::KvOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            },
            StateSnapshotRestoreMode::TreeOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_add_chunk"]);
                self.tree_restore
                    .lock()
                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks
                // from min(kv_progress, tree_progress)) would land bytes in (kv_progress,
                // tree_progress] that the tree side skips and therefore does not re-verify.

                        .unwrap()

                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;

                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;

    /// Verifies that the rightmost known leaf exists in the tree and that the resulting
    /// root hash matches the expected root hash.
    pub fn verify(
        &self,
        expected_root_hash: HashValue,
        rightmost_known_leaf: SparseMerkleLeafNode,
        left_siblings: Vec<HashValue>,
    ) -> Result<()> {
        let num_siblings = left_siblings.len() + self.right_siblings.len();
        let mut left_sibling_iter = left_siblings.iter();
        let mut right_sibling_iter = self.right_siblings().iter();

        let mut current_hash = rightmost_known_leaf.hash();
        for bit in rightmost_known_leaf
            .key()
            .iter_bits()
            .rev()
            .skip(HashValue::LENGTH_IN_BITS - num_siblings)
        {
            let (left_hash, right_hash) = if bit {
                (
                    *left_sibling_iter
                        .next()
                        .ok_or_else(|| format_err!("Missing left sibling."))?,
                    current_hash,
                )
            } else {
                (
                    current_hash,
                    *right_sibling_iter
                        .next()
                        .ok_or_else(|| format_err!("Missing right sibling."))?,
                )
            };
            current_hash = SparseMerkleInternalNode::new(left_hash, right_hash).hash();
        }

        ensure!(
            current_hash == expected_root_hash,
            "{}: Root hashes do not match. Actual root hash: {:x}. Expected root hash: {:x}.",
            type_name::<Self>(),
            current_hash,
            expected_root_hash,
        );

        Ok(())
    }

    pub fn add_chunk_impl(
        &mut self,
        chunk: Vec<(&K, HashValue)>,
        proof: SparseMerkleRangeProof,
    ) -> Result<()> {
        self.verify_chunk(chunk, proof)?;
        self.commit_chunk()
    }

    /// Verifies a chunk and stages frozen nodes in memory; call [`Self::commit_chunk`] to
    /// flush. On error, in-memory state is partially updated — abort the restore rather
    /// than calling again.
    pub fn verify_chunk(
        &mut self,
        mut chunk: Vec<(&K, HashValue)>,
        proof: SparseMerkleRangeProof,
    ) -> Result<()> {
        if self.finished {
            info!("State snapshot restore already finished, ignoring entire chunk.");
            return Ok(());
        }

        if let Some(prev_leaf) = &self.previous_leaf {
            let skip_until = chunk
                .iter()
                .find_position(|(key, _hash)| key.hash() > *prev_leaf.account_key());
            chunk = match skip_until {
                None => {
                    info!("Skipping entire chunk.");
                    return Ok(());
                },
                Some((0, _)) => chunk,
                Some((num_to_skip, next_leaf)) => {
                    info!(
                        num_to_skip = num_to_skip,
                        next_leaf = next_leaf,
                        "Skipping leaves."
                    );
                    chunk.split_off(num_to_skip)
                },
            }
        };
        if chunk.is_empty() {
            return Ok(());
        }

        for (key, value_hash) in chunk {
            let hashed_key = key.hash();
            if let Some(ref prev_leaf) = self.previous_leaf {
                ensure!(
                    &hashed_key > prev_leaf.account_key(),
                    "State keys must come in increasing order.",
                )
            }
            self.previous_leaf.replace(LeafNode::new(
                hashed_key,
                value_hash,
                (key.clone(), self.version),
            ));
            self.add_one(key, value_hash);
            self.num_keys_received += 1;
        }

        // Verify what we have added so far is all correct.
        self.verify(proof)?;
        Ok(())
    }
