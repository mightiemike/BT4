Before tracing further, I want to establish the binding explicitly and check it against the actual on-chain contract logic, since that is the ground truth for what a "duplicate deposit" means.

**Binding claimed:** `{Bitcoin move-to-vault outputs Clementine presigned}` == `{deposit blobs the mempool will accept}`, and the claim is that `calc_tx_id` (hash of `version‖vin‖vout‖locktime`) collapses two "distinct" presigned blobs (differing only in witness/merkle-proof/scriptPubkey) into one id, silently dropping one.

This binding is false once you look at what `vin` and `locktime` actually encode, and at what the real `Bridge.deposit` function on-chain does:

- `Bridge.sol::deposit` (the actual consensus-critical contract) computes `bytes32 txId = ValidateSPV.calculateTxId(moveTx.version, moveTx.vin, moveTx.vout, moveTx.locktime)` and enforces `require(!processedTxIds[txId], "txId already spent")`, using the exact same field subset (version/vin/vout/locktime, excluding witness) as `DepositDataMempool::calc_tx_id`. [1](#0-0) 
This is not a mempool-specific shortcut — it mirrors Bitcoin's own consensus txid computation, which by design (SegWit) excludes witness data. If `version`, `vin` (which encodes the exact prevout+sequence being spent) `vout`, and `locktime` are bit-for-bit identical between two blobs, they describe **the same underlying Bitcoin transaction** spending the same UTXO(s); only the signature/witness differs. That's witness malleability, not two distinct deposits. Only one witness variant for a given `vin` can ever be mined and get a valid Merkle-inclusion proof against `BitcoinLightClient`, since spending the same UTXO twice on Bitcoin is impossible. [2](#0-1) 

Furthermore, `Bridge.deposit` requires a valid Schnorr signature from Clementine's N-of-N key over the transaction's actual sighash (`verifySigInTx`), reconstructed from the real `vin`/`vout`/witness/`shaScriptPubkeys`.
