## Analysis Summary

I reduced the external report to its core invariant: **a verification routine must bind ALL security-relevant fields it claims to authenticate — omitting a field lets a party silently substitute an unauthorized value.** In the 0x report, `_validateOrder` verified price/fee/tokens but silently left `takerAddress`/`senderAddress` unchecked, letting the signer smuggle in unauthorized restrictions.

I generated and checked several Aptos-native candidates: (1) transaction/output list proof verification (`types/src/transaction/mod.rs`, `types/src/proof/definition.rs`) — these fully bind write-set hash, event hash, gas, status, and transaction hash to the accumulator-proven `TransactionInfo`; no gap found. (2) accumulator/consistency-proof verification (`types/src/proof/definition.rs`, `TransactionAccumulatorSummary`) — fully bound. (3) chunk-executor / state-sync verification paths — fully bound via `TransactionOutputListWithProof::verify` and `TransactionInfoListWithProof::verify_extends_ledger`. (4) `TransactionOutput::ensure_match_transaction_info` used by replay-verification tooling — **this one has an explicit, code-acknowledged gap.**

### Title
`ensure_match_transaction_info` skips checkpoint-hash binding, letting replay-verify tooling certify a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function that binds a locally re-executed `TransactionOutput` to an authenticated `TransactionInfo` (the leaf object proven into the transaction accumulator/`LedgerInfo`). It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that authenticate the post-execution state root.

### Finding Description [1](#0-0) 

The function compares `status`, `gas_used`, `write_set` hash, and `event_root_hash` against `txn_info`, but the comment at lines 2197‑2202 states outright: [2](#0-1) 

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole correctness oracle used by the replay/backfill-verification tools: [3](#0-2) 

`execute_and_verify` re-executes archived transactions and calls `ensure_match_transaction_info` against the `expected_txn_infos` pulled from the (accumulator-proof-authenticated) backup — exactly the check meant to catch a validator/executor computing a different state root than the one actually committed on-chain. The same function is also used by `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`.

Meanwhile, the real state root computation *does* separately track `position_state_checkpoint_hash` gated by the `compute_trading_native_state_roots` feature flag: [4](#0-3) 

So the checkpoint-hash fields exist and are computed/persisted in `TransactionInfo`, but the one comparator relied upon by replay-verification never checks them.

### Impact Explanation
Replay-verify / state-root-divergence detection is the safety net that catches executor/VM non-determinism or storage-commit bugs (e.g. a bug in the Jellyfish Merkle Tree updater, hot-state handling, or the new "trading-native" position-state tree) **before** it causes a hard fork across validators. Because `ensure_match_transaction_info` never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a local execution that produces a *different* state/hot-state/position-state root than what was actually authenticated and committed on-chain will still be reported as "replay successful." This directly matches the in-scope class "Hard-fork-only divergence during commit, replay, restore, or proof verification" — the exact mechanism intended to surface such divergence is blind to it.

### Likelihood Explanation
This is not a hypothetical: the gap is triggered on every call to `ensure_match_transaction_info` since none of the three checkpoint-hash fields are ever compared, regardless of feature flags. The `position_state_checkpoint_hash` case is explicitly called out by the code's own authors as unresolved (guarded behind enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), and the ordinary `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields are unconditionally skipped as well. Any state-root-affecting bug in execution or storage commit (independent root cause elsewhere) would go undetected by this tool with certainty, not merely with some probability.

### Recommendation
Extend `ensure_match_transaction_info` (`types/src/transaction/mod.rs`) to compute the locally derived state-checkpoint hash (and hot-state / position-state checkpoint hashes when applicable) from the execution output actually being verified, and `ensure!` that they equal `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (on `TransactionInfoV1`), and `txn_info.position_state_checkpoint_hash()` before declaring a match, at least whenever those values are available to the caller (`replay_on_archive`, `aptos_debugger`, `cli::commands`). If a caller genuinely cannot supply the recomputed checkpoint hash for a given txn (non-checkpoint transaction), skip only for that specific transaction rather than unconditionally for the whole verification path.

### Proof of Concept
1. Introduce (or trigger) a state-commit divergence: e.g. a bug that causes the local JMT/hot-state/position-state updater to compute a different post-txn state root than the one embedded in the historical, signed `TransactionInfo` pulled from an authenticated backup/archive.
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs::execute_and_verify`), which calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)`.
3. Because `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, the call returns `Ok(())` even though the locally computed state root differs from the authenticated on-chain root — the tool reports the replay as successful, masking the exact class of bug it exists to detect.

**Caveat / uncertainty:** I could not fully trace whether any other independent code path (outside `ensure_match_transaction_info`) redundantly re-verifies these checkpoint hashes during the same replay-verify invocations (e.g., a separate JMT-proof cross-check inside `aptos_debugger` or `cli/commands.rs`), which could partially mitigate this. Given index-size limits I was not able to read the full bodies of `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`; a Devin session with full repository access should confirm whether those callers add any supplementary checkpoint-hash verification before treating this as conclusively unmitigated.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
