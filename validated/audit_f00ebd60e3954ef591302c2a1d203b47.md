### Title
`accrue`'s pause pass-through returns stale index without updating `last-update`, allowing time-delta to be silently absorbed on later un-pause - (File: mainnet/contracts/vault/v0-vault-stx.clar)

### Summary
The `accrue` function in each vault contract (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-sbtc.clar`) checks the `accrue` pause flag and, when paused, returns the cached `index`/`lindex` without reverting and without updating `last-update` [1](#0-0) . Every state-changing entry point (`system-borrow`, `deposit`, `redeem`, `repay`) unconditionally calls `(try! (accrue))` first and then uses the (possibly stale) `index`/`lindex` and, critically, `get-available-assets`/debt figures computed from state that assumed interest had accrued [2](#0-1) .

### Finding Description
`accrue` is the vault's "health check" analog to the report's `checks-effects-interactions` violation: it is expected to update the interest/liquidity index (the state the rest of the function relies on) before the caller proceeds to mutate debt/supply. Instead of reverting when accrual is paused, it silently substitutes the last known values:

```
(if (get accrue states)
    ;; PAUSED: Pass-through without reverting
    (ok { index: idx, lindex: lidx })
    ...)
``` [1](#0-0) 

Because `last-update` is not advanced while `accrue` is paused, the elapsed-time (`time-delta`) used by `next-index`/`next-liquidity-index` is computed against the pre-pause `last-update` timestamp [3](#0-2) . Meanwhile `system-borrow`, `deposit` and `redeem` continue to execute normally (their own pause flags are independent booleans in the same `pause-states` tuple) and mutate `principal-scaled`, `total-borrowed`, and `assets` using the stale `idx`/`lindex` returned by the pass-through [2](#0-1) . When accrual is later un-paused, the entire accumulated real-world time delta (which may span the whole pause window plus any prior elapsed time) is applied in one `next-index` calculation, but by then `principal-scaled`/`total-borrowed` have already changed (via borrows/repays/deposits/redeems that occurred while paused, at the frozen index). This decouples the compounding base from the true elapsed time, letting debt/interest attribution diverge from what should have accrued, i.e., a "clock advanced only on change" analog where the source of truth (`last-update`) is not invalidated even though state that depends on it (principal, borrowed totals) keeps moving underneath it.

### Impact Explanation
This can cause permanent loss/freezing of protocol-level or LP yield: borrows/redeems executed during the pause window use interest-index values that do not reflect the correct interest owed for that period once accrual resumes, so either LPs permanently lose yield that should have accrued on the principal moved during the pause, or the protocol under/over attributes debt scaled principal relative to the eventual `next-index`. Given `accrue` is a prerequisite of every debt/supply mutating call, this is systemic rather than an isolated edge case.

### Likelihood Explanation
Likelihood depends on the DAO/pause-authority setting `accrue: true` while leaving `borrow`/`deposit`/`redeem`/`repay` unpaused — a plausible partial-pause configuration (e.g., pausing only the interest engine during an oracle/rate-model incident while still allowing withdrawals). Any transaction executed in that window is affected without requiring attacker sophistication.

### Recommendation
Either (a) make `accrue` revert with `ERR-PAUSED` when the accrue flag is set, consistent with `deposit`/`redeem`/`borrow` which do revert on their respective pause flags, or (b) if pausing accrual while allowing other operations is intended, decouple `last-update` tracking so time is not lost/misattributed — e.g., still advance `last-update` to the current block while explicitly freezing the index at 1.0 growth, or block all debt/supply-mutating calls whenever `accrue` is paused.

### Proof of Concept
1. DAO/pause-authority sets `pause-states` with `accrue: true`, all other flags `false`, on `v0-vault-stx.clar` (or any vault) [4](#0-3) .
2. Time passes (blocks advance) — `last-update` is not touched because `accrue`'s paused branch never calls `var-set last-update` [1](#0-0) .
3. During this window, a user calls `borrow` (market → `vault-system-borrow` → vault `system-borrow`), which calls `(try! (accrue))` first, gets the pass-through stale `idx`, then updates `principal-scaled`/`total-borrowed` using that stale index [2](#0-1) .
4. DAO unpauses `accrue`. On the next `accrue` call, `next-index` computes `time-delta` from the original `last-update` (which now spans pre-pause + pause + post-pause time) and applies it against the *new* `principal-scaled` that already includes principal added during the pause window at the old index [3](#0-2) .
5. The interest attributed to principal added during the pause window is computed incorrectly (either double counted against a time delta it wasn't present for, or the reserve/treasury fee split is computed off a distorted `debt-delta`), producing a permanent mismatch between LP yield entitlement and protocol debt accounting.

Uncertainty: I could not fully trace `calc-multiplier-delta`/`calc-index-next` internals or confirm the exact magnitude/direction of the resulting misattribution (whether it favors borrowers or LPs), since those helper functions were not retrieved in this session — a deeper review of `mainnet/contracts/vault/v0-vault-stx.clar`'s rate-model helpers would be needed to quantify exact fund impact.
