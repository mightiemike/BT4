### Title
Nested cycle × vote reward-calculation loop in `MortgageService`/`WithdrawBalanceActuator` can exceed block resource limits when the legacy (pre-VI) reward algorithm path is exercised - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The reported bug class is a claim-function whose cost is `O(positions × farms × epochs)` because it walks every unclaimed epoch in a nested loop, letting an attacker (or just an old, inactive account) make the call unexecutable within the block gas/resource limit. java-tron has an analogous, reachable pattern in its vote-reward accounting: `MortgageService.getOldReward()` iterates once per cycle (`for (long cycle = begin; cycle < end; cycle++) { reward += computeReward(cycle, votes); }`) and, for each cycle, `computeReward(cycle, votes)` iterates over the account's entire vote list, giving an `O(cycles × votes)` cost that is triggered directly by a `WithdrawBalanceContract` transaction.

### Finding Description
`WithdrawBalanceActuator.execute()` calls `mortgageService.withdrawReward(address)` unconditionally for every withdrawal transaction [1](#0-0) , and its `validate()` also calls `mortgageService.queryReward(address)` [2](#0-1) , so both code paths execute the reward computation before the actuator even checks fees.

Inside `MortgageService`, both `withdrawReward()` and `queryReward()` call `computeReward(beginCycle, endCycle, accountCapsule)` [3](#0-2) [4](#0-3) . This method branches: for the range of cycles that predate `newRewardAlgorithmEffectiveCycle`, it delegates to `getOldReward()` [5](#0-4) . `getOldReward()` in turn, when `allowOldRewardOpt()` is not enabled, executes a raw per-cycle loop:

```
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
  if (dynamicPropertiesStore.allowOldRewardOpt()) {
    return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
  }
  long reward = 0;
  for (long cycle = begin; cycle < end; cycle++) {
    reward += computeReward(cycle, votes);
  }
  return reward;
}
``` [6](#0-5) 

`computeReward(cycle, votes)` itself iterates the account's full vote list on every cycle, doing storage reads (`delegationStore.getReward`, `delegationStore.getWitnessVote`) per vote per cycle [7](#0-6) . This reproduces the exact `P (votes) × E (cycles)` nested-loop shape described in the external report: any account/contract that has an old `beginCycle` (i.e., has not withdrawn/queried reward in a long time, or is a fresh account inheriting a stale begin cycle) and a populated vote list will force the transaction to run this loop for every elapsed cycle since `beginCycle`, multiplied by the vote-list length.

Reachability is confirmed for TVM-triggered voting too: `VoteRewardUtil.withdrawReward`/`queryReward`, used by TVM `vote()`/reward query precompiles, follow the identical `beginCycle`/`endCycle`/`computeReward` structure [8](#0-7) , though that path always uses the VI (`getWitnessVi`) delta formula (O(votes) only, no cycle loop) rather than the legacy per-cycle loop, so the worst-case nested loop is specific to the native `MortgageService` path when `allowOldRewardOpt` is disabled.

### Impact Explanation
If `allowOldRewardOpt` is not enabled for a chain/cycle range predating `newRewardAlgorithmEffectiveCycle`, a `WithdrawBalanceContract` (or any transaction indirectly triggering `queryReward`/`withdrawReward`, e.g. via freeze/unfreeze/vote actuators that also invoke `mortgageService.withdrawReward`) for an account with a long-stale `beginCycle` and many concurrent votes can force the node to execute a loop whose iteration count is `(endCycle - beginCycle) × votes.size()`. On chains that have run many cycles (each maintenance cycle is typically ~6 hours; years of cycles accumulate into the thousands) and where an account can vote for many witnesses (bounded by `MAX_VOTE_NUMBER`), this can make individual transaction processing arbitrarily expensive, risking node performance degradation or slow block processing — a DoS-class impact analogous to the reported "block gas limit" issue, though java-tron does not meter this cost with per-instruction gas outside the TVM, so the practical effect is CPU/latency degradation for block producers/validators rather than a reverted-transaction failure.

### Likelihood Explanation
Likelihood is bounded because: (1) the vulnerable per-cycle branch (`getOldReward`'s manual loop) is only exercised for the range of cycles below `newRewardAlgorithmEffectiveCycle`, which is a value fixed once, in the codebase's history (mainnet has already computed/fixed a Merkle root for the new VI algorithm, per `RewardViCalService`'s `MAIN_NET_ROOT_HEX` constant) [9](#0-8) ; (2) `allowOldRewardOpt()` gates whether `getOldReward` uses the cheap VI-based `rewardViCalService.getNewRewardAlgorithmReward` (O(votes)) instead of the expensive manual per-cycle loop [10](#0-9) . I was not able to determine from the available code/index whether `allowOldRewardOpt` is enabled by default on the target network or is still a pending/committee-controlled proposal (`ProposalUtil.java` references it as a settable parameter). If it is still disabled, or if new networks/testnets are deployed with a lower `newRewardAlgorithmEffectiveCycle` cutoff and later have many stale cycles pass, the described nested-loop cost is directly reachable by any ordinary user submitting a `WithdrawBalanceContract`.

### Recommendation
- Confirm `allowOldRewardOpt` is enabled network-wide (or make the VI-based `rewardViCalService.getNewRewardAlgorithmReward` unconditional) so `getOldReward()` never falls back to the manual per-cycle loop in `MortgageService.java` line 265-267.
- Cap the number of cycles processed per call, or require the epoch/cycle range to be swept in bounded batches (mirroring the report's recommendation of masterchef-style O(1) accounting), so no single transaction's reward computation scales with unclaimed cycle count.
- Since the VI-based algorithm already achieves O(votes) reward computation independent of cycle count, prioritize retiring/removing the legacy per-cycle fallback path entirely rather than gating it behind a toggle.

### Proof of Concept
1. Deploy/observe an account (via `AccountCreateContract` or `TransferContract`) whose `DelegationStore` `beginCycle` predates `newRewardAlgorithmEffectiveCycle` by many thousands of cycles (achievable on any network where the account votes early and never withdraws until long after the VI cutover, or on a fresh testnet deployment where `allowOldRewardOpt` has not yet been enabled by committee proposal).
2. Have that account vote for the maximum allowed number of witnesses (`MAX_VOTE_NUMBER`, defined in `common/src/main/java/org/tron/core/config/Parameter.java`) via `VoteWitnessContract`.
3. Broadcast a `WithdrawBalanceContract` from that address. `WithdrawBalanceActuator.execute()`/`validate()` invoke `mortgageService.withdrawReward`/`queryReward`, which route into `computeReward` → `getOldReward`, executing `(endCycle-beginCycle) × votes.size()` iterations of storage reads and BigInteger math [11](#0-10) .
4. Measure processing time/CPU for this single transaction versus a normal transfer to demonstrate disproportionate resource consumption scaling with historical cycle count and vote-list size.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }
