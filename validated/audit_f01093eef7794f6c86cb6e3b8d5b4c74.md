## Verdict: Valid vulnerability

### Title
Outbound accounting corruption on `ExecutePayloadV2` success + `AttachOutboundsToExistingUniversalTx` failure permanently freezes withdrawn funds - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
`ExecuteInboundFundsAndPayload` commits the EVM side-effects of a UEA payload call (via `ExecutePayloadV2`'s internal `writeCache()`) *before* it attempts to translate the resulting withdraw/outbound event into a tracked `OutboundTx`. If that translation step fails, the code still records the payload's `PCTx` as `SUCCESS` and only stores a best-effort `RevertError` string — no `PendingOutbounds` entry, no TSS-signable outbound, and no automatic refund/retry path exists.

### Finding Description
`ExecutePayloadV2` executes the UEA call and gas-fee deduction inside a `CacheContext`, and unconditionally calls `writeCache()` once both succeed [1](#0-0) . This commits any EVM state change made by the payload — including a PRC20 burn/lock performed by `UniversalGatewayPC` when the payload triggers a withdraw — directly onto `sdkCtx`, independent of whether the outbound can later be recorded.

Back in `ExecuteInboundFundsAndPayload`, once `ExecutePayloadV2` returns a non-nil receipt with no error, `payloadPcTx.Status` is set to `"SUCCESS"` immediately [2](#0-1) , and only afterward does the code call `AttachOutboundsToExistingUniversalTx` to parse the receipt logs into an `OutboundTx` and register it in `PendingOutbounds` [3](#0-2) . If that call fails, the only effect is setting `utx.RevertError` — the `payloadPcTx` with `Status = SUCCESS` is still unconditionally appended to `utx.PcTx` right after [4](#0-3) .

`AttachOutboundsToExistingUniversalTx` calls `BuildOutboundsFromReceipt`, which decodes the `UniversalTxOutbound` log emitted by the `UniversalGatewayPC` contract using attacker-influenced fields (`event.ChainId`, `event.Token`) and then performs two lookups that can fail on attacker-chosen values:
- `IsChainOutboundEnabled(ctx, event.ChainId)` — returns an error if outbound is disabled for the destination chain, aborting with `"outbound is disabled for chain %s"` [5](#0-4) .
- `GetTokenConfigByPRC20(ctx, event.ChainId, event.Token)` — returns an error if no token config maps that PRC20 address on that destination chain [6](#0-5) .

Either failure short-circuits `BuildOutboundsFromReceipt` before any outbound is constructed, so `attachOutboundsToUtx` (which writes the `PendingOutbounds` entry) is never reached [7](#0-6) . Since the burn/withdraw already committed via `writeCache()` in `ExecutePayloadV2`, the net effect is: PRC20 balance is destroyed/locked on Push Chain, the `UniversalTx` shows a `SUCCESS` PcTx for the payload, but there is no `PendingOutbounds` entry and no `OutboundTx` for TSS to sign and relay to the destination chain.

### Impact Explanation
This breaks the core invariant that every fund-releasing payload event must yield a trackable, TSS-signable outbound. An unprivileged user submitting an ordinary inbound/CEA payload that calls the gateway's withdraw path with a mismatched or unregistered `(ChainId, Token)` pair (or a chain for which outbound has been paused) causes real funds to be irreversibly burned/locked on the Push Chain EVM side with no corresponding payout ever relayed to the destination chain — a permanent freeze/loss of user funds, and no retry mechanism is visible in this code path (only a `RevertError` string is stored on the UTX, with no automated recovery/rescue path shown for this specific case, as opposed to the CEA-deposit-failure or `INBOUND_REVERT`-based rescue flows in `AttachRescueOutboundFromReceipt`).

### Likelihood Explanation
High reachability: this is triggerable through ordinary user-submitted payload execution with no validator, admin, or TSS collusion. The attacker only needs to construct a `UniversalPayload` whose UEA call reaches `UniversalGatewayPC`'s withdraw path with a token/chain combination not present in `uregistry`'s PRC20 mapping, or targeting a chain temporarily configured with outbound disabled. Since `event.ChainId` and `event.Token` originate from data the payload itself controls (arguments to the gateway contract call), an attacker has direct influence over whether this failure path is hit.

### Recommendation
Make the EVM-side commit and outbound-registration atomic: either (a) defer `writeCache()` in `ExecutePayloadV2` until after `BuildOutboundsFromReceipt`/`attachOutboundsToUtx` have succeeded (wrapping both in the same cache context and only committing once the outbound record is durably created), or (b) if commit must happen first, treat an `AttachOutboundsToExistingUniversalTx` failure as a hard failure state that is queued for automatic retry/rescue (similar to the existing `AttachRescueOutboundFromReceipt` flow) rather than silently recording `PcTx.Status = SUCCESS` with only a `RevertError` string.

### Proof of Concept
1. Register a PRC20 token config for chain A but not chain B (or set chain B's outbound as disabled via registry state).
2. Submit an inbound `UniversalPayload` whose UEA-executed call invokes `UniversalGatewayPC`'s withdraw function specifying chain B and/or a PRC20 address with no matching token config.
3. `ExecutePayloadV2` executes the withdraw call successfully, burns/locks the PRC20 balance, and commits via `writeCache()`.
4. `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt` fails at `IsChainOutboundEnabled` or `GetTokenConfigByPRC20`.
5. Assert: `utx.PcTx` contains an entry with `Status == "SUCCESS"` for the payload execution, `utx.RevertError` is set, and no entry exists in `PendingOutbounds` for the corresponding outbound — funds are burned on Push Chain with no path to reach the destination chain.

func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
