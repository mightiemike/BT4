Confirmed: `freezeBalanceV2` and `unfreezeBalanceV2` are exposed as TVM native contracts (opcodes), callable directly from Solidity contract code within a single transaction, via `Program.freezeBalanceV2()` and the corresponding unfreeze path. This is the concrete atomic "flash mint/burn" analog in java-tron.

### Title
`totalNetWeight`/`totalEnergyWeight` can be flash-manipulated via TVM `freezeBalanceV2`/`unfreezeBalanceV2` native contracts within a single transaction, corrupting resource-usage-transfer ratios - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
A smart contract can call the TVM-exposed native operations `freezeBalanceV2(uint256,uint256)` and `unfreezeBalanceV2(uint256,uint256)` (via `Program.freezeBalanceV2` [1](#0-0) ) atomically within one transaction. These calls immediately mutate the global `totalNetWeight`/`totalEnergyWeight` counters in `DynamicPropertiesStore` [2](#0-1) . These same global weights are used as divisors to compute proportional resource-usage transfer amounts in `UnDelegateResourceProcessor.execute` [3](#0-2) , mirroring the `fShareRatio` manipulation pattern in the referenced report: a self-contained mint-then-burn (here freeze-then-unfreeze) sequence temporarily distorts a shared ratio that other logic in the same or an adjacent transaction relies on.

### Finding Description
`freezeBalanceV2` lets any account (including a contract, via the TVM opcode) increase `totalNetWeight`/`totalEnergyWeight`/`totalTronPowerWeight` by an arbitrary amount up to its TRX balance, instantly and without any waiting period [4](#0-3) . `unfreezeBalanceV2` immediately decreases the same weight again (the withdrawal of the underlying TRX is delayed, but the weight decrement used for resource-share calculations is not) [5](#0-4) .

Between the freeze and unfreeze calls (both of which can be triggered from within a single contract execution, exactly as demonstrated by `TestFreezeV2` calling `freezeBalanceV2` then later `unfreezeBalanceV2` in the test harness) [6](#0-5) , the attacker-inflated `totalEnergyWeight`/`totalNetWeight` is visible to any other logic reading it in the same block, including `UnDelegateResourceProcessor.execute`, which divides by `repo.getTotalEnergyWeight()` / `dynamicStore.getTotalNetLimit()` to compute `unDelegateMaxUsage` for whichever receiver is being processed [7](#0-6) . Temporarily inflating the denominator artificially caps/skews `transferUsage`, and temporarily deflating it (by unfreezing someone else's large stake first, in a hypothetical multi-actor sequence within the block) inflates the transferred usage beyond what should be proportionally justified.

This is directly analogous to the referenced `fShareRatio` bug: a self-reversing balance change (mint+burn / freeze+unfreeze) is used to distort a ratio computed from a mutable global aggregate, and that ratio feeds a downstream accounting decision within the same atomic execution window.

### Impact Explanation
The direct, provable consequence is corrupted bandwidth/energy usage accounting during `unDelegateResource` calls that land in the same block as an attacker's flash freeze/unfreeze, because the divisor (`totalEnergyWeight`/`totalNetWeight`) used to bound `transferUsage` no longer reflects genuine, sustained network stake. This can shift/leak already-consumed usage between owner and receiver accounts, and — via the same divisor being used elsewhere for computing `unDelegateMaxUsage` — bias resource accounting in the manipulator's favor. Unlike the original finding (bounded loss due to fee), this manipulation costs the attacker no explicit fee, only bandwidth/energy for the two native-contract calls, making it cheaper to attempt.

### Likelihood Explanation
Likelihood is limited by two factors: (1) `freezeBalanceV2`/`unfreezeBalanceV2` are only exposed to TVM once `VMConfig.allowTvmFreezeV2()` is active, and only affects other transactions' `unDelegateResource` computations if they occur in the same block/execution context; (2) the actual balance moved is bounded by the attacker's own TRX balance, and unfreezing requires the account to not already be at unfreeze-list capacity. Still, since both operations are unrestricted, feeless from a resource-weight-manipulation standpoint, and immediately effective, a well-resourced account can perform this every block.

### Recommendation
Do not let a single freeze followed immediately by an unfreeze (or vice versa) of the same account/resource type within one block change the effective `totalNetWeight`/`totalEnergyWeight` used for `unDelegateMaxUsage` computations. Consider snapshotting or averaging the weight at the start of the block/cycle for use in `UnDelegateResourceProcessor`, `UnfreezeBalanceV2Processor`, and `FreezeBalanceV2Processor`'s resource-usage calculations, or impose a minimum holding time before a freeze contributes to global weight used in usage-transfer math, similar to the report's recommendation of enforcing a wait time to prevent flash mint/burn-style manipulation.

### Proof of Concept
1. Deploy a contract exposing `freezeBalanceV2(uint256,uint256)` and `unfreezeBalanceV2(uint256,uint256)` calls (as in `TestFreezeV2` bytecode) [8](#0-7) .
2. In transaction T1 (or as an internal call sequence within one transaction), call `freezeBalanceV2(largeAmount, ENERGY)` to spike `totalEnergyWeight` [9](#0-8) .
3. While the inflated weight is in effect within the same block, have a victim/receiver-triggered `UnDelegateResourceContract` execute, whose `unDelegateMaxUsage` is computed using the now-inflated `repo.getTotalEnergyWeight()` [7](#0-6) , producing a `transferUsage` different from the value that would be computed under steady-state weight.
4. Call `unfreezeBalanceV2(largeAmount, ENERGY)` to revert `totalEnergyWeight` back to (approximately) its original value, recovering the frozen TRX after the standard unfreeze delay, having paid only transaction fees for the freeze/unfreeze calls.

  public boolean freezeBalanceV2(DataWord frozenBalance, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner,
        frozenBalance.longValue(), null,
        "freezeBalanceV2For" + convertResourceToString(resourceType), nonce, null);

    try {
      FreezeBalanceV2Param param = new FreezeBalanceV2Param();
      param.setOwnerAddress(owner);
      param.setResourceType(parseResourceCodeV2(resourceType));
      param.setFrozenBalance(frozenBalance.sValue().longValueExact());

      FreezeBalanceV2Processor processor = new FreezeBalanceV2Processor();
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM FreezeBalanceV2: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM FreezeBalanceV2: frozenBalance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
  }

  public void execute(FreezeBalanceV2Param param, Repository repo) {
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();

    byte[] ownerAddress = param.getOwnerAddress();
    long frozenBalance = param.getFrozenBalance();
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }
    switch (param.getResourceType()) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(frozenBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        repo.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(frozenBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        repo.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;
      case TRON_POWER:
        long oldTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        accountCapsule.addFrozenForTronPowerV2(frozenBalance);
        long newTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        repo.addTotalTronPowerWeight(newTPWeight - oldTPWeight);
        break;
      default:
        logger.debug("Resource Code Error.");
    }
