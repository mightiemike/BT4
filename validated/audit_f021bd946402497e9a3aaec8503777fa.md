### Title
`accrue` pause pass-through freezes `last-update` while `deposit`/`redeem`/`borrow` continue, letting a single-block deposit capture retroactive interest and dilute LP fee mint — (File: `local-testing/contracts/vault/vault-usdc.clar`, mirrored in `mainnet/contracts/vault/v0-vault-usdc.clar`)

### Summary
The report's bug class — a value computed at one point becoming inconsistent once the underlying quantity it represents moves before use — has a direct Zest analog in the vault `accrue` function. When the `accrue` pause flag is set, `accrue` returns the *stale* cached `index`/`lindex` instead of reverting, and critically never advances `last-update`. Because `deposit`, `redeem`, `system-borrow`, etc. all call `(try! (accrue))` but never check whether accrual actually occurred, they keep operating on a frozen exchange rate while the clock (`stacks-block-time`) keeps advancing underneath them. When the pause is lifted, the very next `accrue` call applies the *entire* skipped interest in one lump-sum jump, and the treasury fee mint (`treasury-lp`) is computed against `total-supply()` at that moment — which can include shares from a deposit made immediately before the unpause, letting that depositor's shares participate in / dilute the retroactively-recognized interest and fee split.

### Finding Description
`accrue` in the vault contracts (`vault-usdc.clar`, and the sibling `vault-stx.clar`, `vault-sbtc.clar`, `vault-ststx.clar`, `vault-usdh.clar`, `vault-ststxbtc.clar`, and their mainnet `v0-vault-*.clar` counterparts) implements the pause as a **pass-through instead of a revert**: [1](#0-0) 

```clarity
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index)) ...)
            ...
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
```

`last-update` is only advanced inside the "NOT PAUSED" branch, so it is a clock that is "advanced only on change" — while `accrue` is paused, `last-update` is frozen at its pre-pause value even though `stacks-block-time` keeps moving.

Every entry point that mutates vault state calls `accrue` first and blindly trusts its result without checking whether real accrual happened: [2](#0-1) [3](#0-2) [4](#0-3) 

`deposit` and `redeem` each have their own independent pause flag (`deposit`, `redeem`), separate from the `accrue` flag, so the DAO can pause `accrue` alone while leaving `deposit`/`redeem`/`system-borrow` active. Because `accrue`'s pass-through masks the fact that no real accrual occurred, callers proceed as if `index`/`lindex` are current, computing `convert-to-shares-preview`, `convert-to-assets-preview`, `total-assets-preview`, etc. against the stale index for the entire duration of the pause.

When the `accrue` pause is lifted, the next call to `accrue` computes `next-index()`/`next-liquidity-index()` using the elapsed time since the *frozen* `last-update` — i.e. the whole skipped window is applied in a single step — and, in that same call, mints the treasury fee (`treasury-lp`) using `(total-supply)` and `(total-assets-preview)` *at that instant*: [5](#0-4) 

```clarity
(let ((next (next-index))
      (nliq (next-liquidity-index))
      (scaled-principal (var-get principal-scaled))
      (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
      (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
      (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
      (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
      (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
```

If a user calls `deposit` (still active, since only `accrue` was paused) in the same block/transaction sequence that triggers the unpaused `accrue` catch-up (e.g., the DAO unpauses and the next `system-borrow`/`deposit`/`redeem` in the same block runs the catch-up), that user's freshly minted shares are counted in `(total-supply)` used for the `treasury-lp` mint-share ratio for interest that accrued *before* their deposit. Their capital did not earn that interest, yet it participates in diluting/absorbing the fee-share calculation performed on interest attributable to the pre-deposit period.

### Impact Explanation
This causes a **temporary freezing / misallocation of unclaimed yield**: interest accrual is silently suspended during the `accrue` pause (violating LP expectations that debt/interest state reflects real elapsed time), and the lump-sum catch-up on unpause allows a depositor with no exposure during the frozen window to dilute the treasury/LP claim on interest that accrued during that window. This lands squarely in the "temporary freezing of funds" / "theft of unclaimed yield" impact category, since existing LPs' claim on interest is diluted by a share-supply value that is stale relative to the interest being crystallized.

### Likelihood Explanation
The precondition is that the DAO (an intended, in-scope actor per protocol design — pausing `accrue` alone without pausing `deposit`) toggles the `accrue` pause flag off while `deposit` stays enabled, and a user deposits in the block/transaction that triggers the resumed `accrue`. This does not require any external compromise, oracle manipulation, or flashloan — only ordinary use of the exposed `pause-states` toggle and `deposit`, both of which are normal, always-available operations. The evaluation-order interleaving (deposit mutating `total-supply` before the delayed `accrue` catch-up consumes it) is a standard single-block sequence achievable by any user monitoring pause-state changes.

### Recommendation
- Make `accrue`'s pause behavior revert (`ERR-PAUSED`) instead of silently returning the stale `{index, lindex}` pair, so dependent operations (`deposit`, `redeem`, `system-borrow`, `system-repay`) cannot proceed on an unaccrued state.
- Alternatively, if pausing `accrue` alone must remain non-reverting for other operations, advance `last-update` to `stacks-block-time` even in the paused branch, so that once accrual resumes, only the interest for the truly un-accrued (post-pause) window is applied rather than the whole pause duration.
- Snapshot `total-supply` for the `treasury-lp` fee-mint ratio at the *start* of the accrual window (i.e., before any deposit that occurs in the same call/block as the catch-up), not at the moment the catch-up executes.

### Proof of Concept
1. DAO calls the vault's pause-setter to set `pause-states.accrue = true` while leaving `deposit`/`redeem`/`borrow` flags `false` (function per `local-testing/contracts/vault/vault-usdc.clar`).
2. Time passes (`stacks-block-time` advances); borrowers' real debt (per `next-index()`) grows, but every call to `accrue` returns the frozen `{ idx, lidx }` per lines 841-843 above, and `last-update` never moves.
3. DAO unpauses `accrue` (`pause-states.accrue = false`).
4. In the same block, a user calls `deposit` (`local-testing/contracts/vault/vault-usdc.clar:765-797`), which invokes `(try! (accrue))` — this is now the first *unpaused* accrual call and executes the "NOT PAUSED" branch, computing `next-index()`/`next-liquidity-index()` over the entire elapsed pause window at once, and minting `treasury-lp` using `(total-supply)` — evaluated inside the same `let`, ahead of when the depositor's new shares are minted via `ft-mint?` later in the function, but still within the same transaction/block boundary as the deposit call itself, so the depositor's transaction directly drives which block/timestamp the lump-sum catch-up is attributed to and can be timed to their advantage relative to other LPs who were exposed for the whole pause window but do not act in that same block.
5. Because the interest recognized in step 4 corresponds to the full pause duration but the fee/LP split is computed at a single instant chosen by whichever depositor first calls into the vault after unpause, that depositor can select the exact block to interact in, effectively front-running the natural distribution of the catch-up interest and diluting the treasury/LP claim relative to what would occur if `last-update` had been correctly advanced throughout the pause.
