### Title
Unclosed native LevelDB/RocksDB iterator in `TxCacheDB.initCache()` leaks native resources under attacker-influenced startup load - (File: `chainbase/src/main/java/org/tron/core/db2/common/TxCacheDB.java`)

### Summary
`TxCacheDB.initCache()` opens a native database iterator via `persistentStore.iterator()` and consumes it in a `while` loop, but never calls `iterator.close()`, either on the normal completion path or on the early-return path inside the loop. This mirrors the reported bug class: a resource (there, a `context.WithTimeout`; here, a native `DBIterator`/`RocksIterator`) is acquired repeatedly/持续 without deterministic release, so the resource stays alive far longer than intended, causing a build-up of native memory/file handles.

### Finding Description
`initCache()` retrieves an iterator with:
```java
DBIterator iterator = (DBIterator) persistentStore.iterator();
``` [1](#0-0) 

This iterator is never wrapped in try-with-resources and `close()` is never invoked on it, unlike every other call site in the codebase that reads from a `LevelDbDataSourceImpl`/`RocksDbDataSourceImpl` iterator. Both underlying implementations explicitly document that the iterator "holds native resources and MUST be closed after use to prevent memory leaks," and recommend try-with-resources: [2](#0-1) [3](#0-2) 

Every other reader in `LevelDbDataSourceImpl` (`allKeys`, `allValues`, `getlatestValues`, `getValuesNext`, `getKeysNext`, `getNext`, `prefixQuery`, `getTotal`) and `RocksDbDataSourceImpl` correctly uses try-with-resources to guarantee the native iterator is released even on early return or exception: [4](#0-3) 
`TxCacheDB.initCache()` is the outlier that both (a) never closes the iterator and (b) has an early `return;` mid-loop on malformed entries, guaranteeing the leak whenever that branch is taken:
```java
if (ArrayUtils.isEmpty(entry.getKey()) || ArrayUtils.isEmpty(entry.getValue())) {
  return;
}
``` [5](#0-4) 

`initCache()` is invoked from `TxCacheDB.init()` when the recent-transaction-cache size doesn't match `MAX_BLOCK_SIZE`, which happens on node (re)start / re-sync: [6](#0-5) 

### Impact Explanation
Each call to `TxCacheDB.newInstance()` / re-`init()` leaks one native iterator handle (LevelDB snapshot/iterator or RocksDB `RocksIterator`+`ReadOptions`), consuming native (off-heap) memory and open file/handle resources that are not reclaimed by the JVM garbage collector, since these are backed by JNI objects. This is a genuine resource leak matching the reported bug class (leaked contexts stacking up), but the trigger is a node-lifecycle/DB-initialization event rather than something an anonymous remote peer can repeatedly invoke on a running, already-initialized node. I could not confirm a path by which an ordinary broadcast transaction or RPC call causes `TxCacheDB.init()`/`initCache()` to be invoked repeatedly at runtime; it appears to run once per process lifetime (or per DB-reset), which limits it to at most a small, bounded leak per node run rather than an unbounded DoS vector reachable from RPC/broadcast tx as the validation rules require.

### Likelihood Explanation
Low likelihood of remote/RPC-triggered exploitation because `initCache()`/`init()` is startup/recovery-path code (invoked once when the tx-cache size doesn't match `MAX_BLOCK_SIZE`), not on the hot path for RPC handling, transaction broadcast, or contract execution. I was not able to verify (within available context) any way for a remote/anonymous actor to repeatedly re-trigger `TxCacheDB.init()` on a live node, which is required to accumulate the leak.

### Recommendation
Wrap the iterator in try-with-resources (or an explicit `try/finally { iterator.close(); }`) so it is released deterministically on every code path, including the early `return`:
```java
private void initCache() {
  long start = System.currentTimeMillis();
  try (DBIterator iterator = (DBIterator) persistentStore.iterator()) {
    long persistentSize = 0;
    while (iterator.hasNext()) {
      Entry<byte[], byte[]> entry = iterator.next();
      if (ArrayUtils.isEmpty(entry.getKey()) || ArrayUtils.isEmpty(entry.getValue())) {
        return;
      }
      bloomFilters[1].put(entry.getKey());
      persistentSize++;
    }
    ...
  }
}
```

### Proof of Concept
Not applicable as a remotely triggerable PoC: reaching `initCache()` requires controlling node startup/DB-recovery conditions (e.g., forcing `recentTransactionStore.size() != MAX_BLOCK_SIZE`) rather than sending an RPC request or broadcasting a transaction to a running node. I could not construct a concrete remote-trigger PoC given the available context; this weakens confidence that the finding meets the "reachable from anonymous RPC/broadcast tx/contract call" bar required by the validation rules.
