Reorg-permission check uses purely local, unsynchronized signer timestamps around a hard deadline, letting a minority miner force signers to disagree on tenure validity - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
The external report's bug class is: a state-transition decision hinges on a hard time cutoff, and an attacker who controls *when* a transaction lands relative to that cutoff (via delay/mempool manipulation) can flip the outcome between two very different results for the same logical action. The stacks-core analog is `SortitionData::check_parent_tenure_choice`, which decides whether a competing miner is allowed to reorg a prior tenure. The decision is based on comparing two **locally recorded wall-clock timestamps** against the `first_proposal_burn_block_timing` threshold, rather than any value derived from chain state that all signers agree on.

### Finding Description
`check_parent_tenure_choice` in [1](#0-0)  decides whether a new tenure is allowed to reorg a previously-mined tenure. For each reorged tenure that already produced exactly one globally-accepted block, the signer computes:

```
proposal_to_sortition = sortition_state_received_time - local_block_info.approved_time
allow_reorg = proposal_to_sortition < first_proposal_burn_block_timing
``` [2](#0-1) 

Both timestamps are strictly local, per-signer values:
- `sortition_state_received_time` comes from `signer_db.get_burn_block_receive_time(&self.burn_block_hash)`, i.e. the local time *this* signer's node happened to receive/record the burn block [3](#0-2) .
- `local_block_info.approved_time` comes from `signer_db.get_first_approved_block_in_tenure`, i.e. the local time *this* signer happened to approve/sign the reorged tenure's first block [4](#0-3) .

Neither value is a consensus-derived quantity (unlike a burn height or a block's on-chain timestamp); each signer computes it from its own network-latency-dependent observation history. The result of this comparison feeds directly into `validate_tenure_change_payload`, which turns a `false` result into `RejectReason::ReorgNotAllowed` [5](#0-4) , and an analogous path exists in `v2.rs`'s tenure-extend/reorg checks that read local timing too [6](#0-5) .

This is structurally identical to the external report's bug: a binary outcome (allow vs. reject) is decided by comparing an elapsed-time value against a fixed threshold, where the elapsed-time value's endpoints are subject to network/propagation jitter that an adversarial actor can influence by choosing *when* to broadcast/propose. In the Gamma report, the attacker delays inclusion of a victim's transaction across a re-lock boundary; here, a competing miner can choose the timing of the tenure-change block/tenure broadcast (or exploit ordinary propagation-delay variance) so that some signers' locally observed `proposal_to_sortition` falls just under `first_proposal_burn_block_timing` while other signers' falls just over it — because each signer's `sortition_state_received_time` and `approved_time` are recorded independently based on when messages reach that specific signer.

### Impact Explanation
Because the threshold comparison is evaluated independently per signer against local timestamps rather than a value that is fixed/shared for all signers, different honest signers can reach opposite verdicts (`Ok(true)` vs `Ok(false)`) for the exact same tenure-change block. This is a validation verdict two nodes disagree on: some signers will treat the prior tenure as superseded and sign the reorging block, while others will reject it with `ReorgNotAllowed`. This can split signature weight across two competing chain views, producing a temporary tip disagreement in the signer set until the discrepancy resolves — matching the "High" impact category (minority-triggerable divergence causing temporary tip disagreement).

### Likelihood Explanation
No majority stake or admin/privileged key is required. Any miner attempting to win a competing tenure and reorg a single-block prior tenure can trigger the codepath; the disagreement arises from ordinary signer-to-signer network latency variance around the `first_proposal_burn_block_timing` boundary, and a miner has some ability to further widen this variance by choosing when they broadcast the burn-chain block/commit relative to signers' processing of the previous block. The precondition (previous tenure produced exactly one globally-accepted block) is a normal, frequently-occurring chain state, not a rare edge case, which increases realistic likelihood versus the original report's "last-second" scenario.

### Recommendation
Avoid basing multi-party-visible acceptance decisions on unsynchronized local timestamps. Where possible, derive the "was the tenure's block proposed early enough" determination from consensus-visible data (e.g., burn-block heights/consensus hashes recorded by the node, or a majority-agreed value broadcast via StackerDB) rather than each signer's own `get_burn_block_receive_time`/`approved_time`. At minimum, document that this check is best-effort and intentionally tolerant of transient disagreement, and ensure the signer coordination protocol can safely converge (e.g., via re-evaluation windows or requiring supermajority in one direction) rather than assuming all honest signers compute the same boolean.

### Proof of Concept
This is a design/timing-window analysis rather than a directly reproducible unit test, since it depends on network-latency race conditions across independent signer processes:
1. Miner A mines tenure T with exactly one globally-accepted block; each signer records `approved_time` locally as it independently signs that block, so approval time already varies slightly across signers.
2. Miner B wins the next sortition and proposes a `TenureChange` (`BlockFound`) reorging tenure T.
3. Each signer independently computes `sortition_state_received_time` (local receipt of the new burn block) and evaluates `sortition_state_received_time - approved_time` against `first_proposal_burn_block_timing`, in `check_parent_tenure_choice` [2](#0-1) .
4. If the true elapsed time is close to the configured `first_proposal_burn_block_timing` value, ordinary propagation jitter between signers (further amplifiable by Miner B choosing broadcast timing) causes some signers to compute a value just below the threshold (reorg allowed) and others just above it (reorg rejected), leading `validate_tenure_change_payload` to accept the block for a subset of signers and reject it (`ReorgNotAllowed`) for others [7](#0-6) .

    pub fn check_parent_tenure_choice(
        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        first_proposal_burn_block_timing: &Duration,
    ) -> Result<bool, SignerChainstateError> {
        // if the parent tenure is the last sortition, it is a valid choice.
        // if the parent tenure is a reorg, then all of the reorged sortitions
        //  must either have produced zero blocks _or_ produced their first (and only) block
        //  very close to the burn block transition.
        if self.prior_sortition == self.parent_tenure_id {
            return Ok(true);
        }
        info!(
            "Most recent miner's tenure does not build off the prior sortition, checking if this is valid behavior";
            "sortition_state.consensus_hash" => %self.consensus_hash,
            "sortition_state.prior_sortition" => %self.prior_sortition,
            "sortition_state.parent_tenure_id" => %self.parent_tenure_id,
        );

        let tenures_reorged =
            client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)?;
        if tenures_reorged.is_empty() {
            warn!("Miner is not building off of most recent tenure, but stacks node was unable to return information about the relevant sortitions. Marking miner invalid.");
            return Ok(false);
        }

        // this value *should* always be some, but try to do the best we can if it isn't
        let sortition_state_received_time =
            signer_db.get_burn_block_receive_time(&self.burn_block_hash)?;

        // Track which tenures are superseded by the reorg, then mark them in
        // the DB after the reorg is permitted.
        let mut superseded_tenures = Vec::new();
        for tenure in tenures_reorged.iter() {
            if tenure.consensus_hash == self.parent_tenure_id {
                // this was a built-upon tenure, no need to check this tenure as part of the reorg.
                continue;
            }

            // disallow reorg if more than one block has already been signed
            let globally_accepted_blocks =
                signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
            if globally_accepted_blocks > 1 {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already more than one globally accepted block.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => ?tenure.first_block_mined,
                    "globally_accepted_blocks" => globally_accepted_blocks,
                );
                return Ok(false);
            }

            let Some(first_block_mined) = &tenure.first_block_mined else {
                // The node saw no blocks in this tenure, so the reorg takes nothing away from
                // the canonical chain. We may still hold a signature over a block in it that
                // the node has never seen (a block we accept locally is not handed to the node
                // until the whole signer set has signed it), so the reorg must still be
                // recorded if it is permitted.
                superseded_tenures.push(tenure);
                continue;
            };
            let Some(local_block_info) =
                signer_db.get_first_approved_block_in_tenure(&tenure.consensus_hash)?
            else {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks, and there is no local knowledge for that tenure's block timing.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => %first_block_mined,
                );
                return Ok(false);
            };

            let checked_proposal_timing = if let Some(sortition_state_received_time) =
                sortition_state_received_time
            {
                // how long was there between when the proposal was received and the next sortition started?
                let proposal_to_sortition = if let Some(approved_at) =
                    local_block_info.approved_time
                {
                    sortition_state_received_time.saturating_sub(approved_at)
                } else {
                    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
                    0
                };
                if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
                    info!(
                        "Miner is not building off of most recent tenure. A tenure they reorg has already mined blocks, but the block was poorly timed, allowing the reorg.";
                        "parent_tenure" => %self.parent_tenure_id,
                        "last_sortition" => %self.prior_sortition,
                        "violating_tenure_id" => %tenure.consensus_hash,
                        "violating_tenure_first_block_id" => %first_block_mined,
                        "violating_tenure_proposed_time" => local_block_info.proposed_time,
                        "new_tenure_received_time" => sortition_state_received_time,
                        "new_tenure_burn_timestamp" => self.burn_header_timestamp,
                        "first_proposal_burn_block_timing_secs" => first_proposal_burn_block_timing.as_secs(),
                        "proposal_to_sortition" => proposal_to_sortition,
                    );
                    superseded_tenures.push(tenure);
                    continue;
                }
                true
            } else {
                false
            };

            warn!(
                "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks.";
                "parent_tenure" => %self.parent_tenure_id,
                "last_sortition" => %self.prior_sortition,
                "violating_tenure_id" => %tenure.consensus_hash,
                "violating_tenure_first_block_id" => %first_block_mined,
                "checked_proposal_timing" => checked_proposal_timing,
            );
            return Ok(false);
        }
        // Every reorged tenure cleared the rules, so the reorg is permitted.
        for tenure in superseded_tenures {
            self.record_superseded_tenure(signer_db, tenure);
        }
        Ok(true)
    }
