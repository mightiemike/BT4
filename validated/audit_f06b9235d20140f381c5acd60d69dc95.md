### Title
ZKProofStore is a non-revoking, fee-agnostic cache keyed only by txid, allowing `checkProof` to skip zk re-verification when `calcFee()` changes between mempool validation and block-time re-validation - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
`checkProof` caches only a boolean pass/fail result in `ZKProofStore`, keyed by `tx.getTransactionId()`, and returns the cached `true` without re-running `librustzcashSaplingCheckSpend/CheckOutput/FinalCheck` on a repeat `validate()` call. `ZKProofStore` extends the plain `TronDatabase` (not `TronStoreWithRevoking`), so unlike every other accounting-relevant store (`AccountStore`, `NullifierStore`, `DynamicPropertiesStore`), its writes are **not** part of the revoking-session mechanism and survive `session.reset()`/rollback. Because the fee (and thus the `valueBalance` bound into the sapling `FinalCheck`) depends on external, mutable state (`calcFee()` checks whether `toAccount` currently exists), a transaction can be tentatively validated once with one fee, have its `ZKProofStore` entry persist through a session reset that discards everything else, and later be re-validated/executed with a different fee while skipping the cryptographic re-check.

### Finding Description
`checkProof` is:
```java

  ...
  ZKProofStore proofStore = chainBaseManager.getProofStore();
  if (proofStore.has(tx.getTransactionId().getBytes())) {
    if (proofStore.get(tx.getTransactionId().getBytes())) {
      return;                      // <-- skips CheckSpend/CheckOutput/FinalCheck entirely
    } else {
      throw new ZkProofValidateException("record is fail, skip proof", false);
    }
  }
  ...

}

`ZKProofStore` bypasses the revoking-store mechanism used by every other consensus-relevant store:
```java
public class ZKProofStore extends TronDatabase<Boolean> {
  ...
  public void put(byte[] key, Boolean item) { ...; dbSource.putData(key, b); }
}
``` [4](#0-3) 
Compare to `AccountStore`, `NullifierStore`, `DynamicPropertiesStore`, etc., which all `extend TronStoreWithRevoking`, i.e., they participate in `revokingStore` sessions and are rolled back on `session.reset()`/failed processing. `ZKProofStore` writes are direct to `dbSource` and are permanent regardless of session outcome.

Exploit flow:
1. Manager applies transactions tentatively when they enter the mempool, inside a temp `ISession` that is merged into the shared pending `session`:
```java
try (ISession tmpSession = revokingStore.buildSession()) {
  processTransaction(trx, null);
  ...
  tmpSession.merge();
}
``` [5](#0-4) 
2. When block generation starts, all pending/tentative session state is discarded and rebuilt from the last confirmed block:
```java
session.reset();
session.setValue(revokingStore.buildSession());
``` [6](#0-5) 
3. Pending transactions (still held in `pendingTransactions`, independent of session state) are then reprocessed one by one via `processTransaction(trx, blockCapsule)` inside fresh per-tx sessions, calling `validate()`/`checkProof()` again.
4. Because `ZKProofStore`'s earlier `true` entry (recorded during step 1's tentative validation with `fee1`) was never rolled back by `session.reset()`, `checkProof()` on the same transaction id in step 3 short-circuits at `proofStore.has(...)==true` and returns without recomputing `valueBalance` or calling `FinalCheck` — even though the account-existence state used by `calcFee()` may now differ (e.g., because an account-creating transaction was processed just before it within the same block-building pass, or by governance changing `getShieldedTransactionFee()`/`getShieldedTransactionCreateAccountFee()` between the two passes).
5. `execute()` recomputes `fee` fresh each call (`long fee = calcFee(shieldedTransferContract);`) and uses this second, different fee value to run `Commons.adjustTotalShieldedPoolValue(...)`, while the actual sapling value commitments/binding signature in the transaction were only ever cryptographically checked against the *first* fee's `valueBalance`. The two are never required to match.

### Impact Explanation
`totalShieldedPoolValue` (the accounting invariant tying the shielded pool's tracked value to the actual sapling value commitments) can be adjusted by a `valueBalance` that was never verified by `librustzcashSaplingFinalCheck` for the fee actually used at execution time. This is a genuine "recompute inconsistently with cached proof" divergence: the on-chain accounting can drift from the amount cryptographically proven to move in/out of the shielded pool, corrupting `totalShieldedPoolValue` and creating a persistent state-integrity defect in the shielded pool bookkeeping (as opposed to unauthorized fund transfer directly, since the note-level value commitments and nullifiers are still checked independently for that specific fee only once).

### Likelihood Explanation
Requires: (1) a shielded transfer with a transparent output to a currently-non-existent account so `calcFee()` is state-dependent, (2) that transaction being pushed to the mempool/tentatively processed at least once (a routine step for every pushed transaction, not privileged), and (3) the target account's existence state (or the governance-configured fee constants) changing before the transaction is finally packed/re-processed into a block. Steps (1) and (2) are fully attacker-controlled with an ordinary unprivileged transaction; step (3) can be attacker-triggered by submitting a second, ordinary funding transaction to the same target address timed to land in the mempool/block-building window before the shielded transaction is finally packed. The `session.reset()` discarding all revoking-store state while `ZKProofStore` retains its entry is a deterministic code-path property, not a race condition, making the underlying cache-staleness reproducible in a unit/integration test even without perfectly winning a network race.

### Recommendation
- Make `ZKProofStore` participate in the revoking-store mechanism (`extends TronStoreWithRevoking`) so cached proof results are rolled back along with all other tentative state on `session.reset()`/failed processing, consistent with `NullifierStore`, `AccountStore`, etc.
- Additionally/alternatively, do not cache proof validity independent of the fee-dependent `valueBalance`: include the computed `fee`/`valueBalance` (or a hash of it) as part of the cache key, or simply drop the fee dependence from `calcFee()` for shielded transfers so the sapling-bound `valueBalance` is deterministic and independent of external account existence at validate-time vs execute-time.
- At minimum, recompute and re-verify `valueBalance`/`FinalCheck` whenever `calcFee()` at `execute()` time differs from the fee used when the cached proof entry was recorded.

### Proof of Concept
Integration test plan (Java, using existing `ShieldedTransferActuatorTest`/`ManagerMockTest` infrastructure):
```java
@Test
public void cachedProofSkipsRevalidationWhenFeeChanges() throws Exception {
  // 1. Build a shielded transfer tx to a transparent toAddress that does NOT exist yet.
  //    Craft spend/receive descriptions + binding signature consistent with
  //    valueBalance1 = toAmount - fromAmount + createAccountFee.
  TransactionCapsule tx = buildShieldedTxToNonexistentAccount();
  ShieldedTransferActuator actuator1 = newActuator(tx);

  // 2. First validate(): toAccount == null -> fee1 = createAccountFee.
  //    checkProof() cache-misses, runs full CheckSpend/CheckOutput/FinalCheck (must pass),
  //    then recordProof(tid, true) is persisted directly to ZKProofStore (non-revoking).
  actuator1.validate();
  Assert.assertTrue(dbManager.getChainBaseManager()
      .getProofStore().get(tx.getTransactionId().getBytes()));

  // 3. Simulate the mempool->block session reset: create the target account
  //    via a normal TransferContract, WITHOUT reverting the ZKProofStore entry
  //    (mirrors Manager#generateBlock's session.reset() which does not touch ZKProofStore).
  createAccount(toAddress);

  // 4. Second validate() on a fresh actuator instance for the SAME tx id:
  //    calcFee() now returns fee2 = normal shieldedTransactionFee (fee2 != fee1).
  ShieldedTransferActuator actuator2 = newActuator(tx);
  actuator2.validate(); // must NOT throw, because checkProof() hits the cache and returns early

  // 5. Execute and assert the value actually deducted from totalShieldedPoolValue
  //    uses fee2, while the binding signature only ever proved valueBalance1 (with fee1).
  TransactionResultCapsule ret = new TransactionResultCapsule();
  long poolBefore = dbManager.getDynamicPropertiesStore().getTotalShieldedPoolValue();
  actuator2.execute(ret);
  long poolAfter = dbManager.getDynamicPropertiesStore().getTotalShieldedPoolValue();

  long trueValueBalance = addExact(subtractExact(toAmount, fromAmount), fee1); // cryptographically proven
  long recordedValueBalance = poolBefore - poolAfter; // uses fee2 internally

  // Assertion demonstrating the bug: recorded accounting deviates from the
  // cryptographically-verified valueBalance because FinalCheck was skipped on revalidation.
  Assert.assertNotEquals(trueValueBalance, recordedValueBalance);
}
```
This test demonstrates that `checkProof`'s cache returns `true` on the second `validate()` call despite `calcFee()` (and therefore the sapling-bound `valueBalance`) having changed, and that `execute()`'s `adjustTotalShieldedPoolValue` uses the new, unverified fee value instead of the one actually checked by `librustzcashSaplingFinalCheck`.
