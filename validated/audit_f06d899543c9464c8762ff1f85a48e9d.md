Confirmed: `ExchangeCreateActuator` is fully permissionless—any account can create an Exchange by paying `getExchangeCreateFee()`, becoming its "creator" [1](#0-0) . This confirms the attack path is viable without any special/administrative privilege.

### Title
Bancor-style Exchange price can be manipulated within a single block via unaveraged token-balance ratio - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
TRON's on-chain Bancor-style Exchange feature (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) prices trades using the *instantaneous* `firstTokenBalance`/`secondTokenBalance` of the exchange pool, with no time-weighted average or cooldown. Any unprivileged account can create an exchange (becoming its "creator"), then within the very same block: inject a large skewing amount of one token to move the price, let/force a victim's `ExchangeTransactionContract` execute against the manipulated ratio, and withdraw the injected liquidity back out — extracting value from the victim in a single-block sandwich, structurally identical to the reported "utilization rate manipulated via instantaneous, unaveraged debt value" bug class.

### Finding Description
The Exchange pricing math lives in `ExchangeCapsule.transaction()`, which reads the pool's current `firstTokenBalance`/`secondTokenBalance` directly and feeds them into the Bancor formula implemented in `ExchangeProcessor`/`SafeExchangeProcessor` — there is no averaging or TWAP mechanism whatsoever: [2](#0-1) 

The core price formula itself operates purely on the balances passed in, with no historical smoothing: [3](#0-2) 

`ExchangeCreateActuator` lets any funded account create a brand-new exchange and become its `creatorAddress`, entirely permissionlessly (only a configurable TRX fee is charged): [4](#0-3) 

`ExchangeInjectActuator` and `ExchangeWithdrawActuator` allow the exchange creator to instantly add or remove large amounts of either token, directly and immediately shifting `firstTokenBalance`/`secondTokenBalance` — and thus the trade price for anyone else who calls `ExchangeTransactionContract` in between: [5](#0-4) [6](#0-5) 

`ExchangeTransactionActuator` — callable by *any* account, not just the creator — executes trades strictly against the current pool ratio with only a caller-specified minimum-received (`tokenExpected`) slippage guard, which does not protect against pool-side manipulation happening in adjacent transactions of the same block: [7](#0-6) 

Because Tron block production packs multiple transactions per block and there is no mechanism preventing the creator's `Inject` → victim's `Transaction` → creator's `Withdraw` sequence from all landing in the same block (or consecutive blocks under proposer/attacker control), an attacker fully controls both ends of the price move, exactly mirroring the reported bug class where "the code used to calculate the utilization rate does not take into account the average ... allowing for this manipulation to occur."

### Impact Explanation
An attacker who creates (or already controls) an Exchange pool can sandwich any counterparty's `ExchangeTransactionContract` trade: inject liquidity to skew the price against the victim, let the victim's already-broadcast transaction execute at the worse rate, then withdraw the injected liquidity to reclaim it (minus negligible fees, since `calcFee()` returns 0 for inject/withdraw/transaction). This constitutes direct extraction of victim funds/asset value through the protocol's own accounting — an asset/accounting-corruption impact reachable purely from broadcast transactions, without any privileged role.

### Likelihood Explanation
Likelihood is high for any actively-traded Exchange pool: the actions required (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) are all standard, unprivileged broadcast transaction types available to any account, cost only ordinary bandwidth/TRX fees, and the manipulation completes deterministically within the ordinary block-packing window since no averaging or per-block rate limiting exists on the pool balances used for pricing.

### Recommendation
Introduce a time-weighted/average balance (or minimum holding period) for the token balances used in `ExchangeCapsule.transaction()`'s pricing formula, analogous to the fix recommended in the source report — i.e., use an averaged `firstTokenBalance`/`secondTokenBalance` rather than the instantaneous value — and/or enforce a cooldown between `ExchangeInjectContract`/`ExchangeWithdrawContract` and subsequent `ExchangeTransactionContract` executions on the same exchange within a block.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create exchange E with tokens A/B (`ExchangeCreateActuator`).
2. Victim broadcasts `ExchangeTransactionContract` intending to trade A for B at the currently observed ratio, setting `tokenExpected` based on that ratio.
3. Before the victim's transaction is packed, attacker (as creator) broadcasts `ExchangeInjectContract` with a large skewed `tokenId`/`quant` to shift `firstTokenBalance`/`secondTokenBalance` unfavorably for the victim's trade direction (`ExchangeInjectActuator` lines 60-83).
4. Victim's `ExchangeTransactionContract` executes via `ExchangeCapsule.transaction()` against the skewed ratio — still passing because `tokenExpected` slippage check only guards against *some* worse price, not the attacker-induced one, if set loosely, or the attacker can time-order transactions within the block they control as a witness/relayer.
5. Attacker immediately broadcasts `ExchangeWithdrawContract` to pull the injected liquidity back out (`ExchangeWithdrawActuator` lines 63-89), restoring the pool close to its original ratio and capturing the spread extracted from the victim's trade.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
