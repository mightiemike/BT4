### Title
Unbounded allocation from attacker-controlled Cairo0 syscall array-length felt - (File: `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`)

### Summary
The Envoy Gateway advisory describes a class of bug where a size value taken directly from untrusted, attacker-supplied data is used to drive a memory allocation (`make([]byte, h.Size)`) before that size is validated against the actual bounds of the data available, allowing a single malicious input to trigger an unrecoverable OOM and crash a shared, persistent service. The analogous pattern exists in the sequencer's deprecated (Cairo 0) syscall calldata-reading path: `read_felt_array` reads a raw felt as the array size and converts it to a `usize` without validating it against the actual number of remaining memory cells or against any sane upper bound (e.g. `SIERRA_ARRAY_LEN_BOUND`), then immediately passes that size into `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)`.

### Finding Description
`read_felt_array` in [1](#0-0)  reads `array_size` as a raw `Felt` from the syscall request segment (`felt_from_ptr`), and — unless it is exactly zero — converts it directly to `usize` (`usize::try_from(array_size.to_biguint())?`) and forwards it as the read length to `felt_range_from_ptr`:

```
let array_size = felt_from_ptr(vm, ptr)?;
...
Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
```

`felt_range_from_ptr` is defined in [2](#0-1)  and simply forwards the untrusted `size` to `vm.get_integer_range(ptr, size)` with no upper-bound check performed by blockifier before the call. Unlike the "modern" syscall variant `read_felt_array` in [3](#0-2) , where the size is computed as the *difference between two already-existing pointers in the same segment* (`array_data_end_ptr - array_data_start_ptr`, i.e., naturally capped by data that has actually been written), the deprecated-syscall path takes the length as a raw, unconstrained felt value that a Cairo 0 contract can set to anything it likes when constructing the `LibraryCallRequest`/`CallContractRequest`/`DeployRequest` before invoking `library_call`, `call_contract`, or `deploy`. There is no check comparable to the OS's own `calldata_size` sanity check seen in `execute_entry_point.cairo` (`assert [range_check_ptr] = calldata_size + 2**128 - SIERRA_ARRAY_LEN_BOUND`) applied at this syscall-argument-reading layer for the deprecated syscalls.

Because Starknet felts can represent values far larger than any real array (up to ~2^251, with `usize::try_from` still succeeding for any value below `usize::MAX`, i.e. up to 2^64 on 64-bit hosts), a contract can set `array_size` to an astronomically large value and have it flow, unchecked, into a VM memory-range read that will attempt to allocate/scan a correspondingly large buffer.

### Impact Explanation
Any transaction that invokes a deployed Cairo 0 contract's `library_call`, `call_contract`, or `deploy` syscall path (a widely-reachable, unprivileged action available to any contract call/invoke transaction) can supply an attacker-chosen size felt for the calldata array. This drives an allocation/read attempt sized by that felt rather than by the real, bounded calldata, which can cause the executing sequencer node to OOM or panic while validating/executing a single transaction — a single-transaction, non-volumetric denial of service against the shared block-building/validation process, consistent with the "honest node unable to process new transactions" impact class.

### Likelihood Explanation
Reaching this path requires only a standard, unprivileged transaction that calls into (or deploys and calls) a Cairo 0 class implementing `library_call`/`call_contract`/`deploy`, and crafting the request felt for the array length maliciously. No special privileges, no p2p/prover assumptions are needed — this is directly reachable by any transaction sender/contract deployer during normal blockifier execution.

### Recommendation
Add an explicit upper-bound / sanity check on `array_size` in `read_felt_array` (deprecated syscalls) before converting to `usize` and before calling `felt_range_from_ptr`/`vm.get_integer_range` — e.g., bound it by `SIERRA_ARRAY_LEN_BOUND` (as already done for the OS's own calldata-size check) or by the actual number of cells present in the target segment, mirroring the safety property that the non-deprecated syscall variant gets "for free" by deriving size from two already-materialized pointers.

### Proof of Concept
Not verified with a runnable repro in this pass (report reviewed conceptually against the code paths). To confirm exploitability, a Devin agent with code execution should:
1. Build a minimal Cairo 0 contract that invokes `library_call_syscall`/`call_contract_syscall` with a `calldata_size` felt set to a very large value (e.g. `2^63`) while leaving the calldata pointer valid but pointing to a much smaller actual segment.
2. Execute this via blockifier's deprecated-syscall entry point execution and observe whether `felt_range_from_ptr`/`vm.get_integer_range` attempts a large allocation before returning a memory error, and whether this is caught gracefully or crashes/OOMs the process.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,

    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
