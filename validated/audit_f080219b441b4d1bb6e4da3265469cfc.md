### Title
Hardened `divideCeilExact`/`addExact` resource accounting throws uncaught `ArithmeticException` on legitimate large usage values, causing consensus-critical DoS - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
This is an analog of the reported Uniswap `UniswapV2OracleLibrary.currentCumulativePrices()` bug class: code that used to rely on silent wraparound arithmetic was "fixed" by switching to checked/exact arithmetic (Solidity `unchecked{}` removal ↔ java-tron's `hardenCalculation()`/`allowHardenResourceCalculation` path using `BigInteger`-based `divideCeilExact` and `StrictMathWrapper.addExact`), which now **reverts/throws** instead of wrapping, on values that are reachable in normal (non-malicious) operation.

### Finding Description
`ResourceProcessor.increase(...)` and `increaseV2(...)` compute bandwidth/energy usage windows every time an account consumes or recovers resources [1](#0-0) . When the dynamic property `allowHardenResourceCalculation` is enabled, the "hardened" path replaces the legacy `long` arithmetic (`lastUsage * precision`, plain `+`) with `BigInteger`-based `divideCeilExact` and `StrictMathWrapper.addExact`, which throw `ArithmeticException` on overflow instead of silently wrapping like the legacy `long` path does [2](#0-1) [3](#0-2) .

The test suite itself demonstrates the divergence in behavior between the two modes: with hardening off, an overflow-prone computation completes silently (wraps) [4](#0-3) ; with hardening on, the identical computation throws `ArithmeticException` [5](#0-4) . This is precisely the same class of behavior change the external report describes for Solidity 0.8+ checked math: previously "desired"/tolerated wraparound arithmetic now aborts execution.

`increase()`/`increaseV2()` are called from `BandwidthProcessor.updateUsage`, `updateUsageForDelegated`, `useAccountNet`, and analogous methods in `EnergyProcessor`, which are invoked on essentially every transaction during block validation/execution (`BandwidthProcessor.java` lines 40-78, 468-504) [6](#0-5) [7](#0-6) . No `catch` for `ArithmeticException` was found wrapping these call sites in `BandwidthProcessor.java` in the search performed, meaning a thrown `ArithmeticException` from the hardened path would propagate up through the actuator/transaction-processing pipeline uncaught.

### Impact Explanation
If `allowHardenResourceCalculation` is turned on (a dynamic/committee-controlled chain parameter, analogous to the Solidity compiler-version bump that silently changed semantics), any account whose resource usage/time values legitimately reach the magnitudes exercised in the hardening tests (e.g., `lastUsage` near `Long.MAX_VALUE/10`, reachable through resource delegation, staking, or repeated usage accumulation over long time windows) will cause `ResourceProcessor.increase`/`increaseV2` to throw an uncaught `ArithmeticException` during block/transaction processing. Because this code runs in the consensus-critical resource-accounting path (bandwidth/energy consumption checked on every transaction), an uncaught exception here can:
- Crash or halt block processing for validating/producing nodes when they process a transaction hitting this condition, or
- Cause non-deterministic divergence between nodes if the flag/behavior is inconsistently applied, breaking consensus.

This matches the accepted analog categories: DoS via protocol implementation / consensus divergence in resource and reward accounting.

### Likelihood Explanation
Likelihood depends on (a) whether `allowHardenResourceCalculation` is actually enabled on mainnet/testnet (not confirmed — I was unable to locate the getter/setter wiring in `DynamicPropertiesStore.java` or confirm default value within the available index), and (b) whether realistic account usage values can reach the overflow-triggering magnitudes. The provided test suite (`ResourceProcessorHardenTest`, `RepositoryImplHardenTest`) explicitly exercises and documents this divergence, indicating the authors were aware hardening changes behavior from "silent wraparound" to "throws," which is the exact bug class flagged in the external report. However, without confirming production activation and reachable input magnitudes, I could not fully verify exploitability at the level of a concrete PoC transaction.

### Recommendation
- Ensure `increase`/`increaseV2`/`divideCeilExact`/`getUsage` never throw uncaught exceptions in the consensus path; catch `ArithmeticException` at all call sites in `BandwidthProcessor`/`EnergyProcessor` and degrade gracefully (e.g., clamp to `Long.MAX_VALUE` or reject the transaction via `ContractValidateException`/`AccountResourceInsufficientException` instead of letting the exception propagate).
- Audit every other "hardened" (`allowHarden*`) toggle introduced across `ExchangeProcessor`, `ExchangeCapsule`, `RepositoryImpl`, and `ResourceProcessor` for the same "checked math replaces silent wraparound" pattern, and verify all call sites already catch and convert `ArithmeticException` to a validated rejection rather than an unhandled crash.
- If any of these hardened paths are gated behind a dynamic property that can flip behavior for existing/legitimate large-magnitude accounts, add explicit regression/integration tests simulating mainnet-scale values (not just synthetic `Long.MAX_VALUE/10` inputs) to confirm no legitimate transaction can trigger the exception once hardening is turned on network-wide.

### Proof of Concept
Analogous to the external report's PoC path, the existing repository test demonstrates the vulnerable transition directly: [8](#0-7) 
- With `allowHardenResourceCalculation=0`: `processor.increase(Long.MAX_VALUE/10, 1L, 9990L, 9995L, 28800L)` completes silently (wraps).
- With `allowHardenResourceCalculation=1`: the identical call throws `ArithmeticException`.

Since `increase`/`increaseV2` are invoked from `BandwidthProcessor`/`EnergyProcessor` on ordinary account resource consumption during transaction execution, any transaction from an account whose `lastUsage`/`usage` reaches this magnitude while hardening is enabled will surface this uncaught exception in the block-processing path rather than being handled as a normal validation failure — the concrete node-level effect (crash vs. silently-accepted invalid state) could not be fully confirmed from the available index due to missing visibility into the top-level exception handling in `TransactionTrace`/block-processing code, which should be verified directly in a full checkout.

    long averageLastUsage;

      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);

    }

      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay,
            this.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }

  private long divideCeil(long numerator, long denominator) {
    return (numerator / denominator) + ((numerator % denominator) > 0 ? 1 : 0);
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }

  private long getUsage(long usage, long windowSize) {
    if (hardenCalculation()) {
      return BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize))
          .divide(BigInteger.valueOf(precision)).longValueExact();
    }
    return usage * windowSize / precision;
  }

  private boolean useAccountNet(AccountCapsule accountCapsule, long bytes, long now) {

    long netUsage = accountCapsule.getNetUsage();
    long latestConsumeTime = accountCapsule.getLatestConsumeTime();
    long netLimit = calculateGlobalNetLimit(accountCapsule);

    long newNetUsage;
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newNetUsage = increase(netUsage, 0, latestConsumeTime, now);
    } else {
      // only participate in the calculation as a temporary variable, without disk flushing
      newNetUsage = recovery(accountCapsule, BANDWIDTH, netUsage, latestConsumeTime, now);
    }


    if (bytes > (netLimit - newNetUsage)) {
      logger.debug("Net usage is running out, now use free net usage."
              + " Bytes: {}, netLimit: {}, newNetUsage: {}.",
          bytes, netLimit, newNetUsage);
      return false;
    }

    long latestOperationTime = chainBaseManager.getHeadBlockTimeStamp();
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newNetUsage = increase(newNetUsage, bytes, now, now);
    } else {
      // Participate in calculation and flush disk persistence
      newNetUsage = increase(accountCapsule, BANDWIDTH, netUsage, bytes, latestConsumeTime, now);
    }

    accountCapsule.setNetUsage(newNetUsage);
    accountCapsule.setLatestOperationTime(latestOperationTime);
    accountCapsule.setLatestConsumeTime(now);

    chainBaseManager.getAccountStore().put(accountCapsule.createDbKey(), accountCapsule);
    return true;
  }
