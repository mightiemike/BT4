### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay-verify tooling accept a corrupted/divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used by the chunk executor's `verify_execution` path (used by replay-verify / db-tool `replay_on_archive`) to check that a locally re-executed transaction matches the authenticated `TransactionInfo` pulled from the backup/ledger stream. The function explicitly skips comparison of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, per its own TODO comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against the supplied `txn_info`, but explicitly states: [2](#0-1) 

"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is called from `ChunkExecutorInner::verify_execution` in [3](#0-2) , which is the mechanism used to validate that locally re-executed transactions (from `DoGetExecutionOutput::by_transaction_execution`) reproduce the same result as the transaction infos fetched from a backup/replay source, before trusting the local re-execution result as a consistency check. Because `state_checkpoint_hash` (and the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields introduced alongside `TransactionInfoV1`, see the builder in [4](#0-3) ) are never compared here, a divergence in the *state Merkle root* computed by local re-execution versus the authenticated root carried in the downloaded `TransactionInfo` will not cause `verify_execution` to fail.

### Impact Explanation
Replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `storage/backup/backup-cli/src/coordinators/replay_verify.rs`) exists specifically to catch state-root/consensus divergence between local execution and the authenticated ledger — i.e., to detect exactly the kind of hard-fork-class bug that would otherwise silently corrupt derived state on a node performing state-sync-via-chunk-executor or fast-sync/backup restore-with-replay. Because the state checkpoint hash (the field that actually authenticates the Merkle/JMT state root) is excluded from the comparison, any bug in VM execution, in `DoStateCheckpoint`, or in state-tree construction that causes the locally computed state root to diverge from the authentic on-chain root will go undetected by this specific tool. This directly matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong ... state proof accepted as valid" impact classes: an operator relying on `replay_on_archive`/replay-verify to confirm state integrity of a node's replayed history would get a false "success" signal even though the node's derived state store no longer matches the authenticated ledger state.

### Likelihood Explanation
The gap is deterministic and always present whenever `verify_execution` (i.e., chunk-executor replay verification / replay-verify tooling) is invoked; it does not require an attacker, only a pre-existing correctness bug elsewhere in the state-checkpoint computation path (e.g. in `DoStateCheckpoint`, hot-state, or position-state root logic) to go unnoticed. The code's own comment confirms the authors are aware this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," indicating the checkpoint-hash fields it omits are on a code path already reachable (`TransactionInfoV1`/`maybe_hot_state_checkpoint_hash`/`maybe_position_state_checkpoint_hash` are already wired through `assemble_transaction_infos` in [5](#0-4) ) even though the "trading native" root computation itself may be gated behind that on-chain flag.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` (where present/expected) against the locally computed equivalents before returning `Ok(())`, so that replay-verify and `replay_on_archive` correctly fail when a state root diverges, consistent with the intent already documented in the TODO comment.

### Proof of Concept
Not applicable as an exploit script (this is a detection-logic gap, not an externally triggerable attack). The proof is the code path itself: `verify_execution` (`execution/executor/src/chunk_executor/mod.rs:648-706`) → `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`), where the function body never reads `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, confirmed by its own inline TODO acknowledging the gap.

**Note on verification limits:** I was unable to fully trace whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and thus the hot/position state checkpoint hashes) is currently enabled on mainnet, or whether any other caller of `verify_execution`/`ensure_match_transaction_info` performs a supplementary checkpoint-hash check outside this function. If such a check exists elsewhere in the replay-verify pipeline, the practical severity would be reduced to "missing defense-in-depth" rather than a complete detection bypass; the code-level gap and the developers' own acknowledgment of it, however, are confirmed directly in the repository.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
