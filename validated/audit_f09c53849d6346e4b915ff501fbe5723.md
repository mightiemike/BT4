### Title
Relayer fee refund is unconditionally dispatched before the corresponding user action is validated to succeed, allowing fee extraction without action execution - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In the NEAR Wallet Contract's `inner_rlp_execute`, the relayer-fee refund promise (`env::promise_batch_create` + `env::promise_batch_action_transfer`) is dispatched immediately after parsing the Ethereum-emulated transaction, *before* the corresponding user action (`action_to_promise(target, action)`) is constructed and confirmed to succeed. Because NEAR promises created via the raw host functions are emitted as outgoing receipts regardless of what the enclosing function later returns, a failure in building/dispatching the main action promise after this point still results in the relayer being paid, decoupling "pay relayer" from "perform user's requested transfer/call" — the same Checks-Effects-Interactions ordering violation flagged in the referenced report, adapted to NEAR's async cross-contract-call model.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-410`) does the following in order:
1. Parses/validates the RLP transaction via `parse_rlp_tx_to_action`, which computes `tx_fee` and validates nonce/target/sender/chain id/gas (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:43-166`).
2. Increments the nonce (except for the address-check-deferred case).
3. **Unconditionally creates and dispatches the relayer refund promise** when `fee` is non-zero and predecessor != current account:
```rust
if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
    env::promise_batch_action_transfer(refund_promise, *fee);
}
```
(`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:374-385`)
4. Only *afterward* does the code match on `transaction_kind` and attempt to build the main promise for the user's requested action, e.g. via `action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:466-470`).

If `action_to_promise` (or, for the ERC-20/EOA-transfer paths, the constructed lookup/callback promise) fails to build (returns `Err`), `inner_rlp_execute` returns `Err(e)`, and the top-level `rlp_execute` converts this into `PromiseOrValue::Value(e.into())` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:116-127`) — a plain returned value, not a panic. On NEAR, promises created via the raw `env::promise_batch_*` host calls during a successful (non-panicking) function execution are still emitted as receipts regardless of the function's ultimate return value; only a panic/abort of the whole receipt rolls back all promise creation. Consequently the relayer refund receipt is sent and executed even though the wallet owner's intended action was never performed.

This is the direct analog of the reported bug class: an "external transfer" (Effect — paying the relayer) is committed before the "critical operation" (validating/dispatching the user's actual requested action) completes, violating Checks-Effects-Interactions. On NEAR, the attacker is the *relayer* (an unprivileged transaction sender relaying meta-transactions on behalf of the wallet owner) reachable via `WalletContract::rlp_execute`, a plain `FunctionCall` action any account can submit against an eth-implicit account.

### Impact Explanation
A malicious or careless relayer can craft/relay a signed Ethereum-emulation transaction whose fee is nonzero but whose underlying action is engineered to fail after the fee-refund promise has already been queued (e.g. an ERC-20 transfer/self-transfer path where a later fallible step such as promise construction for the target action errors out, or any future/このcode path where the match on `transaction_kind` after the refund can produce an `Err`). The relayer collects the fee even though the wallet owner receives no benefit (no successful transfer/call), resulting in unauthorized value extraction from the wallet account by a relayer without performing the corresponding service — a concrete, attacker-triggerable value movement from a single transaction.

### Likelihood Explanation
The refund dispatch happens on every fee-bearing `EOABaseTokenTransfer`/`ERC20Transfer` regardless of whether the subsequent action construction succeeds; the ordering bug is structural (not a rare race), so it can be triggered deterministically by any relayer that also controls (or can influence) whether the second half of `inner_rlp_execute` errors out. The main residual uncertainty is whether current callable code paths after the refund can realistically produce an `Err` for a well-formed, fee-bearing transaction (the observed `Err` sources in the shown code are mostly `action_to_promise`'s target/account parsing failures) — this needs closer verification of `action_to_promise`'s full error surface, which was not fully retrievable within the available indexed content.

### Recommendation
Reorder the logic so the relayer refund promise is only dispatched after the main action promise has been successfully constructed (ideally chained so the refund is sent as part of/after the successful `.then()` callback confirming the user's action promise was created), following Checks-Effects-Interactions: validate and build the full promise chain for the user's action first, and only queue the relayer fee transfer once that succeeds (or make the refund itself conditional on the callback's success rather than unconditionally emitted up front).

### Proof of Concept
Conceptual PoC (exact reproduction requires the full `action_to_promise` implementation, which was not fully retrievable from the indexed codebase):
1. Relayer submits an RLP-encoded Ethereum transaction to `rlp_execute` for a wallet contract, structured as a fee-bearing `ERC20Transfer` or `EOABaseTokenTransfer` (with `address_check`/target such that a downstream step in `action_to_promise` or the associated `.then()` construction can be made to return `Err`, e.g. by choosing a `target`/`receiver_id` combination that passes `parse_rlp_tx_to_action` but fails later account/action_to_promise conversion).
2. `inner_rlp_execute` computes `tx_fee`, increments nonce, and immediately issues `env::promise_batch_create`/`promise_batch_action_transfer` refunding the relayer.
3. The subsequent `action_to_promise(target, action)?` call errors; `inner_rlp_execute` returns `Err(e)`.
4. `rlp_execute` converts this into `PromiseOrValue::Value(ExecuteResponse{success:false, ...})`.
5. Because the refund promise was already created as a receipt in step 2 and the overall function call did not panic, the refund receipt executes and pays the relayer — despite `success:false` being returned and no user-requested action ever taking effect. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

pub fn parse_rlp_tx_to_action(
    tx_bytes_b64: &str,
    target: &AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<(near_action::Action, TransactionKind), Error> {
    let tx_bytes = decode_b64(tx_bytes_b64)?;
    let tx_kind: EthTransactionKind = tx_bytes.as_slice().try_into()?;
    let tx: NormalizedEthTransaction = tx_kind.try_into()?;
    let target_kind = validate_tx_relayer_data(&tx, target, context, expected_nonce)?;

    // Compute the fee based on the user's Ethereum transaction.
    // This is sent as a refund to the relayer in the case of an emulated base token
    // transfer or ERC-20 transfer. The reason for this refund is that it allows a
    // user with $NEAR to use a relayer service from their wallet immediately without
    // additional on-boarding.
    let tx_fee = {
        // Limit the cost by `VALUE_MAX` since we will convert this to a $NEAR amount.
        // The call to `low_u128` is safe because `VALUE_MAX` is the largest accepted value.
        let wei_amount = tx.max_fee_per_gas.saturating_mul(tx.gas_limit).min(VALUE_MAX).low_u128();
        NearToken::from_yoctonear(wei_amount.saturating_mul(MAX_YOCTO_NEAR as u128))
    };
