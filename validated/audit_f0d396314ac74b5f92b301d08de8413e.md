### Title
`0s`-prefixed deterministic account IDs use a truncated 160-bit hash and silently skip re-initialization, enabling a CREATE2-style meet-in-the-middle preimage collision that lets an attacker seize a victim protocol's deterministic account and redirect its funding deposit - (File: `core/primitives/src/utils.rs`, `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
NEAR's NEP-616 deterministic accounts (`0s...` IDs) compute the account id as `keccak256(borsh(state_init))[12..32]` — a 160-bit truncated digest of an attacker/caller-fully-controlled `DeterministicAccountStateInit{code, data}` structure [1](#0-0) . This is the exact address-space size (and the exact "arbitrary attacker-controlled preimage vs. someone else's pre-computable address" shape) that the original report exploits for `CREATE2`. Because `action_deterministic_state_init` only deploys code/data on the `uninit -> active` transition and silently no-ops on any subsequent `DeterministicStateInitAction` sent to an already-initialized account (only settling/refunding the deposit), an attacker who wins a 160-bit preimage collision against a legitimate protocol's future deterministic-account id can install malicious code/data first, causing the legitimate protocol's later initialization deposit to be silently absorbed by the attacker-controlled account instead of deploying the intended contract state.

### Finding Description
The deterministic account id is derived with a truncated Keccak256 hash: `format!("0s{}", hex::encode(&hash[12..32]))`, giving only 160 bits of preimage resistance [1](#0-0) . The hashed input, `DeterministicAccountStateInit` (`code: GlobalContractIdentifier`, `data: BTreeMap<Vec<u8>, Vec<u8>>`), is fully attacker-controlled — arbitrary extra key/value pairs can be inserted into `data` purely to perturb the hash without materially affecting the code/logic a "victim" cares about, exactly like a brute-forceable `salt` in the original `CREATE2` report [2](#0-1) .

`action_deterministic_state_init` gates the actual deploy step (`deploy_deterministic_account`, which sets the contract code and writes the `data` map) behind `if account.contract().is_none()`. If the account already has a contract, the function skips straight to `settle_state_init_deposit`, which merely tops up storage-stake from the attached `deposit` and refunds the remainder — it does not verify that the caller's `state_init` matches whatever is already deployed on-chain: [3](#0-2) . This idempotent-skip behavior is confirmed by `test_repeated_deterministic_state_init`, which explicitly documents that a second init "does nothing" to the state but still allows a deposit/refund flow [4](#0-3) .

Combined, these two properties reproduce the report's core primitive: (1) an address space small enough (160 bits) to be brute-forced with a meet-in-the-middle search comparable to Ethereum `CREATE2`, and (2) a "deploy-then-can't-be-overwritten-but-silently-absorbs-later-deposits" semantics analogous to Solidity's address being claimed first via `CREATE2`/`selfdestruct` reuse. An attacker who finds a `state_init_attacker` colliding (in the truncated hash) with a `state_init_victim` that some lending/vault protocol will later derive for a legitimate user (e.g., a per-user vault deployed via a deterministic-account factory pattern, mirroring Arcadia's per-user `Account` proxies) can:
1. Submit `DeterministicStateInitAction{state_init_attacker}` first via a normal signed transaction, deploying malicious code (e.g., a global contract that grants the attacker unlimited withdrawal rights) at the shared 0s address.
2. Wait for the victim protocol to submit `DeterministicStateInitAction{state_init_victim, deposit}` to the same derived id, believing it is initializing a fresh vault.
3. Because `account.contract().is_none()` is now false, `deploy_deterministic_account` is skipped; the victim's deposit is simply merged into the attacker-controlled account's balance via `settle_state_init_deposit` [5](#0-4) .
4. The attacker withdraws the funds using the access already granted by their earlier malicious `code`/`data`.

### Impact Explanation
This produces concrete unauthorized value movement: funds a legitimate protocol intends to deposit into a fresh deterministic vault/account instead accrue to and become withdrawable from an attacker-controlled contract, with no on-chain check that the currently-deployed state matches the caller's `state_init`. Any protocol built on deterministic accounts as a per-user/per-position vault factory (the direct NEAR analog of the Arcadia `Factory.createAccount` pattern) is exposed to full drain of whatever is deposited during (re-)initialization, once a collision is found.

### Likelihood Explanation
Likelihood is bounded by the same birthday-bound cost analysis as the original report: 160-bit truncated digests, brute-forceable from either side because `data`/`code` are entirely attacker-supplied, put this in the same $O(2^{80})$-class feasibility bucket cited in the source report (tens of minutes to low hours of aggregate hashing at large but attainable compute, well below the security margin expected for irrevocably locking user deposits). It requires no privileged role — any account able to submit a signed transaction with a `DeterministicStateInitAction` can execute the front-run once a collision has been precomputed offline.

### Recommendation
- Use the full 256-bit `keccak256`/`sha3_256` digest for the `0s` deterministic-account id instead of truncating to `hash[12..32]`, removing the 160-bit collision budget (this is the pattern already used for the `0u` universal-account id via `derive_universal_account_id`, which hashes with `Sha3_256::digest` untruncated) [6](#0-5) .
- Alternatively/additionally, make `action_deterministic_state_init` verify that the `state_init` supplied in a `DeterministicStateInitAction` still matches the currently-deployed contract/data (or reject re-init attempts targeting an account whose contract was not deployed by this exact `state_init`) rather than silently no-op'ing and accepting the deposit regardless of provenance.

### Proof of Concept
1. Attacker offline brute-forces many candidate `DeterministicAccountStateInit{code: malicious_global_contract, data: {..., junk_key: random_padding}}` values, computing `derive_near_deterministic_account_id` for each [1](#0-0) .
2. In parallel, attacker (knowing the deterministic factory scheme a target lending/vault protocol uses, e.g., `code = vault_global_contract`, `data = {owner: victim_pubkey}`) brute-forces the victim-side `state_init` space (varying unused padding fields) to find a 160-bit collision with one of the precomputed attacker addresses (meet-in-the-middle, same technique cited in the source report).
3. Attacker submits `DeterministicStateInitAction{state_init_attacker, deposit: minimal}` to `0s<collision>` — `deploy_deterministic_account` runs because `account.contract().is_none()` is true, installing attacker's malicious code/data [7](#0-6) .
4. When the victim protocol later submits `DeterministicStateInitAction{state_init_victim, deposit: large}` to the same `0s<collision>` id (e.g., as part of onboarding a user's vault), `account.contract().is_none()` is now false, so `deploy_deterministic_account` is skipped entirely and only `settle_state_init_deposit` runs, crediting the large deposit to the attacker's already-installed account [8](#0-7) .
5. Attacker withdraws the deposited funds using the withdrawal capability their malicious `code`/`data` granted in step 3, matching the "silently accepts state without validating provenance" behavior already demonstrated (functionally) by `test_repeated_deterministic_state_init` [4](#0-3) .

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition. "uninit" here is the
        // NEP-616 sense, a deterministic account with no contract yet, not
        // `Account::Uninitialized`: a `0u` id can never reach this, because
        // `validate_deterministic_state_init` pins the receiver to the derived
        // `0s` id.
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }
    if result.result.is_err() {
        return Ok(());
    }

    settle_state_init_deposit(
        account,
        action.deposit,
        account_id,
        receipt,
        &apply_state.config,
        result,
    )
}

/// Ensure repeating a state initialization does not fail, to allow lazy
/// initialization. The submitted deposit should be refunded.
///
/// This test also checks that the signer is charged the balance correctly.
#[test]
fn test_repeated_deterministic_state_init() {
    let mut env = TestEnv::setup(Balance::from_near(100));
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let data = BTreeMap::from_iter([(b"key".to_vec(), vec![0u8; 100_000])]);
    let (state_init, det_account) = env.new_deterministic_account_with_data(data.clone());

    // send 10 times the required amount
    let required_for_storage = env.balance_for_storage(state_init);
    let attached_balance = required_for_storage.checked_mul(10).unwrap();

    let deposit_before = env.get_account_state(env.user_account()).amount;

    // first init
    let outcome = env.try_deploy_deterministic_account_with_data(data.clone(), attached_balance);
    outcome.expect("should be able to send transaction").assert_success();
    assert_eq!(
        required_for_storage,
        env.get_account_state(det_account.clone()).amount,
        "exactly required balance should be on the created account"
    );
    let deposit_between = env.get_account_state(env.user_account()).amount;
    assert!(
        deposit_between <= deposit_before.checked_sub(required_for_storage).unwrap(),
        "signer should have been charged the deposit cost + gas cost"
    );

    // second init
    let outcome = env.try_deploy_deterministic_account_with_data(data, attached_balance);
    outcome.expect("should be able to send transaction").assert_success();
    assert_eq!(
        required_for_storage,
        env.get_account_state(det_account).amount,
        "exactly attached balance should be on created account, nothing added on the second call"
    );
    let deposit_after = env.get_account_state(env.user_account()).amount;
    assert!(
        deposit_after > deposit_between.checked_sub(required_for_storage).unwrap(),
        "signer should have been refunded the deposit cost and only spend gas cost on the second call"
    );
}
