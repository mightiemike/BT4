### Title
Declare transactions trigger permanent disk writes to class storage before signature/authorization validation - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
In the gateway's `add_tx_inner` flow, an incoming `Declare` transaction's Sierra class is compiled and **permanently persisted to disk** by the class manager before the account's `__validate_declare__` signature check, nonce check, or mempool admission checks run. Any sender who can reach the gateway's `add_tx` endpoint — without a valid signature, without a funded/deployed account, and without a valid nonce — can force the sequencer to compile arbitrary Sierra classes and write them to the class manager's persistent filesystem storage, which is never rolled back when the transaction is later rejected.

### Finding Description
`Gateway::add_tx_inner` performs, in order: `check_declare_permissions` (an address allow-list check that is disabled by default, since `authorized_declarer_accounts` defaults to `None`/allow-all) [1](#0-0) , then `stateless_tx_validator.validate(&tx)` [3](#0-2)  — none of which verify the transaction signature or any account state. It then calls `convert_rpc_tx_to_internal_and_executable_txs`, and only afterwards runs `extract_state_nonce_and_run_validations`, which is where the account's nonce is fetched and the `__validate_declare__` entry point (the actual signature/authorization check) is executed [4](#0-3) .

Inside `convert_rpc_tx_to_internal_and_executable_txs`, for a `Declare` transaction, `TransactionConverter::convert_rpc_tx_to_internal` calls `self.class_manager_client.add_class(tx.contract_class).await?` [5](#0-4) . `ClassManager::add_class` compiles the Sierra class to CASM and then calls `self.classes.set_class(...)`, which writes the class permanently [6](#0-5) . The write path is `CachedClassStorage::set_class` → `FsClassStorage::set_class`, which atomically writes the Sierra and CASM files to the node's persistent filesystem (`persistent_root`) and marks the class hash as existent in a separate on-disk `ClassHashStorage` [7](#0-6) .

Crucially, none of this — compilation nor the filesystem write — is undone if the declare transaction is subsequently rejected: for example, because the signature fails `__validate_declare__`, the nonce is stale/invalid, the sender account doesn't exist, or the account can't pay the fee. There is no compensating deletion path invoked from the gateway's declare rejection handling; the class simply remains on disk as an "existent" class forever, since `set_class`/`write_class_atomically` are one-way and idempotent only for re-adds of the same class, never removals.

This exactly parallels the reported bug class: expensive, disk-persisting work (`add_class` → compile + `write_class_atomically`) is performed before the operation that determines whether the request should have been honored at all (the account's `__validate_declare__` signature check and nonce/state validation).

### Impact Explanation
Any network-reachable, unauthenticated sender (no valid signature, no funded account, no correct nonce — `authorized_declarer_accounts` is `None`/allow-all by default in the shipped configs) can submit a stream of syntactically-valid but never-executable `Declare` transactions, each declaring a unique Sierra class (varying trivial bytecode changes trivially changes the class hash), and force the sequencer to:
1. Run CPU/memory-intensive Sierra→CASM compilation (bounded only by `max_concurrent_declare_compilations`, a concurrency limit, not a total-volume limit).
2. Permanently write two files per class plus a class-hash-storage entry to the node's local disk — data that is never cleaned up because the underlying declare transaction is rejected only after the write already happened.

Because rejected declares are never retried/re-validated to trigger cleanup, and the filesystem storage has no expiry or garbage collection tied to transaction outcome, this is an unauthenticated, unbounded disk-exhaustion / storage-bloat vector against every gateway-hosting node. Sustained abuse can degrade or crash class-manager/gateway nodes (disk full), which is a network-availability impact — nodes may become unable to serve valid declares or, in constrained environments, unable to process transactions at all, satisfying "a network unable to confirm new transactions."

### Likelihood Explanation
High reachability: this requires nothing but network access to a gateway's `add_tx` RPC endpoint and a syntactically valid but arbitrarily-signed/unauthorized `Declare` transaction (invalid signature, non-existent sender, or wrong nonce all still reach `add_class` before being rejected). No special privileges, staking, or prior state are required. The `authorized_declarer_accounts` allow-list is disabled by default in the shipped deployment configs, so the only remaining friction is the stateless validator's size/format checks and the `max_concurrent_declare_compilations` semaphore, neither of which limits the total volume of classes persisted over time — merely the instantaneous concurrency of compilation.

### Recommendation
Defer `class_manager_client.add_class` (compilation + persistent write) until after the declare transaction has passed the account's `__validate_declare__` signature check, nonce validation, and mempool admission checks — i.e., move the class-manager `add_class` call to occur only once the transaction is confirmed valid and about to be forwarded to the mempool. Alternatively, perform an idempotent staging/quarantine write with an explicit garbage-collection sweep tied to transaction rejection so classes belonging to rejected declares are deleted, and/or add a per-address or global rate limit on the total number of classes actually persisted, independent of the existing concurrency semaphore.

### Proof of Concept
1. Configure a gateway with default settings (`authorized_declarer_accounts: None`, default `max_concurrent_declare_compilations`).
2. Submit an RPC `Declare` V3 transaction where:
   - `sender_address` is any address (no deployed account, or one for which the attacker has no private key), and
   - `signature` is empty/garbage, and
   - `contract_class` is a small-but-unique valid Sierra class (vary a no-op constant to get a unique class hash per submission).
3. Observe in the gateway trace that `convert_rpc_tx_to_internal` → `class_manager_client.add_class` is invoked and completes (compiles the class and writes `sierra`/`casm` files under the class manager's `persistent_root`, and commits an entry in `ClassHashStorage`) before `extract_state_nonce_and_run_validations` runs.
4. Observe the request is ultimately rejected (e.g., `InvalidSignature`/`InvalidTransactionNonce` from stateful validation), yet the class files added in step 3 remain on disk (`get_persistent_dir(class_hash)` still exists and `get_executable_class_hash_v2(class_hash)` still returns `Some`).
5. Repeat with unique classes at the maximum sustained submission rate the gateway allows; disk usage under `persistent_root` grows unbounded with no corresponding valid mempool entries.

    #[instrument(skip(self, class, executable_class), level = "debug", ret, err)]

        class_id: ClassId,
        class: RawClass,
        executable_class_hash_v2: ExecutableClassHash,
        executable_class: RawExecutableClass,

        if self.contains_class(class_id)? {
            return Ok(());

        self.write_class_atomically(class_id, class, executable_class)?;
        self.mark_class_id_as_existent(class_id, executable_class_hash_v2)?;

        Ok(())
    }
