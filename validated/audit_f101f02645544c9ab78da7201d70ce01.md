Nearcore's signature verification is strongly typed and does not have an analog to jwt-simple's algorithm-confusion bug. The core `Signature::verify` function matches the signature variant and public-key variant together in a single `match (&self, public_key)` expression — `ED25519` signatures only verify against `ED25519` keys, `SECP256K1` against `SECP256K1`, and `MLDSA65` against `MLDSA65`; any mismatch falls through to `_ => false` [1](#0-0) . Unlike JWT, where the `alg` field is an attacker-controlled string that independently selects the verification algorithm (enabling `alg: none` or HS/RS confusion), nearcore's `KeyType`/`PublicKey`/`Signature` are Rust enums whose variant is fixed at construction (`Signature::from_parts` requires the caller to pick a `KeyType` matching the byte layout, and the wire-format tag on `PublicKey`/`Signature` is bound to the actual cryptographic scheme) [2](#0-1) . There's no place in the transaction-verification path (`ValidatedTransaction::new`, `verify_and_charge_tx_ephemeral`, `get_signer_and_authorization`) where the verification algorithm is chosen independently of the cryptographic proof, so a signer cannot "downgrade" or select a weaker/bypassable verification path [3](#0-2) . Test coverage explicitly confirms cross-scheme verification always returns `false` and never panics [4](#0-3) .

I also checked the Wallet Contract's Ethereum-transaction path, which recovers a secp256k1 address via ECDSA and requires it to match the target ETH-implicit account; this uses a single fixed scheme (secp256k1/keccak) with no attacker-selectable algorithm field [5](#0-4) .

No exploitable "algorithm confusion" or signature-scheme downgrade analog exists in this codebase.

                match ed25519_dalek::VerifyingKey::from_bytes(&public_key.0) {
                    Err(_) => false,
                    Ok(public_key) => public_key.verify(data, signature).is_ok(),

            }
