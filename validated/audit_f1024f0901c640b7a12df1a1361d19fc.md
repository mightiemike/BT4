### Title
`decodeHost` returns un-sanitized raw string post-`sanitizeHost` regex validation, allowing CRLF-bearing base64 `host` to reach embedded-app redirect URL construction - (File: `packages/apps/shopify-api/lib/auth/decode-host.ts`)

### Summary
`decodeHost` is a one-line `atob(host)` wrapper with no output sanitization, and the validation step in `sanitizeHost` (`packages/apps/shopify-api/lib/utils/shop-validator.ts`) checks the decoded string only after it has passed through the WHATWG `URL` parser, which silently strips ASCII tab/CR/LF characters before matching the hostname regex. `buildEmbeddedAppUrl` (`packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts`) then calls `decodeHost(host)` a *second* time on the raw, un-stripped string and concatenates it directly into a redirect URL, meaning the CRLF sequence that was invisible to the validator survives into the string returned to the caller.

### Finding Description
`decodeHost` performs no validation: [1](#0-0) 

`sanitizeHost` validates a base64 `host` param by decoding it and extracting `hostname` via `new URL(https://${decodeHost(sanitizedHost)})`, then testing that hostname against an allow-list regex: [2](#0-1) 

Because the WHATWG `URL` parser strips ASCII tab/newline/CR characters from the input before tokenizing it, a base64-encoded value that decodes to something like `attacker.com\r\n.myshopify.com` will have its embedded CR/LF silently removed during `new URL(...)` construction, producing hostname `attacker.com.myshopify.com`, which the regex `\.(myshopify\.com|...)$` accepts (ends in `.myshopify.com`) — so `sanitizeHost` returns the (still raw, un-stripped) base64 host as "valid".

`buildEmbeddedAppUrl` then does its own independent `decodeHost(host)` call on the same raw base64 value (not on the stripped hostname the validator actually checked) and interpolates the result directly into a string: [3](#0-2) 

This is a validate-one-thing/use-another mismatch: `sanitizeHost` validates a *URL-parsed, CRLF-stripped* hostname, but the value actually returned and used to build `https://${decodedHost}/apps/${config.apiKey}` is the *raw, un-stripped* decoded string, which can still contain literal `\r\n`. If that returned string is subsequently used to populate an HTTP redirect `Location` header by a host application (a documented use case for `getEmbeddedAppUrl`/`buildEmbeddedAppUrl` per `docs/reference/auth/buildEmbeddedAppUrl.md`), the embedded CRLF enables HTTP response header/CRLF injection or splitting, which can be leveraged for open redirect or cookie/header injection.

This does not require any non-default configuration — `config.domainTransformations` is irrelevant here; the vulnerable path exists purely because of the double-decode/validate-vs-use mismatch between `sanitizeHost` and `buildEmbeddedAppUrl`, independent of the allowlist-widening scenario described in the question (that specific `applyDomainTransformations` widening concern applies only to `sanitizeShop`/`sanitizeHost` domain matching, not to introducing CRLF).

### Impact Explanation
An attacker who controls the `host` query parameter of a request into an app built on `shopify-api` (an anonymous capability — `host` is a public, unauthenticated query param used for embedded-app iframe context) can produce a `buildEmbeddedAppUrl`/`getEmbeddedAppUrl` output string containing literal CRLF bytes. If a host application uses this value to set a `Location` header for a redirect (which is exactly its intended purpose — to build a URL to redirect the browser into the embedded app), this could result in HTTP response splitting/header injection, which can be escalated to open redirect (Shopify HackerOne / Immunefi "open redirect leading to token theft" impact class).

### Likelihood Explanation
- No privileged role, secret, or non-default config is required; `host` is fully attacker-controlled (unauthenticated GET parameter).
- The vulnerable code path (`sanitizeHost` → `new URL()` stripping vs. `buildEmbeddedAppUrl`'s independent raw `decodeHost` call) is default-config; the domain-transformation widening angle in the question is not actually necessary to reach it.
- Exploitability further depends on how the *host application* (not this library) uses the returned string (e.g., whether it uses `res.redirect(url)` with a low-level header API that does not itself reject CR/LF, since Node's `http` module does throw on invalid header characters in many cases). This introduces uncertainty about whether the impact is realized end-to-end without a cooperating host-app behavior, which the rules ask to reject ("bug in the host app rather than in this library"). I could not verify, within this codebase alone, a concrete internal call site (in `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router`) that takes `buildEmbeddedAppUrl`'s return value and sets it as a raw `Location` header without further processing — the CLI/grep search only found usage sites, not their exact redirect implementation, so this cannot be fully confirmed as an in-library exploit chain.

### Recommendation
- Make `decodeHost` return output consistent with what was validated: derive the returned string from the parsed/normalized `URL` object used during validation (or reject/strip control characters, and re-validate with `encodeURI`/hostname-only reconstruction) rather than re-decoding the raw base64 independently in `buildEmbeddedAppUrl`.
- Add explicit rejection in `sanitizeHost` (and `decodeHost`) of any decoded value containing control characters (`\r`, `\n`, `\0`, etc.) before treating it as valid, instead of relying on `URL`'s silent stripping behavior.
- Add a regression test asserting that a base64 host decoding to a string containing `\r\n` is rejected by `sanitizeHost` and that `buildEmbeddedAppUrl` never returns a string containing CR/LF.

### Proof of Concept

// packages/apps/shopify-api/lib/auth/__tests__/decode-host-crlf.test.ts
import {shopifyApi} from '../../..';
import {testConfig} from '../../../__tests__/test-config';
import {buildEmbeddedAppUrl} from '../get-embedded-app-url';

test('CRLF survives sanitizeHost validation into buildEmbeddedAppUrl output', () => {
  const shopify = shopifyApi(testConfig());

  // Decoded value: "attacker.com\r\n.myshopify.com/admin"
  const malicious = Buffer.from(
    'attacker.com\r\n.myshopify.com/admin',
  ).toString('base64');

  // sanitizeHost validates the URL-parsed hostname, which has CR/LF stripped
  // by the WHATWG URL parser, so this incorrectly passes as "valid".
  expect(shopify.utils.sanitizeHost(malicious)).toEqual(malicious);

  // buildEmbeddedAppUrl independently re-decodes the raw base64 value and
  // interpolates it directly, so the CRLF survives into the output string.
  const url = buildEmbeddedAppUrl(shopify.config)(malicious);
  expect(url).toMatch(/\r\n/); // CRLF present in the "sanitized" redirect URL
});

export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;

    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);

      const originsRegex = [
        'myshopify\\.com',
        'shopify\\.com',
        'myshopify\\.io',
        'spin\\.dev',
        'shop\\.dev',
      ];

      if (config.domainTransformations) {
        const hostTransformationDomains = config.domainTransformations
          .filter((t) => t.includeHost !== false)
          .flatMap((t) =>
            getTransformationDomains({
              ...config,
              domainTransformations: [t],
            }),
          );
        originsRegex.push(...hostTransformationDomains);
      }

      const hostRegex = new RegExp(`\\.(${originsRegex.join('|')})$`);
      if (!hostRegex.test(hostname)) {
        sanitizedHost = null;
      }
    }

export function buildEmbeddedAppUrl(
  config: ConfigInterface,
): BuildEmbeddedAppUrl {
  return (host: string): string => {
    sanitizeHost(config)(host, true);
    const decodedHost = decodeHost(host);

    return `https://${decodedHost}/apps/${config.apiKey}`;
  };
