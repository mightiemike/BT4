## Analysis

The Hinkal report describes unrestricted, unmetered endpoint calls causing resource exhaustion. The closest reachable analog in Push Chain's scoped code is the gasless transaction admission path in `app/ante/account_init_decorator.go`, combined with the gasless whitelist in `app/txpolicy/gasless.go`. That pipeline lets an unprivileged attacker create unlimited new on-chain accounts completely free of charge (no fee, no minimum gas price), because the account-creation side effect commits to state even though the underlying message afterward can fail its business-logic authorization checks.

### Title
Unmetered, free account creation via gasless `AccountInitDecorator` enables unbounded state-bloat DoS - (File: `app/ante/account_init_decorator.go`)

### Summary
`AccountInitDecorator` creates a brand-new `auth` account for any signer of a whitelisted gasless message the moment it observes the signer has no existing account, requiring only a self-consistent signature over `account_number=0, sequence=0` [1](#0-0) . This account-creation write is committed by the Cosmos SDK regardless of whether the wrapped message later fails downstream authorization checks (e.g. "not a bonded Universal Validator", "invalid UEA signature"), because ante-handler state writes and message-execution state writes are independent commit boundaries. Since `DeductFeeDecorator` and `MinGasPriceDecorator` both skip all fee/gas-price enforcement for any tx whose messages are entirely in the gasless whitelist [2](#0-1) [3](#0-2) , an attacker can mint an unbounded number of throwaway keypairs and submit an unbounded number of zero-cost transactions, each permanently growing the `auth` account KV-store — a direct, unprivileged, non-network-level resource-exhaustion analog to the reported "absence of rate limiting."

### Finding Description
The gasless whitelist (`IsGaslessTx`) admits seven message types purely by `TypeUrl`, with **no check on whether the signer is authorized to submit that specific message** (e.g. bonded-UV status for `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration`, or UEA-ownership binding for `MsgExecutePayload`/`MsgMigrateUEA`) [4](#0-3) . That authorization is enforced later, inside the message handler itself (per the module's own documentation: "The chain module deliberately does not enforce `Signer == EVM(Owner)`" and bonded-status gating happens in `x/uvalidator`/`x/uexecutor` keeper logic, not in the ante chain) [5](#0-4) .

`AccountInitDecorator` runs *before* any of that: it fires purely on `IsGaslessTx(tx) == true` plus `!ak.HasAccount(ctx, newAccAddr)` [6](#0-5) , verifies only a self-signature (trivial for any attacker-controlled fresh keypair, since `account_number=0, sequence=0` is fixed and known), then unconditionally persists a new `BaseAccount`:

```go
acc := aid.ak.NewAccountWithAddress(ctx, newAccAddr)
acc.SetSequence(1)
aid.ak.SetAccount(ctx, acc)
``` [7](#0-6) 

Because the ante-handler's cache-context is committed on tx admission independently of whether the subsequently-executed message reverts, the account persists even when:
- The signer is not a bonded Universal Validator, so `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration` will fail downstream.
- The `MsgExecutePayload`/`MsgMigrateUEA` payload signature does not match the target UEA owner, so `executeUniversalTx` reverts.

No fee is required (`DeductFeeDecorator` skips deduction for gasless txs) and no minimum gas price is enforced (`MinGasPriceDecorator` skips the FeeMarket check for gasless txs), so the entire operation costs the attacker nothing beyond generating a keypair and a signature — both computationally trivial and infinitely repeatable.

### Impact Explanation
This is a state-growth denial-of-service vector reachable by any unprivileged, unfunded external actor through the ordinary default transaction submission path — no validator, relayer, or governance privilege required. An attacker can:
1. Generate an arbitrary number of Ed25519/secp256k1 keypairs.
2. Sign a trivially-constructed gasless message (e.g., a `MsgVoteChainMeta` or `MsgExecutePayload` with garbage payload) for each keypair.
3. Submit each as a zero-fee transaction.

Each accepted transaction permanently adds a new `BaseAccount` entry to the `x/auth` KV-store on every full node and validator, with no offsetting cost to the attacker. Sustained abuse inflates chain state size (disk, IAVL tree depth/proof size, snapshot/sync time) indefinitely, degrading node performance and increasing operational costs for all node operators — the same "resource exhaustion / degraded performance" impact category as the source report, but realized as persistent on-chain state bloat rather than transient request flooding.

### Likelihood Explanation
High. No specialized access, timing, or race condition is needed — only unbonded standard SDK transaction submission using freshly-generated keys, i.e. exactly the "ordinary unprivileged user actions alone" trigger condition called out in the allowed-impact scope. The whitelist and decorator logic are static/production code paths hit on every gasless tx, and the underlying message's ultimate failure does not prevent the account-creation side effect from being retained.

### Recommendation
- Require `AccountInitDecorator` to only create/commit the new account atomically together with successful execution of the wrapped message (e.g., defer account persistence until after message execution succeeds, or use an ante-level authorization pre-check — such as bonded-UV membership or UEA-ownership binding — before creating the account), so failed/unauthorized gasless messages cannot leave a persistent account behind.
- Alternatively, gate account creation on a lightweight, per-message ante-level authorization check (e.g., verify the signer is a currently bonded Universal Validator for vote messages) before calling `NewAccountWithAddress`/`SetAccount`.
- Consider bounding the number of new-account creations per block/per signer-set via a dedicated counter or minimal anti-spam charge specific to first-use account bootstrap, independent of the general gasless fee exemption.

### Proof of Concept
1. Generate a fresh keypair `K` not previously used on-chain.
2. Construct a `MsgVoteChainMeta` (or any other gasless-whitelisted message) with arbitrary/invalid content, signed by `K` using `account_number=0, sequence=0`.
3. Submit the transaction with `gas > 0` and no fee.
4. Observe: `AccountInitDecorator.AnteHandle` passes signature verification (self-consistent for the fresh key), creates and persists the account via `NewAccountWithAddress`/`SetAccount` [7](#0-6) , and returns success from the ante chain.
5. The subsequent message execution fails (signer is not a bonded Universal Validator), but the new account row persists in the `auth` module store.
6. Repeat with N fresh keypairs to grow chain state by N accounts at zero cost.

func (aid AccountInitDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	if !txpolicy.IsGaslessTx(tx) {
		// Skip account initialization for non-gasless transactions
		ctx.Logger().Debug("account init decorator: non-gasless tx, skipping account init")
		return next(ctx, tx, simulate)
	}

	sigTx, ok := tx.(authsigning.Tx)
	if !ok {
		return ctx, errorsmod.Wrap(sdkerrors.ErrTxDecode, "invalid transaction type")
	}

	signers, err := sigTx.GetSigners()
	if err != nil || len(signers) != 1 {
		ctx.Logger().Debug("account init decorator: could not get unique signer, passing to next handler",
			"num_signers", len(signers),
			"error", err,
		)
		return next(ctx, tx, simulate)
	}

	newAccAddr := signers[0]
	if !aid.ak.HasAccount(ctx, newAccAddr) {
		ctx.Logger().Debug("account init decorator: new account detected on gasless tx, verifying signature",
			"address", sdk.AccAddress(newAccAddr).String(),
			"simulate", simulate,
		)
		// if account does not exist on chain, bypass rest of ante chain (especially gas and signature verification) here.
		// Perform signature verification on account number e and sequence number e instead.
		if err := aid.verifySignatureForNewAccount(ctx, tx, simulate); err != nil {
			ctx.Logger().Debug("account init decorator: signature verification failed for new account",
				"address", sdk.AccAddress(newAccAddr).String(),
				"error", err,
			)
			return ctx, err
		}

		acc := aid.ak.NewAccountWithAddress(ctx, newAccAddr)
		acc.SetSequence(1)
		aid.ak.SetAccount(ctx, acc)
		ctx.Logger().Info("account init decorator: new account created via gasless tx",
			"address", sdk.AccAddress(newAccAddr).String(),
		)
		return ctx, nil
```

func IsGaslessTx(tx sdk.Tx) bool {
	var (
		// GaslessMsgTypes defines the message types that are allowed in gasless transactions
		GaslessMsgTypes = []string{
			sdk.MsgTypeURL(&uexecutortypes.MsgMigrateUEA{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgExecutePayload{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteInbound{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteOutbound{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteTssKeyProcess{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteFundMigration{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteChainMeta{}),
		}
	)

	msgs := tx.GetMsgs()
	if len(msgs) == 0 {
		return false
	}

	for _, msg := range msgs {
		switch m := msg.(type) {
		case *authz.MsgExec:
			// Only gasless if ALL inner messages are allowed
			for _, innerMsg := range m.Msgs {
				if !slices.Contains(GaslessMsgTypes, innerMsg.TypeUrl) {
					return false
				}
			}
		default:
			if !slices.Contains(GaslessMsgTypes, sdk.MsgTypeURL(msg)) {
				return false
			}
		}
	}
	return true
}

```markdown
`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```
