### Title
Backup/restore accepts unauthenticated `WriteSet` not bound to `TransactionInfo.state_change_hash`, allowing corrupted ledger state on replay-restore - (File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs)

### Summary
The transaction backup/restore path deserializes `(Transaction, TransactionInfo, Vec<ContractEvent>, WriteSet)` (or the V1 variant with `PersistedAuxiliaryInfo`) records from an untrusted backup file, but only feeds `Transaction`, `TransactionInfo`, and events into the accumulator-based verification (`TransactionListWithProofV2::verify`). The `WriteSet`, whose hash (`state_change_hash`) is supposed to be committed inside the already-verified `TransactionInfo`, is never hashed and compared against that field anywhere in the restore code.

### Finding Description
`LoadedChunk::load` in `storage/backup/backup-cli/src/backup_types/transaction/restore.rs:99-186` reads each backup record and splits it into `txns`, `persisted_aux_info`, `txn_infos`, `event_vecs`, and `write_sets` [1](#0-0) . It then builds a `TransactionListWithProofV2` from `txns`, `event_vecs`, and `txn_infos` and calls `.verify(ledger_info.ledger_info(), Some(manifest.first_version))` [2](#0-1) . Note `write_sets` is entirely absent from the struct being verified.

`TransactionListWithProof::verify` (`types/src/transaction/mod.rs:2693-2752`) checks: (1) transaction hash equals `txn_info.transaction_hash()`, (2) the accumulator proof binds `txn_info` hashes to the target ledger info's `transaction_accumulator_hash()`, and (3) event lists match `txn_info.event_root_hash()` via `verify_events_against_root_hash` [3](#0-2) . There is no corresponding check against `state_change_hash`, which is precisely the field that commits the write set into the accumulator (as constructed originally in `assemble_transaction_infos`, where `write_set_hash = CryptoHash::hash(txn_output.write_set())` feeds `state_change_hash` into the builder) [4](#0-3) .

The unverified `write_sets` are then passed straight through `TransactionRestoreBatchController::save_before_replay_version` to `RestoreHandler::save_transactions` / `save_transactions_and_replay_kv` (`storage/aptosdb/src/backup/restore_handler.rs:78-126`), down to `restore_utils::save_transactions_impl` (`storage/aptosdb/src/backup/restore_utils.rs:205-293`), which persists them via `WriteSetDb::put_write_set` and, when `kv_replay` is enabled, uses them directly to compute the new ledger state via `state_store.calculate_state_and_put_updates(&StateUpdateRefs::index_write_sets(...))` [5](#0-4) . At no point in this call chain is `CryptoHash::hash(write_set)` compared to `txn_infos[idx].state_change_hash()`.

### Impact Explanation
Because the write set is not bound by any check to the already-accumulator-verified `TransactionInfo.state_change_hash`, a corrupted or tampered backup archive (e.g., disk bit-rot, a compromised/misconfigured backup storage backend, or a bug in the backup-writing tool) can supply a `WriteSet` whose actual contents differ from what was truly executed, while `txn_infos`/`transactions`/events still pass `verify()` since that check never touches the write set. During `kv_replay` restore this directly corrupts the durable state committed to `StateKvDb`/`StateMerkleDb` (wrong values indexed via `index_write_sets`), and unconditionally corrupts the persisted `WriteSetDb` used to answer `get_write_set` /API queries for that version, i.e., committed state that differs from the correct VM result and is presented as an authenticated result at that version. This falls squarely in the state-commitment/proof-integrity impact category, since the restored `WriteSetDb` and derived JMT state will silently diverge from the true committed ledger state without the pipeline detecting anything.

### Likelihood Explanation
This requires access to a backup archive with a subtly corrupted `WriteSet` field (not the whole record, since `Transaction`/`TransactionInfo`/events must still pass verification) — realistically triggered by storage corruption, a malfunctioning/compromised backup storage provider, or a backup tool bug that mismatches records, rather than a purely remote network attacker. It doesn't require a validator's signing key or governance privilege, only control (or corruption) of the backup file contents, which restore operators trust implicitly today. Given restore is a normal operational disaster-recovery path (state sync bootstrap, node recovery, replay-verify), the likelihood of this defect mattering is moderate rather than purely theoretical.

### Recommendation
In `LoadedChunk::load` (or immediately after, before any write sets are persisted or used for `kv_replay`), recompute `CryptoHash::hash(&write_set)` for each transaction and assert equality with `txn_infos[i].state_change_hash()` before returning/using the chunk, mirroring the existing hash checks done for transactions and events in `TransactionListWithProof::verify`. This should be enforced both in the pure "save" path and the "replay" path so that corrupted or mismatched write sets are rejected before they can taint `WriteSetDb`, `StateKvDb`, or the Jellyfish Merkle tree.

### Proof of Concept
1. Take a legitimate transaction backup chunk file (format `V0` or `V1`) containing `(Transaction, [PersistedAuxiliaryInfo], TransactionInfo, Vec<ContractEvent>, WriteSet)` records.
2. For one record, replace only the trailing `WriteSet` bytes with a different, structurally valid `WriteSet` (e.g., one that grants extra balance to an account), leaving `Transaction`, `TransactionInfo` (and hence `state_change_hash`, `transaction_hash`, `event_root_hash`), and events untouched.
3. Run `TransactionRestoreController` (or the underlying `LoadedChunk::load` + `TransactionRestoreBatchController::save_before_replay_version` with `kv_only_replay=true`) against this tampered chunk plus a legitimate matching `(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)` proof file.
4. Observe that `txn_list_with_proof.verify(...)` at `storage/backup/backup-cli/src/backup_types/transaction/restore.rs:167` succeeds (since it never touches `write_sets`), and the tampered `WriteSet` is committed to `WriteSetDb` and, under `kv_replay`, used to compute new state via `calculate_state_and_put_updates`, producing a JMT/state-kv value that diverges from the value that would result from the transaction's true execution/committed `state_change_hash`.
