## Title
Unchecked `.unwrap()` on `receiver_shard_id()` in `DelayedReceiptQueueWrapper::receipt_filter_fn` can panic and halt chunk processing on stale cross-shard receipts - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The btrfs CVE fixes a null-pointer dereference caused by `btrfs_search_slot()` trusting a corrupted/`NULL` root without a sanity check. The analogous pattern in nearcore is code that trusts a `Result`-returning lookup to always succeed and `.unwrap()`s it instead of propagating the error, so that unexpected/attacker-influenced input reaches an implicit panic instead of a handled error path. `DelayedReceiptQueueWrapper::receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs:876` does exactly this with `receiver_shard_id()`.

### Finding Description
`Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437-467`) is explicitly designed to return `Err(EpochError::ShardingError(...))` for `GlobalContractDistribution` receipts whose `target_shard` no longer exists in the current shard layout *or its split history*: [1](#0-0) 

This is a real, reachable failure mode — the surrounding comment states the target shard "may be from an arbitrarily old layout (the receipt could have been delayed across multiple resharding events)". Delayed/buffered `GlobalContractDistribution` receipts are exactly the kind of long-lived, cross-shard state that can accumulate through several resharding generations while stuck in the congestion-controlled delayed-receipt queue.

The delayed-receipt queue's shard filter, however, discards that `Result` with `.unwrap()`: [2](#0-1) 

If `resolve_to_current_shard` (`core/primitives/src/shard_layout/mod.rs`, `v3.rs`) fails to map a stale `target_shard` to any shard in the current layout — e.g., because the split-history chain does not (or cannot, for some multi-generation/edge-case resharding sequence) reach far enough back — `receiver_shard_id` returns `Err`, and `receipt_filter_fn`'s `.unwrap()` panics inside chunk apply, exactly analogous to a null-root dereference: a data structure invariant ("every enqueued receipt's target shard is resolvable") that the code assumes but does not defensively verify at the point of use.

The repository already contains a regression test acknowledging this exact failure mode is possible and testing that current code does not regress into it: [3](#0-2) 
The test comment states plainly: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations." That the maintainers wrote a dedicated double-resharding regression test for this exact panic site confirms it is a recognized, previously-triggerable crash path — the `.unwrap()` itself remains in the code as the single point of failure if `resolve_to_current_shard`'s split-history coverage is incomplete for any layout/ordering not covered by the existing test (e.g., three or more resharding generations, non-adjacent splits, or shard-merge scenarios not exercised by `test_stale_global_contract_distribution_after_double_resharding`).

### Impact Explanation
A panic inside `DelayedReceiptQueueWrapper::pop` during chunk apply is not recoverable per-transaction — unlike verifier-level errors, this occurs deep inside receipt processing and will abort chunk application entirely. Because `apply_chunk` in `chain/chain/src/runtime/mod.rs:1226-1305` re-panics on any non-storage error from `process_state_update` (`_ => panic!("{err}")`), a Rust panic that escapes as an unhandled runtime error causes every validator/chunk-producer processing that chunk to crash or fail to produce a valid state transition, which is a transaction/receipt-triggered consensus halt — the class of impact explicitly called out as in-scope ("a transaction-triggered halt").

### Likelihood Explanation
Reaching this requires: (1) submitting a `DeployGlobalContract` action to trigger a `GlobalContractDistribution` receipt (available to any account, no special privilege), and (2) the receipt becoming delayed/buffered across multiple dynamic-resharding events before being processed, so its `target_shard` becomes stale relative to the current shard layout's recorded split history. Dynamic resharding is protocol-controlled and not attacker-triggered on demand, so exploitation likelihood is tied to specific resharding schedules/configurations (this is why the existing test needed to force two resharding splits via `DynamicReshardingConfig`). It is a genuine but conditionally-reachable panic path rather than one triggerable by a single ordinary transaction in a static shard layout.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` (and audit any other call sites of `receiver_shard_id`) with proper error propagation (`?`) so an unresolvable stale receipt produces a `RuntimeError`/`StorageInconsistentState` instead of an unrecoverable panic, and extend resharding-history coverage/tests beyond the two-generation case already tested to ensure `resolve_to_current_shard` is complete for arbitrary resharding depths and shard-merge scenarios.

### Proof of Concept
1. Deploy a shard layout with `DynamicReshardingConfig` configured to force multiple sequential splits (as in `test_stale_global_contract_distribution_after_double_resharding`, `test-loop-tests/src/tests/global_contracts_distribution.rs:30-186`).
2. From any account, submit a `DeployGlobalContract` transaction, generating a `GlobalContractDistribution` receipt with `target_shard` = the shard about to be split.
3. Saturate compute on that shard every block so the receipt is pushed into the delayed-receipt queue and remains there through two (or more, in an unverified case) resharding events.
4. When the delayed queue drains and `DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn`, if `resolve_to_current_shard` cannot map the doubly/triply-stale `target_shard` into the current layout, `receiver_shard_id(&shard_layout).unwrap()` panics, aborting chunk apply for every node processing that chunk.     pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
