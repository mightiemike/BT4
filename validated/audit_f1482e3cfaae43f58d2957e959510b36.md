## Title
FunctionCallPermission allowance limit is not enforced when a restricted access key's actions are routed through a meta transaction (delegate action) - (File: `runtime/runtime/src/actions.rs`)

## Summary
A `FunctionCall` access key's `allowance` field exists specifically to cap the financial exposure a limited-scope key can create against its owning account — the on-chain analog of the reported "slippage limit" that a user sets to bound a transaction's effect. When a transaction is signed directly with such a key, `verify_and_charge_tx_ephemeral` enforces the cap via `check_and_compute_new_allowance` [1](#0-0)  before the key can authorize any spend. However, when the very same key signs a `DelegateAction` and the resulting `SignedDelegateAction` is unpacked on-chain in `apply_delegate_action`, the allowance check is never invoked — the function validates signature, expiry, sender/receiver match, and nonce, but has no call into the allowance-checking path at all [2](#0-1) .

## Finding Description
`FunctionCallPermission.allowance` is described in the protocol data model as a hard balance cap: "Allowance is a balance limit to use by this access key to pay for function call gas and transaction fees. When this access key is used, both account balance and the allowance is decreased by the same value" [3](#0-2) . This is the on-chain guarantee equivalent to the "slippage limit" in the external report: a bound the key's creator relies on to constrain what the key can authorize.

In the direct-signing path, this bound is checked and mutated atomically as part of transaction verification: `verify_and_charge_tx_ephemeral` calls `check_and_compute_new_allowance`, and an insufficient allowance fails the transaction with `NotEnoughAllowance` before any state changes [1](#0-0) .

When the same key instead signs a `DelegateAction` (NEP-366 meta transaction), the relayer pays all gas/deposit costs on its own account, and `apply_delegate_action` performs signature verification, `max_block_height` expiry check, sender/receiver match, and key/nonce validation via `validate_delegate_action_key` — but at no point checks or decrements `allowance` [4](#0-3) . This is explicitly acknowledged in the architecture docs: "For allowance, however, there is no check. All costs have been covered by the relayer. Hence, even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work... if someone were to limit a function access key to one trivial action by setting a very small allowance, that is circumventable by going through a relayer." [5](#0-4) 

The pattern mirrors the reported bug class precisely: a user-declared bound intended to be checked at the moment of authorization is only enforced on one execution path (direct submission), while a second, equally reachable path (meta-transaction/relayer submission) silently skips it — analogous to Passage's order-matching path skipping the slippage check that was only enforced by an off-chain keeper on the "normal" path.

## Impact Explanation
An account owner who issues a `FunctionCall` access key with a small `allowance` does so specifically to cap the blast radius of that key (e.g., an automation bot, a dApp session key, or a key handed to a semi-trusted service). Because `apply_delegate_action` never checks the allowance, any holder of that key can wrap its authorized actions in a `SignedDelegateAction` and have an independent relayer submit it, executing actions whose *implied* cost basis exceeds the allowance the owner set — the on-chain enforcement point for the user-declared limit is simply absent on this path. This breaks the authorization/access-control guarantee that the key's allowance is supposed to provide, an unauthorized-value-movement-adjacent access-control bypass reachable purely by an unprivileged holder of a restricted key plus any relayer account, both of which are ordinary transaction signers.

## Likelihood Explanation
This requires only a `FunctionCall` access key holder and a cooperating (or even the same) relayer account submitting a standard `SignedTransaction` containing an `Action::Delegate`; both are default capabilities of any account. No validator or node compromise is needed, and the behavior is deterministic and reproducible on every apply of a delegate action. It is explicitly documented as a known, unaddressed gap rather than a hypothetical.

## Recommendation
Enforce the `FunctionCallPermission.allowance` bound inside `apply_delegate_action` (or in `validate_delegate_action_key`) by computing the total cost of the inner actions/gas being authorized by the delegated key and checking/decrementing the corresponding access key's allowance the same way `check_and_compute_new_allowance` does for direct transactions, rejecting with an equivalent `NotEnoughAllowance` error when the delegated request would exceed it — mirroring the fix pattern the external report cites (checking the limit at the actual point of state-changing execution rather than relying on an out-of-band assumption that the relayer's payment makes the limit irrelevant).

## Proof of Concept
1. Account `alice` adds a `FunctionCall` access key `K` with `receiver_id = "bob.near"`, `method_names = []`, and `allowance = 1 yoctoNEAR` (effectively unusable directly, since any real function call costs far more, as shown by the direct-path test `test_validate_transaction_invalid_not_enough_allowance` which fails with `NotEnoughAllowance` for a 100-yocto allowance [6](#0-5) ).
2. `alice` (holder of `K`) signs a `DelegateAction { sender_id: alice, receiver_id: bob.near, actions: [FunctionCall{...}], public_key: K, max_block_height: <future> }`, following the same construction as `meta_tx_from_actions` [7](#0-6) .
3. Any relayer account wraps this in a `SignedTransaction` and submits it, paying gas/deposit itself.
4. `apply_delegate_action` validates signature, `max_block_height`, sender/receiver, and key/nonce via `validate_delegate_action_key`, but never calls `check_and_compute_new_allowance` or otherwise inspects `allowance` [2](#0-1) , so the function call executes successfully despite the 1-yoctoNEAR allowance that would have rejected it on the direct-signing path.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }
