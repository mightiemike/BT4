### Title
`liquidate-multi` silently commits partially-executed liquidations that fail mid-flow, stranding liquidator funds - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` batches per-position liquidations through `(map call-liquidate positions)` and always returns `(ok (list ...))` regardless of whether individual liquidations succeeded or failed [1](#0-0) . `call-liquidate` invokes the public `liquidate` function directly as an in-contract call (not `contract-call?`) [2](#0-1) . Inside `liquidate`, a real value-moving cross-contract call (`vault-system-repay`, which pulls the liquidator's repayment tokens into the vault) executes and commits *before* the subsequent cross-contract calls that update the debt ledger (`debt-remove-scaled`) and seize collateral (`collateral-remove`) [3](#0-2) .

### Finding Description
This is the same bug class as the SUI-receiver report: a multi-step operation performs a value-affecting side effect, then a later step in the same logical operation can fail — but the failure is absorbed rather than causing a full revert, so the side effect is not undone and the caller is left worse off.

Concretely:
1. `liquidate-multi` calls `map call-liquidate positions` [4](#0-3) .
2. `call-liquidate` calls `liquidate` as a plain function call within the same contract, not via `contract-call?` [2](#0-1) .
3. Within `liquidate`, preconditions are asserted, then `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` executes — a genuine `contract-call?` to a vault contract that pulls tokens from the liquidator and updates vault accounting [5](#0-4) .
4. Immediately after, `(try! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-to-remove debt-aid))` and `(try! (contract-call? .v0-market-vault collateral-remove ...))` run to update the borrower's debt/collateral ledger [6](#0-5) . If either of these later calls returns an error (e.g., due to a market-vault-side validation failure), the `try!` propagates an `err` value out of `liquidate`.
5. Because `call-liquidate` does not wrap this in its own `contract-call?` boundary, and `liquidate-multi`'s `map` merely collects each `(response ok/err)` into a list without unwrapping, the overall `liquidate-multi` call still returns `(ok (list ... (err ...) ...))`.
6. Since the *top-level* public function (`liquidate-multi`) returns `(ok ...)`, Clarity commits the entire transaction — including the `vault-system-repay` transfer that already occurred for the failing position, even though the corresponding debt-removal/collateral-seizure never happened.

The bound value is the liquidator's repayment tokens already pulled into the vault by `vault-system-repay`; the invalidating event is the later failure of `debt-remove-scaled`/`collateral-remove` for the same position within the same `map` iteration; the later use is the top-level `(ok ...)` return of `liquidate-multi` that commits everything unconditionally. This exactly parallels the report's root cause: a value-affecting action is taken, a later validation/step can fail, and the failure is not treated as fatal to the enclosing flow, so the earlier action's effects are stranded rather than reverted.

### Impact Explanation
A liquidator using `liquidate-multi` for one of the affected positions loses the repayment tokens they supplied (pulled by `vault-system-repay`) without receiving the corresponding collateral, and the borrower's debt is not reduced in market-vault's ledger — causing an accounting desync between the vault (which now holds/accounted-for extra repayment) and market-vault (whose debt ledger is unchanged for that position). This is theft/permanent loss of the liquidator's funds for that batch entry, and can also produce protocol-level ledger inconsistency (vault balance vs. recorded debt), which falls under the in-scope Critical impact classes (theft of user funds / protocol insolvency).

### Likelihood Explanation
This requires a scenario in which `debt-remove-scaled` or `collateral-remove` on `.v0-market-vault` can fail for a position after `vault-system-repay` on the debt-asset vault has already succeeded (e.g., a stale/racing position where the borrower's collateral or debt state changed between when `liquidate` computed its scaled values and when it applied them — the note in the code explicitly says `liquidate-multi` intentionally skips price-feed/staleness re-validation per-position and processes a stale snapshot: "Note: price-feeds not supported in batch"). Given `liquidate-multi` is designed for third-party liquidator bots batching many positions in one transaction, and any transient market-vault-side failure (e.g., a position whose collateral was already fully removed by a concurrent operation earlier in the same batch) can trigger this, the likelihood is non-trivial in production usage of the batch liquidation feature.

### Recommendation
Ensure each per-position liquidation in `liquidate-multi` is executed within its own atomic rollback boundary, e.g. by invoking `liquidate` via `contract-call? .v0-market-vault` / `contract-call? .v0-4-market liquidate ...` (a genuine cross-contract call) inside `call-liquidate` rather than a direct in-contract function call, so that if the inner call returns `err`, only that position's state changes (including the `vault-system-repay` transfer) are rolled back while the rest of the batch and the top-level `(ok ...)` return remain unaffected.

### Proof of Concept
Not independently executable from the indexed context — verifying the exact conditions under which `debt-remove-scaled`/`collateral-remove` on `.v0-market-vault` can return an error after `vault-system-repay` has already succeeded requires reading `market-vault.clar`'s implementation of those functions, which I was not able to fully inspect before running out of tool iterations. The control-flow/atomicity argument above (steps 1–6) is fully supported by the cited `v0-4-market.clar` code and is independent of the specific error condition; any error return from either of those two `market-vault` calls, for any reason, triggers this stranding behavior.
