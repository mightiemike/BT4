### Title
Rounding causes protocol reserve fee (`treasury-lp`) to be silently dropped while borrow index still advances - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and identical `accrue` implementations in the other v0-vault-*.clar files)

### Summary
`accrue()` computes the protocol's share of newly-accrued interest (`reserve-inc` → `treasury-lp`) from the delta between the *old* borrow index and the *next* borrow index, then unconditionally advances `index` to `next` regardless of whether that share rounded to zero. Once `index` moves forward, the interest increment that produced a zero `reserve-inc` can never be recovered by a future `accrue()` call, because the next call's `old-debt` baseline starts from the already-advanced index. This mirrors the reported `BoostAggregator.unstakeAndWithdraw` pattern: a value is computed and gated by a threshold/rounding check (`pendingRewards > DIVISIONER` / `reserve-inc > u0`), the accounting/mint is skipped below that threshold, but the tracking state that would let the shortfall be captured later (`tokenIdRewards[tokenId]` / `index`) is mutated anyway, permanently stranding the un-minted value.

### Finding Description
In `accrue()`: [1](#0-0) 

- `old-debt`/`new-debt` are computed from `scaled-principal * idx` and `scaled-principal * next` respectively, using `mul-div-down` (rounds toward zero).
- `reserve-inc` is `debt-delta * fee-reserve / BPS`, also `mul-div-down`. For small `debt-delta` (frequent `accrue()` calls, e.g. triggered by every `deposit`/`redeem`/`system-borrow`/`system-repay`/`transfer` in quick succession, or low-utilization/low-rate periods with short time deltas), `reserve-inc` rounds down to `0`.
- `treasury-lp` is only computed/minted `(if (> treasury-lp u0) (try! (ft-mint? zft treasury-lp .dao-treasury)) false)` — when `reserve-inc` is `0`, `treasury-lp` is `0` and no shares are minted to `.dao-treasury`.
- Independent of whether the fee was minted, `index` is unconditionally advanced: `(if (not (is-eq idx next)) (var-set index next) false)`.
- On the *next* call to `accrue()`, `old-debt` is computed from the new (already advanced) `idx`, not from the original pre-accrual index. The interest increment that produced the rounded-to-zero `reserve-inc` is therefore never revisited or combined with a subsequent delta — it is permanently excluded from any future `reserve-inc`/`treasury-lp` calculation.

This is exactly analogous to the `BoostAggregator` bug: `pendingRewards` below `DIVISIONER` skips the `protocolRewards`/claim accounting, but `withdrawToken` (and later `tokenIdRewards[tokenId]` reset in `onERC721Received`) happens regardless, permanently losing the sub-threshold reward. Here, `reserve-inc` rounding to `0` skips the `dao-treasury` mint, but `index` (the state that anchors the next computation) advances regardless, permanently losing the sub-rounding-threshold protocol fee.

### Impact Explanation
Every time `reserve-inc` rounds to zero, the DAO treasury's share of that interest increment is permanently forfeited rather than deferred/accumulated — it silently accrues to LPs instead of the protocol reserve. Because `accrue()` runs on virtually every vault interaction (`deposit`, `redeem`, `transfer`, `system-borrow`, `system-repay`), this can happen repeatedly, especially under frequent transaction activity or low `fee-reserve`/low-utilization conditions where `debt-delta * fee-reserve / BPS < 1`. This causes a permanent loss of unclaimed protocol yield that would otherwise go to `.dao-treasury`, matching the in-scope High-severity impact class: "theft of unclaimed yield ... or permanent freezing of unclaimed yield ... of funds."

### Likelihood Explanation
This requires no privileged access, no external attacker interference between users, and no oracle manipulation — it is a deterministic consequence of `mul-div-down` rounding combined with unconditional index advancement, and it manifests under normal usage patterns (frequent calls to any vault function that triggers `accrue()`, or low `debt-delta` intervals). It is a single-transaction/single-call arithmetic property of the contract, not a multi-user race, so it is within the scope of the requested analog class ("mutation evaluated before its guard").

### Recommendation
Do not mint the treasury share separately from advancing the index. Either:
1. Accumulate the un-minted `reserve-inc` remainder (or the associated `debt-delta` that produced a zero `reserve-inc`) in a persistent variable and carry it forward into the next `accrue()` call's `debt-delta` calculation instead of resetting the baseline to `next`, or
2. Round the reserve fee up (`mul-div-up`) so a fee is always minted when any interest at all has accrued, ensuring the amount is never silently dropped, or
3. Only advance `index` when the corresponding `treasury-lp` mint has actually occurred, so the interest delta is preserved for accounting in a subsequent call if the fee couldn't be minted this time.

### Proof of Concept
1. Assume `fee-reserve` and `BPS` such that `reserve-inc = debt-delta * fee-reserve / BPS` rounds to `0` whenever `debt-delta < BPS / fee-reserve` (e.g., with `fee-reserve` at a modest reserve factor, any `debt-delta` below that threshold rounds to zero under integer division).
2. Caller repeatedly triggers any vault action that calls `accrue()` (e.g., small `deposit`s in quick succession, or `transfer` calls) within short time windows so that each `next-index` computation yields a small `debt-delta`.
3. In each such call: `old-debt`/`new-debt` differ by a small `debt-delta` → `reserve-inc` computes to `0` → `treasury-lp` is `0` → the `(if (> treasury-lp u0) ... false)` branch skips the `ft-mint? zft treasury-lp .dao-treasury` call entirely. [2](#0-1) 
4. Regardless, `(if (not (is-eq idx next)) (var-set index next) false)` runs unconditionally, advancing `index` to `next`. [3](#0-2) 
5. On the next `accrue()` call, `old-debt` is recomputed using the now-advanced `idx` (the previous `next`), so the interest increment consumed in step 3 (whose fee rounded to zero) is not re-included in any future `debt-delta`. The reserve share for that increment is permanently lost — it is never minted to `.dao-treasury`, yet the underlying interest has already been fully reflected in LP share value via the advanced index.

Note: this pattern is identical across all six vault contracts in `mainnet/contracts/vault/` (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`), each containing the same `accrue()` logic. [4](#0-3) [5](#0-4)
