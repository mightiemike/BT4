### Title
`ByResource` deduction step records an untrusted, non-zero balance value when `ConvertToBalance` fails - ([File: core/services/workflows/metering/metering.go])

### Summary
`ByResource`, a `DeductOpt` used by `Report.Deduct` to earmark spend for a capability invocation, calls `r.balance.ConvertToBalance(spendType, amount)` and only guards the *balance mutation* on error, not the *value it records into the report*. On error, `bal` is used directly to populate `step.Deduction` before the error/metering-mode check is applied, mirroring the Canto `swappedAmount` bug where a value returned alongside an error is trusted to be safe.

### Finding Description
In `ByResource`:
```go
bal, err := r.balance.ConvertToBalance(spendType, amount)
if err != nil {
    // Fail open, continue optimistically
    r.switchToMeteringMode(fmt.Errorf("failed to convert to balance [%s]: %w", spendType, err))
}

step.Deduction = bal
``` [1](#0-0) 

Unlike the Canto case, the underlying function does not zero its return value on error — `convertToBalance` explicitly returns the caller-supplied `amount` unmodified when the resource type is unknown:
```go
func (bs *balanceStore) convertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[fromResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}
	...
``` [2](#0-1) 

So on error, `bal == amount` (the raw, unconverted resource amount) rather than zero. `ByResource` unconditionally assigns this to `step.Deduction = bal` *before* checking `r.meteringMode`:
```go
step.Deduction = bal

// if in metering mode, exit early without modifying local balance
if r.meteringMode {
    return []capabilities.SpendLimit{}, nil
}

return []capabilities.SpendLimit{}, r.balance.Minus(bal)
``` [3](#0-2) 

While `r.balance.Minus(bal)` (the actual credit-balance mutation) is correctly skipped once metering mode is entered, the `step.Deduction` field is not reset and is persisted into `r.steps[ref]` via the `defer` at the top of the closure:
```go
defer func() {
    r.steps[ref] = step
}()
``` [4](#0-3) 

This `Deduction` value flows into the metering report sent to the billing service and Beholder via `FormatReport`/`SendReceipt`/`EmitReceipt`, so a conversion failure silently injects an incorrect (raw, unit-mismatched) `Deduction` figure into the emitted report instead of a safe zero value, exactly analogous to the original bug of trusting an error-path return value.

### Impact Explanation
The actual local credit balance (`r.balance`) is protected because `r.meteringMode` is checked before `Minus` is invoked, so this is not a direct fund-drain. However, it is a misreporting/data-tampering issue: the metering report submitted to the billing service (`SendReceipt` → `SubmitWorkflowReceipt`) and to Beholder (`EmitReceipt`) will contain a `Deduction` value derived from an unconverted/garbage amount rather than zero, which corrupts downstream billing/usage records and telemetry for that workflow step whenever a `ConvertToBalance` failure occurs (e.g., due to a spend type missing from the rate card). This matches the class of bug flagged in the source report: a value from a failed operation is trusted and propagated instead of being reset to a safe default.

### Likelihood Explanation
`ConvertToBalance` fails whenever the resource/spend type is not present in the billing rate card returned by `GetWorkflowExecutionRates` (`ErrResourceTypeNotFound`), which is a realistic and reachable condition for any capability whose spend type isn't yet configured in the rate card, or when the rate card is stale/incomplete. This is reachable by any workflow execution that deducts against an unregistered spend type — no privileged or malicious actor is required to trigger it, only a configuration/rate-card gap, making this moderately likely to occur in production.

### Recommendation
Zero out (or otherwise sanitize) the returned value when `ConvertToBalance` errors, before it is written into `step.Deduction`, e.g.:
```go
bal, err := r.balance.ConvertToBalance(spendType, amount)
if err != nil {
    r.switchToMeteringMode(fmt.Errorf("failed to convert to balance [%s]: %w", spendType, err))
    bal = decimal.Zero
}
step.Deduction = bal
```
More generally, `convertToBalance`/`ConvertToBalance` should not return the unconverted input amount as if it were a valid credit value on error; callers should never rely on an error-path return value being safe by convention.

### Proof of Concept
1. Configure a `Report` whose rate card does not include a given `spendType` (e.g., omit it from `GetWorkflowExecutionRates` response, or trigger `ErrEmptyRateCard`/partial rate card population as in `NewReport`) — see rate-card construction path in `NewReport` [5](#0-4) .
2. Call `report.Deduct(ref, metering.ByResource(spendType, capabilityID, amount))` with a non-zero `amount` for that unregistered `spendType`.
3. Inside `ByResource`, `r.balance.ConvertToBalance(spendType, amount)` returns `(amount, ErrResourceTypeNotFound)` per `convertToBalance` [2](#0-1) .
4. `step.Deduction` is set to the raw `amount` (not zero) and stored in `r.steps[ref]`, while `r.meteringMode` is now `true` so the real balance is untouched.
5. Call `report.FormatReport()`/`SendReceipt`/`EmitReceipt` and observe that the emitted `MeteringReportStep` carries a non-zero `Deduction`-derived value for a step that actually failed conversion, rather than reporting zero/no deduction.
