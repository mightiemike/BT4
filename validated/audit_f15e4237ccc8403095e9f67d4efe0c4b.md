### Title
Witness Can Front-Run `payReward` Every Block by Updating Brokerage Right Before Reward Distribution to Reduce Voter Payouts - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
`UpdateBrokerageContract`/`UpdateBrokerageActuator` lets a witness set an arbitrary brokerage percentage (their self-take from block/tx-fee rewards) at any time, with no timelock. The change is written to a "pending" `REMARK` (`-1`) slot immediately, and each maintenance cycle `MaintenanceManager.doMaintenance()` copies that pending value forward into the *next* cycle's brokerage slot. Because a witness fully controls both the timing of the `UpdateBrokerageContract` transaction and (as a block producer) the ordering/inclusion of transactions within blocks they produce, this is directly analogous to the MIMO `setAutomation()` front-running issue: a party who benefits from a lower "cut" for others (here, voters/delegators who share in `delegationStore.addReward`) can adjust the parameter that determines the split immediately before the value that uses it is committed for a new cycle.

### Finding Description
`UpdateBrokerageActuator.execute()` calls `delegationStore.setBrokerage(ownerAddress, brokerage)`, which stores the new value only at the `REMARK` (`cycle = -1`) key [4](#0-3) . This "pending" value is not used directly for reward computation; instead, at every maintenance boundary, `MaintenanceManager.doMaintenance()` reads the witness's current `REMARK` brokerage and copies it into the brokerage slot for `nextCycle`:
```
delegationStore.setBrokerage(nextCycle, witness.createDbKey(),
    delegationStore.getBrokerage(witness.createDbKey()));
``` [2](#0-1) 

`MortgageService.payReward()` (invoked on every block reward and every transaction-fee reward payout to the witness) reads the brokerage for the *current* cycle number and uses it to split the reward between the witness's own allowance and the pool that is later distributed to voters via `delegationStore.addReward` (consumed in `withdrawReward`/`VoteRewardUtil.withdrawReward` and `computeReward`) [3](#0-2) .

Because the witness's own `REMARK` brokerage value can be freely overwritten by a new `UpdateBrokerageContract` transaction at any block, and the witness (as a super representative) both controls when it submits that transaction and how it orders/produces the block containing it, the witness can wait until immediately before the maintenance-cycle boundary (when a very large block/transaction-fee reward is expected) and push the brokerage to the maximum allowed value (`ActuatorConstant.ONE_HUNDRED`) right before `doMaintenance()` snapshots the value for `nextCycle`. Since `getBrokerage` falls back to `DEFAULT_BROKERAGE` (20) only when no entry exists for the cycle [5](#0-4) , once a witness sets a high value it is baked into that cycle's reward split and voters relying on the previously advertised (lower) brokerage receive a smaller share of `addReward` for the whole cycle, only to have the witness lower it back afterward — mirroring the vaultOwner front-running `setAutomation()` pattern in the referenced report, where the beneficiary of the fee/incentive split can unilaterally and instantly change it around the moment value flows, with no delay/timelock protecting the counterparty (voters here, the keeper in the MIMO report).

### Impact Explanation
This affects the vote-reward split for an entire maintenance cycle, since `setBrokerage`/`getBrokerage` operate at cycle granularity rather than per-transaction, so unlike the MIMO keeper case (single tx impact) the java-tron analog can silently divert a full cycle's worth of voter rewards (`WITNESS_STANDBY_ALLOWANCE`, block rewards, and transaction fee rewards) to the witness with no on-chain delay to allow voters to react by un-voting.

### Likelihood Explanation
Likelihood is bounded by the fact that changing brokerage requires a `WitnessCapsule` to exist for the address (i.e., only registered witnesses can do this) [6](#0-5) , and the mechanism only takes effect at the next cycle boundary, so it's a self-serving/expected witness commission adjustment rather than an attack on an unrelated third party's specific transaction. This makes it materially weaker than the MIMO report's per-transaction front-running (which harms an arbitrary caller's expected fee within one block); this is a self-owner adjusting the commission on funds they themselves control (their own witness reward split), which the protocol treats as intended witness behavior, not third-party front-running.

### Recommendation
If stricter fairness guarantees are desired, apply a timelock (e.g., N-cycle delay) between `UpdateBrokerageContract` submission and the value taking effect (beyond the existing one-cycle delay), and/or emit an event/expose the pending brokerage via `GetBrokerageServlet` so voters can react before the value applies.

### Proof of Concept
1. A witness submits `UpdateBrokerageContract` with `brokerage = ActuatorConstant.ONE_HUNDRED` shortly before the maintenance boundary at which `MaintenanceManager.doMaintenance()` snapshots `REMARK` brokerage into `nextCycle`.
2. `doMaintenance()` copies this maximal value into `nextCycle`'s brokerage slot for that witness.
3. For the entirety of `nextCycle`, `MortgageService.payReward()` applies this maximal brokerage rate to every block reward and transaction-fee reward paid to the witness, diverting nearly the entire reward to the witness's own `allowance` instead of `delegationStore.addReward` (voter pool).
4. After the cycle, the witness submits another `UpdateBrokerageContract` to lower brokerage back to a normal, voter-friendly value, having captured one cycle's rewards at the expense of voters who voted expecting the lower rate.
