## Analysis

The Gearbox bug class (unchecked `to == address(0)` leading to permanent loss of transferred value) has a direct analog in Push Chain's revert/refund recipient handling.

**Root cause:** `RevertInstructions.FundRecipient` is a field supplied by the *depositing user themselves* as part of their source-chain deposit call (parsed unmodified from the on-chain event by `universalClient/chains/common/event_processor.go`, function `constructInbound`): [1](#0-0) 

This value is canonicalized (`LenientCanonicalizeAddress`) but never checked for the EVM zero-address sentinel: [2](#0-1) 

Nor does `ValidateForExecution` check `RevertInstructions.FundRecipient` at all — it only validates `p.Recipient`: [3](#0-2) 

Every place that consumes `FundRecipient` guards only against the **empty string**, not the zero address:

- `buildRevertOutbound` (INBOUND_REVERT path): [4](#0-3) 

- `handleFailedOutbound` / `applyGasRefund` (re-mint on failed outbound and unused-gas refund): [5](#0-4) [6](#0-5) 

- `AttachRescueOutboundFromReceipt` (RESCUE_FUNDS path): [7](#0-6) 

In all four flows, `common.HexToAddress(recipient)` is called and passed straight into `CallPRC20Deposit` / `CallUniversalCoreRefundUnusedGas`, which mint PRC20 or refund gas to that address via `DerivedEVMCall`. If an unprivileged depositor supplies `revertRecipient = 0x0000000000000000000000000000000000000000` on the source chain, the string is non-empty, passes every check, and the mint/refund is executed against the zero address — a standard ERC-20-style burn — permanently destroying the bridged funds or gas refund with no recovery path (unlike a `RESCUE_FUNDS` scenario, since the tokens are already "delivered").

### Title
Missing zero-address check on `RevertInstructions.FundRecipient` causes permanent loss of reverted/refunded funds - (File: `x/uexecutor/keeper/outbound.go`, `x/uexecutor/keeper/build_revert_outbound.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
`RevertInstructions.FundRecipient` is attacker-controlled (set by the depositing user in the source-chain deposit call) and is used, unvalidated, as the mint/refund target for INBOUND_REVERT, gas-refund, and RESCUE_FUNDS flows. Only an empty-string check is performed; the EVM zero address is accepted as valid, causing PRC20 mints or gas refunds to be sent to `0x0`, permanently burning the funds.

### Finding Description
`constructInbound` in the universal client copies `RevertFundRecipient` straight from the parsed deposit event into `Inbound.RevertInstructions.FundRecipient` with no address validity check. `Inbound.Canonicalize` only trims/normalizes hex casing; `Inbound.ValidateForExecution` never inspects `RevertInstructions` at all. Every downstream consumer (`buildRevertOutbound`, `handleFailedOutbound`, `applyGasRefund`, `AttachRescueOutboundFromReceipt`) uses the pattern `if RevertInstructions != nil && FundRecipient != "" { recipient = FundRecipient }`, which treats the literal zero address as a legitimate recipient. The resulting `common.HexToAddress(recipient)` is fed into `CallPRC20Deposit`/`CallUniversalCoreRefundUnusedGas`, minting/depositing tokens to `0x0`.

### Impact Explanation
This causes permanent, unrecoverable loss of user or protocol-controlled funds: bridged token re-mints on inbound/outbound revert, and excess gas-fee refunds, can be irrevocably burned to the zero address by an ordinary unprivileged depositor simply setting their own revert-recipient field to `address(0)` on the source chain. This matches the in-scope impact "permanent loss ... of user or protocol-controlled funds," triggered purely through the default deposit/inbound path with honest validators and honest nodes.

### Likelihood Explanation
High likelihood for a griefing/self-harm trigger and non-trivial for third-party loss: any user submitting a cross-chain deposit can set the revert-recipient parameter arbitrarily. If a relayer, integrator, or wallet defaults an unset/placeholder revert field to the zero address (a common convention for "no override"), the funds-loss condition triggers automatically whenever a revert or gas-refund path is taken (swap failure, execution failure, or gas overpayment) — all of which are routine, non-adversarial execution outcomes.

### Recommendation
Add an explicit zero-address check wherever `RevertInstructions.FundRecipient` is consumed (or centrally in `ValidateForExecution`/`Canonicalize`): reject/ignore `FundRecipient` when it equals `EvmZeroAddress`, falling back to `inbound.Sender`/`outbound.Sender` instead of treating it as a valid override, consistent with the checks already applied to `Recipient` in `ValidateForExecution`.

### Proof of Concept
1. Attacker deposits funds on a source chain via the gateway contract, setting `revertRecipient = 0x0000000000000000000000000000000000000000` in the deposit call.
2. Universal Validators observe the event; `constructInbound` sets `Inbound.RevertInstructions.FundRecipient = "0x0000000000000000000000000000000000000000"` (non-empty string, passes all checks).
3. Execution later fails (e.g., autoswap failure in `ExecuteInboundGas`, or downstream outbound execution failure), triggering `buildRevertOutbound`/`handleFailedOutbound`.
4. `recipient` resolves to the zero address; `CallPRC20Deposit(ctx, prc20, common.HexToAddress("0x0..0"), amount)` mints the bridged PRC20 supply to `0x0`.
5. Funds are permanently unrecoverable — no burn/refund fallback exists for value sent to the zero address.

// ValidateForExecution checks fields that are required for actual execution of the inbound.
// Called after ballot finalization, before ExecuteInbound. Failures here produce a failed
// PCTx and (for non-isCEA) a revert outbound, rather than dropping the vote.
func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}
