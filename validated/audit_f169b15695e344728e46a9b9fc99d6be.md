## Finding

### Title
Stale reverted-block classes bypass declaration check for Cairo0 (deprecated) contract classes, enabling honest-node state divergence - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` re-validates a class-hash's declaration status against current committed state (`is_declared`) only when the class served from the process-wide `ContractClassManager` cache is a Cairo1 (`RunnableCompiledClass::V1`/`V1Native`) class. Cairo0 (`RunnableCompiledClass::V0`) classes served from the same cache skip this re-validation entirely, even though the code's own comment acknowledges that a cache hit "might contain a declared class from a reverted block." This is the logical analog of the reported Chromium "use after free" bug class: a stale reference to state that should have been invalidated (a class declared in a now-reverted/unwound block) is reused as if it were still valid, but only the V1 branch was patched against it.

### Finding Description
The relevant code: [1](#0-0) 

```
if let Some(runnable_class) =
    self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
{
```

`contract_class_manager` is a long-lived, LRU-based, process-global cache (`GlobalContractCache`/`RawClassCache`) shared across many blocks in the sequencer/full-node process: [2](#0-1) 

It is populated whenever a class is read from the backing state reader, independent of whether that read later turns out to belong to a block that gets reverted (e.g. an L1 reorg causing `revert_state_diff`), as confirmed by the storage-level revert logic that explicitly removes a Cairo0 class's committed declaration record when its declaring block is reverted: [3](#0-2) 

However, `get_compiled_from_class_manager`'s cache is never invalidated on such a revert. For Cairo1 classes the developers added an explicit `is_declared` check specifically to guard against this "reverted block" scenario (see comment and the dedicated regression test `cached_but_verification_failed_after_reorg_scenario`): [4](#0-3) 

But the equivalent check is missing for `RunnableCompiledClass::V0(_)`, whose branch is a no-op (`{}`). Consequently, once a Cairo0 class hash has been cached by any node process (from a block that is later reverted, e.g. due to an L1 reorg, or from a resync/replay path that touched a state which no longer reflects committed chain state), any later transaction on that same process that references the class hash (via `deploy`, `library_call`, or address dispatch to a contract still pointing at that class) will silently succeed using the stale cached bytecode, even though `is_declared`/committed state says the class is not (or no longer) declared.

### Impact Explanation
This causes **honest-node divergence**: a node whose in-memory cache still holds the Cairo0 class from before a revert will accept and execute a transaction that references that undeclared class hash, producing a state diff/committed root that differs from a node that never cached it (e.g., freshly synced) and correctly rejects the transaction with `StateError::UndeclaredClassHash`. Divergent nodes computing different state roots/block hashes for the same block breaks Starknet's committed-state consistency, and Starknet OS re-execution over the DB-truth (uncached) view will similarly reject what the cache-poisoned sequencer accepted, which can block the network from reaching agreement on / proving the block.

### Likelihood Explanation
The condition (a block containing a Cairo0 class declaration or usage being reverted, e.g. via L1 reorg handling, while the in-process global class cache is warm) is a normal operational path already anticipated and partially fixed by the developers for Cairo1 — the same risk was simply not closed for Cairo0. No special privileges are needed; any ordinary transaction (invoke/deploy/library_call) referencing the affected class hash after the revert triggers the divergent behavior on affected nodes.

### Recommendation
Apply the same `is_declared` (or an equivalent deprecated-class declaration check, e.g. via `get_deprecated_class_definition_block_number`) re-validation to the `RunnableCompiledClass::V0(_)` branch in `get_compiled_from_class_manager`, mirroring the Cairo1 path, so cached deprecated classes are also verified against current committed state before being served.

### Proof of Concept
1. Node executes/syncs a block `B` in which class hash `C0` (Cairo0) is declared or used; `contract_class_manager` caches the compiled `RunnableCompiledClass::V0` for `C0`.
2. Block `B` is reverted (e.g., L1 reorg triggers `revert_state_diff`), removing `C0`'s declaration record from committed storage, as validated by `revert_doesnt_delete_previously_declared_classes`/revert tests in `apollo_storage`.
3. A new transaction on the reorganized chain calls `deploy`/`library_call` referencing `C0`, which is no longer declared in the current committed state.
4. On this node, `get_compiled_from_class_manager` hits the stale cache, takes the `RunnableCompiledClass::V0(_) => {}` branch, skips `is_declared`, and returns the stale bytecode — the transaction succeeds.
5. On a node without the warm cache (or with is_declared enforced), the same transaction is rejected with `StateError::UndeclaredClassHash`, producing a different state root/execution result for the same block — honest-node divergence.

```rust
    /// Locks the cache for atomic access. Although conceptually shared, writing to this cache is

        self.0.lock().expect("Global contract cache is poisoned.")

    pub fn get(&self, class_hash: &ClassHash) -> Option<T> {
        self.lock().cache_get(class_hash).cloned()
    }

    pub fn set(&self, class_hash: ClassHash, contract_class: T) {
        self.lock().cache_set(class_hash, contract_class);
    }

    pub fn clear(&mut self) {
        self.lock().cache_clear();
    }
```
