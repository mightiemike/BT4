### Title
Uncaught `ArithmeticException` on overflowing endowment in `callToPrecompiledAddress` diverges from `callToAddress` error handling - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.callToPrecompiledAddress` calls `msg.getEndowment().value().longValueExact()` at line 1679 with no `try/catch`, while the equivalent code path `Program.callToAddress` wraps the identical call in a `try/catch(ArithmeticException)` block (lines 1033-1042) that either throws a `TransferException` with energy refund (post-Constantinople) or rethrows the raw exception. An attacker-crafted contract that issues `CALL`/`CALLCODE`/`DELEGATECALL` with a `value` operand whose `DataWord.value()` exceeds `Long.MAX_VALUE` targeting a precompiled contract address will hit the unguarded `longValueExact()` in `callToPrecompiledAddress` and produce different exception/refund behavior than the same call directed at a non-precompiled address.

### Finding Description
`callToAddress` (Program.java:1000-1042) explicitly anticipates that the 256-bit endowment `DataWord` can represent a value bigger than a signed `long`, and guards the conversion: [1](#0-0) 

`callToPrecompiledAddress` (Program.java:1659 onward), which is invoked from the CALL-family opcode handling whenever the target `codeAddress` resolves to a precompiled contract, performs the exact same conversion without any exception handling: [2](#0-1) 

Both functions are reachable from the same opcode dispatch (`CALL`/`CALLCODE`/`DELEGATECALL`) and take an attacker-controlled `MessageCall` built from stack operands that an unprivileged user fully controls via ordinary contract bytecode (push a value word > `Long.MAX_VALUE`, then `CALL` to a known precompiled address). The only difference between the two paths is the destination address type (precompiled vs. regular contract), which the attacker also controls by choosing the target address. This causes an uncaught `ArithmeticException` to propagate out of `callToPrecompiledAddress` instead of the controlled `TransferException`/refund-energy behavior seen in `callToAddress`.

### Impact Explanation
The divergence causes different exception types and refund/halt semantics for functionally identical crafted bytecode depending solely on whether the call target is a precompiled address. In `callToAddress`, when `VMConfig.allowTvmConstantinople()` is enabled, the energy is refunded and a well-defined `TransferException` is thrown; in `callToPrecompiledAddress`, an unchecked `ArithmeticException` propagates instead. Since VM exception handling and energy accounting flow into deterministic transaction execution, any place downstream that treats these exception types differently, or the raw `ArithmeticException` not being caught by an appropriate handler in the interpreter loop, produces inconsistent halt/refund behavior between the two paths. This is a code-path inconsistency/potential deterministic execution issue rather than a value theft or state-corruption bug, since both paths ultimately fail the call and do not commit the transfer.

### Likelihood Explanation
Feasibility is high in the sense that an unprivileged attacker fully controls the endowment `DataWord` value pushed onto the stack for the `CALL`/`CALLCODE`/`DELEGATECALL` opcode, and can pick a precompiled contract address as the target. This makes the code path in `callToPrecompiledAddress` trivially reachable with a single crafted contract deployment and execution, no special privileges required.

### Recommendation
Wrap `msg.getEndowment().value().longValueExact()` in `callToPrecompiledAddress` (Program.java:1679, and its repeated calls at 1703/1707) in the same `try/catch(ArithmeticException)` pattern used in `callToAddress` (Program.java:1033-1042), refunding energy and throwing `TransferException` consistently regardless of whether the call target is a precompiled contract.

### Proof of Concept
Java unit test plan (JUnit) in the VM test module:
1. Build two `MessageCall` instances with identical `opCode` (`CALL`), identical `inDataOffs`/`inDataSize`/`energy`, but an `endowment` `DataWord` constructed from a `BigInteger` value greater than `Long.MAX_VALUE` (e.g., `BigInteger.valueOf(Long.MAX_VALUE).add(BigInteger.ONE)`).
2. Target one `MessageCall` at a normal deployed contract address (invoking `Program.callToAddress`) and the other at a known precompiled contract address, e.g. `0000...01` (ecrecover) (invoking `Program.callToPrecompiledAddress` via `PrecompiledContracts.getContractForAddress`).
3. Execute both through the `Program` instance under `VMConfig.allowTvmConstantinople() = true`.
4. Assert: `callToAddress` throws `TransferException` with message `"endowment out of long range"` and energy is refunded via `refundEnergy`.
5. Assert (currently failing): `callToPrecompiledAddress` should behave identically but instead throws raw `ArithmeticException` uncaught, demonstrating the divergence described above.
