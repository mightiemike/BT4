### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, allowing corrupted state/hot-state/position roots to pass replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant check used by replay/verification tooling to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` stored in the ledger (and covered by the transaction accumulator proof). The function explicitly checks status, gas used, write-set hash, and event root hash, but by its own documented `TODO` it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
The function signature and checks are: [2](#0-1) 

It validates `status`, `gas_used`, and the write-set/event hashes against the target `TransactionInfo`, then returns `Ok(())` unconditionally — the comment right before the return spells out the gap explicitly: [3](#0-2) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class, accumulator-committed fields. [4](#0-3) 

These roots are produced in `DoStateCheckpoint::run`, which computes the state root, and conditionally the hot-state root (gated by `HOT_STATE_ROOT_IN_TXN_INFO`) and the native-position root (gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`). [5](#0-4) 

`ensure_match_transaction_info` is used by `storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` — i.e., the exact tooling whose job is to detect divergence between local re-execution and the authenticated on-chain ledger. Because the comparator does not check the checkpoint-hash fields, any of these tools would report success even if `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` computed by local execution diverge from what is stored in the authenticated `TransactionInfo`.

### Impact Explanation
This falls squarely in the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong accumulator root ... accepted as valid" categories. If a bug in state-root computation (e.g., in `DoStateCheckpoint`, hot-state Merkle update, or the newly introduced native-position root logic) produces a wrong `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, replay-verification and debugger tooling that rely on `ensure_match_transaction_info` will not detect it, since these fields are silently excluded from the equality check. This can mask a divergence between the locally computed ledger state and the state actually committed/authenticated on-chain, undermining the primary safety mechanism (replay-verify) meant to catch exactly this class of bug before or after a fork.

### Likelihood Explanation
The gap is not hypothetical: the code's own comment states it directly and ties it to a real feature flag (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that is being staged in this codebase. The trigger condition is "any bug elsewhere causes the locally recomputed checkpoint hash(es) to differ from the authenticated ones" — which is plausible given these are newly added, actively developed subsystems (hot state, native-position roots) as evidenced by the surrounding `TODO(HotState)`/`TODO(trading-native)` comments throughout `do_state_checkpoint.rs` and `execution_output.rs`.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, and when present, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against the corresponding values recomputed by `DoStateCheckpoint`/the executor before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and ideally immediately, since `HOT_STATE_ROOT_IN_TXN_INFO`/`TRANSACTION_INFO_V1` are already toggleable), so replay-verify and debugger paths genuinely detect any divergence in these consensus-committed roots.

### Proof of Concept
Not independently exploitable as an on-chain state-integrity bug by itself (it does not corrupt the ledger); rather, it is a verification-integrity gap: it removes the ability of `replay_on_archive`, `aptos-debugger`, and the CLI verify path to catch a real corruption in `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` should one occur, because `ensure_match_transaction_info` never compares those fields — confirmed by reading the function body and its documented `TODO` at [3](#0-2) .

**Note on completeness:** I was not able to fully trace the exact call sites in `execution/executor/src/chunk_executor/mod.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` (i.e., confirm whether they gate any additional check around this function, or whether an outer caller separately verifies checkpoint hashes elsewhere) before running out of iterations, so it's possible—but unconfirmed—that another code path independently validates these roots and mitigates the gap; this should be verified before treating this as fully proven.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
