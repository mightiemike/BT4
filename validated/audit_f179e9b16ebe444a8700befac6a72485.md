## Title
`TransactionOutput::ensure_match_transaction_info` skips validating hot-state and native-position checkpoint hashes during chunk replay/verification - ([File: types/src/transaction/mod.rs])

### Summary
During chunk replay and archive-replay verification, `TransactionOutput::ensure_match_transaction_info` is the function responsible for asserting that a locally re-executed `TransactionOutput` matches the `TransactionInfo` fetched from an untrusted/remote source before that data is accepted and committed. The implementation checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `hot_state_checkpoint_hash` or `position_state_checkpoint_hash`, both of which are now real, consensus-committed fields of `TransactionInfoV1`. [1](#0-0) 

### Finding Description
`TransactionInfoV1` carries `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` as consensus-authenticated commitments, gated by the `HOT_STATE_ROOT_IN_TXN_INFO` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flags respectively. [2](#0-1) [3](#0-2) 

`ensure_match_transaction_info` is the single-transaction integrity gate used by chunk replay/verification paths (`execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `storage/db-tool/src/replay_on_archive.rs`) to confirm a locally computed `TransactionOutput` is consistent with a `TransactionInfo` obtained from a peer/backup before it's accepted into local storage. It validates `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event root hash — but the function's own comment states it deliberately skips the checkpoint hashes: [4](#0-3) 

This means the hot-state root and the native-position state root — both bound into the accumulator via `TransactionInfoV1` and used as trust anchors for fast-sync snapshot restoration (`expected_snapshot_root` in `state-sync/state-sync-driver/src/bootstrapper.rs` reads `position_state_checkpoint_hash()` directly to seed `StateSnapshotRestore` proof verification) — are never locally re-derived and compared during chunk-executor replay/verify or `replay_on_archive` tooling. [5](#0-4) 

### Impact Explanation
Because chunk replay/verify (used both by full-node chunk execution acceptance and by `db-tool replay-on-archive`, which is the tool operators use to certify that an archive matches consensus-agreed state) does not verify these checkpoint hashes, a divergence between the locally computed hot-state root or position-state root and the one baked into an accepted `TransactionInfoV1` will go undetected. This can let corrupted/incorrect hot-state or native-position ledger state be silently accepted as "verified" during replay, and it undermines the very proof-binding guarantee (`TransactionInfo` binding a version to committed roots) that downstream consumers such as the fast-sync `expected_snapshot_root` path rely on as an authenticated anchor. This is a hard-fork-class integrity gap in state-commitment verification: a computational divergence in hot-state/native-position roots between two otherwise-agreeing nodes would not be caught by this check.

### Likelihood Explanation
This is not attacker-triggerable in the sense of a malicious external input causing incorrect processing by a single honest node in isolation — it requires the hot-state or position-state root computation to actually diverge (e.g., due to a bug in the new hot-state/native-position write-set materialization logic, both of which are recently added, feature-flagged, WIP subsystems per the `TODO(HotState)` / `TODO(trading-native)` comments throughout `types/src/write_set.rs` and `execution/executor/src/workflow/do_get_execution_output.rs`). Given how new and actively-changing this code is, and that the comment itself flags the gap as a known but unaddressed issue ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), the likelihood of an eventual silent divergence going undetected during replay is realistic once these features are enabled on mainnet.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally-computed hot-state checkpoint hash and native-position checkpoint hash (when present in the `TransactionOutput`/local execution context) against `txn_info.hot_state_checkpoint_hash()` and `txn_info.position_state_checkpoint_hash()`, mirroring the existing `state_change_hash`/`event_root_hash` checks, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet.

### Proof of Concept
Not independently exploitable without a companion bug that causes a genuine hot-state/native-position root computation divergence; this finding documents a verification gap (missing invariant check), not a directly triggerable exploit. To demonstrate: construct a `TransactionOutput` whose locally-recomputed hot-state or position-state root differs from a given `TransactionInfoV1`'s `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` while `state_change_hash`, `event_root_hash`, `status`, and `gas_used` all match — `ensure_match_transaction_info` returns `Ok(())`, confirming the check is bypassed, as directly acknowledged by the code's own `TODO(trading-native)` comment. [4](#0-3)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
