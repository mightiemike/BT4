### Title
OAuth callback validates HMAC against a different `shop` value than the one used for token exchange and session creation, due to inconsistent duplicate-parameter parsing - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
In the OAuth `callback` handler, the `shop` query parameter is read twice using two different parsing strategies. If the callback URL contains a duplicated `shop` parameter, HMAC verification is performed against one value while the actual access-token exchange and resulting `Session.shop` are built from a *different* value. This is the same bug class as the C4 finding: a security check (duplicate/uniqueness validation) is bypassed because the same logical input can be represented multiple ways, and different parts of the code resolve that representation inconsistently.

### Finding Description
In `callback()`: [1](#0-0) 

`shop` (used only for logging here) is extracted with `query.get('shop')`, which returns the **first** occurrence of a repeated `URLSearchParams` key.

Then, for HMAC validation: [2](#0-1) 

`Object.fromEntries(query.entries())` is used to build `authQuery`. `Object.fromEntries` keeps the **last** occurrence of a repeated key when iterating entries. This `authQuery` (with the *last* `shop` value) is what gets passed into `validateHmac`.

`validateHmac` → `normalizeQuery` does not perform any de-duplication/merging for the `admin` signator when the input is a plain object (only `URLSearchParams` input is normalized, and even then duplicate keys are joined with a comma rather than rejected): [3](#0-2) 

Finally, the value actually used to exchange the authorization code for an access token and to build the resulting `Session` is taken again with `query.get('shop')` (the **first** occurrence): [4](#0-3) 

So: HMAC is validated against the *last* `shop=` value in the query string, but the shop actually contacted for the token exchange and stored on the resulting `Session` is the *first* `shop=` value. An attacker who can influence the callback URL (e.g., by modifying the URL before the browser follows the Shopify-issued redirect, or via any surface that reflects/forwards this URL) can append a second, attacker-chosen `shop` parameter before the legitimately signed one, so that:
- The last occurrence (Shopify's real, signed shop) makes HMAC validation pass.
- The first occurrence (attacker-chosen, format-valid `*.myshopify.com`/`*.shopify.com` domain) is what `sanitizeShop` cleans and uses for the `/admin/oauth/access_token` POST and for `session.shop`.

### Impact Explanation
This breaks the invariant that "the shop that was cryptographically verified via HMAC is the shop the rest of the callback logic operates on." At minimum this is a validation/usage inconsistency bug of the same class as the reported issue (a check that treats two representations of the same logical field as independent, letting one representation satisfy validation while another representation drives the sensitive action). Whether this is exploitable end-to-end into full token theft or cross-tenant session creation depends on how strictly Shopify's own `/admin/oauth/access_token` endpoint binds the authorization `code` to the shop it was issued for — this external enforcement cannot be verified from this repository. If that binding is strict (which is the expected behavior), the attack would fail at the token-exchange step with an error from Shopify, limiting impact to a confused/rejected request rather than actual token theft. I could not find any code path in this repo that further weakens or bypasses that binding.

### Likelihood Explanation
Low-to-moderate. Exploitation requires an attacker to get a victim (or their own browser) to load a callback URL with a duplicated `shop` parameter positioned so the legitimately-signed value is last, and it relies on external (Shopify-hosted) behavior for the ultimate outcome, which is outside the analyzed codebase's control. No test in the repository (`packages/apps/shopify-api/lib/auth/oauth/__tests__/`) was found covering duplicate `shop` parameters in the callback flow, so this inconsistency is not explicitly guarded against or tested.

### Recommendation
- Extract `shop` once, using a single consistent parsing rule, and use that same normalized value for HMAC validation, the token-exchange request, and session creation.
- Reject requests where a query parameter that must be single-valued (e.g., `shop`, `hmac`, `code`, `state`, `timestamp`) appears more than once in the admin OAuth callback, mirroring the existing `APP_PROXY_SINGLE_VALUE_PARAMS` duplicate-rejection logic in `hmac-validator.ts` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts` lines 118-151), instead of silently joining or picking first/last differently across call sites.

### Proof of Concept
1. Shopify redirects the merchant's browser to:
   `https://yourapp.com/auth/callback?code=CODE&state=STATE&timestamp=TS&hmac=VALID_HMAC_FOR_SHOP%3Dlegit-shop.myshopify.com&shop=legit-shop.myshopify.com`
2. Attacker (with control over the URL before it's submitted, e.g. via a crafted link) inserts an extra `shop` parameter before the legitimate one:
   `...?shop=attacker-shop.myshopify.com&code=CODE&state=STATE&timestamp=TS&hmac=VALID_HMAC_FOR_SHOP%3Dlegit-shop.myshopify.com&shop=legit-shop.myshopify.com`
3. `query.get('shop')` in `oauth.ts` line 147/194 returns `attacker-shop.myshopify.com` (first occurrence) — this becomes `cleanShop`.
4. `Object.fromEntries(query.entries())` used for HMAC validation (`oauth.ts` line 178) resolves `shop` to `legit-shop.myshopify.com` (last occurrence), so `validateHmac` succeeds against the real signature.
5. The app proceeds to POST to `https://attacker-shop.myshopify.com/admin/oauth/access_token` with the victim's authorization `code`, and (if that request were to succeed) would create a `Session` labeled with `attacker-shop.myshopify.com` — a divergence between the HMAC-verified shop and the shop actually acted upon.

Note: step 5's ultimate impact (whether Shopify's token endpoint would accept a code issued for one shop when contacted at a different shop's endpoint) is an external dependency I could not verify within this codebase, so I cannot confirm full token theft — only the concrete, in-repo validation/usage inconsistency described above.

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
