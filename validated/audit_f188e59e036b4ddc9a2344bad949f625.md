### Title
Unbounded Growth of Per-Shop Session-ID Array Causes Denial of Service in Redis/KV Session Storage - (File: packages/apps/session-storage/shopify-app-session-storage-redis/src/redis.ts)

### Summary
The `RedisSessionStorage` and `KVSessionStorage` adapters track all session IDs belonging to a shop in a single JSON array value keyed by shop domain (`idKeysArray` in `redis.ts`, `shopIds` in `kv.ts`). This array is never bounded and, for non-embedded apps using online (per-user) access tokens, a new random UUID session ID is minted on every OAuth completion — including auto-triggered re-authentications for otherwise-unauthenticated requests. Because the whole array is read, mutated, and rewritten as one value on every `storeSession`, and iterated with a per-ID network round-trip in `findSessionsByShop`, the structure degrades identically to the `SHToken.users` array in the reference report: unbounded growth from repeated actor-triggered writes leads to increasingly expensive/failing reads and writes.

### Finding Description
For online, non-embedded apps, `createSession()` assigns a brand-new session id via `crypto.randomUUID()` instead of a deterministic `shop_userId` id: [1](#0-0) 

Each time `storeSession` is called, the Redis adapter appends the new key to the per-shop array without any cap and rewrites the entire JSON blob: [2](#0-1) 

Reading sessions for a shop requires parsing the whole array and then issuing one sequential `client.get()` call per stored id: [3](#0-2) 

The same pattern (single unbounded array value, linear-time membership checks with `.includes()`/`.indexOf()`, full-array rewrite) exists in the KV adapter: [4](#0-3) 

Critically, this array can be grown by an unprivileged, unauthenticated request path: `validateAuthenticatedSession`'s auth-code-flow branch calls `redirectToAuth` whenever no valid session is found for the request: [5](#0-4) 

`redirectToAuth` triggers `api.auth.begin()` server-side for any non-embedded request: [6](#0-5) 

Completing that OAuth flow via `callback()` in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts` calls `createSession()` and `storeSession()`, appending yet another random UUID entry to the shop's array — with no deduplication against previously issued (and possibly still valid) sessions for the same actor, and no upper bound on array size.

`AppInstallations.includes()`/`delete()` in `shopify-app-express` also depend directly on `findSessionsByShop`, so as the array balloons, install-detection and uninstall cleanup slow down or fail alongside normal session lookups: [7](#0-6) 

### Impact Explanation
This is analogous to the HAL-07 class: an ever-growing, iterated data structure that all core storage operations (`storeSession`, `deleteSession`, `findSessionsByShop`) must read and/or rewrite in full. As the array grows into the thousands/millions of entries:
- `storeSession`/`addKeyToShopList` must deserialize, linearly scan (`.includes()`), and reserialize an increasingly large JSON string on every single OAuth completion for the shop, increasing latency and Redis/KV memory/value-size pressure.
- `findSessionsByShop` must issue one sequential network round-trip per stored id, causing dramatic slow-downs or timeouts.
- `AppInstallations.includes()`/`delete()`, which are core to app-install detection and app-uninstalled webhook cleanup, depend on `findSessionsByShop` and will degrade or fail together.
- Redis/KV backends impose maximum value sizes (e.g. Redis strings up to 512MB, but practical operational limits are far lower), so this can eventually cause writes to fail outright, a genuine denial-of-service of the session storage layer for that shop.

### Likelihood Explanation
Reachability depends on a non-embedded, online-token app configuration where `redirectToAuth`/`begin()` is triggered automatically for unauthenticated or invalid-session requests, and `callback()` mints a fresh UUID session id each time. An attacker with app access (a single merchant/customer or someone who can force repeated OAuth completions, e.g. by scripting the auth flow or repeatedly hitting endpoints that lack a valid session cookie) can drive this growth without needing any elevated privilege. However, I could not fully confirm within the available context whether there is any deduplication or replacement logic elsewhere in the flow (e.g. a check that would overwrite the same UUID instead of creating a new one on repeated flows), and whether typical production configurations use the embedded/token-exchange path (which uses the deterministic `shop_userId` id and is not affected) as the default. This uncertainty affects the practical likelihood; embedded apps using token exchange are not vulnerable to this specific growth vector since their session ids are deterministic and idempotent per user.

### Recommendation
- For non-embedded, online-access sessions, avoid unconditionally minting a new `crypto.randomUUID()` per OAuth completion; prefer a deterministic id (or dedupe/replace an existing valid session for the same shop+user) to prevent unbounded accumulation.
- Cap or paginate the per-shop session-id list in `RedisSessionStorage`/`KVSessionStorage`, and prune expired/invalid session ids proactively (e.g., on `storeSession` or via a background job) rather than relying solely on explicit `deleteSession` calls.
- Replace the JSON-array-as-single-value pattern with a native set/sorted-set (Redis `SADD`/`SREM`) or a per-shop namespace + index that supports O(1) add/remove and avoids full-value reserialization and unbounded value growth.
- Add a maximum size/age enforcement to `findSessionsByShop` results and to the underlying id list, evicting oldest/expired entries.

### Proof of Concept
Conceptual reproduction (not executed, based on code paths above):
1. Configure a non-embedded app using `RedisSessionStorage` with `useOnlineTokens: true`.
2. Repeatedly hit an app route without a valid session cookie; each request is redirected by `validateAuthenticatedSession` → `redirectToAuth` → `api.auth.begin()`, and complete the resulting OAuth `callback()` (scriptable since it only requires a valid, repeatable OAuth grant for the same shop/user).
3. Each completed callback calls `createSession()`, generating a new `crypto.randomUUID()` id (see `create-session.ts:35-40`), and `storeSession()` appends it to the shop's array in `addKeyToShopList` (`redis.ts:151-166`) with no bound.
4. After many iterations, `findSessionsByShop(shop)` (`redis.ts:128-145`) and `addKeyToShopList` become progressively slower (one round-trip per id / full-array rewrite), and eventually may fail due to Redis/KV value-size or latency limits — reproducing the "core functions fail due to gas/resource limitations" pattern described in HAL-07, but for the session-storage read/write path instead of gas.

    await this.ready;

    if (!idKeysArrayString) return [];

    const idKeysArray = JSON.parse(idKeysArrayString);

    for (const idKey of idKeysArray) {
