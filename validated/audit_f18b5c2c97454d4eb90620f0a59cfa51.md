### Title
Rescue outbound resolves attacker-chosen `event.PRC20` without binding it to the original locked asset, producing a mismatched asset/amount `RESCUE_FUNDS` outbound - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`AttachRescueOutboundFromReceipt` builds the rescue `OutboundTx` by resolving `event.PRC20` (a value decoded from a topic on the `RescueFundsOnSourceChain` log) via `GetTokenConfigByPRC20(ctx, originalUtx.InboundTx.SourceChain, event.PRC20)`, then copies `Amount` from `originalUtx.InboundTx.Amount` — the amount of the *original*, unrelated asset — without ever checking that `event.PRC20` corresponds to `originalUtx.InboundTx.AssetAddr`.

### Finding Description
`event.PRC20` comes straight from `DecodeRescueFundsOnSourceChainFromLog`, which takes it verbatim from the log topic emitted by the `UniversalGatewayPC` contract [3](#0-2) . This log is produced as a side effect of `ExecutePayload`, which any unprivileged user can trigger by submitting a payload that gets executed through their own UEA (`k.CallUEAExecutePayload`) and that in turn calls the on-chain gateway's rescue-triggering function with whatever `universalTxId` and `PRC20` argument the caller supplies [4](#0-3) . The keeper then:

1. Looks up the original stuck UTX purely by the attacker-supplied `universalTxId` [5](#0-4) .
2. Resolves `tokenCfg` from `event.PRC20` on `originalUtx.InboundTx.SourceChain` — with no check that this equals `originalUtx.InboundTx.AssetAddr` [2](#0-1) .
3. Builds the outbound using `tokenCfg.Address` (asset Y) for `ExternalAssetAddr`, `event.PRC20` (Y) for `Prc20AssetAddr`, but `originalUtx.InboundTx.Amount` (X's amount) for `Amount` [6](#0-5) .

This confirms the attack path described in the question is real at the Go-keeper level: an unprivileged caller can supply any registered `PRC20` (unrelated to the originally locked asset) as long as it's registered for the same `SourceChain`, and the keeper will happily attach a rescue outbound that pairs asset Y with amount X.

### Impact Explanation
This directly matches the "corruption of PRC20 or native asset accounting… revert instructions must not misroute value or attach the wrong asset semantics" impact category. If honest UVs/TSS trust `OutboundTx.ExternalAssetAddr`/`Amount` as canonical instructions for what to release on the source chain, this bug lets an attacker force a mismatched (wrong-token, wrong-amount) release instruction into canonical UTX state, potentially causing TSS to sign a transfer of an amount of token Y (denominated in token X's raw units) that has no relation to any funds actually locked for token Y. Depending on the two tokens' decimals/units this could result in material overpayment from the source-chain vault relative to what's actually owed for that UTX, i.e. unauthorized/incorrect release of protocol-controlled funds.

However, this is bounded by other guards that are honored:
- The `recipient` is still taken from `originalUtx.InboundTx.RevertInstructions`/`Sender` — not attacker-controlled, so funds don't get redirected to an attacker-chosen address [7](#0-6) .
- Eligibility gating (deposit must have `FAILED`, or an `INBOUND_REVERT` must have reached `REVERTED`) still requires the referenced UTX to be a genuinely stuck one [8](#0-7) .
- Whether this outbound record actually causes TSS to release mismatched funds depends on the (out-of-scope) source-chain Vault contract's `rescueFunds(bytes32,bytes32,address,uint256,(address,bytes))` implementation and whatever parameters the universalClient/TSS signer forwards from this record [9](#0-8) . This code path is outside the audited scope and its behavior (whether it independently validates asset/amount coherence before releasing funds) could not be verified from available index content.

### Likelihood Explanation
High — the entry point (`ExecutePayload` → UEA-driven contract call → gateway event) is reachable by any unprivileged user, and no additional privilege is required to choose an arbitrary registered `PRC20` for the same source chain as an existing stuck UTX.

### Recommendation
In `AttachRescueOutboundFromReceipt`, validate that `tokenCfg.Address == originalUtx.InboundTx.AssetAddr` (or equivalently that `event.PRC20`'s canonical PRC20 representation matches the PRC20 originally associated with `originalUtx.InboundTx.AssetAddr`) before constructing the rescue `OutboundTx`, rejecting the rescue attempt if the asset doesn't match the one that was actually locked.

### Proof of Concept
1. Create a stuck CEA UTX whose inbound `AssetAddr` is token X (deposit `PcTx[0].Status == "FAILED"`).
2. Register token Y with its own PRC20 mapping on the same `SourceChain`.
3. Trigger `ExecutePayload` with a payload that causes the gateway contract to emit `RescueFundsOnSourceChain` referencing the stuck UTX's id but with `prc20 = Y`.
4. Observe that the resulting `OutboundTx.ExternalAssetAddr`/`Prc20AssetAddr` are Y while `Amount` is copied from the original X-denominated `InboundTx.Amount`, as shown at [6](#0-5) .

Note: full confirmation of fund-loss impact requires inspecting the source-chain Vault contract's `rescueFunds` implementation and the universalClient code that forwards `ExternalAssetAddr`/`Amount` into the TSS-signed call, which is outside indexed/available scope for this review; the Go-side mismatch itself is confirmed and unguarded.

func DecodeRescueFundsOnSourceChainFromLog(log *evmtypes.Log) (*RescueFundsOnSourceChainEvent, error) {
	if len(log.Topics) < 4 {
		return nil, fmt.Errorf("RescueFundsOnSourceChain: need 4 topics, got %d", len(log.Topics))
	}
	if strings.ToLower(log.Topics[0]) != strings.ToLower(RescueFundsOnSourceChainEventSig) {
		return nil, fmt.Errorf("not a RescueFundsOnSourceChain event")
	}

	event := &RescueFundsOnSourceChainEvent{
		UniversalTxId: log.Topics[1], // bytes32 as 0x-prefixed hex
		PRC20:         common.HexToAddress(log.Topics[2]).Hex(),
		Sender:        common.HexToAddress(log.Topics[3]).Hex(),
	}
