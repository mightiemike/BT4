## Analog Vulnerability Analysis

The external report describes unbounded growth of a per-key array (`_group[account][tokenId]`) that is linearly iterated/shifted on every operation, eventually exceeding gas limits. The closest legitimate analog in Agave's AccountsDb is the per-pubkey `slot_list` (`SlotList<T>`) inside `AccountMapEntry`, which plays exactly the same structural role: one vector per key that accumulates entries and is walked/updated linearly by nearly every index operation (`upsert`, `get_and_then`, `scan`, `clean_rooted_entries`, `purge_older_root_entries`, snapshot/index generation).

### Title
Per-pubkey `slot_list` can grow unbounded when reclaim is skipped for hot accounts, causing disproportionate CPU cost on every index access - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsIndex` stores, for every pubkey, a `slot_list` vector of `(Slot, AccountInfo)` entries [1](#0-0) . Normally, when a pubkey is rewritten in a new slot, `update_slot_list` either replaces the entry in place or, with `UpsertReclaim::ReclaimOldSlots`, evicts older uncached entries and appends the new one, keeping the list compact [2](#0-1) . However, `do_flush_slot_cache` chooses `UpsertReclaim::IgnoreReclaims` instead of `ReclaimOldSlots` whenever `pubkeys_to_store` is `PubkeysToStore::All` — which happens for every unrooted slot ahead of `max_clean_root`, or whenever an in-flight scan pins `max_clean_root` back [3](#0-2) . In that mode, each successive write for the same pubkey is simply appended to `slot_list` rather than compacted, so the list only shrinks later, during a full `clean_accounts` pass on that pubkey's bin.

### Finding Description
`construct_candidate_clean_keys`/`max_clean_root` explicitly documents that a long-running scan caps how far cleaning can proceed: *"If there is a long running scan going on, this could prevent any cleaning based on updates from slots > max_clean_root"* [4](#0-3) . While such a scan is held open (or simply while a pubkey remains "hot" across many not-yet-rooted/not-yet-cleaned slots), every store of that pubkey appends a new `(slot, AccountInfo)` tuple to its `slot_list` instead of reclaiming the older one, because `IgnoreReclaims` is used for `PubkeysToStore::All` flushes [5](#0-4) .

Every subsequent index operation on that pubkey walks the *entire* `slot_list` linearly:
- `purge_older_root_entries`/`clean_rooted_entries` scans the whole list to find the newest slot at or below the clean root and retains/reclaims the rest [6](#0-5) .
- `do_clean_scan`'s per-candidate closure calls `latest_slot` over the full `slot_list` for every clean pass [7](#0-6) .
- `calc_delete_dependencies` iterates `slot_list` for every candidate pubkey on every clean cycle [8](#0-7) .
- `visit_duplicate_pubkeys_during_startup` and the lt-hash startup calculation also perform O(len(slot_list)) work per pubkey during index generation/startup [9](#0-8) .

This mirrors the reported pattern precisely: an append-only, per-key list that grows with each "purchase" (write), is only compacted lazily, and is walked in full by every read/clean/replace/shrink code path that touches that key — the same shape as `_group[account][tokenId]` and `_upsertGroup`/`_transferGroups`.

### Impact Explanation
For a hot pubkey (e.g., a frequently-traded token account, a popular program's state account) that is rewritten every slot while `max_clean_root` is held back (by an ongoing scan, or simply by clean's cadence lagging bank-freeze rate under load), `slot_list` length grows roughly proportional to the number of unrooted/uncleaned writes. Every subsequent `get_and_then`, `scan`, `clean_rooted_entries`, and shrink/dedup pass over that pubkey then costs O(n) instead of O(1), inflating background cleaning, snapshot/index-generation, and read-path CPU cost disproportionately to the actual account state. This falls under the accepted "disproportionate storage and CPU cost" category rather than a hard crash, since Rust's `Vec` won't panic from growth alone and clean eventually catches up once the blocking condition clears.

### Likelihood Explanation
This requires no crafted/malicious snapshot and no validator/peer privilege — any unprivileged workload that writes to the same account across consecutive slots (normal high-frequency trading/programs) combined with a mechanism that delays `max_clean_root` (e.g., an RPC client holding a long scan, as acknowledged in the code's own comments) is sufficient to trigger sustained list growth. It is a naturally reachable condition in the existing clean/flush design rather than a purely theoretical one, though it is self-limiting once the blocking scan ends and clean is allowed to run.

### Recommendation
- **Short term:** Bound how far behind `max_clean_root` can lag due to an ongoing scan (e.g., a time or slot-count cap after which clean proceeds regardless, evicting/copying the scan's required version separately), and/or cap the number of uncompacted entries `IgnoreReclaims` is allowed to accumulate per pubkey before forcing an eager reclaim.
- **Long term:** Avoid O(n) linear scans over `slot_list` in hot paths (`latest_slot`, `purge_older_root_entries`) by keeping the list sorted by slot (it already tends to be append-ordered) and using binary search, or by proactively reclaiming immediately for accounts whose `slot_list` exceeds a threshold, independent of the global clean cadence.

### Proof of Concept
1. Start an `AccountsDb` and mark an artificial "ongoing scan" root (or otherwise cap `max_clean_root` low), mirroring what `construct_candidate_clean_keys`/`max_clean_root` do when an RPC scan is active [4](#0-3) .
2. Repeatedly `store_for_tests` the same pubkey at successive slots and `add_root`, then `flush_rooted_accounts_cache` — since these slots are all above the pinned `max_clean_root`, `pubkeys_to_store` resolves to `PubkeysToStore::All`, and `do_flush_slot_cache` uses `UpsertReclaim::IgnoreReclaims` [5](#0-4) , so no old slot-list entries are reclaimed.
3. Observe `accounts_index.get_and_then(&pubkey, |e| e.unwrap().slot_list_lock_read_len())` growing linearly with the number of stores (this exact instrumentation is already used in existing tests such as `test_remove_zero_lamport_single_ref_accounts_after_shrink` [10](#0-9) ), demonstrating the vector never shrinks while `max_clean_root` stays capped, confirming the O(n) growth and subsequent O(n) cost on any read/clean pass touching that pubkey.

        slot: Slot,
        account_info: T,
        other_slot: Option<Slot>,
        reclaims: &mut ReclaimsSlotList<T>,
        reclaim: UpsertReclaim,
    ) -> (i32, usize) {
        let mut ref_count_change = 1;

        let old_slot = other_slot.unwrap_or(slot);

        // If we find an existing account at old_slot, replace it rather than adding a new entry to the list
        let mut found_slot = false;
        let mut final_len = slot_list.retain_and_count(|cur_item| {
            let (cur_slot, _) = cur_item;
            if *cur_slot == old_slot {
                // Ensure we only find one!
                assert!(!found_slot);

                // Replace the item
                let reclaim_item = mem::replace(cur_item, (slot, account_info));
                match reclaim {
                    UpsertReclaim::ReclaimOldSlots => {
                        reclaims.push(reclaim_item);
                    }
                    UpsertReclaim::IgnoreReclaims => {
                        // do nothing. nothing to assert. nothing to return in reclaims
                    }
                }

                found_slot = true;

                ref_count_change -= 1
            } else if reclaim == UpsertReclaim::ReclaimOldSlots {
                if *cur_slot < slot {
                    reclaims.push(*cur_item);
                    ref_count_change -= 1;
                    return false;
                }

                // Slot is new item that is being added to the slot list
                // If slot is already in the slot list, it must be replaced otherwise it will
                // lead to the same slot being duplicated in the list

                    *cur_slot, slot,

            true

            // if we make it here, we did not find the slot in the list

        slot_list: &mut SlotListWriteGuard<T>,
        reclaims: &mut ReclaimsWithNewestSlot<T>,

                .fetch_add(1, Ordering::Relaxed);
        }
        // Find the newest slot at or below the clean root, then reclaim every slot older than it.

            .iter()
            .map(|(slot, _)| *slot)

            .max()

            let should_purge = *slot < newest_slot;
            if should_purge {
                reclaims.push(((*slot, *value), newest_slot));
