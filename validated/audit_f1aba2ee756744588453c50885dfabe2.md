### Title
`RewardViCalService` aborts the entire node process on any single-record error while accumulating per-witness rewards - (File: chainbase/src/main/java/org/tron/core/service/RewardViCalService.java)

### Summary
The reported Connext issue is a "single failing external call breaks a whole batch loop" fail-safety problem: `RootManager.propagate` iterates over multiple independent connectors and a revert in any one of them reverts the whole call, halting the messaging network until manual intervention. The closest reachable analog in java-tron is `RewardViCalService`, whose periodically-scheduled `maybeRun`/`startRewardCal` path iterates over every witness record and, on any single exception, converts it into a `TronError` that is documented to trigger `System.exit`, killing the whole node rather than isolating the failure to the single bad record.

### Finding Description
`RewardViCalService.maybeRun()` is scheduled every 3 seconds via `ExecutorServiceManager.scheduleWithFixedDelay(es, this::maybeRun, 0, 3, TimeUnit.SECONDS)` [1](#0-0) . Inside, it drives `startRewardCal()`, which iterates over *every* entry of the witness store and processes each one independently:
```
DBIterator iterator = (DBIterator) witnessStore.iterator();
iterator.seekToFirst();
iterator.forEachRemaining(e -> accumulateWitnessReward(e.getKey()));
``` [2](#0-1) 

This is structurally the same pattern as `RootManager.propagate` looping over six independent connectors: a single loop body call per independent entity (witness vs. chain connector), where each iteration performs its own state read/write and is not isolated from the others.

The loop is wrapped by `maybeRun()`'s outer try/catch:
```
} catch (Exception e) {
  logger.error(" Find fatal error, program will be exited soon.", e);
  throw new TronError(e, TronError.ErrCode.REWARD_VI_CALCULATOR);
}
``` [3](#0-2) 

`TronError` is explicitly documented as fatal and non-catchable:
```
/**
 * If a {@link TronError} is thrown, the service will trigger {@link System#exit(int)} by
 * {@link Thread#setDefaultUncaughtExceptionHandler(Thread.UncaughtExceptionHandler)}.
 * NOTE: Do not attempt to catch {@link TronError}.
 */
``` [4](#0-3) 

So any single unexpected exception thrown by `accumulateWitnessReward` for *one* witness record (e.g. a corrupted/legacy DB entry, an unexpected null, an arithmetic edge case in `DelegationStore.accumulateWitnessVi`/`getReward`) is not isolated — it propagates out of `forEachRemaining`, out of `startRewardCal`, is caught only generically in `maybeRun`, and is rethrown as a fatal `TronError` that shuts down the entire node process. There is no try/catch around the per-record processing inside the loop, unlike the RootManager case where the fix (PR 2430) was to add per-iteration isolation (try/catch) so one bad connector doesn't take down the whole propagate call.

### Impact Explanation
Because `RewardViCalService` runs unconditionally on every full/witness node once the new reward algorithm is enabled (`enableNewRewardAlgorithm()`), a single malformed or edge-case witness record encountered during `accumulateWitnessReward` can crash every node executing this service simultaneously — a network-wide denial-of-service requiring manual restart/intervention, analogous to the messaging network "stopping until someone figures out the problem," except the java-tron consequence is more severe (full process exit via `System.exit`) rather than just a reverted call.

### Likelihood Explanation
This code runs automatically and periodically (every 3 seconds) once `newRewardCalStartCycle` is set, with no operator input required to trigger the loop — the only requirement is that some witness/delegation record trip an exception inside `accumulateWitnessReward`, `DelegationStore.getReward`, or `DelegationStore.accumulateWitnessVi`. Given it iterates over *all* witnesses (arbitrary, potentially large and historical data), and the loop lacks any per-entry isolation, the likelihood that a single bad or unexpected record causes a fleet-wide crash is non-trivial, especially across upgrades/migrations that touch delegation data formats.

### Recommendation
Wrap the per-witness processing inside `startRewardCal()`'s `forEachRemaining` callback (and similarly in `MaintenanceManager.doMaintenance()`'s per-witness VI accumulation loop, which has the same shape) in a try/catch that logs and skips the offending record instead of allowing the exception to propagate to the fatal `TronError` path. Reserve `TronError`/`System.exit` for truly unrecoverable, systemic failures (e.g. DB engine failure), not for per-record data-processing errors in a loop over independent entities.

### Proof of Concept
Not applicable as a standalone exploit — this is a code-review-level fail-safety defect. Conceptually: seed the witness/delegation store with a witness entry whose corresponding delegation `getReward`/`getWitnessVi` data is malformed such that `accumulateWitnessVi` (called from `accumulateWitnessReward`, reached via `MaintenanceManager.doMaintenance()`'s `consensusDelegate.getAllWitnesses().forEach(...)` at [5](#0-4) , or via `RewardViCalService.startRewardCal()`) throws (e.g. `ArithmeticException`, `NumberFormatException`, NPE on a null `BytesCapsule`). That exception is uncaught within the per-record loop body, propagates to `maybeRun`'s catch block, is wrapped as `TronError`, and via the documented uncaught-exception handler triggers `System.exit`, terminating the node.
