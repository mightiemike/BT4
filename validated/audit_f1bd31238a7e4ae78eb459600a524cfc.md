### Title
Stale Cairo0 class cache entries from reverted/discarded block execution are never re-validated against committed state - (File: `crates/blockifier/src/state/state_reader_and_contract_manager.rs`)

### Summary
The global, process-wide contract class cache (`ContractClassManager` / `TrivialClassManager`, backed by `class_cache: RawClassCache`) is populated during transaction execution and is **not scoped or cleared per block**. When `get_compiled_from_class_manager` finds a cached class, it re-validates against the authoritative committed state (`is_declared`) only for Cairo1 (`V1`) classes — the code explicitly skips this re-validation for Cairo0 (`V0`) classes, with a comment acknowledging the exact hazard: the cache "might contain a declared class from a reverted block."

### Finding Description
`StateReaderAndContractManager::get_compiled_from_class_manager` looks up `class_hash` in the shared `contract_class_manager` cache first: [1](#0-0) 

For `RunnableCompiledClass::V0` (Cairo0) it takes the cached entry unconditionally (`RunnableCompiledClass::V0(_) => {}`), while for any other (Cairo1) variant it calls `self.state_reader.is_declared(class_hash)` and rejects the class with `StateError::UndeclaredClassHash` if the class is not actually declared per the committed storage state. The comment directly above the Cairo1 branch states the cache "does not guarantee [declaration], since existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)" — i.e., the developers were aware that block execution which is later discarded (e.g., a losing consensus proposal, a failed/aborted speculative validation round) still writes into this shared cache via `set_and_compile`, and the entries are never invalidated when that block's state changes are thrown away.

The cache itself has no block-scoping or eviction tied to commit/revert: `TrivialClassManager::set_and_compile` simply inserts into a size-bounded LRU (`RawClassCache`/`GlobalContractCache`), with no linkage to whether the transaction that declared the class was ultimately committed: [2](#0-1) 

The persistent-state-backed `is_declared` check (used for the Cairo1 defense) is implemented against the confirmed storage, e.g. in `ApolloReader::is_declared`, which reads the class's declaration block number from confirmed storage: [3](#0-2) 

Because this same defensive check is skipped for V0 classes, a Cairo0 class hash that entered the shared cache while executing a transaction belonging to a block/proposal that is never committed remains available afterward and will be returned as a valid "declared" class on subsequent `get_compiled_class` calls, without ever confirming it is declared in the actually-committed state.

### Impact Explanation
This is structurally the same bug class as the referenced report: a piece of mutable, process-lifetime state (`phase4Users` mapping / here, the global class cache) that should be scoped to a single execution unit (an epoch / a block) is instead shared and reused across execution units without being cleared or fully re-validated, and only a partial guard exists (the Cairo1 `is_declared` re-check) while the Cairo0 path is left unguarded. Consequences:
- A class hash can be treated as compiled/executable by the sequencer even though it is not declared in the committed chain state, letting a transaction execute a Cairo0 class body that should be rejected as `UndeclaredClassHash`.
- Because the cache's contents depend on prior (possibly discarded) execution history of a given node process, two honest sequencer nodes with different execution/cache histories (one having previously speculatively executed the declaring transaction in a proposal that lost, another that never did) can diverge on whether the same block's transactions succeed or fail, producing different state diffs / state roots for the same block — a form of honest-node divergence.

### Likelihood Explanation
Reachable purely from unprivileged transaction submission: any account can submit a `Declare` (Cairo0) transaction and any subsequent transaction can reference/call that class hash. The hazard is triggered whenever the same class hash is executed in a proposal/round that is discarded (a normal, frequent consensus event — reorgs at the proposal level, failed rounds) followed by re-use of that class hash without going through a genuine, committed declare. Given the explicit code comment acknowledging this exact scenario for V1 and no equivalent protection for V0, the underlying condition (speculative execution polluting a shared, un-scoped cache) is confirmed to occur in normal operation; what's uncertain (see below) is only whether the surrounding validation/consensus pipeline in this codebase closes the gap through some other means for V0 classes specifically.

### Recommendation
Apply the same `is_declared` re-validation for `RunnableCompiledClass::V0` that is already applied to Cairo1 classes in `get_compiled_from_class_manager`, so a cache hit is never trusted for either class version without confirming declaration against the current committed state (or otherwise scope/invalidate the class cache per-block/per-round instead of keeping it as an unconditionally shared, unscoped structure).

### Proof of Concept
Not independently reproducible with the available tools (no test harness for consensus round rollback/discard was traced end-to-end). The root-cause code path is directly demonstrated by: [4](#0-3) 
which shows the asymmetric handling — V1 classes are re-verified against committed state on every cache hit, V0 classes are not, despite the cache being shared and populated by potentially-discarded block executions.

**Uncertainty**: I could not fully trace the consensus/proposal execution pipeline (`apollo_consensus`, `apollo_batcher`) to confirm whether the same `ContractClassManager` instance/cache is actually shared between a node's speculative execution of a losing/discarded proposal and its subsequent execution of the eventually-committed block, or whether a fresh cache/class manager is instantiated per proposal attempt. If the cache is not shared across discarded rounds, the practical exploitability of this specific asymmetry is reduced, though the code comment (`it might contain a declared class from a reverted block, for example`) strongly suggests the developers considered this a real, reachable scenario for the class cache in general.

    fn is_declared(&self, class_hash: ClassHash) -> StateResult<bool> {
        let state_number = StateNumber(self.latest_block);
        let class_declaration_block_number = self
            .reader()?
            .get_state_reader()
            .and_then(|sr| sr.get_class_definition_block_number(&class_hash))
            .map_err(|err| StateError::StateReadError(err.to_string()))?;
        Ok(
            matches!(class_declaration_block_number, Some(block_number) if block_number <= state_number.0),
        )
    }
