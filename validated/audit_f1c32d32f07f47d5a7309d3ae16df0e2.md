### Title
Missing Cairo-version check in deprecated `replace_class` syscall allows type-confused class replacement - (File: `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`)

### Summary
The `replace_class` syscall handler used by deprecated (Cairo0) contracts omits the class-version validation that the modern (Cairo1/Native) `replace_class` implementation enforces, mirroring the reported pattern of "fewer checks in sibling functions that should apply the same validation."

### Finding Description
In the current (Cairo1/Native) syscall path, `SyscallHandlerBase::replace_class` explicitly ensures the target class is of the same runtime family before allowing the state's `class_hash_at` mapping to be updated: [1](#0-0) 

This function reads the compiled class, checks `is_cairo1(&compiled_class)`, and rejects the call with `SyscallExecutionError::ForbiddenClassReplacement` if the target is a Cairo0 (V0) class — i.e., a Cairo1 contract cannot downgrade itself to a Cairo0 class hash via `replace_class`. This is confirmed by the dedicated regression test asserting the error message `"Cannot replace V1 class hash with V0 class hash"`: [2](#0-1) 

However, the sibling implementation used by the deprecated (Cairo0) syscall path performs no such check at all — it only verifies the class is declared, then unconditionally rewrites the contract's class hash: [3](#0-2) 

This is structurally identical to the reported bug class: two functions that perform the "same" state-mutating action (`replace_class`) on a pair of related-but-distinct object types (Cairo0 vs. Cairo1 compiled classes) apply inconsistent validation — one path checks the type/version compatibility, the sibling path does not.

### Impact Explanation
Because the deprecated path lacks the version check, a Cairo0 contract can call `replace_class` to switch its own class hash to *any* declared class, including a Cairo1 class, with no gating on this transition from that call site. If the two `replace_class` implementations are intended to enforce a symmetric invariant (only allow Cairo0→Cairo0 or Cairo1→Cairo1, or otherwise a controlled transition), the asymmetry means the invariant enforced on the Cairo1/Native side is not actually enforced network-wide, since the same conceptual state transition can be reached unguarded through the deprecated call frame. Any block relying on the modern path's restriction as a security/consistency invariant (e.g., to prevent contracts from being pushed into a Cairo0/Cairo1 execution-model mismatch that the OS or blockifier does not otherwise expect) would diverge from a client that assumes the restriction always holds, or could allow an unauthorized state transition that downstream execution or accounting logic does not correctly handle.

### Likelihood Explanation
Reachability requires only a single Invoke transaction from an unprivileged caller invoking a Cairo0 (deprecated) contract that itself invokes the `replace_class` syscall — a completely standard, permissionless action already supported today by Starknet contracts. No special privileges, mempool ordering, or multi-party coordination is needed.

### Recommendation
Add the equivalent class-version validation to the deprecated `replace_class` handler in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`, mirroring the check in `crates/blockifier/src/execution/syscalls/syscall_base.rs::replace_class` (i.e., reuse `is_cairo1`/an equivalent guard so both call sites enforce the same class-version transition policy).

### Proof of Concept
1. Declare a Cairo0 class `A` and a Cairo1 class `B`.
2. Deploy contract `C` as an instance of Cairo0 class `A`.
3. From an ordinary Invoke transaction, call `C`'s Cairo0 entry point, which internally issues the deprecated `ReplaceClass` syscall with `class_hash = B`.
4. Observe: `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:795-807` only checks that `B` is declared (`get_compiled_class`) and then calls `set_class_hash_at(storage_address, B)` unconditionally — no `is_cairo1` check is performed, unlike the parallel check present in `crates/blockifier/src/execution/syscalls/syscall_base.rs:369-378`, which is exercised and asserted by the test at `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:33-53` for the reverse direction (V1→V0).

**Note on confidence:** I was unable to find code comments, design docs, or commit history in this snapshot (only a single "Initial commit" is present, so no historical diff context is available) explaining the specific security rationale that makes V1→V0 replacement disallowed. It's possible the asymmetry is intentional (e.g., Cairo0→Cairo1 upgrade is a supported/expected migration path, while Cairo1→Cairo0 downgrade is specifically disallowed for VM/gas-accounting compatibility reasons), in which case the missing check in the deprecated path may not be a genuine vulnerability but rather correct, asymmetric-by-design behavior. This should be confirmed with the Starknet core protocol team before treating it as confirmed exploitable; the report is provided strictly as the closest structural analog found in-scope to the reported bug class.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
