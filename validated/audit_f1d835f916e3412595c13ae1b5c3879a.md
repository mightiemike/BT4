### Title
Unauthenticated CPU-Exhaustion DoS via Unvalidated Merkle Paths in Shielded TRC20 Spend-Proof Generation - ([File: framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java])

### Summary
The public HTTP/RPC endpoint `createShieldedContractParameters` accepts caller-supplied `path`, `anchor`, and note fields and passes them straight into `generateSpendProof()`/`librustzcashSaplingSpendProof`, which performs the full, CPU-expensive Sapling Groth16 proving computation before any anchor/merkle-membership validity is established. Because `formatPath()` only checks buffer length (`== 1024`), an anonymous caller can submit arbitrarily fabricated 1024-byte "paths" and anchors that are syntactically valid but not real merkle paths, forcing the node to burn full proving CPU cost on every request.

### Finding Description
`ShieldedTRC20ParametersBuilder.formatPath(byte[] path, long position)` validates only the byte-length of the path against `MERKLE_TREE_PATH_LENGTH` (1024) and throws only if the length is wrong: [1](#0-0) 

`generateSpendProof()` then unconditionally calls the native prover with the caller-supplied `anchor` and the reformatted `path`, without any prior check that the path is an actual merkle-tree membership proof for the claimed commitment/anchor: [2](#0-1) 

This method is reachable from an unauthenticated HTTP POST to `CreateShieldedContractParametersServlet` (and the "WithoutAsk" variant), which merely deserializes the request into `PrivateShieldedTRC20Parameters` and forwards it to `Wallet.createShieldedContractParameters(...)`: [3](#0-2) 

Wallet builds the spend input directly from request-provided `alpha`, `root` (anchor), `path`, and `pos` fields with no on-chain membership check performed in Java before invoking the builder: [4](#0-3) 

The rate-limiter framework applies a default `QpsRateLimiterAdapter` with `qps=1000` to any endpoint not explicitly configured, and no custom limit is configured for the shielded-parameter servlets in `reference.conf` (the example entries are commented out): [5](#0-4) [6](#0-5) 

Because the per-endpoint rate limiter only bounds request *count*, not CPU-time, and the default 1000 QPS ceiling is far above what a Groth16 spend-proof computation can sustain, an attacker can submit garbage-but-length-valid paths/anchors and force full proof computation on every request before the native code's internal verification eventually rejects the fabricated path.

### Impact Explanation
This is a CPU-exhaustion Denial-of-Service against the RPC/HTTP API surface: an anonymous client, without funds or signed transactions, can repeatedly invoke `createShieldedContractParameters` with random fixed-length byte buffers, causing the node to spend disproportionate CPU on native zk-SNARK proving before rejecting each request. Under concurrent load this can starve the node's thread/CPU resources needed to serve legitimate RPC traffic and block production/validation duties, matching the "DoS via RPC-API" bounty impact class.

### Likelihood Explanation
- No privileged role, signed transaction, or fee is required — the endpoint is a plain HTTP POST with JSON body.
- The attacker only needs to generate structurally valid `Note`/`SpendNoteTRC20` fields (which do not require possessing real spending keys or notes) and a 1024-byte buffer.
- The default rate limit (1000 QPS unless explicitly overridden) does not account for the per-request CPU cost of Sapling proving, and no anchor-membership pre-check exists to short-circuit obviously invalid inputs before the expensive computation runs.
- Fully repeatable: each concurrent connection can trigger the same expensive path independently of prior requests, and there is no state/economic cost gating repeated calls.

### Recommendation
- Add a cheap pre-validation step in `ShieldedTRC20ParametersBuilder`/`Wallet` that checks the supplied `anchor` against a known valid merkle root (e.g., current or a bounded window of historical shielded-pool roots) before invoking `generateSpendProof()`, rejecting requests with unrecognized anchors immediately.
- Apply a low, endpoint-specific `IPQPSRateLimiterAdapter` or `GlobalPreemptibleAdapter` (concurrency cap) to `CreateShieldedContractParametersServlet`/`CreateShieldedContractParametersWithoutAskServlet` in `reference.conf`, reflecting the true CPU cost of proof generation rather than relying on the generic 1000 QPS default.
- Consider moving/limiting this proof-generation service off default-enabled full-node HTTP APIs, or requiring proof-of-work/authentication for expensive shielded-parameter generation endpoints.

Expected: the server invokes `generateSpendProof()` and runs the full native `librustzcashSaplingSpendProof` computation, only returning `ZksnarkException("Spend proof failed")` after full computation — measurable via response latency comparable to a legitimate proof generation (hundreds of ms), demonstrating that CPU is fully consumed per rejected request. Sending many concurrent such requests (up to the default 1000 QPS ceiling) demonstrates sustained CPU saturation without triggering rate-limiter rejection until well beyond the point where legitimate throughput would already be degraded.

  private byte[] formatPath(byte[] path, long position) throws ZksnarkException {
    if (path.length != MERKLE_TREE_PATH_LENGTH) {
      throw new ZksnarkException(MERKLE_TREE_PATH_LENGTH_ERROR);
    }

    byte[] result = new byte[1065];
    result[0] = 0x20;
    for (int i = 0; i < 32; i++) {
      result[1 + i * 33] = 0x20;
      System.arraycopy(path, i * 32, result, 2 + i * 33, 32);
    }

    byte[] positionBytes = ByteArray.fromLong(position);
    ZksnarkUtils.sort(positionBytes);
    System.arraycopy(positionBytes, 0, result, 1057, 8);
    return result;
  }

  private SpendDescriptionCapsule generateSpendProof(SpendDescriptionInfo spend,
      long ctx) throws ZksnarkException {
    byte[] cm = spend.note.cm();
    // check if ak exists
    byte[] ak;
    byte[] nf;
    byte[] nsk;
    byte[] path = formatPath(spend.path, spend.position);

    if (!ArrayUtils.isEmpty(spend.ak)) {
      ak = spend.ak;
      nf = spend.note.nullifier(ak, JLibrustzcash.librustzcashNskToNk(spend.nsk), spend.position);
      nsk = spend.nsk;
    } else {
      ak = spend.expsk.fullViewingKey().getAk();
      nf = spend.note.nullifier(spend.expsk.fullViewingKey(), spend.position);
      nsk = spend.expsk.getNsk();
    }

    if (ByteArray.isEmpty(cm) || ByteArray.isEmpty(nf)) {
      throw new ZksnarkException("Spend is invalid");
    }

    byte[] cv = new byte[32];
    byte[] rk = new byte[32];
    byte[] zkproof = new byte[192];
    if (!JLibrustzcash.librustzcashSaplingSpendProof(
        new LibrustzcashParam.SpendProofParams(ctx,
            ak,
            nsk,
            spend.note.getD().getData(),
            spend.note.getRcm(),
            spend.alpha,
            spend.note.getValue(),
            spend.anchor,
            path,
            cv,
            rk,
            zkproof))) {
      throw new ZksnarkException("Spend proof failed");
    }

    PaymentAddress paymentAddress = KeyIo.decodePaymentAddress(note.getPaymentAddress());
