### Title
Unbounded growth of `SecondaryIndex::reverse_index` per-account `Vec<Pubkey>` via repeated live mint/owner rewrites - ([File: accounts-db/src/accounts_index/secondary.rs])

### Summary
`SecondaryIndex::insert` (secondary.rs:133-171) appends a new outer key to the `reverse_index` entry's `Vec<Pubkey>` whenever an spl-token account's mint (or owner) field takes on a value it has not held before, and this Vec is only pruned when the account key is fully purged from the primary index via `purge_secondary_indexes_by_inner_key_if`/`remove_by_inner_key_if`. An unprivileged user who repeatedly closes/reinitializes (or otherwise rewrites) a single spl-token account they control with a new mint each time, while keeping the pubkey alive in the primary index, causes this Vec to grow linearly with the number of distinct historical values (K), not with the number of currently-live secondary-index entries.

### Finding Description
`update_secondary_indexes` (accounts_index.rs:614-660) calls `update_spl_token_secondary_indexes` (accounts_index.rs:557-580) for every stored account when `AccountIndex::SplTokenMint`/`SplTokenOwner` is enabled, unconditionally calling `self.spl_token_mint_index.insert(mint_key, pubkey)` on every store — there is no comparison against the account's previous mint/owner and no removal of the stale mapping before inserting the new one.

Inside `SecondaryIndex::insert` (secondary.rs:133-171), the reverse-index entry for the account (`inner_key`) is a `Vec<Pubkey>` of outer keys (mint/owner values) the account has ever mapped to: [1](#0-0) 
A new value is pushed only if not already present (`outer_keys.contains(key)`), but since the attacker writes a *new, never-before-seen* mint pubkey each round, this check never de-duplicates and the Vec grows by one element per distinct mint value written.

Removal of these stale entries only happens through `remove_by_inner_key_if`/`purge_secondary_indexes_by_inner_key_if`, which is only invoked when the account key is entirely removed from the primary index (`dead_keys`) and is not cache-resident: [2](#0-1) 
As long as the account key stays alive in the primary index (e.g., the attacker keeps recreating/rewriting it before it fully dies, or simply never lets it reach zero lamports past all roots while cache-resident), none of the stale mint mappings are pruned. This is confirmed directly by the existing unit test `run_test_secondary_indexes_same_slot_and_forks`, whose comment states explicitly that after `clean_rooted_entries`, "even though the account with secondary_key1 was outdated by the update in the later slot, the primary account key is still alive, so both secondary keys will still be kept alive": [3](#0-2) 

This directly validates the concern in the comment at secondary.rs:57-60, which explicitly assumes such outer-key changes are "rare": [4](#0-3) 
An attacker can defeat this assumption by deliberately forcing many outer-key changes (e.g. via repeated `CloseAccount` + `InitializeAccount` cycles on a self-owned spl-token account keypair with a fresh mint each cycle), which is entirely within normal, unprivileged token-account lifecycle operations (create/close/reopen/rewrite accounts they pay for).

### Impact Explanation
This is a memory/storage disproportionate-cost issue: for O(K) cheap transactions (each just a `CloseAccount`+`InitializeAccount`/rent-exempt account rewrite, costing rent + tx fee, largely refunded on close), the attacker forces the node to permanently retain O(K) `Pubkey` (32 bytes) entries in the `reverse_index` Vec for that single account, even though only one mint/owner mapping is ever "live" for lookups. This applies to any RPC/validator node running with `AccountIndex::SplTokenMint` or `SplTokenOwner` enabled — a resource-exhaustion / disproportionate storage cost vector rather than balance/consensus corruption.

### Likelihood Explanation
Preconditions: node must have `AccountIndex::SplTokenMint` or `SplTokenOwner` enabled (an opt-in indexing feature used by many RPC nodes to serve `getTokenAccountsByOwner`/`getProgramAccounts` filters). Given that, the attack requires only standard, unprivileged token-account operations repeated many times, is fully automatable, and is confirmed by the codebase's own comments and test behavior (not a hypothetical race). It is highly feasible and fully repeatable, bounded only by the attacker's willingness to pay transaction fees.

### Recommendation
Before pushing a new outer key into the reverse-index Vec, compare against and evict the account's previous mint/owner mapping (i.e., make `update_spl_token_secondary_indexes` diff against a cached "current mint/owner" for the pubkey, or truncate the reverse-index Vec's oldest entries eagerly), or cap the Vec size, or convert it to a small fixed-size structure that overwrites in place instead of accumulating history indefinitely for a still-alive key.

### Proof of Concept
Extend `run_test_secondary_indexes_same_slot_and_forks` into an invariant test in `accounts-db/src/accounts_index.rs`:
```rust
#[test]
fn test_reverse_index_unbounded_growth_for_live_account() {
    let (key_start, key_end, secondary_indexes) = create_spl_token_mint_secondary_index_state();
    let index = AccountsIndex::<bool, bool>::default_for_tests();
    let account_key = Pubkey::new_unique();
    const K: usize = 10_000;

    for slot in 0..K as u64 {
        index.upsert(slot, slot, &account_key, true, &mut ReclaimsSlotList::new(), UPSERT_RECLAIM_TEST_DEFAULT);
        let mint_key = Pubkey::new_unique(); // distinct mint each round
        let mut account_data = make_empty_token_account_data();
        account_data[key_start..key_end].clone_from_slice(&mint_key.to_bytes());
        index.update_secondary_indexes(
            &account_key,
            &AccountSharedData::create_from_existing_shared_data(
                0, Arc::new(account_data), spl_generic_token::token::id(), false, 0,
            ),
            &secondary_indexes,
        );
        // account key remains "alive" in the primary index throughout — never purged
    }

    let reverse_len = index
        .spl_token_mint_index
        .reverse_index
        .get(&account_key)
        .unwrap()
        .value()
        .read()
        .unwrap()
        .len();

    // Expected (bug): reverse_len == K (unbounded growth)
    // Desired invariant after fix: reverse_len should stay bounded (e.g., 1, or a small constant)
    assert!(reverse_len < 100, "reverse_index Vec grew unbounded: {reverse_len} entries for K={K} mutations");
}
```
Running this against current code demonstrates `reverse_len == K`, violating the desired bounded-memory invariant.
