### Title
Exchange pool token balance can be withdrawn down to dust levels, breaking bancor-style pricing invariants - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The Sherlock ELFi finding (M-21) shows that a protocol enforces a minimum margin on position *creation* but has no check preventing a position from being reduced to a dust amount below that minimum, leading to rounding-error exploitation in fee/PnL math. The same bug class exists in java-tron's TRC10 bancor-style `Exchange` (the on-chain AMM pair used by `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`): the withdraw path only rejects a token balance of exactly `0`, never enforcing that reserves stay above a meaningful minimum, so a pool's reserves can be withdrawn down to `1` unit.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` only checks reserves for being exactly zero: [1](#0-0) 
There is no lower-bound check analogous to ELFi's `minOrderMarginUSD`; the only other guard is the "Not precise enough" rounding-tolerance check on the *withdrawal calculation itself*, which does not protect the *remaining* reserve size: [2](#0-1) 

Once a pool's `firstTokenBalance`/`secondTokenBalance` is reduced to a dust value (e.g. `1`), the bancor-formula pricing used by `ExchangeCapsule.transaction()` — which computes swaps via `ExchangeProcessor`/`SafeExchangeProcessor` using `double`/`BigDecimal` power operations against these tiny reserves — becomes extremely sensitive to rounding: [3](#0-2) [4](#0-3) 

With near-zero reserves, a subsequent `ExchangeTransactionActuator` trade of even a small `sellTokenQuantity` can produce wildly disproportionate `anotherTokenQuant` output (or, conversely, force rounding to `0`), exactly mirroring the ELFi issue where a position reduced below the minimum margin causes disproportionate/incorrect fee and PnL computation. There is no analogous "remaining balance must exceed X" check comparable to ELFi's recommended fix.

### Impact Explanation
This is an accounting-integrity issue in a production, unprivileged, user-reachable code path (any account holding exchange-pool tokens can call `ExchangeWithdrawContract`). Driving a pool to dust reserves lets an attacker (or the pool creator) manipulate the effective exchange rate to extreme, rounding-dominated values, enabling extraction of value from subsequent traders via `ExchangeTransactionActuator`/`ExchangeInjectActuator`, or causing swaps to always round to `0` output while still consuming the trader's input token (loss of funds). This satisfies the "underpriced public work"/accounting-divergence bar because the AMM invariant (proportional pricing) breaks down once reserves are dust-sized, and nothing in the actuator prevents reaching that state.

### Likelihood Explanation
Likelihood is moderate: it requires a pool creator/majority LP to withdraw almost all liquidity from one side of a pool, which is a normal, unprivileged operation (`ExchangeWithdrawContract`) requiring no special permission — only ownership of exchange-pool balance. TRC10 exchanges are a legacy but still-active on-chain feature, and no governance/committee gate exists on withdraw amount (unlike `ExchangeInjectActuator`/`ExchangeTransactionActuator`, which are gated behind `dynamicStore.supportAllowMarketTransaction()`-style checks only for the newer Market feature, not for the older token Exchange).

### Recommendation
Add a minimum-reserve check in `ExchangeWithdrawActuator.doValidate()` analogous to ELFi's suggested fix: require that both `newTokenBalance` and `newAnotherTokenBalance` (post-withdrawal) remain above a protocol-defined minimum exchange balance (mirroring the existing `getExchangeBalanceLimit()` upper bound used in `ExchangeInjectActuator`/`ExchangeTransactionActuator`), preventing pools from being driven into a dust/rounding-dominated state.

### Proof of Concept
1. Create an `Exchange` pool with `firstTokenBalance = X`, `secondTokenBalance = Y` via `ExchangeCreateContract`.
2. As the pool owner (or any large LP-equivalent balance holder), repeatedly call `ExchangeWithdrawContract` for `tokenQuant` close to `firstTokenBalance - 1`, which passes validation in `ExchangeWithdrawActuator.doValidate()` since only `firstTokenBalance == 0` is rejected: [1](#0-0) 
3. After the withdrawal, `firstTokenBalance` is left at `1` (dust), while `secondTokenBalance` may still be large.
4. Any subsequent `ExchangeTransactionContract` swap against this pool goes through `ExchangeCapsule.transaction()` using the now-degenerate reserve ratio: [5](#0-4)  producing an output quantity dominated by `double`/rounding behavior in `ExchangeProcessor.exchange()` rather than the intended proportional bancor price, letting the withdrawer's counterpart trades extract disproportionate value or causing legitimate traders' swaps to round to zero output while their input is still consumed.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
