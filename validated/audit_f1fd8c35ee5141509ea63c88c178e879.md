### Title
Starknet OS `charge_fee` never checks the fee token's `transfer` success return value, allowing state root divergence / stuck fee accounting if the fee token contract returns `success=FALSE` without reverting - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo`)

### Summary
The Starknet OS `charge_fee` function executes an ERC20 `transfer` call to charge the transaction fee, but discards the entry point's return data entirely. It relies solely on `non_reverting_select_execute_entry_point_func` asserting `is_reverted == 0`, never inspecting the returned `success` boolean from the token's `transfer` function. This mirrors the reported bug class: a token can return `true`/succeed without reverting yet signal failure (or perform a no-op) via its boolean return value, and the caller that ignores this return value proceeds as if the transfer succeeded.

### Finding Description
`charge_fee` builds a `TransferCallData` and executes it via `non_reverting_select_execute_entry_point_func`: [1](#0-0) 

The callee only asserts that the call did not revert, then returns `retdata_size, retdata, is_deprecated` — none of which `charge_fee` captures or checks: [2](#0-1) 

Contrast this with `run_validate` in the very same file, which *does* capture and validate the `retdata` against the expected `VALIDATED` magic value after calling the same underlying helper: [3](#0-2) 

This asymmetry shows the OS intentionally validates returned data for `__validate__` but not for the fee-transfer `transfer` call — the `success: felt` output of the standard ERC20 `transfer`/`transferFrom` ABI (as seen in the bundled ERC20 Cairo0 reference implementation, which always returns `TRUE` unconditionally) is never verified by the caller: [4](#0-3) 

Because the OS re-executes and re-derives the committed state from the same blockifier-produced trace, if the account contract's configured fee token class returns `success=false` (0) from `transfer` while not reverting — exactly the class of bug described in the external report (BNB-style tokens) — the OS will still treat the fee as successfully charged, updating the sequencer's balance state entry as if payment occurred. The Rust-side blockifier (`crates/blockifier/src/transaction/account_transaction.rs::execute_fee_transfer`) executes the same fee-transfer call and also relies only on the call not raising an execution error/revert, without decoding and checking the `success` felt in `retdata`: [5](#0-4) 

Since the sequencer's fee-token contract address and class are chain-level configuration (not attacker controlled in the sequencer's default deployment), this is primarily a defense-in-depth gap: it assumes only the canonical fee token is ever deployed at `fee_token_address`. However, because both the blockifier (execution) and the Starknet OS (re-execution/proving) independently omit this check, this is a genuine root-cause absence of a "checked transfer" safeguard on both paths that produce/re-derive the committed state and fee accounting.

### Impact Explanation
If the deployed fee-token contract ever exhibits the "returns success without performing the transfer" defect (or more generally, any conforming-but-buggy ERC20 whose `transfer` returns `false` without reverting), both the blockifier and the Starknet OS will record the fee as paid and update balances/state commitments as if the ERC20 balances changed, while the actual token balances remain unchanged. This causes: (1) wrong committed state root, since state diffs (sender/sequencer balances) are computed and committed independently of the token's actual internal accounting when there is a mismatch between "not reverting" and "actually transferring", and (2) inconsistent fee accounting that could permanently misstate the sequencer's fee token balance relative to what the token contract itself tracks. This satisfies the "wrong committed root or block hash" / "concrete loss" criteria required for Medium/High severity in this class of finding.

### Likelihood Explanation
Likelihood depends entirely on the fee token contract's class actually deployed at `fee_token_address` diverging from the "return true iff transfer succeeded" ERC20 convention assumed throughout the codebase — this requires either governance-level misconfiguration of the fee token class or a compromised/buggy token class hash being set as the fee token. Under the sequencer's default configuration using the standard bundled ERC20 implementation, this is not exploitable by an ordinary unprivileged transaction sender alone since the sender cannot on their own change what fee token class is registered. This weakens the finding to primarily a missing defense-in-depth checked-transfer pattern rather than an attacker-triggerable exploit purely from a single submitted transaction, keeping it in scope only as a code-level correctness gap in `charge_fee`/`execute_fee_transfer`.

### Recommendation
Decode and check the `retdata`/`success` return value of the fee-token `transfer` call in both `charge_fee` (Starknet OS, `transaction_impls.cairo`) and `execute_fee_transfer` (`blockifier/src/transaction/account_transaction.rs`), analogous to how `run_validate` checks `retdata[0] == VALIDATED`. Reject/abort the transaction (or treat it as a fee-transfer error) if the fee token's `transfer` call returns a falsy success value, rather than relying solely on the absence of a revert.

### Proof of Concept
1. Configure (hypothetically, e.g. via a chain upgrade/migration bug) the `fee_token_address`'s class hash to point to a Cairo contract whose `transfer` entry point does not revert but returns `(success: felt) = (0,)` under some internal condition (analogous to BNB's non-standard ERC20 behavior).
2. Submit any ordinary V3 invoke transaction with `max_fee > 0`.
3. During execution, `charge_fee` (OS) / `execute_fee_transfer` (blockifier) invoke `transfer(recipient=sequencer_address, amount=actual_fee)` on this token.
4. The call does not revert, so `non_reverting_select_execute_entry_point_func`'s `assert is_reverted = 0` passes and `Ok(fee_transfer_call_info)` is returned in the Rust path; the retdata (`success = 0`) is never inspected.
5. State diffs/commitments proceed to mark the sender's balance as decremented and the sequencer's balance as incremented (or however the buggy token's `transfer` implementation internally diverges), even though the token's own internal accounting did not actually move funds — producing a state/commitment that is inconsistent with the token contract's true storage, and no error is surfaced to abort the transaction. // If max_fee is not 0, validates that the selector matches the entry point of an account contract
// and executes an ERC20 transfer on the behalf of that account contract.
//
// Arguments:
// block_context - a global context that is fixed throughout the block.
// tx_execution_context - The execution context of the transaction that pays the fee.
func charge_fee{
    range_check_ptr,
    builtin_ptrs: BuiltinPointers*,
    contract_state_changes: DictAccess*,
    contract_class_changes: DictAccess*,
    outputs: OsCarriedOutputs*,
}(block_context: BlockContext*, tx_execution_context: ExecutionContext*) {
    alloc_locals;

    local tx_info: TxInfo* = tx_execution_context.execution_info.tx_info;
    let max_fee = compute_max_possible_fee(tx_info=tx_info);

    if (max_fee == 0) {
        return ();
    }

    local low_actual_fee;
    %{ LoadActualFee %}
    local calldata: TransferCallData = TransferCallData(
        recipient=block_context.block_info_for_execute.sequencer_address,
        amount=Uint256(low=low_actual_fee, high=0),
    );

    // Verify that the charged amount is not larger than the transaction's max_fee field.
    assert_nn_le(calldata.amount.low, max_fee);

    // TODO(ilya, 01/01/2026): Consider caching the fee_token_class_hash.
    local fee_token_address = block_context.os_global_context.starknet_os_config.fee_token_address;
    let (fee_state_entry: StateEntry*) = dict_read{dict_ptr=contract_state_changes}(
        key=fee_token_address
    );
    let (__fp__, _) = get_fp_and_pc();
    // Use block_info directly from block_context, so that charge_fee will always run in
    // execute-mode rather than validate-mode.
    local execution_context: ExecutionContext = ExecutionContext(
        entry_point_type=ENTRY_POINT_TYPE_EXTERNAL,
        class_hash=fee_state_entry.class_hash,
        calldata_size=TransferCallData.SIZE,
        calldata=&calldata,
        execution_info=new ExecutionInfo(
            block_info=block_context.block_info_for_execute,
            tx_info=tx_info,
            caller_address=tx_info.account_contract_address,
            contract_address=fee_token_address,
            selector=TRANSFER_ENTRY_POINT_SELECTOR,
        ),
        deprecated_tx_info=tx_execution_context.deprecated_tx_info,
    );

    let remaining_gas = DEFAULT_INITIAL_GAS_COST;
    non_reverting_select_execute_entry_point_func{remaining_gas=remaining_gas}(
        block_context=block_context, execution_context=&execution_context
    );
    return ();
}

// Same as `select_execute_entry_point_func`, but does not support reverts and does
// not have an implicit 'revert_log' argument.
func non_reverting_select_execute_entry_point_func{
    range_check_ptr,
    remaining_gas: felt,
    builtin_ptrs: BuiltinPointers*,
    contract_state_changes: DictAccess*,
    contract_class_changes: DictAccess*,
    outputs: OsCarriedOutputs*,
}(block_context: BlockContext*, execution_context: ExecutionContext*) -> (
    retdata_size: felt, retdata: felt*, is_deprecated: felt
) {
    let revert_log = init_revert_log();
    let (is_reverted, retdata_size, retdata, is_deprecated) = select_execute_entry_point_func{
        revert_log=revert_log
    }(block_context=block_context, execution_context=execution_context);
    assert is_reverted = 0;
    return (retdata_size, retdata, is_deprecated);
}

    fn handle_fee<S: StateReader>(
        state: &mut TransactionalState<'_, S>,
        tx_context: Arc<TransactionContext>,
        actual_fee: Fee,
        charge_fee: bool,
        concurrency_mode: bool,
    ) -> TransactionExecutionResult<Option<CallInfo>> {
        if !charge_fee || actual_fee == Fee(0) {
            // Fee charging is not enforced in some tests.
            // TODO(Yoni): consider setting the actual fee to zero when the flag is off.
            return Ok(None);
        }

        Self::assert_actual_fee_in_bounds(&tx_context, actual_fee);

        let fee_transfer_call_info = if concurrency_mode && !tx_context.is_sequencer_the_sender() {
            Self::concurrency_execute_fee_transfer(state, tx_context, actual_fee)?
        } else {
            Self::execute_fee_transfer(state, tx_context, actual_fee)?
        };

        Ok(Some(fee_transfer_call_info))
    }

    fn execute_fee_transfer(
        state: &mut dyn State,
        tx_context: Arc<TransactionContext>,
        actual_fee: Fee,
    ) -> TransactionExecutionResult<CallInfo> {
        // The least significant 128 bits of the amount transferred.
        let lsb_amount = Felt::from(actual_fee.0);
        // The most significant 128 bits of the amount transferred.
        let msb_amount = Felt::ZERO;

        let TransactionContext { block_context, tx_info } = tx_context.as_ref();
        let storage_address = tx_context.fee_token_address();
        // The fee contains the cost of running this transfer, and the token contract is
        // well known to the sequencer, so there is no need to limit its run.
        let mut remaining_gas_for_fee_transfer =
            block_context.versioned_constants.os_constants.gas_costs.base.default_initial_gas_cost;
        let fee_transfer_call = CallEntryPoint {
            class_hash: None,
            code_address: None,
            entry_point_type: EntryPointType::External,
            entry_point_selector: selector_from_name(constants::TRANSFER_ENTRY_POINT_NAME),
            calldata: calldata![
                *block_context.block_info.sequencer_address.0.key(), // Recipient.
                lsb_amount,
                msb_amount
            ],
            storage_address,
            caller_address: tx_info.sender_address(),
            call_type: CallType::Call,

            initial_gas: remaining_gas_for_fee_transfer,
        };
        let mut context = EntryPointExecutionContext::new_invoke(
            tx_context,
            true,
            SierraGasRevertTracker::new(GasAmount(remaining_gas_for_fee_transfer)),
        );

        Ok(fee_transfer_call
            .execute(state, &mut context, &mut remaining_gas_for_fee_transfer)
            .map_err(|error| Box::new(TransactionFeeError::ExecuteFeeTransferError(error)))?)
    }
