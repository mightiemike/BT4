### Title
`TransactionOutput::ensure_match_transaction_info` skips state-checkpoint hash comparison, letting replay-verify accept a diverged state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
Reducing the external Notional bug (`claimAccountRewards` is missing a check on the untrusted `account` parameter, so it silently accepts an address it should never bind rewards to) to a state-integrity invariant: *a comparator that is supposed to bind computed output to an authenticated reference must check every field of that reference, or the "authenticated" check becomes a false positive.* In Aptos, `TransactionOutput::ensure_match_transaction_info` is exactly such a comparator: it is used by replay/verify tooling to bind locally re-executed VM output to the trusted, backed-up `TransactionInfo` (the object committed into the transaction accumulator and signed via `LedgerInfoWithSignatures`). The function omits the `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields from the equality check, exactly analogous to the missing `account` check — the caller assumes full validation, but a wrong or divergent value passes anyway.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates a re-executed `TransactionOutput` against a trusted `TransactionInfo` by checking `status`, `gas_used`, `write_set_hash`, and `event_root_hash`. It explicitly does **not** check the state-checkpoint-related hashes, and the code says so directly: [2](#0-1) 

This function is the sole verification gate used by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes archived transactions with the VM and compares the result to the `expected_txn_infos` pulled from backup/ledger data: [3](#0-2) 

The `expected_txn_infos` here are `TransactionInfo`s recovered from the authenticated backup stream (ultimately anchored to a signed `LedgerInfoWithSignatures` via the transaction accumulator), i.e., they play the role of a trusted, proof-bound reference — the analog of the `account` parameter in the original bug, which the caller is trusted to have validated but doesn't. Because `state_checkpoint_hash` (the JMT state root committed for that transaction) is never compared, a local execution that produces a *different* state root than the one actually accepted on-chain will still pass `ensure_match_transaction_info` as long as status/gas/write-set/events match. Note that `write_set_hash` matching does not imply `state_checkpoint_hash` matching: the state-checkpoint hash is a derived Merkle root over the *entire* state tree at that version (via `DoStateCheckpoint`, see [4](#0-3) ), which depends on prior accumulated state, hot-state promotion logic, and (when the `trading-native`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature is enabled) the separate position-state tree — none of which are exercised by comparing a single transaction's write set hash.

### Impact Explanation
This falls squarely in the "Hard-fork-only divergence during commit, replay, restore, or proof verification" bucket. `replay_on_archive` (the `db-tool replay-verify` subcommand) is the primary tool used to detect state divergence between different execution engine versions/binaries against historical, signed chain data — it is explicitly relied on to catch consensus-breaking bugs before they reach mainnet or to certify that an archive node's data is consistent with the authenticated chain history. Because the comparator silently ignores the state-checkpoint hash, a state-root-diverging bug (e.g., in the VM, in `DoStateCheckpoint`'s SMT/JMT update logic, or in hot-state/position-state root computation) would not be flagged by this tool even though it walks every transaction and its "expected" `TransactionInfo` from trusted backup data. This can let a genuine ledger-state divergence go undetected, defeating the authenticated verification guarantee the tool is supposed to provide, with high severity given it's the last line of defense for hard-fork-class state-commitment bugs.

### Likelihood Explanation
Likelihood of the check being exercised is high: `replay_on_archive` is intended to be run over long transaction ranges specifically to catch state divergence, so any real divergence in state-checkpoint hash computation between the archived (canonical) execution and a differently-behaving execution/build would go straight through this gap. The gap is acknowledged in-code via the `TODO(trading-native)` comment, confirming maintainers are aware the comparator is incomplete, but as shipped it is unconditionally missing the check for both the pre-existing `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields (not just the newer `position_state_checkpoint_hash`).

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash()`, and where applicable `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, between `self`-derived expectations (recomputed via the same checkpoint pipeline, e.g. `DoStateCheckpoint`) and `txn_info`, failing loudly on mismatch, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or shipping any release that relies on `replay_on_archive` for state-root verification.

### Proof of Concept
No standalone PoC is provided; the finding is a direct code read of the comparator and its caller. The gap is self-documented by the maintainers' own `TODO(trading-native)` comment at [2](#0-1) , and the call site confirming this is the only integrity gate for replay-verify is at [5](#0-4) . I was not able to fully trace every downstream consumer of `TransactionInfo` state-checkpoint hashes (e.g., whether state-sync's chunk executor independently re-validates these hashes elsewhere, which would reduce blast radius to `db-tool` only) within the available search budget — this should be confirmed before treating the impact as chain-wide rather than tooling-scoped.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
