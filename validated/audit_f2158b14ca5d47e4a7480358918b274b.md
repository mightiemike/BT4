### Title
Downward-biased truncation in `ExchangeProcessor` Bancor-formula swap math reduces tokens received - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
TRON's TRC10↔TRX/TRC10↔TRC10 exchange (`ExchangeTransactionActuator`) uses a Bancor-style relay-token formula implemented in `ExchangeProcessor`. Both intermediate steps of the formula truncate their floating-point result toward zero via a `(long)` cast, mirroring the exact bug class described in the Fei Protocol report: intermediate truncation performed before the final result is computed, rather than truncating only once at the very end, biases the output downward and away from the mathematically correct value. This causes traders to systematically receive fewer tokens than they are owed on every default-path swap.

### Finding Description
`ExchangeProcessor.exchange()` computes the amount of the "other" token a user receives in two truncating steps: [1](#0-0) 

`exchangeToSupply` computes `issuedSupply` as a `double` using `Maths.pow(...)` and then truncates it to a `long` with `(long) issuedSupply`, discarding the fractional relay-token amount. This truncated (already-lossy) `long` value is then fed as `supplyQuant` into `exchangeFromSupply`, which again performs a `pow` on a ratio built from this truncated integer and truncates its own output to `long`. Because the second exponentiation operates on an input that has already lost precision (and is truncated toward zero rather than rounded), the compounded rounding always pushes the final `exchangeBalance` below the true value — the same "truncate early, then raise to a power" anti-pattern that caused `twoThirdsRoot`/`threeHalfsRoot` to under-report in the Fei report, just applied to a Bancor curve instead of a bonding curve.

This is the default/non-hardened code path taken from `ExchangeCapsule.transaction()`: [2](#0-1) 

unless the chain has activated `allowHardenExchangeCalculation` (a committee-controlled proposal parameter), in which case `SafeExchangeProcessor` is used instead, which performs the division/power arithmetic with `BigDecimal` and defers truncation (`setScale(0, RoundingMode.DOWN)`) to the very last step: [3](#0-2) 

The existence of the "hardened" replacement, and the actual test asserting the two paths diverge, is direct evidence that the default `ExchangeProcessor` path produces materially different (and biased) output: [4](#0-3) 

The `Assert.assertNotEquals(anotherTokenQuant, result)` at line 278 confirms the two implementations diverge on real numeric ranges used by the exchange, and `safeResult == result` confirms `result` (from `useStrictMath=true` `ExchangeProcessor`) still differs from the true/hardened value that only `SafeExchangeProcessor` reaches correctly — while the fully non-strict-math legacy path (`anotherTokenQuant`, the historical default before `allowStrictMath` was introduced) diverges even further.

### Impact Explanation
Any unprivileged user performing an `ExchangeTransactionContract` swap (or the underlying Bancor-relay math also invoked implicitly through `ExchangeCapsule.transaction`) receives an `anotherTokenQuant` that is systematically less than the mathematically correct amount, because both `exchangeToSupply` and `exchangeFromSupply` truncate downward at intermediate steps rather than deferring truncation to the final output. This is a concrete accounting/settlement impact: value is silently lost from every trader's swap output on the default code path, and the magnitude grows with quant size and imbalance, exactly as described for the `twoThirdsRoot`/`threeHalfsRoot` case in the source report. Because this affects the on-chain, permissionless TRC10 exchange used by ordinary accounts (not a privileged/internal-only path), it is an in-scope, unprivileged-user-facing settlement bug.

### Likelihood Explanation
The vulnerable `ExchangeProcessor` path is the current default for all exchanges unless the `allowHardenExchangeCalculation` proposal has been activated by the committee; every `ExchangeTransactionContract` executed before that activation (and on any network where it remains disabled) takes this path automatically on every trade, with no attacker action required — the bias occurs unconditionally as part of normal swap execution.

### Recommendation
Refactor `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` to defer all truncation to the final result, following the same pattern already implemented in `SafeExchangeProcessor` (perform the power/ratio arithmetic in a higher-precision, non-lossy type such as `BigDecimal`, and only truncate once, at the very end, ideally with `RoundingMode.HALF_UP` rather than `DOWN` to avoid systematic downward bias). Consider making `SafeExchangeProcessor`/hardened math the default and unconditional behavior rather than a proposal-gated opt-in, since the existing behavior causes cumulative, uncorrectable value loss for users on every trade.

### Proof of Concept
Using the `ExchangeProcessorTest.testStrictMath` data set already present in the codebase, e.g. `{4732214L, 2202692725330L, 29218L}`:
1. Run `new ExchangeProcessor(supply, false).exchange(4732214L, 2202692725330L, 29218L)` and `new ExchangeProcessor(supply, true).exchange(4732214L, 2202692725330L, 29218L)`.
2. Compare against `SafeExchangeProcessor.INSTANCE.exchange(4732214L, 2202692725330L, 29218L)`.
3. As asserted at [5](#0-4)  the non-hardened result differs from the true (hardened) value across the full data set, demonstrating that live on-chain swaps using the default `ExchangeProcessor` under-deliver tokens relative to the mathematically correct Bancor-formula output.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
