### Title
Gas fee accounting truncates to zero when the EVM base fee is a fractional `upc`, allowing free UEA payload execution - ([File: x/uexecutor/keeper/fees.go])

### Summary
The Sherlock report describes a fee-accounting fork mismatch: SolidlyV3 stopped updating fee state that UniswapV3 (and the AMO integration built on top of it) assumed would always be tracked, so fees became silently uncollectable. The Push Chain analog is a fee-accounting assumption baked into `CalculateGasCost` in `x/uexecutor/keeper/fees.go`: the code assumes the on-chain EIP-1559 base fee, once unwrapped from its 18-decimal `LegacyDec` representation, is "always a whole number of upc." When it is not, integer division truncates the effective gas price to zero, so `DeductGasFeesFromReceipt` silently skips billing while the corresponding UEA payload execution still commits — the protocol pays for real EVM execution but never charges the account that consumed it, exactly the "fees not updated / permanently uncollected" pattern from the source report.

### Finding Description
`CalculateGasCost` receives `baseFee sdkmath.LegacyDec` from `k.feemarketKeeper.GetBaseFee(sdkCtx)` and does: [1](#0-0) 

The comment explicitly assumes "the base fee is always a whole number of upc — no fractional upc exists," but `x/feemarket`'s EIP-1559 base fee is a dynamically adjusted `LegacyDec` value (it moves up/down by a fraction of itself every block based on gas utilization). There is no invariant anywhere in this code path forcing the base fee to remain ≥ `1e18` (i.e. ≥ 1 whole `upc`) at all times — under low network utilization the fee-market algorithm can legitimately push the base fee below one whole `upc` unit (e.g. to `0.4 upc`, represented internally as `4e17`). In that case:

`baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` truncates `4e17 / 1e18` to `0` in Go's integer big.Int division.

This zero then flows straight through: [2](#0-1) 

`gasCost` becomes `0`, and in `DeductGasFeesFromReceipt`: [3](#0-2) 

the function returns `nil` (no error) without deducting anything. Meanwhile the caller in `ExecutePayloadV2` treats a `nil` fee error as success and commits the cache: [4](#0-3) 

The `CallUEAExecutePayload` EVM state changes (the actual UEA execution, which the protocol paid EVM gas for as a `DerivedEVMCall`) are written via `writeCache()`, but `DeductAndBurnFees` never ran because `gasCost.Sign() <= 0` short-circuited it. The same pattern exists in the smart-contract inbound path (`ExecuteInboundFundsAndPayload`), which also calls `DeductGasFeesFromReceipt` after a `CacheContext`-wrapped EVM call and commits on any nil fee error: [5](#0-4) 

### Impact Explanation
This breaks the gas-fee accounting invariant that every unit of EVM execution performed on behalf of a UEA/user is billed back to that user's `upc` balance. It is reachable via ordinary user activity — any user submitting `MsgExecutePayload` (or `MsgVoteInbound`-driven CEA/UEA payload execution) during a period when the dynamically-computed base fee has drifted below one whole `upc` gets full, real EVM execution (arbitrary calldata through their UEA) for zero cost, permanently uncollected — the same "fees stuck/uncollectable forever" outcome as the source finding, except here it manifests as the protocol absorbing real execution cost instead of a Pool retaining LP fees. Repeated abuse during such periods amounts to unbounded free compute/state-transition execution paid for by the protocol module account (which funds the `DerivedEVMCall` gas), a direct loss to protocol-controlled value.

### Likelihood Explanation
Likelihood depends entirely on whether the deployed `x/feemarket` parameters (`min_gas_price`, initial base fee, elasticity multiplier) can ever let the base fee decay below `1e18` (1 whole `upc`) during sustained low utilization. If the `upc` base denomination is scaled such that "normal" operating base fees are always many orders of magnitude above `1e18`, this is unreachable in practice; if `upc` is the atomic unit (18 decimals, akin to wei) and the network's minimum/floor base fee parameter is not hard-pinned above `1e18`, this is a straightforward, unprivileged, deterministic path to fee-free execution triggerable by any user without needing malicious validators, relayers, or TSS participants. I could not verify the deployed `feemarket` genesis/param values (`MinGasPrice`, base fee floor) in the indexed files, so I cannot confirm without further investigation whether the parameter configuration already prevents the base fee from ever dropping under `1e18`.

### Recommendation
Do not divide out the 18-decimal precision before computing the gas cost. Perform the multiplication (`baseFee (LegacyDec) * gasUsed`) in the full-precision `LegacyDec`/`Int` domain and only convert to an integer `upc` amount at the very end (rounding up, not truncating), so fractional-`upc` base fees still produce a non-zero, correctly-rounded charge. Additionally, add an explicit invariant check/floor so that `CalculateGasCost` never silently returns `gasCost.Sign() <= 0` for `gasUsed > 0`, treating that as an error to be surfaced/aborted rather than a silent no-op that lets `ExecutePayloadV2`/`ExecuteInboundFundsAndPayload` commit their cache.

### Proof of Concept
Conceptual PoC (not run against a live node, since this requires control of the on-chain base fee state which I could not execute in this environment):
1. Let the `x/feemarket` base fee decay under sustained low block utilization until `GetBaseFee(ctx)` returns a `LegacyDec` value less than `1e18` (e.g. `0.5 upc`).
2. Submit `MsgExecutePayload` for a UEA with `maxFeePerGas`/`maxPriorityFeePerGas` set high enough to pass the `maxFeePerGas.Cmp(baseFeeBig) < 0` check (baseFeeBig is now `0`, so any non-negative `maxFeePerGas` passes trivially).
3. `CallUEAExecutePayload` executes the payload's full EVM logic (state-changing calls, PRC20 transfers, etc.) and returns a receipt with `GasUsed > 0`.
4. `CalculateGasCost` computes `effectiveGasPrice = 0`, so `gasCost = 0`; `DeductGasFeesFromReceipt` returns `nil` without touching the recipient's `upc` balance.
5. `ExecutePayloadV2` sees `feeErr == nil` and `execErr == nil`, calls `writeCache()`, committing the EVM execution for free while `DeductAndBurnFees` never executed — no `upc` was transferred to/burned from the module account despite real gas being consumed by the `DerivedEVMCall`.
