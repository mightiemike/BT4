## Analysis



### Title
Deleting an account with a non-existent `beneficiary_id` permanently burns the account's remaining balance instead of returning it - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/action_validation.rs`)

### Summary
`DeleteAccountAction` lets a transaction signer choose an arbitrary `beneficiary_id` to receive the deleted account's remaining balance. The only validation performed is that `beneficiary_id` is a syntactically valid `AccountId`; there is no check that the account actually exists. The runtime unconditionally emits a `Receipt::new_balance_refund` to that id. Because refund receipts are policy-barred from creating new accounts, if the chosen beneficiary does not exist the transfer fails with `AccountDoesNotExist`, and per the documented refund-failure rule the entire amount is burned rather than returned to anyone. This is structurally identical to the reported bug class: a user-selected destination that is never checked for validity/existence, causing an irreversible loss of value when it isn't "configured" (i.e., doesn't exist), just as `wormholeBridgeOut()` burnt items with no check that `_wormholeRemotes[dstWormholeChainId]` was set.

### Finding Description
`validate_delete_action` only calls `validate_action_account_id(&action.beneficiary_id)`, which checks AccountId syntax and nothing else: [1](#0-0) 

`action_delete_account` then unconditionally computes the account's remaining balance and pushes a balance-refund receipt addressed to `beneficiary_id`, without verifying that the beneficiary account exists on-chain: [2](#0-1) 

Refund receipts (`predecessor_id == "system"`) are policy-restricted from creating accounts — this is asserted by the runtime's own test suite (`refund_may_not_create_universal_account`), which explicitly documents "refunds are free ... they must not create an account, a `0u` one included": [3](#0-2) 

When such a refund fails (e.g., `AccountDoesNotExist` because `beneficiary_id` was never created), the runtime's own accounting explicitly burns the deposit instead of returning it to anyone: [4](#0-3) 

This behavior is also codified in the protocol documentation: "If the execution of a refund fails, the refund amount is burnt." [5](#0-4) 

At no point — neither at `validate_delete_action` (validation-time) nor at `action_delete_account` (execution-time) — is there a check analogous to the recommended `_wormholeRemotes[dstWormholeChainId] != bytes32(0)`, i.e. "does the chosen destination actually exist / is it a valid recipient before we irreversibly destroy the source-side balance." The account is deleted (and its balance debited from existence) unconditionally in the same action that attempts (and can fail) to deliver funds to the chosen beneficiary.

### Impact Explanation
Any account holder (an unprivileged transaction signer) who submits a `DeleteAccountAction` with a `beneficiary_id` that does not exist — due to a typo, a not-yet-created named account, or an implicit/universal account id that was never funded/initialized — permanently loses their entire remaining NEAR balance to the burn sink. There is no recovery path: the source account is already deleted by the time the refund is attempted, so the funds cannot be returned to the original owner, and they are not credited to any validator or beneficiary; they are destroyed. This is a direct, unauthorized and irreversible loss of user funds triggered by a single submitted transaction, matching the impact category of "permanently frozen/lost funds."

### Likelihood Explanation
This is trivially reachable by any account owner (or a contract acting on their behalf via `promise_batch_action_delete_account`) simply by supplying a wrong or non-existent `beneficiary_id` — no special privileges, validator status, or malicious peer/network behavior is required. It requires only a single, ordinary `DeleteAccountAction` in a signed transaction or a contract-generated receipt.

### Recommendation
Add a check, analogous to the recommended `_wormholeRemotes[dstWormholeChainId] != bytes32(0)` fix, that verifies `beneficiary_id` corresponds to an existing (or otherwise guaranteed-creatable, e.g. implicit) account before allowing the delete to proceed — or otherwise treat a failed beneficiary refund the same as a normal deposit failure (return to the original account) rather than a silent burn. This should be enforced in `validate_delete_action` (`runtime/runtime/src/action_validation.rs`) or in `action_delete_account` (`runtime/runtime/src/actions.rs`) before the account and its balance are irreversibly removed.

### Proof of Concept
1. Account `alice.near` holds `N` NEAR and has no locked stake.
2. `alice.near` (or a contract it controls) submits a transaction with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "typo-nonexistent.near" })`, where `typo-nonexistent.near` has never been created.
3. `action_delete_account` computes `account_balance = N`, pushes `Receipt::new_balance_refund(&"typo-nonexistent.near", N)`, and deletes `alice.near` from state — as shown in `runtime/runtime/src/actions.rs:380-387`.
4. The refund receipt executes against `typo-nonexistent.near`; because it is a refund receipt it cannot create the account (confirmed by the `refund_may_not_create_universal_account` test at `runtime/runtime/src/tests/apply.rs:6880-6926`), so it fails with `ActionErrorKind::AccountDoesNotExist`.
5. Per `runtime/runtime/src/lib.rs:1046-1054`, this failed refund causes the entire `N` to be added to `other_burnt_amount` — i.e., permanently destroyed. `alice.near` no longer exists to reclaim the funds, and `typo-nonexistent.near` never received them.

```rust
        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],
            Balance::from_near(100),
            Balance::ZERO,
            Gas::from_teragas(1000),
        );

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.

        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(

        );
    }
```

```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```
