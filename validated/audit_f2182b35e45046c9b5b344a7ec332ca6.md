### Title
App Proxy `logged_in_customer_id` parameter-pollution bypasses HMAC duplicate-parameter guard, enabling customer-identity spoofing - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`validateHmac` for the `appProxy` signator protects only four query parameters (`hmac`, `shop`, `signature`, `timestamp`) from duplication via `APP_PROXY_SINGLE_VALUE_PARAMS` [1](#0-0) . Any other parameter, including the security-sensitive `logged_in_customer_id` (which Shopify injects into app-proxy requests to identify the logged-in storefront customer), is treated as a generic "application" parameter: when repeated, `normalizeQuery` silently joins the values with a comma instead of rejecting the request [2](#0-1) .

### Finding Description
The `HmacValidator`'s guard list is a narrow allowlist that assumes only `hmac`/`shop`/`signature`/`timestamp` are security-relevant. But `logged_in_customer_id` is also security-relevant: it is how Shopify tells the app proxy endpoint which customer is currently authenticated on the storefront, and app developers commonly read this parameter directly from the query string to authorize/personalize customer-specific behavior (e.g., look up the customer's cart, orders, loyalty data). The test suite confirms the design intent: a repeated `consentGiven` (an "application" param) is accepted and joined as `"true,false"` and is explicitly treated the same way `logged_in_customer_id` would be [3](#0-2) , while only `hmac`, `shop`, `signature`, `timestamp` are asserted to be rejected when duplicated [4](#0-3) .

Because the value used to compute the canonical HMAC string (`normalizedQuery[key] = "${existingValue},${value}"`) is the *comma-joined concatenation* of all values, an attacker who controls the app-proxy URL (app proxy requests are proxied by Shopify from the storefront, but the underlying request to the app server includes the query string that Shopify forwards, and an attacker who can influence the query — e.g. via a crafted storefront link/form submission that a victim clicks, since app-proxy URLs are public storefront URLs) can append a second `logged_in_customer_id` value. If the app's route handler retrieves `logged_in_customer_id` via a naive lookup (e.g., `URLSearchParams.get()`, which returns only the **first** occurrence) while the HMAC validation computes the canonical string from the **joined** value, this creates a parameter-smuggling primitive: the value trusted by the signature check and the value consumed by application logic can diverge, or an attacker-appended forged ID rides along inside a validly-signed request if the app naively splits/uses the last value.

This mirrors the referenced bug's root cause pattern: a security control expressed as a narrow, explicit list (`APP_PROXY_SINGLE_VALUE_PARAMS`) that does not account for a specific field bearing an identity/security meaning (`logged_in_customer_id`), so that field falls through to weaker, generic handling.

### Impact Explanation
If an app's app-proxy handler reads `logged_in_customer_id` from the incoming request's query parameters using standard first-match semantics (very common pattern, e.g. `url.searchParams.get('logged_in_customer_id')`), and Shopify's own outbound signing behavior for repeated params is undocumented/inconsistent with this library's join-based canonicalization, there is a risk of a genuine customer-identity confusion: the app could act on behalf of a different customer ID than the one Shopify actually authenticated, without the HMAC check being able to flag the tampering, because the duplicate-parameter class only throws for `hmac`/`shop`/`signature`/`timestamp`.

### Likelihood Explanation
Exploitability is constrained by exactly how the underlying framework (Remix/React Router `URLSearchParams`) parses duplicated parameters versus how the shared library computes the signed canonical string, and by whether Shopify's own signing service ever produces repeated `logged_in_customer_id` values in a legitimate flow. I was not able to confirm from the codebase alone whether Shopify's proxy signature service would ever sign a URL with a duplicate `logged_in_customer_id` in production, so I cannot fully validate whether an attacker can produce a validly-signed request with an injected duplicate `logged_in_customer_id`. This significantly limits confidence that this rises to a directly exploitable forged-request vulnerability versus a defense-in-depth gap.

### Recommendation
Add `logged_in_customer_id` (and any other Shopify-injected identity/security parameter such as `path_prefix`) to `APP_PROXY_SINGLE_VALUE_PARAMS` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` so that duplicate occurrences are rejected outright rather than silently joined, closing the gap between the set of "protected" parameters and the set of parameters that carry security/identity meaning.

### Proof of Concept
Not independently verified end-to-end because it depends on server framework request-parsing behavior; the concrete divergence is illustrated by the existing test that shows duplicate non-listed params are joined rather than rejected: [3](#0-2) . Given the uncertainty noted in "Likelihood," this should be treated as a **potential defense-in-depth gap** requiring further verification against real Shopify app-proxy signing behavior before treating it as a confirmed exploitable vulnerability.

```typescript
function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
```
