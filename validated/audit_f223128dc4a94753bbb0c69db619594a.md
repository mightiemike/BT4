### Title
Malicious contract can permanently burn user deposits via `promise_set_refund_to` with a non-existent account — (`runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`)

---

### Summary

The `promise_set_refund_to` host function allows any contract to redirect deposit refunds for a cross-contract call to an arbitrary account ID. The runtime validates only the syntactic format of that account ID, not whether the account exists. When the inner call fails and the deposit-refund receipt is routed to a non-existent named account, the refund receipt itself fails, and the runtime permanently burns the deposit instead of returning it to the original sender.

---

### Finding Description

**Host function and storage of `refund_to`**

`promise_set_refund_to` in `runtime/near-vm-runner/src/logic/logic.rs` reads an account ID from guest memory and stores it on the pending receipt via `self.ext.set_refund_to(receipt_idx, refund_to)`. The only check performed is that the bytes decode to a syntactically valid `AccountId`. [1](#0-0) 

`ReceiptManager::set_refund_to` stores the value unconditionally: [2](#0-1) 

**Receipt validation does not check account existence**

`validate_action_receipt` in `verifier.rs` validates the `refund_to` field only for format correctness — it calls `AccountId::validate` but never queries the trie to confirm the account exists: [3](#0-2) 

**Deposit refund is routed to the attacker-supplied account**

When the inner call fails, `refund_unspent_gas_and_deposits` creates a `Receipt::new_balance_refund` addressed to `receipt.balance_refund_receiver()`, which returns the `refund_to` value if one was set: [4](#0-3) 

`Receipt::new_balance_refund` sets `predecessor_id = "system"`, marking the resulting receipt as a refund receipt: [5](#0-4) 

**Failed refund receipt burns the deposit**

When the refund receipt is applied, `apply_action_receipt` detects `predecessor_id().is_system()`. If the transfer to the non-existent account fails (`AccountDoesNotExist`), the deposit is added to `other_burnt_amount` and permanently destroyed: [6](#0-5) 

This is consistent with the documented invariant: "If the execution of a refund fails, the refund amount is burnt." [7](#0-6) 

Transfers to non-existent non-implicit accounts always fail; refunds explicitly do not create accounts: [8](#0-7) 

---

### Impact Explanation

A user who sends a deposit to a malicious contract loses that deposit permanently. The funds are not locked (recoverable) — they are burnt and removed from total supply. The `ActionReceiptV2.refund_to` field is set entirely by the contract, invisible to the caller at transaction submission time. There is no on-chain mechanism for the victim to detect or prevent this before interacting.

The corrupted value is the user's `deposit` balance: it is credited to `stats.balance.other_burnt_amount` instead of being returned to the sender. [9](#0-8) 

---

### Likelihood Explanation

Any unprivileged account can deploy a contract that:
1. Accepts a deposit-bearing function call from a victim.
2. Calls `promise_set_refund_to` with a syntactically valid but non-existent named account (e.g., `sink.near`).
3. Makes a cross-contract call that is guaranteed to fail (e.g., calling a non-existent method).

The victim's deposit is then permanently burnt. The attack cost is only the gas to deploy and call the contract. The `ActionReceiptV2` struct exposes `refund_to` as an optional field, so the malicious receipt is indistinguishable from a legitimate one at the RPC level. [10](#0-9) 

---

### Recommendation

1. **Existence check at refund time**: In `action_transfer_or_implicit_account_creation`, when the receipt is a refund (`predecessor_id().is_system()`) and the receiver account does not exist, fall back to burning only if the receiver is also not the original predecessor — otherwise credit the predecessor. Alternatively, treat a missing `refund_to` account as if `refund_to` were not set and route the refund to `predecessor_id` instead of burning.

2. **Validation at receipt creation**: In `validate_action_receipt`, when `refund_to` is present and the receipt is being validated as a `NewReceipt`, reject it if the `refund_to` account does not exist in the current state (similar to how `DeleteAccount.beneficiary_id` is validated for format). [11](#0-10) 

---

### Proof of Concept

```
1. Attacker deploys contract C on account `attacker.near`.
2. Contract C implements a method `trap(deposit: u128)`:
     a. Creates a promise to call `nonexistent_method` on `victim_contract.near`
        with the full attached deposit forwarded.
     b. Calls `promise_set_refund_to(promise_idx, "sink.near")`
        where `sink.near` does not exist.
3. Victim calls `C.trap` with deposit = 10 NEAR.
4. The inner call to `victim_contract.near::nonexistent_method` fails
   with `MethodNotFound`.
5. `refund_unspent_gas_and_deposits` creates:
     Receipt { predecessor_id: "system", receiver_id: "sink.near",
               actions: [Transfer { deposit: 10 NEAR }] }
6. The refund receipt executes; `sink.near` does not exist and is not
   an implicit account → `AccountDoesNotExist` error.
7. Because `predecessor_id.is_system()` and `result.result.is_err()`,
   10 NEAR is added to `other_burnt_amount`.
8. Victim's 10 NEAR is permanently destroyed.
```
