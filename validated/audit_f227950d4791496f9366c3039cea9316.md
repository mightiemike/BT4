Missing allowlist/rate-limit enforcement lets any (including previously-blocked) sender push `web_api_trigger` requests to DON nodes - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Sherlock finding describes a Stablecoin implementation where blacklisting an address only seizes its balance but never actually blocks the address from sending/receiving tokens — the enforcement point that should gate every transfer is simply missing. The same *bug class* (a trust boundary that is designed to gate unprivileged-user requests, but the gating check is never actually wired in) exists in the chainlink Gateway's WebAPI capability handler: the code explicitly documents that allowlist/rate-limit checks are supposed to happen for incoming user messages, but the check is left as a `TODO` and never implemented, so every user request is forwarded to DON nodes unconditionally.

### Finding Description
`handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` is the entry point for external, unprivileged HTTP/JSON-RPC callers submitting `web_api_trigger` requests to the gateway. It performs payload decoding, timestamp/staleness validation, and method-name validation, but right where an allowlist/rate-limit check should occur there is only a comment: [1](#0-0) 

After that stubbed-out check, the message is unconditionally forwarded to every DON member: [2](#0-1) 

This is the same architectural pattern used correctly elsewhere in the codebase for equivalent unprivileged-user trust boundaries — e.g. `functionsHandler.HandleLegacyUserMessage` explicitly checks `h.allowlist.Allow(sender)` before processing a request: [3](#0-2) 

and `functionsConnectorHandler.HandleGatewayMessage` performs the identical check before dispatching: [4](#0-3) 

The `capabilities` WebAPI handler is the outlier: its `Methods()` advertises `MethodWebAPITrigger` as a valid user-facing method [5](#0-4) , yet `HandleLegacyUserMessage` never consults any allowlist or the handler's rate limiter (`h.nodeRateLimiter` is only used for outbound node messages in `handleWebAPIOutgoingMessage`, not for gating inbound user messages) before dispatching the request to every DON node via `don.SendToNode`.

### Impact Explanation
Because there is no allowlist/rate-limit gate on the inbound user-message path, any external caller — including one that operators intend to block/deny (analogous to a "blacklisted" account) — can submit unlimited `web_api_trigger` requests that get relayed to every member of the DON. This defeats a manually-administered access-control feature exactly as in the referenced Sherlock finding: the gating mechanism exists in design/config (`OnchainAllowlist`, rate limiter config fields) and in sibling handlers, but is not enforced at this trust boundary, allowing unauthorized triggering of workflow execution across the DON and unbounded resource consumption (DoS) on gateway/DON nodes.

### Likelihood Explanation
High likelihood of reachability: `HandleLegacyUserMessage` is a standard external-facing entry point invoked whenever a gateway receives a legacy user message for this handler's DON, requiring no privileged credentials — only a validly-formed message with a fresh timestamp. The missing check is not hidden in a rare code path; it is the primary and only validation step for this handler's supported method.

### Recommendation
Implement the allowlist and rate-limiting check flagged by the `TODO` comment before forwarding the request to DON nodes, mirroring the pattern already used in `functionsHandler.HandleLegacyUserMessage` (`h.allowlist.Allow(sender)`) and `functionsConnectorHandler.HandleGatewayMessage`. Concretely, add an `OnchainAllowlist`/`ratelimit.RateLimiter` dependency to `handler`/`HandlerConfig`, extract the message sender, and reject (with an appropriate JSON-RPC error response) before the request reaches `h.savedCallbacks` / `don.SendToNode`.

### Proof of Concept
1. Configure a gateway DON with the `capabilities` `WebAPIHandler` (`MethodWebAPITrigger`) and no allowlist configured for that handler (there is no allowlist field to configure in `HandlerConfig` at all).
2. As an external, non-privileged (or explicitly denied/blacklisted-in-intent) client, submit a legacy user message with `Method: web_api_trigger`, a valid non-empty payload, and `Timestamp` within `MaxAllowedMessageAgeSec`.
3. Observe in `HandleLegacyUserMessage` that execution proceeds straight past the `// TODO: apply allowlist and rate-limiting here` comment (line 384) to `common.ValidatedRequestFromMessage` and then `don.SendToNode` for every DON member — the request succeeds and is relayed to all nodes regardless of sender identity, since no `allowlist.Allow(sender)`-style check (as seen in `handler.functions.go` line 210) is ever invoked.

func (h *functionsConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("failed to decode request", "id", gatewayID, "err", err)
		return nil
	}
	body := &msg.Body
	fromAddr := ethCommon.HexToAddress(body.Sender)
	if !h.allowlist.Allow(fromAddr) {
		h.lggr.Errorw("allowlist prevented the request from this address", "id", gatewayID, "address", fromAddr)
		return nil
	}
	if !h.rateLimiter.Allow(body.Sender) {
		h.lggr.Errorw("request rate-limited", "id", gatewayID, "address", fromAddr)
		return nil
	}
