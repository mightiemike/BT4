### Title
Front-running griefing via deterministic CREATE2 address pre-emption blocks legitimate contract deployment - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
The bug class in the external report is a griefing/DoS attack where an attacker permissionlessly pre-creates a resource at a deterministic, publicly-computable address (a Uniswap pair) before the legitimate caller's transaction executes, causing the legitimate caller's subsequent "already exists" check to revert and permanently blocking their intended action. The same root cause — a deterministic target address computed from public inputs, combined with an "already exists → fail" guard with no fallback — exists in java-tron's TVM `CREATE2` contract-creation path.

### Finding Description
`Program.createContractImpl()` is the shared implementation used by both `CREATE` and `CREATE2` (the `isCreate2` flag distinguishes them). For `CREATE2`, the target address is computed deterministically via `WalletUtil.generateContractAddress2()`, which hashes `sender (factory) address || salt || keccak256(initcode)`: [1](#0-0) 

This address depends only on the calling factory contract's address, the salt, and the init code — all of which are visible on-chain or in the mempool once a deployment transaction is broadcast (exactly analogous to how `tokenAddr`/`assetToken` are public in the Uniswap pair case). Any party can call the same factory contract with the same `(code, salt)` parameters to compute and occupy the identical `CREATE2` address ahead of the legitimate deployer, since nothing restricts who may invoke the factory's create function with those parameters.

When the deployment address already has account/contract state, `createContractImpl()` marks `contractAlreadyExists = true` and unconditionally fails the creation: [2](#0-1) [3](#0-2) 

There is no analog to the recommended mitigation from the report (checking whether the pre-existing state actually represents "real" deployed content, e.g., checking code/supply rather than mere existence) — any prior occupation of the address, even a bare account created by a 1-sun TRX transfer or a trivial contract deployed via the same factory call, is sufficient to permanently block the legitimate deployer's expected deployment to that exact address, mirroring the LP-pool griefing pattern in the report (`pool already exists` check based purely on existence, not on real usage/liquidity).

### Impact Explanation
An attacker monitoring the mempool for a pending `CREATE2` deployment (e.g., a factory pattern used for deterministic wallet/contract addresses, counterfactual instantiation, or cross-chain address parity schemes) can front-run it by invoking the same factory function with identical `(code, salt)` parameters, claiming the deterministic address first. The victim's transaction will then hit the `contractAlreadyExists` branch and fail with `BytecodeExecutionException` ("Trying to create a contract with existing contract address"), permanently denying the victim the ability to deploy to their expected, pre-computed address — a persistent griefing/DoS on any protocol relying on deterministic `CREATE2` addressing (similar in effect to blocking `initFromToken()`/`executeApplication()` in the original report).

### Likelihood Explanation
Likelihood is moderate: it requires (a) a `CREATE2`-based factory contract deployed on TRON whose deployment parameters are predictable/observable before confirmation, and (b) an attacker with any account able to submit a transaction ahead of the legitimate one (standard front-running via gas/energy bidding or same-block ordering). This is a generic TVM-level primitive risk rather than a bug confined to one specific in-scope contract, so its exploitability depends on higher-layer dApp design choices (whether salts are secret/unpredictable). Where salts are predictable (sequential, user-address-derived, or announced in advance), the attack is straightforward to mount.

### Recommendation
Documented as VM-level behavior consistent with EVM's `CREATE2` semantics; no code fix is proposed against the in-scope contracts. Protocols built on TRON's `CREATE2` should treat deterministic-address pre-emption as a known griefing vector and design salts/ordering to avoid depending on winning a race against front-runners, analogous to the report's recommendation to verify real usage (e.g., liquidity/state) rather than mere existence before failing.

### Proof of Concept
1. Deploy a `CREATE2` factory contract `F` with a public `deploy(bytes code, uint256 salt)` function.
2. Victim broadcasts a transaction calling `F.deploy(initcode, salt)`, computing target address `A = generateContractAddress2(F, salt, keccak256(initcode))`.
3. Attacker observes the pending transaction (`code`, `salt` are visible), and submits their own call to `F.deploy(initcode, salt)` (or simply transfers TRX to `A` to create a bare account there) with higher priority so it is included first.
4. When the victim's transaction executes, `createContractImpl()` sees `existingAccount != null` at address `A`, sets `contractAlreadyExists = true`, and the creation fails with `BytecodeExecutionException("Trying to create a contract with existing contract address: ...")`, per: [4](#0-3) 
5. The victim's factory call reverts/fails, permanently denying them the intended deterministic address — a direct analog of the Uniswap-pair griefing described in the external report.
