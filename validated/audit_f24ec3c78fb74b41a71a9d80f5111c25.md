### Title
Unguarded division by `totalEnergyWeight`/`totalTronPowerWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` can throw an uncaught `ArithmeticException` when the resource weight reaches zero - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
The external report describes `ExternalBribe.earned` dividing a reward by a checkpointed `supply` value without guarding against that supply being zero, causing a revert. The closest analogous pattern in java-tron is `RepositoryImpl.calculateGlobalEnergyLimit`, which divides a TVM account's frozen-energy weight proportion by the global `totalEnergyWeight` counter, relying only on a Java `assert` statement (disabled by default in production JVMs) instead of an explicit runtime check, before performing a `BigInteger` division that throws `ArithmeticException` on zero.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` computes an account's global energy limit share by dividing `energyWeight * totalEnergyLimit` by `totalEnergyWeight`: [1](#0-0) 

The only protection against `totalEnergyWeight` being `0` is a Java `assert` statement, which is a no-op unless the JVM is started with `-ea`. Production nodes are not run with assertions enabled, so if `totalEnergyWeight` is `0` when this function runs with `hardenResourceCalculation()` enabled, the code performs `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))`, which throws `java.lang.ArithmeticException: BigInteger divide by zero`.

This mirrors the reported bug class in `ExternalBribe.earned`: a value used as a divisor (`supply`/`totalWeight`) is assumed to never be zero based on normal operating conditions, but the code path that decrements the underlying weight/supply counter (e.g., mass unfreezing of energy, as seen in `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor` calling `dynamicStore.addTotalEnergyWeight(weight)` with a negative delta) is not cross-checked against consumers of that value at read time.

By contrast, the twin function `EnergyProcessor.calculateGlobalEnergyLimit` in `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java` (lines 145-166) *does* have an explicit runtime guard for the `allowNewReward()` case (`if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) { return 0; }`), showing that the developers recognized this hazard elsewhere but did not carry the same explicit (non-assert-based) protection into `RepositoryImpl`'s copy of the logic, nor cover the case where `allowNewReward()` is false.

### Impact Explanation
If `totalEnergyWeight` reaches zero (e.g., through a sequence of unfreeze/undelegate operations that drain all globally tracked energy weight while an account still records a stale non-zero `getAllFrozenBalanceForEnergy()`), any subsequent call into `RepositoryImpl.calculateGlobalEnergyLimit` — reachable from ordinary TVM execution paths that need to compute an account's energy limit — throws an uncaught `ArithmeticException`. Because production nodes run without `-ea`, the `assert` provides no protection. An uncaught runtime exception during transaction execution/energy accounting is a state/execution-halting condition for the actuator processing the transaction, and if triggered deterministically it would affect all nodes identically during block validation, which is a liveness/availability risk for that specific code path rather than a fund-theft primitive.

### Likelihood Explanation
Likelihood is low-to-moderate and hard to fully confirm without deeper tracing of every code path that can drive `totalEnergyWeight` to exactly zero on a live network (mainnet total energy weight is unlikely to reach zero given broad staking participation), similar to the "Low" likelihood rated in the original report for the checkpoint-supply-zero scenario. It is more plausible on private/test networks or in edge-case sequences (e.g., all energy unfrozen) where this invariant can be violated. I was not able to fully enumerate every caller of `RepositoryImpl.calculateGlobalEnergyLimit` within the available tool budget, so the exact reachability from an unprivileged TVM call needs further verification by a background agent with full codebase access.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check (e.g., `if (totalEnergyWeight <= 0) { return 0; }`), consistent with the guard already present in `EnergyProcessor.calculateGlobalEnergyLimit`, and audit other divisions guarded only by `assert` in the same class for the same issue.

### Proof of Concept
Not independently reproduced; a concrete PoC would require constructing a sequence of freeze/unfreeze/undelegate transactions that drives `getTotalEnergyWeight()` to `0` while `hardenResourceCalculation()` is enabled, then invoking a TVM path that calls `RepositoryImpl.calculateGlobalEnergyLimit` on an account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`, and observing the resulting `ArithmeticException`. This should be validated with a background Devin session that can run the existing test suite (e.g., `framework/src/test/java/org/tron/core/vm/repository/RepositoryImplHardenTest.java`) and add a targeted unit test forcing `totalEnergyWeight = 0`.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
