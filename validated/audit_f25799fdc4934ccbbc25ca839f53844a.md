### Title
Nil `receipt` dereference in `handleFailedOutbound` can panic all honest nodes during outbound finalization - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
The external report describes a Rust `unwrap()` on an `Option` that the code assumed could never be `None` (`posted_order` in a trade receipt), causing a deterministic node panic reachable from a normal, honest user action. The Go analog is a pointer dereference on an EVM call receipt that the code assumes is non-nil whenever the accompanying error is nil, but the surrounding code in the same file and module treats that exact assumption as unsafe everywhere else.

### Finding Description
In `handleFailedOutbound` [1](#0-0) , the flow is:

```go
receipt, err := k.CallPRC20Deposit(ctx, common.HexToAddress(outbound.Prc20AssetAddr), common.HexToAddress(recipient), amount)
...
if receipt != nil {
    pcTx.TxHash = receipt.Hash
    pcTx.GasUsed = receipt.GasUsed
}
if err != nil {
    ...
    return k.AbortOutbound(...)
}
pcTx.TxHash = receipt.Hash
pcTx.GasUsed = receipt.GasUsed
pcTx.Status = "SUCCESS"
``` [1](#0-0) 

Notice the defensive `if receipt != nil` check exists on line 126, immediately followed on line 138 (the `err == nil` success path) by an **unconditional** `receipt.Hash` dereference with no nil guard. Every other call site in the same module that consumes an `*evmtypes.MsgEthereumTxResponse` treats "receipt possibly nil even when err is nil" as the expected contract and guards accordingly:
- `execute_inbound_funds_and_payload.go` guards `if receipt != nil` before touching `.Hash`/`.GasUsed` at lines 169-172, 264-267, and 298-301 [2](#0-1) .
- `execute_payload.go`'s `ExecutePayloadV2` treats `DeductGasFeesFromReceipt` as "no-op if the receipt is nil" [3](#0-2) .

This is structurally identical to the Nord bug: a comment/pattern elsewhere in the codebase says "we can safely assume X is set here" (there, "we must have a fill or a posted order"; here, implicitly, "a non-error receipt from `CallPRC20Deposit` must be non-nil"), but the one call site that skips the check is exactly the one that panics when the assumption is violated.

`handleFailedOutbound` is invoked from `FinalizeOutbound`, which every honest core validator executes deterministically as part of `VoteOutbound` state-transition processing once 2/3+ Universal Validators vote a `FAILED` observation on a `FUNDS` / `GAS_AND_PAYLOAD` / `FUNDS_AND_PAYLOAD` outbound [4](#0-3) [5](#0-4) . Any ordinary user can cause an outbound whose destination-chain broadcast fails (e.g. sending a payload that produces an outbound targeting a call that reverts on the destination chain), which is an entirely normal, unprivileged trigger for the `FAILED`-observation path that honest UVs vote on.

### Impact Explanation
If `CallPRC20Deposit` can return `(nil, nil)` under any code path in the underlying `DerivedEVMCall`/EVM message-execution plumbing (e.g., an execution result with no error but an empty/nil response, similar to how other call sites in this module explicitly account for), every honest core validator processing that `MsgVoteOutbound` finalization deterministically panics at the same line while applying the state transition. Because this happens inside block/state-transition processing (not a rejected-tx path), it is a chain halt / consensus-liveness failure reachable purely from an ordinary user's crosschain transaction that produces a failing outbound — no privileged, malicious-validator, or malicious-relayer behavior is required, matching the in-scope "denial of service...reachable without privileged control" and "consensus or state-machine divergence reachable from ordinary user...payloads" categories.

### Likelihood Explanation
The likelihood hinges entirely on whether `CallPRC20Deposit` (defined in `x/uexecutor/keeper/evm.go`, whose implementation I was not able to inspect before running out of tool calls) can actually return a `nil` receipt together with a `nil` error. I could not confirm or rule this out from the code available to me. What is confirmed is the code-level inconsistency: this is the only success-path receipt consumption in the module that omits the nil guard used everywhere else, which is a strong structural signal of an overlooked edge case rather than a deliberately-proven invariant.

### Recommendation
Add the same defensive `if receipt != nil` guard before the `pcTx.TxHash = receipt.Hash` / `pcTx.GasUsed = receipt.GasUsed` assignments on the success path of `handleFailedOutbound` (mirroring lines 126-129), or restructure so `receipt.Hash`/`receipt.GasUsed` are only read once, after a single nil check, regardless of the `err` branch. More broadly, audit `CallPRC20Deposit` and all `DerivedEVMCall`-based helpers to document/enforce whether a nil error guarantees a non-nil receipt, and add unit/integration tests that force the “success but empty receipt” branch of every such helper used inside `FinalizeOutbound`, `ExecuteInbound*`, and `ExecutePayloadV2`.

### Proof of Concept
I was unable to construct or verify a concrete trigger for `CallPRC20Deposit` returning `(nil, nil)` because `x/uexecutor/keeper/evm.go` (its implementation) was not available for inspection in this session. A full PoC would require: (1) confirming the exact conditions under which the underlying EVM call plumbing returns a nil `*evmtypes.MsgEthereumTxResponse` with a nil error, and (2) driving an outbound of `TxType_FUNDS`/`GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` to a `FAILED` `MsgVoteOutbound` quorum under that condition. This should be validated by a background engineer with full repository access (including `x/uexecutor/keeper/evm.go`) before treating this as confirmed-exploitable; absent that confirmation, this should be treated as a **defensive-coding gap with plausible but unverified reachability**, not a proven live exploit.
