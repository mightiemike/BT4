### Title
Single invalid `RescueFundsOnSourceChain` log in a multi-log receipt aborts the EVM post-tx hook, blocking all other outbound/rescue accounting in that transaction - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`AttachRescueOutboundFromReceipt` loops over every log in an EVM receipt looking for `RescueFundsOnSourceChain` events, but returns immediately on the *first* per-event validation error (unknown UTX, non-eligible CEA/non-CEA state, decode failure), aborting the loop for the remaining logs in the same receipt.

### Finding Description
`AttachRescueOutboundFromReceipt` iterates `receipt.Logs` and, for each matching `RescueFundsOnSourceChain` event, performs several validations before attaching a `RESCUE_FUNDS` outbound to the referenced UTX: decoding the log, fetching the original UTX, and checking rescue eligibility (CEA deposit failed, or non-CEA `INBOUND_REVERT` reached `REVERTED`). [1](#0-0) 

Any of these per-event checks failing (`rescue: UTX %s CEA deposit did not fail`, `rescue: UTX %s has no reverted inbound-revert outbound`, decode error, "not found") causes the function to `return` an error immediately, without processing any subsequent logs in the same receipt loop. [2](#0-1) 

This is exactly the "uncontained token errors" pattern from the report: a loop over multiple independent "components" (here, rescue events emitted by potentially multiple, unrelated `rescueFunds` calls batched into one transaction/receipt) where a single bad or not-yet-eligible entry reverts processing for every other entry in the same batch.

This function is invoked from the EVM `PostTxProcessing` hook, which runs after every EVM transaction: [3](#0-2) 

Because `AttachRescueOutboundFromReceipt`'s error is propagated straight out of `PostTxProcessing`, any transaction whose receipt happens to contain one ineligible rescue log alongside other legitimate crosschain events (`UniversalTxOutbound` and other valid `RescueFundsOnSourceChain` logs) will have its entire post-processing hook fail. `CreateUniversalTxFromReceiptIfOutbound` runs before it in the same hook and is unaffected in this call, but any rescue events attached within the same receipt after the failing one are silently skipped rather than each being evaluated and recorded independently.

### Impact Explanation
Under the allowed-impact gate, this is not the same magnitude as fund loss, but it does corrupt the canonical `UniversalTx` / outbound-accounting invariant: multiple valid rescue events emitted in one receipt (e.g. by a relayer or user batching several `rescueFunds` calls, or by the gateway contract emitting several rescue logs for unrelated stuck UTXs in one block/tx) will have their processing halted at the first ineligible one — an attacker or relayer can trivially cause this by interleaving one rescue call for a UTX that hasn't yet reached the required state (e.g., its `INBOUND_REVERT` outbound is still `PENDING` rather than `REVERTED`) with legitimate ones, denying accounting attachment for outbounds after it in the same receipt. Since `PostTxProcessing` hook failure semantics ultimately determine whether the hook error propagates to the EVM commit path, this can also manifest as an unprivileged-triggerable partial denial-of-service on legitimate rescue/outbound bookkeeping, without requiring any privileged actor.

### Likelihood Explanation
Reaching this path requires only submitting/observing an EVM transaction whose receipt contains a `RescueFundsOnSourceChain` log for a UTX that fails the eligibility check (trivial to construct — e.g. an attacker calling `rescueFunds` on the vault for a UTX that hasn't reached the required revert state) batched together with other legitimate `RescueFundsOnSourceChain`/`UniversalTxOutbound` logs. No validator collusion or privileged access is needed; the check is purely a function of the referenced UTX's on-chain state, which is attacker-observable.

### Recommendation
Change `AttachRescueOutboundFromReceipt`'s loop to continue processing remaining logs when a single event fails validation, recording a per-event failure (e.g. as an error log / event) instead of returning early, mirroring the `BasicIssuanceModule` fix pattern of isolating failures to the affected component rather than reverting the whole operation. At minimum, aggregate errors across iterations and only surface them after all eligible events have been attempted.

### Proof of Concept
1. Craft an EVM receipt containing two `RescueFundsOnSourceChain` logs from `UniversalGatewayPC`: log A references a UTX whose non-CEA `INBOUND_REVERT` outbound is still `PENDING` (ineligible), log B references a different, legitimately eligible UTX (its `INBOUND_REVERT` is `REVERTED`).
2. Order log A before log B in `receipt.Logs`.
3. Call `AttachRescueOutboundFromReceipt` (or trigger it via `PostTxProcessing`) with this receipt, as shown in the eligibility tests in [4](#0-3) .
4. Observe the function returns `"rescue: UTX %s has no reverted inbound-revert outbound"` on log A and never reaches/attaches the outbound for log B, even though log B's UTX independently qualified for rescue.

			return fmt.Errorf("rescue: failed to fetch UTX %s: %w", originalUtxId, err)

			return fmt.Errorf("rescue: original UTX %s not found", originalUtxId)

			}

				}
