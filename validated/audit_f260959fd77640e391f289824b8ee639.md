### Title
Potential unrecoverable underflow panic in `Runtime::apply_action_receipt` when subtracting `receiver_reward` from `tx_burnt_amount` - (File: `runtime/runtime/src/lib.rs`)

### Summary
The external report describes a Solidity `processEpoch()` bug where a derived value (`totalAssets().mulDivDown(...)`) is subtracted from a stored running total (`yIntercept`) without first re-accruing the total, so the subtrahend can exceed the total and the subtraction underflows/reverts, permanently breaking the epoch-processing state machine. The closest reachable analog in nearcore is the arithmetic in `Runtime::apply_action_receipt`, where a stored running total of burnt tokens for a receipt (`tx_burnt_amount`) is decremented by a separately, differently-priced derived reward amount (`receiver_reward`) via a bare `.unwrap()` on `checked_sub`, without an accompanying invariant proof that the reward can never exceed the burnt total.

### Finding Description
In `runtime/runtime/src/lib.rs`, after gas is burnt and refunds are computed, the code accumulates `tx_burnt_amount` from several components (burnt gas at `gas_burn_price`, minus `price_deficit`, plus `refund_penalty`, `create_account_charge`, and `result.tokens_burnt`): [1](#0-0) 

It then computes a separate `receiver_reward` — the contract's share of gas burnt specifically *for function calls* — priced independently as either `gas_burn_price` or `gas_purchase_price` depending on the `AccountCostIncrease` protocol feature gate: [2](#0-1) 

Finally, this `receiver_reward` is subtracted from `tx_burnt_amount` using an unchecked `.unwrap()`: [3](#0-2) 

This mirrors the report's structural bug-class exactly: a stored/derived aggregate (`tx_burnt_amount`, analogous to `yIntercept`) is decremented by a second, independently-derived quantity (`receiver_reward`, analogous to `totalAssets().mulDivDown(ratio,1e18)`) that is computed from a *different* base (function-call-only gas, priced potentially at a different price than the aggregate) rather than being guaranteed to be a strict sub-component of the aggregate before the subtraction. The code even contains a developer comment at line 1040 acknowledging the underflow risk class ("should always be <= gas_purchase_price, otherwise receiver_reward might underflow or mint new tokens"), confirming that the invariant guaranteeing `receiver_reward <= tx_burnt_amount` is fragile and protocol-feature-gate dependent rather than structurally enforced by the type system. [4](#0-3) 

Because `tx_burnt_amount` is reduced by `price_deficit` before the `receiver_reward` subtraction, and `price_deficit` and `receiver_reward` are computed via separate independent code paths (one from `refund_unspent_gas_and_deposits`, the other from `gas_burnt_for_function_call` times a fee-config ratio), there is no single, statically-checked invariant in this function proving `receiver_reward` is always a subset of `tx_burnt_amount` after all the additions/subtractions — the safety currently rests on informal reasoning and a comment, not a `checked_sub` with graceful handling.

### Impact Explanation
If the arithmetic invariant is ever violated (e.g., via a change in the fee-config ratio, a future protocol upgrade to the `AccountCostIncrease`/NEP-536 refund-penalty logic, or an edge case in `gas_refund_result.price_deficit`/`refund_penalty`/`create_account_charge` computation that is not anticipated), the `.unwrap()` on `checked_sub` at line 1132 will panic. A panic during `apply_action_receipt` is not recoverable by returning a `Result` — it aborts the node process applying the chunk. Since chunk application must be deterministic across all validators, this would either:
- Halt the chain (every honest validator that reaches this code path panics and cannot produce/validate blocks), or
- Cause a state-root divergence between validators using different node/software versions in a way that produces different resulting behavior.

This matches the required Impact categories: "a transaction-triggered halt" / "invalid state transition acceptance" if it is not, in fact, unreachable. The report's underlying bug class ("subtracting a later-computed derived value from a stored/aggregated total without guaranteeing the value is always ≤ the total, causing revert / underflow") is structurally present here.

### Likelihood Explanation
Likelihood is assessed as uncertain/likely-low but not provably zero given the tools available. I was not able to fully trace every branch of `refund_unspent_gas_and_deposits` (the source of `price_deficit`, `refund_penalty`, and `create_account_charge`) within the available iterations to formally prove `receiver_reward <= tx_burnt_amount` holds for *all* protocol-version/fee-config combinations, especially cross-checking the `AccountCostIncrease` and NEP-536 gas-refund-penalty interactions referenced in the developer comment. The explicit in-code comment flagging the underflow risk ("otherwise receiver_reward might underflow or mint new tokens") indicates this was a known, actively-guarded-against class of bug during development of the `AccountCostIncrease` feature, suggesting the current invariant is believed to hold for the shipped configuration but is not proven unconditionally safe by the type system — it depends on `gas_burn_price = min(gas_purchase_price, apply_state.gas_price)` holding at all times, an invariant enforced by convention rather than by construction.

### Recommendation
- Replace the bare `.unwrap()` at line 1132 with a `checked_sub` that returns a `RuntimeError`/`StorageInconsistentState` (as is done elsewhere in the codebase, e.g. `update_validator_accounts` at `runtime/runtime/src/lib.rs:1774-1786`) rather than panicking, so any future invariant violation degrades to a handled error instead of an unrecoverable panic.
- Add an explicit assertion/documented proof (or a unit/property test) establishing that `receiver_gas_reward <= gas_burnt_for_function_call <= gas_burnt`, and that after subtracting `price_deficit` and adding `refund_penalty`/`create_account_charge`/`result.tokens_burnt`, `tx_burnt_amount` can never fall below `receiver_reward` under any combination of `AccountCostIncrease` gating, gas-price fluctuation, and NEP-536 refund-penalty parameters — mirroring the report's recommendation to "call accrue() first" (i.e., ensure the aggregate is fully up to date and consistent with the derived subtractive term before performing the subtraction).

### Proof of Concept
A concrete, fully-verified PoC transaction sequence could not be constructed within the available tool budget, because it requires deep tracing of `refund_unspent_gas_and_deposits` (price_deficit/refund_penalty/create_account_charge derivation) across the `AccountCostIncrease` and NEP-536 gating logic, which was not completed. The finding is reported based on direct code inspection of the vulnerable subtraction and the developer's own comment flagging the underflow risk class, structurally analogous to the reported Solidity bug; further investigation (ideally with fuzzing/property tests on `refund_unspent_gas_and_deposits` outputs against `gas_burnt_for_function_call`/`burnt_gas_reward` ratios across protocol versions) is recommended to confirm or rule out reachability.
