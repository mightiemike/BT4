## Binding (stated as an equality)

For the light‑client‑prover's method‑id state:

`BatchProofMethodIdAccessor::get(ws).last() == max_by_height({ (h, m) : council quorum signed body(h, m, chain_id) and no higher‑height council body has since been accepted })`

i.e. the *gating value* `last_activation_height` used to decide "is this new upgrade newer, so accept it" must track the **highest activation height ever legitimately accepted**, not merely "the most recently *processed* entry in DA-transaction order."

## Trace

`DataOnDa::BatchProofMethodId` handling in `run_l1_block`: [1](#0-0) 

`last_activation_height` is taken from `.last()` of the stored `Vec<(u64,[u32;8])>`, and `BatchProofMethodIdAccessor::insert` simply appends to that vector without sorting or deduplicating by height: [2](#0-1) 

Crucially, **unlike every other branch in the same `blob_loop`** (`Complete`, `Aggregate`, `SequencerCommitment`, which check `blob.sender().as_ref() != <expected_da_public_key>`), the `BatchProofMethodId` branch never checks `blob.sender()` at all — only the embedded EIP‑191 signatures inside the body are checked via `verify_method_id_security_council`: [3](#0-2) 

That signature check has no replay protection (no nonce, no "already applied" set) — it only re-verifies that the 3-of-5 signatures over `body.serialize()` are cryptographically correct for *whatever body bytes are presented*. Any previously-published, council-signed `BatchProofMethodId` body remains "valid" forever and can be copied byte-for-byte out of any earlier Bitcoin transaction and re-inscribed by anyone, from any DA key, since sender is never checked in this branch.

## Root cause and exploit

- `insert()` is append-only; `last()` is used as a stand-in for "maximum height inserted," which is only correct if entries are always inserted in strictly increasing height order.
- Within a single `blob_loop` over `da_txs` (whose order is fixed by Bitcoin block tx order, an untrusted/attacker-influenceable ordering, not by height), an attacker can place a *replayed*, still-cryptographically-valid, higher-height council body (H2, ID2) before a genuine lower-height council body (H1, ID1), where H1 < H2.
- Processing order: H2 processed first → `last_activation_height` was 0 (or below H2) → `H2 > last_activation_height` passes → signatures verify (they're the real council's old signatures) → `insert(H2, ID2)`.
- H1 processed next → `last_activation_height` is now H2 → `H1 <= H2` → `continue` — the genuine, intended, lower-height upgrade is silently dropped.
- Because the vector is append-only and never pruned/re-sorted, `last_activation_height` stays at H2 (or anything ≥ H2) in every subsequent L1 block forever, so the genuine (H1, ID1) upgrade can never be inserted afterward either — it is **permanently** lost.
- No existing guard prevents this: `verify_method_id_security_council` only checks signature validity of the presented bytes, not freshness or ordering; there's no sender allow‑list on this branch; and Bitcoin tx ordering within a block is attacker-influenceable via fee/relative-position choices (or simply waiting for a favorable block), so nothing in `run_l1_block` enforces that height-monotonic processing matches height-monotonic *council intent*.

### Title
Same-block replay of a stale council-signed `BatchProofMethodId` inscription with a higher activation height permanently blocks a genuine, lower-height method-id upgrade - (crates/light-client-prover/src/circuit/mod.rs)

### Summary
The `DataOnDa::BatchProofMethodId` branch in `run_l1_block` gates new method-id upgrades using `.last()` of an append-only `Vec<(height, method_id)>`, and never checks `blob.sender()`. An attacker who simply re-inscribes any previously published, still-signature-valid council body with a higher activation height ahead of a genuinely intended lower-height body in the same Bitcoin block (or block set) can permanently prevent the legitimate upgrade from ever being accepted by the light-client-prover circuit.

### Finding Description
The binding `last_activation_height == max height ever legitimately accepted` is broken because `last_activation_height` is derived from insertion order (`.last()`), not from a height-sorted maximum, and `insert()` [2](#0-1)  appends unconditionally. The `BatchProofMethodId` match arm [1](#0-0)  lacks the `blob.sender()` allow-list check present in the `Complete`/`Aggregate`/`SequencerCommitment` arms, so any old, still-signature-valid council body can be replayed by anyone via a fresh Bitcoin inscription with attacker-chosen tx position/fee. Placing a copied high-height body before a new low-height genuine body in the same block's `da_txs` order causes the genuine, later-intended, lower-height upgrade to be rejected by the `activation_l2_height <= last_activation_height` check and never inserted — permanently, since the vector never shrinks and `last_activation_height` can only grow.

### Impact Explanation
This is a method-id upgrade that the council authorized but that the light-client-prover circuit silently and permanently drops, matching the Critical category "a … method-id upgrade accepted that was never authorised" (its inverse: an authorised upgrade never gets applied, leaving all subsequent batch proofs to be verified against a stale/incorrect method id). This affects every full node and prover that later runs `run_circuit`/`run_l1_block` over that DA history — the drop is deterministic and baked into consensus state, so all honest light-client provers converge on the same (wrong) outcome, silently invalidating the council's intended upgrade path chain-wide and irrecoverably, since the appended stale entry can never be superseded by the correct one at a lower height.

### Likelihood Explanation
The attacker needs no privileged key: they only need (a) a previously published council-signed `BatchProofMethodId` body/signature bytes for any height H2 (public DA data, or leaked/pre-distributed for a future scheduled upgrade), and (b) the ability to pay Bitcoin fees to inscribe a transaction embedding that exact byte blob ahead of the genuine H1 inscription in the same block's transaction order — both explicitly allowed attacker capabilities. This is realistic whenever the council needs to schedule an urgent, sooner-activating fix (lower height) after already pre-signing/publishing a later-height upgrade, or whenever a stale signed body from a superseded upgrade schedule remains crypto-valid indefinitely (no expiry/nonce). Cost is a single low-value Bitcoin inscription fee.

### Recommendation
- Add the missing `blob.sender().as_ref() != method_id_upgrade_authority_da_public_key` style check (or an equivalent replay-protection mechanism, e.g. binding a monotonically increasing nonce/sequence into the signed body) to the `BatchProofMethodId` branch so arbitrary parties cannot re-inject old council bytes.
- Replace `.last()` with `iter().map(|(h,_)| h).max()` (or keep the vector sorted by height on insert and reject/queue out-of-order insertions) so the gating check reflects the true maximum accepted height regardless of DA transaction ordering within a block.
- Consider deduplicating/rejecting bodies whose exact bytes have already been accepted, to prevent any replay regardless of ordering tricks.
