### Title
Single-step account permission update in `AccountPermissionUpdateActuator` can permanently and irrecoverably lock an account's owner/active/witness permissions - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` overwrites an account's `owner`, `witness`, and `active` permission sets in a single atomic step, with no staged/two-step confirmation mechanism analogous to the two-step pattern the report recommends (as used e.g. in `NodeRegistry`). If the new `owner` permission is set to keys/threshold that cannot be satisfied by any address the caller actually controls, the account becomes permanently unable to authorize any further permission changes, effectively bricking the account.

### Finding Description
The actuator unpacks an `AccountPermissionUpdateContract` and immediately calls `AccountCapsule.updatePermissions()`, which replaces the account's `owner`, `witness`, and `active` permissions in one commit with no rollback or pending/confirmation state: [1](#0-0) 

The underlying capsule mutation is a direct, single-step overwrite of the owner permission (and witness/active permissions), with no mechanism requiring the new owner key(s) to first "accept" or prove control before the old permission is discarded: [2](#0-1) 

Validation in `validate()` only checks structural properties of the new permission set — key count bounds, distinct addresses, valid address format, threshold vs. weight-sum consistency, and permission-name length — but it cannot and does not verify that the account's owner actually controls the private keys being set as the new owner permission: [3](#0-2) 

Because the new owner/witness/active permission takes effect immediately upon a successful `execute()`, there is no opportunity to catch a mistake (e.g., a mistyped address, an unreachable key/threshold combination, or accidentally revoking the caller's own effective control) before it becomes irreversible — this mirrors exactly the bug class in the external report: single-step transfer of privileged control with no two-step confirmation safety net.

### Impact Explanation
Once the owner permission is overwritten with keys the account holder does not control (or with a threshold that can never practically be met), the account permanently loses the ability to sign further `AccountPermissionUpdateContract` transactions to correct itself, since the new owner permission is now required to authorize any subsequent owner-permission-level action. This can permanently disable multi-sig control, witness permission management, and any active permission requiring owner-level authorization for the account — a severe and irreversible loss of protocol functionality for the affected account, consistent with the "High" impact rating in the analogous report.

### Likelihood Explanation
Likelihood is low, since it requires a user/account-owner input error (wrong address, wrong threshold, or a duplicate/typo'd key) when constructing the `AccountPermissionUpdateContract`, exactly as characterized in the original report ("requires an admin/owner error"). Unlike the original `AccountRegistry`/`NodeRegistry` example this is not restricted to a privileged admin — it is reachable by any regular account holder that uses the multisig permission feature via `AccountPermissionUpdateActuator`, which is exposed through the standard wallet/API surface (`AccountPermissionUpdateServlet`).

### Recommendation
Introduce a two-step confirmation pattern for owner permission changes in `AccountPermissionUpdateActuator`/`AccountCapsule`: stage the proposed new owner (and witness/active) permission, and require an explicit acceptance transaction signed under the new permission before it replaces the existing one. This mirrors the two-step transfer already used in `NodeRegistry` per the original report and prevents accidental permanent loss of account control.

### Proof of Concept
1. Account `A` (multi-sig enabled) submits `AccountPermissionUpdateContract` setting `owner` permission to a `Key` with an address `X` for which `A` does not hold the private key (typo, wrong address, or hardware wallet not yet configured), with `threshold` satisfiable only by `X`.
2. `AccountPermissionUpdateActuator.validate()` passes because all structural checks (address format validity, key count, threshold ≤ weight-sum) succeed — there is no check possible for "does the submitter control this key." [4](#0-3) 
3. `execute()` calls `account.updatePermissions(...)` and commits the new owner permission in one step. [5](#0-4) 
4. Account `A` can no longer produce a valid signature satisfying the new owner permission threshold, and thus can never again submit a valid `AccountPermissionUpdateContract` to fix the mistake — the account's owner-level control is permanently lost.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
