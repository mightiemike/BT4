### Title
Head-of-line blocking in outgoing receipt buffer can permanently stall a shard's cross-shard receipts behind an oversized receipt - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The `PolicyBook` report describes a class of bug where a FIFO withdrawal queue can only be drained strictly in order, so a single large item at the head that cannot currently be satisfied blocks every smaller item behind it even when resources exist to serve them. The nearcore analog is the per-shard outgoing receipt buffer used by congestion control / the bandwidth scheduler: `ReceiptSinkV2::forward_from_buffer_to_shard` drains the buffer strictly FIFO and `break`s on the first receipt that cannot be forwarded, leaving every subsequent (potentially small, fully fundable) receipt stuck behind it indefinitely.

### Finding Description
`forward_from_buffer_to_shard` iterates a shard's outgoing receipt buffer in order and calls `try_forward` for each receipt against the current `OutgoingLimit{gas, size}` for the destination shard: [1](#0-0) 

Crucially, as soon as one receipt returns `ReceiptForwarding::NotForwarded`, the loop unconditionally `break`s instead of skipping ahead to smaller receipts that would still fit: [2](#0-1) 

The forwarding decision itself is a size+gas admission check against the receiver's per-chunk grant: [3](#0-2) 

The size budget (`forward_limit.size`) comes from `bandwidth_scheduler_output.granted_bandwidth`, which is capped per chunk by `max_single_grant`/`base_bandwidth` and only grows toward `max_allowance` gradually across chunks via `LinkAllowance`: [4](#0-3) 

If a receipt near `max_receipt_size` sits at the head of a shard's outgoing buffer (e.g., produced by a contract call that outputs a large cross-shard receipt), and the per-chunk bandwidth grant to that receiver shard is repeatedly consumed/limited (congestion, other links competing for `max_shard_bandwidth`, or the allowance simply not yet having accumulated enough for that link), the head receipt is not forwarded, and the loop breaks — meaning *every other receipt already queued behind it for that shard*, no matter how small, is also withheld this chunk. This repeats every chunk that the head item still doesn't fit, so a chain of otherwise-forwardable transfers/function-call receipts (which, from a user's perspective, look like "my funds/receipt is stuck") is delayed for as long as the head-of-line receipt is unforwardable. Unlike the delayed-receipt queue (which only stops because gas ran out for the whole chunk, and resumes immediately next chunk with fresh gas), this is a resource-specific ordering bug purely local to one (sender, receiver) shard pair, driven by bandwidth allocation, and is not bounded by "gas ran out" — it's bounded only by how the bandwidth scheduler happens to grant that particular link, which can be starved by contention on `max_shard_bandwidth` from many other sender shards targeting the same receiver.

### Impact Explanation
This does not cause loss of funds or supply inflation, but it matches the "permanently frozen funds"/liveness class from the report: a legitimate small receipt (e.g., a token transfer or a withdrawal-style receipt to another shard) can be held indefinitely behind a large unrelated receipt purely due to strict FIFO draining with no partial/skip-ahead semantics, exactly mirroring the `PolicyBook.sol` "no partial withdrawals when in the queue" defect. The user or dApp waiting on that receipt sees indefinite non-execution with no way to accelerate or bypass it, even though bandwidth exists for their receipt specifically.

### Likelihood Explanation
Reaching this requires only a single account submitting a function call (reachable by any unprivileged transaction signer or RPC caller) that produces a large outgoing receipt to some shard, followed by ordinary receipts to the same shard from any sender. No validator or network-level privilege is needed — an attacker could deliberately place an oversized (near `max_receipt_size`) receipt at the head of a target shard's outgoing buffer to grief other traffic destined for that shard, and repeat it to keep starving the link, since the code comment at `congestion_control.rs:413-427` already acknowledges receipts can exceed intended size limits ("There is a bug which allows to create receipts that are above the size limit"), which is the same size-limit "workaround" tracked as near/nearcore#12606.

### Recommendation
Do not `break` the buffer-forwarding loop on the first non-forwardable receipt; instead, continue attempting to forward subsequent smaller receipts in the same buffer while retaining FIFO order only for receipts destined through the exact same `(size, gas)` budget conflict, or reserve a minimum bandwidth slice per chunk specifically for advancing the queue past oversized head items. At minimum, bound how long a single receipt may occupy the head of the buffer (e.g., prioritizing partial/size-limited forwarding of the head item across chunks, similarly to how the oversized-receipt clamp at `congestion_control.rs:417-427` already treats it as `max_receipt_size` for admission) so the queue behind it is never starved beyond a deterministic number of chunks.

### Proof of Concept
1. Deploy/call a contract on shard A that produces one outgoing receipt to shard B sized close to `wasm_config.limit_config.max_receipt_size` (e.g., large `FunctionCall` args or many actions batched into one receipt) — this lands in `outgoing_buffers.to_shard(B)` via `buffer_receipt` after `try_forward` returns `NotForwarded` due to insufficient current-chunk size grant.
2. Immediately submit several ordinary, small transactions from other accounts on shard A that also produce receipts to shard B (e.g., plain token transfers).
3. Because `forward_from_buffer_to_shard` (`congestion_control.rs:338-385`) drains strictly FIFO and `break`s at the first `NotForwarded` result, the large receipt stays at the head and is retried each chunk; the small receipts queued behind it in the same shard-B buffer are never even attempted until the large one succeeds, even on chunks where `forward_limit.size`/`forward_limit.gas` would have been more than sufficient for them individually.
4. Repeat submitting large receipts targeting shard B before the previous one clears (or rely on natural `max_shard_bandwidth` contention from other senders to B) to keep the link's granted bandwidth below what's needed for the head item, extending the stall on the smaller queued receipts across many chunks.

    fn forward_from_buffer_to_shard(
        &mut self,
        buffer_shard_id: ShardId,
        state_update: &mut TrieUpdate,
        apply_state: &ApplyState,
        shard_layout: &ShardLayout,
    ) -> Result<(), RuntimeError> {
        let mut num_forwarded = 0;
        let mut outgoing_metadatas_updates: Vec<(ByteSize, Gas)> = Vec::new();
        for receipt_result in
            self.outgoing_buffers.to_shard(buffer_shard_id).iter(&state_update.trie, true)
        {
            let receipt = receipt_result?;
            let gas = receipt_congestion_gas(&receipt, &apply_state.config)?;
            let size = receipt_size(&receipt)?;
            let should_update_outgoing_metadatas = receipt.should_update_outgoing_metadatas();
            let receipt = receipt.into_receipt();
            let target_shard_id = receipt.receiver_shard_id(&shard_layout)?;

            match Self::try_forward(
                receipt,
                gas,
                size,
                target_shard_id,
                &mut self.outgoing_limit,
                &mut self.outgoing_receipts,
                apply_state,
                &mut self.stats,
            )? {
                ReceiptForwarding::Forwarded => {
                    self.own_congestion_info.remove_receipt_bytes(size)?;
                    self.own_congestion_info.remove_buffered_receipt_gas(gas.as_gas().into())?;
                    if should_update_outgoing_metadatas {
                        // Can't update metadatas immediately because state_update is borrowed by iterator.
                        outgoing_metadatas_updates.push((ByteSize::b(size), gas));
                    }
                    // count how many to release later to avoid modifying
                    // `state_update` while iterating based on
                    // `state_update.trie`.
                    num_forwarded += 1;
                }
                ReceiptForwarding::NotForwarded(_) => {
                    break;
                }
            }
        }

        self.outgoing_buffers.to_shard(buffer_shard_id).pop_n(state_update, num_forwarded)?;

    fn try_forward(
        receipt: Receipt,
        gas: Gas,
        mut size: u64,
        shard: ShardId,
        outgoing_limit: &mut HashMap<ShardId, OutgoingLimit>,
        outgoing_receipts: &mut Vec<Receipt>,
        apply_state: &ApplyState,
        stats: &mut ReceiptSinkStats,
    ) -> Result<ReceiptForwarding, RuntimeError> {
        // There is a bug which allows to create receipts that are above the size limit. Receipts
        // above the size limit might not fit under the maximum outgoing size limit. Let's pretend
        // that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
        // See https://github.com/near/nearcore/issues/12606
        let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
        if size > max_receipt_size {
            tracing::debug!(
                target: "runtime",
                receipt_id=?receipt.receipt_id(),
                size,
                max_receipt_size,
                "try_forward observed a receipt with size exceeding the size limit",
            );
            size = max_receipt_size;
        }

        // Default case set to `Gas::MAX`: If no outgoing limit was defined for the receiving
        // shard, this usually just means the feature is not enabled. Or, it
        // could be a special case during resharding events. Or even a bug. In
        // any case, if we cannot know a limit, treating it as literally "no
        // limit" is the safest approach to ensure availability.
        let default_gas_limit = Gas::MAX;

        // Since bandwidth scheduler, a shard is not allowed to send any receipts if it doesn't have a grant.
        let default_size_limit = 0;

        let default_outgoing_limit =
            OutgoingLimit { gas: default_gas_limit, size: default_size_limit };
        let forward_limit = outgoing_limit.entry(shard).or_insert(default_outgoing_limit);

        let admission_gas = if ProtocolFeature::ClampOutgoingGasAdmission
            .enabled(apply_state.current_protocol_version)
        {
            gas.min(apply_state.config.congestion_control_config.allowed_shard_outgoing_gas)
        } else {
            gas
        };

        if forward_limit.gas >= admission_gas && forward_limit.size >= size {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "forwarding buffered receipt");
            outgoing_receipts.push(receipt);
            forward_limit.gas = forward_limit.gas.saturating_sub(gas);
            forward_limit.size -= size;
            stats.forwarded_receipts.entry(shard).or_default().add_receipt(size, gas);

            Ok(ReceiptForwarding::Forwarded)
        } else {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "not forwarding buffered receipt");
            Ok(ReceiptForwarding::NotForwarded(receipt))
        }

/// Parameters used in the bandwidth scheduler algorithm.
#[derive(Clone, Copy, Debug, PartialEq, Eq, BorshSerialize, BorshDeserialize, ProtocolSchema)]

    /// This much bandwidth is granted by default.
    /// base_bandwidth = (max_shard_bandwidth - max_single_grant) / (num_shards - 1)
    pub base_bandwidth: Bandwidth,
    /// The maximum amount of data that a shard can send or receive at a single height.
    pub max_shard_bandwidth: Bandwidth,
    /// The maximum amount of bandwidth that can be granted on a single link.
    /// Should be at least as big as `max_receipt_size`.
    pub max_single_grant: Bandwidth,
    /// Maximum size of a single receipt.
    pub max_receipt_size: Bandwidth,
    /// Maximum bandwidth allowance that a link can accumulate.

}
