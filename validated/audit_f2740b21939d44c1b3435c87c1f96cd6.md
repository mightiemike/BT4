### Title
Active-permission holder can rewrite an account's owner/witness/active permissions via `AccountPermissionUpdateContract` - (`actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The analog of the ODSafeManager `allowSAFE()`/`safeAllowed()` flaw exists in TRON's multi-signature permission system. A non-owner "active" key that an account owner delegates limited authority to can be granted (deliberately or by mistake/tooling default) the ability to execute `AccountPermissionUpdateContract`. Because the actuator's authorization boundary is checked purely against a broad `AvailableContractType` bitmap rather than being hard-restricted to the `owner` permission (id 0), that delegated key can then rewrite the account's `owner`, `witness`, and `active` permissions in a single transaction — including replacing the real owner's key entirely — without ever needing the true owner's signature.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unconditionally applies whatever `owner`/`witness`/`actives` permissions are contained in the `AccountPermissionUpdateContract` to the target account: [1](#0-0) 

`validate()` performs structural checks on the new permissions (key counts, thresholds, name length, operations bitmap) but never checks whether the transaction's signer/permission is the *current* owner permission versus some other (e.g. `active`) permission that merely has this contract type enabled in its operations: [2](#0-1) 

Whether a given active permission is authorized to sign an `AccountPermissionUpdateContract` transaction is decided by the operations bitmap check inside `checkPermission()`, which validates the requested operations bits are a subset of `dynamicStore.getAvailableContractType()`: [3](#0-2) 

Crucially, `AvailableContractType` (the ceiling of what CAN be granted to any permission) includes `AccountPermissionUpdateContract`, while the safer `ActiveDefaultOperations` (the DEFAULT bitmap used when an account is created) explicitly excludes it — confirmed directly by the codebase's own regression tests, which special-case-skip `ContractType.AccountPermissionUpdateContract` only when computing the default-active-operations bitmap, not when computing the available-contract-type ceiling: [4](#0-3) 

This asymmetry (excluded from safe defaults, but permitted in the broader ceiling with no additional structural safeguard) means nothing in `AccountPermissionUpdateActuator` prevents an owner-defined `active` permission from being granted (intentionally or by a permissive template/UI default) the `AccountPermissionUpdateContract` bit. Signature validation for contracts is resolved purely from `contract.getPermissionId()` against the account's stored permission set: [5](#0-4) 

Once such an active permission exists, its key holder(s) — who were only meant to have scoped/limited operational rights — can broadcast an `AccountPermissionUpdateContract` themselves (using `permission_id` referencing their own active permission) and replace the account's `owner` permission with keys of their choosing, exactly mirroring the ODSafeManager pattern where an approved delegate could grant/escalate permissions beyond what the owner intended, up to and including displacing the original owner.

### Impact Explanation
A holder of a delegated `active` permission that has (deliberately, accidentally, or via a copy of a template that mirrors `AvailableContractType` instead of `ActiveDefaultOperations`) the `AccountPermissionUpdateContract` operation bit set can single-handedly seize full control of the victim account: reassign `ownerPermission` to itself, remove the legitimate owner's keys, and add/alter `witness`/`active` permissions — without the true owner ever signing. This is a full account takeover / unauthorized privilege escalation, directly matching the accepted C4 finding pattern ("approved address can approve other addresses for an owner's safe").

### Likelihood Explanation
Like the original finding (rated Medium because it is "contingent on the owner granting permissions to an address that becomes malicious"), this TRON analog similarly requires that the account owner (or supporting wallet/dApp tooling) at some point sets an `active` permission's operations to include `AccountPermissionUpdateContract` — which the protocol allows (`AvailableContractType` includes it) even though the safe default deliberately excludes it. Given that permission configuration is exposed through the public HTTP/gRPC API (`AccountPermissionUpdateServlet`, `RpcApiService`) and operations bitmaps are raw 32-byte fields with no additional guardrail or explicit warning/restriction against including this specific contract type, misconfiguration by wallets, custodial services, or social-engineered "convenience" permission grants is a realistic and reachable vector.

### Recommendation
Add an explicit, protocol-level restriction in `AccountPermissionUpdateActuator.validate()`/`checkPermission()` (and in the `AvailableContractType` ceiling check) that forbids `ContractType.AccountPermissionUpdateContract` from ever being set in the operations bitmap of any non-owner permission (`active`/`witness`), rather than only excluding it from the *default* bitmap. This closes the gap between the "safe default" and the "permitted ceiling" and ensures only the true `owner` permission (id 0) can ever modify account permissions, matching the original recommendation of a dedicated owner-only guard (`onlySafeOwner`-style check) instead of a broadly permissive modifier/bitmap.

### Proof of Concept
1. Owner creates/updates account permissions granting an `active` permission P (threshold 1, single key = attacker address) with an operations bitmap that has the `AccountPermissionUpdateContract` bit set (allowed because `AvailableContractType` includes it) — e.g., owner uses a wallet/tool that defaults operations to `AvailableContractType` instead of `ActiveDefaultOperations`.
2. Attacker (holder of the active key P) crafts an `AccountPermissionUpdateContract` with `permission_id` = P's id, setting a new `owner` permission whose only key is the attacker's address.
3. Attacker signs and broadcasts the transaction; `TransactionCapsule.validateSignature` resolves permission P via `getPermissionById(permissionId)` and validates the signature/threshold against P only — the true owner's signature is never required, per [5](#0-4) .
4. `AccountPermissionUpdateActuator.execute()` applies the new owner permission unconditionally via `account.updatePermissions(...)`, per [1](#0-0) , giving the attacker full ownership of the account.

Note: I was unable to fully inspect the body of `checkPermission(int permissionId, Permission permission, Contract contract)` in `TransactionCapsule.java` (only its call site was retrieved before running out of tool calls), so the precise bit-check logic tying a `permissionId`'s operations bitmap to the broadcast transaction's `ContractType` is inferred from the actuator's own bitmap validation pattern and codebase test comments rather than directly confirmed line-by-line. If this inference is incorrect (e.g., if a hard-coded owner-only restriction exists elsewhere that was not surfaced by search), this finding should be treated as unconfirmed pending direct review of that method.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
