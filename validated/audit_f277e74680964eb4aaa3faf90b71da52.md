### Title
Front-runnable "account already exists" check in `CreateAccountActuator` allows permanent DoS of a target address's account-creation intent - (File: actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java)

### Summary
`CreateAccountActuator.validate()` lets any signer create an `AccountCreateContract` naming an arbitrary `account_address` field that is completely unrelated to the signer's own key. The only guard against abuse is a single "already exists" check on that target address [1](#0-0) . Exactly like the InstaDApp `build()`/`setOwner()` front-run described in the external report, an attacker can observe a not-yet-broadcast (or even not-yet-created) legitimate `AccountCreateContract` targeting address `X` and race it with their own `AccountCreateContract`(or a fee-free `TransferContract`) that creates an entry for `X` first, permanently causing the legitimate transaction to revert with `"Account has existed"`.

### Finding Description
`account_address` in `AccountCreateContract` is attacker-controlled and never checked against a signature or any binding to the caller [2](#0-1) . The sole collision guard is:
```
if (accountStore.has(accountAddress)) {
  throw new ContractValidateException("Account has existed");
}
``` [3](#0-2) 

This mirrors the pattern in the report exactly: a "create at address" operation whose only defense against front-running is a not-yet-exists check, with no address-ownership proof (no "pending owner must accept" style two-step protocol, no signature over the target address). Anyone monitoring the mempool for an `AccountCreateContract` transaction destined for address `X` (or anyone who simply wants to grief a known future address, e.g., a CREATE2-predicted contract address, a deterministic HD-wallet address, or an address publicized ahead of time) can submit their own `AccountCreateContract` (or a `TransferContract`/any value-moving contract, which auto-creates the account entry as shown in `BandwidthProcessor.contractCreateNewAccount`) naming `X` first [4](#0-3) . Once any entry exists at `X` in the `AccountStore`, the legitimate, intended `AccountCreateContract(account_address = X)` will permanently fail validation with `"Account has existed"`, exactly as `setOwner(X)` permanently reverts at InstaRegistry line 139 once `proxies[X] != UserWallet(0)`.

### Impact Explanation
This is reachable from any anonymous broadcast transaction with no privileges required — it is a pure griefing/front-running primitive against the `AccountCreateContract` actuator. The impact is a permanent, unrecoverable denial of service on the ability to explicitly initialize account state (custom account type/name at creation time) for a chosen address once an attacker has squatted it, matching the report's "DoS of setter functionality via a pre-emptive existence claim" bug class. It does not compromise key custody or funds (TRON account authority is derived from the ECDSA keypair, not from the `AccountStore` entry), so the severity is bounded to denial-of-service of the creation-time customization feature rather than fund theft.

### Likelihood Explanation
High likelihood of exploitability but low motivation/value for an attacker: the front-run costs only the `CreateAccountFee`/transfer fee, is fully deterministic (no guesswork needed since `account_address` is explicit in the plaintext transaction, visible to mempool watchers), and requires no special permissions. However, actual attacker incentive is limited because squatting an address does not grant control over funds sent there or over spending authority, which is why the practical impact is lower than the referenced UserWallet ownership-hijack scenario.

### Recommendation
Require that `account_address` in `AccountCreateContract` be verified via the account's own signature (i.e., the account being created must co-sign or be identical to `owner_address`), or otherwise remove the arbitrary-target-address creation capability so an unrelated third party cannot pre-empt account initialization for an address it does not control. Alternatively, treat "account already exists but not yet explicitly initialized" as an idempotent success rather than a hard validation failure when the acting `owner_address` matches the address's would-be controller, avoiding the InstaDApp-style front-run DoS.

### Proof of Concept
1. Attacker monitors the mempool/observes that address `X` (owned by victim) is expected to be initialized via `AccountCreateContract`.
2. Attacker broadcasts `AccountCreateContract{owner_address = attacker, account_address = X}` (or simply sends TRX to `X` via `TransferContract`), which is mined first.
3. Victim's legitimate `AccountCreateContract{owner_address = victim-controller, account_address = X}` is submitted and hits `CreateAccountActuator.validate()`'s `accountStore.has(accountAddress)` check [3](#0-2) , permanently reverting with `"Account has existed"` — the victim can never use `AccountCreateContract` to set the intended type/name for `X`.
