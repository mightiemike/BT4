## Title
`socialize-debt` in the vaults uses stale, un-accrued `total-assets` instead of the accrued `total-assets-preview`, causing an incorrect liquidity-index write-down for un-recently-touched vaults during bad-debt socialization - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Each vault (e.g. `v0-vault-usdc.clar`, `v0-vault-stx.clar`, etc.) maintains two different formulas for "total assets": `total-assets`, which uses the currently stored `index` with no time-elapsed accrual, and `total-assets-preview`, which uses `debt-preview`/`next-index` to account for interest accrued since `last-update`. Deposit/redeem/accrue paths consistently use the accrued preview formula, but `socialize-debt` — the function that writes down the liquidity index (`lindex`) when bad debt is socialized — uses the stale, non-accrued `total-assets` formula. Because the market's bad-debt-socialization loop (`socialize-debt-asset` in `market.clar` / `v0-4-market.clar`) calls `vault-socialize-debt` **before** calling `vault-accrue` for each affected debt asset, any vault that was not already brought current earlier in the same liquidation call will compute `old-total-assets` using a stale, understated debt/asset figure. This mirrors the IdleCDO bug class: two divergent implementations of the same accounting quantity used inconsistently across code paths, leading to accounting-invariant violations.

### Finding Description
In `mainnet/contracts/vault/v0-vault-usdc.clar` (and the analogous `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`): [1](#0-0) 

```
(define-private (total-debt)
  (calc-cumulative-debt (var-get principal-scaled) (var-get index)))
(define-private (debt-preview)
  (calc-cumulative-debt (var-get principal-scaled) (next-index)))
(define-private (total-assets)
  ... uses (total-debt) — stale index, no elapsed-time accrual ...)
(define-private (total-assets-preview)
  ... uses (debt-preview) — accounts for elapsed time since last-update ...)
```

`total-assets` is only correct at the exact moment `accrue` was last called (i.e., when `index == next-index`, meaning `time-delta` since `last-update` is zero). Every other public entrypoint (`deposit`, `redeem`, `accrue` itself when minting treasury shares) is careful to call `accrue()` first and then use the `*-preview` variants, so `total-assets`/`total-assets-preview` are kept consistent along those code paths.

`socialize-debt`, however, does **not** call `accrue()` first, and uses the stale `total-assets`: [2](#0-1) 

```
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))          ;; <-- stale formula, no accrual
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        ...
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
    ...
    (var-set lindex new-lindex)
    ...))
```

The caller in the market contract, `socialize-debt-asset`, invokes `vault-socialize-debt` for each debt asset **before** it calls `vault-accrue` to refresh the vault's index: [3](#0-2) 

```
(define-private (socialize-debt-asset ...)
  ...
        ;; Socialize in vault - pass scaled directly to avoid rounding
        (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
        ;; Refresh cache with new indexes post-write-down (lindex decreased)
        (map-set index-cache
                 { timestamp: stacks-block-time, aid: asset-id }
                 (unwrap! (vault-accrue asset-id) failed-status))
        ...)
```

This fold is applied to `fresh-debt-list` (all remaining debt assets of the liquidated borrower), not only the single `debt-aid` asset that was just repaid via `vault-system-repay` inside `liquidate` (which does call `accrue()` first). For any *other* debt asset the borrower owes (multi-asset borrower), the corresponding vault's `last-update` may be stale from an earlier block/period with no recent interaction — its `index`/`lindex` have not been advanced to reflect elapsed time. `socialize-debt` for that vault therefore computes `old-total-assets` using the stale (understated) `total-debt`, rather than the true, interest-accrued `total-assets-preview`.

### Impact Explanation
Because `old-total-assets` is understated relative to the real, interest-accrued total assets of the vault, the ratio `(old-total-assets - debt-reduction) / old-total-assets` used to compute `new-lindex` is smaller than it should be. This causes `lindex` (the liquidity index that determines how much underlying each zToken share is redeemable for) to be written down more severely than the actual bad-debt loss warrants. Every zToken holder of that vault (not just the liquidated borrower) permanently loses more value than the true proportional loss — a permanent, protocol-caused freezing/loss of legitimate depositor yield/principal that is baked into `lindex` and propagates through all future `convert-to-assets` calls for that vault. This lands in the in-scope impact category of "permanent freezing of funds" (and effectively theft of yield/principal for uninvolved depositors), since the mis-write-down of `lindex` can never be self-corrected once persisted.

### Likelihood Explanation
This triggers any time a liquidation results in bad-debt socialization (`liquidate` → `no-collateral-left` → `socialize-debt-asset` fold) for a borrower who holds debt in more than one asset, where at least one of those debt assets' vault has not been recently `accrue`d (i.e., time has passed since its `last-update` due to low activity on that particular vault). This is a realistic, not contrived, scenario — bad debt socialization for multi-asset borrowers on less-active vaults (e.g., zUSDH, zsBTC) is exactly the kind of low-traffic vault where `last-update` staleness is common. No malicious actor collusion or privileged access is required; it occurs as a natural side effect of the existing liquidation flow's ordering (`vault-socialize-debt` before `vault-accrue`).

### Recommendation
Have `socialize-debt` call `accrue()` first (as `deposit`/`redeem`/`system-borrow`/`system-repay` already do) before computing `old-total-assets`, and use the accrued `total-assets-preview` value consistently — mirroring the fix pattern applied in the IdleCDO report, where a single canonical accounting function should be used everywhere the same quantity is needed. Alternatively, reorder `socialize-debt-asset` in the market contract to call `vault-accrue` for `asset-id` before `vault-socialize-debt`, ensuring the vault's index/lindex are current before the write-down calculation.

### Proof of Concept
1. Borrower B opens debt positions in two assets: `USDC` (vault A) and `USDH` (vault B), backed by collateral in a third asset.
2. Vault B (USDH) sees little activity for an extended period — no `deposit`/`redeem`/`accrue`-triggering call occurs, so its `last-update` lags behind `stacks-block-time` while `interest-rate` continues to accrue conceptually (i.e., `next-index` for vault B would be materially larger than the stored `index`).
3. Collateral price for B's collateral asset crashes; a liquidator calls `liquidate` targeting B's USDC debt. `vault-system-repay` for USDC is called (which does call `accrue()` for the USDC vault, so that vault's own state stays consistent), collateral is fully seized, and `no-collateral-left` is true, and B still has remaining USDH debt.
4. `socialize-debt-asset` is folded over the remaining debt list, including the USDH entry. For the USDH vault, `vault-socialize-debt` is invoked (`socialize-debt` in `v0-vault-usdh.clar`) **before** `vault-accrue` for that vault. Inside `socialize-debt`, `(total-assets)` is computed off the stale `index`, understating the vault's true total assets (accrued interest owed by other USDH borrowers is omitted).
5. `new-lindex` is computed as `current-lindex * (old-total-assets - debt-reduction) / old-total-assets` using the understated denominator, producing a `lindex` write-down larger than the borrower's actual proportional bad debt relative to the vault's true (accrued) asset base.
6. This new, over-written-down `lindex` is persisted (`var-set lindex new-lindex`) and only afterward is `vault-accrue` called by the market to refresh the cache — but `accrue()` will treat `lindex` as already current (no further adjustment reverses the excess write-down). All zUSDH holders now redeem for permanently less underlying than warranted by the actual bad debt event.

Note: I was unable to fully trace every call site that might already normalize vault state right before `socialize-debt-asset` runs (e.g., whether any other periodic/global accrue sweep exists across all vaults before liquidation) within the indexed context available; if such a global sweep exists elsewhere in the market contract, it could mitigate this specific likelihood, and a full Devin session with complete file access would be needed to confirm no earlier `accrue` call exists for every debt asset in `fresh-debt-list`.
