### Title
`calculate_allocated_accounts_data_size` in the cost model omits account-data growth performed via CPI/program self-realloc, letting a single transaction's real storage growth bypass the per-block accounts-data-size cap - (File: cost-model/src/cost_model.rs)

### Summary
The Stylus `MemoryGrow` bug is a case where a code path that legitimately grows a resource (WASM linear memory) is priced by a generic/low fallback cost instead of a cost proportional to the actual growth, because the pricer defers costing to a different subsystem that doesn't handle that specific case. Agave's cost model has an analogous gap: `CostModel::calculate_allocated_accounts_data_size` (which feeds the per-block "accounts data size delta" budget) only assigns a non-zero size to *top-level* System Program instructions (`CreateAccount`, `Allocate`, etc.). Any account-data growth performed by a BPF program itself (via `AccountInfo::resize`/realloc, optionally through CPI) is invisible to this accounting function and is costed as `0`.

### Finding Description
`CostModel::calculate_account_data_size_on_instruction` only inspects the `program_id` of each *top-level* instruction and, unless it is exactly `system_program::id()`, unconditionally returns `SystemProgramAccountAllocation::None`: [1](#0-0) 

`calculate_allocated_accounts_data_size` sums these per-instruction allocations and clamps the result to `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION`, producing the `allocated_accounts_data_size` field used for block-level accounting: [2](#0-1) 

However, an SBF program can grow an account's data directly (via the `resize`/realloc syscall path exposed to programs), without the top-level instruction being a System Program instruction at all — the program itself is the top-level `program_id` invoked by the transaction, and it performs the realloc internally (optionally via CPI to itself or another custom program). This is exactly what the `realloc` test program demonstrates: `account.resize(new_len)` grows account data with no System Program instruction present in the top-level instruction list: [3](#0-2) 

Because `calculate_account_data_size_on_instruction` returns `None` for any non-system-program top-level instruction, this growth contributes `0` to `allocated_accounts_data_size`, even though the growth is real, is bounded per-instruction only by `MAX_PERMITTED_DATA_INCREASE`, and is enforced/tracked at the transaction-account level via `resize_delta`/`can_data_be_resized`: [4](#0-3) 

This mirrors the reported bug class precisely: the generic per-opcode/per-instruction pricer defers to a specialized path for the real cost (here, `allocated_accounts_data_size` deferring to "the accounts data size is computed from System Program instructions"), but that specialized path does not cover a legitimate way of triggering the same resource growth (self-realloc via BPF program), so the operation ends up priced as if it allocated zero bytes.

### Impact Explanation
`allocated_accounts_data_size` is the quantity compared against `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100,000,000 bytes) to cap how much new account data storage can be created per block: [5](#0-4) 

Since program-driven reallocs are invisible to this counter, an attacker can submit many transactions that each invoke an arbitrary owned/writable program performing large `resize()` calls (up to `MAX_PERMITTED_DATA_INCREASE` per instruction, and further via nested CPI reallocs as exercised in `programs/sbf/rust/realloc_invoke`), all counted as `0` toward the block's accounts-data-size delta budget. This lets a leader/validator accept real account-data growth (and the associated AccountsDB storage growth, snapshot growth, and downstream shrink/hash work) far beyond what `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` is meant to bound, producing disproportionate storage and CPU cost relative to what the cost model accounted for — the same "resource exhaustion via underpriced growth operation" pattern as the reported `MemoryGrow` issue.

### Likelihood Explanation
This requires no privileged role: any unprivileged user can deploy or reuse an existing writable-account-owning program that calls `resize`, and repeatedly submit ordinary transactions invoking it as the top-level instruction. No validator/operator cooperation, malicious snapshot, or multiple-client assumption is needed, and it is a per-transaction cost-accounting gap rather than a metrics/Geyser/Alpenglow/Loader-V4/RPC issue, keeping it within the stated scope.

### Recommendation
Extend `calculate_allocated_accounts_data_size` (or the surrounding block accounts-data-size accounting) to account for account-data growth caused by non-System-Program instructions as well — e.g., by using the actual measured `resize_delta` from `TransactionAccounts` (already tracked per-transaction) for the executed-cost path (`calculate_cost_for_executed_transaction`) rather than relying solely on statically inspecting top-level System Program instructions, so growth performed by arbitrary programs is not systematically priced at zero.

### Proof of Concept
1. Deploy (or reuse) a program like `programs/sbf/rust/realloc` whose entrypoint calls `account.resize(new_len)` directly on an account it owns.
2. Submit a transaction whose sole top-level instruction invokes that program with `new_len` set near `MAX_PERMITTED_DATA_INCREASE`.
3. Observe that `CostModel::calculate_account_data_size_on_instruction` returns `SystemProgramAccountAllocation::None` for this instruction (its `program_id` is not `system_program::id()`), so `calculate_allocated_accounts_data_size` returns `0` for the transaction: [6](#0-5) 
4. Repeat across many transactions/blocks: each grows real account data (verified in `runtime/src/bank/tests.rs::test_accounts_data_size_and_resize_transactions`, which shows `bank.load_accounts_data_size()` increasing on such resize transactions) while contributing nothing to the tracked `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` budget: [7](#0-6)

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

    pub(crate) fn update_accounts_resize_delta(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        let accounts_resize_delta = self.resize_delta.get();
        self.resize_delta.set(
            accounts_resize_delta.saturating_add((new_len as i64).saturating_sub(old_len as i64)),
        );
        Ok(())
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
