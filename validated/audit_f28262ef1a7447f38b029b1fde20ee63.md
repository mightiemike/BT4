### Title
Unsanitized Internal Exception Details Disclosed to Unauthenticated Callers via HTTP API Servlets - ([File: framework/src/main/java/org/tron/core/services/http/TriggerSmartContractServlet.java])

### Summary
Multiple java-tron HTTP API servlets return raw Java exception messages — and in one case the fully-qualified exception class name — directly to unauthenticated HTTP callers instead of a sanitized, generic error. This is the same bug class as the reported MongoDB verbose error disclosure: internal implementation details (exception types, validation logic internals, parsing library behavior) leak to any anonymous caller who can reach the FullNode/SolidityNode HTTP API, aiding fingerprinting and attack-surface mapping.

### Finding Description
`TriggerSmartContractServlet.doPost` catches any non-`ContractValidateException` and builds the response message as the literal string concatenation of the exception's Java class and its raw message: [1](#0-0) 

This value is placed into the `Return` protobuf and serialized straight back to the caller via `Util.printTransactionExtention`, so any anonymous HTTP client calling `/wallet/triggersmartcontract` with malformed `fee_limit`, `call_value`, `function_selector`/`function_parameter`, or address fields receives the internal Java exception class name plus message.

Other servlets similarly forward `e.getMessage()` (or the generic `Util.processError` → `Util.printErrorMsg` path) unsanitized to the client, e.g.: [2](#0-1) [3](#0-2) 

and the shared error path used by dozens of servlets (`GetAssetIssueByIdServlet`, `GetBlockServlet`, `GetExchangeByIdServlet`, `CreateCommonTransactionServlet`, etc.): [4](#0-3) 

Because these endpoints accept arbitrary attacker-controlled input (hex strings, JSON, numeric parameters) and propagate raw `getMessage()`/class-name output on parse or validation failure (e.g. `NumberFormatException`, `DecoderException` decode errors, `InvalidParameterException`, reflection `InvocationTargetException` wrapping), an attacker can iteratively probe malformed inputs and observe internal exception types/messages, exactly mirroring the reported behavior of feeding malformed `query`/`page`/`limit` values into the MongoDB-backed feed endpoint to harvest driver/engine-specific error text.

### Impact Explanation
This does not by itself allow fund theft, consensus divergence, or RCE, but it does:
- Fingerprint internal library/technology choices (e.g., BouncyCastle `DecoderException` messages, reflection `InvocationTargetException` wrapping in `CreateCommonTransactionServlet`, protobuf/JsonFormat parse exception text) to unauthenticated remote callers.
- Reveal internal validation branch structure (which field failed, in what order, and with what internal Java type), materially reducing the effort needed to craft further targeted exploitation attempts against the FullNode/SolidityNode HTTP API — the same "attack surface expansion" impact called out in the report.
This matches Medium severity under the same reasoning as the original report: it's an information-disclosure issue that lowers the bar for subsequent attacks rather than a direct compromise.

### Likelihood Explanation
High likelihood of triggering: these are unauthenticated, publicly documented HTTP API endpoints (`/wallet/triggersmartcontract`, `/wallet/gettransactionbyid`, etc.) reachable by any anonymous client, and the malformed-input paths (bad addresses, bad hex, bad numeric fields) are trivial to construct, requiring no special privileges or timing.

### Recommendation
- Route all servlet exception handling through a single centralized handler that returns a generic message plus a correlation/trace ID, never the raw `Throwable.getMessage()`/`getClass()` output.
- In particular, remove the `e.getClass() + " : " + errString` construction in `TriggerSmartContractServlet` and replace with a generic `OTHER_ERROR` message; log full exception details server-side only.
- Apply the same sanitization to the direct `e.getMessage()` writes in `GetTransactionByIdSolidityServlet` and `GetTransactionInfoByIdSolidityServlet`, and audit all other servlets using ad hoc `catch` blocks instead of `Util.processError`.

### Proof of Concept
```
POST /wallet/triggersmartcontract
{
  "owner_address": "<valid>",
  "contract_address": "<valid>",
  "function_selector": "transfer(address,uint256)",
  "function_parameter": "not-a-valid-hex-parameter",
  "fee_limit": 1000000
}
```
`Util.parseMethod`/`ByteArray.fromHexString` throws on malformed hex, which is caught by the generic `catch (Exception e)` block in `TriggerSmartContractServlet.doPost`, and the response `message` field contains `e.getClass() + " : " + errString` — the internal Java exception class name and message returned as plain JSON to the anonymous caller.
