### Title
Unbounded `PendingInbounds` scan in inbound-ballot-terminal hook enables inbound-vote DoS via cheap external deposits - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
The Paladin `MultiRangeHook` bug is a case of a permissionless action (range creation) inflating an array that a later, routine hot-path operation (`afterSwap`) must iterate in full, causing out-of-gas DoS. The closest analog in this repo is `x/uexecutor/keeper/ballot_hooks.go`'s `afterInboundBallotTerminal`, which performs a full linear `Walk` over the entire `PendingInbounds` collection on **every** inbound ballot termination, just to locate the entry containing a given `ballot_id`.

### Finding Description
`PendingInbounds` is created the moment the first Universal Validator votes an observed source-chain event via `MsgVoteInbound` [1](#0-0) . An unprivileged, external, unprivileged actor can cheaply generate an unbounded number of distinct genuine bridge/gateway events on a connected external chain (e.g., many minimal-value deposits), each with a unique `sha256(source_chain:tx_hash:log_index)` key, forcing a corresponding number of concurrent `PendingInbounds` entries while votes are in flight. When any one ballot (for any inbound, from any chain) reaches a terminal state, `x/uvalidator`'s generic ballot machine invokes `BallotHooks.AfterBallotTerminal`, which for `INBOUND_TX` ballots calls `afterInboundBallotTerminal`. That function does:

```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [2](#0-1) 

This scan is O(n) in the total number of currently pending inbounds (and their variants) rather than O(1) via direct key lookup, and it fires on **every** terminal ballot transition system-wide — not just for the entry being resolved. The code's own comment concedes the assumption that "[t]he pending set is small and transient" [3](#0-2) , which is exactly the invariant an attacker can violate by flooding cheap source-chain deposits faster than validator voting/finalization can drain them.

### Impact Explanation
If an attacker inflates `PendingInbounds` to a large size, every subsequent `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/TSS vote that causes *any* ballot to reach a terminal state pays an ever-growing store-iteration cost inside the same message-handling call (since the hook runs synchronously inside vote processing, not in an async worker). Because these vote messages are gasless [4](#0-3) , they still consume block/tx gas even though no fee is deducted; a sufficiently large `PendingInbounds` set could push individual vote transactions toward gas-limit failures, stalling inbound finalization broadly (a chain-wide DoS on universal execution, not just the attacker's own inbound), which matches the "denial of service ... reachable without privileged control" allowed-impact category. This does not directly steal or corrupt funds, so its severity is capped at availability degradation of the inbound-finalization pipeline rather than a fund-safety break.

### Likelihood Explanation
Likelihood is moderate-to-low: generating many external-chain deposit events costs the attacker real gas/fees on the source chain, and `PendingInbounds` entries are removed as soon as ballots terminate, so an attacker needs to sustain a flood faster than validators can finalize votes to keep the set large. There is no on-chain rate limit or cap on concurrent pending inbounds, and no code path evicts stale entries other than normal ballot termination, so a sustained flood is achievable without any privileged access — unlike the Solidity report where range creation was free, here the cost is external-chain gas, which raises the bar but does not eliminate the vulnerability class.

### Recommendation
Replace the linear `PendingInbounds.Walk` scan-by-ballot-ID with a direct secondary index (e.g., a `Map[ballotID]string` mapping ballot IDs to their owning `PendingInbounds` key), eliminating the O(n) scan entirely. Additionally, consider bounding the number of concurrent `PendingInbounds`/variants per chain (or enforcing minimum bridged-value thresholds) so that cheap high-frequency low-value deposits cannot inflate this set arbitrarily, mirroring the "maximum of five ranges per pool" mitigation Paladin applied to `MultiRangeHook`.

### Proof of Concept
1. Attacker repeatedly submits minimal-value deposit transactions to the gateway contract on a connected external chain (e.g., thousands of dust-value transfers), each producing a distinct `(source_chain, tx_hash, log_index)` triple.
2. Honest Universal Validators observe and vote each event via `MsgVoteInbound`, creating a large number of concurrent `PendingInboundEntry` records before ballots finalize [1](#0-0) .
3. As soon as any ballot (from this flood or an unrelated legitimate inbound) reaches a terminal state, `afterInboundBallotTerminal` performs a full walk across the inflated `PendingInbounds` map/variants list to find the matching `ballot_id` [2](#0-1) .
4. With enough concurrent entries, the per-vote-transaction cost of this walk grows unbounded, degrading or blocking timely finalization of `MsgVoteInbound` calls chain-wide until the flood subsides — an availability-only failure with no direct fund impact confirmed from static analysis alone (dynamic gas-cost measurement was not performed in this review).
