### Title
Shielded TRC-20 mint/transfer/burn transactions are volatile-state dependent, causing legitimate signed transactions to be griefed via front-running of `frontier`/`leafCount` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `VerifyMintProof`, `VerifyTransferProof`, and `VerifyBurnProof` precompiled contracts require the caller to supply the exact current on-chain merkle-tree state (`frontier`, `leafCount`) as part of the trigger contract calldata. This state is fetched off-chain when a wallet builds a shielded transaction (via `Wallet.createShieldedContractParameters`/`createShieldedContractParametersWithoutAsk`, which invoke `ShieldedTRC20ParametersBuilder`), but the actual verification only happens later when the transaction is broadcast and executed by a full node. Any other shielded mint, transfer, or burn transaction that lands on-chain in between (naturally, or via deliberate front-running) advances `leafCount`/`frontier`, making the previously-built (and already zk-proof-bound) transaction's supplied `frontier`/`leafCount` stale.

### Finding Description
`Wallet.createShieldedContractParameters` at [1](#0-0)  builds the zk-SNARK proof and `bindingSignature`/`messageHash` for a mint/transfer/burn entirely client-side, without binding the proof to a specific merkle anchor/leafCount snapshot in a way that tolerates concurrent updates. The `frontier` and `leafCount` values are queried at build time and later embedded as raw calldata to the on-chain shielded contract, which passes them straight into the precompile.

`VerifyMintProof.execute` and `VerifyTransferProof.execute` parse `frontier`/`leafCount` directly out of the calldata and use them to compute the merkle insertion / anchor check: [2](#0-1)  and similarly for transfer at [3](#0-2) . If `leafCount`/`frontier` supplied in the calldata no longer match the value implied by intervening state changes, the on-chain Solidity shielded contract (not shown in this repo) will reject the call, and the precompile-level checks such as `verifyMintWrongLeafcount`/`verifyTransferWrongLeafcount` tests confirm that any mismatch here causes verification failure (`result[31] == 0`), i.e. the whole transaction reverts. [4](#0-3) 

This mirrors the reported `previewMint()`/`mintWithSignature` bug class exactly: a value (`frontier`/`leafCount`) that is fixed by the client at proof-construction time can be silently invalidated by any other transaction that lands first, and once broadcast, the original transaction is guaranteed to fail rather than degrade gracefully (e.g., by retrying against the newer anchor). Unlike some shielded-pool designs which keep a rolling window of *historical* valid anchors for spend proofs, this repo's `VerifyTransferProof`/`VerifyMintProof` require the exact current `frontier`/`leafCount`, so even a single intervening shielded operation from any other user is sufficient to invalidate a pending transaction.

### Impact Explanation
This is a denial-of-service / griefing issue against the shielded TRC-20 (zk-SNARK privacy) pipeline: any user (or an attacker deliberately racing) submitting a trivial mint/transfer/burn can cause other pending, already-signed shielded transactions to revert on execution, wasting the victim's TRX fee and causing repeated retries especially under load, without any privileged access being required.

### Likelihood Explanation
Likelihood is directly proportional to shielded pool activity: on any moderately used pool, transactions naturally interleave and this occurs unintentionally; an attacker can also actively cause it cheaply by submitting any trivial mint just before a target's shielded transaction is included, since gas/energy costs for spamming trivial mints are low and this requires no special privileges.

### Recommendation
Change the shielded contract/verification design so that anchors/leaf state are validated against a rolling window of recently-valid historical roots (as many privacy pools do) instead of requiring an exact match of the very latest `frontier`/`leafCount`, or have the verification precompile read authoritative state from persistent contract storage server-side and reconcile/merge concurrent updates rather than failing outright on any mismatch.

### Proof of Concept
1. Client A builds a shielded mint/transfer transaction via `Wallet.createShieldedContractParameters`, capturing `frontier`/`leafCount` at time T.
2. Client B submits and gets included any other shielded mint/transfer at time T+1 (before A's tx confirms), advancing `leafCount` and changing `frontier`.
3. Client A's transaction is broadcast and executed; `VerifyMintProof`/`VerifyTransferProof` parses the stale `frontier`/`leafCount` from A's calldata and the check fails, matching the behavior demonstrated by `verifyMintWrongLeafcount`/`verifyTransferWrongLeafcount` unit tests where mismatched `leafCount` causes `result[31] == 0`. [5](#0-4)
