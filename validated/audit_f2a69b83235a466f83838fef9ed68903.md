### Title
Permanent loss of accumulated `TRANSACTION_FEE_POOL` dust due to floor-division rounding in `Manager.payReward()` - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`Manager.payReward()` distributes the accumulated `TRANSACTION_FEE_POOL` to the block-producing witness by computing `transactionFeeReward = floorDiv(transactionFeePool, TRANSACTION_FEE_POOL_PERIOD)` every block, then subtracting exactly that amount from the pool. This is structurally identical to the reported `notifyRewardAmount()` bug: a reward pool is divided by a fixed period constant using integer division, so a remainder (`0 <= pool % PERIOD < PERIOD`) is left behind every time, and there is no mechanism that ever forces this remainder to be flushed to zero.

### Finding Description
`Manager.payReward()` is called once per produced block [1](#0-0) . When `supportTransactionFeePool()` is enabled, the witness reward from the fee pool is computed via floor division by a fixed period and is then subtracted from the pool: [2](#0-1) 

The same floor-division/subtraction pattern is duplicated in the non-delegation-change branch: [3](#0-2) 

The pool itself is filled from resource/energy fees paid by users, e.g. `ResourceProcessor.consumeFeeForBandwidth()` and `ReceiptCapsule.payEnergyBill()` call `dynamicPropertiesStore.addTransactionFeePool(fee)`: [4](#0-3) [5](#0-4) 

The pool accessor logic is a simple persisted counter with no fractional/high-precision component to compensate for rounding: [6](#0-5) 

Exactly as in the reported `notifyRewardAmount()` bug — where `rewardRate = reward.div(duration)` truncates and the leftover `reward - rewardRate*duration` is never redistributed — here `transactionFeeReward = floorDiv(pool, PERIOD)` truncates, and the leftover `pool - transactionFeeReward` is written back to `TRANSACTION_FEE_POOL` and only reduced by further floor-divided amounts in subsequent blocks. As the pool shrinks toward and below `TRANSACTION_FEE_POOL_PERIOD`, `floorDiv` eventually returns `0` for many consecutive blocks (whenever `pool < PERIOD`), while new fees keep trickling in slower than they leak out, causing a persistent residual balance that never converges to zero and is never distributed to any witness. There is no compensating mechanism (comparable to VeToken's suggested "add extra amount to queuedRewards") that carries the truncation remainder forward for exact redistribution — the code simply re-persists the truncated remainder as the new pool value forever.

### Impact Explanation
This causes real user-paid TRX fees to become permanently non-distributable to witnesses (the value is not burned nor sent anywhere — it sits in the `TRANSACTION_FEE_POOL` counter indefinitely, growing slower than it should be depleted, with dust below the rounding threshold effectively locked). This is an accounting/resource-reward-distribution correctness bug affecting consensus-level reward economics network-wide, reachable simply by users paying resource fees and blocks being produced (fully unprivileged, always-on code path). It matches the reward-accounting rounding class in the external report but the actual monetary exposure per period is bounded by `TRANSACTION_FEE_POOL_PERIOD - 1` sun per rounding event, which is small compared to other classes of vulnerabilities.

### Likelihood Explanation
This triggers automatically and deterministically on every single block for which `supportTransactionFeePool()` is enabled — no attacker action or special transaction is required. It is a systemic, always-active rounding defect rather than a rare edge case, but the amount of value at risk on any single truncation is tiny (bounded by `TRANSACTION_FEE_POOL_PERIOD`), so overall likelihood of triggering is certain but the per-event impact is minor. The cumulative effect is only a slow "leakage" of dust value from the distributable pool, not systemic loss of substantial funds, and TRX total supply is not otherwise reduced.

### Recommendation
When computing `transactionFeeReward`, track the truncation remainder and carry it forward so that the full pool is eventually and exactly distributed (e.g., only subtract the computed reward and let it naturally accumulate — which it already partially does — but change the period-based floor division either to distribute the entire remaining pool once it drops under a dust threshold, or use a running "carry" numerator/denominator technique so no dust is permanently below the rounding granularity). Alternatively, expose an operator/DAO recovery path to sweep any residual `TRANSACTION_FEE_POOL` dust to a defined destination once it can no longer be meaningfully distributed via the periodic division.

### Proof of Concept
Given `TRANSACTION_FEE_POOL_PERIOD = P` (exact value not resolved from the index within this session — see note below) and a pool value `X` where `0 < X < P`:
1. `floorDiv(X, P)` evaluates to `0`.
2. `mortgageService.payTransactionFeeReward(witness, 0)` pays nothing to the witness.
3. `saveTransactionFeePool(X - 0)` re-persists `X` unchanged.
4. If new fees added per block (`addTransactionFeePool`) are smaller than `P`, the pool value oscillates near/below `P` indefinitely, with the block-to-block leftover never being fully allocated to any witness in a single sweep — this is the same mechanism as `reward.div(duration)` leaving `reward - rewardRate*duration` stuck in `BaseRewardPool`/`VE3DRewardPool`.

Note: I could not retrieve the exact numeric value of `Constant.TRANSACTION_FEE_POOL_PERIOD` from the index in this session (index size limits may have excluded the exact literal), so the precise per-period dust magnitude is not confirmed — a Devin session with full repo access should verify this constant to quantify exact worst-case leakage per period.

  public void addTransactionFeePool(long amount) {
    if (amount <= 0) {

  public void saveTransactionFeePool(long value) {
    this.put(TRANSACTION_FEE_POOL,
        new BytesCapsule(ByteArray.fromLong(value)));
  }

  public long getTransactionFeePool() {
    return Optional.ofNullable(getUnchecked(TRANSACTION_FEE_POOL))
        .map(BytesCapsule::getData)
        .map(ByteArray::toLong)
        .orElseThrow(
            () -> new IllegalArgumentException("not found TRANSACTION_FEE_POOL"));
  }
