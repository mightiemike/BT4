### Title
`liquidate-multi` absorbs a failed bad-debt socialization, stranding uncollateralized debt permanently on a vault's books - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` wraps each per-position liquidation in `map` and always returns `(ok ...)` at the top level, so a mid-flow failure inside an individual `liquidate` call is only reported as an `err` element of the result list — it does not abort the surrounding transaction. Because `liquidate` performs its real value-moving steps (vault repay, debt removal, collateral seizure) *before* its final bad-debt-socialization check, a failure of that final check leaves the earlier mutations committed while the debt that was supposed to be written off is never socialized, permanently stranding uncollateralized debt on the vault's books.

### Finding Description
`liquidate-multi` is defined as: [1](#0-0) 

Because the outer function's own return value is unconditionally `(ok (map call-liquidate positions))`, Clarity's transaction-level commit/revert decision (which is made solely on the *top-level* function's return value) always commits, regardless of what any individual `call-liquidate`/`liquidate` invocation internally returned.

Inside `liquidate`, the order of operations is:
1. Compute liquidation amounts and health/liquidation-threshold checks. [2](#0-1) 
2. Execute the real, value-moving steps: repay the vault, remove the borrower's scaled debt, and seize/transfer collateral to the liquidator — all of which commit their state changes immediately since they are ordinary (not atomically-guarded) contract calls: [3](#0-2) 
3. Only *after* those transfers, determine whether the position has no collateral left, and if so attempt to socialize any remaining debt (other than the just-repaid asset) via a `fold` over `socialize-debt-asset`, asserting the fold's aggregate `success` flag: [4](#0-3) 

If this final `asserts!` fails (`ERR-BAD-DEBT-SOCIALIZATION-FAILED`), `liquidate` returns an `err`. When called directly (single `liquidate` call as a top-level transaction), this `err` propagates to the top level and the whole transaction — including steps 2's collateral seizure, debt removal, and vault repay — is rolled back, matching the documented invariant "Atomicity: Either full success or full revert. No partial state updates." [5](#0-4) 

But when `liquidate` is invoked through `liquidate-multi`'s `map call-liquidate positions`, that same `err` is merely collected as one element of the mapped list; it is never `try!`-propagated, so it cannot cause the outer `liquidate-multi` transaction (whose own return is `(ok ...)`) to abort. The mutations from step 2 for that position — debt already removed from the borrower's account, collateral already transferred to the liquidator, and the vault's `system-repay` already executed — remain committed. Meanwhile, the borrower's *other* debt assets that `no-collateral-left` determined should be written off via socialization were never actually socialized, since the socialization step is exactly what failed. That debt is now permanently unbacked (the borrower has zero collateral left, per `no-collateral-left`), yet it still counts as outstanding debt on the corresponding vault's books, and can never realistically be repaid or liquidated again (there is no collateral to seize).

This is the multi-step-entry-point-strands-value-on-abort pattern combined with a batch wrapper (`map`) that absorbs a nested function's failure instead of propagating it — exactly the class the rubric highlights as needing to be distinguished from a merely bounded DoS/amplifier: this is not bounded at all, it is a durable, unbounded accounting break that is only reachable because the wrapping `map`/`(ok ...)` construct swallows the deep failure.

### Impact Explanation
The affected debt asset's vault permanently carries scaled debt that has no collateral backing and was never written off through the bad-debt socialization mechanism that exists specifically to compensate suppliers for exactly this situation. Because socialization (which distributes the loss among suppliers via reserve/vault accounting) never runs, the vault's internal accounting overstates recoverable debt, meaning depositors' shares are valued against debt that will never be repaid. This is a protocol-insolvency-class impact for the debt vault in question — a permanent impairment of user (LP) funds, since the vault's reported total debt/interest no longer reflects reality and depositors bear an unaccounted loss with no compensating mechanism ever triggered.

### Likelihood Explanation
Reaching this requires a liquidator to call `liquidate-multi` with a position where, after collateral is fully seized, `no-collateral-left` evaluates true and the resulting bad-debt socialization step (a `fold` over `socialize-debt-asset`, itself calling into `vault-socialize-debt`) fails one of its internal assertions. Any legitimate liquidator batching several positions (which the function is explicitly designed to support, and explicitly documents as tolerating individual failures: "Failed liquidations return error codes but don't revert entire batch") can trigger this whenever one position in the batch happens to hit a socialization failure — no special privilege, timing, or two-party interference is required; it is a single-transaction, single-caller sequence.

### Recommendation
Ensure atomicity per position inside a batch: either (a) have `call-liquidate` catch the `liquidate` result and, on failure, explicitly discard/roll back that position's effects before continuing the `map` (not achievable with Clarity's execution model without redesign), or (b) restructure `liquidate` so the value-transferring steps (`vault-system-repay`, `debt-remove-scaled`, `collateral-remove`) are only committed after the bad-debt-socialization outcome is known and validated, i.e., move the socialization computation/validation earlier so the whole function can still cleanly `asserts!`/abort before any transfer occurs, or make `liquidate-multi` fully abort the transaction if any position's socialization fails (defeating the "don't revert entire batch" feature but restoring atomicity), or explicitly guarantee that `no-collateral-left`/socialization can never fail for a position whose collateral has already been fully seized (i.e., make `vault-socialize-debt` infallible for this call path).

### Proof of Concept
1. Liquidator submits `liquidate-multi` with a `positions` list containing one entry for `borrower` whose collateral (single asset) fully covers less than their total debt across multiple debt assets, such that liquidating the specified `debt-aid` seizes all of the borrower's remaining collateral (`no-collateral-left` becomes true).
2. Inside `liquidate` for that position: `vault-system-repay` executes (real underlying transferred from vault to repay `debt-to-repay`), `debt-remove-scaled` executes (borrower's scaled debt for `debt-aid` reduced), `collateral-remove` executes (borrower's remaining collateral sent to the liquidator) — all committed. [3](#0-2) 
3. `no-collateral-left` is true, so the function attempts to socialize the borrower's remaining other-asset debt via `fold socialize-debt-asset`; craft the scenario (e.g., an amount/precision edge case inside `vault-socialize-debt` for the other debt asset) so this fold's `success` flag ends up `false`. [6](#0-5) 
4. `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.
5. Because this call happened inside `map call-liquidate positions` within `liquidate-multi`, and `liquidate-multi` unconditionally returns `(ok (map call-liquidate positions))`, the overall transaction commits: the vault repay, debt removal, and collateral transfer from step 2 remain permanently on-chain, while the borrower's other debt asset is left outstanding with zero backing collateral and was never socialized to the vault's suppliers.
