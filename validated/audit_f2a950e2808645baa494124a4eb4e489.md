This confirms the analog: the L1 handler transaction lifecycle allows an L1 message sender to trigger `TransactionCancellationStarted` (an action fully within their control, analogous to revoking ERC20 approval) between the time a proposer stages the transaction with `TransactionManager::get_txs` (checking only `Pending` state, per [1](#0-0) ) and the time each validator independently calls `validate_tx` on it via `ValidateTransactionProvider::get_txs` (per [2](#0-1) ). If, by the time validation happens, the record is no longer `is_validatable()` (per [3](#0-2) ), the whole proposal is rejected via `BlockBuilderError::FailOnError(FailOnErrorCause::L1HandlerTransactionValidationFailed(...))` in `add_txs_to_executor` (per [4](#0-3) ), which aborts the *entire* block build (`abort_block`) rather than only dropping that one transaction (per [5](#0-4) ).

### Title
An L1 message sender can cause repeated temporary DoS on block proposals by canceling an L1→L2 message between block proposal and validation - (File: crates/apollo_batcher/src/block_builder.rs)

### Summary
An attacker who submits an L1→L2 message (L1 handler transaction) can request its cancellation on L1 at a moment calculated to land between the time a proposer includes the transaction in a proposed block and the time honest validators independently re-validate it. Because a single invalid L1 handler transaction causes the entire block proposal to be rejected (not just that transaction dropped), this lets an attacker repeatedly force valid proposals to fail, delaying block finalization.

### Finding Description
`TransactionManager::get_txs` (proposer side) only checks that a record's state is `Pending` and stages it, without re-checking validity at the time each validator processes it: [1](#0-0) .

Each validator, independently and possibly with network/processing delay, calls `ValidateTransactionProvider::get_txs`, which invokes `l1_events_provider_client.validate(tx_hash, height)` for every `L1Handler` transaction received from the proposer: [2](#0-1) .

`TransactionManager::validate_tx` calls `record.update_time_based_state(unix_now, policy)` and then checks `record.is_validatable()`; if the record's cancellation-request timelock has since elapsed (transitioning it to `CancelledOnL2`), or if it was consumed on L1 in the interim, `is_validatable()` returns false and an `InvalidValidationStatus` (`CancelledOnL2`/`ConsumedOnL1`/etc.) is returned: [6](#0-5) , [7](#0-6) .

When any validator hits this invalid status, `ValidateTransactionProvider::get_txs` returns `Err(TransactionProviderError::L1HandlerTransactionValidationFailed{..})`, and `BlockBuilder::add_txs_to_executor` converts this into a fatal error for the *entire* proposal (`BlockBuilderError::FailOnError(FailOnErrorCause::L1HandlerTransactionValidationFailed(...))`), rather than skipping just that one transaction: [4](#0-3) . This propagates up through `build_block_inner` -> `build_block`, which aborts the whole block via `abort_block()`: [5](#0-4) , and the batcher reports it as `ProposalStatus::InvalidProposal`: [8](#0-7) .

This mirrors the reported bug class: a party in control of an external precondition (ERC20 approval in the original report; here, the L1 cancellation-timelock/consumption state of their own message) can flip that precondition between the moment other parties commit to an action (accepting a bid / staging a transaction in a proposal) and the moment settlement/validation occurs, causing the entire batched operation (auction settlement / block proposal) to fail rather than just their own individual item.

### Impact Explanation
A single L1 message sender can force honest validators to reject an otherwise-valid proposal containing many legitimate transactions from other users, forcing a consensus round change and delaying block finalization. Because the attacker fully controls the timing of the `TransactionCancellationStarted`/timelock elapse relative to the proposal round (and can resubmit new L1→L2 messages cheaply), this can be repeated across consecutive rounds, resulting in a network unable to confirm new transactions promptly — a temporary but repeatable DoS on block production, matching the "network unable to confirm new transactions" acceptance criterion.

### Likelihood Explanation
Likelihood is bounded by the attacker's ability to align L1 message cancellation timing with the short propose/validate window of a consensus round, and by the `l1_handler_cancellation_timelock_seconds` configuration. However, since the attacker only needs the state transition to complete strictly between propose-time staging and validate-time re-check (both of which occur over network-bound, sub-round timeframes), and the attacker fully controls when to submit the cancellation, this is a moderately practical griefing vector for any actor sending L1→L2 messages, requiring no special privileges beyond being an L1 message sender.

### Recommendation
Consider one or more of: (1) having the proposer re-validate L1 handler transaction validity (including cancellation/consumption state) at inclusion time using the same time-based state update logic used by validators, and communicate a "not-before" or freshness window; (2) on validation failure of a single L1 handler transaction, drop just that transaction from the proposal (if the proposer protocol allows late removal) rather than failing the whole proposal; (3) extend the mandatory proposal cooldown (`l1_handler_proposal_cooldown_seconds`) relative to the cancellation timelock so that a transaction eligible for proposal cannot transition to `CancelledOnL2`/`Consumed` before validators have had a reasonable bound of time to validate it in the same round.

### Proof of Concept
1. Attacker sends an L1→L2 message (`LogMessageToL2`), creating an L1 handler transaction record in `Pending` state.
2. Once past the proposal cooldown, a proposer includes it via `TransactionManager::get_txs`, staging it in a proposed block along with many other unrelated, valid transactions from other users.
3. Just before/while the block is propagated to validators, the attacker submits an L1 cancellation request (`TransactionCancellationStarted`) for that same message, timed such that `l1_handler_cancellation_timelock_seconds` elapses by the time validators call `validate`.
4. Each validator's `ValidateTransactionProvider::get_txs` calls `validate_tx`, which now returns `InvalidValidationStatus::CancelledOnL2` because `update_time_based_state` transitioned the record.
5. `add_txs_to_executor` converts this into `BlockBuilderError::FailOnError(FailOnErrorCause::L1HandlerTransactionValidationFailed(...))`, aborting the whole block for every validator, per [9](#0-8) .
6. The proposal is marked `InvalidProposal`, forcing a new consensus round; attacker repeats with a fresh message to keep disrupting subsequent proposals.

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }
