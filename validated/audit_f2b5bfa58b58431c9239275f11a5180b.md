## Title
Unprotected subtraction in `ExchangeCapsule.transaction` allows exchange pool balances to go negative in default (non-hardened) mode, corrupting future exchange rate calculations - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
Java-tron's built-in Bancor-formula AMM (`ExchangeCreateContract`/`ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`) computes a counter-token amount via `ExchangeProcessor.exchange()` and then updates the pool reserves with a plain subtraction. This subtraction is only checked for going negative when a governance-gated "hardened" mode is active; in the default path it is unprotected, directly analogous to the `_getExchangeRate`/`_getImpliedRate` underflow issue in the external report, where an unchecked subtraction on a rate/reserve value produces an erroneous result that corrupts subsequent rate calculations.

### Finding Description
`ExchangeCapsule.transaction()` computes `buyTokenQuant` from the (unhardened) `ExchangeProcessor`, and then updates reserves with raw `long` subtraction: [1](#0-0) 

The resulting balances are only validated against going negative when `hardenedCalc` is `true`: [2](#0-1) 

Whether `hardenedCalc` is used is controlled entirely by the `allowHarden()` flag of `AbstractExchangeActuator`, which reads a dynamic (governance) property `allowHardenExchangeCalculation`: [3](#0-2) 

`ExchangeTransactionActuator.execute()` passes `allowHarden()` straight into `exchangeCapsule.transaction(...)`, so any ordinary, unprivileged user submitting an `ExchangeTransactionContract` exercises the unprotected path whenever the network-wide hardening proposal has not been activated: [4](#0-3) 

The underlying rate/quantity math itself (`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`) uses floating-point `double` arithmetic and can, under edge-case reserve ratios, yield a `buyTokenQuant` that exceeds the current pool reserve of the token being bought: [5](#0-4) 

When that happens in the default (non-hardened) code path, `secondTokenBalance - buyTokenQuant` (or the symmetric first-token case) underflows into a negative `long` value, which is stored back into the `ExchangeCapsule` reserves without any check, since the guard is gated on `hardenedCalc`: [2](#0-1) 

This mirrors the reported bug class exactly: an unprotected subtraction on a value that feeds an exchange-rate style computation silently produces an out-of-range (here, negative) result instead of reverting, and that corrupted state (the pool reserve) is persisted and used as the input to every subsequent trade's `exchangeToSupply`/`exchangeFromSupply` calculation, perpetuating and compounding the error — analogous to how a corrupted `lastImpliedRate`/`rateAnchor` propagates further miscalculations in the original report.

### Impact Explanation
A negative token reserve in `ExchangeCapsule` breaks the core AMM invariant (reserves should be non-negative and roughly track injected liquidity). Once corrupted, all subsequent `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` operations on that pair compute rates/quantities from a poisoned state, which can let traders extract value at incorrect prices or lock other users' funds behind divide-by-negative/garbage results. This is a state-corruption / mispriced-exchange impact reachable without any special privileges.

### Likelihood Explanation
Exercising the vulnerable path requires only submitting an `ExchangeTransactionContract` against an existing `Exchange` pair while the `allowHardenExchangeCalculation` governance flag is not yet enabled network-wide — this is the actuator's default/legacy behavior and is the code path exercised unless a super-representative proposal has activated hardening, so it is broadly reachable by any unprivileged account, though it requires the pool reserves and trade size to combine such that the double-precision `ExchangeProcessor` output exceeds the available reserve (an edge case around very small remaining reserves or extreme trade ratios).

### Recommendation
Make the negative-balance/overflow check in `ExchangeCapsule.transaction()` unconditional (not gated by `hardenedCalc`), i.e. always reject (`ContractValidateException`) when the computed `newFirstTokenBalance`/`newSecondTokenBalance` would be negative, matching the intent of the fix referenced in the external report (use a `sub`/`subtractExact`-style guard rather than allowing silent underflow), and consider making `SafeExchangeProcessor` the sole processor rather than an opt-in hardened mode.

### Proof of Concept
1. Create an exchange pair with reserves chosen so that a trade of a chosen size drives the Bancor-formula output (`ExchangeProcessor.exchangeFromSupply`) above the current opposite-side reserve (achievable by trading a large fraction of a low-reserve pool), with `allowHardenExchangeCalculation` not yet enabled (default state).
2. Submit an `ExchangeTransactionContract` via `ExchangeTransactionActuator` for that trade; `allowHarden()` returns `false`, so `exchangeCapsule.transaction(..., false)` is invoked.
3. Observe `newFirstTokenBalance`/`newSecondTokenBalance` become negative (`chainbase/.../ExchangeCapsule.java:143-156`) and are persisted with no guard (line 160 only checks when `hardenedCalc` is true), leaving the pool in a corrupted state that mispriced subsequent trades — this is the same scenario the repo's own hardened-mode test suite explicitly designed guards for, confirming the underlying risk is recognized but only mitigated behind a governance toggle: [6](#0-5)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
