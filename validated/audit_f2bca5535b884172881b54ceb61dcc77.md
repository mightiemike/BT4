### Title
Permanent Balance Burn When `DeleteAccount` Beneficiary Is Deleted While Cross-Shard Refund Receipt Is In-Flight — (`File: runtime/runtime/src/actions.rs`)

---

### Summary

`action_delete_account` irrevocably removes the sender's account and emits a system-predecessor balance-refund receipt to `beneficiary_id`. If the beneficiary is a named account on a different shard and that account is deleted before the cross-shard refund receipt is executed, the runtime's system-receipt failure path permanently burns the entire transferred balance with no recovery path.

---

### Finding Description

When `DeleteAccount` executes, `action_delete_account` does two things atomically on the sender's shard:

1. Pushes a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` onto `result.new_receipts`.
2. Calls `remove_account`, erasing the sender's account from state. [1](#0-0) 

`Receipt::new_balance_refund` sets `predecessor_id = "system"`, making it a system receipt. [2](#0-1) 

This receipt is then forwarded cross-shard to the beneficiary's shard. When it arrives and the beneficiary account no longer exists, `check_account_existence` calls `check_transfer_to_nonexisting_account`. For any named (non-implicit) account, this returns `AccountDoesNotExist`, failing the receipt. The code comment there explicitly acknowledges the gap:

> "Account deletion with beneficiary creates a refund, so it'll not create a new account." [3](#0-2) 

Because the receipt has `predecessor_id == "system"`, the failure branch in `apply_action_receipt` does not generate a further refund — it burns the deposit into `other_burnt_amount`: [4](#0-3) 

This is also documented explicitly:

> "If the execution of a refund fails, the refund amount is burnt." [5](#0-4) 

There is no fallback address, no retry mechanism, and no governance recovery path once the sender's account has been removed.

---

### Impact Explanation

The sender's entire account balance is permanently destroyed. The broken invariant is: *a `DeleteAccount` action guarantees the balance is transferred to `beneficiary_id`*. In the cross-shard case, this guarantee is conditional on the beneficiary existing at receipt execution time, but the protocol provides no enforcement of that condition and no recovery when it fails.

This is a **loss of funds** impact reachable from ordinary user actions.

---

### Likelihood Explanation

The attack requires:

1. Alice submits `DeleteAccount` with a named `beneficiary_id` on a different shard.
2. The beneficiary (Bob, the attacker) observes Alice's transaction in the mempool.
3. Bob submits his own `DeleteAccount` (deleting his own account — no special privilege required) timed to execute before Alice's cross-shard refund receipt arrives.
4. Alice's balance is burned.

Bob needs no privileged access; he is simply exercising his right to delete his own account. The cross-shard delay (at least one block) gives Bob a reliable window to front-run. The scenario is also reachable non-maliciously: a smart contract that self-destructs (via `promise_batch_action_delete_account`) while a peer's refund is in-flight produces the same outcome without any attacker intent. [6](#0-5) 

---

### Recommendation

At the point where `action_delete_account` emits the balance-refund receipt, validate that `beneficiary_id` currently exists in state (or is an implicit account that can be auto-created). If the beneficiary does not exist, either:

- Reject the `DeleteAccount` action with a new `ActionErrorKind` (e.g., `BeneficiaryDoesNotExist`), leaving the account intact so the user can choose a valid beneficiary; or
- Fall back to a protocol-level treasury or burn address rather than silently burning the balance.

Additionally, the system-receipt failure path could be hardened to route failed balance refunds to a recoverable location rather than burning them unconditionally.

---

### Proof of Concept

1. Alice (`alice.near`, shard 0) has a balance of 100 NEAR and submits `DeleteAccount { beneficiary_id: "bob.near" }`. `bob.near` lives on shard 1.
2. The `DeleteAccount` receipt executes on shard 0: Alice's account is removed; a system receipt `Transfer(100 NEAR) → bob.near` is emitted and queued for shard 1.
3. Bob (`bob.near`) observes Alice's transaction in the mempool and immediately submits `DeleteAccount { beneficiary_id: "carol.near" }` for his own account. This executes on shard 1 in the same or next block.
4. Alice's system refund receipt arrives at shard 1. `get_account(state_update, "bob.near")` returns `None`. `check_transfer_to_nonexisting_account` returns `AccountDoesNotExist` because `bob.near` is a named account.
5. `apply_action_receipt` detects `predecessor_id == "system"` and `result.result.is_err()`, so it adds 100 NEAR to `stats.balance.other_burnt_amount`.
6. Alice's 100 NEAR is permanently burned. Neither Alice nor Bob can recover it. [1](#0-0) [4](#0-3) [3](#0-2) [2](#0-1)

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a

        Ok(())

        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
