### Title
Negative BitSet capacity via `toBlock < fromBlock` causes `NegativeArraySizeException` in `LogBlockQuery` (eth_getLogs DoS) - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java`)

### Summary
The `LogBlockQuery` constructor computes `minSection` and `maxSection` independently from `fromBlock` and `toBlock` without validating that `fromBlock <= toBlock`. When an attacker sends a `eth_getLogs` filter where `toBlock < fromBlock` (but both still within `currentMaxBlockNum`), `maxSection` can end up smaller than `minSection`, producing a negative `capacity` value passed to `new BitSet(capacity)` in `getPossibleBlock()`, which throws an unhandled `NegativeArraySizeException`.

### Finding Description
In the constructor [1](#0-0) , `minBlock`/`minSection` are derived purely from `fromBlock`, and `maxBlock`/`maxSection` purely from `toBlock` (capped only against `currentMaxBlockNum`, never against `minBlock`). There is no check anywhere in this class enforcing `toBlock >= fromBlock`.

`getPossibleBlock()` only guards against `minBlock > currentMaxBlockNum` [2](#0-1) , and then unconditionally computes:
```
int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
BitSet blockNumBitSet = new BitSet(capacity);
``` [3](#0-2) 

If an attacker supplies `fromBlock` close to (but not exceeding) `currentMaxBlockNum` and `toBlock` small (e.g., `fromBlock = currentMaxBlockNum - 1000`, `toBlock = 1`), then `minBlock <= currentMaxBlockNum` (so the early-return guard is bypassed), yet `maxBlock (=toBlock) < minBlock`. This makes `maxSection < minSection`, so `capacity` becomes negative. `BitSet(int nbits)` throws `NegativeArraySizeException` for a negative argument, which is unhandled in this code path, propagating as an uncaught exception out of the JSON-RPC request handler.

The `fromBlock=0, toBlock=Long.MAX_VALUE` scenario specifically does not overflow, because `Long.MAX_VALUE` is special-cased to be clamped to `currentMaxBlockNum` [4](#0-3) , and real chain heights are far below the point where `int` casting of `blockNum / Bloom.BLOOM_BIT_SIZE` would overflow. The actual reachable defect is the `toBlock < fromBlock` case.

### Impact Explanation
An unprivileged, unauthenticated caller of the public `eth_getLogs` JSON-RPC endpoint can craft a filter with `toBlock < fromBlock` to trigger an uncaught `NegativeArraySizeException` inside `LogBlockQuery.getPossibleBlock()`. This is a request-scoped exception (not demonstrated to crash the entire node process), but it is an unhandled runtime exception on a public API path that produces an unexpected 500-type error/instability rather than a clean validation error, and can be repeated at will to generate log noise / exceptions on the RPC service.

### Likelihood Explanation
Trivially reproducible: it only requires a single crafted `eth_getLogs` call with `fromBlock` and `toBlock` reversed, with no authentication, permissions, or special account state required. The only precondition is that `fromBlock <= currentMaxBlockNum` (any past/near-tip block) while `toBlock < fromBlock`.

### Recommendation
In the `LogBlockQuery` constructor, after computing `minBlock`/`maxBlock` (and hence `minSection`/`maxSection`), explicitly validate `toBlock >= fromBlock` (or equivalently `maxBlock >= minBlock` / `maxSection >= minSection`) and return an empty result (or throw a well-defined `JsonRpcInvalidParamsException`) instead of proceeding to the capacity computation in `getPossibleBlock()`.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/jsonrpc/LogBlockQueryNegativeCapacityTest.java
@Test
public void testToBlockLessThanFromBlockCausesNegativeCapacity() throws Exception {
  long currentMaxBlockNum = 100_000L;
  LogFilterWrapper wrapper = new LogFilterWrapper(
      new FilterRequest("0x" + Long.toHexString(currentMaxBlockNum - 1000), "0x1", null, null, null),
      currentMaxBlockNum, null, false);

  LogBlockQuery query = new LogBlockQuery(wrapper, sectionBloomStore, currentMaxBlockNum, sectionExecutor);

  // Expect this currently throws NegativeArraySizeException due to
  // (maxSection - minSection + 1) < 0 in getPossibleBlock()
  Assert.assertThrows(NegativeArraySizeException.class, query::getPossibleBlock);

  // After fix: expect an empty list or a JsonRpcInvalidParamsException instead
}
```
Fuzz-test variant: iterate `fromBlock` in `{1, currentMaxBlockNum/2, currentMaxBlockNum}` and `toBlock` in `{0, 1, fromBlock-1}` and assert that `getPossibleBlock()` never throws `NegativeArraySizeException`, and that computed `capacity` matches `max(0, maxSection - minSection + 1) * BLOCK_PER_SECTION`.

  public LogBlockQuery(LogFilterWrapper logFilterWrapper, SectionBloomStore sectionBloomStore,
      long currentMaxBlockNum, ExecutorService executor) {
    this.logFilterWrapper = logFilterWrapper;
    this.sectionBloomStore = sectionBloomStore;
    this.sectionExecutor = executor;
    this.currentMaxBlockNum = currentMaxBlockNum;

    if (logFilterWrapper.getFromBlock() == Long.MAX_VALUE) {
      minBlock = currentMaxBlockNum;
    } else {
      minBlock = logFilterWrapper.getFromBlock();
    }
    minSection = (int) (minBlock / Bloom.BLOOM_BIT_SIZE);

    if (logFilterWrapper.getToBlock() == Long.MAX_VALUE) {
      maxBlock = currentMaxBlockNum;
    } else {
      maxBlock = logFilterWrapper.getToBlock();
      if (maxBlock > currentMaxBlockNum) {
        maxBlock = currentMaxBlockNum;
      }
    }
    maxSection = (int) (maxBlock / Bloom.BLOOM_BIT_SIZE);
  }
