### Title
`handle_poison_microblock` slashes a miner's coinbase without verifying the two reported microblock headers actually equivocate (same sequence + same `prev_block`) - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`handle_poison_microblock` only checks that `mblock_header_1` and `mblock_header_2` were signed by the same public key via `check_microblock_header_signer`; it never checks that the two headers share the same `sequence`/`prev_block` (i.e., that they actually constitute a genuine microblock fork). The only place this structural "do these headers conflict" check exists is `PoisonMicroblocksDoNotConflict` in the RPC mempool admission path in `blocks.rs`, not in the consensus-critical Clarity handler that actually executes on-chain during block processing.

### Finding Description
The claimed equality that must hold for a valid poison report is: `mblock_header_1.sequence == mblock_header_2.sequence AND mblock_header_1.prev_block == mblock_header_2.prev_block AND mblock_header_1.block_hash() != mblock_header_2.block_hash()` (both signed by the same key, but genuinely conflicting descendants of the same parent at the same slot). This is enforced only in the mempool pre-check function (`stackslib/src/chainstate/stacks/db/blocks.rs:6844-6861`): [1](#0-0) 

However, the consensus-critical execution path that actually applies a `PoisonMicroblock` transaction inside a processed block — `process_transaction_payload` → `run_poison_microblock` → `handle_poison_microblock` — never performs this check: [2](#0-1) [3](#0-2) 

`check_microblock_header_signer` only compares recovered pubkey hashes; `handle_poison_microblock` then only checks (a) that the pubkeyhash was ever seen at some height, and (b) that this height hasn't matured past `MINER_REWARD_MATURITY`. It never compares `sequence` or `prev_block` between the two headers. Since `get_microblock_pubkey_hash_height` is keyed purely by the pubkeyhash (not by miner identity or tenure), an attacker can take a header signed in tenure H1 and a header signed in tenure H2 by the same reused microblock private key — even though neither tenure had any actual fork — construct a synthetic `PoisonMicroblock(mblock_header_1_from_H2, mblock_header_2_from_H1)` payload, and get it processed successfully as long as it is submitted directly on-chain (e.g., embedded by a colluding/attacker-controlled miner in a block, bypassing the RPC-only `MemPoolRejection::PoisonMicroblocksDoNotConflict` guard that exists solely for mempool admission).

### Impact Explanation
Because every honest validating node runs identical (flawed) logic in `handle_poison_microblock` when replaying the block, there is no chain split — all nodes agree on the wrongful result deterministically. But the miner M at height H1 is wrongfully "poisoned": their coinbase maturation record is punished and the reporter/sender is credited a commission (see `insert_microblock_poison` and the returned tuple in `handle_poison_microblock`, lines 805-856), even though M never equivocated in either tenure. This is a reward-mispayment/reward-theft outcome: an honest miner's coinbase is stolen and paid to an unrelated attacker who filed a fabricated report, satisfying the Critical category "block-reward theft/double-payment/loss."

### Likelihood Explanation
The precondition is that a miner reuses the same microblock signing key across two tenures — nothing in `insert_microblock_pubkey_hash`/`get_microblock_pubkey_hash_height` prevents this, since the mapping is keyed by pubkeyhash → height, not by miner identity, and there is no cross-tenure uniqueness enforcement. The attacker needs only to observe two honestly-published microblock headers signed with the same key (public information from the chain) and craft/submit a `PoisonMicroblock` transaction with them, either directly in their own mined block (if they hold any miner slot) or by getting it accepted into a block through any other unprivileged path that bypasses the mempool's `PoisonMicroblocksDoNotConflict` gate. No majority stake, no signer collusion, and no compromise of M's key is required — this is exploitable by any minority participant who can get a transaction embedded in a block.

### Recommendation
Add the missing structural equivocation check directly inside `handle_poison_microblock` (or `check_microblock_header_signer`) in `stackslib/src/chainstate/stacks/db/transactions.rs`, mirroring the mempool check: require `mblock_header_1.sequence == mblock_header_2.sequence`, `mblock_header_1.prev_block == mblock_header_2.prev_block`, `mblock_header_1.version == mblock_header_2.version`, and `mblock_header_1.block_hash() != mblock_header_2.block_hash()` before proceeding to slash the miner. This must be enforced in the actual consensus execution path, not only in the RPC/mempool admission pre-check.

    /// Given two microblock headers, were they signed by the same key?
    /// Return the pubkey hash if so; return Err otherwise
    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
