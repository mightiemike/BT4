## Title
Wallet Contract's `extract_address` prefix-only match lets a crafted `target` AccountId collide with the current wallet address, bypassing the relayer-honesty (registrar) check — analogous to the Curve `_isETH` sentinel-address bypass ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs])

### Summary
The Sherlock report shows a Curve oracle reentrancy guard that only fires when a pool coin equals the canonical ETH sentinel address; pools that instead list WETH bypass the guard entirely because the check is a naive, format-based identity comparison instead of a semantically correct one. The analogous flaw in `nearcore` is in the ETH-Wallet-Contract's `TargetKind` classification: `extract_address` decides "is this `AccountId` the current wallet's address?" by decoding only the first 42 characters (`0x` + 40 hex) of the string and silently ignoring everything after, rather than requiring the whole `AccountId` to equal the current account. A different, fully independent, attacker-controlled `AccountId` that merely shares that 42-character prefix is misclassified as `TargetKind::CurrentAccount`, exactly as the Curve pool's WETH coin was wrongly treated as "not ETH" due to naive address matching.

### Finding Description
`extract_address` only validates a length lower-bound and decodes a fixed window of the string: [1](#0-0) 

`parse_target` then uses this loosely-derived `Address` for identity comparison to `current_address`: [2](#0-1) 

This `TargetKind` result gates a security-critical branch: when the relayer's calldata parses as an ERC-20-style emulation and the target genuinely is *another* eth-implicit account, the contract forces the action to a plain transfer and requires an on-chain registrar lookup (`address_check`) to confirm the address isn't secretly a named account a dishonest relayer is trying to spoof: [3](#0-2) 

If `target_kind` is instead (mis-)classified as `TargetKind::CurrentAccount`, this branch is skipped entirely and the parsed action executes directly against `target` with **no registrar validation and no self-transfer normalization** (`else => (action, TransactionKind::EthEmulation(eth_emulation.into()))`), even though `target` is not actually `current_account_id`.

Because `extract_address` never checks that the string terminates at index 42, any valid NEAR `AccountId` longer than 42 characters that begins with `0x` followed by the *same 40 hex characters* as the wallet's own address collides and is treated as "the current account," regardless of whether that longer account is a genuinely unrelated, independently-owned account (e.g., a top-level account registered by an attacker through the public account-registrar flow, whose name happens to start with that 40-hex prefix followed by arbitrary extra characters). This is the same class of bug as the audit finding: the check assumes one canonical string form for an identity ("ETH == 0xEee...eee" / "current account == exact 42-char prefix") but a differently-shaped, functionally distinct identifier satisfies the naive comparison and slips past the guard.

The code's own comment acknowledges the prefix-only design is intentional for *sub-account* test deployments and is asserted safe "in production" only because eth-implicit accounts are always exactly 42 characters: [4](#0-3) 

That production-safety argument relies on nobody being able to create a *different*, non-implicit, attacker-owned `AccountId` sharing the 40-hex prefix — but `extract_address` itself does nothing to enforce that the matched 42-character window must be the entire account id, so the invariant is defended only by an assumption about which account ids exist, not by code, mirroring exactly how the Curve/Conic code assumed "all ETH pools use the sentinel address" without verifying it.

### Impact Explanation
If exploited, a dishonest relayer can submit an RLP-encoded transaction to `rlp_execute` with a `target` engineered to prefix-collide with the wallet's own address. This routes an ERC-20-style emulated action (transfer/balance/total-supply calldata) straight to that attacker-influenced `target` via `action_to_promise`/`FunctionCall`, skipping the registrar `address_check` that exists specifically to catch a dishonest relayer routing calls to the wrong account. This is the exact "reentrancy/anti-spoof guard doesn't fire for an alternate but valid representation" bug class from the report, and in the Wallet Contract this guard's entire purpose is to prevent the relayer from tricking the user's Ethereum-style wallet into interacting with unintended accounts/tokens, i.e., unauthorized fund movement/mis-routed value transfer.

### Likelihood Explanation
Exploitation requires only that some relayer (an unprivileged transaction submitter, per the Wallet Contract's design where anyone can relay a user's signed Ethereum-format tx) be dishonest, and that a distinct, attacker-registrable `AccountId` exist which shares the wallet's 42-character `0x`+hex prefix. Given NEAR's public top-level account registration path, an attacker can choose the suffix freely to manufacture such a collision for any target wallet's address, making this practically reachable without any special privileges beyond acting as the relayer for a victim's meta-transaction.

### Recommendation
`extract_address`/`parse_target` should require the input `AccountId`'s length to be **exactly** 42 characters (or otherwise strictly bound the recognized eth-implicit pattern to the entire string, e.g. `hex_str.len() == 42` in production, only relaxing to suffix-aware parsing in explicitly test-only configurations, and never for classifying `TargetKind::CurrentAccount`/`EthImplicit` when the string could belong to an unrelated, independently-created account.

### Proof of Concept
1. Wallet Contract `W` is deployed at eth-implicit account `0xAAAA...AAAA` (42 chars), with `current_address` = bytes of `AAAA...AAAA`.
2. Attacker (or colluding relayer) registers, via the standard NEAR account-registration flow, an independent top-level account `T = "0xAAAA...AAAAxyz"` (same 40-hex prefix, extra trailing chars), fully attacker-owned.
3. Attacker acts as relayer for a user's signed Ethereum tx whose `to`/data encode an ERC-20 `transfer`, and sets the wallet-contract call's `target = T`.
4. In `parse_target`, `extract_address(T)` decodes chars `[2..42]` = `AAAA...AAAA`, equal to `current_address`, so `target_kind = TargetKind::CurrentAccount`.
5. In `parse_rlp_tx_to_action`'s `EthEmulation` branch, since `target_kind` is not `EthImplicit`, the `else` arm executes the parsed FunctionCall/Transfer action directly against `target = T`, with no registrar `address_check`, deviating from the intended anti-spoofing flow that would otherwise apply to any genuine other eth-implicit-looking target. [5](#0-4)

    target: &AccountId,
    context: &ExecutionContext,

    let tx_kind: EthTransactionKind = tx_bytes.as_slice().try_into()?;
    let tx: NormalizedEthTransaction = tx_kind.try_into()?;
    let target_kind = validate_tx_relayer_data(&tx, target, context, expected_nonce)?;

    // This is sent as a refund to the relayer in the case of an emulated base token
    // transfer or ERC-20 transfer. The reason for this refund is that it allows a
    // user with $NEAR to use a relayer service from their wallet immediately without
    // additional on-boarding.
    let tx_fee = {
        // Limit the cost by `VALUE_MAX` since we will convert this to a $NEAR amount.
        // The call to `low_u128` is safe because `VALUE_MAX` is the largest accepted value.
        let wei_amount = tx.max_fee_per_gas.saturating_mul(tx.gas_limit).min(VALUE_MAX).low_u128();
        NearToken::from_yoctonear(wei_amount.saturating_mul(MAX_YOCTO_NEAR as u128))
    };

    // The way an honest relayer assigns `target` is as follows:
    // 1. If the Ethereum transaction payload represents a Near action then use the receiver_id,
    // 2. If the payload looks like a supported Ethereum emulation then use the address registrar:
    // 2.a. if the tx.to address is registered then use the associated account id,
    // 2.b. otherwise, tx.to == target
    // 3. Otherwise, tx.to == target
    // Given this algorithm, the only way to have `TargetKind::EthImplicit` is in the
    // following cases:
    // I)   The Ethereum transaction payload is not parseable as a known action,
    // II)  The payload is parsable as a Near action and the receiver_id is an eth-implicit account
    // III) The payload is parsable as a supported Ethereum emulation but the to address is
    //      not registered in the address registrar.
    // Therefore, to determine if the relayer is honest we must always parse the payload and
    // we only need to check the registrar if the payload is parseable as an Ethereum emulation.
    // Note: the `TargetKind` is determined in `validate_tx_relayer_data` above, and that function

    let (action, transaction_kind) = match parse_tx_data(target, &tx, tx_fee, context) {
        Ok((action, ParsableTransactionKind::NearNativeAction)) => {
            (action, TransactionKind::NearNativeAction)
        }
        Ok((action, ParsableTransactionKind::SelfNearNativeAction)) => {
            if let TargetKind::EthImplicit(_) = target_kind {
                // The calldata was parseable as a Near native action where the target
                // should be the current account, but the target is some other wallet contract.
                // This is technically allowed under the Ethereum standard for base token transfers
                // (where any calldata can be used when sending tokens to another EOA), so we
                // assume such a transfer must have been the user's intent. No address check is
                // required in this case because no Near account other than the current account
                // can be the receiver of these actions.
                (

                    TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                        address_check: None,
                        fee: tx_fee,

                (action, TransactionKind::NearNativeAction)

/// Extracts a 20-byte address from a Near account ID.
/// This is done by assuming the account ID is of the form `^0x[0-9a-f]{40}`,
/// i.e. it starts with `0x` and then hex-encoded 20 bytes.
pub fn extract_address(current_account_id: &AccountId) -> Result<Address, Error> {
    let hex_str = current_account_id.as_bytes();

    // The length must be at least 42 characters because it begins with
    // `0x` and then a 20-byte hex-encoded string. In production it will
    // be exactly 42 characters because eth-implicit accounts will always
    // be top-level, but for testing we may have them be sub-accounts.
    // In this case then the length will be longer than 42 characters.
    if hex_str.len() < 42 {
        return Err(Error::AccountId(AccountIdError::AccountIdTooShort));
    }

    if &hex_str[0..2] != b"0x" {
        return Err(Error::AccountId(AccountIdError::Missing0xPrefix));
    }

    let mut bytes = [0u8; 20];
    hex::decode_to_slice(&hex_str[2..42], &mut bytes)
        .map_err(|_| Error::AccountId(AccountIdError::InvalidHex))?;

    Ok(bytes.into())
}

fn parse_target(target: &AccountId, current_address: Address) -> TargetKind<'_> {
    match extract_address(target) {
        Ok(address) => {
            if address == current_address {
                TargetKind::CurrentAccount
            } else {
                TargetKind::EthImplicit(address)
            }
        }
        Err(_) => TargetKind::OtherNearAccount(target),
    }
