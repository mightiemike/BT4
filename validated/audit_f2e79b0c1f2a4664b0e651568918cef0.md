## Title
Unbounded growth and full-list serving of `DelegatedResourceAccountIndex.toAccounts`/`fromAccounts` enables state-bloat DoS via cheap, repeated `FreezeBalanceContract`/`DelegateResourceContract` broadcasts - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
The reported LiquidityMining bug is about unbounded `for` loops over arrays that grow without limit as items are added, with no `from`/`to` pagination on read. The same anti-pattern exists in java-tron's legacy (V1) delegated-resource-index bookkeeping: an account's `toAccounts`/`fromAccounts` list inside `DelegatedResourceAccountIndexCapsule` grows by one entry for every distinct receiver/sender address it delegates resources to (via `FreezeBalanceContract` with a receiver, in the old resource model), and is never capped. The entire list is later read/rebuilt in full and returned unbounded through both consensus-level actuators and public RPC/HTTP endpoints.

### Finding Description
`DelegatedResourceAccountIndexStore.getWithPrefix()` performs a `prefixQuery` and loads **all** matching index rows for an address into memory, sorts them, and returns the complete `toAccounts`/`fromAccounts` lists with no size limit: [1](#0-0) 

For the legacy (non-`supportAllowDelegateOptimization`) path, `UnfreezeBalanceActuator` reads the owner's/receiver's full index list, mutates it as an `ArrayList`, and writes it back in full: [2](#0-1) 

The list is populated by `FreezeBalanceActuator`/`FreezeBalanceProcessor` whenever a `FreezeBalanceContract` specifies a distinct `receiverAddress` — each new unique receiver becomes a new entry in the owner's `toAccounts` list (and the receiver's `fromAccounts` list), with no cap on distinct counterparties: [3](#0-2) [4](#0-3) 

The only per-request minimum is 1 TRX (`frozenBalance < TRX_PRECISION` check), so an attacker can cheaply create thousands of distinct delegation relationships (thousands of receiver addresses, each getting a minimal 1 TRX delegation), each adding a new row keyed by `FROM_PREFIX/TO_PREFIX + address + counterparty`: [5](#0-4) 

This unboundedly-growing per-account index is then served **in full**, without any pagination parameter, through:
- The `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` methods: [6](#0-5) 
- Public gRPC endpoints reachable by any anonymous client: [7](#0-6) 
- Public HTTP/JSON-RPC endpoints (`/wallet/getdelegatedresourceaccountindex[v2]`) protected only by a generic rate limiter, not by any result-size limit: [8](#0-7) [9](#0-8) 

Additionally, `convert()` (invoked when the delegate-optimization feature switch is enabled) also iterates the full unbounded `toList`/`fromList` for every converted account, meaning a maliciously-bloated index also inflates block-processing/maintenance-time costs once conversion is triggered for that address: [10](#0-9) 

This mirrors the reported bug class exactly: an attacker-controllable array that grows without bound via cheap, repeated transactions, later consumed by unbounded loops (`prefixQuery` iteration, `List.remove`, `convert()` double loop) both in state-transition (actuator) logic and in RPC serialization/response building, with no `from`/`to` pagination offered on the read APIs.

### Impact Explanation
An attacker can cheaply inflate a single account's delegated-resource index to a very large size by broadcasting many minimal `FreezeBalanceContract` (old model, with distinct `receiverAddress` each time) transactions. Consequences:
- Every subsequent `UnfreezeBalanceContract` targeting that account triggers `O(n)` list rebuild/removal work in `UnfreezeBalanceActuator`, increasing per-transaction processing time paid for by fixed/near-fixed fees, degrading block-processing throughput for all validators (a network-wide DoS vector, not merely self-inflicted).
- Any RPC/HTTP client (including public FullNode APIs used by wallets/exchanges) requesting `getDelegatedResourceAccountIndex[V2]` for the bloated address receives (and the node serializes/sends) the entire unbounded list, consuming server memory/CPU/bandwidth on each call — a repeatable, low-cost amplification DoS against public API nodes.
- If/when `supportAllowDelegateOptimization` conversion runs for the bloated address, `convert()` performs `O(n)` re-delegation writes to the DB, further amplifying costs during a state-migration event.

### Likelihood Explanation
Likelihood is moderate-to-high: the primitive (`FreezeBalanceContract` to arbitrary receiver addresses, 1 TRX minimum, no relationship-count cap) is fully attacker-controlled and requires only ordinary broadcast transactions — no privileged role, leaked keys, or malicious peer/node assumptions are needed. The main constraint is the per-transaction bandwidth/energy fee cost of issuing many transactions, which bounds the growth rate but does not prevent it over time; a well-funded or patient attacker can accumulate a large index cheaply.

### Recommendation
- Impose a maximum number of distinct delegation counterparties (`toAccounts`/`fromAccounts` entries) per account, enforced in `FreezeBalanceActuator`/`FreezeBalanceProcessor`/`DelegateResourceActuator` validation, analogous to the existing `frozenCount == 0 || 1` cap already applied to the plain frozen-balance list.
- Add pagination parameters (`offset`/`limit`, mirroring the existing `GetPaginatedNowWitnessList`/`GetPaginatedAssetIssueList`/`GetPaginatedProposalList`/`GetPaginatedExchangeList` patterns already present in `api.proto`) to `GetDelegatedResourceAccountIndex[V2]` so responses and internal reads are bounded.
- Bound `DelegatedResourceAccountIndexStore.getWithPrefix()` and `convert()` to process at most a fixed number of entries per call, or migrate away from full-list rebuild-on-write semantics.

### Proof of Concept
1. Attacker controls address `A` with a modest TRX balance.
2. Attacker repeatedly broadcasts `FreezeBalanceContract` transactions from `A`, each with `frozenBalance = 1_000_000` (1 TRX, the minimum allowed) and a distinct, freshly-generated `receiverAddress` (`R1`, `R2`, ..., `Rn`), using the `ENERGY` or `BANDWIDTH` resource with delegation enabled (`dynamicStore.supportDR()` true, old model).
3. Each transaction is accepted by `FreezeBalanceActuator.execute()` and adds one entry to `A`'s `toAccounts` list (and one entry to each `Ri`'s `fromAccounts` list) via `DelegatedResourceAccountIndexStore` `FROM_PREFIX`/`TO_PREFIX` keys — see `FreezeBalanceActuator.java:80-96` and the underlying `DelegatedResourceAccountIndexStore.java` key writes.
4. After `n` such transactions, any client calls the public gRPC `GetDelegatedResourceAccountIndex` (or HTTP `/wallet/getdelegatedresourceaccountindex`) for address `A`; the node executes `getWithPrefix()`, performing a full `prefixQuery` scan and sort over all `n` entries and returning them all in one response (`DelegatedResourceAccountIndexStore.java:118-138`, `Wallet.java:1040-1051`).
5. Increasing `n` linearly increases both the state size attributable to `A` and the CPU/memory/bandwidth cost of every subsequent `UnfreezeBalanceContract` execution and every RPC/HTTP query for `A`'s index, demonstrating unbounded-loop-driven resource exhaustion analogous to the reported LiquidityMining issue.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  private void delegateResource(
      byte[] ownerAddress,
      byte[] receiverAddress,
      long frozenBalance,
      long expireTime,
      boolean isBandwidth,
      Repository repo) {
    byte[] key = DelegatedResourceCapsule.createDbKey(ownerAddress, receiverAddress);

    // insert or update DelegateResource
    DelegatedResourceCapsule delegatedResourceCapsule = repo.getDelegatedResource(key);
    if (delegatedResourceCapsule == null) {
      delegatedResourceCapsule = new DelegatedResourceCapsule(
          ByteString.copyFrom(ownerAddress),
          ByteString.copyFrom(receiverAddress));
    }
    if (isBandwidth) {
      delegatedResourceCapsule.addFrozenBalanceForBandwidth(frozenBalance, expireTime);
    } else {
      delegatedResourceCapsule.addFrozenBalanceForEnergy(frozenBalance, expireTime);
    }
    repo.updateDelegatedResource(key, delegatedResourceCapsule);

    // do delegating resource to receiver account
    AccountCapsule receiverCapsule = repo.getAccount(receiverAddress);
    if (isBandwidth) {
      receiverCapsule.addAcquiredDelegatedFrozenBalanceForBandwidth(frozenBalance);
    } else {
      receiverCapsule.addAcquiredDelegatedFrozenBalanceForEnergy(frozenBalance);
    }
    repo.updateAccount(receiverCapsule.createDbKey(), receiverCapsule);
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }
