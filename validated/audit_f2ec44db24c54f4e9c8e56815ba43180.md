### Title
Out-of-bounds bucket read in `stateless_compression::decompress` due to missing final-offset validation - (File: crates/starknet_os/src/hints/hint_implementation/stateless_compression/utils.rs)

### Summary
The Rust re-implementation of the Starknet OS stateless-compression decompressor reconstructs data by walking a sequence of attacker/prover-controlled `bucket_index_per_elm` values and indexing into `all_values` via per-bucket offset trackers, but never validates that the final offset for each bucket lands exactly at the start of the next bucket. This mirrors the CVE-2018-13346 (`mpatch_apply`) bug class: a fragment/offset is trusted to stay within the intended region without validating that traversal doesn't run past the boundary of the data it's supposed to be confined to.

### Finding Description
In `decompress` at [1](#0-0) , the function builds `bucket_offset_trackers` from `get_bucket_offsets`, then for every element in `bucket_index_per_elm` it does:
```
let offset = &mut bucket_offset_trackers[bucket_index];
let value = all_values[*offset];
*offset += 1;
```
There is no check that `*offset` stays below the boundary of that bucket (i.e., below the next bucket's starting offset) before advancing it. Compare this to the Cairo/CASM version of the same algorithm in `reconstruct_data` at [2](#0-1)  which explicitly re-verifies, via `dict_update`/`dict_squash`, that each bucket's tracked offset ends up exactly equal to the next bucket's starting offset — i.e. "Verify there was no out-of-bound access to `all_values` array by checking the bucket offset final values." The Rust helper has no equivalent post-condition check.

Because `bucket_index_per_elm` is unpacked directly from attacker-controlled compressed bytes (`unpack_chunk_to_usize(compressed, *data_len, TOTAL_N_BUCKETS...)` at line 599-600) with only a modulo-based range check restricting each index to `[0, TOTAL_N_BUCKETS)`, an attacker can repeat the same bucket index far more times than that bucket's declared length. Each repeat advances that bucket's offset by one without bound, eventually reading past the bucket's own data into an adjacent bucket's data (silent data corruption) or past the end of `all_values` entirely (`all_values[*offset]` panics with index-out-of-bounds).

### Impact Explanation
This exact `decompress` function backs the Starknet OS's stateless state-diff decompression used during OS re-execution to reconstruct the state diff from the compressed felt stream. If this Rust path is exercised during OS/Sierra re-execution of state-diff data supplied by an untrusted party (e.g. as part of proving/verification pipeline input), a malformed `bucket_index_per_elm` can either:
- Silently splice values from the wrong bucket into the reconstructed state diff (wrong decompressed state diff → wrong committed root / block hash / honest-node divergence), or
- Trigger an unhandled panic (index out of bounds), crashing the OS re-execution process and halting block processing (network unable to confirm new transactions).

### Likelihood Explanation
I could not fully confirm, within available tool calls, that this specific Rust `decompress` function (marked `#[allow(dead_code)]`) is actually invoked on the hot re-execution path from an untrusted transaction/state-diff input in production, versus only being used in tests/tooling (e.g. `crates/starknet_os/src/hints/hint_implementation/stateless_compression/tests.rs`) or as a reference implementation whose Cairo counterpart (which does perform the missing bound check) is the one actually executed inside the STARK-provable OS program. The one non-test reference found is in `crates/starknet_os/src/io/os_output_types.rs`, but I did not verify the call site's role or reachability from an untrusted single transaction/message before the iteration budget ran out.

### Recommendation
Add an explicit post-processing check in the Rust `decompress` (and any other native call sites reachable from untrusted state-diff/compressed input) that each bucket's final offset tracker equals the start offset of the next bucket (mirroring the Cairo `dict_update`/`dict_squash` verification), returning an error instead of silently reading out of bounds or panicking. Additionally, replace any `Vec` indexing with `all_values.get(*offset)` returning a structured `OsHintError` on failure.

### Proof of Concept
Not fully constructible without confirming the production call path for this function; conceptually: craft a compressed payload where `unique_value_bucket_lengths` declares a small bucket (e.g. length 1) but `bucket_index_per_elm` references that bucket index more times than its length (e.g. 5 times) while `data_len` accounts for the extra repeats — causing `bucket_offset_trackers[bucket_index]` to exceed the bucket's allotted range and read/panic on `all_values[*offset]`.

**Note on confidence**: Due to remaining uncertainty about whether this native Rust `decompress` function is actually reachable via an untrusted transaction/state-diff path in production (versus being test-only tooling mirroring the Cairo-verified logic), this finding should be treated as a likely-but-unconfirmed analog. I recommend a follow-up Devin session with full repo/terminal access to trace all callers of this function and confirm production reachability before treating this as a confirmed vulnerability.
