### Title
Unbounded Concurrent JSON Parsing Before Any Rate Limiting Enables Memory Exhaustion DoS — (`chain/jsonrpc/src/lib.rs`, `chain/jsonrpc-primitives/src/message.rs`)

---

### Summary

nearcore's JSON-RPC server parses every incoming request body into a full `serde_json::Value` tree **before** any rate limiting, concurrency control, or per-IP throttle is applied. The only guard is a raw-byte body-size cap (default 10 MB). Because `serde_json::de::from_slice` expands compact JSON into heap-allocated Rust enum structures at a 5–8× amplification ratio, a single 10 MB request can consume 50–80 MB of heap. With no per-IP limit and no global parsing semaphore, an unprivileged attacker can drive concurrent requests that exhaust node memory, halting transaction processing and block production without any network-layer involvement.

---

### Finding Description

**Parsing pipeline** (`chain/jsonrpc/src/lib.rs`, `rpc_handler` → `process` → `process_request_internal`):

1. Axum's `RequestBodyLimitLayer` enforces the raw byte cap (10 MB default).
2. `rpc_handler()` immediately calls `near_jsonrpc_primitives::message::from_slice(&body)`.
3. That function calls `serde_json::de::from_slice(s)` unconditionally.
4. The result is a `Message` enum whose `params` field is a `serde_json::Value` — a fully heap-allocated tree.
5. Only then does `process()` dispatch to `process_request()` → `process_request_internal()` → `process_method_call()` → a second `serde_json::from_value()` call for typed parameter parsing.

There is **no rate limiting, no per-IP throttle, and no global parsing semaphore** anywhere in the middleware stack. The router is assembled with only two layers:

```rust
app.layer(get_cors(&cors_allowed_origins))
   .layer(RequestBodyLimitLayer::new(limits_config.json_payload_max_size))
   .with_state(handler)
``` [1](#0-0) 

**Memory amplification mechanism** (`chain/jsonrpc-primitives/src/message.rs:262-264`):

```rust
pub fn from_slice(s: &[u8]) -> Parsed {
    decoded_to_parsed(::serde_json::de::from_slice(s))
}
``` [2](#0-1) 

`serde_json::de::from_slice` materialises every JSON string as a heap-allocated `String`, every array as a `Vec<Value>` (24+ bytes per element), and every object as a `HashMap<String, Value>`. A 10 MB payload of nested arrays or objects routinely expands to 50–80 MB.

**Double-parse penalty**: after the first parse into `Message`, `process_method_call` calls `RpcRequest::parse(request.params)` which invokes `serde_json::from_value()` on the already-materialised `Value`, cloning sub-trees into typed structs. [3](#0-2) 

**No batch amplification** (unlike the external report): `process()` rejects `Message::Batch` with a parse error, so batch-level multiplication does not apply here. [4](#0-3) 

**Default payload cap is 10 MB** (5× larger than the external report's 2 MB): [5](#0-4) 

---

### Impact Explanation

- **Single request**: 10 MB JSON → ~50–80 MB heap allocation, held for the duration of request processing.
- **Concurrent requests**: Axum/Tokio imposes no connection or concurrency limit. An attacker opening N simultaneous connections each sending a 10 MB payload consumes N × 50–80 MB before any request completes.
- **Node effect**: memory exhaustion causes the OS to OOM-kill `neard` or trigger swap thrashing, halting block production and transaction processing on that node. This is an application-level DoS (not network-level) fixable without a hardfork by adding middleware.

---

### Likelihood Explanation

The RPC port (3030) is publicly reachable by design. No authentication is required. The attack requires only standard HTTP POST requests with a crafted JSON body. The 10 MB body limit is enforced by Axum before the TCP connection is closed, so the attacker's cost is low (one TCP connection per request). The absence of any concurrency or rate-limit layer means the attack is trivially repeatable from a single IP.

---

### Recommendation

1. **Pre-parse concurrency semaphore**: add a `tower::limit::ConcurrencyLimitLayer` (or a `tokio::sync::Semaphore`) before `rpc_handler` to cap simultaneous in-flight parse operations.
2. **Per-IP rate limiting**: add a token-bucket or leaky-bucket layer (e.g., `tower_governor`) keyed on the client IP before body reading begins.
3. **Reduce default payload cap**: 10 MB is generous; legitimate NEAR RPC requests (transactions, queries) are at most a few KB. A 64–256 KB cap would eliminate most amplification headroom.
4. **Streaming/lazy parse**: consider reading only the `method` field before deciding whether to parse `params`, so unknown or rate-limited methods never trigger full-body materialisation.

### Proof of Concept

```python
import asyncio, aiohttp, json

# Craft a 10 MB JSON payload with deeply nested arrays
payload = json.dumps({
    "jsonrpc": "2.0",
    "id": 1,
    "method": "block",
    "params": {"_pad": [list(range(50000))] * 4}  # ~10 MB compact JSON
})

async def flood(session, url):
    async with session.post(url, data=payload,
                            headers={"Content-Type": "application/json"}):
        pass

async def main():
    url = "http://<node>:3030/"
    async with aiohttp.ClientSession() as session:
        # 200 concurrent requests → ~200 × 50-80 MB = 10-16 GB heap pressure
        await asyncio.gather(*[flood(session, url) for _ in range(200)])

asyncio.run(main())
```

Each concurrent request triggers `serde_json::de::from_slice` on a 10 MB body, allocating ~50–80 MB before the `block` handler even runs. With 200 concurrent connections this drives 10–16 GB of heap pressure with no authentication required.
