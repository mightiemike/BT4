### Title
Shared fixed-size `sectionExecutor` thread pool in `eth_getLogs`/`eth_getFilterLogs` allows attacker-controlled fan-out to cause RPC-wide convoy/DoS - ([File: LogBlockQuery.java], [File: TronJsonRpcImpl.java])

### Summary
`LogBlockQuery.partialMatch` submits one `Future` per unique bloom bit-index to a globally shared, fixed 5-thread `sectionExecutor`, then blocks with `Future.get()` in a loop before continuing to the next section/condition. Because the number of submitted futures scales with attacker-controlled `topics`/`address` array sizes (up to `maxAddressSize`/`maxSubTopics` = 1000 each by default) across up to 5 filter slots and up to ~3 sections for the max allowed block range, a small number of concurrent worst-case `eth_getLogs` calls can saturate the pool and serialize all other callers of the same executor (`eth_getLogs`, `eth_getFilterLogs`, `eth_getFilterChanges`).

### Finding Description
`TronJsonRpcImpl` creates one shared, hard-coded 5-thread executor for all section-bloom queries: [1](#0-0) 

Every call that resolves candidate blocks (`eth_getLogs`, `eth_getFilterLogs`, filter polling via `eth_getFilterChanges`) goes through `LogBlockQuery.getPossibleBlock()` → `subMatch()` → `partialMatch()`: [2](#0-1) 

Inside `partialMatch`, the code collects all *unique* bit indexes across the OR-group for one filter slot (address or one topic position) and submits one `Future` per unique index to the shared executor, then blocks on all of them before proceeding: [3](#0-2) 

This is called once per section, serially, for each of up to 5 filter slots (address + 4 topic positions), and sections are processed serially per slot: [4](#0-3) 

The fan-out per slot is not capped at 3 (the number of bloom hash functions) — it is capped only by the size of the OR-group the attacker supplies. `LogFilter` allows up to `maxAddressSize` addresses and `maxSubTopics` topics per position, both defaulting to 1000, and the bloom bit space is only `Bloom.BLOOM_BIT_SIZE = 2048`: [5](#0-4) [6](#0-5) [7](#0-6) 

With a few hundred distinct addresses/topics per slot an attacker can drive `uniqueBitIndexes` in `partialMatch` close to the full 2048-bit space, so a single filter slot in a single section can generate on the order of ~2000 `Future` submissions — far more than the 15/section assumed in the question, and this fan-out repeats per section (`maxBlockRange`=5000 / `BLOCK_PER_SECTION`=2048 ≈ 3 sections) and per slot (up to 5). A single crafted `eth_getLogs` call can therefore enqueue tens of thousands of blocking tasks into a pool with only 5 worker threads. Because `Future.get()` calls block the request-handling thread while waiting on the shared pool, a handful of concurrent attacker requests are sufficient to keep all 5 worker threads perpetually busy, and every other JSON-RPC caller that reaches the same executor (`eth_getLogs`, `eth_getFilterLogs`, `eth_getFilterChanges`) queues behind them — a classic convoy effect.

None of the existing checks stop this: `maxBlockRange`, `maxAddressSize`, and `maxSubTopics` bound the *request size* but not the amount of *work per byte of request* funneled into the shared thread pool; there is no per-request cap on the number of `sectionExecutor` submissions, and the default `rate.limiter` configuration for HTTP/gRPC components is commented out/example-only and does not specifically bound concurrent JSON-RPC log queries at the executor level: [8](#0-7) [9](#0-8) 

### Impact Explanation
This is a DoS via RPC-API: an unprivileged, unauthenticated JSON-RPC caller can degrade or stall `eth_getLogs`, `eth_getFilterLogs`, and `eth_getFilterChanges` for all other callers on the node by exhausting the shared 5-thread `sectionExecutor` with attacker-chosen fan-out, well beyond what proportionate/legitimate load would generate. This does not corrupt state or leak keys; the impact is scoped to RPC latency/availability degradation.

### Likelihood Explanation
- Preconditions: default configuration, JSON-RPC HTTP endpoint enabled (already the case for nodes offering `eth_getLogs`), no privileged role needed.
- Cost to attacker: free — read-only RPC calls, no transaction fee, no signature required.
- Feasibility: constructing an `eth_getLogs` request with hundreds of `address`/`topics` entries and the maximum allowed block range is trivial and well within `maxAddressSize`/`maxSubTopics`/`maxBlockRange` defaults (1000/1000/5000).
- Repeatability: fully repeatable; a small number of concurrent such requests (bounded by the attacker's own HTTP client concurrency, not by the node) is enough to keep the 5-thread pool saturated indefinitely.

### Recommendation
- Bound work per request rather than just request size: cap the number of unique bit indexes / `Future` submissions per `partialMatch` call independent of `maxAddressSize`/`maxSubTopics`, or process bit-index lookups synchronously/batched instead of one `Future` per bit index.
- Make `sectionExecutor` size configurable and/or use a bounded queue with fair, per-request or per-IP admission control (e.g., a semaphore limiting concurrent in-flight log queries) so that no single caller (or small set of colluding callers) can monopolize the pool.
- Add a rate limiter specifically for `eth_getLogs`/`eth_getFilterLogs`/`eth_getFilterChanges` (e.g., `GlobalPreemptibleAdapter` or `IPQPSRateLimiterAdapter`) enabled by default, not just as a commented-out example.
- Consider computing `partialMatch` cost from `bitIndexes` size and rejecting queries whose combined slot×section×unique-bit-index cost exceeds a fixed budget.

Load-test outline:
1. Fire N (e.g., 10–20) concurrent such worst-case `eth_getLogs` requests against a default-configured full node.
2. Concurrently issue normal `eth_getLogs`/`eth_getFilterChanges` calls from a separate "victim" client.
3. Measure p99 latency of the victim's calls before and during the attack load.

Expected result: victim call latency grows sharply (queuing behind attacker's `Future.get()` waits on the 5-thread `sectionExecutor`), demonstrating pool starvation caused by attacker-chosen fan-out rather than proportionate legitimate load, confirming the DoS via RPC-API described above.

      return blockNumList;

    int[][][] allConditionsIndex = getConditions();

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet blockNumBitSet = new BitSet(capacity);
    blockNumBitSet.set(0, capacity);

    // works serial
    for (int[][] conditionsIndex : allConditionsIndex) {
      BitSet bitSet = subMatch(conditionsIndex);
      blockNumBitSet.and(bitSet);
    }

      // operate on index i here

      }

  private BitSet subMatch(int[][] bitIndexes) throws ExecutionException, InterruptedException {

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet subBitSet = new BitSet(capacity);

    for (int section = minSection; section <= maxSection; section++) {
      BitSet partialBitSet = partialMatch(bitIndexes, section);

      for (int i = partialBitSet.nextSetBit(0); i >= 0; i = partialBitSet.nextSetBit(i + 1)) {
        // operate on index i here
        if (i == Integer.MAX_VALUE) {
          break; // or (i+1) would overflow
        }
        int offset = (section - minSection) * SectionBloomStore.BLOCK_PER_SECTION + i;
        subBitSet.set(offset);
      }
    }

    return subBitSet;
  }

  private BitSet partialMatch(final int[][] bitIndexes, int section)
      throws ExecutionException, InterruptedException {
    // 1. Collect all unique bitIndexes
    Set<Integer> uniqueBitIndexes = new HashSet<>();
    for (int[] index : bitIndexes) {
      for (int bitIndex : index) { //normally 3, but could be less due to hash collisions
        uniqueBitIndexes.add(bitIndex);
      }
    }

    // 2. Submit concurrent requests for all unique bitIndexes
    Map<Integer, Future<BitSet>> bitIndexResults = new HashMap<>();
    for (int bitIndex : uniqueBitIndexes) {
      Future<BitSet> future
          = sectionExecutor.submit(() -> sectionBloomStore.get(section, bitIndex));
      bitIndexResults.put(bitIndex, future);
    }

    // 3. Wait for all results and cache them
    Map<Integer, BitSet> resultCache = new HashMap<>();
    for (Map.Entry<Integer, Future<BitSet>> entry : bitIndexResults.entrySet()) {
      BitSet result = entry.getValue().get();
      if (result != null) {
        resultCache.put(entry.getKey(), result);
      }
    }
