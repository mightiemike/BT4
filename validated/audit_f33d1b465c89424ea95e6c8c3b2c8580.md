### Title
Insecure Direct Object Reference in `PipelineRunsController.Show` allows any authenticated user to read pipeline run data for jobs they do not own - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `Show` handler for `GET /v2/jobs/:ID/runs/:runID` parses `runID` from the URL and passes it straight to `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)` without ever validating that the run belongs to the job referenced by the `:ID` path parameter or to the authenticated caller/tenant. Any authenticated user who can guess or enumerate a numeric run ID can retrieve another user's pipeline run, including task outputs and fetched values.

### Finding Description
`Show` at `core/web/pipeline_runs_controller.go` lines 67-84 does the following: [1](#0-0) 

It reads `c.Param("runID")`, sets it on an empty `pipeline.Run{}` via `SetID`, and calls `FindRun(ctx, pipelineRun.ID)` directly. Notice that the `:ID` path segment (the job ID) is never read or used in `Show` (unlike `Index`, which explicitly filters `PipelineRuns(ctx, &jobSpec.ID, ...)` at lines 42-53). There is also no comparison against the authenticated user's ownership of the job/run, and `pipeline.Run.ID` is a simple auto-incrementing integer, making IDs sequential and easily enumerable by any authenticated low-privilege user with access to at least one job endpoint.

`FindRun` in `core/services/pipeline/orm.go` is a plain lookup by primary key with no additional predicate for job ownership or organization/tenant scoping — the ORM layer defers entirely to the controller to enforce any authorization boundary, and the controller does not do so here.

This differs from `Index`, which correctly scopes runs to the job ID from the path. `Show` silently drops that scoping, creating an IDOR: an authenticated user (any role permitted to hit the `/v2/jobs/*` routes) can substitute an arbitrary integer `runID` belonging to a different job/user and receive that run's full JSON representation, including task-level inputs/outputs that may contain bridge responses, adapter data, or other values considered sensitive to the owning job.

### Impact Explanation
This is a cross-tenant/cross-user information disclosure vulnerability. Pipeline run outputs frequently contain data fetched from bridges/external adapters and intermediate task results that are meant to be scoped to the job's owner. Exposing this to any other authenticated node user violates per-resource authorization scoping and matches "secret/sensitive data disclosure" impact categories for Chainlink node bug bounty programs, since it allows unauthorized read access to another job's execution data purely by manipulating a URL parameter.

### Likelihood Explanation
High feasibility: exploitation requires only (1) valid, low-privilege authenticated access to the node's web API (any user who can log in), and (2) knowledge or brute-force enumeration of a numeric `runID`, since integer primary keys are sequential and there is no rate limiting or ownership check in this handler. No special privileges, secrets, or social engineering are needed — this is directly reachable from a standard authenticated HTTP request to `GET /v2/jobs/:ID/runs/:runID`.

### Recommendation
Modify `PipelineRunsController.Show` to validate that the fetched `pipelineRun` actually belongs to the job identified by `c.Param("ID")` (mirroring the pattern already used in `Index`), returning `404 Not Found` if the run's `PipelineSpec.JobID` (or equivalent) does not match. Additionally, consider adding a join/predicate in `FindRun` (or a new `FindRunByJob` method) so the ORM enforces job-scoping at the query level rather than relying solely on controller logic.

### Proof of Concept
Integration test plan (Go, using existing web test harness in `core/web`):
1. Create two users/sessions (User A, User B) with standard node-operator credentials via the existing auth test helpers.
2. As User A, create Job J1 and trigger a run, capturing the returned `runID` (e.g., via `POST /v2/jobs/:ID/runs`).
3. As User B (different session/client), call `GET /v2/jobs/<some-other-job-id-or-placeholder>/runs/<J1's runID>`.
4. Assert that the response currently returns `200 OK` with User A's pipeline run JSON (task outputs included) — demonstrating the IDOR.
5. After the fix, assert the same request returns `404 Not Found` or `403 Forbidden`, and that only requests where the run's owning job matches `:ID` (and the job belongs to the requester's tenant/session) succeed.

func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
