### Title
Unbounded HTTP/2 Slow-Loris DoS on Public Transaction-Ingestion HTTP Server (CVE-2023-43622 analog) - (File: crates/apollo_http_server/src/http_server.rs)

### Summary
The sequencer's externally-facing HTTP transaction gateway (`apollo_http_server`, exposing `/gateway/add_transaction` and `/gateway/add_rpc_transaction`) is served with a bare `axum::serve(listener, app)` call that carries none of the HTTP/2 connection hardening that the sequencer's own internal RPC framework (`apollo_infra`) explicitly implements for exactly this bug class. An attacker can open an HTTP/2 connection, advertise (or shrink to) a zero flow-control window, and never issue `WINDOW_UPDATE` frames — the connection/stream is then held open indefinitely by the server, exactly as in Apache CVE-2023-43622, exhausting connection-handling resources on the transaction-ingestion endpoint of the sequencer.

### Finding Description
`HttpServer::run` in [1](#0-0)  binds a `TcpListener` and calls `axum::serve(listener, app)` directly, with no explicit HTTP/2 keepalive interval/timeout, no `max_concurrent_streams`, and no connection-level concurrency limiter.

Contrast this with the sequencer's own internal remote component server, which — per its own code comments — was hardened precisely to defend against slow-loris-style resource exhaustion over HTTP/2: [2](#0-1) 
That server also enforces a per-connection semaphore-based concurrency cap: [3](#0-2) 

`apollo_http_server`, however — the component that is directly reachable by any unprivileged external transaction sender (unlike the internal `RemoteComponentServer`, which is only reached from other sequencer components) — has none of this. Its `app()` method only bounds *request body size* via `RequestBodyLimitLayer`/`DefaultBodyLimit`: [4](#0-3) 
There is no timeout layer, no HTTP/2 PING keepalive, and no cap on the number of concurrent connections/streams. Hyper's default HTTP/2 server behavior (used transparently through `axum::serve`) does not proactively send keepalive pings or terminate idle/stalled streams unless explicitly configured — matching the exact root cause described in the Apache advisory: a connection opened with an initial (or shrunk-to-zero) window size can be held open indefinitely because the server takes no independent action to reclaim it.

### Impact Explanation
Because the transaction-ingestion HTTP server accepts connections from any external, unauthenticated client and lacks the keepalive/timeout/stream-concurrency protections present elsewhere in the codebase, a single attacker can open many HTTP/2 connections with a zero-sized flow-control window (never sending `WINDOW_UPDATE`). Each such connection consumes a `tokio::spawn`-ed task/socket indefinitely (there is no `keep_alive_timeout` to trigger a `GOAWAY`), unlike the internal server which is bounded by `DEFAULT_KEEPALIVE_TIMEOUT_MS` and `DEFAULT_MAX_CONCURRENCY`. With enough concurrent zero-window connections, worker/task and file-descriptor resources on the sequencer's public HTTP ingress are exhausted, preventing legitimate transaction submissions from being accepted — i.e., the node becomes unable to confirm new transactions, satisfying the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
The attack requires only a raw TCP connection and the ability to perform an HTTP/2 preface/SETTINGS handshake while withholding `WINDOW_UPDATE` frames (or advertising an initial window of 0) — no authentication, staking, or special privilege is needed, and it is directly analogous to the well-known "slow loris" class already patched in Apache HTTP Server per the referenced advisory. The absence of any timeout/keepalive/connection-cap configuration on this specific server (as opposed to the internal server, which was hardened for this exact reason) makes exploitation straightforward and repeatable.

### Recommendation
Apply the same HTTP/2 connection hardening used in `RemoteComponentServer` to `apollo_http_server`: switch from the bare `axum::serve` call to a `hyper_util::server::conn::auto::Builder` (or equivalent) configured with `keep_alive_interval`/`keep_alive_timeout`, an explicit `max_concurrent_streams` bound, and a connection-level concurrency limiter (e.g., a semaphore, mirroring `DEFAULT_MAX_CONCURRENCY`/`connection_semaphore` in `remote_component_server.rs`), so idle/stalled HTTP/2 connections are reclaimed after a bounded timeout regardless of flow-control window state.

### Proof of Concept
1. Start the sequencer's HTTP server (`apollo_http_server`) with default configuration.
2. From an attacker-controlled client, open a raw TCP connection and perform the HTTP/2 client preface + an initial `SETTINGS` frame that sets `SETTINGS_INITIAL_WINDOW_SIZE` to `0` (or open a stream and never send `WINDOW_UPDATE` after the connection-level window is exhausted), and send a `HEADERS` frame beginning a POST to `/gateway/add_transaction` without ever completing the body (or completing a request but never reading/acking the response with credit for further frames).
3. Repeat this hundreds/thousands of times from multiple sockets.
4. Observe that none of these connections are closed by the server (no `keep_alive_timeout`/`GOAWAY` is issued, unlike the behavior asserted for the internal server in `crates/apollo_infra/src/tests/remote_server_connection_eviction_test.rs`), and that legitimate transaction submissions begin to fail or queue indefinitely once available tasks/sockets are exhausted.

macro_rules! serve_connection {
    (
        $io:expr,
        $service:expr,
        $max_streams:expr,
        $keepalive_interval:expr,
        $keepalive_timeout:expr
    ) => {
        let result = ServerBuilder::new(TokioExecutor::new())
            .http2()
            .timer(TokioTimer::new())
            .max_concurrent_streams($max_streams)
            .keep_alive_interval($keepalive_interval)
            .keep_alive_timeout($keepalive_timeout)
            .serve_connection($io, $service)
            .await;

        if let Err(e) = result {
            error!("Remote component server start error: {e}");
        }
    };
}

    async fn start(&mut self) {
        let bind_socket = SocketAddr::new(self.config.bind_ip, self.port);
        debug!(
            "Starting server with socket {:?} with {:?} concurrent connections",
            bind_socket, self.config.max_concurrency
        );
        let connection_semaphore = Arc::new(Semaphore::new(self.config.max_concurrency));

        let per_connection_service =
            |io: TokioIo<tokio::net::TcpStream>,
             max_streams: u32,
             keepalive_interval: Duration,
             keepalive_timeout: Duration,
             connection_semaphore: Arc<Semaphore>,
             local_client: LocalComponentClient<Request, Response>,
             metrics: &'static RemoteServerMetrics,
             max_request_body_bytes: usize,
             client_peer: SocketAddr| {
                async move {
                    trace!(remote_addr = %client_peer, "remote component TCP connection opened");
                    match connection_semaphore.try_acquire_owned() {
                        Ok(permit) => {
                            metrics.increment_number_of_connections();
                            trace!("Acquired semaphore permit for connection");
                            let client_peer_for_handler = client_peer;
                            let handle_request_service =
                                service_fn(move |req: HyperRequest<Incoming>| {
                                    trace!("Received request: {:?}", req);
                                    let request_id = req
                                        .headers()
                                        .get(REQUEST_ID_HEADER)
                                        .and_then(|header| header.to_str().ok())
                                        .and_then(|s| s.parse::<RequestId>().ok())
                                        .expect(
                                            "Request ID should be present in the request headers",
                                        );
                                    Self::remote_component_server_handler(
                                        req,
                                        request_id,
                                        client_peer_for_handler,
                                        local_client.clone(),
                                        metrics,
                                        max_request_body_bytes,
                                    )
                                });

                            // Bundle the service and the acquired permit to limit concurrency at
                            // the connection level.
                            let service = PermitGuardedService {
                                inner: handle_request_service,
                                _permit: Some(permit),
                                remote_server_metrics: metrics,
                            };

                            serve_connection!(
                                io,
                                service,
                                max_streams,
                                keepalive_interval,
                                keepalive_timeout
                            );
                            trace!(remote_addr = %client_peer, "remote component TCP connection closed");
                        }
