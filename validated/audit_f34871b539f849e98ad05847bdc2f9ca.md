### Title
App Proxy `logged_in_customer_id` Spoofing via Repeated Query Parameter Desync Between HMAC Validation and Value Extraction - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The App Proxy HMAC validator normalizes repeated query parameters by concatenating their values with commas before computing/verifying the signature, but explicitly exempts only a fixed allowlist (`hmac`, `shop`, `signature`, `timestamp`) from this treatment. Any other Shopify-appended parameter — most notably `logged_in_customer_id` — can be duplicated by an anonymous storefront visitor. The signature still validates correctly (because it is computed over the full, comma-joined value, matching Shopify's real signing algorithm), but application code that reads the parameter with `URLSearchParams.get()` (the exact pattern documented by the library) receives only the *first* occurrence, which can be the attacker-supplied value rather than the value Shopify actually appended.

### Finding Description
`normalizeQuery` in [1](#0-0)  only rejects repeated occurrences of parameters in `APP_PROXY_SINGLE_VALUE_PARAMS`: [2](#0-1) 

Every other parameter — including `logged_in_customer_id`, the value merchants/apps use to identify which customer is making the request — is deliberately allowed to repeat and is merged by joining with a comma: [3](#0-2) 

`stringifyQueryForAppProxy` then serializes that comma-joined value into the canonical string used to compute/verify the HMAC: [4](#0-3) 

This matches Shopify's own app-proxy signing algorithm, so a request containing a duplicated `logged_in_customer_id` (one attacker-supplied value plus the one Shopify legitimately appends) will still pass `validateAppProxyHmac`/`api.utils.validateHmac` — the signature check is satisfied because it was computed over the *combined* value, `"attacker_id,real_id"`.

The library's own authentication helper for app proxy requests only verifies the signature and does not further parse or bind `logged_in_customer_id`, leaving it up to the app: [5](#0-4) 

The documented usage pattern for consuming this value is explicitly shown in generated docs as:
```ts
const customerId = searchParams.get("logged_in_customer_id")
```
`URLSearchParams.get()` returns only the **first** value for a repeated key. Because a customer's own client-supplied query parameters are typically prepended to the parameters Shopify appends (shop, timestamp, signature, `logged_in_customer_id`) when Shopify forwards the app-proxy request, an attacker who appends their own `logged_in_customer_id=<victim_id>` to the request URL before Shopify appends the real (possibly empty, for a logged-out visitor) one can make `.get('logged_in_customer_id')` return the attacker-chosen value — while the HMAC signature still validates, because the underlying validation logic never accounted for the fact that a downstream consumer would read only a single value out of a parameter it deliberately allowed to be multi-valued.

This is directly analogous to the GMX `estimateExecuteWithdrawalGasLimit` bug: a security-relevant computation (gas estimate / HMAC validation) is performed over an incomplete/mismatched view of the data that is actually used later (actual gas consumed including swaps / actual customer identity extracted by the app), causing the guarantee ("fee is sufficient" / "the validated request identifies the correct customer") to silently fail in a specific case the estimator/validator was never designed to detect.

### Impact Explanation
An anonymous storefront visitor can cause a merchant's app (using the officially documented pattern) to believe a forged app-proxy request came from an arbitrary, attacker-chosen `logged_in_customer_id`, even though the cryptographic HMAC/signature check reports the request as valid. Any app logic that trusts `logged_in_customer_id` from an authenticated app-proxy request (e.g., to fetch/act on that customer's orders, loyalty balance, or other private data) is exposed to cross-customer/cross-tenant data access using a request that the library itself reports as validly signed.

### Likelihood Explanation
The attack requires only an unauthenticated HTTP request to a merchant's app-proxy endpoint with a crafted query string (`?logged_in_customer_id=<attacker-chosen-id>&...`); no secrets, privileged access, or MITM position are needed. It relies on the documented `searchParams.get('logged_in_customer_id')` consumption pattern being followed by app developers, which the library's own generated docs recommend.

### Recommendation
Add `logged_in_customer_id` (and any other Shopify-appended, security/identity-relevant app-proxy parameter) to `APP_PROXY_SINGLE_VALUE_PARAMS` so that duplicate occurrences are rejected outright, the same way `hmac`/`shop`/`signature`/`timestamp` already are. Alternatively, have `validateHmac`/`validateAppProxyHmac` return the normalized (post-merge) values it validated, and require callers to use those rather than re-parsing the raw request URL with `URLSearchParams.get()`.

### Proof of Concept
1. A logged-out storefront visitor requests the merchant's app-proxy path directly, injecting a duplicate parameter:
   `https://shop.myshopify.com/apps/my-app?logged_in_customer_id=999999&...`
2. Shopify's proxy forwards the request to the app, appending its own trusted parameters (including the real, e.g. empty/absent, `logged_in_customer_id` and a valid `signature` computed over the full, final parameter set — which now contains two `logged_in_customer_id` occurrences joined by Shopify's canonicalization rule).
3. The app calls `api.utils.validateHmac(searchParams, {signator: 'appProxy'})` (or `authenticate.public.appProxy(request)`), which succeeds because `stringifyQueryForAppProxy`/`normalizeQuery` reproduce Shopify's comma-joined canonicalization exactly, matching the received signature.
4. The app then executes `searchParams.get('logged_in_customer_id')`, per the documented pattern, and receives `"999999"` (the attacker's value, since it is the first occurrence) instead of the real signed-in customer's ID appended by Shopify.
5. The app treats the request as validly authenticated and originating from customer `999999`, enabling impersonation/cross-customer access.

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}
```

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
```
