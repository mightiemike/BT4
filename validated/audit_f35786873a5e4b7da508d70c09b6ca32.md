Confirmed: `ExchangeTransactionContract` (the swap operation) has an `expected` field acting as a slippage guard, validated at `ExchangeTransactionActuator.java#L217-221` — but `ExchangeInjectContract` and `ExchangeWithdrawContract` (the liquidity add/remove operations) carry **no such min/max bound** for the automatically-computed "other side" amount. This is the exact structural analog of the `Portfolio.sol` bug: a single-sided amount is specified by the LP, and the counter-amount is derived from the pool's *current* on-chain ratio at execution time, with no protection against that ratio being manipulated between submission and execution.

### Title
Unprotected TRC10 Bancor-style liquidity inject/withdraw enables MEV sandwich extraction of LP value - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the "other token" amount required/returned for a liquidity operation directly from the exchange pool's live `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with zero caller-supplied bound on that computed amount. `ExchangeTransactionActuator` (the swap operation on the same pool) already includes an `expected` slippage-protection field that is enforced in `doValidate()`, proving the codebase's designers recognized the need for bounding execution-time pool ratios elsewhere — but omitted it for inject/withdraw. An attacker can sandwich a victim's `ExchangeInjectContract`/`ExchangeWithdrawContract` with `ExchangeTransactionContract` swaps to skew the pool ratio, forcing the victim to deposit/withdraw at an unfavorable ratio while the attacker profits by reversing the swap afterward — the same bug class as the reported Portfolio.sol allocate/deallocate vulnerability.

### Finding Description
`ExchangeInjectActuator.execute()` reads the current `firstTokenBalance`/`secondTokenBalance` of the pool and computes `anotherTokenQuant` proportionally: [1](#0-0) . This mirrors Portfolio's `allocate`, where the counter-token amount is derived from live virtual reserves. The `ExchangeInjectContract` protobuf message exposes only `token_id` and `quant` — no max bound on `anotherTokenQuant` [2](#0-1) .

The same pattern exists in `ExchangeWithdrawActuator.execute()`, which computes `anotherTokenQuant` (the second token returned to the withdrawer) from the live ratio with no minimum bound supplied by the caller: [3](#0-2) , and `ExchangeWithdrawContract` similarly only carries `token_id`/`quant` [4](#0-3) .

By contrast, `ExchangeTransactionContract` includes an `expected` field for the swap operation [5](#0-4) , and this bound is actually enforced in validation: [6](#0-5) . The pool's price-setting mechanism itself, `ExchangeCapsule.transaction()`, mutates `firstTokenBalance`/`secondTokenBalance` via the bancor-formula `Processor.exchange()` on every swap: [7](#0-6) , confirming that any account can move the ratio arbitrarily (within balance/liquidity limits) immediately before a victim's inject/withdraw transaction is packed into the same or an adjacent block.

### Impact Explanation
A liquidity provider calling `ExchangeInjectContract` or `ExchangeWithdrawContract` has no way to bound how much of the "other" TRC10 token they will be forced to deposit or will receive back. An attacker (any unprivileged account, including a block-producing witness with ordering control, or simply a fast follow-up transaction submitter) can:
1. Front-run with `ExchangeTransactionContract` to skew `firstTokenBalance`/`secondTokenBalance`.
2. Let the victim's inject (or withdraw) execute at the skewed ratio, forcing an unfavorable token split.
3. Back-run with a reverse `ExchangeTransactionContract` (protected by their own `expected` bound) to restore the ratio and capture the spread as profit, directly extracted from the victim LP's assets.

This is a direct, unprivileged loss of value for any user of the TRC10 Bancor-exchange module's inject/withdraw operations — functionally identical to the disclosed `Portfolio.sol` allocate/deallocate sandwich.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control transaction ordering relative to the victim's inject/withdraw within a short window (same block or adjacent blocks), which is easier for a witness/SR or an attacker racing transaction propagation, but not guaranteed for arbitrary orderings on every network. The `ExchangeTransactionContract`'s existing `expected` field shows the project already anticipated ratio-manipulation risk for swaps but did not extend the same protection to inject/withdraw, making this an omission rather than a design choice.

### Recommendation
Add caller-supplied bounds to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `maxAnotherTokenQuant` for inject, `minAnotherTokenQuant` for withdraw), and enforce them in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()`, mirroring the `expected` check already present in `ExchangeTransactionActuator.doValidate()` ( [6](#0-5) ).

### Proof of Concept
1. Victim submits `ExchangeInjectContract{exchange_id, token_id=A, quant=X}` expecting `anotherTokenQuant` ≈ pool's current `secondTokenBalance/firstTokenBalance * X`.
2. Attacker submits `ExchangeTransactionContract{exchange_id, token_id=A, quant=largeAmount, expected=minAcceptable}` ordered immediately before the victim's transaction, which calls `ExchangeCapsule.transaction()` and skews `firstTokenBalance`/`secondTokenBalance` ( [8](#0-7) ).
3. Victim's `ExchangeInjectActuator.execute()` runs against the skewed ratio, computing an inflated `anotherTokenQuant` that the victim is forced to deposit ( [9](#0-8) ), with no validation rejecting the unfavorable ratio.
4. Attacker submits a reverse `ExchangeTransactionContract` to restore the pool ratio, realizing a profit equal to the spread extracted from the victim's forced deposit — analogous to the `2.12e18 X` MEV profit demonstrated in the original Portfolio.sol report.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
