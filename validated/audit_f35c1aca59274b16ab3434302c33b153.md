Confirmed: `tokenExchange` in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` decodes and signature-verifies the `sessionToken` via `decodeSessionToken`, but **discards the returned payload** without ever comparing its `dest`/`iss` claims against the caller-supplied `shop` parameter. The `shop` value — which per the library's own documented usage pattern comes straight from `req.query.shop` (an attacker-controlled, unauthenticated query parameter) — is independently sanitized by `sanitizeShop` (which only checks that it matches a `*.myshopify.com`/`*.myshopify.io`/etc. domain shape) and then used to build the outbound request URL that carries the app's `client_id`/`client_secret` in the POST body to `https://${cleanShop}/admin/oauth/access_token`.

### Title
Token exchange sends app `client_secret` to an attacker-chosen shop domain because `shop` is never validated against the verified session-token `dest`/`iss` claims - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`shopify.auth.tokenExchange` verifies the cryptographic signature of the session token but never checks that the token's `dest` (the shop it was actually issued for) matches the `shop` argument used to build the outbound access-token request. Since the documented calling pattern takes `shop` from an unauthenticated query parameter, an attacker who possesses *any* valid session token (e.g., one issued for their own installed test shop) can supply an arbitrary `shop` value and cause the app server to send its `client_id` + `client_secret` to that attacker-designated Shopify domain's `/admin/oauth/access_token` endpoint.

### Finding Description
In `tokenExchange()`: [1](#0-0) 

`decodeSessionToken(config)(sessionToken)` is called purely for its side effect of throwing on an invalid/expired/wrong-audience token — its resolved `JwtPayload` (which contains `dest`/`iss`, the shop the token was actually minted for) is never assigned or used. The `shop` used to construct the request URL comes entirely from the caller-supplied `TokenExchangeParams.shop`, sanitized only for domain-shape validity via `sanitizeShop`: [2](#0-1) 

`sanitizeShop` only confirms the string looks like `xyz.myshopify.com` (or other configured storefront domains) — it has no way to know whether that domain matches the shop that actually issued the presented session token. The library's own documentation demonstrates deriving `shop` straight from `req.query.shop` rather than from the decoded token's `dest`: [3](#0-2) 

Contrast this with the safer pattern used elsewhere in the codebase (e.g., `perform-token-exchange.ts` and the remix/react-router `authenticate.ts` strategies), where `shop` is explicitly derived from the verified JWT's `dest` claim before being used: [4](#0-3) [5](#0-4) 

However, `tokenExchange` itself — the shared, documented, public API surface — provides no such enforcement, meaning any integrator following the documented usage (or simply calling the exported function directly with attacker-influenced `shop`) is vulnerable regardless of how carefully they otherwise validate other inputs.

### Impact Explanation
This is directly analogous to the LienToken bug class: a value that should be derived from a cryptographically-verified source (the lien's actual owner / the session token's actual `dest`) is instead taken from an untrusted, attacker-influenced input and used as the destination of a sensitive "push" operation (a lien payment / the app's OAuth client secret). Here, the outbound POST containing `client_id` and `client_secret` in plaintext is sent to whatever `shop` value the caller supplies, as long as it's shaped like a valid Shopify domain — this is a **secret disclosure** vector: an attacker in control of, or able to intercept traffic at, the target shop's domain (or any confusable/attacker-registered `.myshopify.com` store) can capture the app's client secret. A leaked client secret allows full impersonation of the app for OAuth, undermining every merchant using it.

### Likelihood Explanation
Likelihood depends on integrators following the documented pattern (`shop` from `req.query.shop`) verbatim, which the library's own reference documentation explicitly recommends. Any app author who does not independently re-derive and cross-check `shop` against the session token's `dest` before calling `tokenExchange` is exposed. Since a Shopify session token is routinely available to anyone who can install/open a test shop (Shopify's own dev/test stores are freely creatable), an attacker only needs a valid token for *some* shop to trigger a request targeting *any* `shop` value they choose.

### Recommendation
Inside `tokenExchange()`, use the payload returned by `decodeSessionToken` and require that its `dest` (stripped of scheme) matches the sanitized `shop` parameter before making the outbound request; throw an `InvalidJwtError` (or a new dedicated error) on mismatch, exactly as the express/remix/react-router call sites already do manually. This closes the gap for any caller regardless of how they obtain `shop`.

### Proof of Concept
1. Attacker installs a free/test Shopify store `attacker-shop.myshopify.com` and embeds the vulnerable app, obtaining a legitimately signed session token `T` with `dest = https://attacker-shop.myshopify.com`.
2. Attacker sends a request to the app's `/auth` (or wherever `shopify.auth.tokenExchange` is invoked per the documented pattern) with `?shop=victim-or-attacker-controlled-domain.myshopify.com` and the `Authorization: Bearer T` header (or `id_token` param).
3. The app calls `shopify.auth.tokenExchange({ sessionToken: T, shop: 'victim-or-attacker-controlled-domain.myshopify.com', ... })`.
4. `tokenExchange()` verifies `T`'s signature (valid, since it's a real token for `attacker-shop`) but never compares `T.dest` to the `shop` argument, then POSTs `{client_id, client_secret, subject_token: T, ...}` to `https://victim-or-attacker-controlled-domain.myshopify.com/admin/oauth/access_token`.
5. If the attacker controls that domain (e.g., registers `attacker-shop2.myshopify.com` and can log outbound requests, or exploits any interception opportunity), the app's `client_secret` is disclosed to them.

export function sanitizeShop(config: ConfigInterface) {
  return (shop: string, throwOnInvalid = false): string | null => {
    let shopUrl = shop;
    const domainsRegex = [
      'myshopify\\.com',
      'shopify\\.com',
      'myshopify\\.io',
      'shop\\.dev',
    ];

    // Add domains from transformations (both source and target)
    if (config.domainTransformations) {
      domainsRegex.push(...getTransformationDomains(config));
    }

    const shopUrlRegex = new RegExp(
      `^[a-zA-Z0-9][a-zA-Z0-9-_]*\\.(${domainsRegex.join('|')})[/]*$`,
    );

    const shopAdminRegex = new RegExp(
      `^admin\\.(${domainsRegex.join('|')})/store/([a-zA-Z0-9][a-zA-Z0-9-_]*)$`,
    );

    const isShopAdminUrl = shopAdminRegex.test(shopUrl);
    if (isShopAdminUrl) {
      shopUrl = shopAdminUrlToLegacyUrl(shopUrl) || '';
    }

    const sanitizedShop = shopUrlRegex.test(shopUrl) ? shopUrl : null;
    if (!sanitizedShop && throwOnInvalid) {
      throw new InvalidShopError('Received invalid shop argument');
    }

    if (sanitizedShop && config.domainTransformations) {
      return applyDomainTransformations(sanitizedShop, config);
    }

    return sanitizedShop;
  };
