### Title
Missing Early Return in `validate_delegate_action_key` Allows Nonce Advancement on Rejected `DepositWithFunctionCall` DelegateAction — (`runtime/runtime/src/actions.rs`)

---

### Summary

In `validate_delegate_action_key`, on protocol versions below 85 (before `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError`), a missing `return Ok(())` after setting the `DepositWithFunctionCall` error allows execution to fall through to the `receiver_id` and `method_name` checks. When those subsequent checks pass, the access-key nonce is unconditionally advanced even though the action was already flagged as invalid. The caller (`apply_delegate_action`) then sees `result.result.is_err()` and suppresses receipt generation — but the nonce mutation in the trie has already been committed. This is the structural analog of M-05: a secondary condition silently bypasses the primary rejection gate and causes unintended state mutation.

---

### Finding Description

`validate_delegate_action_key` enforces three sequential constraints for FunctionCall-permission access keys:

1. Exactly one action, and it must be `FunctionCall`
2. `deposit` must be zero (`DepositWithFunctionCall` check)
3. `receiver_id` must match the permission's receiver
4. `method_name` must be in the allowed list

On protocol version < 85, after setting `result.result = Err(DepositWithFunctionCall)` at line 638–641, there is no `return Ok(())`. Execution falls through to the `receiver_id` check at line 651. If `receiver_id` matches (no error, no return), and the method-name check at line 661 also passes (no error, no return), execution reaches the nonce-update block at lines 685–699:

```rust
match nonce_update {
    DelegateNonceUpdate::AccessKey => {
        access_key.nonce = delegate_nonce.nonce();
        set_access_key(state_update, sender_id.clone(), public_key.clone(), &access_key);
    }
    ...
}
```

The nonce is written to the trie. Control then returns to `apply_delegate_action`, which checks `result.result.is_err()` (still `DepositWithFunctionCall`) and returns early without emitting a receipt. The action is rejected at the application layer, but the nonce mutation is permanent.

The fix — `return Ok(())` guarded by `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError.enabled(...)` — was introduced at protocol version 85. The minimum supported protocol version is 84, meaning the unfixed path is still compiled and reachable. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

---

### Impact Explanation

**Nonce burning without action execution.** A relayer submits a `SignedDelegateAction` where:
- The sender signed it with a FunctionCall-permission access key
- The inner `FunctionCall` carries `deposit > 0` (forbidden by the key's permission)
- The `receiver_id` in the delegate action matches the key's `receiver_id`
- The `method_name` is in the key's allowed list (or the list is empty)

The runtime sets `DepositWithFunctionCall`, skips the early return, passes the receiver and method checks, and writes the new nonce to trie. `apply_delegate_action` then suppresses receipt generation. The sender's access-key nonce is permanently incremented without any action executing. The sender must use a strictly higher nonce for all future actions signed by that key.

A secondary impact is **error masking**: when `deposit > 0` AND `receiver_id` mismatches, the `DepositWithFunctionCall` error is overwritten by `ReceiverMismatch`, hiding the true rejection reason from the sender. [7](#0-6) 

---

### Likelihood Explanation

Triggering the nonce-burning path requires:
1. A sender who holds a FunctionCall-permission access key
2. A signed `DelegateAction` from that sender with `deposit > 0` (the sender made an error, or was socially engineered by the relayer)
3. The `receiver_id` and `method_name` in the action match the key's permission

Condition 2 is the limiting factor. A sender using a FunctionCall key with a deposit is already violating the key's own restriction, so this scenario arises from user error or a malicious relayer who convinced the user to sign such an action. The relayer can then exploit the missing return to burn the nonce rather than simply rejecting the action off-chain.

The bug is present on any node running protocol version 84 (`MIN_SUPPORTED_PROTOCOL_VERSION`). Protocol version 85 (stable: 86) carries the fix. [6](#0-5) 

---

### Recommendation

The fix is already present in the codebase and activates at protocol version 85:

```rust
if ProtocolFeature::FixDelegateActionDepositWithFunctionCallError
    .enabled(apply_state.current_protocol_version)
{
    return Ok(());
}
```

Once protocol version 84 is no longer reachable (i.e., `MIN_SUPPORTED_PROTOCOL_VERSION` is raised to ≥ 85), the legacy fall-through branch and its protocol-version guard can be removed entirely, leaving only the unconditional `return Ok(())` after the `DepositWithFunctionCall` error is set. This matches the pattern used correctly in `verify_function_call_permission` for regular transactions, which returns immediately on `DepositWithFunctionCall` without any fall-through. [1](#0-0) [8](#0-7)

### Proof of Concept

The repository's own test suite demonstrates both the buggy and fixed behaviors:

```
test_delegate_deposit_with_function_call_reports_receiver_mismatch_before_fix
  → protocol version 84: DepositWithFunctionCall is overwritten by ReceiverMismatch

test_delegate_deposit_with_function_call_reports_deposit_error
  → protocol version 85: DepositWithFunctionCall is correctly preserved and returned
```

To trigger nonce burning on protocol version 84, construct a `DelegateAction` where:
- `public_key` is a FunctionCall key on `sender_id` with `receiver_id = "token.near"`, empty method list
- Inner action: `FunctionCall { method_name: "ft_transfer", deposit: 1, ... }`
- `receiver_id` in the delegate action: `"token.near"` (matches permission)

Submit via a relayer. The runtime sets `DepositWithFunctionCall`, falls through both subsequent checks (receiver matches, method list empty → all methods allowed), reaches the nonce update, writes the incremented nonce to trie, then suppresses the receipt. The sender's nonce is permanently advanced; no transfer occurs. [9](#0-8) [10](#0-9)
