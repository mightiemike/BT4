### Title
Unbounded memory allocation from an attacker-controlled array-length felt in deprecated syscall calldata parsing, causing sequencer node crash/DoS - (File: `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`)

### Summary
`read_felt_array` in the deprecated (Cairo0) syscall hint processor reads an array length directly from Cairo VM memory as a raw `Felt` written by contract bytecode, converts it to `usize`, and immediately passes it to `felt_range_from_ptr`/`vm.get_integer_range` to read (and effectively allocate) that many elements — with no upper bound check analogous to the `SIERRA_ARRAY_LEN_BOUND` check enforced elsewhere in the codebase for Cairo1 entry points and calldata.

### Finding Description
`read_felt_array` reads the declared array size as an arbitrary felt from memory that is fully controlled by the executing Cairo0 contract's bytecode (the contract writes its own syscall-request struct fields, including array lengths, before invoking a syscall): [1](#0-0) 

It converts the felt to `usize` and forwards it unchecked to `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)`: [2](#0-1) 

By contrast, the analogous Cairo1/new-syscall path derives array size from the *difference between two verified pointers* rather than trusting a raw felt value, and the Starknet OS explicitly bounds calldata sizes against `SIERRA_ARRAY_LEN_BOUND` before use: [3](#0-2) [4](#0-3) 

No equivalent bound exists on the value read by `read_felt_array` in the deprecated path. A `usize` on a 64-bit node can represent values up to ~1.8×10^19; a malicious Cairo0 contract (declared and deployed by any unprivileged account) can set this array-size field to a huge but `usize`-representable value (e.g. near `u64::MAX`) when it invokes a deprecated syscall that consumes a felt array (e.g. calldata for `library_call`/`call_contract`, or the `send_message_to_l1` payload), causing the VM to attempt to materialize/allocate a correspondingly huge `Vec<Felt>`. This mirrors the CVE-2025-65834 pattern: an unchecked, attacker-supplied "size" parameter (width×height there, array length here) drives a memory allocation whose scale is never validated against a sane bound before the allocation is attempted.

### Impact Explanation
An oversized allocation attempt from `Vec::with_capacity`/`get_integer_range` on a huge size either aborts the process (Rust's global allocator calls `handle_alloc_error`, which aborts rather than returning a catchable `Result`, when the allocation fails) or induces severe memory pressure/OOM on the node executing/validating the transaction. Because this is reachable from ordinary transaction execution (a single `INVOKE` transaction targeting a deployed Cairo0 contract that issues the vulnerable syscall), it can be triggered by any unprivileged sender against any sequencer or full node that executes the transaction — including during block building, mempool validation re-execution, and Starknet OS re-execution/proving — creating a crash or resource-exhaustion condition that could halt block production or diverge honest nodes if only some nodes crash while others do not.

### Likelihood Explanation
Cairo0 contract classes remain a supported, declarable, and callable class type in the sequencer (deprecated but not removed), and the vulnerable code path is exercised on every deprecated syscall that reads a felt array from VM memory. Crafting a Cairo0 contract that writes an arbitrarily large size felt into its own syscall-request memory layout requires no special privilege — only the ability to declare and invoke a contract, which is available to any account holder. This makes the likelihood of triggering the code path high, though the ultimate impact depends on undocumented (in this repo) behavior of the external `cairo-vm` crate's `get_integer_range`/allocation internals, which could not be fully verified from this codebase alone since `cairo-vm` is an external dependency, not vendored source in this repository.

### Recommendation
Add an explicit upper bound check on the array-size felt in `read_felt_array` (and any other deprecated-syscall array-length reads) before it is used to size an allocation or memory read — mirroring the `SIERRA_ARRAY_LEN_BOUND`-style check already used for Cairo1 calldata — and reject the syscall with a catchable execution error if the declared length exceeds a sane maximum (e.g., bounded by remaining gas/memory or a fixed protocol constant), rather than trusting the raw felt value end-to-end.

### Proof of Concept
1. Declare and deploy a Cairo0 (`DEPRECATED_DECLARE`/legacy) contract whose bytecode manually constructs a syscall request (e.g. for `library_call` or `send_message_to_l1`) and writes an array-length field equal to a very large `usize`-representable value (e.g. `2^62`) instead of the true number of following elements, leaving the data pointer valid but pointing to a small/empty segment.
2. Submit a standard `INVOKE` transaction that calls this contract's entry point, triggering the syscall.
3. During execution, `read_felt_array` reads the crafted length and calls `felt_range_from_ptr(vm, array_data_start_ptr, huge_size)` → `vm.get_integer_range(ptr, huge_size)`, attempting to allocate/read a `Vec<Felt>` of size `huge_size` on the executing node.
4. Observe process abort (allocation failure) or severe memory/CPU exhaustion on any node (gateway validator, batcher, or full node) that executes this transaction — a denial-of-service reachable from a single unprivileged transaction.

Note: Full confirmation of the crash-vs-graceful-error behavior depends on the internal implementation of `cairo-vm`'s `get_integer_range`/memory-reading routines, which are external to this repository and were not directly inspectable here; this should be verified against the specific `cairo-vm` version pinned by the sequencer.

```rust
pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
}
```

```rust
pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
```

```rust
pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
```
