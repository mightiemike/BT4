### Title
Inconsistent reward accounting between `MortgageService.computeReward` and `VoteRewardUtil.computeReward` (TVM native vote reward path) - (File: `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
The reported bug class is "two functions that should account the same state variable identically instead compute/update it differently, causing permanent accounting divergence." The java-tron analog is the existence of two independent implementations of witness-vote reward accounting that are supposed to produce the same result but diverge: `MortgageService.computeReward` (used by the ordinary `VoteWitnessActuator`/`WithdrawBalanceActuator` transaction path) and `VoteRewardUtil.computeReward` (used by the TVM native-contract vote/reward opcodes reachable from any broadcast smart-contract call).

### Finding Description
`MortgageService.computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)` explicitly splits the reward window at `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()`, routing the portion of the interval before that cycle through `getOldReward` (which uses `rewardViCalService.getNewRewardAlgorithmReward` or a per-cycle `computeReward(cycle, votes)` loop) and only using the Vi-delta ("new algorithm") calculation for the remainder: [1](#0-0) 

By contrast, `VoteRewardUtil.computeReward`, which backs all TVM-triggered voting/reward operations (`VoteWitnessProcessor`, `WithdrawRewardProcessor`, `UnfreezeBalanceProcessor`, and `Program.withdrawRewardAndCancelVote`), unconditionally computes the reward for the entire `[beginCycle, endCycle)` window using only the Vi-delta method, with no split around `newRewardAlgorithmEffectiveCycle` and no fallback to the old per-cycle reward computation: [2](#0-1) 

The TVM path is reachable from an ordinary broadcast `TriggerSmartContract` transaction via `Program.voteWitness`, `VoteWitnessProcessor.execute`, `WithdrawRewardProcessor.execute`, or `UnfreezeBalanceProcessor.execute`: [3](#0-2) [4](#0-3) [5](#0-4) 

Both code paths update the same underlying accounting state (`account.allowance`, `delegationStore.beginCycle/endCycle`), but they compute the reward amount to add to that state differently whenever the window queried spans the pre/post `newRewardAlgorithmEffectiveCycle` boundary (or spans cycles whose Vi has not yet been fully backfilled by the asynchronous `RewardViCalService`). This is structurally identical to the Primex `decreaseTraderDebt` vs `batchDecreaseTradersDebt` issue: one accounting routine applies a compensating/legacy calculation step that the other omits, so the same logical operation yields two different numeric outcomes depending on which code path a user's transaction goes through.

### Impact Explanation
A TVM contract account (or any account voting/withdrawing rewards through a deployed smart contract using the `vote`/`withdrawreward`/`unfreeze` TVM opcodes) that has a reward window spanning the `newRewardAlgorithmEffectiveCycle` cutover, or spanning cycles for which `RewardViCalService`'s asynchronous Vi backfill has not yet completed, will receive an `allowance` credit computed purely from `getWitnessVi` deltas instead of the historically-correct value that the standard actuator path (`MortgageService`) would compute. This can under-credit or over-credit the account's `allowance`/balance relative to what the "canonical" reward accounting produces, i.e., a divergence in a value that is directly convertible to TRX via `WithdrawRewardProcessor`/`WithdrawBalanceActuator`. Because `beginCycle`/`endCycle` bookkeeping is advanced past the window regardless of which formula was used, any shortfall is permanently unrecoverable (the reward for that window can never be recomputed), mirroring the "permanent loss" characterization of the source report.

### Likelihood Explanation
Likelihood is currently uncertain/moderate. It requires (a) `VMConfig.allowTvmVote()` enabled, (b) TVM vote/reward opcodes being invoked (fully attacker/user-controllable via a normal contract deployment and broadcast `TriggerSmartContract` transaction), and (c) the reward window queried actually crossing the `newRewardAlgorithmEffectiveCycle` boundary or landing on cycles whose Vi has not yet been backfilled by `RewardViCalService` (an asynchronous background service gated on checkpoint flush, per `RewardViCalService.maybeRun`/`startRewardCal`). This is plausible on any newly-migrated or newly-started node, or shortly after the algorithm-switch activation, but I could not fully verify from the index whether `getWitnessVi` for cycles before the effective cycle is always guaranteed to be backfilled before user transactions can observe it (this depends on `RewardViCalService` timing/`isDone()` gating that I could not trace end-to-end within the available tool budget).

### Recommendation
Make `VoteRewardUtil.computeReward` consistent with `MortgageService.computeReward`: either (a) have `VoteRewardUtil` delegate to the same reward-computation routine used by `MortgageService` (e.g., expose `MortgageService`'s split logic through the `Repository`/`DelegationStore` abstraction so both code paths share one implementation), or (b) explicitly replicate the `newRewardAlgorithmEffectiveCycle` split and `getOldReward` fallback inside `VoteRewardUtil.computeReward` so that both the legacy actuator flow and the TVM native-contract flow always compute identical rewards for identical `(beginCycle, endCycle, votes)` inputs.

### Proof of Concept
Not independently executable from the index alone; the divergence is demonstrable by unit-testing both `MortgageService.queryReward`/`withdrawReward` and `VoteRewardUtil.queryReward`/`withdrawReward` with the same account/vote state where the queried window `[beginCycle, endCycle)` straddles `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()` (or before `RewardViCalService` finishes backfilling `witnessVi` for early cycles) and observing that the two returned reward amounts differ, e.g. by adapting the existing `framework/src/test/java/org/tron/common/runtime/vm/VoteTest.java#testRewardAlgorithmNo1` scenario to also assert equality against `MortgageService.queryReward` for the same contract account.   private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
