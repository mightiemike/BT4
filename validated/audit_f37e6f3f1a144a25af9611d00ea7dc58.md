## Finding

### Title
Replay-verify's `ensure_match_transaction_info` skips checkpoint-hash comparison, letting a divergent state root pass as "verified" - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by Aptos's replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`, used by `testsuite/replay-verify/main.py` to validate mainnet archives, and `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that locally re-executed transactions match the `TransactionInfo` recorded in the archived/authenticated ledger. The function deliberately omits comparison of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values, as the code's own TODO admits.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but never recomputes or compares any state-checkpoint-related hash field of `TransactionInfo`:
- `state_checkpoint_hash` (root of the Sparse Merkle Tree state)
- `hot_state_checkpoint_hash`
- `position_state_checkpoint_hash`

The comment directly documents the gap: [2](#0-1) 

This comparator is the sole verification step used by `Verifier::execute_and_verify` in the replay-on-archive tool: [3](#0-2) 

That tool re-executes transactions read from a backup/archive against `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` to decide pass/fail — it never independently recomputes the JMT/state root from the resulting write sets and compares it to the state-checkpoint hash carried in the accumulator-proven `TransactionInfo`. Since state-checkpoint hashes are exactly the field that binds a transaction's write set into the globally-verified state Merkle root (as seen in the correct, hash-checked usage pattern in `storage/aptosdb/src/db/test_helper.rs` and `storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs`, which do assert `state_root_hash == manifest.root_hash`), skipping it here means the tool can declare "replay succeeded" even when the resulting state tree diverges from the one committed and signed by the validator set.

### Impact Explanation
Replay-verify is the process by which Aptos gains confidence that archived, ledger-info-signed history is reproducible and that no corruption/divergence occurred in a hard fork, storage bug, or malicious archive tampering scenario. Because the comparator used by this tool never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a state-root-corrupting bug elsewhere in the write-set → storage-commit pipeline (e.g., a hard-fork-only state divergence, a corrupted restore, or a tampered archive with an incorrect root but well-formed events/write-set/status/gas) would be silently accepted as "verified" by this tool, defeating its intended integrity guarantee. This directly matches the required impact class "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Wrong ... state proof accepted as valid," since the tool exists specifically to catch such divergence and does not.

### Likelihood Explanation
The gap is unconditional (not feature-gated) and always exercised whenever `db-tool replay-on-archive` or the debugger's mismatch-printing path is run; the TODO in the code confirms the authors are aware but have not yet closed it. Any bug that corrupts the state Merkle root (an area otherwise defended by other checks in the live commit path) but leaves per-transaction write-set/events/gas/status alone would go completely undetected by replay-verify, i.e., the exact family of "hard-fork-only divergence" bugs replay-verify is meant to detect.

### Recommendation
Extend `ensure_match_transaction_info` to recompute the state root(s) from applied write sets (or otherwise obtain the resulting state view root) and compare it against `txn_info.state_checkpoint_hash()` (and, when present, `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`) whenever the transaction is a checkpoint boundary, returning an error on mismatch just as is done for `write_set_hash`/`event_root_hash`. Until fixed, `replay_on_archive`/replay-verify results should not be treated as proof that state roots reproduce correctly.

### Proof of Concept
Not applicable as an on-chain exploit (this is a tooling/verification gap, not an on-chain state-corruption primitive). Demonstration path: run `db-tool replay-on-archive` (or the aptos-debugger `print_mismatches` path) against an archive whose `TransactionInfo.state_checkpoint_hash` was altered (or produced by a divergent execution) while write-set bytes/events/status/gas remain valid for the given transaction; `ensure_match_transaction_info` at [4](#0-3)  returns `Ok(())`, and the replay-verify pipeline reports success despite the state root being wrong.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
