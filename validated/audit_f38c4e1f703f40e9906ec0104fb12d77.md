**Reasoning summary** (the equality was checked before/after and holds):

The claimed equality is: *exactly one `MinerPaymentSchedule` row with `miner=true` should exist per tenure (consensus_hash), and `get_scheduled_block_rewards_at_block` must not return duplicates for the same coinbase height.*

Tracing the path:

1. A second Nakamoto block with its own `TenureChange(BlockFound)+Coinbase` for the *same* `tenure_consensus_hash` can only be `is_wellformed_tenure_start_block()`-valid if its `previous_tenure_end` equals its own `header.parent_block_id` [1](#0-0) , and `check_nakamoto_tenure` further requires that `previous_tenure_end` point to the *actual previous distinct tenure's* last block, not to the first tenure-start block of the same tenure [2](#0-1) . This forces the second "duplicate coinbase" block to be a **sibling fork** of the first tenure-start block (both extending the same prior-tenure parent), not a second block appended after it in the same linear history.

2. `insert_miner_payment_schedule` keys each row by `index_block_hash = StacksBlockId(consensus_hash, block_hash)` [3](#0-2) , so the two sibling blocks produce two *distinct* rows, never colliding under one key.

3. Maturation lookup (`get_matured_miner_reward_schedules` → `get_scheduled_block_rewards_at_block`) resolves the reward-bearing block by walking the **specific tip's ancestor chain** via `get_header_by_coinbase_height(tip_index_hash, matured_coinbase_height)` and then queries by that single resolved `index_block_hash` [4](#0-3) . This is fork-relative, not tenure-ID-relative: any given chain tip has exactly one ancestor at a given coinbase height, so it can never see both sibling rows simultaneously.

4. Only one of the two sibling forks can ever become (or remain) the canonical Nakamoto tip; the sortition DB's `set_stacks_block_accepted_at_tip` explicitly handles this "benign fork" scenario by picking a single canonical tip per burn view [5](#0-4) . Blocks built after that point only ever extend one fork, so `get_scheduled_block_rewards_at_block` for that fork's ancestry only ever contains one `miner=true` coinbase row per tenure.

5. Additionally, getting a second tenure-start block signed at all requires bypassing the signer-level `DuplicateBlockFound` guard (`validate_tenure_change_payload` in both v1 and v2 signer chainstate), which explicitly rejects a second tenure-change proposal once a block has been signed in that tenure [6](#0-5) [7](#0-6) . Getting both duplicate coinbase blocks signed would require compromising a majority of signers, which is out of scope per the rules.

Since the fork-relative, ancestor-walk design of `get_matured_miner_reward_schedules`/`get_scheduled_block_rewards_at_block` already prevents any single chain history from containing two `miner=true` coinbase rows for one tenure — independent of the signer-level guard — the claimed double-coinbase-payment equality break does not materialize.
