### Title
Wallet Contract's `has_in_flight_tx` lock can become permanently stuck after any callback receipt failure, freezing the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (used to let Ethereum-style implicit accounts sign NEAR transactions via `rlp_execute`) guards against concurrent/out-of-order execution with a single boolean flag, `has_in_flight_tx` [1](#0-0) . This flag is set to `true` whenever `rlp_execute` schedules a promise, and is only ever reset to `false` as the *first statement* of one of four `#[private]` callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) . This is structurally the same bug class as the reported DODO `_closetrade` issue: a state-clearing/fund-releasing step is coupled to an external, attacker/relayer-influenced condition (whether the callback receipt succeeds), and if that step reverts, the "unlock" never happens - leaving the position (here, the wallet) permanently stuck.

### Finding Description
`rlp_execute` is the sole entry point that lets a relayer submit a signed Ethereum-style transaction on behalf of an eth-implicit account; it checks `has_in_flight_tx` and rejects new calls while `true` [7](#0-6) . On success it sets `has_in_flight_tx = true` and returns a chained `Promise` [2](#0-1) .

The only code paths that clear the flag are the private callbacks scheduled via `.then(...)`, e.g. `rlp_execute_callback` [8](#0-7) , `address_check_callback` [9](#0-8) , and `nep_141_storage_balance_callback` [10](#0-9) . Each of these callbacks clears the flag and then continues doing more work (parsing a `PromiseResult`, possibly constructing and dispatching another chained `Promise`, e.g. `NEP-141 storage_deposit` + `ft_transfer` in `nep_141_storage_balance_callback` at lines 224-272, or the relayer-refund transfer in `rlp_execute_callback` at lines 296-317).

Per the runtime's documented action-receipt execution model, a receipt's state changes are only durable if the whole receipt succeeds; on any failure of the receipt (including running out of gas or a panic during subsequent logic), the runtime performs a full rollback of the receipt's state changes and none of them are persisted: "Commit or rollback: success commits with `ReceiptProcessing`; failure calls `state_update.rollback()`, discarding all state changes from the receipt" [11](#0-10) . Because `self.has_in_flight_tx = false` is written at the *start* of the callback, any later failure inside that same receipt (out-of-gas while constructing/dispatching a nested cross-contract promise, or any other action failure) discards that write along with everything else, leaving the persisted contract state exactly as it was before the callback ran - i.e. `has_in_flight_tx == true`.

Since `rlp_execute` unconditionally rejects all further calls while `has_in_flight_tx` is `true`, and there is no other function that resets the flag, the wallet becomes permanently unable to process any further Ethereum-style transaction: the user can never move funds, add/remove keys, or interact with any contract via this wallet again. Gas budgets for these callbacks are explicitly attached per-call by the wallet's own logic and, in the NEP-141 path, scale with `action.gas()` which is itself derived from attacker/relayer-influenced input parsed out of the signed Ethereum transaction (`callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` at line 440, similarly at line 417 for `address_check_callback`), so a relayer or user (accidentally or intentionally) supplying transaction parameters that make the callback's actual gas usage exceed its allotted budget (or otherwise cause the receipt to fail) can trigger this permanent freeze in a single reachable transaction.

### Impact Explanation
If any callback receipt of `WalletContract` fails for any reason (gas exhaustion during nested promise construction, unexpected panic, or any other action failure), `has_in_flight_tx` is rolled back to `true` and never gets cleared again, since only the private callbacks - which are now unreachable because they can only be produced by `rlp_execute`, which itself is now permanently blocked - can clear it. This permanently freezes the wallet contract's ability to execute any future user-authorized action, including recovering the underlying NEAR balance. This matches the "permanently frozen funds" impact category.

### Likelihood Explanation
Reachable directly from a single relayer-submitted `rlp_execute` transaction; the relayer/user only needs to supply a transaction whose emulated action (e.g., an ERC-20/NEP-141 transfer requiring a `storage_deposit` + `ft_transfer` chain, or an address-registrar lookup) causes the corresponding callback receipt to fail after `has_in_flight_tx = false` has already been queued for write but before the receipt commits. This can happen accidentally via an under-provisioned/miscalculated gas value in the signed Ethereum transaction, or a bug/edge case in one of the nested `Promise` constructions, without requiring any privileged access, malicious validator, or network-level compromise.

### Recommendation
Do not tie the `has_in_flight_tx` unlock to the success of the whole callback receipt. Options: (1) reset the flag via a genuinely infallible statement that cannot be rolled back with the rest of the receipt (e.g., perform the reset in its own minimal, first-and-only action so a subsequent failure in a *newly scheduled* promise cannot roll it back), or (2) add a permissionless recovery/timeout path so the flag can be cleared if a callback never lands within some deadline. More generally, statically bound the gas required by each callback body (independent of externally supplied `action.gas()`) so its own logic cannot itself run out of gas.

### Proof of Concept
1. A relayer/user submits `rlp_execute` with a signed Ethereum transaction whose target is an unregistered NEP-141 receiver, triggering the `nep_141_storage_balance_of` → `nep_141_storage_balance_callback` path [12](#0-11) .
2. `rlp_execute` sets `has_in_flight_tx = true` and returns the promise [13](#0-12) .
3. `nep_141_storage_balance_callback` executes: it first sets `self.has_in_flight_tx = false` [4](#0-3) , then (since the receiver is unregistered) constructs a chained `storage_deposit` + transfer + `rlp_execute_callback` promise [14](#0-13) , using a gas budget (`callback_gas`) derived from the attacker/relayer-controlled `action.gas()` [15](#0-14) .
4. If this receipt fails for any reason after the flag-clearing write (e.g., insufficient gas for the nested promise construction, or any other action error), the entire receipt - including the `has_in_flight_tx = false` write - is rolled back per the documented commit/rollback semantics [11](#0-10) .
5. `has_in_flight_tx` remains `true` in persisted state forever; every subsequent `rlp_execute` call is rejected with "transaction already in progress" [16](#0-15) , permanently freezing the wallet.

Note: I was not able to fully trace/verify a concrete failure trigger inside `nep_141_storage_balance_callback`'s own logic from the indexed code alone (e.g. exact gas cost of the nested `Promise::new(...).function_call(...).function_call(...)` construction vs. the statically computed `callback_gas`), since the full gas-accounting details for promise-batch construction were not present in the retrieved context. A Devin session with full repo access would be needed to construct and run an exact PoC transaction that forces the callback receipt to fail after the flag write but before commit.
