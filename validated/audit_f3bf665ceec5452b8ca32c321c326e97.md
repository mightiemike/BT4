### Title
Unbounded prefix-scan DoS in `GetDelegatedResourceAccountIndexV2` RPC via attacker-grown delegation index - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
The `getV2Index`/`getWithPrefix` path used by the anonymous, unauthenticated `GetDelegatedResourceAccountIndexV2` gRPC call performs an unbounded full prefix scan and in-memory sort over every delegation relationship (`from`/`to`) ever recorded for a queried address, with no cap on the number of entries. Because creating a delegation record is cheap and attacker-controlled (via `DelegateResourceContract`/`FreezeBalanceContract` broadcast transactions), an attacker can grow this per-address dataset arbitrarily large and then force any node (their own or a victim's) to do O(n) work — reading, materializing, and sorting the whole set — on every subsequent RPC query for that address. This mirrors the reported bug class: unbounded array growth from cheap repeated writes, later consumed in one unbounded read/loop with no cap, causing resource exhaustion.

### Finding Description
`DelegatedResourceAccountIndexStore.getWithPrefix` performs two `prefixQuery` calls (one for `V2_FROM_PREFIX+address`, one for `V2_TO_PREFIX+address`), converts every matching DB entry into a `DelegatedResourceAccountIndexCapsule`, and then **sorts the entire resulting list** by timestamp before returning it: [1](#0-0) 

There is no limit, pagination, or size cap anywhere in this path. `getV2Index` is invoked directly from `Wallet.getDelegatedResourceAccountIndexV2`: [2](#0-1) 

which is wired to the anonymous, unauthenticated gRPC endpoint `GetDelegatedResourceAccountIndexV2` (available on full node, solidity node, and PBFT node services): [3](#0-2) [4](#0-3) 

The number of entries scanned is fully attacker-controlled: each `DelegateResourceContract` (validated/executed by `DelegateResourceActuator`) or the legacy `FreezeBalanceContract` delegate path (`FreezeBalanceActuator.delegateResource`) creates one new persisted key under `V2_FROM_PREFIX`/`V2_TO_PREFIX` (or the legacy `FROM_PREFIX`/`TO_PREFIX`) per distinct owner/receiver pair: [5](#0-4) [6](#0-5) 

An attacker can broadcast many cheap transactions (small delegated amount, one new receiver/owner address per transaction — no dedup or size limit is enforced against the *cumulative* number of distinct counterparties in `DelegateResourceActuator.validate`/`execute`, only per-call resource/balance checks) to grow the `V2_FROM_PREFIX`/`V2_TO_PREFIX` entries for a single address to an arbitrarily large count over time. Each write transaction pays only the normal fixed bandwidth/energy cost for a native contract call; the read side (`GetDelegatedResourceAccountIndexV2`) is a free, unauthenticated RPC query that is not gas-metered and has no per-request cap, so the cost asymmetry (cheap linear writes vs. expensive read-time O(n log n) scan+sort) is the same shape as the reported `massUpdateRewards`/`removeIdFromList` bug: an ever-growing list, walked in full by an unbounded loop/sort in a single call.

### Impact Explanation
Any node exposing the gRPC (or corresponding HTTP: `/wallet/getdelegatedresourceaccountindexv2`) API can be driven to perform large in-memory scans and sorts on demand. Since these RPC calls run on the node's serving path and are not part of consensus/TVM execution (no energy metering applies to reads), an attacker who has built up a sufficiently large delegation index for a target address can repeatedly invoke this query to consume CPU and memory across full nodes, solidity nodes, and PBFT nodes, degrading their ability to serve legitimate RPC traffic — a denial-of-service condition against the RPC-API surface. It does not directly corrupt consensus state or leak keys, so severity is bounded to availability degradation of the queried API/node rather than chain-wide consensus divergence.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to first invest in growing the delegation set for an address they control (paying normal transaction fees for many cheap `DelegateResourceContract`/`FreezeBalanceContract` transactions), which is economically feasible since delegated amounts can be minimal and each entry only costs one ordinary transaction fee. Once the index is large, the exploitation step (repeatedly calling the free RPC) is trivial and requires no special privilege — it is exposed on the public/anonymous RPC/HTTP API of any full, solidity, or PBFT node.

### Recommendation
- Add pagination or a hard cap to `DelegatedResourceAccountIndexStore.getWithPrefix`/`getV2Index` (and the legacy `getIndex`) so the number of `prefixQuery` results materialized and sorted per call is bounded.
- Consider limiting the number of distinct delegation counterparties a single address can accumulate, or requiring the query API to accept offset/limit parameters similar to `GetPaginatedNowWitnessList`/`GetPaginatedProposalList`.
- Add rate limiting specifically for `GetDelegatedResourceAccountIndex(V2)` RPC/HTTP endpoints.

### Proof of Concept
1. From an attacker-controlled account, freeze a small amount of TRX for resource (`FreezeBalanceV2Contract`) sufficient to delegate minimal balances.
2. Repeatedly broadcast `DelegateResourceContract` transactions delegating a minimal amount from the attacker address to a large number (e.g., tens of thousands) of distinct freshly generated receiver addresses. Each transaction creates a new `V2_FROM_PREFIX`/`V2_TO_PREFIX` entry via `DelegatedResourceAccountIndexStore.delegateV2` [5](#0-4) .
3. Call the public gRPC/HTTP `GetDelegatedResourceAccountIndexV2` for the attacker address; the node executes `getWithPrefix`, performing a full prefix scan of all accumulated entries and sorting them in memory before responding [7](#0-6) .
4. Repeat step 3 concurrently/rapidly to consume CPU/memory on the target node, degrading its ability to serve other RPC requests.

(Note: exact scaling/thresholds at which this becomes practically disruptive were not measured in this review — verifying real-world impact would require load-testing a running node, which is outside the scope of static code inspection.)

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
