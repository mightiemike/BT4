### Title
Zero-lamport single-ref accounts are retained (unpurged) until the next full snapshot, allowing unbounded storage/index bloat between full snapshots - ([File: accounts-db/src/accounts_db.rs])

### Summary
The reported Sherlock issue is an economic-incentive bug class: an actor (the order-fulfillment owner) pays an upfront cost (gas to fulfill orders) expecting to be reimbursed later by users claiming their orders, but when the claim is not economically worthwhile to the counterparty, the upfront cost is never recouped, leaving the payer to accumulate unrecoverable loss/bad debt until conditions change. The closest concrete analog in Agave's `AccountsDb` is the handling of zero-lamport ("closed") accounts: `clean_accounts` performs work to identify these dead accounts, but it defers actually reclaiming their storage and index space until a *full* snapshot slot advances past them, per the incremental-snapshot-consistency requirement. Until that full snapshot occurs, the "debt" (retained dead storage, uncleaned index entries, and duplicated bookkeeping structures) accumulates, and any unprivileged user creating/closing accounts can grow this backlog.

### Finding Description
`construct_candidate_clean_keys` explicitly gates purging of zero-lamport accounts behind the latest full snapshot slot: [1](#0-0) 

The comment at the top of this method states the storages holding only "tombstones" (i.e., zero-lamport single-ref accounts) cannot be purged by the normal reclaim path until they are no longer newer than the latest full snapshot, "since until then its tombstones must be retained for an incremental snapshot to propagate the deletion": [2](#0-1) 

The `AccountsDb` struct maintains a dedicated, unbounded set for this deferred work: [3](#0-2) 

Every ordinary user transaction that closes an account (sets its lamports to zero) adds an entry that must wait in this backlog. `clean_accounts` still has to do bookkeeping work each pass (retaining the set, tracking `dirty_stores`, checking `has_only_tombstones`), even though the actual space cannot be reclaimed, meaning the validator repeatedly "pays" scan/CPU cost for slots it cannot yet clean — mirroring the report's pattern of paying cost upfront (gas / CPU) without being able to recoup the benefit (space reclamation) until an external, not-fully-controllable event occurs (a claim by the user / a full snapshot by the snapshot scheduler).

If the full snapshot interval is large (which the validator itself warns is likely to "negatively impact background cleanup tasks in accounts-db"), or if incremental snapshots are enabled while full snapshots lag, an attacker or even ordinary high-throughput usage that closes many accounts can grow `zero_lamport_accounts_to_purge_after_full_snapshot` and the corresponding tombstone-holding storages without bound between two full snapshots, since these queued entries are only drained when `latest_full_snapshot_slot_advanced_since_clean` flips true: [4](#0-3) 

### Impact Explanation
This causes disproportionate storage and CPU cost on the validator: dead/zero-lamport account storages and their associated index bookkeeping (`dirty_stores`, `zero_lamport_accounts_to_purge_after_full_snapshot`) accumulate between full snapshots, growing accounts-db's on-disk footprint and the amount of work `clean_accounts` must repeatedly perform per pass without being able to reclaim space, purely as a function of ordinary account-closing activity from unprivileged users. This matches the "disproportionate storage and CPU cost" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires either a validator configuration with a large full-snapshot interval (which the codebase itself flags as risky) or sustained high volume of zero-lamport account churn from ordinary transactions during the interval between full snapshots. No special privilege is needed by the party generating the zero-lamport accounts — any user can close/zero out an account they control via normal transactions, so the trigger is fully unprivileged, though the magnitude of impact scales with the configured full-snapshot cadence.

### Recommendation
Consider bounding the deferred zero-lamport purge backlog (e.g., a size/age-based cap that forces a full-snapshot-independent reclamation path, or accelerating full snapshot cadence when the backlog grows too large) so that storage and CPU cost imposed by uncleared zero-lamport accounts cannot grow unbounded purely as a function of full-snapshot interval and user-driven account churn.

### Proof of Concept
Not independently reproduced beyond the existing unit test `test_clean_purges_zero_lamport_single_ref_at_reclaim`, which demonstrates the deferral mechanism (an account's zero-lamport purge is gated by `latest_full_snapshot_slot` and only completed once the full snapshot slot advances past it): [5](#0-4) 
A full exploit/PoC demonstrating unbounded growth under a hostile transaction pattern was not constructed here; this would require driving repeated account creation/closure across many slots while the full-snapshot interval is held large, which is best validated with a live/replay harness rather than static analysis.

#[test]
fn test_clean_purges_zero_lamport_single_ref_at_reclaim() {
    let db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    let account_key1 = Pubkey::new_unique();
    let account_key2 = Pubkey::new_unique();
    let account_key3 = Pubkey::new_unique();
    let account1 = AccountSharedData::new(1, 0, AccountSharedData::default().owner());
    let account0 = AccountSharedData::new(0, 0, AccountSharedData::default().owner());

    // Store into slot 0
    db.store_for_tests((0, [(&account_key1, &account1)].as_slice()));
    db.store_for_tests((0, [(&account_key2, &account1)].as_slice()));
    db.store_for_tests((0, [(&account_key3, &account1)].as_slice()));
    db.add_root_and_flush_write_cache(0);

    // Make account_key1 and account_key3 in slot 0 outdated by updating in rooted slots 1
    // and 3 with zero lamport accounts
    db.store_for_tests((1, &[(&account_key1, &account0)][..]));
    db.add_root(1);
    db.store_for_tests((3, &[(&account_key3, &account0)][..]));
    db.add_root(3);
    // Flushes all roots without clean
    db.flush_rooted_accounts_cache_without_clean();

    // Gate zero-lamport purging above slot 1: account_key1's zero-lamport update is
    // covered by the full snapshot, account_key3's is not.
    db.set_latest_full_snapshot_slot(1);

    // Clean reclaims the outdated slot 0 entries, unreffing them at reclaim. That leaves
    // each zero-lamport update as its account's only ref.
    db.clean_accounts(Some(3), false);

    // account_key1's purge is not gated, so the same clean pass purges the account: the
    // pubkey is removed from the index and slot 1's storage, left with no live accounts,
    // is dropped.
    assert_eq!(db.accounts_index.ref_count_from_storage(&account_key1), 0);
    assert!(!db.accounts_index.contains(&account_key1));
    assert_no_storages_at_slot(&db, 1);

    // account_key3's purge is gated behind the full snapshot, so it is instead marked
    // zero-lamport single-ref in slot 3's storage, which now holds only such accounts and
    // is queued for clean via dirty_stores rather than shrink.
    assert_eq!(db.accounts_index.ref_count_from_storage(&account_key3), 1);
    assert_eq!(
        db.get_and_assert_single_storage(3)
            .num_zero_lamport_single_ref_accounts(),
        1
    );
    assert!(db.dirty_stores.contains_key(&3));
    assert!(!db.shrink_candidate_slots.lock().unwrap().contains(&3));

    // Once the full snapshot advances past slot 3, clean purges account_key3 and drops
    // slot 3's storage.
    db.set_latest_full_snapshot_slot(3);
    db.clean_accounts(Some(3), false);
    assert!(!db.accounts_index.contains(&account_key3));
    assert_no_storages_at_slot(&db, 3);
