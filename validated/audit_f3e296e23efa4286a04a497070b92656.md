### Title
Global-contract authority bound to a mutable `AccountId` allows privilege takeover after account deletion/recreation - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`GlobalContractIdentifier::AccountId` lets a global contract be referenced (and later re-deployed / updated) by an `AccountId` rather than an immutable code hash. Any account that has `AccountContract::GlobalByAccount(id)` set will execute whatever code is currently registered under that `id`. The runtime authorizes redeployment of that code purely by checking that the *current* signer of the `DeployGlobalContract` action equals `id` — it never verifies that this is the *same entity* that originally registered the identifier. Because NEAR account IDs are not permanent identities (accounts can be deleted via `DeleteAccount` and the same name/ID later re-claimed by an unrelated party), an attacker who reclaims a previously-used `AccountId` inherits full authority to push new code to every account in the network that still references `GlobalByAccount(id)`, without any of those accounts' consent. This mirrors the Keystone CVE-2014-0204 pattern: authorization is granted based on an ID whose binding to a “role”/entity is assumed stable but is not actually enforced to be unique/immutable over time, so a second, unrelated entity that acquires the same ID inherits privileges intended for the first.

### Finding Description
- `use_global_contract` (`runtime/runtime/src/global_contracts.rs:76-109`) sets `AccountContract::GlobalByAccount(id.clone())` on a consumer account, purely from the `GlobalContractIdentifier::AccountId(id)` supplied in the `UseGlobalContract` action. This binds the consumer's contract execution to whatever code is stored under the trie key `GlobalContractCode { identifier: AccountId(id) }` at call time.
- Redeployment/update of that shared code happens through `action_deploy_global_contract` → `initiate_distribution` (`global_contracts.rs:25-63`, `143-171`). For `GlobalContractDeployMode::AccountId`, the identifier used is simply `account_id.clone()` — i.e., whichever account is currently signing/executing the `DeployGlobalContract` action (`global_contracts.rs:151-158`). There is no check tying this to any original registrant identity or ownership token — only "the account currently named `id` may deploy under identifier `AccountId(id)`".
- The nonce used to prevent stale/duplicate distributions (`increment_nonce`/`check_and_update_nonce`, `global_contracts.rs:173-189`, `248-269`) is stored under `TrieKey::GlobalContractNonce { identifier }`, keyed only by the `AccountId`, **independent of the underlying `Account` record's lifecycle**. It is not reset, invalidated, or tied to account existence. So even if the account named `id` is deleted and the name later reclaimed by a completely different owner, the global-contract code and nonce state for that identifier persist and remain updatable.
- NEAR's account model permits deletion (`DeleteAccount` action, handled in `runtime/runtime/src/actions.rs`) and subsequent re-creation of the same `AccountId` (top-level names via the registrar/`near` root account flow, or sub-accounts via their direct parent, per `protocol-model/spec/accounts-keys.md:71`, "Creation ... a non-top-level id must be a direct sub-account of the predecessor"). Once an `AccountId` is freed, any party legitimately entitled to create that name (e.g., through the standard `.near` registrar contract flow that ordinary users interact with to register/re-register names) becomes the account holding that ID going forward.
- Consequence: the *new* holder of `id` can call `DeployGlobalContract` with `GlobalContractDeployMode::AccountId`, and the resulting `GlobalContractDistributionReceipt` (via `apply_distribution_current_shard`, `global_contracts.rs:191-246`) overwrites the code stored at `TrieKey::GlobalContractCode { identifier: AccountId(id) }` across shards. Every other account still holding `AccountContract::GlobalByAccount(id)` (set up before the original owner's account was deleted) will begin executing this new, attacker-controlled code the moment it is distributed — with full access to those accounts' own state and balances, since global-contract code executes in the context (storage/balance) of the calling account, per NEAR's contract execution model.
- This is a clear analog of CWE-269/CVE-2014-0204: privilege ("who may push code for identifier `X`") is granted based purely on possessing the string ID `X` at the current moment, with no mechanism ensuring the entity currently holding `X` is the same entity the many `GlobalByAccount(X)` consumers originally trusted.

### Impact Explanation
Any account that adopted `GlobalByAccount(id)` is effectively delegating its own execution/authority to whoever currently controls the account named `id`. If that account is deleted and its name reclaimed by an attacker (a routine, permitted operation for ordinary users, not requiring any validator/operator privilege), the attacker gains the ability to silently redeploy arbitrary WASM code that will subsequently execute as every dependent account. Because global-contract code runs with the calling account's own balance/storage context, malicious code can transfer funds out of every such account, effectively enabling unauthorized value movement/drain across potentially many unrelated accounts that never re-consented to trust the new owner. This satisfies the "concrete unauthorized value movement" bar from the validation criteria.

### Likelihood Explanation
Reachable entirely from ordinary, unprivileged transactions: (1) the original owner (or anyone, since `DeleteAccount` requires only full-access-key authorization on that account, which is under the owner's normal control) deletes the account; (2) any user re-registers the freed name through the standard account-creation path (top-level names via the `near` registrar contract that any user can call, sub-account names via the direct-parent flow); (3) the new owner submits a normal `DeployGlobalContract` action with `AccountId` mode. No validator collusion, no network-layer manipulation, and no special operator permission is required — only that some other accounts had previously opted into `GlobalByAccount(id)` for that name and remain unaware the underlying account changed hands.

### Recommendation
Bind `GlobalByAccount` authority to something immutable rather than the mutable `AccountId` string alone — e.g., require the deploy/redeploy path to also verify a persisted "creation epoch"/account nonce or a dedicated ownership token created at first deployment, and invalidate or require re-registration of the `GlobalContractCode`/`GlobalContractNonce` state for an `AccountId` identifier whenever the underlying account is deleted (tie the global-contract record's validity to the account's internal creation nonce/generation so a freshly re-created account cannot inherit the deploy rights or overwrite the previous code silently). At minimum, consumers of `UseGlobalContract` by `AccountId` should be able to detect/pin a specific "generation" of the identifier so a later account-name reuse cannot transparently swap the code they execute.

### Proof of Concept
1. Account `alice.near` deploys a global contract with `GlobalContractDeployMode::AccountId` (`DeployGlobalContractAction`), publishing code under `GlobalContractIdentifier::AccountId("alice.near")`.
2. Many other accounts (`u1`, `u2`, …) call `UseGlobalContract` referencing `AccountId("alice.near")`; `use_global_contract` sets their `AccountContract::GlobalByAccount("alice.near")` (`global_contracts.rs:95-98`).
3. `alice.near` is deleted via a normal `DeleteAccount` action (the account's owner does this, or the key is later exposed/abandoned — either way this is a permitted user action, not a protocol violation).
4. An unrelated attacker re-registers the now-free name `alice.near` through the standard account-creation flow (e.g., via the `near` top-level registrar contract that ordinary users use to claim names).
5. The attacker, now the legitimate holder of `alice.near`, submits `DeployGlobalContract` with `GlobalContractDeployMode::AccountId` and malicious code. `initiate_distribution` computes `id = GlobalContractIdentifier::AccountId("alice.near")` (`global_contracts.rs:155-158`) purely from the current signer, with no check against the previous deployer, and the nonce continues incrementing from its pre-existing stored value (`increment_nonce`, unaffected by the account having been deleted/recreated).
6. The distribution receipt is applied (`apply_distribution_current_shard`) and overwrites `TrieKey::GlobalContractCode { identifier: AccountId("alice.near") }` with the attacker's code.
7. Every account still holding `AccountContract::GlobalByAccount("alice.near")` (`u1`, `u2`, …) now executes the attacker's code on their next function call, executing with their own balance/storage context — enabling the attacker to drain or otherwise misuse those accounts without their consent.
