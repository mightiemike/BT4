## Finding: Unbounded `PendingInbounds` scan lets attacker-inflated inbound spam blow up ballot-finalization gas cost

### Title
Unbounded linear scan over attacker-inflatable `PendingInbounds` set during inbound ballot finalization enables gas-exhaustion DoS of `MsgVoteInbound` processing - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
The external report's bug class is: an attacker cheaply inflates an unbounded, attacker-reachable collection, and a *synchronous, gas-metered* on-chain operation later has to loop over that entire collection, causing legitimate transactions to hit gas limits. Push Chain has a structural analog in `x/uexecutor`'s `PendingInbounds` audit-trail map: every unique source-chain event creates an entry, and every single ballot-termination event triggers a full, unbounded `Walk` over the *entire* map to locate the matching entry.

### Finding Description
`RecordInboundVote` [1](#0-0)  creates a new `PendingInboundEntry` keyed by `utx_key = sha256(source_chain:tx_hash:log_index)` the first time *any* validator votes on a source-chain event, and this happens inside `VoteInbound`, which is invoked for every real (even zero-value/garbage) inbound observation [2](#0-1) . Note that `ValidateBasic()` — the check applied before the vote is recorded — does not reject zero-amount or otherwise near-worthless events; only `ValidateForExecution()`, which runs after ballot finalization, rejects them [3](#0-2) . This means an attacker can cheaply generate a very large number of distinct, valid-looking (but worthless) source-chain events that validators will faithfully vote on and that will each occupy a `PendingInbounds` entry until their own ballot reaches quorum.

Every time *any* inbound ballot (not just the attacker's) reaches a terminal state, `x/uvalidator`'s ballot machine invokes `AfterBallotTerminal` → `afterInboundBallotTerminal`, which performs a **full unindexed walk of the entire `PendingInbounds` collection** to find the entry whose variant carries the finalizing ballot ID: [4](#0-3) 

This walk is explicitly justified in-code as acceptable because "the pending set is small and transient" — an assumption that does not hold once an attacker deliberately grows the set. The walk executes synchronously inside the gas-metered `MsgVoteInbound` transaction of whichever validator's vote triggers finalization (via `VoteOnBallot` → `CheckIfFinalizingVote` → `MarkBallotFinalized` → hooks) [5](#0-4) . As documented, `PendingInbounds` entries are removed only when ALL ballot variants for that utx_key reach a terminal state [6](#0-5) , so the set's size at any moment is bounded only by how many distinct in-flight inbound events exist — directly controllable by an attacker flooding cheap/dust events on any registered source chain.

### Impact Explanation
As the attacker inflates `PendingInbounds` with many concurrently in-flight (not-yet-finalized) inbound events, the cost of `afterInboundBallotTerminal`'s O(n) walk grows linearly with the backlog size, and it is paid on **every** ballot finalization system-wide — including finalizations of legitimate users' unrelated deposits. With enough concurrent attacker-submitted events (analogous to the thousands of tiny bids in the original report), a validator's `MsgVoteInbound` transaction that happens to finalize a ballot can run out of gas mid-execution, reverting that validator's vote. Since the hook re-runs on every subsequent finalizing vote against the same bloated backlog, this can repeatedly block finalization of legitimate inbounds, delaying UniversalTx creation (and therefore fund crediting) for honest users, and increasing the on-chain cost validators must pay to keep voting — a DoS on the inbound-observation pipeline reachable purely through ordinary (if abusive) unprivileged event submission, without requiring any malicious validator.

### Likelihood Explanation
No stake, governance, or validator privilege is required by the attacker — only the ability to submit many cheap/dust transactions to a registered source chain's gateway contract that satisfy `ValidateBasic()` (non-empty `source_chain`, `tx_hash`, `sender`, `log_index`, and a recognized `tx_type`) but need not carry real value. Honest validators will observe and vote on all of them exactly as designed. The severity is bounded by per-chain gas costs of generating garbage events and by the size the `PendingInbounds` backlog can reach before enough finalizations accumulate to trip gas limits, so this is a resource-exhaustion/likelihood question rather than a certain full-halt, but the underlying design flaw (no cap, no index, full-collection scan on the hot path) is clearly present and unguarded.

### Recommendation
Do not use `PendingInbounds.Walk` to locate the entry to update on ballot termination. Maintain a secondary index mapping `ballot_id -> utx_key` (populated in `RecordInboundVote` alongside the variant) so `afterInboundBallotTerminal` can do an O(1) lookup instead of an O(n) scan. Additionally, consider bounding the number of concurrently pending (unfinalized) inbound entries per source chain, or requiring a minimum bonded/economic cost per distinct inbound observation, to prevent unbounded growth of `PendingInbounds` from cheap spam.

### Proof of Concept
Conceptual reproduction path (matches existing test scaffolding in `test/integration/uexecutor/pending_inbound_audit_trail_test.go` and `execute_inbound_gas_test.go`):
1. Register a source chain and have an attacker submit N (e.g. tens of thousands) of distinct, low/zero-value inbound events (unique `tx_hash`/`log_index`) to the gateway contract.
2. Have honest validators observe and submit `MsgVoteInbound` for all N events, but stagger so quorum is not reached instantly for all of them — `PendingInbounds` grows to size N before most entries finalize (this mirrors the natural multi-block round-trip of collecting votes from multiple validators).
3. Submit a normal, legitimate `MsgVoteInbound` that reaches quorum and triggers `MarkBallotFinalized` → `AfterBallotTerminal`. Measure the gas consumed by `afterInboundBallotTerminal`'s `PendingInbounds.Walk` as a function of N, and show it grows linearly, eventually approaching/exceeding a typical block gas limit as N increases (analogous to the `test_reachGasLimit` measurement in the original report, but instrumented on the `PendingInbounds.Walk` call in `x/uexecutor/keeper/ballot_hooks.go`).

```go
// ValidateBasic does minimal sanity checks needed to accept a vote.
// Only fields required to identify the inbound and create a UTX key are validated here.
// Execution-level validation (amount, addresses, payload, recipient) is deferred to
// ValidateForExecution so that invalid inbounds still produce an on-chain UTX record
// (with a failed PCTx / revert) instead of silently dropping the vote and leaving
// user funds stuck in the gateway.
func (p Inbound) ValidateBasic() error {
	// Validate source_chain (must follow CAIP-2 format) — needed for UTX key
	chain := strings.TrimSpace(p.SourceChain)
	if chain == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain cannot be empty")
	}
	if !strings.Contains(chain, ":") {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain must be in CAIP-2 format <namespace>:<reference>")
	}

	// Validate tx_hash — needed for UTX key
	if strings.TrimSpace(p.TxHash) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "tx_hash cannot be empty")
	}

	// Validate sender — needed for revert recipient fallback
	if strings.TrimSpace(p.Sender) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "sender cannot be empty")
	}

	// Validate log_index — needed for UTX key
	if strings.TrimSpace(p.LogIndex) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "log_index cannot be empty")
	}

	// Validate tx_type enum — needed to route execution
	if _, ok := TxType_name[int32(p.TxType)]; !ok || p.TxType == TxType_UNSPECIFIED_TX {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid tx_type: %v", p.TxType)
	}

	return nil
}
```

```go
func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
```

```go
// CheckIfFinalizingVote inspects whether the just-cast vote pushes the ballot
// over its threshold and, if so, drives the finalization through
// MarkBallotFinalized — the single canonical write path for terminal status
// transitions, which applies CEI-style ordering on the secondary indexes.
func (k Keeper) CheckIfFinalizingVote(ctx context.Context, b types.Ballot) (types.Ballot, bool, error) {
	ballot, isFinalizing := b.IsFinalizingVote()
	if !isFinalizing {
		return b, false, nil
	}

	k.Logger().Debug("ballot reached finalization threshold",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)

	if err := k.MarkBallotFinalized(ctx, ballot.Id, ballot.Status); err != nil {
		return ballot, false, errors.Wrap(err, "failed updating finalized ballot")
	}

	k.Logger().Debug("ballot finalized",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)
	return ballot, true, nil
```

```markdown
### `PendingInbounds`

- **Created** by the FIRST validator vote on a given inbound (`RecordInboundVote`
  inside `VoteInbound`). The chain learns about the source-chain event from
  validator observations.
- **Keyed** by `utx_key = sha256(source_chain:tx_hash:log_index)`.
- **Variant-aware:** when validators marshal slightly different `Inbound` bytes
  for the same logical event (different decoded fields, formatting, etc.), each
  unique payload becomes its own `InboundVariant` inside the entry, with its
  own `ballot_id`, `voters[]`, and `terminal_status`.
- **Removed** when ALL related ballot variants reach a terminal state. If any
  variant ended `PASSED`, the existing post-finalization path in `VoteInbound`
  produced a `UniversalTx`. If ALL variants ended `EXPIRED`/`REJECTED`, the
  full per-variant audit trail is moved to `ExpiredInbounds` for the future
  escape-hatch refund flow.
- The cleanup-on-terminal logic lives in `keeper/ballot_hooks.go` (the
  `BallotHooks` impl wired into `x/uvalidator`).
```
