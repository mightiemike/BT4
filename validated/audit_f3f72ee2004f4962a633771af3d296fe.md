## Analysis

I traced the external report's core invariant — "a value used to authorize/finalize state must be independently validated before being trusted" — to Aptos's replay/replay-verify tooling, specifically `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs`.

This function is the authoritative comparator used by `storage/db-tool/src/replay_on_archive.rs` (`execute_and_verify`, calling `executed_outputs[idx].ensure_match_transaction_info(...)` at line 392) and by `aptos-move/aptos-debugger/src/aptos_debugger.rs` (`print_mismatches`) to decide whether a freshly re-executed `TransactionOutput` "matches" the `TransactionInfo` that was actually committed to the ledger accumulator.

### Title
Replay-verify comparator omits checkpoint-hash fields, allowing divergent state roots to pass verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` (lines 2139–2204) checks `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash`, but explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — fields that are part of the committed, accumulator-hashed `TransactionInfo`. The code contains its own acknowledging TODO at lines 2197–2202.

### Finding Description
`TransactionInfo` (both `V0` and `V1`) carries `state_checkpoint_hash`, and `V1` additionally carries `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, all of which are committed on-chain and bound into the transaction accumulator root (verified elsewhere via full struct equality, e.g. `LedgerUpdateOutput::ensure_transaction_infos_match` at `execution/executor-types/src/ledger_update_output.rs:92-114`, which does compare full `TransactionInfo` equality). However, the weaker comparator `ensure_match_transaction_info` used specifically for ad-hoc replay/verification tooling does not check these checkpoint hashes at all: [1](#0-0) 

### Impact Explanation
Both consumers of this function — `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` and `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches` — rely on it as the pass/fail signal for whether re-executed history reproduces the historically committed state: [2](#0-1) [3](#0-2) 

If a code change (accidental regression or deliberately introduced divergence) alters only the state (or hot-state, or "trading-native" position-state) root computed during a state checkpoint without altering the write set, events, gas, or status, `replay_on_archive` and the debugger's mismatch printer will both report a clean match even though the produced ledger state diverges from the historically committed one. This is exactly the "hard-fork-only divergence during commit, replay ... or proof verification" category called out as in-scope: the on-chain accumulator root would differ, but the tool designed to catch exactly this class of bug is blind to it.

### Likelihood Explanation
Likelihood is Medium: this requires either (a) a bug that affects only state/hot-state/position-state root computation while leaving the write set, events, gas, and status unchanged (plausible, since checkpoint hashes are computed by a separate `DoStateCheckpoint` code path from the one producing write sets/events), or (b) a malicious/careless contributor deliberately altering checkpoint-hash logic. Since `replay_on_archive` and `replay-verify` CI are the primary safety nets before mainnet upgrades to detect exactly such divergence, a gap here directly weakens the pre-release integrity gate rather than the live consensus path itself.

### Recommendation
Extend `ensure_match_transaction_info` to accept and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (all available on `TransactionInfo`) whenever they are `Some` on the expected `TransactionInfo`, mirroring the strict equality already performed by `LedgerUpdateOutput::ensure_transaction_infos_match`. The TODO already present in the code (lines 2197-2202) should be implemented before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, and ideally sooner, since it affects all replay-verify usage today, not just the trading-native feature.

### Proof of Concept
Not applicable as a live-network exploit — this is a tooling/verification gap rather than an executable attack against a running node. Concretely: construct (or find) a code change that alters `DoStateCheckpoint`'s computed `state_checkpoint_hash` (e.g., a bug in Merkle-tree update ordering) without touching write-set/event/gas/status outputs, run `replay_on_archive` or the debugger over historical transactions spanning that change, and observe `ensure_match_transaction_info` reporting success while the actual `state_checkpoint_hash` in `TransactionInfo` differs from the locally recomputed one.

### Caveat
This is a genuinely local, provable gap, but note it is already flagged by an in-repo `TODO` comment (not a "hidden" defect), and it affects offline verification tooling rather than the live consensus/commit path itself (the live path's `LedgerUpdateOutput::ensure_transaction_infos_match` does perform full-field comparison). I present it because it matches the requested "replay ... or proof verification" impact category with an exact, locally-verifiable root cause, but flag the reduced severity relative to a defect in the actual state-commit path.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
