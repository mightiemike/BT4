## Analog Found

### Title
Linear O(n) scan over unbounded on-chain allowlist in Vault DON request authorization causes DoS - (`File: core/capabilities/vault/allow_list_based_auth.go`)

### Summary
The reported bug describes a Solidity `onlyAllowed()` modifier that performs an exhaustive array scan over an ever-growing `allowedContracts` list on every privileged call, creating a denial-of-service risk as the list grows unbounded. The equivalent pattern exists in the Vault capability's authorization path: `allowListBasedAuth.fetchAllowlistedItem` performs a linear scan over the full in-memory `allowListedRequests` slice for every single incoming Vault request, and that slice is populated from an on-chain registry that any (unprivileged) workflow owner can append to.

### Finding Description
`AuthorizeRequest` in `core/capabilities/vault/allow_list_based_auth.go` calls `findAllowlistedItemWithRetry`, which fetches the full allowlist snapshot via `r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)` and then calls `fetchAllowlistedItem`, which does a plain `for _, item := range allowListedRequests` linear comparison against the request digest: [1](#0-0) 

This is invoked on every request that reaches `AuthorizeRequest`, and with retries it can be executed up to `allowListBasedAuthRetryCount+1` times per request: [2](#0-1) 

The backing list `w.allowListedRequests` is only pruned by expiry timestamp, not bounded by count, in `syncAllowlistedRequests`: [3](#0-2) 

`GetAllowlistedRequests` returns a full copy of this slice on every call, meaning the cost of both the copy and the subsequent linear scan grows with the number of active (non-expired) allowlisted requests: [4](#0-3) 

Since any workflow owner is able to add allowlist entries on-chain (subject only to expiry, not to any cap), and each entry remains in the active list until its `ExpiryTimestamp` passes, an attacker can flood the registry with a large number of allowlist requests with long expirations, causing this list to grow large during that window. This directly mirrors the reported Solidity bug class: an unbounded, append-mostly list is exhaustively scanned on every use of a hot-path authorization check.

### Impact Explanation
Every Vault request authorization does an O(n) copy and O(n) scan against this list, `n` being unbounded and attacker-influenced. If the list grows large, this degrades the latency of every legitimate Vault request and can starve CPU or memory bandwidth on the Vault DON node, resulting in a denial-of-service against Vault request authorization — the exact impact category (unauthorized resource exhaustion in a privileged trust-boundary check) called out in the report.

### Likelihood Explanation
Any workflow owner (unprivileged w.r.t. node internals) can submit allowlist requests on-chain, and there appears to be no maximum bound / cap on the number of simultaneously active allowlisted requests enforced by the syncer or the auth path — only time-based expiry pruning is applied. This makes the attack straightforward to trigger by continuously registering new allowlisted requests with future expirations.

### Recommendation
Replace the linear array scan with a map/index (e.g., keyed by `RequestDigest`, similar to the recommended `mapping(address => bool)` fix in the original report) so lookups in `fetchAllowlistedItem` are O(1), and/or enforce an upper bound on the number of active allowlisted requests per owner/globally that the syncer will hold in memory.

### Proof of Concept
1. As a workflow owner, repeatedly call the on-chain allowlist-request function (consumed via `GetActiveAllowlistedRequestsReverseMethodName`/`TotalAllowlistedRequestsMethodName`) to register many allowlisted requests with far-future `ExpiryTimestamp` values.
2. The Vault DON's `syncAllowlistedRequests` polling loop syncs and retains all non-expired entries in `w.allowListedRequests`, growing the in-memory list unbounded over time. [5](#0-4) 
3. Each subsequent legitimate Vault request triggers `AuthorizeRequest` → `findAllowlistedItemWithRetry` → `fetchAllowlistedItem`, each of which copies and linearly scans the full (now large) list, with retries multiplying the cost. [6](#0-5) 
4. As the list size grows, authorization latency/CPU cost increases proportionally, degrading or denying service to legitimate Vault requests.

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

func (r *allowListBasedAuth) fetchAllowlistedItem(allowListedRequests []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, digest [32]byte) *workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
	for _, item := range allowListedRequests {
		if item.RequestDigest == digest {
			return &item
		}
	}
	return nil
}

func (w *workflowRegistry) syncAllowlistedRequests(ctx context.Context) {
	ticker := w.getTicker(defaultTickIntervalForAllowlistedRequests)
	w.lggr.Debug("starting syncAllowlistedRequests")
	for {
		select {
		case <-ctx.Done():
			w.lggr.Debug("shutting down syncAllowlistedRequests, %s", ctx.Err())
			return
		case <-ticker:
			newAllowListedRequests, totalAllowlistedRequests, head, err := w.getAllowlistedRequests(ctx, w.contractReader)
			if err != nil {
				w.lggr.Errorw("failed to call getAllowlistedRequests", "err", err)
				continue
			}
			w.allowListedMu.Lock()
			// Prune expired requests
			activeAllowlistedRequests := []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest{}
			expiredRequestsCount := 0
			for _, request := range w.allowListedRequests {
				if int64(request.ExpiryTimestamp) > time.Now().Unix() {
					activeAllowlistedRequests = append(activeAllowlistedRequests, request)
				} else {
					expiredRequestsCount++
				}
			}

			activeAllowlistedRequests = append(activeAllowlistedRequests, newAllowListedRequests...)

func (w *workflowRegistry) GetAllowlistedRequests(_ context.Context) []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
	w.allowListedMu.RLock()
	defer w.allowListedMu.RUnlock()
	allowListedRequests := make([]workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, len(w.allowListedRequests))
	copy(allowListedRequests, w.allowListedRequests)
	return allowListedRequests
}
