No vulnerability found for this question.

**Analysis:**

The premise misunderstands what "non-deterministic" means in this context. `TraversalContext::legacy_check_visited` at [1](#0-0)  and its shared implementation `check_visited_impl` at [2](#0-1)  are pure functions of the `visited` `BTreeMap` that is built up deterministically as the interpreter executes bytecode within a single transaction, via `visit_if_not_special_address`/`visit_if_not_special_module_id` at [3](#0-2) .

The only production callers of `legacy_check_visited` (or its sibling `check_is_special_or_visited`) are the dynamic-dispatch natives (`dispatchable_fungible_asset::dispatchable_*`, `account_abstraction::dispatchable_authenticate`) and `function_info::check_dispatch_type_compatibility_impl`, as shown at [4](#0-3) . In all of these, the check is a documented *precondition*: the target module must already have been loaded (and gas-charged for loading) earlier in the same transaction's execution — e.g. via `function_info::load_function_impl` — before dispatch is permitted. This is by design, not an accidental side channel: see the design note that this check exists "purely for backwards-compatibility" to preserve prior legacy gas-charging semantics, not to preserve accept/reject symmetry across arbitrary sibling instructions.

Critically:
- The `visited` set and its evolution are purely a deterministic function of the transaction's own bytecode instruction stream, executed identically by every validator. There is no scope for an "attacker" to introduce divergence between validators — every node computes the exact same `visited` set for the exact same transaction, so consensus/state-commitment determinism is preserved.
- The proof idea in the question ("two transactions differing only in irrelevant preceding instructions that alter the visited set... assert identical accept/reject behavior") is not a valid invariant of the system. Changing which modules get visited *is* a change to the transaction's semantics (since visiting drives gas charging for module loading), so two such transactions are not "otherwise identical" — they legitimately can produce different abort/success outcomes, and this is intended, reproducible, and consensus-safe behavior, not corruption.
- There is no code path where a native reachable from unprivileged bytecode can invoke `legacy_check_visited` in a way that produces different results on different validators for the same transaction; the visited-tracking is entirely local, synchronous, and deterministic per the VM's own interpreter loop as documented in the design notes at [5](#0-4) .

Since the described behavior does not corrupt committed ledger state, does not produce validator disagreement, and does not violate any proof/accumulator/authenticated-response binding, it fails the State-Integrity Gate.
