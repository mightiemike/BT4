### Title
Weak per-bucket hash seed (`with_seeds(random, random, random, random)`) reduces AccountsIndex bucket-map resistance to attacker-crafted pubkey hash flooding - (File: bucket_map/src/bucket.rs)

### Summary
The disk-backed accounts-index bucket map derives the seed used to place pubkeys into a bucket's hash slots from a single 64-bit random value, but instead of feeding independent entropy into the 4 seed slots that `ahash::RandomState::with_seeds` expects, it passes the *same* `random` value four times: `ahash::RandomState::with_seeds(random, random, random, random)` [1](#0-0) . This is the same bug class as the reported `randomFr` issue — a security-relevant randomization value is derived from insufficient/duplicated information instead of full independent entropy, weakening the guarantee the code's own comment claims to provide.

### Finding Description
`Bucket::bucket_index_ix` is the function responsible for hashing a `Pubkey` into a slot index within an index bucket. The comment directly above it states the purpose of `random`: *"the locally generated random will make it hard for an attacker to deterministically cause all the pubkeys to land in the same location in any bucket on all validators"* [1](#0-0) . This is explicitly a hash-flooding/DoS mitigation, analogous in spirit to keyed-hash/Fiat-Shamir randomization: it exists to prevent an adversary who controls the hashed keys (pubkeys, which any unprivileged user can grind/choose) from predicting or forcing collisions.

However, `random` is generated once as a single `u64` via `rng().random()` [2](#0-1) , and this single 64-bit value is then reused for all four seed parameters of `ahash::RandomState::with_seeds`. Passing identical values into all four independent key slots collapses the seed space from the intended 256 bits of independent per-bucket keying material down to effectively 64 bits, and produces a fixed algebraic relationship between the four internal AES-round keys used to mix the hash. This is structurally the same class of flaw as the reported issue: a randomness-dependent security property (unpredictability of the mapping for an attacker-chosen input) is built from less independent information than what's actually needed, making the resulting keyed hash easier to analyze/predict than intended.

The `random` value is persisted to a restart file and reloaded across validator restarts (`OneIndexBucket::random`, `RestartableBucket::set_file`/`get`) so it is a long-lived per-bucket secret, not a one-time value [3](#0-2) . `bucket_index_ix` is used pervasively for placing/finding/creating index entries and in batch insertion paths reachable when accounts are created or updated [4](#0-3) , [5](#0-4) .

### Impact Explanation
The bucket map is only intended to resist hash-flooding, not to be a cryptographically hiding commitment, so this is not a secret-key-recovery bug. The impact is a degraded security margin against pubkey-based hash-flooding: any unprivileged user can create accounts with arbitrary pubkeys (via `create_account`/grinding with `find_program_address` etc.), so an attacker who can observe or partially infer the reduced-entropy seed relationship has a smaller effective search/analysis space to find pubkey sets that collide into the same probe sequence within a bucket, driving up probe lengths, triggering more frequent index resizes (`BucketMapError::IndexNoSpace`), and increasing CPU/latency cost of account index operations for that node — a disproportionate CPU/storage cost impact from unprivileged, low-cost user actions. This affects the accounts index (an AccountsDb component) and is reachable purely from ordinary account creation, not any validator/operator-privileged action.

### Likelihood Explanation
Exploitation strength is intrinsically limited by ahash's design purpose (best-effort, non-cryptographic DoS resistance) and the seed is per-process/per-restart and not attacker-observable directly, so a full break requires additional analysis of ahash's internal round function under identical-key inputs, which was not verified here. The likelihood of a directly-provable practical collision-finding attack is uncertain without deeper cryptanalysis of ahash's `with_seeds` under degenerate (repeated) keys; this is flagged as unverified/uncertain given available tooling.

### Recommendation
Generate four independent random `u64` values (e.g., via `rng().random::<[u64;4]>()`) and pass them individually into `ahash::RandomState::with_seeds`, storing all four (or a derived 256-bit seed) in the restart file (`OneIndexBucket`) instead of a single `random: u64`, matching the number of independent keys the API expects to actually provide the collision-resistance property the accompanying comment claims.

### Proof of Concept
Not independently reproduced with a working collision demonstration; would require empirical analysis of `ahash::RandomState`'s AES-based mixing under `with_seeds(r, r, r, r)` to confirm the reduced diffusion is practically exploitable for hash-flooding versus four independent seeds. The code-level defect (seed derived from a single value reused four times, contradicting the stated anti-flooding intent) is directly verifiable at [2](#0-1)  and [1](#0-0) .

    /// this bucket is now using `file_name` and `random`.
    /// This gets written into the restart file so that on restart we can re-open the file and re-hash with the same random.
    pub(crate) fn set_file(&self, file_name: u128, random: u64) {
        if let Some(mut restart) = self.restart.as_ref().map(|restart| restart.lock().unwrap()) {
            let bucket = restart.get_bucket_mut(self.index);
            bucket.file_name = file_name;
            bucket.random = random;
        }
    }
    /// retrieve the file_name and random that were used prior to the current restart.
    /// This was written into the restart file on the prior run by `set_file`.
    pub(crate) fn get(&self) -> Option<(u128, u64)> {
        self.restart.as_ref().map(|restart| {
            let restart = restart.lock().unwrap();
            let bucket = restart.get_bucket(self.index);
            (bucket.file_name, bucket.random)
        })
