### Title
Unbounded recursion depth in `serde_json::Value` deserialization of deprecated (Cairo0) contract classes causes stack-overflow crash on declare-transaction processing - ([File: crates/starknet_api/src/deprecated_contract_class.rs])

### Summary
The `Program` struct used for Cairo0 (`DeprecatedContractClass`) contract classes stores several fields as raw, untyped `serde_json::Value` (`attributes`, `data`, `hints`, `identifiers`, `main_scope`, `prime`, `reference_manager`, plus `abi` on the outer struct) and is populated directly via `#[derive(Deserialize)]`. [1](#0-0) 
`serde_json::Value`'s generic `Deserialize` implementation recurses once per nested JSON array/object with no configurable depth limit — the same bug class described in the go-ipld-prime advisory (unbounded recursion on nested collections, CWE-674). This is reachable by an unprivileged sender submitting a Declare transaction whose `contract_class` is a `DeprecatedContractClass`/legacy `Program`, e.g. via `BroadcastedDeclareV1Transaction`/`BroadcastedDeclareV2Transaction` on the RPC write API. [2](#0-1) 

### Finding Description
`Program::attributes/data/hints/identifiers/reference_manager` are typed as `serde_json::Value` and deserialized with no schema constraint, allowing arbitrary nesting depth. [1](#0-0) 
The same untyped pattern also underlies `abi: serde_json::Value` in `CairoContractDefinition`, used when hashing Cairo0 contract classes. [3](#0-2) 
A payload consisting of deeply nested JSON arrays (e.g. `[[[[...]]]]`) in any of these fields — analogous to the DAG-JSON `[[[...]]]` payload in the referenced advisory — forces `serde_json`'s recursive descent parser to recurse once per nesting level, with no `MaxDepth`-style guard anywhere in this deserialization path. Because `serde_json::Value` has no built-in depth limiter (unlike the fix shipped for go-ipld-prime), a multi-megabyte payload of a few hundred thousand nested brackets is sufficient to exhaust the thread stack and trigger Rust's unrecoverable stack-overflow abort — this cannot be caught with `catch_unwind`.

Existing gateway/stateless validation checks (`max_contract_bytecode_size`, `max_contract_class_object_size`) operate on the Sierra (Cairo1) `SierraContractClass` path, whose fields are strongly typed (`Vec<Felt>`, etc.) and therefore not subject to this issue. [4](#0-3) 
No equivalent size/structure validation exists before deserialization of the untyped `Program`/`abi` `serde_json::Value` fields on the deprecated Cairo0 declare path.

### Impact Explanation
A crafted Declare transaction body containing deeply nested JSON in the contract class `program`/`abi` fields causes the deserializing process to abort via a fatal, non-recoverable stack overflow at the moment `serde_json::from_...` is invoked. Any node that must parse the identical declare payload (gateway ingestion, mempool nodes, or full nodes re-processing/re-hashing the class during Starknet OS execution or class-hash computation) will hit the same unbounded recursion and crash deterministically, since the vulnerability is triggered purely by the JSON structure, independent of which machine parses it.

### Likelihood Explanation
Reachability depends on whether the legacy/deprecated Cairo0 declare transaction types (`DeclareV1`/`DeclareV2`/`BroadcastedDeclareV1Transaction`/`V2`) remain an actively accepted transaction type at the gateway (governed by `SUPPORTED_TRANSACTION_VERSIONS` in `apollo_gateway_types`), which I was not able to fully confirm in the time available — this repo may currently reject V0/V1/V2 declares outright, which would eliminate this path. I also could not confirm the exact HTTP request body size limit enforced by `apollo_http_server_config` before JSON parsing begins; if that limit is generous (multi-MB), it is more than sufficient to reach recursion depths that exhaust a typical thread stack. Given these open verification points, likelihood should be treated as **unconfirmed/medium** pending explicit confirmation that (a) legacy declare transactions are still routed to this deserialization code, and (b) body-size limits do not already bound the achievable nesting depth to a safe level.

### Recommendation
- Replace unconstrained `serde_json::Value` fields in `Program` (and `CairoContractDefinition::abi`) with a depth-limited deserializer, or wrap `serde_json::from_...` calls on these untrusted fields with an explicit recursion-depth guard (mirroring the `MaxDepth`/`ErrDecodeDepthExceeded` approach adopted upstream for go-ipld-prime).
- Alternatively, run deserialization of untrusted contract-class JSON on a dedicated thread with a bounded/guarded stack combined with `serde_stacker`-style depth checking, or perform a cheap pre-pass depth check (bracket counting) before invoking `serde_json`.
- Confirm and, if necessary, tighten the HTTP body size limits ahead of JSON parsing so that worst-case nesting depth cannot approach thread-stack-exhausting levels.
- Confirm whether legacy declare V0/V1/V2 transaction types are still reachable in production configurations; if not, this reduces the finding to a defense-in-depth issue rather than an actively exploitable one.

### Proof of Concept
```json
{
  "type": "DECLARE",
  "version": "0x1",
  "sender_address": "0x1",
  "max_fee": "0x0",
  "nonce": "0x0",
  "signature": [],
  "contract_class": {
    "program": {
      "attributes": [[[[[ ... repeated ~500,000 times ... ]]]]],
      "builtins": [],
      "data": [],
      "identifiers": {},
      "main_scope": "__main__",
      "prime": "0x1",
      "reference_manager": {}
    },
    "abi": [],
    "entry_points_by_type": {"CONSTRUCTOR": [], "EXTERNAL": [], "L1_HANDLER": []}
  }
}
```
Submitting this to the gateway's declare endpoint (`BroadcastedDeclareV1Transaction`) causes `serde_json` to recurse once per `[` while parsing the `attributes` field; a few hundred thousand nesting levels (a payload on the order of ~1 MB) is sufficient to exhaust the default 1MB–8MB thread stack and crash the parsing process with a fatal stack overflow (SIGSEGV/abort), before any of the existing size-limit validators in `stateless_transaction_validator.rs` run.                 contract_class_object_size,
