## Finding

### Title
Replay-verify tooling never checks the state-checkpoint (state root) hash, so a corrupted state root passes verification silently - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the sole correctness check used by the `db-tool replay-on-archive` and `aptos-debugger` replay pipelines — validates transaction status, gas used, write-set hash (`state_change_hash`), and event root hash, but never validates `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This means the one authenticated value that actually represents "the world state after this transaction" (the Sparse-Merkle/Jellyfish root committed into the `TransactionInfo`, and ultimately into the ledger-info-signed transaction accumulator) is never independently re-derived or compared during replay-verification.

### Finding Description
`ensure_match_transaction_info` explicitly compares only status, gas, write-set hash, and event root hash, with a developer TODO acknowledging the gap: [1](#0-0) 

The comment at the end of the function states plainly:
> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the actual correctness gate used in two production auditing paths:

1. `storage/db-tool/src/replay_on_archive.rs` — the tool operators run to replay/verify archived mainnet history after a database sync, backup, or hard fork: [2](#0-1) 

2. `aptos-move/aptos-debugger/src/aptos_debugger.rs` — used to detect mismatches when replaying past transactions: [3](#0-2) 

Both call sites feed VM-executed `TransactionOutput`s straight from `AptosVMBlockExecutor::execute_block`, which produces write sets/events/status in memory but does **not** run the state-merklization pipeline (`do_state_checkpoint.rs` / `JellyfishMerkleTree` / hot-state root computation) that produces the real, on-chain-authenticated `state_checkpoint_hash`. Because the comparator skips checking that field, a bug anywhere downstream in state-root construction — e.g., in `execution/executor/src/workflow/do_state_checkpoint.rs`'s checkpoint-hash assembly, in the Jellyfish Merkle tree, or in hot-state root computation feeding `TransactionInfoV1::hot_state_checkpoint_hash`/`position_state_checkpoint_hash` — is structurally invisible to replay-verify, even though the write set and events are byte-for-byte identical to what's expected.

This is precisely the scenario replay-verify exists to catch: a state root that diverges from the correct result while everything "downstream-observable" (events, statuses) looks fine — the classic silent-hard-fork-divergence pattern.

### Impact Explanation
Replay-verify (`storage/db-tool replay-verify`, run as part of `testsuite/replay-verify`) is Aptos's primary tool for validating that a restored/backed-up/re-executed history matches the authenticated on-chain record, and it is explicitly used to gate releases against consensus-breaking VM/state divergence. A comparator that can never fail on state-root divergence means:
- A state-root-corrupting bug (in JMT restore, hot-state computation, or checkpoint hashing) introduced in a release can pass replay-verify with 100% "success," giving false confidence that historical state reconstructs correctly.
- Divergence between an archive/restored node's actual Merkle root and the ledger-info-signed root would go undetected until much later (e.g., a live consensus/state-sync failure), instead of being caught during the dedicated verification step meant to catch exactly this class of bug before it manifests as a hard fork.

This matches the explicitly in-scope impact category: "Hard-fork-only divergence during commit, replay, restore, or proof verification" — the proof/verification invariant that replay-verify is supposed to enforce is broken by omission.

### Likelihood Explanation
This isn't a hypothetical exploit requiring an attacker; it's a standing structural gap in a defense-in-depth tool that is triggered on every run of `replay_on_archive`/aptos-debugger replay, and would activate silently whenever any real state-root computation bug is introduced elsewhere in the codebase (e.g., during ongoing development of hot-state / position-state features, as referenced by the surrounding TODO about `COMPUTE_TRADING_NATIVE_STATE_ROOTS`). The bug requires no privileged access — it's a latent correctness gap in the verification path itself.

### Recommendation
Extend `ensure_match_transaction_info` (or its call sites) to also validate `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` whenever they are `Some` in the expected `TransactionInfo`, by actually materializing the state view through the same merklization path used in commit (`do_state_checkpoint.rs`) before comparing. At minimum, replay-verify should compute the state root at checkpoint boundaries and assert equality with the archived `TransactionInfo`'s checkpoint hash before declaring replay verification successful, closing the gap called out by the existing TODO before enabling any feature (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that depends on these fields being trustworthy.

### Proof of Concept
Not directly exploitable by an external attacker; the gap is demonstrated by the code itself: `ensure_match_transaction_info` never dereferences `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` in its comparison logic [4](#0-3) , while `replay_on_archive.rs`'s `execute_and_verify` relies solely on this function's `Ok(())`/`Err` result to decide pass/fail for each replayed transaction [5](#0-4) . Constructing a synthetic `TransactionOutput` with correct events/write-set/status but a deliberately wrong `state_checkpoint_hash` in the paired `TransactionInfo` demonstrates `ensure_match_transaction_info` returns `Ok(())` regardless.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
