Confirmed: `is-in-voting-window` in `signers-voting.clar` is defined but never invoked by `vote-for-aggregate-public-key`. The comment above the function even documents the intended rule ("This vote must happen after the list of signers has been set by the node… the vote is concluded when the threshold… is reached") but the code never enforces that the vote's `reward-cycle` argument is the currently open voting window. `ERR_OUT_OF_VOTING_WINDOW` is defined and even referenced — but the only place it's actually raised is the unrelated "key already set for this cycle" check at line 155, not a temporal/window check. This is structurally identical to the `farm-manager` bug: a validation helper exists (`validate_farm_epochs` / `is-in-voting-window`) whose purpose is to bound an epoch/cycle parameter to a valid (future/current) range, but the call site never invokes it, letting an unprivileged, minority actor supply an out-of-range cycle value that mutates cycle-scoped state.

### Title
`vote-for-aggregate-public-key` never enforces the voting window, letting a stale/foreign-cycle signer mutate any reward cycle's aggregate-key tally - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
`signers-voting.clar` defines a helper `is-in-voting-window` that is documented as the gate for accepting votes (only during the prepare phase of the cycle whose signer set was most recently computed), but `vote-for-aggregate-public-key` never calls it. Any principal who is a signer entry for *some* reward cycle (past, present, or an already-configured future one) can submit a vote tagged with an arbitrary `reward-cycle`, as long as that cycle's aggregate key hasn't yet been finalized.

### Finding Description
`vote-for-aggregate-public-key` (lines 143-199) accepts a caller-supplied `reward-cycle` argument and only checks:
- the aggregate key isn't already set for that cycle (`is-none (map-get? aggregate-public-keys reward-cycle)`),
- the key is well-formed and novel,
- the caller hasn't already voted in that `(reward-cycle, round)`,
- the round only increments by one,
- and, via `get-signer-weight` → `.signers get-signer-by-index`, that `tx-sender` matches the signer recorded at `signer-index` for that specific `reward-cycle`.

None of these checks confirms that `reward-cycle` is the cycle currently in its voting window. `is-in-voting-window` (lines 95-98) — which checks `(is-eq last-cycle reward-cycle)` against `.signers get-last-set-cycle` and `is-in-prepare-phase` — is defined but dead code; it is not referenced anywhere in `vote-for-aggregate-public-key` or any other function in the file. [1](#0-0) [2](#0-1) 

The `.signers` contract keeps `cycle-signer-set` indexed by cycle indefinitely (`map-set cycle-signer-set reward-cycle signers`, `get-signer-by-index` looks it up by the caller-supplied `cycle`), and never expires old entries, so a signer's authority check against a past cycle still succeeds. [3](#0-2) 

Consequently, a signer belonging to reward cycle `N` (or any signer set for which the aggregate key was never finalized, e.g., a cycle skipped because the threshold was never met) can still call `vote-for-aggregate-public-key` with `reward-cycle = N` weeks/cycles after that cycle's window closed, incrementing `tally`/`round-data`, and — if `is-eq new-total threshold-weight` succeeds against a stale `cycle-total-weight` cache — insert a late `aggregate-public-keys` entry for an already-elapsed cycle. This breaks the invariant that "the aggregate public key for reward cycle N is determined only during N's designated prepare-phase voting window, using the frozen signer set observed by all nodes at that time" — precisely analogous to the farm-manager bug where a farm's `start_epoch` could be set to a past epoch because the validator never checked `start_epoch > current_epoch`.

### Impact Explanation
This is a minority-triggerable divergence in signer-set-consensus state (not requiring a majority): a single signer with any nonzero weight who is present in a stale cycle's `cycle-signer-set` can inject a late/backdated vote for that cycle's aggregate key. Because the DKG aggregate key is used by signer nodes to validate Nakamoto block signatures for a cycle, a late-set aggregate key for a cycle whose block-signing window nodes assumed was closed (`is-none (map-get? aggregate-public-keys reward-cycle)` was true when they last checked) can cause nodes/signers that already treated the cycle's aggregate key as unresolved to disagree with nodes that see the newly-inserted key — a High-severity signer/DKG-state divergence bounded to the DKG bookkeeping for that cycle (comparable to "signer weight below threshold or from the wrong set" / "a validation verdict two nodes disagree on" in the accepted taxonomy).

### Likelihood Explanation
Likelihood is moderate: it requires a signer that was part of a `cycle-signer-set` for a cycle whose aggregate key was never successfully finalized (e.g., a cycle where consensus was never reached, or where the vote simply never reached threshold before the reward cycle rolled over) to later submit a vote tagged with that old `reward-cycle`. No special privilege beyond being a previously-registered signer is required, and no majority coordination is needed — a single signer can trigger the divergence.

### Recommendation
Enforce the intended (already-written) window check at the top of `vote-for-aggregate-public-key`:
```clarity
(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))
```
This restores the documented invariant that a vote's `reward-cycle` must equal `.signers get-last-set-cycle` and must be submitted during that cycle's prepare phase, mirroring the recommended fix in the analog report (explicitly asserting the value is bounded to the current valid window rather than trusting caller input).

### Proof of Concept
1. Node computes the signer set for reward cycle `N` at the start of `N`'s prepare phase; suppose the DKG vote never reaches `threshold-consensus` before cycle `N` ends (`aggregate-public-keys` has no entry for `N`).
2. Time advances several cycles; `last-set-cycle` in `.signers` now points to cycle `N+5`.
3. A signer `S` who was part of `cycle-signer-set` for cycle `N` (still stored, since `.signers` never prunes old cycles — [3](#0-2) ) calls:
```clarity
(contract-call? .signers-voting vote-for-aggregate-public-key signer-index key round N)
```
4. `get-signer-weight` succeeds because `get-signer-by-index N signer-index` still resolves to `S`. `is-none (map-get? aggregate-public-keys N)` is still true. No check exists to reject `reward-cycle = N` as stale, so the vote is recorded and, if it reaches `threshold-weight` (which was cached from cycle `N`'s smaller/stale signer set), `aggregate-public-keys` gets a late entry for cycle `N` — set out-of-band from what other nodes/signers assumed for that closed cycle.

                   (set-at-height uint))
	(let ((cycle-mod (mod reward-cycle u2)))
        (map-set cycle-set-height reward-cycle set-at-height)
        (var-set last-set-cycle reward-cycle)
        (if (is-eq cycle-mod u0)
            (ok (var-set stackerdb-signer-slots-0 signer-slots))
