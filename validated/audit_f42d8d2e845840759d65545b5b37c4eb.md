### Title
`ensure_match_transaction_info` skips validation of `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, allowing a divergent authenticated state/position root to pass replay/output-verification - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk executor replay, `db-tool replay-on-archive`, and the debugger to verify that a locally re-executed `TransactionOutput` matches an authenticated, already-committed `TransactionInfo` (proof-bearing, signed by validators). It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, per the comment directly in the code.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  verifies four fields (status, gas, write-set hash, event root hash) between the locally computed `TransactionOutput` and the on-chain, signature-verified `TransactionInfo`. The trailing comment is explicit about the gap: [2](#0-1) 

This means the state checkpoint root (Sparse Merkle Tree root of world state), and, when `compute_trading_native_state_roots` is on, the hot-state and "trading-native position" checkpoint roots embedded in `TransactionInfoV1`, are never independently confirmed to match local execution in this comparator. This function is called from `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`.

The `compute_trading_native_state_roots` on-chain flag exists and is gated behind `transaction_info_v1` and `hotness_in_epilogue` at [3](#0-2) , meaning this is a real, wired feature path, not dead code — it is only currently disabled by default (`compute_trading_native_state_roots: false` in constructors), so it is not yet exploitable on current mainnet configuration, but the code path is live infrastructure intended for future activation.

### Impact Explanation
If/when `compute_trading_native_state_roots` (or the plain `state_checkpoint_hash`) is relied upon without this comparator being extended, tooling built on `ensure_match_transaction_info` (replay-verify, chunk executor sync validation, debugger checks) could report a **successful replay/verification even though the locally computed state checkpoint root, hot-state root, or position-state root diverges from the authenticated value in the committed `TransactionInfo`**. This is a proof-integrity gap: an authenticated, signed field (`state_checkpoint_hash` et al.) is present in the ledger but silently unchecked by the one function whose explicit job is to assert equivalence between local execution and the authenticated commitment. This matches the required "Wrong ... state proof accepted as valid" and "Authenticated API or state-view output bound to the wrong version, object, or proof context" impact classes — a divergence would not be caught by state-sync/replay verification.

### Likelihood Explanation
Currently low/no direct exploitability: the `compute_trading_native_state_roots` flag defaults to `false` everywhere it is constructed [4](#0-3) , so on present-day mainnet the described roots are not being computed/relied upon by this code, and this is exactly the caveat the authors themselves flagged with a `TODO(trading-native)` comment — it is a known, self-documented gap in unreleased functionality rather than a silently-introduced bug. I could not verify from the indexed code whether `state_checkpoint_hash` (the pre-existing, always-available field, independent of the trading-native flag) is validated by any *other* path during normal chunk-executor commit (e.g., via the state Merkle tree fed by `do_state_checkpoint.rs`), which would materially affect real-world severity; this needs further tracing in `execution/executor/src/workflow/do_state_checkpoint.rs` and the chunk executor's commit path that I did not have iterations left to inspect.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality of `state_checkpoint_hash`, and — when `compute_trading_native_state_roots`/`hot_state_root_in_txn_info` are enabled — `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against the locally-computed equivalents, exactly as the code comment already recommends, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production.

### Proof of Concept
Not independently reproducible as a live exploit today because `compute_trading_native_state_roots` is disabled by default in all `BlockExecutorConfigFromOnchain` constructors [5](#0-4) . The "proof" here is the self-documented invariant gap directly in the source: [1](#0-0)  checks only 4 of the 7 authenticated fields on `TransactionInfo`/`TransactionInfoV1`, leaving `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` unverified against locally recomputed values in every caller (`chunk_executor/mod.rs`, `replay_on_archive.rs`, `aptos_debugger.rs`, `cli/src/commands.rs`).

Given the low current likelihood (feature disabled by default) and that this is a self-acknowledged, not-yet-enabled gap rather than a proven live divergence, I flag this with reduced confidence — a Devin session with broader exploration of `do_state_checkpoint.rs` and the chunk-executor commit path would be needed to confirm whether `state_checkpoint_hash` divergence is independently caught elsewhere, which would downgrade or confirm this finding.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
