### Title
Default 1000 QPS rate limiter is insufficient to prevent CPU-exhaustion DoS on `GetPaginatedAssetIssueListServlet` - ([File: framework/src/main/java/org/tron/core/services/http/GetPaginatedAssetIssueListServlet.java])

### Finding Description
`GetPaginatedAssetIssueListServlet` has no matching entry in the `rate.limiter.http` list, which is empty by default in `common/src/main/resources/reference.conf` (lines 466-483, all entries commented out). At servlet start-up, `RateLimiterServlet.addRateContainer()` looks up the servlet's simple name in `Args.getInstance().getRateLimiterInitialization().getHttpMap()`; when no entry exists it falls back to `DEFAULT_ADAPTER_NAME` (`DefaultBaseQqsAdapter`) and `QpsStrategy.DEFAULT_QPS_PARAM`: [1](#0-0) 

`QpsStrategy.DEFAULT_QPS_PARAM` is computed as `"qps=" + Args.getInstance().getRateLimiterGlobalApiQps()`: [2](#0-1) 

and `global.api.qps` is defaulted to `1000` in `reference.conf`: [3](#0-2) 

The servlet itself performs no bound checking on the `offset`/`limit` request parameters before delegating to `wallet.getAssetIssueList(offset, limit)`: [4](#0-3) 

If (per the prior "question 1" analysis referenced in this prompt) `Wallet.getAssetIssueList` performs a full-store fetch-and-sort of all TRC10 assets on every call regardless of pagination parameters, then a per-endpoint ceiling of 1000 requests/second is not a meaningful mitigation: 1000 concurrent/sequential invocations per second of an O(n log n) sort over the entire asset-issue store will saturate available CPU well before the rate limiter's `RateLimiter.tryAcquire()`/`acquire()` (backed by Guava `RateLimiter`) begins rejecting/queuing traffic. Because `DefaultBaseQqsAdapter`'s 1000 qps applies per-servlet (not globally shared and not tied to computed cost), the limiter caps request *count*, not CPU *cost*, so it provides no effective protection against this specific expensive query path.

### Impact Explanation
This maps to the "DoS via RPC-API" bounty impact class: an unprivileged, unauthenticated HTTP client can drive sustained CPU load on a FullNode by repeatedly calling `/wallet/getpaginatedassetissuelist` (or the Solidity/PBFT equivalents which share the same default-fallback logic), degrading or stalling node responsiveness for legitimate API/RPC clients. This does not corrupt on-chain state, steal funds, or affect consensus — it is limited to node/API-layer availability degradation.

### Likelihood Explanation
- No authentication, signed transaction, or fee is required — the endpoint is public GET/POST HTTP API. 
- The attacker only needs a single unprivileged host capable of issuing up to ~1000 req/s (achievable with trivial concurrency from one or a few machines, no need to exceed the limiter to cause damage since even far below 1000 req/s of a full-table-sort operation can be CPU-heavy).
- Cost to the attacker is $0 (no on-chain transaction, no TRX/energy/bandwidth spent) since this is a read-only HTTP query path, not an actuator or transaction.
- Fully repeatable and does not require any non-default node configuration — the empty `rate.limiter.http` list and `global.api.qps = 1000` are the shipped defaults in `reference.conf`.
- This finding's severity is entirely contingent on the actual cost of `Wallet.getAssetIssueList`, which was established as an expensive full-store sort in the referenced "question 1" analysis; I was not able to re-verify the body of `Wallet.getAssetIssueList` within this session due to tool-call exhaustion, so this should be read as building on that prior finding rather than independently re-confirming the sort cost.

### Recommendation
- Add an explicit, low-QPS `rate.limiter.http` entry (or a `GlobalPreemptibleAdapter` concurrency cap) for `GetPaginatedAssetIssueListServlet` (and its Solidity/PBFT counterparts) reflecting its real per-call cost rather than relying on the generic 1000 qps default.
- Alternatively/additionally, fix the underlying cost issue (cache the sorted list, or avoid re-sorting/re-scanning the whole store per request) so that the per-request cost is bounded regardless of rate-limiter configuration.
- Consider making the default QPS adaptive/cost-aware instead of a flat count-based ceiling for endpoints known to scale with store size.

  private void addRateContainer() {
    final String name = getClass().getSimpleName();
    RateLimiterInitialization.HttpRateLimiterItem item = Args.getInstance()
        .getRateLimiterInitialization().getHttpMap().get(name);

    String cName;
    String params;
    if (item == null) {
      cName = DEFAULT_ADAPTER_NAME;
      params = QpsStrategy.DEFAULT_QPS_PARAM;
    } else {
      cName = item.getStrategy();
      params = item.getParams();
    }

    try {
      container.add(KEY_PREFIX_HTTP, name, buildAdapter(cName, params, name));
    } catch (Exception e) {
      throw rateLimiterInitError(cName, params, name, e);
    }
  }
