### Title
Attacker can DOS the TRC10 order-book market at negligible cost by spamming dust orders that saturate MAX_MATCH_NUM - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator` implements TRON's on-chain order-book market (`MarketSellAssetContract`). Order creation only validates that `sellTokenQuantity`/`buyTokenQuantity` are positive and below `MarketQuantityLimit` — it never enforces any *minimum* notional/quantity, nor any minimum relationship to the existing best price beyond needing to be "better" for it to be matched first. This mirrors the Tessera `OptimisticListing` DOS: an attacker can post a very large number of dust-sized orders at negligibly better prices for almost no cost, forcing any legitimate taker who tries to match a normal-sized order to blow through the fixed `MAX_MATCH_NUM` limit and have the whole transaction (and its fee) fail, effectively DOSing that trading pair.

### Finding Description
In `validate()` the only quantity checks are: [1](#0-0) 
`sellTokenQuantity <= 0 || buyTokenQuantity <= 0` is rejected, and quantities above `dynamicStore.getMarketQuantityLimit()` are rejected, but there is **no minimum order size** requirement (e.g., no lower bound on `sellTokenQuantity` such as 1). The only other guard is a per-account cap on open orders: [2](#0-1) 
which is a per-address limit (`MAX_ACTIVE_ORDER_NUM = 100`), trivially bypassed by using many different accounts.

When a taker order is submitted, `matchOrder` walks the maker order book from the best price and matches up to `MAX_MATCH_NUM` (20) maker orders before throwing: [3](#0-2) 
```
matchOrderCount++;
if (matchOrderCount > MAX_MATCH_NUM) {
  throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
}
```
This exception propagates out of `execute()`: [4](#0-3) 
causing the whole taker transaction to fail with `ContractExeException`.

Because there is no minimum order size, an attacker can create dozens of dust orders (e.g., `sellTokenQuantity = 1`) at prices marginally better than the prevailing best price for a token pair, at the cost of only the per-order market fee (`calcFee()` → `dynamicStore.getMarketSellFee()`) and 1 unit of the sold asset each. Any legitimate user attempting to sell/buy a normal quantity on that pair will have their taker order walk through these dust maker orders first (since they are matched best-price-first via `hasMatch`/`MarketUtils.priceMatch`), and once more than `MAX_MATCH_NUM` (20) of them are consumed, the transaction reverts with "Too many matches", exactly like the Tessera bug where a cheap, adversarial low-value entry (`_collateral = 1`) blocks the legitimate flow (`propose`/here, `sell`) for everyone else. This is directly analogous to the reported root cause: **no lower bound is enforced on the "collateral"/order size relative to cost**, enabling near-zero-cost griefing of the matching mechanism that other users depend on.

### Impact Explanation
This is a protocol-level Denial-of-Service against the java-tron TRC10 exchange/market feature reachable by any account that can broadcast a `MarketSellAssetContract` transaction (no privileged role required). A single attacker (or a small number of colluding/sybil accounts, since the 100-order cap is per-account) can render a specific token pair effectively untradeable for legitimate users: every taker transaction attempting to consume the top of the order book fails with `ContractExeException`, wasting the taker's fee and TRX/asset transfer attempt, and repeatedly forces users to work around the dust wall. Because dust orders cost only the market fee plus 1 unit of the asset, the attack is asymmetric — cheap to sustain, costly for victims (failed transactions, wasted fees/energy, inability to trade).

### Likelihood Explanation
High. `MarketSellAssetContract` is a standard, unprivileged, broadcastable transaction type; the validation path shown above is the only gate and does not require any minimum quantity or minimum total value. The `MAX_MATCH_NUM` constant is small (20), making the number of dust orders required to trigger the revert trivially achievable, and the per-account limit (`MAX_ACTIVE_ORDER_NUM = 100`) does not prevent multi-account sybil order placement.

### Recommendation
Introduce a minimum notional/quantity threshold for orders (e.g., a `MarketOrderMinQuantity`/minimum-value dynamic parameter analogous to `MarketQuantityLimit`, enforced symmetrically as a floor, not just a ceiling), so dust orders cannot be cheaply created purely to occupy the front of the order book. Additionally, consider making the `MAX_MATCH_NUM` overflow behavior non-reverting for the whole transaction (e.g., partially match up to the limit and leave the remainder unmatched/queued) instead of throwing `ContractValidateException` that aborts the entire taker transaction, so dust walls cannot cause outright transaction failure for legitimate takers.

### Proof of Concept
Conceptual PoC (mirrors the Tessera Foundry PoC pattern):
1. Attacker broadcasts `MAX_MATCH_NUM + 1` (21) separate `MarketSellAssetContract` transactions (optionally from different accounts to avoid the 100-order-per-account cap), each with `sellTokenQuantity = 1` and a `buyTokenQuantity` chosen so the resulting price is marginally better than the current best price for a chosen `(sellTokenID, buyTokenID)` pair — cost per order is just `dynamicStore.getMarketSellFee()` plus 1 unit of the sold token, both negligible.
2. A legitimate user submits a normal-sized `MarketSellAssetContract` order on the opposite side of the same pair.
3. `matchOrder`/`matchSingleOrder` walk the order book best-price-first, consuming the 21 dust orders; once `matchOrderCount > MAX_MATCH_NUM`, `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")` is thrown, per [5](#0-4) , causing the legitimate transaction to fail (`ContractExeException`) at [4](#0-3) .
4. The pair remains unusable for normal-sized takers until the dust orders are manually cleared (each requiring a separate cancel transaction), which the attacker fully controls, exactly analogous to the Tessera scenario where the attacker "rejects the proposal himself, resetting the contract state" to repeat the block indefinitely.

Note: I was unable to retrieve the exact default numeric values of `MarketSellFee`/`MarketQuantityLimit` from `DynamicPropertiesStore` within the available context (only match counts were confirmed), so exact cost-per-attack figures are not quantified here; a Devin session with full file access would be needed to pull those defaults for a fully numeric PoC.
