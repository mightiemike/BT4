### Title
Unbounded request-body buffering before required-header check in `authenticate` allows memory-exhaustion DoS - (File: `packages/apps/shopify-app-remix/src/server/authenticate/flow/authenticate.ts`)

### Summary
`authenticateFlowFactory`'s `authenticate` function unconditionally calls `await request.text()` to fully buffer the entire request body into memory before any HMAC/header validation is performed. Because the HMAC header check occurs only after the body is completely read, an attacker can send an arbitrarily large POST body — with or without the required `X-Shopify-Hmac-Sha256` header — and force the server to buffer the full payload in memory before it is ever rejected.

### Finding Description
In `authenticate` (`packages/apps/shopify-app-remix/src/server/authenticate/flow/authenticate.ts`), the code flow is: [1](#0-0) 

`request.text()` reads and buffers the entire request body before `api.flow.validate` is even invoked. Inside `validateHmacFromRequestFactory` (used by `flow.validate`), the checks performed are: reject if `rawBody` is empty, then look up the HMAC header from `request.headers`, and only then compute/compare the HMAC: [2](#0-1) 

Critically, the HMAC header (`ShopifyHeader.Hmac` / `X-Shopify-Hmac-Sha256`) is available directly from `request.headers` without needing to read the body at all — headers are present on the `Request` object before the body stream is consumed. Despite this, `authenticate` reads the full body via `request.text()` unconditionally, *before* checking whether the required HMAC header is even present. This means a request that is missing the required header (or has any header) still causes full-body buffering.

There is no `Content-Length` cap, streaming size limit, or early-header short-circuit anywhere in this library layer (`shopify-app-remix`, `shopify-app-react-router`, or `shopify-api`'s `hmac-validator.ts`/`flow/validate.ts`) — confirmed by the absence of any `maxBodySize`/`bodyLimit`/`content-length` checks in the codebase. The identical pattern (`request.text()` before header/HMAC check) also exists in the sibling `webhooks/authenticate.ts` and `fulfillment-service/authenticate.ts` files, and in the `shopify-app-react-router` port.

### Impact Explanation
An unauthenticated attacker can POST a very large body (limited only by the underlying HTTP server/runtime's own default limits, which this library does not itself enforce or rely on for protection) to the app's `/flow` (or webhook/fulfillment-service) endpoint. Each such request forces the process to allocate memory proportional to the entire body before any authentication check that could short-circuit on the missing header is applied. Repeated concurrent requests of this kind can exhaust server memory or CPU (string decoding/allocation), degrading or crashing the webhook endpoint — a DoS of the authentication handler, matching the "DoS in an authentication handler" impact class named in the rules.

### Likelihood Explanation
This requires no credentials, no valid HMAC, no app-developer role, and no non-default configuration — a single anonymous POST with a large body and a missing/garbage HMAC header is sufficient, and it is trivially repeatable and scriptable (e.g., with concurrent large-body requests). The only mitigating factor is that many deployment platforms (e.g., Node HTTP server, reverse proxies, or hosting providers like Vercel/Fly/Heroku) impose their own default body-size limits — but those are host/environment properties, not protections built into this library, so the library itself provides no bound on work done before authentication.

### Recommendation
Check for the presence of the required HMAC header (and reject early with 400) using `request.headers` *before* calling `request.text()`/consuming the body stream. Additionally, consider enforcing an explicit maximum body size (checking `Content-Length` and/or streaming with a byte cap) in `validateHmacFromRequestFactory`/`authenticate` before buffering, independent of host-platform defaults, for `flow`, `webhooks`, and `fulfillment-service` authenticate handlers.

### Proof of Concept
```ts
// packages/apps/shopify-app-remix/src/server/authenticate/flow/__tests__/authenticate.dos.test.ts
import {shopifyApp} from '../../..';
import {getThrownResponse, testConfig} from '../../../__test-helpers';

const FLOW_URL = 'https://example.myapp.io/authenticate/flow';

it('buffers an arbitrarily large body before rejecting missing HMAC header', async () => {
  const shopify = shopifyApp(testConfig());

  // 200MB body, NO HMAC header present at all
  const hugeBody = 'a'.repeat(200 * 1024 * 1024);

  const start = process.memoryUsage().heapUsed;
  const response = await getThrownResponse(
    shopify.authenticate.flow,
    new Request(FLOW_URL, {
      method: 'POST',
      body: hugeBody, // no 'X-Shopify-Hmac-Sha256' header
    }),
  );
  const end = process.memoryUsage().heapUsed;

  // Request is eventually rejected (400), but only AFTER the full 200MB
  // body was read into memory via request.text() in authenticate.ts,
  // even though the missing-header check needed no body at all.
  expect(response.status).toBe(400);
  expect(end - start).toBeGreaterThan(150 * 1024 * 1024); // large allocation occurred pre-auth-check
});
```
This demonstrates that `authenticate` in `flow/authenticate.ts` performs unbounded, memory-proportional work (`request.text()`) on every POST regardless of whether the cheap, header-only precondition (`X-Shopify-Hmac-Sha256` present) is satisfied, violating the "bounded work before authentication" invariant.
