### Title
DeleteAccount beneficiary refund permanently burns funds when `beneficiary_id` is mistyped or otherwise invalid - ([File: runtime/runtime/src/actions.rs])

### Summary
`DeleteAccountAction` lets the account owner (or a promise the owner authorized) specify an arbitrary `beneficiary_id` to receive the deleted account's remaining balance [1](#0-0) . The only validation performed on this field is that it is a syntactically valid `AccountId` [2](#0-1)  — there is no check that the account actually exists. If the user submits a `DeleteAccount` action with a beneficiary that does not exist (a typo, a never-created sub-account, etc.), the resulting refund receipt executes as a system-refund `Transfer` to that address, and NEAR's refund semantics dictate that a failed refund transfer irrecoverably burns the tokens instead of returning them or creating the account.

### Finding Description
`action_delete_account` computes the account's remaining balance and, instead of transferring it synchronously, always emits a refund receipt targeting `beneficiary_id` via `Receipt::new_balance_refund`: [3](#0-2) 

This receipt is a system-refund receipt (`predecessor_id == "system"`) carrying a single `Transfer` action [4](#0-3) .

When this refund receipt is later applied, `check_account_existence` for the `Transfer` action calls `implicit_creation_allowed`, which explicitly forbids account creation for refund receipts: [5](#0-4) 

So if `beneficiary_id` does not correspond to an existing account (and is not eligible for implicit creation, e.g. it's a named account or a refund at all), the `Transfer` action fails with `AccountDoesNotExist`: [6](#0-5) 

This exact scenario is covered by an existing unit test that confirms a refund to a missing account fails with `AccountDoesNotExist` and does **not** create the account: [7](#0-6) 

Per the documented refund semantics, when a system-refund receipt's execution fails, the runtime does not retry, return the funds to the original owner, or leave them in limbo — it burns them outright: [8](#0-7) 

The apply-loop code that implements this burn-on-failure behavior for system-predecessor receipts is: [9](#0-8) 

Putting this together: an unprivileged account owner signs a single `DeleteAccount` transaction (or `promise_batch_action_delete_account` from a contract they control) with a `beneficiary_id` that is well-formed but does not exist as an account — e.g., a typo of their intended receiver, or an account they have not yet created. There is no reversal mechanism, no second step to correct the address, and the delete itself is irreversible (the source account is already removed by the time the beneficiary refund receipt executes) [10](#0-9) . The entire deleted account's balance is then permanently destroyed via `other_burnt_amount` rather than being deliverable to anyone.

This directly mirrors the report's bug class: a user-supplied receiver/destination address is accepted without existence validation, is fixed at submission time with no way to amend it, and a wrong value results in permanent, unrecoverable loss of funds.

### Impact Explanation
This causes concrete, permanent loss of user funds: the entire remaining balance of a deleted account is burned (removed from circulation) if the `beneficiary_id` account does not exist, with no path to appeal or reroute the funds. This is a "permanently frozen/destroyed funds" impact, one of the accepted impact categories, and is triggerable by a single unprivileged transaction signer or a contract-authorized promise batch action on their own account.

### Likelihood Explanation
Likelihood is realistic given ordinary user error: `beneficiary_id` is free-form text supplied by the caller at the moment of deletion, with only syntactic validation (`validate_action_account_id`) [2](#0-1) , not an existence check. A typo, an account not yet created, or a stale/renamed sub-account name are all plausible real-world mistakes, and because `DeleteAccount` must be the final and only irreversible action in the receipt, there's no opportunity to detect or correct the mistake before the account and its balance are gone.

### Recommendation
Before deleting the account and emitting the balance-refund receipt, validate that `beneficiary_id` refers to an existing (and initialized) account, similar to the `check_account_existence` checks already applied to other actions in `runtime/runtime/src/actions.rs`. If the beneficiary does not exist, fail the `DeleteAccount` action itself (returning something like `AccountDoesNotExist` for the beneficiary) rather than allowing the delete to proceed and then silently burning the refund on a doomed downstream receipt. Alternatively, allow implicit creation of the beneficiary account when it is a valid near-implicit/eth-implicit id, consistent with how ordinary (non-refund) transfers are permitted to create implicit accounts.

### Proof of Concept
1. Account `alice.near` owns balance `B` and no contract restricts deletion (not staking, storage usage under `MAX_ACCOUNT_DELETION_STORAGE_USAGE`).
2. `alice.near` submits a `DeleteAccount { beneficiary_id: "bobb.near" }` transaction where `bobb.near` (a typo of an intended existing account, or simply never created) does not exist as an account.
3. `action_delete_account` removes `alice.near` from state and pushes `Receipt::new_balance_refund("bobb.near", B)` [3](#0-2) .
4. When the refund receipt is applied, `check_account_existence` rejects the `Transfer` action against the non-existent, non-implicit-creatable `bobb.near` with `AccountDoesNotExist` [6](#0-5) , matching the existing test for this exact code path [7](#0-6) .
5. Because the receipt's predecessor is `system`, the failed refund's deposit `B` is added to `other_burnt_amount` instead of being returned anywhere [9](#0-8) , and per the refund documentation this loss is final [8](#0-7) .
6. Result: `B` NEAR tokens permanently destroyed, unrecoverable by `alice.near` or anyone else.

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
