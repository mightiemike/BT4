## Title
Vault `accrue` pause silently returns stale interest indexes instead of reverting, letting `borrow`/`liquidate`/`collateral-add` in `market.clar` compute health using outdated debt/collateral values — ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every vault's `accrue` function (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) is designed so that when the `accrue` pause flag is set, the function does **not** revert — it silently returns the last-known `index`/`lindex` as `(ok ...)`: [1](#0-0) 

This is a pause-that-passes-through-instead-of-reverting analog. `market.clar`'s `accrue-and-cache` treats whatever the vault returns as authoritative and caches it per-block: [2](#0-1) 

`borrow`, `liquidate`, and `collateral-add` all call `accrue-user-debts`/`accrue-user-collateral`/`accrue-and-cache` to populate this cache *before* computing collateral/debt USD values and evaluating health (`is-healthy`, capacity checks, liquidation LTV): [3](#0-2) [4](#0-3) 

### Finding Description
Each vault's `system-borrow`, `system-repay`, `deposit`, and `redeem` all begin with `(u (try! (accrue)))`, expecting a real interest-index refresh. But `accrue` is written to swallow the pause condition rather than failing:

```
(if (get accrue states)
    ;; PAUSED: Pass-through without reverting
    (ok { index: idx, lindex: lidx })
    ...)
```

Because it returns `ok` with the **unchanged, stale** `idx`/`lindex`, and `market.clar`'s `accrue-and-cache` has no way to distinguish "fresh accrual happened" from "accrual was skipped due to pause," market treats the stale numbers as the current, correct scaled-debt/liquidity index for that vault for the rest of the transaction (and for the whole block, due to the timestamp-keyed cache). Every downstream health computation that depends on `get-cached-indexes`/`convert-to-scaled-debt` — `borrow`'s pre/post-health checks, `liquidate`'s LTV and liquidation-parameter math, and `collateral-add`'s future-capacity check — is silently computed against out-of-date debt/liquidity values instead of aborting the operation as an unhealthy/unavailable state.

### Impact Explanation
If a vault's `accrue` pause is active while real interest has accrued (e.g., between the last real accrual and the pause activation, and for however long the pause remains on), any borrower's true debt is understated in every market-side health check that consumes that vault's index. A borrower can be permitted to `borrow` more than their real (unpaused) debt would allow, or a position that should be liquidatable under the true (accrued) debt figure can be evaluated as healthy and evade liquidation — this is a form of protocol insolvency risk / stranded bad debt because the discrepancy is silently absorbed rather than causing the call to fail-safe. This lands in the Critical impact category (protocol insolvency / permanent freezing risk from bad debt that cannot be liquidated at its true value) since the health-check pipeline that gates borrowing and liquidation is fed intentionally-stale state without any signal to callers.

### Likelihood Explanation
This requires only a single admin action (pausing `accrue` on a vault) followed by ordinary user transactions (`borrow`, `liquidate`, `collateral-add`) within the same or later blocks while the pause remains active — no cross-user race or governance compromise is needed beyond the documented pause toggle itself, which is a normal operational lever (not a DAO-registry misconfiguration). Given `accrue` pauses are expected to be used operationally (e.g., during incident response), the window in which stale indexes are consumed by health checks is realistic and not a contrived edge case.

### Recommendation
Do not let `accrue` return `(ok ...)` when paused. Either:
1. Return an explicit error (e.g., `ERR-ACCRUAL-PAUSED`) so all dependent callers (`system-borrow`, `system-repay`, `deposit`, `redeem`, and market's `accrue-and-cache`) fail closed instead of silently continuing with stale indexes; or
2. If pass-through is intentionally required for user withdrawal/repay availability, have `accrue-and-cache` and all market-side health/liquidation logic explicitly check a "vault accrual paused" flag and refuse to execute borrow/liquidate/capacity-increasing operations for assets tied to a paused vault, while still allowing repay/redeem.

### Proof of Concept
1. DAO/admin sets `pause-states.accrue = true` on `v0-vault-stx` (a normal, non-privileged-key pause toggle already exposed by the contract).
2. Time passes such that real interest would have accrued (`next-index` would differ from `idx`), but `accrue` keeps returning the old `idx`/`lindex` every call.
3. A borrower with existing STX debt calls `market.clar`'s `borrow` for a different asset. `accrue-user-debts` → `accrue-and-cache STX` returns the stale `idx`, understating `debt-value` in the health computation at `v0-4-market.clar:1272` and `:1287`.
4. The post-borrow health check `is-healthy-with-mask` passes using understated debt, allowing the user to borrow more than their true (accrued) debt would permit.
5. Alternatively, a liquidator calling `liquidate` on this borrower computes `current-ltv` from the same stale, understated debt figure at `v0-4-market.clar:1424-1435`, so `health-check` (`ERR-HEALTHY`) incorrectly blocks a liquidation that would succeed under the true, accrued debt — stranding bad debt in the protocol until the pause is lifted and accrual catches up (potentially after further price/interest drift worsens the shortfall). (define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
