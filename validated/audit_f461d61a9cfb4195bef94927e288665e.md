## Title
No slippage control in `ExchangeInjectContract` deposit path allows loss of funds from pool-ratio changes between tx submission and execution - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The AllBridge report describes `PortfolioToken.deposit()` minting shares based on the pool's state *at execution time* rather than at the time the user decided to deposit, with no way for the caller to bound the outcome — causing loss of funds when the pool state shifts before the transaction lands. java-tron's Bancor-style `Exchange` (TRC10 token-pair AMM) has the same bug class in `ExchangeInjectContract`/`ExchangeInjectActuator`, which computes the paired ("another") token amount from the pool's live ratio with no user-supplied bound, unlike its sibling `ExchangeTransactionContract` which has an explicit `expected` slippage parameter.

### Finding Description
`ExchangeInjectActuator.execute()` takes a caller-chosen `tokenQuant` of one side of the pair and derives the required amount of the other token proportionally from the *current* pool balances: [1](#0-0) 

This is exactly the mechanism the AllBridge report criticizes: the amount actually charged/received depends on the pool's reserves at the moment the transaction executes, not at the moment the user constructed and signed it. Any other pool-affecting transaction (an `ExchangeTransactionContract` swap, or another `Inject`/`Withdraw`) that lands first will shift `firstTokenBalance`/`secondTokenBalance`, changing `anotherTokenQuant` for the pending inject transaction.

Crucially, `ExchangeInjectContract` has no analog of the `expected` field that `ExchangeTransactionContract` uses to bound slippage on swaps: [2](#0-1) 

The validator for inject checks only that the exchange exists, that the caller is the exchange creator, and coarse amount/precision constraints — it never lets the caller specify a maximum acceptable `anotherTokenQuant` or a minimum ratio, so the deduction is executed unconditionally once accepted: [3](#0-2) 

Compare this with the withdraw path, which at least re-derives and validates the ratio at execution but still has no user-supplied bound, and with the swap path, which does have `expected`: [4](#0-3) 

### Impact Explanation
An exchange creator injecting liquidity commits to sending `tokenQuant` of one token, but the amount of the other token that will actually be deducted from their account (`anotherTokenQuant`) is only fixed at block-execution time based on the live pool ratio. A swap that lands just before the inject transaction (whether organic or deliberately placed by another party observing the pending inject) can shift the ratio so the injector pays substantially more of the second token than they intended when they signed the transaction — a direct, unbounded loss of funds, matching the accounting-impact class in the AllBridge finding.

### Likelihood Explanation
Likelihood is moderate: it requires the injector's transaction to be pending while another swap/inject/withdraw against the same exchange pair is included first (e.g., during high trading activity, MEV-style front-running, or simply due to normal network propagation/mining delay). Since anyone can create an exchange and become its "creator" (the only prerequisite to call Inject), this is reachable by ordinary, unprivileged users and does not require any special/trusted role.

### Recommendation
Add a slippage-bound field to `ExchangeInjectContract` (and enforce it in `ExchangeInjectActuator`/`doValidate`), analogous to the `expected` field already used in `ExchangeTransactionContract`, e.g., a caller-supplied maximum acceptable `anotherTokenQuant` (or minimum/maximum ratio), and fail the transaction if the value computed from the live pool state exceeds that bound.

### Proof of Concept
1. Exchange creator builds an `ExchangeInjectContract` with `tokenQuant = X` of `firstTokenID`, expecting `anotherTokenQuant ≈ secondTokenBalance*X/firstTokenBalance` based on the pool ratio observed when constructing the tx.
2. Before this transaction is included, another account submits an `ExchangeTransactionContract` swap against the same `exchange_id`, shifting `firstTokenBalance`/`secondTokenBalance`.
3. The pending inject transaction executes against the new ratio in `ExchangeInjectActuator.execute()` (lines 71-83), deducting a different, larger `anotherTokenQuant` from the creator's account than they anticipated, with no mechanism in `doValidate()` to reject the trade for exceeding a caller-specified bound.
