### Title
ValidateMultiSign precompile double-counts a single signer's weight via ECDSA signature malleability - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Finding Description
`ValidateMultiSign.execute(byte[])` iterates over the caller-supplied `signatures` array, computes `mergedHash = Sha256Hash.hash(isECKeyCryptoEngine, combine)` and recovers a signer address via `recoverAddrBySign` for each 65-byte chunk, accumulating `totalWeight` from the `Key` in the target account's `Permission` whose address matches the recovered address. The de-duplication mechanism to prevent counting the same signer twice (`executedSignList`) compares the *raw signature bytes* of each chunk (add-if-not-contains), not the *recovered address*.

ECDSA signatures are malleable: for a valid `(r, s, v)` signature, the pair `(r, n-s, v')` (with the recovery id flipped accordingly) is also a valid signature that recovers to the *same* public key/address, yet has different raw bytes. Because `recoverAddrBySign` tries recovery ids to find the matching address (as is standard for Ethereum/Tron-style recoverable signatures) and the dedup set only rejects byte-identical entries, an attacker who possesses one valid signature from a legitimate co-signer can derive this malleable variant *without the private key* and submit `[sig, sig_variant]` to `validatemultisign`. Both entries pass the raw-byte dedup check (they differ), both recover to the same address, and the signer's `Key.weight` is added twice—inflating `totalWeight` beyond what the number of *distinct* keys that actually authorized the operation would justify.

This breaks the intended multisig invariant that `totalWeight` should reflect distinct authorizing keys, letting a permission requiring N signers/weight be satisfied by fewer than N distinct approvals when at least one legitimate signature is available to the attacker (e.g., obtained from a prior, unrelated authorization by that co-signer, or a signature disclosed for a different purpose).

### Impact Explanation
Any TVM contract logic gated by `validatemultisign(address,permissionId,data,signatures[])`—commonly used to require multiple independent approvers before releasing funds or executing privileged contract actions—can be tricked into believing a lower number of distinct keys approved the operation than actually did. This is an "unauthorized account/contract operation via weight-check bypass," potentially enabling unauthorized withdrawal or execution of multisig-guarded contract logic.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid signature from a co-signer over the exact `(address, permissionId, data)` tuple (this is a precondition inherent to how multisig thresholds are meant to be reached—an attacker cannot forge a first signature without the key). Given one legitimate signature, deriving the malleable variant is a pure arithmetic operation on `s` (mod curve order) requiring no cryptographic secret, and is essentially free (no extra fee beyond normal TVM call cost). The dedup logic operating on raw bytes rather than recovered address is a straightforward implementation gap, not dependent on any privileged role, node configuration, or race condition—so it is reliably repeatable.

### Recommendation
Change the de-duplication key in `ValidateMultiSign.execute` from the raw signature bytes to the *recovered address* (or the `Key` object matched), e.g. maintain a `Set<byte[]>`/`Set<String>` of already-counted recovered addresses and skip adding weight if the address was already counted, regardless of whether the raw signature bytes differ.

### Proof of Concept
```java
// Conceptual JUnit-style PoC for PrecompiledContractsTest (ValidateMultiSign)
@Test
public void testMalleableSignatureDoubleCountsWeight() {
  ECKey signerKey = new ECKey(); // co-signer with weight 1, threshold requires e.g. weight 2
  byte[] hash = ...; // the mergedHash the precompile will compute for (ownerAddress, permissionId, data)
  ECKey.ECDSASignature sig = signerKey.sign(hash);

  // Derive malleable variant: s' = n - s, flip recovery id accordingly
  BigInteger sPrime = ECKey.CURVE.getN().subtract(sig.s);
  ECKey.ECDSASignature sigVariant = new ECKey.ECDSASignature(sig.r, sPrime);
  // recompute correct recId for sigVariant so it still recovers to signerKey.getAddress()

  byte[] signBytes = sig.toByteArray();          // original 65-byte sig
  byte[] variantBytes = sigVariant.toByteArray(); // different bytes, same recovered address

  byte[] data = encodeValidateMultiSignCall(ownerAddress, permissionId, rawData,
      new byte[][]{signBytes, variantBytes});

  Pair<Boolean, byte[]> result = new PrecompiledContracts.ValidateMultiSign().execute(data);

  // Expect: totalWeight computed inside should equal 1x signerKey.weight (one distinct key),
  // but bug causes it to equal 2x signerKey.weight, wrongly satisfying a threshold of 2.
  assertTrue(decodeWeight(result.getRight()) > signerKey.getWeight());
}
```
Expected (buggy) behavior: `totalWeight` reported by the precompile double-counts `signerKey`'s weight because `executedSignList` only rejects exact byte-duplicate signatures, allowing the malleable variant through and inflating the weight sum beyond the count of distinct recovered addresses.
