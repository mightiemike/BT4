### Title
Workflow/CRESettings job proposals from the Feeds Manager are auto-approved and executed with no operator review, bypassing the human trust-boundary control that exists for every other job type - ([File: core/services/feeds/service.go])

### Summary
The External Report describes MetaMask snaps that let a less-trusted party (the dapp) supply unsanitized "simulation" data that a human then uses to decide whether to approve a signing action — the dapp is on the wrong side of the trust boundary from the confirming user. The Chainlink analog is the Feeds Manager Service (FMS) job-proposal flow: for ordinary job types, a remote FMS proposes a job spec and a human node operator must explicitly review and approve it via `ApproveJobProposalSpec` before it is created (`core/web/resolver/mutation.go:782-820`). For `job.Workflow` and `job.CRESettings` types, however, `ProposeJob` skips that human trust boundary entirely and self-approves the spec.

### Finding Description
In `service.ProposeJob`, after the proposal is persisted, the job type is checked and if it is `job.Workflow` or `job.CRESettings` the service immediately calls `s.ApproveSpec(ctx, specID, true)` on the caller's behalf, with `force=true`: [1](#0-0) 

This bypasses the exact same review step that every other job type (`OffchainReporting`, `FluxMonitor`, `Bootstrap`, `CCIP`, `Gateway`, etc.) must go through via the GraphQL `ApproveJobProposalSpec` mutation, which requires an authenticated operator with edit permissions: [2](#0-1) 

`ApproveSpec` itself performs only structural/mechanical validation — it parses the spec, checks bridges exist, checks for an `ExternalJobID`, and then creates the job and reports approval back to the FMS: [3](#0-2) [4](#0-3) 

None of these checks validate the *content* or *intent* of the workflow — they do not require a human to look at what the workflow actually does before it starts executing on the node. This is analogous to the report's core complaint (a less-trusted remote party's data drives a privileged action without a faithful human review step), except here there is no review opportunity at all rather than merely an unsanitized one — a strictly stronger version of the same trust-boundary violation. The FMS/Job Distributor connection is a remote gRPC peer (`s.connMgr.GetClient`), and if that channel or its counterpart is compromised, misconfigured, or intentionally malicious/misbehaving, it can cause arbitrary workflow jobs to run on the node with zero operator confirmation, exactly the trust-boundary bypass the report class targets for job/workflow ingestion.

This behavior is also observed operationally in the test/dev tooling, which explicitly documents the assumption that workflow specs auto-approve: `system-tests/lib/cre/don/jobs/jobs.go:135-153` treats a "cannot approve an approved spec" error as success specifically because `type = "workflow"` specs are already auto-approved by the time an explicit approval call is attempted. [5](#0-4) 

### Impact Explanation
A workflow (or CRESettings) job spec pushed through a Feeds Manager connection is created and begins running immediately, with no human-in-the-loop confirmation, unlike every other job type. If the FMS/Job Distributor trust boundary is weaker than assumed (e.g. a compromised or misconfigured JD backend, or a JD operated by a less-trusted party than the node operator), this allows unauthorized privileged node action — arbitrary workflow logic execution — without ever surfacing to the node operator for review, let alone the diluted review the report criticizes (markdown/control-char-laden text). This is a direct node-compromise vector for workflow-capable nodes.

### Likelihood Explanation
Any environment that connects a node to a Feeds Manager/Job Distributor for workflow orchestration (which is the standard CRE/workflow node deployment pattern, as seen throughout `deployment/cre/jobs/` and `system-tests/lib/cre/`) is affected by construction — the auto-approval is unconditional for these job types, not a rare edge case. The likelihood of triggering it is high wherever the FMS channel is reachable and can supply a `job.Workflow`/`job.CRESettings` spec.

### Recommendation
Do not auto-approve `job.Workflow`/`job.CRESettings` specs solely because of their type. At minimum, gate auto-approval behind an explicit, node-operator-controlled configuration flag (opt-in), and/or require the same human confirmation path (`ApproveJobProposalSpec`) used for all other job types. If auto-approval must remain for automation reasons, add cryptographic/authorization checks on the workflow content (e.g., signer/owner allowlisting already present for `RegistryBasedLaunchAllowlist`-style controls) so the trust decision is anchored to a verifiable, node-operator-approved source rather than merely "this spec parses as type=workflow."

### Proof of Concept
1. Configure a node with a connected Feeds Manager (FMS/Job Distributor).
2. From the FMS side (or by compromising/spoofing that channel), call `ProposeJob` with a spec whose TOML sets `type = "workflow"` (or `cre_settings`) and a valid `externalJobID`.
3. Observe in `service.ProposeJob` (`core/services/feeds/service.go:847-863`) that `getJobType` classifies it as `job.Workflow`/`job.CRESettings`, and `s.ApproveSpec(ctx, specID, true)` is invoked automatically — no call to the `ApproveJobProposalSpec` GraphQL mutation, no operator interaction.
4. The job is created via `s.jobSpawner.CreateJob` and begins executing (`core/services/feeds/service.go:1108-1113`), and `ApprovedJob` is reported back to the FMS as if a human had approved it (`core/services/feeds/service.go:1122-1130`) — while for any other job type the same code path would instead require the operator to explicitly call `ApproveJobProposalSpec`.

func (s *service) ApproveSpec(ctx context.Context, id int64, force bool) error {
	spec, err := s.orm.GetSpec(ctx, id)
	if err != nil {
		return errors.Wrap(err, "orm: job proposal spec")
	}

	proposal, err := s.orm.GetJobProposal(ctx, spec.JobProposalID)
	if err != nil {
		return errors.Wrap(err, "orm: job proposal")
	}

	if err = s.isApprovable(ctx, proposal.Status, proposal.ID, spec.Status, spec.ID); err != nil {
		return err
	}

	logger := s.lggr.With(
		"job_proposal_id", proposal.ID,
		"job_proposal_spec_id", id,
	)

	fmsClient, err := s.connMgr.GetClient(proposal.FeedsManagerID)
	if err != nil {
		logger.Errorw("Failed to get FMS Client", "err", err)

		return errors.Wrap(err, "fms rpc client")
	}

	j, err := s.generateJob(ctx, spec.Definition)
	if err != nil {
		return errors.Wrap(err, "could not generate job from spec")
	}

	// All job specs should have external_job_ids
	if j.ExternalJobID == uuid.Nil {
		return errors.New("failed to approve job spec due to missing ExternalJobID in spec")
	}

	// Check that the bridges exist
	if err = s.jobORM.AssertBridgesExist(ctx, j.Pipeline); err != nil {
		logger.Errorw("Failed to approve job spec due to bridge check", "err", err.Error())

		return errors.Wrap(err, "failed to approve job spec due to bridge check")
	}

// ApproveJobProposalSpec approves the job proposal spec.
func (r *Resolver) ApproveJobProposalSpec(ctx context.Context, args struct {
	ID    graphql.ID
	Force *bool
}) (*ApproveJobProposalSpecPayloadResolver, error) {
	if err := authenticateUserCanEdit(ctx); err != nil {
		return nil, err
	}

	id, err := stringutils.ToInt64(string(args.ID))
	if err != nil {
		return nil, err
	}

	forceApprove := false
	if args.Force != nil {
		forceApprove = *args.Force
	}

	feedsSvc := r.App.GetFeedsService()
	if err = feedsSvc.ApproveSpec(ctx, id, forceApprove); err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, feeds.ErrJobAlreadyExists) {
			return NewApproveJobProposalSpecPayload(nil, err), nil
		}
		return nil, err
	}
