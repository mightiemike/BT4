## Analysis

The core mechanism behind the Ambire `tryCatch()` bug — the EIP-150 "63/64ths rule" that reserves `1/64` of available gas in the calling context before forwarding the rest to a sub-call — is explicitly implemented in java-tron's TVM in `Program.getCallEnergy()`: [1](#0-0) 

```java
public DataWord getCallEnergy(DataWord requestedEnergy, DataWord availableEnergy) {
    if (VMConfig.allowTvmCompatibleEvm() && getContractVersion() == 1) {
      DataWord availableEnergyReduce = availableEnergy.clone();
      availableEnergyReduce.div(new DataWord(64));
      availableEnergy.sub(availableEnergyReduce);
    }
    return requestedEnergy.compareTo(availableEnergy) > 0 ? availableEnergy : requestedEnergy;
}
```

This is invoked from `EnergyCost.getCalculateCallCost()` for every `CALL`/`CALLCODE`/`DELEGATECALL`/`STATICCALL`/`CALLTOKEN` opcode to compute `adjustedCallEnergy`, exactly mirroring the EVM's `all but one 64th` semantics referenced in the report.

### Title
EIP-150 "1/64th rule" implemented in TVM's `getCallEnergy` enables identical relayer/attacker gas-griefing against user smart-wallet `tryCatch`-style contracts - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
java-tron's TVM, when a deployed contract has `contractVersion == 1` (EVM-compatible bytecode, enabled via the `allowTvmCompatibleEvm` chain parameter), enforces the identical EIP-150 "reserve 1/64th, forward 63/64th" rule for `CALL`/`CALLCODE`/`DELEGATECALL`/`STATICCALL` as native EVM chains. This means any smart-contract wallet or relayer-executed contract deployed on TRON that implements a `tryCatch()`-style pattern (a low-level call whose failure is caught and does not revert the outer transaction — e.g. a ported Gnosis-Safe/Ambire-style smart account) is exposed to the exact same class of attack described in the external report: a malicious relayer/front-runner can choose the outer energy limit (via `feeLimit`/`energyLimit`) precisely enough to force the inner sub-call to run out of energy while retaining just enough of the reserved `1/64` to let the outer call finish "successfully."

### Finding Description
`EnergyCost.getCalculateCallCost()` computes the energy left in the current frame and passes it to `Program.getCallEnergy(callEnergyWord, getEnergyLimitLeft)`: [2](#0-1) 

`getCallEnergy` then reserves `available/64` before capping the requested call energy against what remains, for contracts with `contractVersion == 1` under `VMConfig.allowTvmCompatibleEvm()`: [1](#0-0) 

The adjusted (capped) energy is what's actually forwarded to the sub-call via `MessageCall`/`callToAddress`, and any unused energy from that sub-call is refunded back into the caller's frame: [3](#0-2) [4](#0-3) 

Crucially, a low-level `call`/`.call()` in TVM Solidity code (compiled for `contractVersion == 1`) never throws — it returns `false` on failure, exactly matching the semantics documented in java-tron's own test suite: [5](#0-4) 

Combining these two facts reproduces the exact root cause from the external report: a contract implementing a `tryCatch(address to, uint256 value, bytes data)`-style function (calling `to.call{gas: gasleft()}(data)` and merely emitting an event on failure, without reverting) is vulnerable to an attacker who crafts the outer transaction's `energyLimit`/`feeLimit` such that the `1/64`-reserved amount left in the outer frame is just enough to finish the wallet's bookkeeping (e.g. incrementing an internal sequence/nonce, charging fees) while the forwarded `63/64` energy is insufficient for the sub-call to complete, causing it to fail with an out-of-energy condition that is silently swallowed.

### Impact Explanation
Any unprivileged, ordinary TRON user who deploys — or who relies on a relayer to execute transactions through — a TVM smart-contract wallet using this pattern (smart accounts, multisig relayers, meta-transaction forwarders ported from EVM ecosystems) is exposed to griefing: a malicious relayer/front-runner can force the intended sub-call (e.g., a token transfer, a governance action, a batched operation) to fail due to out-of-energy while the outer transaction is accepted, resource/fee is consumed, and any state-changing bookkeeping in the outer frame (nonce/sequence increments, fee collection) still commits as if the transaction succeeded. This forces the legitimate user to re-sign and resubmit the intended operation, and in fee-relayed models the user may be charged for a transaction that did not perform its intended sub-call — a concrete griefing/DoS and settlement-divergence impact analogous to the original finding.

### Likelihood Explanation
Exploitability requires: (1) `VMConfig.allowTvmCompatibleEvm()` to be active (this is a chain-level proposal, and once activated network-wide it is not attacker-controlled — it's a network configuration), (2) the target contract deployed with `contractVersion == 1`, and (3) the target contract implementing a `tryCatch`-like failure-swallowing pattern. Given that TRON explicitly ported EVM-compatibility to attract Solidity/EVM contracts (including smart-wallet/relayer patterns) to be deployed unchanged, and the underlying gas-accounting bug is a precise, deterministic re-implementation of EIP-150, this is readily reachable by any user or relayer without special privileges once the network flag is enabled — the same likelihood profile as on Ethereum-compatible chains.

### Recommendation
For any TVM-hosted contract implementing a `tryCatch()`-style call that intentionally swallows sub-call failures, apply the same mitigation recommended in the original report: after the sub-call, verify `gasleft() (energy-left) > availableBefore/64` and revert if not, ensuring the sub-call was not starved due to the 63/64 forwarding rule. At the protocol level, java-tron maintainers should document this EVM-compatibility caveat prominently for developers porting relayer/smart-wallet contracts to TVM, since the `getCallEnergy` 1/64 reservation in `Program.java` (only active for `contractVersion == 1`) reproduces the precise precondition for this class of bug.

### Proof of Concept
Deploy (on a `contractVersion == 1` / EVM-compatible TVM network) a wallet contract mirroring `AmbireAccount.tryCatch`:
```solidity
function tryCatch(address to, uint256 value, bytes calldata data) external payable {
    require(msg.sender == address(this), 'ONLY_IDENTITY_CAN_CALL');
    (bool success, bytes memory returnData) = to.call{ value: value, gas: gasleft() }(data);
    if (!success) emit LogErr(to, value, data, returnData);
}
```
with a target `TestTryCatch.test()` that performs enough SSTORE operations to consume a predictable amount of energy (as in the original PoC). A relayer submits the outer `TriggerSmartContract` transaction with `feeLimit`/computed `energyLimit` chosen so that, after `Program.getCallEnergy` reserves `1/64` of the frame's remaining energy per `Program.java:1842-1848`, the `63/64` forwarded to `TestTryCatch.test()` is insufficient (`OutOfEnergyException` inside the inner `Program`/`VM.play`), while the reserved `1/64` is sufficient for `tryCatch` to catch the failure (`success == false`), emit `LogErr`, and let the outer `execute`/wallet-bookkeeping call return successfully and commit.
