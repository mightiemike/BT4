### Title
Open redirect in `sanitizeRedirectUrl`/`isSafe` via protocol-relative URLs (`//attacker.com/...`) - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts`)

### Summary
`isSafe()` in `validate-redirect-url.ts` fails to verify that the resolved URL's hostname matches the app/shop `domain` passed in. It only checks the raw string for a literal triple slash (`FILE_URI_MATCH`) and checks `url.pathname` (not the raw input or `url.host`) for `INVALID_RELATIVE_URL`. A protocol-relative input such as `//attacker.com/path` bypasses both checks while `new URL(redirectUrl, domain)` resolves to an attacker-controlled origin, producing a genuine open redirect.

### Finding Description
`sanitizeRedirectUrl` is meant to restrict a caller-supplied `redirectUrl` to the app's own `domain` before returning/using it as a redirect target [1](#0-0) . Inside `isSafe`, the checks are:
- `FILE_URI_MATCH = /\/\/\//` on the raw string — only catches 3+ consecutive slashes, so `//attacker.com/path` (exactly 2 slashes) is not caught. [2](#0-1) 
- `INVALID_RELATIVE_URL = /[/\\][/\\]/` is tested against `url.pathname`, **not** the raw input and **not** `url.host`. For `//attacker.com/path`, `new URL('//attacker.com/path', domain)` parses as protocol-relative and resolves `url.hostname` to `attacker.com` while `url.pathname` becomes `/path` — a clean path with no double slash, so this check passes. [3](#0-2) 
- The protocol check (`http:`/`https:`) still passes because the resolved URL inherits `https:` from the base `domain`. [4](#0-3) 

Crucially, there is **no check anywhere in `isSafe` that `url.hostname` (or `url.origin`) equals the hostname of `domain`**. The function's only host-restriction mechanism is the (broken) double-slash heuristic, which does not account for protocol-relative URLs resolving via the WHATWG URL parser to a different authority. As a result, `sanitizeRedirectUrl(domain, '//attacker.com/path')` returns `new URL('//attacker.com/path', domain)`, i.e., `https://attacker.com/path`, instead of throwing.

Any route in the library or a consuming app that passes a user/query-supplied value (e.g., an exit-iframe or post-auth `redirectUrl`/`return_to` parameter) through `sanitizeRedirectUrl` and then redirects the browser to the returned URL (as `renderAppBridge` does via `window.open(destination.toString(), target)` [5](#0-4) ) will send the merchant's browser to the attacker's origin instead of staying within the app/shop domain, defeating the intended allowlist purpose of this helper.

### Impact Explanation
This is a classic open redirect (CWE-601). When an admin/exit-iframe flow redirects the top-level browsing context to an attacker-controlled origin while carrying App Bridge/session-token-bearing URLs or OAuth state, it can leak sensitive tokens/parameters to `attacker.com`, and can be leveraged for phishing within the trusted embedded-app redirect flow. This matches Shopify's open-redirect/SSRF-adjacent impact class for auth-related handlers.

### Likelihood Explanation
Exploitability requires only that some code path pass externally-controlled input (a query parameter, `return_to`/`redirectUrl` value) into `sanitizeRedirectUrl`, which is exactly the documented purpose of the function (sanitizing a redirect target before use) and the scenario given in the question (an exit-iframe/redirect route "built on `sanitizeRedirectUrl`"). No secrets, privileged access, or non-default configuration are required — a single crafted string (`//attacker.com/path`) is sufficient and fully attacker-controlled.

### Recommendation
In `isSafe`, after constructing `url`, explicitly verify that `url.hostname` (and ideally `url.host`/`url.origin`) equals the hostname of the parsed `domain`, rejecting any URL whose authority differs from the app's own domain — do not rely solely on slash-counting heuristics against `url.pathname`. Also apply the double-slash/backslash check to the raw `redirectUrl` (or to `url.host`) in addition to `url.pathname`, since protocol-relative and backslash variants (`\\attacker.com`, `/\attacker.com`) are also normalized by browsers/`URL` in ways that can bypass a pathname-only check.

const FILE_URI_MATCH = /\/\/\//;
const INVALID_RELATIVE_URL = /[/\\][/\\]/;
const WHITESPACE_CHARACTER = /\s/;
const VALID_PROTOCOLS = ['https:', 'http:'];

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

export function sanitizeRedirectUrl<OptionsArg extends Options>(
  domain: string,
  redirectUrl: unknown,
  options: OptionsArg = {} as OptionsArg,
): SanitizedRedirectUrl<OptionsArg> {
  if (isSafe(domain, redirectUrl, options.requireSSL)) {
    return new URL(redirectUrl, domain) as SanitizedRedirectUrl<OptionsArg>;
  } else if (options.throwOnInvalid === false) {
    return undefined as SanitizedRedirectUrl<OptionsArg>;
  } else {
    throw new ShopifyError('Invalid URL. Refusing to redirect');
  }
}
