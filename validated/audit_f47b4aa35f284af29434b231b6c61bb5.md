### Title
Untested, platform-divergent custom math library (`MathWrapper`/`Maths`) used in consensus-critical exchange-rate computation - (File: `platform/src/main/java/x86/org/tron/common/math/MathWrapper.java`, `platform/src/main/java/arm/org/tron/common/math/MathWrapper.java`, `common/src/main/java/org/tron/common/math/Maths.java`)

### Summary
java-tron ships a custom, hand-rolled math abstraction layer (`Maths`, `MathWrapper`, `StrictMathWrapper`) that mirrors the external report's bug class: an untested, ad-hoc arithmetic library sitting underneath consensus-critical accounting logic (the bancor-style exchange/relay computation in `ExchangeProcessor`/`SafeExchangeProcessor`). Unlike the Solidity `SafeMath` case, here the risk is compounded because there are two entirely different, platform-specific implementations of the same `MathWrapper` class — one for x86 and one for ARM — selected at build time, and neither is covered by a dedicated unit test suite (`MathWrapperTest`, `StrictMathWrapperTest`, `MathsTest` do not exist in the repo).

### Finding Description
The library is organized as:
- `common/src/main/java/org/tron/common/math/Maths.java` — a dispatcher that picks between `StrictMathWrapper` (uses `StrictMath`) and `MathWrapper` (platform module) based on a chain parameter `disableJavaLangMath`. [1](#0-0) 
- `platform/src/main/java/x86/org/tron/common/math/MathWrapper.java` implements `pow` via plain `Math.pow`. [2](#0-1) 
- `platform/src/main/java/arm/org/tron/common/math/MathWrapper.java` implements `pow` via a hand-maintained hardcoded lookup table (`powData`, ~50 entries tied to specific historical mainnet block computations) that falls back to `StrictMath.pow` for any input not in the table. [3](#0-2) [4](#0-3) 

This `pow` routine is used directly in the TRC10 bancor-exchange price computation (`ExchangeProcessor`, `SafeExchangeProcessor`), which is exercised by unprivileged users through `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` actuators. [5](#0-4) 

The `MathWrapper` class is explicitly marked `@Deprecated` with a comment stating it should not be used for new code "for cross-platform consistency," which is a documented admission that the two platform variants are not guaranteed to compute identical results. [6](#0-5) [7](#0-6) 

A search of the test tree confirms there is no dedicated unit test class for `Maths`, `MathWrapper` (either platform variant), or `StrictMathWrapper` — the only coverage found is indirect, through `ExchangeProcessorTest`/`BIUtilTest`, which do not exercise the platform-specific `pow` lookup table or the `disableJavaLangMath`/toggle-driven dispatch paths at all.

### Impact Explanation
If a node compiled for x86 (using `Math.pow`, whose result for a given input is only guaranteed correct to within 1 ulp and is *not* required by the JLS to be bit-identical across implementations/architectures) computes a different double value than a node compiled for ARM (using `StrictMath.pow` or the hardcoded lookup table) for the same `(base, exponent)` pair in the bancor exchange formula, the resulting `long` balances stored in `ExchangeCapsule` will diverge between nodes. Since this computation feeds directly into account/asset balance updates executed by the public `ExchangeTransactionActuator`/`ExchangeInjectActuator`, a divergence here is a state/accounting divergence in consensus-critical execution — the exact impact class this analog scan is meant to flag (invalid-state/divergence). The `disableJavaLangMath` flag is a chain-governed toggle (default off, i.e., not "strict"), meaning by default nodes take the `MathWrapper` platform-specific path rather than the safer `StrictMathWrapper` path. [8](#0-7) 

### Likelihood Explanation
Likelihood is limited by two factors I could not fully confirm from the index: (1) whether java-tron mainnet/production nodes are actually built and deployed from both the x86 and arm platform modules simultaneously (mixed-architecture validator set), and (2) whether the ARM lookup table's fallback to `StrictMath.pow` for untabulated inputs makes it byte-identical to the `StrictMathWrapper` path in all reachable exchange scenarios. The comment marking `MathWrapper` `@Deprecated` in favor of `StrictMathWrapper` suggests the project itself has already identified and is migrating away from this divergence risk, which lowers current likelihood of active exploitation, but the code path remains live, reachable by any unprivileged user issuing an exchange transaction, and is not covered by any dedicated arithmetic/consensus test.

### Recommendation
Add exhaustive, cross-platform-parity unit tests for `Maths`, `MathWrapper` (both x86 and arm variants), and `StrictMathWrapper`, specifically asserting that `pow`, `addExact`, `multiplyExact`, etc. produce identical outputs regardless of the compiled platform module for the full range of inputs reachable via `ExchangeProcessor`/`SafeExchangeProcessor`. Complete the migration away from `MathWrapper` to `StrictMathWrapper` (or an equivalent guaranteed-deterministic implementation) for all consensus-critical arithmetic, and consider gating removal of the deprecated path behind a hard fork once full test coverage confirms no residual divergence.

### Proof of Concept
Not applicable as a runnable exploit — this is a code-structure finding based on: `Maths.pow` dispatching to either `MathWrapper.pow` (x86: `Math.pow`) or `StrictMathWrapper.pow` (`StrictMath.pow`) depending on the `disableJavaLangMath` chain parameter, with the ARM `MathWrapper.pow` implementation additionally diverging via a hardcoded historical lookup table, all reachable through the public exchange actuators and none of it covered by dedicated unit tests in the repository's test tree.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
