**Analysis:**

The premise fails at the very first step of `performTokenExchange`. Every incoming session token must pass `api.session.decodeSessionToken(sessionToken)` before any session-storage interaction occurs [1](#0-0) . That function verifies the JWT signature with `jose.jwtVerify` using `getHMACKey(config.apiSecretKey)`, and any signature failure throws `InvalidJwtError` immediately [2](#0-1) . An attacker without the app's `apiSecretKey` cannot produce a token that passes this check, so "freshly-forged (invalid) session tokens" never reach `loadSession`/`storeSession` at all — they are caught in the outer `catch` block and answered via `respondToInvalidSessionToken` with no storage access [3](#0-2) .

Additionally, `config.idempotentPromiseHandler.handlePromise({..., identifier: sessionToken})` is only used to deduplicate the `afterAuth` hook call, not to gate `loadSession`/`storeSession` [4](#0-3) . It has no bearing on session storage races. The `sessionId` used for storage lookups is derived from `shop`/`sub` extracted from the cryptographically-verified JWT payload (`payload.dest`, `payload.sub`), not from an attacker-controlled string, so distinct shops can never collide on the same `sessionId` [5](#0-4) . Since valid tokens for different shops necessarily produce different `sessionId`s, there is no cross-tenant read/write interleaving possible through this code path, and since forged/invalid tokens are rejected before any storage call, there is no resource-exhaustion or race vector introduced by this function that isn't already inherent to ordinary concurrent legitimate traffic.
