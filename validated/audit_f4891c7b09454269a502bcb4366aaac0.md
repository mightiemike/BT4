### Title
Exchange pool ratio manipulation causes miscalculated token amounts in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` due to missing slippage protection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's native bancor-style `Exchange` feature computes the counterpart token amount for `ExchangeInject` and `ExchangeWithdraw` operations purely from the exchange's *current* on-chain `firstTokenBalance`/`secondTokenBalance` ratio at execution time. Unlike `ExchangeTransactionContract`, which includes an `expected` field for slippage protection, `ExchangeInjectContract` and `ExchangeWithdrawContract` have no such field. Any unprivileged account can shift the pool ratio immediately before the target transaction executes by broadcasting an ordinary `ExchangeTransactionContract` (swap), causing the inject/withdraw actuator to compute a manipulated `anotherTokenQuant`, harming the exchange creator (who lacks any means to bound the result) — directly analogous to the exchange-rate manipulation described in the referenced report, where an unprotected mint/redeem calculation based on a manipulable pool state let an attacker cause the victim to receive an unfavorable, unbounded amount.

### Finding Description
`ExchangeInjectActuator.execute()` reads the exchange's live balances and computes the paired amount proportionally: [1](#0-0) 

The same pattern exists in `ExchangeWithdrawActuator.execute()`: [2](#0-1) 

Neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` carry a user-supplied bound/expected value, whereas `ExchangeTransactionContract` explicitly does: [3](#0-2) 

The pool's `firstTokenBalance`/`secondTokenBalance` ratio is freely and cheaply movable by any anonymous account through a normal `ExchangeTransactionContract` broadcast (a swap), which directly mutates the same `ExchangeCapsule` balances used for the ratio calculation: [4](#0-3) 

Because `ExchangeInjectActuator`/`ExchangeWithdrawActuator` compute `anotherTokenQuant` strictly from the balances present at execution time, an attacker can broadcast a swap transaction ordered immediately before the victim's inject/withdraw transaction (transaction ordering within a block/producer window is attacker-influenceable, as in typical front-running/sandwich scenarios) to skew the ratio, then reverse the swap afterward. This mirrors the reported bug class exactly: a state variable (the pool ratio, analogous to `CToken`'s `exchangeRateStoredInternal()`) that determines a minted/withdrawn amount is manipulable by an unprivileged actor right before another user's transaction that has no slippage/bound protection.

### Impact Explanation
An exchange creator injecting liquidity via `ExchangeInjectContract`, or withdrawing liquidity via `ExchangeWithdrawContract`, can be forced to inject a disproportionate amount of the counterpart token, or receive a disproportionate/reduced counterpart amount on withdrawal, respectively, based on a transiently manipulated ratio. This is an asset/accounting-corruption class impact: value can be extracted from the exchange creator by an attacker who sandwiches the operation with `ExchangeTransactionContract` swaps, profiting at the victim's expense. Since `ExchangeInjectActuator`/`ExchangeWithdrawActuator` require the caller to be the exchange creator, the affected party is the entity managing the pool's on-chain TRC10/TRX liquidity — a legitimate value-at-risk scenario for any project relying on this native exchange feature.

### Likelihood Explanation
Executing this requires only ordinary, unprivileged transactions: an `ExchangeTransactionContract` to move the ratio, and reliance on normal block/transaction ordering incentives (attacker can time submission or use existing MEV-style techniques available on any public chain) to have the swap land adjacent to the victim's inject/withdraw call. No special privileges, keys, or node access are needed — only knowledge of a target's pending inject/withdraw transaction and access to the exchange's token(s) to swap.

### Recommendation
Add an `expected`/slippage-bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring the existing `expected` field in `ExchangeTransactionContract`), and validate the actuator-computed `anotherTokenQuant` against that bound in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, rejecting the transaction if the computed amount falls outside the caller-specified tolerance.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) from the exchange creator for exchange `id` with `tokenID = firstTokenID`, `tokenQuant = Q`.
2. Attacker broadcasts an `ExchangeTransactionContract` swap on the same exchange that shifts `firstTokenBalance`/`secondTokenBalance` sharply (e.g., sells a large amount of `secondTokenID` into the pool), landing before the creator's transaction.
3. The creator's `ExchangeInjectActuator.execute()` computes `anotherTokenQuant = secondTokenBalance * Q / firstTokenBalance` using the now-skewed balances, producing a value far from what the creator intended when they signed the transaction, and the creator's account is debited an amount of the counterpart token computed from the skewed ratio.
4. Attacker reverses the swap afterward, restoring the ratio and pocketing the difference extracted from the creator's injected/withdrawn liquidity.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
