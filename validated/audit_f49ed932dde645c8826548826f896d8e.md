### Title
Replay-verify integrity gap: `TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes against the committed `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the authenticated-equivalence check used by chunk-executor commit verification and by `db-tool`'s `replay_on_archive` to confirm that a locally-produced `TransactionOutput` matches the `TransactionInfo` that was actually committed to the ledger accumulator. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but it explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the three fields that actually bind a version to its Merkle state root.

### Finding Description [1](#0-0) 

The function performs the following checks, in order: transaction status, gas used, write-set hash vs `txn_info.state_change_hash()`, and event root hash vs `txn_info.event_root_hash()`. It then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` to any locally computed root. This is called out in an explicit code comment: [2](#0-1) , acknowledging that "replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is invoked from the real replay/verification call sites: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Meanwhile, the state-checkpoint root itself is computed and cross-checked against `known_state_checkpoints`/`known_position_state_checkpoints` only inside `DoStateCheckpoint::run` in the chunk-executor's `update_ledger` path (used for consensus-driven commit/state-sync chunk application), via `get_state_checkpoint_hashes`: [7](#0-6) . That path does enforce equality of the *last checkpoint in a chunk* against the known hash from `TransactionInfo`. However, `ensure_match_transaction_info` is a separate, weaker, general-purpose “does this output match this info” check used by replay/debugging/verification tools that do not go through the full `DoStateCheckpoint` chunk-execution machinery (e.g., single-transaction replay via `aptos-debugger`, `aptos move` CLI verification, or `db-tool replay-on-archive`). In those tools, a transaction whose write set happens to hash to the correct `state_change_hash` (the write set itself matches) but whose *state checkpoint root* computed on top of a different base state (or reached via divergent hot-state or position-state trees) diverges from the ledger-committed checkpoint hash will still pass verification silently.

### Impact Explanation
This breaks the "authenticated API/state-view output must stay bound to the right ledger version, root, and object" and "restore/replay paths must not reinterpret committed data into a different ledger state" invariants required by the scope. A checkpoint hash is the only artifact that binds a version's write-set-derived resource values to a specific global Merkle root; skipping it means replay/verification tooling can affirmatively confirm a "correct" replay of history while the reconstructed state tree (main, hot, or the new native-position tree) has silently diverged from the authenticated one committed by consensus. This is exactly the kind of "hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong… state proof accepted as valid" scenario called out as in-scope, because operators/auditors relying on `replay_on_archive` (a tool whose entire purpose is to detect state divergence across upgrades) would get a false "OK" for a version where the state root is actually wrong.

### Likelihood Explanation
The unverified fields are precisely the new/rarely-exercised ones (`hot_state_checkpoint_hash`, and the newly repurposed `position_state_checkpoint_hash` field for the trading-native subsystem), i.e. paths most likely to contain a currently-undetected divergence bug, and the code comment itself documents that this gap is known but currently unaddressed. The gap is real today (unconditional, not itself feature-gated) in the general-purpose comparator; its practical blast radius grows as `HOT_STATE_ROOT_IN_TXN_INFO` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS` features are turned on, at which point this comparator would give false confidence during any incident investigation or upgrade replay-verification that relies on `ensure_match_transaction_info` rather than the full chunk-executor checkpoint path.

### Recommendation
Extend `ensure_match_transaction_info` to recompute (from `self`/`expected_write_set` context, or require the caller to supply) the state/hot-state/position checkpoint hashes when `txn_info.state_checkpoint_hash()` (etc.) is `Some`, and `ensure!` they match, mirroring the validation already done in `DoStateCheckpoint::get_state_checkpoint_hashes`. At minimum, callers such as `replay_on_archive` should independently verify these checkpoint hashes before reporting success, closing the gap noted in the existing TODO before any feature relying on additional checkpoint roots is enabled in production.

### Proof of Concept
Conceptual (no test harness access in this environment):
1. Construct a `TransactionOutput` whose write set serializes/hashes identically to the real one committed on-chain (`state_change_hash` matches) and whose events match (`event_root_hash` matches), but which is being replayed on top of a divergent base state snapshot (e.g., a subtly corrupted hot-state or position-state tree, or a bug in `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` computation).
2. Call `TransactionOutput::ensure_match_transaction_info(version, txn_info, ...)` — it returns `Ok(())` because status/gas/write-set-hash/event-hash all match.
3. Independently compute the real state-checkpoint root (e.g., via `DoStateCheckpoint::run`) and show it differs from `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` — demonstrating `ensure_match_transaction_info` failed to catch the divergence that a security-relevant replay/verification tool depends on it to catch.

Note: I could not fully trace whether `HOT_STATE_ROOT_IN_TXN_INFO` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled on mainnet today — the feature flags exist ( [8](#0-7) ) but their runtime enablement state is outside what the code index can confirm here; this affects how immediately exploitable the gap is in production versus only in future upgrades.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
