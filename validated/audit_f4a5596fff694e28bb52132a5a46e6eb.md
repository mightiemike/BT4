### Title
Wallet Contract `has_in_flight_tx` flag can become permanently stuck `true`, freezing ETH-implicit account funds forever - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (deployed on every ETH-implicit account, per NEP-518) uses a boolean guard `has_in_flight_tx` to serialize transaction execution. This flag is set to `true` when `rlp_execute` schedules a promise, and is only reset to `false` inside one of the private callback functions (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). If the receipt executing one of these callbacks fails for any reason (including running out of its allotted gas) *after* the `self.has_in_flight_tx = false;` line executes but before the callback receipt finishes successfully, NEAR's runtime rolls back **all** state changes made during that receipt — including the flag reset. The flag remains `true` on-chain forever. Because `rlp_execute` unconditionally rejects all future calls while `has_in_flight_tx == true`, and because ETH-implicit accounts (per `docs/DataStructures/Account.md`) can *only* be operated via this Wallet Contract and can never have a full access key added or be deleted, this is an unrecoverable, permanent freeze of all funds held by that account.

### Finding Description [1](#0-0) 
`has_in_flight_tx` is documented as an invariant that must be `true` while a promise is outstanding and `false` otherwise, but this invariant is enforced only via callback-internal writes, not atomically with the outer call. [2](#0-1) 
`rlp_execute` immediately returns an error response ("transaction already in progress") whenever `has_in_flight_tx` is `true`, with no bypass, timeout, or admin override. [3](#0-2) 
Each callback (`address_check_callback`, `nep_141_storage_balance_callback`) resets the flag as its *first* statement, then goes on to parse an untrusted cross-contract response (`serde_json::from_slice`) and construct a further chained `Promise` (e.g., calling `storage_deposit` + the original action, or `action_to_promise`). All of this work happens inside the same receipt whose gas budget is a small, fixed constant (`ADDRESS_CHECK_CALLBACK_GAS` / `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, 10–15 Tgas plus `action.gas()`), set via `.with_static_gas(callback_gas)` at the call site. [4](#0-3) 
The gas passed to the callback is a fixed value computed from constants plus the user's requested `action.gas()`; it is not guaranteed to be enough for edge cases such as deserializing a maliciously large/complex JSON payload returned by an untrusted `storage_balance_of`/registrar `lookup` call, since the callback body's compute cost scales with the size/complexity of that external response, not with a value the wallet contract controls.

If the callback's receipt runs out of gas anywhere after the initial flag reset (e.g., during `serde_json::from_slice` of an oversized response, or during promise construction for the second `.then()`), the runtime treats the whole receipt as failed: [5](#0-4) 
"Executing actions costs gas. Each receipt has some amount of gas attached to it. If the gas runs out, receipt execution fails... When a receipt fails, its state changes are rolled back using `TrieUpdate`." [6](#0-5) 
"Commit or rollback: success commits ...; failure calls state_update.rollback(), discarding all state changes from the receipt."

This means the `has_in_flight_tx = false` write made at the top of the callback is discarded along with everything else, and the flag remains `true` as it was before the callback ran. Since `rlp_execute` is the **only** entry point for the account (no full access key, no `DeleteAccount`, no admin path — [7](#0-6) ), every subsequent `rlp_execute` call short-circuits at line 97 (`if self.has_in_flight_tx { return ... }`) and the account can never again move any of its NEAR balance or NEP-141 token holdings.

### Impact Explanation
This is a direct analog of the ThunderNFT finding: a stateful "gate" condition (there: asset-whitelist check; here: `has_in_flight_tx` flag) can be left in a state that blocks all future withdrawals/transfers of a user's own funds. Unlike the original bug — which was recoverable by the protocol owner re-whitelisting the asset — this Wallet Contract analog has **no recovery path whatsoever**: ETH-implicit accounts cannot have a full-access key added, cannot be deleted, and are permanently locked to `rlp_execute`. Any NEAR balance or NEP-141 tokens held by the account become permanently frozen. This satisfies the "permanently frozen funds" impact category and is reachable purely through normal usage of the wallet's ERC-20/emulation feature or the address-registrar flow, both of which are triggered by a single submitted (relayed) Ethereum-style transaction — no privileged, validator, or node-level access is required.

### Likelihood Explanation
The trigger requires the callback receipt to run out of gas after the flag reset but before completion. The most concrete path is the `nep_141_storage_balance_callback` / `address_check_callback` flow, where the callback must deserialize a `serde_json` response returned by an external, untrusted contract (the NEP-141 token contract the user is transacting with, or the address registrar) and then build a follow-on chained promise, all within a small fixed gas budget (`NEP_141_STORAGE_BALANCE_OF_GAS` + constants). A user interacting via this wallet with a token/registrar contract that returns an oversized or unusually complex response (whether due to a bug, congestion-driven gas repricing edge cases, or a malicious token the relayer/target routes to) can push the callback over budget. Given the fixed, low static gas allocation and the untrusted, variable-size nature of the deserialized payload, this is a plausible and repeatable condition rather than a purely theoretical one, though it does require a specific gas-exhaustion timing (mid-callback, post-flag-reset) which the test suite (`tests/sanity.rs::test_insufficient_gas`) only demonstrates for the *outer* `rlp_execute` call insufficient-gas case (which is safe, since it fails before the flag is ever set), not for the internal callback case, indicating this specific failure mode is not covered by existing tests.

### Recommendation
Do not reset `has_in_flight_tx` as the first statement of a callback. Instead, reset it only in a state write that is guaranteed to commit atomically with the receipt's success (e.g., set the flag to `false` at the very end, right before returning success/failure) or, better, make the flag reset itself failure-safe by wrapping the risky work in try/catch-equivalent constructs and reserving a fixed, generous gas buffer strictly for deserialization and flag update, ensuring these commit even if follow-on work fails. Alternatively, add a self-recoverable timeout/reset mechanism (e.g., a privileged `reset_in_flight` callable only by the account itself via a subsequent, sufficiently-gassed transaction, or a scheme that treats a stuck flag with an old nonce as eligible for reset after N blocks) so that the invariant "an account can never again execute" cannot be reached irrecoverably.

### Proof of Concept
1. Deploy an NEP-141-like contract whose `storage_balance_of` method returns a very large (near max return-value size) or deeply nested JSON payload for a specific `account_id`.
2. From an ETH-implicit account (Wallet Contract instance), submit (via relayer) an RLP-encoded Ethereum transaction that is an ERC-20 `transfer` targeting that token contract, with `receiver_id` chosen so that `nep_141_storage_balance_callback`'s `NEP_141_STORAGE_BALANCE_OF_GAS`-bounded step is triggered [8](#0-7) .
3. Tune the static gas request (bounded by `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` plus `action.gas()`) and the size/complexity of the malicious token's `storage_balance_of` response so that `serde_json::from_slice` inside `nep_141_storage_balance_callback` consumes more gas than remains after the flag reset, causing the receipt to abort with `GasExceeded`.
4. Observe on-chain that `has_in_flight_tx` remains `true` (the rollback discards the reset), and that any subsequent `rlp_execute` call to this account immediately returns `"Error: transaction already in progress, please try again later."` indefinitely, with no way to reset the flag since the account cannot obtain a full access key or be deleted.

(Note: precisely tuning the gas margin to reliably trigger this mid-callback abort — rather than failing earlier or later — would need to be validated experimentally against the exact `NEP_141_STORAGE_BALANCE_OF_GAS`/`NEP_141_STORAGE_DEPOSIT_GAS` constants and current runtime gas-metering costs for `serde_json` deserialization, which I was not able to fully verify from static analysis alone.)

            predecessor_account_id,

            Err(e) => PromiseOrValue::Value(e.into()),

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

Each account can have multiple access keys, which are used to validate transactions submitted for this account. NEAR supports named accounts which don't have the public key in their name (e.g. `alice.near`). When a transaction is submitted, the verification code fetches the account's access key and verifies the transaction's signature against this key.

Receipts are not signed, so they're not validated using access keys. Receipts can be trusted because their hash has been signed by 2/3 of the chunk validator stake.

To modify the shard's state, the runtime uses `TrieUpdate`. This struct applies changes on top of the chunk's pre-state. It allows to rollback or commit recent changes. When a receipt fails, its state changes are rolled back using `TrieUpdate`.
