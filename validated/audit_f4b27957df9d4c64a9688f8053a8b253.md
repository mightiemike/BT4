### Title
Deposits that fail on-chain during `process_sys_txs` are silently and permanently dropped from the sequencer's deposit mempool - (File: `crates/sequencer/src/runner.rs`)

### Summary
`CitreaSequencer::process_sys_txs` reverts and skips any `BridgeDeposit` system transaction whose EVM execution returns `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful`, excluding it from the produced block's `all_txs`. However, `produce_l2_block_inner` unconditionally removes the *entire originally-fetched* `deposit_data` list from `DepositDataMempool` after block production, regardless of which deposits actually succeeded, causing failed-but-legitimate deposits to vanish from the mempool without ever being credited.

### Finding Description
The binding that must hold is: `deposit_data` (the list fetched via `fetch_deposits` at crates/sequencer/src/runner.rs:517-520 and passed by reference through `dry_run_transactions`/`process_sys_txs`) must equal the set of deposits actually credited (i.e., present in `all_txs` and thus in the produced L2 block).

In `process_sys_txs` (crates/sequencer/src/runner.rs:1617-1706), when `apply_l2_block_txs` returns `StateTransitionError::ModuleCallError(L2BlockModuleCallError::EvmSystemTransactionNotSuccessful)` for a deposit event, the code explicitly reverts `working_set_to_discard` and `continue`s (lines 1682-1697) — the deposit is never pushed to `all_txs` (only pushed on success, line 1701-1702) and is not re-queued anywhere. [1](#0-0) 

Back in `produce_l2_block_inner`, after the block is finalized and saved, the code calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the same `deposit_data` variable fetched at the top of the function — the full original list, not the subset that actually succeeded. [2](#0-1) 

`DepositDataMempool::remove_deposits` removes each matching entry from both `accepted_deposit_txs` and `pending_deposits` unconditionally based on the passed list. [3](#0-2) 

The root cause is that `process_sys_txs`'s per-deposit success/failure result is discarded and never propagated back to `produce_l2_block_inner`; only the aggregate `all_txs` (which the caller doesn't diff against `deposit_data`) reflects it. No existing guard (`apply_l2_block_txs`, `EvmSystemTransactionNotSuccessful` handling, or `remove_deposits`) re-checks which specific deposits landed in the block before eviction.

The failure trigger itself does not require any special "colliding txId" mechanism to be exploitable — because `citrea_sendRawDepositTransaction`'s `eth_call` simulation (crates/sequencer/src/rpc.rs:339-353) is only a point-in-time check against `BlockId::pending()`. Any legitimate deposit that passed simulation can later fail when actually applied in `process_sys_txs` if intervening state changes (e.g., another deposit or contract state change processed earlier in the same `process_sys_txs` loop, or state drift between simulation and eventual block inclusion) cause the Bridge-side call to revert at execution time. An unprivileged attacker can trivially widen this race by submitting a second deposit (via `citrea_sendRawDepositTransaction`, which anyone can call) engineered to consume/alter shared Bridge contract state ahead of a target deposit within the same block's processing order.

### Impact Explanation
When this triggers, the depositor's underlying Bitcoin `moveTx` has already irrevocably moved BTC into the N-of-N vault, but the corresponding cBTC credit never lands in the block, and the deposit blob is deleted from `accepted_deposit_txs` and `pending_deposits`. This is a fund-freezing condition: the depositor's cBTC mint never occurs and there is no automatic retry or record kept by the sequencer. Although the depositor's txid is also removed from `pending_deposits` — meaning a resubmission via `citrea_sendRawDepositTransaction` is *technically* possible if the failure was transient — if the failure results from a permanent state condition (e.g., a Bridge-side state check that can never re-pass, or a race that recurs identically) the deposit can never succeed again. This is reproducible on every block that fetches ≥1 pending deposit and encounters an `EvmSystemTransactionNotSuccessful` for any of them; the blast radius covers every deposit fetched in the same batch alongside a failing one is unaffected (each deposit is handled/removed individually via `calc_tx_id` matching), but the specific failing deposit is dropped every time it's included and fails, matching the Critical "funds permanently frozen" category.

### Likelihood Explanation
No special privileges are needed: any user can submit deposits via `citrea_sendRawDepositTransaction`, and the attacker only needs to get their own deposit(s) processed by the sequencer in the same or an intervening L2 block window relative to a victim's deposit, exploiting the gap between the RPC-time `eth_call` simulation and actual block-time execution in `process_sys_txs`. This requires no majority hashrate, no key compromise, and only Bitcoin fees for a valid deposit inscription (to get any deposit into `deposit_mempool` in the first place) — a cheap and repeatable attack surface, limited by the sequencer's deposit ordering/batch composition, which the attacker cannot fully control but can influence via submission timing.

### Recommendation
`process_sys_txs` should return the list (or indices) of deposits that failed with `EvmSystemTransactionNotSuccessful` back to the caller, and `produce_l2_block_inner` must compute `remove_deposits` on the actually-succeeded subset only (e.g., `deposit_data` minus the failed ones), leaving failed deposits in the mempool for retry in a subsequent block, or explicitly surfacing/logging them as requiring manual/automatic resubmission rather than silently discarding.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });
