### Title
Blocking rate-limiter `acquire()` on the gRPC request-handling thread enables server thread-pool exhaustion DoS - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/RateLimiterInterceptor.java])

### Summary
`RateLimiterInterceptor.interceptCall` invokes `rateLimiter.acquirePermit(runtimeData)` synchronously before delegating to `next.startCall(...)`, and when `rate.limiter.apiNonBlocking=false` (the shipped default in both `reference.conf` and `CommonParameter.rateLimiterApiNonBlocking`) this dispatches to `IPQPSRateLimiterAdapter.acquire`, which calls the blocking Guava `RateLimiter.acquire()` inside `IPQpsStrategy.acquire(String)`. An unprivileged client opening many concurrent gRPC calls to a low-qps, IP-rate-limited method can park many gRPC executor threads inside this blocking call, since Guava's `RateLimiter` has no bound on the number of concurrent waiters and computed wait time grows with contention.

### Finding Description
`RateLimiterInterceptor.interceptCall` runs on the gRPC server's call-handling thread and executes rate-limiting logic before `next.startCall`: [1](#0-0) 

The per-endpoint check dispatches through `IRateLimiter.acquirePermit`, which chooses between non-blocking `tryAcquire` and blocking `acquire` purely based on the `apiNonBlocking` flag: [2](#0-1) 

For an `IPQPSRateLimiterAdapter`-configured method, `acquire` delegates to `IPQpsStrategy.acquire(String)`: [3](#0-2) [4](#0-3) 

`limiter.acquire()` is Guava's blocking `RateLimiter.acquire()`, which computes a synchronization delay proportional to how many permits have already been reserved for other pending callers on the same key; because there is no cap on outstanding acquisitions, an attacker opening `N` concurrent calls against a low-qps IP-limited method causes wait times to grow roughly linearly with `N`, holding the calling thread parked for an unbounded duration. `apiNonBlocking=false` is the documented and shipped default (`reference.conf` line 520, `CommonParameter.rateLimiterApiNonBlocking = false`), so no non-default configuration is required to hit the blocking path — only that some endpoint is configured with `IPQPSRateLimiterAdapter` and a low `qps` (an explicitly documented/supported configuration, not exotic).

None of the existing checks stop this: the per-endpoint limiter runs before the global limiter, so the blocking happens regardless of `GlobalRateLimiter`; there is no concurrency cap on how many threads may simultaneously block inside `IPQpsStrategy.acquire`; and the permit-release logic (`onComplete`/`onCancel`/catch block) only fires after `acquirePermit` returns, i.e., after the thread is already unblocked — it does nothing to bound the number of threads that can be blocked concurrently.

### Impact Explanation
This maps to "DoS via RPC-API": if the number of concurrently blocked threads exceeds the server's available gRPC worker/executor threads, unrelated legitimate callers (different IPs, different methods sharing the same executor) experience call starvation/timeouts because no threads are free to run `interceptCall` for their requests. The attack requires only unprivileged network access to the gRPC endpoint — no signed transaction, funded account, or special role is needed.

### Likelihood Explanation
Preconditions: `apiNonBlocking=false` (shipped default) and at least one gRPC method configured with `IPQPSRateLimiterAdapter` at a low `qps` (a documented, supported configuration pattern shown in `reference.conf`/`docs/configuration.md`). Cost to the attacker is negligible — opening concurrent TCP/gRPC connections is free and requires no fee, signature, or on-chain footprint. Feasibility depends on operational specifics not verifiable from the index alone: the actual gRPC server executor/thread-pool size and connection limits in `RpcApiService`/`RpcService` (I was not able to fully inspect `RpcApiService.java`'s `ServerBuilder` construction within available tool calls, so I cannot confirm the exact executor type/size, e.g., whether it's Netty's default cached executor or a fixed-size pool). This uncertainty affects how many concurrent connections are needed to exhaust the pool, but the underlying blocking-call defect in `RateLimiterInterceptor`/`IPQpsStrategy` is independently confirmed by the code cited above.

### Recommendation
Avoid blocking the gRPC call-handling thread inside `interceptCall`. Options: (1) bound the number of concurrent blocked acquirers per IP/method (e.g., cap via a semaphore before invoking `acquire`, rejecting excess with `RESOURCE_EXHAUSTED` instead of queuing indefinitely); (2) perform the blocking `acquire()` on a dedicated bounded executor with a timeout and fail fast if the timeout elapses, rather than the shared server-handling thread; (3) reconsider whether `apiNonBlocking=false` (blocking) should remain the default given it directly ties client-controlled concurrency to server thread consumption.

### Proof of Concept
Extend `RateLimiterInterceptorTest` style: configure a small fixed executor as the gRPC server's call executor, register an `IPQPSRateLimiterAdapter` with `qps=1` for a test method (mirroring `IPQpsStrategy` construction in `AdaptorTest.testIPQPSRateLimiterAdapter`), then fire more concurrent calls than executor threads from a single source IP and a control call from a different IP:

```java
IPQPSRateLimiterAdapter adapter = new IPQPSRateLimiterAdapter("qps=1");
container.add(KEY_RPC, METHOD_NAME, adapter);
Args.getInstance().setRateLimiterApiNonBlocking(false);

ExecutorService pool = Executors.newFixedThreadPool(2); // simulate small server pool
// Fire N=10 concurrent interceptCall invocations from IP "1.2.3.4" on `pool`
// Fire 1 interceptCall from IP "9.9.9.9" and assert it completes within e.g. 200ms.
// Expected (vulnerable): the control call from "9.9.9.9" is delayed/times out because
// both pool threads are parked inside IPQpsStrategy.acquire("1.2.3.4").
```

Note: full reproduction requires wiring an actual bounded executor into the gRPC `Server`/`ServerBuilder` used by `RpcApiService`, which was not fully inspected in this session; the JUnit sketch above isolates and demonstrates the blocking-thread-consumption defect at the `IRateLimiter`/`IPQpsStrategy` level, which is the root cause.
