## Analysis

The GMXv2 bug is a **misdirected fee/deposit refund on failure**: the party that actually pays for a transaction's execution (the keeper) is not the party the protocol refunds when that transaction later fails, because the refund address (`self.refundee`) is left pointing at the original depositor.

NEAR has a structurally identical pattern in its **meta-transaction (NEP-366) balance-refund logic**.

### Finding Description

In a meta transaction, a relayer signs and pays for a `SignedDelegateAction` that is unpacked on the sender's (`Alice`'s) shard and forwarded as a new action receipt to the final receiver (`Bob`). If execution fails on `Bob`'s shard, the runtime computes a **deposit refund** and sends it to `receipt.balance_refund_receiver()`, which resolves to the receipt's `predecessor_id` unless an explicit `refund_to` override was set: [1](#0-0) 

That receiver is then used directly when constructing the refund receipt: [2](#0-1) 

Because the receipt forwarded from `Alice`'s shard to `Bob`'s shard has `predecessor_id == Alice` (not the relayer who actually funded the deposit), any attached-deposit refund from a failed inner action goes to `Alice`, even though the relayer paid for the deposit and the gas. This is explicitly documented as a known, exploitable-by-design gap: [3](#0-2) 

By contrast, **gas refunds** correctly go to `action_receipt.signer_id()` (the original transaction signer/relayer), which is the correct payer: [4](#0-3) 

This is the same root-cause shape as the GMX report: a fee/deposit-bearing operation is executed by one party (keeper / relayer) but reversal-time refund logic defaults to crediting a different party (depositor / meta-tx sender) that did not pay.

A partial mitigation (`promise_set_refund_to` / `refund_to_account_id` host functions) now lets a predecessor explicitly redirect refunds for receipts it creates: [5](#0-4) 

However, this is opt-in — relayers/receivers that don't proactively call `promise_set_refund_to` when forwarding delegate-action-derived receipts remain exposed to the default behavior, exactly as the docs warn: *"this is something relayer implementations must be aware of since there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard."*

### Impact Explanation

A relayer that funds attached deposits for a meta-transaction's inner actions can have those deposits refunded to the meta-transaction's sender instead of itself when the inner action fails on the final receiver's shard, resulting in a direct, protocol-level, unauthorized value transfer away from the party that paid. Malicious senders can craft meta-transactions with deliberately-failing, deposit-heavy inner actions on `Bob`'s shard specifically to capture this refund. This meets the "concrete unauthorized value movement" bar.

### Likelihood Explanation

This requires no privileged capability — any account can act as `Alice`, sign a `DelegateAction`/`DelegateActionV2` with an inner action carrying an attached deposit that is designed to fail on the final receiver's shard, and forward it to any relayer willing to pay. The only precondition is that the relayer (or the intermediate forwarding logic) does not explicitly call `promise_set_refund_to`. Since this is documented as the *default* behavior and not universally mitigated at the protocol layer for arbitrary relayer implementations, likelihood is Medium-to-High depending on relayer sophistication.

### Recommendation

For receipts forwarded as a result of unpacking a `DelegateAction`/`DelegateActionV2`, the runtime should default `refund_to` to the original relayer (the outer transaction's `signer_id`) rather than leaving it to fall back to `predecessor_id`, mirroring how gas refunds already correctly route to the original signer. Alternatively, mandate that any code path constructing forwarded receipts from delegate actions explicitly set `refund_to` to the relayer before dispatch, rather than relying on relayer implementations to opt in via `promise_set_refund_to`.

### Proof of Concept

1. Relayer `R` accepts a `SignedDelegateAction` from sender `Alice`, targeting `Alice`'s own account, wrapping an inner `FunctionCall` action to contract `Bob` with a non-trivial attached deposit and gas.
2. `R` submits the outer transaction; gas and the deposit are paid from `R`'s balance.
3. On `Alice`'s shard, the delegate action is unpacked and a new action receipt (with `predecessor_id = Alice`, `receiver_id = Bob`) carrying the attached deposit is forwarded to `Bob`.
4. `Bob`'s contract call is crafted to always fail (e.g., panics or asserts false).
5. The runtime computes `deposit_refund` for the failed receipt and calls `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`, which resolves to `Alice` (the `predecessor_id`), not `R` (the relayer who funded the deposit) — per [2](#0-1)  and [1](#0-0) .
6. `Alice` receives the deposit refund despite never having funded it; `R` bears the loss.

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```

```rust
pub fn promise_set_refund_to(
    ctx: &mut Ctx,
    memory: &mut [u8],
    promise_idx: u64,
    account_id_len: u64,
    account_id_ptr: u64,
) -> Result<()> {
    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(HostError::ProhibitedInView {
            method_name: "promise_set_refund_to".to_string(),
        }
        .into());
    }
    let refund_to = read_and_parse_account_id(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        &ctx.config,
        account_id_ptr,
        account_id_len,
    )?;
    let promise = ctx
        .promises
        .get(promise_idx as usize)
        .ok_or(HostError::InvalidPromiseIndex { promise_idx })?;

    let receipt_idx = match &promise {
        Promise::Receipt(receipt_idx) => Ok(*receipt_idx),
        Promise::NotReceipt(_) => Err(HostError::CannotSetRefundToOnJointPromise),
    }?;

    ctx.ext.set_refund_to(receipt_idx, refund_to);
    Ok(())
```
