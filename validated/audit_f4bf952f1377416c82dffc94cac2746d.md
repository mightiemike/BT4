### Title
Missing window-size clamp in legacy `unDelegateIncrease` re-locks bandwidth/energy quota that should already be available - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
The reported bug class is: when a schedule-controlling variable (release rate / decay window) is recomputed as a weighted average of "remaining locked amount over remaining time" and "returned amount over a fresh full-length time window", without properly accounting for what has already unlocked, the merged value can become distorted so that assets which should already be usable/claimable get locked again for longer than intended. java-tron's bandwidth/energy consumption-decay model uses an analogous mechanism (`windowSize`/usage decay) when resource delegation is cancelled, and the legacy (V1) code path recomputes the owner's decay window without bounding it to the protocol maximum, unlike its V2 counterpart.

### Finding Description
TRON's bandwidth/energy accounting tracks a `usage` value that decays linearly to zero over a `windowSize` (an analog of the "release/claim schedule" in the report). When a delegator calls `UnDelegateResourceContract`/`UnDelegateResourceActuator` to reclaim delegated TRX, part of the receiver's consumed usage is transferred back to the owner via `ResourceProcessor.unDelegateIncrease` [1](#0-0) .

In this legacy path, the owner's own remaining usage is first decayed correctly via `increase(...)`, then merged with the transferred usage from the receiver using a weighted average of `(ownerUsage, remainOwnerWindowSize)` and `(transferUsage, remainReceiverWindowSize)`: [2](#0-1) 

The helper `getNewWindowSize` performs this weighted-average merge with no upper bound applied to the result: [3](#0-2) 

Compare this to the V2 counterpart `unDelegateIncreaseV2`, which performs the same weighted merge but explicitly clamps the result to the maximum protocol window size before storing it: [4](#0-3) 

Because the V1 `unDelegateIncrease` path lacks the `min(newWindowSize, this.windowSize, ...)` clamp present in V2, if the receiver's `remainReceiverWindowSize` is large relative to the owner's `remainOwnerWindowSize` (e.g., the receiver has consumed usage very recently while the owner's usage has almost fully decayed), the resulting `newOwnerWindowSize` can exceed the protocol's normal decay window (`this.windowSize`, i.e., 24h-equivalent in slots). This directly mirrors the reported bug class: a merge/redistribution operation applied on unlock/reclaim that stretches the decay/unlock schedule beyond what it should be, so bandwidth/energy usage that should already have "unlocked" (decayed to zero, freeing quota) remains counted as consumed for an extended period.

`unDelegateIncrease` (legacy) is reached whenever `supportAllowCancelAllUnfreezeV2` is not enabled, from both the classic actuator path and the TVM native-contract path: [5](#0-4) [6](#0-5) 

### Impact Explanation
An extended `windowSize` slows down usage decay for the owner account, meaning the owner's available bandwidth/energy quota that should already be free (because the original usage should have decayed to zero by then) is treated as still consumed for a longer duration than the protocol's designed window. This is a resource-accounting corruption analogous to the report's "tokens which should be claimable are locked again": it produces incorrect (higher-than-should-be) consumption tracking for the owner account, potentially causing legitimate transactions to be rejected for insufficient bandwidth/energy (a localized DoS on that account) or, in edge cases, allowing distorted future usage/window recalculations to persist since `windowSize` state feeds into subsequent `increase()` calls, compounding the miscalculation over time. This can be triggered by any account that both delegates and un-delegates resources - an unprivileged, RPC-reachable transaction flow (`UnDelegateResourceContract`, broadcastable by anyone with a wallet, and TVM `unDelegateResource` opcode reachable by any smart contract).

### Likelihood Explanation
This legacy path is only active when `supportAllowCancelAllUnfreezeV2` (an `AllowCancelAllUnfreezeV2` chain parameter) is not enabled. On networks where this feature has already been activated (e.g., current mainnet), the V2 path with the clamp is used and this specific defect is not reachable. However, on any chain/testnet/private network where this proposal is still disabled, any user performing delegate/undelegate cycles with mismatched decay windows between the two accounts can trigger the unclamped computation. Given it requires no privileged role and only ordinary `DelegateResource`/`UnDelegateResource` transactions, likelihood is moderate wherever the legacy code path is still active.

### Recommendation
Apply the same upper bound used in `unDelegateIncreaseV2` to the legacy `unDelegateIncrease`/`getNewWindowSize` result, i.e., clamp `newOwnerWindowSize` to `this.windowSize` before calling `owner.setNewWindowSize(...)`, ensuring the owner's decay window can never exceed the protocol maximum regardless of the receiver's remaining window size. Additionally, audit other callers of `getNewWindowSize` (the V1 `increase` method) for the same missing bound.

### Proof of Concept
Conceptual reproduction (legacy path, `supportAllowCancelAllUnfreezeV2` disabled):
1. Owner delegates bandwidth to Receiver. Receiver consumes a large amount of bandwidth immediately before Owner calls un-delegate, so `remainReceiverWindowSize` (Receiver's `getWindowSize`) is close to the full window (e.g., ~14400 slots), while Owner's own usage has almost fully decayed, so `remainOwnerWindowSize` is small.
2. Owner calls `UnDelegateResourceContract` to reclaim part of the delegated balance. `UnDelegateResourceActuator.execute` computes `transferUsage` proportional to Receiver's usage and calls `BandwidthProcessor.unDelegateIncrease(ownerCapsule, receiverCapsule, transferUsage, BANDWIDTH, now)` [5](#0-4) .
3. Inside `unDelegateIncrease`, `getNewWindowSize(ownerUsage, remainOwnerWindowSize, transferUsage, remainReceiverWindowSize, newOwnerUsage)` computes a weighted average that, given the disparity in window sizes and usages, can produce a `newOwnerWindowSize` greater than `this.windowSize` [3](#0-2) , and this value is stored unclamped via `owner.setNewWindowSize(resourceCode, newOwnerWindowSize)` [7](#0-6) .
4. On the owner's subsequent transactions, `increase()`/`recovery()` use this oversized `windowSize` to decay usage more slowly than the protocol's designed 24h-equivalent window, effectively keeping bandwidth/energy quota "locked" (counted as used) longer than intended - directly analogous to the reported vesting-unlock disruption.

  public void unDelegateIncrease(AccountCapsule owner, final AccountCapsule receiver,
      long transferUsage, ResourceCode resourceCode, long now) {
    if (dynamicPropertiesStore.supportAllowCancelAllUnfreezeV2()) {
      unDelegateIncreaseV2(owner, receiver, transferUsage, resourceCode, now);
      return;
    }
    long lastOwnerTime = owner.getLastConsumeTime(resourceCode);
    long ownerUsage = owner.getUsage(resourceCode);
    // Update itself first
    ownerUsage = increase(owner, resourceCode, ownerUsage, 0, lastOwnerTime, now);

    long remainOwnerWindowSize = owner.getWindowSize(resourceCode);
    long remainReceiverWindowSize = receiver.getWindowSize(resourceCode);
    remainOwnerWindowSize = remainOwnerWindowSize < 0 ? 0 : remainOwnerWindowSize;
    remainReceiverWindowSize = remainReceiverWindowSize < 0 ? 0 : remainReceiverWindowSize;

    long newOwnerUsage = ownerUsage + transferUsage;
    // mean ownerUsage == 0 and transferUsage == 0
    if (newOwnerUsage == 0) {
      owner.setNewWindowSize(resourceCode, this.windowSize);
      owner.setUsage(resourceCode, 0);
      owner.setLatestTime(resourceCode, now);
      return;
    }
    // calculate new windowSize
    long newOwnerWindowSize = getNewWindowSize(ownerUsage, remainOwnerWindowSize, transferUsage,
        remainReceiverWindowSize, newOwnerUsage);
    owner.setNewWindowSize(resourceCode, newOwnerWindowSize);
    owner.setUsage(resourceCode, newOwnerUsage);
    owner.setLatestTime(resourceCode, now);
  }

  private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,
      long windowSize, long newUsage) {
    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(lastUsage).multiply(BigInteger.valueOf(lastWindowSize))
          .add(BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize)));
      return bi.divide(BigInteger.valueOf(newUsage)).longValueExact();
    }
    return (lastUsage * lastWindowSize + usage * windowSize) / newUsage;
  }
