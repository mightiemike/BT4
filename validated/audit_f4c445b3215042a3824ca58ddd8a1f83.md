### Title
Panic (`.expect()` unwrap) on empty `Calldata` in `l1_handler_message_hash` — potential CHECK-fail DoS via `L1HandlerTransaction` (File: `crates/starknet_api/src/hash.rs`)

### Summary
`l1_handler_message_hash` (used by `L1HandlerTransaction::calc_msg_hash`) unconditionally calls `.expect("Invalid calldata, expected at least from_address")` on `calldata.0.split_first()`. If an `L1HandlerTransaction` is ever constructed/deserialized with empty `calldata`, this call panics the process, analogous to the TensorFlow `IRFFT` `CHECK`-fail DoS pattern (crash on malformed/edge-case input reachable through normal message handling rather than a graceful `Result` error). [1](#0-0) 

### Finding Description
`calc_msg_hash` delegates to `l1_handler_message_hash`, which assumes `calldata` always has at least one element (the `from_address`) and panics via `.expect(...)` otherwise: [2](#0-1) 

The codebase's own maintainers have already recognized that `Calldata` carries no "non-empty" invariant and that `L1HandlerTransaction` derives `Deserialize`, making an empty-calldata instance constructible — this is explicitly called out and defended against in a *sibling* function, `payload_size()`, which was patched to use `saturating_sub` specifically to avoid an underflow/panic on empty calldata, with a dedicated regression test: [3](#0-2) [4](#0-3) 

However, `l1_handler_message_hash` / `calc_msg_hash` in `hash.rs` was **not** given the same defensive treatment and still panics unconditionally on empty calldata via `.expect()`.

In the normal, well-formed flow, `L1HandlerTransaction` is always constructed by prepending the L1 sender address to the payload (e.g., `From<EventData>` in `papyrus_base_layer/src/lib.rs` and `From<MessageFromL1>` in `apollo_rpc/src/v0_8/transaction.rs`), guaranteeing non-empty calldata: [5](#0-4) [6](#0-5) 

The vulnerable call sites are in `apollo_rpc/src/v0_8/api/api_impl.rs` (2 call sites) and `apollo_l1_events/src/l1_events_provider.rs` / `l1_scraper.rs` (1 call site each). I was **not able to fully confirm**, within the available search iterations, whether any of these call sites can be reached with a directly attacker/user-controlled `L1HandlerTransaction`/`Calldata` value that bypasses the "prepend sender" construction path (e.g., a raw/deserialized transaction object accepted from an RPC parameter or a `TransactionHash`-keyed lookup where the calldata field itself, rather than a `MessageFromL1`, is attacker-supplied). Given the `Deserialize` derive on `L1HandlerTransaction`/`Calldata` and the existing "no non-empty invariant" comment in the codebase, such a path is architecturally plausible but not proven with certainty from the code I could inspect.

### Impact Explanation
If reachable with attacker-controlled data (e.g., through an RPC endpoint or state-sync/other deserialization path that ingests transaction objects rather than a safely-constructed `MessageFromL1`), this causes an unrecoverable process panic (crash) in whatever service invokes `calc_msg_hash` — a full node/sequencer service — resulting in denial of service. If limited only to internally-constructed paths (always non-empty due to prepended sender address), the practical severity is much lower, effectively unreachable by an external unprivileged actor.

### Likelihood Explanation
Likelihood is **uncertain**. All identified construction paths that build `L1HandlerTransaction` from external data (`MessageFromL1`, `EventData`) prepend the sender address, guaranteeing non-empty calldata, which would make this unreachable via the standard, sanctioned flows. The vulnerability's reachability by an unprivileged actor hinges on whether any of the 5+ call sites in `apollo_rpc` or `apollo_l1_events` can receive an already-deserialized/raw `L1HandlerTransaction` (bypassing the prepend logic) from an external or lower-trust source — a detail this investigation could not conclusively verify within the available tool budget.

### Recommendation
Regardless of current reachability, harden `l1_handler_message_hash` to mirror the defensive fix already applied to `payload_size()`: replace the `.expect()`-based `split_first()` call with a `Result`-returning check (or treat empty calldata as `from_address = 0`), so the function cannot panic on malformed/empty `Calldata`, consistent with the "never panic on data reachable from requests" coding guideline already documented in this repository.

### Proof of Concept

```rust
// crates/starknet_api/src/hash.rs
use starknet_api::executable_transaction::L1HandlerTransaction as ExecutableL1Handler;
use starknet_api::transaction::L1HandlerTransaction;
use starknet_api::transaction::fields::Calldata;
use std::sync::Arc;

let tx = L1HandlerTransaction {
    version: L1HandlerTransaction::VERSION,
    nonce: Default::default(),
    contract_address: Default::default(),
    entry_point_selector: Default::default(),
    calldata: Calldata(Arc::new(vec![])), // empty calldata — constructible via Deserialize
};

// Panics: "Invalid calldata, expected at least from_address"
let _ = tx.calc_msg_hash();
```
This mirrors the exact scenario the maintainers already guarded against in `payload_size()` (see the regression test `l1_handler_payload_size_empty_calldata_does_not_underflow`), but `calc_msg_hash`/`l1_handler_message_hash` remains unpatched.

```rust
/// Calculating the message hash of L1 -> L2 message.
/// For more info: <https://docs.starknet.io/documentation/architecture_and_concepts/Network_Architecture/messaging-mechanism/#structure_and_hashing_l1-l2>
pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());

    let payload_length_as_felt =
        Felt::from(u64::try_from(payload.len()).expect("usize should fit in u64"));
    encoded.extend(payload_length_as_felt.to_bytes_be());

    for felt in payload {
        encoded.extend(felt.to_bytes_be());
    }

    let mut keccak = Keccak256::default();
    keccak.update(&encoded);
    L1L2MsgHash(keccak.finalize().into())
}
```
