Confirmed: within `x/uexecutor/keeper/`, the outbound-enabled gate (`IsChainOutboundEnabled`) is only checked in `create_outbound.go` (normal outbound creation path). The revert-outbound builder is never gated by it.

### Title
INBOUND_REVERT outbounds are created and queued for signing even when the destination (source) chain has outbound disabled - (File: x/uexecutor/keeper/build_revert_outbound.go)

### Summary
`buildRevertOutbound()` unconditionally creates an `INBOUND_REVERT` `OutboundTx` targeting `inbound.SourceChain` whenever a post-vote inbound execution fails, with no check against `ChainConfig.Enabled.IsOutboundEnabled` for that chain. This is inconsistent with the normal outbound-creation path, `BuildOutboundsFromReceipt`, which explicitly calls `k.uregistryKeeper.IsChainOutboundEnabled` and refuses to create the outbound (returning an error) if outbound is disabled for the destination chain.

### Finding Description
`BuildOutboundsFromReceipt` in [1](#0-0)  enforces the admin-controlled `IsOutboundEnabled` flag before ever constructing a normal outbound.

`buildRevertOutbound` in [2](#0-1)  builds an `INBOUND_REVERT` `OutboundTx` with `DestinationChain: inbound.SourceChain` and immediately attaches it via `attachOutboundsToUtx`/`PendingOutbounds`, with **no equivalent `IsChainOutboundEnabled` check**. It is invoked from every post-vote failure path: [3](#0-2) , [4](#0-3) , and [5](#0-4) . Grep confirms `IsChainOutboundEnabled`/`IsChainInboundEnabled` are referenced only in `create_outbound.go` and `msg_vote_inbound.go` inside `x/uexecutor/keeper/`, never in the revert-build path.

This mirrors the EIP-3156 report's structural bug class: two functions that are supposed to consistently honor the same "operation paused/disabled" flag treat it inconsistently — one path enforces the invariant, the sibling path silently ignores it, producing state that violates the operator's safety control.

Any unprivileged user can trigger this by submitting a source-chain deposit whose Push Chain-side execution deterministically fails post-quorum (e.g. missing/removed token config, zero-amount `GAS` inbound, a failed autoswap on a `GAS`/`GAS_AND_PAYLOAD` inbound, or a failed `FUNDS_AND_PAYLOAD` deposit) — no privileged role or malicious validator/relayer is required; honest Universal Validators simply vote the observed inbound as-is. Once quorum is reached (honest validators, no forged votes), `handleFailedInboundValidation`/`ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload` build and attach the revert outbound unconditionally.

### Impact Explanation
When an admin has disabled outbound for a given chain (typically because that chain's TSS signing path, vault, or gateway is unsafe — e.g. during a TSS key migration, an active incident, or gateway deprecation), the revert path bypasses that control:
- A `PendingOutbounds` entry and a `PENDING` `INBOUND_REVERT` `OutboundTx` are still created and committed to canonical `UniversalTx` state, in direct contradiction to the chain's `IsOutboundEnabled = false` configuration — a corruption of the canonical `UniversalTx`/`PendingOutbounds` invariant that `IsOutboundEnabled` is supposed to protect.
- Because there is no compensating mechanism to re-attempt or expire this specific revert outbound once it is created, and because the on-chain state now claims a refund is `PENDING` when it structurally cannot be authorized to leave via that gate, the user's original inbound funds are represented as "in the process of being refunded" while being effectively unable to progress through the normal, gated path — a state inconsistency that can manifest as **permanent freezing of user funds** from the honest user's perspective (the UTX shows a pending revert that the protocol's own policy prohibits from completing through the intended channel).
- It also creates a consistency violation between two Push Chain subsystems that are both supposed to be driven by `ChainConfig.Enabled.IsOutboundEnabled`: the `uexecutor` outbound-creation logic (correctly gated) and the `uexecutor` revert-outbound logic (ungated), which is exactly the “two sibling functions ignoring a pause flag differently” bug class from the source report.

### Likelihood Explanation
High likelihood of triggering the inconsistent state: any of the many existing failure conditions already exercised by the test suite (missing token config, zero-amount GAS inbound, swap failure, deposit failure) can be induced by an ordinary user crafting a source-chain transaction, combined with an admin disabling outbound for that same chain (a realistic, foreseeable admin action e.g. during a TSS key rotation or gateway incident on that chain). No malicious validator, relayer, or privileged actor is needed to trigger the revert-build code path itself.

### Recommendation
Add the same `k.uregistryKeeper.IsChainOutboundEnabled(ctx, inbound.SourceChain)` check inside `buildRevertOutbound` (or in each call site before invoking it) that `BuildOutboundsFromReceipt` already performs, and define an explicit, on-chain-visible fallback state (e.g. an `ABORTED`/`BLOCKED` status with a clear reason, or a deferred-retry queue) for the case where a revert cannot be issued because the destination chain has outbound disabled, so canonical UTX state never claims a `PENDING` outbound that the registry's own policy forbids from being signed/broadcast.

### Proof of Concept
1. Admin registers chain `eip155:X` with `Enabled.IsInboundEnabled = true`, `Enabled.IsOutboundEnabled = false` (e.g. via `MsgUpdateChainConfig`, or by disabling outbound after a prior enable).
2. A user submits/observes a `GAS` inbound on `eip155:X` with `Amount = 0` (or any condition that fails `ValidateForExecution`/deposit).
3. Honest Universal Validators reach quorum via `MsgVoteInbound` — this succeeds because `IsChainInboundEnabled` passes (see `x/uexecutor/keeper/msg_vote_inbound.go`).
4. Execution fails validation; `handleFailedInboundValidation` (`x/uexecutor/keeper/handle_failed_inbound_validation.go:39-65`) calls `buildRevertOutbound`, which creates an `INBOUND_REVERT` `OutboundTx` with `DestinationChain: "eip155:X"` and attaches/indexes it in `PendingOutbounds`, despite `IsChainOutboundEnabled("eip155:X")` being `false`.
5. Compare with attempting a normal, non-revert outbound to the same chain via a successful inbound with an outbound-triggering payload: `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:49-57`) correctly returns `"outbound is disabled for chain eip155:X"` and creates nothing — demonstrating the asymmetry between the two code paths that are both supposed to honor the same `IsOutboundEnabled` flag.

Note: I could not fully verify within the available context whether the off-chain `universalClient` TSS signing layer (`sessionmanager.verifyOutboundSigningRequest`, which does check `IsChainOutboundEnabled` before signing per `universalClient/tss/sessionmanager/sessionmanager_test.go:483-522`) applies identically to `INBOUND_REVERT`-typed outbounds picked up from `PendingOutbounds`, since that check operates on `OutboundCreatedEvent.DestinationChain` generically. If it does apply, actual fund release may be blocked at the off-chain layer, but the on-chain state corruption (a `PENDING` `OutboundTx`/`PendingOutbounds` entry existing in contradiction to the registry's `IsOutboundEnabled=false` policy, with no path to reconcile or retry) remains a real, reachable invariant violation and is the core of this finding.

func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {
	recipient := inbound.Sender
	if inbound.RevertInstructions != nil && inbound.RevertInstructions.FundRecipient != "" {
		recipient = inbound.RevertInstructions.FundRecipient
	}

	outbound := &types.OutboundTx{
		DestinationChain:  inbound.SourceChain,
		Recipient:         recipient,
		Amount:            inbound.Amount,
		ExternalAssetAddr: inbound.AssetAddr,
		Sender:            inbound.Sender,
		TxType:            types.TxType_INBOUND_REVERT,
		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}
