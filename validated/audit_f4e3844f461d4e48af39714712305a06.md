Confirmed: neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` carry any caller-supplied `expected`/`amountMin` field, and their actuators derive `anotherTokenQuant` purely from the current on-chain pool ratio at execution time, with no bound check against attacker-manipulated ratios.

### Title
Missing slippage/amountMin protection in ExchangeInjectActuator and ExchangeWithdrawActuator enables sandwich extraction of value from TRC10 exchange liquidity operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` (java-tron's Bancor-style TRC10 exchange, analogous to a Uniswap-v2-style AMM pool) let a user inject or withdraw one side of a token pair while the contract computes the paired amount (`anotherTokenQuant`) from the *current* pool ratio at execution time. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in `ExchangeTransactionActuator.doValidate` (`token required must greater than expected`), neither Inject nor Withdraw carries any minimum/maximum bound on `anotherTokenQuant`. This is the same missing-slippage-guard bug class as the reported Hypervisor `pool.mint`/`pool.burn` finding, where amounts are derived from pool state manipulable by a preceding trade in the same block.

### Finding Description
`ExchangeInjectActuator.execute` computes: [1](#0-0) 
using `firstTokenBalance`/`secondTokenBalance` read at execution time, with the only checks in `doValidate` being a positivity check and a global `balanceLimit` cap: [2](#0-1) 

`ExchangeWithdrawActuator.execute` similarly derives `anotherTokenQuant` from the live ratio: [3](#0-2) 
with validation limited to a "precise enough" rounding check, not a caller-specified bound: [4](#0-3) 

By contrast, `ExchangeTransactionActuator` (the "swap" analog) does have exactly the recommended `amountMin`-style parameter, `expected`, validated against the computed `anotherTokenQuant`: [5](#0-4) 

Because any account can broadcast an `ExchangeTransactionContract` trade against the same `exchange_id` before and after a victim's `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction, and TRON's ordering is determined by the block-producing witness (not the sender), an attacker (or a colluding/observing witness) can shift `firstTokenBalance`/`secondTokenBalance` immediately before the victim's inject/withdraw executes, causing the victim to inject/withdraw at a distorted ratio, then trade back afterward to restore the ratio and pocket the difference — a classic sandwich, exactly the bug class described for `Hypervisor.rebalance`/`_mintLiquidity`/`_burnLiquidity` calling `pool.mint`/`pool.burn` without an `amountMin`.

### Impact Explanation
A victim injecting or withdrawing liquidity into/from a TRC10 exchange pair can receive a materially worse `anotherTokenQuant` than expected, with the difference captured by the sandwiching party. This is direct, protocol-level asset/accounting corruption for the victim's counter-token balance — not a merely cosmetic issue — and requires no privileged access, only ordinary broadcast transactions (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`), all reachable via the public `/wallet/exchangeinject`, `/wallet/exchangewithdraw`, `/wallet/exchangetransaction` RPC/HTTP endpoints.

### Likelihood Explanation
Exploitation only requires observing a pending inject/withdraw transaction (e.g., in the mempool or via a cooperating block producer) and broadcasting bracketing trade transactions against the same exchange pair — no special privileges, keys, or node compromise needed. The existing precedent that `ExchangeTransactionActuator` alone received an `expected` slippage-guard field, while Inject/Withdraw did not, indicates this gap was likely unintentional/inconsistent rather than a deliberate design choice.

### Recommendation
Add an `expected`-style minimum (or min/max range) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate`/`execute` and `ExchangeWithdrawActuator.doValidate`/`execute`, mirroring the existing `token required must greater than expected` check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim V targeting `exchange_id=X`, injecting token A quantity `Q_A`, expecting proportional token B back into the pool at ratio `B/A`.
2. Attacker broadcasts `ExchangeTransactionContract` selling a large amount of token A into pool X (via `ExchangeTransactionActuator.execute`, using `ExchangeCapsule.transaction`), driving the `A:B` ratio unfavorably before V's transaction is packed into the same or next block by the witness.
3. V's `ExchangeInjectContract` executes with the skewed ratio, computing a smaller `anotherTokenQuant` (token B credited into pool on V's behalf) than under the pre-attack ratio, since `ExchangeInjectActuator` performs no minimum-output check [1](#0-0) .
4. Attacker broadcasts an offsetting `ExchangeTransactionContract` trade to restore the ratio, extracting the value difference at V's expense.
