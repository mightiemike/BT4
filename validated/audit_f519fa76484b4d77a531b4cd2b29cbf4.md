### Title
Meta-transaction (`DelegateAction`) could withdraw funds from a sender's gas key into their own balance, bypassing the relayer/self-only intent boundary of NEP-366 - (File: `runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/action_validation.rs`)

### Summary
Before `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`, a `WithdrawFromGasKeyAction` could be nested inside a `DelegateAction` (a NEP-366 meta transaction). Because `apply_delegate_action` unwraps the inner actions and executes them against the sender's own account with the sender's `account_id` used as-is [1](#0-0) , and `action_withdraw_from_gas_key` moves balance out of a gas key into the account balance without any extra restriction tied to how the action was submitted [2](#0-1) , a relayer-submitted meta transaction could trigger a fund movement (gas-key balance → spendable account balance) that the protocol later decided must not be permitted through the delegate/relayer path. This mirrors the reported bug class: a "pull/move funds" primitive (`WithdrawFromGasKeyAction`) reachable through an indirect submission path (`DelegateAction`, analogous to the arbitrary `account` parameter in `rebalance()`), where the protocol had not validated that this specific action type was disallowed for that submission path, letting a relayer-mediated transaction move funds in a way not originally intended for meta transactions.

### Finding Description
`WithdrawFromGasKeyAction` moves a specified `amount` from a named gas key's balance into the owning account's spendable balance: `action_withdraw_from_gas_key` decrements `gas_key_info.balance` and credits `account.amount()` by `action.amount` [2](#0-1) . This is a legitimate action normally sent directly by the account owner. However, it could also be embedded as an inner action of a `SignedDelegateAction` (NEP-366 meta transaction), which is unwrapped and re-executed by `apply_delegate_action`, generating a receipt with `receiver_id = delegate_action.receiver_id()` and the inner actions taken verbatim from `delegate_action.get_actions()` [1](#0-0) . The dedicated regression test `test_reject_delegated_gas_key_withdraw_protocol_upgrade` demonstrates that, pre-upgrade, a `DelegateAction` whose `sender_id == receiver_id` and whose single inner action is `WithdrawFromGasKey` is admitted and successfully drains the gas key's balance into the account [3](#0-2) . The fix introduces `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` and a new validation error `ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate`, rejecting this nested-action pattern at transaction admission post-upgrade [4](#0-3) .

### Impact Explanation
Gas keys are meant to be a bounded, sub-account-scoped balance intended primarily for paying gas via relayers/meta-transactions, distinct from the account's main spendable balance. Allowing a `WithdrawFromGasKey` action to be smuggled through the `DelegateAction`/meta-transaction pathway broke the intended boundary that gas-key funds should only move via the account's own directly-signed, non-delegated actions. This blurred the isolation between "funds a relayer is trusted to spend gas from" and "funds the user can freely reallocate," which — depending on how gas keys are provisioned/trusted by relayer infrastructure — could allow value to move in ways the relayer/protocol model did not intend, i.e., an unintended value-movement path enabled through an indirect submission mechanism, directly analogous to the reported bug's "unvalidated destination for a fund-pulling action reachable via an indirect call path." This qualifies as at least Medium severity given it is a concrete, protocol-recognized bypass (evidenced by a dedicated protocol feature and rejection error being shipped to close it) affecting balance/allowance-like accounting reachable from a single submitted transaction.

### Likelihood Explanation
This is directly reachable by any single unprivileged account: any user who has a relayer (or self-acts as relayer) can construct a `SignedDelegateAction` with `sender_id == receiver_id == self` and a nested `WithdrawFromGasKeyAction`, then submit it in a regular transaction — exactly as shown in the test's `delegated_withdraw_tx` helper [5](#0-4) . No validator, node, or peer misbehavior is required — it is a pure single-transaction construction issue, matching this scan's reachability requirements.

### Recommendation
This has already been fixed in the codebase via `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`, which adds a validation check (`ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate`) rejecting `WithdrawFromGasKeyAction` when nested inside `Delegate`/`DelegateV2` actions at the `validate_action_with_mode` stage [6](#0-5) . Confirm this protocol feature is enabled on all networks and that any pre-upgrade in-flight receipts containing this pattern are handled gracefully (as validated by the "tolerate in-flight receipts across the upgrade boundary" portion of the regression test).

### Proof of Concept
1. Create account `alice`, add a gas key (`AddKey` with `AccessKey::gas_key_full_access`), and fund it via `TransferToGasKey` [7](#0-6) .
2. Construct a `DelegateAction` with `sender_id = receiver_id = alice`, whose single inner action is `WithdrawFromGasKeyAction { public_key: gas_key.public_key(), amount: WITHDRAW_AMOUNT }`, signed by alice's regular access key [5](#0-4) .
3. Wrap it in an outer transaction signed/submitted by a `relayer` account and execute it.
4. On protocol versions before `RejectWithdrawFromGasKeyInDelegate`, the transaction succeeds and the gas key's balance is drained into alice's main account balance, confirmed by the balance-before/after assertion in the test [8](#0-7) .

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
