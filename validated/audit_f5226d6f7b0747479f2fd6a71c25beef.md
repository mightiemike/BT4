### Title
Block-scoped index cache in `market.clar` is not invalidated when a vault's accrual pause state changes mid-block, causing stale zToken pricing for the remainder of the block - (File: `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
`market.clar` caches each vault's `(index, lindex)` pair in `index-cache` keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . Because `stacks-block-time` is identical for every transaction inside a block, this cache is effectively **shared across all transactions in the block**, not just within one transaction. The vault's own `accrue` function has a "pass-through without reverting" branch for when accrual is paused: it returns the *unchanged* `index`/`lindex` and explicitly skips updating `last-update` [2](#0-1) . If the first transaction in a block populates the market's cache while the vault is paused (or before a rate-affecting state change is applied), and the vault's real accrual source is later moved (accrual is unpaused, or a separate deposit/repay/system call inside the same block drives a fresh, higher `index`/`lindex`), every subsequent transaction in that same block that resolves a zToken price via `resolve-ztoken` will still read the earlier, now-stale cached value instead of the vault's updated state, because `accrue-and-cache` only re-accrues on a cache **miss**, not when the underlying source has moved [3](#0-2) .

### Finding Description
1. `market.clar` resolves zToken collateral/debt prices through `resolve-callcode` → `resolve-ztoken`, which reads the liquidity index exclusively from the cache via `get-cached-indexes`, never re-querying the vault directly [4](#0-3) .
2. The cache is populated/consulted through `accrue-and-cache`, whose cache key is `{ timestamp: stacks-block-time, aid }` [3](#0-2) . `stacks-block-time` does not change between transactions of the same block, so once any transaction in a block populates the entry for a given `aid`, every later transaction in the same block that calls `accrue-and-cache` for the same `aid` gets a **cache hit** and reuses that same value — it never calls `vault-accrue` again for the rest of the block.
3. The vault's `accrue` function has an explicit bypass for the paused state: `(if (get accrue states) (ok { index: idx, lindex: lidx }) ...)` — i.e., while accrual is paused it *passes through* the stale index/lindex instead of reverting, and also skips the `last-update` write [2](#0-1) .
4. Sequence that produces the stale-use analog within a single block (Clarity transactions execute sequentially within a block, each atomic, but state — including this map — persists across them):
   - Tx A (early in block): `borrow`/`collateral-add`/`liquidate` on `market.clar` calls `accrue-and-cache(USDC)` while `vault-usdc`'s `accrue` is paused (`pause-states.accrue = true`). The vault returns its old `(index, lindex)` pass-through values, which are written into `index-cache` for this block's timestamp.
   - Mid-block: the DAO/admin unpauses accrual (or a direct, market-independent vault call causes real state to change), so the vault's true `index`/`lindex` would now be materially different if freshly computed.
   - Tx B (later in the same block): a different user's `borrow`, `collateral-add`, `collateral-remove`, or `liquidate` call on `market.clar` for a position holding `zUSDC` collateral/debt calls `accrue-and-cache(USDC)` again. Because the map already has an entry for `{timestamp, USDC}` from Tx A, this is a cache **hit** — `resolve-ztoken` uses the stale, paused-era `lindex`, not the vault's now-current value.
5. This is the same bug class as the Stargate report: a value (`dstGasForCall`/here, the vault's liquidity index) is bound once and then used unconditionally by a later step without checking whether the source it was derived from has since moved (unpaused/updated), because the invalidation trigger (`stacks-block-time` change) does not actually correlate with "the vault's true index changed."

### Impact Explanation
Mispriced `zToken` collateral/debt directly affects `is-healthy` checks in `borrow`/`collateral-remove` and the liquidation threshold checks in `liquidate` (`current-ltv`, `ltv-liq-partial` comparisons) [5](#0-4) . Using a stale (lower) lindex undervalues a user's zToken collateral for the remainder of the block, which can push an otherwise-healthy position over the liquidation threshold, or block legitimate borrows/collateral-removals that should be healthy — a temporary, incorrect freezing of a user's ability to act on their own funds within that block window, and potentially an unjust liquidation with real penalty loss for the borrower. This lands in the in-scope **temporary freezing of funds** impact class.

### Likelihood Explanation
Requires two conditions to coincide within one block: (a) the vault's accrual pause flag being toggled or the vault's index otherwise materially changing after the first `accrue-and-cache` call for that asset in the block, and (b) a second market operation for the same asset occurring later in the same block. Pause toggles are DAO-controlled and would typically happen around maintenance windows, and heavy market activity (multiple borrows/liquidations per block) is plausible during volatile periods — exactly when stale pricing is most consequential (e.g., during a liquidation cascade). Likelihood is therefore contingent on specific operational timing (admin pause/unpause combined with sequenced user transactions in the same block) rather than being trivially triggerable by a single attacker alone, but it does not require any privileged compromise beyond a normal DAO pause/unpause operation.

### Recommendation
Do not rely solely on the `stacks-block-time` component of the cache key to determine validity. Either:
- Invalidate/refresh the `index-cache` entry whenever the vault's pause-accrual state or `last-update` timestamp changes (e.g., compare a cached `last-update` snapshot against the vault's `last-update` on every read, not just on a timestamp-based cache miss), or
- Have `accrue-and-cache` always call `vault-accrue` (rather than trusting a same-block cache hit) whenever the previously cached result was produced while `pause-states.accrue` was true, since a pass-through value should never be treated as a stable "already accrued" fact.

### Proof of Concept
1. DAO pauses `vault-usdc` accrual (`pause-states.accrue = true`).
2. Within block N, Tx1: any user calls `market.borrow`/`collateral-add` touching `zUSDC`, which calls `accrue-and-cache(USDC)`. Vault's `accrue` hits the paused pass-through branch and returns the old `(index, lindex)`; market caches `{timestamp: T, aid: USDC} -> (old_index, old_lindex)`.
3. Still within block N, DAO unpauses `vault-usdc` accrual mid-block.
4. Tx2 in the same block N: Borrower B holds `zUSDC` collateral. Liquidator calls `market.liquidate` against B. `liquidate` calls `accrue-user-collateral` → `accrue-and-cache(USDC)` again; since `{T, USDC}` is already present in `index-cache`, the stale `old_lindex` is returned and used by `resolve-ztoken` to price B's `zUSDC` collateral, instead of the vault's now-current (higher, post-unpause) `lindex`.
5. B's collateral is undervalued relative to its true worth, so `current-ltv` computed in `liquidate` is inflated, potentially pushing B past `ltv-liq-partial` and triggering a liquidation (with penalty) that would not have occurred against the correct, current index — a real loss to B for that block's window, caused purely by the cache not tracking the vault's actual state transition.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
