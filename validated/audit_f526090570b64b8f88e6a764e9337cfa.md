## Title
Front-runnable, permanent Account ID squatting via `SetAccountIdContract` enables denial-of-service against legitimate ID claims - (File: `actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java`)

### Summary
`SetAccountIdActuator` lets any account attach a globally-unique, case-insensitive, and **permanent** `accountId` to itself. Uniqueness is enforced only against whatever is already stored in `AccountIdIndexStore` at validation time, with no binding of the claimed id to the claimer's identity beyond "whoever's transaction lands first." Any unprivileged party who observes a pending/broadcast transaction proposing a given `accountId` can broadcast their own `SetAccountIdContract` with the identical id and, if it is included first, permanently deny that id to the original submitter — mirroring the reported `addCandidate`/hash-squatting DoS pattern (Scenario 3: blocking "a new listing... using the same name").

### Finding Description
`validate()` only checks that the target account has no id yet and that the requested id is not already present in `accountIdIndexStore`: [1](#0-0) 

There is nothing tying the `accountId` value to `msg.sender`/`ownerAddress` — it is an arbitrary attacker-chosen byte string, exactly the "predictable/attacker-suppliable identifier" pattern flagged in the report (`addCandidate`'s `hash` parameter). Because Tron transactions are broadcast to the network and sit in the mempool before block inclusion, an attacker (Eve) can observe Alice's `SetAccountIdContract` transaction (or simply guess/pre-empt a popular id) and submit her own transaction with the same `accountId` value.

`AccountIdIndexStore` additionally treats ids as case-insensitive when indexing, widening the collision surface: [2](#0-1) 

Once either party's transaction executes, the id becomes permanently taken (`account.getAccountId()` becomes non-empty for the owner who wins, and the id enters `AccountIdIndexStore` for everyone else), and there is no mechanism to release or reassign an id: [3](#0-2) 

This exactly parallels the reported vulnerability class: like `addCandidate`'s `hash` being claimable by any caller to block a specific listing/parameter-change/challenge, `accountId` claiming is a race any anonymous broadcaster can win to permanently block a specific, otherwise-legitimate claim by another user. The `calcFee()` for this actuator is `0`, so the attack is essentially free (only bandwidth cost) to repeat against many targets: [4](#0-3) 

A related, weaker analog exists in `AssetIssueActuator`, where under the legacy `AllowSameTokenName == 0` mode, token names are globally unique and any broadcaster can squat a name before the intended issuer's transaction is confirmed: [5](#0-4) 
This mode is legacy/deprecated (superseded by ID-based `AssetIssueV2Store`), so its practical impact is limited to networks/testnets still running with `AllowSameTokenName == 0`; the `SetAccountIdContract` path has no such escape hatch and always enforces a single, permanent, global namespace.

### Impact Explanation
A successful front-run permanently denies a specific `accountId` string to its intended owner — there is no retry with the same id, since ids can be set only once per account and are never released. This is a genuine, irreversible denial-of-service against a specific unprivileged user's desired on-chain identity binding, reachable purely through normal transaction broadcast — no special privilege, leaked key, or malicious peer/node behavior required.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to observe the victim's pending `SetAccountIdContract` transaction in the mempool (or otherwise learn the desired id in advance) and race a competing transaction with a higher priority/earlier inclusion. This is straightforward for any network participant running a node and monitoring broadcast transactions, and the near-zero fee (`calcFee() == 0`) makes repeated squatting attempts cheap.

### Recommendation
- Short term: document that `accountId` values are not reserved until confirmed on-chain and are subject to front-running races; advise integrators to avoid relying on `SetAccountIdContract` for time-sensitive or high-value identity bindings without additional coordination (e.g., commit-reveal).
- Long term: bind the claimable id to `ownerAddress` (e.g., require id to incorporate or be signed together with the address, or adopt a commit-reveal scheme) so that a value chosen by one address cannot be trivially "raced" and permanently claimed by an unrelated address, consistent with the report's long-term recommendation to make hash/id generation non-repeatable and tied to `msg.sender`.

### Proof of Concept
1. Alice broadcasts `SetAccountIdContract{ownerAddress: Alice, accountId: "myBrand"}`.
2. Eve, monitoring the mempool/broadcast layer, immediately broadcasts `SetAccountIdContract{ownerAddress: Eve, accountId: "myBrand"}` (or `"MYBRAND"`/`"MyBrand"` given case-insensitive indexing) with sufficient fee/priority to be included first.
3. Eve's transaction executes: `accountIdIndexStore.put(Eve's account)` stores `"myBrand"` as taken (see `SetAccountIdActuator.execute`, lines 45-53).
4. Alice's transaction then fails validation with `"This id has existed"` (`SetAccountIdActuator.validate`, lines 94-96), permanently and irreversibly denying her the `"myBrand"` id, since ids cannot be changed or released once set for any account.

```java
  @Override
  public boolean execute(Object result) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) result;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    final SetAccountIdContract setAccountIdContract;
    final long fee = calcFee();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    AccountIdIndexStore accountIdIndexStore = chainBaseManager.getAccountIdIndexStore();
    try {
      setAccountIdContract = any.unpack(SetAccountIdContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    byte[] ownerAddress = setAccountIdContract.getOwnerAddress().toByteArray();
    AccountCapsule account = accountStore.get(ownerAddress);

    account.setAccountId(setAccountIdContract.getAccountId().toByteArray());
    accountStore.put(ownerAddress, account);
    accountIdIndexStore.put(account);
    ret.setStatus(fee, code.SUCESS);

    return true;
```
