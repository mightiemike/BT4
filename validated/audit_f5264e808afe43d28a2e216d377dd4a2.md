## Finding

### Title
Stale txpool-prewarm snapshot can be consulted for a different parent state, producing wrong account/storage reads during block validation and building - ([File: crates/engine/execution-cache/src/cached_state.rs])

### Summary
The `TxPoolPrewarmCacheSnapshot` mechanism speculatively executes pending pool transactions against a "current" parent and publishes an immutable read cache that block validation and payload building attach to their `CachedStateProvider` via `with_txpool_snapshot`. `CachedStateProvider::basic_account`/`storage`/`bytecode_by_hash` consult this snapshot *unconditionally*, without ever checking that `snapshot.parent_hash()` matches the parent state actually being executed against. This mirrors the UniV3-oracle bug class: a previously-observed value is trusted as still accurate without confirming it is fresh relative to the current reference point.

### Finding Description
The worker in `crates/engine/tree/src/tree/txpool_prewarm/worker.rs` warms a `CachedReads` cache keyed to `cache_parent`, and only republishes a new `Snapshot` when the cache is dirty: [1](#0-0) 

When a newer parent arrives via `Command::Start`, `apply()` swaps `self.job` immediately, but the previously published `Snapshot` (keyed to the *old* parent) remains sitting in the shared `publication` slot until the worker completes another warm batch and calls `publish_snapshot_if_dirty()`: [2](#0-1) 

The test `newest_start_wins` only checks that the *final* published snapshot corresponds to the newest parent, not that intermediate consumers reading the shared slot during the transition window are prevented from seeing the stale snapshot: [3](#0-2) 

On the consuming side, `TxPoolPrewarmCacheSnapshot` stores `parent_hash` but the read path in `CachedStateProvider` never checks it — `basic_account`, `storage`, and `bytecode_by_hash` all check the snapshot as the first, unconditional tier keyed only by address/slot/hash, before falling through to the execution cache or provider: [4](#0-3) 

If block validation or payload building attaches a snapshot that was warmed against a stale/different parent (e.g., due to the race window above, or a reorg where the pool hasn't yet caught up to the new canonical head), the values served by `basic_account`/`storage` would reflect the *wrong* parent's committed state — exactly the "state read that differs from the parent's committed post-state" pattern called out as an accepted equality-break in these rules.

### Impact Explanation
If the stale snapshot is attached during actual block execution (not just prewarming), the account/storage values fed into the EVM diverge from the correct parent's post-state. This can cause:
- The payload builder to build a block with an execution result that does not match a full, correct execution against the real parent, producing a `reth`-built block that other clients (or the same node re-validating) reject — a High-impact divergence.
- If also used during validation (`CacheFillMode::LookupOnly` path with a snapshot attached — see `payload_validator.rs` construction of `CachedStateProvider::new_with_mode(...).with_txpool_snapshot(...)`), a wrong state/receipts root relative to a full recompute — a Critical-impact divergence.

### Likelihood Explanation
This requires no malicious actor: it is a straightforward timing race between the txpool-prewarm worker's asynchronous publication cadence (up to `REFRESH_INTERVAL` = 100ms) and canonical head transitions, which happen naturally and frequently (every block, and especially during reorgs). Given the explicit design comment "This process assumes that payloads are received sequentially" appears elsewhere in the codebase around similar caches, and no equivalent hash-matching guard is visible in the snapshot consumption path, this is a plausible, reachable path rather than a theoretical one — though I was not able to fully trace every call site in `payload_validator.rs`/`mod.rs` in the time available to confirm whether an outer guard (e.g., checking the snapshot's `parent_hash()` before calling `with_txpool_snapshot`) exists elsewhere. This uncertainty should be resolved by checking those call sites directly.

### Recommendation
Before attaching a `TxPoolPrewarmCacheSnapshot` to a `CachedStateProvider` (in `payload_validator.rs` / `mod.rs`), verify `snapshot.parent_hash() == env.parent_hash` (or the parent hash of the block currently being built/validated) and skip the snapshot entirely on mismatch. Additionally, consider having `basic_account`/`storage`/`bytecode_by_hash` in `CachedStateProvider` take the expected parent hash and assert/skip the snapshot tier if it doesn't match, so the safety check is enforced at the point of use rather than solely relying on callers doing it correctly.

### Proof of Concept
Not independently reproduced/executed; based on static analysis of the code paths cited above. A concrete PoC would need to: (1) start the txpool-prewarm worker against parent A, (2) trigger a chain advance to parent B while a snapshot for A is still the last-published one in `publication`, (3) have the engine/payload-processor immediately build/validate a block against parent B while attaching the stale-A snapshot, and (4) show the resulting state/receipts diverge from a full serial re-execution against B. I was unable to verify within the available iterations whether the call sites in `payload_validator.rs`/`mod.rs` already gate on `parent_hash()` before attaching the snapshot — this should be checked directly in the repository to confirm or refute the finding before treating it as confirmed.

    /// Publishes a fresh snapshot if the cache gained reads since the last publication.
    fn publish_snapshot_if_dirty(&mut self) {
        let entries = entry_counts(&self.cache);
        if entries == self.published_entries {
            return
        }

        let parent_hash = self.cache_parent.expect("reads only accumulate after a cache reset");
        *self.publication.write() = Some(Snapshot::new(parent_hash, Arc::new(self.cache.clone())));
        self.published_entries = entries;
        let (accounts, storage, bytecodes) = entries;
        debug!(
            target: "engine::tree::txpool_prewarm",
            ?parent_hash,
            accounts,
            storage,
            bytecodes,
            "published txpool prewarming snapshot"
        );
    }

impl<S: AccountReader> AccountReader for CachedStateProvider<S> {
    fn basic_account(&self, address: &Address) -> ProviderResult<Option<Account>> {
        if let Some(snapshot) = &self.txpool_snapshot {
            if let Some(account) = snapshot.account(address) {
                self.record_txpool_account_hit();
                return Ok(account)
            }
            self.record_txpool_account_miss();
        }

        if self.should_fill_on_miss() {
            match self.caches.get_or_try_insert_account_with(*address, || {
                self.state_provider.basic_account(address)
            })? {
                CachedStatus::NotCached(value) => {
                    self.record_account_miss();
                    Ok(value)
                }
                CachedStatus::Cached(value) => {
                    self.record_account_hit();
                    Ok(value)
                }
            }
        } else if let Some(account) = self.caches.0.account_cache.get(address) {
            self.record_account_hit();
            Ok(account)
        } else {
            self.record_account_miss();
            self.state_provider.basic_account(address)
        }
    }
}

#[inline]
fn nonzero_storage_value(value: StorageValue) -> Option<StorageValue> {
    if value.is_zero() {
        None
    } else {
        Some(value)
    }
}

impl<S: StateProvider> StateProvider for CachedStateProvider<S> {
    fn storage(
        &self,
        account: Address,
        storage_key: StorageKey,
    ) -> ProviderResult<Option<StorageValue>> {
        if let Some(snapshot) = &self.txpool_snapshot {
            if let Some(value) = snapshot.storage(account, storage_key) {
                self.record_txpool_storage_hit();
                return Ok(nonzero_storage_value(value))
            }
            self.record_txpool_storage_miss();
        }

        if self.should_fill_on_miss() {
            match self.caches.get_or_try_insert_storage_with(account, storage_key, || {
                self.state_provider.storage(account, storage_key).map(Option::unwrap_or_default)
            })? {
                CachedStatus::NotCached(value) => {
                    self.record_storage_miss();
                    Ok(nonzero_storage_value(value))
                }
                CachedStatus::Cached(value) => {
                    self.record_storage_hit();
                    Ok(nonzero_storage_value(value))
                }
            }
        } else if let Some(value) = self.caches.0.storage_cache.get(&(account, storage_key)) {
            self.record_storage_hit();
            Ok(nonzero_storage_value(value))
        } else {
            self.record_storage_miss();
            self.state_provider.storage(account, storage_key)
        }
    }
