### Title
`ExchangeInjectContract` lacks a caller-supplied expected/minimum-return field, allowing pool-ratio drift between validation and execution to silently take more of the counter-token than the injector intended - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `protocol/src/main/protos/core/contract/exchange_contract.proto`)

### Summary
`ExchangeTransactionContract` was hardened against exchange-rate drift by adding an `expected` field that the caller sets and that `ExchangeTransactionActuator.doValidate()` checks against the actual computed `anotherTokenQuant` [1](#0-0) , [2](#0-1) . `ExchangeInjectContract`, however, has no such field — only `owner_address`, `exchange_id`, `token_id`, and `quant` [3](#0-2) . This is the same class of bug as the external report: the code assumes the exchange ratio at execution time will match what the caller expected, with no way for the caller to bound the actual counter-token amount pulled from their balance.

### Finding Description
`ExchangeInjectActuator.doValidate()` computes the counterpart token amount (`anotherTokenQuant`) using the pool's `firstTokenBalance`/`secondTokenBalance` read at validation time [4](#0-3) . `execute()` re-reads the pool balances independently and recomputes `anotherTokenQuant` from whatever the balances are *at execution time* [5](#0-4) . Because validation and execution happen at different points (validation occurs when the transaction is accepted into the tx pool/block being built; execution occurs later, after other transactions — including `ExchangeTransaction`, `ExchangeInject`, and `ExchangeWithdraw` on the same pool — may have already executed and moved `firstTokenBalance`/`secondTokenBalance`), the ratio used at `execute()` time can differ materially from what was used at `doValidate()` time or from what the user observed when constructing the transaction.

Unlike `ExchangeTransactionActuator`, which lets the caller specify `expected` and rejects the transaction if the computed output falls short [2](#0-1) , `ExchangeInjectActuator` has no caller-controlled bound at all: it always injects the exact `quant` of `token_id` the caller specified, then computes and pulls whatever `anotherTokenQuant` the constant-ratio formula (`bigSecondTokenBalance * bigTokenQuant / bigFirstTokenBalance`, or the mirrored calculation) dictates from the *current* pool state [6](#0-5) , [7](#0-6) . This mirrors the report's core issue: an assumed/expected exchange rate is baked into a transaction without any mechanism for the actor to cap their exposure to rate movement between intent and settlement. Just as `WstEth.withdraw()` computed `minOut` from a stale peg assumption instead of a user-supplied bound, `ExchangeInjectActuator` computes and pulls a counter-token amount from a live, moving ratio with zero user-supplied bound.

The bug is reachable purely through the public `/wallet/exchangeinject` RPC/HTTP path and ordinary broadcast transactions — no privileged role or compromised key is required; any account that is the "creator" of an exchange pool can be affected by other unprivileged parties' `ExchangeTransactionContract`/`ExchangeWithdrawContract` calls against the same pool shifting the ratio before the inject is applied [8](#0-7) .

### Impact Explanation
An exchange-pool creator who submits `ExchangeInjectContract` intending to inject `quant` of `token_id` at an observed ratio can end up having a different (larger or smaller) amount of the counterpart token pulled from their account balance than intended, because the ratio is recomputed at execution time from whatever state the pool is in after preceding transactions in the block executed. In a single block, an attacker (unprivileged, using ordinary `ExchangeTransactionContract`/`ExchangeWithdrawContract` calls) can shift the pool ratio just before the victim's `ExchangeInjectContract` executes, causing the victim to inject an unfavorable ratio and lose value relative to the true market rate, or fail balance/limit checks unexpectedly. This is an accounting/value-extraction risk on the exchange (bancor-style AMM) actuators rather than a node-crashing bug.

### Likelihood Explanation
Moderate. It requires an attacker to have visibility into pending `ExchangeInjectContract` transactions (e.g., via the P2P network / mempool) and to be able to get their own `ExchangeTransactionContract`/`ExchangeWithdrawContract` ordered before the victim's inject within the same block — a standard front-running/sandwich pattern achievable by any unprivileged network participant, similar to the MEV/sandwich risk explicitly called out as a consequence in the original report.

### Recommendation
Add a caller-specified bound to `ExchangeInjectContract` (e.g., a maximum acceptable `anotherTokenQuant`, or a minimum/maximum ratio tolerance), analogous to the `expected` field already present on `ExchangeTransactionContract`, and enforce it in both `ExchangeInjectActuator.doValidate()` and `execute()` so that pool-ratio drift between transaction construction and execution causes the transaction to fail rather than silently execute at an unexpected rate.

### Proof of Concept
Not independently reproduced against a running node in this analysis; the conclusion is based on static code comparison between `ExchangeTransactionActuator` (which has an `expected`/slippage guard) and `ExchangeInjectActuator` (which has none) and the proto definitions confirming the missing field [9](#0-8) . A full end-to-end PoC (two transactions in the same block: an `ExchangeTransactionContract` that shifts the ratio, followed by the victim's `ExchangeInjectContract`) would require running the actual block-production/actuator pipeline, which is outside the scope of this static analysis.
