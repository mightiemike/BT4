### Title
`ensure_match_transaction_info` omits state/position checkpoint hash validation, allowing undetected state-root divergence during chunk replay and verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the canonical function used by state-sync chunk execution, `db-tool replay-verify`, and the debugger to confirm that a locally re-executed `TransactionOutput` matches an authenticated `TransactionInfo` (obtained via accumulator proof against a `LedgerInfo`). The function checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually authenticate the resulting state/position Merkle roots.

### Finding Description
Looking at `types/src/transaction/mod.rs:2139-2204`: [1](#0-0) 
the code comment states verbatim that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

This function is invoked as the sole per-transaction correctness gate in three important integrity-critical paths:
1. Chunk executor's `verify_execution`, used during backup/state-sync-v2 replay verification: [2](#0-1) 
2. `db-tool`'s `replay_on_archive`, whose entire purpose is to replay history and confirm it matches the authenticated chain: [3](#0-2) 
3. `aptos-debugger`'s mismatch printer: [4](#0-3) 

In each case, `ensure_match_transaction_info` is treated as if it fully validates that local execution reproduced the authenticated ledger state, but it structurally cannot detect a state root (or, if native position is enabled, position-tree root) divergence, since those root hashes are the very fields skipped.

Contrast this with the DB-level acceptance path for `TransactionInfo`/write-set consistency, `assert_committed_write_set_version` in `execution/executor/tests/db_bootstrapper_test.rs:196-217`, and with `TransactionOutputListWithProof::verify` in `types/src/transaction/mod.rs:2940-3022`, both of which do check `state_change_hash` (write-set hash) but likewise never check `state_checkpoint_hash` against a recomputed state Merkle root inside these particular verify paths — the root of trust for state-checkpoint-hash correctness is `DoLedgerUpdate::assemble_transaction_infos` at execution time (`execution/executor/src/workflow/do_ledger_update.rs:82,100-109`), not any of the replay/backup verifiers.

### Impact Explanation
If the state/position checkpoint-hash computation logic (e.g., Jellyfish Merkle tree, hot-state or native-position summary construction) ever diverges from the authenticated ledger's checkpoint hash — whether from a bug, a non-deterministic path, or a malicious archive/backup source substituting a different (still self-consistent) state root, — `ensure_match_transaction_info` will report success as long as write-set bytes, events, gas, and status match. Consumers relying on this check (replay-verify tooling, chunk-executor-driven state sync v2, and the debugger) would falsely certify a chain of blocks as correctly replayed even though the actual Merkle state root committed differs from ground truth. This directly matches the "Committed state that differs from the correct VM result" and "Authenticated API or state-view output bound to the wrong version/root" impact classes, since operators use replay-verify as an authoritative integrity check before trusting a backup/restore or an alternate execution path.

### Likelihood Explanation
This is not a hypothetical edge case — the code comment itself documents the gap and names `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, an on-chain feature that is presumably intended to be validated by this exact path once enabled. The check is unprivileged (any consumer of the chunk-executor/replay-verify/debugger code paths hits it) and requires no attacker action to be silent — it is a systemic blind spot in the state-root/position-root proof chain for these tools, not conditioned on adversarial input.

### Recommendation
Extend `ensure_match_transaction_info` to accept and validate `state_checkpoint_hash` (and, where enabled, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against locally recomputed roots before flagging `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/native-position features as verified, matching the same rigor already applied to write-set and event-root hashes.

### Proof of Concept
Not directly exploitable as a standalone PoC without executing state-sync/backup infrastructure; the defect is demonstrable by inspection: construct a `TransactionOutput` whose `write_set()`, `events()`, `gas_used()`, and `status()` match a given `TransactionInfo`, but whose actual resulting state Merkle root (as would be computed by `DoStateCheckpoint`) differs from `txn_info.state_checkpoint_hash()`. Calling `ensure_match_transaction_info(version, txn_info, ...)` returns `Ok(())` despite the state root mismatch, because `state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` are never read in the function body (`types/src/transaction/mod.rs:2139-2204`).
