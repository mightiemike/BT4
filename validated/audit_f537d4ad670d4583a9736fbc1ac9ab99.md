### Title
`DeleteAccountAction` with a non-existent/non-existable `beneficiary_id` permanently burns the deleted account's remaining balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
In `action_delete_account`, the deleted account's remaining `amount` is sent as a `Receipt::new_balance_refund` to the caller-supplied `beneficiary_id`, and the account is removed unconditionally in the same step. There is no check that `beneficiary_id` refers to an existing (or creatable) account before the deletion is committed. If the balance-refund receipt subsequently fails because the beneficiary does not exist, the protocol's own refund-failure rule burns the tokens instead of returning them — an outcome directly analogous to `TokenLock.revoke()` destroying the contract before paying out `releasableAmount() + surplusAmount()`, permanently losing funds that were never meant to be forfeited.

### Finding Description
`action_delete_account` computes the payout unconditionally from the current balance and queues a refund receipt, then deletes the account in the same call: [1](#0-0) 

Validation of the action only checks that `beneficiary_id` is a syntactically valid account id (per `docs/RuntimeSpec/Actions.md`), not that the account actually exists: [2](#0-1) 

A `Receipt::new_balance_refund` is a system-refund receipt (`predecessor_id == "system"`): [3](#0-2) 

Refund receipts can never implicitly create the destination account, for any account type, including named accounts (which additionally can *never* be implicitly created by a `Transfer` regardless of refund status): [4](#0-3) [5](#0-4) 

This is confirmed by a dedicated regression test showing a refund to a non-existent account fails with `AccountDoesNotExist` and the account is never created: [6](#0-5) 

Per the protocol's documented refund semantics, when a refund receipt's execution fails, the refund amount is burnt rather than retried or returned: [7](#0-6) 

Because `action_delete_account` has already deleted the source account by the time this refund receipt executes (and fails), the original account balance is gone, the refund is rejected, and the tokens are burnt — an irreversible loss of funds triggered entirely by a single, unprivileged `DeleteAccount` transaction.

### Impact Explanation
Any account owner (or any access key permitted to submit a `DeleteAccount` action) can trigger permanent, protocol-level destruction of that account's entire remaining NEAR balance by specifying a `beneficiary_id` that is syntactically valid but does not exist (a mistyped/never-created named account, or any account of a type that a refund receipt cannot implicitly create). Unlike an ordinary failed `Transfer`, which simply leaves the sender's balance untouched, `DeleteAccountAction` unconditionally removes the source account first and then attempts payout via a system refund, so a failed payout cannot be reversed by re-crediting the (now nonexistent) source account — the funds are burnt. This matches the "permanently frozen/lost funds" outcome class: real value is destroyed as a direct, deterministic consequence of a single submitted transaction, with no attacker collusion or privileged access required.

### Likelihood Explanation
High likelihood of occurrence through simple user error (typo in `beneficiary_id`, or supplying an account that was since deleted/never created), and it is trivially reproducible by any signer who wants to delete their account. No special privileges, timing, or protocol version gating are required — the code path is exercised on every `DeleteAccount` action and is explicitly covered by the existing `refund_may_not_create_universal_account` test, which already demonstrates the failure mode (it stops short of tying it to the `DeleteAccount` deletion-then-burn sequence).

### Recommendation
Before committing account deletion, validate that `beneficiary_id` refers to an account capable of receiving the refund (i.e., either an existing account, or an account type/shape for which the resulting transfer receipt is guaranteed to succeed). Alternatively, defer removal of the source account's balance/state until the beneficiary refund receipt is confirmed to succeed, or fall back to refunding the original account (undoing the deletion) instead of burning the funds when the beneficiary refund fails.

### Proof of Concept
1. Create account `alice.near` with balance `X`.
2. Submit a transaction from `alice.near` containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "ghost-account-that-was-never-created.near" })`.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:380-387`) queues `Receipt::new_balance_refund(&"ghost-account...", X)` and deletes `alice.near` in the same step.
4. The refund receipt executes with `predecessor_id == "system"`; because the beneficiary is a named account that does not exist, `check_account_existence`/`implicit_creation_allowed` reject it with `AccountDoesNotExist` (as shown by `refund_may_not_create_universal_account`, `runtime/runtime/src/tests/apply.rs:6880-6926`, which demonstrates the identical failure for a refund receipt).
5. Per `docs/RuntimeSpec/Refunds.md:10-12`, the failed refund amount `X` is burnt — `alice.near`'s tokens are permanently and irreversibly lost.

    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    receipt_shape: ReceiptShape,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            }

                    account_id: account_id.clone(),

                .into());

            if account.is_none() && !implicit_creation_allowed(account_type, receipt_shape) {
                return Err(ActionErrorKind::AccountDoesNotExist {
                    account_id: account_id.clone(),

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
