### Title
Unbounded, non-deduplicated growth of the per-shop session-ID index in `KVSessionStorage` can brick token-exchange authentication for a shop - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
The Hats finding describes an unbounded `activePaymentReceivers`-style array that is appended to on every payment event but never pruned/deduplicated, eventually growing large enough to make the processor unusable. The same bug class exists in `KVSessionStorage.addShopIds()`: every call to `storeSession()` unconditionally appends the session id to the shop's index array with no de-duplication and no bound, unlike the Redis implementation which explicitly checks membership before pushing.

### Finding Description
`KVSessionStorage.storeSession()` writes the session, then calls the private helper `addShopIds`, which reads the current `shop:${shop}` index array and blindly concatenates the new id(s) onto it before writing it back: [1](#0-0) 

Unlike `RedisSessionStorage.addKeyToShopList`, which checks `if (!idKeysArray.includes(idKey))` before pushing: [2](#0-1) 

the KV variant has no such guard, so calling `storeSession` repeatedly with the *same* session id (offline sessions always use the deterministic id `offline_${shop}`; online sessions use `${shop}_${userId}`) keeps growing the `shop:${shop}` array with duplicate entries indefinitely.

`storeSession` is invoked from the token-exchange authentication handlers on the reachable path whenever a stored session is missing or inactive: [3](#0-2) 

This path also runs after any `401` from the Admin API, which explicitly invalidates and re-stores the session (again under the same deterministic id): [4](#0-3) [5](#0-4) 

The same `storeSession` sequence exists in the remix and react-router token-exchange strategies: [6](#0-5) [7](#0-6) 

A merchant (an unprivileged, single-tenant actor relative to the platform) fully controls when their own offline/online session becomes invalid — e.g., by revoking API access/scopes for the app, or by simply waiting out expiry when `expiringOfflineAccessTokens`/online tokens are used — and can therefore repeatedly drive requests through the "no valid session" branch. Each pass appends another duplicate entry to the shop's KV index array, which is never deduplicated or capped.

`findSessionsByShop` (used by installation checks, uninstall webhook cleanup, and `ensureValidOfflineSession`) then has to fetch and parse this ever-growing array and `loadSession` every id in it: [8](#0-7) 

### Impact Explanation
Cloudflare Workers KV enforces hard per-value size limits (and per-key write-rate limits). Once the JSON-serialized `shop:${shop}` array approaches that limit, `namespace.put()` in `addShopIds` will fail, causing the `await config.sessionStorage.storeSession(...)` call inside the auth handler to throw. Because that call sits directly in the critical path of `performTokenExchange`/the remix and react-router `authenticate()` strategies, the exception propagates out of the try/catch as an "Unexpected error during token exchange", returning a `500` to the merchant for every future authenticated request. This is a self-inflicted but concrete Denial of Service of the app's authentication handler for that specific shop — matching the reachable analog class explicitly accepted by the rules ("DoS of an auth handler"). Even before hitting the hard size limit, every token-exchange request becomes slower and more expensive as it must load and parse a linearly growing array and issue a `loadSession` GET per (duplicate) id in `findSessionsByShop`.

### Likelihood Explanation
Reaching the vulnerable code only requires being a legitimate merchant using an embedded app with `KVSessionStorage` configured, forcing their own offline/online session to be treated as inactive repeatedly (via scope/token revocation or waiting for natural expiry with `expiringOfflineAccessTokens`). No cross-tenant or platform-privileged access is required, and the missing dedup check is a straightforward, deterministic root cause in `addShopIds`. The growth rate is bounded only by how frequently the app is re-authenticated, which an attacker fully controls for their own shop, making this readily triggerable, though the KV size limit means substantial repeated triggering is needed before the handler actually breaks.

### Recommendation
In `KVSessionStorage.addShopIds`, deduplicate before writing back (mirroring the Redis implementation's `includes` check), e.g. `const merged = Array.from(new Set([...shopIds, ...ids]))`. Additionally consider capping the index size or storing it as a KV list/secondary index keyed by session id prefix rather than a single growing JSON array, so a single shop's session churn cannot degrade or break `storeSession`/`findSessionsByShop` for that shop.

### Proof of Concept
1. Configure an embedded app with `KVSessionStorage` and `future.expiringOfflineAccessTokens: true` (or `useOnlineTokens: true`).
2. As the installing merchant, repeatedly cause the stored offline (or online) session to become invalid — either by waiting for token expiry, or by revoking the app's access programmatically and issuing an authenticated request so the Admin API returns `401`, which triggers `invalidateAccessToken` → `storeSession`.
3. Each cycle re-enters `performTokenExchange`'s "No valid session found" branch (`packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts:91-116`), calling `storeSession(offlineSession)` with the same deterministic id `offline_${shop}`.
4. Observe that `KVSessionStorage.addShopIds` (`packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts:75-79`) appends a new duplicate entry to the `shop:${shop}` KV value on every cycle, with no cap or dedup.
5. After sufficient repetitions, the KV value size limit is reached; `namespace.put` in `addShopIds` throws, `storeSession` throws, and `performTokenExchange` returns `500 Internal Server Error` for all subsequent authentication attempts for that shop, bricking the app's auth handler.

    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }

import {Session} from '@shopify/shopify-api';

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}
