### Title
Backup restore commits transactions without verifying `WriteSet` matches `TransactionInfo.state_change_hash` - ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
During transaction-backup restore (the non-replay "save before replay" fast path), `LoadedChunk::load` reads `(txn, aux_info, txn_info, events, write_set)` tuples from an untrusted backup file and verifies only `txns`, `events`, and `txn_infos` against the ledger accumulator via `TransactionListWithProofV2::verify` [1](#0-0) . The `write_sets` vector is parsed from the same file but is never included in, or checked against, that proof, and it is never hashed and compared to `transaction_info.state_change_hash()` before being persisted via `restore_handler.save_transactions(...)` [2](#0-1) .

### Finding Description
`TransactionInfo` commits to the write set only indirectly through `state_change_hash`, a field that is itself covered by the accumulator proof (since `TransactionInfo` is hashed as a whole into the accumulator leaf) [3](#0-2) . However, nothing in the restore/save path recomputes the hash of the loaded `write_set` and compares it to `transaction_info.state_change_hash()`. `save_transactions` in `restore_utils.rs` writes `write_sets` directly into `WriteSetDb` and, when `kv_replay` is enabled, feeds them into `state_store.calculate_state_and_put_updates` to derive the new `LedgerState`, with no cross-check against the accompanying `TransactionInfo` [4](#0-3) . Because a backup file is loaded via `storage.open_for_read` and deserialized directly from bytes with no signature over the write-set field itself, a backup source that can supply an internally-consistent `(txn, txn_info, events)` triple (which is all the accumulator proof binds) together with an arbitrary `write_set` can cause the restoring node to persist a `WriteSet` for that version that never matches what `state_change_hash` attests to, and that differs from the actual VM-computed result for that transaction.

### Impact Explanation
If accepted, this would let a node operator restoring from an untrusted/compromised backup source silently ingest an incorrect ledger state at a given version — durable data diverging from the correct VM result — which is exactly the "committed state differs from the correct VM result" class called out in the state-integrity gate.

### Likelihood Explanation
I was not able to fully verify, within the remaining budget, whether the trust boundary here is actually "unprivileged": backup files are typically fetched from a `BackupStorage` configured by the node operator (their own S3/GCS bucket or similar), so the realistic threat requires an attacker to control or tamper with that storage or the transport to it. I could not confirm in this pass whether there is an additional integrity check (e.g., a wrapping signature over the whole backup blob, or a later replay-verification step in `VerifyExecutionMode`) that would catch this before commit becomes durable and externally observable. Because of this unresolved trust-boundary question, I cannot assert this meets the "unprivileged root cause" bar with confidence.

### Recommendation
Recompute and check `CryptoHash::hash(&write_set) `-derived contribution against `transaction_info.state_change_hash()` (or otherwise verify the write set is consistent with the accumulator-proven `TransactionInfo`) before calling `save_transactions`/`calculate_state_and_put_updates` in the non-replay restore path, mirroring the checks already implicitly required for `events`/`event_root_hash`.

### Proof of Concept
Not constructed — I was unable to confirm within budget whether write-set/`state_change_hash` binding is actually absent end-to-end (e.g., possibly enforced later during `VerifyExecutionMode::Verify` replay) or whether the backup-storage threat model is in scope as "unprivileged." Given this unresolved uncertainty, I present this as a candidate requiring further investigation rather than a confirmed, standalone high/critical finding.

/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
