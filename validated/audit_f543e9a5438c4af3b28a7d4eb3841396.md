### Title
Account resources JSON conversion binds to latest state view instead of the requested historical `ledger_version` - (File: `api/src/accounts.rs`)

### Summary
`Account::resources` fetches raw BCS resource bytes at `self.ledger_version` (which can be any historical, unpruned version supplied by the caller), but for the JSON accept-type path it builds the `MoveConverter`'s underlying state view from `self.context.latest_state_view_poem(&self.latest_ledger_info)` rather than from `self.ledger_version`. This is inconsistent with the sibling helper `find_resource` in the same file, which correctly requests a version-pinned view via `self.context.state_view(Some(self.ledger_version))`. ### Finding Description
`Account::resources` retrieves the raw resource bytes at the caller-supplied `self.ledger_version` via `get_resources_by_pagination(..., self.ledger_version, ...)`, but constructs the JSON-path `state_view` from `latest_state_view_poem(&self.latest_ledger_info)`, which is pinned to the current latest committed version, not `self.ledger_version`: [3](#0-2) 

The resulting `state_view` is then passed into `converter.try_into_resources(...)`, which uses `MoveConverter`'s internal `AptosValueAnnotator` (constructed over that same `state_view`) to resolve module ABIs/struct layouts and any auxiliary lookups (e.g., table handle -> type info, resource-group member types) needed to turn the raw BCS bytes into JSON `MoveResource` values: [4](#0-3) 

Contrast this with `find_resource` in the same file, which explicitly asks for a version-scoped view: [2](#0-1) 

Because the annotator's type/layout resolution machinery is driven off whatever `StateView` it is given, and here that view reflects the *latest* chain state rather than the state at `self.ledger_version`, any type-resolution-dependent behavior that differs between the requested historical version and the latest version (module resolution for the resource's own struct, table type mappings for embedded `Table<K,V>` handles, or resource-group member composition) is resolved against the wrong version. The raw bytes are correctly historical, but the "lens" used to interpret them into JSON is not.

### Impact Explanation
This falls under "Authenticated API or state-view output bound to the wrong version, object, or proof context." The JSON representation returned to the client for a historical `ledger_version` query is decorated with `latest_ledger_info` (correct, since headers reflect the query-time latest ledger info) but the *content* is produced using type-resolution state from the latest version instead of the version the resource bytes actually belong to. For resources whose interpretation depends on chain state at the time (e.g., decoding table handles into typed key/value JSON, or resolving object/resource-group membership), this can yield JSON fields that do not correspond to the exact same versioned state as the raw BCS resource — i.e., a client cannot trust that the JSON output for `ledger_version=V` reflects only state as-of `V`. This does not corrupt BCS accept-type responses (those return raw bytes/BTreeMap unaffected), and it does not corrupt committed ledger state, accumulator roots, or proof material — the mismatch is confined to auxiliary type-resolution used by the JSON `MoveResource` converter for the account resources endpoint.

### Likelihood Explanation
Triggering an observable divergence requires the type/table-resolution context looked up via `state_view` to actually differ between `self.ledger_version` and the latest version, e.g., a table created/destroyed/recreated with a different key/value type mapping, or resource-group membership changes, between those two versions. Aptos' module-upgrade compatibility checker restricts arbitrary struct-layout changes for existing on-chain resource types, which limits (but does not eliminate) this class of divergence for plain resources; auxiliary lookups such as `TableInfo` are not subject to the same compatibility guarantees and are more directly at risk. I could not fully confirm the exact behavior of `latest_state_view_poem` vs. `state_view` in `api/src/context.rs` (file read was inconclusive in this session), so the precise scope of what differs between the two views should be verified directly against that file.

### Recommendation
In `Account::resources` (JSON branch), build the state view from `self.ledger_version` (consistent with `find_resource`'s use of `self.context.state_view(Some(self.ledger_version))`) instead of `self.context.latest_state_view_poem(&self.latest_ledger_info)`, so that the `MoveConverter` used by `try_into_resources` performs all type/table resolution against the same version the raw resource bytes were fetched from.

### Proof of Concept
1. Publish/observe an account/table whose table-handle-to-type mapping changes between an older version `V` and the current latest version `L` (e.g., a table destroyed and its handle-adjacent metadata changed, or a resource-group's member set changes across versions).
2. Call `GET /accounts/:address/resources?ledger_version=V` with `Accept: application/json`.
3. Compare the returned JSON `MoveResource` fields (which depend on type resolution done against `latest_state_view_poem`) against a manual conversion pinned strictly to version `V`'s state.
4. Observe divergence in decoded fields (e.g., table entry key/value typing) that would not occur if the state view had been correctly pinned to `V`, confirming the code path in `api/src/accounts.rs:474-490` uses the wrong version for JSON conversion. [5](#0-4)
