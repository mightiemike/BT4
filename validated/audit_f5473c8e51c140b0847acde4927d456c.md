### Title
Replay-verify tool accepts a diverged state root because `ensure_match_transaction_info` never checks `state_checkpoint_hash` - (File: `types/src/transaction/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`)

### Summary
The `db-tool replay-on-archive` command re-executes archived transactions and validates the results solely via `TransactionOutput::ensure_match_transaction_info`. This function checks status, gas used, write-set hash, and event root hash, but explicitly skips the `state_checkpoint_hash` (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`), which are the authenticated Sparse-Merkle/JMT roots committed into the ledger's transaction accumulator. As a result, a state-root divergence between local execution and the archived, signature-backed ledger is never detected by this tool.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  compares only:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed event root vs `txn_info.event_root_hash()`

It never compares `txn_info.state_checkpoint_hash()` (or the hot-state/position variants) against a recomputed state root. The function's own comment documents this gap: [2](#0-1) 

This is the exact verification function used by the mainnet replay-verify tool, `storage/db-tool/src/replay_on_archive.rs`, whose `execute_and_verify` loop calls it as the sole pass/fail criterion after re-executing a chunk of archived transactions: [3](#0-2) 

`state_checkpoint_hash` is a field of `TransactionInfo` [4](#0-3) , and `TransactionInfo`'s hash is what is committed into the transaction accumulator whose root is authenticated by the `LedgerInfo` signature (see the accumulator/proof verification chain in [5](#0-4) ). It is therefore part of the *authenticated* ledger state, not an incidental value. A grep of the entire `replay_on_archive.rs` file confirms no other code path in that tool ever calls `get_root_hash`, compares `state_checkpoint_hash`, or otherwise re-derives/validates the Merkle state root — `ensure_match_transaction_info` is the only gate.

### Impact Explanation
If local execution (or the Move VM/native environment on the machine running the tool) produces a divergent state tree — e.g. due to a non-determinism bug in state-checkpoint/JMT construction, a storage-schema bug, or a corrupted/malicious archive that swaps in an incorrect but internally-consistent write set/state root pairing at the leaf level — `replay-on-archive` will report the replay as fully successful as long as status, gas, write-set hash and event root all happen to match. Any wrong `state_checkpoint_hash` slips through undetected. This directly satisfies the "Wrong ... transaction proof ... accepted as valid" and "Hard-fork-only divergence during commit, replay, restore, or proof verification" state-integrity impact categories: the tool exists specifically to catch consensus/state divergence across node versions or hard forks, and this is precisely the class of bug (silent state-root divergence) it is meant to catch but cannot.

### Likelihood Explanation
This is not a hypothetical: it's a documented, code-provable gap in the one function relied upon by an operational security tool. It requires no privileged actor or malicious peer — it's a correctness gap in an unprivileged verification utility used by node operators/auditors to detect divergence. The TODO explicitly ties enabling this fix to `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, implying the position-state-root piece is future work, but the core issue — that `state_checkpoint_hash` and `hot_state_checkpoint_hash` (both already live, non-experimental fields used in normal Aptos block production per `do_state_checkpoint.rs`) are unchecked — exists today, independent of that upcoming feature.

### Recommendation
Extend `ensure_match_transaction_info` to accept and validate the recomputed state (and hot-state) checkpoint hash(es) whenever the transaction is a checkpoint boundary, comparing against `txn_info.state_checkpoint_hash()` / `txn_info.hot_state_checkpoint_hash()`, and wire this through `replay_on_archive.rs`'s `execute_and_verify` (which already runs `DoStateCheckpoint`-adjacent machinery via the block executor) so that a state-root mismatch causes the replay to fail rather than silently pass.

### Proof of Concept
Not independently reproducible as a runtime exploit without executing the full replay pipeline against a crafted archive; the finding is a static code-path proof: (1) `TransactionInfo` carries `state_checkpoint_hash` as an authenticated field [4](#0-3) ; (2) `ensure_match_transaction_info` never reads or compares it [1](#0-0) ; (3) `replay_on_archive.rs`'s `execute_and_verify` uses only this function as its correctness oracle and contains no independent state-root check [6](#0-5) . Therefore any execution divergence confined to the state tree (while write-set bytes, events, gas, and status remain identical) is provably undetectable by this tool.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
