### Title
Slot leak in `ParallelExecutor.ExecuteTask` on shutdown race causes permanent capability-execution DoS - ([File: core/capabilities/remote/parallel_executor.go])

### Summary
`ExecuteTask` acquires a `taskSemaphore` slot via `case t.taskSemaphore <- struct{}{}` before checking whether the executor is stopped. If `t.IfNotStopped(...)` returns `false` (executor already stopped/stopping), the closure containing `t.wg.Go(...)` and its deferred `<-t.taskSemaphore` release is never executed, so the previously acquired slot is never released. This is an exception-unsafe (non-RAII) acquire/release pattern that permanently exhausts the semaphore.

### Finding Description
In `ExecuteTask` [1](#0-0) , the slot is acquired unconditionally at line 69 (`case t.taskSemaphore <- struct{}{}`), and only *after* acquiring it does the code call `t.IfNotStopped(func() { t.wg.Go(...) })`. The release logic (`<-t.taskSemaphore`) lives inside a `defer` nested inside the closure passed to `wg.Go`, which itself is nested inside the closure passed to `IfNotStopped`. If `Close()` has already run (or races concurrently with `ExecuteTask`) such that `IfNotStopped` observes the stopped state, `IfNotStopped` returns `false` without ever invoking the inner closure — meaning `wg.Go` (and therefore the deferred semaphore release) never runs. The already-acquired slot at line 69 remains permanently occupied since nothing decrements `taskSemaphore` for that call.

This is reachable from an unprivileged capability-execute message flow: `ExecuteTask` is called from `core/capabilities/remote/executable/server.go` when handling incoming capability execution requests (e.g. via `server.Receive` dispatch) and is bounded by `ServerMaxParallelRequests`. Any external node/peer sending a burst of capability-execute messages that lands exactly while the local node's `ParallelExecutor.Close()` is racing (e.g. during capability config reload/restart or node shutdown) can trigger this leak. Repeated occurrences (each capability reconfiguration/restart is an opportunity) will progressively or immediately exhaust the fixed-size `taskSemaphore`, permanently blocking all future legitimate capability executions on that server instance since `occupiedSlots()` never returns to zero and new `ExecuteTask` calls will block forever on `case t.taskSemaphore <- struct{}{}` (or be forced onto the `<-ctx.Done()`/`<-t.stopChan` paths).

No existing check mitigates this: `IfNotStopped` is only a StateMachine gate and is not integrated with the semaphore's acquire/release pair in an exception-safe way (no `defer` guarding the release immediately after acquisition).

### Impact Explanation
This causes a permanent, unrecoverable capability-execution Denial of Service on the executable-capability server: once slots leak past the configured `ServerMaxParallelRequests` limit, no further capability executions (including legitimate CCIP/OCR capability calls) can be processed by that executor instance, requiring a full node restart to recover. This matches a service-disruption / DoS impact category.

### Likelihood Explanation
The race requires only that the node be shutting down, or a capability be reconfigured/restarted (both of which invoke `Close()` on the `ParallelExecutor`), while an attacker or normal peer traffic continues sending capability-execute messages — a state transition that happens routinely in operational Chainlink nodes (deployments, config updates, restarts). An unprivileged party who can send capability-execute messages during this window (e.g., flooding requests around a known restart/reconfig event) can reliably trigger the leak; each additional leaked slot compounds toward exhaustion of the small parallelism bound, and this is deterministically reproducible in a race test.

### Recommendation
Make the acquire/release atomic and exception-safe: check the stopped state and increment the WaitGroup counter (or use `wg.Add(1)` synchronously) *before* or *atomically with* semaphore acquisition, and use a single `defer` immediately following the successful acquire to guarantee release regardless of which branch executes. For example, restructure so that the semaphore slot is released via a `defer` placed directly after the `case t.taskSemaphore <- struct{}{}` acquisition (outside of `IfNotStopped`'s closure), and only decide whether to actually invoke `fn` based on the stopped check — releasing the slot immediately in the stopped case without waiting for `wg.Go`.

### Proof of Concept
Unit/race test in `core/capabilities/remote/parallel_executor_test.go`:
1. Create `NewParallelExecutor(N, "test")`, call `Start`.
2. Launch many goroutines calling `ExecuteTask(ctx, fn)` concurrently.
3. Concurrently call `Close()` from another goroutine, racing with the `ExecuteTask` calls (repeat across many iterations to increase chance of hitting the acquire-then-stopped window).
4. After all goroutines complete and `Close()` returns, assert `occupiedSlots() == 0`.
5. Expected (buggy) result: after enough iterations, `occupiedSlots()` is non-zero and remains stuck at a positive value even though no tasks are in flight, demonstrating the leaked slot; a subsequent `ExecuteTask` call on a *new* executor instance is unaffected, but repeated leaks on a long-lived instance would exhaust `ServerMaxParallelRequests` capacity in `core/capabilities/remote/executable/server.go`.

func (t *ParallelExecutor) ExecuteTask(ctx context.Context, fn func(ctx context.Context)) error {
	select {
	case t.taskSemaphore <- struct{}{}:
		t.recordSlotUsage(ctx)
		stopped := !t.IfNotStopped(func() {
			t.wg.Go(func() {
				ctxWithStop, cancel := t.stopChan.Ctx(ctx)
				defer func() {
					<-t.taskSemaphore
					t.recordSlotUsage(ctxWithStop)
					cancel()
				}()
				fn(ctxWithStop)
			})
		})

		if stopped {
			return errors.New("executor stopped")
		}
	case <-t.stopChan:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}

	return nil
}
