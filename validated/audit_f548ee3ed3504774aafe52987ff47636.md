## Title
Bancor-style TRC10 Exchange price can be manipulated by front-running / sandwiching a swap - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Just as `CurveLiquidityWarehouse._withdrawFromTarget` derives `sharePrice` from an on-chain, instantaneously-manipulable spot price (`calc_withdraw_one_coin`), java-tron's built-in TRC10 `Exchange` (Bancor-relay AMM) computes swap output purely from the current on-chain reserve balances at execution time, with no TWAP or external oracle. Any account can shift the pool ratio in one transaction and unwind it in another around a victim's swap in the same block, extracting value exactly like the reported spot-price manipulation.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, ...)`, which delegates to `ExchangeProcessor.exchange()` (or `SafeExchangeProcessor` when hardened math is enabled) using the pool's *current* `firstTokenBalance`/`secondTokenBalance` read directly from state at execution time: [1](#0-0) [2](#0-1) 

These reserve balances can be moved arbitrarily within the same block by anyone calling `ExchangeInjectContract` (adds liquidity at the current ratio, does not change price by itself) or, more directly, by submitting a preceding `ExchangeTransactionContract` swap that skews the ratio, and a following one that reverses it — a classic sandwich attack against a pending swap: [3](#0-2) 

The only protection available to a taker is the client-supplied `expected` (minimum-out) field, checked in `doValidate()`: [4](#0-3) 

This is precisely the mitigation the Curve report recommends ("calculate the amount off-chain and pass it as a parameter"), but it only bounds the victim's own loss — it does not prevent an attacker from sandwiching the trade to move the price as close as possible to the victim's `expected` threshold and pocketing the difference, since there is no oracle, EMA check, or price-deviation guard anywhere in the exchange logic (`ExchangeCapsule`, `ExchangeProcessor`, `SafeExchangeProcessor`).

### Impact Explanation
Any anonymous account can extract value from other users' TRC10↔TRX or TRC10↔TRC10 swaps by front-running and back-running them within the same block (transaction ordering is controlled by the block-producing witness and by whoever broadcasts first), causing direct accounting/asset loss to the victim and profit to the attacker — an unprivileged, broadcast-transaction-reachable accounting corruption analogous to the reported bug class.

### Likelihood Explanation
Any account holding sufficient TRX/TRC10 balance can perform this without special privileges, purely via standard `ExchangeTransactionContract` broadcasts; the attack requires only capital and same-block transaction placement, same precondition as the original Curve exploit (front-running a pending tx before it lands on-chain).

### Recommendation
As the auditor suggested for the Curve case, do not rely purely on the instantaneous on-chain reserve ratio for pricing: enforce a maximum per-block/per-transaction price-impact bound, and/or require callers to supply an off-chain-computed expected amount with a tight, protocol-enforced slippage tolerance (rather than an arbitrary client-chosen `expected`), and consider TWAP-style averaging over the exchange balances to raise the cost of manipulation.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` swapping `X` of token A → token B on exchange `E` with `expected = M` (loose slippage bound).
2. Attacker submits `ExchangeTransactionContract` (swap A→B) with a large amount to push the reserve ratio unfavorably for the victim, ordered before the victim's tx in the same block.
3. Victim's swap executes via `ExchangeCapsule.transaction()` using the now-skewed reserves, still passing the `anotherTokenQuant >= tokenExpected` check at `ExchangeTransactionActuator.java:219` but receiving less than the un-manipulated market price.
4. Attacker submits a reverse swap (B→A) after the victim's tx to restore the ratio and realize the price difference as profit, mirroring the front-run/back-run pattern described for `calc_withdraw_one_coin` in the Curve report.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
