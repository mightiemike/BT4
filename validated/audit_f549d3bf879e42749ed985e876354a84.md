### Title
Sequencer removes all fetched deposit blobs from `DepositDataMempool` even when their `BridgeContract::deposit` call failed inside `process_sys_txs`, permanently discarding valid unincluded deposits - (File: `crates/sequencer/src/runner.rs`)

### Summary
`CitreaSequencer::produce_l2_block_inner` fetches a batch of deposit blobs from `DepositDataMempool`, attempts to execute each as a `BridgeContract::deposit` system transaction in `process_sys_txs`, and silently skips (via `continue`) any deposit whose execution reverts with `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful`. Despite this, the *entire original* `deposit_data` batch — not the subset that actually landed in `all_txs`/the produced block — is passed to `self.deposit_mempool.lock().remove_deposits(&deposit_data)`, permanently deleting the reverted-but-legitimate deposit bytes from the mempool.

### Finding Description
Binding claimed: `(set of deposit blobs removed via remove_deposits) == (set of deposit blobs whose BridgeWrapper::deposit call actually committed on-chain)`.

Trace:
1. `send_raw_deposit_transaction` (`crates/sequencer/src/rpc.rs:329-388`) admits a deposit blob after an `eth_call` simulation against `BlockId::pending()`, then calls `deposit_mempool.add_deposit_tx(...)`, queuing the raw bytes in `DepositDataMempool::accepted_deposit_txs` [1](#0-0) .
2. `produce_l2_block_inner` fetches (not removes) up to `deposit_mempool_fetch_limit` deposits into a local `deposit_data: Vec<Deposit>` via `fetch_deposits` [2](#0-1) .
3. This same `deposit_data` slice is passed through `dry_run_transactions` → `produce_and_run_system_transactions` → `process_sys_txs`, which builds one system event per deposit via `populate_deposit_system_events(deposit_data)` and executes each as a signed system tx [3](#0-2) .
4. Inside `process_sys_txs`, if applying a deposit's system tx returns `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful`, the working set is reverted, the nonce is decremented, and the loop simply `continue`s — the failed deposit's `sys_tx_rlp` is never pushed to `all_txs` [4](#0-3) . The code comment explicitly acknowledges this as an expected, non-exceptional path ("as deposits to non-EOA addresses can revert").
5. Because the failed deposit was never added to `all_txs`, it is never included in `txs_to_run`, never applied for real via `apply_l2_block_txs`, and produces no receipt in the final `L2Block`.
6. Yet after the block is committed, `produce_l2_block_inner` unconditionally calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the **original, unfiltered** `deposit_data` fetched in step 2 — not a filtered set restricted to deposits whose bytes actually appear in the committed `all_txs`/`txs_to_run` [5](#0-4) .
7. `DepositDataMempool::remove_deposits` computes `calc_tx_id` for every blob in `deposit_data` and evicts matching entries from both `accepted_deposit_txs` and `pending_deposits` with no success/failure distinction [6](#0-5) .

Root cause: the removal step trusts the *fetched* batch as a proxy for the *committed* batch, but `process_sys_txs`'s per-deposit revert-and-skip logic (lines 1678-1697) already breaks that equivalence by design. No code re-derives which deposits actually succeeded (e.g., by diffing `all_txs`/receipts against `deposit_data`) before calling `remove_deposits`.

Why existing guards don't catch this: the `eth_call` admission check in `rpc.rs` only validates against a single point-in-time `pending` state; nothing re-validates a deposit right before removal, and `remove_deposits` has no visibility into whether the corresponding system tx was actually committed.

### Impact Explanation
A legitimate, Clementine-presigned move-to-vault Bitcoin deposit whose blob passes RPC admission but reverts at inclusion time (e.g. gas exhaustion from earlier system/deposit txs in the same batch, or short-header-proof/light-client state advancing between simulation and inclusion) is permanently purged from `DepositDataMempool::accepted_deposit_txs` and `pending_deposits`. No cBTC is minted for it, and once purged, the only way to fix this is out-of-band manual resubmission of the raw bytes by an external actor — the sequencer itself has lost all record of the deposit. This is a fund-freezing bug: real BTC has moved on L1 but the corresponding L2 credit is permanently blocked absent manual intervention, matching the Critical "funds permanently frozen" category. It is repeatable for every batch containing more than one deposit or any deposit competing for gas/nonce/light-client state with other system events.

### Likelihood Explanation
No privileged role is required — any user who submits a valid deposit blob via `citrea_sendRawDepositTransaction` is exposed once the sequencer's fetch batch (`deposit_mempool_fetch_limit`) contains more than one deposit, since `process_sys_txs` executes them sequentially and cumulative gas/nonce/light-client state can diverge between the RPC-time `eth_call` simulation and actual inclusion. The scenario doesn't require an adversarial attacker at all — it is a natural race between admission-time simulation and inclusion-time execution that the sequencer's own code (comment at `runner.rs:1682-1683`) acknowledges as expected behavior ("deposits to non-EOA addresses can revert"), making it highly likely to occur in normal operation with no attacker cost.

### Recommendation
Track which deposit blobs actually succeeded during `process_sys_txs` (e.g., collect the subset of `deposit_data` whose system tx was pushed into `all_txs`, or diff `deposit_data` against `all_txs`/committed receipts) and pass only that successfully-committed subset to `remove_deposits`. Failed deposits should remain in `DepositDataMempool` so they are retried in a future block.

### Proof of Concept
`cargo test` in `crates/sequencer` (new test module in `deposit_data_mempool.rs` or an integration test around `runner.rs`):
1. Construct a `DepositDataMempool`, add two valid deposit blobs `d1`, `d2` (`add_deposit_tx`).
2. Simulate `produce_l2_block_inner`'s flow: `fetch_deposits(2)` → `deposit_data = [d1, d2]`.
3. Feed `deposit_data` into a harness around `process_sys_txs` that forces `d2`'s underlying `BridgeContract::deposit` call to revert (e.g., by pre-exhausting `SYSTEM_TX_GAS_LIMIT`/1_000_000 remaining block gas before `d2`'s system tx, or by making the light-client short-header-proof state have advanced past what `d2`'s deposit assumed).
4. Assert `all_txs` (returned from `process_sys_txs`) contains the RLP for `d1`'s system tx but NOT `d2`'s.
5. Call `remove_deposits(&deposit_data)` (the unfiltered full batch, as `runner.rs:638` does) and assert `removed_count == 2`.
6. Assert `d2`'s bytes are absent from `DepositDataMempool::accepted_deposit_txs`/`pending_deposits` after this call, even though no receipt for `d2` exists in `all_txs`/the produced block — demonstrating the equality binding is violated: `remove_deposits` evicted a deposit that never committed on-chain.

```rust
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
```
