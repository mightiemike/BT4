### Title
`performTokenExchange` fast-path skips OAuth scope validation enforced by the sibling Auth-Code-Flow path - (File: `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`)

### Summary
`Session.isActive(scopes, withinMillisecondsOfExpiry)` is designed so that scope drift (the app's configured scopes no longer matching the scopes recorded on the stored session) makes the session inactive, forcing re-authorization. `validateWithAuthCodeFlow` (the legacy OAuth path) always calls this with the current `api.config.scopes`, correctly enforcing that check. The token-exchange fast path in `performTokenExchange`, however, calls `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` — passing `undefined` for scopes — which makes `isScopeChanged` always return `false` regardless of the session's actual `scope` field.

### Finding Description
`Session.isActive` explicitly documents that it should be checked "has the given scopes if scopes is equal to a truthy value" [1](#0-0) , and `isScopeChanged` returns `false` (i.e. "no problem") whenever `scopes` is `undefined` [2](#0-1) .

The Auth-Code-Flow validator, `validateWithAuthCodeFlow`, correctly threads `api.config.scopes` through: `session.isActive(api.config.scopes)` [3](#0-2) , and this is exactly the pattern the v6 migration guide calls out as the required change ("If the scopes of the session don't match the scopes of the application ... the session is deemed to be inactive and OAuth should be initiated again") [4](#0-3) . The sibling middleware `ensureInstalledOnShop` follows the same correct pattern: `session.isActive(api.config.scopes)` [5](#0-4) .

By contrast, `performTokenExchange`'s "session is already valid, skip re-auth" fast path does:
```ts
if (session && session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)) {
  ...
  res.locals.shopify = {...res.locals.shopify, session};
  next();
  return;
}
``` [6](#0-5) 

This is structurally analogous to the reported `amoMinterBorrow` bug: a specialized/"fast" bypass entry point (there, borrowing collateral without the mint/redeem cycle; here, reusing a cached session without going through the full token-exchange re-issuance) omits a safety gate (`recollateralizePaused`/`collateralEnabled` there; the app's current required-scopes check here) that all the equivalent, non-bypass code paths in the same codebase enforce.

### Impact Explanation
If a merchant reduces the scopes the app requires (via `shopify.app.toml` update and redeploy) — for example removing a sensitive scope like `write_orders` or `read_customers` after revoking consent — the app is expected to detect the scope mismatch on the next request and force re-authorization (as the code comments and Auth-Code-Flow path show is the intended security model). Under the token-exchange strategy, this enforcement is skipped: as long as the previously stored offline/online session has a non-expired access token, the stale session (with its old, broader scope set) continues to be treated as valid indefinitely, and the underlying Shopify access token — which Shopify itself will have already narrowed/reissued according to the merchant's granted scopes — continues to be used by the app without the app-side scope re-validation flow (and without triggering `afterAuth` hooks that many apps use to re-sync consent state, billing, or webhook registration).

### Likelihood Explanation
This path is used by every app that enables the `future.tokenExchange` flag together with an embedded app configuration — this is the currently recommended/default strategy for new embedded apps, and it is the primary path for `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router` in Shopify-managed-installation mode. Triggering this requires no privileged action from an attacker: it is simply a consequence of a normal merchant scope-reduction event followed by an ordinary authenticated request from that merchant's session, which is very likely to occur in production apps that add or remove scopes over their lifetime.

### Recommendation
- **Short term**: Change `performTokenExchange`'s fast-path check to `session.isActive(api.config.scopes, WITHIN_MILLISECONDS_OF_EXPIRY)`, matching `validateWithAuthCodeFlow` and `ensureInstalledOnShop`, so that a scope mismatch always falls through to `exchangeToken`/re-authorization instead of being accepted as-is.
- **Long term**: Audit every call site of `Session.isActive` across `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router` (and any future auth strategies) to ensure `scopes` is always passed explicitly rather than left to default/`undefined`, and add a lint rule or wrapper that fails a build if `isActive` is called without an explicit scopes argument.

### Proof of Concept
1. Configure an embedded app with `future.tokenExchange: true` and `scopes: ['read_orders', 'write_orders']`.
2. Merchant installs the app; `performTokenExchange` stores an offline session with `scope: 'read_orders,write_orders'` and a long-lived, non-expired `accessToken`.
3. App developer redeploys with a reduced scope list, e.g. `scopes: ['read_orders']` (dropping `write_orders`), intending that any session granted broader scopes be forced to re-authenticate before being trusted again.
4. Merchant makes a normal authenticated request (embedded admin page load / fetch) that hits `validateAuthenticatedSession()` → `validateWithTokenExchange` → `performTokenExchange`.
5. Because `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` ignores scopes entirely [6](#0-5) , the stale session with the old `write_orders` scope is accepted, `next()` is called, and the request proceeds using the outdated session/scope assumptions without a fresh token exchange or `afterAuth` hook invocation — unlike the Auth-Code-Flow path, which would have detected `isScopeChanged` and redirected to re-authorize [7](#0-6) .

  /**
   * Whether the session is active. Active sessions have an access token that is not expired, and has has the given
   * scopes if scopes is equal to a truthy value.
   */
  public isActive(
    scopes: AuthScopes | string | string[] | undefined,
    withinMillisecondsOfExpiry = 500,
  ): boolean {
    const hasAccessToken = Boolean(this.accessToken);
    const isTokenNotExpired = !this.isExpired(withinMillisecondsOfExpiry);
    const isScopeChanged = this.isScopeChanged(scopes);
    return !isScopeChanged && hasAccessToken && isTokenNotExpired;
  }

  /**
   * Whether the access token includes the given scopes if they are provided.
   */
  public isScopeChanged(
    scopes: AuthScopes | string | string[] | undefined,
  ): boolean {
    if (typeof scopes === 'undefined') {
      return false;
    }

    return !this.isScopeIncluded(scopes);
  }
