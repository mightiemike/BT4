### Title
Denial-of-Service via unmetered unbounded trie iteration in `action_delete_account` / `remove_account` - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
`DeleteAccountAction` is charged a fixed, size-independent `delete_account_cost` fee [1](#0-0) , yet its execution calls `remove_account()`, which iterates and deletes *every* access-key, gas-key-nonce, and contract-data trie entry belonging to the account [2](#0-1) . Only the storage-usage byte total is capped (`Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`), and the compute cost that is actually added back for this work only covers gas-key-nonce rows, not the (potentially numerous) plain access keys or contract-data entries that were iterated and removed [3](#0-2) . This mirrors the reported bug class: a per-transaction unbounded loop over a data structure whose size is not reflected in the gas actually charged, allowing an attacker to buy disproportionate node work for a fixed, cheap fee.

### Finding Description
`action_delete_account` computes `account_storage_usage` (minus contract-code bytes) and rejects deletion only if it exceeds `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` [4](#0-3) . If that check passes, `remove_account(state_update, account_id)` is called unconditionally [5](#0-4) .

`remove_account` performs three separate unbounded trie scans:
1. Iterating the full access-key prefix range, parsing each raw key (handling gas-key nonce rows specially), and collecting every key into `keys_to_remove` before deleting them one by one [6](#0-5) .
2. A second full-prefix iteration over all contract-data keys belonging to the account, parsing and collecting them, then deleting each [7](#0-6) .

The number of entries touched by these loops is bounded only by the account's total storage-usage bytes (`MAX_ACCOUNT_DELETION_STORAGE_USAGE`), not by any per-entry gas charge tied to `DeleteAccountAction`. Compare this with `action_delete_account`'s actual gas accounting: it only adds extra `compute_usage` for `gas_key_nonce_count` entries via `storage_removes_compute` [8](#0-7) ; plain `AccessKey` and `ContractData` deletions performed inside `remove_account` are not separately metered/charged beyond the single flat `delete_account_cost` fee (147,489,000,000 gas ≈ 0.147 Tgas) [1](#0-0) .

An attacker can therefore populate an account with many small `storage_write` entries or many `AddKey` access keys, up to the point where `storage_usage` approaches (but stays under) `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, and then submit a single `DeleteAccountAction`. The node performing `apply()` must run two full trie prefix-iterations (parsing, collecting into `Vec<TrieKey>`, then issuing per-key `state_update.remove()` calls) for a fee that does not scale with the number of items being iterated/removed — reproducing the "cheap fixed cost, unbounded internal loop" DoS pattern described in the external report (`_getTotalReservesAndCollaterals`/`_getTotalLiabilities`), just realized here as a NEAR runtime action rather than a Solidity view/loop.

Note: I could not read the exact numeric value of `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` from `core/primitives-core/src/account.rs` (the index did not surface the constant definition), so I cannot state precisely how many access keys/contract-data entries this permits. This is a gap in verification that a background agent with full repo access should close before treating this as conclusively exploitable versus adequately bounded.

### Impact Explanation
If the per-key iteration/removal cost that `remove_account` performs (trie lookups, nibble parsing, and node deletions/squashing) is not proportional to the gas actually charged for `DeleteAccountAction`, a chunk producer can be forced to spend disproportionate wall-clock/IO time processing a single cheap transaction. Because `remove_account`'s work happens synchronously and unconditionally inside `apply_action`, and only gas-key-nonce cost is added to `compute_usage` afterward, the chunk's `compute_limit` accounting (used to bound per-chunk work, see `process_receipts`) may not reflect the true cost of this action [9](#0-8) . This could allow an attacker to submit transactions whose real execution cost exceeds what the gas/compute accounting assumes, potentially causing chunk-application slowdowns across all validators applying the same chunk (a shared, protocol-level cost, not merely local to the attacker), which is the DoS pattern class this analog targets.

### Likelihood Explanation
Reachable by any unprivileged transaction signer: create/fund an account, populate it with contract-data entries or access keys (each a separate transaction, standard priced actions), then submit one `DeleteAccountAction`. No special privileges are required. The main uncertainty is the actual numeric bound of `MAX_ACCOUNT_DELETION_STORAGE_USAGE` and whether it already limits entry counts tightly enough that the flat `delete_account_cost` remains proportionate — I was unable to verify this constant's value or history (e.g., whether it was already tuned specifically to bound this cost) within the available index.

### Recommendation
- Meter `remove_account`'s work by the number of access-key and contract-data entries actually removed (not just gas-key nonces), analogous to the existing `gas_key_nonce_count`/`storage_removes_compute` accounting, and add that compute cost to `result.compute_usage` in `action_delete_account`.
- Confirm/tighten `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` so that the worst-case entry count achievable within that byte budget corresponds to bounded, already-priced-for work under the flat `delete_account_cost`.
- Consider incremental/paginated account deletion (already precedented by the paginated `view_access_keys`) if a single-transaction full deletion of large numbers of entries cannot be safely bounded by a flat fee.

### Proof of Concept
1. Create account `victim.near` with a full-access key.
2. Submit many transactions (`storage_write`-based contract calls, or `AddKey` actions) from `victim.near`'s own contract to add as many small `ContractData` entries (or access keys) as `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` allows without deploying a large contract.
3. Submit a single `DeleteAccountAction` receipt for `victim.near`, paying only the flat `delete_account_cost` fee.
4. Observe that `action_delete_account` → `remove_account` performs two full trie prefix-scans (`get_raw_prefix_for_access_keys`, `get_raw_prefix_for_contract_data`) and deletes every collected key [10](#0-9) , while `result.compute_usage` is only incremented for gas-key-nonce rows [8](#0-7) , showing the mismatch between actual iteration/deletion work and charged compute for the plain access-key/contract-data portion.

(This PoC could not be executed against the live repo in this session; the exact magnitude of the achievable entry count under `MAX_ACCOUNT_DELETION_STORAGE_USAGE` should be measured by a background agent to quantify real-world severity.)

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
