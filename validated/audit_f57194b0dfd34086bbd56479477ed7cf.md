### Title
KV session storage adapter accumulates unbounded duplicate session IDs in shop index, causing storage bloat and lookup corruption - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`KVSessionStorage.storeSession` unconditionally appends the session ID to the per-shop index list on every call without checking for an existing entry, unlike the equivalent Redis adapter which explicitly deduplicates. Because `storeSession` is called on every session persist/update (OAuth callback, online-session refresh, token exchange), this causes the shop's index array to grow without bound and never self-heals, similar to the `Lock.extendLock` accounting bug where a value used later for a critical calculation is never correctly maintained.

### Finding Description
`storeSession` writes the session data, then calls the private `addShopIds` helper to track the shop → session-id mapping used by `findSessionsByShop`: [1](#0-0) 

`addShopIds` simply concatenates the new IDs onto the existing list with no deduplication check: [2](#0-1) 

Compare this to the Redis session storage adapter's equivalent function, `addKeyToShopList`, which explicitly checks `if (!idKeysArray.includes(idKey))` before pushing: [3](#0-2) 

This is the same class of bug as `Lock.extendLock`: a value (`totalLocked` / the shop's session-id array) that is incremented on one code path (`lock` / `storeSession` for a new session) is incremented again on a repeat/update path (`extendLock` / `storeSession` on an existing session) without accounting for the fact that the underlying entity already exists, corrupting the tracking structure that a later read/release operation (`Lock.release` / `findSessionsByShop`) depends on.

`storeSession` is called by `@shopify/shopify-api`'s OAuth `callback` handler every time a session (online or offline) is persisted, including re-authentication of an already-installed shop or refresh of an existing user's online session — the session ID for a returning/online user is stable, so `storeSession` is invoked repeatedly with the same `session.id`: [4](#0-3) 

Each such call appends a duplicate entry to `shop:${shop}` in the KV namespace, and `deleteSession`'s `removeShopIds` only cleans this up when a session is explicitly deleted (via `filter`, which does remove duplicates, but only on that one path) — normal reinstall/token-refresh/OAuth flows never trigger `deleteSession`, so duplicates accumulate indefinitely: [5](#0-4) 

### Impact Explanation
`findSessionsByShop` is used by consuming applications (documented pattern in `AppInstallations.includes`/`delete`) to determine whether a shop has a valid installed session, gating auth/webhook handling flows: [6](#0-5) 

Because `findSessionsByShop` calls `loadSession` for every ID in the (unbounded, duplicate-laden) list, repeated OAuth callbacks/online-session refreshes from a single merchant/session will cause the per-shop KV value to grow without bound. In Cloudflare Workers KV, values have hard size limits; once exceeded, `namespace.put` for the shop index will begin failing, silently breaking `addShopIds`/`removeShopIds` and therefore `findSessionsByShop`. This degrades or denies the installed-shop lookup used by auth/installation-gating logic for that shop (a DoS of an auth-adjacent handler), and produces incorrect/duplicated results well before that limit is hit, undermining the integrity of session bookkeeping that other package logic relies on.

### Likelihood Explanation
No forgery or elevated privileges are required — any legitimate merchant/user whose app performs OAuth (or refreshes an online session) repeatedly against the KV storage adapter will trigger unbounded growth. This is a direct, deterministic consequence of normal usage of the documented `@shopify/shopify-app-session-storage-kv` package with no attacker-controlled input needed beyond ordinary repeated authentication, making it highly likely to manifest in production for any app that sees repeat visits/logins from the same shop or user.

### Recommendation
Mirror the Redis adapter's approach in `addShopIds`: read the existing list and only append IDs not already present (deduplicate), e.g. `const merged = Array.from(new Set([...shopIds, ...ids]))`, before writing back to the KV namespace.

### Proof of Concept
1. Configure an app to use `KVSessionStorage`.
2. Complete OAuth for `shop.myshopify.com`, producing session ID `S1`; `addShopIds` sets `shop:shop.myshopify.com` = `["S1"]`.
3. Trigger a second OAuth/online-session refresh for the same shop/user, again producing session ID `S1` (as is normal for online sessions tied to a stable user), or reinstall flow producing offline session `offline_shop.myshopify.com`; `storeSession` overwrites the session content, but `addShopIds` appends `S1` again, resulting in `shop:shop.myshopify.com` = `["S1", "S1"]`.
4. Repeat step 3 N times (e.g., via normal app usage/page loads that refresh the online token) — the array grows to `["S1", "S1", ..., S1]` (N entries) with no bound.
5. Call `findSessionsByShop('shop.myshopify.com')`; it returns N duplicate `Session` objects, and continued growth will eventually exceed the underlying KV value size limit, causing `namespace.put` calls in `addShopIds`/`removeShopIds` to fail.

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
      );
    }
  }
