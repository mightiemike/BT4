### Title
Unchecked `.unwrap()` on fallible shard-layout remapping causes deterministic chain halt when processing delayed receipts across resharding boundaries - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The CVE-2021-47207 pattern (dereferencing a value from a function that can return an absent/error result without checking it, causing a panic) has a direct analog in `DelayedReceiptQueueWrapper::receipt_filter_fn`, which double-`unwrap()`s a fallible shard-layout lookup and a fallible receipt-to-shard remap while draining the delayed receipt queue during every chunk apply.

### Finding Description
`receipt_filter_fn` is called from `DelayedReceiptQueueWrapper::pop` on every receipt popped off the delayed-receipt queue during `process_delayed_receipts`, which runs on every chunk apply on every validating/tracking node: [1](#0-0) 

Both calls in this function are unchecked:
- `self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap()` — panics if the epoch's shard layout cannot be resolved.
- `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()` — panics if the receipt's stored target shard cannot be remapped into the current shard layout.

The accompanying test (`test_stale_global_contract_distribution_after_double_resharding`) demonstrates that this exact code path was already a proven crash: a `GlobalContractDistribution` receipt (created by an unprivileged user submitting a `DeployGlobalContract` transaction) can sit in the delayed queue across two resharding generations, at which point `receiver_shard_id()` previously failed to remap the receipt's stale `target_shard` into the new layout: [2](#0-1) 

That test only exercises and asserts non-panicking behavior for the *two-resharding* case. The `unwrap()` calls in `receipt_filter_fn` remain unconditional — there is no `Result`/`Option` handling — so any receipt that stays delayed long enough (three or more resharding generations, or any other combination the remap logic does not account for), or any epoch whose shard layout cannot be resolved by `epoch_info_provider.shard_layout`, will still panic every node applying that shard, exactly like the kernel's unchecked pointer dereference in `snd_gf1_dma_next_block`.

### Impact Explanation
Because `process_delayed_receipts` runs deterministically as part of `Runtime::apply` on every honest node validating/tracking the shard, a panic here is not a single-node crash — it is a synchronized, protocol-level halt: all nodes attempting to apply the chunk containing the problematic delayed receipt panic identically, since delayed-queue contents and shard layout are part of consensus state. This matches the "transaction-triggered halt" acceptance criterion: an unprivileged user needs only to submit a `DeployGlobalContract` (or, more generally, any receipt subject to congestion-driven delay/`receipt_filter_fn`) at a moment when the shard undergoes enough resharding transitions for the remap to fail or the epoch shard-layout lookup to error.

### Likelihood Explanation
Reaching the vulnerable path requires: (1) triggering enough congestion on a shard to push a receipt into the delayed-receipt queue, (2) the shard undergoing resharding (dynamic resharding is enabled), and (3) the receipt surviving through resharding transitions in numbers/order the fix does not cover. This requires favorable network/config conditions (dynamic resharding active) but no validator or operator privilege — the triggering action (submitting transactions to saturate compute and deploying a global contract) is fully available to an ordinary transaction signer/contract deployer, as demonstrated by the existing regression test that reconstructs exactly this scenario.

### Recommendation
Replace both `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (`?` returning `RuntimeError`/`StorageError::StorageInconsistentState`) instead of panicking, and audit `receiver_shard_id()`'s remap logic to guarantee it can resolve *any* number of resharding generations a delayed receipt may have survived, not just two. Add fuzz/property tests that delay `GlobalContractDistribution` (and other receipt kinds subject to `receipt_filter_fn`) across N ≥ 3 resharding generations to confirm the remap never errors, or make the queue draining logic tolerate an unresolvable target shard (e.g., by re-routing rather than panicking).

### Proof of Concept
Extend the existing test `test_stale_global_contract_distribution_after_double_resharding` (`test-loop-tests/src/tests/global_contracts_distribution.rs:32`) to force a *third* sequential shard split (`force_split_shards` with three entries) instead of two, while keeping the target-shard-saturation loop that keeps the `GlobalContractDistribution` receipt delayed. If `receiver_shard_id()`'s remap logic is bounded to the two-generation case (as its narrow test coverage suggests), draining the queue after the third resharding will panic in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`), causing `run_until_head_height(drain_end)` to stall exactly as the original test's comment predicts for the unfixed case.

    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }
