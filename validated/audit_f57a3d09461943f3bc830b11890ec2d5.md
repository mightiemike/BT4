### Title
Precompile signature verification (secp256k1/ed25519/secp256r1) is fully unmetered by the compute-unit budget, allowing expensive EC verification loops to run unbounded per transaction - ([File: program-runtime/src/invoke_context.rs])

### Summary
Analogous to the Megapot bug — where a nested loop's iteration count (`bonusballMax * normalTiers * subsets`) was not bounded relative to the enforced gas ceiling, causing the drawing-settlement transaction to always exceed the block gas limit — agave's precompile-processing path executes attacker-controlled signature-verification loops (`for i in 0..count`) that are entirely excluded from the runtime's per-transaction compute-unit metering. The cost is only *estimated* for block-inclusion cost-tracking purposes, but the actual VM compute meter never decrements for this work, decoupling the enforced budget from the true computational cost.

### Finding Description
When the SVM processes a message, `InvokeContext::process_message` special-cases precompile programs and routes them to `process_precompile` instead of `process_instruction`: [1](#0-0) 

`process_precompile` calls the precompile's `verify` closure but never touches `compute_units_consumed`, which remains `0` for the entire instruction: [2](#0-1) 

This is explicitly documented by the test `test_builtin_ix_precompiled`, whose comment states "VM Execution: consume 0 from CU-meter" and whose expected `cost_adjustment` equals the full builtin allocation with nothing subtracted for the precompile's actual work: [3](#0-2) 

Meanwhile, the precompile `verify` functions themselves run unbounded, attacker-sized loops of expensive elliptic-curve operations. `secp256k1::verify` loops `for i in 0..count` (count up to `u8::MAX = 255`), calling `libsecp256k1::recover` (EC point recovery) per iteration: [4](#0-3) 

`ed25519::verify` likewise loops up to 255 times calling `ed25519_dalek` strict signature verification: [5](#0-4) 

`secp256r1::verify` is the only one of the three that caps `num_signatures` at 8, showing that a bound is achievable and was applied inconsistently: [6](#0-5) 

The `signature_instruction_index`/`offset` fields let each declared signature reference *arbitrary* instruction data elsewhere in the same transaction (via `get_data_slice`), so the heavy EC-verification workload can be amplified far beyond what the small 14-byte-per-signature offset table costs in transaction size: [7](#0-6) 

The only accounting for this cost is the cost-model's *estimate*, used purely for block-inclusion/cost-tracker limits, not for stopping in-flight execution: [8](#0-7) [9](#0-8) 

This mirrors the Megapot root cause precisely: a loop whose bound is attacker/user-controlled (`num_signatures`, and the number of precompile instructions packed into one transaction) is not gated by the mechanism (compute-unit budget) that is supposed to bound per-transaction work; instead, a separate, coarser estimate (block cost units in agave; gas-limit assumption in Megapot) is used, while the *real* execution path runs to completion regardless of the requested/enforced compute budget.

### Impact Explanation
Because precompile verification bypasses the 1.4M CU per-transaction compute budget entirely, a transaction can request a minimal `compute_unit_limit` (and thus pay a minimal compute-based priority fee) while still forcing the leader/replaying validators to perform substantial elliptic-curve computation (ECDSA recovery, OpenSSL signature checks) during message processing — work whose actual wall-clock cost is not reflected in what the compute-budget system was designed to bound. Packed across many transactions in a block, this creates a mismatch between the compute budget the protocol believes it is enforcing and the CPU time validators actually spend, which is the class of "unbounded work vs. enforced limit" issue the Megapot report describes (there, it manifested as guaranteed-exceeded block gas limit breaking settlement; here it manifests as a metering gap that can be used to extract disproportionate leader/replay CPU time per unit of accounted compute budget).

### Likelihood Explanation
Any ordinary client can construct such a transaction: it only requires including secp256k1/ed25519 precompile instructions with the maximum `num_signatures` byte and offset tables pointing at shared data, well within the standard packet size limit, no privileged sender or special feature flag needed. The relevant code paths (`process_precompile`, `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`) are on the normal transaction execution path exercised by every validator.

### Recommendation
Charge compute units for precompile verification work proportional to the actual number of signatures verified (using the existing `SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST`/`SECP256R1_VERIFY_COST` constants) inside `InvokeContext::process_precompile`/`process_message`, deducting from `accumulated_consumed_units` and aborting with `ComputeBudgetExceeded` if the transaction's requested compute budget is exhausted, instead of only using these constants for block-cost estimation. Additionally, apply a hard cap on `num_signatures` for secp256k1/ed25519 (as already done for secp256r1's cap of 8) rather than allowing the full `u8::MAX`.

### Proof of Concept
Not applicable in this format (no runnable environment). The logical PoC is: construct a versioned transaction containing several `secp256k1_program`/`ed25519_program` instructions, each with `num_signatures = 255` (or repeated across several instructions to accumulate hundreds of verifications), with offsets pointing to a shared small "seed" instruction's data. Submit with `SetComputeUnitLimit` set to a very low value (e.g., 200 CU). Observe that `process_precompile` still runs every EC verification to completion (0 CU is charged against the requested budget, per `core/tests/scheduler_cost_adjustment.rs::test_builtin_ix_precompiled`), i.e., actual expensive work executes fully independent of the enforced per-transaction compute budget.

fn get_data_slice<'a>(
    data: &'a [u8],
    instruction_datas: &'a [&[u8]],
    instruction_index: u16,
    offset_start: u16,
    size: usize,
) -> Result<&'a [u8], PrecompileError> {
    let instruction = if instruction_index == u16::MAX {
        data
    } else {
        let signature_index = instruction_index as usize;
        if signature_index >= instruction_datas.len() {
            return Err(PrecompileError::InvalidDataOffsets);
        }
        instruction_datas[signature_index]
    };

    let start = offset_start as usize;
    let end = start.saturating_add(size);
    if end > instruction.len() {
        return Err(PrecompileError::InvalidDataOffsets);
    }

    Ok(&instruction[start..end])
}
