### Title
Griefable rounding in `UnDelegateResourceActuator` lets any user dilute another owner's returned bandwidth/energy usage credit - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.execute` computes the amount of `NetUsage`/`EnergyUsage` to transfer back from a resource receiver to the resource owner as a proportion: `receiverCapsule.getNetUsage() * (unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth())`. The denominator (`getAllFrozenBalanceForBandwidth`/`getAllFrozenBalanceForEnergy`) aggregates resource frozen/delegated to the receiver from **any** unprivileged account, not just the caller performing the undelegate. This is the same bug class as the reported ERC1155 issue: an attacker can inflate a shared denominator used in someone else's proportional-transfer calculation between the time it is measured and used, causing rounding losses for the victim.

### Finding Description
In `UnDelegateResourceActuator.execute`, when the owner un-delegates part of the resource they previously delegated to a receiver, the actuator computes the usage that must be "given back" to the owner proportionally to the un-delegated balance versus the receiver's total resource: [1](#0-0) 

The denominator, `receiverCapsule.getAllFrozenBalanceForBandwidth()` (and the ENERGY analog `getAllFrozenBalanceForEnergy()`), reflects the receiver's own frozen balance plus all acquired delegated balances received from every delegator, not solely the caller of this transaction: [2](#0-1) 

Any unprivileged account can increase this denominator at any time by calling `DelegateResourceActuator`, which credits the receiver's `AcquiredDelegatedFrozenV2BalanceForBandwidth`/`Energy` (part of `getAllFrozenBalanceForBandwidth`/`Energy`): [3](#0-2) 

Because the un-delegating owner has no control over, and no visibility into, other parties' delegations to the same receiver at the moment their transaction is mined, an attacker can front-run/interleave a delegation to the receiver right before the victim's `UnDelegateResourceContract` executes. This inflates `getAllFrozenBalanceForBandwidth`/`Energy`, shrinking the computed `transferUsage` fraction through integer truncation of the `(double) unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth()` division. The victim then receives less (or, with a large enough denominator, zero) bandwidth/energy usage credit back via `processor.unDelegateIncrease(...)`, even though they undelegate the exact TRX balance they intended: [4](#0-3) 

This directly mirrors the external report's root cause: a shared proportional-accounting denominator (`balanceOf(from, ids[i])` there vs. `getAllFrozenBalanceForBandwidth/Energy` here) that any unprivileged actor can inflate ("donate") before a victim's transfer/undelegate executes, causing rounding-driven under-crediting of the victim's tracked accounting value (contribution vs. usage).

### Impact Explanation
The impact is accounting divergence rather than fund theft: the un-delegating owner permanently loses part of the `NetUsage`/`EnergyUsage` credit that should be transferred back to them, while the receiver silently retains usage that no longer corresponds to any resource actually delegated to them (their `NetUsage`/`EnergyUsage` is reduced by less than it should be). This can degrade or dilute the resource accounting fairness for the owner-receiver pair and is a state-integrity/accounting-correctness impact, consistent with a low-severity griefing issue similar to the original finding.

### Likelihood Explanation
`DelegateResourceActuator` is a fully public, unprivileged actuator that any account can call against any receiver address at any time (no relationship or authorization required), and `UnDelegateResourceActuator` reads the receiver's current, live `AllFrozenBalanceForBandwidth/Energy` at execution time rather than a value pinned to the owner's own delegation. This makes the griefing condition trivially and repeatedly reproducible by any attacker who wants to target a particular owner/receiver undelegate flow, matching the "High likelihood" characterization in the original report.

### Recommendation
Do not let a third party's unrelated delegation to the receiver affect the owner's own undelegate accounting. Compute `transferUsage` using a denominator scoped to the delegation between the specific owner and receiver (e.g., derived from the `DelegatedResourceCapsule` between `ownerAddress` and `receiverAddress`) rather than the receiver's aggregate `AllFrozenBalanceForBandwidth/Energy`, or otherwise guarantee that `transferUsage` is never truncated to a disproportionately small value when `receiverCapsule.getNetUsage()`/`getEnergyUsage()` is non-zero and `unDelegateBalance` is a meaningful fraction of what the owner originally delegated.

### Proof of Concept
Conceptual sequence (cannot be executed without a live node/test harness, but derivable directly from the code):
1. Owner `O` delegates `X` bandwidth-TRX to receiver `R` via `DelegateResourceActuator`; `R.AcquiredDelegatedFrozenV2BalanceForBandwidth += X`.
2. `R` accumulates `NetUsage` from using that bandwidth.
3. Attacker `A` (unrelated party) calls `DelegateResourceActuator` to delegate a large amount `Y >> X` of bandwidth-TRX to the same receiver `R`, inflating `R.AllFrozenBalanceForBandwidth` (via `AcquiredDelegatedFrozenV2BalanceForBandwidth`).
4. `O` calls `UnDelegateResourceContract` to reclaim `X`. `UnDelegateResourceActuator.execute` computes:
   `transferUsage = (long)(R.getNetUsage() * ((double) X / R.getAllFrozenBalanceForBandwidth()))` [5](#0-4) 
   Because the denominator now includes `Y`, `transferUsage` is truncated to a smaller value than it would have been absent `A`'s delegation (potentially 0), so `O` receives less-than-expected `NetUsage` credit back via `unDelegateIncrease`, while `R.NetUsage` is reduced by the same diminished amount — a permanent, unrecoverable loss of usage-accounting fidelity for `O`, purely due to `A`'s unrelated action inflating a shared denominator.
