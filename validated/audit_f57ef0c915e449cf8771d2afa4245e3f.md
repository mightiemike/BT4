### Title
Divergent buffered-receipt accumulators (`CongestionInfo` vs `ReceiptGroupsQueue`) cause an incorrect/underflowing congestion-info computation during resharding — ([File: chain/chain/src/resharding/manager.rs])

### Summary
This nearcore bug class mirrors the Sherlock PoolTogether finding: multiple accumulators that are supposed to represent the *same* logical quantity are updated at different granularities/conditions, and later one accumulator's per-bucket value is subtracted from the other's aggregate total as if they were always kept in lock-step. In PoolTogether, `_startDrawIdInclusive` was computed against the "total" accumulator's retention window but applied to the vault/donation accumulators, which had a different (shorter) retention. In nearcore, the analogous pair is `CongestionInfo::buffered_receipts_gas`/`receipt_bytes` (updated unconditionally on every buffered receipt in `ReceiptSinkV2::buffer_receipt`) versus the per-receiver-shard `ReceiptGroupsQueue` totals (`total_size`/`total_gas`, updated only when `receipt.should_update_outgoing_metadatas()` is true).

### Finding Description
`ReceiptSinkV2::buffer_receipt` (`runtime/runtime/src/congestion_control.rs:466-501`) always increments the shard-wide totals:
```
self.own_congestion_info.add_receipt_bytes(size)?;
self.own_congestion_info.add_buffered_receipt_gas(gas)?;
```
but only *conditionally* updates the per-receiver-shard `ReceiptGroupsQueue` bookkeeping used for bandwidth requests:
```
if receipt.should_update_outgoing_metadatas() {
    self.outgoing_metadatas.update_on_receipt_pushed(shard, ByteSize::b(size), gas, state_update)?;
}
``` [1](#0-0) 

`ReceiptGroupsQueueDataV0::total_size`/`total_gas` are otherwise maintained as strict, checked incremental accumulators (`update_on_receipt_pushed`/`update_on_receipt_popped`, using `checked_add`/`checked_sub` that `.expect()` on overflow/underflow): [2](#0-1) 

At resharding time, `ResardingManager::get_child_congestion_info_not_finalized` computes the *right* child's congestion info by taking the parent's `CongestionInfo` (the "total" accumulator) and subtracting, for every shard in the parent layout, the `ReceiptGroupsQueue` totals (the per-shard "partial" accumulator) loaded straight from the trie:
```rust
let bytes = receipt_groups.total_size();
let gas = receipt_groups.total_gas();
congestion_info.remove_buffered_receipt_gas(gas)
    .expect("Buffered gas must not exceed congestion info buffered gas");
congestion_info.remove_receipt_bytes(bytes)
    .expect("Buffered size must not exceed congestion info buffered size");
``` [3](#0-2) 

This subtraction implicitly assumes `sum(ReceiptGroupsQueue.total_size/total_gas over all shards) == CongestionInfo.receipt_bytes/buffered_receipts_gas` exactly. But because `should_update_outgoing_metadatas()` gates whether a given buffered receipt is counted in the `ReceiptGroupsQueue` accumulator while `own_congestion_info.add_receipt_bytes/add_buffered_receipt_gas` is unconditional, any receipt kind for which that predicate is false is present in the aggregate `CongestionInfo` total but **absent** from every `ReceiptGroupsQueue` used in the subtraction. This is structurally identical to the Sherlock bug: the "total" accumulator (`CongestionInfo`) and the more narrowly-updated accumulator (`ReceiptGroupsQueue`) are not kept in the same accounting domain, yet a range/quantity derived from one is subtracted from/applied to the other as if they always matched.

### Impact Explanation
Two concrete, protocol-level consequences follow, both directly reachable from ordinary user transactions that create buffered outgoing receipts prior to a shard-split (resharding) event that these accumulators feed into:

1. **Transaction/receipt-triggered chain halt.** If, for the excluded receipt kind(s), the untracked bytes/gas exceed what remains after subtracting the (smaller) `ReceiptGroupsQueue` totals for other receipts, `remove_buffered_receipt_gas`/`remove_receipt_bytes` can still succeed numerically in some cases but produce a **wrong** (understated) residual `CongestionInfo` for the right child; conversely, if the excluded receipts are large enough relative to what's tracked, the checked subtraction can underflow and hit the `.expect()` panic, crashing every node applying that chunk — a network-wide, transaction/receipt-triggered halt at the exact resharding boundary. This satisfies the "transaction-triggered halt" acceptance criterion.
2. **Invalid state transition / consensus divergence risk.** Even short of a panic, an inflated or deflated `CongestionInfo.buffered_receipts_gas`/`receipt_bytes` on the right child after a shard split feeds directly into `CongestionControl::congestion_level`, `outgoing_gas_limit`, and `shard_accepts_transactions` (per `protocol-model/spec/cross-shard-congestion.md`), meaning the derived congestion state committed to the chunk header can be wrong relative to the receipts actually present in the child shard's trie. Because congestion info is a consensus-critical, header-committed field, an incorrect value computed deterministically-but-wrongly by all honest nodes would still validate (since all nodes run the same buggy code), but it corrupts subsequent admission/backpressure decisions — i.e., transactions can be wrongly rejected (tx-admission bypass in the conservative direction) or wrongly admitted beyond intended congestion limits. [4](#0-3) 

### Likelihood Explanation
Reaching this requires: (a) triggering `should_update_outgoing_metadatas() == false` for some receipt kind (I was unable to locate and inspect this predicate's implementation directly within the indexed context, so I cannot confirm precisely which receipt kind(s) it excludes — this is the main unverified link in the chain), and (b) having such receipts sit in the outgoing buffer of a shard at the moment ReshardingV3 splits that shard. Both buffered receipts and the timing relative to a shard split are influenced by ordinary user transaction/receipt traffic (congestion is user-driven), so the trigger is plausibly reachable by an unprivileged actor who can shape receipt traffic, though the resharding event itself is a protocol-scheduled, not attacker-scheduled, event. Given I could not verify `should_update_outgoing_metadatas()`'s exact semantics, I am flagging this as **uncertain** rather than fully proven.

### Recommendation
Verify that `Receipt::should_update_outgoing_metadatas()` truly excludes some receipt kinds from `ReceiptGroupsQueue` accounting while `CongestionInfo::add_receipt_bytes/add_buffered_receipt_gas` remains unconditional in `buffer_receipt`. If so, either (a) make `ReceiptGroupsQueue` track every buffered receipt unconditionally so its totals always equal the aggregate `CongestionInfo` buffered totals, or (b) change `get_child_congestion_info_not_finalized` to recompute the right child's congestion info by iterating the actual outgoing-buffer contents (as `bootstrap_congestion_info` does) rather than trusting `ReceiptGroupsQueue` totals to match `CongestionInfo` exactly, and replace the `.expect()` panics with a graceful, validated error path.

### Proof of Concept
Not independently reproducible from the indexed context alone: a full PoC would require (1) confirming `should_update_outgoing_metadatas()`'s exact exclusion condition, (2) constructing a transaction workload that buffers an excluded-kind receipt to a to-be-split shard, and (3) driving a ReshardingV3 shard split while that receipt remains buffered, then observing either the `.expect()` panic in `get_child_congestion_info_not_finalized` or a divergent `CongestionInfo` on the resulting child shard. This step could not be completed within the available tooling/index and should be validated with a live checkout of the repository (e.g., via a Devin session) before treating this as a confirmed, exploitable vulnerability.

    pub fn update_on_receipt_pushed(
        &mut self,
        receipt_size: ByteSize,
        receipt_gas: Gas,
        state_update: &mut TrieUpdate,
        groups_config: &ReceiptGroupsConfig,
    ) -> Result<(), StorageError> {
        add_size_checked(&mut self.data.total_size, receipt_size);
        add_gas_checked(&mut self.data.total_gas, receipt_gas);
        self.data.total_receipts_num = self
            .data
            .total_receipts_num
            .checked_add(1)
            .expect("Overflow! - Number of receipts doesn't fit into u64!");

        // Take out the last group from the queue and inspect it.
        match self.pop_back(state_update)? {
            Some(mut last_group) => {
                if groups_config.should_start_new_group(&last_group, receipt_size, receipt_gas) {
                    // Adding the new receipt to the last group would make the group too large.
                    // Start a new group for the receipt.
                    self.push_back(state_update, &last_group).expect("Integer overflow on push");
                    self.push_back(state_update, &ReceiptGroup::new(receipt_size, receipt_gas))
                        .expect("Integer overflow on push");
                } else {
                    // It's okay to add the new receipt to the last group, do it.
                    add_size_checked(last_group.size_mut(), receipt_size);
                    add_gas_checked(last_group.gas_mut(), receipt_gas);
                    self.push_back(state_update, &last_group).expect("Integer overflow on push");
                }
            }
            None => {
                // No groups in the queue, start a new group which contains the new receipt.
                self.push_back(state_update, &ReceiptGroup::new(receipt_size, receipt_gas))
                    .expect("Integer overflow on push");
            }
        }

        Ok(())
    }

    pub fn update_on_receipt_popped(
        &mut self,
        receipt_size: ByteSize,
        receipt_gas: Gas,
        state_update: &mut TrieUpdate,
    ) -> Result<(), StorageError> {
        subtract_size_checked(&mut self.data.total_size, receipt_size);
        subtract_gas_checked(&mut self.data.total_gas, receipt_gas);

        self.data.total_receipts_num = self
            .data
            .total_receipts_num
            .checked_sub(1)
            .expect("Underflow! - More receipts were popped than pushed!");

        assert!(self.data.indices.len() > 0, "No receipt groups to pop from!");

        self.modify_first(state_update, |mut first_group| {
            subtract_size_checked(first_group.size_mut(), receipt_size);
            subtract_gas_checked(first_group.gas_mut(), receipt_gas);
            if first_group.is_empty() {
                // No more receipts in the first group, remove it.
                None
            } else {
                // Still some receipts in the group. Save the updated group.
                Some(first_group)
            }
        })
    }

    // Get the congestion info for the child shard. The congestion info can be
    // inferred efficiently from the combination of the parent shard's
    // congestion info and the receipt group metadata, that is available in the
    // parent shard's trie.
    fn get_child_congestion_info_not_finalized(
        parent_trie: &dyn TrieAccess,
        parent_shard_layout: &ShardLayout,
        parent_congestion_info: CongestionInfo,
        retain_mode: RetainMode,
    ) -> Result<CongestionInfo, Error> {
        // The left child contains all the delayed and buffered receipts from the
        // parent so it should have identical congestion info.
        if retain_mode == RetainMode::Left {
            return Ok(parent_congestion_info);
        }

        // The right child contains all the delayed receipts from the parent but it
        // has no buffered receipts. It's info needs to be computed by subtracting
        // the parent's buffered receipts from the parent's congestion info.
        let mut congestion_info = parent_congestion_info;
        for shard_id in parent_shard_layout.shard_ids() {
            let receipt_groups = ReceiptGroupsQueue::load(parent_trie, shard_id)?;
            let Some(receipt_groups) = receipt_groups else {
                continue;
            };

            let bytes = receipt_groups.total_size();
            let gas = receipt_groups.total_gas();

            congestion_info
                .remove_buffered_receipt_gas(gas)
                .expect("Buffered gas must not exceed congestion info buffered gas");
            congestion_info
                .remove_receipt_bytes(bytes)

### 5. Congestion control math (NEP-539)

`CongestionControl::congestion_level` (`congestion_info.rs:44`) is the **max** of four
fractions, each clamped to [0,1] (`clamped_f64_fraction`, `:474`):

- incoming = `delayed_receipts_gas / max_congestion_incoming_gas` (`:331`)
- outgoing = `buffered_receipts_gas / max_congestion_outgoing_gas` (`:338`)
- memory = `receipt_bytes / max_congestion_memory_consumption` (`:345`)
- missed-chunks = `missed_chunks_count / max_congestion_missed_chunks`, but 0 when
  `missed_chunks_count <= 1` (`:68`)

`outgoing_gas_limit(sender_shard)` (`:80`) drives how much a given sender may forward
to this shard next block:

- **Fully congested** (`congestion_level == 1.0`, `is_fully_congested`, `:95`): only
  the `allowed_shard` may send, and only `allowed_shard_outgoing_gas`; every other
  shard gets `Gas::ZERO` (`:83-89`). This is the "red light" that guarantees progress
  while stopping unbounded growth.
- Otherwise: linearly interpolate between `max_outgoing_gas` and `min_outgoing_gas` by
  the congestion level via `mix_gas` (`:91`, `mix` at `:484` works in integer space to
  avoid f64 precision loss at high gas).

`outgoing_size_limit` (`:103`) gives the allowed shard `outgoing_receipts_big_size_limit`
and everyone else `outgoing_receipts_usual_size_limit` (used as bandwidth-request
context, not the primary size gate — that is the bandwidth grant).

**Transaction admission**: `shard_accepts_transactions` (`:123`) rejects new
transactions targeting this shard once `congestion_level >=
reject_tx_congestion_threshold` (default 0.8, asserted in tests at `:641`), reporting
which of the four dimensions caused it (`RejectTransactionReason`, `:161`).
`process_tx_limit` (`:115`) throttles gas spent converting new transactions to
receipts using only the *incoming* congestion.
