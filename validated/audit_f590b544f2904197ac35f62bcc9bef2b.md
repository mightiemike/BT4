### Title
Storage row-key truncation in `Storage#compose` causes distinct SSTORE keys with identical low-128-bits to alias to the same persisted `StorageRowCapsule` - (File: actuator/src/main/java/org/tron/core/vm/program/Storage.java)

### Summary
`Storage#compose(byte[] key, byte[] addrHash)` builds the persisted row key by concatenating only the first 16 bytes of `addrHash` with the last 16 bytes of `key`, discarding the first 16 bytes of `key` entirely whenever `contractVersion != 1` (i.e., the raw, un-hashed key path). Two distinct 32-byte storage keys that share the same last 16 bytes but differ in their first 16 bytes therefore compose to the identical `rowKey`, and `StorageRowStore` will persist the later `SSTORE` on top of the earlier one, corrupting the first logical slot.

### Finding Description
`Storage.put(DataWord key, DataWord value)` caches new writes in `rowCache` keyed by the *raw* `DataWord key` [1](#0-0) , so two different keys `key_x` and `key_y` are tracked as separate cache entries during execution. However each cached `StorageRowCapsule` stores its persistence key via `compose()`: [2](#0-1) 

When `contractVersion != 1`, `key` is used unhashed, and `result[16:32] = key[16:32]` while `result[0:16] = addrHash[0:16]` — the first 16 bytes of `key` never enter the composed row key at all. If `key_x[16:32] == key_y[16:32]`, then `compose(key_x, addrHash) == compose(key_y, addrHash)` regardless of `key_x[0:16]` vs `key_y[0:16]`.

On `commit()`, each dirty cache entry is flushed independently to the underlying `StorageRowStore` using `row.getRowKey()` [3](#0-2) . Since both entries share the same composed `rowKey`, the second `put` to the store overwrites the first — even though the two `SSTORE` operations targeted logically distinct 32-byte keys. In a subsequent transaction, `getValue()` for `key_x` will miss the (per-tx) `rowCache` and fetch from `store.get(compose(key_x, addrHash))`, returning the value that was actually written for `key_y`.

This is a genuine key-truncation/aliasing defect in the compose scheme, not a hash-preimage attack: when `contractVersion != 1`, the attacker fully controls the raw key bytes (e.g., via inline assembly `sstore`), so crafting two keys with identical low 16 bytes but different high 16 bytes requires no computation at all.

I was unable to fully confirm in this session what conditions actually produce `contractVersion != 1` for an attacker-deployable contract (i.e., whether this is limited to legacy/pre-upgrade contracts or reachable by any newly deployed contract), since `Program.java`'s use of `contractVersion` and the `RepositoryImpl`/`VMActuator` wiring were not fully traced before running out of iterations. This precondition materially affects real-world exploitability and should be verified.

### Impact Explanation
If reachable, an attacker-controlled contract could cause one logical storage slot (e.g., a balance/allowance mapping slot manipulated via raw assembly `sstore`) to be silently overwritten by a second unrelated `SSTORE`, or could make two logically distinct slots resolve to the same persisted value, enabling value corruption/duplication within that contract's own storage (e.g., in a hand-rolled token contract using non-standard, non-keccak-derived storage slots).

### Likelihood Explanation
Exploitability hinges entirely on whether `contractVersion != 1` is attacker-reachable for arbitrary deployed contracts. If it is only set for legacy pre-fork contracts and cannot be chosen by a new attacker deployment, the practical attack surface is limited to affecting the attacker's own contract's storage (self-corruption), not third-party contracts, since crafting a collision against a *victim* contract's specific keccak-derived mapping slot (version 1 path) would still require a ~2^128 preimage search. This could not be conclusively resolved with the available context.

### Recommendation
Change `compose()` to derive the row key from a full-width hash of `(addrHash, key)` (e.g., `Hash.sha3(ByteUtil.merge(addrHash, key))`) instead of naively splicing 16 bytes from each input, ensuring the composed key is a function of the *entire* 32-byte logical key, not just its low 128 bits.

### Proof of Concept
```java
// actuator/src/test/java/org/tron/core/vm/program/StorageAliasTest.java
@Test
public void testStorageKeyAliasingCollision() {
  byte[] address = randomAddress();
  StorageRowStore store = mockStorageRowStore();
  Storage storage = new Storage(address, store);
  storage.setContractVersion(0); // raw-key path

  byte[] suffix = repeat((byte) 0xAB, 16); // shared low 16 bytes
  byte[] keyXBytes = concat(repeat((byte) 0x01, 16), suffix);
  byte[] keyYBytes = concat(repeat((byte) 0x02, 16), suffix);

  DataWord keyX = new DataWord(keyXBytes);
  DataWord keyY = new DataWord(keyYBytes);
  DataWord v1 = new DataWord(1);
  DataWord v2 = new DataWord(2);

  storage.put(keyX, v1);
  storage.put(keyY, v2);
  storage.commit();

  // Fresh Storage instance simulating a new transaction, forcing store lookup
  Storage storage2 = new Storage(address, store);
  storage2.setContractVersion(0);
  DataWord readBack = storage2.getValue(keyX);

  // Expected: readBack.equals(v1) — but due to compose() truncation,
  // readBack actually equals v2, proving aliasing/corruption.
  assertEquals(v1, readBack);
}
```
Expected result if the bug is present: the assertion fails because `keyX`'s persisted value was overwritten by `keyY`'s write, confirming the aliasing described.
