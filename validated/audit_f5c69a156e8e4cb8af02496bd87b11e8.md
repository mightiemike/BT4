`ensure_match_transaction_info()` skips checkpoint-hash validation, letting replay-verify accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the single-source-of-truth comparator used by both replay/verify tooling (`db-tool`, `backup-cli`'s `replay_on_archive`) and `execution/executor`'s `verify_execution` chunk-replay path to confirm that a freshly re-executed `TransactionOutput` matches the authenticated on-chain `TransactionInfo`. It checks status, gas, write-set hash (`state_change_hash`) and event-root hash, but by its own documented admission it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The function validates four things — status, gas used, write-set hash against `state_change_hash()`, and event root hash — and then returns `Ok(())` unconditionally, with an inline TODO stating the gap explicitly: [2](#0-1) 

This comment is the code's own acknowledgment that `state_checkpoint_hash`, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` — the fields that authenticate the actual Merkle root of the global state tree(s) at that version — are never compared to the recomputed ones. This function is called from two real, non-test code paths:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution()`, part of the chunk executor's execution-verification mode used during state-sync/replay of pre-recorded chunks: [3](#0-2) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches()`, used by db-tool / debugger tooling to diagnose divergence.
- `aptos-move/cli/src/commands.rs` (one match, tooling use).

Because none of these callers independently verify the state/hot-state/position-state checkpoint hash before or after calling `ensure_match_transaction_info`, if VM execution produces a correct write set/events/gas/status but an incorrect state root (e.g., due to a state-tree construction bug, a bug in the position/trading-native subsystem, or an incorrect state key computation that still lands the same aggregate write set hash but different post-application merkle root), the mismatch is invisible to this comparator.

### Impact Explanation
This directly violates the Proof And Storage Pivot requirement that "Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding," and it matches the accepted impact class "Hard-fork-only divergence during commit, replay, restore, or proof verification." Concretely:
- `db-tool`'s replay-verify (used to validate archived history / detect consensus bugs across the network) can report a clean, successful replay even when the locally recomputed state root diverges from the authenticated on-chain state root.
- The chunk executor's execution-verification mode (`verify_execution_mode.should_verify()`), used when state-syncing/verifying chunks against a backup or peer, would similarly accept the chunk without confirming that its own recomputed post-commit state root matches the state root committed to the ledger.
- This does not corrupt the actual committed ledger state on a live validator (the "hot path" `DoStateCheckpoint`/commit logic is separate and presumably still checks known checkpoint hashes on commit), but it removes the safety net that would otherwise let operators, auditors, or automated CI detect a state-divergence bug (including a consensus-breaking / hard-fork-class bug) before or after the fact via replay-verify — precisely the "authenticated API or state-view output bound to the wrong version/root" and "hard-fork-only divergence during replay/proof verification" categories called out as in-scope.

### Likelihood Explanation
The gap is on every execution-verification/replay-verify invocation covering `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields — it is not conditional on attacker behavior, and the code comment confirms it is a known, currently-unaddressed gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating the authors are aware this must be fixed before the trading-native/position-state feature is safe to rely on for verification. Because `compute_trading_native_state_roots` and `hot_state_root_in_txn_info` are already wired through `chunk_executor` and `TransactionInfo` (see `execution/executor/src/chunk_executor/mod.rs` lines ~380–394), the feature surface exists today even if not fully enabled, making this a real, currently reachable code path rather than dead code.

### Recommendation
Extend `ensure_match_transaction_info()` to also recompute and compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()` (when applicable), and `position_state_checkpoint_hash()` (when `compute_trading_native_state_roots` is enabled) against the values carried in `txn_info`, failing the same way as the existing checks (`ensure!` with a descriptive error) so that replay-verify and chunk-execution-verification cannot silently pass when the state root diverges.

### Proof of Concept
Not independently reproducible from static analysis alone: exploiting this gap requires an underlying bug elsewhere (e.g., in trading-native/position-state root computation, or hot-state merkle computation) that produces a wrong state root while keeping write-set/event/gas/status identical, so that `ensure_match_transaction_info` still returns `Ok(())`. What is proven locally is the code's own inline TODO and the four-check body of `ensure_match_transaction_info` that omits all checkpoint-hash comparisons [1](#0-0) , plus its live call sites in `chunk_executor::verify_execution` [3](#0-2)  and `aptos-debugger::print_mismatches`.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
