Based on the investigation, the strongest analog found relates to the difference between the Cairo1 (new) and Cairo0 (deprecated) syscall array-reading paths in the blockifier.

### Title
Unbounded allocation from an attacker-controlled length felt in the deprecated (Cairo0) syscall calldata/array reader - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
`read_felt_array` in the deprecated (Cairo0) syscall hint processor reads an `array_size` value directly as a raw felt from Cairo VM memory and converts it to a `usize` to read a range of that many felts, with no upper bound check against the amount of data actually present. This is structurally the same class of bug as the reported `russh` issue (CVE-2024-43410): a length value taken from untrusted, attacker-influenced input is used to drive an allocation/read before any sanity check is performed.

### Finding Description
In the Cairo1 syscall path, `read_felt_array` (`crates/blockifier/src/execution/syscalls/hint_processor.rs:860-879`) computes the array length as the difference between two `Relocatable` pointers already present in VM memory (`array_data_end_ptr - array_data_start_ptr`), which is implicitly bounded by real memory layout. [1](#0-0) 

In contrast, the deprecated (Cairo0) `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:931-949`) reads `array_size` as a raw felt directly from the VM (`felt_from_ptr`), converts it with `usize::try_from(array_size.to_biguint())`, and passes that untrusted value straight into `felt_range_from_ptr` to read/allocate the requested number of elements — with no comparison against the size of the underlying calldata/memory segment before the read/allocation is attempted. [2](#0-1) 

This function is used by `read_calldata`/`read_call_params`, which back the `call_contract`, `library_call`, and `deploy` Cairo0 syscalls — syscalls invocable by any account or contract that a user deploys/declares and calls. [3](#0-2) 

### Impact Explanation
If `felt_range_from_ptr` performs an eager allocation (e.g., `Vec::with_capacity`/similar) sized by the attacker-supplied `array_size` before validating that the corresponding memory actually contains that many felts, a contract can supply an arbitrarily large size value (up to `usize::MAX` on 64-bit platforms, since the felt is only truncated by `usize::try_from`) as part of a legitimate syscall request. This could cause an out-of-memory abort of the sequencer/executor process, i.e., a DoS analogous to the `russh` issue, triggered by any unprivileged transaction that deploys/calls such a Cairo0 contract.

### Likelihood Explanation
I could **not** directly confirm the implementation of `felt_range_from_ptr` (declared in `crates/blockifier/src/execution/execution_utils.rs`, but its body was not returned by my searches within the remaining tool budget). Whether this is actually exploitable depends entirely on whether that function eagerly allocates a buffer sized by the requested length before verifying the corresponding VM memory segment actually holds that many elements, or whether cairo-vm's memory access APIs reject out-of-range reads cheaply without a large allocation. Given the standard `Vec::with_capacity(len)`-then-fill pattern seen elsewhere in this codebase (e.g., `apollo_storage/src/serialization/serializers.rs:855-862`, `apollo_cairo_utils` before its fix) and in cairo-vm's typical `get_range`-style helpers, this is a plausible but **unconfirmed** vector.

### Recommendation
Verify the implementation of `felt_range_from_ptr` in `crates/blockifier/src/execution/execution_utils.rs`. If it allocates a buffer using the caller-supplied length before validating the request against the real segment size, bound `array_size` in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs::read_felt_array` (mirroring the `SIERRA_ARRAY_LEN_BOUND`-style checks used elsewhere, e.g., in `execute_entry_point.cairo`) before performing the read, or ensure the underlying VM read fails cheaply (without large allocation) when the requested range exceeds actual memory content.

### Proof of Concept
Not constructed — a concrete PoC would require confirming `felt_range_from_ptr`'s allocation behavior, which I was unable to inspect within the available tool calls. Given the size of the sequencer codebase and the index limits noted for this session, I recommend a Devin session with full repository/terminal access to (1) read the full body of `felt_range_from_ptr`, and (2) if it confirms unbounded pre-allocation, write a Cairo0 contract that issues a `library_call`/`call_contract` syscall with a maliciously large declared calldata/array size to validate OOM behavior in a test harness.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
