### Title
Webhook `shop` domain header is not bound to the HMAC signature, enabling cross-tenant session hijack via header spoofing - (File: `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts`)

### Summary
The webhook `authenticate` function trusts the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value to look up and attach an offline session/admin client, but the HMAC signature that "validates" the request only covers the raw request body, never the shop domain (or topic) header. Since a single `apiSecretKey` is shared by every shop that has the app installed, any party who can obtain one valid `(rawBody, hmac)` pair for the app (e.g. from a webhook legitimately delivered to their own installed shop) can replay that exact body/HMAC pair while substituting the domain header of a different, victim shop that also has the app installed, causing the library to attach the victim shop's real offline session/admin client to attacker-controlled payload processing.

### Finding Description
In `authenticateWebhookFactory`'s `authenticate` function, the raw body is read and passed to `api.webhooks.validate`, which internally calls `validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts`. That validator computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)` and compares it against the `X-Shopify-Hmac-Sha256` header using `safeCompare`: [1](#0-0) 

Critically, only `rawBody` is signed — the shop domain and topic headers are never part of the HMAC input. Those fields are extracted independently, straight from attacker-visible/attacker-suppliable request headers, in `checkWebhooksHeaders`/`checkEventsHeaders`: [2](#0-1) 

Back in `authenticate.ts`, once `check.valid` is true, `check.domain` (the unauthenticated header value) is passed directly into `ensureValidOfflineSession`, which loads the real offline session/access token for that shop and, if found, builds a live `admin` client bound to it: [3](#0-2) [4](#0-3) 

`ensureValidOfflineSession` performs no check that `shop` was cryptographically tied to the request — it just loads whatever session exists in storage for that shop string: [5](#0-4) 

Because `apiSecretKey` is one shared app-level secret used to sign webhooks for *every* shop that installs the app (not a per-shop secret), any merchant/customer who legitimately receives one valid webhook to their own shop (or otherwise obtains a `(rawBody, hmac)` pair, e.g., by triggering an event on their own store) possesses a body+HMAC pair that is valid for the app regardless of which shop's domain header accompanies it. That attacker can then POST the same `rawBody` and `hmac` to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different, victim shop that also has the app installed. `validateHmacString` still succeeds (body unchanged, HMAC recomputed only over body), `check.domain` becomes the attacker-chosen victim shop, and the library resolves and attaches the victim's real offline session/admin client — handing the attacker-controlled payload processing (and any handler logic keyed off `shop`) the identity and admin API access of the victim shop.

### Impact Explanation
This breaks the intended invariant that the shop identity returned to the webhook handler is cryptographically bound to the signed request. An attacker can force the app's webhook business logic to run with a victim shop's session/admin client while supplying their own chosen payload content (limited to whatever a body they can generate an HMAC for — trivially their own shop's real webhook body/topic, or a body/topic combination they can arrange to be delivered to themselves). Depending on what the app's webhook handlers do with `shop`, `topic`, and `payload` (e.g. write/delete data via `admin`, mark orders fulfilled, trigger downstream actions), this enables cross-tenant state changes or data access under the victim's identity — matching the "cross-tenant webhook action" impact class.

### Likelihood Explanation
Preconditions: (1) the attacker has the app installed on their own shop (or otherwise possesses a valid `rawBody`/HMAC pair for the shared `apiSecretKey`), which is an "unprivileged" position — any merchant can install a public app; (2) the victim shop also has the app installed and has a stored offline session (true for essentially every installed app). No secrets, no app-developer role, and no non-default configuration are required — this stems purely from the fact that the shared HMAC only signs the body and the library trusts the domain header verbatim. It is reproducible with a simple crafted HTTP POST with real headers copied except for the domain.

### Recommendation
Do not treat the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header as trusted merely because the body HMAC is valid. Either (a) require the shop domain (and topic) to be part of the HMAC-signed material, or (b) cross-check the header-provided shop domain against an independently verified source (e.g., validate that the webhook subscription belongs to that shop through a Shopify API call, or bind webhook registration IDs to a specific shop at delivery-registration time) before using it to load a session/admin client. At minimum, warn/document that `check.domain` in `authenticate.ts` is not cryptographically authenticated and downstream handlers must not assume it is trustworthy without additional verification.

### Proof of Concept
```ts
// packages/apps/shopify-app-remix/src/server/authenticate/webhooks/__tests__/authenticate.spoof.test.ts
import {shopifyApp} from '../../..';
import {MemorySessionStorage} from '@shopify/shopify-app-session-storage-memory';
import {Session} from '@shopify/shopify-api';
import crypto from 'crypto';
import {APP_URL, testConfig} from '../../../__test-helpers';

function hmac(secret: string, body: string) {
  return crypto.createHmac('sha256', secret).update(body).digest('base64');
}

it('accepts a valid HMAC/body pair with a spoofed victim shop domain', async () => {
  const sessionStorage = new MemorySessionStorage();
  const shopify = shopifyApp(testConfig({sessionStorage}));

  // Victim shop already has the app installed (offline session exists)
  await sessionStorage.storeSession(
    new Session({
      id: 'offline_victim-shop.myshopify.com',
      shop: 'victim-shop.myshopify.com',
      state: 'test',
      isOnline: false,
      accessToken: 'victim-access-token',
    }),
  );

  const body = JSON.stringify({some: 'attacker-controlled-payload'});
  // Attacker computes this HMAC themselves, e.g. from a webhook legitimately
  // delivered to their OWN shop, since apiSecretKey is shared app-wide.
  const validHmac = hmac(shopify.config.apiSecretKey, body);

  const request = new Request(`${APP_URL}/webhooks`, {
    method: 'POST',
    body,
    headers: {
      'X-Shopify-Topic': 'app/uninstalled',
      'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com', // spoofed
      'X-Shopify-API-Version': '2023-01',
      'X-Shopify-Webhook-Id': '1234567890',
      'X-Shopify-Hmac-Sha256': validHmac,
    },
  });

  const ctx = await shopify.authenticate.webhook(request);

  // Attacker-controlled request results in the victim's real session/admin
  // client being attached, despite no relationship between attacker and victim.
  expect(ctx.shop).toBe('victim-shop.myshopify.com');
  expect(ctx.session?.accessToken).toBe('victim-access-token');
  expect(ctx.admin).toBeDefined();
});
```
