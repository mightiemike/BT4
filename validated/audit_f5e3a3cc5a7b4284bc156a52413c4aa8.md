### Title
Unbounded `responseCache.cache` growth with no maximum entry/size bound - (`core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
`responseCache.Fetch` and `responseCache.Set` insert entries keyed by `req.Hash()` (derived from method/URL/headers/body/workflowOwner) with no limit on the number of distinct keys or total memory the map can hold. Eviction only happens via time-based `DeleteExpired`, run periodically by `gatewayHandler` (`CleanUpPeriodMs`), so between sweeps the map can grow proportionally to the number of distinct cacheable `OutboundHTTPRequest`s processed.

### Finding Description
`responseCache.cache` is a plain `map[string]*cachedResponse` [1](#0-0) . `Fetch` stores a new entry for every unique `cacheKey := req.Hash()` when the response is cacheable (2xx/4xx) and `storeOnFetch` is true [2](#0-1) , and `Set` does the same directly [3](#0-2) . Neither function checks a maximum entry count, checks total cache size, or evicts anything (e.g., LRU) when inserting — the only removal path is `DeleteExpired`, which is purely TTL/time based and runs only on a periodic timer (`CleanUpPeriodMs`) from `gatewayHandler.Start` [4](#0-3) . Because the key is a hash of `Method`, `URL`, `Headers`, `Body`, and `workflowOwner`, an actor able to trigger outbound HTTP action requests with varying `URL`/`Body` (e.g. via templated trigger input feeding into the `OutboundHTTPRequest`) can generate arbitrarily many distinct cache keys, each occupying map storage until the next TTL sweep.

However, reaching `responseCache.Fetch`/`Set` requires going through the gateway's HTTP-action node-message path in `http_handler.go`, which is gated by `globalNodeRateLimiter` and `perNodeRateLimiters` on incoming node/workflow requests [5](#0-4) . This means the request source is not a fully unauthenticated, arbitrary internet caller — it is a workflow/DON-node-originated action (per the README's process flow: "Gateway receives HTTP action request from a workflow node") [6](#0-5) , subject to existing rate limits. I was not able to fully trace `http_handler.go`'s `HandleNodeMessage`/outbound-action dispatch code in this session to confirm the exact authorization boundary and rate-limit values, so the precise growth rate achievable per unit time (and whether it is effectively unbounded vs. merely elevated) is not fully verified.

### Impact Explanation
This is a real code-level gap: there is no maximum cache size, entry count cap, or per-entry size bound enforced anywhere in `Set`/`Fetch`/`DeleteExpired`. Given sufficient distinct, cacheable outbound HTTP request variants (achievable through workflow logic/templated bodies) issued faster than the TTL cleanup interval, the gateway process's memory used by `rc.cache` can grow well beyond what a single workflow's traffic would normally require, degrading gateway availability (memory-pressure DoS) — consistent with a MEDIUM scoped impact for a Chainlink bounty (resource-exhaustion within a single service component, not a full node compromise, key leak, or unauthorized transaction).

### Likelihood Explanation
Exploitability is gated by the existing `globalNodeRateLimiter`/`perNodeRateLimiters` on the gateway's node-message ingestion path, plus the requirement that requests come from a workflow able to issue `OutboundHTTPRequest`s with attacker-influenceable `Body`/`URL` content (not a fully anonymous internet caller). This reduces the practical growth rate compared to a truly unauthenticated endpoint, but does not eliminate it, since rate limiting bounds requests-per-second rather than the number of distinct cache keys, and TTL cleanup only runs periodically. The severity therefore depends on the configured rate limits and `OutboundRequestCacheTTLMs`/`CleanUpPeriodMs` values, which were not fully confirmed in this investigation.

### Recommendation
Add a maximum entry count (or approximate memory budget) to `responseCache`, evicting the oldest/least-recently-used entries (or rejecting new `Set`/`Fetch` stores) once the limit is reached, in addition to the existing TTL-based `DeleteExpired` sweep. Consider also bounding per-request `Body`/`Header` size before it becomes part of the cache key/value to limit per-entry memory footprint.

### Proof of Concept
Unit/load test plan for `core/services/gateway/handlers/capabilities/v2/response_cache_test.go`:
1. Construct a `responseCache` via `newResponseCache` with a realistic TTL (e.g., 10 minutes).
2. In a loop, call `cache.Set` (or `cache.Fetch` with `storeOnFetch=true`) with N distinct `OutboundHTTPRequest`s differing only by `Body` (e.g., `Body: []byte(fmt.Sprintf("payload-%d", i))`), each returning a cacheable status code (200).
3. Assert `len(cache.cache)` grows linearly with N and that no eviction occurs before `DeleteExpired` is invoked, even for large N (e.g., 100k+), demonstrating the absence of a size cap.
4. Optionally measure `runtime.MemStats` before/after the loop to quantify memory growth per entry, and compare against a fix that enforces a max-size/eviction policy (expected: map size plateaus at the configured cap instead of growing unbounded).

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}
```

func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
}
```
