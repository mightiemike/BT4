### Title
Pre-fork multisig double-counting via non-canonical (malleable) ECDSA signature encodings deduped by raw signature string instead of recovered address - (File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java)

### Summary
`TransactionCapsule.checkWeight` deduplicates signatures in a `HashMap` keyed by the base64-encoded raw signature bytes, and only switches the dedup key to the recovered address (`encode58Check(address)`) once `ForkController.instance().pass(VERSION_4_7_1)` is true. Before that fork activates, an attacker holding a single private key can submit two distinct raw signature byte-encodings over the same transaction hash (e.g. the malleable `(r, N-s, flipped-v)` counterpart) that both recover to the same address, so the weight for that one key is counted twice, letting a single key satisfy a multisig threshold meant to require multiple distinct signers.

### Finding Description
`TransactionCapsule.checkWeight` (chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:233-270) only rejects a signature if `sig.size() < 65` and never checks canonical `s` (`s <= HALF_CURVE_ORDER`) at this call site — unlike `ECKey.doSign`, which always canonicalizes via `toCanonicalised()` (crypto/src/main/java/org/tron/common/crypto/ECKey.java:770-791, 948-963), non-canonical signatures constructed directly by an attacker are never rejected here. `getBase64FromByteString` (TransactionCapsule.java:463-466) reconstructs the base64 string directly from the raw `(r, s, v)` bytes without canonicalizing `s`, so `(r, s, v)` and `(r, N-s, v')` produce two different base64 strings even though `ECKey.recoverPubBytesFromSignature` (ECKey.java:518-560+) will recover the identical public key/address for both, because ECDSA recovery is defined for both the canonical and non-canonical `s` provided the recovery id `v` is adjusted accordingly.

The dedup key logic is:
```java
String base64 = TransactionCapsule.getBase64FromByteString(sig);
byte[] address = SignUtils.signatureToAddress(hash, base64, ...);
...
if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
  base64 = encode58Check(address);
}
if (addMap.containsKey(base64)) {
  throw new PermissionException(...);
}
addMap.put(base64, weight);
...
currentWeight += weight;
```
(TransactionCapsule.java:248-267)

Before the fork passes, `base64` (the raw signature encoding) is the dedup key, not the recovered address. An attacker who signs once with their private key can derive the second, distinct-byte-encoding signature `(r, N-s mod N, v XOR 1)` purely algebraically (no private key knowledge beyond the one already-produced signature is needed — standard ECDSA malleability) that recovers to the same address. Both signatures pass the `weight == 0` check (same address, same key entry in `permission.getKeysList()`), both produce distinct `base64` strings, so `addMap.containsKey(base64)` is false for both, and `currentWeight` is incremented twice for what is effectively one signer.

This is reachable from real, unprivileged user-facing entry points that all funnel into `checkWeight`: `TransactionCapsule.validateSignature` (TransactionCapsule.java:468-496, used during transaction acceptance/block validation), `TransactionCapsule.addSign` (TransactionCapsule.java:597-633, used by wallet clients composing multisig transactions), `TransactionUtil.getTransactionSignWeight` (actuator/src/main/java/org/tron/core/utils/TransactionUtil.java:199-276, exposed via a public gRPC/HTTP API), and `Wallet.getTransactionApprovedList` (framework/src/main/java/org/tron/core/Wallet.java:632-702, also a public API). An attacker with a single active key under a multi-key permission (threshold > single key's weight) could submit a transaction with two malleable signature encodings of that one key and have it treated as satisfying the threshold as if two distinct authorized keys signed.

### Impact Explanation
If exploitable pre-fork, a single compromised/attacker-controlled key on a multisig permission could push `currentWeight` above `permission.getThreshold()` without a second legitimate signer's participation, allowing unauthorized execution of the underlying contract (transfer, vote, account update, etc.) as the multisig account — a direct authorization bypass with fund/value impact.

### Likelihood Explanation
The vulnerability is explicitly and intentionally scoped by the code itself to "ForkController has not yet passed VERSION_4_7_1." In the current codebase, this hard fork gate already exists as the fix, meaning this exact address-based dedup was added as a remediation for a previously-shipped, weaker signature-string-based dedup. On any network/branch/differential-test configuration where `VERSION_4_7_1` has not yet activated (a legitimate historical/pre-fork state, not merely test setup), the flawed base64-based dedup path is live and reachable by any user submitting a transaction/API call with signatures they craft. Exploitability further depends on whether upstream signature encoding validation (e.g., `SignUtils.isValidLength`, size checks in `TransactionUtil.truncateSignatures`/network ingress) rejects non-standard-length or non-canonical signatures before reaching `checkWeight` — the `SignUtils.isValidLength` comment explicitly documents that `checkWeight` intentionally uses a looser `size < 65` check and is not gated by the stricter admission-entry-point length check, indicating this consensus path was deliberately left permissive.

### Recommendation
Always dedupe by the recovered address, not by raw signature bytes, regardless of fork status: remove the `ForkController.instance().pass(VERSION_4_7_1)` conditional in `checkWeight` and instead unconditionally use `encode58Check(address)` (or the raw `address` bytes) as the `addMap` key. If backward-compatible behavior for un-forked chains must be preserved, canonicalize `s` before deriving `base64` for the pre-fork branch as well.

```java
  byte[] hash = Sha256Hash.hash(true, "test-tx".getBytes());

  // 2. Produce the canonical signature bytes.
  ECKey.ECDSASignature sig = key.doSign(hash); // canonicalized (r, s)
  byte[] sigBytes = /* build 65-byte r|s|v from sig, v = 27/28 */ ...;

  // 3. Derive the malleable counterpart: (r, N - s, flipped recovery id).
  BigInteger n = ECKey.CURVE.getN();
  BigInteger sMalleable = n.subtract(sig.s);
  byte vFlipped = (byte) (sigBytes[64] == 27 ? 28 : 27); // flip parity
  byte[] malleableSigBytes = /* build 65-byte r|sMalleable|vFlipped */ ...;

  List<ByteString> sigs = Arrays.asList(
      ByteString.copyFrom(sigBytes),
      ByteString.copyFrom(malleableSigBytes));

  // 4. Simulate pre-fork state: ensure ForkController.instance().pass(VERSION_4_7_1) == false
  //    (e.g. via test ForkController setup / DynamicPropertiesStore not yet activating the fork).

  List<ByteString> approveList = new ArrayList<>();
  long weight = TransactionCapsule.checkWeight(permission, sigs, hash, approveList);

  // Expected (correct) behavior: recovered address is identical for both signatures,
  // so weight should be capped at 1 and a PermissionException "has signed twice!" should be thrown.
  // Actual pre-fork behavior: no exception is thrown, weight == 2, satisfying threshold=2
  // with a single distinct key, and approveList incorrectly contains the same address twice.
  assertEquals(1, weight); // fails pre-fork, demonstrating the bug
  assertEquals(1, approveList.stream().distinct().count());
}
```
Assert that regardless of raw signature byte permutations, `currentWeight` never exceeds `getWeight(permission, address)` summed once per distinct recovered address (using `ByteArraySet`/`ByteArrayWrapper` address-content equality as the oracle) — the test should fail on the pre-fork code path and pass only once the fix (always dedupe by recovered address) is applied.
