## Analysis

This CL-2020-11 disclosure describes a class of bug where an elliptic-curve verification routine fails to reject the identity/infinity point, which nullifies the discrete-log binding of one operand (`x·O = O` for any `x`), letting the verifier accept proofs independent of the real secret.

I found a structurally identical gap in this repo's VRF verification, which is directly wired into Nakamoto sortition/tenure validation.

### Root cause

`VRF::verify` in [1](#0-0)  explicitly checks `proof.Gamma().is_small_order()` and rejects a degenerate `Gamma`, but never performs the equivalent check on `Y_point_ed` — the decompressed VRF **public key** used in the same equation (`U_point = s_reduced * B - proof.c() * Y_point_ed`).

The public key is only validated for being *some* valid curve point at construction time in `VRFPublicKey::from_bytes`, [2](#0-1) , which calls `decompress()` but performs no small-order/identity exclusion — unlike `Gamma`, which is explicitly filtered in `verify`.

This degenerate public key is freely attacker-controlled: `LeaderKeyRegisterOp::parse_data`, [3](#0-2) , accepts any bytes that pass `VRFPublicKey::from_bytes`, with no additional curve-subgroup check, and any unprivileged burnchain-transaction sender can register a leader key this way.

Because `curve25519_dalek` scalar multiplication does not reduce the scalar modulo the point's own (small) order, when `Y_point_ed` lies in the 8-element torsion subgroup, `proof.c() * Y_point_ed` depends only on `proof.c() mod ord(Y_point_ed)` (1, 2, 4, or 8) rather than the full challenge. This breaks the intended one-to-one binding between the registered public key, the input `alpha`, and the unique valid proof — the core "uniqueness" property VRFs are supposed to guarantee — allowing multiple distinct `(Gamma, c, s)` triples to verify for the same key/input.

This VRF-verify equation is exactly what gates block/tenure acceptance:
- `StacksBlockHeader::validate_vrf`-style checks in [4](#0-3) 
- `NakamotoChainState::check_normal_coinbase_tx`, [5](#0-4) 

Both ultimately call `VRF::verify(leader_vrf_key, proof, sortition_hash)` to determine if a tenure-start block's VRF seed legitimately came from the sortition winner's registered key.

### Title
Missing small-order/identity check on VRF public key breaks proof uniqueness in `VRF::verify` — (File: stacks-common/src/util/vrf.rs)

### Summary
`VRF::verify` rejects a degenerate (small-order) `Gamma` point but never rejects a degenerate registered public key (`Y_point`). A registered VRF key in the 8-element torsion subgroup lets an attacker construct multiple distinct valid VRF proofs for the same sortition input, breaking the VRF's uniqueness guarantee that Nakamoto tenure/coinbase validation depends on.

### Finding Description
`VRF::verify` computes `U_point = s_reduced * B - proof.c() * Y_point_ed` and `V_point = s_reduced * H - proof.c() * proof.Gamma()`, then checks `c_prime(H, Gamma, U, V) == c`. It explicitly guards against a degenerate `Gamma` (`proof.Gamma().is_small_order()`) but performs no equivalent guard on `Y_point_ed`, the decompressed public key. `VRFPublicKey::from_bytes` only checks that the bytes decompress to *a* valid curve point, not that the point is outside the small (order ≤ 8) torsion subgroup. `LeaderKeyRegisterOp::parse_data` accepts any such key with no further validation, and any unprivileged burnchain sender can register it as their VRF leader key. When `Y_point_ed` is chosen from the torsion subgroup, `proof.c() * Y_point_ed` collapses to depend only on `proof.c() mod ord(Y_point_ed)`, decoupling the challenge scalar from the registered key across multiple candidate proofs, so several distinct `(Gamma, c, s)` proof triples can pass verification for the same key and input.

### Impact Explanation
This breaks the equality the sortition/tenure machinery relies on: "exactly one VRF proof legitimately attests that this sortition-winning leader produced this tenure's seed." Multiple crafted proofs for one registered (degenerate) key let a minority attacker (a single miner registering one malformed leader key) bias/grind the derived `VRFSeed` used by `BlockSnapshot::sample_burn_distribution` for subsequent sortitions, producing a minority-triggerable VRF/sortition divergence rather than requiring majority collusion. This matches the "High: minority-triggerable sortition/VRF/static-validation divergence" impact class.

### Likelihood Explanation
Registration requires only submitting a standard `LeaderKeyRegisterOp` burnchain transaction with a crafted low-order public key — no special privilege, no majority stake, and no cooperation from other nodes is required. The missing check is a straightforward oversight relative to the existing (but incomplete) `is_small_order()` guard applied only to `Gamma`.

### Recommendation
Add an explicit check in `VRF::verify` (and ideally in `VRFPublicKey::from_bytes`/leader-key registration validation) rejecting any public key point that is small-order (in the 8-element torsion subgroup), mirroring the existing `proof.Gamma().is_small_order()` check, e.g. `if Y_point_ed.is_small_order() { return Err(Error::InvalidPublicKey); }` immediately after decompression.

### Proof of Concept
1. Craft a 32-byte compressed Edwards point `Y` that decompresses to a nonzero small-order torsion point (order 2, 4, or 8) — such points are publicly known/computable and pass `CompressedEdwardsY::decompress()`.
2. Submit a `LEADER_KEY_REGISTER` burnchain transaction with `Y` as the proving public key; `LeaderKeyRegisterOp::parse_data` accepts it since `VRFPublicKey::from_bytes` only checks decompression succeeds.
3. Craft two different tuples `(Gamma_1, c_1, s_1)` and `(Gamma_2, c_2, s_2)` (with `c_1 ≠ c_2 mod ord(Y)`'s complement structure) that both satisfy `c' = hash_points(H, Gamma, U, V)` for the same `alpha`/sortition hash, exploiting that `c_i * Y` only depends on `c_i mod ord(Y)`.
4. Both proofs pass `VRF::verify`, yielding two different `VRFSeed::from_proof` values for the same registered key/input, letting the miner select whichever seed is more favorable for the next sortition round — violating the single-valid-proof invariant relied on by `check_normal_coinbase_tx` / `validate_vrf_seed`.

    pub fn verify(Y_point: &VRFPublicKey, proof: &VRFProof, alpha: &[u8]) -> Result<bool, Error> {
        let H_point = VRF::hash_to_curve(Y_point, alpha);
        let s_reduced = proof.s();
        let Y_point_ed = CompressedEdwardsY(Y_point.to_bytes())
            .decompress()
            .ok_or(Error::InvalidPublicKey)?;
        if proof.Gamma().is_small_order() {
            return Err(Error::InvalidPublicKey);
        }

        let U_point = s_reduced * &ED25519_BASEPOINT_POINT - proof.c() * Y_point_ed;
        let V_point = s_reduced * &H_point - proof.c() * proof.Gamma();

        let c_prime_hashbuf = VRF::hash_points(&H_point, proof.Gamma(), &U_point, &V_point);
        let Some(c_prime) = VRF::ed25519_scalar_from_hash128(&c_prime_hashbuf) else {
            return Err(Error::InvalidHashPoints);
        };

        // NOTE: this leverages constant-time comparison inherited from the Scalar impl
        Ok(c_prime == *(proof.c()))
    }

    /// Verify that if this block has a coinbase, that its VRF proof is consistent with the leader
    /// public key's VRF key. If there is no coinbase tx, then this is a no-op.
    fn check_normal_coinbase_tx(
        &self,
        leader_vrf_key: &VRFPublicKey,
        sortition_hash: &SortitionHash,
    ) -> Result<(), ChainstateError> {
        assert!(!self.is_shadow_block());

        // If this block has a coinbase, then verify that its VRF proof was generated by this
        // block's miner.  We'll verify that the seed of this block-commit was generated from the
        // parnet tenure's VRF proof via the `validate_vrf_seed()` method, which requires that we
        // already have the parent block.
        if let Some(coinbase_tx) = self.get_coinbase_tx() {
            let (_, _, vrf_proof_opt) = coinbase_tx
                .try_as_coinbase()
                .expect("FATAL: `get_coinbase_tx()` did not return a coinbase");

            let vrf_proof = vrf_proof_opt.ok_or(ChainstateError::InvalidStacksBlock(
                "Nakamoto coinbase must have a VRF proof".into(),
            ))?;

            // this block's VRF proof must have been generated from the last sortition's sortition
            // hash (which includes the last commit's VRF seed)
            let valid = match VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes()) {
                Ok(v) => v,
                Err(e) => {
                    warn!(
                        "Invalid Stacks block header {}: failed to verify VRF proof: {}",
                        self.header.block_hash(),
                        e
                    );
                    false
                }
            };

            if !valid {
                warn!("Invalid Nakamoto block: leader VRF key did not produce a valid proof";
                    "consensus_hash" => %self.header.consensus_hash,
                    "stacks_block_hash" => %self.header.block_hash(),
                    "stacks_block_id" => %self.header.block_id(),
                    "leader_public_key" => %leader_vrf_key.to_hex(),
                    "sortition_hash" => %sortition_hash
                );
                return Err(ChainstateError::InvalidStacksBlock(
                    "Invalid Nakamoto block: leader VRF key did not produce a valid proof".into(),
                ));
            }
        }
