### Title
Imprecise floating-point brokerage/reward fee split in `MortgageService.payReward` and `payStandbyWitness` causes systematic under-payment of witness rewards - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payReward` and `payStandbyWitness` compute a fee-style split (witness brokerage cut / per-vote reward share) using `double` arithmetic and truncating casts to `long`, analogous to the Juicebox `_feeAmount` finding where an imprecise fee formula produced systematically lower fees than the protocol intended.

### Finding Description
`payReward` derives the brokerage cut from a witness's `brokerage` percentage using floating point: [1](#0-0) 
```
double brokerageRate = (double) brokerage / 100;
long brokerageAmount = (long) (brokerageRate * value);
```
Instead of an integer-safe formula (e.g. `value * brokerage / 100` computed in `long`/`BigInteger`), the code converts the percentage to a `double` ratio and multiplies, then truncates towards zero via the `(long)` cast. This is structurally the same failure mode as the referenced Juicebox bug: an "approximate" formula is substituted for the exact integer proportion, and the result is always rounded down, never up, so the computed brokerage/witness reward is systematically less than the mathematically correct value.

The same pattern appears in `payStandbyWitness`, where the total reward pool is split across witnesses by vote weight using `double eachVotePay` and a truncating cast per witness: [2](#0-1) 
```
double eachVotePay = (double) totalPay / voteSum;
for (WitnessCapsule w : witnessStandbys) {
  long pay = (long) (w.getVoteCount() * eachVotePay);
  payReward(w.getAddress().toByteArray(), pay);
```
Both the per-vote payout and the divide-by-100 brokerage ratio are subject to IEEE-754 rounding error and truncation, unlike the exact-fraction `BigInteger`-based approach already used elsewhere in the codebase for similar money-math (e.g. `RepositoryImpl.getUsage` and `EnergyProcessor.scaleByRate` both use `BigInteger.multiply().divide()` to avoid this exact class of error, guarded behind a "harden calculation" flag): [3](#0-2) 

By contrast, `payReward`/`payStandbyWitness` have no such hardened/BigInteger path at all — they unconditionally use `double`.

### Impact Explanation
Because the brokerage/reward split always truncates down rather than rounding to nearest, the witness (and the network reward pool that receives the complementary `value -= brokerageAmount`) reliably receives fractionally less than the exact percentage entitles them to. Over the lifetime of the chain, with rewards paid every block/cycle to every active and standby witness, this compounds into a real (if individually small) accounting shortfall against the intended tokenomics — directly matching the referenced bug class ("calculates less fees than anticipated"). This is a resource/reward accounting correctness issue in the consensus reward-distribution path, not a privileged-actor or off-chain issue: it affects every witness's/voter's on-chain payout on every reward cycle.

### Likelihood Explanation
This code executes on every block reward (`payBlockReward`), every transaction-fee reward (`payTransactionFeeReward`), and every maintenance-cycle standby-witness payout (`payStandbyWitness`), so the imprecision triggers continuously and deterministically for any non-trivial `brokerage` value or vote distribution — no attacker action is required, it's an inherent, always-reachable computation error.

### Recommendation
Replace the `double`-based ratio computations in `payReward` and `payStandbyWitness` with exact integer arithmetic (matching the pattern already used in `RepositoryImpl`/`EnergyProcessor`), e.g.:
```java
long brokerageAmount = BigInteger.valueOf(value)
    .multiply(BigInteger.valueOf(brokerage))
    .divide(BigInteger.valueOf(100))
    .longValueExact();
```
and similarly compute `pay = BigInteger.valueOf(voteCount).multiply(BigInteger.valueOf(totalPay)).divide(BigInteger.valueOf(voteSum)).longValueExact()` per witness in `payStandbyWitness`, so the shares are computed without floating-point rounding loss.

### Proof of Concept
Given `value = 1000`, `brokerage = 33` (33%):
- Correct integer result: `1000 * 33 / 100 = 330`.
- Current double-based result: `brokerageRate = 33.0/100 = 0.33` (not exactly representable in binary floating point), `brokerageAmount = (long)(0.33 * 1000)` — depending on floating point representation this can resolve to `329` instead of `330` due to the double product landing slightly below the exact integer boundary before truncation, silently under-paying the witness by 1 unit per call. Multiplied across every block reward and every voter of every witness across the network's lifetime, this produces a systematic, unrecoverable accounting shortfall, exactly analogous to the Juicebox `_feeAmount` under-collection bug.
