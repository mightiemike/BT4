### Title
Unbounded pre-metering computation in `LogBlockQuery.getPossibleBlock` allows RPC-API DoS via CPU/memory exhaustion before result-size rejection - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java])

### Summary
`LogBlockQuery.getPossibleBlock()` performs the entire bloom-filter matching computation — concurrent per-section DB fetches, BitSet AND/OR operations across all sections, and a full `nextSetBit` scan of the resulting BitSet — before checking whether the result size exceeds `MAX_RESULT` (10000). The `JsonRpcTooManyResultException` is thrown only after this expensive work has fully completed, so an attacker can repeatedly submit broad `eth_getLogs` queries that are guaranteed to be rejected, forcing the node to redo unbounded CPU/memory work on every request.

### Finding Description
In `LogBlockQuery.getPossibleBlock()` [1](#0-0) , the method:
1. Builds `allConditionsIndex` from the filter's addresses/topics.
2. Allocates a `BitSet blockNumBitSet` sized to the full section range (`maxSection - minSection + 1`) times `BLOCK_PER_SECTION`, and for every condition calls `subMatch()`, which itself submits concurrent per-bit-index DB lookups via `sectionExecutor` and `sectionBloomStore.get(section, bitIndex)` for every section in range [2](#0-1)  and [3](#0-2) .
3. ANDs all condition bitsets together (`blockNumBitSet.and(bitSet)`), then iterates every set bit with `nextSetBit` to build `blockNumList` [4](#0-3) .
4. Only after this full computation does it check `if (blockNumList.size() >= MAX_RESULT)` and throw `JsonRpcTooManyResultException` [5](#0-4) .

There is no early-exit/short-circuit: the bit-counting loop does not break once `MAX_RESULT` is reached, and the per-section bloom lookups/BitSet AND operations for the entire block range are always executed regardless of how many results will ultimately be returned. This violates a "reject-before-work" (FAITHFUL_METERING) invariant: the cost of the query (DB reads proportional to section count, BitSet operations proportional to range size) is paid in full even for queries that are guaranteed to be rejected.

### Impact Explanation
This is a resource-exhaustion / RPC-API DoS vector: an unauthenticated JSON-RPC client can repeatedly submit wildcard/wide-range `eth_getLogs` filters that are known in advance to match far more than `MAX_RESULT` blocks, forcing the node to repeatedly perform full bloom-section scans, concurrent DB fetches, and large `BitSet` allocations/operations, only to discard the entire result at the end. Repeating this in a tight loop can degrade RPC responsiveness and consume CPU/memory/thread-pool (`sectionExecutor`) resources on the node, corresponding to the "DoS via RPC-API" impact class.

### Likelihood Explanation
This requires only a default-configuration node exposing the JSON-RPC `eth_getLogs` endpoint, with no special privileges, keys, or funded account needed — a fully anonymous HTTP/JSON-RPC caller can trigger it repeatedly at will. The feasibility and severity depend on chain size and history depth (larger `maxSection - minSection` and more matched blocks worsen cost), which I could not fully quantify since I was unable to confirm within this investigation whether `LogFilterWrapper` or the JSON-RPC layer already enforces a maximum `fromBlock`/`toBlock` range (a config-driven range cap would bound, but not eliminate, the wasted work per rejected call). Given the confirmed code path, the vulnerability is real regardless of range capping, though its magnitude is uncertain without further inspection of `LogFilterWrapper`'s range validation logic.

### Recommendation
Add an early-exit check inside the bit-scanning loop in `getPossibleBlock()` so that once `blockNumList.size()` reaches `MAX_RESULT`, the loop (and outer per-section computation, if possible) breaks immediately and throws `JsonRpcTooManyResultException` without processing remaining sections/bits. Additionally, consider estimating potential result cardinality (e.g., total blocks in `[minBlock, maxBlock]`) before invoking `subMatch`/`partialMatch`, and reject queries whose block range alone exceeds a safe bound before doing any bloom lookups.

  public List<Long> getPossibleBlock() throws ExecutionException, InterruptedException,
      JsonRpcTooManyResultException {
    List<Long> blockNumList = new ArrayList<>();
    if (minBlock > currentMaxBlockNum) {
      return blockNumList;
    }

    int[][][] allConditionsIndex = getConditions();

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet blockNumBitSet = new BitSet(capacity);
    blockNumBitSet.set(0, capacity);

    // works serial
    for (int[][] conditionsIndex : allConditionsIndex) {
      BitSet bitSet = subMatch(conditionsIndex);
      blockNumBitSet.and(bitSet);
    }

    for (int i = blockNumBitSet.nextSetBit(0); i >= 0; i = blockNumBitSet.nextSetBit(i + 1)) {
      // operate on index i here
      if (i == Integer.MAX_VALUE) {
        break; // or (i+1) would overflow
      }
      long blockNum = (long) minSection * SectionBloomStore.BLOCK_PER_SECTION + i;
      if (minBlock <= blockNum && blockNum <= maxBlock) {
        blockNumList.add(blockNum);
      }
    }

    if (blockNumList.size() >= MAX_RESULT) {
      throw new JsonRpcTooManyResultException(
          "query returned more than " + MAX_RESULT + " results");
    }

    return blockNumList;
  }

  private BitSet subMatch(int[][] bitIndexes) throws ExecutionException, InterruptedException {

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet subBitSet = new BitSet(capacity);

    for (int section = minSection; section <= maxSection; section++) {
      BitSet partialBitSet = partialMatch(bitIndexes, section);

      for (int i = partialBitSet.nextSetBit(0); i >= 0; i = partialBitSet.nextSetBit(i + 1)) {
        // operate on index i here
        if (i == Integer.MAX_VALUE) {
          break; // or (i+1) would overflow
        }
        int offset = (section - minSection) * SectionBloomStore.BLOCK_PER_SECTION + i;
        subBitSet.set(offset);
      }
    }

    return subBitSet;
  }

  private BitSet partialMatch(final int[][] bitIndexes, int section)
      throws ExecutionException, InterruptedException {
    // 1. Collect all unique bitIndexes
    Set<Integer> uniqueBitIndexes = new HashSet<>();
    for (int[] index : bitIndexes) {
      for (int bitIndex : index) { //normally 3, but could be less due to hash collisions
        uniqueBitIndexes.add(bitIndex);
      }
    }

    // 2. Submit concurrent requests for all unique bitIndexes
    Map<Integer, Future<BitSet>> bitIndexResults = new HashMap<>();
    for (int bitIndex : uniqueBitIndexes) {
      Future<BitSet> future
          = sectionExecutor.submit(() -> sectionBloomStore.get(section, bitIndex));
      bitIndexResults.put(bitIndex, future);
    }

    // 3. Wait for all results and cache them
    Map<Integer, BitSet> resultCache = new HashMap<>();
    for (Map.Entry<Integer, Future<BitSet>> entry : bitIndexResults.entrySet()) {
      BitSet result = entry.getValue().get();
      if (result != null) {
        resultCache.put(entry.getKey(), result);
      }
    }


    // 4. Process valid groups with reused BitSet objects
    BitSet finalResult = new BitSet(SectionBloomStore.BLOCK_PER_SECTION);
    BitSet tempBitSet = new BitSet(SectionBloomStore.BLOCK_PER_SECTION);

    for (int[] index : bitIndexes) {

      // init tempBitSet with all 1
      tempBitSet.set(0, SectionBloomStore.BLOCK_PER_SECTION);

      // and condition in second dimension
      for (int bitIndex : index) {
        BitSet cached = resultCache.get(bitIndex);
        if (cached == null) { //match nothing
          tempBitSet.clear();
          break;
        }
        // "and" condition in second dimension
        tempBitSet.and(cached);
        if (tempBitSet.isEmpty()) {
          break;
        }
      }

      // "or" condition in first dimension
      if (!tempBitSet.isEmpty()) {
        finalResult.or(tempBitSet);
      }
    }

    return finalResult;
  }
