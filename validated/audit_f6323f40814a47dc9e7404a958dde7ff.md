### Title
Vote-reward accounting rounds to whole DPoS maintenance cycles, allowing a "flash-vote" to earn a full cycle's reward with negligible real holding time - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The vote-reward mechanism in java-tron (`MortgageService`/`VoteRewardUtil`, backed by `DelegationStore`'s per-witness `Vi` accumulator and driven by `MaintenanceManager.doMaintenance()`) computes rewards using cycle-granular snapshots (`getWitnessVi(cycle)`), not time-weighted balances. A voter's weight only affects reward computation for whichever discrete cycle it is batched into at the next maintenance event, and once "in", the vote is credited for the entire cycle regardless of how long it was actually held before or after the cycle boundary. This mirrors the LendingLedger H-01 pattern: reward eligibility is decided by which side of a rounding boundary an action falls on, not by actual duration held.

### Finding Description
Reward accrual is implemented with a per-cycle "Vi" (value-per-vote) ledger:
- `DelegationStore.accumulateWitnessVi()` / `RewardViCalService.accumulateWitnessVi()` accumulate `deltaVi = reward(cycle) * DECIMAL / voteCount(cycle)` once per cycle, called from `MaintenanceManager.doMaintenance()`: [1](#0-0) 
- `witness.getVoteCount()` used inside that same maintenance call is the value **as it stood before** this maintenance's own vote-count update (the `countWitness.forEach(...)` block that applies newly-cast/cleared votes runs immediately **after** `accumulateWitnessVi`): [2](#0-1) 
- A user's actual reward is then computed as a delta between two whole-cycle `Vi` snapshots multiplied by their vote count, in `MortgageService.computeReward` / `VoteRewardUtil.computeReward`: [3](#0-2) [4](#0-3) 

Because vote/unvote actions recorded any time within a cycle are all batched and applied together at the next maintenance boundary (`VoteWitnessProcessor.execute()` / `VoteWitnessActuator` just record vote deltas into account/`VotesStore`, they don't immediately affect `witness.getVoteCount()`): [5](#0-4)  — the exact timing of a vote or an unvote **inside** a cycle is irrelevant to when it starts/stops counting. It only matters which cycle-boundary bucket it lands in. The consequence: once a vote's weight becomes registered into `witness.getVoteCount()` (which happens uniformly at the maintenance that ends the cycle in which the vote was cast, updated in the `countWitness.forEach` block after `accumulateWitnessVi` had already been called), that entire weight is used, unreduced, when the NEXT cycle's `Vi` is accumulated at the following maintenance — even if the user submits a clear-vote/unvote transaction in the very first block of that next cycle. The clear-vote delta is only applied to `witness.getVoteCount()` at the *end* of that cycle (again after `accumulateWitnessVi` runs), so it cannot reduce the weight used to compute that cycle's reward split. This lets a user who votes right before a maintenance boundary, waits one full cycle for registration, and then immediately withdraws right after the following cycle begins, still collect that entire cycle's reward as if the vote had been held for the whole cycle — the reward is decoupled from actual holding duration in exactly the way the LendingLedger bug describes (deposit right before the boundary, withdraw right after, full-period reward). The `withdrawReward` path used by both the actuator (`WithdrawRewardProcessor`) and `MortgageService.withdrawReward` performs no time-weighting either, only cycle counting: [6](#0-5) 

This is reachable from any unprivileged account by simply broadcasting `VoteWitnessContract` transactions (or the TVM `vote`/`withdrawreward`/`clearvote` precompiles) at the appropriate moment relative to `nextMaintenanceTime`, requiring only TRON Power (frozen balance), which is a normal, permissionless operation.

### Impact Explanation
This allows any voter to claim a disproportionate share of the SR (witness) voting-reward pool relative to genuine long-term voters, diluting rewards paid to honest long-term stakers who actually keep capital committed to the voted witnesses for the full cycle. Because vote weight is fungible and can be re-registered every cycle by flash-voting near boundaries, an attacker (or coordinated set of accounts/bots) can repeatedly harvest reward without providing sustained voting support/liquidity to the network's governance mechanism, which is the entire economic purpose of DPoS vote incentives. This is an accounting/reward-corruption issue rather than a fund-theft bug (funds still come from the legitimate reward pool), but it systematically transfers reward from genuine long-duration voters to short-duration "flash" voters.

### Likelihood Explanation
The precondition (owning any amount of TRON Power / frozen balance and submitting `VoteWitnessContract` transactions at times relative to the publicly-known `nextMaintenanceTime`) is trivially satisfiable by any account and requires no special privilege, matching the "unprivileged actor via broadcast transaction" requirement. The maintenance schedule (`nextMaintenanceTime`) is a public, deterministic chain parameter, so timing the vote/unvote around it is straightforward to automate.

### Recommendation
Move to time-weighted (or block-weighted) accounting of vote power within a cycle rather than crediting a full cycle's reward based on a binary "was registered at maintenance time" check. For example, weight each voter's contribution to `Vi` accumulation by the number of blocks/time their vote was actually active during the cycle (similar to the veRWA fix that switched to time-weighted balances), or require a minimum holding period spanning multiple maintenance boundaries before a vote's weight is applied to reward computation, and likewise require a delay before an unvote can stop accruing.

### Proof of Concept
Conceptual scenario mapped directly onto the code paths found:
1. Just before `nextMaintenanceTime` for cycle N, Attacker calls `VoteWitnessContract`/`vote` to vote for witness W with tronPower V. This is recorded by `VoteWitnessProcessor.execute()` ( [7](#0-6) ) but does not affect `witness.getVoteCount()` yet.
2. At maintenance ending cycle N, `MaintenanceManager.doMaintenance()` first calls `accumulateWitnessVi(N, W, oldVoteCount)` (not including Attacker's vote), then applies `countWitness` to add Attacker's vote V into `witness.getVoteCount()` ( [8](#0-7) ).
3. During cycle N+1, block rewards accumulate into `delegationStore.addReward(N+1, W, ...)`.
4. At maintenance ending cycle N+1, `accumulateWitnessVi(N+1, W, voteCountIncludingAttacker)` computes `Vi(N+1)` using Attacker's full vote weight V for the whole cycle.
5. Attacker submits a clear-vote transaction in the very first block of cycle N+2 (removing V). This delta is only applied to `witness.getVoteCount()` at the maintenance ending cycle N+2 — **after** `Vi(N+1)` (used for the reward Attacker will claim) was already fixed.
6. Attacker calls `withdrawReward`/`queryReward`; `computeReward` uses `deltaVi = Vi(N+1) - Vi(N)` times Attacker's vote count V, granting the full cycle N+1 reward share ( [3](#0-2) ), despite Attacker's vote having been economically "live" for essentially zero real duration relative to cycle N+1.

Note: I was not able to directly view the `countVote(VotesStore)` method body (it appears to live further down in `MaintenanceManager.java`/`Wallet.java` beyond what the index returned) to confirm the exact delta-application order with 100% certainty; this analysis is based on the confirmed call ordering in `doMaintenance()` (`accumulateWitnessVi` executes before `countWitness.forEach`) and the vote-recording behavior in `VoteWitnessProcessor`. A Devin session with full repository access should verify `countVote`'s exact semantics and the maintenance-interval default (`DynamicPropertiesStore.MAINTENANCE_TIME_INTERVAL`) to confirm cycle length and finalize a concrete numeric PoC.

      if (account != null) {
        return;

    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }

    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  public void execute(VoteWitnessParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getVoterAddress();
    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);

    VotesCapsule votesCapsule = repo.getVotes(ownerAddress);
    if (votesCapsule == null) {
      votesCapsule = new VotesCapsule(ByteString.copyFrom(ownerAddress),
          accountCapsule.getVotesList());
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    Map<ByteString, Long> voteMap = new HashMap<>();
    Iterator<Protocol.Vote> iterator = param.getVotes().iterator();
    try {
      long sum = 0;
      while (iterator.hasNext()) {
        Protocol.Vote vote = iterator.next();

        byte[] witnessAddress = vote.getVoteAddress().toByteArray();
        /*
          Already covered while doing maintenance in MaintenanceManager.java, for tvm performance,
          we remove the account check
         */
//        if (repo.getAccount(witnessAddress) == null) {
//          throw new ContractValidateException(
//              ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(witnessAddress) + NOT_EXIST_STR);
//        }
        if (repo.getWitness(witnessAddress) == null) {
          throw new ContractExeException(
              WITNESS_EXCEPTION_STR + StringUtil.encode58Check(witnessAddress) + NOT_EXIST_STR);
        }

        long voteCount = vote.getVoteCount();
        if (voteCount < 0) {
          throw new ContractExeException("Vote count must not be less than 0");
        } else if (voteCount == 0) {
          iterator.remove();
        } else {
          sum = LongMath.checkedAdd(sum, voteCount);
          // merge vote for same witness
          voteMap.put(vote.getVoteAddress(),
              LongMath.checkedAdd(voteMap.getOrDefault(vote.getVoteAddress(), 0L), voteCount));
        }
      }

      long tronPower;
      if (repo.getDynamicPropertiesStore().supportUnfreezeDelay()
          && repo.getDynamicPropertiesStore().supportAllowNewResourceModel()) {
        tronPower = accountCapsule.getAllTronPower();
      } else {
        tronPower = accountCapsule.getTronPower();
      }
      sum =  LongMath.checkedMultiply(sum, TRX_PRECISION);
      if (sum > tronPower) {
        throw new ContractExeException(
            "The total number of votes[" + sum + "] is greater than the tronPower[" + tronPower
                + "]");
      }
    } catch (ArithmeticException e) {
      throw new ContractExeException(e.getMessage());
    }

    for (Map.Entry<ByteString, Long> entry : voteMap.entrySet()) {
      accountCapsule.addVotes(entry.getKey(), entry.getValue());
      votesCapsule.addNewVotes(entry.getKey(), entry.getValue());
    }
    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    repo.updateVotes(ownerAddress, votesCapsule);
  }
