### Title
Unbounded per-account asset map growth causes O(n) iteration cost in `BandwidthProcessor.updateUsage` reachable from anonymous RPC — ([File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java])

### Summary
`BandwidthProcessor.updateUsage(AccountCapsule)` iterates over every distinct TRC10 asset ID an account has ever held (`accountCapsule.getAssetMapV2()` merged with `getAllFreeAssetNetUsageV2()`), with no cap on the number of distinct asset entries. Any address can be sent an unlimited number of distinct TRC10 tokens by anonymous callers via `TransferAssetContract`, and once an entry is created for an asset ID it is never removed even if the balance later goes to zero, so the map only grows. This map is walked on every subsequent `GetAccountNet`/`GetAccountResource` API call (and via `getAssetIssueList()`), which are unauthenticated read RPCs, mirroring the "unbounded array grows and is scanned each call" pattern from the referenced report.

### Finding Description
`AccountCapsule.addAssetV2`/`addAssetMapV2` add new keys to the account's `asset_v2` map for every distinct TRC10 token ID the account is transferred, with no upper bound check: [1](#0-0) 

Entries are keyed by asset ID and are not removed when balance reaches zero — `getAllAssets`/`getAssetMapV2` simply keep the key with value `0`, as demonstrated in the store-level accounting logic: [2](#0-1) 

`BandwidthProcessor.updateUsage(AccountCapsule)` then iterates the full merged asset map (`assetMapV2` plus `getAllFreeAssetNetUsageV2()`) on every invocation, performing per-entry lookups and mutations: [3](#0-2) 

This method is invoked from the unauthenticated wallet API methods `getAccountNet` and `getAccountResource`, both of which are exposed as gRPC/HTTP endpoints reachable by any caller who supplies a victim's address: [4](#0-3) 

There is no limit anywhere in this path on the number of distinct asset IDs an account may accumulate (unlike, e.g., `frozenList` in `AssetIssueActuator`, which is bounded by `getMaxFrozenSupplyNumber`, or `MarketSellAssetActuator`, which is bounded by `MAX_MATCH_NUM`). An attacker with no special privileges can issue many low-cost TRC10 tokens (subject only to the asset-issuance fee, not to per-recipient limits) and transfer minimal amounts of each to a victim address, growing that victim's `asset_v2` map without bound.

### Impact Explanation
Because the map is never pruned, every future call to `getAccountNet`/`getAccountResource` for the victim address — and every `TransferAssetContract` involving that account through `BandwidthProcessor.consume` code paths that call `updateUsage`-style asset iteration — incurs cost proportional to the number of distinct asset entries the account has ever received. As the attacker keeps adding distinct asset IDs, the per-request cost keeps growing, degrading node responsiveness for that account's read APIs and increasing the resource cost of processing further transactions involving the account. This is a resource-accounting DoS vector rather than fund theft, consistent with the medium severity assigned to the analogous finding in the external report.

### Likelihood Explanation
Likelihood is moderate: creating each TRC10 asset costs the standard asset-issuance fee, and each transfer costs ordinary bandwidth/fee, so there is an economic cost to the attacker, but no protocol-level cap prevents accumulating an arbitrarily large number of distinct asset entries on a single victim account over time (e.g., across many blocks/days), and the affected read APIs are unauthenticated and reachable by anyone.

### Recommendation
Impose an explicit upper bound on the number of distinct asset entries (`asset_v2` / `free_asset_net_usage_v2` map size) an account can hold, analogous to the `MaxFrozenSupplyNumber` and `MAX_MATCH_NUM` limits already used elsewhere in the codebase, and/or prune zero-balance asset entries from the map instead of retaining them indefinitely, so that `BandwidthProcessor.updateUsage` and related iteration paths have a bounded worst-case cost.

### Proof of Concept
1. Issue N distinct TRC10 tokens (`AssetIssueContract`) from attacker-controlled accounts.
2. For each token, broadcast a `TransferAssetContract` sending a minimal amount to victim address `V`.
3. After N transfers, `V`'s `asset_v2` map (`AccountCapsule.getAssetMapV2`) contains N entries that are never removed even if `V`'s balance of each token later becomes 0 (`AccountAssetStore.getAllAssets`, `AccountCapsule.getAssetMapV2`).
4. Call the unauthenticated RPC `GetAccountNet`/`GetAccountResource` for `V` (`Wallet.getAccountNet`/`getAccountResource`, which call `BandwidthProcessor.updateUsage(accountCapsule)`); observe that execution time/work scales linearly with N, with no configured maximum.

  public void updateUsage(AccountCapsule accountCapsule) {
    long now = chainBaseManager.getHeadSlot();
    long oldNetUsage = accountCapsule.getNetUsage();
    long latestConsumeTime = accountCapsule.getLatestConsumeTime();
    accountCapsule.setNetUsage(increase(accountCapsule, BANDWIDTH,
            oldNetUsage, 0, latestConsumeTime, now));
    long oldFreeNetUsage = accountCapsule.getFreeNetUsage();
    long latestConsumeFreeTime = accountCapsule.getLatestConsumeFreeTime();
    accountCapsule.setFreeNetUsage(increase(oldFreeNetUsage, 0, latestConsumeFreeTime, now));

    if (chainBaseManager.getDynamicPropertiesStore().getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = accountCapsule.getAssetMap();
      assetMap.forEach((assetName, balance) -> {
        long oldFreeAssetNetUsage = accountCapsule.getFreeAssetNetUsage(assetName);
        long latestAssetOperationTime = accountCapsule.getLatestAssetOperationTime(assetName);
        accountCapsule.putFreeAssetNetUsage(assetName,
            increase(oldFreeAssetNetUsage, 0, latestAssetOperationTime, now));
      });
    }
    Map<String, Long> assetMapV2 = accountCapsule.getAssetMapV2();
    Map<String, Long> map = new HashMap<>(assetMapV2);
    accountCapsule.getAllFreeAssetNetUsageV2().forEach((k, v) -> {
      if (!map.containsKey(k)) {
        map.put(k, 0L);
      }
    });
    map.forEach((assetName, balance) -> {
      long oldFreeAssetNetUsage = accountCapsule.getFreeAssetNetUsageV2(assetName);
      long latestAssetOperationTime = accountCapsule.getLatestAssetOperationTimeV2(assetName);
      accountCapsule.putFreeAssetNetUsageV2(assetName,
          increase(oldFreeAssetNetUsage, 0, latestAssetOperationTime, now));
    });
  }
