### Title
Unrestricted "Bootstrap Declare" bypass allows any unauthorized sender to declare contract classes for free at any block, bypassing all validation and fee accounting - (File: crates/blockifier/src/transaction/account_transaction.rs)

### Summary
The Diamond-cut report flags a privileged state-mutating entry point (`diamondCut`) that has no access-control check, letting any caller reach code meant only for a trusted party. The sequencer's analog is the "bootstrap declare" fast-path: `AccountTransaction::execute_raw` special-cases any `Declare` transaction whose `sender_address` equals the hard-coded `bootstrap_address()`, whose `nonce == 0`, and whose `charge_fee` is false, and lets it skip `__validate_declare__`, nonce checks, and fee charging entirely. Nothing restricts this path to genesis/bootstrap time or to a trusted operator — any unprivileged transaction submitted through the ordinary gateway/mempool pipeline can hit this branch.

### Finding Description
`DeclareTransaction::is_bootstrap_declare` only checks three attacker-controlled fields: `sender_address == bootstrap_address()`, `nonce == 0`, and `!charge_fee`: [1](#0-0) 

`charge_fee` itself is derived purely from the transaction's own resource bounds via `enforce_fee`, which is called with the attacker-supplied transaction when building the `AccountTransaction` for sequencing: [2](#0-1) 

When `execute_raw` runs (this is the exact code path invoked both for real block-building and for gateway/mempool admission of Declare/DeployAccount transactions), it detects the bootstrap condition and completely bypasses `perform_pre_validation_stage`, `__validate_declare__`, and `charge_fee`, going straight to declaring the class: [3](#0-2) 

Critically, the gateway's stateful admission check for Declare transactions does not merely simulate `__validate__`; it fully executes the transaction (`self.execute(tx)` → `TransactionExecutor::execute` → the same `execute_raw`), specifically because "Declare transaction should also be fully executed": [4](#0-3) 

The Starknet OS mirrors the same unrestricted bootstrap branch (checked only via `sender_address == 'BOOTSTRAP'`, `nonce == 0`, and `version == 3`, with `max_possible_fee == 0` — again fully attacker-controlled fields), so a malicious re-execution would also succeed in the OS, producing the same wrong (but internally "consistent") state: [5](#0-4) 

Nothing in any of these code paths restricts the bootstrap branch to a genesis block, to a specific chain state, or to a trusted caller — the only "access control" is that the sender address field of an ordinary, unsigned-in-effect V3 Declare transaction must equal a publicly known constant (`0x424f4f545354524150`, i.e. ASCII "BOOTSTRAPSTRAP") and the transaction must set zero resource bounds. Both of these are fully within an unprivileged sender's control, and the design comment itself only documents the *functional consequence* (the tx stays in the mempool and gets rejected on replay), not any authorization boundary, confirming the omission is an unintended lack of access control rather than a deliberately gated administrative operation.

### Impact Explanation
Any unprivileged party can submit a V3 Declare transaction with `sender_address = bootstrap_address()`, `nonce = 0`, and all-zero resource bounds, at any block height (not just genesis), and have an arbitrary Sierra/CASM class hash committed into contract-class state:
- Completely bypassing fee/resource accounting (`charge_fee` is forced false), defeating the network's core spam-resistance mechanism for Declare transactions, which are normally the most expensive/state-heavy transaction type.
- Completely bypassing `__validate_declare__` and any account-existence/signature requirement, since the special address requires no deployed account contract.
- Being repeatable indefinitely with different class hashes (only `prev_value=0` reuse of the *same* class hash is blocked), enabling unbounded free growor state growth and repeated mempool/bouncer churn, since each successful declare is not "seen" by the mempool notification path and gets re-proposed and only rejected on the next block — consuming validator/bouncer capacity for free, block after block.
This directly maps to "fee and resource accounting" / "bouncer weights" impact categories: an attacker can force the network to include and reprocess declare transactions at zero cost, undermining the sequencer's DoS-resistance guarantees and its committed state (class hashes appear in state without payment), which the honest, fee-accounting design assumes is impossible for unauthorized senders.

### Likelihood Explanation
High. The only "gate" is knowledge of a hardcoded, public constant address and setting resource bounds to zero — both trivially achievable by any external transaction sender through the normal RPC/gateway declare endpoint. No special node privileges, timing, or race conditions are required.

### Recommendation
Restrict the bootstrap-declare fast path so that it can only execute when the chain has not yet produced any blocks (e.g., gate on `block_context.block_info.block_number == BlockNumber(0)` or an explicit "system not yet bootstrapped" state flag), in both the blockifier (`AccountTransaction::execute_raw`) and the Starknet OS (`execute_declare_transaction`). Once the system is bootstrapped, any Declare transaction from the reserved bootstrap address should be rejected outright, regardless of nonce/fee fields, closing off the ability for a non-genesis, unprivileged sender to invoke this privileged, fee-free declaration path.

### Proof of Concept
1. Craft a `DeclareTransaction::V3` with:
   - `sender_address = ExecutableDeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`)
   - `nonce = Nonce(Felt::ZERO)`
   - `resource_bounds` set to all-zero (e.g. `ValidResourceBounds::create_for_testing_no_fee_enforcement()`-equivalent all-zero bounds), so `enforce_fee(&tx, false) == false`
   - `class_hash` / `compiled_class_hash` for any Sierra class the attacker controls, with a valid CASM hash so `check_compile_class_hash_v2_declaration` passes.
2. Submit at any block height (not genesis) via the gateway `add_tx` Declare flow.
3. `check_declare_permissions` in the gateway does not check for the bootstrap address (only `authorized_declarer_accounts`, see `crates/apollo_gateway/src/gateway.rs:407-433`), so it passes.
4. Stateful admission calls `StatefulValidator::perform_validations` → `self.execute(tx)` → `AccountTransaction::execute_raw`, which detects `is_bootstrap_declare` is true and declares the class with zero fee and no validation, as shown at `crates/blockifier/src/transaction/account_transaction.rs:899-911`.
5. Repeat with new class hashes indefinitely to declare arbitrary classes for free at zero cost, at any point in the chain's lifetime, not only during genesis bootstrap.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.

        // Do not run validate or perform any account-related actions for declare transactions that
        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
            }
        }

    pub fn perform_validations(&mut self, tx: AccountTransaction) -> StatefulValidatorResult<()> {
        // Deploy account transaction should be fully executed, since the constructor must run
        // before `__validate_deploy__`. The execution already includes all necessary validations,
        // so they are skipped here.
        // Declare transaction should also be fully executed - otherwise, if we only go through
        // the validate phase, we would miss the check that the class was not declared before.
        match tx.tx {
            ApiTransaction::DeployAccount(_) | ApiTransaction::Declare(_) => self.execute(tx),
            ApiTransaction::Invoke(_) => {
                let tx_context = Arc::new(self.tx_executor.block_context.to_tx_context(&tx));
                tx.perform_pre_validation_stage(self.state(), &tx_context)?;
                if !tx.execution_flags.validate {
                    return Ok(());
                }

                // `__validate__` call.
                let (_optional_call_info, actual_cost) = self.validate(&tx, tx_context.clone())?;

                // Post validations.
                PostValidationReport::verify(
                    &tx_context,
                    &actual_cost,
                    tx.execution_flags.charge_fee,
                )?;

                Ok(())
            }
        }
    }
