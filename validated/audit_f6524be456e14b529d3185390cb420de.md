### Title
Unbounded gzip decompression of attacker-controlled Cairo-0 `compressed_program` in RPC declare-transaction execution path - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
The `decompress_program` helper used to convert a Cairo‑0 (`DeclareV1`) `BroadcastedDeclareTransaction`'s `compressed_program` field fully decompresses attacker-supplied gzip data into memory with **no size limit**, before any validation occurs — the same root-cause pattern flagged in the CredSweeper advisory (full materialization before budget enforcement).

### Finding Description
`decompress_program` decodes base64 and then reads the entire gzip stream to completion via `decoder.read_to_end(&mut decompressed)` with an explicit `// TODO(dan): add time and size limits.` comment acknowledging the gap: [2](#0-1) 

This is reached from `user_deprecated_contract_class_to_sn_api`, which is called when converting a `BroadcastedDeclareV1Transaction` (an RPC-submitted declare transaction) into the internal `DeclareTransactionV0V1` representation used for execution/fee-estimation: [1](#0-0) [3](#0-2) 

Contrast this with the equivalent, properly hardened path used for the primary sequencer gateway ingestion of declare transactions (both Sierra and legacy), which enforces the limit *during* decompression using a bounded `.take(max_size + 1)` read *before* the decompressed buffer can exceed the configured bound — this is the exact mitigation pattern the CredSweeper advisory recommends, already correctly implemented elsewhere in this codebase: [4](#0-3) 

The RPC read-node's `decompress_program`, however, has no equivalent bound: an attacker can submit a small (few KB) base64-encoded gzip "bomb" as `compressed_program` in a `starknet_estimateFee` / `starknet_simulateTransactions` (or similar execution) JSON-RPC call, causing the node to inflate it to an arbitrarily large in-memory buffer before any check occurs.

### Impact Explanation
An unprivileged RPC/transaction sender can force a sequencer/full-node component to allocate gigabytes of memory from a small request payload, causing an out-of-memory condition or severe CPU/latency degradation on the node servicing JSON-RPC declare-transaction fee-estimation/simulation requests. This is a resource-exhaustion (availability) issue on the RPC execution path reachable via a single crafted transaction/API request — meeting the "network unable to confirm new transactions" bar if the affected process is shared with core node duties (e.g., the RPC/read component becomes unresponsive, or memory pressure triggers OOM-kill on a shared host), consistent with CWE-409/CWE-400.

### Likelihood Explanation
High: the only requirements are (1) crafting a standard gzip "bomb" (trivial, standard tooling), and (2) calling an RPC method (e.g. fee estimation/simulation for a v1 declare transaction) with the malicious `compressed_program` field. No special privileges, prior state, or protocol quirks are needed — this exactly mirrors the CredSweeper PoC pattern (small compressed input → unbounded decompressed output → no budget check before use).

### Recommendation
Apply the same bounded-decompression pattern already used in `starknet_api::compression_utils::decompress_with_size_limit` to `decompress_program`: wrap the `GzDecoder` in a `.take(max_size + 1)` reader and enforce a hard maximum size limit (e.g. matching `max_contract_bytecode_size` / `max_sierra_program_size`), returning an error before the buffer is fully materialized if the size limit is exceeded. Remove the outstanding `// TODO(dan): add time and size limits.` by wiring in an explicit, configured size (and ideally time) budget for this decompression path, consistent with the other gateway-side hardened deserializers in the codebase.

### Proof of Concept
1. Generate a gzip-compressed payload that decompresses to several hundred MB from a few KB of input (a standard "zip bomb" style highly-repetitive JSON program body), base64-encode it.
2. Submit a JSON-RPC `starknet_estimateFee` (or `starknet_simulateTransactions`) request containing a `BROADCASTED_DECLARE_TXN` of type V1 whose `contract_class.program` field is set to this base64 string.
3. Observe that `user_deprecated_contract_class_to_sn_api` → `decompress_program` fully decompresses the payload via `read_to_end` with no size cap, causing large memory allocation and/or excessive CPU time before any validation of program contents occurs, as shown at [2](#0-1) .

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
