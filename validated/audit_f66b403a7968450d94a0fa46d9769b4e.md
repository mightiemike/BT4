### Title
Inbound-revert outbounds are created without checking `IsChainOutboundEnabled`, permanently freezing user funds when the source chain has outbound disabled - (File: `x/uexecutor/keeper/build_revert_outbound.go`, `x/uexecutor/keeper/handle_failed_inbound_validation.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
The external report's root cause is: a bridge-out flow creates a value-transfer transaction to a destination without verifying that destination is actually configured to receive it, causing permanent loss of the asset. The direct analog in Push Chain is the `INBOUND_REVERT` outbound path: when inbound processing fails after ballot finalization, the code builds and attaches an outbound to send the user's funds back to the **source chain**, but never checks whether that chain has outbound enabled — unlike the normal (forward) outbound-creation path, which does perform this exact check.

### Finding Description
`BuildOutboundsFromReceipt` explicitly validates the destination chain before creating a forward outbound: [1](#0-0) 

However, the revert-outbound builder used across all inbound execution paths (`execute_inbound_funds.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, `handle_failed_inbound_validation.go`, `admin_revert.go`) has no equivalent check: [2](#0-1) 

`handleFailedInboundValidation`, which fires whenever `ValidateForExecution` fails for a non-CEA inbound after the UTX has already been finalized (i.e., funds already accounted for on Push Chain), calls `buildRevertOutbound` unconditionally and attaches the resulting outbound via `attachOutboundsToUtx`: [3](#0-2) 

`attachOutboundsToUtx` itself performs no chain-enabled validation either — it only best-effort looks up `TssSigningDeadline` from the chain config and unconditionally writes the outbound into `PendingOutbounds`, emitting a `SIGN_OUTBOUND`-style event that the `universalClient` will pick up: [4](#0-3) 

`IsChainInboundEnabled` and `IsChainOutboundEnabled` are independent boolean flags in `ChainEnabled`, so a chain can be configured with inbound enabled but outbound disabled: [5](#0-4) 

Downstream, the `universalClient`'s `SessionManager.verifyOutboundSigningRequest` does check `IsChainOutboundEnabled` and will refuse to sign such a transaction: [6](#0-5) 

This means an `INBOUND_REVERT` outbound created for a source chain with `IsOutboundEnabled=false` will sit in `PendingOutbounds` in `Status_PENDING` forever — it can never be signed. Worse, the only recovery mechanism, `AttachRescueOutboundFromReceipt`, requires the auto-revert outbound to have already reached `Status_REVERTED` before rescue is permitted: [7](#0-6) 

Since the stuck revert never transitions past `PENDING`, the rescue path is unreachable too, leaving the user's already-debited/escrowed funds permanently frozen with no on-chain recovery path.

### Impact Explanation
This matches the "Permanent Freezing of user funds" impact category. An unprivileged user can trigger this purely by submitting an inbound that later fails execution validation (e.g., a malformed `UniversalPayload`, a validation failure discovered post-finalization) from a chain that is inbound-enabled but outbound-disabled (a legitimate, non-malicious admin configuration state — e.g. temporarily pausing outbound to a chain for maintenance while inbound deposits remain open). The user's deposited/represented funds become stuck: the revert outbound can never be signed by honest TSS/UVs, and the rescue-outbound flow's precondition (`Status_REVERTED`) is never met.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a chain configuration with `IsInboundEnabled=true` and `IsOutboundEnabled=false` (a supported, plausible operational state, e.g., during incident response or migration) and (2) an inbound from that chain whose execution validation fails after ballot finalization (reachable by any user submitting a payload that fails `ValidateForExecution`, or via the admin `RevertStuckInbound` path for expired ballots). No malicious validator, relayer, or admin action is required — only ordinary/adversarial user transaction submission plus a chain-config state that operators are expected to be able to set.

### Recommendation
Add the same `IsChainOutboundEnabled` check used in `BuildOutboundsFromReceipt` before attaching any `INBOUND_REVERT` (or `RESCUE_FUNDS`) outbound in `buildRevertOutbound` / `attachOutboundsToUtx` / `handleFailedInboundValidation` / `admin_revert.go`. If the destination (source) chain has outbound disabled, the module should either: hold off creating the revert outbound and retry once outbound is re-enabled (persisting a distinct "revert pending — outbound disabled" status rather than silently entering the normal `PENDING` unsigned queue), or fail loudly and surface this state via a queryable/alertable UTX field so operators can react before funds are considered lost. Additionally, consider relaxing the rescue-outbound precondition so it does not strictly require `Status_REVERTED`, since a permanently un-signable `PENDING` revert can never reach that state.

### Proof of Concept
1. Admin/operator configures chain `eip155:X` with `ChainEnabled{IsInboundEnabled: true, IsOutboundEnabled: false}` (a supported, non-malicious configuration, e.g. pausing outbound during an incident) via `x/uregistry`.
2. A user submits/votes-in a valid inbound from `eip155:X` for a non-CEA payload; the ballot finalizes and the UTX is created (funds already credited/escrowed on Push Chain).
3. Execution of the inbound payload fails `ValidateForExecution` (any of several ordinary failure conditions, e.g., malformed `UniversalPayload` fields caught post-finalization), triggering `handleFailedInboundValidation`.
4. `buildRevertOutbound` builds an `INBOUND_REVERT` outbound targeting `eip155:X` with no check against `IsChainOutboundEnabled`; `attachOutboundsToUtx` attaches it and writes a `PendingOutbounds` entry in `Status_PENDING`.
5. The `universalClient`'s `SessionManager.verifyOutboundSigningRequest` rejects signing this outbound forever (`"outbound disabled for chain %s, refusing to sign"`), so it never transitions to `Status_REVERTED`.
6. `AttachRescueOutboundFromReceipt` requires an existing `Status_REVERTED` auto-revert outbound before permitting a rescue outbound, which is never satisfied — the user's funds are permanently stuck with no path to recovery.

func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {

		DestinationChain:  inbound.SourceChain,

		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}

// IsChainInboundEnabled checks if inbound is enabled for a given chain
func (k Keeper) IsChainInboundEnabled(ctx context.Context, chain string) (bool, error) {
	config, err := k.GetChainConfig(ctx, chain)
	if err != nil {
		if errors.Is(err, collections.ErrNotFound) {
			// chain not found
			return false, nil
		}
		return false, err
	}
	if config.Enabled == nil {
		return false, nil
	}
	return config.Enabled.IsInboundEnabled, nil
}
