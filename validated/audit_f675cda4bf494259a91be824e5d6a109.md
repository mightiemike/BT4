### Title
Hardcoded 0x41 (mainnet) address prefix in `HistoryBlockHashUtil` breaks TIP-2935 historical-block-hash contract on any non-default-prefix chain - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil` deploys the TIP-2935 (EIP-2935) "BlockHashHistory" system contract at a compile-time constant, mainnet-prefixed address. The address prefix byte used to build this constant is hardcoded to `0x41` rather than the node's actual configured address prefix, so on any java-tron based chain (private/consortium chain, or any deployment using a non-default prefix such as the well-known `0xa0` testnet convention) the deployed system contract lives at an address that the VM's own address-translation logic will never construct at call time, making the feature effectively unreachable on those chains — the same class of defect as the audited Solidity report where a single hardcoded cross-chain address broke contract functionality outside of the chain it was copied from.

### Finding Description
`HISTORY_STORAGE_ADDRESS` and `HISTORY_DEPLOYER_ADDRESS` are defined as fixed byte constants with the `0x41` (TRON mainnet) prefix hard-baked in: [1](#0-0) 

The comment in the codebase itself documents that the TRON address prefix is configurable and differs between mainnet (`0x41`) and testnet/private deployments (`0xa0`), and that this prefix is baked in at compile time for other constructs (e.g. CREATE2 hashing): [2](#0-1) 

`Wallet.getAddressPreFixString()`/`DecodeUtil.addressPreFixString` shows the prefix is a runtime-configurable, chain-specific value, not a universal constant: [3](#0-2) [4](#0-3) 

`HistoryBlockHashUtil.deploy()` writes the code/account/contract capsules directly at `HISTORY_STORAGE_ADDRESS` (the `0x41`-prefixed constant) once the `ALLOW_TVM_PRAGUE` proposal is activated, with no adjustment for the chain's actual configured prefix: [5](#0-4) 

This is invoked from the consensus-critical `ProposalService.process` maintenance path: [6](#0-5) 

Because the deployment key is a fixed 21-byte value with `0x41` hardcoded rather than derived from the node's actual `addressPreFixByte`, any chain that runs with a different prefix (documented in-repo as `0xa0` for testnet configs, and freely configurable for private/consortium chains built from this codebase) will have the BlockHashHistory contract physically stored at an address that never matches the addresses the TVM constructs for STATICCALL targets on that chain (the VM always prepends the chain's *actual* configured prefix byte when converting the 20-byte EVM-style address `0x0000f90827f1c53a10cb7a02335b175320002935` used by callers). The result: the feature is silently unreachable, exactly mirroring the audited bug where the hardcoded `V3_POS_MGR` address "won't be the same on every chain."

### Impact Explanation
On any java-tron-derived chain not using the exact `0x41` mainnet prefix, activating `ALLOW_TVM_PRAGUE` deploys the TIP-2935 contract at an address that is unreachable via the chain's normal address space, meaning:
- Contracts relying on TIP-2935 historical block hash reads (a protocol-level feature gated by a hard fork flag) silently never work on those chains, a functional/consensus divergence between the intended EIP-2935 semantics and actual behavior per chain — a defect in core protocol implementation, not caused by a malicious actor.
- Because deployment is a one-time, irreversible write gated by `saveBlockHashHistoryInstalled(1L)`, the mismatch cannot be corrected once the proposal passes, permanently breaking the feature for that network.

This does not fit "privileged-actor" exclusion because it is a defect intrinsic to the protocol code itself (any chain operator who legitimately configures a non-default address prefix, a fully supported and documented configuration path in this codebase, triggers the bug merely by adopting the hard fork).

### Likelihood Explanation
Likelihood is moderate: it requires (1) a java-tron-derived chain configured with a non-`0x41` address prefix (common for private/consortium/testnet deployments built on this codebase, as evidenced by in-repo test comments referencing `0xa0`), and (2) the chain reaching the `ALLOW_TVM_PRAGUE` hard fork via normal governance. Both conditions are ordinary operational configurations rather than attacker actions, making this a realistic deployment-time defect rather than a purely theoretical one.

### Recommendation
Derive `HISTORY_STORAGE_ADDRESS` (and `HISTORY_DEPLOYER_ADDRESS`) from the chain's actual configured address prefix (`DecodeUtil.addressPreFixByte` / `CommonParameter`) at deploy time instead of hardcoding the `0x41` mainnet byte, so the stored capsule key matches the address the VM will construct when resolving STATICCALL targets on that specific chain.

### Proof of Concept
Not applicable as an on-chain exploit — this is a configuration-dependent protocol defect. It can be demonstrated by: (1) starting a java-tron node with a non-default address prefix (e.g. `0xa0`), (2) passing/activating the `ALLOW_TVM_PRAGUE` proposal so `HistoryBlockHashUtil.deploy()` runs, and (3) observing that a contract issuing `STATICCALL` to the canonical EIP-2935 20-byte address (`0x0000f90827f1c53a10cb7a02335b175320002935`) resolves to a 21-byte address with the node's actual prefix (e.g. `a0...2935`) which has no code/account, while the deployed contract sits at the unreachable hardcoded `41...2935` key.
