### Title
Single global `shrink_ratio` config value silently reused across unrelated shrink decision paths (normal shrink candidate selection vs. per-store shrink-productivity gating) - (`accounts-db/src/accounts_db.rs`)

### Summary
The bug class in the external report is "the same tolerance/threshold parameter is silently reused for two logically distinct operations that should be governed independently, allowing behavior calibrated for one path to produce unintended effects on the other." In `agave`, `AccountsDb` has a single `shrink_ratio: AccountShrinkThreshold` field that is used both by `select_candidates_by_total_usage` (the aggregate, all-candidates shrink-goal calculation used in `shrink_candidate_slots`) and by `is_candidate_for_shrink` (per-store gating used elsewhere, e.g. to decide if an individual store is "productive" to shrink, and consulted from the ancient-append-vec packing path). [1](#0-0) [2](#0-1) 

### Finding Description
`AccountShrinkThreshold` supports two distinct semantics, `TotalSpace { shrink_ratio }` and `IndividualStore { shrink_ratio }`, but only one `shrink_ratio` value is configurable and stored in `self.shrink_ratio` for the whole `AccountsDb` instance. [3](#0-2) 

This same value is consumed in at least two different decision contexts:

1. `shrink_candidate_slots`, which drives the periodic, non-ancient shrink pass and calls `select_candidates_by_total_usage(&shrink_candidates_slots, shrink_ratio)` — an aggregate calculation that walks all candidate stores sorted by sparseness and stops once the cumulative alive-ratio across the whole batch exceeds `shrink_ratio`. [4](#0-3) [5](#0-4) 

2. `is_candidate_for_shrink`, a per-store predicate reused for other purposes (e.g., adding "ancient" slots back into the shrink set in `shrink_candidate_slots` itself, and gating whether combining/shrinking an individual store in the ancient-append-vec path is worthwhile), which — for `IndividualStore { shrink_ratio }` — checks a completely different, per-store condition: `(alive_bytes / total_bytes) < shrink_ratio`. [2](#0-1) [6](#0-5) 

These two consumers have opposite operational goals: the aggregate `TotalSpace` calculation is meant to bound *total* dead-byte accumulation and reclaim just enough to hit a global target, while the per-store check is meant to identify individually sparse stores worth reclaiming (and is also invoked from the ancient-slot-shrink candidate injection logic that feeds back into the same aggregate calculation). Because both consumers pull from the identical `self.shrink_ratio`, an operator tuning `--accounts-shrink-ratio` for one behavior (e.g., a conservative aggregate target to limit shrink I/O) simultaneously and silently re-tunes the unrelated per-store/ancient-eligibility gate, and vice versa. There is no way to set an aggregate target independently from a per-store/ancient eligibility threshold, mirroring the Connext report's core flaw of one knob serving two operations with different correct values. [7](#0-6) [8](#0-7) 

### Impact Explanation
This does not directly corrupt account data, hashes, or capitalization — `is_candidate_for_shrink` and `select_candidates_by_total_usage` both operate purely on liveness/sparseness bookkeping, and shrink only compacts storage without changing account content or the accounts hash. The impact is limited to disproportionate storage/CPU cost: an operator who sets `shrink_ratio` low to reduce aggregate shrink I/O also lowers the bar for individual-store shrink eligibility (or vice versa), causing either excessive re-shrinking/I/O amplification or insufficient reclamation and unbounded disk growth from stale append-vec bytes, depending on which direction the misconfiguration goes. This falls into the "disproportionate storage and CPU cost" category called out as acceptable impact for this analog exercise.

### Likelihood Explanation
Any validator operator who customizes `--accounts-shrink-ratio` (a documented, user-facing CLI flag) away from the default is affected, since the single value always propagates to both consumers; no attacker action or malicious input is required, only configuration by a legitimate node operator. [7](#0-6) 

### Recommendation
Introduce separate configuration knobs (and corresponding fields on `AccountsDb`) for the aggregate `TotalSpace` shrink target used by `select_candidates_by_total_usage` versus the per-store gating threshold used by `is_candidate_for_shrink`/ancient-slot eligibility, so operators can tune the two independently, analogous to allowing two separate slippage tolerances in the Connext fix.

### Proof of Concept
Not applicable in the traditional sense (no exploit transaction) — the issue is demonstrated by code inspection: `self.shrink_ratio` is read in `shrink_candidate_slots` for the aggregate `TotalSpace` path [9](#0-8)  and independently in `is_candidate_for_shrink` for the per-store `IndividualStore` path [10](#0-9) , both sourced from the same single CLI-configured value [8](#0-7) , confirming one parameter governs two semantically different thresholds.

    fn select_candidates_by_total_usage(
        &self,
        shrink_slots: &ShrinkCandidates,
        shrink_ratio: f64,
    ) -> (IntMap<Slot, Arc<AccountStorageEntry>>, ShrinkCandidates) {
        struct StoreUsageInfo {
            slot: Slot,
            alive_ratio: f64,
            alive_bytes_after_shrink: u64,
            store: Arc<AccountStorageEntry>,
        }
        let mut store_usages = Vec::with_capacity(shrink_slots.len());
        let mut total_alive_bytes: u64 = 0;
        let mut total_bytes: u64 = 0;
        for slot in shrink_slots {
            let Some(store) = self.storage.get_slot_storage_entry(*slot) else {
                continue;
            };
            let alive_bytes_after_shrink = self.alive_bytes_after_shrink(&store) as u64;
            total_alive_bytes += alive_bytes_after_shrink;
            let written_bytes = store.written_bytes();
            total_bytes += written_bytes;
            debug_assert!(
                written_bytes > 0,
                "shrink candidate has zero written bytes! slot: {slot} id: {}",
                store.id(),
            );
            let alive_ratio = alive_bytes_after_shrink as f64 / written_bytes as f64;
            store_usages.push(StoreUsageInfo {
                slot: *slot,
                alive_ratio,
                alive_bytes_after_shrink,
                store: store.clone(),
            });
        }
        store_usages.sort_by(|a, b| {
            a.alive_ratio
                .partial_cmp(&b.alive_ratio)
                .unwrap_or(std::cmp::Ordering::Equal)
        });

        // Working from the beginning of store_usage which are the most sparse and see when we can stop
        // shrinking while still achieving the overall goals.
        let mut shrink_slots = IntMap::default();
        let mut shrink_slots_next_batch = ShrinkCandidates::default();
        for store_usage in &store_usages {
            let store = &store_usage.store;
            let alive_ratio = (total_alive_bytes as f64) / (total_bytes as f64);
            debug!(
                "alive_ratio: {:?} store_id: {:?}, store_ratio: {:?} requirement: {:?}, \
                 total_bytes: {:?} total_alive_bytes: {:?}",
                alive_ratio,
                store_usage.store.id(),
                store_usage.alive_ratio,
                shrink_ratio,
                total_bytes,
                total_alive_bytes
            );
            if alive_ratio > shrink_ratio {
                // we have reached our goal, stop
                debug!(
                    "Shrinking goal can be achieved at slot {:?}, total_alive_bytes: {:?} \
                     total_bytes: {:?}, alive_ratio: {:}, shrink_ratio: {:?}",
                    store_usage.slot, total_alive_bytes, total_bytes, alive_ratio, shrink_ratio
                );
                if store_usage.alive_ratio < shrink_ratio {
                    shrink_slots_next_batch.insert(store_usage.slot);
                } else {
                    break;
                }
            } else {
                let current_store_size = store.written_bytes();
                let after_shrink_size = store_usage.alive_bytes_after_shrink;
                let bytes_saved = current_store_size.saturating_sub(after_shrink_size);
                total_bytes -= bytes_saved;
                shrink_slots.insert(store_usage.slot, Arc::clone(store));
            }
        }
        (shrink_slots, shrink_slots_next_batch)
    }

    /// Determines whether a given AccountStorageEntry instance is a
    /// candidate for shrinking.
    pub(crate) fn is_candidate_for_shrink(&self, store: &AccountStorageEntry) -> bool {
        let total_bytes = store.written_bytes();
        let alive_bytes = self.alive_bytes_after_shrink(store) as u64;
        match self.shrink_ratio {
            AccountShrinkThreshold::TotalSpace { shrink_ratio: _ } => alive_bytes < total_bytes,
            AccountShrinkThreshold::IndividualStore { shrink_ratio } => {
                (alive_bytes as f64 / total_bytes as f64) < shrink_ratio
            }
        }
    }
