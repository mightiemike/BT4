## Title
Denial of Service via Unbounded `SecondaryIndex` Reverse-Index Growth and O(n) Linear Scan on Insert - (File: `accounts-db/src/accounts_index/secondary.rs`)

### Summary
The `SecondaryIndex::insert()` function used to maintain the optional `--account-index` (`program-id`, `spl-token-owner`, `spl-token-mint`) mappings stores, for every indexed account pubkey (`inner_key`), a `Vec<Pubkey>` of "outer keys" (owner/mint/program-id values seen for that account across slots) rather than a `HashSet`. Insertion performs an O(n) linear `.contains()` scan of this vector before pushing a new entry, and the comment explicitly assumes divergence is "rare" to justify the `Vec` choice. This mirrors the reported bug class: an unbounded, user-influenced collection combined with an O(n) existence check on every insert, leading to disproportionate CPU cost and unbounded memory growth as more entries accumulate.

### Finding Description
`SecondaryIndex::insert()` is called from `update_secondary_indexes()`/`update_spl_token_secondary_indexes()` in `accounts-db/src/accounts_index.rs`, which in turn is invoked on every account write matching the configured secondary index (e.g., every SPL token account creation/close/reinitialization when `--account-index spl-token-owner` or `spl-token-mint` is enabled). The reverse-index entry for a given account pubkey is a `RwLock<Vec<Pubkey>>`: [1](#0-0) 

Every call to `insert()` performs a linear `.contains(key)` scan of this vector before deciding whether to push a new entry: [2](#0-1) 

The code comment explicitly acknowledges the assumption that an account pubkey mapping to multiple different outer keys (e.g., different token mints/owners) across slots is "rare," which is the same flawed assumption behind the vulnerable `deposit()`/`_checkExists()` pattern in the analog report — an unprivileged, external actor controls how often this "rare" case occurs. A user can create an SPL token account at a given address, populate it, close it (zero lamports), and reinitialize a new token account with a different mint/owner at the very same address repeatedly and rapidly across many slots. Because entries in the reverse index are only pruned when the corresponding primary index entries are unref'd/reclaimed during `clean_accounts` (via `remove_by_inner_key_if`), and clean runs periodically rather than synchronously with every write, a user issuing writes faster than clean can catch up can make a single account's reverse-index `Vec` grow arbitrarily large. Each subsequent `insert()` for that same account then must scan the ever-growing vector, and the memory footprint grows unbounded as well, since nothing caps the vector's length.

### Impact Explanation
This falls under "disproportionate storage and CPU cost" in the AccountsDb secondary index — an unprivileged, ordinary account owner (no special privileges) can, purely through transaction submission, force ever-growing per-key vectors and O(n) scans on the hot account-update path for any validator/RPC node running with SPL token secondary indexes enabled (a common configuration for RPC nodes serving `getTokenAccountsByOwner`/`getProgramAccounts` style queries). Sustained abuse degrades bank-processing throughput and can inflate the process's memory usage, a disproportionate-cost DoS vector consistent with the reported bug class.

### Likelihood Explanation
Likelihood is moderate: it requires the validator to be configured with `--account-index spl-token-owner` or `spl-token-mint` (or `program-id`), which is common on RPC-serving nodes but not on all validators. It also requires the attacker's write rate for a fixed address to outpace clean cycles, which is achievable but bounded by how quickly `clean_accounts` reclaims and how many distinct addresses/slots the attacker can churn through with normal transaction fees.

### Recommendation
Replace the reverse-index `Vec<Pubkey>` with a `HashSet<Pubkey>` (or otherwise cap/bound its size) to make membership checks O(1) instead of O(n), removing the incentive/impact of intentionally diverging an account's indexed key across slots, and/or bound the number of divergent entries retained per inner key, forcing eager cleanup instead of waiting for a full `clean_accounts` pass.

### Proof of Concept
1. Start a node with `--account-index spl-token-owner` (or `spl-token-mint`) enabled.
2. Repeatedly, at a single account address `A`: create/initialize a token account owned by `owner_1`, submit a transaction in slot `S1`; then close it and reinitialize it as a token account owned by `owner_2` in slot `S2`; repeat with `owner_3`, `owner_4`, ... across many slots, submitting faster than the background `clean_accounts` pass reclaims older references to `A`.
3. Each of these writes calls `SecondaryIndex::insert()` for the same `inner_key = A`, appending a new distinct `outer_key` (owner) to `reverse_index[A]`'s `Vec`, per `accounts-db/src/accounts_index/secondary.rs` lines 132-153.
4. As the vector for `A` grows to thousands of entries, every subsequent `insert()`/`.contains()` check for `A` becomes progressively more expensive, and the reverse-index memory usage for that single pubkey grows unbounded, degrading account processing for the whole node.

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }
