### Title
`DelegateAction` (Meta Transaction) Signed Payload Contains No Chain Identifier, Enabling Cross-Network Replay by a Malicious Relayer — (`File: core/primitives/src/action/delegate.rs`)

---

### Summary

`DelegateAction` (NEP-366 meta transactions) is signed off-chain by a user and submitted on-chain by a relayer. The signed payload is hashed with a NEP-number discriminant but contains **no chain identifier**. A malicious relayer can take a `SignedDelegateAction` created for one NEAR network (e.g., testnet) and submit it on a different network (e.g., mainnet), executing the inner actions on the wrong chain without the user's consent, potentially draining mainnet funds.

---

### Finding Description

`DelegateAction` is defined in `core/primitives/src/action/delegate.rs`:

```rust
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,
    pub nonce: Nonce,
    pub max_block_height: BlockHeight,
    pub public_key: PublicKey,
}
``` [1](#0-0) 

None of these fields are chain-specific. The signing hash is produced by `get_nep461_hash()`:

```rust
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
``` [2](#0-1) 

`SignableMessage` prepends only a `MessageDiscriminant` — a 4-byte integer derived from the NEP number (366 or 611):

```rust
const NEP_366_META_TRANSACTIONS: u32 = 366;
const NEP_611_GAS_KEYS: u32 = 611;
``` [3](#0-2) 

The discriminant encodes only the NEP number, not any chain identifier:

```rust
MessageDiscriminant::new_on_chain(NEP_366_META_TRANSACTIONS).unwrap()
``` [4](#0-3) 

By contrast, regular `SignedTransaction` includes a `block_hash` field that is chain-specific (a block hash from testnet is not present in mainnet's chain history), making cross-network replay of ordinary transactions impossible. `DelegateAction` replaces `block_hash` with `max_block_height` — a plain integer that is not chain-specific and is typically valid on both mainnet and testnet simultaneously.

`apply_delegate_action` in `runtime/runtime/src/actions.rs` verifies the signature and nonce but performs no chain-binding check:

```rust
pub(crate) fn apply_delegate_action(...) {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    ...
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    ...
    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
``` [5](#0-4) 

There is no step that checks whether the signed action was intended for the current chain.

**Attack scenario:**

1. Alice has the same account ID and key pair on both testnet and mainnet (common for developers and users who create named accounts on both networks).
2. Alice's mainnet access key nonce is `N`. She signs a `DelegateAction` with `nonce = N+1` and `max_block_height = current_mainnet_height + 1000` for a testnet relayer, intending to execute a testnet FT transfer.
3. A malicious relayer intercepts the `SignedDelegateAction` (or operates a relayer service that logs submitted actions) and submits it on mainnet instead.
4. The runtime on mainnet verifies the signature (valid — same key, same payload hash), checks the nonce (valid — `N+1 > N`), checks `max_block_height` (valid — mainnet and testnet block heights are comparable after years of parallel operation), and executes the inner actions on mainnet.
5. Alice's mainnet funds are transferred or her mainnet contract state is mutated without her consent.

The `DelegateActionV2` / `VersionedSignedDelegateAction` path has the same flaw:

```rust
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateActionV2);
    ...
}
``` [6](#0-5) 

---

### Impact Explanation

A malicious relayer can replay a `SignedDelegateAction` created for one NEAR network on a different NEAR network. The inner actions execute with `sender_id` as the predecessor, so any action the user authorized for testnet (token transfers, key additions/deletions, contract calls) executes on mainnet. This constitutes **unauthorized transaction execution** and **fund loss** from the user's mainnet account. The relayer pays gas on mainnet; the user's mainnet state is mutated without consent.

---

### Likelihood Explanation

- Many NEAR users and developers maintain the same account ID and key pair on both testnet and mainnet.
- Relayer services are a trusted intermediary by design; a compromised or malicious relayer has direct access to all `SignedDelegateAction` payloads before submission.
- Block heights on mainnet and testnet are both in the tens of millions and grow at similar rates, so a `max_block_height` set for testnet is almost always also valid on mainnet.
- The nonce on mainnet may be lower than on testnet (or vice versa), making the replayed nonce valid.
- No on-chain mechanism prevents this; the only protection is relayer honesty.

---

### Recommendation

Add a `chain_id` field to `DelegateAction` and `DelegateActionV2` that is included in the signed payload. The chain ID is already available to contracts via the `chain_id` host function:

```rust
pub fn chain_id(&mut self, register_id: u64) -> Result<()> {
    let chain_id = self.ext.chain_id();
    ...
}
``` [7](#0-6) 

The `SignableMessage` discriminant or the `DelegateAction` struct itself should commit to the chain ID (e.g., `"mainnet"`, `"testnet"`) so that a signature produced for one network is cryptographically invalid on any other network. This mirrors how EIP-155 added `chain_id` to Ethereum transaction signing to prevent cross-chain replay — the same pattern the wallet contract already enforces for Ethereum-style transactions:

```rust
if tx.chain_id != Some(CHAIN_ID) {
    return Err(Error::Relayer(RelayerError::InvalidChainId));
}
``` [8](#0-7) 

---

### Proof of Concept

1. Alice creates a `DelegateAction` on testnet with `nonce = ak_nonce + 1`, `max_block_height = testnet_height + 500`, inner action `Transfer { deposit: 10 NEAR }` to Bob, and signs it with her ED25519 key.
2. Alice submits the `SignedDelegateAction` to a relayer service.
3. The malicious relayer, instead of broadcasting to testnet, constructs a `SignedTransaction` on **mainnet** wrapping the same `SignedDelegateAction` (relayer pays mainnet gas).
4. Mainnet runtime calls `apply_delegate_action`: signature verifies (same key, same payload), nonce is valid (mainnet nonce equals `ak_nonce`), `max_block_height` is valid (mainnet height < testnet_height + 500 ≈ mainnet_height + 500).
5. A new receipt is created on mainnet with `predecessor_id = alice`, `receiver_id = bob`, `actions = [Transfer { deposit: 10 NEAR }]`.
6. Alice loses 10 NEAR on mainnet without having authorized any mainnet transaction. [1](#0-0) [9](#0-8) [10](#0-9)

pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
#[non_exhaustive]
pub enum SignableMessageType {
    /// A delegate action, intended for a relayer to included it in an action list of a transaction.
    DelegateAction,
    /// A delegate action with gas key support, intended for a relayer to include it in an action
    /// list of a transaction.
    DelegateActionV2,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum ReadDiscriminantError {
    #[error("does not fit any known categories")]
    UnknownMessageType,
    #[error("NEP {0} does not have a known on-chain use")]
    UnknownOnChainNep(u32),
    #[error("NEP {0} does not have a known off-chain use")]
    UnknownOffChainNep(u32),
    #[error("discriminant is in the range for transactions")]
    TransactionFound,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum CreateDiscriminantError {
    #[error("nep number {0} is too big")]
    NepTooLarge(u32),
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }

```rust
pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

    // Generate a new receipt from DelegateAction.
    let new_receipt = Receipt::V0(ReceiptV0 {
        predecessor_id: sender_id.clone(),
        receiver_id: delegate_action.receiver_id().clone(),
        receipt_id: CryptoHash::default(),

        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: action_receipt.signer_id().clone(),
            signer_public_key: action_receipt.signer_public_key().clone(),
            gas_price: action_receipt.gas_price(),
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: delegate_action.get_actions(),
        }),
    });

    // Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas.
    // If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction.
    // Gas is refunded to the signer, this is Relayer.
    // Some contracts refund the deposit. Usually they refund the deposit to the predecessor and this is sender_id/Sender from DelegateAction.
    // Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit.

    let prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, action_receipt.actions())?;
    let required_cost = receipt_required_cost(apply_state, &new_receipt)?;
    // This gas will be burnt by the receiver of the created receipt.
    // Compute costs of that are not relevant at this point, the "used" gas is
    // only reserved for execution later, potentially on a different shard.
    result.gas_used = result.gas_used.checked_add_result(required_cost.gas)?;
    // This gas was prepaid on Relayer shard. Need to burn it because the receipt is going to be sent.
    // gas_used is incremented because otherwise the gas will be refunded. Refund function checks only gas_used.
    result.gas_used = result.gas_used.checked_add_result(prepaid_send_fees.gas)?;
    result.gas_burnt = result.gas_burnt.checked_add_result(prepaid_send_fees.gas)?;
    result.compute_usage = safe_add_compute(result.compute_usage, prepaid_send_fees.compute)?;
    result.new_receipts.push(new_receipt);

    Ok(())
}
