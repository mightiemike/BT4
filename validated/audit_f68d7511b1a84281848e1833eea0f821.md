### Title
Signer keys with malformed length silently collapse to the all-zero public key, letting unrelated stackers merge voting weight under one phantom signer identity - (File: stackslib/src/chainstate/nakamoto/signer_set.rs)

### Summary
`RawRewardSetEntry::from_pox_4_tuple` reads the `signer` buffer returned by `.pox-4`'s `get-reward-set-pox-address` and, instead of rejecting a buffer whose length is not exactly `SIGNERS_PK_LEN` (33 bytes), silently substitutes an all-zero 33-byte array as the "public key": [1](#0-0) 

This is directly analogous to the external report's class of bug: an address/identity field is allowed to default to the zero value instead of the call being rejected outright.

### Finding Description
`from_pox_4_tuple` fetches the `signer` field as a `(buff 33)` from the Clarity tuple and only length-checks it defensively in Rust:
```
let pk_bytes = if signer.len() == SIGNERS_PK_LEN {
    ...
} else {
    [0; SIGNERS_PK_LEN]
};
``` [2](#0-1) 

`(buff 33)` in Clarity is a *maximum*-length type — it does not require the stored value to be exactly 33 bytes; shorter buffers (including an empty `0x`) are valid values of that type. If `.pox-4` ever stores (or a caller can get stored) a `signer` buffer shorter than 33 bytes for a `stack-stx`/`stack-aggregation-commit`/`delegate-stack-stx` style call, the resulting `RawRewardSetEntry.signer` becomes `Some([0u8; 33])` rather than being rejected.

Downstream, `make_signer_set`/`pox_5_make_signer_set` aggregate entries **by `signing_key`** via a `BTreeMap`/`HashMap` keyed on the raw 33-byte value: [3](#0-2) 

Any number of distinct stackers who (accidentally or intentionally) submit a signer key that fails the length check will all be merged into the *same* `[0;33]` "signer" bucket and their `amount_stacked` will be summed together into one `NakamotoSignerEntry`, which can then cross the weight threshold and be included as if it were one real signer with an aggregated weight: [4](#0-3) 

The consensus threshold check `verify_signer_signatures` computes `total_weight` and `threshold` from exactly this weight list, so if the merged "zero-key signer" ends up holding meaningful weight, that weight is permanently unattributable to any real key pair (an all-zero point is not a valid recoverable secp256k1 public key), because signature recovery in `verify_signer_signatures` can never legitimately produce `[0;33]`: [5](#0-4) 

### Impact Explanation
This does not change the deterministic computation itself — every node parses the same on-chain tuple and reaches the same zero-key aggregate deterministically, so it does not directly cause a state-root divergence between honest nodes. Its harm is instead a **reward/voting-weight sink**: any stacker who supplies (or is forced by a bug in `.pox-4`/`.pox-5` to have recorded) a malformed-length signer buffer has their weight silently pooled into an unusable "ghost" signer slot that can never sign, permanently reducing the effective quorum of real signers and wasting reward-set capacity that should have gone to a legitimate signer or been rejected outright. This is a reward-slot loss and signer-set integrity flaw, not a chain split, since it is reproducible identically by every node from the same contract-state.

### Likelihood Explanation
Reaching this path is gated on `.pox-4`/`.pox-5` actually being able to store a `signer` buffer of length other than 33 bytes. I could not confirm within this repo's `pox-4.clar`/`pox-5.clar` whether the on-chain `stack-stx`/`delegate-stack-stx` entry points enforce a strict 33-byte length on the `signer-key` argument before persisting it (the grep for the exact validation logic in `pox-4.clar` did not return conclusive results in the time available). If the Clarity contract already enforces exact 33-byte length at every insertion point, this Rust-side fallback is unreachable dead code and the finding would not be exploitable. This uncertainty limits confidence in real-world triggerability.

### Recommendation
Change the length mismatch branch in `RawRewardSetEntry::from_pox_4_tuple` to return a hard error (e.g., `ChainstateError::Expects("signer buff has invalid length")`) instead of silently defaulting to `[0; SIGNERS_PK_LEN]`, and audit all `.pox-4`/`.pox-5` entry points (`stack-stx`, `stack-aggregation-commit`, `delegate-stack-stx`, `pox-5` equivalents) to confirm/enforce that `signer`/`signer-key` values are always exactly `SIGNERS_PK_LEN` bytes before being persisted.

### Proof of Concept
