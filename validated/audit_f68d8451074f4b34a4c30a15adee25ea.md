## Title
Stack Exhaustion Denial-of-Service in `get_recursive_transaction_results` via Deep Receipt Chains - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` recursively walks the receipt DAG produced by a transaction to assemble a `FinalExecutionOutcomeView`, calling itself once per `receipt_id` with no depth bound. [1](#0-0)  This function is invoked by `get_final_transaction_result`, which is reachable from unauthenticated JSON-RPC transaction-status queries. [2](#0-1)  A contract can trivially produce an arbitrarily long linear chain of receipts by chaining `promise_then`/`promise_batch_then` callbacks (as demonstrated by the test-contract's `call_promise` chaining mechanism and multi-callback tests), and any RPC caller who then queries the resulting transaction's status forces the node to recurse to a depth proportional to the number of chained receipts, exhausting the call stack.

### Finding Description
`get_recursive_transaction_results` performs plain unbounded Rust recursion — for every receipt in `outcome.receipt_ids`, it calls itself again with no maximum depth or iterative fallback: [3](#0-2)  Unlike other trie/graph traversal code in this same repository which was explicitly converted to iterative/stack-based algorithms specifically "to avoid any potential stack overflows" (e.g. `TrieCachingStorage::get_subtree_size` in `core/store/src/trie/trie_recording.rs`), this transaction-outcome traversal remains naively recursive. [4](#0-3) 

The receipt chain length is entirely attacker-controlled: a single signed transaction's `FunctionCall` action can invoke a contract that repeatedly calls `promise_then` to chain callback after callback (`account_id -> account_id -> account_id -> ...`), each producing a new receipt whose outcome links to the next via `SuccessReceiptId`. Nothing in the runtime bounds the length of such a linear promise chain besides gas/deposit economics, and gas limits per block only bound per-block work, not the total chain length across many blocks (an attacker can pace calls over successive blocks or use large gas budgets in a single call to fan out many sequential `promise_then` hops). The existing test suite already demonstrates multi-hop promise chains across accounts (e.g. `test_two_promises_with_two_callbacks`, `test_account_factory`). [5](#0-4) [6](#0-5) 

Once such a deep receipt chain has executed, any unprivileged client can call the JSON-RPC transaction-status method (`tx` / `EXPERIMENTAL_tx_status`) for the originating transaction hash. This routes to `get_final_transaction_result`, which drives the unbounded recursive walk over the entire receipt chain to build the `FinalExecutionOutcomeView`. [2](#0-1)  A sufficiently long chain will exhaust the thread's call stack, crashing/aborting the RPC/view-client's serving thread.

### Impact Explanation
This is a client/RPC-node-side denial of service: it can crash or hang the RPC-serving thread of any node that answers `tx_status` queries (validators typically also expose RPC or run alongside RPC nodes), matching the CWE-674 uncontrolled-recursion bug class from the external report, ported to the analogous NEAR receipt-DAG traversal. It does not by itself cause loss of funds, state-root divergence, or invalid state transitions — the recursion is purely inside a read/view-serving code path, not inside `apply`/consensus-critical state transition logic. Given the scope rules requiring concrete value-movement/consensus impact for High/Critical, this issue is best characterized as a Medium-severity transaction-triggered denial of service against RPC-node availability, consistent with the CVSS 6.0 rating of the original report.

### Likelihood Explanation
High likelihood of triggering: constructing a long promise chain requires only a deployed contract capable of calling `promise_then` repeatedly (any contract, no special permissions needed) and a modest amount of gas/deposit; triggering the vulnerable code path afterward requires only a single unauthenticated JSON-RPC `tx` query, which is the primary intended use of that RPC method.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative, explicit-stack (or worklist/queue) traversal, matching the pattern already used elsewhere in the codebase (e.g. `TrieCachingStorage::get_subtree_size`, `flatten_nodes`) and bound the maximum number of receipts/iterations it will traverse (returning a partial result or error once exceeded) so that a pathological receipt chain cannot exhaust the stack.

### Proof of Concept
1. Deploy a contract (e.g. the existing `call_promise` test contract) and submit a `FunctionCall` transaction whose args encode a long linear chain of `then`/`batch_then` promise actions targeting a sequence of receiver accounts, as exercised by `test_two_promises_with_two_callbacks` and `test_account_factory`. [5](#0-4) 
2. Repeat/extend the chain (programmatically or across several transactions/blocks) to produce a receipt DAG with tens of thousands of sequential `SuccessReceiptId` links.
3. Once all receipts have executed, issue a JSON-RPC `tx` (or `EXPERIMENTAL_tx_status`) request for the original transaction hash against the RPC node.
4. The node calls `Chain::get_final_transaction_result` → `get_recursive_transaction_results`, recursing once per receipt in the chain, exhausting the serving thread's stack and crashing/aborting that thread. [7](#0-6)

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Returns FinalExecutionOutcomeView for the given transaction.
    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }
