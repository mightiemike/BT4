## Title
Unbounded Gzip Decompression Bomb in `decompress_program` During Cairo0 `declare` Transaction Deserialization - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The RPC gateway path that ingests a `BroadcastedDeclareV1Transaction` (a Cairo0/deprecated `declare` transaction submitted by an unprivileged client) decompresses the attacker-supplied `compressed_program` field with an **unbounded** `GzDecoder`, unlike the analogous Sierra/Cairo0-class-ingestion paths elsewhere in the codebase which explicitly enforce a maximum decompressed size. This mirrors the Redlib `restore_preferences` DEFLATE decompression-bomb bug class (GHSA-g8vq-v3mg-7mrg / CVE-2025-30160): a small compressed payload can expand to an enormous size in memory, causing a denial-of-service on the node that processes the `declare` submission.

### Finding Description
`decompress_program` reads a base64+gzip-compressed program from a client-submitted deprecated (Cairo0) contract class and decompresses it with `flate2::read::GzDecoder`, writing the full output into an in-memory `Vec<u8>` via `read_to_end`, with **no cap on the decompressed size**: [1](#0-0) 

This function is invoked from `user_deprecated_contract_class_to_sn_api`, which converts a user-submitted `DeprecatedContractClass` (from `apollo_starknet_client::writer::objects::transaction`) into the internal `starknet_api::deprecated_contract_class::ContractClass` used to build the transaction to be forwarded/hashed/processed: [2](#0-1) 

This is the exact bug class flagged in the source code itself via the inline TODO: `// TODO(dan): add time and size limits.` immediately above the unbounded decompression call.

By contrast, the codebase demonstrably knows how to guard against this class of bug and does so in sibling code paths:
- `decode_and_decompress_with_size_limit` in `starknet_api::compression_utils` enforces a `max_size` bound using `.take(max_size + 1)` before reading, returning `CompressionError::SizeLimitExceeded` if exceeded: [3](#0-2) 
- The gateway's Sierra-program conversion path (`DeprecatedGatewaySierraContractClass::convert_to_sierra_contract_class`) uses this size-limited helper: [4](#0-3) 
- The p2p/protobuf Cairo0 class conversion path also enforces `MAX_CAIRO0_PROGRAM_SIZE` (4MB) using the same size-limited helper: [5](#0-4) 

The `decompress_program` function in `apollo_rpc`'s RPC-facing `declare`-transaction ingestion path is the outlier that was never hardened with the same size-limit pattern.

### Impact Explanation
An attacker who submits a crafted Cairo0 `declare` transaction (`starknet_addDeclareTransaction` RPC call) with a small, highly-compressible `compressed_program` payload can force the node to allocate an arbitrarily large in-memory buffer during decompression (classic zip-bomb amplification, potentially many orders of magnitude). This can exhaust node memory, causing the RPC/gateway process serving `declare` submissions to crash or become unresponsive — a network-reachable DoS vector directly analogous to the reported Redlib vulnerability, and consistent with the "network unable to confirm new transactions" impact criterion since a crashed/OOM gateway node cannot process further transaction submissions.

### Likelihood Explanation
High. The vulnerable code path (`starknet_addDeclareTransaction` → `user_deprecated_contract_class_to_sn_api` → `decompress_program`) is reachable directly by any unprivileged external caller submitting a Cairo0 `declare` transaction over the public RPC interface, requires no special privileges, and the decompression bomb technique (highly-compressible repeated-byte payloads) is trivial and well-documented to construct.

### Recommendation
Replace the raw `GzDecoder::new(...).read_to_end(...)` call in `decompress_program` (crates/apollo_rpc/src/v0_8/api/mod.rs) with a size-bounded decompression, mirroring `decode_and_decompress_with_size_limit` in `starknet_api::compression_utils` (e.g., wrap the decoder with `.take(max_size)` and reject the transaction with an error if the limit is exceeded), using a bound consistent with `MAX_CAIRO0_PROGRAM_SIZE` used elsewhere in the codebase.

### Proof of Concept
1. Craft a Cairo0 program-body payload consisting of a large amount of trivially compressible data (e.g., all-zero bytes), compress it with gzip to a small size, then base64-encode it to produce `compressed_program`.
2. Submit a `starknet_addDeclareTransaction` RPC request with `contract_class.program = compressed_program` (Cairo0 class).
3. Observe that `decompress_program` decompresses the payload without any size cap, allocating memory proportional to the uncompressed size (which can be made arbitrarily large relative to the compressed request size), leading to excessive memory consumption/OOM on the serving node.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
