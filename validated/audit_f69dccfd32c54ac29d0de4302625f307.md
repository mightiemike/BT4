### Title
Fold-based debt socialization silently absorbs per-asset failures, leaving vault debt and index cache inconsistent - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`socialize-debt-asset` is a fold accumulator used to write off (socialize) bad debt across a borrower's debt assets during a bad-debt event. For each debt entry it (1) calls `vault-socialize-debt`, (2) refreshes the index cache via `map-set index-cache`, and (3) removes the scaled debt from the borrower's position via `contract-call? .v0-market-vault debt-remove-scaled`. Any of these three steps can fail and is wrapped with `unwrap!` returning a `failed-status` accumulator, but the steps already executed for that same debt entry before the failing step are **not undone** — Clarity's `unwrap!` only short-circuits the *current* fold step's return value, it does not roll back state mutations (`map-set`, `contract-call?`) already performed earlier within the same fold iteration. [1](#0-0) 

### Finding Description
Walk through one fold iteration for a given `debt-entry`:
1. `(unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)` — this call mutates vault-level accounting (writes down aggregate debt/liquidity index for the asset) as a side effect *before* the unwrap even evaluates its success. [2](#0-1) 
2. `(map-set index-cache { timestamp: stacks-block-time, aid: asset-id } (unwrap! (vault-accrue asset-id) failed-status))` — this both re-caches the index (permanent mutation of `index-cache`) and can itself fail via `unwrap!`. [3](#0-2) 
3. `(unwrap! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-debt asset-id) failed-status)` — removes the scaled debt from the borrower's position bookkeeping. [4](#0-3) 

If step 3 (`debt-remove-scaled`) fails for this asset (e.g. due to a transient vault-side guard), the fold returns `failed-status` for the whole accumulator (marking `success: false`), causing all *subsequent* debt entries in the fold to be skipped via the early-return guard at the top: `(if (not (get success acc)) acc ...)`. [5](#0-4) 
However, the vault-level write-down from step 1 (`vault-socialize-debt`) and the index-cache refresh from step 2 for *this* asset have already been committed as Clarity map/contract-call side effects prior to the failure — the fold's `failed-status` sentinel only communicates failure to the *caller* of the fold (to decide whether to abort the outer transaction), but it does not itself undo the two writes that already ran. If the outer caller of `socialize-debt-asset` (the top-level fold driver) does not itself `asserts!`/abort on `success: false` before committing the transaction, the debt is socialized (vault write-down applied, cache updated) for that asset while the corresponding per-borrower debt removal for the *remaining unprocessed* assets never executes, and the whole multi-asset socialization stops short — stranding some borrower debt entries un-socialized while the vault-side aggregate accounting for the first asset has already moved.

This matches the "fold that absorbs failure" analog class: a single failed step inside one fold iteration is swallowed into a boolean/sentinel accumulator rather than reverting the whole transaction, so mutations from steps that ran before the failure persist unless an outer `asserts!` on the final accumulator forces a full abort.

### Impact Explanation
If the outer driver of this fold does not immediately abort the transaction on `success: false` (or if a later entry succeeds and overwrites the visible "final" accumulator status in a way that under-reports the partial failure), the market is left with inconsistent debt-socialization state: vault-level debt/liquidity indexes reflect a write-down for assets already processed, while the borrower's own scaled-debt bookkeeping for not-yet-processed assets is untouched and other borrowers' index caches used for interest accrual can be left stale. This falls under temporary/permanent freezing of funds or protocol insolvency risk category, since socialization is the mechanism that keeps total debt commitments solvent versus available vault liquidity — a partially applied socialization directly threatens the accounting invariant the mechanism exists to protect.

### Likelihood Explanation
Likelihood is Medium: it requires the bad-debt/liquidation path to touch a borrower with multiple debt assets and for `vault-socialize-debt`, `vault-accrue`, or `debt-remove-scaled` to fail partway through the batch (e.g. hitting a vault-side invariant on one asset but not others), which is a plausible operational condition during multi-asset bad-debt cleanup rather than a contrived edge case.

### Recommendation
Ensure the top-level caller of the `socialize-debt-asset` fold always checks the final accumulator's `success` field and `asserts!`s on it (forcing the entire transaction, including all prior fold-iteration side effects, to revert atomically) rather than treating `failed-status` purely as an early-return signal for skipping remaining entries. Alternatively, restructure the fold to compute all socialization amounts first (pure calculation) and only perform the mutating `vault-socialize-debt` / `map-set index-cache` / `debt-remove-scaled` calls after every entry has been validated, so a single failure cannot leave earlier entries partially committed.

### Proof of Concept
1. Borrower has two debt entries: asset A (id 1) and asset B (id 2), both to be socialized.
2. Fold processes asset A first: `vault-socialize-debt` succeeds, `map-set index-cache` succeeds, `debt-remove-scaled` succeeds — accumulator remains `success: true`.
3. Fold processes asset B: `vault-socialize-debt` succeeds (vault write-down applied for B), `map-set index-cache` succeeds (cache updated for B), but `debt-remove-scaled` fails (returns err) — `unwrap!` returns `failed-status` for the accumulator.
4. If the outer function that invoked this fold does not `asserts!` on the final accumulator's `success` flag before returning `(ok ...)`, the transaction commits: vault B's aggregate debt/index has already been written down and the index cache for B was refreshed, but the borrower's own scaled debt for asset B was never removed — the borrower's recorded debt and the vault's aggregate accounting are now out of sync. (define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
