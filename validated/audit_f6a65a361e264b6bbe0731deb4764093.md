## Finding

This confirms a real, code-verifiable gap: `TransactionOutput::ensure_match_transaction_info` is the primary local-execution-vs-authenticated-`TransactionInfo` consistency check used by replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`), the debugger, and the chunk executor, but it never validates `state_checkpoint_hash` (the JMT/state root committed on-chain) at all — only `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash` are checked.

### Title
Replay-verify accepts divergent state roots because `ensure_match_transaction_info` never checks `state_checkpoint_hash` - (File: types/src/transaction/mod.rs)

### Summary
`ensure_match_transaction_info` [1](#0-0)  is the function used to verify that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` from the accumulator/ledger. It checks execution status, gas used, the write-set hash against `state_change_hash`, and the event root hash — but it contains no comparison of the locally-computed state-checkpoint (state Merkle root) against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, and the code even documents this gap in a TODO comment [2](#0-1) .

### Finding Description
`TransactionInfo` binds a transaction to four authenticated roots: `state_change_hash` (write-set hash), `event_root_hash`, `state_checkpoint_hash` (state Merkle tree root at checkpoint boundary), and (in V1) `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`. The write-set hash check only proves that write-set *bytes* match; it does not prove the *resulting state tree root* (the actual committed ledger state after applying the write set into the Jellyfish Merkle Tree) matches what consensus/DB has authenticated. `ensure_match_transaction_info` is exactly the function meant to close that gap for replay/verification workflows, since state root computation is a separate step (JMT update in `execution/executor-types/src/state_checkpoint_output.rs` / `execution/executor/src/workflow/do_state_checkpoint.rs`) from write-set/output verification. As written, the function silently omits the state-checkpoint-hash comparison, so a divergence between the locally-computed state root and the authenticated on-chain `state_checkpoint_hash` (e.g., due to a JMT update bug, hot-state/position-state divergence, or any subtle discrepancy introduced by future changes to `update_with_db_reader`) would go undetected by this check.

This directly parallels the "unchecked return value" bug class from the external report: just like `transfer`/`transferFrom` calls that don't check success and thus silently accept a failed operation as if it succeeded, `ensure_match_transaction_info` silently accepts a `TransactionOutput` as "matching" without checking one of its four core authenticated fields, treating an unverified/potentially wrong state as verified.

### Impact Explanation
Callers such as `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` [3](#0-2)  rely on this exact function as the sole per-transaction correctness gate during archive replay verification. If a state-root-affecting divergence exists anywhere in the executor/storage pipeline (independent of write-set content, e.g. in JMT node construction, hot-state merge, or position-state summary logic), replay-verify, the debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`), and the CLI (`aptos-move/cli/src/commands.rs`) would all report success even though the locally computed committed ledger state differs from the authenticated one. This is a proof-integrity gap matching the "Wrong ... state proof accepted as valid" category in the gate: the tooling that is supposed to catch exactly this kind of divergence structurally cannot, because it doesn't compare the field that carries the state-root commitment.

### Likelihood Explanation
This is not a remotely triggerable vulnerability by itself (no external actor can force output through this path), but it is a genuine, unprivileged blind spot in the state-integrity verification tooling: any future correctness bug in state-checkpoint/state-root computation (hot state, position/trading native state roots, JMT batch update, etc.) would be masked by this check rather than caught, undermining the primary safety net used to detect hard-fork-causing divergences before they reach mainnet. The code's own TODO comment at lines 2197–2203 confirms the authors are aware the checkpoint hashes are not validated here, specifically flagging the trading-native state root risk, but the gap for `state_checkpoint_hash`/`hot_state_checkpoint_hash` is unconditional, not just tied to `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, where applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) computed from the locally re-executed state checkpoint against the corresponding fields in `txn_info`, erroring out on mismatch just as it does today for `state_change_hash` and `event_root_hash`. This requires plumbing the locally-computed checkpoint hash(es) into the call sites (`chunk_executor`, `replay_on_archive`, debugger, CLI) since `TransactionOutput` itself does not carry a state-checkpoint hash (it's produced later in the state-checkpoint stage) — the check should be added at (or near) the point where the executor already knows both values.

### Proof of Concept
Not applicable as a remote PoC; this is a logic-gap in a verification routine, not an externally exploitable bug. The proof is structural: read `ensure_match_transaction_info` [1](#0-0)  and observe it performs exactly four `ensure!` checks (status, gas_used, write_set_hash, event_root_hash) and returns `Ok(())` without ever reading `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, then trace its only production caller `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` [4](#0-3)  to confirm no separate state-root comparison is performed elsewhere in that loop.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
