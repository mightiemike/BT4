### Title
Front-running griefing DoS on `AssetIssueContract` token-name reservation - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
The reported bug class is a check-then-act race on a user-chosen unique identifier: `LoanManager.createUserLoan` checks `isUserLoanActive(loanId)` and, if false, sets the loan active — an attacker can observe a pending transaction's `loanId` in the mempool and front-run it with the same `loanId`, permanently blocking the legitimate loan creation. The equivalent pattern exists in java-tron's TRC10 token issuance path, where the uniqueness check on the asset `name` is performed in `validate()` and the actual claim/write happens later in `execute()`, with no reservation or exclusivity enforced atomically for the mempool-visible name.

### Finding Description
`AssetIssueActuator.validate()` rejects a token-issuance transaction if a token with the same name already exists in the `AssetIssueStore`: [1](#0-0) 

The actual persistence of the asset record (the "claim" of the name) happens later, in `execute()`: [2](#0-1) 

Because a transaction's `AssetIssueContract.name` field is visible in the broadcast/pending transaction before it is included in a block, an attacker can observe a victim's chosen token name and submit their own `AssetIssueContract` transaction with the identical `name` (and a higher fee/priority, or simply timing luck), getting it packed first. When the legitimate transaction is later validated, `assetIssueStore.get(name) != null` is true and the transaction reverts with `"Token exists"` — exactly the same TOCTOU/front-running griefing pattern as `LoanManager.createUserLoan`'s `isUserLoanActive(loanId)` check. This is confirmed by the project's own regression test that simulates two competing issuances for the same name and expects the second one to fail: [3](#0-2) 

This uniqueness enforcement is gated by the `AllowSameTokenName` dynamic parameter: the vulnerable exclusive-name path is taken whenever `dynamicStore.getAllowSameTokenName() == 0`: [1](#0-0) 

### Impact Explanation
When the exclusive-name mode is active, an attacker can grief any user attempting to issue a TRC10 token by front-running their transaction with the same `name`, causing the legitimate issuance to permanently revert with `"Token exists"` and forcing the victim to either pick a different name or repeatedly retry (each attempt being front-runnable again). This matches the report's "Griefing" impact category — no profit motive required for the attacker (aside from possibly paying the issuance fee themselves), but it denies the intended token-creation functionality to the legitimate account, degrading platform usability for asset issuance similarly to how the LoanManager bug denies loan creation.

### Likelihood Explanation
Exploitation requires only observing a pending, unconfirmed `AssetIssueContract` transaction (mempool/broadcast visibility) and submitting a copy-cat transaction with the same `name` before the original is packed into a block — a standard, low-cost front-running technique requiring no privileged role, matching the "unprivileged-user" and "no special access needed" profile of the original report. The likelihood is bounded by whether `AllowSameTokenName` is disabled (`0`) on the target network; when enabled (`1`, the long-standing mainnet configuration via governance proposal), this specific name-uniqueness check is skipped and the vector does not apply.

### Recommendation
Do not rely on a public, attacker-visible unique field (`name`/`loanId`-style) as the sole gate for resource creation. Options: (1) derive the identifier deterministically from the creator's account address plus a nonce so it cannot be squatted by a third party, (2) require a commit-reveal scheme for name reservation, or (3) as already effectively done via the `AllowSameTokenName` hard fork, remove global name-exclusivity requirements from the consensus-critical path entirely and enforce uniqueness only within namespaces the creator controls (e.g., per-account, as `AssetIssueV2` already does via auto-incrementing `tokenIdNum`).

### Proof of Concept
Existing project test demonstrates the check-then-act race outcome directly (attacker's earlier-processed same-name issuance causes the victim's subsequent issuance to revert with `"Token exists"`): [3](#0-2) 
In a live network, this is triggered by an attacker monitoring pending transactions for a target `name` and broadcasting their own `AssetIssueContract` with the same `name` field first (e.g., with a higher energy price to be prioritized by block producers).
