### Title
Unprivileged `TransferToGasKey` griefing blocks `DeleteAccount`/`DeleteKey` via the `GasKeyBalanceTooHigh` strict check - (File: `runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`TransferToGasKey` actions are not restricted to be self-only (`actor_id == account_id`), unlike every other gas-key/account-mutating action. Any transaction signer able to submit a receipt to a victim account can add funds to any of that account's *existing* gas keys, pushing the total gas-key balance above `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR). This is the same bug class as the audited `close_withdrawal_window` issue: a third party can deposit value into a resource owned by another party, and a subsequent strict balance-threshold check then blocks the legitimate owner from closing/deleting that resource.

### Finding Description
`check_actor_permissions` in [1](#0-0)  requires `actor_id == account_id` for `WithdrawFromGasKey`, `AddKey`, `DeleteKey`, and `DeleteAccount`, but explicitly allows `TransferToGasKey` from any actor. `action_transfer_to_gas_key` in [2](#0-1)  only checks that the target gas key exists on `account_id`; it does not check who the predecessor/sender is, and simply increments `gas_key_info.balance` by the deposit attached to the action/receipt.

Later, `delete_gas_key` (invoked from `action_delete_key`) enforces a strict check:
```
if gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN {
    result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh { ... });
    return Ok(());
}
``` [3](#0-2) 

`action_delete_account` performs the analogous aggregate check across all of an account's gas keys via `compute_gas_key_balance_sum`, rejecting the whole `DeleteAccount` action if the sum exceeds the same 1 NEAR threshold: [4](#0-3) 

Because `TransferToGasKey` can be sent by anyone (with any deposit) to any account's existing gas key, an attacker can deliberately push a victim's gas-key balance (or the sum across all their gas keys) above 1 NEAR, causing every future `DeleteKey` (for that gas key) and `DeleteAccount` (for the whole account) attempt to fail with `GasKeyBalanceTooHigh`, exactly mirroring the reported Solana bug where dust sent to `window_base_token_account` blocked closing via a strict `amount == 0` check.

### Impact Explanation
This permanently blocks the rightful owner from deleting the gas key or the entire account, since the runtime only burns balances at or below the threshold and provides no sweep/withdraw path once the balance exceeds it (unlike `action_withdraw_from_gas_key`, which the owner *would* normally use — but withdrawing does not bypass the block, it just reduces balance, and can be re-griefed by the attacker before/at the same block as the deletion attempt, since `TransferToGasKey` requires no special permission and can be resent immediately in the deleting transaction's own receipt-application sequence or race against the owner's action). This results in permanently frozen state/funds within the gas key (funds that were validly deposited plus any legitimate top-up), a denial-of-service on account/key lifecycle management, and a griefing vector with real value lock-up (the attacker's deposit itself, plus the owner's own gas-key balance, become undeleteable).

### Likelihood Explanation
Reaching this requires only a single transaction: submit `TransferToGasKey` with `receiver_id` set to any account that already has a gas key (gas keys are visible on-chain via `AddKey` transactions or state queries) and attach a deposit sufficient to push the balance over 1 NEAR (a small, affordable cost). No validator, node, or peer misbehavior is needed — a normal RPC-submitted transaction from any funded account suffices, satisfying the "reachable by unprivileged transaction signer" criterion.

### Recommendation
Restrict `TransferToGasKey` to require `actor_id == account_id` (i.e., only the account itself, via its own access key, may top up its own gas keys), consistent with `WithdrawFromGasKey`/`AddKey`/`DeleteKey`/`DeleteAccount`. Alternatively/additionally, provide a sweep/withdraw path that lets the owner reduce a gas-key balance below the burn threshold even when it currently exceeds it (e.g., allow `WithdrawFromGasKey` regardless of the `MAX_BALANCE_TO_BURN` cap, since that check should only gate the *burn-on-delete* path, not owner-initiated withdrawal), removing the permanent-freeze condition.

### Proof of Concept
1. Victim account `victim.near` adds a gas key with `num_nonces` via `AddKey` (`add_gas_key`, [5](#0-4) ), balance starts at 0 (enforced by `AddGasKeyWithNonZeroBalance` validation).
2. Attacker submits a transaction with `receiver_id = victim.near`, `actions = [Action::TransferToGasKey(TransferToGasKeyAction { public_key: victim_gas_key, deposit: 2 NEAR })]`, funded from the attacker's own account. `check_actor_permissions` allows this since `TransferToGasKey` requires no actor match ( [6](#0-5) ), and `action_transfer_to_gas_key` credits the balance unconditionally ( [7](#0-6) ).
3. `victim.near`'s gas key balance is now 2 NEAR, exceeding `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR).
4. Victim submits `DeleteKey` for that gas key, or `DeleteAccount` — both fail with `ActionErrorKind::GasKeyBalanceTooHigh` per `delete_gas_key` ( [3](#0-2) ) and `action_delete_account` ( [4](#0-3) ), permanently blocking key/account deletion until the balance is brought back under the threshold — which the attacker can repeat to re-grief.

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) | Action::UniversalStateInit(_) => (),
    };
    Ok(())

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
