### Title
Single-transaction atomic AMM trades in the TRC10 `Exchange` pool allow unbounded, single-block price manipulation / arbitrage extraction - (`actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
The Maple report describes how a protocol default forces a single, atomic trade of a huge notional amount against a constant-pool AMM (Balancer), instantly repricing the pool token and creating an outsized, un-mitigated arbitrage window. The java-tron internal TRC10 `Exchange` mechanism (the on-chain bancor-formula AMM used by `ExchangeCreateContract`/`ExchangeTransactionContract`) has the analogous structural weakness: any unprivileged account can submit one `ExchangeTransactionContract` that swaps an arbitrarily large `quant` of tokens against the pool in a single atomic transaction, moving the bonded-curve price by an unbounded amount with no per-trade size cap relative to pool depth and no time-weighted/anti-manipulation guard, only an absolute `balanceLimit` ceiling and a caller-supplied minimum-out (`expected`).

### Finding Description
`ExchangeTransactionActuator.execute()` calls `ExchangeCapsule.transaction()` which invokes the bancor-style `ExchangeProcessor`/`SafeExchangeProcessor` to compute the counter-asset amount from the current two-sided pool reserves in one shot: [1](#0-0) 

The only checks performed in `doValidate()` are: token quant/expected must be positive, the pool must not be closed (zero balance), and the resulting *sell-side* token balance must not exceed `dynamicStore.getExchangeBalanceLimit()`: [2](#0-1) 

There is no check bounding the trade size as a fraction of pool reserves, no cumulative/rate-limited exposure per block, and no protection for the *other* side of the pool (holders/other traders) analogous to a TWAP or max-price-impact guard — only the trader's own `expected` slippage floor is enforced. This means a single broadcast transaction from any account can execute a trade whose size is limited only by the trader's own asset/TRX balance and the `balanceLimit` constant, instantly repricing the pool exactly as described in the Maple report ("the repayment happens at once, this creates a huge arbitrage opportunity" — here, "the trade happens at once").

### Impact Explanation
Because the bancor formula reprices the pool multiplicatively based on `quant / balance`, a large atomic trade can move the effective price of a TRC10 asset drastically within one block, letting the trader (or a colluding party) extract value from anyone relying on the exchange's spot price (e.g., other DApps or contracts reading `getFirstTokenBalance()`/`getSecondTokenBalance()` as an oracle, or subsequent traders in the same block) before the market can react. This is the same "huge arbitrage opportunity from an atomic large-size trade against a constant-pool AMM" bug class as the referenced finding, applied to java-tron's own on-chain AMM rather than an external Balancer pool.

### Likelihood Explanation
Reachable by any account via a normal broadcast transaction (`ExchangeTransactionContract`) with no special privilege, gated only by having sufficient balance of the token being sold and the pool not exceeding `exchangeBalanceLimit`; no admin/witness action is required.

### Recommendation
Introduce a maximum single-trade price-impact/size limit relative to current pool reserves (e.g., cap `sellTokenQuant` to a percentage of `sellTokenBalance` per transaction), and/or a per-block cumulative trade cap on a given exchange pair, mirroring the mitigation ("atomically liquidate and burn") the Maple team ultimately adopted to avoid unbounded atomic repricing.

### Proof of Concept
1. Attacker/creator sets up an `Exchange` pair with reserves R1/R2 via `ExchangeCreateContract` (`ExchangeCreateActuator.execute`). [3](#0-2) 
2. Attacker broadcasts a single `ExchangeTransactionContract` with `quant` equal to a large fraction of R1 (bounded only by `exchangeBalanceLimit` and the attacker's own asset balance), executed atomically by `ExchangeTransactionActuator.execute()`. [4](#0-3) 
3. `ExchangeCapsule.transaction()` applies the bancor formula in one step, producing a large, instantaneous shift in R1/R2 and thus the marginal price, which the attacker (or an accomplice) can immediately arbitrage against external markets or other on-chain consumers of the pool price, with no mechanism preventing this single-block repricing. [5](#0-4)
