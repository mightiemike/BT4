### Title
Gas-abstraction swap slippage protection is self-referential to the manipulable spot swap quote, enabling sandwich extraction of protocol/user funds - (File: x/uexecutor/keeper/execute_inbound_gas.go, x/uexecutor/keeper/outbound.go)

### Summary
Push Chain's gas-abstraction and gas-refund flows fetch a swap quote from an on-chain Quoter contract at execution time and then compute a slippage bound (`minPCOut = quote * 95 / 100`) directly from that same quote, before immediately executing the swap in the same module-originated EVM call. This mirrors the IchiLpOracle bug class: a security bound (there, LP valuation; here, minimum acceptable swap output) is derived from an instantaneous, attacker-manipulable on-chain price rather than a time-weighted or externally-anchored value.

### Finding Description
In `ExecuteInboundGas`, the flow is:
1. `k.GetSwapQuote(sdkCtx, quoterAddr, prc20AddressHex, wpcAddr, fee, amount)` — a spot quote from the Uniswap-style Quoter contract.
2. `minPCOut := quote * 95 / 100` — a 5% slippage tolerance computed from that spot quote.
3. `k.CallPRC20DepositAutoSwap(sdkCtx, prc20AddressHex, ueaAddr, amount, fee, minPCOut)` — the actual swap executed against the same AMM pool, in the same transaction. [1](#0-0) 

The same self-referential pattern exists in the outbound gas-refund path (`applyGasRefund` → `getSwapQuoteForRefund` → `GetSwapQuote` → `minPCOut` → `CallUniversalCoreRefundUnusedGas` with `withSwap=true`): [2](#0-1) [3](#0-2) 

In both flows, `quote` and the resulting `minPCOut` are computed at the moment the module executes the swap — using the pool's current reserve ratio / price, which is the same value an attacker could move immediately beforehand via a large swap in the same pool (front-run), then reverse afterward (back-run). Because the slippage bound is derived from the very quote that the attacker controls, it provides no real protection: the bound moves together with the manipulated price, so the forced swap still executes "within tolerance" of an artificially bad price, and the attacker captures the difference in the back-run. This is functionally identical to the ICHI issue, where `_amountsForLiquidity` used `slot0` (spot, manipulable) instead of a TWAP to compute a value that was then trusted downstream without independent verification.

`GetSwapQuote` and `CallPRC20DepositAutoSwap` themselves are implemented via `evmKeeper.CallEVM`/`DerivedEVMCall` against the Quoter/UniversalCore contracts; I was not able to fully inspect their Solidity implementation within this index, so I cannot confirm whether the underlying pool queried uses `slot0`-equivalent spot pricing or already includes TWAP protection at the contract layer — this should be verified directly.

### Impact Explanation
- `ExecuteInboundGas` is triggered by ordinary, unprivileged user deposits (gas-abstraction inbound flow) and unconditionally attempts the swap with a bound computed from a value the same unprivileged actor can manipulate in the same block.
- `applyGasRefund` handles protocol-controlled gas-fee excess (`PcRefundExecution`) on every outbound — this refund value is also swapped using a self-referential bound.
- An attacker can sandwich either forced swap: manipulate the pool price immediately before the module's quote+swap call, let the module swap execute at the manipulated price (within its own manipulated 5% tolerance), then reverse the price — extracting value from PC/PRC20 liquidity that funds gas abstraction and refunds. This is unauthorized value extraction from protocol/user-controlled funds through a user-reachable execution path (inbound submission, outbound observation) with honest validators/nodes, matching the in-scope impact of "corruption of ... gas fee accounting, refund accounting ... token mapping."

### Likelihood Explanation
Likely to be exploitable whenever:
- The referenced Quoter/pool is a standard AMM with spot-based quoting and is liquid enough to be moved within a single block/transaction by the attacker, and
- The attacker can trigger (or wait for) inbound gas-abstraction swaps or outbound gas refunds, both of which are reachable through ordinary user deposits and outbound observation with no privileged access required.

The severity depends on pool depth/liquidity for the WPC/PRC20 pairs and whether the underlying Quoter contract already applies TWAP protection (unverified from available Go-side code). If the pools are shallow or attacker-seeded, this is highly exploitable; if the Solidity contracts already use TWAP oracles for the Quoter, the risk is mitigated at the contract layer and this Go-side pattern would just be redundant with existing protection — this needs to be confirmed by inspecting the referenced Solidity contracts (`UniversalCore`, Quoter) which are out of the scanned Go index.

### Recommendation
- Do not derive the slippage bound (`minPCOut`) from the same instantaneous quote used to execute the swap in the same call. Instead, use an independent reference price (e.g., a TWAP oracle, or a governance/registry-configured price band) to bound acceptable swap outputs.
- Alternatively, cap the maximum price impact allowed per swap based on pool depth, and/or split large forced swaps to reduce sandwich profitability.
- Audit the Solidity-side Quoter and pool contracts referenced by `GetSwapQuote`/`CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` to confirm whether they already implement TWAP-based pricing; if not, treat this as a live vulnerability affecting both the gas-abstraction inbound swap and the gas-refund outbound swap paths.

### Proof of Concept
Conceptual (cannot be fully executed without contract-level access, since exact pool/quoter implementation wasn't available in the indexed Go code):
1. Attacker submits (or waits for) an inbound gas-abstraction transaction that will trigger `ExecuteInboundGas` for a PRC20/WPC pair with attacker-influenced liquidity.
2. In the same block, immediately before the module executes the swap, attacker performs a large swap against the same pool to depress/inflate the pool price.
3. Module calls `GetSwapQuote` (spot quote reflecting the manipulated price) then computes `minPCOut = quote * 95/100` — the bound is now anchored to the manipulated price. [4](#0-3) 
4. Module executes `CallPRC20DepositAutoSwap` with this manipulated `minPCOut`, which "succeeds" even though the effective price is unfavorable to the protocol/recipient.
5. Attacker reverses their initial swap (back-run), capturing the value lost by the module's forced swap.

Because I could not view the Solidity swap/quoter contract logic (`UniversalCore`, PRC20 auto-swap, Quoter) within the indexed repository content, the exact mechanics of price manipulation (pool type, available liquidity, whether a TWAP already guards the Quoter) remain unverified and should be confirmed with direct contract-source review or a live Devin session with full repository/contract access.

// getSwapQuoteForRefund fetches a Uniswap quote for the gas token refund swap.
func (k Keeper) getSwapQuoteForRefund(ctx sdk.Context, gasToken common.Address, fee *big.Int, amount *big.Int) (*big.Int, error) {
	quoterAddr, err := k.GetUniversalCoreQuoterAddress(ctx)
	if err != nil {
		return nil, err
	}
	wpcAddr, err := k.GetUniversalCoreWPCAddress(ctx)
	if err != nil {
		return nil, err
	}
	return k.GetSwapQuote(ctx, quoterAddr, gasToken, wpcAddr, fee, amount)
}
