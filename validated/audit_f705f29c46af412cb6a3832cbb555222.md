## Title
Replay-verify tooling silently accepts a diverged authenticated position/hot-state root when `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` is on - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the routine used by replay/verification tooling (`db-tool`'s `replay_on_archive`, `aptos-debugger`, and `aptos-move/cli`) to prove that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` committed on-chain. It compares status, gas, write-set hash, and event root hash, but it explicitly does **not** compare the state-checkpoint, hot-state-checkpoint, or `position_state_checkpoint_hash` fields of `TransactionInfo`. The code contains a self-documented TODO acknowledging this gap.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates:
- execution status
- gas used
- write-set hash (`state_change_hash`)
- event root hash

but its trailing comment states: [2](#0-1) 

i.e. it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This is a real, distinct proof-binding gap in the authenticated-commitment surface introduced by the `TransactionInfoV1`/native-trading feature set (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`), which is committed into the transaction accumulator and therefore into consensus-verified ledger state, per [3](#0-2) . These new checkpoint hashes ride inside `TransactionInfoV1`, exactly like the traditional `state_checkpoint_hash`, and are supposed to be an authenticated commitment of the position/hot-state Merkle roots — but the general-purpose "does this locally-computed output match the on-chain TransactionInfo" check does not verify them.

By contrast, the actual block/chunk *commit* path (`DoStateCheckpoint::run`, `DoLedgerUpdate`, and `ChunkResultVerifier::verify_chunk_result` → `ensure_transaction_infos_match`) does perform full-value equality on the entire `TransactionInfo` struct (see [4](#0-3)  and [5](#0-4) ), so state-sync/chunk-execution commit integrity is not affected. The gap is confined to the separate, weaker `ensure_match_transaction_info` helper used by offline/debug replay-verification tools.

### Impact Explanation
This does not corrupt committed ledger state (the commit path remains fully checked), so it does not meet the "wrong write set/root accepted during commit" bar directly. Its impact is limited to giving false assurance in **archive replay-verification tooling** (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger`, `aptos-move/cli`): an operator or auditor running replay-verify against archived history could get a "success" result even though the VM's locally recomputed native-position/hot-state root diverges from the authenticated on-chain root. This weakens a diagnostic/integrity safety net (used to detect divergence bugs, e.g., hard-fork risk in the new native-trading state machine) rather than directly enabling an on-chain state-corruption exploit.

### Likelihood Explanation
Medium-low: the divergence itself would require some other bug in the native-position/hot-state computation logic (a "hard-fork-only divergence" scenario), but if such a bug existed elsewhere, this gap means replay-verify tooling — the safety net meant to catch exactly this class of bug — would fail to catch it, silently.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` between the locally computed output/checkpoint result and the authenticated `TransactionInfo`, gated on whichever of `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled, as already flagged by the in-code TODO.

### Proof of Concept
Not applicable as an on-chain exploit (no unprivileged transaction sequence corrupts committed state); the "proof" is the code-level gap itself:
1. Enable `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or `HOT_STATE_ROOT_IN_TXN_INFO`) on-chain.
2. Introduce (hypothetically) a divergence in native-position/hot-state root computation between two node builds.
3. Run `db-tool replay-on-archive` (which calls `ensure_match_transaction_info`) against the archived chain.
4. Observe the tool reports success despite `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` differing from the authenticated values, because those fields are never compared.

Note: I was not able to fully trace every downstream caller of `ensure_match_transaction_info` in `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` within the available search budget; those call sites appear to be additional replay/debug tooling entry points reinforcing the same gap, but I did not read their full bodies to confirm exact context.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,

        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),

            expected_write_set,

        let event_hashes = self
            .events()

        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;

        // local execution. Validate the checkpoint hashes here before enabling

    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())
        {
            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
    }
