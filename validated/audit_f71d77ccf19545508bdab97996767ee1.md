### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by HMAC signature, allowing cross-tenant webhook replay/spoofing - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`, `packages/apps/shopify-api/lib/webhooks/validate.ts`)

### Summary
This mirrors the `AccountableAsyncRedeemVault` bug class: the code verifies one identity/attribute (the `msg.sender`/HMAC signature over the raw body) but grants access/loads state for a *different*, unverified identity (the `receiver`/`controller` address, here the `X-Shopify-Shop-Domain` header). In the webhook pipeline, `validateHmacFromRequestFactory` [1](#0-0)  computes and checks the HMAC over `rawBody` only, using the app's single shared `apiSecretKey`. The shop domain that determines *whose* session/access-token gets loaded is read separately from the `X-Shopify-Shop-Domain` header in `checkWebhooksHeaders`/`checkEventsHeaders` [2](#0-1)  — a value that is never included in the signed data.

### Finding Description
`shopify.webhooks.validate()` [3](#0-2)  validates a webhook request in two independent steps:

1. `validateHmacFromRequestFactory` verifies `hmac == HMAC-SHA256(apiSecretKey, rawBody)` [1](#0-0) . Only `rawBody` and the `hmac` header are bound together by the signature.
2. `checkWebhookHeaders` then separately extracts `domain`, `topic`, `apiVersion`, `webhookId`, etc. straight from HTTP headers with no cryptographic binding to the HMAC/body [4](#0-3) .

The consuming code in `authenticate.webhook` then takes `check.domain` — the unverified header value — and uses it directly to load that shop's stored offline session and construct an authenticated Admin API client: [5](#0-4) [6](#0-5) 

`ensureValidOfflineSession(params, shop)` loads/creates the offline session keyed purely by this `shop` string, with no additional verification that it matches the entity that actually produced the signed body [7](#0-6) .

Because `apiSecretKey` is a single app-wide secret shared across every merchant who installs the app (it is not per-shop), any attacker who installs the app on their own store can capture a legitimately-signed webhook delivery to their own endpoint (valid `rawBody` + valid `X-Shopify-Hmac-Sha256`), then replay that exact `rawBody`/`hmac` pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a victim shop. `validateHmacFromRequestFactory` only checks body-vs-hmac and passes, since the header isn't part of the signed data. The webhook handler then treats the request as originating from the victim shop, loads the victim's offline `Session`/access token, and executes the app's webhook business logic against the victim's store using the attacker-controlled/replayed payload — this is a session-storage lookup/authentication analog of "receiver != verified account."

### Impact Explanation
An attacker-controlled or attacker-installed test shop can be used to forge webhook events attributed to any other shop that has installed the same app, as long as the shop domain is known/guessable (shop domains are not secret). Depending on what the app's webhook handlers do (e.g., `app/uninstalled` cleanup, order/inventory sync, GDPR data requests, billing state changes), this can lead to:
- Cross-tenant state corruption (deleting/altering another merchant's app data, sessions, or triggering unwanted API calls with the victim's access token).
- Denial of service against a specific victim shop (e.g., forged `app/uninstalled` triggers session/data teardown for a store that never uninstalled).
- Information leakage if the handler logic emits data back based on attacker-supplied replayed payload content combined with victim's authenticated session.

This is a cross-tenant confusion vulnerability reachable from an anonymous HTTP request to the app's public webhook endpoint, requiring only that the attacker has installed the app once (a normal, unprivileged, attacker-obtainable state) to capture one legitimate signed webhook of their own.

### Likelihood Explanation
Moderate-to-high likelihood: exploitation requires (1) the attacker installs the target app on a shop they control (trivial, unprivileged, standard onboarding flow) to receive at least one real signed webhook, and (2) knowledge of the victim's `myshopify.com` domain (public/discoverable). No secret material needs to be broken — only the unsigned header needs to be swapped in the replayed HTTP request, which is fully within an external, anonymous attacker's control. This is a structural design gap (unsigned header driving tenant-scoped authorization) rather than a timing or race condition, so it is reliably reproducible.

### Recommendation
Bind the acting shop's identity to the signed material, or otherwise cryptographically/logically verify that the `X-Shopify-Shop-Domain` header corresponds to the shop that actually produced the signed body:
- Prefer relying on Shopify's per-webhook-subscription secret (if using subscription-specific secrets) rather than a single app-wide secret for HMAC verification, since Shopify now supports per-webhook secrets in some configurations.
- If only the shared `apiSecretKey` is available, incorporate the `domain`/shop header (and ideally `webhookId`/timestamp) into the HMAC-checked data, or otherwise reject requests where the declared domain does not match an independently-obtained identity for that delivery (e.g., cross-check against Shopify's webhook subscription registry / delivery metadata when available).
- At minimum, add replay protection (e.g., track and reject already-seen `webhookId` + timestamp combinations) to prevent naive replay-with-domain-swap attacks even though this doesn't fully close the design gap.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers a real event (e.g., updates a product) causing Shopify to deliver a legitimately signed webhook to the app's webhook endpoint, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: products/update
   X-Shopify-Hmac-Sha256: <valid HMAC over rawBody, computed by Shopify using the app's shared apiSecretKey>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   X-Shopify-Webhook-Id: ...
   X-Shopify-API-Version: ...

   { ...raw JSON body... }
   ```
3. Attacker captures this exact `rawBody` and `X-Shopify-Hmac-Sha256` value.
4. Attacker replays the identical request to the same `/webhooks` endpoint, but changes only:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
   keeping `rawBody` and `X-Shopify-Hmac-Sha256` unchanged.
5. `validateHmacFromRequestFactory` recomputes `HMAC(apiSecretKey, rawBody)` and finds it matches the (unchanged) `hmac` header → validation succeeds [8](#0-7) .
6. `checkWebhooksHeaders` extracts `domain = 'victim-shop.myshopify.com'` from the forged header with no cross-check against the HMAC-verified body [9](#0-8) .
7. `authenticate.webhook` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's stored offline session/access token, and invokes the app's `products/update` webhook handler as if the victim shop sent this event [10](#0-9) .

Note: I was unable to fully verify from the index whether any downstream app-level or Shopify-platform-level mitigation (such as webhook delivery IP allowlisting, or a documented requirement that developers additionally validate `domain` against known merchants) exists outside `shopify-app-js` itself; this analysis is scoped strictly to the code paths visible in this repository.

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
