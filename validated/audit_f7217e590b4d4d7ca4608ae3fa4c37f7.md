### Title
Integer-division precision loss in ancient-storage shrink threshold silently disables ratio-based shrinking — ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
`AncientSlotInfos::clear_should_shrink_after_cutoff` computes a shrink budget (`threshold_bytes`) using integer division of `total_alive_bytes_shrink * percent_of_alive_shrunk_data / 100`. Just like the Sherlock finding (where `long_utilization`/`short_utilization` truncate to `0` when the numerator is small relative to the denominator, silently zeroing out the funding fee), this calculation truncates to `0` whenever `total_alive_bytes_shrink.0 * percent_of_alive_shrunk_data < 100`. When that happens, the very first (and every subsequent) entry in the loop fails the `bytes_to_shrink_due_to_ratio.0 >= threshold_bytes` check immediately, so `info.should_shrink` is cleared for *all* candidates, defeating the ratio-based ancient-shrink selection for that pass.

### Finding Description
`clear_should_shrink_after_cutoff` is responsible for capping how many ancient append-vec candidates are shrunk in a single pass, based on a percentage of the total alive bytes that were flagged for shrinking due to a low alive-ratio: [1](#0-0) 

The threshold is computed with plain integer arithmetic:
```
let threshold_bytes =
    (self.total_alive_bytes_shrink.0 * tuning.percent_of_alive_shrunk_data / 100).min(...)
``` [2](#0-1) 

Because both `total_alive_bytes_shrink.0` and `percent_of_alive_shrunk_data` are `u64`, and the division by `100` happens *after* the multiplication truncates toward zero, `threshold_bytes` becomes `0` whenever the alive-bytes-to-shrink pool is small (e.g., early in a validator's life, or after a period where few storages qualify for ratio-based shrink). Once `threshold_bytes == 0`, the loop condition `bytes_to_shrink_due_to_ratio.0 >= threshold_bytes` (starting at `0 >= 0`) is true on the very first iteration, so `info.should_shrink` is forced to `false` for every entry in `shrink_indexes`, even though these entries were legitimately identified (via `is_candidate_for_shrink`) as having a poor alive ratio in `AncientSlotInfos::add`: [3](#0-2) 

This is structurally the same class of bug as the referenced report: a percentage computed via truncating integer division on a small numerator silently degrades to `0`, and downstream logic that assumes a "reasonable non-zero budget" instead behaves as if the budget were exhausted before any work is done.

### Impact Explanation
When the ratio-driven shrink budget silently collapses to zero, ancient append-vecs that were correctly identified as sparse (low alive/total ratio) are skipped for shrink-by-ratio in that pass and fall through to be considered only by the storage-count-driven `truncate_to_max_storages` path. If the storage count is still under `max_ancient_slots`/`max_resulting_storages`, these sparse ancient storages are not repacked at all in that iteration. Because clean/shrink of ancient storages runs continuously in the background, this manifests as accumulation of dead space in ancient append-vecs over multiple background passes whenever the "total alive bytes eligible for ratio shrink" stays small (a state that is easy to re-enter every pass since the value is recomputed fresh each call) — i.e., disproportionate/needless growth of on-disk accounts storage relative to what the shrink-ratio tuning was designed to bound. This does not corrupt state, cause stale reads, or diverge hashes/capitalization; the correctness of account data is unaffected because `truncate_to_max_storages`'s storage-count limit still eventually forces combination. The impact is limited to a resource-efficiency regression (extra disk usage / I/O amplification), not a consensus or safety break.

### Likelihood Explanation
The condition is reachable in ordinary operation, not merely in adversarial input: `total_alive_bytes_shrink` is a sum of alive bytes across storages that already failed the alive-ratio check, and `percent_of_alive_shrunk_data` is a fixed tuning constant. Any state where this product is under 100 (e.g., a handful of small ancient storages, or a low-activity validator/test cluster) trips the truncation. This is a normal, non-privileged internal computation performed automatically by the background ancient-shrink/pack loop, requiring no attacker action.

### Recommendation
Avoid truncating the percentage calculation to zero by computing with wider precision and rounding conservatively, e.g. use `u128` intermediate math and `div_ceil`, or clamp the result to a minimum of `1` byte (or better, skip the ratio cap entirely when `total_alive_bytes_shrink` is non-zero but the computed threshold would be zero), mirroring how the referenced report's mitigation suggests scaling up or enforcing a minimum non-zero value for a percentage-derived quantity before it gates further logic:
```rust
let threshold_bytes = ((self.total_alive_bytes_shrink.0 as u128
    * tuning.percent_of_alive_shrunk_data as u128)
    .div_ceil(100) as u64)
    .min(...);
```

### Proof of Concept
Given:
- `total_alive_bytes_shrink.0 = 50` (bytes)
- `percent_of_alive_shrunk_data = 1` (1%, a plausible low-alive-ratio pass)

`threshold_bytes = 50 * 1 / 100 = 0` (integer truncation).

In `clear_should_shrink_after_cutoff`'s loop, for the first (and every) `info_index`:
```
bytes_to_shrink_due_to_ratio.0 (0) >= threshold_bytes (0)  // true
=> info.should_shrink = false;
```
All entries in `shrink_indexes`, despite being flagged by `is_candidate_for_shrink` as sparse ancient storages needing shrink, have `should_shrink` reset to `false` and are deferred to the file-count-based selection in `truncate_to_max_storages`, which may not select them if the ancient-storage count is still below its threshold — reproducing the "budget rounds to zero, gating logic silently no-ops" pattern from the referenced funding-fee precision-loss report.

    fn clear_should_shrink_after_cutoff(&mut self, tuning: &PackedAncientStorageTuning) {
        let mut bytes_to_shrink_due_to_ratio = Saturating(0);
        // shrink enough slots to write 'percent_of_alive_shrunk_data'% of the total alive data
        // from slots that exceeded the shrink threshold.
        // The goal is to limit overall i/o in this pass while making progress.
        // Simultaneously, we cannot allow the overall budget to be dominated by ancient storages that need to be shrunk.
        // So, we have to limit how much of the total resulting budget can be allocated to re-packing/shrinking ancient storages.
        let threshold_bytes =
            (self.total_alive_bytes_shrink.0 * tuning.percent_of_alive_shrunk_data / 100).min(
                u64::from(tuning.max_resulting_storages)
                    * u64::from(tuning.ideal_storage_size)
                    * tuning.percent_of_alive_shrunk_data
                    / 100,
            );
        // At this point self.shrink_indexes have been sorted by the
        // largest amount of dead bytes first in the corresponding
        // storages.
        self.best_slots_to_shrink = VecDeque::with_capacity(self.shrink_indexes.len());
        for info_index in &self.shrink_indexes {
            let info = &mut self.all_infos[*info_index];
            self.best_slots_to_shrink
                .push_back((info.slot, info.written_bytes));
            if bytes_to_shrink_due_to_ratio.0 >= threshold_bytes {
                // we exceeded the amount to shrink due to alive ratio, so don't shrink this one just due to 'should_shrink'
                // It MAY be shrunk based on total capacity still.
                // Mark it as false for 'should_shrink' so it gets evaluated solely based on # of files.
                info.should_shrink = false;
            } else {
                bytes_to_shrink_due_to_ratio += info.alive_bytes;
            }
        }
    }
