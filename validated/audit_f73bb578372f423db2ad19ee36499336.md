### Title
Unbounded native recursion when hashing bytecode-segment trees derived from a declared Sierra class - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
`bytecode_hash_node` recursively walks a `NestedIntList` tree that describes how a declared contract's CASM bytecode is segmented, with no depth limit, cap on nesting, or iterative fallback. [1](#0-0) 
The tree's depth is derived from the structure of the Sierra program submitted in a `DECLARE` transaction, and the hashing call happens **outside** the CPU/memory-limited compiler subprocess, in the main process of the `SierraCompiler`/`ClassManager` component.

### Finding Description
When a class is declared, the Sierra program is compiled to CASM inside a resource-limited subprocess (`SierraToCasmCompiler::compile`, bounded by `max_cpu_time`/`max_memory_usage`). [2](#0-1) 
Immediately after that subprocess returns the deserialized `CasmContractClass`, the calling code computes the compiled-class hash **in-process** (not sandboxed): [3](#0-2) 

That hash computation calls `HashableCompiledClass::hash` → `hash_inner` → `bytecode_hash` → `bytecode_hash_node`: [4](#0-3) [5](#0-4) 

`bytecode_hash_node` is a plain Rust function that recurses once per level of the `NestedIntList` (`bytecode_segment_lengths`) that the Sierra-to-CASM compiler produced for that class:
```
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
{
    if node.is_leaf() { ... }
    else {
        let inner_nodes = node.iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))   // <-- unbounded native recursion
            .collect_vec();
        ...
    }
}
``` [6](#0-5) 

The segment-length tree is generated from the function/branch structure of the compiled Sierra program (functions can be nested by segmenting on branches). A contract declarer fully controls the Sierra program's structure (up to the size limits `max_bytecode_size`, `DEFAULT_MAX_BYTECODE_SIZE = 80*1024` felts), so a deeply, degenerately nested control-flow structure can force the compiler to emit a bytecode-segment tree whose *depth* — not just node count — is very large (e.g., a long chain of single-child nested nodes rather than a shallow, wide tree). Because `bytecode_hash_node` recurses natively per tree level with no maximum-depth check, sufficiently deep nesting drives native stack consumption and can exhaust the thread stack, causing the hosting process to abort (Rust aborts on stack overflow; it cannot be caught with `catch_unwind`).

Unlike the CASM compilation step itself — explicitly isolated in a subprocess with CPU/memory bounds precisely because compiler crashes must not affect the sequencer (`compile_with_args`/`ResourceLimits`, see `apollo_compile_to_casm/src/compiler.rs` and the `memory_limit_error_message` regression test showing crashes are caught out-of-process) — the post-compilation hash computation runs unprotected inside the long-lived `SierraCompiler`/`ClassManager` component process. A stack-overflow abort there terminates that whole component, not just the one request.

The same unbounded-recursion pattern exists in the Starknet OS's Rust hint helper that (re)builds this tree during OS re-execution, `create_bytecode_segment_structure_inner` in `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`, and in the corresponding `BytecodeSegmentNode::hash` method, which is likewise pure Rust recursion with no depth bound. [7](#0-6) [8](#0-7) 

This is the direct analog of CVE-2015-3227 (unbounded XML/document tree depth causing `SystemStackError`/stack overflow): here the "document" is the compiler-derived bytecode-segment tree, and the "parser" is the native Rust hash-tree walker with no depth ceiling, reachable from an ordinary `DECLARE` transaction.

### Impact Explanation
A successful stack overflow aborts the Rust process hosting the hash computation:
- If it happens in the `SierraCompiler`/`ClassManager` component (`apollo_compile_to_casm`/`apollo_class_manager`), that whole component crashes, halting processing of further `DECLARE` transactions (and any transaction depending on class-manager availability) until the process is restarted — matching "a network unable to confirm new transactions" for the affected node.
- If it happens during Starknet OS re-execution (`create_bytecode_segment_structure_inner`/`BytecodeSegmentNode::hash`), it can crash the OS/prover pipeline that must re-execute the block, which is part of state-commitment production and thus block finalization.

This is a Medium-severity denial-of-service: reachable by any single, unprivileged `DECLARE` transaction sender, and does not require attacker-controlled fees, other privileged access, or a malicious peer/operator.

### Likelihood Explanation
Reachability requires only a normal declarer submitting a Sierra class through the gateway/class-manager pipeline. Whether an actual stack overflow is trivially achievable depends on:
1. The nesting depth the Sierra→CASM compiler (`cairo-lang-starknet-classes`, external to this repo) can be induced to produce for the `bytecode_segment_lengths` structure via crafted Cairo/Sierra control flow, and
2. The default thread stack size of the hosting process (not shown in this repo's config for `apollo_compile_to_casm`/`apollo_class_manager`, unlike the blockifier's explicitly pre-allocated `stack_size` for native execution).

The `max_bytecode_size` limit (80 KiB felts) bounds total code size but does not bound tree *depth*, since depth is governed by segmentation topology, not by total data volume — a long, thin chain of single-child segments can be built well within the size limit. Because the exact depth achievable via the external compiler's segmentation logic could not be verified from this repo alone, likelihood is assessed as Medium rather than High/Critical.

### Recommendation
- Convert `bytecode_hash_node` (and `bytecode_hash`) in `crates/starknet_api/src/contract_class/compiled_class_hash.rs`, and `create_bytecode_segment_structure_inner`/`BytecodeSegmentNode::hash` in `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`, into iterative (explicit-stack/worklist) implementations, or add an explicit maximum-depth check that returns an error before recursing further.
- Alternatively/additionally, validate and cap the depth of `bytecode_segment_lengths` immediately after CASM compilation (still inside the resource-limited subprocess, before returning `CasmContractClass` to the parent process), rejecting classes whose segment tree exceeds a sane depth bound.
- Run the post-compilation hash computation inside the same sandboxed/resource-limited execution context as compilation itself, rather than in the long-lived component process, so a crash there cannot take down `SierraCompiler`/`ClassManager`.

### Proof of Concept
Conceptual (exact external-compiler behavior not verifiable from this repo alone):
1. Craft a Cairo/Sierra contract whose control-flow forces the Sierra-to-CASM compiler to emit a `NestedIntList` bytecode-segment structure that is a long, thin chain of nested single-child "Node" segments (e.g., via many sequentially nested branches/functions), rather than a shallow/wide tree, while staying within `max_bytecode_size` (80 KiB felts).
2. Submit this as a `DECLARE` transaction through the gateway.
3. The class passes subprocess-sandboxed compilation (bounded by CPU/memory limits) and returns a `CasmContractClass` whose `bytecode_segment_lengths` has depth N.
4. `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:69`) then calls `executable_class.hash(&HashVersion::V2)` in the unsandboxed component process, triggering N nested native calls into `bytecode_hash_node`.
5. For sufficiently large N (bounded only by the compiler's willingness to segment that deeply, and by the process's thread stack size), the native stack is exhausted and the process aborts, taking down class-declaration processing for that node until restart.

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

/// Computes the compiled class hash for a given hashable class using the specified hash algorithm.
fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))

impl BytecodeSegmentNode {
    pub(crate) fn hash<H: HashFunction>(&self) -> StarkHash {
        match self {
            BytecodeSegmentNode::Leaf(leaf) => H::hash_array(&leaf.data),
            BytecodeSegmentNode::InnerNode(inner_node) => {
                let flatten_input: Vec<_> = inner_node
                    .segments
                    .iter()
                    .flat_map(|segment| [Felt::from(segment.length), segment.node.hash::<H>()])
                    .collect();
                H::hash_array(&flatten_input) + Felt::ONE
            }
        }
    }

/// Creates the bytecode segment structure from the given bytecode and bytecode segment lengths.
pub(crate) fn create_bytecode_segment_structure(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
) -> Result<BytecodeSegmentNode, OsHintError> {
    let (structure, total_len) =
        create_bytecode_segment_structure_inner(bytecode, bytecode_segment_lengths, 0);
    // Sanity checks.
    if total_len != bytecode.len() {
        return Err(OsHintError::AssertionFailed {
            message: format!(
                "Invalid length bytecode segment structure: {}. Bytecode length: {}.",
                total_len,
                bytecode.len()
            ),
        });
    }

    Ok(structure)
}
