### Title
Anonymous front-running of `ExchangeTransactionContract` allows griefing/sandwiching of other users' TRC10 Bancor-exchange trades - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
java-tron implements an on-chain Bancor-style constant-formula AMM for TRC10↔TRX/TRC10↔TRC10 swaps (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`), backed by `ExchangeCapsule`/`ExchangeProcessor`. Any account can submit an `ExchangeTransactionContract` to trade against the pool's `firstTokenBalance`/`secondTokenBalance`. Because trade execution mutates the pool balances used to price the *next* trade, and there is no delay, minimum-hold-time, or anti-sandwich protection, an attacker can front-run/back-run a victim's known pending trade to shift the pool ratio, causing the victim's trade to receive materially less output (or to revert via the `getExpected` slippage check), and then reverse the position to recover most of the moved liquidity - directly analogous to the TrueFi report's front-run-borrow/repay griefing pattern against NAV-dependent withdrawal pricing.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, ...)` which directly mutates the exchange's `firstTokenBalance`/`secondTokenBalance` state based on the bonding-curve formula in `ExchangeProcessor.exchange()`: [1](#0-0) [2](#0-1) [3](#0-2) 

Any address (no whitelist, no borrower eligibility, no owner check) can call this at will, exactly like Alice in the TrueFi report needing only to be "eligible" - here there is no eligibility requirement at all, so the attack surface is strictly easier to reach. The only user protection is a client-supplied minimum-output check performed at validation time: [4](#0-3) 

Since `tokenExpected` is computed off-chain by the victim before broadcasting, an attacker observing the pending transaction in the mempool can submit a same-direction trade immediately before it (front-run), shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for the victim. This either (a) causes the victim's `anotherTokenQuant < tokenExpected` check to fail, reverting the victim's transaction (griefing/DoS), or (b) if the victim did not set a tight `expected` bound, causes them to receive a worse rate than intended. The attacker can then immediately reverse their own position with an opposite-direction trade (or `ExchangeWithdrawActuator`) to restore the pool ratio and recoup most of the moved liquidity, repeating the attack against many victims over time — mirroring the TrueFi report's "Alice borrows right before Bob's redeemNFT() then repays immediately, repeating over and over" pattern, but here against the exchange pool's NAV/price rather than a lending pool's liquidity.

### Impact Explanation
Victims submitting `ExchangeTransactionContract` swaps can be forced into either a failed transaction (wasting bandwidth/energy fees, a DoS) or an economically worse trade execution than expected, at low, repeatable cost to the attacker (only the algorithm's inherent rounding loss and transaction fees, no capital lock-up since the curve is fully invertible within the same or adjacent blocks). This is an unprivileged accounting/market-math corruption reachable by any broadcast transaction, matching the "asset or accounting corruption... via protocol implementation" acceptance criterion.

### Likelihood Explanation
Likelihood is high: no whitelisting or eligibility gating exists for calling `ExchangeTransactionActuator` (unlike TrueFi's borrower whitelist), the pool state (`firstTokenBalance`/`secondTokenBalance`) is fully public via `ExchangeStore`/`ExchangeV2Store`, and pending transactions are visible before block inclusion, making ordering manipulation (front-running within the same block/queue or across adjacent blocks by a block-producing or well-connected node) straightforward. The attack requires no privileged role, no leaked keys, and no malicious-peer assumptions — only an ordinary account and knowledge of a victim's pending swap.

### Recommendation
Introduce trade-size/impact limits or a per-block price-impact cap on `ExchangeCapsule.transaction()`, and/or require victims to always supply a tight `tokenExpected` bound enforced with a stricter default; additionally consider a minimum block-delay/commit-reveal or TWAP-based pricing for `ExchangeTransactionContract` rather than instantaneous spot pool balances, so that a single-block sandwich cannot materially move the executed price, closing the same attack class the TrueFi report recommends addressing via a borrow/transfer delay.

### Proof of Concept
1. Alice observes Bob's pending `ExchangeTransactionContract` (sell `tokenA` for `tokenB`, exchangeId=X) in the network/mempool with a known `getExpected()` (min output).
2. Alice broadcasts her own `ExchangeTransactionContract` on the same exchangeId, same direction as Bob, with higher fee/priority so it lands first, shifting `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()`.
3. Bob's transaction executes against the worsened pool ratio; `ExchangeTransactionActuator.doValidate()`'s check `anotherTokenQuant < tokenExpected` at [4](#0-3)  either reverts Bob's trade or Bob receives less than intended.
4. Alice immediately submits an opposite-direction `ExchangeTransactionContract` (or `ExchangeWithdrawActuator`) to restore/exploit the pool ratio, recovering most of her capital, and repeats against subsequent victims.

```java
  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
```

```java
  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
```
