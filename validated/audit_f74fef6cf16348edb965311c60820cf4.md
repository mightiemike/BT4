### Title
Missing Slippage Protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` Enables Front-Running/Sandwich Attacks on TRX/TRC10 Exchange Pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The Bancor-style `Exchange` pools in java-tron allow any account to inject or withdraw liquidity via `ExchangeInjectContract` and `ExchangeWithdrawContract`. Unlike `ExchangeTransactionContract` (buy/sell), which carries an `expected` field to bound slippage, neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` allow the caller to specify a minimum/maximum acceptable counter-token amount. This mirrors the reported bug class: an unprivileged actor can move the pool ratio immediately before a victim's inject/withdraw transaction executes, causing the victim to receive (or supply) a worse ratio than expected, with no on-chain mechanism to abort the transaction.

### Finding Description
`ExchangeTransactionContract` explicitly documents and enforces a minimum-received-amount check (`expected`) to defend traders against price movement/front-running: [1](#0-0) 

By contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — no counterpart-amount bound: [2](#0-1) 

`ExchangeInjectActuator.execute()` computes the required amount of the paired token purely from the *current* on-chain pool ratio at execution time (`firstTokenBalance`, `secondTokenBalance`), and unconditionally debits the account for that computed `anotherTokenQuant`: [3](#0-2) 

The validate step re-derives the same ratio-dependent `anotherTokenQuant` from the pool state at validation time and only checks balance sufficiency and pool caps — there is no user-supplied bound comparing the *expected* value against the actual computed value: [4](#0-3) 

`ExchangeWithdrawActuator` has the same structural gap: the returned `anotherTokenQuant` (the amount of the second token a withdrawer receives) is computed from the live pool ratio with no user-specified floor: [5](#0-4) 

Because any account may submit `ExchangeInjectContract`/`ExchangeWithdrawContract` for any exchange (subject only to balance/type checks), and because `ExchangeTransactionContract` (buy/sell) can freely move the pool ratio in the same or a preceding block, an attacker can:
1. Observe a pending large `ExchangeInjectContract` (or `ExchangeWithdrawContract`) in the mempool.
2. Submit an `ExchangeTransactionContract` that shifts `firstTokenBalance`/`secondTokenBalance` favorably for the attacker just before the victim's transaction is packed into the same or a subsequent block.
3. The victim's inject/withdraw then executes against the manipulated ratio, causing the victim to inject a disadvantageous ratio of tokens (locking more value than intended) or receive fewer tokens on withdrawal than they anticipated when they signed the transaction — with the deficit becoming attacker profit after reversing the trade.

This is directly analogous to the reported "front-run deposits to steal pool tokens" bug class: an unprivileged party can manipulate pricing/ratio parameters between the user's signature and on-chain execution, and the affected instructions (`ExchangeInjectContract`/`ExchangeWithdrawContract`) provide no slippage-bound field to let the instruction abort, whereas the sibling instruction (`ExchangeTransactionContract`) already has this protection via `expected`.

### Impact Explanation
A liquidity provider injecting into or withdrawing from an `Exchange` pool can be forced to accept an economically worse token ratio than what was true when they signed and broadcast their transaction, resulting in direct loss of value to a front-running attacker. This is a concrete accounting/value-theft impact reachable by any unprivileged account, not a theoretical or trusted-role-only issue — anyone can create the attacking `ExchangeTransactionContract`, and anyone can be the victim submitting `ExchangeInjectContract`/`ExchangeWithdrawContract`.

### Likelihood Explanation
The `Exchange` module (TRX/TRC10 exchange, distinct from the newer TRC10 `Market`) is a longstanding, always-reachable actuator path with no privileged gating on `ExchangeInjectContract`, and `ExchangeWithdrawActuator` restricts withdrawal to the pool creator but still lacks slippage protection for that creator against sandwiching by third parties trading via `ExchangeTransactionContract` immediately beforehand. Given that the codebase already demonstrates awareness of this exact risk class (by adding `expected` to `ExchangeTransactionContract`) but did not extend the same protection to inject/withdraw, exploitation requires only ordinary transaction submission/mempool visibility — no special privileges.

### Recommendation
Add an `expected`/slippage-bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and have `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate the computed `anotherTokenQuant` against the caller-supplied bound, aborting the transaction if the ratio has moved unfavorably beyond the caller's tolerance.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim intending to inject `tokenQuant` of `firstTokenID` at the currently known ratio (`firstTokenBalance`/`secondTokenBalance`).
2. Attacker submits an `ExchangeTransactionContract` selling a large amount of `firstTokenID` into the pool (within their own configured `expected` bound), which shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for subsequent injectors, and gets it included immediately before the victim's transaction.
3. Victim's `ExchangeInjectContract` executes via `ExchangeInjectActuator.execute()` computing `anotherTokenQuant` from the now-shifted ratio (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java:73-82`), forcing the victim to lock in more of the paired token than intended, with no field available to specify and enforce a minimum/maximum acceptable ratio.
4. Attacker reverses their trade via another `ExchangeTransactionContract`, restoring the pool ratio and extracting the value differential caused by the victim's unprotected injection.
