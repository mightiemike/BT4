This confirms the binding is enforced cryptographically. In `BitcoinVerifier::verify_transactions`, each blob's `wtxid` is checked against `calculate_wtxid(tx)` for every transaction in the completeness proof — `if &calculate_wtxid(tx) != wtxid { return Err(ValidationError::RelevantTxNotInProof); }` [1](#0-0) , and the full set of wtxids is bound to the block header's witness-commitment merkle root via the coinbase witness commitment check [2](#0-1) . This means `blob.wtxid()` handed to `run_l1_block` is exactly `wtxid(tx)` for the actual Bitcoin transaction included and merkle-proven in that DA block — it is not attacker-assignable independent of transaction content.

## Binding being tested

`ChunkAccessor::get(wtxid)` returns the body stored via `ChunkAccessor::insert(blob.wtxid(), chunk, ...)` for the `DataOnDa::Chunk` blob whose actual wtxid is `wtxid` [3](#0-2) [4](#0-3) . The claimed equality is:

`ChunkAccessor::get(wtxid) == chunk body of the Bitcoin transaction whose SHA256d(SHA256d(tx bytes)) == wtxid`

Since `wtxid` is a cryptographic hash of the reveal transaction's serialized bytes (including witness), and the verifier enforces `calculate_wtxid(tx) == wtxid` before the blob is ever handed to the circuit, an attacker cannot make two different chunk bodies map to the same `wtxid` key without finding a SHA256d collision/second-preimage — computationally infeasible and out of scope (cryptographic break).
