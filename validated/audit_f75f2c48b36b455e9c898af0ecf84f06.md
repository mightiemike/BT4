### Title
Uncontained Exception From Untrusted Event-Plugin Escalates To Fatal `TronError`, Crashing The Entire Node - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
The `SponsorVault` finding is a "single point of failure" bug class: a call to a pluggable/third-party component, without exception isolation, propagates and aborts a critical, otherwise-independent protocol operation. In java-tron, `Manager.blockTrigger` calls into `EventPluginLoader`, which dynamically loads third-party PF4J plugins that implement `IPluginEventListener` and execute arbitrary listener code (`handleBlockEvent`, etc.) for every produced/synced block. [2](#0-1) [3](#0-2)  Instead of degrading gracefully, any exception thrown by the plugin is caught, wrapped, and re-thrown as `TronError`, which by design causes `System.exit()` for the whole node process. [1](#0-0) 

### Finding Description
`blockTrigger()` is invoked for every pushed block (from `pushBlock` -> `processBlock` sequence). [4](#0-3)  It calls `postBlockTrigger(block, false)` and `postSolidityTrigger(newSolid)`, which ultimately dispatch to `EventPluginLoader.getInstance().postBlockTrigger`/`postSolidityLogTrigger`/etc. [5](#0-4)  These methods iterate `eventListeners` (loaded via PF4J from an operator-configured external `.jar`/native plugin path) and invoke listener callbacks directly, without any per-listener isolation. [3](#0-2) 

Any `RuntimeException` thrown inside a plugin listener callback (bug, incompatible plugin version behavior, native-queue/serialization failure, etc.) is caught by the generic `catch (Exception e)` in `blockTrigger`, but rather than being neutralized it is wrapped and re-thrown as a fatal `TronError`. [6](#0-5)  The class-level Javadoc on `TronError` states explicitly that it must not be caught and that its purpose is to trigger `System.exit(int)` via the thread's uncaught exception handler. [1](#0-0)  A dedicated unit test (`ManagerTest.blockTrigger`) confirms this exact behavior: mocking `postBlockTrigger` to throw a `RuntimeException` results in `blockTrigger` throwing `TronError` with `ErrCode.EVENT_SUBSCRIBE_ERROR`. [7](#0-6) 

This is structurally identical to the SponsorVault bug: a call into an external/pluggable dependency during a core, per-block operation is not isolated with a fail-safe (try/catch that swallows and logs), so a defect in the third-party component takes down far more than itself. Notably, the codebase already recognizes and mitigates this exact pattern elsewhere — `postContractTrigger` wraps the same kind of plugin dispatch (`contractTriggerCapsule.processTrigger()`) in a `try { } catch (Throwable throwable) { logger.warn(...); }` block specifically to avoid propagating plugin failures. [8](#0-7)  `blockTrigger`, however, does the opposite: it intentionally converts the caught exception into a fatal, unswallowable error.

### Impact Explanation
Where the SponsorVault bug only disrupts a single domain's cross-chain relayed transfers (recoverable by resetting the vault address), this java-tron analog is more severe: any bug or incompatibility in an event-subscribe plugin (a component explicitly designed to be pluggable/third-party, versioned independently, per `MIN_PLUGIN_VERSION` compatibility checks) [9](#0-8)  causes the entire full node process to terminate via `System.exit()`. [1](#0-0)  Because `blockTrigger` runs on the block-push/sync path for every node with event subscription enabled, a single crafted or buggy trigger payload/plugin defect halts block processing/production for that node, which is a denial-of-service on a core network-participant process, not merely a single feature.

### Likelihood Explanation
Likelihood is bounded by the fact that event plugins are operator-selected/configured (not attacker-controlled by default), similar to how `SponsorVault` is deployed by a trusted-but-unaudited third party per domain. However, exploitation only requires that any of: (a) the plugin has a bug triggered by adversarial-but-otherwise-valid on-chain data (attacker-controlled contract logs/events feeding into `toJsonString(trigger)` or listener logic), (b) a version-mismatch edge case, or (c) transient I/O failure in `NativeMessageQueue`, occurs during normal block processing — all of which are plausible operational conditions rather than requiring a malicious operator.

### Recommendation
Do not escalate exceptions from event-plugin invocation to a fatal `TronError`. Wrap `postBlockTrigger`/`postSolidityTrigger` calls (and the plugin dispatch inside `EventPluginLoader`) the same way `postContractTrigger` already does — catch `Throwable`, log it, and continue block processing, ensuring an external plugin's failure never crashes node consensus/sync.

### Proof of Concept
1. Enable event subscription with a plugin configured (`Args.getInstance().getEventPluginConfig()`), so `eventPluginLoaded = true`.
2. Have the plugin's `IPluginEventListener.handleBlockEvent` (or `handleContractEventTrigger`/`handleTransactionTrigger`) throw a `RuntimeException` for a particular block/event payload — this can occur due to a plugin bug in parsing on-chain data attacker can shape (e.g., unusual log/event contents).
3. `pushBlock` -> `processBlock` -> `blockTrigger` is invoked for the incoming block; `postBlockTrigger` propagates the listener's `RuntimeException`. [10](#0-9) 
4. `blockTrigger`'s `catch (Exception e)` wraps it into `new TronError(e, TronError.ErrCode.EVENT_SUBSCRIBE_ERROR)` and re-throws. [6](#0-5) 
5. Per `TronError`'s documented contract, the uncaught `Error` reaches the thread's default uncaught-exception handler and the process calls `System.exit()`, confirmed by `ManagerTest.blockTrigger` reproducing the `TronError` throw from a mocked plugin failure. [7](#0-6)

  void blockTrigger(final BlockCapsule block, long oldSolid, long newSolid) {
    // post block and logs for jsonrpc
    try {
      if (CommonParameter.getInstance().isJsonRpcHttpFullNodeEnable()) {
        postBlockFilter(block, false);
        postLogsFilter(block, false, false);
      }

      if (CommonParameter.getInstance().isJsonRpcHttpSolidityNodeEnable()) {
        postSolidityFilter(oldSolid, newSolid);
      }

      if (EventPluginLoader.getInstance().getVersion() != 0) {
        lastUsedSolidityNum = newSolid;
        return;
      }

      // if event subscribe is enabled, post block trigger to queue (real-time, not removed)
      postBlockTrigger(block, false);
      // if event subscribe is enabled, post solidity trigger to queue
      // (also emits solidified-mode block/transaction triggers)
      postSolidityTrigger(newSolid);
    } catch (Exception e) {
      logger.error("Block trigger failed. head: {}, oldSolid: {}, newSolid: {}",
          block.getNum(), oldSolid, newSolid, e);
      throw new TronError(e, TronError.ErrCode.EVENT_SUBSCRIBE_ERROR);
    }
  }
