### Title
Global contract references by `AccountId` give the referenced account's owner silent, retroactive code-execution control over every account that has "used" it — ([File: runtime/runtime/src/global_contracts.rs])

### Summary
The `Perennial::Collateral` bug lets an unverified, caller-supplied "product" become a trusted authority that can arbitrarily control a user's collateral. The structural analog in nearcore is `UseGlobalContractAction` with `GlobalContractDeployMode::AccountId` / `GlobalContractIdentifier::AccountId`: any account can point its own contract slot at another account's global contract by that account's `AccountId`, but the reference is a live pointer, not a snapshot. The referenced account's owner can redeploy new code under that same `AccountId` identifier at any later time, and every account that previously "used" it will silently start running the new code — without any re-confirmation, allow-listing, or verification that the code is still what the user originally trusted.

### Finding Description
`AccountContract::GlobalByAccount(AccountId)` is stored on the "using" account and is resolved dynamically at execution time by looking up whatever code currently lives under `TrieKey::GlobalContractCode { identifier: GlobalContractIdentifier::AccountId(id) }` [1](#0-0) .

`action_use_global_contract` / `use_global_contract` only checks that *some* code currently exists at the given identifier — it performs no check that the code is the same as when the account first opted in, nor any check tying the identifier to a vetted or immutable source: [2](#0-1) 

`action_deploy_global_contract` lets the owner of `account_id` redeploy code under `GlobalContractDeployMode::AccountId` at will, and this is explicitly documented as mutable-by-design: "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users" [3](#0-2) , and further: "the owner to update the contract for all its users" [4](#0-3) .

Just like `Collateral` trusting an arbitrary `product` address to report maintenance amounts, the "using" account trusts an arbitrary `AccountId` to supply the code that will execute *with the using account's own permissions and balance* on every future function call, indefinitely, with no mapping or factory-style registry that pins the code to what was reviewed/trusted at opt-in time.

### Impact Explanation
Because the referenced code executes as the "using" account's own contract, a global-contract owner (or anyone who compromises/social-engineers that owner's account) can:
1. Publish benign code and let unrelated accounts opt in via `UseGlobalContractAction`.
2. Later redeploy malicious code under the same `AccountId` (`action_deploy_global_contract`, `initiate_distribution`) — e.g., a hidden method that issues a `Transfer` action moving the "using" account's entire NEAR balance to an attacker-controlled account.
3. Have that malicious method invoked via an ordinary `FunctionCall` receipt/RPC call against the victim account — the code runs with the victim account's own execution context, so it can freely construct promises to drain the victim's balance.

This is concrete unauthorized value movement (funds leaving an account without the account's fresh, informed consent), reachable purely through transactions any unprivileged signer/relayer can send: `DeployGlobalContractAction` (by the malicious owner) and a subsequent `FunctionCall` (by anyone) on the victim account.

### Likelihood Explanation
The attack requires the victim to have opted into an `AccountId`-mode global contract (an explicit, deliberate action, similar to Perennial's product-owner "freedom" model), and for the code owner to be malicious or compromised after the fact. This mirrors the judged Medium severity of the original finding: it is contingent on external factors (a victim choosing to trust a mutable reference, and the reference later turning malicious) rather than being unconditionally exploitable, but it is straightforward to execute once those conditions hold, and nothing in the protocol prevents or warns about it.

### Recommendation
- Pin the code a "using" account commits to at the time of `UseGlobalContractAction` (e.g., record the code hash actually observed at that identifier at the time of use), so that later updates to the `AccountId`-keyed global contract cannot silently change behavior for accounts that already opted in.
- Alternatively, require an explicit re-confirmation/opt-in (a new `UseGlobalContractAction`) before an account picks up a newer version of an `AccountId`-mode global contract, rather than resolving the reference dynamically on every call.
- At minimum, surface this mutability prominently in wallets/RPC tooling (e.g., `ViewGlobalContractCodeByAccountId`) so callers can detect when the code behind an `AccountId` identifier they depend on has changed since they last reviewed it.

### Proof of Concept
1. Attacker account `A` deploys a benign global contract with `DeployGlobalContractAction { deploy_mode: AccountId }` (see `action_deploy_global_contract`) [5](#0-4) .
2. Victim account `V` sends `UseGlobalContractAction { contract_identifier: GlobalContractIdentifier::AccountId(A) }`, setting `V.contract = AccountContract::GlobalByAccount(A)` [2](#0-1) .
3. Later, `A` redeploys new code under the same `AccountId` mode containing a public method `drain()` that issues `Transfer` of the calling account's full balance to `A`.
4. Anyone submits a `FunctionCall` receipt targeting `V` calling `drain` — this executes with `V`'s own account context (its balance, its promise-issuing rights), moving `V`'s funds to `A` without `V`'s renewed consent.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
