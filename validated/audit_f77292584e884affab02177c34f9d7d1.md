Based on the code I was able to review, there is a real logic gap in `try_start` worth flagging, though I could not fully verify the caller-side guard in `block.move` before running out of tool calls (noted below).

### Title
Chunky DKG session can be silently discarded by `try_start` before completion when the accompanying regular DKG has already finished - (`File: aptos-move/framework/aptos-framework/sources/reconfiguration_with_dkg.move`)

### Summary
`reconfiguration_with_dkg::try_start` decides whether to clear the on-chain `ChunkyDKGState::in_progress` session using the *regular* DKG module's completion status, not the chunky session's own staleness (its `dealer_epoch` vs current epoch). This conflates two independent state machines and can cause a legitimate, still-active chunky session to be wiped mid-flight.

### Finding Description
`try_start` first checks whether `dkg::incomplete_session()` exists and matches the current epoch; if so it returns early [1](#0-0) . Only when there is **no** in-progress regular DKG session (or it belongs to a different/stale epoch) does it fall through to unconditionally clear any in-progress chunky session via `chunky_dkg::try_clear_incomplete_session` [2](#0-1) . That helper unconditionally sets `in_progress = option::none()` with no check on the session's own `dealer_epoch`, effectively discarding it rather than finishing it via `chunky_dkg::finish` [3](#0-2) .

Unlike `try_start`, the combined starter `try_start_with_chunky_dkg` explicitly bails out via `reconfiguration_state::is_in_progress()` before touching any state [4](#0-3) ; `try_start` has no such guard.

The reconfiguration flow allows the regular DKG and Chunky DKG sessions for the *same* epoch to complete independently: `finish_with_dkg_result` calls `dkg::finish` (clearing only the regular DKG's `in_progress`) and then `try_finalize_reconfig`, which explicitly tolerates chunky still being in progress until its grace period elapses [5](#0-4) . In that window — regular DKG finished, chunky still legitimately in progress for the *current* (non-stale) epoch, and reconfiguration still "in progress" — `dkg::incomplete_session()` is `None`, so `try_start`'s early-return guard (line 44) does not fire, and it proceeds to destroy the still-valid chunky session at line 53-56, then restarts a fresh `dkg::start` for the same epoch.

The comment on lines 50-52 asserts this is meant only for "stale" sessions recoverable via `chunky_dkg_override_seq_num`, but the code enforces no such staleness check on the chunky session itself — it only checks whether a *different* module's state (`dkg`) is complete/matches the epoch.

### Impact Explanation
If this path is reachable, the decryption key material bound to the next epoch would be derived from a newly-started chunky session rather than the one validators were actively working on, silently invalidating in-flight aggregated sub-transcripts and changing which encryption key is authoritative for the following epoch/version — a form of committed on-chain state corruption in `ChunkyDKGState`.

### Likelihood Explanation
This requires `try_start` (the V1/regular-DKG-only dispatch path) to be invoked while a chunky session is independently mid-flight for the current epoch and the regular DKG has already finished. I was unable to confirm, within the tool budget available, whether the caller in `block.move`/`aptos_governance.move` already guards against invoking `try_start` while `reconfiguration_state::is_in_progress()` is true — my grep against `block.move` for the caller context did not return results before I ran out of iterations, so the actual reachability of this branch under normal block-prologue dispatch is unverified.

### Recommendation
In `try_start`, gate the chunky-session-clearing branch on the chunky session's own staleness (e.g., compare `chunky_dkg::session_dealer_epoch(session) != reconfiguration::current_epoch()`), mirroring the check already done for the regular DKG session, instead of relying on the unrelated `dkg::incomplete_session()` state as a proxy for chunky staleness.

### Proof of Concept
Move unit test sketch:
1. Call `chunky_dkg::start(epoch, ...)` and `dkg::start(epoch, ...)` together (simulating `try_start_with_chunky_dkg`).
2. Call `dkg::finish(result)` to complete only the regular DKG session for `epoch`.
3. Call `reconfiguration_with_dkg::try_start()` again before the chunky grace period elapses.
4. Assert `chunky_dkg::incomplete_session()` was cleared (destroyed) rather than finalized via `chunky_dkg::finish`, and that a brand-new `dkg::start` session was created for the same epoch — demonstrating the original chunky session was discarded, not completed.

**Caveat:** I could not confirm from available tool calls whether `try_start` is ever actually invoked by `block.move`/`aptos_governance.move` while a chunky session is concurrently active for the current epoch (i.e., whether an outer guard prevents this scenario). This should be verified against the caller sites before treating this as confirmed-exploitable on mainnet.
