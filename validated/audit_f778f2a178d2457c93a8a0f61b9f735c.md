This confirms the guard exists precisely at the network entry point: `process_new_nakamoto_block_ext` in `net/relay.rs` explicitly drops any incoming shadow-flagged block immediately upon receipt, before it ever reaches `accept_block` or `check_block_commit_vrf_seed`.

### Analysis

The claimed equality — "every block with an associated winning block-commit must have its VRF proof bound to that commit's seed" — is not actually broken in a way reachable by an unprivileged attacker, because the shadow-bit bypass in `check_block_commit_vrf_seed` is unreachable for attacker-submitted blocks in the first place.

Key findings:
1. `check_block_commit_vrf_seed` does skip VRF validation for shadow blocks via the `if block.is_shadow_block() { return Ok(()); }` branch, as the question states. [1](#0-0) 

2. However, shadow blocks are not a network-broadcastable or attacker-submittable object at all. They are documented as "directly inserted into the chainstate by means of a consensus rule... neither mined nor relayed," created only via an emergency node-upgrade/SIP process. [2](#0-1) 

3. The network ingestion path (`process_new_nakamoto_block_ext`, which handles both directly-pushed and downloaded blocks) explicitly checks `block.is_shadow_block()` and immediately drops it as `AlreadyStored`, with a comment explaining that shadow blocks are only ever obtained from the local node itself when downloading a tenure that ends in one — never accepted from a peer. [3](#0-2) 

4. Shadow blocks are inserted only via `NakamotoStagingBlocksTx::add_shadow_block`, which is called from `process_shadow_block`, explicitly marked "DO NOT RUN ON A RUNNING NODE (unless you're testing)" — i.e., an operator/consensus-rule tool, not something reachable via P2P from an unprivileged peer.
