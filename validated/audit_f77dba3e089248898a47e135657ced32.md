### Title
Replay/checkpoint-hash validation gap in `ensure_match_transaction_info` allows state-checkpoint divergence to go undetected during chunk replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function that checks a locally re-executed transaction output against the already-authenticated `TransactionInfo` (the object that is hashed into the transaction accumulator and thus covered by validator signatures / accumulator proofs). This function is called from the chunk executor's replay path (`execution/executor/src/chunk_executor/mod.rs`), the debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`), and the CLI replay tooling (`aptos-move/cli/src/commands.rs`). It validates `status`, `gas_used`, `write_set_hash` (state_change_hash) and `event_root_hash`, but — by its own acknowledged TODO — does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` re-derives `write_set_hash` and `event_root_hash` from the locally computed `TransactionOutput` and compares them against the fields recorded in the trusted `TransactionInfo`, but explicitly skips the checkpoint-hash fields: [2](#0-1) 

The comment in the code states this directly: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." These checkpoint hashes are exactly the fields that bind a `TransactionInfo` to the JMT/hot-state/position-tree state roots computed at checkpoint boundaries (see `assemble_transaction_infos` in `execution/executor/src/workflow/do_ledger_update.rs`, which populates `maybe_state_checkpoint_hash`, `maybe_hot_state_checkpoint_hash`, and `maybe_position_state_checkpoint_hash`). [3](#0-2) 

Because these fields are onchain-committed and gate consensus-verified state roots (per the feature-flag docs for `HOT_STATE_ROOT_IN_TXN_INFO` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), a divergence between a node's locally computed state/hot-state/position-tree root and the authenticated root recorded on-chain represents exactly the kind of "committed state differs from correct VM result" or "hard-fork-only divergence during replay" scenario this task is scoped to detect — yet the replay/verification code path that is supposed to catch such divergence does not check it. [4](#0-3) 

### Impact Explanation
If a bug or nondeterminism exists in state-checkpoint-root computation (state tree, hot-state tree, or the newer native-position tree), a node performing chunk-based replay (state sync / fast sync via `execution/executor/src/chunk_executor/mod.rs`) or replay-verify tooling (`aptos-debugger`, `aptos move replay`) will still report success even though its locally recomputed checkpoint root does not match the authenticated one. This defeats the core purpose of replay verification as a safety net for catching consensus-breaking bugs before they cause a chain split, and could let a divergent/corrupted state root propagate silently through a syncing node.

### Likelihood Explanation
This is a real, currently-existing gap in the comparator, but its practical exploitability is currently gated: the affected fields (`hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are only populated when the corresponding feature flags (`TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) are enabled — and the code comment itself indicates the fix should land "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying that flag is not yet active. I could not verify from the available index whether `HOT_STATE_ROOT_IN_TXN_INFO` is already active on mainnet, nor could I fully inspect `execution/executor/src/chunk_executor/mod.rs` (the file appears empty/unindexed in this environment), so I cannot confirm today's exact blast radius on mainnet with full certainty.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally recomputed values whenever they are present in the `TransactionInfo`, before any dependent feature flag (especially `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled on mainnet.

### Proof of Concept
Not applicable as a runnable exploit — the finding is a code-level omission demonstrated directly by the cited TODO and comparator logic in `types/src/transaction/mod.rs:2139-2204`. Given the current unindexed state of `execution/executor/src/chunk_executor/mod.rs` and uncertainty about live feature-flag activation, I cannot construct or confirm an end-to-end triggering scenario on mainnet today.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
