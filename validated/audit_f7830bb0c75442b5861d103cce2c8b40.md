### Title
Zero-fee, unbounded TRC10 Bancor-exchange trades permit single-transaction pool insolvency and permanent DoS of exchange trading - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
`ExchangeTransactionActuator`, the actuator that lets any account trade against a TRC10 Bancor-style liquidity pool (`ExchangeCapsule`), hard-codes its transaction fee to zero and does not verify that the computed "another token" payout does not exceed the pool's actual reserve before mutating pool balances. Combined with the fact that the balance-underflow guard (`hardenedCalc`) is opt-in and disabled unless the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal (id 98) has been enacted, an unprivileged caller can submit a single, essentially free transaction that drives one side of the pool's reserve to zero or negative, permanently disabling that exchange for all subsequent legitimate traders — the same "set fee to 0 → cheap pool-draining DoS" pattern described in the Beedle report, just realized against java-tron's on-chain exchange market instead of a lending pool.

### Finding Description
`ExchangeTransactionActuator.calcFee()` is hard-coded to return `0`, unlike the configurable `MarketSellFee`/`MarketCancelFee` used by the order-book market: [1](#0-0) 

The actual balance update happens in `ExchangeCapsule.transaction()`, which computes the counter-token payout via the Bancor-curve `ExchangeProcessor`/`SafeExchangeProcessor` and then unconditionally subtracts it from the pool reserve — *unless* `hardenedCalc` is `true`: [2](#0-1) 

The negative-balance guard only fires `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))`; when `hardenedCalc` is `false` (the default, since `allowHarden()` requires the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal to have been passed), an underflowing subtraction silently persists a negative or nonsensical balance: [3](#0-2) [4](#0-3) 

`ExchangeTransactionActuator.doValidate()` only bounds the *sell*-side balance against `ExchangeBalanceLimit` (an upper bound) — it never checks that the derived `anotherTokenQuant` (the amount to be paid out of the *buy*-side reserve) is less than or equal to the current reserve of that token: [5](#0-4) 

Because the Bancor `exchangeFromSupply` calculation is a power-law function of the injected relay supply, a trade that is a large fraction of the sell-side reserve (e.g., roughly doubling it in a single transaction) can yield a payout close to or exceeding the entire remaining reserve on the other side, since the exponent (2000) amplifies even modest relay-supply fractions: [6](#0-5) 

Once the reserve of either token reaches (or is pushed below/at) zero, every subsequent `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` call on that exchange pair reverts permanently with "the exchange has been closed": [7](#0-6) 

There is no economic disincentive to attempt this: `calcFee()` returns `0`, so the attacker pays only bandwidth/energy for the transaction, mirroring the report's "borrower fee = 0 → attack is essentially free" premise. `ExchangeWithdrawActuator`, by contrast, is creator-only and thus out of scope as a privileged path, but `ExchangeTransactionActuator` is fully public and reachable from any broadcast transaction.

### Impact Explanation
A successful exploitation permanently blocks the "borrow"-equivalent core feature here — on-chain TRC10↔TRX/TRC10↔TRC10 exchange trading for the affected pool — for every other user, and can corrupt the pool's recorded balances (potentially negative values persisted to `ExchangeStore`/`ExchangeV2Store`), which is a form of accounting corruption reachable by an anonymous transaction, matching the "Impact" bar requiring DoS via protocol implementation or asset/accounting corruption.

### Likelihood Explanation
Likelihood is moderate-to-high on networks/pools where `ALLOW_HARDEN_EXCHANGE_CALCULATION` has not been activated (this is an opt-in fork/proposal, not default-on) and where a pool's reserves are shallow enough that a single large trade can economically approach 1:1 the reserve ratio; the zero fee removes the main deterrent, and no special privileges are required — only a `ExchangeTransactionContract` broadcast and enough of the sell-side token/TRX.

### Recommendation
- Always validate, in `ExchangeTransactionActuator.doValidate()` (and `ExchangeWithdrawActuator`), that the computed `anotherTokenQuant` does not exceed the current reserve of the token being paid out, independent of the `allowHarden()`/`hardenedCalc` flag.
- Make the underflow/negative-balance check in `ExchangeCapsule.transaction()` unconditional rather than gated behind `hardenedCalc`.
- Consider re-introducing a nonzero, non-bypassable minimum fee (or a max-trade-to-reserve ratio) for `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` to raise the cost of repeated pool-draining attempts, consistent with the mitigation suggested in the referenced report (avoid permitting an effectively zero-cost operation that can exhaust a shared liquidity pool).

### Proof of Concept
1. Attacker identifies (or creates) a TRC10 exchange pair with a small `secondTokenBalance` relative to `firstTokenBalance`, on a network where `ALLOW_HARDEN_EXCHANGE_CALCULATION` (proposal 98) has not been enacted (default state).
2. Attacker broadcasts a single `ExchangeTransactionContract` selling `firstTokenId` in an amount comparable to (or larger than) `firstTokenBalance`. `ExchangeProcessor.exchange()` computes `anotherTokenQuant` via the Bancor curve; because the exponent (2000) amplifies the relay-supply fraction, the computed payout can approach or exceed `secondTokenBalance`.
3. `ExchangeTransactionActuator.doValidate()` only checks `tokenBalance (sell side) > balanceLimit` and `anotherTokenQuant < tokenExpected` — it never checks `anotherTokenQuant <= secondTokenBalance`, so validation passes: [5](#0-4) 
4. `execute()` calls `exchangeCapsule.transaction(...)` again and persists the new (potentially negative/near-zero) `secondTokenBalance` via `Commons.putExchangeCapsule(...)`.
5. Any subsequent user attempting to trade or withdraw on this exchange pair hits the `firstTokenBalance == 0 || secondTokenBalance == 0` guard and receives "Token balance in exchange is equal with 0, the exchange has been closed", permanently blocking further trading — the on-chain analog of the Beedle borrow-DoS, achieved at near-zero cost because `calcFee()` is hard-coded to `0`.

Note: I was not able to fully verify, purely through static reading, the exact numeric threshold (trade-size-to-reserve ratio) at which `exchangeFromSupply`'s double-precision power computation actually returns a value exceeding the live reserve for realistic on-chain balances; confirming the precise economic threshold would require running the `ExchangeProcessor`/`SafeExchangeProcessor` formulas against representative reserve sizes, which a Devin session with code-execution access could verify empirically.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
