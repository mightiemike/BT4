### Title
Replay-verification comparator ignores the authenticated state-checkpoint (state-root) hash, letting a diverged state root pass as valid — (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`aptos-debugger`, `aptos` CLI, and `storage/db-tool`'s `replay_on_archive`) to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` that is bound into the transaction accumulator and signed by validators. The function validates status, gas used, write-set hash, and event root hash, but never compares the locally computed state root against `txn_info.state_checkpoint_hash()` (nor the hot-state / `position_state_checkpoint_hash` fields). This gap is even acknowledged in a TODO in the same function. As a result, replay-verification can report success even when the locally computed state root diverges from the authenticated on-chain state root.

### Finding Description
`TransactionInfo` (both `TransactionInfoV0` and `TransactionInfoV1`, `types/src/transaction/mod.rs:2390-2461`) carries `state_checkpoint_hash` (and, for V1, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) — the root of the Sparse/Jellyfish Merkle state tree at the end of a transaction, produced during commit and bound into the transaction accumulator that ledger-info signatures authenticate (see `verify_transaction_info` in `types/src/proof/mod.rs:40-61` and `TransactionInfoListWithProof::verify` in `types/src/proof/definition.rs:908-925`).

`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) is the local (client-side) equivalent check used when a `TransactionOutput` (re-executed locally, e.g. during replay/backup-verify) is asserted to match a trusted, authenticated `TransactionInfo`: [1](#0-0) 

It checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (hash of the write set) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It explicitly does **not** check `txn_info.state_checkpoint_hash()` (or the V1 hot-state / position-state checkpoint hashes) against any locally recomputed state root, and the code says so directly: [2](#0-1) 

`state_change_hash` is only a hash of the write set contents (deterministic per write-set, independent of prior state), whereas `state_checkpoint_hash` is the actual Merkle root of world state after applying that write set on top of the (potentially large, historical) state tree. A bug that corrupts state accumulation/merge logic (e.g., in JMT batch update, hot-state merge, or parallel state-checkpoint computation in `execution/executor/src/workflow/do_state_checkpoint.rs`) without altering the individual write set contents would leave `state_change_hash` and `event_root_hash` unaffected, while the true state root silently diverges — and `ensure_match_transaction_info` would not catch it.

This function is the sole state/output-vs-proof comparator used by: [3](#0-2) 
and by the `aptos-debugger` and `aptos` CLI tooling, which are the primary mainnet tools operators/auditors use to detect state-root divergence when replaying historical chain data against a new binary (e.g., to catch consensus-breaking VM/state bugs before they fork the chain).

### Impact Explanation
Replay-verification against archival, authenticated ledger data is a key safety net for catching state-root-diverging bugs before/after a binary upgrade reaches mainnet (hard-fork detection). Because `ensure_match_transaction_info` never validates the state checkpoint hash, a state-root-corrupting bug (in state-merge, JMT/hot-state logic, or a future defect introduced by ongoing "trading-native" state root changes) can pass `replay_on_archive` / debugger verification even though the locally derived state root is provably wrong relative to the validator-signed record. This directly weakens detection of "committed state that differs from the correct VM result" and of "hard-fork-only divergence during commit/replay/restore," per the state-integrity gate — the check that is supposed to catch such divergence is a no-op for the state root.

### Likelihood Explanation
This is not a remotely triggerable attack (no adversarial input path); it is a latent gap in an internal integrity-verification tool used by node operators/auditors. The likelihood of exploitation is tied to the likelihood of an underlying (separate) state-computation bug existing; when such a bug does exist, this comparator would fail to detect it. The gap is self-acknowledged by the authors (TODO comment), confirming it is a live, unresolved issue rather than a false positive from the review.

### Recommendation
In `TransactionOutput::ensure_match_transaction_info`, when a `state_checkpoint_hash` (or in V1, hot-state / position-state checkpoint hash) is present on `txn_info`, recompute the corresponding local state-root value from the post-transaction state and assert equality against `txn_info.state_checkpoint_hash()` / the V1 equivalents, mirroring how `write_set_hash` and `event_root_hash` are already validated, before any feature (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that adds new checkpoint-hash fields is enabled.

### Proof of Concept
Not directly demonstrable as a standalone exploit since it requires an independent state-corruption bug to manifest; the proof is the code path itself:
1. Node replays a historical transaction and produces a `TransactionOutput` whose write set matches expectations (so `state_change_hash` matches) but whose internally-applied state (e.g., due to a JMT merge/order bug) diverges from the authenticated `state_checkpoint_hash` recorded in `txn_info`.
2. `replay_on_archive`/`aptos-debugger`/CLI calls `ensure_match_transaction_info` ( [1](#0-0) ), which returns `Ok(())` because it never reads or compares `txn_info.state_checkpoint_hash()`.
3. The tool reports "replay verified", even though the true, validator-authenticated state root has silently diverged from the locally computed one.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
