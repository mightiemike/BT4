### Title
`sanitizeHost` throws an uncaught `TypeError` on base64-valid-but-URL-invalid `host` values, causing an unhandled exception in the admin authentication path - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` only validates that the raw input matches a base64 character set regex before calling `decodeHost` and feeding the decoded bytes directly into `new URL(https://${decodeHost(sanitizedHost)})` with no `try/catch`. Because the base64 alphabet check does not constrain what bytes the decoded string can contain, an attacker can supply a `host` value whose decoded form contains WHATWG-forbidden host code points (e.g. `\x00`, space, `@`, `#`), causing `new URL()` to throw a `TypeError: Invalid URL` that propagates uncaught out of `sanitizeHost`.

### Finding Description
`sanitizeHost` (packages/apps/shopify-api/lib/utils/shop-validator.ts, lines 52-90) validates the base64 charset with `base64regex.test(host)` and then unconditionally does: [1](#0-0) 
`decodeHost` is a thin `atob` wrapper with no further sanitization of the decoded bytes: [2](#0-1) 

Since base64 characters (`A-Za-z0-9+/=`) can encode arbitrary binary data, an attacker can craft a base64 string that decodes to text containing forbidden host code points (NUL, space, `@`, `#`, `<`, `>`, etc.). When such a string is embedded in `https://${decoded}` and passed to `new URL()`, the WHATWG URL host parser rejects the forbidden code point and the constructor throws a `TypeError`, which is not caught anywhere inside `sanitizeHost`.

This function is invoked directly on the unauthenticated `host` query parameter in the admin OAuth/embedded-app entry points, e.g.: [3](#0-2) [4](#0-3) 
Neither caller wraps the `sanitizeHost` call in a `try/catch`, so a thrown `TypeError` propagates as an unhandled exception rather than the intended `InvalidHostError`/`null` fail-closed behavior.

Note: the specific claim in the question that this is reached via the **Flow** (`shopify.authenticate.flow`) caller chain does not hold — `authenticateFlowFactory` (packages/apps/shopify-app-remix/src/server/authenticate/flow/authenticate.ts) validates the request via `api.flow.validate` (HMAC) and looks up an offline session by `shopify_domain`; it never reads or validates a `host` parameter, so `sanitizeHost` is not reachable from that chain. [5](#0-4) 
The genuinely reachable, unauthenticated caller chain is the **admin** authentication/embedded-app-load path (`validateShopAndHostParams`, `auth-code-flow.ts`), where `host` is taken straight from the request URL query string before any session or HMAC check occurs.

### Impact Explanation
This is a request-scoped denial-of-service condition: a crafted `host` query parameter causes an uncaught exception in the admin auth entry point instead of the intended `null`/`InvalidHostError` fail-closed result. In frameworks with proper error boundaries (Remix/React Router) this typically surfaces as an unhandled 500 rather than a full process crash, but it violates the "fail closed with handled errors, not throw" invariant and is an availability/robustness defect in a security-sensitive validator used in the authentication path.

### Likelihood Explanation
No privileges are required: the `host` parameter is fully attacker-controlled in any request to app routes that call `validateShopAndHostParams`/`sanitizeHost` (e.g., a crafted link sent to a merchant, or a direct request to the app's auth/embedded routes). Constructing a base64 string that decodes to a hostname containing a forbidden character (e.g. NUL byte) is trivial and repeatable.

### Recommendation
Wrap the `new URL(...)` call in `sanitizeHost` in a `try/catch`, treating any thrown error as an invalid host (return `null` or throw `InvalidHostError` when `throwOnInvalid` is set), matching the fail-closed contract already used for the base64-regex and origin-regex checks.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost should not throw on malformed decoded host', () => {
  const shopify = shopifyApi(testConfig());

  // decodes to "a\u0000.myshopify.com" - forbidden host code point (NUL)
  const malformedHost = Buffer.from('a\u0000.myshopify.com').toString('base64');

  expect(() => shopify.utils.sanitizeHost(malformedHost)).not.toThrow();
  expect(shopify.utils.sanitizeHost(malformedHost)).toBeNull();
});
```
Expected today: the `new URL()` call throws `TypeError: Invalid URL`, which is not caught, so the test fails with an uncaught exception instead of returning `null`.
