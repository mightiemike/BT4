## Analysis

The external report's core issue — hardcoded zero minimum-out amounts around AMM interactions — has already been patched in this codebase for the primary swap paths. Every module-initiated Uniswap V3 interaction now computes `minPCOut` as 95% of a freshly-fetched quote, as documented in the `chain-meta` upgrade handler [1](#0-0) .

However, the analog vulnerability survives in how that quote is sourced. `GetSwapQuote` derives `minPCOut` from a live, spot on-chain call to `QuoterV2.quoteExactInputSingle` with `SqrtPriceLimitX96: big.NewInt(0)` — i.e., the current AMM pool price, with no TWAP and no external price reference: [2](#0-1) 

This spot quote is then immediately used to compute a flat 5% slippage tolerance and passed straight into the real swap, in three separate call sites:

- `ExecuteInboundGas` (GAS inbound autoswap): [3](#0-2) 
- `gasAndPayloadDepositAutoSwap` (GAS_AND_PAYLOAD inbound autoswap): [4](#0-3) 
- `applyGasRefund` (outbound excess-gas refund swap): [5](#0-4) 

Because the reference price is the pool's own instantaneous state rather than a manipulation-resistant oracle (e.g., a TWAP), and because these module-originated swaps execute deterministically once a `MsgVoteInbound`/`MsgVoteOutbound` quorum transaction lands in a block (a block whose transaction ordering an unprivileged actor can still influence relative to their own transactions), an attacker can sandwich the module's autoswap: push the pool price down within the 5% band immediately before the finalizing vote transaction is included, let the module's `CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas` execute at that depressed price (still "passing" the self-referential 5% check because the check is derived from the same manipulated state), then reverse the price move afterward to capture the spread. The e2e setup confirms these are shallow, protocol-deployed pools (e.g. `1`/`4` token/WPC seed liquidity), which makes manipulation cheap: [6](#0-5) .

This doesn't require any privileged validator/relayer misbehavior — the UVs and nodes are honest and follow the documented flow exactly; the flaw is that "slippage protection" is measured against a price the calling module itself lets an ordinary user manipulate in the same block.

### Title
Self-referential spot-price slippage check in module autoswap/refund paths allows same-block price-manipulation extraction - (File: x/uexecutor/keeper/evm.go)

### Summary
`GetSwapQuote` (used by `ExecuteInboundGas`, `gasAndPayloadDepositAutoSwap`, and `applyGasRefund`) computes `minPCOut` from a live `QuoterV2.quoteExactInputSingle` call against the current Uniswap V3 pool state, then applies a flat 5% tolerance and immediately executes the real swap in the same keeper flow. Because both the reference quote and the guarded swap read the same manipulable on-chain price, an unprivileged actor can move the pool price within a single block (via ordinary swap transactions on the same pool) to make the module's "protected" swap execute at a degraded rate, then reverse the move to capture the difference.

### Finding Description
`GetSwapQuote` issues a static `CallEVM` to the deployed `QuoterV2` contract with `SqrtPriceLimitX96: big.NewInt(0)`, meaning it returns the exact-input quote at the pool's current spot price with no time-weighting or manipulation resistance: [7](#0-6) .

All three consumers use this quote to derive `minPCOut = quote * 95 / 100` and pass it straight into a state-changing `DerivedEVMCall` in the very next statements, with no intervening delay or independent price check:
- `ExecuteInboundGas`: quote fetched at line 135, swap executed at line 148 of the same function invocation [8](#0-7) .
- `gasAndPayloadDepositAutoSwap`: same pattern [4](#0-3) .
- `applyGasRefund`: same pattern for the excess-gas refund swap [9](#0-8) .

These calls execute as part of vote-finalization processing (when the 2/3+ UV quorum is reached for `MsgVoteInbound`/`MsgVoteOutbound`), which is a transaction included in an ordinary block alongside any other user transaction. An unprivileged actor who can predict or influence the ordering of transactions in that block (e.g., via gas price / MEV, or simply by observing the pending vote transaction in the mempool) can:
1. Submit a large swap against the same Uniswap V3 pool (e.g., PRC20/WPC or gas-token/WPC) immediately before the vote-finalizing transaction, pushing the spot price down.
2. Let the module's `GetSwapQuote` + `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` execute against that manipulated price — the 5% band is computed from the same degraded state, so it does not actually bound the loss relative to fair value.
3. Submit a reverse swap afterward to restore the price, netting the value that would otherwise have gone to the deposit recipient (the user's UEA or the gas refund recipient).

This is the direct Push Chain analog of the reported issue: nominal slippage protection exists, but the reference price it is measured against is itself attacker-manipulable within the same execution window, so the protection does not prevent value extraction — it only bounds the *reported* deviation, not the *actual* one.

### Impact Explanation
This is user/protocol fund loss: the recipient (a user's UEA on `GAS`/`GAS_AND_PAYLOAD` inbound execution, or the gas-refund recipient on outbound finalization) receives fewer PC/native tokens than the fair-value swap would have produced, while the attacker captures the spread via the sandwich. Because these pools are small, protocol-deployed pools with shallow liquidity, manipulating the spot price by the full 5% tolerance is inexpensive, making the attack economically attractive across every inbound `GAS`/`GAS_AND_PAYLOAD` deposit and every outbound gas refund with an excess amount.

### Likelihood Explanation
Medium-to-High. No privileged access is required — only the ability to submit ordinary swap transactions on Push Chain's own AMM pools and to get them ordered around the vote-finalizing transaction, which is a normal, unprivileged MEV/sandwich pattern. The trigger (any `GAS`/`GAS_AND_PAYLOAD` inbound reaching quorum, or any outbound with excess gas) happens routinely as part of normal protocol operation, not as an edge case.

### Recommendation
Do not derive the slippage bound from the same-block spot price of the pool being traded against. Use a manipulation-resistant reference instead, e.g.:
- A time-weighted average price (TWAP) over a window that cannot be moved within a single block, or
- An external/oracle-derived reference price independent of the pool's instantaneous reserves, or
- A governance-configured minimum acceptable rate rather than a percentage of a live quote,
and revert the whole inbound/outbound processing if the achieved rate falls outside that independently-derived bound rather than only bounding relative to the pool's own current (attacker-influenced) state.

### Proof of Concept
1. Attacker identifies a pending `MsgVoteInbound` (or `MsgVoteOutbound`) transaction in the mempool that will reach quorum and trigger `ExecuteInboundGas` (or `applyGasRefund`) for a sizable `amount`.
2. Attacker submits, with higher priority/gas, a large swap on the relevant Uniswap V3 pool (prc20 → WPC or gasToken → WPC) to move the spot price down by ~5%.
3. The quorum transaction lands next; `GetSwapQuote` fetches the now-depressed spot price, computes `minPCOut = quote * 95 / 100` off that depressed value, and `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` executes successfully at the bad rate (since the check only compares against its own manipulated reference).
4. Attacker submits a reverse swap to restore the pool price, realizing a profit equal to the difference between the true price and the manipulated execution price, at the expense of the deposit/refund recipient.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
