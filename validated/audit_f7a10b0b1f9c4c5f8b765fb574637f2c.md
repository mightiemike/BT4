### Title
`isSafe` in `validate-redirect-url.ts` fails to validate the resulting hostname, allowing protocol-relative URL open redirect - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts`)

### Summary
`isSafe`/`sanitizeRedirectUrl` are supposed to ensure a redirect target stays on the app's own domain, but the implementation never compares the resolved `URL.hostname`/`origin` against the `domain` argument. A protocol-relative input such as `//evil.com` parses cleanly via `new URL(redirectUrl, domain)`, inherits the `https:` protocol from the trusted `domain` base, and passes every existing check (file-URI regex, whitespace regex, `INVALID_RELATIVE_URL` pathname regex, protocol allow-list, SSL requirement) while actually pointing at an attacker-controlled host.

### Finding Description
`isSafe` performs these checks, in order, on `redirectUrl` [1](#0-0) :
1. Reject non-strings.
2. Reject `///` (file URI) or whitespace.
3. Parse with `new URL(redirectUrl, domain)`.
4. Reject if `url.pathname` contains `//` or `\\` (`INVALID_RELATIVE_URL`).
5. Reject if protocol isn't `http:`/`https:`.
6. Reject non-HTTPS when `requireSSL` is set.

None of these steps ever compares `url.hostname` (or `url.host`/`url.origin`) to the trusted `domain` parameter. For a protocol-relative input like `//evil.com`, `new URL('//evil.com', 'https://my-app.example.com')` resolves to `https://evil.com/`: the protocol is inherited as `https:` from the base, the pathname is `/` (no double slashes), and it passes every check — `isSafe` returns `true` even though the resulting URL's host is completely attacker-controlled.

`sanitizeRedirectUrl` then returns `new URL(redirectUrl, domain)` — i.e., `https://evil.com/` — as a "validated safe" redirect target [2](#0-1) .

This helper is consumed by `renderAppBridge`, which takes `redirectTo.url` and embeds the sanitized destination directly into an inline script executed in the browser: `window.open(destination.toString(), target)` [3](#0-2) . Because `sanitizeRedirectUrl` incorrectly certifies `//evil.com` as safe, any code path that passes attacker-influenced redirect targets into this helper produces a redirect to an external, attacker-controlled origin from within the app's authenticated/embedded context — an open redirect. The existing Jest test suite for this file has no test case for protocol-relative (`//host`) inputs, only for `///path` (triple-slash) file URIs, confirming this bypass is untested [4](#0-3) .

### Impact Explanation
An attacker who can influence the `redirectUrl`/`redirectTo.url` value reaching `sanitizeRedirectUrl` can force the app to redirect (via `window.open`) to an arbitrary external origin instead of staying within the app's own domain, despite the function's explicit purpose of preventing exactly that. This is an open-redirect / host-confusion primitive that can be leveraged for phishing or, in flows where the redirect carries session/OAuth artifacts, token/credential exfiltration to the attacker's origin — matching the "open redirect leading to token theft" impact class referenced in the question.

### Likelihood Explanation
Exploitability requires that some request-controllable value reach the `redirectUrl` argument of `sanitizeRedirectUrl` (e.g., via `renderAppBridge`'s `redirectTo.url`, ultimately sourced from callers such as billing or embedding flows). I was not able to fully trace, within the available index, every caller path to confirm which specific end-user-facing parameter feeds an entirely attacker-controlled string into this argument versus a value already constrained by other logic in each caller; this would need further tracing per call site (`billing/*.ts`, `authenticate/admin/authenticate.ts`, etc.) to confirm an unauthenticated/single-merchant-controllable end-to-end path. Regardless, the core validation defect in `isSafe` — accepting protocol-relative URLs as same-origin-safe — is a concrete, reproducible bug in the library itself, independent of any specific caller.

### Recommendation
In `isSafe`, after constructing `url`, explicitly verify that `url.hostname` (or `url.origin`) equals the hostname/origin derived from `domain`, rejecting any redirect target whose host differs from the trusted app domain (this also covers `//`-prefixed protocol-relative inputs, which `new URL(input, base)` treats as absolute with a new host).

### Proof of Concept
```ts
import {APP_URL} from '../../../../__test-helpers';
import {sanitizeRedirectUrl} from '../validate-redirect-url';

it('BUG: incorrectly treats protocol-relative URL as safe', () => {
  // Attacker-controlled protocol-relative redirect target
  const result = sanitizeRedirectUrl(APP_URL, '//evil.com/steal');

  // Currently this does NOT throw and returns a URL pointing at evil.com,
  // even though sanitizeRedirectUrl is meant to keep redirects on APP_URL's domain.
  expect(result.hostname).not.toEqual('evil.com'); // FAILS today: result.hostname === 'evil.com'
});
```
Expected (correct) behavior: `sanitizeRedirectUrl(APP_URL, '//evil.com/steal')` should throw `ShopifyError('Invalid URL. Refusing to redirect')` because the resolved host does not match `APP_URL`'s host; instead it currently returns a valid `URL` object for `https://evil.com/steal`.

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}

export function sanitizeRedirectUrl<OptionsArg extends Options>(
  domain: string,
  redirectUrl: unknown,
  options: OptionsArg = {} as OptionsArg,
): SanitizedRedirectUrl<OptionsArg> {
  if (isSafe(domain, redirectUrl, options.requireSSL)) {
    return new URL(redirectUrl, domain) as SanitizedRedirectUrl<OptionsArg>;
  } else if (options.throwOnInvalid === false) {
    return undefined as SanitizedRedirectUrl<OptionsArg>;
  } else {
    throw new ShopifyError('Invalid URL. Refusing to redirect');
  }
}
