### Title
Unbounded `DelegatedResourceAccountIndexCapsule` list migration causes an O(N) hot-loop DoS in a single transaction - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegatedResourceAccountIndexStore.convert()` iterates over an account's entire legacy `toAccountsList`/`fromAccountsList` and re-writes a new index entry (two DB puts) for every element before deleting the old key. These lists are populated one entry per unique delegatee/delegator by `FreezeBalanceActuator.delegateResource()` with no cap on the number of distinct receiver addresses a single account can accumulate. Because `convert()` is invoked synchronously inside a single user-submitted transaction (via `delegateResource`/`UnfreezeBalanceActuator`), an attacker can pre-inflate one address's index list to an arbitrarily large size and then trigger a single transaction that performs that many iterations and store writes at once — the same "unbounded nested loop over an attacker-controlled list executed inside one transaction" bug class described in the external report.

### Finding Description
`DelegatedResourceAccountIndexStore.convert(byte[] address)` loops over `toList`/`fromList` with no size bound: [1](#0-0) 

Each iteration calls `this.delegate(...)`, which performs two `put()` calls into the revoking DB: [2](#0-1) 

These lists are grown, one entry per unique counterparty, by the old (non-optimized) delegation path in `FreezeBalanceActuator.delegateResource()`: [3](#0-2) 
This code checks only `if (!toAccountsList.contains(...))` before appending — there is no maximum count enforced on the number of distinct delegatees/delegators an account can accumulate, unlike `UnfreezeBalanceV2Actuator`, which caps unfreeze operations via `UNFREEZE_MAX_TIMES` [4](#0-3)  or `MarketSellAssetActuator`, which caps matched orders per transaction via `MAX_MATCH_NUM` [5](#0-4) .

Once `dynamicStore.supportAllowDelegateOptimization()` becomes true (a chain-parameter-gated feature switch), the very next `delegateResource` call for that same owner/receiver address unconditionally calls `convert()` on both addresses before performing the new-model delegation: [6](#0-5) 
The same unconditional `convert()` call pattern also exists in `UnfreezeBalanceActuator`'s legacy undelegate path.

Because this happens inside `execute()` of a normal, unprivileged `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction, and because the pre-optimization index-growth path had no upper bound on list size, a single account could accumulate a very large `toAccountsList`/`fromAccountsList` (thousands of entries, one per tiny freeze-delegation to a distinct throwaway address) before the optimization flag flips. The first transaction touching that account afterward then performs O(N) DB writes synchronously within block/transaction execution — a direct analog of the reported `clearLoop()` nested-loop-over-unbounded-lists gas/CPU exhaustion pattern, but expressed as unbounded store iteration triggered from an ordinary broadcast transaction rather than as EVM gas.

### Impact Explanation
Impact is Low-to-Moderate: the attacker (any unprivileged account) must first spend transaction fees to build up the oversized index list (one `FreezeBalanceContract` tx per unique receiver), so the cost is borne by the attacker over many transactions, but the payoff is a single victim transaction (their own, or forced via the optimization flag flip) that performs a disproportionately large amount of synchronous store I/O, slowing block/transaction processing for that one transaction. This does not corrupt consensus state, but it is an inefficiency/DoS-shaped issue matching the report's classification.

### Likelihood Explanation
Likelihood is Low-to-Moderate given it depends on (a) an account choosing to build a huge legacy delegation index before `supportAllowDelegateOptimization` is enabled network-wide, and (b) the one-time migration triggering afterward. It is a one-shot event per affected account rather than a repeatable steady-state DoS, which is a weaker likelihood profile than the original `clearLoop()` report (which is triggered every time the function is called).

### Recommendation
- Enforce an upper bound on the number of distinct delegatee/delegator entries an account can accumulate in `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` in `FreezeBalanceActuator.delegateResource()`, analogous to `UNFREEZE_MAX_TIMES`/`MAX_MATCH_NUM`.
- In `DelegatedResourceAccountIndexStore.convert()`, cap or chunk the number of entries migrated per invocation (e.g., process a bounded batch per call and mark partial-migration state) instead of migrating the full list synchronously in one call.

### Proof of Concept
Not independently verified end-to-end (no local execution/testnet access); the trace below is based on static code reading only:
1. Before `supportAllowDelegateOptimization` is enabled, attacker's account `A` sends many `FreezeBalanceContract` transactions, each delegating a minimal frozen balance to a distinct newly generated receiver address `R_i`. This is confirmed possible by the existing test `testMultiFreezeDelegatedBalanceForBandwidth`, which builds a 100-entry `toAccountsList` this way: [7](#0-6)  — nothing in `delegateResource` prevents scaling this to thousands of entries.
2. Committee enables `supportAllowDelegateOptimization` (or it is already enabled on a live chain going forward).
3. Attacker sends one more `FreezeBalanceContract`/delegate transaction from account `A`; `delegateResource()` executes the `else` branch and calls `delegatedResourceAccountIndexStore.convert(ownerAddress)`, which loops over the full accumulated `toAccountsList`/`fromAccountsList` and performs two DB writes per entry in a single transaction's `execute()` call. With a sufficiently large pre-built list, this single transaction executes far more store operations than a typical transaction, in direct analogy to the reported `clearLoop()` OOG pattern.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
