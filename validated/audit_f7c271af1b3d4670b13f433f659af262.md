### Title
Silent, non-retried failure of afterAuth hook in `IdempotentPromiseHandler` causes critical post-token-exchange setup to be permanently skipped - ([File: packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts])

### Summary
`IdempotentPromiseHandler.handlePromise`, used by the token-exchange authentication strategy to dedupe the `afterAuth` hook call per session token, marks an identifier as "already handled" *before* the wrapped promise runs and never clears that identifier if the promise fails — only after a 60-second TTL. This is the same failure pattern as the reported `VUSD#processWithdrawals` bug: a failed operation is treated as done and silently dropped instead of being retried, with the caller none the wiser.

### Finding Description
`isPromiseRunnable` inserts the identifier into the map and returns `true` (allowing the promise to run) on the very first call, before the promise has resolved or rejected: [1](#0-0) 

If `promiseFunction()` throws, the exception propagates out of `handlePromise` (there is no `catch`, only a `finally` that just prunes stale entries older than `IDENTIFIER_TTL_MS` = 60000ms), but the identifier is **not removed** from the map on failure. This means the failed attempt is still recorded as "already run" for the current session token.

This handler is used in the token-exchange auth strategy to guard the `afterAuth` hook call, keyed by the raw session token (JWT) itself: [2](#0-1) 

and is invoked from `authenticate()` right after the offline/online access token exchange completes and the session is stored: [3](#0-2) 

Shopify App Bridge session tokens are short-lived (about one minute) — matching almost exactly the 60-second `IDENTIFIER_TTL_MS` window. Sequence of events:
1. Merchant's browser calls the app with session token `T`. Token exchange succeeds, session is stored, and `handleAfterAuthHook` runs `triggerAfterAuthHook` (which typically performs webhook registration, billing checks, or other mandatory setup for the merchant). `T` is now recorded as "attempted" in `identifiers`.
2. The `afterAuth` hook throws (e.g., transient GraphQL failure/throttling registering webhooks — a scenario the codebase explicitly handles elsewhere by logging without re-raising, see `registerWebhooksFactory`'s throttling branch) — the strategy converts this into a `500 Internal Server Error` response.
3. App Bridge (or any client) retries the same request using the identical, still-valid session token `T` (very plausible given the ~1 minute token lifetime and that this is the standard App Bridge retry/re-fetch behavior on error).
4. On retry, `isPromiseRunnable(T)` returns `false` because `T` is still in the map from step 1. `promiseFunction` (the `afterAuth` hook) is **skipped entirely**, no exception is thrown, and `handlePromise` resolves normally.
5. `authenticate()` treats this as success, returns the new session, and the request proceeds — but the mandatory `afterAuth` setup was never actually completed on the retry, and no error is surfaced anywhere.

The identical logic exists in the React Router and Express packages as well: [4](#0-3) [5](#0-4) 

### Impact Explanation
This causes silent loss of the app's `afterAuth` setup logic (webhook registration, billing enforcement, etc.) for up to 60 seconds after any transient failure — without ever surfacing an error to the app author, the merchant, or logs on the retry that "succeeds." Since `afterAuth` is frequently used to register mandatory webhooks or enforce billing, an app could end up running without required webhooks/billing enforcement for an indeterminate period while behaving as if OAuth/token-exchange completed successfully — a functional degradation of the auth completion handler triggered purely by ordinary transient errors and a client retry, requiring no attacker privilege beyond being a normal merchant session.

### Likelihood Explanation
Reachable by any single merchant performing the standard embedded-app token exchange flow; no elevated privileges are required. The trigger condition (a transient failure in the `afterAuth` hook, e.g., webhook registration throttling that the codebase already anticipates in `registerWebhooksFactory`) combined with a client retry using the same still-valid session token within ~60 seconds is a realistic, unprivileged occurrence rather than a contrived edge case.

### Recommendation
Remove the identifier from the map (or otherwise mark it eligible to retry) when `promiseFunction()` rejects, so that a subsequent invocation with the same identifier actually re-attempts the `afterAuth` hook instead of silently no-opping. Alternatively, cache and surface the failure so the caller can decide to retry deliberately, mirroring the report's recommendation to make failed operations retryable rather than dropping them.

### Proof of Concept
1. Configure an app with an `afterAuth` hook that registers a webhook, and simulate the webhook GraphQL mutation returning a throttled/error response on the first call.
2. Complete embedded app installation via token exchange with session token `T`; `authenticate()` exchanges the token, stores the session, then calls `handleAfterAuthHook` with `identifier: T`, which invokes `triggerAfterAuthHook` → hook throws → `authenticate()` returns a `500 Response`.
3. Immediately re-issue the same authenticated request with the same still-valid session token `T` (as App Bridge naturally would on error).
4. Observe: `isPromiseRunnable(T)` returns `false`; `triggerAfterAuthHook` is never invoked; `handlePromise` resolves without error; `authenticate()` returns the session and the request is treated as fully successful — even though the webhook registration set up in `afterAuth` never actually ran on this attempt.

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }

    params: BasicParams,

    request: Request,

    await config.idempotentPromiseHandler.handlePromise({

        return triggerAfterAuthHook(params, session, request, this);
      },
      identifier: sessionToken,
