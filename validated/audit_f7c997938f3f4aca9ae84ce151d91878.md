### Title
Missing/zero chain-meta gas price permanently strands INBOUND_REVERT outbounds - (File: `x/uexecutor/keeper/build_revert_outbound.go`)

### Summary
When an inbound fails pre-execution validation (missing token config, invalid amount, or failed autoswap) for a non-isCEA inbound, `buildRevertOutbound` creates an `INBOUND_REVERT` outbound to return the user's funds. If gas info from `UniversalCore.getOutboundTxGasAndFees` cannot be resolved (e.g. no chain-meta gas price has ever been voted for that source chain, or the token lacks a usable `NativeRepresentation`), the code deliberately proceeds and stores the outbound with empty/zero gas fields, treating this as acceptable "graceful degradation." However, the downstream Universal Validator client (`universalClient/chains/evm/tx_builder.go`) explicitly rejects any outbound whose gas price is zero or missing before it will build a signing request, so the outbound can never be signed, broadcast, or observed.

### Finding Description
`buildRevertOutbound` in [1](#0-0)  looks up the token config and calls `GetGasFeeInfoForRevertOutbound`. On any failure (missing `NativeRepresentation`, or an error from `getOutboundTxGasAndFees`), it logs a warning and returns the outbound **without** `GasToken`/`GasFee`/`GasPrice`/`GasLimit` populated — i.e. these fields remain empty strings. This is explicitly acknowledged as intended, non-error behavior in the integration tests: [2](#0-1)  states "Gas fields ... may be zero/empty — that's OK, the outbound is still created (graceful degradation)."

The `INBOUND_REVERT` outbound is then written to `UniversalTx.OutboundTx` and indexed in `PendingOutbounds` (created by chain code before any validator vote, per [3](#0-2) ). The Universal Validator's TxBuilder, however, hard-rejects a zero/missing gas price when assembling the outbound signing transaction: [4](#0-3) . Since no UV can ever build a valid signing request for this outbound, it can never be signed via TSS, broadcast, or observed via `MsgVoteOutbound`.

Critically, `PendingOutbounds` entries are documented as being removed **only** on validator consensus via `MsgVoteOutbound`, and are explicitly **not** cleaned up on ballot expiry: [5](#0-4) . There is no automatic timeout, retry, or refund path for an outbound that can never be broadcast in the first place (as opposed to one that was broadcast but failed) — the design assumes stuck outbounds require manual/governance intervention, but there is no signal or codepath that even flags "genesis-unsignable" outbounds distinctly from ones awaiting normal confirmation.

### Impact Explanation
Any unprivileged user whose inbound triggers a pre-execution revert (e.g., submitting an inbound for a token whose config was removed/disabled, a zero-amount `GAS` inbound, or a `GAS` inbound whose autoswap fails) can end up with an `INBOUND_REVERT` outbound that is permanently stuck in `PENDING` status if chain-meta gas price has not yet been established for that source chain (freshly-added chains, or chains where `VoteChainMeta` bootstrap threshold hasn't been reached — see `chainMetaMinVotesForFirstWrite` referenced in [6](#0-5) ). The user's original funds (which were meant to be returned via the revert) are never released back to them and never delivered, resulting in a permanent, unprivileged, and non-recoverable freezing of user funds — reachable purely through ordinary transaction submission, with no privileged actor involved.

### Likelihood Explanation
This is most likely to manifest on any newly onboarded external chain (before the first 3 chain-meta votes land) or a chain that stops receiving fresh gas-price votes, combined with any of several ordinary, user-triggerable pre-execution failure paths (missing token config, zero amount, failed autoswap) that are already exercised by the project's own test suite. No malicious or privileged actor is required — an ordinary user transacting during this window is sufficient to trigger the stuck state.

### Recommendation
- Do not silently accept zero/missing gas fields on `INBOUND_REVERT` outbound creation; either defer outbound creation until gas info is resolvable, retry gas-info resolution before finalizing the outbound, or apply a safe non-zero default/fallback gas price/limit so the outbound is always constructible by the TxBuilder.
- Add an explicit "unsignable due to missing gas info" state (or reuse `ABORTED`) distinct from ordinary `PENDING`, and surface it via a query so operators can detect and remediate stuck reverts rather than relying on outbound-vote consensus that can never occur.
- Add an integration test asserting that an `INBOUND_REVERT` outbound created with unresolved gas info is never left permanently un-broadcastable.

### Proof of Concept
1. Register a new chain in `x/uregistry` with a token config, but do not call `MsgVoteChainMeta` enough times to reach `chainMetaMinVotesForFirstWrite` (so `UniversalCore.getOutboundTxGasAndFees` cannot resolve a real gas price/fee).
2. Submit an inbound (via `MsgVoteInbound` from a quorum of UVs) with `TxType_GAS` and `Amount = "0"` (or otherwise trigger `GetTokenConfig` failure) — this is a normal, unprivileged path already covered by [7](#0-6) .
3. Observe that an `INBOUND_REVERT` `OutboundTx` is created with empty/zero `GasPrice`/`GasFee`/`GasLimit` and added to `PendingOutbounds`.
4. Run the Universal Validator's `TxBuilder.GetOutboundSigningRequest` against this outbound's data — it returns `"gas price is zero or missing in outbound event"` per [4](#0-3) , and no signing/broadcast ever proceeds. The `PendingOutbounds` entry persists indefinitely, per the documented non-removal-on-expiry behavior.
