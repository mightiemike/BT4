Found a concrete analog. The `SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` binds a StackerDB chunk signature to only `slot_id`, `slot_version`, and `data_hash` — it does not include the StackerDB contract identifier (the `.miners` / `.signers-N-M` contract) at all. This is the same "signature without domain separation" bug class as the reported Factory.sol issue (missing chain-id/contract/domain binding), applied to Stacks' own signer-authenticated chunk protocol.

### Title
StackerDB chunk signatures lack contract-domain binding, enabling cross-StackerDB signature replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest as `sha512/256(slot_id || slot_version || data_hash)` with no binding to the target StackerDB contract (e.g. `.signers-1-1` vs `.miners`, or a different reward-cycle's `.signers-N-M` contract). A signer's or miner's key is often used across multiple StackerDB contracts (rotating reward-cycle signer contracts, `.miners`), so a chunk signed for one contract/slot/version/data-hash tuple verifies identically for any other StackerDB contract that happens to have the same `(slot_id, slot_version, data_hash)`.

### Finding Description
`auth_digest()` [1](#0-0)  hashes only `slot_id`, `slot_version`, and `data_hash`. `SlotMetadata::sign`/`verify` and `StackerDBChunkData::sign`/`verify` operate purely on this digest [2](#0-1) , with no contract identifier, reward-cycle, or chain-id in the preimage. The verification call sites (`postblock_proposal`/StackerDB chunk-push handlers and `StackerDBListener`) authenticate a chunk purely by recovering the pubkey from this digest and checking that pubkey's `Hash160` against the expected signer address for that slot in that contract [3](#0-2) . Because the same signer key/address is reused verbatim across different StackerDB contracts each reward cycle (the signer set config carries `signing_key` per reward cycle, and the same Stacks key is commonly used across consecutive/adjacent reward-cycle contracts), a signature produced for slot `i`/version `v`/data-hash `h` in one contract is valid for the identically-indexed slot in a different StackerDB contract, as long as data hash and version happen to coincide (attacker fully controls a lower-value contract's chunk data to force a coincidence, or replays an old identical-content message such as a `BlockResponse::Accepted` for the same block hash at the same slot/version index across two different reward-cycle `.signers` contracts).

### Impact Explanation
This is a signer-set/weight validation divergence: `StackerDBListener` accumulates `total_weight_approved` per slot based on the recovered pubkey matching the expected `signer_entry` for that slot [4](#0-3) . A replayed/cross-contract chunk with a colliding `(slot_id, slot_version, data_hash)` can be injected into the wrong StackerDB instance and be accepted as a legitimate, freshly-issued signature by a signer for that contract/reward-cycle, letting an attacker (who does not hold the key) rebroadcast a stale, out-of-context chunk to accrue weight toward a block-acceptance threshold it was never intended for. This falls into the "signer weight below threshold or from the wrong set" analog class — a minority-triggerable divergence bounded to signer weight/consensus tallying, not requiring key compromise, only requiring the attacker to relay previously-observed signed chunks into a different StackerDB contract context.

### Likelihood Explanation
Exploitation requires the attacker to find or engineer a `(slot_id, slot_version, data_hash)` collision across two live StackerDB contracts for which the same signer key is registered — realistic because slot_version is a small monotonically increasing lamport counter (frequently 0/1/2 early in a cycle) and identical `BlockResponse` payloads (same block, same signature bytes) can legitimately recur across adjacent reward cycles for signers who are members of both reward-cycle's signer sets. No majority collusion or admin access is needed; a single non-signer relayer with network access can replay an observed valid chunk.

### Recommendation
Bind the StackerDB chunk signature to the target contract by including the `QualifiedContractIdentifier` (and ideally chain-id and reward-cycle) in `auth_digest()`, mirroring the SIP-018 structured-data domain-separation approach already used in `pox-4.clar`'s `get-signer-key-message-hash` [5](#0-4) . Concretely, extend `SlotMetadata::auth_digest` to hash `contract_id || chain_id || slot_id || slot_version || data_hash`, and thread the contract id through `sign`/`verify` call sites in `StackerDBChunkData` and its callers.

### Proof of Concept
1. Signer key `K` is registered in both `.signers-N-M` (cycle N) and `.signers-(N+1)-M'` (cycle N+1) — plausible since reward-cycle membership frequently overlaps.
2. Signer legitimately signs a `BlockResponse::Accepted` chunk for slot `3`, version `1`, in `.signers-N-M`, producing `sig = Sign(K, sha512/256(3 || 1 || hash(payload)))` per `auth_digest()` [1](#0-0) .
3. An unprivileged relayer observes this chunk on the network and re-submits the identical `StackerDBChunkData{slot_id:3, slot_version:1, sig, data}` to `.signers-(N+1)-M'`, where slot 3 also maps to key `K`'s address.
4. `StackerDBChunkData::verify`/`SlotMetadata::verify` [6](#0-5)  and `241" end="244" /> succeed because the digest computation never referenced which contract it was for, so the recovered pubkey still matches slot 3's expected signer in the new contract.
5. `StackerDBListener` for cycle `N+1` accepts the injected message as a fresh valid signer response and adds `signer_entry.weight` toward `total_weight_approved` for a block it was never actually validated against [4](#0-3) .

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
