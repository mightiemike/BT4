### Title
Unbounded per-asset iteration in bandwidth accounting can be inflated by unprivileged TRC10 transfers, causing a resource-exhaustion DoS on `getAccountNet` and related bandwidth-processing paths - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java)

### Summary
`BandwidthProcessor.updateUsage(AccountCapsule)` iterates over every entry of an account's TRC10 asset balance map (`getAssetMapV2()` / `getAllFreeAssetNetUsageV2()`) to recompute free-bandwidth usage for each asset the account holds. Unlike Canto's coinswap pool (which only accepts whitelisted denoms), java-tron places no cap on how many distinct TRC10 assets can exist or be transferred into an arbitrary account. An unprivileged attacker can create an unbounded number of distinct assets and transfer a tiny amount of each into a victim account, inflating the victim's `AssetV2` map to an arbitrary size. Any subsequent call that walks this map — most directly the unauthenticated `getAccountNet` API exposed through `Wallet` — then performs an unbounded, attacker-sized loop, degrading or stalling that request handling. [1](#0-0) 

### Finding Description
`updateUsage(AccountCapsule accountCapsule)` builds a merged map of all asset IDs from `accountCapsule.getAssetMapV2()` plus `accountCapsule.getAllFreeAssetNetUsageV2()`, then calls `.forEach(...)` over that merged map to recompute `FreeAssetNetUsageV2` for every single asset entry: [2](#0-1) 

This is directly analogous to the coinswap bug's `k.bk.GetAllBalances`, which iterates every coin denomination held by an escrow address. In java-tron, the equivalent "denomination list" is the account's TRC10 asset map, and it is populated by ordinary, unprivileged `TransferAssetActuator` transactions — there is no whitelist restricting which asset IDs can be sent to a given account (in contrast to Canto's coinswap, where pools can only be created for whitelisted denoms, which is exactly why the Canto team downgraded severity): [3](#0-2) 

An attacker can:
1. Issue many distinct TRC10 assets (each `AssetIssueContract` just costs the standard issuance fee; issuance is open to any account, not privileged).
2. Use `TransferAssetContract` to send a minimal amount of each distinct asset into the victim's account. `TransferAssetActuator` auto-creates the recipient's asset balance entry (`addAssetAmountV2`) with no consent or cap check on the number of distinct assets a recipient can hold.
3. Once the victim's `AssetV2Map` (and correspondingly `FreeAssetNetUsageV2Map`) contains an attacker-controlled, arbitrarily large number of entries, any code path that walks the full map is forced to do O(N) work per call, where N is fully attacker-controlled and unbounded.

`Wallet.getAccountNet(ByteString accountAddress)` — reachable from an anonymous gRPC/HTTP API call with no signature or authorization required — calls `processor.updateUsage(accountCapsule)` directly on the target account, triggering the unbounded loop for whichever address is queried: [4](#0-3) 

The same `setAssetNetLimit` helper additionally performs a second unbounded loop over `allFreeAssetNetUsage.keySet()`, each iteration issuing a store lookup (`assetIssueStore.get(key)`), multiplying the cost per attacker-inflated entry: [5](#0-4) 

### Impact Explanation
Because `getAccountNet` is a public, unauthenticated wallet API, any client (including block explorers, exchanges, or other automated services that periodically query account bandwidth) can be induced to trigger this expensive computation simply by querying a victim address that an attacker has polluted with a large number of distinct TRC10 balances. Repeated or concurrent queries against such an address can consume excessive CPU/memory on the node servicing the RPC/HTTP-JSON-RPC request, degrading throughput of that node's API layer — a denial-of-service against the affected node's query service, consistent with the "DoS via RPC-API" impact class. It does not directly threaten consensus or fund safety, but it does degrade availability of a core read API without requiring any privileged capability from the attacker.

### Likelihood Explanation
Likelihood is high for the setup step (issuing many TRC10 assets and transferring them into a victim account is unprivileged and cheap relative to the achievable blow-up), and the trigger step only requires calling a public, unauthenticated API (`getAccountNet`) against the polluted address. No special timing, node compromise, or leaked keys are needed — this matches the "unprivileged, RPC-reachable" scope required.

### Recommendation
- Cap the number of distinct TRC10 asset entries a single account may hold, enforced in `TransferAssetActuator.validate()`/`execute()` (reject transfers that would push a recipient's distinct-asset count above a configurable limit), mirroring the recommended coinswap fix of avoiding unbounded "get everything" queries.
- Alternatively/additionally, change `BandwidthProcessor.updateUsage(AccountCapsule)` and `Wallet.setAssetNetLimit` to avoid iterating the entire asset map for API-level queries — e.g., compute/query bandwidth usage per-asset lazily/on-demand instead of eagerly walking the full map, or bound the number of entries processed per call.
- Add pagination/limits to `getAccountNet`/`getAccount` style APIs so a single malicious account cannot force unbounded server-side work per request.

### Proof of Concept
1. From attacker key A, submit N `AssetIssueContract` transactions to create N distinct TRC10 assets (`asset_1 … asset_N`), paying the standard issuance fee for each — no whitelist or privilege required.
2. For each `asset_i`, submit a `TransferAssetContract` from A to victim address V, transferring 1 unit. `TransferAssetActuator.execute()` calls `toAccountCapsule.addAssetAmountV2(...)`, growing V's `AssetV2Map` by one entry each time, with no upper bound enforced in `validate()`.
3. Repeat for a large N (e.g., tens of thousands of distinct assets) to inflate V's asset map.
4. Call the public `getAccountNet` gRPC/HTTP API against address V. Observe that `Wallet.getAccountNet` → `BandwidthProcessor.updateUsage(accountCapsule)` and `setAssetNetLimit` each perform an O(N) loop (with a store lookup per iteration in `setAssetNetLimit`), and that response latency/node CPU scales linearly with the attacker-chosen N, demonstrating the resource-exhaustion DoS.

  public void updateUsage(AccountCapsule accountCapsule) {
    long now = chainBaseManager.getHeadSlot();
    long oldNetUsage = accountCapsule.getNetUsage();
    long latestConsumeTime = accountCapsule.getLatestConsumeTime();
    accountCapsule.setNetUsage(increase(accountCapsule, BANDWIDTH,
            oldNetUsage, 0, latestConsumeTime, now));
    long oldFreeNetUsage = accountCapsule.getFreeNetUsage();
    long latestConsumeFreeTime = accountCapsule.getLatestConsumeFreeTime();
    accountCapsule.setFreeNetUsage(increase(oldFreeNetUsage, 0, latestConsumeFreeTime, now));

    if (chainBaseManager.getDynamicPropertiesStore().getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = accountCapsule.getAssetMap();
      assetMap.forEach((assetName, balance) -> {
        long oldFreeAssetNetUsage = accountCapsule.getFreeAssetNetUsage(assetName);
        long latestAssetOperationTime = accountCapsule.getLatestAssetOperationTime(assetName);
        accountCapsule.putFreeAssetNetUsage(assetName,
            increase(oldFreeAssetNetUsage, 0, latestAssetOperationTime, now));
      });
    }
    Map<String, Long> assetMapV2 = accountCapsule.getAssetMapV2();
    Map<String, Long> map = new HashMap<>(assetMapV2);
    accountCapsule.getAllFreeAssetNetUsageV2().forEach((k, v) -> {
      if (!map.containsKey(k)) {
        map.put(k, 0L);
      }
    });
    map.forEach((assetName, balance) -> {
      long oldFreeAssetNetUsage = accountCapsule.getFreeAssetNetUsageV2(assetName);
      long latestAssetOperationTime = accountCapsule.getLatestAssetOperationTimeV2(assetName);
      accountCapsule.putFreeAssetNetUsageV2(assetName,
          increase(oldFreeAssetNetUsage, 0, latestAssetOperationTime, now));
    });
  }

  private Map<String, Long> setAssetNetLimit(Map<String, Long> assetNetLimitMap,
      AccountCapsule accountCapsule) {
    Map<String, Long> allFreeAssetNetUsage;
    if (chainBaseManager.getDynamicPropertiesStore().getAllowSameTokenName() == 0) {
      allFreeAssetNetUsage = accountCapsule.getAllFreeAssetNetUsage();
      allFreeAssetNetUsage.keySet().forEach(asset -> {
        byte[] key = ByteArray.fromString(asset);
        assetNetLimitMap
            .put(asset, chainBaseManager.getAssetIssueStore().get(key).getFreeAssetNetLimit());
      });
    } else {
      allFreeAssetNetUsage = accountCapsule.getAllFreeAssetNetUsageV2();
      allFreeAssetNetUsage.keySet().forEach(asset -> {
        byte[] key = ByteArray.fromString(asset);
        assetNetLimitMap
            .put(asset, chainBaseManager.getAssetIssueV2Store().get(key).getFreeAssetNetLimit());
      });
    }
    return allFreeAssetNetUsage;
  }
