### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay/restore integrity checks pass despite a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole consistency check used by replay/restore/debugging tools to confirm that a locally re-executed `TransactionOutput` matches the archived `TransactionInfo` stored in the ledger. It verifies status, gas, write-set hash, and event-root hash, but explicitly does not verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This means the tooling that is supposed to detect state divergence between an archive and a fresh replay can report success even when the actual Merkle state root (or the new trading-native position-state root) has diverged.

### Finding Description
`ensure_match_transaction_info` checks four fields — transaction status, gas used, write-set hash (`state_change_hash`), and event root hash — against the provided `TransactionInfo`: [1](#0-0) 

The function's own trailing comment acknowledges the gap: [2](#0-1) 

`TransactionInfoV0`/`V1` carry a `state_checkpoint_hash` (the Sparse/Jellyfish Merkle root summarizing world state) and, for `V1`, a `hot_state_checkpoint_hash` and a repurposed `position_state_checkpoint_hash` used when the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature is enabled: [3](#0-2) 

These checkpoint hashes are computed independently during normal block execution in `DoStateCheckpoint::run`, which derives `state_checkpoint_hashes`, `hot_state_checkpoint_hashes`, and (when `execution_output.compute_trading_native_state_roots` is set) `position_state_checkpoint_hashes` from the Jellyfish-Merkle/position-state summaries: [4](#0-3) 

`ensure_match_transaction_info` is used by `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `execution/executor/src/chunk_executor/mod.rs`, and `storage/db-tool/src/replay_on_archive.rs` — i.e., exactly the "restore/replay" and offline audit tooling in scope. Because the comparator never touches `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, if a bug in state-checkpoint computation (JMT root, hot-state root, or the new position-state root) causes local re-execution to diverge from what is archived, none of these call sites will detect it — they will all report "match" as long as the write-set/event-hash/status/gas happen to align, even though the summarized world-state root differs.

### Impact Explanation
This breaks the "restore/replay must preserve deterministic proof binding" and "authenticated ... proof-bearing responses must stay bound to the right ... root" invariants for the archival/replay-verification tooling explicitly listed as in-scope (`replay_on_archive`, chunk-executor verify path). A silent state-root divergence during replay-verify would be a high-impact integrity failure for anyone relying on these tools (auditors, node operators verifying archives, the `db-tool replay-verify` workflow) to detect corruption or non-determinism in execution/storage — the very purpose of the tool would be defeated for the class of bugs that manifest only in the state-checkpoint root and not in the write-set hash. It is most acute for `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state roots, a newly introduced code path, where the check is entirely absent and the comment flags it as a precondition that must be fixed "before enabling" the feature.

### Likelihood Explanation
This is a real, currently-present gap in shipped code (not speculative): the omission is self-documented by the developers with a `TODO`, and the function is invoked from multiple production tools. No adversary action is even needed — it takes effect for any legitimate divergence in state-checkpoint hash computation that a correct comparator should have caught. Likelihood of the underlying trigger (a real world-state root divergence during replay) depends on other bugs, but the detection mechanism itself is unconditionally weak today, making silent, undetected divergence plausible whenever `state_checkpoint_hash` (or the hot/position variants) computation regresses.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) against the corresponding fields on `txn_info`, mirroring the existing `ensure!` pattern used for `state_change_hash`/`event_root_hash`. This should be completed and enabled before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on in production, as the code comment itself indicates.

### Proof of Concept
Not directly exploitable by an external actor as a standalone PoC; the issue is a missing-check code path rather than an attacker-triggerable transaction. Demonstration path:
1. In `execution/executor/src/workflow/do_state_checkpoint.rs`, introduce (or trigger via an existing latent bug) a divergence so that `state_checkpoint_hashes` (or `position_state_checkpoint_hashes`) computed during replay differs from the value stored in the archived `TransactionInfo`, while write set, events, gas, and status remain identical.
2. Run `storage/db-tool/src/replay_on_archive.rs` (or `aptos-debugger`) against the archive.
3. Because `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2203) never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, the replay-verify tool reports the transaction as matching despite the state-root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
