### Title
Missing bounds validation on `ENERGY_FEE` / `EXCHANGE_CREATE_FEE` chain parameters in `ProposalUtil.validator` allows unsafe values to be committed via governance proposals - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator()` is the single safety gate that `ProposalCreateActuator.validate()` calls before a chain-parameter-change proposal is accepted onto the chain, and the same values are later written verbatim into `DynamicPropertiesStore` by `ProposalService.process()` once the proposal is approved. Most numeric parameters (`ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, `TRANSACTION_FEE`, etc.) are bounds-checked against `[0, LONG_VALUE]`, but `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` explicitly fall through with `break` and no check at all, so any value — including `0`, a negative number, or `Long.MAX_VALUE` — is accepted and later applied unconditionally by `ProposalService.process()`.

### Finding Description
`ProposalUtil.validator()` is the "guarded path" analogous to the proxy's `_assertValidStorageParams` in the 0x report: it is meant to reject nonsensical parameter values before they are ever written to persistent state. [1](#0-0) 
enforces `[0, LONG_VALUE]` for a whole family of fee-like parameters, but the very next case, [2](#0-1) 
for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` performs no check whatsoever and simply `break`s out of the switch, letting `validate()` return `true` for any `long` value supplied in the `ProposalCreateContract`.

`ProposalCreateActuator.validate()` calls this validator for every parameter in the proposal and, if it does not throw, treats the value as safe: [3](#0-2) 

Once the proposal collects enough approvals, `ProposalService.process()` writes the unvalidated value directly into `DynamicPropertiesStore` with no further sanity check: [4](#0-3) 

`ENERGY_FEE` is the SUN-per-energy exchange rate used throughout energy/fee accounting for every smart-contract transaction (`VMActuator`, `ReceiptCapsule`, `Wallet`, `TransactionTrace`, etc.), and `EXCHANGE_CREATE_FEE` gates the cost of creating a bancor-style exchange pair. Neither is checked for being non-negative or within any sane bound before being persisted, unlike its sibling fee parameters a few lines above in the same switch statement — mirroring exactly the pattern in the 0x report where `setParams` skipped the range checks otherwise enforced during initialization/attach.

### Impact Explanation
If `ENERGY_FEE` is set to `0` (or a negative value, since `long` is signed and unchecked), every energy unit consumed by TVM execution becomes free, letting any account submit arbitrarily heavy smart-contract transactions with no TRX cost — a direct resource-accounting break that enables denial-of-service against the network's energy market. Setting it to `Long.MAX_VALUE` would make ordinary contract calls prohibitively/impossibly expensive, effectively halting all smart-contract activity. `EXCHANGE_CREATE_FEE` set to `0` similarly removes the economic friction meant to rate-limit exchange creation, enabling spam of `ExchangeCreateContract`s that consume chain storage.

### Likelihood Explanation
Exploitation requires that a proposal containing these parameter codes be created (any account registered as a witness can create a `ProposalCreateContract`, per the check at `ProposalCreateActuator.validate()`) and subsequently approved by the required quorum of active witnesses through the normal governance/voting flow — this is the same "authorized address" precondition as in the original report, where `setParams` was still restricted to an authorized caller yet still lacked bounds checking. The missing check means the proposal-approval consensus mechanism (multi-witness governance) is the only remaining safeguard, and unlike other numeric parameters there is no automated/protocol-level range enforcement to catch a mistaken or malicious value for these two fields specifically.

### Recommendation
Add explicit bounds checks for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` in `ProposalUtil.validator()` (e.g. `value >= 0` and an upper bound consistent with `LONG_VALUE` or another sane ceiling, mirroring the checks already applied to `ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, etc.), so that `ProposalService.process()` can never persist an unsafe or nonsensical energy-fee/exchange-fee value into `DynamicPropertiesStore`.

### Proof of Concept
1. Register (or use) a witness account and submit a `ProposalCreateContract` with `parameters = { ENERGY_FEE_CODE: 0 }`.
2. `ProposalCreateActuator.validate()` calls `ProposalUtil.validator(..., ENERGY_FEE, 0)`, which hits the `case ENERGY_FEE: ... break;` branch (`ProposalUtil.java:74-76`) and returns without throwing — the proposal is accepted.
3. Once the proposal reaches the required witness-approval quorum, `ProposalService.process()` executes `case ENERGY_FEE: manager.getDynamicPropertiesStore().saveEnergyFee(entry.getValue());` and commits `ENERGY_FEE = 0` to state with no further validation.
4. From that point, all TVM energy consumption becomes free, so any account can submit maximally energy-intensive contract calls at zero SUN cost, exhausting node resources.
