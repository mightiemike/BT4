## Finding: Replay-verification skips checkpoint-hash comparison, masking state-root divergence

### Title
Replay-verification (`ensure_match_transaction_info`) omits state/hot-state/position checkpoint hash comparison, allowing a locally-diverged execution to be reported as matching the authenticated ledger - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole integrity check used by all replay/verify tooling (chunk-executor's `verify_execution`, `db-tool replay_on_archive`/`replay_verify`, and `aptos-debugger`) to confirm that a locally re-executed transaction reproduces the state actually committed and authenticated on-chain. The function explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the trusted `TransactionInfo`, so a state root divergence at a checkpoint boundary will not be detected by these tools.

### Finding Description
`ensure_match_transaction_info` verifies status, gas used, write-set hash (`state_change_hash`), and event root hash, but the checkpoint-hash fields are left unchecked, with an explicit acknowledgment in the code: [1](#0-0) 

Specifically the trailing comment states:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is the only comparator used across every consumer that performs local-execution-vs-authenticated-ledger verification:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, invoked when `VerifyExecutionMode` is engaged during chunk execution / backup verification (`storage/db-tool/src/replay_verify.rs`, `storage/backup/backup-cli/src/coordinators/replay_verify.rs`, `restore.rs`, `verify.rs`). [3](#0-2) 
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the archive-replay tool used to independently re-derive ledger state from an archive node and confirm it matches the authenticated `TransactionInfo`s. [4](#0-3) 
- `aptos-move/cli/src/commands.rs`, the CLI's transaction-replay comparison path. [5](#0-4) 

Because the checkpoint-hash fields (`state_checkpoint_hash`, and, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`hot_state_root_in_txn_info` are enabled, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) are precisely the fields that bind a `TransactionInfo` to the Merkle root of the actual committed state, [6](#0-5) 
skipping them means these tools validate only the write-set/event/gas/status agreement, not that the *resulting state tree root* after applying that write set matches what was actually committed and proven by the accumulator/ledger info chain.

### Impact Explanation
This is an integrity gap in the proof/replay-verification pivot specifically called out in the task's scope ("Hard-fork-only divergence during commit, replay, restore, or proof verification"). If local execution silently diverges from consensus-committed execution at a state-checkpoint boundary (e.g., due to a non-determinism bug, a native/aggregator materialization bug, or an intentionally malicious replay source feeding a crafted `TransactionInfo`/write-set pair whose write-set hash still matches but whose downstream Merkle state differs from what the network actually settled on), `replay_on_archive`, `replay_verify`, and the chunk-executor's execution-verification path will all report success. This defeats the exact safety mechanism operators rely on to detect state-root divergence (hard-fork-class bugs) before they propagate, and to validate archive/backup data prior to restore.

### Likelihood Explanation
The condition is deterministic and always present — it is not a race or edge case, but a structural omission acknowledged directly in the source as a `TODO`. Any divergence that affects only the state/hot-state/position checkpoint roots (without altering write-set bytes, event bytes, gas, or status) will go undetected every time these tools are run. The severity is elevated because this is precisely the failure mode that the "trading-native"/native-position feature (guarded by `compute_trading_native_state_roots`) introduces new checkpoint roots for, and the comment shows the authors are aware but have not yet closed the gap before flipping that feature on.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally-computed equivalents (when available/applicable) before treating a replay as verified, and gate the enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on this check being in place, as the existing TODO comment recommends.

### Proof of Concept
Not applicable as a live network exploit — the issue is a verification-tooling gap, not a consensus-safety-net bypass. Concretely: construct (or corrupt) a chunk of `(Transaction, TransactionOutput, TransactionInfo)` where the write set, events, gas, and status all match the given `TransactionInfo`, but where a locally computed state-checkpoint root (from applying the write set to the prior state tree) differs from `txn_info.state_checkpoint_hash()`. Running `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` (or `chunk_executor::verify_execution`) over this chunk returns `Ok(())`/no error, because `ensure_match_transaction_info` never inspects the checkpoint-hash fields.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
