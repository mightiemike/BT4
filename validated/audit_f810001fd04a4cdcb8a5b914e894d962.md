### Title
Unbounded O(N) full-store scan in `getAssetIssueByAccount` allows public-cost-underpriced DoS - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`GetAssetIssueByAccountServlet` is a public, unauthenticated HTTP GET/POST endpoint that calls `Wallet.getAssetIssueByAccount`, which loads the *entire* asset-issue store via `getAllAssetIssues()` and runs `BandwidthProcessor.updateUsage()` on every entry before filtering by the requested address. Unlike `Wallet.getAssetIssueList(offset, limit)`, this method has no pagination or bound, so its cost scales linearly with the total number of TRC10 assets on the chain regardless of how many (or how few) assets the queried address actually owns.

### Finding Description
The HTTP entrypoint `GetAssetIssueByAccountServlet.doGet`/`doPost` accepts an arbitrary attacker-supplied `address` parameter and calls `wallet.getAssetIssueByAccount(address)` [1](#0-0) .

`Wallet.getAssetIssueByAccount` retrieves the full list of asset issues with `getAssetIssueStoreFinal(...).getAllAssetIssues()`, runs `BandwidthProcessor.updateUsage(issueCapsule)` on *every* capsule, and only afterward filters by `ownerAddress.equals(accountAddress)`: [2](#0-1) 

`AssetIssueStore.getAllAssetIssues()` performs a full iterator scan over the entire underlying store with no limit: [3](#0-2) 

By contrast, `Wallet.getAssetIssueList(offset, limit)` uses `getAssetIssuesPaginated(offset, limit)`, which caps the result via `ASSET_ISSUE_COUNT_LIMIT_MAX` [4](#0-3) [5](#0-4)  — no equivalent bound exists on `getAssetIssueByAccount`.

The only protection at the servlet layer is `RateLimiterServlet`, which enforces a per-endpoint QPS/permit limiter (`DefaultBaseQqsAdapter`/`QpsStrategy.DEFAULT_QPS_PARAM`) and a `GlobalRateLimiter`, but this bounds *request count*, not *per-request CPU cost* [6](#0-5) . A fixed QPS ceiling multiplied by an O(N) per-request cost (N = total asset issues on-chain) still yields unbounded aggregate CPU work as N grows, so the guard does not neutralize the underlying complexity issue.

### Impact Explanation
An unprivileged remote caller can repeatedly invoke `GET /getassetissuebyaccount?address=<any address>` (a query for an account that owns zero or one asset costs the same as scanning the whole store). On a node with a large TRC10 asset population, each request forces a full store deserialization/iteration plus a `BandwidthProcessor.updateUsage` call per asset issue, consuming CPU/I/O disproportionate to the requester's own resource footprint. Sustained calls at the endpoint's allowed QPS can degrade the full node's HTTP tier responsiveness, indirectly affecting other public API consumers (e.g., transaction broadcast clients) sharing the same JVM/thread pool — a resource-exhaustion availability degradation scoped to the queried full node.

### Likelihood Explanation
The endpoint requires no authentication, no on-chain transaction, and no special privileges — any HTTP client can call it. The precondition (a large number of issued TRC10 assets on the target full node) is realistic for public mainnet/testnet nodes with years of TRC10 issuance history. The attack is trivially repeatable (loop of GET requests within the rate-limit budget) and doesn't require crafting valid signatures or paying fees, since it is a read-only HTTP query, not a state-changing transaction.

### Recommendation
Bound `Wallet.getAssetIssueByAccount` similarly to the paginated variant: either (a) look up assets by owner via an index (if one exists) instead of a full scan, or (b) cap the number of `AssetIssueCapsule` entries scanned/processed per request (e.g., reuse `ASSET_ISSUE_COUNT_LIMIT_MAX` or short-circuit after the account's known asset count from `AccountCapsule`), and defer/skip `BandwidthProcessor.updateUsage` for entries filtered out before processing bandwidth accounting.

### Proof of Concept
Java benchmark test (JUnit) sketch, added alongside `WalletTest`:
```java
@Test
public void benchmarkGetAssetIssueByAccountScalesWithTotalAssets() {
  // Populate N synthetic AssetIssueCapsule entries owned by distinct addresses,
  // none matching the queried address except possibly one.
  int[] sizes = {1_000, 10_000, 50_000};
  long[] elapsedNanos = new long[sizes.length];
  for (int i = 0; i < sizes.length; i++) {
    seedAssetIssueStore(dbManager, sizes[i]); // helper inserting AssetIssueCapsule w/ unique owners
    ByteString queried = ByteString.copyFromUtf8("NonExistentAddress");
    long start = System.nanoTime();
    wallet.getAssetIssueByAccount(queried);
    elapsedNanos[i] = System.nanoTime() - start;
  }
  // Assert latency grows roughly linearly with N (total assets), not with the
  // queried account's asset count (which is 0 in all cases).
  double ratio1 = (double) elapsedNanos[1] / elapsedNanos[0];
  double ratio2 = (double) elapsedNanos[2] / elapsedNanos[1];
  Assert.assertTrue("latency should scale ~linearly with total asset count",
      ratio1 > 5 && ratio2 > 3); // sizes grow 10x and 5x respectively
}
```
Expected result: latency/CPU scales with total store size N rather than the 0 assets actually owned by the queried address, confirming the O(N) unbounded-scan cost model; combined with `RateLimiterServlet`'s fixed QPS budget (`QpsStrategy.DEFAULT_QPS_PARAM`), aggregate per-second CPU cost is shown to grow unbounded as N increases, since the limiter caps request count, not per-request work.

  public AssetIssueList getAssetIssueByAccount(ByteString accountAddress) {
    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),

    AssetIssueList.Builder builder = AssetIssueList.newBuilder();

        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
