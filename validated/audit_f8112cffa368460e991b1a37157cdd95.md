### Title
Unvalidated attacker-controlled `ak`/`nk` byte array lengths reach native JNI `librustzcashComputeNf` via `/wallet/isspend`, causing native heap corruption/JVM crash - ([File: IsSpendServlet.java])

### Summary
The public HTTP endpoint `/wallet/isspend` accepts a `NoteParameters` payload whose `ak`/`nk` fields are forwarded unchecked through `Wallet.isSpend` → `Note.nullifier(byte[] ak, byte[] nk, long position)` → `JLibrustzcash.librustzcashComputeNf` → the native JNI method `librustzcashSaplingComputeNf`. Unlike sibling methods in the same class, `librustzcashComputeNf` performs no length validation before invoking native code that expects fixed 32-byte buffers.

### Finding Description
`IsSpendServlet.doPost` parses arbitrary user-supplied JSON into `NoteParameters` via `PostParams.getPostParams` and `JsonFormat.merge`, then calls `wallet.isSpend(build.build())` [1](#0-0) . That data flows into `Note.nullifier(byte[] ak, byte[] nk, long position)`, which builds a `ComputeNfParams` object directly from the raw `ak`/`nk` arrays with no size check and hands it to `JLibrustzcash.librustzcashComputeNf` [2](#0-1) .

Critically, `JLibrustzcash.librustzcashComputeNf` calls straight into the native JNI binding `INSTANCE.librustzcashSaplingComputeNf(...)` with no preceding validation [3](#0-2) . This is inconsistent with sibling methods in the exact same class — `librustzcashAskToAk`, `librustzcashNskToNk`, `librustzcashSaplingGenerateR`, and `librustzcashToScalar` all call `LibrustzcashParam.valid32Params(...)` or `validParamLength(...)` before invoking their respective native calls [4](#0-3) , and `librustzcashToScalar` validates its 64-byte input explicitly [5](#0-4) . `librustzcashComputeNf` is the outlier that skips this pattern entirely, despite the underlying Rust/C `librustzcash_sapling_compute_nf` FFI signature expecting exactly 32-byte `ak`/`nk`/`d`/`r` buffers (standard Zcash Sapling ABI convention used throughout this codebase's other JNI calls).

I was unable to fully retrieve the body of `Wallet.isSpend` in this session (only match counts were returned, not source), so I cannot confirm with certainty whether `Wallet.isSpend` inserts its own length check on `ak`/`nk` before calling `note.nullifier(...)`. This is a genuine gap in verification that should be resolved before treating this as conclusively exploitable — if `Wallet.isSpend` already validates lengths (e.g., via `checkAllowShieldedTransactionApi` or explicit array-length asserts), the vulnerability would be mitigated at that layer. This should be checked directly in `framework/src/main/java/org/tron/core/Wallet.java` before acting on this report.

### Impact Explanation
If `Wallet.isSpend` does not itself enforce 32-byte lengths on `ak`/`nk` (unconfirmed), an unauthenticated remote caller could submit a `NoteParameters` JSON body with `ak`/`nk` of arbitrary length (0, 16, 31, 33, 1024 bytes) to `/wallet/isspend`. Because the JNI boundary in `librustzcashComputeNf` reads/writes fixed-size buffers in native code without a Java-side length check, a mismatched buffer size passed across the JNI boundary can cause an out-of-bounds native memory read/write, corrupting the JVM native heap and crashing the node process — a denial-of-service against any full node exposing this public HTTP API.

### Likelihood Explanation
This requires only that shielded transaction APIs be enabled (a standard, common node configuration, not an attacker precondition beyond normal operation) and that the attacker can reach the public `/wallet/isspend` HTTP endpoint, which requires no authentication. Feasibility hinges entirely on whether `Wallet.isSpend` validates array lengths before calling `Note.nullifier` — this could not be confirmed with the available tool budget.

### Recommendation
Add explicit length validation for `ak` and `nk` (and other fixed-size fields such as `d`, `pkD`, `rcm`) in `JLibrustzcash.librustzcashComputeNf`, mirroring the pattern already used by `librustzcashAskToAk`, `librustzcashNskToNk`, and `librustzcashToScalar` (i.e., call `LibrustzcashParam.valid32Params(...)` on each buffer before invoking `INSTANCE.librustzcashSaplingComputeNf(...)`), and/or validate lengths in `Note.nullifier` before constructing `ComputeNfParams`, and/or in `Wallet.isSpend` immediately after deserializing the `NoteParameters` request, throwing a catchable `ZksnarkException`/`ContractValidateException` instead of allowing malformed buffers to reach the JNI boundary.

### Proof of Concept
Since `Wallet.isSpend`'s source could not be confirmed in this session, the PoC below targets the confirmed unvalidated path directly, and should be paired with an integration test at the HTTP layer once `Wallet.isSpend`'s validation behavior is confirmed:

```java
// Unit test in chainbase/src/test/java/org/tron/common/zksnark/JLibrustzcashTest.java
@Test
public void testComputeNfWithInvalidAkNkLengths() {
  int[] badLengths = {0, 16, 31, 33, 1024};
  for (int len : badLengths) {
    byte[] d = new byte[11];
    byte[] pkD = new byte[32];
    byte[] rcm = new byte[32];
    byte[] ak = new byte[len];   // malformed
    byte[] nk = new byte[len];   // malformed
    byte[] result = new byte[32];
    ComputeNfParams params = new ComputeNfParams(d, pkD, 100L, rcm, ak, nk, 0L, result);
    // Expected: a catchable Java exception (e.g., IllegalArgumentException/ZksnarkException)
    // Actual (if unpatched): JVM crash/hang or silent native memory corruption
    assertThrows(Exception.class, () -> JLibrustzcash.librustzcashComputeNf(params));
  }
}
```

An HTTP-level fuzz/integration test should additionally POST crafted `NoteParameters` JSON bodies (with `ak`/`nk` set to hex strings of 0, 32, 62, 66, and 2048 hex chars) to `/wallet/isspend` against a running node with shielded transactions enabled, and assert the node process remains alive and returns an HTTP error rather than crashing — this requires confirming `Wallet.isSpend`'s actual validation logic first.
