### Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, letting corrupted state roots pass replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the single function used to confirm that a locally re-executed `TransactionOutput` matches an authenticated, previously-committed `TransactionInfo` (the accumulator leaf that is signed by validators / bundled in backups). It checks status, gas, write-set hash, and event-root hash, but it deliberately skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually bind a transaction to the Sparse-Merkle/Jellyfish state root. This is functionally analogous to the `PhiNFT1155` bug: a guard exists and looks complete, but the specific field that must be checked to enforce the invariant ("committed state == this execution's state") is silently omitted.

### Finding Description
`ensure_match_transaction_info` compares the recomputed `TransactionOutput` against the trusted `TransactionInfo` for status, gas used, write-set hash (`state_change_hash`) and event root hash: [1](#0-0) 

Immediately after these checks, the function contains an explicit acknowledgement that the state-root-related fields are not verified: [2](#0-1) 

`TransactionInfoV1` (and V0) carry `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as the cryptographic commitments to the actual world-state root(s) at that version: [3](#0-2) 

This function is the sole verifier used by the `db-tool replay-verify` / `replay_on_archive` tool, which re-executes archived transactions through the real VM and calls `ensure_match_transaction_info` against the archived (authenticated) `TransactionInfo` to decide pass/fail: [4](#0-3) 

Because the state-checkpoint-hash family is skipped, a divergence between the state root produced by local re-execution and the state root that was actually committed/signed on-chain (whether from a determinism bug, storage corruption, or an incorrectly applied write-op/state-value-metadata conversion — the very class of bug hinted at in `write_op_converter.rs`) will not be detected: the tool will report a *successful* replay even though the authenticated state root has silently diverged.

### Impact Explanation
This breaks the "authenticated response bound to the right root" invariant: the entire purpose of `replay-verify`/`replay_on_archive` is to catch exactly this class of divergence (VM output != committed ledger state). A silent gap here means that a hard-fork-class state-transition bug, a state-value-metadata/WriteOp conversion bug, or storage-level corruption affecting the JMT/hot-state/position-native state root would pass the state-integrity audit undetected on mainnet archival data, undermining the guarantee that "committed state differs from the correct VM result" would be caught. This is a proof/commitment-integrity gap in the primary tool relied upon to detect exactly that class of issue.

### Likelihood Explanation
The gap is unconditional and always present in `ensure_match_transaction_info` — it is not gated by any config, and the comment states it applies before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is even enabled. Any future or existing state-root-affecting bug (e.g. a state-value-metadata bug in `write_op_converter.rs`, or a hot-state/position accumulation bug in `block-executor`/`native_state_committer.rs`) is automatically invisible to this checker, so likelihood of the checker's blind spot mattering scales directly with the likelihood of any state-corrupting bug elsewhere in the stack — and there is no compensating control in this code path.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the recomputed output/state and the trusted `TransactionInfo` whenever those hashes are present (i.e., at checkpoint boundaries), rather than only checking write-set/event root hashes. At minimum, gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS` enablement on this fix being landed, as the comment itself recommends.

### Proof of Concept
1. Run `db-tool replay-verify` (`storage/db-tool/src/replay_on_archive.rs::Verifier::execute_and_verify`) against an archive.
2. Craft (or simulate via a bug) a scenario where the VM re-execution produces a correct write set/events/gas/status but an incorrect state checkpoint root (e.g., due to a bug in state-value-metadata handling or in-memory SMT update logic that doesn't affect the write set hash itself, only how it's folded into the checkpoint root).
3. `ensure_match_transaction_info` at [5](#0-4)  will return `Ok(())` because it never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
4. The replay tool at [6](#0-5)  records no failure, reporting a clean replay-verify run despite the state root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
