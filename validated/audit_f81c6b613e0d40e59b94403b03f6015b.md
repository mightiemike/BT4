### Title
Dynamic Energy Factor grief attack via asymmetric snap-up/slow-decay update in `ContractStateCapsule.catchUpToCycle` - (File: `chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java`)

### Summary
`ContractStateCapsule.catchUpToCycle()` implements TVM's "dynamic energy" congestion-pricing mechanism for smart contracts. Like the ETWAP bug in the external report, it updates a state variable (`energyFactor`) asymmetrically: the factor jumps up **immediately** (within the very next cycle) once usage exceeds a threshold, but only decays **gradually**, multiplicatively over subsequent cycles. Any unprivileged account can trigger the spike by sending ordinary `TriggerSmartContract` transactions that push a target contract's energy usage above `dynamicEnergyThreshold`, after which the elevated factor imposes an energy "penalty" surcharge on every subsequent caller of that contract for several cycles until it decays back down.

### Finding Description
`catchUpToCycle` is invoked once per contract per cycle transition from `Program.updateContextContractFactor()`: [1](#0-0) 

The core asymmetry is in the update logic itself: [2](#0-1) [3](#0-2) 

- If `energyUsage` (accumulated in the just-finished cycle) exceeds `threshold`, the factor is bumped up by `increasePercent` **immediately** for the very next cycle (`lastCycle += 1`).
- Any subsequent gap of cycles is only ever handled by the decrease branch, which multiplies the factor by `decreasePercent` raised to `cycleCount` — a slow exponential decay (documented in-code as 75%–100% per step).

There is no path that lets the factor snap back down quickly; it can only be driven up quickly and must decay slowly, mirroring the ETWAP flaw's "immediate set on increase, slow decay on decrease" pattern.

This factor is then read back and applied as an energy multiplier/penalty on every opcode and every CALL executed against the contract, for as long as the factor remains above `DYNAMIC_ENERGY_FACTOR_DECIMAL`: [4](#0-3) [5](#0-4) 

Energy usage accumulation itself is attacker-controllable and cheap: any account can call `TriggerSmartContract` on a target contract repeatedly (or in one heavy transaction) to push `energyUsage` above `threshold`: [6](#0-5) 

Once the next cycle boundary is crossed, `energyFactor` snaps up (bounded by `dynamicEnergyMaxFactor`), and every other unrelated user calling that same contract in the following cycles pays an inflated energy cost / penalty (`penalty = energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL - energy`) until the multiplicative decay eventually brings the factor back down — this can take multiple cycles depending on `dynamicEnergyIncreaseFactor` (the feature is committee-tunable: `DYNAMIC_ENERGY_THRESHOLD`, `DYNAMIC_ENERGY_INCREASE_FACTOR`, `DYNAMIC_ENERGY_MAX_FACTOR`, `ALLOW_DYNAMIC_ENERGY`): [7](#0-6) 

The test suite confirms the decay is gradual over consecutive cycles (7500 → 5312 → 3398 → ... rather than an immediate reset): [8](#0-7) 

### Impact Explanation
Any account can, with an ordinary broadcast transaction (no special privileges), force a target smart contract's dynamic-energy factor into its elevated state, then stop transacting. All subsequent unrelated legitimate callers of that same contract pay elevated energy costs (`spendEnergyWithPenalty`) or, if they had budgeted for the base energy cost, may fail with `OutOfEnergyException`, for several cycles while the factor decays. This is a griefing/DoS on legitimate users of a specific contract's calls, directly reachable via unprivileged `TriggerSmartContract` transactions — analogous to the reported redeem-DoS grief attack, just applied to contract call economics instead of a redeem cap.

### Likelihood Explanation
Medium. The feature (`allowDynamicEnergy`) must be enabled by committee proposal for it to be active, and the attacker must spend real energy/fees to push usage above `dynamicEnergyThreshold` in a cycle — there is no flash-loan-style "spike and instantly reverse in the same transaction" available here because the factor update only happens at cycle boundaries (there's no atomic mint+redeem primitive as in the DeFi report), so the attack cost is nonzero and cannot be perfectly undone within one transaction. This lowers likelihood relative to the original flash-loan-enabled report, but the underlying "instant up / slow decay" asymmetry is structurally identical and is exploitable by any funded account willing to pay for the initial energy spike.

### Recommendation
Apply symmetric responsiveness in both directions: either allow the decrease branch to also react within the same cycle transition that produced the increase (so a single high-usage cycle doesn't lock in elevated pricing for many subsequent low-usage cycles), or bound the maximum number of cycles the factor can remain elevated independent of actual subsequent usage, and consider decaying based on measured subsequent low usage rather than a fixed multiplicative schedule — mirroring the original recommendation to apply the same update logic in both directions.

### Proof of Concept
1. Assume `allowDynamicEnergy = 1`, `dynamicEnergyThreshold = T`, `dynamicEnergyIncreaseFactor = F` are enabled via committee proposal (`ProposalService.process`, case `ALLOW_DYNAMIC_ENERGY`/`DYNAMIC_ENERGY_THRESHOLD`/`DYNAMIC_ENERGY_INCREASE_FACTOR`).
2. Attacker sends one or more `TriggerSmartContract` transactions against victim contract `C` within a single cycle, driving `ContractStateCapsule.energyUsage` for `C` above `T` (via `Program.addContextContractUsage`).
3. At the next cycle boundary, any call into `C` triggers `Program.updateContextContractFactor()` → `catchUpToCycle()`, which immediately raises `energyFactor` for `C` (lines 108–120 of `ContractStateCapsule.java`).
4. For the following cycles, legitimate unrelated users calling `C` via `VM.play`/`EnergyCost.getCalculateCallCost` pay `penalty = energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL - energy` extra energy, or exhaust their energy limit and revert with `OutOfEnergyException`, until the exponential decay (`decreasePercent^cycleCount`) brings `energyFactor` back near baseline — a delay controllable by tuning how large the initial spike was (up to `dynamicEnergyMaxFactor`).

  public long updateContextContractFactor() {
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());

    if (contractStateCapsule == null) {
      contractStateCapsule = new ContractStateCapsule(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber());
      contractState.updateContractState(getContextAddress(), contractStateCapsule);
    } else {
      if (contractStateCapsule.catchUpToCycle(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber(),
          VMConfig.getDynamicEnergyThreshold(),
          VMConfig.getDynamicEnergyIncreaseFactor(),
          VMConfig.getDynamicEnergyMaxFactor(),
          VMConfig.allowStrictMath(),
          VMConfig.disableJavaLangMath())) {
        contractState.updateContractState(getContextAddress(), contractStateCapsule
        );
      }
    }
    contextContractFactor = contractStateCapsule.getEnergyFactor()
        + Constant.DYNAMIC_ENERGY_FACTOR_DECIMAL;
    return contextContractFactor;
  }
