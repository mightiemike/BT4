### Title
Missing minimum-liquidity validation in `ExchangeCreateActuator` allows anonymous creation of permanently malfunctioning bonding-curve exchange pairs — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java])

### Summary
`ExchangeCreateActuator.doValidate()` only rejects `firstTokenBalance`/`secondTokenBalance` that are `<= 0` or above the platform-wide `ExchangeBalanceLimit`, but enforces no *minimum* liquidity for a newly created TRX/TRC10 bonding-curve exchange pair. Any anonymous account able to broadcast an `ExchangeCreateContract` (paying only the modest `ExchangeCreateFee`) can create a pool with balances as small as `1` unit on each side. Because the pool's pricing math (`ExchangeProcessor`/`SafeExchangeProcessor`) is a Bancor-style formula that raises `1 + quant/balance` to fractional exponents (`0.0005`/`2000.0`) using double/`BigDecimal` arithmetic and then truncates the result to a `long`, an extremely small initial balance causes any subsequent legitimate trade against that exchange id to be rounded down to (or near) zero output — the exact "malfunctioning pair with maturity/state" bug class described in the Timeswap report, where a caller-controlled tiny initial reserve value permanently breaks the AMM invariant for that pool.

The created pool is persisted with these attacker-chosen balances via `ExchangeCapsule.setBalance` and stored in both `ExchangeStore`/`ExchangeV2Store`: [2](#0-1) 

Trading against the pool goes through `ExchangeCapsule.transaction()`, which delegates to `ExchangeProcessor`/`SafeExchangeProcessor`: [3](#0-2) 

The core pricing routine performs a Bancor-relay calculation with `Math.pow` and casts the final result to `long`, which truncates any fractional/near-zero result to `0`: [4](#0-3) [5](#0-4) 

With `firstTokenBalance = 1` and `secondTokenBalance = 1` (the minimum permitted by validation), a manual walk-through of `exchangeToSupply`/`exchangeFromSupply` for even a modest sell quantity yields a computed `exchangeBalance` well under `1.0`, which is floored to `0` by the `(long)`/`setScale(..., RoundingMode.DOWN)` cast. `ExchangeTransactionActuator.execute()` nonetheless commits the trade unconditionally — the seller's tokens are deducted and added to the pool, while the buyer receives `anotherTokenQuant = 0`: [6](#0-5) 

This mirrors the confirmed Timeswap finding: an attacker/creator sets the pool's reserve to a value so small that the bonding-curve math can no longer produce meaningful, monotonic pricing, permanently "bricking" that specific pair for any counter-party who later interacts with it via `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` (all of which operate on whatever balances happen to be stored, with no minimum-balance re-check beyond `!=0`): [7](#0-6) 

### Impact Explanation
Any account that funds a trade against such a degenerate exchange loses the tokens it sends into the pool while the pricing formula returns `0` (or a negligible amount) back, because the reduce/add of token balances in `ExchangeTransactionActuator.execute()` happens unconditionally after `exchangeCapsule.transaction()` runs, regardless of how small the computed `anotherTokenQuant` is. This is an **asset/accounting corruption / value-extraction vector**: the pool creator can seed a 1/1 (or similarly tiny) pair, and any unsuspecting trader who selects that exchange id by mistake or via a wallet/dApp that doesn't check reserve depth suffers value loss with no recourse, while the pool itself becomes unusable for its intended economic purpose (a permanent DoS on that specific liquidity pair, matching the "malfunction the pair ... can only be abandoned" language in the source report).

### Likelihood Explanation
The `ExchangeCreateContract` is a standard, unprivileged, broadcastable transaction type reachable by any funded account — the only requirement is paying `ExchangeCreateFee` and satisfying `firstTokenBalance > 0`/`secondTokenBalance > 0` plus the upper `ExchangeBalanceLimit`. No admin/witness/SR privilege is required, and no minimum-balance floor exists to prevent this. Because TRON's exchange model allows arbitrarily many exchange ids for the same token pair (unlike a single canonical AMM pair per token pair), an attacker can freely create additional low-liquidity, malfunctioning pairs for popular token pairs to try to lure traders.

### Recommendation
Add a minimum-liquidity check in `ExchangeCreateActuator.doValidate()` (and ideally in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` post-conditions) requiring `firstTokenBalance` and `secondTokenBalance` to be no smaller than a chain-governed minimum (a new dynamic property, e.g. `MIN_EXCHANGE_BALANCE`), analogous to the Timeswap recommendation of enforcing a minimum `state.y`. Additionally, `ExchangeTransactionActuator` should reject trades whose computed `anotherTokenQuant` rounds to `0` (or falls under `tokenExpected`), rather than committing a trade that transfers real tokens into the pool for zero (or dust) return.

### Proof of Concept
1. Attacker broadcasts `ExchangeCreateContract` with `first_token_id = "_"` (TRX), `first_token_balance = 1`, `second_token_id = <TRC10 id>`, `second_token_balance = 1`. `doValidate()` passes because both values are `> 0` and `<= ExchangeBalanceLimit`, per [1](#0-0) .
2. The exchange is created and stored with `firstTokenBalance=1, secondTokenBalance=1` via [8](#0-7) .
3. A victim broadcasts `ExchangeTransactionContract` selling, e.g., `1_000` sun of TRX into this exchange id. `ExchangeCapsule.transaction()` invokes `ExchangeProcessor.exchange(1, 1, 1000)` (or the hardened `SafeExchangeProcessor` equivalent), whose intermediate `Math.pow`/`BigDecimal.pow`-based computation for such an extreme `quant/balance` ratio produces a final `exchangeBalance` that truncates to `0` when cast to `long` (see [9](#0-8) ).
4. `ExchangeTransactionActuator.execute()` deducts the victim's `1_000` sun and calls `addAssetAmountV2(anotherTokenID, 0, ...)`, so the victim receives nothing back while the pool absorbs their TRX, per [6](#0-5) .

Note: I was unable to fully verify within the available context whether `ExchangeTransactionActuator.doValidate()` compares the pre-computed `anotherTokenQuant` against `tokenExpected` as a slippage guard before `execute()` runs (the validate method body I inspected covers balance/limit checks but I did not confirm an explicit `anotherTokenQuant >= tokenExpected` assertion). If such a check exists elsewhere in `doValidate()`, it would mitigate — but not eliminate — the underlying root cause, since `tokenExpected` is user-supplied and a naive trader/dApp integration could still set a low or default expected value. A Devin session with full file access would be needed to confirm this detail conclusively.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
