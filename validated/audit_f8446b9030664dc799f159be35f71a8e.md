## Analog Identified: Permanent poisoning of DKG aggregate-key candidates via unconditional `used-aggregate-public-keys` write

### Title
Single signer vote permanently blocks reuse of an aggregate public key in future reward cycles, with no recovery mechanism — (`File: stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
The `QuailFinance` report's root cause is a state-mutating action that any single required party can perform (or withhold) with no expiry/undo path, permanently locking funds. The same structural flaw exists in Stacks' signer DKG aggregate-key voting contract: `vote-for-aggregate-public-key` unconditionally marks a candidate key as "used" for a reward cycle the instant *any single signer* casts a vote for it — regardless of whether that vote ever reaches the 70% consensus threshold. That mark is permanent and has no expiry, so it can pre-emptively block that exact key from ever being approved in any other reward cycle.

### Finding Description
`vote-for-aggregate-public-key` records `used-aggregate-public-keys` for a key on every vote cast, not only on a vote that completes consensus: [1](#0-0) 

The novelty check that gates future votes only tolerates re-use of a key *within the same reward cycle*; any other cycle sees it as already used and rejects it: [2](#0-1) 

```
(define-read-only (is-novel-aggregate-public-key (key (buff 33)) (reward-cycle uint))
    (is-eq (default-to reward-cycle (map-get? used-aggregate-public-keys key)) reward-cycle))
```

Because a single signer's vote for candidate key `K` in reward-cycle `C` — even one that never accumulates enough weight to be approved — writes `used-aggregate-public-keys[K] = C`, that exact key `K` becomes permanently unusable in every other reward cycle (`is-novel-aggregate-public-key` will return `false` for it, causing `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY` on `asserts!` at line 159). This is a state-mutation performed unilaterally by a minority/unprivileged party (a single signer with any nonzero weight is enough — see `get-signer-weight`), with no threshold requirement to write the poison mark, and no window/expiry to undo it — structurally identical to the reported pattern of "a required unilateral action, once withheld or misused, has no time-bounded fallback."

The equality broken is the one the voting protocol relies on: *the same aggregate key value must remain votable in the reward cycle that the actual DKG round settles on it*. A single minority signer can break that invariant for a specific key value by pre-emptively "voting" for it in an earlier, unrelated cycle.

### Impact Explanation
If the honest signer set's deterministic FROST/DKG protocol (same signer-set membership, same round index) reproduces the *same* aggregate public key value in a later reward cycle that a minority signer already poisoned in an earlier cycle, every subsequent `vote-for-aggregate-public-key` call for that key in the later cycle reverts with `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY`, and the round cannot complete for that value. Because `get-approved-aggregate-key` for that cycle is then consulted by the node to determine the signing key for block validation and PoX transfers (`get_aggregate_public_key_pox_4` in `stackslib/src/chainstate/stacks/boot/mod.rs`), a stalled DKG round can delay or prevent block signing/finalization for that reward cycle — a temporary tip disagreement / liveness degradation bounded to the affected reward cycle, consistent with the "High" severity bucket (minority-triggerable divergence bounded impact) rather than Critical, since it requires the poisoned value to coincide with an actual future DKG output and does not by itself corrupt already-finalized state. [3](#0-2) 

### Likelihood Explanation
Triggering the state write itself requires only a single signer with nonzero weight submitting one transaction — this is trivially minority-triggerable and costs only the fee for one contract call. The harder part is causing an actual collision between the poisoned key and a future legitimate DKG output; this is straightforward if the DKG/FROST coordination software used by the signer set is deterministic for a given signer-set/round-index pair (common in many FROST implementations unless explicit randomness is injected per attempt), since an attacker who is himself part of the signer set (or can predict signer-set composition) can precompute or observe the candidate key before it's ratified and "burn" it in advance in an unrelated cycle.

### Recommendation
Only write to `used-aggregate-public-keys` when the vote actually causes `(map-insert aggregate-public-keys reward-cycle key)` to succeed (i.e., only mark a key "used" once it becomes the cycle's *approved* key), not on every individual vote. Alternatively, scope `used-aggregate-public-keys` uniqueness checks by reward-cycle only where necessary and add an explicit sunset/expiry so an unapproved vote's key-reservation cannot outlive its own voting window.

### Proof of Concept
1. In reward cycle `C`, attacker (any registered signer, even with the minimum single reward slot) calls `vote-for-aggregate-public-key(signer-index, K, round=0, reward-cycle=C)` for an arbitrary/predicted key `K`. The vote does not reach the 70% `threshold-weight`, so no key is approved for cycle `C`, but `used-aggregate-public-keys[K]` is now set to `C` (line 171 executes unconditionally before the threshold check at line 181).
2. In a later reward cycle `C'`, the honest signer majority's DKG round independently derives aggregate key `K` (plausible if the underlying DKG round is deterministic for the same signer set/round index, or the attacker otherwise anticipates the value).
3. Every honest signer's call to `vote-for-aggregate-public-key(index, K, round, C')` now fails `(asserts! (is-novel-aggregate-public-key key reward-cycle) (err ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY))` at line 159, because `used-aggregate-public-keys[K] = C ≠ C'`.
4. No aggregate key can be approved for `C'` using `K`; the round must restart with a different key, delaying finalization for cycle `C'` and demonstrating a minority-triggered liveness break with no time-bound recovery path, mirroring the `rotateLiquidity` freeze scenario in the source report.

    /// Get the aggregate public key for a given reward cycle from pox 4
    pub fn get_aggregate_public_key_pox_4(
        &mut self,
        sortdb: &SortitionDB,
        block_id: &StacksBlockId,
        reward_cycle: u64,
    ) -> Result<Option<Vec<u8>>, Error> {
        let aggregate_public_key_opt = self
            .eval_boot_code_read_only(
                sortdb,
                block_id,
                SIGNERS_VOTING_NAME,
                &format!("(get-approved-aggregate-key u{reward_cycle})"),
            )?
            .expect_optional()
            .map_err(|_| {
                Error::Expects("get-approved-aggregate-key did not return optional".to_string())
            })?;
        debug!(
            "Aggregate public key for reward cycle {reward_cycle} is {aggregate_public_key_opt:?}"
        );

        let aggregate_public_key = match aggregate_public_key_opt {
            Some(value) => {
                // A point should have 33 bytes exactly.
                Some(value.expect_buff(33).map_err(|_| {
                    Error::Expects(
                        "get-approved-aggregate-key did not return buff of length 33".to_string(),
                    )
                })?)
            }
            None => None,
        };
        Ok(aggregate_public_key)
    }
