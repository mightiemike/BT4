### Title
Receipts exceeding `max_receipt_size` bypass size enforcement via a "pretend it fits" clamp, permanently inflating congestion/bandwidth state - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
An analog to the Liferay `maxFileSize` DoS (CWE-400/CWE-770 — a size limit that is supposed to bound resource consumption is not actually enforced against the real object, only against a self-declared/clamped stand-in value) exists in nearcore's receipt-size enforcement path. `ValidateReceiptMode` explicitly documents (and tolerates) that receipts can be created above `max_receipt_size` after being modified post-validation, and the runtime's congestion/bandwidth-forwarding code intentionally substitutes a fake, clamped size instead of enforcing the real one.

### Finding Description
Receipt size validation happens once, at creation time, in `validate_action_receipt`/`validate_data_receipt` (`runtime/runtime/src/verifier.rs:742`, `:772`). But a receipt's `output_data_receivers` can be appended to *after* that validation (e.g. via `promise_return`/promise DAG wiring), so the final borsh-serialized size used everywhere downstream — `compute_receipt_size` (`runtime/runtime/src/congestion_control.rs:964`) — can exceed `max_receipt_size` despite passing validation. This is acknowledged directly in code: `ValidateReceiptMode::ExistingReceipt` explains "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed. See https://github.com/near/nearcore/issues/12606" (`runtime/runtime/src/verifier.rs:736-739`).

Rather than fixing the root cause (re-validating size after all mutations, or rejecting the receipt), `try_forward` in the congestion-control/bandwidth path silently **lies about the size**:
```
// There is a bug which allows to create receipts that are above the size limit. Receipts
// above the size limit might not fit under the maximum outgoing size limit. Let's pretend
// that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
if size > max_receipt_size {
    size = max_receipt_size;
}
``` [1](#0-0) 

The same clamp-and-pretend logic is duplicated in bandwidth-request generation: [2](#0-1) 

The actual `size` value used to charge `own_congestion_info.add_receipt_bytes(size)` and `outgoing_metadatas.update_on_receipt_pushed` when buffering, however, is the **unclamped**, real (oversized) size: [3](#0-2) 

So the accounting that decides whether the shard is "congested" uses the true oversized value, while the accounting that decides whether bandwidth/outgoing-limit budget is *consumed* on forward uses the clamped, smaller value — i.e. `forward_limit.size -= size` (`congestion_control.rs:455`) subtracts less than the receipt actually costs to transmit and store. This produces divergence between declared resource cost and actual resource cost, directly parallel to the Liferay bug where a client-declared `maxFileSize` was trusted instead of the real upload size.

A regression test in the repo (`test-loop-tests/src/tests/max_receipt_size.rs:124-208`, `test_max_receipt_size_promise_return`) confirms the mechanism is exploitable today: a contract call creates a promise DAG where `output_data_receivers` is appended after the receipt already sits at `max_receipt_size`, producing a receipt that exceeds the limit; the test comment states plainly "The receipt should be rejected, but currently isn't because of a bug." [4](#0-3) 

### Impact Explanation
This is a resource-accounting bypass reachable from an ordinary contract call (any unprivileged transaction signer/contract deployer can trigger it by deploying+calling a contract that builds a promise DAG with a callback, per the reproduction in the test). The consequence is that the congestion-control/bandwidth-scheduler bookkeeping — which is supposed to bound per-shard memory/bandwidth consumption from outgoing/buffered receipts — undercounts the true byte cost of oversized receipts when they are forwarded, while still counting the true (larger) cost when buffering. This lets an attacker construct receipts that are silently larger than the protocol's `max_receipt_size` invariant while the forwarding/limit-consumption logic treats them as if they were within limit, undermining the size-based DoS protection the limit exists to enforce (CWE-400: uncontrolled resource consumption / CWE-770: allocation without limits). Because congestion/bandwidth accounting feeds directly into consensus-relevant `CongestionInfo` in the chunk header, any divergence in how nodes compute/clamp these sizes is also a state-transition-correctness risk, though the current code path clamps deterministically the same way on every validator (so it is not by itself proven to cause state-root divergence — this would require the same computation to actually differ across implementations, which was not confirmed in the available context).

### Likelihood Explanation
High reachability: the reproduction is a plain `SignedTransaction::call` sequence on a deployed contract building a promise DAG, no special privileges needed, and it's already demonstrated as a passing/expected-behavior regression test in the codebase (`test_max_receipt_size_promise_return`) rather than a hypothetical. The underlying bug is openly tracked as nearcore issue #12606 and is still unresolved in this snapshot — the code contains "pretend" workarounds rather than a fix.

### Recommendation
- Re-validate the final serialized receipt size against `max_receipt_size` after all mutations (including `output_data_receivers` appended via `promise_return`) before the receipt is committed/queued, rejecting receipts that exceed the true limit rather than clamping the value used for downstream accounting.
- Remove or protocol-gate the clamp-to-`max_receipt_size` workarounds in `try_forward` (`congestion_control.rs:413-427`) and `generate_bandwidth_request` (`:556-562`) once root-cause validation is fixed, so that congestion/bandwidth accounting always uses the real receipt size consistently at both buffer-time and forward-time.
- Add an explicit protocol-level bound check at the point where `output_data_receivers`/callback wiring is added post-creation, so no receipt can ever be persisted or forwarded above `max_receipt_size`.

### Proof of Concept
Existing repository test demonstrates the underlying condition end-to-end: [5](#0-4) 
1. Deploy `near_test_contracts::rs_contract()`.
2. Call `max_receipt_size_promise_return_method1` with `args_size` sized so the base receipt for promise `A` lands exactly at `max_receipt_size` (4,194,304 bytes).
3. When promise `A` executes and performs `promise_return`, the runtime rewires the DAG (`C -> then -> B`), appending an `output_data_receivers` entry to `C`'s already-maximal receipt, pushing its true serialized size above `max_receipt_size`.
4. The oversized receipt is not rejected; it flows into `try_forward`/`buffer_receipt`, which clamps the size used for outgoing-limit consumption to `max_receipt_size` while congestion-info byte accounting (`add_receipt_bytes`) uses the real, larger size — confirming the size-enforcement/accounting divergence described above.
