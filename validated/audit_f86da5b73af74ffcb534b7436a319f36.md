### Title
Missing deposit refund on eth-implicit early return in `AddressRegistrar::register` — (`runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
`AddressRegistrar::register` is `#[payable]` but silently consumes any attached deposit when the caller passes an eth-implicit `account_id`, because the early-return path at line 45 issues no refund promise.

### Finding Description
The `register` function accepts deposits (marked `#[payable]`) to cover storage costs for non-eth-implicit accounts. When the `is_eth_implicit` guard fires, the function returns `None` at line 45 without:
1. Reading `env::attached_deposit()`, and
2. Issuing a `promise_batch_action_transfer` refund to `env::predecessor_account_id()`.

The deposit is therefore permanently credited to the contract's balance. The `Entry::Occupied` branch (lines 80–83) correctly issues a refund in its analogous "no storage written" case, confirming the omission in the eth-implicit path is unintentional. [3](#0-2) 

### Impact Explanation
Any caller who attaches a non-zero deposit when calling `register` with an eth-implicit account ID permanently loses that deposit. The funds are credited to the address-registrar contract's balance with no mechanism for recovery. This is a direct, irreversible loss of funds for the caller.

### Likelihood Explanation
The function is `#[payable]`, so the NEAR SDK does not reject deposits at the protocol level. A caller who:
- Programmatically calls `register` without pre-checking the account type, or
- Attaches a deposit expecting the same storage-payment behavior as for named accounts,

will silently lose their funds. The likelihood is moderate given that the function's `#[payable]` annotation implies deposits are always meaningful.

### Recommendation
Before the early return, either:
1. Assert zero deposit: `assert_eq!(env::attached_deposit(), NearToken::from_yoctonear(0), "No deposit allowed for eth-implicit accounts");` — this panics and triggers an automatic deposit refund.
2. Or explicitly refund: read `env::attached_deposit()` and, if non-zero, issue a `promise_batch_action_transfer` back to `env::predecessor_account_id()` before returning `None`.

### Proof of Concept
Call `register` with `account_id = "0x8fd379246834eac74b8419ffda202cf8051f7a03"` and `deposit = 1 NEAR`. The existing test at line 233 of `sanity.rs` already covers this scenario but does **not** assert that the deposit is refunded — it only checks the log message and `None` return value. [4](#0-3) 

A complete proof would add a balance assertion: record the caller's balance before the call, execute the call, then assert `post_balance >= pre_balance - gas_costs`, demonstrating the 1 NEAR deposit is not returned.
