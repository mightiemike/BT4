## Title
Liquidity withdrawal/injection payout is computed from a manipulable spot balance ratio, allowing sandwich extraction from Bancor-style TRC10 Exchange pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The java-tron `ExchangeWithdrawContract`/`ExchangeInjectContract` actuators (the on-chain Bancor-style TRC10 "Exchange" market) compute the amount of the paired token to return/consume using the exchange's *current* `firstTokenBalance`/`secondTokenBalance` ratio at execution time, exactly as the Salty.IO liquidation reward was computed from the *current* WETH/WBTC spot ratio. Because that ratio can be shifted arbitrarily within the same block by preceding `ExchangeTransactionContract` swaps against the very same pool, an actor can sandwich an `ExchangeWithdraw` (or `ExchangeInject`) with swaps to receive a disproportionate share of the pool's value, then reverse the swap - draining real value from the pool that other traders rely on.

### Finding Description
`ExchangeWithdrawActuator.execute`/`doValidate` derives `anotherTokenQuant` purely from the live pool balances: [1](#0-0) 

The same pattern is used for deposits in `ExchangeInjectActuator`: [2](#0-1) 

Both computations use `firstTokenBalance`/`secondTokenBalance` fields read directly from the `ExchangeCapsule` at the moment of execution: [3](#0-2) 

Those balances are exactly what `ExchangeTransactionActuator` mutates on every swap, via the Bancor-formula `ExchangeCapsule.transaction`: [4](#0-3) [5](#0-4) 

Since `ExchangeTransactionContract` (swap) is callable by any account with no cooldown, and `ExchangeWithdrawContract`/`ExchangeInjectContract` are callable by the pool's creator (an unprivileged role obtained simply by having created the exchange via `ExchangeCreateContract`), the same account can:
1. Broadcast (or bundle within one block) a large swap that pushes the reserve ratio far from its "fair" value (e.g., dumping one side toward the dust amount, as described in the report).
2. Immediately call `ExchangeWithdraw` with a quantity of the now-scarce token, so the proportional-ratio math (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`) returns a wildly inflated amount of the now-abundant token.
3. Reverse the initial swap, netting a profit extracted from the pool at the expense of the pool's economic backing (and thus future traders' realized prices).

This is the same root cause as the reported bug: a reward/settlement amount computed from a spot ratio that can be moved atomically by the same caller who then benefits from the settlement, instead of being computed from state fixed independent of the caller's own manipulation.

### Impact Explanation
An attacker (any account, no special permission needed beyond being the creator of a self-created exchange pool, which anyone can create) can extract value disproportionate to their actual pool share, corrupting the token-balance accounting (`firstTokenBalance`/`secondTokenBalance`) of the exchange. This degrades the pool for all other participants who trade against it via `ExchangeTransactionContract`, effectively a form of asset/accounting corruption reachable purely from broadcast transactions.

### Likelihood Explanation
Exploitation requires only ordinary broadcast transactions (`ExchangeTransactionContract` + `ExchangeWithdrawContract`/`ExchangeInjectContract`) from a single unprivileged account that created its own exchange pool, or colludes with the creator; all three steps can be included by the same account, and (subject to normal transaction ordering within a block/validator) can be executed atomically in sequence, making the attack straightforward and non-privileged, mirroring the original sandwich scenario closely.

### Recommendation
- Short term: For `ExchangeWithdraw`/`ExchangeInject`, do not use the pool's live spot balance ratio at execution time to compute the counter-token amount; instead track and use LP-share-style accounting (e.g., a recorded contribution/relay-token share) that is invariant to short-term swap-induced ratio shifts, or bound the allowed deviation of the ratio used from a TWAP/anchored ratio.
- Long term: Formally specify invariants for the Exchange withdraw/inject/transaction actuators (e.g., "withdraw amount must reflect the withdrawer's originally contributed proportion of the pool, not the instantaneous swap-affected ratio") and add tests that simulate a swap-then-withdraw-then-reverse-swap sequence within one block to ensure no net value can be extracted beyond fees.

### Proof of Concept
1. Account A creates an Exchange pool for TokenX/TokenY via `ExchangeCreateContract`, becoming the pool's `creatorAddress` (required by `ExchangeWithdrawActuator.doValidate`, line 181-183 check against `exchangeCapsule.getCreatorAddress()`).
2. Account A broadcasts an `ExchangeTransactionContract` swapping a large amount of TokenX into the pool for TokenY, sharply increasing `firstTokenBalance` and depleting `secondTokenBalance` (per `ExchangeCapsule.transaction`).
3. In the same block, Account A broadcasts `ExchangeWithdrawContract` requesting withdrawal of a small `tokenQuant` of TokenX; because `secondTokenBalance` is now artificially low relative to `firstTokenBalance`, the computed `anotherTokenQuant` in `ExchangeWithdrawActuator` (lines 79-89) is disproportionately small/large depending on direction chosen, letting A extract more value than their true share when reversed.
4. Account A broadcasts a reverse swap (`ExchangeTransactionContract`) to restore the ratio, pocketing the extracted difference and leaving the pool's actual backing degraded for other users.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
