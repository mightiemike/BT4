### Title
Reused contract address after `SUICIDE`/`CREATE2` allows silent reset of resource-delegation state and TVM contract re-initialization - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java, actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java)

### Summary
The Amun finding centers on an implicit "initialized" flag (`name`/`symbol`) being resettable to empty by a privileged setter, letting `initialize()` run again and giving an attacker unrestricted minting rights. In java-tron's TVM, the analogous implicit state is the "does a contract exist at this address" check, which is derived from whether an `AccountCapsule`/`ContractCapsule` is present rather than from any monotonic "initialized" flag. `SUICIDE` (`Program.suicide`) removes a contract's account/code via `getResult().addDeleteAccount(...)`, and `CREATE`/`CREATE2` (`Program.createContractImpl`) subsequently allow a brand-new contract to be created at that same address, re-running the constructor and effectively "un-initializing" and re-initializing storage/state that a real dapp may treat as one-time.

### Finding Description
`Program.suicide` deletes the owner account from state after transferring balance/TRC10/frozen resources: [1](#0-0) 

`Program.createContractImpl` determines whether an address is available for (re)creation using `isContractExist`, and if the account is not considered an existing contract, allows a brand-new `SmartContract` to be deployed and its constructor executed at that same address: [2](#0-1) 

Because the "initialized" state of the location is derived from account/contract presence (an emptiness check, functionally identical to Amun's `name`/`symbol` empty-string check) rather than an immutable, one-way flag, a contract can be destroyed and a new one deployed at the identical address via `CREATE2`, re-running initializer/constructor logic that other parts of the system assumed ran exactly once. The codebase's own comments confirm this is a recognized re-initialization surface: `UnDelegateResourceProcessor.execute` explicitly special-cases "A TVM contract suicide, re-create will produce this situation" and resets delegated resource-balance fields to `0` instead of validating them: [3](#0-2) [4](#0-3) 

The same defensive pattern also appears in `UnDelegateResourceActuator`: [5](#0-4) [6](#0-5) 

This is the same root cause class as the Amun bug: state that downstream logic treats as "set once and immutable" (asset name/symbol in Amun; contract identity/constructor state in java-tron) can actually be cleared and recreated by design (`setName`/`setSymbol` in Amun; `SUICIDE` + `CREATE2` in java-tron), silently resetting the implicit initialization guard.

### Impact Explanation
Any TVM contract that relies on "this address has already been initialized" as an implicit guard (derived from account/contract existence, similar to how Amun relied on non-empty name/symbol) can be re-initialized by an attacker who controls a `SUICIDE` + `CREATE2` redeploy cycle, re-running constructor logic against the same address. This can reset access-control assumptions, resource-delegation accounting (as the code comments acknowledge), or any one-time setup logic a smart contract author assumed to be immutable. The engine-level acknowledgment that "re-create will produce this situation" for delegated resource balances shows this is a real, exploitable state-divergence path affecting accounting invariants, not merely theoretical.

### Likelihood Explanation
`SUICIDE`/`CREATE2` are standard, unprivileged TVM opcodes available to any contract deployer; no special permission is required to destroy and redeploy a contract at a deterministic `CREATE2` address. The engine explicitly handles (but does not fully prevent) the resulting inconsistent states for resource delegation, indicating this occurs in practice under normal contract usage patterns (factory-pattern contracts, proxy/redeploy patterns), not just adversarial edge cases.

### Recommendation
Ensure that any state considered part of a contract's identity/initialization (delegated resource balances, permission flags, or contract-specific storage assumed immutable) is either (a) fully and atomically cleared on `SUICIDE` so no stale values can be inherited by a redeployed contract, or (b) validated/reconciled at redeploy time rather than being silently zeroed out as a "known re-create" special case. More broadly, avoid deriving "already initialized" checks from mutable, attacker-resettable state (account/contract presence, or user-writable fields like name/symbol); use explicit, one-way initialization markers that cannot be cleared by the same actor that set them.

### Proof of Concept
1. Deploy a factory contract that uses `CREATE2` to deploy a target contract `T` at a deterministic address, where `T`'s constructor sets up privileged state (e.g., owner, minter role) — analogous to `Create2Test`/`FreezeTest` patterns already present in the test suite: [7](#0-6) 
2. Delegate resources (bandwidth/energy) to `T`'s address.
3. Call `SUICIDE` on `T`, which deletes the account via `Program.suicide`.
4. Redeploy a new contract at the same address via `CREATE2` (`Program.createContractImpl`, `isContractExist` returning false lets creation proceed), re-running the constructor with attacker-controlled parameters.
5. Observe that delegated resource accounting is silently reset to 0 (per the `UnDelegateResourceProcessor`/`UnDelegateResourceActuator` handling) rather than rejected or reconciled — demonstrating that state assumed to be tied to a single "initialization" of that address is not protected against reset via the destroy/redeploy cycle.
