## Finding: Backup/restore path persists write sets without binding them to the accumulator-proven `state_change_hash`

### Title
Transaction restore accepts write sets that are never hash-bound to the accumulator-proven `TransactionInfo.state_change_hash` - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
The transaction-restore path loads `(Transaction, TransactionInfo, Events, WriteSet)` tuples from a backup chunk file and only submits `txns`, `event_vecs`, and `txn_infos` (wrapped without the `write_sets`) to `TransactionListWithProofV2::verify`, which authenticates them against the accumulator via the ledger info. The `write_sets` vector is loaded and carried forward completely outside of this verification and is later written straight into `WriteSetDb` and fed into `state_store.calculate_state_and_put_updates` for `kv_replay`, without ever checking that `CryptoHash::hash(write_set) == txn_info.state_change_hash()`.

### Finding Description
In `LoadedChunk::load` [1](#0-0) , the code parses each backup record into `(txn, aux_info, txn_info, events, write_set)` and pushes `write_set` into a separate `write_sets` vector. It then builds a verification object explicitly excluding `write_sets`: [2](#0-1) 

Only `txns`, `event_vecs`, and `txn_infos` (via `TransactionInfoListWithProof`) participate in `verify()`. Compare this to the sibling type `TransactionOutputListWithProof::verify`, which explicitly authenticates the write set by hashing it and comparing to `txn_info.state_change_hash()`: [3](#0-2) 

That same invariant is enforced elsewhere too, in `TransactionOutput::ensure_match_transaction_info`: [4](#0-3) 

But the transaction-restore chunk loader never calls anything equivalent for the `write_sets` it read from the backup file. The unverified `write_sets` are then handed straight to `save_transactions`/`save_transactions_impl`, which persists them to `WriteSetDb` and — when `kv_replay` is enabled — uses them to compute and commit the actual state values via `StateUpdateRefs::index_write_sets` and `state_store.calculate_state_and_put_updates`: [5](#0-4) 

`save_transactions_impl` itself performs no cross-check between `write_sets[i]` and `txn_infos[i].state_change_hash()` either — it simply serializes and writes each write set: [6](#0-5) 

So while `txn_info` (and thus its `state_change_hash` field) is proven to be part of the accumulator via `range_proof`/`ledger_info`, nothing proves that the specific `WriteSet` bytes being written to durable storage (or used to derive state during `kv_replay`) are the same bytes whose hash produced that `state_change_hash`.

### Impact Explanation
A node performing a `db-restore` / transaction restore (or `kv_replay`-based state derivation) from a backup source that returns a tampered or corrupted `write_set` byte blob for a given version — while keeping the corresponding `txn`, `events`, and `txn_info` intact/valid — will have that mismatched write set silently:
1. Written into `WriteSetDb`, corrupting durable ledger data returned by later `get_write_set`/backup APIs, and
2. Used to compute and commit the live state tree (`state_store.calculate_state_and_put_updates`) during `kv_replay`, meaning the resulting state values/state root the node serves afterward diverge from the true VM-committed state, while the node still believes its history was authenticated by the accumulator proof.

This directly violates the "restore paths must preserve deterministic proof binding" and "committed state that differs from the correct VM result" invariants called out in the task's proof/storage pivots, and would be a durable, silent divergence rather than a transient error.

### Likelihood Explanation
This requires an untrusted or compromised backup storage backend (or a bug in the backup-writing path) supplying a write-set blob whose content does not match the transaction it accompanies while `txn_info`/`txn`/events remain valid — this is exactly the trust boundary backup/restore proof verification is supposed to close. Given that `TransactionOutputListWithProof::verify` in the same codebase performs the analogous write-set hash check for a similar code path, and this restore path does not, this looks like an actual gap rather than an intentional design decision.

### Recommendation
In `LoadedChunk::load` (or in `save_transactions_impl`), after verifying `txn_list_with_proof`, add an explicit check for every index `i` that `CryptoHash::hash(&write_sets[i]) == txn_infos[i].state_change_hash()`, mirroring `TransactionOutputListWithProof::verify`'s write-set hash check, before the write sets are persisted or used for `kv_replay` state computation.

### Proof of Concept
Not independently runnable in this environment (no filesystem/CLI access), but conceptually:
1. Prepare a valid transaction backup chunk (`transactions` file + `proof` file) for a version range.
2. Modify only the `write_set` field of one record in the `transactions` chunk file to a different (but still well-formed) `WriteSet`, leaving `txn`, `txn_info`, and `events` untouched.
3. Run `db-restore` (or `kv_only_replay`) against this backup.
4. Observe that `LoadedChunk::load`'s `txn_list_with_proof.verify(...)` call succeeds (since it never inspects `write_sets`), and the tampered write set is written to `WriteSetDb` and (if `kv_replay` is enabled) used to compute the committed state — producing a state root that diverges from the one implied by `txn_info.state_change_hash()`, with no verification failure raised.

**Note on completeness:** I was unable to fully read `TransactionListWithProof::verify`'s implementation (ran out of tool iterations) to double-confirm no other code path independently authenticates `write_sets` before/after this point; the strongest evidence is structural — `write_sets` is never included in the object passed to `.verify()`, and `save_transactions_impl` performs no hash check either. If such a check exists elsewhere in the call chain that I did not locate, this finding would not hold.
