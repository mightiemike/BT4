### Title
Broken transaction atomicity in `SetAuthToken` allows API token duplication/loss under concurrent regeneration requests - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`SetAuthToken` opens a transaction via `sqlutil.TransactDataSource` but the DELETE and INSERT statements inside the closure are executed against `oi.ds` (the base, non-transactional data source) instead of the `tx` parameter that is passed into the closure. This makes the "transaction" a no-op wrapper: the two statements run as independent, non-isolated, non-atomic autocommit operations, opening a race window when `SetAuthToken`/`CreateAndSetAuthToken` is invoked concurrently for the same user.

### Finding Description
In `SetAuthToken` [1](#0-0) , the code calls:

```go
err = sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
    if _, err = oi.ds.ExecContext(ctx, "DELETE FROM oidc_user_api_tokens WHERE user_email = $1", user.Email); err != nil { ... }
    _, err = oi.ds.ExecContext(ctx, "INSERT INTO oidc_user_api_tokens (...) VALUES (...)", ...)
    ...
})
```

Both the DELETE and INSERT reference `oi.ds`, not the `tx` argument supplied by `TransactDataSource`. This means the pair of statements never actually execute inside the same DB transaction/connection — each is its own autocommit statement on the underlying pooled connection. Consequently, the intended atomic "rotate token" semantics (delete-old, insert-new as a single unit) do not hold: two concurrent callers of `SetAuthToken` for the same `user.Email` (e.g., two parallel calls to the API-token-regeneration mutation/endpoint reachable via `CreateAndSetAuthToken`, exposed through `core/web/resolver/mutation.go` and `core/web/user_controller.go`) [2](#0-1)  can interleave their DELETE/INSERT pairs. Depending on interleaving and on whether `user_email` has a uniqueness constraint in `oidc_user_api_tokens`, the result can be zero rows (both DELETEs succeed and only one INSERT survives due to a later race) or two rows with different salts/hashed secrets both remaining valid, defeating the "exactly one active token per user" invariant that `FindUserByAPIToken` depends on [3](#0-2) . No SQL-level locking, `SELECT ... FOR UPDATE`, or unique-constraint-based `ON CONFLICT` handling exists to prevent this, and the outer `TransactDataSource` call provides no actual protection since it is never used.

### Impact Explanation
If token duplication occurs, a previously issued token that the user (or an admin) believed was rotated/revoked can remain valid alongside the newly created one, because the DELETE that was supposed to invalidate the old token can be "lost" against a differently-ordered INSERT from a concurrent request. This allows continued authenticated API access using a token that should have been revoked — a token-rotation/session-invalidation bypass. This matches the "broken authentication/session invalidation" class of bounty impact (unauthorized continued access after intended rotation/revocation).

### Likelihood Explanation
Exploitation requires the ability to fire two concurrent requests to the token-creation/regeneration path (`CreateAndSetAuthToken` → `SetAuthToken`) for the same user — reachable by any authenticated user regenerating their own API token twice in short succession, or by an attacker who has already obtained a valid session and races the regeneration endpoint immediately after suspecting compromise/before an admin can revoke it. This is a normal, unauthenticated-timing race (no special privileges beyond the already-established session), and is trivially reproducible with two goroutines issuing near-simultaneous SQL statements, since the closure never actually serializes on `tx`.

### Recommendation
Use the `tx` argument (not `oi.ds`) for both the DELETE and INSERT statements inside the `TransactDataSource` closure so they execute as a single atomic transaction. Additionally, enforce a unique constraint/index on `oidc_user_api_tokens.user_email` (or use `INSERT ... ON CONFLICT (user_email) DO UPDATE`) so that even racing transactions converge to a single row per user rather than relying solely on transaction ordering.

### Proof of Concept
Integration/invariant test against a real Postgres test DB:
1. Create a test user and enable `UserAPITokenEnabled`.
2. Launch two goroutines that both call `oi.SetAuthToken(ctx, &user, auth.NewToken())` concurrently for the same `user.Email`.
3. After both goroutines complete, query `SELECT count(*) FROM oidc_user_api_tokens WHERE user_email = $1`.
4. Assert the count is exactly 1 (expected/desired invariant) — with the current code (using `oi.ds` instead of `tx`), repeated runs will show non-deterministic results (occasionally 0 or 2 rows), demonstrating the race, whereas after the fix (using `tx` plus a unique constraint) the count is deterministically 1 and the retained `token_salt`/`token_hashed_secret` corresponds to the last completed call.

func (oi *oidcAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (clsessions.User, error) {
	if !oi.config.UserAPITokenEnabled() {
		return clsessions.User{}, errors.New("API token is not enabled")
	}

	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc user API token table for given token, user role and email are cached so
		// no further upstream OIDC query is performed, sessions and tokens are synced against the upstream server
		// via the UpstreamSyncInterval config and reaper.go sync implementation
		var foundUserToken struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundUserToken,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_user_api_tokens WHERE token_key = $1",
			apiToken, oi.config.UserAPITokenDuration().Duration(),
		); err != nil {
			return err
		}
		if !foundUserToken.Valid {
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundUserToken.UserEmail,
			Role:  foundUserToken.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			// API Token expired, purge
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
				oi.lggr.Errorf("error purging stale oidc API token session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}

// CreateAndSetAuthToken generates a new credential token with the user role
func (oi *oidcAuthenticator) CreateAndSetAuthToken(ctx context.Context, user *clsessions.User) (*auth.Token, error) {
	newToken := auth.NewToken()
	err := oi.SetAuthToken(ctx, user, newToken)
	if err != nil {
		return nil, err
	}
	return newToken, nil
}
