### Title
Function-call access-key `allowance` cap is never enforced or decremented on the meta-transaction (`DelegateAction`) execution path — (File: `runtime/runtime/src/actions.rs`)

### Summary
`FunctionCallPermission.allowance` is meant to be a hard cap on how much of an account's balance a restricted, non-full-access key can ever cause to be spent on gas/fees (`allowance: Option<Balance>`, "the total amount... allocations for a specific... type" analog to the vesting contract's missing total check). On the ordinary transaction path this cap is enforced by `check_and_compute_new_allowance`/`verify_and_charge_tx_ephemeral`. On the meta-transaction (`Action::Delegate`/`DelegateV2`) execution path, `validate_delegate_action_key` performs nonce, receiver, method-name, and zero-deposit checks but has no equivalent allowance check or decrement, so the "total amount" ceiling the key owner configured is never calculated or enforced when a relayer executes the same key via a signed `DelegateAction`.

### Finding Description
`validate_delegate_action_key` (`runtime/runtime/src/actions.rs:579-728`) is the sole authorization gate applied to a `FunctionCall`-permissioned access key when it signs a `DelegateAction` receipt (a meta-transaction, [near/NEPs #366]). It validates:
- key existence,
- nonce monotonicity/upper bound,
- exactly one `FunctionCall` action with zero deposit,
- `receiver_id` match,
- `method_names` match.

It never inspects `function_call_permission.allowance`, unlike the equivalent ordinary-transaction gate `verify_and_charge_tx_ephemeral` → `check_and_compute_new_allowance` (`runtime/runtime/src/verifier.rs:282-303`, `:365-373`), which subtracts `total_cost` from `allowance` and fails with `NotEnoughAllowance` if it would go negative. Because gas/fees for a delegated action are instead charged from the relayer's own account (the transaction signer that wraps the `DelegateAction`), the restricted key's allowance is simply bypassed: it is neither checked as a cap nor decremented as spend accounting, so the key can be used to make an unbounded number of calls regardless of the allowance the account owner configured. This is explicitly acknowledged in `docs/architecture/how/meta-tx.md:244-266`, which states "For allowance, however, there is no check... even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work."

### Impact Explanation
An account owner (or a service granting restricted access to a third party) creates a `FunctionCall` access key with a small `allowance` specifically to bound the maximum financial exposure of a key that might be compromised, over-shared, or abused (e.g. an app-embedded key, a bot key, a key handed to a partially-trusted script). The owner's threat model relies on the allowance being a hard, protocol-enforced ceiling. Because the cap is never checked on the delegate-action path, anyone controlling that key (attacker with a leaked restricted key, a malicious dApp instructed to relay, or the key holder itself acting in bad faith against an allowance meant to limit blast radius) can route arbitrarily many calls through any willing relayer, invoking the allowed method on the allowed receiver an unbounded number of times, completely defeating the configured spending/usage cap. This breaks an explicit, user-facing security invariant of the access-key model and can enable unauthorized/uncapped invocation of gas-costing contract methods (e.g. repeated `ft_transfer`-like calls, staking actions inside a function, or other value-moving operations gated only by "receiver + method name") beyond what the key owner authorized, even though a `FunctionCall` key deliberately cannot attach a deposit itself — the exposure is unbounded call-count/gas budget circumvention rather than deposit-of-funds circumvention.

### Likelihood Explanation
High. No validator collusion, network manipulation, or special privileges are required: any holder of a restricted `FunctionCall` key (which is explicitly designed to be handed out with reduced trust) can wrap any transaction as a `DelegateAction` and have any relayer (including a self-relay via any full-access key, or a public relayer service) submit it. The relayer's cost coverage is the normal, intended design of meta-transactions; the missing allowance check is unconditional on this path, not a rare configuration.

### Recommendation
Enforce and decrement `FunctionCallPermission.allowance` in `validate_delegate_action_key` (or in the delegate-action's action-execution path that ultimately debits gas from the relayer), mirroring `check_and_compute_new_allowance`'s subtract/underflow-reject semantics from `verifier.rs:282-303`, using an appropriate cost basis for the delegated inner action (e.g. `total_send_fees`/`exec_fee` of the wrapped `FunctionCall`). If the design intent is genuinely "allowance only bounds direct-tx spending, not meta-tx use," this must be a clearly documented, deliberate protocol decision rather than an incidental gap, since it silently defeats the security guarantee users are told the field provides.

### Proof of Concept
1. Alice creates account `alice.near` and adds a `FunctionCall` access key `K` with `allowance: Some(1_yoctoNEAR-equivalent-of-one-call)`, `receiver_id: "app.near"`, `method_names: ["do_thing"]`, intending "this key can call `do_thing` on `app.near` at most once/very few times before running out of allowance."
2. An attacker who obtains `K` (e.g. via a leaked embedded key) builds a `SignedDelegateAction` calling `do_thing` on `app.near`, signed with `K`, and submits it wrapped inside a transaction signed by any relayer account `R` (their own account, or a public relayer) via `Action::Delegate`.
3. `validate_delegate_action_key` (`runtime/runtime/src/actions.rs:579-728`) validates nonce/receiver/method/deposit and succeeds; it never reads or reduces `K`'s `allowance`.
4. The attacker repeats step 2 with incrementing nonces indefinitely (each time via a relayer, who pays gas from their own account). Every call succeeds regardless of `K.allowance`, which is never observed to be exhausted — directly contradicting `test_access_key_smart_contract`'s expectation (`integration-tests/src/tests/standard_cases/mod.rs:1335-1405`) that the same key used directly would be capped and eventually rejected with `NotEnoughAllowance`.

```rust
fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
```

```markdown
## Function access keys in meta transactions

Assume alice sends a meta transaction and signs with a function access key.
How exactly are permissions applied in this case?

Function access keys can limit the allowance, the receiving contract, and the
contract methods. The allowance limitation acts slightly strange with meta
transactions.

But first, both the methods and the receiver will be checked as expected. That
is, when the delegate action is unwrapped on Alice's shard, the access key is
loaded from the DB and compared to the function call. If the receiver or method
is not allowed, the function call action fails.

For allowance, however, there is no check. All costs have been covered by the
relayer. Hence, even if the allowance of the key is insufficient to make the call
directly, indirectly through meta transaction it will still work.

This behavior is in the spirit of allowance limiting how much financial
resources the user can use from a given account. But if someone were to limit a
function access key to one trivial action by setting a very small allowance,
that is circumventable by going through a relayer. An interesting twist that
comes with the addition of meta transactions.
```
