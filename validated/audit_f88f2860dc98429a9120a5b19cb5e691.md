### Title
Non-atomic update of `ForkTracker`'s independent atomics allows pool validation to observe an inconsistent fork state, diverging from actual chain-spec validity - (File: crates/transaction-pool/src/validate/eth.rs)

### Summary
This is the closest in-scope analog to the "parameter updates not propagated" class of bug. `EthTransactionValidator` caches hardfork-derived parameters in a `ForkTracker` struct that is later read by `ensure_intrinsic_gas` and other validation paths, but the individual fields of that cache are updated independently (as separate atomics), rather than as one consistent snapshot derived from the chain spec, the same root cause as the C4 report where multiple related parameters live in separate storage slots and can go out of sync with each other and with the source of truth.

### Finding Description
`ForkTracker` holds a set of independently-stored atomics that are all supposed to reflect the *same* head/timestamp's fork configuration: `shanghai`, `cancun`, `prague`, `osaka`, `amsterdam`, `tip_timestamp`, `max_blob_count`, `max_initcode_size`, and `tx_gas_limit_cap`. [1](#0-0) 

These fields are written via separate `.store()` calls (5 distinct store sites found in `on_new_head_block`), meaning there is a window where one flag (e.g. `tip_timestamp` or `cancun`) has been advanced to reflect the new head while a related flag (e.g. `max_blob_count`, `tx_gas_limit_cap`) still holds the value for the previous fork/head. Any concurrent call to `validate_stateless`/`validate_stateful` (which run on separate validation task(s) per `TransactionValidationTaskExecutor`) reading `fork_tracker` during this window observes a torn, self-inconsistent combination of parameters that never actually existed as a single `ChainSpec` state.

`ensure_intrinsic_gas` directly branches on this torn state to pick a `SpecId` and EIP-2780 behavior: [2](#0-1) 

Because the "current chain spec" the pool believes is active can differ from the chain spec actually enforced by block execution/validation for the same head, the pool's accept/reject decision (intrinsic gas floor, blob count cap, initcode size cap, gas limit cap) can diverge from what the execution layer would actually enforce for a block built on that head, exactly the "propagation gap between config source and dependent components" pattern in the reported finding, just realized here as a torn-read/ordering race between fork-parameter fields rather than a single un-propagated `Uber Owner` setter.

### Impact Explanation
This maps to the explicitly allowed impact "pool admission diverging from block validity." If the pool's `ForkTracker` briefly reflects a mixed pre/post-fork parameter set, it can either:
- Reject a transaction that would actually be valid under the block-execution chain spec for the same head (e.g., rejecting on `IntrinsicGasTooLow` using a stale/newer `SpecId` mismatched with the actual blob/initcode/gas-limit caps), or
- Accept a transaction into the pool that violates the currently-enforced hardfork rules (e.g., allowing a blob count / initcode size that the newly active fork's real `max_blob_count`/`max_initcode_size` should reject).

This is a correctness/consistency bug in the pool's admission logic relative to the authoritative chain spec, not merely a performance or caching-freshness inconvenience.

### Likelihood Explanation
The likelihood is moderate and depends on timing: it requires a transaction to be validated concurrently with (or in the narrow window during) an `on_new_head_block` update that straddles a hardfork activation boundary, since only around fork transitions do the tracked booleans/values actually change. Given hardfork transitions are rare, discrete events (block-timestamp-based), the exposure window is narrow, but it is deterministic given the right timing rather than requiring any malicious actor. I was not able to fully inspect the body of `on_new_head_block` (iteration budget exhausted before reading it directly), so I cannot confirm whether the five `.store()` calls are ordered/guarded in a way that prevents readers from ever observing a genuinely inconsistent combination, or whether they are effectively harmless because each flag is independently gated by its own hardfork's activation and only becomes relevant in isolation.

### Recommendation
Replace the per-field atomics in `ForkTracker` with a single atomically-swapped snapshot (e.g., `ArcSwap<ForkTrackerSnapshot>` or a struct behind a `RwLock`) so that all fork-derived parameters for a given head are updated and read as one consistent unit, eliminating any possibility of validation logic observing a mixed pre/post-fork parameter set.

### Proof of Concept
Not independently reproducible from static analysis alone: it requires (1) locating the exact `on_new_head_block` update site in `crates/transaction-pool/src/validate/eth.rs` (found via `grep_search` but not read in full due to iteration limits), and (2) constructing a timing test where a transaction is submitted to `validate_stateless`/`validate_stateful` precisely as the pool crosses a hardfork boundary, then confirming its accept/reject outcome differs from what `evm`/block-execution's `ChainSpec` would compute for the resulting block. This should be verified with direct file access (e.g., a Devin session) since the index did not surface the full `on_new_head_block` function body needed to confirm exact ordering/atomicity guarantees.

pub fn ensure_intrinsic_gas<T: EthPoolTransaction>(
    transaction: &T,
    fork_tracker: &ForkTracker,
) -> Result<(), InvalidPoolTransactionError> {
    use revm::primitives::hardfork::SpecId;
    let spec_id = if fork_tracker.is_amsterdam_activated() {
        SpecId::AMSTERDAM
    } else if fork_tracker.is_prague_activated() {
        SpecId::PRAGUE
    } else if fork_tracker.is_shanghai_activated() {
        SpecId::SHANGHAI
    } else {
        SpecId::MERGE
    };

    // EIP-2780 replaces the flat intrinsic base cost with a decomposed one that depends on
    // `tx.to` and `tx.value`.
    let eip2780 = fork_tracker.is_amsterdam_activated().then(|| {
        revm::context_interface::cfg::gas_params::Eip2780TxInfo {
            value: transaction.value(),
            // Self-transfer: a `Call` whose recipient is the sender itself.
            is_self_transfer: transaction.kind().to() == Some(&transaction.sender()),
        }
    });
