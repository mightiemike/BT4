### Title
Non-hardened branch of ExchangeCapsule.transaction stores negative pool balances unchecked - (chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeCapsule.transaction` computes `newFirstTokenBalance`/`newSecondTokenBalance` from the bancor-style curve in `ExchangeProcessor`, but only validates `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` when `hardenedCalc` is `true`. When `hardenedCalc` is `false` (the default state, controlled by the `allowHardenExchangeCalculation` dynamic property), any negative result computed by the legacy floating-point processor is written directly into on-chain state with no bound check.

### Finding Description
`ExchangeCapsule.transaction` selects between `SafeExchangeProcessor` (hardened) and legacy `ExchangeProcessor` based on `hardenedCalc`, computes `buyTokenQuant` via `processor.exchange(...)`, and derives new balances: [1](#0-0) 

The negativity guard is gated exclusively on `hardenedCalc`: [2](#0-1) 

`hardenedCalc` is passed in from `ExchangeTransactionActuator.execute`/`doValidate` as `allowHarden()`, which reads `dynamicStore.allowHardenExchangeCalculation()` — a chain parameter that is off by default and only becomes `true` via an SR governance proposal: [3](#0-2) [4](#0-3) 

The legacy `ExchangeProcessor.exchange` uses `Math.pow`-based double arithmetic (bancor-style relay-token curve) to compute `buyTokenQuant`: [5](#0-4) 

While this curve is designed to asymptotically approach but not exceed `buyTokenBalance`, it relies on floating-point `Math.pow`/`double` arithmetic with no bound enforcement. The fact that the hardened branch explicitly re-checks `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` after already using overflow-checked arithmetic (`StrictMathWrapper.addExact/subtractExact`, which alone would only catch `long` overflow, not a `buyTokenQuant` that legitimately exceeds the token balance) demonstrates that the underlying computation can produce a `buyTokenQuant` greater than the available `buyTokenBalance` under certain input ratios — this is precisely the scenario the hardened-branch check exists to catch. In the non-hardened path this same scenario is never checked and the negative balance is persisted via `Commons.putExchangeCapsule` in `ExchangeTransactionActuator.execute`: [6](#0-5) 

`doValidate()` also does not independently bound-check `anotherTokenQuant` against the actual pool balance — it only checks against the caller-supplied `tokenExpected` minimum: [7](#0-6) 

### Impact Explanation
An attacker executing a single `ExchangeTransactionContract` against a thin/low-liquidity pair, while the network has not enabled `allowHardenExchangeCalculation` (the default state), can drive the opposing token balance negative in on-chain state. Because `Exchange.firstTokenBalance`/`secondTokenBalance` are protobuf `int64` fields with no unsigned semantics enforced elsewhere, a negative stored balance permanently corrupts pool accounting and subsequent trades computed against it will produce nonsensical results (potentially free/duplicated tokens for later traders, or a permanently frozen/unusable pair since `validate()` rejects trades when a balance is `== 0` but not when negative).

### Likelihood Explanation
Requires only an unprivileged account issuing a normal `ExchangeTransactionContract`, a low-liquidity `Exchange` pair (attacker-creatable or naturally occurring), and the network default of `allowHardenExchangeCalculation() == false`. No special privileges are needed; feasibility of triggering an actual negative result depends on finding sell-quantity/balance ratios that push the `double`-precision bancor curve output past the pool's real balance, which is exactly the condition the hardened-branch check was added to guard against.

### Recommendation
Move the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check outside the `hardenedCalc` conditional so it applies unconditionally in `ExchangeCapsule.transaction`, rejecting the transaction with `ContractValidateException` regardless of the `allowHardenExchangeCalculation` setting.

```java
@Test
public void testLegacyTransactionCanUnderflowSecondBalance() throws Exception {
  ExchangeCapsule capsule = new ExchangeCapsule(
      ByteString.copyFromUtf8("owner"), 200L, 0L,
      "abc".getBytes(), "def".getBytes());
  // Thin liquidity pool
  capsule.setBalance(1_000_000_000_000L, 100L);

  // Large sell quantity against thin buy-side balance, hardenedCalc=false (legacy path)
  long buyQuant = capsule.transaction("abc".getBytes(), Long.MAX_VALUE / 2, true, false);

  // Expected (post-fix) behavior: should throw ContractValidateException or clamp at 0
  // Actual (current) behavior: no exception, and balance can go negative
  Assert.assertTrue("secondTokenBalance must never go negative",
      capsule.getSecondTokenBalance() >= 0);
}
```
Run against the current (unpatched) code to observe that no exception is thrown and `getSecondTokenBalance()` can be negative, whereas the equivalent hardened-mode call (`hardenedCalc=true`) with the same inputs throws `ContractValidateException("Exchange balance must be >=0 after transaction")`.

```java
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }
```

```java
  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
```
