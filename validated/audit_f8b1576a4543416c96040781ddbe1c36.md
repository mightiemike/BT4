## Title
CREATE2 (`createContract2`) fails to enforce the maximum call-stack depth limit when TVM feature flags are disabled, permitting unbounded call recursion - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.createContract2` (the TVM handler for the `CREATE2` opcode) enforces the `MAX_DEPTH` (64) call-stack limit only when `VMConfig.allowTvmCompatibleEvm()` or `VMConfig.allowTvmOsaka()` is enabled. When neither flag is active, the code falls back to `MUtil.checkCPUTimeForCreate2()`, which itself only throws once a specific hard fork (`VERSION_4_8_1_1`) has activated on the network. If that hard fork has not yet activated, the depth check silently no-ops and execution proceeds into `createContractImpl`, incrementing the recursion depth past `MAX_DEPTH`. Because every depth check in this class (for `CALL`, `CREATE`, `CREATE2`, precompiled calls) uses strict equality (`getCallDeep() == MAX_DEPTH`) rather than `>=`, once depth passes 64 the check can never fire again for the remainder of that call chain, letting `CREATE2` recursion continue unbounded.

### Finding Description
Compare the unconditional depth guard in `CREATE` (`createContract`): [1](#0-0) 

against the conditional guard in `CREATE2` (`createContract2`): [2](#0-1) 

The `stackPushZero(); return;` short-circuit that stops recursion only executes `if ((VMConfig.allowTvmCompatibleEvm() || VMConfig.allowTvmOsaka()) && getCallDeep() == MAX_DEPTH)`. If both flags are `false`, the code instead calls `MUtil.checkCPUTimeForCreate2()`: [3](#0-2) 

This method is a no-op unless `ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_8_1_1)` is true. On any java-tron-derived network (private chain, sidechain, or testnet built from this codebase) where that specific hard fork has not been activated, or during any window prior to its activation, `checkCPUTimeForCreate2()` does nothing, and control falls through to `createContractImpl(...)`, which increments the internal call depth and recurses.

Because the guard condition is a strict equality check (`getCallDeep() == MAX_DEPTH`), once the depth counter passes 64 on the very first miss, it will never equal `MAX_DEPTH` again for the rest of that execution — the check becomes permanently ineffective for that call chain. A contract using recursive `CREATE2` calls can therefore drive the TVM's internal (Java-level) recursion depth arbitrarily high, limited only by available energy, rather than being capped at 64 as intended for `CALL`/`CREATE`.

The regression test `testCreate2MaxDepthWithNeitherFlag` in `OperationsTest.java` confirms this exact behavior: with both flags disabled, `createContract2` proceeds past `MAX_DEPTH`, records an internal transaction, and pushes a nonzero address instead of stopping: [4](#0-3) 

### Impact Explanation
Unbounded `CREATE2` recursion drives deep, nested recursive Java method calls inside `Program`/`VMActuator` execution (each nested call constructs a new `Program`/`ProgramInvoke` and recurses through the interpreter). Beyond the intended 64-level cap, this can exhaust the JVM thread stack and trigger a `StackOverflowError` during block/transaction processing. Because all consensus-participating nodes execute the same transaction while validating/replaying a block, this is a determinism/availability risk affecting the entire network processing that block (potential node crash or divergent handling of the uncaught error), i.e., a DoS vector reachable via an ordinary broadcast contract-call transaction.

### Likelihood Explanation
Exploitability depends on the hard fork/feature-flag state of the deployed network: on TRON mainnet today, `VERSION_4_8_1_1` and the `allowTvmCompatibleEvm`/`allowTvmOsaka` flags are expected to be active, in which case the fallback `checkCPUTimeForCreate2()` catches the first depth-64 hit and the bug is masked. However, java-tron is a general-purpose codebase deployed by many independent networks; any network that has not yet activated `VERSION_4_8_1_1` (fresh chains, private/sidechain deployments, or during the gap before that specific fork height is reached) is directly exposed to unbounded `CREATE2` recursion from any unprivileged, broadcast smart-contract call — no special privileges are required, only a small deployed contract that recursively self-creates via `CREATE2`.

### Recommendation
Make the `MAX_DEPTH` enforcement in `createContract2` unconditional and independent of `allowTvmCompatibleEvm`/`allowTvmOsaka`/fork-activation state, mirroring the guard already used in `createContract`/`callToAddress`/`callToPrecompiledAddress`. Additionally, replace strict-equality depth checks (`getCallDeep() == MAX_DEPTH`) with `getCallDeep() >= MAX_DEPTH` throughout `Program.java` so the guard remains effective even if depth is somehow incremented past the checkpoint, removing the fork-gating hazard entirely.

### Proof of Concept
1. Deploy a contract whose fallback/function recursively invokes itself via `CREATE2` (each iteration deploying a new instance and immediately calling back into the deployer), similar to the pattern in `ChargeTest.testCallDepth` but using the `CREATE2` opcode path (`Program.createContract2`).
2. On a java-tron network where `VERSION_4_8_1_1` has not activated and `allowTvmCompatibleEvm`/`allowTvmOsaka` are disabled (the default/older configuration, as exercised by `OperationsTest.testCreate2MaxDepthWithNeitherFlag`), broadcast a transaction invoking this contract with a large enough energy/fee limit.
3. Observe that `getCallDeep() == MAX_DEPTH` in `createContract2` fires at most once (or not at all if the timing doesn't align), after which recursion continues unchecked, eventually exhausting the Java call stack during transaction execution across all nodes processing the block.
