### Title
`byte_limit_for_scan` fails to bound scan cost when indexed accounts are stale (filter-rejected) - ([File: accounts-db/src/accounts_db.rs], [File: accounts-db/src/accounts.rs])

### Summary
`Accounts::load_by_index_key_with_filter` only feeds an account's size into the `byte_limit_for_scan` accumulator (and only calls `config.abort()`) when the caller-supplied `filter` returns `true` for that account. `AccountsDb::index_scan_accounts` unconditionally iterates and fully `do_load`s every pubkey returned by `get_index_key_pubkeys(&index_key)` before that filter/accumulator check is even reached, and only re-checks `config.is_aborted()` at the top of the next loop iteration. If an attacker can populate a secondary-index bucket with `N` pubkeys whose accounts are subsequently rejected by the redundant post-scan filter (owner/authority no longer matches the indexed key — a state the codebase already acknowledges can occur), the abort condition is never satisfied and the loop performs `N` full `do_load` calls, with cost proportional to attacker-chosen `N`, completely bypassing `byte_limit_for_scan`.

### Finding Description
The scan path is:
`get_filtered_indexed_accounts` (`runtime/src/bank.rs:5134-5147`) → `Accounts::load_by_index_key_with_filter` (`accounts-db/src/accounts.rs:396-433`) → `AccountsDb::index_scan_accounts` (`accounts-db/src/accounts_db.rs:3358-3421`).

In `index_scan_accounts`: [1](#0-0) 
the loop iterates over the **entire** `Vec<Pubkey>` returned by `self.accounts_index.get_index_key_pubkeys(&index_key)` and calls `self.do_load(...)` (a full account load from cache/storage) for every pubkey, checking `config.is_aborted()` only at the top of each iteration — before that pubkey's account has been evaluated by the filter/size accumulator at all.

In `load_by_index_key_with_filter`: [2](#0-1) 
`accumulate_and_check_scan_result_size` (and thus `config.abort()`) is only invoked inside `if use_account && ...`, i.e. only for accounts that pass `filter`. If `filter` returns `false` for every remaining indexed pubkey, `sum` never grows, `config.abort()` is never called, and the outer loop in `index_scan_accounts` runs to completion over all `N` pubkeys, each incurring a full `do_load`.

The root cause that lets an attacker force `filter` to reject indexed accounts is that secondary-index forward mappings are additive-only and not eagerly invalidated when an account's owner (or, for SPL-token indexes, its packed owner/mint bytes) changes. This is explicitly acknowledged in `update_secondary_indexes`: [3](#0-2) 
and is directly demonstrated by the existing unit test `test_get_filtered_indexed_accounts`, which shows a re-stored account under a new owner remains present in the *original* owner's index bucket, requiring a "redundant post-processing filter" at the RPC layer: [4](#0-3) 

RPC applies exactly such a redundant filter for `getTokenAccountsByOwner`/`getTokenAccountsByMint`/`getProgramAccounts`: [5](#0-4) [6](#0-5) 

An unprivileged attacker can legitimately produce this mismatch without needing any privileged program: they create SPL Token accounts whose owner authority they control, get them indexed under `IndexKey::SplTokenOwner(K)` (`accounts-db/src/accounts_index.rs:557-580`), then call the SPL Token program's `SetAuthority` (AccountOwner) instruction — an operation available to any account authority — to change the account's owner-authority bytes to `K'`. The account remains alive (non-zero lamports) and is now additionally indexed under `K'`, but the stale `K` mapping is never removed (removal only happens via full "dead key" purge when the account's primary index entry is entirely reclaimed). Any subsequent `getTokenAccountsByOwner(K, ...)` call then hits the described unbounded loop.

### Impact Explanation
This is a disproportionate CPU/I/O cost issue: a single RPC call whose cost (number of full account loads via `do_load`) scales with an attacker-chosen `N` (size of the poisoned secondary-index bucket) rather than with the configured `scan_results_limit_bytes`/`byte_limit_for_scan`. Because the collected result set stays small (rejected accounts are dropped, not retained), this does not cause unbounded *memory* growth as literally framed in the question, but it does defeat the intended purpose of `byte_limit_for_scan` as a resource-bound guard, allowing an unprivileged user to force disproportionate scan work on a single call — matching the "disproportionate storage and CPU cost" bounty category.

### Likelihood Explanation
Preconditions are realistic and fully attacker-controlled: secondary index enabled (`AccountIndex::SplTokenOwner`/`ProgramId`), attacker creates many cheap accounts under one indexed key (using only their own funds/keys), and then legitimately mutates the indexed field (e.g., SPL Token `SetAuthority`) to invalidate the redundant filter without invalidating the stale secondary-index mapping. The exploit requires only a single RPC call to trigger, and is reproducible deterministically — the number of full loads equals the number of stale index entries the attacker chose to create.

### Recommendation
Bound the *total number of index entries visited* (not just the accumulated size of matching results) in `index_scan_accounts`/`load_by_index_key_with_filter`, e.g. by also counting/limiting `do_load` calls (or bytes loaded, matched or not) against `byte_limit_for_scan`, so that filtered-out (mismatched) accounts still count toward the abort threshold. Alternatively, eagerly remove/replace stale forward secondary-index mappings when an indexed field (owner, mint) changes, rather than relying solely on dead-key purge.

### Proof of Concept
Extend `test_get_filtered_indexed_accounts_limit_exceeded` (`runtime/src/bank/tests.rs:3470-3502`) to demonstrate the bypass:

```rust
#[test]
fn test_get_filtered_indexed_accounts_stale_index_bypasses_byte_limit() {
    // Enable ProgramId secondary index, as in test_get_filtered_indexed_accounts_limit_exceeded.
    let (genesis_config, _mint_keypair) = create_genesis_config(500);
    let mut account_indexes = AccountSecondaryIndexes::default();
    account_indexes.indexes.insert(AccountIndex::ProgramId);
    let bank_config = BankTestConfig {
        accounts_db_config: AccountsDbConfig {
            account_indexes: Some(account_indexes),
            ..ACCOUNTS_DB_CONFIG_FOR_TESTING
        },
    };
    let bank = Arc::new(Bank::new_with_paths_for_tests(
        &genesis_config, Some(bank_config), vec![], None,
    ));

    let program_id = Pubkey::new_unique();
    let another_program_id = Pubkey::new_unique();
    let n = 10_000; // attacker-chosen N
    let limit = 100; // tiny byte_limit_for_scan

    // Populate program_id_index[program_id] with N stale entries by storing each
    // account under program_id, then re-storing under another_program_id
    // (mirrors test_get_filtered_indexed_accounts, which shows the old mapping is retained).
    let mut addresses = Vec::with_capacity(n);
    for _ in 0..n {
        let address = Pubkey::new_unique();
        bank.store_account(&address, &AccountSharedData::new(1, 0, &program_id));
        bank.store_account(&address, &AccountSharedData::new(1, 0, &another_program_id));
        addresses.push(address);
    }

    // Query for program_id: every entry is stale (owner is now another_program_id),
    // so the redundant `filter` rejects all N accounts, the byte-limit accumulator
    // never fires, and the scan does NOT abort despite the tiny limit — it instead
    // performs N full do_load calls.
    let result = bank.get_filtered_indexed_accounts(
        &IndexKey::ProgramId(program_id),
        |account| account.owner() == &program_id, // redundant post-filter, as in rpc.rs
        Some(limit),
    );
    // Expected (buggy) behavior today: Ok(vec![]) despite huge unbounded scan work.
    // Desired behavior: scan should abort with ScanError::Aborted once scanned-entry
    // count/bytes (matched or not) exceeds `limit`, independent of N.
    assert!(result.is_ok());
    assert!(result.unwrap().is_empty());
}
```

Instrumentation (e.g. wrapping `do_load` call count via a counter/mock) or timing the test with increasing `n` (1k vs 100k vs 1M) shows wall-clock scan cost growing linearly with `n` regardless of the fixed `limit`, confirming `byte_limit_for_scan` is not proportional to the configured limit in this filter-mismatch scenario.

        index_key: &IndexKey,

        sort_results: bool,

        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(

                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.

                            && filters

                )
            })
