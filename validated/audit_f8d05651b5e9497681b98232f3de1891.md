## Finding: `TransactionOutput::ensure_match_transaction_info` skips the state-checkpoint hash, letting chunk-replay verification accept a wrong state root

### Title
Replay/backup verification (`ChunkExecutorInner::verify_execution`) can succeed even when the locally recomputed JMT state-checkpoint root diverges from the authenticated `TransactionInfo` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the single comparator used by chunk-replay/backup-verification code paths to confirm that locally re-executed transactions match an already-authenticated (proof-bound) `TransactionInfo`, deliberately skips comparing the `state_checkpoint_hash` (and `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) fields. Since this is the only check performed after re-execution in `execution/executor/src/chunk_executor/mod.rs::verify_execution` (used for `replay-verify`/backup restore validation) and `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, a chunk whose locally-recomputed state root differs from the validator-signed accumulator commitment will still be reported as "verified" successfully.

### Finding Description
`TransactionInfo` is the object committed into the transaction accumulator and whose hash is bound by validator signatures via `LedgerInfo` [1](#0-0) . It carries `state_checkpoint_hash` (the JMT/state root produced by a transaction) as one of its authenticated fields, alongside `write_set` hash, `event_root_hash`, `gas_used`, and `status`.

When replay/verification code re-executes transactions from an untrusted chunk (backup archive, state-sync chunk) and wants to confirm the re-execution reproduces the authenticated ledger state, it calls `TransactionOutput::ensure_match_transaction_info`: [2](#0-1) 

This function checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash — but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as admitted by the inline TODO: [3](#0-2) 

This comparator is the sole post-re-execution check in the chunk-executor replay-verification path: [4](#0-3) 

and in the `db-tool` archive-replay tool: [5](#0-4) 

Neither path threads the authenticated `state_checkpoint_hash` values from `transaction_infos` into `DoGetExecutionOutput`/`DoStateCheckpoint` as "known" checkpoints to be cross-checked against the locally computed JMT root — that cross-check only happens in `DoStateCheckpoint::get_state_checkpoint_hashes` when `known_state_checkpoints` is `Some(..)`, which is not how the chunk-executor's `verify_execution` invokes execution (it calls `DoGetExecutionOutput::by_transaction_execution` without threading `transaction_infos` in as known checkpoints) [6](#0-5) . Consequently the write-set/event equality check is the *only* signal used to accept a chunk as verified, and it silently ignores whether the locally derived state root actually matches the one bound into the accumulator/`LedgerInfo`.

### Impact Explanation
If a transaction produces a write set that hashes correctly (unchanged since the pre-update behavior) but whose *effect on the state tree*, once folded into a checkpoint, yields a different Merkle root than what validators signed — for example due to a state-tree construction bug, a hot-state/position-state accounting divergence, or any non-deterministic/incorrectly-replayed state-materialization step — `verify_execution`/`replay_on_archive` will report success and the chunk executor will commit its own (wrong) locally computed state root as the ledger's durable state, rather than detecting the divergence. This breaks the guarantee that "committed state that differs from the correct VM result... corrupts durable ledger data" is caught before being persisted, undermining the trust model of replay-verify and archive-based restore/consistency checks: they exist specifically to catch state-root divergence, and this exact class of divergence is the one they fail to catch.

### Likelihood Explanation
This requires a state-materialization/state-checkpoint bug (hot-state or position-state related, or a JMT construction bug) to actually produce a diverging root while write sets/events still hash identically — this is plausible because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are derived by hashing the *resulting node structure*, not merely the write set, so bugs in checkpoint construction (as hinted by the neighboring `HOT_STATE_ROOT_IN_TXN_INFO` / `position_state_checkpoint_hash` feature work referenced in `do_ledger_update.rs`) are a distinct failure surface from write-set hashing. Given that the codebase's own comment explicitly flags this gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), the underlying feature is apparently still under active development, making an undetected divergence plausible during that rollout.

### Recommendation
In `TransactionOutput::ensure_match_transaction_info`, also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when the fields are populated) against locally-computed equivalents (or otherwise thread `transaction_infos`' checkpoint hashes into `DoStateCheckpoint` as `known_state_checkpoints` in the chunk-executor and `replay_on_archive` verification paths) so that any divergence between locally re-executed state roots and the authenticated, validator-signed roots causes `verify_execution`/`replay_on_archive` to fail rather than silently succeed.

### Proof of Concept
Not independently reproducible from static analysis alone — the missing checks are unconditional and directly visible in the diffed code ( [7](#0-6) ). Exploiting it in practice requires a scenario where the local checkpoint-hash computation genuinely diverges from the authenticated one while the write set/events hash identically; I could not find/verify such a triggering scenario within this repository snapshot (the checkpoint-hash divergence itself would stem from a separate, currently-gated feature: `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state/position-state root computation, whose full logic I was not able to fully trace within available iterations). This limits the finding to a proven **missing-invariant / broken verification gate**, not a fully demonstrated end-to-end state-corruption exploit.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
