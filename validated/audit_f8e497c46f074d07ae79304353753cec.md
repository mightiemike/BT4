This confirms the finding: the pre-check that gates whether a slot is *eligible* for shrinking (`is_candidate_for_shrink`/`is_shrinking_productive`, and `select_candidates_by_total_usage`) is computed only from `alive_bytes_after_shrink()`, while the actual downstream decision made inside `shrink_storage()` (`should_not_shrink`) is computed from `total_rewrite_bytes = alive_total_bytes + tombstones_total_bytes` — a strictly larger quantity whenever tombstones exist. This is structurally the same defect class as the referenced Golom finding: an eligibility pre-check uses a different (looser) formula than the actual operation's real computation, so the pre-check can pass (declare a slot "worth shrinking") in cases where the real, more complete computation shows shrinking would not actually save space, wasting the shrink pipeline's I/O/CPU, or can otherwise diverge from the real decision.

### Title
Shrink eligibility pre-check omits tombstone bytes, diverging from the real shrink-worthiness computation - (File: `accounts-db/src/accounts_db.rs`)

### Summary
`AccountsDb::is_candidate_for_shrink`, `AccountsDb::is_shrinking_productive`, and `AccountsDb::select_candidates_by_total_usage` all gate/prioritize shrink work using `alive_bytes_after_shrink(store)` compared against `store.written_bytes()`. But the actual shrink operation, `shrink_storage`, computes worthiness using `total_rewrite_bytes = shrink_collect.alive_total_bytes + shrink_collect.tombstones_total_bytes` against `shrink_collect.written_bytes`, a strictly larger numerator whenever the storage carries forward zero-lamport tombstones. The two checks are not the same formula, so a slot's shrink pre-check pass/fail can be wrong relative to what shrinking will actually accomplish.

### Finding Description
`is_candidate_for_shrink` [1](#0-0)  and `is_shrinking_productive`/`should_not_shrink` [2](#0-1)  both use `alive_bytes_after_shrink`, which returns either `store.alive_bytes_exclude_zero_lamport_single_ref_accounts()` or `store.alive_bytes()` depending on the latest full snapshot slot gating [3](#0-2) . These functions are used both as the initial candidacy filter (in `remove_dead_accounts`, `shrink_slot_forced`) and as the sorting/selection heuristic in `select_candidates_by_total_usage` [4](#0-3) .

However, when the actual shrink runs in `shrink_storage`, the real quantity that determines whether the rewrite reduces size is `total_rewrite_bytes`, which additionally includes `tombstones_total_bytes` — the bytes of zero-lamport, single-ref accounts that must be carried forward as tombstones (because the full snapshot has not yet advanced past their slot) rather than dropped: [5](#0-4) . `tombstones_total_bytes` is populated separately in `shrink_collect` from `tombstones_to_carry_forward`, which is disjoint from what `alive_bytes_after_shrink`/`alive_total_bytes` count [6](#0-5) , [7](#0-6) .

Because the pre-check formula (`alive_bytes_after_shrink` vs `written_bytes`) omits `tombstones_total_bytes` while the actual shrink-worthiness formula (`should_not_shrink` in `shrink_storage`) includes it, a storage can be selected as a shrink candidate by the pre-check (alive bytes alone are less than written bytes) yet fail the real check once tombstone bytes are added in — `total_rewrite_bytes >= written_bytes`. The code even documents this exact mismatch scenario with a runtime warning: "Unexpected shrink for slot {} alive {} written {}, likely caused by a bug for calculating alive bytes." [8](#0-7) . The same asymmetric formula (`alive_bytes_after_shrink`) is also used to compute `alive_bytes_after_shrink` inputs for `AncientSlotInfos::add`/`calc_ancient_slot_info` in the ancient-append-vec packing path [9](#0-8) , [10](#0-9) , propagating the same mismatch into ancient-slot shrink/combine decisions.

### Impact Explanation
This is a "pre-check does not match the real computation" defect analogous to the referenced report: cheap eligibility checks (`is_candidate_for_shrink`, `select_candidates_by_total_usage`, `AncientSlotInfos::add`) systematically under-count the bytes that will actually need to be rewritten whenever tombstones are present, causing candidates to be selected for the expensive `shrink_collect`/rewrite pipeline that then discovers — after doing the full scan/index-lookup/collect work — that shrinking is not actually beneficial and bails out via `should_not_shrink`. This wastes CPU and I/O (disproportionate cost) on slots that a correct pre-check would have skipped, and it can also misallocate priority in `select_candidates_by_total_usage`'s sorting (which decides which of several candidates to process this round and which to defer), since the sort key ignores tombstone overhead that the real shrink accounts for.

### Likelihood Explanation
Tombstones are carried forward whenever a slot contains zero-lamport single-ref accounts that are newer than the latest full snapshot slot (a very common, non-adversarial steady-state condition, not something requiring a malicious actor), so the divergence between the pre-check and the real computation can occur during normal validator operation whenever shrink runs on any slot with pending zero-lamport tombstones.

### Recommendation
Make the pre-check formulas consistent with the actual shrink decision by including tombstone bytes (or an equivalent conservative estimate) wherever `alive_bytes_after_shrink` is used as a shrink-worthiness/candidacy signal — in `is_candidate_for_shrink`, `is_shrinking_productive`, `select_candidates_by_total_usage`, and `AncientSlotInfos::add`/`calc_ancient_slot_info` — so that a slot is only selected as a candidate when `alive_bytes_after_shrink(store) + estimated_tombstone_bytes(store) < written_bytes`, matching the real `total_rewrite_bytes` computation performed in `shrink_storage`.

### Proof of Concept
1. Create a storage/slot whose only "not obviously alive" content is a set of zero-lamport, single-ref accounts, and set `latest_full_snapshot_slot` to a value older than this slot so `can_purge_zero_lamport_single_ref_after_shrink` returns `false` (as in `test_shrink_collect_carries_forward_existing_tombstones` [11](#0-10) ).
2. Observe `alive_bytes_after_shrink(&storage)` is small (excludes these zero-lamport accounts), so `is_candidate_for_shrink`/`is_shrinking_productive` report the slot as a productive shrink candidate and it is inserted into `shrink_candidate_slots`.
3. When `shrink_storage` actually runs `shrink_collect`, `tombstones_total_bytes` (non-zero because these accounts must be carried forward, per `can_purge_zero_lamport_single_ref_after_shrink` gating) is added to `alive_total_bytes` to form `total_rewrite_bytes`, which can equal or exceed `written_bytes`, triggering `should_not_shrink` to return `true` and the shrink attempt to be aborted after the full collect pass has already run: [5](#0-4) .
4. This reproduces the exact log line the code anticipates ("Unexpected shrink ... likely caused by a bug for calculating alive bytes"), confirming the pre-check and the real computation disagree.

#[test]
fn test_shrink_collect_carries_forward_existing_tombstones() {
    let accounts_db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    let slot = 2;
    // Latest full snapshot older than `slot`: tombstones are not yet purgeable.
    accounts_db.set_latest_full_snapshot_slot(slot - 1);

    let alive_pubkey = Pubkey::new_unique();
    let tombstone_pubkey = Pubkey::new_unique();
    let alive_account = AccountSharedData::new(1, 0, &Pubkey::default());
    let zero_lamport_account = AccountSharedData::new(0, 0, &Pubkey::default());

    let (_temp_dirs, paths) = get_temp_accounts_paths(1).unwrap();
    let storage = Arc::new(AccountStorageEntry::new(
        &paths[0],
        slot,
        100,
        DEFAULT_FILE_SIZE,
        accounts_db.accounts_file_provider,
    ));
    // An ordinary alive account, present in the index.
    append_single_account_with_default_hash(
        &storage,
        &alive_pubkey,
        &alive_account,
        true,
        Some(&accounts_db.accounts_index),
    );
    // A zero-lamport account physically in the storage but NOT in the index: i.e. a tombstone
    // carried forward by a prior shrink of an even-older storage.
    append_single_account_with_default_hash(
        &storage,
        &tombstone_pubkey,
        &zero_lamport_account,
        true,
        None,
    );
    accounts_db.storage.insert(Arc::clone(&storage));
    accounts_db.add_root(slot);

    // would have.
    let mut tombstone_offset = None;
    storage
        .accounts
        .scan_accounts_without_data(|offset, account| {
            if account.pubkey == &tombstone_pubkey {
                tombstone_offset = Some(offset);
            }
        })
        .unwrap();
    storage.batch_insert_tombstone_offsets([tombstone_offset.unwrap()]);
    assert_eq!(storage.num_zero_lamport_single_ref_accounts(), 1);

    // not mis-routed into the alive set.
    let mut unique_accounts =
        accounts_db.get_unique_accounts_from_storage_for_shrink(&storage, &ShrinkStats::default());
    let shrink_collect = accounts_db.shrink_collect::<AliveAccounts<'_>>(
        &storage,
        &mut unique_accounts,
        &ShrinkStats::default(),

    assert_eq!(shrink_collect.tombstones_to_carry_forward.len(), 1);
