Based on my research, there is a valid analog to the audit finding. The bug class ("iterating over an unbounded array in a state-mutating operation, causing excessive gas/CPU usage and potential DoS") maps to `MUtil.transferAllToken` in java-tron's TVM implementation, which iterates over an account's entire TRC10 asset map during a `SUICIDE`/`SUICIDE2` opcode execution, with no cap on the number of distinct tokens a contract account can accumulate.

### Title
Unbounded iteration over an account's TRC10 asset map (`AssetMapV2`) during contract self-destruct causes excessive CPU/energy usage - (File: `actuator/src/main/java/org/tron/core/vm/utils/MUtil.java`)

### Summary
`MUtil.transferAllToken`, invoked from `Program.suicide`/`Program.suicide2` when a smart contract executes the `SUICIDE`/`SUICIDE2` opcode, iterates over the full `AssetMapV2` of the destructing account to transfer every held TRC10 token to the beneficiary address. Unlike other per-account repeated-resource lists in java-tron (e.g. `FrozenSupply`, capped by `dynamicStore.getMaxFrozenSupplyNumber()`, or `UnFreezeV2`, capped by `UnfreezeBalanceV2Actuator.UNFREEZE_MAX_TIMES = 32`), there is no cap on the number of distinct TRC10 token types a contract account can accumulate over its lifetime, since any external account or contract can freely send any number of distinct token IDs to it via `transferToken`.

### Finding Description
`Program.suicide()` and `Program.suicide2()` call `MUtil.transferAllToken(getContractState(), owner, obtainer)` (or to the black hole address) as part of self-destruct handling: [1](#0-0) 

`transferAllToken` iterates the entire asset map with a `forEach`, doing per-entry map lookups/inserts for both accounts: [2](#0-1) 

This is analogous to the reported `allTokens`-array cycle: the loop bound is determined entirely by how many distinct TRC10 tokens have accumulated in the account's map, a quantity that grows unboundedly as arbitrary senders (anyone submitting a `TransferAssetContract` or calling `transferToken` from a contract) send new token types to the account, with no validation limiting the number of distinct token types per account, unlike the capped `FrozenSupply`/`UnFreezeV2` lists elsewhere in the codebase: [3](#0-2) [4](#0-3) 

### Impact Explanation
If an attacker (or accumulated organic activity) causes a contract account to hold a very large number of distinct TRC10 token IDs, a single `SUICIDE`/`SUICIDE2` execution against that account must iterate the entire map within one transaction. Because TVM execution is subject to per-opcode energy accounting and a CPU time limit (`program.checkCPUTimeLimit`, enforced in the main VM loop): [5](#0-4) 
a sufficiently large asset map can cause the transaction to run out of energy or hit the CPU timeout mid-way through `transferAllToken`'s `forEach`, partially mutating protobuf builders before failing. This risks either denial-of-service on the contract's ability to self-destruct/clean up (a `SUICIDE` that can never complete within `feeLimit`) or inconsistent/wasted execution, consistent with the original report's "high gas fees ... hit gas limits" concern.

### Likelihood Explanation
Reaching this path only requires standard, unprivileged actions: sending TRC10 tokens (via `TransferAssetContract`, or `transferToken` in a smart contract) of many distinct token IDs to a target contract address, then broadcasting a transaction that triggers that contract's `SUICIDE` opcode. All three actuators/opcodes involved (`TransferAssetContract`, `transferToken`, `SUICIDE`) are reachable by any anonymous account via normal broadcast transactions, requiring no special privilege — matching the validation criteria for a reachable path from a broadcast transaction.

### Recommendation
Introduce an explicit, enforced cap on the number of distinct TRC10 token types a single account may hold simultaneously (mirroring the existing caps on `FrozenSupply`/`UnFreezeV2` list sizes), and/or make `transferAllToken` energy-metered per iterated entry (charging additional energy proportional to map size) so that an oversized map causes an early, well-defined out-of-energy failure rather than an unmetered/CPU-time-limited loop. Alternatively, reject `SUICIDE` operations when the asset map exceeds a safe bound, requiring assets to be manually drained first.

### Proof of Concept
1. Deploy a contract `C` with a `suicide(address)` function that calls `selfdestruct`/equivalent (as in `framework/src/test/java/org/tron/common/runtime/vm/TransferTokenTest.java`).
2. Issue N distinct TRC10 tokens (via repeated `AssetIssueContract` transactions) and transfer at least one unit of each to `C` (via `transferToken` calls or `TransferAssetContract`), building up `C`'s `AssetMapV2` to a large size.
3. Trigger `C.suicide(beneficiary)`. Observe that `MUtil.transferAllToken` must iterate the full N-entry map inside a single transaction; measure energy usage and elapsed CPU time as N grows, and confirm behavior once N is large enough to approach `feeLimit`/CPU timeout limits (similar in structure to the existing `TransferTokenSingleInstructionTimeTest` performance test at `framework/src/test/java/org/tron/common/runtime/vm/TransferTokenTest.java:203-229`).   public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
