### Title
Unbounded per-asset DB reads in `Wallet.getAccountResource` via `setAssetNetLimit` allow underpriced disk amplification through the public `/wallet/getaccountresource` API - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`Wallet.getAccountResource(ByteString)` calls `setAssetNetLimit`, which iterates every key in `accountCapsule.getAllFreeAssetNetUsage()` (or `getAllFreeAssetNetUsageV2()`) and performs one `AssetIssueStore`/`AssetIssueV2Store` DB lookup per distinct asset the queried account has ever held. Because `GetAccountResourceServlet` is a rate-limited but otherwise unauthenticated public HTTP endpoint, an attacker who accumulates many distinct TRC10 balances on one address can force each subsequent request for that address to perform O(n) DB reads.

### Finding Description
`GetAccountResourceServlet.fillResponse` (lines 49-56) directly forwards the caller-supplied `address` to `wallet.getAccountResource(address)` with no bound on account complexity. [1](#0-0) 

Inside `Wallet.getAccountResource`, `setAssetNetLimit(assetNetLimitMap, accountCapsule)` is invoked unconditionally: [2](#0-1) 

`setAssetNetLimit` iterates `accountCapsule.getAllFreeAssetNetUsage()` (or the V2 map, depending on the `allowSameTokenName` chain parameter) and, for every key (i.e., every distinct asset ID the account has interacted with), performs a `chainBaseManager.getAssetIssueStore().get(key)` / `getAssetIssueV2Store().get(key)` lookup: [3](#0-2) 

The `free_asset_net_usage`/`free_asset_net_usageV2` map on `AccountCapsule` accumulates one entry per distinct asset the account has ever received (each `TransferAssetContract` receipt to a new asset ID adds a new map key), and there is no cap in the actuator path preventing an account from holding an unbounded number of distinct asset entries. Because receiving a TRC10 asset is a cheap/normal-cost transaction (paid for by the sender, not amplified per read), an attacker can cheaply grow this map to a large size (e.g., thousands of entries) on a single address, then repeatedly call the public, unauthenticated `/wallet/getaccountresource` (or `/wallet/getaccountnet`, which has the identical `setAssetNetLimit` call) endpoint. Each call costs the attacker only the fixed per-request rate-limit budget enforced by `RateLimiterServlet`, but triggers N DB point-lookups against `AssetIssueStore`/`AssetIssueV2Store` server-side — an asymmetric cost multiplier controlled entirely by the attacker's pre-built account state.

`getAccountNet` has the same vulnerable call: [4](#0-3) 

No caching, pagination, or asset-count cap exists in this path to bound the work; the only mitigation present is the fixed per-endpoint request rate limiter (`RateLimiterServlet`), which limits request *frequency* but not *per-request cost*.

### Impact Explanation
Repeated calls to `/wallet/getaccountresource` (and `/wallet/getaccountnet`) for an address with a large number of distinct asset holdings cause the node to perform a correspondingly large number of DB reads per request. This is a CPU/disk amplification vector: the attacker's cost (building the asset list once, then making cheap rate-limited HTTP calls) is far lower than the server's cost (N random-access disk reads per request), which can degrade HTTP service availability for the node, particularly under concurrent requests from multiple crafted "fat" addresses.

### Likelihood Explanation
Feasibility is moderate to high: any account can receive many distinct TRC10 assets via ordinary `TransferAssetContract` transactions (or by issuing/holding many assets itself), and each unique asset ID adds one entry to `free_asset_net_usage`/`free_asset_net_usageV2` with no visible cap in the account/asset actuator logic reachable from this analysis. The endpoint is public and requires no authentication — only the existing per-IP/per-endpoint rate limit applies, and that limit governs request count, not request cost. Repeatability is high since the crafted account state is persistent and can be reused indefinitely.

### Recommendation
Bound or amortize the cost of `setAssetNetLimit`: cache `AssetIssueCapsule`/`freeAssetNetLimit` lookups (e.g., in an in-memory LRU keyed by asset ID, since asset limits change infrequently), or cap the number of asset entries processed per request/response (with pagination), or move the free-asset-limit lookups out of the hot request path (e.g., embed the current free-limit snapshot instead of a live per-asset DB fetch). Additionally, consider limiting the maximum number of distinct assets an account can be recorded as holding usage for, or charging bandwidth/energy proportional to the number of distinct assets when performing account-resource queries above a threshold.

### Proof of Concept
Java integration test plan (extends `WalletTest`/`BaseHttpTest`, or a JMH-style microbenchmark):
1. Create N (e.g., 10,000) distinct `AssetIssueCapsule` entries in `AssetIssueStore`/`AssetIssueV2Store`, mirroring how `AssetIssueActuator` would create them via `TransferAssetContract`/`AssetIssueContract`.
2. Populate a single `AccountCapsule`'s `free_asset_net_usage`/`free_asset_net_usageV2` map with all N asset keys (as would occur from N `TransferAssetContract` receipts), and persist it via `AccountStore`.
3. Benchmark `wallet.getAccountResource(ByteString.copyFrom(address))` wall-clock time and instrument/count `AssetIssueStore.get`/`AssetIssueV2Store.get` invocations (e.g., via a spy/wrapper store) for:
   - Baseline account with 1 asset.
   - Crafted account with 10,000 distinct assets.
4. Assert: DB-read count scales linearly with N (`assertEquals(N, readCount)`), and wall-clock time for N=10,000 significantly exceeds (e.g., >100x) that for N=1 — demonstrating that a single HTTP request's cost is unbounded relative to the fixed per-request rate-limit budget enforced by `RateLimiterServlet`.
5. Optionally, drive this through the actual servlet (`GetAccountResourceServlet.doGet`) using `MockHttpServletRequest`/`MockHttpServletResponse` (as in `GetAccountResourceServletTest`) to confirm the amplification is reachable end-to-end through the public HTTP API.

```java
  private Map<String, Long> setAssetNetLimit(Map<String, Long> assetNetLimitMap,
      AccountCapsule accountCapsule) {
    Map<String, Long> allFreeAssetNetUsage;
    if (chainBaseManager.getDynamicPropertiesStore().getAllowSameTokenName() == 0) {
      allFreeAssetNetUsage = accountCapsule.getAllFreeAssetNetUsage();
      allFreeAssetNetUsage.keySet().forEach(asset -> {
        byte[] key = ByteArray.fromString(asset);
        assetNetLimitMap
            .put(asset, chainBaseManager.getAssetIssueStore().get(key).getFreeAssetNetLimit());
      });
    } else {
      allFreeAssetNetUsage = accountCapsule.getAllFreeAssetNetUsageV2();
      allFreeAssetNetUsage.keySet().forEach(asset -> {
        byte[] key = ByteArray.fromString(asset);
        assetNetLimitMap
            .put(asset, chainBaseManager.getAssetIssueV2Store().get(key).getFreeAssetNetLimit());
      });
    }
    return allFreeAssetNetUsage;
  }
```
