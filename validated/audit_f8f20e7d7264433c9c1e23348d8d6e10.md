### Title
Webhook shop-domain header is not cryptographically bound to the HMAC-authenticated body, allowing cross-tenant webhook spoofing - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`)

### Summary
`shopify.webhooks.validate()` authenticates an inbound webhook by computing an HMAC over `rawBody` only, then trusts the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header verbatim to decide which shop's offline session to load and expose to the handler. The header is never covered by the HMAC, so nothing cryptographically ties the "which shop is this for" claim to the value that was actually authenticated — the same verification gap as the reported Solidity bug, where an inner value's internal consistency is checked but never tied to the outer trusted root.

### Finding Description
`validateHmacFromRequestFactory` / `validateHmacString` compute and compare an HMAC over `rawBody` alone: [1](#0-0) [2](#0-1) 

`validateFactory` calls this HMAC check and then, independently, calls `checkWebhookHeaders(request.headers, webhookType)` to read `domain`, `topic`, `webhookId`, etc. straight from headers, with the domain field defined by `ShopifyHeader.Domain` / `ShopifyEventsHeader.Domain`: [3](#0-2) [4](#0-3) [5](#0-4) 

The returned `check.domain` is then used directly to look up and attach the offline session/admin client for that shop, without any check that the domain matches what was actually signed: [6](#0-5) [7](#0-6) 

This mirrors the reported analog bug class precisely: `stateProof`/`extraProof.leaf` integrity is checked internally (here: body ↔ HMAC), but the value that determines *which trust context the data belongs to* (`extraProof.root` ↔ `massExitBlock`; here: `X-Shopify-Shop-Domain` header ↔ signed payload) is never verified against the authenticated artifact.

Because a single app-wide `apiSecretKey` is shared across every shop that installs the app (it is not per-shop), any legitimately-received webhook (with a real, verifiable HMAC over its body) can be replayed by an attacker with only the `domain` header value changed to a different installed shop's domain — the HMAC still validates because it never covered the header. This lets a webhook payload be re-attributed to another tenant, causing the framework to attach that other shop's offline `Session`/admin client to a handler processing attacker-controlled body content (since the body's HMAC only proves the body was signed for *some* installation, not for the claimed shop).

### Impact Explanation
An attacker who can trigger or capture one legitimate webhook delivery to their own installation (trivial — install the app, trigger an event) can forge a POST to the app's webhook endpoint with the original HMAC-valid body but an arbitrary `X-Shopify-Shop-Domain` value corresponding to a *different* merchant that has installed the same app. The webhook handler will authenticate this as valid, load that other shop's offline `Session`, and invoke the app's business logic (and often the admin API client) as if the event genuinely originated from that shop. This is a cross-tenant confusion vulnerability affecting any app relying on `shopify.webhooks.validate()`/`authenticate.webhook()` for shop-scoped webhook processing — the topic/body may not correspond to a legitimate business event for the targeted shop, but the app will act on it under that shop's authenticated session.

### Likelihood Explanation
Exploitation requires no privileged access beyond installing the app once (a normal merchant/attacker action) or observing any single valid webhook delivery, and crafting a raw HTTP POST with a substituted header — well within reach of "a single merchant" per the validation rules. No secret material needs to be leaked; the flaw is structural (HMAC scope excludes the header used for tenant attribution).

### Recommendation
Bind the shop-domain (and topic/webhook id) into the HMAC-covered material, or otherwise cryptographically verify that the claimed `domain` header corresponds to the shop the HMAC was computed for (e.g., include the header values as part of the canonical string being HMAC'd, or perform a secondary verification such as checking the domain against session-provisioned data known only for that shop's registered webhook subscription). At minimum, apps should be warned that `check.domain` is unauthenticated header data and must not be trusted for authorization decisions without additional binding.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining a legitimate installation and a registered webhook (e.g., `orders/create`).
2. Attacker triggers an event so Shopify delivers a webhook POST to the app's `/webhooks` endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, then replays it to the same endpoint but replaces only `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (a real, unrelated installed shop). The body and HMAC header are left unchanged.
4. In `validateFactory` (`packages/apps/shopify-api/lib/webhooks/validate.ts`), `validateHmacFromRequestFactory` recomputes `HMAC(secret, B)` — since `B` is unchanged, the HMAC check passes (`validate.ts` lines 56-71).
5. `checkWebhookHeaders` reads `domain = 'victim-shop.myshopify.com'` from the header and returns `valid: true`.
6. `authenticateWebhookFactory` (`authenticate.ts`, both remix and react-router variants) calls `ensureValidOfflineSession(params, check.domain)`, loading and attaching `victim-shop`'s offline session/admin client to the handler, which then processes the attacker-supplied body `B` as if it were a genuine event for `victim-shop`.

*Note: I was not able to fully verify from the indexed code whether any additional runtime layer (e.g., Shopify's edge infra outside this repo) re-validates the domain header before requests reach `shopify-app-js`; this analysis is scoped strictly to what `shopify-app-js` itself validates.*

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}
