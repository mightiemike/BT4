### Title
Proposal approvals can be mutated after resolution (APPROVED/DISAPPROVED) due to missing finalized-state check - ([File: actuator/src/main/java/org/tron/core/actuator/ProposalApproveActuator.java])

### Summary
`ProposalApproveActuator.validate()` only rejects a `ProposalApproveContract` when the target proposal is `CANCELED` or has expired according to `latestBlockHeaderTimestamp`, but it never checks whether the proposal has already reached a terminal resolution (`APPROVED`/`DISAPPROVED`). This mirrors the reported `updateProposal` bug class: the function that mutates a proposal's votes/resolution does not verify that the update is not reusing/overwriting a state that has already been finalized.

### Finding Description
`ProposalApproveActuator.execute()` unconditionally mutates the stored `ProposalCapsule`'s approval list via `addApproval`/`removeApproval` and persists it back to `ProposalStore`: [1](#0-0) 

`validate()` guards against a `CANCELED` proposal and an expired proposal (using `dynamicStore.getLatestBlockHeaderTimestamp()` compared against `proposalCapsule.getExpirationTime()`), but performs no check for `State.APPROVED` or `State.DISAPPROVED`: [2](#0-1) 

The `ProposalCapsule` itself exposes a `hasProcessed()` helper that is specifically meant to detect a finalized proposal (`APPROVED` or `DISAPPROVED`), but this helper is used only by `ProposalController`, never by `ProposalApproveActuator`: [3](#0-2) 

Proposal finalization happens out-of-band in `ProposalController.processProposal()`, which is invoked from `processProposals()` when `proposalCapsule.hasExpired(currentTime)` is true, where `currentTime` is `manager.getDynamicPropertiesStore().getNextMaintenanceTime()` — not the actual current/latest block timestamp used by the actuator: [4](#0-3) 

Because the finalization check in `ProposalController` uses `getNextMaintenanceTime()` (which is advanced ahead of the real current time at each maintenance cycle) while the actuator's own expiry check uses `getLatestBlockHeaderTimestamp()`, there is a window in which a proposal has already transitioned to `APPROVED`/`DISAPPROVED` and had `setDynamicParameters()` applied, yet the actuator still treats it as "not expired" and permits further `addApproval`/`removeApproval` mutations. Even setting the timing nuance aside, the structural flaw is that the actuator never checks the terminal `hasProcessed()` state at all, so a witness can keep calling `ProposalApproveContract` against a resolved proposal, corrupting the on-chain record of what was actually approved.

### Impact Explanation
This allows an already-resolved governance proposal's approval list to keep changing after resolution, producing an on-chain state where `Proposal.state` (APPROVED/DISAPPROVED, already acted upon via `setDynamicParameters`) is inconsistent with `Proposal.approvals` as later read through wallet/RPC/HTTP proposal-query APIs. This is a data/state-integrity corruption in the governance actuator layer (not a privileged-actor bypass — any existing witness, whose addresses are public information, can trigger it via a normal broadcast transaction), and it undermines the auditability/finality guarantees of the on-chain proposal mechanism.

### Likelihood Explanation
Any account registered as a witness (`witnessStore.has(ownerAddress)`) can send a `ProposalApproveContract` transaction referencing any non-canceled, non-expired-by-timestamp proposal ID at any time, with no restriction tied to the proposal's `state` field. This requires no privileged/owner-only capability beyond being one of the existing witnesses, and no special conditions beyond timing relative to `expirationTime`/`nextMaintenanceTime`, making it straightforwardly reachable via a standard broadcast transaction.

### Recommendation
Add an explicit terminal-state check in `ProposalApproveActuator.validate()` using the existing `ProposalCapsule.hasProcessed()` helper, rejecting any `ProposalApproveContract` targeting a proposal whose state is already `APPROVED` or `DISAPPROVED`, in addition to the existing `CANCELED` check. Additionally, align the expiry semantics used by the actuator with the one used by `ProposalController` (e.g., also compare against `getNextMaintenanceTime()`), so that the actuator cannot classify a proposal as "still open" once `ProposalController` has already finalized it.

### Proof of Concept
1. A witness creates/observes proposal `P` with `expirationTime = T_exp`.
2. At a maintenance cycle, `ProposalController.processProposals()` runs with `currentTime = getNextMaintenanceTime()` such that `T_exp <= getNextMaintenanceTime()`, so `proposalCapsule.hasExpired(currentTime)` is true; `processProposal()` sets `P.state` to `APPROVED` or `DISAPPROVED` and applies `setDynamicParameters()`. [5](#0-4) 
3. If the real chain time (`latestBlockHeaderTimestamp`) has not yet reached `T_exp`, a witness broadcasts a `ProposalApproveContract` for `P`. `validate()` passes because state is neither `CANCELED` nor is `now >= T_exp`: [6](#0-5) 
4. `execute()` mutates `P.approvals` in `ProposalStore` even though `P.state` is already `APPROVED`/`DISAPPROVED`, producing an inconsistent, mutable "final" record. [1](#0-0)

  public void processProposals() {
    long latestProposalNum = manager.getDynamicPropertiesStore().getLatestProposalNum();
    if (latestProposalNum == 0) {
      logger.info("latestProposalNum is 0, return");
      return;
    }

    long proposalNum = latestProposalNum;

    ProposalCapsule proposalCapsule = null;

    while (proposalNum > 0) {
      try {
        proposalCapsule = manager.getProposalStore()
            .get(ProposalCapsule.calculateDbKey(proposalNum));
      } catch (Exception ex) {
        logger.error("", ex);
        proposalNum--;
        continue;
      }

      if (proposalCapsule.hasProcessed()) {
        logger
            .info("Proposal has processed, id:[{}], skip it and before it",
                proposalCapsule.getID());
        //proposals with number less than this one, have been processed before
        break;
      }

      if (proposalCapsule.hasCanceled()) {
        logger.info("Proposal has canceled, id:[{}], skip it", proposalCapsule.getID());
        proposalNum--;
        continue;
      }

      long currentTime = manager.getDynamicPropertiesStore().getNextMaintenanceTime();
      if (proposalCapsule.hasExpired(currentTime)) {
        processProposal(proposalCapsule);
        proposalNum--;
        continue;
      }

      proposalNum--;
      logger.info("Proposal has not expired, id:[{}], skip it", proposalCapsule.getID());
    }
    logger.info("Processing proposals done, oldest proposal[{}]", proposalNum);
  }

  public void processProposal(ProposalCapsule proposalCapsule) {

    List<ByteString> activeWitnesses = this.manager.getWitnessScheduleStore().getActiveWitnesses();
    if (proposalCapsule.hasMostApprovals(activeWitnesses)) {
      logger.info(
          "Processing proposal,id:{},it has received most approvals, "
              + "begin to set dynamic parameter:{}, "
              + "and set proposal state as APPROVED",
          proposalCapsule.getID(), proposalCapsule.getParameters());
      setDynamicParameters(proposalCapsule);
      proposalCapsule.setState(State.APPROVED);
      manager.getProposalStore().put(proposalCapsule.createDbKey(), proposalCapsule);
    } else {
      logger.info(
          "Processing proposal,id:{}, "
              + "it has not received enough approvals, set proposal state as DISAPPROVED",
          proposalCapsule.getID());
      proposalCapsule.setState(State.DISAPPROVED);
      manager.getProposalStore().put(proposalCapsule.createDbKey(), proposalCapsule);
    }
