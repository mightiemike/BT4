### Title
L1Handler execution commits state changes before the terminal fee-paid check, corrupting the block state for a transaction later reported as rejected — ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs])

### Summary
`L1HandlerTransaction::execute_raw` commits the Cairo execution's state diff into the shared per-block `TransactionalState` *before* performing the final "was any fee paid on L1" check. If that check fails, the function does not roll back the already-committed writes — it instead returns a hard `Err(TransactionExecutionError::TransactionFeeError(InsufficientFee))`, which the batcher's block builder treats as a rejected transaction (excluded from the block's transaction list, receipts, and fee accounting), while the state mutations produced by running the L1 handler's entry point remain permanently applied to the block state that feeds the final state diff / root.

### Finding Description
In `crates/blockifier/src/transaction/l1_handler_transaction.rs`, `execute_raw` runs the L1 handler's entry point in an isolated `TransactionalState::create_transactional(state)` layer, then performs two sequential post-execution checks: [1](#0-0) 

1. Resource-bounds check (`FeeCheckReport::check_all_gas_amounts_within_bounds`). If it fails, `execution_state.abort()` is correctly called before returning `Ok(..)` with a proper "reverted" receipt — no state leaks, and the transaction stays in the block with `fee: 0`.
2. If the bounds check passes, `execution_state.commit()` is called immediately [2](#0-1) , permanently merging the Cairo execution's writes (arbitrary contract storage/state changes performed by the L1 handler entry point) into `state`. Only *after* this commit does the code check `paid_fee_on_l1 == Fee(0)` and, if so, return `Err(TransactionFeeError::InsufficientFee)` [3](#0-2) .

Because `state: &mut TransactionalState<'_, U>` is the actual mutable per-block state passed into `execute_raw` (not a further nested, discardable wrapper), the `commit()` call is not reversible by the caller once it executes. When the function subsequently returns `Err`, the caller has no way to distinguish "this transaction's effects were already baked into the block state" from "this transaction never touched state," yet it treats the transaction as fully rejected.

Downstream, in `apollo_batcher`, `collect_execution_results_and_stream_txs` unconditionally records every L1Handler transaction hash into `consumed_l1_handler_tx_hashes` before inspecting the execution result [4](#0-3) , and on `Err(..)` results it inserts the hash into `rejected_tx_hashes`, logging only an informational message [5](#0-4) . The transaction is therefore simultaneously:
- Marked "consumed" (so the L1 message will not be retried),
- Marked "rejected" (excluded from the executed transaction list, receipts, and fee accounting),
- While its Cairo-level state writes remain committed in the block's `CachedState`, and will be reflected in the final `state_diff` / commitment computed at `close_block`.

This is the direct structural analog of the reported Geode `WithdrawalModuleLib` bug: an irreversible side effect (`burn()` there, `execution_state.commit()` here) is applied unconditionally before a later validation step that can still cause the overall operation to be treated as failed, with no mechanism to undo the side effect or reconcile the accounting for the "in-between" state.

### Impact Explanation
A phantom, unauthorized state mutation becomes baked into the sequencer's committed state root for a transaction that is simultaneously reported to the rest of the system (execution receipts, `rejected_tx_hashes`, fee accounting, pre-confirmed transaction stream) as never having succeeded. This can produce:
- An incorrect committed state root / block hash that does not correspond to the officially recorded set of executed/accepted transactions.
- Potential honest-node divergence if this path is hit non-deterministically (e.g., differing `paid_fee_on_l1` values supplied to proposer vs. validator via `TransactionConverter`, currently hardcoded as `Fee(1)` with an explicit TODO to replace it with the real value from L1 — meaning once that TODO is resolved and a legitimately zero fee is observed, this code path becomes live in production).
- Unauthorized account/contract state changes (e.g., balance or storage mutations performed by the L1 handler's Cairo code) applied to L2 state despite the transaction not being part of the block.

### Likelihood Explanation
The `paid_fee_on_l1 == Fee(0)` branch is explicitly reachable any time an L1 handler is executed with a zero recorded L1 fee — currently masked in this codebase because `convert_consensus_l1_handler_to_internal_l1_handler` hardcodes `Fee(1)` as a placeholder [6](#0-5) , explicitly noted as a TODO to be replaced with the real L1-observed fee. Once real fee values are wired in (or if any caller path constructs an `L1HandlerTransaction` with `paid_fee_on_l1 = Fee(0)`, e.g. via a malformed/adversarial L1 event or a future code path), the vulnerable sequence executes deterministically inside normal block building/validation for any single L1-originated message — no privileged actor is required, only an L1 message whose recorded fee is zero.

### Recommendation
Move the `paid_fee_on_l1` check before `execution_state.commit()`, or perform the commit only after all post-execution checks (including the fee-paid check) have succeeded — mirroring the pattern already used for the resource-bounds check, where `execution_state.abort()` is called before returning any non-committing outcome. If a hard `Err` must be produced for zero-fee L1 handlers, `execution_state.abort()` must be called first so no writes leak into the shared block state.

### Proof of Concept
1. Construct or observe an `L1HandlerTransaction` with `paid_fee_on_l1 == Fee(0)` (reachable once the `Fee(1)` placeholder in `transaction_converter.rs` is replaced with the true L1-scraped fee, or via any caller that constructs the executable transaction directly with a zero fee).
2. Have this transaction's entry point perform a state-changing write (e.g., the existing test helper `l1handler_tx` in `crates/blockifier/src/test_utils/l1_handler.rs`, which calls `l1_handler_set_value`).
3. Execute via `execute_raw`: the resource-bounds check passes, so `execution_state.commit()` runs and the storage write becomes part of `state`.
4. The zero-fee check then fires and `execute_raw` returns `Err(TransactionFeeError::InsufficientFee)`.
5. Inspect `state` after the call (as done in `transactions_test.rs`'s existing negative-flow test around line 2940-2961, which currently only asserts the returned `Err` but does not check whether the storage write persisted) — the storage location touched by `l1_handler_set_value` should be checked to confirm it retains the new value despite the transaction being reported as failed, verifying the state-commit-then-error sequence.
