### Title
Non-hardened `ExchangeWithdrawActuator` uses double-precision math for precision checks, causing legitimate exchange withdrawals to revert unpredictably - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` lets an exchange creator withdraw liquidity from a bonding-curve style exchange pool by specifying a `quant` of one token; the contract must compute the corresponding amount of the other token (`anotherTokenQuant`) via a ratio of pool balances. Just like the Ion Protocol `repayWithdraw` bug (amount specified in one unit, converted into an internal unit that can drift due to rounding), the default (non-hardened) code path here performs this cross-check using `double` arithmetic, which can diverge from the integer truncated result used to actually move funds, causing the transaction to revert with `"Not precise enough"` even though the requested withdrawal is legitimate.

### Finding Description
In `doValidate()`, `anotherTokenQuant` is first computed with exact integer truncation: [1](#0-0) 

It is then cross-checked against a second, independently computed value to guard against imprecision. When `allowHarden()` is `false` (the default, governance-gated legacy path), this second computation uses `double`/`BigDecimal.doubleValue()` math instead of exact integer/BigDecimal arithmetic: [2](#0-1) 

`allowHarden()` gates this behavior on the `AllowHardenExchangeCalculation` dynamic property, which is a proposal/governance-controlled feature that must be explicitly activated by committee vote: [3](#0-2) 

Because `double` cannot exactly represent the same rational value as the `BigInteger`/`BigDecimal` integer-truncated computation used in `execute()`: [4](#0-3) 

the `remainder` calculated with `doubleValue()` can differ from the `BigDecimal`-only tolerance check enough to push `remainder / anotherTokenQuant` over the hard-coded `0.0001` threshold, triggering a spurious `"Not precise enough"` revert for a withdrawal that is otherwise fully valid and fully covered by pool balances. This is structurally the same bug class as the Ion Protocol finding: a user-specified amount in one unit is converted (via a rate/ratio) into another accounting unit, and rounding/precision mismatch between the “expected” and “actual” computed value causes the transaction to revert, especially for larger or near-full withdrawal amounts where absolute rounding error is largest.

The test suite in this repo explicitly demonstrates both the failure mode and its mitigation (the `allowHarden` flag), confirming this is a real, previously-identified issue: [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a Denial-of-Service on a legitimate on-chain financial operation (protocol implementation logic reachable directly from a broadcast `ExchangeWithdrawContract` transaction). Any exchange creator withdrawing liquidity — particularly near-full pool withdrawals, where the absolute magnitude of the double-precision rounding error is largest relative to `0.0001` tolerance — can have their transaction fail even though the pool has sufficient balance and the exact integer computation is legitimate. Because the flag defaults to disabled until committee/governance enables `AllowHardenExchangeCalculation`, the double-precision, imprecise path is the live default behavior on the network unless/until that proposal is passed.

### Likelihood Explanation
Likelihood is moderate: it requires specific pool balance ratios and quantities where the truncated integer ratio and the double-computed ratio diverge beyond the 0.0001 relative tolerance — a naturally occurring condition for certain balance/quant combinations (as shown by the existing test `SameTokenNameCloseNotPreciseEnough` which fails at `quant = 9991` and succeeds at `quant = 10001`). No malicious actor is required; ordinary users performing full or partial exchange withdrawals can hit this at any time the hardened flag is not enabled.

### Recommendation
Ensure the precision cross-check always uses exact `BigDecimal`/`BigInteger` arithmetic (the `allowHarden()` code path) rather than `double`, and consider removing or defaulting-enabling `allowHardenExchangeCalculation` so the imprecise legacy path is not reachable network-wide by default. Alternatively, remove the redundant double-precision tolerance check entirely since the integer-truncated `anotherTokenQuant` computed in `execute()` is already deterministic and exact.

### Proof of Concept
Using the existing repo test harness (`ExchangeWithdrawActuatorTest`), with `AllowHardenExchangeCalculation` left at its default (disabled) value, calling `ExchangeWithdrawActuator.validate()`/`execute()` with `firstTokenBalance = 100000000`, `secondTokenBalance = 200000000`, and `quant = 9991` (as in `SameTokenNameCloseNotPreciseEnough`) reverts with `"Not precise enough"` even though the corresponding integer-truncated `anotherTokenQuant` is fully covered by the pool balances, demonstrating the spurious-revert condition: [7](#0-6)
