### Title
Unbounded full-table scan via unpaginated `getAssetIssueList()`/`getAssetIssueByAccount()`/`getAssetIssueListByName()` endpoints allows linear-cost DoS amplification on every future public request - ([File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java])

### Summary
`AssetIssueStore.getAllAssetIssues()` performs a full, unbounded `Streams.stream(iterator())` scan of the entire asset-issue table, and this method is invoked directly (with no offset/limit) by the public `getAssetIssueList()`, `getAssetIssueByAccount()`, and `getAssetIssueListByName()`/`getAssetIssueByName()` RPC/HTTP endpoints in `Wallet.java`. Since asset issuance has no cap on the total count of assets in the store, every future call to these unpaginated endpoints imposes CPU/memory cost that grows linearly with however many assets any attacker has ever created, even though the attacker pays only once per asset.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` [1](#0-0)  is called with no limit by `Wallet.getAssetIssueList()`, `Wallet.getAssetIssueByAccount()`, and `Wallet.getAssetIssueListByName()` [2](#0-1) [3](#0-2) [4](#0-3) . These are reachable via public gRPC (`GetAssetIssueByAccount`) and HTTP (`GetAssetIssueByAccountServlet`) [5](#0-4)  and gRPC `RpcApiService` [6](#0-5) . A paginated alternative exists (`getAssetIssuesPaginated`, capped by `ASSET_ISSUE_COUNT_LIMIT_MAX`) [7](#0-6) , but it is a separate endpoint (`GetPaginatedAssetIssueListServlet`) that callers must opt into; the unpaginated endpoints remain live and unbounded.

Asset issuance itself is fee-gated: `AssetIssueActuator.calcFee()` charges `getAssetIssueFee()` (default `1024000000L` sun = 1024 TRX) [8](#0-7) [9](#0-8) , and `validate()` additionally enforces that "An account can only issue one asset" [10](#0-9) . This means an attacker cannot cheaply spam N assets from a single account; each new asset requires a distinct, separately funded account paying the full `AssetIssueFee` (1024 TRX by default) plus any account-activation cost. This substantially raises the real-world per-item attacker cost above the "low-cost" premise in the question, but it does not change the underlying architectural issue: once N assets exist (from any combination of attackers over the chain's lifetime), every single future call to the unpaginated endpoints costs O(N) work on every node that serves it, indefinitely — a one-time payment converted into a permanent, repeated cost multiplier on all servicing nodes.

### Impact Explanation
Every full node exposing the public gRPC/HTTP `getAssetIssueList()`, `getAssetIssueByAccount()`, or `getAssetIssueListByName()` endpoints pays an O(N) iteration cost on every single call, where N is the cumulative total of all assets ever issued on the network (bounded only by cumulative historical `AssetIssueFee` payments across all accounts, not by any protocol-enforced ceiling). As N grows over the chain's lifetime, the cost of servicing this specific public request grows without bound, while the pagination-capped variant (`getAssetIssueList(offset, limit)`) that already exists in the codebase is not enforced as the only entry point.

### Likelihood Explanation
The precondition (funding many distinct accounts each with 1024 TRX plus activation cost) makes this a comparatively expensive, but still linear-cost, growth vector rather than a "cheap spam" attack as characterized in the question — the `AssetIssueFee` and one-asset-per-account restriction significantly raise attacker cost per unit of induced server-side work compared to typical zero/low-fee spam vectors. It is nonetheless feasible for a well-resourced or patient attacker (or organic growth over years of chain operation) to accumulate a large N, at which point every public caller of the unpaginated endpoints — not just the attacker — pays the induced iteration cost on every node servicing that call.

### Recommendation
Deprecate or hard-cap the unpaginated `getAssetIssueList()`, `getAssetIssueByAccount()`, and `getAssetIssueListByName()` code paths: internally route them through `getAssetIssuesPaginated()` with an enforced maximum (`ASSET_ISSUE_COUNT_LIMIT_MAX`), or require callers to always supply offset/limit and reject calls without them once the total asset count exceeds a configurable threshold. Alternatively, maintain a secondary index (e.g., by owner address) so `getAssetIssueByAccount()` does not require scanning the entire table.

```java
@Test
public void benchmarkGetAllAssetIssuesScaling() {
  // Populate assetIssueStore with N synthetic entries (bypassing actuator fee logic
  // to directly measure store-level scan cost).
  int[] sizes = {1_000, 10_000, 100_000};
  for (int n : sizes) {
    for (int i = 0; i < n; i++) {
      AssetIssueCapsule c = createAssetIssue(i, "asset" + i);
      assetIssueStore.put(c.createDbKey(), c);
    }
    long start = System.nanoTime();
    List<AssetIssueCapsule> all = assetIssueStore.getAllAssetIssues();
    long elapsed = System.nanoTime() - start;
    Assert.assertEquals(n, all.size());
    // Assert cost grows roughly linearly with n, demonstrating unbounded
    // per-request cost as N grows, independent of the calling client's own fee spend.
    System.out.println("N=" + n + " elapsedNs=" + elapsed);
  }
}
```
Expected result: wall-clock time of `getAllAssetIssues()` (and therefore `Wallet.getAssetIssueList()`/`getAssetIssueByAccount()`) scales linearly with the total number of stored asset issuances, with no ceiling enforced by the store or by the unpaginated Wallet-layer methods, confirming the O(N) per-request cost is unbounded relative to any single caller's request cost, even though attacker cost to grow N is gated by the `AssetIssueFee` and one-asset-per-account rule in `AssetIssueActuator`.

```java
  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
```

```java
  public AssetIssueList getAssetIssueByAccount(ByteString accountAddress) {
    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues();

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }
```
