### Title
Witness/SR signing private key held as un-scrubbed plaintext `String` for the node's entire runtime - ([File: chainbase/src/main/java/org/tron/common/utils/LocalWitnesses.java])

### Summary
The Halborn/Pontem report concerns the mnemonic/wallet password remaining in process memory as plaintext, exploitable via a memory dump on a compromised machine. The analogous condition exists in java-tron's witness (Super Representative) startup path: the block-signing private key, once read from `config.conf` or the CLI, is stored as an immutable `String` in the long-lived `LocalWitnesses` singleton and is never zeroed/scrubbed, unlike the newer keystore CLI tooling (`KeystoreImport`, `KeystoreCliUtils`) which correctly uses `char[]`/`byte[]` with `Arrays.fill(...)` to wipe secrets after use.

### Finding Description
`LocalWitnesses` stores the raw hex private key(s) in a `List<String> privateKeys` field that lives for the lifetime of the witness node process: [1](#0-0) 

The values are populated straight from `config.conf` (`initFromCFGPrivateKey`), from the `-p/--private-key` CLI flag (`initFromCLIPrivateKey`), or from a decrypted keystore (`initFromKeystore`, which converts the decrypted key back into a hex `String` via `ByteArray.toHexString(sign.getPrivateKey())`): [2](#0-1) 

Because Java `String` objects are immutable and interned/managed by the garbage collector, this plaintext signing key cannot be explicitly wiped from the heap and may persist (including in swapped pages, heap dumps, or crash dumps) for as long as the JVM runs — exactly the class of exposure described in the external report ("plain text password/mnemonic available in memory... memory dumps... revealed the plain text... phrase"). This contrasts with the project's own newer keystore CLI code (`KeystoreImport.readPrivateKey`, `KeystoreCliUtils.readPassword`) which reads secrets into `char[]`/`byte[]` and calls `Arrays.fill(..., (byte)0)` / `Arrays.fill(..., '\0')` in `finally` blocks specifically to minimize memory residency: [3](#0-2) 

No equivalent scrubbing exists anywhere in the `LocalWitnesses` / `WitnessInitializer` path — the hex private key stays as a `String` in `privateKeys` for the entire node lifetime and is also re-derived as further intermediate `String`/`byte[]` copies (`getPrivateKey()`, `ByteArray.fromHexString(...)`) each time it's used for address derivation or signing.

### Impact Explanation
The witness/SR private key is the credential that authorizes block production and signing for that Super Representative. An attacker who obtains memory access to the node's host (via a core dump, swap file, cold-boot attack, or another local compromise vector) can recover the plaintext signing key indefinitely for as long as the process runs, since it is never cleared. Compromise of this key allows the attacker to sign/produce blocks as that witness, a direct consensus-integrity impact, which is materially more severe than the wallet-password-disclosure impact described in the original report.

### Likelihood Explanation
Exploitation requires the same precondition as the original report: the attacker must already have some form of memory-read access to the machine (a compromised host, a crash/core dump, or memory-forensics access). Given that precondition, extraction is trivial — the same `strings`-style memory scan used in the original report would recover the raw hex private key, since it is stored as an unencrypted, un-scrubbed `String` for the process's entire lifetime (unlike short-lived, explicitly-zeroed `char[]` buffers used elsewhere in the codebase).

### Recommendation
Store the witness private key as a mutable `byte[]` (derived once via `ByteArray.fromHexString`) instead of retaining the original hex `String`, and scrub it with `Arrays.fill(..., (byte) 0)` once it has been consumed to construct the signing `SignInterface`/`ECKey`. Avoid re-deriving/holding the hex `String` form (`getPrivateKey()`) beyond what is strictly needed for one-time address/key derivation, following the same pattern already used in `KeystoreImport`/`KeystoreCliUtils` (`char[]` + `Arrays.fill` in `finally`).

### Proof of Concept
1. Start a witness node with `config.conf` containing a `localwitness` private key (as parsed by `initFromCFGPrivateKey`) — the key is stored in `LocalWitnesses.privateKeys` as plaintext `String`.
2. While the node is running, trigger a heap/core dump of the JVM process (e.g., `jmap -dump`, or an OS-level core dump / hibernation file capture, mirroring the attacker capability assumed in the original report).
3. Run `strings` on the dump file: the plaintext hex private key is present verbatim, because it was never converted to a scrubbable byte buffer nor cleared, matching the "plain text mnemonic phrase" recovered via `strings` in the original Pontem report.
