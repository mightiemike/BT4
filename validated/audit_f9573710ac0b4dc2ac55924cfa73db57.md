### Title
Unbounded Gzip Decompression in `decompress_program` Allows Decompression-Bomb DoS via RPC Declare V1/estimateFee Path - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
The actual sequencer gateway/mempool admission path for real declare transactions (`crates/apollo_http_server/src/deprecated_gateway_transaction.rs`, `crates/apollo_gateway/src/stateless_transaction_validator.rs`) uses `decode_and_decompress_with_size_limit`, which bounds decompressed output via a `.take(max_size + 1)` reader wrapper before failing with `CompressionError::SizeLimitExceeded`. [1](#0-0) . However, a second, independent decompression helper, `decompress_program`, used to convert a user-submitted deprecated (Cairo0) contract class's gzip+base64 `compressed_program` field into a `Program`, has no such limit and is marked with an explicit `TODO` to add one. [2](#0-1) 

### Finding Description
`decompress_program` base64-decodes attacker-supplied data and feeds it into a `flate2::bufread::GzDecoder`, then calls `read_to_end` on an unbounded `Vec<u8>` with no cap on the number of bytes produced or wall-clock time spent decompressing: [2](#0-1) 

This function is invoked by `user_deprecated_contract_class_to_sn_api`, which converts the `contract_class.program` field of a user-submitted `BroadcastedDeclareV1Transaction` (a Cairo0/deprecated declare transaction submitted through the JSON-RPC `estimateFee` / `simulateTransactions` conversion path): [3](#0-2) 

This is reached from the `TryFrom<BroadcastedDeclareTransaction> for ExecutableTransactionInput` conversion, used for fee estimation of any Declare V1 transaction a caller submits: [4](#0-3) 

A caller controls the `compressed_program` string end-to-end (it is deserialized directly from the JSON-RPC request body as a `String`) [5](#0-4) , so a small (e.g. tens-of-KB) gzip payload crafted with an extreme compression ratio (a "zip bomb") can expand to gigabytes in memory when decompressed by `decompress_program`, with no size or time limit enforced before or during decompression.

This is analogous to the reported Apache Thrift Ruby `THeaderTransport` issue: an externally supplied compressed blob is decompressed without bound, allowing a small input to cause data amplification (the reported bug class — "Improper Handling of Highly Compressed Data").

### Impact Explanation
Every JSON-RPC full node exposing `starknet_estimateFee` / `starknet_simulateTransactions` with a `DECLARE` V1 (deprecated Cairo0) transaction in the batch can be driven to allocate unbounded memory and CPU purely from decompressing a small, attacker-crafted gzip payload, since `decompress_program` performs no `SizeLimitExceeded`-style bound (unlike its sibling `decode_and_decompress_with_size_limit` used elsewhere in the codebase for other class/tx paths). Repeated or concurrent requests can exhaust node memory/CPU, causing request-handling failures, OOM crashes, or severe latency/availability degradation of the RPC service used to serve fee estimation and simulation.

### Likelihood Explanation
Likelihood is high for triggering the resource exhaustion: no signature, fee payment, or state validation gates this code path — it executes purely as part of converting the caller-supplied JSON payload into an `ExecutableTransactionInput` before any nonce/balance/state checks occur, so any unauthenticated RPC caller can send a crafted `BroadcastedDeclareV1Transaction` with a small, highly compressible `program` field.

### Recommendation
Replace the manual `GzDecoder` + unbounded `read_to_end` logic in `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) with the same bounded approach already used by `decompress_with_size_limit` / `decode_and_decompress_with_size_limit` in `crates/starknet_api/src/compression_utils.rs:32-46` — i.e., wrap the decoder in `.take(max_size + 1)` and reject inputs whose decompressed size exceeds a configured maximum (consistent with `max_contract_class_object_size` / `max_sierra_program_size` limits enforced elsewhere), removing the outstanding `TODO(dan): add time and size limits.` comment by actually implementing the limit.

### Proof of Concept
1. Craft a gzip payload that decompresses to several GB from a small compressed size (a classic "zip bomb", e.g. nested/repeated zero-byte streams compressing at extreme ratios).
2. Base64-encode it and place it as the `program` field of a `DEPRECATED_CONTRACT_CLASS` inside a `BROADCASTED_DECLARE_TXN_V1` object.
3. Submit this transaction via `starknet_estimateFee` (or `starknet_simulateTransactions`) to a node's JSON-RPC endpoint.
4. Observe `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671`) allocate unbounded memory while decompressing the payload with no size/time cap, causing high memory/CPU consumption or an OOM condition on the serving node — reproducible repeatedly/concurrently for a denial-of-service effect.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.
    let mut decoder = GzDecoder::new(compressed_data.as_slice());
    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}
