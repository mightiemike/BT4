### Title
Internal session-storage error messages disclosed in HTTP responses - (File: `packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts`)

### Summary
In `shopify-app-express`, the auth-code-flow branch of `validateAuthenticatedSession` catches errors thrown by `api.session.getCurrentId(...)` and `config.sessionStorage.loadSession(...)` and sends the raw `error.message` directly back to the requester in the HTTP response body, instead of returning a generic error message.

### Finding Description
When a request hits `validateAuthenticatedSession()` on the (non-token-exchange) auth-code-flow path, two failure modes propagate the underlying exception's message verbatim to the client:

- `handleSessionError` sends `error.message` for any non-`InvalidJwtError` thrown while resolving the session id: [1](#0-0) 
- The `loadSession` catch block sends `error.message` with a 500 status when the session storage layer throws: [2](#0-1) 

This is confirmed by the existing test asserting the storage error text is echoed verbatim to the HTTP client: [3](#0-2) 

This mirrors the bug class in the referenced Zebra fix (surfacing a storage-engine's raw error text, e.g. `"IO error: No space left on device"`) — except here the message is exposed to the requesting HTTP client rather than to a trusted operator log. Depending on the `SessionStorage` implementation in use (Postgres/MySQL/SQLite/Prisma/Drizzle/Redis adapters under `packages/apps/session-storage/`), driver-level errors can include internal details such as connection strings, table/column names, file paths, or query fragments, all of which would be reflected straight into the response body.

### Impact Explanation
An unauthenticated or minimally-authenticated caller (any request reaching this Express middleware with a session id that triggers a storage exception — e.g., transient DB outage, malformed/oversized session id causing a driver error, connection-pool exhaustion) receives the storage engine's internal error text in the response. This is an information-disclosure issue: it can leak infrastructure details (DB engine, connection info fragments, file paths) that aid further attacks, and unlike server logs, it is exposed to the client without any authorization check. Severity is moderate (information disclosure, not direct account/session takeover).

### Likelihood Explanation
Triggering the `loadSession` failure only requires the app's session storage backend to throw during a request that carries (or lacks) a session id — this can happen under ordinary operational conditions (DB downtime, network blips, pool exhaustion) or could potentially be induced by supplying crafted session ids/cookies that cause the storage driver to error. Because `validateAuthenticatedSession` runs on essentially every protected route for auth-code-flow embedded/non-embedded apps, the failure path is broadly reachable from any external request, making likelihood non-trivial though dependent on backend faults being reachable/inducible.

### Recommendation
Do not forward `error.message` to the HTTP client in `handleSessionError` or the `loadSession` catch block. Log the full error server-side (as is already done via `config.logger.error`) and return a generic, fixed message (e.g., `"Internal Server Error"`) with the appropriate status code, consistent with how `perform-token-exchange.ts` already handles equivalent failures generically. [4](#0-3) 

### Proof of Concept
1. Configure a `shopify-app-express` app using the auth-code-flow (token exchange disabled) with any `SessionStorage` adapter.
2. Cause the backing store to throw during `loadSession` (e.g., stop the database, or supply a session id value that causes the underlying driver to error).
3. Send a request with a valid-looking Authorization Bearer JWT or existing cookie targeting a route protected by `validateAuthenticatedSession()`.
4. Observe the 500 response body contains the raw driver/storage exception message instead of a generic error, as reproduced by the existing test: [3](#0-2) 

Note: I could not fully verify every code path leading into `getCurrentId`/`loadSession` failures for non-Bearer (cookie-based) requests within the available indexed content — the `session-utils.ts`/`get-current-id` implementation details were not retrieved before the tool budget ran out, so the precise set of externally-triggerable storage-error conditions beyond the demonstrated test case is not fully confirmed.

function handleSessionError(_req: Request, res: Response, error: Error) {
  switch (true) {
    case error instanceof InvalidJwtError:
      res.status(401);
      res.send(error.message);
      break;
    default:
      res.status(500);
      res.send(error.message);
      break;
  }
}
