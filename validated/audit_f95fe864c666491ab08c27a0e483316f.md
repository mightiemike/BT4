### Title
Unhandled exception in `sanitizeHost` from malformed decoded `host` parameter crashes admin authentication path before authentication - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates the `host` query parameter's character set with a base64 regex, then blindly passes the base64-decoded value into `new URL('https://' + decodeHost(sanitizedHost))` with no `try/catch`. Because the base64 regex only constrains the *encoded* form, an attacker can craft a base64 string that decodes into a value containing a forbidden host code point (e.g. a space), which causes the WHATWG `URL` constructor to throw a `TypeError` instead of `sanitizeHost` returning `null` or throwing the expected `InvalidHostError`.

### Finding Description
`sanitizeHost` in [1](#0-0)  does:
```js
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
  ...
``` [2](#0-1) 

`decodeHost` is a trivial `atob(host)` wrapper with no further sanitization: [3](#0-2) . The `base64regex` (`/^[0-9a-zA-Z+/]+={0,2}$/`) only validates that the *encoded* string is well-formed base64 — it says nothing about the decoded bytes. An attacker can choose an arbitrary decoded string (e.g. `"exa mple.com"`, containing a raw space) and base64-encode it; this passes the regex and `atob`, but when concatenated into `https://exa mple.com` and passed to `new URL(...)`, the WHATWG URL parser detects a forbidden host code point (space is on the forbidden-host-code-point list) and throws `TypeError: Invalid URL`. There is no `try/catch` around this call in `sanitizeHost`, so the exception propagates uncaught out of the function, contrary to the function's documented/expected contract of returning `null` (or throwing the library's own `InvalidHostError`) for invalid input.

This function is called directly on attacker-supplied, pre-authentication query parameters in multiple app-facing entry points, e.g.:
- `validateShopAndHostParams` in the Remix/React Router admin authentication helpers, called before session/HMAC validation completes: [4](#0-3) 
- `redirectWithExitIframe`, part of the embedded-app exit-iframe redirect flow: [5](#0-4) 
- `redirectToAuth`'s `clientSideRedirect` in `shopify-app-express`: [6](#0-5) 

None of these call sites wrap `sanitizeHost` in a `try/catch`, so they rely entirely on `sanitizeHost` returning `null` for bad input, per its own documented contract of validation. The existing test suite only exercises inputs that are either valid base64/valid host, or invalid base64 charset, or valid host string but wrong domain — it never fuzzes decoded content containing forbidden host code points, so this failure mode is not covered: [7](#0-6) .

### Impact Explanation
This is a scoped denial-of-service in an authentication-adjacent handler: an unauthenticated attacker can throw an uncaught `TypeError` inside `sanitizeHost`, which is invoked from admin-authentication and OAuth-redirect code paths before any session/HMAC verification. Depending on the host framework's error handling, this surfaces as at minimum an unhandled 500 for that request; in the worst case (frameworks/adapters that do not catch synchronous throws from within these particular call sites), it can produce an unhandled promise rejection/crash of the request-handling process. This matches the "DoS in an authentication handler" impact class permitted by the audit scope.

### Likelihood Explanation
High feasibility and full repeatability: the endpoint is reachable pre-authentication with a single unauthenticated GET request containing `shop=<valid-shop>.myshopify.com&host=<base64 of a string containing a forbidden host code point>`. No secrets, no privileged role, and no non-default configuration are required — this occurs under default library configuration.

### Recommendation
Wrap the `new URL(...)` construction in `sanitizeHost` in a `try/catch`, returning `null` (or throwing `InvalidHostError` when `throwOnInvalid` is set) on any parse failure, so malformed decoded host values are always treated as invalid input rather than causing an uncaught exception:
```js
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  try {
    const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
    ...
  } catch {
    sanitizedHost = null;
  }
}
```

export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;

    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);

      const originsRegex = [
        'myshopify\\.com',
        'shopify\\.com',
        'myshopify\\.io',
        'spin\\.dev',
        'shop\\.dev',
      ];

      if (config.domainTransformations) {
        const hostTransformationDomains = config.domainTransformations
          .filter((t) => t.includeHost !== false)
          .flatMap((t) =>
            getTransformationDomains({
              ...config,
              domainTransformations: [t],
            }),
          );
        originsRegex.push(...hostTransformationDomains);
      }

      const hostRegex = new RegExp(`\\.(${originsRegex.join('|')})$`);
      if (!hostRegex.test(hostname)) {
        sanitizedHost = null;
      }
    }
    if (!sanitizedHost && throwOnInvalid) {
      throw new InvalidHostError('Received invalid host argument');
    }

    return sanitizedHost;
  };
```
