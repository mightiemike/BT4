## Local proof-integrity gap: `ensure_match_transaction_info` never validates state-checkpoint roots during replay verification

### Title
Replay-verify path accepts execution whose committed state/hot-state/position-state checkpoint roots diverge from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole integrity check used by the chunk-executor's replay-verification path (`verify_execution` in `execution/executor/src/chunk_executor/mod.rs`) to confirm a locally re-executed transaction output actually matches the trusted, proof-carrying `TransactionInfo` fetched from a backup or archive. This function checks status, gas, write-set hash, and event root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — a gap that is even flagged by an unresolved `TODO(trading-native)` comment in the code itself.

### Finding Description
`ensure_match_transaction_info` validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed event root vs `txn_info.event_root_hash()` [1](#0-0) 

It then returns `Ok(())` without ever comparing the locally-computed Sparse-Merkle-Tree state-checkpoint root, hot-state checkpoint root, or the position-state checkpoint root against the corresponding fields carried in the authenticated `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), which is called out directly in the surrounding comment: [2](#0-1) 

This function is the only check performed in the `verify_execution` path used by `db-tool`'s `replay-verify`/`replay_on_archive` tooling: [3](#0-2) 

This differs from the normal commit/chunk-apply path (`update_ledger`), where `DoStateCheckpoint` is fed `known_state_checkpoints`/`known_position_state_checkpoints` derived from the trusted `TransactionInfo`s and explicitly `ensure!`s that the locally computed root matches the known one: [4](#0-3) [5](#0-4) 

So the state-checkpoint root **is** cross-checked when transactions are actually applied/committed through `update_ledger`, but the independent `verify_execution` code path — whose entire purpose is to authenticate replayed execution against backup data ahead of/instead of a full commit (used for auditing archival replay, e.g. `replay_on_archive`) — silently omits this check for all three checkpoint-hash fields.

### Impact Explanation
If local re-execution during replay-verification produces a different Sparse-Merkle-Tree/hot-state/position-state root than what is committed in the authenticated `TransactionInfo` (e.g., due to a state-view divergence, a bug in state-checkpoint construction, or divergent trading-native position accounting once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled), `ensure_match_transaction_info` returns `Ok(())` regardless. Replay-verify tooling that relies on this function (per the code's own comment, `db-tool`'s `replay_on_archive`) would report a "successful replay" even though the authenticated state root has silently diverged from what local execution actually produced. This defeats the entire purpose of replay-verification as an integrity check on historical/archival state commitments — a state-commitment/proof-integrity guarantee that the task's gate explicitly calls out ("Committed state that differs from the correct VM result... accepted as valid").

### Likelihood Explanation
This is not a remotely triggerable consensus-safety bug (the normal commit path still validates checkpoint hashes via `DoStateCheckpoint`), so it doesn't cause an incorrect ledger to be committed by validators. Its likelihood/severity is scoped specifically to the replay-verification/auditing tool path and is highest once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/trading-native position-state roots are enabled, since that is exactly the scenario the TODO warns about; any latent divergence in position-state root computation would go undetected by this specific verification.

### Recommendation
In `ensure_match_transaction_info` (`types/src/transaction/mod.rs`), compute the local state-checkpoint hash(es) (state, hot-state, and position-state, when applicable/available) and add `ensure!` comparisons against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, matching the same validation already performed in `DoStateCheckpoint::get_state_checkpoint_hashes`, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled in production, as the existing TODO instructs.

### Proof of Concept
Not independently exploitable in a PoC sense without a concrete divergence-inducing bug in state-checkpoint computation; the finding is a structural verification gap proven directly by the code:
1. `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2203`) never reads/compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.
2. `verify_execution` (`execution/executor/src/chunk_executor/mod.rs:648-706`) calls only this function to validate replayed output against trusted `TransactionInfo`.
3. Contrast with `update_ledger`'s use of `known_state_checkpoints`/`known_position_state_checkpoints` and `DoStateCheckpoint`'s `ensure!` check at `do_state_checkpoint.rs:213-219`, proving the intended invariant exists elsewhere but is absent from the replay-verify path.

**Uncertainty note:** I could not fully trace whether any other guard (outside `ensure_match_transaction_info`) is layered on top in the `db-tool replay-verify` CLI command itself, since that CLI entry point wasn't reached within available searches; it's possible (though not shown by any code found) that an additional checkpoint-hash check exists elsewhere in that specific tool wrapper. This should be verified before treating the gap as fully unmitigated in that particular tool's invocation path.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
