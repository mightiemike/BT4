### Title
Unmetered gasless `MsgExecutePayload` admission enables unprivileged, cost-free transaction-spam DoS - (File: `app/txpolicy/gasless.go`, `app/ante/fee.go`, `app/cosmos/min_gas_price.go`, `app/ante/account_init_decorator.go`)

### Summary
The external report's core bug class is: a protocol exposes a rate-limited/gated resource (mint/redeem windows) to *any* caller with no cost, so an attacker exhausts the window and denies the resource to everyone else. Push Chain's gasless-transaction admission path has the same structural flaw in a stronger form: `MsgExecutePayload` — a message any unprivileged account may submit — is fee-exempt, min-gas-price-exempt, and even account-creation-exempt, with **no rate limit, quota, or per-window cap at all**. An attacker can flood blocks with free `MsgExecutePayload` transactions, consuming validator CPU/signature-verification and block gas space that legitimate UV votes and paid users compete for, with zero token cost.

### Finding Description
`app/txpolicy/gasless.go:IsGaslessTx` [1](#0-0)  whitelists `MsgExecutePayload` as gasless, and per `x/uexecutor/README.md`, this message can be submitted by **any** account, not just bonded Universal Validators: [2](#0-1) 

Three ante decorators cooperate to make this fully free:
- `DeductFeeDecorator` skips fee deduction entirely for gasless txs [3](#0-2) 
- `MinGasPriceDecorator` skips the FeeMarket minimum-gas-price check for gasless txs [4](#0-3) 
- `AccountInitDecorator` will even create a brand-new on-chain account mid-pipeline for a gasless tx signer that doesn't exist yet, requiring only a valid signature over `account_number=0, sequence=0` — no funding, no existing balance [5](#0-4) 

`MsgExecutePayload` itself only requires syntactically well-formed fields (`ValidateBasic`) — a non-empty hex `VerificationData`, a non-nil `UniversalAccountId`/`UniversalPayload` — none of which requires the signer to control real funds or a real UEA: [6](#0-5) 

`ms.k.ExecutePayload` then invokes `CallUEAExecutePayload`, a real `DerivedEVMCall` (`commit=true`) against the UEA contract, meaning the node performs full EVM signature-recovery/verification and state simulation work for every submitted payload, even one that is guaranteed to revert: [7](#0-6) 

Because an attacker can generate unlimited throwaway keypairs off-chain for free, sign one dummy `MsgExecutePayload` per key (satisfying `AccountInitDecorator`'s account_number=0/sequence=0 signature check), and repeat indefinitely, there is no economic or state-based limiter (no per-address counter, no per-block cap on gasless messages, no `resetMintDuration`-style throttle analog) preventing them from saturating block gas and validator CPU with these transactions — exactly the "cheap/free repeated action exhausts a shared, unthrottled resource" pattern from the external report, except here there isn't even a throttle to legitimately max out; the resource is simply unmetered.

### Impact Explanation
An unprivileged attacker with no funds can submit unbounded volumes of free, valid-looking `MsgExecutePayload` transactions. Each one forces the node to run full ante-chain signature verification (including the `AccountInitDecorator`'s custom signature check) and a real EVM `DerivedEVMCall` against a UEA contract. This crowds out block space and CPU that legitimate gasless UV-vote messages (`MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, TSS votes) and paying EVM/Cosmos users depend on, degrading or halting timely inbound/outbound finalization and normal user transaction throughput — a chain-level, non-network-layer DoS reachable purely through the ordinary user-facing `MsgExecutePayload` submission path, with no privileged actor required.

### Likelihood Explanation
High. No capital is required (no fee, no min gas price, no funded account) and no privileged role is needed — any address, including a freshly generated one created for free by `AccountInitDecorator`, can submit `MsgExecutePayload`. The only "cost" to the attacker is CPU to sign transactions, which is far cheaper than the CPU cost the transaction imposes on every validator that must verify it and execute the EVM call. The mempool/mempool-priority ordering that typically limits spam via fee-based priority does not apply here, since these transactions carry zero fee by design.

### Recommendation
- Introduce a rate limit / quota for gasless message submission analogous to (but correctly bounded, unlike) `TimeBasedRateLimiter` — e.g., a per-address or global cap on `MsgExecutePayload` submissions per block/time-window, independent of the UEA-level nonce/signature checks.
- Consider requiring a minimal anti-spam bond or a lightweight proof-of-work/CAPTCHA-equivalent for `MsgExecutePayload` submitted by non-UV signers, or bill a small gas cost to the *signer* (not the UEA) for malformed/reverting payloads so signature-verification failures aren't free.
- Cap the number of new gasless-tx-triggered account creations (`AccountInitDecorator`) processed per block, since this is the cheapest amplification vector (unlimited throwaway keys).
- Ensure `evmante.NewGasWantedDecorator`/FeeMarket-style block gas accounting is enforced uniformly regardless of the `gasless` flag so a flood of gasless txs cannot exceed a reasonable share of block gas.

### Proof of Concept
1. Generate N ECDSA/ed25519 keypairs (`k_1..k_N`), each with no on-chain account and no balance.
2. For each `k_i`, construct a `MsgExecutePayload` with a syntactically valid but functionally meaningless `UniversalAccountId`/`UniversalPayload` (e.g., pointing at a non-existent or arbitrary UEA) and a non-empty (but incorrect) `VerificationData` hex string, satisfying `ValidateBasic`.
3. Sign each message under `account_number=0, sequence=0` per `AccountInitDecorator.verifySignatureForNewAccount`.
4. Broadcast all N transactions. `IsGaslessTx` classifies each as gasless; `DeductFeeDecorator` and `MinGasPriceDecorator` both bypass fee/min-gas checks; `AccountInitDecorator` creates a fresh account for each and lets the tx proceed to `ExecutePayload`, which performs a full `DerivedEVMCall`/`executeUniversalTx` attempt (reverting due to bad `VerificationData`, but only after the EVM has done the work).
5. Repeat with new keypairs indefinitely — the attacker pays nothing per transaction while validators bear full verification and execution cost each time, with no counter-measure capping the volume.

func IsGaslessTx(tx sdk.Tx) bool {
	var (
		// GaslessMsgTypes defines the message types that are allowed in gasless transactions
		GaslessMsgTypes = []string{
			sdk.MsgTypeURL(&uexecutortypes.MsgMigrateUEA{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgExecutePayload{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteInbound{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteOutbound{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteTssKeyProcess{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteFundMigration{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteChainMeta{}),
		}
	)

	msgs := tx.GetMsgs()
	if len(msgs) == 0 {
		return false
	}

	for _, msg := range msgs {
		switch m := msg.(type) {
		case *authz.MsgExec:
			// Only gasless if ALL inner messages are allowed
			for _, innerMsg := range m.Msgs {
				if !slices.Contains(GaslessMsgTypes, innerMsg.TypeUrl) {
					return false
				}
			}
		default:
			if !slices.Contains(GaslessMsgTypes, sdk.MsgTypeURL(msg)) {
				return false
			}
		}
	}
	return true
}

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.

func (msg *MsgExecutePayload) ValidateBasic() error {
	// Validate signer
	if _, err := sdk.AccAddressFromBech32(msg.Signer); err != nil {
		return errors.Wrap(err, "invalid signer address")
	}

	// Validate universalAccountId
	if msg.UniversalAccountId == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal account cannot be nil")
	}

	// Validate universal payload
	if msg.UniversalPayload == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal payload cannot be nil")
	}

	// Validate verificationData
	if len(msg.VerificationData) == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "verificationData cannot be empty")
	}
	if _, err := hex.DecodeString(strings.TrimPrefix(msg.VerificationData, "0x")); err != nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "invalid verificationData hex")
	}

	// Validate universalAccountId structure
	if err := msg.UniversalAccountId.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universalAccountId")
	}

	// Validate universal payload structure
	if err := msg.UniversalPayload.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universal payload")
	}

	return nil
}
