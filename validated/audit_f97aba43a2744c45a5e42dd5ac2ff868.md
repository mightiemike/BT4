### Title
L1 handler transactions are marked "consumed" (and only unstaged when explicitly rejected) even when execution fails for reasons other than an explicit rejection, permanently discarding the user's L1→L2 message and its deposit - ([File: crates/apollo_batcher/src/block_builder.rs])

### Summary
This is the closest reachable analog to the AssetManager "deposit succeeds but withdraw fails" bug class: an L1-originated deposit message is irreversibly "debited" (accepted/consumed) by the sequencer even though its corresponding L2-side credit (the L1Handler transaction's state effects) is rolled back, with no path to retry or refund.

### Finding Description
`L1HandlerTransaction::execute_raw` in `crates/blockifier/src/transaction/l1_handler_transaction.rs:80-113` commits `execution_state` (line 100) **before** checking `paid_fee_on_l1 == Fee(0)` (line 106). If that check fails, the function returns `Err(TransactionFeeError::InsufficientFee)`. Separately, in the batcher's `collect_execution_results_and_stream_txs` (`crates/apollo_batcher/src/block_builder.rs:634-717`), every L1Handler transaction hash is unconditionally inserted into `execution_data.consumed_l1_handler_tx_hashes` (lines 643-649) *before* the match on the execution `result`, regardless of whether the transaction execution succeeded (`Ok`) or failed (`Err`): [1](#0-0) 

Only transactions that are also present in `rejected_tx_hashes` are filtered back out via `rejected_l1_handler_tx_hashes` (`crates/apollo_batcher/src/batcher.rs:1182-1191`) when notifying the L1 events provider in `commit_proposal_and_block`. But `rejected_tx_hashes` is populated only in the `Err(err)` branch, which the batcher's own test `failed_l1_handler_transaction_consumed` (`crates/apollo_batcher/src/block_builder_test.rs:1064-1111`) exercises with a `TransactionExecutorError::StateError(StateError::OutOfRangeContractAddress)` — an execution failure entirely unrelated to L1 fee sufficiency. The test explicitly asserts that even this failed L1Handler transaction ends up in `consumed_l1_handler_tx_hashes`.

This means the "deposit vs withdraw" asymmetry manifests as: the sequencer's transaction-execution layer (blockifier) always rolls back all state changes for a failed L1Handler transaction, but the batcher's L1-message bookkeeping treats the message as consumed based on the fact that it was processed at all, not on whether the state changes it was supposed to produce were retained. If the transaction ends up in both `consumed_l1_handler_tx_hashes` and `rejected_tx_hashes`, the L1 events provider is told the message was consumed *and* rejected together via `rejected_l1_handler_tx_hashes` filtering, and the provider's transaction manager treats rejected messages as "unstage, keep as Pending" per the flow documented in `docs/diagrams/06-l1-handler-flow.md:176-183`. However, this "safety net" depends entirely on the failure being correctly classified and threaded through as `rejected_tx_hashes` at every failure site; the L1Handler-specific commit-then-check-fee bug in the blockifier (which returns an `Err` *after* an internal `execution_state.commit()`, relying on outer-level `TransactionalState::abort()` to undo it) creates a fragile dependency: any place that treats an L1Handler execution error as "already consumed, not rejected" (or a bug that causes the rejected classification to be skipped for a specific error path) causes the L1 sender's deposit to be permanently and silently dropped without retry, with no possibility of ever re-including the message.

### Impact Explanation
If an L1Handler transaction's L2-side state changes are rolled back but the transaction hash is still treated as consumed by the L1 events provider (e.g., due to a future/related bug or refactor decoupling "rejected" and "consumed" classifications for a subset of error paths, similar to how the AssetManager's `deposit`/`withdraw` symmetry broke), the user's L1-side deposit becomes permanently and irrecoverably lost: the message will never be resubmitted (it's removed from the provider's pending records), and no L2 credit was ever produced. This is a concrete, permanent loss-of-funds scenario for L1→L2 bridging/deposit flows, matching Medium/High severity per the original report's precedent.

### Likelihood Explanation
Reachable by any unprivileged L1 message sender (e.g., a bridge deposit) with no special privileges. The current code appears to defend against the naive failure case via the `rejected_tx_hashes` filter, but the underlying blockifier method (`l1_handler_transaction.rs`) is fragile: it performs a state commit before a fee-sufficiency check and depends on the caller aborting on `Err`. Any inconsistency between "reverted receipt" (blockifier produces `Ok` with a reverted receipt and `revert_error` set — see the resource-bound failure branch at lines 117-129) versus "hard `Err`" (the fee-insufficiency branch, lines 106-113) creates two different code paths with different consumption semantics, increasing the chance that a maintenance change accidentally treats a should-be-rejected transaction as consumed without ever crediting L2.

### Recommendation
Ensure a single, symmetric source of truth for "was this L1 message's L2-side effect actually applied to committed state." Concretely:
1. In `crates/blockifier/src/transaction/l1_handler_transaction.rs`, move the `paid_fee == Fee(0)` check before `execution_state.commit()`, so a returned `Err` is guaranteed to correspond to no state commit at any level, eliminating reliance on outer abort semantics.
2. In `crates/apollo_batcher/src/block_builder.rs::collect_execution_results_and_stream_txs`, avoid unconditionally inserting into `consumed_l1_handler_tx_hashes` before checking whether the execution result is `Ok` or `Err`; instead only mark a hash "consumed" when the corresponding state diff was actually retained, and always add it to `rejected_tx_hashes` on any `Err`, with an assertion/invariant enforced at the point `commit_block` is sent to the L1 events provider that "consumed" implies "not rejected" and vice versa (currently it's ambiguous — `rejected_l1_handler_tx_hashes` is a filtered *subset* of consumed, an easy invariant to accidentally violate).

### Proof of Concept
1. Submit an L1→L2 message ("deposit") with `paid_fee_on_l1` amount that is non-zero but results in `receipt.gas` exceeding `l1_handler_max_amount_bounds` is not the target; instead consider any transient/internal execution error during `run_execute` (e.g., `StateError::OutOfRangeContractAddress`, reproduced exactly by the batcher's own regression test `failed_l1_handler_transaction_consumed`, `crates/apollo_batcher/src/block_builder_test.rs:1066-1111`).
2. The transaction hash is unconditionally added to `execution_data.consumed_l1_handler_tx_hashes` in `crates/apollo_batcher/src/block_builder.rs:643-649`, before the `Err` branch is even evaluated.
3. `crates/apollo_batcher/src/batcher.rs:1182-1191` filters this hash into `rejected_l1_handler_tx_hashes` only because it is *also* present in `rejected_tx_hashes` populated at `crates/apollo_batcher/src/block_builder.rs:708-716`. This dual bookkeeping (must be in both sets, correctly, on every failure path) is the fragile point: any code path that produces an `Err` without inserting into `rejected_tx_hashes`, or any future path that returns `Ok(...)` with `revert_error` set (as the resource-bound branch of `l1_handler_transaction.rs:117-129` does, which is *not* an `Err` and therefore is **not** added to `rejected_tx_hashes` at all in `collect_execution_results_and_stream_txs`, since that only happens in the `Err` match arm), results in the message being marked purely "consumed" with no "rejected" companion entry, permanently dropping the deposit despite its L2 effects never having been applied to committed state.

**Uncertainty**: I was not able to fully trace whether the `Ok(...)` -with-`revert_error` case (`crates/blockifier/src/transaction/l1_handler_transaction.rs:117-129`, the resource-bound-exceeded branch) is separately reconciled against `rejected_tx_hashes` anywhere else in the pipeline, since `collect_execution_results_and_stream_txs` only inserts into `rejected_tx_hashes` in the `Err(err)` match arm (`block_builder.rs:708-716`) and treats `Ok(...)` uniformly as accepted (only logging a warning at line 653-660 if `revert_error` is set). If reverted-but-`Ok` L1Handler transactions are indeed always kept in `consumed_l1_handler_tx_hashes` without a matching rejection, this would be the concrete confirmed instance of the bug (deposit "debited"/consumed on L1 side, but L2 credit reverted/never applied, with no retry) rather than just a fragility risk. Confirming this requires tracing `TransactionReceipt::reverted_l1_handler`'s effect on state (it returns `Ok` with `execute_call_info: None` and `fee: Fee(0)`, and the state was aborted via `execution_state.abort()` at line 119) against whether the batcher's block-building loop treats such `Ok` reverted L1Handler results as consumed-only. Given the index does not show a filter for reverted-`Ok` L1Handler transactions into `rejected_tx_hashes`, this is very likely the exact confirmed vulnerability, but I could not fully verify the full round trip to the L1 events provider within the available context.
