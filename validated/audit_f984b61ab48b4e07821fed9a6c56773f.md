### Title
Individual liquidation debt-repay funds are stranded when `liquidate-multi` swallows a downstream failure in `liquidate` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` batches liquidations by calling the public `liquidate` function directly (not via `contract-call?`) and collecting each result with `map`, explicitly documented as tolerating individual failures without reverting the whole batch. Because `liquidate` pulls the liquidator's repayment tokens into the vault (`vault-system-repay`) *before* it removes the borrower's debt obligation and seizes/transfers collateral, a failure in either of those later `try!` steps causes `liquidate` to return `(err ...)`, which `liquidate-multi` absorbs as a normal list element instead of propagating. Since the top-level `liquidate-multi` transaction still commits `(ok ...)`, the already-executed debt repayment (a completed `contract-call?` sub-transaction) is never rolled back, while the offsetting debt-obligation removal / collateral seizure for that position never happens. The liquidator's repayment funds are stranded with no refund path - the same class of bug as the ZetaChain report: a multi-step operation where an early step's transfer commits, a later step aborts, and the entry point marks/records the failure instead of reverting or refunding.

### Finding Description
`liquidate` is defined as a `define-public` function and is invoked as an ordinary function call (not `contract-call?`) from the batch helper `call-liquidate`: [1](#0-0) 

`liquidate-multi` collects the results of each position with `map` and always returns `(ok ...)` at the top level, explicitly documenting that failed entries do not revert the batch: [2](#0-1) 

Inside `liquidate`, the execution order is: preconditions/slippage asserts, then `vault-system-repay` (pulls the liquidator's debt tokens and repays the vault) via `try!`, and only afterward `debt-remove-scaled` and `collateral-remove` (both `contract-call?` into `.v0-market-vault`), also gated by `try!`: [3](#0-2) 

Per Clarity's execution model, a `contract-call?` that succeeds is committed as soon as it returns `(ok ...)`; it is only rolled back if the *top-level* transaction ultimately returns `(err ...)`. Because `liquidate` is called as a plain function (no `contract-call?` boundary) from `call-liquidate`, and `liquidate-multi` deliberately swallows any `(err ...)` produced by an individual `liquidate` invocation via `map`/`(ok (map ...))`, the top-level transaction still commits successfully even when one position's `liquidate` fails partway through. Any state already committed earlier in that failed `liquidate` invocation - specifically the `vault-system-repay` transfer of the liquidator's tokens into the vault - is not undone, while the corresponding `debt-remove-scaled` (reducing the borrower's obligation) and/or `collateral-remove` (paying the liquidator their seized collateral) never execute for that position.

### Impact Explanation
The liquidator's repayment funds are transferred into the vault but the liquidator receives neither the offsetting collateral nor an accounting reduction of the borrower's debt for that failed leg, and there is no refund mechanism in `liquidate` or `liquidate-multi` for this case. This is a direct, permanent loss of the liquidator's funds with no path to recovery from within the protocol, matching the Critical impact bar (direct theft/permanent freezing of user funds).

### Likelihood Explanation
This requires only that a single position within a `liquidate-multi` batch fail on its `debt-remove-scaled` or `collateral-remove` step after `vault-system-repay` has already succeeded - e.g., a stale/no-longer-valid `min-collateral-expected`/scaled-debt state for a position that was already partially modified earlier in the same batch, or any other condition causing those later `try!` calls to error. Given `liquidate-multi` is a standard permissionless liquidator entry point and the comment at line 1592 confirms per-position failures are an accepted/expected outcome of the design, the interleaving is realistically reachable, not a contrived edge case.

### Recommendation
Either (a) make `liquidate-multi` propagate failures as a full batch abort (revert on any single failure), restoring Clarity's normal atomicity guarantee, or (b) wrap each individual `liquidate` call in its own isolated `contract-call?` boundary so a failure fully rolls back that position's `vault-system-repay` transfer along with the rest of its state changes, ensuring no partial, uncompensated fund movement can be committed for a position whose overall liquidation attempt fails.

### Proof of Concept
1. Liquidator submits `liquidate-multi` with two positions, where the second position's expected collateral/debt state depends on results that change after the first position in the same batch is processed (e.g., same borrower/asset, or a value computed from cached indexes that shift between calls).
2. For the first position, `liquidate` executes successfully end-to-end.
3. For the second position, `vault-system-repay` succeeds (liquidator's tokens are pulled into the vault) at [4](#0-3) , but the subsequent `debt-remove-scaled`/`collateral-remove` call fails and returns `(err ...)` via `try!`.
4. `call-liquidate` returns this `(err ...)` for the second position; `liquidate-multi`'s `(ok (map call-liquidate positions))` at [5](#0-4)  still returns `(ok ...)` overall, so the transaction commits.
5. The liquidator's debt-token repayment for the second position is now stuck in the vault with no compensating collateral or debt-reduction, and no protocol function exists to refund it.
