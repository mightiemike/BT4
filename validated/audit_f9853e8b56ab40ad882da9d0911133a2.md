## Analysis: Gasless Admission Path — Zero-Cost Spam of `MsgExecutePayload`

The strongest analog to the Audius "cheap dust delegator fills a rate-limited resource for free" bug-class in this repo is in the **gasless admission path** (`app/txpolicy/gasless.go`, `app/ante/fee.go`, `app/cosmos/min_gas_price.go`, `app/ante/account_init_decorator.go`), rather than in ballot/TSS/registry code (those resources — `Ballots.EligibleVoters`, `UniversalValidatorSet`, `TokenConfigs` — are either admin-curated or validator-driven, not attacker-fillable by an unprivileged party, so the Audius pattern does not transfer there).

### Title
Zero-cost spam of `MsgExecutePayload` via the gasless whitelist lets an unprivileged attacker force free EVM execution on every validator - ([File: app/txpolicy/gasless.go])

### Summary
`MsgExecutePayload` is in the gasless whitelist and can be submitted by "any" signer [1](#0-0) [2](#0-1) . Both `DeductFeeDecorator` and `MinGasPriceDecorator` unconditionally skip fee/min-gas-price checks whenever `IsGaslessTx(tx)` is true, independent of whether the account already exists [3](#0-2) [4](#0-3) . `AccountInitDecorator` additionally lets a brand-new signer bootstrap an on-chain account for free the first time, requiring only a valid signature over `account_number=0, sequence=0` — no balance, no stake, no bonded-validator check [5](#0-4) . Because `MsgExecutePayload` is gasless indefinitely (the whitelist check is purely by message type, not one-time), a single funded-free attacker account can submit unlimited `MsgExecutePayload` transactions, each dispatching a real `DerivedEVMCall`/`CallUEAExecutePayload` on every validator (with an attacker-chosen `gasLimit`) [6](#0-5) , at zero economic cost.

### Finding Description
The Audius vulnerability exploited an admission control that was priced "per delegator" but not properly bounded against splitting across many cheap slots, letting an attacker occupy all of a shared, rate-limited resource for a bargain price. Push Chain's gasless admission has the analogous structural flaw: it treats `MsgExecutePayload` as *always* gasless (any signer, any account state) instead of gasless only for the narrow bootstrap case it was designed for (letting a fresh UV hot key or UEA owner get their first payload in without pre-funding). Combined:

1. `IsGaslessTx` classifies `MsgExecutePayload` as gasless for every invocation, not just the first [2](#0-1) .
2. `DeductFeeDecorator.AnteHandle` returns early (no fee deducted, no balance required) whenever `IsGaslessTx` is true [3](#0-2) .
3. `MinGasPriceDecorator.AnteHandle` likewise skips the minimum-fee check for gasless messages [4](#0-3) .
4. `AccountInitDecorator` lets the attacker mint the very first account used to submit these messages without ever holding a balance, only requiring a self-signed signature [7](#0-6) .
5. The dispatched message handler for `MsgExecutePayload`, `ExecutePayloadV2`, always performs a real EVM call (`CallUEAExecutePayload`) with the payload's attacker-supplied `gasLimit` before any authorization is checked cryptographically inside the UEA contract [8](#0-7) ; the design doc itself confirms authorization is enforced only deep inside the EVM call (UEA contract signature check), after the module has already spent CPU/EVM-gas resolving the factory and dispatching the call [9](#0-8) .

The `Signer` need not equal, or even correspond to, a real `UniversalAccountId.Owner` [10](#0-9) ; an attacker can supply arbitrary/garbage `UniversalAccountId` and `VerificationData` values. The EVM call will revert deep inside the UEA contract, but every validator has already spent computation dispatching it, and the entire transaction was submitted, propagated, and processed for $0.

### Impact Explanation
An unprivileged attacker who needs only a single self-funded (0-balance) keypair can submit an unbounded stream of gasless `MsgExecutePayload` transactions, each forcing every honest validator to perform a real `DerivedEVMCall` at an attacker-chosen gas limit, without ever paying a Cosmos fee or an EVM gas price. This is a denial-of-service vector reachable purely through the default transaction submission path — it does not require any privileged role, malicious validator, or malicious peer. Sustained abuse can consume block gas/computation budget that would otherwise go to legitimate inbound/outbound/ballot processing, degrading the chain's material throughput for honest UEA users and Universal Validators. This falls within the allowed "denial of service ... not network-level ... reachable without privileged control" impact category, and is rooted specifically in the "custom ante or gasless transaction controls" scope area.

### Likelihood Explanation
High. No stake, bonding, admin approval, or capital outlay is required — only knowledge of the public gasless whitelist and the ability to sign a Cosmos transaction with a fresh or existing key. The relevant code paths (`IsGaslessTx`, `DeductFeeDecorator`, `MinGasPriceDecorator`, `AccountInitDecorator`) apply identically to `MsgExecutePayload` as they do to the UV-only vote messages, but `MsgExecutePayload` has no bonded/tombstoned gate at all [11](#0-10) .

### Recommendation
- Restrict "always gasless, any signer" treatment to messages that are validator-gated (`MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/TSS votes), where bonded-stake slashing risk already deters spam.
- For `MsgExecutePayload`, either require a minimal Cosmos fee/gas-price floor from the `Signer` (decoupled from the UEA's own gas accounting), impose a strict per-signer or per-block rate limit on gasless `MsgExecutePayload` submissions, or perform a cheap pre-check (e.g., verifying the target UEA exists and the `VerificationData` has plausible shape) before dispatching the expensive `DerivedEVMCall`.
- Consider capping the `gasLimit` accepted from a gasless `MsgExecutePayload` far below the block gas limit, and/or requiring the `Signer` account to have pre-existing state (i.e., disallow `AccountInitDecorator` bootstrapping for this particular message type) so that account creation itself cannot be chained into free repeated spam.

### Proof of Concept
1. Generate a fresh secp256k1 key `A` with zero balance.
2. Build and sign a `MsgExecutePayload` transaction from `A` with `account_number=0, sequence=0`, an arbitrary/garbage `UniversalAccountId` and `VerificationData`, and a large `gasLimit` inside `UniversalPayload`.
3. Submit it. `AccountInitDecorator` verifies only the self-consistent signature and creates the account for free [7](#0-6) ; `DeductFeeDecorator`/`MinGasPriceDecorator` skip fee/min-gas checks because `IsGaslessTx` is true [3](#0-2) [4](#0-3) .
4. The message handler calls `ExecutePayloadV2` → `CallUEAExecutePayload`, dispatching a real EVM call on every validator with the attacker-chosen gas limit [12](#0-11) ; the call reverts (owner signature mismatch), but validators have already spent the computation.
5. Repeat step 2-4 indefinitely from the same account `A` (subsequent transactions still classify as gasless by message type alone), at zero cumulative cost, to sustain load on validator nodes.

```markdown
`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```

```markdown
#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**
```

// CallUEAExecutePayload executes a universal payload through UEA
func (k Keeper) CallUEAExecutePayload(
	ctx sdk.Context,
	from, ueaAddr common.Address,
	universal_payload *types.UniversalPayload,
	verificationData []byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	abi, err := types.ParseUeaABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UEA ABI")
	}

	abiUniversalPayload, err := types.NewAbiUniversalPayload(universal_payload)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal payload")
	}

	gasLimit := new(big.Int)
	gasLimit, ok := gasLimit.SetString(universal_payload.GasLimit, 10)
	if !ok {
		return nil, fmt.Errorf("invalid gas limit: %s", universal_payload.GasLimit)
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,
		ueaAddr,
		big.NewInt(0),
		gasLimit,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"executeUniversalTx",
		abiUniversalPayload,
		verificationData,
	)
}

	// Step 1: Validate payload and verificationData early (fast-fail before EVM work)
	if _, err := types.NewAbiUniversalPayload(universalPayload); err != nil {
		return nil, errors.Wrapf(err, "invalid universal payload")
	}

	verificationDataVal, err := utils.HexToBytes(verificationData)
	if err != nil {
		return nil, errors.Wrapf(err, "invalid verificationData format")
	}

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}
