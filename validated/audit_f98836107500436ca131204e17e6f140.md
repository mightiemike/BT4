### Title
Webhook HMAC validation does not bind the signature to the claimed shop domain, enabling cross-tenant webhook forgery/replay - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
Shopify webhook authentication in `@shopify/shopify-api` validates only that the raw request body was signed with the app's single, shared `apiSecretKey`; it never incorporates the shop domain (or any other per-tenant identifier) into the signed material. The verified `domain` value is taken directly from an unauthenticated request header and is subsequently trusted to load a specific shop's offline session and access token. This mirrors the GMX `Oracle.SALT` pattern: a signature-validity context (chain id / shop domain) is fixed outside of what is actually verified, so an artifact that is legitimately signed for one context can be replayed unmodified in a different context.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC purely from `rawBody` and `config.apiSecretKey`, and compares it against the `X-Shopify-Hmac-Sha256` header value: [1](#0-0) 

The `apiSecretKey` is a single, static value scoped to the whole app (shared across every shop that installs it), not per-shop: [2](#0-1) 

`validateFactory` (used by `shopify.webhooks.validate`) only calls this body/secret HMAC check and, after it succeeds, reads `domain`, `topic`, etc. straight out of headers via `checkWebhookHeaders` — none of those header values are part of the signed material: [3](#0-2) 

Downstream, `authenticateWebhookFactory` (shopify-app-remix and shopify-app-react-router) uses the unauthenticated `check.domain` value to load the target shop's offline session and to construct an `admin` API client bound to that shop's access token, then hands the attacker-controlled `rawBody` payload to the app's webhook handler under that shop's identity: [4](#0-3) [5](#0-4) 

Because the HMAC covers only `rawBody`, an unprivileged actor who is merely a merchant with the app installed on their own shop can:
1. Trigger any webhook event on their own store, capturing the exact `rawBody` and its valid `X-Shopify-Hmac-Sha256` value delivered to the app (this pair is fully legitimate and shared-secret-signed, but not bound to any shop).
2. Replay that identical `rawBody`/HMAC pair directly to the app's webhook endpoint themselves, while spoofing `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, which are likewise unsigned) to point at a victim shop.
3. The HMAC check still passes (body+secret match), `checkWebhookHeaders` succeeds, and `ensureValidOfflineSession(params, check.domain)` loads the victim shop's real offline session/access token, invoking the app's webhook handler as if the event legitimately originated from the victim shop, with attacker-controlled payload and topic.

This is directly analogous to the GMX SALT bug: the signature's "chain of trust" is anchored to a fixed, out-of-band value (the shared api secret / SALT) instead of dynamically re-verifying the specific execution context (shop domain / chain id) at validation time, permitting replay across contexts.

### Impact Explanation
An attacker controlling only their own installed shop can forge webhook deliveries attributed to an arbitrary victim shop that also has the app installed, obtaining:
- Cross-tenant access: the victim's offline `Session`/access token is loaded and an `admin` GraphQL/REST client bound to it is handed to the app's own webhook handler.
- Ability to trigger handler logic (e.g., `APP_UNINSTALLED`, data-sync, billing, or custom shop-specific handlers) against the victim shop using attacker-supplied payload content, potentially causing data corruption, unwanted mutations via the victim's access token, or denial of service for that shop's integration.

### Likelihood Explanation
Reachable from a fully anonymous/unprivileged position: any merchant who installs the app (a normal, non-privileged action) can capture one legitimate body+HMAC pair from their own store's webhook traffic and immediately reuse it against the app's public webhook endpoint with forged headers — no secrets, admin access, or MITM are required, only knowledge of the target's `myshopify.com` domain, which is public.

### Recommendation
Bind the webhook signature to the tenant context instead of trusting the `X-Shopify-Shop-Domain` (and other) headers implicitly:
- After body-HMAC validation succeeds, cross-check the `domain` header against session storage in a way that can't be freely spoofed (e.g., require it to match a domain that was independently verified, such as by looking up the webhook subscription/registration record for the given `webhookId` and comparing its registered shop), or
- Where possible, additionally validate requests via mutual TLS/IP allow-listing for Shopify's webhook infrastructure, and/or maintain a per-shop nonce/webhook-id replay cache so a given `(hmac, webhookId)` pair can only be consumed once, preventing this exact body/signature pair from being reused against a different domain.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`. Trigger any webhook subscription (e.g. `products/update`) so Shopify POSTs a body `B` with header `X-Shopify-Hmac-Sha256: H` (where `H = HMAC-SHA256(secret, B)`) to the app's webhook URL.
2. Capture `B` and `H` (e.g. via a proxy/logging on the attacker's own infrastructure, since this is the attacker's own traffic).
3. Send a new POST to the same webhook endpoint with body `B` unchanged, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com` and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
4. `validateHmacFromRequestFactory` (packages/apps/shopify-api/lib/utils/hmac-validator.ts) validates `H` against `B` successfully (domain is irrelevant to the HMAC). `authenticateWebhookFactory` then loads `victim.myshopify.com`'s offline session and passes it, plus the attacker's payload `B`, to the app's webhook handler as if it were a legitimate event from the victim shop.

```typescript
export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
```

```typescript
export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}
```
