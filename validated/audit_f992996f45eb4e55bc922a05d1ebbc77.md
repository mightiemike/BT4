### Title
Missing distinct-header check in `check_microblock_header_signer` allows `PoisonMicroblock(h, h.clone())` to be accepted as valid equivocation proof - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`check_microblock_header_signer` only verifies that the two supplied microblock headers recover to the same public-key hash; it never checks that the two headers are actually distinct (different `block_hash()`/signature) at the same sequence number. Because `pkh1 == pkh2` holds trivially when `mblock_header_1` and `mblock_header_2` are byte-identical, `handle_poison_microblock` will accept and record a "poison" report for a miner who produced only one microblock, not two conflicting ones.

### Finding Description
The equality the question is about: `pkh1 == pkh2` (does NOT imply) `slashed-miner-double-signed == true`. `slashed-miner-double-signed` should require two headers with the same `sequence`/`prev_block` but *different* content/signature (an actual equivocation). The code never checks header inequality:

```
fn check_microblock_header_signer(
    mblock_hdr_1: &StacksMicroblockHeader,
    mblock_hdr_2: &StacksMicroblockHeader,
) -> Result<Hash160, Error> {
    let pkh1 = mblock_hdr_1.check_recover_pubkey()...
    let pkh2 = mblock_hdr_2.check_recover_pubkey()...
    if pkh1 != pkh2 { return Err(...) }
    Ok(pkh1)
}
``` [1](#0-0) 

`handle_poison_microblock` then uses only this equality to validate the poison claim before inserting a report:
```
let pubkh =
    StacksChainState::check_microblock_header_signer(mblock_header_1, mblock_header_2)?;
...
env.global_context.database.insert_microblock_poison(
    mblock_pubk_height,
    &sender_principal,
    mblock_header_1.sequence,

``` [2](#0-1) 

The upstream mempool admission guard (`MemPoolRejection` check in `blocks.rs`) only requires matching `sequence`, `prev_block`, `version` and matching pubkey-hash recovery — again all trivially true for `h == h.clone()`:
```
TransactionPayload::PoisonMicroblock(microblock_header_1, microblock_header_2) => {
    if microblock_header_1.sequence != microblock_header_2.sequence
        || microblock_header_1.prev_block != microblock_header_2.prev_block
        || microblock_header_1.version != microblock_header_2.version
    { return Err(MemPoolRejection::PoisonMicroblocksDoNotConflict); }
    ...
    if microblock_pkh_1 != microblock_pkh_2 { return Err(MemPoolRejection::PoisonMicroblocksDoNotConflict); }
``` [3](#0-2) 

Neither guard rejects the degenerate case where `microblock_header_1 == microblock_header_2` byte-for-byte. Because block miners publish signed microblock headers publicly, any observer can take a single, honestly-produced, already-broadcast microblock header `h` and submit `PoisonMicroblock(h, h.clone())`. `check_microblock_header_signer` recovers the same `pkh` from both copies and returns `Ok(pkh)`, so `handle_poison_microblock` proceeds exactly as if a genuine fork/equivocation had been proven: it looks up `pubkh`'s block height, validates the `MINER_REWARD_MATURITY` window, and inserts a poison record crediting the sender (attacker) as the reporter at `mblock_header_1.sequence`. This is a false-positive "proof of equivocation" against a miner who never double-signed.

The only genuine equivocation-detection code paths (`validate_parent_microblock_stream` in `blocks.rs:2904-3057`, and `load_and_vet_parent_microblocks` machinery) construct `PoisonMicroblock` payloads only from truly conflicting headers found in a stream (duplicate `prev_block` or duplicate `sequence` with differing `block_hash()`), so honest miners are safe against automatically-generated poison transactions. But nothing stops an attacker crafting and submitting their own `PoisonMicroblock(h, h.clone())` transaction directly, bypassing that construction logic entirely, since the on-chain validator (`check_microblock_header_signer`) does not re-derive or require the two headers to differ.

### Impact Explanation
This is a reward-integrity bug bounded to the poison/commission mechanism, not a chain split: an attacker (any principal, no stake or signer privilege required) can register a bogus poison report against a miner who committed no equivocation, consuming/claiming the reporter-commission slot for that miner's coinbase key/height, and potentially causing the miner's coinbase to be treated as forfeited/slashed once the report is used at maturation. This falls under the "High" category ("a poison or reward mis-payment bounded to fees"): an honest miner can lose (or have contested) their commission/reward, and an attacker gains an illegitimate reporter credit, purely by replaying a header they observed on the wire. It does not cause disagreement between honest nodes on validity (both nodes apply the same faulty rule deterministically), so it is not a chain-split/Critical-category issue, but it is a real, deterministic reward-mispayment vector reachable by an unprivileged single participant.

### Likelihood Explanation
Preconditions are minimal: the attacker needs to observe any already-broadcast, validly-signed microblock header `h` from any miner (trivial — headers are gossiped publicly), and needs enough STX to pay the transaction fee for submitting a `PoisonMicroblock` transaction. No majority stake, no signer key, no admin/node privilege, and no double-signing by the miner is required. The attack is fully repeatable against every microblock header ever produced by any miner, subject only to the `MINER_REWARD_MATURITY` window and one report being recorded per `(pubkh, height)` pair (subsequent attempts by others at a lower sequence can supersede it, but the first attacker still gets recorded and credited unless outbid).

### Recommendation
In `check_microblock_header_signer` (or in `handle_poison_microblock` before calling it), explicitly reject the case where the two headers are identical, e.g. require `mblock_header_1.block_hash() != mblock_header_2.block_hash()` (or equivalently compare full serialized headers/signatures) in addition to `sequence`/`prev_block` matching and `pkh1 == pkh2`. Apply the same distinctness check in the mempool admission path (`blocks.rs` `PoisonMicroblock` validation) so degenerate poison transactions are rejected before entering the mempool at all.

### Proof of Concept

fn process_poison_microblock_identical_headers_should_be_rejected() {
    // setup: same TestChainstateBuilder harness as process_poison_microblock_invalid_transaction
    // insert a known microblock pubkey hash at height 1 (block_pubkh)
    // create ONE signed microblock header `h` from block_privk (only ONE header, no fork)
    let mblock = make_signed_microblock(&block_privk, &block_privk, BlockHeaderHash([0x11; 32]), 5);

    // attacker crafts PoisonMicroblock(h, h.clone()) -- byte-identical headers
    let tx_poison = StacksTransaction::new(
        TransactionVersion::Testnet,
        TransactionAuth::from_p2pkh(&attacker_privk).unwrap(),
        TransactionPayload::PoisonMicroblock(mblock.header.clone(), mblock.header.clone()),
    );
    // sign & submit via StacksChainState::process_transaction

    let result = StacksChainState::process_transaction(&mut conn, &signed_tx_poison, false, None);

    // EQUALITY CHECK BEFORE: mblock_header_1 == mblock_header_2 (true, identical bytes)
    // EQUALITY CHECK AFTER (expected true equivocation semantics): should require header_1 != header_2
    // Assert the tx MUST be rejected as non-conflicting/duplicate, not accepted:
    assert!(result.is_err(), "identical header PoisonMicroblock must be rejected");
    // Also assert no poison report was inserted:
    let report = StacksChainState::get_poison_microblock_report(&mut conn, 1).unwrap();
    assert!(report.is_none(), "no report should be recorded for a non-equivocating single header");
