### Title
Silent truncation on index/account length mismatch during shrink can leave stale account-index entries pointing at pre-shrink storage - (File: accounts-db/src/accounts_db.rs)

### Summary
The external report's bug class is: a variable-length collection (`remaining_accounts`) is consumed by a critical state-transition without validating that its length matches the expected/authoritative count, so a mismatch is silently tolerated instead of causing a hard failure — leading the program to fall back to incorrect, attacker-favorable default behavior. The closest reachable analog in AccountsDB is `AccountsDb::update_index_for_shrink`, which computes the number of index updates to perform as `min(accounts.len(), infos.len())` rather than asserting the two lengths are equal [1](#0-0) .

### Finding Description
During shrink, `shrink_storage` rewrites alive accounts into a new storage via `store_accounts_for_shrink`, which calls `write_accounts_to_storage` to append the accounts and obtain per-account `AccountInfo` entries, and separately calls `update_index_for_shrink` to repoint each pubkey's accounts-index entry at the new `(store_id, offset)` [2](#0-1) .

`write_accounts_to_storage` does defensively assert that the number of `offsets` returned equals the number of accounts requested, panicking on any mismatch [3](#0-2) . However, the accompanying index-update step, `update_index_for_shrink`, receives `infos` (built from those offsets) and the original `accounts` list, and rather than asserting `accounts.len() == infos.len()` it computes:
```
let len = std::cmp::min(accounts.len(), infos.len());
```
and only updates the index for pubkeys in `0..len` [4](#0-3) . This mirrors exactly the reported bug class: instead of hard-failing on a length mismatch between the "authoritative" count and a derived collection, the code silently truncates to the smaller of the two and proceeds. If any future code path (e.g. a refactor of `write_accounts_to_storage`, or a change to how `infos` is constructed/passed) ever produces `infos.len() < accounts.len()` without tripping the assert in `write_accounts_to_storage` (for example if `infos` is filtered or truncated after being computed, or constructed by a different caller than `store_accounts_for_shrink`), the last `accounts.len() - infos.len()` pubkeys would silently keep their old index entries pointing at the pre-shrink storage/offset instead of being errored on or corrected. Because shrink's caller (`remove_old_stores_shrink`) subsequently drops/reclaims the old storage entry, any pubkeys whose index entries were not updated would end up pointing to storage that is removed or is about to be repurposed by a different `AccountsFile` id — i.e., a stale/wrong-version account reference in the primary index. This is the same class of "trust the shorter list, don't validate the count against the authoritative source" defect that let the CEGA report's attacker skip the knock-in penalty by omitting `remaining_accounts`.

### Impact Explanation
If `update_index_for_shrink` is ever invoked with mismatched `accounts`/`infos` lengths, the tail pubkeys' index entries would not be updated to the new post-shrink storage location while the underlying old storage is torn down. Subsequent reads for that pubkey via `AccountsIndex` would resolve to a stale `(store_id, offset)` that either no longer exists (causing a load failure/panic) or, worse, has since been reused by `next_id()` for an unrelated storage file, causing the read to return a different, unrelated account entirely — a silent, wrong-version account load without any explicit error. This falls squarely under "concrete stale or wrong-version account loads" and could also manifest as an accounts-lt-hash/capitalization divergence between nodes that hit the code path versus those that don't, or a node panic on the next load attempt.

### Likelihood Explanation
Today, `write_accounts_to_storage`'s internal assert makes it unlikely that `infos` and `accounts` diverge in length within the current single call chain (`shrink_storage` → `store_accounts_for_shrink` → `write_accounts_to_storage` + `update_index_for_shrink`), because both are derived from the same `accounts` value in the same function. The likelihood is Low given the current call sites, since no current caller passes mismatched slices. However, the defensive design pattern is inverted relative to best practice: `update_index_for_shrink` is a `pub(crate)`-adjacent helper that silently tolerates a length mismatch by taking the `min()`, rather than asserting equality like its sibling `write_accounts_to_storage` does. This makes it a latent trap for any future refactor or new caller (shrink code has multiple entry points, e.g. `store_accounts_for_shrink` used by both `shrink_storage` and ancient-append-vec combining) that could introduce a length mismatch without any test or assertion catching it, exactly mirroring how the CEGA program's regression (missing length check introduced in a later commit) went unnoticed until exploited.

### Recommendation
Replace the silent `min()` truncation in `update_index_for_shrink` with a hard assertion (or `Result`-returning validation) that `accounts.len() == infos.len()` before proceeding, consistent with the invariant already enforced in `write_accounts_to_storage`. This ensures any future divergence fails loudly (panic on the validator that hits it, which is safe/deterministic and detectable) instead of silently leaving stale index entries that could produce wrong-version account loads or hash divergence.

### Proof of Concept
Not applicable as a working exploit against current code: no reachable current caller of `update_index_for_shrink` supplies `accounts` and `infos` of different lengths, since both are derived together in `store_accounts_for_shrink`/`shrink_storage`.     fn update_index_for_shrink<'a>(
        &self,
        infos: &[AccountInfo],
        accounts: &impl StorableAccounts<'a>,
        update_index_thread_selection: UpdateIndexThreadSelection,
        thread_pool: &ThreadPool,
    ) {
        let target_slot = accounts.target_slot();
        let len = std::cmp::min(accounts.len(), infos.len());

        let update = |start, end| {
            (start..end).for_each(|i| {
                let info: AccountInfo = infos[i];
                let old_slot = accounts.slot(i);
                let pubkey = accounts.pubkey(i);
                self.accounts_index
                    .replace(target_slot, old_slot, pubkey, info);
            });
        };

        let threshold = 1;
        if matches!(
            update_index_thread_selection,
            UpdateIndexThreadSelection::PoolWithThreshold,
        ) && len > threshold
        {
            let chunk_size = len.div_ceil(thread_pool.current_num_threads());
            let batches = 1 + len / chunk_size;
            thread_pool.install(|| {
                (0..batches).into_par_iter().for_each(|batch| {
                    let start = batch * chunk_size;
                    let end = std::cmp::min(start + chunk_size, len);
                    update(start, end)
                })
            });
        } else {
            update(0, len);
        }
    }
