### Title
Integer overflow in `WithdrawBalanceActuator.execute()` due to unchecked `+` and TOCTOU on `allowance` vs. `validate()`'s `LongMath.checkedAdd` - ([File: actuator/src/main/java/org/tron/core/actuator/WithdrawBalanceActuator.java])

### Summary
`WithdrawBalanceActuator.execute()` calls `mortgageService.withdrawReward()` (line 54) *before* snapshotting `oldBalance`/`allowance` (lines 59-60) and then computes `oldBalance + allowance` with plain `+` (line 64), whereas `validate()` only checks overflow via `LongMath.checkedAdd` (line 135) on the *pre-withdrawal* allowance stored in `AccountStore`. Because `withdrawReward()` can itself inflate `allowance` via `MortgageService.adjustAllowance()` before the unchecked addition runs, the overflow check performed in `validate()` does not cover the value actually added in `execute()`.

### Finding Description
- `validate()` reads `accountCapsule.getBalance()` and `accountCapsule.getAllowance()` directly from the store and verifies `LongMath.checkedAdd(balance, allowance)` does not overflow: [1](#0-0) .
- `execute()` does **not** re-run this check. Instead it first calls `mortgageService.withdrawReward(...)` (line 54), which can call `adjustAllowance()` and increase the stored `allowance` field beyond what `validate()` inspected, and only afterwards reads `oldBalance`/`allowance` and performs a plain, unchecked `oldBalance + allowance` addition: [2](#0-1) .
- `MortgageService.withdrawReward()` computes newly accrued rewards from `delegationStore`/vote cycles and pushes them into the account's `allowance` field via `adjustAllowance()`, independent of whatever `allowance` value `validate()` saw: [3](#0-2)  and [4](#0-3) .
- By contrast, the equivalent TVM-native path (`WithdrawRewardProcessor.execute()`) and the suicide/self-destruct path (`Program.withdrawRewardAndCancelVote`) both use safe arithmetic (`LongMath.checkedAdd` / `addExact`) for the *same* balance+allowance addition, confirming the actuator's plain `+` is an inconsistency with the rest of the codebase: [5](#0-4) , [6](#0-5) .

### Impact Explanation
If `balance + allowance` (where `allowance` includes the amount added by `withdrawReward()` during `execute()`) exceeds `Long.MAX_VALUE`, the plain `+` wraps to a negative or corrupted value that is written directly into the account via `accountStore.put(...)` at line 68, i.e. silent accounting corruption of the account's `balance` field. This is a VALUE_CONSERVATION violation (accounting corruption) — a corrupted/negative balance can cascade into further inconsistent behavior in any code that assumes non-negative balances.

### Likelihood Explanation
Exploitability strictly depends on an attacker's account balance plus pending reward/allowance being close to `Long.MAX_VALUE` sun. Under TRON's actual token-supply economics this is not realistically reachable by any legitimate account (total network supply is orders of magnitude below `Long.MAX_VALUE` in sun units), so absent some other bug that mints/inflates a balance close to the long boundary, this specific overflow cannot be triggered on mainnet today. It is, however, a genuine code-correctness defect: the overflow guard in `validate()` inspects a value that can be stale by the time `execute()` performs the actual unchecked addition, and the addition itself lacks the safe-math pattern used elsewhere in the codebase for the identical operation.

### Recommendation
Use `LongMath.checkedAdd` (or equivalent safe/checked arithmetic) in `WithdrawBalanceActuator.execute()` at line 64, mirroring `WithdrawRewardProcessor.execute()`, and throw `ContractExeException` on overflow instead of relying solely on the potentially-stale check in `validate()`.

### Proof of Concept
```java
@Test
public void testWithdrawBalanceOverflow() {
  byte[] address = ByteArray.fromHexString(OWNER_ADDRESS);
  AccountCapsule accountCapsule = dbManager.getAccountStore().get(address);
  accountCapsule.setBalance(Long.MAX_VALUE - 100);
  accountCapsule.setAllowance(200); // > 100 so balance+allowance overflows
  dbManager.getAccountStore().put(address, accountCapsule);

  WitnessCapsule witnessCapsule = new WitnessCapsule(ByteString.copyFrom(address), 100, "http://x.com");
  dbManager.getWitnessStore().put(address, witnessCapsule);

  WithdrawBalanceActuator actuator = new WithdrawBalanceActuator();
  actuator.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getContract(OWNER_ADDRESS));
  TransactionResultCapsule ret = new TransactionResultCapsule();

  try {
    actuator.validate(); // may throw here if allowance already reflects the 200
    actuator.execute(ret);
    AccountCapsule owner = dbManager.getAccountStore().get(address);
    // EXPECT: owner.getBalance() >= 0 and mathematically correct,
    // or a ContractExeException should have been thrown.
    Assert.assertTrue("Balance wrapped to negative", owner.getBalance() >= 0);
  } catch (ContractValidateException | ContractExeException e) {
    // acceptable outcome if overflow is properly rejected
  }
}
```
Note: to actually demonstrate the TOCTOU gap (rather than a pre-existing overflow already caught by `validate()`), seed `allowance` low enough to pass `validate()`, then have `mortgageService.withdrawReward()` (via pending vote/cycle rewards in `delegationStore`) inject enough additional allowance during `execute()` so that `oldBalance + allowance` (post-withdrawReward) overflows despite `validate()` having passed.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }
