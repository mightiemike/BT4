Based on my research, I found a genuine analog. It centers on an unconditional zero-amount PRC20 mint call in the outbound-failure handling path, inconsistent with the zero-amount guards used everywhere else in the same codebase.

### Title
Unconditional zero-amount `depositPRC20Token` call in `handleFailedOutbound` can abort outbound processing and permanently strand the excess gas refund - (File: x/uexecutor/keeper/outbound.go)

### Summary
`handleFailedOutbound` re-mints bridged funds for `FUNDS`, `GAS_AND_PAYLOAD`, and `FUNDS_AND_PAYLOAD` outbound types whenever an outbound is observed as failed, calling `CallPRC20Deposit` with the outbound's `Amount` unconditionally [1](#0-0) . Unlike every other call site in this repository that invokes the same deposit path, this one has no `Sign() > 0` guard.

### Finding Description
`GAS_AND_PAYLOAD` is a valid inbound/outbound type that legitimately carries `Amount = "0"` — it represents a pure gas top-up plus payload execution with no bridged funds. This is explicitly supported and tested: zero-amount `GAS_AND_PAYLOAD` inbounds skip the deposit step and still succeed [2](#0-1) .

Every other execution path that calls `depositPRC20`/`CallPRC20Deposit` explicitly guards against a zero amount before making the EVM call:
- `ExecuteInboundFundsAndPayload` only deposits `if inboundAmount.Sign() > 0` [3](#0-2) , and again at the non-isCEA path [4](#0-3) .

This pattern strongly indicates that `depositPRC20Token` on the `UNIVERSAL_CORE` handler contract reverts (or otherwise fails) when called with a zero amount — consistent with the `ZeroAmount` custom error present in the same contract's ABI alongside other guard errors like `ZeroAddress`, `ZeroGasPrice`, and `GasFeeTransferFailed` [5](#0-4) .

`handleFailedOutbound`, however, includes `TxType_GAS_AND_PAYLOAD` in the set of types for which it unconditionally re-mints funds on outbound failure, with no zero-amount check [6](#0-5) . If a `GAS_AND_PAYLOAD` outbound with `Amount = "0"` is later observed by universal validators as failed on the destination chain (an ordinary, honestly-reported outcome — e.g., the destination-chain payload call reverts), `CallPRC20Deposit` is invoked with `amount = 0`. If the handler contract rejects a zero-amount deposit, `err != nil`, and the function takes the abort branch:

```go
if err != nil {
    pcTx.Status = "FAILED"
    pcTx.ErrorMsg = err.Error()
    outbound.PcRevertExecution = &pcTx
    return k.AbortOutbound(ctx, utxId, outbound,
        fmt.Sprintf("failed to re-mint tokens for revert: %s", err.Error()))
}
``` [7](#0-6) 

Critically, this `return` happens *before* `applyGasRefund` is ever called [8](#0-7) . `applyGasRefund` is what returns the user's excess prepaid gas (`gasFee - gasFeeUsed`) via `CallUniversalCoreRefundUnusedGas` [9](#0-8) . Because the outbound is marked `ABORTED` by `AbortOutbound`, the normal finalize/refund flow never resumes automatically for it — it requires manual admin intervention, and the gas refund logic never runs at all for that outbound.

### Impact Explanation
An ordinary, unprivileged user submitting a `GAS_AND_PAYLOAD` cross-chain transaction with an intentionally reverting/failing destination payload and `Amount = "0"` (funds-free gas top-up) can cause their outbound to hit the zero-amount re-mint call. If the handler contract rejects zero-amount deposits, the outbound is forced into `ABORTED` state, and the excess-gas refund the user is entitled to (`PcRefundExecution`) is never computed or delivered — it is skipped by the early return, not merely delayed. This is a permanent freezing of the refund accounting for that outbound absent a privileged admin fix, matching the in-scope impact "permanent freezing... of user or protocol-controlled funds" and "corruption of ... gas fee accounting, refund accounting."

### Likelihood Explanation
Triggering a `GAS_AND_PAYLOAD` outbound with `Amount = "0"` is a normal, supported user flow (already covered by tests for the inbound side). Causing that outbound to be observed as failed only requires the user's own destination-chain payload to revert, which is fully within an unprivileged user's control and requires no malicious validator or admin behavior — honest UVs will report the (accurate) failure.

### Recommendation
Guard the re-mint call in `handleFailedOutbound` the same way it is guarded everywhere else in the codebase:
```go
if amount.Sign() > 0 && (outbound.TxType == types.TxType_FUNDS ||
    outbound.TxType == types.TxType_GAS_AND_PAYLOAD ||
    outbound.TxType == types.TxType_FUNDS_AND_PAYLOAD) {
    ... existing CallPRC20Deposit logic ...
}
```
and ensure `applyGasRefund` still executes regardless of whether the re-mint branch was skipped, so the gas-refund accounting is never made contingent on an unrelated zero-amount funds re-mint.

### Proof of Concept
1. Construct a `GAS_AND_PAYLOAD` inbound/outbound flow where `outbound.Amount = "0"` (pure gas top-up + payload, no bridged funds), similar to the setup in `inbound_zero_amount_test.go` [10](#0-9) .
2. Have the destination-chain payload revert, and have universal validators vote `MsgVoteOutbound` with `success=false` and a `gasFeeUsed < gasFee` (so a nonzero excess-gas refund is due).
3. `FinalizeOutbound` → `handleFailedOutbound` is invoked with `outbound.Amount = "0"` and `outbound.TxType = TxType_GAS_AND_PAYLOAD` [11](#0-10) .
4. `CallPRC20Deposit` is called with `amount = 0`; if the `UNIVERSAL_CORE` handler contract's `depositPRC20Token` rejects zero amounts (consistent with the `ZeroAmount` ABI error [5](#0-4) ), the call returns an error.
5. The outbound is marked `ABORTED` via `AbortOutbound`, and `applyGasRefund` is never reached — the excess gas fee refund is never computed or paid out, and the outbound requires manual admin resolution instead of completing the normal `REVERTED` finalize path that the equivalent successful-amount case would take.

Note: I was unable to directly inspect the Solidity source of `UniversalCore.depositPRC20Token` to confirm the exact revert condition (index limits prevented finding the contract source); the finding relies on the strong circumstantial evidence of the `ZeroAmount` ABI error and the explicit `Sign() > 0` guards used at every other call site in this Go codebase. A Devin session with full repo/contract access would be needed to confirm the exact Solidity revert condition.

func (k Keeper) applyGasRefund(ctx sdk.Context, outbound *types.OutboundTx, obs *types.OutboundObservation) {
	if obs.GasFeeUsed == "" || outbound.GasFee == "" || outbound.GasToken == "" {
		return
	}

	gasFee := new(big.Int)
	if _, ok := gasFee.SetString(outbound.GasFee, 10); !ok {
		return
	}

	gasFeeUsed := new(big.Int)
	if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok {
		return
	}

	// No excess gas to refund
	if gasFee.Cmp(gasFeeUsed) <= 0 {
		return
	}

	refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
	gasToken := common.HexToAddress(outbound.GasToken)

	// Refund recipient: prefer fund_recipient in revert_instructions, fall back to sender
	refundRecipient := outbound.Sender
	if outbound.RevertInstructions != nil && outbound.RevertInstructions.FundRecipient != "" {
		refundRecipient = outbound.RevertInstructions.FundRecipient
	}
	recipientAddr := common.HexToAddress(refundRecipient)

	refundPcTx := &types.PCTx{
		Sender:      outbound.Sender,
		BlockHeight: uint64(ctx.BlockHeight()),
	}

	// Step 1: try refund with swap (gasToken → PC native)
	fee, swapErr := k.GetDefaultFeeTierForToken(ctx, gasToken)
	var swapFallbackReason string

	if swapErr == nil {
		quote, quoteErr := k.getSwapQuoteForRefund(ctx, gasToken, fee, refundAmount)
		if quoteErr == nil {
			minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
			minPCOut.Div(minPCOut, big.NewInt(100))

			resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, true, fee, minPCOut)
			if err == nil {
				refundPcTx.TxHash = resp.Hash
				refundPcTx.GasUsed = resp.GasUsed
				refundPcTx.Status = "SUCCESS"
				outbound.PcRefundExecution = refundPcTx
				return
			}
