### Title
Asset (Token) Name Squatting via Transaction Front-Running in `AssetIssueActuator` - (File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java)

### Summary
`AssetIssueActuator.validate()` enforces a first-come-first-served uniqueness check on the human-readable asset `name` field when `AllowSameTokenName` is disabled, exactly mirroring the "handle" uniqueness pattern that enabled front-running in the referenced Aave Lens `createProfile` finding. Because pending `AssetIssueContract` transactions are visible in the public mempool before being packed into a block, any account holding the minimal TRX balance required to pay the issuance fee can observe a victim's pending asset-creation transaction and submit a competing transaction with the same `name` and a higher priority/fee, claiming the name first and causing the victim's transaction to fail.

### Finding Description
In `validate()`, when same-token-name support is disabled (the default historically, controlled by `DynamicPropertiesStore.getAllowSameTokenName()`), the actuator performs a simple existence check on the raw `name` bytes in `AssetIssueStore`: [1](#0-0) 

This is the sole gate protecting name uniqueness — there is no commit/reveal step, no reservation mechanism, and no binding of the name to a specific submitter prior to broadcast. Any account (identified only by an address that must already exist and hold enough balance to pay `calcFee()`, i.e. the `AssetIssueFee`) can call this actuator: [2](#0-1) 

When the transaction executes, the name is persisted as the DB key in `AssetIssueStore`/`AssetIssueV2Store` and bound to the issuer's account via `accountCapsule.setAssetIssuedName(...)`: [3](#0-2) [4](#0-3) 

Because transactions broadcast to the network are visible before block inclusion (standard mempool exposure, no special privilege needed to observe them), an attacker can:
1. Monitor the network for a pending `AssetIssueContract` transaction with a desirable `name`.
2. Broadcast their own `AssetIssueContract` transaction using the identical `name`, with sufficient fee/priority to be included first.
3. Once confirmed, the attacker's transaction claims the name in `AssetIssueStore`; the victim's original transaction then fails validation with `"Token exists"` when processed (or is rejected during re-validation), because it's `getAllowSameTokenName() == 0` path only allows one registrant per name.

This directly parallels the Lens `createProfile` frontrunning bug class: an unprivileged party can win a race for a unique, human-meaningful identifier by observing pending broadcast transactions, with no protocol-level protection (no commit/reveal, no escrow).

### Impact Explanation
A successful front-run:
- Denies the legitimate user their intended asset name permanently (an account, per `!accountCapsule.getAssetIssuedName().isEmpty()` check, can only issue one asset ever), forcing them to either abandon the desired name or negotiate/ransom with the squatter for the name — the same "demand ransom" scenario described in the source report.
- The victim may still have paid TRX bandwidth/energy costs for the failed broadcast attempt even though the `AssetIssueFee` itself is not charged on validation failure, since `adjustBalance`/blackhole burn only occurs in `execute()` after `validate()` succeeds. [5](#0-4) 
- This is a griefing/availability issue against specific, valuable token names rather than a direct fund-theft primitive, consistent with the Medium severity classification given to the analogous Lens Protocol finding.

### Likelihood Explanation
Likelihood is non-trivial: no special/privileged role is required (unlike governance-based whitelisting in Lens), any funded TRON account can call `AssetIssueContract`, and transactions are broadcast publicly prior to confirmation, making observation and out-bidding straightforward with standard higher-fee/priority resubmission — a well-known and easily executed MEV-style front-running technique on public blockchains.

### Recommendation
- Introduce a commit-reveal scheme for asset name registration: users first submit a hash commitment of `(name, salt, ownerAddress)`, then reveal the actual name after a delay, binding the name claim to the committing address before it is publicly visible.
- Alternatively/additionally, bind name reservation to the transaction's declared owner address at commit time and require a minimum confirmation delay before the name is considered finalized, rejecting late "same name, different owner" transactions that arrived within the same block/short window unless from the original committer.
- Consider requiring `AllowSameTokenName` to remain enabled network-wide (as later versions of the protocol default to, allowing duplicate names disambiguated by token ID) to structurally remove the incentive for name squatting via front-running.

### Proof of Concept
1. Victim broadcasts `AssetIssueContract` transaction `Tx_V` with `name = "GOLD"`, valid `startTime`/`endTime`, and sufficient balance for `AssetIssueFee`.
2. Attacker observes `Tx_V` in the public mempool/P2P broadcast layer (no special access required).
3. Attacker crafts `Tx_A` with the identical `name = "GOLD"` from their own funded account, and submits it with a higher energy/bandwidth fee or via faster propagation so it is included in an earlier block or earlier position within the same block.
4. Block is produced; `AssetIssueActuator.execute()` processes `Tx_A` first, storing `"GOLD"` in `AssetIssueStore` under the attacker's account per lines 78-87/113-118.
5. When `Tx_V` is subsequently validated/executed, the check at lines 210-214 finds `assetIssueStore.get("GOLD") != null` and throws `ContractValidateException("Token exists")`, permanently blocking the victim (per the one-asset-per-account restriction at lines 287-289) from ever issuing under that name unless they negotiate with the attacker.
