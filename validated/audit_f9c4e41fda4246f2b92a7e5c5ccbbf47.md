### Title
Non-deterministic committee-encryption key generation in the Starknet OS `GenerateKeysUsingSha256Hash` hint causes honest-node divergence in the committed state-diff output - (File: `crates/starknet_os/src/hints/hint_implementation/output.rs`)

### Summary
When a block's compressed state diff must be encrypted for the DA committee (`n_keys > 0`), the OS hint `calculate_keys_using_sha256_hash` derives the symmetric encryption key and per-committee-member StarkNet private keys from a seed that mixes 32 bytes read from `OsRng` (a true, non-reproducible entropy source) with a hash of the compressed state diff. Because the OS program is re-executed independently by every sequencer/validator node to reproduce and verify the block output (Starknet OS re-execution), any hint output that is not a pure function of the block's transactions will differ from node to node.

### Finding Description
`calculate_keys_using_sha256_hash` explicitly seeds its SHA-256-based key derivation with fresh OS randomness: [1](#0-0) 

The derived `symmetric_key` and `sn_private_keys` are inserted into VM memory and consumed by the Cairo `encrypt_state_diff` function, whose output (`n_keys`, `sn_public_keys`, `encrypted_symmetric_keys`, `ciphertext`) becomes part of the on-chain data-availability segment produced by `process_data_availability` in `output.cairo`: [2](#0-1) 

That DA segment is subsequently relocated directly into the OS program's output via `serialize_data_availability`: [3](#0-2) 

The Cairo-level documentation for this scheme itself states the private keys and symmetric key are meant to be generated by an hint that hashes the compressed state diff — i.e., it is designed to be reproducible from public inputs — but the actual Rust hint implementation adds `OsRng.fill_bytes` entropy on top of that hash, defeating reproducibility: [4](#0-3) 

Since the Starknet OS program is executed by every honest node independently to verify/reproduce a block's state diff and commitments (this is the "Starknet OS re-execution" path referenced by the sequencer's verification model), each node running this hint for the same block will compute a *different* `symmetric_key`, different `sn_private_keys`, different `sn_public_keys`, and different `encrypted_symmetric_keys`/ciphertext — all because `OsRng` is process-local and non-deterministic. This causes the emitted OS output (and therefore the resulting state/DA commitment derived from it) to diverge between honest nodes even though they processed identical transactions and identical state.

This is directly reachable by an ordinary user: any block that contains transactions modifying contract state and is built with encryption enabled (`n_keys > 0`) will trigger this hint during OS execution/re-execution, regardless of which specific transactions are included — the attacker does not need special privileges, only the ability to have their transaction included and DA-committee-encryption to be turned on for that block.

### Impact Explanation
If the OS output (which includes the encrypted DA segment) feeds into a hash/commitment that is checked for equality between the block proposer/prover and other honest re-executing nodes (or into the STARK proof's public input used for state-diff commitment), any two honest nodes independently reproducing the OS run for the same block will compute different outputs. This is a consensus-breaking correctness bug: the network could be unable to agree on / reconfirm a canonical block whose output is influenced by this hint, effectively halting confirmation of new transactions for encrypted-DA blocks, or leading to false-fault/verification failures at the node performing OS re-execution. It maps to the "honest-node divergence" / "network unable to confirm new transactions" acceptance criteria.

### Likelihood Explanation
The condition is deterministic to trigger: whenever a block is produced with committee encryption enabled (`n_keys > 0`, i.e. `NKeys` set), the `GenerateKeysUsingSha256Hash` hint always executes `OsRng.fill_bytes` and will always produce different keys per invocation/process, so divergence is certain, not merely probabilistic, on every such block.

### Recommendation
Remove the `OsRng` entropy source from `calculate_keys_using_sha256_hash` and derive the seed purely and deterministically from data that is already agreed upon by all honest nodes (e.g., solely the compressed state diff, combined with a block-specific public value such as the block hash/number and a domain separator), so that every node re-executing the OS for the same block computes bit-for-bit identical `symmetric_key`, `sn_private_keys`, and thus identical encrypted DA output.

### Proof of Concept
1. Configure a block to use DA-committee encryption (`n_keys > 0`).
2. Run the Starknet OS program for that exact block (same transactions, same state) on two separate processes/nodes.
3. Observe that `calculate_keys_using_sha256_hash` in `crates/starknet_os/src/hints/hint_implementation/output.rs` (lines 149-167) calls `OsRng.fill_bytes(&mut random_bytes)`, injecting process-local entropy into `random_key_seed` before deriving `symmetric_key` and `sn_private_keys`.
4. Compare the two runs' OS outputs (`sn_public_keys`, `encrypted_symmetric_keys`, ciphertext in the DA segment emitted via `process_data_availability`/`serialize_data_availability` in `output.cairo`); they will differ between the two runs despite identical inputs, demonstrating non-determinism in a value that is committed to the block's public output.

pub(crate) fn calculate_keys_using_sha256_hash(mut ctx: HintContext<'_>) -> OsHintResult {
    // Generate a cryptographically secure random seed.
    let mut random_bytes = [0u8; 32];
    OsRng.fill_bytes(&mut random_bytes);

    let mut hasher = Sha256::new();
    hasher.update(random_bytes);

    // In addition, hash the compressed state diff for extra defense against potential attacks on
    // randomness source.
    let compressed_start = ctx.get_ptr(Ids::CompressedStart)?;
    let compressed_end = ctx.get_ptr(Ids::CompressedEnd)?;
    let array_size = (compressed_end - compressed_start)?;
    for i in 0..array_size {
        let felt = ctx.vm.get_integer((compressed_start + i)?)?;
