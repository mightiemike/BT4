### Title
Single-step, irrevocable permission replacement in `AccountPermissionUpdateContract` lacks a two-step confirmation mechanism - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` allows an account to replace its `owner`, `witness`, and `active` permissions (i.e., the set of keys and thresholds that control the account) in a single atomic transaction, with no two-step "propose then confirm" mechanism. This mirrors the reported `Timelock.sol`/`WithdrawalDelayer.sol` bug class: a single function call performs a critical, non-recoverable role/authority change, so a malformed or mistaken update can permanently and irrevocably lock the account owner out of their own account.

### Finding Description
The `execute` method unpacks the `AccountPermissionUpdateContract` and immediately overwrites the account's owner/witness/active permission sets via `AccountCapsule.updatePermissions`, persisting the result in the same transaction: [1](#0-0) 

`updatePermissions` unconditionally replaces the owner permission, the witness permission (if applicable), and clears/rebuilds the entire active permission list from the submitted contract, with no rollback or confirmation step: [2](#0-1) 

`validate()` performs structural checks (key validity, weight sums, threshold, operations bitmap, permission counts) via `checkPermission`, but never verifies that the resulting owner permission retains any key controlled by the current signer, nor does it require any secondary confirmation from the addresses being granted new permission weight: [3](#0-2) 

Because the whole state transition — validating and swapping out the entire owner/active/witness key set — happens in one `AccountPermissionUpdateContract` transaction, this is structurally the same "several critical operations done in one function call" pattern flagged in the report: there is no `propose`/`accept` handshake analogous to `approve-transferFrom` that would let the new key set be staked out and then confirmed by a signature from the new key(s) before it takes effect.

### Impact Explanation
If an account owner (or any tooling/wallet submitting this contract on their behalf) supplies an incorrect address in the new owner permission's `Key` list — a typo, wrong checksum, wrong network address, or an address whose private key is unknown/lost — the account's owner authority is transferred immediately and irreversibly upon block confirmation. Since owner permission is the root of trust for the account (it can further change active/witness permissions and authorize resource/asset operations), this results in permanent loss of account control with no built-in recovery path, matching the report's "too late to revert" exploit scenario. This is reachable directly through a broadcast transaction (`AccountPermissionUpdateServlet` / `Wallet.createTransactionCapsule`) without any privileged-node access.

### Likelihood Explanation
The contract is a first-class, publicly documented multisig feature (`AllowMultiSign`) usable by any account once multisig is enabled network-wide, and is exercised through normal wallet/HTTP API flows: [4](#0-3) 
Given permission-update transactions are user/tooling generated (manually constructed key lists and thresholds), a single malformed address or an incomplete active-permission list is a realistic and easy mistake, and the actuator provides no safety net (e.g., dry-run confirmation, delay, or "new key must co-sign" requirement) to catch it before the change becomes final.

### Recommendation
Introduce a two-step procedure for `AccountPermissionUpdateContract`-style permission changes: first "propose" the new permission set (recorded on-chain but not yet active), then require a confirming transaction — signed by at least one key in the proposed new owner permission — before `updatePermissions` commits the change. Alternatively, add a mandatory activation delay plus a cancellation window during which the current owner permission can still revert the pending change, and add a validation rule requiring the new owner permission to reference an address capable of confirming receipt.

### Proof of Concept
1. Enable multisig on the network (`AllowMultiSign = 1`, as done in `AccountPermissionUpdateActuatorTest.createCapsule`).
2. Owner account `X` broadcasts an `AccountPermissionUpdateContract` transaction (via `AccountPermissionUpdateServlet` or `wallet/accountpermissionupdate` gRPC API) setting the new `owner` permission's `keys` list to an address `Y` that nobody controls (typo/wrong address), as constructed in: [5](#0-4) 
3. `AccountPermissionUpdateActuator.execute` commits the change in the same transaction via `account.updatePermissions(...)`, replacing the owner permission immediately with no confirmation from `Y`: [6](#0-5) 
4. Once the block is confirmed, account `X` has permanently lost owner authority over its own account, since no key controlled by `X` remains in the owner permission, and there is no mechanism to revert the change.

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
