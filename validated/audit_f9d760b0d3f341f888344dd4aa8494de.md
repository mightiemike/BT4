### Title
Unbounded recursion on attacker-influenced CASM bytecode-segment structure can crash the sequencer / OS re-execution - (File: crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs, crates/starknet_api/src/contract_class/compiled_class_hash.rs, crates/blockifier/src/execution/contract_class.rs)

### Summary
Several functions that walk the `bytecode_segment_lengths` (`NestedIntList`/`NestedFeltCounts`) of a compiled (CASM) class recurse once per nesting level with **no depth bound and no resource metering**, unlike Cairo call-recursion which is explicitly protected by `RecursionDepthGuard`, `max_recursion_depth`, gas metering, and a dedicated large pre-allocated stack for native execution. The segment structure originates from the Sierra→CASM compilation of a contract submitted via an ordinary `Declare` transaction, so its shape is influenced by the declarer. A pathologically deep (chain-like) segmentation structure could drive native-stack recursion deep enough to overflow the thread stack and crash the process, mirroring the CVE-2021-46530 pattern where a crafted/malformed input drove unbounded recursion in an interpreter to a SEGV.

### Finding Description
Three consumers recurse over the nested segment-length tree with no depth guard:

- `bytecode_hash_node` in compiled-class-hash computation, called on every `Declare` (class hashing path): [1](#0-0) 

- `create_bytecode_segment_structure_inner`, used while loading classes for Starknet OS (re-)execution: [2](#0-1) 

- `get_visited_segments`, used by the blockifier when computing which bytecode segments were visited during execution: [3](#0-2) 

None of these functions bound `segmentation_depth`. This is in sharp contrast to `NestedFeltCounts::new_inner`, which explicitly asserts a maximum supported nesting of 1 (`assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.")`), showing the team is aware deep nesting is a real possibility that needs guarding — yet this guard is only applied in one of the several recursive consumers, and it uses `assert!` (itself a panic-based DoS if triggered) rather than a graceful, metered rejection: [4](#0-3) 

The `bytecode_segment_lengths` come directly from the `CasmContractClass` produced by compiling the declarer's Sierra program: [5](#0-4) 

By contrast, ordinary Cairo call-recursion (a very similar bug class) is deliberately hardened everywhere it's reachable from a transaction: a `RecursionDepthGuard` enforces `max_recursion_depth`, execution is additionally gas-metered so it terminates with `Out of gas` before real stack exhaustion, and Cairo Native execution pre-allocates a large thread stack sized specifically to survive `MAX_POSSIBLE_SIERRA_GAS` worth of recursion: [6](#0-5) [7](#0-6) 

The bytecode-segment recursion paths above have none of these mitigations: they run outside the gas-metered VM loop (during class hashing / OS hint preprocessing), are not covered by `max_recursion_depth`, and are not thread-stack-sized for worst case.

### Impact Explanation
If a declarer can shape a Sierra program whose compiled bytecode-segment structure is a deep, narrow chain of `NestedIntList::Node` wrappers (rather than a wide, shallow tree), then:
- Class-hash computation (`bytecode_hash_node`) executed by every node processing the `Declare` could stack-overflow and crash the node process — a Denial of Service reachable from a single unprivileged `Declare` transaction.
- The same structure re-processed during Starknet OS re-execution (`create_bytecode_segment_structure_inner`) could crash the OS/prover re-execution process, which is explicitly listed as an in-scope reachable path ("Starknet OS re-execution").

A process crash on any honest node processing the same transaction is a network-wide DoS candidate (matches "a network unable to confirm new transactions" if this hits enough sequencer/validator instances), which is the qualifying impact under the validation rules.

### Likelihood Explanation
Medium, with an important caveat: the actual *shape* of the `NestedIntList` tree is produced by the Sierra→CASM compiler in the external `cairo_lang_starknet_classes` crate, which is not part of this repository, so I could not directly verify from this codebase whether the compiler's segmentation algorithm can be steered by contract source code into a deep, narrow chain versus only ever producing shallow/wide trees. What is verifiable in-repo is that: (1) the consuming code in this repo places **no depth limit** on this structure in the class-hashing and OS-hint paths, (2) the one place that does assume shallow depth encodes that assumption as a hard, unguarded `assert!` rather than input validation, and (3) the team already recognizes and heavily engineers around this exact bug class (stack overflow via recursion) for the semantically similar Cairo call-recursion path, but that protection was not extended to bytecode-segment traversal. Given the uncertainty about compiler output shape, this should be treated as a plausible but unconfirmed root cause pending confirmation of how deep/narrow `bytecode_segment_lengths` can practically become for a `max_contract_bytecode_size`-sized declared class.

### Recommendation
- Add an explicit, gracefully-enforced maximum nesting depth check (returning a validation error, not `assert!`/panic) wherever `NestedIntList`/`NestedFeltCounts`/`BytecodeSegmentNode` trees are recursively traversed: `bytecode_hash_node` (compiled_class_hash.rs), `create_bytecode_segment_structure_inner` (starknet_os/utils.rs), `get_visited_segments` and `NestedFeltCounts::new_inner` (blockifier/contract_class.rs).
- Reject classes at declaration/validation time whose segment structure exceeds the supported depth, consistent with existing size limits like `max_contract_bytecode_size`.
- Alternatively, convert these recursive traversals to iterative (stack/queue-based) implementations to remove the native-stack dependency entirely.

### Proof of Concept
Not fully constructible from this repository alone, since generating a contract whose compiled `bytecode_segment_lengths` forms a deep narrow chain requires driving the external Sierra→CASM compiler's segmentation heuristic, which is outside this codebase. Conceptually: craft a Cairo1 contract (within `max_contract_bytecode_size`) structured so that the compiler emits deeply nested function/segment boundaries (e.g., many levels of nested inlined branches or successive small functions each becoming its own segment level), declare it via a standard `Declare` transaction, and observe whether `bytecode_hash_node` / `create_bytecode_segment_structure_inner` recursion depth scales with the nesting rather than being capped — a background engineering session with compiler access would be needed to confirm actual achievable nesting depth and reproduce a crash.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}

                }

fn get_visited_segments(
    segment_lengths: &NestedFeltCounts,
    visited_pcs: &mut Vec<usize>,
    bytecode_offset: &mut usize,
) -> Result<Vec<usize>, TransactionExecutionError> {
    let mut res = Vec::new();

    match segment_lengths {
        NestedFeltCounts::Leaf(length, _) => {
            let segment = *bytecode_offset..*bytecode_offset + length;
            if visited_pcs.last().is_some_and(|pc| segment.contains(pc)) {
                res.push(segment.start);
            }

            while visited_pcs.last().is_some_and(|pc| segment.contains(pc)) {
                visited_pcs.pop();
            }
            *bytecode_offset += length;
        }
        NestedFeltCounts::Node(segments) => {
            for segment in segments {
                let segment_start = *bytecode_offset;
                let next_visited_pc = visited_pcs.last().copied();

                let visited_inner_segments =
                    get_visited_segments(segment, visited_pcs, bytecode_offset)?;

                if next_visited_pc.is_some_and(|pc| pc != segment_start)
                    && !visited_inner_segments.is_empty()
                {
                    return Err(TransactionExecutionError::InvalidSegmentStructure(
                        next_visited_pc.unwrap(),
                        segment_start,
                    ));
                }

                res.extend(visited_inner_segments);
            }
        }
    }
    Ok(res)
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
