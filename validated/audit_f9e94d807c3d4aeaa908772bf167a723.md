### Title
Relayer Fee Refund Is Sent Unconditionally, Regardless of the Underlying Transfer's Success - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract's `inner_rlp_execute` fires an independent, un-chained "relayer refund" promise for the fee whenever an emulated base-token or ERC-20 transfer carries a non-zero fee, *before* the actual transfer promise is created and *without* linking the refund to the success of that transfer. This mirrors the "unchecked return value" bug class from the report: value is moved based on an assumed outcome ("the transfer will succeed") without verifying that outcome, allowing the wallet's funds to be paid out to the relayer even when the corresponding NEP-141/base-token transfer subsequently fails.

### Finding Description
In `inner_rlp_execute`, after parsing the RLP transaction into an `Action`/`TransactionKind`, the code eagerly schedules the relayer's fee refund as a standalone promise batch: [1](#0-0) 

This `env::promise_batch_create(&context.predecessor_account_id)` / `env::promise_batch_action_transfer` call creates a **new, independent receipt** — it is not `.then()`-chained to the promise that actually performs the requested transfer (`action_to_promise(...)`, the `storage_balance_of` → `storage_deposit` → `ft_transfer` chain, or the address-registrar lookup chain built afterward at lines 412-472): [2](#0-1) 

Because the refund promise is dispatched before, and independently of, the promise that performs the transfer, its execution and success are not conditioned on the transfer's outcome. The only downstream check, `rlp_execute_callback`, only inspects `env::promise_result(0)` of the *transfer* promise chain — it has no visibility into, and cannot roll back, the already-dispatched refund promise: [3](#0-2) 

This is the direct analog of the reported bug class: a value-moving operation (`transfer`) is treated as if it always succeeds, and the caller (here, the relayer) is compensated without checking the return/outcome of the operation that was supposed to justify the payment.

### Impact Explanation
A relayer (an unprivileged, arbitrary account that only needs a `FunctionCall` access key for `rlp_execute`, as shown in `test_wallet_contract_interaction`) can submit a validly-signed user transaction whose emulated transfer fails downstream — e.g., an `EOABaseTokenTransfer`/`ERC20Transfer` where the wallet has insufficient NEAR/token balance, or where the NEP-141 `ft_transfer`/`storage_deposit` receipt fails — yet the relayer will still receive the `fee` refund because that refund promise was already fired unconditionally. This constitutes unauthorized value movement out of the user's wallet contract to the relayer without the user's intended action being completed, directly matching the "Accept only concrete unauthorized value movement" criterion.

### Likelihood Explanation
The `fee` amount is attacker/relayer-influenced input derived from `tx.max_fee_per_gas * tx.gas_limit` (bounded by `VALUE_MAX`), computed in `parse_rlp_tx_to_action`: [4](#0-3) 

Any account holding an access key on the eth-implicit wallet (which, per the design doc, is explicitly meant to allow untrusted relayers to be granted a `FunctionCallPermission` key for `rlp_execute`) can trigger this path by crafting/relaying a transaction that is guaranteed or likely to fail downstream (e.g. an ERC-20 transfer to an account whose `storage_deposit` will fail, or a base-token transfer that drains the account below the amount needed, or exploiting normal EVM/relayer economics to always claim the fee even on failed sends) while still collecting the fee. This requires only a single crafted, signed transaction plus a relayer able to submit it — well within the reachable "single submitted transaction" threat model.

### Recommendation
Chain the relayer fee-refund transfer to the same promise as the actual action, and only execute it in the success branch (e.g. via a callback that inspects `PromiseResult` of the main transfer/ERC-20 action before issuing the refund), instead of firing it unconditionally and independently in `inner_rlp_execute`. Alternatively, include the fee-refund action as part of the same promise/receipt as the emulated transfer so that failure of the transfer also fails the refund atomically.

### Proof of Concept
1. Deploy the Wallet Contract to an eth-implicit account and register a relayer's access key restricted to `rlp_execute`, as in `test_wallet_contract_interaction`: [5](#0-4) 
2. Have the relayer submit an RLP-encoded ERC-20 `transfer` (selector `ERC20_TRANSFER_SELECTOR`) or base-token transfer with a non-zero `gas_price`/`fee`, targeting a token/account configuration engineered to fail post-dispatch (e.g., a token contract that reverts on `ft_transfer`, or insufficient wallet balance causing the base `Transfer` action to fail).
3. Because the refund promise created at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:381-384` is independent of the transfer promise, the relayer's account still receives `fee` yoctoNEAR even though `rlp_execute_callback` (lines 296-316) subsequently reports `success: false` for the main action.
4. Repeat with an intentionally-failing transfer to repeatedly drain fees from the wallet with no successful transfers, each time incrementing the nonce (nonce increments happen prior to/independently of the refund dispatch per the logic at lines 358-365), demonstrating unauthorized, repeatable value extraction.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

    // This is sent as a refund to the relayer in the case of an emulated base token
    // transfer or ERC-20 transfer. The reason for this refund is that it allows a
