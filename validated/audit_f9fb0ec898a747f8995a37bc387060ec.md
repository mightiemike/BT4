## Finding: `ensure_match_transaction_info` skips authenticated position/hot-state checkpoint hash verification during replay

### Title
Replay/state-sync consistency check silently ignores hot-state and trading-native position-state checkpoint hashes - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant check used by chunk executor/replay/debugger tooling to confirm that a locally-recomputed `TransactionOutput` matches the authenticated `TransactionInfo` fetched from storage/backup. It validates status, gas, write-set hash, and event-root hash, but the code explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields carried in `TransactionInfoV1`.

### Finding Description [1](#0-0) 

The function checks four invariants (`status`, `gas_used`, `write_set_hash` vs `state_change_hash`, and `event_root_hash`), and then contains this comment before returning `Ok(())` without further checks:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

This is analogous in structure to the reported bug pattern: a state-defining value (the collateral/position-derived root) is not actually re-verified — the code trusts a partial/derived signal (write-set hash, event hash, gas, status) instead of independently confirming the full committed state root that is bound to this transaction. Just as the Solidity code assumed 0 collateral based on a stale accessor instead of `balanceOf`, this Rust code omits comparing the locally computed `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` against the ones embedded in the trusted `TransactionInfo`.

`TransactionInfoV1` carries these fields as first-class, authenticated data included in the accumulator leaf hash: [2](#0-1) . The checkpoint hashes are produced by `DoStateCheckpoint::get_state_checkpoint_hashes`, which is the authoritative binding between the JMT/hot-state/position-state roots and a specific transaction/version [3](#0-2) .

### Impact Explanation
This is currently gated by the fact that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (position-state / "trading-native") is not yet enabled, per the comment itself. However:
- `ensure_match_transaction_info` is the actual mechanism used by `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` (`replay_on_archive`/replay-verify tooling) to detect divergence between local re-execution and the authenticated ledger.
- If/when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and `HOT_STATE_ROOT_IN_TXN_INFO`) is turned on, this comparator would allow a chunk/transaction whose locally-computed position-state or hot-state root diverges from the authenticated `TransactionInfo` to be accepted as "verified" — i.e., a corrupted or forked state root committed by a node (or introduced via a compromised backup/state-sync source) would not be caught by replay-verify, defeating the purpose of the check. This is exactly the class of "hard-fork-only divergence during commit/replay/restore or proof verification" the scope calls out.
- I could not fully confirm the current on/off status or rollout stage of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` beyond finding its plumbing across `types/src/block_executor/config.rs`, `execution/executor/src/workflow/do_get_execution_output.rs`, `execution/executor-types/src/execution_output.rs`, and `storage/aptosdb/src/db/aptosdb_reader.rs`; I was not able to inspect the feature-flag default/activation state or whether it is already live on any network within the remaining budget.

### Likelihood Explanation
This is a code-documented gap (the TODO explicitly states the exact failure mode), not a speculative one, so the root cause is confirmed. However, the exploitability/likelihood is conditional: it only matters once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and/or `HOT_STATE_ROOT_IN_TXN_INFO`) is enabled in a live network, and it requires the local execution/derived root to actually diverge from the authenticated one for the gap to matter (e.g., a bug elsewhere in the position-state pipeline, or a malicious backup/state-sync source with divergent hot/position roots). I could not verify from the index whether these feature flags are currently active on mainnet, which is required to assess whether this is presently exploitable versus a documented future-risk item.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (for `TransactionInfoV1`) against the locally recomputed values before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled, exactly as the existing TODO comment recommends, so that replay-verify tooling cannot report success on a diverging authenticated state root.

### Proof of Concept
Not applicable as an active exploit today — the gap is dormant while `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is disabled. The "proof" is the source itself: `ensure_match_transaction_info` returns `Ok(())` at [4](#0-3)  without ever reading `txn_info`'s `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, meaning any caller relying on this function (chunk executor replay, `aptos-debugger`, `aptos move` CLI replay commands) to validate a `TransactionOutput` against a trusted, remotely-sourced `TransactionInfo` will not detect a mismatch confined to those three fields.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
