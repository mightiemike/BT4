## Analysis

The external report's core pattern is: **a two-sided invariant check that validates one side (buyer funds) but not the other (seller funds)**, allowing a state transition to be accepted despite an unverified condition.

The strongest Aptos-native analog is in the transaction-output/transaction-info equivalence check used by replay-verify tooling.

### Title
Replay-verify comparator `ensure_match_transaction_info()` skips checkpoint-hash validation, allowing divergent state/position roots to pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the authenticated-equivalence check used to confirm that a locally re-executed transaction output matches the `TransactionInfo` recorded in the backup/archive during replay. It validates status, gas, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a fact the code itself documents as a known gap.

### Finding Description [1](#0-0) 

The function checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but the trailing comment states plainly:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```
This is exactly the "checks buyer funds but not seller funds" pattern: the comparator only confirms half of the committed state (write set + events), while the other authenticated commitments (the sparse-merkle state-checkpoint root, hot-state checkpoint root, and the newer "position" Merkle root) are silently skipped.

This function is invoked from the chunk executor's `verify_execution`, which is the code path used by `replay_on_archive` / `replay-verify` to confirm that locally-executed results match what is recorded as authoritative in the archive: [2](#0-1) 

### Impact Explanation
Replay-verify (`db-tool replay-on-archive`, `replay_verify`) is the mechanism operators and the Aptos Labs release pipeline use to confirm that a proposed VM/runtime change reproduces byte-identical committed state across historical mainnet transactions before it is trusted for a hard fork or release. Because the checkpoint hashes (state root, hot-state root, and position-state root) are not compared, a regression that alters state, hot-state, or position (native trading) tree contents — while leaving the write set and events unchanged — will be reported as a **successful, verified replay**, even though the actual persisted Merkle roots differ from the archived, authenticated values. This can mask a hard-fork-only state divergence exactly in the category this review is scoped to accept (wrong state root treated as verified because the check that should catch it is absent).

### Likelihood Explanation
The gap is deterministic and always present (not a race or a rare edge case): any code path that produces a correct `write_set`/events for a transaction but a different resulting checkpoint root (state, hot-state, or the newer position tree) will pass this check unconditionally, every time it is invoked. The comment in the code confirms Aptos engineers were already aware of the gap ahead of enabling the related feature flag, but the fix had not landed in this checkout.

### Recommendation
Extend `ensure_match_transaction_info()` to also compare `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` (when present) against locally computed values before returning `Ok(())`, so replay-verify cannot certify a divergent ledger state as matching.

### Proof of Concept
Not directly exploitable by an external attacker (no adversarial network input triggers it); it is a tooling/verification gap. Conceptually: construct a `TransactionOutput` whose `write_set()` and `events()` hash identically to a given `TransactionInfo`, but whose replay produces a state tree (or hot-state/position tree) with a different root than `txn_info.state_checkpoint_hash()` (e.g., by having local execution incorrectly promote/skip a hot-state entry, as exercised in [3](#0-2)  for the position "hotness" write path). `ensure_match_transaction_info` returns `Ok(())` regardless, so `execute_and_verify`/`verify_execution` in the chunk executor reports success for a version whose durable checkpoint root has silently diverged.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
