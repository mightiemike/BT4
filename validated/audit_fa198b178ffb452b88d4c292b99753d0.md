## Verdict: Partially valid — real caching gap exists, but the specific "gas divergence" mechanism claimed is not accurate

### Title
Unversioned, first-writer-wins `ScriptCache::insert_verified_script` can serve a script permanently bound to a stale/speculative dependency snapshot to unrelated transactions in the same block - (File: `third_party/move/move-vm/types/src/code/cache/script_cache.rs`)

### Summary
`insert_verified_script`'s occupied-and-already-verified branch never overwrites the cached entry — it silently discards the caller's newly-built `verified_script` and returns whatever was cached first: `entry.get().verified().clone()` [1](#0-0) [2](#0-1) . The cache key is only `sha3_256(serialized_script)` [3](#0-2)  — it carries no notion of which module versions the cached `Script`'s `immediate_dependencies` were linked against, and unlike `SyncModuleCache`/`GlobalModuleCache`, which use `VersionedModuleCode` and reject/replace stale versions with an explicit `version_too_small_error!` [4](#0-3) , there is no equivalent version-aware invalidation for scripts.

### Finding Description
`EagerLoader::unmetered_verify_and_cache_script` resolves `immediate_dependencies` via `unmetered_get_existing_eagerly_verified_module` and builds `verified_script` from that specific set, then calls `insert_verified_script` [5](#0-4) . Within Block-STM, this script cache is the `SyncScriptCache` embedded in the per-block `MVHashMap`, shared across all transactions/incarnations executing within that block [6](#0-5) .

Each individual module dependency lookup is captured and validated per-incarnation via `CapturedReads`/`validate_module_reads`, and if a module read turns out to be stale relative to the final ordering, that incarnation is aborted and re-executed [7](#0-6) . That protects the aborted transaction's own output. However, the *side effect* of that aborted incarnation — the `Verified(Script)` entry it inserted into the shared script cache, bound to the stale dependency set — is not rolled back. Because `insert_verified_script` never replaces an already-verified entry, that stale entry becomes the canonical result for every future caller with the same script hash, for the rest of the block, with no re-validation tied to the module cache's own versioning/`mark_overridden` mechanism used for modules [8](#0-7) .

This is consistent with the acknowledged design gap that the newer MonoMove loader design doc explicitly calls out and aims to fix — that speculative execution can make "some transaction upgrade module A, and other transaction end up seeing both old and new versions at the same time" — and states the current design's read-set-consistency guarantee applies at the module level, not necessarily to derived artifacts like verified scripts [9](#0-8) .

### Correction to the proof idea in the question
The specific mechanism alleged — "gas charged for `check_dependencies_and_charge_gas` diverging from the actual dependencies used by the cached verified script" — does not hold up under inspection. Gas for script dependencies is charged using `compiled_script.immediate_dependencies_iter()` (the declared `ModuleId` list from the *deserialized* script, not the `Arc<Module>` pointers embedded in the cached `Verified(Script)`), and `check_dependencies_and_charge_gas` performs its own fresh, per-transaction module resolution which is itself subject to the standard captured-reads validation [10](#0-9) . So gas metering for a given transaction is not driven by whatever dependency set happens to be baked into the cached `Script`; it is independently re-derived and validated. The state-integrity risk, if any, would instead have to come from actual linking/verification-outcome or execution-semantic differences frozen into the cached `Script` object itself (e.g., if `build_verified_script`'s type/signature checks against a stale module version would have produced a different accept/reject decision, or if runtime dispatch actually uses the embedded dependency pointers rather than re-resolving per call).

### Impact Explanation
If confirmed to affect actual verification-decision or execution behavior (not just gas), this could plausibly produce validator-dependent (cache-hit-timing-dependent) divergence in whether a script's execution succeeds/fails or in which module version's code it links against within a block — a hard-fork-class concern. However, I could not fully verify from the available code whether interpreter execution of a `LoadedFunction`/`Script` actually reuses the `Arc<Module>` pointers embedded at verification time for subsequent calls, or whether every call re-resolves modules afresh through the transaction's own (validated) view. This distinction is central to whether the bug is merely a caching efficiency/correctness inconsistency (harmless if execution always re-resolves calls) or an actual state-committing divergence (harmful if stale bindings are used for execution).

### Likelihood Explanation
This requires: (1) a script whose bytecode hash collides across two transactions/incarnations in the same block, (2) one of those incarnations reading a dependency module version that is later invalidated (a normal, not-uncommon occurrence under Block-STM speculation, especially around module publish/upgrade transactions), and (3) the frozen dependency set actually mattering for subsequent execution/verification outcomes rather than being purely advisory. Component (1) and (2) are readily achievable by unprivileged input (any script + any module upgrade transaction ordered nearby in the same block). Component (3) is unconfirmed.

### Recommendation
- Tie script cache entries to the same version/invalidation mechanism used for modules (e.g., record the max transaction index of modules used to build `immediate_dependencies`, and reject/replace cache entries analogous to `version_too_small_error!` in `module_cache.rs`), or
- Ensure (and add an explicit test proving) that runtime execution of a verified `Script` never relies on the specific `Arc<Module>` dependency pointers captured at verification time, and instead always re-resolves modules per-call through each transaction's own validated read path, making the frozen dependency snapshot purely a verification-time artifact with no execution-time effect.

### Proof of Concept
Not independently reproducible from the available static analysis — a full PoC would require instrumenting Block-STM to force an abort of the first script-caching incarnation after it inserts into `SyncScriptCache`, then observing whether a second, correct-view transaction using the same script bytes exhibits different execution results (not just re-verifies). This exceeds what can be confirmed via code reading alone; a live/test-harness reproduction in `aptos-move/block-executor` (e.g., extending `test_block_cache_module_reads`-style tests in `captured_reads.rs` to cover scripts) would be needed to conclusively confirm or refute execution-level impact.

**File:** third_party/move/mono-move/loader/DESIGN.md (L15-22)
```markdown
When a single transaction executes, it may "load" modules into its local read-set.
The read-set is used to cache a consistent local view of the cache for transaction.
This is needed to avoid cases where some transaction upgrades module `A`, and other transaction ends up seeing both old and new versions at the same time.

Loading a module can either be a hit in long-living module cache or a miss.
On a miss, loader fetches the module from storage, deserializes it, verifies, translates to execution IR, and adds it to the long-living cache.
To cover for the worst case, every module load has to be charged gas.
Importantly, the charging must be **deterministic** irrespective of the cache state that may be different on different validators due to speculation.
```
