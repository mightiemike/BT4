## Finding

### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, letting `replay_on_archive` accept a corrupted or diverged state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole consistency check used by the `db-tool replay-on-archive` verifier to confirm that locally re-executed transaction outputs match the authenticated `TransactionInfo` recorded in a backup/archive. The function verifies status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of `TransactionInfoV1` and are themselves committed to the transaction accumulator / ledger info. As a result, the tool can report a "successful replay" even when the locally computed state root (including the native-position state root gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) diverges from the authenticated on-chain value.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks:
- execution status equality,
- gas used equality,
- write-set hash vs `txn_info.state_change_hash()`,
- event root hash vs `txn_info.event_root_hash()`,

then returns `Ok(())` without checking `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The function's own comment acknowledges the gap: [2](#0-1) .

This is the only comparator used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which drives blocks through `AptosVMBlockExecutor::execute_block` directly (bypassing `DoStateCheckpoint`/`DoLedgerUpdate`) and then calls `ensure_match_transaction_info` per transaction: [3](#0-2) .

By contrast, the production commit/chunk-sync path (`chunk_executor::update_ledger`) does validate these same checkpoint hashes against `known_state_checkpoints` / `known_position_state_checkpoints` via `DoStateCheckpoint::get_state_checkpoint_hashes`, which uses `ensure!` to hard-fail on mismatch: [4](#0-3)  fed from `execution/executor/src/chunk_executor/mod.rs` lines 380-394. So the production sync/replay pipeline is protected, but the standalone `replay_on_archive` auditing tool — whose stated purpose is to validate consensus-committed history against an executed VM re-run — is not, because it never runs the `DoStateCheckpoint` stage nor checks these hash fields in `ensure_match_transaction_info`.

### Impact Explanation
`replay_on_archive` is an authenticated-replay/verification tool relied on to detect divergence between local re-execution and the historically committed (and BFT-signed) ledger state, specifically for the new trading-native state root feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`). Because the checkpoint hash fields are silently skipped, a bug in native-position state computation, hot-state computation, or main-state checkpoint computation that causes hard-fork-only divergence would not be caught by this tool: it would report a clean, successful replay while the locally computed position/state/hot-state root differs from the authenticated one recorded on-chain. This directly matches the required impact "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Authenticated API ... output bound to the wrong version, object, or proof context," since the tool's raison d'être is verifying exactly this binding.

### Likelihood Explanation
This is not a hypothetical edge case — the checkpoint-hash skip is unconditional in `ensure_match_transaction_info`, it applies every time `replay_on_archive` is run, and the feature flags (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) are newly-introduced permanent-lifetime flags actively being rolled into `TransactionInfoV1`. Any latent bug in the new native-position/hot-state root computation logic would go completely undetected by this specific verification tool until/unless some other detection mechanism (e.g. live consensus divergence) surfaces it.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values (when the corresponding feature is enabled and a checkpoint boundary applies), mirroring the checks already performed in `DoStateCheckpoint::get_state_checkpoint_hashes`. Alternatively, route `replay_on_archive` through the same `DoStateCheckpoint`/`DoLedgerUpdate` pipeline used by `chunk_executor` so checkpoint-hash validation is enforced consistently across all replay/verification code paths.

### Proof of Concept
1. Enable `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and commit a block whose native-position writes are correctly written to storage but whose in-memory position Merkle root computation has a bug causing the wrong `position_state_checkpoint_hash` to be recorded in the archived `TransactionInfoV1` (i.e., an authenticated but internally-inconsistent history, or simulate by patching the position tree computation used at replay time to diverge from the original).
2. Run `db-tool replay-on-archive` against the backup covering that version range: `storage/db-tool/src/replay_on_archive.rs` `Verifier::run` → `execute_and_verify` → `ensure_match_transaction_info`.
3. Observe that the tool reports success (`Ok(())` from `ensure_match_transaction_info`) even though the position root computed during local VM re-execution does not match `expected_txn_infos[idx].position_state_checkpoint_hash()`, because that field is never compared. In contrast, the same divergence during normal chunk sync (`chunk_executor::update_ledger`) would be caught by the `ensure!` in `do_state_checkpoint.rs`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
