### Title
Proof-of-Reserve CRE workflow ignores `TxStatus`/`ReceiverContractExecutionStatus` after `WriteReport`, causing silent on-chain reporting failures - (File: `system-tests/tests/canaries_sentinels/proof-of-reserve/cron-based/main.go`)

### Summary
The Proof-of-Reserve cron-based CRE workflow's `onTrigger` function submits a signed report via `evmClient.WriteReport` and only checks whether the top-level `Await()` call returned a Go `error`. It then inspects only the `ErrorMessage` field of the `WriteReportReply` for a human-readable status string, but never validates `TxStatus` or `ReceiverContractExecutionStatus`, and treats the workflow as successful regardless of on-chain execution outcome.

### Finding Description
In `onTrigger`, the report write is performed here: [1](#0-0) 

The reply type returned by `WriteReport`, `evm.WriteReportReply`, carries a `TxStatus`, an optional `ReceiverContractExecutionStatus`, and an optional `ErrorMessage`, as demonstrated by the reference implementation in the EVM fake chain used for local/simulated execution: on a receiver-side revert it still returns a non-nil `WriteReportReply` (no top-level Go error) with `TxStatus = TX_STATUS_REVERTED` and `ReceiverContractExecutionStatus = RECEIVER_CONTRACT_EXECUTION_STATUS_REVERTED`: [2](#0-1) 

The PoR workflow's success/failure handling is:
```go
wrOutput, err := evmClient.WriteReport(runtime, &evm.WriteCreReportRequest{...}).Await()
if err != nil {
    ...
    return "", fmt.Errorf("failed to write report on-chain: %w", err)
}
...
var message = "PoR Workflow successfully completed"
if wrOutput.ErrorMessage != nil {
    message = *wrOutput.ErrorMessage
}
return message, nil
``` [3](#0-2) 

Because a top-level revert on the receiver contract (e.g., forwarder succeeds but `onReport` reverts) does **not** produce a Go `error` from `Await()` — it is surfaced only via `TxStatus`/`ReceiverContractExecutionStatus`/`ErrorMessage` in the reply — the workflow proceeds past the `err != nil` check. It only substitutes the `ErrorMessage` string into the returned `message`, but still returns a nil error (`return message, nil`), so the workflow execution is recorded as a completed/successful run regardless of the actual outcome. This mirrors exactly the reported CRE `writeCloseRounds.ts` pattern: reading only a subset of `WriteReportReply` fields (here, only `ErrorMessage`, and not even branching on it) and treating every reply as a successful workflow completion.

The existing regression test suite for EVM writes (`system-tests/tests/regression/cre/evm/evmwrite-negative/main.go`) demonstrates the correct pattern — checking `ReceiverContractExecutionStatus` and `TxStatus` explicitly — confirming that the PoR canary workflow deviates from the established safe pattern: [4](#0-3) 

### Impact Explanation
Each cron tick (every minute, per the configured schedule) that encounters a persistent revert condition on the receiver (data-feeds cache) contract — e.g., forwarder not whitelisted for that DON round, stale/expired report, config drift, or any `onReport` revert — will:
- Broadcast a transaction consuming up to the configured `GasLimit` (400,000 gas) on every tick, with no back-off or halt, since the workflow always returns success.
- Report `"PoR Workflow successfully completed"` even when the on-chain write reverted, unless the caller happens to inspect the returned message string for embedded revert text (which is not surfaced as a failure state, alert, or non-zero exit).
- Provide no signal to CRE/monitoring/dashboards that the PoR feed has stopped being updated on-chain, delaying detection of a proof-of-reserve outage indefinitely (until manual on-chain inspection), which is a misreporting/data-integrity concern for a proof-of-reserve pipeline whose entire purpose is to catch reserve mismatches or halt on `Ripcord`.

This is functionally the same silent-failure/gas-waste/misreporting class as the external report, applied to production canary/monitoring workflow code in this repo, not just a mocked or test-only path — the `onTrigger` function is the actual workflow entrypoint executed on the wasm runtime (`//go:build wasip1`) that would run in a live CRE deployment.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where the receiver contract's write path can revert independent of the forwarder's own success (which is the entire justification for the `ReceiverContractExecutionStatus` field existing separately from `TxStatus`/Go `error`). Any transient or persistent contract-state precondition failure (wrong workflow ID, missing role, stale price bounds, config mismatch) will trigger this silently, and because the schedule runs every minute indefinitely, the condition is very likely to recur and accumulate cost/risk once triggered.

### Recommendation
Check `wrOutput.TxStatus` and `wrOutput.ReceiverContractExecutionStatus` explicitly after `WriteReport`, returning a non-nil error (and/or a distinct failure status string) instead of merely embedding `ErrorMessage` into an otherwise-successful return value, mirroring the pattern already used in `evmwrite-negative/main.go`:
```go
if wrOutput.TxStatus != evm.TxStatus_TX_STATUS_SUCCESS ||
    wrOutput.GetReceiverContractExecutionStatus() == evm.ReceiverContractExecutionStatus_RECEIVER_CONTRACT_EXECUTION_STATUS_REVERTED {
    errMsg := ""
    if wrOutput.ErrorMessage != nil {
        errMsg = *wrOutput.ErrorMessage
    }
    return "", fmt.Errorf("WriteReport failed: txStatus=%s receiverStatus=%s error=%s",
        wrOutput.TxStatus, wrOutput.GetReceiverContractExecutionStatus(), errMsg)
}
```
Also propagate this failure into workflow-level metrics/alerts so that repeated on-chain reverts are visible in monitoring rather than only in workflow logs.

### Proof of Concept
1. Deploy the PoR cron-based workflow with `DataFeedsCacheAddress` pointed at a receiver contract that reverts `onReport` under some condition reachable in production (e.g., stale timestamp, role/config mismatch) — see `system-tests/tests/canaries_sentinels/proof-of-reserve/cron-based/main.go` lines 152–182.
2. On each cron tick (every minute per `cron.Config{Schedule: "0 * * * * *"}`), `evmClient.WriteReport` returns a `WriteReportReply` with `TxStatus = TX_STATUS_REVERTED` / `ReceiverContractExecutionStatus = RECEIVER_CONTRACT_EXECUTION_STATUS_REVERTED` and a non-nil `ErrorMessage`, but `Await()` returns `err == nil` (as demonstrated by `FakeEVMChain.WriteReport`'s revert branch returning a populated reply with no Go error): `core/capabilities/fakes/evm_chain.go` lines 219–234.
3. `onTrigger` skips the `err != nil` branch, sets `message = *wrOutput.ErrorMessage`, and returns `(message, nil)` — a successful workflow completion despite the on-chain revert.
4. Every subsequent minute repeats step 2–3, burning gas indefinitely with no automated alert distinguishing this from a genuinely successful PoR update.

func runWriteReportFailingOnReceiver(evmClient evm.Client, runtime cre.Runtime, wfCfg config.Config, report *cre.Report) (*evm.WriteReportReply, error) {
	runtime.Logger().Info("Attempting to write report that should fail on the receiver")
	receiver := wfCfg.DataFeedsCache.DataFeedsCacheAddress.Bytes()
	wrOutput, err := writeReport(runtime, evmClient, receiver, report, &evm.GasConfig{GasLimit: 400000})
	if err != nil {
		runtime.Logger().Error("got unexpected error", "error", err)
		return nil, fmt.Errorf("unexpected error for WriteReport  %w", err)
	}

	if wrOutput.GetReceiverContractExecutionStatus() == evm.ReceiverContractExecutionStatus_RECEIVER_CONTRACT_EXECUTION_STATUS_REVERTED {
		runtime.Logger().Info("WriteReport failed on the receiver and set the tx status to reverted")
		return nil, fmt.Errorf("expected WriteReport to fail on the receiver")
	}

	if wrOutput == nil {
		runtime.Logger().Error("got unexpected nil output for WriteReport with no error")
		return nil, fmt.Errorf("unexpected nil output for WriteReport with no error")
	}
	runtime.Logger().Info("This is not expected, WriteReport should fail on the receiver and set the receiver contract execution status to reverted, instead got", "receiver contract execution status", wrOutput.ReceiverContractExecutionStatus)
	return wrOutput, fmt.Errorf("writeReport should've returned tx status reverted, but instead returned %d", wrOutput.TxStatus)
}
