### Title
Node-unreachable fallback in `check_latest_block_in_tenure` folds an RPC error into an "accept" verdict, causing signer-set validation divergence - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_latest_block_in_tenure` fetches the tenure tip from the Stacks node via `client.get_tenure_tip(tenure_id)` to decide whether a block proposal's chain length is actually higher than the tenure's current tip. When this RPC call errors (e.g., because the signer's paired node is temporarily unreachable), the function does not propagate a distinguishable error/indeterminate result — it silently coerces the failure into `Ok(true)` ("assume proposal is higher"), the same code path used for a genuine successful validation.

### Finding Description
The function is:
```rust
let tip = match client.get_tenure_tip(tenure_id) {
    Ok(tip) => tip.anchored_header,
    Err(e) => {
        warn!(
            "Failed to fetch the tenure tip for the parent tenure: {e:?}. Assuming proposal is higher than the parent tenure for now.";
            ...
        );
        return Ok(true);
    }
};
``` [1](#0-0) 

This is functionally the same defect pattern as the reported Solidity issue: a fallible external call's failure is not handled as its own case with correct semantics; instead it is merged into one of the two "normal" outcomes of the check (`Ok(true)`/"proposal accepted as valid"), rather than being surfaced as an error that halts processing or is otherwise treated distinctly from "validation succeeded." The design intent (documented in `docs/signer-flows.md`) is explicit about this: "node unreachable → assume higher — node's proposal endpoint is the backstop." [2](#0-1) 

Because `check_latest_block_in_tenure` feeds directly into `check_tenure_change_confirms_parent` and `confirms_latest_block_in_same_tenure`, which in turn gate whether a signer accepts or rejects a tenure-change/continuation block [3](#0-2) , a signer whose paired Stacks node is transiently unreachable (a condition entirely outside its control and not requiring any privileged or majority action against the network) will validate a block as passing this check purely due to an RPC hiccup, while other signers with healthy node connections correctly compute `tip.height() < block.header.chain_length` and may reject the same proposal.

### Impact Explanation
This does not itself accept an invalid *chain state* — it is scoped to the signer's local decision on whether a specific tenure/proposal check passes. However, it can cause different honest, unprivileged signers to reach different verdicts on the same block proposal purely because of transient node connectivity, which is exactly the class of "validation verdict two nodes disagree on" that the rules classify as High-impact temporary tip disagreement: some signers may sign/pre-commit a block that should have been rejected as not confirming the expected parent/tenure tip, contributing weight toward a proposal that other signers reject, potentially delaying consensus or (in combination with other signers being similarly affected) allowing a proposal to cross the signing threshold that a fully-informed signer set would have rejected.

### Likelihood Explanation
Likelihood is Medium: it requires a signer-to-node RPC failure (a network blip, a restart, or a load spike on the signer's associated node) at the moment a tenure-change/continuation proposal is being validated — a naturally occurring, minority-triggerable condition (a single signer's node), not requiring any majority coordination, admin access, or another party's key.

### Recommendation
Do not collapse an RPC/connectivity failure into the `Ok(true)` success branch. Return a distinct error (or an explicit `Option`/`Result` variant indicating "indeterminate — node unreachable") from `check_latest_block_in_tenure` so callers can decide to retry, delay signing, or reject/abstain rather than silently treating a failed height check as a passed one. This keeps the "node's proposal endpoint is the backstop" design intent but requires the caller to make an explicit, auditable choice about how to treat backstop failure instead of implicitly voting "accept."

### Proof of Concept
1. Configure a signer whose paired Stacks node's `/v3/tenures/info` (or equivalent tenure-tip RPC) endpoint is made temporarily unavailable (e.g., via network partition or node restart) right as a tenure-change block proposal referencing that parent tenure arrives.
2. The signer calls `SortitionData::check_tenure_change_confirms_parent` → `check_latest_block_in_tenure`, whose `client.get_tenure_tip(tenure_id)` call fails.
3. Per the code path, the function returns `Ok(true)`, so `confirms_expected_parent` is `true` and the tenure-change validation proceeds past this check as if the proposal legitimately confirms a higher tip than the parent tenure's actual last block. [4](#0-3) 
4. Meanwhile, other signers whose nodes are reachable perform the real `tip.height() < block.header.chain_length` comparison and may reject the same proposal as not confirming the expected parent tip.
5. Result: signers disagree on the validity of the same block purely due to one signer's transient node connectivity, not due to any difference in the proposal's actual correctness — a verdict divergence bounded to temporary tip disagreement among honest signers.
