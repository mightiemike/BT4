### Title
Unbounded array-size read from felt allows OOM/DoS in deprecated syscall handling - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The analog bug class in the OneFlow CVE is: an externally-influenced size parameter is used to allocate/construct a buffer without an upper bound check, causing a Denial of Service. The Cairo-0 (deprecated) syscall array reader `read_felt_array` reproduces this pattern: it takes a raw felt value directly from Cairo VM memory as the declared array length and converts it to a `usize` with no upper-bound validation before using it to read/allocate a felt range.

### Finding Description
`read_felt_array` in the deprecated-syscalls hint processor reads `array_size` as an arbitrary `Felt` from VM memory (the syscall request structure written by the executing Cairo 0 contract code) and converts it directly to `usize`: [1](#0-0) 

Unlike the modern syscall implementation, which derives the array length from the difference between a start and end `Relocatable` pointer (`array_data_end_ptr - array_data_start_ptr`), which is bounded by actual allocated VM segments: [2](#0-1) 

the deprecated path trusts a size value supplied as a plain felt with only a zero-check, then forwards it as the requested length to `felt_range_from_ptr` (`crates/blockifier/src/execution/execution_utils.rs`). This is the same class of bug as CVE-2025-71011: a size/shape value taken from input is used to size a buffer/read operation without a sanity bound, so an attacker can supply an astronomically large value (limited only by `usize`/felt range) to force the executor to attempt a huge memory read/allocation.

### Impact Explanation
This path is reachable by any contract deployer who deploys a Cairo 0 (deprecated) class that issues a deprecated syscall using an array-typed request (e.g., library-call/data-segment style syscalls processed via `read_felt_array`), and by any transaction sender who then invokes that contract. If `felt_range_from_ptr`/the underlying `usize`-sized read causes a large allocation or an unhandled resource exhaustion before validation against the actual segment size, every sequencer node executing that transaction hits the same code path deterministically. This can crash or stall the node process, which — since all honest nodes must re-execute the same transaction to reach state agreement — can produce a network-wide denial of service (nodes unable to confirm new transactions), matching the CVE's DoS class translated to this codebase's execution path.

### Likelihood Explanation
Medium: reaching this code requires only deploying a Cairo 0 class and invoking it — no special privileges — matching the "contract deployer"/"unprivileged transaction sender" threat model allowed by scope. The severity depends on how `felt_range_from_ptr` and the underlying cairo-vm memory-read primitives behave for an out-of-range huge length (whether they pre-allocate before validating the segment exists). I could not fully confirm the internal allocation strategy of `felt_range_from_ptr`/cairo-vm's range-read primitive within this repo's indexed content, since its concrete body is defined via an external cairo-vm dependency call chain not fully resolvable here — this is the main uncertainty in confirming exploitability versus a benign early `MemoryError`.

### Recommendation
Bound `array_size` in `read_felt_array` (deprecated_syscalls/hint_processor.rs) to a sane maximum (e.g., calldata/segment size limits already enforced elsewhere) before converting to `usize` and before calling `felt_range_from_ptr`, or validate the target memory range's existence prior to allocating a `Vec` of that length — mirroring the safer start/end-pointer-derived length approach used in the non-deprecated `syscalls/hint_processor.rs::read_felt_array`.

### Proof of Concept
1. Deploy a Cairo 0 class whose entry point constructs a deprecated syscall request (any syscall that goes through `read_felt_array`, e.g. one using an array of felts in its request) but writes an extremely large felt (e.g. `2^128 - 1`) into the `array_size` slot instead of the real array length, followed by a valid `Relocatable` for `array_data_start_ptr`.
2. Send a transaction invoking this entry point.
3. During execution, `read_felt_array` converts the huge felt to `usize` and calls `felt_range_from_ptr` with that length, triggering an oversized read/allocation attempt on every executing node, deterministically degrading or crashing the node's execution of that block. [3](#0-2)

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
