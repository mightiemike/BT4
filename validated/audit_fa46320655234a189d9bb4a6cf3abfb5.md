### Title
Byte-sum estimate in `many_ref_accounts_can_be_moved` can underestimate actual bin-packing buckets, letting multi-ref accounts be packed into a slot lower than their current slot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
`AccountsDb::many_ref_accounts_can_be_moved` decides whether it is safe to relocate "many-ref, newest" accounts into the top N target slots using a coarse `alive_bytes / ideal_storage_size` estimate, but the actual bin-packer `PackedAncientStorage::pack` is a *next-fit* algorithm that can require substantially more buckets than that estimate when individual account sizes are adversarially chosen. This mismatch can let the safety check pass while the real packing places a many-ref account's data into a target slot below the slot it is required to stay at or above.

### Finding Description
`combine_ancient_slots_packed_internal` (`accounts-db/src/ancient_append_vecs.rs:417-518`) computes `many_refs_newest` (accounts with `ref_count > 1` that are alive in more than one ancient slot, sorted highest-slot-first) and validates feasibility with: [1](#0-0) 

`required_ideal_packed` is derived purely from `alive_bytes / ideal_storage_size + 1` — an estimate of the *minimum possible* number of buckets (essentially `ceil(alive_bytes/ideal_size)`), assuming perfect packing. The check then verifies that the lowest of the top `required_ideal_packed` target slots is still `>=` every many-ref account's current slot.

The actual packer, `PackedAncientStorage::pack`, is a **next-fit** bin packer: it never revisits an earlier, partially-filled bucket once it moves to a new one, and it closes the current bucket as soon as the *next* account would overflow `ideal_size`: [2](#0-1) 

Next-fit bin packing has a well-known worst case of using up to ~2x the optimal number of bins when item sizes are adversarially chosen (e.g. alternating a tiny account with a large account forces each bucket to close almost empty). Because `required_ideal_packed` approximates the *optimal* bucket count (not next-fit's actual bucket count), an attacker who controls account data sizes can force the real number of many-ref buckets `m` produced by `pack()` to exceed `required_ideal_packed`.

The many-ref buckets are placed first in the packed sequence (`many_refs_newest.iter().chain(...)`, sorted highest-slot-first) and are matched to target slots via: [3](#0-2) 

Since `target_slots_sorted` is ascending and iterated in reverse, the first `m` packed buckets are always mapped to the *top `m`* target slots — regardless of what `required_ideal_packed` predicted. If `m > required_ideal_packed`, the many-ref account that `many_ref_accounts_can_be_moved` verified against `target_slots_sorted[len - required_ideal_packed]` (a comparatively high slot) can actually be written into `target_slots_sorted[len - m]`, a lower slot than checked and potentially lower than the account's current slot — violating the documented invariant "accounts in `many_refs_newest` must be moved a slot >= each account's current slot."

The only remaining safety net is a total-count guard: [4](#0-3) 

This only aborts the whole packing if the *total* bucket count (many-ref + one-ref) exceeds the number of target slots; it does not verify that each individual many-ref account still lands at or above its own current slot. If there is slack from one-ref accounts (fewer bytes there than assumed), the total count can still fit while the specific many-ref-to-slot mapping is wrong.

### Impact Explanation
If a many-ref account is written to a slot below its true current/alive slot during ancient squashing, the accounts index can end up shadowing the newest version of an account behind an older, lower-slot entry for the same pubkey that was not yet cleaned. Subsequent reads keyed by ancestor/root slot could then resolve to the wrong (stale) version of the account data — a silent stale/incorrect account load, matching the "stale or wrong-version account load" bounty category. In the worst case this could also produce accounts-hash/capitalization divergence between nodes if the corruption is not always deterministic in when it triggers relative to snapshotting.

### Likelihood Explanation
Triggering requires the attacker (unprivileged) to: (1) create/rewrite the same pubkey across multiple ancient slots so it accumulates `ref_count > 1` and lands in `many_refs_newest`, and (2) choose account data sizes across those writes (and neighboring one-ref accounts in the batch) that force next-fit fragmentation relative to `ideal_storage_size` (currently `get_ancient_append_vec_capacity()`, a large fixed constant). Constructing such sizes is fully within attacker control (account data length, lamports, write frequency), but assembling the exact combination of many-ref accounts, competing one-ref slack, and slot ordering needed to make `pack.len() <= target_slots_sorted.len()` while still misplacing a specific many-ref bucket is intricate and requires precise control over the ancient-slot shrink candidate set, which is a background/periodic maintenance path (`combine_ancient_slots_packed`) that isn't directly invocable by the attacker — it must be provoked indirectly by normal account activity and observed to occur eventually.

### Recommendation
Replace the byte-sum heuristic in `many_ref_accounts_can_be_moved` with an actual simulation of `PackedAncientStorage::pack` (or a provably tight upper bound accounting for worst-case next-fit fragmentation, e.g. `2 * ceil(alive_bytes/ideal_size)` or bucket-count derived from real per-account sizes) before deciding target-slot sufficiency. Alternatively, after `PackedAncientStorage::pack` runs, add an explicit post-check that each many-ref account's assigned target slot (from the `write_packed_storages` zip) is `>=` that account's original slot, and abort the whole packed-write if any such per-account assignment violates the invariant (mirroring the existing total-length check but at the per-account granularity).

### Proof of Concept
Rust integration test plan (extending patterns already used in `test_many_ref_accounts_can_be_moved` and `test_combine_ancient_slots_packed_internal`):

2. Call `AccountsDb::many_ref_accounts_can_be_moved(&many_refs_newest, &target_slots_sorted, &tuning)` with `target_slots_sorted.len() == k` (only just satisfying the check) and assert it returns `true`.
3. Call `PackedAncientStorage::pack(many_refs_newest.iter(), tuning.ideal_storage_size)` directly and assert `result.len() > k`, proving the packer needs more buckets than the check assumed.
4. Extend to a full `combine_ancient_slots_packed_internal` invocation with real storages/index entries (using `get_sample_storages`/`create_db_with_storages_and_index` helpers already in the test module) where one pubkey is alive in two ancient slots (`slot_low`, `slot_high`) with `slot_high` being the newest; craft sibling one-ref accounts so total `pack.len() <= target_slots_sorted.len()` passes but the many-ref bucket for this pubkey maps (via the reverse-zip in `write_packed_storages`) to a target slot `< slot_high`.
5. After running, call `db.get_unique_accounts_from_storage_for_shrink` / read via the accounts index to assert LOAD_FRESHNESS: the pubkey's newest stored slot in the index must remain `>= slot_high`; a failing assertion here demonstrates the invariant violation and a wrong-version load risk.

    fn many_ref_accounts_can_be_moved(
        many_refs_newest: &[AliveAccounts<'_>],
        target_slots_sorted: &[Slot],
        tuning: &PackedAncientStorageTuning,
    ) -> bool {
        let alive_bytes = many_refs_newest
            .iter()
            .map(|alive| alive.bytes)
            .sum::<usize>();
        let required_ideal_packed = (alive_bytes as u64 / tuning.ideal_storage_size + 1) as usize;
        if alive_bytes == 0 {
            // nothing required, so no problem moving nothing
            return true;
        }
        if target_slots_sorted.len() < required_ideal_packed {
            return false;
        }
        let i_last = target_slots_sorted
            .len()
            .saturating_sub(required_ideal_packed);

        let highest_slot = target_slots_sorted[i_last];
        many_refs_newest
            .iter()
            .all(|many| many.slot <= highest_slot)
    }
