The closest analogous contract handling BTC deposits/withdrawals is `Bridge.sol`, but its payment-handling functions enforce exact value matching rather than allowing overpayment with a refund mechanism:

- `withdraw` requires `msg.value == depositAmount` exactly, with no overpay/refund path. [1](#0-0) 
- `batchWithdraw` requires `msg.value == depositAmount * txIds.length` exactly. [2](#0-1) 
- `deposit` is triggered by the system/operator (not user-paid), transferring `depositAmount` to the recipient with a fallback to `failedDepositVault` on failure — no refund-address parameter or overpayment logic exists. [3](#0-2) 

There is no LayerZero-style `send()` call, no loop over multiple destinations with a shared refund address, and no mechanism in this codebase where excess funds could be misdirected to the contract instead of the user. Since the bug class (overpayment refunded to the wrong address) has no reachable equivalent code path here, and none of the required binding violations (custody, proof, determinism, DA-integrity, or authority) are crossed, this does not constitute a valid analog in scope.
