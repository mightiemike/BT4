## Finding

### Title
`library_call` syscall does not enforce the `block_direct_execute_call` restriction that `call_contract` and `meta_tx_v0` enforce - (File: crates/blockifier/src/execution/syscalls/hint_processor.rs, crates/blockifier/src/execution/native/syscall_handler.rs)

### Summary
The blockifier's `call_contract` syscall handler explicitly blocks a contract from invoking another contract's `__execute__` entry point when `versioned_constants.block_direct_execute_call` is enabled, via `maybe_block_direct_execute_call`. The same restriction is enforced for the `meta_tx_v0` syscall. However, the `library_call` syscall handler — which also allows an in-transaction contract to trigger arbitrary entry-point execution (including `__execute__`) on an arbitrary declared class — never calls this check.

### Finding Description
`call_contract` explicitly guards against invoking `__execute__`: [1](#0-0) 
and the deprecated (Cairo0) hint processor path does the same: [2](#0-1) 

The shared helper implementing this restriction is `maybe_block_direct_execute_call`, gated by the `block_direct_execute_call` versioned constant: [3](#0-2) 

The `meta_tx_v0` syscall likewise restricts its target selector to be exactly `EXECUTE_ENTRY_POINT_NAME` (the opposite check, but confirming `__execute__` invocation is a specially-controlled operation): [4](#0-3) 

By contrast, the `library_call` implementations in both the CASM/VM path and the native path build a `CallEntryPoint` with `entry_point_selector: request.function_selector` / `function_selector` directly, with no call to `maybe_block_direct_execute_call` and no selector restriction of any kind: [5](#0-4) [6](#0-5) 

Critically, `library_call` executes the target class's code as a delegate call, preserving `storage_address: self.base.call.storage_address` and `caller_address: self.base.call.caller_address` from the calling context — i.e., it runs the arbitrary class's `__execute__` entry point *as if it were the calling contract itself*, with the calling contract's own storage and identity. This is exactly the "direct execute call" scenario that `block_direct_execute_call` was introduced to prevent for `call_contract`, but the guard is entirely absent on this alternate call path.

This mirrors the structure of the reported DODO issue: `DODORouteProxy` explicitly disallowed one specific dangerous call target (`_DODO_APPROVE_PROXY_`) via `swapTarget.call`, but failed to block an equally dangerous target (`DODOApprove.sol`) reachable through the same generic external-call mechanism. Here, the sequencer explicitly disallows one specific dangerous invocation path (`call_contract` → `__execute__`), but fails to close the equally reachable `library_call` → `__execute__` path.

### Impact Explanation
An account contract (or any contract) whose Cairo1/Cairo0 code invokes `library_call_syscall` with a selector of `__execute__` and an attacker-controlled class hash can execute arbitrary declared class logic in the context of the calling contract's own storage/identity, bypassing the protection `block_direct_execute_call` is meant to provide. Depending on why `block_direct_execute_call` exists (preventing bypass of the top-level transaction's validate→execute lifecycle guarantees, e.g. re-entering `__execute__` semantics with attacker-chosen bytecode under a victim account's own storage/address context), this allows unauthorized account actions and can be used to manipulate a contract's own state/authorization checks in ways the protocol intended to disallow, since the callee runs as if it "is" the caller.

### Likelihood Explanation
Reachable directly from any Cairo1/Cairo0 contract code executed as part of a normal `INVOKE` transaction — the caller only needs to issue a `library_call_syscall` (or the deprecated `library_call`/`library_call_l1_handler` syscall) with `function_selector = selector("__execute__")` and any declared class hash. No special privileges or node/operator control are needed; a single unprivileged submitted transaction triggering this contract logic is sufficient.

### Recommendation
Add the same `maybe_block_direct_execute_call(selector)` check (or equivalent selector comparison against `EXECUTE_ENTRY_POINT_NAME` gated by `versioned_constants.block_direct_execute_call`) to the `library_call` implementations in `crates/blockifier/src/execution/syscalls/hint_processor.rs`, `crates/blockifier/src/execution/native/syscall_handler.rs`, `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`, and the corresponding Cairo OS implementation in `crates/apollo_starknet_os_program/.../execution/syscall_impls.cairo` / `deprecated_execute_syscalls.cairo`, so that all inner-call mechanisms consistently enforce the restriction rather than only `call_contract`.

### Proof of Concept
1. Deploy/declare a class `Malicious` implementing `__execute__` with attacker-chosen logic.
2. From any account contract `Victim` during normal transaction execution (not `__validate__`), call:
   `library_call_syscall(class_hash=Malicious, function_selector=selector!("__execute__"), calldata=[...])`.
3. Per `library_call`'s `CallType::Delegate` semantics, this executes `Malicious::__execute__` with `storage_address` and `caller_address` set to `Victim`'s own values, succeeding even though `versioned_constants.block_direct_execute_call == true` — whereas the equivalent `call_contract_syscall(Victim/other, selector!("__execute__"), ...)` would be rejected with `DirectExecuteCall`/`Invalid argument`, as demonstrated by the existing test: [7](#0-6)

    pub(crate) fn maybe_block_direct_execute_call(
        &mut self,
        selector: EntryPointSelector,
    ) -> SyscallResult<()> {
        let versioned_constants = &self.context.tx_context.block_context.versioned_constants;
        if versioned_constants.block_direct_execute_call
            && selector == selector_from_name(EXECUTE_ENTRY_POINT_NAME)
        {
            return Err(SyscallExecutionError::Revert { error_data: vec![INVALID_ARGUMENT_FELT] });
        }
        Ok(())
    }
