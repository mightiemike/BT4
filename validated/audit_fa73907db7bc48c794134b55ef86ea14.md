**Explanation:** The apparent "double round vs single round" difference between `OnChainConfig::deserialize_into_config` and the native `validator_txn_enabled_internal` is not a divergence in interpreting identical bytes — it reflects the two functions operating on different serialization layers of the *same* data by design.

- The Move resource is `struct ConsensusConfig has key { config: vector<u8> }`. Its raw on-chain state-value bytes are the BCS encoding of that struct, which for a single `vector<u8>` field is byte-identical to `bcs::to_bytes(&config)` — i.e., the length-prefixed `config` bytes themselves. [1](#0-0) 

- `OnChainConfig::deserialize_into_config` (used by config-fetch/REST paths) receives that raw resource state-value and therefore must first strip the outer `vector<u8>` wrapper (`bcs::from_bytes::<Vec<u8>>`) before decoding the inner bytes into `OnChainConsensusConfig`. This is explicitly documented in the code comment. [2](#0-1) 

- `validator_txn_enabled()` in Move reads the resource's `config` field directly (a normal Move field access, not a raw BCS decode of the whole resource), which already yields exactly the same inner bytes that `deserialize_into_config`'s first BCS round would produce. It then passes those bytes to `validator_txn_enabled_internal`, which performs the single remaining decode round into `OnChainConsensusConfig`. [3](#0-2) [4](#0-3) 

Because a single-field `vector<u8>` struct's BCS encoding is byte-identical to the field's own BCS encoding, the "field access" path and the "one extra BCS-decode-of-Vec<u8>" path are mathematically equivalent — there is no crafted byte string that makes them diverge on the same underlying `config` content. The premise that identical bytes are fed "as-is" through both a single-round native decode and a double-round `deserialize_into_config` decode does not hold: the native function's input is already the pre-stripped inner payload, not the raw resource bytes, so the two code paths are consistent by construction rather than divergent. This is an intentional design (per the explicit comment "we need two rounds of bcs deserialization to turn it back to OnChainConsensusConfig"), not a state-integrity bug, and does not allow unprivileged input to bind an authenticated response to the wrong ledger object, version, or proof context.
