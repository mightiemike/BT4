Based on my research, I found a valid, locally-provable integrity gap in the replay-verification comparator, distinct from the smart-contract slippage bug used as a seed.

### Title
Replay-verification skips state/hot-state/position checkpoint hash comparison, allowing undetected state-root corruption - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by the `replay_on_archive` db-tool (and other replay/debugger paths) to confirm that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` recorded in an archived/backup ledger. The function checks status, gas, write-set hash, and event-root hash, but explicitly and admittedly does **not** compare the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields carried in `TransactionInfo` against the checkpoint hash computed from local re-execution.

### Finding Description [1](#0-0) 

The function's own comment documents the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

`replay_on_archive::Verifier::execute_and_verify` re-executes archived transactions with `AptosVMBlockExecutor` and calls exactly this comparator against the `TransactionInfo` pulled from the backup/archive to decide pass/fail: [3](#0-2) 

Because `ensure_match_transaction_info` never re-derives or checks `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` against what local re-execution and state-tree construction would produce, an archived `TransactionInfo` whose checkpoint hash fields do not correspond to the actual state produced by the recorded write sets/transactions will still be reported as a **successful, verified replay**. The same gap is present anywhere else in the codebase that reuses this comparator to assert equivalence between an untrusted/backup-sourced `TransactionInfo` and re-executed output (e.g. `aptos-debugger` and CLI `commands.rs` call sites also invoke `ensure_match_transaction_info`).

Contrast this with the normal on-chain commit path, `DoLedgerUpdate::assemble_transaction_infos`, which does compute and bind `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` into the `TransactionInfo` that later gets hashed into the transaction accumulator: [4](#0-3) . So the checkpoint hash is a first-class, security-relevant field of `TransactionInfo` that is bound into the accumulator/ledger-info root — but the tool whose entire purpose is to validate that an archived ledger matches re-execution silently drops this field from its equivalence check.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... during replay" and "hard-fork-only divergence during commit, replay, restore" invariant classes. A backup/archive (or an adversarial/corrupted data source feeding `replay_on_archive`, `aptos-debugger`, or the CLI replay commands) could carry `TransactionInfo` records whose write set, events, gas, and status all match re-executed output, but whose `state_checkpoint_hash` (i.e., the actual Merkle root of world state after the transaction) is wrong or stale — for example due to state-sync corruption, a downgrade/hard-fork state-root divergence, or deliberate tampering of the checkpoint field in a distributed backup. Operators relying on `replay-verify` to certify the integrity of archived history (a standard practice before promoting/serving a node from backup, or to detect hard-fork-induced state divergence) would get a false "verified" result even though the actual state root is corrupted, since the state root itself is never independently recomputed and compared here.

### Likelihood Explanation
The code path is exercised by the standard `db-tool replay-on-archive` operational tool intended specifically to catch this class of divergence, so triggering the check is trivial (run replay-verify against any archive with a mismatched checkpoint hash). No privileged access is needed to produce the mismatch other than control (or corruption) of the archived data being replay-verified. The gap is also self-documented in the source as a known, currently-unaddressed omission gated behind an unreleased feature flag (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`), confirming it is not accidental but genuinely unmitigated in the current comparator.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` to independently recompute (or accept as an additional input) the expected state-checkpoint / hot-state-checkpoint / position-state-checkpoint hash from the post-execution state view and assert equality with the corresponding fields of `txn_info`, mirroring the existing checks for write-set hash and event-root hash. At minimum, `replay_on_archive` and other tools relying on this comparator should fail loudly (not silently pass) when a `TransactionInfo`'s checkpoint hash cannot be validated, rather than only performing this validation after `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Proof of Concept
1. Take any backed-up/archived range containing a transaction that is a state checkpoint (i.e., `state_checkpoint_hash` is `Some`).
2. Tamper the `TransactionInfo.state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) stored in the backup metadata to a different, arbitrary `HashValue`, leaving write set, events, gas, status, and transaction hash untouched.
3. Run `db-tool replay-on-archive` against this corrupted backup: `Verifier::execute_and_verify` re-executes the transactions and calls `ensure_match_transaction_info` [5](#0-4) , which never inspects the checkpoint hash fields [6](#0-5) .
4. Observe the tool reports success (no failed transactions), despite the archived `TransactionInfo`'s state root being wrong — confirming the proof/commitment field is not actually verified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
