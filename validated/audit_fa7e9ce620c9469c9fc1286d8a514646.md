### Title
Truncation drift between aggregate `totalNetWeight`/`totalEnergyWeight` and per-account frozen-balance weight causes resource-limit accounting divergence - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceV2Processor.java])

### Summary
`totalNetWeight` and `totalEnergyWeight` (the network-wide "supply" of staking weight used to allocate bandwidth/energy limits) are not derived by summing exact per-account frozen balances; instead they are updated incrementally with `frozenBalance / TRX_PRECISION` truncated integer division on every freeze/unfreeze, exactly mirroring the StWSX pattern where an aggregate ("total supply") diverges from the sum of individually-tracked, independently-rounded per-user balances.

### Finding Description
When freezing/unfreezing TRX for resources, each actuator/processor computes the account's weight delta by truncating dividing the account's frozen balance by `TRX_PRECISION` (1,000,000) both before and after the operation, then adds only the delta to the global `totalNetWeight`/`totalEnergyWeight`: [1](#0-0) 

The same truncate-then-diff pattern is repeated across `FreezeBalanceActuator.addTotalWeight`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator.updateTotalResourceWeight`, `CancelAllUnfreezeV2Processor`, and `UnfreezeBalanceV2Processor`: [2](#0-1) [3](#0-2) 

Separately, when computing an individual account's resource limit share, `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` re-derive the account's weight from scratch via a fresh truncation of its current total frozen balance: [4](#0-3) [5](#0-4) 

Because each account's contribution to the global weight (`totalNetWeight`/`totalEnergyWeight`) is truncated independently at freeze-time and again independently at unfreeze-time (and again independently when queried for limit calculation), the sum of all individually-truncated account weights does not equal `floor(sum of all frozen TRX) / TRX_PRECISION`. Every freeze/unfreeze cycle for amounts not evenly divisible by `TRX_PRECISION` can shift the truncation boundary, causing the "total supply" counter (`totalNetWeight`/`totalEnergyWeight`) to drift relative to the true aggregate frozen balance actually backing it — precisely the "sum of balances doesn't match total supply" pattern described in the report, where dust differences of small magnitude compound as more freeze/unfreeze operations occur across many accounts.

### Impact Explanation
`totalNetWeight`/`totalEnergyWeight` is the denominator used in `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` to proportionally allocate the network's fixed bandwidth/energy budget (`totalNetLimit`/`totalEnergyCurrentLimit`) among all frozen accounts: [6](#0-5) 
If the aggregate weight drifts low relative to the true frozen pool, every account's computed resource limit is inflated (each account effectively receives a slightly larger share of a shared, capped public resource — free bandwidth/energy — than their actual stake entitles them to), an instance of underpriced/over-allocated public resource distribution. Conversely if it drifts high, legitimate stakers are shortchanged. This is a network-wide accounting/economic divergence rather than a direct fund-theft bug, matching the Medium severity and "small but compounding" characterization in the original report.

### Likelihood Explanation
This requires no privileged access — any account calling `FreezeBalanceV2`, `UnfreezeBalanceV2`, `FreezeBalance`, or `UnfreezeBalance` with amounts not evenly divisible by `TRX_PRECISION` (1 TRX) triggers the truncation drift. Given `TRX_PRECISION` is 1,000,000 (1 TRX in sun) and frozen balances need not be exact multiples of it after multiple partial freeze/unfreeze operations (delegation, partial unfreeze, etc.), this is a naturally and continuously reachable condition on mainnet under normal usage, not a contrived edge case.

### Proof of Concept
1. Account A freezes `1,500,000` sun (1.5 TRX) for ENERGY via `FreezeBalanceV2Contract`. `oldEnergyWeight = 0/TRX_PRECISION = 0`, `newEnergyWeight = 1,500,000/TRX_PRECISION = 1`; `totalEnergyWeight += 1` (see `FreezeBalanceV2Processor.java:85-89`).
2. Account A later freezes an additional `1,500,000` sun. `oldEnergyWeight = 1,500,000/TRX_PRECISION = 1`, `newEnergyWeight = 3,000,000/TRX_PRECISION = 3`; `totalEnergyWeight += 2` (total `3`).
3. True aggregate frozen balance is `3,000,000` sun = exactly `3` TRX, and `3,000,000/TRX_PRECISION = 3` — matches here, but interleaving freezes/unfreezes across many accounts and partial unfreezes (each independently truncating at differing balance boundaries per `UnfreezeBalanceV2Processor.updateTotalResourceWeight`) causes the running sum of independently-truncated deltas to diverge from a single truncation of the true aggregate, exactly as demonstrated by the differing V1 (floor-then-scale) vs V2 (scale-then-floor) semantics documented in the codebase's own tests: [7](#0-6) 
This test explicitly shows the same nominal frozen balance (`1,500,000` sun) yields a limit of `25` under the floor-first weight model versus `37` under the fractional-weight model — a divergence of over 40% for a single account, illustrating how the choice/order of truncation directly produces measurable resource-limit drift analogous to the balance/total-supply mismatch in the referenced report.

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
