### Title
Poison-microblock reporter can be front-run by a copy-cat report using identical headers with a lower sequence-tie tx-index - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`handle_poison_microblock` accepts a poison-microblock report whenever the newly submitted `mblock_header_1.sequence` is strictly lower than whatever sequence is already stored for that block height via `get_microblock_poison_report`/`insert_microblock_poison`. Because the comparison only looks at the sequence number embedded in the (public, copyable) microblock headers and not at who first observed/broadcast the conflicting pair, any unprivileged party who sees the two conflicting microblock headers (either in the mempool or once mined) can resubmit them signed as their own report and, if their transaction lands earlier in tx-index order for the same sequence, become the recorded/paid reporter instead of the original discoverer.

### Finding Description
The claimed broken equality is: *reward paid to reporter == the party who supplied a previously-unreported double-signature evidence*. In practice the code enforces only: *reward paid to reporter == whichever valid report tx for a given sequence value is processed first in tx order*, with ties/duplicates at the same sequence resolved by ordering, not by discovery precedence. `handle_poison_microblock` fetches the previously stored `get_microblock_poison_report` sequence for the affected block height and only overwrites/pays out when the new report's sequence is strictly lower (`mblock_header_1.sequence < reported_seq`), or when no report yet exists. It does not bind the report to the identity or timing of whoever first constructed/broadcast the header pair. Since `mblock_header_1`/`mblock_header_2` are ordinary signed microblock headers that become visible to any observer once they are broadcast on the network (mempool) or included in any fork, an attacker can copy the exact byte-for-byte header pair from a legitimate reporter's pending poison-microblock transaction, wrap it in their own `TransactionPayload::PoisonMicroblock` transaction, and get it mined with a competitive fee/nonce so it lands in an earlier tx-index (or earlier block) than the original reporter's transaction. Existing guards (`check_tenure_tx`, signature verification on the microblock headers, VRF/static validation) only validate that the two headers are a genuine conflicting pair signed by the tenure's actual miner key — none of them tie the reward to the original detector's identity, so they do not prevent this front-running.

### Impact Explanation
This does not cause a chain split, an invalid block being accepted, a non-reproducible MARF/state root, or a double-payment of the block reward — every node processing the chain in the same tx order reaches the identical, self-consistent state. The only visible effect is that the poison-microblock commission (a fee-bounded reward tied to the fork's committed microblock fees, not the block subsidy) is redirected from the true discoverer to a copier. Per the audit's own severity taxonomy this falls under **High** — "a poison or reward mis-payment bounded to fees" — rather than Critical, since no reward-schedule invariant, sortition outcome, or consensus state diverges between honest nodes; the mis-payment is deterministic and identical across all nodes given the same transaction ordering.

### Likelihood Explanation
Preconditions: the attacker must simply observe a legitimate poison-microblock report (visible in the mempool before confirmation, or trivially reconstructable from any two conflicting mined microblocks on a fork) and race it with a competitive fee/nonce. No majority stake, signer key, or special privilege is required — this is achievable by any unprivileged network participant with minimal BTC/STX cost (just enough to pay a competitive tx fee), and is repeatable for every future poison-microblock report a monitor detects in the mempool before it confirms.

### Recommendation
Bind the poison-microblock reward to the earliest verifiable discovery rather than to raw tx-index ordering — e.g., record and compare a commitment/first-seen timestamp derived from mempool arrival for a given `(mblock_header_1, mblock_header_2)` pair rather than only comparing `sequence`, or require that the reporting principal match a key derivable only by the original detector (not simply "whoever resubmits the same public headers first"). At minimum, use a "first valid report per fork/sequence wins" strict tie-break so a copied header pair received later at the same sequence cannot retroactively reassign a reward already implicitly committed to in the mempool by an earlier-broadcast honest report.

### Proof of Concept
1. Set up a two-node/local chainstate harness where a leader mines a legitimate fork producing two conflicting microblocks `A` and `B` at the same `sequence`.
2. Node 1 (honest reporter) broadcasts `PoisonMicroblock(A, B)` signed with `reporter_honest`.
3. Attacker observes the mempool, copies `A`/`B` verbatim, and broadcasts `PoisonMicroblock(A, B)` signed with `reporter_attacker` using a higher fee so it is selected first in block assembly.
4. Mine the block; assert that `StacksChainState::get_microblock_poison_report` for that height returns `reporter_attacker`'s sequence/report, and that the account balance change from `poison_microblock_commission` credits `reporter_attacker`, not `reporter_honest`.
5. Assert that resubmitting the honest report afterward fails (returns the "already reported"/insufficient-sequence error) since the stored sequence is no longer strictly greater than the honest report's sequence. [1](#0-0) [2](#0-1)
