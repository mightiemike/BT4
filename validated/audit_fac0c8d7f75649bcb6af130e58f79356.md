### Title
`append_block` never re-validates tenure-sortition canonicality that `accept_block` already checked - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Finding Description
`NakamotoChainState::accept_block` calls `Self::validate_normal_nakamoto_block_burnchain` → `Self::validate_nakamoto_tenure_snapshot` [1](#0-0) , which explicitly checks that the block's tenure sortition is an ancestor of `SortitionDB::get_canonical_burn_chain_tip(db_handle)` at call time (T1): [2](#0-1) 

Later, when `NakamotoChainState::process_next_nakamoto_block` pulls the staged block out of `nakamoto_staging_blocks` and calls `append_block` (T2), the tenure snapshot is *not* re-validated against the then-current canonical burn chain tip. Instead:
- `next_ready_block_snapshot` is fetched purely by consensus hash via `SortitionDB::get_block_snapshot_consensus`, with no ancestor-of-canonical-tip check [3](#0-2) .
- `get_block_burn_view` derives the burn view consensus hash and only checks that it connects to the *parent's own recorded* burn view, again using `get_ancestor_sort_id` against `handle.context.chain_tip`, which is rooted at the block's own claimed history, not the live canonical tip [4](#0-3) .
- `append_block` is then invoked with `burn_dbconn = sort_db.index_handle(&burnchain_view_sn.sortition_id)` — a handle rooted at the tenure's *own* sortition ID [5](#0-4)  — and calls `Self::check_sortition_exists(burn_dbconn, &block.header.consensus_hash)` [6](#0-5) , which by construction can only succeed or fail relative to a fork history anchored at that very sortition, not relative to whatever the globally canonical Bitcoin/PoX fork is at T2.

The broken equality is: *tenure-validity verdict at accept-time (`validate_nakamoto_tenure_snapshot` vs. live canonical tip)* ≠ *tenure-validity verdict at append-time (`check_sortition_exists` vs. a handle rooted at the tenure's own, possibly now-orphaned, sortition)*. `validate_nakamoto_tenure_snapshot` is only invoked from `validate_normal_nakamoto_block_burnchain` and `validate_shadow_nakamoto_block_burnchain` (both staging-time paths); it is never called from `append_block`, so there is no code path that repeats the canonical-ancestor check at processing time.

### Impact Explanation
I was not able to fully confirm within the available search budget whether the ChainsCoordinator's Nakamoto-specific reorg-handling path (analogous to the epoch2 `invalidate_descendants_of`/re-accept logic shown for legacy blocks) proactively un-marks `burn_attachable` or orphans already-staged Nakamoto blocks whose tenure sortition becomes non-canonical due to a later-arriving, heavier Bitcoin fork. If no such safeguard exists for Nakamoto staging, the structural gap above means a block could be pulled from staging and processed by `append_block` on the strength of a tenure sortition that is no longer part of the canonical Bitcoin fork, since `append_block`'s only sortition check is self-referential to that same (possibly orphaned) sortition. This would match the "invalid block accepted" / minority-triggerable divergence category. If such a safeguard does exist elsewhere in the coordinator loop (i.e., burnchain reorg processing always fully precedes and invalidates/evicts affected staged Nakamoto blocks before `process_next_nakamoto_block` can run), then the divergence is not reachable and there is no vulnerability.

### Likelihood Explanation
The precondition is a real Bitcoin-level minority reorg that displaces a previously-canonical tenure sortition between the moment a node's relay thread calls `accept_block` and the moment its coordinator thread later calls `process_next_nakamoto_block`/`append_block` for the same block, which is plausible for any node given normal Bitcoin reorg depths and Stacks' asynchronous accept/process separation. This requires only an attacker capable of mining a competing minority block-commit fork (unprivileged, minority BTC hash power), consistent with the stated attacker model.

### Recommendation
Have `append_block` (or `process_next_nakamoto_block` immediately before calling it) re-run `NakamotoChainState::validate_nakamoto_tenure_snapshot`-equivalent logic against `SortitionDB::get_canonical_burn_chain_tip` at T2, rather than relying solely on a `SortitionHandleConn` rooted at the block's own claimed tenure/burn-view sortition. Additionally, confirm and, if absent, add explicit re-validation/eviction of staged Nakamoto blocks in the coordinator's burnchain-reorg handling path, mirroring the epoch2 `stacks_blocks_to_reaccept`/`unorphan_blocks`/`invalidate_descendants_of` logic.

### Proof of Concept
Rust integration test plan (two-fork harness, single node):
1. Build a `TestPeer`/`ChainsCoordinator` harness with two Bitcoin forks: fork A (canonical) containing tenure sortition `CH_A`, fork B (competing, initially shorter) that will later overtake fork A.
2. Mine a Nakamoto block `blk` whose `header.consensus_hash == CH_A`, and call `NakamotoChainState::accept_block(..., db_handle_at_fork_A_tip, ...)`. Assert `Ok(true)` (stored in staging) — establishes the T1 verdict via `validate_nakamoto_tenure_snapshot`.
3. Before calling `process_next_nakamoto_block`, extend fork B past fork A's height so fork B becomes canonical (reorging past `CH_A`'s sortition height), and drive the coordinator's burnchain-block handling (`handle_new_burnchain_block`) to process this reorg.
4. Call `SortitionDB::get_canonical_burn_chain_tip` and independently call `NakamotoChainState::validate_nakamoto_tenure_snapshot`-style ancestor check for `CH_A` against the new canonical tip; assert it now returns not-canonical (i.e., accept-time verdict would now be `Err(InvalidStacksBlock)`).
5. Call `NakamotoChainState::process_next_nakamoto_block` (which internally calls `append_block`) and assert on both sides of the equality: assert whether `append_block` returns `Err(Error::InvalidStacksBlock(..))`/`Err(Error::ExpectedTenureChange)` (equality preserved) or `Ok(..)` (equality broken, block appended despite orphaned tenure).
6. If step 5 returns `Ok(..)`, this confirms the divergence; if it returns `Err`, inspect which specific check (`check_sortition_exists`, `get_block_burn_view`, or a coordinator-level pre-eviction) caught it, and downgrade/close the finding accordingly.
