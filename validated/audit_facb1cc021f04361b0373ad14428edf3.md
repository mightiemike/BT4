### Title
Spurious overflow revert in `ExchangeInjectActuator.execute()` due to `long` multiplication where `validate()` uses `BigInteger` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the counter-token amount to inject into a TRC10 exchange pool twice: once in `doValidate()` using `BigInteger` arithmetic, and again in `execute()` using raw `long` arithmetic with `Math.multiplyExact`. The intermediate product `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`) can overflow a 64-bit `long` even when the final, division-reduced result comfortably fits in a `long`. Because `validate()` never overflows (it uses `BigInteger`) but `execute()` can, a transaction that passes validation can still fail during execution with an `ArithmeticException`, blocking legitimate liquidity injections — the same root cause as the reported analog (undersized integer type used for a multiply-before-divide operation).

### Finding Description
In `doValidate()` the counter-token quantity is computed safely: [1](#0-0) 

But in `execute()`, the same computation is redone using plain `long` multiplication guarded only by `Math.multiplyExact`, which throws instead of silently wrapping, but throws for products that are perfectly valid once divided: [2](#0-1) 

`multiplyExact(secondTokenBalance, tokenQuant)` computes the numerator *before* dividing by `firstTokenBalance`. A `long` in Java (max ≈ 9.22×10^18) can easily be exceeded by this intermediate product even though the final quotient `anotherTokenQuant` is small and within the pool's `exchangeBalanceLimit`. For example, if `secondTokenBalance ≈ 10^15` and `tokenQuant ≈ 10^15` (both allowed under `exchangeBalanceLimit`, as exercised in the project's own tests with balances in the `10^14`–`10^15` range), the product is `~10^30`, far exceeding `Long.MAX_VALUE`, while the quotient after dividing by a comparably sized `firstTokenBalance` stays well within a valid `long`. `doValidate()` uses `BigInteger.multiply().divide()` and therefore never encounters this overflow for the very same inputs, so the transaction is accepted by validation and then unconditionally fails in `execute()`.

This mirrors the reported bug class exactly: a formula requiring `a * b` before further reduction is implemented with an integer type too small to hold the intermediate product, causing legitimate operations to revert.

### Impact Explanation
Any account (the exchange's creator, the only party allowed to call `ExchangeInjectContract`) attempting to inject liquidity into a pool with balances/quantities large enough to overflow the intermediate `long` product will have their transaction accepted by `validate()` but fail at `execute()` with `ArithmeticException`, wrapped into `ContractExeException`. This is a denial-of-service on the DEX's core liquidity-management functionality — genuine liquidity injections that should succeed are unconditionally blocked, and the transaction still consumes bandwidth/energy/fee resources before failing. It also creates a divergence between the validate and execute phases of the same actuator, which is a correctness/state-machine hazard.

### Likelihood Explanation
Reaching this state requires only realistic pool balances/inject amounts (on the order of 10^15, well under existing `exchangeBalanceLimit` and already used in the repository's own test fixtures), no privileged access beyond being the pool creator, and no attacker cooperation — it is a straightforward, reachable operational bug rather than a theoretical edge case.

### Recommendation
Compute `anotherTokenQuant` in `execute()` the same way as in `doValidate()` — using `BigInteger` multiplication/division (or widen to `BigInteger`/`Math.multiplyHigh`-based 128-bit-safe arithmetic) instead of `Math.multiplyExact` on raw `long`s — so the intermediate product cannot overflow independently of whether the final result fits in a `long`. Ideally, factor the calculation into a single shared helper used by both `validate()` and `execute()` to eliminate the duplicated, inconsistent logic.

### Proof of Concept
1. Create an exchange pool via `ExchangeCreateActuator` with `firstTokenBalance` and `secondTokenBalance` on the order of `10^15` each (within `exchangeBalanceLimit`, as used in `ExchangeCreateActuatorTest`). [3](#0-2) 
2. Submit an `ExchangeInjectContract` with `tokenQuant` also on the order of `10^15` for the first token.
3. `doValidate()` succeeds because `bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` (BigInteger) never overflows and yields a small, valid quotient. [4](#0-3) 
4. `execute()` then calls `multiplyExact(secondTokenBalance, tokenQuant)` on the same ~10^15 × 10^15 values, which overflows `long` and throws `ArithmeticException`, which is caught and rethrown as `ContractExeException`, failing the transaction despite having passed validation. [5](#0-4)
