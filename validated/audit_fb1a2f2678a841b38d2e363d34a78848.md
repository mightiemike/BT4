### Title
Shadow-parent block-commit validation is skipped for out-of-order block delivery, causing honest nodes to diverge on block validity - ([File: stackslib/src/chainstate/nakamoto/shadow.rs])

### Summary
`NakamotoChainState::validate_shadow_parent_burnchain` only enforces that a child block's block-commit correctly points to its shadow-block parent's tenure sortition when the parent header is *already present* in the local staging DB at the moment the child is received. If the parent hasn't arrived yet, the function returns `Ok(())` unconditionally, and this check is never re-run later during `append_block` processing, so the skip is permanent for that node.

### Finding Description
The invariant the code intends to enforce is: for any accepted `NakamotoBlock` whose parent is a shadow block, `block_commit.parent_vtxindex == 0` and `block_commit.parent_block_ptr == parent_shadow_sortition.block_height`. The broken equality is: *verdict of `validate_shadow_parent_burnchain` at block-acceptance time == verdict at block-processing (`append_block`) time*, which the code assumes holds but does not actually enforce.

In `stackslib/src/chainstate/nakamoto/shadow.rs`: [1](#0-0) 
the function looks up the parent header via `staging_db.get_nakamoto_block_header(&block.header.parent_block_id)`. If that lookup returns `None` (i.e., the parent has not yet been received/staged by this node), the function early-returns `Ok(())`, treating the block as if its parent were not a shadow block at all — skipping the `parent_vtxindex`/`parent_block_ptr` checks entirely.

This function is invoked exactly once, from `validate_normal_nakamoto_block_burnchain`, which is explicitly documented as running "before inserting the block into the staging DB": [2](#0-1) 

Critically, this check is never re-invoked during `append_block`/processing. The related comment on `get_expected_burns` confirms that out-of-order storage (child staged before parent is processed) is an expected, supported condition: [3](#0-2) 
but the only consequence handled there is burn-total continuity, not the shadow-parent block-commit consistency check.

Meanwhile, at the burnchain-operation layer, `LeaderBlockCommitOp` validation deliberately relaxes the anchor-block-descent check whenever `parent_vtxindex == 0` and `parent_block_ptr != 0`, on the explicit assumption that "the block validation logic will check that the parent block is indeed a shadow block, and that `self.parent_block_ptr` points to the shadow block's tenure's burnchain block": [4](#0-3) 
So `validate_shadow_parent_burnchain` is the *sole* enforcement point for this invariant; if it is skipped, a block-commit that falsely claims a shadow-tenure lineage (bypassing the normal anchor-block-descent/reward-set check) is never actually verified.

Exploit flow: an attacker (a miner/leader) crafts a block-commit with `parent_vtxindex = 0` and an arbitrary `parent_block_ptr` that does not match the true sortition height of an existing shadow block, then produces a `NakamotoBlock` whose header's `parent_block_id` references that real shadow block. If this child block reaches a given node's staging DB before that node has received/staged the shadow-block header itself (a plausible race given asynchronous P2P propagation and the fact that blocks may legitimately arrive out of order), `get_nakamoto_block_header` returns `None`, the check is skipped, and the block is accepted into staging with `Ok(())`. Because the check is never re-run at `append_block` time, once the parent later arrives and is processed, the malformed child proceeds to be processed and can become part of that node's canonical chain — despite the fact that a node which happened to receive the shadow parent first would have rejected the identical child block with `InvalidStacksBlock`.

### Impact Explanation
This produces genuine divergence between honest, non-colluding, non-majority nodes based purely on network message arrival order: some nodes accept and build on the malformed child block, others reject it outright. This is a chain-split / fork condition caused by an invalid block being accepted on a subset of the network while being correctly rejected elsewhere, matching the Critical category ("an invalid block accepted or a valid block rejected network-wide").

### Likelihood Explanation
The attacker only needs to be a single miner able to submit a block-commit and a corresponding Nakamoto block referencing an already-existing shadow-block ancestor — no majority stake or signer collusion is required. The timing race (child block propagating to some nodes before the shadow-block header does) is plausible under normal P2P/gossip conditions, especially for nodes that are catching up or that receive blocks via different propagation paths, and is explicitly acknowledged as a supported scenario in the codebase's own comments about out-of-order block storage.

### Recommendation
Re-run `validate_shadow_parent_burnchain` (or an equivalent check) at `append_block`/processing time, once the parent header is guaranteed to be available (since processing requires the parent to already be processed), rather than relying solely on the best-effort check performed at initial acceptance. Alternatively, defer full acceptance/staging of a block whose parent header cannot yet be resolved for shadow-block status determination until that determination can be made, and re-validate before it is marked as ready for processing.

### Proof of Concept
Rust integration test plan (chainstate-only harness, e.g. extending `stackslib/src/chainstate/nakamoto/tests/node.rs`):
1. Set up a chain with a real shadow-block tenure `S` inserted per consensus rule (as in existing shadow-block tests).
2. Construct a valid tenure-start block `B` whose header `parent_block_id` = `S.block_id()`, but whose corresponding `LeaderBlockCommitOp` has `parent_vtxindex = 1` (or `parent_block_ptr` not equal to `S`'s sortition `block_height`) — an intentionally invalid shadow-parent commit.
3. **Path A (parent absent)**: Before inserting `S`'s header into `chainstate.nakamoto_blocks_db()`, call `NakamotoChainState::validate_shadow_parent_burnchain(staging_db, &sortdb.index_handle_at_tip(), &B, &bad_block_commit)` and assert it returns `Ok(())` (demonstrating the skip).
4. **Path B (parent present)**: Insert `S`'s header into the staging DB, then call the same validation call again with identical inputs and assert it returns `Err(ChainstateError::InvalidStacksBlock(_))`.
5. Assert these two results differ (`Ok(()) != Err(...)`) for the identical block `B` and commit, proving the accept-time verdict is order-dependent.
6. Extend to a full `append_block` call in the Path-A ordering (parent staged only after child is accepted) and confirm that no re-validation call rejects `B` during processing, i.e., `B` becomes part of the processed/canonical chain tip despite having a malformed shadow-parent commit.
