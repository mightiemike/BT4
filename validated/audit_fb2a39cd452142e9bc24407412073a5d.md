### Title
Missing caller-deposit refund on relayer-side callback failures permanently locks user's attached NEAR in the Wallet Contract - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`WalletContract::rlp_execute` accepts an attached NEAR deposit from an external, non-self predecessor and tracks it in `CallerDeposit` so it can be refunded if the emulated Ethereum action ultimately fails [1](#0-0) . The refund is only implemented in the terminal `rlp_execute_callback` on `PromiseResult::Failed` [2](#0-1) . The two intermediate multi-step callbacks, `address_check_callback` and `nep_141_storage_balance_callback`, both receive `caller_deposit` as a parameter but do not refund it on their own failure branch (`PromiseResult::Failed` from the registrar lookup / `storage_balance_of` call) — they simply return an error `ExecuteResponse` and drop the reference [3](#0-2) [4](#0-3) .

### Finding Description
This is the closest reachable analog in nearcore to the reported bug class: a contract that receives value from a caller but has an incomplete "receive/return" path for a subset of failure conditions, so the value becomes unrecoverable by the caller.

The flow:
1. An external (non-self) caller invokes the `#[payable]` `rlp_execute` entry point with an attached deposit [5](#0-4) .
2. `inner_rlp_execute` builds `ExecutionContext` and computes `CallerDeposit::new(&context)`, which is `Some` whenever `predecessor_account_id != current_account_id` and the attached deposit is non-zero [6](#0-5) [7](#0-6) . The deposit itself is simply credited to the wallet contract's own balance by the runtime (payable method), it is not forwarded anywhere at this point.
3. For an `EOABaseTokenTransfer` with `address_check`, or an `ERC20Transfer`, the code dispatches to a multi-step promise chain: `address_registrar.lookup(...).then(address_check_callback(target, action, caller_deposit))` or `storage_balance_of(...).then(nep_141_storage_balance_callback(...))` [8](#0-7) .
4. If the first promise in the chain (the registrar lookup, or the `storage_balance_of` query) fails — e.g. the registrar or token contract is down, out of gas, or the account doesn't exist — the corresponding callback hits its `PromiseResult::Failed` branch and returns an `ExecuteResponse{success:false,...}` immediately, without ever creating a refund promise back to `caller_deposit.account_id` [9](#0-8) [10](#0-9) .
5. Only the final `rlp_execute_callback`, reached when the actual action promise resolves, contains the refund logic: `if let Some(CallerDeposit{...}) = caller_deposit { promise_batch_action_transfer(...) }` [2](#0-1) .

Because the refund logic exists in exactly one of the three callback exit points, any failure that occurs in the registrar-lookup step or the NEP-141 `storage_balance_of` step leaves the user's originally-attached NEAR permanently on the wallet contract's own balance with no code path that returns it to the caller — functionally the same root cause as the reported Solidity issue: a value-receiving entry point that lacks the corresponding return/refund path on certain failure branches, permanently stranding attached funds.

### Impact Explanation
Funds attached by an external caller to `rlp_execute` for an `EOABaseTokenTransfer` (with address_check) or `ERC20Transfer` are permanently frozen inside the Wallet Contract's account balance whenever the address-registrar lookup or the token's `storage_balance_of` call fails, with no automated or user-triggered recovery path present in the callback logic. This is a direct, transaction-triggered loss of user funds (frozen, not just delayed), satisfying "permanently frozen funds."

### Likelihood Explanation
This is reachable by any unprivileged relayer/caller submitting a normal `rlp_execute` transaction with a nonzero attached deposit and a transaction kind that routes through `address_check_callback` or `nep_141_storage_balance_callback`. The failure trigger (registrar or token contract call failing, e.g. due to insufficient prepaid gas for the sub-call, the registrar/token contract being paused, or transient cross-contract failure) is plausible in normal operation and does not require any malicious validator/node/peer behavior — only a single transaction from a normal caller plus an ordinary external-call failure.

### Recommendation
Add the same deposit-refund logic present in `rlp_execute_callback` to the `PromiseResult::Failed` branches of `address_check_callback` and `nep_141_storage_balance_callback`, so that any failure prior to reaching the terminal callback still issues a `promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near`.

### Proof of Concept
1. Deploy the Wallet Contract for an eth-implicit account and enable the address registrar / NEP-141 token flows as in the test harness (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`) [11](#0-10) .
2. From an external account (not the wallet's own account), call `rlp_execute` with an attached deposit and an RLP transaction that decodes to `EthEmulationKind::EOABaseTokenTransfer{ address_check: Some(addr), .. }` targeting an unregistered/invalid address so that `address_registrar.lookup(...)` fails (e.g., point the registrar constant at a nonexistent/paused contract, or exhaust `REGISTRAR_LOOKUP_GAS`).
3. Observe: `address_check_callback` is invoked with `PromiseResult::Failed`, returns `ExecuteResponse{success:false,...}`, and the caller's attached deposit is *not* refunded — contrast with the existing `test_caller_refunds` test which only exercises the failure path through `rlp_execute_callback` (target `fake.near`) and shows the refund logic works there but not in the registrar/token failure paths [12](#0-11) .
4. Query the caller's account balance before/after: the deposit amount is deducted and never returned, remaining stuck as part of the wallet contract's account balance.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
