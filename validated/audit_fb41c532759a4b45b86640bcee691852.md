### Title
Unbounded recursion over attacker-influenced `NestedIntList` bytecode-segment structure enables stack-overflow DoS during compiled-class-hash computation and OS re-execution - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
The Poppler CVE (JLSEC-2026-82) is a crash caused by unbounded recursive descent (`OutlineItem::open`) over an attacker-crafted, deeply nested document structure. The sequencer contains an analogous unbounded-recursion pattern: `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` and its sibling `create_bytecode_segment_structure_inner` in `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs` both recurse over a `NestedIntList` (`bytecode_segment_lengths`) tree with no depth bound.

### Finding Description
`bytecode_hash_node` recurses once per nesting level of the `NestedIntList` describing how a `CasmContractClass`'s bytecode is segmented: [1](#0-0) 

This function is invoked from `hash_inner`, which is called every time a compiled class hash is computed via `HashableCompiledClass::hash`: [2](#0-1) 

The equivalent recursive builder, `create_bytecode_segment_structure_inner`, is used by the Starknet OS during block re-execution to reconstruct the bytecode-segment tree for every Cairo-1 class touched in a block, again with unbounded recursion depth over attacker-shaped `NestedIntList` data: [3](#0-2) [4](#0-3) 

The `bytecode_segment_lengths` value originates from the `CasmContractClass` produced by the Sierra-to-CASM compiler when a class is declared: [5](#0-4) 
The compiler enforces a bytecode-size cap (`max_bytecode_size`) but I found no explicit bound on the *nesting depth* of the resulting segment tree — only overall byte-length is capped: [6](#0-5) 
Whether the cairo-lang compiler's segment-generation logic itself limits nesting depth (as opposed to segment count/total length) could not be verified from this repository, since that logic lives in the external `cairo-lang-starknet-classes` crate, not in-tree. This is the main uncertainty in this analog: if the external compiler bounds nesting depth proportionally to code size (rather than allowing an attacker-controlled Sierra program to produce a segment tree whose depth scales independently of `max_bytecode_size`, e.g., via long non-terminating statement runs or many nested scopes), the practical exploitability is reduced. The sequencer-side code itself, however, performs no independent depth check before recursing.

Notably, the codebase elsewhere is very deliberate about recursion-depth risk for user-controlled data — e.g., dedicating a pre-allocated large stack specifically to guard against native Cairo execution stack overflows: [7](#0-6) 
No equivalent guard (stack pre-allocation, explicit depth counter, or iterative rewrite) exists for the `bytecode_hash_node` / `create_bytecode_segment_structure_inner` recursion paths.

### Impact Explanation
If a declared class's `bytecode_segment_lengths` tree can be made sufficiently deep, computing its compiled class hash (done on the normal execution/fee-accounting path whenever the class's `CompiledClassV1` needs its hash, and unconditionally during Starknet OS block re-execution of any block that declares/loads such a class) would overflow the thread stack and crash the process (SIGSEGV/abort), rather than return a graceful error. Because this runs inside blockifier's transaction-processing threads (and inside prover/OS re-execution), a crash here can halt block production or re-execution for that block — a sequencer availability/liveness impact (DoS), matching the reported bug class (crash via malicious/crafted nested structure in a "parsing"-style recursive walk). This does not directly cause fund loss or wrong state commitments, so it is bounded to Medium severity, consistent with the source CVE's rating (CVSS 5.5, availability-only impact).

### Likelihood Explanation
Reachability is real but conditioned on an external, unverified assumption: an attacker must be able to declare a Cairo-1 class whose Sierra compilation yields an abnormally deep `bytecode_segment_lengths` tree while staying within `max_bytecode_size`/CPU/memory compilation limits enforced by `SierraCompilationConfig`. This depends on internal compiler segment-generation heuristics external to this repository, which I could not confirm. Given the codebase's other careful stack-overflow mitigations for different recursive paths (native Cairo execution), the absence of any corresponding safeguard for this particular recursion is notable, but likelihood is Medium/uncertain pending verification of the external compiler's segment-tree depth characteristics.

### Recommendation
- Add an explicit maximum recursion/nesting-depth check (or convert to an iterative, explicit-stack-based) traversal in `bytecode_hash_node` (crates/starknet_api/src/contract_class/compiled_class_hash.rs) and `create_bytecode_segment_structure_inner` (crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs).
- Reject classes at declaration time whose `bytecode_segment_lengths` nesting depth exceeds a sane bound, independent of total bytecode-size limits.
- Verify, from the `cairo-lang-starknet-classes` crate's segment-generation logic, whether nesting depth is already implicitly bounded by `max_bytecode_size`; if not, this needs an explicit sequencer-side guard.

### Proof of Concept
Not constructible from this repository alone: reproducing the crash requires generating (or hand-crafting) a `CasmContractClass` whose `bytecode_segment_lengths` field is a deeply right-nested `NestedIntList::Node` chain (e.g., depth on the order of the platform's default thread stack size divided by the per-frame cost of `bytecode_hash_node`/`create_bytecode_segment_structure_inner`), then calling `HashableCompiledClass::hash` (crates/starknet_api/src/contract_class/compiled_class_hash.rs:144) or the OS hint `load_classes_and_create_bytecode_segment_structures` (crates/starknet_os/src/hints/hint_implementation/compiled_class/implementation.rs:169) on it and observing a stack overflow instead of a bounded error. Confirming whether the Sierra-to-CASM compiler can actually be driven to emit such a tree from a legitimately-declarable Sierra program requires access to/testing against the external `cairo-lang-starknet-classes` compiler, which is outside the scope of this repo's indexed contents.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }

#[test]
fn test_max_bytecode_size() {
    let contract_class = get_test_contract();
    let expected_casm_bytecode_length = 1965;

    // Positive flow.
    let compiler = SierraToCasmCompiler::new(SierraCompilationConfig {
        max_bytecode_size: expected_casm_bytecode_length,
        max_memory_usage: DEFAULT_MAX_MEMORY_USAGE,
        max_cpu_time: DEFAULT_MAX_CPU_TIME,
        audited_libfuncs_only: false,
    });
    let casm_contract_class = compiler
        .compile(contract_class.clone())
        .expect("Failed to compile contract class. Probably an issue with the max_bytecode_size.");
    assert_eq!(casm_contract_class.bytecode.len(), expected_casm_bytecode_length);

    // Negative flow.
    let compiler = SierraToCasmCompiler::new(SierraCompilationConfig {
        max_bytecode_size: expected_casm_bytecode_length - 1,
        max_memory_usage: DEFAULT_MAX_MEMORY_USAGE,
        max_cpu_time: DEFAULT_MAX_CPU_TIME,
        audited_libfuncs_only: false,
    });
    let result = compiler.compile(contract_class);
    assert_matches!(result, Err(CompilationUtilError::CompilationError(string))
        if string.contains("Code size limit exceeded.")
    );
}
