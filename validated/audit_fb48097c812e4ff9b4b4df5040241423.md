### Title
Unbounded memory allocation when decompressing legacy Declare-v1 Cairo0 program in the RPC write API - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The JSON-RPC write endpoint that accepts legacy (Cairo0) `DECLARE` transactions decompresses the attacker-supplied `compressed_program` field with no size limit before any validation, unlike the equivalent path in the gateway which enforces `decode_and_decompress_with_size_limit`. A single declare-v1 transaction with a small gzip payload that expands to gigabytes can exhaust node memory, analogous to ALPINE-CVE-2023-0809 (Mosquitto allocating memory from an unvalidated initial packet field before checking packet legitimacy).

### Finding Description
`decompress_program` reads the entire decompressed gzip stream into an unbounded `Vec<u8>` via `decoder.read_to_end(&mut decompressed)` with a `// TODO(dan): add time and size limits.` comment explicitly noting the missing guard: [1](#0-0) 

This function is invoked when converting a user-submitted deprecated (Cairo0) contract class into the internal `starknet_api` representation: [2](#0-1) 

This conversion is reached from the `BroadcastedDeclareV1Transaction`/`DeclareV1Transaction` path exposed by the JSON-RPC write API (`add_declare_transaction`), i.e. directly reachable by any unprivileged transaction sender submitting a `DECLARE` transaction with `version 0`/`1` and an attacker-controlled `contract_class.program` (base64+gzip encoded string), as referenced in `crates/apollo_rpc/src/v0_8/api/api_impl.rs` and `crates/apollo_rpc/src/v0_8/broadcasted_transaction.rs`.

By contrast, the equivalent decompression path used for the newer Sierra-declare flow through the deprecated HTTP gateway is explicitly size-bounded: [3](#0-2) [4](#0-3) 

The RPC-write `decompress_program` function lacks this protection entirely — it decompresses to completion regardless of output size, and only performs `base64::decode` twice (redundantly) with no bound on the resulting buffer.

### Impact Explanation
An attacker can submit a legacy declare transaction whose `compressed_program` field is a small, highly-compressible gzip blob (a "zip bomb") that decompresses to an arbitrarily large size (limited only by available memory/CPU on the node processing the RPC write request). Repeated or concurrent submissions can exhaust the memory of any sequencer/full-node process exposing this JSON-RPC write endpoint, causing process OOM/crash — a network-availability impact matching a Medium severity DoS, consistent with the original CVE's classification.

### Likelihood Explanation
The bug is trivially reachable: no signature verification, stateful validation, or fee payment is required before decompression occurs — it happens purely during request/type conversion of the submitted transaction, prior to `StatelessTransactionValidator`-style size checks that exist elsewhere in the code for the RPC-native declare flow. Any client with network access to the JSON-RPC write endpoint can trigger it with a single small HTTP request.

### Recommendation
Apply the same bounded-decompression pattern already used elsewhere in the codebase (`starknet_api::compression_utils::decompress_with_size_limit` / `decode_and_decompress_with_size_limit`) to `decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs`, capping both the base64-decoded and gzip-decompressed sizes to a configured maximum (e.g., the existing `max_contract_bytecode_size`/`max_sierra_program_size` style limits) before returning `Program`. Remove the redundant duplicate `base64::decode` call as well.

### Proof of Concept
1. Craft a `DECLARE` transaction (version 0 or 1) with `contract_class.program` set to a small base64+gzip-encoded blob (e.g., a few KB) that decompresses to several GB (a standard zip-bomb construction, e.g. repeated zero bytes compress at ~1000:1 with gzip).
2. Submit it via the JSON-RPC `starknet_addDeclareTransaction` method to a node's RPC endpoint.
3. Observe `decompress_program` calling `decoder.read_to_end(&mut decompressed)` with no size cap, driving the process's memory usage to the size of the decompressed payload before any subsequent validation or hashing occurs.

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;

}

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
