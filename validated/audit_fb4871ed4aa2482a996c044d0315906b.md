I found a validate/execute mismatch in `UnDelegateResourceActuator` that mirrors the SFPM bug class: validation sums an aggregate quantity across two separate keyed sources, but execution only mutates one of them by the requested amount — matching the "netLiquidity vs chunk liquidity" divergence pattern (aggregate check vs. per-item mutation touched multiple times).

### Title
Insufficient per-key deduction in `UnDelegateResourceActuator` allows validate/execute state divergence when combined lock+unlock delegated balances are used - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.validate()` computes `delegateBalance` as the **sum** of two distinct `DelegatedResourceCapsule` records — the "unlock" key and the "lock" key (only if the lock's expire time has passed) — and only checks that this combined sum is `>= unDelegateBalance`. However, `execute()` unconditionally deducts the full `unDelegateBalance` from the "unlock" resource capsule alone via `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)` (and the ENERGY equivalent), never touching the "lock" resource capsule's balance. [1](#0-0) [2](#0-1) 

### Finding Description
This is the same bug class as the SFPM report: a validation step checks an **aggregate** value (`unlockResourceCapsule.getFrozenBalanceForBandwidth() + lockResourceCapsule.getFrozenBalanceForBandwidth()`, i.e., two "legs"/keys combined) against a requested amount, while the state-mutating step in `execute()` treats a **single leg** (the unlock-key `DelegatedResourceCapsule`) as if it alone held the full aggregate: [3](#0-2) 

```
long delegateBalance = 0;
if (unlockResourceCapsule != null) {
  delegateBalance += unlockResourceCapsule.getFrozenBalanceForBandwidth();
}
if (lockResourceCapsule != null && lockResourceCapsule.getExpireTimeForBandwidth() < now) {
  delegateBalance += lockResourceCapsule.getFrozenBalanceForBandwidth();
}
if (delegateBalance < unDelegateBalance) { throw ... }
```

In `execute()`, only the unlock-key capsule is fetched and decremented by the full `unDelegateBalance`: [4](#0-3) 

If `unlockResourceCapsule.getFrozenBalanceForBandwidth()` alone is smaller than `unDelegateBalance` (validation only passed because the *lock*-key balance was added in), `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)` drives that capsule's stored balance negative — exactly the "netLiquidity == chunk liquidity" mismatch from the SFPM report, where an aggregated/net figure used for validation does not correspond to the single per-key figure actually mutated. The `lockResourceCapsule` (holding contributed balance from the second key) is never decremented at all, so its stale, undeducted balance remains in storage and can be independently used again (e.g., in a subsequent `UnDelegateResourceActuator` call, or once its own unlock timer passes), while the owner/receiver accounting fields (`addDelegatedFrozenV2BalanceForBandwidth`, `addFrozenBalanceForBandwidthV2`) have already been adjusted by the full amount.

### Impact Explanation
This produces an invalid/divergent state in the `DelegatedResourceStore`: a negative `FrozenBalanceForBandwidth`/`FrozenBalanceForEnergy` value on the unlock-key capsule, and an un-deducted (double-available) balance on the lock-key capsule. Since delegated resource accounting feeds bandwidth/energy grants and `TotalNetWeight`/`TotalEnergyWeight` global counters (touched elsewhere in this actuator family), this can permit resource entitlements to be double-counted or corrupted relative to the TRX actually frozen, i.e., a state-accounting divergence affecting network resource issuance — a concrete "invalid-state/accounting divergence" impact per the given criteria.

### Likelihood Explanation
Reachable by any unprivileged account holder that has both a locked and an unlocked `DelegatedResourceCapsule` toward the same receiver for the same resource type (a normal, permitted end-state of `DelegateResource`/lock functionality) and then issues a single `UnDelegateResourceContract` for an amount that exceeds the unlock-key balance alone but is covered by the combined lock+unlock total. This requires no special privileges — only the standard freeze/delegate/lock resource flow available to any account — making the precondition realistically reachable rather than purely theoretical.

### Recommendation
In `execute()`, deduct `unDelegateBalance` proportionally/sequentially from the two capsules in the same order validation summed them (first drain `unlockResourceCapsule` up to its available balance, then draw the remainder from `lockResourceCapsule`), mirroring the aggregate check performed in `validate()`, and persist both capsules' updated (non-negative) balances.

### Proof of Concept
Conceptual reproduction (would need to be exercised via a Devin session against the actual test harness to confirm runtime behavior, since I could not execute code):
1. Freeze balance for BANDWIDTH, delegate part of it to `receiver` (creates unlock-key `DelegatedResourceCapsule` with e.g. balance `X`).
2. Additionally create a "locked" delegation to the same `receiver` for BANDWIDTH (lock-key capsule with balance `Y`), and let its expire time pass so `lockResourceCapsule.getExpireTimeForBandwidth() < now`.
3. Call `UnDelegateResourceContract` with `balance = X + Y` (or any value `> X` but `<= X + Y`).
4. `validate()` passes because `delegateBalance = X + Y >= unDelegateBalance`.
5. `execute()` only calls `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)` on the unlock-key capsule (whose actual balance is only `X`), driving its stored balance negative, while the lock-key capsule's `Y` balance is never touched/deducted. [5](#0-4) [6](#0-5)
