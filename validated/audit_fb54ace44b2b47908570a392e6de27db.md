### Title
Permanent freeze of a NEAR Wallet Contract account via gas-exhaustion during ERC20 callback parsing before `has_in_flight_tx` reset is committed - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The `near-wallet-contract` (the Ethereum-transaction-emulation wallet used for eth-implicit accounts) serializes all mutating calls through a single `has_in_flight_tx` boolean guard so only one Ethereum-style transaction can be "in flight" at a time. For an emulated ERC-20 transfer, the contract calls an *arbitrary, attacker-reachable* NEP-141 token contract (`storage_balance_of`) and parses its response inside a callback that first sets `has_in_flight_tx = false` and only then deserializes the (attacker-controlled) response with `serde_json::from_slice`. If that parsing step exhausts the callback's gas budget (or otherwise panics) before the function returns, the entire receipt — including the in-memory `has_in_flight_tx = false` write — is rolled back by NEAR's standard "failed receipt discards all its state changes" semantics. This leaves `has_in_flight_tx` permanently `true`, and every subsequent `rlp_execute` call short-circuits with "transaction already in progress" forever, permanently freezing the wallet account.

### Finding Description
`WalletContract::rlp_execute` is the sole entry point that lets the account's owner (or a relayer acting on their signed payload) act through the contract, guarded by: [1](#0-0) 

For an `EthEmulationKind::ERC20Transfer`, `inner_rlp_execute` builds a promise chain that first queries the (attacker-deployable) token contract's `storage_balance_of` and schedules `nep_141_storage_balance_callback` as the `.then()` continuation: [2](#0-1) 

The callback itself resets the in-flight flag as its *first* statement, then parses the promise result (attacker-controlled bytes returned by the token contract) with `serde_json::from_slice`: [3](#0-2) 

The identical pattern (reset-then-parse-attacker-data) also exists in `address_check_callback`: [4](#0-3) 

Because the underlying `storage_balance_of` query is executed with only a small static gas allotment (`NEP_141_STORAGE_BALANCE_OF_GAS` = 5 Tgas), a malicious token contract can nonetheless emit a large response value bounded only by the protocol-wide `max_length_returned_data` limit (4 MiB in production configs): [5](#0-4) 
this cap is enforced generically in `value_return` and in `validate_data_receipt`, not by the wallet contract itself: [6](#0-5) [7](#0-6) 

The callback's own gas budget is only `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (15 Tgas static) plus the user's small `action.gas()` for the eventual `ft_transfer` call: [8](#0-7) [9](#0-8) 

An attacker-controlled token contract can therefore return a large/adversarial JSON payload (e.g. a multi-megabyte string, or deeply nested/duplicated structures crafted to maximize `serde_json` parsing cost) that consumes more gas during `serde_json::from_slice(&value)` than the ~15-20 Tgas allotted to the callback, causing the callback's WASM execution to fail with a gas-exceeded host error *after* `self.has_in_flight_tx = false;` executes in the borrowed/mutable contract state but *before* the function returns successfully. Per the runtime's documented semantics ("If any action fails, the whole receipt fails ... When a receipt fails, its state changes are rolled back using `TrieUpdate`"), a failing FunctionCall receipt never commits any of its state writes — so the flag reset is discarded and the persisted `has_in_flight_tx` remains `true` from before the callback ran.

`rlp_execute` unconditionally treats `has_in_flight_tx == true` as a signal to reject *any* further transaction without creating a new promise, and there is no other function in the contract that can clear the flag: [10](#0-9) 
Consequently, once the flag is stuck at `true`, the account becomes permanently unusable through this contract — the sole intended control surface for the eth-implicit account.

### Impact Explanation
The wallet contract is the exclusive mechanism through which an eth-implicit NEAR account executes actions (adding a full-access key is explicitly disallowed, see `Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey))` in `action_to_promise`). Getting `has_in_flight_tx` permanently stuck at `true` therefore permanently freezes the account: the owner can never submit another Ethereum-emulated transaction (transfers, ERC-20 transfers, key management) again. This is a concrete "permanently frozen funds" outcome triggered by a single external call chain initiated by an unprivileged caller (any relayer, or the account owner themselves if tricked into targeting a malicious token), directly analogous to the reported ERC-20 `transfer`-revert DoS where an adversarial token implementation permanently blocks finalization of on-chain state.

### Likelihood Explanation
- Deploying a malicious NEP-141-style contract on NEAR is unprivileged and trivial (High likelihood precondition satisfied).
- The 4 MiB return-value ceiling gives ample room to craft a `storage_balance_of` response whose JSON deserialization cost exceeds a ~15–20 Tgas callback budget; `serde_json`'s recursive-descent parsing over adversarially large/duplicated content is a well-known gas/CPU amplification vector.
- The exploit requires the ERC20-emulation code path (`EthEmulationKind::ERC20Transfer`) to be exercised against the attacker's contract, i.e. a relayer or the wallet owner must submit an `rlp_execute(target=<malicious token>, tx_bytes)` call — a single, ordinary transaction, requiring no validator or node compromise.
- I was unable to fully confirm from the indexed files whether `target` is additionally constrained to match the RLP-encoded transaction's "to" address for the `ERC20Transfer` case (the `internal.rs` validation logic that would confirm or refute this was not retrieved before the tool budget was exhausted). If `target` must strictly match a value derived from the signed transaction (which is the documented design intent), the practical trigger requires either the account owner signing a transaction against a token they (unknowingly) deployed maliciously, or a colluding/malicious relayer being able to influence which token gets used — this affects exploitability nuance but not the underlying rollback bug itself, which is a genuine defect in the contract's failure-handling design.

### Recommendation
- Do not perform state-mutating writes (like resetting `has_in_flight_tx`) before performing potentially-failable, attacker-influenced work (like deserializing untrusted callback data) within the same receipt; instead, structure callbacks so the flag is only cleared after all failure-prone parsing has completed, or clear it in a way that is robust to partial failure (e.g., using a dedicated always-succeeding final action, or wrapping the parse in a bounded/pre-sized method that cannot exceed remaining gas).
- Bound the size and structural complexity of data accepted from arbitrary NEP-141 contracts before calling `serde_json::from_slice` (e.g., reject oversized payloads outright, or use a streaming/limited parser) rather than relying on gas metering alone to bound cost.
- Add a recovery mechanism (e.g., a permissionless "unstick" method, gated on evidence that no promise is genuinely pending, or a self-callback with generous fixed gas that cannot itself be starved by the untrusted response) so a stuck `has_in_flight_tx` cannot permanently brick the account.

### Proof of Concept
1. Attacker deploys account `evil-token.near` implementing the NEP-141 `storage_balance_of` method to return a large (up to ~4 MiB, the protocol `max_length_returned_data` limit) or deeply-nested JSON payload instead of a well-formed `Option<StorageBalance>`.
2. The wallet owner (or a relayer on their behalf) signs/relays an Ethereum-emulated ERC-20 transfer transaction with `target = evil-token.near`, invoking `WalletContract::rlp_execute`.
3. `inner_rlp_execute` sets `has_in_flight_tx` conceptually pending and schedules: `storage_balance_of` (5 Tgas) → `nep_141_storage_balance_callback` (callback_gas ≈ `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` + `action.gas()`, e.g. 15–30 Tgas total). [11](#0-10) 
4. `evil-token.near::storage_balance_of` returns its oversized/adversarial payload as `PromiseResult::Successful(value)`.
5. `nep_141_storage_balance_callback` executes: line 202 sets `self.has_in_flight_tx = false;` in the in-memory contract state, then line 211 calls `serde_json::from_slice(&value)`, which exhausts the remaining prepaid gas and causes the WASM execution to abort with a gas-exceeded error. [12](#0-11) 
6. Because the FunctionCall receipt fails, all of its state changes (including the flag reset) are discarded; the persisted `WalletContract.has_in_flight_tx` remains `true` (its value from before this receipt began).
7. Every future call to `rlp_execute` immediately hits the early-return guard and returns `"transaction already in progress, please try again later"` without ever creating a new promise, forever: [13](#0-12) 
   The account is permanently frozen with respect to this contract, its sole control surface.

/// Validates given data receipt. Checks validity of the length of the returned data.
fn validate_data_receipt(
    limit_config: &LimitConfig,
    receipt: &DataReceipt,
) -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded {
            length: data_len as u64,
            limit: limit_config.max_length_returned_data,
        });
    }
    Ok(())
}
