**Analysis:**

`CrossShardStateView::set_value` at [1](#0-0)  does `self.cross_shard_data.get(state_key).unwrap().set_value(...)`. If `state_key` is not in `cross_shard_data`, this **panics** rather than silently falling through to or shadowing `base_view`. This matches exactly one of the "acceptable" outcomes named in the proof idea itself (panic/ignore/reject), so the invariant that only pre-declared keys can be cross-shard-updated is enforced — just via a hard panic instead of a graceful rejection.

Additionally, the only caller that produces `RemoteTxnWriteMsg` is `CrossShardCommitSender::send_remote_update_for_success` at [2](#0-1) , which only sends a write for a `state_key` if it is found in `edges.get(state_key)` — i.e., only for keys that were already recorded as `dependent_edges` for that shard/round. These `dependent_edges` are derived from the same `cross_shard_dependencies` structure produced by the block partitioner (`txn_with_deps.cross_shard_dependencies.dependent_edges()`), which is exactly the same source used to build the receiving shard's `cross_shard_data` key set in `CrossShardStateView::create_cross_shard_state_view` ( [3](#0-2) ). Both sides are built from the same deterministic partitioner output derived from the transaction dependency graph, not from arbitrary unprivileged network input that could target an undeclared key. There is no code path by which unprivileged transaction/API input can inject a `RemoteTxnWriteMsg` for a key outside this pre-computed dependency set without going through partitioning first.

Even in the hypothetical case of a mismatched/undeclared key reaching `set_value`, the result is a process panic (a crash/DoS), not silent state corruption or a shadowed value returned from `get_state_value`. Per the review's scope rules, generic DoS/panic conditions and any dependency on a compromised/malicious shard peer are explicitly out of scope, and no path exists where honest, unprivileged transaction input alone can cause a value for an undeclared key to be silently written into `cross_shard_data` and returned by `get_state_value` in place of `base_view`'s value.

    pub fn create_cross_shard_state_view(
        base_view: &'a S,
        transactions: &[TransactionWithDependencies<AnalyzedTransaction>],
    ) -> CrossShardStateView<'a, S> {
        let mut cross_shard_state_key = HashSet::new();
        for txn in transactions {
            for (_, storage_locations) in txn.cross_shard_dependencies.required_edges_iter() {
                for storage_location in storage_locations {
                    cross_shard_state_key.insert(storage_location.clone().into_state_key());
                }
            }
        }
        CrossShardStateView::new(cross_shard_state_key, base_view)
    }
