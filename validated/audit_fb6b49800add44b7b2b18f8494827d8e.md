### Title
Ambiguous single-byte format sniffing in `WriteSet::decode_value` can silently misdecode legacy write sets into corrupted state — (File: `storage/aptosdb/src/schema/write_set/mod.rs`)

### Summary
`WriteSetSchema`'s `ValueCodec::decode_value` distinguishes the new tagged `WriteSet` enum encoding from the pre-enum legacy `LegacyWriteSetV1Payload` encoding purely by checking whether the **first byte of the stored blob equals `1`**. That single byte is ambiguous: it is exactly the same byte that BCS emits both for the `WriteSet::V1` enum discriminant *and* for a legacy `BTreeMap` whose length happens to be 1. When the two collide, the decoder attempts to parse a legacy payload as a new-format `WriteSetV1`, and only detects failure if that mis-parse happens to run out of bytes (`bcs::Error::Eof`). If it does not run out of bytes exactly at that point, no error is raised and a corrupted `WriteSet` — with wrong keys/values/hotness/extensions — is silently returned as if it were the correct persisted write set.

The check `data.first() == Some(&1)` is used to decide whether the buffer is:
1. A new-format `WriteSet` enum (`V0` or `V1`), whose BCS variant tag `1` (for `V1`) is a leading uleb128 byte, or
2. A `LegacyWriteSetV1Payload` (no tag byte at all), whose first field is `value: WriteSetV0`, itself just a `BTreeMap<StateKey, WriteOp>` whose BCS-encoded length prefix is the very first byte of the blob. [2](#0-1) [3](#0-2) 

A legacy `WriteSetV0`'s `value_writes` map is a plain `BTreeMap<StateKey, WriteOp>`; BCS encodes its length as a uleb128 varint immediately followed by the entries — for a map with **exactly one entry**, that length byte is `0x01`, which is bit-for-bit identical to the enum discriminant that the new format uses for `WriteSet::V1`.

So, for any legacy blob whose top-level `write_set` map has length 1, `decode_value` takes the `Some(&1)` branch and tries `bcs::from_bytes::<WriteSet>(data)`. This misinterprets:
- byte 0 (the legacy map-length byte) as the `WriteSet` enum tag (selecting `V1`),
- the following legacy `StateKey`/`WriteOp` bytes as if they were the fields of `WriteSetV1 { value_writes, hotness, extensions }`.

The code only recovers via the explicit fallback for `bcs::Error::Eof` (i.e., when the misinterpretation runs out of bytes before finishing). If the byte stream instead happens to have compatible lengths at each misaligned boundary (a realistic possibility given BCS's uleb128/length-prefixed structure for nested collections), `bcs::from_bytes` returns `Ok(ws)` with a semantically wrong `WriteSet` and no error is ever surfaced — the exact same "silently returns the wrong-but-plausible value" pattern as the referenced Friday-timestamp bug, translated to a storage/decoding invariant instead of a time invariant.

### Impact Explanation
`WriteSet` decoded through this schema feeds directly into state-integrity–critical paths:
- API responses that describe committed transaction changes (`api/types/src/convert.rs::into_transaction_info` consumes `WriteSet::into_write_op_iter()`), so a corrupted decode could bind a wrong set of state changes to a real, authenticated transaction version.
- Backup/restore and replay flows (`storage/aptosdb/src/backup/restore_utils.rs`, `storage/backup/backup-cli/.../transaction/restore.rs`) read/re-persist `WriteSet`s across versions; a corrupted read can propagate wrong durable ledger data into a freshly restored DB without any hash mismatch being raised at the decode layer itself (the schema layer does not re-verify content against the `TransactionInfo::state_change_hash`).
- Any indexer, debugger, or downstream consumer trusting `WriteSetDb::get_write_set`/`get_write_sets` receives incorrect data silently.

This matches the "Committed state that differs from the correct VM result or corrupts durable ledger data" and "Authenticated API ... output bound to the wrong version/object" impact categories.

### Likelihood Explanation
This path is explicitly gated by the code's own comment as a temporary compatibility shim for "binaries that pre-date the `WriteSet` enum" and forge-compat baselines that still write the legacy, untagged format — i.e., it is a real, reachable migration-window code path, not dead code. It triggers whenever a legacy write set's outer map has exactly one entry, which is a common shape (e.g., single-resource updates), and only requires that the accidental re-parse not hit EOF at the wrong spot — plausible given nested variable-length collections. No attacker action or privilege is required; ordinary historical data plus routine node upgrade/restore/replay is sufficient to hit it.

### Recommendation
Do not sniff format by a single ambiguous byte. Instead:
- Persist an explicit, unambiguous format/version marker (e.g., a dedicated schema/column family, or a length-delimited outer envelope) when writing legacy-compat data, or
- Eagerly migrate/rewrite all legacy entries to the new tagged format during upgrade instead of doing best-effort format sniffing on every read, or
- At minimum, validate the round-trip: after a successful `bcs::from_bytes::<WriteSet>(data)`, re-serialize and compare byte-for-byte with `data`; if it doesn't match, fall back to the legacy path instead of trusting a coincidental structural match.

### Proof of Concept
1. Construct a legacy-format blob (no enum tag) whose `value_writes: BTreeMap<StateKey, WriteOp>` has exactly one entry, i.e., BCS bytes begin with `0x01` followed by one `(StateKey, WriteOp)` pair, followed by a BCS-encoded `hotness: BTreeSet<StateKey>`.
2. Feed these bytes to `WriteSet::decode_value` (`storage/aptosdb/src/schema/write_set/mod.rs`).
3. Because `data.first() == Some(&1)`, the function attempts `bcs::from_bytes::<WriteSet>(data)`, treating byte 0 as the `V1` tag and re-parsing the remaining bytes as `WriteSetV1 { value_writes, hotness, extensions }`.
4. Choose (or brute-force) a `StateKey`/`WriteOp`/hotness-set byte layout such that this misaligned re-parse completes without hitting `bcs::Error::Eof` (achievable since nested BCS length prefixes can coincidentally line up).
5. Observe that `decode_value` returns `Ok(ws)` with a `WriteSet` whose keys/values do not match the originally written legacy write set — no error, no panic, silent corruption on read.

/// `pub enum WriteSet { V0, V1 }` representation.
/// TODO(HotState): this is only needed temporarily to avoid forge-compat test failures because in
/// these tests the baseline validators would write legacy format to DB.
#[derive(Deserialize, Serialize)]
struct LegacyWriteSetV1Payload {
    value: WriteSetV0,
    hotness: BTreeSet<StateKey>,
}

impl ValueCodec<WriteSetSchema> for WriteSet {
    fn encode_value(&self) -> Result<Vec<u8>> {
        bcs::to_bytes(self).map_err(Into::into)
    }

    fn decode_value(data: &[u8]) -> Result<Self> {
        // TODO(HotState): we could simply use `bcs::from_bytes` for everything once the latest
        // release branch does not write LegacyWriteSetV1Payload and forge-compat test would not
        // fail in CI.
        match data.first() {
            Some(&1) => match bcs::from_bytes::<WriteSet>(data) {
                Ok(ws) => Ok(ws),
                // Legacy V1 payload lacks the trailing `extensions` field, so the new decoder
                // runs out of bytes while reading it. Any other error indicates real corruption
                // and should propagate.
                Err(bcs::Error::Eof) => {
                    let legacy: LegacyWriteSetV1Payload = bcs::from_bytes(&data[1..])?;
                    let mut ws = WriteSet::V0(legacy.value);
                    ws.add_hotness(legacy.hotness);
                    Ok(ws)
                },
                Err(e) => Err(e.into()),
            },
            _ => bcs::from_bytes::<WriteSet>(data).map_err(Into::into),
        }
    }
}
