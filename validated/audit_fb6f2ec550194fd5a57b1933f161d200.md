### Title
Asset issuer can unrestrictedly change TRC10 URL/description and free bandwidth limits post-issuance, harming existing token holders - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateAssetActuator.java`)

### Summary
`UpdateAssetActuator` allows the account that issued a TRC10 asset to call `UpdateAssetContract` at any time, without limit on frequency, to change the asset's `url`, `description`, `free_asset_net_limit` (`newLimit`) and `public_free_asset_net_limit` (`newPublicLimit`) [1](#0-0) . This mirrors the PhiFactory `updateArtSettings` bug class: a token creator can retroactively change settings that existing holders relied upon, with no time-lock, no cap tied to the original issuance, and no holder consent mechanism.

### Finding Description
`validate()` only bounds-checks the raw values (`url`/`description` format, `0 <= newLimit/newPublicLimit < oneDayNetLimit`), and confirms the caller is the account that issued the asset [2](#0-1) . There is no restriction on:
- How often the issuer can change these settings (can be called every block).
- Whether the new limits represent a meaningful reduction from the values holders originally transacted under.
- Whether the `url`/`description` (which downstream wallets/explorers treat as canonical asset metadata) can be swapped to arbitrary/misleading content at any time.

`execute()` unconditionally overwrites `AssetIssueCapsule` fields for both V1 and V2 asset stores with the new values [3](#0-2) . The `UpdateAssetContract` protobuf itself carries no versioning or holder-approval field [4](#0-3) , so the change is applied immediately and irreversibly overwrites prior settings that holders may have relied on.

This is directly reachable by any broadcast transaction from any account that has issued a TRC10 asset — no special/committee-only permission is required, only ownership of the previously-issued asset (analogous to the "artist" role in the original finding).

### Impact Explanation
`free_asset_net_limit`/`public_free_asset_net_limit` govern the free bandwidth budget available to transfers of the asset (an accounting/resource parameter). An issuer can reduce these to 0 at any time after holders have acquired the token, forcing every subsequent transfer to consume the sender's own bandwidth/TRX — an unexpected cost change imposed on existing holders, directly analogous to the "Modifying Royalties" impact in the source report. Likewise, arbitrary changes to `url`/`description` at any time mirror the "Updating URLs" impact — third parties (wallets, exchanges, block explorers) that surface this metadata to end users can be misled after the fact, since there is no commit-then-reveal or notice period.

### Likelihood Explanation
Any account that has issued a TRC10 asset can trigger this at will via a normal signed broadcast transaction (`/wallet/updateasset` HTTP endpoint or the equivalent gRPC contract) [5](#0-4) . No governance/timelock/committee approval is required, and it can be repeated indefinitely, making exploitation trivial and repeatable.

### Recommendation
Add restrictions analogous to what the Phi team implemented: cap how much `free_asset_net_limit`/`public_free_asset_net_limit` can be reduced relative to prior values (or disallow decreases below levels already relied upon), rate-limit or timelock metadata (`url`/`description`) changes, and/or require holder-visible versioning/events so downstream consumers can detect and react to changes rather than silently trusting the latest state.

### Proof of Concept
1. Account `A` issues a TRC10 asset with `free_asset_net_limit = 500`, `public_free_asset_net_limit = 8000`, and `url = "https://legit-project.com"`.
2. Users acquire the asset and begin transferring it relying on the advertised free bandwidth and URL.
3. Account `A` broadcasts an `UpdateAssetContract` transaction (via `UpdateAssetActuator`) setting `new_limit = 0`, `new_public_limit = 0`, and `url = "https://malicious-site.example"`.
4. `UpdateAssetActuator.validate()` passes (values are within `[0, oneDayNetLimit)` and caller matches issuer) [6](#0-5) ; `execute()` immediately overwrites the asset's stored `url`, `description`, and limits [3](#0-2) .
5. All subsequent holder transfers of this asset lose their free-bandwidth allowance, and any client trusting the on-chain `url` field is redirected to attacker-controlled content — with no way for holders to have prevented or been warned of the change.

        throw new ContractValidateException("Account has not issued any asset");

        throw new ContractValidateException("Asset is not existed in AssetIssueStore");
      }
    } else {
      if (account.getAssetIssuedID().isEmpty()) {
        throw new ContractValidateException("Account has not issued any asset");
      }

      if (assetIssueV2Store.get(account.getAssetIssuedID().toByteArray())
          == null) {
        throw new ContractValidateException("Asset is not existed in AssetIssueV2Store");
      }
    }

    if (!TransactionUtil.validUrl(newUrl.toByteArray())) {
      throw new ContractValidateException("Invalid url");
    }

    if (!TransactionUtil.validAssetDescription(newDescription.toByteArray())) {
      throw new ContractValidateException("Invalid description");

    if (newLimit < 0 || newLimit >= dynamicStore.getOneDayNetLimit()) {
      throw new ContractValidateException("Invalid FreeAssetNetLimit");
