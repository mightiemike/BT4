## Finding: `ensure_match_transaction_info` skips checkpoint-hash verification during chunk replay

### Title
Replay/restore integrity check `ensure_match_transaction_info` omits state/hot-state/position checkpoint hashes, letting a diverged state root pass verification — (File: `types/src/transaction/mod.rs`)

### Summary
This is structurally the same bug class as the ExtraordinaryFunding report: a critical field is excluded from an integrity-binding hash/comparison, so a value that should invalidate the object instead sails through unnoticed. In `ExtraordinaryFunding::proposeExtraordinary`, `endBlock_` was excluded from the proposal hash, letting an attacker substitute a corrupted `endBlock` while keeping the "same" proposal identity. In `TransactionOutput::ensure_match_transaction_info`, the `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields are explicitly excluded from the equality check between locally re-executed output and the persisted, ledger-info-authenticated `TransactionInfo`, even though the function's entire purpose is to assert that the two are identical. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` checks status, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash`, but the function's own comment admits the state/hot-state checkpoint hash and `position_state_checkpoint_hash` are intentionally left unchecked: [2](#0-1) 

This function is the sole correctness gate used when replaying/restoring transactions against previously persisted, cryptographically-authenticated `TransactionInfo` records — i.e. it is meant to prove "my local VM execution reproduces exactly the ledger-committed result." It is invoked from the chunk-replay verification path: [3](#0-2) 

and from the CLI/debugger/db-tool replay-verify entry points (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `storage/db-tool/src/replay_on_archive.rs`), all of which rely on this comparator to certify that a replayed execution matches the authenticated chain history.

Because the state-checkpoint-related hashes (which bind the Sparse-Merkle-Tree / Jellyfish-Merkle state root, and — per `COMPUTE_TRADING_NATIVE_STATE_ROOTS` — the "trading native" state root) are never compared, a transaction whose write set/events/gas/status match but whose resulting state tree root diverges from the persisted, signed ledger data will still be reported as a successful match.

### Impact Explanation
If the local state root ever diverges from the authenticated root (e.g. due to a VM/state-computation bug, a corrupted local DB during restore, or a divergent hot-state/position-checkpoint computation), this verification path — used by `replay_on_archive`, debugger commands, and CLI replay-execution — would not detect it. This defeats the primary purpose of replay verification: to catch and flag exactly this class of hard-fork-relevant, state-commitment divergence. The comment itself flags the concrete risk: "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

### Likelihood Explanation
This is a self-documented, code-confirmed gap (not speculative): the TODO explicitly states the comparator "ignores the checkpoint hashes" and instructs future authors to "Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [2](#0-1) . Note the caveat: the `position_state_checkpoint_hash`/hot-state fields are tied to `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, a feature referenced in `types/src/on_chain_config/aptos_features.rs` and `storage/aptosdb/src/db/aptosdb_writer.rs`/`aptosdb_reader.rs`; I could not confirm within the available context whether this feature is currently enabled on mainnet. If it is not yet active, the practical exposure today is limited to the plain `state_checkpoint_hash` field, which is still excluded from this same check for the base (V0) `TransactionInfo` as well — so the gap is real regardless of that feature flag's status. Actual triggering requires an independent root cause (state-root divergence) to already exist; this finding is about the missing detection mechanism, not a standalone state-corruption primitive by itself.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed output and `txn_info`, mirroring the mitigation pattern from the source report (binding the previously-excluded field into the check before it is relied upon for security-relevant verification), and do this before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any dependent restore/replay-verify tooling is treated as authoritative.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without live state-divergence tooling):
1. Persist a `TransactionInfo` (V0 or V1) with a given `state_checkpoint_hash` computed from a correct state tree.
2. Locally re-execute the same transaction against a state view whose resulting Sparse Merkle Tree root differs (e.g., due to a bug in state-checkpoint construction, or a restore process that mis-applies write sets) but which produces the same write-set hash, event root, gas used, and status.
3. Call `ensure_match_transaction_info` (as done in `execution/executor/src/chunk_executor/mod.rs::verify_execution`, or via `replay_on_archive`).
4. Observe that verification succeeds — no error is raised — despite the state checkpoint root diverging from the authenticated ledger data, matching the exact gap called out in the code's own comment at `types/src/transaction/mod.rs:2197-2202`. [1](#0-0) [4](#0-3)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
