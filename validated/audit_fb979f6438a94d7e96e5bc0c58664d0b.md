### Title
Withdraw to an unregistered destination-chain/token pair burns the PRC20 on Push Chain but permanently fails to create the matching outbound, causing unrecoverable user fund loss - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`AttachOutboundsToExistingUniversalTx` / `BuildOutboundsFromReceipt` parse `UniversalTxOutbound` events emitted by `UniversalGatewayPC` *after* the triggering EVM call (payload execution / withdraw) has already committed state (PRC20 burn). If the event's `(ChainId, Token)` pair is not registered in `x/uregistry` (or outbound is disabled for that chain), `BuildOutboundsFromReceipt` returns an error, and the caller only records a `RevertError` string on the `UniversalTx` — it never re-mints the burned PRC20 or otherwise compensates the user. This mirrors the reported ITSHub bug class: an accounting/state-tracking record (here, the `OutboundTx`) can be skipped for a chain/token combination that isn't "initialized" in the registry, while the value-moving action (the burn) has already been committed, leading to a permanent, unrecoverable loss for an ordinary unprivileged user.

### Finding Description
Withdraw flow:
1. A user's UEA payload (submitted via `MsgExecutePayload`, gasless, callable by anyone with a validly signed payload for their own UEA) calls the `UniversalGatewayPC` system contract to withdraw PRC20 funds to an arbitrary `(destination chain, token)` pair chosen by the payload itself. This call burns the PRC20 and emits a `UniversalTxOutbound` event.
2. `ExecutePayloadV2`'s EVM call is executed and, on success, committed via `writeCache()` (see `x/uexecutor/keeper/execute_inbound_gas_and_payload.go:238-256` for the analogous CEA path, and the non-CEA path calls `k.AttachOutboundsToExistingUniversalTx(sdkCtx, receipt, utx)` at `x/uexecutor/keeper/execute_inbound_gas_and_payload.go:326` after the EVM state is already committed).
3. `AttachOutboundsToExistingUniversalTx` (`x/uexecutor/keeper/create_outbound.go:144-155`) calls `BuildOutboundsFromReceipt`, which:
   - Checks `IsChainOutboundEnabled` for the destination chain — fails if the chain is unknown/disabled [1](#0-0) 
   - Looks up the destination token via `GetTokenConfigByPRC20(ctx, event.ChainId, event.Token)` — fails with `collections.ErrNotFound` if that PRC20 isn't registered for that specific destination chain [2](#0-1) 
4. On either failure, `BuildOutboundsFromReceipt` returns an error and no `OutboundTx` is created. The caller in the payload-execution path (`execute_inbound_gas_and_payload.go:326-333`) only does:
```go
if attachErr := k.AttachOutboundsToExistingUniversalTx(sdkCtx, receipt, utx); attachErr != nil {
    ... u.RevertError = attachErr.Error() ...
}
``` [3](#0-2) 
There is no re-mint of the burned PRC20 and no `INBOUND_REVERT`/refund outbound created for this case — the `RevertError` field is purely informational text, not a fund-recovery mechanism.

Because `event.ChainId` and `event.Token` come from the `UniversalGatewayPC` call arguments — which are ultimately driven by the user's own `UniversalPayload` data — an ordinary user (not a validator, admin, or relayer) can trigger a withdraw to any `(chainId, prc20Address)` combination, including ones that are not registered as a `TokenConfig` for that chain (e.g. a valid PRC20 but registered only under a different destination chain, or a chain that exists but never had this specific token mapped, per the `PRC20Index` chain-scoped lookup in `GetTokenConfigByPRC20`) [4](#0-3) .

### Impact Explanation
The PRC20 burn inside `UniversalGatewayPC`'s withdraw call is part of the already-committed EVM state (the payload-execution cache is written via `writeCache()` on success before outbound attachment runs). If outbound attachment subsequently fails due to an unregistered `(chain, token)` pair, the burned value has no corresponding `OutboundTx`, so:
- TSS never signs/broadcasts anything for this "withdrawal" (no `PendingOutbounds` entry is created since `attachOutboundsToUtx` is never reached).
- The `UniversalTx` only carries an opaque `RevertError` string with no automated remediation.
- The user's PRC20 balance is permanently destroyed with no path to recovery besides manual, out-of-band (admin/governance) intervention.

This satisfies "permanent loss of user funds" from an unprivileged, ordinary user action — no malicious validator, relayer, or admin is required to trigger it.

### Likelihood Explanation
Medium-to-High. The trigger requires only a normal user constructing a `UniversalPayload` that calls `UniversalGatewayPC`'s withdraw function with a destination chain/token pair that isn't registered (e.g., typo'd PRC20 address, a token registered on a different chain, or a chain whose outbound was never enabled/registered for that token). This can happen accidentally (user or dApp error) or be deliberately triggered by an attacker targeting their own funds or, more importantly, exploited to test/repeatedly burn funds that a griefer tricks another dApp/contract into withdrawing incorrectly. No special privileges, front-running of admin actions, or validator collusion is needed — only a correctly signed payload for the caller's own UEA.

### Recommendation
Ensure the token/chain registration check happens *before* the PRC20 burn is committed, or make outbound attachment failure trigger an automatic re-mint/refund path on Push Chain (symmetric to `handleFailedOutbound`'s re-mint logic at `x/uexecutor/keeper/outbound.go:99-147`) instead of merely recording a `RevertError` string. Concretely:
- Validate `IsChainOutboundEnabled` and `GetTokenConfigByPRC20` for the requested destination/token *inside* the `UniversalGatewayPC` withdraw path (or via a pre-check before the EVM call executes), so the burn itself reverts atomically when the destination is unregistered, rather than allowing the burn to commit and the tracking record to fail afterward.
- Alternatively, when `BuildOutboundsFromReceipt` fails after the burn has committed, automatically re-mint the burned PRC20 back to the sender/`RevertInstructions.FundRecipient` and record this as a proper `PCTx`, mirroring the existing `handleFailedOutbound` re-mint mechanism.

### Proof of Concept
1. Register `ChainConfig` for `eip155:11155111` (outbound enabled) but only register `TokenConfig` for USDC's PRC20 mapped to `eip155:11155111`; do not register that PRC20 for `eip155:1` (or omit registering `eip155:1` entirely, or register a different PRC20 for it).
2. Deploy a UEA and fund it with PRC20 via a normal inbound FUNDS deposit (standard flow).
3. Submit a `MsgExecutePayload` whose `UniversalPayload.Data` calls `UniversalGatewayPC`'s withdraw method targeting `destinationChain = eip155:1` with `token = <the PRC20 address>` (a chain/token pair never registered together in `uregistry`).
4. Observe: the payload executes successfully (burns the PRC20, `writeCache()` commits), `ExecuteInboundGasAndPayload`/`ExecuteInboundFundsAndPayload` then calls `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt`, which returns `collections.ErrNotFound` from `GetTokenConfigByPRC20`.
5. Verify the `UniversalTx.RevertError` field is set to the error string, `UniversalTx.OutboundTx` remains empty, `PendingOutbounds` has no entry, and the user's PRC20 balance was already decremented by the burn with no compensating mint — funds are permanently lost.

```go
func (k Keeper) GetTokenConfigByPRC20(
	ctx context.Context,
	chain string,
	prc20Addr string,
) (types.TokenConfig, error) {

	if strings.TrimSpace(prc20Addr) == "" {
		return types.TokenConfig{}, fmt.Errorf("prc20 address is empty")
	}
	// Same canonical form as the index function, so any case variant hits the row.
	prc20Addr = canonicalPRC20(prc20Addr)

	// PRC20 addresses are globally unique by construction; MatchExact returns at most one.
	iter, err := k.TokenConfigs.Indexes.PRC20Index.MatchExact(ctx, prc20Addr)
	if err != nil {
		return types.TokenConfig{}, err
	}
	defer iter.Close()

	for ; iter.Valid(); iter.Next() {
		pk, err := iter.PrimaryKey()
		if err != nil {
			return types.TokenConfig{}, err
		}
		cfg, err := k.TokenConfigs.Get(ctx, pk)
		if err != nil {
			return types.TokenConfig{}, err
		}
		if cfg.Chain == chain {
			return cfg, nil
		}
	}

	return types.TokenConfig{}, collections.ErrNotFound
}
