### Title
Uncontrolled recursion in compiled-class-hash bytecode-segment hashing enables sequencer stack-overflow DoS on declare - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
The `SierraCompiler::compile` path isolates the actual Sierra→CASM compilation in a resource-limited subprocess, but the subsequent compiled-class-hash computation runs unprotected, in-process. That hash computation recurses over the CASM `bytecode_segment_lengths` tree (`NestedIntList`) with a depth proportional to the segment nesting produced by the untrusted, attacker-declared Sierra program, with no depth limit — the same bug class as CVE-2026-0990 (uncontrolled recursion driven by attacker-supplied nested structure, leading to stack exhaustion / crash).

### Finding Description
`SierraCompiler::compile` first compiles the declared Sierra program to CASM inside a resource-limited external process (CPU time/memory bounded), but then immediately computes the compiled class hash **in the parent process**, with no resource isolation: [1](#0-0) 

That hash routine is `HashableCompiledClass::hash`, which calls `bytecode_hash`, which recurses over the `bytecode_segment_lengths` (`NestedIntList`) tree via `bytecode_hash_node`: [2](#0-1) 

This is a genuine native-stack recursive function (`.map(...).collect_vec()` recursing into `bytecode_hash_node` per child, with no depth check or iterative rewrite). The recursion depth equals the depth of the `NestedIntList` tree, which is derived by the Sierra→CASM compiler from the structure of the user-submitted Sierra program (segments per function/branch). Nothing in this repository enforces a bound on the *nesting depth* of that segment tree — only the overall CASM bytecode size is bounded (`max_bytecode_size`, default 80*1024 felts): [3](#0-2) 

A bytecode-size bound does not bound tree *depth*: a pathological but valid Sierra program (e.g. one built from many deeply nested match/branch/function-call chains, each contributing a single-element segment) can make the compiler emit a `NestedIntList` that is a long, mostly-linear chain up to on the order of tens of thousands of levels deep, while still respecting the felt-count limit. Because `bytecode_hash_node` is not tail-recursive (it collects children into a `Vec` and does post-processing/hash mixing after the recursive calls return), this cannot be optimized into a loop by the compiler, and each level consumes a normal stack frame with no artificial depth checks.

This differs qualitatively from the general-purpose recursion protections that the blockifier explicitly builds for VM/Sierra execution — e.g., `RecursionDepthGuard`/`max_recursion_depth` for nested contract calls, and the pre-allocated Native stack sized to `MAX_POSSIBLE_SIERRA_GAS` so out-of-gas triggers before stack overflow: [4](#0-3) [5](#0-4) 
Those protections all guard *contract call* recursion during execution/validation. They do not cover the compiled-class-hash computation performed by the `SierraCompiler` component when a class is declared, and that computation is not run inside the sandboxed/resource-limited subprocess used for the actual compilation: [6](#0-5) 

### Impact Explanation
The `SierraCompiler`/class-manager `add_class` path is reached by any unprivileged account submitting a `DECLARE` transaction (subject only to the gateway's stateless size/version checks, which bound sierra program size/bytecode size but not segment-tree nesting depth): [7](#0-6) [8](#0-7) 
If the compiled `NestedIntList` structure is deep enough, `bytecode_hash_node`'s native-stack recursion overflows the thread's stack and crashes the process running the `SierraCompiler`/class-manager component. Since all honest sequencer nodes process the same declared class identically (deterministic compilation and hashing), a single malicious declare transaction can crash every node that attempts to compile/hash that class — a network-wide, reproducible denial of service (loss of liveness / inability to confirm new transactions), not merely a resource-cost or single-node issue.

### Likelihood Explanation
Reachable from a single, otherwise well-formed `DECLARE` transaction, with no special privileges, keys, or operator/proposer misbehavior required. The gateway's stateless checks bound Sierra program length/bytecode size but never inspect or bound the depth of the compiler-derived bytecode segmentation tree, so an attacker can iterate/tune a Sierra program (nested function calls/branches within the size cap) to try to maximize the resulting `NestedIntList` depth. Whether current compiler versions in practice generate segmentation trees deep enough to overflow a default thread stack is not verified here (the segmentation logic itself lives in the external `cairo-lang-starknet-classes` compiler crate, outside this repository, so its exact segment-depth-vs-program-structure relationship could not be fully confirmed from the indexed code).

### Recommendation
- Convert `bytecode_hash_node` (and the analogous Cairo OS hint-side traversal in `starknet_os`) to an explicit iterative/worklist algorithm instead of native recursion, removing the dependency on call-stack depth entirely.
- Alternatively/additionally, enforce an explicit maximum nesting depth on `bytecode_segment_lengths` as part of class validation before hashing, and reject classes that exceed it.
- Move the compiled-class-hash computation into the same resource/stack-isolated execution context as the Sierra→CASM compilation step (or pre-allocate a bounded worker stack for it, as already done for Cairo Native contract execution), so a stack overflow there cannot crash the parent service.

### Proof of Concept
Not independently reproduced here — full verification would require running the actual `cairo-lang-starknet-classes` Sierra→CASM compiler (an external dependency not present in this repository's index) against a crafted Sierra program with maximal branch/function nesting within the `max_bytecode_size` cap, then invoking `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:60-74`) to observe whether the resulting `bytecode_segment_lengths` tree is deep enough to overflow the default thread stack during `executable_class.hash(&HashVersion::V2)`.

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}

    #[instrument(skip(self, class), ret, err)]
    pub async fn add_class(&mut self, class: RawClass) -> ClassManagerResult<ClassHashes> {
        let sierra_class = SierraContractClass::try_from(&class)?;
        let class_hash = sierra_class.calculate_class_hash();
        if let Ok(Some(executable_class_hash_v2)) =
            self.classes.get_executable_class_hash_v2(class_hash)
        {
            // Class already exists.
            return Ok(ClassHashes { class_hash, executable_class_hash_v2 });
        }

        let compilation_start_time = Instant::now();
        let (raw_executable_class, executable_class_hash_v2) =
            self.compiler.compile(class.clone()).await.map_err(|err| match err {
                SierraCompilerClientError::SierraCompilerError(error) => {
                    ClassManagerError::SierraCompiler { class_hash, error }
                }
                SierraCompilerClientError::ClientError(error) => {
                    ClassManagerError::Client(error.to_string())
                }
            })?;
        debug!(
            %class_hash,
            compiled_class_hash = %executable_class_hash_v2,
            compilation_elapsed_ms = compilation_start_time.elapsed().as_millis(),
            class_size_bytes =
                class.size().map_or("Failed to get class size".to_owned(), |size| size.to_string()),
            casm_size_bytes =
                raw_executable_class.size().map_or("Failed to get casm size".to_owned(), |size| size.to_string()),
            "Finished compiling class."
        );

        self.validate_class_length(&raw_executable_class)?;
        Self::validate_class_version(&sierra_class)?;
        self.classes.set_class(
            class_hash,
            class,
            executable_class_hash_v2,
            raw_executable_class,
        )?;

        let class_hashes = ClassHashes { class_hash, executable_class_hash_v2 };
        Ok(class_hashes)
    }
