### Title
`inner_insert_matured_miner_reward` panics via `assert_eq!` when two forks sharing a common matured ancestor block compute different `MinerReward`s due to fork-divergent poison-microblock report state - ([File: stackslib/src/chainstate/stacks/db/accounts.rs])

### Summary
`inner_insert_matured_miner_reward` treats a second insert for the same `(parent_block_id, child_block_id)` pair as a no-op only if the newly computed `MinerReward` is byte-for-byte equal (`assert_eq!`) to the one already stored, otherwise it panics [1](#0-0) . The reward is computed from `find_mature_miner_rewards`, which looks up any poison-microblock report at `reward_height` from the *current* fork's Clarity/MARF state [2](#0-1) , and that report is written by `handle_poison_microblock` only when a reporting transaction is actually included in a block on that specific fork [3](#0-2) . Because the `(parent_block_id, child_block_id)` pair is fixed by the identity of the common-ancestor block being matured (not by the current tip), but the poison-report visibility is fork-dependent, two forks that share that ancestor can legitimately compute two different `MinerReward`s for the identical pair, and a node that reprocesses both (e.g. during a reorg-and-reconverge) will panic.

### Finding Description
The broken equality is: `reward_computed_on_fork_A(parent_block_id, child_block_id) == reward_computed_on_fork_B(parent_block_id, child_block_id)` for a shared ancestor block. The code's own comment concedes this equality is assumed, not enforced: "the only time it's okay to re-insert the same reward is if there are two Stacks forks trying to store the same matured rewards for a common ancestor block" [4](#0-3) .

`find_mature_miner_rewards` derives `poison_recipient_opt` by calling `get_poison_microblock_report(clarity_tx, reward_height)` against the *currently processing* fork's Clarity DB [5](#0-4) , and that value is fed into `calculate_miner_reward`, directly changing which address receives the coinbase and how much is destroyed (poison punishment) [6](#0-5) . `get_poison_microblock_report` is a plain read against `clarity_tx`'s readonly DB view [7](#0-6) , i.e. it is scoped to whatever fork's MARF state is currently open, not to the historical ancestor block alone. The actual report is only written into that state when a `PoisonMicroblock` transaction reporting the equivocation is *processed inside a block on that fork* via `handle_poison_microblock`, which records the reporter/sequence via `insert_microblock_poison` [8](#0-7) .

Exploit flow (attacker needs only a single miner slot / minority stake, consistent with the allowed threat model):
1. A miner (possibly the attacker or any miner) equivocates a microblock stream in tenure at height `C` (the "common ancestor"). This equivocation is fixed, shared history for any fork extending block `C`.
2. The attacker (or anyone) submits a `PoisonMicroblock`-reporting transaction to the mempool.
3. Two competing forks extend from `C` (fork A and fork B, e.g. via ordinary burnchain block-commit races that any minority miner can create). Fork A's miner includes the poison-report tx within the 100-block maturity window; fork B's miner does not (differing mempool timing/miner choice — normal, non-privileged behavior).
4. An honest full node initially follows fork A to height `C+100`. `find_mature_miner_rewards` computes `reward_A` with `poison_recipient_opt = Some(reporter)`, and `insert_matured_child_miner_reward` stores it keyed by `(parent_block_id, child_block_id)` for block `C` (a persistent, non-fork-scoped SQLite table) [9](#0-8) .
5. The node reorgs to fork B (heavier burnchain weight). Reprocessing fork B's chain to height `C+100` recomputes the reward for the *same* `(parent_block_id, child_block_id)` pair, this time with `poison_recipient_opt = None`, producing `reward_B != reward_A` (different recipient address and coinbase split).
6. `inner_insert_matured_miner_reward` finds the pre-existing `reward_A` row, compares it to `reward_B`, and hits `assert_eq!(rw, reward, "FATAL: tried to insert multiple distinct matured parent block reward records")`, panicking and crashing the node's block-processing thread.

Existing guards do not prevent this: no code in `check_tenure_tx`, `validate_vrf_seed`, or `common_validate_against_burnchain` constrains which fork includes a poison-report transaction, and the maturity window computation (`reward_height = tip_stacks_height - MINER_REWARD_MATURITY`) is agnostic to which fork is being replayed. The stored `matured_rewards` table is keyed purely by block IDs, with no fork discriminator, so the same key can legitimately receive two different computed values across a reorg.

### Impact Explanation
The node that experiences the reorg-and-reconverge sequence crashes deterministically and will crash again identically on restart (since reprocessing to reach fork B still recomputes `reward_B` against the already-stored `reward_A`), effectively freezing that node's ability to follow the canonical chain until manual DB intervention. Peers that never processed fork A (e.g., they only ever observed fork B, or processed forks in a different order due to network timing) never panic and continue normally. This produces divergent liveness across honest nodes for the identical reorg event — a subset of nodes is permanently taken offline while others proceed — which is the "chain split via crash-induced desync of a subset of nodes" failure mode. No funds are misallocated on the surviving fork (the surviving fork's own reward computation is self-consistent), but the crashing nodes suffer irreversible desynchronization from the network without operator intervention.

### Likelihood Explanation
The preconditions are: (1) a microblock-equivocation event by some miner at a given tenure height (a `PoisonMicroblock`-eligible fork), which is not attacker-privileged to create — any miner's own tenure can produce this incidentally or an attacker miner can deliberately equivocate their own microblocks; (2) a subsequent burnchain-level fork/reorg spanning that tenure, which any minority miner can attempt by submitting competing block-commits; (3) asymmetric inclusion of a poison-report transaction between the two forks, achievable by simply submitting the report transaction to only one of the two mining efforts or relying on ordinary mempool/timing divergence. None of these require majority stake, majority signers, or privileged roles — they rely solely on capabilities explicitly granted to the attacker (broadcasting block-commits, extending forks, filing poison reports). The attack is repeatable by any party willing to mine a minority fork and file a poison report.

### Recommendation
Do not `assert_eq!`/panic on a mismatch. Either (a) key `matured_rewards` rows by the enclosing fork's tenure/tip context rather than solely by `(parent_block_id, child_block_id)`, so that per-fork reward variants can coexist, or (b) make `poison_recipient_opt` lookup depend only on state guaranteed to be common to all forks sharing the ancestor (e.g., freeze the poison-report determination at the ancestor block's own maturity boundary rather than re-derived per current tip), or (c) on mismatch, replace the panic with a recoverable error that keeps the first-seen (or canonical-fork) reward and logs/reports the anomaly instead of crashing the process.

### Proof of Concept
Rust integration test plan (two-fork harness, e.g. extending existing tests in `stackslib/src/chainstate/nakamoto/coordinator/tests.rs` or `stackslib/src/chainstate/stacks/tests/block_construction.rs`):
1. Build a chain to tenure height `C` where a miner produces two conflicting microblocks (equivocation), matching the pattern in `process_poison_microblock_multiple_same_block` test setup [10](#0-9) .
2. Fork the chain into fork A and fork B both extending from block `C`.
3. In fork A, include a `PoisonMicroblock` report transaction within the 100-block maturity window; in fork B, omit it.
4. Advance fork A to height `C + MINER_REWARD_MATURITY`, assert `find_mature_miner_rewards` returns `reward_A` with `poison_recipient_opt.is_some()`, and that it is stored via `insert_matured_child_miner_reward`.
5. Force the node/test harness to reorg onto fork B and advance it to height `C + MINER_REWARD_MATURITY`.
6. Assert on both sides of the equality: `reward_A == reward_B` (this is the invariant the code assumes) — the PoC should show this assertion is **false** (different `address`/`coinbase` fields), and that calling `insert_matured_child_miner_reward` for fork B's block triggers the `assert_eq!` panic in `inner_insert_matured_miner_reward`, aborting the test process instead of returning a recoverable `Error`.
