### Title
Unbounded linear scan over `PendingInbounds` on every inbound-ballot terminal transition, attacker-inflatable via ordinary crosschain traffic - ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
`x/uexecutor`'s `BallotHooks.afterInboundBallotTerminal` performs a full `Walk` over the entire `PendingInbounds` collection every time *any* inbound ballot reaches a terminal state (PASSED/REJECTED/EXPIRED), in order to find the one entry containing the matching `BallotId`. The size of `PendingInbounds` scales with the number of distinct, concurrently-unresolved crosschain inbound events, which an unprivileged external attacker can inflate simply by submitting many source-chain transactions — no privileged access to Push Chain is required, and honest Universal Validators (UVs) processing them behave exactly per protocol. This mirrors the Skale Network Manager pattern: an action that logically concerns a single item (`transfer`/one vote) is forced to iterate over a global, externally-growable set of items.

### Finding Description
`RecordInboundVote` (`x/uexecutor/keeper/inbound.go:27-88`) creates one `PendingInboundEntry` per distinct logical inbound event, keyed by `utxKey = sha256(source_chain:tx_hash:log_index)`, the first time a UV votes on it. Each entry stays in `PendingInbounds` until **all** its ballot variants (one per distinct byte-encoding UVs may observe) reach a terminal ballot status [1](#0-0) .

The cleanup path, `afterInboundBallotTerminal`, is wired as `x/uvalidator`'s generic `BallotHooks` callback and fires on **every** terminal transition of **every** INBOUND_TX ballot in the system. Because ballot IDs are one-way hashes and not equal to the `PendingInbounds` map key, the hook cannot do a direct lookup — it instead scans the entire collection linearly:

```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [2](#0-1) 

The code comment explicitly (and incorrectly, from a security standpoint) assumes the data set is bounded: *"the pending set is small and transient"* [3](#0-2) . Nothing enforces that assumption. `VoteInbound` (`x/uexecutor/keeper/msg_vote_inbound.go`) is a gasless-whitelisted message type [4](#0-3) , and its only gating condition on new entries is that the source chain has inbound enabled — an attacker fully controls the volume of distinct source-chain transactions/logs that generate new `utxKey`s (cheap, external-chain-only cost). Honest UVs are obligated to observe and vote on all of them per protocol, growing `PendingInbounds` without any cap tied to Push Chain resources. Each such entry remains pending for up to `DefaultExpiryAfterBlocks` blocks before its ballot(s) auto-expire, giving the attacker a window to accumulate a large backlog.

Once accumulated, every one of those N entries eventually reaches a terminal ballot state (pass, reject, or expire), and each transition individually triggers an O(N) walk of the whole map. In the worst case (many entries created in the same window, sharing similar expiry heights), this produces O(N²) aggregate work concentrated near expiry, executed synchronously inside message/ballot-finalization processing paths (`VoteOnBallot` → `CheckIfFinalizingVote` → `MarkBallotFinalized` → `fireBallotTerminalHook`) [5](#0-4) [6](#0-5) .

I was not able to fully confirm from the index whether ballot-expiry finalization in `x/uvalidator/abci.go` is batched per block (which would concentrate this O(N²) cost into a single block and directly threaten block-processing time/gas), so that amplification detail should be verified directly in `x/uvalidator/abci.go` before treating it as certain; however, the core per-transition O(N) walk over an attacker-inflatable, unbounded collection is directly confirmed in the code shown above and is sufficient on its own to reproduce the reported bug class.

### Impact Explanation
This is a state-safety / non-network-level DoS reachable by an ordinary unprivileged external actor: an attacker who floods a supported source chain with cheap, distinct transactions can grow `PendingInbounds` arbitrarily large. As the set grows, the fixed per-terminal-ballot cost of maintaining the audit trail grows linearly with total system-wide backlog rather than with the attacker's own transaction count, degrading throughput for all inbound processing and, in the worst case (large backlogs expiring in bursts), risking materially slowed or halted block processing — the same "block gas limit" concern flagged in the original Skale report. It does not, by itself, allow theft or unauthorized minting, but it is a legitimate liveness/availability risk within the "denial of service, not network-level, reachable without privileged control" allowed-impact category.

### Likelihood Explanation
Medium. Exploitation only requires submitting distinct, real transactions on any Push Chain-supported external chain (no Push Chain gas or privilege needed) to force honest, protocol-compliant UVs to create many `PendingInboundEntry` records. No malicious validator, relayer, or governance action is required. The severity depends on how large `PendingInbounds` can realistically grow before entries clear (bounded by `DefaultExpiryAfterBlocks` and UV vote throughput), which was not independently verified from the index.

### Recommendation
Avoid the unbounded reverse-lookup by indexing `PendingInbounds` (or a secondary map) by `ballotID → utxKey` directly, so `afterInboundBallotTerminal` can do an O(1) lookup instead of scanning the whole collection. If a secondary index is undesirable, embed the `utxKey` in the ballot itself (or in the ballot ID's associated metadata already tracked by `x/uvalidator`) so the hook receives it directly instead of having to search for it. Separately, consider bounding the number of concurrently pending inbound entries per source chain, or rate-limiting new distinct `utxKey` creation, to remove the attacker's ability to unboundedly inflate the backlog.

### Proof of Concept
1. Attacker submits `N` distinct low-value transactions on a supported source chain (e.g., `eip155:11155111`), each producing a unique `(source_chain, tx_hash, log_index)` triple and thus a unique `utxKey`.
2. Honest UVs observe and vote on each with `MsgVoteInbound`, each creating a new `PendingInboundEntry` via `RecordInboundVote` (`x/uexecutor/keeper/inbound.go:37-46`).
3. As ballots for these `N` inbounds reach terminal status (pass/reject, or expire after `DefaultExpiryAfterBlocks`), each terminal transition invokes `afterInboundBallotTerminal`, which performs a full `Walk` over all `N` (or however many remain) entries in `PendingInbounds` (`x/uexecutor/keeper/ballot_hooks.go:86-94`).
4. As `N` grows, the aggregate work done across all these terminal transitions grows superlinearly, imposing growing per-vote/per-block processing cost that the attacker triggered but does not bear directly.

// CheckIfFinalizingVote inspects whether the just-cast vote pushes the ballot
// over its threshold and, if so, drives the finalization through
// MarkBallotFinalized — the single canonical write path for terminal status
// transitions, which applies CEI-style ordering on the secondary indexes.
func (k Keeper) CheckIfFinalizingVote(ctx context.Context, b types.Ballot) (types.Ballot, bool, error) {
	ballot, isFinalizing := b.IsFinalizingVote()
	if !isFinalizing {
		return b, false, nil
	}

	k.Logger().Debug("ballot reached finalization threshold",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)

	if err := k.MarkBallotFinalized(ctx, ballot.Id, ballot.Status); err != nil {
		return ballot, false, errors.Wrap(err, "failed updating finalized ballot")
	}

	k.Logger().Debug("ballot finalized",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)
	return ballot, true, nil
```

func (k Keeper) MarkBallotFinalized(ctx context.Context, id string, status types.BallotStatus) error {
	if status != types.BallotStatus_BALLOT_STATUS_PASSED && status != types.BallotStatus_BALLOT_STATUS_REJECTED {
		return fmt.Errorf("invalid finalization status: %v", status)
	}

	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as finalized",
		"ballot_id", id,
		"final_status", status.String(),
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.FinalizedBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = status
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, status)
	return nil
```
