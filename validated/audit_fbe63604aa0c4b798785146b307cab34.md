Based on the investigation, I found a concrete analog of the CVE-2026-14739 bug class (declared count used to allocate memory before validating it against the actual amount of data present) inside the Starknet OS output parsing code, which is on the OS re-execution path.

### Title
Unbounded `Vec::with_capacity` from unvalidated declared length in OS output parsing enables node OOM/DoS - (File: crates/starknet_os/src/io/os_output_types.rs)

### Summary
`TryFromOutputIter for Vec<T>` reads a declared item count `n_items` directly from the Felt stream and immediately calls `Vec::with_capacity(n_items)` without checking that the underlying iterator actually contains that many remaining elements, mirroring the DBI placeholder-count heap-overflow class (a declared count is trusted for allocation before the corresponding data is verified to exist).

### Finding Description
`Vec<T>::try_from_output_iter` reads `n_items` from the felt stream and allocates `Vec::with_capacity(n_items)` before any items are actually parsed or validated against the remaining iterator length: [1](#0-0) 

The same unguarded pattern (`wrap_missing_as` producing a `usize` from a single Felt, then `Vec::with_capacity(n)` with no bound check) recurs in several other OS-output/message parsers reached from the same code path: message payload sizes, KZG blob counts (which does have an explicit cap), aggregator output counts, and the virtual OS output message-hash array: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Notably, this codebase has already recognized and patched exactly this bug class elsewhere: `CairoArray::try_from` explicitly validates that a contract-controlled declared array length cannot exceed the number of remaining Felts *before* calling `Vec::with_capacity`, with a comment stating the purpose is "to prevent a contract-controlled length felt from triggering an unbounded `Vec::with_capacity`": [6](#0-5) 

The `os_output_types.rs`/`os_output.rs`/`virtual_os_output.rs` parsers were not given the equivalent guard, so a declared count field that is inconsistent with the actual remaining felts (e.g. an oversized `usize` value) triggers an attempted allocation of an arbitrary size purely based on the untrusted felt value, exactly analogous to DBI trusting an untrusted placeholder count before checking it against the actual statement content.

### Impact Explanation
If this parsing path is fed felts whose declared count field does not match the real amount of remaining data — as can occur when validating/re-executing Starknet OS program output (Cairo VM output segment) that is not itself independently length-checked before this decode step — the parser will attempt to reserve a very large `Vec` allocation, causing an out-of-memory abort/crash of the process performing OS re-execution or output decoding. This can halt or crash a node that is verifying/re-executing blocks, i.e. a denial-of-service on block verification/re-execution — a network unable to confirm new transactions if it happens broadly.

### Likelihood Explanation
I was not able to fully confirm, within the available tool budget, the exact call path establishing that the felt stream consumed by `Vec<T>::try_from_output_iter` / `VirtualOsOutput::from_raw_output` can contain a declared-length felt that is not already length-validated by an earlier, independent check (e.g. some callers read from a program-output segment whose overall length is already known and bounded by the caller). The `runner.rs` caller and the exact provenance of the felt slice at the point these functions are invoked could not be verified fully due to running out of iterations. This uncertainty is significant: if an upstream caller already bounds/validates the felt buffer length against `n_items` before invoking these parsers, the practical exploitability is much lower.

### Recommendation
Add the same defensive check used in `apollo_cairo_utils::CairoArray::try_from` to every place in `crates/starknet_os/src/io/os_output_types.rs`, `os_output.rs`, and `virtual_os_output.rs` that reads a declared count/length felt and then calls `Vec::with_capacity`: validate the declared count against the number of remaining elements in the iterator (or against an explicit sane upper bound) before allocating, returning an `OsOutputError` instead of allocating on an unvalidated value.

### Proof of Concept
Not independently reproducible without confirming the exact call site that supplies the untrusted felt buffer to these parsers (see Likelihood Explanation) — a Devin session with full repository/test access would be needed to trace `runner.rs`/`aggregator/implementation.rs` callers and construct a concrete felt sequence with a mismatched declared item count to confirm the OOM trigger.         let n_outputs = wrap_missing(iter.next(), "n_output")?;
        let n_outputs_usize = felt_to_usize(&n_outputs)?;
        assert!(n_outputs_usize > 0, "No tasks found in the bootloader output.");

        let mut program_hash: Option<Felt> = None;
        let mut outputs = FullOsOutputs(Vec::<FullOsOutput>::with_capacity(n_outputs_usize));
        for _ in 0..n_outputs_usize {
            wrap_missing(iter.next(), "output_size")?;
            let current_output_program_hash = wrap_missing(iter.next(), "program_hash")?;
            assert_eq!(
                program_hash.get_or_insert(current_output_program_hash),
                &current_output_program_hash
            );
            outputs.0.push(OsOutput::try_from_output_iter(iter, private_keys)?.try_into()?);
        }
        Ok(Self {
            outputs,
            n_outputs: n_outputs_usize,
            program_hash: program_hash.expect("n_outputs > 0 but program hash wasn't initialized."),
        })
    }
