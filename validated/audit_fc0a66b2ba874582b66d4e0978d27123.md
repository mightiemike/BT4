Based on my investigation, I found a documented, acknowledged bug that matches the CVE-2018-1301 bug class (a size limit checked at one point, but the checked object grows afterward, past the point where the check occurred, without a follow-up re-check — analogous to Apache's header-size check happening before further data was appended).

### Title
Receipt size validated before `output_data_receivers`/return-value expansion, allowing a receipt to exceed `max_receipt_size` after the check - ([File: test-loop-tests/src/tests/max_receipt_size.rs])

### Summary
`max_receipt_size` is meant to be a hard limit enforced on every newly created receipt, keeping `ChunkStateWitness` size bounded [1](#0-0) . However, the codebase has an explicitly acknowledged bug (tracked as near/nearcore#12606) where a receipt is validated against `max_receipt_size` while it is still at (or under) the limit, but is subsequently mutated — either by attaching `output_data_receivers` after a `promise_return`, or by attaching a large returned value converted into a data receipt — growing it past `max_receipt_size` without the size being re-checked.

### Finding Description
The test file `test-loop-tests/src/tests/max_receipt_size.rs` documents two reproduction scenarios for this exact class of bug:

1. `test_max_receipt_size_promise_return`: a function call generates a promise DAG `[A -then-> B]`; when promise `A` executes it creates receipt `C` and calls `promise_return`. The comment states explicitly: "Size of this receipt will be equal to `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and the receipt's size will go above `max_receipt_size`. The receipt should be rejected, but currently isn't because of a bug" [2](#0-1) .

2. `test_max_receipt_size_value_return`: "Return a value that is as large as max_receipt_size. The value will be wrapped in a data receipt and the data receipt will be bigger than max_receipt_size. The receipt should be rejected, but currently isn't because of a bug" [3](#0-2) .

The runtime's `ReceiptManager` (`runtime/runtime/src/receipt_manager.rs`) mutates `output_data_receivers` on an already-created `ActionReceiptMetadata` via `create_action_receipt`, which pushes a `DataReceiver` into a receipt that may already be at the exact size boundary [4](#0-3) . This mirrors the CVE-2018-1301 pattern: a bound is checked against a buffer/structure, then more content is appended to that same structure without re-validating the bound, producing a result that violates the invariant the check was meant to guarantee.

### Impact Explanation
An oversized receipt breaks the core invariant that `max_receipt_size` bounds `ChunkStateWitness` size, and by extension `main_storage_proof_size_soft_limit`/witness accounting used by chunk validators (`docs/misc/state_witness_size_limits.md`). If a chunk producer can, via a single ordinary user transaction (deploying a contract that calls `promise_return` or returns a large value), cause a receipt to be created that exceeds `max_receipt_size`, it risks:
- Chunk-witness size blowup beyond the ~21 MiB design budget, potentially straining Reed-Solomon-encoded witness distribution to validators.
- A possible state-transition divergence between honest nodes if different nodes handle the "too-large" receipt inconsistently (the test explicitly calls out "Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`", implying the runtime path for handling this is fragile) [5](#0-4) .

This is reachable purely from an unprivileged transaction signer/contract deployer submitting ordinary `FunctionCall` transactions to a deployed contract — no validator or network-layer privilege is required.

### Likelihood Explanation
High likelihood of triggerability: the bug is not speculative — it is explicitly documented in-repo with working reproduction test scaffolding (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) referencing a real tracked issue (near/nearcore#12606). The trigger only requires deploying the standard `near_test_contracts::rs_contract()` test contract and calling documented methods (`max_receipt_size_promise_return_method1`, `max_receipt_size_value_return_method`) with attacker-chosen size parameters, i.e., fully reachable by an unprivileged RPC caller/contract deployer.

### Recommendation
Re-validate a receipt's serialized size against `max_receipt_size` at every point where its structure can grow after initial construction — specifically after `output_data_receivers` are appended in `ReceiptManager::create_action_receipt` (`runtime/runtime/src/receipt_manager.rs:112-138`) and after a returned value is converted into a data receipt for `promise_return`. The check should occur at receipt finalization (when it is converted from `ActionReceiptMetadata` to the final `Receipt`/`ReceiptEnum::Action`), not only at an earlier point when the receipt happened to still be under the limit, and the runtime must handle the oversized case gracefully (reject/fail the causing action) rather than allow it to propagate, consistent with the intent already partially implemented for `ReceiptValidationError::ReceiptSizeExceeded` in `runtime/runtime/src/verifier.rs`.

### Proof of Concept
Using the already-checked-in reproduction harness in the repo:
1. Deploy `near_test_contracts::rs_contract()` as in `test_max_receipt_size_promise_return` / `test_max_receipt_size_value_return` [6](#0-5) .
2. Call `max_receipt_size_promise_return_method1` with `args_size` computed so the base receipt (`base_receipt_size`) plus `args_size` equals exactly `max_receipt_size` (4,194,304 bytes) [7](#0-6) , or call `max_receipt_size_value_return_method` with `value_size` equal to `max_receipt_size` [8](#0-7) .
3. Observe that the resulting receipt C, after `output_data_receivers`/data-receipt wrapping is added post-validation, exceeds `max_receipt_size` but is not rejected, per the documented behavior tied to near/nearcore#12606.

```rust
    pub(super) fn create_action_receipt(
        &mut self,
        input_data_ids: Vec<CryptoHash>,
        receipt_indices: Vec<ReceiptIndex>,
        receiver_id: AccountId,
    ) -> Result<ReceiptIndex, VMLogicError> {
        assert_eq!(input_data_ids.len(), receipt_indices.len());
        for (data_id, receipt_index) in input_data_ids.iter().zip(receipt_indices.into_iter()) {
            self.action_receipts
                .get_mut(receipt_index as usize)
                .ok_or(HostError::InvalidReceiptIndex { receipt_index })?
                .output_data_receivers
                .push(DataReceiver { data_id: *data_id, receiver_id: receiver_id.clone() });
        }

        let new_receipt = ActionReceiptMetadata {
            receiver_id,
            refund_to: None,
            output_data_receivers: vec![],
            input_data_ids,
            actions: vec![],
            is_promise_yield: false,
        };
        let new_receipt_index = self.action_receipts.len() as ReceiptIndex;
        self.action_receipts.push(new_receipt);
        Ok(new_receipt_index)
    }
```
