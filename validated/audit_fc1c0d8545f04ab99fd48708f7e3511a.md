### Title
Super Representatives can set `brokerage` to 100%, letting them steal all voter staking rewards - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
`UpdateBrokerageActuator` allows any witness (Super Representative, SR) to set its own reward-sharing "brokerage" ratio up to 100%, with no cap below that. This mirrors the reported bug class: an unbounded/100%-capable commission parameter that is later used to split rewards between the party who set it and the party who actually staked/voted, allowing the setter to take everything and leave the other side with zero.

### Finding Description
`UpdateBrokerageActuator.validate()` only enforces: [1](#0-0) 
i.e. `brokerage < 0 || brokerage > ActuatorConstant.ONE_HUNDRED` throws — so any value from 0 to 100 (inclusive) is accepted, with no cap below the maximum. `execute()` stores this directly via `delegationStore.setBrokerage(ownerAddress, brokerage)`: [2](#0-1) 

This value is later used in `MortgageService.payReward` to split block/standby/transaction-fee rewards between the witness and the voters who delegated votes to it: [3](#0-2) 
When `brokerage == 100`, `brokerageAmount == value`, so `value` (the amount credited to `delegationStore.addReward(cycle, witnessAddress, value)`, i.e. the pool voters draw rewards from) becomes `0`, while the entire reward is credited to the witness's own allowance via `adjustAllowance`.

Voter rewards are computed strictly proportional to this per-cycle reward pool: [4](#0-3) 
so if the pool is `0`, every voter who voted for that SR receives `0` reward for that cycle, regardless of how much TRX they staked/voted.

The new brokerage value is stored under a "pending" key (`cycle = -1`) and only becomes effective for reward accounting starting at the **next** maintenance cycle, when `MaintenanceManager.doMaintenance()` copies it into that cycle's slot: [5](#0-4) 
This is functionally identical in root cause to the reported `_updateDAORevenueCommission()` bug: the only bound on the commission/brokerage parameter is the maximum percentage itself (100% / `MODULO`), with no intermediate cap, so the party who controls the setter role can unilaterally zero out the counterparty's rewards.

### Impact Explanation
Any witness (SR) can call `UpdateBrokerageContract` to set `brokerage = 100`. Once it takes effect at the next maintenance cycle, all TRX holders who voted for that witness receive zero staking rewards for every subsequent cycle the setting remains at 100%, while the witness captures the entire reward via `adjustAllowance`. This is a direct loss-of-funds/loss-of-rewards impact for unprivileged voters who have no on-chain mechanism to prevent the SR from doing this beyond eventually un-voting (which itself only takes effect at cycle boundaries, during which time rewards are already lost).

### Likelihood Explanation
Becoming a witness/SR requires only receiving enough votes (a permissionless, decentralized process, not an admin-only role), so this is reachable by any sufficiently-voted network participant, not merely a "trusted" system-level actor. Setting `brokerage=100` is a single, cheap, always-available transaction (`UpdateBrokerageContract`, fee = 0 per `calcFee()`), and the delay is only one maintenance cycle, so the attack is straightforward and low-cost to execute; the main mitigating factor is that voters could eventually unvote, matching exactly the "node runners can see it coming, but not necessarily in time" argument raised (and still accepted as a valid finding) in the original report.

### Recommendation
Introduce a maximum cap on `brokerage` below 100% (e.g., configurable via `DynamicPropertiesStore`, or a hard-coded reasonable ceiling such as 50%) enforced in `UpdateBrokerageActuator.validate()`, and/or add a minimum notice/delay period longer than a single maintenance cycle before a brokerage increase takes effect, giving voters time to react before losing rewards.

### Proof of Concept
1. Attacker becomes/operates an SR (witness) with active voters.
2. Attacker submits `UpdateBrokerageContract{owner_address: SR, brokerage: 100}` via `/wallet/updateBrokerage` (`UpdateBrokerageServlet` → `UpdateBrokerageActuator`), which passes validation since 100 ≤ `ActuatorConstant.ONE_HUNDRED`. [6](#0-5) 
3. At the next maintenance cycle, `MaintenanceManager.doMaintenance()` copies `brokerage=100` into that cycle's slot for the witness.
4. For every subsequent block reward paid to this witness, `MortgageService.payReward` computes `brokerageAmount = value` (100%), credits it entirely to the witness's `allowance`, and adds `0` to `delegationStore`'s cycle reward for voters.
5. Voters who call `withdrawReward`/`getReward` for that cycle receive `0`, as `computeReward` multiplies their vote share by a `totalReward` of `0`.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
```

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
