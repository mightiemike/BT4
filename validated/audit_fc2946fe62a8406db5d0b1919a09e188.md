### Title
Stale market-level index cache after `socialize-debt` writes down vault `lindex` mid-transaction, allowing understated debt / overstated ztoken collateral in same-block liquidation flows - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches each vault's `{index, lindex}` in `index-cache` keyed only by `{timestamp: stacks-block-time, aid}` [1](#0-0) . The cache is populated once per block via `accrue-and-cache`, which returns the cached value on any subsequent call for the same `aid` within that same timestamp without re-querying the vault [2](#0-1) . However, `socialize-debt` on the vault side directly overwrites `lindex` (and `principal-scaled`/`assets`) outside of the normal `accrue` path [3](#0-2) , and nothing in the market invalidates or refreshes `index-cache` when this happens. Any later read of that asset's index/lindex within the same block will silently reuse the pre-socialization value.

### Finding Description
1. Value bound: `index-cache { timestamp: stacks-block-time, aid }` → `{ index, lindex }`, populated by `accrue-and-cache` the first time a given asset is accrued in a block [2](#0-1) .
2. Event that invalidates the source: `liquidate()` on the market, when a position has no remaining collateral, calls `socialize-debt-asset` in a fold over the position's debt list, which in turn calls the vault's public `socialize-debt` [4](#0-3) . `socialize-debt` mutates the vault's `lindex` directly (`(var-set lindex new-lindex)`), writing down the liquidity index to reflect the bad-debt loss [5](#0-4) . This bypasses `accrue()` entirely, so the market's `index-cache` entry for that `aid`/timestamp is never touched or removed.
3. Later use: in the same block (any subsequent transaction with the same `stacks-block-time`), any operation that needs that asset's index — e.g. `borrow`, `repay`, `collateral-remove`, or `resolve-ztoken` pricing a zToken collateral asset via `get-cached-indexes` [6](#0-5)  — hits the cache and gets the stale pre-socialization `lindex`/`index` instead of the vault's true post-write-down value.

Concretely: since `socialize-debt` writes `lindex` *down* to absorb a loss, code that priced a zToken using the stale (higher) cached `lindex` via `resolve-ztoken` would compute an inflated collateral value for zSTX/zsBTC/etc. collateral in the same block [7](#0-6) . This overstated collateral value directly feeds `is-healthy`/`is-healthy-with-mask` health checks used to gate `borrow`, `collateral-remove`, and liquidation eligibility, causing positions that should be marked unhealthy (undercollateralized after the loss write-down) to appear healthy.

### Impact Explanation
This is a single-block interleaving where a stale cached liquidity index causes health checks to pass when they should fail, letting a user borrow against, or withdraw, collateral that is actually worth less than the market believes — i.e., protocol insolvency risk / theft of funds at rest via an unhealthy borrow that should have been rejected. This satisfies the Critical impact bucket (protocol insolvency / theft of funds beyond unclaimed yield).

### Likelihood Explanation
Requires (a) a liquidation that triggers bad-debt socialization for a vault whose zToken is also used elsewhere as collateral, and (b) a second transaction in the same block that reads the market's cached index for that same `aid` before the block ends. Both are achievable by the same actor: submit the triggering liquidation and the exploiting borrow/withdraw in the same block (e.g., via a single multi-call bundle or two back-to-back transactions), since Clarity's block-time-keyed cache has no other invalidation mechanism.

### Recommendation
Invalidate (or refresh) the market's `index-cache` entry for the affected `aid` whenever `socialize-debt` is invoked, or have the market re-query the vault's index/lindex immediately after calling `socialize-debt` and overwrite the cache entry (`map-set index-cache`) with the fresh values before continuing, rather than relying solely on the per-block cache.

### Proof of Concept
1. Attacker (or two colluding accounts) sets up Position A with debt in vault V and collateral fully consumable, and Position B holding zV (the ztoken of vault V) as collateral.
2. Within block T, liquidate Position A fully such that `no-collateral-left` is true, triggering `socialize-debt-asset` → vault V's `socialize-debt`, which writes `lindex` down [8](#0-7) [9](#0-8) .
3. In the same block T, call `borrow`/`collateral-remove` for Position B; since `stacks-block-time` is unchanged, `accrue-and-cache` for vault V returns the stale cached `{index, lindex}` from before the socialization [10](#0-9) , so `resolve-ztoken` overprices zV collateral [11](#0-10) .
4. Position B's health check passes using the inflated collateral value, allowing a borrow/withdrawal that would fail against the true, post-write-down value.

Note: I was unable to fully trace every call path that could read the stale index (e.g., interactions across `v0-market-vault.clar`) within the indexed portion of the repo; a Devin session with full file access is recommended to confirm every downstream consumer of `index-cache` and validate exploitability end-to-end.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
