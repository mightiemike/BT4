### Title
Contract owner can front-run `consume_user_resource_percent` to shift 100% of energy cost onto callers - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java`)

### Summary
`UpdateSettingContract` lets a smart contract's origin/owner address instantly change `consume_user_resource_percent`, the ratio that determines how much of an incoming call's energy fee is charged to the caller versus to the contract's own frozen/staked energy. There is no timelock, cooldown, or advance-notice mechanism, so the owner can broadcast an update transaction that takes effect immediately for the very next call, letting them front-run a pending user transaction and shift the maximum possible cost onto that user — the same "adjustable fee parameter with no timelock, controlled by an untrusted pool/contract creator" pattern flagged in the referenced NFTX report.

### Finding Description
`UpdateSettingContractActuator.execute()` directly overwrites the `consume_user_resource_percent` field on the deployed `ContractCapsule` as soon as the transaction is processed, with no delay: [1](#0-0) 

`validate()` only checks that the caller is the contract's origin address and that the new percent is in `[0,100]` — there is no cooldown, no minimum notice period, and no restriction preventing the value from being changed in the same block right before a victim's call executes: [2](#0-1) 

The stored value is read back via `ContractCapsule.getConsumeUserResourcePercent()`, clamped to `[0,100]`, and used by the VM execution logic (`VMActuator`) to split the energy fee between the caller and the contract owner's frozen resources: [3](#0-2) 

This is directly analogous to the NFTX report: any user can deploy a contract (the "pool"), the deployer/owner ("manager") is not a trusted actor from the caller's perspective, and a fee-like parameter that determines how much value is extracted from other participants has a maximum bound (100%) that can be set instantaneously and unilaterally, with no timelock to let users react.

### Impact Explanation
A malicious or opportunistic contract owner can observe a pending, energy-intensive call to their contract in the mempool (e.g., a large token transfer or DeFi interaction where the caller expects the contract owner to subsidize most of the energy cost via a low `consume_user_resource_percent`), then submit an `UpdateSettingContract` transaction to raise the percent to 100 before the victim's transaction is packed/executed. The victim ends up paying the full energy fee out of their own bandwidth/energy or TRX balance instead of the discounted rate they relied on, resulting in unexpected value extraction (excess TRX burned for energy) with no recourse, since the change is irreversible once the block is produced.

### Likelihood Explanation
Likelihood is comparable to the original finding's "medium" rating: it requires the contract owner to actively monitor incoming transactions and race an update into an earlier position in the same or an adjacent block, but Super Representatives/packers or MEV-aware owners can reliably achieve this since block producers control transaction ordering. Unlike the DPoS witness "brokerage" fee (`UpdateBrokerageActuator`/`DelegationStore`), which is intentionally deferred to the next voting cycle before taking effect (see `MaintenanceManager.doMaintenance()`), no equivalent timelock protects `consume_user_resource_percent`, making it comparatively easier to exploit for ordinary user-facing contracts.

### Recommendation
Introduce a timelock/delay for `UpdateSettingContract` (and the related `UpdateEnergyLimitContract`) similar to the brokerage-rate deferral pattern already used for witnesses: stage the new `consume_user_resource_percent` value and only activate it after a fixed number of blocks or at the start of the next maintenance cycle, so users interacting with a contract can observe and react to fee changes before they take effect.

### Proof of Concept
1. Deploy a contract with `consume_user_resource_percent = 0` (owner subsidizes all energy).
2. Wait for a victim to broadcast a high-energy-cost call to the contract expecting to pay little to no TRX for energy.
3. As contract owner, broadcast `UpdateSettingContract{contract_address, consume_user_resource_percent=100}` with a higher fee/priority so it lands in an earlier position in the same block (or the immediately preceding block).
4. Because `UpdateSettingContractActuator.execute()` applies the change immediately and unconditionally, the victim's subsequent call is charged using the new 100% value via `ContractCapsule.getConsumeUserResourcePercent()`, causing the victim to pay full energy fees they did not agree to.
