## Title
TRC10 asset can be issued with name "trx" when AllowSameTokenName==0, causing `TransactionLogTriggerCapsule` to mislabel `TransferAssetContract` events identically to native TRX transfers - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`, `framework/src/main/java/org/tron/common/logsfilter/capsule/TransactionLogTriggerCapsule.java`)

## Summary
The "trx" name-collision guard in `AssetIssueActuator.validate()` is only enforced when `getAllowSameTokenName() != 0` [1](#0-0) , so on a chain where `AllowSameTokenName==0` an unprivileged account can create a TRC10 token literally named `trx`. A subsequent `TransferAssetContract` of that token causes `TransactionLogTriggerCapsule` to set `assetName` to the literal string `"trx"` [2](#0-1) , identical to the constant used for native TRX transfers and resource operations elsewhere in the same switch statement [3](#0-2) .

## Finding Description
`AssetIssueActuator.validate()` checks for a name collision with `"trx"` only inside the `if (dynamicStore.getAllowSameTokenName() != 0)` block [1](#0-0) . When `AllowSameTokenName == 0`, that block is skipped entirely, and the only other name-related check is a pre-existing-token-name uniqueness check against `assetIssueStore` (v1 store), which does not reserve or forbid the literal string `"trx"` [4](#0-3) . Thus an unprivileged, funded account can broadcast an `AssetIssueContract` with `name = "trx"` and have it accepted and executed by `AssetIssueActuator.execute()` [5](#0-4) .

Later, when the attacker (or any holder) sends this TRC10 token via `TransferAssetContract`, `TransactionLogTriggerCapsule`'s constructor unpacks the contract and sets `transactionLogTrigger.setAssetName(transferAssetContract.getAssetName().toStringUtf8())` [6](#0-5) . Because the asset's stored name is the raw bytes for `"trx"`, this event field becomes indistinguishable from the literal `"trx"` string hardcoded for native `TransferContract`, `UnfreezeBalanceContract`, `FreezeBalanceV2Contract`, `UnfreezeBalanceV2Contract`, `WithdrawExpireUnfreezeContract`, `DelegateResourceContract`, `UnDelegateResourceContract`, and `CancelAllUnfreezeV2Contract` events [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) [11](#0-10) [12](#0-11) [13](#0-12) [14](#0-13) . A downstream consumer (exchange/bridge) that subscribes to this event stream and dispatches purely on `assetName == "trx"` without also checking `contractType` would misclassify a TRC10 transfer as a native TRX deposit.

No fork gate, permission check, or the `TransactionCapsule.validateSignature` / `DecodeUtil.addressValid` mechanisms address this — they validate signatures/address format, not the semantic collision between an asset name and the reserved "trx" ticker. The only defense (the trx-name check) is conditioned on the wrong parameter path.

## Impact Explanation
This is real but the impact is **entirely a client-side/off-chain event-consumer confusion issue**, not an on-chain accounting corruption. The on-chain ledger correctly tracks the TRC10 asset separately from native TRX balances — `AssetIssueActuator.execute()` and `TransferAssetActuator` operate on separate asset-balance maps (`addAsset`/`addAssetV2`), not on the native TRX balance field. The vulnerability's real-world exploitability depends entirely on whether a downstream consumer negligently dispatches solely on the string `assetName=='trx'` without also checking `contractType` (which is also populated in the same trigger object, e.g. `TransferAssetContract` vs `TransferContract`) [15](#0-14) . Any reasonably-implemented consumer differentiates on `contractType`, which correctly reflects `TransferAssetContract` vs `TransferContract`, making the practical impact conditional on a downstream implementation flaw outside this repo's control.

Additionally, per the rules, `AllowSameTokenName == 0` reflects a legacy/pre-proposal-15 state; on live TRON mainnet this proposal was activated years ago, making `AllowSameTokenName != 0` the current default, under which the guard at lines 169-174 is active and blocks "trx"-named token creation. Exploitability requires a network still running with `AllowSameTokenName==0`, which is a non-default/legacy configuration.

## Likelihood Explanation
- Preconditions: network with `AllowSameTokenName==0` (non-default on mainnet today), attacker only needs enough TRX to pay the `AssetIssueContract` fee (`calcFee()`) — no privileged role required. [16](#0-15) 
- Cost: standard asset-issuance fee, ordinary transaction bandwidth/fee.
- Repeatable: yes, any account can attempt this once per issuance fee, though note the uniqueness check at line 210-214 means only the first creator of "trx" would succeed (once taken, no one else can reissue "trx").
- Real-world impact depends on an external/off-chain consumer's dispatch logic being naive (asset-name-only matching), which is outside the scope of the on-chain repo and cannot be confirmed from this codebase alone.

## Recommendation
Move the "trx" reserved-name check out of the `AllowSameTokenName != 0` conditional block so it always applies regardless of the `AllowSameTokenName` proposal state, e.g.:
```java
String name = assetIssueContract.getName().toStringUtf8().toLowerCase(Locale.ROOT);
if ("trx".equals(name)) {
  throw new ContractValidateException("assetName can't be trx");
}
```
unconditionally in `AssetIssueActuator.validate()`. Additionally, downstream event consumers should be documented to always key on `contractType` in conjunction with `assetName`, never on `assetName` alone, since it is user-controlled input for TRC10 tokens.

## Proof of Concept
```java
// AssetIssueActuatorTest-style: asset creation with name "trx" succeeds when AllowSameTokenName == 0
dynamicStore.saveAllowSameTokenName(0);
AssetIssueContract contract = AssetIssueContract.newBuilder()
    .setOwnerAddress(ownerAddress)
    .setName(ByteString.copyFromUtf8("trx"))
    .setTotalSupply(1000L)
    .setTrxNum(1)
    .setNum(1)
    .setStartTime(startTime)
    .setEndTime(endTime)
    .build();
AssetIssueActuator actuator = new AssetIssueActuator();
actuator.setChainBaseManager(chainBaseManager);
actuator.setAny(Any.pack(contract));
actuator.validate(); // does NOT throw, because AllowSameTokenName == 0 skips the "trx" guard
actuator.execute(ret); // succeeds, asset "trx" created

// TransactionLogTriggerCapsuleTest: transfer of the "trx" TRC10 asset
TransferAssetContract transferAssetContract = TransferAssetContract.newBuilder()
    .setAssetName(ByteString.copyFromUtf8("trx"))
    .setOwnerAddress(ownerAddress)
    .setToAddress(toAddress)
    .setAmount(100L)
    .build();
// wrap into TransactionCapsule with contractType == TransferAssetContract
TransactionLogTriggerCapsule capsule = new TransactionLogTriggerCapsule(trxCapsule, blockCapsule);
assertEquals("trx", capsule.getTransactionLogTrigger().getAssetName());
assertEquals("TransferAssetContract", capsule.getTransactionLogTrigger().getContractType());
// A naive downstream consumer keying only on assetName=="trx" would misclassify this
// TRC10 transfer as a native TRX deposit despite contractType clearly indicating otherwise.
```
