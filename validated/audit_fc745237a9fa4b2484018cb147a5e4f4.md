### Title
Fragmentation in `PackedAncientStorage::pack` can produce more storage chunks than `many_ref_accounts_can_be_moved` accounts for, letting a multi-ref "newest" account version be packed into a slot lower than its current slot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Finding Description
`combine_ancient_slots_packed_internal` gates packing of multi-reference "newest alive" accounts (`many_refs_newest`) with `many_ref_accounts_can_be_moved`, which estimates the number of packed storages these accounts will need purely from total byte count: [1](#0-0) 

`required_ideal_packed` is `ceil(total_bytes / ideal_storage_size)`-ish, and the function only checks that every `many_refs_newest` group's slot is `<= target_slots_sorted[i_last]`, i.e. it validates against a single threshold slot computed from the *estimated* chunk count, not the slot that each chunk will actually be assigned to.

The actual chunking is done later by `PackedAncientStorage::pack`, a greedy first-fit packer that fills each output storage up to `ideal_size` and moves to a new storage whenever the next whole account/group doesn't fit: [2](#0-1) 

Because accounts/groups are placed as whole units (an item that doesn't fully fit is deferred entirely to the next storage rather than split at the byte level unless it's larger than one bin), this is a classic bin-packing scenario: several items each larger than half of `ideal_size` force one item per bin, so the *actual* number of chunks produced can exceed the simple `total_bytes / ideal_size` estimate used by `many_ref_accounts_can_be_moved`. Since `many_refs_newest` is sorted descending by slot before packing, extra fragmentation pushes lower-slot groups into extra trailing chunks that `many_ref_accounts_can_be_moved` never validated.

`write_packed_storages` then maps packed chunks to `target_slots_sorted` (reversed to descending) strictly by position, with no per-item slot validation: [3](#0-2) 

and the only remaining safety check is a length comparison, not a per-chunk slot comparison: [4](#0-3) 

**Concrete failure**: with `ideal_size=100`, three multi-ref groups `A(slot=200,60B)`, `B(slot=190,60B)`, `C(slot=150,60B)` (total 180B) yield `required_ideal_packed = 180/100+1 = 2`. If `target_slots_sorted = [140, 210, 220]`, the gate check uses `target_slots_sorted[len-2]=210 >= max(200,190,150)` and passes. But because each item is >50% of `ideal_size`, `pack()` actually produces **3** singleton chunks (`A`,`B`,`C`), and `pack.len()=3 == target_slots_sorted.len()=3` so the length guard also passes. `write_packed_storages` then zips `target_slots_sorted.rev() = [220,210,140]` with `[A,B,C]`, moving `C` (currently the newest alive version at slot 150) into storage at slot **140**, violating the documented invariant that packed accounts must move to a slot `>=` their current slot.

Since `C` belongs to `many_refs_this_is_newest_alive` (ref_count > 1, current slot is the *highest* slot-list entry for those pubkeys), there necessarily exists at least one older slot-list entry for the same pubkeys. If that older entry sits between the new (140) and old (150) slot, index lookups that pick the highest slot in the slot list will now resolve to the older, stale entry instead of the data that was actually newest, silently reviving a superseded account version.

### Impact Explanation
This is a real logic gap between the "can this be packed safely" estimator and the actual bin-packing algorithm used to write ancient storages. If triggered, it causes a stale/superseded account version to become the visible "newest" version for affected pubkeys after ancient-append-vec packing — matching the "wrong-version account load / silent balance change" bounty category for `AccountsDb`.

### Likelihood Explanation
Exploitation requires an attacker to engineer specific account data sizes (each group's byte size >50% of the dynamically-computed `ideal_storage_size`), specific slot separations, and enough distinct ancient slots with the right combination of alive/dead multi-ref accounts so the greedy packer fragments beyond the byte-based estimate while the length-only final guard still passes. `ideal_storage_size` is recomputed per-run from live-cluster state (`total_alive_bytes * 2 / max_ancient_slots`), and slot selection/ordering is influenced by many other live accounts, making precise construction of this scenario on a live validator difficult but not proven impossible over repeated attempts, since the attacker fully controls account data sizes, lamports, write frequency, and can create/close/reopen accounts to influence ref counts across slots. This is a genuine invariant gap, not merely a theoretical corner case, and is unexercised by the existing `test_many_ref_accounts_can_be_moved`/`test_calc_accounts_to_combine_many_refs` tests, which only test simple byte totals rather than fragmentation.

### Recommendation
Make `many_ref_accounts_can_be_moved` (or a post-pack validation step) verify against the *actual* number of chunks/target slots produced by `PackedAncientStorage::pack`, not a byte-count estimate. Concretely: after calling `pack()`, before calling `write_packed_storages`, walk the zipped `(target_slot, packed_chunk)` pairs and assert/bail if any chunk's constituent account slot exceeds its assigned `target_slot` (i.e. validate the invariant directly on the real pairing rather than trusting an independent capacity estimate).

### Proof of Concept
Add a Rust unit test in `accounts-db/src/ancient_append_vecs.rs` tests module that:
1. Builds `many_refs_newest` as three `AliveAccounts` groups mimicking `A(slot=200, bytes=60)`, `B(slot=190, bytes=60)`, `C(slot=150, bytes=60)` with `ideal_size = NonZeroU64::new(100)`.
2. Confirms `AccountsDb::many_ref_accounts_can_be_moved(&many_refs_newest, &[140,210,220], &tuning)` returns `true`.
3. Calls `PackedAncientStorage::pack(many_refs_newest.iter(), ideal_size)` and asserts `result.len() == 3`.
4. Simulates the same zip as `write_packed_storages` (`target_slots_sorted.iter().rev().zip(result)`) and asserts, for every `(target_slot, packed)` pair and every `(slot, _)` in `packed.accounts`, that `*target_slot >= slot` — this assertion should **fail** for the `C`/140 pairing, proving the invariant violation.

A broader property-based/fuzz harness would generate random sets of `(slot, bytes)` groups and random `ideal_size`/`target_slots_sorted`, then check the same post-hoc invariant across all `(target_slot, packed_chunk)` pairs after `many_ref_accounts_can_be_moved` returns `true` and `pack.len() <= target_slots_sorted.len()`.

    fn pack(
        mut accounts_to_combine: impl Iterator<Item = &'a AliveAccounts<'a>>,
        ideal_size: NonZeroU64,
    ) -> Vec<PackedAncientStorage<'a>> {
        let mut result = Vec::default();
        let ideal_size: u64 = ideal_size.into();
        let ideal_size = ideal_size as usize;
        let mut current_alive_accounts = accounts_to_combine.next();
        // starting at first entry in current_alive_accounts
        let mut partial_inner_index = 0;
        // 0 bytes written so far from the current set of accounts
        let mut partial_bytes_written = Saturating(0);
        // pack a new storage each iteration of this outer loop
        loop {
            let mut bytes_total = 0usize;
            let mut accounts_to_write = Vec::default();

            // walk through each set of alive accounts to pack the current new storage up to ideal_size
            let mut full = false;
            while !full && current_alive_accounts.is_some() {
                let alive_accounts = current_alive_accounts.unwrap();
                if partial_inner_index >= alive_accounts.accounts.len() {
                    // current_alive_accounts have all been written, so advance to next set from accounts_to_combine
                    current_alive_accounts = accounts_to_combine.next();
                    // reset partial progress since we're starting over with a new set of alive accounts
                    partial_inner_index = 0;
                    partial_bytes_written = Saturating(0);
                    continue;
                }
                let bytes_remaining_this_slot =
                    alive_accounts.bytes.saturating_sub(partial_bytes_written.0);
                let bytes_total_with_this_slot =
                    bytes_total.saturating_add(bytes_remaining_this_slot);
                let mut partial_inner_index_max_exclusive;
                if bytes_total_with_this_slot <= ideal_size {
                    partial_inner_index_max_exclusive = alive_accounts.accounts.len();
                    bytes_total = bytes_total_with_this_slot;
                } else {
                    partial_inner_index_max_exclusive = partial_inner_index;
                    // adding all the alive accounts in this storage would exceed the ideal size, so we have to break these accounts up
                    // look at each account and stop when we exceed the ideal size
                    while partial_inner_index_max_exclusive < alive_accounts.accounts.len() {
                        let account = alive_accounts.accounts[partial_inner_index_max_exclusive];
                        let account_size = account.stored_size();
                        let new_size = bytes_total.saturating_add(account_size);
                        if new_size > ideal_size && bytes_total > 0 {
                            full = true;
                            // partial_inner_index_max_exclusive is the index of the first account that puts us over the ideal size
                            // so, save it for next time
                            break;
                        }
                        // this account fits
                        partial_bytes_written += account_size;
                        bytes_total = new_size;
                        partial_inner_index_max_exclusive += 1;
                    }
                }

                if partial_inner_index < partial_inner_index_max_exclusive {
                    // these accounts belong in the current packed storage we're working on
                    accounts_to_write.push((
                        alive_accounts.slot,
                        // maybe all alive accounts from the current or could be partial
                        &alive_accounts.accounts
                            [partial_inner_index..partial_inner_index_max_exclusive],
                    ));
                }
                // start next storage with the account we ended with
                // this could be the end of the current alive accounts or could be anywhere within that vec
                partial_inner_index = partial_inner_index_max_exclusive;
            }
            if accounts_to_write.is_empty() {
                // if we returned without any accounts to write, then we have exhausted source data and have packaged all the storages we need
                break;
            }
            // we know the full contents of this packed storage now
            result.push(PackedAncientStorage {
                bytes: bytes_total as u64,
                accounts: accounts_to_write,
            });
        }
        result
    }
