Based on my research, I found the closest analog in nearcore. Note `check_actor_permissions` at `runtime/runtime/src/actions.rs:755-801` requires `actor_id == account_id` for `UseGlobalContract`, meaning only the account itself can opt into a global contract — this is actually the exact protective mechanism the Marmo report recommended (self-authorization). However, once an account opts into a **mutable** `GlobalContractIdentifier::AccountId` reference, the owner of that global contract retains perpetual, unilateral code-swap power over every account that ever referenced it — with no re-consent, no version pinning, and no way for the referencing account to detect or block the change.

### Title
Mutable Global Contracts (`GlobalContractDeployMode::AccountId`) grant the publisher perpetual unchecked control over every subscriber account's code, mirroring the Marmo `delegatecall`-to-arbitrary-implementation risk - (File: runtime/runtime/src/global_contracts.rs)

### Summary
NEAR's "global contracts" feature lets an account point its own code at a shared contract identified either immutably by `CodeHash` or mutably by the publisher's `AccountId` (`GlobalContractDeployMode::AccountId`, `core/primitives/src/action/mod.rs:135-144`). When an account calls `UseGlobalContract(GlobalContractIdentifier::AccountId(publisher))`, that account's own `FunctionCall` executions are thereafter serviced by whatever code currently lives at `publisher`'s global-contract slot — and the publisher can redeploy that slot at any later time via a fresh `DeployGlobalContractAction` with `deploy_mode: AccountId` [1](#0-0) , instantly and silently changing the code that runs with every subscriber account's authority, with no additional signature or consent from those subscribers.

### Finding Description
`UseGlobalContractAction` only stores a reference (`AccountContract::GlobalByAccount(id)`), not a pinned code hash, when the `AccountId` mode is used [2](#0-1) . The docs confirm this is intentional: "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users." [3](#0-2) 

Crucially, `check_actor_permissions` correctly restricts *who can call* `UseGlobalContract`/`DeployGlobalContract` — it requires `actor_id == account_id` [4](#0-3)  — so an account can only opt itself into a global contract, and only the publisher account itself can redeploy under its own `AccountId`. This is exactly the "self-authorized relay" pattern the Marmo report's resolution relied on (an SDK/owner signs the intent). However, that check only gates the *opt-in* and *redeploy* actions themselves — it does nothing to gate what happens *after* opt-in. Once subscribed, every `FunctionCall` action executed against the subscriber account resolves its code via `RuntimeContractIdentifier::resolve` to whatever is currently stored for the publisher's identifier at execution time (`docs/RuntimeSpec/Actions.md` / `protocol-model/spec/runtime-execution.md:88` — "`FunctionCall` | `action_function_call`... Resolves the contract"). That resolved code then executes with the full authority of the subscriber account — it can create promises that transfer the subscriber's balance, add/delete access keys via self-targeted receipts (where `predecessor_id == receiver_id == subscriber`, trivially satisfying `check_actor_permissions`), or otherwise fully control the account, exactly as an arbitrary `delegatecall`-chosen implementation would control the Marmo wallet.

The subscriber has no mechanism to pin to the code hash they reviewed at opt-in time, no on-chain notification of a code change, and no recourse if the publisher (or an attacker who compromises the publisher's keys) redeploys malicious code.

### Impact Explanation
Any account using `GlobalContractIdentifier::AccountId` effectively grants the publisher account continuing, revocable-only-by-migration control over its own contract logic and, transitively, its balance and access keys. If the publisher's keys are compromised or the publisher acts maliciously, they can redeploy code that drains every subscribing account's balance (via self-targeted `Transfer`/promise actions) or bricks subscriber accounts, constituting unauthorized value movement across every account that opted into that shared identifier — a systemic, multi-account fund-loss vector triggered by ordinary, protocol-legal transactions from a single account (the publisher).

### Likelihood Explanation
This requires no protocol bug or unusual code path — it is the documented, by-design behavior of `GlobalContractDeployMode::AccountId`. Any subscriber who opts in via `UseGlobalContract(AccountId(...))` is exposed for as long as they reference that identifier. The bar to trigger is only that the publisher's account key be compromised or the publisher itself turn malicious after subscribers have already opted in trusting the code reviewed at subscription time — a realistic, low-complexity threat given no on-chain warning or hash-pinning exists to mitigate it.

### Recommendation
Consider either (a) requiring `UseGlobalContract` for `AccountId`-mode identifiers to also record the code hash observed at opt-in time and treat subsequent mismatches as requiring explicit re-confirmation, or (b) prominently surfacing (in RPC/view responses and wallet UX) that `AccountId`-mode global contracts are mutable and re-deployable by the publisher at will, analogous to how the Marmo report recommended stating the `delegatecall`-implementation risk clearly to end users. At minimum, documentation and any SDK/wallet integration should treat opting into `GlobalContractIdentifier::AccountId` as granting the publisher perpetual code-execution authority over the subscriber account.

### Proof of Concept
1. Publisher account `pub.near` deploys a benign global contract: `DeployGlobalContractAction { code: benign_code, deploy_mode: AccountId }` [1](#0-0) .
2. Victim account `victim.near` reviews `benign_code` and opts in: `UseGlobalContractAction { contract_identifier: AccountId(pub.near) }`, which sets `victim.near`'s `AccountContract::GlobalByAccount(pub.near)` [5](#0-4) .
3. At any later time, `pub.near` (or an attacker who compromises `pub.near`'s key) redeploys under the same `AccountId` mode with malicious code containing, e.g., a method that issues `promise_batch_action_transfer` of `victim.near`'s entire balance to an attacker-controlled account, or `promise_batch_action_delete_account` with an attacker beneficiary.
4. Anyone (or a cron/keeper) calls a method on `victim.near`; the runtime resolves and executes `pub.near`'s newly redeployed malicious code with `victim.near`'s account authority, draining its funds — without `victim.near` ever having signed anything after step 2.

        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
