### Title
Unguarded `.unwrap()` on Sierra-to-Native compilation result crashes the sequencer when the compiler process is killed for exceeding `max_memory_usage` - (File: crates/apollo_compile_to_native/src/compiler.rs)

### Summary
The Suricata CVE-2024-38536 pattern is: hitting a configured memory cap (`http.memcap`) causes an allocation failure whose `NULL`/error result is not checked before being dereferenced, crashing the process. The closest reachable analog in this repo is in the Sierra-to-Native compiler wrapper: when the `max_memory_usage` resource cap (the sequencer's equivalent of `memcap`) is hit and the external native-compiler subprocess is killed or produces an incomplete artifact, the result is force-unwrapped with `.unwrap()` instead of being propagated as an error, which can panic the calling thread.

### Finding Description
`SierraToNativeCompiler::compile` runs the `starknet-native-compile` binary as a child process under `ResourceLimits` that enforce `max_cpu_time`, `max_file_size`, and `max_memory_usage` (the sequencer's memcap-style guard) via `setrlimit(RLIMIT_AS, ...)`: [1](#0-0) 

After `compile_with_args` returns success (i.e., the subprocess exited with status 0), the code loads the resulting native artifact from disk and immediately force-unwraps it: [2](#0-1) 

The call chain is `AotContractExecutor::from_path(...).map_err(...)?.unwrap()` — the `?` only converts the outer `Result`'s `Err` case; the trailing `.unwrap()` operates on an inner value (implied to be `Option<AotContractExecutor>` by the chaining pattern) and panics unconditionally if that inner value is anything other than the expected populated artifact (e.g., `None`, or a value indicating an unreadable/incomplete/mismatched compiled artifact). This mirrors the Suricata bug class: a resource-limit-triggered failure path (subprocess truncated/aborted near the memcap boundary) that is not defensively checked before being unwrapped, unlike the analogous CASM path (`SierraToCasmCompiler::compile` in `crates/apollo_compile_to_casm/src/compiler.rs`) which propagates compiler-process failures cleanly as `CompilationUtilError::CompilationError` without any unchecked unwrap. [3](#0-2) 

This compiler is invoked from `process_compilation_request` in the blockifier's `NativeClassManager`, which is reachable whenever a class is declared/executed and Cairo-Native compilation is enabled (`CairoNativeMode::WaitOnCompilation` or `LazyCompilation`): [4](#0-3) 

In `WaitOnCompilation` mode, compilation is invoked synchronously and inline from `set_and_compile`, itself called from `get_compiled_from_class_manager` during ordinary transaction execution (contract call to an as-yet-uncompiled class): [5](#0-4) [6](#0-5) 

Because the panic occurs inside `compiler.compile(...)` itself (not inside the `Result`-returning `process_compilation_request` wrapper), the existing `panic_on_compilation_failure` config flag — which is meant to be the single, explicit toggle for whether compilation failures should panic — is bypassed entirely; the unconditional `.unwrap()` fires regardless of that setting: [7](#0-6) 

### Impact Explanation
If reached in `WaitOnCompilation` mode, the panic propagates out of the transaction-execution call stack, since it is not isolated in a background worker thread the way `LazyCompilation` mode is (`run_compilation_worker` runs on a dedicated `std::thread::spawn`, so a panic there is thread-local and does not crash the process). A panic on the block-building/execution thread of the sequencer node would abort processing of the current block, i.e., a denial-of-service against block production — matching the "network unable to confirm new transactions" impact class. Note that whether the panic unwinds to abort the whole process or only the calling thread depends on how the batcher's tx-execution call sites are structured (thread boundaries, panic hooks, `catch_unwind` usage), which I could not fully verify from static inspection alone.

### Likelihood Explanation
Exploitability is conditioned on the operator having enabled Cairo-Native execution (`cairo_native_run_config.cairo_native_mode` != `Off`), which is not the default (`config_schema.json` shows the default as `"off"`), and additionally on `WaitOnCompilation` mode specifically for the panic to land in the synchronous execution path. I was unable to confirm from the code alone (a) the exact return type/semantics of the external `cairo_native::executor::AotContractExecutor::from_path` (it is defined in an external crate not present in this repo/index) or (b) under what precise conditions it would yield the value that trips the `.unwrap()` when the compilation subprocess is interrupted near its memory cap. This uncertainty limits confidence in likelihood; confirming it would require access to the `cairo_native` crate source or empirical testing (e.g., forcing `max_memory_usage` low enough to truncate/corrupt the native output file and observing whether `compile()` panics instead of returning `CompilationUtilError::CompilationError`).

### Recommendation
Replace the unconditional `.unwrap()` in `SierraToNativeCompiler::compile` with proper error propagation (e.g., `.ok_or_else(|| CompilationUtilError::CompilationError("Native compiler produced no output".into()))?`), consistent with how `apollo_compile_to_casm` handles compiler-process failures, so that a killed/OOM'd compilation subprocess always surfaces as a catchable `CompilationUtilError` rather than an unconditional panic that bypasses `panic_on_compilation_failure`.

### Proof of Concept
Not independently verified end-to-end (would require running with `cairo_native_mode: wait_on_compilation`, a real `starknet-native-compile` binary, and a crafted large Sierra class that trips `max_memory_usage`, then confirming whether `from_path` returns a value that triggers the `.unwrap()` panic rather than an `Err`). This is flagged as an area needing further, tool-assisted validation (e.g., a Devin session with the ability to build and run the sequencer with the `cairo_native` feature) rather than a fully proven exploit chain.

/// Processes a compilation request and caches the result.
fn process_compilation_request(
    class_cache: RawClassCache,
    compiler: Arc<SierraToNativeCompiler>,
    compilation_request: CompilationRequest,
    panic_on_compilation_failure: bool,
) -> Result<(), CompilationUtilError> {
    let (class_hash, sierra, casm) = compilation_request;
    if let Some(CompiledClasses::V1Native(_)) = class_cache.get(&class_hash) {
        // The contract class is already compiled to native - skip the compilation.
        return Ok(());
    }
    let sierra_for_compilation = into_contract_class_for_compilation(sierra.as_ref());
    let start = Instant::now();
    let compilation_result = compiler.compile(sierra_for_compilation);
    let duration = start.elapsed();
    log::info!(
        "Compiling to native contract with class hash: {:#066x}. Duration: {:.3} seconds",
        class_hash.0,
        duration.as_secs_f32()
    );
    match compilation_result {
        Ok(executor) => {
            let native_compiled_class = NativeCompiledClassV1::new(executor, casm);
            class_cache.set(
                class_hash,
                CompiledClasses::V1Native(CachedCairoNative::Compiled(native_compiled_class)),
            );
            log::info!("Compilation succeeded");
            Ok(())
        }
        Err(err) => {
            class_cache.set(
                class_hash,
                CompiledClasses::V1Native(CachedCairoNative::CompilationFailed(casm)),
            );
            log::error!(
                "Error compiling contract class with class hash: {:#066x}: {err}",
                class_hash.0
            );
            NATIVE_COMPILATION_ERROR.increment(1);
            if panic_on_compilation_failure {
                panic!("Compilation of class hash: {:#066x} failed", class_hash.0);
            }
            Err(err)
        }
    }
}
