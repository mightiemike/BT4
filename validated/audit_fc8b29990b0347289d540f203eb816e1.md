This is a strong, well-documented analog to the pico H-8 bug class. The root cause pattern matches precisely: `validate_receipt` (the "checker") validates a receipt's size only at the moment `ReceiptSizeExceeded` is checked in `ValidateReceiptMode::NewReceipt`, but the value being checked (the serialized receipt) is not actually constrained afterward — the runtime mutates the receipt (e.g., appending `output_data_receivers`, or via a returned value becoming a `Data` receipt) *after* that check, so the final on-chain receipt can exceed `max_receipt_size` even though it "passed validation." This is directly acknowledged in the codebase itself as [nearcore#12606](https://github.com/near/nearcore/issues/12606), with a workaround patched into forwarding logic but the root validation gap left unfixed. ### Title
Receipt size limit checked before mutation, not enforced on the final serialized receipt - ([File: runtime/runtime/src/verifier.rs])

### Summary
`validate_receipt` in `verifier.rs` enforces `max_receipt_size` only at one point in time (`ValidateReceiptMode::NewReceipt`), assuming that this snapshot remains a valid upper bound for the receipt as it is later persisted and transmitted. Similar to the pico `FieldWordRangeChecker` bug — where a range-check "assumes" its operand is already constrained to a canonical form without enforcing it — nearcore's receipt-size check assumes the receipt object it validates is the same object that will ultimately be serialized into the `ChunkStateWitness` and cross-shard receipt proofs, but the runtime does not re-validate after subsequent mutation (e.g. attaching `output_data_receivers`, or wrapping a large returned value into a `DataReceipt`).

### Finding Description
`validate_receipt` computes `borsh::object_length(receipt)` and compares it against `limit_config.max_receipt_size`, rejecting the receipt if it's too large, but only in `ValidateReceiptMode::NewReceipt` mode [5](#0-4) . This check happens at receipt-creation time, before promise resolution logic finishes composing the final receipt. Two concrete attacker-triggerable paths bypass the enforced invariant:

1. A `FunctionCall` that constructs a receipt whose size is exactly at `max_receipt_size` passes validation, but a subsequent `promise_return` mutates it by adding `output_data_receivers`, pushing it past the limit after the check already passed.
2. A returned value from a function call, sized up to `max_receipt_size`, is wrapped in a `DataReceipt` whose total (including framing) exceeds `max_receipt_size`, but this new/composed receipt is never re-validated against the same limit.

The runtime is aware of the issue: `ValidateReceiptMode::ExistingReceipt` documents that it "has to be less strict" specifically "because there is a bug which allows to create receipts that are above the size limit" [6](#0-5) , and `try_forward` in `congestion_control.rs` explicitly clamps oversized receipt sizes to `max_receipt_size` as "a bug workaround for oversized receipts" [3](#0-2) . This is the same class of defect as the pico finding: a size/limit invariant that a downstream consumer (forwarding/bandwidth logic, or the `ChunkStateWitness` size budget) implicitly relies on, but which is never actually enforced on the value that ultimately propagates through the system.

### Impact Explanation
The state-witness size limits are explicitly designed to bound the total uncompressed `ChunkStateWitness` to ~21 MiB precisely because `max_receipt_size` is assumed to be a hard cap [7](#0-6) . Because a legitimate user transaction can produce a receipt whose true serialized size exceeds `max_receipt_size` without failing validation, this budget is not actually enforced. Test cases in the repo demonstrate that oversized receipts do reach cross-shard incoming-receipt proofs / chunk state witnesses (`assert_oversized_receipt_occurred`) [8](#0-7) . This can inflate `ChunkStateWitness` beyond its intended bound, risking oversized witnesses being distributed to validators (contradicting the documented invariant that "all receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected") and potentially defeating the anti-DoS purpose of the receipt-size cap. This is not a hypothetical bug: it is a currently open, code-acknowledged issue (nearcore#12606), and only worked around (not fixed) for the forwarding/bandwidth-admission path.

### Likelihood Explanation
High reachability: any unprivileged contract caller can trigger both variants purely through ordinary cross-contract calls (`promise_return`/`promise_then` and returning a large value from a callback), as demonstrated by the repo's own tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) which are marked as reproducing a known, currently-unfixed bug [9](#0-8) . No special privileges, validator status, or network position are required — a standard transaction from an RPC caller suffices.

### Recommendation
Re-validate the final, fully-composed receipt (after `output_data_receivers` are attached and after return-value-to-`DataReceipt` conversion) against `max_receipt_size` before it is persisted or queued for cross-shard delivery, rather than relying on a pre-mutation snapshot check. Equivalently, ensure any mutation that can grow a receipt's serialized size is itself bounded so the post-mutation size cannot exceed the already-validated pre-mutation size, closing the gap the same way pico's fix would require directly constraining `operand_to_check`'s limbs rather than assuming they were already valid.

### Proof of Concept
The existing repository tests already constitute a reproduction: `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs` deploy a contract, drive a promise DAG that creates a receipt at exactly `max_receipt_size`, then mutate/wrap it so the final receipt exceeds the limit, and assert via `assert_oversized_receipt_occurred` that an oversized receipt is indeed observed in the chain's incoming receipt proofs / chunk data [10](#0-9) .

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
