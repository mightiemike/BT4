### Title
Missing balance/overflow validation in default (non-hardened) TRC10 Exchange swap path allows corrupted/negative pool balances - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary

### Finding Description
The reported bug class (unchecked overflow in swap USD/amount computation, plus no validation that the "dispensing" account actually holds enough of the output token before the swap debits it) maps directly onto java-tron's TRC10 **Bancor-style exchange** swap path used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`.

`ExchangeCapsule.transaction()` computes the output amount (`buyTokenQuant`) via a `Processor` and then updates both pool balances: [1](#0-0) 

The balance-update code only guards against a negative resulting pool balance (i.e. "dispensing custody has enough funds") when `hardenedCalc` is `true`: [2](#0-1) 

`hardenedCalc` comes from `allowHarden()`, which is gated behind the dynamic-parameter `allowHardenExchangeCalculation`, an opt-in chain parameter that must be turned on via a committee proposal: [3](#0-2) 

When this parameter is not enabled (the default, pre-proposal state on any chain/deployment), `ExchangeCapsule.transaction()` uses the plain `ExchangeProcessor`, which:
1. Performs the Bancor curve math using `double`/`Math.pow` arithmetic instead of exact/checked integer math, so extreme reserve/quantity combinations produce imprecise or corrupted `buyTokenQuant` values (the direct analog of the reported unchecked `u64` multiplication overflow): [4](#0-3) 
2. Performs `firstTokenBalance +/- quant` and `secondTokenBalance +/- buyTokenQuant` with plain Java arithmetic and **no post-condition check** that the resulting balances stay non-negative, exactly mirroring the report's second issue — no validation that the `dispensing_custody` (here, the token reserve being paid out) has enough funds before executing the swap: [5](#0-4) 

The existence of `SafeExchangeProcessor` (BigDecimal-based, with `addExact`/`subtractExact` and an explicit non-negative-balance check) and the `allowHarden()` opt-in flag confirms the java-tron team is aware of and has already engineered a fix for this exact bug class, but it is not the default enforced behavior: [6](#0-5) 

### Impact Explanation
On any network where `allowHardenExchangeCalculation` has not been activated by proposal, a broadcast `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transaction that drives an exchange pool toward extreme reserve ratios or very large quantities can cause `ExchangeProcessor`'s floating-point computation to produce a `buyTokenQuant` that exceeds the actual reserve, and the code will still subtract it from `secondTokenBalance`/`firstTokenBalance` without any check, corrupting the on-chain TRC10 exchange pool balances (potential negative balances stored in `Exchange`/`ExchangeV2` protobuf, or downstream users receiving more tokens than the pool holds). This is an accounting-corruption issue reachable from ordinary broadcast transactions, consistent with "asset or accounting corruption" impact category.

### Likelihood Explanation
The vulnerable code path (`ExchangeProcessor`, non-hardened) is the **default** execution path unless the committee has passed the `allowHardenExchangeCalculation` proposal; any anonymous account can create/fund an exchange pool and drive it to skewed ratios via `ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`, all of which are ordinary, permissionless transaction types.

### Recommendation
Make the `SafeExchangeProcessor` (checked-arithmetic, non-negative-balance validation) the mandatory path for all exchange swap/inject/withdraw calculations rather than gating it behind an opt-in hard fork parameter, or at minimum add the same non-negative-balance assertion currently applied only in the `hardenedCalc` branch to the default `ExchangeProcessor` branch in `ExchangeCapsule.transaction()`.

### Proof of Concept
Not independently reproduced in this analysis (test-execution environment unavailable); however, `ExchangeCapsuleTest`/`ExchangeProcessorTest` already exercise the divergence between the default double-based `ExchangeProcessor` and the checked `SafeExchangeProcessor`/hardened path, e.g. the hardened-only overflow-detection tests: [7](#0-6) 
demonstrate that only the hardened path throws/guards against overflow/negative-balance conditions, confirming the default path lacks this protection.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
