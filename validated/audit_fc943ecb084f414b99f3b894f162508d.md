### Title
Batch Liquidation via `liquidate-multi` Absorbs Partial Failures, Stranding Committed Sub-Call State - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` iterates over a list of liquidation positions using `map`, calling `call-liquidate` for each one, and always returns `(ok (list-of-responses))` at the top level. Because Clarity's automatic rollback-on-error only reverts the specific `contract-call?` that returns an error (and its own sub-calls), not the whole logical "position" being processed inside a `map`, a `liquidate` invocation that partially succeeds (e.g., the debt repayment to the vault commits) and then fails on a later step (e.g., the market-vault ledger update) leaves the earlier, already-committed cross-contract mutation in place while the corresponding debt/collateral bookkeeping never happens — because the overall transaction, as returned by `liquidate-multi`, is still `ok`.

### Finding Description
`liquidate` performs several sequential cross-contract calls guarded by `try!`: [1](#0-0) 

```
;; execute liquidation
(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))

;; update obligations and socialize bad debt
(let ((debt-updated (try! (contract-call? .v0-market-vault
                          debt-remove-scaled
                          borrower
                          scaled-to-remove
                          debt-aid)))
      ...
      (coll-removed (try! (contract-call? .v0-market-vault
                          collateral-remove
                          borrower
                          coll-final
                          collateral-ft
                          coll-aid
                          actual-receiver)))
``` [2](#0-1) 

`vault-system-repay` is a separate `contract-call?` (to `.v0-vault-*`) and therefore its own atomicity boundary: if it succeeds, its state changes commit independently of what happens afterward in `liquidate`. If the *subsequent* `debt-remove-scaled` or `collateral-remove` call to `.v0-market-vault` then fails, `liquidate` returns an `err` — but this does not undo the already-committed `vault-system-repay` state, because that was a distinct, already-successful `contract-call?`.

`liquidate-multi` invokes `liquidate` for each position through `call-liquidate` via `map`, and never asserts on the outcome: [3](#0-2) 

```
;; Failed liquidations return error codes but don't revert entire batch
(define-public (liquidate-multi
                (positions (list 64 { ... })))
  (ok (map call-liquidate positions)))
``` [4](#0-3) 

Because `liquidate-multi`'s own top-level result is unconditionally `(ok ...)`, Clarity's "roll back everything if the top-level call errors" rule never triggers — the transaction as a whole commits. Only the specific failed `contract-call?` (e.g. `debt-remove-scaled`/`collateral-remove`) rolls back its own effects; the earlier `vault-system-repay` contract-call's effects (debt-ft tokens pulled and delivered to the vault) remain permanently committed, even though the position's debt ledger in `market-vault` was never reduced and no collateral was seized for the liquidator.

This is structurally the same defect class described in the analog report: a loop/batch step assumes each iteration is all-or-nothing, but in reality partial execution from one iteration can leave irreversible side effects when a later step in that same iteration fails, and the enclosing batch construct (`map`, unguarded) absorbs the failure instead of causing the whole operation to revert.

### Impact Explanation
A liquidator calling `liquidate-multi` can have their debt-token repayment consumed by the vault (`vault-system-repay`, an irreversible external asset movement) for a given position, while never receiving the corresponding seized collateral and while the borrower's on-chain debt record is left unchanged for that position, if the immediately following `debt-remove-scaled`/`collateral-remove` call errors out. Because `liquidate-multi` always returns `ok`, there is no transaction-level revert to undo the repayment. This is a direct loss of the liquidator's funds with no compensating collateral or debt-reduction — this falls under **Critical: direct theft of user funds (permanent loss to the liquidator) / protocol insolvency risk** since vault accounting and market-vault ledger accounting become desynchronized (vault received real assets tied to a debt-repay that was never reflected on the ledger).

### Likelihood Explanation
Exploitability depends on being able to force `debt-remove-scaled` or `collateral-remove` to fail on `.v0-market-vault` after `vault-system-repay` has already succeeded for the same call — e.g., by crafting a batch where an earlier position in the list mutates shared state (the borrower's collateral/debt bitmask, cached indexes) such that a later position's freshly-recomputed `coll-final`/`scaled-to-remove` becomes inconsistent with the market-vault's actual stored state at the time of the second contract-call, or by supplying a `collateral-ft`/`debt-ft` trait argument that is internally consistent with `liquidate`'s own pre-checks but causes the underlying `ft-transfer?` inside `market-vault`'s `collateral-remove` to fail. This requires careful setup of a batch (multiple attacker-chosen positions, possibly involving the attacker's own borrow positions) but does not require any privileged access, oracle manipulation, or DAO compromise — it only needs a caller of the already-public `liquidate-multi` entry point.

### Recommendation
Do not silently absorb per-position failures in `liquidate-multi`. Either:
1. Make `call-liquidate` execute each position via a true `contract-call?` boundary (e.g. call back into the market contract itself, or a dedicated helper) so that Clarity's per-call rollback guarantees actually apply to each position, not just to the innermost failing sub-call; or
2. Explicitly `asserts!`/`try!` on each `call-liquidate` result inside `liquidate-multi` so any partial failure causes the entire batch transaction to revert, matching the "atomic" claims in the code comments (`;; Liquidates multiple positions atomically`), which currently contradicts the actual `map`-based swallow-and-continue behavior.

### Proof of Concept
1. Liquidator submits `liquidate-multi` with a list containing position `P` for `borrower B`, asset pair `(collateral-ft, debt-ft)`.
2. Inside `liquidate(B, ...)` (invoked via `call-liquidate`/`map`), all pre-checks pass and `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` succeeds, transferring the liquidator's `debt-ft` tokens into `.v0-vault-*` — this contract-call commits independently. [5](#0-4) 
3. The following `(try! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-to-remove debt-aid))` or the subsequent `collateral-remove` call fails (e.g., due to a state inconsistency caused by another position in the same batch, or a mismatched `collateral-ft`). [6](#0-5) 
4. `liquidate` returns `err`; `call-liquidate` passes this `err` through unmodified; `map` collects it as a list element. [4](#0-3) 
5. `liquidate-multi` still returns `(ok (list ... err-for-P ...))` — the top-level call succeeds, so no transaction-wide rollback occurs, and the `vault-system-repay` transfer from step 2 remains permanently committed while `B`'s debt/collateral records are unchanged for `P`. [7](#0-6)
