### Title
PoisonMicroblock accepts identical header pairs (mblock_header_1 == mblock_header_2), allowing miner-reward theft with zero actual equivocation - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
`check_microblock_header_signer` and `handle_poison_microblock` never verify that `mblock_header_1 != mblock_header_2`; they only require that both headers recover to the same public-key hash. Because a header trivially recovers to the same pubkey as itself, an attacker can submit `PoisonMicroblock(h, h.clone())` for any single, honestly-produced, publicly broadcast microblock header `h` and have it accepted as a valid equivocation, redirecting the miner's coinbase commission to the "reporter."

### Finding Description
The broken equality: a valid PoisonMicroblock report must represent a genuine double-signature, i.e. `mblock_header_1 != mblock_header_2` at the same `(prev_block, sequence)`. This precondition is never checked.

- `check_microblock_header_signer` (stackslib/src/chainstate/stacks/db/transactions.rs:686-713) only compares the two recovered pubkey hashes: [1](#0-0) 
If `mblock_hdr_1 == mblock_hdr_2` (bit-identical, including identical signature), `pkh1` and `pkh2` are trivially equal, so this passes with no fork evidence whatsoever.

- The mempool/static admission check for `PoisonMicroblock` (stackslib/src/chainstate/stacks/db/blocks.rs:6844-6868) only checks `sequence`, `prev_block`, `version` equality and pubkey-hash equality between the two headers — never that the headers actually differ (e.g. differing `tx_merkle_root`/`signature`), which is exactly what "identical headers" satisfy: [2](#0-1) 

- `handle_poison_microblock` (stackslib/src/chainstate/stacks/db/transactions.rs:722-856) then looks up `get_microblock_pubkey_hash_height(&pubkh)`, checks the maturity window, and unconditionally calls `insert_microblock_poison` using `mblock_header_1.sequence` as the reported fork point — with no additional inequality check: [3](#0-2) [4](#0-3) 

Attacker's exact input: take any legitimately signed/broadcast `StacksMicroblockHeader h` (public data, no private key needed) whose signer's pubkey hash was registered at some height `H` still within `MINER_REWARD_MATURITY`, and submit `TransactionPayload::PoisonMicroblock(h.clone(), h.clone())`. Both the mempool admission path and `handle_poison_microblock`/`process_transaction_payload` accept it, and `insert_microblock_poison(H, reporter, h.sequence)` is written.

Downstream consequence: `find_mature_miner_rewards` in stackslib/src/chainstate/stacks/db/accounts.rs reads this report via `get_poison_microblock_report` and redirects the miner's coinbase commission to the reporter instead of the miner: [5](#0-4) [6](#0-5) 

No guard in the traced path (`check_microblock_header_signer`, the mempool static check, `handle_poison_microblock`, or `find_mature_miner_rewards`) ever asserts the two headers are distinct. All existing tests that exercise this path (e.g. transactions.rs:5525-5529, 5647-5649, 5741-5745, 5765-5769) explicitly construct two *different* signed headers (`assert!(mblock_1 != mblock_2)`), so the identical-header case is untested and unguarded.

### Impact Explanation
This is a reward mis-payment: the honest miner's coinbase commission (5% per `POISON_MICROBLOCK_COMMISSION_FRACTION`, stackslib/src/chainstate/stacks/db/mod.rs:939) at the affected block height is redirected to an attacker who never observed or caused any actual microblock fork/equivocation. This matches the "poison or reward mis-payment bounded to fees" High-severity category: it is a bounded, repeatable reward theft against any specific miner/height (any time a miner's microblock-signed header becomes public and is within the maturity window), triggerable by a single unprivileged participant with no stake requirement.

### Likelihood Explanation
Preconditions are minimal and cheap: the attacker needs only (a) the miner's pubkey hash registered at some height `H` (this happens automatically for every anchored block that declares a microblock pubkey hash, or once any single microblock is produced and observed on the network), and (b) submission within `MINER_REWARD_MATURITY` blocks of `H`. No BTC spend, no stake, no privileged role, and no access to any private key is required — the attacker only needs to observe one publicly broadcast, honestly-signed microblock header and resubmit it twice as the "poison" pair. This is trivially repeatable against any miner who ever produces microblocks.

### Recommendation
Add an explicit equivocation check before treating a `PoisonMicroblock` as valid: require `mblock_header_1 != mblock_header_2` (full struct inequality, not just pubkey/sequence/prev_block/version equality) in both `check_microblock_header_signer` (or immediately before/after it in `handle_poison_microblock`) and in the mempool/static admission check in `blocks.rs`. Reject the transaction (return `Err`/`MemPoolRejection`) if the two headers are bit-identical.

### Proof of Concept
Rust integration test plan (extending the existing `process_poison_microblock_valid` style test in stackslib/src/chainstate/stacks/db/transactions.rs):
1. Register a microblock pubkey hash for a real signer key at height 1 via `StacksChainState::insert_microblock_pubkey_hash`.
2. Construct one honestly-signed `StacksMicroblockHeader h` via `make_signed_microblock(&block_privk, &privk, BlockHeaderHash([0x11;32]), 123)`.
3. Build `TransactionPayload::PoisonMicroblock(h.header.clone(), h.header.clone())` (bit-identical pair) rather than the two independently-generated headers used in existing tests.
4. Sign and call `StacksChainState::process_transaction(&mut conn, &signed_tx_poison_microblock, false, None)`.
5. Assert the equality that should NOT hold: `report_opt = StacksChainState::get_poison_microblock_report(&mut conn, 1)` must be `None` (no report inserted), and `process_transaction` must return `Err(Error::InvalidStacksTransaction(..))` — asserting the fix. Currently (pre-fix) the call succeeds and `report_opt` equals `Some((reporter_addr, 123))`, demonstrating the wrongful slash.
