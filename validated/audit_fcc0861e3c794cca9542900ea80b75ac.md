### Title
Token Name Front-Running in `AssetIssueActuator` Causes Denial-of-Service - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator.validate()` rejects an `AssetIssueContract` transaction if an asset with the same `name` already exists in the `AssetIssueStore`. Because `name` is taken directly from user-supplied transaction parameters (visible in the mempool before confirmation), an attacker can observe a pending `AssetIssueContract` transaction, extract the desired asset name, and submit a competing transaction with a higher energy/bandwidth priority to register the same name first. This causes the victim's original transaction to fail validation with `"Token exists"`, mirroring the root cause described in the external report: a deterministic, publicly predictable/observable identifier taken straight from mempool input is used in an existence check that reverts if front-run.

### Finding Description
In `AssetIssueActuator.validate()` (actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java, lines 210-214), when `allowSameTokenName == 0`, the actuator performs a pre-existence check keyed purely on the attacker-observable `name` field: [1](#0-0) 

```java
if (dynamicStore.getAllowSameTokenName() == 0
    && assetIssueStore.get(assetIssueContract.getName().toByteArray())
    != null) {
  throw new ContractValidateException("Token exists");
}
```

The `name` value comes directly from the `AssetIssueContract` protobuf message submitted by the user, with no binding to the submitter's address, transaction hash, or any other value that would make it unique per-sender (unlike, e.g., `WalletUtil.generateContractAddress`, which mixes in `ownerAddress` and the transaction hash: [2](#0-1) ). This is structurally identical to the reported `LeapFactory.createDrop()` bug: the salt/identifier used for a global existence check is raw user input observable in the mempool, so an attacker can front-run with an identical value and cause the victim's transaction to revert.

The relevant test `IssueSameTokenNameAssert` confirms the exact "Token exists" revert path exercised when a name collision occurs: [3](#0-2) 

### Impact Explanation
An attacker monitoring the mempool can identify a pending `AssetIssueContract` transaction with a distinctive asset `name`, then submit a transaction issuing an asset with the identical `name` (with a small TRX fee sufficient to pass `calcFee()`), aiming to be included in an earlier block or the same block with priority. If the attacker's transaction is confirmed first, the victim's transaction fails at `validate()` with `"Token exists"`, denying the legitimate user their intended token identifier. This is a concrete availability/DoS impact against an unprivileged, permissionless actuator (`AssetIssueContract`) reachable by any account with sufficient balance to pay the asset issue fee — no privileged role is required to exploit or be affected.

### Likelihood Explanation
Likelihood is limited by the fact that `allowSameTokenName` is a chain-wide dynamic parameter; on chains/configurations where it is set to `1` (allow same token name), this specific check is bypassed entirely (`dynamicStore.getAllowSameTokenName() == 0` guards the check). On networks/configurations still operating with `allowSameTokenName == 0`, the attack is straightforward: mempool transactions are publicly visible, the `name` field is plaintext, and front-running only requires submitting a competing transaction with the same name and adequate fee before the victim's transaction is packed into a block.

### Recommendation
Avoid keying the uniqueness/existence check purely on attacker-controlled, mempool-visible data. Options include:
- Bind the effective asset identifier to the owner address (e.g., derive/store a combined key of `ownerAddress + name`, or continue to rely on the auto-incrementing numeric `id` from `dynamicStore.getTokenIdNum()` as the canonical unique identifier, and treat `name` collisions as a soft/non-blocking condition when `allowSameTokenName` semantics allow it).
- If uniqueness of human-readable names must be enforced, consider a commit-reveal scheme or allow the original submitter to reclaim/retry with a deterministic tie-breaker (e.g., first-seen by transaction hash within the same block ranking, or refund-and-retry semantics) so a losing collision does not simply fail with no recourse.

### Proof of Concept
1. Attacker monitors the mempool and observes a pending `AssetIssueContract` transaction from Victim with `name = "MYTOKEN"`.
2. Attacker crafts and broadcasts their own `AssetIssueContract` transaction with `name = "MYTOKEN"`, `ownerAddress = attacker`, and a fee sufficient to pass validation, ensuring it gets packed into an earlier block (or with higher priority in the same block).
3. Attacker's transaction succeeds, calling `assetIssueStore.put(...)` for `"MYTOKEN"` as shown in `AssetIssueActuator.execute()`: [4](#0-3) 
4. When Victim's original transaction is processed, `validate()` finds `assetIssueStore.get("MYTOKEN") != null` and throws `ContractValidateException("Token exists")`, as covered by the existing test `IssueSameTokenNameAssert`: [5](#0-4) 
5. Victim's transaction is rejected, denying them the intended token name — a direct DoS analog to the `createDrop()` front-running issue in the external report.
