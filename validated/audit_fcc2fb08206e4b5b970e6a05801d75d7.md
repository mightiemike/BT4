### Title
Duplicate witness-vote entries can be persisted into `AccountCapsule`/`VotesCapsule` via `VoteWitnessActuator` due to missing per-witness merge/dedup check - (File: `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

### Summary
`VoteWitnessActuator`, the actuator handling the unprivileged, user-submitted `VoteWitnessContract` transaction, appends every `Vote` entry from the transaction directly into the voter's `AccountCapsule` votes list and the corresponding `VotesCapsule` without checking whether an entry for the same witness address already exists in that same transaction. This is the same root-cause pattern as the reported Phuture "duplicate asset can be added" bug: a routine that mutates a collection is missing a "does this key already exist" check before appending, so a single call can push duplicate entries into a list that is expected to hold one entry per key.

### Finding Description
`VoteWitnessActuator.validate()` iterates `contract.getVotesList()` and only validates each vote's address/witness existence and the aggregate vote sum against the voter's TRON power; it never rejects or merges multiple `Vote` entries that reference the same witness address: [1](#0-0) 

`countVoteAccount()` then clears the previous votes and blindly re-adds every vote from the contract, one-by-one, with no deduplication: [2](#0-1) 

This is a real divergence from the parallel implementation of the same feature for the TVM native-contract path, `VoteWitnessProcessor`, which explicitly builds a `Map<ByteString, Long>` keyed by witness address and merges duplicate votes for the same witness before applying them: [3](#0-2) [4](#0-3) 

The existence of a test helper that deliberately constructs a `VoteWitnessContract` with many repeated `Vote` entries for the same witness address (`getRepeateContract`) confirms that this scenario is reachable and was at least partially considered by the test suite: [5](#0-4) [6](#0-5) 

Because `VoteWitnessActuator` does not perform the same per-witness merge that `VoteWitnessProcessor` performs, a `VoteWitnessContract` containing multiple `Vote` entries for the same witness address results in multiple duplicate `Vote` protobuf entries being stored in the voter's persisted `AccountCapsule` votes list and the `VotesCapsule` new-votes list, rather than a single merged entry per witness — mirroring the "duplicate asset" defect pattern (append without existence/merge check).

### Impact Explanation
The `AccountCapsule`/`VotesCapsule` votes lists are consumed elsewhere in the system (e.g., wallet/API vote queries, and vote/reward accounting in `MortgageService`/maintenance processing) with an implicit assumption of one entry per witness. Duplicated entries for the same witness:
- Corrupt the on-chain representation of a voter's ballot (the persisted list no longer matches the canonical "one vote entry per witness" invariant enforced by the TVM path), a state/accounting divergence between the two code paths implementing the identical feature.
- Can distort or bloat data returned via wallet/API vote queries, and any downstream logic that does an address-keyed lookup/get against this list (returning only the first match) will silently drop votes/lose data, while logic that sums all list entries will still work by coincidence — an inconsistency depending on the consumer, itself a form of internal-state divergence risk.
- Is reachable by any unprivileged account merely by crafting a normal `VoteWitnessContract` with a repeated witness address; no special privilege is required.

The overall total-vote bound (checked against `tronPower`) still holds because it sums all `Vote` entries regardless of duplication, so this does not directly enable over-voting beyond the account's `tronPower`, but it does create a genuine and provable structural divergence in stored account state versus the invariant maintained by the equivalent TVM-based processor.

### Likelihood Explanation
High — this requires no special privileges, only crafting a normal `VoteWitnessContract` with duplicate witness addresses in the `votes` field, exactly as demonstrated by the existing test helper `getRepeateContract`.

### Recommendation
Mirror the merge logic already present in `VoteWitnessProcessor.execute()` inside `VoteWitnessActuator.countVoteAccount()`: aggregate `Vote` entries by witness address into a map before calling `accountCapsule.addVotes(...)` / `votesCapsule.addNewVotes(...)`, ensuring at most one entry per witness is ever persisted, consistent with the TVM code path.

### Proof of Concept
1. An unprivileged account submits a `VoteWitnessContract` whose `votes` field contains multiple `Vote` messages that all reference the same witness address (as constructed by `getRepeateContract` in the test file, e.g. 30 `Vote` entries of 1 vote each for `WITNESS_ADDRESS`). [5](#0-4) 
2. `VoteWitnessActuator.validate()` accepts the contract because it only validates the summed vote count against `tronPower`, never checking for duplicate witness addresses within the contract. [1](#0-0) 
3. `countVoteAccount()` iterates the 30 duplicate `Vote` entries and calls `accountCapsule.addVotes(...)` / `votesCapsule.addNewVotes(...)` once per entry with no merge, resulting in 30 duplicate `Vote` records for the same witness stored in the account's votes list, instead of one merged `Vote` record with the summed count. [2](#0-1)
