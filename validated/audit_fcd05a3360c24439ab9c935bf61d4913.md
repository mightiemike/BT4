### Title
Unbounded Native Recursion in Compiled Class Hash Computation Causes Stack Overflow on Declare — ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
The CVE describes a preprocessor (GPP) that recurses on a crafted, deeply nested input without a depth bound, exhausting the native call stack and causing a segmentation fault. The sequencer contains an analogous pattern: `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` recursively walks a `NestedIntList` bytecode-segmentation tree with **no depth limit**, and this function is invoked directly (not in the isolated compiler subprocess) whenever a class is declared.

### Finding Description
When a class is declared, the gateway's `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:60-74`) first shells out to a resource-limited *subprocess* to run the external Sierra→CASM compiler (`crates/apollo_compile_to_casm/src/compiler.rs:30-55`, via `compile_with_args` in `crates/apollo_compilation_utils/src/compiler_utils.rs`). That subprocess is only bounded by CPU time, memory (AS) and file-size rlimits — there is no `RLIMIT_STACK` enforcement (`crates/apollo_compilation_utils/src/resource_limits/resource_limits_unix.rs`).

Critically, after the subprocess returns the compiled `CasmContractClass` (deserialized straight from subprocess stdout), the **calling process itself** immediately computes the compiled class hash:
```rust
let executable_class = self.compiler.compile(class)?;
let executable_class_hash = executable_class.hash(&HashVersion::V2);
``` [1](#0-0) 

`hash()` calls `hash_inner` → `bytecode_hash` → `bytecode_hash_node`, which recurses once per nesting level of the `bytecode_segment_lengths: NestedIntList` field returned by the compiler, with no depth check whatsoever: [2](#0-1) 

This runs in the SierraCompiler/gateway's own native process/thread — the same process whose crash affects tx ingestion, not the sandboxed compiler subprocess.

Notably, the blockifier's own analogous structure-builder explicitly asserts the depth is bounded:
```rust
assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");
``` [3](#0-2) 
This assertion's mere existence shows the segmentation tree emitted by the Sierra→CASM compiler is not guaranteed to be flat/shallow — yet the hash computation path in `starknet_api` imposes no equivalent guard, and is the one that executes first, prior to any depth sanity check, directly on attacker-influenced compiler output.

### Impact Explanation
An unbounded, deeply nested `bytecode_segment_lengths` tree returned by the compiler drives `bytecode_hash_node` to recurse once per tree level. Each recursion level allocates a stack frame (iterator state, `Vec` collection via `collect_vec()`, hash-array allocation). With enough nesting, this exhausts the native thread stack of the SierraCompiler/gateway component. A native stack overflow in Rust is not a catchable panic — it aborts/segfaults the process. If the SierraCompiler runs as a shared gateway component (as its architecture and `max_concurrent_declare_compilations` config imply), crashing it halts declare-transaction ingestion network-wide until the component restarts — an availability/DoS impact on the sequencer's ability to admit transactions, reachable purely by submitting a declare transaction with a crafted class.

### Likelihood Explanation
This is reachable by any unprivileged declarer — no special privileges are required, and the class only needs to be shaped so that the compiler's segmentation heuristic produces a deeply nested (rather than flat) `NestedIntList`. Whether the standard Sierra→CASM compiler can be driven, within the `max_bytecode_size` limit (default `80 * 1024` felts, `crates/apollo_sierra_compilation_config/src/config.rs:9`), to emit segmentation nesting deep enough to overflow the default thread stack is the main determinant of practical likelihood; it is bounded by the external `cairo-lang-starknet-classes` segmentation algorithm, which is outside this repo, so exact feasibility cannot be fully confirmed from code alone — but the complete absence of any recursion-depth guard on the hashing path (in contrast to the explicit depth assertion the same codebase applies elsewhere for the identical data structure) is a clear defect matching the reported bug class.

### Recommendation
Convert `bytecode_hash_node` (and its sibling `bytecode_hash` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs`) to an iterative/explicit-stack algorithm, or enforce a maximum segmentation depth (mirroring the `segmentation_depth <= 1` invariant already relied on elsewhere) before hashing, rejecting classes whose compiler output violates it instead of recursing unboundedly. Additionally, consider performing the hash computation inside the same resource-limited subprocess/sandbox used for compilation, so a crash there cannot affect the gateway/SierraCompiler process.

### Proof of Concept
1. Craft (or find) a Sierra contract whose control-flow/function structure causes the Sierra→CASM compiler to emit a `bytecode_segment_lengths` tree with many nested `NestedIntList::Node` levels (test fixtures such as `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils_test.rs:1-133` show the nested-node shape the field can take).
2. Submit this class via a Declare transaction to the gateway.
3. `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:60-74`) successfully compiles it in the sandboxed subprocess, then calls `executable_class.hash(&HashVersion::V2)` in-process.
4. `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:111-132`) recurses once per nesting level with no bound; sufficiently deep nesting exhausts the native stack of the gateway/SierraCompiler process, aborting it and disrupting declare-transaction ingestion for the network until restart.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
```
