Duplicate witness addresses in `VoteWitnessContract` bypass per-witness accounting and inflate stored vote entries - ([File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java])

### Summary
`VoteWitnessActuator.validate()` and `countVoteAccount()` accept a `VoteWitnessContract` containing a list of `Vote` entries and only validate that: (1) the vote count is ≤ `MAX_VOTE_NUMBER` (30), (2) each address is valid, exists as an account and a witness, and (3) the *sum* of all vote counts does not exceed the voter's `tronPower`. Unlike the SSVNetwork `registerValidator()` bug (which validated sorted-order but not uniqueness of operator IDs), this code performs no uniqueness check at all on `vote.getVoteAddress()` across the list, and unlike the newer TVM-native path (`VoteWitnessProcessor`), it does not merge duplicate witness entries into a map before applying them.

### Finding Description
In `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`: [1](#0-0) 

The loop only checks address validity, positive vote count, and accumulates a `sum` for the `tronPower` cap — it never tracks which witness addresses have already appeared. A voter can submit a contract with the same witness address repeated multiple times (up to the 30-vote limit), and `validate()` will accept it as long as the total sum stays within `tronPower`.

In `countVoteAccount()`, each `Vote` is applied independently: [2](#0-1) 

`AccountCapsule.addVotes()` simply appends a new `Vote` protobuf entry to the account's votes list rather than merging by address: [3](#0-2) 

This is functionally identical in spirit to the SSVNetwork issue: a list that is supposed to represent one entry per distinct participant (operator ID / witness) is stored with duplicates because uniqueness is never enforced, only aggregate/order constraints are checked.

By contrast, the newer VM-native voting path (`actuator/src/main/java/org/tron/core/vm/nativecontract/VoteWitnessProcessor.java`) explicitly merges duplicate witness votes into a `HashMap` before persisting: [4](#0-3) 

This demonstrates the java-tron team is aware duplicate-witness merging is required for correctness, but the older `VoteWitnessActuator` (still reachable via the ordinary `VoteWitnessContract` broadcast transaction, not just via TVM) lacks this protection.

Reward computation (`MortgageService.computeReward`) then iterates the account's stored votes list per-entry without deduplication: [5](#0-4) [6](#0-5) 

### Impact Explanation
The most direct effect is that an account's `votes` list (both in `AccountCapsule` and `VotesCapsule`) can contain multiple `Vote` entries for the same witness address instead of one merged entry. Because reward/tally logic (`MortgageService.computeReward`, `VoteRewardUtil.computeReward`, `MaintenanceManager.countVote`/`Wallet.countVote`) sums per-entry contributions, the total vote count and total reward attributed to that witness end up numerically equivalent to a single merged entry with the summed count — so this does not obviously allow forging additional voting power beyond what `tronPower` already limits. The primary confirmed impact is data/state bloat and inconsistency: the account's votes list can hold up to 30 duplicate entries referencing the same witness, consuming more storage than intended and producing votes-list representations that differ from the semantically equivalent merged-map path used by `VoteWitnessProcessor`. I was not able to fully verify, within the scope of this analysis, whether any other consumer of `accountCapsule.getVotesList()` (e.g. genesis/exchange calculations, TVM `VoteCount` precompile, RPC serialization) assumes uniqueness in a way that would produce a stronger consensus-divergence or double-counting effect; this would require deeper tracing of every reader of that list across `chainbase`/`actuator`/`framework`.

### Likelihood Explanation
Triggering this requires only broadcasting an ordinary `VoteWitnessContract` transaction (a standard, unprivileged wallet action) with a repeated witness address in the `votes` list. No special permissions, leaked keys, or malicious peer/node behavior are needed — it is directly reachable from any account holder via a normal signed transaction.

### Recommendation
Add a uniqueness check on `vote.getVoteAddress()` within `VoteWitnessActuator.validate()`, mirroring what `VoteWitnessProcessor.execute()` already does by merging votes into a `Map<ByteString, Long>` before summing/persisting them, so that `countVoteAccount()` writes at most one `Vote` entry per witness address into `AccountCapsule`/`VotesCapsule`.

### Proof of Concept
1. Freeze balance for `OWNER_ADDRESS` sufficient to cover the intended vote count for `TRX_PRECISION`-scaled votes.
2. Construct a `VoteWitnessContract` for `OWNER_ADDRESS` with, e.g., 3 `Vote` entries all pointing to the same `WITNESS_ADDRESS`, each with `vote_count = 1`, so the sum (3) stays within `tronPower`.
3. Call `VoteWitnessActuator.validate()` — it succeeds because no duplicate-address check exists (see lines 98–121 of `VoteWitnessActuator.java`).
4. Call `execute()` → `countVoteAccount()` — `accountCapsule.addVotes(WITNESS_ADDRESS, 1)` is invoked three times, appending three separate `Vote` protobuf entries for `WITNESS_ADDRESS` into the account's votes list instead of one merged entry with count 3 (compare with `VoteWitnessActuatorTest.voteWitnessTwice` at framework/src/test/java/org/tron/core/actuator/VoteWitnessActuatorTest.java:498-536, which shows repeated votes producing multiple/aggregated results depending on path).
5. Inspect `dbManager.getAccountStore().get(OWNER_ADDRESS).getVotesList()` to confirm multiple entries exist for the same witness address, unlike the deduplicated map used in `VoteWitnessProcessor`.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
