### Title
Stack exhaustion (process abort) via deeply nested JSON in `Message` untagged enum during JSON-RPC request parsing - ([File: chain/jsonrpc-primitives/src/message.rs])

### Summary
The JSON-RPC ingress path deserializes every incoming request body into `WireMessage`/`Message`, both declared with `#[serde(untagged)]`. Untagged enum deserialization in `serde`/`serde_json` works by first buffering the entire JSON payload into an internal recursive `Content` representation, trying each variant against it. For arbitrarily-nested JSON arrays/objects, this buffering recurses once per nesting level with no depth limit, exactly the bug class described in the external report for Go's `gob` decoder (stack exhaustion on deeply nested input during `Decode`).

### Finding Description
`chain/jsonrpc-primitives/src/message.rs` defines: [1](#0-0) 
`Message` is `#[serde(untagged)]` and one of its variants is `Batch(Vec<Message>)`, i.e., the type is directly recursive. It is wrapped again by `WireMessage`, also `#[serde(untagged)]`: [2](#0-1) 

Every inbound JSON-RPC request reaches this deserializer via `from_slice`/`from_str`, called directly from the RPC entrypoint before any method-specific validation: [3](#0-2) 

Because the enum is untagged, `serde` cannot know ahead of time which variant applies, so it first deserializes the *entire* payload into a generic, recursively-structured buffer (`serde::__private::de::Content` internally) before attempting each candidate variant (`Request`, `Response`, `Notification`, `Batch(Vec<Message>)`, `UnmatchedSub(Value)`). This buffering step recurses once per level of JSON array/object nesting with no depth limit, independent of whether the payload is semantically a valid RPC batch. A payload consisting of thousands of nested arrays (e.g., `"[[[[[...]]]]]"`) is small in bytes but drives the parser to a proportional recursion depth.

Per `chain/jsonrpc/RPC_ARCHITECTURE.md`, the only guard on the request path is a flat request body size limit (10MB default) applied by middleware before parsing — there is no JSON nesting-depth limit: [4](#0-3) 

A stack overflow triggered inside a worker thread in Rust is not a catchable panic; the language runtime's overflow guard page handler prints a diagnostic and calls `abort()`, terminating the entire process — not just the offending task/thread. This means a single unauthenticated HTTP POST to the JSON-RPC endpoint (`/`) can crash the whole `neard` process, including validator and RPC-serving nodes, satisfying the "transaction/RPC-triggered halt" impact category.

This is functionally analogous to the reported `encoding/gob` `Decoder.Decode` stack exhaustion (CVE-2024-34156): both are cases of a general-purpose deserializer recursing per nesting level of attacker-supplied structured data with no depth cap, callable directly by an untrusted remote caller.

Note: I was not able to fully verify within available tool access whether Axum/Tokio's specific worker-thread stack size or any global `serde_json` recursion limit configuration mitigates this in the exact deployed configuration — I found no code setting a JSON depth limit or non-default recursion limit anywhere in `chain/jsonrpc/src/lib.rs` or `chain/jsonrpc-primitives`, but I could not exhaustively rule out a `serde_json` version-level default recursion guard given index limitations on this file's exact dependency configuration.

### Impact Explanation
A successful stack-exhaustion payload aborts the entire node process. For a validator, this is a transaction/RPC-triggered halt of consensus participation; for a plain RPC node, it is a full denial of service. Because JSON-RPC is exposed to any caller by design (it's the primary public API), the blast radius is every node with RPC enabled, and the attack requires no privileges, no valid account, and no funds — a few KB of adversarial JSON is sufficient.

### Likelihood Explanation
High reachability: the vulnerable parser sits at the very front of the JSON-RPC request pipeline (`rpc_handler()` → `Message::from_slice`), before any authentication, method dispatch, or semantic validation occurs. The only precondition is network access to the RPC port, which is intentionally public on most deployments. Constructing the payload requires no cryptographic material and is trivially automatable.

### Recommendation
- Impose an explicit maximum JSON nesting depth check (or reject deeply nested arrays/objects) before/while deserializing `WireMessage`/`Message`, independent of the flat byte-size limit.
- Consider replacing the untagged `Message`/`Batch` recursive enum with a non-recursive, iteratively-parsed representation (parse the top-level JSON once into `serde_json::Value` with a bounded custom depth-tracking visitor, then dispatch variants explicitly instead of relying on `#[serde(untagged)]`’s automatic buffering).
- Run the JSON-RPC request-parsing task on a thread configured with `std::thread::Builder::stack_size` isolation and/or `catch_unwind`-safe boundaries so a worst-case parse failure degrades to a single request/connection failure rather than aborting the whole process (this does not fix the root cause but limits blast radius).
- Add a regression test that submits a JSON body with deep array/object nesting (e.g., 100,000 levels) well under the 10MB body cap and assert the server returns a parse error rather than crashing.

### Proof of Concept
1. Start a node with the JSON-RPC server enabled (default `neard` configuration).
2. Send an HTTP POST to `/` with `Content-Type: application/json` and a body consisting of `N` repetitions of `[` followed by `N` repetitions of `]` (no other content), where `N` is large enough to exceed the runtime's stack size (empirically on the order of tens of thousands to a few hundred thousand nested arrays, well under the 10MB body-size limit):
   ```
   POST / HTTP/1.1
   Host: <node-rpc-host>
   Content-Type: application/json
   Content-Length: <len>

   [[[[[[[[[[ ... repeated N times ... ]]]]]]]]]]
   ```
3. `chain/jsonrpc/RPC_ARCHITECTURE.md`'s documented pipeline routes this body straight to `rpc_handler()` → `JsonRpcHandler::process()` → `near_jsonrpc_primitives::message::from_slice(&bytes)` (`chain/jsonrpc-primitives/src/message.rs:262-264`), which invokes `serde_json::de::from_slice::<WireMessage>`.
4. Because `WireMessage`/`Message` are `#[serde(untagged)]` (`message.rs:158-181`, `240-246`), `serde_json` recurses once per `[` while buffering the payload for variant matching.
5. Observe the node process aborts with a stack-overflow diagnostic (`thread '<name>' has overflowed its stack`), taking down the entire `neard` process rather than just failing the single request.

pub enum Message {
    /// An RPC request.
    Request(Request),
    /// A response to a Request.
    Response(Response),
    /// A notification.
    Notification(Notification),
    /// A batch of more requests or responses.
    ///
    /// The protocol allows bundling multiple requests, notifications or responses to a single
    /// message.
    ///
    /// This variant has no direct constructor and is expected to be constructed manually.
    Batch(Vec<Message>),
    /// An unmatched sub entry in a `Batch`.
    ///
    /// When there's a `Batch` and an element doesn't conform to the JSONRPC 2.0 format, that one
    /// is represented by this. This is never produced as a top-level value when parsing, the
    /// `Err(Broken::Unmatched)` is used instead. It is not possible to serialize.
    #[serde(skip_serializing)]

}
