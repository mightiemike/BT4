Found a concrete analog in the failed-outbound revert path: `handleFailedOutbound` can return an error path that leaves the outbound record permanently stuck at `Status_OBSERVED` — a state the code doesn't otherwise expect to persist — because `Amount` parse failure happens *after* `UpdateOutbound` already committed `OutboundStatus = Status_OBSERVED` in the caller, and the error return from `handleFailedOutbound`/`FinalizeOutbound` is only recorded as a `RevertError` string with no state or funds correction, exactly mirroring the reported bug class of "accepted terminal/void outcome whose accounting side effects are never applied."

### Title
Failed-outbound finalization can permanently strand bridged funds in `OBSERVED` state when `outbound.Amount` fails to parse - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`VoteOutbound` (`x/uexecutor/keeper/msg_vote_outbound.go`) sets `outbound.OutboundStatus = Status_OBSERVED` and persists it via `UpdateOutbound` *before* calling `FinalizeOutbound`, which for `success=false` observations delegates to `handleFailedOutbound` to re-mint the bridged PRC20 back to the user. If `handleFailedOutbound` fails to parse `outbound.Amount` (`amount.SetString(outbound.Amount, 10)`), it returns a bare Go error without writing any further outbound state. [1](#0-0) 

### Finding Description
The `VoteOutbound` message handler updates the on-chain outbound record to `OBSERVED` and removes it from `PendingOutbounds` unconditionally, then calls `FinalizeOutbound`: [2](#0-1) 

`FinalizeOutbound` dispatches to `handleFailedOutbound` for failed observations: [3](#0-2) 

Inside `handleFailedOutbound`, for `FUNDS`/`GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` outbound types, `outbound.Amount` is parsed as a big int. If parsing fails, the function returns immediately:
```go
amount, ok := amount.SetString(outbound.Amount, 10)
if !ok {
    return fmt.Errorf("invalid amount: %s", outbound.Amount)
}
``` [4](#0-3) 

This is the only early-return path in `handleFailedOutbound`/`handleSuccessfulOutbound` that does **not** call `k.AbortOutbound` (which would at least mark the outbound `ABORTED` for manual operator intervention) and does **not** call `k.UpdateOutbound` to reflect `REVERTED`. Compare this to the sibling failure path a few lines later, where a failed re-mint EVM call explicitly calls `AbortOutbound`: [5](#0-4) 

Back in `VoteOutbound`, the error from `FinalizeOutbound` is only stringified into `UniversalTx.RevertError`; no outbound status transition, no re-mint, and no `ABORTED` marker is ever recorded: [6](#0-5) 

The net result: the `OutboundTx` record is permanently left with `outbound_status = OBSERVED` and `observed_tx.success = false`, a combination the rest of the codebase's derived-status model (per `x/uexecutor/README.md`) treats as terminal/consistent but which here reflects an outbound that failed on the destination chain and whose bridged collateral was never re-minted back to the user. There is no automatic or admin re-entry path analogous to `RevertStuckInbound` for this specific stuck-outbound shape (that admin path only targets `EXPIRED` ballots pre-UTX-creation, not `OBSERVED`-with-failed-amount outbounds). [7](#0-6) 

### Impact Explanation
When this path triggers, the bridged funds represented by the outbound (originally minted as PRC20 on Push Chain and locked/burned for the outbound leg) are neither refunded to the user nor flagged `ABORTED` for operator remediation. The outbound sits at `OBSERVED`/failed indefinitely with no code path re-processing it (once removed from `PendingOutbounds`, nothing revisits it), a permanent-freezing outcome for the user's collateral consistent with the "Oracle void outcome leaves ... payouts unset, locking collateral" bug class.

### Likelihood Explanation
Triggering requires `outbound.Amount` to be an unparsable decimal string at the time of failed-outbound finalization. `OutboundTx.Amount` is set at outbound-creation time from validated inbound/execution data under normal conditions, so this specific string-corruption trigger is not obviously reachable by an ordinary unprivileged external attacker through the standard deposit/payload submission path — I could not confirm within the available context a concrete attacker-controlled input that forces `Amount` into a non-numeric string at outbound-creation time (`x/uexecutor/keeper/create_outbound.go`, which I did not fully review). Because I cannot verify a concrete unprivileged trigger for the malformed-`Amount` precondition, I cannot confirm this meets the "unprivileged external attacker" root-cause requirement with certainty.

### Recommendation
In `handleFailedOutbound` (`x/uexecutor/keeper/outbound.go`), route the `amount.SetString` failure (and any other early-return error in that function) through `k.AbortOutbound` instead of a bare `return fmt.Errorf(...)`, so the outbound is marked `ABORTED` with a reason and flagged for manual/admin remediation rather than silently left in a stale `OBSERVED` state with no further code path touching it. Additionally, consider adding an admin escape hatch (mirroring `RevertStuckInbound`) that can force-transition `OBSERVED`+`ABORTED`/stuck outbounds back to a refundable state.

### Proof of Concept
I was not able to construct a concrete, verified proof-of-concept because I could not confirm (within available context/time) a code path that lets an unprivileged external attacker cause `OutboundTx.Amount` to be a non-numeric string reaching `handleFailedOutbound`. This finding should be treated as **conditional** — valid as a defense-in-depth/robustness gap in the finalization state machine, but not confirmed as independently attacker-triggerable without further review of `x/uexecutor/keeper/create_outbound.go` and all `OutboundTx` construction sites.

func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

		return nil

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

}

// RevertStuckInbound creates an INBOUND_REVERT outbound for an inbound whose
// ballot has expired without finalizing. The revert outbound enters the normal
// PendingOutbounds flow; UVs sign it via TSS and broadcast it to the source
// chain, refunding the user.
//
// Strict precondition: the ballot for the supplied inbound must be in EXPIRED
// state. Admin must run MsgRecomputeBallotQuorum first to drive a stuck ballot
// to EXPIRED if it isn't already (recompute auto-expires when no eligible
// voters remain).
//
// Returns the new UTX ID and revert outbound ID for telemetry.
func (k Keeper) RevertStuckInbound(ctx context.Context, inbound types.Inbound) (utxId, outboundId string, err error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Same canonical form as the vote path, so the admin-supplied payload
	// derives the same ballot key / UTX key the votes did.
	inbound.Canonicalize()

	if vErr := inbound.ValidateBasic(); vErr != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, vErr.Error())
	}

	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, fmt.Sprintf("failed to derive ballot key: %s", err))
	}

	ballot, err := k.uvalidatorKeeper.GetBallot(ctx, ballotKey)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrNotFound, fmt.Sprintf("ballot for inbound not found (key=%s): %s", ballotKey, err))
	}

	if ballot.Status != uvalidatortypes.BallotStatus_BALLOT_STATUS_EXPIRED {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest,
			fmt.Sprintf("ballot %s status is %s; admin revert requires EXPIRED (use MsgRecomputeBallotQuorum to drive a stuck pending ballot to EXPIRED)",
				ballotKey, ballot.Status.String()))
	}
