### Title
Missing `supportUnfreezeDelay` Guard in `FreezeBalanceProcessor` Allows Legacy V1 Freeze via TVM Opcode After Migration to Resource Model V2, Corrupting Total Weight Accounting - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
The reported bug class is an incomplete override of a base contract's asset-tracking logic (`mint`/`withdraw` not updating `_totalAssets`), causing accounting divergence between individual balances and pool-wide totals. The closest reachable analog in java-tron is the freeze-balance (V1) native contract implementation used by the TVM, which omits a validation guard and an accounting rule that its sibling actuator enforces, letting stale V1 resource-freezing logic run and desynchronize network-wide resource weight totals after the chain has migrated to the new resource model (V2/"unfreeze delay").

### Finding Description
`FreezeBalanceActuator` (the regular broadcast-transaction actuator for `FreezeBalanceContract`, i.e., legacy V1 freezing) explicitly disables itself once the network has switched to the new resource model: [1](#0-0) 

It also computes the change to the network-wide total weight using an "increment" value that accounts for `allowNewReward()` semantics: [2](#0-1) 

However, `FreezeBalanceProcessor`, the native-contract equivalent invoked from the TVM (reachable from `Program.java` when a smart contract calls the freeze-balance opcode), reimplements the same V1 freezing logic but:
1. Its `validate()` method has no equivalent check against `dynamicStore.supportUnfreezeDelay()`, so it never rejects the operation once the chain has migrated to V2: [3](#0-2) 
2. Its total-weight adjustment unconditionally adds the raw `frozenBalance / TRX_PRECISION`, ignoring the `allowNewReward()`-based increment logic used by the actuator: [4](#0-3) 

This is structurally the same class of bug as the ERC-4626 report: a code path that reuses/duplicates state-mutating logic from a "base" implementation but incompletely mirrors the accounting/guard rules of the canonical path, producing inconsistent global totals (`_totalAssets` in the report; `TotalNetWeight`/`TotalEnergyWeight` here) relative to what individual account state implies.

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight` are the divisors used network-wide to compute bandwidth/energy allotment per unit of frozen TRX and to distribute staking rewards. If a smart contract can still trigger legacy V1 freezing through the TVM opcode after `supportUnfreezeDelay()` (V2) is enabled, and/or if the weight delta added doesn't match the actuator's semantics, the network's aggregate resource weight state diverges from what governance/consensus assumes for the migrated model. This directly affects resource accounting and reward distribution across all accounts, which is an accounting-corruption impact.

### Likelihood Explanation
The precompiled/native-contract freeze code is reachable from any contract call executing the corresponding TVM opcode (per `Program.java`), i.e., from ordinary broadcast transactions that trigger contract execution — no privileged actor or leaked key is required, satisfying the requirement of a bug reachable from "a contract call."

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` rejection in `FreezeBalanceProcessor.validate()` as in `FreezeBalanceActuator.validate()`, and align `FreezeBalanceProcessor.execute()`'s total-weight adjustment with the increment-based logic gated by `dynamicStore.allowNewReward()` used in `FreezeBalanceActuator`/`addTotalWeight`.

### Proof of Concept
Not independently executed; based on static comparison of `FreezeBalanceActuator.validate()` (guarded) versus `FreezeBalanceProcessor.validate()`/`execute()` (unguarded, differing weight math), both implementing the same `FreezeBalanceContract`/`FreezeBalanceParam` semantics for V1 freezing, reachable via the TVM opcode path referenced in `Program.java`. I was unable to fully trace the opcode dispatch/gating logic inside `PrecompiledContracts.java`/`Program.java` (only one `supportUnfreezeDelay` reference was found there for a different call) in the remaining investigation budget, so it is not fully confirmed whether an additional external gate exists at the opcode-dispatch layer that prevents this call once V2 is active.

  private void addTotalWeight(ResourceCode resourceCode, DynamicPropertiesStore dynamicStore,
                              long frozenBalance, long increment) {
    long weight = dynamicStore.allowNewReward() ? increment : frozenBalance / TRX_PRECISION;
    switch (resourceCode) {
      case BANDWIDTH:
        dynamicStore.addTotalNetWeight(weight);
        break;
      case ENERGY:
        dynamicStore.addTotalEnergyWeight(weight);
        break;
      case TRON_POWER:
        dynamicStore.addTotalTronPowerWeight(weight);
        break;
      default:
        logger.debug("Resource Code Error.");
    }
  }

  public void validate(FreezeBalanceParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(
            "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
    }

    // validate for delegating resource
    byte[] receiverAddress = param.getReceiverAddress();
    if (!FastByteComparisons.isEqual(ownerAddress, receiverAddress)) {
      param.setDelegating(true);

      // check if receiver account exists. if not, then create a new account
      AccountCapsule receiverCapsule = repo.getAccount(receiverAddress);
      if (receiverCapsule == null) {
        receiverCapsule = repo.createNormalAccount(receiverAddress);
      }

      // forbid delegating resource to contract account
      if (receiverCapsule.getType() == Protocol.AccountType.Contract) {
        throw new ContractValidateException(
            "Do not allow delegate resources to contract addresses");
      }
    }
  }
