## Finding

### Title
Unsigned-subtraction difficulty-adjustment miscalculation causes light-client proof journal to diverge from Bitcoin consensus - (File: `crates/bitcoin-da/src/verifier.rs`)

### Summary
`calculate_new_difficulty` computes the actual epoch timespan as an unsigned `u32` subtraction, `last_timestamp - epoch_start_time` [1](#0-0) , whereas real Bitcoin consensus (and Bitcoin Core) computes this quantity as a **signed** difference before clamping it into `[expected/4, expected*4]`. If the last block's timestamp of a 2016-block epoch is smaller than the epoch's first block timestamp, the `u32` subtraction produces either a debug-mode panic or, in a release-mode guest build (no `overflow-checks` configuration found anywhere in the workspace, so the default `cargo build --release` semantics — silent wraparound — apply [2](#0-1) ), a wrapped value close to `u32::MAX`. That wrapped value is then clamped by the *upper* bound (`actual_timespan > expected_epoch_timespan * 4`) instead of the correct *lower* bound, producing a difficulty target that does not match the target a real Bitcoin node (or the reference difficulty-adjustment algorithm) would compute for the same header sequence.

### Finding Description
`verify_header_chain_mainnet`, `verify_header_chain_testnet4`, and `verify_header_chain_signet` all call `calculate_new_difficulty` on the last block of every 2016-block epoch, passing `epoch_start_time` (timestamp of the epoch's first block) and `last_timestamp` (timestamp of the current, last block of the epoch) [3](#0-2) :

```
let mut actual_timespan = last_timestamp - epoch_start_time;
if actual_timespan < expected_epoch_timespan / 4 {
    actual_timespan = expected_epoch_timespan / 4;
} else if actual_timespan > expected_epoch_timespan * 4 {
    actual_timespan = expected_epoch_timespan * 4;
}
``` [4](#0-3) 

Bitcoin's timestamp consensus rule only requires that a block's timestamp exceed the **median** of the previous 11 blocks' timestamps — enforced here in `verify_timestamp` [5](#0-4)  — not that timestamps increase monotonically block-to-block, nor that the last block of an epoch have a timestamp greater than the epoch's first block. Real Bitcoin Core computes the analogous quantity as a signed `int64_t` difference, so a negative actual timespan is handled correctly by clamping to the lower bound (`expected/4`). This code, by using unsigned `u32` subtraction, cannot represent a negative timespan: it wraps to a huge value near `u32::MAX`, which is then clamped to the *opposite*, wrong bound (`expected*4` instead of `expected/4`), yielding an incorrect `current_target_bits`/difficulty in the `LatestDaState` output.

This directly parallels the JalaPair bug class: an arithmetic operation whose author assumed a particular numeric domain (signed/wrapping semantics in the old code, non-overflowing conditions here) breaks once the language/runtime's default arithmetic behavior differs from what is assumed, corrupting a value that downstream logic depends on.

### Impact Explanation
The output of `verify_header_chain_*` (specifically `current_target_bits` inside `LatestDaState`) feeds directly into the light-client proof's DA header-chain verification result, which is exactly the "root/target computed natively (real Bitcoin) versus computed in the guest" binding this scan is meant to catch. A wrong `current_target_bits` value means the light-client circuit's journal about the validity/parameters of the Bitcoin chain diverges from what real Bitcoin nodes computed for the same block range. Any consumer trusting this proof (e.g., Citrea's bridge/light-client state) could accept a Bitcoin chain state whose recorded difficulty does not match the real chain, or reject valid future headers because the derived target no longer matches what real miners produced under the correct target — a false/incorrect DA-integrity result. In debug/overflow-checked builds it instead panics, which is a denial-of-service outcome that is explicitly out of scope for this report.

### Likelihood Explanation
This requires the last block of a 2016-block (~2-week) epoch to have a timestamp earlier than the epoch's first block. Over real Bitcoin's actual history this has apparently never occurred, since average timestamps track real elapsed time and multi-day monotonic decreases across an entire epoch are not observed on mainnet. The protocol itself does not forbid it (only median-of-11 monotonicity is enforced), so it remains a theoretical edge condition rather than a currently exploitable path — similar in nature (rare, far-future/edge-case, but a genuine spec mismatch) to the original JalaPair finding, which was judged Medium precisely because of this kind of "low probability, but breaks correctness/DoS when it hits" profile.

### Recommendation
Compute `actual_timespan` using a signed type (e.g. `i64`) mirroring Bitcoin Core's `nActualTimespan` calculation, clamp using signed comparisons against `expected_epoch_timespan/4` and `expected_epoch_timespan*4`, and only then cast to the unsigned type used for the `U256` multiplication, ensuring the wrap-around/underflow condition can never occur and that the clamping direction matches Bitcoin consensus regardless of whether `last_timestamp` is smaller than `epoch_start_time`.

### Proof of Concept
Conceptually:
1. Construct (or observe) a chain segment where the epoch's first block (`epoch_block == 0`) has timestamp `T0`, and the epoch's last block (`epoch_block == BLOCKS_PER_EPOCH - 1`) has timestamp `T1 < T0` — permitted because only the median-of-11 rule constrains individual block timestamps, not epoch-start-vs-epoch-end ordering.
2. Feed this header sequence into `verify_header_chain_mainnet` (or testnet4/signet).
3. `calculate_new_difficulty(epoch_start_time = T0, last_timestamp = T1, ...)` executes `T1 - T0` as `u32` subtraction.
4. In a release-profile guest binary (no `overflow-checks = true` found in any workspace `Cargo.toml`), this silently wraps to `u32::MAX - (T0 - T1) + 1`, a value greater than `expected_epoch_timespan * 4`, so `actual_timespan` gets clamped to `expected_epoch_timespan * 4` — the opposite of the correct clamp to `expected_epoch_timespan / 4` that a signed calculation would produce.
5. The resulting `current_target_bits` written into `LatestDaState` therefore differs from the target Bitcoin Core would derive for the identical header sequence, causing the light-client proof's recorded chain parameters to diverge from the real chain.
