### Title
Epoch-boundary burn-window collapse lets a minority miner "flash-spike" a commit to win sortition without median damping - (File: stackslib/src/burnchains/burnchain.rs)

### Summary
`BurnchainStateTransition::from_block_ops` decides whether a sortition's burn distribution is computed over the full `MINING_COMMITMENT_WINDOW` (with min/median smoothing) or collapses to a single-block window. For up to `mining_commitment_window()` blocks after every Stacks epoch upgrade, the collapse condition is met, disabling the anti-spike median damping that the burn-distribution algorithm is designed to provide. This lets a single miner (no majority hashpower required) inflate a block-commit's burn for one sortition to disproportionately win it, then immediately revert to normal (low) burns — an arbitrage pattern structurally identical to the reported "deposit large, withdraw immediately, repeat" LP-rewards exploit, but here targeting sortition-winner selection instead of LP rewards.

### Finding Description
`BurnSamplePoint::make_min_median_distribution` computes each candidate's effective burn as `min(last_burn_amount, median_burn_over_window)` [1](#0-0) , specifically to prevent a miner from spiking a single block's burn to guarantee winning sortition and then dropping back down. This smoothing is only applied when the caller supplies a full multi-block `windowed_block_commits` window; the function "does not consider which window is active; it merely deduces it by inspecting the length" of the given argument [2](#0-1) .

The caller, `BurnchainStateTransition::from_block_ops`, decides the window length via:

```
let epoch_id = ...;                 // epoch at block_height + 1
let window_start_epoch_id = ...;    // epoch at block_height - mining_commitment_window()
if !prepare_phase && !after_sunset && (epoch_id < Epoch30 || window_start_epoch_id == epoch_id) {
    // full window built, smoothing applies
} else {
    // window collapses to length 1 (only the current block's own commits)
}
``` [3](#0-2) 

Whenever an epoch upgrade (e.g. Epoch 3.0→4.0, or any future epoch boundary) occurred within the last `mining_commitment_window()` blocks, `window_start_epoch_id != epoch_id`, so the branch falls to the `else` case and the window is truncated to just the current block's own commits — i.e., no median damping at all, `burns == last_burn_amount` [4](#0-3) .

Critically, because each sortition height in this post-boundary span independently re-checks `window_start_epoch_id == epoch_id`, every one of the `mining_commitment_window()` blocks following the epoch start also collapses its own window to 1 (since their lookback still reaches into the pre-boundary epoch). This means a burn spike made at the very first post-boundary block is never incorporated into any subsequent median calculation during the entire collapsed span — the spike is "deposited" with full weight for its own sortition and then structurally excluded from ever being "charged against" the miner in future windows, exactly mirroring the deposit-then-immediately-withdraw arbitrage in the referenced report.

The existing in-repo comment only documents a different, narrower intentional exception (the mod-0/prepare-phase 1-block window) [5](#0-4) ; it does not address or justify the epoch-boundary collapse, and the repository's own test suite treats windowing correctness across an epoch boundary as a real risk worth guarding against, explicitly noting "a windowing bug at the boundary surfaces as a failure mode" [6](#0-5) .

### Impact Explanation
This breaks the intended equality that the sortition winner must be selected according to the median-damped burn-weight function (`burns = min(last_burn, median_over_window)`); during the post-epoch-upgrade window it instead uses the raw, undamped `last_burn_amount`. This is a minority-triggerable divergence in the sortition/burn-weight computation: any single miner can unilaterally increase their probability of winning a specific sortition during this window without being subject to the anti-spike smoothing every other sortition enjoys, and without that spike persisting into later medians. This falls under "a minority-triggerable sortition/VRF/static-validation divergence" (High), since it distorts the fairness guarantee of the burn-weighted lottery for legitimate low-burn miners competing during that window, and is repeatable at every future epoch boundary.

### Likelihood Explanation
Likelihood is moderate-to-high in the long run: epoch boundaries are rare but deterministic, scheduled, and public events (visible in `epochs.toml`/`StacksEpochId` config), so any miner can pre-plan a burn spike to land in the exact multi-block window following a known future epoch transition. No majority hashpower, insider access, or other privileged party is required — only sufficient capital for one (or a few) inflated commits, similar to a flash-loan-funded spike in the original report.

### Recommendation
Do not silently collapse the mining-commitment window to length 1 whenever the lookback crosses an epoch boundary. Instead, either (a) cap the window to only the sub-range of blocks that share the *current* epoch (partial-width windowing) rather than dropping to width 1, or (b) explicitly document and formally reason why width-1 windowing at epoch boundaries preserves the same anti-spike guarantee as the standard window, and add a consensus test that exercises adversarial (asymmetric, spiking) burn amounts specifically at the transition boundary — not just the smooth/constant-fee scenario used in the current `epoch_4_0_burn_distribution_chains_across_boundary` test.

### Proof of Concept
1. A miner observes the scheduled start height of an upcoming Stacks epoch (e.g. Epoch 4.0), which is public configuration.
2. At the first sortition of the new epoch, `window_start_epoch_id` (computed from `block_height - mining_commitment_window()`) resolves to the prior epoch, causing `window_start_epoch_id != epoch_id`, per `stackslib/src/burnchains/burnchain.rs:218-243`.
3. The window therefore collapses to length 1: `make_min_median_distribution` is invoked with a single-entry `block_commits` vector, so `burns = last_burn_amount` with no median damping (`stackslib/src/chainstate/burn/distribution.rs:149-189`).
4. The miner submits one block-commit with an inflated `burn_fee` for this sortition only, winning (or substantially increasing odds of winning) that sortition disproportionately to their sustained commitment level.
5. For the following `mining_commitment_window()-1` blocks, the same collapse condition still holds (their own lookback still reaches into the old epoch), so the spike commit is never folded into any median computation — the miner reverts to minimal burns immediately with no smoothing penalty.
6. This can be repeated at every subsequent epoch upgrade, each time re-acquiring an undamped one-block sortition advantage that the burn-distribution's min/median mechanism was specifically designed to prevent.
