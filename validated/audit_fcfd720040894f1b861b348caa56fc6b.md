### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash verification, letting replay-verify tooling accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by replay/verification tooling to authenticate a freshly-executed `TransactionOutput` against a trusted `TransactionInfo`, validates status, gas used, write-set hash, and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The code itself contains a `TODO` acknowledging this gap. Because this is the authenticated comparison used by `db-tool replay-verify` (`storage/db-tool/src/replay_on_archive.rs`) and `aptos-debugger`, a state root divergence in the checkpoint/JMT-derived roots can pass as "verified" even though the locally recomputed state does not match the archived/authenticated ledger state.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  checks four properties between a computed `TransactionOutput` and the trusted `TransactionInfo` read from storage/backup: status, gas used, write-set hash (`state_change_hash`), and event root hash. The function's tail contains an explicit acknowledgment of missing checks: [2](#0-1) 

This comment states that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

`TransactionInfo` (both `V0` and `V1`) carries these checkpoint hashes as first-class, hashed fields that are part of the accumulator leaf and therefore part of the authenticated ledger commitment: `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` [3](#0-2) . These hashes are produced from the Sparse-Merkle/Jellyfish-Merkle state summaries in `DoStateCheckpoint::run` and `compute_position_checkpoint`, e.g. the position-state checkpoint hash is derived from a completely independent state tree (native "position" state) that is extended and merklized incrementally [4](#0-3) .

The only actual call site that performs this "authenticated" verification against archived backup data is `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes transactions and calls `ensure_match_transaction_info` per transaction to decide whether replay is faithful to the trusted `TransactionInfo` list pulled from backup/archive: [5](#0-4) . Since the checkpoint hash fields are skipped, this comparator can return `Ok(())` even when the replayed node computed a different `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` than what is embedded in the trusted `TransactionInfo`.

This is a direct integrity analog to the external report's core issue: a value is computed (`previewDeposit`/`previewMint` in the seed report; here, the locally-computed checkpoint root) but never actually checked against the value the caller is relying on (user's slippage bound in the seed report; here, the archived/authenticated `TransactionInfo` checkpoint hash) before the operation is treated as validated/successful.

### Impact Explanation
Replay-verify (`db-tool replay-verify`) and `aptos-debugger` are the trust anchors used to detect silent state divergence between a node's local VM/state-checkpoint computation and the historically committed, signature-authenticated ledger (backed by validator-signed `LedgerInfo`s over the transaction accumulator, whose leaves are `TransactionInfo` hashes including these checkpoint fields). If a bug in state-checkpoint computation, hot-state tracking, or the native "position" state tree (a newer, less-battle-tested subsystem, as seen by the `compute_trading_native_state_roots` feature gate) produces a wrong root, `ensure_match_transaction_info` will not catch it — it only compares write-set hash and event root hash, not the state-checkpoint-derived roots. This means:
- A hard-fork-class state divergence (e.g., a JMT/position-state bug) could go undetected by the primary replay-verification tool used to audit archive nodes/history.
- Downstream consumers (auditors, chain analysis, disaster recovery) relying on `replay_on_archive`'s pass/fail signal would receive a false "verified" result while the authenticated state root is actually wrong.

This satisfies the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Authenticated API or state-view output bound to the wrong version, object, or proof context" impact categories, since the checkpoint hash is exactly the value that binds a transaction's committed state to a specific ledger version/root.

### Likelihood Explanation
The gap is real and acknowledged in the code (not speculative) — the comment explicitly names the exact scenario ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"). It requires an independent triggering bug (e.g., in state-checkpoint or position-state computation) to actually produce a wrong root for this comparator gap to matter in practice; by itself, `ensure_match_transaction_info` is a validation/detection gap rather than a primary state-corruption bug. It is most exploitable/relevant against the newer `position_state_checkpoint_hash` path (guarded by `compute_trading_native_state_roots`), which is explicitly called out as not yet safe to enable without fixing this comparator.

### Recommendation
Extend `ensure_match_transaction_info` to also assert `self`-derived checkpoint hashes (state, hot-state, and position-state, when present/enabled) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, mirroring the existing `ensure!` pattern used for `write_set_hash` and `event_root_hash`. Until this is done, `COMPUTE_TRADING_NATIVE_STATE_ROOTS` should remain disabled (as the comment already recommends), and `replay_on_archive`/`aptos-debugger` results should not be treated as a full state-root authentication guarantee.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
