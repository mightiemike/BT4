## Title
Stale market-level index cache not invalidated by vault `socialize-debt` within the same `liquidate-multi` transaction - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` (and its mainnet twin `v0-4-market.clar`) maintains a private, transaction-scoped index cache `index-cache-` keyed by `{ timestamp: stacks-block-time, aid }`, populated the first time `accrue-and-cache` is called for a given asset in a block [1](#0-0) . Because the key uses `stacks-block-time` rather than a per-call token, every subsequent lookup for that asset within the *same transaction* returns the first cached `{index, lindex}` pair, even if the underlying vault's `lindex`/`index` state variables are mutated later in the same transaction by `socialize-debt` [2](#0-1) . `liquidate-multi` processes several borrower positions atomically in one transaction via `map`, and `liquidate` triggers bad-debt socialization (`vault-socialize-debt`) whenever a borrower's collateral is fully drained [3](#0-2) . If an earlier position in the same batch has already caused `accrue-and-cache` to memoize the pre-socialization `lindex`/`index` for an asset, a later position in the same batch that shares that asset will be valued and liquidated using the stale, pre-socialization index instead of the vault's now-updated real index.

### Finding Description
1. `accrue-and-cache(aid)` checks `index-cache-` map with key `{timestamp: stacks-block-time, aid}`. On a cache hit it returns the cached value without re-querying the vault [1](#0-0) .
2. `liquidate()` calls `accrue-user-debts`/`accrue-user-collateral`, which call `accrue-and-cache` for every debt/ztoken-collateral asset in the borrower's position, and this cached value backs the notional valuation used for LTV/health calculations [4](#0-3) .
3. When a borrower's collateral is fully seized during liquidation, `liquidate()` socializes the remaining bad debt via `fold socialize-debt-asset` over the debt list, which calls into the vault's `socialize-debt` function [3](#0-2) .
4. Inside the vault, `socialize-debt` directly mutates `lindex`, `principal-scaled`, `total-borrowed`, and `assets` with `var-set`, bypassing the market's `accrue`/`accrue-and-cache` flow entirely [2](#0-1) . This mutation does not touch or invalidate `market.clar`'s `index-cache-` map.
5. `liquidate-multi` executes `call-liquidate` over a list of positions via `map` in a single atomic transaction, with no batch-level price/index refresh between positions ("price-feeds not supported in batch") [5](#0-4) .
6. Consequence: if position N triggers `socialize-debt` for asset X (changing the vault's real `lindex`), and position N+1 in the same batch also involves asset X, the market's `index-cache-` for asset X (primed earlier in the transaction, before the socialization) is still returned for position N+1's collateral/debt valuation, since the cache key does not change within the block. This produces a mismatch between the actual on-chain vault index and what the market uses to compute collateral/debt USD values and liquidation math for the later position.

### Impact Explanation
Health checks, `current-ltv`, liquidation-amount calculations (`process-debt-asset`, `process-collateral-asset`, `calc-final-liquidation-amounts`) and the size of `debt-to-repay`/`coll-final` for the later position in the batch are all computed from the notional valuation that depends on the (now stale) cached index [6](#0-5) . This can under- or over-value that borrower's zToken-denominated debt/collateral relative to the vault's true post-socialization index, causing the liquidator to seize an incorrect (potentially larger) amount of collateral than the true accounted debt/collateral value, or a position that should not be liquidatable being pushed past the liquidation threshold (or vice versa) purely due to stale index math — a temporary/permanent misallocation of user collateral/debt value within a single-batch liquidation. This lands in the "temporary freezing of funds" / theft-adjacent impact class described by the rules, since a borrower's collateral could be seized based on an incorrect valuation baseline in the same transaction.

### Likelihood Explanation
This requires: (a) a `liquidate-multi` (or otherwise a single transaction touching multiple positions sharing an asset) batch where one position fully wipes out collateral and triggers bad-debt socialization for an asset, and (b) another position in the same batch/transaction involving that same asset processed after the socialization. `liquidate-multi` is specifically built to batch multiple borrower liquidations "atomically" in one call [5](#0-4) , and bad-debt socialization is a documented, expected occurrence during liquidation of undercollateralized positions, so the ordering condition is plausible during volatile market conditions, e.g. an attacker/liquidator crafting a `liquidate-multi` batch that intentionally orders a bad-debt-triggering liquidation before another shared-asset liquidation to exploit the stale index. Note: I was not able to fully trace whether `socialize-debt`'s index change actually diverges the *same-block* index in a way that materially affects notional values (the note "cache invalidates each block" documentation strongly implies same-block reuse is intentional for gas savings, and the delta from socialize-debt within one block may be small), so likelihood should be treated as uncertain pending deeper analysis of `next-index`/`next-liquidity-index` and the magnitude of `socialize-debt`'s index jump.

### Recommendation
Either (a) invalidate/refresh the `index-cache-` entry for an asset immediately whenever `socialize-debt` (or any other function that directly `var-set`s the vault's `lindex`/`index`) is invoked from within the same transaction, or (b) route `socialize-debt`'s index update through the same `accrue`/cache-population path used elsewhere so the market's cache always reflects the vault's latest true state, or (c) disallow/serialize `liquidate-multi` batches so that any bad-debt socialization for an asset forces re-accrual (cache eviction) of that asset before subsequent positions using it are processed within the same batch.

### Proof of Concept
Conceptual (not verified end-to-end due to reasoning-budget/tool constraints):
1. Set up two borrowers, Borrower A and Borrower B, both with debt in asset X (e.g. USDC) and collateral in different assets, where asset X is a ztoken-tracked debt/collateral asset relying on `lindex`/`index` caching.
2. Call `market.borrow`/other calls so that asset X's index is cached in `index-cache-` for the current block (e.g. via any earlier operation in the same transaction, or the first entry in the `liquidate-multi` list).
3. Construct a `liquidate-multi` list where the first entry liquidates Borrower A such that all of Borrower A's collateral is seized, triggering `no-collateral-left` and `socialize-debt-asset` → vault `socialize-debt` for asset X, which directly `var-set`s `lindex`/`index` in the asset X vault [3](#0-2) [2](#0-1) .
4. The second entry liquidates Borrower B, whose debt/collateral notional valuation for asset X is computed via `accrue-and-cache`, which returns the cache entry from step 2 rather than the updated vault index from step 3 [1](#0-0) .
5. Compare Borrower B's `coll-final`/`debt-to-repay` computed in this batch against what would be computed for the same borrower in an isolated `liquidate` call issued in a fresh transaction after Borrower A's socialization is already reflected on-chain. A discrepancy confirms the stale-cache issue.

I was unable to run this scenario against the test suite or trace the exact numerical magnitude of `next-index`/`next-liquidity-index` divergence caused by `socialize-debt`, so this PoC is a structural/code-path argument rather than a confirmed exploit trace. If precise reproduction is required, a Devin session with test-suite execution access (e.g. `local-testing/tests/flows/liquidation/**`) would be needed to instrument `liquidate-multi` with two positions sharing an asset and assert on the before/after index values.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
