## Title
Duplicate-account check for the accounts lattice hash is compiled out in production (release) builds - (File: runtime/src/bank/accounts_lt_hash.rs)

### Summary
The `Chainlink min/maxAnswer` bug class is: a critical validity check exists conceptually but is never actually enforced at runtime, so the system silently continues to operate on invalid/stale input and produces an incorrect result. The direct analog in this codebase is in `Bank::enqueue_off_chain_accounts_lt_hash_updates`, where the invariant "callers must not pass duplicate pubkeys" is only checked when `cfg!(debug_assertions)` is true. In a real, production (release) validator build, this check is compiled out entirely, so if any caller ever violates the "no duplicates" contract, the accounts lattice hash (`accounts_lt_hash`) is silently updated incorrectly and no panic or error is raised.

### Finding Description
`enqueue_off_chain_accounts_lt_hash_updates` explicitly documents an invariant: "Does not deduplicate accounts, requiring the caller to ensure there are no duplicates." [1](#0-0) 

The enforcement of that invariant is gated behind `cfg!(debug_assertions)`: [2](#0-1) 

Outside of the debug-only block, the function unconditionally proceeds to load the previous version of each account and enqueue an lt-hash update job per account entry, with no duplicate detection at all: [3](#0-2) 

This is called from `Bank::store_accounts_without_stakes_cache`, which itself documents the same "callers must ensure there are no duplicates" contract, and is invoked by every account-storing path in `Bank` (including `store_accounts` used by runtime/program-execution account writes): [4](#0-3) 

The pattern is structurally identical to the reported oracle bug class: a safety check that is supposed to catch a bad/degenerate input (min/maxAnswer bound check in the oracle; duplicate-pubkey check here) exists in the code, but is not actually active on the path that matters in production — Chainlink's circuit breaker check was simply missing; here the check exists but is deliberately disabled outside of `debug_assertions`, which is off in release/production validator builds. If any future code change, edge case, or caller (e.g. new callers of `store_accounts`/`store_accounts_without_stakes_cache`, or a bug in an existing caller such as partitioned epoch rewards processing) ever produces `accounts` with a duplicate pubkey, the following consequences are unique to release builds:
- The debug build would `panic!("duplicate accounts were enqueued for hashing: ...")`, catching the bug in CI/testing.
- The release build (the only thing that actually runs in production) does the load/enqueue for each duplicate entry independently. Because `prev_account` is loaded once per index using `load_with_fixed_root_do_not_populate_read_cache` and mixed with `curr_account` from `accounts.account(index, ...)` per-index, a set of duplicate pubkey entries will cause the lt hash mixing logic to mix-in/mix-out the wrong sequence of before/after states multiple times for the same pubkey, corrupting `accounts_lt_hash` silently, with no crash and no log/error.

### Impact Explanation
`accounts_lt_hash` is the value used by `Bank::verify_accounts` / `Bank::verify_snapshot_bank` at startup to confirm that a bank rebuilt from a snapshot or replay matches the expected on-chain state: [5](#0-4) [6](#0-5) 

If the duplicate-account invariant is ever violated in a release build (the only build type validators actually run), the resulting corruption is silent: the bank hash / accounts lt hash computed by that node will diverge from what other honest nodes compute for the same slot, without any panic, error log, or observable symptom until a later hash-mismatch is detected (if ever) — i.e. exactly the "hash/capitalization divergence" / "honest-node snapshot-vs-replay mismatch" impact category. This is a defense-in-depth failure: the debug-only assertion means the invariant is never actually verified on any node that matters for consensus.

### Likelihood Explanation
Likelihood of the underlying "caller passes duplicates" input actually occurring today is not established from what I could inspect — I did not find a currently-reachable, unprivileged caller producing duplicate pubkeys, and I was not able to fully audit every call site of `store_accounts` / `store_accounts_without_stakes_cache` (e.g., partitioned epoch rewards account writes) within tool/time constraints. What is concretely established is that the guard rail meant to catch such a bug (in-code documentation says "callers must ensure there are no duplicates") is only active in debug builds via `cfg!(debug_assertions)`, so this is a structural weakness rather than a proven exploitable path today. This matches the report's bug class ("a safety check is present but not actually enforced where it matters") rather than a proven live exploit, similar to how the oracle bug required a specific market condition (LUNA crash) to manifest.

### Recommendation
Make the duplicate-pubkey check for `enqueue_off_chain_accounts_lt_hash_updates` (and any other invariant currently gated by `cfg!(debug_assertions)` that protects `accounts_lt_hash` correctness) run unconditionally, or at minimum add a lightweight always-on check (e.g., a cheap hash-set based duplicate scan without the expensive detailed panic-message construction) so production/release builds also detect and fail loudly (panic or reject the write) rather than silently corrupting the accounts lattice hash.

### Proof of Concept
Not established as a live PoC — I could not, within the constraints of this investigation, confirm a concrete unprivileged-reachable call path that currently passes duplicate pubkeys into `store_accounts`/`store_accounts_without_stakes_cache`. The existing test `test_enqueue_off_chain_accounts_lt_hash_updates_catches_duplicates` demonstrates the check firing only because it is compiled with `debug_assertions` (as is default for `cargo test`), and explicitly documents that this is a debug-only safety net: [7](#0-6)

    // Store `accounts`.
    //
    // - Callers must ensure there are no duplicates in `accounts`.
    // - `thread_pool_for_loading_accounts` is used for accounts lt hashing,
    //   to load the previous version of accounts in parallel.
    pub fn store_accounts<'a>(
        &self,
        accounts: impl StorableAccounts<'a>,
        thread_pool_for_loading_accounts: Option<&ThreadPool>,
    ) {
        assert!(!self.freeze_started());
        let mut m = Measure::start("stakes_cache.check_and_store");
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();

        (0..accounts.len()).for_each(|i| {
            accounts.account(i, |account| {
                self.stakes_cache.check_and_store(
                    account.pubkey(),
                    &account,
                    new_warmup_cooldown_rate_epoch,
                    use_fixed_point_stake_math,
                )
            })
        });
        self.store_accounts_without_stakes_cache(accounts, thread_pool_for_loading_accounts);
        m.stop();
        self.rc
            .accounts
            .accounts_db
            .stats
            .stakes_cache_check_and_store_us
            .fetch_add(m.as_us(), Relaxed);
    }

    fn store_account_without_stakes_cache(&self, pubkey: &Pubkey, account: &AccountSharedData) {
        self.store_accounts_without_stakes_cache((self.slot(), &[(pubkey, account)][..]), None)
    }

    // Store `accounts`, without updating the stakes cache.
    //
    // - Callers must ensure there are no duplicates in `accounts`.
    // - `thread_pool_for_loading_accounts` is used for accounts lt hashing,
    //   to load the previous version of accounts in parallel.
    fn store_accounts_without_stakes_cache<'a>(
        &self,
        accounts: impl StorableAccounts<'a>,
        thread_pool_for_loading_accounts: Option<&ThreadPool>,

        assert!(!self.freeze_started());
        self.update_bank_hash_stats(&accounts);
        self.enqueue_off_chain_accounts_lt_hash_updates(

            thread_pool_for_loading_accounts,
        );
        self.rc
            .accounts
            .store_accounts_par(accounts, self.bank_id(), None, &self.ancestors);
    }

    fn verify_accounts(&self, calculated_accounts_lt_hash: Option<&AccountsLtHash>) -> bool {
        let accounts_db = &self.rc.accounts.accounts_db;

        fn check_lt_hash(
            expected_accounts_lt_hash: &AccountsLtHash,
            calculated_accounts_lt_hash: &AccountsLtHash,
        ) -> bool {
            let is_ok = calculated_accounts_lt_hash == expected_accounts_lt_hash;
            if !is_ok {
                let expected = expected_accounts_lt_hash.0.checksum();
                let calculated = calculated_accounts_lt_hash.0.checksum();
                error!(
                    "Verifying accounts failed: accounts lattice hashes do not match, expected: \
                     {expected}, calculated: {calculated}",
                );
            }
            is_ok
        }

        info!("Verifying accounts...");
        let start = Instant::now();
        let expected_accounts_lt_hash = self.accounts_lt_hash.lock().unwrap().clone();
        let is_ok = if let Some(calculated_accounts_lt_hash) = calculated_accounts_lt_hash {
            check_lt_hash(&expected_accounts_lt_hash, calculated_accounts_lt_hash)
        } else {
            let calculated_accounts_lt_hash =
                accounts_db.calculate_accounts_lt_hash_at_startup_from_index(&self.ancestors);
            check_lt_hash(&expected_accounts_lt_hash, &calculated_accounts_lt_hash)
        };
        info!("Verifying accounts... Done in {:?}", start.elapsed());
        is_ok
    }

    pub fn verify_snapshot_bank(
        &self,
        skip_shrink: bool,
        force_clean: bool,
        latest_full_snapshot_slot: Slot,
        calculated_accounts_lt_hash: Option<&AccountsLtHash>,
    ) -> bool {
        let (verified_accounts, verify_accounts_time_us) = measure_us!({
            let should_verify_accounts = !self.rc.accounts.accounts_db.skip_initial_hash_calc;
            if should_verify_accounts {
                self.verify_accounts(calculated_accounts_lt_hash)
            } else {
                info!("Verifying accounts... Skipped.");
                true
            }
        });

        let (_, clean_time_us) = measure_us!({
            let should_clean = force_clean || (!skip_shrink && self.slot() > 0);
            if should_clean {
                info!("Cleaning...");
                // We cannot clean past the latest full snapshot's slot because we are about to
                // perform an accounts hash calculation *up to that slot*.  If we cleaned *past*
                // that slot, then accounts could be removed from older storages, which would
                // change the accounts hash.
                self.rc
                    .accounts
                    .accounts_db
                    .clean_accounts(Some(latest_full_snapshot_slot), true);
                info!("Cleaning... Done.");
            } else {
                info!("Cleaning... Skipped.");
            }
        });

        let (_, shrink_time_us) = measure_us!({
            let should_shrink = !skip_shrink && self.slot() > 0;
            if should_shrink {
                info!("Shrinking...");
                self.rc.accounts.accounts_db.shrink_all_slots(
                    true,
                    // we cannot allow the snapshot slot to be shrunk
                    Some(self.slot()),
                );
                info!("Shrinking... Done.");
            } else {
                info!("Shrinking... Skipped.");
            }
        });

        info!("Verifying bank...");
        let (verified_bank, verify_bank_time_us) = measure_us!(self.verify_hash());
        info!("Verifying bank... Done.");

        datapoint_info!(
            "verify_snapshot_bank",
            ("clean_us", clean_time_us, i64),
            ("shrink_us", shrink_time_us, i64),
            ("verify_accounts_us", verify_accounts_time_us, i64),
            ("verify_bank_us", verify_bank_time_us, i64),
        );

        verified_accounts && verified_bank
    }
