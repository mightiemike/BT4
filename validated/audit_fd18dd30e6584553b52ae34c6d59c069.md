### Title
Clean/shrink race can trip `assert!(is_alive)` in `AccountsDb::load_accounts_index_for_shrink` - ([File: accounts-db/src/accounts_db.rs])

### Summary
`clean_accounts` reclaims a superseded rooted slot's index entry in one pass and only marks the corresponding storage offsets obsolete in a later, separate pass. If a background shrink of the just-superseded slot runs in that window, `shrink_collect` will not have filtered the now-stale account (obsolete flag not set yet), but the index scan performed by `load_accounts_index_for_shrink` will no longer contain the slot being shrunk, tripping `assert!(is_alive)`.

### Finding Description
`AccountsDb::clean_accounts` performs cleaning in two temporally separated phases against the same `reclaims` set:

1. `do_clean_scan` → `collect_reclaims` → `accounts_index::clean_rooted_entries` → `purge_older_root_entries`, which removes the older slot's `(slot, AccountInfo)` from the pubkey's `slot_list` and unrefs it. This happens entirely inside the parallel scan loop. [1](#0-0) [2](#0-1) 

2. Only after that entire scan completes does `clean_accounts` call `self.clean_accounts_older_than_root(&reclaims)`, which invokes `handle_reclaims(..., MarkAccountsObsolete::Yes(newest_slot))` to mark the reclaimed offsets obsolete on the *old* slot's storage. [3](#0-2) [4](#0-3) 

Concurrently, `shrink_storage`/`shrink_collect` for that same old slot first reads the storage's obsolete-offset set to filter dead accounts out of `stored_accounts`, then calls `load_accounts_index_for_shrink`, which re-queries the index for each remaining pubkey and asserts the returned `slot_list` still contains `slot_to_shrink`: [5](#0-4) [6](#0-5) 

If the shrinker's storage read of obsolete offsets happens after clean's phase 1 (index entry for the old slot already removed) but before clean's phase 2 (obsolete flag not yet set on that storage), the account is not filtered out of `stored_accounts`, yet `accounts_index.scan` for that pubkey returns a `slot_list` containing only the newer slot (e.g. `B`), not `slot_to_shrink` (`A`). `is_alive` becomes `false` and `assert!(is_alive)` panics. Nothing in `accounts_index` or `accounts_db.rs` takes a lock spanning both phases of `clean_accounts`, nor is there a lock preventing `shrink_storage` from running on a slot while `clean_accounts` is mid-flight on that same slot's pubkeys — the per-pubkey bin `RwLock` only guards individual accesses, not the whole clean pass.

This is architecturally analogous to the documented "reader vs. flusher/shrinker/cleaner" races in the large comment block in `retry_to_get_account_accessor`, all of which are shown to be "safu" because the later step retries via the index and is guaranteed consistent — but no equivalent retry/consistency guarantee is documented or implemented for `load_accounts_index_for_shrink`'s hard `assert!(is_alive)`. [7](#0-6) 

### Impact Explanation
This causes `AccountsDb::shrink_collect` (via `load_accounts_index_for_shrink`) to panic the validator process — a denial-of-service via a hard `assert!` triggered purely by ordinary account write/rewrite/close patterns from an unprivileged user, matching Agave's "node panic" bounty category.

### Likelihood Explanation
Reachability requires: (1) an attacker repeatedly writing/closing/resizing a single pubkey across rooted slots to generate superseded rooted entries that clean will reclaim, and (2) that same slot being independently registered as a shrink candidate (e.g. from unrelated dead/obsolete bytes in the same append vec) so a background shrink thread races `shrink_storage` against `clean_accounts` on that slot. The precise timing window between clean's phase 1 (index removal) and phase 2 (obsolete marking) is narrow but not otherwise synchronized, and clean/shrink use independent locks (per-bin index locks and `shrink_candidate_slots` mutex) rather than a single mutual-exclusion mechanism, so the interleaving is architecturally possible under thread-scheduler control. I was not able to fully verify, within available tooling, whether the accounts-background-service in this repo serializes clean and shrink work on the same background thread pool call ordering (no `accounts-background-service` file was found in this checked-out crate to confirm strict sequential per-iteration scheduling), which is the main remaining uncertainty affecting real-world (non-fuzzed) exploitability.

### Recommendation
Make `load_accounts_index_for_shrink`'s alive check tolerant of the case where the index no longer contains `slot_to_shrink` for a pubkey (treat it as "already reclaimed elsewhere, skip") instead of hard-asserting, or make marking-obsolete-in-storage and removing-from-index atomic (single critical section per pubkey/slot rather than two separate global passes) so shrink can never observe an inconsistent intermediate state.

### Proof of Concept
Rust integration/fuzz test plan for `accounts-db/src/accounts_db/tests/impl.rs`:
1. Create an `AccountsDb` with a scheduler-controllable interleaving (e.g. using a test hook/barrier inserted between `do_clean_scan` completion and `clean_accounts_older_than_root` in a forked test build, or by manually driving the two phases separately since they are already exposed as separate private calls in tests).
2. Store `pubkey` at slot `A`, root it, flush; store `pubkey` at slot `B > A`, root it, flush (`store_for_tests` + `add_root_and_flush_write_cache`).
3. Manually invoke the equivalent of phase 1 only: call the internal reclaim-collection step that calls `accounts_index.clean_rooted_entries`/`purge_older_root_entries` for `pubkey` with `max_clean_root_inclusive = B`, removing slot `A`'s entry from the index but *without* calling `remove_dead_accounts`/marking obsolete on storage `A`.
4. While in that state, call `get_unique_accounts_from_storage_for_shrink(&storage_A, ...)` followed by `shrink_collect::<AliveAccounts<'_>>(&storage_A, ..., slot_to_shrink = A)`.
5. Expected (bug) result: panic at `assert!(is_alive)` in `load_accounts_index_for_shrink`, because the index scan for `pubkey` now returns `slot_list = [(B, _)]` only, not containing `A`. A fix should instead make this test pass (e.g., by not tripping the assert and correctly treating the account as dead/obsolete for shrink purposes).

    fn purge_older_root_entries(
        &self,
        slot_list: &mut SlotListWriteGuard<T>,
        reclaims: &mut ReclaimsWithNewestSlot<T>,
        max_clean_root_inclusive: Option<Slot>,
    ) -> bool {
        if slot_list.len() <= 1 {
            self.purge_older_root_entries_one_slot_list
                .fetch_add(1, Ordering::Relaxed);
        }
        // Find the newest slot at or below the clean root, then reclaim every slot older than it.
        let newest_slot = slot_list
            .iter()
            .map(|(slot, _)| *slot)
            .filter(|slot| slot <= &max_clean_root_inclusive.unwrap_or(Slot::MAX))
            .max()
            .unwrap_or_default();

        slot_list.retain_and_count(|(slot, value)| {
            let should_purge = *slot < newest_slot;
            if should_purge {
                reclaims.push(((*slot, *value), newest_slot));
            }
            !should_purge
        }) == 0
    }
