### Title
Division by Zero in `RepositoryImpl::calculateGlobalEnergyLimit` from an unreachable `assert` guard - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` computes a TVM-caller's energy limit by dividing by `totalEnergyWeight`, guarded only by a Java `assert` statement instead of a runtime check. [1](#0-0)  This mirrors the CvgRewards pattern: a shared "total weight" accumulator that is normally non-zero can theoretically reach zero, and the reward/limit computation divides by it unconditionally.

### Finding Description
The function divides `energyWeight * totalEnergyLimit` by `totalEnergyWeight`, both in the BigInteger "hardened" path and the legacy double-based path: [2](#0-1) 

The only protection is `assert totalEnergyWeight > 0;` at line 976. In production JVMs, `assert` statements are disabled by default (they require the `-ea` JVM flag), so this assertion provides **no actual runtime protection** — if `totalEnergyWeight` were ever 0, the code proceeds directly to the division, throwing an unhandled `ArithmeticException` (integer divide-by-zero) or, in the non-hardened path, producing `NaN`/`Infinity` from a double division by zero (which then truncates to an undefined `long` value via `(long)`).

By contrast, the sibling non-VM implementations in `EnergyProcessor.calculateGlobalEnergyLimit` and `BandwidthProcessor.calculateGlobalNetLimit` correctly guard this same computation with real runtime checks: [3](#0-2) [4](#0-3) 

This shows the codebase is aware `totalEnergyWeight`/`totalNetWeight` can legitimately be zero (e.g., before any account freezes TRX for energy/bandwidth, or right after a chain reset/fork activation), and handles it safely everywhere except in `RepositoryImpl`, the repository implementation used by the TVM execution path (`ContractState` delegates directly to it at line 278-280) [5](#0-4) .

### Impact Explanation
If `totalEnergyWeight` is zero at the moment `calculateGlobalEnergyLimit` is invoked during TVM contract execution (e.g., via `RepositoryImpl.getAccountLeftEnergyFromFreeze`, used in energy accounting for contract calls in `VMActuator`), the resulting uncaught `ArithmeticException`/undefined value would propagate out of energy accounting logic used by every smart-contract transaction, potentially causing transaction processing divergence between nodes that hit the exception path differently, or an unhandled exception during block application — a state/processing halt class issue analogous to the original CvgRewards permanent-DoS impact. Because `assert` is compiled out in standard `java` deployment (no `-ea`), there is truly zero defense once this state is reached, unlike the sibling classes which have real checks.

### Likelihood Explanation
Under normal mainnet operation `totalEnergyWeight` is very unlikely to be exactly zero, since witnesses/users continuously freeze TRX for energy. However, this is the same "unlikely but possible" characterization that Sherlock judges accepted as Medium severity for the original finding — the risk surfaces during chain bootstrap, private/test networks, or edge-case state transitions (e.g., mass unfreezing under `AllowTvmFreeze`/`supportUnfreezeDelay` transitions) where `totalEnergyWeight` could transiently be zero before this specific code path is guarded elsewhere. The asymmetry between `RepositoryImpl` (unguarded) and `EnergyProcessor`/`BandwidthProcessor` (guarded) indicates this is an overlooked path rather than an intentionally-accepted invariant.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check consistent with `EnergyProcessor`'s guard, returning `0` (or another safe default) when `totalEnergyWeight <= 0`, before performing either the BigInteger or double division:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```

### Proof of Concept
1. Reach a chain state where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., early genesis/private-network state before any energy freeze, or post-unfreeze edge case).
2. Trigger any TVM contract call path that invokes `RepositoryImpl.calculateGlobalEnergyLimit` (called from `getAccountLeftEnergyFromFreeze`, used throughout `VMActuator.getAccountEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFixRatio`) [6](#0-5) .
3. Since `assert` is a no-op in production, execution proceeds to `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))` in the hardened path, throwing `ArithmeticException: / by zero`, or to `(double) totalEnergyLimit / 0` (yielding `Infinity`/`NaN`) in the legacy path, producing an undefined `long` energy limit.

Note: I could not confirm from the indexed code whether `totalEnergyWeight` can actually reach zero in a fully-deployed mainnet scenario (this would require deeper analysis of `DynamicPropertiesStore` initialization and all mutation sites of `totalEnergyWeight`); the finding is based on the observed inconsistency between the unguarded `RepositoryImpl` implementation and the guarded sibling implementations, which is a legitimate code-quality/defense-in-depth gap regardless.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();

      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;

    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
