### Title
Non-deterministic `OsRng` usage in Starknet OS state-diff encryption breaks output/commitment determinism - (File: `crates/starknet_os/src/hints/hint_implementation/output.rs`)

### Summary
The `calculate_keys_using_sha256_hash` hint generates the symmetric key and committee private keys used to encrypt the state-diff DA segment by pulling entropy from `rand::rngs::OsRng`, an OS-level cryptographically secure RNG that is *not* seeded deterministically from block data [1](#0-0) . These freshly-generated keys are written directly into the Cairo program's memory (`SymmetricKey`, `SnPrivateKeys`) and flow into the `encrypt_state_diff` Cairo function, whose output (`sn_public_keys`, `encrypted_symmetric_keys`, ciphertext) becomes part of the OS's on-chain output/DA segment [2](#0-1) , which is then relocated into the committed output segment via `process_data_availability`/`serialize_data_availability` [3](#0-2) .

### Finding Description
Everything else in the `SnosHintProcessor` is carefully engineered to be a deterministic function of block data — the processor's own general-purpose `rng` field is explicitly seeded from the Poseidon hash of the block hashes (`rng_seed`), specifically so that re-executing the OS over the same blocks always yields identical randomness [4](#0-3) . In contrast, `calculate_keys_using_sha256_hash` bypasses this deterministic RNG entirely and instead calls `OsRng.fill_bytes(&mut random_bytes)` to seed the key-derivation hash [5](#0-4) . `OsRng` pulls fresh entropy from the operating system on every invocation, so two independent executions of the OS over the *exact same block* (same transactions, same state diff, same public committee keys) will derive different `symmetric_key` and `sn_private_keys` values, and therefore different `encrypted_symmetric_keys` and ciphertext in the DA/output segment.

Because that output segment is hashed into the OS's program output / fact and ultimately becomes part of the block's committed data-availability output, any two honest parties that both re-execute the Starknet OS over the same block (e.g., the sequencer that builds/proves the block versus a verifying node, or the same node re-running the OS for auditing/replay) will compute different output hashes for an identical input, even though nothing malicious or different was fed into the computation.

### Impact Explanation
This directly produces honest-node divergence on the committed output/root: for a network feature that is otherwise fully deterministic (Starknet OS execution is supposed to be a pure function of the block inputs so that its output commitment can be independently verified), the encrypted-DA branch introduces external, non-reproducible randomness into that committed output. Any consumer that expects re-execution of the OS to reproduce the same output/commitment (verifiers, replay/audit tooling, or a second proving run after a failure) will get a mismatching output hash purely because of OS-level entropy, not because of any difference in transactions or state. This falls squarely in the "wrong committed root/output, honest-node divergence" impact category for the OS re-execution path, and is triggered simply by any block being built with `n_keys > 0` (committee/public keys configured for encrypted DA) — no malicious operator, peer, or prover behavior is required, only normal DA encryption of a state diff generated from unprivileged submitted transactions.

### Likelihood Explanation
This will trigger deterministically (100% of the time) whenever the encrypted-DA code path is exercised — i.e., whenever `n_keys > 0` in `process_data_availability`, which happens for every block on a deployment that enables committee-encrypted DA. It requires no attacker action at all; a single legitimate transaction that ends up in a state diff triggers this hint during block/proof generation. It is a design/implementation defect, not a race condition or attacker-dependent trigger, so the "likelihood" is effectively certain wherever the feature is enabled.

### Recommendation
Replace the `OsRng`-derived entropy in `calculate_keys_using_sha256_hash` with the processor's existing deterministic `rng` (seeded via `rng_seed`, i.e., derived from the block hash(es) and `rng_seed_salt`), or otherwise derive `random_bytes` deterministically from block-specific data (e.g., the compressed state diff plus the block hash) so that repeated executions of the OS over identical inputs always produce identical `symmetric_key`/`sn_private_keys`, and therefore identical committed output. If secrecy of the per-block key from would-be predictors is a concern, combine deterministic per-block material with a domain separation tag rather than OS entropy, preserving both unpredictability-to-outsiders and reproducibility-across-honest-re-executions.

### Proof of Concept
1. Configure a chain/sequencer with committee-based encrypted DA enabled (non-empty `public_keys` passed to `process_data_availability`, i.e., `n_keys > 0`).
2. Submit any ordinary transaction that produces a non-trivial state diff.
3. Run the Starknet OS (`SnosHintProcessor`) twice over the exact same `OsBlockInput`/state diff (e.g., once as the original proving run, once as an independent re-execution/verification run).
4. Observe that `calculate_keys_using_sha256_hash` invokes `OsRng.fill_bytes` each time [6](#0-5) , producing different `symmetric_key`/`sn_private_keys` on each run, which propagate into different `sn_public_keys`, `encrypted_symmetric_keys`, and ciphertext in the `encrypt_state_diff` output [7](#0-6) .
5. Compare the resulting DA/output segments and the derived output hash between the two runs — they differ despite identical block inputs, demonstrating non-deterministic commitments for a supposedly deterministic re-execution path.

pub(crate) fn calculate_keys_using_sha256_hash(mut ctx: HintContext<'_>) -> OsHintResult {
    // Generate a cryptographically secure random seed.
    let mut random_bytes = [0u8; 32];
    OsRng.fill_bytes(&mut random_bytes);

    let mut hasher = Sha256::new();
    hasher.update(random_bytes);

    // In addition, hash the compressed state diff for extra defense against potential attacks on
    // randomness source.
    let compressed_start = ctx.get_ptr(Ids::CompressedStart)?;
    let compressed_end = ctx.get_ptr(Ids::CompressedEnd)?;
    let array_size = (compressed_end - compressed_start)?;
    for i in 0..array_size {
        let felt = ctx.vm.get_integer((compressed_start + i)?)?;
        hasher.update(felt.to_bytes_be());
    }
    let random_key_seed = hasher.finalize().to_vec();

// Returns the final data-availability to output.
func process_data_availability{range_check_ptr, ec_op_ptr: EcOpBuiltin*}(
    state_updates_start: felt*,
    state_updates_end: felt*,
    compress_state_updates: felt,
    n_keys: felt,
    public_keys: felt*,
) -> (da_start: felt*, da_end: felt*) {
    if (compress_state_updates == 0) {
        return (da_start=state_updates_start, da_end=state_updates_end);
    }

    alloc_locals;

    // Compress the state updates.
    local compressed_start: felt*;
    %{ SetCompressedStart %}
    let compressed_dst = compressed_start;
    with compressed_dst {
        compress(data_start=state_updates_start, data_end=state_updates_end);
    }

    if (n_keys == 0) {
        // No public keys - skip the state updates encryption.
        return (da_start=compressed_start, da_end=compressed_dst);
    }

    // Encrypt the compressed state updates.
    let (encrypted_start, encrypted_end) = encrypt_state_diff(
        compressed_start=compressed_start,
        compressed_end=compressed_dst,
        n_keys=n_keys,
        public_keys=public_keys,
    );

    return (da_start=encrypted_start, da_end=encrypted_end);
}
