### Title
Host/Authority Injection in `buildEmbeddedAppUrl` via Userinfo-Style `host` Parameter Bypassing `sanitizeHost` Validation - (File: `packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts`)

### Summary
`sanitizeHost` validates a Shopify `host` query parameter by base64-decoding it and checking only the `.hostname` property of a `URL` object built from it. `buildEmbeddedAppUrl`, however, uses the raw decoded string — not the validated/normalized `hostname` — when constructing the final embedded-app redirect URL. Because `URL` parsing discards userinfo (`user@`), this creates a mismatch between what is *validated* (the parsed hostname) and what is *used* (the full raw decoded string), letting an anonymous requester smuggle attacker-controlled authority data into a Shopify-trusted redirect URL — the same "validate one representation, act on another" root cause as the `serve-here` path-traversal report, applied to URL/host construction instead of filesystem paths.

### Finding Description
`sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` only inspects the `hostname` field after parsing: [1](#0-0) 

It never re-serializes or re-validates the full authority component (userinfo, path, etc.), it only checks that `hostname` ends in an allowed suffix such as `.myshopify.com`.

`buildEmbeddedAppUrl` then decodes the same host value again and interpolates the raw decoded string directly into the final URL, bypassing the URL object entirely: [2](#0-1) 

Because `sanitizeHost(config)(host, true)` only asserts that `new URL('https://' + decodeHost(host)).hostname` matches the allow-list, an attacker can craft a base64 `host` value whose decoded form is e.g. `evil-phisher.example@shop.myshopify.com`. When parsed by `URL`, `evil-phisher.example` becomes discarded userinfo and `hostname` resolves to `shop.myshopify.com`, satisfying the regex in `sanitizeHost`. But `buildEmbeddedAppUrl` never re-parses the string — it directly builds:
```
https://evil-phisher.example@shop.myshopify.com/apps/<apiKey>
```
This is returned and used as a `redirect()` target by every consumer of `getEmbeddedAppUrl`, all reachable from anonymous/merchant-controlled query parameters: [3](#0-2) [4](#0-3) 

In all three of these call sites, `host` originates straight from `url.searchParams.get('host')`/`req.query.host`, i.e. attacker/merchant-controlled, single-request input with no session or privilege requirement.

### Impact Explanation
This is a validation/construction mismatch analogous to path traversal: `sanitizeHost` "canonicalizes" (parses) the value for the purpose of the security check, but the consuming function later re-derives its own path from the same raw untrusted string instead of the canonical/validated form — precisely the class of bug in the `serve-here` report, where a validated/expected path segment differs from what is actually used to resolve the target resource. Here the practical result is that a value which should be rejected as escaping the `myshopify.com`/`shopify.com` origin allow-list can instead be embedded, unfiltered, into the authority component of a trusted Shopify redirect URL. This enables convincing phishing redirects (`https://attacker-string@shop.myshopify.com/...`) originating from the app's own trusted OAuth/redirect flow, and demonstrates that the sanitization boundary is not actually enforced end-to-end on the value that gets used.

### Likelihood Explanation
High reachability: the `host` parameter is read directly from the request query string with no authentication, at multiple redirect call sites used during normal OAuth completion / app-root redirection flows in Express, Remix, and React Router adapters. No secrets or elevated privileges are required — a single crafted GET request containing a specially base64-encoded `host` is sufficient to trigger the mismatch.

### Recommendation
- In `buildEmbeddedAppUrl` (`packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts`), construct the final URL using the validated `URL` object's `hostname` (and, if a path is legitimately part of the host format such as `spin.dev`/`shop.dev` variants, its normalized `href`), not the raw `decodeHost(host)` string.
- Have `sanitizeHost` reject decoded host values containing `@`, `\`, control characters, or any character other than what is valid in a bare hostname, rather than only checking the `URL`-derived `hostname` suffix.
- Add regression tests asserting that `host` values decoding to strings containing `@`/userinfo segments are rejected or safely stripped rather than passed through to `buildEmbeddedAppUrl`'s output.

### Proof of Concept
1. Craft `host = base64("evil-phisher.example@shop.myshopify.com")`.
2. Send `GET /auth/callback?shop=shop.myshopify.com&host=<that base64 value>` (or any route invoking `redirectToShopifyOrAppRoot`/`getEmbeddedAppUrl` for a non-`ShopifyAdmin`-distribution embedded app).
3. `sanitizeHost` parses `https://evil-phisher.example@shop.myshopify.com`, extracts `hostname = shop.myshopify.com`, and the check passes.
4. `buildEmbeddedAppUrl` returns `https://evil-phisher.example@shop.myshopify.com/apps/<apiKey>`, which is used verbatim in the server's redirect response — i.e., a Shopify-trusted domain redirect that contains attacker-supplied userinfo/authority text, without ever being re-validated as a whole URL.

```typescript
export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;

    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);

      const originsRegex = [
        'myshopify\\.com',
        'shopify\\.com',
        'myshopify\\.io',
        'spin\\.dev',
        'shop\\.dev',
      ];

      if (config.domainTransformations) {
        const hostTransformationDomains = config.domainTransformations
          .filter((t) => t.includeHost !== false)
          .flatMap((t) =>
            getTransformationDomains({
              ...config,
              domainTransformations: [t],
            }),
          );
        originsRegex.push(...hostTransformationDomains);
      }

      const hostRegex = new RegExp(`\\.(${originsRegex.join('|')})$`);
      if (!hostRegex.test(hostname)) {
        sanitizedHost = null;
      }
    }
    if (!sanitizedHost && throwOnInvalid) {
      throw new InvalidHostError('Received invalid host argument');
    }

    return sanitizedHost;
  };
```

```typescript
export function buildEmbeddedAppUrl(
  config: ConfigInterface,
): BuildEmbeddedAppUrl {
  return (host: string): string => {
    sanitizeHost(config)(host, true);
    const decodedHost = decodeHost(host);

    return `https://${decodedHost}/apps/${config.apiKey}`;
  };
```
