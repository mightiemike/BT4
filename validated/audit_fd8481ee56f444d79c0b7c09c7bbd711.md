### Title
`get-rewards` in pox-5.clar derives sBTC rewards from a raw, donatable token balance instead of an internally tracked deposit ledger - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`get-rewards` computes the reward pool by reading the live sBTC token balance of the contract and subtracting internally tracked accounting variables, rather than tracking actual reward deposits through an authenticated entry point. This is the same anti-pattern flagged in the external report: deriving an economically meaningful quantity from a spot balance that any external, unprivileged party can directly inflate by transferring tokens to the contract address, instead of using state that is exclusively updated through protocol-controlled accounting.

### Finding Description
`get-rewards` is defined as: [1](#0-0) 

```
(define-read-only (get-rewards)
    (let (
            (cur-reserve (var-get reserve-balance))
            (total-staked-sbtc (get-total-sbtc-staked))
            (current-balance (unwrap-panic (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
                get-balance current-contract
            )))
        )
        (- current-balance total-staked-sbtc cur-reserve)
    )
)
```

and `get-new-rewards`/`calculate-rewards` build directly on top of it: [2](#0-1) 

`gross-accrued-rewards` (= `get-new-rewards`) feeds directly into `calculate-rewards`, which apportions it between the reserve, protocol bonds, and STX-only stakers via `cumulative-rewards-per-ustx`.

Because `sbtc-token` is a standard SIP-010 fungible token, **any principal** can call `transfer` on the sbtc-token contract to send sBTC directly to the pox-5 contract's principal, with no interaction with pox-5 itself. That donated balance is indistinguishable, from `get-rewards`'s point of view, from legitimate protocol income (e.g., stacking/mining reward flow into the contract). `total-staked-sbtc` and `cur-reserve` are internal ledger variables that only track *known* custodied/settled amounts — they cannot "subtract out" an arbitrary donation, so any external transfer is counted 1:1 as "new rewards" and gets distributed through `calculate-rewards` to whoever is a bond-holder/STX staker at the time `calculate-rewards` is next invoked.

This is the direct structural analog of the reported `ConnextPriceOracle.getPriceFromDex` bug: instead of querying an authoritative, protocol-computed reserve/accounting figure, the contract derives an economically consequential number (distributable rewards) from a `balanceOf`-style call that is trivially manipulable by an unprivileged actor.

### Impact Explanation
An attacker who is a bond-holder or STX staker (or colludes with one) at the time `calculate-rewards` executes can:
1. Transfer sBTC directly to the pox-5 contract just before calling the permission-less `calculate-rewards`.
2. Have that donated sBTC counted as "gross accrued rewards" and distributed proportionally across current stakers/bonds — including back to the attacker's own share, while diluting the distribution owed to depositors who join between the donation and the next `calculate-rewards` call.
3. More critically, because `get-rewards`/`get-new-rewards` treat the raw balance delta as legitimate reward income, this breaks the invariant that "amounts owed to stakers ⇐ actual protocol income accounted for by the ledger." Repeated donation/harvest cycles can desynchronize `last-accounted-rewards-only`/`reserve-balance` bookkeeping from the real custodial requirements, causing reward mis-payment (some stakers receive sBTC that was never protocol-earned reward, at the expense of others, or the reserve accounting becomes permanently incorrect relative to actual custody obligations).

This is a fee/reward-mispayment class issue (bounded by the size of the manipulable balance and reachable by a single unprivileged token holder — no majority or node-operator/admin key required), matching the "reward mis-payment bounded to fees" High-impact category defined in scope.

### Likelihood Explanation
Likelihood is high for the actor precondition (owning or acquiring sBTC and being a current bond/staker) since:
- `calculate-rewards` is `define-public` and callable by anyone.
- sBTC token transfers to the pox-5 contract principal require no pox-5 permission at all — it is a plain SIP-010 transfer.
- No sanity check exists in `get-rewards`/`calculate-rewards` comparing the live balance against an internally accumulated "expected deposits" ledger; the code trusts the balance unconditionally.

### Recommendation
Do not derive `get-rewards` from the live sBTC balance of the contract. Instead, maintain an explicit, protocol-controlled "total rewards received" counter that is incremented only through an authenticated deposit/settlement entry point (e.g., the specific bridge/mint/settlement call that legitimately delivers mining/stacking rewards), analogous to using `getReserves()` instead of `balanceOf()`. If a balance-based sanity check is still desired, treat any balance in excess of the tracked ledger as un-attributable and exclude it from distribution (e.g., sweep it to the reserve only after verification, or require it to be routed through a dedicated "donate" function that is fenced off from `calculate-rewards`'s payout math).

### Proof of Concept
1. Deploy/observe the pox-5 contract's sBTC balance `B0`, tracked staked amount `S`, and reserve `R0`, so `get-rewards() = B0 - S - R0 = D0` (pre-existing undistributed rewards).
2. Attacker (holding sBTC and also being, or colluding with, a current bond-holder/STX staker) calls `sbtc-token.transfer` to send `X` sBTC to the pox-5 contract principal. New balance is `B0 + X`.
3. Attacker (or anyone) calls `calculate-rewards`. `get-new-rewards()` now returns `D0 + X - last-accounted-rewards-only`, i.e., the donated `X` is treated as legitimate protocol income.
4. `calculate-rewards` apportions `X` (net of `RESERVE_RATIO`) into `cumulative-rewards-per-ustx` for current stakers/bonds, from which the attacker (as an existing staker) reclaims a share of their own donation while diluting/mis-crediting rewards intended for genuine bridge/mining income, or for stakers who join after step 2 but before step 3.

This confirms the equality "distributed reward = protocol-earned income" is broken by an unprivileged, minority-triggerable balance donation, mirroring the `balanceOf`-derivation flaw from the external report.
