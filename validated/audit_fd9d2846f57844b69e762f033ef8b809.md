Confirmed: `ExternalInitiator` struct has no `JobID`/webhook-spec binding field at all [1](#0-0) , and `AuthenticateExternalInitiator` in `core/bridges/external_initiator.go` only checks that the secret matches the stored hash — it never checks which job/bridge the EI was intended for [2](#0-1) .

### Title
Unauthorized job run triggering via unbound External Initiator credential on POST /v2/jobs/:ID/runs - (File: core/web/router.go)

### Summary
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` authenticates an EI purely by access-key/secret and then unconditionally injects a synthetic `UserRoleRun` user into the Gin context, with no linkage to the specific job or bridge the EI was created for. `PipelineRunsController.Create` accepts any authenticated "run role" principal (including this synthetic EI user) and directly calls `RunJobV2` with the caller-supplied `jobID` from the URL path, so any EI key can trigger runs on any job ID, not just the job it was provisioned for.

### Finding Description
The route `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))` is reachable by three auth methods including `auth.AuthenticateExternalInitiator` [3](#0-2) . That function looks up the EI purely by access key/secret via `store.FindExternalInitiator` and `bridges.AuthenticateExternalInitiator`, then sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` unconditionally for any valid EI, with a comment claiming this "inherently assume[s] the role of run" [4](#0-3) . `RequiresRunRole` only checks `user.Role != UserRoleView`, so any EI-authenticated request passes [5](#0-4) .

In `PipelineRunsController.Create`, the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed," but the actual check is `_, isUser := auth.GetAuthenticatedUser(c)` [6](#0-5) . Since `AuthenticateExternalInitiator` also populates `SessionUserKey` with a synthetic `User`, `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests too — the intended EI exclusion does not actually happen. The handler then parses the URL `:ID` param as an int32 job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly, without checking that the authenticated EI (or its `SessionExternalInitiatorKey`) is associated with that specific job. The `bridges.ExternalInitiator` struct itself carries no `JobID` or webhook-spec reference at all [1](#0-0) , so there is no data model support for such a binding even if the check were added.

### Impact Explanation
Any holder of a valid EI access-key/secret pair (a low-trust credential intended only to trigger its own webhook job) can execute the pipeline of an arbitrary job by integer ID via `POST /v2/jobs/:ID/runs`. This is unauthorized workflow/job execution across job boundaries, potentially causing pipeline tasks with embedded secrets, bridge credentials, or on-chain transaction side effects to be executed on behalf of an attacker who was never granted access to that job — matching a "unauthorized workflow execution" / job execution privilege boundary bypass class of impact.

### Likelihood Explanation
The precondition is possessing any valid EI keypair, which is explicitly a normal, low-trust credential obtainable through the ordinary bridge/EI creation flow (`RequiresEditRole` only, not admin) [7](#0-6) . No further privilege or exploitation complexity is required beyond sending one HTTP request with a job ID that differs from the EI's intended job; this is directly and repeatably exploitable.

### Recommendation
Bind External Initiators to the job(s)/webhook spec they were created for (e.g., store a job/webhook reference on `bridges.ExternalInitiator` or on the webhook job spec), and in `PipelineRunsController.Create` (or a dedicated EI-only run path) verify that the authenticated `SessionExternalInitiatorKey` matches the target job before invoking `RunJobV2`. Additionally, fix the `isUser` check to actually distinguish real users from the synthetic EI-derived `SessionUserKey` (e.g., via a distinct context key or a `IsExternalInitiator` marker) so the existing comment's intent — "EIs not allowed to run jobs using int IDs" — is enforced in code.

### Proof of Concept
Integration test in `core/web/pipeline_runs_controller_test.go`-style test:
1. Create job X and job Y (two distinct webhook/pipeline jobs).
2. Create External Initiator `EI_A` intended for job X via `POST /v2/external_initiators` (using an edit-role user session).
3. Using `EI_A`'s access key/secret headers (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`), send `POST /v2/jobs/<jobY-ID>/runs`.
4. Assert the response is `401/403` (rejected) — expected per the intended invariant.
5. Actual current behavior: the request succeeds (`200 OK` with a `pipelineRun` resource for job Y), demonstrating that `EI_A` triggered a run on job Y despite having no association with it, confirming the vulnerability.

```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
```

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
