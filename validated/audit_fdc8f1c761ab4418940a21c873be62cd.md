### Title
Unbounded Gzip Decompression (Zip-Bomb) DoS in RPC Declare-Class Handling - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
The RPC node's `decompress_program` function decompresses a client-supplied, base64+gzip-encoded Cairo0 program with no size or time limit, unlike every other decompression path in the codebase, which enforces an explicit cap. A single unprivileged caller submitting a Declare (or a `simulate_transaction`/`estimate_fee`/trace call that carries a `DeprecatedContractClass`) can supply a small gzip bomb that expands to an arbitrarily large in-memory buffer, exhausting node memory — the same bug class as CVE-2020-11612 (Netty `ZlibDecoder` unbounded allocation).

### Finding Description
`decompress_program` reads the entire decompressed stream into an unbounded `Vec<u8>` via `decoder.read_to_end(&mut decompressed)`, with a `// TODO(dan): add time and size limits.` comment acknowledging the gap: [1](#0-0) 

This function is used by `TryFrom<ApiContractClass> for GatewayContractClass`, which converts a client-provided `DeprecatedContractClass` (legacy Cairo0 program, submitted as base64+gzip in the JSON-RPC payload) into the internal `GatewayContractClass::Cairo0` representation: [2](#0-1) 

This is reachable from any client call that submits a broadcasted Declare-style transaction/class (e.g. `starknet_simulateTransactions`, `starknet_estimateFee`, or `starknet_addDeclareTransaction`-adjacent RPC flows that pass through `ApiContractClass::DeprecatedContractClass`) — i.e., an unprivileged contract declarer/transaction sender.

By contrast, every other decompression helper in the codebase enforces a strict cap:
- `starknet_api::compression_utils::decompress_with_size_limit` uses `.take(max_size + 1)` before `read_to_end`: [3](#0-2) 
- `apollo_storage::compression_utils::decompress` bounds output via `zstd::bulk::decompress(data, MAX_DECOMPRESSED_SIZE)` (256 MB cap): [4](#0-3) 

`decompress_program` is the outlier that skips this protection entirely, mirroring the Netty `ZlibDecoder` flaw where a small compressed payload triggers unbounded allocation on decode.

### Impact Explanation
A malicious but unprivileged RPC caller can send a request containing a tiny (KB-scale) gzip-compressed "program" field that decompresses to gigabytes of data, forcing the node to allocate that memory in `decompress_program`. Because RPC servers typically process many concurrent requests, an attacker can repeat this to exhaust available memory or trigger OOM kills, causing denial of service to the sequencer/RPC node — a network unable to serve/confirm requests. This matches CWE-400/CWE-770 resource exhaustion, analogous to the Netty advisory's impact (`AV:N/AC:L/PR:N/UI:N ... A:H`).

### Likelihood Explanation
The path requires no privileges — any JSON-RPC client can submit a Declare-shaped payload with a crafted `program` field. Gzip decompression bombs achieve very high compression ratios (>1000x) trivially, so a small request body (well under typical HTTP body-size limits like the `max_request_body_size` guard seen elsewhere in the codebase) can decompress into an enormous buffer. Likelihood is high because the vulnerable code path lacks any of the size/time guards present elsewhere, and the TODO comment confirms this was a known, unaddressed gap.

### Recommendation
Apply the same bounded-decompression pattern used elsewhere in the codebase to `decompress_program`: wrap the `GzDecoder` read in a size-limited reader (e.g., `.take(MAX_SIZE)`), reject/error if the decompressed output would exceed the limit, and optionally enforce a decompression time budget, matching `starknet_api::compression_utils::decompress_with_size_limit`.

### Proof of Concept
1. Craft a legacy (Cairo0) `program` payload consisting of highly repetitive data (e.g., all zero bytes), gzip-compress it (achieving >1000x ratio), and base64-encode it.
2. Submit an RPC call that carries a `DeprecatedContractClass` with this crafted `program` field (e.g., via `starknet_estimateFee` or `starknet_simulateTransactions` with a broadcasted Declare transaction).
3. The node calls `decompress_program`, which allocates and fills a `Vec<u8>` with the entire decompressed multi-gigabyte content with no cap, exhausting memory on the node handling the request.

fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}

pub(crate) const MAX_DECOMPRESSED_SIZE: usize = 1 << 28; // 256 MB
// The compression level to use. Higher levels are slower but compress better.
const COMPRESSION_LEVEL: i32 = zstd::DEFAULT_COMPRESSION_LEVEL;

/// Returns the compressed data in a vector.
///
/// # Arguments
/// * data - bytes to compress.
///
/// # Errors
/// Returns [`std::io::Error`] if any read error is encountered.
pub fn compress(data: &[u8]) -> Result<Vec<u8>, std::io::Error> {
    zstd::bulk::compress(data, COMPRESSION_LEVEL)
}

/// Serialized and then compress object.
///
/// # Arguments
/// * object - the object to serialize and compress.
///
/// # Errors
/// Returns [`StorageSerdeError`] if any error is encountered in the serialization or compression.
pub fn serialize_and_compress(object: &impl StorageSerde) -> Result<Vec<u8>, StorageSerdeError> {
    let mut buf = Vec::new();
    object.serialize_into(&mut buf)?;
    Ok(compress(buf.as_slice())?)
}

/// Decompress data and returns it as bytes in a vector.
///
/// # Arguments
/// * data - bytes to decompress.
///
/// # Errors
/// Returns [`std::io::Error`] if any read error is encountered.
pub fn decompress(data: &[u8]) -> Result<Vec<u8>, std::io::Error> {
    zstd::bulk::decompress(data, MAX_DECOMPRESSED_SIZE)
}
