### Title
`ExchangeTransactionContract` rejection can be bypassed by toggling `AllowHardenExchangeCalculation` - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.pushTransaction()` is supposed to unconditionally reject `ExchangeTransactionContract` transactions by calling `isExchangeTransaction(trx.getInstance())` [1](#0-0) . However, exactly like the `RubiconMarket` bug where `buyEnabled` was only checked in `_buys` (reachable only when `matchingEnabled` was true) instead of unconditionally in `buy`, the java-tron analog conditions the "is this an exchange transaction" determination itself on the unrelated `AllowHardenExchangeCalculation` dynamic parameter, so the rejection silently stops firing once that parameter is turned on.

### Finding Description
`pushTransaction` gates `ExchangeTransactionContract` submission with:
```java
if (isExchangeTransaction(trx.getInstance())) {
  throw new ContractValidateException("ExchangeTransactionContract is rejected");
}
``` [1](#0-0) 

`isExchangeTransaction` is a private method on `Manager` that determines contract type detection, but its return value flips to `false` (i.e. "not an exchange transaction", bypassing rejection) once `AllowHardenExchangeCalculation` is set to `1`. This is proven by the test suite:
```java
// Default: hardened disabled (==0) -> contract is treated as exchange
chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
Assert.assertTrue(... (boolean) m.invoke(dbManager, exchange));

// Hardened enabled -> bypass returns false
chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
Assert.assertFalse("Exchange tx must be bypassed when hardened enabled",
    (boolean) m.invoke(dbManager, exchange));
``` [2](#0-1) 

The consequence is directly analogous to the `RubiconMarket` finding: the intended "disable" gate (`buyEnabled` there, the exchange-rejection gate here) is entangled with a separate feature toggle (`matchingEnabled` there, `AllowHardenExchangeCalculation` here) instead of being an independent, unconditional check. Flipping the unrelated toggle re-opens a code path meant to stay closed.

This is corroborated by the actuator-level test showing that once the toggle is enabled, `ExchangeTransactionActuator` fully executes trades (mutating balances and exchange pool state) rather than being rejected:
```java
dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
...
actuator.validate();
actuator.execute(ret);
Assert.assertEquals(code.SUCESS, ret.getInstance().getRet());
``` [3](#0-2) 

And `rejectExchangeTransaction`, the enforcement companion invoked elsewhere in the transaction pipeline, is tested only under the default (hardened-disabled) condition, without exercising the hardened-enabled bypass path: [4](#0-3) 

The underlying math toggle itself is legitimate for `ExchangeCapsule.transaction()` (choosing `SafeExchangeProcessor` vs `ExchangeProcessor`) [5](#0-4) , and `AllowHardenExchangeCalculation` is a committee-governed chain parameter validated in `ProposalUtil` [6](#0-5)  — but that governance toggle should control *how* the exchange math is computed, not *whether the deprecated `ExchangeTransactionContract` pathway is rejected at all*.

Note: I could not directly view the body of `isExchangeTransaction`/`rejectExchangeTransaction` in `Manager.java` due to index size limits on file contents; the behavior above is inferred from the calling site and the dedicated unit tests that exercise it via reflection. A Devin session with full file access would be needed to confirm the exact implementation and all call sites.

### Impact Explanation
If the intent of this check is to permanently retire `ExchangeTransactionContract` in favor of the newer `Market*` actuators (as evidenced by the fork-gated `rejectExchangeTransaction` logic), then any account can re-enable the deprecated exchange trading pathway network-wide simply because the committee (or whichever governance path sets dynamic properties) turned on `AllowHardenExchangeCalculation`. This defeats the deprecation/rejection policy and reopens a previously-disabled state-mutating transaction type (balance and asset transfers via `ExchangeCapsule.transaction`) to normal users, which is an unauthorized-account-operation / broken state-transition-gating issue reachable from any anonymous broadcast transaction.

### Likelihood Explanation
Requires `AllowHardenExchangeCalculation` to be `1`, which is set through the standard proposal/parameter mechanism [6](#0-5) . This is not attacker-controlled directly, but once set (e.g., intended purely to switch to safer math), it has the unintended side effect of also disabling the `ExchangeTransactionContract` rejection gate, which any transaction submitter can then exploit by simply broadcasting an `ExchangeTransactionContract`.

### Recommendation
Decouple the "detect `ExchangeTransactionContract`" logic from the `AllowHardenExchangeCalculation` state. The rejection check in `pushTransaction` (and any equivalent check in `rejectExchangeTransaction`) should identify the contract type unconditionally (e.g., purely via `ContractType.ExchangeTransactionContract`), and only use `AllowHardenExchangeCalculation` inside `ExchangeCapsule.transaction()`/`ExchangeTransactionActuator` to select the math implementation, not to determine whether the transaction type itself should be treated as an exchange transaction subject to rejection.

### Proof of Concept
1. Deploy/observe a network state where `ExchangeTransactionContract` submission is meant to be rejected via `pushTransaction` [7](#0-6) .
2. Set `AllowHardenExchangeCalculation=1` via governance (`saveAllowHardenExchangeCalculation(1)`).
3. Broadcast an `ExchangeTransactionContract` transaction.
4. `isExchangeTransaction` now returns `false` for this contract (per `ManagerTest.isExchangeTransactionBypassedWhenHardenedEnabled` [8](#0-7) ), so the rejection in `pushTransaction` is skipped and the transaction is queued/processed.
5. `ExchangeTransactionActuator.execute()` proceeds and completes successfully, mutating account balances and exchange pool balances (`hardenedSuccessExchangeTransaction` test) [3](#0-2) , confirming the deprecated/rejected pathway is fully reachable.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

    forkUtils.getManager().getDynamicPropertiesStore()

        .getMaintenanceTimeInterval();
    long hardForkTime =
        ((ForkBlockVersionEnum.VERSION_4_8_2.getHardForkTime() - 1) / maintenanceTimeInterval + 1)
            * maintenanceTimeInterval;
    forkUtils.getManager().getDynamicPropertiesStore()
        .saveLatestBlockHeaderTimestamp(hardForkTime - 1);

    // 1) before fork 4.8.2 -> rejected
    ContractValidateException thrown = assertThrows(ContractValidateException.class, proposeOne);
    assertEquals("Bad chain parameter id [ALLOW_HARDEN_EXCHANGE_CALCULATION]",
        thrown.getMessage());

    forkUtils.getManager().getDynamicPropertiesStore()
        .saveLatestBlockHeaderTimestamp(hardForkTime + 1);
    Arrays.fill(stats, (byte) 1);
    forkUtils.getManager().getDynamicPropertiesStore()
        .statsByVersion(ForkBlockVersionEnum.VERSION_4_8_2.getValue(), stats);

    // 2) value not in {0, 1} -> rejected
    thrown = assertThrows(ContractValidateException.class, proposeTwo);
    assertEquals("This value[ALLOW_HARDEN_EXCHANGE_CALCULATION] is only allowed to be 0 or 1",
        thrown.getMessage());

    // 3) current value is 0 (default), proposing 0 again -> rejected
    thrown = assertThrows(ContractValidateException.class, proposeZero);
    assertEquals("[ALLOW_HARDEN_EXCHANGE_CALCULATION] has been set to 0, no need to propose again",
        thrown.getMessage());

    // 4) value=1 to enable -> ok
    try {
      proposeOne.run();
    } catch (Throwable e) {
      Assert.fail("Should pass when toggling 0 -> 1: " + e.getMessage());
