## Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash verification, letting chunk-executor replay commit a divergent state root - ([File: types/src/transaction/mod.rs])

### Summary
The DKIM report's core lesson is: a verification routine that is supposed to bind an authenticated value to *all* of the fields it claims to cover, but silently skips some of them, lets an attacker (or a buggy/malicious execution path) smuggle a different value through while the "verification passed" signal is still produced. The Aptos analog is `TransactionOutput::ensure_match_transaction_info` in [1](#0-0) , which is the function used during chunk-based replay/state-sync to confirm that a locally re-executed `TransactionOutput` matches the `TransactionInfo` that was authenticated by consensus/the accumulator proof.

### Finding Description
`ensure_match_transaction_info` checks `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash`, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as the code itself documents: [2](#0-1) 

These checkpoint hashes are exactly the fields that summarize the Sparse-Merkle/JMT state root (and, with `TRANSACTION_INFO_V1`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, the hot-state and native-position state roots) that the transaction produced — i.e., they are the state-commitment fields of `TransactionInfoV0`/`TransactionInfoV1` [3](#0-2) [4](#0-3) .

This function is called from `execution/executor/src/chunk_executor/mod.rs`, which is the code path used by state-sync/chunk-executor to accept and commit `TransactionOutputListWithProof`/replayed outputs without full transaction re-execution consensus. Because `ensure_match_transaction_info` is the only local sanity check tying the recomputed/received `TransactionOutput` to the `TransactionInfo` that is bound to the ledger accumulator by the accumulator proof, omitting the checkpoint-hash fields means: as long as `write_set` hash, `event_root_hash`, `status`, and `gas_used` line up, a `TransactionOutput` whose state_checkpoint_hash / hot_state_checkpoint_hash / position_state_checkpoint_hash diverges from the one actually committed to the ledger accumulator will still pass this check and be treated as consistent.

### Impact Explanation
State-checkpoint hashes are precisely the Sparse Merkle Tree root committing the world-state at a checkpoint boundary, and (with `TRANSACTION_INFO_V1`) the hot-state and native-position state roots that are consensus-authenticated via the transaction accumulator. If a chunk-executor/replay/state-sync flow relies on `ensure_match_transaction_info` as its integrity gate rather than independently re-verifying these checkpoint hashes against the state actually computed and persisted, a node could commit or accept as "verified" a locally-computed/replayed state whose checkpoint (state) root differs from the authenticated one, without the mismatch being caught by this function. That is a state-commitment integrity gap: durable ledger data (state merkle root reference) could diverge from the correct VM result while `ensure_match_transaction_info` reports success. The code comment itself flags this as capable of causing "replay-verify tooling... to report a successful replay even when the authenticated position state root diverges from local execution," which is a direct admission of a broken proof/commitment invariant in a security-relevant checking function.

### Likelihood Explanation
This requires local execution to actually produce a different checkpoint hash than what's on ledger while write set/events/status/gas coincidentally match, which for organic bugs (e.g., correct writes but different state root) is a plausible outcome. It is gated behind `TRANSACTION_INFO_V1` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flags for the hot-state/position roots, and for the plain `state_checkpoint_hash` field it's a permanent condition unrelated to any feature flag. The severity depends on whether other layers (e.g. the accumulator proof check itself, or a separate SMT recomputation-and-compare elsewhere in the chunk executor) independently re-verify the checkpoint hash — I could not fully confirm from the retrieved code whether such an independent check exists elsewhere in `execution/executor/src/chunk_executor/mod.rs`, since I was only able to see matches for the pattern, not full surrounding logic, before running out of investigation budget.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (when present in `txn_info`) against the locally recomputed values, mirroring how `write_set_hash` and `event_root_hash` are already checked, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` as the code comment itself recommends.

### Proof of Concept
Not independently exploitable purely from the retrieved code snippets without confirming the absence of an out-of-band checkpoint-hash check elsewhere in `execution/executor/src/chunk_executor/mod.rs`; the code's own TODO comment at [5](#0-4)  is the strongest available evidence that this gap exists and is acknowledged but unresolved.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
