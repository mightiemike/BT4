## Finding

### Title
Replay-verify accepts a diverging world-state root because `TransactionOutput::ensure_match_transaction_info` never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness check used by `db-tool`'s replay-verify, `aptos-debugger`, and the Move `cli` to confirm that a freshly re-executed transaction matches the archived, authenticated `TransactionInfo` for that version. It validates status, gas, the write-set hash (`state_change_hash`) and the event root, but it never compares the freshly computed world-state Merkle root against `txn_info.state_checkpoint_hash()` (or `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`). This is admitted directly in the code by the `TODO(trading-native)` comment. As a result, a chunk whose accumulated global state diverges from the correct VM result — while individual per-transaction write-set/event hashes still match — is reported as a successful, verified replay.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  performs four checks: transaction status, gas used, write-set hash against `state_change_hash`, and event root hash. It explicitly does not validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, which is called out by its own comment: [2](#0-1) 

This function is the only correctness gate used by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` per transaction to decide whether the replay "passed": [3](#0-2) 

Note that `execute_block` here is invoked directly on the VM executor, not through the full `do_state_checkpoint`/`do_ledger_update` executor pipeline that would otherwise recompute and cross-check `state_checkpoint_hash` against `known_state_checkpoints`. `do_state_checkpoint::get_state_checkpoint_hashes` does perform that comparison, but only inside the normal execution pipeline, not inside the replay-verify tool's direct-VM-execution + `ensure_match_transaction_info` path: [4](#0-3) 

`state_checkpoint_hash` is the periodic Sparse-Merkle-Tree/Jellyfish-Merkle-Tree root summarizing the entire world state at a checkpoint (typically end of block) — a different (and much larger, cumulative) commitment than the single-transaction `state_change_hash` (hash of that transaction's own write set) that is checked: [5](#0-4) 

Because per-transaction write-set hashes only prove that one transaction's own write set is correct, they cannot catch bugs in how those writes are folded into the global JMT/SMT (e.g. a stale-index bug, hot-state tracking bug, incorrect base-state resolution, or an intentionally corrupted archive substituting a different but hash-preserving write blob at some other key). Such divergences are precisely what `state_checkpoint_hash` is designed to catch, and precisely what replay-verify's stated purpose is meant to detect — yet the check is silently skipped in this tool.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... accepted as valid" invariant for the archive replay-verification tool: `db-tool replay-verify` (and any downstream automation gating archive integrity, node bootstrap validation, or governance decisions on "replay-verify passed") can report full success for a version range whose real world-state root diverges from the correct VM execution result, as long as per-transaction write-set/event hashes happen to still match. This directly undermines a tool whose entire purpose is proof/commitment integrity verification of ledger data, and could mask corruption or non-determinism bugs in the JMT/hot-state/position-state commitment pipeline that would otherwise cause a hard fork.

### Likelihood Explanation
No malicious/privileged actor is required to trigger the check to be skipped — it's a straightforward code-review-provable gap that always applies for every call, unconditionally (the check for `state_checkpoint_hash`/`hot_state_checkpoint_hash` is not feature-gated; the TODO comment only frames it in terms of the newer `position_state_checkpoint_hash`, but the same missing checks apply to the long-standing `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields as well). Any scenario where per-transaction hashes coincidentally match but global-state folding diverges (a JMT/hot-state bug, or a crafted/corrupted backup archive) will silently pass this verifier.

### Recommendation
In `ensure_match_transaction_info`, when the transaction is a state checkpoint (`txn_info.has_state_checkpoint_hash()`), recompute the accumulated world-state root (and hot-state/position-state roots where applicable) and assert equality with `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, mirroring the check already performed in `do_state_checkpoint::get_state_checkpoint_hashes`. Since `replay_on_archive.rs` bypasses the full executor pipeline, it will need to plumb through (or reconstruct) the state-checkpoint output so this comparison can happen before declaring a chunk "verified".

### Proof of Concept
Not applicable as a runnable PoC (this is a missing-check finding in a verification tool, not an exploitable state transition). The gap is directly demonstrable by inspection: [1](#0-0)  never reads `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` from `self`/`txn_info`, and its only caller performing archive verification, [6](#0-5) , treats a passing `ensure_match_transaction_info` call as proof the chunk replayed correctly.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
