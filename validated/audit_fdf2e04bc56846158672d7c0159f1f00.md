### Title
Missing vote-only-bank enforcement in `process_and_record_aged_transactions()` allows non-vote transactions to be committed during vote-only mode - (File: core/src/banking_stage/consumer.rs)

### Summary
`Consumer::process_and_record_transactions` re-validates every transaction against `bank.vote_only_bank()` immediately before scheduling for execution, rejecting any non-vote transaction with `TransactionError::SanitizeFailure` if the bank has entered vote-only mode. `Consumer::process_and_record_aged_transactions`, which is the actual production path used by both the internal `ConsumeWorker::consume` (central scheduler) and the external `ExternalWorker::execute_batch`/`check_batch`, does not perform this re-check at all, mirroring the "batch path missing single-path logic" bug class from the referenced report.

### Finding Description
`process_and_record_transactions` (core/src/banking_stage/consumer.rs:126-153) builds its `check_results` and explicitly filters non-vote transactions when the bank is in vote-only mode: [1](#0-0) 

In contrast, `process_and_record_aged_transactions` (core/src/banking_stage/consumer.rs:173-191), which is the function actually invoked by the leader's consume workers (`ConsumeWorker::consume` at core/src/banking_stage/consume_worker.rs:105-131, and `ExternalWorker::execute_batch` at core/src/banking_stage/consume_worker.rs:360-458), only calls `bank.resanitize_transaction_minimally(...)` for epoch/ALT validity — it contains no `bank.vote_only_bank()` check whatsoever: [2](#0-1) 

Both functions funnel into the same `process_and_record_transactions_with_pre_results` (core/src/banking_stage/consumer.rs:193-257), which locks accounts and executes/commits the transaction based solely on the `pre_results` passed in.

The only other place a vote-only-mode filter exists on the ingestion side is `translate_to_runtime_view` in `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs:139`, which checks `bank.vote_only_bank() && !view.is_simple_vote_transaction()` against the **root bank** at packet-ingestion/precheck time: [3](#0-2) 

This is a time-of-check-to-time-of-use gap: a non-vote transaction is admitted into the scheduler's pending container when the working bank was not yet in vote-only mode (or was checked against a lagging root bank). By the time the transaction is actually dequeued and executed via `process_and_record_aged_transactions` against the current (possibly now vote-only) working bank, there is no re-check, so the transaction is executed and committed as a normal transaction — bypassing the vote-only-mode restriction entirely.

### Impact Explanation
`vote_only_bank` is a consensus-safety mechanism used to restrict block production to only vote transactions (e.g., during partition/duplicate-block recovery scenarios) so that the cluster can continue to make forward progress on consensus without arbitrary user transactions being included. If the enforcement can be bypassed for transactions already buffered before the mode flip (or admitted through the root-bank precheck window), a leader could commit non-vote user transactions into a block that is supposed to contain vote transactions only. This undermines the safety guarantee vote-only mode is meant to provide and can affect cluster recovery/consensus behavior — a bank/consensus-state correctness issue, not merely a cosmetic inconsistency.

### Likelihood Explanation
Likelihood is bounded by the narrow window in which `vote_only_bank()` transitions to `true` while transactions are already staged in the scheduler's container (ingested/pre-validated against a bank not yet in vote-only mode). This requires precise timing around the mode transition, so it is not trivially triggerable by an arbitrary client on demand, but it is a legitimate reachable path for an ordinary client's already-broadcast transaction to slip through once vote-only mode activates, without any special privilege needed from the sender.

### Recommendation
Add the same `bank.vote_only_bank() && !vote_parser::is_valid_vote_only_transaction(tx)` (or the `is_simple_vote_transaction` equivalent) check inside `process_and_record_aged_transactions`, evaluated against the *current working bank* immediately before generating `pre_results`, so that vote-only-mode is enforced consistently at commit time regardless of which Consumer entry point processed the transaction.

### Proof of Concept
Conceptual PoC (cannot be executed without a live cluster/test harness in this context):
1. Buffer a non-vote transaction via the scheduler’s `receive_and_buffer` path while the working/root bank is not in vote-only mode; it passes `translate_to_runtime_view`’s vote-only check and is placed in the pending container with a `MaxAge`.
2. Trigger the bank to enter vote-only mode (`bank.vote_only_bank()` becomes `true`) before the transaction is dequeued for execution.
3. The scheduler dispatches the transaction to a `ConsumeWorker`/`ExternalWorker`, which calls `Consumer::process_and_record_aged_transactions` (core/src/banking_stage/consumer.rs:173-191) against the now-vote-only working bank.
4. Because `process_and_record_aged_transactions` never checks `bank.vote_only_bank()`, the non-vote transaction proceeds through `process_and_record_transactions_with_pre_results`, is locked, executed, and committed into the block — violating the vote-only-mode invariant that `process_and_record_transactions` enforces for its own callers.

    pub fn process_and_record_aged_transactions(
        &self,
        bank: &Bank,
        txs: &[impl TransactionWithMeta],
        max_ages: &[MaxAge],
        flags: &ExecutionFlags,
    ) -> ProcessTransactionBatchOutput {
        // Need to filter out transactions since they were sanitized earlier.
        // This means that the transaction may cross and epoch boundary (not allowed),
        //  or account lookup tables may have been closed.
        let pre_results = txs.iter().zip(max_ages).map(|(tx, max_age)| {
            bank.resanitize_transaction_minimally(
                tx,
                max_age.sanitized_epoch,
                max_age.alt_invalidation_slot,
            )
        });
        self.process_and_record_transactions_with_pre_results(bank, txs, pre_results, flags)
    }
