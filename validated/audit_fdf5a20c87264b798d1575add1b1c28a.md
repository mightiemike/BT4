### Title
Meta-Transaction Deposit Refund Misdirection Allows Sender to Steal Relayer's Deposited NEAR — (`File: runtime/runtime/src/actions.rs`)

### Summary

In nearcore's meta-transaction (NEP-366) implementation, when a `DelegateAction` inner receipt fails execution on the receiver's shard, the attached deposit is refunded to the **sender** (Alice), not the **relayer** who actually paid it. An unprivileged sender can deliberately craft a `DelegateAction` with a large deposit that will fail, causing the relayer to lose the deposited NEAR while the sender gains it.

### Finding Description

`apply_delegate_action` constructs the inner receipt with `predecessor_id: sender_id.clone()` (Alice), not the relayer: [1](#0-0) 

The relayer's balance is debited for the full deposit when the outer transaction is converted to a receipt. However, when the inner receipt fails on Bob's shard, `refund_unspent_gas_and_deposits` issues a deposit refund to `receipt.balance_refund_receiver()`: [2](#0-1) 

`balance_refund_receiver()` returns `predecessor_id` of the inner receipt — which is Alice, not the relayer: [3](#0-2) 

The code comment in `apply_delegate_action` itself acknowledges the broken invariant: [4](#0-3) 

The `DelegateAction` struct carries the deposit inside its inner actions (e.g., a `Transfer`), and the relayer pays this deposit at transaction-processing time. The nonce is consumed and the relayer's balance is debited before the inner receipt ever executes: [5](#0-4) 

### Impact Explanation

**Broken invariant**: The entity that pays the deposit (relayer) is not the entity that receives the deposit refund (sender/Alice).

**Attack flow**:
1. Alice signs a `DelegateAction` containing a `FunctionCall` with a large deposit `D` targeting a contract she controls (or any contract she can cause to panic).
2. The relayer verifies the action off-chain, sees the deposit, and submits the outer transaction — paying `D` from its own balance.
3. Alice's contract deliberately panics (or Alice changes contract state between relayer verification and execution to cause failure).
4. The inner receipt fails on Bob's shard. `refund_unspent_gas_and_deposits` sends `D` NEAR to Alice (the `predecessor_id` of the inner receipt).
5. The relayer loses `D` NEAR; Alice gains `D` NEAR net of gas costs.

The deposit `D` is bounded only by the relayer's balance. Gas refunds correctly return to the relayer (via `signer_id`), but the deposit refund is permanently misdirected to Alice. [6](#0-5) 

### Likelihood Explanation

- **Trigger**: Any user who can sign a `DelegateAction` (all NEAR accounts). No special privilege required.
- **Precondition**: A relayer must be willing to submit the action. Relayers that accept arbitrary `DelegateAction`s from untrusted users are fully exposed.
- **Detectability**: The relayer cannot fully prevent this by pre-simulating, because Alice can change contract state (e.g., via a separate transaction) between the relayer's simulation and the actual execution. The attack is race-condition-free if Alice controls the target contract.
- **Repeatability**: Alice can repeat this with fresh nonces and fresh `DelegateAction`s indefinitely, draining a relayer's balance.

### Recommendation

1. **Protocol-level fix**: Change `apply_delegate_action` to set `predecessor_id` of the inner receipt to the relayer's account ID (the outer receipt's `signer_id`) rather than `sender_id`, so deposit refunds return to the party that paid them. Alternatively, introduce an `ActionReceiptV2`-style `refund_to` field on the inner receipt pointing to the relayer.

2. **Interim mitigation**: Relayers should treat any `DelegateAction` containing a non-zero deposit as high-risk unless they have a trust relationship with the sender, or they use a pre-execution simulation that accounts for possible state changes.

### Proof of Concept

```
1. Alice deploys a contract on `bob.near` that panics on any call.
2. Alice signs:
   DelegateAction {
     sender_id: "alice.near",
     receiver_id: "bob.near",
     actions: [FunctionCall { method: "any", deposit: 100 NEAR, gas: 10 TGas }],
     nonce: current_ak_nonce + 1,
     max_block_height: current + 100,
     public_key: alice_key,
   }
3. Alice sends the SignedDelegateAction to a relayer.
4. Relayer submits: SignedTransaction { signer: relayer, receiver: alice.near,
     actions: [Delegate(signed_delegate_action)] }
   → Relayer's balance is debited 100 NEAR (deposit) + gas.
5. Inner receipt reaches bob.near, contract panics → receipt fails.
6. refund_unspent_gas_and_deposits issues Receipt::new_balance_refund(
     alice.near,   // predecessor_id of inner receipt
     100 NEAR
   )
7. Alice receives 100 NEAR. Relayer lost 100 NEAR.
```

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
