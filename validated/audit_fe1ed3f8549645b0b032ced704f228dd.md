Based on the code paths examined, this is a real, exploitable divergence between the ZK-proof-verified value balance and the actual pool accounting applied at execution time.

### Title
Fee recalculation after proof caching causes `totalShieldedPoolValue` to diverge from the cryptographically-verified `valueBalance` - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
`ShieldedTransferActuator.checkProof()` verifies the Sapling binding signature against `valueBalance = toAmount - fromAmount + fee`, where `fee` comes from `calcFee()`, and caches the verification result keyed only by transaction ID via `ZKProofStore` [1](#0-0) . Because `calcFee()` depends on mutable chain state (whether `transparentToAddress` already exists as an account) [2](#0-1) , and `execute()` independently recomputes `fee` from current state without ever re-running the cryptographic check [3](#0-2) , the `fee` used in the cached proof verification can differ from the `fee` used to actually adjust `totalShieldedPoolValue`.

### Finding Description
`checkProof()` computes `valueBalance = addExact(subtractExact(toAmount, fromAmount), fee)` and uses it both for the SNARK binding-signature check (`librustzcashSaplingFinalCheck`) and for a preliminary `totalShieldedPoolValue` sanity check, but this whole block is skipped on subsequent calls if `proofStore.has(txId)` is already true [4](#0-3) [5](#0-4) .

`calcFee()` returns `getShieldedTransactionCreateAccountFee()` if the `transparentToAddress` account does not yet exist, otherwise `getShieldedTransactionFee()` [2](#0-1) . This value is recomputed independently in `validate()` (line 223) and again in `execute()` (line 73), each time reflecting the *current* account-existence state rather than the state at proof-generation time.

`execute()` never re-invokes `checkProof`/`librustzcashSaplingFinalCheck`; it simply reuses whatever `fee` it computes at that moment for the blackhole fee credit and for `Commons.adjustTotalShieldedPoolValue` [6](#0-5) , which decrements `totalShieldedPoolValue` via `Commons.adjustTotalShieldedPoolValue` [7](#0-6) .

Exploit flow: an attacker submits a `ShieldedTransferContract` with `transparentToAddress = X` where `X` does not yet exist, computing spend/output notes and the binding signature so that `valueBalance = toAmount - fromAmount + createAccountFee` is cryptographically correct. The transaction is validated once (e.g. accepted into the mempool) while `X` still doesn't exist; `checkProof` succeeds with the higher `createAccountFee` and the result `true` is permanently cached in `ZKProofStore`. Before this transaction is packed into a block, another transaction (attacker-controlled or organic) creates account `X` (e.g. any TRX/TRC10 transfer to `X`). When the shielded transaction is later processed for block application, `validate()` re-runs `calcFee()`, now returning the lower regular fee, but `checkProof()` short-circuits on the cache and never re-verifies the binding signature against this new fee. `execute()` then uses the lower fee for both the blackhole credit and `adjustTotalShieldedPoolValue`, which is inconsistent with the `valueBalance` that was actually cryptographically proven (using the higher fee). This causes `totalShieldedPoolValue` to be decremented by less than the value truly leaving the pool as guaranteed by the SNARK, silently inflating the recorded pool value relative to the true aggregate note value it is supposed to bound.

No existing guard prevents this: `validateTransparent` only checks non-negativity/balance/overflow of `fromAmount`/`toAmount`/`fee` [8](#0-7) , and there is no re-verification of the proof against the fee actually applied in `execute()`.

### Impact Explanation
`totalShieldedPoolValue` is a chain-wide invariant intended to bound how much value can ever be withdrawn from the shielded pool to the transparent side (guarded by the `< 0` check in `adjustTotalShieldedPoolValue`) [7](#0-6) . If it becomes inflated relative to the true cryptographically-backed note value (because less was subtracted than the SNARK actually proved left the pool), the guard rail no longer accurately reflects real backing, permanently corrupting a global invariant used to protect all shielded-pool participants, not just the attacker's own funds.

### Likelihood Explanation
Exploitability requires: (1) the attacker's shielded transaction targets a not-yet-existing `transparentToAddress`; (2) it gets validated/cached once while that address doesn't exist; (3) some transaction creates that address before the shielded transaction is actually applied in a block. Step 3 is trivially achievable by the attacker themselves (submit a cheap transfer to the same address) or can happen organically. This is fully repeatable and requires no privileged access, only ordinary transaction submission — a real, unprivileged attack surface.

### Recommendation
Re-verify (or recompute and re-check) the binding-signature/valueBalance relationship in `execute()` using the fee actually applied there, or make `calcFee()` deterministic/pinned at first validation (e.g., store the fee alongside the cached proof result in `ZKProofStore` and reuse that exact fee in `execute()` instead of recalculating it from current account-existence state).

### Proof of Concept
Integration test plan (extends `ShieldedTransferActuatorTest`):
1. Build a `ShieldedTransferContract` with `transparentToAddress = X` (not existing), `toAmount`, computing a valid binding signature assuming `createAccountFee`.
2. Call `actuator.validate()` — assert it succeeds and `ZKProofStore` now caches `true` for this tx id.
3. Manually create account `X` in `AccountStore` (simulating an intervening transaction in the block).
4. Call `actuator.validate()` again (simulating block-application re-validation) — assert `calcFee()`/`checkProof` returns early via cache without exception.
5. Call `actuator.execute(ret)` — record `dynamicStore.getTotalShieldedPoolValue()` before and after.
6. Assert that the actual decrement equals `toAmount - fromAmount + regularFee` (execute's fee) rather than `toAmount - fromAmount + createAccountFee` (the fee actually verified by the SNARK), demonstrating the recorded pool value no longer matches the cryptographically-attested `valueBalance`.

  private long calcFee(ShieldedTransferContract shieldedTransferContract) {
    byte[] toAddress = shieldedTransferContract.getTransparentToAddress().toByteArray();
    boolean hasTransparentTo = (toAddress.length > 0);
    if (hasTransparentTo) {
      AccountCapsule toAccount = chainBaseManager.getAccountStore().get(toAddress);
      if (toAccount == null) {
        return chainBaseManager.getDynamicPropertiesStore()
            .getShieldedTransactionCreateAccountFee();

  public static void adjustTotalShieldedPoolValue(long valueBalance,
      DynamicPropertiesStore dynamicPropertiesStore) throws BalanceInsufficientException {
    long totalShieldedPoolValue = subtractExact(
        dynamicPropertiesStore.getTotalShieldedPoolValue(), valueBalance,
        dynamicPropertiesStore.disableJavaLangMath());
    if (totalShieldedPoolValue < 0) {
      throw new BalanceInsufficientException(String.format(
          "total shielded pool value can not below 0, actual: %d", totalShieldedPoolValue));
    }
    dynamicPropertiesStore.saveTotalShieldedPoolValue(totalShieldedPoolValue);
