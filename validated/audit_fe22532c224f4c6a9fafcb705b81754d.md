### Title
Excess attached deposit from an unprivileged caller of `rlp_execute` is never refunded on success, permanently absorbed by the Wallet Contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `zappers_leverage_exchange_leftovers` report's core bug class — a contract accepting more value than an operation actually needs, and never sweeping the leftover back to the caller — has a direct analog in the NEAR Wallet Contract's `rlp_execute` entry point. An unprivileged, unauthorized (non-relayer-key) caller can attach a `CallerDeposit` to cover the NEAR cost of a cross-contract action executed on behalf of an eth‑implicit account. The refund path only triggers when the downstream promise **fails**; on success, any unused/excess portion of the attached deposit is never returned and becomes part of the wallet contract's own balance.

### Finding Description
`rlp_execute` is `#[payable]`, so any account (the report's "unprivileged transaction signer" / "RPC caller") can attach an arbitrary NEAR deposit when submitting a signed Ethereum transaction for a wallet contract to relay: [1](#0-0) 

Internally, `inner_rlp_execute` captures this attachment as `CallerDeposit` via `CallerDeposit::new(&context)`, and this value is threaded through every callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`): [2](#0-1) 

The only place that ever moves the `caller_deposit` back to the caller is on a **failed** promise result: [3](#0-2) 

On the success branch of `rlp_execute_callback`, `caller_deposit` is dropped entirely — no comparison is made between the amount the caller attached and the amount the underlying action (`action_to_promise`, `FunctionCall`/`Transfer` deposit, `storage_deposit`, etc.) actually required. Because `attached_deposit` on a `#[payable]` call is credited into the receiving account's balance *before* execution begins (per the documented NEAR economics model), any amount beyond what the inner action consumes is permanently retained by the wallet contract account rather than returned to the caller who supplied it: [4](#0-3) 

The existing test suite explicitly demonstrates this asymmetry: a refund occurs when the cross-contract call fails, but "External caller does not get a refund when their tokens are spent" even though the assertion only requires the loss to be `>= deposit_amount` — i.e. the code never checks for or handles overpayment: [5](#0-4) 

### Impact Explanation
Any unprivileged external caller (not holding the wallet's Ethereum-style access key) who relays a transaction and attaches more NEAR than strictly necessary for the inner action to succeed loses the excess permanently — it becomes indistinguishable wallet-account balance with no path to recovery, since only the failure path issues a refund. This is a concrete, protocol-level value-movement defect reachable directly from a single RPC-submitted, unauthorized transaction (no privileged role required), matching the "missing sweep" bug class in the source report where overpayment sent to a contract silently becomes unrecoverable/misappropriated.

### Likelihood Explanation
The mechanism is triggered by ordinary use of `rlp_execute` by any caller who does not precisely calculate the minimal deposit needed for the inner action (e.g., attaching a safety margin, or in flows like NEP‑141 `storage_deposit` + `ft_transfer` bundling where the exact combined cost is non-trivial to compute off-chain). Given that `rlp_execute` is explicitly designed to be callable by third parties without an access key (see `test_caller_refunds`), overpayment is a realistic and easily reachable scenario, not a contrived edge case.

### Recommendation
In `rlp_execute_callback` (and equivalently in the `Failed` branch, which already does this correctly), compare the actual deposit consumed by the executed action against the recorded `CallerDeposit` amount, and refund any positive difference back to `caller_deposit.account_id` on the success path as well — mirroring the fix recommended in the source report ("missing sweeps"). At minimum, document/require that `caller_deposit` must equal the amount consumed exactly and reject calls where attached deposit exceeds what will be used, to avoid silent value loss.

### Proof of Concept
1. An external account (not the wallet's registered relayer key) calls `rlp_execute` on a deployed Wallet Contract instance, attaching, say, 3 NEAR (`deposit_amount`) alongside a validly signed Ethereum transaction whose emulated action (e.g., a `FunctionCall`/NEP-141 transfer requiring `storage_deposit`) only actually needs 1.25 NEAR (`NEP_141_STORAGE_DEPOSIT_AMOUNT`, see [6](#0-5) ) plus whatever deposit is included in the underlying `FunctionCall` action.
2. The action succeeds; `rlp_execute_callback` hits the `PromiseResult::Successful` branch (`lib.rs:313-315`), which does nothing with `caller_deposit`.
3. The excess NEAR (attached deposit minus what was actually consumed by the promise chain) remains permanently as part of the wallet contract account's balance; the external caller has no way to reclaim it.
4. This is directly confirmed by the existing `test_caller_refunds` test, whose second scenario asserts the caller's balance decreases by *at least* the full `deposit_amount` on success, with no refund logic invoked ( [7](#0-6) ).

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
