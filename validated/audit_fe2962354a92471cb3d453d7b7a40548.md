### Title
Stale cached `cycle-total-weight` denominator vs. freshly-read per-signer weight numerator in aggregate-key voting threshold - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
`signers-voting.clar` computes the DKG/aggregate-public-key vote threshold as `(signer-weight-so-far) >= (threshold-consensus% of cached total-weight)`. The denominator (`cycle-total-weight`) is memoized the *first* time any signer votes in a reward cycle, via `get-and-cache-total-weight`, while the numerator contributions (`get-signer-weight`) are read fresh, per vote, from `.signers`' `cycle-signer-set` map. If the `.signers` weight table for that reward cycle can be (re-)written after the cache is populated but before voting concludes, the percentage-of-total check is evaluated against two different snapshots of the signer-weight distribution — an equality (numerator/denominator consistency) that the vault bug report's "amount deposited == amount received" analog also depends on.

### Finding Description
`get-and-cache-total-weight` in `signers-voting.clar` caches `cycle-total-weight` on first use: [1](#0-0) 

`get-threshold-weight` derives the pass/fail bar purely from that cached value: [2](#0-1) 

Meanwhile, each vote's *weight contribution* is fetched live from `.signers` for the caller's `signer-index`, not from any cached snapshot: [3](#0-2) 

`vote-for-aggregate-public-key` combines these two independently-sourced values — a per-vote fresh numerator and a cycle-scoped cached denominator — to decide whether the 70% threshold is reached: [4](#0-3) 

The `.signers` boot contract's `cycle-signer-set` map is populated by `set-signers`, which is invoked from `update_signers` in the Rust boot-contract machinery every time a signer-set computation is (re-)run for a given reward cycle: [5](#0-4) 

For PoX-5, this computation is called `pox_5_compute_and_update_signers`, which recomputes `signer_set`/weights from PoX-5 stake entries via `pox_5_make_signer_set` and calls `update_signers` (→ `set-signers`) with the new weights: [6](#0-5) 

The `.signers` contract's own guard only checks that `set-signers` is called for the currently "last-set" cycle — it does not forbid the weight table for a given `reward-cycle` from being overwritten more than once, and there is no coupling between this rewrite and the cached `cycle-total-weight` in `signers-voting.clar`: [7](#0-6) 

If the underlying stake distribution used to build the signer set is recalculated (the codebase explicitly names this a "waterfall" reward-set mechanism, i.e. progressive/repeated computation as more stacking commitments accrue before the reward-cycle boundary, exercised in `epoch_4_0_waterfall.rs` and `pox_5_compute_and_update_signers`), a signer's on-chain weight for the reward cycle can change between the moment `cycle-total-weight` was first cached (triggered by any signer's first vote) and the moment later signers cast their votes. Because `get-signer-weight` always reads the *current* `.signers` weight, while the threshold denominator is frozen at the first-vote snapshot, the arithmetic `sum(signer-weight at read time) >= 70% * cached-total-weight` no longer represents a consistent 70%-of-actual-current-weight check. This is structurally the same class of bug as the reported vault issue: an accounting equality (`amount transferred == amount received`, here `sum of live per-signer weights == 70% of the live total weight`) silently breaks because one side of the equation is read at a different, stale point in time than the other, due to a dynamically-changing underlying "balance" (signer stake weight) that the code assumed was static once cached.

### Impact Explanation
If a later signer-set recomputation *reduces* total weight relative to what was cached, a minority of the (updated, smaller) live signer set could accumulate votes whose live weights sum to ≥ 70% of the larger, stale cached total less easily (harder, not a vulnerability by itself). Conversely, if the later recomputation *increases* total weight (e.g., additional stakers/keys added in a later waterfall round) while the cache still reflects the earlier, smaller total, then a genuinely minority-weighted subset of the *current* signer set (by true, current total weight) could push `new-total >= threshold-weight` computed against the stale, smaller cached total — approving an aggregate DKG public key without truly holding 70% of the real, current signer weight. This is a minority-triggerable divergence in a threshold-based validation check confined to the `signers-voting` boot contract's aggregate-key approval, which downstream feeds `.signers`/aggregate-key consumers (e.g., sBTC deposit key derivation in the PoX-5 waterfall path). It does not by itself cause chain-split or fund loss beyond whatever relies on the approved aggregate key, bounding it to a High-severity static-validation/threshold divergence rather than a Critical chain split.

### Likelihood Explanation
Likelihood depends on whether the boot-contract-calculation code actually re-runs `pox_5_compute_and_update_signers` (and thus `set-signers`) more than once for the *same* reward cycle before voting for that cycle finishes, and whether `signers-voting.clar`'s cache can therefore go stale relative to a later overwrite. I was not able to fully verify, within the available tool budget, the exact number and timing of `.signers` weight-table (re)writes per reward cycle relative to the DKG voting window in the "waterfall" flow — the grep for a recompute trigger only surfaced test/contract references without pinning down the call site and cadence of `pox_5_compute_and_update_signers` relative to `is-in-voting-window`. This is an important open question that materially affects likelihood, and it should be confirmed against the actual Rust coordinator/boot-contract invocation flow.

### Recommendation
- Recompute (or invalidate) `cycle-total-weight` in `signers-voting.clar` whenever `.signers`' `cycle-signer-set` is rewritten for a given reward cycle, rather than relying on a one-time, vote-triggered cache.
- Alternatively, have `set-signers` explicitly reject overwrites once any vote has been recorded for that reward cycle (mirroring the "amount deposited must equal amount received" fix pattern: freeze the input the moment accounting begins).
- Add an invariant test asserting that `get-threshold-weight` for a reward cycle always equals `70%` of the *current* (not first-cached) `.signers` total weight for that cycle throughout the voting window.

### Proof of Concept
Conceptual sequence (subject to confirming the exact `pox_5_compute_and_update_signers` call cadence noted above):
1. At prepare-phase height H1, the node computes an initial PoX-5/waterfall signer set for cycle N with total weight W1 and writes it via `update_signers`/`set-signers`.
2. Signer A casts the first `vote-for-aggregate-public-key` for cycle N; `get-and-cache-total-weight` caches `cycle-total-weight[N] = W1`.
3. At a later height H2 (still before voting concludes for cycle N), the node recomputes the PoX-5 signer set (waterfall) because new stacking commitments were observed, producing a new signer set with total weight W2 > W1, again via `set-signers` for the same `reward-cycle: N`.
4. A minority of the *new* (W2-weighted) signer set — whose combined live weight is < 70% of W2 but ≥ 70% of the stale cached W1 — votes and calls `get-signer-weight`, which returns each voter's *current* (post-recompute) weight.
5. `new-total >= threshold-weight` (computed from cached W1) is satisfied even though the voters do not hold 70% of the true, current total signer weight W2, and the aggregate public key is approved.

        ;; Update used aggregate public keys
        (map-set used-aggregate-public-keys key reward-cycle)

            event: "voted",
            signer: tx-sender,
            reward-cycle: reward-cycle,
            round: round,

            new-total: new-total,

                        key: key,
