### Title
BAL parallel-execution gas-admission check can diverge from serial `EthBlockExecutor` block gas admission, letting the parallel path reach a different accept/reject verdict than serial execution - (File: `crates/engine/tree/src/tree/payload_processor/bal/execute.rs`)

### Summary
The BAL (Block Access List) parallel execution path in `execute_block_inner` uses a hand-written `BlockGasTracker::validate_tx_limit` to *replay* the block-gas admission check that the canonical/serial executor normally performs inside `execute_transaction_without_commit`/`execute_transaction_with_result_closure` before committing a transaction. The workers that actually run the transactions never call that entry point — they call `execute_transaction_without_commit` directly per-worker without any block-level gas budget context (see `worker.rs`) — and the canonical loop commits their pre-computed results via `commit_transaction` after the fact, then separately calls `gas_tracker.validate_tx_limit`. This is a second, independently maintained implementation of the same admission rule that the real serial `BlockExecutor` enforces, and the code's own comments acknowledge this is a deliberately reconstructed mirror ("Mirrors `EthBlockExecutor`'s gas admission checks", "The commit loop never calls that entry point ... so the check must be replayed here for BAL and serial execution to reach the same block validity verdict").

### Finding Description
`execute_block_inner` in `crates/engine/tree/src/tree/payload_processor/bal/execute.rs` runs two parallel data paths over the same parent state, analogous to the `BunniQuoter` bug pattern where a "shadow"/simulated execution path is supposed to mirror the real path's checks but only calls back a subset of them:

1. Worker threads (`worker.rs::spawn_worker`) speculatively execute each transaction with `executor.execute_transaction_without_commit(tx)`, with no block-gas-budget awareness at all — they only know the transaction's own gas limit.
2. The canonical committing loop in `execute_block_inner` (lines 140-166) re-implements block gas admission logic in `BlockGasTracker::validate_tx_limit` (lines 267-314), which is explicitly commented as mirroring `EthBlockExecutor::execute_transaction_without_commit`'s pre-execution admission check for both the pre-Amsterdam single-budget rule and the post-Amsterdam (EIP-8037) dual regular/state gas-lane rule.

Because this is a duplicated implementation rather than a shared call into the same code path the serial executor uses, any drift between `BlockGasTracker::validate_tx_limit`'s logic and the real admission check performed by the canonical `EthBlockExecutor` (e.g., a future change to the EIP-8037 dual-lane logic, tx_gas_limit_cap handling, or ordering semantics that is updated in one place but not the other) breaks the equality that "BAL parallel execution and serial execution must reach the same block validity verdict" — exactly the class of bug flagged in the report, where a quoting/shadow path fails to call all the hooks/checks the authoritative path calls, producing an inaccurate result relative to ground truth. ### Impact Explanation
If the two implementations diverge (which is only prevented by manual code-review discipline, not by sharing a single source of truth), the BAL parallel path could accept a block as valid that the canonical serial path would reject, or vice versa. That is a non-deterministic-output-between-parallel-and-serial-paths class defect explicitly listed as in-scope impact ("non-deterministic execution between cached/prewarmed/JIT/parallel and serial paths"), which can manifest as a wrong accept/reject verdict on a block depending on which execution path a given node takes for that block — a consensus-relevant divergence.

### Likelihood Explanation
Today the two implementations appear consistent (both apply the pre-Amsterdam single-budget check and the EIP-8037 dual-lane check with the same `tx_gas_limit_cap` semantics), so under current code there is no live divergence I could confirm. The risk is structural: because the check is duplicated rather than unified, any future modification to `EthBlockExecutor`'s admission logic that isn't mirrored into `BlockGasTracker::validate_tx_limit` will silently reintroduce the divergence, and nothing in the type system or tests forces the two to stay in lockstep beyond the one-off unit test `rejects_tx_gas_limit_that_exceeds_remaining_block_gas`.

### Recommendation
Refactor so the BAL parallel-canonical commit loop calls the same shared gas-admission primitive that `EthBlockExecutor` uses (e.g., extract the admission check into a single function/trait method in `reth-evm`/`alloy-evm` block execution code and have both the serial executor and `BlockGasTracker` call it), rather than maintaining a second hand-written copy of the rule in the engine-tree crate. This removes the possibility of drift and matches the report's recommendation of ensuring the "quote"/shadow path always invokes the exact same logic as the authoritative path instead of an approximated re-implementation.

### Proof of Concept
Not directly exploitable today with a single transaction/block, since the two implementations currently match line-for-line. The structural defect is that they are two independently maintained code paths implementing the same consensus-critical predicate; a PoC would require a code change to one side (e.g., updating `EthBlockExecutor`'s handling of `tx_gas_limit_cap` or the EIP-8037 state/regular lane split) without updating `BlockGasTracker::validate_tx_limit`, after which a block crafted to sit exactly on the old/new boundary would be accepted by one execution path (BAL parallel) and rejected by the other (serial), or vice versa.

    /// Verifies that the transaction's gas limit fits the block's remaining gas budget(s): the
    /// admission check `EthBlockExecutor::execute_transaction_without_commit` performs before
    /// executing a transaction.
    ///
    /// The commit loop never calls that entry point — workers execute speculatively and their
    /// results are committed directly via `commit_transaction` — so the check must be replayed
    /// here for BAL and serial execution to reach the same block validity verdict.
    ///
    /// Pre-Amsterdam there is one budget: the tx gas limit, capped by `tx_gas_limit_cap`
    /// (EIP-7825), must fit `block_gas_limit - cumulative_tx_gas_used`.
    ///
    /// Amsterdam (EIP-8037) splits gas into two lanes, each budgeted at `block_gas_limit`:
    /// - regular: the capped tx gas limit must fit the remaining regular budget
    /// - state: the full, uncapped tx gas limit must fit the remaining state budget, since state
    ///   gas is drawn from the reservoir above `tx_gas_limit_cap` (execution-specs
    ///   `check_block_gas_capacity`)
    fn validate_tx_limit(&self, tx_gas_limit: u64) -> Result<(), BlockExecutionError> {
        let block_gas_used = if self.enable_amsterdam_eip8037 {
            self.block_regular_gas_used
        } else {
            self.cumulative_tx_gas_used
        };
        let block_available_gas = self.block_gas_limit.saturating_sub(block_gas_used);
        let tx_min_gas_limit =
            self.tx_gas_limit_cap.map_or(tx_gas_limit, |cap| tx_gas_limit.min(cap));

        if tx_min_gas_limit > block_available_gas {
            return Err(BlockValidationError::TransactionGasLimitMoreThanAvailableBlockGas {
                transaction_gas_limit: tx_gas_limit,
                block_available_gas,
            }
            .into());
        }
