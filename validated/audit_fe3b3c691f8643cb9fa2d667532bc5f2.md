I found a concrete analog: the NEAR Wallet Contract's `try_into_near_action` function drops the caller's attached value (transaction `value` field converted into `additional_value`) for `AddKey`/`DeleteKey` actions, mirroring the bug class of "cross-call forwards but drops the value that was supposed to accompany it."

### Title
Wallet Contract silently discards the `tx.value` (attached deposit) when the parsed action is `AddKey` or `DeleteKey`, permanently losing user funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs`)

### Summary
`inner_rlp_execute` computes `additional_value` from the Ethereum transaction's `value` field and passes it into `Action::try_into_near_action(additional_value)` so that it is added to the deposit of the resulting NEAR action [1](#0-0) . However, `try_into_near_action` only folds `additional_value` into the `deposit` field for `FunctionCall` and `Transfer` variants; for `AddKey` and `DeleteKey` it is never used at all [2](#0-1) .

### Finding Description
The wallet contract's `rlp_execute` entrypoint is `#[payable]` and accepts an attached NEAR deposit from the caller [3](#0-2) . Inside `inner_rlp_execute`, the RLP-encoded Ethereum transaction's `value` field is parsed and multiplied into yoctoNEAR terms, then forwarded as `additional_value` to `action.try_into_near_action(additional_value)` [1](#0-0) .

Looking at `try_into_near_action` in `types.rs`, only the `FunctionCall` and `Transfer` match arms add `additional_value` to the resulting deposit:
```rust
Action::FunctionCall { .. } => { deposit: NearToken::from_yoctonear(additional_value.saturating_add(yocto_near.into())), ... }
Action::Transfer { .. } => { deposit: NearToken::from_yoctonear(additional_value.saturating_add(yocto_near.into())), ... }
Action::AddKey { .. } => { ... near_action::Action::AddKey(action) }   // additional_value unused
Action::DeleteKey { .. } => { ... near_action::Action::DeleteKey(action) } // additional_value unused
``` [2](#0-1) 

`near_action::Action::AddKey`/`DeleteKey` (the type ultimately converted into a promise) carry no `deposit`/value field at all [4](#0-3) , and `action_to_promise` only calls `add_access_key_allowance_with_nonce` / `delete_key` on the promise for these variants without ever calling `.transfer(...)` for the value [5](#0-4) .

The `CallerDeposit` refund mechanism (used to protect an *external* caller if the cross-contract call fails) only covers the case where `env::promise_result(0)` is `PromiseResult::Failed` [6](#0-5) . If the AddKey/DeleteKey promise *succeeds* (which it normally will, since these actions do not require any deposit to succeed), the caller's attached deposit that was meant to be carried by `tx.value` is neither transferred anywhere nor refunded — it is simply absorbed into the wallet contract's own balance as leftover balance, with no accounting or entitlement recorded for the original relayer/caller who paid it. This mirrors the reported bug class: the wrapper/router (`inner_rlp_execute`, analogous to `MagnetarV2.sol`) computes a value that is *supposed* to be forwarded to the downstream call, but for a whole class of actions it never reaches the downstream promise, and there's no compensating refund path for the successful case.

### Impact Explanation
This causes an unrecoverable/unintended state: a legitimate value the Ethereum-transaction signer specified (the `value` field, expected to accompany an `AddKey`/`DeleteKey`-shaped call per the Ethereum tx format) is deposited into the wallet contract's account balance instead of being transferred as the user intended, and is not automatically returned to the relayer/caller who attached it once the action succeeds. Since NEAR balances belong to the account and only movable through further explicit actions, this represents a fund-accounting bug rather than complete permanent loss (the account owner could still spend the balance later), but from the perspective of the party that attached the deposit expecting a specific transfer effect, the value is diverted from its intended destination with no protocol-level guarantee of recovery — matching a "broken functionality with financial/value consequence" class of bug analogous to the reported `TOFT_REMOVE_AND_REPAY` missing-value-forwarding issue.

### Likelihood Explanation
Medium-likelihood: it is triggered any time a relayer submits (or a signer signs) an `AddKey`/`DeleteKey` Ethereum-style transaction through `rlp_execute` with a non-zero `value` field. This requires an RLP `AddKey`/`DeleteKey` selector match together with `tx.value != 0`, which is directly reachable by any external caller/relayer submitting a transaction to the wallet contract (no privileged position required) — matching the "unprivileged transaction signer / RPC caller" reachability requirement.

### Recommendation
In `try_into_near_action` (`types.rs`), either (a) reject the transaction (return a `UserError`) whenever `additional_value` is non-zero for `AddKey`/`DeleteKey` actions, forcing the value to be excluded from such Ethereum transactions, or (b) explicitly forward the deposited value as a `Transfer` action (or refund it to the predecessor) alongside the `AddKey`/`DeleteKey` promise so that the attached deposit is not silently absorbed by the contract's own balance.

### Proof of Concept
1. Deploy the wallet contract to an eth-implicit account and give it an owner key.
2. Craft and sign an Ethereum-style transaction whose `data` matches `ADD_KEY_SELECTOR` (or `DELETE_KEY_SELECTOR`) and whose `value` field is non-zero.
3. Submit it via `rlp_execute(target, tx_bytes_b64)` with the relayer/predecessor attaching a NEAR deposit corresponding to that `value` (per `MAX_YOCTO_NEAR` conversion, as in `parse_rlp_tx_to_action` at `internal.rs:159-165`).
4. Observe that the resulting `near_action::Action::AddKey`/`DeleteKey` promise is created without any deposit/transfer of the `value` amount (`lib.rs:484-499`), the action succeeds, and the attached deposit remains in the wallet contract's balance instead of being transferred to the intended recipient or refunded to the caller — with no `CallerDeposit` refund triggered since the promise did not fail (`lib.rs:296-316`).

    pub fn try_into_near_action(
        self,
        additional_value: u128,
    ) -> Result<near_action::Action, Error> {
        let action = match self {
            Action::FunctionCall { receiver_id: _, method_name, args, gas, yocto_near } => {
                let action = FunctionCallAction {
                    method_name,
                    args,
                    gas: Gas::from_gas(gas),
                    deposit: NearToken::from_yoctonear(
                        additional_value.saturating_add(yocto_near.into()),
                    ),
                };
                near_action::Action::FunctionCall(action)
            }
            Action::Transfer { receiver_id: _, yocto_near } => {
                let action = TransferAction {
                    deposit: NearToken::from_yoctonear(
                        additional_value.saturating_add(yocto_near.into()),
                    ),
                };
                near_action::Action::Transfer(action)
            }
            Action::AddKey {
                public_key_kind,
                public_key,
                nonce,
                is_full_access,
                is_limited_allowance,
                allowance,
                receiver_id,
                method_names,
            } => {
                let public_key = construct_public_key(public_key_kind, &public_key)?;
                let access_key = if is_full_access {
                    AccessKey { nonce, permission: AccessKeyPermission::FullAccess }
                } else {
                    let allowance = if is_limited_allowance { Some(allowance) } else { None };
                    AccessKey {
                        nonce,
                        permission: AccessKeyPermission::FunctionCall(FunctionCallPermission {
                            allowance: allowance.map(NearToken::from_yoctonear),
                            receiver_id: receiver_id
                                .parse()
                                .map_err(|_| Error::User(UserError::InvalidAccessKeyAccountId))?,
                            method_names,
                        }),
                    }
                };
                let action = AddKeyAction { public_key, access_key };
                near_action::Action::AddKey(action)
            }
            Action::DeleteKey { public_key_kind, public_key } => {
                let action = DeleteKeyAction {
                    public_key: construct_public_key(public_key_kind, &public_key)?,
                };
                near_action::Action::DeleteKey(action)
            }
        };
        Ok(action)
    }

#[derive(Debug, serde::Deserialize, serde::Serialize)]
pub enum Action {
    FunctionCall(FunctionCallAction),
    Transfer(TransferAction),
    AddKey(AddKeyAction),
    DeleteKey(DeleteKeyAction),
}

impl Action {
    pub fn gas(&self) -> Gas {
        match self {
            Self::FunctionCall(fn_call) => fn_call.gas,
            // 2 Tgas is sufficient for any non-function call action
            Self::Transfer(_) | Self::AddKey(_) | Self::DeleteKey(_) => Gas::from_tgas(2),
        }
    }
}

#[derive(Debug, serde::Deserialize, serde::Serialize)]
pub struct FunctionCallAction {
    pub method_name: String,
    pub args: Vec<u8>,
    pub gas: Gas,
    pub deposit: NearToken,
}

#[derive(Debug, serde::Deserialize, serde::Serialize)]
pub struct TransferAction {
    pub deposit: NearToken,
}

#[derive(Debug, serde::Deserialize, serde::Serialize)]
pub struct AddKeyAction {
