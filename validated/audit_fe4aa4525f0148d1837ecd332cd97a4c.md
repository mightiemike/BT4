### Title
Silent `long` overflow in `ExchangeCapsule.transaction()` reserves update when `AllowHardenExchangeCalculation` is disabled - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The reported Caviar bug is a silent-overflow-on-cast issue: `virtualBaseTokenReserves`/`virtualNftReserves` are updated via unchecked narrowing casts from `uint256` to `uint128`, breaking the `x*y=k` invariant. The java-tron TRC10 Exchange (Bancor-style AMM) module contains a structurally analogous class of bug: `ExchangeCapsule.transaction()` updates the pool reserve fields `firstTokenBalance`/`secondTokenBalance` using either checked arithmetic (`StrictMathWrapper.addExact`/`subtractExact`) or unchecked plain `long` arithmetic (`+`/`-`), depending on a runtime feature flag, `hardenedCalc`.

### Finding Description
`ExchangeCapsule.transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath, boolean hardenedCalc)` computes the new pool reserves for the two exchanged tokens: [1](#0-0) 

When `hardenedCalc` is `false`, the reserve update uses plain `long` addition/subtraction (`firstTokenBalance + sellTokenQuant`, `secondTokenBalance - buyTokenQuant`, etc.) with no overflow/underflow check, unlike the `hardenedCalc` path which uses `StrictMathWrapper.addExact`/`subtractExact` and additionally validates that resulting balances are non-negative: [2](#0-1) 

This mirrors the Caviar `PrivatePool.buy()`/`sell()` bug class exactly: a reserve-tracking accounting variable (there `uint128` via unchecked cast; here `long` via unchecked `+`/`-`) is updated without verifying the result fits/behaves correctly, which can silently corrupt the invariant the AMM relies on for pricing (there `x*y=k`, here the Bancor-formula relationship between `firstTokenBalance`/`secondTokenBalance` used by `ExchangeProcessor.exchange()`).

Whether this path is reachable in practice by an unprivileged user hinges on the `AllowHardenExchangeCalculation` chain parameter, controlled via `ProposalUtil`/`DynamicPropertiesStore`, which gates `hardenedCalc` in `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`: [3](#0-2) [4](#0-3) 

If this proposal has not been activated on a given network (default-off, as is typical for new chain parameters until governance votes to enable it), every call to `ExchangeTransactionActuator.execute()` (a fully public, unprivileged-user-triggered actuator — anyone can submit `ExchangeTransactionContract`) hits the unchecked-arithmetic branch of `ExchangeCapsule.transaction()`.

### Impact Explanation
If a user can craft/accumulate `sellTokenQuant`/`buyTokenQuant` values that push `firstTokenBalance` or `secondTokenBalance` past `Long.MAX_VALUE` (overflow to negative) or below zero (underflow) via repeated/large trades while `hardenedCalc` is disabled, the on-chain pool reserves stored in the `Exchange`/`ExchangeV2` state would silently wrap, corrupting the AMM pricing invariant used by `ExchangeProcessor.exchange()`/`SafeExchangeProcessor`. This is a state-accounting divergence with direct settlement impact: mispriced subsequent trades, potential extraction of tokens beyond what the true reserves support, and permanent corruption of the exchange's on-chain balances — analogous in severity to the original High-severity Caviar finding, since it breaks the core `x*y=k`-style invariant of the AMM.

### Likelihood Explanation
Likelihood depends entirely on whether `AllowHardenExchangeCalculation` is active on the target network. If it is active (as the repo's own hardened test suite, e.g. `hardenedSuccessExchangeTransaction`/`hardenedExecuteOverflowThrowsArithmeticException` in `ExchangeTransactionActuatorTest.java`, and `hardenedAddExactOverflowThrows` in `ExchangeInjectActuatorTest.java`, suggests is the developers' intended safe path), then this issue is already mitigated by design — `StrictMathWrapper.addExact`/`subtractExact` will throw `ArithmeticException`, which callers convert to `ContractExeException`/`ContractValidateException`, preventing silent corruption: [5](#0-4) [6](#0-5) 

I was unable to determine, from the indexed code, the actual on-chain/default activation state of this proposal (`AllowHardenExchangeCalculation`) for the target deployment — this depends on `DynamicPropertiesStore` initialization and governance proposal history, which I could not fully confirm within available tool iterations. If the parameter is not yet activated on the network in question, likelihood is meaningful because `TRC10` balances (`long`, 6-decimal precision) can realistically approach the range needed for overflow with high-supply tokens or accumulated pool balances over time, similar to how the Caviar PoC used a high-decimals ERC20 to trigger the overflow. If the parameter is already activated by default/governance, likelihood is low since the checked path fully guards against this.

### Recommendation
- Confirm the current activation status of the `AllowHardenExchangeCalculation` dynamic property on the deployed chain; if not yet enabled, activate it via governance proposal so all exchange operations route through the checked `StrictMathWrapper`/`SafeExchangeProcessor` path.
- Consider removing the legacy unchecked-arithmetic branch entirely from `ExchangeCapsule.transaction()` rather than gating it behind a toggle, eliminating any window where unprivileged users can trigger silent overflow/underflow of exchange reserves.
- Add explicit bounds/invariant checks (e.g., verifying `firstTokenBalance * secondTokenBalance` relationship is preserved, or reserves fit expected TRC10 supply bounds) independent of the `hardenedCalc` flag.

### Proof of Concept
Conceptual reproduction (mirroring the Caviar PoC pattern), assuming `AllowHardenExchangeCalculation` is inactive:
1. Create a TRC10 token with the maximum allowed total supply and use it to seed an `Exchange` pool with a very large `secondTokenBalance` close to `Long.MAX_VALUE`, via `ExchangeCreateActuator` + `ExchangeInjectActuator`, all unprivileged operations.
2. Submit an `ExchangeTransactionContract` via `ExchangeTransactionActuator` with a `tokenQuant` sized so that `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` (or `newFirstTokenBalance = firstTokenBalance + sellTokenQuant`) wraps around `long` bounds in the unchecked branch of `ExchangeCapsule.transaction()`: [7](#0-6) 
3. Observe that `firstTokenBalance`/`secondTokenBalance` stored on-chain no longer reflect the true reserves, and subsequent `buyQuote`/`sellQuote`-equivalent pricing via `ExchangeProcessor.exchange()` produces incorrect trade outputs, allowing extraction of value inconsistent with the pool's actual token holdings.

This PoC is conceptual; I was not able to execute it or confirm the current default state of `AllowHardenExchangeCalculation` in this indexed snapshot, so exploitability should be verified directly against a running node/testnet before treating this as confirmed-exploitable in production.
