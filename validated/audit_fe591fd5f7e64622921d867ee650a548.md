### Title
UniversalCore chain-meta gas price is consumed for fee accounting without checking on-chain `timestampObservedAtByChainNamespace` staleness - (File: x/uexecutor/keeper/gas_fee.go, x/uexecutor/keeper/evm.go)

### Summary
The Chainlink report's core defect — reading a price feed's latest value without checking its `updatedAt`/freshness — has a direct analog in Push Chain's gas-price oracle. `UniversalCore` exposes `timestampObservedAtByChainNamespace(chainNamespace)`, a getter that returns when a chain's gas price/height was last set on-chain [1](#0-0) . However, every consumer that reads `gasPriceByChainNamespace` for actual fee accounting (`GetGasPriceByChain`, `GetOutboundTxGasAndFees`, `GetGasFeeInfoForRevertOutbound`) reads the value and immediately unpacks/uses it without ever calling or checking `timestampObservedAtByChainNamespace` [2](#0-1) [3](#0-2) .

### Finding Description
The gas-price/chain-height oracle write path (`VoteChainMeta`) is well-guarded: it enforces a bootstrap quorum, a monotonic-height requirement, and a `chainMetaVoteStalenessSeconds` (300s) window when computing the validator-vote median before writing to the EVM contract [4](#0-3) [5](#0-4) .

But that guard only protects the *write* side (aggregating fresh validator votes into a median before calling `setChainMeta`). Once the value is committed on-chain via `CallUniversalCoreSetChainMeta`, downstream consumers that later *read* the price for real fee/refund accounting — `GetGasPriceByChain`, `GetOutboundTxGasAndFees` (used by `buildRevertOutbound`/`GetGasFeeInfoForRevertOutbound` and by `applyGasRefund`'s swap-fee path) — never check how old that stored value is [2](#0-1) [6](#0-5) . The contract itself exposes exactly the "last updated" data needed to do this check (`timestampObservedAtByChainNamespace`), analogous to Chainlink's `updatedAt`, yet grep confirms this getter is referenced only in the ABI definition and never called anywhere in the keeper logic that consumes the price for fee computation [7](#0-6) .

This means if validator voting on a given `observedChainId` stops or lags (e.g., an external chain's RPC becomes unreachable to universal validators, or that chain simply sees very low vote traffic because it is a rarely-used destination), the last-applied gas price/height can remain frozen in `UniversalCore` storage indefinitely while ordinary users continue to submit inbound/outbound transactions that get priced, refunded, and re-swapped using that stale number — with no code path ever detecting or rejecting the staleness at consumption time.

### Impact Explanation
Ordinary unprivileged users triggering inbound transactions with gas payloads, or outbounds that later get voted/observed, cause `GetOutboundTxGasAndFees`/`GetGasFeeInfoForRevertOutbound`/`applyGasRefund` to charge/refund gas fees computed from a potentially stale `gasPrice`. If the real destination-chain gas price has since risen sharply while the on-chain value is frozen at an old, lower figure, users are undercharged relative to actual relay cost, and `applyGasRefund` (which refunds `gasFee - gasFeeUsed`) can compute excess refunds based on a wrong baseline `outbound.GasFee`, corrupting gas fee/refund accounting and creating a fund-drain/undercollection vector against protocol-held gas token reserves [8](#0-7) . If the price is frozen high, users are systematically overcharged for gas relative to real relay cost.

### Likelihood Explanation
Likelihood is bounded because it depends on validator voting activity slowing or stopping for a particular destination chain (an operational condition rather than an attacker action), and because the bootstrap/vote-staleness logic on the write side is otherwise sound. This is not an "attacker forges data" bug like the original Chainlink report, but a "missing staleness check on a value already exposed on-chain" gap that matches the reported bug class precisely and can silently persist a wrong monetary value indefinitely with no automatic detection or fallback in the read path.

### Recommendation
Before using `gasPriceByChainNamespace`/`chainHeightByChainNamespace` for fee/refund calculations in `GetGasPriceByChain`, `GetOutboundTxGasAndFees`, and `GetGasFeeInfoForRevertOutbound`, also call `timestampObservedAtByChainNamespace` and reject or fall back (e.g., abort/mark-pending the outbound, or use a configurable max-staleness threshold) if `block.timestamp - observedAt` exceeds an acceptable bound, mirroring the write-side `chainMetaVoteStalenessSeconds` guard.

### Proof of Concept
Not independently executable from static analysis alone — the scenario requires simulating a prolonged absence of `VoteChainMeta` calls for a given `observedChainId` (e.g., stopping the `ChainMetaOracle`/validator votes for that chain) while continuing to drive `ExecuteInboundGas`/outbound voting flows that call `GetOutboundTxGasAndFees` and `applyGasRefund`, then verifying that the frozen `gasPriceByChainNamespace` value keeps being used with no staleness check, despite `timestampObservedAtByChainNamespace` reporting a large elapsed time. I could not locate any test exercising `timestampObservedAtByChainNamespace` consumption, which is consistent with it being unused in production logic, but full contract-level confirmation (the Solidity source for `UniversalCore`) was not available in the indexed codebase to verify the exact storage/timestamp semantics beyond the ABI and Go-side callers shown above.

// GetGasPriceByChain reads the gas price for a chain from the UniversalCore contract.
func (k Keeper) GetGasPriceByChain(ctx sdk.Context, chainNamespace string) (*big.Int, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UniversalCore ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	receipt, err := k.evmKeeper.CallEVM(ctx, abi, ueModuleAccAddress, handlerAddr, false, nil, "gasPriceByChainNamespace", chainNamespace)
	if err != nil {
		return nil, errors.Wrap(err, "failed to call gasPriceByChainNamespace")
	}

	results, err := abi.Methods["gasPriceByChainNamespace"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack gasPriceByChainNamespace result")
	}

	return results[0].(*big.Int), nil
}

	receipt, err := k.evmKeeper.CallEVM(ctx, ucABI, ueModuleAccAddress, handlerAddr, false, nil,
		"getOutboundTxGasAndFees", prc20, gasLimitWithBaseLimit)
	if err != nil {
		return nil, errors.Wrap(err, "failed to call getOutboundTxGasAndFees")
	}

	results, err := ucABI.Methods["getOutboundTxGasAndFees"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack getOutboundTxGasAndFees result")
	}

	gasToken := results[0].(common.Address)
	gasFee := results[1].(*big.Int)
	// protocolFee := results[2].(*big.Int) — not needed for outbound fields

	// gasLimitUsed (results[5]) is the exact gas limit the contract resolved
	// (caller-supplied or per-chain baseGasLimitByChainNamespace fallback).
	// Reading it directly avoids the gasFee/gasPrice round-trip and keeps us
	// in lock-step with the contract's own resolution.
	gasLimit := results[5].(*big.Int)

	return &GasFeeInfo{
		GasToken: gasToken,
		GasFee:   gasFee,
		GasPrice: gasPrice,

	}, nil
