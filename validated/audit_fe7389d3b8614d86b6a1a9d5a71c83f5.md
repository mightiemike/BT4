### Title
DelegatedResourceAccountIndex entries are permanently deleted while a locked delegated resource still exists - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Summary
The Cosmos report describes a class of bug where a tracking/index entry (`STAKERS`) is deleted based on an incomplete zero-check (only `total_staked` and `pending_bro_reward`), silently orphaning another asset (`bBRO` tokens) that was not part of the check. The same bug class exists in java-tron's TVM native-contract path for `unDelegateResource`: `UnDelegateResourceProcessor.execute()` deletes the `DelegatedResourceAccountIndex` entries for an owner/receiver pair based solely on whether the **unlocked** `DelegatedResourceCapsule` (key flag `false`) has zero bandwidth/energy balance, without checking whether a **locked** (still time-locked) `DelegatedResourceCapsule` (key flag `true`) still holds a non-zero balance.

### Finding Description
When a smart contract calls the native `unDelegateResource` precompile/opcode, execution goes through `UnDelegateResourceProcessor.execute()`: [1](#0-0) [2](#0-1) 

The code fetches only the **unlock** `DelegatedResourceCapsule` via `createDbKeyV2(ownerAddress, receiverAddress, false)`, and once its `frozenBalanceForBandwidth`/`frozenBalanceForEnergy` reach zero, it wipes the `DelegatedResourceAccountIndex` for both the `from` and `to` directions by overwriting them with an empty capsule. It never fetches or checks the **locked** capsule under key flag `true` (`createDbKeyV2(ownerAddress, receiverAddress, true)`), nor does it call `delegatedResourceStore.unLockExpireResource(...)` to migrate any expired lock into the unlock record first.

This is in stark contrast to the equivalent, correctly-implemented logic in the ordinary (non-TVM) `UnDelegateResourceActuator`, which:
1. First calls `delegatedResourceStore.unLockExpireResource(...)` to roll expired locked resource into the unlock record.
2. Fetches **both** the unlock and lock capsules.
3. Only deletes the index (`delegatedResourceAccountIndexStore.unDelegateV2(...)`) when **both** `unlockResource == null && lockResource == null`: [3](#0-2) 

Because the TVM path skips the lock-key check, if an owner still has an active, still-time-locked delegated resource to a receiver (created via a "lock" style delegate, e.g. through `DelegateResourceContract` with lock enabled) while the unlock balance happens to reach zero, invoking `unDelegateResource` from a contract will delete the `DelegatedResourceAccountIndexStore` entries even though the underlying locked `DelegatedResourceCapsule` (with non-zero balance) is left in the `DelegatedResourceStore`. The index is the only efficient lookup structure (`getV2Index`/`getWithPrefix`) used by APIs/wallets to discover delegated resources between two addresses: [4](#0-3) 

This means the still-active, non-zero locked delegation becomes practically invisible/unreachable through the index-based lookup path even though the funds are still frozen on-chain and belong to the receiver's/owner's resource allotment — mirroring the "STAKERS item deleted while bBRO balance is still nonzero" pattern from the reference report, where an entity's discoverability/state entry is destroyed based on a partial zero-check that ignores another live component of that entity.

### Impact Explanation
The direct effect is corruption/loss of the index used to enumerate delegated resources for an address pair. Wallets, explorers, and any caller relying on `DelegatedResourceAccountIndexStore.getV2Index()` to discover existing delegations will fail to find the still-locked delegated resource, even though the underlying `DelegatedResourceCapsule` (holding real frozen TRX/bandwidth/energy) still exists in `DelegatedResourceStore`. This can prevent the rightful unDelegate/expiry-driven cleanup flows that depend on index-based iteration, and creates a state divergence between the index store and the resource store — an accounting/discoverability defect analogous to the reported loss of bBRO claim ability. The severity is lower than the original report (funds are not permanently burned — they remain in `DelegatedResourceStore` and can eventually be recovered if the caller directly knows the key — since the TRX itself is not lost, only the index), but it constitutes a genuine state-inconsistency/accounting bug reachable by any user via a smart contract calling `unDelegateResource`.

### Likelihood Explanation
Reaching this condition requires: (1) `supportDR()` and `supportUnfreezeDelay()` (or equivalent VM config flag) enabled, (2) the owner having both an unlocked delegated resource balance and a separate still-time-locked delegated resource balance to the same receiver, and (3) fully un-delegating the unlocked portion via a TVM contract call to the `unDelegateResource` native contract while the locked portion remains outstanding. This is a normal, permissionless flow (any contract account can call `unDelegateResource`), so it is reachable by any unprivileged user, though it requires a specific sequencing of delegate/lock operations to set up the locked+unlocked split.

### Recommendation
Modify `UnDelegateResourceProcessor.execute()` to mirror `UnDelegateResourceActuator`'s behavior:
1. Call `repo`'s equivalent of `unLockExpireResource` (or manually fetch and evaluate the expired lock) before determining zero-balance state.
2. Fetch the locked `DelegatedResourceCapsule` via `createDbKeyV2(ownerAddress, receiverAddress, true)`.
3. Only clear the `DelegatedResourceAccountIndex` entries when **both** the unlock and lock capsules are absent/zero-balance, consistent with the actuator path.

### Proof of Concept
Conceptual reproduction (concrete PoC would need to be built and run in a Devin session against a private/testnet build, which is outside the scope of this read-only analysis):
1. Deploy a contract; have it accumulate a locked (time-locked) delegated resource to a receiver via the lock-delegate flow, and separately an unlocked delegated resource balance to the same receiver.
2. From the contract, invoke the native `unDelegateResource` to fully drain the unlocked balance (bandwidth and energy) to zero while the locked balance is still non-expired and non-zero.
3. Observe `UnDelegateResourceProcessor.execute()` deletes `DelegatedResourceAccountIndex` entries for both `from`/`to` directions at lines 195-206, even though `DelegatedResourceCapsule` under the `true` (locked) key still has a non-zero balance in `DelegatedResourceStore`.
4. Query `DelegatedResourceAccountIndexStore.getV2Index(owner)` / `getV2Index(receiver)` and confirm the still-locked delegation is no longer discoverable via the index, despite the frozen balance still existing in storage — a state divergence between the two stores.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
