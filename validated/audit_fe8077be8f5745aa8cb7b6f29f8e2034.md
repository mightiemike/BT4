## Analysis

I found a legitimate analog in the Vault gateway's `RequestReplayGuard` mechanism, which mirrors the exact bug class: an unprivileged user's one-time-use authorization proof is permanently consumed regardless of whether the downstream privileged action actually succeeds, causing the user to be permanently locked out from retrying an otherwise valid request.

### Title
Vault request replay guard permanently consumes an allowlisted/authorized request digest before the underlying secrets operation executes or succeeds, locking users out of legitimate retries - (File: core/capabilities/vault/authorizer.go)

### Summary
In `authorizer.AuthorizeRequest`, the `RequestReplayGuard.CheckAndRecord` call records (consumes) a request's digest as "seen" immediately after authorization succeeds, but *before* the actual privileged vault operation (`SecretsCreate`/`Update`/`Delete`/`List`) is executed or known to succeed downstream. This is structurally identical to the Vader `Converter.sol` issue: a one-time proof (merkle proof in Vader; allowlisted request digest / replay-guard entry in Chainlink Vault) is marked as consumed unconditionally, decoupled from whether the guarded action actually completes successfully for the user.

### Finding Description
The Vault gateway authorization pipeline is:
`ValidateStructureBeforeAuth → AuthorizeRequest (replay-guard consume) → Prefix ID → StampAuthorizedParams → downstream SecretsService call` [1](#0-0) 

`authorizer.AuthorizeRequest` obtains an `AuthResult` from either the allowlist-based or JWT-based auth mechanism, and **immediately** calls `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())`, marking the request's digest as permanently "seen": [2](#0-1) 

The replay guard itself has no notion of success/failure of the underlying operation — once `CheckAndRecord` succeeds, the digest is stored in `seen` and any subsequent request with the same digest is rejected with `ErrRequestAlreadySeen` until expiry: [3](#0-2) 

For the allowlist-based path specifically, a workflow owner allowlists a request digest on-chain via `AllowlistRequest`, which is a scarce, explicit action (analogous to the merkle-proof-eligibility setup in the Vader report): [4](#0-3) 

After `AuthorizeRequest` (and thus replay-guard consumption) succeeds, `GatewayVaultRequestProcessor.authorizeAndStamp` proceeds to stamp params and only *then* is the actual `SecretsService` operation (e.g., `CreateSecrets`) invoked by the caller (gateway handler / node handler). If that downstream operation fails for any reason unrelated to authorization — e.g., a transient DON/OCR failure, a validation error surfaced later, a service-side error, or a gateway-to-DON timeout — the request's one-time authorization has already been irreversibly burned by the replay guard. The system test comments explicitly acknowledge this consumption-on-timeout behavior: [5](#0-4) [6](#0-5) 

Just as in the Vader report — where the merkle proof is marked invalid regardless of whether VETH was actually converted to VADER (because the allowance was zero) — here the allowlisted/authorized request digest is marked "seen" regardless of whether the secrets operation actually completed. Since the allowlist entry (on-chain, via `WorkflowRegistry.AllowlistRequest`) is tied to the exact digest of the request payload, once consumed by the replay guard, the *same* request cannot be retried even if the user made no mistake — they would need the workflow owner to re-allowlist an entirely new digest (which may itself require redoing on-chain governance/authorization steps), mirroring the "user cannot try again" bug class described in the original report.

### Impact Explanation
An unprivileged Vault user (workflow owner) can be permanently locked out of completing a legitimately-authorized action (creating/updating/deleting secrets) if the downstream operation fails for reasons unrelated to authorization correctness (e.g., transient errors, gateway timeouts noted in the code itself, DON-side processing failures). This causes denial of service for that specific secret operation and forces costly re-authorization (new on-chain allowlist entry with new expiry, or a new JWT) purely due to a bookkeeping mismatch between "authorization consumed" and "operation performed." The system's own test comments (`vault_don_test.go` and `vault_don_test_helpers.go`) already document this behavior as expected/tolerated rather than a hard failure, confirming the replay-guard-consumption-without-success-guarantee design is present in production code paths, not merely test scaffolding.

### Likelihood Explanation
This triggers under any transient failure in the pipeline after authorization succeeds but before the downstream secrets operation is confirmed to the user: gateway-to-DON timeouts (explicitly documented as occurring under burst load), DON-side processing hiccups, or any error thrown between `AuthorizeRequest` and successful completion of `SecretsService.CreateSecrets`/etc. Because this is purely a timing/ordering defect in normal (non-adversarial) request processing, it can be hit by any legitimate unprivileged user without any malicious node/peer/operator involvement.

### Recommendation
Decouple replay-guard consumption from authorization success in the same way recommended for the Vader converter: only mark a request digest as permanently consumed once the guarded downstream action (`SecretsService` call) has been confirmed to succeed, or use a two-phase model (e.g., "reserved" vs. "finalized" state) for replay-guard entries so that a failed downstream operation can be retried with the same authorized digest before its expiry. Alternatively, ensure the on-chain/JWT authorization step is idempotent and independent from the JSON payload's exact digest, or provide an explicit "release"/rollback path for the replay guard on downstream failure.

### Proof of Concept
1. A workflow owner allowlists a `SecretsCreate` request digest on-chain via `WorkflowRegistry.AllowlistRequest` [7](#0-6) .
2. The client sends the exact JSON-RPC request to the gateway; `GatewayVaultRequestProcessor.authorizeAndStamp` calls `authorizer.AuthorizeRequest`, which succeeds and calls `replayGuard.CheckAndRecord(digest, expiresAt)`, marking the digest "seen" [8](#0-7) .
3. Due to a transient failure — e.g., a gateway-to-DON timeout as explicitly described in `shouldRetryGatewayRequest`/`sendConcurrentVaultCreate` — the downstream `SecretsService.CreateSecrets` call never completes successfully for the user, or the gateway cannot relay the success response [5](#0-4) .
4. The client retries with the identical request payload (same digest); `RequestReplayGuard.CheckAndRecord` now returns `ErrRequestAlreadySeen`, and the request is permanently rejected until the on-chain allowlist entry expires, at which point the original authorization opportunity is lost entirely [9](#0-8) .

```go
func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
```

```go
var ErrRequestAlreadySeen = errors.New("request was already authorized previously")

// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```

```go
func shouldRetryGatewayRequest(statusCode int, body []byte) bool {
	if isGatewayNotAllowlistedError(body) {
		return true
	}
	switch statusCode {
	case http.StatusServiceUnavailable, http.StatusBadGateway, http.StatusGatewayTimeout:
		// Gateway-to-DON timeout: the gateway gave up relaying the response, but the DON likely
		// already processed the request. Retrying the same request body just hits the vault
		// replay guard ("request was already authorized previously"). Don't retry these.
		if bytes.Contains(body, []byte("Request timed out")) {
			return false
		}
		return true
	default:
		return false
	}
}
```

```go
func allowlistRequest(t *testing.T, owner string, request jsonrpc.Request[json.RawMessage], sethClient *seth.Client, wfRegistryContract *workflow_registry_v2_wrapper.WorkflowRegistry) {
```

```go
func sendConcurrentVaultCreate(t *testing.T, gwURL, requestID string, jsonRequest jsonrpc.Request[json.RawMessage], authorizedOwner, expectedResponseOwner string, namespaces []string) {
```
