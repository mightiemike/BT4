### Title
Fee-transfer call failure is not checked, allowing transactions to be committed without actual fee payment - (File: crates/blockifier/src/transaction/account_transaction.rs)

### Summary
The sequencer's `execute_fee_transfer` function invokes the fee token's `transfer` entry point via `CallEntryPoint::execute()` (the "reverting-allowed" variant), but never inspects the returned `CallInfo.execution.failed` flag or the return data of the transfer call. This mirrors the reported OpenZeppelin/ERC20 issue: a transfer is performed without checking its success status.

### Finding Description
`AccountTransaction::execute_fee_transfer` builds a `CallEntryPoint` targeting the fee token's `transfer` selector and calls the plain `.execute(...)` method: [1](#0-0) 

Unlike the `validate` flow, which explicitly checks `validate_call_info.execution.failed` and errors out on failure/incorrect return data: [2](#0-1) 

`execute_fee_transfer`'s result (`Ok(CallInfo)`) is returned unconditionally as long as no *EntryPointExecutionError* was produced (`map_err` only converts VM/execution errors, not a "failed" `CallInfo`). Per `execute_entry_point_call_wrapper`, when reverts are enabled (`context.versioned_constants().enable_reverts`, the default for the currently supported tx versions), a failing/panicking inner Cairo1 call is still returned as `Ok(call_info)` with `execution.failed = true`, rather than as an `Err`: [3](#0-2) 

There is a `non_reverting_execute` wrapper specifically designed to convert a `failed` `CallInfo` into an `Err`: [4](#0-3) 

but `execute_fee_transfer` uses `.execute()`, not `.non_reverting_execute()`. Consequently, if the fee token's `transfer` entry point (Cairo1 ERC20) panics/reverts for any reason (e.g. underflow guard, or a custom fee-token implementation that legitimately returns `false` on failure instead of panicking), the sequencer:
- still records this `CallInfo` as `fee_transfer_call_info`,
- still reports `receipt.fee = final_fee` as the amount charged,
- proceeds to `complete_fee_transfer_flow`/`add_fee_to_sequencer_balance` in concurrency mode, which blindly assumes the transfer succeeded and adds the fee to the sequencer's balance in the state diff regardless of whether the account's balance was actually debited.

This is precisely the OpenZeppelin standards issue referenced in the report: the code performs an ERC20-style transfer without validating the boolean success return value, trusting that failure always manifests as a hard revert. Because Starknet fee tokens can be arbitrary Cairo contracts (the fee token address is a versioned-constants parameter, not hardcoded to one canonical implementation) that may implement `transfer` to return `false` on insufficient balance instead of panicking, this assumption is not guaranteed to hold across all deployed/candidate fee-token implementations.

### Impact Explanation
If a fee-token implementation returns `false` (rather than panicking) on transfer failure, the sequencer will treat the fee as successfully collected: the sequencer's balance is credited via `add_fee_to_sequencer_balance` without validating that the sender's balance was actually debited, and the block is committed with a state diff/commitment that does not reflect a real transfer. This causes: (1) permanent loss of the "fee" (sequencer credited a fee balance that was never actually deducted from the sender, corrupting the token's total-supply invariant), and (2) if any other honest node's execution environment differs (e.g. resource-metering causing a revert on one node vs. success on another due to boundary gas conditions around the panic vs. return-false paths), it produces a wrong committed state root / block hash — an honest-node divergence.

### Likelihood Explanation
Reaching this path requires only a single account transaction submitted by an unprivileged sender whose configured fee token contract's `transfer` implementation returns `false` on failure instead of reverting (a legal ERC20-style implementation choice, and technically compliant with token standards more strictly than "revert on failure"). No special privileges, and no cooperation from a validator/proposer are required — the transaction sender fully controls when and how their own account's fee-transfer step is triggered (e.g. by having a fee token balance just at the threshold of the actual computed fee, or by controlling a custom "fee token"-like contract in test/sovereign appchain configurations where the fee token address is configurable).

### Recommendation
Explicitly check the retdata/`failed` status of the fee-transfer `CallInfo` in `execute_fee_transfer` (analogous to `validate_tx`'s check), and error out (or otherwise refuse to consider the fee paid) if `call_info.execution.failed` is true or the expected boolean-`true` retdata is missing. Consider using `non_reverting_execute` for the fee transfer call as is already done in the Cairo OS's `charge_fee` via `non_reverting_select_execute_entry_point_func`, ensuring blockifier is consistent with the OS's re-execution semantics.

### Proof of Concept
1. Deploy (or configure, in a test/appchain context) a fee token contract whose `transfer` entry point returns `Felt::ZERO` (false) on insufficient balance instead of panicking.
2. Submit an account invoke transaction where the sender's fee-token balance is insufficient to cover `actual_fee`.
3. Observe: `execute_fee_transfer` calls `.execute()`, which succeeds with `Ok(CallInfo { execution: CallExecution { failed: false, retdata: [FELT_FALSE], .. }, .. })` since the Cairo1 code returned normally.
4. `handle_fee` records this CallInfo as `fee_transfer_call_info` with no validation of `retdata`/`failed`, and the transaction proceeds to commit with `receipt.fee = final_fee`, even though the sender's balance was never actually debited by the fee token's own accounting logic (which chose to return false rather than write updated balances).
