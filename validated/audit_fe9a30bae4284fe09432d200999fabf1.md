### Title
Reject-then-Accept flip from the same signer slot causes double-counting of `total_weight_approved` + `total_weight_rejected` beyond `self.total_weight` - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
In `StackerDBListener`'s message-processing loop, the `Accepted` handler gates weight-crediting on `gathered_signatures.contains_key(&slot_id)` while the `Rejected` handler gates on `responded_signers.insert(slot_id)`. Because these are two different sets, a signer who first rejects and then accepts the same block (`signer_signature_hash`) gets counted in both `total_weight_rejected` and `total_weight_approved`, breaking the invariant that a signer's weight belongs to exactly one bucket.

### Finding Description
The claimed equality is: a signer's weight must be counted in exactly one of `total_weight_approved` / `total_weight_rejected` for a given `signer_signature_hash`, so that `total_weight_approved + total_weight_rejected <= self.total_weight`.

Tracing the code at `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- `Rejected` arm (around line 515): `if block.responded_signers.insert(slot_id) { block.total_weight_rejected += signer_entry.weight; ... }`. This is the *first* time this slot appears in `responded_signers`, so the insert succeeds and the reject weight is added.
- `Accepted` arm (around line 443): the credit condition is `if !block.gathered_signatures.contains_key(&slot_id) { block.total_weight_approved += signer_entry.weight; ... }`, followed unconditionally by `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)`.

If the attacker (a legitimate signer holding their own slot/key, minority weight) sends `Rejected` for hash `H` first, `responded_signers` now contains `slot_id`, and `total_weight_rejected` is incremented. If the same signer then sends `Accepted` for the same `H`, the accept-path check only looks at `gathered_signatures` — which was never touched by the reject path — so it is empty for that slot, and `total_weight_approved` is also incremented for the same weight. The signer's weight is now counted in both totals simultaneously, and `total_weight_approved + total_weight_rejected > self.total_weight` for the signer set. (The reverse order, Accept-then-Reject, does not double count, because the reject path's guard `responded_signers.insert` already fails once `Accepted` has been processed — so only the Reject→Accept ordering is exploitable.)

No other guard in the file removes a signer's weight from the opposite bucket when it flips response, and there is no check anywhere in `signer_coordinator.rs` or `stackerdb_listener.rs` enforcing `total_weight_approved + total_weight_rejected <= total_weight` before firing `cvar.notify_all()` at `block.total_weight_approved >= self.weight_threshold`.

### Impact Explanation
This produces an internally inconsistent block-status tally within the miner-local `StackerDBListener`/`SignerCoordinator`, where the sum of the two weight buckets can exceed the total configured signer weight for the reward cycle. This can cause `cvar.notify_all()` to fire based on `total_weight_approved` alone, while `total_weight_rejected` (queried for possibly deciding to give up on / retry the block, and used in the log/telemetry percentages) reflects stale data that no longer represents a live disjoint rejection. This is a within-process/local bookkeeping bug in the miner's coordinator that can cause a temporary tip disagreement between what the miner's coordinator believes (block reached threshold and is broadcast) versus other observers reading the rejection/acceptance percentages, matching the "temporary tip disagreement" bucket in the High severity category. It does not cause a chain split, invalid-block acceptance network-wide, or reward mispayment — the double count only affects the miner-local in-memory `BlockStatus` struct used to decide when to broadcast, not chain-level consensus validation (`check_tenure_tx`, `validate_vrf_seed`, MARF hashing are untouched).

### Likelihood Explanation
Preconditions: the attacker must hold a valid signer slot (their own key) for the relevant reward cycle and be able to write two chunks to their own StackerDB slot for the same block — first a `Rejected` message, then an `Accepted` message for the same `signer_signature_hash`. This requires no majority stake, no other signer's key, and no privileged role — only ordinary signer participation with minority weight, which is within the defined threat model. It is fully repeatable per block by any single signer performing this ordering, requiring no BTC spend and no elevated permissions.

### Recommendation
Make the two counters track disjoint, mutually-exclusive membership. E.g., track each signer's *current* response type in a single map (`slot_id -> ResponseKind::{Accepted, Rejected}`), and when a signer's response changes, subtract the previous response's weight from the old bucket before adding to the new one. Concretely, in the `Accepted` arm, before crediting `total_weight_approved`, check whether `slot_id` is present in a rejection-tracking set/map and, if so, subtract `signer_entry.weight` from `total_weight_rejected` (and vice versa in the `Rejected` arm). Alternatively, unify `gathered_signatures` and rejection tracking into one `HashMap<u32, ResponseKind>` gating both branches consistently, and assert `total_weight_approved + total_weight_rejected <= self.total_weight` as an invariant after each update.

### Proof of Concept
Rust integration/unit test plan targeting `StackerDBListener::poll_events`-equivalent handling (or the message dispatch loop directly, by constructing a `BlockStatus` and simulating the two match arms):

1. Set up a signer set with one signer slot `S` of weight `w`, and `self.total_weight = W >= w`.
2. Insert an empty `BlockStatus` for `signer_signature_hash = H` into `self.blocks`.
3. Simulate delivery of a `StackerMessageV0::BlockResponse(BlockResponse::Rejected(...))` from slot `S` for `H` — assert `block.total_weight_rejected == w` and `block.total_weight_approved == 0`.
4. Simulate delivery of a `StackerMessageV0::BlockResponse(BlockResponse::Accepted(...))` from the same slot `S` for the same `H`, with a valid signature over `H`.
5. Assert the broken invariant is observed: `block.total_weight_approved == w` AND `block.total_weight_rejected == w`, therefore `block.total_weight_approved + block.total_weight_rejected == 2*w > self.total_weight` (when `W < 2w`, e.g. single-signer weight equals total weight), proving `total_weight_approved + total_weight_rejected <= self.total_weight` is violated.
6. As a regression assertion for the fix, after applying the recommended change, assert `block.total_weight_rejected == 0` and `block.total_weight_approved == w` after step 4 (i.e., the reject credit is retracted when the signer flips to accept).
