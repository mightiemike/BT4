### Title
Sequencer purges reverted deposits from the mempool without minting cBTC — permanent fund freeze on the analog of the `StakeVault.leave()` catch-block bug - ([File: crates/sequencer/src/runner.rs])

### Summary
`process_sys_txs` in `crates/sequencer/src/runner.rs` mirrors the reported `StakeVault.leave()` pattern: a legitimate/forced revert of a privileged operation is silently swallowed, and the caller-visible bookkeeping is updated as if the operation succeeded (or is discarded) even though the underlying custody-relevant action never took place on-chain.

### Finding Description
When the sequencer builds a block, it fetches pending deposits from `DepositDataMempool::fetch_deposits` and turns them into `SystemEvent::BridgeDeposit` events [1](#0-0) . Each event is executed as a system transaction inside `process_sys_txs`. If the EVM call to `Bridge.deposit()` reverts entirely — which happens whenever the modifier `whenNotPaused` reverts, e.g. `deposit(...) external onlySystemOrOperator whenNotPaused` [2](#0-1)  — `apply_l2_block_txs` returns `StateTransitionError::ModuleCallError(L2BlockModuleCallError::EvmSystemTransactionNotSuccessful)`. For that specific error and only for deposits, the sequencer reverts the working set and silently `continue`s the loop instead of propagating the error: [3](#0-2) .

This is functionally the same shape as the reported try/catch bug: a revert path is deliberately absorbed ("do not fail the whole block because of one bad deposit") but the code does not undo the *external* side of the operation's bookkeeping. Concretely, the deposit that was fetched via `fetch_deposits` and included in `deposit_data` is removed from the `DepositDataMempool` unconditionally after block production, based on the comment "Remove successfully included deposits from the mempool" [4](#0-3) . Nothing in `process_sys_txs` returns which individual deposits among `deposit_data` were actually applied versus reverted — it only returns the RLP-encoded list of transactions that succeeded (`all_txs`), while the caller still holds and later passes the original, unfiltered `deposit_data` slice into `remove_deposits`.

Because Bitcoin-side custody (the `MoveToVault` transaction pre-signed by Clementine signers) is already final and irreversible by the time `citrea_sendRawDepositTransaction` is even accepted into the mempool [5](#0-4) , if the corresponding `deposit()` system transaction reverts once (e.g., contract paused during a security response, or any other `require` failing non-deterministically depending on chain state at execution time) and the deposit entry is nonetheless purged from `pending_deposits`/`accepted_deposit_txs`, the BTC-side deposit that "actually happened" is never reflected by minted cBTC — breaking the binding `cBTC credited == Bitcoin deposit confirmed`.

### Impact Explanation
If confirmed, this breaks the required equality between cBTC credited on Citrea and BTC actually locked on Bitcoin, falling under the Critical impact category "funds permanently frozen" — the user's BTC is irrevocably committed to the vault via Clementine's pre-signed transaction, but the mint never happens and the retry mechanism (the mempool) has already discarded the record needed to resubmit it.

### Likelihood Explanation
This requires a legitimate/forced revert of `Bridge.deposit()` while the deposit is queued in the sequencer (e.g., the bridge being paused, which is a normal operational action per `testCannotDepositWhenPaused` in the test suite) at the same moment the sequencer is trying to include that deposit's system transaction, and further requires that the deposit-removal call in the outer block-production function indeed uses the same unfiltered `deposit_data` that was passed into `process_sys_txs`.

### Recommendation
`process_sys_txs` should return, alongside `all_txs`, the subset of `deposit_data` entries that were actually applied successfully, and the caller should only pass that successful subset to `DepositDataMempool::remove_deposits`, leaving reverted deposits in the mempool for retry in a future block — mirroring the report's recommendation to not silently absorb reverts that leave external state (Bitcoin custody vs. Citrea minting) inconsistent.

### Proof of Concept
I was not able to fully trace, within the available tool budget, the exact origin of the `deposit_data` slice consumed by `remove_deposits` (line 636-643 of `runner.rs`) all the way back through the caller of `produce_and_run_system_transactions`/`process_sys_txs` to conclusively prove it is the same *unfiltered* list rather than one already filtered down to successes. This is the key fact needed to turn this into a fully proven finding rather than a strong structural hypothesis; a Devin session with full read access to `crates/sequencer/src/runner.rs` (the full block-production function, not just the excerpt inspected here) would be needed to confirm or refute whether `deposit_data` is filtered before the `remove_deposits` call.

```markdown
1. **Deposit Transaction**  
   The user initiates a Bitcoin transaction locking, e.g., 10 BTC. The UTXO created:
   - Can be reclaimed by the user after `t1` blocks, **or**
   - Can be spent by revealing the depositor’s **Citrea address** (via a covenant).

   Since Bitcoin does not yet support covenants, the depositor shares their Citrea address with the bridge **signers**, who then **pre-sign a MoveToVault transaction**.  
   This transaction transfers the BTC to a vault UTXO and reveals the depositor’s Citrea address on-chain. The vault output is structured such that it can be redeemed by the **Operator** who fronted the withdrawal amount in the Peg-Out phase.

2. **MoveToVault Submission & Light Client Interaction**  
   When the MoveToVault transaction is posted on Bitcoin, it reveals the recipient’s Citrea address.  
   Citrea runs a system contract called [**Bitcoin light client**](./bitcoin-light-client-contract.md), which will be used to verify the inclusion of this transaction.

3. **System Transaction Generation via RPC**  
   Clementine’s aggregator sends the deposit data to the Citrea Sequencer using the RPC call:
   `citrea_sendRawDepositTransaction`
    This generates a **Citrea system transaction** calling the [`deposit`](./bridge-contract.md) function of the Bridge Contract with:
    - The `MoveToVault` transaction
    - Merkle proof of its Bitcoin block inclusion (verified via the [`verifyInclusion`](../crates/evm/src/evm/system_contracts/src/BitcoinLightClient.sol) function  of the Light Client Contract)
    - SHA script pubkeys (for verifying Schnorr signatures in the MoveTx)

4. **Finalization**  
    Inside the `deposit` function:
    - Firstly witness is extracted, from witness,  the script, and from the script, the recipient address (depositor Citrea address) is extracted.
    - If validations are successful the **cBTC is minted** to the recipient’s Citrea account.
```
