Based on my investigation, I found a locally-provable, self-documented gap in replay-verification's `TransactionOutput::ensure_match_transaction_info`.

### Title
Replay-verification (`replay_on_archive`) accepts a transaction output whose position/state/hot-state checkpoint root diverges from the authenticated `TransactionInfo` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify` uses to decide whether a freshly re-executed transaction matches the archived, consensus-authenticated `TransactionInfo` — deliberately skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`. This is documented in-code as a known gap, not something already fixed.

### Finding Description
`ensure_match_transaction_info` checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly stops short of validating the checkpoint-root fields: [1](#0-0) 

The comment states plainly:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution.
``` [2](#0-1) 

`storage/db-tool/src/replay_on_archive.rs` is the concrete consumer: it re-executes archived transactions with `AptosVMBlockExecutor::execute_block` and calls `ensure_match_transaction_info` per-transaction as the sole correctness gate for the replay: [3](#0-2) 

Because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never compared here, this replay path will report "success" for a chunk even if the locally-recomputed Sparse-Merkle/Jellyfish state root (main state, hot state, or the newly-added native-position tree) differs from the value that was actually consensus-committed in the archived `TransactionInfoV1`. Note that the normal chunk-executor commit/sync path (`chunk_result_verifier.rs`'s `verify_chunk_result` → `ensure_transaction_infos_match`) does compare full `TransactionInfo` equality including these hashes, so state-sync and normal chunk replay are not affected — the gap is isolated to `ensure_match_transaction_info`, used by `replay_on_archive`, the CLI debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`), and `aptos-move/cli/src/commands.rs`.

### Impact Explanation
`replay_on_archive` and the debugger/CLI replay tools are the primary offline mechanisms operators and auditors use to independently verify that historical state roots (including the new `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` features once enabled) match what was committed by consensus. A local execution bug that corrupts the state/hot-state/position checkpoint root — while still producing the correct write-set hash and event root (state_change_hash and event_root_hash are independent of checkpoint-tree construction) — would go completely undetected by this verification path. This directly matches the required-impact criterion "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong accumulator root ... state proof accepted as valid," since the tool exists specifically to catch such divergence and silently doesn't.

### Likelihood Explanation
This is not a hypothetical: it's an explicit, acknowledged TODO in the shipped code guarding features (`TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that are being actively built out (native-position/trading-native subsystem). The comment itself says checkpoint-hash validation must be added "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS," indicating the authors know replay verification is currently blind to state-checkpoint-root regressions for this feature.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against locally-computed values before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`, so `replay_on_archive` and other consumers cannot report success while a checkpoint root has silently diverged.

### Proof of Concept
Not applicable as a runtime exploit — the finding is a verification-gap in offline tooling, provable by code inspection: `ensure_match_transaction_info`'s body at [4](#0-3)  never reads `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, while `replay_on_archive.rs`'s `execute_and_verify` at [5](#0-4)  relies solely on this function to flag mismatches.

Note: I was not able to fully confirm the current default/feature-flag rollout status of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` on mainnet (whether "Lifetime: permanent" implies already-active), which affects whether this gap is presently exploitable in production versus latent for an upcoming feature — a Devin session with broader repo/feature-flag-state access would be needed to confirm exact mainnet activation status.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
