## Title
Collateral ledger credits the nominal transfer amount without verifying tokens actually received, unsafe for fee-on-transfer/deflationary collateral - (File: `local-testing/contracts/market/market-vault.clar`, `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`market-vault.collateral-add` records a user's collateral balance using the caller-supplied `amount` argument, and separately calls `receive-tokens` to pull that same `amount` from the depositor. Neither step compares the contract's actual token balance before/after the transfer to the recorded amount, so any collateral asset that takes a fee (or otherwise delivers less than the nominal amount) on transfer causes the protocol to over-credit the depositor's collateral relative to what it actually custodies.

### Finding Description
In `collateral-add`, the `let` bindings compute and *persist* the new collateral amount via `add-user-collateral` before the body performs the token pull: [1](#0-0) 

`add-user-collateral` unconditionally adds the full `amount` parameter to the user's ledger entry: [2](#0-1) 

The actual fund-movement step, `receive-tokens`, simply forwards `amount` to the token's `transfer` function and trusts its `(ok true)` response — it never checks the contract's balance delta against `amount`: [3](#0-2) 

If the collateral token contract deducts a fee, rebases, or otherwise delivers less than `amount` to the recipient (the scenario in the referenced report: a token that starts fee-free and later enables a transfer fee), `transfer` still returns `(ok true)` for the requested `amount`, so `receive-tokens` succeeds. Because the collateral map was already set to reflect the full nominal `amount` (via the `let`-binding evaluation of `add-user-collateral`) and there is no post-transfer balance check to reconcile it, the position is permanently over-credited: the ledger says the vault holds `amount`, but it actually holds `amount - fee`. This is exactly the fee-on-transfer accounting mismatch identified in the source report, just relocated from Polynomial's `ShortCollateral._addCollateral` to Zest's `market-vault.collateral-add`. The identical pattern (mutate bookkeeping to the nominal `amount`, then call an external transfer whose actual delivered amount is not verified) also exists in `mainnet/contracts/market/v0-market-vault.clar` and in the vault `deposit` functions (e.g., `vault-sbtc.clar` `deposit`, which mints shares from `convert-to-shares-preview amount` before/around `receive-underlying`).

### Impact Explanation
Over-crediting collateral inflates a user's on-chain collateral value used for LTV/health calculations in `market.clar`, letting them borrow against value the protocol does not actually hold. Repeated or scaled use of a fee-bearing (or otherwise short-delivering) approved collateral asset directly erodes the backing of the pool relative to recorded liabilities, i.e., protocol insolvency — collateral bookkeeping exceeds actual custodied assets, and there is no mechanism (balance check, or ability to disable/remove such an asset's use once misbehaving) to prevent or correct this.

### Likelihood Explanation
Requires only that a DAO-approved collateral asset's transfer behavior changes to deliver less than the requested amount (fee-on-transfer, rebasing, or similar) — this is not a DAO compromise, since the asset was legitimately approved before the behavior changed, matching the original report's premise. Any user depositing such an asset via the standard `collateral-add`/`market.collateral-add` path triggers the mismatch in a single transaction.

### Recommendation
After calling `receive-tokens`/`receive-underlying`, measure the token's actual balance delta on the contract (e.g., `get-balance` before and after the transfer) and credit the collateral ledger / mint shares using that delta rather than the caller-supplied `amount`. Additionally, provide a DAO-controlled mechanism to disable a collateral asset that begins behaving unexpectedly.

### Proof of Concept
1. DAO registers and enables token `X` as collateral when it has zero transfer fee.
2. Token `X`'s issuer later enables a transfer fee (e.g., 1%).
3. User calls `collateral-add` (`market.clar` → `market-vault.collateral-add`) with `amount = 1000`.
4. `add-user-collateral` sets the user's ledger entry to `+1000` (evaluated in the `let` bindings): [2](#0-1) 
5. `receive-tokens` calls `transfer 1000 ...`, which succeeds but only delivers `990` to the vault due to the fee: [3](#0-2) 
6. Transaction completes successfully; the user's recorded collateral is `1000` while the contract's actual token balance only increased by `990`, creating a permanent 10-unit deficit backing borrowing power.

(define-private (add-user-collateral (user-id uint) (asset-id uint) (amount uint))
  (let ((key { id: user-id, asset: asset-id })
        (collateral-amount (default-to u0 (map-get? collateral key))) ;; graceful default
        (updated-collateral-amount (+ collateral-amount amount)))
      (map-set collateral key updated-collateral-amount)
      updated-collateral-amount))

        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true)) ;; collateral, insert
        (updated-entry (merge entry (refresh updated-mask)))
        (result (add-user-collateral user-id asset-id amount)))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
