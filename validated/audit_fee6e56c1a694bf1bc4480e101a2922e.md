Based on my investigation, I found one credible, locally-provable candidate, but with an important caveat about scope/exploitability that I could not fully resolve within available iterations. I'll present it along with that caveat rather than overstate confidence.

### Title
`TransactionOutput::ensure_match_transaction_info` skips validating checkpoint/proof-root hash fields used by state-sync chunk execution - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the comparator that checks a freshly re-executed `TransactionOutput` against the `TransactionInfo` that was bundled with a transaction chunk (itself authenticated by an accumulator proof against a signed `LedgerInfo`). It validates status, gas, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents with a `TODO(trading-native)` comment.

### Finding Description [1](#0-0) 

The function hashes and compares `write_set` and `events` against the values recorded in the authenticated `TransactionInfo`, but the comment at lines 2197-2202 states plainly that the checkpoint hashes (main/hot state and `position_state_checkpoint_hash`) are ignored, and that this allows replay-verify tooling to report success even when "the authenticated position state root diverges from local execution."

This comparator is not confined to an offline debugging tool — it is invoked from the actual chunk-executor commit path used during state sync: [2](#0-1) 
as well as from `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. In `replay_on_archive.rs`, it is the sole per-transaction correctness check performed after re-execution: [3](#0-2) 

Because the check never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` against expectation, a locally computed state root that diverges from the chain's authenticated Merkle root at a checkpoint boundary would not be flagged as a mismatch by this function alone.

### Impact Explanation
If this comparator is the only safeguard along a given commit/verification path, a divergence between locally re-executed state and the chain's committed (authenticated) state root would go undetected — i.e., corrupted/incorrect ledger state could be accepted as "verified" by tooling or a sync path relying solely on this check. This maps to the "committed state differs from correct VM result" and "wrong... state proof accepted as valid" impact classes in scope.

However, I could not fully confirm, within the available search budget, whether the **main** `state_checkpoint_hash` is independently re-validated elsewhere in the chunk-executor commit path (e.g. via the SMT/checkpoint-hash logic in `execution/executor/src/workflow/do_state_checkpoint.rs`, which does perform its own "known-hash validation" for position/hot state roots separately from `ensure_match_transaction_info`). If that independent validation always runs before commit, the practical exploitability of this specific comparator's gap is limited to `replay_on_archive`/debugger tooling (a diagnostic/monitoring gap rather than a consensus-committed state-corruption path), and the checkpoint-hash fields in question (`hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are tied to a "trading-native" feature gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, which the comment implies is not yet fully enabled.

### Likelihood Explanation
Low-to-uncertain. This is a self-documented, intentional TODO rather than an accidental oversight, and the affected fields belong to a feature that appears not yet fully active. I was not able to conclusively determine, before the iteration limit, whether any other check redundantly enforces the main `state_checkpoint_hash` on the same commit path that calls `ensure_match_transaction_info`, which is necessary to establish real mainnet exploitability versus a diagnostic-tooling-only gap.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` (and, once the trading-native feature is enabled, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the values computed from local re-execution, so that any commit or replay-verification path relying on this single comparator cannot silently accept a divergent state root. At minimum, gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS` enablement on this comparator being completed, as the comment itself indicates.

### Proof of Concept
Not independently reproducible from static analysis alone; the finding rests on the documented comparator gap at `types/src/transaction/mod.rs:2197-2202` and its production call sites. Confirming end-to-end exploitability would require verifying, at runtime, whether `execution/executor/src/chunk_executor/mod.rs`'s commit path has any other checkpoint-hash validation guarding it — this could not be completed within the available investigation budget.

**Caveat on confidence:** Given the acknowledged uncertainty about redundant validation elsewhere and the feature-gated nature of the affected hash fields, I cannot assert with high confidence that this constitutes an exploitable High/Critical mainnet integrity break today. I'm reporting it because it is the strongest locally-supported candidate found, but flag it as needing further confirmation (specifically, whether `do_state_checkpoint.rs`'s "known-hash validation" independently and unconditionally covers every path that also calls `ensure_match_transaction_info`) before being treated as a confirmed vulnerability rather than a documented tooling gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
