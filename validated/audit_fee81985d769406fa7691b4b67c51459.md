### Title
`citrea_network_to_chain_id` maps `Network::Nightly` and `Network::TestNetworkWithForks` to the same chain id, breaking the per-network uniqueness binding used to gate `BatchProofMethodId` replay - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
The binding claimed by the check at `run_l1_block` (`circuit_chain_id != batch_proof_method_id.body.chain_id`) is: every `Network` variant maps to a distinct `chain_id`. `citrea_network_to_chain_id` actually returns `5665` for both `Network::Nightly` and `Network::TestNetworkWithForks`, so the equality holds simultaneously for two distinct networks. Additionally, by default (absent env-var overrides) `initial_values.rs` configures `TestNetworkWithForks`'s sequencer DA key, batch-prover DA key and method-id-upgrade council keys to be byte-identical to `Nightly`'s defaults.

### Finding Description
Binding as claimed: `∀ n1 ≠ n2 ∈ Network, citrea_network_to_chain_id(n1) ≠ citrea_network_to_chain_id(n2)`.

Actual code: [1](#0-0) 
returns `Mainnet=4114, Testnet=5115, Devnet=62298, Nightly=5665, TestNetworkWithForks=5665` — `Nightly` and `TestNetworkWithForks` collide at `5665`, falsifying the binding.

This value is consumed in `run_l1_block`'s `BatchProofMethodId` handling: [2](#0-1) 
where `circuit_chain_id = citrea_network_to_chain_id(network)` is compared against `batch_proof_method_id.body.chain_id` before calling `verify_method_id_security_council`. Because the comparison is satisfied identically for both `Nightly` and `TestNetworkWithForks`, this check provides zero cross-network separation between those two specific variants — a signed `BatchProofMethodIdBody{chain_id: citrea_network_to_chain_id(Network::Nightly)}` (i.e. `chain_id == 5665`) passes the guard on a `TestNetworkWithForks` deployment exactly as it would on `Nightly`, and vice versa.

Compounding this, `InitialValueProvider<BitcoinSpec>::method_id_upgrade_authority_da_public_keys`/`sequencer_da_public_key`/`batch_prover_da_public_key` for `TestNetworkWithForks` default (when the corresponding env vars are unset at compile time) to the exact same constants as `Nightly`: [3](#0-2) [4](#0-3) 

Under this default configuration, a council-signed `BatchProofMethodId` blob genuinely produced (and inscribed on the DA appropriate for `Nightly`) is byte-for-byte acceptable on a `TestNetworkWithForks` light-client-prover instance sharing the default keys, because both the `chain_id` check and the signature-over-council-keys check pass identically.

However, `TestNetworkWithForks` is explicitly documented as a test-only construct — "All forks from genesis to Nightly / This is used for testing purposes only" [5](#0-4)  — and it is wired only to regtest guest ELFs (`BATCH_PROOF_REGTEST_BITCOIN_GUESTS`, `LIGHT_CLIENT_LATEST_BITCOIN_GUESTS`) in `bin/citrea/src/rollup/bitcoin.rs` [6](#0-5) , not a distinct live production network with its own Bitcoin DA that an unprivileged attacker could target alongside a real Nightly deployment. There is no evidence in the repository that `Mainnet` and `Testnet` (the pair named in the question) collide, nor that any production/public-facing deployment reuses this chain_id with `Nightly`'s DA council keys in a way reachable by an unprivileged attacker holding only a captured public blob and no privileged role.

### Impact Explanation
As specified, this would be a Critical-category concern ("method-id upgrade accepted that was never authorised") if it were reachable against a real, independently-operated Citrea network. The concrete collision found (`Nightly` vs `TestNetworkWithForks`) is between one production-adjacent network (`Nightly`) and an internal test-harness-only variant that is not exposed as a standalone attacker-reachable public deployment with its own Bitcoin DA per the code paths inspected. No collision was found between `Mainnet` and `Testnet`/`Nightly` as posited in the question — those chain ids (4114, 5115, 5665) are pairwise distinct.

### Likelihood Explanation
Exploiting the actual collision (`Nightly` ↔ `TestNetworkWithForks`) requires: (1) a genuine council-signed blob for one of those two networks to exist and be publicly observable on DA, and (2) a running light-client-prover configured for the other of the two networks with the default (non-overridden) council/sequencer/prover keys. `TestNetworkWithForks` is used only in the internal e2e fork test harness, not as a standing public deployment; there's no demonstrated attacker-reachable target satisfying (2) outside of test infrastructure, which is explicitly out of scope per the rules (mocks/tests, test-only network). No collision exists for the `Mainnet`/`Testnet` pair actually named in the question.

### Recommendation
Make `citrea_network_to_chain_id` return a unique value for every `Network` variant (e.g., give `TestNetworkWithForks` its own chain id distinct from `Nightly`), and add a compile-time or unit-test assertion enumerating all `Network` variants and asserting pairwise distinctness to prevent silent future collisions.

### Proof of Concept
```rust
#[test]
fn chain_ids_are_pairwise_distinct() {
    use sov_rollup_interface::Network::*;
    let all = [Mainnet, Testnet, Devnet, Nightly, TestNetworkWithForks];
    for i in 0..all.len() {
        for j in (i+1)..all.len() {
            assert_ne!(
                citrea_network_to_chain_id(all[i]),
                citrea_network_to_chain_id(all[j]),
                "{:?} and {:?} share chain_id", all[i], all[j]
            );
        }
    }
}
```
This test fails today because `citrea_network_to_chain_id(Nightly) == citrea_network_to_chain_id(TestNetworkWithForks) == 5665`, proving the binding is broken at the `Network` level, though not for the `Mainnet`/`Testnet` pair named in the question, and not against any attacker-reachable production deployment identified in this repository.
