## Title
TRC10 Exchange pool balances can go negative in legacy (non-hardened) mode, permanently corrupting shared pool state and bricking all subsequent Exchange operations - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The reported bug describes a shared accounting cap (`borrowCaps`) that can be pushed past its limit by a privileged/system-level flow (`harvestFees`), after which an ordinary unprivileged operation (`availableBorrow`, invoked on every deposit/withdraw) underflows and reverts for everyone. The equivalent shared-resource-cap pattern in java-tron is the TRC10 **Exchange** (bancor-style AMM pool) balances stored in `ExchangeCapsule`, which are a single shared piece of state (`firstTokenBalance`/`secondTokenBalance`) consumed by every subsequent `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` call against that exchange ID.

### Finding Description
`ExchangeCapsule.transaction()` computes new pool balances using either a legacy double-precision path (`ExchangeProcessor`) or a "hardened" `SafeExchangeProcessor` path, selected by the `allowHardenExchangeCalculation` chain parameter: [1](#0-0) 

Only the hardened branch validates the invariant that pool balances must stay non-negative after a trade: [2](#0-1) 

In the legacy (default, non-hardened) path, `ExchangeProcessor.exchange()` performs the bancor relay math with plain `double` arithmetic and no bounds checking at all: [3](#0-2) 

Because of floating point rounding, extreme trade sizes, or repeated dust trades, `newFirstTokenBalance`/`newSecondTokenBalance` in the legacy path can go negative (as confirmed by the project's own test `testHardenedTransactionNegativeBalanceThrows`, which demonstrates that only the hardened path detects/rejects this): [4](#0-3) 

Once the shared `ExchangeCapsule` balance is corrupted to a negative (or otherwise invalid) value, every subsequent unprivileged user action against that exchange ID is affected: `ExchangeWithdrawActuator` performs `BigInteger` division using the corrupted balance as a divisor/multiplier and then calls `subtractExact` on the results, `ExchangeInjectActuator` performs `floorDiv(multiplyExact(...))` using the corrupted balance, and `ExchangeTransactionActuator` calls `exchangeCapsule.transaction(...)` again on the same broken state: [5](#0-4) [6](#0-5) 

Any of these operations can throw `ArithmeticException` (e.g., division by a non-positive/zero balance, or `longValueExact()`/`subtractExact` failures on out-of-range values) which is caught and converted into `ContractExeException`, causing the transaction to fail: [7](#0-6) 

This mirrors the report's structure exactly: a shared accounting/cap value (senior vault borrow cap vs. exchange pool balance) can be driven into an invalid range by one flow, and a completely unrelated, routine unprivileged function (`availableBorrow` vs. `ExchangeWithdraw/Inject/Transaction`) then permanently reverts for every user of that shared resource, because there is no floor/clamp check in the "hot" default code path.

### Impact Explanation
Once a given Exchange ID's pool state is corrupted under the legacy math path, that specific exchange becomes permanently unusable for deposits, withdrawals, injections, and further trades — every unprivileged user attempting to interact with it will have their transactions fail. This is a persistent, invalid-state/halt condition on that shared exchange resource, matching the "public function bricked due to unchecked shared accounting" impact class described in the report, though scoped to the affected Exchange rather than the whole chain.

### Likelihood Explanation
This requires `allowHardenExchangeCalculation` to be inactive (its default/legacy state, matching the pattern of other "Allow*" feature-flags in this codebase which require an explicit committee proposal to activate) and requires an attacker/legitimate large or repeated small trade to push the double-precision bancor formula's result negative. This is a purely user-triggerable sequence (`ExchangeTransactionContract`/`ExchangeInjectContract`) requiring no privileged role, satisfying the "unprivileged-user analog" requirement. Exact triggering parameters (specific `sellTokenQuant`/pool ratios needed to drive balances negative under double-precision rounding) were not fully reproduced/proven numerically within this review — this should be validated with a concrete PoC harness before treating it as confirmed exploitable in production.

### Recommendation
Apply the same non-negative invariant check used in the hardened path (`SafeExchangeProcessor` / the `< 0` guard in `ExchangeCapsule.transaction`) unconditionally in the legacy path as well, rather than gating it behind `allowHardenExchangeCalculation`, so that no exchange pool can ever be committed to a negative-balance state, analogous to clamping `availableBorrow` at zero in the original report's recommendation.

### Proof of Concept
Not independently reproduced with concrete numeric inputs in this review. The existing regression test `ExchangeCapsuleTest#testHardenedTransactionNegativeBalanceThrows` (and the accompanying `testHardenedTransactionSecondTokenSell`) demonstrates the underlying mechanism — that the legacy `ExchangeProcessor` path lacks the negative-balance guard that the hardened path enforces — but a full end-to-end PoC (specific trade sequence via `ExchangeTransactionActuator` with `allowHardenExchangeCalculation=0` that drives `firstTokenBalance`/`secondTokenBalance` negative and then demonstrates a subsequent legitimate withdraw/inject reverting) was not executed here and should be built by a background engineer to confirm exploitability before remediation.   public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public void testHardenedTransactionSecondTokenSell() throws Exception {
    byte[] key = ByteArray.fromLong(1);
    ExchangeCapsule capsule = chainBaseManager.getExchangeStore().get(key);
    capsule.setBalance(100_000_000L, 100_000_000L);

    long sellQuant = 1_000_000L;
    long buyQuant = capsule.transaction("def".getBytes(), sellQuant, true, true);

    Assert.assertTrue(buyQuant > 0);
    Assert.assertEquals(100_000_000L - buyQuant, capsule.getFirstTokenBalance());
    Assert.assertEquals(100_000_000L + sellQuant, capsule.getSecondTokenBalance());
  }

  @Test
  public void testHardenedTransactionNegativeBalanceThrows() throws Exception {
    // Construct a corrupt-state pool with a negative balance to drive the
    // < 0 invariant in the hardened branch via subtractExact wrapping.
    ExchangeCapsule capsule = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 99L, 0L,
        "abc".getBytes(), "def".getBytes());
    capsule.setBalance(Long.MAX_VALUE, 1L);

    // Selling abc adds to firstTokenBalance: addExact(MAX, q) overflows -> ArithmeticException
    Assert.assertThrows(ArithmeticException.class,
        () -> capsule.transaction("abc".getBytes(), 1L, true, true));
