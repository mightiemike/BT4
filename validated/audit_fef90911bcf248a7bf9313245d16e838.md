### Title
DeleteAccount to a beneficiary that cannot receive the balance-refund transfer permanently burns the account's funds instead of failing atomically - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`DeleteAccountAction` immediately deletes the account and schedules the remaining balance as a separate, asynchronous system `Transfer` receipt to `beneficiary_id`. If that receipt later fails to execute (e.g. `beneficiary_id` is a syntactically valid but non-existent named account), the deletion itself has already committed and cannot be rolled back — the runtime's only fallback for a failed refund is to permanently burn the tokens.

### Finding Description
`action_delete_account` computes the account's `amount()` and unconditionally enqueues it as a new system-originated balance-refund receipt to `delete_account.beneficiary_id`, then removes the account from state in the same step: [1](#0-0) 

That refund receipt is built via `Receipt::new_balance_refund`, which is a single `Action::Transfer` receipt with `predecessor_id == "system"`: [2](#0-1) 

When this receipt is later applied, `check_account_existence` is invoked for the `Action::Transfer` case. A named (non-implicit) `beneficiary_id` that does not exist cannot be implicitly created by a transfer, even when the transfer is the receipt's only action — this is an intentionally-pinned invariant: [3](#0-2) [4](#0-3) 

So the refund receipt fails with `AccountDoesNotExist`. Crucially, refund receipts have no second-level fallback: the runtime explicitly documents and implements that a failed refund's deposit is burned rather than returned anywhere: [5](#0-4) [6](#0-5) 

The `DeleteAccount` action's validation only checks that `beneficiary_id` is a syntactically valid account id and that it is the final action in the receipt — it never checks that the account actually exists or can receive value: [7](#0-6) 

By contrast, tests show the developers are aware the beneficiary must exist for the funds to survive ("The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" — but note that comment is inaccurate for a *named*, non-existent beneficiary: there is no "come straight back," the funds are burned since the failed receipt is itself a system refund): [8](#0-7) 

This is structurally the same bug class as the reported ERC20-blocklist issue: a push-style value transfer to a receiver that is unable to receive it is not validated up front, is not atomic with the state-destroying operation that produced it, and has no pull-based fallback — so the value becomes permanently unrecoverable once the primary action (account deletion) has already committed.

### Impact Explanation
Any account holder can lose their entire remaining NEAR balance irrecoverably in a single self-submitted transaction by naming a non-existent `beneficiary_id` (e.g. a typo, a not-yet-created sub-account, or an account that is deleted/never created between transaction construction and execution). Unlike an ordinary failed `Transfer` action — which is refunded back to the predecessor via a normal deposit refund — a refund receipt that itself fails has no predecessor to return to and is burned outright. This is a genuine, transaction-triggered, permanent, irreversible loss of user funds (effectively a supply-destroying bug), matching the "permanently frozen funds" / value-loss category, with no way for the user or anyone else to recover the tokens afterward.

### Likelihood Explanation
High reachability: any unprivileged account owner can trigger this with a single `DeleteAccount` transaction they fully control, and no additional permission or attacker cooperation is required — a simple mistake in specifying `beneficiary_id` (or a beneficiary account being removed/never created before the receipt executes) is sufficient. There is no pre-execution check that `beneficiary_id` exists.

### Recommendation
Validate that `beneficiary_id` refers to an existing account (or is a valid implicit-creatable id) before committing the account deletion, or make the deletion and the balance transfer atomic (i.e., fail the whole `DeleteAccount` action if the beneficiary cannot receive funds) instead of deleting the account first and relying on a best-effort, burn-on-failure refund receipt.

### Proof of Concept
1. Create/own account `alice.near` with a positive balance.
2. Submit a transaction from `alice.near` containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent-name.near" })`, where `nonexistent-name.near` has never been created.
3. `action_delete_account` runs: `alice.near` is removed from state and a `Receipt::new_balance_refund("nonexistent-name.near", alice_balance)` is queued [9](#0-8) .
4. That system refund receipt executes against `nonexistent-name.near`; `check_account_existence` rejects the `Transfer` with `AccountDoesNotExist` because a named account cannot be implicitly created [3](#0-2) .
5. Because `receipt.predecessor_id().is_system()` and the result is `Err`, the runtime adds `alice_balance` to `other_burnt_amount` instead of refunding anyone [6](#0-5) .
6. Result: `alice.near`'s entire balance is permanently destroyed; no account holds it.

## DeleteAccountAction

```rust
pub struct DeleteAccountAction {
    /// The remaining account balance will be transferred to the AccountId below
    pub beneficiary_id: AccountId,
}
```

**Outcomes**:

- The account, as well as all the data stored under the account, is deleted and the tokens are transferred to `beneficiary_id`.

### Errors

**Validation Error**:

- If `beneficiary_id` is not a valid account id, the following error will be returned

```rust
/// Invalid account ID.
InvalidAccountId { account_id: AccountId },
```

- If this action is not the last action in the action list of a receipt, the following error will be returned

```rust
/// The delete action must be a final action in transaction
DeleteActionMustBeFinal
```

- If the account still has locked balance due to staking, the following error will be returned

```rust
/// Account is staking and can not be deleted
DeleteAccountStaking { account_id: AccountId }
```

**Execution Error**:

- If state or storage is corrupted, a `StorageError` is returned.
