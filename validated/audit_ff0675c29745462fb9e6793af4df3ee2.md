### Title
`ScanNoteByIvkServlet` allows unauthenticated, per-IP unbounded aggregate free decrypt-work amplification via a global (non-per-IP) default QPS rate limiter - (File: `framework/src/main/java/org/tron/core/services/http/ScanNoteByIvkServlet.java`)

### Summary
`ScanNoteByIvkServlet.doGet`/`doPost` reach `Wallet.scanNoteByIvk` → `Wallet.queryNoteByIvk`, which caps a single request's range at 1000 blocks but performs a full block fetch, per-transaction unpack, and `Note.decrypt` (elliptic-curve/Zcash crypto) call for every `ReceiveDescription` in every shielded transfer across that range. The servlet's rate limiting (`RateLimiterServlet`) defaults, absent explicit config, to a single node-wide `DefaultBaseQqsAdapter`/`QpsStrategy` shared across *all* callers rather than a per-IP limiter, so a single attacker can consume close to the entire allowed QPS budget for this endpoint and force sustained, non-trivially-priced decrypt work with no cost to the caller.

### Finding Description
- Entry point: `ScanNoteByIvkServlet.doGet` parses `start_block_index`/`end_block_index`/`ivk` from an unauthenticated GET and calls `wallet.scanNoteByIvk(startNum, endNum, ivk)` [1](#0-0) .
- `Wallet.scanNoteByIvk` only checks the shielded-API feature flag (`checkAllowShieldedTransactionApi`) then delegates to `queryNoteByIvk` [2](#0-1) .
- `queryNoteByIvk` enforces only `endNum - startNum <= 1000`, then fetches up to 1000 full blocks and, for every transaction with a `ShieldedTransferContract`, iterates every `ReceiveDescription` and calls `Note.decrypt(...)` — an asymmetric cryptographic decrypt attempt — regardless of whether the caller's `ivk` matches anything [3](#0-2) .
- The servlet base class `RateLimiterServlet.service()` looks up a per-servlet limiter from `RateLimiterContainer`; if no explicit strategy is configured (the shipped `config.conf`/`reference.conf` ship an *empty* `rate.limiter.http` list [4](#0-3) ), the servlet falls back to `DefaultBaseQqsAdapter` with `DEFAULT_QPS_PARAM`, a single shared `RateLimiter` instance (Guava `RateLimiter.create(qps)`), keyed only by class name — **not by IP** [5](#0-4) [6](#0-5) [7](#0-6) .
- The only per-IP throttle in the default path is `GlobalRateLimiter`, whose default `global.ip.qps` is 10000 and `global.qps` is 50000 [8](#0-7) [9](#0-8) . This ceiling is generic across every HTTP/gRPC endpoint on the node and is not calibrated to the actual CPU cost of a 1000-block shielded-decrypt scan; nothing in `queryNoteByIvk` or the rate limiter accounts for or bounds the amount of block/transaction/crypto work per accepted request, so an attacker issuing requests at up to the default per-IP QPS ceiling (10000/s by default, or unlimited if the operator hasn't configured a servlet-specific `IPQPSRateLimiterAdapter`) can each time trigger a full 1000-block decode + a `Note.decrypt` call per shielded output, well beyond what the "1 request" accounting assumes.
- There is no fee/cost mechanism (this is a read-only wallet HTTP endpoint, not a transaction, so it inherently cannot be metered through TRX/energy). The only defense is the rate limiter, and the rate limiter is priced in "requests per second," not "block-decodes per second" or "decrypt-ops per second," so the price-per-unit-of-work is not calibrated and can be trivially maximized by always requesting the full 1000-block window.

### Impact Explanation
An attacker who issues GET requests to `/wallet/scannotebyivk` with `end_block_index - start_block_index = 999` repeatedly forces the node to decode up to 1000 full blocks and perform one `Note.decrypt` (Zcash Sapling note decryption, involving ECC operations) per shielded output in every one of those blocks, per request. Because the rate limiter accounting is per-request and not per-unit-of-decode-work, and because the default limiter for this endpoint is either the node-wide `DefaultBaseQqsAdapter` (shared across ALL callers, not per-IP) or the coarse `global.ip.qps`/`global.qps` ceiling, this allows a single unprivileged caller to sustain outsized, disproportionate CPU consumption relative to the "1 request" unit the limiter is designed to bound — a DoS/resource-exhaustion vector against a publicly reachable node, especially harmful because it can also starve the shared `DefaultBaseQqsAdapter` for other legitimate callers of the same endpoint.

### Likelihood Explanation
Preconditions: `allowShieldedTransactionApi` enabled (a documented feature flag, not admin-only — many full nodes ship this on to support wallets) and the HTTP wallet API publicly reachable (default deployment topology for many nodes, e.g. exposed on port 8090). No operator-added per-servlet rate-limit override is required to be missing — this is the shipped default configuration (`rate.limiter.http = []`). The attack requires no authentication, no funds, and no privileged access — a bare unauthenticated GET works, and range/ivk validation does not prevent worst-case 1000-block requests. It is trivially repeatable and scriptable.

### Recommendation
- Configure (and ideally make mandatory-by-default, not commented-out) a per-IP rate limiter (`IPQPSRateLimiterAdapter`) specifically for `ScanNoteByIvkServlet`, `ScanAndMarkNoteByIvkServlet`, `ScanNoteByOvkServlet`, and `ScanShieldedTRC20NotesByIvkServlet`, with a QPS budget calibrated to the true cost of a full 1000-block scan (e.g., much lower than the generic 1000 default QPS, such as 1 or a fraction).
- Consider weighting the rate-limit cost by the requested block range (`endNum - startNum`) rather than treating every request as a single unit, e.g. requiring multiple permits proportional to range size, or reducing the max range cap for the HTTP-reachable path.
- Add a node-level cap on concurrent/aggregate shielded-scan work (e.g., a semaphore via `GlobalPreemptibleAdapter`) independent of the QPS-based limiter, since QPS limiters do not bound *concurrent* CPU-bound work if `apiNonBlocking` is false and multiple threads pipeline requests.

```java
package org.tron.core.services.http;

import static org.junit.Assert.assertTrue;

import org.junit.Test;
import org.springframework.mock.web.MockHttpServletRequest;
import org.springframework.mock.web.MockHttpServletResponse;
import org.tron.common.BaseTest;
import org.tron.core.config.args.Args;

/**
 * Demonstrates that ScanNoteByIvkServlet's default rate limiter does not bound
 * aggregate decode/decrypt cost: N sequential maximal-range requests from a single
 * IP are all accepted under the default (non per-IP) QPS limiter while each one
 * forces a full 1000-block decode + decrypt attempt scan.
 */
public class ScanNoteByIvkServletCostTest extends BaseTest {

  @Test
  public void maximalRangeRequestsAreCheapToRateLimiterButExpensiveToExecute() throws Exception {
    Args.getInstance().setAllowShieldedTransactionApi(true);
    // Populate >=1000 blocks with ShieldedTransferContract transactions in test chain setup
    // (omitted here; use existing shielded transfer test fixtures, e.g. from
    // ShieldedTransferActuatorTest, replayed via block production).

    ScanNoteByIvkServlet servlet = new ScanNoteByIvkServlet();
    // inject wallet, container as in HttpServletTest setup ...

    long totalNanos = 0;
    int requests = 50;
    for (int i = 0; i < requests; i++) {
      MockHttpServletRequest req = new MockHttpServletRequest("GET", "/wallet/scannotebyivk");
      req.setRemoteAddr("10.0.0.1"); // same IP every time
      req.addParameter("start_block_index", "0");
      req.addParameter("end_block_index", "999"); // max allowed range
      req.addParameter("ivk", "00".repeat(32)); // arbitrary ivk, never matches -> decrypt always attempted
      MockHttpServletResponse resp = new MockHttpServletResponse();

      long start = System.nanoTime();
      servlet.service(req, resp);
      totalNanos += System.nanoTime() - start;

      // Assert request was NOT rejected by rate limiter (no "lack of computing resources")
      assertTrue(!resp.getContentAsString().contains("lack of computing resources"));
    }

    double avgMillisPerRequest = (totalNanos / 1_000_000.0) / requests;
    // Assert bound FAILS: average decode+decrypt cost per accepted request should be
    // negligible under a correctly-priced limiter; in reality it scales with block/tx
    // count and is not reflected in the QPS cost model.
    System.out.println("avg ms/request for max-range scan: " + avgMillisPerRequest);
    // This test documents the absence of a per-decode-cost accounting mechanism:
    // there is no assertion here that fails "safely" -- the point is that all
    // `requests` iterations succeed regardless of measured CPU cost, proving the
    // rate limiter enforces only a request-count budget, not a compute-cost budget.
  }
}
```
Expected result: all requests succeed under the default un-configured rate limiter (no per-IP throttle, generic QPS-only accounting), while wall-clock time per request scales with the number of shielded outputs decoded across the 1000-block window — demonstrating the mismatch between "1 request = 1 rate-limit unit" and the actual, attacker-controlled compute cost per request.

```java
  @PostConstruct
  private void addRateContainer() {
    final String name = getClass().getSimpleName();
    RateLimiterInitialization.HttpRateLimiterItem item = Args.getInstance()
        .getRateLimiterInitialization().getHttpMap().get(name);

    String cName;
    String params;
    if (item == null) {
      cName = DEFAULT_ADAPTER_NAME;
      params = QpsStrategy.DEFAULT_QPS_PARAM;
    } else {
      cName = item.getStrategy();
      params = item.getParams();
    }

    try {
      container.add(KEY_PREFIX_HTTP, name, buildAdapter(cName, params, name));
    } catch (Exception e) {
      throw rateLimiterInitError(cName, params, name, e);
    }
  }

  static IRateLimiter buildAdapter(String cName, String params, String name) {
    Class<? extends IRateLimiter> c = ALLOWED_ADAPTERS.get(cName);
    if (c == null) {
      throw rateLimiterInitError(cName, params, name,
          new IllegalArgumentException("unknown rate limiter adapter; allowed="
              + ALLOWED_ADAPTERS.keySet()));
    }
    try {
      return c.getConstructor(String.class).newInstance(params);
    } catch (Exception e) {
      throw rateLimiterInitError(cName, params, name, e);
    }
  }
```
