### Title
Unbounded recursion in compiled-class-hash bytecode-segment hashing outside the resource-limited compiler sandbox - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
`bytecode_hash_node` recursively walks the `NestedIntList` bytecode-segment tree of a compiled Sierra→CASM class with no depth bound, and it is invoked from `SierraCompiler::compile` *after* the CASM compilation subprocess has already returned — i.e. outside of the CPU/memory `ResourceLimits` sandbox that protects the actual compilation step. This mirrors the tcpdump BGP parser bug: unbounded, attacker-influenced recursion over untrusted structured data with no depth guard, performed in the unprotected parent process.

### Finding Description
When a `declare` transaction is validated/compiled, `SierraCompiler::compile` first compiles the Sierra program to CASM inside a resource-limited subprocess (`ResourceLimits` sets CPU-time and memory rlimits, see `crates/apollo_compilation_utils/src/compiler_utils.rs` and `crates/apollo_compile_to_casm/src/compiler.rs`), but the resulting `CasmContractClass` is then hashed in the *calling* (unsandboxed) process: [1](#0-0) 

That hash call reaches `HashableCompiledClass::hash` → `hash_inner` → `bytecode_hash`, which recurses into `bytecode_hash_node`: [2](#0-1) 

`bytecode_hash_node` recurses once per level of the `NestedIntList` bytecode-segment tree via `node.iter_children()`, with no maximum-depth check anywhere in this function or its callers: [3](#0-2) 

The `NestedIntList` structure reflects the nested branch/segment structure produced by the Sierra→CASM compiler for the submitted class's bytecode (functions divided into branches, sub-branches, etc., as documented for the analogous Cairo hint in `bytecode_hash_node` of the Starknet OS): [4](#0-3) 

Because the segment nesting depth is a function of the *control-flow nesting* the declarer chooses to write in their Sierra program, an attacker can deliberately construct a class whose CASM control flow produces a deeply right-nested/skewed segment tree (e.g., a long chain of nested `match`/branch constructs, one per bytecode instruction group). The `SierraToCasmCompiler` bounds only `max_bytecode_size`, `max_memory_usage`, and `max_cpu_time` for the *compilation* step itself; none of these caps limit the depth of the resulting segment tree, and none of them protect the subsequent, unsandboxed `hash()` call: [5](#0-4) 

This differs fundamentally from the entry-point call recursion in the blockifier, which is explicitly guarded by `RecursionDepthGuard` / `max_recursion_depth` and terminated by Sierra-gas/step accounting before a stack overflow can occur: [6](#0-5) [7](#0-6) 
No equivalent guard exists for `bytecode_hash_node`.

### Impact Explanation
If the recursion depth of `bytecode_hash_node` exceeds the native thread stack size of the sequencer/gateway/class-manager process computing the hash, the process crashes with a stack overflow. Since this hashing happens in the main sequencer process (not the sandboxed compile subprocess, and not under Cairo VM step/gas accounting), a crash here brings down the node process handling declare transactions — a single malicious but well-formed `declare` transaction (or a class propagated via the class manager/compiler service) can cause denial of service across nodes that compile/hash the same class, i.e., "a network unable to confirm new transactions" if this hits enough sequencers simultaneously, or repeated node crashes/restarts for any node that processes the class.

### Likelihood Explanation
Reachable directly from a single `declare` transaction's Sierra program content, which is fully attacker-controlled (an unprivileged contract declarer). The Sierra→CASM compiler enforces `max_bytecode_size`/`max_memory_usage`/`max_cpu_time` on the subprocess but no explicit limit on branch/segment nesting depth, and the hashing step executes entirely outside that sandbox. Constructing Sierra code that yields deep segment nesting is a standard code-generation exercise (deeply nested conditionals/match arms), making this practically reachable, though the exact required nesting depth to overflow a given stack size was not verified against the compiler's actual segment-tree generation logic (which lives in the external `cairo-lang-sierra-to-casm` crate, not in this repository) — this is the main remaining uncertainty.

### Recommendation
- Add an explicit maximum recursion/tree-depth check in `bytecode_hash_node` (and its Cairo OS counterparts) and return an error/reject the class instead of recursing unbounded.
- Convert `bytecode_hash_node` to an iterative, explicit-stack-based traversal so recursion depth is decoupled from the process's native call stack.
- Enforce the hash computation for a newly compiled class inside the same resource-limited subprocess/sandbox as the CASM compilation itself (or re-apply CPU/stack/memory limits around the `hash()` call in `SierraCompiler::compile`).
- Add a declare-time / class-validation check that rejects Sierra programs whose derived CASM segment-tree nesting exceeds a configured maximum depth, similar to `max_bytecode_size`.

### Proof of Concept
Not independently executable within this review: the exact segment-tree shape is produced by the external `cairo-lang-sierra-to-casm` compiler crate (outside this repository's index), so a concrete depth-to-crash Sierra program could not be constructed and verified here. Conceptually: craft a Sierra program whose functions are composed of a long chain of nested conditional branches (each branch containing another nested branch) sufficient to produce a `NestedIntList` tree deep enough that `bytecode_hash_node`'s call depth exceeds the sequencer process's default stack size when `SierraCompiler::compile` calls `executable_class.hash(&HashVersion::V2)` after successful CASM compilation.

/// Computes the hash of the bytecode according to the provided segment structure.
/// The function iterates over the bytecode, partitioning it into segments as described
/// by the `HashableNestedIntList`. For each segment, it recursively computes a hash
/// using the provided `StarkHash` implementation. The final result is a hash representing the
/// entire bytecode structure, as required by Starknet's contract class hash computation.
fn bytecode_hash<H, NL>(bytecode: &[Felt], bytecode_segment_lengths: &NL) -> Felt
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    let mut bytecode_iter = bytecode.iter().copied();
    let (len, bytecode_hash) =
        bytecode_hash_node::<H, NL>(&mut bytecode_iter, bytecode_segment_lengths);
    assert_eq!(len, bytecode.len());
    bytecode_hash
}

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
