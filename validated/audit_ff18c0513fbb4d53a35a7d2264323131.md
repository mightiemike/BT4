### Title
`replace_class` syscall is not restricted in Validate execution mode, allowing account/class swap during transaction validation - (File: crates/blockifier/src/execution/syscalls/syscall_base.rs)

### Summary
Across the blockifier's syscall implementations, `ExecutionMode::Validate` is used as a sandbox to restrict which syscalls an account's `__validate__` (and constructor-in-validate) code can invoke, since validation runs before fee charging/nonce commitment and its side effects must be limited and deterministic. `deploy`, `get_class_hash_at`, `get_block_hash`, `meta_tx_v0`, `get_sequencer_address`, and cross-contract `call_contract` all explicitly check `self.context.execution_mode == ExecutionMode::Validate` and reject the syscall via `reject_syscall_in_validate_mode`/`InvalidSyscallInExecutionMode`. `replace_class`, however, has no such check in either the Cairo1 syscall base (`SyscallHandlerBase::replace_class`) or the deprecated Cairo0 handler (`DeprecatedSyscallExecutor::replace_class`).

### Finding Description
The Cairo1 `replace_class` implementation only validates that the target class exists and is Cairo1: [1](#0-0) 

Compare this to sibling syscalls in the same file that explicitly gate on `ExecutionMode::Validate`, e.g. `get_class_hash_at`: [2](#0-1) 
and `meta_tx_v0`: [3](#0-2) 
and `get_block_hash`: [4](#0-3) 

The deploy syscall is guarded by a dedicated helper `should_reject_deploy`, again keyed on `ExecutionMode::Validate`: [5](#0-4) 

The Cairo1 hint-processor entry point for `replace_class` simply forwards to the base function with no additional mode check: [6](#0-5) 

The same gap exists in the deprecated (Cairo0) syscall handler: [7](#0-6) 
whereas that same file's `call_contract` explicitly enforces the Validate-mode restriction: [8](#0-7) 

Notably, this exact syscall is documented and tested as forbidden in the Starknet OS's "virtual OS" mode (a different sandbox used for read-only/virtual execution), confirming that `ReplaceClass` is treated by the protocol as a side-effecting syscall that must be blocked in restricted execution contexts: [9](#0-8) 
Yet the sequencer's actual `ExecutionMode::Validate` (used for both the gateway's pre-submission validation and the sequencer's `__validate__` invocation prior to fee charge) has no equivalent restriction for it, unlike deploy/call_contract/get_block_hash/get_class_hash_at/meta_tx_v0, which are enumerated as validate-mode restricted: [10](#0-9) 

### Impact Explanation
An account contract (or its constructor, in the "faulty account" validate-constructor scenario) can invoke `replace_class_syscall` from within `__validate__` to swap its own class hash to an arbitrary already-declared Cairo1 class before the transaction's actual execution phase begins. Because `ExecutionMode::Validate` is the mode used by the gateway to gate mempool admission and by the sequencer immediately prior to committing to fee deduction, this allows validation logic to run against one class (to pass validation, e.g. a legitimate signature-check account) while the state committed to the `execute` phase — and to future transactions from the same address — reflects a different, attacker-chosen class. This is a sandbox/mode-isolation violation analogous to the Bruno CVE: an execution phase intended to run with restricted side effects (validate) ends up permitted to perform a state mutation meant only for the execute phase, enabling unauthorized account behavior and inconsistent state transitions between what was validated and what is later executed/committed.

### Likelihood Explanation
Exploitability requires only deploying/declaring a class and constructing an account (or invoking any contract used in a `__validate__`/validate-constructor context) that calls `replace_class_syscall`; this is fully reachable by any unprivileged transaction sender without operator or peer collusion. The restriction pattern is well-established for the other five side-effecting/state-observing syscalls in the same code paths, making the omission for `replace_class` a plausible unintentional oversight rather than an intentionally permitted case, though I could not find an explicit design comment confirming intent either way in the reachable code.

### Recommendation
Add an `ExecutionMode::Validate` check to `SyscallHandlerBase::replace_class` (mirroring `get_class_hash_at`/`meta_tx_v0`) in `crates/blockifier/src/execution/syscalls/syscall_base.rs`, and to `DeprecatedSyscallExecutor::replace_class` in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`, rejecting the syscall via `reject_syscall_in_validate_mode("replace_class")` / `InvalidSyscallInExecutionMode` respectively when `execution_mode == ExecutionMode::Validate`. Add regression tests analogous to `disable_deploy_in_validate_mode_flag_behavior` and `test_forbidden_syscall_in_virtual_mode` asserting `replace_class` is rejected during `ExecutionMode::Validate` for both Cairo0 and Cairo1 (VM and native) paths.

### Proof of Concept
1. Declare two Cairo1 classes: `AccountA` (passes its own `__validate__` for a given signature) and `AccountB` (arbitrary/malicious logic), both already declared on-chain.
2. Deploy `AccountA` at address `X`.
3. Craft `AccountA::__validate__` (or, per the existing `test_replace_class`/faulty-account test pattern, the constructor invoked in a validate-mode context) to call `replace_class_syscall(AccountB.class_hash)`.
4. Submit an ordinary transaction from address `X`. The gateway/sequencer executes `__validate__` under `ExecutionMode::Validate`; because no check rejects `replace_class` here (unlike `deploy`/`call_contract`/`get_block_hash`/`get_class_hash_at`/`meta_tx_v0`, all of which are demonstrated to fail with `Unauthorized syscall ... in execution mode Validate.` in `crates/blockifier/src/transaction/transactions_test.rs:2464-2540` and `crates/blockifier/src/execution/syscalls/syscall_tests/deploy.rs:323-362`), the call succeeds and `state.set_class_hash_at(X, AccountB.class_hash)` is committed to the state diff.
5. Validation passes using `AccountA`'s logic, but the class hash at `X` is now `AccountB`; subsequent execution of this transaction (and all future transactions from `X`) runs under `AccountB`'s code, demonstrating unauthorized account-class mutation smuggled through the supposedly restricted Validate sandbox.

    pub fn get_block_hash(&mut self, requested_block_number: BlockNumber) -> SyscallResult<Felt> {
        // Note: we take the actual block number (and not the rounded one for validate)
        // in any case; it is consistent with the OS implementation and safe (see `Validate` arm).
        let current_block_number = self.context.tx_context.block_context.block_info.block_number;

        if !block_number_in_range(requested_block_number, current_block_number) {
            // Requested block is too recent.
            match self.context.execution_mode {
                ExecutionMode::Execute => {
                    // Revert the syscall.
                    return Err(SyscallExecutionError::Revert {
                        error_data: vec![BLOCK_NUMBER_OUT_OF_RANGE_ERROR_FELT],
                    });
                }
                ExecutionMode::Validate => {
                    // In this case, the transaction must be **rejected** to avoid the following
                    // attack:
                    //   * query a given block in validate,
                    //   * if reverted - ignore, if succeeded - panic.
                    //   * in the gateway, the queried block is (actual_latest - 9),
                    //   * while in the sequencer, the queried block can be further than that.
                    self.reject_syscall_in_validate_mode("get_block_hash on recent blocks")?;
                }
            }
        }

    pub fn get_class_hash_at(
        &mut self,
        contract_address: ContractAddress,
    ) -> SyscallResult<ClassHash> {
        if self.context.execution_mode == ExecutionMode::Validate {
            self.reject_syscall_in_validate_mode("get_class_hash_at")?;
        }

        self.storage_access_tracker.accessed_contract_addresses.insert(contract_address);
        let class_hash = self.state.get_class_hash_at(contract_address)?;
        self.storage_access_tracker.read_class_hash_values.push(class_hash);
        Ok(class_hash)
    }

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
