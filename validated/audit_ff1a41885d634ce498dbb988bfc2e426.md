## Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting `replay-verify` accept a divergent authenticated position/state root — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `execution/executor/src/chunk_executor/mod.rs`) to confirm that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed to the ledger accumulator. It checks status, gas, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that authenticate the JMT/SMT state roots (including the new native-position tree gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`).

### Finding Description
`TransactionInfoV1` carries multiple checkpoint-hash fields that bind a transaction to the resulting state roots:
- `state_checkpoint_hash` (main state SMT root)
- `hot_state_checkpoint_hash` (hot-state root, gated by `HOT_STATE_ROOT_IN_TXN_INFO`)
- `position_state_checkpoint_hash` (native-position JMT root, gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`)

These are the fields that `DoStateCheckpoint::run` / `Self::get_state_checkpoint_hashes` compute and place into each committed `TransactionInfo` [1](#0-0) . They are proof-bearing values: `position_state_checkpoint_hash` is the root that clients would use, via `get_position_state_proof_by_version_ext`, to verify Merkle proofs against the native-position tree [2](#0-1) .

However, `TransactionOutput::ensure_match_transaction_info` — the function that compares a *recomputed* output (from real VM execution) against the *persisted* `TransactionInfo` — only validates `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`. It self-documents the gap:

```rust
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

This function is the sole correctness gate used by `replay_on_archive`'s `execute_and_verify`, which re-executes historical transactions against archived state and calls `ensure_match_transaction_info` to decide whether replay succeeded or must report a divergence:

```rust
if let Err(err) = executed_outputs[idx].ensure_match_transaction_info(
    version,
    &expected_txn_infos[idx],
    Some(&expected_writesets[idx]),
    Some(&expected_events[idx]),
) {
    ...
    return Ok(Some(err));
}
``` [4](#0-3) 

Because the comparator never re-derives or compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a state root computed and committed as part of `TransactionInfoV1` (e.g., the native-position JMT root feeding `commit_native_position`/`position_summary_at_commit` at `storage/aptosdb/src/db/aptosdb_writer.rs`) can silently diverge from what local re-execution actually produces, and the replay/verification tooling would still report success. The write-set hash check alone does not cover this, because the checkpoint hash is a separately computed Merkle root over the incrementally-updated state tree (main state SMT, hot-state, or native-position JMT) rather than a hash of the write set itself — a bug in state-tree extension logic (e.g., in `PositionStateWithSummary::extend`, `position_summary_at_commit`, or `DoStateCheckpoint::compute_position_checkpoint`) that produces a wrong root but a correct write-set hash would go completely undetected by this "verification" pass.

### Impact Explanation
This breaks the proof/commit-integrity invariant that "committed state must survive executor-to-storage handoff unchanged and be verifiable via replay." Replay-verify is one of the primary tools operators and auditors rely on to catch divergence between VM execution and the durable ledger (including hard-fork-only divergence scenarios). If the actual on-chain `position_state_checkpoint_hash` (or `state_checkpoint_hash`/`hot_state_checkpoint_hash`) committed to `TransactionInfoV1` and the accumulator is wrong — due to a bug elsewhere in the state-checkpoint/JMT-extension pipeline — this specific verification function will not detect the divergence, and `replay_on_archive` will falsely report a clean replay. Any client or storage-service response bound to that (wrong) root would be treated as authenticated when the underlying state summary is actually corrupted or unreproducible from a straight VM re-execution. This is a self-admitted, exact, and currently-live gap in the one function whose job is to catch this class of divergence.

### Likelihood Explanation
The gap is unconditional in the current code — it is not behind a feature flag inside `ensure_match_transaction_info` itself, so it applies today even though `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are currently off in production per code comments elsewhere (`// TODO(HotState): this is currently None in testnet and mainnet`). The risk becomes live the moment either feature is turned on, or if any other bug causes a `state_checkpoint_hash` mismatch, since the intended safety net (replay verification) has already been shown by the code author's own comment to not catch it.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, and (when present in `txn_info`) `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against values independently derived from re-execution before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` in any environment where replay-verify results are trusted as a correctness signal.

### Proof of Concept
Not directly exploitable as a standalone PoC without a second bug that actually produces a wrong checkpoint hash; the finding is that the safety-net check is provably absent (per the TODO and the function body itself), meaning any future/existing state-root divergence in the checkpoint pipeline (main-state, hot-state, or native-position) would not be caught by `replay_on_archive`'s `ensure_match_transaction_info` call, contrary to its intended purpose. This can be confirmed by inspection: instrument `ensure_match_transaction_info` to always pass when write-set/events/status/gas match, and inject a deliberately wrong `position_state_checkpoint_hash` at commit time (e.g., corrupt `position_summary_at_commit`'s output) — `execute_and_verify` in `replay_on_archive.rs` will not surface an error.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
