### Title
TVM precompiled Freeze/Unfreeze V2 native contracts allow a single transaction to temporarily inflate global resource-weight accounting, bypassing the one-contract-per-transaction invariant - (`actuator/src/main/java/org/tron/core/actuator/FreezeBalanceV2Actuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java`, `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Blend report shows that chaining `supply → borrow → withdraw` inside one atomic action batch lets an attacker temporarily inflate `total_supply`, pass a ratio-based limit check (`utilization <= max_util`), and then reverse the inflation before the transaction ends, permanently leaving the pool in an illegal state. java-tron enforces a strict "one `Contract` per transaction" rule at the top level (`Manager.processTransaction` throws `ContractSizeNotEqualToOneException` if `getContractList().size() != 1`) specifically to prevent this class of multi-step, same-transaction state manipulation. However, this invariant only applies to top-level, externally signed contracts. The resource-freezing operations (`FreezeBalanceV2`, `UnfreezeBalanceV2`, delegate/undelegate resource) are also exposed as TVM native contracts (precompiles), meaning a smart contract can invoke them repeatedly as *internal* calls within a single external transaction/VM execution — recreating exactly the "inflate → exploit → revert, all in one tx" pattern the top-level restriction was meant to prevent.

### Finding Description
`Manager.processTransaction` [1](#0-0)  guarantees that ordinary broadcast transactions contain exactly one actuator invocation, and `ActuatorFactory`/`ActuatorCreator` build exactly one actuator per `Contract` entry, executed with `validate()` immediately followed by `execute()` [2](#0-1) .

This restriction does not apply to internal calls made by a smart contract during TVM execution. `PrecompiledContracts.java` exposes native resource-management actions (freeze/unfreeze/delegate v2) as callable precompiles from within a single `TriggerSmartContract` transaction [3](#0-2) . The underlying native processors mutate global, shared accounting state immediately and reversibly within the same call:

- `FreezeBalanceV2Actuator.execute` immediately increases the account's frozen balance and the network-wide `TotalNetWeight`/`TotalEnergyWeight` used for resource-allocation ratios [4](#0-3) .
- `UnfreezeBalanceV2Processor.execute` immediately decrements that same global weight via `updateTotalResourceWeight`, while only the actual TRX return is delayed by an unlock queue (`addUnfrozenV2List`) [5](#0-4) .

Because the *weight* portion of the state (the value used in ratio/ceiling computations elsewhere in the protocol, analogous to Blend's `total_supply`) is updated and reversible instantly — unlike the underlying TRX balance, which is locked — a contract can, in one externally-submitted transaction (satisfying the "exactly one Contract" rule at the top level), internally call freeze then unfreeze (or delegate then undelegate) back-to-back through the precompile interface. This reproduces the Blend "inflate mid-flow, use the inflated state to pass a check, then revert" pattern that java-tron's single-contract-per-transaction rule was designed to prevent, but only prevents at the top level, not for TVM-triggered internal calls to these native contracts.

### Impact Explanation
Any protocol logic that reads `TotalNetWeight`/`TotalEnergyWeight` (or account-level frozen/delegated balances) to compute a ratio-bound resource allocation, vote power, or eligibility check performed at a point *within* the same transaction as the freeze/unfreeze pair is exposed to a temporary, self-reversing manipulation of denominator/numerator values — the same root cause category as the referenced high-severity Blend finding (a ratio-limit check bypassed via same-transaction inflate/deflate). This falls under resource and reward accounting corruption, reachable purely from a contract call triggered by an anonymous RPC-submitted transaction.

### Likelihood Explanation
Reachability is straightforward: any account can deploy a contract and call it via `TriggerSmartContract`, and the precompiled freeze/unfreeze/delegate native contracts are unprivileged, callable by any caller with sufficient balance/energy. No leaked keys, malicious peers, or privileged roles are required — only ordinary RPC transaction broadcast to a contract that internally sequences the native-contract calls.

### Recommendation
- Enforce a lock/cooldown on the *weight* component of freeze/unfreeze (not just on TRX withdrawal) so that `TotalNetWeight`/`TotalEnergyWeight` cannot be inflated and reverted within a single transaction/VM execution.
- Alternatively, disallow calling `FreezeBalanceV2`/`UnfreezeBalanceV2`/delegate-undelegate native contracts more than once per external transaction, or snapshot weight-derived limits at the start of transaction execution rather than recomputing them from live, mutable totals mid-execution.
- Audit every downstream consumer of `TotalNetWeight`/`TotalEnergyWeight` (and per-account frozen balances) for reliance on values that can be temporarily manipulated via chained native-contract precompile calls in one transaction.

### Proof of Concept
Conceptual sequence (exact precompile call signatures were not fully traceable in the available index and would need confirmation in a full checkout):
1. Deploy a contract that, in a single external call, invokes the `freezeBalanceV2` native precompile with a large TRX amount, increasing its own `TotalNetWeight`/`TotalEnergyWeight` share [6](#0-5) .
2. Within the same call, trigger whatever downstream logic relies on the inflated weight/ratio (e.g., resource-limit-dependent behavior).
3. Immediately call the `unfreezeBalanceV2` native precompile, which reduces `TotalNetWeight`/`TotalEnergyWeight` back down via `updateTotalResourceWeight`, while the TRX itself simply enters the unlock queue rather than being lost [7](#0-6) .
4. All three steps occur inside one externally signed transaction, satisfying `Manager.processTransaction`'s "exactly one Contract" check [1](#0-0) , since that check only inspects the top-level `Contract` list, not internal TVM calls.

Note: I was not able to fully confirm within the indexed code whether any specific downstream check reads `TotalNetWeight`/`TotalEnergyWeight` mid-transaction in a way that grants an immediately-exploitable, irreversible benefit (e.g., a one-time resource grant that outlives the unfreeze). Given index size limits, some call sites of `TotalNetWeight`/`TotalEnergyWeight` consumers and the exact precompile method signatures in `PrecompiledContracts.java` were not retrievable in full; a full checkout via a Devin session would be needed to confirm a concrete, currently-exploitable downstream consumer and finalize severity.

  public long execute(UnfreezeBalanceV2Param param, Repository repo) {
    byte[] ownerAddress = param.getOwnerAddress();
    long unfreezeBalance = param.getUnfreezeBalance();
    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();

    long unfreezeExpireBalance = this.unfreezeExpire(accountCapsule, now);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    long expireTime = this.calcUnfreezeExpireTime(now, repo);
    accountCapsule.addUnfrozenV2List(param.getResourceType(), unfreezeBalance, expireTime);

    this.updateTotalResourceWeight(accountCapsule, param.getResourceType(), unfreezeBalance, repo);
    this.updateVote(accountCapsule, param.getResourceType(), ownerAddress, repo);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && !accountCapsule.oldTronPowerIsInvalid()) {
      accountCapsule.invalidateOldTronPower();
    }

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return unfreezeExpireBalance;
  }
