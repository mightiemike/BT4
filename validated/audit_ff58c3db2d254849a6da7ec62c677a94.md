### Title
`liquidate-multi` batch calls `liquidate` without a rollback boundary, so a late assertion failure (bad-debt socialization) still leaves collateral seized/debt repaid committed while the transaction reports success - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` iterates positions with `(map call-liquidate positions)` where `call-liquidate` invokes the public function `liquidate` as a **direct, same-contract function call** (not via `contract-call?`) [1](#0-0) . Because `liquidate-multi` never applies `try!`/`asserts!` to the individual results and simply wraps the map output in `(ok ...)` [2](#0-1) , the top-level transaction always returns `ok`. Any state mutation performed earlier inside a given `liquidate` invocation (vault repay, debt bookkeeping removal, collateral removal) is only rolled back if the **outermost** transaction call returns `err`; here it never does. `liquidate` itself performs its irreversible, value-moving steps (`vault-system-repay`, `debt-remove-scaled`, `collateral-remove`) *before* the final bad-debt-socialization check that can still fail [3](#0-2) [4](#0-3) .

### Finding Description
The relevant sequence in `liquidate` (mainnet/contracts/market/v0-4-market.clar):
1. Fail-fast guards (pause, auth, amounts, slippage) run first, before any mutation [5](#0-4) .
2. `vault-system-repay` executes — pulls the debt token from the liquidator and repays the vault [6](#0-5) .
3. `debt-remove-scaled` and `collateral-remove` are called via `contract-call?` to `.v0-market-vault`, which actually transfers the seized collateral to the liquidator/receiver and reduces the borrower's recorded debt [7](#0-6) .
4. Only *after* these value-moving steps, if the position now has `no-collateral-left`, the code attempts to socialize (write off) the borrower's remaining debt on other assets, folding over `socialize-debt-asset` [8](#0-7) . If that socialization fails (e.g., the other debt asset's vault rejects `vault-socialize-debt` for any reason), `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)` — but that return value happens deep inside a same-contract call chain (`call-liquidate` → `liquidate`), not a `contract-call?` boundary.

Clarity's automatic rollback-on-error guarantee applies at the granularity of the outermost transaction call (and of individual `contract-call?`s that themselves return `err`). It does **not** create an implicit checkpoint for a plain function invocation of one public function from another inside the same contract. Since `liquidate-multi` invokes `liquidate` this way and swallows the error inside `map` (never propagating it with `try!`), the already-committed effects of steps 2–3 for that borrower persist even though `liquidate`'s own return value for that entry is `err`, and the overall transaction still returns `ok`.

The developers' own comment acknowledges the "doesn't revert" behavior as an intended feature — "Failed liquidations return error codes but don't revert entire batch" [9](#0-8)  — without accounting for the fact that a "failure" can occur *after* debt/collateral have already been moved, not only before any mutation.

### Impact Explanation
When bad-debt socialization for a fully-collateral-stripped borrower fails, that borrower's remaining debt on other assets is never written off, yet their collateral is already gone (transferred out in step 3) and the repaid debt asset's vault already booked the repayment. The vault(s) holding the un-socialized debt continue to carry it as a collectible receivable backed by nothing, permanently inflating recorded assets relative to real backing. This is unresolvable through a normal retry because the borrower already has zero collateral, so subsequent liquidation attempts on the same borrower for that debt asset have nothing to seize. This corresponds to the in-scope **protocol insolvency** impact class (permanent phantom debt / asset-liability mismatch), since supplier share pricing is computed from indexes that assume that debt is real and recoverable.

### Likelihood Explanation
The `no-collateral-left` + socialization-failure branch requires a specific but reachable condition set: a liquidation that removes all collateral from a multi-debt-asset borrower while one of the *other* debt assets' `vault-socialize-debt` call fails (e.g., due to a pause flag, a caller-authorization mismatch, or any other guard on that vault). Any DAO-driven pause toggling on a debt vault at the wrong moment, or an edge case in `socialize-debt-asset`'s `unwrap!` failure paths, is sufficient to trigger it inside a `liquidate-multi` batch — no attacker collusion or DAO compromise is required to *trigger* it, only ordinary operational conditions (e.g., an emergency pause activated on one vault while a `liquidate-multi` batch touching a shared borrower is in flight). Likelihood is moderate: it depends on a race between routine pause operations and batch liquidations, not attacker-crafted state.

### Recommendation
In `liquidate-multi`, propagate failures from `call-liquidate` instead of using bare `map`, or wrap `call-liquidate`'s invocation of `liquidate` through a boundary that guarantees atomic rollback per position (e.g., structure the per-position work so that the bad-debt-socialization decision and check occur *before* any vault repay/collateral-removal side effects, or explicitly revert all of that position's effects when socialization fails, e.g., by aborting the whole `liquidate-multi` transaction on any single failure instead of silently continuing).

### Proof of Concept
1. Borrower B holds collateral in asset X and debt in assets Y and Z (multi-debt egroup).
2. A liquidator submits `liquidate-multi` containing one entry targeting B's collateral X against debt Y, sized so that after seizure B's collateral list becomes empty (`no-collateral-left` = true).
3. At the same/overlapping point, debt asset Z's vault has a pause flag or guard condition set (e.g., admin pause on `socialize-debt`) such that `vault-socialize-debt` for Z fails inside `socialize-debt-asset`.
4. `liquidate` executes: `vault-system-repay` for Y succeeds, `debt-remove-scaled`/`collateral-remove` succeed (collateral X sent to liquidator, Y debt reduced) — then the socialization fold for remaining debt (Z) fails, and `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.
5. Because this happened inside `call-liquidate`'s direct invocation (no `contract-call?`/`try!` boundary) within `map`, and `liquidate-multi` returns `(ok (list ... (err u...) ...))`, the whole transaction commits: B has lost all collateral, Y's debt is cleared, but Z's debt remains fully booked on the vault with zero backing collateral, permanently.

Note: I could not directly inspect the exact `vault-socialize-debt`/`socialize-debt` failure conditions (auth checks, pause flags) within the size/time budget of this session; the specific triggering condition for step 3 (why `vault-socialize-debt` can fail) should be verified against each vault contract's `socialize-debt` implementation before treating the likelihood as fully confirmed.
