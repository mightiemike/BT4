This confirms the exploit path is concrete: after `validateHmac` returns `true`, `authenticateAppProxyFactory` reads `logged_in_customer_id` directly from `request.url`'s real `URLSearchParams` (documented usage: `searchParams.get("logged_in_customer_id")` in `packages/apps/shopify-app-remix/src/server/authenticate/public/types.ts`), and the app is expected to trust that value as coming from Shopify. This is exactly the pattern needed for the collision to matter — verification and consumption both happen on the real parsed query object, so a canonical-string collision lets an attacker present a genuinely different real query (with a forged `logged_in_customer_id`) that reuses a signature legitimately obtained for a different, attacker-crafted query.

### Title
Non-injective App Proxy HMAC canonicalization allows signature-collision forgery of `logged_in_customer_id`/`shop` fields - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
`stringifyQueryForAppProxy` builds the string that is HMAC-signed/verified for Shopify App Proxy requests by sorting query keys and concatenating `key=value` pairs with **no delimiter between pairs and no escaping/length-prefixing of values**. This mirrors the reported `dynamic_fields.move` bug class: concatenating variable-length, attacker-influenced fields without a separator/length prefix makes the hash input non-injective, so distinct real query structures can produce an identical signed string.

### Finding Description [1](#0-0) 
```
function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}
```
Unlike `stringifyQueryForAdmin`, which uses `URLSearchParams`/percent-encoding via `ProcessedQuery` [2](#0-1) , the App Proxy canonicalizer emits raw, unescaped values concatenated back-to-back. Because non-reserved query parameter names/values in an App Proxy call are attacker-controlled (any visitor of a storefront `/apps/...` proxy URL can add arbitrary extra query params, and only `hmac`, `shop`, `signature`, `timestamp` are restricted to a single value, per `APP_PROXY_SINGLE_VALUE_PARAMS` [3](#0-2) ), an attacker can choose a custom key whose value textually contains `logged_in_customer_id=<id>` (or another sensitive key). When sorted alphabetically before that key, the resulting canonical string is byte-identical to a genuinely different query that has a *real*, separate `logged_in_customer_id=<id>` key.

The attacker:
1. Visits the app's own proxy path with a single custom param whose value embeds `logged_in_customer_id=<targetId>` as trailing text, causing Shopify to legitimately sign that exact (single-key) query and issue a valid `signature`.
2. Sends a direct HTTP request straight to the app's route (the app-proxy authentication logic only checks `api.utils.validateHmac(searchParams, {signator: 'appProxy'})` [4](#0-3)  — nothing verifies the request actually transited Shopify's network), but with a genuinely different two-key query (`custom=...` and a real `logged_in_customer_id=<targetId>` key) plus the signature obtained in step 1.
3. `validateHmac` re-derives the same canonical string from this new two-key query (because the concatenation is non-injective) and the signature check passes.
4. The route handler then reads `logged_in_customer_id` from the real, now-forged `URLSearchParams` as documented for app usage [5](#0-4) , believing it is an authentic value supplied by Shopify for a logged-in customer.

### Impact Explanation
Any app that trusts `logged_in_customer_id` (or other reserved-looking fields reconstructable via this technique, e.g. impersonating `shop` boundaries) from an app-proxy-authenticated request — a documented, recommended pattern — can be tricked into acting on behalf of an arbitrary target customer ID without that customer’s session, enabling cross-customer/cross-tenant data access or actions gated on `logged_in_customer_id`. This is a forged, accepted "Shopify-signed" request from an anonymous/unprivileged actor.

### Likelihood Explanation
Reachable by any anonymous internet user: App Proxy routes are public storefront URLs, custom query parameters are always attacker-supplied, and no special privileges or secrets are required — only two self-triggered requests (one signed via a normal storefront visit, one sent directly to the app). The only constraint is knowing/guessing the target `logged_in_customer_id` value (Shopify customer IDs), which is a numeric ID often obtainable through other means.

### Recommendation
Match the admin canonicalizer's approach: URL-encode/escape values and insert an unambiguous delimiter (e.g., `&`) between `key=value` pairs in `stringifyQueryForAppProxy`, or otherwise make the canonicalization injective (e.g., length-prefix each key and value before hashing), consistent with the remediation applied to `hash_type_and_key` in the referenced patch (`5b71cef`).

### Proof of Concept
1. Attacker (customer id `12345`, target victim id `99999`) visits: `https://shop.myshopify.com/apps/proxy?x=1logged_in_customer_id=99999` while logged out, so Shopify computes canonical string `shop=<shop>x=1logged_in_customer_id=99999timestamp=<ts>` and returns a valid `signature=S`.
2. Attacker sends directly to the app's registered proxy route: `GET /apps/proxy?shop=<shop>&x=1&logged_in_customer_id=99999&timestamp=<ts>&signature=S`.
3. `validateHmac` recomputes the canonical string from these now-separate `x` and `logged_in_customer_id` keys — identical bytes to step 1 — and returns `true`.
4. The app's loader reads `searchParams.get("logged_in_customer_id")` and obtains `99999`, believing it was authenticated by Shopify as the currently logged-in customer, though no such session existed. [1](#0-0)
