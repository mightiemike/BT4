No vulnerability found for this question.

The reasoning:

`DbStateView::get` does skip proof verification when `maybe_verify_against_state_root_hash` is `None` [1](#0-0) , and `PooledVMValidator`/`VMValidator` do construct their validation view via `latest_state_checkpoint_view()`, which always sets `maybe_verify_against_state_root_hash: None` [2](#0-1) [3](#0-2) .

However, this is not an exploitable state-integrity issue because:

1. **No untrusted response is involved.** The `db: Arc<dyn DbReader>` used by `VMValidator` is the node's own local `AptosDB` instance, obtained directly via `PooledVMValidator::new(db_reader, ...)` from the mempool runtime wiring — it is not a peer-supplied, network-transmitted, or otherwise externally authenticated response [4](#0-3) . Proof verification exists to authenticate *external* claims about state (e.g., verifying a remote state snapshot or API response against a ledger's root hash), not to protect against the local storage engine lying to its own process.

2. **The proof-verifying variant is used for a different purpose.** `verified_state_view_at_version` is the constructor that supplies `maybe_verify_against_state_root_hash = Some(state_root_hash)`, and it is designed for cases where a `LedgerInfo` (an already-authenticated ledger commitment) is available and the caller wants to verify a state read against it [5](#0-4) . Mempool/VM validation intentionally uses the unverified `latest_state_checkpoint_view` because it operates on the node's own already-committed, locally-consistent DB state — there's no separate "authenticated root" to compare against in this flow, since the DB itself is the trust anchor for local validation.

3. **This matches the explicitly excluded scope.** The proof-of-concept requires "a tampered underlying DbReader response," which presumes a compromised/malicious local storage engine — this is a trusted-component (operator/storage) compromise scenario, not unprivileged attacker-controlled input corrupting an authenticated response. The review's Decision Standard explicitly rejects findings that "depend on trusted operator mistakes alone."

4. **No hard-fork or committed-state divergence.** Mempool validation is a soft admission-control gate; even a stale or incorrect read here would only affect whether a transaction is queued in the local mempool, not what gets executed/committed by consensus and the VM, which independently re-validates via its own execution path.

Since the mechanism described doesn't correspond to an unprivileged-input path that corrupts committed state, proof material, or an authenticated response, this does not meet the acceptance criteria.

impl VerifiedStateViewAtVersion for Arc<dyn DbReader> {
    fn verified_state_view_at_version(
        &self,
        version: Option<Version>,
        ledger_info: &LedgerInfo,
    ) -> StateViewResult<DbStateView> {
        let db = self.clone();

        if let Some(version) = version {
            let txn_with_proof =
                db.get_transaction_by_version(version, ledger_info.version(), false)?;
            txn_with_proof.verify(ledger_info)?;

            let state_root_hash = txn_with_proof
                .proof
                .transaction_info
                .state_checkpoint_hash()
                .ok_or_else(|| StateViewError::NotFound("state_checkpoint_hash".to_string()))?;

            Ok(DbStateView {
                db,
                version: Some(version),
                maybe_verify_against_state_root_hash: Some(state_root_hash),
            })
        } else {
            Ok(DbStateView {
                db,
                version: None,
                maybe_verify_against_state_root_hash: None,
