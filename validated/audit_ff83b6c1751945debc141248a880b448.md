### Title
Attacker can grow a victim's `DelegatedResourceAccountIndexCapsule` account-index array without bound via cheap `FreezeBalanceContract` delegations, causing an O(n) linear-scan / O(n) migration DoS on the victim's subsequent delegate/undelegate operations - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
The reported bug class is: an unprivileged party can force entries into an unbounded array owned by the victim, and a later victim-triggered operation must linearly search/remove from that array, causing degraded performance or failure. Java-tron's legacy resource-delegation bookkeeping (`DelegatedResourceAccountIndexCapsule.toAccountsList` / `fromAccountsList`) reproduces the same pattern: the array is populated by an attacker-controlled, permissionless action (freezing TRX with a `receiverAddress`), and is later scanned/removed with `List.contains()`/`List.remove()`, and can also be bulk-replayed via `DelegatedResourceAccountIndexStore.convert()`.

### Finding Description
`FreezeBalanceActuator.delegateResource()` lets any account freeze as little as the minimum bandwidth/energy amount and delegate it to an arbitrary `receiverAddress`, when the `AllowDelegateOptimization` proposal is not active: [1](#0-0) 

This appends the delegator's address to the receiver's `fromAccountsList` (and the receiver's address to the delegator's `toAccountsList`), guarded only by a `contains()` check that prevents *duplicate* entries from the same address, not from many distinct attacker-controlled addresses: [2](#0-1) 

Because an attacker can create unlimited new accounts and freeze the minimum unit of TRX from each one to the same victim `receiverAddress`, the victim's `fromAccountsList` (stored as a single protobuf-embedded list under one DB key, keyed by the victim's address) can be grown without bound, entirely by anonymous broadcast transactions.

That poisoned array is later processed in two places:
1. `UnfreezeBalanceActuator.execute()` removes an address from these lists using `List.remove(Object)`, an O(n) linear scan, once for the owner's list and once for the receiver's list: [3](#0-2) 
2. `DelegatedResourceAccountIndexStore.convert()` — invoked lazily the first time a poisoned account participates in a delegate/undelegate call after the optimization feature is enabled — iterates the *entire* legacy `toList`/`fromList` and performs a full read-modify-write (`this.delegate(...)`) for every single entry: [4](#0-3) 

If the attacker inflates the victim's list to a very large size, the victim's next `UnfreezeBalanceContract`/`DelegateResourceContract`/`UnDelegateResourceContract` transaction that touches this account triggers a proportionally large amount of work (linear scans and, in the `convert()` path, one DB write per historical spam entry) inside a single block-processing transaction — unlike the Solidity original, java-tron's native actuators aren't per-opcode gas metered, so this manifests as unbounded CPU/DB work and processing-time inflation for that single transaction/block rather than an EVM "out of gas" revert, but the effect on the victim (their transaction becomes disproportionately expensive/slow, or a block producer may need to spend excessive time executing/verifying it) is the direct analog of the reported DoS.

### Impact Explanation
An attacker can, at negligible cost (minimum-unit freezes/delegations from many throwaway accounts, cheaper still if TRON deploys this codebase on a low-fee sidechain/L2 as the original report notes for Ethereum L2s), poison a target account's index list. This can:
- Degrade block-processing performance for any transaction from the victim that touches the poisoned index (unfreeze, delegate, undelegate), since these are O(n) or worse against attacker-controlled list size.
- Force a large burst of store writes inside a single transaction execution via `convert()` once optimization activates for that account, which is a resource-exhaustion / DoS vector against the node processing that block and against the victim's ability to interact with delegation/unfreeze features in a timely manner.

This maps to "DoS via protocol implementation" state-transition handling reachable from anonymous broadcast transactions.

### Likelihood Explanation
Reachability requires only broadcasting `FreezeBalanceContract` transactions (unprivileged, no special permission), and is gated on the network *not* having activated the `AllowDelegateOptimization` committee proposal — i.e., it is live on any chain instance (mainnet history, private nets, or forks) where that proposal parameter has not been turned on. I could not verify from the available code/index whether this proposal is enabled by default at genesis or requires committee activation, so likelihood on a fully up-to-date, already-optimized mainnet is lower; likelihood is high on any deployment still relying on the legacy (non-optimized) delegation index path, or during any window between such a fork's launch and the proposal's activation.

### Recommendation
- Cap the size of `toAccountsList`/`fromAccountsList` per account, or migrate all networks unconditionally to the prefix-keyed V2 index scheme (`V2_FROM_PREFIX`/`V2_TO_PREFIX`) which avoids storing an unbounded list inside a single capsule.
- Remove/disable the legacy non-optimized delegation-index code path entirely rather than keeping it reachable behind a runtime proposal flag.
- If legacy support must remain, bound `convert()`'s per-transaction work (e.g., migrate incrementally across multiple blocks) and use a `Set`/indexed map instead of `List.contains()`/`List.remove()` for membership and removal.

### Proof of Concept
Not directly executable without a live node/testnet where `AllowDelegateOptimization` is disabled, but the flow is:
1. Attacker generates N distinct accounts, each funded with the minimum required TRX.
2. From each account, broadcast `FreezeBalanceContract` with `resource=BANDWIDTH` (or `ENERGY`), minimal `frozen_balance`, and `receiver_address = victim`.
3. Each transaction appends a new entry to `victim`'s `DelegatedResourceAccountIndexCapsule.fromAccountsList` via `FreezeBalanceActuator.delegateResource()` [5](#0-4) .
4. After N is large, victim calls `UnfreezeBalanceContract` for any of their own delegated resources; the removal loop in `UnfreezeBalanceActuator` [6](#0-5)  now scans/removes against the N-sized list, and if the optimization proposal was just enabled, the account's first touch also triggers `convert()` [4](#0-3) , replaying N delegate operations inside one transaction.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
