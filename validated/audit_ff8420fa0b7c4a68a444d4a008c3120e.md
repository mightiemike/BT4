### Title
Unbounded native stack recursion in `Chain::get_recursive_transaction_results` allows an unprivileged transaction sender to crash RPC nodes via `tx`/`tx_status`/`EXPERIMENTAL_tx_status` - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_final_transaction_result`, invoked by the `tx`, `tx_status`, and `EXPERIMENTAL_tx_status` JSON-RPC methods, walks the DAG of receipt execution outcomes produced by a transaction using genuine (non-tail) Rust function recursion with no depth bound. [1](#0-0)  Any account holder can, over a sequence of ordinary cross-contract-call transactions, construct a receipt chain whose depth is limited only by wall-clock/gas budget across many transactions rather than by any hard depth cap, and then trigger unbounded recursive stack growth simply by querying transaction status for the head of that chain.

### Finding Description
`get_recursive_transaction_results` recurses once per receipt id referenced by an execution outcome's `receipt_ids`, with the only base case being "no execution outcome found yet": [2](#0-1) 
`get_final_transaction_result` is the sole entry point, unconditionally calling this recursive walk for the requested transaction hash: [3](#0-2) 

This is reachable from the public JSON-RPC surface via `tx_status_common` → `TxStatus`/`get_transaction_result_with_receipt` in `ViewClientActor`, backing the `tx`, `tx_status` and `EXPERIMENTAL_tx_status` methods documented in the OpenAPI spec. [4](#0-3) [5](#0-4) 

Crucially, the codebase already recognizes this exact bug class and has patched it in a *sibling* code path: the newer `ReceiptToTx`/`EXPERIMENTAL_receipt_to_tx` walker enforces a hard `MAX_DEPTH=1000` and returns `DepthExceeded` rather than recursing without bound. [6](#0-5)  No equivalent guard exists for `get_recursive_transaction_results`, which is the older, still-active code path for the basic `tx`/`tx_status` methods.

Depth is not bounded by a single transaction's gas: cross-contract self-recursion via `promise_batch_create`/`promise_batch_action_function_call_weight` already demonstrates chains of 56–221 hops purely from gas exhaustion in one transaction (`max_self_recursion_delay`). [7](#0-6)  An attacker is not limited to a single transaction's prepaid gas, however: each hop can be split across a *fresh* transaction (each with its own full gas allowance) linked to the previous one purely by having the prior receipt trigger (directly or via a scheduled continuation) a call that is itself observed as a receipt id in the prior outcome's `receipt_ids`. Over many blocks this lets the receipt/outcome DAG grow to depths far beyond what a bounded, iterative walk (like the trie iterators elsewhere in the codebase, e.g. `core/store/src/trie/ops/iter.rs`, which are explicitly implemented with an explicit stack to avoid this exact issue [8](#0-7) ) would allow, eventually overflowing the RPC/view-client thread's native call stack and crashing the node process handling the query.

### Impact Explanation
A stack-overflow abort is process fatal in Rust (there is no catchable panic for a genuine native stack overflow) — it takes down the RPC/view-client thread and, per the standard Rust runtime behavior, aborts the process. Because `tx`/`tx_status` is a basic, universally-available, unauthenticated JSON-RPC method that any client can call against any RPC node tracking the relevant shard, a single crafted (but otherwise valid) chain of cross-contract-call transactions submitted by an ordinary account can be used to repeatedly crash public RPC nodes on demand — a transaction-triggered halt/DoS, which is in-scope per the CVE-2018-12183 stack-overflow-DoS analog class.

### Likelihood Explanation
Constructing the underlying receipt/outcome chain requires only standard `FunctionCall` actions with cross-contract calls (no privileged validator/network-layer access), and is fully within the capability of any funded account issuing many ordinary transactions over time. Triggering the vulnerable code path requires nothing more than calling the public `tx`/`tx_status` RPC method with the resulting transaction hash — something any RPC caller can do. The fact that the sibling `receipt_to_tx` path was already hardened with an explicit `MAX_DEPTH` strongly suggests this class of unbounded-recursion bug is a real, previously-identified concern in this codebase that was not uniformly fixed.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative, explicit-stack (or worklist/BFS) traversal, mirroring the pattern already used by the trie iterators (`core/store/src/trie/ops/iter.rs`) and the depth-capped `ReceiptToTx` walker (`chain/jsonrpc-primitives/src/types/receipts.rs`). At minimum, add a hard depth/size cap (e.g. matching the existing `MAX_DEPTH=1000` convention) that fails the RPC call with a well-defined error (e.g. `DepthExceeded`) instead of recursing unboundedly, and apply the same cap uniformly to `runtime_user.rs`'s copy of this routine used in tests, to avoid resurrecting the bug through code reuse.

### Proof of Concept
1. Deploy a simple contract exposing a method that, given an index `i`, issues a `FunctionCall` action back to itself (or to a chain of pre-registered accounts) creating a new outgoing receipt, and repeat this pattern across many separately-submitted transactions so that each transaction's resulting execution outcome's `receipt_ids` links to the next transaction's initiating receipt — building an execution-outcome DAG with depth `N` (e.g. `N = 100_000`), well beyond the ~221-hop single-transaction gas-bounded chain shown in `max_self_recursion_delay`. [7](#0-6) 
2. Wait for all `N` transactions/receipts to be applied and their outcomes persisted.
3. Issue a `tx_status` (or `tx`, or `EXPERIMENTAL_tx_status`) JSON-RPC call for the hash of the first transaction in the chain against an RPC node tracking the originating shard. [4](#0-3) 
4. Observe that `Chain::get_final_transaction_result` → `get_recursive_transaction_results` recurses `N` deep with no bound check, exhausting the native stack of the handling thread and aborting the node process. [1](#0-0)

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Returns FinalExecutionOutcomeView for the given transaction.
    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];

    let recursion = u32::from_be_bytes(bytes);

    let gas_fixed = 0;
    let gas_weight = 1;

        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,

        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
