### Title
Global contracts deployed with `AccountId` mode let the owner unilaterally rewrite code executing under every account that references it, enabling a rug pull of "using" accounts' funds - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
The `DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` publishes a piece of WASM code that is referenced (not copied) by any account that later executes `UseGlobalContractAction` pointing at that owner's `AccountId`. The owner keeps the standing ability to redeploy under the same `AccountId` identifier at any later time and the update is retroactively applied to every account that already opted in, with no further consent, notice, or restriction from those "using" accounts. This mirrors the original Livepeer `L1Escrow.approve` bug class: a single, ordinary (non-protocol-admin) account holds unilateral, unrestricted power to redirect value/behavior belonging to other parties who trusted it, and can "rug" them at will.

### Finding Description
Any regular transaction signer can call `DeployGlobalContractAction` with `deploy_mode: GlobalContractDeployMode::AccountId` [1](#0-0) . Other accounts can then reference this code with `UseGlobalContractAction`, storing `AccountContract::GlobalByAccount(id)` on their own account instead of local code [2](#0-1) .

The documentation for this mode is explicit about the trust model: "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users." [3](#0-2) 

Crucially, `action_deploy_global_contract` performs no check on whether the calling account already has "users" and imposes no cooldown, governance, or re-consent step before a redeploy under the same `AccountId` takes effect — `initiate_distribution` simply increments a nonce and broadcasts the new code to all shards, which is applied to the same `GlobalContractIdentifier::AccountId` key that every referencing account resolves against [4](#0-3) . When the distribution receipt lands, the new bytes are written under the very same `TrieKey::GlobalContractCode` key that all "using" accounts already reference, with no versioning pin per user [5](#0-4) . This is confirmed by protocol tests exercising exactly this update path: `test_global_contract_update` deploys a trivial contract, has two accounts adopt it via `UseGlobalContract`, and then redeploys different code under the same `AccountId`; the already-opted-in accounts transparently start executing the new code with no additional action on their part [6](#0-5) .

Because contract code executes with the full authority of the account it is deployed on (it can initiate `Transfer`, `FunctionCall`, `AddKey`/`DeleteKey` promises on that very account's balance and permissions), an owner who redeploys malicious code effectively gains the ability to drain or hijack the balance of every account that had previously opted in to their global contract — with no per-user gate, similar in spirit to the escrow `approve()` bug where a single privileged party can, at will, redirect value belonging to others.

### Impact Explanation
Any account that referenced a global contract by `AccountId` is permanently exposed to the deploying account's future updates. A malicious or subsequently-compromised owner can push new code that transfers away balances, deletes access keys, or otherwise abuses the full on-chain authority of every account still resolving `AccountContract::GlobalByAccount(id)` to that code — a concrete unauthorized-value-movement vector reachable purely by ordinary transactions (`DeployGlobalContractAction` + `UseGlobalContractAction`), not requiring any privileged/validator/protocol-admin role.

### Likelihood Explanation
Likelihood depends on adoption: an attacker (or a legitimate deployer later compromised) needs other accounts to have called `UseGlobalContractAction` against their `AccountId`-mode global contract. This is a realistic social-engineering/supply-chain scenario (e.g., publishing a seemingly useful shared library/global contract that many accounts adopt for storage savings), then redeploying malicious code later. No special privilege beyond normal transaction submission is required at any step, and no additional confirmation/consent is required from already-opted-in accounts at redeploy time.

### Recommendation
Introduce an explicit "pin" or opt-in-per-version mechanism for `GlobalContractIdentifier::AccountId` consumers — e.g., have `UseGlobalContractAction` capture the nonce/version at time of adoption, and require accounts to explicitly re-`Use` the contract to accept a newer version, rather than silently inheriting all future redeployments from the owner. At minimum, surface prominent warnings/telemetry when accounts are using contracts whose code changed after adoption, and consider restricting `AccountId`-mode updates (e.g., requiring a timelock or multi-sig on the owner account) to reduce the rug-pull blast radius.

### Proof of Concept
1. Attacker account `A` deploys a benign, useful contract as a global contract with `deploy_mode: GlobalContractDeployMode::AccountId` [7](#0-6) .
2. Victim accounts `B`, `C`, ... call `UseGlobalContractAction { contract_identifier: GlobalContractIdentifier::AccountId(A) }`, setting `AccountContract::GlobalByAccount(A)` on their own accounts [8](#0-7) .
3. Time passes; `B`, `C` trust and keep using the shared code (mirrored by the update test at `test_global_contract_update`) [6](#0-5) .
4. Attacker `A` submits a second `DeployGlobalContractAction` with the same `deploy_mode: AccountId`, this time containing code that, when triggered (e.g., on any method call, or via a method the victims routinely call), issues `Promise::new(A).transfer(env::account_balance())` from the calling account's own context.
5. Because `B` and `C` still resolve to `GlobalContractIdentifier::AccountId(A)` with no re-consent required, their next interaction with the "shared" contract silently executes the new, malicious code with `B`/`C`'s account authority, draining their balances to `A`.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

#[test]
fn test_global_contract_update() {
    let mut env = GlobalContractsTestEnv::setup(Balance::from_near(1000));
    let use_accounts = [env.account_shard_0.clone(), env.account_shard_1.clone()];

    env.deploy_trivial_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        env.use_global_contract(
            account,
            GlobalContractIdentifier::AccountId(env.deploy_account.clone()),
        );

        // Currently deployed trivial contract doesn't have any methods,
        // so we expect any function call to fail with MethodNotFound error
        let call_tx = env.call_global_contract_tx(account.clone(), account.clone());
        let call_outcome = env.execute_tx(call_tx);
        assert_matches!(
            call_outcome.status,
            FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
                kind: ActionErrorKind::FunctionCallError(FunctionCallError::MethodResolveError(
                    MethodResolveError::MethodNotFound
                )),
                index: _
            }))
        );
    }

    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        // Function call should be successful after deploying rs contract
        // containing the function we call here
        env.assert_call_global_contract_success(account.clone(), account.clone());
    }
}
