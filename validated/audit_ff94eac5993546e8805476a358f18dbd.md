### Title
Wallet Contract hardcodes the Address Registrar account ID with no update mechanism, allowing the address-collision safety check to be permanently bypassed if that account is ever redeployed - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The ETH-implicit `WalletContract` (near-wallet-contract) hardcodes the account ID of the "Address Registrar" contract at compile time via `include_str!` and has no on-chain method to change it. This mirrors the reported Element/APWine pattern: an external contract reference is fixed at deploy time with no upgrade path, so if that referenced contract's account is ever redeployed/reused, the calling contract's security assumption silently breaks — but here the wallet contract itself is a `wasm` resource embedded directly in the nearcore binary and used as the global contract for every ETH-implicit account on the network.

### Finding Description
`ADDRESS_REGISTRAR_ACCOUNT_ID` is baked into the compiled wallet contract as a constant string with no setter, admin method, or migration path to change it: [1](#0-0) 

Every `rlp_execute` call that emulates an EOA base-token transfer with an `address_check` uses this fixed account ID to build the cross-contract lookup call to the registrar: [2](#0-1) 

The purpose of this lookup is explicitly a security check: it confirms that the destination address does not collide with an existing *named* NEAR account before the wallet treats the transfer as a plain implicit-address transfer: [3](#0-2) 

If `env::promise_result(0)` returns `Some(account_id)` the transaction is blocked (target is a real named account); if it returns `None` the transfer proceeds unmodified. This behavior therefore depends entirely on the registrar contract deployed under the hardcoded account ID returning trustworthy answers.

Because NEAR account IDs can be deleted and later re-created by anyone, and because the wallet contract's reference to the registrar can never be updated once wallet contract WASM is baked into a released nearcore binary (per-chain, via `MAINNET`/`TESTNET`/`LOCALNET` statics), any future "upgrade" or migration of the registrar account (deletion + redeployment, intentional or accidental) permanently and irreversibly breaks the trust assumption for every already-deployed ETH-implicit wallet on that chain, exactly as described in the source report for Element/APWine: the calling contract cannot be told about the new address, and cannot be fixed without redeploying/upgrading the wallet contract logic globally (a protocol-level change), unlike a normal dApp which can just redeploy. [4](#0-3) 

### Impact Explanation
If the account behind `ADDRESS_REGISTRAR_ACCOUNT_ID` is ever deleted and recreated by an attacker with a contract that always answers `lookup` with `null`/`None` (or if the registrar's method semantics change on redeploy), every ETH-implicit wallet contract instance on that chain will believe there is never a naming collision. This defeats the very safety check the mechanism exists for and allows a malicious relayer/attacker to induce a "safe" base-token transfer to an address that in fact collides with a legitimate named account, resulting in unauthorized redirection of user funds with no way for the protocol to correct the reference short of a coordinated wallet-contract/protocol upgrade.

### Likelihood Explanation
Reaching the vulnerable code path requires no special privilege — any signer or relayer submitting an RLP-encoded transaction through `rlp_execute` with an `EOABaseTokenTransfer` that triggers `address_check` exercises this hardcoded reference. The precondition (the registrar account being deleted/recreated) is an operational event outside attacker control in the common case, which limits likelihood, but once that precondition occurs the exploit is trivial and affects every wallet contract instance simultaneously, with no per-account or per-deployment remediation possible.

### Recommendation
Do not hardcode the registrar account ID at compile time with no update path. Store it as contract state (or resolve it via a global-contract-style indirection, similar to `GlobalContractDeployMode::AccountId` used elsewhere in the runtime) so it can be safely migrated, and/or require multi-step verification (e.g., signature or governance-gated update) before trusting a new registrar address. At minimum add monitoring/invariants so that if the registrar account is ever deleted, dependent `address_check` calls fail closed rather than silently trusting whatever contract subsequently occupies that account ID.

### Proof of Concept
1. NEAR account `registrar.near` is deployed and set as `ADDRESS_REGISTRAR_ACCOUNT_ID` inside the wallet contract WASM baked into nearcore (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:27`).
2. `registrar.near` is deleted (e.g., during a legitimate migration to a new registrar implementation/account, analogous to the Element vault / APWine router "upgrade" in the source report).
3. An attacker recreates `registrar.near` and deploys a contract whose `lookup` method always returns `null`.
4. Any relayer submits an `rlp_execute` transaction for an existing ETH-implicit wallet with `EOABaseTokenTransfer{ address_check: Some(target_address) }` where `target_address` now collides with a real named account.
5. `address_check_callback` receives `maybe_account_id = None` from the compromised registrar and proceeds with the transfer as if no collision exists, per `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:161-174`, redirecting funds against the safety invariant the mechanism was designed to enforce.
