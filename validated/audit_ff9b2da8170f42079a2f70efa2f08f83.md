### Title
Unhandled NullPointerException in `UpdateAssetActuator.execute()` when `AssetIssuedID` is empty/stale under `AllowSameTokenName==0` - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateAssetActuator.java])

### Summary
`UpdateAssetActuator.execute()` unconditionally performs an `AssetIssueV2Store` lookup keyed on `accountCapsule.getAssetIssuedID()` and immediately dereferences the result, without ever checking `dynamicStore.getAllowSameTokenName()`. `validate()`, in contrast, only guarantees existence of the V1 asset (`AssetIssueStore` keyed by `AssetIssuedName`) when `AllowSameTokenName==0`, and never validates `AssetIssuedID`/V2 existence in that branch. This mismatch lets an account that legitimately passes `validate()` (has a valid V1 asset but empty/garbage `AssetIssuedID`) reach `execute()` and trigger a `NullPointerException`.

### Finding Description
- `validate()` (lines 131-139) branches on `dynamicStore.getAllowSameTokenName()`:
  - if `== 0`: only checks `account.getAssetIssuedName()` is non-empty and exists in `assetIssueStore` (V1). It does **not** check `account.getAssetIssuedID()` or `assetIssueV2Store` at all in this branch.
  - if `!= 0`: checks `AssetIssuedID`/`assetIssueV2Store` instead.
- `execute()` does not branch the same way before touching V2 data:
```
AssetIssueStore assetIssueStoreV2 = assetIssueV2Store;
assetIssueCapsuleV2 = assetIssueStoreV2.get(accountCapsule.getAssetIssuedID().toByteArray());

assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit);   // NPE if lookup returned null
```
This runs regardless of `AllowSameTokenName`, i.e., even in the `==0` code path where `validate()` never guaranteed a V2 entry exists.
- An account can have `AssetIssuedName` set (from legacy asset issuance under `AllowSameTokenName==0`) while `AssetIssuedID` is empty or stale (pointing to no `AssetIssueV2Store` entry), because nothing in `validate()`'s `==0` branch enforces consistency between the two fields.
- Consequently, `assetIssueV2Store.get(...)` returns `null`, and the immediately following `.setFreeAssetNetLimit(newLimit)` call throws an unhandled `NullPointerException`. This exception is not caught by the surrounding `try/catch` (which only catches `InvalidProtocolBufferException`), so it propagates up uncaught through `execute()`, which is declared to throw only `ContractExeException`.
- Because `execute()` is invoked during block/transaction processing on every node applying the block, an uncaught `NullPointerException` here breaks the deterministic execution contract — it is not converted into a transaction-level failure (`code.FAILED`) but instead an unhandled runtime exception, which can crash or halt processing depending on how the caller (`ActuatorFactory`/`TransactionCapsule` processing) handles it.

### Impact Explanation
An unprivileged attacker who has previously issued an asset under `AllowSameTokenName==0` (setting `AssetIssuedName`) but whose `AssetIssuedID` was never set or has become stale/empty can submit an `UpdateAssetContract` that passes `validate()` but crashes `execute()` with an NPE instead of being cleanly rejected. This is a state-machine/liveness risk: an uncaught runtime exception during block application threatens deterministic execution guarantees across nodes, potentially halting or diverging block processing rather than simply failing the single transaction.

### Likelihood Explanation
Feasibility hinges on whether the codebase can actually put an `AccountCapsule` into the state "has `AssetIssuedName` set (non-empty) but `AssetIssuedID` empty/pointing to no V2 entry" while `AllowSameTokenName==0`. This is plausible given `AssetIssuedName` and `AssetIssuedID` are separate fields set by different code paths (V1 vs V2 asset-issue flows, `UnfreezeAssetActuator`, `AssetUpdateHelper`, etc.), but I was unable to fully trace every account-mutation path (e.g., `AssetIssueActuator`, `UnfreezeAssetActuator`, `AssetUpdateHelper`) within the available tool budget to conclusively prove such divergence is reachable purely through legitimate, unprivileged transaction sequences (as opposed to only through migration/tooling code such as `AssetUpdateHelper`, which is not attacker-reachable). This uncertainty affects confidence in real-world exploitability, though the code-level defect (missing null check / inconsistent validation between `validate()` and `execute()`) is clearly present and reproducible via a crafted `AccountCapsule` state in a unit test.

### Recommendation
In `execute()`, guard the V2 lookup and mutation the same way `validate()` does: only perform the `assetIssueV2Store` lookup/mutation when `AllowSameTokenName != 0` (or, defensively, always null-check `assetIssueCapsuleV2` before dereferencing it and throw a `ContractExeException` if null, mirroring the `==0`/`!=0` branching used in `validate()`). Ensure `execute()`'s branching structure exactly matches `validate()`'s so that any state validated as consistent is the same state mutated.

public void testExecuteWithEmptyAssetIssuedIDUnderAllowSameTokenNameZero()
    throws ContractExeException {

  dbManager.getDynamicPropertiesStore().saveAllowSameTokenName(0);

  // 2. Craft AccountCapsule with AssetIssuedName set (valid V1 asset) but
  //    AssetIssuedID empty/garbage (no corresponding AssetIssueV2Store entry).
  AccountCapsule accountCapsule = ... // build with AssetIssuedName = "abc",
                                       // AssetIssuedID = ByteString.EMPTY
  dbManager.getChainBaseManager().getAccountStore().put(ownerAddress, accountCapsule);

  AssetIssueCapsule v1Asset = new AssetIssueCapsule(/* name = "abc" */);
  dbManager.getChainBaseManager().getAssetIssueStore()
      .put(v1Asset.createDbKey(), v1Asset);
  // Deliberately do NOT put anything into assetIssueV2Store for AssetIssuedID.

  // 3. Build UpdateAssetContract referencing ownerAddress.
  UpdateAssetActuator actuator = new UpdateAssetActuator();
  actuator.setChainBaseManager(dbManager.getChainBaseManager());
  actuator.setAny(getUpdateAssetContract(ownerAddress, ...));

  // 4. validate() should pass (only V1 checked under AllowSameTokenName==0).
  Assert.assertTrue(actuator.validate());

  // 5. execute() currently throws an unhandled NullPointerException instead of
  //    a handled ContractExeException — this test documents the bug:
  TransactionResultCapsule ret = new TransactionResultCapsule();
  try {
    actuator.execute(ret);
    Assert.fail("Expected exception due to missing V2 asset entry");
  } catch (NullPointerException npe) {
    Assert.fail("BUG: uncaught NullPointerException propagated from execute(), "
        + "expected a handled ContractExeException instead");
  } catch (ContractExeException expected) {
    // desired behavior after fix
  }
}
