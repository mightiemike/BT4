### Title
Function-call receipts can exceed `max_receipt_size` via post-validation mutation (`output_data_receivers`/return value), bypassing the size limit like the Discourse HTML-comment `max_length` bypass - ([File: test-loop-tests/src/tests/max_receipt_size.rs])

### Summary
The Discourse bug let users exceed a `max_length` limit because content (HTML comments) was added/counted after the length check ran, so the check didn't reflect the final content. nearcore has the same class of bug: `max_receipt_size` is validated on a receipt at creation time, but the receipt is later mutated — `output_data_receivers` are appended when a dependent promise is created (`ReceiptManager::create_action_receipt`, which does `.output_data_receivers.push(...)` on an *already-created* receipt), and a callback's returned value is likewise attached after the size check. In both cases the size check is performed before the final content is added, so the final on-chain/in-witness receipt exceeds `max_receipt_size` without being rejected.

### Finding Description
`ReceiptManager::create_action_receipt` mutates an existing action receipt's `output_data_receivers` in place to record where a dependent promise's output should be delivered: [1](#0-0) 
This happens after the original receipt (already at or near `max_receipt_size`) was constructed and would have already passed its own size validation. Adding `output_data_receivers` afterward, or attaching a large return value via `promise_return`, pushes the effective serialized receipt size above `max_receipt_size` — but this after-the-fact growth is not re-validated. The maintainers themselves documented and reproduced this exact class of bug in the test suite: [2](#0-1) [3](#0-2) 
Both tests construct a receipt that is exactly at `max_receipt_size` at creation, then have the runtime append/attach additional content (`output_data_receivers` for a promise `.then()` chain, or a large returned value wrapped in a `DataReceipt`) that is not covered by the original size check, growing the receipt past the configured limit while `assert_oversized_receipt_occurred` shows the node still processes it (i.e., the limit is silently bypassed) rather than rejecting the receipt outright as `ReceiptSizeExceeded` would require.

This is structurally identical to the Discourse issue: a size/length gate that is evaluated before the full final content is assembled, letting an attacker construct content that is nominally within the limit at validation time, but exceeds it once additional (uncounted) content is appended.

### Impact Explanation
`max_receipt_size` exists specifically to bound `ChunkStateWitness` size (per `docs/misc/state_witness_size_limits.md`, receipts must stay below 4 MiB "otherwise they'll be considered invalid and rejected"). A receipt that silently exceeds this bound after validation can inflate `ChunkStateWitness` beyond the design budget (~21 MiB total), risking outsized witnesses that are costly/slow to distribute and validate, and — because the check-vs-actual-size mismatch is deterministic given the same inputs — can be triggered reliably by any account calling a contract that creates a DAG of promises (`.then()` chaining) or returns a large value from a callback, i.e., by an ordinary unprivileged contract caller, not a validator or network-layer attacker. This is a reachable, transaction-triggered defect in state-witness size accounting; a version-mismatch of a hard size limit is comparable in class to the invalid-state-transition-acceptance category (a receipt that should be rejected outright is instead accepted and executed).

### Likelihood Explanation
High likelihood of reachability: any account can deploy the standard test/production contract patterns (chained `.then()` promises or `promise_return`) to construct a receipt at the size boundary and trigger the bug deterministically, as demonstrated by the maintainers' own reproduction tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`). No special privileges, validator access, or network manipulation are required — a single signed transaction from a funded account suffices.

### Recommendation
Re-validate (or account for) receipt size after any post-construction mutation: specifically, after `create_action_receipt` appends to `output_data_receivers`, and after a callback's return value is wrapped into a `DataReceipt`/promise result, re-check the resulting serialized size against `max_receipt_size` and fail the action (returning `ReceiptSizeExceeded`) before the receipt is emitted, rather than only checking size at initial receipt construction. Alternatively, reserve budget for the maximum possible `output_data_receivers`/return-value growth when performing the original size check, so the checked bound already accounts for all content that will eventually be added.

### Proof of Concept
The maintainers' own test suite already contains a working, deterministic PoC: [4](#0-3) 
1. Deploy the standard test contract.
2. Compute `args_size` so that the initial function-call receipt (`ActionReceipt` with a single `FunctionCall` action) is exactly `max_receipt_size` (4 MiB) bytes when borsh-serialized.
3. Call `max_receipt_size_promise_return_method1`, which builds a promise DAG `[A -then-> B]`; when `A` executes it creates a new promise `C` and calls `promise_return`, changing the DAG to `[C -then-> B]`. Receipt `C` is already at the max size; NEAR then appends `output_data_receivers` to link `C` to `B`, growing `C` beyond `max_receipt_size`.
4. Observe (via `assert_oversized_receipt_occurred`) that the oversized receipt is processed rather than rejected with `ReceiptSizeExceeded`, confirming the bypass — referenced by the maintainers as tracked in https://github.com/near/nearcore/issues/12606.

Note: I could not locate the exact code path in the runtime that performs the *initial* `ReceiptSizeExceeded` check (only its error definition and config value were found in this pass), so I cannot cite the precise validation call site that is skipped on the mutation path; this is a limitation of the current search and would need direct file review of `runtime/runtime/src/lib.rs` / `runtime/runtime/src/actions.rs` around promise resolution to pinpoint exactly where the missing re-check should be inserted.

#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
