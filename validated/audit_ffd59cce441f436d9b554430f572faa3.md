### Title
Self-matched market orders cause silent loss of user tokens due to stale in-memory `AccountCapsule` overwrite - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator` caches the taker's `AccountCapsule` in memory at the start of `execute()`, applies both sell-side and buy-side balance changes to that in-memory object during order matching, and finally persists it with a single `accountStore.put()` call after the whole matching loop finishes. However, when the order book match loop processes a *maker* order, the maker side is credited via a separate helper that re-reads the account from `accountStore` and writes it back immediately. If the taker's address is also the owner of a matched maker order (a self-trade), the maker-side credit is persisted to the store mid-loop, and then unconditionally clobbered by the stale, pre-credit in-memory taker `AccountCapsule` written at the end of `execute()` — losing the tokens/TRX that were credited to the maker side of the same account.

### Finding Description
In `execute()`, the taker's account is loaded once: [1](#0-0) 

`transferBalanceOrToken` debits the sell amount and fee from this in-memory object, then `matchOrder`/`matchSingleOrder` is invoked, and only at the very end is `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` called to persist it.

Inside `matchSingleOrder`, the taker side is credited on the passed-in in-memory object: [2](#0-1) 

but the maker side is credited through a *different* overload of `addTrxOrToken` that independently fetches the account from `accountStore`, mutates it, and immediately writes it back: [3](#0-2) 

If `takerAccountCapsule`'s address equals `makerOrderCapsule.getOwnerAddress()` (i.e., the same account is both the taker and the owner of a matched resting order — a self-trade), the maker-side `addTrxOrToken` call re-reads the account (which at that point in the DB still reflects only the *pre-match* state, since the taker's in-memory changes have not yet been committed), adds the maker credit, and persists it. Then, once the matching loop completes, `execute()` overwrites the account in the store with the taker's in-memory `accountCapsule` object (line 148), which does **not** include the maker-side credit that was just written to the store — permanently discarding it. This mirrors the reported `batchTransfer` bug: a local/in-memory balance snapshot taken before a loop, updated only for one "role", is written back after the loop and silently erases in-loop updates that were applied through a different code path to the same underlying account.

Nothing in `validate()` rejects self-matching; there is no check comparing the taker's `ownerAddress` against maker order owners in the matched price levels: [4](#0-3) 

### Impact Explanation
A user can permanently and silently lose tokens/TRX that should have been credited to them as the maker side of a self-matched trade, corrupting account accounting on-chain. Because `MarketSellAssetActuator` is reachable directly from a broadcast transaction (`MarketSellAssetContract`), this is an unprivileged, remotely triggerable state-transition bug that causes real asset loss for the exploiting/affected account, and could also be leveraged to desynchronize expected balances versus persisted state (accounting corruption) across the market feature.

### Likelihood Explanation
Any account that has previously placed a resting order on the opposite pair (e.g., sell A for B) can trigger the bug by later placing another order (sell B for A) at a matching price — a natural, easily reachable usage pattern (a user managing multiple orders on the same trading pair), requiring no special privileges, keys, or malicious peers. It only requires ordinary transaction broadcast.

### Recommendation
- Add a check in `matchSingleOrder`/`matchOrder` (or in `validate()`) that rejects or specially handles the case where `makerOrderCapsule.getOwnerAddress()` equals the taker's `ownerAddress`, mirroring the report's suggested `require(addr != msg.sender)` mitigation.
- More robustly, refactor `addTrxOrToken` so that all balance mutations for a single transaction/account are applied to one canonical in-memory `AccountCapsule` (looked up once, e.g., via a map keyed by address) and persisted once at the very end, instead of mixing an interim `accountStore.get`/`put` for maker accounts with a final unconditional `put` of the taker's stale in-memory object.

### Proof of Concept
1. Account `A` places order O1: sell token `X` amount 100, buy token `Y` amount 200 (creates a resting maker order in the `Y->X` pair-price book once matched against, but first just sits as a sell order for X/Y).
2. Account `A` later places order O2: sell token `Y` amount 200, buy token `X` amount 100, at a price that matches O1 (opposite pair, matching price ratio), triggering `execute()`:
   - `accountCapsule` for `A` is loaded and debited by `sellTokenQuantity` (200 `Y`) + fee.
   - `matchOrder` finds O1 (owned by `A`) as a maker match.
   - `matchSingleOrder` credits the taker (`A`, via in-memory `accountCapsule`) with the received `X` tokens, and separately credits the maker (`A` again, via `accountStore.get`+`put`) with the received `Y` tokens — this write goes to the DB immediately, based on the state before O2's debit was applied.
   - After the match loop, `execute()` calls `accountStore.put(accountCapsule.createDbKey(), accountCapsule)`, overwriting `A`'s account with the in-memory object that has the `X` credit but lacks the `Y` maker credit just written to the store.
3. Result: `A`'s final on-chain balance is missing the `Y` tokens that should have been received as the maker in the self-trade, matching the same-class bug in the reported `batchTransfer` (payment to `msg.sender` silently lost when the sender is both payer and payee within the same loop-processed operation).
