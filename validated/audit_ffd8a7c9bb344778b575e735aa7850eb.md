## Analysis

The report's root cause is a **binding failure**: security-critical fields (which token/order the permit applies to) are accepted from an untrusted side channel instead of being cryptographically bound to the specific transaction being authorized. Signature/HMAC validation covered only part of the intended data, so material signed for context A could be replayed for context B.

The closest analog in `shopify-app-js` is in the webhook verification pipeline, where the HMAC is computed over the raw body only, while the `domain` and `topic` headers used to load a specific shop's session and dispatch app logic are never included in, or bound to, that signature. ### Title
Webhook HMAC signs only the raw body, letting a malicious app installer replay it with forged `domain`/`topic` headers to impersonate another shop's webhook - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
`validateHmacFromRequestFactory` computes the webhook HMAC exclusively over `rawBody`, using the app's `apiSecretKey`, which is shared across every shop that installs the app. The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers are read afterward by `checkWebhooksHeaders`/`checkEventsHeaders` but are never included in, or bound to, the signed material. `authenticateWebhookFactory` then trusts `check.domain` to look up and return another shop's stored offline session (and a live `admin` API client for it), and trusts `check.topic` to route to whatever business logic the app registered for that topic.

### Finding Description
This mirrors the reported DeFi bug exactly at the architectural level: an authenticated artifact (permit / HMAC) that was legitimately produced for one context (order B / shop A) can be paired with metadata describing a different context (order A / shop B) because the verification only checks internal consistency of the artifact itself, not its binding to the specific context fields used downstream.

- `validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-200` fetches the `hmac` header and compares it against `HMAC(apiSecretKey, rawBody)` only.
- `checkWebhooksHeaders`/`checkEventsHeaders` in `packages/apps/shopify-api/lib/webhooks/validate.ts:99-204` pull `domain`, `topic`, and `webhookId` straight from unauthenticated headers with no cross-check against the signed body.
- `authenticateWebhookFactory` in `packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts:52` calls `ensureValidOfflineSession(params, check.domain)` — i.e., it loads whatever shop's session corresponds to the attacker-supplied `domain` header — and then builds an authenticated `admin` client (`adminClientFactory`) from that session, and dispatches on `check.topic`, which is likewise attacker-supplied.

Because `apiSecretKey` is one value shared by the whole app (not per-shop), any merchant who installs the app can trigger a real Shopify webhook against their own store to obtain a valid `(rawBody, hmac)` pair, then send that exact pair directly to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain (public/guessable, e.g. `victim.myshopify.com`) and `X-Shopify-Topic` with any topic they want the app to act on. The HMAC still validates because it never covered those headers.

### Impact Explanation
A successful forgery causes the app to:
- Load the **victim shop's real offline session and access token** via `ensureValidOfflineSession`/`adminClientFactory`, and
- Execute the app's webhook business logic for an attacker-chosen `topic` (e.g. re-triggering uninstall cleanup, GDPR data-request handling, order/fulfillment side effects) as if it legitimately came from the victim shop, using attacker-controlled `payload` content.

This is a cross-tenant confused-deputy: a single malicious/unprivileged app installer can cause the app to act on behalf of another merchant's authenticated session, potentially leaking or mutating that merchant's data — directly analogous to the taker in the original report draining a maker's tokens meant for a different order.

### Likelihood Explanation
Requires only: (1) the attacker installs the app on their own store (an unprivileged, ordinary onboarding action), (2) the attacker triggers or intercepts one webhook delivery to their own endpoint to obtain a valid `(rawBody, hmac)` pair, and (3) knowledge of a target shop's `myshopify.com` domain, which is public. No secret material, MITM position, or privileged access is required beyond being a regular app user — matching the "single merchant" unprivileged-actor threshold.

### Recommendation
Bind the routing/session-selection headers to the signed payload instead of trusting them independently:
- Include `domain`, `topic`, and `webhookId`/`eventId` in the HMAC input (as Shopify's newer webhook formats and other providers do), or
- At minimum, cross-validate the `domain` header against an expected/allow-listed shop (e.g., the shop tied to the session actually being loaded) before constructing an `admin` client, and treat `topic`/`domain` as untrusted unless covered by the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, giving the app an offline session for that shop.
2. Attacker performs an action that fires a real webhook (e.g. update a product), capturing `rawBody` and the resulting `X-Shopify-Hmac-Sha256` value — both valid under the shared `apiSecretKey`.
3. Attacker POSTs to the app's webhook endpoint with the same `rawBody` and `hmac`, but sets:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled` (or any topic the app handles)
4. `validateHmacFromRequestFactory` succeeds (HMAC only checked `rawBody`). `checkWebhooksHeaders` returns `domain: 'victim.myshopify.com'`, `topic: 'APP_UNINSTALLED'`.
5. `authenticateWebhookFactory` loads `victim.myshopify.com`'s stored offline session, builds an authenticated `admin` client for it, and invokes the app's handler registered for `APP_UNINSTALLED` with attacker-controlled `payload`, acting on the victim's session/data.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
